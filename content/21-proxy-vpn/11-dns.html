وب‌سایت داخلی باز نمی‌شود، یا query از مسیر دیگری رفت؟The internal site fails—or the DNS query took another path?

VPN handshake دارد و route به subnet سازمانی هم نصب شده. آدرس IP کار می‌کند، ولی `wiki.lab.test` resolve نمی‌شود. شاید resolver لپ‌تاپ هنوز DNS عمومی باشد؛ شاید suffix به DNS داخلی برود ولی route آن resolver بیرون tunnel باشد. این فصل دربارهٔ DNS tunneling مخفیانه نیست؛ دربارهٔ فرستادن پرس‌وجوی DNS از مسیر و resolver موردنظر است.

The VPN has a handshake and a route to the organization subnet. The IP works, but `wiki.lab.test` does not resolve. The laptop may still use public DNS, or the private suffix may choose an internal resolver whose route bypasses the tunnel. This chapter is not about covert DNS tunneling; it is about sending DNS queries to the intended resolver over the intended path.

دو تصمیم جدا داریم: کدام resolver برای این نام پاسخ می‌دهد؟ و route به آن resolver از کدام interface می‌رود؟ split tunnel فقط route برنامه را تعیین نمی‌کند؛ سیستم ممکن است برای domainهای مختلف resolver متفاوت انتخاب کند.

There are two separate decisions: which resolver answers this name, and which interface routes packets to that resolver? A split tunnel does not determine only application routes; a system may choose different resolvers for different domains.

resolver selection و route به resolver جدا هستند؛ هر دو را با capture ثابت کن.

Resolver selection and route to that resolver are separate; verify both with packet captures.

resolv.conf همیشه فهرست نهایی DNS نیستresolv.conf is not always the final resolver policy

روی بسیاری از Linuxها `systemd-resolved` برای هر link DNS و routing domain نگه می‌دارد و `/etc/resolv.conf` ممکن است فقط به stub `127.0.0.53` اشاره کند. برنامه از stub می‌پرسد؛ resolved بر اساس domain/link انتخاب می‌کند. در سیستم‌های دیگر NetworkManager, resolvconf, VPN client یا libc رفتار متفاوتی دارند. فایل را تنها شاهد فرض نکن؛ ابتدا وضعیت resolver واقعی را ببین.

On many Linux systems, `systemd-resolved` tracks DNS servers and routing domains per link, while `/etc/resolv.conf` may point only to the local stub at 127.0.0.53. Applications query that stub; resolved selects a link/domain. Other systems may use NetworkManager, resolvconf, a VPN client, or different libc behavior. Do not treat the file as the whole policy—inspect the active resolver.

resolvectl status
resolvectl dns
resolvectl domain

به interface VPN، DNS server، routing domain و default route setting توجه کن. خروجی نشان می‌دهد systemd-resolved چه configی دارد؛ اپی که DoH خودش را پیاده کرده ممکن است اصلاً از آن عبور نکند. روی Windows، macOS و Android فرمان دیگری لازم است و VPN client ممکن است resolver را خودش مدیریت کند.

Inspect the VPN link, DNS server, routing domain, and default-route settings. This shows systemd-resolved’s configuration; an application with its own DoH may bypass it. Windows, macOS, and Android use different tools, and their VPN clients may manage DNS themselves.

DNS خصوصی را در lab کوچک بسازCreate a small private DNS lab

روی gateway آزمایشی که IP تونلش `10.77.0.1` است و interface به نام `wg0` دارد، یک DNS server محلی برای suffix lab بالا بیاور. این command نمونه از dnsmasq است؛ فقط روی disposable VM اجرا کن و مطمئن شو port 53 آزاد است. آن را روی interface عمومی bind نکن:

On a disposable gateway with tunnel IP 10.77.0.1 and interface wg0, run a local DNS server for the lab suffix. This example uses dnsmasq; first confirm port 53 is free. Never bind it to a public interface:

sudo dnsmasq --no-daemon --interface=wg0 --bind-interfaces --listen-address=10.77.0.1 --no-resolv --local=/lab.test/ --address=/lab.test/10.77.0.10

dnsmasq باید روی tunnel IP گوش کند و برای نام lab.test آدرس آزمایشی بدهد. host 10.77.0.10 را در lab بساز و UDP/TCP 53 را فقط داخل tunnel اجازه بده. اگر server start نشد، log و listener port را بررسی کن؛ firewall را عمومی باز نکن. این response فقط local DNS mapping را ثابت می‌کند، نه اتصال به web host.

dnsmasq should listen on the tunnel address and answer lab.test with the test IP. Create 10.77.0.10 in the lab and allow UDP/TCP 53 only inside the tunnel. If it fails to start, inspect logs and port ownership; do not open DNS publicly. This response proves a local mapping, not connectivity to the web host.

روی client، اول direct query را با `dig @10.77.0.1 wiki.lab.test A` بزن. مقصد 10.77.0.1 باید از VPN route شود. اگر جواب آمد، server پاسخ می‌دهد؛ هنوز OS resolver و اپ را تنظیم نکرده‌ای. در خروجی بخش `SERVER:` را بخوان و بعد route به همین resolver را با `ip route get 10.77.0.1` بررسی کن.

On the client, first query explicitly with `dig @10.77.0.1 wiki.lab.test A`. The destination 10.77.0.1 must route through the VPN. A response proves the server answers; it has not configured the OS resolver or application. Read `SERVER:` in dig output and inspect the route to this resolver with `ip route get 10.77.0.1`.

Split DNS: فقط suffix خصوصی به resolver داخل tunnelSplit DNS: send only the private suffix to the tunnel resolver

در systemd-resolved روی disposable client، DNS interface tunnel را موقتاً تنظیم کن و `~lab.test` را به‌عنوان route-only domain بده. tilde می‌گوید این suffix برای انتخاب resolver است؛ خودش search suffix برای کوتاه‌نویسی hostname نیست. interface و resolver IP را از lab خودت جایگزین کن:

On a disposable client using systemd-resolved, temporarily set the VPN link’s DNS server and assign `~lab.test` as a route-only domain. The tilde selects a resolver for that suffix; it is not a search suffix for expanding short hostnames. Substitute your lab interface and resolver address:

sudo resolvectl dns wg0 10.77.0.1
sudo resolvectl domain wg0 '~lab.test'
resolvectl status wg0

حالا `resolvectl query wiki.lab.test` و یک دامنهٔ عمومی را جدا اجرا کن. private query باید به link VPN برسد؛ public query طبق policy باقی سیستم برود. `resolvectl status` و packet capture شواهد resolver selection/path هستند. cache را پیش از تکرار با `resolvectl flush-caches` پاک کن؛ وگرنه پاسخ قبلی می‌تواند query جدیدی روی wire نفرستد.

Run `resolvectl query wiki.lab.test` and a public name separately. The private query should use the VPN link; the public query follows the rest of the system policy. `resolvectl status` and packet captures provide resolver/path evidence. Clear cached data with `resolvectl flush-caches` before repeating, or a cached response may generate no new wire query.

sudo resolvectl flush-caches
resolvectl query wiki.lab.test
resolvectl query example.com
sudo tcpdump -ni wg0 port 53
sudo tcpdump -ni eth0 port 53

در capture روی wg0 باید private DNS query دیده شود؛ روی eth0 نباید همان query plain خارج شود. در full tunnel، ممکن است query هم روی wg0 دیده شود ولی plain آنجا قابل مشاهده باشد—داخل مسیر VPN روی سیم بیرونی، payload باید encapsulated/encrypted باشد. capture روی wg0 در نقطهٔ endpoint بعد از decrypt انجام می‌شود؛ این تناقض نیست.

The private query should appear on wg0 and not escape in plaintext on eth0. In a full tunnel, it may be visible as plaintext on wg0 after decryption while the outer physical link carries encrypted encapsulated traffic. A capture at the tunnel endpoint sees the inner packet after decryption; that is not a contradiction.

خرابی عمدی: resolver هنوز بیرون tunnel استDeliberate failure: the resolver still points outside the tunnel

در client آزمایشی routing domain خصوصی را بردار یا DNS بیرونی را به link اولویت‌دار تبدیل کن؛ پیش از تغییر، `resolvectl status` و captureهای هر دو interface را ذخیره کن. `wiki.lab.test` باید fail/NXDOMAIN بدهد یا درخواست روی interface فیزیکی دیده شود. این دو نشانه را یکی ندان: ممکن است query درست به resolver نادرست رفته و NXDOMAIN گرفته، یا اصلاً نام local resolve نشده باشد.

On the test client, remove the private routing domain or prioritize the outside resolver; first save `resolvectl status` and captures on both interfaces. `wiki.lab.test` may fail/NXDOMAIN or appear on the physical interface. Do not conflate those symptoms: a query may reach the wrong resolver and get NXDOMAIN, or local resolution may fail before a query is sent.

بعد از ثبت evidence، DNS server و `~lab.test` را روی wg0 دوباره تنظیم کن، cache را پاک کن و همان query و capture را تکرار کن. اگر query اصلاً از client خارج نشده، app-specific cache/DoH و name syntax را بررسی کن. failure عمدی فقط وقتی آموزنده است که نتیجه را واقعاً مشاهده کنی؛ خروجی نمونه را به‌جای دستگاه خودت ننویس.

After capturing evidence, restore the VPN DNS server and `~lab.test` on wg0, flush caches, and repeat the same query/capture. If no query leaves the client, inspect application-specific cache/DoH and the name itself. The deliberate failure is useful only when you observe it—never substitute sample output for your own.

DNS داخل VPN رمز است؟ نسبت به کدام ناظر؟Is DNS inside a VPN encrypted—and from which observer?

DNS معمولی با UDP/TCP 53 خودش رمزنگاری نمی‌شود. اگر query داخل VPN افتاد، tunnel آن را روی بخش client→VPN gateway می‌پوشاند؛ اما پس از خروج tunnel، DNS server یا network خروجی ممکن است query را ببیند. DoT/DoH/DoQ رمزنگاری جداگانهٔ client→resolver می‌دهند، ولی resolver مقصد همچنان نام را می‌داند و resolver selection/route policy باید درست باشد. encrypted DNS و correct split DNS دو سؤال مستقل‌اند.

Ordinary DNS over UDP/TCP 53 is not encrypted by itself. If routed through a VPN, the tunnel protects it on the client-to-gateway segment; after tunnel exit, the DNS server or egress network may see the query. DoT/DoH/DoQ provide separate client-to-resolver encryption, but the resolver still learns the name and routing policy must be correct. Encrypted DNS and correct split DNS are independent questions.

اپ‌هایی با built-in DoH ممکن است از system resolver و `resolvectl` عبور نکنند؛ browser policy، proxy/VPN app و OS را جدا بررسی کن. صرف اینکه port 53 در capture نیست ثابت نمی‌کند query امن یا از مسیر درست رفته—ممکن است HTTPS به resolver دیگری رفته باشد.

Applications with built-in DoH may bypass the system resolver and `resolvectl`; check browser, proxy/VPN app, and OS policies separately. Seeing no port 53 packet does not prove a query is encrypted or routed correctly—it may be HTTPS to an unintended resolver.

VPN tool باید DNS را هم به OS معرفی کندA VPN client must also integrate DNS policy with the OS

OpenVPN می‌تواند DNS option را push کند، ولی client platform باید آن را پشتیبانی و اعمال کند؛ WireGuard config هسته‌ای DNS directive ندارد، در حالی که `wg-quick` و appهای mobile قابلیت جدا دارند. روی systemd-resolved، NetworkManager، Windows و macOS روش‌ها فرق می‌کند. config tunnel موفق به‌تنهایی resolver system را عوض نمی‌کند. از docs همان client/provider و status محلی استفاده کن.

OpenVPN can push DNS options, but the client platform must support and apply them. WireGuard’s core config has no DNS directive, while `wg-quick` and mobile apps may provide separate integration. systemd-resolved, NetworkManager, Windows, and macOS differ. A successful tunnel configuration does not itself change the system resolver; consult the exact client/platform docs and inspect local state.

cleanup: فقط تنظیم موقتی همین link را برگردانCleanup: revert only this temporary link setting

پس از جمع‌آوری evidence، settingهای موقتی systemd-resolved را برگردان. روی disposable client فرمان `resolvectl revert wg0` تنظیم DNS/domain موقتی link را حذف می‌کند؛ status را دوباره بخوان و ببین resolver قبلی برگشت. DNS server lab را هم با Ctrl+C متوقف کن. اگر VPN client خودش settingها را sync می‌کند، cleanup را با همان client انجام بده تا دو manager با هم بجنگند.

After preserving evidence, revert temporary systemd-resolved link settings. On the disposable client, `resolvectl revert wg0` removes temporary DNS/domain settings for that link; inspect status again and confirm the prior resolver returned. Stop the lab DNS server with Ctrl+C. If a VPN client manages settings itself, use its own cleanup path to avoid competing managers.

معیار

اسم resolve شدن، مسیر را لو نمی‌دهدA resolved name does not reveal its path

برای هر DNS lookup چهار چیز را ثبت کن: application/resolver؛ domain policy؛ route به resolver؛ interfaceای که query از آن دیده شد. systemd-resolved یک مدل per-link مفید دارد، ولی همهٔ OSها و appها از آن پیروی نمی‌کنند. cache را کنترل کن، DoH را فراموش نکن و capture را روی مسیر درست بگیر. با این evidence می‌توانی DNS leak را از نبود zone، route خرابی یا resolver cache جدا کنی.

For each DNS lookup, record four things: application/resolver, domain policy, route to resolver, and the interface where the query appeared. systemd-resolved offers a useful per-link model, but not every OS or app follows it. Control cache, consider DoH, and capture the correct path. This evidence separates leaks from a missing zone, route failure, or resolver cache.
