DNS inside a tunnel

IP کار می‌کنه، ولی اسم نه؛ یعنی وقتشه DNS رو جدا از خود tunnel ببینیم.

DNS leaks—and how to route queries deliberately.

وب‌سایت داخلی باز نمی‌شه، یا query از مسیر دیگری رفت؟The internal site fails—or the DNS query took another path?

VPN وصله و حتی به IP سرویس داخلی هم می‌رسی، ولی `wiki.lab.test` باز نمی‌شه. اولین واکنش معمولاً اینه که بگیم «DNS خرابه». خب، کدوم بخشش؟ سیستم اصلاً از کدوم resolver پرسیده؟ query از کدوم interface رفته؟ route خود resolver چی بوده؟ این فصل همین دو سؤال رو از هم جدا می‌کنه: چه کسی اسم رو resolve می‌کنه و packet رسیدن به اون resolver از کجا رد می‌شه.

The VPN has a handshake and a route to the organization subnet. The IP works, but `wiki.lab.test` does not resolve. The laptop may still use public DNS, or the private suffix may choose an internal resolver whose route bypasses the tunnel. This chapter is not about covert DNS tunneling; it is about sending DNS queries to the intended resolver over the intended path.

دو تصمیم جدا داریم: کدوم resolver برای این نام پاسخ می‌ده؟ و route به اون resolver از کدوم interface می‌ره؟ split tunnel فقط route برنامه رو تعیین نمی‌کنه؛ سیستم ممکنه برای domainهای مختلف resolver متفاوت انتخاب کند.

There are two separate decisions: which resolver answers this name, and which interface routes packets to that resolver? A split tunnel does not determine only application routes; a system may choose different resolvers for different domains.

resolver selection و route به resolver جدا هستن؛ هر دو رو با capture ثابت کن.

Resolver selection and route to that resolver are separate; verify both with packet captures.

resolv.conf همیشه فهرست نهایی DNS نیستresolv.conf is not always the final resolver policy

روی بسیاری از Linuxها `systemd-resolved` برای هر link DNS و routing domain نگه می‌داره و `/etc/resolv.conf` ممکنه فقط به stub `127.0.0.53` اشاره کند. برنامه از stub می‌پرسد؛ resolved بر اساس domain/link انتخاب می‌کنه. در سیستم‌های دیگر NetworkManager, resolvconf, VPN client یا libc رفتار متفاوتی دارن. فایل رو تنها شاهد فرض نکن؛ ابتدا وضعیت resolver واقعی رو ببین.

On many Linux systems, `systemd-resolved` tracks DNS servers and routing domains per link, while `/etc/resolv.conf` may point only to the local stub at 127.0.0.53. Applications query that stub; resolved selects a link/domain. Other systems may use NetworkManager, resolvconf, a VPN client, or different libc behavior. Do not treat the file as the whole policy—inspect the active resolver.

resolvectl status
resolvectl dns
resolvectl domain

به interface VPN، DNS server، routing domain و default route setting توجه کن. خروجی نشان می‌ده systemd-resolved چه configی داره؛ اپی که DoH خودش رو پیاده کرده ممکنه اصلاً از اون عبور نکند. روی Windows، macOS و Android فرمان دیگری لازمه و VPN client ممکنه resolver رو خودش مدیریت کند.

Inspect the VPN link, DNS server, routing domain, and default-route settings. This shows systemd-resolved’s configuration; an application with its own DoH may bypass it. Windows, macOS, and Android use different tools, and their VPN clients may manage DNS themselves.

DNS خصوصی رو در آزمایشگاه کوچک بسازCreate a small private DNS lab

روی gateway آزمایشی که IP تونلش `10.77.0.1` هست و interface به نام `wg0` داره، یک DNS server محلی برای suffix آزمایشگاه بالا بیاور. این command نمونه از dnsmasq هست؛ فقط روی موقتی VM اجرا کن و مطمئن شو port 53 آزاد هست. اون رو روی interface عمومی bind نکن:

On a disposable gateway with tunnel IP 10.77.0.1 and interface wg0, run a local DNS server for the lab suffix. This example uses dnsmasq; first confirm port 53 is free. Never bind it to a public interface:

sudo dnsmasq --no-daemon --interface=wg0 --bind-interfaces --listen-address=10.77.0.1 --no-resolv --local=/lab.test/ --address=/lab.test/10.77.0.10

dnsmasq باید روی tunnel IP گوش کند و برای نام lab.test آدرس آزمایشی بدهد. host 10.77.0.10 رو در آزمایشگاه بساز و UDP/TCP 53 رو فقط داخل tunnel اجازه بده. اگه server start نشد، log و listener port رو بررسی کن؛ firewall رو عمومی باز نکن. این response فقط local DNS mapping رو ثابت می‌کنه، نه اتصال به web host.

dnsmasq should listen on the tunnel address and answer lab.test with the test IP. Create 10.77.0.10 in the lab and allow UDP/TCP 53 only inside the tunnel. If it fails to start, inspect logs and port ownership; do not open DNS publicly. This response proves a local mapping, not connectivity to the web host.

روی client، اول direct query رو با `dig @10.77.0.1 wiki.lab.test A` بزن. مقصد 10.77.0.1 باید از VPN route بشه. اگه جواب آمد، server پاسخ می‌ده؛ هنوز OS resolver و اپ رو تنظیم نکرده‌ای. در خروجی بخش `SERVER:` رو بخوان و بعد route به همین resolver رو با `ip route get 10.77.0.1` بررسی کن.

On the client, first query explicitly with `dig @10.77.0.1 wiki.lab.test A`. The destination 10.77.0.1 must route through the VPN. A response proves the server answers; it has not configured the OS resolver or application. Read `SERVER:` in dig output and inspect the route to this resolver with `ip route get 10.77.0.1`.

Split DNS: فقط suffix خصوصی به resolver داخل tunnelSplit DNS: send only the private suffix to the tunnel resolver

در systemd-resolved روی موقتی client، DNS interface tunnel رو موقتاً تنظیم کن و `~lab.test` رو به‌عنوان route-only domain بده. tilde می‌گه این suffix برای انتخاب resolver هست؛ خودش search suffix برای کوتاه‌نویسی hostname نیست. interface و resolver IP رو از آزمایشگاه خودت جایگزین کن:

On a disposable client using systemd-resolved, temporarily set the VPN link’s DNS server and assign `~lab.test` as a route-only domain. The tilde selects a resolver for that suffix; it is not a search suffix for expanding short hostnames. Substitute your lab interface and resolver address:

sudo resolvectl dns wg0 10.77.0.1
sudo resolvectl domain wg0 '~lab.test'
resolvectl status wg0

حالا `resolvectl query wiki.lab.test` و یک دامنهٔ عمومی رو جدا اجرا کن. private query باید به link VPN برسه؛ public query طبق قانون باقی سیستم بره. `resolvectl status` و packet capture شواهد resolver selection/path هستن. cache رو پیش از تکرار با `resolvectl flush-caches` پاک کن؛ وگرنه پاسخ قبلی می‌تونه query جدیدی روی wire نفرستد.

Run `resolvectl query wiki.lab.test` and a public name separately. The private query should use the VPN link; the public query follows the rest of the system policy. `resolvectl status` and packet captures provide resolver/path evidence. Clear cached data with `resolvectl flush-caches` before repeating, or a cached response may generate no new wire query.

sudo resolvectl flush-caches
resolvectl query wiki.lab.test
resolvectl query example.com
sudo tcpdump -ni wg0 port 53
sudo tcpdump -ni eth0 port 53

در capture روی wg0 باید private DNS query دیده بشه؛ روی eth0 نباید همون query plain خارج بشه. در full tunnel، ممکنه query هم روی wg0 دیده بشه ولی plain آنجا قابل مشاهده باشه—داخل مسیر VPN روی سیم بیرونی، payload باید encapsulated/encrypted باشه. capture روی wg0 در نقطهٔ endpoint بعد از decrypt انجام می‌شه؛ این تناقض نیست.

The private query should appear on wg0 and not escape in plaintext on eth0. In a full tunnel, it may be visible as plaintext on wg0 after decryption while the outer physical link carries encrypted encapsulated traffic. A capture at the tunnel endpoint sees the inner packet after decryption; that is not a contradiction.

خرابی عمدی: resolver هنوز بیرون tunnel هستDeliberate failure: the resolver still points outside the tunnel

در client آزمایشی routing domain خصوصی رو بردار یا DNS بیرونی رو به link اولویت‌دار تبدیل کن؛ پیش از تغییر، `resolvectl status` و captureهای هر دو interface رو ذخیره کن. `wiki.lab.test` باید fail/NXDOMAIN بدهد یا درخواست روی interface فیزیکی دیده بشه. این دو نشانه رو یکی ندان: ممکنه query درست به resolver نادرست رفته و NXDOMAIN گرفته، یا اصلاً نام local resolve نشده باشه.

On the test client, remove the private routing domain or prioritize the outside resolver; first save `resolvectl status` and captures on both interfaces. `wiki.lab.test` may fail/NXDOMAIN or appear on the physical interface. Do not conflate those symptoms: a query may reach the wrong resolver and get NXDOMAIN, or local resolution may fail before a query is sent.

بعد از ثبت evidence، DNS server و `~lab.test` رو روی wg0 دوباره تنظیم کن، cache رو پاک کن و همون query و capture رو تکرار کن. اگه query اصلاً از client خارج نشده، app-specific cache/DoH و name syntax رو بررسی کن. خرابی عمدی فقط وقتی آموزنده هست که نتیجه رو واقعاً مشاهده کنی؛ خروجی نمونه رو به‌جای دستگاه خودت ننویس.

After capturing evidence, restore the VPN DNS server and `~lab.test` on wg0, flush caches, and repeat the same query/capture. If no query leaves the client, inspect application-specific cache/DoH and the name itself. The deliberate failure is useful only when you observe it—never substitute sample output for your own.

DNS داخل VPN رمز هست؟ نسبت به کدوم ناظر؟Is DNS inside a VPN encrypted—and from which observer?

DNS معمولی با UDP/TCP 53 خودش رمزنگاری نمی‌شه. اگه query داخل VPN افتاد، tunnel اون رو روی بخش client→VPN gateway می‌پوشاند؛ اما پس از خروج tunnel، DNS server یا network خروجی ممکنه query رو ببینه. DoT/DoH/DoQ رمزنگاری جداگانهٔ client→resolver می‌دن، ولی resolver مقصد همچنان نام رو می‌دونه و resolver selection/route قانون باید درست باشه. encrypted DNS و correct split DNS دو سؤال مستقل‌اند.

Ordinary DNS over UDP/TCP 53 is not encrypted by itself. If routed through a VPN, the tunnel protects it on the client-to-gateway segment; after tunnel exit, the DNS server or egress network may see the query. DoT/DoH/DoQ provide separate client-to-resolver encryption, but the resolver still learns the name and routing policy must be correct. Encrypted DNS and correct split DNS are independent questions.

اپ‌هایی با built-in DoH ممکنه از system resolver و `resolvectl` عبور نکنند؛ browser قانون، proxy/VPN app و OS رو جدا بررسی کن. صرف اینکه port 53 در capture نیست ثابت نمی‌کنه query امن یا از مسیر درست رفته—ممکنه HTTPS به resolver دیگری رفته باشه.

Applications with built-in DoH may bypass the system resolver and `resolvectl`; check browser, proxy/VPN app, and OS policies separately. Seeing no port 53 packet does not prove a query is encrypted or routed correctly—it may be HTTPS to an unintended resolver.

VPN tool باید DNS رو هم به OS معرفی کندA VPN client must also integrate DNS policy with the OS

OpenVPN می‌تونه DNS option رو push کند، ولی client platform باید اون رو پشتیبانی و اعمال کند؛ WireGuard config هسته‌ای DNS directive نداره، در حالی که `wg-quick` و appهای mobile قابلیت جدا دارن. روی systemd-resolved، NetworkManager، Windows و macOS روش‌ها فرق می‌کنه. config tunnel موفق به‌تنهایی resolver system رو عوض نمی‌کنه. از docs همون client/provider و status محلی استفاده کن.

OpenVPN can push DNS options, but the client platform must support and apply them. WireGuard’s core config has no DNS directive, while `wg-quick` and mobile apps may provide separate integration. systemd-resolved, NetworkManager, Windows, and macOS differ. A successful tunnel configuration does not itself change the system resolver; consult the exact client/platform docs and inspect local state.

cleanup: فقط تنظیم موقتی همین link رو برگردانCleanup: revert only this temporary link setting

پس از جمع‌آوری evidence، settingهای موقتی systemd-resolved رو برگردان. روی موقتی client فرمان `resolvectl revert wg0` تنظیم DNS/domain موقتی link رو حذف می‌کنه؛ status رو دوباره بخوان و ببین resolver قبلی برگشت. DNS server آزمایشگاه رو هم با Ctrl+C متوقف کن. اگه VPN client خودش settingها رو sync می‌کنه، cleanup رو با همون client انجام بده تا دو manager با هم بجنگند.

After preserving evidence, revert temporary systemd-resolved link settings. On the disposable client, `resolvectl revert wg0` removes temporary DNS/domain settings for that link; inspect status again and confirm the prior resolver returned. Stop the lab DNS server with Ctrl+C. If a VPN client manages settings itself, use its own cleanup path to avoid competing managers.

معیار

اسم resolve شدن، مسیر رو لو نمی‌دهA resolved name does not reveal its path

برای هر DNS lookup چهار چیز رو ثبت کن: application/resolver؛ domain قانون؛ route به resolver؛ interfaceای که query از اون دیده شد. systemd-resolved یک مدل per-link مفید داره، ولی همهٔ OSها و appها از اون پیروی نمی‌کنن. cache رو کنترل کن، DoH رو فراموش نکن و capture رو روی مسیر درست بگیر. با این evidence می‌تونی DNS leak رو از نبود zone، route خرابی یا resolver cache جدا کنی.

For each DNS lookup, record four things: application/resolver, domain policy, route to resolver, and the interface where the query appeared. systemd-resolved offers a useful per-link model, but not every OS or app follows it. Control cache, consider DoH, and capture the correct path. This evidence separates leaks from a missing zone, route failure, or resolver cache.
