TLS and termination

رمزنگاری، گواهی و جایی که رمز باز می‌شود.

Encryption, certificates, and where plaintext appears.

۸۵دقیقهminutes
۱۸تمرینexercises

قفل مرورگر تا کجا را پوشش می‌دهد؟How far does the browser’s lock reach?

مرورگر به سایت HTTPS وصل می‌شود، ولی جلوی سایت یک reverse proxy نشسته. کاربر قفل را می‌بیند؛ backend داخل شبکه با HTTP جواب می‌دهد. داده در کدام نقطه رمز بود و کجا plaintext شد؟ سؤال اصلی TLS و proxy همین است: کدام endpoint هر اتصال را terminate می‌کند و چه کسی آن نقطه را اداره می‌کند؟

A browser connects to an HTTPS site, but a reverse proxy sits in front of it. The user sees the lock; the internal backend uses HTTP. Where was the data encrypted, and where did it become plaintext? The central TLS-and-proxy question is: which endpoint terminates each connection, and who controls that endpoint?

TLS برای اتصال client و server احراز هویت (با گواهی server)، مذاکرهٔ الگوریتم/کلید و حفاظت محرمانگی و تمامیت فراهم می‌کند. جزئیات handshake به نسخه بستگی دارد؛ برای ذهنیت امروز پیام‌ها را ساده می‌کنیم و ادعای byte sequence کامل نمی‌کنیم. در TLS 1.3، ClientHello تنظیمات پیشنهادی و معمولاً SNI را می‌برد؛ server گواهی و شواهد handshake را می‌فرستد؛ دو سمت کلیدهای نشست را می‌سازند و بعد دادهٔ برنامه رمز می‌شود. RFC 8446

TLS authenticates a server certificate, negotiates cryptographic parameters and keys, then protects confidentiality and integrity for that connection. Handshakes vary by version; this is a conceptual sketch, not a complete wire trace. In TLS 1.3, ClientHello carries client capabilities and typically SNI; the server sends its certificate and handshake proof; peers derive traffic keys and then encrypt application data. RFC 8446

Termination یک مرز اعتماد می‌سازدTermination creates a trust boundary

termination یعنی این proxy گواهی را ارائه و TLS را تمام می‌کند؛ از آن نقطه، متن درخواست در حافظهٔ proxy قابل‌دسترسی است.

At termination, this proxy presents the certificate and ends TLS; request plaintext is accessible in the proxy’s memory after that point.

اگر upstream با HTTP باشد، TLS از client تا proxy محافظت می‌کند، نه لزوماً تا backend. اگر backend هم TLS داشته باشد، proxy می‌تواند اتصال دوم بسازد؛ این re-encryption است، نه ادامهٔ همان TLS session. هر اتصال handshake، هویت، trust و احتمال خطای خودش را دارد. در پیکربندی Caddy، backend با `https://` انتخاب می‌شود و گواهی upstream باید مورد اعتماد باشد؛ گزینهٔ خاموش‌کردن verify راه‌حل درست نیست. Caddy: HTTPS to backend

If upstream uses HTTP, TLS protects the client-to-proxy leg, not necessarily the backend leg. If the backend also supports TLS, the proxy can establish a second connection: re-encryption, not continuation of the same TLS session. Each leg has its own handshake, identity, trust, and failure modes. Caddy’s HTTPS upstream scheme requires a trusted backend certificate; disabling verification is not the right fix.

گواهی چه چیزی را ثابت می‌کند؟What does a certificate prove?

گواهی عمومی certificate chain دارد: گواهی server با کلید private مربوطه امضا می‌شود و معمولاً به intermediate و trust anchor مورد اعتماد client می‌رسد. client هم نام hostname را با هویت داخل گواهی تطبیق می‌دهد. این دو بررسی جدا هستند: chain مورد اعتماد ولی hostname اشتباه، هنوز هویت اشتباه است. private key را نباید منتشر کرد؛ certificate عمومی می‌تواند منتشر شود.

A public certificate participates in a chain: the server certificate is tied to its private key and normally chains through intermediates to a trust anchor the client accepts. The client also matches the requested hostname against the certificate identity. These are distinct checks: a trusted chain for the wrong hostname is still the wrong identity. Never publish a private key; a public certificate may be shared.

SNI در ClientHello به سرور کمک می‌کند گواهی/سایت مناسب را برای hostname انتخاب کند. خود نام SNI معمولاً در handshake قابل مشاهده بوده، اما TLS 1.3 با ECH می‌تواند ClientHello را پنهان کند—اگر client/server/network پشتیبانی و استفاده کنند. پس نگوییم SNI همیشه پنهان است یا همیشه آشکار: نسخه و negotiation را بررسی کن. SNI خودش سند هویت نیست؛ certificate validation جداست.

SNI lets a server choose the certificate/site for a hostname during ClientHello. SNI has commonly been visible in the handshake, but TLS 1.3 with ECH can conceal ClientHello when client, server, and network support and negotiate it. Avoid claiming SNI is always visible or always hidden: check the negotiated behavior. SNI is not proof of identity; certificate validation is separate. RFC 9525: Service Identity

آزمایش محلی: خودت یک گواهی کوتاه‌عمر بسازLocal lab: create a short-lived certificate

برای آزمایش بدون دامنهٔ عمومی، origin روی loopback و Caddy جلویش می‌آید. پورت‌های 9000 و 8443 را اول بررسی کن. گواهی یک‌روزه و کلید فقط آزمایشی بساز؛ داخل repository یا جای اشتراکی ذخیره‌اش نکن. این دستور به OpenSSL نسخهٔ دارای `-addext` نیاز دارد:

For a lab without a public domain, run a loopback origin behind Caddy. Check ports 9000 and 8443 first. Create a one-day test certificate and key; do not store them in a repository or shared location. This command requires an OpenSSL version supporting `-addext`:

openssl req -x509 -newkey rsa:2048 -nodes -days 1 -keyout lab.key -out lab.crt -subj "/CN=localhost" -addext "subjectAltName=DNS:localhost"

این self-signed certificate برای آزمایش است، نه برای کاربر واقعی. حالا origin را بالا بیاور:

This self-signed certificate is for testing, not real users. Start the origin:

python -m http.server 9000 --bind 127.0.0.1

Caddyfile زیر termination را عمداً نشان می‌دهد: HTTPS تا Caddy، HTTP از Caddy به origin. directive `bind` پورت ورودی را loopback می‌کند. با نسخهٔ فعلی Caddy اعتبار config را پیش از اجرا بررسی کن.

This Caddyfile makes termination explicit: HTTPS to Caddy, HTTP from Caddy to the origin. The bind directive keeps its listener on loopback. Validate the configuration with your installed Caddy version before running it.

https://localhost:8443 {
  bind 127.0.0.1
  tls ./lab.crt ./lab.key
  reverse_proxy 127.0.0.1:9000
}

Caddy را اجرا کن و در ترمینال دیگر گواهی را موقتاً به‌عنوان trust input همین آزمایش بده: curl --cacert lab.crt https://localhost:8443/. بعد openssl s_client -connect 127.0.0.1:8443 -servername localhost -CAfile lab.crt -verify_hostname localhost را اجرا کن. دنبال verify return code، subject/SAN و TLS protocol بگرد؛ این ثابت می‌کند client آزمایشی زنجیرهٔ انتخابی و hostname را پذیرفته، نه اینکه گواهی عمومی یا امن production است.

Start Caddy, then temporarily provide the lab certificate as this test’s trust input: curl --cacert lab.crt https://localhost:8443/. Also run openssl s_client -connect 127.0.0.1:8443 -servername localhost -CAfile lab.crt -verify_hostname localhost. Inspect verification result, subject/SAN, and negotiated protocol. This shows the test client accepted the supplied trust and hostname—not that the certificate is public or production-secure.

خرابی عمدی: گواهی trusted است، اما برای نام اشتباهDeliberate failure: trusted certificate, wrong name

برای دیدن فرق trust chain و hostname، یک گواهی دوم با SAN برابر wrong.test بساز و موقتاً در Caddy استفاده کن. درخواست به https://localhost:8443 باید خطای hostname بدهد، حتی اگر فایل همان cert را با --cacert داده باشی. پیش از fix، متن دقیق error را ثبت کن. بعد cert صحیح با SAN `localhost` را برگردان و همان curl را دوباره اجرا کن.

To separate chain trust from hostname identity, create a second certificate with SAN wrong.test and temporarily configure Caddy to use it. A request to https://localhost:8443 should fail hostname verification even if that same certificate is supplied with --cacert. Capture the exact error before fixing it. Restore the certificate with SAN localhost and repeat the same curl command.

از `curl -k` برای «حل» استفاده نکن؛ این گزینه بررسی هویت را خاموش می‌کند. ممکن است برای مشاهدهٔ پاسخ سرور در diagnosis کوتاه کمک کند، اما موفقیت آن ثابت نمی‌کند اتصال امن است. اگر با گواهی صحیح هم خطا باقی است، path فایل، SAN، ساعت سیستم، گواهی ارائه‌شده، curl trust input و log Caddy را به‌ترتیب بررسی کن.

Do not “fix” this with `curl -k`; it disables identity verification. It can occasionally help inspect server behavior during brief diagnosis, but success with it proves no secure identity. If the correct certificate still fails, check file paths, SAN, system clock, the certificate actually served, curl’s trust input, and Caddy logs in order.

Pass-through با termination فرق داردPass-through is different from termination

در TLS pass-through، واسطهٔ لایهٔ پایین‌تر (معمولاً TCP) را هدایت می‌کند و TLS تا backend می‌ماند؛ proxy محتوای HTTP رمز‌شده را نمی‌خواند. در termination، واسطه TLS endpoint است و plaintext را می‌بیند. انتخاب یکی یا دیگری معماری، routing، log، certificate lifecycle و trust boundary را عوض می‌کند. «reverse proxy» الزاماً TLS را terminate نمی‌کند؛ mode را از config و trace پیدا کن.

With TLS pass-through, an intermediary routes at a lower layer (often TCP) while TLS terminates at the backend; the proxy does not read encrypted HTTP content. With termination, the intermediary is a TLS endpoint and can access plaintext. The choice changes routing, logging, certificate lifecycle, and trust boundaries. A reverse proxy does not necessarily terminate TLS; inspect configuration and traces.

اتصال دوم به backend را هم verify کنVerify the second connection too

برای re-encryption، backend باید گواهی معتبر خودش را ارائه کند و proxy باید آن را با trust store و hostname مورد انتظار بررسی کند. اگر backend داخلی با CA سازمانی صادر شده، CA همان محیط را به proxy معرفی کن. cert self-signed را بی‌قید نپذیر و verify را خاموش نکن. failure را از دو طرف جدا کن: client→proxy موفق بوده؟ proxy→backend در TLS شکست خورده؟ Caddy upstream logs و گواهی/hostname backend را بررسی کن.

For re-encryption, the backend must present its own certificate and the proxy must validate it using an appropriate trust store and expected hostname. If an internal CA issued it, configure that CA for the proxy. Do not blindly trust a self-signed cert or turn verification off. Separate the legs: did client-to-proxy succeed while proxy-to-backend TLS failed? Inspect Caddy upstream logs and backend certificate/hostname.

Session resumption می‌تواند هزینهٔ handshake را کم کند، اما جای بررسی گواهی و policy را نمی‌گیرد. برای این فصل کافی است بدانی هر اتصال جدا می‌تواند handshake کامل یا resumed داشته باشد؛ اندازه‌گیری و tuning به workload واقعی تعلق دارد.

Session resumption can reduce handshake cost, but does not replace certificate validation or policy. For this chapter, know that each connection can have a full or resumed handshake; tuning belongs to measured workloads.

۱. terminator

۱۷. بررسی گواهی با openssl

در `openssl s_client` چرا `-servername` و `-verify_hostname` هر دو مفیدند؟

Why can both `-servername` and `-verify_hostname` matter in openssl s_client?

پاسخ

اولی SNI را برای انتخاب سایت می‌فرستد؛ دومی هویت hostname را validate می‌کند.

۱۸. نقشهٔ مرز اعتماد

برای مسیر browser→proxy→backend مشخص کن چه کسی private key هر اتصال را دارد، plaintext کجا موجود است و کدام hop باید جدا verify شود. اگر جواب «همه‌جا رمز است» شد، نمودار را دوباره رسم کن.

For browser→proxy→backend, identify who holds each connection’s private key, where plaintext exists, and which hop needs separate validation. If your answer is “encrypted everywhere,” redraw the path.

معیار

هر TLS leg باید terminator، cert/trust و plaintext boundary خودش را داشته باشد.

Each TLS leg has its own terminator, certificate/trust, and plaintext boundary.

قفل را برای هر hop بررسی کنCheck the lock for every hop

گواهی، hostname validation و کلید private هویت هر اتصال را شکل می‌دهند؛ TLS تا نقطهٔ termination از داده محافظت می‌کند. همان‌جا plaintext در اختیار endpoint است. اگر proxy برای backend اتصال HTTPS جدا باز کند، اتصال دوم را با trust و hostname خودش بررسی کن. اگر pass-through باشد، backend terminator باقی می‌ماند. قفل مرورگر فقط leg خودش را توضیح می‌دهد.

Certificates, hostname validation, and private keys define each connection’s identity; TLS protects data up to its termination point. At that endpoint, plaintext is available. If the proxy opens a separate HTTPS connection to the backend, validate that leg independently. With pass-through, the backend remains the terminator. The browser’s lock only describes its own leg.
