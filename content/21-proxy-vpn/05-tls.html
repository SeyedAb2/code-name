TLS and termination

قفل کنار آدرس خوبه؛ ولی دقیقاً تا کجای مسیر رو قفل کرده؟

Encryption, certificates, and where plaintext appears.

۸۵دقیقهminutes
۱۸تمرینexercises

قفل مرورگر تا کجا رو پوشش می‌ده؟How far does the browser’s lock reach?

یه reverse proxy جلوی سرویس نشسته، مرورگر هم قفل HTTPS رو نشون می‌ده. خیلی راحت می‌شه از همین تصویر نتیجه گرفت «پس کل مسیر رمز شده». ولی صبر کن؛ کل مسیر یعنی کجا تا کجا؟ TLS همیشه بین دو endpoint مشخصه. اگه proxy خودش TLS رو terminate کنه، داده همون‌جا از حالت رمز بیرون میاد. پس قبل از هر چیز باید مرز اتصال‌ها رو پیدا کنیم.

A browser connects to an HTTPS site, but a reverse proxy sits in front of it. The user sees the lock; the internal backend uses HTTP. Where was the data encrypted, and where did it become plaintext? The central TLS-and-proxy question is: which endpoint terminates each connection, and who controls that endpoint?

TLS برای اتصال client و server احراز هویت (با گواهی server)، مذاکرهٔ الگوریتم/کلید و حفاظت محرمانگی و تمامیت فراهم می‌کنه. جزئیات handshake به نسخه بستگی داره؛ برای ذهنیت امروز پیام‌ها رو ساده می‌کنیم و ادعای byte sequence کامل نمی‌کنیم. در TLS 1.3، ClientHello تنظیمات پیشنهادی و معمولاً SNI رو می‌برد؛ server گواهی و شواهد handshake رو می‌فرسته؛ دو سمت کلیدهای نشست رو می‌سازن و بعد دادهٔ برنامه رمز می‌شه. RFC 8446

TLS authenticates a server certificate, negotiates cryptographic parameters and keys, then protects confidentiality and integrity for that connection. Handshakes vary by version; this is a conceptual sketch, not a complete wire trace. In TLS 1.3, ClientHello carries client capabilities and typically SNI; the server sends its certificate and handshake proof; peers derive traffic keys and then encrypt application data. RFC 8446

Termination یک مرز اعتماد می‌سازهTermination creates a trust boundary

termination یعنی این proxy گواهی رو ارائه و TLS رو تمام می‌کنه؛ از اون نقطه، متن درخواست در حافظهٔ proxy قابل‌دسترسی هست.

At termination, this proxy presents the certificate and ends TLS; request plaintext is accessible in the proxy’s memory after that point.

اگه upstream با HTTP باشه، TLS از client تا proxy محافظت می‌کنه، نه لزوماً تا backend. اگه backend هم TLS داشته باشه، proxy می‌تونه اتصال دوم بسازه؛ این re-encryption هست، نه ادامهٔ همون TLS session. هر اتصال handshake، هویت، trust و احتمال خطای خودش رو داره. در پیکربندی Caddy، backend با `https://` انتخاب می‌شه و گواهی upstream باید مورد اعتماد باشه؛ گزینهٔ خاموش‌کردن verify راه‌حل درست نیست. Caddy: HTTPS to backend

If upstream uses HTTP, TLS protects the client-to-proxy leg, not necessarily the backend leg. If the backend also supports TLS, the proxy can establish a second connection: re-encryption, not continuation of the same TLS session. Each leg has its own handshake, identity, trust, and failure modes. Caddy’s HTTPS upstream scheme requires a trusted backend certificate; disabling verification is not the right fix.

گواهی چی رو ثابت می‌کنه؟What does a certificate prove?

گواهی عمومی certificate chain داره: گواهی server با کلید private مربوطه امضا می‌شه و معمولاً به intermediate و trust anchor مورد اعتماد client می‌رسه. client هم نام hostname رو با هویت داخل گواهی تطبیق می‌ده. این دو بررسی جدا هستن: chain مورد اعتماد ولی hostname اشتباه، هنوز هویت اشتباهه. private key رو نباید منتشر کرد؛ certificate عمومی می‌تونه منتشر بشه.

A public certificate participates in a chain: the server certificate is tied to its private key and normally chains through intermediates to a trust anchor the client accepts. The client also matches the requested hostname against the certificate identity. These are distinct checks: a trusted chain for the wrong hostname is still the wrong identity. Never publish a private key; a public certificate may be shared.

SNI در ClientHello به سرور کمک می‌کنه گواهی/سایت مناسب رو برای hostname انتخاب کند. خود نام SNI معمولاً در handshake قابل مشاهده بوده، اما TLS 1.3 با ECH می‌تونه ClientHello رو پنهان کند—اگه client/server/network پشتیبانی و استفاده کنند. پس نگوییم SNI همیشه پنهان هست یا همیشه آشکار: نسخه و negotiation رو بررسی کن. SNI خودش سند هویت نیست؛ certificate validation جداست.

SNI lets a server choose the certificate/site for a hostname during ClientHello. SNI has commonly been visible in the handshake, but TLS 1.3 with ECH can conceal ClientHello when client, server, and network support and negotiate it. Avoid claiming SNI is always visible or always hidden: check the negotiated behavior. SNI is not proof of identity; certificate validation is separate. RFC 9525: Service Identity

آزمایش محلی: خودت یک گواهی کوتاه‌عمر بسازLocal lab: create a short-lived certificate

برای آزمایش بدون دامنهٔ عمومی، origin روی loopback و Caddy جلویش میاد. پورت‌های 9000 و 8443 رو اول بررسی کن. گواهی یک‌روزه و کلید فقط آزمایشی بساز؛ داخل repository یا جای اشتراکی ذخیره‌اش نکن. این دستور به OpenSSL نسخهٔ دارای `-addext` نیاز داره:

For a lab without a public domain, run a loopback origin behind Caddy. Check ports 9000 and 8443 first. Create a one-day test certificate and key; do not store them in a repository or shared location. This command requires an OpenSSL version supporting `-addext`:

openssl req -x509 -newkey rsa:2048 -nodes -days 1 -keyout lab.key -out lab.crt -subj "/CN=localhost" -addext "subjectAltName=DNS:localhost"

این self-signed certificate برای آزمایش هست، نه برای کاربر واقعی. حالا origin رو بالا بیاور:

This self-signed certificate is for testing, not real users. Start the origin:

python -m http.server 9000 --bind 127.0.0.1

Caddyfile زیر termination رو عمداً نشان می‌ده: HTTPS تا Caddy، HTTP از Caddy به origin. directive `bind` پورت ورودی رو loopback می‌کنه. با نسخهٔ فعلی Caddy اعتبار config رو پیش از اجرا بررسی کن.

This Caddyfile makes termination explicit: HTTPS to Caddy, HTTP from Caddy to the origin. The bind directive keeps its listener on loopback. Validate the configuration with your installed Caddy version before running it.

https://localhost:8443 {
  bind 127.0.0.1
  tls ./lab.crt ./lab.key
  reverse_proxy 127.0.0.1:9000
}

Caddy رو اجرا کن و در ترمینال دیگر گواهی رو موقتاً به‌عنوان trust input همین آزمایش بده: curl --cacert lab.crt https://localhost:8443/. بعد openssl s_client -connect 127.0.0.1:8443 -servername localhost -CAfile lab.crt -verify_hostname localhost رو اجرا کن. دنبال verify return code، subject/SAN و TLS protocol بگرد؛ این ثابت می‌کنه client آزمایشی زنجیرهٔ انتخابی و hostname رو پذیرفته، نه اینکه گواهی عمومی یا امن production هست.

Start Caddy, then temporarily provide the lab certificate as this test’s trust input: curl --cacert lab.crt https://localhost:8443/. Also run openssl s_client -connect 127.0.0.1:8443 -servername localhost -CAfile lab.crt -verify_hostname localhost. Inspect verification result, subject/SAN, and negotiated protocol. This shows the test client accepted the supplied trust and hostname—not that the certificate is public or production-secure.

خرابی عمدی: گواهی trusted هست، اما برای نام اشتباهDeliberate failure: trusted certificate, wrong name

برای دیدن فرق trust chain و hostname، یک گواهی دوم با SAN برابر wrong.test بساز و موقتاً در Caddy استفاده کن. درخواست به https://localhost:8443 باید خطای hostname بدهد، حتی اگه فایل همون cert رو با --cacert داده باشی. پیش از fix، متن دقیق error رو ثبت کن. بعد cert صحیح با SAN `localhost` رو برگردان و همون curl رو دوباره اجرا کن.

To separate chain trust from hostname identity, create a second certificate with SAN wrong.test and temporarily configure Caddy to use it. A request to https://localhost:8443 should fail hostname verification even if that same certificate is supplied with --cacert. Capture the exact error before fixing it. Restore the certificate with SAN localhost and repeat the same curl command.

از `curl -k` برای «حل» استفاده نکن؛ این گزینه بررسی هویت رو خاموش می‌کنه. ممکنه برای مشاهدهٔ پاسخ سرور در diagnosis کوتاه کمک کند، اما موفقیت اون ثابت نمی‌کنه اتصال امن هست. اگه با گواهی صحیح هم خطا باقی هست، path فایل، SAN، ساعت سیستم، گواهی ارائه‌شده، curl trust input و log Caddy رو به‌ترتیب بررسی کن.

Do not “fix” this with `curl -k`; it disables identity verification. It can occasionally help inspect server behavior during brief diagnosis, but success with it proves no secure identity. If the correct certificate still fails, check file paths, SAN, system clock, the certificate actually served, curl’s trust input, and Caddy logs in order.

Pass-through با termination فرق دارهPass-through is different from termination

در TLS pass-through، واسطهٔ لایهٔ پایین‌تر (معمولاً TCP) رو هدایت می‌کنه و TLS تا backend می‌مونه؛ proxy محتوای HTTP رمز‌شده رو نمی‌خونه. در termination، واسطه TLS endpoint هست و plaintext رو می‌بینه. انتخاب یکی یا دیگری معماری، routing، log، certificate lifecycle و trust boundary رو عوض می‌کنه. «reverse proxy» الزاماً TLS رو terminate نمی‌کنه؛ mode رو از config و trace پیدا کن.

With TLS pass-through, an intermediary routes at a lower layer (often TCP) while TLS terminates at the backend; the proxy does not read encrypted HTTP content. With termination, the intermediary is a TLS endpoint and can access plaintext. The choice changes routing, logging, certificate lifecycle, and trust boundaries. A reverse proxy does not necessarily terminate TLS; inspect configuration and traces.

اتصال دوم به backend رو هم verify کنVerify the second connection too

برای re-encryption، backend باید گواهی معتبر خودش رو ارائه کند و proxy باید اون رو با trust store و hostname مورد انتظار بررسی کند. اگه backend داخلی با CA سازمانی صادر شده، CA همون محیط رو به proxy معرفی کن. cert self-signed رو بی‌قید نپذیر و verify رو خاموش نکن. خرابی رو از دو طرف جدا کن: client→proxy موفق بوده؟ proxy→backend در TLS شکست خورده؟ Caddy upstream logs و گواهی/hostname backend رو بررسی کن.

For re-encryption, the backend must present its own certificate and the proxy must validate it using an appropriate trust store and expected hostname. If an internal CA issued it, configure that CA for the proxy. Do not blindly trust a self-signed cert or turn verification off. Separate the legs: did client-to-proxy succeed while proxy-to-backend TLS failed? Inspect Caddy upstream logs and backend certificate/hostname.

Session resumption می‌تونه هزینهٔ handshake رو کم کند، اما جای بررسی گواهی و قانون رو نمی‌گیره. برای این فصل کافیه بدانی هر اتصال جدا می‌تونه handshake کامل یا resumed داشته باشه؛ اندازه‌گیری و tuning به workload واقعی تعلق داره.

Session resumption can reduce handshake cost, but does not replace certificate validation or policy. For this chapter, know that each connection can have a full or resumed handshake; tuning belongs to measured workloads.

۱. terminator

client با TLS به proxy وصل می‌شه و proxy به backend با HTTP. TLS client کجا تمام می‌شه؟

At the proxy; plaintext is available there.

۲. دو TLS leg

No; they are separate connections and handshakes.

۱۷. بررسی گواهی با openssl

در `openssl s_client` چرا `-servername` و `-verify_hostname` هر دو مفیدند؟

Why can both `-servername` and `-verify_hostname` matter in openssl s_client?

پاسخ

اولی SNI رو برای انتخاب سایت می‌فرسته؛ دومی هویت hostname رو validate می‌کنه.

۱۸. نقشهٔ مرز اعتماد

برای مسیر browser→proxy→backend مشخص کن کی private key هر اتصال رو داره، plaintext کجا موجود هست و کدوم hop باید جدا verify بشه. اگه جواب «همه‌جا رمز هست» شد، نمودار رو دوباره رسم کن.

For browser→proxy→backend, identify who holds each connection’s private key, where plaintext exists, and which hop needs separate validation. If your answer is “encrypted everywhere,” redraw the path.

معیار

هر TLS leg باید terminator، cert/trust و plaintext boundary خودش رو داشته باشه.

Each TLS leg has its own terminator, certificate/trust, and plaintext boundary.

قفل رو برای هر hop بررسی کنCheck the lock for every hop

گواهی، hostname validation و کلید private هویت هر اتصال رو شکل می‌دن؛ TLS تا نقطهٔ termination از داده محافظت می‌کنه. همون‌جا plaintext در اختیار endpoint هست. اگه proxy برای backend اتصال HTTPS جدا باز کند، اتصال دوم رو با trust و hostname خودش بررسی کن. اگه pass-through باشه، backend terminator باقی می‌مونه. قفل مرورگر فقط leg خودش رو توضیح می‌ده.

Certificates, hostname validation, and private keys define each connection’s identity; TLS protects data up to its termination point. At that endpoint, plaintext is available. If the proxy opens a separate HTTPS connection to the backend, validate that leg independently. With pass-through, the backend remains the terminator. The browser’s lock only describes its own leg.
