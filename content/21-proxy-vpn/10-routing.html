مسیریابی و NAT

Routing and NAT

تونل بالا اومده، handshake هم تازه‌ست؛ ولی packet هنوز به سرویس پشت gateway نمی‌رسه.

Routes, forwarding, and masquerading.

۸۵دقیقهminutes
۱۸تمرینexercises

تونل بالا هست؛ اما ping از LAN رد نمی‌شهThe tunnel is up, but the packet cannot reach the LAN

این یکی از اون لحظه‌هاییه که آدم وسوسه می‌شه دوباره تنظیمات VPN رو زیرورو کنه. ولی شاید VPN کاملاً سالم باشه. packet وارد gateway می‌شه؛ حالا سؤال‌های تازه شروع می‌شن: forwarding روشنه؟ route رفت داریم؟ جواب راه برگشت داره؟ firewall اجازه می‌ده؟ NAT واقعاً لازمه؟ بیا مسیر رفت و برگشت رو جدا بکشیم و ببینیم packet دقیقاً کجا گم می‌شه.

WireGuard/OpenVPN has a recent handshake and the client has a TUN address, but a server behind the gateway is unreachable. Encryption is no longer the main question: will the gateway forward the packet? How does the destination route its reply to the tunnel subnet? What does the firewall allow?

برای مسیر یک packet از مبدا تا مقصد و مسیر پاسخ رو جدا رسم می‌کنیم. NAT ممکنه آدرس source رو عوض کند، اما route دوطرفه رو جادویی درست نمی‌کنه و firewall rule هم نیست.

We will trace a packet from source to destination and then trace the reply separately. NAT may rewrite a source address, but it does not magically create correct routing or replace firewall policy.

اول forwarding و مسیر برگشت رو ثابت کن؛ فقط نبود route برگشت می‌تونه دلیل NAT باشه.

Prove forwarding and the return route first; a missing return route may justify NAT.

route رفت، route برگشتA forward route and a return route

برای درخواست client به 192.0.2.10، gateway باید بدونه مقصد از `eth1` در دسترس هست؛ LAN host هم باید بدونه 10.77.0.0/24 از gateway برمی‌گردد. OS route lookup معمولاً longest matching prefix رو ترجیح می‌ده، بعد metric/ruleهای سیستم هم مهم‌اند. در Linux بدون فرستادن packet، `ip route get` تصمیم فعلی رو نشان می‌ده.

For a client request to 192.0.2.10, the gateway must know that destination is reachable via eth1; the LAN host must know that 10.77.0.0/24 returns through the gateway. OS routing usually prefers the longest matching prefix, with metrics and policy rules also relevant. On Linux, `ip route get` inspects the current decision without sending a packet.

ip route get 192.0.2.10
ip route get 10.77.0.2
ip rule show

در خروجی دنبال `dev`, `via`, `src`, و rule/table انتخاب‌شده بگرد. این نشان می‌ده kernel همین حالا کدوم route رو انتخاب می‌کنه؛ نه اینکه interface روشن، firewall باز یا مقصد پاسخگوست. اگه default route اشتباه match شد، prefix اختصاصی‌تر و route قانون رو بررسی کن.

Inspect `dev`, `via`, `src`, and the selected rule/table. This shows the kernel’s current route choice—not whether the interface is up, firewall allows traffic, or the destination responds. If the wrong default matches, inspect more-specific prefixes and policy routing.

Gateway باید اجازهٔ عبور packet رو داشته باشهA gateway must permit packet forwarding

ماشین می‌تونه packetی رو که برای خودش هست بپذیرد، ولی packet عبوری رو forward نکند. در Linux مقدار net.ipv4.ip_forward این رفتار رو کنترل می‌کنه؛ IPv6 کنترل جداگانه داره. مقدار فعلی رو بخوان، نه اینکه روی host روزمره بی‌فکر عوض کنی:

A host can accept packets addressed to itself while refusing to forward transit packets. On Linux, net.ipv4.ip_forward controls IPv4 forwarding; IPv6 has a separate control. Read current state before changing a disposable gateway:

sysctl net.ipv4.ip_forward
sysctl net.ipv6.conf.all.forwarding

خروجی صفر یعنی forwarding اون family خاموش هست؛ یک یعنی فعال، اما firewall هنوز می‌تونه drop کند. تغییر این sysctl روی machine اثر سیستمی داره؛ فقط در VM آزمایشگاه و با cleanup/rollback plan انجامش بده. container/network manager/firewall ممکنه همزمان روی forwarding rule داشته باشن.

A zero value means forwarding for that family is disabled; one means enabled, but firewall policy can still drop packets. Changing the sysctl affects the host; do it only in a lab VM with a rollback plan. Containers/network managers/firewalls may also manage forwarding rules.

برای دیدن packet، دو interface رو همزمان capture کن: `wg0` و `eth1`. اگه request روی wg0 دیده می‌شه اما روی eth1 نه، forwarding/firewall/route gateway رو بررسی کن. اگه روی هر دو دیده شد، gateway اون رو فرستاده؛ هنوز reply route مقصد رو ثابت نکرده‌ای.

Capture both interfaces, `wg0` and `eth1`. If the request appears on wg0 but not eth1, inspect gateway forwarding/firewall/routing. If it appears on both, the gateway sent it; the destination’s return path remains unproven.

sudo tcpdump -ni wg0 host 192.0.2.10
sudo tcpdump -ni eth1 host 192.0.2.10

خرابی اول: reply راه برگشت ندارهFailure one: the reply has no route back

forwarding رو در آزمایشگاه فعال نگه دار، اما عمداً روی LAN host route برگشت به 10.77.0.0/24 حذف کن. درخواست رو بفرست و capture بگیر: gateway خروجی روی eth1 رو می‌بینه؛ LAN host ممکنه reply بسازه ولی به gateway دیگری بدهد. `tcpdump` روی دو سمت و route lookup خود LAN host نشان می‌ده کجا مسیر جدا شده. پیش از NAT، route برگشت دقیق رو به gateway آزمایشگاه اضافه کن و همون test رو تکرار کن.

Keep forwarding enabled in the lab, but deliberately remove the LAN host’s route back to 10.77.0.0/24. Send a request and capture both sides: the gateway sees it leave eth1; the LAN host may reply but send that reply through another gateway. Captures and the LAN host’s route lookup show where the path diverges. Before adding NAT, add a precise return route to the lab gateway and repeat the test.

این خرابی با «forwarding خاموش» یکی نیست: packet از gateway بیرون رفته، ولی پاسخ به subnet tunnel راه برگشت نداره. شواهد دو جهت رو جدا ثبت کن؛ یک capture سمت client برای پیدا کردن این مشکل کافی نیست.

This differs from disabled forwarding: the packet left the gateway, but the reply had no path to the tunnel subnet. Record evidence in both directions; a client-side capture alone may not locate the fault.

NAT فقط وقتی route برگشت نداریمUse NAT only when a return route is not available

اگه LAN host یا router رو نمی‌تونی طوری تنظیم کنی که 10.77.0.0/24 رو route کند، gateway می‌تونه source رو به IP خودش روی eth1 تبدیل کند؛ به این کار SNAT می‌گیم. `masquerade` شکل پویاست که source interface address رو می‌گیره. conntrack mapping رو نگه می‌داره تا reply رو به source اصلی 10.77.0.2 برگردونه. NAT firewall نیست؛ filter ruleها همچنان لازم‌اند.

If you cannot configure the LAN host/router to route 10.77.0.0/24, the gateway can rewrite the source to its own eth1 address—SNAT. `masquerade` is the dynamic form that uses the outgoing interface address. Conntrack tracks the mapping so replies can be translated back to 10.77.0.2. NAT is not a firewall; filtering remains necessary.

در موقتی gateway با nftables و فقط network آزمایشگاه، forwarding قانون رو محدود به wg0→eth1 و subnet مقصد نگه دار؛ بعد masquerade رو در postrouting اضافه کن. نمونهٔ پایین فرض می‌کنه interface و subnet دقیقاً همین نام‌ها رو دارن؛ copy روی host دیگر ممکنه همهٔ forwarding اون رو تغییر دهد، پس اجرا نکن مگر شبکه جدا و rules رو فهمیده باشی.

On a disposable gateway and isolated lab network, restrict forwarding to wg0→eth1 and the test subnet, then add masquerading in postrouting. The sample assumes these exact interfaces/subnets; applying it elsewhere can alter all host forwarding, so do not run it without an isolated network and understanding the existing rules.

table inet vpn_filter {
  chain forward {
    type filter hook forward priority filter; policy drop;
    iifname "wg0" oifname "eth1" ip saddr 10.77.0.0/24 ip daddr 192.0.2.0/24 ct state new,established,related accept
    iifname "eth1" oifname "wg0" ip daddr 10.77.0.0/24 ct state established,related accept
  }
}

table ip vpn_nat {
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    ip saddr 10.77.0.0/24 oifname "eth1" ip daddr 192.0.2.0/24 masquerade
  }
}

از client یک درخواست بفرست و روی LAN host capture کن: source باید gateway eth1 باشه، نه client tunnel IP. conntrack tool و syntax به توزیع وابسته‌اند؛ اگه نصب هست `conntrack -L` می‌تونه mapping رو نشون بده. NAT اینجا فقط روی ترافیک آزمایشگاه محدود شده. وقتی route برگشت اضافه شد، rule NAT رو در همون آزمایشگاه حذف کن و دوباره تست کن؛ اگه همچنان کار کرد، route دوطرفه کافی بوده.

Send a client request and capture on the LAN host: its source should now be the gateway’s eth1 address rather than the tunnel client IP. Conntrack tooling varies; where installed, `conntrack -L` can show the mapping. NAT here is restricted to lab traffic. Once a return route exists, remove the NAT rule in the lab and retest; if it still works, routing alone was sufficient.

خرابی دوم: forwarding خاموش هستFailure two: forwarding is disabled

این بار در VM آزمایشگاه مقدار IPv4 forwarding رو صفر کن، باقی تنظیمات رو دست‌نخورده بذار. request روی wg0 دیده می‌شه اما روی eth1 نمی‌ره؛ route lookup می‌تونه درست باشه و firewall هم اجازه داشته باشه، ولی kernel forward نمی‌کنه. این شاهدها رو پیش از fix کنار هم بذار تا خرابی رو به تغییر route اشتباه نسبت ندهی.

Now set IPv4 forwarding to zero in the lab VM while leaving other settings unchanged. The request appears on wg0 but not eth1; route lookup may be correct and firewall permissive, yet the kernel will not forward it. Correlate those observations before fixing so you do not blame the route incorrectly.

در آزمایش موقتی می‌شه مقدار رو موقتاً فعال کرد و پس از تست به مقدار قبلی برگردونه؛ روی production sysctl رو نساز و بعد فراموش نکن. اگه route و forwarding درست شدند ولی هنوز هیچ packet خروجی نیست، nftables/iptables chain و قانون رو ببین. فرمان‌های nft/iptables یک سیستم مشترک رو تغییر می‌دن؛ محتوای ruleهای موجود رو قبل از هر تغییر حفظ کن.

In a disposable test you can enable the value temporarily and restore the previous value afterward; do not make a production sysctl change and forget it. If routes and forwarding are correct but no packet exits, inspect nftables/iptables chains and policy. Firewall commands mutate shared system state; preserve existing rules before changing anything.

nftables یا iptables؟ یک قانون، نه دو بار NATnftables or iptables? One policy, not duplicate NAT

یک host ممکنه از nftables، iptables-nft compatibility یا iptables legacy استفاده کند. قبل از تغییر بفهم کدوم مدیر firewall مالک ruleهاست و rule set فعال چیه. جدول مثال بالا یک طرح محدود هست، نه دستور universal. Network manager یا VPN tooling می‌تونه ruleهای خودش رو اضافه کند؛ rule تکراری/نامتجانس، debugging و rollback رو سخت می‌کنه. NAT فقط source translation هست؛ filter chain باید اجازهٔ forward بدهد و state برگشت رو کنترل کند.

A host may use nftables, iptables-nft compatibility, or legacy iptables. Before changing anything, determine which firewall manager owns active rules. The table above is a scoped design, not a universal command. Network managers/VPN tools may add their own rules; duplicate or conflicting rules complicate diagnosis and rollback. NAT only translates addresses; a filter chain must allow forwarding and manage return state.

آزمایش مسیر رو با سه capture ثابت کنProve the path with three captures

در VMهای جدا یک نقشهٔ شبکه آزمایشی بساز: client روی tunnel subnet؛ gateway با wg0 و eth1؛ مقصد روی subnet خصوصی دوم. ابتدا route برگشت رو درست کن و بدون NAT آزمون کن. اگه ممکن نیست، NAT رو فقط روی destination/network همین آزمایشگاه محدود کن. آدرس‌های نمونه TEST-NET واقعی نیستند؛ از subnetهای مجزا در محیطت استفاده کن.

Build this isolated VM topology: client on a tunnel subnet; gateway with wg0 and eth1; destination on a second private subnet. Start with a return route and test without NAT. If you cannot add one, scope NAT to this lab destination/network only. TEST-NET addresses are documentation examples, not real targets; use non-overlapping lab prefixes.

برای هر مرحله capture همزمان روی wg0، eth1 و destination بگیر. filter رو به host/subnet آزمایش محدود کن؛ `tcpdump` فقط packetهایی رو نشان می‌ده که اون interface می‌بینه، نه علت config رو. timestamp و source/destination رو کنار هم بسنج.

Capture simultaneously on wg0, eth1, and the destination. Restrict filters to lab hosts/subnets; tcpdump shows packets visible at an interface, not the configuration cause. Compare timestamps and source/destination tuples.

sudo tcpdump -ni wg0 host CLIENT_TUN_IP
sudo tcpdump -ni eth1 host LAB_DEST_IP
sudo tcpdump -ni eth0 host VPN_ENDPOINT

درخواست رو بفرست و جدول بنویس: کجا packet دیده شد، کجا reply برگشت و آیا source تغییر کرده بود؟ اول حالت forwarding خاموش رو تست کن؛ بعد forwarding روشن ولی return route جاافتاده؛ سپس route برگشت؛ در آخر NAT رو فقط در صورت نیاز اضافه کن. بعد از evidence ruleهای آزمایش رو با scope ثبت‌شده حذف و مسیر رو verify کن.

Send a request and record where it appears, where the reply returns, and whether the source changed. Test disabled forwarding first; then enabled forwarding with a missing return route; add the return route; only then add NAT if needed. After capturing evidence, remove lab rules by their recorded scope and verify cleanup.

۱. مسیر ورود

packet از VPN client با مقصد LAN وارد کدوم interface gateway می‌شه؟

Through which gateway interface does a VPN client packet for the LAN arrive?

پاسخ

از tunnel interface، مثلاً wg0 یا tun0.

۲. forward خاموش

packet روی wg0 هست، روی eth1 نیست و ip_forward=0. فرضیهٔ قوی؟

A packet appears on wg0, not eth1; ip_forward is zero. Likely cause?

پاسخ

kernel IPv4 forwarding خاموش هست؛ firewall/route رو هم فقط پس از بررسی جدا نگه دار.

Kernel IPv4 forwarding is disabled; keep firewall and route as separate checks.

۳. packet بیرون رفت، پاسخ نیامد

request روی eth1 دیده می‌شه؛ مقصد route برگشت به tunnel subnet نداره. کدوم جهت مشکل داره؟

The request appears on eth1, but the destination lacks a route to the tunnel subnet. Which direction is broken?

پاسخ

return path؛ یا route برگشت بساز یا در صورت عدم امکان NAT محدود طراحی کن.

The return path; add a return route or use narrowly scoped NAT if routing cannot be changed.

۴. route برگشت بهتر

چه وقت routing از NAT بهتره؟

When is routing preferable to NAT?

پاسخ

وقتی مقصد/روتر رو می‌شه برای subnet tunnel route کرد؛ نشانی اصلی client حفظ و تشخیص ساده‌تر می‌شه.

When the destination/router can route the tunnel subnet; original client identity stays visible and diagnosis is clearer.

۵. masquerade

MASQUERADE چی رو معمولاً تغییر می‌ده؟

What does MASQUERADE usually rewrite?

پاسخ

source address رو به address خروجی gateway بدل می‌کنه؛ destination/filter قانون رو جایگزین نمی‌کنه.

It rewrites the source to the outgoing gateway address; it does not replace destination/filter policy.

۶. conntrack

conntrack برای reply چه کمکی می‌کنه؟

How does conntrack help the reply?

پاسخ

mapping stateful NAT رو پیدا می‌کنه و destination reply رو به client اصلی برمی‌گرداند.

It tracks the NAT mapping and translates the reply back to the original client.

۷. NAT firewall نیست

چرا وجود masquerade به‌تنهایی قانون امن forward رو ثابت نمی‌کنه؟

Why does masquerade alone not prove a safe forwarding policy?

پاسخ

NAT ترجمه هست؛ filter chain هنوز باید مبدأ/مقصد/وضعیت اتصال رو محدود کند.

NAT is translation; a filter chain must still restrict source/destination/connection state.

۸. longest prefix

default route و route /24 هر دو مقصد رو match می‌کنن. کدوم عموماً انتخاب می‌شه؟

A default and a /24 both match. Which is generally selected?

پاسخ

/24 اختصاصی‌تر، با درنظرگرفتن قانون/metrics سیستم.

The more-specific /24, subject to system policy and metrics.

۹. ip route get

این فرمان چی رو ثابت نمی‌کنه؟

What does ip route get not prove?

پاسخ

forwarding/firewall permit، packet delivery یا پاسخ برنامه رو.

Forwarding/firewall permission, packet delivery, or application response.

۱۰. مقصد SYN را دید

LAN host SYN رو می‌بینه، ولی هیچ replyی نیست. کجا رو inspect می‌کنی؟

The LAN host sees a SYN but emits no reply. What do you inspect?

پاسخ

listener/firewall مقصد، route محلی و capture همون host؛ gateway packet رو رسانده هست.

Destination listener/firewall, its local route, and host capture; the gateway delivered the packet.

۱۱. capture فقط روی wg0

capture روی wg0 درخواست رو نشان می‌ده، eth1 نه. سه بررسی gateway؟

wg0 sees the request, eth1 does not. Name three gateway checks.

پاسخ

route lookup، ip_forward و forward firewall قانون.

Route lookup, ip_forward, and forward firewall policy.

۱۲. NAT عیب را پوشاند

NAT روشن هست و ping کار کرد. آیا route برگشت درست شده؟

NAT is enabled and ping works. Has the return route been fixed?

پاسخ

نه؛ conntrack/source rewrite ممکنه نبود route رو پنهان کند. source مقصد و route رو جدا بررسی کن.

No; source rewriting may hide the missing route. Inspect packet source and routes independently.

۱۳. NAT scope

چرا masquerade روی همهٔ outbound traffic gateway رو نمی‌خوایم؟

Why avoid masquerading all outbound gateway traffic?

پاسخ

سطح اثر و عیب‌یابی زیاد می‌شه؛ source/subnet/interface/destination رو به نیاز محدود کن.

It broadens impact and complicates diagnosis; scope source/subnet/interface/destination to the need.

۱۴. IPv6

فقط ip_forward IPv4 رو فعال کردی، اما client مقصد IPv6 داره. نتیجه؟

You enabled only IPv4 forwarding, but the client targets IPv6. What follows?

پاسخ

IPv6 forwarding/route/firewall جداست؛ familyها رو مستقل بررسی کن.

IPv6 forwarding/routes/firewall are separate; inspect each address family independently.

۱۵. nft policy drop

چرا اجرای forward chain با قانون drop روی host اصلی خطرناک هست؟

Why is applying a forward chain with drop policy risky on a real host?

پاسخ

ممکنه شبکهٔ container/VPN/VMهای دیگر رو قطع کند؛ فقط isolated آزمایشگاه و با rollback.

It may interrupt containers, VPNs, or other VMs; use an isolated lab and rollback plan.

۱۶. stateful reply rule

چرا برگشت established/related رو از inbound new جدا می‌کنیم؟

Why distinguish established/related return traffic from new inbound connections?

پاسخ

تا پاسخ به اتصال مجاز برگشت بخورد، ولی اتصال تازهٔ ناخواسته به client route نشه.

Allow replies to authorized sessions without allowing unsolicited new connections to the client subnet.

۱۷. endpoint alive، data down

VPN handshake زنده هست ولی LAN unavailable. کدوم مسیر رو capture می‌کنی؟

The VPN handshake is live but the LAN is unavailable. Which path do you capture?

پاسخ

inner packet روی tunnel، egress gateway، LAN destination و reply تا tunnel؛ outer endpoint فقط health peer رو می‌گه.

Inner packet on tunnel, gateway egress, LAN destination, and reply toward tunnel; outer endpoint proves only peer reachability.

۱۸. incident report

برای خرابی مسیر، symptom، capture سه interface، route get، forwarding value، firewall rule و repair/verification رو در incident note کوتاه ثبت کن. NAT رو فقط با دلیل انتخاب کن.

For a routing incident, record symptom, captures on three interfaces, route lookup, forwarding value, firewall rule, and repair/retest in a short note. Justify NAT if you choose it.

معیار

شاهد باید نشان دهد packet کجا متوقف شد و reply path چطور برگشت؛ «NAT روشن کردم» تشخیص نیست.

Evidence should show where the packet stopped and how the reply returned; “I enabled NAT” is not a diagnosis.

رمزنگاری فقط یک hop از مسیر هستEncryption is only one part of the route

VPN ممکنه packet رو رمز کند و به gateway برسونه؛ gateway هنوز باید forwarding و firewall مجاز داشته باشه، مقصد باید reply رو route کند، و DNS باید resolver مناسب رو به کار برد. route برگشت رو می‌شه با NAT دور زد، ولی source identity رو از دست می‌دهی و ریشهٔ route اشتباه می‌مونه. اول capture و lookup؛ بعد کم‌دامنه‌ترین repair؛ آخر همون test رو تکرار کن.

A VPN can encrypt a packet and deliver it to a gateway, but the gateway still needs forwarding/firewall permission, the destination must route a reply, and DNS must use the intended resolver. NAT can work around a missing return route, at the cost of source identity and a lingering routing flaw. Capture and inspect first; make the narrowest repair; rerun the same test.

فصل بعد DNS رو از مسیر تونل جدا می‌کنه: کی hostname رو resolve می‌کنه و چطور مطمئن شویم query از قانون بیرون نزده هست.
