Certificates, configuration, and comparison with WireGuard.

کلید peer ساده‌ست؛ اما می‌خوایم هویت صادر و لغو کنیمStatic peers are simple; now we need issued and revocable identities

برای دو ماشین، public keyها خیلی تمیز جواب می‌دن. ولی فرض کن ده‌ها کاربر داری و هر کدوم باید هویت جدا داشته باشن؛ یکی وارد تیم می‌شه، یکی می‌ره، یکی certificateش لو می‌ره. اینجا PKI معنی پیدا می‌کنه. OpenVPN می‌تونه با CA و certificate برای هر client هویت جدا بسازه. هزینه‌اش هم معلومه: قطعات بیشتر، تنظیم بیشتر و چیزهای بیشتری که باید درست نگهشون داری.

WireGuard’s peers know one another by public keys and its configuration is compact. Now imagine a team with dozens of clients that needs separately issued, time-bounded certificates and the ability to revoke one departing user. OpenVPN commonly uses TLS and PKI for that lifecycle—with more pieces to manage: a CA, server certificate, client certificates, and configuration.

CA هویت‌ها رو صادر می‌کنه؛ private CA key نباید روی VPN server بی‌دلیل بمونه.

The CA issues identities; its private signing key should not casually live on the VPN server.

در TLS mode، OpenVPN از control channel برای mutual certificate authentication و مذاکرهٔ کلیدهای data channel استفاده می‌کنه. بعد packetهای tunnel در data channel محافظت می‌بشن. گزینه‌هایی مثل `tls-crypt` می‌تونن control-channel packetها رو هم لایه‌ای اضافه بپوشانند؛ جای CA و certificate identity رو نمی‌گیرند. OpenVPN 2.6 Manual

In TLS mode, OpenVPN uses a control channel for mutual certificate authentication and data-channel key negotiation. Tunnel packets then use the protected data channel. Options such as `tls-crypt` can add another layer for control-channel packets; they do not replace the CA or certificate identities.

CA، server و هر client هویت جدا دارنThe CA, server, and every client have distinct identities

Easy-RSA کمک می‌کنه CA بسازی، برای server/client key و request صادر کنی و request رو با نقش درست sign کنی. مدل امن‌تر این هست که private keyهای server/client همون‌جا تولید بشن و request به CA برسه؛ private CA key آفلاین یا محدود بمونه. نمونهٔ دستورها به Easy-RSA 3 مربوط هست و promptهای تعاملی/مسیرها با بسته و نسخه فرق می‌کنه:

Easy-RSA helps create a CA, generate server/client keys and requests, and sign each request for the correct role. A safer pattern is to generate server/client private keys where they will be used and send certificate requests to the CA; keep the CA private key offline or tightly restricted. These commands illustrate Easy-RSA 3; prompts and paths vary by package/version:

./easyrsa init-pki
./easyrsa build-ca
# on a separate server/client request host:
./easyrsa init-pki
./easyrsa gen-req vpn-server nopass
./easyrsa gen-req laptop-01 nopass
# transfer only .req files to the CA securely
./easyrsa import-req vpn-server.req vpn-server
./easyrsa sign-req server vpn-server
./easyrsa import-req laptop-01.req laptop-01
./easyrsa sign-req client laptop-01

`nopass` در این نمونه فقط برای VM موقتی و راحتی آزمایشگاه هست؛ در محیط واقعی، حفاظت key رو با سیاست سازمان بسنج. CA key رو با client profile bundle نکن. CA-issued certificate رو با `openssl x509 -in FILE -noout -subject -issuer -dates` بخوان؛ این subject/issuer/validity رو نشان می‌ده، نه اینکه certificate مقصد درست load شده یا TLS اتصال موفق هست. Easy-RSA 3 Quickstart

`nopass` is used here only for disposable VMs and lab convenience; production key protection needs an explicit policy. Never bundle the CA key in a client profile. Inspect an issued certificate with `openssl x509 -in FILE -noout -subject -issuer -dates`; this reports identity and validity, not whether the intended certificate was loaded or a TLS session will succeed.

دو config، دو نقشTwo configs, two roles

در config سرور، `server` یک TUN subnet می‌سازه و server mode رو فعال می‌کنه؛ فایل‌های CA/server cert/private key باید مسیر امن و دسترسی محدود داشته باشن. نمونه برای OpenVPN 2.6-style هست؛ directiveهای نسخهٔ نصب‌شده رو با manual همون نسخه validate کن.

On the server, `server` configures server mode and a TUN subnet. CA/server certificate/private key files need controlled paths and permissions. This is a 2.6-style sketch; validate directives against the manual for your installed version.

port 1194
proto udp
dev tun
topology subnet
server 10.8.0.0 255.255.255.0
ca pki/ca.crt
cert pki/issued/vpn-server.crt
key pki/private/vpn-server.key
remote-cert-tls client
persist-key
persist-tun
verb 3

client profile هم client mode، endpoint، CA و certificate/key خودش رو داره. `remote-cert-tls server` نقش certificate سمت server رو بررسی می‌کنه تا client گواهی client اشتباه رو به‌جای server نپذیرد. CA trust و server role check هر دو لازم‌اند.

The client profile sets client mode, endpoint, CA, and its own certificate/key. `remote-cert-tls server` checks the server certificate’s role so the client does not accept a client certificate as the server identity. CA trust and server-role validation are both important.

client
dev tun
proto udp
remote VPN_SERVER_HOST 1194
resolv-retry infinite
nobind
persist-key
persist-tun
ca ca.crt
cert laptop-01.crt
key laptop-01.key
remote-cert-tls server
verb 3

چند directive در config sample بسته به build و library می‌تونه warning بدهد. از cipherهای legacy یا `comp-lzo` بی‌دلیل استفاده نکن؛ OpenVPN 2.6 negotiation/defaultها رو مستند کرده و نسخه‌های قدیمی‌تر ممکنه رفتار دیگری داشته باشن. پس config رو با `openvpn --show-ciphers` و log نسخهٔ واقعی بررسی کن، نه با copy/paste کور.

Some directives may warn depending on build and crypto library. Avoid legacy ciphers or `comp-lzo` without a specific reason; OpenVPN 2.6 documents modern negotiation/defaults while older releases may behave differently. Inspect the actual version/log rather than blindly copying a cipher line.

UDP یا TCP؛ سازگاری رو با کارایی قاطی نکنUDP or TCP: do not confuse compatibility with performance

OpenVPN اغلب روی UDP انتخاب می‌شه؛ VPN خودش reliability کنترل channel رو داره و data flow روی UDP از TCP-over-TCP معمولاً بهتر کنار میاد، مخصوصاً وقتی packet loss رخ می‌ده. TCP می‌تونه روی شبکه‌ای که UDP رو می‌بنده سازگاری بدهد، اما nesting TCP و recovery/loss behavior ممکنه latency/throughput رو بدتر کند. هیچ‌کدوم برندهٔ همگانی نیست: network قانون، نوع بار و benchmark واقعی تعیین می‌کنه.

OpenVPN is often deployed over UDP; its control channel has reliability behavior of its own, and UDP data transport generally avoids the pathologies of TCP-over-TCP, especially with packet loss. TCP can improve compatibility on networks that block UDP, but nested TCP recovery/loss behavior may hurt latency or throughput. There is no universal winner: network policy, workload, and measurement decide.

برای مقایسه، فقط یک متغیر رو عوض کن: protocol، endpoint، cipher defaults و route رو ثابت نگه دار. چند run انجام بده و latency, throughput, loss و reconnect رو جدا بسنج؛ ping کوتاه معیار ظرفیت نیست. کنترل firewall و ISP هم می‌تونه UDP/TCP رو متفاوت محدود کند.

For a fair comparison, change one variable: protocol. Keep endpoint, cipher defaults, and route fixed. Measure latency, throughput, loss, and reconnect behavior across repeated runs; a short ping is not a capacity test. Firewalls and providers may treat UDP/TCP differently.

آزمایش: دو VM، یک tunnel و یک client certificateLab: two VMs, one tunnel, one client certificate

این آزمایشگاه فقط در دو Linux VM دورریختنی یا شبکهٔ منزوی اجرا بشه. نصب OpenVPN/Easy-RSA و بازکردن UDP/1194 فقط در firewall همون VMها انجام بشه؛ روی router یا server واقعی port عمومی باز نکن. اول CA رو جدا و محدود بساز، بعد server/client requestها رو role درست sign کن. فایل‌های private رو از همون سیستم صادرکننده خارج نکن.

Run this only in two disposable Linux VMs or an isolated network. Install OpenVPN/Easy-RSA and permit UDP/1194 only in those lab firewalls; do not open a real router or production server. Create the CA separately, then sign server/client requests with the correct roles. Keep private keys on their issuing hosts.

وقتی cert/keyها رو امن منتقل کردی، permission فایل‌ها رو ببین و server config رو foreground اجرا کن تا log رو زنده بخوانی:

After securely transferring the required certificates and keys, check file permissions and run the server in the foreground so its logs are visible:

sudo openvpn --config server.conf

در client، `openvpn --config client.conf` رو اجرا کن. مدرک اتصال فقط log «Initialization Sequence Completed» نیست: `ip addr show tun0` و `ip route` رو هم بخوان، سپس tunnel IP رو ping کن. نام interface ممکنه `tun0` نباشه. ping موفق، ICMP path رو نشان می‌ده—not general Internet routing.

Run `openvpn --config client.conf` on the client. A log line like “Initialization Sequence Completed” is not enough: inspect `ip addr show tun0` and `ip route`, then ping the tunnel IP. The interface may not be named tun0. A successful ping demonstrates ICMP reachability, not general Internet routing.

خرابی عمدی: certificate اشتباه یا route جاافتاده؟Deliberate failure: wrong certificate or missing route?

بار اول عمداً client cert صادرشده برای نقش server یا CA اشتباه رو وارد کن. client/server log باید در TLS verification/authentication شکست نشان دهد؛ پیش از fix زمان log دو سمت، subject/issuer و تاریخ certificate رو بگیر. بعد certificate client معتبر صادرشده از CA درست رو جایگزین و همون اتصال رو تکرار کن. راز key رو برای رفع مشکل به ماشین دیگری کپی نکن.

For the first failure drill, deliberately use a client certificate with the wrong role or the wrong CA. Client/server logs should show TLS verification or authentication failure. Before fixing, capture both timestamps, subject/issuer, and certificate dates. Then use a valid client certificate from the correct CA and repeat; do not copy private keys around as a shortcut.

بار دوم handshake رو برقرار نگه دار ولی route مقصد آزمایشی رو حذف کن یا push نکن. control/data channel می‌تونه برقرار بمونه اما subnet کار نکند. `ip route get DESTINATION`، log route push، forwarding و firewall رو بخوان. handshake موفق احراز تونل رو ثابت می‌کنه؛ route یا رسیدن به application رو نه. بعد route رو در config درست و همون destination رو دوباره verify کن.

For the second drill, keep the handshake working but remove or omit the route to a test destination. Control/data channels may be up while the subnet remains unreachable. Inspect `ip route get DESTINATION`, pushed-route logs, forwarding, and firewall. A successful handshake proves the tunnel authenticated—not routing or application reachability. Correct the route and retest the same destination.

OpenVPN یا WireGuard؟ به نیاز نگاه کنOpenVPN or WireGuard? Start with the requirement

WireGuard مدل key/peer و config جمع‌وجورتری داره و برای بعضی محیط‌ها نگهداری آسان‌تری می‌ده. OpenVPN به TLS/PKI، client certificateهای مستقل، auth integration و گزینه‌های transport متنوع تکیه می‌کنه و به همین خاطر lifecycle و config بیشتری می‌خواد. پشتیبانی OS، قانون سازمان، client management، NAT/firewall و skill تیم ممکنه انتخاب رو عوض کند. benchmark یا ادعای «همیشه سریع‌تر/امن‌تر» بدون workload و version مشخص نکن.

WireGuard has a compact key/peer model that can be simpler to operate in some environments. OpenVPN uses TLS/PKI, individual client certificates, authentication integrations, and varied transport options, bringing more lifecycle/configuration work. OS support, organizational policy, client management, NAT/firewalls, and team skills can change the choice. Avoid claims of “always faster/safer” without a version and workload.

هویت سالم، route سالم، دو مدرک جداValid identity and valid route need separate evidence

OpenVPN با TLS/PKI هویت server/client رو بررسی می‌کنه و control channel کلیدهای data channel رو مذاکره می‌کنه. بعد از اتصال، TUN و routeها باید packet رو به مقصد برسونن. certificate error رو با route عوض نکن؛ handshake موفق رو هم معادل دسترسی به subnet ندان. UDP معمولاً شروع خوبی برای کارایی هست، TCP گاهی سازگاری می‌ده؛ انتخاب رو با firewall و benchmark بگیر. نسخهٔ OpenVPN/Easy-RSA و provider می‌تونه directiveها رو عوض کند، پس manual همون build معیار هست.

OpenVPN uses TLS/PKI to verify server/client identities, and the control channel negotiates data-channel keys. After connection, TUN and routes must deliver packets to their destination. Do not fix a certificate error by changing routes, or mistake a successful handshake for subnet access. UDP is often a good performance starting point; TCP can help compatibility. Choose based on firewall behavior and measurements. OpenVPN/Easy-RSA versions and providers affect directives, so use the installed build’s manual.
