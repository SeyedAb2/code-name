VPN چیه: مدل تونل

What a VPN is: the tunnel model

Proxy معمولاً مسیر یه برنامه رو عوض می‌کنه؛ VPN می‌تونه مسیر خود packetها رو عوض کنه.

The fundamental difference from a proxy is the network layer.

۸۰دقیقهminutes
۱۸تمرینexercises

برنامهٔ تازه‌ای نصب نکردی، ولی مسیر همه‌چیز عوض شدNo new app setting, yet the route changed

اینجا یه تغییر مدل ذهنی داریم. با proxy معمولاً برنامه می‌دونه باید درخواستش رو به یه واسطه بده. ولی VPN می‌تونه یه interface و چند route تازه به سیستم اضافه کنه و بعد kernel تصمیم بگیره کدوم packet بره توی tunnel. یعنی ممکنه خود برنامه اصلاً ندونه VPNی در کاره. فقط حواست باشه: «VPN وصله» هنوز یعنی «همهٔ ترافیک از VPN رد می‌شه» نیست؛ جدول route حرف آخر رو می‌زنه.

With a proxy, an application or operating system typically knows which intermediary should receive a selected request. A VPN can add an IP interface and routes: the kernel sends packets for selected destinations through the tunnel. Applications need not be individually proxy-aware—but that does not mean all traffic automatically uses the tunnel. Routes decide which packets enter.

آدرس بیرونی مقصد tunnel با مقصد packet داخلی فرق داره؛ تونل خودش هم باید از route قابل‌دسترسی استفاده کند.

The tunnel’s outer destination differs from the inner packet destination; the tunnel endpoint itself still needs a reachable route.

مدل دقیق به VPN بستگی داره. در tunnel شبکه‌ای رمزگذار، packet داخلی به‌عنوان payload در packet بیرونی منتقل می‌شه؛ gateway سمت مقابل اون رو decrypt و route می‌کنه. TUN مجازی معمولاً IP packet می‌بینه، TAP Ethernet frame. روی Linux هر دو device می‌تونن packet/frame رو میان kernel و برنامهٔ userspace جابه‌جا کنند؛ نیاز دسترسی و پیکربندی route جداست. Linux kernel: TUN/TAP

The exact model depends on the VPN. A network tunnel can carry an inner packet inside an outer packet; the peer decrypts and routes it. A TUN device works with IP packets; TAP with Ethernet frames. On Linux, both can pass packets/frames between kernel and userspace software, while permissions and routes remain separate concerns.

Proxy و VPN: هر دو route می‌دن، اما در لایهٔ متفاوتProxy and VPN both redirect traffic, but at different layers

HTTP proxy می‌فهمه HTTP request, URL و header چیه. SOCKS5 مقصد socket رو می‌گیره و byte stream رو relay می‌کنه، ولی همچنان برنامه اون رو انتخاب می‌کنه. VPN شبکه‌ای به OS route/interface می‌ده و می‌تونه packetهای چند برنامه رو بگیره. VPN الزاماً app traffic رو می‌خونه؟ نه؛ encryption/VPN software معمولاً packetها رو tunnel می‌کنه، نه اینکه همهٔ protocolهای برنامه رو parse کند.

An HTTP proxy understands HTTP requests, URLs, and headers. SOCKS5 accepts a socket destination and relays a byte stream, but the application still selects it. A network VPN installs or uses OS routes and an interface to carry packets from many applications. Does a VPN necessarily read app content? No: tunnel software typically transports packets rather than parsing each application protocol.

Route تصمیم می‌گیره؛ «اتصال VPN» کافی نیستThe route decides; “VPN connected” is not enough

routeها با prefix مقصد سنجیده می‌بشن؛ معمولاً longest prefix match از route کم‌اختصاصی‌تر جلوتر هست. split tunnel می‌تونه فقط شبکهٔ سازمان رو به VPN بفرسته و اینترنت عمومی رو مستقیم نگه داره. full tunnel معمولاً default routeهای IPv4/IPv6 رو از gateway VPN می‌گذراند. تنظیم فقط IPv4 می‌تونه IPv6 رو بیرون tunnel باقی بذارد. هر سیستم‌عامل/کلاینت ممکنه route قانون و kill switch متفاوتی پیاده کند.

Routes are matched by destination prefix; the longest matching prefix generally beats a less-specific route. A split tunnel sends selected private networks through the VPN while public Internet traffic remains direct. A full tunnel typically sends IPv4/IPv6 default routes through the VPN gateway. Configuring only IPv4 may leave IPv6 outside the tunnel. Client and OS implementations can differ in route policy and kill-switch behavior.

در Linux، بدون تغییر هیچ route، ببین kernel برای یک آدرس نمونه چه تصمیمی می‌گیره: ip route get 198.51.100.7. این بازهٔ TEST-NET-2 برای مستندات هست؛ درخواست شبکه‌ای نمی‌فرسته، فقط lookup می‌کنه. در خروجی دنبال dev و via بگرد. این تصمیم فعلی میزبان رو ثابت می‌کنه؛ نه وضعیت peer VPN یا رسیدن packet به اینترنت رو.

On Linux, inspect the kernel’s current decision without changing routes: ip route get 198.51.100.7. That address belongs to documentation-only TEST-NET-2; the command performs a route lookup, not a network request. Read the dev and via fields. This proves the host’s current lookup decision—not VPN peer health or end-to-end reachability.

ip -6 route

خروجی واقعی به سیستم تو وابسته هست. اگه Linux نداری، معادل route table رو فقط مشاهده کن (Windows: `route print` یا `Get-NetRoute`). پیش از هر command تغییردهنده، مسیر فعلی و راه برگشت رو ذخیره کن؛ این فصل route اضافه/حذف نمی‌کنه.

Actual output depends on your host. On Windows, observe the equivalent with `route print` or `Get-NetRoute`. Before any route-changing command, preserve the existing route and rollback path; this chapter deliberately adds and removes no routes.

Full tunnel یا split tunnel؟Full tunnel or split tunnel?

این یک انتخاب عملیاتی هست، نه درجه‌بندی امنیت. full tunnel مسیر بیشتری رو از gateway عبور می‌ده و خروجی عمومی ممکنه IP gateway باشه؛ ولی اگه DNS، IPv6 یا برنامه‌ای از قانون مستثنا بشه، leak هنوز ممکنه. split tunnel دسترسی به شبکهٔ مشخص رو می‌ده و بقیه رو مستقیم می‌فرسته؛ routeها و DNS suffixها باید دقیق باشن. VPN provider نیز می‌تونه مقصدها و metadata خروجی رو ببینه.

This is an operational choice, not a security score. Full tunnel sends more traffic through the gateway and may expose the gateway’s public egress IP—but DNS, IPv6, or excluded applications can still bypass policy. Split tunnel sends selected networks through the VPN and the rest directly; routes and DNS suffixes must be precise. The VPN provider may still observe destinations and egress metadata.

kill switch هم تضمین ذاتی VPN نیست؛ بعضی clientها firewall rule می‌سازن تا هنگام قطع tunnel، ترافیک انتخابی بیرون نرود. از app خودت بررسی کن دقیقاً چه route/firewall rule ایجاد می‌کنه و IPv4/IPv6 رو جدا بیازما. نام feature به‌تنهایی مدرک نیست.

A kill switch is not inherent to every VPN. Some clients add firewall rules to prevent selected traffic from escaping when the tunnel drops. Check what your client actually installs and test IPv4 and IPv6 separately. A feature label is not evidence.

TUN و TAP رو در حد انتخاب interface بشناسKnow TUN and TAP as interface choices

TUN با IP packet کار می‌کنه و برای خیلی از tunnelهای routed انتخاب طبیعی هست. TAP با Ethernet frame کار می‌کنه و برای bridge/L2 نیازهای خاص کاربرد داره؛ broadcast، bridge و DHCP رو هم وارد طراحی می‌کنه. TAP «بهتر» یا «کامل‌تر» نیست؛ اگه فقط شبکهٔ IP می‌خوای، انتقال Ethernet شاید سربار و پیچیدگی اضافه باشه. جزئیات driver در OS فرق داره.

TUN works with IP packets and is a natural choice for many routed tunnels. TAP works with Ethernet frames and serves specific bridging/L2 needs, bringing broadcast, bridging, and DHCP concerns. TAP is not “better” or “more complete”; carrying Ethernet may add overhead and complexity when you only need IP routing. Driver behavior varies by OS.

خرابی عمدیِ مفهومی: endpoint رو داخل تونل فرستادیDeliberate conceptual failure: you routed the endpoint into its own tunnel

VPN client برای نگه‌داشتن tunnel باید به public endpoint خودش packet بیرونی بفرسته. اگه route جدید باعث بشه همین endpoint هم از داخل تونل route بشه، بسته باید برای عبور از tunnel به همون tunnel برسه؛ recursion یا disconnect محتمل هست. معمولاً client برای endpoint route استثنایی/host route نگه می‌داره یا قانون routing می‌سازه. این جزئیات implementation-specific هست.

A VPN client must send outer packets to its public endpoint to keep the tunnel alive. If a new route also sends that endpoint through the tunnel, packets need the tunnel to reach the tunnel; recursion or disconnect can follow. Clients often preserve an endpoint exception/host route or use policy routing. The implementation is client-specific.

قبل از fix، route lookup برای endpoint واقعی رو روی یک VM آزمایشی بررسی کن؛ دستور read-only ip route get VPN_ENDPOINT نشان می‌ده خروجی از کدوم `dev` می‌ره. اگه interface همون tunnel باشه، فرضیهٔ recursion قوت می‌گیره؛ اما routing rules، mark و tables هم ممکنه تصمیم رو عوض کنند—فقط `ip route` اصلی کافی نیست. توی این فصل config رو روی host روزمره خراب نکن و route جدید نزن.

Before fixing anything, inspect the route lookup for the real endpoint on a disposable VM. The read-only command ip route get VPN_ENDPOINT reveals the selected device. If it is the tunnel itself, recursion is plausible; policy rules, marks, and tables can also change the decision, so the main route table alone may be insufficient. Do not break your daily host or add routes in this chapter.

DNS خرابی جداگانه‌ای هست: اگه endpoint hostname resolve نمی‌شه، ممکنه پیش از route lookup شکست بخوری؛ اگه route درست ولی DNS leak داری، tunnel برقراره اما resolver از مسیر موردنظر نرفته. ترتیب رو حفظ کن: DNS endpoint، route endpoint، handshake tunnel، route مقصد داخلی، DNS اپ. فصل DNS داخل tunnel این آخرین مرز رو باز می‌کنه.

DNS failure is a separate branch: if the endpoint hostname cannot resolve, failure may precede route lookup. If the route is correct but DNS leaks, the tunnel can be up while the resolver bypasses policy. Keep the sequence clear: endpoint DNS, endpoint route, tunnel handshake, inner destination route, application DNS. A later chapter handles DNS inside the tunnel.

آزمایش: مسیر موردانتظار رو پیش‌بینی کنLab: predict the route before looking

روی Linux VM یا محیط محلی مجاز، `ip route` و `ip route get` رو بخوان و مسیر مقصد عمومی و یک private subnet آزمایشی رو جدا ثبت کن. هنوز tunnel نساخته‌ای؛ هدف این هست که route به‌تنهایی رو از رمزنگاری جدا کنی. اگه WireGuard interface نداری، خروجی جعلی نساز—رابطهٔ فرضی رو روی کاغذ رسم کن.

On a Linux VM or authorized local environment, inspect `ip route` and `ip route get` for a public destination and a test private subnet. You have not created a tunnel; the goal is to distinguish routing from encryption. If no WireGuard interface exists, do not invent output—draw the hypothetical relationship.

در یک نمودار فرضی، برای split tunnel یک route مشخص مثلاً `10.40.0.0/16` از `tun0` و default route از interface فیزیکی هست. برای full tunnel default route هم به `tun0` می‌ره، اما endpoint بیرونی باید استثنا داشته باشه. پیش‌بینی کن packet به 10.40.2.8 و 198.51.100.7 از کدوم interface می‌روند؛ بعد با route lookup واقعی در موقتی آزمایشگاه مقایسه کن.

In a hypothetical split tunnel, a route such as `10.40.0.0/16` uses `tun0`, while the default route remains on the physical interface. In a full tunnel, the default route also uses `tun0`, but the outer endpoint needs an exception. Predict which interface carries packets to 10.40.2.8 and 198.51.100.7, then compare with actual lookups in a disposable lab.

مدرک رو چهار بخش کن: route انتخابی؛ endpoint بیرونی؛ DNS resolver؛ و مقصد نهایی. این‌ها مستقل‌اند. اگه فقط interface up می‌بینی، هنوز ثابت نکرده‌ای packet به peer رسیده، DNS درسته یا برنامه به سرویس وصل شده.

Record four separate facts: selected route, outer endpoint, DNS resolver, and final destination. They are independent. An up interface alone proves neither peer reachability, correct DNS, nor application connectivity.

یک interface جدید، یک مرز اعتماد جدیدA new interface is a new trust boundary

proxy به برنامه کمک می‌کنه یک اتصال منتخب رو از واسطه بگیره؛ VPN شبکه‌ای route رو عوض می‌کنه تا packetهای مطابق قانون از tunnel رد بشن. TUN packetهای IP می‌بینه، TAP frameهای Ethernet. full/split tunnel، IPv6، DNS و route endpoint هر کدوم مسیر جدا دارن. دیدن interface یا پیام «connected» فقط یک شاهد هست، نه اثبات کل مسیر.

A proxy lets an application send selected connections through an intermediary; a network VPN changes routes so policy-selected packets enter a tunnel. TUN handles IP packets and TAP Ethernet frames. Full/split routing, IPv6, DNS, and the endpoint route are separate paths. An interface or “connected” message is evidence, not proof of the whole path.
