MTU, encryption overhead, and measurement.

۸۰دقیقهminutes
۱۸تمرینexercises

«VPN کند است» هنوز تشخیص نیست“The VPN is slow” is not yet a diagnosis

کاربر می‌گوید call مکث دارد، دانلود نصف شده و ping گاهی بالا می‌رود. این‌ها سه نشانه‌اند با علت‌های ممکن متفاوت: latency، throughput، jitter/loss، CPU، MTU یا سرور دورتر. قبل از تغییر cipher یا interface یک baseline می‌گیریم، بعد فقط یک متغیر را عوض می‌کنیم.

A user reports a laggy call, half-speed downloads, and occasional ping spikes. These are different symptoms with different possible causes: latency, throughput, jitter/loss, CPU, MTU, or a farther-away server. Before changing ciphers or interfaces, establish a baseline and then vary one factor at a time.

baseline مستقیم را با همان دو میزبان، ساعت، پروتکل و بار بگیر؛ بعد از tunnel همان آزمون را تکرار کن. اگر مسیر مستقیم و tunnel endpointها متفاوت باشند، نتیجه فقط مقایسهٔ دو مسیر است، نه هزینهٔ خالص رمزنگاری. آزمون‌های هم‌زمان می‌توانند خودشان شبکه را اشباع کنند.

Measure the direct baseline with the same hosts, time window, protocol, and load; then repeat through the tunnel. If endpoints differ, you are comparing two paths, not encryption cost alone. Concurrent tests can saturate the network themselves.

اگر packet داخلی و سربار از MTU بیرونی بزرگ‌تر شوند، fragmentation یا PMTUD لازم می‌شود.

If inner packet plus overhead exceeds the outer MTU, fragmentation or PMTU discovery must handle it.

اول مشخص کن کدام «کندی» را اندازه می‌گیریFirst identify which kind of slowness you are measuring

latency زمان رفت‌وبرگشت است؛ throughput نرخ انتقال داده است؛ jitter تغییر latency و packet loss گم‌شدن بسته‌هاست. ping برای RTT/روند و گاهی loss مفید است، اما throughput را نمی‌سنجد. iperf3 انتقال کنترل‌شده می‌سازد، ولی به‌تنهایی رفتار browser، DNS یا کلاینت VPN را توضیح نمی‌دهد.

Latency is round-trip time; throughput is transfer rate; jitter is latency variation, and packet loss is missing traffic. Ping helps inspect RTT/trends and sometimes loss, but not throughput. iperf3 generates a controlled transfer but does not by itself characterize browsers, DNS, or the VPN client.

روی peer آزمایشی سرور iperf3 را بالا بیاور. client یک run کوتاه و محدود انجام دهد؛ `-t 10` زمان را محدود می‌کند، `-P 2` دو stream موازی می‌سازد. server port را فقط در lab باز کن. خروجی receiver throughput همان run را نشان می‌دهد؛ این عدد را با شبکهٔ واقعی و ترافیک دیگران یکی نگیر.

Start iperf3’s server on the test peer. Run a short, bounded client test; `-t 10` limits duration and `-P 2` uses two parallel streams. Expose the server port only in the lab. Receiver throughput describes that run, not every real workload or shared-network condition.

# server peer
iperf3 -s
# client direct, then repeat through the lab tunnel
iperf3 -c PEER_IP -t 10 -P 2

همان test را یک بار مستقیم و یک بار به tunnel IP بزن. بهتر است چند نوبت ثبت کنی و median/range را مقایسه کنی. یک run ممکن است با CPU throttling، Wi‑Fi، server load یا congestion تغییر کند. روی TCP retransmit و receiver rate هم نگاه کن؛ روی UDP فقط bitrate محدود و کم‌کم افزایش بده تا شبکه را flood نکنی.

Run the same test directly and against the tunnel IP. Repeat and compare median/range. One run can change with CPU throttling, Wi-Fi, server load, or congestion. Inspect TCP retransmits and receiver rate; for UDP, use a bounded bitrate and increase gradually rather than flooding the network.

iperf3 -c PEER_IP -u -b 5M -t 10

همزمان CPU دو endpoint را با `top`/Task Manager ببین. اگر throughput پایین و یک core پر است، crypto/packet processing محتمل‌تر است؛ اگر CPU آزاد و loss بالا است، route/radio/queue را بررسی کن. این‌ها فرضیه‌اند؛ telemetry و repetition لازم است.

Watch both endpoints’ CPU with `top`/Task Manager. Low throughput with one core saturated points toward crypto/packet processing; low CPU with loss suggests route/radio/queue issues. These are hypotheses, not conclusions; correlate metrics and repeat.

چرا MTU داخل tunnel کوچک‌تر می‌شود؟Why does the tunnel’s usable MTU shrink?

packet داخلی خودش header دارد؛ tunnel آن را encapsulate می‌کند و outer IP/UDP و header پروتکل VPN هم فضا می‌گیرند. outer path MTU برای کل packet بیرونی سقف دارد. اگر payload داخلی خیلی بزرگ باشد، IP fragmentation یا Path MTU Discovery باید راهی پیدا کند؛ بعضی firewallها ICMP Packet Too Big را drop می‌کنند و PMTUD black hole می‌شود: بستهٔ کوچک کار می‌کند، بزرگ hang/retry می‌شود.

An inner packet already has headers. Encapsulation adds outer IP/UDP and VPN headers, while the outer path MTU limits the full packet. Oversized inner payloads require IP fragmentation or Path MTU Discovery. Some firewalls drop ICMP Packet Too Big, creating a PMTUD black hole: small packets work while large transfers stall or retry.

سربار ثابت جهانی اعلام نمی‌کنیم؛ IPv4/IPv6 outer, protocol, options و encapsulation مقدار را عوض می‌کنند. روی Linux در lab با IPv4 می‌توان اندازهٔ payload را کنترل‌شده امتحان کرد: `ping -M do` نمی‌گذارد packet fragment شود و `-s` اندازهٔ ICMP payload را می‌دهد. با گام‌های محدود از کوچک شروع کن؛ rate پایین و count محدود بگذار.

There is no universal overhead number: outer IPv4/IPv6, protocol, options, and encapsulation change it. On Linux, test bounded IPv4 payload sizes in a lab: `ping -M do` prevents fragmentation and `-s` sets ICMP payload size. Start small, step carefully, and limit count/rate.

ping -c 3 -W 2 -M do -s 1200 TUNNEL_PEER
tracepath TUNNEL_PEER

برای `ping`, اندازهٔ payload به ICMP و IP header هم نیاز دارد؛ در IPv4 معمولاً 20 byte IP و 8 byte ICMP اضافه است، اما optionها ممکن است تغییر دهند. در IPv6 header اندازهٔ دیگری دارد. `tracepath` اگر ICMP feedback در دسترس باشد PMTU را تخمین می‌زند. failure می‌تواند echo filtering هم باشد، پس با TCP transfer/packet capture هم cross-check کن.

The ping payload size is in addition to ICMP and IP headers; IPv4 commonly adds 20 bytes of IP and 8 bytes of ICMP, while options can change that. IPv6 has different base headers. `tracepath` can estimate PMTU when ICMP feedback is available. A failed ping may simply be filtered, so cross-check with TCP transfer and captures.

خرابی عمدی: MTU را پایین‌تر از نیاز بگذارDeliberate failure: set an MTU too small for the path

فقط در دو VM disposable، MTU interface tunnel را موقتاً به مقدار آزمایشیِ کم تغییر بده. پیش از تغییر مقدار فعلی و دستور rollback را ثبت کن. ping کوچک باید عبور کند؛ packetهای بزرگ یا transfer ممکن است شکست بخورند. اگر همهٔ pingها بسته‌اند، این آزمایش دربارهٔ MTU جواب نمی‌دهد؛ ابتدا route/firewall/peer را درست کن.

Only in disposable VMs, temporarily lower the tunnel interface MTU to an intentionally small test value. Record the original value and rollback command first. Small pings should pass while larger packets or transfers may fail. If all pings fail, this test tells you nothing about MTU; fix route/firewall/peer first.

برای تفسیر، capture و `tracepath` را نگه دار. اگر ICMP Packet Too Big برنمی‌گردد، PMTUD ممکن است black-hole شود؛ اگر packet fragment می‌شود، receiver/capture قطعه‌ها را نشان می‌دهد. قبل از افزایش/کاهش، یک اندازهٔ کوچک که موفق است و یک اندازهٔ بزرگ که شکست می‌خورد ثبت کن؛ بعد MTU را مرحله‌ای تغییر بده و همان دو آزمون را تکرار کن.

Keep captures and `tracepath` output. Missing ICMP Packet Too Big can indicate a PMTUD black hole; captures may reveal fragmentation. Before changing anything, record one packet size that works and one that fails. Then adjust in measured steps and repeat those same tests.

MTU را به مقدار ادعایی مقاله‌ای نچسبان؛ path متفاوت است. پس از آزمایش مقدار اصلی را برگردان و transfer بزرگ را verify کن. MSS clamping می‌تواند TCP MSS را به مسیر محدود کند، اما UDP/QUIC و هر پروتکل را حل نمی‌کند و باید در شبکهٔ تحت مدیریت دقیق طراحی شود.

Do not copy a universal MTU from an article; paths differ. Restore the original value after the experiment and verify a large transfer. MSS clamping can constrain TCP MSS, but it does not solve UDP/QUIC or every protocol and must be designed carefully on a managed network.

TCP داخل TCP می‌تواند recovery را بدتر کندTCP inside TCP can worsen recovery

اگر OpenVPN روی TCP باشد و داخلش TCP application (مثلاً HTTPS) هم حمل شود، loss بیرونی و loss داخلی هر دو retransmit/flow control دارند. لایه‌ها از هم بی‌خبرند و می‌توانند head-of-line blocking و timeout را تشدید کنند. این اثر به مسیر و loss profile وابسته است، نه قانون «TCP همیشه بد». UDP اغلب انتخاب بهتری برای tunnel است؛ TCP فقط وقتی محدودیت شبکه آن را لازم می‌کند بسنج.

If OpenVPN uses TCP and carries TCP applications such as HTTPS, outer and inner layers both perform retransmission and flow control. They cannot coordinate, potentially worsening head-of-line blocking and timeouts. Impact depends on path and loss, not a universal “TCP is bad” rule. UDP is often a better tunnel transport; test TCP when network restrictions require it.

مقایسهٔ WireGuard و OpenVPN را منصفانه انجام بدهCompare WireGuard and OpenVPN fairly

همان دو host، مسیر بیرونی، ساعت، MTU، workload و مقصد را نگه دار؛ هر بار فقط tunnel protocol را عوض کن. کلاینت/server version و CPU crypto support را ثبت کن. آزمون direct، WireGuard و OpenVPN را چند بار انجام بده و median، range، loss، CPU و reconnect را بنویس. نتیجهٔ این دو VM را به همهٔ تلفن‌ها/ISPها تعمیم نده؛ acceleration، kernel, DCO, provider و cipher negotiation عوضش می‌کنند.

Keep the same two hosts, outer route, time window, MTU, workload, and destination; change only the tunnel protocol per run. Record client/server versions and CPU crypto support. Repeat direct, WireGuard, and OpenVPN tests and report median/range, loss, CPU, and reconnects. Do not generalize two VMs to every phone/provider; acceleration, kernel, DCO, and cipher negotiation matter.

آزمایش را کنترل‌شده ببندKeep the experiment controlled

در tunnel lab خودت، یک endpoint iperf3 و ping peer را انتخاب کن. direct baseline و tunnel run را با همان مدت/stream count بگیر؛ UDP bitrate را محدود نگه دار. `top` و interface counters را هم‌زمان ثبت کن. بعد MTU failure را اجرا و recover کن. اگر VPN endpointهای مستقیم و tunnel متفاوت‌اند، این را در نتیجه بنویس؛ عددها هزینهٔ مسیر کامل‌اند.

Choose an iperf3 endpoint and peer ping in your own tunnel lab. Measure direct baseline and tunnel with the same duration/stream count; keep UDP bitrate bounded. Record `top` and interface counters at the same time. Then inject and recover the MTU failure. If endpoints differ, state that numbers represent the whole path.

پس از lab، MTU اولیه، route و test interface را برگردان. Server iperf3 را متوقف کن. از `ping -M do`/tracepath خروجی را ذخیره کن، ولی نتیجه را به packet capture و فایل config وصل کن تا معلوم شود اندازهٔ خطا از کجا آمده.

After the lab, restore MTU, routes, and test-interface state, then stop iperf3. Save ping/tracepath output and correlate it with packet captures and config so the failure’s size boundary is explainable.

۱۸ تمرین؛ حدس را به اندازه‌گیری تبدیل کن18 exercises: turn guesses into measurements

۱. latency یا throughput

ping از 30ms به 60ms رفته ولی download rate ثابت است. کدام metric بدتر شده؟

Ping rises from 30 to 60 ms but download rate is unchanged. Which metric worsened?

پاسخ

RTT latency؛ throughput ثابت مانده است.

Round-trip latency; throughput stayed constant.

۲. loss

iperf TCP کند است و retransmit بالا؛ یک علت شبکه‌ای محتمل؟

iperf TCP is slow with many retransmits. Name a plausible network cause.

پاسخ

packet loss/congestion یا MTU/fragmentation مسئله؛ CPU و مسیر را هم جدا بسنج.

Loss/congestion or MTU/fragmentation; also isolate CPU and route effects.

۳. یک run کافی نیست

چرا یک iperf run برای انتخاب VPN protocol کافی نیست؟

Why is one iperf run insufficient to choose a VPN protocol?

پاسخ

load، CPU, route, wifi، congestion و randomness نتیجه را عوض می‌کنند؛ تکرار و کنترل لازم است.

Load, CPU, route, Wi-Fi, congestion, and variance affect results; repeat and control conditions.

۴. iperf `-P`

parallel stream را از 1 به 8 بردی و نرخ بالا رفت. آیا یک stream واقعی هم همان‌قدر بهتر شد؟

Throughput rises when parallel streams increase from 1 to 8. Did one real stream improve equally?

پاسخ

نه؛ parallelism ظرفیت aggregate را می‌سنجد و با یک flow برابر نیست.

No; parallel streams measure aggregate capacity, not a single flow.

۵. CPU اشباع

throughput پایین، loss نزدیک صفر، یک core صددرصد. فرضیهٔ بعدی؟

Low throughput, nearly no loss, one core pegged. Next hypothesis?

پاسخ

CPU/crypto/packet processing bottleneck؛ endpoint و algorithm/acceleration را اندازه بگیر.

CPU/crypto/packet-processing bottleneck; measure endpoint and acceleration behavior.

۶. overhead

چرا tunnel MTU از physical MTU کوچک‌تر می‌شود؟

Why is tunnel MTU smaller than physical MTU?

پاسخ

headerهای outer IP/UDP/protocol فضای MTU بیرونی را مصرف می‌کنند.

Outer IP/UDP/protocol headers consume part of the outer path MTU.

۷. small works, large hangs

کدام MTU-related mechanism را بررسی می‌کنی؟

Which MTU-related mechanism do you investigate?

پاسخ

PMTUD و ICMP Packet Too Big، fragmentation/black hole؛ با اندازه‌های کنترل‌شده آزمایش کن.

PMTUD and ICMP Packet Too Big, fragmentation/black-hole behavior; test controlled sizes.

۸. ping `-M do`

این option چه constraintی اعمال می‌کند؟

What constraint does this ping option apply?

پاسخ

در Linux IPv4 درخواست را با DF می‌فرستد تا fragmentation لازم نشود؛ implementation/platform وابسته است.

On Linux IPv4 it sets DF to prevent fragmentation; behavior is platform-specific.

۹. payload size

`ping -s 1200` یعنی کل packet 1200 bytes است؟

Does `ping -s 1200` mean the entire packet is 1200 bytes?

پاسخ

نه؛ payload ICMP است و IP/ICMP headers هم اضافه می‌شوند.

No; it sets ICMP payload size, with IP/ICMP headers added.

۱۰. ping fail

بستهٔ بزرگ ping شکست می‌خورد. آیا حتماً MTU است؟

A large ping fails. Is MTU definitely the cause?

پاسخ

نه؛ ICMP ممکن است filtered باشد. tracepath/capture و TCP transfer را cross-check کن.

No; ICMP may be filtered. Cross-check with tracepath, captures, and TCP transfers.

۱۱. TCP-over-TCP

چه پدیده‌ای می‌تواند در loss بدتر شود؟

What issue can worsen under loss?

پاسخ

دو recovery/control loop TCP می‌توانند retransmission و head-of-line blocking را تشدید کنند.

Two TCP recovery loops can amplify retransmission and head-of-line blocking.

۱۲. UDP iperf

چرا UDP bandwidth را از ابتدا بی‌حد نمی‌گذاری؟

Why not set unbounded UDP bandwidth from the start?

پاسخ

می‌تواند شبکه را flood و loss بسازد؛ با bitrate/time محدود و مرحله‌ای بالا برو.

It can flood the path and create loss; use a bounded rate/time and increase gradually.

۱۳. MTU regression

بعد از تنظیم lab MTU، کدام دو کار را پیش از بستن incident انجام می‌دهی؟

After a lab MTU adjustment, what two actions do you take before closing?

پاسخ

آزمون قبلی را دوباره verify و مقدار اصلی/cleanup را ثبت و restore می‌کنم.

Rerun the same verification, document cleanup, and restore the original value.

۱۴. route فرق داشت

direct endpoint نزدیک است ولی tunnel server در کشور/region دیگری. آیا latency difference هزینهٔ VPN است؟

The direct endpoint is nearby but VPN server is in another region. Is the latency difference VPN overhead?

پاسخ

نه؛ مسیر/فاصله با protocol confounded است. endpoint یکسان/کنترل‌شده لازم است.

Not solely; route/distance are confounders. Use a matched controlled endpoint.

۱۵. MSS clamping

آیا MSS clamping UDP/QUIC را مستقیم حل می‌کند؟

Does MSS clamping directly fix UDP/QUIC?

پاسخ

نه؛ MSS مربوط به TCP. UDP path MTU را جدا مدیریت می‌کند.

No; MSS applies to TCP. UDP path MTU needs separate handling.

۱۶. CPU دو سمت

چرا فقط CPU client را نمی‌سنجی؟

Why measure more than the client CPU?

پاسخ

server peer و gateway هم ممکن است bottleneck باشند؛ bottleneck یکی از دو طرف یا مسیر است.

Server peer/gateway can also bottleneck; the limiting point may be either endpoint or network.

۱۷. median و range

چرا برای چند run median و spread را می‌دهی، نه فقط بهترین عدد؟

Why report median and spread instead of only the best run?

پاسخ

نوسان و outlierها را پنهان نمی‌کند؛ نتیجه قابل‌تکرارتر دیده می‌شود.

It reveals variance and outliers instead of hiding them, making repeatability clearer.

۱۸. گزارش performance

برای مقایسهٔ direct/WireGuard/OpenVPN protocol version، endpoint، MTU، CPU، test duration، throughput، RTT، loss و نتیجهٔ MTU را ثبت کن. یک ادعا بنویس که این داده هنوز ثابت نمی‌کند.

Compare direct/WireGuard/OpenVPN and record protocol versions, endpoints, MTU, CPU, test duration, throughput, RTT, loss, and MTU findings. State one claim this data still cannot prove.

معیار

نتیجه به همان environment محدود است؛ benchmark همگانی یا امنیت protocol را ثابت نمی‌کند.

Results are environment-specific; a benchmark proves neither universal ranking nor protocol security.

performance را با یک knob درمان نکنDo not treat performance with one magic knob

اول بگو مشکل RTT، throughput، loss، CPU یا packet size است. direct baseline بگیر؛ همان مقصد و workload را از tunnel تکرار کن؛ endpointها و versionها را ثبت کن. کوچک‌کارکردن packetها با بزرگ‌کارکردنشان فرق دارد؛ PMTU/ICMP را با capture و اندازه‌گیری ثابت کن. UDP، CPU acceleration و MTU هر کدام فرضیه‌اند، نه درمان تضمینی. مقدار قبلی را نگه دار و پس از هر تغییر همان آزمون را تکرار کن.

First identify whether the problem is RTT, throughput, loss, CPU, or packet size. Establish a direct baseline and repeat the same destination/workload through the tunnel; record endpoints and versions. Small packets working while large ones fail points elsewhere than general slowness; prove PMTU/ICMP behavior with measurements and captures. UDP, CPU acceleration, and MTU are hypotheses, not guaranteed fixes. Preserve prior values and rerun the same test after each change.
