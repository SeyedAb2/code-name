«VPN کند هست» هنوز تشخیص نیست“The VPN is slow” is not yet a diagnosis

کاربر می‌گه تماس مکث داره، دانلود نصف شده و ping بعضی وقت‌ها می‌پره بالا. اگه همهٔ این‌ها رو با یه برچسب «کندی» جمع کنیم، خیلی زود شروع می‌کنیم به عوض کردن تنظیمات شانسی. اینجا برعکس عمل می‌کنیم: اول می‌گیم دقیقاً چی کند شده، بعد baseline می‌گیریم، بعد فقط یه متغیر رو عوض می‌کنیم. MTU، CPU، latency، loss و مسیر هر کدوم داستان خودشون رو دارن.

A user reports a laggy call, half-speed downloads, and occasional ping spikes. These are different symptoms with different possible causes: latency, throughput, jitter/loss, CPU, MTU, or a farther-away server. Before changing ciphers or interfaces, establish a baseline and then vary one factor at a time.

baseline مستقیم رو با همون دو میزبان، ساعت، پروتکل و بار بگیر؛ بعد از tunnel همون آزمون رو تکرار کن. اگه مسیر مستقیم و tunnel endpointها متفاوت باشن، نتیجه فقط مقایسهٔ دو مسیر هست، نه هزینهٔ خالص رمزنگاری. آزمون‌های هم‌زمان می‌تونن خودشان شبکه رو اشباع کنند.

Measure the direct baseline with the same hosts, time window, protocol, and load; then repeat through the tunnel. If endpoints differ, you are comparing two paths, not encryption cost alone. Concurrent tests can saturate the network themselves.

اگه packet داخلی و سربار از MTU بیرونی بزرگ‌تر بشن، fragmentation یا PMTUD لازم می‌شه.

If inner packet plus overhead exceeds the outer MTU, fragmentation or PMTU discovery must handle it.

اول مشخص کن کدوم «کندی» رو اندازه می‌گیریFirst identify which kind of slowness you are measuring

latency زمان رفت‌وبرگشت هست؛ throughput نرخ انتقال داده هست؛ jitter تغییر latency و packet loss گم‌شدن بسته‌هاست. ping برای RTT/روند و گاهی loss مفید هست، اما throughput رو نمی‌سنجد. iperf3 انتقال کنترل‌شده می‌سازه، ولی به‌تنهایی رفتار browser، DNS یا کلاینت VPN رو توضیح نمی‌ده.

Latency is round-trip time; throughput is transfer rate; jitter is latency variation, and packet loss is missing traffic. Ping helps inspect RTT/trends and sometimes loss, but not throughput. iperf3 generates a controlled transfer but does not by itself characterize browsers, DNS, or the VPN client.

روی peer آزمایشی سرور iperf3 رو بالا بیاور. client یک run کوتاه و محدود انجام دهد؛ `-t 10` زمان رو محدود می‌کنه، `-P 2` دو stream موازی می‌سازه. server port رو فقط در آزمایشگاه باز کن. خروجی receiver throughput همون run رو نشان می‌ده؛ این عدد رو با شبکهٔ واقعی و ترافیک دیگران یکی نگیر.

Start iperf3’s server on the test peer. Run a short, bounded client test; `-t 10` limits duration and `-P 2` uses two parallel streams. Expose the server port only in the lab. Receiver throughput describes that run, not every real workload or shared-network condition.

# server peer
iperf3 -s
# client direct, then repeat through the lab tunnel
iperf3 -c PEER_IP -t 10 -P 2

همون test رو یک بار مستقیم و یک بار به tunnel IP بزن. بهتره چند نوبت ثبت کنی و median/range رو مقایسه کنی. یک run ممکنه با CPU throttling، Wi‑Fi، server load یا congestion تغییر کند. روی TCP retransmit و receiver rate هم نگاه کن؛ روی UDP فقط bitrate محدود و کم‌کم افزایش بده تا شبکه رو flood نکنی.

Run the same test directly and against the tunnel IP. Repeat and compare median/range. One run can change with CPU throttling, Wi-Fi, server load, or congestion. Inspect TCP retransmits and receiver rate; for UDP, use a bounded bitrate and increase gradually rather than flooding the network.

iperf3 -c PEER_IP -u -b 5M -t 10

همزمان CPU دو endpoint رو با `top`/Task Manager ببین. اگه throughput پایین و یک core پر هست، crypto/packet processing محتمل‌تر هست؛ اگه CPU آزاد و loss بالا هست، route/radio/queue رو بررسی کن. این‌ها فرضیه‌اند؛ telemetry و repetition لازمه.

Watch both endpoints’ CPU with `top`/Task Manager. Low throughput with one core saturated points toward crypto/packet processing; low CPU with loss suggests route/radio/queue issues. These are hypotheses, not conclusions; correlate metrics and repeat.

چرا MTU داخل tunnel کوچک‌تر می‌شه؟Why does the tunnel’s usable MTU shrink?

packet داخلی خودش header داره؛ tunnel اون رو encapsulate می‌کنه و outer IP/UDP و header پروتکل VPN هم فضا می‌گیرند. outer path MTU برای کل packet بیرونی سقف داره. اگه payload داخلی خیلی بزرگ باشه، IP fragmentation یا Path MTU Discovery باید راهی پیدا کند؛ بعضی firewallها ICMP Packet Too Big رو drop می‌کنن و PMTUD black hole می‌شه: بستهٔ کوچک کار می‌کنه، بزرگ hang/retry می‌شه.

An inner packet already has headers. Encapsulation adds outer IP/UDP and VPN headers, while the outer path MTU limits the full packet. Oversized inner payloads require IP fragmentation or Path MTU Discovery. Some firewalls drop ICMP Packet Too Big, creating a PMTUD black hole: small packets work while large transfers stall or retry.

سربار ثابت جهانی اعلام نمی‌کنیم؛ IPv4/IPv6 outer, protocol, options و encapsulation مقدار رو عوض می‌کنن. روی Linux در آزمایشگاه با IPv4 می‌شه اندازهٔ payload رو کنترل‌شده امتحان کرد: `ping -M do` نمی‌ذاره packet fragment بشه و `-s` اندازهٔ ICMP payload رو می‌ده. با گام‌های محدود از کوچک شروع کن؛ rate پایین و count محدود بذار.

There is no universal overhead number: outer IPv4/IPv6, protocol, options, and encapsulation change it. On Linux, test bounded IPv4 payload sizes in a lab: `ping -M do` prevents fragmentation and `-s` sets ICMP payload size. Start small, step carefully, and limit count/rate.

ping -c 3 -W 2 -M do -s 1200 TUNNEL_PEER
tracepath TUNNEL_PEER

برای `ping`, اندازهٔ payload به ICMP و IP header هم نیاز داره؛ در IPv4 معمولاً 20 byte IP و 8 byte ICMP اضافه هست، اما optionها ممکنه تغییر دهند. در IPv6 header اندازهٔ دیگری داره. `tracepath` اگه ICMP feedback در دسترس باشه PMTU رو تخمین می‌زند. خرابی می‌تونه echo filtering هم باشه، پس با TCP transfer/packet capture هم cross-check کن.

The ping payload size is in addition to ICMP and IP headers; IPv4 commonly adds 20 bytes of IP and 8 bytes of ICMP, while options can change that. IPv6 has different base headers. `tracepath` can estimate PMTU when ICMP feedback is available. A failed ping may simply be filtered, so cross-check with TCP transfer and captures.

خرابی عمدی: MTU رو پایین‌تر از نیاز بذارDeliberate failure: set an MTU too small for the path

فقط در دو VM موقتی، MTU interface tunnel رو موقتاً به مقدار آزمایشیِ کم تغییر بده. پیش از تغییر مقدار فعلی و دستور rollback رو ثبت کن. ping کوچک باید عبور کند؛ packetهای بزرگ یا transfer ممکنه شکست بخورند. اگه همهٔ pingها بسته‌اند، این آزمایش دربارهٔ MTU جواب نمی‌ده؛ ابتدا route/firewall/peer رو درست کن.

Only in disposable VMs, temporarily lower the tunnel interface MTU to an intentionally small test value. Record the original value and rollback command first. Small pings should pass while larger packets or transfers may fail. If all pings fail, this test tells you nothing about MTU; fix route/firewall/peer first.

برای تفسیر، capture و `tracepath` رو نگه دار. اگه ICMP Packet Too Big برنمی‌گردد، PMTUD ممکنه black-hole بشه؛ اگه packet fragment می‌شه، receiver/capture قطعه‌ها رو نشان می‌ده. قبل از افزایش/کاهش، یک اندازهٔ کوچک که موفق هست و یک اندازهٔ بزرگ که شکست می‌خوره ثبت کن؛ بعد MTU رو مرحله‌ای تغییر بده و همون دو آزمون رو تکرار کن.

Keep captures and `tracepath` output. Missing ICMP Packet Too Big can indicate a PMTUD black hole; captures may reveal fragmentation. Before changing anything, record one packet size that works and one that fails. Then adjust in measured steps and repeat those same tests.

MTU رو به مقدار ادعایی مقاله‌ای نچسبان؛ path متفاوت هست. پس از آزمایش مقدار اصلی رو برگردان و transfer بزرگ رو verify کن. MSS clamping می‌تونه TCP MSS رو به مسیر محدود کند، اما UDP/QUIC و هر پروتکل رو حل نمی‌کنه و باید در شبکهٔ تحت مدیریت دقیق طراحی بشه.

Do not copy a universal MTU from an article; paths differ. Restore the original value after the experiment and verify a large transfer. MSS clamping can constrain TCP MSS, but it does not solve UDP/QUIC or every protocol and must be designed carefully on a managed network.

TCP داخل TCP می‌تونه recovery رو بدتر کندTCP inside TCP can worsen recovery

اگه OpenVPN روی TCP باشه و داخلش TCP application (مثلاً HTTPS) هم حمل بشه، loss بیرونی و loss داخلی هر دو retransmit/flow control دارن. لایه‌ها از هم بی‌خبرند و می‌تونن head-of-line blocking و timeout رو تشدید کنند. این اثر به مسیر و loss profile وابسته هست، نه قانون «TCP همیشه بد». UDP اغلب انتخاب بهتری برای tunnel هست؛ TCP فقط وقتی محدودیت شبکه اون رو لازم می‌کنه بسنج.

If OpenVPN uses TCP and carries TCP applications such as HTTPS, outer and inner layers both perform retransmission and flow control. They cannot coordinate, potentially worsening head-of-line blocking and timeouts. Impact depends on path and loss, not a universal “TCP is bad” rule. UDP is often a better tunnel transport; test TCP when network restrictions require it.

مقایسهٔ WireGuard و OpenVPN رو منصفانه انجام بدهCompare WireGuard and OpenVPN fairly

همون دو host، مسیر بیرونی، ساعت، MTU، workload و مقصد رو نگه دار؛ هر بار فقط tunnel protocol رو عوض کن. کلاینت/server version و CPU crypto support رو ثبت کن. آزمون direct، WireGuard و OpenVPN رو چند بار انجام بده و median، range، loss، CPU و reconnect رو بنویس. نتیجهٔ این دو VM رو به همهٔ تلفن‌ها/ISPها تعمیم نده؛ acceleration، kernel, DCO, provider و cipher negotiation عوضش می‌کنن.

Keep the same two hosts, outer route, time window, MTU, workload, and destination; change only the tunnel protocol per run. Record client/server versions and CPU crypto support. Repeat direct, WireGuard, and OpenVPN tests and report median/range, loss, CPU, and reconnects. Do not generalize two VMs to every phone/provider; acceleration, kernel, DCO, and cipher negotiation matter.

آزمایش رو کنترل‌شده ببندKeep the experiment controlled

در tunnel آزمایشگاه خودت، یک endpoint iperf3 و ping peer رو انتخاب کن. direct baseline و tunnel run رو با همون مدت/stream count بگیر؛ UDP bitrate رو محدود نگه دار. `top` و interface counters رو هم‌زمان ثبت کن. بعد MTU خرابی رو اجرا و recover کن. اگه VPN endpointهای مستقیم و tunnel متفاوت‌اند، این رو در نتیجه بنویس؛ عددها هزینهٔ مسیر کامل‌اند.

Choose an iperf3 endpoint and peer ping in your own tunnel lab. Measure direct baseline and tunnel with the same duration/stream count; keep UDP bitrate bounded. Record `top` and interface counters at the same time. Then inject and recover the MTU failure. If endpoints differ, state that numbers represent the whole path.

پس از آزمایشگاه، MTU اولیه، route و test interface رو برگردان. Server iperf3 رو متوقف کن. از `ping -M do`/tracepath خروجی رو ذخیره کن، ولی نتیجه رو به packet capture و فایل config وصل کن تا معلوم بشه اندازهٔ خطا از کجا آمده.

After the lab, restore MTU, routes, and test-interface state, then stop iperf3. Save ping/tracepath output and correlate it with packet captures and config so the failure’s size boundary is explainable.

۱۸ تمرین؛ حدس رو به اندازه‌گیری تبدیل کن18 exercises: turn guesses into measurements

۱. latency یا throughput

ping از 30ms به 60ms رفته ولی download rate ثابت هست. کدوم metric بدتر شده؟

Ping rises from 30 to 60 ms but download rate is unchanged. Which metric worsened?

پاسخ

RTT latency؛ throughput ثابت مانده هست.

Round-trip latency; throughput stayed constant.

۲. loss

iperf TCP کند هست و retransmit بالا؛ یک علت شبکه‌ای محتمل؟

iperf TCP is slow with many retransmits. Name a plausible network cause.

پاسخ

packet loss/congestion یا MTU/fragmentation مسئله؛ CPU و مسیر رو هم جدا بسنج.

Loss/congestion or MTU/fragmentation; also isolate CPU and route effects.

۳. یک run کافی نیست

چرا یک iperf run برای انتخاب VPN protocol کافی نیست؟

Why is one iperf run insufficient to choose a VPN protocol?

پاسخ

load، CPU, route, wifi، congestion و randomness نتیجه رو عوض می‌کنن؛ تکرار و کنترل لازمه.

Load, CPU, route, Wi-Fi, congestion, and variance affect results; repeat and control conditions.

۴. iperf `-P`

parallel stream رو از 1 به 8 بردی و نرخ بالا رفت. آیا یک stream واقعی هم همون‌قدر بهتر شد؟

Throughput rises when parallel streams increase from 1 to 8. Did one real stream improve equally?

پاسخ

نه؛ parallelism ظرفیت aggregate رو می‌سنجد و با یک flow برابر نیست.

No; parallel streams measure aggregate capacity, not a single flow.

۵. CPU اشباع

throughput پایین، loss نزدیک صفر، یک core صددرصد. فرضیهٔ بعدی؟

Low throughput, nearly no loss, one core pegged. Next hypothesis?

پاسخ

CPU/crypto/packet processing bottleneck؛ endpoint و algorithm/acceleration رو اندازه بگیر.

CPU/crypto/packet-processing bottleneck; measure endpoint and acceleration behavior.

۶. overhead

چرا tunnel MTU از physical MTU کوچک‌تر می‌شه؟

Why is tunnel MTU smaller than physical MTU?

پاسخ

headerهای outer IP/UDP/protocol فضای MTU بیرونی رو مصرف می‌کنن.

Outer IP/UDP/protocol headers consume part of the outer path MTU.

۷. small works, large hangs

کدوم MTU-related mechanism رو بررسی می‌کنی؟

Which MTU-related mechanism do you investigate?

پاسخ

PMTUD و ICMP Packet Too Big، fragmentation/black hole؛ با اندازه‌های کنترل‌شده آزمایش کن.

PMTUD and ICMP Packet Too Big, fragmentation/black-hole behavior; test controlled sizes.

۸. ping `-M do`

این option چه constraintی اعمال می‌کنه؟

What constraint does this ping option apply?

پاسخ

در Linux IPv4 درخواست رو با DF می‌فرسته تا fragmentation لازم نشه؛ implementation/platform وابسته هست.

On Linux IPv4 it sets DF to prevent fragmentation; behavior is platform-specific.

۹. payload size

`ping -s 1200` یعنی کل packet 1200 bytes هست؟

Does `ping -s 1200` mean the entire packet is 1200 bytes?

پاسخ

نه؛ payload ICMP هست و IP/ICMP headers هم اضافه می‌بشن.

No; it sets ICMP payload size, with IP/ICMP headers added.

۱۰. ping fail

بستهٔ بزرگ ping شکست می‌خوره. آیا حتماً MTU هست؟

A large ping fails. Is MTU definitely the cause?

پاسخ

نه؛ ICMP ممکنه filtered باشه. tracepath/capture و TCP transfer رو cross-check کن.

No; ICMP may be filtered. Cross-check with tracepath, captures, and TCP transfers.

۱۱. TCP-over-TCP

چه پدیده‌ای می‌تونه در loss بدتر بشه؟

What issue can worsen under loss?

پاسخ

دو recovery/control loop TCP می‌تونن retransmission و head-of-line blocking رو تشدید کنند.

Two TCP recovery loops can amplify retransmission and head-of-line blocking.

۱۲. UDP iperf

چرا UDP bandwidth رو از ابتدا بی‌حد نمی‌گذاری؟

Why not set unbounded UDP bandwidth from the start?

پاسخ

می‌تونه شبکه رو flood و loss بسازه؛ با bitrate/time محدود و مرحله‌ای بالا برو.

It can flood the path and create loss; use a bounded rate/time and increase gradually.

۱۳. MTU regression

بعد از تنظیم آزمایشگاه MTU، کدوم دو کار رو پیش از بستن incident انجام می‌دهی؟

After a lab MTU adjustment, what two actions do you take before closing?

پاسخ

آزمون قبلی رو دوباره verify و مقدار اصلی/cleanup رو ثبت و restore می‌کنم.

Rerun the same verification, document cleanup, and restore the original value.

۱۴. route فرق داشت

direct endpoint نزدیک هست ولی tunnel server در کشور/region دیگری. آیا latency difference هزینهٔ VPN هست؟

The direct endpoint is nearby but VPN server is in another region. Is the latency difference VPN overhead?

پاسخ

نه؛ مسیر/فاصله با protocol confounded هست. endpoint یکسان/کنترل‌شده لازمه.

Not solely; route/distance are confounders. Use a matched controlled endpoint.

۱۵. MSS clamping

آیا MSS clamping UDP/QUIC رو مستقیم حل می‌کنه؟

Does MSS clamping directly fix UDP/QUIC?

پاسخ

نه؛ MSS مربوط به TCP. UDP path MTU رو جدا مدیریت می‌کنه.

No; MSS applies to TCP. UDP path MTU needs separate handling.

۱۶. CPU دو سمت

چرا فقط CPU client رو نمی‌سنجی؟

Why measure more than the client CPU?

پاسخ

server peer و gateway هم ممکنه bottleneck باشن؛ bottleneck یکی از دو طرف یا مسیر هست.

Server peer/gateway can also bottleneck; the limiting point may be either endpoint or network.

۱۷. median و range

چرا برای چند run median و spread رو می‌دهی، نه فقط بهترین عدد؟

Why report median and spread instead of only the best run?

پاسخ

نوسان و outlierها رو پنهان نمی‌کنه؛ نتیجه قابل‌تکرارتر دیده می‌شه.

It reveals variance and outliers instead of hiding them, making repeatability clearer.

۱۸. گزارش performance

برای مقایسهٔ direct/WireGuard/OpenVPN protocol version، endpoint، MTU، CPU، test duration، throughput، RTT، loss و نتیجهٔ MTU رو ثبت کن. یک ادعا بنویس که این داده هنوز ثابت نمی‌کنه.

Compare direct/WireGuard/OpenVPN and record protocol versions, endpoints, MTU, CPU, test duration, throughput, RTT, loss, and MTU findings. State one claim this data still cannot prove.

معیار

نتیجه به همون environment محدود هست؛ benchmark همگانی یا امنیت protocol رو ثابت نمی‌کنه.

Results are environment-specific; a benchmark proves neither universal ranking nor protocol security.

کارایی رو با یک knob درمان نکنDo not treat performance with one magic knob

اول بگو مشکل RTT، throughput، loss، CPU یا packet size هست. direct baseline بگیر؛ همون مقصد و workload رو از tunnel تکرار کن؛ endpointها و versionها رو ثبت کن. کوچک‌کارکردن packetها با بزرگ‌کارکردنشان فرق داره؛ PMTU/ICMP رو با capture و اندازه‌گیری ثابت کن. UDP، CPU acceleration و MTU هر کدوم فرضیه‌اند، نه درمان تضمینی. مقدار قبلی رو نگه دار و پس از هر تغییر همون آزمون رو تکرار کن.

First identify whether the problem is RTT, throughput, loss, CPU, or packet size. Establish a direct baseline and repeat the same destination/workload through the tunnel; record endpoints and versions. Small packets working while large ones fail points elsewhere than general slowness; prove PMTU/ICMP behavior with measurements and captures. UDP, CPU acceleration, and MTU are hypotheses, not guaranteed fixes. Preserve prior values and rerun the same test after each change.
