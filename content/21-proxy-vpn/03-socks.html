SOCKS5

HTTP رو یه لحظه بذار کنار؛ اگه برنامه فقط بخواد به یه host و port وصل بشه چی؟

A lower-layer relay with more flexibility.

۸۰دقیقهminutes
۱۸تمرینexercises

همهٔ برنامه‌ها HTTP حرف نمی‌زنندNot every application speaks HTTP

HTTP proxy درخواست HTTP رو می‌فهمه؛ method و header و host براش معنی دارن. ولی همهٔ برنامه‌ها HTTP حرف نمی‌زنن. گاهی فقط می‌خوای بگی «منو به این host:port برسون» و دیگه کاری به محتوای اتصال نداشته باشی. اینجا SOCKS وارد ماجرا می‌شه. اول با proxy یه قرار کوتاه می‌ذاری، مقصد رو می‌گی، بعد اگه همه‌چیز اوکی بود جریان بایت‌ها راه می‌افته.

The previous chapter’s HTTP proxy understood a request: method, host, headers, and CONNECT for HTTPS. What if your application speaks another protocol? Perhaps it only needs a TCP connection to a remote host and port, without the intermediary understanding HTTP. SOCKS addresses this by accepting a destination and relaying the stream—not by interpreting the application payload.

SOCKS5 یک مذاکرهٔ دودویی کوتاه داره: client روش‌های پشتیبانی‌شده رو معرفی می‌کنه، server یکی رو انتخاب می‌کنه، بعد client نوع عملیات و نشانی مقصد رو می‌فرسته. پس از موفقیت، proxy TCP رو relay می‌کنه. RFC 1928 هم CONNECT، BIND و UDP ASSOCIATE رو تعریف می‌کنه؛ توی این درس روی CONNECT تمرکز می‌کنیم. RFC 1928

SOCKS5 begins with a short binary negotiation: the client lists supported methods, the server selects one, and the client sends a command and destination address. After success, the proxy relays TCP. RFC 1928 also defines BIND and UDP ASSOCIATE; this lesson focuses on CONNECT.

خطای مذاکره پیش از اتصال مقصد رخ می‌ده؛ reply موفق هم هنوز موفقیت برنامه رو ثابت نمی‌کنه.

Negotiation can fail before connecting to the destination; a successful reply still does not prove application success.

مرحلهٔ اول: چه روش احراز هویتی رو می‌پذیریم؟Step one: which authentication method is acceptable?

پیام greeting با version برابر 5 و فهرستی از methodها شروع می‌شه. مقدار رایج 0x00 یعنی بدون احراز هویت؛ 0x02 یعنی username/password طبق RFC 1929؛ 0xFF از سمت server یعنی روش مشترکی پیدا نشد. server فقط از میان روش‌هایی انتخاب می‌کنه که client پیشنهاد کرده.

The greeting begins with version 5 and a list of methods. Common values include 0x00 for no authentication, 0x02 for username/password as specified by RFC 1929, and 0xFF from the server when no acceptable method is shared. The server selects only a method the client offered. RFC 1929

SOCKS5 خودش رمزنگاری transport رو اضافه نمی‌کنه. اگه username/password رو روی شبکهٔ غیرقابل‌اعتماد بفرستی، این روش به‌تنهایی محافظ credential نیست. SSH dynamic forwarding راه دیگری هست: برنامه با SOCKS محلی حرف می‌زند، ولی SSH مسیر خودش تا سرور رو رمز می‌کنه. این دو لایه رو یکی ندان.

SOCKS5 does not encrypt its transport. Username/password alone does not protect credentials on an untrusted network. SSH dynamic forwarding is different: the application speaks to a local SOCKS listener, while SSH encrypts its own path to the remote server. Do not conflate those layers.

مرحلهٔ دوم: کدوم مقصد رو باز کنیم؟Step two: which destination should be opened?

پس از مذاکره، client فرمان می‌فرسته. برای TCP CONNECT مقدار فرمان 0x01 هست. بعد فیلد ATYP نوع نشانی رو می‌گه: IPv4 مقدار 1، domain name مقدار 3، IPv6 مقدار 4. سپس نشانی و پورت 16-bit می‌آیند. همین اجازه می‌ده client نام رو بدهد تا خود proxy DNS کند؛ یا client پیشاپیش IP رو حل کند.

After negotiation, the client sends a command. TCP CONNECT uses command 0x01. The ATYP field identifies the address type: IPv4 is 1, domain name is 3, and IPv6 is 4. The address and a 16-bit port follow. The client can provide a hostname for proxy-side DNS, or resolve it locally and send an IP address.

reply server status رو می‌ده: 0x00 موفقیت هست؛ مقادیر دیگر خطاهایی مثل ردشدن قانون، شبکه/host غیرقابل‌دسترس یا فرمان پشتیبانی‌نشده رو نشان می‌دن. حتی اگه SOCKS بگه اتصال باز شد، هنوز TLS handshake یا پاسخ HTTP رو ندیده‌ای. هر مرحله رو جدا verify کن.

The server reply carries a status: 0x00 is success; other values report conditions such as policy denial, network/host unreachable, or an unsupported command. Even after SOCKS reports a connection, TLS or HTTP may still fail. Verify each layer separately.

بایت‌ها بالا فقط انتخاب‌های استانداره رو نشان می‌دن، نه packet capture مشخصی از دستگاه تو. برای دیدن byte-level handshake به ابزار و سروری نیاز داری که capture رو مجاز کرده باشه؛ در آزمایش بعدی از نتیجهٔ قابل‌مشاهدهٔ curl و SSH استفاده می‌کنیم و از ساختن خروجی خیالی پرهیز می‌کنیم.

The bytes above are standard field values, not a packet capture from your machine. A byte-level trace requires an authorized capture and a SOCKS server. The next experiment uses observable curl/SSH results rather than fabricated output.

DNS محلی یا سمت proxy؟DNS locally or at the proxy?

این تفاوت در curl بسیار ملموس هست. --socks5 HOST:PORT نام مقصد رو محلی resolve می‌کنه و معمولاً IP رو به SOCKS می‌ده. --socks5-hostname HOST:PORT (یا scheme برابر socks5h://) نام رو برای resolve سمت proxy می‌فرسته. این می‌تونه دسترسی به hostnameای رو ممکن کند که فقط شبکهٔ remote می‌شناسه؛ اما به‌خودی‌خود DNS رو رمز نمی‌کنه یا جلوی همهٔ leakها رو نمی‌گیره.

curl makes this distinction visible. --socks5 HOST:PORT resolves the destination locally and normally sends the proxy an IP address. --socks5-hostname HOST:PORT (or the socks5h:// scheme) asks the proxy to resolve the hostname. This can reach a host known only inside the remote network, but does not itself encrypt DNS or prevent every kind of leak. curl SOCKS options

آزمایش رو روی hostname ساختگی خودت انجام بده، نه دامنهٔ داخلی شرکت یا شبکه‌ای که اجازه نداری. در آزمایشگاه، یک SSH server آزمایشی داشته باش که فقط خودش hostname مثل app.lab.test رو resolve می‌کنه. اگه client نتواند اون نام رو resolve کند، --socks5 قبل از درخواست به SOCKS شکست می‌خوره؛ با --socks5-hostname نام به proxy می‌رسه. مدرک رو از خطای curl و log سمت remote بگیر؛ موفقیت صرفاً می‌گه resolver remote مسیر رو شناخت.

Use a hostname you control, not a company-internal name or a network you are not authorized to access. In a lab, use an SSH test server that alone can resolve a name such as app.lab.test. If the client cannot resolve it, --socks5 fails before the SOCKS request; --socks5-hostname sends the name to the proxy. Use curl’s error and remote-side logs as evidence; success only shows that the remote resolver knew the name.

curl -v --socks5 127.0.0.1:1080 http://app.lab.test:8080/
curl -v --socks5-hostname 127.0.0.1:1080 http://app.lab.test:8080/

اگه روی همون ماشین client و proxy کار می‌کنی و هر دو از یک DNS استفاده می‌کنن، ممکنه هر دو فرمان موفق بشن؛ اون تست تفاوت رو نشان نمی‌ده. برای مقایسه باید hostname فقط از سمت SSH server resolve بشه و سرویس HTTP آزمایشی هم تحت کنترل تو باشه. خرابی اول، وقتی پیش از اتصال SOCKS رخ دهد، دربارهٔ DNS محلی هست؛ خرابی بعد از handshake رو با log remote جدا کن.

If the client and proxy share a DNS view, both commands may work and the experiment proves nothing about where resolution occurred. To distinguish them, make the hostname resolvable only from the SSH server and run a test HTTP service you control. A failure before the SOCKS connection points to local DNS; a failure after negotiation needs remote-side evidence.

SSH dynamic forwarding یک SOCKS محلی می‌سازهSSH dynamic forwarding creates a local SOCKS endpoint

اگه SSH به یک آزمایشگاه host مجاز داری، -D یک dynamic application-level forward می‌سازه. این رو روی loopback bind می‌کنیم تا SOCKS ناخواسته روی شبکهٔ محلی باز نشه. پیش از فرمان، زمینه/hostname و port آزاد رو بررسی کن؛ اتصال SSH باید با host key شناخته‌شده و حساب مجاز باشه.

If you have SSH access to an authorized lab host, -D creates a dynamic application-level forward. Bind it to loopback so the SOCKS listener is not exposed to your LAN. Verify the host and free port first; connect using a known host key and an authorized account.

ssh -N -D 127.0.0.1:1080 user@LAB_HOST

فرمان foreground می‌مونه و خروجی کم یا هیچ خروجی می‌تونه عادی باشه؛ این به‌تنهایی ثابت نمی‌کنه remote مقصد رو می‌بینه. در ترمینال دیگر یک endpoint بی‌حساسیت رو با curl -v --socks5-hostname 127.0.0.1:1080 https://example.com/ تست کن و در trace موفقیت SOCKS، TLS و HTTP رو جدا ببین. با Ctrl+C تونل رو ببند؛ ssh -D از دستگاه تو تا SSH host رو رمز می‌کنه، اما قواعد خروجی و DNS سمت اون host همچنان مهم‌اند.

The command stays in the foreground, and little or no output can be normal; that alone does not prove the remote can reach a destination. In another terminal, test a harmless endpoint with curl -v --socks5-hostname 127.0.0.1:1080 https://example.com/, distinguishing SOCKS, TLS, and HTTP success in the trace. Stop the tunnel with Ctrl+C. SSH encrypts the path from your device to the SSH host, but that host’s egress rules and DNS still matter.

UDP ASSOCIATE: بدان که هست، فعلاً واردش نشوUDP ASSOCIATE: know it exists; defer the details

SOCKS5 پروتکل UDP ASSOCIATE هم داره، اما این فقط یک فرمان درخواست نیست که هر server حتماً پشتیبانی کند. client/server باید association و relay endpoint رو بسازن؛ NAT، lifetime و mapping هم اثر دارن. توی این فصل TCP CONNECT کافیه. این جزئیات رو با UDP proxy واقعی و packet capture در فصل بعدی/مسیر عملی جدا بررسی می‌کنیم.

SOCKS5 also defines UDP ASSOCIATE, but it is not merely a command every server must support. Client and server establish an association and relay endpoint; NAT, lifetime, and mappings matter too. TCP CONNECT is enough here. UDP proxying deserves a separate hands-on study with a real server and packet capture.

خرابی عمدی: SOCKS رو با تونل رمزنگاری اشتباه بگیرDeliberate failure: assume SOCKS is an encrypted tunnel

فرض کن مدیر می‌گه «حالا که برنامه رو از SOCKS5 فرستادیم، مسیر رمز هست». این نتیجه از protocol درنمیاد. اگه SOCKS server روی شبکهٔ عمومی باشه، خود مذاکره و دادهٔ relayشده می‌تونه بی‌رمز باشه، مگر یک transport امن جدا داشته باشی. خطای دیگری هم بساز: به port یک HTTP proxy، SOCKS5 وصل شو یا برعکس. handshake باینری SOCKS و request line متنی HTTP یکی نیستند؛ انتظار reply version/method یا پیام parse خرابی رو داشته باش.

Suppose an operator says, “We route the app through SOCKS5, so the path is encrypted.” The protocol does not justify that conclusion. If the SOCKS server is reached over an untrusted network, negotiation and relayed data may be unencrypted unless a separate secure transport protects them. Another safe failure: point a SOCKS client at an HTTP proxy port, or vice versa. SOCKS’s binary greeting and HTTP’s text request line are incompatible; expect a failed method negotiation or parse error.

برای اثبات از trace بپرس: آیا TLS یا SSH وجود داره و تا کجا ادامه داره؟ اسم SOCKS پاسخ این سؤال نیست. آزمایشگاه رو فقط روی loopback یا SSH host خودت اجرا کن؛ proxy عمومی ناامن نساز و credential واقعی وارد نکن.

Use the trace to ask whether TLS or SSH exists and where it terminates. The word SOCKS cannot answer that. Keep the lab on loopback or your own SSH host; never create an open proxy or enter real credentials.

SOCKS مقصد رو می‌گیره، نه معنای داده راSOCKS receives a destination, not the meaning of the data

SOCKS5 یک مذاکرهٔ روش و سپس درخواست مقصد داره؛ برای TCP، CONNECT می‌خواد، address type رو مشخص می‌کنه و در صورت موفقیت stream رو relay می‌کنه. این انعطاف باعث می‌شه HTTP-only نباشه. در عوض، SOCKS به‌تنهایی encryption، privacy، DNS safety یا موفقیت برنامه رو تضمین نمی‌کنه. curl رو طوری به کار ببر که هر بار یک فرضیه رو بیازماید و DNS، اتصال، TLS و پاسخ برنامه رو از هم جدا نگه داره.

SOCKS5 negotiates a method, then a destination request. For TCP, CONNECT selects an address type and a successful reply leads to stream relay. That flexibility makes it protocol-agnostic with respect to HTTP. But SOCKS alone guarantees no encryption, privacy, DNS safety, or application success. Use curl to test one hypothesis at a time, keeping DNS, connection, TLS, and application response separate.

در فصل بعد همین مرز رو با کد می‌سازیم: socket رو بپذیریم، مقصد رو پیدا کنیم و بایت‌ها رو در دو جهت relay کنیم—بدون اینکه هنوز وارد لایهٔ امنیت و production شویم.
