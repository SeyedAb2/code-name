SOCKS5

لایهٔ پایین‌تر، انعطاف بیشتر.

A lower-layer relay with more flexibility.

۸۰دقیقهminutes
۱۸تمرینexercises

همهٔ برنامه‌ها HTTP حرف نمی‌زنندNot every application speaks HTTP

فصل قبل، HTTP proxy یک درخواست را می‌فهمید: method، host، header و برای HTTPS فرمان CONNECT. اما اگر برنامه‌ات پروتکل دیگری دارد چه؟ می‌خواهی فقط یک اتصال TCP به host:port دوردست باز شود، بی‌آنکه واسطه لازم باشد HTTP را بشناسد. این مسئله را SOCKS حل می‌کند؛ نه با فهم‌کردن محتوای برنامه، با گرفتن مقصد و relayکردن جریان.

The previous chapter’s HTTP proxy understood a request: method, host, headers, and CONNECT for HTTPS. What if your application speaks another protocol? Perhaps it only needs a TCP connection to a remote host and port, without the intermediary understanding HTTP. SOCKS addresses this by accepting a destination and relaying the stream—not by interpreting the application payload.

SOCKS5 یک مذاکرهٔ دودویی کوتاه دارد: client روش‌های پشتیبانی‌شده را معرفی می‌کند، server یکی را انتخاب می‌کند، بعد client نوع عملیات و نشانی مقصد را می‌فرستد. پس از موفقیت، proxy TCP را relay می‌کند. RFC 1928 هم CONNECT، BIND و UDP ASSOCIATE را تعریف می‌کند؛ در این درس روی CONNECT تمرکز می‌کنیم. RFC 1928

SOCKS5 begins with a short binary negotiation: the client lists supported methods, the server selects one, and the client sends a command and destination address. After success, the proxy relays TCP. RFC 1928 also defines BIND and UDP ASSOCIATE; this lesson focuses on CONNECT.

خطای مذاکره پیش از اتصال مقصد رخ می‌دهد؛ reply موفق هم هنوز موفقیت برنامه را ثابت نمی‌کند.

Negotiation can fail before connecting to the destination; a successful reply still does not prove application success.

مرحلهٔ اول: چه روش احراز هویتی را می‌پذیریم؟Step one: which authentication method is acceptable?

پیام greeting با version برابر 5 و فهرستی از methodها شروع می‌شود. مقدار رایج 0x00 یعنی بدون احراز هویت؛ 0x02 یعنی username/password طبق RFC 1929؛ 0xFF از سمت server یعنی روش مشترکی پیدا نشد. server فقط از میان روش‌هایی انتخاب می‌کند که client پیشنهاد کرده.

The greeting begins with version 5 and a list of methods. Common values include 0x00 for no authentication, 0x02 for username/password as specified by RFC 1929, and 0xFF from the server when no acceptable method is shared. The server selects only a method the client offered. RFC 1929

SOCKS5 خودش رمزنگاری transport را اضافه نمی‌کند. اگر username/password را روی شبکهٔ غیرقابل‌اعتماد بفرستی، این روش به‌تنهایی محافظ credential نیست. SSH dynamic forwarding راه دیگری است: برنامه با SOCKS محلی حرف می‌زند، ولی SSH مسیر خودش تا سرور را رمز می‌کند. این دو لایه را یکی ندان.

SOCKS5 does not encrypt its transport. Username/password alone does not protect credentials on an untrusted network. SSH dynamic forwarding is different: the application speaks to a local SOCKS listener, while SSH encrypts its own path to the remote server. Do not conflate those layers.

مرحلهٔ دوم: کدام مقصد را باز کنیم؟Step two: which destination should be opened?

پس از مذاکره، client فرمان می‌فرستد. برای TCP CONNECT مقدار فرمان 0x01 است. بعد فیلد ATYP نوع نشانی را می‌گوید: IPv4 مقدار 1، domain name مقدار 3، IPv6 مقدار 4. سپس نشانی و پورت 16-bit می‌آیند. همین اجازه می‌دهد client نام را بدهد تا خود proxy DNS کند؛ یا client پیشاپیش IP را حل کند.

After negotiation, the client sends a command. TCP CONNECT uses command 0x01. The ATYP field identifies the address type: IPv4 is 1, domain name is 3, and IPv6 is 4. The address and a 16-bit port follow. The client can provide a hostname for proxy-side DNS, or resolve it locally and send an IP address.

reply server status را می‌دهد: 0x00 موفقیت است؛ مقادیر دیگر خطاهایی مثل ردشدن policy، شبکه/host غیرقابل‌دسترس یا فرمان پشتیبانی‌نشده را نشان می‌دهند. حتی اگر SOCKS بگوید اتصال باز شد، هنوز TLS handshake یا پاسخ HTTP را ندیده‌ای. هر مرحله را جدا verify کن.

The server reply carries a status: 0x00 is success; other values report conditions such as policy denial, network/host unreachable, or an unsupported command. Even after SOCKS reports a connection, TLS or HTTP may still fail. Verify each layer separately.

بایت‌ها بالا فقط انتخاب‌های استاندارد را نشان می‌دهند، نه packet capture مشخصی از دستگاه تو. برای دیدن byte-level handshake به ابزار و سروری نیاز داری که capture را مجاز کرده باشد؛ در آزمایش بعدی از نتیجهٔ قابل‌مشاهدهٔ curl و SSH استفاده می‌کنیم و از ساختن خروجی خیالی پرهیز می‌کنیم.

The bytes above are standard field values, not a packet capture from your machine. A byte-level trace requires an authorized capture and a SOCKS server. The next experiment uses observable curl/SSH results rather than fabricated output.

DNS محلی یا سمت proxy؟DNS locally or at the proxy?

این تفاوت در curl بسیار ملموس است. --socks5 HOST:PORT نام مقصد را محلی resolve می‌کند و معمولاً IP را به SOCKS می‌دهد. --socks5-hostname HOST:PORT (یا scheme برابر socks5h://) نام را برای resolve سمت proxy می‌فرستد. این می‌تواند دسترسی به hostnameای را ممکن کند که فقط شبکهٔ remote می‌شناسد؛ اما به‌خودی‌خود DNS را رمز نمی‌کند یا جلوی همهٔ leakها را نمی‌گیرد.

curl makes this distinction visible. --socks5 HOST:PORT resolves the destination locally and normally sends the proxy an IP address. --socks5-hostname HOST:PORT (or the socks5h:// scheme) asks the proxy to resolve the hostname. This can reach a host known only inside the remote network, but does not itself encrypt DNS or prevent every kind of leak. curl SOCKS options

آزمایش را روی hostname ساختگی خودت انجام بده، نه دامنهٔ داخلی شرکت یا شبکه‌ای که اجازه نداری. در lab، یک SSH server آزمایشی داشته باش که فقط خودش hostname مثل app.lab.test را resolve می‌کند. اگر client نتواند آن نام را resolve کند، --socks5 قبل از درخواست به SOCKS شکست می‌خورد؛ با --socks5-hostname نام به proxy می‌رسد. مدرک را از خطای curl و log سمت remote بگیر؛ موفقیت صرفاً می‌گوید resolver remote مسیر را شناخت.

Use a hostname you control, not a company-internal name or a network you are not authorized to access. In a lab, use an SSH test server that alone can resolve a name such as app.lab.test. If the client cannot resolve it, --socks5 fails before the SOCKS request; --socks5-hostname sends the name to the proxy. Use curl’s error and remote-side logs as evidence; success only shows that the remote resolver knew the name.

curl -v --socks5 127.0.0.1:1080 http://app.lab.test:8080/
curl -v --socks5-hostname 127.0.0.1:1080 http://app.lab.test:8080/

اگر روی همان ماشین client و proxy کار می‌کنی و هر دو از یک DNS استفاده می‌کنند، ممکن است هر دو فرمان موفق شوند؛ آن تست تفاوت را نشان نمی‌دهد. برای مقایسه باید hostname فقط از سمت SSH server resolve شود و سرویس HTTP آزمایشی هم تحت کنترل تو باشد. failure اول، وقتی پیش از اتصال SOCKS رخ دهد، دربارهٔ DNS محلی است؛ failure بعد از handshake را با log remote جدا کن.

If the client and proxy share a DNS view, both commands may work and the experiment proves nothing about where resolution occurred. To distinguish them, make the hostname resolvable only from the SSH server and run a test HTTP service you control. A failure before the SOCKS connection points to local DNS; a failure after negotiation needs remote-side evidence.

SSH dynamic forwarding یک SOCKS محلی می‌سازدSSH dynamic forwarding creates a local SOCKS endpoint

اگر SSH به یک lab host مجاز داری، -D یک dynamic application-level forward می‌سازد. این را روی loopback bind می‌کنیم تا SOCKS ناخواسته روی شبکهٔ محلی باز نشود. پیش از فرمان، context/hostname و port آزاد را بررسی کن؛ اتصال SSH باید با host key شناخته‌شده و حساب مجاز باشد.

If you have SSH access to an authorized lab host, -D creates a dynamic application-level forward. Bind it to loopback so the SOCKS listener is not exposed to your LAN. Verify the host and free port first; connect using a known host key and an authorized account.

ssh -N -D 127.0.0.1:1080 user@LAB_HOST

فرمان foreground می‌ماند و خروجی کم یا هیچ خروجی می‌تواند عادی باشد؛ این به‌تنهایی ثابت نمی‌کند remote مقصد را می‌بیند. در ترمینال دیگر یک endpoint بی‌حساسیت را با curl -v --socks5-hostname 127.0.0.1:1080 https://example.com/ تست کن و در trace موفقیت SOCKS، TLS و HTTP را جدا ببین. با Ctrl+C تونل را ببند؛ ssh -D از دستگاه تو تا SSH host را رمز می‌کند، اما قواعد خروجی و DNS سمت آن host همچنان مهم‌اند.

The command stays in the foreground, and little or no output can be normal; that alone does not prove the remote can reach a destination. In another terminal, test a harmless endpoint with curl -v --socks5-hostname 127.0.0.1:1080 https://example.com/, distinguishing SOCKS, TLS, and HTTP success in the trace. Stop the tunnel with Ctrl+C. SSH encrypts the path from your device to the SSH host, but that host’s egress rules and DNS still matter.

UDP ASSOCIATE: بدان که هست، فعلاً واردش نشوUDP ASSOCIATE: know it exists; defer the details

SOCKS5 پروتکل UDP ASSOCIATE هم دارد، اما این فقط یک فرمان درخواست نیست که هر server حتماً پشتیبانی کند. client/server باید association و relay endpoint را بسازند؛ NAT، lifetime و mapping هم اثر دارند. در این فصل TCP CONNECT کافی است. این جزئیات را با UDP proxy واقعی و packet capture در فصل بعدی/مسیر عملی جدا بررسی می‌کنیم.

SOCKS5 also defines UDP ASSOCIATE, but it is not merely a command every server must support. Client and server establish an association and relay endpoint; NAT, lifetime, and mappings matter too. TCP CONNECT is enough here. UDP proxying deserves a separate hands-on study with a real server and packet capture.

خرابی عمدی: SOCKS را با تونل رمزنگاری اشتباه بگیرDeliberate failure: assume SOCKS is an encrypted tunnel

فرض کن مدیر می‌گوید «حالا که برنامه را از SOCKS5 فرستادیم، مسیر رمز است». این نتیجه از protocol درنمی‌آید. اگر SOCKS server روی شبکهٔ عمومی باشد، خود مذاکره و دادهٔ relayشده می‌تواند بی‌رمز باشد، مگر یک transport امن جدا داشته باشی. خطای دیگری هم بساز: به port یک HTTP proxy، SOCKS5 وصل شو یا برعکس. handshake باینری SOCKS و request line متنی HTTP یکی نیستند؛ انتظار reply version/method یا پیام parse failure را داشته باش.

Suppose an operator says, “We route the app through SOCKS5, so the path is encrypted.” The protocol does not justify that conclusion. If the SOCKS server is reached over an untrusted network, negotiation and relayed data may be unencrypted unless a separate secure transport protects them. Another safe failure: point a SOCKS client at an HTTP proxy port, or vice versa. SOCKS’s binary greeting and HTTP’s text request line are incompatible; expect a failed method negotiation or parse error.

برای اثبات از trace بپرس: آیا TLS یا SSH وجود دارد و تا کجا ادامه دارد؟ اسم SOCKS پاسخ این سؤال نیست. lab را فقط روی loopback یا SSH host خودت اجرا کن؛ proxy عمومی ناامن نساز و credential واقعی وارد نکن.

Use the trace to ask whether TLS or SSH exists and where it terminates. The word SOCKS cannot answer that. Keep the lab on loopback or your own SSH host; never create an open proxy or enter real credentials.

SOCKS مقصد را می‌گیرد، نه معنای داده راSOCKS receives a destination, not the meaning of the data

SOCKS5 یک مذاکرهٔ روش و سپس درخواست مقصد دارد؛ برای TCP، CONNECT می‌خواهد، address type را مشخص می‌کند و در صورت موفقیت stream را relay می‌کند. این انعطاف باعث می‌شود HTTP-only نباشد. در عوض، SOCKS به‌تنهایی encryption، privacy، DNS safety یا موفقیت برنامه را تضمین نمی‌کند. curl را طوری به کار ببر که هر بار یک فرضیه را بیازماید و DNS، اتصال، TLS و پاسخ برنامه را از هم جدا نگه دارد.

SOCKS5 negotiates a method, then a destination request. For TCP, CONNECT selects an address type and a successful reply leads to stream relay. That flexibility makes it protocol-agnostic with respect to HTTP. But SOCKS alone guarantees no encryption, privacy, DNS safety, or application success. Use curl to test one hypothesis at a time, keeping DNS, connection, TLS, and application response separate.

در فصل بعد همین مرز را با کد می‌سازیم: socket را بپذیریم، مقصد را پیدا کنیم و بایت‌ها را در دو جهت relay کنیم—بدون اینکه هنوز وارد لایهٔ امنیت و production شویم.
