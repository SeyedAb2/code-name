زنجیره‌کردن پروکسی

Chaining proxies

چند پرش، و هزینهٔ تأخیرش.

More hops—and the latency and failure cost they add.

۷۵دقیقهminutes
۱۸تمرینexercises

درخواست از کجا رد شد که کند شد؟Where did the request go before it slowed down?

یک برنامه از client به proxy A وصل می‌شود؛ A درخواست را به proxy B می‌سپارد؛ B به origin می‌رسد. اگر حالا timeout دیدی، کدام hop مقصر است؟ اگر origin نشانی B را دید، آیا A پنهان‌کاری امنیتی ساخته؟ زنجیره فقط وقتی ارزش دارد که هر hop دلیل مشخص، مالک و شواهد خودش را داشته باشد.

A client connects to proxy A; A sends the request to proxy B; B reaches the origin. If you now see a timeout, which hop failed? If the origin sees B’s address, has A created a security guarantee? A chain is useful only when every hop has a clear purpose, owner, and evidence.

هر hop اتصال جداست؛ DNS و رمزنگاری را برای هر مرز جداگانه مشخص کن.

Each hop is a separate connection; identify DNS and encryption separately at every boundary.

زنجیره می‌تواند policyها را ترکیب کند: مثلاً SOCKS/SSH برای رسیدن به شبکهٔ آزمایش، بعد HTTP proxy سازمانی برای خروجی کنترل‌شده. اما hop جدید round trip، handshake، log و نقطهٔ خرابی اضافه می‌کند. چند واسطه به‌خودی‌خود ناشناس‌بودن نمی‌سازد؛ هر واسطه مسیر و اطلاعاتی را می‌بیند که روی hop خودش رد می‌شود.

A chain can combine policies—for example, SOCKS/SSH to reach a lab network, then an organization’s HTTP proxy for controlled egress. But every hop adds round trips, handshakes, logs, and failure points. More intermediaries do not automatically create anonymity; each sees the traffic and metadata available on its own leg.

تأخیر را از روی مسیر حدس بزن، بعد اندازه بگیرPredict latency from the path, then measure

یک request ممکن است DNS، اتصال TCP و TLS یا مذاکرهٔ proxy را پشت سر هم انجام دهد. هزینهٔ زنجیره فقط جمع ثابت latency نیست: handshakeهای قابل reuse، parallelism، cache، route و فاصلهٔ شبکه نتیجه را تغییر می‌دهند. برای درخواست اول، هر hop می‌تواند round trip اضافه کند؛ برای connection reuse شده، رفتار فرق می‌کند.

A request may perform DNS, TCP setup, and proxy/TLS negotiation in sequence. Chain cost is not a fixed sum of latencies: reusable handshakes, parallelism, caching, routes, and network distance change the result. The first request may pay extra round trips at each hop; a reused connection behaves differently.

در lab، قبل و بعد از اضافه‌شدن hop دوم چند بار همان harmless URL را بزن و با curl -w زمان را ثبت کن. تعداد نمونه و مسیر ثابت نگه دار. عدد یک اجرا benchmark نیست؛ اگر تغییر را دیدی، بگو کدام فاز کند شد و چه چیزی را هنوز نمی‌دانی.

In the lab, run the same harmless URL several times before and after adding hop two; record timings with curl’s -w. Keep sample count and route stable. One run is not a benchmark; if timing changes, identify the slow phase and what remains unknown.

curl -sS -o NUL -w "connect=%{time_connect} total=%{time_total}\n" URL

در PowerShell هم `NUL` مناسب است؛ در Linux/macOS از `/dev/null` استفاده کن. برای اتصال‌های proxyدار curl timing fieldها ممکن است زمان‌های دیگری را هم reflect کنند؛ آن‌ها را با verbose trace و logها تطبیق بده. time_total زمان همان اجرای curl است، نه latency خالص هر hop.

`NUL` is suitable on Windows; use `/dev/null` on Linux/macOS. With proxies, curl timing fields can reflect more than one phase; correlate them with verbose traces and logs. time_total is the whole curl operation, not the pure latency of one hop.

DNS و credential در کدام hop هستند؟Which hop handles DNS and credentials?

فرض کن curl از SOCKS5 به HTTP proxy می‌رود و HTTP proxy بعد به origin. با `--preproxy socks5h://... --proxy http://...` مسیر نخست می‌سازد: curl با SOCKS به HTTP proxy می‌رسد، نه اینکه SOCKS لزوماً تا origin را ادامه دهد. host مربوط به HTTP proxy ممکن است توسط SOCKS remote resolve شود؛ مقصد URL را بعداً HTTP proxy resolve می‌کند. این دو نام را در trace و log جدا دنبال کن.

Suppose curl uses SOCKS5 to reach an HTTP proxy, which then reaches an origin. `--preproxy socks5h://... --proxy http://...` asks curl to reach the HTTP proxy through SOCKS; SOCKS does not necessarily carry the final request all the way to the origin. SOCKS may resolve the HTTP proxy’s hostname remotely; the HTTP proxy then resolves the URL destination. Trace the two names separately.

curl -v --preproxy socks5h://127.0.0.1:1080 --proxy http://HTTP_PROXY_HOST:3128 http://example.com/

در نمونه، `HTTP_PROXY_HOST` باید از SSH host قابل‌دسترسی باشد. پیش از اجرا احراز هویت هر hop را جدا بررسی کن: SOCKS auth با HTTP proxy 407 یکی نیست. اگر credential داری، در command line نگذار—ممکن است در history/process list بیفتد. از حساب آزمایشی و روش امن محیط خودت استفاده کن.

In the example, HTTP_PROXY_HOST must be reachable from the SSH host. Check each hop’s authentication independently: SOCKS auth is not the HTTP proxy’s 407 challenge. Do not put real credentials on a command line; they may appear in shell history or process listings. Use a test account and your environment’s secure method.

آزمایش دو-hop روی محیطی که کنترل می‌کنیTwo-hop lab on systems you control

دو lab VM یا میزبان آزمایشی لازم است: A با SSH و dynamic forwarding، و B با HTTP proxy مجاز. هر دو باید زیر کنترل تو باشند؛ open proxy عمومی نساز. اول اتصال مستقیم از client به B را فقط برای مقایسه امتحان کن، بعد SSH tunnel را بساز و B را از مسیر A صدا بزن:

Use two lab VMs or test hosts: A with SSH dynamic forwarding, and B with an authorized HTTP proxy. You must control both; do not create a public open proxy. First test direct client-to-B only as a baseline, then create the SSH tunnel and reach B through A:

ssh -N -D 127.0.0.1:1080 user@PROXY_A
curl -v --preproxy socks5h://127.0.0.1:1080 --proxy http://PROXY_B:3128 http://example.com/

درخواست را با شناسهٔ آزمایش غیرحساس علامت بزن؛ مثلاً header یکتا. در B access log و در origin log، همان ID و زمان را پیدا کن. SSH `-vv` می‌تواند dynamic forwarding و اتصال مقصد را نشان دهد. logهای هر محصول format متفاوت دارند و ممکن است header سفارشی را ثبت نکنند؛ پیش از lab format را بررسی کن. درخواست موفق به‌تنهایی ثابت نمی‌کند هر سه hop ثبت شده‌اند.

Tag the request with a non-sensitive unique test ID, such as a header. Find the ID and timestamp in B’s access log and the origin log. SSH `-vv` can show dynamic forwarding and destination connection. Logging formats differ and may omit custom headers; inspect formats before the lab. A successful response alone does not prove all three hops were observed.

curl -v -H "X-Lab-ID: chain-001" --preproxy socks5h://127.0.0.1:1080 --proxy http://PROXY_B:3128 http://example.com/

برای سنجش، baseline و chain را چند بار با URL و ساعت مشابه مقایسه کن؛ cache hit را از miss جدا کن. تفاوت `time_total` را latency دقیق A یا B ننام. log correlation نشان می‌دهد درخواست در مسیر دیده شده؛ لزوماً محتوای همهٔ TLS legها یا علت دقیق delay را نه.

Compare baseline and chain several times with the same URL and similar conditions; separate cache hits from misses. Do not label the difference in `time_total` as the exact latency of A or B. Correlated logs show the request traversed observed points, not the contents of every TLS leg or the precise cause of delay.

خرابی عمدی: hop دوم در دسترس نیستDeliberate failure: the second hop is unavailable

port HTTP proxy در B را اشتباه کن یا سرویس آزمایش را در B متوقف کن؛ SSH/SOCKS روی A را دست‌نخورده نگه دار. حالا درخواست شکست می‌خورد. پیش از اصلاح، trace curl، `ssh -vv` و log A/B را در یک timeline بچین. اگر tunnel محلی بالا است ولی curl نمی‌تواند به HTTP_PROXY_HOST وصل شود، موفقیت hop اول دربارهٔ دسترسی hop دوم چیزی نمی‌گوید.

Use the wrong HTTP-proxy port on B or stop the lab service there, while leaving SSH/SOCKS on A untouched. The request now fails. Before fixing it, align curl trace, `ssh -vv`, and A/B logs on a timeline. A live local tunnel does not prove the second hop is reachable.

یک خطای دیگر در زنجیره، loop است: A درخواست را به B می‌فرستد و B دوباره به A برمی‌گرداند. بسته به محصول ممکن است loop-detection، timeout یا ترافیک تکراری ببینی. chain را عمداً loop نکن روی شبکهٔ واقعی؛ در config disposable فقط یک upstream را اشتباه کن و از logهای مقصد و hopها evidence بگیر. بعد مسیر A→B→origin را یک‌طرفه و روشن کن.

Another chain failure is a loop: A sends to B, and B routes back to A. Depending on the product you may see loop detection, timeouts, or repeated traffic. Never create a loop on a real network; in disposable configuration, mis-set one upstream and use hop/origin logs as evidence. Then restore the unambiguous A→B→origin path.

هر hop یک failure domain تازه استEvery hop adds a failure domain

فهرست خطا فقط «proxy down» نیست: name resolution مقصد A، اتصال client→A، auth روی A، DNS نام B، اتصال A→B، ACL در B، DNS origin، TLS client→proxy یا TLS proxy→origin. آزمون را از بیرونی‌ترین شکست جدا کن و همان مرز را دوباره verify کن. در chain، credentialها و log retention هر مالک باید جدا بررسی شود.

The fault list is not just “proxy down”: resolving A, client-to-A connection, A authentication, resolving B, A-to-B connection, B ACL, origin DNS, client-to-proxy TLS, or proxy-to-origin TLS. Diagnose the earliest failing boundary and retest that same boundary. Credentials and log retention must be reviewed separately for every owner.

MTU معمولاً مسئلهٔ اصلی در HTTP proxy chain نیست؛ آن را بی‌دلیل وارد تشخیص نکن. در تونل‌های لایهٔ شبکه یا VPN، encapsulation می‌تواند MTU را مهم کند—آن بخش را در فصل کارایی/مسیریابی با اندازه‌گیری دنبال می‌کنیم.

MTU is rarely the first explanation for an ordinary HTTP-proxy-chain failure; do not add it without evidence. Encapsulation can make MTU important in network-layer tunnels or VPNs, which we’ll measure in the routing/performance chapters.

۱۸ تمرین؛ مسئول هر hop را پیدا کن18 exercises: identify the owner of each hop

۱. دلیل hop دوم

یک دلیل عملیاتی معتبر برای اضافه‌کردن proxy B بعد از A بنویس.

Give one valid operational reason to add proxy B after A.

پاسخ نمونه

رسیدن به شبکهٔ آزمایش از راه SSH و سپس اعمال egress policy سازمانی در B.

Reach a lab network over SSH, then apply organizational egress policy at B.

۲. هزینهٔ تازه

با افزودن B چه دو هزینه/ریسکی زیاد می‌شود؟

Name two costs or risks increased by adding B.

پاسخ

latency/handshake، نقطهٔ خرابی، logging و credential boundary.

Latency/handshakes, failure points, logging, and credential boundaries.

۳. timeout در کدام hop؟

curl به A وصل است ولی B logی ندارد. کدام مرزها را چک می‌کنی؟

curl reaches A, but B has no log. Which boundaries do you inspect?

پاسخ

A→B route/DNS/port، و اینکه درخواست از A خارج شده یا نه؛ log نبودن به‌تنهایی نبودن اتصال را قطعی نمی‌کند.

A-to-B route/DNS/port and whether A sent the request; missing logs alone do not prove no connection occurred.

۴. preproxy

در `--preproxy socks5h://A --proxy http://B` SOCKS معمولاً به کدام peer نهایی وصل می‌شود؟

In that curl setup, which peer does SOCKS typically help curl reach?

پاسخ

خود HTTP proxy در B؛ HTTP proxy بعداً URL origin را درخواست می‌کند.

The HTTP proxy at B; that proxy then requests the origin URL.

۵. DNS در چند جا

در chain نام HTTP_PROXY_HOST و نام origin ممکن است کجا resolve شوند؟

Where might HTTP_PROXY_HOST and origin DNS resolution happen?

پاسخ

host B را SOCKS remote می‌تواند resolve کند؛ origin را HTTP proxy B. تنظیم و request form را بررسی کن.

SOCKS remote may resolve B’s host; HTTP proxy B may resolve the origin. Verify actual settings and request form.

۶. هویت peer

origin اتصال را از B می‌بیند. آیا A دیگر در هیچ logی ثبت نشده؟

The origin sees B as its peer. Does that mean A appears in no logs?

پاسخ

نه؛ هر hop ممکن است نشانی/metadata خودش را log کند. origin peer socket را از header ادعایی جدا کن.

No; each hop may log its own address/metadata. Separate origin socket peer from forwarded headers.

۷. encryption boundary

A با SSH به client وصل است و B با HTTP plain به origin می‌رود. کدام مسیر رمز است؟

A is reached through SSH, while B uses plain HTTP upstream. Which segments are encrypted?

پاسخ

SSH leg تا A؛ باقی مسیر را فقط با scheme/transport خودشان تعیین کن، اسم chain کافی نیست.

The SSH leg to A; determine the rest from their actual transports, not from the fact of chaining.

۸. time_total

زمان کل chain دو برابر baseline است. آیا B دقیقاً همان مقدار تأخیر افزوده؟

Total chain time doubles. Did B add exactly the difference?

پاسخ

نه؛ شرایط، DNS، handshake، cache و زمان‌سنجی curl هم اثر دارند؛ نمونه‌های کنترل‌شده و trace لازم است.

No; conditions, DNS, handshakes, caching, and curl timing matter; use controlled samples and traces.

۹. cache hit

درخواست دوم خیلی سریع‌تر است. قبل از نسبت‌دادن آن به شبکه چه فرضیه‌ای را بررسی می‌کنی؟

The second request is much faster. What do you check before crediting the network?

پاسخ

cache hit، keep-alive/connection reuse و گرم‌شدن DNS یا TLS.

Cache hit, connection reuse/keep-alive, and DNS/TLS warm-up.

۱۰. auth جدا

SOCKS authentication موفق است ولی B پاسخ 407 می‌دهد. مشکل کدام لایه است؟

SOCKS authentication succeeds, but B returns 407. Which layer failed?

پاسخ

احراز هویت HTTP proxy در B؛ credential SOCKS آن را برطرف نمی‌کند.

HTTP proxy authentication at B; SOCKS credentials do not satisfy it.

۱۱. X-Lab-ID پیدا نشد

origin ID را log کرده، Squid B نکرده. آیا درخواست از B رد نشده؟

The origin logged the request ID but Squid B did not. Does that prove it bypassed B?

پاسخ

نه؛ log format ممکن است header سفارشی را ننویسد. format و hop logs را بررسی کن.

No; the log format may omit custom headers. Check format and other hop logs.

۱۲. A listener هست، درخواست نیست

SSH -D بالا است؛ B خاموش است. انتظار چه نوع شکست می‌رود؟

SSH -D is running, but B is stopped. What failure do you expect?

پاسخ

اتصال A→B یا درخواست proxy شکست می‌خورد؛ listener محلی فقط hop اول را ثابت می‌کند.

A-to-B connection or proxy request fails; a local listener proves only the first hop exists.

۱۳. loop

A upstream را B می‌داند و B upstream را A. چه نشانه‌هایی می‌توانی ببینی؟

A forwards to B and B forwards to A. What symptoms might appear?

پاسخ

loop detection، timeout، درخواست‌های تکراری یا رشد بار؛ رفتار دقیق وابسته به محصول است.

Loop detection, timeout, repeated requests, or load growth; behavior is product-specific.

۱۴. نقطهٔ fix

curl به A وصل شده، A log می‌گوید dial B ناموفق. اولین اصلاح کوچک کدام است؟

curl reaches A, and A logs failure to dial B. What is the first minimal check/fix?

پاسخ

از A، نام/route/port B و listener/ACL را بررسی کن؛ client DNS را بی‌دلیل تغییر نده.

From A, verify B’s name/route/port and listener/ACL; do not change client DNS without evidence.

۱۵. origin timeout

B درخواست را می‌بیند اما origin نه. چه hopی را بررسی می‌کنی؟

B sees the request, but the origin does not. Which hop do you inspect?

پاسخ

B→origin DNS, route, ACL, TCP/TLS؛ trace B و origin کنار هم لازم‌اند.

B-to-origin DNS, route, ACL, TCP/TLS; compare B and origin evidence.

۱۶. chain و anonymity

سه proxy در مسیر است. آیا این تعداد، ناشناسی را تضمین می‌کند؟

Three proxies are in the path. Does the count guarantee anonymity?

پاسخ

نه؛ trust، correlation، logging، DNS و endpointها مهم‌اند؛ تعداد hop معیار کافی نیست.

No; trust, correlation, logs, DNS, and endpoints matter; hop count is not enough.

۱۷. MTU

HTTP chain معمولی timeout داده. آیا اول MTU را پایین می‌آوری؟

An ordinary HTTP proxy chain times out. Do you lower MTU first?

پاسخ

نه؛ اول DNS/connection/ACL/TLS و logها. MTU را وقتی encapsulation و شواهد fragmentation/small-packet behavior مطرح است بسنج.

No; inspect DNS, connections, ACLs, TLS, and logs first. Measure MTU when encapsulation and packet evidence point there.

۱۸. timeline

در یک failure report چه چهار timestamp/شاهدی برای correlation جمع می‌کنی؟

Which timestamps/evidence do you collect to correlate a chain failure?

پاسخ نمونه

client شروع/خطا؛ A اتصال مقصد؛ B access/error؛ origin request ID/پاسخ. ساعت‌ها باید قابل‌مقایسه باشند.

Client start/error; A destination connection; B access/error; origin request ID/response. Clocks must be comparable.

هر واسطه باید برای خودش دلیل بیاوردEvery intermediary must justify its place

وقتی chain اضافه می‌کنی، مسیر را به hopهای قابل‌مشاهده بشکن: اتصال client→A، A→B، B→origin. برای هر کدام بپرس DNS کجا حل شد، credential کجا مصرف شد، TLS کجا تمام شد و چه logی شاهد است. بعد زمان کل را بسنج، اما از آن عدد latency هر hop را حدس نزن. اگر یک hop خراب شد، شواهد نزدیک همان مرز را جمع کن و فقط همان مسیر را اصلاح کن.

When you add a chain, split it into observable hops: client-to-A, A-to-B, B-to-origin. For each, ask where DNS resolved, where credentials were used, where TLS terminated, and which logs provide evidence. Measure total time, but do not infer each hop’s latency from that one number. When a hop fails, gather evidence near that boundary and repair only that path.

یک علت واقعی برای hop بعدی لازم است؛ صرفِ «مسیر بیشتر یعنی امن‌تر» کافی نیست. فصل بعد از proxyهای برنامه‌ای فاصله می‌گیریم و می‌پرسیم VPN چه چیزی را در لایهٔ شبکه tunnel می‌کند.

Every extra hop needs a real purpose; “more hops means safer” is not enough. Next we move beyond application proxies and ask what a VPN tunnels at the network layer.
