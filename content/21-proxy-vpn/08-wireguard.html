WireGuard

WireGuard

کلید، peer، و راه‌اندازی از صفر.

Keys, peers, and a first working tunnel.

۹۰دقیقهminutes
۱۸تمرینexercises

دو ماشین همدیگر را می‌بینند، اما route داخلی ندارندTwo machines can reach each other, but lack a private route

دو Linux VM آزمایشی داری؛ می‌توانند روی شبکهٔ بیرونی به هم UDP بفرستند، اما می‌خواهی یک subnet خصوصی میانشان داشته باشی. WireGuard interface و keypair می‌سازد؛ هر peer، public key طرف مقابل و prefixهایی را می‌شناسد که از آن peer انتظار می‌رود. مسیر بیرونی برای رسیدن به endpoint است؛ IPهای tunnel برای packetهای داخل شبکه.

You have two disposable Linux VMs that can exchange UDP on an outer network, but need a private subnet between them. WireGuard creates an interface and keypairs; each peer knows the other’s public key and the prefixes expected through it. The outer route reaches an endpoint; tunnel IPs address packets inside the VPN.

آدرس endpoint، IP تونل و prefixهای AllowedIPs سه مفهوم جدا هستند.

Endpoint address, tunnel IP, and AllowedIPs prefixes are three distinct concepts.

اول کلید؛ private key بیرون این VM نمی‌رودStart with keys; the private key stays on its VM

هر VM private/public keypair خودش را می‌سازد. private key برای ساخت handshake و رمزنگاری می‌ماند روی همان peer؛ public key را به طرف مقابل می‌دهی. برای هر VM فقط یک جفت بساز و فایل را با دسترسی محدود نگه دار. این فرمان را روی دو VM جدا و lab اجرا کن، نه روی یک فایل مشترک:

Each VM generates its own keypair. The private key remains on that peer for handshakes and encryption; share only its public key with the other side. Generate a separate pair on each VM and restrict file access. Run this in the lab on both VMs, not into one shared key file:

umask 077
wg genkey | tee privatekey | wg pubkey > publickey
chmod 600 privatekey

public key را با `cat publickey` می‌توانی در config طرف مقابل وارد کنی؛ private key را در chat، Git، log یا این صفحه paste نکن. بعد از rotate، public key peer مقابل هم باید به‌روز شود. WireGuard Quick Start

Read the public key with `cat publickey` and enter it on the other peer; never paste the private key into chat, Git, logs, or this page. After key rotation, update the corresponding peer configuration too.

Interface، address، peer و routeInterface, address, peer, and route

در دو VM جدا configی شبیه زیر بساز. جای placeholderها فقط public/private key خود lab و outer address قابل‌دسترسی را بگذار؛ secret واقعی نمونه نساز. `Address` روی wg0 آدرس داخلی است، `ListenPort` UDP بیرونی روی A، و `Endpoint` آدرس بیرونی A را به B می‌دهد. فایروال VM-A باید همان UDP port را فقط از منبع/شبکهٔ مجاز بپذیرد.

Create configurations like these on two separate VMs. Replace placeholders only with lab-generated keys and reachable outer addresses; do not invent a real secret. `Address` is the inner wg0 address, `ListenPort` is A’s outer UDP port, and `Endpoint` tells B how to reach A. VM-A’s firewall should allow that UDP port only from an authorized source/network.

# VM-A: /etc/wireguard/wg0.conf
[Interface]
Address = 10.77.0.1/24
ListenPort = 51820
PrivateKey = <VM_A_PRIVATE_KEY>

[Peer]
PublicKey = <VM_B_PUBLIC_KEY>
AllowedIPs = 10.77.0.2/32
# VM-B: /etc/wireguard/wg0.conf
[Interface]
Address = 10.77.0.2/24
PrivateKey = <VM_B_PRIVATE_KEY>

[Peer]
PublicKey = <VM_A_PUBLIC_KEY>
Endpoint = <VM_A_OUTER_IP>:51820
AllowedIPs = 10.77.0.1/32
PersistentKeepalive = 25

هر دو سمت `AllowedIPs` را برای peer مقابل درست می‌کنند. این فقط ACL اسم‌مانند نیست: WireGuard از آن برای انتخاب peer مقصد packet و برای بررسی source IP packet ورودی استفاده می‌کند. با `wg-quick` هم prefixها معمولاً به routeهای OS تبدیل می‌شوند؛ `wg` خام interface crypto config را مدیریت می‌کند ولی خودش الزاماً route table را تنظیم نمی‌کند. ابزار/پلتفرم را از command مشخص کن.

Both peers set AllowedIPs for the remote peer. It is more than a label-like ACL: WireGuard uses it to select a peer for outgoing destination addresses and to validate source addresses on received packets. `wg-quick` also normally translates prefixes into OS routes; the lower-level `wg` tool configures WireGuard but does not necessarily configure the OS route table. Distinguish the tool and platform.

`PersistentKeepalive = 25` گاهی برای peer پشت NAT کمک می‌کند mapping باز بماند؛ همهٔ شبکه‌ها به آن نیاز ندارند و مقدار را policy/نیاز تعیین می‌کند. Peer A که endpointش B را نمی‌داند معمولاً با اولین packet معتبر، endpoint را یاد می‌گیرد؛ برای lab بهتر است B اتصال را آغاز کند.

`PersistentKeepalive = 25` can help a peer behind NAT keep a mapping alive; not every network needs it, and the value is policy-dependent. A peer without a configured endpoint may learn it from an authenticated packet; for this lab, let B initiate.

Tunnel را بالا بیاور، ولی success را در سه لایه بسنجBring up the tunnel, then verify three layers

config فایل حساس است؛ permission را به 600 محدود کن. `wg-quick up` route و interface ایجاد می‌کند و تغییر host می‌دهد، پس فقط در disposable Linux VM اجرا کن. پیش از اجرا interface name را بررسی و مطمئن شو config درست انتخاب شده:

The configuration is sensitive; restrict its permissions to 600. `wg-quick up` creates interfaces and routes and changes the host, so run it only in disposable Linux VMs. Confirm the interface name and intended config first:

sudo install -m 600 wg0.conf /etc/wireguard/wg0.conf
sudo wg-quick up wg0

`wg show` handshake و transfer counters را نشان می‌دهد؛ `ip address show wg0` address/link را؛ `ip route get 10.77.0.2` route lookup را. این سه شاهد را جدا بنویس. handshake می‌تواند هنوز «never» باشد تا traffic آغاز شود؛ ping تازه handshake را trigger می‌کند.

`wg show` reports handshakes and transfer counters; `ip address show wg0` shows address/link; `ip route get 10.77.0.2` shows the route decision. Record them separately. Handshake may remain “never” until traffic starts; a ping can trigger it.

sudo wg show
ip -brief address show wg0
ip route get 10.77.0.2
ping -c 3 10.77.0.2
sudo wg show

تغییر `latest handshake` و counterها بعد از ping نشان می‌دهد تبادل رمزدار میان peerها رخ داده؛ پاسخ ping علاوه بر آن ICMP/firewall و inner route را هم می‌آزماید. اگر handshake بالا رفت ولی ping جواب نداد، کلید/endpoint را همان اول مقصر ندان؛ firewall ورودی، AllowedIPs، route و ICMP policy را ببین.

A recent handshake and increased counters after ping show encrypted exchange between peers; ping also tests ICMP/firewall and inner routing. If handshake advances but ping fails, do not immediately blame keys or endpoint—inspect inbound firewall, AllowedIPs, route, and ICMP policy.

خرابی عمدی: handshake هست، subnet عبوری نیستDeliberate failure: handshake works, routed subnet does not

پس از اتصال point-to-point، یک subnet آزمایش پشت VM-A تعریف کن ولی برای peer B آن prefix را اشتباه یا حذف‌شده بگذار. درخواست به tunnel IP ممکن است هنوز کار کند؛ مقصد داخل subnet نه. پیش از fix، `wg show` handshake/counter، `ip route get DESTINATION`, firewall/forwarding و `sysctl net.ipv4.ip_forward` را ثبت کن. این مشکل را از handshake failure جدا می‌کند.

After the point-to-point link works, define a test subnet behind VM-A but deliberately omit or misconfigure that prefix for B. The tunnel IP may still work while the subnet destination fails. Before fixing, record `wg show` handshake/counters, `ip route get DESTINATION`, firewall/forwarding, and `sysctl net.ipv4.ip_forward`. This separates routed-traffic failure from handshake failure.

برای routed subnet، AllowedIPs سمت client باید مقصدها را به peer انتخاب کند؛ VM-A هم باید IP forwarding مجاز داشته باشد، firewall اجازه دهد و برگشت route موجود باشد. NAT شاید برای شبکه‌ای که route برگشت ندارد لازم شود، اما آن را پیش‌فرض نکن—اول route دوطرفه را بفهم. بعد prefix را درست کن و همان مقصد را دوباره test کن. این lab را روی LAN/home router یا server اصلی اجرا نکن.

For a routed subnet, the client’s AllowedIPs must select that peer for the destination; VM-A must permit IP forwarding, firewall policy must allow it, and a return route must exist. NAT may be needed when the remote network has no return route, but do not default to NAT—understand bidirectional routing first. Correct the prefix, then retest the same destination. Never perform this lab on your daily LAN/router or production server.

پایان lab: routeها را هم جمع کنEnd the lab: clean up routes too

در هر دو VM tunnel را پایین بیاور و status را بررسی کن. `wg-quick down` routeهایی را که خودش ایجاد کرده جمع می‌کند؛ اگر دستی route/firewall rule افزوده‌ای، فقط همان rule ثبت‌شده را حذف کن. پیش از cleanup، `wg show`, `ip route`, و نتیجهٔ ping را نگه دار. هیچ‌وقت فایل config را در Git commit نکن.

Bring the tunnel down on both VMs and verify status. `wg-quick down` removes routes it created; if you added manual routes/firewall rules, remove only those recorded lab changes. Preserve `wg show`, routes, and ping evidence first. Never commit the config file to Git.

sudo wg-quick down wg0
ip -brief address
ip route

برای gateway واقعی علاوه بر tunnel point-to-point باید forwarding، firewall و شاید NAT را دقیق طراحی کنی. برای capstone همین فصل کفایت می‌کند تا این وابستگی‌ها را تشخیص بدهی؛ commandهای عمومیِ بازکردن همهٔ ترافیک را copy نکن.

A real gateway additionally needs deliberate forwarding, firewall, and perhaps NAT design. This chapter’s lab only aims to make those dependencies recognizable; do not copy generic rules that open all traffic.

۱۸ تمرین؛ peer، route و handshake را قاطی نکن18 exercises: separate peer, route, and handshake

۱. key ownership

کدام کلید را به peer می‌دهی و کدام روی دستگاه می‌ماند؟

Which key do you share with the peer, and which stays local?

پاسخ

public key را share می‌کنی؛ private key باید محلی و محدود بماند.

Share the public key; keep the private key local and restricted.

۲. listen port

ListenPort در کدام addressing space است: tunnel IP یا بیرونی؟

Does ListenPort belong to the tunnel address space or the outer transport?

پاسخ

بیرونی؛ UDP port روی host/interface بیرونی.

Outer transport: a UDP port on the outer host/interface.

۳. Endpoint

Endpoint چه چیزی را مشخص می‌کند؟

What does Endpoint identify?

پاسخ

آدرس بیرونی و port برای رسیدن به peer، نه IP داخل tunnel.

The peer’s outer address and port, not its inner tunnel IP.

۴. AllowedIPs outbound

دوران outgoing، AllowedIPs چه نقشی دارد؟

For outgoing traffic, what role does AllowedIPs play?

پاسخ

کمک می‌کند peer مناسب برای destination IP انتخاب شود.

It selects the peer associated with a destination prefix.

۵. AllowedIPs inbound

برای packet دریافتی چه چیزی با AllowedIPs سنجیده می‌شود؟

What does AllowedIPs validate for received packets?

پاسخ

source IPهای مجاز برای همان peer.

Permitted source addresses for that peer.

۶. wg vs wg-quick

چرا `wg show` route table را کامل توضیح نمی‌دهد؟

Why does `wg show` not fully explain the OS route table?

پاسخ

`wg` وضعیت WireGuard را نشان می‌دهد؛ `wg-quick`/OS integration routeها را هم تنظیم می‌کند.

`wg` shows WireGuard state; `wg-quick` and OS integration manage routes too.

۷. handshake never

latest handshake برابر never است. قبل از تغییر AllowedIPs چه trigger ساده‌ای امتحان می‌کنی؟

Latest handshake is “never.” What simple trigger do you try before changing AllowedIPs?

پاسخ

به tunnel IP peer ping یا ترافیک بی‌خطر می‌فرستم تا handshake آغاز شود؛ بعد endpoint/firewall/key را می‌سنجم.

Send harmless traffic such as a tunnel-IP ping to initiate a handshake, then inspect endpoint/firewall/keys.

۸. counters

handshake تازه و sent زیاد، received بدون تغییر. کجا را بررسی می‌کنی؟

Handshake is recent and sent bytes rise, but received stays flat. What do you inspect?

پاسخ

پاسخ سمت peer، firewall/route برگشت و مقصد؛ «ارسال شد» تحویل به برنامه را ثابت نمی‌کند.

Peer response, return routing/firewall, and destination; “sent” does not prove application delivery.

۹. tunnel IP کار می‌کند

ping به 10.77.0.1 موفق، اما subnet پشت peer در دسترس نیست. سه وابستگی؟

Tunnel IP ping works, but the peer’s routed subnet is unreachable. Name three dependencies.

پاسخ

AllowedIPs prefix، IP forwarding، firewall و return route (چهار شاهد مرتبط).

AllowedIPs prefix, IP forwarding, firewall, and return route.

۱۰. PersistentKeepalive

چرا B پشت NAT ممکن است keepalive لازم داشته باشد و چرا عدد 25 قانون همگانی نیست؟

Why might a peer behind NAT need keepalive, and why is 25 not a universal rule?

پاسخ

برای نگه‌داشتن NAT mapping؛ نیاز و interval به NAT/network policy بستگی دارد.

To retain a NAT mapping; need and interval depend on the network.

۱۱. UDP firewall

interface config درست است ولی هیچ handshake نمی‌آید. کدام outer firewall rule را verify می‌کنی؟

Configuration looks right, but no handshake arrives. Which outer firewall rule do you verify?

پاسخ

UDP listen port روی endpoint VM-A از مبدأ مجاز؛ علاوه بر provider firewall.

The UDP listen port at VM-A, allowed from the authorized source, plus any provider firewall.

۱۲. overlapping prefixes

دو peer prefixهای هم‌پوشان دارند. چه چیزی ممکن است مبهم/ناخواسته شود؟

Two peers have overlapping prefixes. What can become ambiguous or unintended?

پاسخ

انتخاب peer/route و source validation؛ prefixها را غیرهم‌پوشان و دقیق طراحی کن.

Peer/route selection and source validation; design precise non-overlapping prefixes.

۱۳. handshake در برابر route

`wg show` handshake تازه دارد، ولی `ip route get` مقصد را از eth0 می‌فرستد. کدام issue محتمل است؟

`wg show` shows a fresh handshake, but route lookup sends the destination via eth0. What is likely wrong?

پاسخ

route/AllowedIPs یا integration، نه الزاماً crypto handshake.

Route/AllowedIPs or integration, not necessarily cryptographic handshake.

۱۴. file permission

چرا config در /etc/wireguard دسترسی محدود می‌خواهد؟

Why should a config under /etc/wireguard have restricted permissions?

پاسخ

حاوی private key است؛ خواندن غیرمجاز می‌تواند هویت peer را بدزدد.

It contains a private key; unauthorized reading can steal peer identity.

۱۵. endpoint route recursion

بعد full-tunnel route، handshake قطع می‌شود و endpoint از wg0 route می‌شود. چه مسیر اصلاحی می‌خواهی؟

After a full-tunnel route, handshakes stop and the endpoint routes via wg0. What kind of correction is needed?

پاسخ

outer endpoint باید route بیرونی/استثنای پایدار داشته باشد؛ روش دقیق تابع client/wg-quick OS است.

The outer endpoint needs a stable outside route/exception; exact method depends on the client/OS integration.

۱۶. forwarding sysctl

برای gateway کردن VM-A، چرا handshake به‌تنهایی کافی نیست؟

Why is a handshake alone insufficient when VM-A is a gateway?

پاسخ

kernel forwarding، firewall و مسیر برگشت نیز باید اجازه دهند packetها عبور کنند.

Kernel forwarding, firewall policy, and return routes must also permit packets.

۱۷. NAT اولین راه‌حل نیست

subnet ریموت جواب نمی‌دهد. چرا پیش از NAT route دوطرفه را بررسی می‌کنی؟

A remote subnet fails. Why inspect bidirectional routes before adding NAT?

پاسخ

NAT آدرس را پنهان/تغییر می‌دهد و می‌تواند عیب route را mask کند؛ ممکن است route برگشت درست کافی باشد.

NAT rewrites addresses and can mask routing faults; a correct return route may be sufficient.

۱۸. گزارش lab

معیار

شواهد layerهای مجزا باشند؛ «فعال است» جای اثبات traffic مسیر را نمی‌گیرد.

Keep evidence for distinct layers; “active” is not proof that traffic traversed the intended path.

کلید، peer و route را جدا بخوانRead keys, peers, and routes separately

WireGuard config کوتاه است، ولی سه مفهوم را فشرده می‌کند: private/public key هویت peer؛ Endpoint مسیر بیرونی؛ AllowedIPs انتخاب peer و محدودهٔ sourceهای پذیرفته‌شده. `wg show` handshake و counter می‌دهد؛ `ip route` تصمیم kernel را؛ ping و برنامه مسیر واقعی را. وقتی یکی شکست خورد، با عوض‌کردن تصادفی همهٔ فیلدها بقیه را خراب نکن—همان لایه را جدا بسنج.

WireGuard configuration is compact but combines three concepts: keys identify peers; Endpoint describes the outer route; AllowedIPs selects peers and accepted source prefixes. `wg show` reports handshake/counters; `ip route` shows the kernel decision; ping and the application test actual reachability. When one layer fails, avoid random edits across all of them—test the failing layer.
