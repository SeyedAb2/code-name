یک درخواست آمد؛ حالا چطور ردش کنیم؟A request arrived; how do we relay it?

تا اینجا proxy را در trace دیدی. حالا با Python یک نمونهٔ کوچک می‌سازیم تا حس کنی دو socket و دو جهت جریان یعنی چه. این برنامه فقط CONNECT به یک origin آزمایشگاهی ثابت را می‌پذیرد، فقط روی loopback گوش می‌دهد و برای production نیست. همین محدودیت‌ها بخشی از درس‌اند: proxyای که مقصد دلخواه اینترنت را می‌پذیرد، می‌تواند به open proxy خطرناک تبدیل شود.

So far, you have seen proxies in traces. Now we’ll build a tiny Python example to make two sockets and two data directions tangible. It accepts CONNECT only to one fixed lab origin, listens only on loopback, and is not production software. Those constraints are part of the lesson: a proxy that accepts arbitrary Internet destinations can become a dangerous open proxy.

قبل از نوشتن relay، مسیر را مشخص کن: client به listener وصل می‌شود؛ برنامه headerها را می‌خواند؛ destination مجاز را باز می‌کند؛ پاسخ CONNECT می‌دهد؛ بعد هر دو سمت می‌توانند هم‌زمان داده بفرستند. همین «هم‌زمان» محل باگ جذاب ماست.

Before writing the relay, map the path: the client connects to a listener; the program reads headers; it opens an allowed destination; it replies to CONNECT; then both sides may send data at once. That “at once” is where our useful bug hides.

هر فلش یک جهت مستقل دارد؛ با تمام‌شدن یکی، جهت دیگر ممکن است هنوز داده داشته باشد.

Each arrow is an independent direction; when one ends, the other may still carry data.

نسخهٔ اول عمداً گیر می‌کندThe first version deliberately hangs

اگر بعد از CONNECT موفق بنویسی «همهٔ ورودی client را تا EOF بخوان، بعد تازه پاسخ origin را به client بفرست»، چه می‌شود؟ client ممکن است منتظر پاسخ origin باشد و origin منتظر ادامهٔ client؛ اما relay تا EOF منتظر مانده. هر دو طرف منتظر هم می‌مانند. حتی اگر یک درخواست ساده گاهی کار کند، پاسخ بزرگ، keep-alive یا جریان تعاملی گیر می‌کند.

What if after CONNECT you read all client input until EOF and only then copy the origin response back? The client may be waiting for origin data while the origin waits for more client input; your relay is waiting for EOF. Both sides stall. A simple request may appear to work, but large responses, keep-alive, or interactive streams can hang.

این خطا را با timeout کوتاه و دادهٔ دوطرفه در lab بازتولید کن؛ پیش از fix، timestamp آخرین بایت هر جهت را ثبت کن. راه‌حل این نیست که timeout را بی‌نهایت کنی؛ دو جریان را هم‌زمان کپی کن، وقتی یک سمت EOF داد فقط جهت متناظر را half-close کن، و برای اتصال بیکار حد زمانی بگذار.

Reproduce it with a short timeout and traffic in both directions; record when each direction last moved before fixing. The solution is not an infinite timeout: copy both streams concurrently, half-close only the corresponding write side on EOF, and enforce an idle deadline.

نمونهٔ کامل: فقط یک مقصد آزمایشگاهیA complete sample: one lab destination only

این پیاده‌سازی کوچک برای فهم جریان است، نه سازگار با همهٔ proxy clientها. header را تا اندازهٔ محدود می‌خواند، فقط CONNECT را می‌پذیرد، authority را بررسی می‌کند و مقصد را به 127.0.0.1:9000 محدود می‌سازد. برای هر client یک thread و برای هر جهت relay یک thread دارد؛ خطاها به قطع اتصال می‌رسند. TLS را باز نمی‌کند و headerهای HTTP داخل tunnel را دست‌کاری نمی‌کند.

This compact implementation teaches the stream, not full client compatibility. It reads a size-limited header, accepts only CONNECT, validates the authority, and restricts the destination to 127.0.0.1:9000. Each client gets a thread and each relay direction gets a thread; errors close the connection. It does not terminate TLS or alter HTTP headers inside the tunnel.

import socket
import socketserver
import threading

ALLOW_HOST, ALLOW_PORT = "127.0.0.1", 9000
LISTEN_HOST, LISTEN_PORT = "127.0.0.1", 8888
HEADER_LIMIT, IDLE_TIMEOUT = 16_384, 30

def read_headers(sock):
    data = bytearray()
    while b"\r\n\r\n" not in data:
        chunk = sock.recv(2048)
        if not chunk:
            raise ValueError("client closed before headers")
        data.extend(chunk)
        if len(data) > HEADER_LIMIT:
            raise ValueError("headers too large")
    return bytes(data).split(b"\r\n\r\n", 1)[0]

def relay(src, dst):
    try:
        while True:
            block = src.recv(16_384)
            if not block:
                break
            dst.sendall(block)
    except (OSError, TimeoutError):
        pass
    finally:
        try:
            dst.shutdown(socket.SHUT_WR)  # half-close only this direction
        except OSError:
            pass

class ProxyHandler(socketserver.BaseRequestHandler):
    def handle(self):
        client = self.request
        client.settimeout(IDLE_TIMEOUT)
        upstream = None
        try:
            first = read_headers(client).split(b"\r\n", 1)[0].decode("ascii")
            parts = first.split()
            if len(parts) != 3 or parts[0] != "CONNECT":
                client.sendall(b"HTTP/1.1 405 Method Not Allowed\r\nConnection: close\r\n\r\n")
                return
            host, port_text = parts[1].rsplit(":", 1)
            if host != ALLOW_HOST or int(port_text) != ALLOW_PORT:
                client.sendall(b"HTTP/1.1 403 Forbidden\r\nConnection: close\r\n\r\n")
                return
            upstream = socket.create_connection((ALLOW_HOST, ALLOW_PORT), timeout=5)
            upstream.settimeout(IDLE_TIMEOUT)
            client.sendall(b"HTTP/1.1 200 Connection Established\r\n\r\n")
            a = threading.Thread(target=relay, args=(client, upstream), daemon=True)
            b = threading.Thread(target=relay, args=(upstream, client), daemon=True)
            a.start(); b.start(); a.join(); b.join()
        except (OSError, ValueError, UnicodeError) as exc:
            print(f"proxy error from {self.client_address}: {exc}", flush=True)
        finally:
            if upstream is not None:
                upstream.close()

class ThreadedServer(socketserver.ThreadingTCPServer):
    allow_reuse_address = True
    daemon_threads = True

with ThreadedServer((LISTEN_HOST, LISTEN_PORT), ProxyHandler) as server:
    print(f"lab proxy listening on {LISTEN_HOST}:{LISTEN_PORT}", flush=True)
    server.serve_forever()

یک باگ عمدی را خودت پیدا کن: اگر host, port_text parse شود ولی port عددی نباشد، ValueError می‌گیری و handler می‌بندد؛ client پاسخ صریح 400 نمی‌گیرد. قبل از هر socket upstream، parse/validation را کامل کن و برای ورودی بد پاسخ 400 بده. نمونه برای production هنوز ناقص است: HTTP version/headers، request smuggling، auth، rate limit، metrics، graceful shutdown و IPv6 را کامل پیاده نمی‌کند.

Find one deliberate rough edge: if a non-numeric port reaches int(port_text), ValueError closes the handler without an explicit 400 response. Complete parsing and validation before opening an upstream socket, and reply 400 for malformed input. This is still not production-ready: it does not fully handle HTTP versions/headers, request smuggling, auth, rate limits, metrics, graceful shutdown, or IPv6.

آزمایش را از origin محلی شروع کنStart the lab with a local origin

سه ترمینال باز کن؛ هیچ port عمومی باز نمی‌شود. اول origin را فقط روی loopback اجرا کن؛ server نسخهٔ Python ممکن است با نسخه‌ها/سیستم‌عامل‌ها تفاوت جزئی داشته باشد:

Open three terminals; no public port is exposed. First run an origin on loopback only. Python’s server output can vary slightly by version and OS:

python -m http.server 9000 --bind 127.0.0.1

ترمینال دوم proxy code را مثلاً در proxy.py ذخیره و اجرا کن. نشانهٔ انتظار: پیام listening روی 127.0.0.1:8888. اگر bind شکست خورد، port اشغال است؛ process قبلی را شناسایی کن، نه اینکه listener را روی 0.0.0.0 ببری.

Save the proxy code as proxy.py and run it in terminal two. Expect a listening message on 127.0.0.1:8888. If binding fails, the port is occupied; identify the existing process rather than widening the listener to 0.0.0.0.

حالا client را به CONNECT و همان origin مجاز محدود کن. --proxytunnel باعث می‌شود حتی برای URL این آزمایش نیز curl ابتدا tunnel بخواهد؛ پاسخ HTTP server داخل tunnel برمی‌گردد. این TLS را آزمایش نمی‌کند:

Now restrict the client request to CONNECT and the same allowed origin. --proxytunnel makes curl request a tunnel even for this lab URL; the HTTP server’s response travels through it. This does not test TLS:

curl -v --noproxy "" --proxytunnel --proxy http://127.0.0.1:8888 http://127.0.0.1:9000/

در trace، CONNECT باید موفق شود و بعد محتوای directory listing از origin بیاید. این فقط loopback allowlist و relay را ثابت می‌کند. در برابر tunnel هم‌زمانِ دوطرفه، response بزرگ و چند client، رفتار را جداگانه آزمایش کن. دستور دیگری به host/port غیرمجاز بزن؛ انتظار 403 را ببین و تأیید کن proxy log/host هیچ outbound اتصال جدیدی ندارد.

The trace should show CONNECT success followed by the origin’s directory listing. This proves only the loopback allowlist and relay. Separately test simultaneous two-way traffic, a larger response, and multiple clients. Try a disallowed host/port; expect 403 and verify no outbound connection was made.

چرا دو pump و half-close؟Why two pumps and a half-close?

TCP جریان بایت است؛ مرز پیام ندارد. یک read ممکن است نصف یک پیام یا چند پیام را برگرداند، پس هر chunk را «یک درخواست» فرض نکن. sendall تا فرستادن همهٔ بایت‌ها تلاش می‌کند. دو pump مستقل اجازه می‌دهند client و server هم‌زمان بنویسند. وقتی client سمتش را بست، سمت upstream را write-half-close می‌کنیم تا origin بداند دیگر ورودی نمی‌آید، اما پاسخ برگشتی هنوز راه داشته باشد. timeout از اتصال بی‌نهایت‌مانده جلوگیری می‌کند، ولی باید متناسب با پروتکل باشد.

TCP is a byte stream, not a message protocol. One read may return part of a message or several together, so never treat each chunk as one request. sendall tries to send every byte. Independent pumps let both peers write simultaneously. When the client ends its write side, we half-close upstream so the origin knows no more request bytes are coming, while still allowing its response back. A timeout avoids forever-idle sockets, but must fit the protocol.

نمونهٔ بالا برای آموزش، timeout را روی هر socket تنظیم می‌کند؛ اگر فقط یک جهت بیکار بماند، pump آن جهت خطا می‌گیرد و half-close می‌کند. رفتار دقیق shutdown و socket exception در سیستم‌عامل‌ها فرق‌های کوچکی دارد؛ در برنامهٔ واقعی lifecycle، cancellation و resource cleanup باید با تست پوشش داده شود.

The sample applies socket timeouts; an idle direction raises an error and half-closes its peer. Shutdown and socket exceptions can vary slightly by OS. A real service needs tested lifecycle, cancellation, and resource cleanup.

یک relay کوچک، مسئولیت کوچک نیستA small relay is not a small responsibility

دیدی یک proxy چند کار جدا دارد: درخواست را درست parse کند، مقصد را محدود کند، دو اتصال را بسازد، دو جهت داده را هم‌زمان relay کند و هنگام EOF/timeout منابع را جمع کند. هر کدام می‌تواند bug یا سطح حمله شود. این نمونه عمداً loopback-only و تک‌مقصدی ماند؛ آن را باز نکن و روی اینترنت نگذار. برای محصول واقعی از proxy نگهداری‌شده، تنظیمات امن و تست پروتکلی استفاده کن.

A proxy has distinct jobs: parse requests, constrain destinations, create two connections, relay both directions concurrently, and clean up resources at EOF/timeout. Every job can become a bug or attack surface. This sample deliberately stays loopback-only and single-destination; do not open it up or put it on the Internet. Real services need maintained software, secure policy, and protocol testing.

حالا relay فقط بایت‌ها را می‌بیند. فصل بعد می‌پرسد چه وقت این بایت‌ها TLS هستند، گواهی در کدام نقطه بررسی می‌شود و termination چه چیزی را عوض می‌کند—بدون اینکه این toy را به MITM تبدیل کنیم.

Our relay now sees only bytes. Next we ask when those bytes are TLS, where certificates are verified, and what termination changes—without turning this toy into a man-in-the-middle.
