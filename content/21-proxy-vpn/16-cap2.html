ماموریت: دو دستگاه، یک راه کنترل‌شده به شبکهٔ آزمایشگاهیMission: two devices, a controlled path into a lab network

یک لپ‌تاپ وصل است، دومی هم باید دسترسی بگیرد. باید بتوانی نشان بدهی هر peer با کدام کلید شناخته می‌شود، packet از کدام interface عبور می‌کند و DNS از کدام مسیر جواب می‌دهد. «Latest handshake» به‌تنهایی نه route را ثابت می‌کند، نه دسترسی را.

One laptop is connected; a second needs access too. Show which key identifies each peer, which interface carries packets, and how DNS answers. A recent handshake alone proves neither routing nor access.

این پروژه را در سه VM لینوکسی روی شبکهٔ host-only یا internal اجرا کن: یک server و دو client. برای نصب package می‌توانی موقتاً اینترنت VM را وصل کنی؛ بعد جدا کن و نبودن default route بیرونی را ثابت کن. روی VPS عمومی، interface اصلی کامپیوتر یا شبکهٔ کاری اجرا نکن. اگر VM نداری، Linux network namespace هم شدنی است؛ runbook اینجا مسیر VM را کامل می‌کند.

Use three Linux VMs on a host-only/internal network: one server and two clients. You may temporarily connect VM internet for package installation, then disconnect it and prove there is no external default route. Do not run this on a public VPS, your computer’s primary interface, or a work network. Linux network namespaces are an alternative; this runbook fully describes the VM path.

شبکهٔ زیرین فقط clientها را به UDP server می‌رساند؛ مسیر داخلی از tunnel می‌گذرد و NAT عمومی نداریم.

The underlay only connects clients to the UDP server; internal traffic uses the tunnel, with no public NAT.

مرز پروژه: آزمایشگاه خصوصی، نه gateway اینترنتBoundary: a private lab, not an internet gateway

آدرس‌های نمونه فقط برای این lab هستند: underlay برابر `192.168.77.0/24`، server برابر `.10` و clientها `.11` و `.12`؛ tunnel برابر `10.77.0.0/24`. اگر hypervisor subnet دیگری ساخته، همه را هماهنگ عوض کن. peerها به هم و به DNS آزمایشگاهی می‌رسند؛ NAT اینترنت نداریم. برای full tunnel باید default route، DNS، endpoint reachability، برگشت مسیر و firewall را جدا طراحی کنی—از این پروژه نتیجه‌اش را حدس نزن.

These sample addresses belong only to this lab: underlay `192.168.77.0/24`, server `.10`, clients `.11` and `.12`; tunnel `10.77.0.0/24`. Change them consistently if your hypervisor uses another subnet. Peers reach each other and lab DNS; there is no internet NAT. A full tunnel requires separate design of default routes, DNS, endpoint reachability, return paths, and firewall.

هر VM یک interface host-only دارد؛ نام و آدرسش را یادداشت کن تا دستور را روی host اشتباه اجرا نکنی. نصب packageها را پیش از جداکردن اینترنت انجام بده. هیچ rule روی firewall میزبان اصلی نساز و هیچ UDP portی را به اینترنت forward نکن.

Each VM has a host-only interface; record its name and address so commands do not land on the wrong host. Install packages before disconnecting internet. Do not edit the main host firewall or forward any UDP port to the internet.

هفت checkpoint؛ هر بار یک مرز تازهSeven checkpoints, one new boundary at a time

۱. underlay را قبل از VPN ثابت کن

در هر VM `ip -br address` و `ip route` را ببین. هر client باید server را ping کند و هیچ default route بیرونی نداشته باشد. این فقط transport آزمایشگاه را ثابت می‌کند؛ هنوز WireGuard بالا نیست.

On each VM inspect `ip -br address` and `ip route`. Each client should ping the server, with no external default route. This proves only the lab transport; WireGuard is not running yet.

راهنمایی

اگر ping زیرین fail است، سراغ key و tunnel نرو؛ interface و subnet hypervisor را درست کن.

If the underlay ping fails, do not debug keys or the tunnel yet; fix the VM interface and subnet.

شاهد لازم

جدول VM/interface/IP/route، ping موفق و مدرک نبودن default route عمومی.

A VM/interface/IP/route table, successful ping, and proof of no public default route.

۲. سه هویت جدا بساز

روی هر VM private/public key خودش را بساز؛ `umask 077` بگذار، mode و owner را بررسی کن و فقط public key را میان VMها جابه‌جا کن. سرور باید دو public key متفاوت با برچسب client-A و client-B داشته باشد.

Generate a separate keypair on each VM; use `umask 077`, check mode and ownership, and copy only public keys between VMs. The server should have distinct public keys labeled client-A and client-B.

راهنمایی

کلید private را در screenshot یا گزارش نگذار. `stat` را روی فایل private اجرا کن؛ خروجی خود کلید را نمایش نده.

Never include private keys in screenshots or reports. Run `stat` on the private-key file without printing its contents.

شاهد لازم

دو peer مجزا و فایل private فقط برای مالک قابل‌خواندن؛ report هیچ secretی ندارد.

Two separate peers and owner-only private files; the report contains no secrets.

۳. handshake را از دسترسی جدا کن

server را روی UDP 51820 تنظیم کن. سمت server به A فقط `10.77.0.2/32` و به B فقط `.3/32` بده؛ clientها برای این lab مسیر `10.77.0.0/24` را در tunnel بگذارند. interfaceها را بالا بیاور، traffic بفرست و `wg show` را بخوان.

Configure the server on UDP 51820. Give A only `10.77.0.2/32` and B only `.3/32` server-side; clients route `10.77.0.0/24` through the tunnel for this lab. Bring interfaces up, send traffic, and inspect `wg show`.

راهنمایی

Endpoint به underlay server اشاره می‌کند، نه tunnel IP. هر client باید آدرس tunnel یکتا داشته باشد.

The endpoint points to the server’s underlay address, not its tunnel IP. Each client needs a unique tunnel address.

شاهد لازم

کلیدها به peer درست map شده‌اند، بعد از traffic handshake تازه می‌شود، route lookup از wg0 است و هر client به server ping می‌زند. handshake به‌تنهایی سرویس را ثابت نمی‌کند.

Keys map to the intended peers, traffic refreshes handshakes, route lookup selects wg0, and both clients ping the server. A handshake alone does not prove service access.

۴. سرویس داخلی و DNS اضافه کن

روی server یک HTTP سرویس آزمایشگاهی فقط روی `10.77.0.1:8080` و dnsmasq فقط روی `10.77.0.1:53` اجرا کن. نام `status.wg-lab.test` را به `10.77.0.1` جواب بده. از هر client با `curl` و `dig @10.77.0.1 status.wg-lab.test` امتحان کن.

Run a lab HTTP service only on `10.77.0.1:8080` and dnsmasq only on `10.77.0.1:53`. Resolve `status.wg-lab.test` to `10.77.0.1`. Test from both clients using `curl` and `dig @10.77.0.1 status.wg-lab.test`.

راهنمایی

query مستقیم، DNS server را می‌سنجد بی‌آنکه resolver سیستم را تغییر بدهی. timeout شد؟ کنار هم ببین: listener، route، handshake/counter.

A direct query tests the DNS server without changing the system resolver. On timeout, inspect listener, route, and handshake/counters together.

شاهد لازم

DNS پاسخ درست و HTTP بدنهٔ مورد انتظار را می‌دهد. این ثابت نمی‌کند resolver پیش‌فرض سیستم از این DNS استفاده می‌کند؛ آن را عمداً تنظیم نکرده‌ایم.

DNS returns the intended record and HTTP returns the expected body. This does not prove the system resolver uses this DNS; we intentionally did not configure it.

۵. failure عمدی: tunnel هست، forwarding نیست

روی server forwarding را خاموش کن، اما tunnel و peerها را دست‌نخورده بگذار. client به خود server می‌رسد اما به peer دیگر نه. پیش از بازکردن hint پیش‌بینی کن: handshake باید قطع شود؟ چه شاهدی forwarding را از route یا firewall جدا می‌کند؟

Disable forwarding on the server but leave tunnel and peers untouched. A client reaches the server but not the other peer. Before opening the hint, predict: should the handshake disappear? What evidence separates forwarding from route or firewall?

راهنمایی

مقدار `net.ipv4.ip_forward`، route lookup، handshake/counter و forward chain هر کدام پاسخ یک پرسش جدا هستند. یک‌بار فقط یک کنترل را تغییر بده.

`net.ipv4.ip_forward`, route lookup, handshake/counters, and the forward chain each answer a different question. Change only one control at a time.

تشخیص و تعمیر

اگر handshake تازه و route درست است ولی `ip_forward=0`، kernel packet عبوری را route نمی‌کند. فقط در VM سرور مقدار را موقتاً 1 کن، همان ping را تکرار و counter را بخوان؛ هنوز fail است؟ بعد firewall را بررسی کن.

If handshake and route are correct but `ip_forward=0`, the kernel is not forwarding transit packets. Temporarily set it to 1 only in the server VM, repeat the same ping, and inspect counters; if it still fails, check the firewall.

۶. firewall را با نیاز واقعی هماهنگ کن

روی VM server فقط UDP 51820 از underlay و مدیریت لازم را به input اجازه بده. forward را فقط برای tunnel-to-tunnel مجاز کن؛ input به خود server با عبور از server یکی نیست. ruleset و آزمون مجاز/غیرمجاز را ثبت کن. اگر VM از قبل UFW/firewalld/nftables دارد، policy را reset نکن و rule را از همان ابزار مدیریت کن.

On the server VM, allow only UDP 51820 from the underlay and required administration to input. Permit tunnel-to-tunnel traffic in forwarding; traffic to the server is not the same as traffic through it. Record rules and positive/negative tests. If the VM already uses UFW, firewalld, or nftables, do not reset policy; use its existing manager.

راهنمایی

هیچ تغییر firewall روی host اصلی لازم نیست. این lab نه UDP را به اینترنت expose می‌کند، نه full-tunnel می‌سازد.

No main-host firewall change is needed. This lab neither exposes UDP to the internet nor creates a full tunnel.

معیار تحویل

UDP listener برای دو client قابل‌دسترسی است؛ port نامرتبط باز نیست؛ مسیر forward محدود است و درخواست منفی واقعاً رد می‌شود.

Both clients can reach the UDP listener, unrelated ports remain closed, forwarding is narrow, and a negative test is actually denied.

۷. restart، counter و handoff

config را روی هر VM جدا نگه دار و permission فایل server را محدود کن. در server VM، `wg-quick@wg0` را enable کن، restart کنترل‌شده انجام بده و همان ping، DNS و HTTP را تکرار. پس از جمع‌آوری شاهد، VMها و شبکهٔ host-only را پاک‌سازی کن؛ private key/config را به گزارش کپی نکن.

Keep configs on their own VMs and restrict the server file’s permissions. Enable `wg-quick@wg0` in the server VM, restart it deliberately, and repeat the same ping, DNS, and HTTP tests. After collecting evidence, clean up the VMs and host-only network; never copy private keys/configs into the report.

راهنمایی

`systemctl enable --now` سرویس را فعال و اجرا می‌کند؛ «active» بعد از restart هنوز handshake و دسترسی را ثابت نمی‌کند.

`systemctl enable --now` enables and starts the unit; “active” after restart still does not prove handshake or access.

شاهد تحویل

پس از restart، هر دو peer دوباره handshake می‌کنند، HTTP و DNS پاسخ می‌دهند و rx/tx جلو می‌رود. `systemctl status` را کنار این شواهد ثبت کن.

After restart, both peers handshake again, HTTP and DNS respond, and rx/tx advances. Include `systemctl status` alongside these results.

پذیرش پروژه یعنی هر چراغ سبز، یک ادعاAcceptance means each green light proves one claim

Reviewer باید بتواند از گزارش تو transport خصوصی، دو هویت، AllowedIPs یکتا، handshake، forwarding محدود، پاسخ DNS و بازیابی بعد از restart را جداگانه ببیند. این پروژه ثابت نمی‌کند gateway برای اینترنت عمومی امن است؛ چنین هدفی نداشته‌ایم.

A reviewer should be able to verify private transport, two identities, unique AllowedIPs, handshake, constrained forwarding, DNS answers, and restart recovery separately. This project does not establish that an internet-facing gateway is secure; that was not its scope.

هر فرمان را در VM درست اجرا و خروجی را با نام VM/زمان برچسب بزن. بعد از repair همان تستی را تکرار کن که قبلش fail شد؛ فقط `active` یا handshake تازه برای پذیرش کافی نیست.

Run each command in the correct VM and label its output with VM and time. After repair, repeat the test that failed; `active` or a recent handshake alone is not acceptance.

runbook مرجع؛ placeholderها را با مقدار امن جایگزین کنReference runbook; replace placeholders safely

در این نمونه نام interface زیرین `enp0s8` فرض شده؛ با `ip -br link` نام واقعی را پیدا کن. روی همهٔ VMها WireGuard و روی server، `dnsmasq` و ابزارهای لازم را نصب کن؛ بعد virtual internet را جدا کن. هیچ keyای را در Git یا صفحهٔ دوره paste نکن.

This example assumes the underlay interface is `enp0s8`; find the real name with `ip -br link`. Install WireGuard on all VMs and `dnsmasq` plus needed tools on the server, then disconnect virtual internet. Never paste keys into Git or the course page.

روی هر VM کلید را با umask محدود بساز؛ فقط public key را کپی کن:

On each VM, generate keys with a restrictive umask; copy only the public key:

sudo install -d -m 700 /etc/wireguard/keys
sudo sh -c 'umask 077; wg genkey > /etc/wireguard/keys/private.key; wg pubkey < /etc/wireguard/keys/private.key > /etc/wireguard/keys/public.key'
sudo stat -c '%a %U:%G %n' /etc/wireguard/keys/private.key

فایل server را در `/etc/wireguard/wg0.conf` بساز و placeholderها را عیناً اجرا نکن:

Create the server file at `/etc/wireguard/wg0.conf`; do not use the placeholders literally:

[Interface]
Address = 10.77.0.1/24
ListenPort = 51820
PrivateKey = <SERVER_PRIVATE_KEY>

[Peer]
# client-a
PublicKey = <CLIENT_A_PUBLIC_KEY>
AllowedIPs = 10.77.0.2/32

[Peer]
# client-b
PublicKey = <CLIENT_B_PUBLIC_KEY>
AllowedIPs = 10.77.0.3/32

config client A؛ برای B از `10.77.0.3/32` و private key خودش استفاده کن:

Client A configuration; for B use `10.77.0.3/32` and its own private key:

[Interface]
Address = 10.77.0.2/32
PrivateKey = <CLIENT_A_PRIVATE_KEY>

[Peer]
PublicKey = <SERVER_PUBLIC_KEY>
Endpoint = 192.168.77.10:51820
AllowedIPs = 10.77.0.0/24

در این host-only lab، `PersistentKeepalive` نیاز نیست. اگر client پشت NAT واقعی باشد، آن را بر اساس topology جدا ارزیابی کن. پیش از بالا آوردن server config را محدود کن و forwarding را در VM روشن کن:

This host-only lab does not need `PersistentKeepalive`; assess it separately for a real NATed client. Restrict the server config before startup and enable forwarding inside the VM:

sudo chmod 600 /etc/wireguard/wg0.conf
sudo sysctl -w net.ipv4.ip_forward=1
sudo nft add table inet wg_lab
sudo nft 'add chain inet wg_lab forward { type filter hook forward priority 0; policy drop; }'
sudo nft add rule inet wg_lab forward iifname "wg0" oifname "wg0" ip saddr 10.77.0.0/24 ip daddr 10.77.0.0/24 accept

این rule نمونه فقط برای VM خالی و disposable است. اگر firewall manager فعالی داری، reset نکن؛ ruleset را بخوان و rule معادل را همان‌جا بساز. NAT عمداً نیست؛ فقط subnet tunnel route می‌شود.

This sample rule is for an empty disposable VM only. If a firewall manager is active, do not reset it; inspect the ruleset and add the equivalent rule through that manager. There is intentionally no NAT; only the tunnel subnet is routed.

server را بالا بیاور و بعد clientها را. برای تازه‌شدن handshake ping بفرست؛ روی server `wg show`, `ip route get` و counterها را بخوان. برای DNS، dnsmasq را فقط روی `10.77.0.1` bind کن و رکورد `status.wg-lab.test` را به `10.77.0.1` بده؛ از client با `dig @10.77.0.1 status.wg-lab.test` بپرس. DNS مستقیم هنوز resolver پیش‌فرض را عوض نمی‌کند.

Start the server, then clients. Generate ping traffic and inspect `wg show`, `ip route get`, and counters on the server. Bind dnsmasq only to `10.77.0.1` with `status.wg-lab.test` resolving to `10.77.0.1`; query it from a client using `dig @10.77.0.1 status.wg-lab.test`. Direct DNS queries do not change the system resolver.

در server VM، `sudo systemctl enable --now wg-quick@wg0` را اجرا و سپس `sudo systemctl restart wg-quick@wg0` را آزمایش کن. بعد از restart، traffic تازه بفرست و handshake، HTTP و DNS را دوباره ببین. اگر unit name در distro متفاوت بود، `systemctl list-unit-files '*wg-quick*'` را بخوان.

In the server VM, run `sudo systemctl enable --now wg-quick@wg0`, then test `sudo systemctl restart wg-quick@wg0`. After restart, generate fresh traffic and recheck handshake, HTTP, and DNS. If the unit name differs on your distro, inspect `systemctl list-unit-files '*wg-quick*'`.

تحویل: چه چیزی را ثابت کردی و چه چیزی را نه؟Handoff: what did you prove—and what did you not?

ثابت کردی دو هویت مستقل از underlay خصوصی به server می‌رسند؛ AllowedIPs آن‌ها را جدا می‌کند؛ kernel با forwarding و firewall محدود مسیر peer-to-peer را عبور می‌دهد؛ DNS و سرویس tunnel پاسخ می‌دهند؛ و systemd interface را پس از restart بالا می‌آورد. ثابت نکردی این طرح برای اینترنت عمومی آماده است، keyها خودکار rotate می‌شوند یا full tunnel امنی ساخته‌ای.

You proved two independent identities can reach the server over private underlay; AllowedIPs distinguish them; the kernel forwards peer traffic under a constrained firewall; DNS and a tunnel service respond; and systemd restores the interface after restart. You did not prove internet readiness, automatic key rotation, or a secure full tunnel.

پروژهٔ بعدی route و proxy را کنار هم می‌گذارد تا gateway بسازی. همان‌جا هم NAT را پیش‌فرض نکن: اول مقصد، مسیر برگشت، firewall و DNS را مشخص کن؛ بعد با شاهد نشان بده هر packet کجا می‌رود.

The next project combines routes and a proxy into a gateway. Do not make NAT the default there either: define destination, return route, firewall, and DNS first, then prove where packets go.

ضمیمهٔ کوتاه: DNS آزمایشگاه را واقعاً اجرا کنSmall appendix: actually run lab DNS

روی server در `/etc/dnsmasq.d/wg-lab.conf` این تنظیم را بساز و فقط در VM آزمایشگاهی restart کن:

On the server, create this file at `/etc/dnsmasq.d/wg-lab.conf` and restart only the lab VM service:

interface=wg0
listen-address=10.77.0.1
bind-interfaces
no-resolv
address=/status.wg-lab.test/10.77.0.1

server باید HTTP origin را هم با `python3 -m http.server 8080 --bind 10.77.0.1` بالا بیاورد. سپس `sudo systemctl restart dnsmasq` و `ss -lunp` را بخوان؛ listener روی `10.77.0.1:53` باشد، نه همهٔ interfaceها. از client ابتدا `dig @10.77.0.1 status.wg-lab.test` را بزن؛ بعد روی Ubuntu/systemd-resolved، `sudo resolvectl dns wg0 10.77.0.1` و `sudo resolvectl domain wg0 '~wg-lab.test'` را اجرا کن، `resolvectl query status.wg-lab.test` و `curl http://status.wg-lab.test:8080/` را بیازما و در پایان `sudo resolvectl revert wg0` اجرا کن.

On the server, also run the HTTP origin with `python3 -m http.server 8080 --bind 10.77.0.1`. Restart `dnsmasq` and inspect `ss -lunp`; the listener should be `10.77.0.1:53`, not every interface. From a client, first run `dig @10.77.0.1 status.wg-lab.test`. Then, on Ubuntu with systemd-resolved, run `sudo resolvectl dns wg0 10.77.0.1` and `sudo resolvectl domain wg0 '~wg-lab.test'`; test `resolvectl query status.wg-lab.test` and `curl http://status.wg-lab.test:8080/`, then undo the per-link settings with `sudo resolvectl revert wg0`.

اگر مستقیم `dig` موفق است ولی `resolvectl query` نه، dnsmasq و مسیر شبکه از client سالم‌اند؛ مشکل در resolver integration یا link domain است. دستورهای `resolvectl` مخصوص systemd-resolved هستند؛ در distro دیگر resolver همان سیستم را بررسی کن، نه اینکه خروجی Ubuntu را فرض بگیری.

If direct `dig` succeeds but `resolvectl query` fails, dnsmasq and the client’s network path work; resolver integration or the link domain is the remaining boundary. `resolvectl` is specific to systemd-resolved; on another distro, inspect its resolver instead of assuming Ubuntu behavior.
