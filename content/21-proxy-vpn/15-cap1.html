ماموریت: یک درخواست HTTP را از مسیر دیگری عبور بدهMission: route one HTTP request through another process

تا اینجا proxy آماده را اجرا کردی و در فصل ۴ یک نمونهٔ کوچک CONNECT دیدی. این بار یک HTTP forward proxy می‌سازی که درخواست سادهٔ HTTP را بگیرد، مقصد را بررسی کند، به origin محلی وصل شود و پاسخ را برگرداند. هدف نوشتن «proxy برای کل اینترنت» نیست؛ هدف این است که مسیر را خط‌به‌خط بفهمی و ثابت کنی برنامه‌ات به proxy باز تبدیل نشده.

You have used an existing proxy and built a small CONNECT example in Chapter 4. Now build an HTTP forward proxy that accepts a simple HTTP request, checks its destination, connects to a local origin, and returns the response. The goal is not an internet-wide proxy; it is to understand each step and prove the program did not become an open proxy.

محدوده را عمداً کوچک نگه می‌داریم: Python 3 استاندارد، فقط `GET` و `HEAD`، فقط origin آزمایشگاهی `127.0.0.1:9000`، بدون body، و listener روی `127.0.0.1:8888`. `CONNECT` و ترافیک HTTPS را این پروژه پیاده نمی‌کند؛ رفتار tunnel را از فصل ۴ می‌شناسی و اضافه‌کردنش دامنه را بزرگ‌تر می‌کند. این نمونه production-ready نیست.

Keep the scope intentionally small: standard-library Python 3, `GET` and `HEAD` only, one lab origin at `127.0.0.1:9000`, no request body, and a listener on `127.0.0.1:8888`. This project does not implement `CONNECT` or HTTPS tunneling; you saw tunnel behavior in Chapter 4, and adding it would expand the scope. This is not production-ready software.

فلش بالا درخواست را به جلو می‌برد؛ فلش پایین پاسخ را برمی‌گرداند. تنها مقصد مجاز همین origin محلی است.

Upper arrows carry the request forward; lower arrows return the response. The only allowed destination is this local origin.

اول origin را بدون proxy بالا بیاورStart the origin without a proxy

اگر از همان ابتدا proxy را وسط بگذاری، وقتی صفحه باز نشود معلوم نیست مشکل از سرور محتواست یا از مسیر تازه. یک پوشهٔ خالی بساز و فایل `index.html` ساده‌ای با متن `hello from origin` داخلش بگذار. سپس سرور موقت Python را فقط روی loopback اجرا کن:

If the proxy is in the path from the start, a missing page could be the origin or the new routing layer. Create a scratch directory with a simple `index.html` containing `hello from origin`, then run Python’s temporary server on loopback only:

python3 -m http.server 9000 --bind 127.0.0.1

در terminal دوم مستقیم درخواست بزن: curl -i http://127.0.0.1:9000/. دنبال status موفق و متن فایل بگرد. این ثابت می‌کند origin زنده است؛ proxy، ACL و concurrency را هنوز نیازموده‌ایم. ویندوز می‌تواند از `py -3 -m http.server ...` استفاده کند.

From a second terminal, request the origin directly with `curl -i http://127.0.0.1:9000/`. Look for a successful status and the file’s text. This proves the origin is alive; it says nothing yet about the proxy, ACL, or concurrency. On Windows, use `py -3 -m http.server ...` if needed.

۱. مرزها را روی کاغذ ببند

پیش از کدنویسی، سه مقدار را ثابت کن: listener، origin مجاز و متدهای پشتیبانی‌شده. در یادداشت پروژه بنویس چه چیزی عمداً پشتیبانی نمی‌شود. خروجی این مرحله باید config کوچکی باشد که هیچ مقصد دلخواهی در آن جا نمی‌گیرد.

Before coding, fix three values: the listener, the permitted origin, and supported methods. Record what is intentionally unsupported. The output is a small configuration that cannot represent an arbitrary destination.

راهنمایی

مثل reference solution از آدرس loopback و یک port ثابت شروع کن. hostname ورودی client را مستقیماً برای اتصال استفاده نکن.

Start with loopback and one fixed port as in the reference solution. Do not connect directly to a hostname supplied by the client.

معیار تحویل

listener=`127.0.0.1:8888`؛ origin=`127.0.0.1:9000`؛ فقط `GET/HEAD`؛ نه body، نه HTTPS، نه مقصد اینترنتی.

Listener `127.0.0.1:8888`; origin `127.0.0.1:9000`; `GET/HEAD` only; no request body, HTTPS, or internet destination.

۲. درخواست را بخوان و مقصد را رد یا قبول کن

درخواست proxy معمولاً URL کامل دارد. خط اول و headerها را بخوان، اندازهٔ header را سقف بگذار، scheme/host/port را با allowlist مقایسه کن و متد یا body خارج از محدوده را رد کن. پیش از هر اتصال upstream، ثابت کن درخواست ممنوع اصلاً به شبکه نمی‌رسد.

A proxy request usually carries an absolute URL. Read the request line and headers, cap header size, compare scheme/host/port to an allowlist, and reject out-of-scope methods or bodies. Prove a forbidden request is rejected before any upstream connection.

راهنمایی

`urllib.parse.urlsplit` URL را تجزیه می‌کند، اما خودش policy امنیتی نیست. allowlist را جدا و دقیق پیاده کن و خطاهای parse را هم رد کن.

`urllib.parse.urlsplit` parses a URL but is not itself a security policy. Implement a separate exact allowlist and reject parse errors.

معیار تحویل

URL غیر HTTP، host یا port متفاوت، method نامجاز، header ناقص و header بیش‌ازحد بزرگ باید پیش از اتصال رد شوند؛ برای مقصد بیرون allowlist پاسخ 403 قابل‌مشاهده ثبت کن.

Reject non-HTTP URLs, a different host or port, unsupported methods, malformed headers, and oversized headers before connecting; show a 403 for a destination outside the allowlist.

۳. به origin وصل شو و پاسخ را برگردان

URL تأییدشده را به origin-form تبدیل کن: مثلاً `/guide?lang=fa`، نه URL کامل proxy. headerهای مخصوص proxy را forward نکن، `Host` درست بفرست و ارتباط را برای این تمرین با `Connection: close` تمام کن. ابتدا یک درخواست `GET` را از انتها تا انتها ثابت کن.

Convert the validated URL to origin-form—for example `/guide?lang=fa`, not the proxy’s absolute URL. Do not forward proxy-specific headers; send the correct `Host` and close the connection for this exercise. First prove one `GET` end to end.

راهنمایی

برای نمونهٔ کوچک، پاسخ origin را تا EOF کپی کن و از origin هم `Connection: close` بخواه. این روش keep-alive را پیاده نمی‌کند؛ محدودیتش را در README بنویس.

For this small implementation, copy the origin response until EOF and ask the origin to close. This does not implement keep-alive; document the limitation.

معیار تحویل

`curl --noproxy "" -i -x http://127.0.0.1:8888 http://127.0.0.1:9000/` همان status و محتوای origin را برگرداند. `--noproxy ""` جلوی دورزدن proxy به‌خاطر تنظیمات محیطی curl را می‌گیرد.

The request returns the origin’s status and body. `--noproxy ""` prevents curl environment settings from bypassing the proxy.

۴. خرابی را بساز: مقصد ممنوع و upstream کند

درخواست به `127.0.0.1:9001` باید پیش از اتصال رد شود. حالا origin مجاز را با handler آزمایشی جایگزین کن که هشت ثانیه صبر می‌کند؛ proxy باید پس از timeout محدود پاسخ خطا بدهد، نه اینکه یک thread را برای همیشه نگه دارد. ثبت کن کدام خطای proxy از کدام boundary آمده است.

A request to `127.0.0.1:9001` must be rejected before connecting. Replace the permitted origin with a lab handler that sleeps for eight seconds; the proxy should return an error after a bounded timeout, not hold a thread forever. Record which boundary produced each error.

راهنمایی

برای timeout، socket upstream را هنگام connect و read محدود کن؛ در مسیر عمومی timeout کوتاه را طوری انتخاب نکن که پاسخ عادی قطع شود. درخواست ممنوع باید 403 و timeout باید 504 باشد.

Bound upstream connect and read time. Do not choose a production timeout so short that normal responses are cut off. A forbidden target should get 403; a timeout should get 504.

معیار تحویل

یک client خارج از allowlist بدون تماس با مقصد، 403 می‌گیرد؛ origin کند در بازهٔ محدود 504 می‌دهد؛ log فقط peer و نتیجهٔ کلی را دارد و query، authorization یا body را چاپ نمی‌کند.

An out-of-allowlist request gets 403 without contacting its destination; a slow origin yields 504 within a bounded time; logs contain only peer and high-level result, not query, authorization, or body.

۵. هم‌زمانی، خاموش‌شدن و handoff

چند درخواست هم‌زمان بفرست و مطمئن شو server threaded است؛ سپس با Ctrl+C خاموشش کن و listener باقی‌مانده را بررسی کن. در handoff تعداد خط‌ها، متدهای پشتیبانی‌شده، محدودیت‌ها، نمونهٔ خروجی، و دستورهای بازتولید دو failure را ثبت کن. هدف کمتر از ۲۰۰ خط کد proxy است، نه کمتر از ۲۰۰ خط توضیح و تست.

Send concurrent requests and verify the server is threaded; stop it with Ctrl+C and check no listener remains. In the handoff, record line count, supported methods, limits, sample output, and commands to reproduce both failures. The proxy code should be under 200 lines—not the documentation and tests.

راهنمایی

در Bash می‌توانی چند `curl` را با `&` اجرا و با `wait` جمع کنی؛ PowerShell از `Start-Job` یا چند window استفاده کند. تست را روی loopback نگه دار.

In Bash, launch several `curl` processes with `&` and join them with `wait`; PowerShell can use `Start-Job` or separate windows. Keep the test on loopback.

معیار تحویل

همهٔ درخواست‌های هم‌زمان status و body درست بگیرند؛ پس از shutdown، `ss -lntp` دیگر port 8888 را نشان ندهد. این هنوز پایداری در برابر load یا امنیت production را ثابت نمی‌کند.

All concurrent requests receive the expected status and body; after shutdown, `ss -lntp` no longer shows port 8888. This still does not prove production security or load resilience.

پذیرش پروژه یعنی مدرک، نه فقط «صفحه باز شد»Acceptance means evidence, not merely “the page loaded”

به reviewer این شواهد را بده: درخواست مستقیم origin و همان درخواست از proxy؛ درخواست ممنوع با 403؛ origin کند با 504 زمان‌دار؛ چند درخواست هم‌زمان با پاسخ درست؛ log بدون secret؛ و اثبات اینکه listener فقط loopback است و پس از shutdown بسته شده. یک بار هم proxy را از محیط تمیز اجرا کن تا به متغیرهای محیطی یا shell قبلی وابسته نباشد.

Give the reviewer these proofs: direct origin and proxied requests; a forbidden destination returning 403; a slow origin returning a bounded 504; concurrent requests with correct responses; logs without secrets; and proof the listener is loopback-only and closes after shutdown. Run it once from a clean environment so it does not depend on stale shell state.

ss -lntp
curl -i http://127.0.0.1:9000/
curl --noproxy "" -i -x http://127.0.0.1:8888 http://127.0.0.1:9000/
curl --noproxy "" -i -x http://127.0.0.1:8888 http://127.0.0.1:9001/

خروجی متغیر است؛ مهم این است که listener روی `127.0.0.1:8888` باشد، درخواست proxy موفق شود و مقصد دیگر 403 بگیرد. وجود port در `ss` سلامت origin را ثابت نمی‌کند؛ status و body را جدا بخوان. برای توقف proxy و origin هر دو process را ببند.

Output varies; the important evidence is a listener at `127.0.0.1:8888`, a successful proxied request, and a 403 for the other destination. A port in `ss` does not prove origin health; inspect status and body separately. Stop both proxy and origin processes.

راه‌حل مرجع — فقط بعد از تلاش خودتReference implementation—after your own attempt

این کد عمدی محدود است: GET/HEAD، یک IP و port ثابت، یک درخواست در هر اتصال و بدون body یا CONNECT. مقصد را از ورودی آزاد client انتخاب نمی‌کند؛ همین محدودیت ساده مانع بخش بزرگی از خطر open proxy و SSRF در این آزمایش می‌شود. یک پیاده‌سازی عمومی به parsing کامل HTTP، مدیریت hop-by-hop headers، IPv6، سیاست DNS، احراز هویت و آزمون امنیتی جدی‌تری نیاز دارد.

This implementation is intentionally narrow: GET/HEAD, one fixed IP and port, one request per connection, and no body or CONNECT. It never lets the client choose an arbitrary destination; this simple boundary avoids much of the open-proxy and SSRF risk in this exercise. A general implementation needs complete HTTP parsing, hop-by-hop header handling, IPv6, DNS policy, authentication, and substantially more security testing.

کد کامل proxy (حدود ۷۰ خط)
import socket
import socketserver
from urllib.parse import urlsplit

LISTEN = ("127.0.0.1", 8888)
ORIGIN = ("127.0.0.1", 9000)
HEADER_LIMIT = 16_384
TIMEOUT = 5

def read_headers(sock):
    data = bytearray()
    while b"\r\n\r\n" not in data:
        block = sock.recv(2048)
        if not block:
            raise ValueError("incomplete headers")
        data.extend(block)
        if len(data) > HEADER_LIMIT:
            raise ValueError("headers too large")
    head, extra = bytes(data).split(b"\r\n\r\n", 1)
    if len(head) > HEADER_LIMIT:
        raise ValueError("headers too large")
    return head, extra

def respond(client, status, reason):
    body = (reason + "\n").encode()
    client.sendall((f"HTTP/1.1 {status} {reason}\r\n"
                    f"Content-Length: {len(body)}\r\n"
                    "Connection: close\r\n\r\n").encode() + body)

class Handler(socketserver.BaseRequestHandler):
    def handle(self):
        client = self.request
        client.settimeout(TIMEOUT)
        upstream = None
        response_started = False
        method, host = "?", "127.0.0.1"
        try:
            raw, extra = read_headers(client)
            rows = raw.decode("iso-8859-1").split("\r\n")
            request_line = rows[0].split()
            if len(request_line) != 3:
                respond(client, 400, "Bad Request")
                return
            method, target, _version = request_line
            if method not in ("GET", "HEAD") or extra:
                respond(client, 400, "Bad Request")
                return
            try:
                parsed = urlsplit(target)
                port = parsed.port
            except ValueError:
                respond(client, 400, "Bad Request")
                return
            host = parsed.hostname or ""
            if (parsed.scheme != "http" or host != ORIGIN[0]
                    or port != ORIGIN[1] or parsed.username
                    or parsed.password or parsed.fragment):
                respond(client, 403, "Forbidden")
                return
            forwarded = []
            for row in rows[1:]:
                if not row:
                    continue
                name, sep, value = row.partition(":")
                if not sep:
                    respond(client, 400, "Bad Request")
                    return
                key = name.lower()
                if key in ("content-length", "transfer-encoding"):
                    if key == "transfer-encoding" or value.strip() != "0":
                        respond(client, 400, "Request Body Not Supported")
                        return
                if key in ("host", "connection", "proxy-connection",
                           "proxy-authorization", "keep-alive"):
                    continue
                forwarded.append(f"{name}: {value.strip()}")
            path = parsed.path or "/"
            if parsed.query:
                path += "?" + parsed.query
            request = [f"{method} {path} HTTP/1.1",
                       f"Host: {ORIGIN[0]}:{ORIGIN[1]}",
                       "Connection: close", *forwarded, "", ""]
            upstream = socket.create_connection(ORIGIN, timeout=TIMEOUT)
            upstream.settimeout(TIMEOUT)
            upstream.sendall("\r\n".join(request).encode("iso-8859-1"))
            while True:
                block = upstream.recv(16_384)
                if not block:
                    break
                response_started = True
                client.sendall(block)
            print(f"peer={self.client_address[0]} method={method} "
                  f"host={host} result=complete", flush=True)
        except TimeoutError:
            if not response_started:
                try:
                    respond(client, 504, "Gateway Timeout")
                except OSError:
                    pass
            print(f"peer={self.client_address[0]} method={method} result=timeout",
                  flush=True)
        except (OSError, ValueError, UnicodeError) as error:
            if not response_started:
                try:
                    respond(client, 502, "Bad Gateway")
                except OSError:
                    pass
            print(f"peer={self.client_address[0]} method={method} "
                  f"error={type(error).__name__}", flush=True)
        finally:
            if upstream is not None:
                upstream.close()

class ThreadedServer(socketserver.ThreadingTCPServer):
    allow_reuse_address = True
    daemon_threads = True

with ThreadedServer(LISTEN, Handler) as server:
    print(f"listening on {LISTEN[0]}:{LISTEN[1]}", flush=True)
    server.serve_forever()

قبل از اجرا کد را خودت بخوان: شرط مقصد پیش از `create_connection` اجرا می‌شود؛ پس request ممنوع socket upstream نمی‌سازد. هر connection در thread جداست، ولی timeout پنج‌ثانیه‌ای فقط برای آزمایش انتخاب شده و برای سرویس واقعی باید بر اساس رفتار برنامه سنجیده شود. پس از دریافت نخستین byte پاسخ، دیگر نمی‌توان status تازه‌ای روی همان stream فرستاد؛ به همین دلیل خطاهای دیرهنگام فقط در log ثبت می‌شوند.

Read the code before running it: destination validation happens before `create_connection`, so a forbidden request never opens an upstream socket. Each connection runs in a thread, but the five-second timeout is a lab choice that must be measured for a real service. Once response bytes have been sent, a new status cannot be inserted into that stream; late errors are therefore logged only.

در نسخهٔ مرجع، یک نکتهٔ آموزشی هم باقی است: حذف headerهای hop-by-hop فقط برای مجموعهٔ کوچک و single-request این تمرین کافی است؛ در HTTP عمومی، `Connection` می‌تواند نام headerهای دیگری را هم اعلام کند که باید حذف شوند. تست parser با درخواست‌های بدساخت و سیاست مقصد قبل از انتشار لازم است.

One deliberate teaching limitation remains: the hop-by-hop header removal is only adequate for this small single-request exercise. General HTTP allows `Connection` to nominate additional headers that must also be removed. A real proxy needs stronger parser tests and destination policy before deployment.

گزارش کوتاه مهندسیA short engineering handoff

تحویل تو باید جواب دهد: proxy کجا گوش می‌دهد؟ چه مقصدی مجاز است؟ timeout کجای اتصال اعمال می‌شود؟ کدام headerها حذف می‌شوند؟ چه چیزی در log نمی‌آید؟ و کدام آزمایش نشان داد درخواست ممنوع پیش از اتصال رد می‌شود؟ کد را با `python3 -m py_compile proxy.py` بررسی کن؛ بعد از shutdown هم listener را دوباره ببین. این دو check syntax و پایان فرایند را نشان می‌دهند، نه کامل‌بودن پروتکل یا امنیت عمومی.

Your handoff should answer: where does the proxy listen, which destination is allowed, where is the timeout applied, which headers are removed, what is intentionally absent from logs, and which test proved rejection before connecting? Run `python3 -m py_compile proxy.py`, then verify the listener is gone after shutdown. These checks establish syntax and process cleanup—not protocol completeness or general security.

پروژهٔ بعدی دیگر یک request محلی نیست؛ یک سرور WireGuard می‌سازیم که چند peer، route و چرخهٔ عمر کلید دارد. همان مرزبندی این پروژه را آنجا هم نگه می‌داریم: فقط هویت‌ها و مقصدهایی که واقعاً لازم‌اند.

The next project is no longer one local request: we will build a WireGuard server with peers, routes, and key lifecycle. Carry the same boundary discipline forward—only the identities and destinations actually needed.
