HTTP proxy و متد CONNECT

HTTP proxies and the CONNECT method

چطور یک درخواست از پروکسی رد می‌شود.

How a request passes through a proxy.

۸۰دقیقهminutes
۱۸تمرینexercises

یک درخواست، اما کدام قالب روی سیم؟One request, but which form goes on the wire?

در فصل قبل گفتیم client می‌تواند forward proxy را انتخاب کند. حالا curl را طوری تنظیم می‌کنی که به proxy وصل شود و بعد یک URL را می‌خواهد. proxy چطور می‌فهمد مقصد کجاست؟ برای HTTP معمولی، مقصد در request-target خودش می‌آید. برای HTTPS، client اول یک تونل TCP می‌خواهد؛ بعد TLS را داخل آن شروع می‌کند.

Last chapter showed that a client can select a forward proxy. Now curl connects to a proxy and asks for a URL. How does the proxy know the destination? For ordinary HTTP, the destination appears in the request target. For HTTPS, the client first asks for a TCP tunnel, then starts TLS inside it.

مرز مهم همین است: CONNECT معمولاً TLS را رمزگشایی نمی‌کند؛ فقط می‌خواهد جریان بایت‌ها تا host:port مشخص عبور کند. تا وقتی proxy عمداً TLS را با گواهی مورداعتماد client terminate نکرده باشد—که در این دوره نمی‌سازیم—TLS میان client و origin باقی می‌ماند.

That boundary matters: CONNECT normally does not decrypt TLS. It asks the proxy to relay a byte stream to a host and port. Unless a proxy deliberately terminates TLS with a certificate trusted by the client—which we will not build here—TLS remains between client and origin.

HTTP ساده: مقصد در request-targetPlain HTTP: the destination is in the request target

بدون proxy، client معمولاً فقط path را می‌فرستد: /docs. وقتی به forward proxy صریح وصل می‌شود، درخواست HTTP معمولاً URI کامل absolute-form را می‌فرستد تا proxy بداند کدام host را درخواست کند. شکل دقیق نسخه/پیاده‌سازی ممکن است جزئیات دیگری داشته باشد، اما host و scheme در درخواست آشکارند.

Without a proxy, a client usually sends only the path, such as /docs. With an explicit forward proxy, an HTTP request commonly uses the full absolute-form URI so the proxy can identify the requested host. Wire details can vary by HTTP version and implementation, but the scheme and host are visible in the request.

proxy درخواست را دریافت می‌کند و به origin می‌فرستد؛ payload HTTP رمز نیست.

The proxy receives and forwards the request; plain HTTP payload is not encrypted.

GET http://example.com/docs HTTP/1.1
Host: example.com
User-Agent: curl/…
Accept: */*

این شکل یک نمونهٔ آموزشی است، نه خروجی دقیق همهٔ نسخه‌های curl. برای دیدن رفتار واقعی، در محیط مجاز Squid محلی را روی loopback اجرا کن. پیش از اجرا مطمئن شو Docker داری و پورت 3128 آزاد است. image نسخه‌دار را از رجیستری رسمی/معتبر بررسی کن؛ tag نمونه باید با tag موجود جایگزین شود:

This is an illustrative request, not byte-for-byte output from every curl version. To observe a real exchange, run local Squid bound only to loopback. Confirm Docker is available and port 3128 is free first. Verify a versioned image tag from a trusted registry; replace the sample tag if needed:

docker run --rm --name proxy-lab -p 127.0.0.1:3128:3128 ubuntu/squid:6

در ترمینال دیگر درخواست HTTP بی‌حساسیت بفرست: curl -v --noproxy "" --proxy http://127.0.0.1:3128 http://example.com/. در trace دنبال اتصال به 127.0.0.1:3128، درخواست proxy و پاسخ بگرد. گزینهٔ --noproxy "" مانع bypass شدن به‌خاطر NO_PROXY می‌شود. اگر Squid دسترسی را رد کرد، log و ACL image را بخوان؛ ACLهای image ممکن است فرق کنند. این آزمایش فقط ثابت می‌کند درخواست از proxy محلی گذشت، نه اینکه خودت آن را در production امن کرده‌ای.

In another terminal, send a harmless HTTP request: curl -v --noproxy "" --proxy http://127.0.0.1:3128 http://example.com/. Look for the connection to 127.0.0.1:3128, the proxy request, and the response. --noproxy "" prevents NO_PROXY from bypassing the proxy. If Squid denies access, inspect its logs and image ACLs; defaults vary. This proves a request passed through a local proxy, not that you have a production-secure proxy.

HTTPS: اول CONNECT، بعد TLSHTTPS: CONNECT first, then TLS

برای URL از نوع https، curl به proxy می‌گوید: «یک اتصال به example.com:443 برایم باز کن.» در HTTP/1.1 این درخواست معمولاً چنین است. این قالب authority-form است؛ path صفحه در آن نیست.

For an HTTPS URL, curl asks the proxy to open a connection to example.com:443. In HTTP/1.1 the request commonly looks like this. This is authority-form; it does not include the page path.

CONNECT example.com:443 HTTP/1.1
Host: example.com:443
Proxy-Connection: Keep-Alive

اگر مجاز بود، proxy یک پاسخ موفق 2xx می‌دهد؛ خیلی از proxyها متن توضیحی 200 Connection established را نشان می‌دهند، ولی عبارت بدنه/دلیل‌نامه به پیاده‌سازی وابسته است. بعد از پاسخ، socket همان اتصال به تونل بایت‌ها تبدیل می‌شود: client TLS ClientHello می‌فرستد و handshake با origin پیش می‌رود.

If allowed, the proxy returns a successful 2xx response. Many proxies display a reason phrase like 200 Connection established, but the wording is implementation-specific. After the response, the socket becomes a byte tunnel: the client sends a TLS ClientHello and the handshake proceeds with the origin.

پاسخ 2xx تونل را باز می‌کند؛ TLS داخل tunnel به origin ختم می‌شود، نه proxy.

A 2xx opens the tunnel; TLS inside it terminates at the origin, not the proxy.

این بار همان Squid محلی را با HTTPS امتحان کن: curl -v --noproxy "" --proxy http://127.0.0.1:3128 https://example.com/. trace باید CONNECT و سپس handshake گواهی TLS را نشان بدهد. عبارت‌های دقیق و ترتیب جزئیات با نسخه curl/proxy فرق می‌کند. گواهی‌ای که curl بررسی می‌کند باید متعلق به origin و قابل‌اعتماد باشد. این خروجی نشان می‌دهد tunnel و TLS ساخته شد؛ محتوای رمز را به proxy نسبت نده.

Try HTTPS through the same local Squid: curl -v --noproxy "" --proxy http://127.0.0.1:3128 https://example.com/. The trace should show CONNECT followed by a TLS certificate handshake. Exact wording and detail order vary by curl/proxy version. curl should validate a trusted certificate for the origin. This shows a tunnel and TLS session were established; it does not mean the proxy can read encrypted content.

proxy مقصد، port، زمان اتصال، اندازه و الگوی ترافیک را می‌تواند ببیند. در TLS 1.3 بخشی از metadata handshake هم رمز می‌شود؛ اینکه دقیقاً چه metadata قابل مشاهده است به DNS، نسخهٔ TLS، ECH و شبکه بستگی دارد. از یک trace ساده ادعای «هیچ اطلاعاتی دیده نمی‌شود» نساز.

The proxy can observe destination, port, timing, traffic size, and patterns. With TLS 1.3, some handshake metadata is encrypted too; exact visibility depends on DNS, TLS version, ECH, and network setup. Do not turn one simple trace into a claim that “nothing is visible.”

خرابی عمدی: انگار HTTPS را مستقیم به proxy داده‌ایمDeliberate failure: pretend HTTPS goes straight to the proxy

یک proxy HTTP منتظر پیام HTTP است. اگر client به‌جای CONNECT، TLS ClientHello را مستقیم به همان پورت بفرستد، proxy نمی‌تواند آن را مثل درخواست HTTP تفسیر کند. برعکسش هم خطاست: بعد از CONNECT موفق، دوباره یک خط درخواست HTTP داخل tunnel نفرست مگر پروتکل مقصد آن را می‌خواهد؛ آنجا باید TLS handshake آغاز شود.

An HTTP proxy expects HTTP messages. If a client sends a TLS ClientHello directly to that port instead of CONNECT, the proxy cannot parse it as an HTTP request. The reverse mistake is also wrong: after a successful CONNECT, do not send another HTTP request line inside the tunnel unless the destination protocol expects it; TLS should begin there.

نشانه‌ها می‌تواند reset، پاسخ malformed، خطای TLS یا پیام syntax در log proxy باشد؛ دقیقاً یک خروجی واحد نداریم. اول curl -v را نگاه کن: آیا CONNECT فرستاده شد؟ آیا پاسخ 2xx آمد؟ آیا TLS با host درست شروع شد؟ بعد log proxy و port را بررسی کن. تشخیص را از مرحله‌ای که شکست خورده شروع کن، نه از حدس «گواهی خراب است».

Symptoms can include a reset, malformed response, TLS error, or proxy syntax log; there is no single guaranteed message. Start with curl -v: was CONNECT sent? Did a 2xx arrive? Did TLS start for the intended host? Then inspect proxy logs and port. Diagnose the failed stage rather than guessing that the certificate is bad.

احراز هویت proxy با احراز هویت سایت یکی نیستProxy authentication is not origin authentication

proxy سازمانی ممکن است پاسخ 407 Proxy Authentication Required بدهد؛ client باید credential proxy را با روش پشتیبانی‌شده بفرستد، و proxy معمولاً Proxy-Authenticate می‌دهد. این با 401 و WWW-Authenticate از origin فرق دارد. هدر Proxy-Authorization برای hop proxy است؛ نباید با Authorization مقصد قاطی شود یا به origin forward شود.

An enterprise proxy may return 407 Proxy Authentication Required and a Proxy-Authenticate challenge. That differs from an origin’s 401 and WWW-Authenticate. Proxy-Authorization is for the proxy hop; it must not be confused with origin Authorization or forwarded to the origin.

برای curl می‌توان از --proxy-user USER استفاده کرد، اما credential را داخل تاریخچهٔ shell، log یا screenshot نگذار. روش Basic روی HTTP معمولی credential را محرمانه نمی‌کند؛ فقط وقتی transport امن و policy روشن است از آن استفاده کن. در آزمایش این فصل auth proxy را روشن نمی‌کنیم تا راز ساختگی هم لازم نشود.

curl supports --proxy-user USER, but never place credentials in shell history, logs, or screenshots. Basic authentication over plain HTTP does not protect credentials; use it only with a secure transport and explicit policy. This chapter’s lab does not enable proxy auth, so no fake secret is needed.

آزمایش: دو نوع URL، دو مکالمهLab: two URL types, two exchanges

پروکسی آزمایش را فقط روی loopback منتشر کن. اگر Docker نداری یا image/tag در دسترس نیست، مرحله را رد کن و یک proxy مجاز محلی انتخاب کن؛ port را عمومی نکن. Container را در ترمینال قابل‌کنترل نگه دار تا با Ctrl+C متوقف شود:

Publish the lab proxy only on loopback. If Docker or the image tag is unavailable, skip this step and use an authorized local proxy; do not publish the port publicly. Keep the container attached so it can be stopped with Ctrl+C:

docker run --rm --name proxy-lab -p 127.0.0.1:3128:3128 ubuntu/squid:6

در ترمینال دوم برای HTTP ساده trace بگیر. دنبال URI کامل و پاسخ origin بگرد:

In a second terminal, capture a trace for plain HTTP. Look for the full URI and origin response:

curl -v --noproxy "" --proxy http://127.0.0.1:3128 http://example.com/

برای HTTPS همان proxy را نگه دار و فقط scheme مقصد را عوض کن. دنبال CONNECT، پاسخ موفق، TLS certificate و درخواست encrypted بگرد. ممکن است curl-version یا proxy policy، CONNECT را رد کند؛ این شکست را ثبت و از log دلیل مجاز را بخوان.

Keep the same proxy and change only the destination scheme to HTTPS. Look for CONNECT, a successful response, TLS certificate details, and the encrypted request. curl version or proxy policy may reject CONNECT; record that result and inspect logs for the permitted reason.

curl -v --noproxy "" --proxy http://127.0.0.1:3128 https://example.com/

حالا یک بار به پورت proxy اشتباه وصل شو و یک بار proxy container را متوقف کن. هر دو می‌توانند اتصال را ناکام کنند، ولی اولی نشانی/listener و دومی چرخهٔ عمر سرویس را مطرح می‌کند. trace client و docker logs را کنار هم بخوان؛ بعد proxy را متوقف کن تا چیزی بی‌دلیل باز نماند.

Now connect once to the wrong proxy port and once after stopping the proxy container. Both can fail, but the first points toward address/listener and the second toward service lifecycle. Compare client trace with container logs, then stop the proxy so nothing remains running unnecessarily.

۶. proxy محتوا را می‌خواند؟

CONNECT عادی برقرار شد و TLS end-to-end است. آیا proxy می‌تواند HTTP body را بخواند؟

Ordinary CONNECT succeeds and TLS is end-to-end. Can the proxy read the HTTP body?

پاسخ

نه، محتوای داخل TLS را نه؛ metadata اتصال ممکن است قابل مشاهده باشد.

۷. HTTP رمز است؟

فرمان proxy scheme برابر http:// دارد. آیا client→proxy رمز است؟

نه به‌خاطر همین scheme؛ برای TLS به proxy باید HTTPS proxy transport پشتیبانی‌شده باشد.

Not because of that scheme; TLS to the proxy needs a supported HTTPS-proxy transport.

۸. 407 یا 401

کدام status به‌طور معمول challenge احراز هویت proxy است؟

Which status normally challenges proxy authentication?

پاسخ

407; an origin normally uses 401 for its own authentication challenge.

۹. دو هدر Authorization

Proxy-Authorization قرار است به کدام hop برسد؟

Which hop is Proxy-Authorization intended for?

پاسخ

به proxy؛ از Authorization مقصد جداست و نباید به origin نشت کند.

The proxy; it is distinct from origin Authorization and must not leak upstream.

TLS ClientHello را مستقیم به portای می‌فرستی که منتظر HTTP proxy است. کجا احتمالاً شکست می‌خورد؟

۱۲. CONNECT رد شد

۱۳. گواهی خطا می‌دهد

CONNECT موفق شد ولی curl گواهی origin را معتبر نمی‌داند. آیا tunnel موفق یعنی TLS هم موفق است؟

CONNECT succeeds, but curl rejects the origin certificate. Does a successful tunnel mean TLS succeeded?

نه؛ CONNECT فقط مسیر TCP را پذیرفته، TLS validation مرحله‌ای جداست.

No; CONNECT accepted a TCP path. TLS validation is a separate stage.

۱۵. Basic proxy auth

چرا فرستادن Proxy-Authorization Basic روی HTTP ساده ریسک دارد؟

Why is sending Basic Proxy-Authorization over plain HTTP risky?

۱۶. مرز مشاهده‌پذیری

proxy در CONNECT چه چیزهایی را با اطمینان بیشتری از body می‌تواند مشاهده کند؟

With CONNECT, what can a proxy more readily observe than the HTTP body?

مقصد/port درخواست‌شده، زمان، حجم و الگوی اتصال؛ جزئیات handshake وابسته به نسخه و قابلیت‌هاست.

۱۷. تفاوت مرحله‌ها

client CONNECT می‌فرستد، 2xx می‌گیرد، سپس timeout می‌شود. چه سه مرحله‌ای را جدا بررسی می‌کنی؟

The client sends CONNECT, receives 2xx, then times out. Which three stages do you inspect separately?

۱۸. trace خودت را گزارش کن

یک curl مستقیم، یک proxied HTTP و یک HTTPS از CONNECT مقایسه کن. برای هرکدام request-target، peer مستقیم، TLS endpoint و چیزی را که شاهدت ثابت نمی‌کند بنویس.

معیار پاسخ

سه مسیر باید در hopها و visibility فرق کنند؛ اگر proxy محلی نداری، آن بخش را صادقانه اجرا‌نشده ثبت کن.

The paths must differ in hops and visibility; if no local proxy was available, honestly mark that part unrun.

تونل را با رمزگشایی اشتباه نگیرDo not confuse tunneling with decryption

در HTTP، proxy URL را می‌بیند و درخواست را به origin می‌فرستد. در HTTPS با CONNECT، اول درخواست ساخت تونل می‌رود؛ پس از پاسخ 2xx، proxy بایت‌ها را relay می‌کند و TLS می‌تواند تا origin ادامه پیدا کند. اگر شکست دیدی، اتصال به proxy، پاسخ CONNECT، TLS و درخواست HTTP را چهار مرحلهٔ جدا بدان. همین جداسازی جلوی تشخیص اشتباه «proxy خراب است» را می‌گیرد.

For HTTP, the proxy sees the URL and forwards the request. For HTTPS with CONNECT, the client first requests a tunnel; after a 2xx, the proxy relays bytes while TLS can continue to the origin. When something fails, separate proxy connection, CONNECT response, TLS, and HTTP request into four stages. That prevents the vague diagnosis “the proxy is broken.”
