HTTP proxy و متد CONNECT

HTTP proxies and the CONNECT method

یه درخواست از proxy رد می‌شه؛ اما روی سیم دقیقاً چی بین client و proxy ردوبدل می‌شه؟

How a request passes through a proxy.

۸۰دقیقهminutes
۱۸تمرینexercises

یک درخواست، اما کدوم قالب روی سیم؟One request, but which form goes on the wire?

فصل قبل جای proxy رو روی مسیر پیدا کردیم. حالا یه قدم نزدیک‌تر می‌شیم. فرض کن curl رو تنظیم کردی که از یه forward proxy رد بشه و بعد یه URL می‌دی. proxy باید از یه جایی بفهمه مقصد کجاست. برای HTTP معمولی، خود درخواست مقصد رو لو می‌ده. برای HTTPS داستان یه کم فرق می‌کنه: اول یه تونل با CONNECT می‌سازیم، بعد TLS رو داخل همون تونل راه می‌اندازیم. بیا این دو مکالمه رو دونه‌دونه ببینیم.

Last chapter showed that a client can select a forward proxy. Now curl connects to a proxy and asks for a URL. How does the proxy know the destination? For ordinary HTTP, the destination appears in the request target. For HTTPS, the client first asks for a TCP tunnel, then starts TLS inside it.

مرز مهم همین هست: CONNECT معمولاً TLS رو رمزگشایی نمی‌کنه؛ فقط می‌خواد جریان بایت‌ها تا host:port مشخص عبور کند. تا وقتی proxy عمداً TLS رو با گواهی مورداعتماد client terminate نکرده باشه—که در این دوره نمی‌سازیم—TLS میان client و origin باقی می‌مونه.

That boundary matters: CONNECT normally does not decrypt TLS. It asks the proxy to relay a byte stream to a host and port. Unless a proxy deliberately terminates TLS with a certificate trusted by the client—which we will not build here—TLS remains between client and origin.

HTTP ساده: مقصد در request-targetPlain HTTP: the destination is in the request target

بدون proxy، client معمولاً فقط path رو می‌فرسته: /docs. وقتی به forward proxy صریح وصل می‌شه، درخواست HTTP معمولاً URI کامل absolute-form رو می‌فرسته تا proxy بدونه کدوم host رو درخواست کند. شکل دقیق نسخه/پیاده‌سازی ممکنه جزئیات دیگری داشته باشه، اما host و scheme در درخواست آشکارند.

Without a proxy, a client usually sends only the path, such as /docs. With an explicit forward proxy, an HTTP request commonly uses the full absolute-form URI so the proxy can identify the requested host. Wire details can vary by HTTP version and implementation, but the scheme and host are visible in the request.

proxy درخواست رو دریافت می‌کنه و به origin می‌فرسته؛ payload HTTP رمز نیست.

The proxy receives and forwards the request; plain HTTP payload is not encrypted.

GET http://example.com/docs HTTP/1.1
Host: example.com
User-Agent: curl/…
Accept: */*

این شکل یک نمونهٔ آموزشی هست، نه خروجی دقیق همهٔ نسخه‌های curl. برای دیدن رفتار واقعی، در محیط مجاز Squid محلی رو روی loopback اجرا کن. پیش از اجرا مطمئن شو Docker داری و پورت 3128 آزاد هست. image نسخه‌دار رو از رجیستری رسمی/معتبر بررسی کن؛ tag نمونه باید با tag موجود جایگزین بشه:

This is an illustrative request, not byte-for-byte output from every curl version. To observe a real exchange, run local Squid bound only to loopback. Confirm Docker is available and port 3128 is free first. Verify a versioned image tag from a trusted registry; replace the sample tag if needed:

docker run --rm --name proxy-lab -p 127.0.0.1:3128:3128 ubuntu/squid:6

در ترمینال دیگر درخواست HTTP بی‌حساسیت بفرست: curl -v --noproxy "" --proxy http://127.0.0.1:3128 http://example.com/. در trace دنبال اتصال به 127.0.0.1:3128، درخواست proxy و پاسخ بگرد. گزینهٔ --noproxy "" مانع bypass شدن به‌خاطر NO_PROXY می‌شه. اگه Squid دسترسی رو رد کرد، log و ACL image رو بخوان؛ ACLهای image ممکنه فرق کنند. این آزمایش فقط ثابت می‌کنه درخواست از proxy محلی گذشت، نه اینکه خودت اون رو در production امن کرده‌ای.

In another terminal, send a harmless HTTP request: curl -v --noproxy "" --proxy http://127.0.0.1:3128 http://example.com/. Look for the connection to 127.0.0.1:3128, the proxy request, and the response. --noproxy "" prevents NO_PROXY from bypassing the proxy. If Squid denies access, inspect its logs and image ACLs; defaults vary. This proves a request passed through a local proxy, not that you have a production-secure proxy.

HTTPS: اول CONNECT، بعد TLSHTTPS: CONNECT first, then TLS

برای URL از نوع https، curl به proxy می‌گه: «یک اتصال به example.com:443 برایم باز کن.» در HTTP/1.1 این درخواست معمولاً چنین هست. این قالب authority-form هست؛ path صفحه در اون نیست.

For an HTTPS URL, curl asks the proxy to open a connection to example.com:443. In HTTP/1.1 the request commonly looks like this. This is authority-form; it does not include the page path.

CONNECT example.com:443 HTTP/1.1
Host: example.com:443
Proxy-Connection: Keep-Alive

اگه مجاز بود، proxy یک پاسخ موفق 2xx می‌ده؛ خیلی از proxyها متن توضیحی 200 Connection established رو نشان می‌دن، ولی عبارت بدنه/دلیل‌نامه به پیاده‌سازی وابسته هست. بعد از پاسخ، socket همون اتصال به تونل بایت‌ها تبدیل می‌شه: client TLS ClientHello می‌فرسته و handshake با origin پیش می‌ره.

If allowed, the proxy returns a successful 2xx response. Many proxies display a reason phrase like 200 Connection established, but the wording is implementation-specific. After the response, the socket becomes a byte tunnel: the client sends a TLS ClientHello and the handshake proceeds with the origin.

پاسخ 2xx تونل رو باز می‌کنه؛ TLS داخل tunnel به origin ختم می‌شه، نه proxy.

A 2xx opens the tunnel; TLS inside it terminates at the origin, not the proxy.

این بار همون Squid محلی رو با HTTPS امتحان کن: curl -v --noproxy "" --proxy http://127.0.0.1:3128 https://example.com/. trace باید CONNECT و سپس handshake گواهی TLS رو نشون بده. عبارت‌های دقیق و ترتیب جزئیات با نسخه curl/proxy فرق می‌کنه. گواهی‌ای که curl بررسی می‌کنه باید متعلق به origin و قابل‌اعتماد باشه. این خروجی نشان می‌ده tunnel و TLS ساخته شد؛ محتوای رمز رو به proxy نسبت نده.

Try HTTPS through the same local Squid: curl -v --noproxy "" --proxy http://127.0.0.1:3128 https://example.com/. The trace should show CONNECT followed by a TLS certificate handshake. Exact wording and detail order vary by curl/proxy version. curl should validate a trusted certificate for the origin. This shows a tunnel and TLS session were established; it does not mean the proxy can read encrypted content.

proxy مقصد، port، زمان اتصال، اندازه و الگوی ترافیک رو می‌تونه ببینه. در TLS 1.3 بخشی از metadata handshake هم رمز می‌شه؛ اینکه دقیقاً چه metadata قابل مشاهده هست به DNS، نسخهٔ TLS، ECH و شبکه بستگی داره. از یک trace ساده ادعای «هیچ اطلاعاتی دیده نمی‌شه» نساز.

The proxy can observe destination, port, timing, traffic size, and patterns. With TLS 1.3, some handshake metadata is encrypted too; exact visibility depends on DNS, TLS version, ECH, and network setup. Do not turn one simple trace into a claim that “nothing is visible.”

خرابی عمدی: انگار HTTPS رو مستقیم به proxy داده‌ایمDeliberate failure: pretend HTTPS goes straight to the proxy

یک proxy HTTP منتظر پیام HTTP هست. اگه client به‌جای CONNECT، TLS ClientHello رو مستقیم به همون پورت بفرسته، proxy نمی‌تونه اون رو مثل درخواست HTTP تفسیر کند. برعکسش هم خطاست: بعد از CONNECT موفق، دوباره یک خط درخواست HTTP داخل tunnel نفرست مگر پروتکل مقصد اون رو می‌خواد؛ آنجا باید TLS handshake آغاز بشه.

An HTTP proxy expects HTTP messages. If a client sends a TLS ClientHello directly to that port instead of CONNECT, the proxy cannot parse it as an HTTP request. The reverse mistake is also wrong: after a successful CONNECT, do not send another HTTP request line inside the tunnel unless the destination protocol expects it; TLS should begin there.

نشانه‌ها می‌تونه reset، پاسخ malformed، خطای TLS یا پیام syntax در log proxy باشه؛ دقیقاً یک خروجی واحد نداریم. اول curl -v رو نگاه کن: آیا CONNECT فرستاده شد؟ آیا پاسخ 2xx آمد؟ آیا TLS با host درست شروع شد؟ بعد log proxy و port رو بررسی کن. تشخیص رو از مرحله‌ای که شکست خورده شروع کن، نه از حدس «گواهی خراب هست».

Symptoms can include a reset, malformed response, TLS error, or proxy syntax log; there is no single guaranteed message. Start with curl -v: was CONNECT sent? Did a 2xx arrive? Did TLS start for the intended host? Then inspect proxy logs and port. Diagnose the failed stage rather than guessing that the certificate is bad.

احراز هویت proxy با احراز هویت سایت یکی نیستProxy authentication is not origin authentication

proxy سازمانی ممکنه پاسخ 407 Proxy Authentication Required بدهد؛ client باید credential proxy رو با روش پشتیبانی‌شده بفرسته، و proxy معمولاً Proxy-Authenticate می‌ده. این با 401 و WWW-Authenticate از origin فرق داره. هدر Proxy-Authorization برای hop proxy هست؛ نباید با Authorization مقصد قاطی بشه یا به origin forward بشه.

An enterprise proxy may return 407 Proxy Authentication Required and a Proxy-Authenticate challenge. That differs from an origin’s 401 and WWW-Authenticate. Proxy-Authorization is for the proxy hop; it must not be confused with origin Authorization or forwarded to the origin.

برای curl می‌شه از --proxy-user USER استفاده کرد، اما credential رو داخل تاریخچهٔ shell، log یا screenshot نگذار. روش Basic روی HTTP معمولی credential رو محرمانه نمی‌کنه؛ فقط وقتی transport امن و قانون روشن هست از اون استفاده کن. در آزمایش این فصل auth proxy رو روشن نمی‌کنیم تا راز ساختگی هم لازم نشه.

curl supports --proxy-user USER, but never place credentials in shell history, logs, or screenshots. Basic authentication over plain HTTP does not protect credentials; use it only with a secure transport and explicit policy. This chapter’s lab does not enable proxy auth, so no fake secret is needed.

آزمایش: دو نوع URL، دو مکالمهLab: two URL types, two exchanges

پروکسی آزمایش رو فقط روی loopback منتشر کن. اگه Docker نداری یا image/tag در دسترس نیست، مرحله رو رد کن و یک proxy مجاز محلی انتخاب کن؛ port رو عمومی نکن. Container رو در ترمینال قابل‌کنترل نگه دار تا با Ctrl+C متوقف بشه:

Publish the lab proxy only on loopback. If Docker or the image tag is unavailable, skip this step and use an authorized local proxy; do not publish the port publicly. Keep the container attached so it can be stopped with Ctrl+C:

docker run --rm --name proxy-lab -p 127.0.0.1:3128:3128 ubuntu/squid:6

در ترمینال دوم برای HTTP ساده trace بگیر. دنبال URI کامل و پاسخ origin بگرد:

In a second terminal, capture a trace for plain HTTP. Look for the full URI and origin response:

curl -v --noproxy "" --proxy http://127.0.0.1:3128 http://example.com/

برای HTTPS همون proxy رو نگه دار و فقط scheme مقصد رو عوض کن. دنبال CONNECT، پاسخ موفق، TLS certificate و درخواست encrypted بگرد. ممکنه curl-version یا proxy قانون، CONNECT رو رد کند؛ این شکست رو ثبت و از log دلیل مجاز رو بخوان.

Keep the same proxy and change only the destination scheme to HTTPS. Look for CONNECT, a successful response, TLS certificate details, and the encrypted request. curl version or proxy policy may reject CONNECT; record that result and inspect logs for the permitted reason.

curl -v --noproxy "" --proxy http://127.0.0.1:3128 https://example.com/

حالا یک بار به پورت proxy اشتباه وصل شو و یک بار proxy container رو متوقف کن. هر دو می‌تونن اتصال رو ناکام کنند، ولی اولی نشانی/listener و دومی چرخهٔ عمر سرویس رو مطرح می‌کنه. trace client و docker logs رو کنار هم بخوان؛ بعد proxy رو متوقف کن تا چیزی بی‌دلیل باز نماند.

Now connect once to the wrong proxy port and once after stopping the proxy container. Both can fail, but the first points toward address/listener and the second toward service lifecycle. Compare client trace with container logs, then stop the proxy so nothing remains running unnecessarily.

The paths must differ in hops and visibility; if no local proxy was available, honestly mark that part unrun.

تونل رو با رمزگشایی اشتباه نگیرDo not confuse tunneling with decryption

در HTTP، proxy URL رو می‌بینه و درخواست رو به origin می‌فرسته. در HTTPS با CONNECT، اول درخواست ساخت تونل می‌ره؛ پس از پاسخ 2xx، proxy بایت‌ها رو relay می‌کنه و TLS می‌تونه تا origin ادامه پیدا کند. اگه شکست دیدی، اتصال به proxy، پاسخ CONNECT، TLS و درخواست HTTP رو چهار مرحلهٔ جدا بدان. همین جداسازی جلوی تشخیص اشتباه «proxy خراب هست» رو می‌گیره.

For HTTP, the proxy sees the URL and forwards the request. For HTTPS with CONNECT, the client first requests a tunnel; after a 2xx, the proxy relays bytes while TLS can continue to the origin. When something fails, separate proxy connection, CONNECT response, TLS, and HTTP request into four stages. That prevents the vague diagnosis “the proxy is broken.”
