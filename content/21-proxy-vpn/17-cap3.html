ماموریت: یک client بیرون، یک سرویس داخلMission: a client outside, a service inside

درخواست آمده: همکارت باید از لپ‌تاپ بیرون شبکه به یک سرویس داخلی برسد. مدیر شبکه هم شرط گذاشته: فقط مسیر لازم باز باشد؛ proxy برای عموم اینترنت نشود؛ اگر route یا DNS خراب شد، با log و counter علت را پیدا کنیم؛ بعد از restart هم سرویس برگردد.

A teammate needs to reach an internal service from a laptop outside the network. The network owner adds constraints: open only the required path, do not create a public proxy, diagnose route or DNS failures from logs and counters, and recover after restart.

این پروژه را در سه VM تحت مالکیت خودت بساز: remote client، gateway دو-شبکه‌ای، و private service. هر سه را روی شبکه‌های host-only/internal بگذار؛ هیچ port را از router به اینترنت forward نکن. اگر محیط ایزوله نداری، متوقف شو و اول VM disposable بساز—این تمرین جای شبکهٔ عمومی نیست. پروژهٔ ۲ را به‌عنوان الگوی peerها ادامه بده؛ proxy را از فصل ۲ و سخت‌سازی را از فصل ۱۴ به‌کار بگیر، نه اینکه دوباره درسشان را از اول بخوانی.

Build this with three VMs you control: a remote client, a two-network gateway, and a private service. Attach them only to host-only/internal networks; do not forward ports from a router to the internet. If you lack an isolated environment, first create disposable VMs—this is not an exercise for a public network. Extend the peer model from Project 2 and apply proxy and hardening concepts from Chapters 2 and 14 instead of reteaching them.

خط‌ها مسیرهای جدا را نشان می‌دهند: tunnel برای route، درخواست HTTP به proxy و شواهد monitoring؛ پیکان‌ها مرز gateway را دور نمی‌زنند.

Distinct lines show routed tunnel traffic, an HTTP request to the proxy, and monitoring evidence; no path bypasses the gateway boundary.

NAT را در این طراحی لازم نداریم: client به سرویس داخلی route می‌شود و service با gateway خصوصی جواب را برمی‌گرداند. حفظ IP اصلی client برای log و عیب‌یابی مفید است. این انتخاب مانع ساخت اینترنت‌gateway ناخواسته می‌شود؛ اگر بعداً NAT لازم شد، آن را تغییر جداگانه با test و rollback طراحی کن.

This design does not need NAT: the client routes to the private service, which returns via its private gateway. Preserving the client’s original address helps logs and diagnosis. This also avoids accidentally building an internet gateway; if NAT is later required, design it as a separate tested change with rollback.

۱. محیط disposable و baseline سرویس

سه VM را با دو شبکهٔ داخلی بساز: underlay برای client↔gateway و private LAN برای gateway↔service. آدرس‌دهی را از جدول بالا اعمال کن، روی service یک صفحهٔ بی‌خطر بساز و فقط روی `10.88.0.10:8080` اجرا کن. قبل از tunnel، gateway باید service را ببیند؛ client نباید مستقیم به LAN دسترسی داشته باشد.

Create three VMs and two isolated networks: underlay for client↔gateway, private LAN for gateway↔service. Apply the address plan, create a harmless page on the service, and bind it only to `10.88.0.10:8080`. Before the tunnel, the gateway should reach the service; the client should not.

راهنمایی

برای server موقت Python از port غیر privileged استفاده کن. `ss -lntp` روی service باید bind روی LAN IP را نشان بدهد، نه `0.0.0.0`.

Use Python’s temporary server on an unprivileged port. On the service VM, `ss -lntp` should show the LAN address, not `0.0.0.0`.

مدرک این مرحله

سه نام VM و interfaceها، route tableها، درخواست موفق gateway→service و درخواست ناموفق client→service پیش از VPN.

VM/interface inventory, route tables, a successful gateway→service request, and a failed client→service request before VPN.

۲. VPN ingress و هویت peer

از Project 2 استفاده کن: client با key خودش، gateway با key خودش، client tunnel=`10.77.0.2/32`، gateway=`10.77.0.1/24`. server-side AllowedIPs فقط `.2/32`؛ client-side فقط `.10.77.0.1/32` و `10.88.0.0/24`. اگر client به default route احتیاج ندارد، `0.0.0.0/0` اضافه نکن.

Reuse Project 2’s model: separate client/gateway keys, client tunnel `10.77.0.2/32`, gateway `10.77.0.1/24`. Server-side AllowedIPs is only `.2/32`; client routes only `10.77.0.1/32` and `10.88.0.0/24`. Do not add `0.0.0.0/0` when no default route is needed.

راهنمایی

اول handshake و ping به خود gateway را ثابت کن. هنوز private LAN را وارد ruleهای firewall نکرده‌ایم؛ این جداسازی کمک می‌کند failure بعدی را دقیق‌تر بخوانی.

First prove handshake and ping to the gateway itself. The private LAN is not yet enabled in forwarding policy; this separation makes the next failure easier to diagnose.

مدرک این مرحله

`wg show` peer صحیح و handshake تازه را نشان می‌دهد؛ route lookup برای gateway از `wg0` است؛ private service هنوز از client unreachable است.

`wg show` identifies the correct peer with a recent handshake; route lookup to the gateway uses `wg0`; the private service is still unreachable from the client.

۳. route را عمدی خراب کن

route `10.88.0.0/24` را موقت از AllowedIPs client بردار. handshake و ping به gateway باید بماند، ولی lookup مقصد service دیگر از tunnel انتخاب نمی‌شود. با `ip route get 10.88.0.10` و `wg show` فرق route و peer را ثابت کن، بعد route لازم را برگردان.

Temporarily remove route `10.88.0.0/24` from client AllowedIPs. The handshake and gateway ping should remain, but lookup for the service no longer selects the tunnel. Use `ip route get 10.88.0.10` and `wg show` to distinguish route from peer, then restore the required route.

راهنمایی

وقتی handshake تازه است، کلید را عوض نکن. route table client اولین شاهد تفکیک‌کننده است.

With a recent handshake, do not rotate the key. The client route table is the first discriminating check.

گزارش incident

نشانه: gateway قابل‌دسترسی است، service نه. شاهد: `ip route get` مسیر مستقیم/غلط نشان می‌دهد. علت: مقصد LAN از AllowedIPs route نشده. repair: route دقیق را اضافه و همان lookup و درخواست را تکرار کن.

Symptom: gateway reachable, service not. Evidence: `ip route get` shows a direct/wrong path. Cause: the LAN destination is absent from AllowedIPs routing. Repair: add the narrow route and repeat the same lookup and request.

۴. forwarding و firewall را فقط برای این مسیر باز کن

gateway باید packet از `wg0` به interface LAN بفرستد؛ service پاسخ را از gateway خصوصی برمی‌گرداند. forwarding را در VM gateway فعال و ruleهای nft را محدود کن به client tunnel `10.77.0.2` → service `10.88.0.10` روی TCP 8080، و پاسخ established. counters را قبل و بعد از یک درخواست بخوان.

The gateway must forward packets from wg0 to the LAN interface; the service returns through its private gateway. Enable forwarding in the gateway VM and restrict nftables to client tunnel `10.77.0.2` → service `10.88.0.10` on TCP 8080, plus established replies. Read counters before and after one request.

راهنمایی

`INPUT` برای خود gateway و `FORWARD` برای عبور از آن است. اگر handshake و route درست‌اند ولی counter forward صفر می‌ماند، مسیر interface یا hook را دوباره بسنج.

`INPUT` is traffic to the gateway; `FORWARD` is traffic through it. If handshake and route are correct but the forward counter stays at zero, recheck interface and hook selection.

مدرک این مرحله

service فقط از مسیر مجاز پاسخ می‌دهد؛ port دیگری publish/open نیست؛ counter rule لازم زیاد می‌شود و درخواست از مبدأ/port نامجاز رد می‌شود. NAT لازم نیست.

The service responds only through the intended path; no unrelated port is exposed; the intended rule counter increases and a disallowed source/port is rejected. NAT is not needed.

۵. DNS را جدا خراب و تشخیص بده

روی gateway یک نام آزمایشگاهی مثل `app.lab.test` به `10.88.0.10` بده و DNS فقط روی `10.77.0.1:53` گوش کند. رکورد را عمداً موقت به IP اشتباه تغییر بده: HTTP با IP مستقیم باید کار کند، ولی lookup/درخواست نامی باید به مقصد غلط برود. DNS cache را هم در نظر بگیر؛ نشانه، query پاسخ‌گو با data نادرست است نه الزاماً timeout.

Map a lab name such as `app.lab.test` to `10.88.0.10` and bind DNS only on `10.77.0.1:53`. Deliberately change the record to a wrong IP: direct-IP HTTP should still work, while lookup/name-based request goes to the wrong destination. Consider DNS caching; the signal may be a successful query with wrong data, not a timeout.

راهنمایی

مستقیم `dig @10.77.0.1 app.lab.test` و resolver سیستم را جدا مقایسه کن. مسیر، DNS record و cache سه بخش متفاوت‌اند.

Compare direct `dig @10.77.0.1 app.lab.test` with the system resolver. Route, DNS record, and cache are separate layers.

گزارش incident

نشانه: IP مستقیم کار می‌کند، نام نه. شاهد: query به DNS می‌رسد اما جواب IP اشتباه دارد. علت: record غلط (یا cache قدیمی). repair: record را درست کن، cache را با روش همان resolver پاک/منقضی کن و lookup و HTTP نامی را تکرار کن.

Symptom: direct IP works, name does not. Evidence: DNS answers, but with the wrong address. Cause: incorrect record or stale cache. Repair the record, expire the relevant resolver cache, then repeat lookup and hostname-based HTTP.

۶. مسیر proxy را بساز و یک service fault تشخیص بده

روی gateway یک Squid lab proxy فقط روی `10.77.0.1:3128` bind کن؛ ACL فقط peer tunnel و مقصد `10.88.0.10:8080` را مجاز کند و بقیه را deny کند. بعد سرویس origin را عمدی روی `127.0.0.1:8080` bind کن. proxy از gateway باید 502/connection failure ببیند؛ از روی host service، `ss -lntp` علت bind محلی را روشن می‌کند.

Run a lab Squid proxy bound only to `10.77.0.1:3128`; allow only the tunnel peer and destination `10.88.0.10:8080`, denying everything else. Then deliberately bind the origin to `127.0.0.1:8080`. The proxy should see a connection failure/502; `ss -lntp` on the service host reveals the loopback-only bind.

راهنمایی

proxy process healthy بودنش را با upstream reachability اشتباه نگیر. اول `ss` روی service، بعد curl از gateway به LAN، بعد log Squid را بررسی کن؛ ACL را بی‌دلیل باز نکن.

Do not confuse a healthy proxy process with upstream reachability. Check service `ss`, then gateway-to-LAN curl, then Squid logs; do not loosen the ACL blindly.

repair و اثبات

origin را روی `10.88.0.10` یا interface LAN bind کن؛ مستقیم از gateway تست بزن، بعد درخواست از client با proxy را تکرار. درخواست به مقصد بیرون allowlist همچنان باید deny شود.

Bind the origin to `10.88.0.10` or its LAN interface; test directly from the gateway, then repeat the client request through the proxy. A destination outside the allowlist must still be denied.

۷. پایش، کلید و backup بدون secret

برای هر سرویس پاسخ این پرسش‌ها را جمع کن: کدام version/config اجراست؟ peer handshake و counter تازه‌اند؟ route کجاست؟ کدام nft counter بالا می‌رود؟ DNS و HTTP چه می‌گویند؟ از `wg show`, `ss`, `nft list ruleset`, `journalctl` و `df -h` استفاده کن. backup فقط از config غیرsecret مثل DNS/proxy/firewall و دستورهای راه‌اندازی باشد؛ فایل WireGuard دارای private key را archive نکن.

Collect evidence for: which version/config is live, whether peer handshake/counters are fresh, where routes point, which nft counter increments, and what DNS/HTTP report. Use `wg show`, `ss`, `nft list ruleset`, `journalctl`, and `df -h`. Back up only non-secret DNS/proxy/firewall config and startup instructions; do not archive the WireGuard file containing a private key.

راهنمایی

قبل از ساخت archive مسیر و فهرست فایل‌ها را بنویس؛ بعد `tar -tzf` را بخوان تا key/config حساس اشتباهی داخلش نباشد. mode و retention backup را هم مشخص کن.

List intended files before archiving, then inspect with `tar -tzf` to ensure private-key config was not included. Define backup mode and retention too.

مدرک لازم

یک snapshot timestampدار از counterها و logs، `df -h`، و archive قابل‌خواندن که فهرستش فقط فایل‌های غیرsecret را دارد. این artifact محرمانگی/قابل‌restore بودن private key را تضمین نمی‌کند؛ اصلاً آن را دربرنمی‌گیرد.

A timestamped snapshot of counters/logs and `df -h`, plus a readable archive containing only non-secret files. This artifact does not guarantee private-key confidentiality or restoration; it intentionally excludes the key.

۸. startup و rollback را روی VMها تمرین کن

روی gateway، WireGuard و proxy/DNS را با systemd فعال کن؛ روی service، برنامه را با user غیر root و unit محدود بالا بیاور. restart کنترل‌شده انجام بده و acceptance probeها را همان ترتیب قبلی اجرا کن. قبل از تغییر config مهم، backup non-secret را بگیر؛ rollback یعنی برگرداندن config تأییدشده و تکرار probe، نه restart بی‌مدرک.

Enable WireGuard and proxy/DNS under systemd on the gateway; run the service under a non-root user and unit on the service VM. Perform a controlled restart and repeat acceptance probes in the same order. Back up non-secret config before significant changes; rollback means restoring known-good config and rerunning probes, not an evidence-free restart.

راهنمایی

`systemctl is-enabled` و `systemctl status` startup policy را نشان می‌دهند؛ درخواست HTTP و handshake بعد از restart recovery را نشان می‌دهند. این دو شاهد را یکی نکن.

`systemctl is-enabled` and `systemctl status` show startup policy; HTTP requests and handshakes after restart show recovery. Do not treat these as the same evidence.

معیار تحویل

پس از restart هر سه سرویس فعال‌اند، peer دوباره handshake می‌کند، DNS/HTTP پاسخ می‌دهند، ACL هنوز مقصد غیرمجاز را رد می‌کند و private LAN port از underlay قابل‌دسترسی نیست.

After restart all three services are active, the peer handshakes again, DNS/HTTP respond, the ACL still rejects a forbidden destination, and the private LAN port is not reachable from the underlay.

۹. incident report و handoff

سه خرابی را جدا ثبت کن: route حذف‌شده، DNS record اشتباه و origin فقط روی loopback. برای هرکدام پنج چیز بنویس: نشانه، شاهد، علت، repair، و همان verification پس از repair. در کنار آن public/private interfaceها، listening portها، ruleهای firewall، key ownership و backup boundary را خلاصه کن.

Document the three faults separately: missing route, wrong DNS record, and origin bound only to loopback. For each, record five things: symptom, evidence, cause, repair, and the same verification after repair. Also summarize public/private interfaces, listening ports, firewall rules, key ownership, and backup boundary.

راهنمایی

برای «علت» command حدس نزن؛ یک شاهدی را بنویس که فرضیه‌های رقیب را جدا کرد. برای «repair» همان probe قبل از repair را دوباره بزن.

Do not list a guessed command as the cause; identify evidence that distinguished competing hypotheses. For repair, rerun the same probe used before.

قبولی

یک نفر دیگر باید بتواند از دفترچه‌ات topology را بفهمد، نسخهٔ آزمایشگاهی را بالا بیاورد، سه incident را بازتولید/رفع کند و بداند کدام secret را نباید از تو بخواهد.

Another person should be able to understand the topology, bring up the lab, reproduce and repair all three incidents, and know which secret they should never ask you to share.

runbook مرجع؛ از مسیر پایه تا gateway کاملReference runbook: from baseline to full lab gateway

ابتدا service VM را فقط روی LAN بالا بیاور و درخواست را از gateway مستقیم امتحان کن. `ss -lntp` باید listener روی `10.88.0.10:8080` نشان بدهد. اگر این پایه کار نمی‌کند، VPN را وارد عیب‌یابی نکن. VMها باید network adapter مجزا و host-only باشند؛ نام interfaceها را با `ip -br link` تشخیص بده.

First start the service only on the private LAN and request it directly from the gateway. `ss -lntp` should show a listener on `10.88.0.10:8080`. If this baseline fails, do not involve the VPN yet. VMs need separate host-only adapters; identify interfaces with `ip -br link`.

روی service یک محتوای بی‌خطر بساز و سرور موقت را با `python3 -m http.server 8080 --bind 10.88.0.10` اجرا کن. در production از سرور توسعهٔ Python استفاده نکن؛ این فقط origin آزمایش است. gateway باید `curl http://10.88.0.10:8080/` را موفق کند، client مستقیم باید fail شود.

Create harmless content on the service VM and run `python3 -m http.server 8080 --bind 10.88.0.10`. Do not use Python’s development server in production; it is only a lab origin. The gateway should fetch `curl http://10.88.0.10:8080/`; the client should fail when trying directly.

WireGuard config را مشابه Project 2 بساز. server tunnel `10.77.0.1/24`، client `10.77.0.2/32`؛ server peer AllowedIPs=`10.77.0.2/32`؛ client peer endpoint=`192.168.77.10:51820` و AllowedIPs=`10.77.0.1/32, 10.88.0.0/24`. private key فقط در فایل با permission محدود بماند. برای رسیدن service، gateway را forward کن؛ gateway-side route به LAN از interface متصل به `10.88.0.0/24` ساخته می‌شود.

Build WireGuard config as in Project 2: server tunnel `10.77.0.1/24`, client `10.77.0.2/32`; server peer AllowedIPs=`10.77.0.2/32`; client endpoint=`192.168.77.10:51820` and AllowedIPs=`10.77.0.1/32, 10.88.0.0/24`. Keep the private key only in a restricted file. Enable forwarding to the LAN; the gateway’s connected route to `10.88.0.0/24` comes from its LAN interface.

روی gateway forwarding را فعال و firewall را default-deny برای عبور قرار بده، سپس فقط `wg0`→LAN از `10.77.0.2` به `10.88.0.10:8080` و برگشت established را مجاز کن. روی service default gateway را `10.88.0.1` قرار بده تا پاسخ به client راه برگشت داشته باشد. در این topology هیچ SNAT لازم نیست؛ با capture/log ثابت کن IP tunnel client در مقصد حفظ می‌شود.

Enable forwarding on the gateway and use a default-deny forward policy. Permit only wg0→LAN from `10.77.0.2` to `10.88.0.10:8080`, plus established replies. Set the service’s default gateway to `10.88.0.1` for the return path. This topology needs no SNAT; verify that the client’s tunnel source address is preserved at the destination.

DNS را با dnsmasq روی `10.77.0.1` bind کن و `app.lab.test` را به `10.88.0.10` بده. ابتدا `dig @10.77.0.1 app.lab.test`، بعد resolver client را فقط برای suffix آزمایشگاهی به این DNS route کن و `curl http://app.lab.test:8080/` بزن. اگر DNS مستقیم جواب می‌دهد ولی hostname نه، route، resolver link و cache را جدا بررسی کن.

Bind dnsmasq to `10.77.0.1` and map `app.lab.test` to `10.88.0.10`. First run `dig @10.77.0.1 app.lab.test`, then route only the lab suffix to this DNS on the client and request `curl http://app.lab.test:8080/`. If direct DNS works but the hostname does not, inspect route, resolver link, and cache separately.

برای proxy در Squid، listener را روی `10.77.0.1:3128` محدود کن؛ ACL source=`10.77.0.2/32`، destination=`10.88.0.10/32`، port=`8080` و در پایان deny برای بقیه. rule allow را پیش از deny نهایی فایل config بگذار و denyهای محافظتی موجود distribution را پاک نکن. از client با `curl -x http://10.77.0.1:3128 http://10.88.0.10:8080/` تست کن؛ بعد مقصد غیرمجاز را امتحان و log Squid را بخوان.

Configure Squid to listen only on `10.77.0.1:3128`; ACL source `10.77.0.2/32`, destination `10.88.0.10/32`, port `8080`, then deny everyone else. Place the allow before the final deny and preserve distro-provided protective denies. Test from the client with `curl -x http://10.77.0.1:3128 http://10.88.0.10:8080/`, then try a forbidden destination and inspect Squid logs.

سه incident را یکی‌یکی بساز: AllowedIPs route را بردار؛ DNS record را اشتباه کن؛ و origin را روی `127.0.0.1` bind کن. هر بار فقط یک علت را وارد کن، شاهد را ذخیره کن، repair را انجام بده و همان درخواست را تکرار کن. این کار جلوی «یک تغییر بزرگ که ظاهراً همه‌چیز را درست کرد» را می‌گیرد.

Create the three incidents one at a time: remove the AllowedIPs route, corrupt the DNS record, and bind the origin to `127.0.0.1`. Introduce one fault, save evidence, repair it, and repeat the same request. This avoids a large change that appears to fix everything without showing why.

startup را در VMها با unitهای systemd فعال کن: gateway برای `wg-quick@wg0`، Squid و dnsmasq؛ service برای origin آزمایشی با user غیر root. اگر config secret در WireGuard unit است، private key را backup plain نکن. از `/etc/squid`, فایل dnsmasq و firewall policy غیرsecret archive بگیر و با `tar -tzf` فهرستش را بخوان. archive این پروژه config قابل‌مشاهده است، نه backup کلید یا recovery کامل.

Enable systemd units in the VMs: `wg-quick@wg0`, Squid, and dnsmasq on the gateway; the lab origin under a non-root user on the service VM. Do not back up private keys in plaintext. Archive non-secret Squid, dnsmasq, and firewall config and inspect it with `tar -tzf`. This project archive is visible configuration, not a key backup or complete recovery plan.

برای evidence یک snapshot زمانی بگیر: `wg show`, `ip route`, `nft list ruleset`, `ss -lntup`, `journalctl` برای unitها، و `df -h`. خروجی‌ها ممکن است endpoint و IP خصوصی داشته باشند؛ پیش از share آن‌ها را پاک‌سازی کن. پس از `systemctl restart`، HTTP مستقیم، HTTP از proxy، DNS و forward را دوباره امتحان کن؛ هر لایه شاهد جدا می‌خواهد.

Capture a timestamped snapshot: `wg show`, `ip route`, `nft list ruleset`, `ss -lntup`, unit journals, and `df -h`. Outputs may reveal endpoints and private IPs; redact before sharing. After `systemctl restart`, retest direct HTTP, proxied HTTP, DNS, and forwarding—each layer needs separate evidence.

گزارش incident و تحویلIncident report and operational handoff

در گزارش نهایی برای هر خرابی این پنج سطر را کامل کن: نشانه؛ شاهدی که فرضیه‌های رقیب را جدا کرد؛ علت؛ repair محدود؛ همان verification پس از repair. بعد نقشهٔ interface/route، public listening ports، ruleهای firewall، محل keyها، سرویس‌های systemd و backupهای غیرsecret را مستند کن. secret یا private key را ضمیمه نکن.

For each incident, write five items: symptom; evidence that ruled between hypotheses; cause; narrow repair; and the same verification after repair. Then document interface/routes, listening ports, firewall policy, key locations, systemd services, and non-secret backups. Do not attach credentials or private keys.

این gateway ثابت می‌کند client مجاز از تونل به یک subnet و سرویس مشخص می‌رسد، proxy مقصدهای خارج ACL را نمی‌پذیرد و خرابی‌ها را می‌توان از شاهد تشخیص داد. ثابت نمی‌کند طراحی برای production، تعداد زیاد کاربر یا عبور امن به اینترنت آماده است؛ آن ادعاها به threat model، ظرفیت‌سنجی و آزمون جدا نیاز دارند.

This gateway proves an authorized client can reach a defined subnet/service over the tunnel, the proxy rejects destinations outside its ACL, and failures can be diagnosed from evidence. It does not establish production readiness, high-user capacity, or safe internet egress; those claims need separate threat modeling, capacity tests, and validation.

سه VM را خاموش کن، adapterهای host-only را جدا کن و فقط فایل‌های disposable همین پروژه را پاک کن. هیچ cleanup عمومی مثل reset firewall یا حذف فایل‌های host لازم نیست. حالا مسیر تمام شد: چیزی که از اینجا به بعد یاد می‌گیری باید روی topology واقعی و با مجوز روشن آزمایش شود.

Shut down the three VMs, detach host-only adapters, and remove only this project’s disposable artifacts. No host-wide firewall reset or file deletion is needed. The track ends here: further experiments belong on real topology only with explicit authorization.

قبل از کپی، روی gateway با `ip -br link` نام underlay و LAN را پیدا کن. این نمونه فرض می‌کند `underlay0` و `lan0` نام آن‌هاست. روی VM با firewall موجود، کل config را جایگزین نکن؛ ruleهای معادل را با manager همان VM وارد کن.

برای gateway، فعال‌کردن forwarding را در همان VM نگه دار:

Enable forwarding only inside the gateway VM:

پیش از ساخت ruleهای nft، مطمئن شو firewall دیگری همین chain را مدیریت نمی‌کند. این نمونه inputها را محدود می‌کند و فقط TCP از peer مجاز به سرویس را forward می‌کند؛ connection برگشت established می‌ماند:

Before adding nftables rules, ensure another firewall manager does not own the same policy. This sample narrows input and forwards only TCP from the permitted peer to the service, allowing established replies:

table inet codenames_lab {
  chain input {
    type filter hook input priority filter; policy drop;
    iifname "lo" accept
    ct state established,related accept
    iifname "underlay0" ip saddr 192.168.77.0/24 udp dport 51820 accept
    iifname "wg0" ip saddr 10.77.0.2 tcp dport 3128 accept
    iifname "wg0" ip saddr 10.77.0.2 udp dport 53 accept
  }
  chain forward {
    type filter hook forward priority filter; policy drop;
    ct state established,related accept
    iifname "wg0" oifname "lan0" ip saddr 10.77.0.2 ip daddr 10.88.0.10 tcp dport 8080 ct state new accept
  }
}

این policy عمدی هیچ SSH دسترسی نمی‌دهد؛ از کنسول VM کار کن یا فقط مبدأ مدیریت آزمایشگاه را با rule محدود اضافه کن. پیش از load، syntax را با `nft -c -f FILE` بررسی کن؛ policy drop اشتباه می‌تواند خودت را از VM بیرون بیندازد. برای آزمایش، داخل همین VM disposable اجرا کن و ruleها را با counter و درخواست مثبت/منفی verify کن.

This policy intentionally grants no SSH access; use the VM console or add a narrowly sourced lab-admin rule. Validate syntax with `nft -c -f FILE` before loading; a wrong drop policy can lock you out. Test only in the disposable VM and verify rules with counters plus positive/negative requests.

Place these directives at the appropriate position in `/etc/squid/squid.conf`; `http_access` order matters. After editing, run `squid -k parse` or the package’s validation command, reload, and test one allowed and one forbidden destination. در Ubuntu مجهز به systemd-resolved، client را فقط برای suffix آزمایشگاهی به DNS tunnel route کن و بعد تنظیم per-link را revert کن. `dig @...` مستقل از این تنظیم است و برای جداکردن خرابی DNS server از integration کاربرد دارد.

On Ubuntu with systemd-resolved, route only the lab suffix to tunnel DNS and revert the per-link settings afterward. `dig @...` is independent of this integration and helps separate DNS-server failure from resolver configuration.

دو تکهٔ آخر runbook: سرویس محدود و مرجع نسخهTwo final runbook pieces: a bounded service and version references

اگر می‌خواهی origin بعد از reboot بالا بیاید، در service VM یک user بدون login به نام `labweb` بساز، `/srv/labweb` را به او بده و unit آزمایشگاهی زیر را در `/etc/systemd/system/lab-origin.service` قرار بده. این فقط برای VM disposable است؛ Python `http.server` سرور production نیست.

To start the origin after reboot, create a non-login `labweb` user in the service VM, give it `/srv/labweb`, and place this lab unit at `/etc/systemd/system/lab-origin.service`. This is only for disposable VMs; Python’s `http.server` is not a production server.

[Unit]
Description=CodeNames lab HTTP origin
After=network-online.target
Wants=network-online.target

[Service]
User=labweb
Group=labweb
WorkingDirectory=/srv/labweb
ExecStart=/usr/bin/python3 -m http.server 8080 --bind 10.88.0.10 --directory /srv/labweb
Restart=on-failure
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target

بعد از ساخت unit، `systemctl daemon-reload`, `systemctl enable --now lab-origin` و `journalctl -u lab-origin` را در service VM اجرا کن. اگر `10.88.0.10` هنوز بالا نیامده باشد، unit ممکن است fail شود؛ network readiness را بررسی کن و بعد همان `curl` را تکرار کن.

After creating the unit, run `systemctl daemon-reload`, `systemctl enable --now lab-origin`, and inspect `journalctl -u lab-origin` in the service VM. If `10.88.0.10` is not configured yet, the unit may fail; check network readiness and repeat the same `curl`.

در nft fragment بالا، چون policy input پیش‌فرض drop است، اگر برای تشخیص از ping به خود gateway استفاده می‌کنی، ICMP را فقط از tunnel peer آزمایشگاهی مجاز کن. rule محدود نمونه: `iifname "wg0" ip saddr 10.77.0.2 ip protocol icmp accept` در chain input. بدون این rule از handshake، DNS و HTTP استفاده کن؛ ping failure را به معنی خرابی WireGuard نگیر.

Because the nft input policy defaults to drop, explicitly permit lab-peer ICMP to the gateway if you use ping for diagnosis. A narrow example in the input chain is `iifname "wg0" ip saddr 10.77.0.2 ip protocol icmp accept`. Without it, use handshake, DNS, and HTTP evidence; do not interpret failed ping as a WireGuard failure.
