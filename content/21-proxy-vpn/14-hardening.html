همه‌چیز کار می‌کنه؛ اما کی می‌تونه از این مسیر استفاده کند؟Everything works—but who can use this path?

تا وقتی فقط دنبال «کار کردن» باشیم، خیلی چیزها قشنگ به نظر می‌رسن: peer وصل می‌شه، proxy جواب می‌ده، route بازه. ولی از زاویهٔ امنیت سؤال برعکسه. اگه private key کپی شد چی؟ اگه proxy روی همهٔ interfaceها گوش بده چی؟ اگه یه peer بیشتر از چیزی که لازم داره route بگیره چی؟ سخت‌سازی از همین سؤال‌ها شروع می‌شه؛ نه از یه فهرست جادویی گزینه‌ها.

Last chapter showed that an up interface, a recent peer handshake, and a route each tell only part of the story. Now inspect the same VPN and proxy from the viewpoint of someone who should not have access. A copied private key, a proxy listening on every interface, or a peer with an overly broad route can turn a useful tool into an unintended entry point.

قرار نیست با چند گزینه ادعا کنیم سیستم «امن شد». سؤال کاربردی‌تر این هست: کی باید بتواند وصل بشه، چه مقصدی رو ببینه، چی رو تغییر دهد و اگه یک جزء لو رفت، دامنهٔ آسیب تا کجا می‌رسه؟

A handful of settings cannot certify a system as “secure.” Ask instead: who may connect, which destinations may they reach, what can they change, and how far could damage spread if one component is exposed?

هر مرز یک کنترل جدا می‌خواد: محدودکردن ورودی، هویت، مقصد و دادهٔ حساس.

Each boundary needs a distinct control: limit entry, identity, destination, and sensitive data.

اول کلید؛ اگه کپی شد، چی رو باید باطل کنیم؟Start with keys: what must be revoked if one is copied?

در WireGuard، private key هویت اون interface هست. اگه اون رو برای همکار فرستادی یا داخل Git گذاشتی، پاک‌کردن فایل از آخرین commit کافی نیست؛ ممکنه نسخه در history، clone یا backup بمونه. کلید تازه بساز، peer قبلی رو از سمت مقابل حذف کن، public key تازه رو ثبت کن و اتصال رو با کلید جدید بیازما. هیچ‌وقت private key رو برای عیب‌یابی چاپ نکن.

In WireGuard, a private key identifies that interface. If you sent it to a colleague or committed it, deleting it from the latest revision is not enough; copies may remain in history, clones, or backups. Generate a replacement, remove the old peer from the other side, register the new public key, and test with the replacement. Never print a private key for troubleshooting.

در آزمایشگاه، permission فایل رو بررسی کن. خروجی باید مالک مناسب و دسترسی محدود رو نشان دهد؛ عدد دقیق مالک/گروه به روش نصب و کاربری که سرویس رو اجرا می‌کنه بستگی داره. `chmod 600` یعنی فقط مالک فایل می‌تونه بخونه و بنویسد؛ اما اگه مالک اشتباه باشه، daemon هم ممکنه دیگر نتواند فایل رو بخونه.

In a lab, inspect the key file permissions. The owner should be appropriate and access restricted; exact ownership depends on installation and the service account. `chmod 600` lets only the owner read and write, but the daemon may lose access if ownership is wrong.

sudo stat -c '%a %U:%G %n' /etc/wireguard/wg0.conf
sudo namei -l /etc/wireguard/wg0.conf
sudo wg show wg0

در خروجی اول، mode و owner رو می‌بینی؛ `namei` دسترسی تک‌تک پوشه‌های مسیر رو هم نشان می‌ده. `wg show` برای بررسی interface و peer مناسب هست، اما private key رو نمایش نمی‌ده. این بررسی ثابت نمی‌کنه فایل backup یا نسخهٔ دیگری جایی افشا نشده.

The first command shows mode and owner; `namei` also checks each directory in the path. `wg show` is useful for interface and peer state without printing the private key. None of these checks proves that no backup or other copy was exposed.

کلید و پیکربندی را یکی نگیر

پیکربندی رو می‌شه backup کرد، اما باید مشخص باشه کدوم بخش راز هست، backup کجا رمزگذاری و نگهداری می‌شه و کی حق restore داره. آرشیو ساده‌ای که private key رو کنار فایل‌های معمولی می‌ذاره، backup امن نیست.

Configuration can be backed up, but identify secret fields, where the backup is encrypted and stored, and who may restore it. A plain archive that places a private key beside ordinary files is not a secure backup.

هر peer باید فقط به مقصد لازم برسهEach peer should reach only the destinations it needs

`AllowedIPs` در WireGuard فقط یک فهرست تزئینی نیست: برای هر peer مشخص می‌کنه چه IPهایی از اون peer پذیرفته بشن و در سمت client معمولاً مسیرهای قابل‌هدایت از tunnel رو هم می‌سازه. `0.0.0.0/0` یعنی همهٔ IPv4ها؛ اون رو فقط وقتی انتخاب کن که full tunnel واقعاً خواسته شده و DNS، مسیر endpoint و قانون خروجی رو هم طراحی کرده‌ای. دسترسی به یک subnet داخلی رو با یک default route اشتباه نگیر.

`AllowedIPs` in WireGuard is not merely descriptive: it identifies which IPs are accepted from each peer and, on a client, commonly installs routes for destinations sent through the tunnel. `0.0.0.0/0` means all IPv4 destinations. Use it only when a full tunnel is intentional and DNS, endpoint reachability, and egress policy are designed too. Do not confuse access to one internal subnet with a default route.

ip route get 10.44.0.10
ip route get 1.1.1.1
sudo wg show wg0 allowed-ips

اگه مقصد داخلی باید از tunnel بره و اینترنت مستقیم بمونه، دو lookup باید مسیرهای متفاوت و مورد انتظار بدهند. با این حال route درست به‌تنهایی مجوز دسترسی یا firewall رو ثابت نمی‌کنه؛ سمت سرور، ACL سرویس و برگشت پاسخ رو هم بررسی کن.

If an internal destination should use the tunnel while ordinary internet stays direct, the two lookups should show the intended different routes. A correct route does not prove authorization or firewall access; check server-side policy, service ACLs, and the return path too.

پروکسی سالم هست؛ آیا ناخواسته برای همه بازش کرده‌ایم؟The proxy works—did we accidentally open it to everyone?

در فصل‌های قبل proxy محلی رو با loopback آزمایش کردیم. اگه همون سرویس روی `0.0.0.0` یا IP عمومی گوش کند و احراز هویت یا ACL نداشته باشه، ممکنه هر کاربر اینترنت از پهنای باند و IP تو برای ترافیک خودش استفاده کند؛ abuse گزارش و هزینه‌اش برای تو می‌مونه. قبل از تغییر، شاهد جمع کن: روی کدوم address و port گوش می‌ده؟ firewall چه اجازه‌ای می‌ده؟ یک درخواست از شبکهٔ مجاز و یکی از مسیر غیرمجاز چه نتیجه‌ای دارن؟

Earlier chapters tested a local proxy on loopback. If the same service listens on `0.0.0.0` or a public IP without authentication or ACLs, internet users may route their traffic through your bandwidth and address; abuse reports and costs land on you. Before changing anything, gather evidence: which address and port are listening, what does the firewall allow, and what happens from an authorized versus unauthorized path?

sudo ss -lntup
sudo nft list ruleset
curl --max-time 3 -x http://127.0.0.1:8080 http://example.test/

فرمان `ss` محل گوش‌دادن processها رو نشان می‌ده؛ `nft` rules فعال رو. درخواست محلی فقط ثابت می‌کنه proxy روی همون میزبان پاسخ می‌ده، نه اینکه دسترسی بیرونی محدود شده. آزمایش دسترسی بیرونی رو فقط از یک VM یا شبکهٔ موقتی خودت انجام بده؛ پورت عمومی رو برای «دیدن چه می‌شه» باز نکن.

`ss` shows where processes listen; `nft` shows active rules. A local request proves only that the proxy responds on that host, not that external access is restricted. Test external access only from your own disposable VM or network; never expose a public port just to see what happens.

الگوی پیش‌فرض امن‌تر

proxy مدیریتی رو روی loopback یا شبکهٔ خصوصی bind کن؛ ACL رو بر اساس clientهای مشخص ببند؛ firewall ورودی رو محدود نگه دار و اگه سرویس عمومی هست، احراز هویت و rate limit متناسب با همون پیاده‌سازی اضافه کن. rate limit جای ACL یا احراز هویت رو نمی‌گیره.

Bind an administrative proxy to loopback or a private network, restrict ACLs to known clients, keep inbound firewall rules narrow, and add authentication and implementation-appropriate rate limits for a public service. Rate limiting does not replace access control or authentication.

نکتهٔ مهم: «VPN وصل هست» مساوی «کاربر فقط منابع لازم رو می‌بینه» نیست. با route محدود، firewall مقصد، جداسازی دسترسی ادمین و قانون هر سرویس، توان هر peer رو جداگانه کوچک کن.

A connected VPN does not mean the user can see only the resources they need. Narrow each peer’s reach with routes, destination firewalls, separate admin access, and service-specific policy.

سخت‌سازی یک‌بار انجام نمی‌شهHardening is not a one-time setting

proxy، OpenVPN، WireGuard، سیستم‌عامل و کتابخانه‌هایشان تغییر می‌کنن. نسخهٔ نصب‌شده رو با package manager و release note رسمی بررسی کن؛ patch رو اول در آزمایشگاه بالا بیاور، بعد اتصال، route و لاگ رو verify کن و تازه سپس زمان تغییر production رو انتخاب کن. `latest` یا یک شمارهٔ قدیمی در یادداشت‌ها، برنامهٔ به‌روزرسانی نیست.

Proxies, OpenVPN, WireGuard, operating systems, and their libraries change. Check installed versions through the package manager and official release notes; test patches in a lab, verify connection, routes, and logs, then schedule production changes. `latest` or an old version number in notes is not an update plan.

دسترسی مدیریتی رو هم از ترافیک کاربران جدا کن: فقط پورت لازم رو برای SSH یا کنسول مدیریت باز بذار، کلید مدیریتی رو میان چند نفر share نکن، و برای هر اپراتور هویت جدا داشته باش. اگه peer یا certificate دیگر لازم نیست، اون رو revoke کن و با تلاش مجدد مطمئن شو credential قبلی کار نمی‌کنه.

Separate administration from user traffic: expose only the required management port, do not share one admin key among people, and give operators distinct identities. Revoke a peer or certificate when it is no longer needed, then confirm the old credential no longer connects.

لاگ رو برای تشخیص نگه دار، نه برای جمع‌کردن همه‌چیز. private key، رمز و payload رو واردش نکن؛ endpoint و هویت دستگاه هم ممکنه حساس باشن. زمان نگهداری، دسترسی خواندن و سقف دیسک باید معلوم باشه. restore تنظیمات رو هم فقط در محیط مجاز تمرین کن تا backup قدیمی ناخواسته peer باطل‌شده رو دوباره فعال نکند.

Keep logs to diagnose, not to collect everything. Do not log private keys, passwords, or payload; endpoints and device identity may also be sensitive. Define retention, read access, and disk limits. Test configuration restores only in an authorized environment so an old backup does not silently reactivate a revoked peer.

lab: proxy رو عمدی بیش‌ازحد باز کن، اما فقط داخل VMLab: deliberately overexpose a proxy, but only inside a VM

این تمرین رو روی VM محلی و شبکهٔ host-only انجام بده؛ نه روی VPS عمومی، Wi‑Fi محل کار یا شبکهٔ شخص دیگری. از proxy آزمایشگاهی فصل ۴ استفاده کن و پیش از روشن‌کردنش دو شاهد ثبت کن: تنظیم bind/ACL و خروجی `ss -lntp`. اگه پیاده‌سازی فصل ۴ آرگومان bind نداره، تنظیم همون فایل رو در VM تغییر بده؛ دستور تازه‌ای رو که در اون برنامه وجود نداره جعل نکن.

Use a local VM on a host-only network—not a public VPS, workplace Wi-Fi, or someone else’s network. Reuse the Chapter 4 lab proxy and record two facts before starting: its bind/ACL configuration and `ss -lntp` output. If that implementation has no bind argument, change its configuration in the VM; do not invent a command-line option it does not support.

نسخهٔ عمداً بد رو فقط روی IP شبکهٔ host-only گوش بده و از client دوم خودت درخواست بفرست. ثبت کن proxy چه addressی نشان می‌ده، کدوم client جواب می‌گیره و آیا ACL در کار هست. اگه VMت شبکهٔ host-only نداره، این بخش رو فقط با نگاه‌کردن به پیکربندی بخوان و سرویس رو روی host عمومی اجرا نکن.

Make the intentionally weak version listen only on the host-only VM address, then send a request from your own second client. Record the listening address, which client receives a response, and whether an ACL applies. If your VM has no host-only network, inspect the configuration only; do not run the service on a public host.

حالا علت رو از شواهد تشخیص بده: bind روی همهٔ interfaceهای VM هست؟ ACL تهی هست؟ firewall آزمایشگاه اجازه داده؟ تنها یک مورد رو تغییر بده—مثلاً bind رو به interface خصوصی محدود کن و ACL client رو اضافه کن—بعد `ss` و دو درخواست رو دوباره اجرا کن. موفقیت باید از client مجاز پاسخ بگیره و از client خارج از محدوده رد بشه. خاموش‌کردن proxy هم بخشی از cleanup هست.

Diagnose from evidence: is it bound to every VM interface, is the ACL empty, or did the lab firewall permit access? Change one thing—such as binding to the private interface and adding a client ACL—then rerun `ss` and both requests. Success means the allowed client works and the out-of-scope client is denied. Shutting the proxy down is part of cleanup.

۱۸ تمرین؛ کوچک‌کردن دامنهٔ آسیب18 exercises: reduce the blast radius

۱. فایل کلید

`stat` برای فایل WireGuard مقدار `644` نشان می‌ده. چه خطری می‌بینی و پیش از تغییر چی رو بررسی می‌کنی؟

`stat` shows mode `644` for a WireGuard file. What is the risk, and what do you check before changing it?

پاسخ

هر user محلی می‌تونه بخونه. اول ببین فایل واقعاً private key داره یا نه، مالک درست کیست و سرویس با کدوم user اجرا می‌شه؛ بعد دسترسی رو محدود کن و دسترسی daemon رو دوباره بیازما.

Any local user can read it. First determine whether it contains a private key, who should own it, and which user runs the service; then restrict access and verify the daemon can still read it.

۲. فقط chmod؟

پس از `chmod 600`، سرویس نمی‌تونه config رو بخونه. کدوم شاهد بعدی مفید هست؟

After `chmod 600`, the service cannot read its config. Which evidence do you inspect next?

پاسخ

owner/group و permission همهٔ parent directoryها رو با `stat` و `namei -l` ببین؛ فقط mode فایل رو حدس نزن. سپس با همون user سرویس، خواندن مجاز رو verify کن.

Check owner/group and every parent directory with `stat` and `namei -l`; do not guess from the file mode alone. Verify access as the service user.

۳. کلید وارد Git شد

private key رو از فایل حذف کردی و commit تازه ساختی. آیا credential دیگر امن هست؟ چرا؟

You removed a private key from the file and made a new commit. Is the credential safe now? Why?

پاسخ

نه؛ تاریخچه، clone و backup ممکنه نسخه رو نگه دارن. کلید رو revoke/rotate کن، دسترسی قبلی رو حذف و credential تازه رو جداگانه verify کن؛ پاک‌کردن تاریخچه به‌تنهایی کافی نیست.

No. History, clones, and backups may retain it. Revoke/rotate the key, remove the old authorization, and verify a new credential; history cleanup alone is insufficient.

۴. route خاص یا همهٔ اینترنت؟

کارمند فقط باید به `10.44.0.0/16` برسه، اما client config شامل `0.0.0.0/0` هست. چی باید روشن بشه؟

An employee needs only `10.44.0.0/16`, but the client config has `0.0.0.0/0`. What must be clarified?

پاسخ

آیا full tunnel عمداً خواسته شده؟ اگه نه، AllowedIPs و route رو محدود به subnet لازم کن و route lookup برای مقصد داخلی و اینترنت رو جدا مقایسه کن.

Was a full tunnel intentional? If not, narrow AllowedIPs/routes to the required subnet and compare route lookups for internal and internet destinations.

۵. route درست

`ip route get` مقصد رو از `wg0` می‌فرسته، ولی اتصال رد می‌شه. آیا مجازبودن دسترسی ثابت شد؟

`ip route get` sends the destination through `wg0`, but the connection is rejected. Is authorization proven?

پاسخ

نه؛ route انتخاب مسیر هست. firewall، AllowedIPs سمت peer، قانون مقصد، port سرویس و برگشت packet رو بررسی کن.

No. A route selects a path. Check firewall, peer-side AllowedIPs, destination policy, service port, and the return packet path.

۶. روی 0.0.0.0

proxy روی `0.0.0.0:8080` گوش می‌ده. پیش از بستن سرویس، چه دو مدرکی جمع می‌کنی؟

A proxy listens on `0.0.0.0:8080`. Which two pieces of evidence do you gather before shutting it down?

پاسخ

با `ss` bind واقعی و process رو ثبت کن؛ سپس ACL/firewall مؤثر و درخواست از clientهای مجاز و خارج از محدوده رو در آزمایشگاه کنترل‌شده بسنج. روی اینترنت عمومی آزمایش نکن.

Record the process and actual bind with `ss`, then inspect effective ACL/firewall and test in-scope and out-of-scope clients in a controlled lab. Do not test against the public internet.

۷. فایروال خاموش؟

برای debug، firewall سرور رو خاموش می‌کنی و «درست شد». این نتیجه چی رو ثابت نمی‌کنه؟

You turn off the server firewall to debug and “it works.” What does that result fail to prove?

پاسخ

علت دقیق rule یا مرز دسترسی رو مشخص نمی‌کنه و سرویس رو بیش‌ازحد در معرض گذاشته. در آزمایشگاه rule لازم رو جدا پیدا کن و فقط همون پورت، مبدأ و جهت رو مجاز کن؛ firewall رو به‌عنوان راه‌حل خاموش نگذار.

It does not identify the exact rule or access boundary and may expose too much. In a lab, isolate the required rule and allow only the needed port, source, and direction; do not leave the firewall disabled.

۸. احراز هویت کافی نیست

proxy کاربر و رمز داره، اما هر مقصد اینترنتی رو می‌پذیرد و request limit نداره. دو کنترل مکمل پیشنهاد بده.

The proxy has username/password but allows every internet destination and has no request limit. Suggest two complementary controls.

پاسخ

destination ACL برای محدودکردن مقصدها و rate/concurrency limit متناسب با پیاده‌سازی. احراز هویت، اجازهٔ هر مقصد یا مقاومت در برابر مصرف بی‌رویه رو به‌تنهایی حل نمی‌کنه.

Use destination ACLs and implementation-appropriate rate/concurrency limits. Authentication alone does not authorize every destination or prevent excessive use.

۹. از کدام شبکه می‌شود وصل شد؟

`ss` آدرس `127.0.0.1:3128` رو نشان می‌ده. چه نتیجه‌ای می‌گیری و چی هنوز معلوم نیست؟

`ss` shows `127.0.0.1:3128`. What can you conclude, and what remains unknown?

پاسخ

process روی loopback IPv4 همین host گوش می‌ده؛ این خروجی به‌تنهایی socketهای دیگر، firewall، IPv6 یا دسترسی از container/network دیگر رو رد نمی‌کنه. همهٔ bindها و مسیر واقعی client رو هم بررسی کن.

The process listens on this host’s IPv4 loopback. That does not rule out other sockets, firewall paths, IPv6, or access from another container/network. Inspect all listeners and the client’s actual route.

۱۰. peer دیگر لازم نیست

گوشی کارمند از دست رفته هست. فقط config رو از پنل او پاک می‌کنی؟

An employee’s phone is lost. Is deleting its local config from the admin portal enough?

پاسخ

نه؛ peer/certificate رو سمت سرویس revoke کن، key یا credential رو rotate کن اگه احتمال کپی هست، و با همون credential قبلی اتصال رو در محیط مجاز ردشده ببین.

No. Revoke the peer/certificate server-side, rotate the key if it may have been copied, and verify the old credential is rejected in an authorized test.

۱۱. patch امن

نسخهٔ جدید proxy منتشر شده. چه ترتیبی ریسک تغییر رو کم می‌کنه؟

A new proxy release is available. What sequence reduces change risk?

پاسخ

release note و اثر نسخه رو بررسی کن؛ در آزمایشگاه update کن؛ listener، ACL، اتصال و log رو بیازما؛ backup تنظیماتِ بدون رازهای قابل‌افشای plain بگیر و زمان/راه rollback رو معلوم کن.

Review release notes and impact, update a lab, test listener, ACL, connectivity, and logs, back up configuration safely, and define a change window and rollback path.

۱۲. backup config

backup تنظیمات در پوشه‌ای با permission `755` هست و private key هم داخل اون هست. قدم بعدی چیه؟

A configuration backup with private keys is in a `755` directory. What is the next action?

پاسخ

فرض کن راز افشا شده: دسترسی backup رو محدود کن، keyهای در معرض رو rotate/revoke کن، تاریخچهٔ دسترسی رو بررسی کن و backup رمزگذاری‌شده با مالک و retention مشخص بساز. فقط پوشه رو chmod کردن اثر کپی‌های قبلی رو از بین نمی‌برد.

Treat the secret as exposed: restrict backup access, rotate/revoke exposed keys, review access history, and create an encrypted backup with clear ownership and retention. Changing directory mode does not erase prior copies.

۱۳. log پر از جزئیات

برای troubleshooting، request URL، username و تمام headerها رو log می‌کنی. کدوم بخش‌ها رو نگه می‌داری؟

For troubleshooting, you log request URLs, usernames, and every header. What should remain?

پاسخ

فقط metadata حداقلی لازم برای سؤال عملیاتی؛ authorization/cookie و payload رو حذف کن، شناسه‌ها رو در صورت امکان pseudonymize کن و retention/access رو مشخص کن. نمونهٔ تولیدی رو پیش از اشتراک پاک‌سازی کن.

Keep only metadata needed for the operational question; remove authorization/cookies and payload, pseudonymize identifiers where possible, and define access/retention. Redact real samples before sharing.

۱۴. admin از همان proxy

پنل مدیریتی روی همون listener عمومی proxy هست و با رمز قوی محافظت می‌شه. چه دفاع لایه‌ای اضافه می‌کنی؟

The admin panel shares the public proxy listener and has a strong password. What layered defense would you add?

پاسخ

پنل رو به loopback/private management network جدا کن، source ACL یا VPN مدیریتی بذار، هویت‌های شخصی/MFA متناسب اضافه کن و پورت public رو فقط برای کاربرهای نهایی نگه دار.

Move it to loopback or a private management network, add source ACL or a management VPN, use individual identities and suitable MFA, and reserve public exposure for user traffic.

۱۵. update و peer منقضی

سرویس patch شد و handshake تازه هست؛ آیا peer قدیمی که دیگر عضو تیم نیست حذف شده؟

The service is patched and a peer has a recent handshake. Does that prove the former team member’s peer was removed?

پاسخ

نه؛ نسخه و availability، فهرست authorization رو ثابت نمی‌کنن. peerها رو با inventory هویت‌ها تطبیق بده و برای حذف‌شده‌ها نبودن key/certificate رو جدا بررسی کن.

No. Version and availability do not establish authorization inventory. Reconcile peers with identities and separately verify removed users’ keys/certificates are absent.

۱۶. آزمون بیرونی امن

می‌خوای ثابت کنی listener عمومی نیست. چرا `curl` از همون VM کافی نیست و چه روش امنی داری؟

You want to prove a listener is not public. Why is `curl` from the same VM insufficient, and what is a safe test?

پاسخ

loopback مسیر ورودی شبکه رو دور می‌زند. از client دوم تحت مالکیت خودت روی host-only VM یا محیط staging استفاده کن؛ در کنار اون listener و firewall رو هم بررسی کن، نه اینکه پورت آزمایشی رو به اینترنت باز کنی.

Loopback bypasses the inbound network path. Use a second client you control on a host-only VM or staging network, alongside listener and firewall checks; do not expose a test port to the internet.

۱۷. گزارش پایش قابل اشتراک

از `wg show` و log سرویس خروجی می‌گیری. پیش از فرستادن برای همکار چه چیزهایی رو مرور می‌کنی؟

You export `wg show` and service logs. What do you review before sending them to a colleague?

پاسخ

private key، endpoint، IP داخلی، username، زمان‌ها و شناسه‌های قابل‌پیوند رو بررسی/پوشانده کن؛ payload رو حذف کن و فقط بازهٔ لازم رو با کانال مجاز بفرست. راز رو برای کمک گرفتن عمومی paste نکن.

Review private keys, endpoints, internal IPs, usernames, timestamps, and linkable identifiers; remove payload and share only the necessary interval through an approved channel. Never paste secrets into a public help request.

۱۸. تصمیم سخت‌سازی

یک peer لازمه به یک API داخلی برسه و گاهی درخواستش کند هست. سه کنترل امنیتی انتخاب کن و بگو با چه مدرکی می‌فهمی هرکدوم کار می‌کنه؛ سرعت رو با بازکردن همهٔ routeها درست نکن.

A peer needs one internal API and sometimes sees slow requests. Choose three security controls and state the evidence for each; do not “fix” speed by opening every route.

معیار پاسخ

نمونه: route/AllowedIPs محدود و `ip route get`؛ firewall مقصد و آزمون port مجاز/غیرمجاز؛ credential اختصاصی با revoke test. کندی رو جدا با latency، MTU و counters بررسی کن تا کنترل امنیتی رو بی‌دلیل کنار نگذاری.

For example: narrow AllowedIPs/routes verified with `ip route get`; destination firewall checked with allowed/denied port tests; an individual credential verified with a revocation test. Diagnose slowness separately using latency, MTU, and counters rather than weakening access controls.

سخت‌سازی یعنی سؤال درست، بعد شاهدHardening starts with the right question, then evidence

برای هر مسیر بپرس: کی وارد می‌شه؟ کدوم هویت رو ثابت می‌کنه؟ تا کجا می‌تونه route بگیره؟ کجا key نگهداری می‌شه؟ و اگه اون key لو رفت، چطور دسترسی رو واقعاً revoke می‌کنیم؟ بعد با listener، قانون، permission، route و آزمون مجاز/غیرمجاز جواب رو ثابت کن. «رمز قوی هست» یا «VPN بالاست» به‌تنهایی مرز امنیتی نمی‌سازه.

For every path, ask: who can enter, which identity proves it, how far can it route, where is the key stored, and how do we actually revoke access if it leaks? Then verify with listeners, policy, permissions, routes, and allowed/denied tests. “The password is strong” or “the VPN is up” does not establish a security boundary.

در پروژهٔ بعدی یک HTTP proxy کوچک می‌سازیم. حالا می‌دونیم پیش از اینکه اون رو به شبکه وصل کنیم، باید تصمیم بگیریم کجا گوش بدهد، چه clientی اجازه داشته باشه و چطور مطمئن شویم ناخواسته به proxy باز تبدیل نشده.

Next, we build a small HTTP proxy. Before connecting it to a network, we now know to decide where it listens, which clients are allowed, and how to verify it has not become an open proxy.
