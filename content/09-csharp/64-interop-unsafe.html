Interop، P/Invoke و unsafe

Interop, P/Invoke and unsafe code

تیم کتابخانهٔ native آماده‌ای دارد و می‌خواهد تابع C را صدا بزند؛ امضای C# شبیه به نظر می‌رسد، اما برنامه روی Linux crash می‌کند. مرز managed/native قرارداد دقیق ABI است: اندازه و layout، encoding، ownership، calling convention و عمر pointer. `unsafe` این قرارداد را حذف نمی‌کند؛ فقط مسئولیت بیشتری به برنامه‌نویس می‌دهد.

The team has a native library and wants to call a C function. The C# signature looks plausible, but the app crashes on Linux. The managed/native boundary is an exact ABI contract: size and layout, encoding, ownership, calling convention and pointer lifetime. `unsafe` does not remove that contract; it gives the programmer more responsibility.

اول header و ABI واقعی را بخوانStart with the real header and ABI

از امضای C# حدس نزن. header native می‌گوید تابع چه نوع‌هایی می‌گیرد، ownership خروجی با کیست، string چه encoding دارد، خطا چطور گزارش می‌شود و تابع state یا callback نگه می‌دارد یا نه. معادل‌های type را با platform و ABI بررسی کن: `int` C معمولاً به `int`، `size_t` به `nuint`، و `uint8_t*` به byte buffer اشاره دارد؛ اما typedefها و calling convention را باید از header و docs همان library تأیید کرد.

Do not guess from the C# signature. The native header defines parameter types, output ownership, string encoding, error reporting and whether state/callbacks are retained. Map types against the target platform and ABI: C `int` commonly maps to C# `int`, `size_t` to `nuint`, and `uint8_t*` to a byte buffer—but confirm typedefs and calling convention from the library's header and documentation.

قرارداد native نمونه / Example native contract
// native header (illustrative)
// int transform(const uint8_t* input, size_t length, uint8_t* output);
// Caller owns input/output buffers; function retains neither pointer.

این comment فقط شکل مسئله را نشان می‌دهد، نه API واقعی. تفاوت `char*` با `wchar_t*`، null termination و UTF-8/UTF-16 می‌تواند نتیجه را عوض کند. struct هم ممکن است alignment/padding متفاوت داشته باشد؛ `StructLayout` را فقط بر اساس سند native تنظیم کن.

This comment illustrates the shape, not a real API. `char*` versus `wchar_t*`, null termination and UTF-8/UTF-16 can change behavior. Struct alignment and padding may differ too; configure StructLayout only from native documentation.

برای .NET 7+، LibraryImport را در صورت پشتیبانی ترجیح بدهPrefer LibraryImport on .NET 7+ when supported

LibraryImport برای signatureهای پشتیبانی‌شده marshalling code را هنگام compile تولید می‌کند؛ نیاز به stub runtime را کم می‌کند و برای trimming/AOT کمک‌کننده است. متد باید static و partial باشد و پروژه امکان unsafe generated code را بدهد. همهٔ marshallingهای قدیمی پشتیبانی نمی‌شوند؛ diagnostics generator را بخوان و وقتی signature پیچیده/پشتیبانی‌نشده است از روش مناسب مستندشده استفاده کن. `DllImport` هنوز برای بعضی موارد معتبر است.

For supported signatures, LibraryImport generates marshalling code at compile time, reducing runtime stub generation and helping trimming/AOT scenarios. The method is static and partial, and the project must allow generated unsafe code. Not every legacy marshalling pattern is supported; read generator diagnostics and use a documented alternative for unsupported signatures. `DllImport` remains valid for some cases.

P/Invoke source-generated / Source-generated P/Invoke
<PropertyGroup>
  <AllowUnsafeBlocks>true</AllowUnsafeBlocks>
</PropertyGroup>

internal static partial class Native
{
    [LibraryImport("transform", EntryPoint = "transform")]
    internal static partial int Transform(
        byte[] input, nuint length, byte[] output);
}

signature بالا تا وقتی native contract با array marshalling سازگار نباشد نمونهٔ قابل‌کپی نیست؛ برای bufferهای ورودی/خروجی direction و طول را دقیق annotate یا API امن‌تر با Span بساز. نام library در Windows، Linux و macOS متفاوت است؛ resolution و packaging native library را جدا verify کن.

The signature is not copy-ready unless the native contract supports array marshalling; annotate direction and length precisely or build a safer Span wrapper. Library naming differs across Windows, Linux and macOS; verify native library resolution and packaging separately.

marshalling تبدیل نوع است، نه حدس خودکارMarshalling transforms types; it is not guesswork

managed string ممکن است برای native به UTF-8، UTF-16 یا رشتهٔ null-terminated تبدیل شود. bool managed و bool native هم لزوماً representation یکسان ندارند؛ struct، enum و array هم همین‌طور. مرز را با contract واقعی annotate کن و output را روی هر OS/architecture هدف تست کن. یک signature درست روی Windows تضمین نمی‌کند روی Linux یا ARM هم درست باشد.

A managed string may need conversion to UTF-8, UTF-16 or a null-terminated native string. Managed and native bool representations may differ, as can structs, enums and arrays. Annotate the boundary from the actual contract and test each target OS/architecture. A signature working on Windows does not guarantee it works on Linux or ARM.

encoding باید صریح باشد / Make string encoding explicit
[LibraryImport("native_text", EntryPoint = "normalize",
    StringMarshalling = StringMarshalling.Utf8)]
internal static partial int NormalizeUtf8(string input);

این signature فقط وقتی درست است که native function واقعاً UTF-8 null-terminated یا قرارداد متناظر را انتظار داشته باشد؛ APIای که `char*` را به binary bytes تعبیر می‌کند چنین نیست. اگر buffer native خروجی را تخصیص می‌دهد، مشخص کن با کدام allocator و کدام تابع آزاد می‌شود؛ managed GC آن حافظه را خودکار آزاد نمی‌کند.

This signature is correct only if the native function really expects the corresponding UTF-8 string contract; a function treating `char*` as binary bytes does not. If native code allocates output, identify its allocator and matching free function; the managed GC does not release that memory automatically.

handle را با SafeHandle مدیریت کنManage handles with SafeHandle

native handle مثل file descriptor یا opaque context باید یک‌بار و با تابع درست آزاد شود، حتی وقتی exception رخ می‌دهد. SafeHandle lifetime و finalization ایمن‌تری فراهم می‌کند و از نگه‌داشتن خام IntPtr در سراسر برنامه بهتر است. ownership را از API بخوان: بعضی تابع‌ها handle را transfer می‌کنند، بعضی borrow می‌کنند و بعضی caller را مسئول close می‌دانند.

A native handle such as a file descriptor or opaque context must be released exactly once with the correct function, including after exceptions. SafeHandle provides safer lifetime/finalization than passing raw IntPtr throughout an application. Read ownership from the API: some functions transfer a handle, others borrow it, and some make the caller responsible for closing it.

wrapper handle / SafeHandle wrapper
sealed class NativeContextHandle : SafeHandle
{
    private NativeContextHandle() : base(IntPtr.Zero, ownsHandle: true) { }

    public override bool IsInvalid => handle == IntPtr.Zero;

    protected override bool ReleaseHandle()
    {
        NativeClose(handle);
        return true;
    }
}

نوع تابع close در این نمونه فرضی است؛ در محصول واقعی calling convention، return code و failure semantics را مطابق header پیاده کن. `ReleaseHandle` باید ساده و قابل‌اعتماد باشد و exception پرتاب نکند. اگر handle از native API به دست می‌آید، constructor/factory را طوری طراحی کن که instance نامعتبر یا ownership مبهم ساخته نشود.

The close function here is illustrative; match calling convention, return code and failure semantics to the real header. Keep ReleaseHandle reliable and non-throwing. If a handle comes from a native API, design a factory so invalid instances and ambiguous ownership are avoided.

unsafe و fixed فقط به اندازهٔ لازم و در کمترین scopeUse unsafe and fixed only as long as needed

GC می‌تواند array را جابه‌جا کند؛ pointer خام به آن فقط وقتی معتبر است که memory pin شده باشد. fixed تضمین را فقط در محدودهٔ block می‌دهد؛ pointer را بیرون نبر و native code را از نگه‌داشتنش منع کن، مگر lifetime pinning جدا و درست طراحی شده باشد. pin طولانی باعث fragmentation و فشار heap می‌شود. برای عملیات sync، API مبتنی بر Span معمولاً مرز امن‌تری می‌دهد.

The GC can move arrays; a raw pointer to one is valid only while memory is pinned. fixed guarantees stability only within its block; do not let the pointer escape or allow native code to retain it unless a separate correct pinning lifetime is designed. Long pinning can fragment the heap. For synchronous operations, a Span-based API usually offers a safer boundary.

pointer فقط در block / Pointer limited to the block
unsafe static int Hash(ReadOnlySpan<byte> input)
{
    fixed (byte* p = input)
    {
        return NativeHash(p, (nuint)input.Length);
    } // native code must not retain p
}

متد native در مثال باید synchronous باشد و pointer را پس از return نگه ندارد. اگر native API کار async می‌کند و pointer را بعداً مصرف می‌کند، این الگو نادرست است؛ باید ownership و pinning lifetime مستقل طراحی شود. برای صفر طول هم native contract ممکن است pointer null یا non-null بخواهد؛ همان را بررسی کن.

The native method must be synchronous and must not retain the pointer after returning. If a native API works asynchronously and consumes the pointer later, this pattern is invalid; design a separate ownership and pinning lifetime. For zero length, the native contract may require a null or non-null pointer; verify it.

خطای native را با OS و معماری بازتولید کنReproduce native failures across OS and architecture

`EntryPointNotFoundException` یعنی export/نام entry point یا نسخه را بررسی کن؛ `DllNotFoundException` ممکن است خود library یا dependency native آن باشد؛ `BadImageFormatException` می‌تواند معماری ناسازگار یا فایل نامعتبر باشد. اما crash در مرز native ممکن است process را بدون managed exception تمام کند. نسخهٔ library، ABI، architecture، dependency chain، encoding و last-error را ثبت کن و کمینهٔ تست را در target واقعی اجرا کن.

`EntryPointNotFoundException` points to export name or library version; `DllNotFoundException` can mean the library or one of its native dependencies is missing; `BadImageFormatException` can indicate an architecture mismatch or invalid binary. A native boundary crash may terminate the process without a managed exception. Record library version, ABI, architecture, dependency chain, encoding and last error, then run a minimal test on the real target.

گرفتن last error / Capture the native error
[LibraryImport("native_io", SetLastError = true)]
internal static partial int ReadNative(SafeFileHandle handle);

int result = ReadNative(handle);
if (result < 0)
{
    int error = Marshal.GetLastPInvokeError();
    throw new IOException($"Native read failed ({error}).");
}

نحوهٔ گزارش خطا تابع قرارداد native است؛ همهٔ APIها errno یا GetLastError را تنظیم نمی‌کنند و return code ممکن است خودش error را حمل کند. SetLastError را فقط مطابق سند فعال کن. error را log کن ولی مسیر حساس و دادهٔ کاربر را بی‌دلیل وارد log نکن.

Error reporting follows the native contract; not every API sets errno/GetLastError, and a return code may carry the error itself. Enable SetLastError only when documented. Log useful error data without exposing sensitive paths or user data unnecessarily.

آزمایشگاه: wrapper امن برای یک C libraryLab: a safer wrapper around a C library

یک C library کوچک و بی‌خطر بساز که ورودی bytes و length بگیرد، checksum سادهٔ غیررمزنگارانه برگرداند و یک context handle داشته باشد. header را منبع حقیقت بگیر. در C# wrapper را جدا از منطق برنامه نگه دار؛ LibraryImport را برای signature پشتیبانی‌شده به‌کار ببر، type width و calling convention را تطبیق بده و handle را با SafeHandle مالک شو. Span را فقط در call synchronous و در fixed کوتاه pin کن؛ native نباید pointer را ذخیره کند. ورودی خالی، buffer کوتاه، خطای native، dispose تکراری و architecture ناسازگار را تست کن. CI را برای OSهای پشتیبانی‌شده اجرا و packageهای native را کنار artifact publish ثبت کن. هیچ pointer خامی را به API عمومی برنامه صادر نکن.

Build a small harmless C library that accepts bytes and a length, returns a non-cryptographic checksum and exposes a context handle. Treat the header as the source of truth. Keep the C# wrapper separate from application logic; use LibraryImport for a supported signature, match type widths/calling convention and own the handle with SafeHandle. Pin Span only briefly for a synchronous call; native code must not retain the pointer. Test empty input, short buffers, native errors, repeated disposal and architecture mismatch. Run CI on supported OSes and document native assets beside publish output. Never expose raw pointers through the application's public API.

  2. The wrapper documents and safely encapsulates ownership.
  3. هیچ pointer پس از fixed block مصرف نشود.
  4. No pointer is used after its fixed block.
  5. هر target پشتیبانی‌شده test و artifact native مشخص داشته باشد.
  6. Each supported target has tests and explicit native artifacts.

در مرز native، ownership و ABI از syntax مهم‌ترندAt the native boundary, ownership and ABI matter more than syntax

LibraryImport برای signatureهای پشتیبانی‌شده marshalling را source-generate می‌کند؛ encoding، struct layout، calling convention و platform را باید از contract گرفت. SafeHandle برای resourceهای handleدار مناسب است؛ fixed فقط pointer را در scope کوتاه ثابت نگه می‌دارد. هیچ‌کدام memory safety یا portability خودکار تضمین نمی‌کنند. با این فصل، مسیر اصلی C# به پروژه‌های پایانی می‌رسد: حالا ابزارها را در deliverableهای واقعی کنار هم می‌گذاریم.

LibraryImport source-generates marshalling for supported signatures, but encoding, struct layout, calling convention and platform behavior come from the contract. SafeHandle suits handle-based resources; fixed stabilizes a pointer only for a short scope. Neither guarantees memory safety or portability automatically.
