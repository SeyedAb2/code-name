متغیر، scope و مقدارههی

Variables, scope and definite assignment

یک متغیر رو داخل if تعریف کرده‌ای و بیرونش نمی‌تونی بخوانی. جای دیگری compiler می‌گه شاید قبل از مقدارههی استفاده‌اش کنی. این محدودیت‌ها سلیقه‌ای نیستن؛ کمک می‌کنن کد دربارهٔ عمر و مقدار داده دروغ نگوید.

You declared a variable inside an `if` and cannot read it outside. Elsewhere the compiler says it might be used before assignment. These rules are not arbitrary; they help code be honest about a value's lifetime and initialization.

یک سفارش، چند مقدار موقتOne order, a few temporary values

فرض کن قیمت رو حساب می‌کنی و چند خط پایین‌تر دوباره `total` می‌سازی. قبل از اینکه کلاس طراحی کنیم، ببینیم خود متغیر چه قولی به compiler می‌ده.

Suppose you calculate a price and create `total` again a few lines later. Before designing classes, let us see what a variable promises the compiler.

Program.cs
decimal subtotal = 125_000m;
decimal shipping = 15_000m;
decimal total = subtotal + shipping;
Console.WriteLine(total);
output
140000

`decimal` نوع داده هست، `subtotal` نامی در scope فعلی و `= 125_000m` مقدارههی اولیه هست. underscore خوانایی عدد رو بهتر می‌کنه و `m` پسوند literal اعشاری برای decimal هست. نقطهٔ اصلی فعلاً اینه که قبل از خواندن متغیر، مقدار مشخصی داده‌ایم.

`decimal` is the type, `subtotal` is a name in the current scope, and `= 125_000m` initializes it. Underscores improve numeric readability, and `m` marks a decimal literal. The key point for now is that the variable has a definite value before it is read.

scope رو وقتی می‌فهمی که یه اسم دیگه در دسترس نیستScope becomes real when a name is no longer available

تعریف scope با جملهٔ «محدودهٔ دسترسی متغیر» درست هست، ولی خیلی زود فراموش می‌شه. راه بهتر اینه که عمداً یه متغیر رو بیرون از block صدا بزنیم و بذاریم compiler اعتراض کنه. بعد دقیق نگاه کنیم چرا یه نام این‌طرف آکولاد زنده‌ست و اون‌طرف نه. compiler اینجا مزاحم نیست؛ داره جلوی وابستگی مبهم رو می‌گیره.

A definition such as “scope is where a variable is accessible” is correct but easy to forget. A better route is to use a variable outside its block on purpose and let the compiler object. Then inspect why the name exists on one side of the brace and not the other. The compiler is not being annoying; it is preventing an ambiguous dependency.

در ادامه هر جا متغیر تازه‌ای ساختی، فقط نوعش رو نبین. عمر و مالکیتش رو هم ببین: کجا ساخته شد، کجا آخرین بار معنی داره و آیا واقعاً لازمه از scope بزرگ‌تری دیده بشه؟ همین سؤال ساده بعداً روی closure، resource lifetime و concurrency هم برمی‌گرده.

From now on, when you introduce a variable, do not look only at its type. Look at its lifetime and ownership too: where was it created, where does it stop being meaningful, and does it really need a wider scope? The same question will return later with closures, resource lifetime, and concurrency.

اسم متغیر تا کجا دیده می‌شه؟How far can a variable name be seen?

یک متغیر داخل بلوک `{ }` تعریف کن و بیرون بلوک استفاده‌اش کن. compiler باید جلویش رو بگیرد، چون آن نام بیرون scope خودش تعریف نشده.

Declare a variable inside a `{ }` block and use it outside. The compiler should reject it because the name is not declared in that outer scope.

C#
if (subtotal > 100_000m)
{
    decimal discount = 5_000m;
}
Console.WriteLine(discount); // CS0103

نام `discount` فقط داخل بلوک if قابل‌استفاده هست. راه درست این نیست که هر چیزی رو بیرون تعریف کنیم؛ اول تصمیم بگیر آیا مقدار واقعاً در هر مسیر لازمه. اگه لازمه، آن رو بیرون تعریف و در همهٔ مسیرها مقدارههی کن؛ اگه نه، مصرف رو داخل همان scope نگه دار.

The name `discount` is available only inside the `if` block. The answer is not to declare everything outside: first decide whether the value is actually needed on every path. If it is, declare it outside and assign it on all paths; otherwise keep its use inside its scope.

چرا compiler متغیر بی‌مقدار رو نمی‌پذیره؟Why does the compiler reject an unassigned variable?

این نسخه رو امتحان کن: تخفیف فقط وقتی شرط درست هست مقدار می‌گیره. آیا compiler می‌تونه ثابت کند پیش از چاپ حتماً مقدار گرفته؟

Try this version: the discount is assigned only when the condition is true. Can the compiler prove it has a value before printing?

C#
decimal discount;
if (subtotal > 100_000m)
{
    discount = 5_000m;
}
Console.WriteLine(discount); // CS0165

اگه شرط false باشه، `discount` مقدار نگرفته؛ پس compiler خطای definite assignment می‌ده. این قاعده دربارهٔ localهاست؛ fieldهای یک شیء قاعدهٔ پیش‌فرض متفاوتی دارن و مقدار پیش‌فرض نوع می‌گیرن. این فرق رو با «متغیرها همیشه صفرند» تعمیم نده.

When the condition is false, `discount` has no value, so the compiler reports a definite-assignment error. This rule concerns locals; fields follow different default-initialization rules. Do not generalize it to “variables are always zero.”

یک راه روشن اینه که هر دو شاخه مقدار بدهند: `decimal discount = subtotal > 100_000m ? 5_000m : 0m;`. این expression خروجی داره و هیچ مسیر بی‌مقداری باقی نمی‌ذاره. هنوز سؤال business rule پابرجاست: آیا صفر واقعاً به معنی «تخفیف نداره» هست؟ نوع بهتر رو وقتی مدل دامنه رو می‌شناسیم انتخاب می‌کنیم.

One clear fix assigns both paths: `decimal discount = subtotal > 100_000m ? 5_000m : 0m;`. The expression produces a value on every path. A domain question remains: does zero really mean “no discount”? We can choose a better model once we know the domain.

var نوع رو حذف نمی‌کنهvar does not remove the type

گاهی سمت راست مقدار اولیه نوع رو روشن می‌کنه: `var orderCount = 3;`. این متغیر همچنان `int` هست. `var` یعنی compiler نوع رو از initializer استنتاج کند؛ نه اینکه نوع در runtime عوض بشه. برای متغیری که مقدار اولیه نداره نمی‌تونی همین شکل رو بنویسی.

Sometimes the initializer makes the type obvious: `var orderCount = 3;`. The variable is still an `int`. `var` asks the compiler to infer a type from the initializer; it does not create a run-time dynamic type. Without an initializer, this form cannot infer a type.

var رو برای خوانایی انتخاب کنChoose var for readability

اگه نوع از عبارت واضح هست، `var` تکرار رو کم می‌کنه؛ اگه خواننده باید برای فهم نوع چند فایل رو بگردد، نوع صریح کمک می‌کنه. این انتخاب سبک هست و type safety رو خاموش نمی‌کنه.

When the type is obvious, `var` avoids repetition; when readers would need to search elsewhere to learn it, an explicit type helps. This is a readability choice and does not disable type safety.
