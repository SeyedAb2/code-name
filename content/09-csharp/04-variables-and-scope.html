متغیر، scope و مقداردهی

Variables, scope and definite assignment

یک متغیر را داخل if تعریف کرده‌ای و بیرونش نمی‌توانی بخوانی. جای دیگری compiler می‌گوید شاید قبل از مقداردهی استفاده‌اش کنی. این محدودیت‌ها سلیقه‌ای نیستند؛ کمک می‌کنند کد دربارهٔ عمر و مقدار داده دروغ نگوید.

You declared a variable inside an `if` and cannot read it outside. Elsewhere the compiler says it might be used before assignment. These rules are not arbitrary; they help code be honest about a value's lifetime and initialization.

یک سفارش، چند مقدار موقتOne order, a few temporary values

فرض کن قیمت را حساب می‌کنی و چند خط پایین‌تر دوباره `total` می‌سازی. قبل از اینکه کلاس طراحی کنیم، ببینیم خود متغیر چه قولی به compiler می‌دهد.

Suppose you calculate a price and create `total` again a few lines later. Before designing classes, let us see what a variable promises the compiler.

Program.cs
decimal subtotal = 125_000m;
decimal shipping = 15_000m;
decimal total = subtotal + shipping;
Console.WriteLine(total);
output
140000

`decimal` نوع داده است، `subtotal` نامی در scope فعلی و `= 125_000m` مقداردهی اولیه است. underscore خوانایی عدد را بهتر می‌کند و `m` پسوند literal اعشاری برای decimal است. نقطهٔ اصلی فعلاً این است که قبل از خواندن متغیر، مقدار مشخصی داده‌ایم.

`decimal` is the type, `subtotal` is a name in the current scope, and `= 125_000m` initializes it. Underscores improve numeric readability, and `m` marks a decimal literal. The key point for now is that the variable has a definite value before it is read.

اسم متغیر تا کجا دیده می‌شود؟How far can a variable name be seen?

یک متغیر داخل بلوک `{ }` تعریف کن و بیرون بلوک استفاده‌اش کن. compiler باید جلویش را بگیرد، چون آن نام بیرون scope خودش تعریف نشده.

Declare a variable inside a `{ }` block and use it outside. The compiler should reject it because the name is not declared in that outer scope.

C#
if (subtotal > 100_000m)
{
    decimal discount = 5_000m;
}
Console.WriteLine(discount); // CS0103

نام `discount` فقط داخل بلوک if قابل‌استفاده است. راه درست این نیست که هر چیزی را بیرون تعریف کنیم؛ اول تصمیم بگیر آیا مقدار واقعاً در هر مسیر لازم است. اگر لازم است، آن را بیرون تعریف و در همهٔ مسیرها مقداردهی کن؛ اگر نه، مصرف را داخل همان scope نگه دار.

The name `discount` is available only inside the `if` block. The answer is not to declare everything outside: first decide whether the value is actually needed on every path. If it is, declare it outside and assign it on all paths; otherwise keep its use inside its scope.

چرا compiler متغیر بی‌مقدار را نمی‌پذیرد؟Why does the compiler reject an unassigned variable?

این نسخه را امتحان کن: تخفیف فقط وقتی شرط درست است مقدار می‌گیرد. آیا compiler می‌تواند ثابت کند پیش از چاپ حتماً مقدار گرفته؟

Try this version: the discount is assigned only when the condition is true. Can the compiler prove it has a value before printing?

C#
decimal discount;
if (subtotal > 100_000m)
{
    discount = 5_000m;
}
Console.WriteLine(discount); // CS0165

اگر شرط false باشد، `discount` مقدار نگرفته؛ پس compiler خطای definite assignment می‌دهد. این قاعده دربارهٔ localهاست؛ fieldهای یک شیء قاعدهٔ پیش‌فرض متفاوتی دارند و مقدار پیش‌فرض نوع می‌گیرند. این فرق را با «متغیرها همیشه صفرند» تعمیم نده.

When the condition is false, `discount` has no value, so the compiler reports a definite-assignment error. This rule concerns locals; fields follow different default-initialization rules. Do not generalize it to “variables are always zero.”

یک راه روشن این است که هر دو شاخه مقدار بدهند: `decimal discount = subtotal > 100_000m ? 5_000m : 0m;`. این expression خروجی دارد و هیچ مسیر بی‌مقداری باقی نمی‌گذارد. هنوز سؤال business rule پابرجاست: آیا صفر واقعاً به معنی «تخفیف ندارد» است؟ نوع بهتر را وقتی مدل دامنه را می‌شناسیم انتخاب می‌کنیم.

One clear fix assigns both paths: `decimal discount = subtotal > 100_000m ? 5_000m : 0m;`. The expression produces a value on every path. A domain question remains: does zero really mean “no discount”? We can choose a better model once we know the domain.

var نوع را حذف نمی‌کندvar does not remove the type

گاهی سمت راست مقدار اولیه نوع را روشن می‌کند: `var orderCount = 3;`. این متغیر همچنان `int` است. `var` یعنی compiler نوع را از initializer استنتاج کند؛ نه اینکه نوع در runtime عوض شود. برای متغیری که مقدار اولیه ندارد نمی‌توانی همین شکل را بنویسی.

Sometimes the initializer makes the type obvious: `var orderCount = 3;`. The variable is still an `int`. `var` asks the compiler to infer a type from the initializer; it does not create a run-time dynamic type. Without an initializer, this form cannot infer a type.

var را برای خوانایی انتخاب کنChoose var for readability

اگر نوع از عبارت واضح است، `var` تکرار را کم می‌کند؛ اگر خواننده باید برای فهم نوع چند فایل را بگردد، نوع صریح کمک می‌کند. این انتخاب سبک است و type safety را خاموش نمی‌کند.

When the type is obvious, `var` avoids repetition; when readers would need to search elsewhere to learn it, an explicit type helps. This is a readability choice and does not disable type safety.

۱) باگ scope را درست کن1) Fix the scope bug

در مثال discount، چاپ را داخل بلوک ببر و دوباره build کن. حالا توضیح بده چرا این تغییر درست است فقط وقتی مصرف discount هم باید وابسته به همان شرط باشد.

Move the print inside the discount block and build again. Explain why that change is correct only when using the discount should depend on the same condition.

پاسخ و توضیحSolution and explanation
C#
if (subtotal > 100_000m)
{
    decimal discount = 5_000m;
    Console.WriteLine(discount);
}

نام و مقدار فقط در شاخه‌ای که تخفیف وجود دارد دیده می‌شوند. اگر بعداً total بیرون بلوک باید از discount استفاده کند، این راه کافی نیست؛ باید مدل مقداردهی در هر مسیر را طراحی کنیم.

The name and value exist only in the branch where the discount applies. If a later total calculation needs the value outside, this is insufficient; assign a meaningful value on every path.

۲) همهٔ شاخه‌ها را مقداردهی کن2) Assign every branch

کد `decimal fee; if (isExpress) fee = 30m; Console.WriteLine(fee);` را اصلاح کن تا هر دو حالت مقدار داشته باشند. برنامه را با هر دو مقدار bool اجرا کن.

Fix `decimal fee; if (isExpress) fee = 30m; Console.WriteLine(fee);` so both cases have a value. Run with both Boolean values.

پاسخ و توضیحSolution and explanation
C#
decimal fee = isExpress ? 30m : 0m;
Console.WriteLine(fee);

برای false، fee صفر و برای true سی است. این مدل فرض می‌کند صفر یعنی بدون هزینه؛ اگر صفر مبلغ معتبر دیگری باشد، شاید nullable یا نوع دامنه‌ای روشن‌تری لازم باشد.

False yields zero and true yields thirty. This assumes zero means no fee; if zero is a meaningful amount, a nullable or more explicit domain type may be better.

۳) var واقعاً چه نوعی گرفت؟3) What type did var infer?

`var count = 3;` بساز و سپس `count = "سه";` را امتحان کن. build چه می‌گوید؟ نوع واقعی را از IDE یا compiler message پیدا کن.

Create `var count = 3;`, then try `count = "three";`. What does the build report? Confirm the inferred type in your IDE or compiler message.

پاسخ و توضیحSolution and explanation

initializer عدد صحیح، `count` را `int` می‌کند؛ رشته را نمی‌پذیرد و compile error می‌دهد. `var` حذف نوع نیست و مقدار بعدی هم نوع متغیر را عوض نمی‌کند.

The integer initializer makes `count` an `int`; assigning a string fails at compile time. `var` does not erase the type, and later values do not change it.

۴) مقدار صفر با «نداریم» فرق دارد؟4) Is zero different from “missing”?

قیمت تخفیف صفر را با «تخفیف محاسبه نشده» قاطی نکن. یک مدل runnable با `decimal?` بنویس که null یعنی هنوز محاسبه نشده و صفر یعنی محاسبه شده ولی تخفیف نداریم؛ هر دو حالت را چاپ کن.

Do not confuse a zero discount with “not calculated.” Write a runnable model using `decimal?` where null means not calculated and zero means calculated with no discount; print both cases.

پاسخ و توضیحSolution and explanation
C#
decimal? discount = null;
Console.WriteLine(discount is null ? "محاسبه نشده" : discount.Value);
discount = 0m;
Console.WriteLine(discount is null ? "محاسبه نشده" : discount.Value);

حالت اول null و حالت دوم صفر چاپ می‌شود. این نشان می‌دهد مقدار default یا صفر لزوماً جایگزین وضعیت «ناموجود» نیست. در فصل nullability شکل‌های خواناتر و امن‌تر دسترسی را می‌سازیم.

The first state is null and the second is zero. A default or zero value is not always a substitute for “missing.” The nullability chapter will develop safer, clearer access patterns.

۵) با compiler دربارهٔ خطا حرف بزن5) Use the compiler to classify a failure

دو نمونه بساز: یکی نام متغیر را داخل scope اشتباه بخواند، دیگری local را پیش از مقداردهی استفاده کند. خروجی build هرکدام را ثبت کن و تفاوت scope error و definite-assignment error را توضیح بده.

Create two cases: one reads a variable outside its scope, the other reads a local before assignment. Record each build diagnostic and explain the difference.

پاسخ و توضیحSolution and explanation

نام بیرون scope معمولاً CS0103 است: compiler آن شناسه را در این محدوده پیدا نمی‌کند. local بی‌مقدار معمولاً CS0165 است: نام شناخته شده اما compiler نمی‌تواند ثابت کند قبل از خواندن مقدار گرفته. هر دو compile-time هستند ولی علت و اصلاحشان فرق می‌کند.

An out-of-scope name commonly produces CS0103: the identifier is not found in this scope. An unassigned local commonly produces CS0165: the name exists, but the compiler cannot prove it was assigned before reading. Both are compile-time failures, but their causes differ.
