reflection، attribute و dynamic

Reflection, attributes and dynamic

فریم‌ورک باید handlerهایی را پیدا کند که نویسنده از قبل نمی‌شناسد. reflection این کشف را ممکن می‌کند؛ بعد تیم برای راحتی همه‌چیز را dynamic می‌کند و خطای تایپی از compile به production می‌رود. راه درست نه حذف ابزارهای runtime است و نه استفادهٔ همه‌جا؛ باید بدانیم metadata چه می‌دهد، کدام کار را cache کنیم و کجا type safety را حفظ کنیم.

A framework must discover handlers unknown to its author. Reflection makes this possible; then the team marks everything dynamic for convenience and moves a typo from compile time to production. The answer is neither banning runtime tools nor using them everywhere: understand metadata, cache repeated work and preserve type safety where possible.

reflection metadata برنامه را در runtime قابل‌پرس‌وجو می‌کندReflection makes program metadata queryable at runtime

Type، Assembly و MemberInfo توصیف runtime از typeها و اعضا هستند. می‌توانی type را از object بگیری، assembly را مرور کنی یا memberها را ببینی. این قدرت برای serializer، plugin host و تست/ابزارسازی مفید است؛ اما جست‌وجوی همهٔ assemblyها در هر درخواست هزینه دارد و ممکن است typeهای ناخواسته یا ناسازگار را وارد مسیر کند. discovery را معمولاً یک‌بار در startup انجام بده.

Type, Assembly and MemberInfo expose runtime descriptions of types and members. You can obtain a type from an object, inspect an assembly or enumerate members. This helps serializers, plugin hosts and tooling, but scanning every assembly per request costs time and can include unintended or incompatible types. Perform discovery once during startup when possible.

بازرسی محدود یک type / Inspect one type
Type type = typeof(Order);
Console.WriteLine(type.FullName);

foreach (PropertyInfo property in type.GetProperties(
    BindingFlags.Instance | BindingFlags.Public))
{
    Console.WriteLine($"{property.Name}: {property.PropertyType.Name}");
}

این نمونه فقط propertyهای public instance را می‌بیند؛ BindingFlagsهای دیگر قرارداد را گسترش می‌دهند و باید عمدی باشند. reflection مجوز دورزدن طراحی encapsulation نیست. private member را فقط به این دلیل که می‌شود کشف کرد به API تست یا plugin تبدیل نکن.

This example sees only public instance properties; other BindingFlags expand the contract and should be deliberate. Reflection is not permission to bypass encapsulation. Do not turn a private member into a testing or plugin API merely because it can be discovered.

attribute metadata است؛ اثر آن را کد تو تعریف می‌کندAn attribute is metadata; your code defines its effect

attribute روی assembly، type یا member اطلاعات declarative می‌گذارد؛ خودش به‌تنهایی رفتار را اجرا نمی‌کند. runtime یا framework آن را می‌خواند و تصمیم می‌گیرد چه کند. برای route، validation یا serialization، attributeهای framework contract مشخص دارند. attribute سفارشی را کوچک و با معنا بساز و target و تکرارپذیری‌اش را محدود کن. اگر فقط metadata را بررسی می‌کنی و نمی‌خواهی constructor attribute اجرا شود، CustomAttributeData مناسب‌تر است.

An attribute attaches declarative information to an assembly, type or member; it does not execute behavior by itself. A runtime or framework reads it and decides what to do. Framework attributes for routes, validation or serialization have defined contracts. Keep custom attributes small and constrain their targets and multiplicity. If you only need metadata and do not want an attribute constructor instantiated, CustomAttributeData is more appropriate.

attribute و discovery / Attribute-driven discovery
[AttributeUsage(AttributeTargets.Class, AllowMultiple = false)]
public sealed class ExportAttribute(string key) : Attribute
{
    public string Key { get; } = key;
}

[Export("csv")]
public sealed class CsvExporter : IExporter { /* ... */ }

ExportAttribute? export = typeof(CsvExporter)
    .GetCustomAttribute<ExportAttribute>();

نام attribute در C# می‌تواند پسوند Attribute را حذف کند. پارامتر constructor آن باید نوع مجاز attribute باشد و مقدارش constant زمان compile باشد. اگر attribute را از assembly غیرقابل‌اعتماد می‌خوانی، metadata را داده فرض کن، نه مجوز اجرای کد یا تصمیم امنیتی.

C# allows the Attribute suffix to be omitted. Constructor arguments must use allowed attribute types and compile-time constants. When reading metadata from an untrusted assembly, treat it as data—not authorization to execute code or make a security decision.

Invoke دیر‌اتصالی می‌آورد؛ exception و type را runtime چک می‌کندInvoke introduces late binding and runtime checks

با MethodInfo.Invoke نام و آرگومان در runtime resolve می‌شوند؛ اشتباه در نام، تعداد پارامتر یا نوع، دیرتر آشکار می‌شود. مقدار خروجی object است و value type ممکن است box شود. exception متد معمولاً در TargetInvocationException wrap می‌شود و علت در InnerException است. اگر reflection فقط یک‌بار برای dispatch لازم است، metadata را cache کن؛ اگر مسیر پرتکرار است، delegate strongly typed بساز یا API عادی را ترجیح بده.

With MethodInfo.Invoke, the name and arguments are resolved at runtime; mistakes in names, arity or types surface later. The result is object and value types may be boxed. A method exception is commonly wrapped in TargetInvocationException, with the cause in InnerException. Cache metadata for one-time dispatch; for hot paths, create a strongly typed delegate or prefer a normal API.

کشف یک‌بار، استفادهٔ دوباره / Discover once, reuse metadata
MethodInfo method = typeof(Formatter).GetMethod(
    nameof(Formatter.Format), [typeof(Order)])
    ?? throw new MissingMethodException();

var formatter = new Formatter();
object? result = method.Invoke(formatter, [order]);

این کد برای توضیح reflection است، نه نسخهٔ نهایی hot path. overload را با signature دقیق انتخاب کن؛ فقط نام متد برای overloadها کافی نیست. اگر متد static است instance نده؛ اگر nullable یا return type مهم است validate کن. برای exception، خطای discovery و خطای اجرای handler را جدا log کن.

This is an explanatory reflection example, not a hot-path recommendation. Select overloads by exact signature; a name alone is ambiguous. Do not pass an instance to a static method; validate nullability and return type where relevant. Log discovery failures separately from handler execution failures.

cache کردن reflection هم lifetime و invalidation می‌خواهدReflection caches also have lifetime and invalidation concerns

اگر هر بار type scan و attribute خوانده شود، هزینهٔ startup در هر request تکرار می‌شود. یک registry immutable در startup بساز یا metadata را با key مناسب cache کن. اما cache سراسری از Type/MethodInfo می‌تواند AssemblyLoadContext collectible را زنده نگه دارد و مانع unload شود. cache را به عمر context گره بزن و هنگام unload پاک کن. برای generic types و contextهای مختلف، key را فقط FullName نگذار؛ type identity مهم است.

Scanning types and reading attributes on every request repeats startup work. Build an immutable registry at startup or cache metadata with an appropriate key. But a global cache of Type/MethodInfo can keep a collectible AssemblyLoadContext alive and block unloading. Scope the cache to the context and clear it during unload. For generic types and multiple contexts, FullName alone is not a sufficient key; type identity matters.

registry از discovery / Build a registry from discovery
var handlers = assembly.GetTypes()
    .Where(type => !type.IsAbstract &&
                   typeof(IHandler).IsAssignableFrom(type))
    .ToDictionary(
        type => type.GetCustomAttribute<HandlerAttribute>()?.Key
            ?? throw new InvalidOperationException($"Missing key: {type}"),
        type => type);

// Resolve from this immutable registry, not by scanning per request.

duplicate keyها باید در startup خطای روشن بدهند، نه اینکه یکی تصادفی overwrite شود. ساخت instance را از metadata discovery جدا نگه دار تا lifetimeهای DI و dispose درست رعایت شوند. اگر plugin unload می‌شود، registry و delegateهای وابسته هم باید آزاد شوند.

Duplicate keys should fail clearly at startup rather than being overwritten unpredictably. Separate instance creation from metadata discovery so DI lifetimes and disposal are respected. If a plugin unloads, its registry entries and delegates must be released too.

dynamic خطای type را از compile به runtime منتقل می‌کندdynamic moves type errors from compile time to runtime

dynamic در ظاهر شبیه object است، اما compiler بسیاری از عملیات را به binder زمان اجرا می‌سپارد. غلط تایپی یا overload نامعتبر تا اجرای همان خط ظاهر نمی‌شود و خروجی expressionها ممکن است dynamic بماند. برای COM یا APIهای واقعاً dynamic کاربرد دارد؛ برای DTO، domain model و قرارداد داخلی معمولاً typeهای قوی‌تر، interface یا generic امن‌تر و قابل‌کشف‌ترند.

dynamic resembles object, but the compiler defers many operations to a runtime binder. A typo or invalid overload may not surface until that line executes, and expression results can remain dynamic. It is useful for COM or genuinely dynamic APIs; DTOs, domain models and internal contracts are usually safer and more discoverable with strong types, interfaces or generics.

خطای زمان اجرا / A runtime binding failure
dynamic value = "hello";
// Compiles, but the runtime object has no Add method.
value.Add(1); // RuntimeBinderException

dynamic نه performance بهتری می‌دهد و نه reflection را حذف می‌کند؛ مدل binding متفاوتی است. خطاها ممکن است از مرز APIهای بیرونی بیایند؛ همان مرز را با validation به نوع داخلی تبدیل کن تا dynamic در کل برنامه پخش نشود. اگر خروجی dynamic است، در نقطهٔ ورود type مورد انتظار را صریح بررسی کن.

dynamic does not inherently improve performance or eliminate reflection; it changes the binding model. When values come from an external API, validate and convert them at the boundary so dynamic does not spread through the application. If an expression remains dynamic, check its expected type explicitly at the point of entry.

reflection با trimming و Native AOT قرارداد ویژه می‌خواهدReflection needs explicit contracts with trimming and Native AOT

اگر برنامه با reflection typeهایی را می‌خواهد که هیچ reference ایستایی به آن‌ها نیست، linker ممکن است در publish trim‌شده metadata یا کد را حذف کند. Native AOT هم محدودیت‌هایی برای reflection و تولید کد runtime دارد. این به معنی ممنوعیت reflection نیست؛ یعنی مسیرهای dynamic باید annotate، source-generate یا در artifact نهایی تست شوند. warningهای linker را نادیده نگیر و publish واقعی را در CI اجرا کن.

If reflection needs types with no static references, a trimmer may remove code or metadata in a trimmed publish. Native AOT also has constraints around reflection and runtime code generation. This does not ban reflection; it means dynamic paths may need annotations, source generation or explicit testing in the final artifact. Do not ignore linker warnings, and run the actual publish in CI.

برای metadata-only tooling، بررسی assembly بدون اجرای آن را از activation جدا کن. در برنامهٔ runtime، allowlist typeهای مجاز و version contract را مشخص کن؛ ورودی کاربر نباید بی‌واسطه به نام type قابل‌ساخت تبدیل شود.

For metadata-only tooling, separate assembly inspection from execution. In runtime applications, define an allowlist of types and a version contract; never turn raw user input directly into an instantiable type name.

آزمایشگاه: registry handler با attributeLab: an attribute-driven handler registry

چند handler برای export بساز و هرکدام را با key یکتا annotate کن. در startup فقط assemblyهای مجاز را scan کن، typeهای concrete سازگار را پیدا کن و registry immutable بساز. duplicate key، attribute گم‌شده، constructor نامعتبر و exception handler را جداگانه گزارش کن. در مسیر درخواست فقط از registry استفاده کن؛ نسخه‌ای که هر بار scan می‌کند را با BenchmarkDotNet مقایسه کن. یک handler را در collectible context قرار بده و نشان بده اگر Type/MethodInfo آن در cache global بماند unload عقب می‌افتد. در پایان نسخهٔ dynamic را برای ورودی JSON بیرونی در مرز parse مقایسه کن با DTO تایپ‌شده و تصمیم را بر اساس وضوح خطا، correctness و هزینه ثبت کن.

Create several export handlers and annotate each with a unique key. At startup, scan only approved assemblies, find compatible concrete types and build an immutable registry. Report duplicate keys, missing attributes, invalid constructors and handler exceptions separately. Requests should use the registry; compare it with scanning every time using BenchmarkDotNet. Put one handler in a collectible context and show how a global Type/MethodInfo cache delays unloading. Finally compare dynamic parsing of external JSON at the boundary with a typed DTO and document the decision based on error clarity, correctness and cost.

ابزار runtime را در مرز runtime نگه دارKeep runtime tools at runtime boundaries

reflection برای metadata و extension pointهای واقعی مفید است؛ cache و lifetime آن را جدی بگیر. attribute فقط داده است تا مصرف‌کننده‌ای آن را تفسیر کند. dynamic انعطاف می‌دهد اما compile-time safety را کم می‌کند؛ دادهٔ بیرونی را زود به مدل تایپ‌شده تبدیل کن. trimming و AOT هم باید در artifact واقعی آزموده شوند. فصل بعد source generator و analyzer را بررسی می‌کنیم: چه چیزهایی را می‌توان قبل از runtime به compiler سپرد؟

Reflection helps with metadata and genuine extension points; take its cache and lifetime seriously. An attribute is data until a consumer interprets it. dynamic adds flexibility but reduces compile-time safety; convert external data to typed models early.
