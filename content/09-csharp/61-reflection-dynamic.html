reflection، attribute و dynamic

Reflection, attributes and dynamic

فریم‌ورک باید handlerهایی رو پیدا کند که نویسنده از قبل نمی‌شناسد. reflection این کشف رو ممکن می‌کنه؛ بعد تیم برای راحتی همه‌چیز رو dynamic می‌کنه و خطای تایپی از compile به production می‌ره. راه درست نه حذف ابزارهای runtime هست و نه استفادهٔ همه‌جا؛ باید بدانیم metadata چه می‌ده، کدوم کار رو cache کنیم و کجا type safety رو حفظ کنیم.

A framework must discover handlers unknown to its author. Reflection makes this possible; then the team marks everything dynamic for convenience and moves a typo from compile time to production. The answer is neither banning runtime tools nor using them everywhere: understand metadata, cache repeated work and preserve type safety where possible.

reflection metadata برنامه رو در runtime قابل‌پرس‌وجو می‌کنهReflection makes program metadata queryable at runtime

Type، Assembly و MemberInfo توصیف runtime از typeها و اعضا هستن. می‌تونی type رو از object بگیری، assembly رو مرور کنی یا memberها رو ببینی. این قدرت برای serializer، plugin host و تست/ابزارسازی مفید هست؛ اما جست‌وجوی همهٔ assemblyها در هر درخواست هزینه داره و ممکنه typeهای ناخواسته یا ناسازگار رو وارد مسیر کند. discovery رو معمولاً یک‌بار در startup انجام بده.

Type, Assembly and MemberInfo expose runtime descriptions of types and members. You can obtain a type from an object, inspect an assembly or enumerate members. This helps serializers, plugin hosts and tooling, but scanning every assembly per request costs time and can include unintended or incompatible types. Perform discovery once during startup when possible.

بازرسی محدود یک type / Inspect one type
Type type = typeof(Order);
Console.WriteLine(type.FullName);

foreach (PropertyInfo property in type.GetProperties(
    BindingFlags.Instance | BindingFlags.Public))
{
    Console.WriteLine($"{property.Name}: {property.PropertyType.Name}");
}

این نمونه فقط propertyهای public instance رو می‌بینه؛ BindingFlagsهای دیگر قرارداد رو گسترش می‌دن و باید عمدی باشن. reflection مجوز دورزدن طراحی encapsulation نیست. private member رو فقط به این دلیل که می‌شه کشف کرد به API تست یا plugin تبدیل نکن.

This example sees only public instance properties; other BindingFlags expand the contract and should be deliberate. Reflection is not permission to bypass encapsulation. Do not turn a private member into a testing or plugin API merely because it can be discovered.

attribute metadata هست؛ اثر آن رو کد تو تعریف می‌کنهAn attribute is metadata; your code defines its effect

attribute روی assembly، type یا member اطلاعات declarative می‌ذاره؛ خودش به‌تنهایی رفتار رو اجرا نمی‌کنه. runtime یا framework آن رو می‌خونه و تصمیم می‌گیره چه کند. برای route، validation یا serialization، attributeهای framework contract مشخص دارن. attribute سفارشی رو کوچک و با معنا بساز و target و تکرارپذیری‌اش رو محدود کن. اگه فقط metadata رو بررسی می‌کنی و نمی‌خوای constructor attribute اجرا بشه، CustomAttributeData مناسب‌تر هست.

An attribute attaches declarative information to an assembly, type or member; it does not execute behavior by itself. A runtime or framework reads it and decides what to do. Framework attributes for routes, validation or serialization have defined contracts. Keep custom attributes small and constrain their targets and multiplicity. If you only need metadata and do not want an attribute constructor instantiated, CustomAttributeData is more appropriate.

attribute و discovery / Attribute-driven discovery
[AttributeUsage(AttributeTargets.Class, AllowMultiple = false)]
public sealed class ExportAttribute(string key) : Attribute
{
    public string Key { get; } = key;
}

[Export("csv")]
public sealed class CsvExporter : IExporter { /* ... */ }

ExportAttribute? export = typeof(CsvExporter)
    .GetCustomAttribute<ExportAttribute>();

نام attribute در C# می‌تونه پسوند Attribute رو حذف کند. پارامتر constructor آن باید نوع مجاز attribute باشه و مقدارش constant زمان compile باشه. اگه attribute رو از assembly غیرقابل‌اعتماد می‌خوانی، metadata رو داده فرض کن، نه مجوز اجرای کد یا تصمیم امنیتی.

C# allows the Attribute suffix to be omitted. Constructor arguments must use allowed attribute types and compile-time constants. When reading metadata from an untrusted assembly, treat it as data—not authorization to execute code or make a security decision.

Invoke دیر‌اتصالی می‌آورد؛ exception و type رو runtime چک می‌کنهInvoke introduces late binding and runtime checks

با MethodInfo.Invoke نام و آرگومان در runtime resolve می‌شن؛ اشتباه در نام، تعداد پارامتر یا نوع، دیرتر آشکار می‌شه. مقدار خروجی object هست و value type ممکنه box بشه. exception متد معمولاً در TargetInvocationException wrap می‌شه و علت در InnerException هست. اگه reflection فقط یک‌بار برای dispatch لازمه، metadata رو cache کن؛ اگه مسیر پرتکرار هست، delegate strongly typed بساز یا API عادی رو ترجیح بده.

With MethodInfo.Invoke, the name and arguments are resolved at runtime; mistakes in names, arity or types surface later. The result is object and value types may be boxed. A method exception is commonly wrapped in TargetInvocationException, with the cause in InnerException. Cache metadata for one-time dispatch; for hot paths, create a strongly typed delegate or prefer a normal API.

کشف یک‌بار، استفادهٔ دوباره / Discover once, reuse metadata
MethodInfo method = typeof(Formatter).GetMethod(
    nameof(Formatter.Format), [typeof(Order)])
    ?? throw new MissingMethodException();

var formatter = new Formatter();
object? result = method.Invoke(formatter, [order]);

این کد برای توضیح reflection هست، نه نسخهٔ نهایی hot path. overload رو با signature دقیق انتخاب کن؛ فقط نام متد برای overloadها کافی نیست. اگه متد static هست instance نده؛ اگه nullable یا return type مهمه validate کن. برای exception، خطای discovery و خطای اجرای handler رو جدا log کن.

This is an explanatory reflection example, not a hot-path recommendation. Select overloads by exact signature; a name alone is ambiguous. Do not pass an instance to a static method; validate nullability and return type where relevant. Log discovery failures separately from handler execution failures.

cache کردن reflection هم lifetime و invalidation می‌خوادReflection caches also have lifetime and invalidation concerns

اگه هر بار type scan و attribute خوانده بشه، هزینهٔ startup در هر request تکرار می‌شه. یک registry immutable در startup بساز یا metadata رو با key مناسب cache کن. اما cache سراسری از Type/MethodInfo می‌تونه AssemblyLoadContext collectible رو زنده نگه داره و مانع unload بشه. cache رو به عمر context گره بزن و هنگام unload پاک کن. برای generic types و contextهای مختلف، key رو فقط FullName نگذار؛ type identity مهمه.

Scanning types and reading attributes on every request repeats startup work. Build an immutable registry at startup or cache metadata with an appropriate key. But a global cache of Type/MethodInfo can keep a collectible AssemblyLoadContext alive and block unloading. Scope the cache to the context and clear it during unload. For generic types and multiple contexts, FullName alone is not a sufficient key; type identity matters.

registry از discovery / Build a registry from discovery
var handlers = assembly.GetTypes()
    .Where(type => !type.IsAbstract &&
                   typeof(IHandler).IsAssignableFrom(type))
    .ToDictionary(
        type => type.GetCustomAttribute<HandlerAttribute>()?.Key
            ?? throw new InvalidOperationException($"Missing key: {type}"),
        type => type);

// Resolve from this immutable registry, not by scanning per request.

duplicate keyها باید در startup خطای روشن بدهند، نه اینکه یکی تصادفی overwrite بشه. ساخت instance رو از metadata discovery جدا نگه دار تا lifetimeهای DI و dispose درست رعایت بشن. اگه plugin unload می‌شه، registry و delegateهای وابسته هم باید آزاد بشن.

Duplicate keys should fail clearly at startup rather than being overwritten unpredictably. Separate instance creation from metadata discovery so DI lifetimes and disposal are respected. If a plugin unloads, its registry entries and delegates must be released too.

dynamic خطای type رو از compile به runtime منتقل می‌کنهdynamic moves type errors from compile time to runtime

dynamic در ظاهر شبیه object هست، اما compiler بسیاری از عملیات رو به binder زمان اجرا می‌سپارد. غلط تایپی یا overload نامعتبر تا اجرای همان خط ظاهر نمی‌شه و خروجی expressionها ممکنه dynamic بماند. برای COM یا APIهای واقعاً dynamic کاربرد داره؛ برای DTO، domain model و قرارداد داخلی معمولاً typeهای قوی‌تر، interface یا generic امن‌تر و قابل‌کشف‌ترند.

dynamic resembles object, but the compiler defers many operations to a runtime binder. A typo or invalid overload may not surface until that line executes, and expression results can remain dynamic. It is useful for COM or genuinely dynamic APIs; DTOs, domain models and internal contracts are usually safer and more discoverable with strong types, interfaces or generics.

خطای زمان اجرا / A runtime binding failure
dynamic value = "hello";
// Compiles, but the runtime object has no Add method.
value.Add(1); // RuntimeBinderException

dynamic نه performance بهتری می‌ده و نه reflection رو حذف می‌کنه؛ مدل binding متفاوتی هست. خطاها ممکنه از مرز APIهای بیرونی بیایند؛ همان مرز رو با validation به نوع داخلی تبدیل کن تا dynamic در کل برنامه پخش نشه. اگه خروجی dynamic هست، در نقطهٔ ورود type مورد انتظار رو صریح بررسی کن.

dynamic does not inherently improve performance or eliminate reflection; it changes the binding model. When values come from an external API, validate and convert them at the boundary so dynamic does not spread through the application. If an expression remains dynamic, check its expected type explicitly at the point of entry.

reflection با trimming و Native AOT قرارداد ویژه می‌خوادReflection needs explicit contracts with trimming and Native AOT

اگه برنامه با reflection typeهایی رو می‌خواد که هیچ reference ایستایی به آن‌ها نیست، linker ممکنه در publish trim‌شده metadata یا کد رو حذف کند. Native AOT هم محدودیت‌هایی برای reflection و تولید کد runtime داره. این به معنی ممنوعیت reflection نیست؛ یعنی مسیرهای dynamic باید annotate، source-generate یا در artifact نهایی تست بشن. warningهای linker رو نادیده نگیر و publish واقعی رو در CI اجرا کن.

If reflection needs types with no static references, a trimmer may remove code or metadata in a trimmed publish. Native AOT also has constraints around reflection and runtime code generation. This does not ban reflection; it means dynamic paths may need annotations, source generation or explicit testing in the final artifact. Do not ignore linker warnings, and run the actual publish in CI.

برای metadata-only tooling، بررسی assembly بدون اجرای آن رو از activation جدا کن. در برنامهٔ runtime، allowlist typeهای مجاز و version contract رو مشخص کن؛ ورودی کاربر نباید بی‌واسطه به نام type قابل‌ساخت تبدیل بشه.

For metadata-only tooling, separate assembly inspection from execution. In runtime applications, define an allowlist of types and a version contract; never turn raw user input directly into an instantiable type name.
