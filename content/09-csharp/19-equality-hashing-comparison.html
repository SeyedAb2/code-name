برابری، hash و ترتیب

Equality, hashing and ordering

گزارش می‌گوید کلیدی که همین الآن داخل Dictionary بوده پیدا نمی‌شود؛ در حالی که object هنوز وجود دارد. تیم آن را mutate کرده و حالا hash متفاوتی می‌دهد. این فصل سه سؤال را جدا می‌کند: دو مقدار برابرند؟ کلید در کدام bucket قرار می‌گیرد؟ و وقتی sort می‌کنیم کدام‌یک قبل از دیگری است؟

A key that was just inserted into a Dictionary can no longer be found, even though the object still exists. The team mutated it, so it now produces a different hash. This chapter separates three questions: are two values equal, which bucket contains the key, and which item comes first when sorting?

فصل ۱۸پیش‌نیازprerequisite

کلید هست، ولی lookup شکست می‌خوردThe key exists, but lookup fails

Dictionary برای پیدا کردن کلید از hash و سپس equality کمک می‌گیرد. اگر فیلدی که در hash شرکت دارد پس از درج تغییر کند، جست‌وجو ممکن است به مسیر دیگری برود. این bug را با class mutable بازتولید می‌کنیم؛ سپس کلید را پایدار می‌کنیم.

A Dictionary uses a hash and then equality to locate a key. If a field participating in the hash changes after insertion, lookup may follow a different path. We will reproduce the bug with a mutable class, then make the key stable.

کلید mutable / Mutable key
sealed class CustomerKey
{
    public string Code { get; set; }
    public CustomerKey(string code) => Code = code;
    public override bool Equals(object? obj)
        => obj is CustomerKey other && Code == other.Code;
    public override int GetHashCode() => Code.GetHashCode();
}

var key = new CustomerKey("C-10");
var map = new Dictionary<CustomerKey, string> { [key] = "active" };
key.Code = "C-11";
Console.WriteLine(map.TryGetValue(key, out var value));

خروجی معمولاً false است، چون شیء در bucket مبتنی بر hash قبلی ذخیره شده ولی اکنون hash دیگری تولید می‌کند. رفتار داخلی Dictionary را از این snippet به یک تضمین ریزساختاری تبدیل نکن؛ نتیجهٔ قابل اتکا این است که کلید mutable قرارداد lookup را می‌شکند و نباید چنین طراحی‌ای کرد.

The result is typically false because the object was placed using its earlier hash and now produces another. Do not turn this snippet into a promise about Dictionary internals; the reliable conclusion is that mutating a key breaks the lookup contract and should be avoided.

قرارداد equality و hashThe equality and hash contract

اگر دو شیء طبق Equals برابرند، GetHashCode آن‌ها باید برابر باشد. برعکس لازم نیست: hash یکسان به‌تنهایی برابری را ثابت نمی‌کند و برخورد hash ممکن است. equality هم باید با قرارداد منطقی‌اش سازگار باشد؛ بازتابی، متقارن و تعدی‌پذیر. پیاده‌سازی ناهماهنگ، Dictionary و HashSet را غیرقابل‌پیش‌بینی می‌کند.

If two objects are equal according to Equals, their GetHashCode values must match. The reverse is not required: equal hashes do not prove equality, because collisions can occur. Equality should also satisfy its logical contract: reflexivity, symmetry and transitivity. Inconsistent implementations make Dictionary and HashSet unreliable.

پیاده‌سازی IEquatable / Equality implementation
sealed class ProductCode : IEquatable<ProductCode>
{
    public string Value { get; }
    public ProductCode(string value) => Value = value;

    public bool Equals(ProductCode? other)
        => other is not null && StringComparer.Ordinal.Equals(Value, other.Value);

    public override bool Equals(object? obj) => obj is ProductCode other && Equals(other);
    public override int GetHashCode() => StringComparer.Ordinal.GetHashCode(Value);
}

پیاده‌سازی typed IEquatable برای مقایسهٔ نوع‌دار مفید است؛ overrideهای object هم باید همان قرارداد را دنبال کنند. اگر equality case-insensitive است، comparer یکسان را در Equals و hash به کار ببر؛ مقایسهٔ ordinal را با culture-based قاطی نکن.

Typed IEquatable helps strongly typed comparisons; object overrides must follow the same contract. If equality is case-insensitive, use a consistent comparer for equality and hashing; do not mix ordinal and culture-sensitive comparisons.

کلید باید در مدت حضور در مجموعه پایدار بماندA key must stay stable while stored

ساده‌ترین اصلاح این است که فیلدهای برابری کلید را تغییرناپذیر کنیم. اگر دامنه نیاز به تغییر شناسه دارد، key تازه بساز و entry را با حذف و درج کنترل‌شده جابه‌جا کن؛ objectی که در مجموعه است را از پشت تغییر نده.

The simplest repair is to make equality-defining key fields immutable. If the domain requires changing an identifier, create a new key and move the entry through controlled removal and insertion; do not mutate an object behind the collection’s back.

کلید immutable / Immutable key
public sealed record CustomerKey(string Code);

var key = new CustomerKey("C-10");
var map = new Dictionary<CustomerKey, string> { [key] = "active" };
Console.WriteLine(map.TryGetValue(new CustomerKey("C-10"), out var status));
Console.WriteLine(status);
خروجی / Output
True
active

record equality برای این مثال مقدارمحور است و Code پس از ساخت init-only می‌ماند. اگر رشتهٔ null یا خالی نامعتبر است، آن را در constructor یا مرز ورودی validate کن؛ immutable بودن به‌تنهایی معتبر بودن را تضمین نمی‌کند.

Record equality is value-oriented here, and Code is init-only after construction. If null or empty text is invalid, validate it in a constructor or input boundary; immutability alone does not guarantee validity.

مقایسه را از داده جدا کنKeep comparison policy separate from the data

برای یکسان‌دانستن کدهای case-insensitive، لازم نیست equality خود CustomerKey را برای همهٔ کاربردها تغییر بدهیم. Dictionary می‌تواند comparer بگیرد؛ پس سیاست یک مجموعه از مدل ذاتی نوع جدا می‌ماند. این برای جست‌وجوهای با قاعدهٔ متفاوت مهم است.

To treat codes case-insensitively in one lookup, we need not change CustomerKey’s equality for every use. A Dictionary can receive a comparer, keeping one collection’s policy separate from the type’s intrinsic model.

Dictionary با comparer صریح
var owners = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase)
{
    ["ops"] = 7
};

Console.WriteLine(owners["OPS"]);

خروجی ۷ است. برای identifierهای پروتکلی یا کدهای ماشینی معمولاً comparer صریح مثل Ordinal یا OrdinalIgnoreCase قابل‌پیش‌بینی‌تر از قواعد زبانی سیستم است. برای متن انسانی، نیاز محصول و فرهنگ زبان را جدا بررسی کن.

The result is 7. For protocol identifiers or machine codes, an explicit comparer such as Ordinal or OrdinalIgnoreCase is often more predictable than machine-language rules. Human text requires a separate product and culture decision.

ترتیب با برابری فرق داردOrdering is different from equality

IComparable ترتیب پیش‌فرضِ یک نوع را بیان می‌کند؛ IComparer سیاست مرتب‌سازیِ بیرونی می‌دهد. اگر چند ترتیب معتبر داریم—مثلاً سفارش با مبلغ یا تاریخ—comparer معمولاً انعطاف‌پذیرتر است. نتیجهٔ CompareTo صفر لزوماً همان قرارداد Equals نیست، اما اختلافش باید آگاهانه باشد چون sort و sorted collection می‌توانند آن را مهم بدانند.

IComparable<T> defines a type’s default ordering; IComparer<T> supplies an external ordering policy. If several orderings are valid—such as orders by amount or date—a comparer is more flexible. CompareTo returning zero is not automatically the same as Equals, but any difference must be deliberate because sorting and sorted collections may rely on it.

مرتب‌سازی بر اساس مبلغ / Sort by amount
var orders = new[]
{
    (Number: "A-1", Total: 90m),
    (Number: "B-2", Total: 25m),
    (Number: "C-3", Total: 60m)
};

var byTotal = orders.OrderBy(order => order.Total).ToArray();
foreach (var order in byTotal)
    Console.WriteLine($"{order.Number}: {order.Total}");

OrderBy یک ترتیب برای همین عملیات می‌سازد و مدل سفارش را مجبور نمی‌کند تنها یک ترتیب طبیعی داشته باشد. برای sortهای چندمرحله‌ای از کلیدهای tie-breaker استفاده کن تا در داده‌های برابر نتیجهٔ مورد انتظار روشن باشد.

OrderBy defines an ordering for this operation without forcing Order to have only one natural ordering. For multi-step sorts, use tie-breakers so the expected result is clear when primary keys match.

۱) implication hash1) Hash implication

اگر Equals برابر است، دربارهٔ hash چه باید درست باشد؟

If Equals reports equality, what must hold for hashes?

پاسخAnswer

hash باید برابر باشد؛ hash برابر اما equality را ثابت نمی‌کند.

Hashes must match; equal hashes do not prove equality.

۲) hash collision2) Hash collision

دو مقدار hash برابر دارند؛ آیا Dictionary حق دارد آن‌ها را یک key بداند؟

Two values share a hash. Must Dictionary treat them as one key?

پاسخAnswer

نه؛ پس از hash equality را هم بررسی می‌کند و برخورد مجاز است.

No; equality is also checked after hashing, and collisions are allowed.

۳) کلید mutable3) Mutable key

چرا تغییر فیلد hashشونده پس از درج خطرناک است؟

Why is changing a hashed field after insertion risky?

پاسخAnswer

lookup از hash جدید مسیر متفاوتی می‌رود، در حالی که entry با hash قبلی درج شده بود.

Lookup follows the new hash path while the entry was inserted using the old one.

۴) collision را با خطا اشتباه نگیر4) Do not confuse collision with failure

Are two objects with the same hash necessarily equal?

خیر؛ hash فقط مرحلهٔ محدودکردن جست‌وجو است.

How must typed Equals and the object override relate?

باید یک قرارداد واحد را پیاده کنند و GetHashCode با همان فیلدهای equality هماهنگ باشد.

۶) OrdinalIgnoreCase6) OrdinalIgnoreCase

برای username ماشینی comparer صریح چه فایده‌ای دارد؟

Why use an explicit comparer for machine usernames?

پاسخAnswer

رفتار مستقل از فرهنگ سیستم و روشن دربارهٔ حساسیت حروف می‌شود.

۷) equality از hash مهم‌تر است؟7) Is equality more important than hash?

یک GetHashCode سازگار کافی است تا دو key برابر شوند؟

Is a compatible GetHashCode enough to make two keys equal?

پاسخAnswer

نه؛ Equality تصمیم منطقی است، hash فقط برای ساختار داده کمک می‌کند.

No; equality is the logical decision, while hashing supports the data structure.

۸) key جدید یا mutation؟8) New key or mutation?

شناسه عوض می‌شود اما object داخل Dictionary است. چه روندی امن‌تر است؟

An identifier changes while an object is in a Dictionary. What is safer?

پاسخAnswer

با key قدیمی حذف کن، immutable key جدید بساز و کنترل‌شده دوباره درج کن.

Remove using the old key, create a new immutable key and insert it deliberately.

۱۰) ordering policy10) Ordering policy

دو مرتب‌سازی معتبر برای Order داری. IComparable یا دو IComparer؟

Orders need two valid orderings. IComparable or two IComparers?

Is caching a hash always beneficial for a large immutable key?

نه؛ هزینهٔ حافظه و محاسبه را اندازه بگیر و correctness را مقدم بدان. الگوریتم hash پایدار بین processها را هم فرض نکن.

مسیرPath

ببین Code در Equals و hash هست؛ قبل و بعد مقدار hash را مقایسه کن؛ ContainsKey/lookup را با key نو بررسی کن. سپس key را immutable کن یا comparer مناسب بده و entry را با حذف/درج جابه‌جا کن.

برابری، hash و ترتیب را یک قرارداد نکنDo not collapse equality, hashing and ordering

Equals معنای برابر بودن را مشخص می‌کند؛ GetHashCode باید با آن سازگار باشد؛ comparer سیاست یک collection یا sort را تعیین می‌کند. key را تا وقتی عضو map است تغییر نده. و یادت باشد hash برای نگهداری پایدار شناسه نیست و نباید بین اجراها یا ماشین‌ها به‌عنوان مقدار ذخیره‌شدنی فرض شود. فصل بعد سراغ operator و conversion می‌رویم: چه زمانی syntax تازه واقعاً خوانایی را بهتر می‌کند؟

Equals defines what equality means; GetHashCode must agree with it; a comparer sets one collection’s or sort’s policy. Do not mutate a key while it is stored. A hash is not a persistent identifier and must not be assumed stable across runs or machines. Next we ask when operator and conversion syntax genuinely improves readability.
