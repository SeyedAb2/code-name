null و قرارداد نوع‌ها

Null and type contracts

سفارش A-42 کد تخفیف نداره. یکی از هم‌تیمی‌ها به‌جای نبودن کد، رشتهٔ خالی گذاشته؛ یکی دیگر صفر گذاشته. گزارش ظاهراً کار می‌کنه، ولی دیگر نمی‌فهمیم «کدی نداریم» با «کد خالی» یا «تخفیف صفر» چه فرقی داره. بیایید نبودن رو در نوع و قرارداد برنامه روشن کنیم.

Order A-42 has no discount code. One teammate uses an empty string for absence; another uses zero. The report runs, but we can no longer distinguish “no code” from “an empty code” or “a zero discount.” Let’s make absence explicit in the program’s types and contracts.

گزارش، «تخفیف نداریم» رو با صفر یکی گرفتهThe report treats “no discount” as zero

بعد از فصل قبل می‌دانیم چند متغیر می‌تونن به یک شیء برسند. حالا مسئله برعکس هست: گاهی اصلاً شیئی وجود نداره. برای کد تخفیف، `null` رو عمداً می‌پذیریم و بعد بدون بررسی سراغ `Length` می‌رویم.

After the previous chapter, we know several variables can refer to one object. Now the problem is the opposite: sometimes no object exists at all. We intentionally allow `null` for a discount code, then read `Length` without checking.

C# · Program.cs
#nullable enable

string? code = null;
Console.WriteLine(code.Length);

compiler هشدار می‌ده که dereference یک reference شاید-null خطرناک هست. اگه برنامه رو با وجود warning اجرا کنیم، خطا در runtime رخ می‌ده. هشدار، exception رو جادویی حذف نمی‌کنه؛ کمک می‌کنه پیش از اجرا مسیر نامطمئن رو ببینیم.

The compiler warns that dereferencing a maybe-null reference is unsafe. If we run despite the warning, the failure occurs at runtime. A warning does not magically remove the exception; it helps us spot an unsafe path before execution.

nullable referenceها runtime رو عوض نمی‌کننNullable references do not change runtime representation

`string` و `string?` دو runtime class جدا نیستن. `?` در nullable context نیت ما رو برای compiler بیان می‌کنه و static analysis هشدار می‌ده؛ تضمین نمی‌کنه کتابخانهٔ قدیمی، ورودی بیرونی یا کدی که warning رو نادیده گرفته، هیچ‌وقت null ندهد.

`string` and `string?` are not separate runtime classes. In a nullable context, `?` expresses intent to the compiler and enables static-analysis warnings; it cannot guarantee that a legacy library, external input, or code ignoring warnings never supplies null.

اول ببین پروژه اصلاً nullable analysis رو روشن کرده یا نهFirst check whether nullable analysis is enabled

در پروژه‌های تازهٔ .NET معمولاً nullable فعال هست؛ اما یک پروژهٔ قدیمی ممکنه warning ندهد. فایل `.csproj` رو نگاه کن و یک null عمدی رو compile کن تا به‌جای حدس، وضعیت واقعی رو ببینی.

Recent .NET templates commonly enable nullable analysis, but an older project may not warn. Inspect the `.csproj` and compile an intentional null case so you see the actual setting rather than guessing.

Project.csproj
<PropertyGroup>
  <Nullable>enable</Nullable>
</PropertyGroup>

برای یک آزمایش تک‌فایلی می‌توان `#nullable enable` گذاشت؛ در پروژهٔ واقعی تنظیم `.csproj` معمولاً قرارداد روشن‌تری برای همهٔ فایل‌هاست. فعال‌کردن ممکنه warningهای قدیمی رو آشکار کند؛ آن‌ها رو یکی‌یکی با قرارداد واقعی اصلاح کن، نه اینکه همه رو خاموش کنی.

For a one-file experiment, use `#nullable enable`; in a real project, the `.csproj` setting usually makes the policy clearer across files. Enabling it may reveal old warnings. Fix them against the real contract instead of turning them all off.

warning یعنی «قرارداد و کد رو مقایسه کن»A warning means “compare the contract with the code”

گاهی نوع اشتباه nullable اعلام شده؛ گاهی واقعاً null ممکنه و caller باید آن رو مدیریت کند. فقط یکی از این دو تغییر رو با دلیل انجام بده: نوع رو دقیق‌تر کن یا مسیر null رو امن کن.

Sometimes the type is annotated incorrectly; sometimes null really is possible and the caller must handle it. Make one justified change: refine the type contract or handle the null path safely.

با بررسی شرطی، به compiler مدرک بدهGive the compiler evidence with a null check

همان کد رو با guard اجرا کنیم. این بار بررسی فقط برای runtime نیست؛ تحلیل جریان کنترل compiler هم می‌فهمد داخل شاخه، `code` null نیست.

Run the same logic with a guard. This check is not only for runtime: compiler flow analysis also knows that `code` is not null inside the branch.

C# · flow analysis
static string DescribeCode(string? code)
{
    if (code is null)
        return "No code";

    return $"Code length: {code.Length}";
}

Console.WriteLine(DescribeCode(null));
Console.WriteLine(DescribeCode("SAVE10"));
خروجی / output
No code
Code length: 6

بعد از شرط `is null`، شاخهٔ اول برمی‌گرده؛ پس در خط بعد مسیر اجرا فقط وقتی ادامه داره که `code` مقدار داشته باشه. early return هم guard رو خوانا می‌کنه، هم تحلیل compiler رو ساده. مقایسهٔ `code == null` هم در این مورد می‌شه ازش استفاده کرد؛ الگوی `is null` در برابر overload شدن `==` غافلگیر نمی‌شه.

The `is null` branch returns early, so execution reaches the next line only when `code` has a value. The early return makes the guard readable and flow analysis straightforward. `code == null` also works here; `is null` is not affected by an overloaded `==` operator.

compiler فقط جریان کدی رو که می‌بینه دنبال می‌کنه؛ از قراردادهای پنهان داخل هر متد خبر نداره. اگه `EnsureLoaded(order)` از نظر برنامه تضمین می‌کنه property پر شده، compiler لزوماً از اسم متد این رو استنتاج نمی‌کنه. یا قرارداد API رو با نوع/attribute مناسب منتقل کن، یا مقدار رو صریح بررسی کن.

The compiler tracks visible control flow; it does not know hidden guarantees inside every method. If `EnsureLoaded(order)` promises to populate a property, the compiler cannot infer that from the method name. Express the API contract with appropriate types/attributes or check the value explicitly.

وقتی نبودن یک مسیر عادی هست، ?. و ?? کمک می‌کننUse ?. and ?? when absence is an ordinary path

نام مشتری اختیاری هست. هدف این نیست که null رو هرجا دیدیم با متن تصادفی عوض کنیم؛ اول قرارداد خروجی رو انتخاب می‌کنیم: آیا غیبت مجاز هست یا گزارش حتماً یک label می‌خواد؟

A customer name is optional. We should not replace every null with arbitrary text; first choose the output contract: is absence allowed, or must the report always have a label?

C# · ?. and ??
string? customerName = null;
int? nameLength = customerName?.Length;
string label = customerName ?? "Guest";

Console.WriteLine(nameLength is null);
Console.WriteLine(label);

string? suppliedCode = null;
suppliedCode ??= "NO-DISCOUNT";
Console.WriteLine(suppliedCode);
خروجی / output
True
Guest
NO-DISCOUNT

`?.` اگه سمت چپ null باشه، ادامهٔ دسترسی رو اجرا نمی‌کنه و برای نتیجهٔ value type معمولاً `Nullable<T>` می‌سازه؛ برای همین `nameLength` از نوع `int?` هست. `??` وقتی سمت چپ null هست fallback می‌ده. `??=` فقط وقتی متغیر null باشه مقدار می‌نویسه.

If the left side of `?.` is null, member access is skipped; for a value-type result it produces a nullable value, which is why `nameLength` is `int?`. `??` supplies a fallback only when its left side is null. `??=` assigns only when its target is null.

fallback می‌تونه دادهٔ واقعی رو جعل کندA fallback can invent business data

`?? 0` اگه null یعنی «قیمت هنوز بارگذاری نشده»، آن رو بی‌صدا به قیمت صفر تبدیل می‌کنه. فقط وقتی fallback بگذار که معنای دامنه‌ای داره؛ وگرنه null رو در نتیجه نگه دار یا خطای معتبر برگردان.

If null means “price not loaded yet,” `?? 0` silently turns it into a zero price. Use a fallback only when the domain defines one; otherwise preserve absence or return a meaningful error.

nullable value type، واقعاً مقدار یا نبود مقدار رو نگه می‌دارهA nullable value type stores a value—or its absence

در فصل ۱۱ دیدیم value type کپی مقدار داره. برای عددی که شاید هنوز تنظیم نشده، `int?` یک مقدار underlying به‌علاوهٔ حالت نبودن داره؛ default آن صفر نیست، null هست.

In Chapter 11, we saw that value types copy their values. For a number that may not be set yet, `int?` carries an underlying value plus an absent state; its default is null, not zero.

C# · nullable value
int? retryLimit = null;
int effectiveLimit = retryLimit ?? 3;
Console.WriteLine($"has value: {retryLimit.HasValue}");
Console.WriteLine($"limit: {effectiveLimit}");

retryLimit = 0;
Console.WriteLine($"has value: {retryLimit.HasValue}");
Console.WriteLine($"configured: {retryLimit.Value}");
خروجی / output
has value: False
limit: 3
has value: True
configured: 0

صفر یک مقدار ثبت‌شده هست؛ null یعنی مقداری ثبت نشده. `.Value` وقتی null باشه InvalidOperationException می‌ده، پس معمولاً pattern matching یا `??` امن‌تر و روشن‌تر هست. مقدار fallback در این مثال سیاست برنامه هست، نه رفتار اجباری C#.

Zero is a configured value; null means no value was supplied. `.Value` throws InvalidOperationException when null, so pattern matching or `??` is usually clearer and safer. The fallback here is application policy, not a C# requirement.

برای `int? a` و `int? b`، عبارت `a + b` هم nullable هست: اگه ورودی null باشه، نتیجه می‌تونه null بماند. پیش از جمع باید تصمیم بگیری نبود یکی از operandها یعنی «نتیجه نداریم»، یعنی صفر، یا یعنی ورودی نامعتبر.

For `int? a` and `int? b`, `a + b` is nullable too: if an input is null, the result can remain null. Before summing, decide whether a missing operand means “no result,” zero, or invalid input.

نوع خروجی، قول متد به caller استA return type is a promise to the caller

lookup کد تخفیف ممکنه چیزی پیدا نکند. اگه امضای متد `string` بگوید ولی گاهی null برگرداند، caller رو با قرارداد نادرست تنها گذاشته‌ایم. نبودن رو در نوع خروجی ثبت می‌کنیم.

A discount-code lookup may find nothing. If its signature says `string` but it sometimes returns null, the caller is left with a false contract. We encode absence in the return type.

C# · nullable API
static string? FindCode(string orderId) => orderId switch
{
    "A-42" => "SAVE10",
    _ => null
};

string message = FindCode("B-17") is { } code
    ? $"Code: {code}"
    : "No code for this order";
Console.WriteLine(message);

امضای `string?` حالا caller رو مجبور می‌کنه مسیر نبودن رو ببیند. الگوی `{ } code` در شاخهٔ true یک مقدار non-null به نام `code` می‌ده. اگه فقدان داده خطاست، به‌جای null می‌توان result/error صریح طراحی کرد؛ nullable annotation جای تصمیم دامنه‌ای نیست.

The `string?` signature makes the caller account for absence. The `{ } code` pattern provides a non-null `code` in the true branch. If absence is an error, design an explicit result/error instead; a nullable annotation does not decide domain policy.

اعتماد بیرونی رو جای بررسی ننشانDo not replace boundary validation with trust

nullable analysis می‌تونه در تعامل با کتابخانهٔ بدون annotation یا دادهٔ deserialized محدود باشه. ورودی بیرونی رو با validation مناسب بررسی کن؛ `string` در signature به‌تنهایی تضمین نمی‌کنه JSON یا کد legacy مقدار non-null تحویل دهد.

Nullable analysis can be limited at boundaries with unannotated libraries or deserialized data. Validate external input appropriately; a `string` signature alone cannot guarantee that JSON or legacy code supplied a non-null value.

علامت ! فقط صدای compiler رو کم می‌کنهThe ! operator only silences the compiler

راه میان‌بر وسوسه‌کننده هست: warning رو با `!` حذف کنیم و برویم سراغ کار بعدی. آزمایش زیر نشان می‌ده runtime از این علامت خبر نداره.

The shortcut is tempting: add `!`, remove the warning and move on. This experiment shows that the runtime does not know about that operator.

C# · suppression is not validation
#nullable enable
string? code = null;
Console.WriteLine(code!.Length); // compiles without nullable warning; still throws

`!` فقط null-state تحلیل compiler رو برای همان expression به not-null تغییر می‌ده؛ مقدار رو عوض نمی‌کنه، بررسی runtime نمی‌سازه و exception رو نمی‌گیره. اگه invariant واقعی داری، آن رو در یک نقطهٔ قابل‌اثبات بررسی کن؛ اگه نمی‌دانی، `!` مدرک نیست.

`!` only changes the compiler’s null-state assumption for that expression; it does not change the value, add a runtime check, or catch an exception. If an invariant is real, verify it at a provable boundary; if you do not know, `!` is not evidence.

آزمایشگاه: قرارداد پیدا کردن تخفیف رو درست کنLab: repair the discount lookup contract

یک گزارش مبلغ، تخفیف اختیاری و کد سفارش داره. حالت فعلی با رشتهٔ خالی نبودن رو قایم کرده و یکی از مسیرها هم exception می‌ده. اول رفتار رو ثبت می‌کنیم، بعد قرارداد رو انتخاب و دوباره همان ورودی‌ها رو آزمایش می‌کنیم.

A price report has an optional discount and order code. The current version hides absence as an empty string and one path throws. First record behavior, then choose a contract and rerun the same inputs.

  1. یک console app بساز و nullable رو در `.csproj` فعال کن. متد `FindCode(string orderId)` بساز که برای `A-42` کد و برای بقیه null برگرداند؛ warningها رو نگه دار.
  2. Create a console app and enable nullable in the `.csproj`. Implement `FindCode(string orderId)` returning a code for `A-42` and null otherwise; keep the warnings.
  3. یک caller بنویس که بدون guard `FindCode(id).Length` رو بخواند. warning رو بخوان، اجرا کن و null case رو جدا ثبت کن.
  4. Write a caller that reads `FindCode(id).Length` without a guard. Read the warning, run it, and record the null case separately.
  5. امضای درست رو `string?` کن و سه ورودی رو تست کن: کد موجود، نبودن کد و رشتهٔ خالی به‌عنوان ورودی. این سه حالت رو با هم یکی نگیر.
  6. Change the contract to `string?` and test three inputs: a found code, no code, and an empty input string. Do not conflate these cases.
  7. گزارش رو با pattern یا guard بازنویسی کن. برای مبلغ `decimal?` هم یک حالت «قیمت هنوز موجود نیست» و یک مبلغ صفر بساز؛ خروجی باید این تفاوت رو حفظ کند.
  8. Rewrite the report with a pattern or guard. For a `decimal?` amount, create both “price unavailable” and zero; output must preserve the distinction.
  9. یک بار `!` اضافه کن و نشان بده فقط warning چه تغییری کرد؛ همان null رو اجرا کن تا ببینی exception باقی می‌مونه.
  10. Add `!` once and show what changed in compiler diagnostics; run the same null and observe that the exception remains.
  11. در پایان جدول ورودی/خروجی بساز: کد موجود، کد پیدا نشده، ورودی خالی و مبلغ صفر. قرارداد متد و رفتار هر ردیف رو کنار هم نگه دار.
  12. Finish with an input/output table for found code, missing code, empty input and zero amount. Keep each method contract beside its behavior.

switch pattern هر حالت رو جدا می‌کنه و امضای `string?` امکان نبودن رو پیشاپیش اعلام می‌کنه. در سامانهٔ واقعی شاید رشتهٔ خالی هم نامعتبر باشه؛ این آزمایش فقط نشان می‌ده null، empty و صفر داده‌های متفاوت‌اند و policy باید از محصول بیاید.

The switch patterns separate each case, and `string?` advertises possible absence in advance. A real system may reject an empty string; this experiment only proves that null, empty and zero are distinct data states whose policy must come from the product.
