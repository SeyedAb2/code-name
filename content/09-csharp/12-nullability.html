null و قرارداد نوع‌ها

Null and type contracts

سفارش A-42 کد تخفیف ندارد. یکی از هم‌تیمی‌ها به‌جای نبودن کد، رشتهٔ خالی گذاشته؛ یکی دیگر صفر گذاشته. گزارش ظاهراً کار می‌کند، ولی دیگر نمی‌فهمیم «کدی نداریم» با «کد خالی» یا «تخفیف صفر» چه فرقی دارد. بیایید نبودن را در نوع و قرارداد برنامه روشن کنیم.

Order A-42 has no discount code. One teammate uses an empty string for absence; another uses zero. The report runs, but we can no longer distinguish “no code” from “an empty code” or “a zero discount.” Let’s make absence explicit in the program’s types and contracts.

گزارش، «تخفیف نداریم» را با صفر یکی گرفتهThe report treats “no discount” as zero

بعد از فصل قبل می‌دانیم چند متغیر می‌توانند به یک شیء برسند. حالا مسئله برعکس است: گاهی اصلاً شیئی وجود ندارد. برای کد تخفیف، `null` را عمداً می‌پذیریم و بعد بدون بررسی سراغ `Length` می‌رویم.

After the previous chapter, we know several variables can refer to one object. Now the problem is the opposite: sometimes no object exists at all. We intentionally allow `null` for a discount code, then read `Length` without checking.

C# · Program.cs
#nullable enable

string? code = null;
Console.WriteLine(code.Length);

compiler هشدار می‌دهد که dereference یک reference شاید-null خطرناک است. اگر برنامه را با وجود warning اجرا کنیم، خطا در runtime رخ می‌دهد. هشدار، exception را جادویی حذف نمی‌کند؛ کمک می‌کند پیش از اجرا مسیر نامطمئن را ببینیم.

The compiler warns that dereferencing a maybe-null reference is unsafe. If we run despite the warning, the failure occurs at runtime. A warning does not magically remove the exception; it helps us spot an unsafe path before execution.

nullable referenceها runtime را عوض نمی‌کنندNullable references do not change runtime representation

`string` و `string?` دو runtime class جدا نیستند. `?` در nullable context نیت ما را برای compiler بیان می‌کند و static analysis هشدار می‌دهد؛ تضمین نمی‌کند کتابخانهٔ قدیمی، ورودی بیرونی یا کدی که warning را نادیده گرفته، هیچ‌وقت null ندهد.

`string` and `string?` are not separate runtime classes. In a nullable context, `?` expresses intent to the compiler and enables static-analysis warnings; it cannot guarantee that a legacy library, external input, or code ignoring warnings never supplies null.

اول ببین پروژه اصلاً nullable analysis را روشن کرده یا نهFirst check whether nullable analysis is enabled

در پروژه‌های تازهٔ .NET معمولاً nullable فعال است؛ اما یک پروژهٔ قدیمی ممکن است warning ندهد. فایل `.csproj` را نگاه کن و یک null عمدی را compile کن تا به‌جای حدس، وضعیت واقعی را ببینی.

Recent .NET templates commonly enable nullable analysis, but an older project may not warn. Inspect the `.csproj` and compile an intentional null case so you see the actual setting rather than guessing.

Project.csproj
<PropertyGroup>
  <Nullable>enable</Nullable>
</PropertyGroup>

برای یک آزمایش تک‌فایلی می‌توان `#nullable enable` گذاشت؛ در پروژهٔ واقعی تنظیم `.csproj` معمولاً قرارداد روشن‌تری برای همهٔ فایل‌هاست. فعال‌کردن ممکن است warningهای قدیمی را آشکار کند؛ آن‌ها را یکی‌یکی با قرارداد واقعی اصلاح کن، نه اینکه همه را خاموش کنی.

For a one-file experiment, use `#nullable enable`; in a real project, the `.csproj` setting usually makes the policy clearer across files. Enabling it may reveal old warnings. Fix them against the real contract instead of turning them all off.

warning یعنی «قرارداد و کد را مقایسه کن»A warning means “compare the contract with the code”

گاهی نوع اشتباه nullable اعلام شده؛ گاهی واقعاً null ممکن است و caller باید آن را مدیریت کند. فقط یکی از این دو تغییر را با دلیل انجام بده: نوع را دقیق‌تر کن یا مسیر null را امن کن.

Sometimes the type is annotated incorrectly; sometimes null really is possible and the caller must handle it. Make one justified change: refine the type contract or handle the null path safely.

با بررسی شرطی، به compiler مدرک بدهGive the compiler evidence with a null check

همان کد را با guard اجرا کنیم. این بار بررسی فقط برای runtime نیست؛ تحلیل جریان کنترل compiler هم می‌فهمد داخل شاخه، `code` null نیست.

Run the same logic with a guard. This check is not only for runtime: compiler flow analysis also knows that `code` is not null inside the branch.

C# · flow analysis
static string DescribeCode(string? code)
{
    if (code is null)
        return "No code";

    return $"Code length: {code.Length}";
}

Console.WriteLine(DescribeCode(null));
Console.WriteLine(DescribeCode("SAVE10"));
خروجی / output
No code
Code length: 6

بعد از شرط `is null`، شاخهٔ اول برمی‌گردد؛ پس در خط بعد مسیر اجرا فقط وقتی ادامه دارد که `code` مقدار داشته باشد. early return هم guard را خوانا می‌کند، هم تحلیل compiler را ساده. مقایسهٔ `code == null` هم در این مورد قابل استفاده است؛ الگوی `is null` در برابر overload شدن `==` غافلگیر نمی‌شود.

The `is null` branch returns early, so execution reaches the next line only when `code` has a value. The early return makes the guard readable and flow analysis straightforward. `code == null` also works here; `is null` is not affected by an overloaded `==` operator.

compiler فقط جریان کدی را که می‌بیند دنبال می‌کند؛ از قراردادهای پنهان داخل هر متد خبر ندارد. اگر `EnsureLoaded(order)` از نظر برنامه تضمین می‌کند property پر شده، compiler لزوماً از اسم متد این را استنتاج نمی‌کند. یا قرارداد API را با نوع/attribute مناسب منتقل کن، یا مقدار را صریح بررسی کن.

The compiler tracks visible control flow; it does not know hidden guarantees inside every method. If `EnsureLoaded(order)` promises to populate a property, the compiler cannot infer that from the method name. Express the API contract with appropriate types/attributes or check the value explicitly.

وقتی نبودن یک مسیر عادی است، ?. و ?? کمک می‌کنندUse ?. and ?? when absence is an ordinary path

نام مشتری اختیاری است. هدف این نیست که null را هرجا دیدیم با متن تصادفی عوض کنیم؛ اول قرارداد خروجی را انتخاب می‌کنیم: آیا غیبت مجاز است یا گزارش حتماً یک label می‌خواهد؟

A customer name is optional. We should not replace every null with arbitrary text; first choose the output contract: is absence allowed, or must the report always have a label?

C# · ?. and ??
string? customerName = null;
int? nameLength = customerName?.Length;
string label = customerName ?? "Guest";

Console.WriteLine(nameLength is null);
Console.WriteLine(label);

string? suppliedCode = null;
suppliedCode ??= "NO-DISCOUNT";
Console.WriteLine(suppliedCode);
خروجی / output
True
Guest
NO-DISCOUNT

`?.` اگر سمت چپ null باشد، ادامهٔ دسترسی را اجرا نمی‌کند و برای نتیجهٔ value type معمولاً `Nullable<T>` می‌سازد؛ برای همین `nameLength` از نوع `int?` است. `??` وقتی سمت چپ null است fallback می‌دهد. `??=` فقط وقتی متغیر null باشد مقدار می‌نویسد.

If the left side of `?.` is null, member access is skipped; for a value-type result it produces a nullable value, which is why `nameLength` is `int?`. `??` supplies a fallback only when its left side is null. `??=` assigns only when its target is null.

fallback می‌تواند دادهٔ واقعی را جعل کندA fallback can invent business data

`?? 0` اگر null یعنی «قیمت هنوز بارگذاری نشده»، آن را بی‌صدا به قیمت صفر تبدیل می‌کند. فقط وقتی fallback بگذار که معنای دامنه‌ای دارد؛ وگرنه null را در نتیجه نگه دار یا خطای معتبر برگردان.

If null means “price not loaded yet,” `?? 0` silently turns it into a zero price. Use a fallback only when the domain defines one; otherwise preserve absence or return a meaningful error.

nullable value type، واقعاً مقدار یا نبود مقدار را نگه می‌داردA nullable value type stores a value—or its absence

در فصل ۱۱ دیدیم value type کپی مقدار دارد. برای عددی که شاید هنوز تنظیم نشده، `int?` یک مقدار underlying به‌علاوهٔ حالت نبودن دارد؛ default آن صفر نیست، null است.

In Chapter 11, we saw that value types copy their values. For a number that may not be set yet, `int?` carries an underlying value plus an absent state; its default is null, not zero.

C# · nullable value
int? retryLimit = null;
int effectiveLimit = retryLimit ?? 3;
Console.WriteLine($"has value: {retryLimit.HasValue}");
Console.WriteLine($"limit: {effectiveLimit}");

retryLimit = 0;
Console.WriteLine($"has value: {retryLimit.HasValue}");
Console.WriteLine($"configured: {retryLimit.Value}");
خروجی / output
has value: False
limit: 3
has value: True
configured: 0

صفر یک مقدار ثبت‌شده است؛ null یعنی مقداری ثبت نشده. `.Value` وقتی null باشد InvalidOperationException می‌دهد، پس معمولاً pattern matching یا `??` امن‌تر و روشن‌تر است. مقدار fallback در این مثال سیاست برنامه است، نه رفتار اجباری C#.

Zero is a configured value; null means no value was supplied. `.Value` throws InvalidOperationException when null, so pattern matching or `??` is usually clearer and safer. The fallback here is application policy, not a C# requirement.

برای `int? a` و `int? b`، عبارت `a + b` هم nullable است: اگر ورودی null باشد، نتیجه می‌تواند null بماند. پیش از جمع باید تصمیم بگیری نبود یکی از operandها یعنی «نتیجه نداریم»، یعنی صفر، یا یعنی ورودی نامعتبر.

For `int? a` and `int? b`, `a + b` is nullable too: if an input is null, the result can remain null. Before summing, decide whether a missing operand means “no result,” zero, or invalid input.

نوع خروجی، قول متد به caller استA return type is a promise to the caller

lookup کد تخفیف ممکن است چیزی پیدا نکند. اگر امضای متد `string` بگوید ولی گاهی null برگرداند، caller را با قرارداد نادرست تنها گذاشته‌ایم. نبودن را در نوع خروجی ثبت می‌کنیم.

A discount-code lookup may find nothing. If its signature says `string` but it sometimes returns null, the caller is left with a false contract. We encode absence in the return type.

C# · nullable API
static string? FindCode(string orderId) => orderId switch
{
    "A-42" => "SAVE10",
    _ => null
};

string message = FindCode("B-17") is { } code
    ? $"Code: {code}"
    : "No code for this order";
Console.WriteLine(message);

امضای `string?` حالا caller را مجبور می‌کند مسیر نبودن را ببیند. الگوی `{ } code` در شاخهٔ true یک مقدار non-null به نام `code` می‌دهد. اگر فقدان داده خطاست، به‌جای null می‌توان result/error صریح طراحی کرد؛ nullable annotation جای تصمیم دامنه‌ای نیست.

The `string?` signature makes the caller account for absence. The `{ } code` pattern provides a non-null `code` in the true branch. If absence is an error, design an explicit result/error instead; a nullable annotation does not decide domain policy.

اعتماد بیرونی را جای بررسی ننشانDo not replace boundary validation with trust

nullable analysis می‌تواند در تعامل با کتابخانهٔ بدون annotation یا دادهٔ deserialized محدود باشد. ورودی بیرونی را با validation مناسب بررسی کن؛ `string` در signature به‌تنهایی تضمین نمی‌کند JSON یا کد legacy مقدار non-null تحویل دهد.

Nullable analysis can be limited at boundaries with unannotated libraries or deserialized data. Validate external input appropriately; a `string` signature alone cannot guarantee that JSON or legacy code supplied a non-null value.

علامت ! فقط صدای compiler را کم می‌کندThe ! operator only silences the compiler

راه میان‌بر وسوسه‌کننده است: warning را با `!` حذف کنیم و برویم سراغ کار بعدی. آزمایش زیر نشان می‌دهد runtime از این علامت خبر ندارد.

The shortcut is tempting: add `!`, remove the warning and move on. This experiment shows that the runtime does not know about that operator.

C# · suppression is not validation
#nullable enable
string? code = null;
Console.WriteLine(code!.Length); // compiles without nullable warning; still throws

`!` فقط null-state تحلیل compiler را برای همان expression به not-null تغییر می‌دهد؛ مقدار را عوض نمی‌کند، بررسی runtime نمی‌سازد و exception را نمی‌گیرد. اگر invariant واقعی داری، آن را در یک نقطهٔ قابل‌اثبات بررسی کن؛ اگر نمی‌دانی، `!` مدرک نیست.

`!` only changes the compiler’s null-state assumption for that expression; it does not change the value, add a runtime check, or catch an exception. If an invariant is real, verify it at a provable boundary; if you do not know, `!` is not evidence.

آزمایشگاه: قرارداد پیدا کردن تخفیف را درست کنLab: repair the discount lookup contract

یک گزارش مبلغ، تخفیف اختیاری و کد سفارش دارد. حالت فعلی با رشتهٔ خالی نبودن را قایم کرده و یکی از مسیرها هم exception می‌دهد. اول رفتار را ثبت می‌کنیم، بعد قرارداد را انتخاب و دوباره همان ورودی‌ها را آزمایش می‌کنیم.

A price report has an optional discount and order code. The current version hides absence as an empty string and one path throws. First record behavior, then choose a contract and rerun the same inputs.

  1. یک console app بساز و nullable را در `.csproj` فعال کن. متد `FindCode(string orderId)` بساز که برای `A-42` کد و برای بقیه null برگرداند؛ warningها را نگه دار.
  2. Create a console app and enable nullable in the `.csproj`. Implement `FindCode(string orderId)` returning a code for `A-42` and null otherwise; keep the warnings.
  3. یک caller بنویس که بدون guard `FindCode(id).Length` را بخواند. warning را بخوان، اجرا کن و null case را جدا ثبت کن.
  4. Write a caller that reads `FindCode(id).Length` without a guard. Read the warning, run it, and record the null case separately.
  5. امضای درست را `string?` کن و سه ورودی را تست کن: کد موجود، نبودن کد و رشتهٔ خالی به‌عنوان ورودی. این سه حالت را با هم یکی نگیر.
  6. Change the contract to `string?` and test three inputs: a found code, no code, and an empty input string. Do not conflate these cases.
  7. گزارش را با pattern یا guard بازنویسی کن. برای مبلغ `decimal?` هم یک حالت «قیمت هنوز موجود نیست» و یک مبلغ صفر بساز؛ خروجی باید این تفاوت را حفظ کند.
  8. Rewrite the report with a pattern or guard. For a `decimal?` amount, create both “price unavailable” and zero; output must preserve the distinction.
  9. یک بار `!` اضافه کن و نشان بده فقط warning چه تغییری کرد؛ همان null را اجرا کن تا ببینی exception باقی می‌ماند.
  10. Add `!` once and show what changed in compiler diagnostics; run the same null and observe that the exception remains.
  11. در پایان جدول ورودی/خروجی بساز: کد موجود، کد پیدا نشده، ورودی خالی و مبلغ صفر. قرارداد متد و رفتار هر ردیف را کنار هم نگه دار.
  12. Finish with an input/output table for found code, missing code, empty input and zero amount. Keep each method contract beside its behavior.

switch pattern هر حالت را جدا می‌کند و امضای `string?` امکان نبودن را پیشاپیش اعلام می‌کند. در سامانهٔ واقعی شاید رشتهٔ خالی هم نامعتبر باشد؛ این آزمایش فقط نشان می‌دهد null، empty و صفر داده‌های متفاوت‌اند و policy باید از محصول بیاید.

The switch patterns separate each case, and `string?` advertises possible absence in advance. A real system may reject an empty string; this experiment only proves that null, empty and zero are distinct data states whose policy must come from the product.

تمرین‌ها: نبودن را صریح مدل کنExercises: model absence explicitly

هر تمرین باید با compile، خروجی، warning یا exception جواب بگیرد. اگر repair می‌کنی، همان ورودی را قبل و بعد اجرا کن تا معلوم شود قرارداد واقعاً عوض شده.

Use compilation, output, warnings or an exception as evidence. When repairing, rerun the same input before and after so the changed contract is visible.

۱) warning را به مسیر ناامن وصل کن1) Connect a warning to an unsafe path

`string? code = null; Console.WriteLine(code.Length);` را با nullable روشن build و اجرا کن. warning چه چیزی می‌گوید و runtime چه می‌کند؟

Build and run `string? code = null; Console.WriteLine(code.Length);` with nullable enabled. What does the warning say, and what happens at runtime?

پاسخAnswer

compiler warning مربوط به dereference مقدار maybe-null می‌دهد؛ اجرای برنامه NullReferenceException می‌دهد. warning پیش‌بینی خطر است، نه جلوگیری خودکار از اجرا.

The compiler warns about dereferencing a maybe-null value; execution throws NullReferenceException. The warning predicts risk but does not automatically block execution.

۲) string خالی را با null یکی نگیر2) Do not conflate empty string and null

برای `null`، `""` و `"SAVE"` خروجی `code is null` و `code.Length` را ثبت کن؛ هر سه را با یک fallback پنهان نکن.

For null, `""` and `"SAVE"`, record `code is null` and `code.Length`; do not hide all three behind one fallback.

مشاهدهObservation

null شرط را true می‌کند و طول ندارد؛ رشتهٔ خالی null نیست و طولش صفر است؛ SAVE طول ۴ دارد. اینکه رشتهٔ خالی معتبر باشد تصمیم دامنه است.

Null passes the null check and has no length; empty string is non-null with length zero; SAVE has length four. Whether empty is valid is a domain decision.

۳) guard را طوری بنویس که flow analysis بفهمد3) Write a guard flow analysis understands

متد `Format(string? name)` بساز. اگر null بود زود برگردد؛ در مسیر دیگر طول و متن را چاپ کن و build را بررسی کن.

Write `Format(string? name)`. Return early on null; otherwise print its length and text, then inspect the build.

نمونهٔ اصلاحSample repair
C#
static string Format(string? name)
{
    if (name is null) return "Guest";
    return $"{name} ({name.Length})";
}

بعد از return، compiler می‌داند ادامهٔ متد null نیست. برای null خروجی Guest و برای بقیه طول واقعی داریم.

After the return, the compiler knows the remaining path is non-null. Null yields Guest; other values keep their real length.

۴) ! را درمان ندان4) Do not treat ! as a fix

روی متغیر null علامت `!` بگذار، build و run را جدا انجام بده. دقیقاً کدام نتیجه عوض شد و کدام نه؟

Apply `!` to a null variable; build and run separately. Which result changed, and which did not?

تفسیرInterpretation

warning nullable سرکوب می‌شود؛ مقدار runtime هنوز null است و dereference همچنان exception می‌دهد. عملگر null-forgiving بررسی runtime نیست.

The nullable warning is suppressed; the runtime value remains null and dereferencing still throws. The null-forgiving operator is not a runtime check.

۵) fallback را با قرارداد انتخاب کن5) Choose a fallback from the contract

برای `string? displayName` از `?? "Guest"` استفاده کن. یک کاربرد که fallback درست است و یک کاربرد که این fallback داده را جعل می‌کند اجرا کن.

Use `?? "Guest"` for `string? displayName`. Run one case where the fallback is valid and another where it invents data.

معیارCriterion

برای نمایش صفحهٔ خوشامد شاید Guest قرارداد محصول باشد؛ برای نام گیرندهٔ فاکتور ممکن است باید خطا بدهیم نه اینکه شخص خیالی ثبت کنیم. `??` فقط null را جایگزین می‌کند، معنای fallback را تعیین نمی‌کند.

Guest may be a valid greeting policy; an invoice recipient may instead require an error rather than an invented person. `??` replaces null but does not define the fallback’s meaning.

۶) ?. را تا نتیجهٔ nullable دنبال کن6) Trace ?. to its nullable result

`string? name = null; int? length = name?.Length;` را اجرا کن و نوع و مقدار `length` را با name غیر null مقایسه کن.

Run `string? name = null; int? length = name?.Length;` and compare the type/value of `length` when name is non-null.

خروجیOutput

با name تهی، length هم null است؛ با مقدار «Mina»، مقدار ۴ می‌شود. دسترسی شرطی از exception جلوگیری می‌کند، ولی null را به صفر تبدیل نمی‌کند.

With a null name, length is null; with “Mina,” it is 4. Conditional access avoids that dereference but does not turn absence into zero.

۷) ??= را در ورودی تکراری بررسی کن7) Inspect ??= with repeated input

یک label nullable بساز و دو مقدار متفاوت را با `??=` به آن پیشنهاد بده. هر دو بار چاپ کن و توضیح بده assignment چه زمانی رخ داد.

Create a nullable label and apply `??=` with two different candidate values. Print after each and explain when assignment occurred.

رفتارBehavior

فقط بار اول که مقصد null است مقدار می‌گیرد؛ پیشنهاد دوم مقدار موجود را overwrite نمی‌کند. اگر overwrite می‌خواهی، assignment معمولی یا شرط دیگری لازم است.

Only the first assignment occurs while the target is null; the second candidate does not overwrite an existing value. Use ordinary assignment or another condition when overwriting is intended.

۸) zero را از unset جدا کن8) Distinguish zero from unset

دو `int?` یکی null و یکی صفر بساز. `HasValue` و `?? 5` را چاپ کن؛ کدام مسیر fallback می‌گیرد؟

Create two `int?` values: null and zero. Print `HasValue` and `?? 5`; which one uses the fallback?

پاسخAnswer

null مقدار ۵ می‌گیرد؛ صفر دارای مقدار است و صفر می‌ماند. `??` بر اساس null تصمیم می‌گیرد، نه falsy بودن عدد.

Null becomes 5; zero is present and remains zero. `??` tests null, not numeric falsiness.

۹) جمع nullable را پیش‌بینی کن9) Predict nullable arithmetic

`int? a=7, b=null; int? sum=a+b;` را چاپ کن. بعد دو policy مختلف برای «یکی از اعداد نیامده» پیاده کن.

Print `int? a=7, b=null; int? sum=a+b;`. Then implement two policies for “one number was not supplied.”

توضیحExplanation

جمع null است؛ nullable arithmetic نبودن را منتقل می‌کند. policy اول حفظ نبودن است؛ policy دیگر می‌تواند `a.GetValueOrDefault() + b.GetValueOrDefault()` باشد، اما این یعنی هر دو null را صفر فرض کرده‌ایم و باید این تصمیم عمدی باشد.

The sum is null; nullable arithmetic propagates absence. One policy preserves absence. Another can use `GetValueOrDefault`, but that assumes null means zero and must be an intentional choice.

۱۰) Value را بدون guard نخوان10) Do not read Value without a guard

`decimal? price = null; price.Value` را اجرا کن. بعد با `is decimal amount` یا `??` خطا را به رفتار صریح تبدیل کن.

Run `decimal? price = null; price.Value`, then make the behavior explicit with `is decimal amount` or `??`.

راه امنSafer path

pattern فقط در شاخهٔ دارای مقدار، amount را می‌دهد؛ `??` fallback را انتخاب می‌کند. `.Value` برای حالتی است که قبلاً وجود مقدار را ثابت کرده‌ای، نه راه تست کردن آن.

The pattern exposes amount only in the present branch; `??` chooses a fallback. `.Value` is for a value already proven present, not a way to test presence.

۱۱) خروجی API را با واقعیت هماهنگ کن11) Align an API return type with reality

`FindOrder(string id)` گاهی چیزی پیدا نمی‌کند. امضای غیر nullable را اصلاح کن و دو caller بساز: یکی نبودن را طبیعی می‌داند، دیگری آن را خطا می‌گیرد.

`FindOrder(string id)` sometimes finds nothing. Fix its signature and create two callers: one treats absence as normal; the other treats it as an error.

مدل طراحیDesign model

اگر نبودن معمول است، `Order? FindOrder(...)` و guard مناسب. اگر نبودن نقض قرارداد است، exception/result صریح مناسب‌تر است. nullable بودن خروجی دربارهٔ سیاست caller تصمیم نمی‌گیرد.

If absence is normal, return `Order?` and handle it. If absence violates the contract, an explicit exception/result may be clearer. A nullable return does not choose caller policy.

۱۲) پروژهٔ قدیمی را با یک warning شروع کن12) Start a legacy migration with one warning

یک property قدیمی nullable را پیدا کن، nullable context را در یک محدوده روشن کن و اولین warning را با تست تعیین کن: داده واقعاً اختیاری است یا invariant شکسته؟

Find one legacy nullable property, enable nullable context for a limited scope, and use a test to decide whether the data is truly optional or an invariant is broken.

قدم اولFirst step

نوع را کورکورانه `?` نکن. fixtureی بساز که null رخ می‌دهد؛ اگر مجاز است امضا و caller را اصلاح کن، اگر نامجاز است منبع مقدار را validate و invariant را نگه دار.

Do not add `?` blindly. Create a fixture that produces null; if allowed, update the signature and callers, otherwise validate the source and preserve the invariant.

۱۳) ورودی legacy را پشت مرز اعتبارسنجی بگذار13) Validate a legacy input at the boundary

یک متد بدون annotation مقدار ممکن-null می‌دهد. مقدار را به API داخلی non-nullable می‌فرستی. warning را با guard معتبر برطرف کن و ورودی null را اجرا کن.

An unannotated method may return null, but an internal API requires non-null. Add a real guard, then run the null input.

توضیحExplanation

مرز را با null-check، validation یا تبدیل به خطای دامنه‌ای حل کن. `!` فقط warning boundary را می‌پوشاند و رفتار legacy را امن نمی‌کند.

Handle the boundary with a null check, validation or domain error. `!` only hides the boundary warning; it does not make legacy behavior safe.

۱۴) warning را با ! خاموش کن یا contract را درست کن؟14) Silence a warning with ! or repair the contract?

یک helper همیشه گاهی null می‌دهد ولی امضایش `string` است. دو اصلاح را مقایسه کن و build/test نشان بده کدام‌یک اطلاعات بیشتری به caller می‌دهد.

A helper sometimes returns null but declares `string`. Compare two repairs and use build/tests to show which communicates more to the caller.

پاسخAnswer

تغییر امضا به `string?` و مدیریت مسیر null contract را دقیق می‌کند. `!` فقط یک محل را ساکت می‌کند و contradiction را باقی می‌گذارد. اگر متد نباید null دهد، bug تولیدکننده را repair کن.

Changing the signature to `string?` and handling absence makes the contract honest. `!` silences one site and leaves the contradiction. If null is forbidden, repair the producer bug instead.

۱۵) دامنهٔ nullable analysis را آزمایش کن15) Test the limits of nullable analysis

property nullable را در یک متد مقداردهی کن و متد جداگانه‌ای برای آماده‌سازی صدا بزن. آیا compiler از بدنهٔ متد فراخوانی‌شده invariant را می‌فهمد؟ با build ثابت کن.

Set a nullable property through a separate preparation method. Does the compiler infer that method’s invariant? Prove the result with a build.

نتیجهResult

تحلیل عادی وارد بدنهٔ همهٔ متدها نمی‌شود تا قرارداد را حدس بزند. annotation مناسب یا بازطراحی API می‌تواند ضمانت را بیان کند؛ وگرنه check صریح لازم است.

Ordinary flow analysis does not inspect every method body to guess its contract. An appropriate annotation or API redesign can express the guarantee; otherwise, check explicitly.

۱۶) ticket «قیمت صفر شد» را عیب‌یابی کن16) Diagnose the “price became zero” ticket

یک endpoint مقدار null را با `?? 0m` جایگزین کرده است. دو علت متفاوت برای null پیشنهاد بده؛ برای هرکدام رفتار درست و تستی بنویس که صفر واقعی را از مبلغ ناموجود جدا کند.

An endpoint replaces null with `?? 0m`. Propose two distinct causes for null; define the right behavior and a test that distinguishes a real zero from a missing amount.

مسیر تشخیصDiagnosis path

ممکن است price هنوز بارگذاری نشده باشد یا سفارش واقعاً قیمت نداشته باشد؛ یکی retry/loading می‌خواهد و دیگری validation/domain error. تست باید هم `0m` و هم null را جدا assert کند. نمایش هر دو به‌صورت صفر، شاهد را از بین برده است.

The price may not have loaded yet, or the order may genuinely lack a price; one may require loading/retry, the other validation or a domain error. Test `0m` and null separately. Rendering both as zero erased the evidence.

null را با صفر و رشتهٔ خالی یکی نکنDo not confuse null with zero or empty text

برای هر داده بپرس: نبودن مجاز است؟ اگر بله، آن را در type (`string?`، `int?` یا return contract) نشان بده و caller را با guard، pattern، `?.` یا `??` آگاهانه مدیریت کن. اگر مجاز نیست، در مرز ورودی جلویش را بگیر و invariant را حفظ کن. warning را با دلیل حل کن؛ `!` فقط وقتی قابل دفاع است که مدرک بیرونیِ روشنی داری و محل اعتماد را می‌پذیری.

For each value, ask whether absence is allowed. If so, express it in the type (`string?`, `int?`, or the return contract) and handle it deliberately with a guard, pattern, `?.`, or `??`. If it is forbidden, reject it at the input boundary and preserve the invariant. Resolve warnings with evidence; use `!` only when you have a clear external guarantee and accept that trust boundary.
