اندازه‌گیری با BenchmarkDotNet

Measurement with BenchmarkDotNet

کد تازه رو اجرا می‌کنیم و stopwatch می‌گه روش دوم دو برابر سریع‌تر هست. اما بار اول JIT بوده، Debug اجرا شده و نتیجهٔ محاسبه حتی استفاده نشده. این عدد جواب نیست؛ سرنخ هست. در این فصل benchmark رو به آزمایشی قابل‌تکرار تبدیل می‌کنیم: ورودی برابر، build بهینه، warmup، چند اندازه‌گیری و گزارش allocation و پراکندگی.

A stopwatch says the new implementation is twice as fast. But the first run included JIT, the build was Debug, and the computed result was unused. That number is not an answer; it is a clue. We turn benchmarking into a repeatable experiment with equal inputs, optimized builds, warmup, multiple measurements and allocation/variance reports.

اول سؤال اندازه‌گیری رو دقیق کنMake the measurement question precise first

«کدوم سریع‌تر هست؟» ناقص هست. کدوم operation، روی چه input، در چه runtime و چه محیطی؟ آیا latency مهمه یا allocations، throughput یا startup؟ دو الگوریتم رو با داده و خروجی یکسان مقایسه کن؛ setup مشترک رو از متد benchmark بیرون بگذار، مگر اینکه setup بخشی از کاری باشه که عمداً می‌سنجی. نتیجهٔ benchmark به سخت‌افزار، runtime، JIT و بار سیستم وابسته هست.

“Which is faster?” is incomplete. Which operation, on what input, under which runtime and environment? Is latency, allocation, throughput or startup important? Compare algorithms using equivalent inputs and outputs; keep shared setup outside benchmark methods unless setup is intentionally part of the measured work. Results depend on hardware, runtime, JIT and system load.

پروژهٔ benchmark باید Console و Release باشهA benchmark project should be a console app run in Release

BenchmarkDotNet یک process جدا و اجرای کنترل‌شده می‌سازه؛ package رو به یک console project جدا اضافه کن تا benchmark وارد برنامهٔ production نشه. برنامه رو از خط فرمان و با configuration برابر Release اجرا کن؛ debugger متصل و build Debug نتیجه رو مخدوش می‌کنن. نسخهٔ SDK/runtime و سیستم‌عامل رو همراه گزارش نگه دار، چون عدد فقط در همان شرایط معنا داره.

BenchmarkDotNet creates controlled runs in separate processes; put the package in a separate console project so benchmarks do not leak into production. Run from the command line in Release; a debugger or Debug build distorts results. Record SDK/runtime and OS with the report because measurements are meaningful only in their context.

ساخت و اجرا / Create and run
dotnet new console -n Parser.Benchmarks
cd Parser.Benchmarks
dotnet add package BenchmarkDotNet
dotnet run -c Release

فرمان نسخهٔ SDK رو انتخاب نمی‌کنه؛ target framework در csproj و SDK نصب‌شده باید با محیط موردنظر سازگار باشه. benchmark برای ASP.NET server مستقیماً جای load test رو نمی‌گیره؛ اینجا هزینهٔ یک operation محدود رو می‌سنجیم.

These commands do not choose an SDK version; the target framework and installed SDK must match the intended environment. A microbenchmark is not a load test for an ASP.NET server; it measures a bounded operation.

ورودی رو آماده کن و خروجی رو مصرف کنPrepare inputs and consume results

ساخت input در هر iteration می‌تونه هزینهٔ target رو با setup قاطی کند. برای ورودی ثابت از GlobalSetup استفاده کن؛ برای اندازه‌های متفاوت [Params] بگذار تا یک نقطهٔ خوش‌شانس نتیجه رو تعیین نکند. مقدار برگشتی رو برگردان یا مصرف کن تا JIT کار بی‌اثر رو حذف نکند. اگه benchmark دو implementation داره، baseline تعریف کن تا نسبت فقط برای همان workload خوانده بشه.

Creating input on every iteration can mix setup cost with target cost. Use GlobalSetup for fixed input and [Params] for varying sizes so one lucky point does not dominate. Return or consume the result so the JIT cannot remove irrelevant work. Set a baseline when comparing implementations so the ratio refers to that workload.

مقایسهٔ دو parser / Compare two parsers
[MemoryDiagnoser]
public class ParserBenchmarks
{
    private string _line = null!;

    [Params(32, 256, 4096)]
    public int Length { get; set; }

    [GlobalSetup]
    public void Setup() => _line = CreateLine(Length);

    [Benchmark(Baseline = true)]
    public int SplitParser() => ParseWithSplit(_line).Code;

    [Benchmark]
    public int SpanParser() => ParseWithSpan(_line).Code;
}

برای اعتبار مقایسه، هر دو مسیر باید semantics برابر داشته باشن؛ اگه یکی validation یا allocation عمدی رو جا می‌اندازد، benchmark برندهٔ ناعادلانه می‌سازه. خروجی رو در بررسی correctness تست کن و BenchmarkDotNet رو فقط برای زمان‌گیری صدا بزن.

For a fair comparison, both paths must have equivalent semantics; skipping validation or deliberate allocation in one implementation creates an unfair winner. Verify output correctness in tests and use BenchmarkDotNet for measurement.

Mean تنها خلاصهٔ داستان نیستThe mean is not the whole story

BenchmarkDotNet warmup و اندازه‌گیری‌های متعدد انجام می‌ده و summaryهایی مثل Mean، Error و StdDev نشان می‌ده. تفاوت کوچک‌تر از نویز یا uncertainty ممکنه تصمیم مهندسی رو توجیه نکند. تعداد رقم اعشار، قطعیت نیست. اگه توزیع دو روش هم‌پوشانی داره یا outlier دیده می‌شه، شرایط اجرا و خود workload رو بررسی کن؛ لازم نیست همیشه هر اختلاف آماری رو به بهبود محصول ترجمه کنی.

BenchmarkDotNet performs warmup and multiple measurements and reports summaries such as Mean, Error and StdDev. A difference smaller than noise or uncertainty may not justify an engineering change. Decimal places do not imply certainty. If distributions overlap or outliers appear, inspect the environment and workload; not every measured difference is a product improvement.

MemoryDiagnoser در بسیاری از سناریوها برای allocation managed مفید هست، اما ابزار جامع native-memory یا profiler همه‌منظوره نیست. اگه نتیجه به GC، lock یا I/O حساس هست، تشخیص مناسب‌تری رو جداگانه اضافه کن؛ یک جدول benchmark جای trace سیستم واقعی رو نمی‌گیره.

MemoryDiagnoser is useful for managed allocations in many scenarios, but it is not a complete native-memory or general-purpose profiler. If results depend on GC, locks or I/O, add suitable diagnostics separately; a benchmark table is not a trace of a real system.

benchmark خراب، عدد دقیق هم تولید می‌کنهA flawed benchmark can still produce precise numbers

benchmark رو روی production data مخرب، سرویس مشترک یا loop بی‌نهایت اجرا نکن. I/O شبکه و دیسک معمولاً benchmark جداگانه و کنترل‌پذیر می‌خواد. از dead-code elimination، ورودی ثابت بیش از حد ساده، ساخت داده در hot path، مقایسهٔ خروجی‌های متفاوت، و اجرای چند workload هم‌زمان دوری کن. با workload کوچک شروع کن و مدت اجرا و منابع مصرفی رو کنترل کن.

Do not run benchmarks against destructive production data, shared services or unbounded loops. Network and disk I/O usually need separate, controllable benchmarks. Avoid dead-code elimination, unrealistically simple constant inputs, creating data in the hot path, comparing different outputs and running multiple workloads at once. Start small and control duration and resource use.

انتخاب benchmark / Select benchmark cases
[MemoryDiagnoser]
[ShortRunJob]
public class LookupBenchmarks
{
    [Params(16, 1024)]
    public int Count { get; set; }

    [GlobalSetup]
    public void Setup() => _items = BuildItems(Count);

    [Benchmark]
    public bool Lookup() => _items.Contains(_target);
}

ShortRun فقط برای بررسی اولیه و زمان سریع‌تر مفید هست؛ نتیجهٔ کم‌نمونه رو حکم نهایی تلقی نکن. برای گزارش قابل‌مقایسه، job پیش‌فرض یا تنظیمات مستند پروژه رو اجرا کن و نسخهٔ code، runtime، machine و command رو کنار artifact ثبت کن.

ShortRun is useful for a quick smoke check, not a final verdict from few samples. For comparable reports, use a documented job and record code revision, runtime, machine and command alongside the artifact.

عدد بهتر باید به تصمیم بهتر ختم بشهA better number should lead to a better decision

نتیجه رو با نیاز محصول تفسیر کن: اگه operation در روز یک‌بار اجرا می‌شه، صرفه‌جویی چند نانوثانیه احتمالاً اولویت نیست؛ اگه در هر درخواست و میلیون‌ها بار اجرا می‌شه، کاهش allocation شاید مهم باشه. سادگی، correctness، نگه‌داری و tail latency نیز هزینه‌اند. benchmark فرضیه رو می‌سنجد؛ بعد از تغییر، correctness test رو دوباره اجرا کن و در صورت نیاز روی staging زیر بار end-to-end verify کن.

Interpret results against product needs: saving a few nanoseconds on an operation run once a day is probably not a priority; reducing allocations in a hot path executed millions of times may matter. Simplicity, correctness, maintainability and tail latency are costs too. A benchmark tests a hypothesis; after a change, rerun correctness tests and, where needed, verify end-to-end under staging load.

Build two equivalent log parsers: a straightforward Split version and a lower-allocation Span version. First use correctness tests to compare outputs for valid, incomplete and invalid lines.
