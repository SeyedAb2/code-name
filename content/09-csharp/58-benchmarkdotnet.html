اندازه‌گیری با BenchmarkDotNet

Measurement with BenchmarkDotNet

کد تازه را اجرا می‌کنیم و stopwatch می‌گوید روش دوم دو برابر سریع‌تر است. اما بار اول JIT بوده، Debug اجرا شده و نتیجهٔ محاسبه حتی استفاده نشده. این عدد جواب نیست؛ سرنخ است. در این فصل benchmark را به آزمایشی قابل‌تکرار تبدیل می‌کنیم: ورودی برابر، build بهینه، warmup، چند اندازه‌گیری و گزارش allocation و پراکندگی.

A stopwatch says the new implementation is twice as fast. But the first run included JIT, the build was Debug, and the computed result was unused. That number is not an answer; it is a clue. We turn benchmarking into a repeatable experiment with equal inputs, optimized builds, warmup, multiple measurements and allocation/variance reports.

اول سؤال اندازه‌گیری را دقیق کنMake the measurement question precise first

«کدام سریع‌تر است؟» ناقص است. کدام operation، روی چه input، در چه runtime و چه محیطی؟ آیا latency مهم است یا allocations، throughput یا startup؟ دو الگوریتم را با داده و خروجی یکسان مقایسه کن؛ setup مشترک را از متد benchmark بیرون بگذار، مگر اینکه setup بخشی از کاری باشد که عمداً می‌سنجی. نتیجهٔ benchmark به سخت‌افزار، runtime، JIT و بار سیستم وابسته است.

“Which is faster?” is incomplete. Which operation, on what input, under which runtime and environment? Is latency, allocation, throughput or startup important? Compare algorithms using equivalent inputs and outputs; keep shared setup outside benchmark methods unless setup is intentionally part of the measured work. Results depend on hardware, runtime, JIT and system load.

پروژهٔ benchmark باید Console و Release باشدA benchmark project should be a console app run in Release

BenchmarkDotNet یک process جدا و اجرای کنترل‌شده می‌سازد؛ package را به یک console project جدا اضافه کن تا benchmark وارد برنامهٔ production نشود. برنامه را از خط فرمان و با configuration برابر Release اجرا کن؛ debugger متصل و build Debug نتیجه را مخدوش می‌کنند. نسخهٔ SDK/runtime و سیستم‌عامل را همراه گزارش نگه دار، چون عدد فقط در همان شرایط معنا دارد.

BenchmarkDotNet creates controlled runs in separate processes; put the package in a separate console project so benchmarks do not leak into production. Run from the command line in Release; a debugger or Debug build distorts results. Record SDK/runtime and OS with the report because measurements are meaningful only in their context.

ساخت و اجرا / Create and run
dotnet new console -n Parser.Benchmarks
cd Parser.Benchmarks
dotnet add package BenchmarkDotNet
dotnet run -c Release

فرمان نسخهٔ SDK را انتخاب نمی‌کند؛ target framework در csproj و SDK نصب‌شده باید با محیط موردنظر سازگار باشد. benchmark برای ASP.NET server مستقیماً جای load test را نمی‌گیرد؛ اینجا هزینهٔ یک operation محدود را می‌سنجیم.

These commands do not choose an SDK version; the target framework and installed SDK must match the intended environment. A microbenchmark is not a load test for an ASP.NET server; it measures a bounded operation.

ورودی را آماده کن و خروجی را مصرف کنPrepare inputs and consume results

ساخت input در هر iteration می‌تواند هزینهٔ target را با setup قاطی کند. برای ورودی ثابت از GlobalSetup استفاده کن؛ برای اندازه‌های متفاوت [Params] بگذار تا یک نقطهٔ خوش‌شانس نتیجه را تعیین نکند. مقدار برگشتی را برگردان یا مصرف کن تا JIT کار بی‌اثر را حذف نکند. اگر benchmark دو implementation دارد، baseline تعریف کن تا نسبت فقط برای همان workload خوانده شود.

Creating input on every iteration can mix setup cost with target cost. Use GlobalSetup for fixed input and [Params] for varying sizes so one lucky point does not dominate. Return or consume the result so the JIT cannot remove irrelevant work. Set a baseline when comparing implementations so the ratio refers to that workload.

مقایسهٔ دو parser / Compare two parsers
[MemoryDiagnoser]
public class ParserBenchmarks
{
    private string _line = null!;

    [Params(32, 256, 4096)]
    public int Length { get; set; }

    [GlobalSetup]
    public void Setup() => _line = CreateLine(Length);

    [Benchmark(Baseline = true)]
    public int SplitParser() => ParseWithSplit(_line).Code;

    [Benchmark]
    public int SpanParser() => ParseWithSpan(_line).Code;
}

برای اعتبار مقایسه، هر دو مسیر باید semantics برابر داشته باشند؛ اگر یکی validation یا allocation عمدی را جا می‌اندازد، benchmark برندهٔ ناعادلانه می‌سازد. خروجی را در بررسی correctness تست کن و BenchmarkDotNet را فقط برای زمان‌گیری صدا بزن.

For a fair comparison, both paths must have equivalent semantics; skipping validation or deliberate allocation in one implementation creates an unfair winner. Verify output correctness in tests and use BenchmarkDotNet for measurement.

Mean تنها خلاصهٔ داستان نیستThe mean is not the whole story

BenchmarkDotNet warmup و اندازه‌گیری‌های متعدد انجام می‌دهد و summaryهایی مثل Mean، Error و StdDev نشان می‌دهد. تفاوت کوچک‌تر از نویز یا uncertainty ممکن است تصمیم مهندسی را توجیه نکند. تعداد رقم اعشار، قطعیت نیست. اگر توزیع دو روش هم‌پوشانی دارد یا outlier دیده می‌شود، شرایط اجرا و خود workload را بررسی کن؛ لازم نیست همیشه هر اختلاف آماری را به بهبود محصول ترجمه کنی.

BenchmarkDotNet performs warmup and multiple measurements and reports summaries such as Mean, Error and StdDev. A difference smaller than noise or uncertainty may not justify an engineering change. Decimal places do not imply certainty. If distributions overlap or outliers appear, inspect the environment and workload; not every measured difference is a product improvement.

MemoryDiagnoser در بسیاری از سناریوها برای allocation managed مفید است، اما ابزار جامع native-memory یا profiler همه‌منظوره نیست. اگر نتیجه به GC، lock یا I/O حساس است، تشخیص مناسب‌تری را جداگانه اضافه کن؛ یک جدول benchmark جای trace سیستم واقعی را نمی‌گیرد.

MemoryDiagnoser is useful for managed allocations in many scenarios, but it is not a complete native-memory or general-purpose profiler. If results depend on GC, locks or I/O, add suitable diagnostics separately; a benchmark table is not a trace of a real system.

benchmark خراب، عدد دقیق هم تولید می‌کندA flawed benchmark can still produce precise numbers

benchmark را روی production data مخرب، سرویس مشترک یا loop بی‌نهایت اجرا نکن. I/O شبکه و دیسک معمولاً benchmark جداگانه و کنترل‌پذیر می‌خواهد. از dead-code elimination، ورودی ثابت بیش از حد ساده، ساخت داده در hot path، مقایسهٔ خروجی‌های متفاوت، و اجرای چند workload هم‌زمان دوری کن. با workload کوچک شروع کن و مدت اجرا و منابع مصرفی را کنترل کن.

Do not run benchmarks against destructive production data, shared services or unbounded loops. Network and disk I/O usually need separate, controllable benchmarks. Avoid dead-code elimination, unrealistically simple constant inputs, creating data in the hot path, comparing different outputs and running multiple workloads at once. Start small and control duration and resource use.

انتخاب benchmark / Select benchmark cases
[MemoryDiagnoser]
[ShortRunJob]
public class LookupBenchmarks
{
    [Params(16, 1024)]
    public int Count { get; set; }

    [GlobalSetup]
    public void Setup() => _items = BuildItems(Count);

    [Benchmark]
    public bool Lookup() => _items.Contains(_target);
}

ShortRun فقط برای بررسی اولیه و زمان سریع‌تر مفید است؛ نتیجهٔ کم‌نمونه را حکم نهایی تلقی نکن. برای گزارش قابل‌مقایسه، job پیش‌فرض یا تنظیمات مستند پروژه را اجرا کن و نسخهٔ code، runtime، machine و command را کنار artifact ثبت کن.

ShortRun is useful for a quick smoke check, not a final verdict from few samples. For comparable reports, use a documented job and record code revision, runtime, machine and command alongside the artifact.

عدد بهتر باید به تصمیم بهتر ختم شودA better number should lead to a better decision

نتیجه را با نیاز محصول تفسیر کن: اگر operation در روز یک‌بار اجرا می‌شود، صرفه‌جویی چند نانوثانیه احتمالاً اولویت نیست؛ اگر در هر درخواست و میلیون‌ها بار اجرا می‌شود، کاهش allocation شاید مهم باشد. سادگی، correctness، نگه‌داری و tail latency نیز هزینه‌اند. benchmark فرضیه را می‌سنجد؛ بعد از تغییر، correctness test را دوباره اجرا کن و در صورت نیاز روی staging زیر بار end-to-end verify کن.

Interpret results against product needs: saving a few nanoseconds on an operation run once a day is probably not a priority; reducing allocations in a hot path executed millions of times may matter. Simplicity, correctness, maintainability and tail latency are costs too. A benchmark tests a hypothesis; after a change, rerun correctness tests and, where needed, verify end-to-end under staging load.

تمرین: نتیجه را درست تفسیر کنExercises: interpret results carefully

۱) stopwatch تک‌اجرا1) One stopwatch run

یک اجرا سریع‌تر شده؛ چه چیزهایی را پیش از ادعا کنترل می‌کنی؟

One run is faster. What do you check before making a claim?

راهنماHint

warmup/JIT، Release، input، debugger، load ماشین و تکرار اندازه‌گیری را کنترل کن.

Control warmup/JIT, Release, inputs, debugger, machine load and repeated measurements.

۲) Debug build2) Debug build

آیا می‌توان benchmark Debug را بهینه‌سازی production تعمیم داد؟

Can a Debug benchmark be generalized to production optimization?

راهنماHint

نه؛ benchmark را از خط فرمان در Release و بدون debugger اجرا کن.

No; run from the command line in Release without a debugger.

۳) محاسبهٔ حذف‌شده3) Eliminated calculation

متد benchmark مقدار را محاسبه می‌کند ولی دور می‌اندازد. خطر چیست؟

A benchmark computes a value and discards it. What is the risk?

راهنماHint

JIT ممکن است کد بی‌اثر را حذف کند؛ خروجی را برگردان یا مصرف کن.

The JIT may eliminate dead work; return or consume the result.

۴) setup داخل benchmark4) Setup inside the benchmark

ساخت input بخش عمدهٔ زمان را می‌گیرد اما هدف، parse است. setup را کجا می‌بری؟

Input creation dominates, but the target is parsing. Where does setup go?

راهنماHint

به GlobalSetup، مگر اینکه ساخت input بخشی از مسیر مورد سنجش باشد.

Move it to GlobalSetup unless input creation is part of the intended operation.

۵) یک input خوش‌شانس5) One lucky input

روش A در طول ۳۲ برنده است اما در ۴KB می‌بازد؛ مقایسه را چطور طراحی می‌کنی؟

A wins at length 32 but loses at 4 KB. How do you structure the comparison?

راهنماHint

از Params برای اندازه‌های نماینده استفاده و نتایج را به تفکیک تحلیل کن.

Use Params for representative sizes and analyze results per size.

۶) نتیجه‌های متفاوت6) Different semantics

A فقط parse می‌کند و B validation هم دارد؛ آیا نسبت سرعت منصفانه است؟

A only parses while B also validates. Is the speed ratio fair?

راهنماHint

نه؛ ورودی و semantics خروجی را برابر کن یا هزینه‌ها را جدا اندازه بگیر.

No; equalize input and semantics or measure the costs separately.

۷) ratio7) Ratio

ratio برابر ۰٫۸ است و baseline را A گذاشته‌ای؛ آن را با احتیاط تفسیر کن.

The ratio is 0.8 with A as baseline. Interpret it carefully.

راهنماHint

در همان job و ورودی، B حدود ۲۰٪ زمان میانگین A را مصرف کرده؛ محیط و پراکندگی همچنان مهم‌اند.

Under that job and input, B uses about 80% of A's mean time; environment and variance still matter.

۸) allocation کمتر8) Fewer allocations

نسخهٔ جدید allocation را نصف کرده اما زمان ثابت است؛ آیا حتماً بهتر است؟

The new version halves allocations but time is unchanged. Is it necessarily better?

راهنماHint

به workload، GC pressure و هدف محصول بستگی دارد؛ allocation metric را به latency یا ظرفیت واقعی ربط بده.

It depends on workload, GC pressure and product goals; relate allocation to real latency or capacity.

۹) StdDev بزرگ9) Large standard deviation

میانگین‌ها نزدیک‌اند ولی پراکندگی بزرگ است؛ قدم بعدی چیست؟

Means are close but variance is large. What is next?

راهنماHint

ماشین را خلوت، workload را پایدار و اندازه‌گیری را تکرار کن؛ عدم قطعیت را گزارش بده.

Reduce machine noise, stabilize workload and repeat; report uncertainty honestly.

۱۰) I/O benchmark10) I/O benchmark

می‌خواهی سرعت دانلود واقعی کاربران را با microbenchmark بسنجی؛ چه چیزی نامتناسب است؟

You want a microbenchmark to measure users' real download speed. What is mismatched?

راهنماHint

شبکه end-to-end، server، latency و concurrency را دربر می‌گیرد؛ load/integration test کنترل‌شده طراحی کن.

End-to-end network behavior includes servers, latency and concurrency; design a controlled load/integration test.

۱۱) Debugger متصل11) Attached debugger

چرا debugger می‌تواند زمان را منحرف کند؟

Why can an attached debugger distort timings?

راهنماHint

instrumentation و توقف‌ها رفتار زمان‌بندی/JIT را تغییر می‌دهند؛ از اجرای مستقل استفاده کن.

Instrumentation and pauses affect scheduling/JIT; use an independent run.

۱۲) نسخهٔ runtime12) Runtime version

نتیجهٔ لپ‌تاپ توسعه را برای سرور Linux تعمیم می‌دهی. چه محدودیتی را ثبت می‌کنی؟

You generalize a developer-laptop result to a Linux server. What limitation do you record?

راهنماHint

OS، CPU، runtime، SDK و پیکربندی فرق دارد؛ روی محیط هدف هم benchmark یا verify لازم است.

OS, CPU, runtime, SDK and configuration differ; benchmark or verify on the target environment too.

۱۳) ShortRun13) ShortRun

ShortRun اختلاف ۲٪ نشان می‌دهد. آیا برای تصمیم قطعی کافی است؟

ShortRun shows a 2% difference. Is that enough for a firm decision?

راهنماHint

نه لزوماً؛ job کوتاه برای smoke test است و اختلاف باید با اندازه‌گیری پایدارتر تأیید شود.

Not necessarily; a short job is a smoke check and needs confirmation with more stable measurement.

۱۴) MemoryDiagnoser14) MemoryDiagnoser

آیا این diagnoser مصرف native حافظه را کامل نشان می‌دهد؟

Does this diagnoser fully report native memory use?

راهنماHint

نه؛ عمدتاً allocation managed را گزارش می‌کند. برای native از ابزار مناسب دیگری استفاده کن.

No; it primarily reports managed allocations. Use a separate appropriate tool for native memory.

۱۵) hot path یا سرد15) Hot or cold path

یک متد سالی چند بار اجرا می‌شود و ۱۰٪ سریع‌تر شده؛ آیا اولویت بهینه‌سازی دارد؟

A method runs a few times a year and is 10% faster. Is it an optimization priority?

راهنماHint

اثر محصول، هزینهٔ نگه‌داری و bottleneckهای واقعی را بسنج؛ نسبت به‌تنهایی اهمیت نیست.

Consider product impact, maintenance cost and actual bottlenecks; a ratio alone is not importance.

۱۶) نتیجهٔ قابل بازبینی16) Reviewable result

چه اطلاعاتی کنار CSV benchmark می‌گذاری تا هم‌تیمی نتیجه را بازتولید کند؟

What do you store with a benchmark CSV so a teammate can reproduce it?

راهنماHint

commit، SDK/runtime، OS و CPU، command، job، ورودی و هدف اندازه‌گیری.

Commit, SDK/runtime, OS and CPU, command, job, input and measurement goal.

آزمایشگاه: ادعای سریع‌تر بودن را بیازماLab: test the claim that one implementation is faster

دو parser معادل برای رکورد لاگ بساز: نسخهٔ ساده با Split و نسخهٔ کم‌تخصیص‌تر با Span. ابتدا با تست correctness خروجی هر دو را برای خط معتبر، خط ناقص و ورودی بد برابر/متمایز کن. سپس benchmark console جدا بساز، ورودی را در GlobalSetup آماده کن و طول‌های کوتاه، متوسط و بلند را با Params اجرا کن. MemoryDiagnoser را فعال کن و در Release بدون debugger بزن. Mean، پراکندگی، ratio و allocation را ثبت کن؛ یک بار هم workload را با ShortRun فقط برای آشنایی اجرا کن و تفاوت قطعیت آن را توضیح بده. در گزارش، محیط و revision را بنویس و بگو آیا نتیجه آن‌قدر مهم هست که پیچیدگی implementation دوم را نگه داریم یا نه.

Build two equivalent log parsers: a straightforward Split version and a lower-allocation Span version. First use correctness tests to compare outputs for valid, incomplete and invalid lines. Then create a separate benchmark console project, prepare input in GlobalSetup and use Params for short, medium and long inputs. Enable MemoryDiagnoser and run Release without a debugger. Record mean, spread, ratio and allocation; also run ShortRun once as a quick check and explain its lower confidence. Document environment and revision, then decide whether the measured gain justifies the second implementation's complexity.

  1. برابری رفتار را با تست ثابت کن، نه از روی سرعت حدس بزن.
  2. Prove behavioral equivalence with tests; do not infer it from speed.
  3. جدول نتایج و محدودیت محیط را ضمیمه کن.
  4. Include results and environmental limitations.
  5. تصمیم نهایی باید بر مبنای نیاز محصول باشد.
  6. Base the final decision on product needs.

benchmark ابزار تصمیم است، نه دستگاه تولید قطعیتA benchmark informs decisions; it does not manufacture certainty

Release، ورودی نماینده، warmup، جلوگیری از حذف کد و گزارش پراکندگی پایه‌اند. نتایج را به همان ماشین/runtime محدود بدان تا وقتی محیط هدف را هم نسنجیده‌ای. allocation کمتر یا mean پایین‌تر فقط وقتی ارزش دارد که correctness ثابت بماند و رفتار مهم محصول بهتر شود. فصل بعد solution و NuGet را کنار هم می‌گذاریم تا کتابخانهٔ تست‌شده واقعاً قابل‌انتشار و مصرف باشد.

Release, representative inputs, warmup, protection from dead-code elimination and variance reporting are fundamentals. Limit claims to the measured machine/runtime until the target environment is checked. Lower allocation or mean matters only when correctness holds and an important product behavior improves. Next we bring solutions and NuGet together so a tested library can actually be published and consumed.
