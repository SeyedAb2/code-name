آرایه، List، Queue و Stack

Arrays, lists, queues and stacks

گزارش سفارش‌ها بارها اولین عضو List را حذف می‌کند و بقیه جابه‌جا می‌شوند. آیا collection اشتباه است؟ از کاری که برنامه انجام می‌دهد شروع می‌کنیم، بعد ساختار را برمی‌گزینیم.

An order report repeatedly removes the first List item, shifting the rest. Is the collection wrong? We start from what the program does, then choose a structure.

اول workload، بعد collectionWorkload before collection

در فصل قبل قرارداد API را از قابلیت لازم انتخاب کردیم. حالا داخل پیاده‌سازی، نوع concrete مهم می‌شود: اندازه ثابت است؟ index می‌خواهیم؟ ابتدا یا انتها حذف می‌کنیم؟ فقط ترتیب ورود مهم است؟ همین پرسش‌ها گزینهٔ شروع را می‌سازند؛ نه محبوبیت یک نوع.

Last chapter chose an API contract from required capabilities. Now the concrete type matters: fixed size, indexed reads, front or tail removal, or arrival order? These questions determine the initial candidate, not popularity.

پیکان‌ها به‌معنای محدود شدن انتخاب از روی الگوی دسترسی‌اند، نه تضمین کارایی.

The visual means access patterns narrow the choice; it does not guarantee performance.

Count تعداد عضو است؛ Capacity فضای آمادهCount is item count; Capacity is reserved storage

آرایه اندازهٔ ثابت دارد. List روی آرایهٔ داخلی ساخته می‌شود و ظرفیت اضافه برای رشد نگه می‌دارد. وقتی ظرفیت پر شود ممکن است آرایهٔ بزرگ‌تری بسازد و داده‌ها را کپی کند. پس افزودن انتهایی معمولاً سرشکن کم‌هزینه است، نه اینکه هر Add دقیقاً یک هزینه داشته باشد. ضریب رشد جزئیات runtime است.

An array has fixed size. List uses an underlying array with spare capacity. When full, it may allocate a larger one and copy values. Appending is usually efficient amortized, not identical-cost for every Add. The growth factor is a runtime detail.

یک بررسی کوچک / Inspect the difference
var orders = new List<string>(3);
orders.Add("A-104");
orders.Add("A-105");
Console.WriteLine($"Count={orders.Count}, Capacity={orders.Capacity}");

Count برابر دو است و Capacity دست‌کم سه. این خروجی وضعیت همین اجرا را ثابت می‌کند، نه یک ضریب رشد عمومی. TrimExcess را بعد از هر تغییر اجرا نکن؛ کوچک‌سازی و رشد دوباره ممکن است کپی و تخصیص اضافه بسازد.

Count is two and Capacity is at least three. This output proves the current run, not a universal growth factor. Do not call TrimExcess after every change; shrinking and regrowing may cause extra copies and allocations.

Queue و Stack ترتیب را صریح می‌کنندQueue and Stack make ordering explicit

Queue موردی را که زودتر وارد شده زودتر خارج می‌کند؛ برای کارهای نوبتی مناسب است. Stack آخرین مورد را اول پس می‌دهد؛ برای undo و backtracking. RemoveAt(0) روی List هم می‌تواند FIFO بسازد، اما عناصر باقی‌مانده را جابه‌جا می‌کند و intent را پنهان می‌سازد.

Queue removes the earliest item first, fitting turn-based work. Stack returns the latest item first, fitting undo and backtracking. RemoveAt(0) on List can implement FIFO, but shifts remaining items and hides intent.

خالی‌بودن صف را عادی مدیریت کن / Handle an empty queue
var pending = new Queue<string>();
pending.Enqueue("order-41");
pending.Enqueue("order-42");
if (pending.TryDequeue(out var next))
    Console.WriteLine($"Processing {next}");

TryDequeue حالت خالی را بدون exception معمول مدیریت می‌کند. Queue معمولی thread-safe نیست؛ انتخاب collection مسئلهٔ هماهنگی چند نخ را حل نمی‌کند.

TryDequeue handles normal emptiness without an exception. A regular Queue is not thread-safe; choosing a collection does not solve multi-thread coordination.

عملکرد را اندازه بگیر، از اسم نوع حدس نزنMeasure performance; do not infer it from a type name

برای ده عضو شاید سادگی از هزینهٔ چند جابه‌جایی مهم‌تر باشد؛ برای حذف‌های بسیار زیاد، الگوریتم تعیین‌کننده می‌شود. یک اجرای اتفاقی Stopwatch benchmark نیست. ورودی نماینده، تکرار، خروجی صحیح و allocation را بررسی کن. ابزار benchmark را در فصل خودش می‌آموزیم؛ فعلاً ادعا را به همان workload محدود نگه می‌داریم.

For ten items, simplicity may outweigh a few shifts; for massive repeated removals, the algorithm dominates. A casual Stopwatch run is not a benchmark. Use representative inputs, repetitions, correctness and allocation checks. Dedicated tools come later; scope claims to this workload.

آزمایشگاه: صف سفارش‌هاLab: order queue

با پنج سفارش آزمایشی، نسخهٔ پایه را با List و RemoveAt(0) بساز. ترتیب خروجی را در تست تثبیت کن. سپس Queue را جایگزین کن و همان تست را بدون تغییر اجرا کن. دو اندازهٔ ورودی را benchmark کن؛ این آزمایش کوچک به‌تنهایی گلوگاه production را ثابت نمی‌کند.

With five fixture orders, build a baseline using List and RemoveAt(0). Lock output order in a test. Replace it with Queue and rerun the unchanged test. Benchmark two input sizes; this small experiment alone does not prove a production bottleneck.

  1. شناسه‌های قابل تشخیص و baseline ثبت کن.
  2. Create identifiable IDs and record the baseline.
  3. FIFO و حالت خالی را assert کن.
  4. Assert FIFO and empty behaviour.
  5. نسخهٔ Queue و benchmark را تحویل بده.
  6. Deliver the Queue version and benchmark.

اگر تفاوت قابل‌اندازه‌گیری نیست، همان را بنویس. Queue می‌تواند به‌دلیل بیان روشن FIFO انتخاب بهتری باشد؛ دلیل طراحی را از ادعای سرعت جدا نگه دار.

If no measurable difference appears, say so. Queue may still better express FIFO; keep design rationale separate from speed claims.

ساختار تابع عملیات استStructure follows operations

آرایه اندازهٔ ثابت، List رشد و index، Queue ترتیب FIFO و Stack ترتیب LIFO را مدل می‌کند. Count را با Capacity اشتباه نکن و از اسم نوع، کارایی دقیق حدس نزن. مسئلهٔ بعدی lookup سریع، یکتایی و ترتیب مرتب‌شده است.

Array models fixed size, List growth and indexing, Queue FIFO and Stack LIFO. Do not confuse Count with Capacity or infer exact performance from the type name. Next comes fast lookup, uniqueness and sorted order.
