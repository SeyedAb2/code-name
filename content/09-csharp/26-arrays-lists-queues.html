آرایه، List، Queue و Stack

Arrays, lists, queues and stacks

گزارش سفارش‌ها بارها اولین عضو List رو حذف می‌کنه و بقیه جابه‌جا می‌شن. آیا collection اشتباه هست؟ از کاری که برنامه انجام می‌ده شروع می‌کنیم، بعد ساختار رو برمی‌گزینیم.

An order report repeatedly removes the first List item, shifting the rest. Is the collection wrong? We start from what the program does, then choose a structure.

در فصل قبل قرارداد API رو از قابلیت لازم انتخاب کردیم. حالا داخل پیاده‌سازی، نوع concrete مهم می‌شه: اندازه ثابت هست؟ index می‌خوایم؟ ابتدا یا انتها حذف می‌کنیم؟ فقط ترتیب ورود مهمه؟ همین پرسش‌ها گزینهٔ شروع رو می‌سازن؛ نه محبوبیت یک نوع.

Last chapter chose an API contract from required capabilities. Now the concrete type matters: fixed size, indexed reads, front or tail removal, or arrival order? These questions determine the initial candidate, not popularity.

پیکان‌ها به‌معنای محدود شدن انتخاب از روی الگوی دسترسی‌اند، نه تضمین کارایی.

The visual means access patterns narrow the choice; it does not guarantee performance.

List همیشه جواب پیش‌فرض نیستList is not always the default answer

`List<T>` خوب و همه‌کاره‌ست، برای همین خیلی راحت تبدیل می‌شه به انتخاب خودکار. ولی اگه رفتار سیستم صفه، `Queue<T>` قصد رو بهتر نشون می‌ده؛ اگه LIFO می‌خوای، `Stack<T>` هم API درست‌تری می‌ده. حتی array وقتی اندازه ثابت و دسترسی مستقیم داری می‌تونه انتخاب روشن‌تری باشه.

`List<T>` is useful and flexible, which is exactly why it often becomes an automatic choice. But if the system is genuinely FIFO, `Queue<T>` communicates the contract better; for LIFO, `Stack<T>` exposes the right operations. Even an array can be the clearest option when size is fixed and indexed access dominates.

تو این فصل هزینهٔ عملیات رو فقط از جدول Big-O نمی‌خونیم. یه workload کوچیک می‌سازیم، بعد می‌بینیم هر ساختار چه چیزی رو راحت یا سخت کرده. Big-O بدون pattern دسترسی فقط نصف داستانه.

We do not learn operation costs from a Big-O table alone. Build a small workload and observe what each structure makes easy or awkward. Big-O without an access pattern is only half the story.

Count تعداد عضو هست؛ Capacity فضای آمادهCount is item count; Capacity is reserved storage

آرایه اندازهٔ ثابت داره. List روی آرایهٔ داخلی ساخته می‌شه و ظرفیت اضافه برای رشد نگه می‌داره. وقتی ظرفیت پر بشه ممکنه آرایهٔ بزرگ‌تری بسازد و داده‌ها رو کپی کند. پس افزودن انتهایی معمولاً سرشکن کم‌هزینه هست، نه اینکه هر Add دقیقاً یک هزینه داشته باشه. ضریب رشد جزئیات runtime هست.

An array has fixed size. List uses an underlying array with spare capacity. When full, it may allocate a larger one and copy values. Appending is usually efficient amortized, not identical-cost for every Add. The growth factor is a runtime detail.

یک بررسی کوچک / Inspect the difference
var orders = new List<string>(3);
orders.Add("A-104");
orders.Add("A-105");
Console.WriteLine($"Count={orders.Count}, Capacity={orders.Capacity}");

Count برابر دو هست و Capacity دست‌کم سه. این خروجی وضعیت همین اجرا رو ثابت می‌کنه، نه یک ضریب رشد عمومی. TrimExcess رو بعد از هر تغییر اجرا نکن؛ کوچک‌سازی و رشد دوباره ممکنه کپی و تخصیص اضافه بسازد.

Count is two and Capacity is at least three. This output proves the current run, not a universal growth factor. Do not call TrimExcess after every change; shrinking and regrowing may cause extra copies and allocations.

Queue و Stack ترتیب رو صریح می‌کننQueue and Stack make ordering explicit

Queue موردی رو که زودتر وارد شده زودتر خارج می‌کنه؛ برای کارهای نوبتی مناسب هست. Stack آخرین مورد رو اول پس می‌ده؛ برای undo و backtracking. RemoveAt(0) روی List هم می‌تونه FIFO بسازد، اما عناصر باقی‌مانده رو جابه‌جا می‌کنه و intent رو پنهان می‌سازه.

Queue removes the earliest item first, fitting turn-based work. Stack returns the latest item first, fitting undo and backtracking. RemoveAt(0) on List can implement FIFO, but shifts remaining items and hides intent.

خالی‌بودن صف را عادی مدیریت کن / Handle an empty queue
var pending = new Queue<string>();
pending.Enqueue("order-41");
pending.Enqueue("order-42");
if (pending.TryDequeue(out var next))
    Console.WriteLine($"Processing {next}");

TryDequeue حالت خالی رو بدون exception معمول مدیریت می‌کنه. Queue معمولی thread-safe نیست؛ انتخاب collection مسئلهٔ هماهنگی چند نخ رو حل نمی‌کنه.

TryDequeue handles normal emptiness without an exception. A regular Queue is not thread-safe; choosing a collection does not solve multi-thread coordination.

عملکرد رو اندازه بگیر، از اسم نوع حدس نزنMeasure performance; do not infer it from a type name

برای ده عضو شاید سادگی از هزینهٔ چند جابه‌جایی مهم‌تر باشه؛ برای حذف‌های بسیار زیاد، الگوریتم تعیین‌کننده می‌شه. یک اجرای اتفاقی Stopwatch benchmark نیست. ورودی نماینده، تکرار، خروجی صحیح و allocation رو بررسی کن. ابزار benchmark رو در فصل خودش می‌آموزیم؛ فعلاً ادعا رو به همان workload محدود نگه می‌داریم.

For ten items, simplicity may outweigh a few shifts; for massive repeated removals, the algorithm dominates. A casual Stopwatch run is not a benchmark. Use representative inputs, repetitions, correctness and allocation checks. Dedicated tools come later; scope claims to this workload.
