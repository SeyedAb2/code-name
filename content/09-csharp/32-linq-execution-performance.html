اجرای LINQ و هزینهٔ پیمایش

LINQ execution and enumeration cost

query را یک بار برای count و یک بار برای render اجرا می‌کنیم. اگر منبع فایل یا دیتابیس باشد، آیا کار هم دو بار انجام شده؟ اینجا با شمارنده، buffering و مرز materialize پاسخ می‌گیریم.

We enumerate a query once for count and again for rendering. If its source is a file or database, did the work run twice? We use counters, buffering and materialization boundaries to find out.

ساخت query، اجرای آن نیستCreating a query is not executing it

Where معمولاً predicate را برای زمان پیمایش نگه می‌دارد. قبل از foreach ممکن است source هنوز نخوانده باشد. ToArray و ToList نتیجه را در همان لحظه materialize می‌کنند. با counter می‌بینیم خط اجرا کجا اتفاق می‌افتد، به‌جای اینکه از syntax نتیجه بگیریم.

Where usually stores its predicate for enumeration. Before foreach the source may not have been read. ToArray and ToList materialize at that point. A counter reveals when work runs instead of inferring from syntax.

منبع شمارنده‌دار / Counted source
int reads = 0;
IEnumerable<int> Source()
{
    foreach (var value in new[] { 2, 4, 6 })
    {
        reads++;
        yield return value;
    }
}
var query = Source().Where(x => x > 2);
Console.WriteLine(reads); // 0
_ = query.ToArray();
Console.WriteLine(reads); // 3

خروجی ۰ و سپس ۳ نشان می‌دهد source در زمان ساخت query مصرف نشده و ToArray هر سه عضو را خوانده. این شاهد زمان اجراست؛ تعداد queryهای database یا هزینهٔ شبکه را به‌تنهایی ثابت نمی‌کند.

The 0 then 3 shows that query construction did not consume the source and ToArray read all three items. This proves execution timing, not database round trips or network cost by itself.

IEnumerable قول چندبارپذیری نمی‌دهدIEnumerable does not promise repeatability

هر foreach می‌تواند منبع را دوباره اجرا کند. روی query دیتابیس، Count و سپس حلقه ممکن است دو فرمان جدا بفرستد. materialize کردن جلوی اجرای دوباره را می‌گیرد ولی حافظه می‌گیرد؛ اگر یک گذر کافی است، accumulator تک‌گذره معمولاً روشن‌تر است.

Every foreach may rerun the source. A database query counted and then looped may issue separate commands. Materializing prevents reruns but costs memory; when one pass suffices, a single-pass accumulator is often clearer.

همهٔ operatorها streaming نیستندNot every operator streams

Select اغلب موردبه‌مورد جلو می‌رود؛ OrderBy برای تعیین اولین نتیجهٔ مرتب باید ورودی را بررسی کند و GroupBy ممکن است گروه‌ها را نگه دارد. پس «LINQ lazy است» جملهٔ کافی نیست. operator، منبع و provider را کنار هم تحلیل کن و در ورودی بزرگ حافظه را اندازه بگیر.

Select often advances item by item; OrderBy must inspect input to identify the first sorted result, and GroupBy may retain groups. “LINQ is lazy” is not enough. Analyze operator, source and provider together, and measure memory on large input.

IQueryable مرز ترجمه استIQueryable is a translation boundary

IQueryable expression tree را به provider می‌دهد. یک تابع محلی ممکن است ترجمه نشود؛ پس از ToList همان تابع در حافظه اجرا می‌شود و شاید دادهٔ بیش‌ازحد به برنامه منتقل شود. query log، SQL و تعداد round-trip را ببین. اگر count و render دو بار query می‌زنند، repair را با همان log ثابت کن.

IQueryable supplies an expression tree to a provider. A local method may not translate; after ToList it runs in memory and can transfer too much data. Inspect query logs, SQL and round trips. If count and rendering issue two queries, prove the repair with the same logs.

آزمایشگاه: یک منبع، چند مصرف‌کنندهLab: one source, multiple consumers

source شمارنده‌دار بساز و همان query را برای count، بررسی وجود و خروجی مصرف کن. هر بار شمارنده و خروجی را ثبت کن. سپس راهبرد تک‌گذره یا materialize را پیاده کن؛ correctness و allocations را مقایسه کن. اگر provider دیتابیس داری، command logging را روشن و تعداد SQLها را ثبت کن.

Create a counted source and consume one query for count, existence and output. Record counters and results each time. Implement a single-pass or materialized alternative; compare correctness and allocations. With a database provider, enable command logging and record SQL count.

مرز اجرای واقعی را پیدا کنFind the actual execution boundary

deferred execution زمان اجرا را عقب می‌اندازد؛ چندبارپیمایش می‌تواند منبع را تکرار کند؛ buffering حافظه می‌خواهد؛ IQueryable کار را به provider می‌سپارد. قبل از optimize، با شمارنده، log و query trace ثابت کن چه چیزی واقعاً اجرا شده. فصل بعد تابع را به‌عنوان value وارد طراحی می‌کند.

Deferred execution postpones work; repeated enumeration may rerun a source; buffering costs memory; IQueryable delegates work to a provider. Before optimizing, use counters, logs and query traces to establish what actually ran. Next, functions become values in API design.
