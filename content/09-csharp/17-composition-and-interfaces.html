ترکیب و interface برای تغییرپذیری

Composition and interfaces for change

سفارش‌ها اول با پیک شهری ارسال می‌شدند. حالا کسب‌وکار ارسال فوری، تحویل حضوری و شرکت‌های بیرونی هم می‌خواهد. اگر همهٔ تفاوت‌ها را با شرط‌های تازه داخل Order بچپانیم، هر تغییر shipping ریسک منطق سفارش را بالا می‌برد. چطور مسئولیت را جدا کنیم و هنوز بتوانیم آن را تست کنیم؟

Orders originally shipped by a local courier. Now the business wants express delivery, pickup and external carriers too. If every difference becomes another branch inside Order, shipping changes increase risk to order logic. How can we separate the responsibility and still test it?

شرط‌های ارسال دارند مالک سفارش را می‌بلعندShipping branches are taking over Order

اگر Order هم مبلغ و اقلام را نگه دارد، هم تعرفهٔ سه شرکت را بشناسد و هم تصمیم تحویل حضوری بگیرد، تغییر یک سیاست می‌تواند همهٔ این مسئولیت‌ها را لمس کند. اینجا اول مشکل را به نام الگو نمی‌زنیم؛ می‌پرسیم کدام بخش باید مستقل تغییر کند.

If Order stores items and totals, knows three carrier tariffs, and chooses pickup rules, one policy change can touch all those responsibilities. We will not begin by naming a pattern; we ask which part needs to change independently.

شرط‌های در حال رشد / Branches that keep growing
decimal ShippingCost(string method, decimal weight)
{
    if (method == "local") return 40m + weight * 3m;
    if (method == "express") return 90m + weight * 6m;
    if (method == "pickup") return 0m;
    throw new ArgumentException("Unknown method", nameof(method));
}

برای سه گزینه شاید این کد کاملاً قابل‌قبول باشد؛ abstraction برای هر شرط لازم نیست. اما اگر تعرفه‌ها جدا منتشر می‌شوند، تست مستقل می‌خواهند یا اضافه‌کردن carrierها Order را تغییر می‌دهد، سیاست ارسال مرز تغییر مناسبی است.

For three options, this code may be perfectly adequate; not every conditional needs an abstraction. But if tariffs ship independently, need isolated tests, or every carrier changes Order, shipping policy is a useful change boundary.

interface قرارداد توانایی است، نه کپیِ کلاسAn interface is a capability contract, not a copied class

Order به‌جای شناختن همهٔ شرکت‌ها می‌تواند به یک توانایی تکیه کند: محاسبهٔ هزینهٔ ارسال. interface شکل این قرارداد را بیان می‌کند؛ پیاده‌سازی‌ها سیاست خودشان را دارند. interface نباید هر property آینده‌ای را پیش‌بینی کند؛ قرارداد را از نیاز فعلی و مصرف‌کنندهٔ واقعی بساز.

Instead of knowing every carrier, Order can depend on one capability: calculating a delivery cost. The interface describes that contract; implementations own their policies. Do not predict every future property—the contract should come from actual needs and consumers.

قرارداد و دو سیاست / Contract and policies
public interface IShippingPolicy
{
    decimal CalculateCost(decimal weight);
}

public sealed class LocalShipping : IShippingPolicy
{
    public decimal CalculateCost(decimal weight) => 40m + weight * 3m;
}

public sealed class ExpressShipping : IShippingPolicy
{
    public decimal CalculateCost(decimal weight) => 90m + weight * 6m;
}

پیاده‌سازی‌ها باید قرارداد را کامل کنند. اگر ورودی وزن منفی مجاز نیست، validation را در مرز مناسب قرار بده؛ صرف امضای interface دامنهٔ عدد را اعتبارسنجی نمی‌کند. قرارداد رفتار را نام‌گذاری می‌کند، اما شرط‌های معنایی باید مستند و تست شوند.

Implementations must fulfil the contract. If negative weight is invalid, validate it at the appropriate boundary; an interface signature does not validate the numeric domain. The contract names behaviour, while semantic constraints still need documentation and tests.

Order سیاست را می‌گیرد؛ با وراثت به آن نمی‌چسبدOrder receives a policy instead of inheriting one

composition یعنی یک شیء از همکاری شیء دیگری استفاده کند. سیاست را از بیرون به Order می‌دهیم؛ در نتیجه Order می‌تواند بدون دانستن کلاس concrete کار کند، و تست هم fake کوچکی تزریق کند. این تزریق دستی است؛ container مربوط به DI را فصل‌های ASP.NET جداگانه آموزش می‌دهند.

Composition means one object collaborates with another. We supply a policy to Order from outside, so it can work without knowing a concrete class and tests can inject a small fake. This is manual injection; ASP.NET chapters cover DI containers separately.

وابستگی از بیرون / Injecting a dependency
public sealed class Order
{
    private readonly IShippingPolicy _shipping;
    public decimal Weight { get; }

    public Order(decimal weight, IShippingPolicy shipping)
    {
        if (weight <= 0) throw new ArgumentOutOfRangeException(nameof(weight));
        Weight = weight;
        _shipping = shipping ?? throw new ArgumentNullException(nameof(shipping));
    }

    public decimal ShippingCost => _shipping.CalculateCost(Weight);
}

var order = new Order(4m, new ExpressShipping());
Console.WriteLine(order.ShippingCost);
خروجی / Output
114

مبلغ ۹۰ + ۴×۶ شده است. اگر سیاست ارسال در زمان حیات سفارش عوض می‌شود، نگه‌داشتن readonly dependency انتخاب درستی نیست؛ مدل را با lifecycle واقعی هماهنگ کن. composition مرز مسئولیت می‌دهد، نه تضمین خودکار طراحی خوب.

The result is 90 + 4×6. If shipping policy can change during the order’s lifetime, a readonly dependency may not fit; align the model with the real lifecycle. Composition creates a responsibility boundary, not an automatic guarantee of good design.

interface وقتی ارزش دارد که تفاوت را قابل آزمایش کندAn interface earns its keep when it enables a useful test

در تست Order لازم نیست API شرکت پیک واقعی را صدا بزنیم. یک fake قطعی می‌سازیم و اثبات می‌کنیم Order وزن را به سیاست می‌دهد. تست واحد اینجا منطق همکاری را می‌سنجد؛ رفتار carrier واقعی همچنان به integration test جدا نیاز دارد.

An Order test need not call a real carrier API. A deterministic fake proves that Order passes the weight to its policy. This unit test checks collaboration; a real carrier still needs separate integration tests.

fake برای تست / Test fake
sealed class FlatShipping(decimal cost) : IShippingPolicy
{
    public decimal CalculateCost(decimal weight) => cost;
}

var order = new Order(4m, new FlatShipping(25m));
if (order.ShippingCost != 25m)
    throw new Exception("Order did not use the supplied policy.");

اگر بعداً Order منطق خودش را با interface می‌سازد، به concrete نوع‌هایش شرط می‌زند یا fake را ناممکن می‌کند، abstraction به هدفش نرسیده. از طرف دیگر، یک interface تک‌پیاده‌سازی که هیچ مرز تغییر یا تستی نمی‌سازد ممکن است فقط هزینهٔ پرش بین فایل‌ها باشد.

If Order later constructs concrete policies itself, branches on their concrete types, or makes fakes impossible, the abstraction has missed its purpose. Conversely, a one-implementation interface with no change boundary or testing value may only add file-navigation cost.

پیاده‌سازی صریح و default member: ابزارهای محدودExplicit implementation and default members: narrow tools

پیاده‌سازی صریح وقتی مفید است که دو interface عضو هم‌نام دارند یا نمی‌خواهیم عضو بخشی از API عمومی concrete class باشد. مصرف‌کننده باید از مسیر interface صدا بزند. default interface implementation می‌تواند عضو مشترکی به قرارداد بدهد، اما برای compatibility و runtime هدف باید بررسی شود؛ جایگزین بی‌فکرِ class پایه یا راهی برای انباشتن منطق در interface نیست.

Explicit implementation helps when interfaces contain same-named members or when a concrete class should not expose the member as part of its public API. Consumers call through the interface. A default interface implementation can supply shared behaviour, but target runtime compatibility matters; it is not an automatic replacement for a base class or a place to accumulate logic.

عضو صریح / Explicit member
interface ILabel
{
    string Describe();
}

sealed class OrderLabel : ILabel
{
    string ILabel.Describe() => "Order label";
}

ILabel label = new OrderLabel();
Console.WriteLine(label.Describe());

اگر new OrderLabel().Describe() کار نمی‌کند، چون پیاده‌سازی صریح از API مستقیم کلاس پنهان است؛ از قرارداد ILabel استفاده کن. برای default interface member، نسخهٔ compiler و runtime را با target framework پروژه تطبیق بده و اگر سازگاری کتابخانه‌ای مهم است، آن را در consumer واقعی build کن.

If new OrderLabel().Describe() is unavailable, it is because explicit implementation is hidden from the class’s direct API; use ILabel. For default interface members, align compiler/runtime support with the project target and build a real consumer when library compatibility matters.

آزمایشگاه: سیاست ارسال را بدون شرط‌های Order تغییر بدهLab: swap shipping policy without Order branches

یک برنامهٔ کنسولی کوچک بساز. سه پیاده‌سازی local، express و pickup داشته باش و Order را طوری طراحی کن که از نام این کلاس‌ها خبر نداشته باشد.

Build a small console program with local, express and pickup implementations. Design Order so it does not know those concrete class names.

  1. قرارداد IShippingPolicy و شرط ورودی وزن را تعریف کن.
  2. Define IShippingPolicy and the valid weight contract.
  3. سه policy بساز و ورودی‌های مرزی را تست کن.
  4. Implement three policies and test boundary inputs.
  5. dependency را از constructor به Order بده؛ بررسی کن new Order بدون policy شکست می‌خورد.
  6. Pass the dependency through Order’s constructor; verify construction without a policy fails.
  7. یک fake بساز و بدون network تست کن که Order همان را فراخوانی می‌کند.
  8. Create a fake and test Order’s collaboration without a network.
  9. یک branch موقت بر اساس concrete class اضافه و حذف کن؛ coupling را مقایسه کن.
  10. Temporarily add then remove a concrete-type branch; compare coupling.
  11. گزارش بده interface چه هزینه‌ای داشت و چه ارزشی ساخت.
  12. Report the interface’s cost and the value it created.
معیار پایانDefinition of done

Order concrete policyها را نمی‌شناسد؛ تست fake قطعی است؛ ورودی نامعتبر رد می‌شود؛ و اگر interface را حذف کنی، می‌توانی دقیق بگویی چه coupling یا قابلیت آزمونی از دست می‌رود.

Order does not know concrete policies; the fake test is deterministic; invalid input is rejected; and you can state exactly what coupling or testability is lost if the interface is removed.

۱) سه shipping branch1) Three shipping branches

سه شرط ساده را فوراً به interface تبدیل می‌کنی؟ چه شواهدی لازم داری؟

Would you immediately turn three simple branches into an interface? What evidence do you need?

استدلالReasoning

نه لزوماً؛ تغییر مستقل، پیاده‌سازی‌های جدا، تست یا رشد شرط‌ها توجیه می‌سازند. abstraction بدون این نیاز هزینهٔ اضافه است.

Not necessarily; independent change, separate implementations, testing needs or growing branches may justify it. Without that need, abstraction adds cost.

۲) قرارداد را کوچک نگه دار2) Keep the contract small

برای محاسبهٔ هزینه، چه عضو حداقلی در IShippingPolicy لازم است؟

What is the minimum IShippingPolicy member for cost calculation?

پاسخAnswer
decimal CalculateCost(decimal weight);

هر عضو دیگر فقط وقتی اضافه شود که مصرف‌کننده‌ای واقعی لازم دارد.

Add other members only when a real consumer needs them.

۳) composition یا inheritance؟3) Composition or inheritance?

Order می‌خواهد policy ارسال را انتخاب کند؛ آیا Order باید از ExpressShipping ارث ببرد؟

Order needs a shipping policy. Should Order inherit from ExpressShipping?

پاسخAnswer

خیر؛ «سفارش یک ارسال فوری است» رابطهٔ نوعی نیست. Order یک policy دارد و از composition استفاده می‌کند.

No; an order is not a kind of express shipping. It has a policy, so composition fits.

۴) وابستگی را از constructor بده4) Supply the dependency in the constructor

مزیت constructor injection نسبت به ساختن policy داخل Order چیست؟

Why inject through the constructor instead of creating a policy inside Order?

پاسخAnswer

وابستگی آشکار و قابل جایگزینی می‌شود؛ تست fake می‌دهد و ساخت معتبر را الزام می‌کند.

The dependency is visible and replaceable; tests can supply a fake and construction requires it.

۵) fake چه چیزی ثابت می‌کند؟5) What does a fake prove?

آیا fake موفقیت سرویس بیرونی را ثابت می‌کند؟

Does a fake prove the external service works?

پاسخAnswer

نه؛ فقط همکاری Order با قرارداد را می‌سنجد. integration test برای رفتار carrier واقعی لازم است.

No; it tests Order’s collaboration with the contract. The real carrier needs integration tests.

۶) ورودی وزن منفی6) Negative weight

interface خودش وزن منفی را رد می‌کند؟ کجا validation می‌گذاری؟

Does the interface reject negative weight? Where do you validate?

پاسخAnswer

خیر؛ امضا فقط type را می‌گوید. ورودی را در مرز دامنه/سیاست بررسی و قرارداد را تست کن.

No; the signature only states types. Validate at the domain/policy boundary and test the contract.

۷) interface بی‌ارزش را حذف کن7) Remove a pointless interface

یک interface تک‌پیاده‌سازی داری که consumer جایگزین یا تست ندارد. چه ارزیابی می‌کنی؟

You have a single-implementation interface with no alternate consumer or testing need. What do you evaluate?

جهتDirection

آیا مرز تغییر واقعی است؟ اگر نه، حذف abstraction ممکن است کد را ساده‌تر کند. تعداد implementation به‌تنهایی تصمیم‌گیر نیست.

Is there a real change boundary? If not, removing the abstraction may simplify the code. Implementation count alone is not decisive.

۸) explicit implementation8) Explicit implementation

چرا OrderLabel.Describe ممکن است قابل صدا زدن مستقیم نباشد؟

Why might OrderLabel.Describe not be callable directly?

پاسخAnswer

عضو صریح فقط از مسیر ILabel در دسترس است؛ این کار عضو را از API مستقیم کلاس پنهان می‌کند.

An explicit member is available through ILabel, hiding it from the concrete class API.

۹) دو interface هم‌نام9) Two same-named interface members

نوعی هر دو IReadable و IWritable با متد Reset متفاوت را پیاده‌سازی می‌کند. چطور ابهام را حذف می‌کنی؟

A type implements IReadable and IWritable with different Reset behaviour. How do you disambiguate?

پاسخAnswer

explicit implementation برای هر قرارداد و صدا زدن از مسیر interface مربوطه.

Use explicit implementations and call through the corresponding interface.

۱۰) default interface method10) Default interface method

چه چیزی را باید پیش از استفاده در کتابخانه بررسی کنی؟

What must you check before using one in a library?

پاسخAnswer

سازگاری language version و target runtime و رفتار consumerها؛ تغییر را روی targetهای واقعی build و test کن.

Language-version and target-runtime support, plus consumer behaviour; build and test against real targets.

۱۱) interface را به دیتابیس تبدیل نکن11) Do not turn an interface into a database

ده property آینده‌نگر به contract اضافه شده اما هیچ consumerی آن‌ها را نمی‌خواند. چه می‌کنی؟

Ten speculative properties are added to a contract, but no consumer reads them. What do you do?

پاسخAnswer

قرارداد را به capability موردنیاز مصرف‌کننده برمی‌گردانم؛ interface بزرگ coupling و هزینهٔ پیاده‌سازی می‌آورد.

Reduce it to the capability consumers need; a bloated interface increases coupling and implementation cost.

۱۲) تعویض policy در runtime12) Runtime policy replacement

اگر روش ارسال قبل از ثبت نهایی تغییر کند، readonly بودن dependency را بررسی کن.

If shipping may change before confirmation, reconsider a readonly dependency.

استدلالReasoning

باید مشخص شود سیاست در چه lifecycleای انتخاب می‌شود؛ می‌توان سفارش را immutable و با policy جدید بازسازی کرد یا تغییر کنترل‌شده ارائه داد. انتخاب را با قواعد دامنه هماهنگ کن.

Define when policy selection occurs. The order may be rebuilt immutably with the new policy or expose a controlled change; align with domain rules.

۱۳) dependency را از کجا بشناسم؟13) How do you identify a dependency?

Order در constructor خودش new ExpressShipping می‌زند. چه couplingی ایجاد شده؟

Order constructs ExpressShipping in its constructor. What coupling is introduced?

پاسخAnswer

Order به concrete class و انتخاب آن وابسته شده و جایگزینی/fake دشوارتر است. policy را از بیرون بگیر اگر مرز تغییر واقعاً لازم است.

Order depends on the concrete class and its selection, making replacement and fakes harder. Inject the policy if the change boundary is real.

۱۴) composition چه زمانی اضافه است؟14) When is composition unnecessary?

یک فرمول ثابت کوچک هیچ variation یا test seam ندارد. آیا باید آن را به interface تبدیل کنی؟

A tiny fixed formula has no variation or test seam. Should it become an interface?

پاسخAnswer

نه لزوماً؛ تابع سادهٔ داخل type کافی است. complexity طراحی باید با نیاز واقعی متناسب باشد.

Not necessarily; a simple method may suffice. Design complexity should match actual needs.

۱۵) تست واحد یا integration؟15) Unit test or integration test?

برای محاسبهٔ Order با fake و برای API شرکت ارسال کدام را انتخاب می‌کنی؟

Which test type for Order calculation with a fake, and for the carrier API?

پاسخAnswer

اول unit test؛ دومی integration/contract test با boundary بیرونی کنترل‌شده.

A unit test for the first; an integration/contract test for the external boundary.

۱۶) ticket رشد روش ارسال16) The growing-shipping ticket

چه evidenceای باعث می‌شود branchها را به policyهای جدا تبدیل کنی؟

What evidence would justify replacing branches with separate policies?

مسیر تصمیمDecision path

تغییر مستقل تعرفه، نیاز تست جدا، چند consumer و تکرار branchها را بررسی کن. اگر فقط یک شرط ثابت است، refactor شاید سودی نداشته باشد؛ اگر مرز واقعی است، interface کوچک و composition را با تست ثابت کن.

Look for independently changing tariffs, isolated testing needs, multiple consumers and repeated branches. A single stable condition may not justify refactoring; for a real boundary, prove a small interface and composition with tests.

interface را برای تغییر واقعی بسازCreate interfaces for real variation

composition شیءها را به همکاری کنار هم می‌آورد؛ interface قرارداد توانایی را جدا می‌کند؛ تزریق وابستگی، انتخاب پیاده‌سازی را از مصرف‌کنندهٔ آن جدا نگه می‌دارد. اما interface رایگان نیست: باید تغییر، تست یا مرز مستقلی را بهتر کند. فصل بعد وراثت و polymorphism را با همین معیار می‌سنجیم و جایگزینی subtype را از ادعای «کد مشترک» جدا می‌کنیم.

Composition brings objects together as collaborators; an interface separates a capability contract; injection separates implementation choice from its consumer. But interfaces are not free: they should improve a change boundary, testing or independent variation.
