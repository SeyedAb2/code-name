extension method و API خوش‌خوان

Extension methods and readable APIs

نوعی از کتابخانهٔ بیرونی داریم که نمی‌توانیم تغییرش دهیم؛ هر بار برای یک عملیات کوچک، helper را صدا می‌زنیم و جریان کد قطع می‌شود. extension method می‌تواند call site را طبیعی‌تر کند—اما عضو واقعی type نیست و نباید وانمود کند دسترسی ویژه‌ای به داخل دارد.

A library type cannot be changed, and every small operation interrupts the flow with a helper call. An extension method can make the call site more natural—but it is not a real member of the type and must not pretend to have privileged access to its internals.

فصل ۲۰پیش‌نیازprerequisite

helper درست است، اما هر call یک قدم اضافه می‌خواهدThe helper works, but every call adds a step

تابع helper عادی روشن و صریح است. اگر عملیات کوچک، پرتکرار و واقعاً روی خود receiver تعریف‌پذیر باشد، extension syntax می‌تواند خواندن زنجیره را طبیعی کند؛ بدون اینکه کلاس اصلی را تغییر دهیم.

An ordinary helper is explicit and valid. If an operation is small, repeated and naturally phrased on the receiver, extension syntax can make a chain read naturally without changing the original class.

helper قبل از extension / Before
static bool HasContent(string? value)
    => !string.IsNullOrWhiteSpace(value);

if (HasContent(input))
    Save(input);

برای C# پیش از ۱۴، extension method در non-generic static class تعریف می‌شد و پارامتر اول با this نوع receiver را مشخص می‌کرد. از دید runtime یک static method است؛ syntax نقطه‌ای فقط شکل فراخوانی را بهتر می‌کند.

Before C# 14, an extension method was declared in a non-generic static class, with this on its first parameter to identify the receiver. It is a static method at runtime; dot syntax improves only the call-site shape.

تعریف و فراخوانی / Declaration and call
namespace App.Text;

public static class StringExtensions
{
    public static bool HasContent(this string? value)
        => !string.IsNullOrWhiteSpace(value);
}

// In a file that imports App.Text:
if (input.HasContent())
    Save(input);

extension class باید static و top-level باشد و مصرف‌کننده باید namespace آن را در scope بیاورد. این syntax اجازه نمی‌دهد به private memberهای string دسترسی بگیریم؛ داخل متد فقط APIهای عمومی قابل دسترسی‌اند.

The extension class must be static and top-level, and the consumer must bring its namespace into scope. This syntax does not grant access to string’s private members; the method can use only publicly accessible APIs.

compiler از کجا extension مناسب را پیدا می‌کند؟How does the compiler find an extension?

اول memberهای واقعی type در overload resolution حضور دارند؛ extensionها fallbackای هستند که از namespaceهای in-scope می‌آیند. اگر extension مناسب پیدا نشود، همان فراخوانی static همیشه شکل قابل‌مشاهده و قابل‌تشخیص است. namespace زیاد و importهای مبهم می‌توانند چند candidate بسازند.

Real members participate in overload resolution before extension fallbacks, which come from namespaces in scope. If no suitable extension is found, the explicit static-call form remains visible and diagnosable. Broad namespaces and imports can introduce competing candidates.

نقطه‌ای یا static call / Two equivalent call forms
var readable = input.HasContent();
var explicitCall = StringExtensions.HasContent(input);

اگر string در آینده member واقعی HasContent داشته باشد، رفتار call نقطه‌ای را با member جدید دوباره بررسی کن؛ extension جای member واقعی را نمی‌گیرد. خطای ambiguity را با importهای محدود یا static call حل کن، نه با نام‌گذاری تصادفی.

If string later gains a real HasContent member, re-check the dotted call: an extension does not replace a real member. Resolve ambiguity with narrow imports or an explicit static call, not arbitrary renaming.

extension generic را از عملیات لازم بسازDerive a generic extension from the required operation

اگر عملیات روی چند نوع تکرار می‌شود، generic extension می‌تواند تکرار را کم کند؛ constraint باید دقیقاً توانایی لازم را بیان کند. C# نمی‌تواند صرفاً هر نوعی را به‌خاطر داشتن یک متد هم‌نام structurally قبول کند؛ یا constraint/interface لازم است یا الگوریتم عمومی‌تری انتخاب می‌کنیم.

If an operation repeats across types, a generic extension can reduce duplication; its constraint should express exactly the required capability. C# does not structurally accept any type merely because it has a same-named method; use a constraint/interface or choose a more general algorithm.

extension روی IEnumerable / Enumerable extension
public static class SequenceExtensions
{
    public static bool IsEmpty<T>(this IEnumerable<T> source)
    {
        ArgumentNullException.ThrowIfNull(source);
        using var iterator = source.GetEnumerator();
        return !iterator.MoveNext();
    }
}

var empty = Array.Empty<int>().IsEmpty();

این نسخه lazy sequence را کامل enumerate نمی‌کند؛ فقط یک عضو جلو می‌رود و iterator را dispose می‌کند. برای بعضی منبع‌ها حتی گرفتن enumerator می‌تواند هزینه یا اثر داشته باشد. اگر نوع Count دارد، implementation مناسب‌تری می‌تواند از آن استفاده کند؛ قرارداد و cost را پنهان نکن.

This version does not enumerate the whole lazy sequence; it advances once and disposes the iterator. Even obtaining an enumerator can cost or have effects for some sources. A type with Count may allow a more suitable implementation; do not hide contract and cost.

receiver تهی و دامنهٔ namespace را آگاهانه مدیریت کنHandle null receivers and namespace scope deliberately

extension call روی reference تهی می‌تواند اجرا شود، چون در واقع static method است و null به‌عنوان آرگومان می‌رود؛ رفتار را خود extension تعیین می‌کند. این با فراخوانی instance method روی null فرق دارد. تصمیم را روشن کن: guard و exception مناسب، یا عملیات null-safe فقط وقتی معنی دامنه‌ای دارد.

An extension call on a null reference can execute because it is a static call receiving null as an argument; the extension defines the behaviour. This differs from invoking an instance method on null. Choose deliberately: guard and throw, or be null-safe only when the domain meaning supports it.

null guard صریح / Explicit null guard
public static int WordCount(this string? text)
{
    ArgumentNullException.ThrowIfNull(text);
    return text.Split(' ', StringSplitOptions.RemoveEmptyEntries).Length;
}

متد بالا روی receiver null، ArgumentNullException می‌دهد. اگر extension را در چند namespace عمومی پخش کنی، autocomplete و resolution شلوغ می‌شود؛ یک namespace هدفمند و اسم‌هایی انتخاب کن که دامنهٔ کاربرد را بگویند.

This method throws ArgumentNullException for a null receiver. Scattering extensions across many broad public namespaces makes completion and resolution noisy; choose a focused namespace and names that communicate intended scope.

در C# 14: extension block و propertyهای توسعه‌ایIn C# 14: extension blocks and extension properties

C# 14 syntax تازه‌ای برای extension members اضافه کرد: extension block می‌تواند method و property توسعه‌ای تعریف کند و حتی عضو static متناظر با نوع توسعه‌یافته داشته باشد. این قابلیت به C# 14 و SDK مناسب نیاز دارد؛ اگر پروژهٔ قدیمی‌تر است از syntax کلاسیک استفاده کن. C# 15 indexer توسعه‌ای موضوع این فصل نیست و نباید با قابلیت C# 14 اشتباه شود.

C# 14 added extension-member syntax: an extension block can declare extension methods and properties, and can expose static members associated with the extended type. It requires C# 14 and a compatible SDK; use classic syntax for older projects. C# 15 extension indexers are outside this chapter and must not be confused with the C# 14 feature.

extension property در C# 14
public static class TextExtensions
{
    extension(string text)
    {
        public bool HasContent => !string.IsNullOrWhiteSpace(text);

        public int WordCount
            => text.Split(' ', StringSplitOptions.RemoveEmptyEntries).Length;
    }
}

string message = "ship the order";
Console.WriteLine(message.HasContent);
Console.WriteLine(message.WordCount);

در این block، receiver به شکل پارامتر extension معرفی شده و propertyها از call site مثل member خوانده می‌شوند؛ اما داخل نوع اصلی ذخیره نشده‌اند و دسترسی private ایجاد نمی‌کنند. syntax را فقط وقتی به‌کار ببر که target framework و compiler پروژه پشتیبانی می‌کنند و مزیت API از شگفتی آن بیشتر است.

The block declares an extension receiver and properties are read like members at the call site, but they are not stored on the original type and gain no private access. Use this syntax only when the project’s compiler supports it and its API benefit outweighs the surprise.

آزمایشگاه: یک extension کوچک و قابل‌دفاع بسازLab: build one small, defensible extension

برای رشته یا IEnumerable یک عملیات پرتکرار انتخاب کن. قبل از ساخت extension ثابت کن call site فعلی واقعاً ناخواناست؛ بعد دو syntax را مقایسه و اثر null، enumeration و namespace را تست کن.

Choose a repeated operation on string or IEnumerable. First show that the current call site is awkward; then compare both syntaxes and test null, enumeration and namespace behaviour.

  4. Create the classic extension and also call it statically.

  8. Test a null receiver and lazy source; count enumerations.

معیار پایانDefinition of done

extension API عمومی اضافه‌کاری نیست؛ namespace و رفتار null روشن‌اند؛ عملیات روی lazy sequence هزینهٔ پنهان ندارد؛ و تفاوت extension method واقعی و extension syntax را می‌توانی توضیح بدهی.

The extension is not gratuitous public API; namespace and null behaviour are explicit; lazy-sequence work has no hidden cost; and you can explain extension dispatch versus syntax.

تمرین‌ها: extension یا helper؟Exercises: extension or helper?

با call site و رفتار compiler جواب بده، نه با سلیقهٔ ظاهری.

Answer from call sites and compiler behaviour, not visual preference.

۱) extension واقعاً عضو type شد؟1) Did the extension become a real member?

آیا extension method metadata نوع اصلی را تغییر می‌دهد؟

Does an extension method alter the original type’s metadata?

پاسخAnswer

نه؛ static method در نوع extension است و syntax فراخوانی تغییر می‌کند.

No; it is a static method in an extension type; only call syntax changes.

۲) namespace را حذف کن2) Remove the namespace import

چرا dotted call دیگر resolve نمی‌شود؟

Why does the dotted call stop resolving?

پاسخAnswer

extension namespace در scope نیست؛ type assembly هم باید reference شده باشد.

The extension namespace is out of scope; its assembly must also be referenced.

۳) instance member یا extension؟3) Instance member or extension?

هر دو signature قابل‌اعمال‌اند؛ کدام معمولاً اولویت دارد؟

Both signatures apply. Which is generally preferred?

پاسخAnswer

member واقعی type در resolution مقدم است؛ extension fallback است.

The real type member takes precedence; an extension is a fallback.

۴) دسترسی private4) Private access

extension می‌تواند private field receiver را بخواند؟

Can an extension read the receiver’s private field?

پاسخAnswer

خیر؛ فقط دسترسی‌ای دارد که static helper معمولی دارد.

No; it has only the access of an ordinary static helper.

۵) receiver تهی5) Null receiver

چرا ممکن است extension روی string تهی اجرا شود؟

Why can an extension be called on a null string?

پاسخAnswer

در واقع static call است و null آرگومان می‌شود؛ بدنه باید رفتار را مدیریت کند.

It is a static call receiving null; the body must handle it.

۶) extension class6) Extension class

چه شکل کلی باید داشته باشد؟

What general shape must it have?

پاسخAnswer

static class سطح بالا، متد static و this روی پارامتر اول در syntax کلاسیک.

A top-level static class, static method and this on the first parameter in classic syntax.

۷) lazy enumeration7) Lazy enumeration

آیا شمارش یک IEnumerable برای IsEmpty هزینهٔ صفر دارد؟

Is checking emptiness on IEnumerable always free?

پاسخAnswer

نه؛ ممکن است enumerator بگیرد و یک عضو مصرف کند یا source اثر داشته باشد؛ Count یا قرارداد source را بررسی کن.

No; it may acquire an enumerator, consume an item or interact with an effectful source; inspect Count and source contracts.

۹) extension ambiguity9) Extension ambiguity

دو namespace متد هم‌نام و هم‌امضا را وارد scope کرده‌اند. repair چیست؟

Two imported namespaces expose same-named matching extensions. How do you repair?

پاسخAnswer

import را محدود، نام‌ها/namespaceها را معنادار، یا static call را برای رفع ابهام استفاده کن.

۱۰) C# 14 extension property10) C# 14 extension property

این قابلیت در کدام نسخه اضافه شد و چه dependency می‌خواهد؟

Which language version added it, and what dependency does it need?

پاسخAnswer

C# 14؛ compiler/SDK سازگار لازم است. project قدیمی از syntax کلاسیک استفاده کند.

C# 14; a compatible compiler/SDK is required. Older projects can use classic syntax.

۱۱) extension property private access11) Private access from an extension property

آیا syntax جدید دسترسی private بیشتری می‌دهد؟

Does the newer syntax grant extra private access?

پاسخAnswer

خیر؛ ظاهر memberوار است ولی مالکیت داخل نوع اصلی ایجاد نمی‌کند.

No; the call looks member-like but does not become part of the original type.

۱۲) extension یا static helper؟12) Extension or static helper?

عملیات به چند ورودی هم‌وزن نیاز دارد و روی یک receiver طبیعی نیست. چه انتخابی؟

An operation has several equal inputs and no natural receiver. What do you choose?

پاسخAnswer

helper/static service شفاف‌تر از extension روی یکی از ورودی‌های دلخواه است.

A helper/static service is clearer than arbitrarily extending one input.

۱۳) extension عمومی13) Public extension API

چرا namespaceهای عمومی با extensionهای خیلی عمومی می‌توانند مزاحم شوند؟

Why can broad public extension namespaces become disruptive?

پاسخAnswer

autocomplete، overload resolution و احتمال ambiguity را زیاد می‌کنند؛ دامنه را محدود و اسم را دقیق کن.

They clutter completion, overload resolution and ambiguity; narrow scope and use precise names.

۱۴) extension را نقد کن14) Review an extension

helper موجود فقط برای یک call استفاده می‌شود و نام اصلی خواناست؛ آیا باید extension بسازی؟

An existing helper is used once and already reads clearly. Must you turn it into an extension?

پاسخAnswer

خیر؛ extension API عمومی و scope جدید می‌آورد، پس سود call site باید هزینه‌اش را توجیه کند.

No; an extension adds public API and scope, so call-site benefit should justify that cost.

extension syntax مالکیت را عوض نمی‌کندExtension syntax does not change ownership

extension method و extension member راهی برای call site بهترند، نه راهی برای اصلاح type اصلی از بیرون و نه دسترسی مخفی به privateها. receiver، namespace، null و هزینهٔ enumeration را شفاف نگه دار. C# 14 extension blockها را معرفی کرده؛ syntax کلاسیک هنوز برای targetهای قدیمی انتخاب درست است. فصل بعد از این ابزارهای API به generic می‌رویم تا ببینیم چطور یک الگوریتم را type-safe و بدون تکرار می‌سازیم.

Extension methods and members improve call sites; they do not patch the original type or gain hidden private access. Keep receiver, namespace, null behaviour and enumeration cost explicit. C# 14 introduced extension blocks; classic syntax remains right for older targets. Next we move from API helpers to generics and build type-safe algorithms without duplication.
