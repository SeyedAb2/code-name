مجموعه‌های immutable، frozen و concurrent

Immutable, frozen and concurrent collections

دو درخواست هم‌زمان تنظیمات را می‌خوانند و یکی وسط کار آن را عوض می‌کند. آیا هر درخواست یک نسخه می‌بیند؟ مسئله این بار انتخاب بین «هرگز عوض نمی‌شود»، «پس از ساخت ثابت می‌ماند» و «چند نویسنده هم‌زمان دارد» است؛ این‌ها یک مفهوم نیستند.

Two requests read configuration while another update occurs. Does each request see one consistent version? We distinguish “never changes,” “frozen after construction,” and “many concurrent writers”—different requirements.

چه چیزی دقیقاً ثابت می‌ماند؟What exactly stays unchanged?

IReadOnlyDictionary فقط قرارداد دسترسی این reference را محدود می‌کند؛ اگر reference دیگری به Dictionary داشته باشیم، هنوز می‌تواند آن را تغییر دهد. Immutable collection با عملیات غیرتغییردهنده نسخهٔ تازه می‌سازد. Frozen collection یک بار ساخته می‌شود و برای خواندن طولانی‌مدت مناسب است، اما برای updateهای پی‌درپی نیست. هیچ‌کدام objectهای mutable داخل خود را خودکار immutable نمی‌کنند.

IReadOnlyDictionary limits access through this reference; another reference can still mutate the Dictionary. Immutable collections create new versions for updates. Frozen collections are built once for long-lived reads, not frequent updates. None automatically makes mutable objects stored inside immutable.

Immutable یعنی update نتیجهٔ تازه داردImmutable means updates produce a new result

اگر ImmutableArray را Add کنی ولی مقدار برگشتی را نگه نداری، نسخهٔ قبلی تغییر نکرده است. این رفتار به درخواست‌های هم‌زمان اجازه می‌دهد reference نسخهٔ قبلی را نگه دارند؛ در عوض ساخت نسخه هزینه دارد و باید انتخاب را با نرخ update بسنجیم.

If you call Add on ImmutableArray and discard the returned value, the old version remains unchanged. Concurrent readers can retain the prior version, but creating versions has a cost that must be weighed against update frequency.

نسخه را نگه دار / Retain the new version
using System.Collections.Immutable;
var first = ImmutableArray.Create("A", "B");
var second = first.Add("C");
Console.WriteLine(first.Length);  // 2
Console.WriteLine(second.Length); // 3

دو طول متفاوت evidence است که نسخهٔ اول دست‌نخورده مانده. این کد دربارهٔ immutable بودن عنصرهای درون آرایه چیزی ثابت نمی‌کند؛ اگر عنصرها mutable باشند، آن‌ها را هم جدا بررسی کن.

The different lengths show the original version remains unchanged. This says nothing about mutability of the contained elements; inspect those separately.

Frozen برای دادهٔ ثابت و خواندن پرتکرارFrozen fits stable data and repeated reads

اگر پیکربندی یا lookup table یک بار ساخته و بعد هزاران بار خوانده می‌شود، FrozenDictionary نامزد است. باید زمان ساخت، حافظه و هزینهٔ lookup را در workload واقعی کنار Dictionary بسنجیم. Frozen صرفاً «محکم‌تر» یا برای هر dictionary سریع‌تر نیست؛ update پس از ساخت در مدل آن نیست.

For configuration or lookup tables built once and read thousands of times, FrozenDictionary is a candidate. Compare build time, memory and lookup cost against Dictionary on the actual workload. Frozen is not universally “stronger” or faster; repeated updates are not its model.

یک نکته: frozen بودن ظرف، valueای را که خودش mutable است منجمد نمی‌کند. مالکیت و چرخهٔ عمر داده همچنان بخشی از طراحی است.

Freezing the container does not freeze a mutable value stored inside. Ownership and lifecycle remain design concerns.

thread-safe بودن هر عملیات، transaction نمی‌سازدThread-safe operations do not create a transaction

Dictionary و List معمولی برای read/write هم‌زمان بدون هماهنگی ساخته نشده‌اند. ConcurrentDictionary عملیات کلیدی را امن می‌کند؛ اما تغییر دو collection یا حفظ invariant چندمرحله‌ای را با هم اتمیک نمی‌کند. حتی factoryهای GetOrAdd/AddOrUpdate ممکن است چند بار اجرا شوند؛ اثر جانبی بیرونی را آنجا قرار نده.

Regular Dictionary and List are not designed for unsynchronized concurrent mutation. ConcurrentDictionary protects individual operations, not a multi-collection invariant or multi-step transaction. GetOrAdd/AddOrUpdate factories may run more than once; do not put external side effects there.

check-then-act را حذف کن / Avoid check-then-act
if (!counts.ContainsKey("orders"))
    counts["orders"] = 0; // race between check and write

counts.TryAdd("orders", 0); // one atomic operation

TryAdd برای همین تصمیم تک‌کلیدی است. اگر invariant هم‌زمانی چند state را دربرمی‌گیرد، قفل مشترک یا طراحی اتمیک دیگری لازم است؛ یک ConcurrentDictionary آن invariant را خودکار نمی‌فهمد.

TryAdd handles this single-key decision. If an invariant spans multiple state changes, use shared coordination or another atomic design; ConcurrentDictionary cannot infer that invariant.

1) snapshot1) Snapshot

دو reference یک List را نگه می‌دارند؛ یکی تغییر می‌دهد. تست کن دیگری چه می‌بیند.

Two references share a List; one mutates it. Test what the other sees.

تحلیلReasoning

interface فقط دسترسی را محدود می‌کند؛ کپی مستقل snapshot می‌سازد.

An interface only limits access; an independent copy creates a snapshot.

2) Immutable افزودن2) Immutable update

ImmutableArray را تغییر بده و مقدار برگشتی را نگه ندار؛ سپس نسخهٔ درست را تست کن.

Update an ImmutableArray but discard the returned value; then test the correct version.

تحلیلReasoning

عملیات نسخهٔ تازه برمی‌گرداند و مقدار قبلی را تغییر نمی‌دهد؛ نتیجه را ذخیره کن.

An operation returns a new value and leaves the old one unchanged; retain the result.

3) ConcurrentDictionary3) ConcurrentDictionary

چند task کلیدهای مختلف را اضافه می‌کنند. نوع و مدرک نهایی را انتخاب کن.

Several tasks add different keys. Choose a type and final evidence.

تحلیلReasoning

ConcurrentDictionary برای عملیات concurrent طراحی شده؛ count نهایی را بعد از اتمام taskها assert کن.

ConcurrentDictionary supports concurrent operations; assert final count after tasks complete.

4) TryAdd اتمیک4) Atomic TryAdd

چند worker هم‌زمان یک کلید را ثبت می‌کنند؛ فقط یک برنده می‌خواهی.

Workers concurrently register one key; exactly one should win.

تحلیلReasoning

TryAdd نتیجهٔ اتمیک می‌دهد؛ ContainsKey سپس Add یک check-then-act race است.

TryAdd provides an atomic result; ContainsKey then Add is a check-then-act race.

5) factory چندبار5) Factory may run more than once

GetOrAdd factory شمارنده را زیاد می‌کند؛ آیا دقیقاً یک بار تضمین است؟

GetOrAdd's factory increments a counter; is exactly-once execution guaranteed?

تحلیلReasoning

delegate factory ممکن است خارج lock و بیش از یک بار اجرا شود؛ اثر جانبی را داخلش نگذار.

The factory may run outside locks and more than once; avoid side effects inside it.

6) ConcurrentBag6) ConcurrentBag

کارها producer/consumer تک‌جهته‌اند؛ چرا Bag شاید گزینهٔ بدی باشد؟

Work is single-direction producer/consumer; why might Bag be a poor fit?

تحلیلReasoning

Bag ترتیب ندارد و هدفش دسترسی کارگرهاست؛ FIFO را با Queue/Channel مدل کن.

Bag is unordered and worker-oriented; model FIFO with Queue/Channel.

7) BlockingCollection7) BlockingCollection

consumer وقتی خالی است باید منتظر بماند و ظرفیت محدود باشد؛ آزمایش طراحی کن.

Consumer should wait when empty and capacity must be bounded; design a test.

تحلیلReasoning

Bounding و blocking را صریح تست کن؛ completion باید consumer منتظر را آزاد کند.

Test bounding and blocking; completion must release waiting consumers.

8) ConcurrentQueue safety8) ConcurrentQueue safety

آیا enumerate کردن هم‌زمان queue snapshot کامل است؟ مستندات و test را بررسی کن.

Is concurrent queue enumeration a complete snapshot? Check docs and test.

تحلیلReasoning

thread-safe بودن عملیات به معنی snapshot semantics برای هر پیمایش نیست؛ قرارداد همان API را بخوان.

Thread-safe operations do not imply snapshot semantics for every enumeration; inspect that API's contract.

9) Frozen برای دادهٔ ثابت9) Frozen for stable data

داده هنگام startup ساخته و سپس فقط lookup می‌شود؛ چه چیزی را benchmark می‌کنی؟

Data is built at startup and only read afterward; what would you benchmark?

تحلیلReasoning

زمان ساخت، حافظه و lookup را با Dictionary مقایسه کن؛ Frozen برای ساخت یک‌بار/خواندن زیاد طراحی شده.

Compare construction, memory and lookup with Dictionary; Frozen targets build-once/read-many.

10) Frozen mutable value10) Frozen mutable value

FrozenDictionary مقدار mutable نگه می‌دارد؛ آیا کل value immutable شده؟

A FrozenDictionary stores a mutable value; did the value become immutable?

تحلیلReasoning

نه؛ immutability/frozen بودن ساختار بیرونی، object graph را خودکار immutable نمی‌کند.

No; freezing the outer structure does not make the object graph immutable.

11) Dictionary فقط خواندنی11) Read-only Dictionary

Dictionary پس از ساخت بین threadها فقط read می‌شود؛ آیا concurrent type لازم است؟

A Dictionary is built then read-only across threads; is a concurrent type required?

تحلیلReasoning

اگر هیچ mutation هم‌زمانی نیست، معمولاً نوع عادی کافی است؛ publish امن و عمر داده را هم تضمین کن.

Usually the regular type suffices without concurrent mutation; also ensure safe publication and lifetime.

12) قفل یا concurrent12) Lock or concurrent

یک invariant باید دو collection را با هم تغییر دهد؛ ConcurrentDictionary به‌تنهایی کافی است؟

One invariant updates two collections together; is ConcurrentDictionary alone enough?

تحلیلReasoning

نه؛ thread safety هر عملیات، transaction بین دو ساختار نمی‌سازد؛ lock یا مدل اتمیک مشترک لازم است.

No; per-operation safety does not create a transaction across structures; use shared coordination.

13) Immutable snapshot پیکربندی13) Immutable config snapshot

درخواست‌ها باید config یک نسخه‌ای ببینند، حتی وسط reload؛ طراحی و تست کن.

Requests must see one config version even during reload; design and test it.

تحلیلReasoning

نسخهٔ immutable بساز و reference را اتمیک جابه‌جا کن؛ هر درخواست همان snapshot را capture کند.

Build an immutable version and atomically swap its reference; each request captures one snapshot.

14) عملکرد update14) Update performance

Immutable مکرر update می‌شود؛ آیا همیشه سریع‌تر یا thread-safeتر است؟

Immutable is updated frequently; is it always faster or more thread-safe?

تحلیلReasoning

نه؛ نسخه‌سازی allocation دارد و typeهای immutable thread-safe هستند اما workload تعیین می‌کند.

No; versioning allocates. Immutable types are thread-safe, but workload determines suitability.

15) تست race15) Race test

increment سادهٔ value در ConcurrentDictionary را با AddOrUpdate اجرا کن و lost update را بررسی کن.

Use AddOrUpdate to increment a value and examine lost updates.

تحلیلReasoning

value factoryها ممکن است چندبار اجرا شوند؛ side effect بیرونی نگذار و update را بر اساس قرارداد تست کن.

Value factories may run multiple times; avoid external side effects and test the documented update semantics.

16) انتخاب نهایی16) Final selection

سناریوی read-mostly، write-heavy و bounded producer-consumer را به نوع مناسب وصل کن و دلیل را بسنج.

Match read-mostly, write-heavy and bounded producer-consumer scenarios to types and justify.

تحلیلReasoning

Dictionary/Frozen، ConcurrentDictionary، و Channel یا BlockingCollection گزینه‌های نامزدند؛ ساخت، contention و backpressure را اندازه بگیر.

Dictionary/Frozen, ConcurrentDictionary, and Channel or BlockingCollection are candidates; measure build cost, contention and backpressure.

آزمایشگاه: پیکربندی نسخه‌دارLab: versioned configuration

یک Dictionary از تنظیمات بساز و دو درخواست آزمایشی را طوری اجرا کن که یکی هنگام خواندن، تنظیمات جدید را منتشر کند. ابتدا مشکل reference مشترک را نشان بده. سپس یک immutable snapshot بساز، reference نسخه را در یک نقطه جابه‌جا کن و تضمین کن هر درخواست تمام کلیدهای خود را از همان نسخه بخواند.

Create a configuration Dictionary and simulate two requests while a new configuration is published. First expose the shared-reference problem. Then build an immutable snapshot, swap the version reference at one boundary, and ensure each request reads all keys from one version.

  1. دو نسخه با شناسهٔ قابل تشخیص بساز.
  2. Create two visibly different versions.
  3. تست هم‌زمانی بنویس که درخواست نیمه‌قدیمی/نیمه‌جدید را پیدا کند.
  4. Write a concurrency test that detects mixed-version reads.
  5. snapshot را جایگزین کن و همان تست را تکرار کن.
  6. Replace with a snapshot and rerun the same test.
  7. هزینهٔ ساخت نسخه را گزارش کن؛ دربارهٔ production ادعای بیش از مدرک نکن.
  8. Report version-construction cost without overclaiming about production.

نوع را با الگوی تغییر انتخاب کنChoose by mutation pattern

immutable نسخهٔ تازه می‌دهد؛ frozen برای ساخت یک‌بار و خواندن زیاد است؛ concurrent برای دسترسی هم‌زمان طراحی شده. thread-safe بودن یک عملیات به‌معنی transaction چندمرحله‌ای نیست، و container ثابت، value mutable را ثابت نمی‌کند. فصل بعد از ساخت sequence تنبل و iterator می‌پرسد: داده چه زمانی واقعاً تولید می‌شود؟

Immutable creates new versions; Frozen fits build-once/read-many data; concurrent collections support concurrent access. Thread safety of one operation is not a multi-step transaction, and a fixed container does not freeze mutable values. Next we ask when a lazy sequence is actually produced.
