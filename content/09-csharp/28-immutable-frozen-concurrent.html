مجموعه‌های immutable، frozen و concurrent

Immutable, frozen and concurrent collections

دو درخواست هم‌زمان تنظیمات رو می‌خونن و یکی وسط کار آن رو عوض می‌کنه. آیا هر درخواست یک نسخه می‌بینه؟ مسئله این بار انتخاب بین «هرگز عوض نمی‌شه»، «پس از ساخت ثابت می‌مونه» و «چند نویسنده هم‌زمان داره» هست؛ این‌ها یک مفهوم نیستن.

Two requests read configuration while another update occurs. Does each request see one consistent version? We distinguish “never changes,” “frozen after construction,” and “many concurrent writers”—different requirements.

چه چیزی دقیقاً ثابت می‌مونه؟What exactly stays unchanged?

IReadOnlyDictionary فقط قرارداد دسترسی این reference رو محدود می‌کنه؛ اگه reference دیگری به Dictionary داشته باشیم، هنوز می‌تونه آن رو تغییر دهد. Immutable collection با عملیات غیرتغییردهنده نسخهٔ تازه می‌سازه. Frozen collection یک بار ساخته می‌شه و برای خواندن طولانی‌مدت مناسب هست، اما برای updateهای پی‌درپی نیست. هیچ‌کدوم objectهای mutable داخل خود رو خودکار immutable نمی‌کنن.

IReadOnlyDictionary limits access through this reference; another reference can still mutate the Dictionary. Immutable collections create new versions for updates. Frozen collections are built once for long-lived reads, not frequent updates. None automatically makes mutable objects stored inside immutable.

همهٔ collectionهای thread-safe هم یک قرارداد ندارنThread-safe collections do not all provide the same contract

immutable، frozen و concurrent رو فقط چون اسم‌های پیشرفته دارن کنار هم نذار. immutable یعنی تغییر نسخهٔ موجود رو دست‌کاری نمی‌کنه؛ frozen یعنی هزینهٔ ساخت رو می‌دی تا read-heavy lookup خوبی بگیری؛ concurrent یعنی چند thread بتونن روی ساختار مشترک کار کنن بدون اینکه خودت دور هر عملیات یه lock ساده بکشی. مسئله‌هاشون یکی نیست.

Do not group immutable, frozen, and concurrent collections together merely because they sound advanced. Immutable structures avoid mutating an existing version; frozen collections pay construction cost for read-heavy lookup; concurrent collections coordinate access by multiple threads. They solve different problems.

این فصل جاییه که باید از عبارت مبهم «thread-safe هست» هم فاصله بگیریم. حتی روی collection concurrent، یه sequence از چند عملیات لزوماً atomic نیست. قرارداد هر متد رو جدا بخون و invariant چندمرحله‌ای رو خودت طراحی کن.

This chapter also moves beyond the vague phrase “it is thread-safe.” Even with a concurrent collection, a sequence of multiple operations is not automatically atomic. Read each operation's contract and design multi-step invariants deliberately.

Immutable یعنی update نتیجهٔ تازه دارهImmutable means updates produce a new result

اگه ImmutableArray رو Add کنی ولی مقدار برگشتی رو نگه نداری، نسخهٔ قبلی تغییر نکرده هست. این رفتار به درخواست‌های هم‌زمان اجازه می‌ده reference نسخهٔ قبلی رو نگه دارن؛ در عوض ساخت نسخه هزینه داره و باید انتخاب رو با نرخ update بسنجیم.

If you call Add on ImmutableArray and discard the returned value, the old version remains unchanged. Concurrent readers can retain the prior version, but creating versions has a cost that must be weighed against update frequency.

نسخه را نگه دار / Retain the new version
using System.Collections.Immutable;
var first = ImmutableArray.Create("A", "B");
var second = first.Add("C");
Console.WriteLine(first.Length);  // 2
Console.WriteLine(second.Length); // 3

دو طول متفاوت evidence هست که نسخهٔ اول دست‌نخورده مانده. این کد دربارهٔ immutable بودن عنصرهای درون آرایه چیزی ثابت نمی‌کنه؛ اگه عنصرها mutable باشن، آن‌ها رو هم جدا بررسی کن.

The different lengths show the original version remains unchanged. This says nothing about mutability of the contained elements; inspect those separately.

Frozen برای دادهٔ ثابت و خواندن پرتکرارFrozen fits stable data and repeated reads

اگه پیکربندی یا lookup table یک بار ساخته و بعد هزاران بار خوانده می‌شه، FrozenDictionary نامزد هست. باید زمان ساخت، حافظه و هزینهٔ lookup رو در workload واقعی کنار Dictionary بسنجیم. Frozen صرفاً «محکم‌تر» یا برای هر dictionary سریع‌تر نیست؛ update پس از ساخت در مدل آن نیست.

For configuration or lookup tables built once and read thousands of times, FrozenDictionary is a candidate. Compare build time, memory and lookup cost against Dictionary on the actual workload. Frozen is not universally “stronger” or faster; repeated updates are not its model.

یک نکته: frozen بودن ظرف، valueای رو که خودش mutable هست منجمد نمی‌کنه. مالکیت و چرخهٔ عمر داده همچنان بخشی از طراحی هست.

Freezing the container does not freeze a mutable value stored inside. Ownership and lifecycle remain design concerns.

thread-safe بودن هر عملیات، transaction نمی‌سازهThread-safe operations do not create a transaction

Dictionary و List معمولی برای read/write هم‌زمان بدون هماهنگی ساخته نشده‌اند. ConcurrentDictionary عملیات کلیدی رو امن می‌کنه؛ اما تغییر دو collection یا حفظ invariant چندمرحله‌ای رو با هم اتمیک نمی‌کنه. حتی factoryهای GetOrAdd/AddOrUpdate ممکنه چند بار اجرا بشن؛ اثر جانبی بیرونی رو آنجا قرار نده.

Regular Dictionary and List are not designed for unsynchronized concurrent mutation. ConcurrentDictionary protects individual operations, not a multi-collection invariant or multi-step transaction. GetOrAdd/AddOrUpdate factories may run more than once; do not put external side effects there.

check-then-act را حذف کن / Avoid check-then-act
if (!counts.ContainsKey("orders"))
    counts["orders"] = 0; // race between check and write

counts.TryAdd("orders", 0); // one atomic operation

TryAdd برای همین تصمیم تک‌کلیدی هست. اگه invariant هم‌زمانی چند state رو دربرمی‌گیره، قفل مشترک یا طراحی اتمیک دیگری لازمه؛ یک ConcurrentDictionary آن invariant رو خودکار نمی‌فهمد.

TryAdd handles this single-key decision. If an invariant spans multiple state changes, use shared coordination or another atomic design; ConcurrentDictionary cannot infer that invariant.
