Expressions, operators and precedence

یک شرط قیمت نوشته‌ای و مشتری تخفیفی گرفته که انتظارش رو نداشتی. کد compile می‌شه؛ پس خطا احتمالاً از معنی عبارت هست، نه نحو. بیایید به‌جای حدس، ترتیب ارزیابی رو نشان بدهیم.

You wrote a pricing condition and a customer got an unexpected discount. The code compiles, so the issue may be expression meaning rather than syntax. Let us make evaluation order visible instead of guessing.

اول پیش‌بینی کن، بعد اجراPredict first, then run

به این عبارت نگاه کن: `int total = 100 + 20 * 2;`. به‌نظر تو total چند هست؟ اجرا کن و بعد توضیح بده کدوم عملگر زودتر اجرا شد.

Consider `int total = 100 + 20 * 2;`. What do you expect? Run it, then explain which operator was evaluated first.

C#
int total = 100 + 20 * 2;
Console.WriteLine(total);

خروجی ۱۴۰ هست، چون ضرب precedence بالاتری از جمع داره. اگه مقصودت این بود اول صد و بیست رو جمع کنی، پرانتز بگذار: `(100 + 20) * 2`. پرانتز فقط ابزار رفع ابهام parser نیست؛ راهی برای نشان‌دادن قصد به نفر بعدی هم هست.

The result is 140 because multiplication has higher precedence than addition. To add 100 and 20 first, write `(100 + 20) * 2`. Parentheses do more than guide the parser; they communicate intent to the next reader.

عبارت expression مقداری تولید می‌کنه: `subtotal * rate` یا `isPaid && amount > 0`. دستور statement جریان اجرا رو پیش می‌بره: انتساب، `if`, `return`. بعضی ساختارها هر دو نقش دارن؛ شناخت اینکه «کدوم مقدار ساخته می‌شه» کمک می‌کنه expressionهای بلند رو بشکنی.

An expression produces a value: `subtotal * rate` or `isPaid && amount > 0`. A statement advances control flow: assignment, `if`, `return`. Some constructs combine roles; asking “what value is produced?” helps break up long expressions.

وقتی یک خط کد بیشتر از چیزی که فکر می‌کنی کار می‌کنهWhen one expression does more than you think

بعضی باگ‌ها از الگوریتم پیچیده نمیان؛ از یه expression میان که آدم ترتیب اجرای عملگرهاش رو اشتباه حدس زده. این فصل قرار نیست جدول precedence رو حفظ کنه. چند expression رو قبل از اجرا پیش‌بینی می‌کنیم، بعد با پرانتز و typeها بازشون می‌کنیم تا ببینیم compiler دقیقاً چه چیزی می‌فهمه.

Some bugs do not come from complex algorithms; they come from a single expression whose evaluation order was guessed incorrectly. This chapter is not about memorizing a precedence table. Predict several expressions, run them, then use parentheses and types to expose what the compiler actually understands.

قانون خوب این نیست که «من precedence رو حفظم». قانون خوب اینه که وقتی خواننده مجبور می‌شه دو ثانیه مکث کنه، با پرانتز یا متغیر میانی قصد رو روشن کنی. کد درست ولی مبهم هنوز هزینهٔ نگه‌داری داره.

A good rule is not “I know precedence by heart.” A better rule is that if the reader must pause to decode intent, use parentheses or an intermediate variable. Correct but opaque code still carries maintenance cost.

تقسیم، cast و ترتیب تبدیلDivision, casts and conversion order

یک باگ رایج اینه که قبل از تبدیل، دو integer رو تقسیم می‌کنیم:

A common bug is dividing two integers before converting the result:

C#
int shipped = 1;
int ordered = 2;
double ratio = shipped / ordered;
Console.WriteLine(ratio);

چاپ `0` هست؛ چون عملوندها int هستن و تقسیم صحیح، بخش اعشار رو قبل از assignment حذف می‌کنه. تبدیل رو پیش از تقسیم انجام بده: `double ratio = (double)shipped / ordered;`. حالا خروجی `0.5` هست. cast عملگر رو جادویی نمی‌کنه؛ نوع عملوندهایی رو که وارد محاسبه می‌شن تغییر می‌ده.

It prints `0`: both operands are integers, so integer division discards the fraction before assignment. Convert before dividing: `double ratio = (double)shipped / ordered;`. Now the output is `0.5`. A cast does not magically alter an operation after the fact; it changes the operand types entering it.

شرط درست، بدون محاسبهٔ اضافهCorrect conditions without unnecessary evaluation

این شرط رو در نظر بگیر: «موجودی مثبت هست و مقدار سفارش از موجودی بیشتر نیست». با `&&`، اگه بخش اول false بشه، C# بخش دوم رو اجرا نمی‌کنه؛ به این رفتار short-circuit می‌گوییم.

Consider: “stock is positive and requested quantity does not exceed stock.” With `&&`, C# skips the second operand when the first is false. This is short-circuit evaluation.

C#
bool canShip = stock > 0 && requested <= stock;
bool needsReview = isNewCustomer || amount > reviewLimit;

`||` هم وقتی سمت چپ true باشه، سمت راست رو ارزیابی نمی‌کنه. این فقط بهینه‌سازی نیست؛ اگه سمت راست index آرایه بخواند یا متدی با side effect باشه، آیا باید اصلاً اجرا بشه؟ شرط‌ها رو طوری بچین که سمت چپ هم ایمن باشه و هم دلیل تصمیم رو نشان دهد.

`||` also skips the right operand when the left is true. This is not merely an optimization: if the right side indexes an array or calls a method with side effects, should it run at all? Arrange conditions so the left side is safe and the rule is clear.

پرانتز برای انسانParentheses for people

جدول precedence کامل رو لازم نیست حفظ کنی. اگه ترکیب `&&` و `||` یا عملگرهای مقایسه خواندن رو کند کرده، پرانتز بگذار و قانون business رو در تست نام‌دار ثبت کن.

You do not need to memorize the full precedence table. If mixed `&&`, `||` or comparisons slow reading, add parentheses and capture the business rule in a named test.

پاسخ و دلیلSolution and reasoning

در ترتیب امن، شرط طول false و index اصلاً خوانده نمی‌شه. در ترتیب وارونه ابتدا `items[0]` خوانده می‌شه و IndexOutOfRangeException رخ می‌ده. پس ترتیب عملوندها بخشی از safety هست، نه فقط ظاهر.

In the safe order, the length check is false and the index is never read. Reversing operands reads `items[0]` first and throws. Operand order therefore affects safety, not just style.
