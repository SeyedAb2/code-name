عبارت‌ها، عملگرها و تقدم

Expressions, operators and precedence

یک شرط قیمت نوشته‌ای و مشتری تخفیفی گرفته که انتظارش را نداشتی. کد compile می‌شود؛ پس خطا احتمالاً از معنی عبارت است، نه نحو. بیایید به‌جای حدس، ترتیب ارزیابی را نشان بدهیم.

You wrote a pricing condition and a customer got an unexpected discount. The code compiles, so the issue may be expression meaning rather than syntax. Let us make evaluation order visible instead of guessing.

فصل ۵پیش‌نیازprerequisite

اول پیش‌بینی کن، بعد اجراPredict first, then run

به این عبارت نگاه کن: `int total = 100 + 20 * 2;`. به‌نظر تو total چند است؟ اجرا کن و بعد توضیح بده کدام عملگر زودتر اجرا شد.

Consider `int total = 100 + 20 * 2;`. What do you expect? Run it, then explain which operator was evaluated first.

C#
int total = 100 + 20 * 2;
Console.WriteLine(total);

خروجی ۱۴۰ است، چون ضرب precedence بالاتری از جمع دارد. اگر مقصودت این بود اول صد و بیست را جمع کنی، پرانتز بگذار: `(100 + 20) * 2`. پرانتز فقط ابزار رفع ابهام parser نیست؛ راهی برای نشان‌دادن قصد به نفر بعدی هم هست.

The result is 140 because multiplication has higher precedence than addition. To add 100 and 20 first, write `(100 + 20) * 2`. Parentheses do more than guide the parser; they communicate intent to the next reader.

عبارت expression مقداری تولید می‌کند: `subtotal * rate` یا `isPaid && amount > 0`. دستور statement جریان اجرا را پیش می‌برد: انتساب، `if`, `return`. بعضی ساختارها هر دو نقش دارند؛ شناخت اینکه «کدام مقدار ساخته می‌شود» کمک می‌کند expressionهای بلند را بشکنی.

An expression produces a value: `subtotal * rate` or `isPaid && amount > 0`. A statement advances control flow: assignment, `if`, `return`. Some constructs combine roles; asking “what value is produced?” helps break up long expressions.

تقسیم، cast و ترتیب تبدیلDivision, casts and conversion order

یک باگ رایج این است که قبل از تبدیل، دو integer را تقسیم می‌کنیم:

A common bug is dividing two integers before converting the result:

C#
int shipped = 1;
int ordered = 2;
double ratio = shipped / ordered;
Console.WriteLine(ratio);

چاپ `0` است؛ چون عملوندها int هستند و تقسیم صحیح، بخش اعشار را قبل از assignment حذف می‌کند. تبدیل را پیش از تقسیم انجام بده: `double ratio = (double)shipped / ordered;`. حالا خروجی `0.5` است. cast عملگر را جادویی نمی‌کند؛ نوع عملوندهایی را که وارد محاسبه می‌شوند تغییر می‌دهد.

It prints `0`: both operands are integers, so integer division discards the fraction before assignment. Convert before dividing: `double ratio = (double)shipped / ordered;`. Now the output is `0.5`. A cast does not magically alter an operation after the fact; it changes the operand types entering it.

شرط درست، بدون محاسبهٔ اضافهCorrect conditions without unnecessary evaluation

این شرط را در نظر بگیر: «موجودی مثبت است و مقدار سفارش از موجودی بیشتر نیست». با `&&`، اگر بخش اول false شود، C# بخش دوم را اجرا نمی‌کند؛ به این رفتار short-circuit می‌گوییم.

Consider: “stock is positive and requested quantity does not exceed stock.” With `&&`, C# skips the second operand when the first is false. This is short-circuit evaluation.

C#
bool canShip = stock > 0 && requested <= stock;
bool needsReview = isNewCustomer || amount > reviewLimit;

`||` هم وقتی سمت چپ true باشد، سمت راست را ارزیابی نمی‌کند. این فقط بهینه‌سازی نیست؛ اگر سمت راست index آرایه بخواند یا متدی با side effect باشد، آیا باید اصلاً اجرا شود؟ شرط‌ها را طوری بچین که سمت چپ هم ایمن باشد و هم دلیل تصمیم را نشان دهد.

`||` also skips the right operand when the left is true. This is not merely an optimization: if the right side indexes an array or calls a method with side effects, should it run at all? Arrange conditions so the left side is safe and the rule is clear.

پرانتز برای انسانParentheses for people

جدول precedence کامل را لازم نیست حفظ کنی. اگر ترکیب `&&` و `||` یا عملگرهای مقایسه خواندن را کند کرده، پرانتز بگذار و قانون business را در تست نام‌دار ثبت کن.

You do not need to memorize the full precedence table. If mixed `&&`, `||` or comparisons slow reading, add parentheses and capture the business rule in a named test.

۱) تخفیف را پرانتزگذاری کن1) Parenthesize the discount

برای `100 + 20 * 2` و `(100 + 20) * 2` خروجی را پیش‌بینی و اجرا کن. کدام با «جمع پایه بعد دوبرابر» سازگار است؟

Predict and run both expressions. Which matches “add the base amounts, then double”?

پاسخ و دلیلSolution and reasoning

اولی ۱۴۰ و دومی ۲۴۰ است. ضرب پیش از جمع اجرا می‌شود؛ پرانتز intent را روشن می‌کند. خروجی برنامه این precedence را نشان می‌دهد، نه اینکه قاعدهٔ قیمت‌گذاری درست انتخاب شده.

The results are 140 and 240. Multiplication precedes addition; parentheses clarify intent. The output shows precedence, not whether the pricing rule itself is correct.

۲) نسبت ۱ از ۲ را درست حساب کن2) Calculate one-half correctly

کد تقسیم integer را اصلاح کن تا 0.5 بدهد، بعد نسخه‌ای بنویس که هر دو ورودی double باشند. تفاوت را توضیح بده.

Fix integer division to produce 0.5, then write a version using two doubles. Explain the difference.

پاسخ و دلیلSolution and reasoning
C#
double ratio = (double)shipped / ordered;
// or: double ratio = 1.0 / 2.0;

در نسخهٔ اول cast پیش از division نوع یکی از عملوندها را double می‌کند؛ در دومی literalها از ابتدا floating point هستند. cast نتیجهٔ integer را به عقب برنمی‌گرداند.

In the first version, the cast makes an operand a double before division; in the second, literals are floating point from the start. Casting an integer result cannot recover its discarded fraction.

۳) short-circuit را با خطا ثابت کن3) Prove short-circuit with a failure

عبارت `items.Length > 0 && items[0] == "urgent"` را برای آرایهٔ خالی اجرا کن. بعد عملوندها را جابه‌جا کن و همان آرایه را بده. چه اتفاقی افتاد؟

Run `items.Length > 0 && items[0] == "urgent"` with an empty array. Swap the operands and repeat. What happened?

پاسخ و دلیلSolution and reasoning

در ترتیب امن، شرط طول false و index اصلاً خوانده نمی‌شود. در ترتیب وارونه ابتدا `items[0]` خوانده می‌شود و IndexOutOfRangeException رخ می‌دهد. پس ترتیب عملوندها بخشی از safety است، نه فقط ظاهر.

In the safe order, the length check is false and the index is never read. Reversing operands reads `items[0]` first and throws. Operand order therefore affects safety, not just style.

۴) قاعدهٔ ترکیبی را خوانا کن4) Make a compound rule readable

قاعده: سفارش فقط اگر پرداخت شده باشد و یا عادی باشد، یا مشتری ویژه باشد ارسال می‌شود. یک expression با پرانتز بنویس و سه تست برای ترکیب‌های مرزی اجرا کن.

Rule: ship only when paid and either standard, or when the customer is VIP. Write a parenthesized expression and run three boundary tests.

نمونهٔ پاسخSample solution
C#
bool canShip = isPaid && (isStandard || isVip);

این صورت‌بندی می‌گوید پرداخت شرط سراسری است. تست کن: unpaid+VIP باید false؛ paid+standard true؛ paid+VIP true. اگر مقصود «VIP حتی بدون پرداخت» است، expression دیگری می‌خواهیم و باید خطر کسب‌وکاری‌اش را صریح کنیم.

Payment is a global requirement. Test unpaid+VIP as false, paid+standard as true, and paid+VIP as true. If VIP should bypass payment, the expression changes—and the business risk should be explicit.

۵) expression طولانی را به متغیر نام‌دار بشکن5) Name parts of a long expression

یک شرط شامل پرداخت، موجودی و سقف ارسال بساز. آن را به دو bool نام‌دار بشکن، اجرا و خروجی را با نسخهٔ یک‌خطی مقایسه کن. چه چیزی برای review بهتر شد؟

Create a condition involving payment, stock and a shipping limit. Split it into two named Booleans, run it and compare with a one-liner. What improved for review?

نمونهٔ پاسخSample solution
C#
bool inventoryReady = stock > 0 && requested <= stock;
bool paymentReady = isPaid && amount <= shippingLimit;
bool canShip = inventoryReady && paymentReady;

خروجی منطقی یکی است اما نام‌های میانی علت false شدن را قابل ثبت و تست می‌کنند. این refactor فقط وقتی ارزش دارد که اسم‌ها مفهوم domain داشته باشند، نه اینکه هر عملگر را یک متغیر بی‌معنی کنیم.

The Boolean result is equivalent, but named intermediates make failures easier to inspect and test. This refactor helps when names express domain concepts—not when every operator gets an arbitrary variable.
