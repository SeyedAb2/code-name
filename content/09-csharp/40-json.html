JSON؛ از مدل تا جریان

JSON: from models to streaming

یک سرویس سفارش JSON می‌فرستد و سرویس ما بی‌سروصدا مقدارها را اشتباه می‌خواند؛ بعد هم یک فایل بزرگ، حافظه را بالا می‌برد. اول قرارداد را روشن می‌کنیم، بعد ابزار خواندن را انتخاب می‌کنیم: مدل typed، درخت قابل‌پیمایش یا جریان tokenها.

An order service sends JSON, our code quietly reads values incorrectly, and a large file then spikes memory. We clarify the contract first, then choose a typed model, a traversable tree, or a stream of tokens.

فصل ۳۹پیش‌نیازprerequisite

اول قرارداد را ببین، بعد کلاس را بسازRead the contract before designing a class

فرض کن ورودی این است: {"id":"A-17","total":12.50,"paid":true}. اگر property کلاس تو OrderId باشد، serializer خودش حدس نمی‌زند که باید آن را به id وصل کند. نام، نوع، مقدار غایب و مقدار null بخشی از قراردادند؛ یک نمونهٔ موفق کافی نیست، نمونهٔ ناقص و ناسازگار را هم ببین.

Suppose the input is {"id":"A-17","total":12.50,"paid":true}. If the class property is OrderId, the serializer cannot always infer that it maps to id. Names, types, missing values and null are all part of the contract; inspect incomplete and mismatched samples too.

مدل صریح / Explicit model
using System.Text.Json;
using System.Text.Json.Serialization;

public sealed record Order(
    [property: JsonPropertyName("id")] string Id,
    [property: JsonPropertyName("total")] decimal Total,
    [property: JsonPropertyName("paid")] bool Paid);

var options = new JsonSerializerOptions(JsonSerializerDefaults.Web);
Order? order = JsonSerializer.Deserialize<Order>(json, options);
if (order is null) throw new JsonException("Order was null");

در .NET، System.Text.Json انتخاب استاندارد این فصل است. تنظیمات وب نام‌گذاری رایج را ساده می‌کند، اما attribute قرارداد را در نقطهٔ حساس روشن نگه می‌دارد. دربارهٔ propertyهای ضروری، مقدار پیش‌فرض و unknown field سیاست بگذار؛ deserialize موفق الزاماً یعنی داده از نظر کسب‌وکار معتبر است؟ نه؛ validation مرحلهٔ جداگانه‌ای است.

In .NET, System.Text.Json is our standard choice. Web defaults simplify common naming, while an attribute makes an important mapping explicit. Define policies for required properties, defaults and unknown fields. Successful deserialization does not mean the data is valid for the business; validation is a separate step.

گزینه‌ها را بی‌هدف زیاد نکنDo not accumulate options without intent

یک JsonSerializerOptions مشترک، قرارداد تکرارشوندهٔ برنامه را یکدست می‌کند. اما تنظیمی مثل case-insensitive بودن، ناسازگاری قرارداد را پنهان می‌کند؛ در boundary ورودی، تصمیم باید عمدی و تست‌شده باشد. شماره و تاریخ هم ظرافت دارند: عدد پول را به decimal نگاشت کن و برای زمان، قالب مورد انتظار را صریح کن. برای JSON نامعتبر، JsonException را با context ثبت کن؛ بدنهٔ حساس کامل را بی‌محابا log نکن.

A shared JsonSerializerOptions keeps application conventions consistent. But case-insensitive matching can hide a contract mismatch, so boundary behavior should be deliberate and tested. Numbers and dates need care: map money to decimal and define the expected time representation. Catch JsonException with useful context, without casually logging sensitive request bodies.

سیاست قابل‌آزمون / Testable policy
var options = new JsonSerializerOptions(JsonSerializerDefaults.Web)
{
    PropertyNameCaseInsensitive = false,
    WriteIndented = false
};

try
{
    var order = JsonSerializer.Deserialize<Order>(json, options);
    ValidateOrder(order);
}
catch (JsonException ex)
{
    logger.LogWarning(ex, "Invalid order JSON at {Path}", sourceName);
}

این نمونه سیاست نام را سخت‌گیرانه می‌گیرد. اگر producerهای قدیمی casing متفاوت دارند، قبل از تغییر این گزینه fixture واقعی و برنامهٔ سازگاری داشته باش؛ سخت‌گیری ناگهانی ممکن است مشتری را بشکند.

This example enforces exact property casing. If older producers vary their casing, inspect real fixtures and plan compatibility before tightening the setting; an abrupt change can break clients.

وقتی شکل wire با مدل فرق دارد: converterUse a converter when wire shape differs from the model

گاهی API مقدار enum را به‌شکل رشته می‌فرستد، یا یک شناسه را گاهی عدد و گاهی رشته می‌نویسد. converter محل تبدیل این تفاوت است؛ آن را محدود به همان نوع نگه دار و برای ورودی بد رفتار روشن تعریف کن. اگر مدل را با چند شرط پراکنده بعد از deserialize اصلاح کنی، هر مصرف‌کننده یک قرارداد متفاوت می‌سازد.

An API may encode an enum as text or send an identifier as either a number or a string. A converter centralizes that representation difference; keep it scoped to the relevant type and define invalid-input behavior. Scattered post-deserialization fixes create competing contracts.

enum رشته‌ای / String enum
using System.Text.Json.Serialization;

var options = new JsonSerializerOptions(JsonSerializerDefaults.Web);
options.Converters.Add(new JsonStringEnumConverter<OrderState>());

public enum OrderState { Pending, Paid, Cancelled }

converter عمومی enum برای قرارداد رشته‌ای ساده مناسب است؛ اگر نام wire مستقل از نام عضو C# است یا قواعد سفارشی دارد، converter اختصاصی بنویس و round-trip، مقدار ناشناخته و ورودی نامعتبر را تست کن. این converterها را با یک source generator یا serializer دیگر اشتباه نگیر.

The generic string-enum converter fits a simple textual contract. If wire names differ from C# member names or rules are custom, write a dedicated converter and test round trips, unknown values and malformed input. Do not confuse converters with source generation or a different serializer.

DOM؛ وقتی باید داخل سند بگردیUse a DOM when you need to inspect the document

JsonDocument یک نمای فقط‌خواندنی و سریع برای پرس‌وجوی سند می‌دهد؛ JsonNode برای دست‌کاری درخت راحت‌تر است. بهای DOM این است که سند و ساختار آن در حافظه می‌ماند. عمر JsonDocument را با using ببند و اگر element را بیرون از عمر document نگه می‌داری، مالکیتش را درست مدیریت کن. یک property ممکن است غایب باشد یا نوعش چیزی باشد که انتظار نداشتی.

JsonDocument provides a fast, read-only view for querying a document; JsonNode is convenient for editing a tree. A DOM keeps the document structure in memory. Dispose JsonDocument with using, and manage ownership if an element outlives its document. A property may be absent or have an unexpected kind.

خواندن property اختیاری / Read an optional property
using var document = JsonDocument.Parse(json);
var root = document.RootElement;

if (root.TryGetProperty("total", out var totalElement) &&
    totalElement.TryGetDecimal(out var total))
{
    Console.WriteLine(total);
}

DOM وقتی خوب است که واقعاً چند بخش سند را جست‌وجو یا تغییر می‌دهی؛ اگر فقط یک مدل شناخته‌شده داری، deserialize به مدل ساده‌تر است. برای ورودی غیرقابل‌اعتماد، اندازه و عمق را هم محدود کن. منعکس‌کردن همهٔ سند ورودی در log هم ریسک حریم خصوصی دارد.

A DOM is useful when you genuinely need to navigate or edit several parts of a document; for a known model, deserialization is simpler. Bound input size and depth for untrusted documents. Logging the entire input can also expose private data.

فایل بزرگ: token به tokenLarge documents: process token by token

فصل قبل دیدیم Stream چطور فایل را مرحله‌ای می‌خواند. حالا Utf8JsonReader را داریم: parser کم‌سطحی که روی byteها جلو می‌رود و token می‌دهد. این انتخاب حافظهٔ سند کامل را حذف می‌کند، اما state، مرز buffer و خطاها را بیشتر به عهدهٔ خودت می‌گذارد. برای فایل بزرگ با آرایه‌ای از رکوردها، لازم نیست یک DOM کامل بسازی؛ ولی stream ورودی باید اندازه‌محدود باشد و تست مرزی داشته باشی.

The previous chapter showed incremental file reading. Utf8JsonReader is a lower-level parser that advances over UTF-8 bytes and yields tokens. It avoids a full-document DOM but makes you responsible for state, buffer boundaries and errors. A large array of records need not become one DOM, but bound input size and test boundaries.

گشتن در tokenها / Walk tokens
var reader = new Utf8JsonReader(utf8Bytes, isFinalBlock: true, state: default);
while (reader.Read())
{
    if (reader.TokenType == JsonTokenType.PropertyName &&
        reader.ValueTextEquals("id"))
    {
        if (!reader.Read() || reader.TokenType != JsonTokenType.String)
            throw new JsonException("Expected string id");

        Console.WriteLine(reader.GetString());
    }
}

این نمونه یک buffer کامل را می‌گیرد و برای فهم tokenهاست؛ هنوز ورودی بزرگ را streaming نکرده‌ایم. برای خواندن تکه‌ای از stream باید JsonReaderState را میان bufferها حفظ و token نصفه را به buffer بعد منتقل کنی. اگر این پیچیدگی نیاز واقعی ندارد، serializerهای مدل‌محور را انتخاب کن. Utf8JsonWriter هم برای ساخت خروجی معتبر بدون الحاق دستی رشته‌هاست.

This example receives one complete buffer and illustrates token parsing; it is not yet streaming a large input. Incremental parsing must preserve JsonReaderState between buffers and carry incomplete tokens forward. If that complexity is not needed, prefer model-based serialization. Utf8JsonWriter builds valid output without manual string concatenation.

source generation؛ وقتی metadata زمان اجرا گران استSource generation: reduce runtime metadata work

در برنامهٔ عادی، serializer می‌تواند metadata مدل را در زمان اجرا بررسی کند. System.Text.Json source generation با تعریف context در زمان build کد metadata لازم را تولید می‌کند؛ این می‌تواند برای startup، trimming و Native AOT مفید باشد، اما خودبه‌خود هر برنامه را سریع‌تر نمی‌کند. اندازه‌گیری و تست انتشار واقعی لازم است.

In a typical application, the serializer can inspect model metadata at runtime. System.Text.Json source generation emits required metadata at build time, which can help startup, trimming and Native AOT. It does not automatically make every application faster; benchmark and test the published artifact.

context تولیدشده / Generated context
[JsonSerializable(typeof(Order))]
internal partial class ApiJsonContext : JsonSerializerContext;

var order = JsonSerializer.Deserialize(
    json,
    ApiJsonContext.Default.Order);

var output = JsonSerializer.Serialize(
    order,
    ApiJsonContext.Default.Order);

context باید نوع‌هایی را پوشش دهد که واقعاً serialize می‌کنی؛ مسیرهای runtime ناخواسته را در تست publish پیدا کن. برای هر DTO لازم نیست از روز اول source generation بیاوری؛ ابتدا محدودیت deployment یا startup را بازتولید کن.

The context must cover the types you actually serialize; catch unintended runtime paths with a publish test. You do not need source generation for every DTO from day one—first reproduce a deployment or startup constraint.

تمرین: قرارداد را با تست محکم کنExercises: make the contract executable

۱) نام property1) Property names

JSON با order_id می‌آید و مدل OrderId دارد. mapping صریح بساز و round-trip را assert کن.

JSON uses order_id while the model uses OrderId. Add an explicit mapping and assert a round trip.

پاسخ فنیTechnical reasoning

JsonPropertyName را روی property بگذار؛ هم serialization و هم deserialization را با fixture بررسی کن.

Apply JsonPropertyName and verify both serialization and deserialization against a fixture.

۲) null با غایب فرق دارد2) Missing is not null

برای یک property سه ورودی بساز: غایب، null و مقدار معتبر؛ رفتار مدل و validation را مشخص کن.

Create missing, null and valid cases for one property; define model and validation behavior.

پاسخ فنیTechnical reasoning

default مدل ممکن است غیبت را پنهان کند؛ presence را جداگانه تشخیص بده یا قرارداد را با required validation روشن کن.

A model default can hide absence; track presence separately or enforce an explicit required-field contract.

مبلغ اعشاری را deserialize کن و precision را با مقدار مرزی تست کن.

Deserialize a decimal amount and test precision with a boundary value.

پاسخ فنیTechnical reasoning

برای مبلغ decimal به‌کار ببر و شکل wire را هم مطابق قرارداد، نه حدس محلی، کنترل کن.

Use decimal for money and validate the wire representation against the contract, not locale guesses.

۴) enum رشته‌ای4) String enum

enum را به JSON رشته‌ای تبدیل کن؛ مقدار ناشناخته را هم آزمایش کن.

Serialize an enum as text and test an unknown value as well.

پاسخ فنیTechnical reasoning

converter رشته‌ای را ثبت کن و برای مقدار ناشناخته تصمیم سازگار و تست‌شده داشته باش.

Register a string-enum converter and choose tested, compatible behavior for unknown values.

۵) JSON خراب5) Malformed JSON

ورودی بریده‌شده را deserialize کن؛ خطا را بدون افشای کل payload گزارش بده.

Deserialize truncated input and report the failure without exposing the full payload.

پاسخ فنیTechnical reasoning

برای JsonException مسیر خطا و شناسهٔ درخواست را ثبت کن؛ دادهٔ حساس را redact کن.

Record the JsonException path and request identifier; redact sensitive content.

۶) DOM یا مدل؟6) DOM or model?

یک endpoint شناخته‌شده و یک گزارش با فیلدهای متغیر را مقایسه کن؛ برای هرکدام ابزار و دلیل انتخاب را بنویس.

Compare a known endpoint with a report containing variable fields; choose a tool for each and justify it.

پاسخ فنیTechnical reasoning

مدل typed برای قرارداد پایدار؛ DOM برای جست‌وجوی ساختار متغیر؛ تصمیم را با مصرف حافظه و تغییرپذیری بسنج.

Use a typed model for a stable contract and a DOM for variable structure; consider memory and change frequency.

۷) property اختیاری7) Optional property

کد مستقیم GetProperty را طوری اصلاح کن که غیبت و نوع اشتباه را جدا مدیریت کند.

Repair direct GetProperty access to handle absence and wrong type separately.

پاسخ فنیTechnical reasoning

TryGetProperty و بررسی ValueKind را به‌کار ببر؛ هر دو حالت باید تست شوند.

Use TryGetProperty and inspect ValueKind; test both failure cases.

۸) عمر document8) Document lifetime

یک JsonElement را پس از dispose کردن document مصرف کن؛ ایراد lifetime را رفع کن.

Use a JsonElement after disposing its document; fix the lifetime issue.

پاسخ فنیTechnical reasoning

element را در محدودهٔ document مصرف کن یا با Clone عمر مستقل بساز.

Consume it within the document lifetime or call Clone to create an independent copy.

۹) تغییر درخت9) Edit a JSON tree

یک property را در payload متغیر تغییر بده؛ بین JsonNode و ساخت مدل تصمیم بگیر.

Modify a property in a variable payload; choose between JsonNode and building a model.

پاسخ فنیTechnical reasoning

برای دست‌کاری درخت JsonNode مناسب است؛ اگر شکل ثابت است، مدل typed معمولاً امن‌تر است.

JsonNode suits tree edits; a typed model is usually safer when the shape is stable.

۱۰) ورودی بزرگ10) Large input

یک fixture محدود با صد هزار رکورد بساز و peak memory DOM را با پردازش جریانی مقایسه کن.

Generate a bounded fixture of one hundred thousand records and compare DOM with streaming peak memory.

پاسخ فنیTechnical reasoning

زمان، memory و correctness را با دادهٔ یکسان ثبت کن؛ fixture را محدود و قابل‌تکرار بساز.

Measure time, memory and correctness on identical data; keep the fixture bounded and reproducible.

۱۱) reader نوع‌دار11) Typed reader

token با نام total پیدا کن و اگر مقدار رشته بود به‌جای crash بی‌توضیح، خطای قراردادی بساز.

Find the total token and report a contract error instead of an opaque crash when it is a string.

پاسخ فنیTechnical reasoning

نوع token را پیش از خواندن typed بررسی و برای mismatch، JsonException معنادار ایجاد کن.

Check token type before typed access and throw a meaningful JsonException on mismatch.

۱۲) مرز buffer12) Buffer boundary

در آزمون parser جریانی، یک token را عمداً بین دو buffer تقسیم کن.

In a streaming-parser test, deliberately split a token across two buffers.

پاسخ فنیTechnical reasoning

state reader را نگه دار و byteهای token ناقص را به buffer بعد منتقل کن؛ boundary را تست کن.

Preserve reader state and carry incomplete token bytes forward; assert the boundary case.

۱۳) خروجی معتبر13) Valid output

مقداری شامل نقل‌قول و newline را بدون string concatenation در JSON خروجی بنویس.

Write a value containing quotes and newlines without JSON string concatenation.

پاسخ فنیTechnical reasoning

از serializer یا Utf8JsonWriter استفاده کن تا escape و ساختار درست مدیریت شود.

Use the serializer or Utf8JsonWriter to handle escaping and structure correctly.

۱۴) قرارداد case14) Casing policy

یک producer با OrderId و دیگری با orderId می‌فرستد. سیاست سازگاری را با تست مستند کن.

One producer sends OrderId and another sends orderId. Document compatibility policy with tests.

پاسخ فنیTechnical reasoning

تنظیم case-insensitive را آگاهانه انتخاب کن و هر دو fixture را تست کن؛ ناهماهنگی را کورکورانه پنهان نکن.

Choose case-insensitive handling deliberately and test both fixtures; do not blindly hide inconsistency.

۱۵) publish و AOT15) Publish and AOT

برنامهٔ serializerدار را با trimming/AOT هدف publish کن؛ خطاها و تفاوت خروجی را ثبت کن.

Publish a serializer-based app for a trimmed/AOT target and record warnings or output differences.

پاسخ فنیTechnical reasoning

source-generation context را برای مدل‌های لازم تعریف و artifact نهایی را اجرا و تست کن.

Define a source-generation context for required models, then run and test the published artifact.

۱۶) رخداد ناسازگاری16) Contract incident

یک JSON از producer جدید فقط در production رد می‌شود؛ evidence و تست regression طراحی کن.

JSON from a new producer fails only in production; design evidence collection and a regression test.

پاسخ فنیTechnical reasoning

نمونهٔ redactشده، نسخهٔ schema، مسیر خطا و تنظیمات serializer را حفظ کن؛ fixture امن regression بساز.

Capture a redacted sample, schema version, error path and serializer settings; create a safe regression fixture.

آزمایشگاه: importer سفارشLab: an order importer

یک importer بساز که فایل سفارش را از مدل typed بخواند، ولی گزارش اختیاری را با DOM بررسی کند. نسخهٔ جریانی برای فایل محدود بزرگ را فقط وقتی پیاده کن که اندازه‌گیری، نیاز را نشان می‌دهد. ورودی معتبر، property غایب، نوع غلط، JSON بریده، enum ناشناخته و record تکراری را در fixture داشته باش. log باید شناسه و محل خطا را بدهد، نه payload حساس را. زمان و حافظهٔ سه مسیر را با یک داده و خروجی مورد انتظار مقایسه کن.

Build an importer that reads orders into typed models and inspects an optional report with a DOM. Add a streaming path for a bounded large file only when measurements justify it. Fixtures should cover valid data, missing properties, wrong types, truncated JSON, unknown enums and duplicate records. Logs should include an identifier and error location—not sensitive payloads. Compare time and memory on identical data with the same expected output.

  1. قرارداد را با fixture و تست مشخص کن.
  2. Define the contract with fixtures and tests.
  3. مدل و validation را جدا بنویس.
  4. Keep model binding and validation separate.
  5. DOM و stream را اندازه بگیر و دلیل انتخاب را در README ثبت کن.
  6. Measure DOM and streaming, then record the choice in the README.
  7. ورودی نامعتبر و افشای اطلاعات در log را تست کن.
  8. Test malformed input and prevent sensitive log exposure.

ابزار را از روی نیاز انتخاب کنChoose the tool that matches the need

مدل typed قرارداد پایدار را روشن می‌کند؛ converter اختلاف نمایش را در یک نقطه مهار می‌کند؛ DOM برای پیمایش یا تغییر سند است؛ parser جریانی برای کنترل حافظه به بهای پیچیدگی بیشتر می‌آید؛ source generation مسئلهٔ metadata زمان اجرا و deployment را هدف می‌گیرد. انتخاب خوب با fixture، تست و اندازه‌گیری ثابت می‌شود، نه با اسم پیشرفته‌تر API. فصل بعد سراغ زمان می‌رویم؛ جایی که یک timestamp ظاهراً ساده می‌تواند در منطقهٔ زمانی و تغییر ساعت تابستانی دو معنی داشته باشد.

Typed models clarify stable contracts; converters isolate representation differences; a DOM supports navigation and edits; streaming trades complexity for memory control; source generation targets runtime metadata and deployment constraints. Tests, fixtures and measurements justify a choice—not a more advanced API name. Next we tackle time, where one apparently simple timestamp can mean two things across time zones and daylight-saving transitions.
