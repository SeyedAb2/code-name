solution، NuGet و انتشار

Solutions, NuGet and publishing

کتابخانهٔ قیمت‌گذاری تست داره، اما API آن با اپلیکیشن قاطی شده و پروژهٔ دوم هم نمی‌تونه راحت مصرفش کند. وسوسه می‌شویم همه‌چیز رو به solution اضافه کنیم یا package بسازیم؛ ولی هر project مرز dependency و هزینهٔ build داره. این فصل تصمیم می‌گیره چه چیزی project جدا می‌خواد، چه چیزی package هست، و خروجی برای مصرف‌کننده یا اجرا روی یک میزبان چطور منتشر می‌شه.

The pricing library has tests, but its API is tangled with the application and another project cannot consume it cleanly. We are tempted to split everything or create packages, but every project adds dependency and build costs. This chapter decides what deserves a project boundary, what belongs in a package, and how to publish an artifact for consumers or a target machine.

solution ظرف هماهنگی projectهاست، نه محصول deployableA solution coordinates projects; it is not itself deployable

solution می‌تونه چند project رو کنار هم نگه داره تا restore، build، test و navigation یکجا انجام بشه. هر project خروجی و dependencyهای خودش رو داره. اگه کتابخانهٔ محاسبه و برنامهٔ CLI دو مسئولیت و چرخهٔ تغییر جدا دارن، جداسازی ارزش داره؛ اگه فقط برای یک فایل دو line کد یک project تازه بسازی، پیچیدگی بی‌دلیل ساخته‌ای. مرز رو با مسئولیت و قابلیت استفادهٔ مستقل انتخاب کن، نه با تعداد پوشه‌ها.

A solution groups projects so restore, build, test and navigation can be coordinated. Each project has its own output and dependencies. Separating a calculation library from a CLI can help when they have independent responsibilities or change cycles; creating a project for two lines of code adds needless complexity. Choose boundaries by responsibility and independent reuse, not folder count.

ساختار کوچک / A small solution
Pricing.sln
src/
  Pricing.Core/Pricing.Core.csproj
  Pricing.Cli/Pricing.Cli.csproj
tests/
  Pricing.Core.Tests/Pricing.Core.Tests.csproj

CLI می‌تونه به Core project reference داشته باشه؛ تست هم به Core. dependency جهت‌دار و روشن می‌مونه. project reference در همان repository به source وصل می‌شه؛ PackageReference یک package نسخه‌دار رو از feed دریافت می‌کنه. تا وقتی مصرف‌کننده و چرخهٔ انتشار جدا لازم نیست، project reference معمولاً ساده‌تر هست.

The CLI can reference Core, and the test project can reference Core. Dependencies remain directional and explicit. A project reference links source inside the repository; a PackageReference obtains a versioned package from a feed. Until consumers or release cycles need separation, project references are usually simpler.

referenceها رو آگاهانه انتخاب کنChoose references deliberately

ProjectReference و PackageReference رو بی‌دلیل هم‌زمان برای یک dependency نگذار؛ restore ممکنه دو graph متفاوت بسازد. Packageهای مستقیم رو در فایل project ثبت کن و package transitive رو فقط وقتی مستقیم معرفی کن که کد خودت API آن رو مصرف می‌کنه یا کنترل نسخه‌اش لازمه. در repository تیمی، lock file می‌تونه closure نسخه‌ها رو برای restore قابل‌تکرارتر کند؛ اما lock file جای انتخاب نسخه، بررسی امنیت و به‌روزرسانی package نیست.

Do not casually use ProjectReference and PackageReference for the same dependency; restore can produce different graphs. Declare direct packages in the project file, and promote a transitive package to direct only when your code consumes its API or needs to control its version. A lock file can make dependency closure more repeatable for a team, but it does not replace version selection, security review or package updates.

dependency صریح / Explicit dependency
<ItemGroup>
  <ProjectReference Include="..\Pricing.Core\Pricing.Core.csproj" />
  <PackageReference Include="Some.Direct.Dependency" Version="4.2.0" />
</ItemGroup>

<PropertyGroup>
  <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
</PropertyGroup>

lock file تولیدشده رو مطابق policy تیم version control کن؛ در CI از restore سازگار با lock استفاده کن و تغییر lock رو code review کن. Central Package Management می‌تونه نسخه‌ها رو متمرکز کند، اما ساختار و policy آن باید در سطح repository یکپارچه باشه و با فایل‌های موجود تیم تداخل نکند.

Version-control the generated lock file according to team policy; use a lock-aware restore in CI and review lock changes. Central Package Management can centralize versions, but its structure and policy must be consistent across the repository and must not conflict with existing team files.

یک کتابخانهٔ NuGet، API عمومی و قرارداد نسخه دارهA NuGet library has a public API and a versioning contract

هر assembly قابل‌ارجاع، package خوب نیست. قبل از dotnet pack مشخص کن package چه مسئله‌ای حل می‌کنه، namespace و public API آن چیه، چه target frameworkهایی رو پشتیبانی می‌کنه و مصرف‌کننده چطور نسخه رو pin یا به‌روزرسانی می‌کنه. README، توضیح package، license، repository link، symbol و version در انتخاب مصرف‌کننده اثر دارن. package رو از پروژهٔ library بساز، نه از output اجرایی برنامه.

Not every referenceable assembly is a useful package. Before dotnet pack, define the package's problem, namespace and public API, supported target frameworks, and how consumers pin or update versions. README, package description, license, repository link, symbols and version matter to consumers. Pack the library project, not the executable application's output.

metadata و package محلی / Package metadata and local pack
<PropertyGroup>
  <PackageId>Acme.Pricing.Core</PackageId>
  <Version>1.2.0</Version>
  <Description>Pricing rules for Acme applications</Description>
  <PackageLicenseExpression>MIT</PackageLicenseExpression>
</PropertyGroup>

dotnet pack src/Pricing.Core/Pricing.Core.csproj -c Release -o ./artifacts

version نمونه هست؛ license رو فقط اگه واقعاً مجاز به انتخاب آن هستی ثبت کن. package تولیدی رو پیش از push در feed عمومی/خصوصی بررسی کن: محتویات، dependency، target framework، README و symbol. secrets و فایل‌های build رو وارد package نکن.

The version is illustrative; declare a license only when you are authorized to do so. Inspect a package before pushing it to a public or private feed: contents, dependencies, target frameworks, README and symbols. Never package secrets or build artifacts unintentionally.

نسخه‌گذاری به مصرف‌کننده می‌گه چه تغییری رخ دادهVersioning communicates change to consumers

در Semantic Versioning رایج، patch برای اصلاح سازگار، minor برای قابلیت سازگار و major برای تغییر ناسازگار هست؛ اما فقط وقتی ادعا می‌کنی که policy package واقعاً این قرارداد رو رعایت کند. حذف public member، تغییر رفتار یا محدودکردن targetها می‌تونه breaking change باشه. قبل از major، migration note و compatibility test آماده کن. version یکتا منتشر کن؛ بازنویسی package با همان version باعث می‌شه cache و مصرف‌کننده‌ها به artifactهای متفاوت اشاره کنند.

Under common Semantic Versioning, patch is for compatible fixes, minor for compatible features and major for breaking changes—but only when the package actually follows that contract. Removing a public member, changing behavior or dropping a target can be breaking. Prepare migration notes and compatibility tests before a major release. Publish unique versions; replacing an artifact under the same version makes caches and consumers disagree.

قابلیت سازگارCompatible featureافزودن API جدید بدون حذف قبلیMinor, if policy permits

شمارهٔ نسخه جای بررسی dependencyها و changelog رو نمی‌گیره. package consumer رو با نسخهٔ تازه restore و تست کن؛ یک library build موفق به‌تنهایی اثبات نمی‌کنه مصرف‌کنندهٔ قبلی هنوز کار می‌کنه.

A version number does not replace dependency and changelog review. Restore and test a consumer against the new package; a successful library build alone does not prove existing consumers still work.

publish برای برنامه هست؛ pack برای packagePublish is for applications; pack is for packages

dotnet publish خروجی اجرایی برنامه و dependencyهای لازم رو در پوشهٔ publish آماده می‌کنه؛ dotnet pack package NuGet می‌سازه. framework-dependent به runtime سازگار روی host نیاز داره و معمولاً artifact کوچک‌تر هست. self-contained runtime رو همراه برنامه می‌آورد، ولی بزرگ‌تر هست و باید برای RID هدف publish بشه؛ به‌روزرسانی runtime هم با انتشار تازهٔ app انجام می‌شه. انتخاب رو با محیط اجرا و سیاست patch/security هماهنگ کن.

dotnet publish prepares an application's executable output and dependencies in a publish directory; dotnet pack creates a NuGet package. Framework-dependent deployment requires a compatible runtime on the host and is usually smaller. Self-contained deployment bundles the runtime but is larger and targets a RID; runtime updates then require a new application release. Choose according to the execution environment and patch/security policy.

دو خروجی، دو هدف / Two outputs, two purposes
# Pack a reusable library
dotnet pack src/Pricing.Core/Pricing.Core.csproj -c Release

# Publish an app for a host with compatible runtime
dotnet publish src/Pricing.Cli/Pricing.Cli.csproj -c Release --self-contained false

# Publish self-contained for a specific target
dotnet publish src/Pricing.Cli/Pricing.Cli.csproj -c Release -r linux-x64 --self-contained true

RID رو از فهرست رسمی و architecture میزبان انتخاب کن؛ خروجی linux-x64 روی Windows اجرا نمی‌شه. از --no-restore فقط وقتی استفاده کن که restore قبلی با همان TFM، RID و publish properties انجام شده باشه. single-file، trimming و AOT تصمیم‌های جدا هستن و باید compatibility و reflection رو تست کنند؛ صرفاً برای کوچک‌کردن فایل فعالشان نکن.

Choose a RID from the official catalog and match the host architecture; linux-x64 output does not run on Windows. Use --no-restore only when restore used the same TFM, RID and publish properties. Single-file, trimming and AOT are separate choices that require compatibility and reflection testing; do not enable them merely to shrink output.
