solution، NuGet و انتشار

Solutions, NuGet and publishing

کتابخانهٔ قیمت‌گذاری تست دارد، اما API آن با اپلیکیشن قاطی شده و پروژهٔ دوم هم نمی‌تواند راحت مصرفش کند. وسوسه می‌شویم همه‌چیز را به solution اضافه کنیم یا package بسازیم؛ ولی هر project مرز dependency و هزینهٔ build دارد. این فصل تصمیم می‌گیرد چه چیزی project جدا می‌خواهد، چه چیزی package است، و خروجی برای مصرف‌کننده یا اجرا روی یک میزبان چطور منتشر می‌شود.

The pricing library has tests, but its API is tangled with the application and another project cannot consume it cleanly. We are tempted to split everything or create packages, but every project adds dependency and build costs. This chapter decides what deserves a project boundary, what belongs in a package, and how to publish an artifact for consumers or a target machine.

solution ظرف هماهنگی projectهاست، نه محصول deployableA solution coordinates projects; it is not itself deployable

solution می‌تواند چند project را کنار هم نگه دارد تا restore، build، test و navigation یکجا انجام شود. هر project خروجی و dependencyهای خودش را دارد. اگر کتابخانهٔ محاسبه و برنامهٔ CLI دو مسئولیت و چرخهٔ تغییر جدا دارند، جداسازی ارزش دارد؛ اگر فقط برای یک فایل دو line کد یک project تازه بسازی، پیچیدگی بی‌دلیل ساخته‌ای. مرز را با مسئولیت و قابلیت استفادهٔ مستقل انتخاب کن، نه با تعداد پوشه‌ها.

A solution groups projects so restore, build, test and navigation can be coordinated. Each project has its own output and dependencies. Separating a calculation library from a CLI can help when they have independent responsibilities or change cycles; creating a project for two lines of code adds needless complexity. Choose boundaries by responsibility and independent reuse, not folder count.

ساختار کوچک / A small solution
Pricing.sln
src/
  Pricing.Core/Pricing.Core.csproj
  Pricing.Cli/Pricing.Cli.csproj
tests/
  Pricing.Core.Tests/Pricing.Core.Tests.csproj

CLI می‌تواند به Core project reference داشته باشد؛ تست هم به Core. dependency جهت‌دار و روشن می‌ماند. project reference در همان repository به source وصل می‌شود؛ PackageReference یک package نسخه‌دار را از feed دریافت می‌کند. تا وقتی مصرف‌کننده و چرخهٔ انتشار جدا لازم نیست، project reference معمولاً ساده‌تر است.

The CLI can reference Core, and the test project can reference Core. Dependencies remain directional and explicit. A project reference links source inside the repository; a PackageReference obtains a versioned package from a feed. Until consumers or release cycles need separation, project references are usually simpler.

referenceها را آگاهانه انتخاب کنChoose references deliberately

ProjectReference و PackageReference را بی‌دلیل هم‌زمان برای یک dependency نگذار؛ restore ممکن است دو graph متفاوت بسازد. Packageهای مستقیم را در فایل project ثبت کن و package transitive را فقط وقتی مستقیم معرفی کن که کد خودت API آن را مصرف می‌کند یا کنترل نسخه‌اش لازم است. در repository تیمی، lock file می‌تواند closure نسخه‌ها را برای restore قابل‌تکرارتر کند؛ اما lock file جای انتخاب نسخه، بررسی امنیت و به‌روزرسانی package نیست.

Do not casually use ProjectReference and PackageReference for the same dependency; restore can produce different graphs. Declare direct packages in the project file, and promote a transitive package to direct only when your code consumes its API or needs to control its version. A lock file can make dependency closure more repeatable for a team, but it does not replace version selection, security review or package updates.

dependency صریح / Explicit dependency
<ItemGroup>
  <ProjectReference Include="..\Pricing.Core\Pricing.Core.csproj" />
  <PackageReference Include="Some.Direct.Dependency" Version="4.2.0" />
</ItemGroup>

<PropertyGroup>
  <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
</PropertyGroup>

lock file تولیدشده را مطابق policy تیم version control کن؛ در CI از restore سازگار با lock استفاده کن و تغییر lock را code review کن. Central Package Management می‌تواند نسخه‌ها را متمرکز کند، اما ساختار و policy آن باید در سطح repository یکپارچه باشد و با فایل‌های موجود تیم تداخل نکند.

Version-control the generated lock file according to team policy; use a lock-aware restore in CI and review lock changes. Central Package Management can centralize versions, but its structure and policy must be consistent across the repository and must not conflict with existing team files.

یک کتابخانهٔ NuGet، API عمومی و قرارداد نسخه داردA NuGet library has a public API and a versioning contract

هر assembly قابل‌ارجاع، package خوب نیست. قبل از dotnet pack مشخص کن package چه مسئله‌ای حل می‌کند، namespace و public API آن چیست، چه target frameworkهایی را پشتیبانی می‌کند و مصرف‌کننده چطور نسخه را pin یا به‌روزرسانی می‌کند. README، توضیح package، license، repository link، symbol و version در انتخاب مصرف‌کننده اثر دارند. package را از پروژهٔ library بساز، نه از output اجرایی برنامه.

Not every referenceable assembly is a useful package. Before dotnet pack, define the package's problem, namespace and public API, supported target frameworks, and how consumers pin or update versions. README, package description, license, repository link, symbols and version matter to consumers. Pack the library project, not the executable application's output.

metadata و package محلی / Package metadata and local pack
<PropertyGroup>
  <PackageId>Acme.Pricing.Core</PackageId>
  <Version>1.2.0</Version>
  <Description>Pricing rules for Acme applications</Description>
  <PackageLicenseExpression>MIT</PackageLicenseExpression>
</PropertyGroup>

dotnet pack src/Pricing.Core/Pricing.Core.csproj -c Release -o ./artifacts

version نمونه است؛ license را فقط اگر واقعاً مجاز به انتخاب آن هستی ثبت کن. package تولیدی را پیش از push در feed عمومی/خصوصی بررسی کن: محتویات، dependency، target framework، README و symbol. secrets و فایل‌های build را وارد package نکن.

The version is illustrative; declare a license only when you are authorized to do so. Inspect a package before pushing it to a public or private feed: contents, dependencies, target frameworks, README and symbols. Never package secrets or build artifacts unintentionally.

نسخه‌گذاری به مصرف‌کننده می‌گوید چه تغییری رخ دادهVersioning communicates change to consumers

در Semantic Versioning رایج، patch برای اصلاح سازگار، minor برای قابلیت سازگار و major برای تغییر ناسازگار است؛ اما فقط وقتی ادعا می‌کنی که policy package واقعاً این قرارداد را رعایت کند. حذف public member، تغییر رفتار یا محدودکردن targetها می‌تواند breaking change باشد. قبل از major، migration note و compatibility test آماده کن. version یکتا منتشر کن؛ بازنویسی package با همان version باعث می‌شود cache و مصرف‌کننده‌ها به artifactهای متفاوت اشاره کنند.

Under common Semantic Versioning, patch is for compatible fixes, minor for compatible features and major for breaking changes—but only when the package actually follows that contract. Removing a public member, changing behavior or dropping a target can be breaking. Prepare migration notes and compatibility tests before a major release. Publish unique versions; replacing an artifact under the same version makes caches and consumers disagree.

نوع تغییرChangeنمونهٔ محتاطانهTypical version response
اصلاح سازگارCompatible fixرفع edge case بدون تغییر contractPatch, if compatibility holds
قابلیت سازگارCompatible featureافزودن API جدید بدون حذف قبلیMinor, if policy permits
شکستن contractBreaking changeحذف member یا تغییر semanticsMajor plus migration guidance

شمارهٔ نسخه جای بررسی dependencyها و changelog را نمی‌گیرد. package consumer را با نسخهٔ تازه restore و تست کن؛ یک library build موفق به‌تنهایی اثبات نمی‌کند مصرف‌کنندهٔ قبلی هنوز کار می‌کند.

A version number does not replace dependency and changelog review. Restore and test a consumer against the new package; a successful library build alone does not prove existing consumers still work.

publish برای برنامه است؛ pack برای packagePublish is for applications; pack is for packages

dotnet publish خروجی اجرایی برنامه و dependencyهای لازم را در پوشهٔ publish آماده می‌کند؛ dotnet pack package NuGet می‌سازد. framework-dependent به runtime سازگار روی host نیاز دارد و معمولاً artifact کوچک‌تر است. self-contained runtime را همراه برنامه می‌آورد، ولی بزرگ‌تر است و باید برای RID هدف publish شود؛ به‌روزرسانی runtime هم با انتشار تازهٔ app انجام می‌شود. انتخاب را با محیط اجرا و سیاست patch/security هماهنگ کن.

dotnet publish prepares an application's executable output and dependencies in a publish directory; dotnet pack creates a NuGet package. Framework-dependent deployment requires a compatible runtime on the host and is usually smaller. Self-contained deployment bundles the runtime but is larger and targets a RID; runtime updates then require a new application release. Choose according to the execution environment and patch/security policy.

دو خروجی، دو هدف / Two outputs, two purposes
# Pack a reusable library
dotnet pack src/Pricing.Core/Pricing.Core.csproj -c Release

# Publish an app for a host with compatible runtime
dotnet publish src/Pricing.Cli/Pricing.Cli.csproj -c Release --self-contained false

# Publish self-contained for a specific target
dotnet publish src/Pricing.Cli/Pricing.Cli.csproj -c Release -r linux-x64 --self-contained true

RID را از فهرست رسمی و architecture میزبان انتخاب کن؛ خروجی linux-x64 روی Windows اجرا نمی‌شود. از --no-restore فقط وقتی استفاده کن که restore قبلی با همان TFM، RID و publish properties انجام شده باشد. single-file، trimming و AOT تصمیم‌های جدا هستند و باید compatibility و reflection را تست کنند؛ صرفاً برای کوچک‌کردن فایل فعالشان نکن.

Choose a RID from the official catalog and match the host architecture; linux-x64 output does not run on Windows. Use --no-restore only when restore used the same TFM, RID and publish properties. Single-file, trimming and AOT are separate choices that require compatibility and reflection testing; do not enable them merely to shrink output.

تمرین: مرز project و artifact را انتخاب کنExercises: choose project boundaries and artifacts

۱) solution یا project؟1) Solution or project?

یک برنامه با چند class داری؛ آیا هر class باید project جدا شود؟

An app has several classes. Should each class become a project?

راهنماHint

نه؛ مرز را با مسئولیت، dependency و استقلال تغییر بسنج.

No; use responsibility, dependencies and independent change as criteria.

۲) ProjectReference یا PackageReference2) ProjectReference or PackageReference

دو project در یک repo و یک چرخهٔ release دارند؛ کدام reference ساده‌تر است؟

Two projects share one repository and release cycle. Which reference is simpler?

راهنماHint

معمولاً ProjectReference تا وقتی package boundary مستقل لازم نشده.

Usually ProjectReference until an independent package boundary is needed.

۳) transitive dependency3) Transitive dependency

کد تو API یک package ترانزیتیو را مستقیم صدا می‌زند؛ چه تغییری در dependency ثبت می‌کنی؟

Your code directly calls a transitive package API. What dependency change do you make?

راهنماHint

آن را direct PackageReference کن تا قرارداد dependency صریح باشد.

Declare a direct PackageReference so the dependency contract is explicit.

۴) lock file4) Lock file

آیا packages.lock.json جلوی آسیب‌پذیری package را می‌گیرد؟

Does packages.lock.json prevent package vulnerabilities?

راهنماHint

نه؛ graph را تثبیت می‌کند، ولی audit و به‌روزرسانی لازم است.

No; it stabilizes the graph, but auditing and updates remain necessary.

۵) pack یا publish5) Pack or publish

می‌خواهی reusable library را به feed بدهی؛ کدام فرمان؟

You want to distribute a reusable library through a feed. Which command?

راهنماHint

dotnet pack؛ publish برای خروجی برنامهٔ قابل‌اجراست.

dotnet pack; publish is for application deployment output.

۶) API عمومی6) Public API

package دو class داخلی هم دارد. آیا باید همه public شوند تا NuGet کار کند؟

A package has two internal classes. Must they all become public for NuGet?

راهنماHint

نه؛ فقط API لازم را منتشر کن و سطح پشتیبانی‌شده را کوچک نگه دار.

No; expose only the required API and keep the supported surface small.

۷) حذف متد7) Removing a method

یک public method حذف شده؛ آیا patch version مناسب است؟

A public method was removed. Is a patch version appropriate?

راهنماHint

عموماً breaking change است؛ major و migration guidance را بررسی کن.

Usually it is breaking; consider a major version and migration guidance.

۸) نسخهٔ تکراری8) Reusing a package version

artifact جدید را با همان PackageVersion push می‌کنی؛ چه خطری دارد؟

You push a new artifact under the same package version. What is the risk?

راهنماHint

cacheها و مصرف‌کننده‌ها artifactهای متفاوت می‌بینند؛ نسخهٔ منتشرشده را immutable فرض کن.

Caches and consumers may see different artifacts; treat published versions as immutable.

۹) framework-dependent9) Framework-dependent

runtime سازگار روی VPS نصب است و patch شدن runtime مرکزی است؛ چه مزیتی دارد؟

A compatible runtime is installed on the VPS and centrally patched. What is the benefit?

راهنماHint

artifact کوچک‌تر و استفاده از runtime host؛ dependency و نسخهٔ موجود را verify کن.

A smaller artifact using the host runtime; verify its availability and version.

۱۰) self-contained10) Self-contained

برنامه برای linux-arm64 می‌رود اما publish روی win-x64 انجام شده؛ اشکال چیست؟

The app targets linux-arm64 but was published on win-x64. What is wrong?

راهنماHint

RID/architecture اشتباه است؛ برای linux-arm64 publish کن و روی target verify کن.

The RID/architecture is wrong; publish for linux-arm64 and verify on target.

۱۱) --no-restore11) --no-restore

برای سرعت این flag را گذاشتی ولی RID تازه‌ای انتخاب شده؛ چرا ممکن است fail شود؟

You added this flag for speed but selected a new RID. Why might it fail?

راهنماHint

assets فایل restore با RID/publish properties فعلی سازگار نیست؛ restore متناظر انجام بده.

The restore assets do not match the current RID/publish properties; restore accordingly.

۱۲) package metadata12) Package metadata

README دارد اما license و repository link ندارد؛ چه چیزهایی را پیش از انتشار کامل می‌کنی؟

A package has a README but no license or repository link. What do you complete before publishing?

راهنماHint

فقط metadata مجاز و درست: توضیح، license تأییدشده، repo، version و targetها.

Accurate authorized metadata only: description, approved license, repository, version and targets.

۱۳) lock conflict13) Lock-file conflict

merge دو branch packages.lock.json را conflict کرده؛ آیا فایل را دستی حدس می‌زنی؟

Two branches conflict in packages.lock.json. Should you guess-edit it manually?

راهنماHint

dependencyها را حل کن، restore نسخهٔ مناسب بزن و تغییر generated lock را بازبینی کن.

Resolve dependency declarations, run the appropriate restore, then review the regenerated lock file.

۱۴) trimming14) Trimming

کتابخانه reflection-based است و publish trim‌شدهٔ کوچک می‌خواهی؛ قدم ایمن چیست؟

A library uses reflection and you want a trimmed publish. What is the safe next step?

راهنماHint

warningها را حل و مسیرهای dynamic را روی خروجی publish تست کن؛ trim را کور فعال نکن.

Address warnings and test dynamic paths on published output; do not enable trimming blindly.

۱۵) self-contained patch15) Self-contained runtime patch

runtime security patch آمده؛ برنامهٔ self-contained چگونه آن را دریافت می‌کند؟

A runtime security patch is released. How does a self-contained app receive it?

راهنماHint

با runtime به‌روز rebuild و دوباره منتشر شود؛ rollout و verify را انجام بده.

Rebuild and republish with the updated runtime, then roll out and verify.

۱۶) مرز package16) Package boundary

سه مصرف‌کننده مستقل package را می‌خواهند ولی API هنوز مدام تغییر می‌کند؛ چه مرحله‌ای را جلو می‌اندازی؟

Three independent consumers want the package, but its API keeps changing. What do you do first?

راهنماHint

contract عمومی را تثبیت، سازگاری و تست مصرف‌کننده را اضافه و بعد انتشار را version کن.

Stabilize the public contract, add compatibility/consumer tests, then version the release.

آزمایشگاه: کتابخانه‌ای که واقعاً مصرف می‌شودLab: a library that is actually consumed

solutionی شامل Core library، CLI و تست بساز. پروژه‌ها را با ProjectReference وصل کن و dependencyهای NuGet را مستقیم و نسخه‌دار ثبت کن. lock file را طبق policy تولید و در clean checkout restore کن. برای Core metadata package را تنظیم و در یک feed محلی pack کن؛ یک consumer کوچک بساز که package را از feed بخواند و API عمومی را compile/test کند. سپس CLI را هم framework-dependent و هم برای یک RID مشخص self-contained publish کن؛ روی محیط هدف یا محیط سازگار اجرا کن و اندازهٔ artifact و runtime dependency را گزارش بده. در پایان یک تغییر سازگار و یک تغییر breaking را روی versioning/changelog توضیح بده، بدون اینکه package منتشرشده را بازنویسی کنی.

Create a solution with a Core library, CLI and tests. Connect projects with ProjectReference and declare direct versioned NuGet dependencies. Generate the lock file according to policy and restore from a clean checkout. Configure package metadata for Core and pack it to a local feed; create a small consumer that restores the package and compiles/tests its public API. Publish the CLI both framework-dependent and self-contained for a chosen RID; run on the target or a compatible environment and report artifact size and runtime requirements. Finally document one compatible and one breaking change without rewriting a published package.

  1. consumer مستقل فقط از API عمومی package استفاده کند.
  2. An independent consumer uses only the package's public API.
  3. خروجی publish و وابستگی runtime هر دو مدل ثبت شود.
  4. Record publish output and runtime requirements for both modes.
  5. restore از clean checkout بدون فایل محلی پنهان موفق باشد.
  6. Restore must succeed from a clean checkout without hidden local files.

هر artifact برای یک مصرف‌کننده و یک قرارداد ساخته می‌شودEvery artifact serves a consumer and a contract

solution برای هماهنگی projectهاست؛ ProjectReference برای همکاری source در یک repo؛ NuGet برای توزیع نسخه‌دار library؛ pack برای ساخت package؛ و publish برای آماده‌کردن برنامهٔ اجرا. lock file تکرارپذیری restore را بهتر می‌کند، نه امنیت خودکار را. مدل runtime-dependent یا self-contained هم trade-off اندازه، patch و محیط دارد. فصل بعد سراغ assembly و بارگذاری plugin می‌رویم تا بفهمیم مرز compile-time و runtime چه تفاوتی دارد.

A solution coordinates projects; ProjectReference connects source within a repository; NuGet distributes versioned libraries; pack creates packages; publish prepares applications to run. A lock file improves restore repeatability, not automatic security. Framework-dependent and self-contained modes trade artifact size, patching and host requirements.
