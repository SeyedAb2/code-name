شیء، کلاس و فیلد

Objects, classes and fields

دو گزارش از یک سفارش داریم و هر دو عدد متفاوتی برای مبلغ نشان می‌دن. مشکل از حساب‌وکتاب نیست؛ وضعیت سفارش در چند متغیر پراکنده شده و هیچ‌کس مسئول نگهداری سازگاری‌شان نیست. بیایید داده و رفتاری رو که باید با هم بمانند، داخل یک شیء جمع کنیم.

Two reports show different totals for the same order. The arithmetic is not the problem: order state is scattered across variables, and nothing owns the responsibility of keeping it consistent. Let’s bring data and the behaviour that belongs with it into an object.

وقتی مبلغ سفارش در دو جا دو جواب دارهWhen two places show two order totals

فصل قبل دربارهٔ ارجاع‌ها دیدیم چند متغیر ممکنه به یک شیء برسند. حالا هنوز شیء نداریم: چند مقدار مستقل داریم که باید همیشه هماهنگ بمانند.

In the previous chapter, we saw that several variables can refer to one object. Here we do not have an object yet—only independent values that are expected to stay in sync.

وضعیت پراکنده · Program.cs / Scattered state
string orderNumber = "A-42";
int itemCount = 2;
decimal unitPrice = 125m;
decimal total = itemCount * unitPrice;

// A later discount changes total, but not every report is updated.
total = 200m;
Console.WriteLine($"{orderNumber}: {itemCount} × {unitPrice} = {total}");

کد کامپایل می‌شه، اما رابطهٔ total با تعداد و قیمت از دست رفته. هر متدی که این مقادیر رو جدا بگیرد می‌تونه ترکیب ناسازگاری بسازد: تعداد دو، قیمت ۱۲۵ و مبلغ ۲۰۰، بی‌آنکه بداند تخفیف از کجا آمده. پرسش طراحی این هست: کدوم داده‌ها یک مفهوم رو می‌سازن و کدوم رفتار باید مسئول سازگاری‌شان باشه؟

The code compiles, but the relationship between total, quantity and price is lost. A method receiving these values separately can assemble an inconsistent combination: quantity two, price 125 and total 200, without knowing where the discount came from. The design question is: which values form one concept, and which behaviour owns their consistency?

کلاس فقط کیسهٔ فیلدها نیستA class is more than a bag of fields

کلاس زمانی مفید هست که علاوه بر کنار هم گذاشتن داده‌ها، مرز مسئولیت رو روشن کند. صرف ساختن یک کلاس هنوز invariant رو تضمین نمی‌کنه؛ caller ممکنه راه مستقیمی برای خراب‌کردنش داشته باشه.

A class is useful when it clarifies responsibility as well as grouping data. Merely creating a class does not guarantee an invariant; callers may still have a direct way to break it.

کلاس رو برای کنار هم گذاشتن داده نساز؛ برای صاحب‌کردن مسئولیت بسازDo not create a class just to group data; give responsibility an owner

یه کلاس با ده تا property عمومی هنوز طراحی شیءگرا نیست؛ فقط یه bag شیک از داده‌هاست. نقطهٔ جالب وقتی شروع می‌شه که بپرسیم «چه کسی حق داره این state رو عوض کنه و چه شرطی باید همیشه برقرار بمونه؟». اگه هر caller بتونه هر فیلدی رو مستقیم دست‌کاری کنه، اسم class به‌تنهایی هیچ invariantی رو نجات نمی‌ده.

A class with ten public properties is not automatically object-oriented design; it may only be a nicer bag of data. The interesting question is: “Who is allowed to change this state, and which condition must always remain true?” If every caller can mutate every field directly, the word `class` does not protect an invariant.

در مثال سفارش، هدف این نیست که صرفاً `Order` بسازیم. می‌خوایم پراکندگی state رو جمع کنیم، بعد قدم‌به‌قدم راه‌های خراب‌کردنش رو ببندیم. همین مدل ذهنی فصل‌های constructor، property، composition و inheritance رو به هم وصل می‌کنه.

With the order example, the goal is not merely to create an `Order` type. We gather scattered state, then close the paths that can corrupt it one by one. That mental model connects constructors, properties, composition, and inheritance in the following chapters.

کلاس تعریفه؛ شیء یک نمونهٔ مشخصA class is a definition; an object is one instance

کلاس نوع و اعضایش رو تعریف می‌کنه. هر بار که نمونه می‌سازیم، object جدا با state خودش داریم. رفتار تعریف‌شده مشترک هست، اما شماره و تعداد هر سفارش به همان instance تعلق داره.

A class defines a type and its members. Each construction gives us a separate object with its own state. The defined behaviour is shared, while each order’s number and quantity belong to that instance.

تعریف کلاس و دو نمونه / Class and two instances
class Order
{
    public string Number = string.Empty;
    public int ItemCount;
    public decimal UnitPrice;

    public decimal Total() => ItemCount * UnitPrice;
}

var first = new Order { Number = "A-42", ItemCount = 2, UnitPrice = 125m };
var second = new Order { Number = "B-17", ItemCount = 1, UnitPrice = 80m };

Console.WriteLine(first.Total());
Console.WriteLine(second.Total());
خروجی / Expected output
250
80

هر new یک object می‌سازه. تغییر تعداد first نباید سفارش second رو تغییر دهد. اما متغیرها خود object نیستن؛ reference دارن. پس var alias = first یک نام دیگر برای همان instance می‌سازه، نه سفارش تازه.

Each new creates an object. Changing first’s quantity should not change second. But variables are not the objects themselves; they hold references. So var alias = first creates another name for the same instance, not a new order.

فیلد state نگه می‌داره؛ متد رفتار رو کنار آن می‌آوردFields store state; methods bring behaviour beside it

فیلد محل نگهداری دادهٔ instance هست. متد Total با خواندن همان فیلدها، یک محاسبهٔ واحد می‌ده؛ لازم نیست هر مصرف‌کننده تعداد و قیمت رو دوباره ارسال کند و فرمول تازه‌ای بسازد. فعلاً فیلدها public هستن تا شکل پایه رو ببینیم؛ این آزادی رو عمداً در آزمایش بعد نقد می‌کنیم.

An instance field stores object state. Total reads those fields and provides one calculation; consumers need not resend quantity and price and invent another formula. The fields are public for this first sketch; we will deliberately critique that freedom next.

رفتار اعتبارسنجی‌شده / A validated operation
class Order
{
    public string Number = string.Empty;
    public int ItemCount;
    public decimal UnitPrice;

    public decimal Total() => ItemCount * UnitPrice;

    public void AddItems(int count)
    {
        if (count <= 0)
            throw new ArgumentOutOfRangeException(nameof(count));

        ItemCount += count;
    }
}

AddItems ردکردن ورودی نامعتبر و تغییر state رو یک‌جا انجام می‌ده؛ اما caller هنوز می‌تونه مستقیم ItemCount = -10 بنویسد و این متد رو دور بزند. پس رفتار داخل کلاس مفید هست، ولی تا وقتی دسترسی مستقیم باز هست invariant کامل نیست. فصل‌های سازنده و property این مرز رو محکم‌تر می‌کنن.

AddItems validates input and changes state in one place, but a caller can still assign ItemCount = -10 directly and bypass it. Behaviour inside the class is useful, but the invariant is not complete while direct access remains open. The constructor and property chapters will strengthen this boundary.

دو نام ممکنه به یک سفارش برسندTwo names may reach the same order

پیش‌بینی کن تغییر از alias در original دیده می‌شه یا نه؛ بعد اجرا کن. این همان مدل reference فصل ۱۱ هست، این‌بار با یک مفهوم واقعی.

Predict whether a mutation through alias will be visible through original, then run it. This is the reference model from Chapter 11, now with a real domain concept.

یک شیء، دو مسیر دسترسی / One object, two references
var original = new Order { Number = "A-42", ItemCount = 1, UnitPrice = 50m };
var alias = original;
alias.ItemCount = 3;

Console.WriteLine(original.ItemCount);
Console.WriteLine(ReferenceEquals(original, alias));
خروجی / Output
3
True

کپی reference سفارش تازه نمی‌سازه. اگه دو سفارش باید مستقل باشن، دو بار نمونه‌سازی کن. alias ناخواسته یکی از علت‌های تغییر state از مسیری هست که هنگام بررسی اولیه به چشم نمیاد؛ identity و مقدار رو جداگانه بررسی کن.

Copying a reference does not create another order. If two orders must be independent, construct twice. An accidental alias can make state change through an unexpected path; inspect identity and values separately.

از مثال نتیجهٔ حافظه‌ای نسازDo not infer a memory-layout myth

این آزمایش دربارهٔ semantics ارجاع هست: دو متغیر به همان instance می‌رسن. از آن نتیجهٔ ساده‌انگارانه‌ای مثل «همهٔ objectها همیشه در فلان ناحیهٔ حافظه‌اند» نگیر؛ پیاده‌سازی runtime موضوع دیگری هست.

This experiment demonstrates reference semantics: two variables reach the same instance. Do not infer a simplistic claim such as “all objects are always in a particular memory region”; runtime implementation is a separate subject.

state متعلق به instance هست یا type؟Does state belong to an instance or to the type?

شماره و تعداد مخصوص هر سفارش‌اند. اگه ItemCount رو static کنیم، دیگر تعداد هر سفارش رو نداریم؛ یک state مشترک متعلق به خود type داریم. static رو فقط وقتی انتخاب کن که داده واقعاً بین همهٔ نمونه‌ها مشترک هست.

Number and quantity belong to each order. If ItemCount becomes static, we no longer have a quantity per order; we have shared state belonging to the type. Choose static only when data truly is shared by every instance.

عضو مشترک / Type-level state
class Order
{
    public static int ItemCount;
}

Order.ItemCount = 4;
Console.WriteLine(Order.ItemCount);

دسترسی به عضو static با نام type انجام می‌شه. اگه دو سفارش تعداد متفاوت دارن، این مدل از اساس اشتباهه: هر تغییر مقدار مشترک رو عوض می‌کنه. جای state رو با نیاز محصول تعیین کن، نه برای راحت‌شدن دسترسی از هر نقطه.

A static member is accessed through its type. If two orders have different quantities, this model is fundamentally wrong: every mutation changes the shared value. Let product requirements decide state ownership, not convenience of global access.

یک برنامهٔ کوچک کنسولی بساز. هدف فقط «نوشتن کلاس» نیست؛ باید با شواهد نشان بدهی دو سفارش مستقل‌اند، محاسبه یک‌جا انجام می‌شه و alias همان سفارش رو تغییر می‌ده.

Build a small console program. The goal is not merely to “write a class”: prove with evidence that two orders are independent, the calculation lives in one place, and an alias mutates the same order.

  1. Order رو با شماره، تعداد، قیمت واحد و Total بساز.
  2. Create Order with number, quantity, unit price and Total.
  3. دو سفارش بساز، خروجی رو حدس بزن و بعد مبلغ هر دو رو چاپ کن.
  4. Create two orders, predict the output, then print both totals.
  5. reference یکی رو کپی کن، از مسیر دوم تعداد رو تغییر بده و state اصلی رو بخوان.
  6. Copy one reference, mutate quantity through the second name and inspect the original state.
  7. تعداد رو منفی کن؛ invariant رو تعریف و مسیرهای دورزدنش رو فهرست کن.
  8. Set quantity negative; define the invariant and list ways to bypass it.
  9. تغییر رو داخل AddItems قرار بده و ورودی صفر و منفی رو جدا آزمایش کن.
  10. Move mutation into AddItems and test zero and negative inputs separately.
شواهدی که نگه می‌داری / Evidence to keep
Order A-42 total: 250
Order B-17 total: 80
After alias mutation, A-42 quantity: 3
Same instance: True

اگه عددها متفاوت شد، اول ورودی، تعداد دفعات new و reference تغییرکرده رو بررسی کن. تفاوت ممکنه خطای آزمایش باشه یا نشانهٔ state مشترک ناخواسته؛ با چاپ identity و مقدار فرضیه رو بسنج.

If the values differ, first inspect inputs, construction count and the reference you mutated. The difference may be an experiment mistake or unintended shared state; test the hypothesis by printing identity and values.
