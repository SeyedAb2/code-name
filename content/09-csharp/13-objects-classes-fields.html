شیء، کلاس و فیلد

Objects, classes and fields

دو گزارش از یک سفارش داریم و هر دو عدد متفاوتی برای مبلغ نشان می‌دهند. مشکل از حساب‌وکتاب نیست؛ وضعیت سفارش در چند متغیر پراکنده شده و هیچ‌کس مسئول نگهداری سازگاری‌شان نیست. بیایید داده و رفتاری را که باید با هم بمانند، داخل یک شیء جمع کنیم.

Two reports show different totals for the same order. The arithmetic is not the problem: order state is scattered across variables, and nothing owns the responsibility of keeping it consistent. Let’s bring data and the behaviour that belongs with it into an object.

فصل ۱۲پیش‌نیازprerequisite

وقتی مبلغ سفارش در دو جا دو جواب داردWhen two places show two order totals

فصل قبل دربارهٔ ارجاع‌ها دیدیم چند متغیر ممکن است به یک شیء برسند. حالا هنوز شیء نداریم: چند مقدار مستقل داریم که باید همیشه هماهنگ بمانند.

In the previous chapter, we saw that several variables can refer to one object. Here we do not have an object yet—only independent values that are expected to stay in sync.

وضعیت پراکنده · Program.cs / Scattered state
string orderNumber = "A-42";
int itemCount = 2;
decimal unitPrice = 125m;
decimal total = itemCount * unitPrice;

// A later discount changes total, but not every report is updated.
total = 200m;
Console.WriteLine($"{orderNumber}: {itemCount} × {unitPrice} = {total}");

کد کامپایل می‌شود، اما رابطهٔ total با تعداد و قیمت از دست رفته. هر متدی که این مقادیر را جدا بگیرد می‌تواند ترکیب ناسازگاری بسازد: تعداد دو، قیمت ۱۲۵ و مبلغ ۲۰۰، بی‌آنکه بداند تخفیف از کجا آمده. پرسش طراحی این است: کدام داده‌ها یک مفهوم را می‌سازند و کدام رفتار باید مسئول سازگاری‌شان باشد؟

The code compiles, but the relationship between total, quantity and price is lost. A method receiving these values separately can assemble an inconsistent combination: quantity two, price 125 and total 200, without knowing where the discount came from. The design question is: which values form one concept, and which behaviour owns their consistency?

کلاس فقط کیسهٔ فیلدها نیستA class is more than a bag of fields

کلاس زمانی مفید است که علاوه بر کنار هم گذاشتن داده‌ها، مرز مسئولیت را روشن کند. صرف ساختن یک کلاس هنوز invariant را تضمین نمی‌کند؛ caller ممکن است راه مستقیمی برای خراب‌کردنش داشته باشد.

A class is useful when it clarifies responsibility as well as grouping data. Merely creating a class does not guarantee an invariant; callers may still have a direct way to break it.

کلاس تعریف است؛ شیء یک نمونهٔ مشخصA class is a definition; an object is one instance

کلاس نوع و اعضایش را تعریف می‌کند. هر بار که نمونه می‌سازیم، object جدا با state خودش داریم. رفتار تعریف‌شده مشترک است، اما شماره و تعداد هر سفارش به همان instance تعلق دارد.

A class defines a type and its members. Each construction gives us a separate object with its own state. The defined behaviour is shared, while each order’s number and quantity belong to that instance.

تعریف کلاس و دو نمونه / Class and two instances
class Order
{
    public string Number = string.Empty;
    public int ItemCount;
    public decimal UnitPrice;

    public decimal Total() => ItemCount * UnitPrice;
}

var first = new Order { Number = "A-42", ItemCount = 2, UnitPrice = 125m };
var second = new Order { Number = "B-17", ItemCount = 1, UnitPrice = 80m };

Console.WriteLine(first.Total());
Console.WriteLine(second.Total());
خروجی / Expected output
250
80

هر new یک object می‌سازد. تغییر تعداد first نباید سفارش second را تغییر دهد. اما متغیرها خود object نیستند؛ reference دارند. پس var alias = first یک نام دیگر برای همان instance می‌سازد، نه سفارش تازه.

Each new creates an object. Changing first’s quantity should not change second. But variables are not the objects themselves; they hold references. So var alias = first creates another name for the same instance, not a new order.

فیلد state نگه می‌دارد؛ متد رفتار را کنار آن می‌آوردFields store state; methods bring behaviour beside it

فیلد محل نگهداری دادهٔ instance است. متد Total با خواندن همان فیلدها، یک محاسبهٔ واحد می‌دهد؛ لازم نیست هر مصرف‌کننده تعداد و قیمت را دوباره ارسال کند و فرمول تازه‌ای بسازد. فعلاً فیلدها public هستند تا شکل پایه را ببینیم؛ این آزادی را عمداً در آزمایش بعد نقد می‌کنیم.

An instance field stores object state. Total reads those fields and provides one calculation; consumers need not resend quantity and price and invent another formula. The fields are public for this first sketch; we will deliberately critique that freedom next.

رفتار اعتبارسنجی‌شده / A validated operation
class Order
{
    public string Number = string.Empty;
    public int ItemCount;
    public decimal UnitPrice;

    public decimal Total() => ItemCount * UnitPrice;

    public void AddItems(int count)
    {
        if (count <= 0)
            throw new ArgumentOutOfRangeException(nameof(count));

        ItemCount += count;
    }
}

AddItems ردکردن ورودی نامعتبر و تغییر state را یک‌جا انجام می‌دهد؛ اما caller هنوز می‌تواند مستقیم ItemCount = -10 بنویسد و این متد را دور بزند. پس رفتار داخل کلاس مفید است، ولی تا وقتی دسترسی مستقیم باز است invariant کامل نیست. فصل‌های سازنده و property این مرز را محکم‌تر می‌کنند.

AddItems validates input and changes state in one place, but a caller can still assign ItemCount = -10 directly and bypass it. Behaviour inside the class is useful, but the invariant is not complete while direct access remains open. The constructor and property chapters will strengthen this boundary.

دو نام ممکن است به یک سفارش برسندTwo names may reach the same order

پیش‌بینی کن تغییر از alias در original دیده می‌شود یا نه؛ بعد اجرا کن. این همان مدل reference فصل ۱۱ است، این‌بار با یک مفهوم واقعی.

Predict whether a mutation through alias will be visible through original, then run it. This is the reference model from Chapter 11, now with a real domain concept.

یک شیء، دو مسیر دسترسی / One object, two references
var original = new Order { Number = "A-42", ItemCount = 1, UnitPrice = 50m };
var alias = original;
alias.ItemCount = 3;

Console.WriteLine(original.ItemCount);
Console.WriteLine(ReferenceEquals(original, alias));
خروجی / Output
3
True

کپی reference سفارش تازه نمی‌سازد. اگر دو سفارش باید مستقل باشند، دو بار نمونه‌سازی کن. alias ناخواسته یکی از علت‌های تغییر state از مسیری است که هنگام بررسی اولیه به چشم نمی‌آید؛ identity و مقدار را جداگانه بررسی کن.

Copying a reference does not create another order. If two orders must be independent, construct twice. An accidental alias can make state change through an unexpected path; inspect identity and values separately.

از مثال نتیجهٔ حافظه‌ای نسازDo not infer a memory-layout myth

این آزمایش دربارهٔ semantics ارجاع است: دو متغیر به همان instance می‌رسند. از آن نتیجهٔ ساده‌انگارانه‌ای مثل «همهٔ objectها همیشه در فلان ناحیهٔ حافظه‌اند» نگیر؛ پیاده‌سازی runtime موضوع دیگری است.

This experiment demonstrates reference semantics: two variables reach the same instance. Do not infer a simplistic claim such as “all objects are always in a particular memory region”; runtime implementation is a separate subject.

state متعلق به instance است یا type؟Does state belong to an instance or to the type?

شماره و تعداد مخصوص هر سفارش‌اند. اگر ItemCount را static کنیم، دیگر تعداد هر سفارش را نداریم؛ یک state مشترک متعلق به خود type داریم. static را فقط وقتی انتخاب کن که داده واقعاً بین همهٔ نمونه‌ها مشترک است.

Number and quantity belong to each order. If ItemCount becomes static, we no longer have a quantity per order; we have shared state belonging to the type. Choose static only when data truly is shared by every instance.

عضو مشترک / Type-level state
class Order
{
    public static int ItemCount;
}

Order.ItemCount = 4;
Console.WriteLine(Order.ItemCount);

دسترسی به عضو static با نام type انجام می‌شود. اگر دو سفارش تعداد متفاوت دارند، این مدل از اساس اشتباه است: هر تغییر مقدار مشترک را عوض می‌کند. جای state را با نیاز محصول تعیین کن، نه برای راحت‌شدن دسترسی از هر نقطه.

A static member is accessed through its type. If two orders have different quantities, this model is fundamentally wrong: every mutation changes the shared value. Let product requirements decide state ownership, not convenience of global access.

آزمایشگاه: هر سفارش صاحب state خودش باشدLab: let each order own its state

یک برنامهٔ کوچک کنسولی بساز. هدف فقط «نوشتن کلاس» نیست؛ باید با شواهد نشان بدهی دو سفارش مستقل‌اند، محاسبه یک‌جا انجام می‌شود و alias همان سفارش را تغییر می‌دهد.

Build a small console program. The goal is not merely to “write a class”: prove with evidence that two orders are independent, the calculation lives in one place, and an alias mutates the same order.

  1. Order را با شماره، تعداد، قیمت واحد و Total بساز.
  2. Create Order with number, quantity, unit price and Total.
  3. دو سفارش بساز، خروجی را حدس بزن و بعد مبلغ هر دو را چاپ کن.
  4. Create two orders, predict the output, then print both totals.
  5. reference یکی را کپی کن، از مسیر دوم تعداد را تغییر بده و state اصلی را بخوان.
  6. Copy one reference, mutate quantity through the second name and inspect the original state.
  7. تعداد را منفی کن؛ invariant را تعریف و مسیرهای دورزدنش را فهرست کن.
  8. Set quantity negative; define the invariant and list ways to bypass it.
  9. تغییر را داخل AddItems قرار بده و ورودی صفر و منفی را جدا آزمایش کن.
  10. Move mutation into AddItems and test zero and negative inputs separately.
شواهدی که نگه می‌داری / Evidence to keep
Order A-42 total: 250
Order B-17 total: 80
After alias mutation, A-42 quantity: 3
Same instance: True

اگر عددها متفاوت شد، اول ورودی، تعداد دفعات new و reference تغییرکرده را بررسی کن. تفاوت ممکن است خطای آزمایش باشد یا نشانهٔ state مشترک ناخواسته؛ با چاپ identity و مقدار فرضیه را بسنج.

If the values differ, first inspect inputs, construction count and the reference you mutated. The difference may be an experiment mistake or unintended shared state; test the hypothesis by printing identity and values.

۱۲) static را نقد کن12) Critique static

چرا ItemCount مشترک برای چند سفارش مدل درستی نیست؟

Why is one shared ItemCount wrong for multiple orders?

پاسخAnswer

تعداد متعلق به هر سفارش است؛ static آن را به یک مقدار مشترک تبدیل می‌کند و state مستقل را از بین می‌برد.

۱۳) دو فرمول تکراری را حذف کن13) Remove duplicate calculations

دو گزارش فرمول total جدا دارند و یکی تخفیف را فراموش می‌کند. چه تغییری می‌دهی؟

Two reports calculate total separately and one forgets discounts. What would you change?

پاسخAnswer

قاعده را در یک مسئولیت نگه می‌دارم و هر دو گزارش را به همان قرارداد وصل می‌کنم؛ انتخاب مالک با دامنهٔ قاعده است.

Keep the rule under one owner and make both reports use that contract; the domain determines the owner.

۱۵) متد instance یا تابع مستقل؟15) Instance method or standalone function?

چه وقت Total(count, price) بیرونی مناسب است و چه وقت order.Total خواناتر است؟

When is standalone Total(count, price) suitable, and when is order.Total clearer?

استدلالReasoning

محاسبهٔ عمومی و بی‌حالت می‌تواند تابع مستقل باشد. اگر قاعده به state و invariant سفارش وابسته است، رفتار instance دادهٔ تکراری و محاسبهٔ پراکنده را کم می‌کند.

A general stateless calculation can be standalone. If the rule depends on order state and invariants, instance behaviour reduces duplicated inputs and scattered calculations.

۱۶) گزارشِ state مشترک را عیب‌یابی کن16) Diagnose unexpectedly shared state

با تغییر سفارش آخر، گزارش قبلی هم عوض شده. به‌ترتیب چه شواهدی را بررسی می‌کنی؟

Changing the latest order also changes an earlier report. What evidence do you inspect, in order?

مسیر تشخیصDiagnosis path

تعداد newها، assignment و aliasها، سپس static یا منبع دادهٔ مشترک. با دو نمونهٔ مستقل، چاپ ReferenceEquals و state فرضیه را بسنج؛ فقط از روی ظاهر گزارش نتیجه نگیر.

Check construction count, assignments and aliases, then static members or a shared data source. Test with two instances, ReferenceEquals and printed state; do not diagnose from the report alone.

شیء یعنی state با مسئولیت روشنAn object gives state a clear owner

وقتی چند مقدار با هم تغییر می‌کنند، بپرس آیا یک مفهوم‌اند، کدام instance صاحب state است و کدام رفتار باید آن را تغییر دهد. کلاس وقتی کمک می‌کند که مرز را روشن کند؛ اگر فقط نام تازه‌ای برای متغیرهای پراکنده بسازد، مسئله حل نشده.

When several values change together, ask whether they form one concept, which instance owns the state, and which behaviour should change it. A class helps when it clarifies that boundary; merely renaming scattered variables does not solve the problem.

در این فصل دیدیم caller می‌تواند اعتبارسنجی را دور بزند چون فیلد public بود. فصل بعد با سازنده و property این مرز را محکم می‌کنیم و invariant را هنگام ساختن و تغییر شیء حفظ می‌کنیم.

We saw that callers can bypass validation because the field was public. Next, constructors and properties will strengthen the boundary and preserve invariants during construction and mutation.
