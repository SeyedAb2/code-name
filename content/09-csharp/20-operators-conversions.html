Operators and conversions

در کد مالی، این عبارت از نظر ظاهری ساده است اما کسی نمی‌داند گردکردن کجا انجام شده: مبلغ + مالیات. اگر برای نوع‌های خودمان operator بسازیم، کد خواناتر می‌شود یا معنای تازه‌ای را پنهان می‌کنیم؟

In a financial code path, this expression looks simple, but no one knows where rounding happened: amount + tax. Will custom operators make our types clearer, or hide new semantics?

تبدیل ضمنی راحت است؛ اما کجا هزینه دارد؟Implicit conversion is convenient—but what does it cost?

تبدیل implicit به compiler اجازه می‌دهد بدون syntax آشکار نوع را عوض کند. این برای تبدیل بی‌خطر و بدون از دست‌رفتن اطلاعات مناسب است؛ اما اگر precision، واحد یا اعتبار داده تغییر می‌کند، call site باید تصمیم را ببیند.

An implicit conversion lets the compiler change types without visible syntax. It fits safe conversions with no information loss; when precision, units or validity change, the call site should see the decision.

واحد را پنهان نکن / Make units visible
decimal metres = 1.5m;
decimal centimetres = metres * 100m;
Console.WriteLine(centimetres);

برای مقدارهای خام decimal، کامپایلر نمی‌داند این عدد متر است یا سانتی‌متر. تبدیل نوع سفارشی ممکن است واحد را مدل کند، اما تبدیل ضمنی بین واحدهای متفاوت می‌تواند باگ را بی‌صدا عبور دهد. انتخاب explicit باید call site را به تصمیم وادار کند.

A raw decimal does not tell the compiler whether it represents metres or centimetres. A custom type can model units, but an implicit conversion between different units may silently pass a bug. An explicit conversion forces the call site to acknowledge the decision.

operator را فقط وقتی تعریف کن که خواننده معنایش را حدس می‌زندDefine an operator only when readers can predict its meaning

برای نوع مقدارمحور مثل Money، جمع دو مقدار هم‌ارز می‌تواند طبیعی باشد. عملگر باید دقیقاً همان معنا را اجرا کند که از syntax انتظار می‌رود، بدون I/O یا تغییر پنهانی state. همهٔ operatorها قابل overload نیستند و قواعد زبانی شکل declaration را محدود می‌کنند؛ مستند رسمی را برای جفت‌های لازم بررسی کن.

For a value type such as Money, adding two compatible amounts may be natural. The operator should do exactly what its syntax suggests, without I/O or hidden state mutation. Not every operator is overloadable, and declaration forms are constrained by the language; check the reference for required operator pairs.

Money مقدارمحور / Value-oriented Money
public readonly record struct Money(decimal Amount, string Currency)
{
    public static Money operator +(Money left, Money right)
    {
        if (!StringComparer.Ordinal.Equals(left.Currency, right.Currency))
            throw new InvalidOperationException("Currencies must match.");

        return new Money(left.Amount + right.Amount, left.Currency);
    }
}

var total = new Money(12m, "IRR") + new Money(8m, "IRR");
Console.WriteLine(total);

جمع ارزهای یکسان ۲۰ می‌شود؛ جمع IRR و EUR رد می‌شود. اگر عملیات نیازمند نرخ زنده، زمان یا شبکه است، operator نام مناسبی نیست؛ متد صریحی مثل ConvertTo(rate) قرارداد و خطا را بهتر نشان می‌دهد.

Adding the same currency yields 20; mixing IRR and EUR is rejected. If an operation needs a live rate, time or network, an operator is the wrong abstraction; an explicit method such as ConvertTo(rate) communicates its contract and failure better.

برابری را بین operator و Equals هماهنگ کنKeep operator equality aligned with Equals

اگر == را overload می‌کنی، رفتار آن باید با Equals و GetHashCode هماهنگ باشد؛ وگرنه یک call site «برابر» و Dictionary نتیجهٔ دیگری می‌بیند. ترجیح بده record یا نوع‌های مقدارمحورِ زبان equality را بسازند، مگر اینکه قرارداد ویژه‌ای لازم باشد و کامل تست شود.

If you overload ==, keep it consistent with Equals and GetHashCode; otherwise one call site sees “equal” while a Dictionary sees something else. Prefer language-generated equality for records or value-oriented types unless a special, fully tested contract is needed.

خوانایی محلی کافی نیستLocal readability is not enough

operator کوتاه ممکن است کنار call site زیبا باشد اما معنایش برای کسی که نوع را نمی‌شناسد پنهان بماند. API عمومی باید رفتار و exceptionها را مستند کند و تست برابری/hash را باهم داشته باشد.

A short operator may look elegant at one call site while hiding meaning from someone unfamiliar with the type. A public API should document behaviour and exceptions and test equality and hashing together.

implicit، explicit و checked را از دست‌رفتن اطلاعات تعیین می‌کندInformation loss should drive implicit, explicit and checked conversions

تبدیل narrowing ممکن است بخشی از مقدار را دور بیندازد. در C# تبدیل explicit این تصمیم را در syntax آشکار می‌کند؛ checked برای بعضی تبدیل‌های عددی و عملگرهای checked جلوی سرریز را می‌گیرد، اما هر تبدیل خطرناکی را جادویی ایمن نمی‌کند. رفتار نوع مقصد و نسخهٔ زبان را جدا بررسی کن.

A narrowing conversion may discard information. In C#, explicit syntax makes that choice visible; checked protects against overflow for supported numeric conversions and checked operators, but it does not magically validate every dangerous conversion. Inspect the target type and language support separately.

checked و unchecked
int value = 300;
byte wrapped = unchecked((byte)value);
Console.WriteLine(wrapped);

try
{
    byte checkedValue = checked((byte)value);
}
catch (OverflowException)
{
    Console.WriteLine("outside byte range");
}
خروجی / Output
44
outside byte range

در این تبدیل عددی، unchecked wrap نتیجهٔ قابل‌استفاده اما از دست‌رفته می‌دهد؛ checked استثنا می‌دهد. این تفاوت را با parsing اشتباه نگیر: parse ممکن است format نامعتبر را هم رد کند، در حالی که cast فقط تبدیل عددی انجام می‌دهد.

For this numeric conversion, unchecked wraps to a lossy result while checked throws. Do not confuse this with parsing: parsing can reject invalid text format, while a cast performs a numeric conversion.

تبدیل user-defined باید یک‌جهته و قابل‌پیش‌بینی باشدA user-defined conversion should be one-way and predictable

تبدیل implicit سفارشی برای چیزی مناسب است که همیشه امن، ارزان و بدون ابهام باشد؛ مثل wrapperی که دقیقاً همان مقدار را نمایندگی می‌کند. اگر ممکن است شکست بخورد یا معنای محصول انتخاب لازم دارد، explicit یا factory method بهتر است. تبدیل‌های زنجیره‌ای مبهم نساز.

A custom implicit conversion fits a value that is always safe, cheap and unambiguous, such as a wrapper representing exactly the same value. If it can fail or requires a product decision, explicit conversion or a factory method is clearer. Avoid ambiguous conversion chains.

تبدیل صریح قابل‌ردیابی / Explicit conversion
readonly record struct Percentage(decimal Value)
{
    public static explicit operator Percentage(decimal value)
    {
        if (value is < 0m or > 100m)
            throw new ArgumentOutOfRangeException(nameof(value));
        return new Percentage(value);
    }
}

var discount = (Percentage)15m;

cast در call site نشان می‌دهد decimal قرار است به یک مفهوم دامنه‌ای تبدیل شود؛ validation هم مقادیر خارج از بازه را می‌گیرد. اگر مصرف‌کننده به توضیح خطا یا چند policy نیاز دارد، static factory با نام روشن ممکن است بهتر باشد.

The cast makes the domain conversion visible, and validation rejects values outside the range. If callers need detailed errors or multiple policies, a clearly named static factory may be better.

معیار پایانDefinition of done

تبدیل خطرناک در call site پیداست؛ واحدها بی‌صدا قاطی نمی‌شوند؛ equality/hash یک قرارداد دارند؛ و تست‌ها مسیر موفق و خطا را پوشش می‌دهند.

Expressions gain competing conversion paths, harming overload resolution and clarity. Choose one clear direction or named APIs.
