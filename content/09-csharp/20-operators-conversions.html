Operators and conversions

در کد مالی، این عبارت از نظر ظاهری ساده هست اما کسی نمی‌دونه گردکردن کجا انجام شده: مبلغ + مالیات. اگه برای نوع‌های خودمان operator بسازیم، کد خواناتر می‌شه یا معنای تازه‌ای رو پنهان می‌کنیم؟

In a financial code path, this expression looks simple, but no one knows where rounding happened: amount + tax. Will custom operators make our types clearer, or hide new semantics?

تبدیل ضمنی راحت هست؛ اما کجا هزینه داره؟Implicit conversion is convenient—but what does it cost?

تبدیل implicit به compiler اجازه می‌ده بدون syntax آشکار نوع رو عوض کند. این برای تبدیل بی‌خطر و بدون از دست‌رفتن اطلاعات مناسب هست؛ اما اگه precision، واحد یا اعتبار داده تغییر می‌کنه، call site باید تصمیم رو ببیند.

An implicit conversion lets the compiler change types without visible syntax. It fits safe conversions with no information loss; when precision, units or validity change, the call site should see the decision.

واحد را پنهان نکن / Make units visible
decimal metres = 1.5m;
decimal centimetres = metres * 100m;
Console.WriteLine(centimetres);

برای مقدارهای خام decimal، کامپایلر نمی‌دونه این عدد متر هست یا سانتی‌متر. تبدیل نوع سفارشی ممکنه واحد رو مدل کند، اما تبدیل ضمنی بین واحدهای متفاوت می‌تونه باگ رو بی‌صدا عبور دهد. انتخاب explicit باید call site رو به تصمیم وادار کند.

A raw decimal does not tell the compiler whether it represents metres or centimetres. A custom type can model units, but an implicit conversion between different units may silently pass a bug. An explicit conversion forces the call site to acknowledge the decision.

operator رو فقط وقتی تعریف کن که خواننده معنایش رو حدس می‌زنهDefine an operator only when readers can predict its meaning

برای نوع مقدارمحور مثل Money، جمع دو مقدار هم‌ارز می‌تونه طبیعی باشه. عملگر باید دقیقاً همان معنا رو اجرا کند که از syntax انتظار می‌ره، بدون I/O یا تغییر پنهانی state. همهٔ operatorها قابل overload نیستن و قواعد زبانی شکل declaration رو محدود می‌کنن؛ مستند رسمی رو برای جفت‌های لازم بررسی کن.

For a value type such as Money, adding two compatible amounts may be natural. The operator should do exactly what its syntax suggests, without I/O or hidden state mutation. Not every operator is overloadable, and declaration forms are constrained by the language; check the reference for required operator pairs.

Money مقدارمحور / Value-oriented Money
public readonly record struct Money(decimal Amount, string Currency)
{
    public static Money operator +(Money left, Money right)
    {
        if (!StringComparer.Ordinal.Equals(left.Currency, right.Currency))
            throw new InvalidOperationException("Currencies must match.");

        return new Money(left.Amount + right.Amount, left.Currency);
    }
}

var total = new Money(12m, "IRR") + new Money(8m, "IRR");
Console.WriteLine(total);

جمع ارزهای یکسان ۲۰ می‌شه؛ جمع IRR و EUR رد می‌شه. اگه عملیات نیازمند نرخ زنده، زمان یا شبکه هست، operator نام مناسبی نیست؛ متد صریحی مثل ConvertTo(rate) قرارداد و خطا رو بهتر نشان می‌ده.

Adding the same currency yields 20; mixing IRR and EUR is rejected. If an operation needs a live rate, time or network, an operator is the wrong abstraction; an explicit method such as ConvertTo(rate) communicates its contract and failure better.

برابری رو بین operator و Equals هماهنگ کنKeep operator equality aligned with Equals

اگه == رو overload می‌کنی، رفتار آن باید با Equals و GetHashCode هماهنگ باشه؛ وگرنه یک call site «برابر» و Dictionary نتیجهٔ دیگری می‌بینه. ترجیح بده record یا نوع‌های مقدارمحورِ زبان equality رو بسازند، مگر اینکه قرارداد ویژه‌ای لازم باشه و کامل تست بشه.

If you overload ==, keep it consistent with Equals and GetHashCode; otherwise one call site sees “equal” while a Dictionary sees something else. Prefer language-generated equality for records or value-oriented types unless a special, fully tested contract is needed.

خوانایی محلی کافی نیستLocal readability is not enough

operator کوتاه ممکنه کنار call site زیبا باشه اما معنایش برای کسی که نوع رو نمی‌شناسد پنهان بماند. API عمومی باید رفتار و exceptionها رو مستند کند و تست برابری/hash رو باهم داشته باشه.

A short operator may look elegant at one call site while hiding meaning from someone unfamiliar with the type. A public API should document behaviour and exceptions and test equality and hashing together.

implicit، explicit و checked رو از دست‌رفتن اطلاعات تعیین می‌کنهInformation loss should drive implicit, explicit and checked conversions

تبدیل narrowing ممکنه بخشی از مقدار رو دور بیندازد. در C# تبدیل explicit این تصمیم رو در syntax آشکار می‌کنه؛ checked برای بعضی تبدیل‌های عددی و عملگرهای checked جلوی سرریز رو می‌گیره، اما هر تبدیل خطرناکی رو جادویی ایمن نمی‌کنه. رفتار نوع مقصد و نسخهٔ زبان رو جدا بررسی کن.

A narrowing conversion may discard information. In C#, explicit syntax makes that choice visible; checked protects against overflow for supported numeric conversions and checked operators, but it does not magically validate every dangerous conversion. Inspect the target type and language support separately.

در این تبدیل عددی، unchecked wrap نتیجهٔ قابل‌استفاده اما از دست‌رفته می‌ده؛ checked استثنا می‌ده. این تفاوت رو با parsing اشتباه نگیر: parse ممکنه format نامعتبر رو هم رد کند، در حالی که cast فقط تبدیل عددی انجام می‌ده.

For this numeric conversion, unchecked wraps to a lossy result while checked throws. Do not confuse this with parsing: parsing can reject invalid text format, while a cast performs a numeric conversion.

تبدیل user-defined باید یک‌جهته و قابل‌پیش‌بینی باشهA user-defined conversion should be one-way and predictable

تبدیل implicit سفارشی برای چیزی مناسب هست که همیشه امن، ارزان و بدون ابهام باشه؛ مثل wrapperی که دقیقاً همان مقدار رو نمایندگی می‌کنه. اگه ممکنه شکست بخورد یا معنای محصول انتخاب لازم داره، explicit یا factory method بهتره. تبدیل‌های زنجیره‌ای مبهم نساز.

A custom implicit conversion fits a value that is always safe, cheap and unambiguous, such as a wrapper representing exactly the same value. If it can fail or requires a product decision, explicit conversion or a factory method is clearer. Avoid ambiguous conversion chains.

تبدیل صریح قابل‌ردیابی / Explicit conversion
readonly record struct Percentage(decimal Value)
{
    public static explicit operator Percentage(decimal value)
    {
        if (value is < 0m or > 100m)
            throw new ArgumentOutOfRangeException(nameof(value));
        return new Percentage(value);
    }
}

var discount = (Percentage)15m;

cast در call site نشان می‌ده decimal قرار هست به یک مفهوم دامنه‌ای تبدیل بشه؛ validation هم مقادیر خارج از بازه رو می‌گیره. اگه مصرف‌کننده به توضیح خطا یا چند policy نیاز داره، static factory با نام روشن ممکنه بهتر باشه.

The cast makes the domain conversion visible, and validation rejects values outside the range. If callers need detailed errors or multiple policies, a clearly named static factory may be better.
