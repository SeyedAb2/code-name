variance در interfaceها

Variance in interfaces

تابعی که string می‌سازه برای جایی که object می‌خواد هم قابل‌استفاده به نظر می‌رسه؛ اما listای که string می‌پذیره رو نمی‌شه هرجا List

A producer of strings seems usable where objects are expected, but a list accepting strings cannot safely stand in for a List<object>. These different intuitions come from data direction. We will understand variance through safe substitutions, not memorised Greek terms.

تولیدکننده و مصرف‌کننده جهت مخالف دارنProducers and consumers face opposite directions

یک IEnumerable فقط string بیرون می‌ده. چون هر string یک object هست، مصرف‌کننده‌ای که object می‌خواد می‌تونه خروجی رو بخواند. اما اگه List رو به List

An IEnumerable<string> only produces strings. Since each string is an object, a consumer expecting objects can safely read them. But if we converted List<string> to List<object>, that consumer could insert a DateTime and corrupt the original string list.

تبدیل امن و ناامن / Safe and unsafe assignments
IEnumerable<string> names = new[] { "Mina", "Reza" };
IEnumerable<object> values = names; // safe: read-only producer

List<string> mutableNames = new() { "Mina" };
// List<object> mutableValues = mutableNames; // rejected: unsafe writes

IEnumerable خروجی می‌ده، پس T covariant هست. List هم می‌خونه و هم می‌نویسه، پس invariant می‌مونه؛ compiler نمی‌تونه اجازه دهد نوع گسترده‌تر مقداری ناسازگار بنویسد.

IEnumerable<out T> produces values, so T is covariant. List<T> both reads and writes, so it remains invariant; the compiler cannot permit a wider type to write incompatible values.

covariance: مقدار خاص‌تر رو به مصرف‌کنندهٔ عمومی‌تر بدهCovariance: give a more specific producer to a broader reader

در declaration، out روی پارامتر نوع می‌گه T فقط در موقعیت خروجی به کار می‌ره. این اجازه می‌ده رابطی که object بیرون می‌ده با رابطی که string بیرون می‌ده سازگار بشه؛ رابطهٔ ارث‌بری خود نوع‌هاست که تبدیل رو امن می‌کنه.

In a declaration, out says T is used only in output positions. This allows an interface producing objects to accept one producing strings; the types’ own inheritance relationship makes that conversion safe.

تولیدکنندهٔ covariant
interface ISource<out T>
{
    T Get();
}

sealed class StringSource : ISource<string>
{
    public string Get() => "hello";
}

ISource<string> strings = new StringSource();
ISource<object> objects = strings;
Console.WriteLine(objects.Get());

در زمان اجرا همان StringSource هست؛ فقط قرارداد مصرف‌کننده گسترده‌تر شده. out اجازه نمی‌ده متدی با ورودی T به interface اضافه کنیم، چون مصرف‌کنندهٔ ISource

At runtime it is still the same StringSource; only the consumer-facing contract is broader. out prevents adding a method that accepts T, because a consumer of ISource<object> could pass an arbitrary object that a string source cannot accept.

contravariance: مصرف‌کنندهٔ عمومی‌تر رو برای ورودی خاص‌تر به‌کار ببرContravariance: use a broader consumer for a more specific input

in روی T یعنی interface آن رو ورودی می‌گیره. عملیاتی که هر object رو می‌پذیره، می‌تونه string رو هم بپذیرد؛ پس مصرف‌کنندهٔ object در جای مصرف‌کنندهٔ string امن هست.

in means the interface consumes T as input. An operation accepting any object can also accept a string, so an object consumer is safe where a string consumer is needed.

مصرف‌کنندهٔ contravariant
interface IHandler<in T>
{
    void Handle(T item);
}

sealed class ObjectHandler : IHandler<object>
{
    public void Handle(object item) => Console.WriteLine(item);
}

IHandler<object> allObjects = new ObjectHandler();
IHandler<string> strings = allObjects;
strings.Handle("hello");

اگه جهت رو برعکس کنیم، handler مخصوص string رو به IHandler

Reversing the direction—using a string-only handler as IHandler<object>—would allow callers to pass numbers, so the compiler rejects it.

delegateها هم جهت ورودی و خروجی دارنDelegates also have input and output directions

Func آرگومان می‌گیره و نتیجه می‌ده؛ پس TArg در جهت ورودی و TResult در جهت خروجی هست. Action مصرف‌کننده هست. variance امضا رو جادویی عوض نمی‌کنه؛ فقط assignment امن بین generic interface/delegateها رو ممکن می‌کنه.

Func<TArg,TResult> accepts an argument and returns a result, so TArg is input and TResult is output. Action<T> is a consumer. Variance does not magically rewrite signatures; it permits safe assignments between generic interfaces/delegates.

ورودی و خروجی Func / Func input and output
Func<string> makeText = () => "done";
Func<object> makeObject = makeText;

Action<object> logAnything = value => Console.WriteLine(value);
Action<string> logText = logAnything;

Func رو می‌توان در Func

Func<string> can be used as Func<object> because a specific output flows to a broader output. Action<object> can be used as Action<string> because it accepts the broader input. For signatures with several parameters, trace each position independently.

variance کجا کار نمی‌کنه؟Where does variance not apply?

variance فقط روی generic interfaceها و delegateهایی کار می‌کنه که خودشان in/out رو اعلام کرده‌اند؛ generic class و struct از assignment variance پشتیبانی نمی‌کنن. تبدیل‌های variance به reference type arguments وابسته‌اند؛ مثلاً List تبدیل covariant به List

Variance applies only to generic interfaces and delegates that declare in/out; generic classes and structs do not support variant assignments. Variant conversions rely on reference-type arguments: List<int> does not become covariant List<object>, and value types do not substitute under this rule.

نوع قراردادContract shapeجهت TT direction
IEnumerable<out T>فقط تولیدcovariantOutput
IComparer<in T>فقط مصرفcontravariantInput
List<T>خواندن و نوشتنinvariantInput and output

اگه interface هم T رو برمی‌گردونه هم می‌پذیره، معمولاً invariant می‌مونه. دو interface کوچک‌تر با جهت‌های جدا گاهی بهترند؛ ولی فقط برای رفع یک assignment عجیب interfaceهای تازه نساز—مصرف‌کنندهٔ واقعی و عملیاتش رو ببین.

If an interface both returns and accepts T, it usually remains invariant. Two smaller interfaces with separate directions may fit, but do not invent interfaces merely to fix a puzzling assignment—inspect real consumers and operations.

از جهت مصرف و تولید تصمیم بگیرDecide from input and output direction

out برای تولیدکنندهٔ T و تبدیل به قرارداد عمومی‌تر؛ in برای مصرف‌کنندهٔ T و استفادهٔ مصرف‌کنندهٔ عمومی‌تر در جای خاص‌تر؛ هر دو جهت یعنی invariant. فقط interface و delegateهای variant پشتیبانی می‌شن و value typeها استثنای مهم‌اند. بعد از این، فصل بعد سراغ constraints پیشرفته‌تر یا طراحی genericهای دنیای واقعی می‌رویم؟ مسیر مصوب دوره رو دنبال می‌کنیم: الگوریتم‌های generic رو با collectionها و APIهای کاربردی می‌سنجیم.

out suits a producer of T and conversion to a broader contract; in suits a consumer of T and lets a broader consumer stand in for a narrower one; both directions mean invariance. Only variant interfaces and delegates support it, with value types as an important exception. Next we apply generic design to practical collection and API problems.

اگه کدهای این فصل رو خودت اجرا کردی و می‌تونی شکست نزدیکشون رو توضیح بدی، آماده‌ای بریم سراغ «ریاضی عمومی و static abstract». قرار نیست از صفر شروع کنیم؛ همین مدل رو با خودمون می‌بریم.

If you ran the examples yourself and can explain the nearby failure, you are ready for “Generic math and static abstract members”. We will not restart from zero; we will carry this model forward.
