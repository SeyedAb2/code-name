زمان، منطقه و تقویم

Time, time zones and calendars

کاربر می‌گه «سفارش ساعت ۲:۳۰ ثبت شده»، اما گزارش یک ساعت اختلاف داره. شاید ساعت سرور UTC هست، شاید منطقهٔ کاربر فرق داره، شاید ساعت محلی به‌خاطر تغییر ساعت تابستانی اصلاً وجود نداشته یا دوبار تکرار شده. قبل از جمع‌زدن تاریخ‌ها، باید بفهمیم دربارهٔ کدوم نوع زمان حرف می‌زنیم.

A user says an order was placed at 2:30, but a report is an hour off. The server may use UTC, the user may be in another zone, or daylight-saving rules may make that local time nonexistent or repeated. Before doing date arithmetic, identify which kind of time you have.

سه سؤال متفاوت رو یکی نکنDo not collapse three different questions

«الان چند هست؟» یک instant می‌خواد؛ «جلسه ساعت ۹ محلی است» ساعت دیواری و منطقه می‌خواد؛ «امروز در تقویم چه روزی هست؟» تقویم و فرهنگ می‌خواد. یک DateTime به‌تنهایی نمی‌گه این مقدار UTC هست یا محلی؛ property به نام Kind هم منطقهٔ زمانی رو نگه نمی‌داره. اگه چیزی رو به‌عنوان یک لحظه در جهان ثبت می‌کنی، معمولاً DateTimeOffset انتخاب روشن‌تری هست.

“What time is it now?” asks for an instant; “the meeting is at 9 local time” needs a wall clock and a zone; “what date is it today?” involves a calendar and culture. A DateTime value alone does not tell you whether it is UTC or local, and Kind does not store a time zone. For a point on the global timeline, DateTimeOffset is usually clearer.

ثبت یک instant / Record an instant
DateTimeOffset occurredAt = DateTimeOffset.UtcNow;
string wireValue = occurredAt.ToString("O");

DateTimeOffset received = DateTimeOffset.Parse(
    wireValue,
    CultureInfo.InvariantCulture,
    DateTimeStyles.RoundtripKind);

Console.WriteLine(received.UtcDateTime);

فرمت round-trip offset رو حفظ می‌کنه و parse با culture ثابت از تنظیم سیستم‌عامل مستقل می‌شه. بااین‌حال offset مثل +03:30، نام منطقه و قواعد تاریخی آن نیست؛ اگه می‌خوای «هر روز ساعت ۹ تهران» رو برای ماه‌های آینده برنامه‌ریزی کنی، فقط offset امروز کافی نیست.

The round-trip format preserves the offset, and invariant parsing avoids dependence on machine culture. But an offset such as +03:30 is not a zone identifier with its historical rules. To schedule “every day at 9 in Tehran” for future months, today’s offset alone is insufficient.

instant، زمان محلی و تاریخِ بدون ساعتInstants, local times and dates without a clock

برای زمان وقوع رویداد، instant رو UTC ذخیره کن و هنگام نمایش به منطقهٔ مخاطب تبدیل کن. برای قرار آینده، معمولاً ساعت محلی به‌همراه شناسهٔ منطقه ذخیره می‌شه؛ تبدیل نهایی به instant نزدیک زمان اجرا انجام می‌گیره چون قواعد منطقه عوض می‌شن. برای تولد یا سررسید روزانه که ساعت مهم نیست، DateOnly گویاتر از نیمه‌شب ساختگی هست؛ مدت زمان هم TimeSpan هست، نه تاریخ.

Store event instants in UTC and convert for the viewer. A future appointment is often stored as local wall time plus a zone identifier, then resolved near execution because zone rules can change. For a birthday or all-day due date, DateOnly is clearer than a fake midnight; a duration is a TimeSpan, not a date.

تبدیل برای نمایش / Convert for display
DateTimeOffset instant = DateTimeOffset.UtcNow;
TimeZoneInfo zone = TimeZoneInfo.FindSystemTimeZoneById(zoneId);
DateTimeOffset local = TimeZoneInfo.ConvertTime(instant, zone);

Console.WriteLine(local.ToString("yyyy-MM-dd HH:mm zzz",
    CultureInfo.InvariantCulture));

DateOnly dueDate = new(2026, 10, 4);

شناسه‌های منطقه در سیستم‌عامل‌ها ممکنه نام‌گذاری متفاوتی داشته باشن؛ FindSystemTimeZoneById باید در محیط‌های پشتیبانی‌شده تست بشه، نه این‌که یک شناسهٔ ویندوزی رو همه‌جا hardcode کنیم. در نسخه‌های جدید .NET نگاشت‌های متداول پشتیبانی می‌شن، اما image/container و دادهٔ timezone نصب‌شده هم در نتیجه اثر دارن.

Time-zone identifiers can differ across operating systems. Test FindSystemTimeZoneById on supported environments rather than hardcoding a Windows identifier everywhere. Recent .NET versions support common mappings, but the container image and installed time-zone data still matter.

DST ساعت رو جلو می‌بره، اما زمان واقعی رو نهDST changes wall clocks, not elapsed reality

در شروع تغییر ساعت، بعضی ساعت‌های محلی جا می‌افتند؛ آن ساعت نامعتبر هست. هنگام برگشت، یک ساعت دوبار دیده می‌شه؛ آن ساعت مبهم هست و به دو instant می‌تونه اشاره کند. پس «به‌علاوهٔ یک روز» برای برنامهٔ تقویمی با «به‌علاوهٔ ۲۴ ساعت» یکی نیست. برای رزرو آینده، ambiguity رو با قانون محصول حل کن: انتخاب کاربر، offset مشخص یا سیاست رسمی—نه انتخاب تصادفی runtime.

When clocks move forward, some local times never occur; they are invalid. When clocks move back, an hour occurs twice; it is ambiguous and maps to two instants. Therefore, “add one calendar day” is not the same as “add 24 hours.” For future bookings, resolve ambiguity through a product rule—user choice, explicit offset or documented policy—not an accidental runtime choice.

بررسی زمان محلی / Inspect a local wall time
DateTime wallTime = new(2026, 11, 1, 1, 30, 0,
    DateTimeKind.Unspecified);

if (zone.IsInvalidTime(wallTime))
    throw new InvalidOperationException("This local time does not exist.");

if (zone.IsAmbiguousTime(wallTime))
{
    TimeSpan[] possibleOffsets = zone.GetAmbiguousTimeOffsets(wallTime);
    // Apply an explicit product policy or ask the user to choose.
}

تاریخ نمونه فقط وقتی transition رو نشان می‌ده که منطقه و قواعد همان سال با آن منطبق باشن؛ برای تست قابل‌حمل، منطقهٔ آزمایشی و تاریخ transition رو از دادهٔ واقعی همان سیستم بگیر یا fake zone بساز. خود زمان محلی رو با DateTimeKind.Unspecified نگه دار تا به‌طور ضمنی local machine تلقی نشه.

The sample date demonstrates a transition only when the chosen zone has matching rules for that year. For portable tests, obtain transition dates from the zone’s actual rules or construct a test zone. Keep a wall-clock value as DateTimeKind.Unspecified so it is not implicitly treated as the machine’s local time.

تقویم نمایشی، instant ذخیره‌شده رو عوض نمی‌کنهA display calendar does not change the stored instant

ممکنه محصول تاریخ رو هجری شمسی نشان دهد، ولی رویداد همچنان یک instant یا یک تاریخ قراردادی هست. تقویم تعیین می‌کنه اجزای سال/ماه/روز چطور تفسیر و نمایش بشن؛ culture روی قالب‌بندی هم اثر داره. culture سیستم رو برای ذخیرهٔ timestamp دخیل نکن. ورودی متنی رو با فرهنگ مورد انتظار parse کن و هنگام ساخت نام ماه یا اعداد، خروجی رو آگاهانه قالب‌بندی کن.

A product may display a date in the Persian calendar while the event remains an instant or a domain date. A calendar governs year/month/day interpretation and display; culture also affects formatting. Do not let machine culture determine stored timestamps. Parse text with the intended culture and format month names or digits deliberately.

تقویم و culture جدا هستند / Calendar and culture are distinct
var persian = new PersianCalendar();
DateTime date = new(2026, 3, 21);
int year = persian.GetYear(date);
int month = persian.GetMonth(date);
int day = persian.GetDayOfMonth(date);

var culture = CultureInfo.GetCultureInfo("fa-IR");
string display = date.ToString("D", culture);

قواعد تقویم و فرهنگ display رو با نیاز محصول انتخاب کن؛ فرمت «D» یک قرارداد ذخیره‌سازی نیست. اگه تاریخ شمسی وارد می‌کنی، تبدیل رفت‌وبرگشت و روزهای مرزی سال رو تست کن و معلوم کن مدل دامنه Gregorian DateOnly هست یا صریحاً سال/ماه/روز در تقویم دیگر.

Choose calendar and display culture according to product needs; the “D” format is not a storage contract. If users enter Persian dates, test round trips and year boundaries, and decide whether the domain stores a Gregorian DateOnly or explicit year/month/day in another calendar.

ساعت سیستم رو مستقیم به منطق گره نزنDo not couple business logic to the system clock

کدی که داخل هر متد DateTime.UtcNow می‌خونه، در تست به سختی می‌تونه انقضا یا مرز نیمه‌شب رو بازتولید کند. در .NET 8 به بعد TimeProvider وابستگی ساعت و timer رو قابل تزریق می‌کنه؛ در تست، بستهٔ Microsoft.Extensions.TimeProvider.Testing و FakeTimeProvider زمان رو جلو می‌برن بی‌آن‌که تست واقعاً منتظر بماند.

Code that reads DateTime.UtcNow inside every method is hard to test around expiry or midnight. In .NET 8 and later, TimeProvider makes clock and timer dependencies injectable. In tests, Microsoft.Extensions.TimeProvider.Testing and FakeTimeProvider advance time without waiting in real time.

زمان قابل‌آزمون / Testable clock
public sealed class ExpiringTokenService(TimeProvider timeProvider)
{
    public DateTimeOffset CreateExpiry(TimeSpan lifetime) =>
        timeProvider.GetUtcNow().Add(lifetime);
}

// Test: inject FakeTimeProvider, advance it, assert expiry.

در منطق elapsed time و timeout، clock یکنواخت مثل Stopwatch فرق داره: ساعت دیواری ممکنه با همگام‌سازی سیستم جابه‌جا بشه. timestampهای performance رو با wall clock مقایسه نکن. اگه timer هم می‌سازی، عمر و Dispose آن رو در تست و برنامه مشخص کن.

For elapsed time and timeouts, a monotonic clock such as Stopwatch differs from a wall clock, which can jump when the system synchronizes. Do not compare performance timestamps with wall-clock values. If you create timers, define their lifetime and disposal in both tests and production.
