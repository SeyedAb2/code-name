پروژهٔ ۲ — کتابخانهٔ قابل انتشار

Project 2 — a publishable library

تیم‌های چندگانه فرمت‌های مختلفی از مقدار و کلید دارن و هرکدوم mapping خودشان رو نوشته‌اند. مأموریت تو یک library کوچک برای انتخاب و ترکیب policyهاست؛ package باید API عمومی محدود، nullable روشن، تست مصرف‌کننده و release version داشته باشه. مهم‌ترین خروجی NuGet نیست؛ قراردادی هست که مصرف‌کننده بتواند به آن تکیه کند و تو بتوانی بدون شکستن ناخواسته تغییرش بدهی.

Several teams have different key and value formats, each with its own mapping code. Build a small library for selecting and composing policies. It needs a narrow public API, explicit nullability, consumer tests and versioned releases. The most important output is not the NuGet file; it is a contract consumers can rely on and you can evolve without accidental breaks.

مأموریت: یک API کوچک، نه یک framework تازهMission: a small API, not a new framework

کتابخانهٔ «Keyed Pipeline» باید چند منبع دادهٔ typed رو بر اساس key انتخاب کند و policyهای transformation رو ترکیب کند. می‌تونی مسئلهٔ دقیق‌تری انتخاب کنی—مثلاً formatter، validation pipeline یا collection helper—اما API باید generic معنی‌دار داشته باشه، nullability رو دقیق کند و behavior با تست مشخص بشه. قابلیت‌های زیاد و extension pointهای مبهم تحویل رو بهتر نمی‌کنن.

The “Keyed Pipeline” library selects typed data sources by key and composes transformation policies. You may choose a more precise domain—such as a formatter, validation pipeline or collection helper—but the API must use meaningful generics, express nullability accurately and define behavior through tests. More features and vague extension points do not improve the delivery.

محدوده: package رو روی feed محلی یا artifact پوشه‌ای بساز؛ بدون credential واقعی و بدون انتشار عمومی. مقصد package رو در gitignore نگه دار، مگر اینکه artifact پروژه عمداً تحویل باشه.

Scope: pack to a local feed or artifact folder; use no real credentials and do not publish publicly. Ignore the local package destination unless the artifact is explicitly part of delivery.

مصرف‌کننده باید بدون دانستن implementation بتواند استفاده کندConsumers should use the library without knowing its implementation

  • API عمومی کوچک، نام‌گذاری‌شده و با nullable annotations فعال باشه.
  • The public API is small, named clearly and built with nullable annotations enabled.
  • generic constraintها فقط وقتی وجود دارن که contract به آن‌ها نیاز داره.
  • Generic constraints exist only when required by the contract.
  • ورودی null، key تکراری، comparer و ترتیب enumeration رفتار تعریف‌شده دارن.
  • Null inputs, duplicate keys, comparers and enumeration order have defined behavior.
  • unit test و یک consumer مستقل از package ساخته‌شده تست می‌شن.
  • Unit tests and an independent consumer of the packed package both pass.
  • package metadata، README، license مجاز، version و target framework روشن هست.
  • Package metadata, README, authorized license, version and target framework are explicit.
  • benchmark فقط برای یک ادعای performance مشخص و قابل‌سنجش اضافه می‌شه.
  • A benchmark is included only for a specific measurable performance claim.

مراحل ساخت و انتشارBuild and release milestones

  1. قرارداد: یک صفحهٔ design بنویس که مسئله، non-goals، null semantics و duplicate-key policy رو مشخص کند.
  2. Contract: write a one-page design with problem, non-goals, null semantics and duplicate-key policy.
  3. API sketch: public interface و نمونهٔ مصرف رو قبل از implementation بنویس؛ از یک consumer فرضی feedback بگیر.
  4. API sketch: define public interfaces and a sample consumer before implementation; review with a hypothetical consumer.
  5. رفتار: حداقل implementation رو بساز و edge caseها رو با xUnit قفل کن.
  6. Behavior: build the smallest implementation and pin edge cases with xUnit.
  7. سازگاری: nullable warnings رو حل کن و analyzerهای مناسب رو فعال کن؛ warning رو کور خاموش نکن.
  8. Compatibility: resolve nullable warnings and enable suitable analyzers; do not silence warnings blindly.
  9. مصرف package: pack رو به local feed بده و consumer مستقل رو فقط با PackageReference به آن وصل کن.
  10. Package consumer: pack to a local feed and connect an independent consumer using PackageReference only.
  11. اندازه‌گیری: یک benchmark claim مثل هزینهٔ comparer یا allocation رو بسنج؛ اگه سؤال performance نداری benchmark اضافه نکن.
  12. Measurement: benchmark one claim such as comparer cost or allocation; add none if there is no performance question.
  13. Release: نسخه، changelog، breaking-change note و restore از clean checkout رو تکمیل کن.
  14. Release: finalize version, changelog, breaking-change note and clean-checkout restore.

قبولی با دو نگاه: نویسنده و مصرف‌کنندهAcceptance from both author and consumer perspectives

  • فقط API لازم public هست؛ implementation detail با public classهای بی‌دلیل نشت نمی‌کنه.
  • Only required APIs are public; implementation details are not exposed accidentally.
  • consumer مستقل با target framework اعلام‌شده build و test می‌شه.
  • An independent consumer builds and tests against the declared target framework.
  • null، duplicate key، comparer و exception contract برای public API آزموده شده‌اند.
  • Nulls, duplicate keys, comparer and exception contracts are tested.
  • package محلی محتویات درست و dependencyهای مستقیم درست داره.
  • The local package contains the expected files and direct dependencies.
  • یک Release قابل بازتولید با نسخه یکتا ساخته شده؛ package منتشرشده overwrite نمی‌شه.
  • A reproducible Release uses a unique version; published packages are not overwritten.
  • README نصب و یک نمونهٔ واقعی، limitationها و policy compatibility رو می‌گه.
  • The README explains installation, a real usage example, limitations and compatibility policy.

failure drillهای کتابخانهLibrary failure drills

  • nullable contract مبهم: consumer مقدار null می‌ده؛ رفتار رو تعریف و test کن، نه اینکه NRE تصادفی تحویل دهی.
  • Ambiguous nullable contract: a consumer passes null; define and test behavior instead of leaking an accidental NRE.
  • breaking API: یک public overload رو حذف کن، consumer قبلی رو build کن و اثر رو ثبت کن؛ سپس source compatibility رو برگردان یا major migration مستند بده.
  • Breaking API: remove a public overload, build the previous consumer and record impact; then restore source compatibility or document a major migration.
  • package قدیمی cache شده: consumer نسخهٔ اشتباه رو می‌گیره؛ source/feed/version و restore graph رو با evidence بررسی کن.
  • Stale package cached: the consumer resolves the wrong version; inspect source/feed/version and restore graph with evidence.
راهنما: مرز public API رو کوچک نگه دارHint: keep the public API boundary small

در شروع فقط یک factory/entry point و interfaceهای لازم رو public کن. اگه مصرف‌کننده برای استفاده باید internals رو بشناسد، مثال README رو اصلاح کن قبل از اینکه API بیشتری منتشر کنی.

Start with one entry point and only required interfaces. If a consumer must know internals, fix the README example before exposing more API.

بازبینی compatibility مثل بازبینی correctness استReview compatibility as carefully as correctness

public API پس از انتشار هزینهٔ تغییر پیدا می‌کنه. typeهای generic، nullable annotations، exceptionها و ordering behavior همگی contract هستن. آیا می‌تونی implementation رو عوض کنی بی‌آن‌که consumer رو بشکنی؟ آیا package به dependency غیرضروری وابسته شده؟ آیا docs نشان می‌دن چطور از API استفاده نکنند؟ نسخهٔ 1.0 رو زمانی بزن که این پرسش‌ها پاسخ روشن دارن، نه وقتی فایل `.nupkg` ساخته شد.

A public API becomes costly to change after release. Generic types, nullability, exceptions and ordering are all part of the contract. Can implementation change without breaking consumers? Does the package carry unnecessary dependencies? Do docs show misuse boundaries? Release 1.0 when these questions have clear answers—not merely when a .nupkg exists.

راهنمایی‌های مرحله‌ایStaged hints

راهنما ۱ — اول consumer بنویسHint 1 — write the consumer first

یک console کوچک در پروژهٔ جدا بساز و تجربهٔ استفاده رو قبل از شکل‌دادن library ببین.

Create a small separate console consumer and inspect the experience before shaping the library.

راهنما ۲ — generic برای تکرار واقعیHint 2 — use generics for real reuse

اگه دو type فقط نام متفاوت دارن ولی رفتار/contract مشترک ندارن، generic کردن شاید abstraction غلط باشه.

If two types only share a name pattern but not behavior or contract, a generic abstraction may be wrong.

راهنما ۳ — package محلی پیش از feed عمومیHint 3 — local package before public feed

یک local NuGet source در پوشهٔ موقت بساز و ابتدا consumer مستقل رو با همان package امتحان کن.

Create a temporary local NuGet source and test an independent consumer before using any public feed.

طرح مرجع در انتهای پروژهReference design at the end

پاسخ واحدی وجود نداره؛ تحویل قوی معمولاً این ساختار رو داره:

There is no single answer; a strong delivery commonly has this shape:

  1. src/KeyedPipeline با public API کم و implementation داخلی؛ public annotations و documentation file فعال.
  2. src/KeyedPipeline with a narrow public API, internal implementation, nullable annotations and XML documentation.
  3. tests/KeyedPipeline.Tests برای قرارداد و edge caseها؛ هیچ network/feed واقعی در unit test.
  4. tests/KeyedPipeline.Tests for contracts and edge cases; no real network/feed in unit tests.
  5. samples/Consumer یا project جدا که nupkg رو از local feed می‌گیره، نه ProjectReference.
  6. samples/Consumer as a separate project restoring the nupkg from a local feed, not ProjectReference.
  7. `dotnet pack -c Release` با PackageId، Description، license مجاز، RepositoryUrl و نسخهٔ یکتا؛ محتویات package رو inspect کن.
  8. Release pack with PackageId, description, authorized license, repository URL and unique version; inspect package contents.
  9. benchmark جدا و محدود فقط وقتی hypothesis مشخص هست؛ correctness رو با xUnit ثابت کن.
  10. A separate bounded benchmark only for a clear hypothesis; prove correctness with xUnit.
  11. README با quick start، semantics null/duplicate، compatibility promise، limitation و migration notes.
  12. README with quick start, null/duplicate semantics, compatibility promise, limitations and migration notes.

برای قبولی، دستورهای README رو از clone تمیز اجرا کن و package واقعی consumer رو compile کن. توضیح دربارهٔ package جای artifact و verification رو نمی‌گیره.

For acceptance, run README commands from a clean clone and compile a consumer against the actual package. Documentation does not replace the artifact and verification.

یک package کوچک با contract پایدار، محصول استA small package with a stable contract is a product

این پروژه نشان می‌ده API خوب فقط implementation تمیز نیست؛ مصرف‌کننده، نسخه و داستان سازگاری هم بخشی از کار هستن. پروژهٔ پایانی بعدی چند نخ و buffer رو کنار هم می‌ذاره: processor پُربازدهی می‌سازی که backpressure داره، cancellation رو رعایت می‌کنه و فقط با benchmark ادعای سرعت می‌کنه.

This project shows that a good API is more than a clean implementation; consumers, versions and compatibility are part of the work. The final project combines workers and buffers into a high-throughput processor with backpressure, cancellation and performance claims supported by benchmarks.
