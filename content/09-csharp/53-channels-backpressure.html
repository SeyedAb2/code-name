Channel و فشار برگشتی

Channels and backpressure

سامانهٔ import ده‌هزار رکورد در ثانیه می‌گیرد، اما ذخیره‌سازی فقط هزار رکورد می‌نویسد. صف داخل حافظه بزرگ می‌شود تا process از پا بیفتد. مشکل با «worker بیشتر» لزوماً حل نمی‌شود؛ producer باید بفهمد consumer جا ندارد. Channel محدود این مکالمه را ممکن می‌کند: صبر کن، رد کن یا طبق سیاست مشخص داده‌ای را دور بریز.

An importer receives 10,000 records per second while storage writes only 1,000. The in-memory queue grows until the process collapses. “More workers” is not necessarily the answer; producers need to know consumers are saturated. A bounded Channel makes that conversation possible: wait, reject or drop according to an explicit policy.

صف نامحدود فشار را پنهان می‌کندAn unbounded queue hides pressure

اگر producer سریع‌تر از consumer باشد، تعداد کارهای درحال‌انتظار رشد می‌کند؛ latency هم آرام‌آرام زیاد می‌شود تا memory تمام شود. queue نامحدود مشکل ظرفیت را حل نکرده، فقط هزینه‌اش را به آینده انداخته. باید مشخص کنیم هنگام پرشدن، تولیدکننده منتظر بماند، درخواست را رد کند یا داده‌ای را drop کند—و این تصمیم تابع معنای محصول است.

When producers outpace consumers, pending work grows; latency rises until memory is exhausted. An unbounded queue does not solve capacity—it postpones the cost. Decide whether producers wait, requests are rejected or items are dropped when full; the correct policy depends on product semantics.

Channel محدود با Wait فشار را به producer برمی‌گرداندA bounded Channel with Wait sends pressure upstream

Channel<T> کانال امن میان writer و reader است. با capacity محدود و BoundedChannelFullMode.Wait، WriteAsync وقتی پر است تا جا بازشدن await می‌کند؛ producer نمی‌تواند با سرعت نامحدود جلو برود. queue ظرفیت دارد، اما اگر تعداد producerهای معطل یا درخواست‌های ورودی هم نامحدود باشد، فشار هنوز در جای دیگری انباشته می‌شود؛ ورودی را هم محدود کن.

Channel<T> is a safe conduit between writers and readers. With bounded capacity and BoundedChannelFullMode.Wait, WriteAsync awaits space when full, so producers cannot outrun consumers indefinitely. The queue is bounded, but unbounded waiting producers or inbound requests can still accumulate pressure elsewhere; bound admission too.

Channel محدود / Bounded Channel
var channel = Channel.CreateBounded<WorkItem>(
    new BoundedChannelOptions(128)
    {
        FullMode = BoundedChannelFullMode.Wait,
        SingleReader = true,
        SingleWriter = false
    });

await channel.Writer.WriteAsync(item, cancellationToken);

SingleReader/SingleWriter فقط وقتی true هستند که contract واقعاً همین را تضمین کند؛ در غیر این صورت correctness یا optimization آسیب می‌بیند. capacity ۱۲۸ نمونه است، نه نسخهٔ همهٔ سرویس‌ها؛ اندازهٔ item، زمان مصرف و latency هدف را بسنج.

Set SingleReader/SingleWriter to true only when the contract guarantees it; otherwise correctness or optimization may suffer. Capacity 128 is illustrative, not universal; measure item size, processing time and latency goals.

Wait، DropNewest، DropOldest و DropWrite معنا دارندWait, DropNewest, DropOldest and DropWrite have semantics

برای telemetry لحظه‌ای شاید قدیمی‌ترین sample بی‌ارزش باشد؛ DropOldest می‌تواند منطقی باشد. برای سفارش یا پرداخت، drop یعنی از دست‌دادن کار و معمولاً انتخاب بدی است. DropWrite آیتم جدید را می‌اندازد، DropNewest آیتم جدیدترِ داخل queue را حذف می‌کند. حتماً شمارندهٔ dropped و رفتار producer را مستند کن؛ drop policy جای backpressure نیست اگر داده باید حفظ شود.

For live telemetry, an old sample may be worthless, making DropOldest reasonable. For orders or payments, dropping means lost work and is usually unacceptable. DropWrite discards the incoming item; DropNewest removes the newest queued item. Document producer behavior and count dropped items. A drop policy is not a substitute for backpressure when data must be retained.

پایان کانال، پایان producer استCompleting a channel signals producer completion

consumer باید بداند دیگر کاری نمی‌آید؛ writer با TryComplete کانال را تمام می‌کند. چند producer داشته باشی، هر producer نباید کانال را زود ببندد؛ یک مالک هماهنگ‌کننده پس از اتمام همه complete می‌کند. اگر producer با exception تمام شود، exception را به complete بده تا reader failure را ببیند. cancellation کانال و completion طبیعی دو حالت جدا هستند.

Consumers need to know when no more work will arrive; a writer completes the channel with TryComplete. With multiple producers, each must not close the channel prematurely—a coordinator completes after they all finish. Pass producer failures into completion so readers observe them. Cancellation and normal completion are distinct outcomes.

تکمیل و خواندن / Complete and drain
async Task ProduceAsync(ChannelWriter<WorkItem> writer, CancellationToken ct)
{
    try
    {
        await foreach (WorkItem item in ReadSourceAsync(ct))
            await writer.WriteAsync(item, ct);
        writer.TryComplete();
    }
    catch (Exception ex)
    {
        writer.TryComplete(ex);
        throw;
    }
}

await foreach (WorkItem item in channel.Reader.ReadAllAsync(ct))
    await ProcessAsync(item, ct);

اگر reader با cancellation بیرون بیاید، producer ممکن است هنوز منتظر WriteAsync باشد؛ همان token یا token هماهنگ‌شده را به دو طرف بده و در shutdown writer را complete/cancel کن. آیتم‌های باقی‌مانده را drain می‌کنی یا دور می‌ریزی؟ این تصمیم باید صریح باشد.

If a reader exits via cancellation, a producer may still be waiting in WriteAsync; propagate a coordinated token and complete/cancel the writer during shutdown. Will remaining items be drained or abandoned? Make that decision explicit.

چند reader ظرفیت را زیاد می‌کند، نه نامحدودMultiple readers increase capacity, not without limit

می‌توان چند worker از یک channel بخوانند. اگر کار مستقل است، throughput ممکن است بالا برود؛ اگر همه به DB یا یک lock می‌رسند، bottleneck فقط جابه‌جا می‌شود. تعداد worker، ظرفیت channel و حداکثر ورودی باید با هم تنظیم شوند. ترتیب خواندن channel FIFO است، اما پایان پردازش چند worker الزاماً به ترتیب ورودی نیست.

Several workers can read one channel. Throughput may improve for independent work, but if all workers hit one database or lock, the bottleneck merely moves. Tune worker count, channel capacity and maximum admission together. Reads are FIFO, but multiple workers do not guarantee completion order.

failure در worker باید به مالک pipeline برسدWorker failures must reach the pipeline owner

اگر یک consumer exception بدهد و Task رها شود، producer شاید همچنان کار تولید کند تا صف پر شود و آن‌جا گیر کند. همهٔ workerها را await کن، failure را به لغو linked تبدیل کن و خروجی partial را ثبت کن. از taskهای یتیم و shutdown بی‌نهایت دوری کن. Channel queue است، نه durable broker؛ با restart process، آیتم‌های حافظه‌ای از بین می‌روند.

If a consumer faults and its Task is abandoned, producers may keep producing until the queue fills and then stall. Await every worker, propagate critical failure through linked cancellation and record partial output. Avoid orphan tasks and infinite shutdown. A Channel is an in-memory queue, not a durable broker; process restart loses its items.

تمرین: ظرفیت و سیاست drop را مشخص کنExercises: define capacity and drop policy

۱) unbounded queue1) Unbounded queue

producer ده برابر consumer سرعت دارد؛ رشد حافظه را محدود و backpressure نشان بده.

A producer is ten times faster than its consumer; bound memory and demonstrate backpressure.

پاسخ فنیTechnical reasoning

Channel محدود با Wait بساز و زمان WriteAsync را هنگام پرشدن مشاهده کن.

Use a bounded Channel with Wait and observe WriteAsync when capacity is full.

۲) ظرفیت2) Capacity

اندازهٔ itemها متفاوت است؛ capacity را از روی تعداد تنها انتخاب نکن.

Items vary in size; choose capacity using more than item count.

پاسخ فنیTechnical reasoning

اندازهٔ payload، peak memory، مصرف‌کننده و latency هدف را اندازه بگیر و حد محافظه‌کارانه انتخاب کن.

Measure payload size, peak memory, consumer rate and latency goals; choose a conservative bound.

۳) TryWrite false3) TryWrite returns false

TryWrite شکست می‌خورد ولی producer item را رها می‌کند؛ رفتار ردشدن را مدیریت کن.

TryWrite fails but the producer discards the item; handle rejection correctly.

پاسخ فنیTechnical reasoning

برای Wait mode از WriteAsync استفاده یا failure را به retry/backpressure/response قابل‌مشاهده تبدیل کن.

Use WriteAsync in Wait mode or turn rejection into visible retry/backpressure/response behavior.

۴) DropOldest برای telemetry4) DropOldest for telemetry

داشبورد فقط تازه‌ترین نمونه‌ها را لازم دارد؛ سیاست drop و شمارش دادهٔ ازدست‌رفته را پیاده کن.

A dashboard needs only recent samples; implement a drop policy and count discarded data.

پاسخ فنیTechnical reasoning

DropOldest مناسب این semantics است؛ dropped metric و توضیح non-durable بودن را ارائه کن.

DropOldest fits these semantics; expose dropped metrics and non-durable behavior.

۵) Drop برای سفارش5) Dropping orders

سفارش را هنگام full کانال drop می‌کنند؛ data-loss را حذف کن.

Orders are dropped when the channel fills; prevent data loss.

پاسخ فنیTechnical reasoning

Wait و admission control یا durable queue انتخاب کن؛ سفارش را بی‌صدا حذف نکن.

Use Wait/admission control or a durable queue; never silently discard orders.

۶) complete زودهنگام6) Premature completion

اولین producer کانال را complete می‌کند و producer دوم خطا می‌گیرد؛ مالکیت completion را اصلاح کن.

The first producer completes the channel and the second fails; fix completion ownership.

پاسخ فنیTechnical reasoning

هماهنگ‌کننده پس از اتمام همهٔ producerها یک‌بار complete کند.

A coordinator completes once after all producers finish.

۷) exception کانال7) Channel completion error

producer fault می‌شود ولی reader فقط پایان طبیعی می‌بیند؛ exception را propagate کن.

A producer faults but the reader sees normal completion; propagate the error.

پاسخ فنیTechnical reasoning

به TryComplete(ex) بده و Task producer را نیز await کن.

Pass the exception to TryComplete(ex) and await the producer Task.

۸) shutdown consumer8) Consumer shutdown

reader لغو می‌شود اما producer پشت WriteAsync می‌ماند؛ shutdown دوطرفه بساز.

A reader is cancelled while a producer remains blocked in WriteAsync; coordinate shutdown.

پاسخ فنیTechnical reasoning

token هماهنگ‌شده را به read/write بده، writer را complete کن و producer/consumerها را await کن.

Share a coordinated token, complete the writer and await all producers and consumers.

۹) SingleReader اشتباه9) Incorrect SingleReader

دو worker فعال‌اند ولی SingleReader=true؛ declaration را با واقعیت هماهنگ کن.

Two workers read concurrently while SingleReader is true; align options with reality.

پاسخ فنیTechnical reasoning

SingleReader را false کن یا تضمین یک reader را در ساختار واقعی enforce کن.

Set SingleReader to false or enforce one reader in the actual design.

۱۰) FIFO با چند consumer10) FIFO with multiple consumers

ورودی به ترتیب خوانده می‌شود اما خروجی completion جابه‌جاست؛ contract ترتیب را تحلیل کن.

Inputs are read in order but completions differ; analyze the ordering contract.

پاسخ فنیTechnical reasoning

چند consumer زمان پایان را reorder می‌کنند؛ sequence number و reorder buffer یا یک reader لازم است.

Multiple consumers reorder completion; use sequence numbers/reorder buffering or one reader.

۱۱) worker بیش از حد11) Too many workers

افزایش workerها throughput را کم می‌کند چون همه DB pool را می‌گیرند؛ ظرفیت end-to-end را تنظیم کن.

More workers reduce throughput by exhausting the DB pool; tune end-to-end capacity.

پاسخ فنیTechnical reasoning

worker count را زیر ظرفیت downstream نگه دار و queue age/latency را اندازه بگیر.

Keep workers within downstream capacity and measure queue age and latency.

۱۲) exception یتیم worker12) Orphaned worker failure

worker fault می‌شود ولی producer همچنان می‌نویسد؛ Taskها و failure را به هم وصل کن.

A worker faults while producers keep writing; link tasks and failures.

پاسخ فنیTechnical reasoning

linked cancellation، complete با exception و await همهٔ taskها را هماهنگ کن.

Coordinate linked cancellation, exceptional completion and awaiting every task.

۱۳) backlog و age13) Backlog age

queue count ثابت ولی کارها دیر انجام می‌شوند؛ چه metricهایی برای pipeline لازم است؟

Queue count is stable while work is delayed; which pipeline metrics are needed?

پاسخ فنیTechnical reasoning

queue length به‌تنهایی کافی نیست؛ enqueue-to-start age، processing duration، drop/rejection و throughput را بسنج.

Queue length alone is insufficient; measure enqueue age, processing duration, drops/rejections and throughput.

۱۴) مصرف memory14) Memory consumption

capacity ۱۰۰ است اما payload هر item بزرگ و peak memory بالا است؛ bound را بازنگری کن.

Capacity is 100 but payloads are large and memory spikes; revisit the bound.

پاسخ فنیTechnical reasoning

capacity را بر اساس byte budget/اندازهٔ worst-case تنظیم و payload را کوچک یا reference را محدود کن.

Set capacity against a byte budget/worst-case size and reduce or constrain payloads.

۱۵) Channel durable نیست15) A Channel is not durable

process restart سفارش‌های queued را حذف می‌کند؛ boundary معماری را تشخیص بده.

A restart loses queued orders; identify the architectural boundary.

پاسخ فنیTechnical reasoning

Channel داخل حافظه است؛ برای durability از storage/broker پایدار و acknowledgement درست استفاده کن.

A Channel is in-memory; use durable storage/brokers and correct acknowledgement semantics for durability.

۱۶) incident producer سریع16) Fast-producer incident

memory و latency رشد کرده، DB محدود شده؛ report علت، backpressure، ظرفیت و verification بنویس.

Memory and latency rise while the DB is saturated; report cause, backpressure, capacity and verification.

پاسخ فنیTechnical reasoning

bounded channel و ورودی محدود، worker متناسب با DB، queue age و rejection metrics اضافه؛ بار کنترل‌شده را تکرار و memory/latency را verify کن.

Add a bounded channel and admission control, size workers to DB capacity, expose queue-age/rejection metrics, then repeat controlled load and verify memory/latency.

آزمایشگاه: pipeline با دو consumerLab: a pipeline with two consumers

یک producer محدود و دو consumer بساز؛ ظرفیت Channel را کوچک بگیر تا backpressure دیده شود. سرعت producer، پردازش consumer، latency، تعداد item فعال و peak memory را ثبت کن. حالت Wait را با DropOldest روی دادهٔ telemetry مقایسه کن، اما دادهٔ سفارش را drop نکن. consumer را عمداً fault و بعد cancellation را حین full queue اجرا کن؛ مطمئن شو همهٔ Taskها پایان می‌یابند، exception به مالک می‌رسد و هیچ producer معطل نمی‌ماند. shutdown طبیعی را با complete و drain کامل تست کن.

Build one bounded producer and two consumers with a small Channel capacity so backpressure is visible. Record production/consumption rates, latency, active items and peak memory. Compare Wait with DropOldest for telemetry, but never drop order data. Deliberately fault a consumer and cancel while the queue is full; verify every Task completes, failures reach the owner and no producer remains blocked. Test graceful completion and full draining.

  1. حالت full را با evidence زمان WriteAsync نشان بده.
  2. Prove the full state using WriteAsync timing evidence.
  3. تعداد dropped را در policy مربوطه assert کن.
  4. Assert dropped-item counts under the selected policy.
  5. shutdown را بدون task باقی‌مانده verify کن.
  6. Verify shutdown leaves no outstanding tasks.

backpressure ظرفیت را حذف نمی‌کند؛ آن را صادق می‌کندBackpressure does not remove limits; it makes them visible

Channel bounded حافظهٔ صف را کنترل می‌کند و در Wait mode سرعت producer را با consumer هماهنگ می‌سازد. drop mode فقط وقتی درست است که semantics حذف داده را بپذیرد. workerهای بیشتر نیز اگر downstream گلوگاه است مشکل را حل نمی‌کنند؛ فقط فشار را جابه‌جا می‌کنند. برای یک فرایند درون حافظه Channel مناسب است، اما اگر کار باید پس از crash بماند، durability از جنس دیگری است. فصل بعد سراغ Span و Memory می‌رویم تا هزینهٔ کپی و مالکیت buffer را ببینیم.

A bounded Channel controls queue memory and, in Wait mode, matches producer rate to consumer capacity. Drop modes are valid only when the data semantics permit loss. More workers do not fix a downstream bottleneck; they move pressure around. Channels suit in-process work, but crash durability requires a different mechanism.
