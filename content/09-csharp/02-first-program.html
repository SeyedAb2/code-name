اول یک برنامهٔ قابل تکرار بسازیمFirst, make a reproducible program

به‌جای چسباندن کد در یک فایل ناشناس، از SDK پروژهٔ معمولی بساز. پروژه می‌گه کدوم framework هدف هست و build چه فایل‌هایی رو باید بشناسد.

Instead of pasting code into an unknown file, use the SDK to create a regular project. The project declares its target framework and the files and settings the build understands.

terminal
dotnet new console --framework net10.0 --name OrderHello
cd OrderHello
dotnet run
representative output
Hello, World!

در قالب جدید، ممکنه `Program.cs` فقط یک دستور top-level داشته باشه و `Main` رو نبینی. این به معنی حذف نقطهٔ شروع نیست؛ compiler ساختار لازم رو تولید می‌کنه. فعلاً با `Console.WriteLine` خروجی بگیریم و از رفتار قابل مشاهده شروع کنیم.

A current template may show only a top-level statement in `Program.cs`, with no visible `Main`. The entry point has not disappeared; the compiler supplies the required structure. For now, use `Console.WriteLine` and start from observable behavior.

برنامهٔ اول قرار نیست فقط Hello World باشهThe first program should be more than Hello World

اگه اولین برنامه فقط یک متن ثابت چاپ کنه، خیلی چیزها رو نمی‌بینیم. ورودی، خروجی، exit code و خطا چهار تا مرز واقعی برنامه‌ان. برای همین همین پروژهٔ کوچیک رو کمی جدی‌تر می‌کنیم: از command line داده می‌گیره، برای ورودی بد تصمیم مشخص داره و می‌تونه به shell بگه کار موفق بوده یا نه. هنوز ساده‌ست، ولی دیگه اسباب‌بازی نیست.

If the first program only prints a fixed string, we learn very little about real program boundaries. Input, output, exit codes, and failures are all observable contracts, so we make this tiny program slightly more serious: it accepts command-line data, has a deliberate policy for invalid input, and tells the shell whether the run succeeded. It is still small, but it is no longer a toy.

هر بار که کد رو تغییر می‌دی دو سؤال جدا داشته باش: «آیا build شد؟» و «آیا همون‌طور که انتظار داشتم اجرا شد؟» این دوتا رو قاطی کنی، خطای compiler رو با stack trace می‌گردی یا exception زمان اجرا رو با پاک‌کردن bin/obj درمان می‌کنی. از همین فصل عادت می‌کنیم failure رو اول در مرحلهٔ درست قرار بدیم.

Every code change should answer two different questions: “Did it build?” and “Did it behave as expected when it ran?” Mixing those questions leads to searching for a compiler problem in a stack trace or trying to repair a runtime exception by deleting build folders. From this chapter onward, place every failure at the correct stage first.

برنامه رو تغییر بده؛ فقط فایل رو نگاه نکنChange the program; do not just inspect the file

`Program.cs` رو با این کد عوض کن. برنامه نام رو از آرگومان می‌گیره و اگه ورودی نداشته باشیم، مقدار پیش‌فرض داره.

Replace `Program.cs` with this code. The program reads a name from an argument and has a default when no input is supplied.

Program.cs
string name = args.Length > 0 ? args[0] : "دوست";
Console.WriteLine($"سلام، {name}!");

حالا دو شکل اجرا رو مقایسه کن:

Now compare two invocation forms:

terminal
dotnet run
dotnet run -- نگار

`--` به `dotnet run` می‌گه آرگومان‌های بعدش رو به برنامه بدهد، نه اینکه آن‌ها رو خودش تفسیر کند. خط دوم باید «سلام، نگار!» چاپ کند. اگه `args[0]` رو بی‌بررسی بخوانی، اجرای بدون آرگومان می‌تونه `IndexOutOfRangeException` بدهد؛ مقدار پیش‌فرض این مسیر رو امن می‌کنه.

`--` tells `dotnet run` to pass the remaining arguments to the application instead of interpreting them itself. The second command should print “Hello, Negar!”. Reading `args[0]` without checking can throw `IndexOutOfRangeException` when no argument is supplied; the default protects that path.

ورودی‌ها رشته‌اندArguments are strings

حتی اگه کاربر `42` وارد کند، `args[0]` متن هست. تبدیل و اعتبارسنجی رو در فصل نوع‌ها و بعدتر در پروژهٔ CLI دقیق‌تر انجام می‌دهیم؛ فعلاً این تفاوت رو با عدد و متن اشتباه نگیر.

Even when a user enters `42`, `args[0]` is text. We will handle conversion and validation in the types module and the CLI project; for now, do not confuse a string with a number.

دو جور شکست: قبل از اجرا و حین اجراTwo failures: before execution and during it

یک حرف رو در نام متغیر اشتباه کن و `dotnet build` بگیر. compiler خطا می‌ده و برنامه شروع نمی‌شه. بعد کد رو طوری عوض کن که `args[0]` رو بدون بررسی بخواند و بدون آرگومان اجرا کن؛ این بار compile موفق هست ولی runtime exception می‌ده.

Mistype a variable name and build. The compiler reports an error and the app never starts. Then read `args[0]` without checking and run with no arguments; this time compilation succeeds but the runtime throws.

به پیام شکست نگاه کن، اما فقط پیام رو حفظ نکن. سؤال تشخیصی این هست: آیا برنامه اصلاً به مرحلهٔ اجرا رسیده؟ این سؤال نیمی از مسیرهای بی‌ربط عیب‌یابی رو حذف می‌کنه.

Read the failure message, but do not merely memorize it. Ask: did execution start at all? That question eliminates many irrelevant debugging paths.

۲) با ورودی خالی crash نکن2) Do not crash on empty input

کد رو موقتاً به `args[0]` تغییر بده؛ بدون آرگومان اجرا کن و exception رو ببین. بعد guard یا مقدار پیش‌فرض رو برگردان و همان دستور رو دوباره اجرا کن.

Temporarily change the code to `args[0]`, run without arguments and observe the exception. Restore a guard or default, then repeat the same invocation.

معیار موفقیت: کد باید build یا run بشه و پیش‌بینی‌ات رو با خروجی یا خطای واقعی compiler/runtime مقایسه کنی.

راهنماییHint

Write your expected result in a comment before running. Any mismatch is the part worth investigating.

پاسخ و توضیحSolution and explanation

آرایهٔ خالی اندیس صفر نداره، پس دسترسی runtime exception می‌ده. `args.Length > 0` شرط دسترسی رو برقرار می‌کنه؛ اجرای دوباره باید بدون exception مقدار پیش‌فرض رو چاپ کند. این فقط نبودن آرگومان رو پوشش می‌ده، نه رشتهٔ خالی یا ورودی نامعتبر.

An empty array has no index zero, so access throws at run time. The length check guards the access; repeating the command should print the default without an exception. It does not handle an empty string or invalid input.

برای بستن تمرین، خروجی یا test result رو نگه دار و یک بار نسخهٔ قبل و بعد رو کنار هم ببین. هدف فقط سبزشدن کد نیست؛ باید معلوم باشه کدوم رفتار واقعاً عوض شده.

Finish by keeping the output or test result and comparing the before/after behaviour. The goal is not merely green code; make the changed behaviour explicit.

۳) خطای اسم رو تشخیص بده3) Diagnose a name error

`Console.WriteLine(greeting);` رو بنویس، درحالی‌که متغیرت `name` هست. build بگیر، خطای compiler رو ثبت کن و اصلاح کن. چرا stack trace برای این خطا نداری؟

Write `Console.WriteLine(greeting);` while the variable is named `name`. Build, record the compiler diagnostic and fix it. Why is there no stack trace?

معیار موفقیت: کد باید build یا run بشه و پیش‌بینی‌ات رو با خروجی یا خطای واقعی compiler/runtime مقایسه کنی.

راهنماییHint

If it fails, first classify the failure as compile-time or runtime; only then repair it.

پاسخ و توضیحSolution and explanation

نام تعریف‌نشده خطای compile-time می‌ده و executable قابل اجرا ساخته نمی‌شه؛ پس exception زمان اجرا و stack trace هم نداریم. شناسه رو به `name` اصلاح کن و build رو تکرار کن.

An undefined name is a compile-time error, so no runnable program is produced; there is no run-time exception or stack trace. Correct the identifier and build again.

آخر کار یه بار از خودت بپرس این آزمایش دقیقاً چی رو ثابت کرد و چی رو نه. این عادت جلوی نتیجه‌گیری بزرگ از یه مثال کوچیک رو می‌گیره.

At the end, state exactly what this experiment proves and what it does not. That habit prevents broad conclusions from a tiny example.
