پردازش موازی با TPL

Parallel work with the TPL

گزارش حجیم باید زودتر ساخته شود. نسخهٔ جدید loop را با Parallel.ForEach عوض کرده؛ زمان بدتر شده و خروجی گاهی ترتیبش عوض است. موازی‌سازی رایگان نیست: partition، schedule، merge و synchronization هزینه دارند. اول کار را به قطعه‌های مستقل تبدیل می‌کنیم، بعد اندازه می‌گیریم که TPL از کار واقعی سریع‌تر هست یا نه.

A large report needs to finish sooner. A new version replaces a loop with Parallel.ForEach; it runs slower and sometimes changes result order. Parallelism is not free: partitioning, scheduling, merging and synchronization cost time. We first isolate independent work, then measure whether the TPL helps the real workload.

TPL برای کار CPU مستقل مناسب استThe TPL fits independent CPU work

هر رکورد را جدا normalize و score می‌کنی؟ اگر عملیات CPU-bound، مستقل و به‌اندازهٔ کافی سنگین است، Parallel.ForEach می‌تواند از چند core استفاده کند. اگر هر iteration شبکه را صدا می‌زند، بهتر است API async و concurrency محدود انتخاب کنی. اگر iterationها state مشترک یا ترتیب قطعی می‌خواهند، قبل از موازی‌سازی آن contract را حل کن.

If each record can be normalized and scored independently, and the CPU-bound work is large enough, Parallel.ForEach can use multiple cores. If each iteration calls a network API, prefer async APIs with bounded concurrency. If iterations require shared state or deterministic order, resolve that contract before parallelizing.

Parallel.For هزینهٔ scheduling هم داردParallel.For also pays scheduling costs

به TPL ورودی، سقف هم‌زمانی و cancellation می‌دهی. مقدار پیش‌فرض اغلب از processor count کمک می‌گیرد؛ اما I/O، quota container و workload واقعی را نمی‌شناسد. عدد را با اندازه‌گیری تنظیم کن. اگر loop زود تمام می‌شود یا body خیلی سبک است، sequential ممکن است برنده باشد. اشتراک mutable state را هم با طراحی کاهش بده.

TPL receives input, a concurrency bound and cancellation. Defaults often consider processor count, but they do not know your I/O, container quota or workload. Tune using measurements. If iterations are tiny or the loop finishes quickly, sequential code may win. Reduce shared mutable state through design.

ParallelOptions / cancellation and bounds
var options = new ParallelOptions
{
    MaxDegreeOfParallelism = Math.Max(1, Environment.ProcessorCount - 1),
    CancellationToken = cancellationToken
};

Parallel.ForEach(records, options, record =>
{
    cancellationToken.ThrowIfCancellationRequested();
    ProcessCpuBound(record);
});

processor count فقط نقطهٔ شروع است؛ اگر container محدودیت CPU دارد، رفتار runtime و تنظیمات محیط را بررسی کن. token باید به کار درون body برسد؛ عملیات synchronous را نمی‌توان با token به‌زور قطع کرد. TPL هنگام cancellation exception مناسب می‌دهد و caller باید آن را مدیریت کند.

Processor count is only a starting point; inspect runtime/environment behavior when a container has CPU limits. Pass the token into work inside the body; cancellation cannot forcibly stop synchronous code. The TPL reports cancellation through its exception path, which the caller must handle.

state محلی را جمع کن، نه این‌که همه lock بگیرندAggregate local state instead of locking every iteration

اگر هر worker هر رکورد را در یک List مشترک Add کند، lock و contention سود parallelism را می‌خورند. برای aggregateها از overloadهای partition-local استفاده کن یا خروجی مستقل را concurrent collection بگیر؛ در پایان merge را واضح انجام بده. حواست باشد thread-local با partition-local یکی نیست و delegate ممکن است چند بار برای partitionها ساخته شود.

If every worker locks a shared List for each record, contention can erase parallel gains. Use partition-local aggregation overloads or a concurrent collection for independent output, then merge explicitly. Thread-local and partition-local are not identical; local-state delegates may be created for multiple partitions.

شمارش محلی و merge / Local counts and merge
long total = 0;
Parallel.ForEach(
    partitions,
    () => 0L,
    (partition, _, local) => local + CountMatches(partition),
    local => Interlocked.Add(ref total, local));

قفل فقط یک بار به‌ازای local نتیجهٔ partition گرفته می‌شود، نه هر رکورد. هنوز باید overflow و معنای CountMatches را بررسی کنی. برای sum سادهٔ داده، PLINQ Sum یا aggregate اختصاصی می‌تواند همین کار را خواناتر انجام دهد.

Synchronization happens once per partition result rather than per record. Still validate overflow and CountMatches semantics. For a simple sum, PLINQ’s Sum or an appropriate aggregate may express the intent more clearly.

PLINQ ترتیب را پیش‌فرض حفظ نمی‌کندPLINQ does not preserve order by default

AsParallel() LINQ-to-Objects را به query موازی تبدیل می‌کند. نتیجه‌ها ممکن است به ترتیب completion بیایند؛ اگر ترتیب source بخشی از قرارداد است از AsOrdered() استفاده کن و هزینهٔ merge را بپذیر. query کوچک یا delegate سبک غالباً کندتر می‌شود. side effect در Select/Where و فرض اجرای هم‌زمان iterationها، query را شکننده می‌کند.

AsParallel() turns a LINQ-to-Objects query into a parallel query. Results may arrive in completion order; use AsOrdered() only when source order is part of the contract, and accept the merge cost. Small queries or cheap delegates often run slower. Side effects in Select/Where and assumptions about iteration timing make queries fragile.

ترتیب فقط وقتی لازم است / Preserve order only when needed
var scores = records
    .AsParallel()
    .AsOrdered()
    .Where(IsEligible)
    .Select(Score);

int[] result = scores.ToArray(); // materialization executes query

query تا materialize شدن ممکن است اجرا نشود؛ هر بار enumerate کردن می‌تواند دوباره کار کند. AsOrdered تضمین می‌کند ترتیب خروجی مطابق source باشد، نه این‌که bodyها به همان ترتیب اجرا شوند. اگر نتیجهٔ aggregate است، ترتیب شاید لازم نباشد و هزینهٔ اضافی حذف شود.

The query may not run until materialized; enumerating it again can repeat work. AsOrdered preserves output order, not execution order of the bodies. For aggregates, order may be unnecessary and its cost can be avoided.

async I/O را با Parallel.For اشتباه نگیرDo not confuse async I/O with Parallel.For

برای چند endpoint async، Parallel.ForEach مناسب نیست چون body آن synchronous است. Parallel.ForEachAsync برای async delegate و حداکثر degree دارد؛ cancellation را هم می‌گیرد. اما همچنان مقصد rate limit دارد و degree پیش‌فرض/انتخابی باید با ظرفیت و latency سنجیده شود. برای streamهای بسیار بزرگ، تولید کار و backpressure را هم محدود کن.

For multiple asynchronous endpoints, synchronous Parallel.ForEach is the wrong tool. Parallel.ForEachAsync accepts an asynchronous delegate and a maximum degree, with cancellation support. The downstream service still has rate limits, so choose the degree against capacity and latency. For very large streams, also bound work production and backpressure.

I/O موازی محدود / Bounded async I/O
await Parallel.ForEachAsync(
    ids,
    new ParallelOptions
    {
        MaxDegreeOfParallelism = 6,
        CancellationToken = cancellationToken
    },
    async (id, ct) =>
    {
        var item = await client.GetAsync(id, ct);
        await SaveAsync(item, ct);
    });

این API برای concurrency async است؛ تضمین نمی‌کند شش thread ثابت یا شش درخواست در همهٔ لحظه‌ها وجود دارد. اگر هر iteration state مشترک می‌نویسد، thread-safe collection یا partitioning لازم است. شکست یک iteration هم باید با policy exception/cancellation هماهنگ شود.

This API coordinates asynchronous concurrency; it does not guarantee six fixed threads or exactly six requests at every instant. Shared writes still need safe collections or partitioning. Define how iteration failures and cancellation should interact.

سرعت را با baseline و هزینه‌ها بسنجMeasure speed against a baseline and overhead

baseline ترتیبی را حفظ کن و ورودی/خروجی دو نسخه یکسان باشد. warmup، JIT، نویز ماشین، allocation و contention را در نظر بگیر. برای parallel، زمان کل به‌تنهایی کافی نیست: peak memory، CPU usage، latency tail و فشار مقصد هم مهم‌اند. اگر سرعت فقط در fixture مصنوعی بهتر شده، deployment واقعی هنوز اثبات نشده.

Keep a sequential baseline and identical input/output. Account for warmup, JIT, machine noise, allocations and contention. For parallel work, total time is not enough: measure peak memory, CPU, tail latency and downstream pressure. A win on a synthetic fixture does not prove a production improvement.

صد عدد کوچک را با Parallel.For پردازش کن و با حلقهٔ ساده benchmark بگیر.

Process one hundred tiny values with Parallel.For and benchmark a simple loop.

هزینهٔ scheduling از محاسبه بیشتر می‌شود؛ نسخهٔ ترتیبی احتمالاً بهتر است اما اندازه‌گیری کن.

Scheduling can cost more than the work; sequential may win, but measure.

۲) CPU-heavy مستقل2) Independent CPU-heavy work

رکوردهای مستقل را score کن و سقف parallelism را با دادهٔ بزرگ/کوچک بسنج.

Score independent records and measure parallelism bounds on small and large data.

پاسخ فنیTechnical reasoning

بدنهٔ سنگین مستقل candidate مناسبی است؛ هر اندازه را جدا benchmark کن و correctness را assert کن.

Heavy independent work is a candidate; benchmark sizes separately and assert correctness.

۳) async network3) Async network work

Parallel.For داخلش GetAsync صدا می‌زند؛ آن را به API async و degree محدود تبدیل کن.

Parallel.For calls GetAsync; replace it with async coordination and a concurrency cap.

پاسخ فنیTechnical reasoning

از Parallel.ForEachAsync یا worker محدود استفاده و rate limit مقصد را رعایت کن.

Use Parallel.ForEachAsync or bounded workers and respect downstream limits.

۴) نتیجه بی‌ترتیب4) Out-of-order results

PLINQ ترتیب ردیف‌های گزارش را عوض می‌کند؛ نیاز واقعی ترتیب را تعیین و repair کن.

PLINQ changes report row order; establish whether order matters and fix it.

پاسخ فنیTechnical reasoning

اگر contract ترتیب source را می‌خواهد AsOrdered بگذار؛ وگرنه مرتب‌سازی نهایی یا بی‌نظمی را آگاهانه بپذیر.

Use AsOrdered when source order is contractual; otherwise sort afterward or deliberately accept unordered output.

۵) side effect در Select5) Side effects in Select

Select داخل query، متغیر مشترک را تغییر می‌دهد؛ query را pure و نتیجه را aggregation کن.

Select mutates shared state; make the query pure and aggregate its result.

پاسخ فنیTechnical reasoning

side effect را بیرون از query نگه دار؛ aggregateهای داخلی PLINQ یا خروجی immutable را مصرف کن.

Keep side effects out of the query and use PLINQ aggregation or immutable results.

۶) shared List6) Shared List

workerها به یک List اضافه می‌کنند؛ contention و correctness را برطرف کن.

Workers append to one List; fix correctness and contention.

پاسخ فنیTechnical reasoning

خروجی local و merge، یا ConcurrentBag/Queue را با ترتیب موردنیاز انتخاب کن.

Use local outputs and merge, or choose a concurrent collection matching ordering needs.

۷) cancellation7) Cancellation

parallel loop پس از cancel به کار ادامه می‌دهد؛ ParallelOptions و body را درست کن.

A parallel loop continues after cancellation; wire options and the body correctly.

پاسخ فنیTechnical reasoning

token را به ParallelOptions بده و عملیات داخلی را هم cooperative کن؛ cancellation را catch کن.

Pass the token through ParallelOptions and make inner work cooperative; handle cancellation.

۸) degree نامحدود8) Unbounded degree

API بیرونی 429 می‌دهد؛ concurrency را به‌جای retry storm محدود و اندازه‌گیری کن.

An external API returns 429; cap concurrency instead of creating a retry storm.

پاسخ فنیTechnical reasoning

degree را بر اساس ظرفیت و Retry-After محدود و رفتار را با load test کنترل‌شده بسنج.

Bound degree against capacity and Retry-After, then test with controlled load.

۹) merge overhead9) Merge overhead

AsOrdered زمان را دو برابر می‌کند؛ آیا ترتیب بخشی از contract است؟ تصمیم را تست کن.

AsOrdered doubles duration; determine whether order is contractual and test the choice.

پاسخ فنیTechnical reasoning

اگر ترتیب لازم نیست unordered را نگه دار؛ اگر هست هزینه را در benchmark و contract ثبت کن.

Keep unordered execution when order is unnecessary; otherwise document and measure the cost.

۱۰) exception چند worker10) Multiple worker failures

چند iteration fault می‌شوند؛ همهٔ failureها و cancellation را در گزارش observe کن.

Several iterations fault; observe all failures and cancellation outcomes.

پاسخ فنیTechnical reasoning

AggregateException/inner exceptions را بررسی و خطای واقعی را با index ورودی log کن؛ cancellation را fault عادی نکن.

Inspect AggregateException/inner exceptions and log input indices; distinguish cancellation from ordinary faults.

۱۱) ThreadLocal aggregation11) Thread-local aggregation

sum مشترک هر item lock می‌گیرد؛ overload local state را پیاده و correctness ثابت کن.

A shared sum locks on every item; use local state and prove correctness.

پاسخ فنیTechnical reasoning

partial sum محلی بساز و در مرحلهٔ نهایی merge کن؛ overflow را هم لحاظ کن.

Accumulate local partial sums and merge at the end; account for overflow.

۱۲) TPL روی UI12) TPL on a UI thread

Parallel.For از UI thread اجرا و رابط را freeze می‌کند؛ اجرای محاسبه را درست جابه‌جا کن.

Parallel.For runs on the UI thread and freezes it; move computation appropriately.

پاسخ فنیTechnical reasoning

محاسبهٔ CPU را از UI جدا و نتیجه را روی dispatcher نمایش بده؛ خود موازی‌سازی جای responsiveness نیست.

Move CPU work off the UI thread and marshal results back; parallelism alone does not guarantee responsiveness.

۱۳) PLINQ کوچک13) Small PLINQ query

برای ده عنصر AsParallel کندتر است؛ علت و threshold را اندازه بگیر.

AsParallel is slower on ten items; explain and measure the threshold.

پاسخ فنیTechnical reasoning

partition و merge هزینه دارند؛ روی اندازه و هزینهٔ body نماینده benchmark بگیر.

Partitioning and merging cost time; benchmark representative sizes and delegate costs.

۱۴) container CPU limit14) Container CPU limit

degree را با host processor count تنظیم کرده‌اند اما container سهم کوچکی دارد؛ تنظیم را بررسی کن.

Degree uses host processor count although the container has a small CPU quota; investigate.

پاسخ فنیTechnical reasoning

runtime و quota محیط را verify کن؛ مقدار را با load test در deployment واقعی تنظیم کن نه با host حدسی.

Verify runtime/container quota behavior and tune via load tests in the real deployment.

۱۵) nested parallel loops15) Nested parallel loops

هر درخواست outer loop و inner loop موازی دارد؛ oversubscription را پیدا و فقط یک لایه را موازی کن.

Both outer and inner loops parallelize; detect oversubscription and choose one layer.

پاسخ فنیTechnical reasoning

nested scheduling و contention می‌تواند throughput را کم کند؛ ownership موازی‌سازی را در یک لایه قرار بده.

Nested scheduling and contention can reduce throughput; assign parallelism to one layer.

۱۶) incident کندتر شدن report16) Slower parallel report incident

نسخهٔ موازی کندتر و نامرتب است؛ root cause و معیار rollback را evidence-based بنویس.

The parallel version is slower and unordered; document root cause and rollback criteria from evidence.

پاسخ فنیTechnical reasoning

baseline، هزینهٔ delegate/merge، contention و نیاز ordering را اندازه بگیر؛ اگر معیار latency و correctness پاس نیست، sequential را برگردان.

Measure baseline, delegate/merge cost, contention and ordering needs; revert to sequential if latency and correctness targets fail.

آزمایشگاه: گزارش‌ساز قابل‌مقایسهLab: a comparable report builder

یک گزارش‌ساز با دادهٔ ثابت و body CPU-bound بساز. baseline ترتیبی، Parallel.For با سقف‌های مختلف، PLINQ ordered/unordered را اجرا کن؛ برای هرکدام صحت count/checksum، زمان، allocation و peak memory را ثبت کن. نسخهٔ کوچک و بزرگ داده را بسنج. بعد یک عملیات I/O آزمایشی اضافه کن و آن را با Parallel.ForEachAsync و سقف کنترل‌شده جدا مقایسه کن. shared state را حذف یا local aggregation کن، cancellation و exception را تست و معیار انتخاب نهایی را در README ثبت کن.

Build a report processor over fixed data with CPU-bound work. Compare a sequential baseline, Parallel.For with several bounds, and ordered/unordered PLINQ; record count/checksum correctness, time, allocations and peak memory. Test small and large datasets. Add a controlled I/O operation and compare it separately with bounded Parallel.ForEachAsync. Remove shared state or use local aggregation, test cancellation/failure and document the decision in the README.

  1. ورودی، seed و خروجی را بین اجراها ثابت نگه دار.
  2. Keep input, seed and expected output identical across runs.
  3. برای ordering هزینه و دلیل را بنویس.
  4. Document the cost and need for ordering.
  5. هرگز سرعت را بدون correctness اعلام نکن.
  6. Never claim a speedup without correctness evidence.

Parallel را از روی profile انتخاب کن، نه از روی هیجانChoose parallelism from a profile, not excitement

TPL partition، schedule و state را از تو می‌گیرد ولی هزینه و پیچیدگی را حذف نمی‌کند. Parallel.For برای CPU مستقل، ForEachAsync برای I/O async محدود، و PLINQ برای queryهای مناسب است؛ ترتیب و shared state باید صریح بمانند. baseline ترتیبی، correctness و معیار واقعی latency شرط پذیرش‌اند. فصل بعد سراغ Channel می‌رویم تا producer و consumer با صف bounded و فشار برگشتی با هم کار کنند.

The TPL handles partitioning, scheduling and state coordination but does not eliminate their costs. Parallel.For suits independent CPU work, ForEachAsync bounded asynchronous I/O, and PLINQ suitable queries; ordering and shared state remain explicit. A sequential baseline, correctness and real latency targets are prerequisites. Next we connect producers and consumers with bounded Channels and backpressure.
