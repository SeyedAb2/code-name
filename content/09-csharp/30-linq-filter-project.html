LINQ: فیلتر و projection

LINQ: filtering and projection

گزارش می‌خواهد فقط سفارش‌های پرداخت‌شده را نشان بدهد و از هرکدام شماره و مبلغ را بیرون بکشد. اگر وسط کار همه‌چیز را با حلقه و List دستی بنویسیم، خواندن شرط‌ها سخت می‌شود. LINQ را با سؤال گزارش شروع می‌کنیم: کدام ردیف بماند و چه شکلی از آن بسازیم؟

A report needs paid orders and only their IDs and totals. Hand-written loops and temporary lists can obscure the selection rule. We start LINQ from the report question: which rows remain, and what shape should each become?

Where انتخاب می‌کندWhere filters

Where predicate برای هر عنصر تصمیم می‌گیرد نگه داشته شود یا نه. خودش عنصر را تبدیل نمی‌کند و معمولاً اجرای آن deferred است؛ پس خطای predicate ممکن است موقع enumeration رخ دهد، نه هنگام نوشتن query.

The Where predicate decides whether each item remains. It does not transform items and is generally deferred, so predicate failures may occur during enumeration rather than query construction.

نمونه / Example
var report = orders
    .Where(order => order.Status == OrderStatus.Paid)
    .Select(order => new { order.Id, order.Total });

foreach (var row in report)
    Console.WriteLine($"{row.Id}: {row.Total:C}");

خروجی نماینده: A-104: $25.00. این مشاهده اجرای منبع را نشان می‌دهد؛ دربارهٔ هزینهٔ کل یا تکرارپذیری بدون آزمایش دیگر چیزی ثابت نمی‌کند.

Representative output: A-104: $25.00. This shows the source being consumed; it does not prove total cost or repeatability without further tests.

Select شکل خروجی را می‌سازدSelect projects

Select هر عنصر باقی‌مانده را به شکل دیگری نگاشت می‌کند: از Order به یک projection کوچک. projection می‌تواند تخصیص بسازد و انتخاب فیلدهای لازم، هم معنای گزارش را روشن می‌کند هم از حمل بی‌دلیل کل entity دوری می‌کند.

Select maps each remaining item into another shape, such as Order to a small projection. Projection may allocate, but selecting required fields clarifies intent and avoids carrying whole entities unnecessarily.

دو نحو، یک جریانTwo syntaxes, one pipeline

روش‌های extension و query syntax هر دو خوانایی‌اند و اغلب به همان عملیات تبدیل می‌شوند. انتخاب را با پیچیدگی query بسنج؛ ترتیب Where/Select را جوری بچین که معنا واضح باشد و از اجرای دوبارهٔ sequence آگاه باش.

Method and query syntax are both readability choices and often express the same operators. Choose based on query complexity; keep filtering/projection clear and watch for repeated enumeration.

IQueryable مرز ترجمه استIQueryable is a translation boundary

روی IEnumerable، delegate معمولاً در برنامه اجرا می‌شود. روی IQueryable، provider ممکن است expression را به SQL ترجمه کند؛ همهٔ متدهای C# قابل ترجمه نیستند. ToList مرز اجرای query را عوض می‌کند؛ SQL تولیدشده را inspect کن، نه اینکه حدس بزنی.

With IEnumerable, delegates usually run in the application. IQueryable providers may translate expressions into SQL, but not every C# method is translatable. ToList changes the execution boundary; inspect generated SQL instead of guessing.

یک پروژهٔ کنسولی و fixture کوچک بساز. رفتار baseline را با تست و خروجی ثبت کن، یک فرض را عمداً بشکن، failure را در نزدیک‌ترین مرز پیدا کن، اصلاح کن و همان تست را دوباره اجرا کن. گزارشت باید کد، خروجی، تفسیر و چیزی را که هنوز ثابت نشده در بر بگیرد.

Create a console project and a small fixture. Capture baseline behaviour with a test and output, deliberately break one assumption, locate the nearest failure boundary, repair it and rerun the same test. Report code, output, interpretation, and what remains unproven.

  1. baseline و انتظار را ثبت کن.
  2. Record baseline and expected behaviour.
  3. تغییر کنترل‌شده و failure را بازتولید کن.
  4. Make a controlled change and reproduce failure.
  5. repair را با همان acceptance test اثبات کن.
  6. Prove the repair with the same acceptance test.
