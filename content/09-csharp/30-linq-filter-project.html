LINQ: فیلتر و projection

LINQ: filtering and projection

گزارش می‌خواد فقط سفارش‌های پرداخت‌شده رو نشان بدهد و از هرکدوم شماره و مبلغ رو بیرون بکشد. اگه وسط کار همه‌چیز رو با حلقه و List دستی بنویسیم، خواندن شرط‌ها سخت می‌شه. LINQ رو با سؤال گزارش شروع می‌کنیم: کدوم ردیف بماند و چه شکلی از آن بسازیم؟

A report needs paid orders and only their IDs and totals. Hand-written loops and temporary lists can obscure the selection rule. We start LINQ from the report question: which rows remain, and what shape should each become?

Where انتخاب می‌کنهWhere filters

Where predicate برای هر عنصر تصمیم می‌گیره نگه داشته بشه یا نه. خودش عنصر رو تبدیل نمی‌کنه و معمولاً اجرای آن deferred هست؛ پس خطای predicate ممکنه موقع enumeration رخ دهد، نه هنگام نوشتن query.

The Where predicate decides whether each item remains. It does not transform items and is generally deferred, so predicate failures may occur during enumeration rather than query construction.

نمونه / Example
var report = orders
    .Where(order => order.Status == OrderStatus.Paid)
    .Select(order => new { order.Id, order.Total });

foreach (var row in report)
    Console.WriteLine($"{row.Id}: {row.Total:C}");

خروجی نماینده: A-104: $25.00. این مشاهده اجرای منبع رو نشان می‌ده؛ دربارهٔ هزینهٔ کل یا تکرارپذیری بدون آزمایش دیگر چیزی ثابت نمی‌کنه.

Representative output: A-104: $25.00. This shows the source being consumed; it does not prove total cost or repeatability without further tests.

Select شکل خروجی رو می‌سازهSelect projects

Select هر عنصر باقی‌مانده رو به شکل دیگری نگاشت می‌کنه: از Order به یک projection کوچک. projection می‌تونه تخصیص بسازد و انتخاب فیلدهای لازم، هم معنای گزارش رو روشن می‌کنه هم از حمل بی‌دلیل کل entity دوری می‌کنه.

Select maps each remaining item into another shape, such as Order to a small projection. Projection may allocate, but selecting required fields clarifies intent and avoids carrying whole entities unnecessarily.

دو نحو، یک جریانTwo syntaxes, one pipeline

روش‌های extension و query syntax هر دو خوانایی‌اند و اغلب به همان عملیات تبدیل می‌شن. انتخاب رو با پیچیدگی query بسنج؛ ترتیب Where/Select رو جوری بچین که معنا واضح باشه و از اجرای دوبارهٔ sequence آگاه باش.

Method and query syntax are both readability choices and often express the same operators. Choose based on query complexity; keep filtering/projection clear and watch for repeated enumeration.

IQueryable مرز ترجمه استIQueryable is a translation boundary

روی IEnumerable، delegate معمولاً در برنامه اجرا می‌شه. روی IQueryable، provider ممکنه expression رو به SQL ترجمه کند؛ همهٔ متدهای C# قابل ترجمه نیستن. ToList مرز اجرای query رو عوض می‌کنه؛ SQL تولیدشده رو inspect کن، نه اینکه حدس بزنی.

With IEnumerable, delegates usually run in the application. IQueryable providers may translate expressions into SQL, but not every C# method is translatable. ToList changes the execution boundary; inspect generated SQL instead of guessing.
