class، struct و record در عمل

Class, struct and record in practice

دو سفارش جدا ممکن است دادهٔ یکسان داشته باشند و باز هم دو موجودیت باشند؛ دو مختصات با x و y برابر معمولاً یک مقدار مفهومی‌اند. اختلاف از syntax نیست: انتخاب class، struct یا record معنای هویت، کپی و برابری را عوض می‌کند.

Two separate orders may have identical data and still be distinct entities; two coordinates with equal x and y usually represent the same conceptual value. This is not syntax style: class, struct and record change the meaning of identity, copying and equality.

داده برابر است؛ پس خود شیء هم یکی است؟Equal data—does that make the object the same?

قبل از keyword، نقش مدل را روشن کن: موجودیتی با هویت و چرخهٔ عمر داریم یا مقداری که با داده‌هایش تعریف می‌شود؟ این تصمیم روی assignment، equality، nullability و شکل API اثر می‌گذارد. اندازه و سرعت را با قانون عام حدس نمی‌زنیم؛ workload واقعی را می‌سنجیم.

Before choosing a keyword, identify the model’s role: is it an entity with identity and a lifecycle, or a value defined by its data? This affects assignment, equality, nullability and API shape. We do not guess size or speed from a universal rule; we measure the real workload.

class: دو reference، یک هویتClass: two references, one identity

در class، assignment reference را کپی می‌کند. دو متغیر ممکن است یک instance را ببینند. equality پیش‌فرض class معمولاً identity مرجع را می‌سنجد، مگر type آن را تغییر دهد؛ operator برابر هم ممکن است overload شده باشد.

With a class, assignment copies a reference, so two variables can reach one instance. Default class equality usually tests reference identity unless changed by the type; the equality operator may also be overloaded.

دو موجودیت و یک alias
sealed class Order
{
    public string Number { get; }
    public Order(string number) => Number = number;
}

var a = new Order("A-42");
var b = new Order("A-42");
var alias = a;
Console.WriteLine(a.Equals(b));
Console.WriteLine(a.Equals(alias));
خروجی معمول / Representative output
False
True

دو object هم‌داده identity جدا دارند؛ alias همان object است. اگر برابری دامنه‌ای لازم است، Equals و GetHashCode را با هم و آگاهانه تعریف کن؛ برابری داده‌ایِ تصادفی را جای هویت موجودیت ننشان.

The equal-data objects have different identities; alias is the same object. If domain equality is required, define Equals and GetHashCode consistently and deliberately; do not substitute accidental data equality for entity identity.

struct: assignment مقدار را کپی می‌کندStruct: assignment copies the value

برای بعضی مقدارهای کوچک و مستقل، struct انتخاب مناسبی است. assignment مقدار را کپی می‌کند؛ این گزاره دربارهٔ semantics زبان است، نه اینکه هر struct الزاماً روی stack و هر class روی heap قرار دارد. یک struct هم می‌تواند بزرگ باشد یا field ارجاعی داشته باشد.

A struct can fit some small, independent values. Assignment copies the value; this describes language semantics, not a rule that every struct lives on the stack and every class on the heap. A struct can be large or contain reference fields.

کپی مقدار / Value copy
struct Point
{
    public int X;
    public int Y;
}

var first = new Point { X = 2, Y = 5 };
var copy = first;
copy.X = 99;
Console.WriteLine(first.X);
Console.WriteLine(copy.X);
خروجی / Output
2
99

کپی struct لزوماً deep نیست: اگر reference به List داشته باشد، reference کپی می‌شود و دو مقدار ممکن است به یک List برسند. پس «struct همه‌چیز را بازگشتی کپی می‌کند» نادرست است. readonly struct هم برای بیان ارزشِ غیرقابل‌تغییر مفید است، نه وعدهٔ عملکرد.

Struct copying is not necessarily deep: a reference to a List is copied, so both values may reach one List. “A struct recursively copies everything” is false. readonly struct can express an immutable-value intent, not a performance guarantee.

record برای مدل مقدارمحورRecord for value-oriented models

record class همچنان reference type است، اما equality تولیدشده بر داده تکیه می‌کند؛ record struct value type است. record به‌تنهایی همهٔ اعضای mutable را immutable نمی‌کند.

A record class remains a reference type, but generated equality is data-oriented; a record struct is a value type. A record does not automatically make mutable members immutable.

برابری record و کپی with
public record Coordinate(int X, int Y);
public readonly record struct Pixel(int X, int Y);

var c1 = new Coordinate(2, 5);
var c2 = new Coordinate(2, 5);
Console.WriteLine(c1 == c2);

var p1 = new Pixel(2, 5);
var p2 = p1 with { X = 99 };
Console.WriteLine(p1.X);
Console.WriteLine(p2.X);
خروجی / Output
True
2
99

دو Coordinate با دادهٔ یکسان در equality تولیدشده برابرند، هرچند ReferenceEquals آن‌ها false است. with یک نسخهٔ تازه می‌سازد؛ کپی shallow است، پس reference داخلی به عضو mutable می‌تواند مشترک بماند. record برای هر entity یا DTO انتخاب خودکار نیست.

Equal Coordinate data compares equal under generated equality even though ReferenceEquals is false. with creates a copy; it is shallow, so an inner reference to a mutable member may remain shared. Record is not the automatic choice for every entity or DTO.

دو record ممکن است مقدار برابر و reference متفاوت داشته باشند؛ دو variable class می‌توانند یک reference داشته باشند؛ struct هم می‌تواند مقدارش را کپی کند ولی reference داخلی را مشترک نگه دارد. پرسش دقیق، ابزار آزمون درست می‌سازد.

Two records may have equal values and distinct references; class variables may share one reference; a struct may copy its value yet share an inner reference. A precise question leads to the right test.

انتخاب را از نقش داده شروع کنStart the choice with the data’s role

برای entity با هویت و lifecycle معمولاً class را بسنج؛ برای value با کپی طبیعی struct را؛ برای دادهٔ مقدارمحور record یا record struct را. سپس mutation، nullability، اندازه، equality، boxing و workload واقعی را بررسی کن. این‌ها heuristic هستند، نه قانون مطلق.

For an entity with identity and lifecycle, consider class; for a value with natural copy semantics, consider struct; for data-oriented equality, evaluate record or record struct. Then inspect mutation, nullability, size, equality, boxing and real workload. These are heuristics, not laws.

تبدیل برای performance را اندازه بگیرMeasure performance-driven changes

تبدیل کورکورانهٔ class به struct می‌تواند کپی، boxing و فشار collection را بیشتر کند. workload نماینده را قبل و بعد benchmark کن؛ یک تست کوچک جدا ممکن است الگوی واقعی برنامه را نشان ندهد.

Blindly changing a class to a struct can increase copying, boxing and collection pressure. Benchmark a representative workload before and after; an isolated micro-test may not represent the application.

مفهوم را قبل از keyword انتخاب کنChoose the concept before the keyword

class معمولاً reference و هویت؛ struct semantics مقدار و کپی؛ record برابری مقدارمحور را به همراه دارد—اما هر سه نیازمند قرارداد روشن‌اند. stack/heap را افسانه نکن، deep-copy را فرض نگیر و برای performance حدس نزن. بعد از انتشار این فصل، برابری و کپی را در انتخاب composition و interface هم به کار می‌گیریم.

A class commonly models reference identity; a struct has value-copy semantics; a record supplies value-oriented equality—but all need clear contracts. Avoid stack/heap myths, assumed deep copies and performance guesses. We will carry these ideas into composition and interfaces next.
