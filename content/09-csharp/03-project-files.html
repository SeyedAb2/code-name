پروژه، solution و تنظیمات build

Projects, solutions and build settings

کد برنامهٔ ما درست هست، اما روی سیستم همکار build نمی‌شه. هر دو یک فایل `.cs` داریم؛ پس اختلاف کجاست؟ جواب خیلی وقت‌ها داخل فایل پروژه و SDK انتخاب‌شده پنهان شده.

Our code is fine, but it will not build on a teammate's machine. We have the same `.cs` file, so what differs? Often the answer is hidden in the project file and selected SDK.

فایل csproj قرارداد build استThe csproj is a build contract

پروژهٔ console فصل قبل رو باز کن. فایل `.csproj` معمولاً کوتاه هست، اما چیزهای مهمی مثل SDK-style project و target framework رو ثبت می‌کنه.

Open the console project from the previous chapter. Its `.csproj` is usually short, but declares important things such as the SDK-style project and target framework.

OrderHello.csproj
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>

`TargetFramework` می‌گه پروژه برای کدوم APIهای .NET ساخته می‌شه. این با نسخهٔ SDKی که build رو انجام می‌ده یکی نیست. SDK جدید می‌تونه پروژه‌ای با target قدیمی‌تر بسازد؛ اما دسترسی به APIها و runtime مقصد رو target تعیین می‌کنه. `OutputType` مشخص می‌کنه خروجی برنامهٔ اجرایی هست یا library.

`TargetFramework` identifies the .NET API surface the project targets. It is not the SDK version performing the build. A newer SDK can build for an older target, but the target determines available APIs and the expected runtime. `OutputType` distinguishes an executable from a library.

target رو برای خاموش‌کردن خطا عوض نکنDo not change the target just to silence an error

اگه SDK مناسب نداری یا packageای target رو پشتیبانی نمی‌کنه، پایین‌آوردن `TargetFramework` ممکنه خطا رو پنهان کند و deployment رو ناسازگار کند. اول علت رو بخوان؛ تغییر target تصمیم سازگاری محصول هست.

If the required SDK is missing or a package does not support the target, lowering `TargetFramework` may hide the error and break deployment compatibility. Diagnose first; changing a target is a product compatibility decision.

فایل پروژه هم بخشی از کدهThe project file is part of the program

خیلی وقت‌ها csproj فقط وقتی دیده می‌شه که merge conflict خورده یا package نصب نشده. ولی واقعیت اینه که همین فایل تعیین می‌کنه پروژه برای چه frameworkی ساخته بشه، چه قابلیت‌هایی فعال باشن و build چه چیزهایی رو وارد محاسبه کنه. پس باهاش مثل یک فایل پیکربندی فرعی رفتار نکن؛ بخشی از قرارداد پروژه‌ست.

The csproj file is often noticed only when a merge conflict appears or a package refuses to restore. In reality it decides which framework the project targets, which language/build features are enabled, and what the build includes. Treat it as part of the project contract, not as incidental configuration.

اینجا هدف حفظ propertyهای MSBuild نیست. می‌خوایم یه تغییر کوچیک بدیم و اثرش رو در build ببینیم. هر چیزی که فقط اسمش رو بخونی زود فراموش می‌شه؛ ولی وقتی `TargetFramework` یا nullable setting رو عوض می‌کنی و compiler رفتار متفاوتی نشون می‌ده، ارتباط فایل پروژه با کد واقعی جا می‌افته.

The goal is not to memorize MSBuild properties. Change one property and observe the build consequence. Names are easy to forget; seeing `TargetFramework` or a nullable setting alter compiler behaviour gives the project file a concrete meaning.

restore با build چه فرقی داره؟How does restore differ from build?

در پوشهٔ پروژه این فرمان‌ها رو جدا اجرا کن:

Run these commands separately from the project folder:

terminal
dotnet restore
dotnet build --no-restore
dotnet test
dotnet publish -c Release -o ./publish

restore dependencyهای NuGet رو resolve می‌کنه و فایل‌هایی مثل `obj/project.assets.json` می‌سازه. `--no-restore` در build می‌گه این مرحله رو تکرار نکن؛ اگه assets موجود یا به‌روز نباشن build باید شکست بخورد. این فرمان‌ها جدا هستن تا بفهمیم failure از دریافت dependency هست یا از compile.

Restore resolves NuGet dependencies and creates files such as `obj/project.assets.json`. `--no-restore` asks build not to repeat that stage; if assets are absent or stale, the build should fail. Separating the commands helps identify whether a failure comes from dependency resolution or compilation.

`dotnet test` معمولاً پروژهٔ تست رو build و تست‌هایش رو اجرا می‌کنه. `publish` خروجی deployment می‌سازه؛ publish موفق هنوز نمی‌گه سیستم مقصد runtime یا native dependency لازم رو داره. بعداً در پروژهٔ CLI این مرز رو عملاً آزمایش می‌کنیم.

`dotnet test` normally builds the test project and runs its tests. `publish` creates deployment output; a successful publish does not prove the target machine has a required runtime or native dependency. We will test that boundary in the CLI project.

Debug، Release و RIDDebug, Release and RIDs

Debug و Release نام configurationهای build هستن. خروجی معمولاً در `bin/Debug/net10.0` یا `bin/Release/net10.0` قرار می‌گیره. Release برای انتشار متداول هست، اما «Release همیشه سریع‌تر است» ادعایی هست که باید روی workload واقعی سنجید.

Debug and Release are build configurations. Output commonly appears under `bin/Debug/net10.0` or `bin/Release/net10.0`. Release is common for deployment, but “Release is always faster” is a claim to measure against a real workload.

RID مثل `linux-x64` یا `win-x64` سیستم‌عامل و معماری مقصد رو دقیق‌تر می‌کنه. این رو با `TargetFramework` قاطی نکن: یکی APIهای .NET رو مشخص می‌کنه، دیگری در صورت نیاز، محیط native مقصد رو. `global.json` هم می‌تونه SDK انتخابی مخزن رو محدود کند؛ اگه نسخهٔ قفل‌شده نصب نباشه، build به‌جای انتخاب تصادفی باید روشن شکست بخورد.

A RID such as `linux-x64` or `win-x64` specifies a target OS and architecture. Do not confuse it with `TargetFramework`: one selects .NET APIs, the other can select native target assets. `global.json` can constrain the SDK selected for a repository; if that SDK is absent, the build should fail clearly rather than silently use an arbitrary version.

چه وقت solution لازم می‌شه؟When do you need a solution?

وقتی برنامه، تست و library رو در پروژه‌های جدا نگه می‌داریم، solution آن‌ها رو یک‌جا باز و build می‌کنه. خود solution برنامه رو اجرا نمی‌کنه و dependency نیست؛ ظرفی برای هماهنگی چند project هست.

When the app, tests and library live in separate projects, a solution opens and builds them together. The solution is not an executable or a dependency; it coordinates multiple projects.

terminal
dotnet new sln --name OrderTools
dotnet sln add ./OrderHello/OrderHello.csproj
dotnet sln list

خروجی `dotnet sln list` باید پروژهٔ افزوده‌شده رو نشان دهد. اگه فرمان رو از پوشهٔ اشتباه زدی، مسیر relative ممکنه اشتباه بشه؛ پیش از عوض‌کردن فایل، working directory و مسیر project رو بررسی کن.

`dotnet sln list` should show the added project. If run from the wrong folder, a relative path may be wrong; check the working directory and project path before editing files.

For example, a project may target `net10.0` while the installed SDK is a specific 10.0.x patch. The target selects APIs; the SDK performs the build. Their version strings need not be identical.

تمرین رو با همون ورودی اول دوباره اجرا کن و بعد یک ورودی مرزی هم اضافه کن. اگه فقط یکی از این دو مسیر رو دیده باشی، هنوز قرارداد کامل تمرین رو ثابت نکردی.

Run the original input again, then add one boundary case. If you observed only one path, you have not yet proved the full exercise contract.

تمرین 3.2Exercise 3.2کاربردیApplied۸ دقیقه8 min

۲) restore رو از build جدا کن2) Separate restore from build

در یک پوشهٔ پاک restore و سپس build با `--no-restore` بگیر. نام یک فایل تولیدشده در `obj` رو ثبت کن. پاک‌کردن `obj` چرا می‌تونه build بعدی رو خراب کند؟

In a clean project, restore and then build with `--no-restore`. Record one generated file under `obj`. Why can deleting `obj` break the next no-restore build?

معیار موفقیت: کد باید build یا run بشه و پیش‌بینی‌ات رو با خروجی یا خطای واقعی compiler/runtime مقایسه کنی.

Success criterion: the code must build or run, and you must compare your prediction with real compiler/runtime evidence.

راهنماییHint

قبل از اجرا، نتیجه رو توی یک کامنت بنویس. اختلاف پیش‌بینی و خروجی همون جاییه که باید بیشتر بررسی کنی.

Write your expected result in a comment before running. Any mismatch is the part worth investigating.

پاسخSolution

restore فایل assetهای dependency مثل `project.assets.json` رو تولید می‌کنه. بعد از حذف `obj`، build با `--no-restore` ممکنه این فایل رو پیدا نکند. restore دوباره وضعیت وابستگی رو می‌سازه؛ حذف `obj` فقط وقتی امن هست که بتوانی آن رو بازتولید کنی و مرحلهٔ restore رو اجرا کنی.

Restore generates dependency assets such as `project.assets.json`. After deleting `obj`, a no-restore build may not find them. Restore regenerates dependency state; deleting `obj` is safe only when it can be recreated and restore is run.

برای بستن تمرین، خروجی یا test result رو نگه دار و یک بار نسخهٔ قبل و بعد رو کنار هم ببین. هدف فقط سبزشدن کد نیست؛ باید معلوم باشه کدوم رفتار واقعاً عوض شده.

Finish by keeping the output or test result and comparing the before/after behaviour. The goal is not merely green code; make the changed behaviour explicit.

۳) خروجی دو configuration رو مقایسه کن3) Compare two configurations

Debug و Release build بگیر، مسیر assembly هر دو رو پیدا کن. آیا نام Release به‌تنهایی ثابت می‌کنه برنامه سریع‌تر هست؟

Build Debug and Release and locate each assembly. Does the Release label alone prove the app is faster?

معیار موفقیت: کد باید build یا run بشه و پیش‌بینی‌ات رو با خروجی یا خطای واقعی compiler/runtime مقایسه کنی.

Success criterion: the code must build or run, and you must compare your prediction with real compiler/runtime evidence.

راهنماییHint

اگه شکست خورد، اول مشخص کن compile-time هست یا runtime؛ بعد سراغ fix برو.

If it fails, first classify the failure as compile-time or runtime; only then repair it.

پاسخSolution

مسیرها معمولاً `bin/Debug/net10.0` و `bin/Release/net10.0` هستن. Release تنظیمات بهینه‌سازی متداول داره اما سرعت رو بدون workload و اندازه‌گیری ثابت نمی‌کنه. برای ادعای کارایی باید benchmark منصفانه اجرا بشه.

Typical paths are `bin/Debug/net10.0` and `bin/Release/net10.0`. Release commonly enables optimizations but does not prove speed without a workload and measurement. A fair benchmark is needed.

آخر کار یه بار از خودت بپرس این آزمایش دقیقاً چی رو ثابت کرد و چی رو نه. این عادت جلوی نتیجه‌گیری بزرگ از یه مثال کوچیک رو می‌گیره.

At the end, state exactly what this experiment proves and what it does not. That habit prevents broad conclusions from a tiny example.

تمرین 3.4Exercise 3.4چالشیChallenge۱۲ دقیقه12 min

۴) شکست SDK رو عیب‌یابی کن4) Diagnose an SDK-selection failure

در یک پوشهٔ موقت `global.json` بساز که نسخهٔ نصب‌نشده‌ای رو درخواست کند. `dotnet --version` و build رو اجرا کن؛ بعد نسخه رو به SDK موجود تغییر بده. چه چیزی ثابت شد و چه چیزی نه؟

In a disposable folder, create a `global.json` requesting an SDK you do not have. Run `dotnet --version` and build, then change it to an installed SDK. What did the experiment prove—and what did it not?

معیار موفقیت: کد باید build یا run بشه و پیش‌بینی‌ات رو با خروجی یا خطای واقعی compiler/runtime مقایسه کنی.

Success criterion: the code must build or run, and you must compare your prediction with real compiler/runtime evidence.

راهنماییHint

اول با کوچک‌ترین ورودی ممکن امتحانش کن؛ بعد فقط یک چیز رو عوض کن و دوباره خروجی رو ببین.

Start with the smallest input, then change one thing and observe the output again.

پاسخSolution

درخواست نسخهٔ غایب باید خطای انتخاب SDK بدهد؛ با نسخهٔ نصب‌شده، CLI باید آن SDK رو انتخاب کند. آزمایش نشان می‌ده `global.json` روی انتخاب SDK اثر داره، نه اینکه target framework یا runtime مقصد رو عوض کند. فایل رو فقط در پوشهٔ آزمایشی نگه دار.

A missing requested version should fail SDK selection; using an installed version should let the CLI select it. This shows `global.json` affects SDK selection, not the target framework or deployment runtime. Keep the file in the disposable test folder.

همون سناریو رو با یک حالت مرزی تکرار کن. اگه نتیجه متفاوت شد، به‌جای patch فوری اول مرز قراردادی که شکسته رو مشخص کن.

Repeat the scenario with a boundary case. If behaviour changes, identify the broken contract boundary before applying another patch.
