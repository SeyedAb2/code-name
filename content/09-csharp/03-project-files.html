پروژه، solution و تنظیمات build

Projects, solutions and build settings

کد برنامهٔ ما درست است، اما روی سیستم همکار build نمی‌شود. هر دو یک فایل `.cs` داریم؛ پس اختلاف کجاست؟ جواب خیلی وقت‌ها داخل فایل پروژه و SDK انتخاب‌شده پنهان شده.

Our code is fine, but it will not build on a teammate's machine. We have the same `.cs` file, so what differs? Often the answer is hidden in the project file and selected SDK.

فایل csproj قرارداد build استThe csproj is a build contract

پروژهٔ console فصل قبل را باز کن. فایل `.csproj` معمولاً کوتاه است، اما چیزهای مهمی مثل SDK-style project و target framework را ثبت می‌کند.

Open the console project from the previous chapter. Its `.csproj` is usually short, but declares important things such as the SDK-style project and target framework.

OrderHello.csproj
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>

`TargetFramework` می‌گوید پروژه برای کدام APIهای .NET ساخته می‌شود. این با نسخهٔ SDKی که build را انجام می‌دهد یکی نیست. SDK جدید می‌تواند پروژه‌ای با target قدیمی‌تر بسازد؛ اما دسترسی به APIها و runtime مقصد را target تعیین می‌کند. `OutputType` مشخص می‌کند خروجی برنامهٔ اجرایی است یا library.

`TargetFramework` identifies the .NET API surface the project targets. It is not the SDK version performing the build. A newer SDK can build for an older target, but the target determines available APIs and the expected runtime. `OutputType` distinguishes an executable from a library.

target را برای خاموش‌کردن خطا عوض نکنDo not change the target just to silence an error

اگر SDK مناسب نداری یا packageای target را پشتیبانی نمی‌کند، پایین‌آوردن `TargetFramework` ممکن است خطا را پنهان کند و deployment را ناسازگار کند. اول علت را بخوان؛ تغییر target تصمیم سازگاری محصول است.

If the required SDK is missing or a package does not support the target, lowering `TargetFramework` may hide the error and break deployment compatibility. Diagnose first; changing a target is a product compatibility decision.

restore با build چه فرقی دارد؟How does restore differ from build?

در پوشهٔ پروژه این فرمان‌ها را جدا اجرا کن:

Run these commands separately from the project folder:

terminal
dotnet restore
dotnet build --no-restore
dotnet test
dotnet publish -c Release -o ./publish

restore dependencyهای NuGet را resolve می‌کند و فایل‌هایی مثل `obj/project.assets.json` می‌سازد. `--no-restore` در build می‌گوید این مرحله را تکرار نکن؛ اگر assets موجود یا به‌روز نباشند build باید شکست بخورد. این فرمان‌ها جدا هستند تا بفهمیم failure از دریافت dependency است یا از compile.

Restore resolves NuGet dependencies and creates files such as `obj/project.assets.json`. `--no-restore` asks build not to repeat that stage; if assets are absent or stale, the build should fail. Separating the commands helps identify whether a failure comes from dependency resolution or compilation.

`dotnet test` معمولاً پروژهٔ تست را build و تست‌هایش را اجرا می‌کند. `publish` خروجی deployment می‌سازد؛ publish موفق هنوز نمی‌گوید سیستم مقصد runtime یا native dependency لازم را دارد. بعداً در پروژهٔ CLI این مرز را عملاً آزمایش می‌کنیم.

`dotnet test` normally builds the test project and runs its tests. `publish` creates deployment output; a successful publish does not prove the target machine has a required runtime or native dependency. We will test that boundary in the CLI project.

Debug، Release و RIDDebug, Release and RIDs

Debug و Release نام configurationهای build هستند. خروجی معمولاً در `bin/Debug/net10.0` یا `bin/Release/net10.0` قرار می‌گیرد. Release برای انتشار متداول است، اما «Release همیشه سریع‌تر است» ادعایی است که باید روی workload واقعی سنجید.

Debug and Release are build configurations. Output commonly appears under `bin/Debug/net10.0` or `bin/Release/net10.0`. Release is common for deployment, but “Release is always faster” is a claim to measure against a real workload.

RID مثل `linux-x64` یا `win-x64` سیستم‌عامل و معماری مقصد را دقیق‌تر می‌کند. این را با `TargetFramework` قاطی نکن: یکی APIهای .NET را مشخص می‌کند، دیگری در صورت نیاز، محیط native مقصد را. `global.json` هم می‌تواند SDK انتخابی مخزن را محدود کند؛ اگر نسخهٔ قفل‌شده نصب نباشد، build به‌جای انتخاب تصادفی باید روشن شکست بخورد.

A RID such as `linux-x64` or `win-x64` specifies a target OS and architecture. Do not confuse it with `TargetFramework`: one selects .NET APIs, the other can select native target assets. `global.json` can constrain the SDK selected for a repository; if that SDK is absent, the build should fail clearly rather than silently use an arbitrary version.

چه وقت solution لازم می‌شود؟When do you need a solution?

وقتی برنامه، تست و library را در پروژه‌های جدا نگه می‌داریم، solution آن‌ها را یک‌جا باز و build می‌کند. خود solution برنامه را اجرا نمی‌کند و dependency نیست؛ ظرفی برای هماهنگی چند project است.

When the app, tests and library live in separate projects, a solution opens and builds them together. The solution is not an executable or a dependency; it coordinates multiple projects.

terminal
dotnet new sln --name OrderTools
dotnet sln add ./OrderHello/OrderHello.csproj
dotnet sln list

خروجی `dotnet sln list` باید پروژهٔ افزوده‌شده را نشان دهد. اگر فرمان را از پوشهٔ اشتباه زدی، مسیر relative ممکن است اشتباه شود؛ پیش از عوض‌کردن فایل، working directory و مسیر project را بررسی کن.

`dotnet sln list` should show the added project. If run from the wrong folder, a relative path may be wrong; check the working directory and project path before editing files.

تمرین: build را قابل توضیح کنExercises: make the build explainable

۱) target framework را پیدا کن1) Find the target framework

از پروژهٔ قبل `TargetFramework` را بخوان، `dotnet --info` بگیر و تفاوت target پروژه و SDK نصب‌شده را در دو خط توضیح بده.

Read `TargetFramework` from the previous project, run `dotnet --info`, and explain the difference between the project target and installed SDK.

پاسخSolution

مثلاً پروژه `net10.0` را هدف می‌گیرد ولی SDK نصب‌شده نسخهٔ 10.0.x است. target APIهایی را تعیین می‌کند که پروژه برایشان compile می‌شود؛ SDK ابزار اجرای build است. این دو ممکن است شمارهٔ متفاوت داشته باشند.

For example, a project may target `net10.0` while the installed SDK is a specific 10.0.x patch. The target selects APIs; the SDK performs the build. Their version strings need not be identical.

۲) restore را از build جدا کن2) Separate restore from build

در یک پوشهٔ پاک restore و سپس build با `--no-restore` بگیر. نام یک فایل تولیدشده در `obj` را ثبت کن. پاک‌کردن `obj` چرا می‌تواند build بعدی را خراب کند؟

In a clean project, restore and then build with `--no-restore`. Record one generated file under `obj`. Why can deleting `obj` break the next no-restore build?

پاسخSolution

restore فایل assetهای dependency مثل `project.assets.json` را تولید می‌کند. بعد از حذف `obj`، build با `--no-restore` ممکن است این فایل را پیدا نکند. restore دوباره وضعیت وابستگی را می‌سازد؛ حذف `obj` فقط وقتی امن است که بتوانی آن را بازتولید کنی و مرحلهٔ restore را اجرا کنی.

Restore generates dependency assets such as `project.assets.json`. After deleting `obj`, a no-restore build may not find them. Restore regenerates dependency state; deleting `obj` is safe only when it can be recreated and restore is run.

۳) خروجی دو configuration را مقایسه کن3) Compare two configurations

Debug و Release build بگیر، مسیر assembly هر دو را پیدا کن. آیا نام Release به‌تنهایی ثابت می‌کند برنامه سریع‌تر است؟

Build Debug and Release and locate each assembly. Does the Release label alone prove the app is faster?

پاسخSolution

مسیرها معمولاً `bin/Debug/net10.0` و `bin/Release/net10.0` هستند. Release تنظیمات بهینه‌سازی متداول دارد اما سرعت را بدون workload و اندازه‌گیری ثابت نمی‌کند. برای ادعای کارایی باید benchmark منصفانه اجرا شود.

Typical paths are `bin/Debug/net10.0` and `bin/Release/net10.0`. Release commonly enables optimizations but does not prove speed without a workload and measurement. A fair benchmark is needed.

۴) شکست SDK را عیب‌یابی کن4) Diagnose an SDK-selection failure

در یک پوشهٔ موقت `global.json` بساز که نسخهٔ نصب‌نشده‌ای را درخواست کند. `dotnet --version` و build را اجرا کن؛ بعد نسخه را به SDK موجود تغییر بده. چه چیزی ثابت شد و چه چیزی نه؟

In a disposable folder, create a `global.json` requesting an SDK you do not have. Run `dotnet --version` and build, then change it to an installed SDK. What did the experiment prove—and what did it not?

پاسخSolution

درخواست نسخهٔ غایب باید خطای انتخاب SDK بدهد؛ با نسخهٔ نصب‌شده، CLI باید آن SDK را انتخاب کند. آزمایش نشان می‌دهد `global.json` روی انتخاب SDK اثر دارد، نه اینکه target framework یا runtime مقصد را عوض کند. فایل را فقط در پوشهٔ آزمایشی نگه دار.

A missing requested version should fail SDK selection; using an installed version should let the CLI select it. This shows `global.json` affects SDK selection, not the target framework or deployment runtime. Keep the file in the disposable test folder.
