برنامهٔ C# از کجا می‌آید؟

Where does a C# program come from?

کد را می‌نویسی و اجرا را می‌زنی. ولی بین این دو چه خبر است؟ اگر build شکست بخورد یا برنامه روی سیستم دیگری بالا نیاید، شناخت این مسیر کمک می‌کند به‌جای حدس‌زدن همان مرز خراب را پیدا کنی.

You write code and press Run. What happens in between? When a build fails or the app will not start elsewhere, understanding the path helps you find the broken boundary rather than guess.

کدام ابزار برنامه را اجرا کرد؟Which tool ran the program?

همکارت می‌گوید «روی سیستم من کار می‌کند»، اما روی لپ‌تاپ تو `dotnet run` خطا می‌دهد. قبل از نصب دوبارهٔ همه‌چیز، اول بپرس چه نسخه‌ای از ابزار واقعاً نصب است.

A teammate says “it works on my machine,” but `dotnet run` fails on yours. Before reinstalling everything, first ask which tool versions are actually installed.

terminal
dotnet --info · dotnet --list-sdks · dotnet --list-runtimes

`dotnet --info` محیط را خلاصه می‌کند. SDK ابزار توسعه است: CLI، MSBuild، compiler و هدف‌های build. runtime برنامهٔ ساخته‌شده را اجرا می‌کند. SDK معمولاً runtime همان نسخه را هم نصب دارد؛ اما runtime قدیمی تضمین نمی‌کند برنامهٔ هدف‌گرفته برای نسخهٔ جدید اجرا شود.

`dotnet --info` summarizes the environment. The SDK is the development toolset: CLI, MSBuild, compiler and build targets. The runtime executes built apps. An SDK normally includes its matching runtime, but an older runtime does not guarantee an app targeting a newer release can run.

build و اجرا یکی نیستندBuilding and running are different

برای توسعه SDK می‌خواهی. برای اجرای برنامهٔ framework-dependent، runtime سازگار لازم است. در انتشار self-contained runtime همراه خروجی می‌آید؛ اندازه و مسئولیت به‌روزرسانی هم عوض می‌شود.

Development needs an SDK. A framework-dependent deployment needs a compatible runtime. A self-contained publish carries the runtime in its output, changing size and servicing responsibilities.

از فایل منبع تا کد ماشینFrom source to machine code

کامپایلر C# معمولاً فایل `.cs` را مستقیم به دستورهای CPU همین لپ‌تاپ تبدیل نمی‌کند. اول کد را بررسی و خروجی میانی به‌همراه metadata تولید می‌کند؛ runtime بقیهٔ مسیر را می‌برد.

The C# compiler does not normally turn `.cs` directly into instructions for this laptop's CPU. It checks the code and emits intermediate output with metadata; the runtime continues the journey.

Roslyn که از راه SDK اجرا می‌شود، کد را parse و type-check می‌کند، خطا و warning می‌دهد و assembly می‌سازد. assembly معمولاً IL و metadata دارد: IL دستورهای میانیِ وابسته‌نبودن به یک CPU مشخص است؛ metadata نوع‌ها و memberها را توصیف می‌کند. این portability نسبی است، نه قول اجرای یکسان روی هر سیستم‌عامل؛ target framework و وابستگی native هنوز مهم‌اند.

Roslyn, invoked through the SDK, parses and type-checks code, reports errors and warnings, and creates an assembly. Assemblies commonly contain IL and metadata: IL is intermediate code not tied to one CPU, and metadata describes types and members. This is relative portability, not a promise of identical execution on every OS; target frameworks and native dependencies still matter.

در اجرای معمول، CLR و runtime assembly را بار می‌کنند و سرویس‌هایی مثل مدیریت حافظه و exception را فراهم می‌کنند. JIT متدهای لازم را برای معماری فعلی به machine code تبدیل می‌کند. ReadyToRun بخشی از کد را برای target از قبل آماده می‌کند؛ Native AOT مسیر انتشار native دیگری است و محدودیت خودش را دارد. این‌ها انتخاب‌اند، نه مراحل اجباری هر پروژه.

In the common path, the CLR and runtime load assemblies and provide services such as memory management and exception handling. The JIT compiles needed methods to machine code for the current architecture. ReadyToRun precompiles some code for a target; Native AOT is another native publishing path with its own constraints. These are options, not mandatory stages.

managed یعنی رایگان؟ نه.Does managed mean free? No.

بیشتر C# managed است و runtime بسیاری از عمر شیءها را مدیریت می‌کند. allocation، GC، I/O و lock همچنان هزینه دارند. کتابخانهٔ native یا `unsafe` هم مرز مالکیت حافظه و ABI را وارد می‌کند.

Most C# is managed, and the runtime manages much object lifetime. Allocations, GC, I/O and locks still cost something. Native libraries and `unsafe` code introduce memory-ownership and ABI boundaries.

اولین پروژه و چیزی که واقعاً ثابت می‌کندThe first project and what it actually proves

اگر SDK 10 نصب است، در پوشهٔ تازه اجرا کن. `dotnet new` قالب می‌سازد و `dotnet run` معمولاً restore، build و اجرا را پشت‌سرهم انجام می‌دهد.

If SDK 10 is installed, run this in a fresh folder. `dotnet new` creates a template; `dotnet run` commonly restores, builds and executes it.

terminal
dotnet new console --framework net10.0 --name OrderProbe
cd OrderProbe
dotnet run
representative output
Hello, World!

این خروجی ثابت می‌کند همین برنامه در همین محیط اجرا شده؛ نه اینکه تست دارد یا روی server دیگری بالا می‌آید. `dotnet restore` dependencyها را resolve می‌کند، `dotnet build` compile و هدف‌های build را تمام می‌کند، `dotnet test` تست‌های کشف‌شده را اجرا می‌کند و `dotnet publish` خروجی استقرار می‌سازد. هیچ‌کدام جای دیگری را نمی‌گیرد.

This output proves the app ran in this environment—not that it has tests or starts on another server. `dotnet restore` resolves dependencies, `dotnet build` compiles and runs build targets, `dotnet test` executes discovered tests, and `dotnet publish` creates deployment output. None substitutes for another.

Debug و Release دو configuration هستند، نه دو runtime. معمولاً `obj` فایل‌های میانی و restore را دارد، `bin` خروجی build و `publish` خروجی مناسب تحویل را. Release ممکن است بهینه‌سازی کند؛ دربارهٔ سرعت با benchmark نتیجه می‌گیریم، نه از اسم پوشه.

Debug and Release are configurations, not different runtimes. `obj` commonly holds intermediate and restore files, `bin` build output, and `publish` deployment output. Release may optimize code; use benchmarks—not folder names—to make performance claims.

تمرین‌ها: از حدس به مدرکExercises: from guesses to evidence

۱) محیطت چه چیزی دارد؟1) What is installed?

`dotnet --list-sdks` و `--list-runtimes` را اجرا و جدا گزارش کن. چه چیزی را نباید از یکی دربارهٔ دیگری نتیجه بگیری؟

Run `dotnet --list-sdks` and `--list-runtimes`, reporting each separately. What must you not infer from one list about the other?

پاسخ و دلیلSolution and reasoning

SDK ابزار ساخت است و runtime ابزار اجرای برنامه. داشتن runtime به معنی SDK نیست؛ داشتن SDK هم سازگاری هر targetی را تضمین نمی‌کند. target پروژه را هم باید خواند.

The SDK builds and the runtime executes. A runtime does not imply an SDK, and an SDK does not guarantee compatibility with every target. Inspect the project target too.

۲) خطای کامپایل را بازتولید کن2) Reproduce a compiler error

در پروژه local تعریف کن و پیش از مقداردهی چاپش کن؛ build بگیر، کد خطا را ثبت و بعد مقداردهی کن. آیا تلاش اول به JIT رسید؟

Declare a local, print it before assignment, build, record the diagnostic and then initialize it. Did the first attempt reach the JIT?

پاسخ و دلیلSolution and reasoning
C#
int total;
Console.WriteLine(total); // CS0165
total = 0;
Console.WriteLine(total);

CS0165 خطای compile-time در definite assignment است. برنامه‌ای برای اجرا ساخته نشده، پس JIT دخیل نبوده. مقداردهی خطا را رفع می‌کند.

CS0165 is a compile-time definite-assignment error. No runnable program was produced, so the JIT was not involved. Initialization fixes the error.

۳) build را از run جدا کن3) Separate build from run

`dotnet build -c Release` را اجرا و مسیر خروجی را پیدا کن؛ بعد run کن. کدام مدرک مربوط به compiler است و کدام به اجرای runtime؟

Run `dotnet build -c Release`, locate output, then run the app. Which evidence concerns compilation and which concerns runtime execution?

پاسخ و دلیلSolution and reasoning

Build succeeded و فایل‌های `bin/Release` مدرک build است؛ خروجی برنامه مدرک اجرا. build موفق exception زمان اجرا را رد نمی‌کند.

Build success and `bin/Release` artifacts evidence the build; program output evidences execution. A successful build does not rule out run-time exceptions.

۴) زنجیره را کامل کن4) Complete the pipeline

source → ؟ → assembly دارای ؟ → runtime → ؟ را کامل کن و توضیح بده کدام مرحله کد ماشین را برای معماری جاری می‌سازد.

Complete source → ? → assembly with ? → runtime → ?, and identify which stage creates machine code for the current architecture.

پاسخ و دلیلSolution and reasoning

source → Roslyn → assembly شامل IL و metadata → runtime/CLR → JIT → machine code. مسیر معمول همین است؛ ReadyToRun و Native AOT زمان‌بندی/شکل خروجی را تغییر می‌دهند.

Source → Roslyn → assembly containing IL and metadata → runtime/CLR → JIT → machine code. This is the common path; ReadyToRun and Native AOT change output shape or compilation timing.

۵) حدود مدرک را گزارش کن5) Report the evidence boundary

یک پروژهٔ تازه بساز و `restore`، `build`، `run` و `publish` را جدا اجرا کن. برای هرکدام یک شاهد واقعی بنویس و یک چیزی که آن شاهد ثابت نمی‌کند.

Create a fresh project and run restore, build, run and publish separately. Record one real observation and one thing it does not prove for each.

پاسخ و دلیلSolution and reasoning

restore موفق dependency resolution را ثابت می‌کند، نه compile. build موفق compile را ثابت می‌کند، نه رفتار. run خروجی این ماشین را نشان می‌دهد، نه مقصد دیگر. publish خروجی تحویل می‌سازد، نه آمادگی runtime مقصد. همین تفکیک جلوی نتیجه‌گیری بیش از شواهد را می‌گیرد.

Restore proves dependency resolution, not compilation. Build proves compilation, not behavior. Run shows output on this machine, not another target. Publish creates deployment output, not target runtime readiness. Separating these claims prevents over-reading evidence.

حالا نوبت خود زبان استNow for the language itself

حالا می‌دانیم چه چیزی برنامه را می‌سازد و چه چیزی اجرا می‌کند. در فصل بعد متغیرها را وارد بازی می‌کنیم، مقدارها را عوض می‌کنیم و اولین اشتباهی را می‌سازیم که compiler پیش از اجرا می‌گیرد.
