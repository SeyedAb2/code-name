برنامهٔ C# از کجا میاد؟

Where does a C# program come from?

کد رو می‌نویسی و اجرا رو می‌زنی. ولی بین این دو چه خبره؟ اگه build شکست بخورد یا برنامه روی سیستم دیگری بالا نیاید، شناخت این مسیر کمک می‌کنه به‌جای حدس‌زدن همان مرز خراب رو پیدا کنی.

You write code and press Run. What happens in between? When a build fails or the app will not start elsewhere, understanding the path helps you find the broken boundary rather than guess.

کدوم ابزار برنامه رو اجرا کرد؟Which tool ran the program?

همکارت می‌گه «روی سیستم من کار می‌کنه»، اما روی لپ‌تاپ تو `dotnet run` خطا می‌ده. قبل از نصب دوبارهٔ همه‌چیز، اول بپرس چه نسخه‌ای از ابزار واقعاً نصب هست.

A teammate says “it works on my machine,” but `dotnet run` fails on yours. Before reinstalling everything, first ask which tool versions are actually installed.

terminal
dotnet --info · dotnet --list-sdks · dotnet --list-runtimes

`dotnet --info` محیط رو خلاصه می‌کنه. SDK ابزار توسعه هست: CLI، MSBuild، compiler و هدف‌های build. runtime برنامهٔ ساخته‌شده رو اجرا می‌کنه. SDK معمولاً runtime همان نسخه رو هم نصب داره؛ اما runtime قدیمی تضمین نمی‌کنه برنامهٔ هدف‌گرفته برای نسخهٔ جدید اجرا بشه.

`dotnet --info` summarizes the environment. The SDK is the development toolset: CLI, MSBuild, compiler and build targets. The runtime executes built apps. An SDK normally includes its matching runtime, but an older runtime does not guarantee an app targeting a newer release can run.

build و اجرا یکی نیستنBuilding and running are different

برای توسعه SDK می‌خوای. برای اجرای برنامهٔ framework-dependent، runtime سازگار لازمه. در انتشار self-contained runtime همراه خروجی میاد؛ اندازه و مسئولیت به‌روزرسانی هم عوض می‌شه.

Development needs an SDK. A framework-dependent deployment needs a compatible runtime. A self-contained publish carries the runtime in its output, changing size and servicing responsibilities.

قبل از حفظ‌کردن اسم ابزارها، مرزشون رو پیدا کنیمBefore memorizing tool names, find their boundaries

یه اشتباه رایج اینه که SDK، runtime و compiler رو سه اسم برای یک چیز ببینیم. تا وقتی همه‌چیز روی لپ‌تاپ خودت کار می‌کنه شاید این اشتباه دردسر نسازه؛ دردسر از جایی شروع می‌شه که CI فقط runtime داره، پروژه target تازه‌تری می‌خواد، یا خروجی روی ماشین دیگری بالا نمیاد. این فصل رو با یک سؤال ساده جلو ببر: «الان دقیقاً کدوم بخش از زنجیره مسئول این کاره؟» هر بار جواب این سؤال روشن شد، نصف عیب‌یابی‌های بعدی هم کوتاه‌تر می‌شن.

A common mistake is to treat the SDK, runtime, and compiler as three names for the same thing. That may stay hidden while everything runs on your own laptop; it becomes expensive when CI has only a runtime, a project targets a newer framework, or an artifact fails on another machine. Carry one question through this chapter: “Which part of the chain is responsible for this step?” Once that boundary is clear, later debugging gets much shorter.

قرار نیست همین اول وارد جزئیات JIT و GC بشیم. فعلاً فقط مرزها رو درست بچین: SDK برای ساخت و ابزارهای توسعه، runtime برای اجرا، Roslyn برای فهمیدن و کامپایل‌کردن C#، و CLR برای اجرای managed code و سرویس‌های runtime. فصل‌های جلوتر هرکدوم رو دوباره باز می‌کنن؛ اینجا نقشه رو می‌سازیم تا بعداً گم نشیم.

We are not diving into JIT or GC internals yet. The goal is to place the boundaries correctly: the SDK supplies build/development tooling, the runtime executes the program, Roslyn understands and compiles C#, and the CLR provides managed execution services. Later chapters will reopen each area; here we build the map so those details have somewhere to attach.

از فایل منبع تا کد ماشینFrom source to machine code

کامپایلر C# معمولاً فایل `.cs` رو مستقیم به دستورهای CPU همین لپ‌تاپ تبدیل نمی‌کنه. اول کد رو بررسی و خروجی میانی به‌همراه metadata تولید می‌کنه؛ runtime بقیهٔ مسیر رو می‌بره.

The C# compiler does not normally turn `.cs` directly into instructions for this laptop's CPU. It checks the code and emits intermediate output with metadata; the runtime continues the journey.

Roslyn که از راه SDK اجرا می‌شه، کد رو parse و type-check می‌کنه، خطا و warning می‌ده و assembly می‌سازه. assembly معمولاً IL و metadata داره: IL دستورهای میانیِ وابسته‌نبودن به یک CPU مشخص هست؛ metadata نوع‌ها و memberها رو توصیف می‌کنه. این portability نسبی هست، نه قول اجرای یکسان روی هر سیستم‌عامل؛ target framework و وابستگی native هنوز مهم‌اند.

Roslyn, invoked through the SDK, parses and type-checks code, reports errors and warnings, and creates an assembly. Assemblies commonly contain IL and metadata: IL is intermediate code not tied to one CPU, and metadata describes types and members. This is relative portability, not a promise of identical execution on every OS; target frameworks and native dependencies still matter.

در اجرای معمول، CLR و runtime assembly رو بار می‌کنن و سرویس‌هایی مثل مدیریت حافظه و exception رو فراهم می‌کنن. JIT متدهای لازم رو برای معماری فعلی به machine code تبدیل می‌کنه. ReadyToRun بخشی از کد رو برای target از قبل آماده می‌کنه؛ Native AOT مسیر انتشار native دیگری هست و محدودیت خودش رو داره. این‌ها انتخاب‌اند، نه مراحل اجباری هر پروژه.

In the common path, the CLR and runtime load assemblies and provide services such as memory management and exception handling. The JIT compiles needed methods to machine code for the current architecture. ReadyToRun precompiles some code for a target; Native AOT is another native publishing path with its own constraints. These are options, not mandatory stages.

managed یعنی رایگان؟ نه.Does managed mean free? No.

بیشتر C# managed هست و runtime بسیاری از عمر شیءها رو مدیریت می‌کنه. allocation، GC، I/O و lock همچنان هزینه دارن. کتابخانهٔ native یا `unsafe` هم مرز مالکیت حافظه و ABI رو وارد می‌کنه.

Most C# is managed, and the runtime manages much object lifetime. Allocations, GC, I/O and locks still cost something. Native libraries and `unsafe` code introduce memory-ownership and ABI boundaries.

اولین پروژه و چیزی که واقعاً ثابت می‌کنهThe first project and what it actually proves

اگه SDK 10 نصب هست، در پوشهٔ تازه اجرا کن. `dotnet new` قالب می‌سازه و `dotnet run` معمولاً restore، build و اجرا رو پشت‌سرهم انجام می‌ده.

If SDK 10 is installed, run this in a fresh folder. `dotnet new` creates a template; `dotnet run` commonly restores, builds and executes it.

terminal
dotnet new console --framework net10.0 --name OrderProbe
cd OrderProbe
dotnet run
representative output
Hello, World!

این خروجی ثابت می‌کنه همین برنامه در همین محیط اجرا شده؛ نه اینکه تست داره یا روی server دیگری بالا میاد. `dotnet restore` dependencyها رو resolve می‌کنه، `dotnet build` compile و هدف‌های build رو تمام می‌کنه، `dotnet test` تست‌های کشف‌شده رو اجرا می‌کنه و `dotnet publish` خروجی استقرار می‌سازه. هیچ‌کدوم جای دیگری رو نمی‌گیره.

This output proves the app ran in this environment—not that it has tests or starts on another server. `dotnet restore` resolves dependencies, `dotnet build` compiles and runs build targets, `dotnet test` executes discovered tests, and `dotnet publish` creates deployment output. None substitutes for another.

Debug و Release دو configuration هستن، نه دو runtime. معمولاً `obj` فایل‌های میانی و restore رو داره، `bin` خروجی build و `publish` خروجی مناسب تحویل رو. Release ممکنه بهینه‌سازی کند؛ دربارهٔ سرعت با benchmark نتیجه می‌گیریم، نه از اسم پوشه.

Debug and Release are configurations, not different runtimes. `obj` commonly holds intermediate and restore files, `bin` build output, and `publish` deployment output. Release may optimize code; use benchmarks—not folder names—to make performance claims.

پاسخ و دلیلSolution and reasoning
C#
int total;

Console.WriteLine(total);

CS0165 خطای compile-time در definite assignment هست. برنامه‌ای برای اجرا ساخته نشده، پس JIT دخیل نبوده. مقدارههی خطا رو رفع می‌کنه.

CS0165 is a compile-time definite-assignment error. No runnable program was produced, so the JIT was not involved. Initialization fixes the error.

برای بستن تمرین، خروجی یا test result رو نگه دار و یک بار نسخهٔ قبل و بعد رو کنار هم ببین. هدف فقط سبزشدن کد نیست؛ باید معلوم باشه کدوم رفتار واقعاً عوض شده.
