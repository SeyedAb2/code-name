قفل و primitiveهای همگام‌سازی

Locks and synchronization primitives

موجودی حساب منفی شده؛ هر درخواست جدا درست به نظر می‌رسد، اما دو برداشت هم‌زمان از یک موجودی قدیمی خوانده‌اند. فصل قبل race را دیدیم؛ حالا باید invariant را تعریف و ابزار متناسب انتخاب کنیم. lock برای انحصار یک بخش است، Interlocked برای تغییر اتمیک ساده، SemaphoreSlim برای ظرفیت یا gate ناهمگام—و هیچ‌کدام جای طراحی درست state را نمی‌گیرند.

An account balance went negative. Each request looked correct alone, but two concurrent withdrawals read the same old balance. We saw races last chapter; now we define the invariant and choose a matching primitive. A lock protects a critical section, Interlocked handles simple atomic updates, and SemaphoreSlim provides async gates or capacity—none replaces sound state design.

اول invariant، بعد lockDefine the invariant before the lock

قانون حساب این است: برداشت فقط وقتی انجام شود که موجودی کافی باشد و balance با ledger هماهنگ بماند. read-check-write باید یک واحد اتمیک از دید threadهای رقیب باشد. اگر lock فقط دور assignment باشد و check بیرون بماند، race هنوز هست. تمام stateهایی را که قانون به هم مرتبط می‌کند داخل همان critical section نگه دار.

The account rule is: withdraw only when funds are sufficient, and keep balance consistent with the ledger. Read-check-write must appear atomic to competing threads. Locking only the assignment while leaving the check outside preserves the race. Protect all state participating in one invariant within the same critical section.

قفل اختصاصی / Private lock
private readonly Lock _gate = new(); // .NET 9 / C# 13+
private decimal _balance;

public bool TryWithdraw(decimal amount)
{
    lock (_gate)
    {
        if (amount <= 0 || _balance < amount) return false;
        _balance -= amount;
        return true;
    }
}

در .NET 9 و C# 13، نوع اختصاصی System.Threading.Lock برای lock statement شناخته می‌شود. در targetهای قدیمی‌تر، یک object خصوصی و اختصاصی نگه دار؛ روی this، type یا string قفل نکن چون کد بیرونی هم ممکن است همان شیء را lock کند. lock در پایان scope حتی با exception آزاد می‌شود.

In .NET 9 and C# 13, the dedicated System.Threading.Lock type is recognized by the lock statement. On older targets, keep a private dedicated object. Do not lock this, a type or a string—external code might lock the same object. The lock is released at scope exit, including exceptions.

Interlocked برای یک تغییر ساده، نه invariant بزرگInterlocked for one simple update, not a large invariant

counter مستقل را با Interlocked.Increment به‌روز کن؛ compare-and-swap با CompareExchange امکان transition شرطی را می‌دهد. اما خواندن چند متغیر، validate کردنشان و نوشتن همه با چند Interlocked لزوماً transaction نمی‌شود. اگر invariant چندمرحله‌ای است، lock یا ساختار concurrent مناسب لازم است. volatile هم read-modify-write را atomic نمی‌کند.

Update an independent counter with Interlocked.Increment; compare-and-swap via CompareExchange enables conditional transitions. But reading, validating and updating several variables with multiple Interlocked calls does not create a transaction. Multi-step invariants need a lock or an appropriate concurrent structure. volatile does not make read-modify-write atomic.

transition شرطی / Conditional transition
int state = 0;
const int Ready = 0, Running = 1;

bool claimed = Interlocked.CompareExchange(
    ref state, Running, Ready) == Ready;

if (claimed) StartWork();

این نمونه transition از Ready به Running را اتمیک می‌کند. اگر چند فیلد دیگر باید با state همگام شوند، آن‌ها را بیرون این transition رها نکن. اگر کار بعد از claim fail می‌شود، transition برگشت و recovery را هم طراحی کن.

This atomically transitions Ready to Running. If other fields must remain consistent with state, do not leave them outside the transition. Define rollback/recovery if work fails after the claim.

SemaphoreSlim تعداد ورود را محدود می‌کندSemaphoreSlim bounds the number of entrants

lock حداکثر یک thread را داخل می‌برد؛ semaphore اجازهٔ تعداد مشخصی ورود می‌دهد. SemaphoreSlim برای داخل یک process است و WaitAsync می‌دهد تا منتظر permit ماندن thread را block نکند. هر Wait موفق باید دقیقاً یک Release داشته باشد؛ try/finally ضروری است. ترتیب FIFO تضمین نشده و semaphore thread/task مالک را enforce نمی‌کند.

A lock allows at most one thread inside; a semaphore permits a configured number. SemaphoreSlim is process-local and provides WaitAsync so waiting for a permit need not block a thread. Every successful wait requires exactly one release, so try/finally is essential. FIFO order is not guaranteed, and the semaphore does not enforce thread/task ownership.

gate ناهمگام / Async gate
private readonly SemaphoreSlim _gate = new(3, 3);

await _gate.WaitAsync(cancellationToken);
try
{
    await CallLimitedServiceAsync(cancellationToken);
}
finally
{
    _gate.Release();
}

ظرفیت ۳ یعنی حداکثر سه عملیات داخل gate، نه سه thread ثابت. semaphore را در lifetime سرویس نگه دار و هنگام shutdown پس از پایان waiterها dispose کن. اشتباه Release اضافه می‌تواند SemaphoreFullException بدهد؛ هر مسیر exception و cancellation را تست کن.

Capacity three means at most three operations inside the gate, not three dedicated threads. Keep the semaphore for the service lifetime and dispose only after waiters finish during shutdown. An extra Release can throw SemaphoreFullException; test exception and cancellation paths.

بن‌بست از چرخهٔ انتظار ساخته می‌شودDeadlocks emerge from wait cycles

اگر thread A قفل حساب اول را بگیرد و برای حساب دوم منتظر شود، و B برعکس، هر دو منتظر هم می‌مانند. برای چند lock، ترتیب سراسری و ثابت تعریف کن یا state را طوری مدل کن که هر بار یک lock کافی باشد. قفل را کوتاه نگه دار و network/file I/O را داخل lock انجام نده. lock در C# قابل await نیست؛ async coordination به primitive دیگری نیاز دارد.

If thread A locks account one then waits for account two while B does the reverse, both wait forever. Define one global lock order, or model state so one lock suffices. Keep critical sections short and never perform network/file I/O while holding a lock. C# does not allow await inside lock; asynchronous coordination needs another primitive.

ترتیب ثابت / Consistent order
object first = CompareIds(a.Id, b.Id) <= 0 ? a.Gate : b.Gate;
object second = ReferenceEquals(first, a.Gate) ? b.Gate : a.Gate;

lock (first)
lock (second)
{
    TransferWithoutAwait(a, b, amount);
}

هر دو طرف باید همان ترتیب را رعایت کنند؛ در کد واقعی identity مقایسه را پایدار تعریف کن. اگر انتقال به DB هم می‌رود، transaction دیتابیس مرز سازگاری durable را حل می‌کند؛ lock داخل process جای آن را نمی‌گیرد.

Every participant must follow the same order; define a stable identity comparison in real code. If transfers persist to a database, a database transaction protects durable consistency—an in-process lock does not.

ابزار را با نوع مسئله جفت کنMatch the primitive to the problem

lock برای critical section کوتاه synchronous؛ Interlocked برای یک primitive atomic؛ SemaphoreSlim برای حداکثر تعداد و انتظار async؛ Mutex وقتی واقعاً هماهنگی بین process لازم است؛ ReaderWriterLockSlim فقط وقتی نسبت read/write و اندازه‌گیری، پیچیدگی‌اش را توجیه کند. Concurrent collections دسترسی collection را امن می‌کنند، نه invariant برنامه را.

Use lock for a short synchronous critical section; Interlocked for one atomic primitive; SemaphoreSlim for bounded admission and async waits; Mutex only when cross-process coordination is required; and ReaderWriterLockSlim only when measured read/write patterns justify its complexity. Concurrent collections protect collection operations, not application invariants.

۱) برداشت هم‌زمان1) Concurrent withdrawals

دو برداشت از موجودی یکسان انجام و balance منفی می‌شود؛ check و update را اتمیک کن.

Two withdrawals read the same balance and make it negative; make check and update atomic.

پاسخ فنیTechnical reasoning

کل read-check-write را در یک lock اختصاصی بگذار یا transaction durable استفاده کن.

Protect the whole read-check-write in one private lock or use a durable transaction.

۲) شمارنده2) Counter

counter ساده با lock محافظت شده؛ نسخهٔ Interlocked را بساز و correctness را assert کن.

A simple counter uses a lock; implement Interlocked and assert correctness.

پاسخ فنیTechnical reasoning

Interlocked.Increment برای متغیر مستقل مناسب است و read-modify-write را atomic می‌کند.

Interlocked.Increment suits an independent variable and makes its update atomic.

۳) await در lock3) Await inside lock

کد داخل lock نیاز به I/O دارد؛ هماهنگی async را بازطراحی کن.

Code inside a lock needs I/O; redesign the asynchronous coordination.

پاسخ فنیTechnical reasoning

منطقهٔ داده را کوتاه lock و بیرونش I/O کن؛ اگر async gate لازم است SemaphoreSlim.WaitAsync بگیر.

Lock only the short state section and perform I/O outside; use SemaphoreSlim.WaitAsync for an async gate.

۴) release در exception4) Release after exception

کد permit را می‌گیرد و exception باعث گم‌شدنش می‌شود؛ مسیر را اصلاح کن.

An exception leaks a semaphore permit; repair the control flow.

پاسخ فنیTechnical reasoning

پس از WaitAsync موفق، عملیات را در try/finally قرار بده و دقیقاً یک Release انجام بده.

After successful WaitAsync, wrap work in try/finally and release exactly once.

۵) SemaphoreSlim ظرفیت5) SemaphoreSlim capacity

مقصد فقط چهار درخواست هم‌زمان می‌پذیرد؛ gate را بساز و سقف را verify کن.

A downstream service accepts only four concurrent calls; build and verify the gate.

پاسخ فنیTechnical reasoning

با capacity برابر چهار و WaitAsync/Release، بیشینهٔ فعال را با شمارندهٔ آزمایشی assert کن.

Use capacity four and WaitAsync/Release; assert maximum activity with a test counter.

۶) قفل روی this6) Locking this

کلاس روی this lock می‌کند؛ caller هم همان شیء را قفل می‌کند و hang رخ می‌دهد. repair کن.

A class locks this while a caller locks the same object, causing a hang. Fix it.

پاسخ فنیTechnical reasoning

روی شیء Lock خصوصی و اختصاصی lock کن تا کد بیرونی نتواند وارد synchronization شود.

Lock a private dedicated object that external code cannot use for synchronization.

۷) string lock7) Locking a string

دو component روی literal یکسان lock می‌کنند؛ خطر interning و repair را توضیح بده.

Two components lock the same literal; explain interning risk and repair.

پاسخ فنیTechnical reasoning

رشته‌ها intern می‌شوند و ممکن است ناخواسته مشترک باشند؛ از lock خصوصی اختصاصی استفاده کن.

Strings may be interned and accidentally shared; use a private dedicated lock object.

۸) deadlock دو قفل8) Two-lock deadlock

دو thread قفل‌ها را به ترتیب معکوس می‌گیرند؛ invariant ترتیب را برای هر دو برقرار کن.

Two threads acquire locks in reverse order; enforce one ordering invariant.

پاسخ فنیTechnical reasoning

ترتیب ثابت بر اساس شناسه اعمال کن یا state را طوری بازطراحی کن که هر دو lock لازم نباشند.

Order locks by a stable identifier or redesign state to avoid acquiring both.

۹) volatile counter9) Volatile counter

با volatile عدد را افزایش می‌دهند و گم می‌شود؛ توضیح و اصلاح ارائه کن.

A volatile counter loses increments; explain and repair it.

پاسخ فنیTechnical reasoning

volatile read/write ساده را تضمین می‌کند، نه عملیات ترکیبی؛ Interlocked یا lock لازم است.

Volatile governs simple reads/writes, not a compound update; use Interlocked or a lock.

۱۰) C# 13 Lock10) C# 13 Lock

کد target net8 دارد ولی System.Threading.Lock معرفی شده؛ نسخهٔ سازگار انتخاب کن.

Code targets net8 but uses System.Threading.Lock; choose a compatible target strategy.

پاسخ فنیTechnical reasoning

نوع ویژه با .NET 9 و C# 13 همراه است؛ برای target قدیمی‌تر object خصوصی استفاده یا target را عمداً ارتقا بده.

The special type is associated with .NET 9/C# 13; use a private object on older targets or upgrade deliberately.

۱۱) Mutex یا lock؟11) Mutex or lock?

دو process فایل مشترک را تغییر می‌دهند؛ ابزار داخل process کافی است؟

Two processes modify a shared file; is an in-process lock sufficient?

پاسخ فنیTechnical reasoning

lock/Monitor فقط threadهای همان process را هماهنگ می‌کند؛ برای بین process، Mutex یا قفل فایل/سرویس مناسب نیاز است.

lock/Monitor coordinates threads within one process; cross-process work needs a Mutex or suitable file/service lock.

۱۲) wait و cancellation12) Waiting with cancellation

WaitAsync بدون token است و shutdown طولانی می‌شود؛ لغو را تا gate عبور بده.

WaitAsync lacks a token and shutdown stalls; propagate cancellation to the gate.

پاسخ فنیTechnical reasoning

token را به WaitAsync(token) بده و اگر گرفتن permit موفق نشد Release انجام نده.

Pass the token to WaitAsync(token) and do not release if acquisition never succeeded.

۱۳) ReaderWriterLockSlim13) ReaderWriterLockSlim

هزینهٔ primitive پیشرفته را بدون اندازه‌گیری پذیرفته‌اند؛ workload read/write را بسنج.

An advanced primitive was added without evidence; measure the read/write workload.

پاسخ فنیTechnical reasoning

نسبت و مدت read/write، contention و starvation را benchmark کن؛ lock معمولی ممکن است ساده‌تر و کافی باشد.

Benchmark read/write ratio, duration, contention and starvation; a simple lock may be sufficient.

۱۴) collection امن، invariant ناامن14) Safe collection, unsafe invariant

ConcurrentDictionary استفاده می‌شود ولی check-then-add هنوز race دارد؛ عملیات ترکیبی را اتمیک کن.

ConcurrentDictionary is used, but check-then-add still races; make the compound operation atomic.

پاسخ فنیTechnical reasoning

از TryAdd/GetOrAdd یا factory امن استفاده کن؛ چند operation مستقل را یک transaction فرض نکن.

Use TryAdd/GetOrAdd or a safe factory; do not treat separate operations as one transaction.

۱۵) lock طولانی15) Long-held lock

داخل lock، فایل شبکه‌ای خوانده می‌شود؛ contention و lock duration را کم کن.

A network file is read inside a lock; reduce contention and lock duration.

پاسخ فنیTechnical reasoning

I/O را بیرون critical section انجام بده و فقط state انتقال را کوتاه lock کن؛ race جدید را تست کن.

Perform I/O outside the critical section and lock only the short state update; test for new races.

۱۶) reentrancy16) Reentrancy

callback کاربر هنگام lock فراخوانی و دوباره وارد component می‌شود؛ خطر را کاهش بده.

A user callback runs under a lock and re-enters the component; reduce the risk.

پاسخ فنیTechnical reasoning

callback خارجی را بیرون lock invoke کن؛ snapshot state را داخل lock بگیر و بیرون منتشر کن.

Invoke external callbacks outside the lock; snapshot state inside and publish it afterward.

۱۷) lock-disposal lifetime17) Lock/disposal lifetime

سرویس SemaphoreSlim را هنگام کار dispose می‌کند؛ shutdown و waiterها را هماهنگ کن.

A service disposes SemaphoreSlim while operations are active; coordinate shutdown and waiters.

پاسخ فنیTechnical reasoning

اول پذیرش کار جدید را ببند، cancellation بده، waiterها را await کن و بعد semaphore را dispose کن.

Stop new work, signal cancellation, await active waiters, then dispose the semaphore.

۱۸) رخداد موجودی منفی18) Negative-balance incident

حساب گاهی منفی می‌شود؛ race، lock scope، DB boundary و evidence لازم برای repair را گزارش کن.

An account sometimes goes negative; report race, lock scope, database boundary and repair evidence.

پاسخ فنیTechnical reasoning

check و update مشترک را در یک boundary اتمیک کن؛ برای چند process از transaction/optimistic concurrency DB استفاده و تست هم‌زمانی تکرارپذیر اجرا کن.

Make validation and update atomic; use a database transaction/optimistic concurrency across processes, then run a reproducible concurrency test.

آزمایشگاه: حساب با سقف برداشت هم‌زمانLab: an account with bounded withdrawals

یک مدل حساب با invariant «موجودی منفی نشود» بساز و ده‌ها برداشت کوچک هم‌زمان را از موجودی ثابت اجرا کن. نسخهٔ بدون محافظ را در تست deterministic با barrier و در محیط disposable بساز؛ نسخهٔ lock و نسخهٔ transaction DB را جدا مقایسه کن. شمار برداشت پذیرفته، ردشده و balance نهایی را assert کن. سپس یک API بیرونی کند را پشت SemaphoreSlim با ظرفیت مشخص بگذار؛ بیشترین عملیات فعال، cancellation هنگام انتظار و Release پس از exception را verify کن. lock را داخل network I/O نگه ندار.

Build an account enforcing nonnegative balance and run many concurrent small withdrawals against a fixed balance. Reproduce the unsafe version deterministically with a barrier in a disposable test; compare an in-memory lock with a database transaction. Assert accepted/rejected withdrawals and final balance. Then gate a slow external API with a bounded SemaphoreSlim; verify maximum active operations, cancellation while waiting and permit release after exceptions. Never hold a lock during network I/O.

  1. race را پیش از fix با test بازتولید کن.
  2. Reproduce the race before the fix.
  3. برای هر invariant بگو primitive چه چیزی را قفل می‌کند.
  4. State exactly what the primitive protects for each invariant.
  5. shutdown را حین operation و حین انتظار آزمایش کن.
  6. Test shutdown during both active work and waiting.

همگام‌سازی خوب، قانون state را واضح‌تر می‌کندGood synchronization clarifies state rules

lock یک بخش انحصاری است، Interlocked یک primitive را اتمیک می‌کند، semaphore ظرفیت را کنترل می‌کند و Mutex می‌تواند از مرز process عبور کند. انتخاب را invariant و lifetime تعیین می‌کند؛ نه این‌که کدام API اسم جذاب‌تری دارد. بعد از اطمینان از correctness می‌توان سرعت را سنجید. فصل بعد پردازش موازی با TPL را می‌سازیم و هزینهٔ تقسیم کار را از سود واقعی جدا می‌کنیم.

A lock makes a region exclusive, Interlocked makes one primitive update atomic, a semaphore controls capacity and a Mutex can cross process boundaries. The invariant and lifetime determine the choice, not the API with the flashiest name. Once correctness is established, measure speed. Next we use the TPL and separate partitioning costs from real gains.
