قفل و primitiveهای همگام‌سازی

Locks and synchronization primitives

موجودی حساب منفی شده؛ هر درخواست جدا درست به نظر می‌رسه، اما دو برداشت هم‌زمان از یک موجودی قدیمی خوانده‌اند. فصل قبل race رو دیدیم؛ حالا باید invariant رو تعریف و ابزار متناسب انتخاب کنیم. lock برای انحصار یک بخش هست، Interlocked برای تغییر اتمیک ساده، SemaphoreSlim برای ظرفیت یا gate ناهمگام—و هیچ‌کدوم جای طراحی درست state رو نمی‌گیرن.

An account balance went negative. Each request looked correct alone, but two concurrent withdrawals read the same old balance. We saw races last chapter; now we define the invariant and choose a matching primitive. A lock protects a critical section, Interlocked handles simple atomic updates, and SemaphoreSlim provides async gates or capacity—none replaces sound state design.

اول invariant، بعد lockDefine the invariant before the lock

قانون حساب این هست: برداشت فقط وقتی انجام بشه که موجودی کافی باشه و balance با ledger هماهنگ بماند. read-check-write باید یک واحد اتمیک از دید threadهای رقیب باشه. اگه lock فقط دور assignment باشه و check بیرون بماند، race هنوز هست. تمام stateهایی رو که قانون به هم مرتبط می‌کنه داخل همان critical section نگه دار.

The account rule is: withdraw only when funds are sufficient, and keep balance consistent with the ledger. Read-check-write must appear atomic to competing threads. Locking only the assignment while leaving the check outside preserves the race. Protect all state participating in one invariant within the same critical section.

قفل اختصاصی / Private lock
private readonly Lock _gate = new(); // .NET 9 / C# 13+
private decimal _balance;

public bool TryWithdraw(decimal amount)
{
    lock (_gate)
    {
        if (amount <= 0 || _balance < amount) return false;
        _balance -= amount;
        return true;
    }
}

در .NET 9 و C# 13، نوع اختصاصی System.Threading.Lock برای lock statement شناخته می‌شه. در targetهای قدیمی‌تر، یک object خصوصی و اختصاصی نگه دار؛ روی this، type یا string قفل نکن چون کد بیرونی هم ممکنه همان شیء رو lock کند. lock در پایان scope حتی با exception آزاد می‌شه.

In .NET 9 and C# 13, the dedicated System.Threading.Lock type is recognized by the lock statement. On older targets, keep a private dedicated object. Do not lock this, a type or a string—external code might lock the same object. The lock is released at scope exit, including exceptions.

lock باید از invariant محافظت کنه، نه فقط از یه خط کدA lock should protect an invariant, not just one line

اگه دو فیلد با هم یه state معتبر می‌سازن، lock فقط دور assignment اول کافی نیست. critical section باید همون مرزی رو بپوشونه که invariant رو حفظ می‌کنه. زیادی بزرگش کنی concurrency رو خفه می‌کنی؛ زیادی کوچیکش کنی correctness می‌ریزه. این trade-off رو با مثال واقعی می‌بینیم.

If two fields together form a valid state, locking only the first assignment is not enough. The critical section must cover the boundary that protects the invariant. Make it too large and concurrency collapses; make it too small and correctness does. We make that trade-off visible with real code.

`Interlocked` هم lock جادویی برای همه‌چیز نیست. برای عملیات atomic مشخص عالیه، ولی اگه تصمیم چندمرحله‌ای داری باید دوباره قرارداد کل state رو ببینی. ابزار رو از روی اندازهٔ مسئله انتخاب کن.

`Interlocked` is not a magical replacement for every lock either. It is excellent for specific atomic operations, but a multi-step decision still requires reasoning about the whole state contract. Choose the primitive from the invariant, not from fashion.

Interlocked برای یک تغییر ساده، نه invariant بزرگInterlocked for one simple update, not a large invariant

counter مستقل رو با Interlocked.Increment به‌روز کن؛ compare-and-swap با CompareExchange امکان transition شرطی رو می‌ده. اما خواندن چند متغیر، validate کردنشان و نوشتن همه با چند Interlocked لزوماً transaction نمی‌شه. اگه invariant چندمرحله‌ای هست، lock یا ساختار concurrent مناسب لازمه. volatile هم read-modify-write رو atomic نمی‌کنه.

Update an independent counter with Interlocked.Increment; compare-and-swap via CompareExchange enables conditional transitions. But reading, validating and updating several variables with multiple Interlocked calls does not create a transaction. Multi-step invariants need a lock or an appropriate concurrent structure. volatile does not make read-modify-write atomic.

transition شرطی / Conditional transition
int state = 0;
const int Ready = 0, Running = 1;

bool claimed = Interlocked.CompareExchange(
    ref state, Running, Ready) == Ready;

if (claimed) StartWork();

این نمونه transition از Ready به Running رو اتمیک می‌کنه. اگه چند فیلد دیگر باید با state همگام بشن، آن‌ها رو بیرون این transition رها نکن. اگه کار بعد از claim fail می‌شه، transition برگشت و recovery رو هم طراحی کن.

This atomically transitions Ready to Running. If other fields must remain consistent with state, do not leave them outside the transition. Define rollback/recovery if work fails after the claim.

SemaphoreSlim تعداد ورود رو محدود می‌کنهSemaphoreSlim bounds the number of entrants

lock حداکثر یک thread رو داخل می‌بره؛ semaphore اجازهٔ تعداد مشخصی ورود می‌ده. SemaphoreSlim برای داخل یک process هست و WaitAsync می‌ده تا منتظر permit ماندن thread رو block نکند. هر Wait موفق باید دقیقاً یک Release داشته باشه؛ try/finally ضروری هست. ترتیب FIFO تضمین نشده و semaphore thread/task مالک رو enforce نمی‌کنه.

A lock allows at most one thread inside; a semaphore permits a configured number. SemaphoreSlim is process-local and provides WaitAsync so waiting for a permit need not block a thread. Every successful wait requires exactly one release, so try/finally is essential. FIFO order is not guaranteed, and the semaphore does not enforce thread/task ownership.

gate ناهمگام / Async gate
private readonly SemaphoreSlim _gate = new(3, 3);

await _gate.WaitAsync(cancellationToken);
try
{
    await CallLimitedServiceAsync(cancellationToken);
}
finally
{
    _gate.Release();
}

ظرفیت ۳ یعنی حداکثر سه عملیات داخل gate، نه سه thread ثابت. semaphore رو در lifetime سرویس نگه دار و هنگام shutdown پس از پایان waiterها dispose کن. اشتباه Release اضافه می‌تونه SemaphoreFullException بدهد؛ هر مسیر exception و cancellation رو تست کن.

Capacity three means at most three operations inside the gate, not three dedicated threads. Keep the semaphore for the service lifetime and dispose only after waiters finish during shutdown. An extra Release can throw SemaphoreFullException; test exception and cancellation paths.

بن‌بست از چرخهٔ انتظار ساخته می‌شهDeadlocks emerge from wait cycles

اگه thread A قفل حساب اول رو بگیرد و برای حساب دوم منتظر بشه، و B برعکس، هر دو منتظر هم می‌مونن. برای چند lock، ترتیب سراسری و ثابت تعریف کن یا state رو طوری مدل کن که هر بار یک lock کافی باشه. قفل رو کوتاه نگه دار و network/file I/O رو داخل lock انجام نده. lock در C# قابل await نیست؛ async coordination به primitive دیگری نیاز داره.

If thread A locks account one then waits for account two while B does the reverse, both wait forever. Define one global lock order, or model state so one lock suffices. Keep critical sections short and never perform network/file I/O while holding a lock. C# does not allow await inside lock; asynchronous coordination needs another primitive.

ترتیب ثابت / Consistent order
object first = CompareIds(a.Id, b.Id) <= 0 ? a.Gate : b.Gate;
object second = ReferenceEquals(first, a.Gate) ? b.Gate : a.Gate;

lock (first)
lock (second)
{
    TransferWithoutAwait(a, b, amount);
}

هر دو طرف باید همان ترتیب رو رعایت کنند؛ در کد واقعی identity مقایسه رو پایدار تعریف کن. اگه انتقال به DB هم می‌ره، transaction دیتابیس مرز سازگاری durable رو حل می‌کنه؛ lock داخل process جای آن رو نمی‌گیره.

Every participant must follow the same order; define a stable identity comparison in real code. If transfers persist to a database, a database transaction protects durable consistency—an in-process lock does not.

ابزار رو با نوع مسئله جفت کنMatch the primitive to the problem

lock برای critical section کوتاه synchronous؛ Interlocked برای یک primitive atomic؛ SemaphoreSlim برای حداکثر تعداد و انتظار async؛ Mutex وقتی واقعاً هماهنگی بین process لازمه؛ ReaderWriterLockSlim فقط وقتی نسبت read/write و اندازه‌گیری، پیچیدگی‌اش رو توجیه کند. Concurrent collections دسترسی collection رو امن می‌کنن، نه invariant برنامه رو.

Use lock for a short synchronous critical section; Interlocked for one atomic primitive; SemaphoreSlim for bounded admission and async waits; Mutex only when cross-process coordination is required; and ReaderWriterLockSlim only when measured read/write patterns justify its complexity. Concurrent collections protect collection operations, not application invariants.
