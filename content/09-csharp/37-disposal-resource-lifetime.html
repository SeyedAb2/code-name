عمر منبع و IDisposable

Resource lifetime and IDisposable

پردازش فایل چند ساعت خوب کار می‌کنه، بعد خطای بازکردن فایل می‌ده؛ حتی فایل‌های قبلی هم باز مانده‌اند. GC حافظهٔ managed رو جمع می‌کنه، اما آیا می‌دونه handle فایل رو چه زمانی آزاد کند؟ این فصل مالکیت resource و پایان deterministic عمرش رو دنبال می‌کنه.

A file processor runs well for hours, then cannot open another file; previous files remain open. The GC reclaims managed memory, but does it know when to release a file handle? We trace resource ownership and deterministic cleanup.

GC حافظه رو می‌گیره؛ مالک resource باید آن رو ببنددThe GC reclaims memory; owners close resources

managed wrapper می‌تونه FileStream یا socket رو نگه داره، اما آزاد شدن حافظهٔ wrapper زمان آزاد شدن handle رو تضمین نمی‌کنه. IDisposable قراردادی برای cleanup صریح هست. سؤال اول همیشه این هست: چه کسی مالک resource هست؟ owner آن رو Dispose می‌کنه؛ کسی که فقط borrowed reference داره نباید بی‌اجازه ببندد.

A managed wrapper may hold a FileStream or socket, but reclaiming the wrapper does not promptly release the handle. IDisposable provides explicit cleanup. First ask who owns the resource: the owner disposes it; a borrower must not close it without contract.

using مسیر cleanup را می‌بندد / using scopes cleanup
using var stream = File.OpenRead(path);
var buffer = new byte[4096];
int read = stream.Read(buffer, 0, buffer.Length);
Console.WriteLine($"Read {read} bytes");

پایان scope به Dispose می‌رسه، حتی اگه خواندن exception بدهد. این command فقط یک خواندن رو ثابت می‌کنه؛ برای اثبات نشت‌نداشتن، مسیر خطا و تکرار بار رو هم آزمایش کن.

Leaving scope calls Dispose even if reading throws. One successful read does not prove absence of leaks; test failure paths and repeated load.

wrapper فقط resourceهای متعلق به خودش رو cascade می‌کنهA wrapper cascades only resources it owns

کلاسی که stream رو خودش می‌سازه و مالک آن هست باید آن رو dispose کند. متدی که stream رو از caller می‌گیره، معمولاً مالک نیست. قراردادهایی مانند leaveOpen یا overload جدا این مرز رو روشن می‌کنن. Dispose بهتره تکرارپذیر و امن طراحی بشه، اما این تضمین رو بی‌مدرک فرض نکن.

A class that creates and owns a stream disposes it. A method receiving a caller's stream is not necessarily its owner. A leaveOpen option or separate overload makes the boundary explicit. Design disposal to tolerate repetition, but do not assume that contract without evidence.

در کلاس قابل‌ارث‌بری، الگوی پایه/مشتق جزئیات داره؛ اغلب بهتره composition رو به inheritance ترجیح دهیم. اگه resource native داری، SafeHandle معمولاً از نوشتن finalizer دستی امن‌تر هست.

Inheritable base types need a more careful base/derived pattern; composition is often simpler. For native handles, SafeHandle is generally safer than writing a custom finalizer.

وقتی cleanup async هست، await using لازم می‌شهWhen cleanup is asynchronous, use await using

برخی resourceها cleanup ناهمگام دارن و IAsyncDisposable پیاده می‌کنن. await using پایان scope رو تا DisposeAsync منتظر می‌مونه. اگه cleanup خودش exception بدهد، باید روشن باشه exception اصلی و cleanup چطور log یا ترکیب می‌شن؛ finally بی‌حساب خطای اصلی رو پنهان نکند.

Some resources have asynchronous cleanup and implement IAsyncDisposable. await using waits for DisposeAsync at scope exit. Define how primary and cleanup failures are logged or combined; an indiscriminate finally must not hide the original error.

finalizer ساعت و تضمین cleanup نیستA finalizer is not a cleanup clock or guarantee

GC زمان اجرای finalizer رو تضمین نمی‌کنه و حتی ممکنه تا پایان process اجرا نشه. برای resourceهای managed، Dispose صریح کن. برای native handle معمولاً SafeHandle رو به‌کار ببر؛ finalizer دستی پیچیده هست و وقتی واقعاً لازم نباشه خطر اضافه می‌کنه. GC.Collect هم جای ownership و using رو نمی‌گیره.

The GC does not guarantee when a finalizer runs, and it may not run before process exit. Dispose managed resources explicitly. SafeHandle is usually the right wrapper for native handles; custom finalizers add risk when unnecessary. GC.Collect does not replace ownership or using.

Success criterion: execute both the successful path and at least one boundary/failure path, then explain the observed behaviour.

راهنماییHint

اگه رفتار به lifetime وابسته‌ست، زمان subscribe/capture/dispose رو صریح ثبت کن.

If behaviour depends on lifetime, record exactly when capture/subscription/disposal happens.

مسیر حلReasoning

Open a thousand files in a loop; compare process handle counts.

Dispose every resource and repeat the same experiment; the measurement is environment-dependent, so document its limits.

آخر کار یه بار از خودت بپرس این آزمایش دقیقاً چی رو ثابت کرد و چی رو نه. این عادت جلوی نتیجه‌گیری بزرگ از یه مثال کوچیک رو می‌گیره.

At the end, state exactly what this experiment proves and what it does not. That habit prevents broad conclusions from a tiny example.

Handle exhaustion incident

A service reaches its handle limit; trace resource ownership and prove the repair.

معیار موفقیت: مسیر موفق و حداقل یک مسیر مرزی/خراب رو اجرا کن و از روی رفتار برنامه توضیح بده چرا نتیجه درست یا غلطه.

Success criterion: execute both the successful path and at least one boundary/failure path, then explain the observed behaviour.

راهنماییHint

failure رو حذف نکن؛ همون exception، capture یا event lifetime می‌تونه بخش اصلی تمرین باشه.

Do not hide the failure; the exception, capture, or event lifetime may be the main evidence in the exercise.

مسیر حلReasoning

A service nears handle exhaustion; trace ownership and prove repair.

Use a profiler/handle count to find the allocation/opening site, add proper disposal, and repeat the load; GC.Collect is not the fix.

همون سناریو رو با یک حالت مرزی تکرار کن. اگه نتیجه متفاوت شد، به‌جای patch فوری اول مرز قراردادی که شکسته رو مشخص کن.

Repeat the scenario with a boundary case. If behaviour changes, identify the broken contract boundary before applying another patch.

آزمایشگاه: نشت فایل در پردازش دسته‌ایLab: a file leak in batch processing

نسخهٔ خراب، در حلقه برای هر ورودی فایل باز می‌کنه و با شرط زودهنگام از متد خارج می‌شه. تعداد فایل‌ها رو کم نگه دار؛ اول خطای handle رو بازتولید کن. سپس مالکیت رو مشخص، using رو اضافه و همان مسیر success و exception رو تست کن. در ویندوز، بازکردن/rename فایل پس از پایان scope شاهد مفیدی هست.

The broken version opens a file per input and exits early. Keep the fixture bounded; reproduce the handle issue, establish ownership, add using and test success and exception paths. On Windows, reopening or renaming after scope exit is useful evidence.

  1. baseline رو با ورودی محدود اجرا و handle/output رو ثبت کن.
  2. Run bounded baseline and record handles/output.
  3. استثنا رو در میانهٔ پردازش تزریق کن و cleanup رو بررسی کن.
  4. Inject a mid-processing exception and inspect cleanup.
  5. repair رو با همان تست‌ها ثابت و نتیجه رو گزارش کن.
  6. Prove the repair with the same tests and report results.

عمر resource رو به شانس GC نسپارDo not leave resource lifetime to GC timing

IDisposable پایان صریح عمر، IAsyncDisposable پایان ناهمگام، و SafeHandle مرز امن native handle رو می‌ده. owner رو پیدا کن، borrowed resource رو نبند و finalizer رو درمان عمومی ندان. حالا می‌تونیم فایل و stream رو به‌صورت واقعی پردازش کنیم، نه اینکه همه‌چیز رو بی‌محابا در حافظه بریزیم.

IDisposable provides deterministic cleanup, IAsyncDisposable asynchronous cleanup, and SafeHandle a safer native-handle boundary. Find the owner, do not close borrowed resources and do not treat finalizers as a general fix. Next we process files and streams without loading everything into memory.

اینجا لازم نیست همه‌چیز رو حفظ کرده باشی؛ مهم اینه که مدلش رو بتونی با یه مثال کوچیک دوباره بسازی. فصل بعد این مدل رو می‌بریم سراغ «فایل و Stream» و می‌بینیم همون تصمیم‌ها اونجا چه اثر تازه‌ای پیدا می‌کنن.

You do not need to memorize every detail here; you need to be able to rebuild the model with a small example. Next we carry it into “Files and streams” and see what new consequence appears there.
