عمر منبع و IDisposable

Resource lifetime and IDisposable

پردازش فایل چند ساعت خوب کار می‌کند، بعد خطای بازکردن فایل می‌دهد؛ حتی فایل‌های قبلی هم باز مانده‌اند. GC حافظهٔ managed را جمع می‌کند، اما آیا می‌داند handle فایل را چه زمانی آزاد کند؟ این فصل مالکیت resource و پایان deterministic عمرش را دنبال می‌کند.

A file processor runs well for hours, then cannot open another file; previous files remain open. The GC reclaims managed memory, but does it know when to release a file handle? We trace resource ownership and deterministic cleanup.

فصل ۳۶پیش‌نیازprerequisite

GC حافظه را می‌گیرد؛ مالک resource باید آن را ببنددThe GC reclaims memory; owners close resources

managed wrapper می‌تواند FileStream یا socket را نگه دارد، اما آزاد شدن حافظهٔ wrapper زمان آزاد شدن handle را تضمین نمی‌کند. IDisposable قراردادی برای cleanup صریح است. سؤال اول همیشه این است: چه کسی مالک resource است؟ owner آن را Dispose می‌کند؛ کسی که فقط borrowed reference دارد نباید بی‌اجازه ببندد.

A managed wrapper may hold a FileStream or socket, but reclaiming the wrapper does not promptly release the handle. IDisposable provides explicit cleanup. First ask who owns the resource: the owner disposes it; a borrower must not close it without contract.

using مسیر cleanup را می‌بندد / using scopes cleanup
using var stream = File.OpenRead(path);
var buffer = new byte[4096];
int read = stream.Read(buffer, 0, buffer.Length);
Console.WriteLine($"Read {read} bytes");

پایان scope به Dispose می‌رسد، حتی اگر خواندن exception بدهد. این command فقط یک خواندن را ثابت می‌کند؛ برای اثبات نشت‌نداشتن، مسیر خطا و تکرار بار را هم آزمایش کن.

Leaving scope calls Dispose even if reading throws. One successful read does not prove absence of leaks; test failure paths and repeated load.

wrapper فقط resourceهای متعلق به خودش را cascade می‌کندA wrapper cascades only resources it owns

کلاسی که stream را خودش می‌سازد و مالک آن است باید آن را dispose کند. متدی که stream را از caller می‌گیرد، معمولاً مالک نیست. قراردادهایی مانند leaveOpen یا overload جدا این مرز را روشن می‌کنند. Dispose بهتر است تکرارپذیر و امن طراحی شود، اما این تضمین را بی‌مدرک فرض نکن.

A class that creates and owns a stream disposes it. A method receiving a caller's stream is not necessarily its owner. A leaveOpen option or separate overload makes the boundary explicit. Design disposal to tolerate repetition, but do not assume that contract without evidence.

در کلاس قابل‌ارث‌بری، الگوی پایه/مشتق جزئیات دارد؛ اغلب بهتر است composition را به inheritance ترجیح دهیم. اگر resource native داری، SafeHandle معمولاً از نوشتن finalizer دستی امن‌تر است.

Inheritable base types need a more careful base/derived pattern; composition is often simpler. For native handles, SafeHandle is generally safer than writing a custom finalizer.

وقتی cleanup async است، await using لازم می‌شودWhen cleanup is asynchronous, use await using

برخی resourceها cleanup ناهمگام دارند و IAsyncDisposable پیاده می‌کنند. await using پایان scope را تا DisposeAsync منتظر می‌ماند. اگر cleanup خودش exception بدهد، باید روشن باشد exception اصلی و cleanup چگونه log یا ترکیب می‌شوند؛ finally بی‌حساب خطای اصلی را پنهان نکند.

Some resources have asynchronous cleanup and implement IAsyncDisposable. await using waits for DisposeAsync at scope exit. Define how primary and cleanup failures are logged or combined; an indiscriminate finally must not hide the original error.

finalizer ساعت و تضمین cleanup نیستA finalizer is not a cleanup clock or guarantee

GC زمان اجرای finalizer را تضمین نمی‌کند و حتی ممکن است تا پایان process اجرا نشود. برای resourceهای managed، Dispose صریح کن. برای native handle معمولاً SafeHandle را به‌کار ببر؛ finalizer دستی پیچیده است و وقتی واقعاً لازم نباشد خطر اضافه می‌کند. GC.Collect هم جای ownership و using را نمی‌گیرد.

The GC does not guarantee when a finalizer runs, and it may not run before process exit. Dispose managed resources explicitly. SafeHandle is usually the right wrapper for native handles; custom finalizers add risk when unnecessary. GC.Collect does not replace ownership or using.

عمر resource را به شانس GC نسپارDo not leave resource lifetime to GC timing

IDisposable پایان صریح عمر، IAsyncDisposable پایان ناهمگام، و SafeHandle مرز امن native handle را می‌دهد. owner را پیدا کن، borrowed resource را نبند و finalizer را درمان عمومی ندان. حالا می‌توانیم فایل و stream را به‌صورت واقعی پردازش کنیم، نه اینکه همه‌چیز را بی‌محابا در حافظه بریزیم.

IDisposable provides deterministic cleanup, IAsyncDisposable asynchronous cleanup, and SafeHandle a safer native-handle boundary. Find the owner, do not close borrowed resources and do not treat finalizers as a general fix. Next we process files and streams without loading everything into memory.
