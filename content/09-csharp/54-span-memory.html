Span، Memory و برش بدون کپی

Span, Memory and slicing without copies

parser لاگ برای هر خط سه substring می‌سازه؛ فایل بزرگ هست و allocationها جمع می‌شن. می‌خوایم بخشی از همان buffer رو موقت و امن بررسی کنیم، بی‌آن‌که string یا array تازه بسازیم. اما Span یک magic buffer نیست: view هست، مالک حافظه نیست و نمی‌تونه از هر مرزی عبور کند. این مرزها رو با compiler و اندازه‌گیری می‌بینیم.

A log parser creates three substrings per line; large files accumulate allocations. We want to inspect slices of the same buffer without new strings or arrays. But Span is not a magic buffer: it is a view, not an owner, and cannot cross every boundary. We examine those limits with the compiler and measurements.

Span یک view روی حافظهٔ contiguous استSpan is a view over contiguous memory

Span<T>/ReadOnlySpan<T> یک بازهٔ پیوسته رو با offset و length نمایش می‌ده؛ Slice معمولاً فقط view تازه می‌سازه و محتوا رو کپی نمی‌کنه. خود Span مالک buffer نیست و طول عمر backing memory رو تمدید نمی‌کنه. می‌تونه روی array، stack memory یا حافظهٔ unmanaged مجاز قرار بگیرد. برای ورودی که نباید تغییر کند، ReadOnlySpan انتخاب بهتره.

Span<T>/ReadOnlySpan<T> represents a contiguous region by offset and length; slicing generally creates another view without copying content. Span does not own the buffer or extend its lifetime. It can refer to an array, stack memory or valid unmanaged memory. Prefer ReadOnlySpan for input that must not be mutated.

parse با Slice / Parse with slices
ReadOnlySpan<char> line = "2026-10-04|WARN|disk low";
int first = line.IndexOf('|');
int secondRelative = line[(first + 1)..].IndexOf('|');
int second = first + 1 + secondRelative;

ReadOnlySpan<char> date = line[..first];
ReadOnlySpan<char> level = line[(first + 1)..second];
ReadOnlySpan<char> message = line[(second + 1)..];

sliceها زیررشتهٔ مستقل و immutable تولید نمی‌کنن؛ هنوز به buffer اصلی اشاره دارن. اگه باید message رو نگه داری و buffer بعداً reuse می‌شه، آن وقت copy/ToString عمدی لازمه. zero-copy تا لحظه‌ای خوب هست که lifetime و owner رو درست نگه داری.

Slices are not independent immutable strings; they still reference the original buffer. If the message must outlive a buffer that will be reused, an intentional copy/ToString is required. Zero-copy helps only when lifetime and ownership remain valid.

ref struct مرز escape رو کامپایلر enforce می‌کنهref struct enforces escape boundaries

Span<T> یک ref struct هست تا reference به stack memory از scope خارج نشه. پس نمی‌توان آن رو به field یک class تبدیل، box، داخل closure capture یا across await/yield نگه داشت. این محدودیت نقص نیست؛ راه جلوگیری از dangling reference هست. اگه buffer باید از async boundary رد بشه، Memory<T>/ReadOnlyMemory<T> رو به‌کار ببر.

Span<T> is a ref struct so references to stack memory cannot escape their valid scope. It cannot be stored in a class field, boxed, captured by a closure or kept across await/yield. This is a safety rule, not a flaw: it prevents dangling references. Use Memory<T>/ReadOnlyMemory<T> when a buffer must cross async boundaries.

Span موضعی / Local Span
static int ParseHeader(ReadOnlySpan<byte> bytes)
{
    // Synchronous, scoped view: no copy required.
    return BinaryPrimitives.ReadInt32BigEndian(bytes);
}

نسخه‌های جدید زبان ref safety رو گسترش داده‌اند، اما قواعد دقیق به target و language version وابسته هست؛ مثال‌های این فصل عمداً روی قاعدهٔ قابل‌حمل تکیه دارن: Span رو کوتاه و synchronous مصرف کن. compiler error رو با حفظ owner حل کن، نه با unsafe cast.

Newer language versions have expanded ref-safety rules, but exact capabilities depend on target and language version. These examples use the portable rule: consume Span briefly and synchronously. Fix compiler errors by preserving ownership, not by unsafe casts.

Memory view رو نگه می‌داره؛ owner رو باید بشناسیMemory can persist; ownership still matters

Memory<T> یک struct معمولی هست که می‌تونه در field یا متغیر async بماند؛ با .Span در بخش synchronous view می‌گیری. ولی Memory هم الزاماً owner نیست؛ ممکنه به array متعلق به کس دیگری اشاره کند. برای pool یا buffer اجاره‌ای، مالکیت رو با IMemoryOwner<T> یا قرارداد صریح نگه دار و پس از Dispose دیگر view رو مصرف نکن.

Memory<T> is an ordinary struct that can live in a field or across async work; access .Span for a synchronous view. But Memory is not necessarily the owner—it may reference somebody else’s array. For pooled or rented buffers, make ownership explicit with IMemoryOwner<T> or a documented contract, and never use views after disposal.

Memory در async API / Memory in an async API
static async Task ParseAsync(Memory<byte> buffer, CancellationToken ct)
{
    int count = await ReadIntoAsync(buffer, ct);
    ParseSynchronously(buffer.Span[..count]);
}

static int ParseSynchronously(Span<byte> bytes) => bytes.Length;

Memory در await می‌مونه، اما تضمین نمی‌کنه producer هم‌زمان همان array رو دست‌کاری نکند. برای concurrent use، ownership و synchronization همچنان لازمه. immutable بودن variable reference به معنای immutable بودن محتوا نیست.

Memory can survive an await, but it does not prevent another producer from mutating the same array concurrently. Ownership and synchronization remain necessary for concurrent use. An immutable reference variable does not make its contents immutable.

stackalloc کوچک، ثابت و بیرون loopKeep stackalloc small, bounded and outside loops

stackalloc فضای stack می‌گیره و GC لازم نداره؛ اما stack محدود هست و محتوا لزوماً صفرشده نیست. اندازه رو از ورودی نامحدود کاربر نگیر، در loop تکراری stack مصرف نکن و پیش از خواندن مقدارها رو initialize کن. اگه اندازه بزرگ یا متغیر هست، array یا pool مناسب‌تر هست.

stackalloc uses stack storage without GC allocation, but stacks are limited and contents are not necessarily zeroed. Do not size it from unbounded user input, repeatedly allocate inside loops or read before initialization. For larger or variable sizes, an array or pool is more appropriate.

اندازهٔ محدود / Bounded stack allocation
Span<byte> header = stackalloc byte[16];
header.Clear();
int written = EncodeHeader(header);
Send(header[..written]);

بهتره بافر یک بار در scope مناسب ساخته و reuse بشه. مقدار ۱۶ اینجا قرارداد header هست. stackalloc size رو صرفاً با «می‌دانم این ورودی معمولاً کوچک است» توجیه نکن؛ upper bound واقعی لازمه.

Allocate once in the appropriate scope and reuse. Sixteen bytes is the header contract here. Do not justify a stackalloc size with “this input is usually small”; enforce a real upper bound.

parser بدون substring؛ نه الزاماً سریع‌ترA parser without substrings is not automatically faster

با Span می‌توان delimiter رو پیدا و بخش‌ها رو مستقیم parse کرد؛ مثلاً int.TryParse(ReadOnlySpan<char>) از substring واسط بی‌نیاز هست. اما readability، Unicode، culture و مسیر خطا هنوز مهم‌اند. اگه parser تبدیل string به عدد یا allocation دیگری انجام می‌ده، یک Slice به تنهایی همهٔ allocationها رو حذف نمی‌کنه. نتیجه رو profiler و benchmark نشان می‌دن.

Span can locate delimiters and parse fields directly; for example, int.TryParse(ReadOnlySpan<char>) avoids an intermediate substring. Readability, Unicode, culture and failure paths still matter. If parsing allocates elsewhere, one slice does not eliminate every allocation. A profiler and benchmark reveal the actual result.
