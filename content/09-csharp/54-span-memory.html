Span، Memory و برش بدون کپی

Span, Memory and slicing without copies

parser لاگ برای هر خط سه substring می‌سازد؛ فایل بزرگ است و allocationها جمع می‌شوند. می‌خواهیم بخشی از همان buffer را موقت و امن بررسی کنیم، بی‌آن‌که string یا array تازه بسازیم. اما Span یک magic buffer نیست: view است، مالک حافظه نیست و نمی‌تواند از هر مرزی عبور کند. این مرزها را با compiler و اندازه‌گیری می‌بینیم.

A log parser creates three substrings per line; large files accumulate allocations. We want to inspect slices of the same buffer without new strings or arrays. But Span is not a magic buffer: it is a view, not an owner, and cannot cross every boundary. We examine those limits with the compiler and measurements.

Span یک view روی حافظهٔ contiguous استSpan is a view over contiguous memory

Span<T>/ReadOnlySpan<T> یک بازهٔ پیوسته را با offset و length نمایش می‌دهد؛ Slice معمولاً فقط view تازه می‌سازد و محتوا را کپی نمی‌کند. خود Span مالک buffer نیست و طول عمر backing memory را تمدید نمی‌کند. می‌تواند روی array، stack memory یا حافظهٔ unmanaged مجاز قرار بگیرد. برای ورودی که نباید تغییر کند، ReadOnlySpan انتخاب بهتر است.

Span<T>/ReadOnlySpan<T> represents a contiguous region by offset and length; slicing generally creates another view without copying content. Span does not own the buffer or extend its lifetime. It can refer to an array, stack memory or valid unmanaged memory. Prefer ReadOnlySpan for input that must not be mutated.

parse با Slice / Parse with slices
ReadOnlySpan<char> line = "2026-10-04|WARN|disk low";
int first = line.IndexOf('|');
int secondRelative = line[(first + 1)..].IndexOf('|');
int second = first + 1 + secondRelative;

ReadOnlySpan<char> date = line[..first];
ReadOnlySpan<char> level = line[(first + 1)..second];
ReadOnlySpan<char> message = line[(second + 1)..];

sliceها زیررشتهٔ مستقل و immutable تولید نمی‌کنند؛ هنوز به buffer اصلی اشاره دارند. اگر باید message را نگه داری و buffer بعداً reuse می‌شود، آن وقت copy/ToString عمدی لازم است. zero-copy تا لحظه‌ای خوب است که lifetime و owner را درست نگه داری.

Slices are not independent immutable strings; they still reference the original buffer. If the message must outlive a buffer that will be reused, an intentional copy/ToString is required. Zero-copy helps only when lifetime and ownership remain valid.

ref struct مرز escape را کامپایلر enforce می‌کندref struct enforces escape boundaries

Span<T> یک ref struct است تا reference به stack memory از scope خارج نشود. بنابراین نمی‌توان آن را به field یک class تبدیل، box، داخل closure capture یا across await/yield نگه داشت. این محدودیت نقص نیست؛ راه جلوگیری از dangling reference است. اگر buffer باید از async boundary رد شود، Memory<T>/ReadOnlyMemory<T> را به‌کار ببر.

Span<T> is a ref struct so references to stack memory cannot escape their valid scope. It cannot be stored in a class field, boxed, captured by a closure or kept across await/yield. This is a safety rule, not a flaw: it prevents dangling references. Use Memory<T>/ReadOnlyMemory<T> when a buffer must cross async boundaries.

Span موضعی / Local Span
static int ParseHeader(ReadOnlySpan<byte> bytes)
{
    // Synchronous, scoped view: no copy required.
    return BinaryPrimitives.ReadInt32BigEndian(bytes);
}

نسخه‌های جدید زبان ref safety را گسترش داده‌اند، اما قواعد دقیق به target و language version وابسته است؛ مثال‌های این فصل عمداً روی قاعدهٔ قابل‌حمل تکیه دارند: Span را کوتاه و synchronous مصرف کن. compiler error را با حفظ owner حل کن، نه با unsafe cast.

Newer language versions have expanded ref-safety rules, but exact capabilities depend on target and language version. These examples use the portable rule: consume Span briefly and synchronously. Fix compiler errors by preserving ownership, not by unsafe casts.

Memory view را نگه می‌دارد؛ owner را باید بشناسیMemory can persist; ownership still matters

Memory<T> یک struct معمولی است که می‌تواند در field یا متغیر async بماند؛ با .Span در بخش synchronous view می‌گیری. ولی Memory هم الزاماً owner نیست؛ ممکن است به array متعلق به کس دیگری اشاره کند. برای pool یا buffer اجاره‌ای، مالکیت را با IMemoryOwner<T> یا قرارداد صریح نگه دار و پس از Dispose دیگر view را مصرف نکن.

Memory<T> is an ordinary struct that can live in a field or across async work; access .Span for a synchronous view. But Memory is not necessarily the owner—it may reference somebody else’s array. For pooled or rented buffers, make ownership explicit with IMemoryOwner<T> or a documented contract, and never use views after disposal.

Memory در async API / Memory in an async API
static async Task ParseAsync(Memory<byte> buffer, CancellationToken ct)
{
    int count = await ReadIntoAsync(buffer, ct);
    ParseSynchronously(buffer.Span[..count]);
}

static int ParseSynchronously(Span<byte> bytes) => bytes.Length;

Memory در await می‌ماند، اما تضمین نمی‌کند producer هم‌زمان همان array را دست‌کاری نکند. برای concurrent use، ownership و synchronization همچنان لازم است. immutable بودن variable reference به معنای immutable بودن محتوا نیست.

Memory can survive an await, but it does not prevent another producer from mutating the same array concurrently. Ownership and synchronization remain necessary for concurrent use. An immutable reference variable does not make its contents immutable.

stackalloc کوچک، ثابت و بیرون loopKeep stackalloc small, bounded and outside loops

stackalloc فضای stack می‌گیرد و GC لازم ندارد؛ اما stack محدود است و محتوا لزوماً صفرشده نیست. اندازه را از ورودی نامحدود کاربر نگیر، در loop تکراری stack مصرف نکن و پیش از خواندن مقدارها را initialize کن. اگر اندازه بزرگ یا متغیر است، array یا pool مناسب‌تر است.

stackalloc uses stack storage without GC allocation, but stacks are limited and contents are not necessarily zeroed. Do not size it from unbounded user input, repeatedly allocate inside loops or read before initialization. For larger or variable sizes, an array or pool is more appropriate.

اندازهٔ محدود / Bounded stack allocation
Span<byte> header = stackalloc byte[16];
header.Clear();
int written = EncodeHeader(header);
Send(header[..written]);

بهتر است بافر یک بار در scope مناسب ساخته و reuse شود. مقدار ۱۶ اینجا قرارداد header است. stackalloc size را صرفاً با «می‌دانم این ورودی معمولاً کوچک است» توجیه نکن؛ upper bound واقعی لازم است.

Allocate once in the appropriate scope and reuse. Sixteen bytes is the header contract here. Do not justify a stackalloc size with “this input is usually small”; enforce a real upper bound.

parser بدون substring؛ نه الزاماً سریع‌ترA parser without substrings is not automatically faster

با Span می‌توان delimiter را پیدا و بخش‌ها را مستقیم parse کرد؛ مثلاً int.TryParse(ReadOnlySpan<char>) از substring واسط بی‌نیاز است. اما readability، Unicode، culture و مسیر خطا هنوز مهم‌اند. اگر parser تبدیل string به عدد یا allocation دیگری انجام می‌دهد، یک Slice به تنهایی همهٔ allocationها را حذف نمی‌کند. نتیجه را profiler و benchmark نشان می‌دهند.

Span can locate delimiters and parse fields directly; for example, int.TryParse(ReadOnlySpan<char>) avoids an intermediate substring. Readability, Unicode, culture and failure paths still matter. If parsing allocates elsewhere, one slice does not eliminate every allocation. A profiler and benchmark reveal the actual result.

logهای ذخیره‌شده رشته‌های یکسان اما محتوای متغیر دارند؛ aliasing و owner را بررسی و regression تست بساز.

Saved logs share a string-like view but show changing content; investigate aliasing/ownership and add a regression test.

پاسخ فنیTechnical reasoning

چند view به buffer reusable اشاره می‌کنند؛ هنگام persist کپی owned بساز یا owner را تا پایان نگه دار و عمر را تست کن.

Multiple views reference a reused buffer; make an owned copy when persisting or retain the owner, then test lifetime.

آزمایشگاه: parser رکورد کم‌تخصیصLab: a low-allocation record parser

یک parser برای خطوط جداشده با delimiter بساز: نسخهٔ Split و نسخهٔ ReadOnlySpan. inputهای سالم، field خالی، delimiter اضافه، Unicode و خط خیلی بلند داشته باش. هر دو نسخه باید نتیجهٔ یکسان بدهند؛ allocation/op، throughput و readability را ثبت کن. اگر reader async است، buffer را با Memory بگیر و Span را فقط پس از await در helper sync مصرف کن. عمداً buffer را reuse کن تا باگی که view را بیشتر از عمرش نگه می‌دارد بازتولید شود؛ سپس owner/copy را درست کن. stackalloc فقط برای header کوچک و ثابت باشد.

Build a delimiter-separated line parser using both Split and ReadOnlySpan. Test valid input, empty fields, extra delimiters, Unicode and very long lines. Both versions must return identical results; record allocations/op, throughput and readability. For an async reader, receive Memory and use Span only in a synchronous helper after await. Reuse a buffer deliberately to reproduce a view-lifetime bug, then fix ownership/copy. Use stackalloc only for a small fixed header.

Span کپی را کم می‌کند؛ مالکیت را حذف نمی‌کندSpan reduces copies; it does not remove ownership

Span یک view کوتاه‌عمر روی حافظهٔ پیوسته است؛ Memory آن view را برای async قابل‌حمل‌تر می‌کند، اما owner را خودش تضمین نمی‌کند. stackalloc کوچک و محدود است؛ pool هم lifecycle و Dispose می‌خواهد. هر optimization باید هم correctness و lifetime را نگه دارد هم با profiler توجیه شود. فصل بعد می‌رویم سراغ pooling و دنباله‌های بایت تا ببینیم reuse buffer کجا سود می‌دهد و کجا بدهی مالکیت می‌سازد.

Span is a short-lived view over contiguous memory; Memory makes that view usable across async boundaries but does not guarantee ownership. stackalloc is small and bounded; pools also require lifecycle and disposal. Optimizations must preserve correctness/lifetime and be justified by profiling. Next we examine pooling and byte sequences: where buffer reuse helps and where it creates ownership debt.
