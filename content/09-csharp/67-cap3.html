Project 3 — a high-throughput concurrent processor

یک importer فایل ورودی رو سریع‌تر از storage پردازش می‌کنه. نسخهٔ فعلی برای هر رکورد Task می‌سازه، queue محدود نداره و با Ctrl+C ممکنه نیمه‌کاره خارج بشه. این بار یک pipeline واقعی می‌سازی: ورودی، صف، workerها و sink. هدف «بیشترین تعداد نخ» نیست؛ throughput قابل‌اندازه‌گیری با حافظهٔ محدود، failure قابل‌گزارش و shutdown قابل‌اعتماد هست.

An importer reads input faster than storage can process it. The current version creates a Task per record, has no bounded queue and may exit halfway on Ctrl+C. Build a real pipeline with a producer, bounded queue, workers and sink. The goal is not “the most threads”; it is measurable throughput with bounded memory, visible failures and reliable shutdown.

مأموریت: ورودی رو با ظرفیت sink هماهنگ کنMission: match input rate to sink capacity

یک processor بساز که رکوردهای line-based رو از فایل می‌خونه، آن‌ها رو parse/validate می‌کنه، با تعداد worker محدود تبدیل می‌کنه و در خروجی می‌نویسه. pipeline باید ظرفیت queue مشخص داشته باشه، exception worker رو به coordinator برساند و با cancellation همهٔ Taskها رو جمع کند. خروجی می‌تونه ترتیب ورودی رو حفظ کند یا نه؛ تو انتخاب می‌کنی، اما contract رو روشن می‌نویسی و اگه ترتیب حفظ نمی‌شه، هر رکورد شناسهٔ پایدار داره.

Build a processor that reads line-based records, parses/validates them, transforms them with a bounded worker count and writes results. The queue has explicit capacity, worker exceptions reach the coordinator, and cancellation joins every Task. Output may preserve input order or not; choose and document the contract, and use stable record IDs if order is not preserved.

بار کنترل‌شده: فقط fixture ساختگی و حجم محدود. benchmark رو روی ماشین بیکار و dataset ثابت اجرا کن. هیچ loop بی‌نهایت، fork bomb یا فشار بدون حد روی host نساز.

Bounded load: use synthetic fixtures and finite workloads. Benchmark on an idle machine with fixed data. Never create an unbounded loop, fork bomb or host-wide resource pressure.

پیش از کدنویسی، قرارداد pipeline رو رسم کنDraw the pipeline contract before coding

وقتی queue پر می‌شه، producer باید منتظر بماند یا طبق policy رد کند؛ حافظه نباید نامحدود رشد کند. worker بیشتر ممکنه throughput رو کم کند اگه sink گلوگاه باشه. queue capacity، worker count و maximum input رو جدا و قابل‌تنظیم نگه دار.

When the queue fills, the producer waits or rejects according to policy; memory must not grow without bound. More workers can reduce throughput if the sink is the bottleneck. Keep queue capacity, worker count and maximum input independently bounded and configurable.

محدودیت‌های غیرقابل‌مذاکرهNon-negotiable constraints

  • Channel محدود با full mode انتخاب‌شده و مستند؛ کار مهم بی‌صدا drop نمی‌شه.
  • A bounded Channel with a documented full mode; important work is never silently dropped.
  • تعداد worker و ورودی finite هست؛ هیچ Task برای هر record بدون سقف ساخته نمی‌شه.
  • Worker count and input are finite; no unbounded task-per-record fan-out.
  • producer، consumer و sink cancellation token مناسب دارن.
  • Producer, consumers and sink receive appropriate cancellation tokens.
  • exception یک worker به coordinator می‌رسه و pipeline رو طبق policy متوقف/لغو می‌کنه.
  • Worker exceptions reach the coordinator, which stops/cancels the pipeline by policy.
  • shutdown طبیعی queue رو drain می‌کنه؛ shutdown ناشی از failure وضعیت partial رو گزارش می‌ده.
  • Normal shutdown drains the queue; failure shutdown reports partial progress.
  • pooling فقط بعد از benchmark نماینده و با ownership روشن مجاز هست.
  • Pooling is allowed only after representative benchmarks and with explicit ownership.

هشت مرحله تا processor قابل‌تحویلEight milestones to a deliverable processor

  1. Baseline همگام: نسخهٔ سادهٔ یک‌worker بنویس؛ correctness، throughput و allocation رو ثبت کن.
  2. Synchronous baseline: write a simple one-worker version and record correctness, throughput and allocation.
  3. قرارداد نتیجه: موفق، invalid record، cancellation و fatal failure رو از هم جدا کن.
  4. Result contract: distinguish success, invalid records, cancellation and fatal failures.
  5. Channel محدود: capacity کوچک انتخاب کن تا Wait و backpressure قابل مشاهده بشه.
  6. Bounded Channel: choose a small capacity so Wait/backpressure can be observed.
  7. چند worker: تعداد رو با پارامتر محدود کن؛ ترتیب خروجی رو آزمایش کن.
  8. Multiple workers: expose a bounded count and test output ordering.
  9. Failure propagation: consumer رو عمداً fault کن و producer منتظر رو آزاد کن.
  10. Failure propagation: fault a consumer deliberately and unblock any waiting producer.
  11. Shutdown: cancellation حین queue پر، drain طبیعی و timeout خاموش‌شدن رو بیازما.
  12. Shutdown: test cancellation with a full queue, normal draining and a bounded shutdown timeout.
  13. Benchmark: worker count، capacity و نسخهٔ pooled/unpooled رو با data ثابت مقایسه کن.
  14. Benchmark: compare worker count, capacity and pooled/unpooled variants using fixed data.
  15. Handoff: README، محدودیت memory، behavior order و نتایج قابل‌تکرار رو ارائه کن.
  16. Handoff: deliver README, memory bounds, ordering behavior and reproducible results.

قبولی یعنی failure هم قابل توضیح باشهAcceptance means failures are explainable too

  • در fixture ثابت، تعداد خروجی با policy invalid record برابر هست و duplicate/loss ناخواسته نداریم.
  • For fixed fixtures, output count matches invalid-record policy with no accidental duplicates or losses.
  • peak queued work از capacity تعریف‌شده بیشتر نمی‌شه؛ workerها هم سقف دارن.
  • Peak queued work stays within configured capacity, and worker count is bounded.
  • consumer fault باعث hang نمی‌شه؛ همهٔ producer/workerها در timeout مشخص پایان می‌یابند.
  • A consumer fault does not hang the process; all producers/workers finish within a defined timeout.
  • cancellation و shutdown طبیعی نتیجهٔ قابل‌تمایز و گزارش‌شده دارن.
  • Cancellation and graceful shutdown have distinct, reported outcomes.
  • benchmark هر run رو با OS، runtime، hardware، input و commit ثبت می‌کنه.
  • Each benchmark report records OS, runtime, hardware, input and commit.
  • اگه pool سرعت/GC رو بهبود نداده، حذف شده یا دلیل نگه‌داشتنش مستند هست.
  • If pooling does not improve speed/GC, remove it or document a justified reason to keep it.

خرابی‌های عمدی pipelineDeliberate pipeline failures

  • consumer متوقف: consumer رو pause کن و زمان WriteAsync رو بسنج؛ ثابت کن فشار به producer برمی‌گرده.
  • Paused consumer: pause a consumer and measure WriteAsync; prove pressure reaches the producer.
  • worker exception: یک رکورد marker باعث exception بشه؛ coordinator باید taskها رو cancel کند، نه اینکه process hang کند.
  • Worker exception: make a marker record throw; the coordinator must cancel tasks instead of hanging.
  • خطای sink: نوشتن خروجی رو fail کن؛ report partial رو با خروجی نهایی اشتباه نگیر.
  • Sink failure: fail output writing and distinguish partial progress from a complete result.
راهنما: owner تکمیل Channel کیست؟Hint: who owns channel completion?

یک coordinator پس از پایان producer یا بروز failure channel رو complete می‌کنه. workerها معمولاً نباید زودتر از بقیه writerها آن رو ببندند.

One coordinator completes the channel after producer completion or failure. Individual workers should not close it while other writers remain active.

pooling رو به‌عنوان فرضیه بررسی کنTreat pooling as a hypothesis

برای bufferهای کوچک و کوتاه‌عمر شاید pool پیچیدگی اضافه باشه. ابتدا baseline رو بگیر، بعد یک hot path رو انتخاب و allocation رو اندازه بگیر. اگه ArrayPool وارد شد، طول معتبر رو از capacity جدا نگه دار، Return رو در همهٔ مسیرها تضمین کن و پس از Return هیچ view رو مصرف نکن. اگه سود در workload نماینده تکرار نشد، حذفش کن. «zero-copy» یا allocation کمتر به‌تنهایی acceptance criterion نیست.

Pooling small short-lived buffers may add complexity without benefit. Establish a baseline, then measure allocation in one hot path. If using ArrayPool, track valid length separately from capacity, return on every path and never use a view afterward. Remove pooling if representative workloads do not show repeatable gains. “Zero-copy” or fewer allocations alone are not acceptance criteria.

راهنمایی مرحله‌ایStaged hints

راهنما ۱ — هر boundary یک owner دارهHint 1 — every boundary has an owner

producer کانال رو می‌نویسه؛ coordinator مالک lifecycle/completion هست؛ workerها فقط می‌خونن و نتیجه می‌نویسن.

The producer writes; the coordinator owns lifecycle/completion; workers consume and write results.

راهنما ۲ — همهٔ Taskها رو نگه دار و await کنHint 2 — retain and await every Task

Taskهای worker رو در collection محدود نگه دار. پس از failure، cancellation رو منتشر کن و همه رو join کن؛ fire-and-forget نکن.

Keep the bounded set of worker Tasks. On failure, propagate cancellation and join all of them; do not fire-and-forget.

راهنما ۳ — ترتیب و throughput دو contract جدا هستنHint 3 — order and throughput are separate contracts

چند worker completion رو reorder می‌کنن. اگه ترتیب مهمه، sequence number و reorder stage یا یک consumer رو انتخاب و هزینه‌اش رو اندازه بگیر.

Multiple workers reorder completion. If order matters, use sequence numbers and a reorder stage or one consumer, then measure the cost.

طرح مرجع pipeline در پایانReference pipeline at the end

  1. producer با await foreach یا stream bounded ورودی رو می‌خونه و با token به bounded Channel می‌نویسه.
  2. A producer reads through an async stream and writes to a bounded Channel with cancellation.
  3. worker count از config validate می‌شه و هر worker reader رو تا completion مصرف می‌کنه.
  4. Worker count is validated from configuration; each worker consumes until channel completion.
  5. Coordinator همهٔ worker taskها رو نگه می‌داره؛ producer پس از EOF channel رو complete می‌کنه.
  6. The coordinator tracks all workers; the producer completes the channel after EOF.
  7. اگه producer/worker fault شد، coordinator failure رو ثبت، token مشترک رو cancel و channel رو با exception complete می‌کنه.
  8. If producer/worker fails, the coordinator records it, cancels the shared token and completes the channel exceptionally.
  9. output writer یک owner داره تا interleaved writes یا corruption رخ ندهد؛ اگه چند worker به sink می‌نویسن، یک مرحلهٔ sink جدا بساز.
  10. One owner serializes output to avoid interleaving/corruption; use a separate sink stage when workers produce concurrently.
  11. shutdown طبیعی queue رو drain می‌کنه؛ failure mode تعداد موفق/ناموفق و path خروجی ناقص رو گزارش می‌کنه.
  12. Normal shutdown drains the queue; failure reports successful/failed counts and any partial-output path.
  13. benchmark baseline، bounded channel و pooling احتمالی رو در Release مقایسه می‌کنه؛ correctness قبل از timing تست شده.
  14. Release benchmarks compare baseline, bounded channel and any pooling variant after correctness tests pass.

این طرح نسخهٔ قطعی همهٔ برنامه‌ها نیست؛ transactionality، ترتیب، retry و durable queue به محصول بستگی دارن. در این پروژه claimهایی رو که پیاده نکرده‌ای—مثل exactly-once یا durability پس از crash—صریحاً رد کن.

This is not a universal architecture; transactionality, ordering, retries and durable queues depend on the product. Explicitly reject guarantees you did not implement, such as exactly-once or crash durability.

تحویل عملیاتی و جمع‌بندی دورهOperational handoff and course wrap-up

README باید ورودی نمونه، worker/capacity defaults، ترتیب خروجی، رفتار invalid record، cancel/failure و command benchmark رو ثبت کند. یک نفر دیگر باید بتواند از clean clone تست رو اجرا و pipeline رو با dataset محدود بازتولید کند. گزارش benchmark رو همراه شرایط اجرا بده و ادعای بیشتر از evidence نکن.

The README documents sample input, worker/capacity defaults, output order, invalid-record policy, cancellation/failure behavior and benchmark commands. Another person must be able to test from a clean clone and reproduce the pipeline on bounded data. Include benchmark conditions and make no claims beyond the evidence.
