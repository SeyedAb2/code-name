پروژهٔ ۳ — پردازشگر همروند پُربازده

Project 3 — a high-throughput concurrent processor

یک importer فایل ورودی را سریع‌تر از storage پردازش می‌کند. نسخهٔ فعلی برای هر رکورد Task می‌سازد، queue محدود ندارد و با Ctrl+C ممکن است نیمه‌کاره خارج شود. این بار یک pipeline واقعی می‌سازی: ورودی، صف، workerها و sink. هدف «بیشترین تعداد نخ» نیست؛ throughput قابل‌اندازه‌گیری با حافظهٔ محدود، failure قابل‌گزارش و shutdown قابل‌اعتماد است.

An importer reads input faster than storage can process it. The current version creates a Task per record, has no bounded queue and may exit halfway on Ctrl+C. Build a real pipeline with a producer, bounded queue, workers and sink. The goal is not “the most threads”; it is measurable throughput with bounded memory, visible failures and reliable shutdown.

مأموریت: ورودی را با ظرفیت sink هماهنگ کنMission: match input rate to sink capacity

یک processor بساز که رکوردهای line-based را از فایل می‌خواند، آن‌ها را parse/validate می‌کند، با تعداد worker محدود تبدیل می‌کند و در خروجی می‌نویسد. pipeline باید ظرفیت queue مشخص داشته باشد، exception worker را به coordinator برساند و با cancellation همهٔ Taskها را جمع کند. خروجی می‌تواند ترتیب ورودی را حفظ کند یا نه؛ تو انتخاب می‌کنی، اما contract را روشن می‌نویسی و اگر ترتیب حفظ نمی‌شود، هر رکورد شناسهٔ پایدار دارد.

Build a processor that reads line-based records, parses/validates them, transforms them with a bounded worker count and writes results. The queue has explicit capacity, worker exceptions reach the coordinator, and cancellation joins every Task. Output may preserve input order or not; choose and document the contract, and use stable record IDs if order is not preserved.

بار کنترل‌شده: فقط fixture ساختگی و حجم محدود. benchmark را روی ماشین بیکار و dataset ثابت اجرا کن. هیچ loop بی‌نهایت، fork bomb یا فشار بدون حد روی host نساز.

Bounded load: use synthetic fixtures and finite workloads. Benchmark on an idle machine with fixed data. Never create an unbounded loop, fork bomb or host-wide resource pressure.

پیش از کدنویسی، قرارداد pipeline را رسم کنDraw the pipeline contract before coding

وقتی queue پر می‌شود، producer باید منتظر بماند یا طبق policy رد کند؛ حافظه نباید نامحدود رشد کند. worker بیشتر ممکن است throughput را کم کند اگر sink گلوگاه باشد. queue capacity، worker count و maximum input را جدا و قابل‌تنظیم نگه دار.

When the queue fills, the producer waits or rejects according to policy; memory must not grow without bound. More workers can reduce throughput if the sink is the bottleneck. Keep queue capacity, worker count and maximum input independently bounded and configurable.

محدودیت‌های غیرقابل‌مذاکرهNon-negotiable constraints

  • Channel محدود با full mode انتخاب‌شده و مستند؛ کار مهم بی‌صدا drop نمی‌شود.
  • A bounded Channel with a documented full mode; important work is never silently dropped.
  • تعداد worker و ورودی finite است؛ هیچ Task برای هر record بدون سقف ساخته نمی‌شود.
  • Worker count and input are finite; no unbounded task-per-record fan-out.
  • producer، consumer و sink cancellation token مناسب دارند.
  • Producer, consumers and sink receive appropriate cancellation tokens.
  • exception یک worker به coordinator می‌رسد و pipeline را طبق policy متوقف/لغو می‌کند.
  • Worker exceptions reach the coordinator, which stops/cancels the pipeline by policy.
  • shutdown طبیعی queue را drain می‌کند؛ shutdown ناشی از failure وضعیت partial را گزارش می‌دهد.
  • Normal shutdown drains the queue; failure shutdown reports partial progress.
  • pooling فقط بعد از benchmark نماینده و با ownership روشن مجاز است.
  • Pooling is allowed only after representative benchmarks and with explicit ownership.

هشت مرحله تا processor قابل‌تحویلEight milestones to a deliverable processor

  1. Baseline همگام: نسخهٔ سادهٔ یک‌worker بنویس؛ correctness، throughput و allocation را ثبت کن.
  2. Synchronous baseline: write a simple one-worker version and record correctness, throughput and allocation.
  3. قرارداد نتیجه: موفق، invalid record، cancellation و fatal failure را از هم جدا کن.
  4. Result contract: distinguish success, invalid records, cancellation and fatal failures.
  5. Channel محدود: capacity کوچک انتخاب کن تا Wait و backpressure قابل مشاهده شود.
  6. Bounded Channel: choose a small capacity so Wait/backpressure can be observed.
  7. چند worker: تعداد را با پارامتر محدود کن؛ ترتیب خروجی را آزمایش کن.
  8. Multiple workers: expose a bounded count and test output ordering.
  9. Failure propagation: consumer را عمداً fault کن و producer منتظر را آزاد کن.
  10. Failure propagation: fault a consumer deliberately and unblock any waiting producer.
  11. Shutdown: cancellation حین queue پر، drain طبیعی و timeout خاموش‌شدن را بیازما.
  12. Shutdown: test cancellation with a full queue, normal draining and a bounded shutdown timeout.
  13. Benchmark: worker count، capacity و نسخهٔ pooled/unpooled را با data ثابت مقایسه کن.
  14. Benchmark: compare worker count, capacity and pooled/unpooled variants using fixed data.
  15. Handoff: README، محدودیت memory، behavior order و نتایج قابل‌تکرار را ارائه کن.
  16. Handoff: deliver README, memory bounds, ordering behavior and reproducible results.

قبولی یعنی failure هم قابل توضیح باشدAcceptance means failures are explainable too

  • در fixture ثابت، تعداد خروجی با policy invalid record برابر است و duplicate/loss ناخواسته نداریم.
  • For fixed fixtures, output count matches invalid-record policy with no accidental duplicates or losses.
  • peak queued work از capacity تعریف‌شده بیشتر نمی‌شود؛ workerها هم سقف دارند.
  • Peak queued work stays within configured capacity, and worker count is bounded.
  • consumer fault باعث hang نمی‌شود؛ همهٔ producer/workerها در timeout مشخص پایان می‌یابند.
  • A consumer fault does not hang the process; all producers/workers finish within a defined timeout.
  • cancellation و shutdown طبیعی نتیجهٔ قابل‌تمایز و گزارش‌شده دارند.
  • Cancellation and graceful shutdown have distinct, reported outcomes.
  • benchmark هر run را با OS، runtime، hardware، input و commit ثبت می‌کند.
  • Each benchmark report records OS, runtime, hardware, input and commit.
  • اگر pool سرعت/GC را بهبود نداده، حذف شده یا دلیل نگه‌داشتنش مستند است.
  • If pooling does not improve speed/GC, remove it or document a justified reason to keep it.

خرابی‌های عمدی pipelineDeliberate pipeline failures

  • consumer متوقف: consumer را pause کن و زمان WriteAsync را بسنج؛ ثابت کن فشار به producer برمی‌گردد.
  • Paused consumer: pause a consumer and measure WriteAsync; prove pressure reaches the producer.
  • worker exception: یک رکورد marker باعث exception شود؛ coordinator باید taskها را cancel کند، نه اینکه process hang کند.
  • Worker exception: make a marker record throw; the coordinator must cancel tasks instead of hanging.
  • خطای sink: نوشتن خروجی را fail کن؛ report partial را با خروجی نهایی اشتباه نگیر.
  • Sink failure: fail output writing and distinguish partial progress from a complete result.
راهنما: owner تکمیل Channel کیست؟Hint: who owns channel completion?

یک coordinator پس از پایان producer یا بروز failure channel را complete می‌کند. workerها معمولاً نباید زودتر از بقیه writerها آن را ببندند.

One coordinator completes the channel after producer completion or failure. Individual workers should not close it while other writers remain active.

pooling را به‌عنوان فرضیه بررسی کنTreat pooling as a hypothesis

برای bufferهای کوچک و کوتاه‌عمر شاید pool پیچیدگی اضافه باشد. ابتدا baseline را بگیر، بعد یک hot path را انتخاب و allocation را اندازه بگیر. اگر ArrayPool وارد شد، طول معتبر را از capacity جدا نگه دار، Return را در همهٔ مسیرها تضمین کن و پس از Return هیچ view را مصرف نکن. اگر سود در workload نماینده تکرار نشد، حذفش کن. «zero-copy» یا allocation کمتر به‌تنهایی acceptance criterion نیست.

Pooling small short-lived buffers may add complexity without benefit. Establish a baseline, then measure allocation in one hot path. If using ArrayPool, track valid length separately from capacity, return on every path and never use a view afterward. Remove pooling if representative workloads do not show repeatable gains. “Zero-copy” or fewer allocations alone are not acceptance criteria.

راهنمایی مرحله‌ایStaged hints

راهنما ۱ — هر boundary یک owner داردHint 1 — every boundary has an owner

producer کانال را می‌نویسد؛ coordinator مالک lifecycle/completion است؛ workerها فقط می‌خوانند و نتیجه می‌نویسند.

The producer writes; the coordinator owns lifecycle/completion; workers consume and write results.

راهنما ۲ — همهٔ Taskها را نگه دار و await کنHint 2 — retain and await every Task

Taskهای worker را در collection محدود نگه دار. پس از failure، cancellation را منتشر کن و همه را join کن؛ fire-and-forget نکن.

Keep the bounded set of worker Tasks. On failure, propagate cancellation and join all of them; do not fire-and-forget.

راهنما ۳ — ترتیب و throughput دو contract جدا هستندHint 3 — order and throughput are separate contracts

چند worker completion را reorder می‌کنند. اگر ترتیب مهم است، sequence number و reorder stage یا یک consumer را انتخاب و هزینه‌اش را اندازه بگیر.

Multiple workers reorder completion. If order matters, use sequence numbers and a reorder stage or one consumer, then measure the cost.

طرح مرجع pipeline در پایانReference pipeline at the end

  1. producer با await foreach یا stream bounded ورودی را می‌خواند و با token به bounded Channel می‌نویسد.
  2. A producer reads through an async stream and writes to a bounded Channel with cancellation.
  3. worker count از config validate می‌شود و هر worker reader را تا completion مصرف می‌کند.
  4. Worker count is validated from configuration; each worker consumes until channel completion.
  5. Coordinator همهٔ worker taskها را نگه می‌دارد؛ producer پس از EOF channel را complete می‌کند.
  6. The coordinator tracks all workers; the producer completes the channel after EOF.
  7. اگر producer/worker fault شد، coordinator failure را ثبت، token مشترک را cancel و channel را با exception complete می‌کند.
  8. If producer/worker fails, the coordinator records it, cancels the shared token and completes the channel exceptionally.
  9. output writer یک owner دارد تا interleaved writes یا corruption رخ ندهد؛ اگر چند worker به sink می‌نویسند، یک مرحلهٔ sink جدا بساز.
  10. One owner serializes output to avoid interleaving/corruption; use a separate sink stage when workers produce concurrently.
  11. shutdown طبیعی queue را drain می‌کند؛ failure mode تعداد موفق/ناموفق و path خروجی ناقص را گزارش می‌کند.
  12. Normal shutdown drains the queue; failure reports successful/failed counts and any partial-output path.
  13. benchmark baseline، bounded channel و pooling احتمالی را در Release مقایسه می‌کند؛ correctness قبل از timing تست شده.
  14. Release benchmarks compare baseline, bounded channel and any pooling variant after correctness tests pass.

این طرح نسخهٔ قطعی همهٔ برنامه‌ها نیست؛ transactionality، ترتیب، retry و durable queue به محصول بستگی دارند. در این پروژه claimهایی را که پیاده نکرده‌ای—مثل exactly-once یا durability پس از crash—صریحاً رد کن.

This is not a universal architecture; transactionality, ordering, retries and durable queues depend on the product. Explicitly reject guarantees you did not implement, such as exactly-once or crash durability.

تحویل عملیاتی و جمع‌بندی دورهOperational handoff and course wrap-up

README باید ورودی نمونه، worker/capacity defaults، ترتیب خروجی، رفتار invalid record، cancel/failure و command benchmark را ثبت کند. یک نفر دیگر باید بتواند از clean clone تست را اجرا و pipeline را با dataset محدود بازتولید کند. گزارش benchmark را همراه شرایط اجرا بده و ادعای بیشتر از evidence نکن.

The README documents sample input, worker/capacity defaults, output order, invalid-record policy, cancellation/failure behavior and benchmark commands. Another person must be able to test from a clean clone and reproduce the pipeline on bounded data. Include benchmark conditions and make no claims beyond the evidence.
