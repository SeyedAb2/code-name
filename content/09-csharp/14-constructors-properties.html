سازنده، property و مقداردهی

Constructors, properties and initialization

در فصل قبل Order ساختیم، اما هر caller می‌توانست سفارش ناقص بسازد یا تعدادش را منفی کند. حالا قانون را دقیق می‌کنیم: شیء از چه لحظه‌ای معتبر است و چه کسی اجازه دارد بعداً تغییرش دهد؟

شیء ساخته شد، اما آیا قابل استفاده است؟The object exists—but is it usable?

گزارش می‌گوید سفارشی با شمارهٔ خالی و یک قلم صفر ثبت شده. کد از نظر نحوی مشکلی نداشته: object ساخته شده و بعداً فیلدهایش تنظیم شده‌اند. مسئله این است که هیچ نقطه‌ای تضمین نکرده سفارش پیش از استفاده کامل باشد.

A report shows an order with an empty number and zero items. Nothing was syntactically wrong: the object was created and its fields were set later. No boundary guaranteed that the order was complete before use.

ساخت ناقص / Incomplete construction
var order = new Order();
order.Number = "";
order.ItemCount = 0;
SendToWarehouse(order);

constructor هنگام ساخته‌شدن نمونه اجرا می‌شود؛ پس جای مناسبی برای الزام داده‌های ضروری و برقرارکردن invariant اولیه است. property راه کنترل خواندن و نوشتن عضو است و object initializer فقط شکل نوشتن مقدارها را عوض می‌کند؛ خودش اعتبارسنجی یا اتمی‌بودن ایجاد نمی‌کند.

A constructor runs as an instance is created, making it a natural place to require essential data and establish initial invariants. A property controls access to a member; an object initializer changes syntax only—it does not validate or make initialization atomic.

ساختن باید قرارداد را کامل کندConstruction should establish the contract

شماره و تعداد برای سفارش ضروری‌اند. آن‌ها را در constructor بررسی می‌کنیم و فقط بعد از معتبر بودن ورودی‌ها state را مقدار می‌دهیم. fieldهای private جزئیات داخلی‌اند؛ caller با API عمومی کار می‌کند.

An order requires a number and positive quantity. Validate them in the constructor and assign state only after inputs pass. Private fields remain implementation details; callers use the public API.

قرارداد ساخت / Constructor contract
class Order
{
    private readonly string _number;
    private int _itemCount;
    public decimal UnitPrice { get; }

    public Order(string number, int itemCount, decimal unitPrice)
    {
        if (string.IsNullOrWhiteSpace(number))
            throw new ArgumentException("Order number is required.", nameof(number));
        if (itemCount <= 0)
            throw new ArgumentOutOfRangeException(nameof(itemCount));
        if (unitPrice < 0)
            throw new ArgumentOutOfRangeException(nameof(unitPrice));

        _number = number;
        _itemCount = itemCount;
        UnitPrice = unitPrice;
    }

    public string Number => _number;
    public int ItemCount => _itemCount;
    public decimal Total => _itemCount * UnitPrice;
}

new با ورودی نامعتبر شکست می‌خورد و caller نمی‌تواند field خصوصی را مستقیم تغییر دهد. readonly برای _number یعنی در کد عادی پس از مقداردهی مجاز، دوباره assignment نمی‌شود؛ این قاعدهٔ زبان است، نه مرز امنیتی در برابر reflection. شرط‌ها را از نیاز محصول بگیر، نه از حفظ‌کردن مثال.

Construction with invalid input fails, and callers cannot assign the private field directly. readonly means ordinary code cannot reassign _number after permitted initialization; it is a language rule, not a security boundary against reflection. Derive constraints from product requirements rather than memorising this example.

اگر چند constructor داریم، زنجیره‌کردن‌شان با this کمک می‌کند اعتبارسنجی فقط یک‌جا بماند. overload کوتاه باید به constructor اصلی برسد، نه اینکه نسخهٔ ناقص دیگری از همان قانون را کپی کند.

When a type has multiple constructors, chaining with this keeps validation in one place. A shorter overload should delegate to the primary constructor rather than duplicate a weaker version of the same rules.

زنجیرهٔ سازنده / Constructor chaining
public Order(string number) : this(number, itemCount: 1, unitPrice: 0m)
{
}

اینجا یک قلم و قیمت صفر فقط نمونه‌اند؛ اگر سفارش بدون قیمت مجاز نیست، این overload نباید ساخته شود. chaining ترتیب اجرای constructor مقصد را تضمین می‌کند، اما صحت انتخاب defaultها را نه.

One item and a zero price are illustrative defaults; if an order without a price is invalid, do not add this overload. Chaining invokes the target constructor, but it does not prove your defaults are correct.

مرزهای معتبر را هم تست کنTest valid boundaries too

شاید سفارش رایگان یا پیش‌سفارش با تعداد نامعلوم مجاز باشد. برای مقدارهای مرزیِ مجاز هم تست بنویس تا validation بیش‌ازحد، رفتار محصول را خراب نکند.

Free orders or pre-orders with an unknown quantity may be valid. Test allowed boundary values too, so over-validation does not break product behaviour.

property بخشی از API استA property is part of the API

property می‌تواند getter و setter داشته باشد یا فقط خواندنی باشد. setter آزاد برای state دارای invariant کافی نیست. متد تغییر، قاعده را اجرا می‌کند و property محاسباتی لازم نیست field دوم ذخیره کند.

A property may expose a getter and setter, or be read-only. An unrestricted setter is not enough for state with invariants. A mutation method enforces the rule, and a computed property need not store a second field.

تغییر کنترل‌شده / Controlled mutation
class Order
{
    private int _itemCount;
    public int ItemCount
    {
        get => _itemCount;
        private set
        {
            if (value <= 0)
                throw new ArgumentOutOfRangeException(nameof(value));
            _itemCount = value;
        }
    }

    public void AddItems(int count)
    {
        if (count <= 0)
            throw new ArgumentOutOfRangeException(nameof(count));
        ItemCount = checked(ItemCount + count);
    }
}

caller می‌تواند مقدار را بخواند اما فقط خود Order اجازهٔ set دارد. جمع checked است تا سرریز بی‌صدا state ظاهراً معتبری نسازد. سیاست تبدیل و rounding قیمت بیرونی هم باید در مرز دامنه روشن باشد.

Callers can read the value, but only Order can set it. The checked addition prevents silent overflow from creating plausible-looking state. Conversion and rounding policy for external prices must also be explicit at the domain boundary.

init و required دقیقاً چه تضمینی می‌دهند؟What do init and required actually guarantee?

برای شیء داده‌ای، initializer می‌تواند خوانا باشد. init اجازهٔ مقداردهی در constructor یا هنگام ساخت را می‌دهد و بعد از آن caller معمولی نمی‌تواند تغییرش دهد. required از compiler می‌خواهد عضو را هنگام ساخت مقداردهی کند؛ اما محتوای آن را اعتبارسنجی نمی‌کند.

For a data-oriented object, an initializer can be readable. init permits assignment in a constructor or during initialization, but ordinary callers cannot change it later. required asks the compiler to require an assignment at construction; it does not validate the content.

مقداردهی با required و init
class Shipment
{
    public required string TrackingCode { get; init; }
    public required DateOnly ShipDate { get; init; }
    public string? Note { get; init; }
}

var shipment = new Shipment
{
    TrackingCode = "TR-204",
    ShipDate = new DateOnly(2026, 10, 4),
    Note = "Handle with care"
};

رشتهٔ خالی هم برای compiler «مقداردهی شده» است؛ پس اگر خالی ممنوع است، runtime validation لازم است. نسخهٔ compiler و language version پروژه را هم بررسی کن؛ پروژهٔ قدیمی الزاماً این قابلیت‌ها را فعال ندارد.

An empty string still counts as “assigned” to the compiler; runtime validation is needed if it is invalid. Check the project’s compiler and language version: older projects may not support these features.

initializer تراکنش نیستAn initializer is not a transaction

propertyها یکی‌یکی مقدار می‌گیرند. اگر setter اول side effect بگذارد و setter بعدی exception بیندازد، اثر قبلی خودکار rollback نمی‌شود. برای invariant چندعضوی، constructor یا factoryای که کل ورودی را بررسی و بعد نمونهٔ معتبر بسازد معمولاً روشن‌تر است.

Properties are assigned one at a time. If one setter has a side effect and a later setter throws, the earlier effect is not automatically rolled back. For multi-member invariants, a constructor or factory that validates all input before producing a valid instance is often clearer.

گزینه‌های گزارش / Report options
class ReportOptions
{
    public required string OutputPath { get; init; }
    public int PageSize { get; init; } = 50;
    public bool IncludeArchived { get; init; }
}

var options = new ReportOptions
{
    OutputPath = "daily.csv",
    PageSize = 100
};

برای options ساده initializer خواناست؛ برای Order که قاعده و تغییر کنترل‌شده دارد، سازنده و متدهای دامنه معنای بیشتری می‌دهند. نقش نوع، انتخاب API را تعیین می‌کند.

An initializer is readable for simple options. For Order, with rules and controlled mutation, a constructor and domain methods express more meaning. The type’s role should drive API choice.

indexer وقتی نوع، مجموعه‌ای از عضوهای قابل‌اندیس استAn indexer when a type behaves like an indexed collection

property معمولاً یک مقدار نام‌دار را نشان می‌دهد؛ indexer دسترسی شبیه براکت را برای نوعی فراهم می‌کند که واقعاً مجموعهٔ عضوهاست. این syntax جایگزین validation نیست و نباید فقط برای کوتاه‌شدن کد اضافه شود.

A property usually exposes one named value; an indexer provides bracket-style access for a type that genuinely represents a collection. The syntax does not replace validation and should not be added merely to shorten code.

indexer روی ردیف‌های سفارش / Order lines
class OrderLines
{
    private readonly List<string> _items = [];

    public int Count => _items.Count;

    public string this[int index]
    {
        get => _items[index];
        set
        {
            if (string.IsNullOrWhiteSpace(value))
                throw new ArgumentException("Item name is required.", nameof(value));
            _items[index] = value;
        }
    }
}

استفاده شبیه `lines[0]` است؛ همان قواعد محدودهٔ List اعمال می‌شود و index نامعتبر خطا می‌دهد. چون setter اینجا نام خالی را هم رد می‌کند، indexer بخشی از قرارداد نوع است. اگر مصرف‌کننده به کنترل کامل مجموعه نیاز ندارد، APIهایی مثل افزودن/خواندن ممکن است شفاف‌تر باشند.

Usage looks like `lines[0]`; List’s bounds behaviour still applies, so an invalid index throws. This setter also rejects empty names, making the indexer part of the type’s contract. If callers do not need full collection control, explicit add/read methods may be clearer.

۱۴) initializer تراکنش نیست14) Initializers are not transactions

۱۶) incident شیء ناقص16) The incomplete-object incident

شیء معتبر را زود بساز و مرزش را حفظ کنCreate valid objects early and preserve their boundary

constructor state اولیه را معتبر می‌کند؛ property بخشی از API خواندن و تغییر است؛ init و required کمک زبانی‌اند، نه جایگزین validation دامنه. initializer برای دادهٔ ساده خواناست اما invariant چندعضوی را خودکار تضمین نمی‌کند. فصل بعد سطح دسترسی، static و readonly را برای شکل‌دادن API در مقیاس بزرگ‌تر بررسی می‌کنیم.

A constructor establishes valid initial state; properties form the read/mutation API; init and required are language features, not domain validation. Initializers are readable for simple data but do not enforce multi-member invariants. Next we use access levels, static and readonly to shape larger APIs.
