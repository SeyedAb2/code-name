استثنا و مرز خطا

Exceptions and failure boundaries

یک درخواست شکست می‌خورد؛ catch کلی آن را به «خطای نامعلوم» تبدیل می‌کند و stack trace هم از بین می‌رود. از همین رخداد یاد می‌گیریم کجا exception را بگیریم، کجا دوباره پرتاب کنیم و چه وقت خطا اصلاً exception نیست.

A request fails; a broad catch turns it into “unknown error” and loses the stack trace. This incident teaches where to catch, how to rethrow, and when a failure is not an exception.

exception برای exceptional pathExceptions for exceptional paths

استثنا را برای شکست غیرعادی به‌کار ببر، نه برای هر نتیجهٔ معمول مانند «یافت نشد». خطای ورودی قابل‌پیش‌بینی می‌تواند Result یا validation response باشد. catch را در مرزی بگذار که بتوانی تصمیم مفید بگیری؛ در غیر این صورت خطا را بالا بفرست.

Use exceptions for exceptional failures, not every normal outcome such as “not found.” Expected input failures may be Results or validation responses. Catch at a boundary where you can make a useful decision; otherwise propagate.

نمونه / Example
try
{
    await SaveAsync(order, cancellationToken);
}
catch (DbException ex) when (IsTransient(ex))
{
    logger.LogWarning(ex, "Temporary database failure");
    throw;
}

در مسیر موفق، خروجی متناسب با الگوی داده است؛ مسیر null، مرز و خطا را جدا تست کن. اجرای نمونه، کامل بودن مدل دامنه را به‌تنهایی ثابت نمی‌کند.

The successful path follows the data shape; test null, boundaries and failures separately. A sample run alone does not prove domain completeness.

نوع، inner و stack traceType, inner exception and stack trace

exception type و inner exception علت نزدیک/پایین‌دست را نشان می‌دهند. throw; stack trace را حفظ می‌کند؛ throw ex; محل پرتاب را از نو آغاز می‌کند. اگر abstraction خطا را wrap می‌کند، inner را نگه دار و context مفید اضافه کن.

Exception type and inner exception carry lower-level context. throw; preserves the stack trace; throw ex; restarts it. When wrapping, retain the inner exception and add useful context.

catch filterException filters

when filter اجازه می‌دهد فقط exceptionهایی را بگیری که واقعاً می‌توانی مدیریت کنی. filter false باشد، exception به catch بعدی یا caller می‌رسد. خطای transient را با خطای دائمی قاطی نکن؛ retry policy نیز باید محدود و cancellation-aware باشد.

A when filter catches only exceptions you can handle. If false, the exception continues to another catch or caller. Distinguish transient from permanent failure; retries must be bounded and cancellation-aware.

finally و cleanupFinally and cleanup

finally برای cleanup اجرا می‌شود، اما نباید failure اصلی را با exception تازه پنهان کند. برای resource از using/Dispose استفاده کن. log کردن و ادامه‌دادن بدون repair ممکن است برنامه را در state ناسازگار بگذارد.

finally is for cleanup, but must not hide the original failure with a new exception. Use using/Dispose for resources. Logging and continuing without repair may leave inconsistent state.

آزمایشگاه رخدادIncident lab

یک پروژهٔ کنسولی با ورودی کوچک بساز. baseline و تست رفتار را ثبت کن، failure را با تغییر کنترل‌شده بازتولید کن، مدرک را از نزدیک‌ترین مرز جمع کن و اصلاح را با همان acceptance test ثابت کن. در تحویل کد، خروجی و محدودیت چیزی را که نتیجه گرفته‌ای بنویس.

Create a console project with a small fixture. Record baseline tests, reproduce a failure with a controlled change, collect evidence at the nearest boundary and prove the repair with the same acceptance test. Submit code, output and limits of your conclusion.

  1. baseline و انتظار را ثبت کن.
  2. Record baseline and expected behaviour.
  3. failure و evidence را مستند کن.
  4. Document failure and evidence.
  5. repair و regression test را اجرا کن.
  6. Run the repair and regression test.
