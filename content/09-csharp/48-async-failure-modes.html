شکست‌های رایج async

Common async failure modes

کاربر دکمهٔ ذخیره را می‌زند، UI می‌ایستد؛ گاهی هم خطا اصلاً به catch نمی‌رسد. در backend، latency بالا رفته ولی CPU بیکار است: threadها با .Result منتظرند. این‌ها «async خراب است» نیست؛ مرزهای Task، thread و exception اشتباه استفاده شده‌اند. هر خطا را با آزمایش کوچک بازتولید می‌کنیم.

A user clicks Save and the UI freezes; sometimes an exception never reaches the expected catch. On the backend, latency rises while CPU is idle: threads are blocked on .Result. This does not mean “async is broken”; Task, thread and exception boundaries are being misused. We reproduce each failure with a small experiment.

sync-over-async: نخ منتظر Task می‌ماندSync-over-async blocks a thread on a Task

.Result و .Wait() انتظار را synchronous می‌کنند. در UI، نخ اصلی ممکن است context را نگه دارد درحالی‌که continuation می‌خواهد روی همان context برگردد؛ deadlock حاصل می‌شود. در ASP.NET Core معمولاً آن synchronization context قدیمی نیست، اما block کردن thread pool همچنان می‌تواند starvation و latency بسازد. نبود deadlock دلیل سالم‌بودن blocking نیست.

.Result and .Wait() make waiting synchronous. In UI apps, the main thread may hold a context while a continuation tries to return to it, causing deadlock. Typical ASP.NET Core code lacks that old synchronization context, but blocking thread-pool threads can still cause starvation and latency. Avoiding deadlock does not make blocking healthy.

رفع: async تا ریشه / Fix: async to the boundary
// Avoid:
Customer customer = LoadCustomerAsync(id).Result;

// Prefer:
Customer customer = await LoadCustomerAsync(id, cancellationToken);

متد فراخوان هم باید async و نتیجه‌اش Task باشد تا await به مرز event/HTTP برسد. ساخت یک sync wrapper روی عملیات async معمولاً همین مشکل را دوباره پنهان می‌کند؛ اگر واقعاً API sync لازم است، مسیر مستقل synchronous بساز یا مرز معماری را بازطراحی کن.

The caller must also become async so await reaches the event or HTTP boundary. A synchronous wrapper around asynchronous work usually hides the same problem again; if a truly synchronous API is required, provide a separate synchronous path or redesign the boundary.

async void تقریباً فقط برای event handlerasync void is almost only for event handlers

caller از متد async void نه Task می‌گیرد و نه می‌تواند await کند؛ exception هم به مسیر معمول Task برنمی‌گردد و completion قابل مشاهده نیست. eventهای .NET قدیمی گاهی signature را تحمیل می‌کنند؛ آن‌جا handler را adapter نازک نگه دار و منطق را به Task-returning method بسپار. همهٔ APIهای دیگر باید Task/Task<T> برگردانند.

A caller gets no Task from async void, cannot await completion, and cannot observe exceptions through the normal task path. Legacy .NET events sometimes require that signature; keep the handler as a thin adapter and move logic into a Task-returning method. Other async APIs should return Task or Task<T>.

adapter امن برای event / Safe event adapter
private async void SaveButton_Click(object? sender, EventArgs e)
{
    try
    {
        await SaveCoreAsync(_lifetime.Token);
    }
    catch (OperationCanceledException) when (_lifetime.IsCancellationRequested)
    {
        // Expected during shutdown.
    }
    catch (Exception ex)
    {
        logger.LogError(ex, "Save failed");
        ShowSaveError();
    }
}

private Task SaveCoreAsync(CancellationToken ct) => repository.SaveAsync(ct);

اینجا catch لازم است چون امضای event اجازهٔ تحویل Task نمی‌دهد؛ خطا را هم پنهان نکردیم و به UI گزارش دادیم. کد اصلی قابل‌آزمون باقی می‌ماند. برای eventهایی که API ناهمگام را می‌پذیرند، wrapper event را هم می‌توان Task-based طراحی کرد.

The catch is needed because the event signature cannot return a Task; failures are reported rather than hidden. Core logic remains testable. Where an event API supports asynchronous delegates, the adapter itself can also be Task-based.

Task را رها کنی، exception هم بی‌صاحب می‌شودAbandon a Task and its exception loses an owner

کد SaveAsync(); می‌زند و ادامه می‌دهد. اگر fault شود، caller نقطهٔ مشاهدهٔ خطا ندارد؛ تست هم ممکن است پیش از اتمام کار تمام شود. warning کامپایلر دربارهٔ await‌نشدن را جدی بگیر. اگر کار باید جداگانه اجرا شود، queue و worker مالک باید Task را await، log، retry-policy و shutdown را مدیریت کنند.

Code calls SaveAsync(); and moves on. If it faults, no caller observes the error; a test may also end before it completes. Take the unawaited-task compiler warning seriously. If work must run independently, a queue and worker should own the task, await it, log failures, apply retry policy and handle shutdown.

thread pool starvation شبیه کندی سرویس دیده می‌شودThread-pool starvation looks like a slow service

وقتی تعداد زیادی request نخ را با I/O synchronous، .Result یا lock انتظار می‌دهند، کارهای آمادهٔ ادامه هم نخ پیدا نمی‌کنند. ممکن است CPU پایین باشد چون نخ‌ها منتظرند؛ افزایش thread pool شاید نشانه را موقت جابه‌جا کند اما ریشه را حل نمی‌کند. stack trace، طول صف، تعداد thread و زمان انتظار را با هم ببین.

When many requests block threads on synchronous I/O, .Result or locks, ready continuations may have no threads to run on. CPU can be low because threads are waiting; increasing pool size may shift the symptom temporarily without fixing the cause. Correlate stack traces, queue length, thread count and wait time.

علت را در call stack پیدا کن / Find the cause in the call stack
// Suspect:
var body = client.GetStringAsync(uri).GetAwaiter().GetResult();

// Repair the call chain instead:
var body = await client.GetStringAsync(uri, cancellationToken);

GetAwaiter().GetResult() wrapper exception اضافی نمی‌سازد، اما همچنان thread را block می‌کند و deadlock/starvation را جادویی برطرف نمی‌کند. آن را نسخهٔ async یا درمان پیش‌فرض ندان.

GetAwaiter().GetResult() avoids an extra exception wrapper but still blocks a thread and does not magically fix deadlock or starvation. Do not treat it as the async alternative or default remedy.

ConfigureAwait را برای context واقعی انتخاب کنChoose ConfigureAwait for the actual context

ConfigureAwait(false) می‌گوید continuation لازم نیست به context گرفته‌شده برگردد. این برای کتابخانه‌ای که UI را لمس نمی‌کند می‌تواند وابستگی پنهان به context را حذف کند؛ اما application UI بعد از await ممکن است حتماً به UI thread نیاز داشته باشد. در ASP.NET Core عموماً context قدیمی وجود ندارد و افزودن false به همهٔ خط‌ها مشکل اساسی را درمان نمی‌کند.

ConfigureAwait(false) says the continuation need not return to the captured context. In a library that does not touch UI, it can remove an implicit context dependency; UI application code may need to resume on the UI thread. Typical ASP.NET Core apps do not use the old context, and adding false everywhere does not fix fundamental problems.

استثنا را دوبار نپیچ و دوباره نپرانDo not wrap and rethrow exceptions carelessly

await exception اصلی را در محل await ظاهر می‌کند. اگر آن را log و دوباره پرتاب می‌کنی، throw; stack trace را حفظ می‌کند؛ throw ex; مسیر را از همین نقطه شروع می‌کند. catch عمومی فقط برای افزودن context یا تبدیل آگاهانه به نتیجهٔ دامنه‌ای باشد، نه این‌که هر خطا را success یا خطای مبهم کند.

Await surfaces the original exception at the await point. If you log and rethrow, throw; preserves the stack trace; throw ex; resets it from that point. Catch broadly only to add context or deliberately map to a domain result, not to turn every failure into success or an opaque error.

۱) UI deadlock1) UI deadlock

روی UI context، async method را با .Result صدا بزن و hang را در پروژهٔ disposable بازتولید کن.

On a UI context, call an async method with .Result and reproduce the hang in a disposable project.

پاسخ فنیTechnical reasoning

thread UI مسدود و continuation منتظر بازگشت به همان context می‌شود؛ call chain را await کن.

The UI thread blocks while the continuation waits to return to that context; await through the call chain.

۲) ASP.NET Core و blocking2) Blocking in ASP.NET Core

در load محدود، sync-over-async را با نسخهٔ await مقایسه و threads/latency را ثبت کن.

Under bounded load, compare sync-over-async with await and record threads/latency.

پاسخ فنیTechnical reasoning

نبود context قدیمی deadlock را کم می‌کند ولی block، thread pool را مصرف و throughput را کاهش می‌دهد.

The lack of an old context reduces that deadlock pattern, but blocking still consumes pool threads and harms throughput.

۳) async void در service3) async void in a service

سرویس متدی async void دارد و caller نمی‌تواند await کند؛ API را به Task تبدیل کن.

A service exposes async void, so callers cannot await; convert its API to Task.

پاسخ فنیTechnical reasoning

متد service باید Task/Task<T> برگرداند؛ async void فقط adapter رویداد باشد.

A service method should return Task/Task<T>; reserve async void for event adapters.

۴) exception گم‌شده4) Lost exception

یک Task fault می‌شود ولی تست سبز است؛ مالک و assertion را پیدا کن.

A task faults but the test passes; identify ownership and add an assertion.

پاسخ فنیTechnical reasoning

Task را await کن تا exception وارد مسیر تست شود؛ task رهاشده قرارداد completion ندارد.

Await the task so its exception reaches the test; an abandoned task has no completion contract.

۵) ConfigureAwait در UI5) ConfigureAwait in UI

کد بعد از await کنترل را تغییر می‌دهد ولی context را capture نمی‌کند؛ thread را verify کن.

Code updates a control after await without capturing context; verify the thread.

پاسخ فنیTechnical reasoning

در UI از context لازم استفاده کن یا dispatcher را صریح صدا بزن؛ بعد از false فرض UI thread نکن.

Preserve the UI context or dispatch explicitly; do not assume UI-thread resumption after false.

۶) ConfigureAwait در library6) ConfigureAwait in a library

کتابخانهٔ مستقل به context caller وابسته شده؛ وابستگی را در تست contextدار آشکار کن.

A context-independent library accidentally depends on the caller context; expose it with a context-aware test.

پاسخ فنیTechnical reasoning

اگر library به context نیاز ندارد، awaitها را با ConfigureAwait(false) مستقل کن و contract را تست کن.

If the library needs no context, use ConfigureAwait(false) and test that contract.

۷) throw ex7) throw ex

stack trace فقط wrapper را نشان می‌دهد؛ مسیر واقعی را حفظ کن.

The stack trace shows only the wrapper; preserve the original path.

پاسخ فنیTechnical reasoning

از throw; استفاده کن؛ اگر context اضافه می‌کنی exception را inner exception قرار بده.

Use throw;; when adding context, retain the original as an inner exception.

۸) Task.Run برای HTTP8) Task.Run for HTTP

GetAsync داخل Task.Run است؛ هم‌زمانی و threadها را بررسی و wrapper را حذف کن.

GetAsync is inside Task.Run; inspect concurrency/threads and remove the wrapper.

پاسخ فنیTechnical reasoning

HTTP را مستقیم await کن؛ API خودش I/O asynchronous انجام می‌دهد.

Await HTTP directly; its API already performs asynchronous I/O.

۹) sync-over-async در constructor9) Sync-over-async in a constructor

constructor تنظیمات را از شبکه sync می‌گیرد؛ initialization را دوباره طراحی کن.

A constructor synchronously downloads configuration; redesign initialization.

پاسخ فنیTechnical reasoning

async factory یا مرحلهٔ initialization async بساز؛ constructor را کوتاه و هم‌زمان نگه دار.

Use an async factory or initialization phase; keep constructors short and synchronous.

۱۰) race در متغیر مشترک10) Shared-state race

دو task متغیر count را افزایش می‌دهند؛ await یعنی thread-safe؟ آزمایش و اصلاح کن.

Two tasks increment a shared count; does await make it thread-safe? Test and fix.

پاسخ فنیTechnical reasoning

async تضمین serialization نمی‌دهد؛ lock/Interlocked یا aggregation محلی و combine انتخاب کن.

Async does not serialize access; use a lock/Interlocked or local aggregation followed by combination.

۱۱) nested Task11) Nested Task

امضا Task<Task<T>> می‌دهد؛ بفهم چرا await یک‌بار کافی نیست و ساده‌اش کن.

A method returns Task<Task<T>>; explain why one await is insufficient and simplify it.

پاسخ فنیTechnical reasoning

delegateی که Task برمی‌گرداند را با Task.Run overload مناسب unwrap کن یا async lambda را اصلاح کن.

Use an unwrapping Task.Run overload or correct the async lambda shape.

۱۲) cancellation قورت‌داده‌شده12) Swallowed cancellation

catch عمومی OperationCanceledException را log می‌کند و ادامه می‌دهد؛ رفتار shutdown را درست کن.

A broad catch logs OperationCanceledException and continues; correct shutdown behavior.

پاسخ فنیTechnical reasoning

cancellation مورد انتظار را propagate/return کن و catch عمومی آن را failure عادی جلوه ندهد.

Propagate or return on expected cancellation; do not turn it into an ordinary failure.

۱۳) async در lock13) Await inside lock

کد تلاش می‌کند داخل lock await کند؛ مشکل compile و synchronization را رفع کن.

Code tries to await inside lock; fix compilation and synchronization design.

پاسخ فنیTechnical reasoning

برای بخش ناهمگام از SemaphoreSlim.WaitAsync و try/finally Release استفاده کن؛ critical section را کوتاه نگه دار.

Use SemaphoreSlim.WaitAsync with try/finally release for async coordination; keep the critical section short.

۱۴) async enumerable فراموش‌شده14) Forgotten async enumerable

IAsyncEnumerable را با foreach عادی مصرف می‌کنند؛ iteration و cancellation را اصلاح کن.

An IAsyncEnumerable is consumed with ordinary foreach; fix iteration and cancellation.

پاسخ فنیTechnical reasoning

از await foreach استفاده و token را با WithCancellation عبور بده.

Use await foreach and propagate cancellation with WithCancellation.

۱۵) test که زود تمام می‌شود15) A test that exits too early

تست background work را صدا می‌زند و بلافاصله سبز می‌شود؛ synchronization قابل‌آزمون اضافه کن.

A test starts background work and passes immediately; add testable synchronization.

پاسخ فنیTechnical reasoning

Task را از API برگردان و await کن یا signal completion کنترل‌شده بساز؛ sleep تصادفی نگذار.

Return and await the Task, or use a controlled completion signal; avoid arbitrary sleeps.

۱۶) incident کندی async16) Async-latency incident

CPU پایین است ولی درخواست‌ها صف شده‌اند؛ stack trace را برای blocking و continuation بخوان.

CPU is low while requests queue; inspect stacks for blocking and continuations.

پاسخ فنیTechnical reasoning

waitهای sync، thread pool starvation و I/O بدون cancellation را evidence بگیر؛ یک علت را اصلاح و زیر بار مقایسه کن.

Gather evidence for sync waits, thread-pool starvation and uncancelled I/O; fix one cause and compare under load.

آزمایشگاه: دو failure قابل‌بازتولیدLab: two reproducible failures

در یک پروژهٔ محلی و disposable، اول یک async API را با .Result از UI context صدا بزن و deadlock را با timeout آزمایش بازتولید کن؛ بعد همان flow را end-to-end await کن. دوم یک task رهاشده بساز که fault می‌شود و نشان بده تست پیش از آن تمام می‌شود؛ سپس ownership را به caller/worker بده و exception را observe کن. برای backend جداگانه sync-over-async را با load کوچک و کنترل‌شده بسنج؛ از فشار نامحدود یا sleepهای طولانی استفاده نکن. در هر آزمایش stack، thread، زمان و مسیر error را ثبت کن.

In a local disposable project, first call an async API with .Result from a UI context and reproduce the deadlock with a bounded test timeout; then await the flow end to end. Second, create an abandoned faulting task and show the test finishing early; then give ownership to a caller/worker and observe its exception. Separately compare backend sync-over-async under small, controlled load; avoid unbounded pressure or long sleeps. Record stacks, threads, duration and error path for each experiment.

اگر کسی Task را await نمی‌کند، بپرس مالک کار کیستIf no one awaits a Task, ask who owns the work

sync-over-async نخ را گرو می‌گیرد؛ async void مشاهدهٔ completion و خطا را می‌شکند؛ Task رهاشده owner ندارد؛ ConfigureAwait context لازم را تغییر می‌دهد اما جایگزین async end-to-end نیست. برای هر operation، مالک نتیجه، خطا، cancellation و cleanup را مشخص کن. فصل بعد ValueTask و جریان async را می‌بینیم؛ جایی که بهینه‌سازی تخصیص باید پس از شناخت قرارداد مصرف بیاید.

Sync-over-async blocks threads; async void hides completion and failures; an abandoned task has no owner; ConfigureAwait changes context behavior but does not replace end-to-end async. Define who owns each operation’s result, failures, cancellation and cleanup.
