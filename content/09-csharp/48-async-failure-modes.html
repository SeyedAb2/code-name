شکست‌های رایج async

Common async failure modes

کاربر دکمهٔ ذخیره رو می‌زنه، UI می‌ایستد؛ گاهی هم خطا اصلاً به catch نمی‌رسه. در backend، latency بالا رفته ولی CPU بیکار هست: threadها با .Result منتظرند. این‌ها «async خراب است» نیست؛ مرزهای Task، thread و exception اشتباه استفاده شده‌اند. هر خطا رو با آزمایش کوچک بازتولید می‌کنیم.

A user clicks Save and the UI freezes; sometimes an exception never reaches the expected catch. On the backend, latency rises while CPU is idle: threads are blocked on .Result. This does not mean “async is broken”; Task, thread and exception boundaries are being misused. We reproduce each failure with a small experiment.

sync-over-async: نخ منتظر Task می‌مونهSync-over-async blocks a thread on a Task

.Result و .Wait() انتظار رو synchronous می‌کنن. در UI، نخ اصلی ممکنه context رو نگه داره درحالی‌که continuation می‌خواد روی همان context برگردد؛ deadlock حاصل می‌شه. در ASP.NET Core معمولاً آن synchronization context قدیمی نیست، اما block کردن thread pool همچنان می‌تونه starvation و latency بسازد. نبود deadlock دلیل سالم‌بودن blocking نیست.

.Result and .Wait() make waiting synchronous. In UI apps, the main thread may hold a context while a continuation tries to return to it, causing deadlock. Typical ASP.NET Core code lacks that old synchronization context, but blocking thread-pool threads can still cause starvation and latency. Avoiding deadlock does not make blocking healthy.

رفع: async تا ریشه / Fix: async to the boundary
// Avoid:
Customer customer = LoadCustomerAsync(id).Result;

// Prefer:
Customer customer = await LoadCustomerAsync(id, cancellationToken);

متد فراخوان هم باید async و نتیجه‌اش Task باشه تا await به مرز event/HTTP برسد. ساخت یک sync wrapper روی عملیات async معمولاً همین مشکل رو دوباره پنهان می‌کنه؛ اگه واقعاً API sync لازمه، مسیر مستقل synchronous بساز یا مرز معماری رو بازطراحی کن.

The caller must also become async so await reaches the event or HTTP boundary. A synchronous wrapper around asynchronous work usually hides the same problem again; if a truly synchronous API is required, provide a separate synchronous path or redesign the boundary.

async void تقریباً فقط برای event handlerasync void is almost only for event handlers

caller از متد async void نه Task می‌گیره و نه می‌تونه await کند؛ exception هم به مسیر معمول Task برنمی‌گردد و completion قابل مشاهده نیست. eventهای .NET قدیمی گاهی signature رو تحمیل می‌کنن؛ آن‌جا handler رو adapter نازک نگه دار و منطق رو به Task-returning method بسپار. همهٔ APIهای دیگر باید Task/Task<T> برگردانند.

A caller gets no Task from async void, cannot await completion, and cannot observe exceptions through the normal task path. Legacy .NET events sometimes require that signature; keep the handler as a thin adapter and move logic into a Task-returning method. Other async APIs should return Task or Task<T>.

adapter امن برای event / Safe event adapter
private async void SaveButton_Click(object? sender, EventArgs e)
{
    try
    {
        await SaveCoreAsync(_lifetime.Token);
    }
    catch (OperationCanceledException) when (_lifetime.IsCancellationRequested)
    {
        // Expected during shutdown.
    }
    catch (Exception ex)
    {
        logger.LogError(ex, "Save failed");
        ShowSaveError();
    }
}

private Task SaveCoreAsync(CancellationToken ct) => repository.SaveAsync(ct);

اینجا catch لازمه چون امضای event اجازهٔ تحویل Task نمی‌ده؛ خطا رو هم پنهان نکردیم و به UI گزارش دادیم. کد اصلی قابل‌آزمون باقی می‌مونه. برای eventهایی که API ناهمگام رو می‌پذیرن، wrapper event رو هم می‌توان Task-based طراحی کرد.

The catch is needed because the event signature cannot return a Task; failures are reported rather than hidden. Core logic remains testable. Where an event API supports asynchronous delegates, the adapter itself can also be Task-based.

Task رو رها کنی، exception هم بی‌صاحب می‌شهAbandon a Task and its exception loses an owner

کد SaveAsync(); می‌زنه و ادامه می‌ده. اگه fault بشه، caller نقطهٔ مشاهدهٔ خطا نداره؛ تست هم ممکنه پیش از اتمام کار تمام بشه. warning کامپایلر دربارهٔ await‌نشدن رو جدی بگیر. اگه کار باید جداگانه اجرا بشه، queue و worker مالک باید Task رو await، log، retry-policy و shutdown رو مدیریت کنند.

Code calls SaveAsync(); and moves on. If it faults, no caller observes the error; a test may also end before it completes. Take the unawaited-task compiler warning seriously. If work must run independently, a queue and worker should own the task, await it, log failures, apply retry policy and handle shutdown.

thread pool starvation شبیه کندی سرویس دیده می‌شهThread-pool starvation looks like a slow service

وقتی تعداد زیادی request نخ رو با I/O synchronous، .Result یا lock انتظار می‌دن، کارهای آمادهٔ ادامه هم نخ پیدا نمی‌کنن. ممکنه CPU پایین باشه چون نخ‌ها منتظرند؛ افزایش thread pool شاید نشانه رو موقت جابه‌جا کند اما ریشه رو حل نمی‌کنه. stack trace، طول صف، تعداد thread و زمان انتظار رو با هم ببین.

When many requests block threads on synchronous I/O, .Result or locks, ready continuations may have no threads to run on. CPU can be low because threads are waiting; increasing pool size may shift the symptom temporarily without fixing the cause. Correlate stack traces, queue length, thread count and wait time.

علت را در call stack پیدا کن / Find the cause in the call stack
// Suspect:
var body = client.GetStringAsync(uri).GetAwaiter().GetResult();

// Repair the call chain instead:
var body = await client.GetStringAsync(uri, cancellationToken);

GetAwaiter().GetResult() wrapper exception اضافی نمی‌سازه، اما همچنان thread رو block می‌کنه و deadlock/starvation رو جادویی برطرف نمی‌کنه. آن رو نسخهٔ async یا درمان پیش‌فرض ندان.

GetAwaiter().GetResult() avoids an extra exception wrapper but still blocks a thread and does not magically fix deadlock or starvation. Do not treat it as the async alternative or default remedy.

ConfigureAwait رو برای context واقعی انتخاب کنChoose ConfigureAwait for the actual context

ConfigureAwait(false) می‌گه continuation لازم نیست به context گرفته‌شده برگردد. این برای کتابخانه‌ای که UI رو لمس نمی‌کنه می‌تونه وابستگی پنهان به context رو حذف کند؛ اما application UI بعد از await ممکنه حتماً به UI thread نیاز داشته باشه. در ASP.NET Core عموماً context قدیمی وجود نداره و افزودن false به همهٔ خط‌ها مشکل اساسی رو درمان نمی‌کنه.

ConfigureAwait(false) says the continuation need not return to the captured context. In a library that does not touch UI, it can remove an implicit context dependency; UI application code may need to resume on the UI thread. Typical ASP.NET Core apps do not use the old context, and adding false everywhere does not fix fundamental problems.

استثنا رو دوبار نپیچ و دوباره نپرانDo not wrap and rethrow exceptions carelessly

await exception اصلی رو در محل await ظاهر می‌کنه. اگه آن رو log و دوباره پرتاب می‌کنی، throw; stack trace رو حفظ می‌کنه؛ throw ex; مسیر رو از همین نقطه شروع می‌کنه. catch عمومی فقط برای افزودن context یا تبدیل آگاهانه به نتیجهٔ دامنه‌ای باشه، نه این‌که هر خطا رو success یا خطای مبهم کند.

Await surfaces the original exception at the await point. If you log and rethrow, throw; preserves the stack trace; throw ex; resets it from that point. Catch broadly only to add context or deliberately map to a domain result, not to turn every failure into success or an opaque error.
