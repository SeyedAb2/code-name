نوع‌های عددی و سرریز

Numeric types and overflow

قیمت ۲۹٫۹۹ هست، تعداد کالا ۳ هست و دما ۲۹٫۹۹ درجه. هر سه «عدد» هستن، اما یک نوع عددی برای هر سه انتخاب خوبی نیست. نوع داده بخشی از قرارداد محاسبه هست.

A price is 29.99, an item count is 3, and a temperature is 29.99 degrees. They are all numbers, but one numeric type is not ideal for all three. A type is part of a calculation's contract.

فصل ۴پیش‌نیازprerequisite

همهٔ عددها یک مسئله نیستنNot all numbers represent the same problem

برای تعداد سفارش معمولاً عدد صحیح می‌خوایم. برای پول، اعشار ده‌دهی و قاعدهٔ گردکردن مهمه. برای محاسبهٔ علمی، بازه و سرعت floating point ممکنه اولویت داشته باشه. قبل از انتخاب نوع، معنای داده رو مشخص کن.

Order counts are usually whole numbers. Money involves decimal quantities and explicit rounding. Scientific calculations may prioritize floating-point range and speed. Identify the meaning before choosing a type.

C#
int itemCount = 3;
decimal unitPrice = 29.99m;
decimal total = itemCount * unitPrice;
Console.WriteLine(total);
output
89.97

`int` برای شمارش مناسب هست؛ `decimal` برای مقدارهای اعشاری مالی معمولاً انتخاب مناسب‌تری از `float` و `double` هست. پسوند `m` لازمه تا literal از همان ابتدا decimal باشه. این انتخاب به‌تنهایی سیاست مالی نمی‌سازه: مالیات، نرخ، و گردکردن هر مرحله رو باید محصول تعریف کند.

`int` suits counting; `decimal` is commonly preferable to `float` or `double` for decimal financial quantities. The `m` suffix makes the literal decimal from the start. This choice does not define financial policy: the product must specify tax, rates and rounding at each step.

عدد فقط عدد نیست؛ قرارداد محاسبه‌ستA number is a computation contract

اگه قیمت، تعداد و دمای سنسور رو فقط «عدد» ببینی، دیر یا زود یه انتخاب نوع بد می‌کنی. این فصل رو با اسم typeها حفظ نکن. برای هر عدد بپرس: بازه چقدره؟ دقت چقدر مهمه؟ مقدار اعشاری باید دقیق ده‌دهی باشه یا تقریب دودویی مشکلی نداره؟ سرریز باید دیده بشه یا wrap شدن قابل‌قبوله؟ جواب این سؤال‌ها type مناسب رو خیلی طبیعی‌تر از جدول اندازهٔ بایت‌ها مشخص می‌کنه.

If price, item count, and sensor temperature are all just “numbers” to you, a poor type choice is inevitable. Do not memorize this chapter as a table of type names. Ask: what range is required, how much precision matters, whether decimal fractions must be represented exactly, and whether overflow should be visible. Those answers choose a type more reliably than byte-size trivia.

یه بخش مهم کار هم اینه که به خروجی عجیب اعتماد کور نکنیم. `0.1 + 0.2`، overflow و گردکردن رو اجرا می‌کنیم تا ببینیم ماشین چه قراردادی رو اجرا می‌کنه، نه قراردادی که تو ذهن ما بوده. بعد type رو از روی نیاز محصول انتخاب می‌کنیم.

An important habit is not trusting surprising output blindly. We run `0.1 + 0.2`, overflow, and rounding examples to see the contract the machine actually follows rather than the one we imagined, then choose types from product requirements.

چرا ۰٫۱ + ۰٫۲ دقیقاً ۰٫۳ نیست؟Why is 0.1 + 0.2 not exactly 0.3?

این آزمایش رو اجرا کن:

Run this experiment:

C#
double a = 0.1;
double b = 0.2;
Console.WriteLine(a + b == 0.3);
Console.WriteLine($"{a + b:R}");

معمولاً خط اول `False` هست. بسیاری از کسرهای ده‌دهی نمایش دودویی محدود ندارن؛ عدد ذخیره‌شده نزدیک‌ترین مقدار قابل نمایش هست، نه دقیقاً همان کسری که نوشته‌ای. قالب `R` نمایش round-trip رو نشان می‌ده. این رفتار خرابی محاسبه نیست؛ محدودیت نمایش floating point هست.

The first line is commonly `False`. Many decimal fractions have no finite binary representation, so the stored value is the nearest representable one, not the exact written fraction. The `R` format shows a round-trip representation. This is not a broken calculation; it is a floating-point representation limit.

برای مقایسهٔ اندازه‌گیری‌شده، گاهی tolerance مناسب لازمه؛ اما tolerance دلخواه هم سیاست هست و می‌تونه مقادیر متفاوت رو برابر فرض کند. برای مبلغی که باید با رقم اعشار مشخص نگهداری بشه، `decimal` رو بررسی کن. برای محاسبهٔ علمی یا گرافیکی، `double` به‌دلیل دامنه و کارایی مناسب هست. نوع رو از مسئله انتخاب کن.

Measured values may need an explicit tolerance, but an arbitrary tolerance is also a policy and can treat distinct values as equal. For amounts requiring decimal digits, consider `decimal`; for scientific or graphics calculations, `double` may fit its range and performance needs. Choose from the problem.

وقتی عدد از محدوده بیرون می‌زنهWhen a value exceeds its range

`int` بازهٔ محدودی داره. رفتار overflow برای محاسبهٔ integer معمولی معمولاً wraparound هست و exception خودکار نیست. وقتی سرریز باید به خطای قابل‌تشخیص تبدیل بشه، `checked` رو امتحان کن.

`int` has a finite range. Ordinary integer overflow commonly wraps and does not automatically throw. When overflow must become a detectable failure, use `checked`.

C#
int max = int.MaxValue;
Console.WriteLine(unchecked(max + 1));
Console.WriteLine(checked(max + 1));

خط اول بعد از wrap به `int.MinValue` می‌رسه؛ خط دوم `OverflowException` می‌ده. `checked` رو می‌توان روی expression یا block گذاشت. این تنظیم رو به همهٔ محاسبات کورکورانه نچسبان؛ نقطه‌ای رو انتخاب کن که overflow واقعاً نقض قرارداد باشه.

The first addition wraps to `int.MinValue`; the second throws `OverflowException`. `checked` can apply to an expression or block. Do not add it blindly everywhere; choose boundaries where overflow violates a real contract.

checked یک محافظ همه‌چیز نیستchecked is not a universal guard

باید رفتار عملگر و زمینه رو شناخت؛ overflow در integer با خطای دقت floating point یکی نیست. برای عددهای اعشاری، `checked` دقت رو بالا نمی‌بره و مسئلهٔ نمایش دودویی رو حل نمی‌کنه.

Know the operation and context: integer overflow is not the same as floating-point precision error. `checked` does not increase decimal precision or fix binary representation.

تبدیل نوع، گردکردن و ورودی کاربرConversions, rounding and user input

تبدیل از `double` به `int` ممکنه بخش اعشاری رو حذف کند؛ این همان گردکردن مالی نیست. برای parse متن از culture آگاه باش: نقطه و ویرگول اعشار در localeهای مختلف یکسان نیستن. در CLI و پروژه‌ها ورودی رو صریح اعتبارسنجی می‌کنیم.

Converting `double` to `int` can discard the fractional part; that is not a financial rounding policy. Parsing text is culture-sensitive: decimal separators differ across locales. We will validate input explicitly in the CLI project.

C#
double measurement = 12.8;
int truncated = (int)measurement;
decimal charge = 12.825m;
decimal rounded = Math.Round(charge, 2, MidpointRounding.AwayFromZero);
Console.WriteLine($"{truncated} / {rounded}");

این خروجی `12 / 12.83` هست. cast عدد رو truncate می‌کنه؛ `Math.Round` با policy صریح عمل می‌کنه. انتخاب midpoint strategy باید از قاعدهٔ domain بیاید، چون روش پیش‌فرض ممکنه با انتظارت از گردکردن مالی فرق داشته باشه.

This prints `12 / 12.83`. The cast truncates; `Math.Round` applies an explicit policy. The midpoint strategy should come from domain rules, because the default may differ from a financial rounding expectation.
