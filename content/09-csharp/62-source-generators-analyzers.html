source generator و analyzer

Source generators and analyzers

هر DTO باید mapping مشابهی داشته باشد و تیم هر هفته همان اشتباه را در کد تکرار می‌کند. reflection در startup می‌تواند mapping بسازد، اما هزینه و خطا تا runtime می‌ماند. analyzer می‌تواند هنگام نوشتن هشدار دهد و source generator بخشی از کد را پیش از اجرا به compilation اضافه کند. این ابزارها وقتی می‌ارزند که contract تکراری و قاعده روشن باشد؛ برای هر helper کوچک compiler plugin نسازیم.

Every DTO needs similar mapping, and the same mistake appears in code each week. Reflection can build mappings at startup, but cost and errors remain at runtime. An analyzer can warn while code is written, and a source generator can add code to the compilation before execution. These tools are worthwhile when contracts repeat and rules are clear—not for every tiny helper.

اول بفهم تکرار واقعاً از جنس تولید کد است یا نهFirst decide whether repetition is really a code-generation problem

کدی که از input مشخص و contract پایدار تولید می‌شود، نامزد generator است؛ مثل serializer، binding یا API boilerplate. اگر منطق business پیچیده و متغیر است، generator آن را قابل‌فهم‌تر نمی‌کند. اگر rule تخلف را می‌فهمد و فقط هشدار می‌دهد، analyzer مناسب است؛ اگر پیشنهاد تغییر syntax هم دارد، code fix جداگانه می‌سازیم. منبع حقیقت را در input/attribute/schema نگه دار و خروجی generated را به‌عنوان خروجی build ببین، نه فایل دست‌کاری‌شوندهٔ دستی.

Code derived from stable inputs and contracts may suit a generator—such as serializer, binding or API boilerplate. A generator does not make complex changing business logic clearer. Use an analyzer to detect and report a rule violation; add a separate code fix when an edit can be suggested. Keep the source of truth in inputs, attributes or schemas, and treat generated output as build output, not a hand-edited file.

generator کلاس موجود را rewrite نمی‌کند؛ source تازه به compilation اضافه می‌کند. اگر طراحی به بازنویسی syntax موجود نیاز دارد، analyzer/code fix یا refactoring را بررسی کن، نه اینکه از generator انتظار تغییر فایل کاربر را داشته باشی.

A generator does not rewrite an existing class; it adds new source to the compilation. If the design requires transforming existing syntax, consider an analyzer/code fix or refactoring rather than expecting a generator to edit user files.

generator افزایشی باید pure و قابل‌تکرار بماندAn incremental generator should remain pure and repeatable

پیاده‌سازی جدید معمولاً IIncrementalGenerator است. pipeline از syntax یا AdditionalFiles شروع می‌کند، ورودی relevant را فیلتر و به دادهٔ کوچک تبدیل می‌کند و در مرحلهٔ output کد می‌سازد. compiler ممکن است بخشی از pipeline را reuse کند؛ state mutable را در field generator نگه ندار، چون lifetime instance تضمین نیست. ورودی و خروجی deterministic باشند: یک compilation یکسان باید همان source را تولید کند.

Modern implementations commonly use IIncrementalGenerator. A pipeline starts from syntax or AdditionalFiles, filters relevant inputs, converts them into compact data and emits source at the output stage. The compiler may reuse pipeline stages; do not keep mutable state in generator fields because instance lifetime is not guaranteed. Inputs and outputs should be deterministic: the same compilation should produce the same source.

pipeline کوچک افزایشی / A small incremental pipeline
[Generator]
public sealed class ExportGenerator : IIncrementalGenerator
{
    public void Initialize(IncrementalGeneratorInitializationContext context)
    {
        var exports = context.SyntaxProvider
            .ForAttributeWithMetadataName(
                "Acme.ExportAttribute",
                static (node, _) => node is ClassDeclarationSyntax,
                static (ctx, ct) => ReadExport(ctx, ct))
            .Where(static item => item is not null);

        context.RegisterSourceOutput(exports,
            static (spc, item) => Emit(spc, item!));
    }
}

جزئیات typeهای ورودی و nullable را ساده کرده‌ایم؛ generator واقعی باید symbolهای semantic را resolve کند و diagnostic مناسب بدهد. syntax شبیه‌بودن کافی نیست: partial، generic، nested type، accessibility و namespace را لحاظ کن. از ForAttributeWithMetadataName در نسخهٔ Roslyn پشتیبانی‌شده استفاده کن و نسخهٔ analyzer package را با hostهای هدف هماهنگ کن.

Input and nullable details are abbreviated; a real generator must resolve semantic symbols and report diagnostics. Similar syntax is not enough: handle partial/generic/nested types, accessibility and namespaces. Use ForAttributeWithMetadataName only with a supported Roslyn version and align the analyzer package with its target hosts.

کد تولیدی باید معتبر، نام‌گذاری‌شده و قابل‌دیدن باشدGenerated code must be valid, uniquely named and inspectable

برای هر output یک hint name یکتا بساز؛ namespace و identifier را escape کن و ورودی کاربر را مستقیم به کد concatenate نکن. با SourceText.From و encoding مشخص source را به AddSource بده. اگر ورودی نامعتبر است، diagnostic با location مناسب گزارش کن و source ناقص تولید نکن. خروجی generated را در IDE/build مشاهده کن تا خطاهای generator از خطاهای کد دست‌نویس جدا شوند.

Give each output a unique hint name; escape namespaces and identifiers, and never concatenate raw user input into code. Pass source to AddSource with SourceText.From and an explicit encoding. For invalid input, report a diagnostic at a useful location and avoid emitting broken source. Inspect generated output in the IDE/build so generator errors are distinguishable from handwritten-code errors.

افزودن source و diagnostic / Add source and report a diagnostic
context.RegisterSourceOutput(exports, static (spc, item) =>
{
    if (item is null)
    {
        spc.ReportDiagnostic(Diagnostic.Create(
            InvalidExportRule, Location.None, "Export metadata is invalid."));
        return;
    }

    string hintName = $"{Sanitize(item.MetadataName)}.g.cs";
    spc.AddSource(hintName,
        SourceText.From(EmitCode(item), Encoding.UTF8));
});

نمونهٔ helperها را حذف کرده تا مرز API دیده شود. diagnostic ID باید پایدار و یکتا باشد، message قابل‌فهم داشته باشد و location تا حد ممکن به محل ورودی اشاره کند. generated code را با comment خودکار مشخص کن و warningهای generator را از error واقعی compilation پنهان نکن.

Helper implementations are omitted to show the API boundary. Diagnostic IDs must be stable and unique, messages understandable, and locations point to the input where possible. Mark generated code as auto-generated and do not hide generator warnings or real compilation errors.

analyzer syntax را می‌بیند و برای معنا سراغ symbol می‌رودAn analyzer inspects syntax and uses symbols for meaning

قاعدهٔ «هر متد public باید cancellation token را به عملیات async بدهد» فقط با syntax کامل نیست؛ باید call و overload انتخاب‌شده را semantic بررسی کرد. analyzerها باید سریع، thread-safe و cancellation-aware باشند. nodeهای مرتبط را register کن، generated code را در صورت نیاز نادیده بگیر، و در callbackهای پرتکرار I/O یا reflection سنگین انجام نده. diagnostic severity، category، title، message و help link را طوری تعریف کن که مصرف‌کننده بفهمد چه مشکلی دارد.

A rule such as “public async operations must propagate cancellation tokens” cannot rely on syntax alone; inspect the selected call and overload semantically. Analyzers should be fast, thread-safe and cancellation-aware. Register relevant nodes, skip generated code when appropriate, and avoid heavy I/O or reflection in frequent callbacks. Define diagnostic severity, category, title, message and help link so consumers understand the problem.

ثبت analyzer / Register an analyzer
[DiagnosticAnalyzer(LanguageNames.CSharp)]
public sealed class NoSyncWaitAnalyzer : DiagnosticAnalyzer
{
    public override ImmutableArray<DiagnosticDescriptor> SupportedDiagnostics
        => [Rule];

    public override void Initialize(AnalysisContext context)
    {
        context.ConfigureGeneratedCodeAnalysis(
            GeneratedCodeAnalysisFlags.None);
        context.EnableConcurrentExecution();
        context.RegisterSyntaxNodeAction(Analyze,
            SyntaxKind.SimpleMemberAccessExpression);
    }
}

نمونه فقط skeleton است؛ قاعدهٔ واقعی باید semantic model و cancellation token را در بررسی به کار ببرد و false positive ندهد. اگر analyzer concurrent است، collection mutable مشترک نساز. برای ruleهای پیکربندی‌پذیر از AnalyzerConfigOptions استفاده کن و defaultهای منطقی تعیین کن.

This is only a skeleton; a real rule should use the semantic model and cancellation token and avoid false positives. Do not use shared mutable collections in a concurrent analyzer. Use AnalyzerConfigOptions for configurable rules and provide sensible defaults.

code fix تغییر پیشنهادی را جدا از تشخیص نگه می‌داردA code fix separates the suggested edit from diagnosis

analyzer می‌گوید کجا rule نقض شده؛ code fix یک راه اصلاح قابل‌انتخاب در IDE پیشنهاد می‌دهد. هر diagnostic الزاماً fix امن ندارد. fix باید syntax tree جدید و document جدید برگرداند، trivia/commentها را حفظ کند و با cancellation کار کند. اگر چند اصلاح معتبر هست، گزینه‌ها را توضیح بده؛ اگر اصلاح ممکن است semantics را تغییر دهد، خودکار و بی‌توضیح اعمال نکن.

An analyzer reports where a rule is violated; a code fix offers an optional IDE correction. Not every diagnostic has a safe fix. A fix should return a new syntax tree/document, preserve trivia and comments, and honor cancellation. If several corrections are valid, explain the options; do not silently apply a fix that may change semantics.

ثبت یک code action / Register one code action
context.RegisterCodeFix(
    CodeAction.Create(
        title: "Use cancellation token",
        createChangedDocument: cancellationToken =>
            AddCancellationTokenAsync(
                context.Document, invocation, cancellationToken),
        equivalenceKey: "UseCancellationToken"),
    diagnostic);

وقتی چند diagnostic از یک node می‌آیند، fix باید diagnostic هدف را بر اساس span پیدا کند، نه اولین node مشابه در فایل. provider را به Diagnostic ID درست محدود کن. تحلیل و fix را هر دو با test harness بسنج: diagnostic expected، diagnostic absent و متن source پس از fix.

When several diagnostics occur in one node, locate the target by diagnostic span rather than selecting the first similar node in the file. Restrict the provider to the correct diagnostic ID. Test both analysis and fixes: expected diagnostics, absent diagnostics and the resulting source text.

compiler tool هم محصول است و test می‌خواهدCompiler tooling is a product and needs tests

برای generator، ورودی‌های معمول، partial، generic، ورودی نامعتبر و دو ورودی هم‌نام را اجرا کن و source تولیدشده را compile کن. برای analyzer، positive و negative case بنویس و code fix را دقیق مقایسه کن. snapshot golden کمک می‌کند خروجی تغییرکرده دیده شود، اما نباید compile و behavior را جایگزین کند. incremental behavior، determinism و cancellation هم بخشی از کیفیت generator هستند.

For a generator, test normal input, partial/generic declarations, invalid input and colliding names, then compile generated source. For an analyzer, test positive and negative cases and compare code-fix output exactly. Golden snapshots reveal output changes but do not replace compilation and behavior tests. Incremental behavior, determinism and cancellation are also part of generator quality.

اجرای تست tool / Run tool tests
dotnet test tests/CodeTools.Tests/CodeTools.Tests.csproj
dotnet build samples/Consumer/Consumer.csproj -c Release

# Inspect generated files when supported by the project:
dotnet build samples/Consumer/Consumer.csproj -c Release \
  -p:EmitCompilerGeneratedFiles=true

مسیر output generated و optionهای نمایش میان SDK/IDEها فرق دارد؛ فایل‌های generated را به‌اشتباه source دستی یا تغییر لازم در repository فرض نکن. generator package را با compiler hostهای مورد پشتیبانی آزمایش کن و سازگاری version Roslyn را مستند کن.

Generated-output paths and inspection options vary across SDKs and IDEs; do not mistake generated files for hand-maintained source or required repository edits. Test the generator package with supported compiler hosts and document Roslyn-version compatibility.

analyzer و generator را مثل dependency واقعی بسته‌بندی کنPackage analyzers and generators as real dependencies

مصرف‌کننده باید analyzer/generator را با نصب package دریافت کند، نه با copy/paste فایل DLL. analyzer package layout، target runtime و private assets با library عادی فرق دارد؛ از template و packaging راهنمای فعلی Roslyn/NuGet استفاده کن و خروجی package را بازبینی کن. مستند کن diagnosticها چطور پیکربندی یا suppress می‌شوند، generator چه ورودی‌هایی می‌خواند و package با کدام SDK/compiler test شده است.

Consumers should receive analyzers and generators by installing a package, not by copying a DLL. Analyzer package layout, runtime target and private assets differ from ordinary libraries; follow the current Roslyn/NuGet template and packaging guidance and inspect the package output. Document diagnostic configuration/suppression, generator inputs and the SDK/compiler versions tested.

آزمایشگاه: generator و analyzer کوچک تیمLab: a small team generator and analyzer

یک attribute برای command بساز و incremental generator بنویس که registry strongly typed تولید کند. ورودی‌های partial، generic، نام تکراری و metadata ناقص را وارد تست کن. خروجی generated باید در consumer compile شود و commandها را بدون reflection زمان اجرا dispatch کند. سپس analyzerی بساز که key خالی یا تکراری را با diagnostic پایدار گزارش دهد؛ برای key خالی code fix امن اضافه کن. diagnosticهای مثبت و منفی و متن دقیق پس از fix را تست کن. build را با generator package در CI اجرا، فایل generated را inspect و نسخهٔ compiler پشتیبانی‌شده را مستند کن. اگر rule بیش از boilerplate هزینه دارد، دلیل نگه‌داشتنش را در README بنویس.

Create a command attribute and an incremental generator that emits a strongly typed registry. Test partial/generic inputs, duplicate names and incomplete metadata. The generated output must compile in a consumer and dispatch commands without runtime reflection. Then build an analyzer that reports empty or duplicate keys with stable diagnostics; add a safe fix for empty keys. Test positive/negative diagnostics and exact post-fix source. Run the package in CI, inspect generated files and document supported compiler versions. If the rule costs more than the boilerplate, justify keeping it in the README.

compiler extension وقتی می‌ارزد که قرارداد تکرار می‌شودCompiler extensions pay off when a contract repeats

generator کد تازه به compilation می‌دهد؛ analyzer rule را گزارش می‌کند؛ code fix تغییر انتخابی می‌سازد. pipeline افزایشی باید deterministic، cancellation-aware و بی‌state mutable باقی بماند. ابزارها خودشان محصولند و به test، package، version compatibility و CI نیاز دارند. فصل بعد سراغ رمزنگاری می‌رویم؛ آن‌جا دیگر «به نظر امن» کافی نیست و باید primitive مناسب مسئله را انتخاب کنیم.

A generator adds source to a compilation; an analyzer reports rules; a code fix offers an optional edit. Incremental pipelines should be deterministic, cancellation-aware and free of mutable shared state. These tools are products that need tests, packaging, version compatibility and CI.
