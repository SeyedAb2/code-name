ValueTask و جریان ناهمگام

ValueTask and async streams

یک cache بیشتر درخواست‌ها را همان لحظه جواب می‌دهد و گاهی باید به storage برود؛ تیم برای کم‌کردن allocation، Task<T> را به ValueTask<T> تغییر داده و مصرف‌کننده دوبار await می‌کند. در همان سرویس، endpoint صفحه‌ها را یکی‌یکی می‌خواند اما همه را پیش از پردازش جمع می‌کند. این فصل می‌پرسد بهینه‌سازی واقعاً کجا لازم است و جریان مرحله‌ای چه قراردادی دارد.

A cache answers most requests synchronously but sometimes calls storage; the team replaces Task<T> with ValueTask<T> to reduce allocations, and a consumer awaits it twice. Another endpoint fetches pages one at a time but collects them all before processing. We ask where optimization is justified and what incremental streaming promises.

فصل ۴۸پیش‌نیازprerequisite

ValueTask فقط وقتی ارزش دارد که نتیجه اغلب همین حالا آماده باشدValueTask helps only when results are often synchronous

ValueTask<T> یک struct است و می‌تواند نتیجهٔ آماده یا Task/منبع async دیگری را در خود نگه دارد. اگر hot path اغلب cache hit دارد، ممکن است allocation یک Task را کم کند؛ اما struct بزرگ‌تری جابه‌جا می‌شود و مصرف‌کننده محدودیت بیشتری دارد. اول با profiler نشان بده allocation مسئله است؛ بعد تغییر بده و benchmark همان workload را مقایسه کن.

ValueTask<T> is a struct that can carry an already-available result or another asynchronous source. If a hot path usually hits cache, it may avoid allocating a Task; but a larger struct is copied and consumers face stricter rules. Use a profiler to prove allocation is a problem, then benchmark the real workload before changing the API.

cache hit synchronous / miss asynchronous
public ValueTask<Product?> FindAsync(
    string id, CancellationToken ct = default)
{
    if (_cache.TryGetValue(id, out Product? cached))
        return ValueTask.FromResult<Product?>(cached);

    return new ValueTask<Product?>(
        _store.LoadAsync(id, ct));
}

API فقط وقتی منصفانه است که مصرف‌کننده انتظار یک‌بارمصرف بودن را بداند. هر ValueTask را یک‌بار await کن؛ اگر چند مصرف‌کننده لازم است یا باید cache شود، با AsTask() یک بار تبدیل و همان Task را share کن. روی یک instance چند بار AsTask نزن. API عمومی libraryها اغلب Task ساده‌تری می‌خواهد، مگر این‌که اندازه‌گیری و قرارداد هزینه را توجیه کنند.

This API is fair only when consumers understand its single-consumption contract. Await each ValueTask once. If multiple consumers or caching are required, convert it once with AsTask() and share that Task; do not call AsTask repeatedly on one instance. Public library APIs often benefit from plain Task unless measurement and contract justify the extra complexity.

یک await، یک مالکOne await, one owner

بعضی ValueTaskها از IValueTaskSource poolشده می‌آیند؛ پس مصرف چندباره می‌تواند رفتار تعریف‌نشده بدهد. حتی اگر مسیر cache فعلی دوبار await را تصادفاً تحمل می‌کند، مسیر storage آینده ممکن است نکند. shape async را مستقیم و بدون ذخیره/مصرف تکراری بنویس؛ اگر واقعاً چند await یا combinator می‌خواهی، یک بار به Task تبدیل کن.

Some ValueTasks are backed by a pooled IValueTaskSource, so multiple consumption can be undefined behavior. Even if today’s cache path happens to tolerate two awaits, a future storage path may not. Consume the awaitable once; if you need multiple awaits or combinators, convert once to Task.

تبدیل کنترل‌شده / Convert once
ValueTask<Record> pending = repository.LoadAsync(id);
Task<Record> shared = pending.AsTask();

await Task.WhenAll(AuditAsync(shared), RenderAsync(shared));

در این نمونه هر helper همان Task را await می‌کند؛ نه خود ValueTask را. اگر فقط یک مصرف‌کننده داری، ساده‌ترین شکل این است: return await repository.LoadAsync(id); در متدی که نتیجه‌اش Task است—و اگر لازم نیست wrapper async باشد، API را بر اساس signature و error flow ساده کن.

Both helpers await the same Task, not the ValueTask. With one consumer, the simplest path is to await the repository result once; otherwise shape the wrapper around the desired return type and error flow.

IAsyncEnumerable نتیجه را مرحله‌ای می‌دهدIAsyncEnumerable yields results incrementally

IAsyncEnumerable<T> هر عضو را با امکان await به مصرف‌کننده می‌دهد؛ برای pagination، فایل یا producer کند، لازم نیست کل نتیجه از اول در حافظه باشد. هر عضو ممکن است بعد از network I/O تولید شود. بدنهٔ iterator معمولاً با شروع enumeration اجرا می‌شود، نه صرفاً هنگام ساختن enumerable؛ پس cancellation و resource lifetime باید تا پایان enumeration زنده بمانند.

IAsyncEnumerable<T> yields each item asynchronously, so pagination, file processing or a slow producer need not materialize the full result first. Each item may follow network I/O. An iterator body generally runs when enumeration begins, not when the enumerable is merely created; cancellation and resource lifetimes must last through enumeration.

تولید مرحله‌ای / Yield incrementally
static async IAsyncEnumerable<Item> ReadPagesAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    string? cursor = null;
    do
    {
        Page page = await FetchPageAsync(cursor, ct);
        foreach (Item item in page.Items)
            yield return item;
        cursor = page.NextCursor;
    }
    while (cursor is not null);
}

attribute EnumeratorCancellation توکن caller که از WithCancellation می‌آید را به پارامتر iterator وصل می‌کند. اگر attribute نباشد compiler ممکن است هشدار دهد و توکن enumeration به بدنه نرسد. هر fetch باید cancellation را رعایت کند و خطای صفحهٔ میانی باید contract جریان را روشن کند: ادامه‌دادن، retry یا fail کل enumeration.

EnumeratorCancellation connects the caller token supplied through WithCancellation to the iterator parameter. Without it, the compiler can warn that enumeration cancellation is not forwarded into the body. Each fetch must honor cancellation, and a mid-stream page failure needs an explicit policy: continue, retry or fail the enumeration.

مصرف‌کننده هم async و قابل‌لغو استConsumers are asynchronous and cancellable too

برای async stream از await foreach استفاده کن؛ حلقه هر عضو را می‌گیرد و پیش از حرکت بعدی می‌تواند backpressure طبیعی ایجاد کند. token را با WithCancellation عبور بده. اگر consumer هر عضو را سریع‌تر از تولیدکننده جمع می‌کند، مرحلهٔ پردازش خودش queue را پر می‌کند؛ streaming همهٔ حافظه و concurrency را خودکار محدود نمی‌کند.

Consume asynchronous streams with await foreach; processing each item before requesting the next can provide natural backpressure. Pass cancellation through WithCancellation. If the consumer queues items faster than it processes them, its own queue still grows—streaming does not automatically bound all memory or concurrency.

مصرف و لغو / Consume and cancel
await foreach (Item item in ReadPagesAsync(ct)
    .WithCancellation(ct)
    .ConfigureAwait(false))
{
    await SaveAsync(item, ct);
}

اینجا هر item تا ذخیره‌شدن، عضو بعدی را درخواست نمی‌کند؛ concurrency عمداً یک است. برای throughput بیشتر، pipeline محدود لازم است و ترتیب ممکن است تغییر کند. async iterator می‌تواند resource را با await using آزاد کند؛ disposal هنگام break یا cancellation هم باید تست شود.

This requests the next item only after saving the current one, so concurrency is intentionally one. Higher throughput needs a bounded pipeline and may alter ordering. An async iterator can dispose resources with await using; verify disposal on early break and cancellation too.

streaming حافظه را کم می‌کند، اما رفتار partial می‌آوردStreaming reduces memory but introduces partial results

در مدل جمع‌شده، خطای صفحهٔ آخر می‌تواند کل نتیجه را fail کند؛ در stream ممکن است مصرف‌کننده پیش از آن صدها رکورد را commit کرده باشد. باید دربارهٔ checkpoint، duplicate، retry و بازپذیری عملیات تصمیم بگیری. اگر خروجی باید atomic باشد، اول در staging ذخیره یا transaction طراحی کن؛ صرفاً async stream کردن ضمانت اتمیک نمی‌دهد.

With materialized results, a final-page error can fail the whole operation; with streaming, the consumer may already have committed hundreds of records. Define checkpoints, duplicates, retries and idempotency. For atomic output, stage data or design a transaction; an async stream alone provides no atomicity guarantee.

بهینه‌سازی را با مصرف‌کنندهٔ واقعی بسنجMeasure with the real consumer

برای ValueTask، cache hit ratio، allocation per operation و throughput را اندازه بگیر؛ struct می‌تواند برای مسیرهایی با نتیجهٔ async همیشه هزینهٔ اضافه باشد. برای stream، peak memory، latency تا اولین عضو، زمان کل، تعداد درخواست‌ها و رفتار failure را مقایسه کن. benchmark مصنوعی بدون workload نماینده دلیل تغییر API نیست.

For ValueTask, measure cache-hit ratio, allocation per operation and throughput; the struct can add cost when results are usually asynchronous. For streams, compare peak memory, time to first item, total duration, request count and failure behavior. A synthetic benchmark is not enough reason to change an API without representative workloads.

۱۳) resource دیرهنگام13) Deferred resource lifetime

متد stream می‌سازد، فایل را می‌بندد و بعد consumer enumerate می‌کند؛ ownership را جابه‌جا کن.

پاسخ فنیTechnical reasoning

۱۵) Task یا async stream15) Task or async stream

API ده هزار رکورد را در یک Task لیست می‌دهد؛ هزینه و semantics را مقایسه کن.

پاسخ فنیTechnical reasoning

stream first-item latency و memory را کم می‌کند اما partial result و cancellation/lifetime را پیچیده‌تر می‌کند.

پاسخ فنیTechnical reasoning

مصرف چندباره و AsTask را بررسی کن، telemetry correctness و perf را مقایسه و اگر قرارداد سود ندارد به Task برگرد.

پیچیدگی را فقط در برابر مدرک بپذیرAccept complexity only for measured evidence

ValueTask یک قرارداد مصرف سخت‌گیرانه‌تر برای کاهش تخصیص در مسیر synchronous پرتکرار است؛ async stream نتیجه را زودتر و مرحله‌ای می‌دهد، اما partial commit و عمر منبع را هم وارد طراحی می‌کند. هر دو ابزار می‌توانند مفید باشند و هر دو می‌توانند API را سخت‌تر کنند. پس اول workload را اندازه بگیر، بعد پیچیدگی را وارد کن. فصل بعد از async خارج می‌شویم و سراغ طراحی درست مدل API و تحلیل شبکه‌ای می‌رویم.

ValueTask offers a stricter consumption contract to reduce allocation on frequent synchronous paths; async streams yield results earlier and incrementally, but bring partial commits and resource lifetimes into the design. Both tools can help and both can complicate an API. Measure the workload before adding complexity. Next we leave async and focus on API design and network analysis.
