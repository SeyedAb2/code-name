کپی مقدار و کپی ارجاع

Value copies and reference copies

تنظیم تخفیف سفارش A-42 را برای یک پیش‌نمایش کپی می‌کنیم. بعد یک فیلد را در نسخهٔ پیش‌نمایش عوض می‌کنیم و می‌بینیم سفارش اصلی هم تغییر کرده است. اسم متغیرها جداست؛ پس چرا داده یکی است؟ بیا رفتار assignment را با آزمایش ببینیم، نه با جملهٔ «struct روی stack است».

We copy the discount settings for order A-42 into a preview, then change one field and discover that the original order changed too. The variables have different names, so why did the data move together? Let’s observe assignment semantics instead of relying on “structs live on the stack.”

پیش‌نمایش، سفارش اصلی را هم تغییر دادThe preview changed the original order

تیم فروش می‌خواهد روی یک نسخهٔ آزمایشی، نرخ تخفیف را عوض کند؛ نباید سفارش ثبت‌شده دست بخورد. این کد را اجرا کن و قبلش حدس بزن دو خط آخر چه چاپ می‌کنند.

Sales wants to experiment with a discount rate without changing the recorded order. Run this code, but first predict the last two lines.

در assignment به یک class، مقدار متغیر یعنی reference به شیء کپی می‌شود. شیء تازه‌ای نساختیم؛ هر دو متغیر به همان تنظیمات اشاره می‌کنند. `preview.Rate` و `original.Rate` دو راه رسیدن به یک property هستند.

Assigning a class value copies the reference to the object. No new object was created; both variables refer to the same settings. `preview.Rate` and `original.Rate` reach the same property.

نام متفاوت، شیء متفاوت نمی‌سازدA new variable name does not create a new object

`var preview = original` متغیر تازه می‌سازد، نه نسخهٔ مستقل از شیء. قبل از تغییر آزمایشی باید تصمیم بگیری: آیا عمداً هر دو نام یک وضعیت مشترک را می‌بینند؟

`var preview = original` creates a new variable, not an independent object. Before a trial mutation, decide whether both names are meant to observe shared state.

با struct همان assignment، نتیجهٔ دیگری داردThe same assignment behaves differently with a struct

حالا settings را یک `struct` کوچک می‌کنیم. خط‌ها تقریباً همان‌اند؛ این بار پیش از اجرا نتیجه را پیش‌بینی کن.

Now make the settings a small `struct`. The lines are almost identical; predict the result before running them.

C# · value type
struct DiscountSnapshot
{
    public decimal Rate;
}

var original = new DiscountSnapshot { Rate = 0.10m };
var preview = original;       // copies the struct value
preview.Rate = 0.20m;

Console.WriteLine(original.Rate);
Console.WriteLine(preview.Rate);
خروجی / output
0.10
0.20

هر متغیر value type مقدار خودش را دارد؛ assignment مقدار struct را کپی کرد. تغییر فیلد در `preview`، مقدار `original` را عوض نکرد. این قرارداد زبانی دربارهٔ معناست، نه قولی دربارهٔ جای فیزیکی هر متغیر.

Each value-type variable has its own value; assignment copied the struct value. Mutating `preview` did not change `original`. This is a language-level semantic contract, not a promise about where each variable physically lives.

برای `int` هم همین است: `int b = a` عدد را کپی می‌کند. برای class، `b = a` ارجاع به همان object را کپی می‌کند. پس «value type یعنی همیشه روی stack» و «reference type یعنی همیشه فقط یک جای heap» مدل قابل اتکایی برای تصمیم روزمره نیست؛ JIT و عمر متغیرها در جزئیات حافظه دخیل‌اند.

The same applies to `int`: `int b = a` copies the number. For a class, `b = a` copies a reference to the same object. “Value types always live on the stack” and “reference types always mean one heap location” are not reliable everyday models; the JIT and variable lifetimes affect implementation details.

پارامتر متد هم طبق همان قاعده کپی می‌شودMethod parameters follow the same copy rule

یک helper نرخ تخفیف را تغییر می‌دهد. آیا caller تغییر را می‌بیند؟ جواب به «کلاس یا struct بودن خود متغیر» ربط ندارد؛ باید ببینیم مقدار کپی‌شده چیست و داخل متد چه کاری می‌کنیم.

A helper changes a discount rate. Does the caller observe it? The answer is not simply about whether the variable is a class or struct; ask what value was copied and what the method does with it.

C# · parameter is a copy
static void Replace(DiscountSettings settings)
{
    settings = new DiscountSettings { Rate = 0.30m };
}

static void Mutate(DiscountSettings settings)
{
    settings.Rate = 0.25m;
}

var original = new DiscountSettings { Rate = 0.10m };
Replace(original);
Console.WriteLine(original.Rate); // 0.10
Mutate(original);
Console.WriteLine(original.Rate); // 0.25

در هر دو فراخوانی reference پارامتر کپی می‌شود. `Replace` فقط کپی محلی را به شیء تازه وصل می‌کند؛ متغیر caller همچنان شیء قبلی را می‌بیند. `Mutate` از reference کپی‌شده به همان شیء می‌رسد و property مشترک را عوض می‌کند. اگر واقعاً قرار است خود متغیر caller دوباره مقدار بگیرد، بحث `ref` فصل ۸ مطرح است؛ برای API بهتر است اول از خودت بپرسی mutation لازم است یا مقدار تازه برگرداندن روشن‌تر است.

Both calls copy the reference into the parameter. `Replace` redirects only its local copy; the caller still refers to the old object. `Mutate` follows the copied reference to the shared object and changes its property. If the caller’s variable itself must be reassigned, Chapter 8’s `ref` is relevant; for API design, first ask whether mutation or returning a new value is clearer.

یک جملهٔ دقیق‌ترA more precise sentence

C# آرگومان را به متد می‌دهد و پارامتر به‌طور پیش‌فرض مقدار را می‌گیرد. در reference type، آن مقدار یک reference است؛ پس کپی reference می‌تواند به دادهٔ مشترک راه بدهد، اما assignment دوباره به پارامتر، caller را عوض نمی‌کند.

C# passes an argument value to a parameter by default. For a reference type, that value is a reference; copying it can expose shared data, but reassigning the parameter does not reassign the caller’s variable.

کپی شیء همیشه کپی عمیق نیستCopying an object is not automatically a deep copy

برای جلوگیری از alias، یک نمونهٔ تازه می‌سازیم. اما object یک فهرست mutable هم دارد؛ اگر فقط خود object را کپی کنیم، فهرست چه می‌شود؟

To avoid the alias, we create a new instance. But the object also owns a mutable list. What happens if we copy only the outer object?

C# · shallow copy
sealed class OrderDraft
{
    public string Id { get; init; } = "";
    public List<string> Items { get; init; } = [];
}

var original = new OrderDraft { Id = "A-42", Items = ["book"] };
var preview = new OrderDraft { Id = original.Id, Items = original.Items };
preview.Items.Add("pen");

Console.WriteLine(original.Items.Count);
Console.WriteLine(ReferenceEquals(original.Items, preview.Items));
خروجی / output
2
True

دو `OrderDraft` داریم، ولی هر دو property `Items` به یک `List` اشاره می‌کند. این کپی سطحی است: فیلدهای مقدار، مقدارشان را می‌گیرند و فیلدهای reference همان reference را. کپی عمیق باید دربارهٔ هر شیء تو در تو تصمیم بگیرد؛ یک دکمهٔ عمومی و بی‌هزینه نیست.

There are two `OrderDraft` objects, but both `Items` properties refer to one list. This is a shallow copy: value fields get their values, while reference fields get the same references. A deep copy must decide what to do with every nested object; it is not a universal, free button.

اگر فهرست هم مستقل باشد، باید آن را هم بسازیم: `Items = [.. original.Items]`. اما این فقط یک سطح را کپی می‌کند؛ اگر خود آیتم‌ها mutable object باشند، آن‌ها هنوز مشترک‌اند. immutable کردن داده یا طراحی یک `Copy` صریح با قرارداد مشخص، معمولاً از کپی مبهم امن‌تر است.

If the list must also be independent, create it too: `Items = [.. original.Items]`. That copies only one level; mutable item objects may still be shared. Immutable data or an explicit `Copy` operation with a clear contract is often safer than an ambiguous copy.

struct هم می‌تواند reference مشترک درون خودش داشته باشدA struct can still contain a shared reference

حالا `OrderStamp` یک struct است، ولی داخلش `List` دارد. کپی خود struct چه چیزی را جدا می‌کند و چه چیزی را نه؟

Now `OrderStamp` is a struct, but it contains a `List`. What does copying the struct separate, and what remains shared?

C# · value containing a reference
struct OrderStamp
{

    public List<string> Notes;

var first = new OrderStamp { Revision = 1, Notes = ["created"] };
var second = first;

فیلد `Revision` در struct کپی جدا دارد؛ `Notes` یک reference است و کپی struct، فهرست تازه‌ای نساخت. پس سؤال مفید «این نوع value است یا reference؟» است، اما برای فهم استقلال واقعی باید یک لایه پایین‌تر هم ساختار فیلدها را ببینیم.

The `Revision` field has an independent copied value; `Notes` is a reference, and copying the struct did not create another list. “Is this a value or reference type?” is useful, but to understand independence we must inspect the fields one level deeper.

boxing مقدار value type را کپی می‌کند و به شکل object قابل‌ارجاع در اختیار می‌گذارد؛ متغیر `revision` و مقدار box‌شده دو مقدار جدا هستند. هنگام unboxing نوع دقیق باید درست باشد: `(short)boxed` تبدیل عددی عمومی نیست و با boxed `int` خطای زمان اجرا می‌دهد. genericهایی مثل `List<int>` معمولاً از boxing ناخواستهٔ هر عضو جلوگیری می‌کنند؛ اما قبل از بهینه‌سازی، مسیر واقعی را بسنج.

Boxing copies a value-type value into an object you can reference; `revision` and the boxed value are separate. Unboxing requires the exact boxed type: `(short)boxed` is not a general numeric conversion and fails at runtime for a boxed `int`. Generics such as `List<int>` generally avoid boxing each item; measure a real path before optimizing.

C# · explicit copy contract
sealed class DiscountSettings
{
    public decimal Rate { get; set; }
}

sealed class OrderDraft
{
    public required string Id { get; init; }
    public required DiscountSettings Discount { get; init; }
    public required List<string> Items { get; init; }

    public OrderDraft CopyForPreview() => new()
    {
        Id = Id,
        Discount = new DiscountSettings { Rate = Discount.Rate },
        Items = [.. Items]
    };
}

var original = new OrderDraft
{
    Id = "A-42",
    Discount = new DiscountSettings { Rate = 0.10m },
    Items = ["book"]
};
var preview = original.CopyForPreview();
preview.Discount.Rate = 0.20m;
preview.Items.Add("pen");

Console.WriteLine($"original: {original.Discount.Rate}, {string.Join(",", original.Items)}");
Console.WriteLine($"preview: {preview.Discount.Rate}, {string.Join(",", preview.Items)}");
Console.WriteLine(ReferenceEquals(original.Discount, preview.Discount));
Console.WriteLine(ReferenceEquals(original.Items, preview.Items));

متد نام‌دار، قرارداد کپی را کنار مدل نگه می‌دارد و هر دو reference mutable را تازه می‌سازد. این مثال چون string immutable است، کپی رشتهٔ `Id` نگرانی mutation ندارد. اگر `Items` شامل objectهای mutable باشد، کپی لیست فقط container را جدا می‌کند؛ باید همان قرارداد را برای عضوها هم تعریف کنیم.

The named method keeps the copy contract with the model and creates both mutable references anew. `Id` is a string, so copying its reference is safe for mutation because strings are immutable. If `Items` contains mutable objects, copying the list separates only the container; define a contract for its elements too.

۶) کپی سطحی را تعمیر کن6) Repair a shallow copy

یک `OrderDraft` با `List<string>` بساز؛ object تازه ولی فهرست مشترک تولید کن. کمینه‌ترین تغییری که فهرست را جدا می‌کند چیست؟

Create a new `OrderDraft` but reuse its `List<string>`. What smallest change separates the list?

اصلاحRepair

`Items = [.. original.Items]` یا `original.Items.ToList()` یک فهرست تازه با همان stringها می‌سازد. اگر اعضا mutable باشند، آن‌ها هنوز مشترک‌اند؛ مرز کپی باید با مدل هماهنگ باشد.

`Items = [.. original.Items]` or `original.Items.ToList()` creates a new list with the same strings. Mutable elements remain shared; the copy boundary must match the model.

۷) struct دارای List را بررسی کن7) Inspect a struct containing a List

struct را کپی کن؛ یک فیلد عددی و یک List را جداگانه تغییر بده. با دو خروجی نشان بده چرا عبارت «struct همیشه کپی مستقل است» ناقص است.

Copy a struct, then change a numeric field and its List separately. Use two outputs to show why “a struct is always an independent copy” is incomplete.

مدل پاسخAnswer model

فیلد عددیِ کپی‌شده مستقل است؛ reference مربوط به List کپی شده و هر دو struct یک collection را می‌بینند. نوع بیرونی کافی نیست؛ ساختار داخلی هم مهم است.

The copied numeric field is independent; the List reference was copied, so both structs see one collection. The outer type alone is not enough; inspect its fields.

۸) خطای unboxing را بازتولید کن8) Reproduce an unboxing failure

عدد `int` را به object تبدیل کن و آن را مستقیم به `short` cast کن. exception را ثبت و cast درست را آزمایش کن.

Box an `int`, cast it directly to `short`, record the exception, then test the correct cast.

تشخیصDiagnosis

`(short)boxed` با InvalidCastException شکست می‌خورد؛ داخل object یک `int` box شده، نه `short`. ابتدا `(int)boxed` unbox می‌کند، بعد تبدیل عددی جدا انجام بده: `short n = (short)(int)boxed;` و محدوده را هم بررسی کن.

`(short)boxed` throws InvalidCastException because the object contains a boxed `int`, not a boxed `short`. Unbox as `(int)boxed`, then convert separately: `short n = (short)(int)boxed;`, checking the range too.

۹) boxing را در API قدیمی پیدا کن9) Find boxing in a legacy API

یک `ArrayList` از intها و یک `List<int>` بساز. یک دلیل فنی برای انتخاب دومی بنویس و نتیجه را با کد اجرا کن؛ ادعای benchmark نکن.

Create an `ArrayList` and a `List<int>`. Use code to show one technical reason for preferring the generic list; do not claim a benchmark.

نمونهExample

`ArrayList` مقدارهای value type را از مسیر `object` نگه می‌دارد و read نیازمند unboxing/cast است؛ `List<int>` نوع را حفظ می‌کند و cast را حذف می‌کند. اندازهٔ کارایی را بدون اندازه‌گیری واقعی اعلام نکن.

`ArrayList` stores value types through `object`, requiring an unbox/cast on read; `List<int>` preserves the type and removes that cast. Do not quantify performance without measurement.

۱۰) مقدار tuple را کپی کن10) Copy a tuple value

یک tuple شامل `int Count` و `decimal Total` بساز، assign کن و یکی از فیلدها را در کپی عوض کن. آیا tuple یک class است؟

Create a tuple with `int Count` and `decimal Total`, assign it, and mutate one field in the copy. Is a tuple a class?

پاسخAnswer

ValueTuple یک value type است؛ assignment مقدار را کپی می‌کند. دو متغیر مستقل‌اند. نام‌های `Count` و `Total` خوانایی compile-time می‌دهند، نه شیء مرجع مستقل.

ValueTuple is a value type; assignment copies its value, so the variables are independent. `Count` and `Total` improve compile-time readability, not reference identity.

۱۱) mutable element را در کپی لیست بیازما11) Test a mutable element in a copied list

`List<DiscountSettings>` را با collection expression کپی کن. property اولین عضو را از کپی تغییر بده و مشخص کن آیا فقط list تازه شده یا object عضو هم.

Copy a `List<DiscountSettings>` with a collection expression. Mutate the first element through the copy and determine whether only the list or the element object was copied.

شاهدEvidence

collection expression container جدید می‌سازد، اما اعضای class همان referenceهای قبلی‌اند؛ پس property شیء اصلی هم تغییر می‌کند. برای استقلال باید هر عضو را هم کپی یا immutable کرد.

The collection expression creates a new container, but class elements remain the same references; mutating one changes the original object too. Copy each element or make them immutable for independence.

۱۲) قرارداد کپی را در نام متد روشن کن12) Make the copy contract visible in a method name

برای `OrderDraft` متدی بساز که مشخص کند فقط snapshot سطحی می‌دهد یا preview مستقل. یک تست با mutation بنویس که قرارداد را ثابت کند.

Add a method to `OrderDraft` that states whether it returns a shallow snapshot or independent preview. Write a mutation test that proves the contract.

راه حلApproach

اسم `CopyForPreview` را فقط وقتی به‌کار ببر که هر مسیر mutable موردنیاز را جدا کرده‌ای. تست: original و copy را بساز، copy را تغییر بده، مقدار اصلی و `ReferenceEquals`های مورد انتظار را assert کن. اسم `Clone` به‌تنهایی عمق کپی را تضمین نمی‌کند.

Use `CopyForPreview` only after separating every required mutable path. Test by mutating the copy, asserting original values and expected `ReferenceEquals` results. The name `Clone` alone does not promise copy depth.

۱۳) آیا ref جواب استقلال است؟13) Does ref solve independence?

یک helper با `ref Settings` بنویس که caller را به object جدید وصل کند. بعد بگو مشکل اشتراک state حل شد یا فقط متغیر caller دوباره assign شد.

Write a `ref Settings` helper that points the caller at a new object. Did this solve shared state, or only reassign the caller’s variable?

تفسیرInterpretation

`ref` اجازه می‌دهد متد خود متغیر caller را دوباره assign کند؛ این می‌تواند alias آن متغیر را قطع کند، اما سایر aliasهای قبلی و referenceهای تو در تو را خودکار اصلاح نمی‌کند. قرارداد کپی همچنان لازم است.

`ref` lets the method reassign the caller’s variable. That can break that variable’s alias, but does not repair other aliases or nested references automatically. A copy contract is still required.

۱۴) identity را با equality قاطی نکن14) Do not confuse identity with equality

دو object جدا با propertyهای برابر بساز. `ReferenceEquals` و `Equals` را جدا اجرا کن و توضیح بده کدام سؤال را جواب می‌دهند.

Create two distinct objects with equal properties. Run `ReferenceEquals` and `Equals` separately; explain what each asks.

نکتهKey point

`ReferenceEquals` می‌پرسد آیا همان instance است. `Equals` قرارداد برابری نوع را صدا می‌زند و برای class عادی، اگر override نشده باشد، معمولاً identity است؛ نوع‌هایی مثل record می‌توانند value equality داشته باشند. این فصل equality را پیاده‌سازی نمی‌کند؛ فصل ۱۹ مرزش را باز می‌کند.

`ReferenceEquals` asks whether this is the same instance. `Equals` invokes the type’s equality contract; an ordinary class typically uses identity unless overridden, while records can provide value equality. Chapter 19 develops that contract.

۱۵) افسانهٔ stack/heap را با ادعای قابل‌اثبات عوض کن15) Replace stack/heap folklore with a provable claim

این گزاره را اصلاح کن: «همهٔ structها روی stack و همهٔ classها روی heap هستند.» دو جملهٔ درست دربارهٔ assignment بنویس و یک محدودیت ادعا را اضافه کن.

Correct: “All structs are on the stack and all classes are on the heap.” Write two true assignment statements and one limitation.

پاسخAnswer

در assignment، value type مقدارش کپی می‌شود؛ reference type مقدار reference را کپی می‌کند. این semantics تضمینِ محل فیزیکی نیست. رفتار allocation و performance را باید با runtime و benchmark مناسب بررسی کرد.

Assignment copies a value-type value and copies a reference-type reference. These semantics do not guarantee physical storage locations. Inspect allocation and performance with appropriate runtime evidence and benchmarks.

۱۶) گزارش کپی را برای یک سفارش طراحی کن16) Design a copy report for an order

یک سفارش با discount، فهرست قلم‌ها و metadata بساز. دو سیاست «shared preview» و «independent preview» را پیاده کن؛ mutationها، identity و محدودیت عمق هرکدام را با خروجی مستند کن.

Build an order with a discount, item list and metadata. Implement shared and independent preview policies; document mutations, identity and copy-depth limits with output.

معیار پاسخ قویStrong-answer criteria

کد باید برای هر property مشخص کند immutable است، value است یا reference mutable. تست باید حداقل یک تغییر را در preview انجام دهد و ثابت کند کدام مقدار در اصل تغییر کرده یا نکرده است؛ مرز کپی عمیق هم صریح نوشته شود.

For each property, state whether it is immutable, a value, or a mutable reference. The test must mutate the preview and prove what did or did not change in the original; state the deep-copy boundary explicitly.

قبل از کپی بپرس: استقلال می‌خواهیم یا اشتراک؟Before copying, ask: independence or sharing?

برای عدد یا struct ساده، assignment معمولاً یک value مستقل می‌دهد. برای class و آرایه، متغیر تازه می‌تواند همان object را share کند. پارامتر متد هم reference را کپی می‌کند، نه اینکه caller را خودکار بازنویسی کند. کپی سطحی فقط یک سطح را جدا می‌کند؛ referenceهای تو در تو را باید دنبال کرد. برای API، قرارداد را با immutability یا متد کپی نام‌دار روشن کن و با تست mutation ثابتش کن.

Assignment gives an independent value for a number or simple struct. A new variable holding a class or array may still share the same object. A method parameter copies the reference; it does not automatically reassign the caller. A shallow copy separates only one level, so trace nested references. Make API intent clear with immutability or a named copy operation, then prove it with mutation tests.

در فصل بعد سراغ `null` می‌رویم: حالا که می‌دانیم چند نام می‌توانند به یک object برسند، باید ببینیم اگر یکی از این referenceها اصلاً به object نرسد، compiler و runtime چه هشداری می‌دهند.
