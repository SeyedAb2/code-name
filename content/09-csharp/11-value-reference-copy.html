کپی مقدار و کپی ارجاع

Value copies and reference copies

تنظیم تخفیف سفارش A-42 رو برای یک پیش‌نمایش کپی می‌کنیم. بعد یک فیلد رو در نسخهٔ پیش‌نمایش عوض می‌کنیم و می‌بینیم سفارش اصلی هم تغییر کرده هست. اسم متغیرها جداست؛ پس چرا داده یکی هست؟ بیا رفتار assignment رو با آزمایش ببینیم، نه با جملهٔ «struct روی stack است».

We copy the discount settings for order A-42 into a preview, then change one field and discover that the original order changed too. The variables have different names, so why did the data move together? Let’s observe assignment semantics instead of relying on “structs live on the stack.”

پیش‌نمایش، سفارش اصلی رو هم تغییر دادThe preview changed the original order

تیم فروش می‌خواد روی یک نسخهٔ آزمایشی، نرخ تخفیف رو عوض کند؛ نباید سفارش ثبت‌شده دست بخورد. این کد رو اجرا کن و قبلش حدس بزن دو خط آخر چه چاپ می‌کنن.

Sales wants to experiment with a discount rate without changing the recorded order. Run this code, but first predict the last two lines.

C# · Program.cs
sealed class DiscountSettings
{
    public decimal Rate { get; set; }
}

var original = new DiscountSettings { Rate = 0.10m };
var preview = original;
preview.Rate = 0.20m;

Console.WriteLine(original.Rate);
Console.WriteLine(ReferenceEquals(original, preview));

در assignment به یک class، مقدار متغیر یعنی reference به شیء کپی می‌شه. شیء تازه‌ای نساختیم؛ هر دو متغیر به همان تنظیمات اشاره می‌کنن. `preview.Rate` و `original.Rate` دو راه رسیدن به یک property هستن.

Assigning a class value copies the reference to the object. No new object was created; both variables refer to the same settings. `preview.Rate` and `original.Rate` reach the same property.

نام متفاوت، شیء متفاوت نمی‌سازهA new variable name does not create a new object

`var preview = original` متغیر تازه می‌سازه، نه نسخهٔ مستقل از شیء. قبل از تغییر آزمایشی باید تصمیم بگیری: آیا عمداً هر دو نام یک وضعیت مشترک رو می‌بینن؟

`var preview = original` creates a new variable, not an independent object. Before a trial mutation, decide whether both names are meant to observe shared state.

با struct همان assignment، نتیجهٔ دیگری دارهThe same assignment behaves differently with a struct

حالا settings رو یک `struct` کوچک می‌کنیم. خط‌ها تقریباً همان‌اند؛ این بار پیش از اجرا نتیجه رو پیش‌بینی کن.

Now make the settings a small `struct`. The lines are almost identical; predict the result before running them.

C# · value type
struct DiscountSnapshot
{
    public decimal Rate;
}

var original = new DiscountSnapshot { Rate = 0.10m };
var preview = original;       // copies the struct value
preview.Rate = 0.20m;

Console.WriteLine(original.Rate);
Console.WriteLine(preview.Rate);
خروجی / output
0.10
0.20

هر متغیر value type مقدار خودش رو داره؛ assignment مقدار struct رو کپی کرد. تغییر فیلد در `preview`، مقدار `original` رو عوض نکرد. این قرارداد زبانی دربارهٔ معناست، نه قولی دربارهٔ جای فیزیکی هر متغیر.

Each value-type variable has its own value; assignment copied the struct value. Mutating `preview` did not change `original`. This is a language-level semantic contract, not a promise about where each variable physically lives.

برای `int` هم همین هست: `int b = a` عدد رو کپی می‌کنه. برای class، `b = a` ارجاع به همان object رو کپی می‌کنه. پس «value type یعنی همیشه روی stack» و «reference type یعنی همیشه فقط یک جای heap» مدل قابل اتکایی برای تصمیم روزمره نیست؛ JIT و عمر متغیرها در جزئیات حافظه دخیل‌اند.

The same applies to `int`: `int b = a` copies the number. For a class, `b = a` copies a reference to the same object. “Value types always live on the stack” and “reference types always mean one heap location” are not reliable everyday models; the JIT and variable lifetimes affect implementation details.

پارامتر متد هم طبق همان قاعده کپی می‌شهMethod parameters follow the same copy rule

یک helper نرخ تخفیف رو تغییر می‌ده. آیا caller تغییر رو می‌بینه؟ جواب به «کلاس یا struct بودن خود متغیر» ربط نداره؛ باید ببینیم مقدار کپی‌شده چیه و داخل متد چه کاری می‌کنیم.

A helper changes a discount rate. Does the caller observe it? The answer is not simply about whether the variable is a class or struct; ask what value was copied and what the method does with it.

C# · parameter is a copy
static void Replace(DiscountSettings settings)
{
    settings = new DiscountSettings { Rate = 0.30m };
}

static void Mutate(DiscountSettings settings)
{
    settings.Rate = 0.25m;
}

var original = new DiscountSettings { Rate = 0.10m };
Replace(original);
Console.WriteLine(original.Rate); // 0.10
Mutate(original);
Console.WriteLine(original.Rate); // 0.25

در هر دو فراخوانی reference پارامتر کپی می‌شه. `Replace` فقط کپی محلی رو به شیء تازه وصل می‌کنه؛ متغیر caller همچنان شیء قبلی رو می‌بینه. `Mutate` از reference کپی‌شده به همان شیء می‌رسه و property مشترک رو عوض می‌کنه. اگه واقعاً قرار هست خود متغیر caller دوباره مقدار بگیرد، بحث `ref` فصل ۸ مطرح هست؛ برای API بهتره اول از خودت بپرسی mutation لازمه یا مقدار تازه برگرداندن روشن‌تر هست.

Both calls copy the reference into the parameter. `Replace` redirects only its local copy; the caller still refers to the old object. `Mutate` follows the copied reference to the shared object and changes its property. If the caller’s variable itself must be reassigned, Chapter 8’s `ref` is relevant; for API design, first ask whether mutation or returning a new value is clearer.

یک جملهٔ دقیق‌ترA more precise sentence

C# آرگومان رو به متد می‌ده و پارامتر به‌طور پیش‌فرض مقدار رو می‌گیره. در reference type، آن مقدار یک reference هست؛ پس کپی reference می‌تونه به دادهٔ مشترک راه بدهد، اما assignment دوباره به پارامتر، caller رو عوض نمی‌کنه.

C# passes an argument value to a parameter by default. For a reference type, that value is a reference; copying it can expose shared data, but reassigning the parameter does not reassign the caller’s variable.

کپی شیء همیشه کپی عمیق نیستCopying an object is not automatically a deep copy

برای جلوگیری از alias، یک نمونهٔ تازه می‌سازیم. اما object یک فهرست mutable هم داره؛ اگه فقط خود object رو کپی کنیم، فهرست چه می‌شه؟

To avoid the alias, we create a new instance. But the object also owns a mutable list. What happens if we copy only the outer object?

C# · shallow copy
sealed class OrderDraft
{
    public string Id { get; init; } = "";
    public List<string> Items { get; init; } = [];
}

var original = new OrderDraft { Id = "A-42", Items = ["book"] };
var preview = new OrderDraft { Id = original.Id, Items = original.Items };
preview.Items.Add("pen");

Console.WriteLine(original.Items.Count);
Console.WriteLine(ReferenceEquals(original.Items, preview.Items));
خروجی / output
2
True

دو `OrderDraft` داریم، ولی هر دو property `Items` به یک `List` اشاره می‌کنه. این کپی سطحی هست: فیلدهای مقدار، مقدارشان رو می‌گیرن و فیلدهای reference همان reference رو. کپی عمیق باید دربارهٔ هر شیء تو در تو تصمیم بگیرد؛ یک دکمهٔ عمومی و بی‌هزینه نیست.

There are two `OrderDraft` objects, but both `Items` properties refer to one list. This is a shallow copy: value fields get their values, while reference fields get the same references. A deep copy must decide what to do with every nested object; it is not a universal, free button.

اگه فهرست هم مستقل باشه، باید آن رو هم بسازیم: `Items = [.. original.Items]`. اما این فقط یک سطح رو کپی می‌کنه؛ اگه خود آیتم‌ها mutable object باشن، آن‌ها هنوز مشترک‌اند. immutable کردن داده یا طراحی یک `Copy` صریح با قرارداد مشخص، معمولاً از کپی مبهم امن‌تر هست.

If the list must also be independent, create it too: `Items = [.. original.Items]`. That copies only one level; mutable item objects may still be shared. Immutable data or an explicit `Copy` operation with a clear contract is often safer than an ambiguous copy.

struct هم می‌تونه reference مشترک درون خودش داشته باشهA struct can still contain a shared reference

حالا `OrderStamp` یک struct هست، ولی داخلش `List` داره. کپی خود struct چه چیزی رو جدا می‌کنه و چه چیزی رو نه؟

Now `OrderStamp` is a struct, but it contains a `List`. What does copying the struct separate, and what remains shared?

C# · value containing a reference
struct OrderStamp
{
    public int Revision;
    public List<string> Notes;
}

var first = new OrderStamp { Revision = 1, Notes = ["created"] };
var second = first;
second.Revision = 2;
second.Notes.Add("reviewed");

Console.WriteLine($"{first.Revision}/{second.Revision}");
Console.WriteLine(string.Join(",", first.Notes));

فیلد `Revision` در struct کپی جدا داره؛ `Notes` یک reference هست و کپی struct، فهرست تازه‌ای نساخت. پس سؤال مفید «این نوع value هست یا reference؟» هست، اما برای فهم استقلال واقعی باید یک لایه پایین‌تر هم ساختار فیلدها رو ببینیم.

The `Revision` field has an independent copied value; `Notes` is a reference, and copying the struct did not create another list. “Is this a value or reference type?” is useful, but to understand independence we must inspect the fields one level deeper.

A legacy API accepts `object`. We pass it a number, then change the numeric variable. What did the object keep?

C# · boxing and unboxing
int revision = 3;
object boxed = revision;       // boxing: copies 3 into an object
revision = 4;

Console.WriteLine(revision);
Console.WriteLine(boxed);
int restored = (int)boxed;     // unboxing: type must match
Console.WriteLine(restored);

boxing مقدار value type رو کپی می‌کنه و به شکل object قابل‌ارجاع در اختیار می‌ذاره؛ متغیر `revision` و مقدار box‌شده دو مقدار جدا هستن. هنگام unboxing نوع دقیق باید درست باشه: `(short)boxed` تبدیل عددی عمومی نیست و با boxed `int` خطای زمان اجرا می‌ده. genericهایی مثل `List<int>` معمولاً از boxing ناخواستهٔ هر عضو جلوگیری می‌کنن؛ اما قبل از بهینه‌سازی، مسیر واقعی رو بسنج.

Boxing copies a value-type value into an object you can reference; `revision` and the boxed value are separate. Unboxing requires the exact boxed type: `(short)boxed` is not a general numeric conversion and fails at runtime for a boxed `int`. Generics such as `List<int>` generally avoid boxing each item; measure a real path before optimizing.

آزمایشگاه: پیش‌نویس رو واقعاً مستقل کنLab: make the draft genuinely independent

پیش‌نمایش سفارش باید نرخ و اقلام خودش رو داشته باشه. اول با کد معیوب شروع کن؛ بعد استقلال هر لایه رو با `ReferenceEquals` و خروجی تغییرها ثابت کن.

An order preview needs its own rate and items. Start with a broken copy, then prove independence at each layer with `ReferenceEquals` and mutation output.

  2. Create an `OrderDraft` with an ID, `DiscountSettings`, and `List<string> Items`. Assign the preview from the original and predict which mutations will leak.
  3. نرخ تخفیف و یک قلم به preview اضافه کن. مقدارها و `ReferenceEquals` برای هر دو property رو چاپ کن؛ فقط به برابری شناسه‌ها اکتفا نکن.
  4. Change the preview discount and add an item. Print the values and `ReferenceEquals` for both properties; equal IDs do not prove independent state.
  5. یک کپی سطحی بساز: object تازه، ولی همان `DiscountSettings` و `Items`. دوباره آزمایش کن و دقیق بگو کدوم لایه هنوز مشترک هست.
  6. Make a shallow copy: a new outer object but the same `DiscountSettings` and `Items`. Repeat the test and identify every shared layer.
  7. قرارداد رو انتخاب کن: کپی مستقل، دادهٔ immutable، یا shared state عمدی. اگه مستقل می‌خوای، helper `CopyForPreview` بنویس که فهرست رو هم کپی کند و تنظیمات mutable رو نیز مستقل بسازد.

  9. در فهرست یک شیء mutable تو در تو قرار بده و نشان بده کپی فهرست هنوز آن شیء رو share می‌کنه. یا کپی عمیق همان مورد رو پیاده کن یا مدل رو immutable کن؛ ادعای «deep copy کامل» بدون تعریف عمق نکن.
  10. Put a mutable nested object in the list and show that copying the list still shares that object. Copy that level too or make the model immutable; do not claim “deep copy” without defining its depth.
  11. آزمایش رو با متد `Replace` و `Mutate` تکرار کن؛ مشخص کن کدوم فقط پارامتر محلی رو عوض می‌کنه و کدوم object مشترک رو.

مسیر حل نمونه؛ بعد از آزمایش بازش کنOne solution path—open after experimenting
C# · explicit copy contract
sealed class DiscountSettings
{
    public decimal Rate { get; set; }
}

sealed class OrderDraft
{
    public required string Id { get; init; }
    public required DiscountSettings Discount { get; init; }
    public required List<string> Items { get; init; }

    public OrderDraft CopyForPreview() => new()
    {
        Id = Id,
        Discount = new DiscountSettings { Rate = Discount.Rate },
        Items = [.. Items]
    };
}

var original = new OrderDraft
{
    Id = "A-42",
    Discount = new DiscountSettings { Rate = 0.10m },
    Items = ["book"]
};
var preview = original.CopyForPreview();
preview.Discount.Rate = 0.20m;
preview.Items.Add("pen");

Console.WriteLine($"original: {original.Discount.Rate}, {string.Join(",", original.Items)}");
Console.WriteLine($"preview: {preview.Discount.Rate}, {string.Join(",", preview.Items)}");
Console.WriteLine(ReferenceEquals(original.Discount, preview.Discount));
Console.WriteLine(ReferenceEquals(original.Items, preview.Items));

original: 0.10, book
preview: 0.20, book,pen
False

متد نام‌دار، قرارداد کپی رو کنار مدل نگه می‌داره و هر دو reference mutable رو تازه می‌سازه. این مثال چون string immutable هست، کپی رشتهٔ `Id` نگرانی mutation نداره. اگه `Items` شامل objectهای mutable باشه، کپی لیست فقط container رو جدا می‌کنه؛ باید همان قرارداد رو برای عضوها هم تعریف کنیم.

The named method keeps the copy contract with the model and creates both mutable references anew. `Id` is a string, so copying its reference is safe for mutation because strings are immutable. If `Items` contains mutable objects, copying the list separates only the container; define a contract for its elements too.

آخر کار یه بار از خودت بپرس این آزمایش دقیقاً چی رو ثابت کرد و چی رو نه. این عادت جلوی نتیجه‌گیری بزرگ از یه مثال کوچیک رو می‌گیره.

At the end, state exactly what this experiment proves and what it does not. That habit prevents broad conclusions from a tiny example.

قبل از کپی بپرس: استقلال می‌خوایم یا اشتراک؟Before copying, ask: independence or sharing?

برای عدد یا struct ساده، assignment معمولاً یک value مستقل می‌ده. برای class و آرایه، متغیر تازه می‌تونه همان object رو share کند. پارامتر متد هم reference رو کپی می‌کنه، نه اینکه caller رو خودکار بازنویسی کند. کپی سطحی فقط یک سطح رو جدا می‌کنه؛ referenceهای تو در تو رو باید دنبال کرد. برای API، قرارداد رو با immutability یا متد کپی نام‌دار روشن کن و با تست mutation ثابتش کن.

Assignment gives an independent value for a number or simple struct. A new variable holding a class or array may still share the same object. A method parameter copies the reference; it does not automatically reassign the caller. A shallow copy separates only one level, so trace nested references. Make API intent clear with immutability or a named copy operation, then prove it with mutation tests.

در فصل بعد سراغ `null` می‌رویم: حالا که می‌دانیم چند نام می‌تونن به یک object برسند، باید ببینیم اگه یکی از این referenceها اصلاً به object نرسد، compiler و runtime چه هشداری می‌دن.

Next we turn to `null`. Now that several names can reach one object, we need to understand what the compiler and runtime tell us when a reference reaches no object at all.
