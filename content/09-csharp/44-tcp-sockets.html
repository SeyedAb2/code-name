TCP، socket و جریان بایت

TCP, sockets and byte streams

کلاینت می‌گوید «یک پیام فرستادم»، سرور دو تکه می‌خواند؛ یا دو پیام را یک‌جا می‌بیند. باگ از TCP نیست: ما stream را با پیام اشتباه گرفته‌ایم. این فصل روی localhost، یک قرارداد framing کوچک می‌سازد تا ببینیم اتصال چه چیزی را تضمین می‌کند و چه چیزی را باید پروتکل خودمان تعریف کند.

A client says it sent one message, but the server reads two chunks—or sees two messages together. TCP is not broken: we confused a stream with messages. On localhost, we build a small framing contract to see what a connection guarantees and what our protocol must define.

اتصال، کانال بایت است نه صف پیامA connection carries bytes, not messages

TCP بایت‌ها را مرتب و قابل‌اعتماد تحویل می‌دهد تا اتصال برقرار است؛ مرز فراخوانی WriteAsync را نگه نمی‌دارد. یک write ممکن است چند read شود و چند write ممکن است در یک read جمع شوند. پس پروتکل application باید بگوید یک پیام کجا تمام می‌شود: طول ثابت، delimiter با escaping، یا طول‌پیشوند.

TCP delivers an ordered, reliable byte stream while the connection exists; it does not preserve WriteAsync call boundaries. One write may require several reads, and several writes may arrive in one read. An application protocol must define message endings: fixed size, escaped delimiter, or a length prefix.

TCP چه تضمین نمی‌کند؟ / What TCP does not guarantee
// These writes are not guaranteed to be separate server reads.
await stream.WriteAsync(headerBytes, cancellationToken);
await stream.WriteAsync(payloadBytes, cancellationToken);

// A read may return fewer bytes than requested.
int count = await stream.ReadAsync(buffer, cancellationToken);

TCP ترتیب byteها را حفظ می‌کند، نه این‌که هر write دقیقاً یک read شود. اندازهٔ بافر هم مرز پیام نیست. اگر parser با فرض «یک read برابر یک پیام» نوشته شود، زیر بار یا با packet segmentation تصادفی خراب می‌شود.

TCP preserves byte order, not one-write-to-one-read behavior. Buffer size is not a message boundary. A parser assuming one read equals one message will fail under load or different packet segmentation.

قرارداد ساده: طول ۴ بایتی، بعد payloadA simple contract: four-byte length, then payload

برای آزمایش، اول ۴ byte طول را به ترتیب network byte order می‌فرستیم، بعد payload UTF-8. گیرنده اول header کامل را جمع می‌کند، طول را validate می‌کند و فقط بعد به اندازهٔ مشخص payload می‌خواند. هیچ‌وقت طول اعلام‌شده را بی‌حد allocation نکن؛ peer می‌تواند طول جعلی بفرستد.

For this experiment, send a four-byte network-byte-order length followed by a UTF-8 payload. The receiver reads the complete header, validates its size, then reads exactly the payload length. Never allocate without a bound based solely on the peer’s claimed length.

نوشتن frame / Write a frame
static async Task WriteFrameAsync(
    Stream stream, string message, CancellationToken ct)
{
    byte[] payload = Encoding.UTF8.GetBytes(message);
    if (payload.Length > 1_048_576)
        throw new InvalidDataException("Frame too large");

    byte[] header = new byte[4];
    BinaryPrimitives.WriteInt32BigEndian(header, payload.Length);
    await stream.WriteAsync(header, ct);
    await stream.WriteAsync(payload, ct);
}

هر دو سمت باید روی signed/unsigned بودن و حداکثر طول توافق کنند. این نمونه از عدد signed استفاده می‌کند و طول منفی را گیرنده رد می‌کند. write کردن header و body جداست اما گیرنده آن را frame واحد می‌بیند چون خود پروتکل مرز را تعریف کرده است.

Both sides must agree on signedness and maximum length. This example uses a signed integer, so the receiver rejects negative values. Header and body are written separately, yet the receiver reconstructs one frame because the protocol defines its boundary.

ReadAsync یعنی «تا اینجا»، نه «همه‌اش»ReadAsync means “some bytes,” not “all of them”

برای header چهار بایتی ممکن است read اول فقط دو byte بدهد؛ حلقه باید تا تکمیل header جلو برود. وقتی read صفر می‌دهد، طرف مقابل graceful shutdown کرده؛ اگر وسط frame باشد، پیام ناقص است و باید خطای پروتکل محسوب شود. cancellation و پایان peer را از هم تفکیک کن.

A read for a four-byte header may return only two bytes; loop until the header is complete. A zero-byte read indicates graceful peer shutdown; in the middle of a frame, the message is truncated and should be treated as a protocol error. Distinguish cancellation from peer closure.

خواندن دقیق / Read exactly
static async Task ReadExactlyAsync(
    Stream stream, Memory<byte> buffer, CancellationToken ct)
{
    int offset = 0;
    while (offset < buffer.Length)
    {
        int read = await stream.ReadAsync(buffer[offset..], ct);
        if (read == 0)
            throw new EndOfStreamException("Peer closed mid-frame");
        offset += read;
    }
}

helper عمداً هیچ retry خودکاری روی اتصال تازه نمی‌زند؛ اتصال peer بسته‌شده یک رخداد lifecycle است. در .NET جدید می‌توان از ReadAtLeastAsync استفاده کرد، ولی پیام framing را خودش حل نمی‌کند و برای EOF ناقص همچنان سیاست لازم است.

The helper deliberately does not reconnect automatically; a closed peer is a connection-lifecycle event. Newer .NET versions offer ReadAtLeastAsync, but it does not solve message framing and you still need an incomplete-EOF policy.

TcpListener و TcpClient برای تمرین کافی‌اندTcpListener and TcpClient are enough for this lab

TcpListener روی loopback و یک پورت انتخابی گوش می‌دهد؛ TcpClient وصل می‌شود و NetworkStream را می‌گیریم. برای این فصل فقط یک client و payload محدود می‌خواهیم. سرویس production باید هم‌زمانی اتصال، احراز هویت، TLS، backpressure، محدودیت frame، timeout، مدیریت خطا و shutdown را هم حل کند؛ listener آموزشی را اینترنتی منتشر نکن.

TcpListener listens on loopback at a chosen port; TcpClient connects and exposes a NetworkStream. This chapter needs one client and bounded payloads. A production service must also address concurrent connections, authentication, TLS, backpressure, frame limits, timeouts, errors and shutdown; do not expose this teaching listener to the internet.

listener محلی / Local listener
var listener = new TcpListener(IPAddress.Loopback, 5055);
listener.Start();
try
{
    using TcpClient peer = await listener.AcceptTcpClientAsync(ct);
    await using NetworkStream stream = peer.GetStream();
    string message = await ReadFrameAsync(stream, ct);
    Console.WriteLine(message);
}
finally
{
    listener.Stop();
}

برای تمرین فقط loopback را bind کردیم تا سرویس از شبکهٔ بیرون قابل‌دسترسی نباشد. NetworkStream lifetime client را جادویی مدیریت نمی‌کند؛ owner اتصال را dispose می‌کنیم و listener را در finally می‌بندیم. socket، firewall یا TLS در این مثال کامل آموزش داده نمی‌شود.

We bind to loopback so the exercise is not reachable from outside. NetworkStream does not magically own the client’s lifetime; dispose the connection owner and stop the listener in finally. This example is not a full socket, firewall or TLS lesson.

طول، طول byte است نه طول charLength counts bytes, not characters

متن فارسی هر حرف را الزاماً با یک byte UTF-8 نشان نمی‌دهد. اگر طول string.Length را بفرستی و receiver آن را byte count فرض کند، frame می‌شکند. اول encode، بعد طول byteها را بگیر؛ سمت دریافت نیز دقیقاً همان تعداد byte را بخوان و سپس UTF-8 را decode کن. برای frameهای بزرگ، allocation و decoding مرحله‌ای را جدا بررسی کن.

A Persian character is not necessarily one UTF-8 byte. Sending string.Length as a byte count breaks framing. Encode first, count bytes, read exactly that many bytes at the receiver, and only then decode UTF-8. For large frames, consider allocation and incremental decoding separately.

خواندن frame / Read a frame
static async Task<string> ReadFrameAsync(
    Stream stream, CancellationToken ct)
{
    byte[] header = new byte[4];
    await ReadExactlyAsync(stream, header, ct);
    int length = BinaryPrimitives.ReadInt32BigEndian(header);
    if (length < 0 || length > 1_048_576)
        throw new InvalidDataException("Invalid frame length");

    byte[] payload = new byte[length];
    await ReadExactlyAsync(stream, payload, ct);
    return new UTF8Encoding(false, true).GetString(payload);
}

UTF-8 strict در این نمونه byte نامعتبر را می‌گیرد به‌جای این‌که بی‌صدا replacement character بسازد. حد یک مگابایت قرارداد همین آزمایش است، نه حد استاندارد TCP؛ در سیستم واقعی بر اساس payload و ظرفیت انتخاب و مستند کن.

Strict UTF-8 detects invalid bytes rather than silently inserting replacement characters. The one-megabyte limit is this lab’s contract, not a TCP standard; choose and document a bound for the real workload.

خطای شبکه را به پیام پروتکل تبدیل نکنDo not confuse network failures with protocol messages

connection refused یعنی listener نپذیرفته؛ timeout یعنی deadline گذشته؛ EOF وسط body یعنی frame ناقص؛ طول نامعتبر یعنی peer قرارداد را نقض کرده. این‌ها علت‌های یکسانی نیستند. برای هرکدام log شامل endpoint محلی/دور، مرحلهٔ پروتکل، شناسهٔ اتصال و اندازهٔ frame بگذار، اما payload حساس را ثبت نکن. retry اتصال شاید امن باشد؛ retry پیامِ تغییردهندهٔ وضعیت بدون idempotency نه.

Connection refused means no listener accepted; timeout means the deadline elapsed; EOF mid-body means a truncated frame; invalid length means the peer violated the contract. These are different causes. Log local/remote endpoints, protocol phase, connection ID and frame size without sensitive payloads. Reconnecting may be safe; retrying a state-changing message without idempotency may not be.

پاسخ فنیTechnical reasoning

length را decode و حداقل/حداکثر را پیش از ساخت آرایه validate کن.

peer طول چند گیگابایتی می‌فرستد؛ سقف امن و پاسخ پروتکل را طراحی کن.

پاسخ فنیTechnical reasoning

حد صریح متناسب با workload بگذار و connection متخلف را کنترل‌شده ببند؛ allocation براساس دادهٔ peer بی‌حد ممنوع است.

پاسخ فنیTechnical reasoning

طول byte array رمزگذاری‌شده را در header بگذار، نه تعداد charها را.

Put the encoded byte-array length in the header, not the number of characters.

دو پیاده‌سازی length را با ترتیب متفاوت می‌خوانند؛ big-endian را در تست ثابت کن.

پروتکل newline-delimited متن چندخطی را می‌شکند؛ دو راه repair را مقایسه کن.

پاسخ فنیTechnical reasoning

escaping دقیق delimiter یا طول‌پیشوند انتخاب کن؛ برای body آزاد، length-prefix معمولاً ساده‌تر است.

۱۰) UTF-8 نامعتبر10) Invalid UTF-8

payload byte نامعتبر دارد؛ decoder باید رفتار strict و تست‌شده داشته باشد.

token را به ReadAsync بده و cancellation را از EOF و protocol error جدا گزارش کن.

آزمایشگاه ناخواسته روی همهٔ interfaceها listen می‌کند؛ exposure را محدود و verify کن.

۱۳) reconnect و duplicate13) Reconnects and duplicates

بعد از قطع مبهم connection، client پیام پرداخت را دوباره می‌فرستد؛ خطر و پروتکل repair را توضیح بده.

After an ambiguous disconnect, a client resends a payment message; explain the risk and protocol fix.

پاسخ فنیTechnical reasoning

قطع اتصال نشان نمی‌دهد عملیات سمت سرور انجام نشده؛ request ID idempotent و query نتیجه لازم است.

۱۴) چند frame روی یک اتصال14) Multiple frames per connection

یک client سه frame پشت‌سرهم می‌فرستد؛ loop receiver را بدون گم‌شدن مرزها بساز.

A client sends three frames in sequence; build a receiver loop that preserves boundaries.

پاسخ فنیTechnical reasoning

برای هر frame header و سپس دقیقاً body را بخوان تا EOF؛ state هر پیام را از بعدی جدا کن.

For each frame, read the header then exact body until EOF; keep message state separate.

پاسخ فنیTechnical reasoning

SocketException و local endpoint را ثبت؛ process صاحب پورت را پیدا و تست را به port تخصیصی منتقل کن.

۱۶) incident پیام‌های تکه‌تکه16) Split-message incident

تست فقط گاهی JSON ناقص می‌خواند؛ framing، partial read، EOF و max length را در incident report بررسی کن.

A test intermittently reads incomplete JSON; investigate framing, partial reads, EOF and maximum length in an incident report.

پاسخ فنیTechnical reasoning

یک read را message ندان؛ length-prefix و ReadExactly، سقف frame و تست chunkهای تصادفی بساز، بعد اتصال را محلی و قابل‌بازتولید نگه دار.

آزمایشگاه: پیام‌رسان loopbackLab: a loopback message exchange

یک server و client روی loopback بساز که frame طول‌پیشوند UTF-8 تبادل کنند. متن فارسی، body خالی، چند frame پشت‌سرهم، header تکه‌تکه، EOF وسط body، طول منفی و frame بزرگ را تست کن. فقط تست‌ها را به یک stream واقعی سریع‌ـ‌تحویل وابسته نکن؛ یک stream آزمایشی بنویس که chunkهای کوچک و تصادفی برگرداند. cancellation و shutdown تمیز را اضافه کن؛ listener را روی interface عمومی باز نگذار.

Build a loopback server and client exchanging length-prefixed UTF-8 frames. Test Persian text, empty bodies, multiple frames, split headers, EOF mid-body, negative lengths and oversized frames. Do not rely only on a fast local stream; write a test stream that returns small randomized chunks. Add cancellation and graceful shutdown, and never bind the listener publicly.

  2. Encode lengths using network byte order.
  3. برای هر malformed frame، نوع خطا را جدا assert کن.
  4. Assert a distinct failure for each malformed frame.
  5. یک بازهٔ طولانی اجرا کن و مطمئن شو منابع آزاد می‌شوند.
  6. Run repeatedly and verify resources are released.

TCP بایت را تحویل می‌دهد؛ پیام را تو تعریف می‌کنیTCP delivers bytes; you define messages

TCP ترتیب جریان را می‌دهد، نه مرز پیام یا طول امن. قرارداد framing، خواندن دقیق، حد اندازه، encoding و رفتار EOF باید کنار هم باشند. برای برنامهٔ معمول وب، HTTP این framing و معنا را از قبل تعریف می‌کند؛ socket خام وقتی ارزش دارد که نیاز پروتکل مشخصی داشته باشی، نه فقط برای حذف چند خط کد. در فصل بعد از socket پایین‌تر نمی‌رویم؛ process محلی را اجرا می‌کنیم و exit code و streamهای خروجی‌اش را مثل یک شبکهٔ کوچک مدیریت می‌کنیم.

TCP provides ordered bytes, not message boundaries or safe lengths. Framing, exact reads, size limits, encoding and EOF behavior belong together. For ordinary web applications, HTTP already defines these semantics; raw sockets are justified by a specific protocol need, not merely fewer lines of code. Next we run a local process and manage its exit code and output streams like another system boundary.
