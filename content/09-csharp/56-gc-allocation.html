GC، ریشه و هزینهٔ تخصیص

GC, roots and allocation cost

سرویس بعد از چند ساعت حافظهٔ بیشتری می‌گیره. اولین پیشنهاد تیم این هست: «هر دقیقه GC.Collect() بزنیم.» اما GC حافظه‌ای رو که هنوز reachable هست آزاد نمی‌کنه؛ حتی ممکنه collection اجباری مکث و CPU بیشتری بسازد. این فصل از symptom شروع می‌کنه: چه مقدار تخصیص داریم، چه چیزی زنده مانده، و آیا اصلاً managed heap مقصر هست؟

After several hours, a service uses more memory. The first suggestion is: “Call GC.Collect() every minute.” But GC cannot reclaim objects that are still reachable, and forced collections may add pauses and CPU cost. We begin with the symptom: how much is allocated, what remains alive, and whether the managed heap is even responsible.

حافظهٔ process با حافظهٔ اشیای زنده یکی نیستProcess memory is not the same as live-object memory

working set می‌گه چه مقدار صفحه از حافظهٔ process اکنون در RAM هست؛ managed heap اندازهٔ دیگری هست؛ و مجموع حافظهٔ native، stackها، JIT و mappingها هم در working set جا می‌گیرن. پس بالا بودن RAM به‌تنهایی اثبات memory leak در objectهای managed نیست. ابتدا ابزار رو انتخاب کن: allocation rate برای سرعت ساخت object، heap size برای اندازهٔ heap، و dump برای فهم اینکه چه referenceهایی object رو زنده نگه داشته‌اند.

Working set measures process pages currently resident in RAM; managed heap size is a different quantity, while native allocations, stacks, JIT and mappings also contribute to working set. High RAM alone does not prove a managed-object leak. Choose evidence first: allocation rate for object creation, heap size for heap size, and a dump to identify references keeping objects alive.

دیدن counterهای runtime / Monitor runtime counters
dotnet-counters monitor --process-id 1234
# در صورت نیاز، provider را محدود کن / Optionally scope the provider
dotnet-counters monitor --process-id 1234 --counters System.Runtime

نام process رو با PID واقعی جایگزین کن. ابزارهای diagnostic باید به process دسترسی داشته باشن و ممکنه در container یا محیط محدود نیاز به تنظیم داشته باشن. counter نمونه‌برداری هست، نه تشخیص قطعی: روند چند دقیقه‌ای رو زیر بار بازتولیدپذیر با زمان درخواست، CPU و خطاها کنار هم ببین.

Replace the PID with the real process ID. Diagnostic tools need access to the process and may require configuration in a container or restricted environment. Counters are sampled evidence, not a diagnosis: correlate trends over a reproducible workload with request duration, CPU and errors.

GC از روی root می‌فهمد چه چیزی هنوز لازمهGC uses roots to determine what is still needed

GC از rootهایی مثل localهای زندهٔ stack، static fieldها، registerها و handleها مسیر referenceها رو دنبال می‌کنه. اگه object از root قابل‌دسترسی باشه، زباله نیست؛ حتی اگه از نگاه محصول دیگر به درد نخورد. یک cache static بدون سقف، event subscription فراموش‌شده یا dictionary که رکوردها رو حذف نمی‌کنه می‌تونه همه‌چیز رو reachable نگه داره. سؤال درست «چرا GC جمع نکرد؟» نیست؛ «چه کسی هنوز reference داره؟» هست.

GC follows references from roots such as live stack locals, static fields, registers and handles. If an object is reachable from a root, it is not garbage—even if the product no longer needs it. An unbounded static cache, forgotten event subscription or dictionary that never removes entries can keep everything reachable. The useful question is not “Why didn’t GC collect?” but “Who still holds a reference?”

یک root ماندگار / A long-lived root
static readonly Dictionary<string, byte[]> Cache = new();

void Add(string key, byte[] value)
{
    Cache[key] = value; // stays reachable until removed
}

وجود static ذاتاً leak نیست؛ ممکنه cache عمداً داده نگه داره. ظرفیت، eviction، اندازهٔ value، tenant isolation و invalidation رو تعریف کن. در dump، مسیر ریشه‌یابی‌شده رو از root تا object دنبال کن و قبل از حذف reference مطمئن شو آن object هنوز برای درخواست فعال لازم نیست.

A static field is not inherently a leak; a cache may intentionally retain data. Define capacity, eviction, value size, tenant isolation and invalidation. In a dump, trace the path from a root to the object, and before removing a reference verify that no active request still needs it.

نسل‌ها یک فرض مفید دربارهٔ عمر objectها هستنGenerations are a useful hypothesis about object lifetimes

objectهای تازه معمولاً در Gen 0 میان. اگه collection رخ دهد و زنده بمانند، به Gen 1 و بعد Gen 2 ارتقا پیدا می‌کنن. خیلی از objectهای request عمر کوتاه دارن؛ برای همین جمع‌کردن ناحیهٔ جوان اغلب ارزان‌تر از پیمایش کل heap هست. این‌ها تضمین عمر object نیستن و نباید منطق برنامه رو به شمارهٔ generation گره بزنی. Gen 2 collection همهٔ نسل‌های جوان‌تر رو هم شامل می‌شه و می‌تونه پرهزینه‌تر باشه.

New objects usually start in Gen 0. If they survive collections, they are promoted to Gen 1 and then Gen 2. Many request objects are short-lived, so collecting a young region is often cheaper than traversing the entire heap. These generations do not guarantee object lifetimes; application logic must not depend on generation numbers. A Gen 2 collection includes younger generations and can cost more.

نسل، مدل تشخیصی است / Generations as a diagnostic model
int generation = GC.GetGeneration(suspect);
Console.WriteLine($"Generation: {generation}");
Console.WriteLine($"Gen 0 count: {GC.CollectionCount(0)}");
Console.WriteLine($"Gen 1 count: {GC.CollectionCount(1)}");
Console.WriteLine($"Gen 2 count: {GC.CollectionCount(2)}");

این snapshot فقط یک لحظه و یک process رو نشان می‌ده. برای نتیجه، شمارنده‌ها رو پیش و پس از workload مقایسه کن. زیادشدن Gen 0 به‌تنهایی مشکل نیست؛ نرخ allocation بالا همراه با زمان زیاد در GC، Gen 2های پرتکرار یا latency بدتر ارزش بررسی داره.

This snapshot describes one process at one moment. Compare counters before and after a workload. A high Gen 0 count alone is not a problem; high allocation combined with time in GC, frequent Gen 2 collections or worse latency merits investigation.

آرایهٔ بزرگ مسیر GC رو تغییر می‌دهLarge arrays change the GC path

در پیاده‌سازی رایج .NET، objectهای حدود ۸۵٬۰۰۰ بایت و بزرگ‌تر وارد Large Object Heap می‌شن؛ آستانه و جزئیات اجرایی رو hard-code نکن، چون implementation هست. LOH همراه collection نسل ۲ بررسی می‌شه و معمولاً مثل heap کوچک compact نمی‌شه، چون جابه‌جایی object بزرگ هزینه داره. ساخت مکرر آرایهٔ بزرگ می‌تونه فشار، fragmentation و جهش حافظه ایجاد کند؛ اما پایین‌بودن تعدادشان هم تضمین سلامت نیست.

In common .NET implementations, objects around 85,000 bytes or larger go to the Large Object Heap; do not hard-code the threshold or implementation details. The LOH is collected with Gen 2 and is generally not compacted like the small-object heap because moving large objects is costly. Repeated large-array allocation can create pressure, fragmentation and memory spikes, but a low count does not prove the system is healthy.

آرایهٔ بزرگ و هزینهٔ تکرار / Repeated large allocations
byte[] payload = new byte[100_000];
// Ask: is this per request, per connection, or reused?
// Measure before pooling or changing the design.

قبل از poolکردن، اندازه و lifetime آرایه، peak هم‌زمانی و نرخ ساخت رو پیدا کن. pooling فصل قبل تنها وقتی کمک می‌کنه که چرخهٔ اجاره و بازگشت درست باشه و benchmark نشان دهد بهبود واقعی داریم. خروجی فایل یا شبکه رو chunk کن فقط اگه protocol و طراحی اجازه می‌دن؛ کوچک‌کردن buffer ممکنه تعداد I/O رو بالا ببرد.

Before pooling, identify array size, lifetime, concurrency peak and creation rate. Pooling from the previous chapter helps only with a correct rent/return lifecycle and a measured improvement. Chunk file or network output only when the protocol and design allow it; smaller buffers may increase I/O calls.

GC حافظهٔ managed رو مدیریت می‌کنه، نه هر منبعی راGC manages managed memory, not every resource

فایل، socket، handle و اتصال دیتابیس منابع محدودی هستن و باید deterministic آزاد بشن؛ منتظر GC نمان. IDisposable/using برای پایان قابل‌پیش‌بینی هست. finalizer آخرین پشتیبان برای بعضی resourceهای unmanaged هست، نه جایگزین Dispose: اجرای آن زمان مشخص نداره و object رو دست‌کم تا چرخهٔ finalization نگه می‌داره. SafeHandle رو برای wrapper امن handle ترجیح بده، نه finalizer دست‌ساز در هر کلاس.

Files, sockets, handles and database connections are scarce resources and should be released deterministically; do not wait for GC. IDisposable/using provides predictable cleanup. A finalizer is a last-resort fallback for some unmanaged resources, not a replacement for Dispose: its timing is unspecified and finalization keeps the object alive for at least another stage. Prefer SafeHandle for safe handle wrappers over hand-written finalizers in every class.

مدیریت deterministic / Deterministic cleanup
await using var connection = new SomeAsyncResource();
await connection.OpenAsync(ct);
await DoWorkAsync(connection, ct);
// DisposeAsync runs even if an exception occurs.

نام type در این مثال نمایشی هست؛ در برنامهٔ واقعی interface و الگوی async-dispose همان کتابخانه رو بررسی کن. Dispose باید idempotent بودن یا محدودیتش رو مستند کند. یک object managed می‌تونه wrapper یک منبع native باشه؛ GC wrapper رو می‌شناسد، اما پایان عمر wrapper به‌تنهایی زمان آزادشدن منبع رو تضمین نمی‌کنه.

The type name here is illustrative; verify the actual library’s interface and async-disposal pattern. Document whether Dispose is idempotent or has restrictions. A managed object can wrap a native resource; GC tracks the wrapper, but the wrapper’s eventual collection alone does not guarantee timely resource release.

از allocation تا root، یک زنجیرهٔ تشخیص بسازBuild an evidence chain from allocation to root

اگه حافظه رشد می‌کنه، ابتدا در همان workload allocation rate و heap size رو ثبت کن. اگه allocation بالاست ولی بعد از GC heap به baseline برمی‌گرده، شاید churn داریم نه leak. اگه heap پس از چند چرخه بالا می‌مونه، dump بگیر و نوع‌های غالب و مسیرهای root رو بررسی کن. اگه heap کوچک هست اما working set بزرگ، سراغ native allocation، حافظهٔ mapped، stackها و ابزارهای همان بخش برو. ابزارها رو با دسترسی و اثرشان روی process بسنج؛ dump می‌تونه حجیم و حاوی دادهٔ حساس باشه.

When memory grows, record allocation rate and heap size under the same workload. If allocation is high but the heap returns to baseline after collections, you may have churn rather than a leak. If the heap remains elevated across cycles, capture a dump and inspect dominant types and root paths. If the managed heap is small but working set is large, investigate native allocations, mapped memory and stacks. Consider tool access and process impact; dumps can be large and contain sensitive data.

یک مشاهدهٔ کوتاه / A short observation
dotnet-counters monitor --process-id 1234 --refresh-interval 2
# Run a bounded, reproducible workload in another terminal.
# Compare allocation rate, heap size, Gen counts and time in GC.

به‌جای «حافظه زیاد است»، سؤال رو دقیق کن: از چه زمانی، با چه نرخ درخواست، کدوم metric رشد می‌کنه، بعد از توقف بار چه می‌شه، و چه نوعی root path غیرمنتظره داره؟ این پرسش‌ها راه رو از حدس به آزمایش می‌برن.

Replace “memory is high” with precise questions: since when, at what request rate, which metric grows, what happens after load stops, and which type has an unexpected root path? Those questions turn guesses into experiments.
