GC، ریشه و هزینهٔ تخصیص

GC, roots and allocation cost

سرویس بعد از چند ساعت حافظهٔ بیشتری می‌گیرد. اولین پیشنهاد تیم این است: «هر دقیقه GC.Collect() بزنیم.» اما GC حافظه‌ای را که هنوز reachable است آزاد نمی‌کند؛ حتی ممکن است collection اجباری مکث و CPU بیشتری بسازد. این فصل از symptom شروع می‌کند: چه مقدار تخصیص داریم، چه چیزی زنده مانده، و آیا اصلاً managed heap مقصر است؟

After several hours, a service uses more memory. The first suggestion is: “Call GC.Collect() every minute.” But GC cannot reclaim objects that are still reachable, and forced collections may add pauses and CPU cost. We begin with the symptom: how much is allocated, what remains alive, and whether the managed heap is even responsible.

حافظهٔ process با حافظهٔ اشیای زنده یکی نیستProcess memory is not the same as live-object memory

working set می‌گوید چه مقدار صفحه از حافظهٔ process اکنون در RAM است؛ managed heap اندازهٔ دیگری است؛ و مجموع حافظهٔ native، stackها، JIT و mappingها هم در working set جا می‌گیرند. پس بالا بودن RAM به‌تنهایی اثبات memory leak در objectهای managed نیست. ابتدا ابزار را انتخاب کن: allocation rate برای سرعت ساخت object، heap size برای اندازهٔ heap، و dump برای فهم اینکه چه referenceهایی object را زنده نگه داشته‌اند.

Working set measures process pages currently resident in RAM; managed heap size is a different quantity, while native allocations, stacks, JIT and mappings also contribute to working set. High RAM alone does not prove a managed-object leak. Choose evidence first: allocation rate for object creation, heap size for heap size, and a dump to identify references keeping objects alive.

دیدن counterهای runtime / Monitor runtime counters
dotnet-counters monitor --process-id 1234
# در صورت نیاز، provider را محدود کن / Optionally scope the provider
dotnet-counters monitor --process-id 1234 --counters System.Runtime

نام process را با PID واقعی جایگزین کن. ابزارهای diagnostic باید به process دسترسی داشته باشند و ممکن است در container یا محیط محدود نیاز به تنظیم داشته باشند. counter نمونه‌برداری است، نه تشخیص قطعی: روند چند دقیقه‌ای را زیر بار بازتولیدپذیر با زمان درخواست، CPU و خطاها کنار هم ببین.

Replace the PID with the real process ID. Diagnostic tools need access to the process and may require configuration in a container or restricted environment. Counters are sampled evidence, not a diagnosis: correlate trends over a reproducible workload with request duration, CPU and errors.

GC از روی root می‌فهمد چه چیزی هنوز لازم استGC uses roots to determine what is still needed

GC از rootهایی مثل localهای زندهٔ stack، static fieldها، registerها و handleها مسیر referenceها را دنبال می‌کند. اگر object از root قابل‌دسترسی باشد، زباله نیست؛ حتی اگر از نگاه محصول دیگر به درد نخورد. یک cache static بدون سقف، event subscription فراموش‌شده یا dictionary که رکوردها را حذف نمی‌کند می‌تواند همه‌چیز را reachable نگه دارد. سؤال درست «چرا GC جمع نکرد؟» نیست؛ «چه کسی هنوز reference دارد؟» است.

GC follows references from roots such as live stack locals, static fields, registers and handles. If an object is reachable from a root, it is not garbage—even if the product no longer needs it. An unbounded static cache, forgotten event subscription or dictionary that never removes entries can keep everything reachable. The useful question is not “Why didn’t GC collect?” but “Who still holds a reference?”

یک root ماندگار / A long-lived root
static readonly Dictionary<string, byte[]> Cache = new();

void Add(string key, byte[] value)
{
    Cache[key] = value; // stays reachable until removed
}

وجود static ذاتاً leak نیست؛ ممکن است cache عمداً داده نگه دارد. ظرفیت، eviction، اندازهٔ value، tenant isolation و invalidation را تعریف کن. در dump، مسیر ریشه‌یابی‌شده را از root تا object دنبال کن و قبل از حذف reference مطمئن شو آن object هنوز برای درخواست فعال لازم نیست.

A static field is not inherently a leak; a cache may intentionally retain data. Define capacity, eviction, value size, tenant isolation and invalidation. In a dump, trace the path from a root to the object, and before removing a reference verify that no active request still needs it.

نسل‌ها یک فرض مفید دربارهٔ عمر objectها هستندGenerations are a useful hypothesis about object lifetimes

objectهای تازه معمولاً در Gen 0 می‌آیند. اگر collection رخ دهد و زنده بمانند، به Gen 1 و بعد Gen 2 ارتقا پیدا می‌کنند. خیلی از objectهای request عمر کوتاه دارند؛ برای همین جمع‌کردن ناحیهٔ جوان اغلب ارزان‌تر از پیمایش کل heap است. این‌ها تضمین عمر object نیستند و نباید منطق برنامه را به شمارهٔ generation گره بزنی. Gen 2 collection همهٔ نسل‌های جوان‌تر را هم شامل می‌شود و می‌تواند پرهزینه‌تر باشد.

New objects usually start in Gen 0. If they survive collections, they are promoted to Gen 1 and then Gen 2. Many request objects are short-lived, so collecting a young region is often cheaper than traversing the entire heap. These generations do not guarantee object lifetimes; application logic must not depend on generation numbers. A Gen 2 collection includes younger generations and can cost more.

نسل، مدل تشخیصی است / Generations as a diagnostic model
int generation = GC.GetGeneration(suspect);
Console.WriteLine($"Generation: {generation}");
Console.WriteLine($"Gen 0 count: {GC.CollectionCount(0)}");
Console.WriteLine($"Gen 1 count: {GC.CollectionCount(1)}");
Console.WriteLine($"Gen 2 count: {GC.CollectionCount(2)}");

این snapshot فقط یک لحظه و یک process را نشان می‌دهد. برای نتیجه، شمارنده‌ها را پیش و پس از workload مقایسه کن. زیادشدن Gen 0 به‌تنهایی مشکل نیست؛ نرخ allocation بالا همراه با زمان زیاد در GC، Gen 2های پرتکرار یا latency بدتر ارزش بررسی دارد.

This snapshot describes one process at one moment. Compare counters before and after a workload. A high Gen 0 count alone is not a problem; high allocation combined with time in GC, frequent Gen 2 collections or worse latency merits investigation.

آرایهٔ بزرگ مسیر GC را تغییر می‌دهدLarge arrays change the GC path

در پیاده‌سازی رایج .NET، objectهای حدود ۸۵٬۰۰۰ بایت و بزرگ‌تر وارد Large Object Heap می‌شوند؛ آستانه و جزئیات اجرایی را hard-code نکن، چون implementation است. LOH همراه collection نسل ۲ بررسی می‌شود و معمولاً مثل heap کوچک compact نمی‌شود، چون جابه‌جایی object بزرگ هزینه دارد. ساخت مکرر آرایهٔ بزرگ می‌تواند فشار، fragmentation و جهش حافظه ایجاد کند؛ اما پایین‌بودن تعدادشان هم تضمین سلامت نیست.

In common .NET implementations, objects around 85,000 bytes or larger go to the Large Object Heap; do not hard-code the threshold or implementation details. The LOH is collected with Gen 2 and is generally not compacted like the small-object heap because moving large objects is costly. Repeated large-array allocation can create pressure, fragmentation and memory spikes, but a low count does not prove the system is healthy.

آرایهٔ بزرگ و هزینهٔ تکرار / Repeated large allocations
byte[] payload = new byte[100_000];
// Ask: is this per request, per connection, or reused?
// Measure before pooling or changing the design.

قبل از poolکردن، اندازه و lifetime آرایه، peak هم‌زمانی و نرخ ساخت را پیدا کن. pooling فصل قبل تنها وقتی کمک می‌کند که چرخهٔ اجاره و بازگشت درست باشد و benchmark نشان دهد بهبود واقعی داریم. خروجی فایل یا شبکه را chunk کن فقط اگر protocol و طراحی اجازه می‌دهند؛ کوچک‌کردن buffer ممکن است تعداد I/O را بالا ببرد.

Before pooling, identify array size, lifetime, concurrency peak and creation rate. Pooling from the previous chapter helps only with a correct rent/return lifecycle and a measured improvement. Chunk file or network output only when the protocol and design allow it; smaller buffers may increase I/O calls.

GC حافظهٔ managed را مدیریت می‌کند، نه هر منبعی راGC manages managed memory, not every resource

فایل، socket، handle و اتصال دیتابیس منابع محدودی هستند و باید deterministic آزاد شوند؛ منتظر GC نمان. IDisposable/using برای پایان قابل‌پیش‌بینی است. finalizer آخرین پشتیبان برای بعضی resourceهای unmanaged است، نه جایگزین Dispose: اجرای آن زمان مشخص ندارد و object را دست‌کم تا چرخهٔ finalization نگه می‌دارد. SafeHandle را برای wrapper امن handle ترجیح بده، نه finalizer دست‌ساز در هر کلاس.

Files, sockets, handles and database connections are scarce resources and should be released deterministically; do not wait for GC. IDisposable/using provides predictable cleanup. A finalizer is a last-resort fallback for some unmanaged resources, not a replacement for Dispose: its timing is unspecified and finalization keeps the object alive for at least another stage. Prefer SafeHandle for safe handle wrappers over hand-written finalizers in every class.

مدیریت deterministic / Deterministic cleanup
await using var connection = new SomeAsyncResource();
await connection.OpenAsync(ct);
await DoWorkAsync(connection, ct);
// DisposeAsync runs even if an exception occurs.

نام type در این مثال نمایشی است؛ در برنامهٔ واقعی interface و الگوی async-dispose همان کتابخانه را بررسی کن. Dispose باید idempotent بودن یا محدودیتش را مستند کند. یک object managed می‌تواند wrapper یک منبع native باشد؛ GC wrapper را می‌شناسد، اما پایان عمر wrapper به‌تنهایی زمان آزادشدن منبع را تضمین نمی‌کند.

The type name here is illustrative; verify the actual library’s interface and async-disposal pattern. Document whether Dispose is idempotent or has restrictions. A managed object can wrap a native resource; GC tracks the wrapper, but the wrapper’s eventual collection alone does not guarantee timely resource release.

از allocation تا root، یک زنجیرهٔ تشخیص بسازBuild an evidence chain from allocation to root

اگر حافظه رشد می‌کند، ابتدا در همان workload allocation rate و heap size را ثبت کن. اگر allocation بالاست ولی بعد از GC heap به baseline برمی‌گردد، شاید churn داریم نه leak. اگر heap پس از چند چرخه بالا می‌ماند، dump بگیر و نوع‌های غالب و مسیرهای root را بررسی کن. اگر heap کوچک است اما working set بزرگ، سراغ native allocation، حافظهٔ mapped، stackها و ابزارهای همان بخش برو. ابزارها را با دسترسی و اثرشان روی process بسنج؛ dump می‌تواند حجیم و حاوی دادهٔ حساس باشد.

When memory grows, record allocation rate and heap size under the same workload. If allocation is high but the heap returns to baseline after collections, you may have churn rather than a leak. If the heap remains elevated across cycles, capture a dump and inspect dominant types and root paths. If the managed heap is small but working set is large, investigate native allocations, mapped memory and stacks. Consider tool access and process impact; dumps can be large and contain sensitive data.

یک مشاهدهٔ کوتاه / A short observation
dotnet-counters monitor --process-id 1234 --refresh-interval 2
# Run a bounded, reproducible workload in another terminal.
# Compare allocation rate, heap size, Gen counts and time in GC.

به‌جای «حافظه زیاد است»، سؤال را دقیق کن: از چه زمانی، با چه نرخ درخواست، کدام metric رشد می‌کند، بعد از توقف بار چه می‌شود، و چه نوعی root path غیرمنتظره دارد؟ این پرسش‌ها راه را از حدس به آزمایش می‌برند.

Replace “memory is high” with precise questions: since when, at what request rate, which metric grows, what happens after load stops, and which type has an unexpected root path? Those questions turn guesses into experiments.

استدلالReasoning

۴) نسل ۲4) Gen 2 collections

Gen 2 هر چند ثانیه رخ می‌دهد و p99 بدتر شده. چه شواهدی جمع می‌کنی؟

۶) cache نامحدود6) Unbounded cache

cache سرعت را بهتر کرده اما heap ماه‌به‌ماه بالا می‌رود؛ سه کنترل طراحی پیشنهاد بده.

A cache improves speed but heap rises month after month. Propose three design controls.

استدلالReasoning

ظرفیت، eviction/TTL، و سقف اندازه یا tenant quota؛ سپس hit rate و memory را بسنج.

۷) finalizer جای Dispose؟7) Finalizer instead of Dispose?

socket را فقط با finalizer آزاد می‌کنند؛ چه ریسکی دارد؟

A socket is released only by a finalizer. What is the risk?

استدلالReasoning

زمان آزادشدن نامعلوم است و منابع محدود می‌مانند؛ Dispose/using یا SafeHandle را به کار ببر.

Release timing is unspecified and scarce resources remain occupied; use Dispose/using or SafeHandle.

۸) heap جمع می‌شود، RAM نه8) Heap falls, RAM does not

بعد از بار heap کوچک شده اما working set ثابت است؛ نتیجهٔ قطعی چیست؟

After load, heap shrinks but working set stays flat. What is the definitive conclusion?

استدلالReasoning

نتیجهٔ قطعی ندارد؛ runtime ممکن است segment را نگه دارد و native memory هم مطرح است. روند و علت را بررسی کن.

None by itself; the runtime may retain segments, and native memory may contribute. Investigate trends and causes.

۹) root در event9) Event-handler root

صفحهٔ بسته‌شده زنده مانده؛ publisher سراسری event را نگه می‌دارد. اصلاح lifetime چیست؟

A closed page remains alive because a global publisher retains its event handler. Fix the lifetime.

استدلالReasoning

هنگام پایان عمر unsubscribe کن یا subscription disposable/weak و مناسب معماری بساز.

Unsubscribe when the page ends, or use a suitable disposable/weak subscription pattern.

۱۰) تخصیص و نگه‌داری10) Allocation versus retention

allocation rate بالاست ولی heap پس از بار به baseline می‌رسد؛ محتمل‌تر churn است یا retention leak؟

Allocation rate is high but heap returns to baseline after load. Is churn or retention leak more likely?

استدلالReasoning

چرخش allocation محتمل‌تر است؛ باز هم latency و GC time را برای اثر واقعی بررسی کن.

۱۱) dump حساس11) Sensitive dump

dump ممکن است token کاربر را داشته باشد؛ پیش از ارسال به همکار چه می‌کنی؟

A dump may contain user tokens. What do you do before sharing it?

۱۲) GC.Collect در هر درخواست12) GC.Collect on every request

تیم آن را برای «پاک‌کردن زودتر» اضافه کرده. چه آزمایشی تصمیم را روشن می‌کند؟

استدلالReasoning

stream/chunk، reuse کنترل‌شده یا pool را با correctness، peak concurrency و benchmark بسنج؛ اندازه را کورکورانه کم نکن.

۱۶) گزارش تشخیص رشد حافظه16) Memory-growth diagnosis

روند heap بعد از هر batch بالاتر می‌رود. symptom، آزمایش، root evidence و verification را در گزارش حادثه ثبت کن.

Heap baseline rises after every batch. Record the symptom, experiment, root evidence and verification in an incident report.

استدلالReasoning

بار تکرارپذیر، counters، dump مقایسه‌ای، نوع‌های غالب و root path لازم است؛ پس از اصلاح همان بار را تکرار و baseline را بسنج.

Use reproducible load, counters, comparable dumps, dominant types and root paths; repeat the same load after the fix and compare baselines.

آزمایشگاه: churn را از leak جدا کنLab: distinguish churn from a leak

یک برنامهٔ آزمایشی بساز که دو حالت دارد: در حالت اول objectهای موقت را می‌سازد و رها می‌کند؛ در حالت دوم آن‌ها را در cache static نگه می‌دارد. هر دو را با حجم batch محدود اجرا کن تا دستگاه تحت فشار نامحدود قرار نگیرد. با dotnet-counters allocation rate، heap size، generation counts و time in GC را ثبت کن. پس از توقف بار، برای حالت دوم مسیر root را در dump بررسی کن و مالک reference را پیدا کن. بعد cache را bounded کن یا eviction اضافه کن و همان آزمایش را تکرار کن. در پایان یک مسیر resource مثل stream را با و بدون using مقایسه کن و توضیح بده چرا این موضوع با جمع‌آوری objectهای managed یکی نیست.

Build a bounded experiment with two modes: one creates and releases temporary objects; the other retains them in a static cache. Keep batches limited so the machine is not subjected to unbounded pressure. Use dotnet-counters to record allocation rate, heap size, generation counts and time in GC. After load stops, inspect a dump for the retained mode and trace the root to its owner. Bound the cache or add eviction, then repeat the same experiment. Finally compare a stream managed with and without using, explaining why deterministic resource release differs from collecting managed objects.

  1. نمودار یا جدول counterها را برای دو حالت ثبت کن.
  2. Record counters for both modes in a chart or table.
  3. یک root path واقعی برای object نگه‌داشته‌شده مشخص کن.
  4. Identify a real root path for a retained object.
  5. پس از اصلاح، همان batch را دوباره اجرا و baseline را مقایسه کن.
  6. Repeat the same batch after the fix and compare the baseline.

GC زباله را جمع می‌کند، نه reference اشتباه راGC collects garbage, not incorrect references

نسل‌ها به runtime کمک می‌کنند objectهای کوتاه‌عمر را اقتصادی‌تر جمع کند. LOH و تخصیص‌های بزرگ باید با نرخ، عمر و concurrency سنجیده شوند. حافظهٔ بالا می‌تواند allocation churn، reference ماندگار یا native memory باشد؛ این‌ها symptomهای متفاوت‌اند. forced collection معمولاً جای اصلاح root، lifetime یا allocation pattern را نمی‌گیرد. حالا که روش سنجش را داریم، فصل بعد تست‌های خودکار می‌سازیم تا رفتار درست را در هر تغییر حفظ کنیم.

Generations help the runtime collect short-lived objects efficiently. LOH and large allocations must be assessed by rate, lifetime and concurrency. High memory may mean allocation churn, retained references or native memory—different symptoms with different causes. Forced collection rarely replaces fixing roots, lifetimes or allocation patterns.
