پروژهٔ ۱ — ابزار خط فرمان واقعی

Project 1 — a real command-line tool

تیم عملیات هر شب چند فایل رویداد را دستی می‌خواند و CSV گزارش می‌سازد. گاهی سطر خراب کل کار را متوقف می‌کند؛ گاهی هم معلوم نیست برنامه چند رکورد را پردازش کرده. مأموریت تو ساخت یک CLI است که ورودی را ایمن بخواند، خطا را قابل‌تشخیص گزارش کند، cancellation را رعایت کند و نفر دیگری بتواند با یک دستور آن را build، test و اجرا کند.

Operations manually reads event files and creates CSV reports every night. One malformed row sometimes stops everything, and it is unclear how many records were processed. Build a CLI that reads input safely, reports actionable errors, honors cancellation, and lets another developer build, test and run it with documented commands.

مأموریت: لاگ خام را به گزارش قابل‌اعتماد تبدیل کنMission: turn raw logs into a trustworthy report

یک فایل UTF-8 شامل رویدادهای جداشده با pipe داری: timestamp، level، code و message. برنامه باید فایل یا پوشهٔ ورودی بگیرد و گزارش خلاصهٔ JSON تولید کند: تعداد هر level، بازهٔ زمانی و تعداد سطرهای نامعتبر. پیام می‌تواند delimiter داشته باشد، فایل ممکن است خالی یا بزرگ باشد و خروجی نباید بی‌دلیل کل فایل را در حافظه نگه دارد. قرارداد input را خودت در README دقیق کن.

Input is a UTF-8 pipe-delimited event file with timestamp, level, code and message. The CLI accepts a file or directory and emits a JSON summary: counts by level, time range and malformed-row count. A message may contain delimiters, files may be empty or large, and the entire input should not be retained needlessly. Define the exact input contract in your README.

مرز پروژه: فقط فایل‌های ساختگی و یک output directory آزمایشی. فایل‌های شخصی، system log و مسیرهای مهم را وارد نکن. برنامه نباید ورودی را overwrite کند یا فایل را حذف کند.

Project boundary: use synthetic files and a disposable output directory. Do not process personal/system logs or important paths. The tool must never overwrite its input or delete files.

قرارداد خروجی را پیش از پیاده‌سازی ببندDefine the output contract before implementing

  • فرمان شامل ورودی، مسیر خروجی و گزینهٔ strict برای توقف روی اولین سطر خراب باشد.
  • The command accepts input, output path and a strict mode that stops on the first malformed row.
  • خروجی JSON با encoding روشن و ترتیب قابل‌تکرار تولید شود.
  • Emit JSON with explicit encoding and deterministic ordering.
  • خطاها روی stderr، نتیجه/خلاصهٔ موفق روی stdout و exit code معنادار باشد.
  • Errors go to stderr, successful summaries to stdout, with meaningful exit codes.
  • فایل با stream خوانده شود؛ cancellation بین batchها و I/O propagation داشته باشد.
  • Read via streams and propagate cancellation through I/O and processing batches.
  • هیچ password، token یا secret واقعی در config یا fixture نیست.
  • No real password, token or secret appears in configuration or fixtures.

می‌توانی syntax آرگومان را خودت طراحی کنی یا از package معتبر استفاده کنی. معیار پروژه نام library نیست؛ validation، help، خروجی و کد خروج باید قرارداد تست‌شده داشته باشند.

You may design argument syntax or use a reputable package. The project is not about a particular library; validation, help, output and exit codes must have tested contracts.

هفت مرحله تا تحویلSeven milestones to delivery

  1. نمونهٔ ورودی: ۵ fixture بساز: عادی، خالی، timestamp نامعتبر، پیام دارای pipe و فایل بزرگ ساختگی.
  2. Input fixtures: create five cases: normal, empty, invalid timestamp, message containing a pipe and a synthetic large file.
  3. مدل: event و summary را تعریف کن؛ invariantها را قبل از CLI تست کن.
  4. Model: define event and summary types; test invariants before the CLI.
  5. ورودی: parser خط‌به‌خط و cancellation را اضافه کن؛ malformed row را با شمارهٔ خط گزارش بده.
  6. Input: add line-based parsing and cancellation; report malformed rows with line numbers.
  7. CLI: help، validation، stdout/stderr و exit code را تفکیک کن.
  8. CLI: separate help, validation, stdout/stderr and exit-code behavior.
  9. خروجی: JSON را در فایل موقت بنویس، سپس طبق policy به مقصد منتقل کن تا failure خروجی ناقص جا نگذارد.
  10. Output: write JSON to a temporary file and move it according to policy so failures do not leave a partial report.
  11. تست: unit test برای parser/summary و integration test محدود برای فایل واقعی بساز.
  12. Tests: write unit tests for parsing/summary and a bounded integration test for real files.
  13. تحویل: Release publish، نمونهٔ command، limitation و clean-checkout test را مستند کن.
  14. Handoff: document Release publish, sample commands, limitations and a clean-checkout test.

معیار قبولی: رفتار با مدرکAcceptance: behavior backed by evidence

  • `--help` بدون ورودی هم exit code صفر و راهنمای درست دارد.
  • --help exits successfully and documents usage without requiring input.
  • مسیر نامعتبر یا output parent ناموجود، خطای روشن در stderr و کد غیرصفر می‌دهد.
  • Invalid paths or a missing output parent produce clear stderr and a nonzero code.
  • روی fixture معتبر countها و time range با expected assert می‌شوند.
  • Counts and time range for a valid fixture are asserted against expected values.
  • در حالت tolerant، سطر خراب شمرده و processing ادامه می‌یابد؛ در strict، رفتار مشخص و تست‌شده است.
  • Tolerant mode counts malformed rows and continues; strict behavior is explicit and tested.
  • در cancellation، عملیات متوقف می‌شود و report ناقص به‌عنوان report نهایی جا نمی‌ماند.
  • Cancellation stops work and does not leave a partial report presented as final.
  • یک clone تمیز با `dotnet test` و دستور مستند اجرا می‌شود.
  • A clean clone runs with the documented dotnet test and CLI commands.

سه خرابی عمدیThree deliberate failures

بعد از کارکرد مسیر اصلی، هر خرابی را جدا بازتولید کن و evidence قبل/بعد را نگه دار:

After the happy path works, reproduce each failure independently and keep before/after evidence:

  • Encoding اشتباه: fixture UTF-8 فارسی بساز و parser را موقتاً با encoding ناسازگار اجرا کن؛ متن خراب را پیدا و اصلاح کن.
  • Wrong encoding: create a Persian UTF-8 fixture, run the parser with an incompatible encoding, identify corruption and fix it.
  • خروجی ناقص: هنگام نوشتن cancellation ایجاد کن؛ ثابت کن temp output به‌عنوان نتیجهٔ نهایی باقی نمی‌ماند.
  • Partial output: cancel during writing and prove the temporary file is not left as a final report.
  • پوشه به‌جای فایل: مسیر ورودی اشتباه را بده؛ خطا نباید stack trace نامفهوم یا exit code صفر تولید کند.
  • Directory passed as a file: provide the wrong input shape; the tool must not return a confusing stack trace or exit code zero.
راهنما: از کجا تشخیص را شروع کنم؟Hint: where should diagnosis begin?

اول آرگومان parseشده، نوع filesystem object و encoding را چاپ/ثبت کن؛ بعد exception اصلی و cleanup path را بررسی کن. قبل از تغییر، reproduction کوچک بساز.

Inspect parsed arguments, filesystem object type and encoding first; then examine the root exception and cleanup path. Make a minimal reproduction before changing code.

بازبینی نهاییFinal review

یک هم‌تیمی باید بتواند بدون پیام‌دادن به تو بفهمد چه ورودی مجاز است، خروجی کجا می‌رود، هر exit code چه معنایی دارد و چطور تست‌ها اجرا می‌شوند. آیا مسیر فایل با ترکیب pathها از پوشهٔ مجاز خارج می‌شود؟ آیا cancellation فایل اصلی را خراب می‌کند؟ آیا پیام خطا line number دارد اما محتوای حساس را لو نمی‌دهد؟ این‌ها را در README و تست‌ها جواب بده.

A teammate should understand valid inputs, output location, exit-code meanings and how to run tests without asking you. Can path combination escape the allowed folder? Can cancellation damage an existing file? Does an error include a line number without leaking sensitive contents? Answer these in tests and the README.

اگر گیر کردی، راهنمای مرحله‌ایIf stuck, use the staged hints

راهنما ۱ — اول طراحی، نه command lineHint 1 — design before the CLI

parser را تابعی جدا با ورودی متن و نتیجهٔ typed بساز؛ خطای هر row را به شمارهٔ خط وصل کن.

Make parsing a separate function returning typed results; attach row errors to line numbers.

راهنما ۲ — خطا و داده را قاطی نکنHint 2 — separate errors from data

مدل نتیجهٔ هر سطر می‌تواند parsed event یا parse issue باشد؛ tolerant/strict policy در لایهٔ orchestration تصمیم بگیرد.

A row result can be either an event or a parse issue; orchestration chooses tolerant or strict policy.

راهنما ۳ — خروجی اتمیکHint 3 — atomic output

در همان directory یک فایل موقت یکتا بنویس، flush/close کن و بعد move/replace را طبق policy انجام بده. cleanup را در finally بگذار.

Write a unique temporary file in the same directory, flush/close it, then move/replace according to policy. Clean up in finally.

طرح مرجع — بعد از ساخت خودت ببینReference design — inspect after your own attempt

این یک implementation یگانه نیست؛ این مرزها را نگه دار و syntax را با نسخهٔ SDK پروژه هماهنگ کن:

This is not the only valid implementation. Preserve these boundaries and adapt syntax to the project's SDK:

  1. EventParser یک line را به event یا issue تبدیل می‌کند و به فایل/کنسول وابسته نیست.
  2. EventParser converts one line into an event or issue and knows nothing about files or consoles.
  3. ReportBuilder فقط summary را از stream رویدادها می‌سازد و هیچ I/O ندارد.
  4. ReportBuilder builds the summary from events without performing I/O.
  5. CliOptions ورودی/خروجی، mode و help را validate می‌کند؛ command handler exit code را تعیین می‌کند.
  6. CliOptions validates paths, mode and help; the command handler selects the exit code.
  7. reader با FileStream/StreamReader و token استفاده می‌شود؛ برای فایل حجیم همهٔ lineها را در List انباشته نکن.
  8. Read with FileStream/StreamReader and a token; do not accumulate every line of a large file in a List.
  9. serializer فقط DTO خروجی را می‌نویسد. ابتدا temp file و سپس commit به مقصد؛ overwrite policy صریح باشد.
  10. Serialize only the output DTO. Write to a temporary file, then commit; define overwrite policy explicitly.
  11. log عملیاتی روی stderr/ILogger، خروجی ماشینی در فایل؛ این دو channel را مخلوط نکن.
  12. Operational logs go to stderr/ILogger and machine output to the file; keep channels separate.
  13. تست unit برای parser و aggregation، integration test برای filesystem موقت؛ ساعت و cancellation کنترل‌شده.
  14. Unit-test parsing/aggregation, integration-test a temporary filesystem, and control time/cancellation.

قبولی با معماری قشنگ نیست؛ acceptance را اجرا کن، output واقعی را نگه دار و محدودیت‌هایی را که حل نکرده‌ای صادقانه بنویس.

A pretty architecture does not pass the project. Run acceptance checks, retain real outputs and state unresolved limitations honestly.

ابزار تو باید برای شیفت بعدی قابل‌اعتماد باشدYour tool should be trustworthy for the next shift

وقتی خروجی، خطا و cancellation قرارداد روشن دارند، این برنامه از یک script شخصی به ابزار تیم تبدیل می‌شود. پروژهٔ بعدی همین discipline را به library عمومی می‌برد: دیگر فقط خودت consumer نیستی؛ هر تصمیم public API می‌تواند روی کاربران package اثر بگذارد.

When output, errors and cancellation have clear contracts, a personal script becomes a team tool. The next project applies the same discipline to a public library: you are no longer the only consumer, and every public API decision affects package users.
