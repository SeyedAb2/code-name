closure و event

Closures and events

صفحه بسته شده اما publisher هنوز handler آن را صدا می‌زند. از کجا می‌فهمیم شیء آزاد نشده؟ closure می‌تواند متغیر و عمرش را نگه دارد؛ event هم subscription را در publisher ذخیره می‌کند. با آزمایش، capture و lifecycle را جدا می‌کنیم.

A page is closed, yet the publisher still calls its handler. Why is the object retained? A closure can retain a variable and its lifetime; an event stores subscriptions on the publisher. Experiments separate capture from lifecycle.

فصل ۳۳پیش‌نیازprerequisite

closure متغیر را می‌گیرد، نه لزوماً مقدار لحظه‌ای راA closure captures a variable, not necessarily its current value

وقتی lambda به متغیر بیرونش دسترسی دارد، آن متغیر باید تا زمان نیاز قابل‌دسترسی بماند. اگر مقدار بعداً عوض شود، lambda معمولاً مقدار جدید را می‌بیند. این تفاوت بین capture متغیر و snapshot مقدار است. در حلقه، local جدا برای هر iteration کمک می‌کند رفتار مورد انتظار را ثبت کنیم.

When a lambda accesses an outer variable, that variable must remain available. If it changes later, the lambda generally observes the updated value. This is variable capture versus a value snapshot. A per-iteration local makes loop behaviour explicit.

هر iteration مقدار خودش / Capture per iteration
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
{
    int item = i;
    actions.Add(() => Console.WriteLine(item));
}
foreach (var action in actions) action();

خروجی ۰، ۱، ۲ است، چون هر closure local خودش را دارد. اگر مستقیم i را capture کنی، مشاهده با تصور «کپی خودکار مقدار» فرق می‌کند؛ تست را روی target framework واقعی اجرا کن.

Output is 0, 1, 2 because each closure has its own local. Capturing i directly differs from an assumed automatic value copy; run the test on the target framework.

event مرز subscription است، نه مدیریت خودکار عمرAn event is a subscription boundary, not automatic lifetime management

بیرون publisher می‌تواند += و -= کند، اما فقط خود publisher event را invoke می‌کند. publisher تا وقتی handler ثبت است delegate را نگه می‌دارد و delegate ممکن است subscriber یا this را capture کرده باشد. برای subscriber کوتاه‌عمر، unsubscribe را در Dispose یا پایان lifecycle انجام بده و تست کن.

Outside code can use += and -=, while only the publisher raises the event. The publisher retains the delegate; it may capture a subscriber or this. Short-lived subscribers should unsubscribe during Dispose or at their lifecycle boundary, and tests should verify it.

اگر یک handler exception بدهد، فراخوانی عادی multicast ممکن است به بقیه نرسد. اگر قرارداد می‌گوید بقیه باید مستقل اجرا شوند، هر handler را جدا invoke و failureها را طبق policy ثبت کن.

If a handler throws, normal multicast invocation may not reach later handlers. If the contract requires isolation, invoke handlers separately and record failures according to policy.

عمر متغیر و عمر publisher را کنار هم ببینConsider captured-variable and publisher lifetimes together

closure می‌تواند متغیر local را بعد از پایان متد زنده نگه دارد؛ event می‌تواند closure را پس از پایان صفحه نگه دارد. این دو reference chain را جدا trace کن. برای اثبات leak، صرفاً دیدن callback کافی نیست؛ weak reference، memory profiler یا تست کنترل‌شدهٔ lifetime لازم است.

A closure can retain a local after its method returns; an event can retain the closure after a page closes. Trace both reference chains. A callback alone does not prove a leak; use a controlled lifetime test, weak reference or memory profiler.

async callback دامنهٔ تازه‌ای از خطا می‌سازدAsync callbacks introduce another failure boundary

async lambda را به Action تبدیل نکن مگر async void عمداً لازم باشد؛ exception و completion آن قابل await نیست. برای کار async از Func یا event pattern مشخص استفاده کن. همچنین اگر چند handler موازی اجرا می‌شوند، ترتیب و cancellation باید قرارداد باشند، نه اتفاق.

Do not convert an async lambda to Action unless async void is intentional; its completion and exceptions cannot be awaited. Use Func<Task> or an explicit async event pattern. If handlers run concurrently, ordering and cancellation must be contractual, not accidental.

آزمایشگاه: پنجرهٔ اعلانLab: notification window

یک publisher بلندعمر و سه subscriber کوتاه‌عمر بساز. یکی closure در حلقه دارد، یکی بعد از dispose حذف می‌شود و یکی عمداً exception می‌دهد. ابتدا با testهای کوچک رفتار فعلی را ثبت کن؛ سپس local capture، unsubscribe و policy failure را اصلاح کن. در پایان تعداد callbackها و lifecycle هر object را گزارش بده.

Create a long-lived publisher and three short-lived subscribers. One captures a loop variable, one must detach on disposal, and one deliberately throws. Record behaviour with small tests, then fix capture, unsubscription and failure policy. Report callback counts and object lifetimes.

  1. با سه subscriber baseline را بازتولید کن.
  2. Reproduce baseline with three subscribers.
  3. با counter/reference evidence محل نگهداری را نشان بده.
  4. Use counters/reference evidence to show retention.
  5. اصلاح را با همان testها ثابت کن.
  6. Prove the fix with the same tests.

event را ثبت کردی، حذفش را هم طراحی کنIf you subscribe, design unsubscription too

closure معمولاً متغیر را زنده نگه می‌دارد؛ event هم delegate را تا زمان حذف subscription نگه می‌دارد. async void و exception policy خطر جدا دارند. حالا شاخه‌های پیچیده را با pattern matching می‌نویسیم، اما همچنان باید رفتار هر branch را با تست قفل کنیم.

Closures retain variables; events retain delegates until unsubscription. async void and exception policy create separate risks. Next we simplify complex branches with pattern matching while still locking each branch down with tests.
