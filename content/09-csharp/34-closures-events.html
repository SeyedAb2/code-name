closure و event

Closures and events

صفحه بسته شده اما publisher هنوز handler آن رو صدا می‌زنه. از کجا می‌فهمیم شیء آزاد نشده؟ closure می‌تونه متغیر و عمرش رو نگه داره؛ event هم subscription رو در publisher ذخیره می‌کنه. با آزمایش، capture و lifecycle رو جدا می‌کنیم.

A page is closed, yet the publisher still calls its handler. Why is the object retained? A closure can retain a variable and its lifetime; an event stores subscriptions on the publisher. Experiments separate capture from lifecycle.

closure متغیر رو می‌گیره، نه لزوماً مقدار لحظه‌ای راA closure captures a variable, not necessarily its current value

وقتی lambda به متغیر بیرونش دسترسی داره، آن متغیر باید تا زمان نیاز قابل‌دسترسی بماند. اگه مقدار بعداً عوض بشه، lambda معمولاً مقدار جدید رو می‌بینه. این تفاوت بین capture متغیر و snapshot مقدار هست. در حلقه، local جدا برای هر iteration کمک می‌کنه رفتار مورد انتظار رو ثبت کنیم.

When a lambda accesses an outer variable, that variable must remain available. If it changes later, the lambda generally observes the updated value. This is variable capture versus a value snapshot. A per-iteration local makes loop behaviour explicit.

هر iteration مقدار خودش / Capture per iteration
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
{
    int item = i;
    actions.Add(() => Console.WriteLine(item));
}
foreach (var action in actions) action();

خروجی ۰، ۱، ۲ هست، چون هر closure local خودش رو داره. اگه مستقیم i رو capture کنی، مشاهده با تصور «کپی خودکار مقدار» فرق می‌کنه؛ تست رو روی target framework واقعی اجرا کن.

Output is 0, 1, 2 because each closure has its own local. Capturing i directly differs from an assumed automatic value copy; run the test on the target framework.

event مرز subscription هست، نه مدیریت خودکار عمرAn event is a subscription boundary, not automatic lifetime management

بیرون publisher می‌تونه += و -= کند، اما فقط خود publisher event رو invoke می‌کنه. publisher تا وقتی handler ثبت هست delegate رو نگه می‌داره و delegate ممکنه subscriber یا this رو capture کرده باشه. برای subscriber کوتاه‌عمر، unsubscribe رو در Dispose یا پایان lifecycle انجام بده و تست کن.

Outside code can use += and -=, while only the publisher raises the event. The publisher retains the delegate; it may capture a subscriber or this. Short-lived subscribers should unsubscribe during Dispose or at their lifecycle boundary, and tests should verify it.

اگه یک handler exception بدهد، فراخوانی عادی multicast ممکنه به بقیه نرسد. اگه قرارداد می‌گه بقیه باید مستقل اجرا بشن، هر handler رو جدا invoke و failureها رو طبق policy ثبت کن.

If a handler throws, normal multicast invocation may not reach later handlers. If the contract requires isolation, invoke handlers separately and record failures according to policy.

عمر متغیر و عمر publisher رو کنار هم ببینConsider captured-variable and publisher lifetimes together

closure می‌تونه متغیر local رو بعد از پایان متد زنده نگه داره؛ event می‌تونه closure رو پس از پایان صفحه نگه داره. این دو reference chain رو جدا trace کن. برای اثبات leak، صرفاً دیدن callback کافی نیست؛ weak reference، memory profiler یا تست کنترل‌شدهٔ lifetime لازمه.

A closure can retain a local after its method returns; an event can retain the closure after a page closes. Trace both reference chains. A callback alone does not prove a leak; use a controlled lifetime test, weak reference or memory profiler.

async callback دامنهٔ تازه‌ای از خطا می‌سازهAsync callbacks introduce another failure boundary

async lambda رو به Action تبدیل نکن مگر async void عمداً لازم باشه؛ exception و completion آن قابل await نیست. برای کار async از Func یا event pattern مشخصهفاده کن. همچنین اگه چند handler موازی اجرا می‌شن، ترتیب و cancellation باید قرارداد باشن، نه اتفاق.

Do not convert an async lambda to Action unless async void is intentional; its completion and exceptions cannot be awaited. Use Func<Task> or an explicit async event pattern. If handlers run concurrently, ordering and cancellation must be contractual, not accidental.
