نخ، ThreadPool و مسابقهٔ داده

Threads, the ThreadPool and data races

گزارش روزانه می‌گه صد worker هر کدوم ۱۰ هزار رکورد پردازش کرده‌اند، اما شمار نهایی کمتر از یک میلیون هست. همهٔ خط‌ها اجرا شده‌اند؛ مشکل در count++ مشترک هست. از این باگ شروع می‌کنیم تا فرق «چند کار در جریان»، «چند کار هم‌زمان روی هسته‌ها» و «انتظار بدون نگه‌داشتن نخ» رو روشن کنیم.

A daily report says 100 workers each processed 10,000 records, yet the final count is below one million. Every loop ran; the bug is the shared count++. We start there to distinguish work in progress, work executing simultaneously on cores, and waiting without holding a thread.

concurrency، parallelism و async یکی نیستنConcurrency, parallelism and async are different

concurrency یعنی چند کار پیشرفتشان با هم هماهنگ هست؛ ممکنه با جابه‌جایی روی یک هسته جلو بروند. parallelism یعنی چند کار واقعاً هم‌زمان روی چند هسته اجرا بشن. async یعنی هنگام انتظار بتوانی کنترل رو واگذار کنی؛ عملیات I/O async الزاماً نخ جدید یا اجرای موازی نداره. process حافظهٔ مستقل داره؛ thread مسیر اجرای داخل process هست و دادهٔ مشترک می‌تونه race بسازد.

Concurrency means multiple tasks make coordinated progress, possibly interleaved on one core. Parallelism means multiple tasks execute simultaneously on multiple cores. Async means control can be yielded during waits; async I/O does not require a new thread or parallel execution. A process has separate memory; threads execute within it and can race over shared data.

race condition معمولاً تو review دیده نمی‌شه؛ تو زمان‌بندی دیده می‌شهA race condition often hides in review and appears only in scheduling

دو خط کد ممکنه هرکدوم به‌تنهایی درست باشن ولی وقتی دو thread بینشون جابه‌جا می‌شن نتیجه خراب بشه. برای همین race رو با نگاه‌کردن به source نمی‌فهمیم؛ یه workload تکراربشنه می‌سازیم و اجازه می‌دیم زمان‌بندی چند interleaving مختلف تولید کنه.

Two lines can each be correct in isolation while the result becomes wrong when threads interleave between them. That is why a race is not fully understood by staring at source code; create a repeatable workload and let scheduling expose different interleavings.

هدف فصل این نیست که thread بیشتری بسازیم. اول می‌خوایم shared mutable state رو ببینیم، بعد بفهمیم آیا اصلاً concurrency لازم داریم یا می‌شه ownership رو طوری طراحی کرد که اشتراک کمتر بشه.

The goal is not to create more threads. First identify shared mutable state, then ask whether concurrency is actually required or whether ownership can be redesigned to reduce sharing.

count++ یک عمل اتمیک نیستcount++ is not one atomic operation

این عبارت در واقع read، add و write هست. دو thread می‌تونن یک مقدار رو بخوانند، هر دو یک واحد اضافه کنند و یکی از writeها دیگری رو بپوشاند. اجرای هم‌زمان هم برای دیدن این باگ لازم نیست؛ interleaving کافی هست. برای عدد مستقل از lock، Interlocked.Increment عملیات اتمیک می‌ده؛ برای invariant چند فیلدی، فقط atomic کردن یک عدد کافی نیست.

count++ is a read, add and write. Two threads can read the same value, increment it and overwrite one another. Simultaneous execution is not required; interleaving is enough. For an independent counter, Interlocked.Increment is atomic; for a multi-field invariant, atomically updating one number is not sufficient.

counter thread-safe / Thread-safe counter
int count = 0;
Parallel.For(0, 100_000, _ =>
{
    Interlocked.Increment(ref count);
});

Console.WriteLine(count); // 100000

این آزمایش نتیجهٔ درست رو برای یک counter مستقل می‌ده، اما Interlocked تراکنش چند متغیر نیست. اگه counter برای آمار هست، aggregation محلی هر worker و جمع در پایان شاید سریع‌تر باشه؛ اگه قرار هست مقدار با چند state سازگار بماند، critical section لازمه.

This fixes an independent counter, but Interlocked is not a transaction across multiple variables. For metrics, per-worker local aggregation and a final sum may be faster; for a consistent multi-value state, a critical section is needed.

ThreadPool نخ رو reuse می‌کنه؛ صف بی‌نهایت نیستThe ThreadPool reuses threads; it is not an infinite queue

.NET یک pool مدیریت‌شده داره که TPL و بسیاری از callbackها از آن استفاده می‌کنن. ساخت thread اختصاصی هزینه و lifecycle داره؛ برای کار کوتاه، Task/ThreadPool معمولاً انتخاب بهتره. اما اگه هزار کار blocking به pool بدهی، صف و latency رشد می‌کنه. بالا بردن حداقل threadها راه‌حل پیش‌فرض نیست؛ اول blocking، نرخ ورود و مدت کار رو اندازه بگیر.

.NET has a managed pool used by TPL and many callbacks. Dedicated threads have lifecycle and creation costs; Task/ThreadPool is generally better for short work. But thousands of blocking jobs can grow queues and latency. Raising minimum thread counts is not the default fix; first measure blocking, arrival rate and work duration.

thread ID هویت کار نیستA thread ID is not task identity

بعد از await ممکنه continuation روی thread دیگری ادامه یابد. Task هم الزاماً یک thread ثابت نداره؛ thread ID رو برای correlation کار یا مالکیت state ذخیره نکن. برای پیگیری، Activity/correlation ID و log structured به‌کار ببر. دادهٔ local به جریان منطقی وابسته هست، نه همیشه به نخ؛ AsyncLocal هم ابزار زمینه‌ای هست و باید مرز propagation آن رو شناخت.

After await, a continuation may resume on another thread. A Task is not permanently tied to one thread; do not use thread IDs as work correlation or state ownership. Use Activity/correlation IDs and structured logs. Logical-flow context is not always thread-local; AsyncLocal is a contextual tool whose propagation boundaries must be understood.

کار منطقی را همبسته کن / Correlate logical work
using var activity = ActivitySource.StartActivity("ImportBatch");
activity?.SetTag("batch.id", batchId);

await ReadAsync(ct);
logger.LogInformation("Batch {BatchId} continues", batchId);

برای بیشتر logها correlation ID صریح و Activity استانداره، از ذخیرهٔ thread ID قابل‌اعتمادترند. Activity رو هم در payload حساس پر نکن؛ tagها ممکنه در telemetry ماندگار بشن.

Explicit correlation IDs and standard Activity are more reliable than recording thread IDs. Do not put sensitive payloads into Activity tags; telemetry may persist them.

I/O رو ناهمگام کن؛ CPU رو اندازه بگیرMake I/O asynchronous; measure CPU work

درخواست فایل/شبکه رو با API async انجام بده تا هنگام انتظار نخ آزاد بماند. محاسبهٔ CPU اگه parallel بشه، باید workload واقعاً قابل‌تقسیم و هزینهٔ هماهنگی از سود کمتر باشه. هر دو رو مخلوط نکن: Task.Run دور HttpClient معمولاً فقط نخ رو برای انتظار اشغال می‌کنه؛ parallelizing یک کار خیلی کوچک هم ممکنه کندتر بشه.

Use asynchronous file/network APIs so threads are free while waiting. Parallelize CPU work only when it can be partitioned and coordination costs less than the gain. Do not confuse the two: wrapping HttpClient in Task.Run can occupy a thread while waiting; parallelizing tiny work can also make it slower.

برای race، نتیجهٔ نهایی کافی نیستA final value is not enough to diagnose a race

باگ race ممکنه فقط گاهی دیده بشه. برای بازتولید، ورودی ثابت، barrier یا hook آزمایشی بساز تا ترتیب رو کنترل کنی؛ از sleep تصادفی به‌عنوان اثبات استفاده نکن. بعد از fix، invariant رو تست کن و چند اجرای تکراری بگیر. race detector عمومیِ قابل‌اتکا برای همهٔ کدهای .NET جای طراحی thread-safe و تست رو نمی‌گیره.

Race bugs can be intermittent. Reproduce them with deterministic inputs and a test barrier or hook to control ordering; arbitrary sleeps are not proof. After fixing the code, assert the invariant and repeat tests. No universal race detector replaces thread-safe design and testing for all .NET code.
