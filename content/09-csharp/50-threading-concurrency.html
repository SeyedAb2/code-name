نخ، ThreadPool و مسابقهٔ داده

Threads, the ThreadPool and data races

گزارش روزانه می‌گوید صد worker هر کدام ۱۰ هزار رکورد پردازش کرده‌اند، اما شمار نهایی کمتر از یک میلیون است. همهٔ خط‌ها اجرا شده‌اند؛ مشکل در count++ مشترک است. از این باگ شروع می‌کنیم تا فرق «چند کار در جریان»، «چند کار هم‌زمان روی هسته‌ها» و «انتظار بدون نگه‌داشتن نخ» را روشن کنیم.

A daily report says 100 workers each processed 10,000 records, yet the final count is below one million. Every loop ran; the bug is the shared count++. We start there to distinguish work in progress, work executing simultaneously on cores, and waiting without holding a thread.

فصل ۴۹پیش‌نیازprerequisite

concurrency، parallelism و async یکی نیستندConcurrency, parallelism and async are different

concurrency یعنی چند کار پیشرفتشان با هم هماهنگ است؛ ممکن است با جابه‌جایی روی یک هسته جلو بروند. parallelism یعنی چند کار واقعاً هم‌زمان روی چند هسته اجرا شوند. async یعنی هنگام انتظار بتوانی کنترل را واگذار کنی؛ عملیات I/O async الزاماً نخ جدید یا اجرای موازی ندارد. process حافظهٔ مستقل دارد؛ thread مسیر اجرای داخل process است و دادهٔ مشترک می‌تواند race بسازد.

Concurrency means multiple tasks make coordinated progress, possibly interleaved on one core. Parallelism means multiple tasks execute simultaneously on multiple cores. Async means control can be yielded during waits; async I/O does not require a new thread or parallel execution. A process has separate memory; threads execute within it and can race over shared data.

count++ یک عمل اتمیک نیستcount++ is not one atomic operation

این عبارت در واقع read، add و write است. دو thread می‌توانند یک مقدار را بخوانند، هر دو یک واحد اضافه کنند و یکی از writeها دیگری را بپوشاند. اجرای هم‌زمان هم برای دیدن این باگ لازم نیست؛ interleaving کافی است. برای عدد مستقل از lock، Interlocked.Increment عملیات اتمیک می‌دهد؛ برای invariant چند فیلدی، فقط atomic کردن یک عدد کافی نیست.

count++ is a read, add and write. Two threads can read the same value, increment it and overwrite one another. Simultaneous execution is not required; interleaving is enough. For an independent counter, Interlocked.Increment is atomic; for a multi-field invariant, atomically updating one number is not sufficient.

counter thread-safe / Thread-safe counter
int count = 0;
Parallel.For(0, 100_000, _ =>
{
    Interlocked.Increment(ref count);
});

Console.WriteLine(count); // 100000

این آزمایش نتیجهٔ درست را برای یک counter مستقل می‌دهد، اما Interlocked تراکنش چند متغیر نیست. اگر counter برای آمار است، aggregation محلی هر worker و جمع در پایان شاید سریع‌تر باشد؛ اگر قرار است مقدار با چند state سازگار بماند، critical section لازم است.

This fixes an independent counter, but Interlocked is not a transaction across multiple variables. For metrics, per-worker local aggregation and a final sum may be faster; for a consistent multi-value state, a critical section is needed.

ThreadPool نخ را reuse می‌کند؛ صف بی‌نهایت نیستThe ThreadPool reuses threads; it is not an infinite queue

.NET یک pool مدیریت‌شده دارد که TPL و بسیاری از callbackها از آن استفاده می‌کنند. ساخت thread اختصاصی هزینه و lifecycle دارد؛ برای کار کوتاه، Task/ThreadPool معمولاً انتخاب بهتر است. اما اگر هزار کار blocking به pool بدهی، صف و latency رشد می‌کند. بالا بردن حداقل threadها راه‌حل پیش‌فرض نیست؛ اول blocking، نرخ ورود و مدت کار را اندازه بگیر.

.NET has a managed pool used by TPL and many callbacks. Dedicated threads have lifecycle and creation costs; Task/ThreadPool is generally better for short work. But thousands of blocking jobs can grow queues and latency. Raising minimum thread counts is not the default fix; first measure blocking, arrival rate and work duration.

thread ID هویت کار نیستA thread ID is not task identity

بعد از await ممکن است continuation روی thread دیگری ادامه یابد. Task هم الزاماً یک thread ثابت ندارد؛ thread ID را برای correlation کار یا مالکیت state ذخیره نکن. برای پیگیری، Activity/correlation ID و log structured به‌کار ببر. دادهٔ local به جریان منطقی وابسته است، نه همیشه به نخ؛ AsyncLocal هم ابزار زمینه‌ای است و باید مرز propagation آن را شناخت.

After await, a continuation may resume on another thread. A Task is not permanently tied to one thread; do not use thread IDs as work correlation or state ownership. Use Activity/correlation IDs and structured logs. Logical-flow context is not always thread-local; AsyncLocal is a contextual tool whose propagation boundaries must be understood.

کار منطقی را همبسته کن / Correlate logical work
using var activity = ActivitySource.StartActivity("ImportBatch");
activity?.SetTag("batch.id", batchId);

await ReadAsync(ct);
logger.LogInformation("Batch {BatchId} continues", batchId);

برای بیشتر logها correlation ID صریح و Activity استاندارد، از ذخیرهٔ thread ID قابل‌اعتمادترند. Activity را هم در payload حساس پر نکن؛ tagها ممکن است در telemetry ماندگار شوند.

Explicit correlation IDs and standard Activity are more reliable than recording thread IDs. Do not put sensitive payloads into Activity tags; telemetry may persist them.

I/O را ناهمگام کن؛ CPU را اندازه بگیرMake I/O asynchronous; measure CPU work

درخواست فایل/شبکه را با API async انجام بده تا هنگام انتظار نخ آزاد بماند. محاسبهٔ CPU اگر parallel شود، باید workload واقعاً قابل‌تقسیم و هزینهٔ هماهنگی از سود کمتر باشد. هر دو را مخلوط نکن: Task.Run دور HttpClient معمولاً فقط نخ را برای انتظار اشغال می‌کند؛ parallelizing یک کار خیلی کوچک هم ممکن است کندتر شود.

Use asynchronous file/network APIs so threads are free while waiting. Parallelize CPU work only when it can be partitioned and coordination costs less than the gain. Do not confuse the two: wrapping HttpClient in Task.Run can occupy a thread while waiting; parallelizing tiny work can also make it slower.

برای race، نتیجهٔ نهایی کافی نیستA final value is not enough to diagnose a race

باگ race ممکن است فقط گاهی دیده شود. برای بازتولید، ورودی ثابت، barrier یا hook آزمایشی بساز تا ترتیب را کنترل کنی؛ از sleep تصادفی به‌عنوان اثبات استفاده نکن. بعد از fix، invariant را تست کن و چند اجرای تکراری بگیر. race detector عمومیِ قابل‌اتکا برای همهٔ کدهای .NET جای طراحی thread-safe و تست را نمی‌گیرد.

Race bugs can be intermittent. Reproduce them with deterministic inputs and a test barrier or hook to control ordering; arbitrary sleeps are not proof. After fixing the code, assert the invariant and repeat tests. No universal race detector replaces thread-safe design and testing for all .NET code.

برای درخواست شبکه، محاسبهٔ image و UI responsiveness مشخص کن کدام async، concurrency یا parallelism است.

Classify a network request, image computation and UI responsiveness by async, concurrency or parallelism.

Network is async I/O, multiple requests are concurrent, multi-core computation is parallel; UI responsiveness comes from nonblocking waits.

read-modify-write race دارد؛ Interlocked.Increment یا جمع محلی هر worker را انتخاب کن.

Read-modify-write races; use Interlocked.Increment or local per-worker aggregation.

continuation می‌تواند روی نخ دیگری ادامه یابد؛ از Activity یا correlation ID استفاده کن.

The continuation can resume on another thread; use Activity or a correlation ID.

balance و transaction count باید با هم تغییر کنند؛ آیا Interlocked روی balance کافی است؟

Balance and transaction count must change together; is Interlocked on balance enough?

۶) Task و thread6) Task and thread

از روی یک Task بگو چند thread حتماً ساخته می‌شود؛ فرضیه را آزمایش و اصلاح کن.

Predict how many threads one Task necessarily creates; test and correct the assumption.

پاسخ فنیTechnical reasoning

Task الزاماً thread جدید ندارد؛ I/O task می‌تواند بدون نخ منتظر بماند و continuation بعداً schedule شود.

A Task does not require a new thread; I/O can remain pending without a waiting thread, with continuation scheduled later.

۷) threadهای اختصاصی7) Dedicated threads

برای هر item یک Thread جدید می‌سازی؛ startup و resource را با ThreadPool بسنج.

A new Thread is created per item; compare startup and resource cost with ThreadPool.

پاسخ فنیTechnical reasoning

برای کار کوتاه TPL/ThreadPool مناسب‌تر است؛ نخ اختصاصی را برای نیاز lifecycle یا blocking مشخص نگه دار.

TPL/ThreadPool is usually better for short work; reserve dedicated threads for clear lifecycle or blocking needs.

۸) starvation8) Starvation

CPU پایین، queue بالا و تعداد زیادی Task منتظرند؛ چه شواهدی ThreadPool starvation را نشان می‌دهد؟

CPU is low, queues are high and many tasks wait; what evidence indicates ThreadPool starvation?

پاسخ فنیTechnical reasoning

thread count، stackهای blocking، queue delay و نرخ تکمیل را هم‌بسته کن؛ فقط CPU پایین علت را ثابت نمی‌کند.

Correlate thread count, blocking stacks, queue delay and completion rate; low CPU alone proves nothing.

۹) حداقل thread pool9) ThreadPool minimum

تیم حداقل نخ‌ها را ده‌برابر می‌کند؛ عوارض احتمالی را با آزمایش کنترل‌شده بررسی کن.

A team multiplies minimum threads by ten; investigate possible side effects safely.

پاسخ فنیTechnical reasoning

رقابت CPU، context switching و contention می‌تواند بدتر شود؛ ابتدا blocking و queue را رفع و فقط با benchmark تنظیم کن.

CPU contention, context switching and contention can worsen; fix blocking/queues first and tune only with benchmarks.

۱۰) local aggregation10) Local aggregation

Interlocked روی هر رکورد گلوگاه شده؛ شمارش محلی و merge پایان کار را پیاده کن.

Interlocked per record is a bottleneck; implement local counts and a final merge.

پاسخ فنیTechnical reasoning

هر worker شمارندهٔ خودش را نگه دارد و یک بار در پایان جمع کند؛ عدد نهایی را با baseline assert کن.

Give each worker a local counter and sum once at the end; assert against a baseline.

۱۱) state مشترک11) Shared state

Taskها یک List را هم‌زمان Add می‌کنند؛ مسئلهٔ collection safety و طراحی را حل کن.

Tasks add to one List concurrently; address collection safety and design.

پاسخ فنیTechnical reasoning

از collection concurrent، lock یا buffer محلی و merge استفاده کن؛ تصمیم را از ترتیب/throughput موردنیاز بگیر.

Use a concurrent collection, lock, or local buffers and merge; decide based on ordering and throughput needs.

۱۲) AsyncLocal یا ThreadLocal12) AsyncLocal or ThreadLocal

correlation بعد await ناپدید می‌شود چون ThreadLocal است؛ context را متناسب انتخاب کن.

Correlation disappears after await because it is ThreadLocal; choose context appropriately.

پاسخ فنیTechnical reasoning

AsyncLocal برای جریان منطقی async طراحی شده، اما propagation/عملکرد و cleanup آن را آگاهانه بسنج.

AsyncLocal follows logical async flow, but its propagation, performance and cleanup still need deliberate design.

۱۳) atomic بودن assignment13) Atomic assignment

assignment یک reference را thread-safe می‌دانند و کل شیء را همزمان update می‌کنند؛ مرز تضمین را توضیح بده.

Reference assignment is assumed to make an entire object update thread-safe; clarify the guarantee boundary.

پاسخ فنیTechnical reasoning

اتمی‌بودن reference assignment، تغییر فیلدهای mutable در شیء یا invariantهای چندمرحله‌ای را thread-safe نمی‌کند.

Atomic reference assignment does not make mutable object fields or multi-step invariants thread-safe.

۱۴) race تکرارناپذیر14) Intermittent race

test با sleep گاهی fail می‌شود؛ barrier کنترل‌شده برای interleaving بساز.

A sleep-based test fails intermittently; use a controlled barrier to force an interleaving.

پاسخ فنیTechnical reasoning

دو worker را با Barrier/TaskCompletionSource در نقطهٔ read نگه دار و ordering را قطعی trigger کن.

Coordinate workers with Barrier/TaskCompletionSource at the read point to force deterministic ordering.

۱۵) concurrency یا throughput15) Concurrency or throughput

تعداد هم‌زمانی را دو برابر می‌کنی ولی throughput ثابت است؛ bottleneckهای ممکن را رتبه‌بندی کن.

You double concurrency but throughput stays flat; rank plausible bottlenecks.

پاسخ فنیTechnical reasoning

CPU، مقصد rate-limited، lock contention و I/O bandwidth را با trace اندازه بگیر؛ concurrency بیشتر خودکار ظرفیت نمی‌سازد.

Measure CPU, downstream limits, lock contention and I/O bandwidth; more concurrency does not create capacity.

۱۶) incident شمارش نهایی16) Final-count incident

counter تحت بار کمتر از انتظار است؛ تشخیص، اصلاح و verification را در گزارش بنویس.

A counter is low under load; document diagnosis, repair and verification.

پاسخ فنیTechnical reasoning

race read-modify-write را با trace/test اثبات؛ Interlocked یا aggregation مناسب را انتخاب و مجموع deterministic را assert کن.

Prove the read-modify-write race with tests/traces, choose Interlocked or aggregation, and assert a deterministic total.

آزمایشگاه: آمارگر parallel محدودLab: a bounded parallel counter

یک مجموعهٔ ورودی ثابت بساز و تعداد موردها را با نسخهٔ ترتیبی، counter مشترک ناامن، Interlocked و local aggregation مقایسه کن. نتیجهٔ همه باید یکسان باشد. بعد workload CPU را با Parallel.For و workload I/O را با API async جداگانه بسنج؛ concurrency را محدود و latency/throughput/thread count را ثبت کن. race را با barrier آزمایشی بازتولید کن، نه sleep. کد را چند بار اجرا و invariant را assert کن؛ بعد traceها را ذخیره و تفاوت CPU-bound و I/O-bound را در گزارش بگو.

Create a fixed input set and compare sequential counting, an unsafe shared counter, Interlocked and local aggregation. Every result must match. Then measure CPU work with Parallel.For separately from I/O through async APIs; bound concurrency and record latency, throughput and thread count. Reproduce the race with a test barrier, not sleeps. Repeat and assert the invariant, then report the CPU-bound versus I/O-bound evidence.

  1. هر نسخه را با ورودی و خروجی برابر benchmark کن.
  2. Benchmark each version on identical input and output.
  3. نتیجهٔ ناامن را برای یک میلیون count چند بار assert کن.
  4. Repeat and assert the unsafe million-count result.
  5. تغییر concurrency را بدون افزایش بی‌حد اندازه بگیر.
  6. Measure concurrency changes without unbounded scale.

نخ ابزار اجراست؛ invariant مسئولیت طراحی توستThreads execute work; invariants remain your responsibility

ThreadPool نخ را reuse می‌کند، Task کار را نمایندگی می‌کند، async انتظار را غیرمسدودکننده می‌سازد و parallelism از چند هسته کمک می‌گیرد؛ هیچ‌کدام دادهٔ مشترک را خودکار امن نمی‌کنند. حتی شمارنده‌ای ساده یک invariant دارد و باید با primitive درست محافظت شود. فصل بعد سراغ گزینه‌ها می‌رویم: lock، Interlocked، semaphore و این‌که کدام مسئله را حل می‌کنند و کدام را نه.

The ThreadPool reuses threads, Task represents work, async makes waits nonblocking and parallelism uses multiple cores; none makes shared data safe automatically. Even a simple counter has an invariant that needs the right primitive. Next we compare locks, Interlocked and semaphores—and which problems each does and does not solve.
