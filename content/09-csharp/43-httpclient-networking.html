HTTP and HttpClient

سرویس گزارش برای هر سفارش یک client می‌سازد و می‌بندد؛ چند ساعت بعد درخواست‌ها کند و اتصال‌ها ناپایدار شده‌اند. هم‌زمان، کد هر status غیر ۲۰۰ را exception می‌بیند و header احراز هویت را روی client مشترک تغییر می‌دهد. این فصل درخواست را از ساخت تا پاسخ دنبال می‌کند و lifetime شبکه را از lifetime یک پیام جدا می‌سازد.

A reporting service creates and disposes a client for every order; hours later, requests slow down and connections become unstable. Meanwhile, code treats every non-200 status as an exception and mutates authentication headers on a shared client. We trace a request end to end and separate connection lifetime from message lifetime.

HTTP یک پیام با قرارداد مشخص استHTTP is a message with an explicit contract

درخواست فقط URL نیست: method، header، body و گاهی cancellation هم دارد. پاسخ هم status، header و محتوا دارد. اول معلوم کن API چه می‌خواهد؛ بعد message را بساز. HttpRequestMessage برای درخواست موردی مفید است و HttpResponseMessage منبعی است که باید پس از مصرف مدیریت و dispose شود.

A request is more than a URL: it has a method, headers, a body and often cancellation. A response contains a status, headers and content. Start from the API contract, then build the message. HttpRequestMessage is useful for per-request details, and HttpResponseMessage should be disposed after its content is consumed.

درخواست و پاسخ / Request and response
using var request = new HttpRequestMessage(
    HttpMethod.Get, "v1/orders/A-17");
request.Headers.Accept.ParseAdd("application/json");

using HttpResponseMessage response = await client.SendAsync(
    request, HttpCompletionOption.ResponseHeadersRead, cancellationToken);

if (response.StatusCode == HttpStatusCode.NotFound)
    return null;

response.EnsureSuccessStatusCode();
return await response.Content.ReadFromJsonAsync<Order>(
    cancellationToken: cancellationToken);

relative URI وقتی base address تنظیم شده معنا دارد. 404 ممکن است در دامنهٔ برنامه «پیدا نشد» باشد، نه خطای زیرساخت؛ status را متناسب با قرارداد تفسیر کن. EnsureSuccessStatusCode هر پاسخ خارج از 2xx را exception می‌کند، پس فقط وقتی آن را بگذار که همهٔ این وضعیت‌ها واقعاً failure محسوب شوند. با ResponseHeadersRead محتوا را جداگانه و با cancellation بخوان.

A relative URI requires a configured base address. A 404 may mean “not found” in the application domain, not infrastructure failure; interpret status according to the contract. EnsureSuccessStatusCode throws for every non-2xx response, so use it only if all such statuses are genuine failures. With ResponseHeadersRead, read content separately and propagate cancellation.

HttpClient برای هر درخواست ساخته نمی‌شودDo not create an HttpClient per request

هر client معمولاً connection pool خودش را دارد. ساخت و Dispose پشت‌سرهم poolها را دور می‌اندازد؛ در بار زیاد، پورت‌ها می‌توانند در وضعیت انتظار بمانند و به کمبود connection برسیم. راه رایج: client بلندعمر و handler با PooledConnectionLifetime متناسب با تغییر DNS، یا clientهای کوتاه‌عمر از IHttpClientFactory که handlerها را مدیریت و pool را reuse می‌کند.

Each client generally owns a connection pool. Repeated construction and disposal discards pools; under load, ports can linger in wait states and connections become scarce. Common choices are a long-lived client with a handler’s PooledConnectionLifetime tuned to DNS changes, or short-lived clients from IHttpClientFactory, which manages handlers and reuses pools.

client بلندعمر / Long-lived client
var handler = new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(5)
};
using var client = new HttpClient(handler)
{
    BaseAddress = new Uri("https://api.example.test/")
};

پنج دقیقه فقط یک مقدار نمونه است؛ بر اساس رفتار DNS و زیرساخت خودت تصمیم بگیر. DNS در هر درخواست دوباره resolve نمی‌شود؛ اتصال‌های poolشده ممکن است نشانی قبلی را نگه دارند. این هم به معنی آن نیست که TTL سرور DNS باید عیناً این مقدار باشد.

Five minutes is illustrative, not a universal recommendation; choose based on DNS and infrastructure behavior. DNS is not resolved again for every request, so pooled connections can retain an earlier address. This does not mean the value must equal the DNS server’s TTL.

IHttpClientFactory برای clientهای نقش‌دارUse IHttpClientFactory for role-specific clients

در برنامهٔ مبتنی بر DI، typed client قرارداد یک سرویس بیرونی را جمع می‌کند: base address، headerهای ثابت، serializer و cancellation. برای هر نقش client جدا تعریف کن؛ secret یا token هر کاربر را روی default header یک client مشترک نگذار، چون درخواست هم‌زمان کاربرها می‌تواند هویت را قاطی کند. header اختصاصی را روی HttpRequestMessage همان درخواست بگذار.

In a DI-based app, a typed client groups one external service’s contract: base address, stable headers, serialization and cancellation. Use separate clients by role. Do not put a per-user secret or token in a shared client’s default headers; concurrent requests can cross identities. Add per-request headers to that request’s HttpRequestMessage.

ثبت typed client / Register a typed client
builder.Services.AddHttpClient<CatalogClient>(client =>
{
    client.BaseAddress = new Uri(builder.Configuration["Catalog:BaseUrl"]!);
    client.Timeout = TimeSpan.FromSeconds(10);
});

public sealed class CatalogClient(HttpClient http)
{
    public async Task<Item?> GetAsync(
        string id, CancellationToken cancellationToken)
    {
        using var response = await http.GetAsync(
            $"items/{Uri.EscapeDataString(id)}", cancellationToken);
        if (response.StatusCode == HttpStatusCode.NotFound) return null;
        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<Item>(
            cancellationToken: cancellationToken);
    }
}

این نمونه به Microsoft.Extensions.Http نیاز دارد و timeout را برای client تنظیم می‌کند؛ cancellation caller هم جدا عبور می‌کند. یک timeout سراسری نباید جای cancellation کلاینت یا deadline درخواست را بگیرد. اگر از cookie استفاده می‌کنی، pooling handler در factory می‌تواند CookieContainer را بین clientها شریک کند؛ رفتار و جداسازی cookie را با نیاز امنیتی بسنج.

This example needs Microsoft.Extensions.Http, sets a client timeout and separately propagates caller cancellation. A global timeout is not a replacement for caller cancellation or a request deadline. If you use cookies, factory handler pooling can share a CookieContainer across clients; evaluate cookie isolation against your security requirements.

status، header و body شواهدندStatus, headers and body are evidence

200 یعنی درخواست در سطح HTTP موفق بوده، نه الزاماً داده از نظر دامنه درست است. 401 با 403 فرق دارد؛ 429 ممکن است Retry-After بدهد؛ 500 پاسخ سرور است و معمولاً retry کورکورانهٔ POST می‌تواند عملیات تکراری بسازد. برای هر endpoint قرارداد status و idempotency را ثبت کن. headerهای response را از response.Headers و headerهای محتوا را از response.Content.Headers بخوان؛ همه در یک مجموعه نیستند.

A 200 means HTTP-level success, not necessarily valid domain data. 401 differs from 403; 429 may include Retry-After; a 500 is a server response, and blindly retrying a POST can duplicate work. Document status and idempotency per endpoint. Read response headers from response.Headers and content headers from response.Content.Headers; they are not one collection.

شبکه قطع می‌شود؛ cancellation را تا انتها ببرNetworks stall; propagate cancellation end to end

ارسال، خواندن body و deserialize می‌توانند منتظر بمانند. token درخواست ورودی را از لایهٔ API تا SendAsync و خواندن محتوا عبور بده. cancellation با timeout یک چیز نیست: cancellation ممکن است کاربر یا shutdown باشد؛ timeout یعنی deadline سپری شده. exception شبکه هم با HTTP status مثل 503 متفاوت است؛ response دریافتی status دارد، ولی شکست transport شاید اصلاً response نداشته باشد.

Sending, reading a body and deserializing can all wait. Propagate the incoming request token from the API layer through SendAsync and content reading. Cancellation and timeout are not identical: cancellation may come from a caller or shutdown, while timeout is an elapsed deadline. A transport exception also differs from an HTTP status such as 503; a received response has a status, while a transport failure may have no response at all.

کوکی و credential را روی client مشترک نچسبانDo not attach per-user cookies or credentials to shared clients

HttpClient برای connection و تنظیمات مشترک است؛ request برای هویت و دادهٔ همان عملیات. API key سرویس ممکن است header ثابت typed client باشد، اما bearer token کاربر را در هر request بگذار. لاگ شبکه را هم با احتیاط فعال کن: headerهای Authorization و body ممکن است اطلاعات حساس داشته باشند. proxy، certificate validation و handler سفارشی را برای رفع خطا بی‌دلیل شل نکن.

HttpClient holds shared connection and configuration; a request carries the identity and data for one operation. A service API key may be a stable typed-client header, but a user bearer token belongs on each request. Enable network logging carefully: Authorization headers and bodies may be sensitive. Do not loosen proxy, certificate validation or custom-handler behavior as a casual fix.

تمرین: درخواست را از مرزها عبور بدهExercises: trace a request across boundaries

۱) response را dispose کن1) Dispose the response

کدی responseهای متوالی را نگه می‌دارد؛ عمر منبع و محتوا را اصلاح کن.

Code retains responses across repeated calls; fix response and content lifetimes.

پاسخ فنیTechnical reasoning

response را با using مدیریت کن و قبل از پایان scope محتوای لازم را بخوان.

Dispose the response with using and read required content before leaving its scope.

۲) client در حلقه2) Client in a loop

برای ۵۰۰ درخواست client جدید ساخته می‌شود؛ دو راه lifecycle را پیاده یا طرح کن.

A new client is created for 500 calls; implement or outline two lifecycle strategies.

پاسخ فنیTechnical reasoning

client بلندعمر با PooledConnectionLifetime یا factory-managed client با handler pool را انتخاب کن.

Choose a long-lived client with PooledConnectionLifetime or factory-created clients with pooled handlers.

۳) DNS جابه‌جا شده3) DNS changed

server به IP جدید منتقل شده ولی client اتصال قدیمی را نگه می‌دارد؛ دلیل و repair را مستند کن.

A server moved to a new IP but the client retains old connections; explain and fix the issue.

پاسخ فنیTechnical reasoning

connection pool را با lifetime مناسب بچرخان تا اتصال جدید DNS را دوباره resolve کند؛ مقدار را با زیرساخت بسنج.

Rotate pooled connections using an appropriate lifetime so new connections resolve DNS again; tune it to the infrastructure.

۴) 404 دامنه‌ای4) Domain-level 404

تابع با EnsureSuccessStatusCode، 404 عادی را exception می‌کند؛ contract را اصلاح کن.

A method throws on a normal 404 because it calls EnsureSuccessStatusCode; repair the contract.

پاسخ فنیTechnical reasoning

404 را پیش از Ensure بررسی و مطابق دامنه به null/نتیجه تبدیل کن؛ statusهای دیگر را جدا مدیریت کن.

Handle 404 before Ensure and map it to a domain result; treat other statuses separately.

۵) header کاربر5) Per-user header

token روی DefaultRequestHeaders client مشترک تنظیم می‌شود؛ race دو کاربر را بازتولید و درست کن.

A shared client stores a token in DefaultRequestHeaders; reproduce and fix a two-user race.

پاسخ فنیTechnical reasoning

Authorization را روی هر HttpRequestMessage مجزا قرار بده، نه state مشترک client.

Set Authorization on each separate HttpRequestMessage, not shared client state.

۶) cancellation6) Cancellation

کاربر اتصال را قطع می‌کند اما سرویس بیرونی همچنان صدا می‌شود؛ token را از route تا content بخوانی عبور بده.

The user disconnects but the outbound call continues; propagate cancellation from route through response reading.

پاسخ فنیTechnical reasoning

همان token را به SendAsync و API async محتوا بده و cancellation را به‌عنوان خطای transport گزارش نکن.

Pass the token to SendAsync and asynchronous content APIs; do not report cancellation as a transport failure.

۷) retry روی POST7) Retrying POST

سرویس هر POST را پس از timeout خودکار دوباره می‌فرستد؛ خطر duplicate را تحلیل و سیاست امن طراحی کن.

A service retries every POST after timeout; analyze duplicate risk and design a safe policy.

پاسخ فنیTechnical reasoning

retry فقط با semantics idempotent یا idempotency key و بودجهٔ محدود؛ timeout ثابت نمی‌کند سرور عملیات را اجرا نکرده.

Retry only with idempotent semantics or an idempotency key and a bounded budget; timeout does not prove the server skipped the operation.

۸) timeout و cancellation8) Timeout versus cancellation

دو exception در log یکی دیده می‌شوند؛ نوع علت و پاسخ مشاهده‌پذیری را تفکیک کن.

Two failures look identical in logs; distinguish their causes and telemetry response.

پاسخ فنیTechnical reasoning

deadline timeout، token لغوشده و exception شبکه را جدا classify و بدون ثبت payload حساس log کن.

Classify deadline timeout, cancelled token and transport exception separately without logging sensitive payloads.

۹) response header یا content header9) Response or content header?

کد Content-Type را در مجموعهٔ response می‌جوید؛ محل درست را پیدا کن.

Code looks for Content-Type in response headers; locate the correct collection.

پاسخ فنیTechnical reasoning

Content-Type در response.Content.Headers است؛ headerهای عمومی را در response.Headers بخوان.

Content-Type is in response.Content.Headers; read general response headers from response.Headers.

۱۰) 429 و Retry-After10) 429 and Retry-After

API محدودیت نرخ برمی‌گرداند؛ client زمان پیشنهادی و سقف retry را رعایت کند.

An API returns a rate limit; make the client respect the suggested delay and retry cap.

پاسخ فنیTechnical reasoning

429 و Retry-After را parse کن؛ retry budget محدود و cancellation/deadline را رعایت کن.

Parse 429 and Retry-After, apply a bounded retry budget, and honor cancellation/deadlines.

۱۱) body بزرگ11) Large response body

یک response بزرگ بی‌جهت کامل در string materialize می‌شود؛ با stream مصرفش کن.

A large response is unnecessarily materialized as one string; consume it as a stream.

پاسخ فنیTechnical reasoning

از ResponseHeadersRead و stream content استفاده کن؛ حد اندازه و cancellation را هم نگه دار.

Use ResponseHeadersRead and the content stream, while retaining size limits and cancellation.

۱۲) base address12) Base address

آدرس نسبی به host اشتباه می‌رود؛ URI ترکیبی و slash پایانی را تست کن.

A relative URI targets the wrong location; test URI composition and trailing slash behavior.

پاسخ فنیTechnical reasoning

BaseAddress و path را در fixture مستند کن؛ slash نهایی base روی resolve مسیر اثر دارد.

Document BaseAddress and path in a fixture; a trailing slash on the base affects path resolution.

۱۳) cookie pooling13) Pooled cookies

دو کاربر از factory handler مشترک cookie می‌گیرند؛ نشت احتمالی را تحلیل کن.

Two users share cookies through a factory-pooled handler; analyze possible leakage.

پاسخ فنیTechnical reasoning

CookieContainer ممکن است بین handlerهای poolشده مشترک شود؛ client/cookie lifecycle را جدا طراحی یا factory را برای این مورد کنار بگذار.

A CookieContainer can be shared by pooled handlers; isolate cookie lifetimes or avoid the factory for this use case.

۱۴) DNS و test server14) DNS and a test server

integration test به شبکهٔ بیرونی وابسته است؛ handler محلی بساز تا status و body قطعی شوند.

An integration test depends on the public network; use a local handler to make status and body deterministic.

پاسخ فنیTechnical reasoning

HttpMessageHandler سفارشی/Mock را تزریق و پاسخ، timeout و cancellation را بدون DNS واقعی تست کن.

Inject a custom or mocked HttpMessageHandler and test responses, timeout and cancellation without real DNS.

۱۵) token سرویس15) Service token

token ثابت سرویس را در source code گذاشته‌اند؛ محل config و redaction log را اصلاح کن.

A fixed service token is hardcoded; move configuration and redact logs appropriately.

پاسخ فنیTechnical reasoning

secret را از secret store/config امن بگیر؛ برای هر درخواست header مجزا و logging با redaction به‌کار ببر.

Load the secret from secure configuration; attach it per request and use redacted logging.

۱۶) رخداد پورت‌ها16) Port-exhaustion incident

با افزایش بار، requestها کند می‌شوند؛ ساخت client، پاسخ‌های disposeنشده و DNS را بررسی و evidence جمع کن.

Requests slow under load; investigate client creation, undisposed responses and DNS, collecting evidence.

پاسخ فنیTechnical reasoning

تعداد client/connection، عمر pool، زمان انتظار و handler را بسنج؛ اصلاح lifecycle را load-test و status/latency را مقایسه کن.

Measure client/connection counts, pool lifetime, wait time and handlers; load-test the lifecycle fix and compare status and latency.

آزمایشگاه: client سرویس کاتالوگLab: a catalog-service client

یک client کوچک برای API محلی بساز که مسیر موفق، 404، 429، 500، پاسخ JSON خراب و لغو را برگرداند. typed client یا client بلندعمر مناسب معماری‌ات را انتخاب کن؛ token کاربر را روی request بگذار، response را dispose کن، cancellation را تا خواندن body عبور بده و برای هر status نتیجهٔ دامنه‌ای بساز. روی retry فقط برای عملیات idempotent تصمیم بگیر؛ secret و payload را در log افشا نکن. test handler را محلی نگه دار تا شبکهٔ عمومی وابستگی تست نباشد.

Build a small local API that returns success, 404, 429, 500, malformed JSON and cancellation cases. Choose a typed or long-lived client that fits the architecture; attach user tokens per request, dispose responses, propagate cancellation through body reading and map statuses to domain results. Retry only idempotent operations; never expose secrets or full payloads in logs. Keep the test handler local so tests do not depend on the public network.

  1. برای هر status ورودی و خروجی را assert کن.
  2. Assert request and result for each status.
  3. دو درخواست هم‌زمان با token جدا بفرست و عدم اختلاط را ثابت کن.
  4. Send concurrent calls with separate tokens and prove isolation.
  5. connection lifecycle انتخاب‌شده و علتش را ثبت کن.
  6. Document the chosen connection lifecycle and its rationale.

پیام کوتاه‌عمر است، connection نه لزوماًMessages are short-lived; connections need not be

درخواست و پاسخ را در scope مصرف کن؛ client را برای هر پیام دور نینداز. status، transport failure، timeout و cancellation را یکی نکن. connection pool و DNS با lifetime handler سروکار دارند؛ هویت کاربر و body با request خودش. وقتی این مرزها درست باشند، API client قابل تست و هم‌زمانی است—و بعد می‌توانیم پایین‌تر برویم تا ببینیم TCP چرا اصلاً مرز message را تضمین نمی‌کند.

Scope requests and responses to their use; do not throw away a client for every message. Keep status, transport failure, timeout and cancellation distinct. Connection pools and DNS belong to handler lifetime; user identity and body belong to each request. With those boundaries in place, the client is testable and concurrency-safe—and next we go beneath HTTP to see why TCP does not preserve message boundaries.
