دسترسی، static و ساختار نوع

Access, static and type organization

یک همکار با نوشتن مستقیم در property داخلی، گزارش سفارش را خراب کرده. سفارش را در فصل قبل معتبر ساختیم؛ حالا باید ببینیم چه کسی از بیرون اجازهٔ دیدن یا تغییر هر عضو را دارد و کدام مقدار واقعاً بین نمونه‌ها مشترک است.

A teammate corrupted an order report by writing directly to an internal property. Last chapter we made an order valid; now we ask who outside may see or change each member, and which values are genuinely shared between instances.

API یعنی چه چیزی را مجاز می‌کنی؟An API defines what you permit

اگر هر مصرف‌کننده‌ای بتواند هر عضو را تغییر دهد، invariant سازنده و property خصوصی هیچ کمکی نمی‌کنند. سطح دسترسی فقط «پنهان‌کاری» نیست؛ قرارداد استفاده از نوع است. قبل از انتخاب modifier بپرس: چه کدی واقعاً باید این عضو را مصرف کند؟

If every consumer can mutate every member, constructor and private-property invariants do not help. Access modifiers are not just about hiding; they define how a type may be used. Before choosing one, ask which code genuinely needs this member.

protected internal و private protected ترکیب دو مرزند: اولی دسترسی از همان assembly یا derivedها را می‌دهد؛ دومی فقط derivedهای داخل همان assembly را. این‌ها را برای رفع خطای دسترسی تصادفی انتخاب نکن؛ دلیل طراحی باید روشن باشد.

protected internal combines same-assembly access with derived-type access; private protected limits access to derived types in the same assembly. Do not choose them merely to silence an access error; have a clear design reason.

جزئیات داخلی را به قرارداد تبدیل نکنDo not turn implementation details into contracts

وقتی field را public می‌کنی، مصرف‌کننده به شکل فعلی ذخیره‌سازی وابسته می‌شود. بعداً حتی اگر بخواهی اعتبارسنجی یا logging اضافه کنی، تغییر API می‌تواند callerها را بشکند. مرز کوچک‌تر، آزادی تغییر داخل type را بیشتر می‌کند.

A public field couples consumers to the current storage representation. Later, even adding validation or logging may require a breaking API change. A smaller boundary gives the type more freedom to evolve internally.

API با مرز تغییر روشن / A controlled API
public sealed class Order
{
    private int _itemCount;

    public int ItemCount => _itemCount;

    public void AddItems(int count)
    {
        if (count <= 0)
            throw new ArgumentOutOfRangeException(nameof(count));

        _itemCount = checked(_itemCount + count);
    }
}

مصرف‌کننده state را می‌خواند و درخواست تغییر می‌دهد؛ خودش invariant را بازنویسی نمی‌کند. sealed هم جلوی ارث‌بری را می‌گیرد؛ فقط وقتی بگذار که واقعاً نمی‌خواهی این type نقطهٔ توسعهٔ زیرنوع‌ها باشد، نه به‌عنوان طلسم امنیتی.

Consumers can read state and request a mutation without rewriting the invariant themselves. sealed prevents derivation; use it when the type is intentionally not an extension point, not as a security charm.

static یعنی متعلق به type، نه یک instanceStatic means belonging to the type, not an instance

فصل ۱۳ دیدیم تعداد سفارش نباید مشترک باشد. در مقابل، تعداد سفارش‌های ساخته‌شده یا یک تابع تبدیل بی‌حالت ممکن است به خود type تعلق داشته باشد. عضو static با نام type صدا زده می‌شود و برایش instance لازم نیست.

In Chapter 13, we saw that item count should not be shared between orders. By contrast, a count of created orders or a stateless conversion helper may belong to the type. Static members are accessed through the type and require no instance.

تابع نوع در برابر state هر نمونه / Type member and instance state
class Money
{
    public static decimal WithTax(decimal amount, decimal rate)
        => amount * (1 + rate);
}

Console.WriteLine(Money.WithTax(100m, 0.09m));

تابع بالا از state پنهان instance استفاده نمی‌کند، پس static بودن قابل‌فهم است. اگر تابع به نرخ مالیات شهر، زمان یا تنظیمات قابل‌تغییر وابسته شود، ورودی‌ها و مالکیت آن را دوباره بررسی کن؛ static به‌تنهایی تابع را pure یا thread-safe نمی‌کند.

The method uses no hidden instance state, so static is understandable. If it later depends on a city tax rate, time or mutable settings, reconsider its inputs and ownership; static alone does not make a method pure or thread-safe.

const و readonly یک قرارداد زمانی ندارندconst and readonly have different timing contracts

const مقدار compile-time است و مصرف‌کننده ممکن است مقدار آن را هنگام build در کد خود بگنجاند. تغییر مقدار const در کتابخانه و جایگزین‌نکردن binary مصرف‌کننده می‌تواند مقدار قدیمی را باقی بگذارد. readonly در زمان اجرا فقط از assignment معمولی بعد از initialization جلوگیری می‌کند و می‌تواند در constructor مقدار بگیرد.

A const is a compile-time value, and consumers may embed it in their own binaries during compilation. Changing a library constant without rebuilding consumers can leave the old value in place. readonly prevents ordinary reassignment after initialization at runtime and may be assigned in a constructor.

مقدار ثابت یا تنظیم‌پذیر در ساخت / Compile-time or construction-time
class RetryPolicy
{
    public const int MaximumDocumentedAttempts = 5;
    public readonly int MaxAttempts;

    public RetryPolicy(int maxAttempts)
    {
        if (maxAttempts < 1)
            throw new ArgumentOutOfRangeException(nameof(maxAttempts));
        MaxAttempts = maxAttempts;
    }
}

const برای مقدار literal و واقعاً ثابت مناسب است؛ readonly وقتی مقدار بر اساس configuration یا ورودی سازنده انتخاب می‌شود. readonly هم عمیق نیست: اگر reference به شیء mutable باشد، خود reference را نمی‌توان عوض کرد، ولی شاید محتوای آن شیء هنوز تغییرپذیر باشد.

const suits literal values that are genuinely fixed; readonly fits values selected from configuration or constructor input. readonly is not deep immutability: a reference may not be reassigned while the referenced mutable object’s contents can still change.

static constructor: مقداردهی type، با احتیاطStatic constructors: type initialization, with care

static constructor بدون پارامتر است و خود runtime آن را برای مقداردهی type اجرا می‌کند؛ caller مستقیم صدا نمی‌زند. اگر initialization آن exception بدهد، استفاده از type ممکن است در همان process شکست‌خورده بماند و خطای دیرهنگام را به فراخوانی معمولی تبدیل نکن.

A static constructor has no parameters and is run by the runtime to initialize a type; callers do not invoke it directly. If initialization throws, later use of the type in that process may remain failed, so do not hide fallible routine work there.

initialization بی‌نیاز از ورودی بیرونی / Type initialization
class CurrencyTable
{
    public static readonly IReadOnlyDictionary<string, string> Symbols;

    static CurrencyTable()
    {
        Symbols = new Dictionary<string, string>
        {
            ["USD"] = "$",
            ["EUR"] = "€"
        };
    }
}

برای اتصال شبکه، خواندن secret یا کاری که ممکن است به تنظیمات محیط وابسته باشد، static constructor معمولاً مرز خوبی نیست؛ خطا و چرخهٔ عمرش را مصرف‌کننده کنترل نمی‌کند. این مثال فقط initialization داخلی را نشان می‌دهد. حتی IReadOnlyDictionary هم الزاماً dictionary زیرین را از همهٔ مسیرها immutable نمی‌کند؛ مرز واقعی را درست انتخاب کن.

A static constructor is usually a poor boundary for network access, secret loading or environment-dependent work: consumers cannot control its failure and lifecycle. This example shows internal initialization only. IReadOnlyDictionary does not necessarily make the underlying dictionary immutable through every path; choose the actual boundary carefully.

partial برای تقسیم یک type؛ نه چند هویتpartial splits one type, not its identity

partial اجازه می‌دهد تعریف یک type در چند فایل بیاید؛ پس از compile همچنان یک type واحد است. این برای جداسازی کد تولیدشده از کد دستی مفید است، اما خردکردن بی‌دلیل یک کلاس کوچک پیدا کردن رفتار را سخت می‌کند. type تو در تو هم فقط وقتی به مالکیت و دسترسی کمک می‌کند مناسب است؛ ساختار را برای زیبایی ظاهری عمیق نکن.

partial allows one type definition to span files; after compilation it remains one type. This helps separate generated and handwritten code, but splitting a small class without reason makes behaviour harder to find. A nested type is useful only when it clarifies ownership or access; do not add nesting for visual neatness.

فایل دستی و فایل تولیدشده / Handwritten and generated files
// Order.cs
public partial class Order
{
    public string Number { get; private set; } = "";
}

// Order.Generated.cs
public partial class Order
{
    public string DisplayLabel => $"Order {Number}";
}

هر دو بخش باید namespace و نوع partial سازگار داشته باشند. فایل generated را دستی ویرایش نکن؛ ابزار در build بعدی بازنویسی‌اش می‌کند. بخش دستی باید جای extension باشد یا تغییر در generator انجام شود.

Both parts must agree on namespace and partial type. Do not hand-edit generated output; the tool may overwrite it on the next build. Extend through the handwritten part or change the generator instead.

آزمایشگاه: API سفارش را کوچک و قابل اتکا کنLab: make the Order API narrow and dependable

از Order فصل ۱۴ شروع کن. هدف این نیست که همه‌چیز private شود؛ هدف این است که هر عضو عمومی دلیل روشنی داشته باشد و هیچ مسیر دورزدن invariant باقی نماند.

Start from Chapter 14’s Order. The goal is not to make everything private; every public member should have a reason, and no mutation path should bypass the invariant.

  1. تمام fieldها را فهرست و برای هرکدام مصرف‌کنندهٔ واقعی مشخص کن.
  2. List every field and identify its real consumers.
  3. دسترسی هر عضو را حداقلِ لازم انتخاب کن و compile را اجرا کن.
  4. Choose the least access each member needs and compile.
  5. یک helper بی‌حالت را static کن؛ اگر تنظیم mutable لازم دارد، ورودی‌اش کن.
  6. Make a stateless helper static; pass mutable settings as inputs.
  7. یک const را با readonly مقایسه کن و با rebuild مصرف‌کننده تفاوت انتشار را توضیح بده.
  8. Compare const with readonly and explain consumer rebuild implications.
  9. یک کلاس تولیدشده را با partial جدا کن و build را ثابت کن؛ فایل generated را ویرایش نکن.
  10. Split a generated type with partial and prove the build; do not edit generated output.
  11. تست کن caller بیرونی نمی‌تواند ItemCount را مستقیماً خراب کند.
  12. Test that an external caller cannot directly corrupt ItemCount.
معیار پایانDefinition of done

API عمومی کوچک و مستند است، helperهای static واقعاً state نمونه ندارند، تغییر state از مسیر کنترل‌شده می‌گذرد و partial فقط مرز تولید/دستی یا تقسیم معنادار را حل می‌کند.

The public API is small and intentional, static helpers truly have no instance state, mutations use controlled paths, and partial solves a meaningful generated/handwritten or organizational boundary.

فیلدی فقط داخل همان کلاس استفاده می‌شود؛ چه modifierی انتخاب می‌کنی؟

A field is used only inside its class. Which modifier?

private; do not widen access without a need.

۲) قرارداد assembly2) Assembly boundary

دو کلاس در یک assembly همکاری می‌کنند، اما مصرف‌کنندهٔ بیرونی نباید helper را ببیند. انتخاب؟

Two classes in one assembly share a helper that external consumers must not see. Choose an access level.

پاسخAnswer

internal، اگر دسترسی همهٔ کد همان assembly قابل قبول است؛ برای یک کلاس خاص private یا طراحی دیگری لازم است.

internal if all code in the assembly may access it; use private or another design if only one type should.

۳) protected را چه وقت بدهیم؟3) When to expose protected?

آیا protected یعنی دسترسی «امن‌تر»؟ یک ریسک API آن را توضیح بده.

Does protected mean “safer”? Explain one API risk.

پاسخAnswer

نه؛ زیرنوع‌ها به جزئیات وابسته می‌شوند و تغییر آن‌ها را می‌شکند. فقط عضو توسعهٔ عمدی را protected کن.

No; derived types become coupled to implementation details. Expose only intentional extension points.

۴) static یا instance؟4) Static or instance?

تابع تبدیل decimal مستقل از هر سفارش را کجا می‌گذاری؟

Where would you put a decimal conversion independent of any order?

پاسخAnswer

static روی نوع مناسب یا helper؛ اگر وابستگی mutable دارد آن را پارامتر بده یا مالکیت را بازطراحی کن.

On an appropriate type as a static helper; pass mutable dependencies or redesign ownership.

۵) state سفارش را static نکن5) Keep order state instance-specific

دو سفارش تعداد مختلف دارند؛ نتیجهٔ static کردن ItemCount چیست؟

Two orders have different quantities. What happens if ItemCount is static?

پاسخAnswer

یک مقدار مشترک می‌شود و تفکیک سفارش‌ها از بین می‌رود.

It becomes shared state and the orders are no longer distinguished.

۶) const یا readonly؟6) const or readonly?

حد retry از تنظیمات هنگام ساخت می‌آید. انتخاب و علت؟

A retry limit comes from configuration at construction. Choose and explain.

پاسخAnswer

readonly؛ مقدار در compile-time ثابت نیست و می‌تواند در constructor تعیین شود.

readonly; the value is not fixed at compile time and can be set in the constructor.

۷) پیامد تغییر const7) Changing a const

کتابخانه مقدار const را تغییر داده، اما برنامهٔ مصرف‌کننده rebuild نشده. چه خطری هست؟

A library changes a const but the consumer is not rebuilt. What can happen?

پاسخAnswer

مقدار قدیمی که موقع compile مصرف‌کننده در کدش embed شده باقی می‌ماند.

The old value embedded into the consumer at compile time may remain.

۸) readonly عمیق است؟8) Is readonly deep?

reference به List را readonly کن. آیا itemهای List حتماً immutable می‌شوند؟

Make a List reference readonly. Are its items necessarily immutable?

پاسخAnswer

نه؛ فقط assignment مجدد خود reference محدود می‌شود. محتوای list ممکن است تغییر کند.

No; reassignment of the reference is restricted, but the list’s contents may still change.

۹) static constructor و I/O9) Static constructor and I/O

چرا خواندن secret شبکه‌ای در static constructor پرریسک است؟

Why is reading a network secret in a static constructor risky?

پاسخAnswer

caller چرخه و زمان اجرا را کنترل نمی‌کند؛ شکست initialization استفاده از type را مختل می‌کند. dependency را صریح و قابل مدیریت کن.

Callers cannot control its timing or lifecycle, and failure can poison type use. Make the dependency explicit and manageable.

۱۰) partial چه می‌کند؟10) What does partial do?

کلاس partial در دو فایل چند type مستقل می‌سازد؟

How many independent types do two partial declarations define?

پاسخAnswer

یک type واحد پس از ترکیب در compile.

One type after compile-time combination.

۱۱) فایل generated را ویرایش کن؟11) Should you edit generated output?

generator در build فایل را بازنویسی می‌کند. تغییر را کجا بگذاری؟

A generator overwrites a file during build. Where should your change go?

پاسخAnswer

در بخش دستی partial یا در خود generator؛ خروجی تولیدشده را منبع حقیقت نکن.

In the handwritten partial part or the generator; do not treat generated output as the source of truth.

۱۲) protected internal را تفسیر کن12) Interpret protected internal

دو راه دسترسی مجازش چیست؟

What are its two allowed access paths?

پاسخAnswer

از همان assembly یا از زیرنوع، حتی بیرون assembly.

۱۳) API را باریک کن13) Narrow an API

کلاسی پنج public عضو دارد که فقط دو موردشان لازم بیرون باشند. روش بررسی؟

A class has five public members but only two are needed externally. How do you review it?

مسیرApproach

مصرف‌کننده‌ها را جست‌وجو کن، دسترسی هر عضو را به حداقل لازم کاهش بده، سپس کل solution و تست‌ها را build کن تا وابستگی پنهان آشکار شود.

Search consumers, reduce each member to the minimum needed, then build the solution and tests to reveal hidden dependencies.

۱۴) طراحی فایل چندتکه را توجیه کن14) Justify a split type

یک دلیل موجه و یک دلیل ضعیف برای partial بنویس.

Give one sound and one weak reason for partial.

پاسخAnswer

جداکردن generated code از handwritten دلیل موجه است؛ صرفاً طولانی‌شدن فایل بدون مرز مسئولیت، دلیل ضعیفی است.

Separating generated from handwritten code is sound; splitting a long file without a responsibility boundary is weak.

سطح دسترسی را به اندازهٔ نیاز باز کنExpose only what the contract needs

private جزئیات داخلی را نگه می‌دارد؛ public API پشتیبانی‌شده می‌سازد؛ internal مرز assembly است؛ protected نقطهٔ توسعه برای زیرنوع‌هاست. static مالکیت type را نشان می‌دهد، const مقدار compile-time است و readonly جلوی assignment مجدد معمول را می‌گیرد. فصل بعد همین تفاوت مالکیت و کپی را برای class، struct و record از روی رفتار می‌سنجیم.

private keeps implementation details inside; public creates a supported API; internal marks an assembly boundary; protected exposes an extension point. static expresses type ownership, const is compile-time, and readonly prevents ordinary reassignment. Next we compare ownership and copying across class, struct and record through behaviour.
