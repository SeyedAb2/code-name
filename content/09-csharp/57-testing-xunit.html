تست اجرایی با xUnit

Executable tests with xUnit

تغییر کوچکی در محاسبهٔ تخفیف، سفارش قدیمی را رایگان کرده. تیم می‌گوید «روی سیستم من درست بود». تا وقتی رفتار مورد انتظار به یک تست خودکار تبدیل نشده، هر اصلاح می‌تواند همان باگ را برگرداند. تست قرار نیست همهٔ برنامه را ثابت کند؛ قرار است یک رفتار مشخص را سریع، قابل‌تکرار و بی‌نیاز از قضاوت چشمی بررسی کند.

A small discount change made an old order free. The team says, “It worked on my machine.” Until expected behavior becomes an automated test, another change can reintroduce the bug. Tests do not prove the whole application; they check a specific behavior quickly, repeatably and without visual judgment.

تست، مثال اجراییِ یک قرارداد استA test is an executable example of a contract

برای تخفیف سفارش، contract را اول به زبان روشن بگو: subtotal منفی ممنوع؛ تخفیف بین صفر و یک است؛ قیمت نهایی منفی نمی‌شود؛ و rounding طبق واحد پول تعریف می‌شود. تست خوب همین قرارداد را نام‌گذاری و اجرا می‌کند. تستی که فقط متد را صدا بزند اما چیزی را assert نکند، موفقیت را ثابت نمی‌کند.

State the discount contract first: subtotal cannot be negative; discount is between zero and one; the final price cannot be negative; and rounding follows the currency unit. A good test names and executes that contract. A test that only calls a method without asserting anything proves no outcome.

تست رفتار / A behavior test
public sealed class DiscountCalculator
{
    public decimal Apply(decimal subtotal, decimal rate)
    {
        if (subtotal < 0) throw new ArgumentOutOfRangeException(nameof(subtotal));
        if (rate is < 0 or > 1) throw new ArgumentOutOfRangeException(nameof(rate));
        return decimal.Round(subtotal * (1 - rate), 2);
    }
}

[Fact]
public void Apply_ValidRate_ReturnsDiscountedSubtotal()
{
    var sut = new DiscountCalculator();

    decimal actual = sut.Apply(100m, 0.15m);

    Assert.Equal(85m, actual);
}

نام sut یعنی system under test؛ لازم نیست همه از این مخفف استفاده کنند، اما نام تست باید رفتار را لو بدهد. الگوی Arrange، Act، Assert مرز آماده‌سازی، اجرا و بررسی را روشن می‌کند. هر تست را به یک رفتار اصلی محدود نگه دار تا شکستش قابل‌فهم باشد.

The name sut means system under test; the abbreviation is optional, but the test name should reveal behavior. Arrange, Act, Assert separates setup, execution and verification. Keep each test focused on one primary behavior so its failure is understandable.

Fact برای یک مثال، Theory برای چند ورودی یک قانونUse Fact for one case and Theory for one rule across inputs

[Fact] یک سناریوی مستقل را اجرا می‌کند. اگر چند ورودی باید همان رابطه را رعایت کنند، [Theory] و [InlineData] از تکرار تست جلوگیری می‌کنند. داده‌ها باید مرزهای مهم را پوشش دهند، نه اینکه صرفاً عددهای زیادی تولید کنیم. برای ورودی پیچیده‌تر می‌توان از منبع دادهٔ مناسب استفاده کرد؛ خوانایی داده از کوتاهی syntax مهم‌تر است.

[Fact] runs one scenario. When several inputs should satisfy the same rule, [Theory] and [InlineData] avoid duplicated tests. Cover meaningful boundaries rather than generating many arbitrary values. More complex inputs can use an appropriate data source; readable data matters more than terse syntax.

ورودی‌های مرزی / Boundary inputs
[Theory]
[InlineData(100, 0, 100)]
[InlineData(100, 15, 85)]
[InlineData(0, 50, 0)]
public void Apply_ValidInputs_ReturnExpectedPrice(
    int subtotal, int discountPercent, int expected)
{
    var sut = new DiscountCalculator();

    decimal actual = sut.Apply(subtotal, discountPercent / 100m);

    Assert.Equal((decimal)expected, actual);
}

در project واقعی اگر precision مالی مهم است، policy rounding را با product/حسابداری روشن کن؛ تست نباید تصمیم مبهم را پنهان کند. برای نرخ‌های نامعتبر هم یک Theory جدا بساز تا failure contract از نتیجهٔ موفق جدا باشد.

In a real product, agree on monetary rounding with the business/accounting policy; a test must not hide an ambiguous decision. Create a separate theory for invalid rates so failure contracts remain distinct from successful outcomes.

exception را دقیق و با علت تست کنTest exceptions precisely, including their cause

تست فقط نباید بگوید «یه exception آمد». نوع exception و ورودی/شرطی که آن را ایجاد می‌کند بخشی از contract است. در xUnit از assertion async برای متد async استفاده کن و task را await کن. اگر exception اشتباه یا از بخش آماده‌سازی بیاید، تست باید شکست بخورد؛ action را جدا و واضح نگه دار.

A test should not merely say “some exception happened.” Exception type and the input or condition that triggers it are part of the contract. Use xUnit's asynchronous assertion for async methods and await it. The test should fail if the wrong exception occurs or setup throws; keep the action explicit.

اعتبارسنجی و async exception / Validation and async exceptions
[Theory]
[InlineData(-1, 10)]
[InlineData(10, -10)]
[InlineData(10, 110)]
public void Apply_InvalidInput_Throws(int subtotal, int ratePercent)
{
    var sut = new DiscountCalculator();

    Assert.Throws<ArgumentOutOfRangeException>(
        () => sut.Apply(subtotal, ratePercent / 100m));
}

[Fact]
public async Task LoadAsync_CancelledRequest_PropagatesCancellation()
{
    using var cts = new CancellationTokenSource();
    cts.Cancel();

    await Assert.ThrowsAnyAsync<OperationCanceledException>(
        () => service.LoadAsync(cts.Token));
}

اگر API عمداً subtype مشخص‌تری می‌دهد، همان را assert کن؛ اگر contract هر OperationCanceledException را می‌پذیرد، assertion عام‌تر معنی‌دار است. برای async test از async void استفاده نکن؛ runner نمی‌تواند پایان و exception آن را مثل Task قابل انتظار مدیریت کند.

If the API promises a specific subtype, assert that; if its contract accepts any OperationCanceledException, a broader assertion is appropriate. Do not write async tests as async void; the runner cannot observe completion and failures like it can with an awaitable Task.

تست واحد باید سریع و مستقل بماندA unit test should stay fast and isolated

تست محاسبهٔ تخفیف نباید به اینترنت، دیتابیس واقعی، ساعت سیستم یا ترتیب اجرای تست‌ها وابسته باشد. اگر قانون business را می‌سنجی، dependencyهای بیرون از واحد را از مرز تست دور نگه دار. fake ساده‌ای که رفتار لازم را واقعاً اجرا می‌کند اغلب از mockهای فراوان واضح‌تر است. mock را جایی به کار ببر که تعامل با یک collaborator خودش contract باشد، نه برای اینکه هر property و متدی را تقلید کنیم.

A discount calculation test should not depend on the internet, a real database, system time or test execution order. When testing a business rule, keep external dependencies outside the unit boundary. A small fake with real behavior is often clearer than many mocks. Use a mock when interaction with a collaborator is itself part of the contract, not to imitate every property and method.

تزریق ساعت به‌جای انتظار برای زمان واقعی / Inject time instead of waiting
public sealed class ExpirationPolicy(TimeProvider clock)
{
    public bool IsExpired(DateTimeOffset expiresAt) =>
        clock.GetUtcNow() >= expiresAt;
}

[Fact]
public void IsExpired_AtBoundary_ReturnsTrue()
{
    var now = new DateTimeOffset(2026, 10, 4, 12, 0, 0, TimeSpan.Zero);
    var clock = new FakeTimeProvider(now);
    var sut = new ExpirationPolicy(clock);

    Assert.True(sut.IsExpired(now));
}

کلاس FakeTimeProvider در package مربوط به testing زمان فراهم می‌شود و باید آن را به‌عنوان dependency test اضافه کنی؛ API واقعی را با نسخهٔ target پروژه هماهنگ کن. هدف این است که زمان تست کنترل شود، نه اینکه تست به sleep و ساعت ماشین وابسته شود.

FakeTimeProvider comes from the time-testing package, which must be added as a test dependency; match its API to the project's target version. The goal is controlled test time, not dependence on sleeps or the machine clock.

fixture مشترک را فقط وقتی state را ایزوله می‌کنی به اشتراک بگذارShare fixtures only when shared state remains isolated

xUnit برای هر اجرای تست instance تازه‌ای از test class می‌سازد؛ constructor برای setup هر تست و Dispose برای cleanup همان instance کاربرد دارد. fixtureهای سطح class/collection برای منبع گران مثل server موقت‌اند، اما state مشترک می‌تواند تست‌ها را به ترتیب اجرا وابسته کند. resource مشترک را به‌روشنی بساز و آزاد کن و تست parallel را فقط در صورتی خاموش کن که دلیل واقعی و scope محدود داری.

xUnit creates a fresh test-class instance for each test; the constructor can set up that test and Dispose can clean it up. Class or collection fixtures suit expensive resources such as a temporary server, but shared state can make tests order-dependent. Create and release shared resources explicitly, and disable parallel tests only for a real reason and a narrow scope.

setup و cleanup هر تست / Per-test setup and cleanup
public sealed class CartTests : IDisposable
{
    private readonly Cart _cart = new();

    [Fact]
    public void AddItem_IncreasesCount()
    {
        _cart.Add(new Item("book", 1));
        Assert.Equal(1, _cart.Count);
    }

    public void Dispose() => _cart.Clear();
}

در مثال ساده بالا cleanup شاید لازم نباشد؛ عمداً ببین که هر تست instance خودش را دارد. برای تست‌هایی که DB یا فایل واقعی دارند، آن‌ها را integration test بنام، fixture و cleanup قطعی تعریف کن و وابستگی زیرساخت را پنهان نکن.

Cleanup may be unnecessary in this simple example; notice that each test has its own instance. Tests using a real database or file system are integration tests: name them accordingly, define fixtures and reliable cleanup, and do not hide infrastructure dependencies.

تست باید از CLI و CI هم قابل‌اجرا باشدTests must run from the CLI and CI too

ساختار ساده: یک پروژهٔ library و پروژهٔ تست که به آن project reference دارد. dotnet test restore/build/test را در مسیر معمول اجرا می‌کند. نتیجهٔ سبز وقتی ارزش دارد که همان command برای هم‌تیمی و pipeline هم کار کند. اگر تستی فقط در IDE یا روی ماشین نویسنده پیدا می‌شود، مشکل کشف، package، environment یا وابستگی پنهان را بررسی کن.

A simple structure has a library project and a test project referencing it. dotnet test performs the usual restore/build/test flow. A green result matters when the same command works for teammates and CI. If a test is discovered only in one IDE or on its author's machine, investigate discovery, packages, environment or hidden dependencies.

اجرای تست و فیلتر / Run and filter tests
dotnet test
dotnet test --filter "FullyQualifiedName~DiscountCalculator"
dotnet test --logger "console;verbosity=normal"

گزینه‌های دقیق filter و logger تابع test platform/adapter هستند؛ در صورت مهاجرت به Microsoft.Testing.Platform یا نسخهٔ جدید runner، docs همان نسخه را ببین. test framework، adapter و platform سه نقش مرتبط اما یکی نیستند. `dotnet test` نقطهٔ شروع است؛ جزئیات runner را در CI صریح و سازگار نگه دار.

Exact filter and logger options depend on the test platform and adapter; consult the matching version when adopting Microsoft.Testing.Platform or a newer runner. The test framework, adapter and platform are related but distinct roles. `dotnet test` is the starting point; keep runner details explicit and consistent in CI.

۸) fake یا mock8) Fake or mock

سرویس فقط به clock نیاز دارد. آیا برای آن کل فریم‌ورک mock لازم است؟

A service only needs a clock. Do you need a full mocking framework?

۹) تست وابسته به ترتیب9) Order-dependent test

تست تنها پس از تست قبلش پاس می‌شود چون static list پاک نشده. راه اصلاح چیست؟

A test passes only after the previous test because a static list was not cleared. How do you fix it?

راهنمای فنیTechnical hint

state را per-test کن یا fixture cleanup قطعی و محدود بساز؛ ترتیب تست را مبنا نگذار.

Make state per-test or add reliable scoped fixture cleanup; do not rely on test order.

۱۰) تست parallel10) Parallel tests

دو تست از یک فایل موقت ثابت استفاده می‌کنند و گاهی fail می‌شوند. اصلاح بهتر از خاموش‌کردن parallelization چیست؟

Two tests use the same temporary file and sometimes fail. What is better than disabling parallelization?

راهنمای فنیTechnical hint

مسیر یکتا برای هر تست، cleanup و مالکیت مستقل؛ فقط resource واقعاً مشترک را serialize کن.

Use a unique path per test with cleanup and isolated ownership; serialize only truly shared resources.

۱۱) assert مبهم11) Vague assertion

فقط `Assert.True(result > 0)` داری اما باید مبلغ دقیق برابر ۸۵ باشد؛ assertion را تقویت کن.

You only assert `result > 0`, but the exact amount must be 85. Strengthen the assertion.

راهنمای فنیTechnical hint

مقدار دقیق مورد انتظار و actual را با Assert.Equal مقایسه کن.

Compare the exact expected and actual values with Assert.Equal.

۱۲) inline data نامناسب12) Poor inline data

ورودی Theory یک فایل بزرگ و stream است؛ چرا InlineData انتخاب مناسبی نیست؟

A Theory input is a large file and stream. Why is InlineData a poor fit?

راهنمای فنیTechnical hint

دادهٔ پیچیده را با MemberData یا fixture خوانا و قابل‌ساخت ارائه کن و resource را cleanup کن.

Use readable MemberData or a fixture for complex data, and clean up resources.

۱۳) تست و implementation13) Tests coupled to implementation

تستی private method را از reflection صدا می‌زند؛ چه چیزی را جایگزین می‌کنی؟

A test invokes a private method via reflection. What should replace it?

راهنمای فنیTechnical hint

رفتار قابل مشاهده از public API را تست کن؛ اگر جداشدن logic ارزش دارد، طراحی را به component مستقل تغییر بده.

Test observable behavior through the public API; extract a separate component if the logic deserves an independent boundary.

۱۴) test platform14) Test platform

xUnit framework، adapter و runner را یکی فرض کرده‌ای. وظیفهٔ هر کدام را جدا توضیح بده.

You treated the xUnit framework, adapter and runner as one thing. Distinguish their roles.

راهنمای فنیTechnical hint

framework API/attribute را می‌دهد؛ adapter ارتباط می‌دهد؛ platform testها را کشف و اجرا و نتیجه را گزارش می‌کند.

The framework supplies APIs and attributes; the adapter connects it; the platform discovers, executes and reports tests.

۱۵) flaky در CI15) Flaky in CI

تست فقط گاهی در CI fail می‌شود و retry سبزش می‌کند. قبل از retry چه evidence جمع می‌کنی؟

A test intermittently fails in CI and retry makes it green. What evidence do you collect first?

راهنمای فنیTechnical hint

log زمان‌بندی، resource مشترک، timeout، ساعت، network و parallel run را ضبط کن؛ retry علت را درمان نمی‌کند.

Capture scheduling, shared resources, timeouts, clock, network and parallel execution; retries do not fix root causes.

۱۶) نام‌گذاری scenario16) Naming a scenario

برای سبد خالی، تستی بنویس که قصد business آن از نام و assertion روشن باشد.

Write a test for an empty cart whose business intent is clear from its name and assertion.

راهنمای فنیTechnical hint

رفتاری مانند `Checkout_EmptyCart_IsRejected` را انتخاب و نتیجهٔ ردشدن/خطا را assert کن.

Choose a behavior such as `Checkout_EmptyCart_IsRejected` and assert the rejection or error.

۱۷) setup گران17) Expensive setup

هر تست یک سرور سنگین بالا می‌آورد. چه زمانی fixture مشترک و چه زمانی جداسازی کامل؟

Every test starts an expensive server. When should you share a fixture versus isolate fully?

راهنمای فنیTechnical hint

اگر server immutable/shared است، fixture با scope مشخص؛ دادهٔ هر تست جدا و cleanup تضمین‌شده بماند.

Share an immutable server via a scoped fixture, while isolating each test's data and guaranteeing cleanup.

۱۸) گزارش تست شکست‌خورده18) Failure report

تستی فقط می‌گوید expected true, actual false. آن را برای تشخیص سریع‌تر بازنویسی کن.

A test only says expected true, actual false. Improve it for faster diagnosis.

راهنمای فنیTechnical hint

نام scenario، ورودی کلیدی و انتظار business را نشان بده؛ assertion را دقیق و setup را کوچک نگه دار.

Expose the scenario, key input and business expectation; keep the assertion precise and setup small.

آزمایشگاه: قانون قیمت‌گذاری که برنمی‌گرددLab: a pricing rule that does not regress

یک کتابخانهٔ کوچک قیمت‌گذاری بساز و برایش پروژهٔ تست xUnit جدا قرار بده. ابتدا contract تخفیف، rounding و ورودی نامعتبر را بنویس؛ سپس Fact و Theoryهای مرزی بساز و با dotnet test اجرا کن. یک تست را عمداً با expected اشتباه قرمز کن و پیام failure را تا حد ممکن تشخیصی کن. بعد ساعت و یک dependency بیرونی را به abstraction تزریق‌پذیر تبدیل کن و نشان بده تست بدون sleep، شبکه یا دیتابیس واقعی قابل‌اجراست. در آخر suite را چندبار و با اجرای parallel اجرا کن؛ اگر نتیجه به ترتیب وابسته است، state مشترک را پیدا و حذف کن. خروجی نهایی باید برای clone تازه با یک دستور قابل اجرا باشد.

Build a small pricing library with a separate xUnit test project. Write the discount, rounding and invalid-input contracts first; then add boundary Facts and Theories and run dotnet test. Deliberately make one expected value wrong and improve the failure message until it is diagnostic. Make the clock and one external dependency injectable, proving tests run without sleeps, network or a real database. Finally run the suite repeatedly and in parallel; if results depend on order, find and remove shared state. A fresh clone must run the suite with one command.

  4. Give each failure a precise expectation and behavior-focused name.
  5. فرمان fresh clone و خروجی سبز را در README ثبت کن.
  6. Document the fresh-clone command and green result in the README.

تست خوب، قرارداد را سریع و مستقل قابل‌اجرا می‌کندA good test makes a contract fast and independently executable

Fact و Theory شکل بیان سناریو هستند؛ ارزش تست از contract روشن، assertion دقیق و isolation می‌آید. تست واحد را از integration جدا نگه دار، زمان و state را کنترل کن و شکست را با retry پنهان نکن. اگر هزاران تست داری، سرعت و خوانایی مهم‌تر می‌شوند، نه کمتر. در فصل بعد BenchmarkDotNet را می‌آوریم تا برخلاف تست correctness، هزینهٔ اجرا را با روش قابل‌مقایسه اندازه بگیریم.

Fact and Theory express scenarios; a test's value comes from a clear contract, precise assertion and isolation. Keep unit tests distinct from integration tests, control time and state, and do not hide failures with retries. With thousands of tests, speed and clarity matter even more. Next we use BenchmarkDotNet to measure execution cost reproducibly, unlike correctness tests.
