assembly و بارگذاری افزونه

Assemblies and plugin loading

برنامه‌ای داریم که دستورهای تازه را بدون build مجدد می‌خواهد؛ تیم می‌گوید DLL را با Assembly.LoadFile بخوانیم و تمام. اما plugin ممکن است dependency خودش را داشته باشد، با نسخهٔ میزبان تعارض کند یا نوعی بسازد که میزبان «همان نام» را دارد اما همان type نیست. این‌جا assembly را از فایل روی دیسک تا context بارگذاری دنبال می‌کنیم و مرز اعتماد را فراموش نمی‌کنیم.

An application must add commands without rebuilding; the team proposes loading a DLL with Assembly.LoadFile and calling it done. But a plugin may have its own dependencies, conflict with host versions, or create a type with the same name that is not the same type to the host. We follow an assembly from disk into a load context without confusing loading with trust.

فصل ۵۹پیش‌نیازprerequisite

assembly فایل نیست، اما معمولاً از DLL می‌آیدAn assembly is not merely a file, though it commonly comes from a DLL

compiler کد را به IL، metadata و manifest تبدیل می‌کند؛ CLR آن را به‌عنوان assembly بارگذاری می‌کند و JIT در زمان اجرا code لازم را آماده می‌کند. فایل DLL معمولاً assembly managed است، اما نام فایل به‌تنهایی کافی نیست: dependency، target framework، culture و load context هم در resolution نقش دارند. دو type هم‌نام اگر از assembly identity یا context متفاوت بیایند الزاماً قابل cast به هم نیستند.

The compiler turns code into IL, metadata and a manifest; the CLR loads it as an assembly and the JIT prepares code when needed. A DLL commonly contains a managed assembly, but the file name is not enough: dependencies, target framework, culture and load context affect resolution. Two same-named types from different assembly identities or contexts are not necessarily cast-compatible.

دیدن هویت assembly / Inspect assembly identity
Assembly assembly = typeof(Program).Assembly;
AssemblyName identity = assembly.GetName();
Console.WriteLine(identity.FullName);
Console.WriteLine(AssemblyLoadContext.GetLoadContext(assembly)?.Name);

AssemblyName فقط یکی از بخش‌های تشخیص است؛ version binding و policyهای runtime را هم باید در سناریوی واقعی دید. از نام فایل، مسیر یا namespace نتیجه نگیر که نوع با type دیگری یکی است.

AssemblyName is only part of diagnosis; examine runtime binding behavior in the actual scenario too. Do not infer type identity from a file name, path or namespace.

plugin به contract پایدار نیاز داردA plugin needs a stable contract

میزبان نباید از داخل plugin با reflection هر متدی را حدس بزند. یک interface کوچک در assembly قراردادی جدا تعریف کن و هر دو طرف همان contract را share کنند. میزبان قرارداد را در default context بارگذاری می‌کند؛ plugin implementation و dependencyهای خودش را در context جدا. اگر contract assembly هم دوباره در context plugin بارگذاری شود، دو IPlugin ظاهراً هم‌نام ولی از نظر runtime متفاوت می‌شوند و cast شکست می‌خورد.

The host should not guess arbitrary plugin methods with reflection. Define a small interface in a separate contract assembly and share that contract on both sides. The host loads the contract in the default context; the plugin implementation and its private dependencies live in a separate context. If the contract is loaded again in the plugin context, the two apparently identical IPlugin types have different runtime identities and casts fail.

contract کوچک / A small plugin contract
public interface ICommandPlugin
{
    string Name { get; }
    ValueTask<int> ExecuteAsync(
        string[] args, CancellationToken cancellationToken);
}

contract را تا حد ممکن کم‌وابستگی نگه دار و دربارهٔ lifetime، thread-safety، exception، version compatibility و ownership داده‌ها تصمیم بگیر. interface boundary درون process، sandbox امنیتی نیست؛ plugin کد دلخواه با authority همان process اجرا می‌کند. کد غیرقابل‌اعتماد باید در مرز process و با کنترل سیستم‌عامل جدا شود.

Keep the contract low-dependency and define lifetime, thread safety, exceptions, version compatibility and data ownership. An in-process interface boundary is not a security sandbox: plugin code runs with the process's authority. Untrusted code needs an out-of-process boundary with operating-system controls.

هر plugin context خودش را دارد، dependencyها را resolver پیدا می‌کندGive each plugin a context and let a resolver find its dependencies

AssemblyLoadContext مرز resolution و type identity در .NET است؛ چند context می‌توانند نسخه‌های سازگار اما متفاوتی از dependency را در یک process بارگذاری کنند. برای plugin با dependency، از AssemblyDependencyResolver استفاده کن؛ این resolver به مسیر assembly اصلی و فایل‌های deployment مثل .deps.json تکیه دارد. در load، dependency خصوصی plugin را از مسیر resolver بیاور و contract مشترک را در context پیش‌فرض نگه دار.

AssemblyLoadContext defines an assembly-resolution and type-identity boundary in .NET; multiple contexts can load compatible but different dependency versions in one process. For plugins with dependencies, use AssemblyDependencyResolver, which relies on the main assembly path and deployment files such as .deps.json. Resolve private plugin dependencies from it while keeping the shared contract in the default context.

context برای dependencyهای plugin / Context for plugin dependencies
sealed class PluginLoadContext : AssemblyLoadContext
{
    private readonly AssemblyDependencyResolver _resolver;

    public PluginLoadContext(string pluginPath)
        : base(isCollectible: true)
        => _resolver = new AssemblyDependencyResolver(pluginPath);

    protected override Assembly? Load(AssemblyName name)
    {
        if (name.Name == typeof(ICommandPlugin).Assembly.GetName().Name)
            return null; // resolve the shared contract in Default

        string? path = _resolver.ResolveAssemblyToPath(name);
        return path is null ? null : LoadFromAssemblyPath(path);
    }

    protected override IntPtr LoadUnmanagedDll(string name)
    {
        string? path = _resolver.ResolveUnmanagedDllToPath(name);
        return path is null ? IntPtr.Zero : LoadUnmanagedDllFromPath(path);
    }
}

نمونه برای خوانایی ساده شده است: در برنامهٔ واقعی path را canonical/اعتبارسنجی کن، خطای فایل و dependency را مدیریت کن و انتشار plugin را با deps/runtimeconfig مناسب بساز. null از Load یعنی این context تصمیم نگرفته و resolution معمول ادامه یابد؛ به معنی «assembly وجود ندارد» نیست. native dependency هم مسیر resolver جدا دارد.

The sample is simplified for clarity: production code should canonicalize/validate paths, handle missing files and dependencies, and deploy suitable deps/runtimeconfig files. Returning null from Load means this context declines resolution so normal resolution can continue; it does not mean “the assembly does not exist.” Native dependencies have their own resolver path.

assembly را load کن، interface را پیدا کن و از contract عبور نکنLoad the assembly, find its implementation and stay within the contract

مسیر plugin باید به فایل اصلی assembly اشاره کند؛ resolver از metadata خروجی build کمک می‌گیرد. typeهای concrete را در assembly بگرد، implementation contract را پیدا کن و instance بساز. اگر constructor یا static initializer شکست خورد، exception را با نام plugin و مرحلهٔ load ثبت کن، نه اینکه کل خطا را بی‌صدا قورت بدهی. در اجرای command هم cancellation و timeout سمت میزبان تعریف شود؛ plugin نباید process را برای همیشه نگه دارد.

The plugin path must point to its main assembly; the resolver uses build output metadata. Find concrete types implementing the contract and create an instance. If construction or a static initializer fails, report the plugin name and loading stage rather than swallowing the error. The host should define cancellation and timeouts for command execution; a plugin must not hold the process forever.

پیداکردن implementation / Find an implementation
var loadContext = new PluginLoadContext(pluginPath);
Assembly assembly = loadContext.LoadFromAssemblyPath(pluginPath);

Type? implementation = assembly.GetTypes()
    .FirstOrDefault(type =>
        !type.IsAbstract &&
        typeof(ICommandPlugin).IsAssignableFrom(type));

if (implementation is null)
    throw new InvalidOperationException("Plugin contract not implemented.");

var plugin = (ICommandPlugin?)Activator.CreateInstance(implementation)
    ?? throw new InvalidOperationException("Plugin could not be created.");

برای pluginهای بزرگ، قرارداد discovery را مشخص کن: attribute، manifest یا factory شناخته‌شده. reflection روی همهٔ typeها ممکن است type initializer اجرا کند یا در assembly ناسازگار خطا بدهد؛ خطاها را isolate و گزارش‌پذیر کن. version قرارداد را در metadata/manifest مشخص کن و پیش از فعال‌سازی compatibility را بسنج.

For larger plugin systems, define discovery through an attribute, manifest or known factory. Reflecting over every type can trigger initializers or fail on incompatible assemblies; isolate and report those errors. Record the contract version in metadata/manifest and check compatibility before activation.

Unload همکاری دوطرفه است و فوری اتفاق نمی‌افتدUnloading is cooperative and is not immediate

اگر context با isCollectible: true ساخته شده، Unload() فقط شروع درخواست unload است. تا وقتی threadی در کد plugin باشد یا object/type/delegate/event handler آن از بیرون reference شود، context آزاد نمی‌شود. reference به instance و Assembly را کنار بگذار، eventها را unsubscribe کن، timer و thread را متوقف کن و taskها را await کن. context collectible مرز جداسازی dependency است، نه تضمین unload آنی.

With isCollectible: true, Unload() only initiates unloading. The context remains while a thread executes plugin code or an object, type, delegate or event handler is referenced externally. Release instances and Assembly references, unsubscribe events, stop timers and threads, and await tasks. A collectible context separates dependencies; it does not guarantee immediate unloading.

درخواست unload / Initiate unload
WeakReference contextRef = LoadAndRun(pluginPath);
// LoadAndRun creates a collectible context in a separate method,
// stops plugin work, releases plugin instances, then calls Unload().
for (int i = 0; contextRef.IsAlive && i < 10; i++)
{
    GC.Collect();
    GC.WaitForPendingFinalizers();
    GC.Collect();
}
Console.WriteLine(contextRef.IsAlive ? "Still referenced" : "Unloaded");

اجبار GC در این حلقه فقط یک آزمایش تشخیصی محدود برای unloadability است، نه الگوی production. localهای JIT هم ممکن است تا پایان scope زنده بمانند؛ helper جدا بساز تا referenceهای موقت از stack خارج شوند. اگر context زنده ماند، dump و tutorial unloadability را برای rootهای باقی‌مانده بررسی کن.

Forced GC in this loop is a bounded unloadability diagnostic, not a production pattern. JIT locals may remain live until a scope ends; use a separate helper so temporary references leave the stack. If the context stays alive, inspect remaining roots with a dump and the official unloadability guidance.

بارگذاری کد یعنی اجرای کد؛ آن را sandbox فرض نکنLoading code means executing code; do not treat it as a sandbox

AssemblyLoadContext دسترسی فایل، شبکه، environment، process یا native code را محدود نمی‌کند. امضای package یا hash به تشخیص اصالت کمک می‌کند اما کد بدخواه را بی‌خطر نمی‌سازد. pluginهای غیرقابل‌اعتماد را در process جدا با هویت سیستم‌عامل، مجوز محدود، IPC تعریف‌شده و سیاست منابع اجرا کن؛ اگر threat model جدی است، isolation را با متخصص امنیت طراحی کن.

AssemblyLoadContext does not restrict file, network, environment, process or native-code access. A package signature or hash helps verify provenance but does not make malicious code safe. Run untrusted plugins in a separate process with a restricted OS identity, explicit IPC and resource policy; involve security expertise for a serious threat model.

آزمایشگاه: میزبان فرمان و دو افزونهLab: a command host and two plugins

یک solution بساز که contract، host و دو plugin را جدا نگه می‌دارد. هر plugin یک dependency خصوصی با نسخهٔ متفاوت داشته باشد، اما هر دو interface مشترک را از contract واحد بگیرند. خروجی pluginها را در پوشهٔ مستقل publish کن تا deps.json و dependencyها کنار assembly باشند. برای هر plugin context و resolver خودش را بساز؛ هر دو را کشف و اجرا کن و identity نوع contract را ثابت کن. سپس plugin اول را collectible load کن، subscription و taskهایش را متوقف کن، instanceها را آزاد و unload را درخواست کن. با WeakReference در تست تشخیصی نتیجه را بررسی کن؛ اگر زنده ماند، rootهای باقی‌مانده را پیدا کن، نه اینکه حلقهٔ GC را در production کپی کنی. در گزارش نهایی روشن بنویس که این طراحی dependency isolation است و sandbox نیست.

Create a solution with separate contract, host and two plugin projects. Give each plugin a private dependency version while both use the same contract assembly. Publish plugin output into separate directories with their deps.json and dependencies. Create one context and resolver per plugin, discover and run both, and verify shared contract identity. Then load the first plugin into a collectible context, stop its subscriptions and tasks, release instances and initiate unload. Inspect the result through a WeakReference in a diagnostic test; if it remains alive, find the roots rather than copying a GC loop into production. State clearly that this is dependency isolation, not a sandbox.

  1. هر دو plugin بدون conflict dependency اجرا شوند.
  2. Both plugins run without dependency conflicts.
  3. contract از دو context به‌صورت type واحد شناخته شود.
  4. The contract has one shared type identity across contexts.
  5. محدودیت امنیتی و شرط‌های unload مستند شوند.
  6. Security limits and unload conditions are documented.

context بارگذاری، مرز dependency است؛ مرز اعتماد نیستA load context separates dependencies, not trust

AssemblyLoadContext کمک می‌کند dependencyهای plugin از میزبان و pluginهای دیگر جدا resolution شوند؛ AssemblyDependencyResolver فایل‌های managed و native را از خروجی plugin پیدا می‌کند. contract باید مشترک و پایدار باشد تا type identity حفظ شود. unload collectible همکاری می‌خواهد و reference باقی‌مانده جلوی آن را می‌گیرد. اگر کد نامطمئن است، process جدا مرز واقعی‌تری است. فصل بعد reflection و dynamic را می‌بینیم: چه وقت کشف runtime مفید است و چه وقت هزینه و شکنندگی می‌آورد.

AssemblyLoadContext helps resolve plugin dependencies separately from the host and other plugins; AssemblyDependencyResolver locates managed and native assets from plugin output. A stable shared contract preserves type identity. Collectible unload is cooperative and remaining references prevent completion. Untrusted code needs a separate process for a stronger boundary.
