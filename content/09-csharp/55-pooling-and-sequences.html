Pooling and byte sequences

parser فصل قبل کپی‌های غیرضروری را کم کرد؛ اما حالا برای هر بسته یک آرایهٔ بزرگ می‌سازیم و زود دور می‌اندازیم. آیا pool همیشه سریع‌تر است؟ نه. اگر buffer را پس ندهیم، اندازهٔ واقعی را اشتباه بگیریم یا پس از Return دوباره از آن استفاده کنیم، به جای بهبود، باگ می‌سازیم. این فصل را با اندازه‌گیری شروع می‌کنیم، نه با شعار «allocation صفر».

The previous parser reduced unnecessary copies, but now it creates and discards a large array for every packet. Is a pool always faster? No. Forgetting to return a buffer, confusing its rented length with the usable length, or using it after Return creates bugs instead of performance. We start with measurement, not a “zero allocations” slogan.

اول ببینیم تخصیص واقعاً مسئله استFirst establish whether allocation is a problem

یک آرایهٔ ۶۴ کیلوبایتی برای هر پیام کوچک، حتی اگر فقط ۷۰۰ بایت مصرف شود، ممکن است فشار غیرضروری روی GC بسازد. ولی pool کردن همه‌چیز هم هزینه دارد: bookkeeping، عمر طولانی‌تر buffer، رقابت میان threadها و خطر استفادهٔ پس از آزادسازی. قبل از تغییر، تعداد پیام، اندازهٔ تخصیص در هر عملیات، نرخ درخواست و latency را در workload واقعی اندازه بگیر؛ بعد نسخهٔ ساده را baseline نگه دار.

A 64-KB array per small message may create needless GC pressure when only 700 bytes are used. But pooling everything has costs too: bookkeeping, longer buffer lifetimes, contention and use-after-return bugs. Measure allocation per operation, message rate and latency under representative load before changing anything; keep the simple implementation as your baseline.

baseline / اندازه‌گیری اولیه
long before = GC.GetAllocatedBytesForCurrentThread();
for (int i = 0; i < 10_000; i++)
    ParsePacket(packet);
long allocated = GC.GetAllocatedBytesForCurrentThread() - before;
Console.WriteLine($"Allocated: {allocated:N0} bytes");

این شمارنده فقط allocationهای managed همین thread را در این بازه می‌سنجد؛ حافظهٔ native، threadهای دیگر و latency را پوشش نمی‌دهد. برای مقایسهٔ قابل اتکا از BenchmarkDotNet و workload گرم‌شده استفاده کن؛ benchmark کوچک، جای پایش رفتار سرویس در محیط واقعی نیست.

This counter measures managed allocations on the current thread only; it does not cover native memory, other threads or latency. Use BenchmarkDotNet with a warmed-up workload for a reliable comparison; a microbenchmark does not replace observing the service in production.

ArrayPool اجاره می‌دهد؛ مالک دائمی نمی‌دهدArrayPool lends a buffer; it does not give you permanent ownership

Rent(minimumLength) آرایه‌ای با طول حداقل خواسته‌شده می‌دهد؛ ممکن است آرایه بزرگ‌تر و حاوی دادهٔ قبلی باشد. فقط همان محدوده‌ای را بخوان که خودت پر کرده‌ای، نه کل array.Length. پس از پایان، دقیقاً همان آرایه را به همان pool برگردان. buffer اجاره‌ای را در property، cache یا callback بلندمدت نگه ندار؛ قراردادش اجارهٔ کوتاه و مالکیت روشن است.

Rent(minimumLength) returns an array at least as large as requested; it may be larger and may contain previous data. Read only the region you initialized, not the entire array.Length. Return the same array to the same pool when finished. Do not keep a rented buffer in a long-lived property, cache or callback: the contract is a short loan with explicit ownership.

اجاره و بازگرداندن امن / Rent and return
using System.Buffers;

byte[] rented = ArrayPool<byte>.Shared.Rent(4096);
try
{
    int written = await stream.ReadAsync(rented.AsMemory(0, 4096), ct);
    Process(rented.AsSpan(0, written));
}
finally
{
    ArrayPool<byte>.Shared.Return(rented, clearArray: true);
}

بازگرداندن در finally حتی با exception یا cancellation انجام می‌شود. clearArray: true می‌تواند پیش از reuse داده را پاک کند، اما هزینه دارد؛ برای دادهٔ حساس سیاست پاک‌سازی را آگاهانه انتخاب کن و فرض نکن pool به‌طور پیش‌فرض آرایه را صفر می‌کند. هیچ reference یا Span ساخته‌شده از آرایه را پس از Return استفاده نکن.

Returning in finally also works after exceptions or cancellation. clearArray: true can clear data before reuse, at a cost; choose a clearing policy deliberately for sensitive data and never assume the pool zeroes arrays by default. Do not use any reference or Span derived from the array after Return.

ظرفیت اجاره‌ای با طول معتبر یکی نیستRented capacity is not the valid data length

اگر برای ۴۰۹۶ بایت Rent کردی ولی فقط ۱۲۰۰ بایت خوانده‌ای، طول داده ۱۲۰۰ است؛ بقیه ممکن است دادهٔ قدیمی باشد. طول معتبر را جدا نگه دار و به parser، serializer یا شبکه فقط همان بخش را بده. هیچ‌وقت با طول کل آرایه پاسخ HTTP نساز یا کل buffer را بنویس؛ هم خروجی خراب می‌شود، هم احتمال افشای دادهٔ قبلی وجود دارد.

If you rented 4096 bytes but read only 1200, the valid data length is 1200; the rest may contain stale data. Track the valid length separately and pass only that region to parsers, serializers or the network. Never build an HTTP response or write the full array just because that is its length: output may be corrupted and old data may leak.

طول داده، نه ظرفیت / Data length, not capacity
int count = await stream.ReadAsync(rented.AsMemory(0, requested), ct);
ReadOnlySpan<byte> valid = rented.AsSpan(0, count);
Parse(valid);

طول صفر هم حالت معتبر است. برای stream ممکن است یک Read همهٔ دادهٔ درخواستی را نخواند؛ تا تکمیل frame یا رسیدن به پایان/timeout، خواندن را طبق protocol ادامه بده. pooling جای طراحی framing را نمی‌گیرد.

A zero length is valid too. A stream read may return fewer bytes than requested; continue according to the protocol until the frame is complete or an end/timeout condition occurs. Pooling does not replace framing design.

وقتی buffer باید از یک متد بیرون برود، مالکیت را منتقل کنWhen a buffer outlives a method, transfer ownership explicitly

ArrayPool برای bufferهای موقت synchronous یا یک scope روشن خوب است. اگر داده باید از یک API بیرون برود یا async boundary را رد کند، lifetime را با Memory<T> نمایش بده و در صورت نیاز به مالکیت قابل Dispose از IMemoryOwner<T> استفاده کن. دارندهٔ owner مسئول Dispose است؛ پیش از آن هیچ consumer فعالی نباید حافظه را نگه داشته باشد. owner را یا مصرف می‌کنی و Dispose می‌کنی، یا مالکیتش را منتقل می‌کنی—هر دو با هم نه.

ArrayPool suits temporary buffers within a clear scope. If data must leave an API or cross an async boundary, represent its lifetime with Memory<T> and use IMemoryOwner<T> when disposable ownership is needed. The owner is responsible for Dispose; no active consumer may keep using the memory afterward. Either consume and dispose the owner or transfer ownership—never both.

مالکیت با MemoryPool / Ownership with MemoryPool
using IMemoryOwner<byte> owner = MemoryPool<byte>.Shared.Rent(2048);
Memory<byte> memory = owner.Memory[..2048];
int count = await stream.ReadAsync(memory, ct);
await ProcessAsync(memory[..count], ct);
// owner is disposed here, after the consumer is finished.

در API واقعی اگر اندازهٔ اجاره‌شده از خواسته بیشتر است، طول معتبر را جداگانه نگه دار. واگذاری Memory<T> به task یا callbackی که بعد از Dispose اجرا می‌شود، use-after-dispose است. مالکیت را در امضای API و مستندات روشن کن؛ اسم Memory به‌تنهایی مالک را مشخص نمی‌کند.

In real APIs, track valid length separately if the rented region is larger than requested. Passing Memory to a task or callback that runs after Dispose is a use-after-dispose bug. Make ownership clear in the API contract and documentation; the type name Memory alone does not identify its owner.

دادهٔ شبکه همیشه یک تکه نیستNetwork data is not always one contiguous block

بعضی APIهای شبکه داده را در چند segment می‌دهند. جمع‌کردن همه در یک آرایه یعنی allocation و copy اضافه؛ ReadOnlySequence<T> می‌تواند چند بخش را به شکل یک دنبالهٔ منطقی نمایش دهد. برای خواندن protocol از SequenceReader<T> استفاده کن تا مرز segment را خودت مدیریت نکنی. بااین‌حال sequence هم مالک حافظه نیست و عمر آن به bufferهای underlying وابسته است.

Some networking APIs provide data in multiple segments. Concatenating them into one array adds allocation and copying; ReadOnlySequence<T> can represent multiple segments as one logical sequence. SequenceReader<T> helps parse protocols without manually managing segment boundaries. A sequence still does not own memory; its lifetime depends on the underlying buffers.

خواندن از sequence / Reading a sequence
var reader = new SequenceReader<byte>(sequence);
if (!reader.TryReadTo(out ReadOnlySequence<byte> header, (byte)'\n'))
{
    // The complete header has not arrived yet.
    return NeedMoreData;
}

foreach (ReadOnlyMemory<byte> segment in header)
    Consume(segment.Span);

ممکن است delimiter بین segmentها باشد؛ به همین دلیل جست‌وجوی دستی در segment اول کافی نیست. اگر ورودی ناقص است، state parser و بخش مصرف‌شده را نگه دار، نه اینکه بی‌قید همه‌چیز را کپی کنی. در مقابل، برای پیام کوچک و مسیر کم‌ترافیک، یک کپی ساده گاهی ارزان‌تر و قابل‌فهم‌تر از abstraction پیچیده است.

A delimiter may cross segment boundaries, which is why searching only the first segment is insufficient. For incomplete input, retain parser state and consumed position rather than copying everything blindly. Conversely, for small messages and low-throughput paths, one simple copy may be cheaper and clearer than a complex abstraction.

۱) چرا pool؟1) Why pool?

سرویسی می‌گوید ArrayPool حتماً سریع‌تر است. چه baselineی لازم داری؟

A service claims ArrayPool must be faster. What baseline do you need?

راهنمای فنیTechnical hint

allocation/operation، latency و throughput را در workload مشابه با benchmark گرم‌شده مقایسه کن.

Compare allocation per operation, latency and throughput under a warmed-up representative benchmark.

۲) طول بیشتر از درخواست2) Longer than requested

Rent(1000) آرایه‌ای با طول 1024 داد. آیا 1024 بایت ورودی معتبر داری؟

Rent(1000) returned an array of length 1024. Do you have 1024 valid input bytes?

راهنمای فنیTechnical hint

خیر؛ طول buffer ظرفیت است. فقط تعداد بایت‌هایی که واقعاً نوشته/خوانده‌ای معتبرند.

No; array length is capacity. Only bytes actually written or read are valid.

۳) Return پس از exception3) Return after an exception

Process ممکن است exception بدهد؛ مسیر بازگرداندن آرایه را کامل کن.

Process may throw; complete the buffer-return path.

راهنمای فنیTechnical hint

استفاده را در try و Return را در finally قرار بده.

Put use in try and Return in finally.

۴) استفاده پس از Return4) Use after Return

Span را ساخته‌ای، آرایه را Return کرده‌ای و سپس Span را می‌خوانی. مشکل را توضیح بده.

You created a Span, returned its array, then read the Span. Explain the bug.

راهنمای فنیTechnical hint

pool ممکن است همان آرایه را به caller دیگری بدهد؛ همهٔ viewها پس از Return نامعتبرند.

The pool may lend the array to another caller; all views are invalid after Return.

۵) دادهٔ حساس5) Sensitive data

buffer شامل token بوده؛ چه سیاستی برای پاک‌سازی می‌گذاری و چه هزینه‌ای دارد؟

The buffer held a token. What clearing policy will you choose, and what does it cost?

راهنمای فنیTechnical hint

بر اساس threat model از Return(clearArray:true) یا پاک‌سازی محدودهٔ معتبر استفاده کن؛ هزینه را بسنج و به صفرشدن پیش‌فرض pool تکیه نکن.

Choose Return(clearArray: true) or clear the valid region according to the threat model; measure the cost and do not assume the pool clears by default.

۶) read کوتاه6) Short read

ReadAsync برای 4096 درخواست، 300 بایت برگردانده؛ چند بایت را parse می‌کنی؟

ReadAsync requested 4096 bytes and returned 300. How many bytes do you parse?

راهنمای فنیTechnical hint

همان 300 بایت؛ protocol ممکن است خواندن‌های بیشتری لازم داشته باشد.

Only 300; the protocol may require additional reads.

۷) owner فراموش‌شده7) Forgotten owner

MemoryPool.Rent را صدا می‌زنی اما owner Dispose نمی‌شود. پیامد را پیدا کن.

You call MemoryPool.Rent but never dispose the owner. Identify the consequence.

راهنمای فنیTechnical hint

منبع ممکن است آزاد یا به pool برنگردد؛ از using/Dispose یا انتقال مستند مالکیت استفاده کن.

The resource may not be released or returned; use using/Dispose or a documented ownership transfer.

۸) دو owner8) Two owners

دو component هر دو فکر می‌کنند مسئول Dispose یک owner هستند. contract را اصلاح کن.

Two components both believe they must dispose an owner. Fix the contract.

راهنمای فنیTechnical hint

یک owner تعیین کن؛ هنگام transfer، فرستنده دیگر از حافظه استفاده و آن را Dispose نکند.

Define one owner; after transfer, the sender must neither use nor dispose the memory.

۹) خروجی بلندمدت9) Long-lived output

می‌خواهی یک آرایهٔ اجاره‌ای را در cache یک‌ساعته نگه داری. جایگزین امن‌تری طراحی کن.

You want to keep a rented array in a one-hour cache. Design a safer alternative.

راهنمای فنیTechnical hint

مالکیت مستقل و عمر مشخص ایجاد کن؛ یا دادهٔ لازم را کپی کن. تا وقتی cache مصرف می‌کند Return نکن.

Give the data independent ownership and a defined lifetime, or copy the required data. Do not return it while the cache uses it.

۱۰) sequence چندبخشی10) Segmented sequence

delimiter آخر segment صفر و اولین بایت segment یک است. چرا parser ساده شکست می‌خورد؟

A delimiter ends segment zero and the next byte begins segment one. Why does a simple parser fail?

راهنمای فنیTechnical hint

فرض contiguous بودن غلط است؛ SequenceReader یا parserی با state بین segmentها استفاده کن.

The contiguous assumption is wrong; use SequenceReader or a parser that preserves state across segments.

۱۱) Sequence مالک نیست11) A sequence is not an owner

ReadOnlySequence از memory متعلق به pool ساخته شده. آیا می‌توانی بعد از Dispose owner آن را مصرف کنی؟

A ReadOnlySequence refers to pooled memory. Can you consume it after disposing its owner?

راهنمای فنیTechnical hint

نه؛ sequence فقط view است و عمرش به backing memory وابسته است.

No; the sequence is only a view, and its lifetime depends on the backing memory.

۱۲) آلودگی پاسخ12) Leaking stale bytes

پاسخ شبکه شامل بایت‌هایی بیشتر از payload تازه است؛ علت محتمل و اصلاح را بنویس.

A network response contains bytes beyond the new payload. Give a likely cause and fix.

راهنمای فنیTechnical hint

طول کل آرایه به‌جای طول معتبر استفاده شده؛ فقط slice طول معتبر را serialize/write کن.

The full array length was used instead of valid length; serialize/write only the valid slice.

۱۳) allocation کمتر، latency بدتر13) Fewer allocations, worse latency

benchmark allocation را کم نشان می‌دهد ولی p99 بدتر شده؛ pooling را قبول می‌کنی؟

Allocation falls in a benchmark but p99 latency worsens. Do you accept pooling?

راهنمای فنیTechnical hint

نه تا علت contention، clearing و tail latency بررسی شود؛ معیار محصول را با load نماینده ارزیابی کن.

Not until contention, clearing and tail latency are understood; evaluate product goals under representative load.

۱۴) گزارش incident بافر14) Buffer incident report

یک باگ use-after-return و یک نشت مالکیت را با symptom، evidence، root cause و verification ثبت کن.

Document a use-after-return bug and an ownership leak with symptom, evidence, root cause and verification.

راهنمای فنیTechnical hint

از تست تکرارشونده و ownership timeline استفاده کن؛ بعد از اصلاح، مسیر exception و cancellation را هم اجرا کن.

Use a repeatable test and ownership timeline; after fixing, exercise exception and cancellation paths too.

آزمایشگاه: parser با buffer قرضیLab: a parser using rented buffers

یک برنامهٔ کوچک بساز که frameهای طول‌دار را از stream می‌خواند و جدا می‌کند. ابتدا نسخهٔ ساده با آرایهٔ تازه را پیاده کن و allocation و latency را ثبت کن. سپس با ArrayPool buffer موقت بگیر، readهای کوتاه و frame ناقص را درست مدیریت کن و فقط محدودهٔ معتبر را parse کن. exception و cancellation را وسط خواندن تزریق کن و ثابت کن buffer در همهٔ مسیرها Return می‌شود. بعد یک نسخهٔ مبتنی بر MemoryPool بساز که owner تا پایان پردازش زنده بماند؛ عمداً زود Dispose کن و خطای lifetime را در تست شناسایی کن. اگر ورودی را به segmentهای جدا تقسیم می‌کنی، delimiter میان دو segment را نیز بیازمای. آخر سر هر سه نسخه را در BenchmarkDotNet بسنج و فقط اگر gain قابل‌توجه و قابل‌تکرار است، نسخهٔ pooled را نگه دار.

Build a small program that reads and extracts length-prefixed frames from a stream. First implement a straightforward fresh-array version and record allocations and latency. Then rent a temporary ArrayPool buffer, handle short reads and incomplete frames correctly, and parse only the valid region. Inject exceptions and cancellation during reads and prove the buffer is returned on every path. Next create a MemoryPool version whose owner remains alive through processing; deliberately dispose too early and detect the lifetime bug in a test. If input is segmented, test a delimiter crossing segment boundaries. Finally compare all versions with BenchmarkDotNet and keep pooling only if its gain is meaningful and repeatable.

  1. برای هر frame خروجی با نسخهٔ ساده byte-for-byte برابر باشد.
  2. Each frame must match the simple implementation byte for byte.
  3. exception و cancellation نباید buffer اجاره‌ای را بدون Return باقی بگذارد.
  4. Exceptions and cancellation must not leak a rented buffer.
  5. اندازه‌گیری شامل throughput، latency و allocation باشد.
  6. Measurements must include throughput, latency and allocation.

pooling یک قرارداد مالکیت است، نه تزئین سرعتPooling is an ownership contract, not a speed decoration

ArrayPool هزینهٔ ساخت مکرر را شاید کم کند، اما buffer بزرگ‌تر از درخواست، صفرنشده و فقط تا Return در اختیار توست. MemoryPool برای lifetimeهای صریح‌تر مناسب است، به شرط آن‌که owner درست Dispose یا منتقل شود. Sequence چند segment را به شکل یک ورودی منطقی می‌خواند، اما حافظه را مالک نمی‌شود. پس baseline را نگه دار، اندازه بگیر و فقط آن‌جا پیچیدگی اضافه کن که عدد و contract هر دو از آن دفاع کنند. فصل بعد از بافر به GC می‌رسیم: چرا بعضی حافظه‌ها زود آزاد نمی‌شوند و چه چیزی واقعاً فشار ایجاد می‌کند.

ArrayPool may reduce repeated allocation, but a buffer can exceed the requested size, is not guaranteed cleared and is yours only until Return. MemoryPool helps express longer lifetimes when its owner is disposed or transferred correctly. A sequence presents multiple segments as one logical input but does not own their memory. Keep a baseline, measure, and add complexity only where both the numbers and ownership contract justify it.
