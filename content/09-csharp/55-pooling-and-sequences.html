pooling و دنبالهٔ بایت

Pooling and byte sequences

parser فصل قبل کپی‌های غیرضروری رو کم کرد؛ اما حالا برای هر بسته یک آرایهٔ بزرگ می‌سازیم و زود دور می‌اندازیم. آیا pool همیشه سریع‌تر هست؟ نه. اگه buffer رو پس ندهیم، اندازهٔ واقعی رو اشتباه بگیریم یا پس از Return دوباره از آن استفاده کنیم، به جای بهبود، باگ می‌سازیم. این فصل رو با اندازه‌گیری شروع می‌کنیم، نه با شعار «allocation صفر».

The previous parser reduced unnecessary copies, but now it creates and discards a large array for every packet. Is a pool always faster? No. Forgetting to return a buffer, confusing its rented length with the usable length, or using it after Return creates bugs instead of performance. We start with measurement, not a “zero allocations” slogan.

اول ببینیم تخصیص واقعاً مسئله استFirst establish whether allocation is a problem

یک آرایهٔ ۶۴ کیلوبایتی برای هر پیام کوچک، حتی اگه فقط ۷۰۰ بایت مصرف بشه، ممکنه فشار غیرضروری روی GC بسازد. ولی pool کردن همه‌چیز هم هزینه داره: bookkeeping، عمر طولانی‌تر buffer، رقابت میان threadها و خطر استفادهٔ پس از آزادسازی. قبل از تغییر، تعداد پیام، اندازهٔ تخصیص در هر عملیات، نرخ درخواست و latency رو در workload واقعی اندازه بگیر؛ بعد نسخهٔ ساده رو baseline نگه دار.

A 64-KB array per small message may create needless GC pressure when only 700 bytes are used. But pooling everything has costs too: bookkeeping, longer buffer lifetimes, contention and use-after-return bugs. Measure allocation per operation, message rate and latency under representative load before changing anything; keep the simple implementation as your baseline.

baseline / اندازه‌گیری اولیه
long before = GC.GetAllocatedBytesForCurrentThread();
for (int i = 0; i < 10_000; i++)
    ParsePacket(packet);
long allocated = GC.GetAllocatedBytesForCurrentThread() - before;
Console.WriteLine($"Allocated: {allocated:N0} bytes");

این شمارنده فقط allocationهای managed همین thread رو در این بازه می‌سنجد؛ حافظهٔ native، threadهای دیگر و latency رو پوشش نمی‌ده. برای مقایسهٔ قابل اتکا از BenchmarkDotNet و workload گرم‌شده استفاده کن؛ benchmark کوچک، جای پایش رفتار سرویس در محیط واقعی نیست.

This counter measures managed allocations on the current thread only; it does not cover native memory, other threads or latency. Use BenchmarkDotNet with a warmed-up workload for a reliable comparison; a microbenchmark does not replace observing the service in production.

ArrayPool اجاره می‌ده؛ مالک دائمی نمی‌دهArrayPool lends a buffer; it does not give you permanent ownership

Rent(minimumLength) آرایه‌ای با طول حداقل خواسته‌شده می‌ده؛ ممکنه آرایه بزرگ‌تر و حاوی دادهٔ قبلی باشه. فقط همان محدوده‌ای رو بخوان که خودت پر کرده‌ای، نه کل array.Length. پس از پایان، دقیقاً همان آرایه رو به همان pool برگردان. buffer اجاره‌ای رو در property، cache یا callback بلندمدت نگه ندار؛ قراردادش اجارهٔ کوتاه و مالکیت روشن هست.

Rent(minimumLength) returns an array at least as large as requested; it may be larger and may contain previous data. Read only the region you initialized, not the entire array.Length. Return the same array to the same pool when finished. Do not keep a rented buffer in a long-lived property, cache or callback: the contract is a short loan with explicit ownership.

اجاره و بازگرداندن امن / Rent and return
using System.Buffers;

byte[] rented = ArrayPool<byte>.Shared.Rent(4096);
try
{
    int written = await stream.ReadAsync(rented.AsMemory(0, 4096), ct);
    Process(rented.AsSpan(0, written));
}
finally
{
    ArrayPool<byte>.Shared.Return(rented, clearArray: true);
}

بازگرداندن در finally حتی با exception یا cancellation انجام می‌شه. clearArray: true می‌تونه پیش از reuse داده رو پاک کند، اما هزینه داره؛ برای دادهٔ حساس سیاست پاک‌سازی رو آگاهانه انتخاب کن و فرض نکن pool به‌طور پیش‌فرض آرایه رو صفر می‌کنه. هیچ reference یا Span ساخته‌شده از آرایه رو پس از Return استفاده نکن.

Returning in finally also works after exceptions or cancellation. clearArray: true can clear data before reuse, at a cost; choose a clearing policy deliberately for sensitive data and never assume the pool zeroes arrays by default. Do not use any reference or Span derived from the array after Return.

ظرفیت اجاره‌ای با طول معتبر یکی نیستRented capacity is not the valid data length

اگه برای ۴۰۹۶ بایت Rent کردی ولی فقط ۱۲۰۰ بایت خوانده‌ای، طول داده ۱۲۰۰ هست؛ بقیه ممکنه دادهٔ قدیمی باشه. طول معتبر رو جدا نگه دار و به parser، serializer یا شبکه فقط همان بخش رو بده. هیچ‌وقت با طول کل آرایه پاسخ HTTP نساز یا کل buffer رو بنویس؛ هم خروجی خراب می‌شه، هم احتمال افشای دادهٔ قبلی وجود داره.

If you rented 4096 bytes but read only 1200, the valid data length is 1200; the rest may contain stale data. Track the valid length separately and pass only that region to parsers, serializers or the network. Never build an HTTP response or write the full array just because that is its length: output may be corrupted and old data may leak.

طول داده، نه ظرفیت / Data length, not capacity
int count = await stream.ReadAsync(rented.AsMemory(0, requested), ct);
ReadOnlySpan<byte> valid = rented.AsSpan(0, count);
Parse(valid);

طول صفر هم حالت معتبر هست. برای stream ممکنه یک Read همهٔ دادهٔ درخواستی رو نخواند؛ تا تکمیل frame یا رسیدن به پایان/timeout، خواندن رو طبق protocol ادامه بده. pooling جای طراحی framing رو نمی‌گیره.

A zero length is valid too. A stream read may return fewer bytes than requested; continue according to the protocol until the frame is complete or an end/timeout condition occurs. Pooling does not replace framing design.

وقتی buffer باید از یک متد بیرون برود، مالکیت رو منتقل کنWhen a buffer outlives a method, transfer ownership explicitly

ArrayPool برای bufferهای موقت synchronous یا یک scope روشن خوب هست. اگه داده باید از یک API بیرون برود یا async boundary رو رد کند، lifetime رو با Memory<T> نمایش بده و در صورت نیاز به مالکیت قابل Dispose از IMemoryOwner<T> استفاده کن. دارنهٔ owner مسئول Dispose هست؛ پیش از آن هیچ consumer فعالی نباید حافظه رو نگه داشته باشه. owner رو یا مصرف می‌کنی و Dispose می‌کنی، یا مالکیتش رو منتقل می‌کنی—هر دو با هم نه.

ArrayPool suits temporary buffers within a clear scope. If data must leave an API or cross an async boundary, represent its lifetime with Memory<T> and use IMemoryOwner<T> when disposable ownership is needed. The owner is responsible for Dispose; no active consumer may keep using the memory afterward. Either consume and dispose the owner or transfer ownership—never both.

مالکیت با MemoryPool / Ownership with MemoryPool
using IMemoryOwner<byte> owner = MemoryPool<byte>.Shared.Rent(2048);
Memory<byte> memory = owner.Memory[..2048];
int count = await stream.ReadAsync(memory, ct);
await ProcessAsync(memory[..count], ct);
// owner is disposed here, after the consumer is finished.

در API واقعی اگه اندازهٔ اجاره‌شده از خواسته بیشتر هست، طول معتبر رو جداگانه نگه دار. واگذاری Memory<T> به task یا callbackی که بعد از Dispose اجرا می‌شه، use-after-dispose هست. مالکیت رو در امضای API و مستندات روشن کن؛ اسم Memory به‌تنهایی مالک رو مشخص نمی‌کنه.

In real APIs, track valid length separately if the rented region is larger than requested. Passing Memory to a task or callback that runs after Dispose is a use-after-dispose bug. Make ownership clear in the API contract and documentation; the type name Memory alone does not identify its owner.

دادهٔ شبکه همیشه یک تکه نیستNetwork data is not always one contiguous block

بعضی APIهای شبکه داده رو در چند segment می‌دن. جمع‌کردن همه در یک آرایه یعنی allocation و copy اضافه؛ ReadOnlySequence<T> می‌تونه چند بخش رو به شکل یک دنبالهٔ منطقی نمایش دهد. برای خواندن protocol از SequenceReader<T> استفاده کن تا مرز segment رو خودت مدیریت نکنی. بااین‌حال sequence هم مالک حافظه نیست و عمر آن به bufferهای underlying وابسته هست.

Some networking APIs provide data in multiple segments. Concatenating them into one array adds allocation and copying; ReadOnlySequence<T> can represent multiple segments as one logical sequence. SequenceReader<T> helps parse protocols without manually managing segment boundaries. A sequence still does not own memory; its lifetime depends on the underlying buffers.

خواندن از sequence / Reading a sequence
var reader = new SequenceReader<byte>(sequence);
if (!reader.TryReadTo(out ReadOnlySequence<byte> header, (byte)'\n'))
{
    // The complete header has not arrived yet.
    return NeedMoreData;
}

foreach (ReadOnlyMemory<byte> segment in header)
    Consume(segment.Span);

ممکنه delimiter بین segmentها باشه؛ به همین دلیل جست‌وجوی دستی در segment اول کافی نیست. اگه ورودی ناقص هست، state parser و بخش مصرف‌شده رو نگه دار، نه اینکه بی‌قید همه‌چیز رو کپی کنی. در مقابل، برای پیام کوچک و مسیر کم‌ترافیک، یک کپی ساده گاهی ارزان‌تر و قابل‌فهم‌تر از abstraction پیچیده هست.

A delimiter may cross segment boundaries, which is why searching only the first segment is insufficient. For incomplete input, retain parser state and consumed position rather than copying everything blindly. Conversely, for small messages and low-throughput paths, one simple copy may be cheaper and clearer than a complex abstraction.

قاعدهٔ تصمیم: اول correctness و سادگی، بعد benchmark نماینده، سپس تغییر محدود و اندازه‌گیری مجدد. اگه gain معنی‌دار نیست، کد ساده رو نگه دار. «بدون کپی» هدف مستقل نیست؛ هدف latency و مصرف منابع قابل قبول با contract قابل‌فهم هست.

آزمایشگاه: parser با buffer قرضیLab: a parser using rented buffers

یک برنامهٔ کوچک بساز که frameهای طول‌دار رو از stream می‌خونه و جدا می‌کنه. ابتدا نسخهٔ ساده با آرایهٔ تازه رو پیاده کن و allocation و latency رو ثبت کن. سپس با ArrayPool buffer موقت بگیر، readهای کوتاه و frame ناقص رو درست مدیریت کن و فقط محدودهٔ معتبر رو parse کن. exception و cancellation رو وسط خواندن تزریق کن و ثابت کن buffer در همهٔ مسیرها Return می‌شه. بعد یک نسخهٔ مبتنی بر MemoryPool بساز که owner تا پایان پردازش زنده بماند؛ عمداً زود Dispose کن و خطای lifetime رو در تست شناسایی کن. اگه ورودی رو به segmentهای جدا تقسیم می‌کنی، delimiter میان دو segment رو نیز بیازمای. آخر سر هر سه نسخه رو در BenchmarkDotNet بسنج و فقط اگه gain قابل‌توجه و قابل‌تکرار هست، نسخهٔ pooled رو نگه دار.

Build a small program that reads and extracts length-prefixed frames from a stream. First implement a straightforward fresh-array version and record allocations and latency. Then rent a temporary ArrayPool buffer, handle short reads and incomplete frames correctly, and parse only the valid region. Inject exceptions and cancellation during reads and prove the buffer is returned on every path. Next create a MemoryPool version whose owner remains alive through processing; deliberately dispose too early and detect the lifetime bug in a test. If input is segmented, test a delimiter crossing segment boundaries. Finally compare all versions with BenchmarkDotNet and keep pooling only if its gain is meaningful and repeatable.

  1. برای هر frame خروجی با نسخهٔ ساده byte-for-byte برابر باشه.
  2. Each frame must match the simple implementation byte for byte.
  3. exception و cancellation نباید buffer اجاره‌ای رو بدون Return باقی بگذارد.
  4. Exceptions and cancellation must not leak a rented buffer.
  5. اندازه‌گیری شامل throughput، latency و allocation باشه.
  6. Measurements must include throughput, latency and allocation.

pooling یک قرارداد مالکیت هست، نه تزئین سرعتPooling is an ownership contract, not a speed decoration

ArrayPool هزینهٔ ساخت مکرر رو شاید کم کند، اما buffer بزرگ‌تر از درخواست، صفرنشده و فقط تا Return در اختیار توست. MemoryPool برای lifetimeهای صریح‌تر مناسب هست، به شرط آن‌که owner درست Dispose یا منتقل بشه. Sequence چند segment رو به شکل یک ورودی منطقی می‌خونه، اما حافظه رو مالک نمی‌شه. پس baseline رو نگه دار، اندازه بگیر و فقط آن‌جا پیچیدگی اضافه کن که عدد و contract هر دو از آن دفاع کنند. فصل بعد از بافر به GC می‌رسیم: چرا بعضی حافظه‌ها زود آزاد نمی‌شن و چه چیزی واقعاً فشار ایجاد می‌کنه.

ArrayPool may reduce repeated allocation, but a buffer can exceed the requested size, is not guaranteed cleared and is yours only until Return. MemoryPool helps express longer lifetimes when its owner is disposed or transferred correctly. A sequence presents multiple segments as one logical input but does not own their memory. Keep a baseline, measure, and add complexity only where both the numbers and ownership contract justify it. Next we move from buffers to GC: why some memory remains alive and what actually creates pressure.
