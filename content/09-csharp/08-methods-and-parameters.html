متدها و پارامترها

Methods and parameters

در فصل قبل، تصمیم‌های یک سفارش را روشن کردیم. حالا اگر محاسبهٔ تخفیف، کنترل موجودی و ساخت پیام را وسط حلقهٔ اصلی بنویسیم، تغییر هرکدام بقیه را هم به‌هم می‌ریزد. متد کمک می‌کند یک کار را با ورودی و خروجی معلوم جدا کنیم؛ نه اینکه فقط کد را به چند تکه تقسیم کنیم.

In the previous chapter we made order decisions explicit. If discount calculation, stock checks and message creation all live in the main flow, changing one can disturb the others. A method isolates one job behind clear inputs and outputs—not merely a way to split text into chunks.

اول یک کار واقعی را نام‌گذاری کنیمGive one real job a name

قیمت نهایی سفارش یک قاعده دارد: جمع ردیف‌ها منهای تخفیف. اگر همان فرمول را در سه جای برنامه کپی کنیم، روزی که قانون عوض شود احتمالاً فقط دو نسخه را اصلاح می‌کنیم. یک متد واحد، قانون را یک‌جا نگه می‌دارد.

An order total follows a rule: sum the lines, then subtract the discount. If we copy that formula into three places, a future rule change may update only two copies. One method keeps the rule in one place.

C# · Program.cs
decimal CalculatePayable(decimal subtotal, decimal discount)
{
    return subtotal - discount;
}

decimal payable = CalculatePayable(120m, 15m);
Console.WriteLine(payable); // 105

`decimal` برای مبلغ نمونهٔ مناسبی است؛ `return` نتیجه را به فراخواننده برمی‌گرداند و متد پس از آن تمام می‌شود. این امضا می‌گوید دو مقدار decimal می‌گیرد و یک decimal پس می‌دهد. چون این کد در سطح بالای فایل است، متد محلی top-level program محسوب می‌شود؛ بعدتر همین شکل را داخل کلاس هم می‌بینیم.

`decimal` is a suitable choice for this money example. `return` sends the result to the caller and ends the method. The signature says it accepts two decimals and returns one. At the top level this is a local function in a top-level program; we will also use methods inside classes later.

قرارداد را قبل از بدنه بخوانRead the contract before the body

نام، نوع خروجی، نام و نوع پارامترها می‌گویند متد چه قولی می‌دهد. بدنه جزئیات اجرای آن قول است. متدی که فقط کار می‌کند اما نام مبهمی مثل `DoIt` دارد، برای نفر بعد قرارداد خوبی نیست.

The name, return type and parameter names and types describe the promise. The body implements it. A method that works but is named `DoIt` gives the next developer a poor contract.

نتیجه برمی‌گردانیم یا فقط کاری انجام می‌دهیم؟Return a value or perform an action?

گاهی caller به یک مقدار نیاز دارد؛ گاهی متد یک اثر جانبی انجام می‌دهد، مثل نوشتن گزارش. نوع `void` یعنی متد مقدار نتیجه‌ای برنمی‌گرداند؛ به معنی «هیچ کاری نمی‌کند» نیست.

Sometimes the caller needs a value; sometimes a method performs a side effect, such as writing a log. `void` means no result value is returned, not that nothing happens.

C#
decimal CalculateLineTotal(decimal unitPrice, int quantity)
{
    if (unitPrice < 0 || quantity < 0)
        throw new ArgumentOutOfRangeException();

    return unitPrice * quantity;
}

void PrintReceipt(string orderId, decimal total)
{
    Console.WriteLine($"{orderId}: {total:C}");
}

محاسبه خروجی می‌دهد تا caller بتواند آن را ذخیره یا آزمایش کند. چاپ رسید خروجی متنی دارد، اما آن را به محیط می‌فرستد؛ caller دیگر مقدار رسید را برای تصمیم بعدی در دست ندارد. اگر قرار است هم محاسبه کنیم و هم چاپ، جداسازی این دو معمولاً تست را ساده‌تر می‌کند.

The calculation returns a value so the caller can store or test it. Receipt printing emits text to the environment; the caller does not receive that text as a result for later decisions. Separating calculation from printing usually makes tests simpler.

مسئولیت متد را بیش از حد بزرگ نکنDo not overload a method with responsibilities

متدی که هم ورودی می‌خواند، هم قیمت را حساب می‌کند، هم فایل می‌نویسد و هم ایمیل می‌فرستد، چند دلیل متفاوت برای تغییر دارد. مرز خوب را از مسئله پیدا کن؛ نه با قانون خشک «هر متد فقط یک خط».

A method that reads input, calculates a price, writes a file and sends email has several independent reasons to change. Find boundaries in the problem; do not apply a rigid “one line per method” rule.

overload: یک نام، قراردادهای ورودی متفاوتOverloads: one name, different input contracts

اگر گاهی فقط شناسهٔ سفارش را داریم و گاهی شناسه به‌همراه ردیف‌ها، می‌توانیم دو overload داشته باشیم. کامپایلر با تعداد و نوع آرگومان‌ها تصمیم می‌گیرد کدام امضا را فراخوانی کند.

Sometimes we have only an order ID; sometimes the ID and its lines. Overloads let us offer two signatures under one name. The compiler selects one from the argument count and types.

C# · static class
static class Pricing
{
    public static decimal CalculatePayable(decimal subtotal) =>
        CalculatePayable(subtotal, 0m);

    public static decimal CalculatePayable(decimal subtotal, decimal discount)
    {
        if (discount < 0 || discount > subtotal)
            throw new ArgumentOutOfRangeException(nameof(discount));
        return subtotal - discount;
    }
}

Console.WriteLine(Pricing.CalculatePayable(120m)); // 120
Console.WriteLine(Pricing.CalculatePayable(120m, 15m)); // 105

این دو overload عضو یک type هستند؛ این شکل را در فایل Program.cs خودت بعد از top-level statements بگذار. overload اول قانون را دوباره پیاده نکرد؛ به overload دوم واگذار کرد. نام پارامتر به‌تنهایی امضای متفاوتی نمی‌سازد.

Both overloads belong to one type; in a top-level Program.cs, place this type after the top-level statements. The first overload delegates instead of duplicating the rule. Parameter names alone do not create a distinct signature.

اگر تبدیل‌های ضمنی چند overload را قابل‌استفاده کنند، فراخوانی می‌تواند مبهم شود و build خطا بدهد. نوع آرگومان را صریح کن یا امضاها را بازطراحی کن؛ حدس‌زدن overload انتخاب‌شده راه‌حل نیست.

If implicit conversions make multiple overloads applicable, a call may be ambiguous and fail to build. Make the argument type explicit or redesign the signatures.

آرگومان اختیاری، نام‌دار و تعداد متغیرOptional, named and variable-count arguments

وقتی یک پارامتر معمولاً مقدار پیش‌فرض مشخصی دارد، می‌توان آن را اختیاری کرد. آرگومان نام‌دار ترتیب را خواناتر می‌کند. `params` هم اجازه می‌دهد تعداد متغیری از ورودی‌های هم‌نوع را به شکل آرایه دریافت کنیم.

A parameter with a sensible default can be optional. Named arguments make intent clear regardless of position. `params` accepts a variable number of same-typed arguments as an array.

C#
string FormatReceipt(string orderId, string currency = "IRR", bool includeTax = true)
{
    return $"{orderId} · {currency} · tax={includeTax}";
}

Console.WriteLine(FormatReceipt("A-42", includeTax: false));

decimal SumLines(params decimal[] amounts)
{
    decimal total = 0m;
    foreach (decimal amount in amounts) total += amount;
    return total;
}

Console.WriteLine(SumLines(10m, 12.5m, 4m)); // 26.5

پارامترهای اختیاری بعد از پارامترهای اجباری می‌آیند؛ آرگومان نام‌دار کمک می‌کند از روی `false` حدس نزنیم کدام گزینه خاموش شده. `params` باید آخرین پارامتر باشد و در هر فراخوانی عملاً آرایه می‌سازد یا آرایهٔ آماده می‌گیرد. برای مجموعهٔ بزرگی از داده، این هزینه را با نیاز واقعی بسنج.

Optional parameters follow required ones. A named argument prevents us from guessing what `false` disables. `params` must be last and represents an array at the call boundary. For large data sets, consider that allocation and the actual API needs.

default بخشی از API استA default is part of the API

مقدار پیش‌فرض باید رفتار بی‌خطر و مورد انتظار بسازد. همچنین default پارامتر اختیاری در محل فراخوانی کامپایل می‌شود؛ پس تغییر default در کتابخانه، لزوماً رفتار برنامه‌ای را که قبلاً کامپایل شده عوض نمی‌کند. در API عمومی، نسخه‌پذیری را هم در نظر بگیر.

A default should be safe and unsurprising. Optional defaults are compiled into the caller, so changing a library default does not necessarily change already-compiled callers. Consider compatibility for public APIs.

ref، out و in: وقتی انتقال معمولی کافی نیستref, out and in: when ordinary passing is not enough

در حالت معمول، مقدار آرگومان به پارامتر می‌رسد. برای نوع مقداری، این یعنی یک کپی؛ برای متغیر reference type، مقدار reference کپی می‌شود و هنوز به همان شیء اشاره می‌کند. این دو را با «همه‌چیز کپی است» یا «همه‌چیز reference است» قاطی نکن.

Normally the argument value is passed to the parameter. For a value type, that means a copy; for a reference-type variable, the reference value is copied and still points to the same object. Avoid the myths that “everything is copied” or “everything is a reference.”

شکلFormقرارداد مهمKey contract
refrefcaller باید متغیر مقداردهی‌شده بدهد؛ متد می‌تواند همان متغیر را بخواند و تغییر دهد.Caller supplies an initialized variable; the method may read and change that variable.
outoutcaller لازم نیست پیش از فراخوانی مقدار بدهد؛ متد باید پیش از خروج همهٔ مسیرها را مقداردهی کند.Caller need not initialize it; the method must assign it on every return path.

C#
bool TryParseQuantity(string text, out int quantity)
{
    return int.TryParse(text, out quantity);
}

if (TryParseQuantity("12", out int quantity))
    Console.WriteLine(quantity); // 12

void ApplyDiscount(ref decimal total, decimal discount)
{
    total -= discount;
}

decimal total = 100m;
ApplyDiscount(ref total, 10m);
Console.WriteLine(total); // 90

`TryParse` الگوی `out` را نشان می‌دهد: مقدار موفقیت را جدا از خروجی می‌دهد. متد `ref` متغیر caller را عوض می‌کند؛ این قدرت اضافی، خواندن اثر متد را دشوارتر می‌کند. اگر یک خروجی معمولی یا یک نوع نتیجه کافی است، آن راه معمولاً شفاف‌تر است.

`TryParse` demonstrates `out`: success is separate from the parsed value. A `ref` method mutates the caller's variable, which makes effects harder to follow. If a normal return value or result object is enough, it is usually clearer.

C# · in
decimal CalculateTax(in decimal subtotal, in decimal rate)
{
    return subtotal * rate;
}

decimal tax = CalculateTax(100m, 0.09m);

`in` خواندن از پارامتر را مجاز می‌کند، نه نوشتن در آن. برای عددهای کوچک معمولاً لازم نیست از آن برای «سرعت» استفاده کنیم؛ اندازه‌گیری و نوع داده تعیین می‌کند این شکل فایده دارد یا فقط امضا را شلوغ می‌کند. `ref`، `out` و `in` هنگام فراخوانی هم باید در دو طرف قرارداد رعایت شوند.

`in` permits reading but not assigning through the parameter. For small values, do not add it speculatively for “speed”; measure and consider whether it clarifies or complicates the API. Calls and declarations must agree on `ref`, `out` and `in`.

تابع محلی و خروجی ref را فقط با دلیل انتخاب کنUse local functions and ref returns deliberately

تابع محلی وقتی مفید است که یک قاعده فقط در همان عملیات معنا دارد؛ مثل اعتبارسنجی شناسه در محاسبهٔ سفارش. بیرون‌بردن آن به API کلاس، اگر هیچ مصرف‌کنندهٔ دیگری ندارد، سطح عمومی بی‌دلیل می‌سازد.

A local function is useful when a rule belongs to one operation, such as validating an ID during order calculation. Moving it into a class API without another caller creates unnecessary surface area.

C#
decimal CalculateOrder(string orderId, decimal subtotal)
{
    ValidateId(orderId);
    return subtotal;

    static void ValidateId(string id)
    {
        if (string.IsNullOrWhiteSpace(id))
            throw new ArgumentException("شناسه لازم است", nameof(id));
    }
}

تابع محلی static به متغیرهای بیرونی دسترسی نمی‌گیرد؛ ورودی‌های لازم باید صریح به آن داده شوند. این محدودیت گاهی باگ capture ناخواسته را حذف می‌کند. جای تعریف تابع در انتهای بدنه مانع فراخوانی آن از خطوط بالاتر نیست.

A static local function cannot capture outer variables; required inputs must be passed explicitly. That restriction can prevent accidental captures. Defining it after the call does not prevent earlier lines from calling it.

تابع می‌تواند با `ref` به یک عضو آرایه برگردد؛ این نمونه همان خانه را تغییر می‌دهد، نه یک کپی را. آرایه باید هنوز زنده باشد و caller باید آگاهانه با `ref` دریافت کند. این قرارداد حساس را فقط وقتی لازم است انتخاب کن.

A method can return a reference to an array element; this example changes that slot rather than a copy. The array must remain alive, and the caller must explicitly receive by `ref`. Use this delicate contract only when needed.

C# · ref return
ref int Slot(int[] values, int index) => ref values[index];

int[] stock = [2, 5];
ref int firstBin = ref Slot(stock, 0);
firstBin = 8;
Console.WriteLine(stock[0]); // 8

مقدار برگشتی alias قابل‌نوشتن به عنصر آرایه است. ref return به متغیر local معمولی مجاز نیست، چون عمرش با پایان متد تمام می‌شود؛ compiler جلوی این escape را می‌گیرد. برای بیشتر APIهای روزمره، return معمولی خواناتر و امن‌تر است.

The result is a writable alias to an array element. Returning a reference to an ordinary local is forbidden because its lifetime ends with the method; the compiler prevents that escape. For most everyday APIs, a regular return is clearer and safer.

۱) مبلغ قابل پرداخت را جدا کن1) Extract the payable calculation

فرمول `subtotal - discount` را به متدی تبدیل کن که دو `decimal` بگیرد و نتیجه بدهد. با ۱۲۰ و ۱۵ اجرا کن.

Extract `subtotal - discount` into a method accepting two decimals and returning the result. Run it with 120 and 15.

پاسخ و دلیلSolution and reasoning
C#
decimal CalculatePayable(decimal subtotal, decimal discount)
{
    return subtotal - discount;
}

Console.WriteLine(CalculatePayable(120m, 15m)); // 105

نوع ورودی و خروجی یکسان است و فراخواننده نتیجهٔ ۱۰۵ را می‌گیرد. این نسخه هنوز ورودی منفی یا تخفیف بیشتر از subtotal را رد نمی‌کند؛ قرارداد اعتبارسنجی را باید با نیاز برنامه تعیین کرد.

Inputs and result share the decimal type and the caller receives 105. This version does not reject negative values or an excessive discount; validation belongs to the actual contract.

۲) مقدار مرزی را رد کن2) Reject an invalid boundary

به متد تمرین قبل شرطی اضافه کن که تخفیف منفی یا بزرگ‌تر از subtotal را با `ArgumentOutOfRangeException` رد کند. یک ورودی درست و دو ورودی غلط را اجرا کن.

Reject a negative discount or one greater than subtotal with `ArgumentOutOfRangeException`. Run one valid and two invalid inputs.

پاسخ و دلیلSolution and reasoning
C#
decimal CalculatePayable(decimal subtotal, decimal discount)
{
    if (subtotal < 0) throw new ArgumentOutOfRangeException(nameof(subtotal));
    if (discount < 0 || discount > subtotal)
        throw new ArgumentOutOfRangeException(nameof(discount));
    return subtotal - discount;
}

شرط‌ها نام پارامتر نادرست را در exception گزارش نمی‌کنند و قبل از خروج، ورودی نامعتبر را متوقف می‌کنند. در برنامهٔ واقعی باید سیاست خطا را با قرارداد caller هماهنگ کرد.

Each guard identifies the offending parameter and stops invalid input before calculation. A real API should align its exception policy with its callers.

۳) خروجی void را با مقدار برگشتی اشتباه نگیر3) Distinguish a void action from a return value

دو متد بنویس: یکی مبلغ را برگرداند؛ دیگری همان مبلغ و شناسه را چاپ کند. نشان بده چرا نتیجهٔ دوم را نمی‌توان در `decimal` ذخیره کرد.

Write one method returning an amount and another printing the amount with an ID. Show why the second cannot be assigned to a decimal.

پاسخ و دلیلSolution and reasoning
C#
decimal Total(decimal price, int count) => price * count;
void PrintTotal(string id, decimal total) => Console.WriteLine($"{id}: {total}");

decimal value = Total(12m, 3);
PrintTotal("A-4", value);

`Total` مقدار decimal تولید می‌کند؛ `PrintTotal` فقط اثر چاپ دارد و نوعش void است. اگر `decimal x = PrintTotal(...)` بنویسیم، خطای کامپایل می‌گیریم.

`Total` produces a decimal; `PrintTotal` has a printing side effect and returns void. Assigning its result to a decimal is a compile-time error.

۴) یک overload را به دیگری واگذار کن4) Delegate one overload to another

برای محاسبهٔ مبلغ، دو overload هم‌نام داخل یک type بساز. اولی باید دومی را با discount صفر فراخوانی کند. در هر دو حالت یک نتیجه را بررسی کن.

Create two same-named overloads inside one type. The first must call the second with zero discount. Verify both results.

پاسخ و دلیلSolution and reasoning
C#
static class Pricing
{
    public static decimal Total(decimal subtotal) => Total(subtotal, 0m);
    public static decimal Total(decimal subtotal, decimal discount) => subtotal - discount;
}

Console.WriteLine(Pricing.Total(40m)); // 40
Console.WriteLine(Pricing.Total(40m, 5m)); // 35

در یک فایل top-level، این type را بعد از دستورات بالای فایل بگذار. overload کوتاه‌تر قانون را کپی نمی‌کند. guard برای مبلغ منفی یا تخفیف نامعتبر را هم به قرارداد اضافه کن.

In a top-level file, place the type after the top-level statements. The shorter overload does not duplicate the rule. Add guards for negative amounts or invalid discounts to the actual contract.

۵) overload مبهم را تشخیص بده5) Diagnose an ambiguous overload

داخل یک type دو overload عددی با تبدیل ضمنی بساز و ببین آیا فراخوانی با literal بدون پسوند به خطای ambiguity می‌رسد. خطای کامپایل را ثبت کن و با پسوند نوع اصلاحش کن.

Put two numeric overloads in one type and see whether an unsuffixed literal is ambiguous. Record the compiler error, then fix it with an explicit suffix.

پاسخ و دلیلSolution and reasoning
C#
static class Output
{
    public static void Print(long value) => Console.WriteLine("long");
    public static void Print(ulong value) => Console.WriteLine("ulong");
}

// Output.Print(10); // ambiguous
Output.Print(10L); // long

literal صحیح `10` به هر دو نوع قابل تبدیل است و انتخاب یکتا وجود ندارد. پسوند `L` نوع را روشن می‌کند. دو امضا در یک type معتبرند؛ برخلاف دو تابع محلی هم‌نام در یک scope که تعریف overload نمی‌شوند.

The integer literal converts to both types, so there is no unique choice. `L` clarifies the type. The overloads are valid members of one type; same-named local functions in one scope are not overloaded this way.

۶) مقدار پیش‌فرض را با آرگومان نام‌دار عوض کن6) Override a default with a named argument

متدی با `currency = "IRR"` و `includeTax = true` بساز. آن را فقط با خاموش‌کردن مالیات فراخوانی کن و خروجی را نشان بده.

Create a method with `currency = "IRR"` and `includeTax = true`. Call it while disabling only tax and show the output.

پاسخ و دلیلSolution and reasoning
C#
string Label(string currency = "IRR", bool includeTax = true) =>
    $"{currency}, tax={includeTax}";

Console.WriteLine(Label(includeTax: false)); // IRR, tax=False

آرگومان نام‌دار پارامتر دوم را هدف می‌گیرد و مقدار اول را روی پیش‌فرض می‌گذارد؛ caller از روی `false` مجبور نیست ترتیب را به خاطر بسپارد.

The named argument targets the second parameter and leaves the first at its default, so the caller need not remember positional order.

۷) پارامتر اجباری را بعد از اختیاری نگذار7) Keep required parameters before optional ones

امضای نامعتبر `Send(string channel = "email", string recipient)` را build کن. خطا را بخوان و امضا را طوری بازچینی کن که recipient اجباری و channel اختیاری باشد.

Build the invalid signature `Send(string channel = "email", string recipient)`. Read the diagnostic and reorder it so recipient is required and channel optional.

پاسخ و دلیلSolution and reasoning
C#
void Send(string recipient, string channel = "email")
{
    Console.WriteLine($"{channel} -> {recipient}");
}

Send("ops@example.test");

پارامترهای لازم قبل از پارامترهای دارای مقدار پیش‌فرض می‌آیند. در APIهای موجود، جابه‌جایی ترتیب ممکن است callerهای positional را بشکند؛ تغییر امضا را مثل تغییر قرارداد بررسی کن.

Required parameters precede optional ones. Reordering an existing API may break positional callers, so treat signature changes as contract changes.

۸) params را با آرایه و آرگومان جدا امتحان کن8) Call params with an array and separate arguments

متد `params decimal[]` برای جمع مبلغ ردیف‌ها بساز. آن را با سه مقدار جدا و با یک آرایهٔ آماده صدا بزن؛ خروجی هر دو یکی باشد.

Create a `params decimal[]` sum method. Call it with three separate values and with an existing array; both results should match.

پاسخ و دلیلSolution and reasoning
C#
decimal Sum(params decimal[] values) => values.Sum();

decimal[] lines = [3m, 7m, 2m];
Console.WriteLine(Sum(3m, 7m, 2m)); // 12
Console.WriteLine(Sum(lines));       // 12

`params` آرایهٔ ورودی را در بدنه نشان می‌دهد. این مثال از LINQ فقط برای کوتاهی استفاده کرده؛ اگر LINQ را هنوز نخوانده‌ای، همان جمع را با `foreach` بنویس. آرایهٔ تهی نتیجهٔ صفر می‌دهد.

The body sees an array. LINQ is used only for brevity; if you have not learned it yet, use a `foreach`. An empty array sums to zero.

۹) ref واقعاً متغیر caller را تغییر می‌دهد9) Show that ref changes the caller variable

متدی بنویس که با `ref decimal` تخفیف را از متغیر caller کم کند. مقدار قبل و بعد را چاپ کن؛ سپس همان کد را بدون `ref` مقایسه کن.

Write a method subtracting a discount through `ref decimal`. Print the caller value before and after, then compare with a version lacking `ref`.

پاسخ و دلیلSolution and reasoning
C#
void Discount(ref decimal total) => total -= 5m;

decimal amount = 20m;
Discount(ref amount);
Console.WriteLine(amount); // 15

با `ref` متد به متغیر caller دسترسی تغییر دارد؛ بدون modifier فقط مقدار کپی‌شده را عوض می‌کنیم. اثر پنهانی کمتر، معمولاً API بهتری می‌سازد؛ این شکل را فقط وقتی نیاز واقعی به mutation همان متغیر هست نگه دار.

With `ref`, the method can mutate the caller variable; without it, only a copied value changes. Prefer fewer hidden effects and use this only when mutation of that exact variable is needed.

۱۰) خروجی out را در همهٔ مسیرها بده10) Assign an out parameter on every path

یک `TryReadQuantity` بساز که اگر متن عدد صحیح بود true و quantity را بدهد؛ در غیر این صورت false و صفر برگرداند. ورودی درست و خراب را امتحان کن.

Build `TryReadQuantity`: return true with the parsed integer for valid input; otherwise return false and zero. Test valid and invalid text.

پاسخ و دلیلSolution and reasoning
C#
bool TryReadQuantity(string text, out int quantity)
{
    if (int.TryParse(text, out quantity)) return true;
    quantity = 0;
    return false;
}

Console.WriteLine(TryReadQuantity("7", out int q)); // True
Console.WriteLine(q);                              // 7

compiler تضمین می‌کند `out` قبل از خروج مقدار داشته باشد. اگر در شاخهٔ false مقداردهی را حذف کنی build شکست می‌خورد. zero در این قرارداد فقط مقدار خروجی شکست است، نه اینکه ورودی واقعاً صفر بوده.

The compiler enforces assignment to `out` before every return. Removing the failure-path assignment fails the build. Zero here means failure output, not that the input was truly zero.

۱۱) in را فقط‌خواندنی نگه دار11) Keep an in parameter read-only

متدی با `in decimal subtotal` بساز که درصد مالیات را حساب کند. تلاش کن subtotal را در بدنه تغییر بده؛ build را ببین و خط را حذف کن.

Create a method taking `in decimal subtotal` and calculating tax. Try assigning to subtotal, observe the build failure, then remove the assignment.

پاسخ و دلیلSolution and reasoning
C#
decimal Tax(in decimal subtotal, decimal rate) => subtotal * rate;

Console.WriteLine(Tax(100m, 0.09m)); // 9.00

پارامتر `in` از داخل متد قابل assignment نیست. این قرارداد فقط‌خواندنی بودن را نشان می‌دهد، اما برای یک decimal کوچک لزوماً مزیت کارایی ندارد.

An `in` parameter cannot be assigned in the method. It communicates read-only intent but is not automatically a performance win for a small decimal.

۱۲) تابع محلی را به ورودی‌هایش محدود کن12) Restrict a local function to explicit inputs

داخل `Calculate` تابع محلی static برای اعتبارسنجی شناسه بساز. ابتدا سعی کن متغیر محلی بیرونی را بخواند؛ خطای compiler را ببین، سپس مقدار لازم را به‌صورت پارامتر بده.

Add a static local validation function inside `Calculate`. First try reading an outer local and observe the compiler error, then pass the needed value explicitly.

پاسخ و دلیلSolution and reasoning
C#
decimal Calculate(string orderId, decimal total)
{
    Validate(orderId);
    return total;

    static void Validate(string id)
    {
        if (string.IsNullOrWhiteSpace(id))
            throw new ArgumentException("Required", nameof(id));
    }
}

تابع static محلی capture ندارد؛ پارامتر `id` وابستگی را آشکار کرده. این کار اگر helper فقط همین‌جا لازم است، آن را نزدیک مصرف‌کننده نگه می‌دارد بی‌آنکه عضو کلاس بسازد.

The static local function captures nothing; `id` makes its dependency explicit. Keeping a one-use helper nearby avoids adding a class member.

۱۳) اثر جانبی را از محاسبه جدا کن13) Separate a side effect from calculation

متدی را که مبلغ را حساب و چاپ می‌کند به دو متد تبدیل کن. محاسبه باید بدون Console قابل آزمایش باشد؛ چاپ‌کننده نتیجه را بگیرد.

Split a method that calculates and prints an amount into two. Calculation must be testable without Console; the printer consumes its result.

پاسخ و دلیلSolution and reasoning
C#
decimal CalculateTotal(decimal price, int count) => price * count;
void PrintTotal(decimal total) => Console.WriteLine(total);

decimal result = CalculateTotal(8m, 3);
PrintTotal(result); // 24

می‌توان نتیجهٔ محاسبه را مستقیم assert کرد، بدون اینکه خروجی کنسول را capture کنیم. چاپ هنوز side effect است و در مرز جداگانه قرار گرفته.

The calculation can be asserted directly without capturing console output. Printing remains a side effect at a separate boundary.

۱۴) مشخص کن overload کدام بود14) Determine which overload was selected

دو overload با پارامتر `int` و `double` بساز که نام نوع را چاپ کنند. فراخوانی با `3` و `3.0` را جدا اجرا کن و نوع literalها را توضیح بده.

Create `int` and `double` overloads that print their selected type. Run calls with `3` and `3.0` and explain the literal types.

پاسخ و دلیلSolution and reasoning
C#
static class Renderer
{
    public static void Show(int value) => Console.WriteLine("int");
    public static void Show(double value) => Console.WriteLine("double");

literal صحیح بدون اعشار int و literal اعشاری پیش‌فرض double است؛ overload دقیق‌تر انتخاب می‌شود. overloadها عضو یک type هستند، نه تابع محلی هم‌نام.

۱۵) API را بدون ref طراحی کن15) Redesign an API without ref

متدی که با `ref` هم مبلغ نهایی را عوض می‌کند و هم تخفیف اعمال‌شده را می‌نویسد، بازطراحی کن تا خروجی‌ها با یک tuple نام‌دار برگردند. نتیجه‌ها را چاپ کن.

Redesign a `ref` method that mutates a total and reports the applied discount, returning a named tuple instead. Print both outputs.

پاسخ و دلیلSolution and reasoning
C#
(decimal payable, decimal discount) ApplyDiscount(decimal subtotal, decimal requested)
{
    decimal applied = Math.Clamp(requested, 0m, subtotal);
    return (subtotal - applied, applied);
}

var result = ApplyDiscount(100m, 12m);
Console.WriteLine(result.payable);  // 88
Console.WriteLine(result.discount); // 12

خروجی‌ها در یک مقدار قابل مشاهده برگشتند؛ متد دیگر caller را از پشت سر تغییر نمی‌دهد. اگر نتیجهٔ بزرگ‌تر شود، یک record یا نوع Result نام‌دار می‌تواند از tuple مناسب‌تر باشد.

Both outputs are returned as an explicit value; the method no longer mutates caller state invisibly. For a larger result, a named record or result type may be clearer than a tuple.

۱۶) قرارداد یک API سفارش را بازبینی کن16) Review an order API contract

برای «ساخت رسید» امضایی طراحی کن که شناسه و مبلغ اجباری، ارز اختیاری و پارامتر مالیات نام‌دار داشته باشد. مشخص کن خطاهای ورودی چگونه گزارش می‌شوند و با سه فراخوانی build/run را ثابت کن.

Design a receipt API with required ID and amount, optional currency, and a named tax option. State how invalid inputs are reported and prove it with three build/run calls.

یک پاسخ ممکن و دلیلOne possible solution and reasoning
C#
string BuildReceipt(string id, decimal amount, string currency = "IRR", bool includeTax = true)
{
    if (string.IsNullOrWhiteSpace(id)) throw new ArgumentException("Required", nameof(id));
    if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount));
    return $"{id} | {amount:C} {currency} | tax={includeTax}";
}

Console.WriteLine(BuildReceipt("A-8", 50m));
Console.WriteLine(BuildReceipt("A-8", 50m, includeTax: false));
// BuildReceipt("", -2m); // throws; test each invalid input separately

امضای پیشنهادی caller را مجبور به واردکردن گزینه‌های رایج نمی‌کند و نام‌گذاری، boolean را قابل‌فهم می‌سازد. برای کد واقعی، محاسبهٔ مالیات را جدا و فرمت پول را وابسته به culture بررسی کن؛ `C` صرفاً نمایش سادهٔ نمونه است.

This signature keeps common options optional and makes the Boolean readable. Real code should separate tax calculation and handle culture-aware currency formatting; `C` is only a compact demonstration.
