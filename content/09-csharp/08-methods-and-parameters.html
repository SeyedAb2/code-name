متدها و پارامترها

Methods and parameters

در فصل قبل، تصمیم‌های یک سفارش رو روشن کردیم. حالا اگه محاسبهٔ تخفیف، کنترل موجودی و ساخت پیام رو وسط حلقهٔ اصلی بنویسیم، تغییر هرکدوم بقیه رو هم به‌هم می‌ریزد. متد کمک می‌کنه یک کار رو با ورودی و خروجی معلوم جدا کنیم؛ نه اینکه فقط کد رو به چند تکه تقسیم کنیم.

In the previous chapter we made order decisions explicit. If discount calculation, stock checks and message creation all live in the main flow, changing one can disturb the others. A method isolates one job behind clear inputs and outputs—not merely a way to split text into chunks.

اول یک کار واقعی رو نام‌گذاری کنیمGive one real job a name

قیمت نهایی سفارش یک قاعده داره: جمع ردیف‌ها منهای تخفیف. اگه همان فرمول رو در سه جای برنامه کپی کنیم، روزی که قانون عوض بشه احتمالاً فقط دو نسخه رو اصلاح می‌کنیم. یک متد واحد، قانون رو یک‌جا نگه می‌داره.

An order total follows a rule: sum the lines, then subtract the discount. If we copy that formula into three places, a future rule change may update only two copies. One method keeps the rule in one place.

C# · Program.cs
decimal CalculatePayable(decimal subtotal, decimal discount)
{
    return subtotal - discount;
}

decimal payable = CalculatePayable(120m, 15m);
Console.WriteLine(payable); // 105

`decimal` برای مبلغ نمونهٔ مناسبی هست؛ `return` نتیجه رو به فراخواننده برمی‌گردونه و متد پس از آن تمام می‌شه. این امضا می‌گه دو مقدار decimal می‌گیره و یک decimal پس می‌ده. چون این کد در سطح بالای فایل هست، متد محلی top-level program محسوب می‌شه؛ بعدتر همین شکل رو داخل کلاس هم می‌بینیم.

`decimal` is a suitable choice for this money example. `return` sends the result to the caller and ends the method. The signature says it accepts two decimals and returns one. At the top level this is a local function in a top-level program; we will also use methods inside classes later.

قرارداد رو قبل از بدنه بخوانRead the contract before the body

نام، نوع خروجی، نام و نوع پارامترها می‌گن متد چه قولی می‌ده. بدنه جزئیات اجرای آن قول هست. متدی که فقط کار می‌کنه اما نام مبهمی مثل `DoIt` داره، برای نفر بعد قرارداد خوبی نیست.

The name, return type and parameter names and types describe the promise. The body implements it. A method that works but is named `DoIt` gives the next developer a poor contract.

نتیجه برمی‌گردانیم یا فقط کاری انجام می‌دهیم؟Return a value or perform an action?

گاهی caller به یک مقدار نیاز داره؛ گاهی متد یک اثر جانبی انجام می‌ده، مثل نوشتن گزارش. نوع `void` یعنی متد مقدار نتیجه‌ای برنمی‌گرداند؛ به معنی «هیچ کاری نمی‌کنه» نیست.

Sometimes the caller needs a value; sometimes a method performs a side effect, such as writing a log. `void` means no result value is returned, not that nothing happens.

C#
decimal CalculateLineTotal(decimal unitPrice, int quantity)
{
    if (unitPrice < 0 || quantity < 0)
        throw new ArgumentOutOfRangeException();

    return unitPrice * quantity;
}

void PrintReceipt(string orderId, decimal total)
{
    Console.WriteLine($"{orderId}: {total:C}");
}

محاسبه خروجی می‌ده تا caller بتواند آن رو ذخیره یا آزمایش کند. چاپ رسید خروجی متنی داره، اما آن رو به محیط می‌فرسته؛ caller دیگر مقدار رسید رو برای تصمیم بعدی در دست نداره. اگه قرار هست هم محاسبه کنیم و هم چاپ، جداسازی این دو معمولاً تست رو ساده‌تر می‌کنه.

The calculation returns a value so the caller can store or test it. Receipt printing emits text to the environment; the caller does not receive that text as a result for later decisions. Separating calculation from printing usually makes tests simpler.

مسئولیت متد رو بیش از حد بزرگ نکنDo not overload a method with responsibilities

متدی که هم ورودی می‌خونه، هم قیمت رو حساب می‌کنه، هم فایل می‌نویسه و هم ایمیل می‌فرسته، چند دلیل متفاوت برای تغییر داره. مرز خوب رو از مسئله پیدا کن؛ نه با قانون خشک «هر متد فقط یک خط».

A method that reads input, calculates a price, writes a file and sends email has several independent reasons to change. Find boundaries in the problem; do not apply a rigid “one line per method” rule.

overload: یک نام، قراردادهای ورودی متفاوتOverloads: one name, different input contracts

اگه گاهی فقط شناسهٔ سفارش رو داریم و گاهی شناسه به‌همراه ردیف‌ها، می‌تونیم دو overload داشته باشیم. کامپایلر با تعداد و نوع آرگومان‌ها تصمیم می‌گیره کدوم امضا رو فراخوانی کند.

Sometimes we have only an order ID; sometimes the ID and its lines. Overloads let us offer two signatures under one name. The compiler selects one from the argument count and types.

C# · static class
static class Pricing
{
    public static decimal CalculatePayable(decimal subtotal) =>
        CalculatePayable(subtotal, 0m);

    public static decimal CalculatePayable(decimal subtotal, decimal discount)
    {
        if (discount < 0 || discount > subtotal)
            throw new ArgumentOutOfRangeException(nameof(discount));
        return subtotal - discount;
    }
}

Console.WriteLine(Pricing.CalculatePayable(120m)); // 120
Console.WriteLine(Pricing.CalculatePayable(120m, 15m)); // 105

این دو overload عضو یک type هستن؛ این شکل رو در فایل Program.cs خودت بعد از top-level statements بگذار. overload اول قانون رو دوباره پیاده نکرد؛ به overload دوم واگذار کرد. نام پارامتر به‌تنهایی امضای متفاوتی نمی‌سازه.

Both overloads belong to one type; in a top-level Program.cs, place this type after the top-level statements. The first overload delegates instead of duplicating the rule. Parameter names alone do not create a distinct signature.

اگه تبدیل‌های ضمنی چند overload رو قابل‌استفاده کنند، فراخوانی می‌تونه مبهم بشه و build خطا بدهد. نوع آرگومان رو صریح کن یا امضاها رو بازطراحی کن؛ حدس‌زدن overload انتخاب‌شده راه‌حل نیست.

If implicit conversions make multiple overloads applicable, a call may be ambiguous and fail to build. Make the argument type explicit or redesign the signatures.

آرگومان اختیاری، نام‌دار و تعداد متغیرOptional, named and variable-count arguments

وقتی یک پارامتر معمولاً مقدار پیش‌فرض مشخصی داره، می‌توان آن رو اختیاری کرد. آرگومان نام‌دار ترتیب رو خواناتر می‌کنه. `params` هم اجازه می‌ده تعداد متغیری از ورودی‌های هم‌نوع رو به شکل آرایه دریافت کنیم.

A parameter with a sensible default can be optional. Named arguments make intent clear regardless of position. `params` accepts a variable number of same-typed arguments as an array.

C#
string FormatReceipt(string orderId, string currency = "IRR", bool includeTax = true)
{
    return $"{orderId} · {currency} · tax={includeTax}";
}

Console.WriteLine(FormatReceipt("A-42", includeTax: false));

decimal SumLines(params decimal[] amounts)
{
    decimal total = 0m;
    foreach (decimal amount in amounts) total += amount;
    return total;
}

Console.WriteLine(SumLines(10m, 12.5m, 4m)); // 26.5

پارامترهای اختیاری بعد از پارامترهای اجباری میان؛ آرگومان نام‌دار کمک می‌کنه از روی `false` حدس نزنیم کدوم گزینه خاموش شده. `params` باید آخرین پارامتر باشه و در هر فراخوانی عملاً آرایه می‌سازه یا آرایهٔ آماده می‌گیره. برای مجموعهٔ بزرگی از داده، این هزینه رو با نیاز واقعی بسنج.

Optional parameters follow required ones. A named argument prevents us from guessing what `false` disables. `params` must be last and represents an array at the call boundary. For large data sets, consider that allocation and the actual API needs.

default بخشی از API استA default is part of the API

مقدار پیش‌فرض باید رفتار بی‌خطر و مورد انتظار بسازد. همچنین default پارامتر اختیاری در محل فراخوانی کامپایل می‌شه؛ پس تغییر default در کتابخانه، لزوماً رفتار برنامه‌ای رو که قبلاً کامپایل شده عوض نمی‌کنه. در API عمومی، نسخه‌پذیری رو هم در نظر بگیر.

A default should be safe and unsurprising. Optional defaults are compiled into the caller, so changing a library default does not necessarily change already-compiled callers. Consider compatibility for public APIs.

ref، out و in: وقتی انتقال معمولی کافی نیستref, out and in: when ordinary passing is not enough

در حالت معمول، مقدار آرگومان به پارامتر می‌رسه. برای نوع مقداری، این یعنی یک کپی؛ برای متغیر reference type، مقدار reference کپی می‌شه و هنوز به همان شیء اشاره می‌کنه. این دو رو با «همه‌چیز کپی است» یا «همه‌چیز reference است» قاطی نکن.

Normally the argument value is passed to the parameter. For a value type, that means a copy; for a reference-type variable, the reference value is copied and still points to the same object. Avoid the myths that “everything is copied” or “everything is a reference.”

شکلFormقرارداد مهمKey contract
refrefcaller باید متغیر مقدارههی‌شده بدهد؛ متد می‌تونه همان متغیر رو بخواند و تغییر دهد.Caller supplies an initialized variable; the method may read and change that variable.
outoutcaller لازم نیست پیش از فراخوانی مقدار بدهد؛ متد باید پیش از خروج همهٔ مسیرها رو مقدارههی کند.Caller need not initialize it; the method must assign it on every return path.

C#
bool TryParseQuantity(string text, out int quantity)
{
    return int.TryParse(text, out quantity);
}

if (TryParseQuantity("12", out int quantity))
    Console.WriteLine(quantity); // 12

void ApplyDiscount(ref decimal total, decimal discount)
{
    total -= discount;
}

decimal total = 100m;
ApplyDiscount(ref total, 10m);
Console.WriteLine(total); // 90

`TryParse` الگوی `out` رو نشان می‌ده: مقدار موفقیت رو جدا از خروجی می‌ده. متد `ref` متغیر caller رو عوض می‌کنه؛ این قدرت اضافی، خواندن اثر متد رو دشوارتر می‌کنه. اگه یک خروجی معمولی یا یک نوع نتیجه کافی هست، آن راه معمولاً شفاف‌تر هست.

`TryParse` demonstrates `out`: success is separate from the parsed value. A `ref` method mutates the caller's variable, which makes effects harder to follow. If a normal return value or result object is enough, it is usually clearer.

C# · in
decimal CalculateTax(in decimal subtotal, in decimal rate)
{
    return subtotal * rate;
}

decimal tax = CalculateTax(100m, 0.09m);

`in` خواندن از پارامتر رو مجاز می‌کنه، نه نوشتن در آن. برای عددهای کوچک معمولاً لازم نیست از آن برای «سرعت» استفاده کنیم؛ اندازه‌گیری و نوع داده تعیین می‌کنه این شکل فایده داره یا فقط امضا رو شلوغ می‌کنه. `ref`، `out` و `in` هنگام فراخوانی هم باید در دو طرف قرارداد رعایت بشن.

`in` permits reading but not assigning through the parameter. For small values, do not add it speculatively for “speed”; measure and consider whether it clarifies or complicates the API. Calls and declarations must agree on `ref`, `out` and `in`.

تابع محلی و خروجی ref رو فقط با دلیل انتخاب کنUse local functions and ref returns deliberately

تابع محلی وقتی مفید هست که یک قاعده فقط در همان عملیات معنا داره؛ مثل اعتبارسنجی شناسه در محاسبهٔ سفارش. بیرون‌بردن آن به API کلاس، اگه هیچ مصرف‌کنندهٔ دیگری نداره، سطح عمومی بی‌دلیل می‌سازه.

A local function is useful when a rule belongs to one operation, such as validating an ID during order calculation. Moving it into a class API without another caller creates unnecessary surface area.

C#
decimal CalculateOrder(string orderId, decimal subtotal)
{
    ValidateId(orderId);
    return subtotal;

    static void ValidateId(string id)
    {
        if (string.IsNullOrWhiteSpace(id))
            throw new ArgumentException("شناسه لازم است", nameof(id));
    }
}

تابع محلی static به متغیرهای بیرونی دسترسی نمی‌گیره؛ ورودی‌های لازم باید صریح به آن داده بشن. این محدودیت گاهی باگ capture ناخواسته رو حذف می‌کنه. جای تعریف تابع در انتهای بدنه مانع فراخوانی آن از خطوط بالاتر نیست.

A static local function cannot capture outer variables; required inputs must be passed explicitly. That restriction can prevent accidental captures. Defining it after the call does not prevent earlier lines from calling it.

تابع می‌تونه با `ref` به یک عضو آرایه برگردد؛ این نمونه همان خانه رو تغییر می‌ده، نه یک کپی رو. آرایه باید هنوز زنده باشه و caller باید آگاهانه با `ref` دریافت کند. این قرارداد حساس رو فقط وقتی لازمه انتخاب کن.

A method can return a reference to an array element; this example changes that slot rather than a copy. The array must remain alive, and the caller must explicitly receive by `ref`. Use this delicate contract only when needed.

C# · ref return
ref int Slot(int[] values, int index) => ref values[index];

int[] stock = [2, 5];
ref int firstBin = ref Slot(stock, 0);
firstBin = 8;
Console.WriteLine(stock[0]); // 8

مقدار برگشتی alias قابل‌نوشتن به عنصر آرایه هست. ref return به متغیر local معمولی مجاز نیست، چون عمرش با پایان متد تمام می‌شه؛ compiler جلوی این escape رو می‌گیره. برای بیشتر APIهای روزمره، return معمولی خواناتر و امن‌تر هست.

The result is a writable alias to an array element. Returning a reference to an ordinary local is forbidden because its lifetime ends with the method; the compiler prevents that escape. For most everyday APIs, a regular return is clearer and safer.

راهنماییHint

پاسخ و دلیلSolution and reasoning
C#
decimal CalculatePayable(decimal subtotal, decimal discount)
{
    if (subtotal < 0) throw new ArgumentOutOfRangeException(nameof(subtotal));
    if (discount < 0 || discount > subtotal)
        throw new ArgumentOutOfRangeException(nameof(discount));
    return subtotal - discount;
}

شرط‌ها نام پارامتر نادرست رو در exception گزارش نمی‌کنن و قبل از خروج، ورودی نامعتبر رو متوقف می‌کنن. در برنامهٔ واقعی باید سیاست خطا رو با قرارداد caller هماهنگ کرد.

Each guard identifies the offending parameter and stops invalid input before calculation. A real API should align its exception policy with its callers.

برای بستن تمرین، خروجی یا test result رو نگه دار و یک بار نسخهٔ قبل و بعد رو کنار هم ببین. هدف فقط سبزشدن کد نیست؛ باید معلوم باشه کدوم رفتار واقعاً عوض شده.

Finish by keeping the output or test result and comparing the before/after behaviour. The goal is not merely green code; make the changed behaviour explicit.

پاسخ و دلیلSolution and reasoning
C#
decimal Total(decimal price, int count) => price * count;

decimal value = Total(12m, 3);
PrintTotal("A-4", value);

`Total` مقدار decimal تولید می‌کنه؛ `PrintTotal` فقط اثر چاپ داره و نوعش void هست. اگه `decimal x = PrintTotal(...)` بنویسیم، خطای کامپایل می‌گیریم.

`Total` produces a decimal; `PrintTotal` has a printing side effect and returns void. Assigning its result to a decimal is a compile-time error.

(decimal payable, decimal discount) ApplyDiscount(decimal subtotal, decimal requested)

string BuildReceipt(string id, decimal amount, string currency = "IRR", bool includeTax = true)
{
    if (string.IsNullOrWhiteSpace(id)) throw new ArgumentException("Required", nameof(id));
