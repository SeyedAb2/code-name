Dictionary، HashSet و مجموعه‌های مرتب

Hash and sorted collections

گزارش سفارش‌ها برای هر ردیف، مشتری رو با پیمایش کل فهرست پیدا می‌کنه. گاهی سریع هست، گاهی با رشد داده کند می‌شه. حالا lookup، یکتایی و ترتیب رو جدا می‌کنیم تا collection رو برای همان نیاز انتخاب کنیم.

For every order row, a report scans the full customer list. It may be fast now and slow as data grows. We separate lookup, uniqueness and ordering before choosing a collection.

سه نیاز رو با هم قاطی نکنDo not conflate three different needs

Dictionary برای پیدا کردن value با key هست؛ HashSet برای نگه‌داشتن عضویت یکتا؛ مجموعهٔ مرتب وقتی ترتیب بر اساس comparer بخشی از رفتار برنامه هست. هر سه می‌تونن از hash یا مقایسه استفاده کنند، اما هدف‌شان یکی نیست. از سؤال برنامه شروع کن: «چه عملی باید ارزان، یکتا یا مرتب باشه؟»

Dictionary finds a value by key; HashSet stores unique membership; sorted collections make comparer-defined order part of behaviour. Their goals differ even though hashing or comparison may be involved. Ask which operation must be efficient, unique or ordered.

عضویت یکتاUnique membershipHashSet<T>Hash membership

«گزینهٔ شروع» یعنی بعداً با اندازه و الگوی تغییر داده اعتبارسنجی می‌کنیم؛ نام collection خودش benchmark نیست.

“Candidate” means validate against size and mutation patterns; a collection name is not a benchmark.

hash و sort دو مسئلهٔ متفاوت حل می‌کننHashing and sorting solve different problems

Dictionary و SortedDictionary هر دو key/value دارن، ولی این شباهت نباید گولت بزنه. یکی معمولاً lookup سریع با hash می‌خواد، اون یکی ترتیب کلید رو به‌عنوان بخشی از قرارداد نگه می‌داره. HashSet هم وقتی value اضافی نداری، یکتایی رو مستقیم‌تر بیان می‌کنه.

Dictionary and SortedDictionary both store key/value pairs, but that similarity should not hide their different jobs. One generally optimizes hash-based lookup, while the other preserves key ordering as part of the contract. When there is no separate value, a HashSet often expresses uniqueness more directly.

برای اینکه انتخاب واقعی باشه، comparer رو هم وارد بازی می‌کنیم. اگه equality یا ordering با دامنهٔ تو نخونه، بهترین data structure هم جواب اشتباه می‌ده. اینجا قرارداد مقایسه فصل ۱۹ دوباره خودش رو نشون می‌ده.

To make the decision real, comparers must enter the picture too. If equality or ordering does not match the domain, the best data structure can still produce the wrong result. The comparison contract from Chapter 19 returns here for a reason.

hash آدرس تقریبی هست، حکم برابری نیستA hash narrows the search; it does not prove equality

Dictionary ابتدا hash رو برای پیدا کردن ناحیهٔ جست‌وجو به‌کار می‌بره و بعد برابری رو بررسی می‌کنه. دو کلید می‌تونن hash یکسان داشته باشن ولی برابر نباشن. برای کلیدی که در مجموعه نگهداری می‌شه، equality و hash باید پایدار بمانند؛ تغییر فیلد دخیل در آن‌ها می‌تونه lookup رو از کار بیندازد.

Dictionary uses a hash to narrow the search, then checks equality. Two keys may share a hash without being equal. A stored key's equality and hash must remain stable; mutating fields that participate can break lookup.

سیاست comparer را یک‌جا بده / Supply comparer policy once
var users = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase);
users["Sara"] = 7;
Console.WriteLine(users.TryGetValue("SARA", out var id));
Console.WriteLine(id);

این خروجی سیاست مقایسهٔ این dictionary رو نشان می‌ده. به‌جای lowercasing پراکنده در callerها، comparer رو در مرز ساخت مشخص کردیم. برای شناسه‌های culture-sensitive باید سیاست دیگری رو آگاهانه انتخاب کرد.

This output demonstrates the dictionary's comparison policy. Rather than scattered lowercasing, the comparer is defined at construction. Culture-sensitive identifiers require a deliberate different policy.

مجموعهٔ مرتب، comparer رو بخشی از دامنه می‌کنهA sorted collection makes its comparer part of the domain

SortedSet هم ترتیب رو نگه می‌داره و هم از دید comparer عضو تکراری رو نمی‌پذیره. اگه comparer دو مقدار رو برابر تشخیص دهد، یکی وارد نمی‌شه—even اگه Equals آن دو فرق داشته باشه. SortedList و SortedDictionary هم trade-offهای حافظه، lookup و درج متفاوتی دارن؛ workload رو بسنج و ترتیب رو به قرارداد خروجی گره بزن.

SortedSet maintains order and rejects items that compare equal. An item may be rejected even when Equals differs if the comparer returns zero. SortedList and SortedDictionary also trade memory, lookup and insertion differently; measure the workload and make output order an explicit contract.

ترتیب را تست کن / Test ordering
var scores = new SortedSet<int> { 9, 2, 5, 2 };
Console.WriteLine(string.Join(", ", scores));

خروجی نمونه ۲، ۵، ۹ هست: عضو تکراری حذف و پیمایش مرتب شده. اگه ترتیب فقط برای فایل نهایی لازمه، شاید sort هنگام خروجی از نگه‌داشتن دائمی مجموعهٔ مرتب ساده‌تر باشه.

Representative output is 2, 5, 9: duplicates collapse and enumeration is sorted. If order matters only for export, sorting at output may be simpler than maintaining a sorted collection continuously.

اولویت، ترتیب ورود نیستPriority is not arrival order

Queue مسئلهٔ فصل قبل رو حل می‌کرد: FIFO. وقتی کارها اولویت دارن، PriorityQueue گزینهٔ متفاوتی هست و priority رو جدا از عنصر نگه می‌داره. تغییر priority یک عنصر درجا الزاماً heap رو باخبر نمی‌کنه؛ معمولاً باید مورد رو با priority تازه وارد کرد یا ساختار رو بازسازی کرد. tie-breaking رو هم تعریف کن.

Queue solved the previous chapter's FIFO problem. PriorityQueue is different and stores priority separately from the element. Mutating an element's priority does not necessarily notify the heap; enqueue again with a new priority or rebuild. Define tie-breaking too.
