رمزنگاری کاربردی و امن

Practical cryptography

تیمی می‌خواد token رو «encrypt» کند تا بعداً معلوم بشه دست‌کاری نشده؛ یکی SHA-256 رو پیشنهاد می‌ده. اما hash کلید نداره و چیزی رو decrypt نمی‌کنه. هدف رو دقیق کن: محرمانگی، تشخیص دست‌کاری، اثبات فرستنده یا نگه‌داری password؟ هرکدوم ابزار متفاوت می‌خوان. این فصل دربارهٔ انتخاب صحیح API هست، نه طراحی الگوریتم رمزنگاری شخصی.

A team wants to “encrypt” a token so it can later detect tampering; someone proposes SHA-256. But a hash has no key and cannot decrypt anything. First define the goal: confidentiality, tamper detection, sender authentication or password storage? Each needs a different tool. This chapter selects APIs; it does not invent cryptographic algorithms.

random امنیتی و hash رمزنگاری‌شده رو از هم بشناسDistinguish cryptographic randomness from hashing

برای nonce، salt یا token امنیتی از RandomNumberGenerator استفاده کن؛ Random برای simulation هست، نه secret. hash مثل SHA-256 ورودی رو به digest ثابت‌طول می‌بره و کلید نداره. تغییر ورودی احتمالاً digest رو عوض می‌کنه، اما hash ساده نمی‌گه چه کسی داده رو ساخته و به تنهایی جلوی جایگزینی digest رو نمی‌گیره.

Use RandomNumberGenerator for nonces, salts and security tokens; Random is for simulation, not secrets. A hash such as SHA-256 maps input to a fixed-size digest without a key. Changing input usually changes the digest, but a plain hash does not identify who created the data and cannot stop an attacker from replacing both data and digest.

random و hash / Random bytes and a digest
byte[] token = RandomNumberGenerator.GetBytes(32);
byte[] digest = SHA256.HashData(payload);
Console.WriteLine(Convert.ToHexString(digest));

token رو با مقایسهٔ معمولی string در جای حساس authenticate نکن؛ برای مقایسهٔ byteها از CryptographicOperations.FixedTimeEquals استفاده کن، با این دقت که زمان آن به طول داده وابسته هست نه مقدار بایت‌ها. digest برای fingerprint یا integrity در کانال قابل‌اعتماد خوب هست؛ برای پیام روی کانال خصمانه، HMAC یا signature لازم می‌شه.

Do not authenticate tokens with an ordinary string comparison in a sensitive path; use CryptographicOperations.FixedTimeEquals for byte sequences, noting its time depends on length but not byte values. A digest suits fingerprints or integrity over a trusted channel; hostile-channel messages need HMAC or signatures.

HMAC می‌گه دارنهٔ کلید مشترک پیام رو ساختهHMAC authenticates a message with a shared secret

HMAC hash رو با secret key ترکیب می‌کنه؛ گیرنده‌ای که همان key رو داره tag رو دوباره می‌سازه و verify می‌کنه. هر دو طرف قادر به تولید tag هستن، پس HMAC اثبات عمومی اینکه «فقط فرستنده آن رو امضا کرده» نیست. key رو از password به‌صورت مستقیم نساز، در کد commit نکن و برای چند هدف مستقل key جدا/derivation طراحی‌شده به‌کار ببر.

HMAC combines a hash with a secret key; a receiver holding the same key recomputes and verifies the tag. Either party can create tags, so HMAC is not publicly verifiable proof that only the sender signed. Do not use a password directly as the key, commit keys to source, or reuse one key across unrelated purposes without a designed derivation scheme.

محاسبه و verify با key مشترک / Compute and verify a shared-key MAC
byte[] key = LoadSecretFromApprovedStore();
byte[] tag = HMACSHA256.HashData(key, message);

byte[] receivedTag = Convert.FromBase64String(encodedTag);
bool valid = tag.Length == receivedTag.Length &&
    CryptographicOperations.FixedTimeEquals(tag, receivedTag);

کلید باید از secret store مناسب سیستم بیاید؛ sample تابع رو عمداً تعریف نکرده چون محل امن به hosting بستگی داره. قبل از مقایسه length رو چک کن تا API رفتار طول‌وابسته نداشته باشه. فرمت پیام رو canonical کن؛ اگه دو نمایش از یک معنا داشته باشی، HMAC بر bytes متفاوت محاسبه می‌شه.

Load the key from an approved secret store; the sample intentionally leaves that function abstract because secure storage depends on hosting. Check length before comparing so the API does not compare differently sized values. Canonicalize the message format; two encodings of the same meaning produce different byte sequences and MACs.

AES-GCM هم محرمانگی می‌ده هم دست‌کاری رو می‌فهمدAES-GCM provides confidentiality and tamper detection

AES یک cipher متقارن هست؛ AES-GCM یک حالت authenticated encryption هست که ciphertext و authentication tag می‌ده. nonce باید با همان key تکرار نشه؛ تکرار nonce می‌تونه تضمین امنیتی رو خراب کند. nonce secret نیست و معمولاً همراه payload ذخیره می‌شه، اما سیاست تولید یکتایی باید برای کل عمر key درست باشه. associated data مثل tenant یا نسخه رو authenticate می‌کنه ولی encrypt نمی‌کنه.

AES is a symmetric cipher; AES-GCM is authenticated encryption that produces ciphertext and an authentication tag. A nonce must never be reused with the same key; reuse can break security guarantees. A nonce is not secret and is commonly stored with the payload, but its uniqueness policy must hold across the key's lifetime. Associated data such as tenant or version is authenticated but not encrypted.

نمونهٔ آموزشی AES-GCM / AES-GCM example
byte[] key = LoadAesKey(); // key management is outside this snippet
byte[] nonce = RandomNumberGenerator.GetBytes(12); // verify size for chosen API
byte[] ciphertext = new byte[plaintext.Length];
byte[] tag = new byte[16];
byte[] aad = Encoding.UTF8.GetBytes("v1|tenant-42");

using var aes = new AesGcm(key, tag.Length);
aes.Encrypt(nonce, plaintext, ciphertext, tag, aad);
// Store version, nonce, tag, ciphertext, and AAD context as needed.

nonce size رو با API/runtime انتخابی verify کن و هرگز nonce رو با همان key تکرار نکن؛ صرفاً تصادفی‌بودن تضمین مطلق uniqueness نیست، مخصوصاً در سیستم توزیع‌شده یا با تعداد پیام زیاد. هنگام decrypt، tag failure باید کل پیام رو نامعتبر کند؛ plaintext رو پیش از موفقیت authentication مصرف یا منتشر نکن. کلید رو در فایل کنار ciphertext قرار نده.

Verify nonce size for the selected API/runtime and never reuse a nonce with the same key; randomness alone is not an absolute uniqueness guarantee, especially in distributed systems or at high message volumes. On decrypt, tag failure invalidates the whole message; do not consume or release plaintext before authentication succeeds. Do not store the key beside the ciphertext.

امضا با کلید خصوصی تولید و با public key verify می‌شهA private key signs; a public key verifies

امضای دیجیتال integrity و انتساب به دارنهٔ private key رو در چارچوب مدیریت اعتماد فراهم می‌کنه؛ پیام رو مخفی نمی‌کنه. RSA با padding امضای مناسب یا الگوریتم‌های دیگر رو از API استانداره استفاده کن و private key رو محافظت کن. گیرنده باید بداند public key به کدوم هویت/دورهٔ اعتبار اعتماد داره؛ صرف verify شدن ریاضی، اعتماد business رو ثابت نمی‌کنه.

Digital signatures provide integrity and attribution to the private-key holder within a trust-management system; they do not hide the message. Use standard APIs with appropriate signature padding or another supported algorithm, and protect the private key. A receiver must know which identity and validity period the public key is trusted for; mathematical verification alone does not establish business trust.

امضای RSA-PSS / RSA-PSS signature
byte[] signature = privateKey.SignData(
    message,
    HashAlgorithmName.SHA256,
    RSASignaturePadding.Pss);

bool valid = publicKey.VerifyData(
    message,
    signature,
    HashAlgorithmName.SHA256,
    RSASignaturePadding.Pss);

کلیدهای public/private رو با چرخهٔ provisioning، rotation و revocation مدیریت کن. نمونهٔ بالا الگوریتم رو نشان می‌ده، نه گواهی‌نامه، اعتماد PKI یا قالب امضای محصول. اگه چند الگوریتم داری، identifier و نسخه رو در envelope authenticate کن تا downgrade مبهم پیش نیاید.

Manage public/private keys through provisioning, rotation and revocation. The example demonstrates an algorithm, not certificates, PKI trust or a product signature format. With multiple algorithms, authenticate the algorithm identifier and version in the envelope to avoid ambiguous downgrade behavior.

password رو با hash سریع عمومی ذخیره نکنNever store passwords with a fast general-purpose hash

SHA-256 برای fingerprint سریع طراحی شده؛ مهاجم می‌تونه passwordهای حدسی رو با سرعت زیاد امتحان کند. برای sign-in در برنامهٔ ASP.NET Core از PasswordHasher متعلق به Identity استفاده کن؛ خودش format/version و verify رو مدیریت می‌کنه و در صورت نیاز rehash رو تشخیص می‌ده. PBKDF2 low-level هست و برای پروتکل/نیاز خاص؛ Microsoft صریحاً استفادهٔ مستقیم آن برای password storage برنامهٔ جدید رو توصیه نمی‌کنه. salt برای passwordها لازمه و باید از RNG امن بیاید؛ pepper اگه داری باید جدا از دیتابیس و با threat model نگهداری بشه.

SHA-256 is designed to be fast, allowing attackers to test guesses rapidly. For sign-in in ASP.NET Core, use Identity's PasswordHasher, which handles versioned formats, verification and rehash needs. PBKDF2 is a low-level primitive for specific protocols; Microsoft explicitly advises against using it directly for password storage in new apps. Password hashes need salts from a secure RNG; any pepper must be stored separately from the database under a defined threat model.

الگوی Identity / Identity password hashing pattern
var hasher = new PasswordHasher<ApplicationUser>();
string stored = hasher.HashPassword(user, password);

PasswordVerificationResult result = hasher.VerifyHashedPassword(
    user, stored, submittedPassword);

if (result == PasswordVerificationResult.SuccessRehashNeeded)
{
    // Rehash with current policy after successful verification.
}

password رو log نکن و hash رو به کاربر برنگردان. policy work factor باید با نسخه و توان سرور تنظیم و بازبینی بشه؛ عدد نمونهٔ قدیمی رو کور کپی نکن. برای login عمومی، rate limit، lockout، MFA و پاسخ خطای غیرقابل‌تشخیص هم لازم‌اند؛ password hashing به‌تنهایی امنیت حساب رو کامل نمی‌کنه.

Never log passwords or return stored hashes to users. Tune and review work factors for the version and server capacity; do not blindly copy an old sample value. Public login also needs rate limiting, lockout, MFA and non-enumerating error responses; password hashing alone does not secure an account.

کلید و فرمت، نصف مسئلهٔ رمزنگاری‌اندKeys and formats are half the cryptographic problem

کلید رو در source، image، log یا همان database ciphertext نگه ندار. کلید lifecycle می‌خواد: تولید امن، دسترسی محدود، backup محافظت‌شده، rotation، شناسهٔ نسخه و ابطال. payload encrypted باید version و الگوریتم/nonce/tag لازم رو داشته باشه، اما secret رو نه. errorهای authentication رو به پیام عمومی تبدیل کن تا oracle نسازی و جزئیات حساس رو به attacker لو ندهی.

Do not keep keys in source, images, logs or beside ciphertext in the same database. Keys need a lifecycle: secure generation, restricted access, protected backup, rotation, version identifiers and revocation. An encrypted payload may carry its format/algorithm version, nonce and tag, but never the secret key. Normalize authentication errors to avoid creating an oracle or exposing sensitive details.

Design a versioned envelope for synthetic data. Path one computes a public SHA-256 fingerprint and demonstrates that anyone can recompute the digest.
