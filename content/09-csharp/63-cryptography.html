رمزنگاری کاربردی و امن

Practical cryptography

تیمی می‌خواهد token را «encrypt» کند تا بعداً معلوم شود دست‌کاری نشده؛ یکی SHA-256 را پیشنهاد می‌دهد. اما hash کلید ندارد و چیزی را decrypt نمی‌کند. هدف را دقیق کن: محرمانگی، تشخیص دست‌کاری، اثبات فرستنده یا نگه‌داری password؟ هرکدام ابزار متفاوت می‌خواهند. این فصل دربارهٔ انتخاب صحیح API است، نه طراحی الگوریتم رمزنگاری شخصی.

A team wants to “encrypt” a token so it can later detect tampering; someone proposes SHA-256. But a hash has no key and cannot decrypt anything. First define the goal: confidentiality, tamper detection, sender authentication or password storage? Each needs a different tool. This chapter selects APIs; it does not invent cryptographic algorithms.

random امنیتی و hash رمزنگاری‌شده را از هم بشناسDistinguish cryptographic randomness from hashing

برای nonce، salt یا token امنیتی از RandomNumberGenerator استفاده کن؛ Random برای simulation است، نه secret. hash مثل SHA-256 ورودی را به digest ثابت‌طول می‌برد و کلید ندارد. تغییر ورودی احتمالاً digest را عوض می‌کند، اما hash ساده نمی‌گوید چه کسی داده را ساخته و به تنهایی جلوی جایگزینی digest را نمی‌گیرد.

Use RandomNumberGenerator for nonces, salts and security tokens; Random is for simulation, not secrets. A hash such as SHA-256 maps input to a fixed-size digest without a key. Changing input usually changes the digest, but a plain hash does not identify who created the data and cannot stop an attacker from replacing both data and digest.

random و hash / Random bytes and a digest
byte[] token = RandomNumberGenerator.GetBytes(32);
byte[] digest = SHA256.HashData(payload);
Console.WriteLine(Convert.ToHexString(digest));

token را با مقایسهٔ معمولی string در جای حساس authenticate نکن؛ برای مقایسهٔ byteها از CryptographicOperations.FixedTimeEquals استفاده کن، با این دقت که زمان آن به طول داده وابسته است نه مقدار بایت‌ها. digest برای fingerprint یا integrity در کانال قابل‌اعتماد خوب است؛ برای پیام روی کانال خصمانه، HMAC یا signature لازم می‌شود.

Do not authenticate tokens with an ordinary string comparison in a sensitive path; use CryptographicOperations.FixedTimeEquals for byte sequences, noting its time depends on length but not byte values. A digest suits fingerprints or integrity over a trusted channel; hostile-channel messages need HMAC or signatures.

HMAC می‌گوید دارندهٔ کلید مشترک پیام را ساختهHMAC authenticates a message with a shared secret

HMAC hash را با secret key ترکیب می‌کند؛ گیرنده‌ای که همان key را دارد tag را دوباره می‌سازد و verify می‌کند. هر دو طرف قادر به تولید tag هستند، پس HMAC اثبات عمومی اینکه «فقط فرستنده آن را امضا کرده» نیست. key را از password به‌صورت مستقیم نساز، در کد commit نکن و برای چند هدف مستقل key جدا/derivation طراحی‌شده به‌کار ببر.

HMAC combines a hash with a secret key; a receiver holding the same key recomputes and verifies the tag. Either party can create tags, so HMAC is not publicly verifiable proof that only the sender signed. Do not use a password directly as the key, commit keys to source, or reuse one key across unrelated purposes without a designed derivation scheme.

محاسبه و verify با key مشترک / Compute and verify a shared-key MAC
byte[] key = LoadSecretFromApprovedStore();
byte[] tag = HMACSHA256.HashData(key, message);

byte[] receivedTag = Convert.FromBase64String(encodedTag);
bool valid = tag.Length == receivedTag.Length &&
    CryptographicOperations.FixedTimeEquals(tag, receivedTag);

کلید باید از secret store مناسب سیستم بیاید؛ sample تابع را عمداً تعریف نکرده چون محل امن به hosting بستگی دارد. قبل از مقایسه length را چک کن تا API رفتار طول‌وابسته نداشته باشد. فرمت پیام را canonical کن؛ اگر دو نمایش از یک معنا داشته باشی، HMAC بر bytes متفاوت محاسبه می‌شود.

Load the key from an approved secret store; the sample intentionally leaves that function abstract because secure storage depends on hosting. Check length before comparing so the API does not compare differently sized values. Canonicalize the message format; two encodings of the same meaning produce different byte sequences and MACs.

AES-GCM هم محرمانگی می‌دهد هم دست‌کاری را می‌فهمدAES-GCM provides confidentiality and tamper detection

AES یک cipher متقارن است؛ AES-GCM یک حالت authenticated encryption است که ciphertext و authentication tag می‌دهد. nonce باید با همان key تکرار نشود؛ تکرار nonce می‌تواند تضمین امنیتی را خراب کند. nonce secret نیست و معمولاً همراه payload ذخیره می‌شود، اما سیاست تولید یکتایی باید برای کل عمر key درست باشد. associated data مثل tenant یا نسخه را authenticate می‌کند ولی encrypt نمی‌کند.

AES is a symmetric cipher; AES-GCM is authenticated encryption that produces ciphertext and an authentication tag. A nonce must never be reused with the same key; reuse can break security guarantees. A nonce is not secret and is commonly stored with the payload, but its uniqueness policy must hold across the key's lifetime. Associated data such as tenant or version is authenticated but not encrypted.

نمونهٔ آموزشی AES-GCM / AES-GCM example
byte[] key = LoadAesKey(); // key management is outside this snippet
byte[] nonce = RandomNumberGenerator.GetBytes(12); // verify size for chosen API
byte[] ciphertext = new byte[plaintext.Length];
byte[] tag = new byte[16];
byte[] aad = Encoding.UTF8.GetBytes("v1|tenant-42");

using var aes = new AesGcm(key, tag.Length);
aes.Encrypt(nonce, plaintext, ciphertext, tag, aad);
// Store version, nonce, tag, ciphertext, and AAD context as needed.

nonce size را با API/runtime انتخابی verify کن و هرگز nonce را با همان key تکرار نکن؛ صرفاً تصادفی‌بودن تضمین مطلق uniqueness نیست، مخصوصاً در سیستم توزیع‌شده یا با تعداد پیام زیاد. هنگام decrypt، tag failure باید کل پیام را نامعتبر کند؛ plaintext را پیش از موفقیت authentication مصرف یا منتشر نکن. کلید را در فایل کنار ciphertext قرار نده.

Verify nonce size for the selected API/runtime and never reuse a nonce with the same key; randomness alone is not an absolute uniqueness guarantee, especially in distributed systems or at high message volumes. On decrypt, tag failure invalidates the whole message; do not consume or release plaintext before authentication succeeds. Do not store the key beside the ciphertext.

امضا با کلید خصوصی تولید و با public key verify می‌شودA private key signs; a public key verifies

امضای دیجیتال integrity و انتساب به دارندهٔ private key را در چارچوب مدیریت اعتماد فراهم می‌کند؛ پیام را مخفی نمی‌کند. RSA با padding امضای مناسب یا الگوریتم‌های دیگر را از API استاندارد استفاده کن و private key را محافظت کن. گیرنده باید بداند public key به کدام هویت/دورهٔ اعتبار اعتماد دارد؛ صرف verify شدن ریاضی، اعتماد business را ثابت نمی‌کند.

Digital signatures provide integrity and attribution to the private-key holder within a trust-management system; they do not hide the message. Use standard APIs with appropriate signature padding or another supported algorithm, and protect the private key. A receiver must know which identity and validity period the public key is trusted for; mathematical verification alone does not establish business trust.

امضای RSA-PSS / RSA-PSS signature
byte[] signature = privateKey.SignData(
    message,
    HashAlgorithmName.SHA256,
    RSASignaturePadding.Pss);

bool valid = publicKey.VerifyData(
    message,
    signature,
    HashAlgorithmName.SHA256,
    RSASignaturePadding.Pss);

کلیدهای public/private را با چرخهٔ provisioning، rotation و revocation مدیریت کن. نمونهٔ بالا الگوریتم را نشان می‌دهد، نه گواهی‌نامه، اعتماد PKI یا قالب امضای محصول. اگر چند الگوریتم داری، identifier و نسخه را در envelope authenticate کن تا downgrade مبهم پیش نیاید.

Manage public/private keys through provisioning, rotation and revocation. The example demonstrates an algorithm, not certificates, PKI trust or a product signature format. With multiple algorithms, authenticate the algorithm identifier and version in the envelope to avoid ambiguous downgrade behavior.

password را با hash سریع عمومی ذخیره نکنNever store passwords with a fast general-purpose hash

SHA-256 برای fingerprint سریع طراحی شده؛ مهاجم می‌تواند passwordهای حدسی را با سرعت زیاد امتحان کند. برای sign-in در برنامهٔ ASP.NET Core از PasswordHasher متعلق به Identity استفاده کن؛ خودش format/version و verify را مدیریت می‌کند و در صورت نیاز rehash را تشخیص می‌دهد. PBKDF2 low-level است و برای پروتکل/نیاز خاص؛ Microsoft صریحاً استفادهٔ مستقیم آن برای password storage برنامهٔ جدید را توصیه نمی‌کند. salt برای passwordها لازم است و باید از RNG امن بیاید؛ pepper اگر داری باید جدا از دیتابیس و با threat model نگهداری شود.

SHA-256 is designed to be fast, allowing attackers to test guesses rapidly. For sign-in in ASP.NET Core, use Identity's PasswordHasher, which handles versioned formats, verification and rehash needs. PBKDF2 is a low-level primitive for specific protocols; Microsoft explicitly advises against using it directly for password storage in new apps. Password hashes need salts from a secure RNG; any pepper must be stored separately from the database under a defined threat model.

الگوی Identity / Identity password hashing pattern
var hasher = new PasswordHasher<ApplicationUser>();
string stored = hasher.HashPassword(user, password);

PasswordVerificationResult result = hasher.VerifyHashedPassword(
    user, stored, submittedPassword);

if (result == PasswordVerificationResult.SuccessRehashNeeded)
{
    // Rehash with current policy after successful verification.
}

password را log نکن و hash را به کاربر برنگردان. policy work factor باید با نسخه و توان سرور تنظیم و بازبینی شود؛ عدد نمونهٔ قدیمی را کور کپی نکن. برای login عمومی، rate limit، lockout، MFA و پاسخ خطای غیرقابل‌تشخیص هم لازم‌اند؛ password hashing به‌تنهایی امنیت حساب را کامل نمی‌کند.

Never log passwords or return stored hashes to users. Tune and review work factors for the version and server capacity; do not blindly copy an old sample value. Public login also needs rate limiting, lockout, MFA and non-enumerating error responses; password hashing alone does not secure an account.

کلید و فرمت، نصف مسئلهٔ رمزنگاری‌اندKeys and formats are half the cryptographic problem

کلید را در source، image، log یا همان database ciphertext نگه ندار. کلید lifecycle می‌خواهد: تولید امن، دسترسی محدود، backup محافظت‌شده، rotation، شناسهٔ نسخه و ابطال. payload encrypted باید version و الگوریتم/nonce/tag لازم را داشته باشد، اما secret را نه. errorهای authentication را به پیام عمومی تبدیل کن تا oracle نسازی و جزئیات حساس را به attacker لو ندهی.

Do not keep keys in source, images, logs or beside ciphertext in the same database. Keys need a lifecycle: secure generation, restricted access, protected backup, rotation, version identifiers and revocation. An encrypted payload may carry its format/algorithm version, nonce and tag, but never the secret key. Normalize authentication errors to avoid creating an oracle or exposing sensitive details.

آزمایشگاه: پیام versionدار و authenticatedLab: a versioned authenticated message

برای دادهٔ ساختگی یک envelope versionدار طراحی کن. مسیر اول فقط fingerprint عمومی SHA-256 بسازد و نشان بده هر کسی می‌تواند digest را دوباره حساب کند. مسیر دوم HMAC با key آزمایشگاهی بسازد و دست‌کاری byte را با FixedTimeEquals رد کند. مسیر سوم AES-GCM را با key و nonce یکتای هر پیام، tag و AAD اجرا کند؛ پیام را serialize کن و پس از تغییر ciphertext، tag، nonce و AAD هر بار authentication failure را assert کن. کلید را از secret file آزمایشگاهی بیرون از repository بخوان و در log چاپ نکن. یک signature جدا بساز تا نشان بده public key می‌تواند verify کند اما داده را مخفی نمی‌کند. password واقعی یا key واقعی وارد آزمایش نکن؛ خروجی را با threat model و rotation plan مستند کن.

Design a versioned envelope for synthetic data. Path one computes a public SHA-256 fingerprint and demonstrates that anyone can recompute the digest. Path two creates an HMAC with a lab-only key and rejects a changed byte using FixedTimeEquals. Path three uses AES-GCM with a unique nonce per message, tag and AAD; serialize the envelope and assert authentication failure after changing ciphertext, tag, nonce or AAD. Load the lab key from a secret file outside the repository and never print it. Add a separate signature to show that a public key verifies but does not conceal data. Use no real passwords or keys; document the threat model and rotation plan.

  1. نقش هر primitive را با یک test اثبات کن.
  2. Prove each primitive's role with a test.
  3. nonce تکراری در مسیر تولید به‌صورت واضح ممنوع باشد.
  4. The production path explicitly prevents nonce reuse.
  5. هیچ secretی در repository یا log نباشد.
  6. No secret appears in the repository or logs.

انتخاب primitive درست، شروع امنیت است نه پایان آنChoosing the right primitive starts security; it does not finish it

hash fingerprint می‌دهد؛ HMAC احراز پیام با secret مشترک؛ AEAD محرمانگی و integrity؛ signature اعتبارسنجی با public key؛ و PasswordHasher برای password storage است. nonce، key lifecycle و error handling به اندازهٔ الگوریتم مهم‌اند. از APIهای استاندارد استفاده کن و در طراحی رمزنگاری محصولی، threat model و بازبینی متخصص را وارد کن. فصل بعد به مرز native می‌رویم؛ جایی که مدیریت حافظهٔ خودکار دیگر همهٔ lifetimeها را پوشش نمی‌دهد.

A hash gives a fingerprint; HMAC authenticates with a shared secret; AEAD provides confidentiality and integrity; signatures verify with public keys; PasswordHasher is for password storage. Nonces, key lifecycle and error handling matter as much as algorithms. Use standard APIs and involve threat modeling and expert review for product cryptography. Next we cross into native code, where automatic memory management no longer covers every lifetime.
