generic و constraint

Generics and constraints

تیم سه متد تقریباً یکسان برای پیدا کردن اولین عضو نوشته: یکی برای int، یکی برای string و یکی برای Product. هر بار type تازه می‌آید، کپی تازه‌ای هم ساخته می‌شود. چطور تکرار را برداریم، بدون اینکه type safety را با object و cast از دست بدهیم؟

The team has three nearly identical methods for finding the first item: one for int, one for string and one for Product. Every new type creates another copy. How can we remove duplication without giving up type safety through object and casts?

فصل ۲۱پیش‌نیازprerequisite

object تکرار را حذف می‌کند اما تضمین را هم پاک می‌کندobject removes duplication but erases guarantees

اگر همه‌چیز را object بگیریم، یک متد داریم اما هنگام استفاده cast لازم می‌شود و خطای نوع از زمان compile به runtime می‌رود. generic به ما اجازه می‌دهد خود نوع را پارامتر کنیم؛ پیاده‌سازی یکی است و compiler نوع واقعی ورودی/خروجی را نگه می‌دارد.

If everything becomes object, duplication disappears but callers need casts and type errors move from compile time to runtime. Generics let us parameterize the type itself: one implementation, while the compiler preserves actual input/output types.

یک متد برای T / One method for T
static T FirstOrDefault<T>(IEnumerable<T> items, T fallback)
{
    foreach (var item in items)
        return item;
    return fallback;
}

int firstNumber = FirstOrDefault(new[] { 4, 7 }, 0);
string firstName = FirstOrDefault(new[] { "Mina", "Reza" }, "unknown");

T در هر فراخوانی استنتاج می‌شود: یک‌بار int و بار دیگر string. خروجی هم همان نوع است و نمی‌توان آن را تصادفی به Product تبدیل کرد. این generic method است؛ generic type مثل List خود نوع را پارامتری می‌کند و می‌تواند state یا چند عضو مرتبط را در یک قرارداد جمع کند.

T is inferred per call: int once and string another time. The return value has the same type, so it cannot be accidentally cast to Product. This is a generic method; a generic type such as List<T> parameterizes the type itself and can group state or several related members under one contract.

generic یعنی عملیات مشترک روی قرارداد مشترکGenerics mean shared operations over a shared contract

هر الگوریتمی genericشدنی نیست. اگر بدنه فقط T را نگه می‌دارد یا جابه‌جا می‌کند، constraint لازم نیست. اگر باید عضو خاصی را صدا بزند، compiler باید بداند آن توانایی وجود دارد: از طریق interface/base constraint یا شکل دیگری از API. اسم T به‌تنهایی هیچ عضو اضافه‌ای به compiler معرفی نمی‌کند.

Not every algorithm needs constraints. If the body only stores or moves T, no constraint is needed. If it must call a particular member, the compiler must know that capability exists through an interface/base constraint or another API shape. Naming a type parameter T adds no members by itself.

constraint از نیاز متد می‌آید / Constraint from required behaviour
interface IHasTotal
{
    decimal Total { get; }
}

static decimal SumTotals<T>(IEnumerable<T> items)
    where T : IHasTotal
{
    decimal sum = 0m;
    foreach (var item in items)
        sum += item.Total;
    return sum;
}

بدنه واقعاً Total را لازم دارد، پس constraint همین قابلیت را بیان می‌کند. اگر constraint را حذف کنیم، compiler نمی‌تواند member access را ثابت کند. به‌جای افزودن constraintهای حدسی، از اولین عملیاتی که الگوریتم واقعاً انجام می‌دهد شروع کن.

The body genuinely needs Total, so the constraint states exactly that capability. Without it, the compiler cannot validate the member access. Instead of adding speculative constraints, start with the first operation the algorithm really performs.

constraintها compile-time capability می‌دهند. notnull به تحلیل nullable کمک می‌کند اما مقدار null را در runtime رد نمی‌کند. new() برای کدی است که واقعاً T را با new() می‌سازد؛ اگر از factory یا dependency injection استفاده می‌کنی، این constraint ممکن است بی‌دلیل callerها را محدود کند.

Constraints provide compile-time capabilities. notnull helps nullable analysis but does not reject null at runtime. new() fits code that actually constructs T with a parameterless constructor; a factory or dependency injection may make that constraint unnecessarily restrictive.

چند constraint، یک مسئلهٔ واقعیMultiple constraints, one real need

constraint می‌تواند base class، interface و قابلیت ساخت را ترکیب کند؛ ترتیب و محدودیت ترکیب را مطابق reference زبان رعایت کن. مثال زیر آیتم‌هایی می‌خواهد که شناسه دارند و سازندهٔ عمومی بی‌پارامترشان امکان ساخت نمونه می‌دهد. این طراحی فقط برای مدل‌هایی مناسب است که واقعاً چنین قرارداد ساختی دارند.

A constraint can combine a base class, interface and construction capability; follow the language reference for ordering and combination rules. This example needs items with an ID and a public parameterless constructor. It fits only models that genuinely support that construction contract.

ترکیب interface و new()
interface IHasId
{
    int Id { get; set; }
}

static T CreateWithId<T>(int id)
    where T : IHasId, new()
{
    var item = new T();
    item.Id = id;
    return item;
}

اگر ساخت معتبر به چند آرگومان و invariant وابسته است، new() احتمالاً abstraction ضعیفی است؛ factory یا constructor معنادار بهتر است. constraint نباید صرفاً چون از نظر syntax ممکن است، به API اضافه شود.

If valid construction requires several arguments and invariants, new() may be too weak; a factory or meaningful constructor is better. Do not add a constraint merely because the syntax permits it.

enum، Delegate و unmanaged برای دامنهٔ خاصEnum, Delegate and unmanaged for specialised domains

گاهی الگوریتم واقعاً فقط با enum یا delegateها کار می‌کند. constraint نوعی این محدوده را از ابتدا روشن می‌کند. unmanaged زمانی لازم است که API به نوع‌های unmanaged نیاز دارد؛ صرفاً برای «سریع‌تر کردن» generic از آن استفاده نکن.

Some algorithms genuinely work only with enums or delegates. These constraints make that scope explicit. unmanaged is for APIs that require unmanaged types; do not use it merely to make a generic “faster”.

محدودکردن T به enum / Restrict T to enum
static string[] Names<TEnum>()
    where TEnum : struct, Enum
    => Enum.GetNames<TEnum>();

enum OrderState { Draft, Paid, Shipped }
Console.WriteLine(string.Join(", ", Names<OrderState>()));

constraint جلوی استفادهٔ تصادفی با string یا class را می‌گیرد. اگر فقط می‌خواهی نام enumها را بگیری، API استاندارد را هم بشناس؛ wrapper generic زمانی ارزش دارد که قرارداد یا رفتار اضافه‌ای روشن بسازد.

The constraint prevents accidental use with string or class. If you only need enum names, know the standard API too; a generic wrapper is worthwhile only when it adds a clear contract or behaviour.

آزمایشگاه: جست‌وجوی type-safe بسازLab: build a type-safe lookup

سه نسخهٔ FindFirst برای int، string و Product را با generic جایگزین کن. سپس الگوریتمی جدا بساز که فقط مدل‌های دارای predicate مشخص را بپذیرد.

Replace three FindFirst overloads for int, string and Product with a generic version. Then build a separate algorithm that accepts only models with a required predicate contract.

  1. نسخه‌های تکراری را بنویس و بخش‌های یکسان را علامت بزن.
  2. Write the duplicates and mark the repeated parts.
  3. نوع T را استخراج کن و compile-time type خروجی را بررسی کن.
  4. Extract T and inspect the compile-time result type.
  5. یک نسخهٔ object بساز و cast نامعتبر را اجرا کن تا تفاوت خطا دیده شود.
  6. Create an object-based version and trigger a bad cast to observe the difference.
  7. برای SumTotals یک interface constraint حداقلی تعریف کن.
  8. Define a minimal interface constraint for SumTotals.
  9. یک متد بساز که فقط با enum کار کند و constraint را حذف کن؛ خطای compile را ببین.
  10. Build an enum-only method, remove its constraint and inspect compiler errors.
  11. notnull را روی type nullable امتحان کن؛ warning را از runtime رفتار جدا کن.
  12. Try nullable input against notnull; distinguish warnings from runtime behaviour.
  13. در پایان constraintهای اضافه را حذف و دلیل هر باقی‌مانده را ثبت کن.
  14. Remove unnecessary constraints and document every one that remains.
معیار پایانDefinition of done

یک پیاده‌سازی برای چند type کار می‌کند؛ caller cast نمی‌کند؛ compiler فقط عملیات تضمین‌شده را می‌پذیرد؛ و هر constraint دلیل دامنه‌ای دارد.

One implementation works for several types; callers do not cast; the compiler permits only guaranteed operations; and every constraint has a domain reason.

چرا خروجی object در مقایسه با T type-safeتر نیست؟

Why is an object return less type-safe than T?

۱۱) چند constraint11) Multiple constraints

When do you combine an interface constraint and new()?

۱۲) cast را حذف کن12) Remove the cast

تابع object می‌گیرد و Product برمی‌گرداند؛ چگونه type safety می‌دهی؟

A function accepts object and returns Product. How do you restore type safety?

پاسخAnswer

T را پارامتری کن و رابطهٔ ورودی/خروجی را با همان T حفظ کن؛ اگر رفتار لازم است constraint بده.

Parameterize with T and preserve the input/output relation; add a constraint only if behaviour is needed.

۱۳) constraint بی‌دلیل13) An unnecessary constraint

یک تابع فقط T را برمی‌گرداند اما where T : new() دارد. چه می‌کنی؟

A function only returns T but has where T : new(). What do you do?

پاسخAnswer

constraint را حذف می‌کنم؛ قابلیت ساخت استفاده نمی‌شود و callerها بی‌دلیل محدودند.

Remove it; construction is unused and callers are needlessly restricted.

۱۴) algorithm یا wrapper؟14) Algorithm or wrapper?

generic wrapper فقط یک API آماده را با همان امضا صدا می‌زند. آیا ارزشی ساخته؟

A generic wrapper only forwards to an existing API with the same signature. Does it add value?

پاسخAnswer

نه لزوماً؛ اگر قرارداد، سیاست یا reuse معناداری نمی‌سازد حذفش کن.

Not necessarily; remove it if it adds no meaningful contract, policy or reuse.

۱۵) خطای type در compile15) Catch type errors at compile time

چطور ثابت می‌کنی generic method خروجی string را به int نمی‌پذیرد؟

How do you prove the generic method will not accept a string result as int?

روشMethod

یک فراخوانی ناسازگار جداگانه compile کن؛ انتظار خطای compiler است، نه cast exception حین اجرا.

۱۶) API constraint review16) Review the constraint API

یک generic با class، new() و interface constraint دارد اما بدنه فقط interface را لازم دارد. اصلاح؟

A generic has class, new() and interface constraints, but the body only needs the interface. Repair?

پاسخAnswer

constraintهای class و new() را حذف کن؛ فقط interface capability لازم را نگه دار و callerهای مجاز را دوباره build کن.

Remove class and new(); retain only the needed interface capability and rebuild consumers.

T را با قرارداد واقعی محدود کنConstrain T to the real contract

generic تکرار را کم می‌کند و رابطهٔ type را در compile حفظ می‌کند؛ constraint فقط وقتی لازم است که بدنه یک توانایی می‌خواهد. notnull جای guard نیست، new() جای factory را همیشه نمی‌گیرد و unmanaged ابزار عمومی performance نیست. حالا که یک type را بدون دانستن جزئیاتش استفاده می‌کنیم، فصل بعد جهت ورودی و خروجی typeها را دنبال می‌کنیم تا variance را درست بخوانیم.

Generics reduce duplication while preserving type relationships at compile time; constrain only when the body needs a capability. notnull is not a guard, new() is not always a factory substitute, and unmanaged is not a general performance tool.
