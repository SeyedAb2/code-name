async/await بدون افسانه

async/await without myths

صفحهٔ سفارش برای گرفتن آدرس مشتری، یک تماس HTTP می‌زند و نخ را تا جواب نگه می‌دارد. زیر بار، نخ‌ها پر می‌شوند؛ کسی هم برای حلش کل کد را با Task.Run پیچیده است. اینجا از همان درخواست شروع می‌کنیم: کدام کار منتظر I/O است، کدام واقعاً CPU می‌خواهد، و await دقیقاً چه چیزی را آزاد می‌کند؟

An order page calls HTTP for a customer address and holds a thread until the response arrives. Under load, threads are tied up; someone wrapped everything in Task.Run to fix it. We start with that request: which part waits for I/O, which part consumes CPU, and what does await actually release?

انتظار شبکه با محاسبه فرق داردWaiting for the network differs from computation

در I/O-bound، درخواست به فایل یا شبکه داده می‌شود و بخش اصلی زمان منتظر دستگاه/سرویس است؛ API ناهمگام می‌تواند هنگام انتظار thread را به کار دیگری برگرداند. در CPU-bound، processor واقعاً مشغول محاسبه است؛ async کردن امضای متد CPU را آزاد نمی‌کند. برای کار محاسباتی سنگین در UI ممکن است Task.Run رابط را responsive نگه دارد؛ در server، اضافه‌کردن Task.Run دور یک محاسبهٔ هم‌زمان معمولاً ظرفیت جادویی ایجاد نمی‌کند.

For I/O-bound work, a request is issued to a file or network service and most time is spent waiting; an asynchronous API can return the thread to other work. For CPU-bound work, the processor is actively computing; adding async to a method signature does not free the CPU. In UI code, Task.Run can keep the interface responsive during heavy computation; on a server, wrapping synchronous computation in Task.Run does not magically increase capacity.

I/O واقعی را await کن / Await real I/O
public async Task<Customer?> GetCustomerAsync(
    string id, CancellationToken cancellationToken)
{
    using HttpResponseMessage response = await _http.GetAsync(
        $"customers/{Uri.EscapeDataString(id)}", cancellationToken);
    if (response.StatusCode == HttpStatusCode.NotFound) return null;
    response.EnsureSuccessStatusCode();
    return await response.Content.ReadFromJsonAsync<Customer>(
        cancellationToken: cancellationToken);
}

اینجا GetAsync خودش I/O ناهمگام دارد؛ دورش Task.Run لازم نیست. cancellation هم از caller تا هر دو مرحله رسیده. اگر یک API فقط synchronous باشد، چسباندن suffix «Async» به wrapper synchronous نخ را آزاد نمی‌کند.

Here, GetAsync already performs asynchronous I/O; wrapping it in Task.Run is unnecessary. Cancellation reaches both stages from the caller. Appending “Async” to a synchronous wrapper does not free the thread.

Task یک نخ نیستA Task is not a thread

Task نمایندهٔ کار/نتیجه‌ای است که ممکن است هنوز تمام نشده باشد؛ بعضی Taskها I/O را نمایندگی می‌کنند و هیچ نخِ اختصاصیِ در حال انتظار ندارند. بعضی کارهای CPU با thread pool اجرا می‌شوند. compiler متد async را به state machine تبدیل می‌کند تا قبل و بعد از هر await، state لازم را نگه دارد. خود کلیدواژهٔ async نه thread می‌سازد و نه متد را خودکار موازی می‌کند.

Task represents work or a result that may not be complete; some tasks represent I/O without a dedicated thread waiting. CPU work may run on the thread pool. The compiler transforms an async method into a state machine that preserves what is needed before and after awaits. The async keyword itself creates no thread and does not automatically parallelize a method.

ترتیب اجرا / Execution order
Console.WriteLine("before");
Task<string> pending = client.GetStringAsync(uri);
Console.WriteLine("request started");

string body = await pending;
Console.WriteLine("response received");

بخش متد تا رسیدن به await اجرا می‌شود؛ اگر Task تمام نشده باشد، continuation برای بعد ثبت و کنترل به caller برمی‌گردد. ممکن است Task پیش از await تمام شده باشد و ادامه تقریباً فوری اجرا شود. پس «async یعنی همیشه در زمان دیگری اجرا می‌شود» هم درست نیست.

The method runs until an await. If the task is incomplete, a continuation is registered and control returns to the caller. The task may already be complete, in which case continuation can proceed immediately. “Async always runs later” is also false.

await نقطهٔ واگذاری کنترل استawait is a point where control can yield

اگر await شده کامل نباشد، متد فعلی نتیجهٔ خود را به شکل Task برمی‌گرداند، caller هم می‌تواند ادامه دهد؛ وقتی کار تمام شد، continuation ادامه می‌دهد و نتیجه یا exception را تحویل می‌گیرد. اگر Task faulted باشد، await exception اصلی را دوباره پرتاب می‌کند؛ اگر canceled باشد، cancellation از همین مسیر دیده می‌شود. پس exception را فقط اطراف ساخت Task نگذار؛ await را هم در مرز مدیریت خطا در نظر بگیر.

If the awaited operation is incomplete, the current method returns its Task so the caller can continue. When the operation finishes, its continuation resumes and observes the result or exception. If the task faulted, await rethrows the original exception; cancellation is also observed through this path. Handle failures at the await boundary, not only when creating a task.

await در مسیر خطا / Await at the failure boundary
try
{
    return await LoadAsync(cancellationToken);
}
catch (HttpRequestException ex)
{
    logger.LogWarning(ex, "Remote service unavailable");
    throw;
}

exception را اگر نمی‌توانی به نتیجهٔ معنادار تبدیل کنی، با throw; دوباره پرتاب کن تا stack trace حفظ شود؛ throw ex; مسیر قبلی را خراب می‌کند. Cancellation را هم به‌عنوان نتیجهٔ معمول خطای شبکه قورت نده.

If you cannot map the exception to a meaningful result, rethrow with throw; to preserve the stack trace; throw ex; resets it. Do not swallow cancellation as an ordinary network error.

ادامهٔ متد کجا اجرا می‌شود؟Where does a continuation run?

continuation می‌تواند به synchronization context قبلی برگردد؛ در UI این معمولاً همان thread رابط است، اما در برنامهٔ معمول ASP.NET Core چنین context اختصاصیِ قدیمی وجود ندارد. کتابخانه‌ها گاهی ConfigureAwait(false) می‌گذارند تا درخواست بازگشت به context ندهند؛ در کد UI که بعداً به کنترل دست می‌زند باید context را حفظ کند. این تنظیم راه‌حل عمومی performance یا deadlock نیست.

A continuation may return to the captured synchronization context; in UI apps that is commonly the UI thread, while typical ASP.NET Core code does not have the old dedicated request context. Libraries sometimes use ConfigureAwait(false) to avoid requiring context capture; UI code that later accesses controls must preserve it. This is not a universal performance or deadlock fix.

این تفاوت، علت بعضی deadlockهای کد قدیمی را هم توضیح می‌دهد: thread منتظر Task می‌ماند، continuation منتظر همان context مسدودشده است. درمان معمول، async کردن کل زنجیره و پرهیز از .Result/.Wait() است، نه دست‌کاری تصادفی context.

This also explains some deadlocks in older code: a thread blocks waiting for a task while its continuation waits for the blocked context. The usual fix is async all the way and avoiding .Result/.Wait(), not random context manipulation.

برای CPU، Task.Run فقط جابه‌جایی نخ استFor CPU work, Task.Run only moves the work

تصویرسازی سنگین را روی thread UI اجرا نکن؛ انتقال به thread pool responsiveness را بهتر می‌کند اما محاسبه همچنان CPU مصرف می‌کند. در server، اگر هر درخواست کار CPU را به pool بفرستد، فشار فقط جابه‌جا می‌شود و thread pool می‌تواند اشباع شود. الگوریتم، محدودیت هم‌زمانی یا worker اختصاصی شاید تصمیم بهتری باشد. I/O را با Task.Run «ناهمگام» نکن؛ API async واقعی را صدا بزن.

Do not run expensive rendering on the UI thread; moving it to the thread pool improves responsiveness but still consumes CPU. On a server, sending every request’s CPU work to the pool only moves the pressure and may saturate the pool. An algorithmic improvement, concurrency bound or dedicated worker may be better. Do not “async-ify” I/O with Task.Run; call a real asynchronous API.

محاسبهٔ CPU در UI / CPU work in a UI
Result result = await Task.Run(
    () => ExpensiveCalculation(input),
    cancellationToken);

Render(result); // resumes in the UI context when captured

نمونه برای UI است؛ در ASP.NET Core به‌عنوان wrapper عمومی استفاده نکن. تابع محاسبه باید cancellation را درون حلقه هم بررسی کند؛ tokenِ overload به‌تنهایی کار synchronous شروع‌شده را وسط محاسبه متوقف نمی‌کند.

This example targets UI code; do not use it as a general ASP.NET Core wrapper. The computation itself must check cancellation inside its loop; the overload token alone cannot interrupt already-running synchronous work.

ترتیب، موازی‌سازی و fire-and-forgetSequencing, concurrency and fire-and-forget

دو درخواست مستقل را اگر پشت سر هم await کنی، زمان انتظار جمع می‌شود. هر دو Task را شروع و بعد WhenAll کن؛ اما کار هم‌زمان، rate limit و ظرفیت را نادیده نمی‌گیرد. Task را رها نکنی: خطا، cancellation و عمر dependency از دست می‌روند. fire-and-forget واقعی در سرویس معمولاً باید به queue/background service با مالکیت و مشاهده‌پذیری مشخص تبدیل شود.

Sequentially awaiting independent requests adds their waiting times. Start both tasks and await WhenAll, but concurrency does not bypass rate limits or capacity. Do not abandon a task: its failures, cancellation and dependency lifetime are lost. In a service, fire-and-forget work usually belongs in a queue or background service with clear ownership and observability.

کارهای مستقل / Independent operations
Task<Profile> profileTask = GetProfileAsync(id, ct);
Task<Orders> ordersTask = GetOrdersAsync(id, ct);

await Task.WhenAll(profileTask, ordersTask);
return new Dashboard(await profileTask, await ordersTask);

وقتی یکی شکست بخورد، WhenAll پس از پایان Taskهای ورودی fault می‌شود؛ بقیه خودکار لغو نمی‌شوند. اگر شکست یکی باید دیگری را متوقف کند، linked cancellation و سیاست cleanup اضافه کن. تعداد Taskهای بی‌حد هم با semaphore/صف محدود می‌شود؛ فصل Taskها این مرز را کامل می‌کند.

If one task fails, WhenAll faults after its inputs finish; the others are not automatically cancelled. If one failure should stop the rest, add linked cancellation and cleanup policy. Unbounded task creation also needs a semaphore or queue; the next task chapter develops that boundary.

۱) نخ یا Task؟1) Thread or Task?

دو درخواست شبکه در انتظارند؛ برای هرکدام Task و thread فعال را در یک timeline رسم کن.

Two network requests are pending; draw a timeline of tasks and active threads.

پاسخ فنیTechnical reasoning

هنگام I/O، Task زنده می‌ماند اما معمولاً thread منتظر اختصاصی لازم نیست؛ continuation بعداً اجرا می‌شود.

During I/O, the task remains pending without a dedicated waiting thread; its continuation runs later.

۲) I/O و Task.Run2) I/O and Task.Run

کد HTTP را داخل Task.Run می‌پیچد؛ مسیر ساده‌تر و دلیلش را پیاده کن.

HTTP is wrapped in Task.Run; implement a simpler path and explain why.

پاسخ فنیTechnical reasoning

مستقیم API async مثل GetAsync را await کن؛ thread pool wrapper انتظار I/O را بهتر نمی‌کند.

Await the real asynchronous API such as GetAsync; a thread-pool wrapper does not improve I/O waiting.

۳) CPU سنگین در UI3) Heavy CPU work in a UI

محاسبه تصویر رابط را فریز می‌کند؛ responsiveness را بدون ادعای سریع‌ترشدن بسنج.

Image computation freezes the UI; improve responsiveness without claiming faster computation.

پاسخ فنیTechnical reasoning

محاسبه را با Task.Run به pool ببر؛ CPU همان کار را دارد، ولی UI thread آزاد می‌ماند.

Move computation to the pool with Task.Run; CPU work remains, while the UI thread stays responsive.

۴) async بدون await4) async without await

warning کامپایلر از متد async خالی می‌آید؛ return type و implementation را اصلاح کن.

An empty async method triggers a compiler warning; fix its return type and implementation.

پاسخ فنیTechnical reasoning

اگر کار async نیست، async را بردار و Task مناسب برگردان؛ اگر هست، عملیات واقعی را await کن.

If there is no asynchronous work, remove async and return an appropriate Task; otherwise await the real operation.

۵) Task.Result5) Task.Result

UI روی .Result قفل می‌کند؛ کل مسیر فراخوانی را async کن.

The UI blocks on .Result; convert the complete call chain to async.

پاسخ فنیTechnical reasoning

از caller تا I/O، await را ادامه بده تا thread مسدود و context deadlock نشود.

Propagate await from caller to I/O to avoid blocking a thread and deadlocking a context.

۶) exception بعد از await6) Exception after await

try فقط ساخت Task را پوشانده و exception از await خارج می‌شود؛ مرز را جابه‌جا کن.

The try block covers task creation only, so the exception escapes await; move the boundary.

پاسخ فنیTechnical reasoning

خود expression await را داخل try بگذار تا fault هنگام مشاهده مدیریت شود.

Place the await expression inside try so the fault is handled when observed.

۷) Task فراموش‌شده7) Forgotten Task

نتیجهٔ SaveAsync رها شده؛ خطا و lifecycle را به caller برگردان.

The SaveAsync task is discarded; restore error and lifetime ownership.

پاسخ فنیTechnical reasoning

متد را await کن؛ کار background را به queue/hosted service بسپار و خطایش را مشاهده‌پذیر کن.

Await it, or move background work to a queue/hosted service with observable failures.

۸) async event handler8) Async event handler

event handler ناچار async void است؛ exception و test را مدیریت کن.

An event handler must be async void; manage exceptions and testability.

پاسخ فنیTechnical reasoning

handler را تا حد ممکن adapter باریک و exception-safe کن؛ منطق اصلی را به متد Task منتقل کن.

Keep the handler a thin, exception-safe adapter and move core logic into a Task-returning method.

۹) sequential یا concurrent9) Sequential or concurrent?

دو endpoint مستقل را پشت‌سرهم می‌خوانی؛ زمان و failure semantics نسخهٔ WhenAll را بسنج.

Two independent endpoints are awaited sequentially; measure time and inspect WhenAll failure semantics.

پاسخ فنیTechnical reasoning

Taskها را شروع و WhenAll کن؛ concurrency را فقط برای کارهای مستقل و با محدودیت ظرفیت بساز.

Start and await both with WhenAll; use concurrency only for independent work and respect capacity.

۱۰) ConfigureAwait10) ConfigureAwait

کتابخانه به کنترل UI دسترسی دارد ولی false گذاشته؛ خطر و محل درست استفاده را توضیح بده.

A library accesses a UI control after configuring false; explain the risk and proper usage.

پاسخ فنیTechnical reasoning

پس از false continuation الزام بازگشت به UI context ندارد؛ UI code برای دسترسی کنترل باید context مناسب را حفظ کند.

After false, continuation need not return to the UI context; UI code must preserve the proper context for control access.

۱۱) cancellation propagation11) Propagate cancellation

لایهٔ میانی token را نمی‌پذیرد و درخواست بعد از disconnect ادامه دارد؛ signatureها را کامل کن.

A middle layer drops the token, so work continues after disconnect; complete the signatures.

پاسخ فنیTechnical reasoning

token را در همهٔ لایه‌ها بپذیر و به APIهای async پایین‌دست عبور بده.

Accept the token at each layer and pass it to downstream asynchronous APIs.

۱۲) متد async متوالی12) Sequential async method

کد دو I/O مستقل را بی‌دلیل serialize می‌کند؛ dependency واقعی را مشخص کن.

Two independent I/O operations are unnecessarily serialized; identify real dependencies.

پاسخ فنیTechnical reasoning

اگر ورودی یکی به دیگری وابسته نیست، هر دو را آغاز و با WhenAll منتظر شو.

If neither depends on the other, start both and await them with WhenAll.

۱۳) Task.Run روی server13) Task.Run on a server

هر درخواست محاسبهٔ sync را در Task.Run می‌پیچد؛ اشباع thread pool را تشخیص بده.

Every request wraps synchronous CPU work in Task.Run; diagnose thread-pool saturation.

پاسخ فنیTechnical reasoning

Task.Run ظرفیت CPU را زیاد نمی‌کند؛ الگوریتم و نرخ هم‌زمانی را اندازه بگیر و workload را محدود کن.

Task.Run does not add CPU capacity; measure the algorithm and concurrency rate, then bound the workload.

۱۴) continuation سریع14) Synchronous completion

تست می‌گوید continuation گاهی پیش از await بعدی اجرا می‌شود؛ رفتار را توضیح بده.

A test observes continuation before a later await; explain the behavior.

پاسخ فنیTechnical reasoning

اگر Task پیش از رسیدن به await کامل باشد، await می‌تواند بدون yield ادامه یابد.

If the task is complete when awaited, execution may continue without yielding.

۱۵) failure در WhenAll15) Failure in WhenAll

یک Task fault می‌شود و دیگری کار را ادامه می‌دهد؛ سیاست لغو باقی‌ها را به design اضافه کن.

One task faults while another continues; add a policy for cancelling remaining work.

پاسخ فنیTechnical reasoning

WhenAll به‌تنهایی siblingها را لغو نمی‌کند؛ linked CTS، cancellation صریح و await cleanup را طراحی کن.

WhenAll does not cancel siblings; design linked cancellation, explicit cancellation and awaited cleanup.

۱۶) incident نخ‌های اشغال‌شده16) Thread-starvation incident

thread pool در peak اشباع است؛ sync-over-async، Task.Run و I/O واقعی را در trace جدا کن.

The pool saturates at peak; distinguish sync-over-async, Task.Run and real I/O in a trace.

پاسخ فنیTechnical reasoning

stack و duration waitها را بگیر، blocking را به await واقعی تبدیل و CPU jobها را جدا اندازه‌گیری کن؛ فقط thread count را بالا نبر.

Capture stacks and wait durations, replace blocking with real awaits and measure CPU jobs separately; do not merely raise thread count.

آزمایشگاه: داشبورد دو منبعیLab: a two-source dashboard

یک endpoint آزمایشی کند و یک محاسبهٔ CPU محدود بساز. نسخهٔ اول شبکه را sync منتظر بماند و UI/throughput را اندازه بگیر؛ نسخهٔ دوم API async را end-to-end await و cancellation را عبور دهد. دو منبع مستقل را با WhenAll اجرا کن؛ بعد یکی را fault و دیگری را کند کن تا بفهمی taskها خودکار لغو نمی‌شوند. محاسبهٔ CPU را جداگانه در UI از thread pool اجرا کن و روی server آن را بی‌دلیل wrap نکن. timeline شامل call، await، continuation، thread و exception رسم کن.

Create a slow test endpoint and a bounded CPU calculation. In version one, synchronously wait for network I/O and measure UI responsiveness or throughput; in version two, await real async APIs end to end and propagate cancellation. Run independent sources with WhenAll, then fault one and slow the other to see that tasks are not automatically cancelled. Move CPU work off a UI thread separately, but do not wrap it needlessly on a server. Draw a timeline of calls, awaits, continuations, threads and exceptions.

  2. Classify each stage as CPU-bound or I/O-bound.
  3. زمان انتظار و thread اشغال‌شده را جدا اندازه بگیر.
  4. Measure wait time separately from occupied threads.
  5. آزمایش را با cancellation و خطا هم تکرار کن.
  6. Repeat with cancellation and failures.

async ابزار انتظار مقیاس‌پذیر است، نه شتاب‌دهندهٔ همه‌چیزAsync scales waiting; it does not accelerate everything

I/O async کمک می‌کند هنگام انتظار thread را نگه نداریم؛ Task نتیجه و عمر کار را نشان می‌دهد؛ await نقطهٔ بازگشت continuation است؛ Task.Run برای جابه‌جایی CPU کار می‌کند، نه برای تزئین I/O. وقتی این چهار نکته را از هم جدا کنیم، تصمیم async از حدس بیرون می‌آید. فصل بعد Taskها را عمیق‌تر می‌کنیم: چند کار، cancellation، timeout و کنترل failure.

Async I/O avoids holding a thread while waiting; Task represents work and lifetime; await marks where a continuation resumes; Task.Run moves CPU work rather than decorating I/O. Separating these ideas turns async decisions from guesswork into design. Next we explore multiple tasks, cancellation, deadlines and failure control.
