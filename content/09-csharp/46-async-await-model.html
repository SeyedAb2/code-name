async/await بدون افسانه

async/await without myths

صفحهٔ سفارش برای گرفتن آدرس مشتری، یک تماس HTTP می‌زنه و نخ رو تا جواب نگه می‌داره. زیر بار، نخ‌ها پر می‌شن؛ کسی هم برای حلش کل کد رو با Task.Run پیچیده هست. اینجا از همان درخواست شروع می‌کنیم: کدوم کار منتظر I/O هست، کدوم واقعاً CPU می‌خواد، و await دقیقاً چه چیزی رو آزاد می‌کنه؟

An order page calls HTTP for a customer address and holds a thread until the response arrives. Under load, threads are tied up; someone wrapped everything in Task.Run to fix it. We start with that request: which part waits for I/O, which part consumes CPU, and what does await actually release?

انتظار شبکه با محاسبه فرق دارهWaiting for the network differs from computation

در I/O-bound، درخواست به فایل یا شبکه داده می‌شه و بخش اصلی زمان منتظر دستگاه/سرویس هست؛ API ناهمگام می‌تونه هنگام انتظار thread رو به کار دیگری برگرداند. در CPU-bound، processor واقعاً مشغول محاسبه هست؛ async کردن امضای متد CPU رو آزاد نمی‌کنه. برای کار محاسباتی سنگین در UI ممکنه Task.Run رابط رو responsive نگه داره؛ در server، اضافه‌کردن Task.Run دور یک محاسبهٔ هم‌زمان معمولاً ظرفیت جادویی ایجاد نمی‌کنه.

For I/O-bound work, a request is issued to a file or network service and most time is spent waiting; an asynchronous API can return the thread to other work. For CPU-bound work, the processor is actively computing; adding async to a method signature does not free the CPU. In UI code, Task.Run can keep the interface responsive during heavy computation; on a server, wrapping synchronous computation in Task.Run does not magically increase capacity.

I/O واقعی را await کن / Await real I/O
public async Task<Customer?> GetCustomerAsync(
    string id, CancellationToken cancellationToken)
{
    using HttpResponseMessage response = await _http.GetAsync(
        $"customers/{Uri.EscapeDataString(id)}", cancellationToken);
    if (response.StatusCode == HttpStatusCode.NotFound) return null;
    response.EnsureSuccessStatusCode();
    return await response.Content.ReadFromJsonAsync<Customer>(
        cancellationToken: cancellationToken);
}

اینجا GetAsync خودش I/O ناهمگام داره؛ دورش Task.Run لازم نیست. cancellation هم از caller تا هر دو مرحله رسیده. اگه یک API فقط synchronous باشه، چسباندن suffix «Async» به wrapper synchronous نخ رو آزاد نمی‌کنه.

Here, GetAsync already performs asynchronous I/O; wrapping it in Task.Run is unnecessary. Cancellation reaches both stages from the caller. Appending “Async” to a synchronous wrapper does not free the thread.

async رو با thread قاطی کنیم، طراحی از همون اول کج می‌شهConfusing async with threads bends the design from the start

وقتی request منتظر شبکه‌ست، CPU معمولاً کاری برای اون request نداره. `await` ارزشش اینه که این زمان انتظار رو به معنی «یه thread رو همین‌جا نگه دار» تبدیل نکنه. ولی اگه یه محاسبه واقعاً CPU-bound باشه، `await` اون محاسبه رو ناپدید نمی‌کنه. همین مرز ساده خیلی از `Task.Run`های بی‌جا رو توضیح می‌ده.

When a request is waiting on the network, the CPU usually has no work to do for that request. The value of `await` is that this waiting time does not have to mean “keep a thread parked here.” But a truly CPU-bound calculation does not disappear because a method is marked async. That boundary explains many unnecessary `Task.Run` wrappers.

در این فصل timeline مهم‌تر از syntaxه. هر مثال رو با این سه سؤال بخون: الان چه چیزی در حال اجراست؟ چه چیزی فقط منتظره؟ continuation کِی و با چه شرطی برمی‌گرده؟ اگه این سه تا روشن باشن، async دیگه جادو نیست.

In this chapter, the timeline matters more than syntax. Read each example with three questions: what is executing now, what is merely waiting, and when can the continuation resume? Once those are clear, async stops looking like magic.

Task یک نخ نیستA Task is not a thread

Task نمایندهٔ کار/نتیجه‌ای هست که ممکنه هنوز تمام نشده باشه؛ بعضی Taskها I/O رو نمایندگی می‌کنن و هیچ نخِ اختصاصیِ در حال انتظار ندارن. بعضی کارهای CPU با thread pool اجرا می‌شن. compiler متد async رو به state machine تبدیل می‌کنه تا قبل و بعد از هر await، state لازم رو نگه داره. خود کلیدواژهٔ async نه thread می‌سازه و نه متد رو خودکار موازی می‌کنه.

Task represents work or a result that may not be complete; some tasks represent I/O without a dedicated thread waiting. CPU work may run on the thread pool. The compiler transforms an async method into a state machine that preserves what is needed before and after awaits. The async keyword itself creates no thread and does not automatically parallelize a method.

ترتیب اجرا / Execution order
Console.WriteLine("before");
Task<string> pending = client.GetStringAsync(uri);
Console.WriteLine("request started");

string body = await pending;
Console.WriteLine("response received");

بخش متد تا رسیدن به await اجرا می‌شه؛ اگه Task تمام نشده باشه، continuation برای بعد ثبت و کنترل به caller برمی‌گرده. ممکنه Task پیش از await تمام شده باشه و ادامه تقریباً فوری اجرا بشه. پس «async یعنی همیشه در زمان دیگری اجرا می‌شه» هم درست نیست.

The method runs until an await. If the task is incomplete, a continuation is registered and control returns to the caller. The task may already be complete, in which case continuation can proceed immediately. “Async always runs later” is also false.

await نقطهٔ واگذاری کنترل استawait is a point where control can yield

اگه await شده کامل نباشه، متد فعلی نتیجهٔ خود رو به شکل Task برمی‌گردونه، caller هم می‌تونه ادامه دهد؛ وقتی کار تمام شد، continuation ادامه می‌ده و نتیجه یا exception رو تحویل می‌گیره. اگه Task faulted باشه، await exception اصلی رو دوباره پرتاب می‌کنه؛ اگه canceled باشه، cancellation از همین مسیر دیده می‌شه. پس exception رو فقط اطراف ساخت Task نگذار؛ await رو هم در مرز مدیریت خطا در نظر بگیر.

If the awaited operation is incomplete, the current method returns its Task so the caller can continue. When the operation finishes, its continuation resumes and observes the result or exception. If the task faulted, await rethrows the original exception; cancellation is also observed through this path. Handle failures at the await boundary, not only when creating a task.

await در مسیر خطا / Await at the failure boundary
try
{
    return await LoadAsync(cancellationToken);
}
catch (HttpRequestException ex)
{
    logger.LogWarning(ex, "Remote service unavailable");
    throw;
}

exception رو اگه نمی‌تونی به نتیجهٔ معنادار تبدیل کنی، با throw; دوباره پرتاب کن تا stack trace حفظ بشه؛ throw ex; مسیر قبلی رو خراب می‌کنه. Cancellation رو هم به‌عنوان نتیجهٔ معمول خطای شبکه قورت نده.

If you cannot map the exception to a meaningful result, rethrow with throw; to preserve the stack trace; throw ex; resets it. Do not swallow cancellation as an ordinary network error.

ادامهٔ متد کجا اجرا می‌شه؟Where does a continuation run?

continuation می‌تونه به synchronization context قبلی برگردد؛ در UI این معمولاً همان thread رابط هست، اما در برنامهٔ معمول ASP.NET Core چنین context اختصاصیِ قدیمی وجود نداره. کتابخانه‌ها گاهی ConfigureAwait(false) می‌ذارن تا درخواست بازگشت به context ندهند؛ در کد UI که بعداً به کنترل دست می‌زنه باید context رو حفظ کند. این تنظیم راه‌حل عمومی performance یا deadlock نیست.

A continuation may return to the captured synchronization context; in UI apps that is commonly the UI thread, while typical ASP.NET Core code does not have the old dedicated request context. Libraries sometimes use ConfigureAwait(false) to avoid requiring context capture; UI code that later accesses controls must preserve it. This is not a universal performance or deadlock fix.

این تفاوت، علت بعضی deadlockهای کد قدیمی رو هم توضیح می‌ده: thread منتظر Task می‌مونه، continuation منتظر همان context مسدودشده هست. درمان معمول، async کردن کل زنجیره و پرهیز از .Result/.Wait() هست، نه دست‌کاری تصادفی context.

This also explains some deadlocks in older code: a thread blocks waiting for a task while its continuation waits for the blocked context. The usual fix is async all the way and avoiding .Result/.Wait(), not random context manipulation.

برای CPU، Task.Run فقط جابه‌جایی نخ استFor CPU work, Task.Run only moves the work

تصویرسازی سنگین رو روی thread UI اجرا نکن؛ انتقال به thread pool responsiveness رو بهتر می‌کنه اما محاسبه همچنان CPU مصرف می‌کنه. در server، اگه هر درخواست کار CPU رو به pool بفرستد، فشار فقط جابه‌جا می‌شه و thread pool می‌تونه اشباع بشه. الگوریتم، محدودیت هم‌زمانی یا worker اختصاصی شاید تصمیم بهتری باشه. I/O رو با Task.Run «ناهمگام» نکن؛ API async واقعی رو صدا بزن.

Do not run expensive rendering on the UI thread; moving it to the thread pool improves responsiveness but still consumes CPU. On a server, sending every request’s CPU work to the pool only moves the pressure and may saturate the pool. An algorithmic improvement, concurrency bound or dedicated worker may be better. Do not “async-ify” I/O with Task.Run; call a real asynchronous API.

محاسبهٔ CPU در UI / CPU work in a UI
Result result = await Task.Run(
    () => ExpensiveCalculation(input),
    cancellationToken);

Render(result); // resumes in the UI context when captured

نمونه برای UI هست؛ در ASP.NET Core به‌عنوان wrapper عمومی استفاده نکن. تابع محاسبه باید cancellation رو درون حلقه هم بررسی کند؛ tokenِ overload به‌تنهایی کار synchronous شروع‌شده رو وسط محاسبه متوقف نمی‌کنه.

This example targets UI code; do not use it as a general ASP.NET Core wrapper. The computation itself must check cancellation inside its loop; the overload token alone cannot interrupt already-running synchronous work.

ترتیب، موازی‌سازی و fire-and-forgetSequencing, concurrency and fire-and-forget

دو درخواست مستقل رو اگه پشت سر هم await کنی، زمان انتظار جمع می‌شه. هر دو Task رو شروع و بعد WhenAll کن؛ اما کار هم‌زمان، rate limit و ظرفیت رو نادیده نمی‌گیره. Task رو رها نکنی: خطا، cancellation و عمر dependency از دست می‌رن. fire-and-forget واقعی در سرویس معمولاً باید به queue/background service با مالکیت و مشاهده‌پذیری مشخص تبدیل بشه.

Sequentially awaiting independent requests adds their waiting times. Start both tasks and await WhenAll, but concurrency does not bypass rate limits or capacity. Do not abandon a task: its failures, cancellation and dependency lifetime are lost. In a service, fire-and-forget work usually belongs in a queue or background service with clear ownership and observability.

کارهای مستقل / Independent operations
Task<Profile> profileTask = GetProfileAsync(id, ct);
Task<Orders> ordersTask = GetOrdersAsync(id, ct);

await Task.WhenAll(profileTask, ordersTask);
return new Dashboard(await profileTask, await ordersTask);

وقتی یکی شکست بخورد، WhenAll پس از پایان Taskهای ورودی fault می‌شه؛ بقیه خودکار لغو نمی‌شن. اگه شکست یکی باید دیگری رو متوقف کند، linked cancellation و سیاست cleanup اضافه کن. تعداد Taskهای بی‌حد هم با semaphore/صف محدود می‌شه؛ فصل Taskها این مرز رو کامل می‌کنه.

If one task fails, WhenAll faults after its inputs finish; the others are not automatically cancelled. If one failure should stop the rest, add linked cancellation and cleanup policy. Unbounded task creation also needs a semaphore or queue; the next task chapter develops that boundary.
