قرارداد مجموعه‌ها

Collection contracts

یک متد گزارش فقط سفارش‌ها را می‌خواند، اما امضایش List می‌خواهد. callerای که آرایه یا query lazy دارد مجبور می‌شود بی‌دلیل تبدیل کند. از آن طرف، اگر متد قرار است عضو اضافه کند، IEnumerable کافی نیست. قرارداد مجموعه را از کاری انتخاب می‌کنیم که متد واقعاً انجام می‌دهد.

A report method only reads orders, yet its signature demands List<Order>. A caller with an array or lazy query must convert unnecessarily. Conversely, if the method adds items, IEnumerable is insufficient. Choose the collection contract from what the method actually does.

فصل ۲۴پیش‌نیازprerequisite

نوع concrete در امضا یعنی انتخاب پیاده‌سازی را تحمیل کرده‌ایA concrete type in the signature dictates implementation choice

اگر تابع فقط پیمایش می‌خواهد، List بیش از نیازش اختیار و الزام ایجاد می‌کند. caller را مجبور می‌کند همان concrete collection را بسازد. امضا را به کمترین قابلیت لازم تغییر می‌دهیم؛ نه برای abstraction نمایشی، بلکه برای اینکه caller بتواند منبع دادهٔ خودش را بدهد.

If a function only needs enumeration, List<Order> requires more than necessary and dictates a concrete collection. The caller must construct that implementation. We narrow the signature to the minimum needed—not for decorative abstraction, but so callers can supply their own source.

از List به IEnumerable / Narrowing the requirement
static decimal TotalFor(List<Order> orders)
{
    decimal total = 0m;
    foreach (var order in orders)
        total += order.Total;
    return total;
}

static decimal TotalFor(IEnumerable<Order> orders)
{
    decimal total = 0m;
    foreach (var order in orders)
        total += order.Total;
    return total;
}

نسخهٔ دوم آرایه، List یا iterator را می‌پذیرد. ولی IEnumerable قول نمی‌دهد پیمایش ارزان، تکرارپذیر یا بدون اثر جانبی باشد. اگر متد چند بار enumerate کند، query ممکن است دوباره اجرا شود؛ قرارداد کوچک‌تر الزاماً هزینهٔ عملیاتی کمتر نیست.

The second accepts an array, List or iterator. But IEnumerable does not promise cheap, repeatable or side-effect-free enumeration. If the method enumerates repeatedly, a query may execute again; a smaller contract does not automatically mean lower operational cost.

هر interface قابلیت متفاوتی قول می‌دهدEach interface promises different capabilities

نوعContractچه کارهایی را تضمین می‌کند؟What it promises
IEnumerable<T>پیمایشEnumerateفقط گرفتن enumerator و دیدن آیتم‌هاObtain an enumerator and read items

این interfaceها تضمین performance خاص نمی‌دهند مگر خود مستندات type چنین بگویند. IReadOnlyList مثلاً O(1) index را فقط از interface استنتاج نکن؛ پیاده‌سازی واقعی را بشناس. interface بیشتر قرارداد قابلیت است تا benchmark.

These interfaces do not promise particular performance unless the type’s documentation says so. Do not infer O(1) indexing from IReadOnlyList alone; know the implementation. An interface is primarily a capability contract, not a benchmark.

ورودی را باریک بگیر؛ خروجی را با رفتار روشن بدهAccept narrow inputs; return clear behaviour

برای ورودی‌ای که فقط پیمایش می‌شود، IEnumerable اغلب کافی است؛ برای خروجی‌ای که caller باید دوباره و با index بخواند، IReadOnlyList ممکن است معنای مناسب‌تری بدهد. اما IReadOnlyList تضمین immutability نیست: اگر همان backing List بیرون تغییر کند، مشاهدهٔ caller هم عوض می‌شود.

For an input that is only enumerated, IEnumerable<T> is often enough; for a result callers need to revisit and index, IReadOnlyList<T> may be clearer. But IReadOnlyList does not guarantee immutability: if the backing List changes elsewhere, callers observe the change.

متد فقط می‌خواند / A read-only consumer
static IReadOnlyList<string> ActiveNames(IEnumerable<Order> orders)
{
    var result = new List<string>();
    foreach (var order in orders)
        if (order.IsActive)
            result.Add(order.CustomerName);
    return result;
}

داخل تابع مالک result هستیم و caller قرارداد index/read دارد؛ اما اگر نیاز به snapshot تغییرناپذیر واقعی باشد، باید backing storage را هم از mutation محافظت کنیم یا copy/immutable collection مناسب بسازیم. اسم interface به‌تنهایی مرز مالکیت ایجاد نمی‌کند.

The method owns result and callers receive an indexed read contract. If a truly immutable snapshot is required, protect the backing storage from mutation or create an appropriate copy/immutable collection. The interface name alone does not establish ownership.

اگر باید تغییر بدهی، mutation را در قرارداد پنهان نکنIf you mutate, do not hide it in the contract

ICollection به caller می‌گوید متد می‌تواند Add و Remove انجام دهد؛ IEnumerable چنین وعده‌ای نمی‌دهد. اگر فقط به خروجی builder نیاز داری، شاید بهتر باشد concrete ساخت را داخل متد نگه داری و در پایان view یا نتیجهٔ مشخص برگردانی. API نباید caller را برای تغییری که نمی‌تواند انجام دهد بشکند.

ICollection<T> tells callers the method can add and remove; IEnumerable makes no such promise. If you only need an output builder, keep the concrete construction inside and return a clear result/view. Do not expose mutation the caller cannot meaningfully perform.

builder با قرارداد mutable / Mutable collection contract
static void AddExpensiveOrders(
    IEnumerable<Order> source,
    ICollection<Order> destination)
{
    foreach (var order in source)
        if (order.Total >= 1_000m)
            destination.Add(order);
}

source فقط enumerate می‌شود؛ destination باید Add داشته باشد. اگر مقصد read-only باشد، implementation ممکن است با NotSupportedException شکست بخورد؛ قابلیت interface همیشه تضمین نمی‌کند هر instance همهٔ عملیات را پشتیبانی کند. exception policy را مستند یا ورودی را از نظر قابلیت مناسب طراحی کن.

The source is only enumerated; the destination needs Add. A read-only destination may fail with NotSupportedException, so an interface capability does not guarantee every instance supports every operation. Document the failure or choose an input contract that better represents the requirement.

برای lookup، sequence را به dictionary تبدیل نکن مگر نیازش هستUse a dictionary for lookup only when you need keyed access

اگر caller شمارهٔ سفارش را می‌داند و بارها دنبال همان شماره می‌گردد، IDictionary یا IReadOnlyDictionary ممکن است قرارداد مناسبی باشد. اگر فقط یک‌بار روی همهٔ سفارش‌ها فیلتر می‌کنی، dictionary اضافی هزینهٔ ساخت و حافظه دارد. الگوی دسترسی، نوع قرارداد را تعیین می‌کند.

If callers know an order number and repeatedly look it up, IDictionary or IReadOnlyDictionary may fit. If they filter all orders once, building a dictionary adds construction and memory cost. Access pattern determines the contract.

lookup با کلید / Keyed lookup
static bool TryFind(
    IReadOnlyDictionary<string, Order> ordersByNumber,
    string number,
    out Order? order)
    => ordersByNumber.TryGetValue(number, out order);

IReadOnlyDictionary به caller امکان lookup می‌دهد اما عملیات تغییر را از قرارداد عمومی حذف می‌کند. این هم تضمین deep immutability نیست؛ مالک backing collection باید مشخص باشد. comparer کلیدها و رفتار case را هم برای شناسهٔ ماشینی صریح انتخاب کن.

IReadOnlyDictionary exposes lookup while omitting mutation from the public contract. It still does not promise deep immutability; backing ownership must be clear. Choose key comparer and case behaviour explicitly for machine identifiers.

معیار پایانDefinition of done

هیچ متدی فقط به‌خاطر استفاده از List concrete آن را تحمیل نمی‌کند؛ mutation و indexing از امضا مشخص‌اند؛ و lazy enumeration یا read-only view به‌اشتباه snapshot/immutability فرض نشده‌اند.

No method demands List without need; mutation and indexing are visible in signatures; and lazy enumeration or read-only views are not mistaken for snapshots or immutability.

اگر فقط یک بار پیمایش لازم است ورودی را IEnumerable کن؛ دوباره‌پیمایی، Count یا side effect منبع را بررسی کن. caller را بی‌دلیل materialize نکن.

کمترین قابلیت لازم را درخواست کنRequest only the capability you need

IEnumerable برای پیمایش، IReadOnlyCollection برای count، IReadOnlyList برای index، ICollection/IList برای mutation و IDictionary برای lookup کلیدی است. هیچ‌کدام به‌تنهایی performance یا immutability را تضمین نمی‌کنند. فصل بعد پیاده‌سازی‌های concrete را با الگوی دسترسی مقایسه می‌کنیم تا فقط از روی اسم collection انتخاب نکنیم.

IEnumerable supports enumeration, IReadOnlyCollection adds a count, IReadOnlyList adds indexing, ICollection/IList add mutation, and IDictionary supports keyed lookup. None alone guarantees performance or immutability. Next we compare concrete implementations against access patterns instead of choosing by collection name.
