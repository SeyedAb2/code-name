قرارداد مجموعه‌ها

Collection contracts

یک متد گزارش فقط سفارش‌ها رو می‌خونه، اما امضایش List می‌خواد. callerای که آرایه یا query lazy داره مجبور می‌شه بی‌دلیل تبدیل کند. از آن طرف، اگه متد قرار هست عضو اضافه کند، IEnumerable کافی نیست. قرارداد مجموعه رو از کاری انتخاب می‌کنیم که متد واقعاً انجام می‌ده.

A report method only reads orders, yet its signature demands List<Order>. A caller with an array or lazy query must convert unnecessarily. Conversely, if the method adds items, IEnumerable is insufficient. Choose the collection contract from what the method actually does.

فصل ۲۴پیش‌نیازprerequisite

نوع concrete در امضا یعنی انتخاب پیاده‌سازی رو تحمیل کرده‌ایA concrete type in the signature dictates implementation choice

اگه تابع فقط پیمایش می‌خواد، List بیش از نیازش اختیار و الزام ایجاد می‌کنه. caller رو مجبور می‌کنه همان concrete collection رو بسازد. امضا رو به کمترین قابلیت لازم تغییر می‌دهیم؛ نه برای abstraction نمایشی، بلکه برای اینکه caller بتواند منبع دادهٔ خودش رو بدهد.

If a function only needs enumeration, List<Order> requires more than necessary and dictates a concrete collection. The caller must construct that implementation. We narrow the signature to the minimum needed—not for decorative abstraction, but so callers can supply their own source.

از List به IEnumerable / Narrowing the requirement
static decimal TotalFor(List<Order> orders)
{
    decimal total = 0m;
    foreach (var order in orders)
        total += order.Total;
    return total;
}

static decimal TotalFor(IEnumerable<Order> orders)
{
    decimal total = 0m;
    foreach (var order in orders)
        total += order.Total;
    return total;
}

نسخهٔ دوم آرایه، List یا iterator رو می‌پذیره. ولی IEnumerable قول نمی‌ده پیمایش ارزان، تکرارپذیر یا بدون اثر جانبی باشه. اگه متد چند بار enumerate کند، query ممکنه دوباره اجرا بشه؛ قرارداد کوچک‌تر الزاماً هزینهٔ عملیاتی کمتر نیست.

The second accepts an array, List or iterator. But IEnumerable does not promise cheap, repeatable or side-effect-free enumeration. If the method enumerates repeatedly, a query may execute again; a smaller contract does not automatically mean lower operational cost.

اول operation رو انتخاب کن، بعد collection روChoose the operation first, then the collection

وقتی کسی می‌پرسه «بهترین collection چیه؟» سؤال هنوز ناقصه. بهترین برای چی؟ جست‌وجوی کلید؟ حفظ ترتیب ورود؟ یکتا بودن؟ برداشتن اول صف؟ همین workload تصمیم رو می‌سازه. اسم typeها رو حفظ کنی ولی operation اصلی رو ندونی، انتخابت شانسی می‌شه.

When someone asks “what is the best collection?”, the question is incomplete. Best for what: key lookup, insertion order, uniqueness, FIFO, or priority? The workload chooses the structure. Memorizing type names without identifying the dominant operation turns the decision into guesswork.

این فصل اول interfaceها رو به‌عنوان قرارداد می‌بینه و بعد سراغ implementation می‌ره. هدف اینه که API رو تا جایی که لازمه محدود نگه داری؛ متدی که فقط enumerate می‌کنه لازم نیست بی‌دلیل `List<T>` مطالبه کنه.

This chapter starts with collection interfaces as contracts and only then moves toward implementations. The goal is to keep an API as narrow as its needs; a method that only enumerates data usually has no reason to demand a `List<T>`.

این interfaceها تضمین performance خاص نمی‌دن مگر خود مستندات type چنین بگویند. IReadOnlyList مثلاً O(1) index رو فقط از interface استنتاج نکن؛ پیاده‌سازی واقعی رو بشناس. interface بیشتر قرارداد قابلیت هست تا benchmark.

These interfaces do not promise particular performance unless the type’s documentation says so. Do not infer O(1) indexing from IReadOnlyList alone; know the implementation. An interface is primarily a capability contract, not a benchmark.

ورودی رو باریک بگیر؛ خروجی رو با رفتار روشن بدهAccept narrow inputs; return clear behaviour

برای ورودی‌ای که فقط پیمایش می‌شه، IEnumerable اغلب کافی هست؛ برای خروجی‌ای که caller باید دوباره و با index بخواند، IReadOnlyList ممکنه معنای مناسب‌تری بدهد. اما IReadOnlyList تضمین immutability نیست: اگه همان backing List بیرون تغییر کند، مشاهدهٔ caller هم عوض می‌شه.

For an input that is only enumerated, IEnumerable<T> is often enough; for a result callers need to revisit and index, IReadOnlyList<T> may be clearer. But IReadOnlyList does not guarantee immutability: if the backing List changes elsewhere, callers observe the change.

متد فقط می‌خواند / A read-only consumer
static IReadOnlyList<string> ActiveNames(IEnumerable<Order> orders)
{
    var result = new List<string>();
    foreach (var order in orders)
        if (order.IsActive)
            result.Add(order.CustomerName);
    return result;
}

داخل تابع مالک result هستیم و caller قرارداد index/read داره؛ اما اگه نیاز به snapshot تغییرناپذیر واقعی باشه، باید backing storage رو هم از mutation محافظت کنیم یا copy/immutable collection مناسب بسازیم. اسم interface به‌تنهایی مرز مالکیت ایجاد نمی‌کنه.

The method owns result and callers receive an indexed read contract. If a truly immutable snapshot is required, protect the backing storage from mutation or create an appropriate copy/immutable collection. The interface name alone does not establish ownership.

اگه باید تغییر بدهی، mutation رو در قرارداد پنهان نکنIf you mutate, do not hide it in the contract

ICollection به caller می‌گه متد می‌تونه Add و Remove انجام دهد؛ IEnumerable چنین وعده‌ای نمی‌ده. اگه فقط به خروجی builder نیاز داری، شاید بهتر باشه concrete ساخت رو داخل متد نگه داری و در پایان view یا نتیجهٔ مشخص برگردانی. API نباید caller رو برای تغییری که نمی‌تونه انجام دهد بشکند.

ICollection<T> tells callers the method can add and remove; IEnumerable makes no such promise. If you only need an output builder, keep the concrete construction inside and return a clear result/view. Do not expose mutation the caller cannot meaningfully perform.

builder با قرارداد mutable / Mutable collection contract
static void AddExpensiveOrders(
    IEnumerable<Order> source,
    ICollection<Order> destination)
{
    foreach (var order in source)
        if (order.Total >= 1_000m)
            destination.Add(order);
}

source فقط enumerate می‌شه؛ destination باید Add داشته باشه. اگه مقصد read-only باشه، implementation ممکنه با NotSupportedException شکست بخورد؛ قابلیت interface همیشه تضمین نمی‌کنه هر instance همهٔ عملیات رو پشتیبانی کند. exception policy رو مستند یا ورودی رو از نظر قابلیت مناسب طراحی کن.

The source is only enumerated; the destination needs Add. A read-only destination may fail with NotSupportedException, so an interface capability does not guarantee every instance supports every operation. Document the failure or choose an input contract that better represents the requirement.

برای lookup، sequence رو به dictionary تبدیل نکن مگر نیازش هستUse a dictionary for lookup only when you need keyed access

اگه caller شمارهٔ سفارش رو می‌دونه و بارها دنبال همان شماره می‌گردد، IDictionary یا IReadOnlyDictionary ممکنه قرارداد مناسبی باشه. اگه فقط یک‌بار روی همهٔ سفارش‌ها فیلتر می‌کنی، dictionary اضافی هزینهٔ ساخت و حافظه داره. الگوی دسترسی، نوع قرارداد رو تعیین می‌کنه.

If callers know an order number and repeatedly look it up, IDictionary or IReadOnlyDictionary may fit. If they filter all orders once, building a dictionary adds construction and memory cost. Access pattern determines the contract.

lookup با کلید / Keyed lookup
static bool TryFind(
    IReadOnlyDictionary<string, Order> ordersByNumber,
    string number,
    out Order? order)
    => ordersByNumber.TryGetValue(number, out order);

IReadOnlyDictionary به caller امکان lookup می‌ده اما عملیات تغییر رو از قرارداد عمومی حذف می‌کنه. این هم تضمین deep immutability نیست؛ مالک backing collection باید مشخص باشه. comparer کلیدها و رفتار case رو هم برای شناسهٔ ماشینی صریح انتخاب کن.

IReadOnlyDictionary exposes lookup while omitting mutation from the public contract. It still does not promise deep immutability; backing ownership must be clear. Choose key comparer and case behaviour explicitly for machine identifiers.
