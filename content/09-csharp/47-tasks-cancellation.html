Task، لغو و مهلت

Tasks, cancellation and timeouts

صفحه برای ۲۰۰ شناسه، ۲۰۰ درخواست موازی می‌سازه؛ سرویس بیرونی rate limit می‌ده و وقتی کاربر صفحه رو می‌بندد، درخواست‌ها ادامه دارن. WhenAll رو داریم، اما خودش نه سقف هم‌زمانی هست و نه دکمهٔ لغو. باید مالک هر Task، ظرفیت سیستم و معنی «لغو شد» رو روشن کنیم.

A page creates 200 requests for 200 IDs; the remote service rate-limits us, and calls continue after the user leaves. We have WhenAll, but it is neither a concurrency limit nor a cancellation button. We need clear task ownership, system capacity and a precise meaning for “cancelled.”

فصل ۴۶پیش‌نیازprerequisite

Task رو جایی بساز که مالک نتیجه استCreate tasks where their result is owned

متد async تا اولین await اجرا می‌شه و Task رو برمی‌گردونه؛ ساخت Task معمولاً به معنی «فرستادن به صف thread pool» نیست. اگه نتیجهٔ کار برای پاسخ لازمه، await کن. اگه کار باید بعد از پایان درخواست هم ادامه پیدا کند، به lifecycle درخواست گره‌اش نزن؛ آن رو به queue یا hosted service با ثبت خطا و shutdown بده. task رهاشده معمولاً کار پنهان هست.

An async method runs until its first incomplete await and returns a task; creating a task does not usually mean queuing it to the thread pool. If the result is needed for the response, await it. If work must outlive the request, do not tie it to request lifetime—hand it to a queue or hosted service with error tracking and shutdown ownership. An abandoned task is hidden work.

Taskها رو شروع‌کردن آسونه؛ مالکیت پایانشون مهم‌ترهStarting tasks is easy; owning their completion matters more

`WhenAll` خیلی تمیز به نظر می‌رسه، ولی سؤال واقعی اینه که اگه یکی fail شد بقیه چی می‌شن؟ cancellation از کجا میاد؟ timeout کی تصمیم می‌گیره؟ caller چطور می‌فهمه عملیات نیمه‌کاره مونده؟ این فصل Task رو از یه object منتظرشدنی به یه قرارداد کامل‌تر برای نتیجه، خطا و لغو تبدیل می‌کنه.

`WhenAll` looks clean, but the real questions are what happens to the other operations when one fails, where cancellation originates, who owns a timeout, and how the caller learns that work ended early. This chapter turns a Task from “something awaitable” into a contract for result, failure, and cancellation.

هر cancellation token باید یه owner داشته باشه. token رو فقط چون API قبول می‌کنه پاس نده؛ مشخص کن چه کسی حق داره عملیات رو لغو کنه و کد پایین‌دست چقدر سریع باید به اون تصمیم واکنش نشون بده.

Every cancellation token should have an owner. Do not pass a token merely because an API accepts one; decide who is allowed to cancel the operation and how quickly downstream work should observe that decision.

WhenAll همه رو جمع می‌کنه؛ concurrency رو محدود نمی‌کنهWhenAll joins tasks; it does not limit concurrency

اگه تعداد ورودی ثابت و کم هست، Taskها رو بساز و WhenAll کن. اگه ۲۰ هزار ورودی داری، ساختن همهٔ Taskها از همان ابتدا حافظه و سرویس مقصد رو تحت فشار می‌ذاره؛ صف محدود یا worker با ظرفیت مشخص بساز. هنگام شکست یکی، WhenAll تا پایان همهٔ taskهای داده‌شده کامل نمی‌شه و siblingها رو خودکار لغو نمی‌کنه.

For a small, fixed set, create tasks and await WhenAll. For 20,000 inputs, creating every task at once burdens memory and the remote service; use a bounded queue or workers with explicit capacity. If one fails, WhenAll completes after its supplied tasks finish and does not automatically cancel siblings.

محدودکردن هم‌زمانی / Bound concurrency
using var gate = new SemaphoreSlim(8);
Task<Result>[] tasks = ids.Select(async id =>
{
    await gate.WaitAsync(cancellationToken);
    try
    {
        return await FetchAsync(id, cancellationToken);
    }
    finally
    {
        gate.Release();
    }
}).ToArray();

Result[] results = await Task.WhenAll(tasks);

این نمونه ساخت همهٔ Taskها رو هنوز نگه می‌داره ولی فقط ۸ عملیات رو هم‌زمان جلو می‌بره. برای ورودی واقعاً بزرگ، workerهای محدود یا Parallel.ForEachAsync با MaxDegreeOfParallelism مناسب‌ترند. عدد ۸ از نیاز و rate limit میاد، نه قاعدهٔ ثابت.

This still creates a task per input but runs only eight operations concurrently. For very large inputs, bounded workers or Parallel.ForEachAsync with a maximum degree of parallelism may be better. Eight is a workload/rate-limit choice, not a universal constant.

cancellation درخواست محترمانهٔ توقف استCancellation is a cooperative stop request

توکن لغو سیگنال هست؛ خودش thread رو نمی‌کشه و هر API هم الزاماً آن رو نمی‌پذیره. عملیات باید token رو دریافت کند، آن رو به پایین‌دست بدهد و در کار CPU دوره‌ای بررسی کند. ThrowIfCancellationRequested لغو رو به مسیر استانداره OperationCanceledException می‌بره. اگه زیرکار cancel نمی‌پذیره، باید دقیق بگویی می‌خوای خود عملیات متوقف بشه یا فقط انتظار caller.

A cancellation token is a signal; it does not kill a thread, and not every API accepts one. Operations should receive the token, pass it downstream and periodically check it in CPU work. ThrowIfCancellationRequested raises the standard OperationCanceledException. If a child operation cannot be cancelled, decide whether to stop the operation or only the caller’s wait.

کار CPU هم باید همکاری کند / CPU work must cooperate
static long CountMatches(
    IEnumerable<string> rows, CancellationToken ct)
{
    long count = 0;
    foreach (string row in rows)
    {
        ct.ThrowIfCancellationRequested();
        if (row.Contains("ERROR", StringComparison.Ordinal)) count++;
    }
    return count;
}

در حلقهٔ کوتاه check فراوان هزینه داره؛ فاصلهٔ بررسی رو با اندازه‌گیری انتخاب کن. cancellation پس از اتمام طبیعی دیگر کار رو برنمی‌گرداند؛ race بین completion و cancel بخشی از قرارداد مصرف‌کننده هست.

Checking too frequently in a tight loop has a cost; choose a check interval based on measurement. Cancellation after natural completion cannot undo work; the race between completion and cancellation is part of the caller’s contract.

deadline و لغو caller رو linked کن، اما علت رو نگه دارLink caller cancellation and deadline, but preserve the cause

یک درخواست ممکنه از caller لغو بشه یا deadline خودش تمام بشه. linked token هر دو رو به operation می‌رساند، اما telemetry باید بفهمد کدوم رخ داده. از CancelAfter برای deadline استفاده و منبع رو dispose کن؛ مدت زمان رو برای هر مرحله دوباره از نو شروع نکن اگه قرارداد یک deadline کل درخواست هست.

An operation may be cancelled by its caller or exceed its own deadline. A linked token delivers both signals, but telemetry should retain which cause occurred. Use CancelAfter for a deadline and dispose its source; do not restart the full duration at each step if the contract defines one end-to-end deadline.

token لینک‌شده / Linked token
using var deadline = CancellationTokenSource.CreateLinkedTokenSource(
    callerToken);
deadline.CancelAfter(TimeSpan.FromSeconds(3));

try
{
    return await FetchAsync(deadline.Token);
}
catch (OperationCanceledException) when (callerToken.IsCancellationRequested)
{
    logger.LogInformation("Caller cancelled the operation");
    throw;
}
catch (OperationCanceledException) when (deadline.IsCancellationRequested)
{
    throw new TimeoutException("Operation deadline elapsed");
}

ترتیب filterها مهمه؛ اگه caller cancellation و deadline تقریباً هم‌زمان بشن، policy باید tie رو تعریف کند. بعضی APIها برای timeout exception اختصاصی دارن؛ آن رو دوباره به شکل generic cancellation پنهان نکن.

Filter order matters; if caller cancellation and deadline happen together, define a tie policy. Some APIs provide a dedicated timeout exception; do not hide it as generic cancellation.

WhenAny می‌گه کدوم تمام شد، بقیه رو نهWhenAny identifies the winner, not what happens to the rest

WhenAny Task تمام‌شدهٔ اول رو می‌ده—even اگه fault یا cancel شده باشه؛ باید خود Task برنده رو await کنی تا نتیجه‌اش رو ببینی. باقی taskها همچنان اجرا می‌شن. اگه race برای timeout هست، timeout شدن wait لزوماً عملیات اصلی رو متوقف نمی‌کنه؛ token رو به operation بده و آن رو لغو کن، سپس تا حد ممکن cleanup و مشاهدهٔ نتیجه رو انجام بده.

WhenAny returns the first completed task—even if it faulted or was cancelled; await the winning task to observe its outcome. The others keep running. If racing against a timeout, timing out the wait does not necessarily stop the operation; pass a token into the operation, cancel it and observe cleanup/result where possible.

مهلت با Task.WaitAsync / Deadline with Task.WaitAsync
using var operationCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
Task<Data> operation = LoadAsync(operationCts.Token);

try
{
    return await operation.WaitAsync(TimeSpan.FromSeconds(2), ct);
}
catch (TimeoutException)
{
    operationCts.Cancel(); // cooperative request to stop underlying work
    try { await operation; }
    catch (OperationCanceledException) { }
    throw;
}

این الگو برای APIهایی هست که token رو رعایت می‌کنن؛ اگه operation cancellation رو نادیده بگیرد، await cleanup می‌تونه همچنان طولانی بشه و فقط wait رو لغو کرده‌ای. انتخاب بین «لغو wait» و «لغو operation» رو در API مستند کن.

This works for APIs that honor cancellation; if an operation ignores the token, awaiting cleanup may still take a long time, and only the wait was cancelled. Document whether your API cancels the wait or the operation.

لغو، خطا و شکست جزئی رو جدا گزارش کنReport cancellation, faults and partial failure separately

یک batch ممکنه چند موفقیت و چند شکست داشته باشه. اگه به محض exception از WhenAll خارج شوی، نتیجه‌های موفق رو دیگر جمع نمی‌کنی؛ اگه نیاز محصول گزارش partial هست، هر ورودی رو به نتیجهٔ success/failure تبدیل و در پایان summary بساز. cancellation کل batch می‌تونه همه رو متوقف کند، اما ممکنه قبلش تعدادی تغییر دائمی انجام شده باشه—لغو transaction جادویی نیست.

A batch can contain successes and failures. If you exit on a WhenAll exception, you may never collect successful results. If the product needs partial reporting, map each input to a success/failure result and summarize afterward. Cancelling a batch can stop remaining work, but some writes may already be durable—cancellation is not a transaction rollback.
