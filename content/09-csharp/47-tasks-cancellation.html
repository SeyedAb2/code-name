Task، لغو و مهلت

Tasks, cancellation and timeouts

صفحه برای ۲۰۰ شناسه، ۲۰۰ درخواست موازی می‌سازد؛ سرویس بیرونی rate limit می‌دهد و وقتی کاربر صفحه را می‌بندد، درخواست‌ها ادامه دارند. WhenAll را داریم، اما خودش نه سقف هم‌زمانی است و نه دکمهٔ لغو. باید مالک هر Task، ظرفیت سیستم و معنی «لغو شد» را روشن کنیم.

A page creates 200 requests for 200 IDs; the remote service rate-limits us, and calls continue after the user leaves. We have WhenAll, but it is neither a concurrency limit nor a cancellation button. We need clear task ownership, system capacity and a precise meaning for “cancelled.”

Task را جایی بساز که مالک نتیجه استCreate tasks where their result is owned

متد async تا اولین await اجرا می‌شود و Task را برمی‌گرداند؛ ساخت Task معمولاً به معنی «فرستادن به صف thread pool» نیست. اگر نتیجهٔ کار برای پاسخ لازم است، await کن. اگر کار باید بعد از پایان درخواست هم ادامه پیدا کند، به lifecycle درخواست گره‌اش نزن؛ آن را به queue یا hosted service با ثبت خطا و shutdown بده. task رهاشده معمولاً کار پنهان است.

An async method runs until its first incomplete await and returns a task; creating a task does not usually mean queuing it to the thread pool. If the result is needed for the response, await it. If work must outlive the request, do not tie it to request lifetime—hand it to a queue or hosted service with error tracking and shutdown ownership. An abandoned task is hidden work.

WhenAll همه را جمع می‌کند؛ concurrency را محدود نمی‌کندWhenAll joins tasks; it does not limit concurrency

اگر تعداد ورودی ثابت و کم است، Taskها را بساز و WhenAll کن. اگر ۲۰ هزار ورودی داری، ساختن همهٔ Taskها از همان ابتدا حافظه و سرویس مقصد را تحت فشار می‌گذارد؛ صف محدود یا worker با ظرفیت مشخص بساز. هنگام شکست یکی، WhenAll تا پایان همهٔ taskهای داده‌شده کامل نمی‌شود و siblingها را خودکار لغو نمی‌کند.

For a small, fixed set, create tasks and await WhenAll. For 20,000 inputs, creating every task at once burdens memory and the remote service; use a bounded queue or workers with explicit capacity. If one fails, WhenAll completes after its supplied tasks finish and does not automatically cancel siblings.

محدودکردن هم‌زمانی / Bound concurrency
using var gate = new SemaphoreSlim(8);
Task<Result>[] tasks = ids.Select(async id =>
{
    await gate.WaitAsync(cancellationToken);
    try
    {
        return await FetchAsync(id, cancellationToken);
    }
    finally
    {
        gate.Release();
    }
}).ToArray();

Result[] results = await Task.WhenAll(tasks);

این نمونه ساخت همهٔ Taskها را هنوز نگه می‌دارد ولی فقط ۸ عملیات را هم‌زمان جلو می‌برد. برای ورودی واقعاً بزرگ، workerهای محدود یا Parallel.ForEachAsync با MaxDegreeOfParallelism مناسب‌ترند. عدد ۸ از نیاز و rate limit می‌آید، نه قاعدهٔ ثابت.

This still creates a task per input but runs only eight operations concurrently. For very large inputs, bounded workers or Parallel.ForEachAsync with a maximum degree of parallelism may be better. Eight is a workload/rate-limit choice, not a universal constant.

cancellation درخواست محترمانهٔ توقف استCancellation is a cooperative stop request

توکن لغو سیگنال است؛ خودش thread را نمی‌کشد و هر API هم الزاماً آن را نمی‌پذیرد. عملیات باید token را دریافت کند، آن را به پایین‌دست بدهد و در کار CPU دوره‌ای بررسی کند. ThrowIfCancellationRequested لغو را به مسیر استاندارد OperationCanceledException می‌برد. اگر زیرکار cancel نمی‌پذیرد، باید دقیق بگویی می‌خواهی خود عملیات متوقف شود یا فقط انتظار caller.

A cancellation token is a signal; it does not kill a thread, and not every API accepts one. Operations should receive the token, pass it downstream and periodically check it in CPU work. ThrowIfCancellationRequested raises the standard OperationCanceledException. If a child operation cannot be cancelled, decide whether to stop the operation or only the caller’s wait.

کار CPU هم باید همکاری کند / CPU work must cooperate
static long CountMatches(
    IEnumerable<string> rows, CancellationToken ct)
{
    long count = 0;
    foreach (string row in rows)
    {
        ct.ThrowIfCancellationRequested();
        if (row.Contains("ERROR", StringComparison.Ordinal)) count++;
    }
    return count;
}

در حلقهٔ کوتاه check فراوان هزینه دارد؛ فاصلهٔ بررسی را با اندازه‌گیری انتخاب کن. cancellation پس از اتمام طبیعی دیگر کار را برنمی‌گرداند؛ race بین completion و cancel بخشی از قرارداد مصرف‌کننده است.

Checking too frequently in a tight loop has a cost; choose a check interval based on measurement. Cancellation after natural completion cannot undo work; the race between completion and cancellation is part of the caller’s contract.

deadline و لغو caller را linked کن، اما علت را نگه دارLink caller cancellation and deadline, but preserve the cause

یک درخواست ممکن است از caller لغو شود یا deadline خودش تمام شود. linked token هر دو را به operation می‌رساند، اما telemetry باید بفهمد کدام رخ داده. از CancelAfter برای deadline استفاده و منبع را dispose کن؛ مدت زمان را برای هر مرحله دوباره از نو شروع نکن اگر قرارداد یک deadline کل درخواست است.

An operation may be cancelled by its caller or exceed its own deadline. A linked token delivers both signals, but telemetry should retain which cause occurred. Use CancelAfter for a deadline and dispose its source; do not restart the full duration at each step if the contract defines one end-to-end deadline.

token لینک‌شده / Linked token
using var deadline = CancellationTokenSource.CreateLinkedTokenSource(
    callerToken);
deadline.CancelAfter(TimeSpan.FromSeconds(3));

try
{
    return await FetchAsync(deadline.Token);
}
catch (OperationCanceledException) when (callerToken.IsCancellationRequested)
{
    logger.LogInformation("Caller cancelled the operation");
    throw;
}
catch (OperationCanceledException) when (deadline.IsCancellationRequested)
{
    throw new TimeoutException("Operation deadline elapsed");
}

ترتیب filterها مهم است؛ اگر caller cancellation و deadline تقریباً هم‌زمان شوند، policy باید tie را تعریف کند. بعضی APIها برای timeout exception اختصاصی دارند؛ آن را دوباره به شکل generic cancellation پنهان نکن.

Filter order matters; if caller cancellation and deadline happen together, define a tie policy. Some APIs provide a dedicated timeout exception; do not hide it as generic cancellation.

WhenAny می‌گوید کدام تمام شد، بقیه را نهWhenAny identifies the winner, not what happens to the rest

WhenAny Task تمام‌شدهٔ اول را می‌دهد—even اگر fault یا cancel شده باشد؛ باید خود Task برنده را await کنی تا نتیجه‌اش را ببینی. باقی taskها همچنان اجرا می‌شوند. اگر race برای timeout است، timeout شدن wait لزوماً عملیات اصلی را متوقف نمی‌کند؛ token را به operation بده و آن را لغو کن، سپس تا حد ممکن cleanup و مشاهدهٔ نتیجه را انجام بده.

WhenAny returns the first completed task—even if it faulted or was cancelled; await the winning task to observe its outcome. The others keep running. If racing against a timeout, timing out the wait does not necessarily stop the operation; pass a token into the operation, cancel it and observe cleanup/result where possible.

مهلت با Task.WaitAsync / Deadline with Task.WaitAsync
using var operationCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
Task<Data> operation = LoadAsync(operationCts.Token);

try
{
    return await operation.WaitAsync(TimeSpan.FromSeconds(2), ct);
}
catch (TimeoutException)
{
    operationCts.Cancel(); // cooperative request to stop underlying work
    try { await operation; }
    catch (OperationCanceledException) { }
    throw;
}

این الگو برای APIهایی است که token را رعایت می‌کنند؛ اگر operation cancellation را نادیده بگیرد، await cleanup می‌تواند همچنان طولانی شود و فقط wait را لغو کرده‌ای. انتخاب بین «لغو wait» و «لغو operation» را در API مستند کن.

This works for APIs that honor cancellation; if an operation ignores the token, awaiting cleanup may still take a long time, and only the wait was cancelled. Document whether your API cancels the wait or the operation.

لغو، خطا و شکست جزئی را جدا گزارش کنReport cancellation, faults and partial failure separately

یک batch ممکن است چند موفقیت و چند شکست داشته باشد. اگر به محض exception از WhenAll خارج شوی، نتیجه‌های موفق را دیگر جمع نمی‌کنی؛ اگر نیاز محصول گزارش partial است، هر ورودی را به نتیجهٔ success/failure تبدیل و در پایان summary بساز. cancellation کل batch می‌تواند همه را متوقف کند، اما ممکن است قبلش تعدادی تغییر دائمی انجام شده باشد—لغو transaction جادویی نیست.

A batch can contain successes and failures. If you exit on a WhenAll exception, you may never collect successful results. If the product needs partial reporting, map each input to a success/failure result and summarize afterward. Cancelling a batch can stop remaining work, but some writes may already be durable—cancellation is not a transaction rollback.

سه کار مستقل پشت‌سرهم await می‌شوند؛ latency را با WhenAll مقایسه کن.

همهٔ taskها یک‌جا ساخته می‌شوند؛ concurrency و memory را محدود کن.

All tasks are created at once; bound concurrency and memory.

از workerهای محدود یا Parallel.ForEachAsync با سقف سنجیده استفاده کن.

WhenAll waits for its inputs; create a shared token and explicit cancellation policy.

۴) cancellation بدون همکاری4) Cancellation without cooperation

یک loop token دارد ولی بررسی نمی‌کند؛ cancellation را واقعاً responsive کن.

A loop receives a token but never checks it; make cancellation responsive.

پاسخ فنیTechnical reasoning

در loop یا عملیات پایین‌دست token را check/pass کن؛ token به‌تنهایی اجرا را نمی‌کشد.

Check or propagate the token in the loop/downstream operation; the token does not kill execution by itself.

۵) عملیات و wait5) Operation versus wait

WaitAsync timeout می‌شود اما کار DB ادامه دارد؛ فرق wait cancellation و operation cancellation را ثابت کن.

WaitAsync times out while database work continues; prove the difference between cancelling a wait and an operation.

پاسخ فنیTechnical reasoning

token را به عملیات بده و در timeout cancel کن؛ API بدون token را نمی‌توان الزاماً متوقف کرد.

Pass a token into the operation and cancel it on timeout; an API without cancellation cannot necessarily be stopped.

۶) caller یا deadline6) Caller or deadline?

هر دو OperationCanceledException می‌شوند؛ دو علت را در log و رفتار پاسخ تفکیک کن.

Both produce OperationCanceledException; distinguish their logs and response behavior.

پاسخ فنیTechnical reasoning

token caller و deadline CTS را جدا نگه دار و در catch filter با علت درست classify کن.

Keep caller token and deadline CTS distinct, then classify using filtered catches.

۷) CancellationTokenSource leak7) CancellationTokenSource leak

منبع linked در loop ساخته و dispose نمی‌شود؛ ownership را اصلاح کن.

A linked source is created in a loop and never disposed; fix ownership.

پاسخ فنیTechnical reasoning

هر CTS را در scope مالک با using ببند و فقط پس از اتمام مصرف‌کننده‌ها dispose کن.

Dispose each CTS in its owning scope, only after all consumers have completed.

۸) WhenAny و fault8) WhenAny and faults

اولین Task fault شده ولی برنامه موفقیت اعلام می‌کند؛ نتیجهٔ Task برنده را observe کن.

The first task faulted, but the app reports success; observe the winning task’s result.

پاسخ فنیTechnical reasoning

Task برگشتی WhenAny را await کن؛ خود WhenAny معمولاً Task برنده را به عنوان Result تحویل می‌دهد.

Await the task returned by WhenAny; WhenAny itself returns the completed task as its result.

۹) timeout در WhenAny9) Timeout race

Task.Delay برنده می‌شود ولی عملیات ادامه دارد؛ cleanup و مالکیت را طراحی کن.

Task.Delay wins but the operation continues; design cleanup and ownership.

پاسخ فنیTechnical reasoning

operation را با token اجرا، در timeout cancel و نتیجه‌اش را observe/cleanup کن؛ race فقط wait را نمی‌بندد.

Run with a token, cancel on timeout and observe/clean up; the race alone only ends the wait.

۱۰) لغو CPU10) CPU cancellation

Task.Run cancel token دارد اما محاسبهٔ synchronous ادامه می‌یابد؛ علت را رفع کن.

Task.Run has a cancellation token but synchronous computation continues; explain and repair it.

پاسخ فنیTechnical reasoning

delegate محاسبه باید token را درون کار بررسی کند؛ token شروع یا صف را می‌تواند لغو کند، نه کد هم‌اکنون در حال اجرا را.

The computation delegate must check the token; it can cancel scheduling, not forcibly stop code already running.

۱۱) batch با partial result11) Partial batch results

گزارش باید موفقیت‌ها را با وجود چند failure تحویل دهد؛ نتیجهٔ هر ورودی را مدل کن.

A report must retain successes despite some failures; model a per-item result.

پاسخ فنیTechnical reasoning

هر operation را به discriminated/result record موفق یا ناموفق تبدیل و بعد summary بساز.

Map each operation to a success/failure result record, then build a summary.

۱۲) semaphore release12) Semaphore release

exception permit را گم می‌کند و کارهای بعدی گیر می‌کنند؛ release را در مسیر امن بگذار.

An exception leaks a permit and later work stalls; secure the release path.

پاسخ فنیTechnical reasoning

پس از Wait موفق، کل عملیات را در try/finally بگذار و در finally Release کن.

After a successful wait, wrap the operation in try/finally and release in finally.

۱۳) rate limit13) Rate limiting

saturation مقصد زیاد می‌شود؛ concurrency را با ظرفیت و Retry-After تطبیق بده.

The downstream service is saturated; tune concurrency against capacity and Retry-After.

پاسخ فنیTechnical reasoning

حد پایین و اندازه‌گیری‌شده بگذار و backoff محدود را رعایت؛ هم‌زمانی بیشتر throughput را تضمین نمی‌کند.

Use a measured bound and bounded backoff; more concurrency does not guarantee more throughput.

۱۴) timeout کل زنجیره14) End-to-end deadline

سه مرحله هرکدام timeout پنج‌ثانیه‌ای دارند، درخواست تا ۱۵ ثانیه می‌ماند؛ deadline کلی بساز.

Three stages each have a five-second timeout, so the request lasts 15 seconds; add an end-to-end deadline.

پاسخ فنیTechnical reasoning

یک deadline linked در ورودی بساز و همان token را در هر مرحله عبور بده.

Create one linked deadline at entry and propagate the same token through each stage.

۱۵) WhenAll خطاهای متعدد15) Multiple WhenAll failures

چند Task fault شده ولی log فقط اولین exception را می‌بیند؛ همهٔ شواهد را جمع کن.

Several tasks fault but the log shows only one exception; collect all evidence.

پاسخ فنیTechnical reasoning

Task aggregate را نگه دار و Exception همهٔ Taskهای faulted را با context هر ورودی ثبت کن.

Retain the task aggregate and record exceptions from all faulted tasks with per-input context.

۱۶) cancel هم‌زمان completion16) Cancellation/completion race

نتیجه درست هم‌زمان با cancel آماده می‌شود؛ contract خروجی را روشن کن.

A valid result arrives as cancellation is requested; clarify the output contract.

پاسخ فنیTechnical reasoning

پس از completion دیگر لغو، نتیجهٔ تمام‌شده را undo نمی‌کند؛ اولویت completion/cancellation را مستند و test کن.

Cancellation cannot undo completed work; document and test which outcome wins the completion race.

۱۷) fire-and-forget سرویس17) Service fire-and-forget

controller یک Task را رها می‌کند که از scoped service استفاده می‌کند؛ lifecycle را بازطراحی کن.

A controller abandons a task using scoped services; redesign lifetime ownership.

پاسخ فنیTechnical reasoning

job را در queue بگذار تا hosted worker scope بسازد، لغو shutdown و خطا را مدیریت کند.

Enqueue work for a hosted worker that creates a scope and handles shutdown cancellation and failures.

۱۸) incident انبوه Task18) Task-flood incident

latency بالا، 429 و memory رشد کرده؛ گزارش incident با concurrency، wait، لغو و partial result بنویس.

Latency, 429 responses and memory are rising; write an incident report covering concurrency, waits, cancellation and partial results.

پاسخ فنیTechnical reasoning

تعداد عملیات فعال/صف و نرخ خطا را بسنج، ورودی را محدود، deadline و cancellation را end-to-end و نتیجهٔ جزئی را شفاف کن؛ سپس load test تکرارپذیر اجرا کن.

Measure active/queued work and failures, bound inputs, propagate deadlines/cancellation end to end, define partial results and rerun a reproducible load test.

آزمایشگاه: batch محدود برای کاتالوگLab: a bounded catalog batch

یک batch برای ۵۰۰ شناسه بنویس که حداکثر تعداد مشخصی درخواست هم‌زمان دارد. fake client قابل‌کنترل، latency، 429، failure و cancellation را تزریق کند. یک deadline برای کل batch و token مجزا برای درخواست بساز؛ وقتی یکی failure حیاتی می‌دهد، policy لغو بقیه را اجرا و cleanup را await کن. حالت partial success را هم جدا تمرین کن. تعداد Taskهای ساخته‌شده، هم‌زمان فعال، peak memory، زمان و تعداد درخواست مقصد را ثبت کن تا تفاوت «همه را شروع کردم» و «ظرفیت را کنترل کردم» دیده شود.

Write a batch for 500 IDs with a bounded maximum number of concurrent requests. Inject a controllable fake client with latency, 429, failures and cancellation. Use one end-to-end batch deadline and request tokens; when a critical failure occurs, apply the cancellation policy and await cleanup. Also test partial success. Record created tasks, concurrent operations, peak memory, duration and downstream request count to expose the difference between starting everything and controlling capacity.

Taskها را شروع نکن مگر آن‌که بتوانی مالکشان باشیDo not start tasks you cannot own

WhenAll join می‌کند، WhenAny برنده را معرفی می‌کند، token درخواست توقف می‌دهد و semaphore ظرفیت را محدود می‌کند؛ هیچ‌کدام دیگری را جایگزین نیست. timeout ممکن است فقط انتظار را تمام کند. در batch واقعی، نتیجهٔ جزئی، cleanup، deadline و مشاهده‌پذیری هم جزو قراردادند. فصل بعد سراغ failure modeهای async می‌رویم؛ جاهایی که این قواعد رعایت نشده‌اند و برنامه ظاهراً گیر می‌کند.

WhenAll joins, WhenAny identifies a winner, a token requests cancellation and a semaphore bounds capacity; none replaces the others. A timeout can end only the wait. Partial results, cleanup, deadlines and observability are also part of a real batch contract. Next we investigate async failure modes where these rules are ignored and the app appears stuck.
