LINQ: گروه‌بندی، join و ترکیب

LINQ: grouping, joins and composition

گزارش فروش فقط فیلتر نیست: باید سفارش رو به مشتری وصل کنیم، جمع هر گروه رو حساب کنیم و مشتری بی‌سفارش رو هم نگه داریم. هر operator رو از همین نیازهای واقعی درمی‌آوریم؛ بعد cardinality خروجی رو با fixture می‌سنجیم.

A sales report is more than filtering: join orders to customers, aggregate groups, and preserve customers without orders. We derive operators from these needs and verify output cardinality with fixtures.

Join زوج می‌سازه؛ cardinality رو حدس نزنJoin forms pairs; do not guess cardinality

Join برای هر کلید مشترک زوج می‌سازه. order بی‌مشتری در inner join ناپدید می‌شه؛ اگه یک شناسه در سمت customer دو بار باشه، هر order دو خروجی می‌سازه. پیش از aggregate، تعداد و یکتایی کلیدها رو در دادهٔ واقعی بررسی کن؛ خروجی غلط اغلب از رابطهٔ چندبه‌چند ناخواسته میاد.

Join creates a pair for each matching key. An order without a customer disappears in an inner join; duplicate customer IDs multiply output rows. Check key uniqueness and cardinality before aggregating—unexpected many-to-many matches often explain wrong totals.

گزارش تجمیعی / Aggregate report
var totals = orders
    .GroupBy(o => o.CustomerId)
    .Select(g => new { CustomerId = g.Key,
                       Count = g.Count(),
                       Total = g.Sum(o => o.Total) });

قبل از join خروجی رو روی سه customer و چند سفارش دستی پیش‌بینی کن؛ بعد تعداد ردیف و مبلغ رو assert کن. syntax زیبا جای بررسی cardinality رو نمی‌گیره.

Predict output for a tiny fixture before joining, then assert row counts and totals. Elegant syntax does not replace cardinality checks.

قبل از Join تعداد خروجی رو حدس بزنPredict the row count before you Join

LINQ خیلی خوش‌خوانه و همین می‌تونه خطرناک باشه: query قشنگه، compile هم می‌شه، ولی تعداد خروجی دو برابر چیزی شده که business انتظار داشته. قبل از اینکه `Join` یا `GroupJoin` بنویسی، دو طرف رو روی fixture کوچیک بشمار و روی کاغذ بگو چند جفت ساخته می‌شه. این عادت جلوی بخش بزرگی از گزارش‌های «عددش یه کم عجیبه» رو می‌گیره.

LINQ is readable, and that can be dangerous: the query looks elegant and compiles, yet the result count is twice what the business expected. Before writing `Join` or `GroupJoin`, count both sides in a tiny fixture and predict the number of produced pairs. That habit prevents many “the report number looks a little strange” incidents.

GroupBy هم فقط syntax گزارش‌گیری نیست. داری shape داده رو عوض می‌کنی: از itemها به گروه‌ها. هر جا shape عوض شد، باید بدونی چه چیزی حفظ شد، چه چیزی از بین رفت و آیا لازم بود همهٔ memberها رو در حافظه نگه داری یا فقط aggregateها کافی بودن.

`GroupBy` is not merely report syntax either. It changes the shape of the data from items to groups. Whenever shape changes, know what was preserved, what was discarded, and whether you truly needed every group member in memory or only aggregates.

GroupBy گروه می‌سازه؛ همهٔ اعضا رو بی‌دلیل نگه ندارGroupBy creates groups; do not retain every item needlessly

اگه فقط جمع و count لازمه، همان‌ها رو project کن؛ نگه‌داشتن entityهای کامل ممکنه حافظه رو بالا ببرد. برای مشتری بی‌سفارش، GroupJoin سمت چپ رو نگه می‌داره و گروه خالی می‌ده. DefaultIfEmpty راه ساخت left join هست، اما null و مقدار جایگزین باید طبق نیاز دامنه تعریف بشن.

If only sum and count are needed, project those rather than retaining full entities. GroupJoin preserves left-side customers and gives an empty group for those without orders. DefaultIfEmpty can form a left join, but null and fallback values must follow domain requirements.

SelectMany و Zip رابطه‌های متفاوتی‌اندSelectMany and Zip model different relationships

SelectMany sequenceهای تو در تو رو flatten می‌کنه؛ Zip عنصرها رو بر اساس موقعیت جفت می‌کنه و وقتی یکی تمام شد متوقف می‌شه. Zip برای اتصال با کلید نیست. Aggregate هم fold عمومی هست، ولی برای جمع عددی Sum معمولاً قصد رو روشن‌تر منتقل می‌کنه.

SelectMany flattens nested sequences; Zip pairs by position and stops when either source ends. Zip is not a key join. Aggregate is a general fold, while Sum usually communicates numeric intent more clearly.

در IQueryable، provider وارد ماجرا می‌شهWith IQueryable, a provider enters the picture

روی IEnumerable معمولاً delegate در برنامه اجرا می‌شه؛ IQueryable expression tree رو به provider می‌ده تا ترجمه کند. همهٔ تابع‌های C# ترجمه‌پذیر نیستن. مرز ToList اجرای بعدی رو به حافظه می‌آورد و ممکنه دادهٔ زیادی انتقال دهد. SQL و تعداد round-trip رو log کن؛ از روی ظاهر query حدس نزن.

With IEnumerable, delegates usually run in-process; IQueryable supplies an expression tree for a provider to translate. Not every C# function translates. ToList moves later work into memory and may transfer too much data. Log SQL and round trips instead of guessing from query syntax.
