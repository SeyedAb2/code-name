زمان‌سنجی، لاگ و process

Timing, logs and processes

ابزار build گاهی شکست می‌خورد، ولی برنامه فقط می‌گوید «ناموفق». تیم هم process را اجرا می‌کند و بعد منتظر exit می‌ماند؛ اگر خروجی زیاد باشد، هر دو طرف برای خواندن stream قفل می‌شوند. در این فصل process را مثل یک مرز واقعی می‌بینیم: ورودی محدود، دو کانال خروجی، exit code، مهلت و جمع‌آوری مدرک.

A build tool sometimes fails, but the app reports only “failed.” The team starts a process and waits for exit; with enough output, both sides can block on stream reads. We treat a process as a real boundary: bounded input, two output channels, exit code, deadline and evidence collection.

process را با آرگومان‌های جدا اجرا کنPass process arguments separately

ProcessStartInfo نام executable، working directory، environment و policy خروجی را تعیین می‌کند. اگر دادهٔ کاربر را در command string بچسبانی، quoting و shell injection وارد ماجرا می‌شود. با UseShellExecute = false و ArgumentList هر آرگومان را جدا بده؛ executable را از config قابل‌اعتماد انتخاب و مسیر را validate کن.

ProcessStartInfo controls the executable, working directory, environment and output policy. Concatenating user data into a command string introduces quoting and shell-injection risks. With UseShellExecute = false, use ArgumentList to pass each argument separately; select a trusted executable and validate paths.

ساخت process / Configure a process
var start = new ProcessStartInfo
{
    FileName = "dotnet",
    WorkingDirectory = projectDirectory,
    UseShellExecute = false,
    RedirectStandardOutput = true,
    RedirectStandardError = true,
    CreateNoWindow = true
};
start.ArgumentList.Add("test");
start.ArgumentList.Add("--no-restore");

در این الگو shell اجرا نمی‌شود؛ رفتار و پیدا شدن executable هنوز به PATH/محیط وابسته است. در ابزار حساس مسیر executable را صریح و working directory را کنترل کن. روی ورودی نامطمئن آرگومان اختیاری خطرناک نپذیر؛ جداکردن آرگومان‌ها quoting را ساده می‌کند، اما مجوز اجرای هر command را جایگزین نمی‌کند.

This launches without a shell, but executable discovery still depends on PATH and environment. For sensitive tools, specify the executable path and control the working directory. Do not accept dangerous optional arguments from untrusted input; separate arguments simplify quoting but do not authorize arbitrary commands.

stdout و stderr را هم‌زمان تخلیه کنDrain stdout and stderr concurrently

child process برای هر stream بافر محدود دارد. اگر parent روی process صبر کند ولی stream پرشده را نخواند، child برای نوشتن منتظر می‌ماند و parent برای خروج child: deadlock. هر دو stream را هم‌زمان بخوان و بعد exit را await کن. خروجی نامحدود را هم در حافظه جمع نکن؛ می‌توانی خط‌به‌خط مصرف کنی یا سقف log تعیین کنی.

A child process has bounded buffers for its streams. If the parent waits for exit without draining a full stream, the child waits to write while the parent waits for the child: a deadlock. Read both streams concurrently, then await exit. Do not buffer unlimited output in memory; consume incrementally or impose a log cap.

خواندن هم‌زمان / Drain both streams
using var process = new Process { StartInfo = start };
process.Start();

Task<string> stdoutTask = process.StandardOutput.ReadToEndAsync();
Task<string> stderrTask = process.StandardError.ReadToEndAsync();
await process.WaitForExitAsync(cancellationToken);

string stdout = await stdoutTask;
string stderr = await stderrTask;
int exitCode = process.ExitCode;

این نمونه خروجی را کامل در حافظه نگه می‌دارد و فقط برای ابزار با خروجی محدود مناسب است. برای حجم زیاد، event-based async یا حلقهٔ خواندن stream و نوشتن محدود به فایل/log به‌کار ببر. timeout یا cancellation به‌تنهایی process فرزند را خودکار نمی‌کشد؛ سیاست kill و جمع‌کردن فرزندان را جدا طراحی کن.

This buffers all output and is suitable only when output is bounded. For large output, use asynchronous line events or stream into bounded storage/logging. A timeout or cancellation does not automatically kill the child process; design termination and child-process cleanup separately.

exit code، پاسخ process است نه متن خطاExit code is process status, not an error message

معمولاً صفر یعنی موفق و غیرصفر یعنی ناموفق، اما قرارداد دقیق را executable تعریف می‌کند. متن stderr می‌تواند warning داشته باشد حتی با exit صفر؛ stdout هم ممکن است دادهٔ اصلی باشد. پس هر سه را ثبت کن و به جای جست‌وجوی کلمهٔ «error» در متن، exit code و مستندات command را مبنا بگذار.

Zero usually means success and nonzero indicates failure, but the executable defines its exact contract. stderr can contain warnings even when exit is zero, and stdout can be primary data. Record all three; rely on the command’s documented exit semantics, not a search for the word “error.”

ارزیابی نتیجه / Evaluate the result
if (exitCode != 0)
{
    logger.LogError(
        "Command failed: {File} exit={ExitCode} stderr={Stderr}",
        start.FileName, exitCode, Redact(stderr));
    throw new InvalidOperationException("External command failed");
}

logger.LogInformation("Command completed in {Elapsed}", elapsed);

stdout/stderr ممکن است token یا مسیر خصوصی داشته باشند؛ قبل از log کردن redact و truncate کن. اگر stderr حجم بالا دارد، کل رشته را در exception نچسبان. duration را با Stopwatch بسنج، نه با تفریق ساعت wall که ممکن است جابه‌جا شود.

stdout and stderr may contain tokens or private paths; redact and truncate before logging. Do not attach an unbounded stderr string to an exception. Measure duration with Stopwatch, not wall-clock subtraction that can jump.

مهلت اجرا و خاموش‌کردن درستExecution deadlines and graceful termination

برای process مهلت بگذار. وقتی deadline گذشت، اول cancellation را درخواست کن و اگر command امکان shutdown ندارد، process را با سیاست مشخص terminate کن؛ tree فرزندان هم ممکن است لازم باشد. سپس خروجی نهایی و exit code را جمع کن. kill کردن بدون ثبت timeout علت را پنهان می‌کند؛ انتظار نامحدود هم منابع را می‌خواباند.

Give the process a deadline. On expiry, request cancellation first; if the command cannot shut down, terminate it under an explicit policy, possibly including its child tree. Then collect final output and exit status. Killing without recording the timeout hides the cause; waiting forever stalls resources.

wait محدود / Bounded wait
using var timeout = new CancellationTokenSource(
    TimeSpan.FromMinutes(2));
try
{
    await process.WaitForExitAsync(timeout.Token);
}
catch (OperationCanceledException) when (timeout.IsCancellationRequested)
{
    process.Kill(entireProcessTree: true);
    await process.WaitForExitAsync(CancellationToken.None);
    throw new TimeoutException("Command exceeded its deadline");
}

این قطعه را بعد از شروع هم‌زمان خواندن stdout و stderr استفاده کن تا child در bufferها گیر نکند. در محیط‌هایی که اجازهٔ terminate نمی‌دهند، خطای kill را هم مدیریت کن. لغو بیرونی برنامه و پایان مهلت را در telemetry از هم جدا ثبت کن.

Use this after starting concurrent stdout/stderr reads so the child cannot block on full buffers. Handle termination failures in environments where killing is restricted. Record caller cancellation and deadline expiry as distinct telemetry outcomes.

لاگ process باید برای بازسازی رخداد باشدProcess logs should help reconstruct an incident

برای هر اجرا executable، آرگومان‌های بی‌خطر، working directory، مدت، exit code و حجم خروجی را نگه دار. secretها را redact کن و متن خام را محدود کن. eventهای structured بهتر از یک خط متن چندمنظوره‌اند. اگر اجرا موفق اما خروجی غیرمنتظره است، checksum یا schema خروجی را هم بررسی کن؛ exit صفر، درستی معنایی را تضمین نمی‌کند.

For each run, record the executable, safe arguments, working directory, duration, exit code and output size. Redact secrets and bound raw text. Structured events are more useful than one catch-all line. If execution succeeds but output is unexpected, validate its checksum or schema; exit zero does not guarantee semantic correctness.

۱) argument امن1) Safe arguments

کد command string را با نام فایل شامل فاصله اجرا می‌کند؛ به ArgumentList منتقلش کن.

A command string fails on file names with spaces; migrate it to ArgumentList.

پاسخ فنیTechnical reasoning

هر token را جدا اضافه کن و shell را خاموش نگه دار؛ مسیر فایل را به executable تبدیل نکن.

Add each token separately with shell execution disabled; never treat a file path as the executable.

۲) stderr پر2) Full stderr buffer

child هزاران خط stderr می‌نویسد و parent stdout را کامل می‌خواند؛ deadlock را رفع کن.

A child writes thousands of stderr lines while the parent drains stdout; eliminate the deadlock.

پاسخ فنیTechnical reasoning

stdout و stderr را هم‌زمان بخوان یا یکی را async drain کن؛ بعد از اتمام flush و exit را await کن.

Drain stdout and stderr concurrently or asynchronously; await completion and exit afterward.

۳) exit غیرصفر3) Nonzero exit

command روی exit code برابر ۲ خروجی ظاهراً عادی دارد؛ قرارداد را بررسی و failure را تشخیص بده.

A command exits 2 but prints plausible output; verify its contract and detect failure.

پاسخ فنیTechnical reasoning

exit code و معنای مستند command را مبنا بگیر؛ stdout را به‌تنهایی موفقیت فرض نکن.

Use the documented exit semantics; do not treat stdout alone as success.

۴) stderr با exit صفر4) stderr with exit zero

build warning را به‌دلیل وجود stderr شکست می‌زند؛ policy را از قرارداد command جدا کن.

A build is failed merely because stderr is nonempty; separate policy from the command contract.

پاسخ فنیTechnical reasoning

exit code نتیجهٔ process است؛ warning را با قواعد مشخص parse کن، نه صرفاً stream انتخابی.

Exit code is process status; classify warnings using explicit rules, not by which stream contains them.

۵) UseShellExecute5) UseShellExecute

RedirectStandardOutput exception می‌دهد؛ تنظیم process start را درست کن.

RedirectStandardOutput throws; correct the process start configuration.

پاسخ فنیTechnical reasoning

برای redirect، UseShellExecute = false لازم است.

UseShellExecute = false is required for redirected streams.

۶) timeout بدون kill6) Timeout without termination

wait لغو می‌شود ولی child همچنان کار می‌کند؛ shutdown محدود و قابل‌مشاهده بساز.

The wait is cancelled but the child keeps running; implement bounded, observable shutdown.

پاسخ فنیTechnical reasoning

پس از deadline، timeout را ثبت و در صورت نیاز Kill(true) اجرا کن؛ بعد exit را collect کن.

Record deadline expiry, call Kill(true) if needed, then collect process exit.

۷) آرگومان shell injection7) Shell injection

نام branch از کاربر در command string جاگذاری می‌شود؛ سطح حمله را کم کن.

A user branch name is interpolated into a command string; reduce the attack surface.

پاسخ فنیTechnical reasoning

shell را اجرا نکن، executable ثابت و ArgumentList به‌کار ببر و ورودی را طبق grammar ابزار validate کن.

Avoid a shell, use a fixed executable and ArgumentList, and validate input against the tool’s grammar.

۸) stdout نامحدود8) Unbounded stdout

ReadToEnd چند گیگابایت را حافظه می‌گیرد؛ output را محدود یا مرحله‌ای پردازش کن.

ReadToEnd buffers gigabytes in memory; cap or process output incrementally.

پاسخ فنیTechnical reasoning

line-by-line stream را drain و فقط tail محدود نگه دار یا خروجی را به فایل با quota هدایت کن.

Drain line by line and retain a bounded tail, or redirect to quota-limited storage.

۹) Stopwatch9) Stopwatch

duration با DateTime.Now محاسبه شده و گاهی منفی است؛ اندازه‌گیری را اصلاح کن.

Duration measured with DateTime.Now is occasionally negative; fix the measurement.

پاسخ فنیTechnical reasoning

برای elapsed time از Stopwatch monotonic استفاده کن.

Use monotonic Stopwatch for elapsed time.

۱۰) working directory10) Working directory

command در IDE کار می‌کند ولی CI فایل config را نمی‌یابد؛ محیط اجرا را explicit کن.

The command works in the IDE but CI cannot find a config file; make its environment explicit.

پاسخ فنیTechnical reasoning

WorkingDirectory و مسیر config را از root مشخص تنظیم و با artifact واقعی تست کن.

Set WorkingDirectory and config paths explicitly, then test against the real artifact.

۱۱) secret در stderr11) Secret in stderr

فرمان credential را در خطای خود چاپ می‌کند؛ قبل از log کردن خروجی را redact کن.

The command echoes a credential in its error output; redact before logging.

پاسخ فنیTechnical reasoning

secretها را از آرگومان تا حد ممکن حذف و stderr را قبل از نگهداری scrub/truncate کن؛ دسترسی log را هم محدود کن.

Avoid secrets in arguments where possible and scrub/truncate stderr before storage; restrict log access too.

۱۲) child tree12) Child process tree

process اصلی terminate می‌شود اما compiler فرزند باقی می‌ماند؛ shutdown کامل را تست کن.

The parent exits but a compiler child remains; test full process-tree shutdown.

پاسخ فنیTechnical reasoning

در timeout از Kill(entireProcessTree: true) استفاده و فرایندهای باقی‌مانده را در تست verify کن.

Use Kill(entireProcessTree: true) on timeout and verify no descendants remain.

۱۳) cancel caller یا timeout13) Caller cancellation or timeout

هر دو به یک log event تبدیل شده‌اند؛ observability را تفکیک کن.

Both outcomes are logged as one event; separate the telemetry.

پاسخ فنیTechnical reasoning

token بیرونی و CTS مهلت را جدا تشخیص بده و reason را همراه exit/kill نتیجه ثبت کن.

Distinguish the caller token from the deadline CTS and record the reason with exit/termination outcome.

۱۴) رخداد build مبهم14) Ambiguous build incident

build گاهی hang می‌کند و خروجی ناقص است؛ فرضیه‌ها و مدرک لازم را فهرست کن.

A build intermittently hangs with partial output; list hypotheses and the evidence needed.

پاسخ فنیTechnical reasoning

خواندن هر دو stream، process tree، deadline، working directory، exit code و حجم خروجی را ثبت؛ سپس با fixture محلی بازتولید کن.

Capture both stream drains, process tree, deadline, working directory, exit code and output size, then reproduce locally.

آزمایشگاه: runner برای ابزار buildLab: a build-tool runner

یک runner محدود بساز که executable از allowlist اجرا کند و stdout/stderr را هم‌زمان بخواند. برای آزمایش، child کنترل‌شده‌ای داشته باش که چند خط به هر دو stream بنویسد، exit صفر و غیرصفر بدهد و در حالت timeout بماند؛ هیچ command دلخواه یا ورودی destructive اجرا نکن. آرگومان‌ها را جدا، deadline را مشخص، خروجی را محدود و secretها را redact کن. در گزارش نهایی command امن، مدت، exit code و علت timeout/cancellation را از هم جدا کن.

Build a bounded runner that launches only allowlisted executables and drains stdout/stderr concurrently. Use a controlled child that writes to both streams, exits with zero/nonzero codes and hangs for the timeout case; never execute arbitrary or destructive commands. Pass arguments separately, enforce a deadline, bound output and redact secrets. Report safe command identity, duration, exit code and distinct timeout/cancellation causes.

  1. deadlock دو stream را عمداً بساز و اصلاحش را prove کن.
  2. Reproduce a two-stream deadlock and prove the fix.
  3. بیشینهٔ خروجی و timeout را assert کن.
  4. Assert maximum output and timeout behavior.
  5. بعد از هر حالت، نبود child سرگردان را بررسی کن.
  6. Verify no orphan child remains after each scenario.

process خارجی یعنی قرارداد، نه یک خط StartAn external process is a contract, not one Start call

اجرای امن فقط Start() نیست: executable و آرگومان، working directory، دو stream، exit semantics، مهلت، tree فرزندان و redaction همگی قراردادند. اگر یکی جا بماند، ابزار ساده می‌تواند deadlock، نشت secret یا process سرگردان بسازد. این نگاهِ مرزدار، ما را برای فصل‌های async آماده می‌کند؛ آن‌جا باید منتظر ماندن را از اشغال نخ جدا کنیم.

Safe execution is more than Start(): executable and arguments, working directory, both streams, exit semantics, deadlines, child trees and redaction form the contract. Miss one and a small tool can deadlock, leak secrets or leave orphan processes. This boundary-focused model prepares us for async, where waiting must be separated from occupying a thread.
