زمان‌سنجی، لاگ و process

Timing, logs and processes

ابزار build گاهی شکست می‌خوره، ولی برنامه فقط می‌گه «ناموفق». تیم هم process رو اجرا می‌کنه و بعد منتظر exit می‌مونه؛ اگه خروجی زیاد باشه، هر دو طرف برای خواندن stream قفل می‌شن. در این فصل process رو مثل یک مرز واقعی می‌بینیم: ورودی محدود، دو کانال خروجی، exit code، مهلت و جمع‌آوری مدرک.

A build tool sometimes fails, but the app reports only “failed.” The team starts a process and waits for exit; with enough output, both sides can block on stream reads. We treat a process as a real boundary: bounded input, two output channels, exit code, deadline and evidence collection.

process رو با آرگومان‌های جدا اجرا کنPass process arguments separately

ProcessStartInfo نام executable، working directory، environment و policy خروجی رو تعیین می‌کنه. اگه دادهٔ کاربر رو در command string بچسبانی، quoting و shell injection وارد ماجرا می‌شه. با UseShellExecute = false و ArgumentList هر آرگومان رو جدا بده؛ executable رو از config قابل‌اعتماد انتخاب و مسیر رو validate کن.

ProcessStartInfo controls the executable, working directory, environment and output policy. Concatenating user data into a command string introduces quoting and shell-injection risks. With UseShellExecute = false, use ArgumentList to pass each argument separately; select a trusted executable and validate paths.

ساخت process / Configure a process
var start = new ProcessStartInfo
{
    FileName = "dotnet",
    WorkingDirectory = projectDirectory,
    UseShellExecute = false,
    RedirectStandardOutput = true,
    RedirectStandardError = true,
    CreateNoWindow = true
};
start.ArgumentList.Add("test");
start.ArgumentList.Add("--no-restore");

در این الگو shell اجرا نمی‌شه؛ رفتار و پیدا شدن executable هنوز به PATH/محیط وابسته هست. در ابزار حساس مسیر executable رو صریح و working directory رو کنترل کن. روی ورودی نامطمئن آرگومان اختیاری خطرناک نپذیر؛ جداکردن آرگومان‌ها quoting رو ساده می‌کنه، اما مجوز اجرای هر command رو جایگزین نمی‌کنه.

This launches without a shell, but executable discovery still depends on PATH and environment. For sensitive tools, specify the executable path and control the working directory. Do not accept dangerous optional arguments from untrusted input; separate arguments simplify quoting but do not authorize arbitrary commands.

stdout و stderr رو هم‌زمان تخلیه کنDrain stdout and stderr concurrently

child process برای هر stream بافر محدود داره. اگه parent روی process صبر کند ولی stream پرشده رو نخواند، child برای نوشتن منتظر می‌مونه و parent برای خروج child: deadlock. هر دو stream رو هم‌زمان بخوان و بعد exit رو await کن. خروجی نامحدود رو هم در حافظه جمع نکن؛ می‌تونی خط‌به‌خط مصرف کنی یا سقف log تعیین کنی.

A child process has bounded buffers for its streams. If the parent waits for exit without draining a full stream, the child waits to write while the parent waits for the child: a deadlock. Read both streams concurrently, then await exit. Do not buffer unlimited output in memory; consume incrementally or impose a log cap.

خواندن هم‌زمان / Drain both streams
using var process = new Process { StartInfo = start };
process.Start();

Task<string> stdoutTask = process.StandardOutput.ReadToEndAsync();
Task<string> stderrTask = process.StandardError.ReadToEndAsync();
await process.WaitForExitAsync(cancellationToken);

string stdout = await stdoutTask;
string stderr = await stderrTask;
int exitCode = process.ExitCode;

این نمونه خروجی رو کامل در حافظه نگه می‌داره و فقط برای ابزار با خروجی محدود مناسب هست. برای حجم زیاد، event-based async یا حلقهٔ خواندن stream و نوشتن محدود به فایل/log به‌کار ببر. timeout یا cancellation به‌تنهایی process فرزند رو خودکار نمی‌کشه؛ سیاست kill و جمع‌کردن فرزندان رو جدا طراحی کن.

This buffers all output and is suitable only when output is bounded. For large output, use asynchronous line events or stream into bounded storage/logging. A timeout or cancellation does not automatically kill the child process; design termination and child-process cleanup separately.

exit code، پاسخ process هست نه متن خطاExit code is process status, not an error message

معمولاً صفر یعنی موفق و غیرصفر یعنی ناموفق، اما قرارداد دقیق رو executable تعریف می‌کنه. متن stderr می‌تونه warning داشته باشه حتی با exit صفر؛ stdout هم ممکنه دادهٔ اصلی باشه. پس هر سه رو ثبت کن و به جای جست‌وجوی کلمهٔ «error» در متن، exit code و مستندات command رو مبنا بگذار.

Zero usually means success and nonzero indicates failure, but the executable defines its exact contract. stderr can contain warnings even when exit is zero, and stdout can be primary data. Record all three; rely on the command’s documented exit semantics, not a search for the word “error.”

ارزیابی نتیجه / Evaluate the result
if (exitCode != 0)
{
    logger.LogError(
        "Command failed: {File} exit={ExitCode} stderr={Stderr}",
        start.FileName, exitCode, Redact(stderr));
    throw new InvalidOperationException("External command failed");
}

logger.LogInformation("Command completed in {Elapsed}", elapsed);

stdout/stderr ممکنه token یا مسیر خصوصی داشته باشن؛ قبل از log کردن redact و truncate کن. اگه stderr حجم بالا داره، کل رشته رو در exception نچسبان. duration رو با Stopwatch بسنج، نه با تفریق ساعت wall که ممکنه جابه‌جا بشه.

stdout and stderr may contain tokens or private paths; redact and truncate before logging. Do not attach an unbounded stderr string to an exception. Measure duration with Stopwatch, not wall-clock subtraction that can jump.

مهلت اجرا و خاموش‌کردن درستExecution deadlines and graceful termination

برای process مهلت بگذار. وقتی deadline گذشت، اول cancellation رو درخواست کن و اگه command امکان shutdown نداره، process رو با سیاست مشخص terminate کن؛ tree فرزندان هم ممکنه لازم باشه. سپس خروجی نهایی و exit code رو جمع کن. kill کردن بدون ثبت timeout علت رو پنهان می‌کنه؛ انتظار نامحدود هم منابع رو می‌خواباند.

Give the process a deadline. On expiry, request cancellation first; if the command cannot shut down, terminate it under an explicit policy, possibly including its child tree. Then collect final output and exit status. Killing without recording the timeout hides the cause; waiting forever stalls resources.

wait محدود / Bounded wait
using var timeout = new CancellationTokenSource(
    TimeSpan.FromMinutes(2));
try
{
    await process.WaitForExitAsync(timeout.Token);
}
catch (OperationCanceledException) when (timeout.IsCancellationRequested)
{
    process.Kill(entireProcessTree: true);
    await process.WaitForExitAsync(CancellationToken.None);
    throw new TimeoutException("Command exceeded its deadline");
}

این قطعه رو بعد از شروع هم‌زمان خواندن stdout و stderr استفاده کن تا child در bufferها گیر نکند. در محیط‌هایی که اجازهٔ terminate نمی‌دن، خطای kill رو هم مدیریت کن. لغو بیرونی برنامه و پایان مهلت رو در telemetry از هم جدا ثبت کن.

Use this after starting concurrent stdout/stderr reads so the child cannot block on full buffers. Handle termination failures in environments where killing is restricted. Record caller cancellation and deadline expiry as distinct telemetry outcomes.

لاگ process باید برای بازسازی رخداد باشهProcess logs should help reconstruct an incident

برای هر اجرا executable، آرگومان‌های بی‌خطر، working directory، مدت، exit code و حجم خروجی رو نگه دار. secretها رو redact کن و متن خام رو محدود کن. eventهای structured بهتر از یک خط متن چندمنظوره‌اند. اگه اجرا موفق اما خروجی غیرمنتظره هست، checksum یا schema خروجی رو هم بررسی کن؛ exit صفر، درستی معنایی رو تضمین نمی‌کنه.

For each run, record the executable, safe arguments, working directory, duration, exit code and output size. Redact secrets and bound raw text. Structured events are more useful than one catch-all line. If execution succeeds but output is unexpected, validate its checksum or schema; exit zero does not guarantee semantic correctness.

آزمایشگاه: runner برای ابزار buildLab: a build-tool runner

یک runner محدود بساز که executable از allowlist اجرا کند و stdout/stderr رو هم‌زمان بخواند. برای آزمایش، child کنترل‌شده‌ای داشته باش که چند خط به هر دو stream بنویسد، exit صفر و غیرصفر بدهد و در حالت timeout بماند؛ هیچ command دلخواه یا ورودی destructive اجرا نکن. آرگومان‌ها رو جدا، deadline رو مشخص، خروجی رو محدود و secretها رو redact کن. در گزارش نهایی command امن، مدت، exit code و علت timeout/cancellation رو از هم جدا کن.

Build a bounded runner that launches only allowlisted executables and drains stdout/stderr concurrently. Use a controlled child that writes to both streams, exits with zero/nonzero codes and hangs for the timeout case; never execute arbitrary or destructive commands. Pass arguments separately, enforce a deadline, bound output and redact secrets. Report safe command identity, duration, exit code and distinct timeout/cancellation causes.

  1. deadlock دو stream رو عمداً بساز و اصلاحش رو prove کن.
  2. Reproduce a two-stream deadlock and prove the fix.
  3. بیشینهٔ خروجی و timeout رو assert کن.
  4. Assert maximum output and timeout behavior.
  5. بعد از هر حالت، نبود child سرگردان رو بررسی کن.
  6. Verify no orphan child remains after each scenario.

process خارجی یعنی قرارداد، نه یک خط StartAn external process is a contract, not one Start call

اجرای امن فقط Start() نیست: executable و آرگومان، working directory، دو stream، exit semantics، مهلت، tree فرزندان و redaction همگی قراردادند. اگه یکی جا بماند، ابزار ساده می‌تونه deadlock، نشت secret یا process سرگردان بسازد. این نگاهِ مرزدار، ما رو برای فصل‌های async آماده می‌کنه؛ آن‌جا باید منتظر ماندن رو از اشغال نخ جدا کنیم.

Safe execution is more than Start(): executable and arguments, working directory, both streams, exit semantics, deadlines, child trees and redaction form the contract. Miss one and a small tool can deadlock, leak secrets or leave orphan processes. This boundary-focused model prepares us for async, where waiting must be separated from occupying a thread.

اینجا لازم نیست همه‌چیز رو حفظ کرده باشی؛ مهم اینه که مدلش رو بتونی با یه مثال کوچیک دوباره بسازی. فصل بعد این مدل رو می‌بریم سراغ «async/await بدون افسانه» و می‌بینیم همون تصمیم‌ها اونجا چه اثر تازه‌ای پیدا می‌کنن.

You do not need to memorize every detail here; you need to be able to rebuild the model with a small example. Next we carry it into “async/await without myths” and see what new consequence appears there.
