فشرده‌سازی و XML

Compression and XML

شریک ما archive می‌خواد و بعد XML نامطمئنی می‌فرسته. فشرده‌سازی schema رو حل نمی‌کنه؛ XML قابل parse هم لزوماً امن یا معتبر نیست. مرزهای هر دو رو با fixture واقعی می‌آزماییم.

A partner requires an archive, then sends untrusted XML. Compression does not solve schema validation; parseable XML is not necessarily safe or valid. We test both boundaries with real fixtures.

GZip جریان bytes رو wrap می‌کنهGZip wraps a byte stream

GZipStream در مسیر write فشرده و در مسیر read باز می‌کنه. نسبت فشرده‌سازی به داده بستگی داره؛ متن تکراری کم می‌شه ولی دادهٔ تصادفی ممکنه بزرگ‌تر بشه. GZip encryption یا authentication نیست. Dispose wrapper هم پایان stream رو می‌نویسه؛ مالکیت stream داخلی رو صریح نگه دار.

GZipStream compresses on write and decompresses on read. Ratios depend on data; repetitive text shrinks while random data may grow. GZip is not encryption or authentication. Disposing the wrapper writes the stream trailer; define ownership of the inner stream.

پایان stream را کامل کن / Finalize the stream
using var output = new MemoryStream();
using (var gzip = new GZipStream(output, CompressionMode.Compress, leaveOpen: true))
{
    byte[] input = Encoding.UTF8.GetBytes("order report");
    gzip.Write(input);
}
output.Position = 0;

برای proof، archive رو باز و byteها رو مقایسه کن؛ صرف وجود فایل compressed نشان نمی‌ده محتوا سالم برگشته هست.

For proof, decompress and compare bytes; a compressed file's existence does not establish a valid round trip.

نام entry در ZIP رو قابل‌اعتماد فرض نکنDo not trust ZIP entry paths

entry می‌تونه مسیر نسبی مخرب داشته باشه؛ پیش از extract مسیر canonical مقصد رو با root مقایسه کن. archive کوچک هم ممکنه پس از باز شدن دادهٔ عظیمی بسازد؛ تعداد entry و total expanded bytes رو محدود کن و در staging استخراج کن. compressed size سقف فضای خروجی نیست.

An entry may contain a malicious relative path; compare its canonical destination with the extraction root. A small archive can expand enormously; bound entry count and total expanded bytes, and extract to staging. Compressed size does not cap output size.

DOM یا reader: دسترسی آسان در برابر حافظهDOM or reader: navigation versus memory

XDocument کل tree رو می‌سازه و برای سند کوچک و query چندمرحله‌ای راحت هست. XmlReader جلوبرنده هست و برای سند بزرگ مناسب‌تر، اما state record رو خودت مدیریت می‌کنی. namespace جزو نام element هست؛ prefix صرفاً نام مستعار URI هست. برای نوشتن XML از XmlWriter استفاده کن تا escaping درست انجام بشه.

XDocument builds the full tree and is convenient for small documents and rich queries. XmlReader is forward-only and fits large files, but you manage record state. Namespace URI is part of an element name; a prefix is only an alias. Use XmlWriter for correct escaping.

XML untrusted رو با مرز امن parse کنParse untrusted XML at a secure boundary

ورودی نامطمئن رو با DtdProcessing.Prohibit بخوان و XmlResolver رو null بگذار؛ DTD و external entity می‌تونن فایل/شبکه رو درگیر یا منابع رو مصرف کنند. سقف اندازه هم لازمه. اگه DTD واقعاً لازمه، resolver و resourceها رو محدود کن؛ exception parser رو مستقیم برای کاربر افشا نکن.

Parse untrusted input with DtdProcessing.Prohibit and a null XmlResolver; DTDs and external entities can access files/network or consume resources. Also limit document size. If DTD is essential, restrict resolvers and resources; do not expose raw parser exceptions.

تنظیم صریح / Explicit settings
var settings = new XmlReaderSettings
{
    DtdProcessing = DtdProcessing.Prohibit,
    XmlResolver = null,
    MaxCharactersInDocument = 1_000_000
};
using var reader = XmlReader.Create(input, settings);

عدد سقف نمونه هست نه policy همگانی؛ با اندازهٔ مجاز دامنه تنظیمش کن و ورودی DOCTYPE رو در test رد کن.

The limit is illustrative, not universal; tune it to the domain and test rejection of a DOCTYPE input.
