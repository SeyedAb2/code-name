Inheritance, polymorphism and substitution

برای سه نوع گزارش، تیم سه کلاس ساخته و یک متد تکراری را در هر سه کپی کرده. کسی پیشنهاد می‌دهد کلاس پایه بسازیم. سؤال مهم‌تر از «چطور کد را مشترک کنیم؟» این است: آیا هر سه واقعاً یک نوع قابل‌جایگزینی‌اند یا فقط چند خط کد شبیه دارند؟

The team has three report classes and copied one method into all of them. Someone suggests a base class. A better question than “how do we share code?” is: are these genuinely substitutable kinds of one type, or do they merely share a few similar lines?

فصل ۱۷پیش‌نیازprerequisite

شباهت چند خط، رابطهٔ نوعی نمی‌سازدA few shared lines do not create a subtype relationship

وراثت وقتی معنا دارد که derived بتواند به‌جای base به کار رود و قرارداد base را نگه دارد. اگر فقط می‌خواهیم رفتار را دوباره استفاده کنیم، composition یا helper ممکن است شفاف‌تر باشد. شباهت نام یا فیلد به‌تنهایی دلیل is-a نیست.

Inheritance makes sense when a derived instance can stand in for the base and preserve its contract. If the goal is merely code reuse, composition or a helper may be clearer. Similar names or fields alone do not establish an is-a relationship.

پرسش جایگزینیThe substitution question

هرجا کد یک Document می‌خواهد، آیا نوع خاصی از document می‌تواند همهٔ همان کارهای مجاز را انجام دهد، بدون شرط مخفی و بدون ضعیف‌کردن ضمانت؟ اگر نه، رابطه را تحمیل نکن.

Whenever code expects a Document, can the proposed subtype honour every permitted operation without hidden conditions or weakened guarantees? If not, do not force the relationship.

virtual و override: نقطهٔ توسعهٔ صریحvirtual and override: an explicit extension point

متد عادی را derived جایگزین نمی‌کند. virtual اعلام می‌کند type پایه اجازهٔ رفتار متفاوت را می‌دهد؛ override آن رفتار را عوض می‌کند. این تصمیم بخشی از قرارداد API است: تغییر implementation پایه ممکن است رفتار همهٔ derivedها را عوض کند.

A derived type does not replace an ordinary method. virtual declares that the base permits variation; override supplies it. This is part of the API contract: changing base implementation may affect every derived type.

فراخوانی چندریختی / Virtual dispatch
abstract class Report
{
    public string Render() => $"Report: {RenderBody()}";
    protected abstract string RenderBody();
}

sealed class DailyReport : Report
{
    protected override string RenderBody() => "daily totals";
}

Report report = new DailyReport();
Console.WriteLine(report.Render());
خروجی / Output
Report: daily totals

متغیر از نوع Report است اما پیاده‌سازی override شدهٔ DailyReport انتخاب می‌شود. Render رفتار مشترک را نگه می‌دارد و بخش متغیر را به derived می‌سپارد؛ این الگو را template method می‌نامند، اما فقط اگر چنین نقطهٔ تغییری واقعاً لازم باشد.

The variable is typed as Report, yet DailyReport’s override is selected. Render keeps shared behaviour and delegates the varying part to the subtype; this is the template-method shape, useful only when that variation point is real.

abstract برای الزام؛ sealed برای بستن ارث‌بریAbstract to require; sealed to close derivation

abstract class را نمی‌توان مستقیم نمونه‌سازی کرد و می‌تواند عضو abstract داشته باشد که زیرنوع concrete باید پیاده کند. sealed روی کلاس جلوی ارث‌بری را می‌گیرد؛ روی override هم می‌تواند overrideهای پایین‌دست را متوقف کند. هر دو دربارهٔ طراحی extension هستند، نه کنترل دسترسی امنیتی.

An abstract class cannot be instantiated directly and may require concrete subtypes to implement abstract members. sealed prevents deriving from a class; on an override, it can stop further overrides down the hierarchy. Both concern extensibility design, not security access control.

قرارداد ناقصِ عمدی / Intentional abstraction
abstract class Exporter
{
    public abstract string Format { get; }
    public abstract Task ExportAsync(CancellationToken cancellationToken);
}

sealed class CsvExporter : Exporter
{
    public override string Format => "text/csv";
    public override Task ExportAsync(CancellationToken cancellationToken)
        => Task.CompletedTask; // illustrative only
}

پیاده‌سازی CompletedTask فقط شکل امضا را نشان می‌دهد و export واقعی نیست. در کد اجرایی cancellation token باید در کار واقعی رعایت شود. abstract قرارداد را مجبور می‌کند، ولی نمی‌تواند درستی معنایی خروجی را ثابت کند.

CompletedTask only illustrates the signature; it is not a real export. Production work must honour the cancellation token. An abstract member forces an implementation, but cannot prove its semantic correctness.

new متد را پنهان می‌کند، override نمی‌کندnew hides a method; it does not override

اگر متد پایه virtual نباشد، derived با new عضو هم‌نامی می‌سازد که dispatch چندریختی ندارد. انتخاب تابع به نوع static متغیر بستگی پیدا می‌کند؛ همین می‌تواند call siteها را غافلگیر کند.

If a base method is not virtual, new creates a same-named member without polymorphic dispatch. Selection depends on the variable’s static type, which can surprise call sites.

پنهان‌سازی در برابر override / Hiding versus overriding
class BaseReport
{
    public void Describe() => Console.WriteLine("base");
}

class SpecialReport : BaseReport
{
    public new void Describe() => Console.WriteLine("special");
}

BaseReport item = new SpecialReport();
item.Describe();
((SpecialReport)item).Describe();
خروجی / Output
base
special

اگر base متد را virtual و derived آن را override کند، هر دو call مسیر derived را اجرا می‌کنند. new معمولاً هشدار پنهان‌سازی را به انتخاب صریح تبدیل می‌کند؛ این کلمه dispatch را چندریختی نمی‌کند. اگر برای معنای یک call مجبور به cast هستی، API یا مدل subtype را بازبینی کن.

If the base method is virtual and the derived method overrides it, both calls dispatch to the derived implementation. new makes hiding explicit; it does not make dispatch polymorphic. If a call needs a cast to mean the right thing, revisit the API or subtype model.

زیرنوع باید قرارداد پایه را نگه داردA subtype must preserve the base contract

فرض کن base برای هر ورودی مثبت ذخیرهٔ گزارش را تضمین می‌کند. derived اگر بعضی ورودی‌های مجاز را بی‌دلیل رد کند، جایگزین امنی نیست. برعکس، خروجی ضعیف‌تر یا side effect تازه هم می‌تواند caller را بشکند. این ایده به اصل جایگزینی Liskov نزدیک است؛ در عمل با قراردادهای ورودی/خروجی و تست consumer می‌سنجیم.

Suppose the base promises to save a report for every valid positive input. A derived type that rejects some base-valid inputs is not a safe substitute. A weaker result or unexpected side effect can also break callers. This is the Liskov substitution idea; operationally, test input/output contracts through consumers.

پیش‌شرط سخت‌ترStronger preconditionورودی مجاز base رد می‌شودA base-valid input is rejected
پس‌شرط ضعیف‌ترWeaker postconditionضمانت base از بین می‌رودThe base guarantee disappears
اثر جانبی غافلگیرکنندهSurprising side effectمصرف‌کننده رفتار ناخواسته می‌بیندConsumer observes unexpected behaviour

اگر هر زیرنوع شرط‌های متفاوت و castهای فراوان می‌خواهد، شاید به‌جای inheritance از interface کوچک و composition فصل قبل استفاده کن. جایگزینی مهم‌تر از حذف چند خط تکراری است.

If every subtype needs different conditions and repeated casts, prefer the small interface and composition from the previous chapter. Substitutability matters more than removing a few duplicated lines.

آزمایشگاه: تغییر زیرنوع باید caller را نشکندLab: subtype changes must not break consumers

یک Exporter پایه و دو پیاده‌سازی بساز. consumer فقط Exporter را بشناسد. اول تست‌ها را برای قرارداد بنویس، بعد deliberately derivedای بساز که قرارداد را نقض کند و شکست را ببین.

Create a base Exporter and two implementations. A consumer should know only Exporter. Write contract tests first, then deliberately violate the contract in one subtype and observe the failure.

  1. ورودی‌های معتبر و ضمانت خروجی base را دقیق تعریف کن.
  2. Define valid inputs and the base output guarantee precisely.
  3. یک virtual/abstract variation point طراحی کن؛ فقط رفتار واقعاً متفاوت را override کن.
  4. Add a virtual/abstract variation point and override only genuinely varying behaviour.
  5. consumer را با reference پایه بنویس و هر دو derived را به آن بده.
  6. Write the consumer against the base reference and pass both derived types.
  7. یکی از derivedها ورودی معتبر را رد کند؛ تست contract را اجرا کن.
  8. Make one subtype reject a valid input and run the contract test.
  9. new را به‌جای override استفاده کن و دو نوع static متفاوت را صدا بزن.
  10. Use new instead of override and call through two different static types.
  11. در پایان بگو آیا abstraction با interface/composition ساده‌تر می‌شد.
  12. Conclude whether an interface/composition would have been simpler.
معیار پایانDefinition of done

consumer بدون شرط concrete type کار می‌کند؛ هر زیرنوع قرارداد را حفظ می‌کند؛ و تفاوت new و override را با خروجی واقعی نشان داده‌ای.

The consumer has no concrete-type branches; each subtype preserves the contract; and output demonstrates the difference between new and override.

تمرین‌ها: از ارث‌بری دفاع کنExercises: justify inheritance

۱) شباهت یا subtype؟1) Similarity or subtype?

دو گزارش چند خط formatter مشترک دارند. آیا این به‌تنهایی وراثت را توجیه می‌کند؟

Two reports share a few formatter lines. Does that alone justify inheritance?

پاسخAnswer

نه؛ رابطهٔ جایگزینی و قرارداد مشترک لازم است. helper یا composition ممکن است بهتر باشد.

No; a substitutable relationship and shared contract are needed. A helper or composition may fit better.

۲) virtual چه اعلام می‌کند؟2) What does virtual declare?

چه چیزی را به derived اجازه می‌دهد؟

What does it permit a derived type to do?

پاسخAnswer

تغییر عمدی رفتار از طریق override در dispatch چندریختی.

Intentionally vary behaviour through override and polymorphic dispatch.

۳) abstract را نمونه‌سازی کن3) Instantiate an abstract type

آیا می‌شود new Exporter نوشت؟

Can you write new Exporter?

پاسخAnswer

نه؛ abstract class ناقص است و باید نوع concrete ساخت.

No; an abstract class is incomplete; instantiate a concrete type.

۴) abstract member را کامل کن4) Implement an abstract member

کلاس concrete عضو abstract پایه را پیاده نکند؛ انتظار compiler چیست؟

A concrete subtype omits an abstract base member. What does the compiler report?

پاسخAnswer

خطای compile؛ یا باید پیاده‌سازی کند یا خودش abstract بماند.

A compile error; it must implement the member or remain abstract.

۵) virtual dispatch5) Virtual dispatch

متغیر base به derived اشاره می‌کند و متد override را صدا می‌زند؛ کدام بدنه اجرا می‌شود؟

A base-typed variable refers to a derived object and calls an override. Which body runs?

پاسخAnswer

پیاده‌سازی derived، چون dispatch بر اساس نوع runtime object است.

The derived implementation, because dispatch uses the runtime object type.

۶) new را پیش‌بینی کن6) Predict new hiding

بدنهٔ base و derived با new هم‌نام‌اند. call از مسیر base کدام را می‌زند؟

Base and derived methods share a name using new. Which runs through a base-typed variable?

پاسخAnswer

عضو بر اساس نوع static یعنی base انتخاب می‌شود؛ new override نیست.

The member selected by the static base type runs; new is not override.

۷) sealed class7) Sealed class

sealed چه چیزی را می‌بندد و چه چیزی را نه؟

What does sealed prevent, and what does it not?

پاسخAnswer

ارث‌بری از کلاس را می‌بندد؛ boundary امنیتی در برابر همهٔ سازوکارهای runtime نیست.

It prevents derivation; it is not a security boundary against every runtime mechanism.

۸) sealed override8) Sealed override

این modifier روی override چه اثری دارد؟

What does it do on an override?

پاسخAnswer

overrideهای بیشتر در derivedهای بعدی را متوقف می‌کند.

It prevents further overrides in later derived types.

۹) پیش‌شرط سخت‌تر9) Stronger precondition

base ورودی خالی را می‌پذیرد اما derived رد می‌کند. مشکل چیست؟

The base accepts empty input but a subtype rejects it. What is the problem?

پاسخAnswer

caller معتبر بر اساس قرارداد پایه با subtype می‌شکند؛ جایگزینی نقض شده است.

A base-valid caller breaks with the subtype; substitutability is violated.

۱۰) پس‌شرط ضعیف‌تر10) Weaker postcondition

base همیشه فایل کامل می‌سازد اما derived فایل خالی می‌سازد. علت ناسازگاری؟

The base promises a complete file, while the derived returns an empty one. Why incompatible?

پاسخAnswer

derived ضمانت خروجی base را حفظ نکرده است.

The subtype did not preserve the base output guarantee.

۱۱) castهای مکرر11) Repeated casts

consumer مرتب نوع واقعی را cast و چک می‌کند. چه بویی می‌بینی؟

A consumer repeatedly checks and casts concrete types. What design smell do you see?

جهتDirection

contract پایه شاید رفتار کافی ندارد یا رابطهٔ subtype نادرست است؛ interface توانایی کوچک را بررسی کن.

The base contract may be insufficient or the subtype relationship wrong; consider a small capability interface.

۱۲) قالب مشترک export12) Shared export template

کدام بخش را در base نگه می‌داری و کدام را abstract می‌کنی؟

Which part belongs in the base, and which becomes abstract?

نمونهExample

ترتیب ثابت validate/render/write ممکن است در base باشد؛ تولید فرمت متغیر abstract. اگر ترتیب‌ها هم فرق دارند، ترکیب رفتار شاید بهتر شود.

A fixed validate/render/write sequence may belong in the base, with format generation abstract. If sequencing also varies, composition may be better.

۱۳) override یا new؟13) override or new?

می‌خواهی call از reference پایه رفتار derived را اجرا کند. کدام را می‌نویسی؟

You want a base-reference call to execute derived behaviour. Which modifier?

پاسخAnswer

base باید virtual و derived باید override باشد.

The base must be virtual and the derived member override.

۱۴) ارث‌بری برای reuse14) Inheritance for reuse

دو type فقط الگوریتم validation مشترک دارند؛ چه گزینه‌هایی قبل از base class داری؟

Two types share only a validation algorithm. What alternatives come before a base class?

پاسخAnswer

تابع/helper مشترک، composition، یا interface برای رفتار موردنیاز. انتخاب با ownership و تغییر مستقل است.

A shared helper, composition, or an interface for the needed behaviour. Choose based on ownership and independent change.

۱۵) قرارداد را با consumer تست کن15) Test the contract through a consumer

چرا فقط تست کردن خود override کافی نیست؟

Why is testing the override alone insufficient?

پاسخAnswer

باید نشان دهیم consumerی که فقط قرارداد base را می‌شناسد با derived هم درست کار می‌کند.

We must prove that a consumer knowing only the base contract also works with the subtype.

۱۶) incident «derived با cast کار می‌کند»16) The “derived only works after a cast” incident

برای کارکرد exporter جدید همه‌جا cast اضافه شده. مسیر تشخیص و repair چیست؟

The new exporter requires casts everywhere. How do you diagnose and repair it?

مسیر تشخیصDiagnosis path

ببین caller از چه قرارداد پایه‌ای استفاده می‌کند و derived چه شرط اضافه‌ای دارد. contract مشترک و تست consumer تعریف کن؛ اگر جایگزینی شدنی نیست، سلسله‌مراتب را حذف و composition/interface را انتخاب کن.

Inspect the base contract used by callers and extra subtype preconditions. Define a shared contract and consumer test; if substitution is impossible, remove the hierarchy and use composition/interfaces.

وراثت را با جایگزینی توجیه کنJustify inheritance through substitutability

virtual و override برای variation صریح‌اند؛ abstract قرارداد ناقص را مجبور می‌کند؛ sealed مرز توسعه را می‌بندد؛ new فقط عضو هم‌نام را پنهان می‌کند. مهم‌تر از حفظ syntax این است که derived با همان ورودی‌های مجاز، همان ضمانت پایه را نگه دارد. اگر consumer به cast و شرط concrete نیاز دارد، composition و interface فصل قبل را دوباره روی میز بگذار.

virtual and override define explicit variation; abstract requires an incomplete contract; sealed closes an extension point; new merely hides a same-named member. More important than syntax is preserving the base guarantee for all valid inputs. If consumers need concrete-type casts and branches, reconsider composition and interfaces from the previous chapter.
