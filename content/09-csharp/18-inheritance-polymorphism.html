وراثت، چندریختی و جایگزینی

Inheritance, polymorphism and substitution

برای سه نوع گزارش، تیم سه کلاس ساخته و یک متد تکراری رو در هر سه کپی کرده. کسی پیشنهاد می‌ده کلاس پایه بسازیم. سؤال مهم‌تر از «چطور کد رو مشترک کنیم؟» این هست: آیا هر سه واقعاً یک نوع قابل‌جایگزینی‌اند یا فقط چند خط کد شبیه دارن؟

The team has three report classes and copied one method into all of them. Someone suggests a base class. A better question than “how do we share code?” is: are these genuinely substitutable kinds of one type, or do they merely share a few similar lines?

شباهت چند خط، رابطهٔ نوعی نمی‌سازهA few shared lines do not create a subtype relationship

وراثت وقتی معنا داره که derived بتواند به‌جای base به کار رود و قرارداد base رو نگه داره. اگه فقط می‌خوایم رفتار رو دوباره استفاده کنیم، composition یا helper ممکنه شفاف‌تر باشه. شباهت نام یا فیلد به‌تنهایی دلیل is-a نیست.

Inheritance makes sense when a derived instance can stand in for the base and preserve its contract. If the goal is merely code reuse, composition or a helper may be clearer. Similar names or fields alone do not establish an is-a relationship.

پرسش جایگزینیThe substitution question

هرجا کد یک Document می‌خواد، آیا نوع خاصی از document می‌تونه همهٔ همان کارهای مجاز رو انجام دهد، بدون شرط مخفی و بدون ضعیف‌کردن ضمانت؟ اگه نه، رابطه رو تحمیل نکن.

Whenever code expects a Document, can the proposed subtype honour every permitted operation without hidden conditions or weakened guarantees? If not, do not force the relationship.

inheritance رو با نمودار قشنگ انتخاب نکن؛ با رفتار کلاینت بسنجDo not choose inheritance because the diagram looks neat; test client behaviour

دو type ممکنه از نظر اسم شبیه باشن ولی رابطهٔ ارث‌بری بدی بسازن. معیار مفید اینه که کد مصرف‌کننده بتونه subtype رو جای base بذاره و همچنان قرارداد قبلی معنی داشته باشه. اگه subtype مدام مجبور می‌شه متدها رو ممنوع کنه، exception بده یا semantics رو عوض کنه، hierarchy داره چیزی رو پنهان می‌کنه.

Two types may look related by name and still form a poor inheritance relationship. A useful test is whether client code can substitute the subtype for the base type while the original contract still makes sense. If a subtype constantly disables methods, throws for valid base operations, or changes semantics, the hierarchy is hiding a design problem.

برای همین این فصل فقط `virtual` و `override` نیست. چندریختی رو از دید caller می‌بینیم، `new` و override رو کنار هم اجرا می‌کنیم و جایی که composition بهتر جواب می‌ده عمداً hierarchy رو جمع می‌کنیم.

So this chapter is not merely about `virtual` and `override`. We view polymorphism from the caller's side, run `new` hiding and overriding side by side, and deliberately replace a hierarchy with composition when that model fits better.

virtual و override: نقطهٔ توسعهٔ صریحvirtual and override: an explicit extension point

متد عادی رو derived جایگزین نمی‌کنه. virtual اعلام می‌کنه type پایه اجازهٔ رفتار متفاوت رو می‌ده؛ override آن رفتار رو عوض می‌کنه. این تصمیم بخشی از قرارداد API هست: تغییر implementation پایه ممکنه رفتار همهٔ derivedها رو عوض کند.

A derived type does not replace an ordinary method. virtual declares that the base permits variation; override supplies it. This is part of the API contract: changing base implementation may affect every derived type.

فراخوانی چندریختی / Virtual dispatch
abstract class Report
{
    public string Render() => $"Report: {RenderBody()}";
    protected abstract string RenderBody();
}

sealed class DailyReport : Report
{
    protected override string RenderBody() => "daily totals";
}

Report report = new DailyReport();
Console.WriteLine(report.Render());
خروجی / Output
Report: daily totals

متغیر از نوع Report هست اما پیاده‌سازی override شدهٔ DailyReport انتخاب می‌شه. Render رفتار مشترک رو نگه می‌داره و بخش متغیر رو به derived می‌سپارد؛ این الگو رو template method می‌نامند، اما فقط اگه چنین نقطهٔ تغییری واقعاً لازم باشه.

The variable is typed as Report, yet DailyReport’s override is selected. Render keeps shared behaviour and delegates the varying part to the subtype; this is the template-method shape, useful only when that variation point is real.

abstract برای الزام؛ sealed برای بستن ارث‌بریAbstract to require; sealed to close derivation

abstract class رو نمی‌توان مستقیم نمونه‌سازی کرد و می‌تونه عضو abstract داشته باشه که زیرنوع concrete باید پیاده کند. sealed روی کلاس جلوی ارث‌بری رو می‌گیره؛ روی override هم می‌تونه overrideهای پایین‌دست رو متوقف کند. هر دو دربارهٔ طراحی extension هستن، نه کنترل دسترسی امنیتی.

An abstract class cannot be instantiated directly and may require concrete subtypes to implement abstract members. sealed prevents deriving from a class; on an override, it can stop further overrides down the hierarchy. Both concern extensibility design, not security access control.

قرارداد ناقصِ عمدی / Intentional abstraction
abstract class Exporter
{
    public abstract string Format { get; }
    public abstract Task ExportAsync(CancellationToken cancellationToken);
}

sealed class CsvExporter : Exporter
{
    public override string Format => "text/csv";
    public override Task ExportAsync(CancellationToken cancellationToken)
        => Task.CompletedTask; // illustrative only
}

پیاده‌سازی CompletedTask فقط شکل امضا رو نشان می‌ده و export واقعی نیست. در کد اجرایی cancellation token باید در کار واقعی رعایت بشه. abstract قرارداد رو مجبور می‌کنه، ولی نمی‌تونه درستی معنایی خروجی رو ثابت کند.

CompletedTask only illustrates the signature; it is not a real export. Production work must honour the cancellation token. An abstract member forces an implementation, but cannot prove its semantic correctness.

new متد رو پنهان می‌کنه، override نمی‌کنهnew hides a method; it does not override

اگه متد پایه virtual نباشه، derived با new عضو هم‌نامی می‌سازه که dispatch چندریختی نداره. انتخاب تابع به نوع static متغیر بستگی پیدا می‌کنه؛ همین می‌تونه call siteها رو غافلگیر کند.

If a base method is not virtual, new creates a same-named member without polymorphic dispatch. Selection depends on the variable’s static type, which can surprise call sites.

پنهان‌سازی در برابر override / Hiding versus overriding
class BaseReport
{
    public void Describe() => Console.WriteLine("base");
}

class SpecialReport : BaseReport
{
    public new void Describe() => Console.WriteLine("special");
}

BaseReport item = new SpecialReport();
item.Describe();
((SpecialReport)item).Describe();
خروجی / Output
base
special

اگه base متد رو virtual و derived آن رو override کند، هر دو call مسیر derived رو اجرا می‌کنن. new معمولاً هشدار پنهان‌سازی رو به انتخاب صریح تبدیل می‌کنه؛ این کلمه dispatch رو چندریختی نمی‌کنه. اگه برای معنای یک call مجبور به cast هستی، API یا مدل subtype رو بازبینی کن.

If the base method is virtual and the derived method overrides it, both calls dispatch to the derived implementation. new makes hiding explicit; it does not make dispatch polymorphic. If a call needs a cast to mean the right thing, revisit the API or subtype model.

زیرنوع باید قرارداد پایه رو نگه دارهA subtype must preserve the base contract

فرض کن base برای هر ورودی مثبت ذخیرهٔ گزارش رو تضمین می‌کنه. derived اگه بعضی ورودی‌های مجاز رو بی‌دلیل رد کند، جایگزین امنی نیست. برعکس، خروجی ضعیف‌تر یا side effect تازه هم می‌تونه caller رو بشکند. این ایده به اصل جایگزینی Liskov نزدیک هست؛ در عمل با قراردادهای ورودی/خروجی و تست consumer می‌سنجیم.

Suppose the base promises to save a report for every valid positive input. A derived type that rejects some base-valid inputs is not a safe substitute. A weaker result or unexpected side effect can also break callers. This is the Liskov substitution idea; operationally, test input/output contracts through consumers.

اگه هر زیرنوع شرط‌های متفاوت و castهای فراوان می‌خواد، شاید به‌جای inheritance از interface کوچک و composition فصل قبل استفاده کن. جایگزینی مهم‌تر از حذف چند خط تکراری هست.

If every subtype needs different conditions and repeated casts, prefer the small interface and composition from the previous chapter. Substitutability matters more than removing a few duplicated lines.

آزمایشگاه: تغییر زیرنوع باید caller رو نشکندLab: subtype changes must not break consumers

یک Exporter پایه و دو پیاده‌سازی بساز. consumer فقط Exporter رو بشناسد. اول تست‌ها رو برای قرارداد بنویس، بعد deliberately derivedای بساز که قرارداد رو نقض کند و شکست رو ببین.

Create a base Exporter and two implementations. A consumer should know only Exporter. Write contract tests first, then deliberately violate the contract in one subtype and observe the failure.

  1. ورودی‌های معتبر و ضمانت خروجی base رو دقیق تعریف کن.
  2. Define valid inputs and the base output guarantee precisely.
  3. یک virtual/abstract variation point طراحی کن؛ فقط رفتار واقعاً متفاوت رو override کن.
  4. Add a virtual/abstract variation point and override only genuinely varying behaviour.
  5. consumer رو با reference پایه بنویس و هر دو derived رو به آن بده.
  6. Write the consumer against the base reference and pass both derived types.
  7. یکی از derivedها ورودی معتبر رو رد کند؛ تست contract رو اجرا کن.
  8. Make one subtype reject a valid input and run the contract test.
  9. new رو به‌جای override استفاده کن و دو نوع static متفاوت رو صدا بزن.
  10. Use new instead of override and call through two different static types.
  11. در پایان بگو آیا abstraction با interface/composition ساده‌تر می‌شد.
  12. Conclude whether an interface/composition would have been simpler.
معیار پایانDefinition of done

consumer بدون شرط concrete type کار می‌کنه؛ هر زیرنوع قرارداد رو حفظ می‌کنه؛ و تفاوت new و override رو با خروجی واقعی نشان داده‌ای.

The consumer has no concrete-type branches; each subtype preserves the contract; and output demonstrates the difference between new and override.
