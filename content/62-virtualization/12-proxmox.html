Proxmox

Proxmox

Proxmox وقتی جدی می‌شه که تعداد ماشین‌ها بیشتر از یکی دو تاست. اینجا فقط VM نمی‌سازیم؛ node، storage، bridge، backup و restore رو مثل یک محیط واقعی کنار هم می‌بینیم.

On a laptop, Vagrant created a VM. On a lab server we now manage guests, networks, and storage—and must know where they run, where their data lives, and how to restore them.

۱۸تمرینexercises

backup سبز شد؛ آیا ماشین واقعاً قابل‌بازیابی هست؟The backup task is green. Can you actually recover the machine?

در پنل Proxmox یک VM و یک کانتینر ساخته‌ای. شب backup job سبز شده؛ صبح VM بالا نمیاد و فایل مهمی هم روی کانتینر هست. آیا یک snapshot کافیه؟ آیا restore به همون ID، ماشین زنده رو بازنویسی می‌کنه؟ قبل از کلیک، node، storage و نوع guest رو بشناسیم.

You created a VM and a container in Proxmox. The backup job completed overnight; in the morning the VM will not boot, and an important file lives in the container. Is a snapshot enough? Would restoring to the same ID overwrite the running machine? Before clicking, let us identify the node, storage, and guest type.

Proxmox VE یک سکوی مدیریت مجازی‌سازی هست: KVM/QEMU برای VM کامل و LXC برای Linux system کانتینر، همراه شبکه bridge، storage plugin، کاربران و backup task. «node» همون میزبان Proxmox هست؛ VM و CT شناسه و تنظیمات جدا دارن، ولی منابع فیزیکی node رو شریک‌اند.

Proxmox VE is a virtualization management platform: KVM/QEMU for full VMs and LXC for Linux system containers, plus bridges, storage plugins, users, and backup tasks. A node is a Proxmox host. VMs and containers have separate IDs/configuration but share the node’s physical resources.

یک node، چند نوع guest، چند مقصد دادهOne node, guest types, and data destinations

شکل ذهنی رو این‌طور نگه دار: node میزبان هست؛ bridge مثل switch نرم‌افزاری guest رو به شبکه وصل می‌کنه؛ storage مقصد متفاوتی برای VM دیسک، rootfs، ISO/template یا backup داره. همهٔ storageها همهٔ نوع محتوا رو نمی‌پذیرن. داشتن backup روی همون node برای تمرین restore خوب هست، ولی خرابی node یا دیسک مشترک رو پوشش نمی‌ده.

Keep this model: the node is the host; a bridge is a software switch connecting guests; storage backends hold different content such as VM disks, root filesystems, ISOs/templates, or backups. Not every storage supports every content type. A same-node backup is useful for a restore rehearsal but does not protect against failure of that node or shared disk.

VM با LXC یکی نیستA VM is not the same as LXC

VM سخت‌افزار مجازی و kernel مهمان خودش رو داره؛ برای OSهای متفاوت و مرز ایزوله‌سازی قوی‌تر معمولاً انتخاب روشن‌تری هست، ولی RAM و دیسک بیشتری می‌خواد. Proxmox LXC یک Linux system کانتینر هست: فضای کاربر جدا داره، ولی kernel node رو share می‌کنه. فقط Linux؛ برای کانتینرهای برنامه‌ای مثل Docker معمولاً خود مستندات Proxmox توصیه می‌کنه Docker رو داخل VM اجرا کنی، نه اینکه LXC رو معادل اون فرض کنی.

A VM has virtual hardware and its own guest kernel; it is usually the clearer choice for different operating systems and a stronger isolation boundary, at higher RAM/disk cost. A Proxmox LXC is a Linux system container with separate user space but a shared node kernel. Linux only; Proxmox documentation generally recommends running application containers such as Docker inside a VM rather than treating LXC as equivalent.

برای تمرین، VM رو از ISO نصب می‌کنی؛ CT رو از template آماده می‌سازی. کانتینر رو تا جای ممکن unprivileged بذار و بدان root داخل CT با UID mapping به host می‌ره. privileged CT دسترسی حساس‌تری داره؛ صرف راحت‌تر بودن دلیل انتخابش نیست.

For this lab, install a VM from an ISO and create a CT from a prepared template. Prefer an unprivileged container and understand that its root is mapped through user namespaces on the host. A privileged CT carries more authority; convenience alone is not a good reason to choose it.

قبل از ساخت، ببین storage چه محتوایی می‌پذیرهCheck storage content types before creating a guest

در Datacenter → Storage، هر storage ID، نوع backend و content types داره. Directory برای فایل‌هایی مثل ISO، template و backup مناسب هست و با تنظیم درست می‌تونه دیسک image هم بگیره. LVM-thin معمولاً block volumeهای VM/CT رو میزبانی می‌کنه، نه فایل‌های ISO/backup. ZFS، NFS و Proxmox Backup Server قابلیت‌های متفاوتی دارن؛ انتخاب واقعی رو در نصب خودت ببین، نه از روی اسم.

Under Datacenter → Storage, each storage ID has a backend type and allowed content types. Directory storage suits files such as ISOs, templates, and backups and can also hold disk images when configured. LVM-thin commonly hosts VM/CT block volumes, not ISO or backup files. ZFS, NFS, and Proxmox Backup Server differ; inspect your installation instead of guessing by name.

pvesm status
cat /etc/pve/storage.cfg

pvesm status وضعیت و فضای storageهای شناخته‌شده رو نشون می‌ده؛ در Web UI هم content type هرکدام رو ببین. این خروجی وجود mount خارجی یا کیفیت backup رو ثابت نمی‌کنه. اگه storage قرمز/غیرفعال هست، task لاگ و دسترسی mount/شبکه رو بررسی کن؛ guest جدید نساز تا علت معلوم بشه.

pvesm status reports status and space for configured storage; inspect each content type in the UI too. It does not prove an external mount is healthy or backups are good. If storage is inactive, inspect task logs and mount/network access before creating more guests.

Node منبع CPU/RAM هست؛ storage جایی هست که دیسک/rootfs قرار می‌گیره. thin provisioning ظرفیت ظاهری بزرگ‌تری می‌ده، نه فضای فیزیکی نامحدود. قبل از انتخاب، هم فضای آزاد و هم datastore مقصد backup رو بررسی کن.

The node supplies CPU/RAM; storage holds guest disks/root filesystems. Thin provisioning offers larger logical capacity, not unlimited physical space. Check free space and the backup destination before choosing.

bridge رو به چشم switch ببین، نه دکمهٔ اینترنتTreat a bridge as a switch, not an Internet button

در نصب متداول، vmbr0 یک Linux bridge هست که به NIC فیزیکی node وصل می‌شه و guestها رو به LAN می‌آورد؛ هر VM روی bridge می‌تونه مثل دستگاهی جدا در شبکه دیده بشه. این رفتار اینترنت یا DHCP رو تضمین نمی‌کنه؛ router و VLAN سیاست شبکه هم مهم‌اند.

A common installation uses vmbr0, a Linux bridge connected to the node’s physical NIC, to place guests on the LAN; each VM may appear as a separate device. This does not guarantee Internet or DHCP—router and VLAN policies still matter.

در Web UI، قبل از اتصال کارت guest، bridge موجود رو از Node → System → Network بخون. روی سرور راه دور یا تنها میزبان، شبکهٔ management رو برای آزمایش تغییر نده؛ اشتباه bridge/IP می‌تونه دسترسی UI و SSH رو قطع کنه. برای lab nested، شبکهٔ bridge ممکنه محدودیت hypervisor بالادستی داشته باشه؛ NAT یا bridge داخلی رو مطابق هدف برگزین.

Before attaching a guest NIC, inspect available bridges under Node → System → Network. Never experiment on the management network of a remote or sole host; a bridge/IP mistake can disconnect the UI and SSH. Nested labs may be constrained by the upstream hypervisor; choose bridged or isolated networking for the goal.

اگه guest شبکه نداره، از تنظیمات خودش آغاز کن. فرمان‌های فقط‌خواندنی زیر فهرست VM/CT و تنظیم شبکه رو نشون می‌دن:

If a guest has no network, start with its own configuration. These read-only commands list guests and network settings:

qm list
pct list
qm config 101
pct config 201

عددها نمونه‌اند؛ قبل از فرمان، ID واقعی خودت رو پیدا کن. دنبال bridge= یا نام bridge در NIC بگرد، بعد داخل guest، address و route رو بررسی کن. تنظیمات نشون می‌ده guest به چی متصل شده؛ ثابت نمی‌کنه bridge upstream یا DHCP سالم هست.

The IDs are examples; find your actual IDs first. Look for the NIC’s bridge, then inspect address and routes inside the guest. Configuration shows the intended attachment, not that the upstream bridge or DHCP works.

یک VM و یک CT، با مسیرهای روشنCreate one VM and one CT, using clear paths

برای VM، ISO رو در storage دارای content نوع ISO بارگذاری کن؛ Create VM رو بزن، node و ID یکتا، ISO، firmware، دیسک storage/size، CPU/RAM، bridge و کاربر رو انتخاب کن. firmware و دیسک bus باید با نصاب/guest هماهنگ باشه. قبل از Finish خلاصه رو بخون. سپس کنسول رو باز کن و نصب رو مثل فصل قبل کامل کن.

For a VM, upload an ISO to storage that permits ISO content. Choose Create VM, a node and unused ID, ISO, firmware, disk storage/size, CPU/RAM, bridge, and user. Firmware and disk bus must fit the guest installer. Review the summary before finishing, then use the console to install as in the previous chapter.

برای CT، ابتدا template توزیع رو به storageای بگیر که کانتینر templates می‌پذیره. Create CT، ID آزاد، hostname، unprivileged حالت، root دیسک، CPU/RAM، password یا عمومی key و bridge/IP رو تعیین می‌کنه. template با ISO فرق داره: CT نصاب سخت‌افزار مجازی رو boot نمی‌کنه. بعد از start با pct status 201 و در UI وضعیت رو ببین؛ «running» فقط زنده‌بودن کانتینر رو نشون می‌ده.

For a CT, download a distro template to storage that accepts container templates. Create CT asks for a free ID, hostname, unprivileged mode, root disk, CPU/RAM, password or public key, and bridge/IP. A template is not an ISO: the CT does not boot virtual hardware. After start, check pct status 201 and the UI; “running” only proves the container is running.

بعد از ساخت، CLI رو برای دیدن/تغییر هدفمند استفاده کن، نه حدس زدن IDها: qm config برای VM، pct config برای CT و qm status/pct status برای وضعیت. task لاگ کنار همون عملیات می‌گه کدوم مرحله شکست خورد. اسم optionها رو از help همون نسخه بخون؛ CLI نسخه‌حساس هست.

After creation, use CLI to inspect or make a deliberate change, not to guess IDs: qm config for VMs, pct config for CTs, and status commands for state. The task log identifies the failed step. Check your version’s help because options can change.

snapshot نقطهٔ برگشت هست؛ backup راه خروجA snapshot is a rollback point; a backup is an exit path

snapshot وضعیت دیسک و گاهی وضعیت ماشین رو طبق storage/runtime ثبت می‌کنه تا تغییر آزمایشی رو برگردانی. ولی معمولاً به همون node/storage زنجیره داره؛ اگه اون storage خراب بشه، snapshot هم ممکنه بره. backup با ابزار integrated vzdump archive قابل‌بازیابی از guest و تنظیمات می‌سازه. قاعدهٔ ساده: snapshot برای rollback کوتاه؛ backup روی محدودهٔ خرابی جدا برای بازیابی.

A snapshot records disk and sometimes runtime state, depending on storage and guest, so you can roll back an experiment. It usually remains tied to the same node/storage chain; if that storage fails, the snapshot may be lost too. The integrated vzdump tool creates a guest/config archive. Think short-term rollback for snapshots and separate failure-domain recovery for backups.

در UI از VM/CT → Backup، مقصدی انتخاب کن که content type پشتیبانی‌شدهٔ backup داشته باشه؛ برای نمونه directory/NFS یا Proxmox Backup Server. برای lab می‌تونی local directory storage رو مقصد قرار دهی تا restore رو تمرین کنی، ولی این disaster recovery مستقل نیست. حالت snapshot هم سازگاری کامل application یا database رو تضمین نمی‌کنه؛ برای بار کاری stateful quiesce/guest agent و تست restore رو بررسی کن.

In the guest’s Backup view, choose a destination that supports backup content, such as directory/NFS or Proxmox Backup Server. A local directory is fine for a restore exercise, but is not independent disaster recovery. Snapshot mode does not guarantee application/database consistency; evaluate quiescing/guest-agent support and test restores for stateful workloads.

vzdump 101 --storage backup-lab --mode snapshot

ID و storage بالا نمونه‌اند. ابتدا pvesm status و نوع content مقصد رو بررسی کن؛ سپس task history رو باز کن. پایان موفق، ساخته‌شدن archive رو نشون می‌ده، نه اینکه می‌تونی اون رو restore کنی یا نسخهٔ خارج از node داری.

The ID and storage name are examples. Check storage status and allowed content first, then inspect task history. Success proves an archive was created, not that it restores or exists outside the node.

backup job زمان‌بندی‌شده رو در Datacenter → Backup تعریف کن: node/guest selection، schedule، حالت، destination و retention رو آگاهانه تعیین کن. لاگ آخرین task، زمان اجرا و exit result رو نشون می‌ده؛ فقط سبز بودن یک اجرا retention، خارج‌بودن backup از محدودهٔ خرابی یا restore موفق رو اثبات نمی‌کنه.

Schedule a job under Datacenter → Backup and choose guest selection, schedule, mode, destination, and retention deliberately. The latest task log shows run time and result; one green run does not prove retention, off-node protection, or a successful restore.

همه نباید admin باشنNot everyone should be an administrator

کاربر پنل یا API به realm و role نیاز داره؛ role روی مسیر مشخص ACL می‌گیره. برای کار روزانه فقط مجوز لازم روی pool/VM رو بده، نه root@pam credential رو به همه. root روی host می‌تونه به تمام guestها و داده‌ها برسه. برای دیدن حساب‌ها و مجوزها از Datacenter → Permissions استفاده کن؛ token/API و اطلاعات محرمانه رو در shell history یا فایل پروژه نگذار.

A UI/API user needs a realm and role; that role receives ACLs on a specific path. Grant only the permissions needed on a pool/VM, not shared root@pam credentials. Host root can access all guests and data. Inspect accounts and permissions under Datacenter → Permissions; do not leave tokens/secrets in shell history or project files.

Cluster و HA فقط دکمهٔ تک‌node نیستن: cluster چند node و ارتباط/quorum درست می‌خواد؛ HA برای restart/failover روی node دیگر به ظرفیت و طراحی واقعی نیاز داره. در lab تک‌node، فقط مفهوم رو بشناس؛ یک node جای redundancy رو نمی‌گیره.

Cluster and HA are not single-node buttons. Clustering needs multiple nodes and correct communication/quorum; HA restart/failover needs capacity and a real design. In a single-node lab, learn the concepts—a lone node is not redundancy.

خرابی آزمایشگاه: guest روی bridge اشتباه هستLab incident: the guest is on the wrong bridge

یک VM باید از LAN آزمایشگاهی IP بگیره ولی شبکه نداره. قبل از دست‌زدن به شبکه node، تنظیمات VM رو بخون: آیا NIC به bridge موجود و موردانتظار وصل هست؟ سپس task لاگ و داخل guest، link/IP/route/DHCP رو بررسی کن. اگه bridge انتخابی اصلاً در node نیست یا uplink نداره، تغییر فقط NIC همون VM رو تعمیر کن؛ به vmbr0 مدیریتی host دست نزن.

A VM should receive an address from the lab LAN but has no network. Before changing node networking, inspect the VM NIC: is it attached to an existing, intended bridge? Then check task logs and guest link/address/routes/DHCP. If the chosen bridge is absent or has no uplink, repair only this VM’s NIC; do not alter the host’s management bridge.

خرابی دوم: backup task می‌گه storage مقصد از نوع backup پشتیبانی نمی‌کنه یا storage offline هست. از UI task لاگ و pvesm status شاهد بگیر؛ بعد storageای انتخاب کن که backup content رو می‌پذیره و available هست. گزینهٔ delete/format برای «درست‌شدن storage» این تمرین نیست.

Second fault: the backup task says its destination does not support backup content or is offline. Use the UI task log and pvesm status as evidence, then choose an available storage that accepts backups. Deleting or formatting storage is not a repair for this exercise.

آزمایش: backup بگیر و به ID تازه برگردانLab: back up and restore under a new ID

این آزمایش رو روی Proxmox آزمایشگاهی یا میزبان nested پشتیبانی‌شده انجام بده، نه روی node محیط عملیاتی. nested virtualization ممکنه KVM acceleration یا شبکه bridge رو محدود کنه؛ اگه VM تو نمی‌تونه KVM رو ببینه، تمرین nested رو زورکی ادامه نده و از سرور lab/سخت‌افزار مناسب استفاده کن.

Run this on a lab Proxmox host or a supported nested host, never a production node. Nested virtualization may limit KVM acceleration or bridged networking; if the VM cannot access KVM, do not force the nested exercise—use a lab server or suitable hardware.

  1. در node، storage وضعیت/content و IDهای مصرف‌شده رو ببین. backup destination رو مشخص کن؛ در lab همون local directory قابل‌قبول هست، با یادداشت اینکه مستقل نیست.
  2. Inspect node storage status/content and used IDs. Choose a backup destination; a local directory is fine for lab, documented as non-independent.
  3. یک VM کوچک با ISO بساز و یک فایل شناسایی داخلش ایجاد کن؛ مثلاً /etc/lab-marker. از اون یک تصویر/یادداشت نگیر—خود فایل رو بعد restore می‌خونیم.
  4. Create a small VM from ISO and write a marker file such as /etc/lab-marker. We will read the file after restore rather than trust a screenshot.
  5. یک CT از template بساز، اون رو unprivileged نگه دار و داخلش فایل marker دیگری ثبت کن.
  6. Create a CT from a template, keep it unprivileged, and add a second marker file.
  7. برای هر دو guest backup بگیر. task لاگ، archive و زمان اجرا رو ثبت کن.
  8. Back up both guests and record task log, archive, and completion time.
  9. به IDهای تازه restore کن؛ قبل از start شدن، NICها رو بررسی کن تا IP تکراری وارد LAN نشه. سپس marker، سرویس و data رو بررسی کن.
  10. Restore to new IDs. Inspect NICs before starting to avoid duplicate LAN IPs, then verify marker, service, and data.
  11. خرابی bridge رو فقط روی NIC guest بازسازی و با تنظیمات/address/route تشخیص بده؛ سپس backup مقصد نامعتبر رو از task لاگ تشخیص بده. تعمیر رو اعمال و task رو دوباره بررسی کن.
  12. Reproduce a wrong guest bridge and diagnose via config/address/routes; then identify an invalid backup target from the task log. Repair and rerun verification.

پایان آزمایش: از VM و CT restored marker رو بخون؛ این ثابت می‌کنه archive قابل restore بوده و دادهٔ نمونه برگشته. ثابت نمی‌کنه backup off-node، application-consistent یا برنامهٔ پشتیبان‌گیری محیط عملیاتی کامل هست.

Lab proof: Read the marker from restored VM and CT. This proves the archive restored and sample data returned; it does not prove off-node protection, application consistency, or production backup coverage.

تمرین‌هاExercises

۱. node یعنی چه؟

در صفحهٔ VM، node به کدوم بخش اشاره داره؟

What does “node” mean on the VM page?

پاسخ

میزبان Proxmox که guest روی منابعش اجرا می‌شه.

The Proxmox host supplying the guest’s resources.

۲. VM یا CT؟

guest به kernel سفارشی نیاز داره. انتخاب ساده‌تر؟

A guest needs its own custom kernel. Which is the straightforward choice?

پاسخ

VM؛ LXC kernel node رو share می‌کنه.

A VM; LXC shares the node kernel.

۳. Docker داخل LXC

آیا LXC رو خودکار معادل Docker کانتینر بگیریم؟

Should LXC automatically be treated as a Docker container?

پاسخ

نه؛ LXC system کانتینر هست. برای Docker، VM انتخاب پیشنهادی روشن‌تری هست.

No; LXC is a system container. A VM is the clearer recommended place for Docker.

۴. unprivileged

مزیت کلی unprivileged CT چیست؟

What is the general advantage of an unprivileged CT?

پاسخ

UID mapping، root داخل CT رو به کاربر غیرممتاز host نگاشت می‌کنه و authority رو کاهش می‌ده؛ بی‌خطر مطلق نیست.

UID mapping maps container root to an unprivileged host user, reducing authority; it is not risk-free.

۵. ISO آپلود نمی‌شه

احتمالاً چه تنظیمی storage رو محدود کرده؟

Which storage property may be limiting the upload?

پاسخ

محتوای ISO در content types فعال نیست یا storage unavailable/پر هست؛ storage ID و task لاگ رو ببین.

ISO content may not be enabled, or storage may be unavailable/full; inspect its ID and task log.

۶. template و ISO

چرا CT رو از ISO معمولی نصب نمی‌کنی؟

Why not install a CT from a regular ISO?

پاسخ

CT با rootfs template ساخته می‌شه؛ ISO برای boot نصاب در VM هست.

A CT is created from a root-filesystem template; an ISO boots a VM installer.

۷. bridge موجود نیست

guest به vmbr9 وصل شده ولی node اون رو نداره. قدم امن؟

A guest uses vmbr9, which the node lacks. Safe next step?

پاسخ

تنظیمات و bridgeهای موجود رو بخون؛ NIC همون guest رو به bridge تأییدشده وصل کن، نه اینکه management شبکه رو دستکاری کنی.

Inspect guest config and existing bridges; attach that guest NIC to a verified bridge, not by editing management networking.

۸. vmbr0

No; uplink, DHCP/router, and VLAN/firewall must also work.

۹. ID اشغال‌شده

۱۰. دیسک در local-lvm

۱۱. snapshot جای backup

storage خراب شده؛ چرا snapshot کمکی نمی‌کنه؟

Storage failed. Why might a snapshot not help?

پاسخ

snapshot معمولاً به همون storage/chain وابسته هست؛ backup مستقل باید محدودهٔ خرابی دیگری داشته باشه.

A snapshot usually depends on the same storage/chain; independent backup needs another failure domain.

Restore, off-node protection, application consistency, and external data coverage; perform a restore test.

۱۳. مقصد backup رد می‌شه

پاسخ

storage ID، content types، availability و task لاگ؛ storage رو حذف/فرمت نکن.

Storage ID, content types, availability, and task log; do not delete or format it.

۱۴. restore به ID تازه

۱۵. backup job

Which decisions belong in a scheduled job?

Guest selection, schedule, mode, destination, retention, and task-log review; one successful run guarantees none of the rest.

۱۶. cluster تک‌node

آیا یک node می‌تونه HA واقعی در node دیگر بده؟

Can one node provide real HA on another node?

No; another node, quorum, and capacity are needed. One node demonstrates concepts, not redundancy.

۱۷. دسترسی پنل

A user/realm with a minimal role on that VM path—not shared root@pam credentials.

۱۸. اثبات restore

چه نتیجه‌ای restore موفق marker رو می‌ده و چی رو نمی‌ده؟

What does restoring a marker prove—and not prove?

معیار پاسخ

قابل‌خواندن‌بودن archive و برگشت اون فایل رو ثابت می‌کنه؛ backup مستقل، application-consistent یا recovery کامل رو نه.

It proves the archive was readable and that file returned; not independent backup, application consistency, or complete recovery.

ماشین‌ها رو بساز؛ راه بازگشت رو هم ثابت کنCreate the guests—and prove the way back

Proxmox رو با node، guest، bridge، storage، task و ACL بخون. VM kernel خودش رو داره؛ CT kernel میزبان رو شریک هست. bridge اتصال می‌ده، نه تضمین شبکه. snapshot rollback کوتاه هست، backup archive برای restore؛ و هیچ‌کدوم تا وقتی به ID تازه برنگردانی و داده رو نخوانی، بازیابی اثبات‌شده نیستن.

Read Proxmox through nodes, guests, bridges, storage, tasks, and ACLs. A VM has its own kernel; a CT shares the host kernel. A bridge provides attachment, not guaranteed connectivity. A snapshot is short-term rollback; a backup is a restore archive—and neither is proven until you restore to a new ID and inspect data.
