snapshot و کلون

Snapshots and clones

یک تغییر پرریسک لازم داری آزمایش کنی؛ snapshot راه برگشت سریعی می‌دهد، ولی اگر آن را backup حساب کنی ممکن است دقیقاً همان روزی که لازم داری کمکت نکند.

You need to test a risky change. A snapshot gives you a quick way back, but treating it as a backup may leave you without help on the day you need it.

۱۸تمرینexercises

به‌روزرسانی نیمه‌کاره شد؛ یک کلیک تا قبلش برگردیم؟An update went halfway wrong. Can one click take us back?

VM آزمایشگاهی‌ات درست کار می‌کند. می‌خواهی نسخهٔ تازهٔ packageها را نصب کنی؛ اگر boot خراب شد چه؟ کپی‌گرفتن از کل دیسک وقت می‌گیرد، پس قبل تغییر یک snapshot می‌سازی. به حالت پایه برمی‌گردی و packageها ناپدید شده‌اند—اما آیا این یعنی از داده‌ات backup داشتی؟

Your lab VM works. You want to install newer packages; what if it no longer boots? Copying the entire disk takes time, so you create a snapshot first. You revert to the baseline and the packages are gone—but does that mean your data was backed up?

نه؛ snapshot بیشتر شبیه نقطهٔ بازگشت در زنجیرهٔ همان VM است. برای آزمایش عالی است، اما معمولاً روی همان host و همان زنجیرهٔ disk می‌ماند. امروز یک snapshot می‌سازیم، تغییر می‌دهیم و برمی‌گردیم؛ بعد clone لینک‌شده را از پایه جدا می‌کنیم تا وابستگی پنهانش را ببینیم.

No. A snapshot is more like a rollback point in the same VM and disk chain. It is excellent for experiments, but usually remains on the same host and in the same disk chain. Today we take a snapshot, make a change, revert, then inspect the hidden dependency in a linked clone.

snapshot ذخیرهٔ زمان است، نه الزاماً فایل کاملA snapshot records a point in time, not necessarily a whole copy

برای فهمیدن snapshot، به فصل storage برگرد: virtual disk یک image و یک فایل‌سیستم مهمان است. در VirtualBox وقتی snapshot می‌گیری، وضعیت تنظیمات و دیسک را ثبت می‌کند و برای نوشتن‌های بعدی differencing image می‌سازد. بخش پایه تا وقتی تغییر نکرده مشترک می‌ماند؛ دادهٔ تازه در delta می‌رود. بنابراین snapshot اولیه ممکن است کم‌حجم باشد، اما delta با گذشت زمان رشد می‌کند.

Recall the storage chapter: a virtual disk is an image behind a guest filesystem. In VirtualBox, a snapshot records settings and disk state, then writes later changes into a differencing image. Unchanged data remains in the base; new writes go into the delta. The initial snapshot may be small, but the delta grows over time.

پیکان بالا، گذر زمان VM است؛ پیکان پایین، وابستگی delta به base. snapshot گرفتن لزوماً یک image کامل و مستقل نمی‌سازد.

The top arrows show VM time; the lower arrow shows the delta’s dependency on its base. A snapshot does not necessarily create a complete independent image.

برای نمونهٔ دوره از VirtualBox استفاده می‌کنیم چون رابط snapshot و clone را در hostهای رایج نشان می‌دهد. در release فعلی این دوره مستند Oracle برای VirtualBox 7.2 است؛ در نسخه‌های دیگر اسم منو یا رفتار بعضی نوع‌های ذخیره‌سازی ممکن است فرق کند. در KVM/libvirt هم snapshot و clone داریم، اما نوع internal/external و پشتیبانی disk format مهم است؛ فرمان VirtualBox را به QEMU تعمیم نده.

This chapter uses VirtualBox for the hands-on workflow because its snapshot and clone controls are available on common desktop hosts. The current course reference is Oracle’s VirtualBox 7.2 documentation; menu names and storage behaviour can vary by release. KVM/libvirt also supports snapshots and clones, but internal/external types and disk-format support matter—do not apply VirtualBox commands to QEMU.

خاموش، روشن یا saved state؟ فرق داردPowered off, running, or saved state? It matters

snapshotی که از VM خاموش‌شده می‌گیری، دیسک مهمان را در وضعی می‌بیند که OS فرصت shutdown داشته؛ معمولاً نقطهٔ ساده‌تری برای تمرین است. VirtualBox می‌تواند هنگام اجرای VM هم snapshot بگیرد و state حافظه را ذخیره کند؛ restore همان برنامه‌ها را از همان نقطه ادامه می‌دهد، و فایل memory ممکن است به‌اندازهٔ RAM VM باشد. این با «ذخیرهٔ فقط دیسک» یکی نیست.

A snapshot of a powered-off VM captures a guest disk after the OS had a chance to shut down, usually the simpler state for a lab. VirtualBox can also snapshot a running VM and save its memory state; restoring resumes programs from that point, and the memory file may be as large as the VM’s RAM. That is not the same as a disk-only point.

اما «snapshot زنده» خودبه‌خود application-consistent نیست. اگر guest یا database داده‌ای را در حافظه/صف write نگه داشته باشد، فقط متوقف‌کردن VM تضمین نمی‌کند تراکنش برنامه clean ثبت شده باشد. crash-consistent یعنی دیسک شبیه سیستمی است که ناگهان برقش رفته؛ application-consistent نیازمند quiesce یا backup protocol خود برنامه است. برای آزمایش ساده guest را orderly shutdown کن؛ برای پایگاه‌دادهٔ واقعی snapshot را جای backup سازگار با دیتابیس نگذار.

A “live snapshot” is not automatically application-consistent. A guest or database may have data in memory or queued for writing; pausing the VM does not guarantee the application committed transactions cleanly. Crash-consistent state resembles a system after sudden power loss. Application consistency requires application-specific quiescing or backup protocols. For a simple lab, shut the guest down cleanly; never substitute a VM snapshot for a database-aware backup.

پیش از snapshot بپرس: آیا فقط می‌خواهم OS را بعداً rollback کنم، یا می‌خواهم نسخه‌ای مستقل برای بازیابی حادثه داشته باشم؟ اولی شاید snapshot باشد؛ دومی نیاز به backup جدا، ترجیحاً روی رسانه/مقصد دیگری و با restore test دارد.

Before taking a snapshot, ask: do I only want to roll the OS back later, or do I need an independent copy for disaster recovery? The first may call for a snapshot; the second needs a separate backup, preferably on another medium or destination, and a restore test.

یک نقطهٔ بازگشت بساز و اثرش را ببینCreate a rollback point and observe its effect

یک VM disposable با نام `lab-base` را به‌روز و خاموش کن. در VirtualBox Manager از تب Snapshots گزینهٔ Take را بزن و نامی مثل `clean-before-test` و توضیحی بگذار که چه چیزی در آن سالم است. اسم snapshot فقط label است؛ اگر description دقیق ننویسی چند روز بعد معنایش را یادت نمی‌آید.

Update a disposable VM named `lab-base` and shut it down. In VirtualBox Manager, open Snapshots, choose Take, and name it `clean-before-test` with a description of what is known-good. The snapshot name is only a label; without a useful description, its meaning may be unclear later.

VM را روشن کن و یک تغییر قابل‌دیدن بساز، مثلاً فایل `/tmp/snapshot-marker` را با متن `after snapshot` بنویس. بعد خاموشش کن، در تب Snapshots نقطهٔ `clean-before-test` را انتخاب و Restore بزن. تأیید کن که current state فعلی کنار گذاشته می‌شود؛ اگر می‌خواهی آن را هم نگه داری، پیش از restore یک snapshot دیگر بگیر یا از clone استفاده کن.

Start the VM and make a visible change, such as writing `after snapshot` to `/tmp/snapshot-marker`. Shut it down, select `clean-before-test` in Snapshots, and choose Restore. Confirm that the current state is discarded; if you need to keep it, take another snapshot first or use a clone.

# Inside the guest, before reverting
printf 'after snapshot\n' | sudo tee /tmp/snapshot-marker
cat /tmp/snapshot-marker

# After restoring and booting the snapshot
test -e /tmp/snapshot-marker; echo $?

اگر marker بعد از restore وجود ندارد، شاهد خوبی است که disk state به نقطهٔ قبلی برگشته؛ این ثابت نمی‌کند فایل snapshot بیرون host هم موجود است یا می‌تواند host خراب را بازیابی کند. در VirtualBox حذف snapshot از فهرست معمولاً فایل‌ها/deltaها را merge می‌کند؛ ممکن است طول بکشد و موقتاً فضای host بخواهد. حذف snapshot مساوی حذف VM یا rollback به snapshot نیست.

If the marker is absent after restore, that is good evidence the disk state returned to the earlier point. It does not prove snapshot files exist outside the host or can recover a failed host. In VirtualBox, deleting a snapshot may merge its differencing data and take time or temporary host space. Deleting a snapshot is not the same as deleting the VM or reverting to it.

CLI هم امکان مشاهده دارد: `VBoxManage snapshot "lab-base" list --details` نام و درخت snapshotهای ثبت‌شده را نشان می‌دهد. این فهرست فقط وجود metadata را ثابت می‌کند؛ سلامت همهٔ parent imageها را نه. مسیرها و commandها به نام VM و نسخهٔ نصب بستگی دارند.

The CLI can also inspect state: `VBoxManage snapshot "lab-base" list --details` lists registered snapshots and their tree. This proves metadata is present, not that every parent image is healthy. Names and commands depend on the VM and installed version.

VBoxManage snapshot "lab-base" list --details
VBoxManage showvminfo "lab-base"

snapshot زیاد، زنجیره و فضای مصرفی را زیاد می‌کندMore snapshots mean a longer chain and more storage use

هر snapshot تازه می‌تواند delta تازه‌ای به مسیر بنویسد. چند نقطهٔ بازگشت مثل شاخه‌های تاریخچه می‌شوند: برای خواندن بلوک ممکن است از بخش پایه و چند differencing image کمک گرفته شود. تعداد زیاد snapshotها و نوشتن‌های زیاد، مدیریت و I/O را پیچیده‌تر می‌کند؛ هزینه دقیق به فرمت و hypervisor بستگی دارد. به همین دلیل snapshotهای آزمایشی قدیمی را بی‌برنامه تلنبار نکن.

Each new snapshot can add another delta to the write path. Multiple rollback points resemble branches in a history: reading a block may involve the base and several differencing images. Many snapshots and many writes complicate management and I/O; exact cost depends on the format and hypervisor. Do not accumulate old experimental snapshots indefinitely.

در VirtualBox تب Snapshots درخت را نشان می‌دهد و Virtual Media Manager می‌تواند وضعیت disk imageها را روشن کند. برای linked clone، فرق نام VM و فایل image را دنبال کن: حذف یک entry از لیست، حذف فایل‌ها، mergeکردن delta و حذف base چهار عمل متفاوت‌اند. پیش از Delete در پنجرهٔ تأیید دقیق بخوان چه چیزی حذف یا ادغام می‌شود.

In VirtualBox, the Snapshots view shows the tree, and Virtual Media Manager can help inspect disk images. For a linked clone, distinguish the VM list entry from the image files: removing a list entry, deleting files, merging a delta, and deleting a base are four different operations. Read the confirmation dialog carefully before choosing Delete.

کلون کامل یا لینک‌شده؟ هزینه را جابه‌جا می‌کنیFull or linked clone? You are moving the cost

full clone فایل‌های وابستهٔ VM را کپی می‌کند؛ فضای بیشتری می‌خواهد و زمان ساختش به اندازهٔ دیسک‌ها بستگی دارد، اما می‌تواند بدون VM پایه کار کند. linked clone یک differencing disk روی disk پایه می‌سازد؛ شروعش کم‌جا و سریع‌تر است، ولی برای بلوک‌های تغییرنکرده به base وابسته می‌ماند. وابستگی‌اش را جدی بگیر: جابه‌جایی یا حذف image پایه می‌تواند clone را از boot بیندازد.

A full clone copies the VM’s dependent disk images. It needs more space and takes time proportional to the disks, but can operate without the source VM. A linked clone creates a differencing disk over the base disk; it is quicker and initially smaller, but still depends on the base for unchanged blocks. Moving or deleting that base can make the clone fail to boot.

در linked clone فلش به base یعنی وابستگی داده، نه صرفاً رابطهٔ مدیریتی. full clone حافظهٔ جدا می‌گیرد؛ هر دو clone همچنان نیازمند مدیریت جداگانهٔ MAC، hostname و identity سیستم‌عامل‌اند.

For a linked clone, the arrow to the base represents a data dependency, not just a management relationship. A full clone has its own disk copy; both still need unique MAC, hostname, and OS identity when used together.

در Wizard کپی VirtualBox، گزینهٔ Generate New MAC Addresses را وقتی source و clone قرار است کنار هم در یک شبکه باشند حفظ کن؛ MAC تکراری ممکن است اتصال را گیج کند. clone کردن دیسک، الزاماً machine-id یا hostname مهمان را عوض نمی‌کند؛ این‌ها را برای سناریوی شبکه بررسی کن، وگرنه دو Linux ممکن است هویت مشابه داشته باشند.

In the VirtualBox Clone wizard, keep Generate New MAC Addresses selected when source and clone will coexist on one network; duplicate MACs can confuse connectivity. Cloning a disk does not necessarily change the guest hostname or machine-id; review them for a networked scenario or two Linux guests may share identity.

خرابی عمدی: clone لینک‌شده base را پیدا نمی‌کندDeliberate failure: the linked clone cannot find its base

این آزمایش فقط روی VM و linked clone یک‌بارمصرف انجام می‌شود؛ نه روی VM اصلی یا دیسکی که داده‌اش لازم است. ابتدا از base یک Full Clone مستقل بساز و مطمئن شو boot می‌شود؛ آن را خاموش کن. از یک clone جدا، Linked Clone بساز و boot موفق را ثبت کن. در Virtual Media Manager یا تنظیمات storage، delta و media والد را بررسی و screenshot/یادداشت بگیر.

Run this only on disposable VMs and a disposable linked clone—never the original or a disk with needed data. First make an independent Full Clone from the base and verify that it boots; shut it down. Create a separate Linked Clone and verify it boots. Inspect the delta and parent media in Virtual Media Manager or storage settings, and save the evidence.

حالا base را از VirtualBox Manager حذف نکن. برای شبیه‌سازی، وقتی هر دو VM خاموش‌اند یک کپی disposable جدا در پوشهٔ آزمایش بساز؛ از Virtual Media Manager گزینهٔ Show in Explorer/Finder را برای source پیدا کن و فقط همان کپی base را موقتاً به نامی دیگر تغییر بده. linked clone را start کن؛ انتظار می‌رود missing medium/backing file بگوید. اگر رابط اجازهٔ safely moving فایل managed را نمی‌دهد، این مرحله را فقط با نمایش وابستگی در media details انجام بده—لازم نیست چیزی را دست‌کاری کنی.

Do not remove the base from VirtualBox Manager. To simulate the problem, with both VMs off, create a separate disposable copy in a lab folder; use Show in Explorer/Finder from Virtual Media Manager to locate the source, then temporarily rename only that copied base. Start the linked clone; expect a missing-medium/backing-file error. If the UI will not safely move a managed file, demonstrate the dependency in media details instead—no file manipulation is required.

ثبت کن کدام مسیر در خطا نام برده شده و آیا full clone هنوز بالا می‌آید. حالا base آزمایشی را دقیقاً به نام و محل قبلی برگردان و linked clone را دوباره start کن. این repair فقط وابستگی را برمی‌گرداند؛ اگر media واقعی جابه‌جا شده باشد، از مدیریت media/hypervisor برای relink استفاده کن. فایل پایه را برای «آزادکردن فضا» حذف نکن.

Record the path named by the error and whether the full clone still starts. Restore the test base to exactly its former name and location, then start the linked clone again. This repair restores the dependency; if a real medium was moved, use the hypervisor’s media management to relink it. Never delete a base to “free space.”

نکته: جابه‌جایی فایل‌های ثبت‌شدهٔ VirtualBox خارج از UI می‌تواند registry رسانه را هم درگیر کند. اگر نمی‌توانی مطمئن شوی فقط یک کپی جدا را تغییر می‌دهی، fault را شبیه‌سازی نکن؛ dependency را از مسیر media و backing chain نشان بده.

Note: Moving VirtualBox-registered files outside its UI can also affect the media registry. If you cannot prove you are changing only a separate copy, do not simulate the fault; demonstrate the dependency through media details and the backing chain instead.

چرا snapshot backup نیست؟Why is a snapshot not a backup?

snapshot معمولاً کنار VM و deltaهایش روی همان host می‌ماند. خرابی دیسک میزبان، سرقت دستگاه، حذف اشتباه chain یا کمبود فضا ممکن است VM و snapshot را هم‌زمان از بین ببرد. restore هم VM را به همان تاریخ قدیمی برمی‌گرداند؛ داده‌ای که بعد snapshot تولید شده عمداً از current state حذف می‌شود. این رفتار برای آزمایش مفید است و برای بازیابی فایل امروز، خطرناک.

A snapshot usually lives beside the VM and its deltas on the same host. Host-disk failure, theft, accidental chain removal, or low storage can take out both VM and snapshot. Restoring also returns the VM to an older point; data created afterward is intentionally removed from the active state. That is useful for experiments and risky for recovering today’s files.

backup باید نسخه‌ای مستقل از زنجیرهٔ فعال باشد و مقصد/retention مناسب داشته باشد؛ برای سرویس مهم، سازگاری برنامه و restore test هم لازم است. Full clone هم الزاماً backup نیست: اگر همان host یا همان storage را share کند، از بعضی ریسک‌ها جدا نشده و ممکن است هنوز config/secretها را کپی کرده باشد. اسم عملیات تضمین بازیابی نیست.

A backup should be independent of the active chain and have a suitable destination and retention policy; important services also need application consistency and a restore test. A full clone is not automatically a backup either: if it shares the same host or storage, some risks remain, and it may copy configuration or secrets. An operation’s name is not a recovery guarantee.

آزمایش یکپارچه: نقطهٔ تمیز، تغییر، برگشت، کلونIntegrated lab: clean point, change, restore, clone

با VM disposable `lab-base` شروع کن. guest را clean shutdown کن؛ snapshot `clean-before-test` بساز و timestamp/توضیح را یادداشت کن. VM را روشن کن، marker فایل بساز و package آزمایشی غیرحیاتی نصب کن. بعد shutdown و restore انجام بده. پس از boot، نبودن marker/برگشت package state را بررسی کن. شاهد، فایل و package در guest است—not فقط اینکه UI کلمهٔ Restore را نمایش داده.

Start with disposable `lab-base`. Cleanly shut down the guest, create `clean-before-test`, and note its timestamp/description. Boot, write a marker file, and install a nonessential test package. Shut down and restore. After boot, check that the marker/package state reverted. The evidence is the guest’s file and package state—not merely the UI displaying “Restore.”

حالا ماشین را خاموش کن و دو clone بساز: یکی Full و یکی Linked. boot هر دو را تأیید کن و حجم تقریبی base/deltaها را در Virtual Media Manager ثبت کن؛ اندازه‌ها با host filesystem و تاریخچه تغییر فرق دارند، پس انتظار عدد ثابت نداشته باش. تغییر hostname در cloneها را یادداشت کن و اگر هر دو شبکه دارند MAC تازه را بررسی کن.

Now power off the machine and create one Full and one Linked clone. Verify both boot and record approximate base/delta sizes in Virtual Media Manager; sizes depend on host filesystem and write history, so there is no universal number. Note hostname identity and check regenerated MAC addresses if both clones will use a network.

در آخر linked clone را خاموش و فقط dependency را از مسیر UI مستند کن. اگر برای نمایش خطای missing base تجربهٔ امن داری، از clone و base disposable استفاده کن و file را دقیقاً restore کن؛ در غیر این صورت simulated failure تمرین کافی است: پیش‌بینی کن linked clone بدون parent چه می‌شود و چرا full clone رفتارش فرق دارد. هیچ disk image اصلی را پاک نکن.

Finally, shut down the linked clone and document its dependency in the UI. If you can safely demonstrate a missing-base error, use only disposable clone/base files and restore the file exactly. Otherwise, a simulated fault is enough: predict why a linked clone fails without its parent and why the full clone differs. Do not delete original images.

گزارش کوتاه: بنویس snapshot چه چیزی را برگرداند، کدام فایل بعدش ناپدید شد، linked clone به چه pathی وابسته است و کدام نسخه بدون base اجرا شد. کنار آن توضیح بده چه backup جداگانه‌ای لازم بود تا خرابی host را هم پوشش دهد.

Short report: State what the snapshot reverted, which later file disappeared, which path the linked clone depends on, and which copy ran without the base. Then describe what separate backup would be needed to cover host failure.

۱. برگشت ساده

پیش از update یک snapshot داری؛ بعد package خراب نصب می‌شود. snapshot برای چه کاری مناسب است؟

You have a snapshot before an update; a bad package is installed afterward. What is the snapshot useful for?

پاسخ

بازگشت سریع VM آزمایشی به state پیشین؛ نه جایگزین backup مستقل برای خرابی host.

Quickly returning the lab VM to an earlier state, not replacing an independent backup for host failure.

۲. delta بزرگ شده

snapshot در ابتدا چند MiB بود و چند هفته بعد delta چندین GiB است. تناقض است؟

A snapshot initially occupied a few MiB, then its delta grew to several GiB over weeks. Is that contradictory?

پاسخ

نه؛ نوشتن‌های بعد از snapshot در differencing image جمع می‌شوند. هزینه به الگوی تغییر و فرمت بستگی دارد.

No. Writes since the snapshot accumulate in a differencing image. The cost depends on change patterns and format.

۳. snapshot زنده برای database

از VM روشن snapshot می‌گیری و ادعا می‌کنی database حتماً application-consistent است. چرا این ادعا زیاد است؟

You snapshot a running VM and claim its database is definitely application-consistent. Why is that too strong?

پاسخ

snapshot زنده می‌تواند memory state را نگه دارد، اما transactionها و writeهای application را لزوماً quiesce/commit نمی‌کند. backup دیتابیس-aware لازم است.

A live snapshot may preserve memory state, but does not necessarily quiesce or commit application transactions. Use a database-aware backup method.

۴. فایل marker

marker بعد snapshot ساخته شد؛ بعد از restore نیست. دقیقاً چه ادعایی را پشتیبانی می‌کند؟

A marker was created after the snapshot and is absent after restore. Which claim does this support?

پاسخ

دیسک مهمان به نقطهٔ قبلی برگشته؛ این به‌تنهایی سلامت backup خارج از host یا recovery از خرابی میزبان را ثابت نمی‌کند.

The guest disk returned to an earlier point. This alone proves neither an off-host backup nor recovery from host failure.

۵. برق ناگهانی و سازگاری

crash-consistent با application-consistent چه فرقی دارد؟

What distinguishes crash-consistent from application-consistent state?

پاسخ

اولی شبیه قطع برق است و application ممکن است flush/transaction نیمه‌کاره داشته باشد؛ دومی با هماهنگی/ quiesce خود برنامه وضعیت سازگار می‌سازد.

The first resembles sudden power loss and may leave application writes/transactions unfinished; the second coordinates or quiesces the application into a consistent point.

۶. Save State یا snapshot؟

می‌خواهی برنامه‌های باز VM را بعداً دقیقاً از همان لحظه ادامه دهی، نه چند نقطهٔ تاریخچه داشته باشی. کدام مفهوم نزدیک‌تر است؟

You want to resume open programs later from the same moment, not keep multiple history points. Which concept is closer?

پاسخ

Saved state/suspend. snapshot ممکن است memory را هم ذخیره کند، اما برای تاریخچه و rollback با مدیریت disk state استفاده می‌شود.

Saved state/suspend. A snapshot can include memory too, but it is managed as a rollback/history point for disk state.

۷. full clone

می‌خواهی VM را به host دیگری ببری و دیگر به base این host وابسته نباشد. کدام نوع clone مناسب‌تر است؟

You want to move a VM to another host without depending on this host’s base. Which clone type is closer?

پاسخ

Full clone، چون dependent diskها را کپی می‌کند و بدون source قابل‌اجراست؛ با این حال export/انتقال و restore test همچنان لازم است.

A full clone copies dependent disks and can run without the source; export/transfer and restore testing are still required.

۸. clone کم‌حجم

linked clone سریع ساخته می‌شود و کم‌جا است. چه هزینه‌ای در برابرش می‌دهی؟

A linked clone is quick and initially small. What is the trade-off?

پاسخ

وابستگی به image پایه؛ باید base و زنجیره را سالم و در همان محل نگه داری.

Dependency on the base image; its chain and location must remain available.

۹. base گم شد

linked clone خطای missing medium می‌دهد ولی full clone boot می‌شود. کدام فرضیه اولویت دارد؟

A linked clone reports a missing medium while the full clone boots. Which hypothesis has priority?

پاسخ

مسیر یا ثبت backing/base linked clone را بررسی کن؛ full clone data copy مستقل دارد. فایل حذف‌شده را با حدس نساز، path را از chain/manager بخوان.

Inspect the linked clone’s base path/registration; the full clone has an independent data copy. Do not guess the missing filename—read the chain/manager details.

۱۰. MAC یکسان

source و clone هم‌زمان روی یک network می‌آیند؛ چرا MAC تازه مهم است؟

The source and clone will coexist on one network. Why does a new MAC matter?

پاسخ

MAC تکراری به conflict در layer 2 منجر می‌شود؛ Clone wizard را روی Generate New MAC قرار بده. hostname و identity guest را هم جدا بررسی کن.

Duplicate MACs cause a layer-2 conflict. Keep Generate New MAC selected in the clone wizard, and review guest hostname/identity too.

۱۱. حذف snapshot

Delete روی snapshot زدی. آیا VM به آن نقطه برمی‌گردد؟

You clicked Delete on a snapshot. Does the VM revert to that point?

پاسخ

نه؛ delete، نقطهٔ snapshot را از history حذف/merge می‌کند؛ restore عمل جداگانه است. متن dialog و current state را پیش از تأیید بخوان.

No. Delete removes/merges the snapshot point; restore is a separate operation. Read the dialog and check current state before confirming.

۱۲. چرا delete طول می‌کشد؟

حذف snapshot چند دقیقه طول می‌کشد و فضای موقت بالا می‌رود. نشانهٔ خرابی است؟

Deleting a snapshot takes minutes and temporary storage use rises. Does this prove corruption?

پاسخ

نه لزوماً؛ mergeکردن deltaها ممکن است I/O و فضای موقت بخواهد. host free space و progress/error hypervisor را ببین و process را ناگهانی قطع نکن.

Not necessarily; merging deltas can require I/O and temporary space. Check host free space and hypervisor progress/errors; do not kill the operation abruptly.

۱۳. host از دسترس خارج شد

VM و snapshot هر دو روی تنها دیسک host بودند و دیسک خراب شده. آیا snapshot کمکی می‌کند؟

The VM and snapshot were on the host’s only disk, which failed. Does the snapshot help?

پاسخ

احتمالاً نه؛ snapshot همان failure domain را share می‌کرد. backup جدا در رسانه/مقصد دیگر و restore test لازم بود.

Probably not; the snapshot shared the same failure domain. An independent backup on another medium/destination and a restore test were needed.

۱۴. linked clone و پاک‌سازی

می‌خواهی base image را برای آزادکردن فضا حذف کنی؛ یک linked clone هنوز هست. قبلش چه می‌پرسی؟

You want to delete the base to free space, but a linked clone remains. What do you check first?

پاسخ

آیا clone به base وابسته است؟ chain و registered media را در hypervisor ببین. بدون merge/clone مستقل معتبر، base را حذف نکن.

Is the clone dependent on that base? Inspect the chain and registered media; do not delete the base without a valid merge or independent clone.

۱۵. تغییر بعد از snapshot

snapshot را restore کردی و فایل جدید حذف شد. آیا restore داده را «گم» کرده؟

You restored a snapshot and a new file disappeared. Did restore “lose” data?

پاسخ

فایل بعد از نقطهٔ انتخاب‌شده ساخته شده بود و از current branch حذف شد؛ پیش از restore باید تغییرات لازم را بیرون VM ذخیره یا snapshot تازه بگیری.

The file was created after the selected point and is absent from the restored state. Preserve needed changes outside the VM or take another snapshot before reverting.

۱۶. همه‌چیز داخل snapshot؟

VM یک disk با mode خاص دارد که از snapshotها مستثناست. آیا هر virtual disk حتماً restore می‌شود؟

A VM has a disk in a special mode excluded from snapshots. Is every virtual disk necessarily reverted?

پاسخ

نه؛ behavior به hypervisor و disk mode بستگی دارد. تنظیم هر disk و مستندات نسخه را بخوان؛ نام Snapshot به‌تنهایی تضمین پوشش همهٔ storage نیست.

No; behaviour depends on hypervisor and disk mode. Inspect each disk’s settings and version documentation; the word Snapshot alone does not guarantee every storage device is included.

۱۷. ساخت هر دو نوع

می‌خواهی یک clone کوتاه‌عمر برای تست بسازی و یک clone مستقل برای انتقال. چه نوعی انتخاب می‌کنی؟

You want a short-lived test clone and an independent copy for transfer. Which types do you choose?

پاسخ

linked برای آزمایش کوتاه با base سالم و مدیریت‌شده؛ full برای استقلال/انتقال و با پذیرش فضای بیشتر. قبل از استفادهٔ هم‌زمان MAC/hostname را بررسی کن.

A linked clone for a short test with a safely managed base; a full clone for independence/transfer, accepting higher storage cost. Check MAC/hostname before simultaneous use.

۱۸. تصمیم بازیابی

برای database مهم باید upgrade آزمایش کنی و هم از خرابی host بازیابی داشته باشی. snapshot کافی است؟ چه دو مدرکی نگه می‌داری؟

You need to test a database upgrade and recover from host failure. Is a snapshot enough, and what two proofs do you keep?

معیار پاسخ

snapshot فقط rollback آزمایش است و database consistency/host recovery را تضمین نمی‌کند. backup سازگار با دیتابیس را روی مقصد جدا بگیر و restore test انجام بده؛ نتیجهٔ upgrade را با snapshot/clone disposable verify کن.

A snapshot is only an experiment rollback and does not guarantee database consistency or host recovery. Store a database-consistent backup separately and test a restore; verify the upgrade using a disposable snapshot/clone.

راه برگشت داشته باش، ولی وابستگی را هم نگه دارKeep a way back—and keep its dependencies

snapshot برای برگشت به وضعیت قبلی عالی است، به‌خصوص در VM آزمایشگاهی. restore، تغییرهای بعد از آن نقطه را از وضعیت فعال کنار می‌گذارد؛ deltaها با نوشتن رشد می‌کنند و حذفشان ممکن است merge و زمان بخواهد. در linked clone، base بخشی از داده است، نه یک فایل موقت که وقتی جا کم شد پاکش کنیم.

A snapshot is excellent for returning a lab VM to an earlier state. Restore removes later changes from the active state; deltas grow with writes, and deleting them can require a merge. In a linked clone, the base is part of the data—not a temporary file to delete when space gets tight.

برای تغییر روزمره از snapshot استفاده کن؛ برای بازیابی از خرابی host، backup مستقل بگیر و واقعاً restore کن. در فصل بعد از VMها به‌عنوان یک آزمایشگاه شبکه استفاده می‌کنیم: با دو ماشین مسیرها را می‌سنجیم، بی‌آنکه شبکهٔ اصلی‌ات را به هم بزنیم.

Use snapshots for experiments; use independent backups and real restore tests for host recovery. Next we turn the VMs into a network lab and test paths between them without disrupting your real network.
