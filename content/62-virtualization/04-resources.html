منابع

Resources

CPU، RAM و دیسک host محدودند؛ تنظیم VM یعنی تصمیم بگیریم این ظرفیت محدود را چه‌طور بین چند مهمان تقسیم کنیم.

Host CPU, memory, and disk are finite. Configuring VMs means deciding how to divide that capacity among guests.

۸۰دقیقهminutes
۱۸تمرینexercises

دو VM روشن‌اند؛ چرا خود host مکث می‌کند؟Two VMs are running. Why is the host stuttering?

از فصل قبل دو VM کوچک ساخته‌ای. امروز یکی از آن‌ها کند شده و نشانگر میزبان هم هر چند ثانیه می‌ایستد. در تنظیمات هر دو نوشته «۲ CPU» و «۲ GiB RAM». آیا یعنی host باید چهار CPU و چهار GiB RAM داشته باشد؟ و اگر این اعداد از ظرفیت میزبان بیشتر شوند، hypervisor از کجا جبران می‌کند؟

You built two small VMs in the previous chapter. Today one is slow, and the host pointer pauses every few seconds. Each VM says “2 CPUs” and “2 GiB RAM.” Does the host therefore need four CPUs and four GiB of memory? If those numbers exceed host capacity, where does the hypervisor get the difference?

جواب را از عددهای پنجرهٔ تنظیمات حدس نمی‌زنیم. اول ظرفیت host را می‌خوانیم، بعد هم‌زمان host و guest را زیر بار کوتاه می‌سنجیم. عدد تخصیص‌یافته یک سقف یا قرارداد پیکربندی است؛ لزوماً مصرف واقعی همین لحظه نیست.

We will not guess from the settings window. First inspect host capacity, then measure host and guest together under a short workload. An assigned value is a configuration ceiling or promise; it is not necessarily current consumption.

ظرفیت میزبان را یک‌بار خرج نکنDo not spend the host’s capacity twice

ماشین فیزیکی CPU، RAM و فضای ذخیره‌سازی محدودی دارد. خود host، hypervisor، cache و برنامه‌های روزمره هم از همان منابع استفاده می‌کنند. قبل از روشن‌کردن VMها یک baseline بگیر؛ اگر host همین حالا تحت فشار است، اجرای آزمایش بار را عقب بینداز.

A physical machine has finite CPU, memory, and storage. The host, hypervisor, caches, and everyday applications use those same resources. Record a baseline before starting VMs; if the host is already under pressure, defer the load experiment.

nproc
lscpu
free -h
df -h
uptime
vmstat 1 5

`nproc` تعداد CPUهای منطقی در دسترس process را می‌دهد؛ `lscpu` مدل و توپولوژی را نشان می‌دهد؛ `free` حافظه و swap میزبان را خلاصه می‌کند؛ `vmstat` در چند نمونه، run queue و جابه‌جایی حافظه را نشان می‌دهد. در خط اول `vmstat` بعضی شمارنده‌ها میانگین از زمان boot هستند؛ خط‌های بعدی را برای بازهٔ آزمایش بخوان. این فرمان‌ها capacity و نشانه‌ها را می‌دهند، اما تضمین نمی‌کنند همهٔ workloadها در آینده جا شوند.

`nproc` reports logical CPUs available to the process; `lscpu` shows model and topology; `free` summarises host memory and swap; `vmstat` samples the run queue and memory activity. Some first-line `vmstat` counters are averages since boot, so use subsequent lines for the experiment window. These commands show capacity and symptoms, not a guarantee that every future workload will fit.

در `free -h` فقط ستون `free` را هدف نگذار؛ cache و reclaimable memory هم بخشی از رفتار Linux است. `available` برآوردی از حافظه‌ای است که بدون swap جدی می‌توان در اختیار برنامه گذاشت. در `vmstat` افزایش مداوم `si`/`so` نشانهٔ swap-in/out است، اما یک نمونهٔ غیرصفر به‌تنهایی حادثه نیست.

Do not treat only the `free` column in `free -h` as usable memory; Linux also manages caches and reclaimable pages. `available` estimates memory that can be given to applications without heavy swapping. In `vmstat`, sustained `si`/`so` indicates swap activity, but one nonzero sample is not by itself an incident.

وقتی چند VM هم‌زمان کار می‌خواهند، همان ظرفیت فیزیکی بینشان رقابت می‌شود. فضای خالی در پنجرهٔ تنظیمات، CPU یا RAM تازه‌ای تولید نمی‌کند.

When several VMs demand work at once, they compete for the same physical capacity. Empty-looking settings fields do not create more CPU or memory.

vCPU با هستهٔ فیزیکی یکی نیستA vCPU is not a physical core

guest یک یا چند CPU مجازی می‌بیند. hypervisor زمان اجرای آن‌ها را روی threadهای منطقی CPU میزبان زمان‌بندی می‌کند. یک هسته ممکن است با SMT دو thread منطقی ارائه دهد، اما دو thread یکسانِ دو هستهٔ مستقل نیستند؛ کارایی به نسل CPU، workload و هم‌زمانی بستگی دارد. بنابراین «۴ vCPU» را مساوی چهار هستهٔ فیزیکی نگیر.

A guest sees one or more virtual CPUs. The hypervisor schedules them onto the host’s logical CPU threads. A core may expose two logical threads through SMT, but those threads are not equivalent to two independent physical cores; performance depends on CPU generation, workload, and contention. Do not equate “4 vCPUs” with four physical cores.

اگر host چهار CPU منطقی دارد و به هرکدام از سه VM چهار vCPU بدهی، نسبت پیکربندی ۱۲ به ۴ است. این الزاماً مشکل فوری نیست: همهٔ guestها ممکن است بیشتر وقتشان بیکار باشند. ولی وقتی چند workload هم‌زمان CPU بخواهند، صف زمان‌بندی بالا می‌رود و latency زیاد می‌شود. این همان CPU overcommit است؛ وعدهٔ زمان‌بندی، نه ظرفیت اضافه.

If a host has four logical CPUs and you assign four vCPUs to each of three VMs, the configured ratio is 12:4. That is not automatically an immediate failure: guests may be idle most of the time. But when several workloads demand CPU together, scheduling queues grow and latency rises. This is CPU overcommit: a scheduling promise, not extra capacity.

برای دیدن baseline host از `vmstat 1 5` استفاده کن: `r` تعداد runnable processهایی است که برای CPU منتظرند؛ اگر در بازهٔ بار مرتب از CPUهای منطقی host بیشتر است، صف می‌تواند نشانهٔ contention باشد. `us` و `sy` سهم CPU در user/kernel را می‌دهند. داخل guest هم `top` یا `uptime` را بخوان. فقط یک سمت را دیدن کافی نیست: guest ممکن است CPU آزاد گزارش کند درحالی‌که vCPU برای host زمان انتظار می‌کشد.

Use `vmstat 1 5` for a host baseline: `r` counts runnable processes waiting for CPU; if it stays above the host’s logical CPU count under load, it can indicate contention. `us` and `sy` report user/kernel CPU time. Check `top` or `uptime` inside the guest too. One side alone is incomplete: a guest may report available CPU while its vCPU is waiting for host scheduling.

NUMA را فعلاً فقط بشناس: در سرور چندسوکته، CPU و بخشی از RAM به nodeهای نزدیک‌تر تقسیم می‌شوند. قراردادن vCPU و RAM دور از هم می‌تواند دسترسی را کند کند. برای لپ‌تاپ آزمایشگاهی معمولاً لازم نیست topology را دستی pin کنی؛ روی میزبان چندسوکتهٔ بزرگ، تصمیم NUMA را با اندازه‌گیری و مستندات hypervisor بگیر.

For now, just recognise NUMA: on multi-socket servers, CPUs and portions of memory are grouped into locality nodes. Placing vCPUs and memory far from one another can slow access. A laptop lab rarely needs manual topology pinning; on a large multi-socket host, make NUMA decisions from measurements and hypervisor documentation.

RAM تخصیص‌یافته، RAM مصرف‌شده نیستAssigned RAM is not the same as used RAM

برای هر VM دو عدد مهم ببین: memory مجاز/هدف guest و مصرف واقعی host. guest ممکن است ۲ GiB ببیند، اما همهٔ صفحه‌ها را لمس نکرده باشد. از طرف دیگر process ماشین مجازی، page cache و دستگاه‌های مجازی هم host memory مصرف می‌کنند. از روی عدد «۲ GiB» در wizard دربارهٔ فشار واقعی نتیجه نگیر.

For each VM, distinguish the guest’s configured/target memory from actual host use. A guest may see 2 GiB without touching every page. The VM process, page cache, and virtual devices also consume host memory. Do not infer actual pressure from the “2 GiB” in a wizard.

در guest `free -h` و روی host `free -h` را نزدیک به هم ثبت کن. در libvirt، `virsh dommemstat vm-a` ممکن است آمار balloon مثل `actual`, `available`, `unused` و `rss` بدهد؛ این فیلدها به balloon driver، تنظیم stats و hypervisor وابسته‌اند و ممکن است بعضی‌شان اصلاً نیایند. `rss` مصرف resident process روی host است، نه برابر با حافظهٔ قابل‌استفادهٔ guest.

Record `free -h` in the guest and host close together. With libvirt, `virsh dommemstat vm-a` may report balloon statistics such as `actual`, `available`, `unused`, and `rss`; these fields depend on the balloon driver, stats settings, and hypervisor, so some may be absent. `rss` is the VM process’s host resident memory, not the guest’s available memory.

# On the host
free -h
vmstat 1 5
virsh dommemstat vm-a

# Inside vm-a
free -h

ballooning یعنی hypervisor، با همکاری balloon device و driver داخل guest، بتواند بخشی از RAM مهمان را پس بگیرد یا مقدار در دسترسش را تغییر دهد. این «RAM مجانی» یا تعهد همیشگی برای همهٔ VMها نیست؛ guest باید driver مناسب داشته باشد و سیستم‌عامل/پلتفرم پشتیبانی کند. کم‌کردن RAM در حالی‌که guest واقعاً به آن نیاز دارد می‌تواند swap و کندی بسازد.

Ballooning lets a hypervisor, with a balloon device and driver inside the guest, reclaim some guest memory or adjust what is available. It is not “free RAM” or a universal promise across every VM; the guest needs a suitable driver and the platform must support it. Taking memory away while the guest needs it can cause swapping and latency.

وقتی host RAM کم می‌آورد، kernel ممکن است pageها را به swap ببرد؛ دیسک از RAM کندتر است، پس سیستم مکث می‌کند. فشار شدید می‌تواند OOM killer را هم وارد کند و processها را بکشد. در آزمایش این فصل تا رسیدن به OOM نمی‌رویم. اگر `available` host پایین است، `si/so` مداوم می‌بینی یا UI host گیر می‌کند، بار را متوقف کن و VMهای آزمایشی را خاموش کن.

When host RAM runs short, the kernel may move pages to swap; disk is slower than RAM, so the system stutters. Severe pressure can invoke the OOM killer. We will not drive this experiment to OOM. If host `available` is low, `si/so` persist, or the host UI stalls, stop the workload and shut down the lab VMs.

حجم دیسک با سرعت دیسک فرق داردDisk capacity is not disk performance

در wizard ممکن است برای guest دیسک مجازی ۳۰ GiB تعریف کنی. این عدد ظرفیت منطقی است؛ لزوماً همان لحظه ۳۰ GiB از host اشغال نمی‌شود. قالب dynamically allocated یا thin می‌تواند فضای فیزیکی را هنگام نوشتن رشد دهد، تا سقف مجازی. اما اگر چند disk رشد کنند و host پر شود، همهٔ VMها ممکن است با خطای نوشتن روبه‌رو شوند. thin provisioning ظرفیت را زیاد نمی‌کند—فقط زمان تخصیصش را عقب می‌اندازد.

A VM wizard may let you define a 30 GiB virtual disk. That is its logical capacity; it does not necessarily consume 30 GiB on the host immediately. A dynamically allocated or thin disk can grow as data is written, up to its virtual ceiling. But if several disks grow until the host fills, every VM may encounter write failures. Thin provisioning does not add capacity; it delays allocation.

از آن طرف دیسکی با فضای آزاد زیاد ممکن است IOPS یا throughput کافی نداشته باشد. چند VM که هم‌زمان update، boot یا swap می‌کنند روی یک SSD/HDD صف I/O می‌سازند. در این فصل وارد تنظیم storage نمی‌شویم؛ فعلاً تفاوت سه سؤال را نگه دار: چقدر ظرفیت منطقی تعریف شده؟ روی host چقدر جا مانده؟ و عملیات خواندن/نوشتن با چه تأخیری انجام می‌شوند؟

Conversely, a disk with plenty of free capacity may not deliver enough IOPS or throughput. Several VMs updating, booting, or swapping at once can queue I/O on one SSD/HDD. We will not tune storage here; keep three questions distinct: how much logical capacity is configured, how much host space remains, and how much latency reads/writes experience.

df -h
du -h --max-depth=1 /var/lib/libvirt/images 2>/dev/null
virsh domblkstat vm-a vda

مسیر storage pool به distro و URI اتصال وابسته است؛ `du` را فقط روی مسیری اجرا کن که واقعاً در `virsh dumpxml`/pool info دیده‌ای، نه با فرض اینکه همهٔ VMها زیر یک پوشه‌اند. `domblkstat` شمارنده‌های I/O را می‌دهد اگر hypervisor و block device پشتیبانی کنند؛ یک snapshot از شمارنده بدون فاصلهٔ زمانی، نرخ یا latency را ثابت نمی‌کند.

Storage-pool paths depend on distribution and libvirt URI. Run `du` only on a path confirmed by domain XML/pool info; do not assume every VM lives under one directory. `domblkstat` reports I/O counters where the hypervisor and block device support them; a single counter snapshot without an interval does not establish rate or latency.

آزمایش: تغییر یکی از منابع، نه همه با همExperiment: change one resource, not everything at once

دو VM کوچک و disposable از فصل قبل را انتخاب کن. قبل از تغییر، نام domainها را با `virsh list --all` پیدا کن و هر چیزی را که لازم داری ذخیره کن؛ این فصل دادهٔ مهم را حذف نمی‌کند، اما تنظیمات CPU/RAM ممکن است به خاموش‌بودن VM نیاز داشته باشد. ثبت کن هر guest چند vCPU و چه مقدار RAM دارد، host چند logical CPU دارد و `free -h` چه می‌گوید.

Choose two small, disposable VMs from the previous chapter. Identify domain names with `virsh list --all` and save anything important; this chapter does not delete data, but changing CPU/RAM may require the VM to be off. Record each guest’s vCPUs and RAM, the host’s logical CPU count, and `free -h`.

برای CPU، در `virt-manager` تعداد vCPU یکی از guestها را کم کن، VM را boot کن، سپس مقدار را داخل guest با `nproc` ببین. این مقدار CPU مجازی قابل‌مشاهده را ثابت می‌کند، نه سهم تضمین‌شده از پردازندهٔ host را. بعد دو VM را با workload عادی مقایسه کن؛ اگر host کم‌هسته است، بار را کوتاه نگه دار.

For CPU, reduce one guest’s vCPU count in virt-manager, boot it, then check `nproc` inside the guest. This proves the guest-visible virtual CPU count, not a guaranteed share of host processor time. Compare both VMs under ordinary load; keep the test brief on a small host.

برای نمایش contention، فقط اگر host در baseline سالم است و دست‌کم دو CPU منطقی دارد، از هر guest ابزار آزمایش CPU نصب‌شده را استفاده کن (مثلاً `stress-ng` با `--cpu 1 --timeout 15s`). هم‌زمان روی host `vmstat 1 20` یا `top` را بخوان. اگر ابزار نصب نیست، نصبش اجباری نیست؛ workload واقعی کوتاه مثل compile هم می‌تواند مقایسه شود. هیچ stress را بدون timeout اجرا نکن.

To observe contention, only if the host baseline is healthy and it has at least two logical CPUs, use an installed CPU test tool in each guest (for example, `stress-ng --cpu 1 --timeout 15s`). Observe `vmstat 1 20` or `top` on the host at the same time. Installing a stress tool is optional; a short real workload such as a compile can also provide a comparison. Never run an unbounded stress test.

برای RAM، عدد assigned را در تنظیمات VM ببین و مصرف واقعی را با `free -h` در هر دو طرف و `virsh dommemstat` مقایسه کن. عمداً مجموع RAM دو VM را از RAM نصب‌شدهٔ host بیشتر نکن؛ رفتار host در overcommit حافظه به hypervisor و backing policy وابسته است و کمبود RAM می‌تواند کل محیط را قفل کند. اگر host فضای آزاد کافی ندارد، فقط خروجی‌ها و مدل تخصیص را بررسی کن و فشار RAM نساز.

For memory, compare the VM’s assigned value with `free -h` on both sides and `virsh dommemstat`. Do not deliberately configure the two VMs’ combined RAM above installed host memory: memory-overcommit behaviour depends on hypervisor and backing policy, and shortage can lock the whole environment. If the host lacks safe headroom, inspect the values and allocation model without creating memory pressure.

مرز توقف: اگر host برای بازشدن برنامه‌ها مکث کرد، `available` به‌شدت افت کرد یا swap پیوسته بالا رفت، workload را با Ctrl+C متوقف کن و VMها را عادی shutdown کن. برای دیدن «OOM واقعی» ریسک لازم نیست؛ آن آزمایش در محیط محدود و جداگانه معنا دارد.

Stop condition: If the host stalls, `available` drops sharply, or swap keeps rising, stop the workload with Ctrl+C and shut down the VMs normally. There is no need to risk a real host OOM to understand the concept; that experiment belongs in a separately bounded environment.

در پایان فقط یک متغیر را تغییر بده و همان اندازه‌گیری را تکرار کن. اگر هم‌زمان vCPU، RAM و نوع disk را عوض کنی، نمی‌فهمی کدام تغییر تفاوت را ساخته است.

At the end, change one variable and repeat the same measurements. If you change vCPU, memory, and disk type together, you will not know which change caused the difference.

خرابی عمدی: تنظیمات جمع می‌شوند، host نهDeliberate failure: settings add up, but the host does not

دو VM را خاموش کن و در یادداشت آزمایش، به هرکدام vCPU بیشتری نسبت به سهم محافظه‌کارانهٔ host بده—مثلاً روی host چهار-thread، هرکدام چهار vCPU. هنوز آن‌ها را با بار سنگین روشن نکن. این پیکربندی overcommit CPU را نشان می‌دهد، نه اینکه ماشین از همین حالا کند شده باشد. حالا workload CPU کوتاه ۱۵ثانیه‌ای را فقط روی یک guest اجرا کن، بعد روی هر دو اجرا و هر بار `vmstat` host را ثبت کن.

Shut down both VMs and, in your experiment notes, assign more vCPUs than a conservative host share—for example, four vCPUs each on a four-thread host. Do not yet start them under heavy load. This configuration demonstrates CPU overcommit, not that the machine is already slow. Run a 15-second CPU workload in one guest, then both, recording host `vmstat` each time.

ممکن است تفاوت روشن باشد یا نباشد؛ زمان‌بندی، تعداد هسته و سایر برنامه‌های host اثر دارند. شواهد را از `r`, `us`, `sy` و زمان پاسخ workload کنار هم بخوان. فقط دیدن ۸ vCPU در guest ثابت نمی‌کند ۸ هستهٔ فیزیکی داری. اگر host کند شد، workload را قطع کن؛ اصلاح آزمایش یعنی VMها را خاموش کنی و vCPU را کم کنی، نه اینکه به‌دنبال دکمهٔ «تضمین CPU» بگردی.

The difference may be obvious or subtle; scheduling, core count, and other host processes matter. Read `r`, `us`, `sy`, and workload response together. Seeing eight vCPUs inside guests does not prove you own eight physical cores. If the host slows, stop the workload; repair the experiment by shutting down the VMs and reducing vCPUs, not by searching for a “guaranteed CPU” button.

RAM را به‌شکل مشابه overcommit نکن. تخصیص بالاتر از ظرفیت ممکن است در بعضی پلتفرم‌ها تا زمانی که صفحه‌ها واقعاً مصرف نشده‌اند بی‌علامت بماند؛ بعد با page fault، swap یا OOM ظاهر شود. این تفاوت بین «عدد تعریف‌شده» و «صفحهٔ resident» است، نه مجوزی برای آزمودن شانس روی میزبان روزمره.

Do not reproduce memory overcommit the same way. On some platforms, assignments above capacity may appear harmless until pages are touched, then show up as faults, swapping, or OOM. That gap between a configured number and resident pages is not permission to gamble on an everyday host.

«reservation» هم رفتار یکسان و همیشگی ندارد. بعضی hypervisorها reservation/limit جدا دارند، بعضی providerها آن را به policy دیگری نگاشت می‌کنند و بعضی محیط‌ها فقط عدد تخصیص و scheduler دارند. اسم گزینه را نبین و فرض نکن ظرفیت فیزیکی کنار گذاشته شد؛ مستندات همان hypervisor و اثر آن روی میزبان را بررسی کن.

“Reservation” is not a universal behaviour. Some hypervisors provide separate reservations/limits, some providers map them to other policies, and some environments expose only allocation and scheduling. Do not assume a physical resource was set aside just because a field is called a reservation; verify the specific hypervisor documentation and host effect.

مینی‌آزمایشگاه: از حدس به اندازه‌گیریMini-lab: replace guesses with measurements

یک برگه با چهار ستون بساز: زمان، تغییر، host، guest. پیش از کار، دو VM را با تنظیمات فعلی boot کن؛ `lscpu`, `free -h`, `vmstat 1 5` را روی میزبان و `nproc`, `free -h`, `uptime` را در هر guest ثبت کن. اگر host زیر بار است، آزمایش را همین‌جا متوقف کن.

Create a four-column log: time, change, host, guest. Boot the two VMs with their current settings; record `lscpu`, `free -h`, and `vmstat 1 5` on the host, then `nproc`, `free -h`, and `uptime` in each guest. If the host is already under pressure, stop here.

حالا فقط vCPU ماشین دوم را کم کن؛ VM را خاموش/روشن کن و `nproc` و زمان workload کوتاه یکسان را دوباره ثبت کن. نتیجه را با baseline مقایسه کن. آزمایش بعدی فقط memory visibility است: assigned RAM، guest available، host available و balloon statistics در صورت پشتیبانی. در این مرحله عمداً RAM را پر نکن.

Now change only the second VM’s vCPU count; power it off/on if required and repeat `nproc` and the same short workload timing. Compare with baseline. The next test is memory visibility only: assigned RAM, guest available, host available, and balloon statistics if supported. Do not intentionally fill memory.

برای پایان، در تنظیمات domain ظرفیت دیسک مجازی و در میزبان مصرف فایل را جدا ثبت کن؛ اگر مسیر pool را نمی‌دانی، از `virsh pool-list --all`, `virsh pool-info NAME` و `virsh dumpxml VM` شروع کن. چیزی را resize یا compact نکن—آن مبحث فصل ذخیره‌سازی است. گزارش کوتاهت باید بگوید کدام عدد پیکربندی است، کدام مشاهدهٔ لحظه‌ای، و کدام ادعا هنوز نیاز به اندازه‌گیری بیشتر دارد.

Finally, record virtual disk capacity separately from host file usage. If the pool path is unknown, start with `virsh pool-list --all`, `virsh pool-info NAME`, and `virsh dumpxml VM`. Do not resize or compact anything—that belongs to the storage chapter. Your short report should label which values are configuration, which are point-in-time observations, and which claims still need more measurement.

یادداشت تخمین: اگر ابزار `stress-ng` از قبل نصب است، برای CPU می‌توانی از `stress-ng --cpu 1 --timeout 15s` استفاده کنی. فقط CPU guest را می‌فشارد و نتیجهٔ حافظه یا I/O را نشان نمی‌دهد. برای اندازه‌گیری RAM آزمایش حجمی اضافه نکن؛ host و guest را با ابزارهای read-only بالا مقایسه کن.

Measurement note: If `stress-ng` is already installed, `stress-ng --cpu 1 --timeout 15s` is a bounded CPU example. It stresses guest CPU only; it says nothing about memory or I/O. Do not add a memory-filling experiment—compare host and guest using the read-only tools above.

تمرین‌هاExercises

۱. عدد ۴

host چهار CPU منطقی دارد و guest هم چهار vCPU نشان می‌دهد. چند هستهٔ فیزیکی تضمین شده؟

The host has four logical CPUs and a guest sees four vCPUs. How many physical cores are guaranteed?

پاسخ

هیچ تعداد مشخصی تضمین نمی‌شود؛ vCPU زمان‌بندی‌شونده روی host است. توپولوژی `lscpu` و فشار هم‌زمان را هم بررسی کن.

No specific number is guaranteed; vCPUs are scheduled on the host. Check `lscpu` topology and simultaneous demand too.

۲. صف CPU

در چند نمونهٔ `vmstat`، مقدار `r` بالاتر از تعداد CPU منطقی می‌ماند. چه فرضیه‌ای می‌سازی؟

Across several `vmstat` samples, `r` stays above the logical CPU count. What hypothesis do you form?

پاسخ

صف CPU و contention محتمل است. آن را با زمان پاسخ workload و مصرف processها بسنج؛ یک نمونه به‌تنهایی علت کندی را ثابت نمی‌کند.

CPU queueing and contention are plausible. Compare workload latency and process use; one sample does not prove the cause of slowness.

۳. host یا guest؟

داخل guest `free` حافظهٔ زیادی نشان می‌دهد، ولی host swap می‌کند. کدام شاهد را برای فشار میزبان می‌خوانی؟

Guest `free` shows plenty of memory, but the host is swapping. Which evidence do you use for host pressure?

پاسخ

`free -h` و `vmstat` روی host، به‌خصوص available و روند `si/so`. حافظهٔ آزاد guest الزاماً صفحهٔ آزاد host نیست.

Use host `free -h` and `vmstat`, especially available memory and sustained `si/so`. Guest free memory is not necessarily free host memory.

۴. balloon حاضر نیست

`virsh dommemstat` فقط چند فیلد یا خروجی خالی می‌دهد. نتیجهٔ درست چیست؟

`virsh dommemstat` returns only a few fields or none. What is the correct conclusion?

پاسخ

آمار/balloon ممکن است فعال یا پشتیبانی نشده باشد؛ نبودن فیلد ثابت نمی‌کند RAM مصرف نمی‌شود. driver guest، تنظیم stats و پشتیبانی hypervisor را بررسی کن.

Balloon statistics may be disabled or unsupported; missing fields do not prove memory is unused. Check guest drivers, stats configuration, and hypervisor support.

۵. ظرفیت در برابر resident

VM با ۳ GiB RAM تعریف شده، ولی host process RSS برابر ۱٫۴ GiB است. آیا تناقض است؟

A VM is configured with 3 GiB RAM, but its host process RSS is 1.4 GiB. Is that contradictory?

پاسخ

نه؛ تنظیم و حافظهٔ resident مفهوم‌های متفاوت‌اند و guest ممکن است همهٔ pageها را لمس نکرده باشد. host و guest metrics را هم‌زمان و با درنظرگرفتن balloon بخوان.

No. Configuration and resident memory are different; the guest may not have touched every page. Read host and guest metrics together and account for ballooning.

۶. پیکربندی CPU بیش‌ازحد

روی میزبان ۴-thread، دو VM هرکدام ۴ vCPU دارند. آیا همین الان CPU کم آورده‌ای؟

On a four-thread host, two VMs each have four vCPUs. Is the host already out of CPU?

پاسخ

نه لزوماً؛ overcommit پیکربندی است. فشار وقتی هم‌زمانی workloadها بالا برود ظاهر می‌شود؛ baseline و بار محدود را مقایسه کن.

Not necessarily; overcommit is a configuration ratio. Pressure appears when workloads demand CPU together; compare a baseline with a bounded load.

۷. کدام دستور کجا؟

می‌خواهی تعداد CPU مجازی guest و صف CPU host را ببینی. برای هرکدام چه می‌زنی؟

You want the guest’s visible vCPU count and the host CPU queue. What do you run for each?

پاسخ

داخل guest `nproc` یا `lscpu`؛ روی host `vmstat 1 5` و ستون `r`. این‌ها هرکدام سمت متفاوتی از زمان‌بندی را نشان می‌دهند.

Run `nproc` or `lscpu` in the guest; run `vmstat 1 5` on the host and inspect `r`. They show different sides of scheduling.

۸. swap کوتاه

یک خط `vmstat` مقدار `so=4` دارد و خط‌های بعدی صفرند. آیا host وارد swap بحران‌زا شده؟

One `vmstat` line has `so=4`, then later lines are zero. Is the host in a severe swap crisis?

پاسخ

از این شاهد تنها نمی‌شود چنین گفت؛ روند، available memory، latency و workload را بسنج. نمونهٔ اول هم ممکن است میانگین از boot باشد.

That evidence alone is insufficient. Check the trend, available memory, latency, and workload. The first sample may also be an average since boot.

۹. guest کند، host آرام

guest کند است؛ host run queue پایین و swap ندارد. چه بررسی بعدی‌ای از همین فصل انجام می‌دهی؟

The guest is slow, but the host run queue is low and there is no swapping. What next check from this chapter?

پاسخ

guest `top`, `free -h`, CPU count و workload را بررسی کن. کندی ممکن است داخل guest یا از I/O باشد؛ این شواهد host را از متهم‌بودن CPU/RAM دور می‌کنند، نه کل سیستم را.

Inspect guest `top`, `free -h`, CPU count, and workload. Slowness may be inside the guest or due to I/O; these host observations weaken the CPU/memory hypothesis but do not clear the whole system.

۱۰. NUMA، در یک جمله

چرا در server چندسوکته ممکن است محل CPU و RAM مهم باشد؟

Why might CPU and memory placement matter on a multi-socket server?

پاسخ

دسترسی به RAM محلی یک NUMA node معمولاً سریع‌تر از حافظهٔ دور است. برای لپ‌تاپ عادی این موضوع را دستی تنظیم نکن؛ ابتدا topology و measurement لازم است.

Access to memory local to a NUMA node is generally faster than remote memory. Do not tune this manually on an ordinary laptop; topology and measurement come first.

۱۱. virtual disk سی‌گیگی

guest یک virtual disk سی‌گیگی دارد. آیا host همین حالا ۳۰ GiB فایل مصرف کرده؟

A guest has a 30 GiB virtual disk. Has the host necessarily consumed a 30 GiB file already?

پاسخ

نه؛ thin/dynamic disk ممکن است به‌تدریج رشد کند. نوع allocation و اندازهٔ واقعی فایل را در مسیر تأییدشدهٔ pool بررسی کن.

No. A thin/dynamic disk may grow gradually. Check allocation type and actual file size at the verified pool path.

۱۲. disk پرسرعت؟

host فضای دیسک زیادی دارد ولی چند guest موقع boot کندند. چه چیزی دربارهٔ capacity و I/O جدا می‌کنی؟

The host has plenty of disk space, but several guests boot slowly. What do you separate about capacity and I/O?

پاسخ

فضای آزاد، ظرفیت است؛ صف/latency و throughput کارایی‌اند. اندازهٔ مصرف‌شده به‌تنهایی سرعت را نمی‌گوید؛ `domblkstat` را در دو زمان و با workload ثبت کن.

Free space is capacity; queueing/latency and throughput are performance. Used size alone says nothing about speed; sample `domblkstat` at two times under a workload.

۱۳. هم‌زمانی واقعی

چهار VM هرکدام ۲ vCPU دارند، اما معمولاً سه‌تا بیکارند. چرا ممکن است overcommit قابل‌قبول باشد و چه چیزی ریسک را تغییر می‌دهد؟

Four VMs each have 2 vCPUs, but three are usually idle. Why might overcommit be acceptable, and what changes the risk?

پاسخ

تقاضا معمولاً هم‌زمان به سقف نمی‌رسد؛ workloadهای هم‌زمان، latency هدف و حاشیهٔ host ریسک را تعیین می‌کنند. میانگین مصرف جای بررسی peak را نمی‌گیرد.

Demand may not peak simultaneously. Concurrent workloads, latency targets, and host headroom determine risk; average use does not replace peak analysis.

۱۴. reservation تضمینی؟

پنل hypervisor گزینه‌ای به نام `reservation` دارد. آیا از اسمش می‌فهمی RAM فیزیکی همیشه کنار گذاشته می‌شود؟

A hypervisor panel has a `reservation` option. Does its name prove physical RAM is always set aside?

پاسخ

نه؛ معنای پیاده‌سازی و اثرش platform-specific است. مستند همان hypervisor، guest state و میزبان را بررسی کن.

No; implementation and effect are platform-specific. Check that hypervisor’s documentation, guest state, and host behaviour.

۱۵. balloon همه‌کاره نیست

می‌خواهی با ballooning کمبود RAM را حل کنی، اما داخل guest swap در حال رشد است. آیا RAM را همین لحظه reclaim می‌کنی؟

You want ballooning to solve low memory, but guest swap is growing. Should you reclaim its RAM now?

پاسخ

نه بدون تشخیص؛ کم‌کردن memory زیر فشار می‌تواند اوضاع را بدتر کند. توقف workload، بررسی host/guest و کاهش تعداد VMها امن‌تر است.

Not without diagnosis; reducing memory under pressure may worsen it. Stop the workload, inspect host and guest, and reduce the number of active VMs.

۱۶. ابزار stress وجود ندارد

`stress-ng` نصب نیست. آیا آزمایش فصل متوقف می‌شود؟

`stress-ng` is not installed. Is the chapter’s experiment blocked?

پاسخ

نه؛ ابزار اختیاری است. workload واقعی کوتاه مثل compile یا update را با timeout عملی و baseline یکسان مقایسه کن؛ هیچ process نامحدودی اجرا نکن.

No; it is optional. Compare a short real workload such as a compile or update against the same baseline; do not run an unbounded process.

۱۷. میزبان شروع به مکث کرد

حین آزمایش pointer میزبان می‌ایستد و `si/so` بالا می‌رود. اولین کار چیست؟

During a test, the host pointer stalls and `si/so` rise. What is the first action?

پاسخ

workload را متوقف کن، VMهای آزمایشی را orderly shutdown کن و فشار host را دوباره بسنج. برای ادامهٔ آزمایش ریسک را بیشتر نکن.

Stop the workload, shut down the lab VMs cleanly, and reassess host pressure. Do not increase risk to continue the experiment.

۱۸. تیکت کندی ماشین

دو VM کندند. host چهار CPU منطقی، `r` پایدار بالای ۹، available memory مناسب و بدون swap دارد؛ مهم‌ترین فرضیه چیست و قدم بعدی کدام است؟

Two VMs are slow. The host has four logical CPUs, `r` stays above 9, available memory is healthy, and there is no swap. What is the leading hypothesis and next step?

معیار پاسخ

CPU queue/contention محتمل‌تر از RAM است؛ workloadها و vCPUها را ثبت کن، بار را یکی‌یکی متوقف کن و `vmstat` و latency را دوباره مقایسه کن. نتیجه هنوز disk I/O یا مشکل داخل guest را حذف نمی‌کند.

CPU queueing/contention is more likely than memory pressure. Record workloads and vCPU counts, stop load one guest at a time, and compare `vmstat` and latency again. This still does not rule out disk I/O or an in-guest issue.

سهم بده، بعد مصرف را اندازه بگیرAllocate a share, then measure actual use

برای هر VM یک عدد «تعریف‌شده» داری و یک رفتار «واقعی زیر بار». CPU مجازی روی threadهای host زمان می‌گیرد؛ RAM ممکن است از سقف guest کمتر resident باشد یا با balloon تغییر کند؛ disk منطقی می‌تواند thin باشد و I/O همچنان گلوگاه شود. overcommit استفادهٔ بهتر از ظرفیت است فقط وقتی peakها، حاشیهٔ میزبان و پیامد contention را می‌شناسی.

For each VM, there is a configured value and actual behaviour under load. Virtual CPUs need host scheduling time; resident memory may be below the guest ceiling or adjusted by ballooning; a logical disk can be thin while I/O is still the bottleneck. Overcommit improves utilisation only when you understand peaks, host headroom, and contention consequences.

اگر یک VM کند شد، قبل از زیادکردن همهٔ sliderها بپرس: host CPU صف دارد؟ host در swap است؟ guest واقعاً memory کم آورده؟ disk فقط بزرگ است یا I/O هم کند شده؟ یک تنظیم را تغییر بده و همان شواهد را دوباره بگیر. فصل بعد سراغ storage می‌رویم تا خود disk image و pool را بررسی کنیم؛ فعلاً ظرفیت را با سرعت اشتباه نگیر.

When a VM slows down, do not move every slider up. Ask: is the host CPU queueing? Is the host swapping? Is the guest actually short on memory? Is the disk merely large, or is I/O slow too? Change one setting and gather the same evidence again. Next we examine disk images and pools in depth; for now, keep capacity separate from speed.
