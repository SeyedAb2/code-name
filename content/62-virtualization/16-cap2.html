پروژهٔ ۲ — آزمایشگاه سه‌ماشینه

Project 2 — a three-machine lab

این بار یک ماشین کافی نیست. سه توزیع رو روی یک شبکهٔ خصوصی کنار هم می‌ذاریم و باید با مدرک ثابت کنی همدیگه رو می‌بینن و بعد از یک خرابی هم می‌تونی جمعش کنی.

Three distributions, one private network, full connectivity. This time you are not merely booting a VM; you must prove that all three machines can actually see one another.

مأموریت: آزمایشگاه تیم رو تحویل بگیرMission: hand over the team's lab

تیم قراره تمرین‌های Linux و شبکه رو روی سه توزیع متفاوت انجام دهد. هر بار که یکی از VMها خاموش و روشن می‌شه، آدرسش عوض می‌شه؛ و از بیرون هم معلوم نیست مشکل از خود guest هست یا از نوع شبکه. تو باید آزمایشگاهی بسازی که اسم و آدرس هر ماشین روشن باشه، میزبان بتونه SSH بزند، سه node به هم برسند و با یک خطای عمدی هم از هم نپاشد.

The team will practice Linux and networking on three different distributions. Every time a VM reboots, its address seems to change, and from the outside it is unclear whether a failure is in the guest or its network mode. Build a lab with clear names and addresses, host-to-guest SSH, node-to-node reachability, and a deliberate fault that does not require rebuilding anything.

مرز مأموریت: شبکه فقط روی میزبان خودت و VMهای همین آزمایشگاه هست. سراغ Bridged روی شبکهٔ محل کار/خانه نرو؛ این پروژه به حضور VMها روی LAN واقعی نیاز نداره.

Mission boundary: the network stays on your host and these lab VMs. Do not switch to Bridged on a home or work LAN; this project does not need the VMs on a real LAN.

نقشهٔ مسیر؛ دو کارت شبکه برای دو کار متفاوتTopology: two adapters, two different jobs

یک کارت NAT به هر VM اینترنت خروجی می‌ده تا بسته نصب کنه. کارت دوم Host-only میزبان و سه VM رو روی یک شبکهٔ خصوصی کنار هم می‌ذاره. اگه Adapter دوم رو اشتباهی NAT بذاری، اینترنت ممکنه کار کنه ولی nodeها در اون شبکهٔ مشترک نیستن؛ این دقیقاً همون خطایی هست که بعداً تشخیص می‌دی.

A NAT adapter gives each VM outbound internet for package installation. A second, Host-only adapter places the host and all three VMs on one private network. If you accidentally set the second adapter to NAT, internet may still work, but the nodes are not on that shared network—that is the fault you will diagnose later.

ارتباط Host-only برای میزبان و nodeهاست؛ NAT فقط راه خروج هر guest رو به شبکهٔ بیرون فراهم می‌کنه.

Host-only connects the host and nodes; NAT provides each guest with an outbound path to external networks.

بازهٔ 192.168.77.0/24 فقط مثال هست؛ قبل از انتخابش مطمئن شو با VPN یا LAN میزبان تداخل نداره. اگه subnet دیگری داری، همهٔ عددهای این صفحه رو هماهنگ عوض کن. VirtualBox در Host-only می‌تونه DHCP بده و برای MAC هر VM آدرس ثابت تعریف کنه؛ پس لازم نیست IP رو در سه سیستم‌عامل با سه روش متفاوت دست‌کاری کنیم.

The range 192.168.77.0/24 is only an example; first make sure it does not overlap with the host's LAN or VPN. If you choose another subnet, change every address consistently. VirtualBox Host-only networking can provide DHCP and fixed leases per VM MAC, so you do not need three different guest-specific static-IP configurations.

قبل از ساخت: سقف منابع و شرط تحویلBefore building: resource budget and handoff conditions

ترکیب پیشنهادی Ubuntu Server، Debian و Fedora Server هست؛ سه خانواده/توزیع رو تجربه می‌کنی، ولی footprint از سه دسکتاپ کمتر می‌مونه. برای شروع به هر VM یک vCPU و حدود ۱ تا ۲ GiB RAM بده؛ RAM لازم به نسخه و سرویس‌های نصب‌شده بستگی داره. اگه میزبانت کم‌رم هست، فعلاً فقط دو VM رو هم‌زمان روشن کن و این محدودیت رو در گزارش بنویس. دیسک مجازی رو با فضای واقعی آزاد میزبان اشتباه نگیر.

Use Ubuntu Server, Debian, and Fedora Server: three distributions without the footprint of three desktop systems. Start with one vCPU and roughly 1–2 GiB RAM per VM; actual needs depend on release and installed services. If the host is memory-constrained, keep only two VMs running at once and document that limitation. Do not confuse virtual disk capacity with free physical host storage.

قبل از تغییر تنظیمات شبکه، از VMها backup یا snapshot پایهٔ سیستم تمیز داشته باش. Snapshot جای backup دادهٔ مهم نیست؛ این‌ها فقط ماشین آزمایشگاهی‌اند و می‌تونی دوباره بسازی، ولی حذف یا دست‌کاری دیسک میزبان جزو تمرین نیست.

Before network changes, keep a clean baseline snapshot or backup of each VM. A snapshot is not a backup for important data; these are disposable lab machines, but deleting or modifying host disks is outside the exercise.

مرحله ۱ — سه ماشین، نه سه کپی مبهمCheckpoint 1 — three machines, not three vague copies

سه VM جدا بساز و برای هرکدام ISO رسمی و متناسب با معماری میزبان بگیر. نام VM، hostname داخل guest و نقش هرکدام رو از همین اول یکسان نگه دار: lab-a، lab-b و lab-c. هنگام نصب SSH سرور رو انتخاب کن؛ اگه نصاب اون گزینه رو نداره، بعد از نصب اون رو با مدیر بسته توزیع اضافه می‌کنی. از تنظیمات پیش‌فرض partition روی دیسک مجازی تازه استفاده کن و قبل از تأیید، نام دیسک مقصد رو بخون.

Create three separate VMs using official ISOs that match the host architecture. Keep the VM name, guest hostname, and role aligned from the start: lab-a, lab-b, and lab-c. Select an SSH server during installation if offered; otherwise install it afterward with the distribution package manager. Use the installer's default partitioning only on a new virtual disk, and read the target disk name before confirming.

بعد از اولین boot در هر guest، hostname و cat /etc/os-release رو اجرا کن. انتظار داری نام و توزیع متفاوت درست همون چیزی باشه که برای اون VM ثبت کرده‌ای. این خروجی نصب سیستم‌عامل رو ثابت می‌کنه، نه اینکه SSH یا شبکهٔ خصوصی آماده هست.

After the first boot of each guest, run hostname and cat /etc/os-release. The name and distribution should match your inventory. This proves the OS install, not that SSH or the private network is ready.

راهنمای پله‌ایProgressive hint

اگه نصب سه سیستم هم‌زمان RAM میزبان رو می‌فشارد، یکی رو کامل کن و خاموش کن، بعد سراغ بعدی برو. snapshot تمیز رو بعد از نصب و به‌روزرسانی بگیر، نه وسط نصاب.

If three simultaneous installs pressure host RAM, finish one VM, shut it down, then move to the next. Take a clean snapshot after install and updates, not midway through an installer.

شاهد: جدول hostname، توزیع و شناسهٔ VM؛ یک خروجی /etc/os-release از هر node.

Evidence: an inventory of hostnames, distributions, and VM identities, plus one /etc/os-release output from each node.

مرحله ۲ — شبکهٔ خصوصی رو یک بار درست تعریف کنCheckpoint 2 — define the private network once

در VirtualBox Network Manager یک Host-only Network بساز یا شبکهٔ موجود رو بررسی کن. مثلاً interface میزبان 192.168.77.1/24، DHCP سرور برابر 192.168.77.2 و pool پویا .100–.150 باشه تا آدرس‌های ثابت nodeها بیرون pool بمانند. اگه این subnet در host، VPN یا شبکهٔ دیگری استفاده شده، اون رو عوض کن. Adapter 1 هر VM رو NAT بذار و Adapter 2 رو به همون Host-only Network مشترک وصل کن.

In VirtualBox Network Manager, create or inspect a Host-only Network. For example, set the host interface to 192.168.77.1/24, the DHCP server to 192.168.77.2, and its dynamic pool to .100–.150, leaving fixed node addresses outside the pool. Change this subnet if it overlaps a host, VPN, or other network. Set each VM's Adapter 1 to NAT and Adapter 2 to the same Host-only Network.

در تنظیم هر VM، وضعیت دو adapter رو قبل از boot دوباره بخون. NAT و Host-only دو نقش‌اند؛ اگه هر دو رو روی NAT بذاری، هر VM معمولاً پشت NAT جدا می‌ره و nodeها از مسیر مشترک قابل‌دسترسی نیستن. از طرف دیگر Bridged رو انتخاب نکن، چون VM رو وارد شبکهٔ فیزیکی می‌کنه.

Before booting, reread both adapter settings for every VM. NAT and Host-only serve different roles; two independent NAT adapters generally do not put the VMs on a shared reachable segment. Do not choose Bridged either, because that places a guest on the physical network.

گزینه‌ها و نام interface در نسخه‌های مختلف VirtualBox و سیستم‌عامل میزبان کمی فرق می‌کنن. از Network Manager خود VirtualBox برای ساخت شبکه استفاده کن و قبل از ثبت نام دقیق interface، اون رو در VBoxManage list hostonlyifs ببین.

Options and interface names vary slightly across VirtualBox and host OS versions. Use VirtualBox Network Manager to create the network, then inspect VBoxManage list hostonlyifs before recording the exact interface name.

راهنمای پله‌ایProgressive hint

Host-only یعنی میزبان و guestها؛ NAT یعنی دسترسی خروجی ساده. برای این آزمایشگاه هر دو رو لازم داریم، نه اینکه یکی رو جایگزین دیگری کنیم.

Host-only connects host and guests; NAT gives simple outbound access. This lab needs both roles, not one mode pretending to be the other.

شاهد: نام دقیق Host-only Network، subnet انتخابی و تصویر/خروجی تنظیم Adapter 1 و 2 هر سه VM.

Evidence: the exact Host-only Network name, chosen subnet, and Adapter 1/2 configuration for all three VMs.

مرحله ۳ — آدرس‌های ثابت با lease، اسم‌ها با hostsCheckpoint 3 — stable leases, readable names

برای اینکه بعد از reboot آدرس nodeها عوض نشه، MAC کارت دوم هر VM رو از VBoxManage showvminfo "lab-a" یا جزئیات Network بخون. در DHCP scope همون Host-only Network، برای MAC هر VM یک fixed address بذار: lab-a → 192.168.77.21، lab-b → .22، lab-c → .23. نمونهٔ CLI برای scope موجود:

To keep node addresses stable across reboots, read each VM's second-adapter MAC from VBoxManage showvminfo "lab-a" or its Network details. In the DHCP scope for that Host-only Network, assign a fixed address to each VM MAC: lab-a → 192.168.77.21, lab-b → .22, lab-c → .23. CLI example for an existing scope:

VBoxManage dhcpserver modify --interface="HOST-ONLY-INTERFACE" --mac-address="080027A1B2C3" --fixed-address="192.168.77.21"

نام interface و MAC بالا نمونه‌اند؛ از خروجی ماشین خودت کپی کن و برای هر سه MAC یک قانون جدا بساز. اگه دستور می‌گه DHCP سرور یا interface پیدا نشد، اول Host-only DHCP رو در Network Manager فعال کن و نام واقعی interface رو دوباره بخون. این تنظیم DHCP ثابت می‌کنه سرور برای اون MAC چه آدرسی پیشنهاد می‌کنه؛ باید داخل guest هم lease رو تمدید/بررسی کنی.

The interface name and MAC above are placeholders; copy the real values and create a separate rule for all three MACs. If the command says the DHCP server or interface is missing, first enable Host-only DHCP in Network Manager and reread the exact interface name. This configuration proves what address DHCP offers that MAC; you must still renew and verify the lease inside the guest.

در هر guest نام رو تنظیم و DHCP رو renew کن؛ ابزار شبکه با توزیع فرق داره، بعد از تنظیم Network خود توزیع استفاده کن و با ip -4 -brief address آدرس کارت Host-only رو پیدا کن. سپس روی میزبان و هر سه guest، برای اسم‌ها mapping محلی بنویس. روی Linux guest:

Set the hostname in each guest and renew DHCP; network configuration tools differ by distribution, so use that OS's network manager and verify the Host-only address with ip -4 -brief address. Then add local name mappings on the host and all three guests. On Linux guests:

sudo sh -c 'cat >> /etc/hosts' <<'EOF'
192.168.77.21 lab-a
192.168.77.22 lab-b
192.168.77.23 lab-c
EOF

در Windows host، فایل C:\Windows\System32\drivers\etc\hosts رو با دسترسی Administrator و همون سه خط ویرایش کن. این mapping در DNS عمومی ثبت نمی‌شه؛ فقط روی همون ماشین اثر داره. با getent hosts lab-b و ping -c 2 lab-b بررسی کن. اگه IP درست هست ولی ping جواب نمی‌ده، هنوز بین فایروال، NIC و سرویس باید فرق بذاری.

On a Windows host, edit C:\Windows\System32\drivers\etc\hosts as Administrator and add the same three lines. This mapping is not public DNS; it affects only that machine. Check with getent hosts lab-b and ping -c 2 lab-b. If the IP is correct but ping fails, distinguish firewall, NIC, and service causes before changing anything.

راهنمای پله‌ایProgressive hint

سه لایه رو به ترتیب ثابت کن: MAC و fixed lease در VirtualBox، IP روی NIC مهمان، بعد نام در hosts. اگه از نام شروع کنی ممکنه فقط یک mapping اشتباه رو پنهان کنی.

Prove the layers in order: MAC and fixed lease in VirtualBox, IP on the guest NIC, then name resolution in hosts. Starting with names can merely hide a wrong mapping.

شاهد: MAC→IP در inventory، ip -4 -brief address از هر node، و getent hosts یا ping با نام.

Evidence: MAC-to-IP inventory, ip -4 -brief address from each node, and name-based getent hosts or ping.

مرحله ۴ — SSH و یک آزمون مشترک روی هر سه nodeCheckpoint 4 — SSH and one shared check on all nodes

روی هر توزیع مطمئن شو سرور و ابزارهای پایه موجودند. در Ubuntu/Debian از openssh-server و iputils-ping استفاده کن؛ در Fedora از بسته‌های متناظر. سرویس در Debian/Ubuntu معمولاً ssh و در Fedora معمولاً sshd نام داره. بعد با systemctl is-active ssh یا systemctl is-active sshd شاهد بگیر؛ اسم سرویس رو حدس نزن.

Ensure each distribution has the server and basic tools. On Ubuntu/Debian use openssh-server and iputils-ping; on Fedora install the equivalent packages. The service is commonly called ssh on Debian/Ubuntu and sshd on Fedora. Verify with systemctl is-active ssh or systemctl is-active sshd; do not guess the unit name.

از host با نام وصل شو: ssh USER@lab-a. سبعد از lab-a به lab-b و lab-c SSH بزن یا دست‌کم هر سه رو با ping بررسی کن. برای دسترسی node-to-node با کلید، کلید آزمایشگاهی جدا بساز و خصوصی key رو در host نگه دار؛ password authentication رو بی‌دلیل روی شبکه باز نکن. اگه SSH رد شد، listener با ss -ltn، route با ip route و فایروال رو جدا ببین.

Connect from the host by name: ssh USER@lab-a. Then SSH from lab-a to lab-b and lab-c, or at minimum test all three with ping. If you enable key-based node-to-node access, create a dedicated lab key and keep its private half on the host; do not unnecessarily open password authentication. If SSH is refused, inspect the listener with ss -ltn, route with ip route, and firewall separately.

یک اسکریپت سبک و مشترک بساز که فقط hostname، IPv4ها، route و دسترسی به دو peer دیگر رو گزارش کنه؛ قرار نیست benchmark بگیره یا چیزی رو تغییر بده. این نسخه رو بعد از نصب iproute2 و iputils-ping روی سه توزیع می‌تونی با sh اجرا کنی:

Create one small shared script that reports only hostname, IPv4 addresses, routes, and reachability to the other two peers; it should neither benchmark nor mutate anything. After installing iproute2 and iputils-ping on all three distributions, run this with sh:

#!/bin/sh
set -eu
echo "node=$(hostname)"
ip -4 -brief address
ip route
for peer in lab-a lab-b lab-c; do
  [ "$peer" = "$(hostname)" ] && continue
  if ping -c 2 -W 2 "$peer"; then
    echo "reachable: $peer"
  else
    echo "not reachable: $peer"
    exit 1
  fi
done

خروجی موفق فقط می‌گه هر peer در لحظهٔ آزمون به ICMP جواب می‌ده؛ SSH یا دسترسی به سرویس‌های دیگر رو ثابت نمی‌کنه. اسکریپت رو یک بار روی هر node اجرا کن و نتیجه رو کنار نام سیستم‌عامل ثبت کن.

A successful run proves only that each peer answered ICMP at test time; it does not prove SSH or other services work. Run it on every node and record the result beside the OS name.

راهنمای پله‌ایProgressive hint

اگه یکی از توزیع‌ها ping نداره، ابزار رو نصب کن؛ فایروال رو خاموش نکن. اگه نام resolve نمی‌شه، hosts فایل و اگه IP resolve می‌شه ولی پاسخ نیست، subnet/NIC و سیاست رو بررسی کن.

If a distribution lacks ping, install the tool; do not disable the firewall. If a name does not resolve, inspect hosts. If it resolves but gets no reply, inspect subnet/NIC and policy.

شاهد: SSH از host به هر سه VM، خروجی اسکریپت از هر node و وضعیت سرویس SSH.

Evidence: host-to-VM SSH for all three, the script output from each node, and SSH service state.

مرحله ۵ — خرابی رو پیدا کن؛ از صفر شروع نکنCheckpoint 5 — find the fault; do not start over

حالا خرابی عمدی: VM lab-c رو خاموش کن و Adapter 2 اون رو از Host-only به NAT تغییر بده. بعد روشنش کن و همون اسکریپت رو اجرا کن. قبل از دست‌کاری، حدس بزن کدوم شاهد فرق می‌کنه: IP، route، name resolution یا listener SSH؟ اینترنت رو هم آزمایش کن؛ ممکنه NAT باعث بشه خروجی اینترنت همچنان کار کنه، در حالی که lab-c از شبکهٔ خصوصی جدا شده.

Now introduce the fault: power off lab-c and change its Adapter 2 from Host-only to NAT. Boot it and run the same script. Before changing anything, predict which evidence will differ: IP, route, name resolution, or SSH listener. Test internet too; NAT may preserve outbound access even though lab-c has left the private network.

مقایسه کن: ip -4 -brief address، ip route، VBoxManage showvminfo "lab-c" و نتیجهٔ ping از دو طرف. اگه lease ثابت برای MAC کارت Host-only داری، NAT کارت دیگری هست و اون mapping آدرسِ این کارت جدید رو ثابت نمی‌کنه. VM رو خاموش کن، Adapter 2 رو به همون Host-only Network برگردان، boot کن و همون آزمون رو تکرار کن.

Compare ip -4 -brief address, ip route, VBoxManage showvminfo "lab-c", and ping from both sides. A fixed lease for the Host-only MAC does not assign that address to a different NAT adapter. Power off, reconnect Adapter 2 to the same Host-only Network, boot, and repeat the test.

اگه ماشین آدرس درست داره ولی ping نمی‌گیره، خرابی رو فوراً به حالت نسبت نده؛ route، mask، فایروال و هم‌پوشانی subnet رو جدا بررسی کن. تعمیر فقط وقتی کامل هست که اسکریپت قبلی دوباره همون نتیجهٔ موفق رو بده.

If the address looks right but ping fails, do not immediately blame the mode; inspect route, mask, firewall, and subnet overlap independently. The repair is complete only when the original script passes again.

راهنمای پله‌ایProgressive hint

شاهدهای VirtualBox و داخل guest رو کنار هم بذار. تغییر NAT ممکنه یک IP تازه و route پیش‌فرض بده؛ سؤال این هست که آیا interface مشترک Host-only هنوز وجود داره؟

Compare VirtualBox evidence with guest evidence. Changing to NAT may produce a new IP and default route; ask whether the shared Host-only interface is still present.

شاهد: قبل/بعدِ تنظیم Adapter 2، IP و route، خطای دسترسی، تعمیر بدون reinstall و اجرای موفق دوباره.

Evidence: Adapter 2 settings before/after, IP and route, the failed reachability check, repair without reinstall, and a passing rerun.

مرحله ۶ — وضعیت پایه تمیز و بازگشت‌پذیر بسازCheckpoint 6 — create a clean, reversible baseline

وقتی هر سه node پایدار و قابل‌دسترسی‌اند، به‌روزرسانیهای امنیتی توزیع رو انجام بده و reboot رو با SSH دوباره بررسی کن. حالا VMها رو خاموش کن و snapshot با نامی مثل lab-baseline-2026-10 بساز. قبل از snapshot مطمئن شو دیسک‌ها وضعیت سالم دارن و هیچ نصب نیمه‌کاره‌ای نمانده. برای استفادهٔ دوباره، clone کامل یا linked clone بساز؛ در cloneها MAC تازه و DHCP lease جدا رو بررسی کن تا آدرس تکراری نسازی.

Once all nodes are stable and reachable, apply distribution security updates and verify SSH again after reboot. Shut down the VMs and create a snapshot such as lab-baseline-2026-10. Before snapshotting, confirm the disks are healthy and no installation is unfinished. For reuse, create a full or linked clone; check that clones have unique MACs and DHCP leases so they do not duplicate addresses.

Snapshot وضعیت VM در همون محصول hypervisor رو نگه می‌داره و ممکنه فضای دیسک میزبان مصرف کنه؛ backup مستقل نیست. حداقل یک بار restore/revert یکی از nodeها رو روی ماشین آزمایشگاهی امتحان کن و بعد connectivity رو دوباره بسنج.

A snapshot stores VM state within the hypervisor and can consume host disk space; it is not an independent backup. Test a revert/restore on one disposable lab node at least once, then verify connectivity again.

راهنمای پله‌ایProgressive hint

قبل از clone، شبکه identity رو در نظر بگیر: MAC تازه می‌تونه DHCP lease دیگری بگیره. بعد از clone، hostname، MAC، lease، hosts mapping و SSH host key رو بازبینی کن.

Before cloning, consider network identity: a new MAC can receive a different lease. After cloning, review hostname, MAC, lease, hosts mappings, and SSH host keys.

شاهد: نام و زمان snapshot، نتیجهٔ reboot، یک revert آزمایش‌شده و چک شبکه بعد از بازگشت.

Evidence: snapshot name and time, reboot result, one tested revert, and a network check after returning.

مرحله ۷ — تحویل به نفر بعدCheckpoint 7 — hand off the lab

پروژه وقتی تمام هست که نفر دیگری بدون پرسیدن «کدوم IP؟» بتونه nodeها رو پیدا کنه و خطا رو از روی شاهد تشخیص بده. یک صفحه تحویل بنویس: نسخهٔ VirtualBox و سیستم‌عامل میزبان، نام شبکه و subnet، نام/MAC/IP هر VM، نام سرویس SSH، دستور آزمون مشترک، وضعیت snapshotها و محدودیت منابع میزبان. password، خصوصی key و token رو وارد گزارش نکن.

The project is complete when another operator can find the nodes without asking “which IP?” and can diagnose a fault from evidence. Write a one-page handoff with VirtualBox and host OS versions, network name and subnet, each VM's name/MAC/IP, SSH service unit, shared test command, snapshot state, and host resource limits. Do not include passwords, private keys, or tokens.

معیار قبولی: هر سه توزیع boot می‌شن؛ هر سه روی Host-only آدرس یکتا و نام قابل‌حل دارن؛ SSH از host به هر سه کار می‌کنه؛ اسکریپت هر node دو peer رو می‌بینه؛ خرابی عمداً ایجاد و بدون نصب مجدد تعمیر شده؛ وضعیت پایه و روش revert مستند هست.

Acceptance: all three distributions boot; each has a unique Host-only address and resolvable name; host SSH works to all three; each node's script reaches both peers; the deliberate fault is repaired without reinstall; and the baseline and revert procedure are documented.

اگه جایی گیر کردی، از نزدیک‌ترین لایه شروع کنIf you get stuck, start at the nearest layer

اسم resolve نمی‌شهA name does not resolve

اول getent hosts lab-b، بعد mapping فایل hosts رو در همون ماشینی که دستور رو اجرا کرده‌ای بخون. DNS عمومی و hosts محلی دو مسیر متفاوت‌اند.

Start with getent hosts lab-b, then inspect the hosts mapping on the machine where you ran the command. Public DNS and local hosts entries are different paths.

اسم به IP درست می‌رسه ولی پاسخ نیستThe name resolves but there is no reply

داخل guest ip -4 -brief address و ip route رو ببین؛ در VirtualBox نوع و نام Adapter 2 رو مقایسه کن؛ بعد سیاست فایروال و ابزار ping رو بررسی کن. هر بار فقط یک متغیر رو عوض کن.

In the guest inspect ip -4 -brief address and ip route; compare Adapter 2 mode and network in VirtualBox; then inspect firewall policy and ping availability. Change one variable at a time.

بعد از clone دو ماشین یک IP دارنTwo clones have the same IP

MACها و DHCP fixed leaseها رو مقایسه کن. clone رو موقتاً خاموش کن، MAC یکتا بساز، lease درست رو اختصاص بده و mappingهای hosts رو اصلاح کن. خاموش‌کردن فایروال راه‌حل این تداخل نیست.

Compare MACs and fixed DHCP leases. Temporarily power off the clone, give it a unique MAC, assign the correct lease, and update hosts mappings. Disabling the firewall does not fix this collision.

Runbook مرجع — بعد از تلاش خودت سراغش بیاReference runbook — return here after your own attempt

این نسخهٔ مرجع هست، نه تنها چیدمان ممکن. GUI و نام گزینه‌ها بین نسخه‌ها فرق می‌کنن؛ مقصد ثابت هست: یک Host-only مشترک، سه lease ثابت، و NAT جدا برای خروجی.

This is one reference design, not the only valid layout. GUI labels vary by release; the invariant is one shared Host-only network, three fixed leases, and separate NAT for outbound access.

  1. سه VM با Ubuntu Server، Debian و Fedora Server بساز؛ hostnameها رو lab-a/b/c بذار و SSH سرور رو نصب/فعال کن.
  2. Create Ubuntu Server, Debian, and Fedora Server VMs; set hostnames to lab-a/b/c and install/enable the SSH server.
  3. در VirtualBox Network Manager یک Host-only شبکه غیرمتداخل بساز؛ host .1/24، DHCP سرور .2 و pool مثلاً .100–.150. هر guest: Adapter 1=NAT، Adapter 2=همون Host-only.
  4. In VirtualBox Network Manager create a non-overlapping Host-only network: host .1/24, DHCP server .2, pool such as .100–.150. Each guest: Adapter 1=NAT, Adapter 2=that Host-only network.
  5. MAC کارت دوم هر VM رو بخون و با VBoxManage dhcpserver modify --interface="..." --mac-address="..." --fixed-address="192.168.77.21" به‌ترتیب .21، .22 و .23 بده؛ syntax نسخهٔ نصب‌شده رو با VBoxManage dhcpserver --help بررسی کن.
  6. Read each VM's second-adapter MAC and use VBoxManage dhcpserver modify --interface="..." --mac-address="..." --fixed-address="192.168.77.21" to assign .21, .22, and .23; verify syntax with VBoxManage dhcpserver --help for your release.
  7. DHCP رو در هر guest renew کن، IP رو با ip -4 -brief address بررسی کن و mapping یکسان /etc/hosts رو در هر سه guest و فایل hosts میزبان اضافه کن.
  8. Renew DHCP in every guest, verify with ip -4 -brief address, and add identical /etc/hosts mappings on all guests and the host's hosts file.
  9. از host به هر نام SSH بزن؛ ping همهٔ peerها رو اجرا کن؛ با حالت شبکه اشتباه Adapter 2 در lab-c خرابی رو بازتولید کن؛ تنظیم رو برگردان و همون آزمون رو دوباره پاس کن.
  10. SSH from the host to each name and ping all peers; reproduce the fault by setting lab-c Adapter 2 to the wrong network mode; restore it and pass the same test again.
  11. به‌روزرسانی، reboot، connectivity check، snapshot وضعیت پایه و یک revert آزمایشی؛ inventory و تحویل امن رو ذخیره کن.
  12. Update, reboot, check connectivity, snapshot a baseline, test one revert, and save the inventory and safe handoff.

یادداشت مهندسی: این پروژه ثابت کرد «اینترنت دارم» با «روی شبکهٔ آزمایشگاه هستم» یکی نیست. وقتی اسم، MAC، lease، IP و route رو از هم جدا بررسی کنی، یک VM خراب لازم نیست دوباره ساخته بشه—کافیه لایهٔ اشتباه رو پیدا و همون‌جا اصلاح کنی.

Engineering note: this project proved that “I have internet” is not the same as “I am on the lab network.” Once names, MACs, leases, IPs, and routes are checked separately, a broken VM need not be rebuilt—you can find and repair the wrong layer.
