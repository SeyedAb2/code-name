پروژهٔ ۱ — اولین ماشین

Project 1 — your first machine

این پروژه اولین تحویل واقعیته: یک Ubuntu Server که از میزبان بهش SSH می‌زنی، reboot رو رد می‌کنه و نفر بعد هم از روی توضیحاتت می‌فهمه چطور ساخته شده.

Build a clean Ubuntu Server VM reachable over SSH from the host, prove it survives a reboot, and leave a handoff another person can use to reproduce it.

۸۰دقیقهminutes
۵مرحلهcheckpoints

مأموریت: VM بساز و از بیرون به اون وصل شوMission: create a VM and connect from outside

قرار نیست فقط تصویر از نصاب تحویل بدی. ماشین باید واقعاً از دیسک boot بشه، کاربر مشخص داشته باشه، شبکهٔ خروجی داشته باشه و SSH از خود میزبان پاسخ بده. اگه اتصال خراب شد، باید بتونی بگی درخواست کجا گم شد.

A screenshot of the installer is not a deliverable. The machine must boot from disk, have a known user, reach the network, and answer SSH from the host. If the connection fails, you should be able to say where the request was lost.

مسیر اصلی برای Windows/macOS/Linux یکسان می‌مونه: VirtualBox با یک NAT adapter و port-forward محدود به loopback میزبان. اگه میزبانت Hyper-V/UTM/libvirt داره، می‌تونی معادلش رو بسازی؛ ولی رفتار شبکه اون ابزار رو در تحویل روشن بنویس. روی شبکهٔ بیرونی/عمومی پورت SSH رو منتشر نکن.

The primary path is the same across Windows/macOS/Linux: VirtualBox with one NAT adapter and a port forward bound to host loopback. If you use Hyper-V, UTM, or libvirt, implement the equivalent and document its networking behavior. Do not expose SSH on a public/remote network.

خط بالایی مسیر SSH از میزبان به guest هست؛ خط پایین خروجی guest برای به‌روزرسانی. NAT معمولاً اتصال ورودی مستقیم از LAN نمی‌ده؛ port-forward این آزمایش فقط روی 127.0.0.1 bind می‌شه. IP مهمان ممکنه با reboot عوض بشه، ولی پورت میزبان این تمرین ثابت می‌مونه.

The upper path is host-to-guest SSH; the lower path is guest outbound access for updates. NAT usually does not provide direct inbound LAN access; this lab binds the forward only to 127.0.0.1. The guest IP may change after reboot, but the host port remains fixed.

محدودیت‌ها و معیار تحویلConstraints and deliverables

  • یک VM و یک توزیع Linux؛ Ubuntu Server LTS مسیر مرجع هست. database، cluster و reverse proxy نداریم.
  • One VM and one Linux distribution; Ubuntu Server LTS is the reference path. No database, cluster, or reverse proxy.
  • دیسک فقط دیسک مجازی تازه و آزمایشی پروژه هست؛ دیسک میزبان یا VM کاری رو انتخاب نکن.
  • Use only a new disposable project virtual disk; never select the host disk or a work VM.
  • SSH فقط از میزبان و روی loopback؛ رمز/key خصوصی رو در repository یا تحویل ثبت نکن.
  • SSH is host-only on loopback; never store passwords/private keys in the repository or handoff.
  • تحویل شامل مشخصات ماشین، hostname، distro، firmware، شبکه، فرمان SSH، نتیجهٔ به‌روزرسانی، شاهد بعد از reboot و یک گزارش خرابی هست.
  • Deliver VM spec, hostname, distro, firmware, network, SSH command, update result, reboot proof, and one fault report.

معیار قبولی: از host به 127.0.0.1:2222 با SSH وارد می‌شی؛ guest مخزن بسته‌ها رو resolve می‌کنه؛ بعد از reboot همون اتصال کار می‌کنه؛ خرابی عمدی رو با شاهد پیدا و تعمیر کرده‌ای؛ تحویل برای نفر بعد کافیه.

Pass criteria: SSH from the host reaches 127.0.0.1:2222; the guest resolves and reaches its package mirror; SSH works after reboot; you diagnosed and repaired the deliberate fault with evidence; the handoff is reproducible.

مرحله ۱ — مشخصات رو قبل از نصب ببندCheckpoint 1 — decide the VM spec before installing

در VirtualBox یک VM با نام lab-ssh بساز. ISO رسمی Ubuntu Server با معماری میزبانت بگیر و unattended install رو خاموش کن. برای آزمایش سبک، ۲ vCPU، حدود ۲ تا ۴ GiB RAM و دیسک مجازی با ظرفیت منطقی حدود ۲۰ تا ۳۰ GiB نقطهٔ شروع هست؛ اگه host کم‌منبع هست، حداقل‌های نسخه رو بررسی کن. این عددها نسخهٔ جهان‌شمول نیستن.

Create a VirtualBox VM named lab-ssh. Obtain an official Ubuntu Server ISO matching the host architecture and disable unattended install. For a small lab, two vCPUs, roughly 2–4 GiB RAM, and a virtual disk around 20–30 GiB are starting points; check release requirements on a constrained host. These are not universal values.

UEFI رو انتخاب کن و بعد از ساخت، قبل از نصاب خلاصهٔ CPU/RAM/دیسک و ISO رو بخون. host باید فضای آزاد کافی برای رشد فایل دیسک داشته باشه. برای گزارش ثبت کن که VM از کدوم دیسک مجازی boot می‌کنه؛ اگه چیزی با دیسک فیزیکی میزبان برابر بود، فوراً متوقف شو.

Choose UEFI, then review CPU/RAM/disk and ISO before starting the installer. The host needs enough free space for the virtual disk to grow. Record which virtual disk the VM boots from; if it appears to be a host physical disk, stop immediately.

راهنمای پله‌ایProgressive hint

اول در رسانهٔ مجازی و تنظیمات VM دنبال معماری، firmware و دیسک مسیر بگرد؛ هنوز داخل نصاب چیزی رو partition نکن.

First inspect architecture, firmware, and disk path in VM settings; do not partition anything in the installer yet.

شاهد مرحله: یک یادداشت از نام VM، ISO/نسخه/معماری، firmware، RAM/vCPU و ظرفیت/مسیر دیسک.

Checkpoint evidence: Record VM name, ISO/release/architecture, firmware, RAM/vCPU, and disk size/path.

مرحله ۲ — نصب کن، ولی خلاصه رو بخونCheckpoint 2 — install, but read the storage summary

از ISO boot کن و Ubuntu Server رو با guided storage روی همون دیسک مجازی پروژه نصب کن. hostname رو lab-ssh بذار و یک کاربر عادی بساز. رمز آزمایشگاهی یکتا انتخاب کن؛ جایی commit نکن. در بخش SSH، نصب OpenSSH Server رو فعال کن. اگه نصاب اون گزینه رو نداشت، بعد از نصب از console بسته رو نصب می‌کنی.

Boot the ISO and install Ubuntu Server with guided storage on this project’s virtual disk. Set hostname to lab-ssh and create a regular user. Use a unique lab password and never commit it. Enable OpenSSH Server in the installer; if that option is unavailable, install it later from the console.

قبل از تأیید storage، خلاصهٔ partition/فایل‌سیستم و نام دیسک رو تطبیق بده؛ تأیید نصب دادهٔ قبلی همون دیسک مجازی رو پاک می‌کنه. بعد از finish، ISO رو eject کن و VM رو از دیسک boot کن. داخل guest cat /etc/os-release و findmnt / رو اجرا کن؛ این دو نصب سیستم و root mount رو نشون می‌دن، نه سلامت SSH یا شبکه رو.

Before confirming storage, verify partition/filesystem summary and disk identity; installation erases previous data on that virtual disk. After finish, eject the ISO and boot from disk. In the guest run cat /etc/os-release and findmnt /; they show installed OS and root mount, not SSH or network health.

راهنمای پله‌ایProgressive hint

اگه دوباره نصاب آمد، ISO یا ترتیب بوت رو بررسی کن؛ نصب رو فوراً تکرار نکن.

If the installer returns, inspect ISO and boot order; do not immediately reinstall.

شاهد مرحله: guest از دیسک boot شده، hostname و distro درست‌اند و کاربر عادی می‌تونه وارد console بشه.

Checkpoint evidence: The guest boots from disk, distro/hostname are correct, and the regular user can log in on the console.

مرحله ۳ — مسیر SSH رو از دو طرف بسازCheckpoint 3 — configure SSH from both sides

Adapter اول VM رو NAT بذار. در VirtualBox → Settings → Network → Advanced → Port Forwarding VM رو خاموش کن؛ سپس یک قانون TCP بساز: Host IP برابر 127.0.0.1، Host Port برابر 2222، Guest Port برابر 22. خالی‌گذاشتن Guest IP معمولاً قانون رو به آدرس NIC مهمان می‌رساند؛ رفتار رو در نسخهٔ خودت بررسی کن. این پورت رو روی 0.0.0.0 باز نکن.

Set Adapter 1 to NAT. In VirtualBox → Settings → Network → Advanced → Port Forwarding, power off the VM, then add TCP: Host IP 127.0.0.1, Host Port 2222, Guest Port 22. Leaving Guest IP empty commonly targets the guest NIC address; verify behavior in your version. Do not bind this port to 0.0.0.0.

معادل CLI در VirtualBox چنین هست؛ اگه پورت اشغال هست، پورت میزبان دیگری مثل 2224 انتخاب و همهٔ جاها همون رو ثبت کن:

The VirtualBox CLI equivalent is below. If the host port is occupied, choose another, such as 2224, and use it consistently:

VBoxManage modifyvm "lab-ssh" --nat-pf1 "ssh,tcp,127.0.0.1,2222,,22"

داخل guest وضعیت سرویس رو ببین: sudo systemctl status ssh و ss -ltn. باید sshd روی پورت مهمان 22 گوش بده. این فقط listener مهمان رو ثابت می‌کنه؛ NAT forward و دسترسی از host هنوز جدا مانده‌اند. اگه بسته هست، sudo apt update، sudo apt install openssh-server و sudo systemctl enable --now ssh رو اجرا کن و دوباره listener رو ببین.

Check the guest with sudo systemctl status ssh and ss -ltn. sshd should listen on guest port 22. This proves only the guest listener; NAT forwarding and host access remain separate. If absent, run sudo apt update, sudo apt install openssh-server, and sudo systemctl enable --now ssh, then verify again.

روی میزبان یک کلید آزمایشگاهی بساز؛ فقط عمومی key به guest می‌ره و خصوصی key روی host می‌مونه.

Generate a lab key on the host; only the public key goes to the guest, while the private key stays on the host.

New-Item -ItemType Directory -Force "$env:USERPROFILE\.ssh" | Out-Null
ssh-keygen -t ed25519 -f "$env:USERPROFILE\.ssh\lab-ssh-project-1"

mkdir -p ~/.ssh
ssh-keygen -t ed25519 -f ~/.ssh/lab-ssh-project-1

در PowerShell دستورهای اول رو اجرا کن؛ در macOS/Linux دومی. اگه نام فایل از قبل هست، برای جلوگیری از بازنویسی مسیر تازه انتخاب کن. حالا عمومی key رو چاپ کن و همون یک خط رو از console وارد guest کن:

Use the first commands in PowerShell, the second in macOS/Linux. If the key path already exists, choose a new one rather than overwriting it. Print the public key and paste that single line through the guest console:

Get-Content "$env:USERPROFILE\.ssh\lab-ssh-project-1.pub"
cat ~/.ssh/lab-ssh-project-1.pub

داخل console مهمان، در نشست همون کاربر اجرا کن؛ خط کلید رو بعد از فرمان cat paste کن و با Ctrl-D پایان بده:

In the guest console, as that user, run this; paste the key after cat and finish with Ctrl-D:

install -d -m 700 ~/.ssh
cat >> ~/.ssh/authorized_keys
PASTE_PUBLIC_KEY_LINE_THEN_CTRL_D
chmod 600 ~/.ssh/authorized_keys

حالا از host وصل شو: ssh -i KEY -p 2222 USER@127.0.0.1. prompt و hostname رو بررسی کن؛ این اتصال LAN exposure رو ثابت نمی‌کنه—و قرار نیست بکند.

Now connect from the host: ssh -i KEY -p 2222 USER@127.0.0.1. Verify the prompt and hostname; this does not prove LAN exposure—and it should not.

راهنمای پله‌ایProgressive hint

سه عدد رو از هم جدا نگه دار: host IP=127.0.0.1، پورت میزبان=2222، پورت مهمان=22. بعد listener داخل guest و قانون NAT رو جدا بررسی کن.

Keep three values distinct: host IP 127.0.0.1, host port 2222, guest port 22. Then inspect the guest listener and NAT rule separately.

شاهد مرحله: فرمان SSH از host، hostname guest و سرویس ssh فعال.

Checkpoint evidence: SSH command from host, guest hostname, and active ssh service.

مرحله ۴ — خرابی عمدی رو از روی نشانه پیدا کنCheckpoint 4 — diagnose a deliberate mismatch

VM رو خاموش کن؛ در قانون NAT، Host Port رو از 2222 به 2223 تغییر بده ولی عمداً دستور یادداشت‌شده رو دست نزن. VM رو روشن کن و ssh -i KEY -p 2222 USER@127.0.0.1 رو اجرا کن. پیش‌بینی‌ات رو قبل از اجرا بنویس: timeout می‌بینی یا اتصال refused؟ چه شاهدای در guest و host تفاوت رو معلوم می‌کنه؟

Power off the VM, change the NAT rule’s Host Port from 2222 to 2223, and deliberately leave your documented command unchanged. Start the VM and run ssh -i KEY -p 2222 USER@127.0.0.1. Predict before testing: timeout or connection refused? What evidence on host and guest identifies the mismatch?

یک اتصال refused معمولاً نشون می‌ده host به اون پورت رسید ولی listener/forward اونجا نیست؛ timeout می‌تونه فایروال یا route هم باشه. نتیجه قطعی نیست. داخل guest با ss -ltn پورت 22 رو بررسی کن؛ در VirtualBox قانون رو بخون؛ از پورت میزبان 2223 رو جدا test کن. وقتی شاهد mismatch رو نشان داد، قانون رو به 2222 برگردان و همون SSH دستور رو دوباره اجرا کن.

Connection refused usually means the host reached that port but no listener/forward is there; timeout may also involve firewall or routing. Neither is definitive. Verify guest port 22 with ss -ltn, inspect the VirtualBox rule, and test host port 2223 separately. Once evidence shows the mismatch, restore 2222 and rerun the same SSH command.

راهنمای پله‌ایProgressive hint

اگه sshd داخل guest روی 22 گوش می‌ده ولی پورت میزبان 2222 به guest نمی‌رسه، host و پورت مهمان رو قاطی نکن. یک لایه رو اصلاح کن، نه sshd و فایروال رو هم‌زمان.

If sshd listens on guest port 22 but host port 2222 does not reach it, keep host and guest ports distinct. Fix one layer instead of changing sshd and firewall together.

شاهد مرحله: خطای قبل، قانون غلط، تشخیص، قانون اصلاح‌شده و SSH موفق بعد از تعمیر.

Checkpoint evidence: Initial failure, incorrect rule, diagnosis, repaired rule, and successful SSH afterward.

مرحله ۵ — به‌روزرسانی، reboot و تحویلCheckpoint 5 — update, reboot, and handoff

از داخل guest sudo apt update رو اجرا کن. خروجی mirror و پایان بدون خطا، DNS/route/TCP تا repository رو در همون لحظه ثابت می‌کنه؛ نصب همهٔ upgradeها یا سلامت SSH رو نه. اگه DNS خرابی هست، ip route و resolver رو جدا بررسی کن. حالا sudo reboot بزن و بعد از خاموش/بالاآمدن دوباره همون SSH دستور رو از host اجرا کن.

Run sudo apt update in the guest. Successful mirror access proves DNS/route/TCP to the repository at that moment; it does not install all upgrades or prove SSH health. If DNS fails, inspect route and resolver separately. Run sudo reboot, wait for startup, and repeat the exact host SSH command.

این شاهد نشون می‌ده host forward بعد از reboot برقراره و کاربر/sshd می‌تونن login کنند. بعد داخل SSH، hostnamectl --static، ip -br address و systemctl is-active ssh رو ثبت کن. اگه Guest Additions رو برای resize/clipboard نصب کردی، نام نسخه و وضعیت سرویس رو یادداشت کن؛ برای قبولی SSH لازم نیست.

This proves the host forward survived reboot and user/sshd can log in. Over SSH record hostnamectl --static, ip -br address, and systemctl is-active ssh. If you installed Guest Additions for resize/clipboard, note its version and service state; it is not required for SSH acceptance.

snapshot اختیاری رو فقط بعد از وضعیت سالم و با نام روشن بگیر؛ snapshot backup مستقل نیست. تحویل رو بدون رمز و خصوصی key بنویس: host OS، VirtualBox/provider/version، distro/نسخه/معماری، firmware، CPU/RAM/دیسک، شبکه قانون، فرمان اتصال، نتایج به‌روزرسانی/reboot و محل لاگ یا snapshot.

Take an optional, clearly named snapshot only after reaching a known-good state; it is not an independent backup. Write a handoff without passwords/private keys: host OS, VirtualBox/provider/version, distro/release/architecture, firmware, CPU/RAM/disk, network rule, connect command, update/reboot results, and log/snapshot location.

راهنمای پله‌ایProgressive hint

اگه اتصال فقط تا reboot کار می‌کنه، مقایسه کن چی ephemeral بوده: NIC، NAT قانون، SSH سرویس یا address. قانون در تنظیمات VM پایدارتر از فرمان موقتی داخل guest هست.

If access works only until reboot, identify what was ephemeral: NIC, NAT rule, SSH service, or address. A VM-level forwarding rule should outlive guest reboot.

شاهد مرحله: به‌روزرسانی لاگ، SSH بعد از reboot، مشخصات نهایی و تحویل قابل‌بازتولید.

Checkpoint evidence: Update result, post-reboot SSH, final specification, and reproducible handoff.

بازبینی نهایی: آیا نفر بعد هم می‌تونه وصل بشه؟Final review: can the next person connect too?

از یک ترمینال host تازه، بدون تکیه به session قبلی، فرمان SSH رو اجرا کن. کاربر و hostname درست‌اند؟ پورت forward هنوز loopback-only هست؟ بعد از reboot به‌روزرسانی mirror پاسخ داد؟ اگه VM خاموش بشه، تحویل می‌گه چطور دوباره روشنش کنند؟ این‌ها قبولی پروژه‌اند؛ تصویر به‌تنهایی نیست.

From a fresh host terminal, run the SSH command without relying on an old session. Are user and hostname correct? Is forwarding still loopback-only? Did the update mirror respond after reboot? Can the handoff tell someone how to start the VM again? These are the acceptance criteria—not a screenshot alone.

اگه host VirtualBox نداره، همین acceptanceها رو با hypervisor خودت اجرا کن و معادل مسیر شبکه رو واضح بنویس. برای NAT libvirt/Proxmox ممکنه port forwarding آماده نباشه و به شبکهٔ جداگانه نیاز داشته باشه؛ پورت SSH رو به LAN/عمومی باز نکن فقط برای اینکه آزمایش ساده بشه.

If your host does not use VirtualBox, meet the same acceptance criteria with its hypervisor and document the network path. libvirt/Proxmox NAT may not provide the same forwarding automatically; do not expose SSH to LAN/public just to simplify the test.

اگه در مسیر گیر کردیIf you get stuck

راهنما ۱ — ISO دوباره boot می‌شهHint 1 — the ISO boots again

ISO متصل و ترتیب بوت رو بررسی کن؛ بعد نشان بده findmnt / از چه دستگاهای آمده.

Inspect attached ISO and boot order, then identify the root device with findmnt /.

راهنما ۲ — SSH جواب نمی‌دهHint 2 — SSH does not answer

اول guest: sshd روی 22؟ بعد host: listener/forward روی 127.0.0.1:2222؟ سپس key/کاربر.

First guest: is sshd listening on 22? Then host: is forwarding present on 127.0.0.1:2222? Then check key/user.

راهنما ۳ — به‌روزرسانی mirror resolve نمی‌شهHint 3 — the mirror does not resolve

link، guest address، پیش‌فرض route و DNS رو جدا کن؛ ping شکست‌خورده به‌تنهایی علت رو مشخص نمی‌کنه.

Separate link, guest address, default route, and DNS; a failed ping alone does not identify the cause.

Runbook مرجع — راه‌حل کامل در انتهای مأموریتReference runbook — the complete path at the end

این راهنما رو بعد از مرحلهها بخون؛ هدف پروژه این بود که قبل از دیدن جواب، مسیر خودت رو بسازی. مقادیر نمونه رو با host واقعی جایگزین کن.

Read this after completing the checkpoints; the point was to build your own path before seeing the answer. Replace example values with your actual host.

  1. VirtualBox VM تازه با ISO رسمی Ubuntu Server مناسب معماری، UEFI، ۲ vCPU، RAM متناسب و ۲۰–۳۰ GiB دیسک مجازی؛ guided partition بعد از تطبیق نام دیسک.
  2. Create a fresh VirtualBox VM with an official architecture-matched Ubuntu Server ISO, UEFI, two vCPUs, suitable RAM, and a 20–30 GiB virtual disk; use guided partitioning only after confirming the disk.
  3. hostname/کاربر عادی بساز، OpenSSH Server رو نصب کن، ISO رو جدا کن و از دیسک boot؛ با /etc/os-release و findmnt / تأیید کن.
  4. Create hostname/regular user, install OpenSSH Server, detach ISO, boot from disk, and verify with /etc/os-release and findmnt /.
  5. NAT TCP قانون: 127.0.0.1:2222 → guest:22. در guest sudo systemctl enable --now ssh و ss -ltn رو بررسی کن.
  6. Add NAT TCP rule 127.0.0.1:2222 → guest:22. In the guest run sudo systemctl enable --now ssh and verify with ss -ltn.
  7. روی host کلید ed25519 بساز؛ عمومی key رو به authorized_keys مهمان اضافه کن؛ خصوصی key رو host نگه دار. اتصال: ssh -i KEY -p 2222 USER@127.0.0.1.
  8. Generate an Ed25519 host key, install only its public key in guest authorized_keys, and keep the private key on the host. Connect using ssh -i KEY -p 2222 USER@127.0.0.1.
  9. خرابی عمدی 2223 رو با مقایسهٔ دستور، NAT قانون و guest listener پیدا کن؛ قانون رو به 2222 برگردان و همون دستور رو تکرار کن.
  10. Diagnose the deliberate 2223 mismatch by comparing command, NAT rule, and guest listener; restore 2222 and rerun the same command.
  11. از guest sudo apt update؛ سپس sudo reboot و SSH دوباره. hostname، address و سرویس رو ثبت و تحویل بدون اطلاعات محرمانه بنویس.
  12. Run sudo apt update, reboot, and reconnect over SSH. Record hostname, address, service state, and a secret-free handoff.

یادداشت مهندسی: این پروژه ثابت کرد پورت میزبان forward و guest sshd دو جزء جدا هستن، NAT خروجی رو با ورودی یکی نمی‌کنه، و reboot persistence رو باید با آزمون دوباره ثابت کرد.

Engineering note: This project proved that host forwarding and guest sshd are separate components, NAT outbound is not inbound access, and reboot persistence must be tested—not assumed.

برای قبولی، هم اتصال واقعی SSH رو داری و هم توضیح اینکه درخواست از کجا عبور کرد. اگه اتصال شکست بخوره، وضعیت و لاگ رو قبل از تغییر ثبت می‌کنی؛ اگه درست شد، همون آزمون رو بعد از reboot تکرار می‌کنی. همین عادت، VM بعدی رو از «روی لپ‌تاپ من کار می‌کنه» به یک ماشین قابل‌بازتولید تبدیل می‌کنه.

To pass, you have both a working SSH connection and an explanation of its path. If it fails, you record state and logs before changing anything; if it works, you repeat the test after reboot. That habit turns the next VM from “works on my laptop” into a reproducible machine.

پروژهٔ بعدی همین ایده رو بزرگ‌تر می‌کنه: به‌جای یک VM، سه ماشین داریم که باید همدیگه رو ببینن. یادت بمونه NAT و port forwarding مشکل ورود از میزبان رو حل می‌کنن؛ شبکهٔ بین چند مهمان داستان جداست.
