Project 3 — an automated lab

آخر مسیر، آزمایشگاه باید از حافظهٔ تو مستقل بشه. کل محیط سه‌ماشینه رو طوری تعریف می‌کنیم که پاکش کنی، دوباره بسازیش و نتیجه همون باشه.

This time, deleting the lab must not mean rebuilding it from memory. Its definition stays beside your code so one command can bring it back.

مأموریت: آزمایشگاه رو از نو بسازMission: rebuild the lab from scratch

پروژهٔ قبل سه ماشین قابل‌استفاده تحویل داد، ولی ساختنشان وقت گرفت و چند تنظیم فقط در یادداشت‌های تو ماند. این بار همون آزمایشگاه سه‌گرهی رو در یک پوشهٔ نسخه‌بندی‌شده تعریف می‌کنی: سه VM، یک شبکهٔ خصوصی، کاربر و SSH آماده، بسته‌های پایه، و یک آزمون که بعد از هر ساخت اجرا می‌شه.

The previous project delivered three usable machines, but creating them took time and a few settings lived only in your notes. This time, define the same three-node lab in a version-controlled directory: three VMs, a private network, ready users and SSH, baseline packages, and a check that runs after every build.

شرط قبولی یک بار vagrant up نیست. باید آزمایشگاه رو سالم بسازی، خرابی provisioning رو پیدا کنی، provisioning رو دوباره اجرا کنی، همهٔ VMها رو از بین ببری و دوباره بسازی؛ بعد نشان بدی همون hostname، IP، سرویس و آزمون شبکه برگشته‌اند.

Passing once with vagrant up is not enough. Build the lab, diagnose a provisioning defect, rerun provisioning, destroy every VM, and recreate them; then prove that hostnames, addresses, services, and network checks came back as defined.

قید ایمنی: همه‌چیز باید داخل یک پوشهٔ آزمایشگاهی تازه و VMهای Vagrant بمونه. قبل از vagrant destroy، vagrant status و نام محیط رو بررسی کن. روی VM یا دیسک واقعی/مهم این دستورها رو آزمایش نکن؛ اطلاعات محرمانه واقعی هم وارد فایل‌ها نمی‌شه.

Safety constraint: keep everything inside a fresh lab directory and its Vagrant VMs. Before vagrant destroy, inspect vagrant status and the environment name. Never test these commands against an important VM or disk; no real secrets belong in these files.

قرارداد پروژه و نقشهٔ خروجیProject contract and output map

برای اینکه بازسازی قابل‌تکرار بمونه، هر سه node رو روی یک box ثابت Ubuntu می‌سازیم؛ تفاوت توزیع‌ها رو در پروژهٔ قبل آزمودیم. وقتی ساخت و آزمون‌ها پاس شد، عوض‌کردن boxهای Debian و Fedora توسعهٔ بعدی هست. نسخهٔ دقیق box رو از فهرست انتخاب و pin کن؛ نام box به‌تنهایی تضمین نمی‌کنه همیشه به یک image تغییرناپذیر اشاره کنه.

For a repeatable rebuild, this project uses one Ubuntu box for all three nodes; distribution differences were tested in the previous project. Once creation and tests pass, swapping in Debian and Fedora boxes is a follow-up. Select and pin the exact box version from its catalog; a box name alone does not guarantee one immutable image.

Vagrant چرخهٔ عمر VM رو مدیریت می‌کنه؛ provider ماشین رو می‌سازه؛ provisioner دستورهای راه‌اندازی رو اجرا می‌کنه. cloud-init درون guest، دادهٔ آغازین رو از datasource می‌خونه. این‌ها جای هم نیستن. در مأموریت اصلی از shell provisioner استفاده کن تا روی box عمومی روشن باشه چی اجرا می‌شه؛ cloud-init فقط وقتی مناسب هست که image و datasource واقعاً پشتیبانی‌اش کنند.

Vagrant manages VM lifecycle; a provider creates the machine; a provisioner runs setup commands. cloud-init reads instance data from a datasource inside the guest. These are not interchangeable. Use the shell provisioner in the main mission so setup on a general Vagrant box is explicit; use cloud-init only when the image and datasource actually support it.

از فایل تعریف تا آزمون دوبارهFrom definition file to repeated verification

فایل‌های نسخه‌دار VM می‌سازن؛ provisioning مهمان رو آماده می‌کنه؛ بررسی ثابت می‌کنه نتیجه واقعاً آماده هست.

Versioned files create VMs; provisioning prepares guests; verification proves the result is actually ready.

ابر خصوصی این پروژه روی لپ‌تاپ توست؛ اگه provider، box یا virtualization میزبان در دسترس نباشه، فایل‌ها به‌تنهایی ماشین تولید نمی‌کنن. شکست هر مرحله رو از خروجی همون مرحله پیدا کن—مثلاً خطای box با SSH داخل guest حل نمی‌شه.

This project's private cloud is your laptop. If the provider, box, or host virtualization is unavailable, files alone cannot create machines. Diagnose each stage from its own output—a box error, for example, cannot be fixed by changing guest SSH.

مرحله ۱ — محیط رو قبل از کدنویسی آماده کنCheckpoint 1 — prepare the environment before coding

داخل یک پوشهٔ تازه، ابزارها رو بررسی کن: vagrant --version، VBoxManage --version و VBoxManage list hostonlyifs. انتظار داری Vagrant، VirtualBox و دست‌کم یک Host-only شبکه دیده بشن. این فقط نصب ابزار و وجود interface رو ثابت می‌کنه؛ سلامت VT-x/AMD-V یا فضای کافی رو هنوز نه. اگه VirtualBox نمی‌تونه VM بسازد، خطای همون provider رو قبل از ادامه حل کن.

In a fresh directory, inspect vagrant --version, VBoxManage --version, and VBoxManage list hostonlyifs. You should see Vagrant, VirtualBox, and at least one Host-only network. This proves the tools and interface exist, not that hardware virtualization or free disk space is healthy. If VirtualBox cannot create a VM, resolve that provider error before proceeding.

موجودی پروژهٔ قبل رو کنار دستت بذار: سه hostname و IP. subnet رو با LAN/VPN میزبان تطبیق بده و یک subnet غیرمتداخل انتخاب کن. README از همین اول باید نیازمندی‌ها و پاک‌سازی امن رو ثبت کنه؛ هنوز destroy نزن.

Keep the previous project's inventory nearby: three hostnames and addresses. Check the subnet against the host LAN/VPN and choose a non-overlapping range. Start the README with prerequisites and safe cleanup instructions; do not run destroy yet.

راهنمای پله‌ایProgressive hint

اگه provider آماده نیست، Vagrant اون رو از داخل Vagrantfile نصب نمی‌کنه. نسخهٔ VirtualBox، Vagrant و box رو جدا یادداشت کن تا بعداً معلوم باشه بازسازی روی چه ترکیبی انجام شده.

If a provider is missing, the Vagrantfile does not install it. Record Vagrant, VirtualBox, and box versions separately so the rebuild's environment is known.

شاهد: نسخهٔ ابزارها، نام Host-only شبکه، subnet و فضای آزاد میزبان.

Evidence: tool versions, Host-only network name, subnet, and free host disk space.

مرحله ۲ — نسخهٔ box رو شناور نگذارCheckpoint 2 — do not let the box version float

یک box سازگار با Ubuntu Server و provider VirtualBox انتخاب کن. نسخهٔ دقیق رو در .box-version ثبت و همراه Vagrantfile در Git نگه دار. نسخه رو از فهرست تأیید کن؛ مقدار ساختگی ممکنه وجود نداشته باشه یا برای provider دیگری باشه. اسم، version و provider رو در README ثبت کن.

Choose an Ubuntu Server box compatible with the VirtualBox provider. Record the exact version in .box-version and commit it beside the Vagrantfile. Verify the version in its catalog; a made-up value may not exist or may target another provider. Record name, version, and provider in the README.

پروژه رو به Git اضافه و وضعیت رو ببین. تعریف‌ها باید version-control بشن؛ دیسک VM، خصوصی key و اطلاعات محرمانه رو commit نمی‌کنی. اگه box خصوصی هست، دسترسی رو از credential امن Vagrant تأمین کن، نه از متن Vagrantfile.

Put the project under Git and inspect status. Definitions belong in version control; VM disks, private keys, and secrets do not. If the box is private, use Vagrant's secure credentials rather than embedding access material in the Vagrantfile.

راهنمای پله‌ایProgressive hint

box محلی ممکنه cache قدیمی باشه؛ اون رو با فهرست یکی نگیر. نام، version و provider سه مشخصهٔ جدا هستن.

A local box may be an old cache; do not confuse it with the catalog. Name, version, and provider are separate properties.

شاهد: مشخصات box در README و diff فایل‌های تعریف، بدون دیسک یا credential.

Evidence: box details in the README and a diff of definitions, with no disks or credentials.

مرحله ۳ — سه ماشین رو در Vagrantfile تعریف کنCheckpoint 3 — define three machines in the Vagrantfile

برای هر node یک نام، IP خصوصی و منابع روشن تعیین کن. نمونهٔ یک ماشین؛ همین pattern رو برای دو node دیگر تکرار کن. subnet رو با آزمایشگاه واقعی هماهنگ کن. NAT پیش‌فرض Vagrant برای خروجی می‌مونه و خصوصی شبکه ارتباط میزبان/VMها رو می‌ده.

Give each node a name, private IP, and explicit resources. This example shows one machine; repeat it for the other two. Match the subnet to your lab. Vagrant's default NAT remains for outbound access, while the private network connects host and VMs.

Vagrant.configure("2") do |config|
  config.vm.define "lab-a" do |vm|
    vm.vm.box = "ubuntu/noble64"
    vm.vm.box_version = File.read(File.join(__dir__, ".box-version")).strip
    vm.vm.hostname = "lab-a"
    vm.vm.network "private_network", ip: "192.168.77.21"
    vm.vm.provider "virtualbox" do |vb|
      vb.cpus = 1
      vb.memory = 1536
    end
  end
end

وقتی سه تعریف رو نوشتی، اول vagrant validate رو اجرا کن؛ syntax رو می‌سنجد ولی وجود box یا آزادبودن IP رو تضمین نمی‌کنه. بعد vagrant status و برای شروع فقط vagrant up lab-a. اگه boot شد دو node دیگر رو بساز؛ اگه نه، خطای provider، box metadata و subnet رو جدا بررسی کن.

After writing all three definitions, run vagrant validate; it checks syntax but does not guarantee the box exists or the IP is free. Then inspect vagrant status and start with vagrant up lab-a. Add the other nodes after it boots; otherwise inspect provider errors, box metadata, and subnet separately.

در اجرای گروهی، vagrant up همهٔ ماشین‌های تعریف‌شده رو بالا می‌آورد. خروجی provider و وضعیت باید هر سه رو نشون بده؛ این هنوز شبکه یا provisioning کامل رو ثابت نمی‌کنه.

For the group, vagrant up starts every defined machine. Provider output and status should show all three; this does not yet prove networking or provisioning is complete.

راهنمای پله‌ایProgressive hint

گزینه‌های CPU و RAM در block بالا مخصوص VirtualBox هستن. برای provider دیگر block رو با تنظیم همون provider عوض کن؛ فقط نامش رو تغییر نده و سازگاری رو فرض نکن.

The CPU and RAM options shown are VirtualBox-specific. For another provider, use that provider's configuration rather than merely changing its name and assuming compatibility.

شاهد: خروجی validate، وضعیت سه VM و IP خصوصی هر کدوم.

Evidence: validate output, status of all three VMs, and each private address.

مرحله ۴ — guestها رو با provisioning آماده کنCheckpoint 4 — prepare guests with provisioning

هر guest به ابزار شبکه، SSH و نام ثابت نیاز داره. shell provisioner رو به هر node وصل کن تا hostname رو تنظیم کنه، بسته‌های پایه رو نصب و SSH رو فعال کنه. provisioner داخل guest اجرا می‌شه؛ دستورهای privileged رو فقط در VM آزمایشگاهی اجرا کن.

Each guest needs network tools, SSH, and a stable name. Attach a shell provisioner to every node to set its hostname, install baseline packages, and enable SSH. The provisioner runs inside the guest; run privileged commands only in disposable lab VMs.

برای Ubuntu box، فایل scripts/bootstrap.sh رو بساز. دور اول عمداً marker رو append می‌کنه تا اثر اجرای دوباره رو ببینی؛ هنوز راه‌حل نهایی نیست.

For the Ubuntu box, create scripts/bootstrap.sh. The first iteration deliberately appends a marker so you can observe a second run; this is not the final solution.

#!/usr/bin/env bash
set -euo pipefail
NODE="$1"
test -n "$NODE"
hostnamectl set-hostname "$NODE"
apt-get update
DEBIAN_FRONTEND=noninteractive apt-get install -y openssh-server iproute2 iputils-ping
systemctl enable --now ssh
install -d -m 0755 /etc/lab
printf 'configured: %s\n' "$NODE" >> /etc/lab/provision.log

در هر block با vm.vm.provision "shell", path: "scripts/bootstrap.sh", args: ["lab-a"], privileged: true اجرا کن؛ برای هر node آرگومان hostname خودش رو بده. یک بار vagrant provision lab-a بزن و sudo cat /etc/lab/provision.log رو بخون؛ بار دوم هم اجرا و تعداد خط‌ها رو مقایسه کن. آیا وضعیت مطلوب هست؟

Call it from each block with vm.vm.provision "shell", path: "scripts/bootstrap.sh", args: ["lab-a"], privileged: true, passing that node's hostname. Run vagrant provision lab-a, inspect sudo cat /etc/lab/provision.log, then run it again and compare line counts. Is this the desired state?

Vagrant shell provisioner و cloud-init یکی نیستن. اگه box در اولین بوت datasource cloud-init داشته باشه، ترتیب اجرای اون با provisioner رو از رفتار image بررسی کن؛ حدس نزن. در مأموریت اصلی یک منبع تنظیمات نگه دار تا دو ابزار برای یک کاربر یا بسته با هم رقابت نکنن.

Vagrant's shell provisioner and cloud-init are different. If a box has a cloud-init datasource on first boot, check that image's ordering relative to the provisioner; do not guess. Keep one configuration source in the main mission so two tools do not compete over a user or package.

برای SSH، box معمولاً یک کاربر مدیریتی و مسیر ورود مورد انتظار Vagrant داره؛ اسم و کلید رو حدس نزن. vagrant ssh-config lab-a نشون می‌ده Vagrant الان با کدوم User و IdentityFile وصل می‌شه. این خصوصی key رو از مسیر cache کپی نکن و وارد Git نکن. اگه کاربر دیگری لازم داری، فقط عمومی key رو با سازوکار مشخص provisioning به guest بده و خصوصی key رو روی میزبان نگه دار.

For SSH, a box usually provides a management user and login path expected by Vagrant; do not guess the username or key. vagrant ssh-config lab-a shows the current User and IdentityFile. Do not copy that private key from its cache or commit it. If you need another user, provision only its public key into the guest and keep the private key on the host.

راهنمای پله‌ایProgressive hint

اجرای دوم چه تغییری باید بده؟ اگه جواب «هیچ خط اضافه‌ای» هست، append کور مناسب نیست. برای cloud-init هم datasource و وضعیت رو ثابت کن؛ نصب بسته به‌تنهایی کافی نیست.

What should the second run change? If the answer is “no extra line,” blind append is wrong. For cloud-init, prove the datasource and status; package installation alone is not enough.

شاهد: خروجی provisioning اول و دوم، marker، hostname و وضعیت سرویس.

Evidence: first and second provisioning output, marker, hostname, and service state.

مرحله ۵ — شبکه و سرویس رو بعد از build ثابت کنCheckpoint 5 — verify network and services after build

بعد از vagrant up، IP خصوصی رو با ip -4 -brief address داخل guest بخون و از هر node دو peer رو ping کن. روی host، vagrant ssh lab-a -c "hostname; systemctl is-active ssh" شاهد hostname و SSH هست. سه IP باید یکتا باشن؛ خروجی سبز Vagrant به‌تنهایی این رو ثابت نمی‌کنه.

After vagrant up, inspect each private address with ip -4 -brief address inside the guest and ping both peers from each node. On the host, vagrant ssh lab-a -c "hostname; systemctl is-active ssh" verifies hostname and SSH. The three IPs must be unique; successful Vagrant output alone does not prove that.

فایل scripts/verify.sh رو روی host اجرا کن تا وضعیت VMها رو بخونه و با vagrant ssh hostname، آدرس و SSH رو از هرکدام بپرسد. اگه SSH شکست خورد، اول وضعیت VM، بعد IP/فایروال و سپس سرویس guest رو بررسی کن؛ همه رو با هم عوض نکن.

Run scripts/verify.sh on the host to inspect VM states and query hostname, address, and SSH through vagrant ssh. If SSH fails, check VM state first, then IP/firewall, then the guest service; do not change them all at once.

#!/usr/bin/env bash
set -euo pipefail
for node in lab-a lab-b lab-c; do
  echo "== $node =="
  vagrant status "$node"
  vagrant ssh "$node" -c 'hostname; ip -4 -brief address; systemctl is-active ssh'
done

این check ورود SSH مدیریت‌شدهٔ Vagrant و فعال بودن unit رو ثابت می‌کنه. برای اثبات guest-to-guest، آزمون peer رو داخل هر ماشین هم اجرا کن؛ مسیر host→guest مسیر guest→guest رو ثابت نمی‌کنه.

This check proves Vagrant-managed SSH access and an active unit. To prove guest-to-guest reachability, run the peer check inside each machine too; host-to-guest does not prove guest-to-guest.

راهنمای پله‌ایProgressive hint

اگه box نام unit دیگری داره، با systemctl list-unit-files پیدایش کن و بررسی رو با واقعیت هماهنگ کن.

If the box uses a different unit name, find it with systemctl list-unit-files and make verification match reality.

شاهد: گزارش بررسی، IP یکتا، SSH قابل‌استفاده و دسترسی هر node به دو peer.

Evidence: verification report, unique IPs, working SSH, and reachability from each node to both peers.

مرحله ۶ — بازسازی رو از حافظه مستقل کنCheckpoint 6 — remove the memory dependency

خرابی عمدی: فقط روی lab-b دستی یک بسته نصب یا یک تنظیم شبکه اضافه کرده‌ای؛ تغییر در فایل‌های پروژه نیست. پیش‌بینی کن بعد از destroy چه می‌شه. شاهد رو ثبت و مطمئن شو داده‌ای لازم داخل guest نیست. سبعد از پوشهٔ پروژه vagrant status رو بخون و فقط همین environment آزمایشگاهی رو با vagrant destroy حذف کن.

Deliberate defect: you manually installed a package or added a network setting only on lab-b; it is absent from project files. Predict what happens after destroy. Record evidence and confirm no needed guest data remains. From the project directory, inspect vagrant status and destroy only this lab environment with vagrant destroy.

بعد از تأیید prompt، وضعیت باید ماشین‌ها رو ساخته‌نشده/خاموش نشون بده ولی فایل‌های منبع بمانند. از همون directory vagrant up و همون آزمون رو تکرار کن. اگه تغییر دستی از بین رفت، ابزار خراب نشده؛ تعریف ناقص بوده.

After confirming the prompt, status should show machines as absent or powered off while source files remain. Run vagrant up from the same directory and repeat the checks. If the manual change is gone, the tool did not fail; the definition was incomplete.

حالا با شاهد تصمیم بگیر اون بسته یا تنظیم لازمه یا نه. اگه لازمه وارد bootstrap/Vagrantfile بشه؛ اگه نه، در README دلیل حذفش رو بنویس. هر دو از «یادم می‌مونه» مطمئن‌ترند.

Use evidence to decide whether that package or setting is needed. If so, encode it in bootstrap/Vagrantfile; otherwise document why it is excluded. Both are safer than “I'll remember.”

راهنمای پله‌ایProgressive hint

قبل از destroy پوشه، نام environment، وضعیت VM و آزمایشی بودن داده رو بررسی کن. این دستور VMهای همون environment رو حذف می‌کنه، نه Vagrantfile و اسکریپت رو.

Before destroy, verify directory, environment name, VM state, and disposable data. The command removes machines for that environment, not the Vagrantfile or scripts.

شاهد: وضعیت قبل/بعد، فایل‌های تعریف باقی‌مانده، تغییر دستی ازدست‌رفته و آزمون بعد از ساخت دوباره.

Evidence: status before/after, surviving definition files, lost manual change, and post-rebuild verification.

مرحله ۷ — provisioning رو idempotent کنCheckpoint 7 — make provisioning idempotent

در دور اول marker رو append کردیم. اجرای provisioning باید چندبار تکرار بشه بی‌آنکه وضعیت خراب‌تر یا فایل بلندتر بشه. به‌جای append، فایل رو به وضعیت مطلوب برسان:

The first pass appended a marker. Provisioning should be repeatable without worsening state or growing files. Instead of appending, write the desired state:

install -d -m 0755 /etc/lab
printf 'configured: %s\n' "$NODE" > /etc/lab/node

این رو در bootstrap بذار، بعد vagrant provision lab-b رو دو بار اجرا و هر بار sudo cat /etc/lab/node رو بخون. باید همون یک خط بمونه. بسته‌ها نصب و SSH فعال باشه. اگه اجرا شکست خورد، خروجی provisioner و systemctl status ssh رو ببین.

Put this in bootstrap, run vagrant provision lab-b twice, and inspect sudo cat /etc/lab/node each time. It should remain one line. Packages should be installed and SSH enabled. If execution fails, inspect provisioner output and systemctl status ssh.

cloud-init هم moduleها رو بر اساس frequency و instance identity اجرا می‌کنه؛ «یک بار» رو با «هر boot» یکی نگیر. در قابلیت مبتنی بر NoCloud، کاربر-data/meta-data، datasource و رفتار اجرای دوباره رو جدا بررسی کن. در مأموریت حاضر shell provisioner منبع واحد تنظیمات هست.

cloud-init modules also follow frequency and instance identity; “once” is not the same as “every boot.” In a NoCloud extension, verify user-data/meta-data, datasource, and rerun behavior separately. In this mission, the shell provisioner is the single configuration source.

راهنمای پله‌ایProgressive hint

سبز بودن exit وضعیت کافی نیست. فایل، تعداد خط‌ها، hostname و سرویس باید بعد از اجرای دوم همچنان درست باشن.

Reconfirm the directory and vagrant status, then knowingly approve vagrant destroy. Next, vagrant up should build all three VMs from the versioned box and run provisioning.

موفقیت روی لپ‌تاپ فقط همین provider و نسخه‌ها رو تأیید می‌کنه؛ سازگاری با hypervisor دیگر یا شبکهٔ واقعی رو ثابت نمی‌کنه. این مرز رو در README بنویس.

Success on this laptop validates only these provider and box versions; it does not prove compatibility with another hypervisor or a real network. Document that boundary.

Finally review git status --short and the diff: include the Vagrantfile, version, scripts, and README; keep VM disks, caches, private keys, passwords, and cloud credentials outside the repository. Never put a real secret in an image or Git.

Runbook مرجع — بازسازی کاملReference runbook — complete rebuild

این یک مسیر برای Vagrant، VirtualBox و Ubuntu box هست؛ نسخهٔ دقیق box رو از فهرست معتبر بردار و ثبت کن. گزینه‌های provider دیگر الزاماً همین رفتار رو ندارن.

This path targets Vagrant, VirtualBox, and an Ubuntu box; select and record the exact version from its authoritative catalog. Other providers may behave differently.

  1. پوشهٔ تازه و Vagrantfile، .box-version، scripts/bootstrap.sh، scripts/بررسی.sh و README بساز.
  2. Create a fresh directory with Vagrantfile, .box-version, scripts/bootstrap.sh, scripts/verify.sh, and README.
  3. سه block ماشین با box و version یکسان، hostnameهای lab-a/b/c، IP خصوصی یکتا و منابع VirtualBox تعریف کن؛ اول vagrant validate.
  4. Define three machine blocks with the same box/version, hostnames lab-a/b/c, unique private IPs, and VirtualBox resources; run vagrant validate first.
  5. shell provisioner رو وصل کن: بسته‌های لازم، hostname، SSH و فایل وضعیت idempotent؛ اطلاعات محرمانه در فایل نباشه.
  6. Attach the shell provisioner for packages, hostname, SSH, and idempotent state; keep secrets out of files.
  7. vagrant up و بررسی از host؛ آزمون peer از هر guest. خطای provider، شبکه، provisioning و سرویس رو جدا کن.
  8. Run vagrant up and host verification, then peer checks from each guest. Separate provider, network, provisioning, and service errors.
  9. vagrant provision lab-b رو دوبار اجرا کن و نبود وضعیت تکراری رو ثابت کن؛ append آزمایشی رو اصلاح کن.
  10. Run vagrant provision lab-b twice and prove no duplicate state; repair the deliberate append.
  11. بعد از تأیید environment و آزمایشی بودن داده، vagrant destroy و vagrant up؛ همون بررسی اسکریپت رو بدون تغییر پاس کن.
  12. After confirming the environment and disposable data, run vagrant destroy and vagrant up; pass the unchanged verification script.
  13. versionها، نیازمندی‌ها، خطاهای شناخته‌شده و مرز provider/cloud-init رو در README ثبت کن؛ credential و دیسک رو از Git بیرون نگه دار.
  14. Document versions, prerequisites, known errors, and the provider/cloud-init boundary; keep credentials and disks out of Git.
فایل‌های مرجع کاملComplete reference files

این Vagrantfile هر سه node رو با یک box نسخه‌دار می‌سازه. مقدار .box-version باید نسخهٔ واقعی انتخاب‌شده از فهرست باشه؛ placeholder رو عیناً اجرا نکن.

This Vagrantfile creates all three nodes from one versioned box. The .box-version value must be the real release selected from the catalog; do not run a placeholder literally.

Vagrant.configure("2") do |config|
  box_version = File.read(File.join(__dir__, ".box-version")).strip
  nodes = {
    "lab-a" => "192.168.77.21",
    "lab-b" => "192.168.77.22",
    "lab-c" => "192.168.77.23"
  }

  nodes.each do |name, address|
    config.vm.define name do |vm|
      vm.vm.box = "ubuntu/noble64"
      vm.vm.box_version = box_version
      vm.vm.hostname = name
      vm.vm.network "private_network", ip: address
      vm.vm.provider "virtualbox" do |vb|
        vb.cpus = 1
        vb.memory = 1536
      end
      vm.vm.provision "shell",
        path: "scripts/bootstrap.sh",
        args: [name],
        privileged: true
    end
  end
end

scripts/bootstrap.sh در نسخهٔ نهایی باید marker رو به‌جای append بازنویسی کنه و mapping سه peer رو فقط وقتی اضافه کنه که وجود نداره؛ بعد بسته و SSH رو آماده کنه.

In the final version, scripts/bootstrap.sh should overwrite its marker instead of appending and add each peer mapping only if absent, then prepare packages and SSH.

#!/usr/bin/env bash
set -euo pipefail
NODE="$1"
test -n "$NODE"
hostnamectl set-hostname "$NODE"
export DEBIAN_FRONTEND=noninteractive
apt-get update
apt-get install -y openssh-server iproute2 iputils-ping
systemctl enable --now ssh
install -d -m 0755 /etc/lab
printf 'configured: %s\n' "$NODE" > /etc/lab/node
for entry in \
  "192.168.77.21 lab-a" \
  "192.168.77.22 lab-b" \
  "192.168.77.23 lab-c"; do
  grep -qxF "$entry" /etc/hosts || printf '%s\n' "$entry" >> /etc/hosts
done

فایل scripts/verify.sh روی host اجرا می‌شه. خروجی اون وضعیت و وضعیت guest رو می‌سنجد؛ peer check جدا داخل هر VM اجرا می‌شه تا مسیر بین nodeها هم واقعاً آزمایش بشه.

Run scripts/verify.sh on the host. It checks VM and guest state; run the peer check inside each VM separately to exercise node-to-node traffic too.

#!/usr/bin/env bash
set -euo pipefail
for node in lab-a lab-b lab-c; do
  echo "== $node =="
  vagrant status "$node"
  vagrant ssh "$node" -c 'hostname; ip -4 -brief address; systemctl is-active ssh'
  vagrant ssh "$node" -c 'for peer in lab-a lab-b lab-c; do [ "$peer" = "$(hostname)" ] && continue; ping -c 2 -W 2 "$peer"; done'
done

یادداشت مهندسی: تعریف نسخه‌دار فقط وقتی ارزش داره که بعد از حذف ماشین هم کار کنه. بازسازی کامل نشون می‌ده کدوم تنظیم کد شده و کدوم به حافظه، cache یا دست‌کاری دستی وابسته بوده.

Engineering note: a versioned definition matters only if it still works after the machines are gone. A full rebuild reveals which settings were encoded and which depended on memory, cache, or manual edits.
