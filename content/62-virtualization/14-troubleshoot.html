عیب‌یابی

Troubleshooting

VM بالا نمیاد؟ شبکه نداره؟ کند شده؟ این فصل قرار نیست با پاک‌کردن و ساختن دوباره مسئله رو قایم کنیم؛ از پایین‌ترین لایه شروع می‌کنیم و با شاهد جلو می‌ریم.

The VM booted yesterday. Today the screen is black, the guest has no network, or every click takes seconds. Do not call it “a broken VM” and do not delete it yet. First locate the layer that failed.

صفحه سیاه هست؛ ولی کدوم سیستم پاسخ نمی‌ده؟The screen is black—but which system stopped responding?

پنجرهٔ VM باز هست، ولی چیزی نمی‌بینی. شاید guest خاموش هست، شاید از ISO اشتباه boot می‌کنه، شاید console تصویر نمی‌فرسته یا خود host زیر فشار حافظه گیر کرده. هرکدام تعمیر متفاوتی داره. اگه همین حالا snapshot رو برگردانی، ممکنه شاهد رو پاک کنی و وضعیت مهمی رو از دست بدی.

The VM window is open, but nothing appears. Perhaps the guest is off, booting the wrong ISO, producing no console output, or the host is stalled under memory pressure. Each needs a different repair. Reverting a snapshot immediately could erase evidence or useful state.

قاعدهٔ این تعمیرگاه: نشانه رو ثبت کن؛ وضعیت رو از hypervisor بگیر؛ console و لاگ رو بخون؛ بعد مجازی سخت‌افزار، guest، شبکه، منابع و storage رو به‌ترتیب بررسی کن. هر بار یک فرضیه رو تغییر بده و همون آزمونی رو که اول شکست خورد تکرار کن. نصب دوباره آخرین انتخاب هست، نه اولین واکنش.

Our repair-bay rule: record the symptom; inspect hypervisor state; read console and logs; then check virtual hardware, guest, network, resources, and storage in order. Change one hypothesis at a time and repeat the test that failed first. Reinstallation is a last resort, not the first reaction.

از پایین‌ترین لایه شروع کنStart at the lowest failing layer

اگه hypervisor می‌گه VM paused یا خراب، ابتدا task/خطا همون میزبان رو بخون؛ هنوز سراغ DNS مهمان نرو. اگه VM running هست ولی console در boot گیر کرده، media/firmware/دیسک رو بررسی کن. اگه login داری ولی SSH نیست، از شبکهٔ مهمان به‌بعد پایین بیا. وضعیت «running» فقط وضعیت hypervisor هست، نه سلامت سیستم‌عامل.

If the hypervisor says paused or failed, read its task/error first; guest DNS is not yet relevant. If it is running but console stalls during boot, inspect media, firmware, and disk. If you can log in but SSH fails, continue from guest networking. “Running” is a hypervisor state, not an OS health check.

خرابی اول: دوباره نصاب میادFault one: the installer keeps returning

بعد از نصب، VM دوباره از ISO بالا آمده. این به‌تنهایی نمی‌گه نصب روی دیسک شکست خورده. قبل از تغییر، وضعیت ماشین و media متصل رو ببین: آیا optical drive هنوز ISO داره؟ آیا دیسک مجازی attach هست؟ ترتیب بوت کدوم رو جلوتر گذاشته؟

After installation, the VM booted from the ISO again. That alone does not mean the disk installation failed. Before changing anything, inspect attached media: is the ISO still in the optical drive? Is the virtual disk attached? Which device comes first in boot order?

در VirtualBox از Settings → Storage و System → Boot Order بخون؛ روی libvirt، virsh dumpxml vm-lab رو فقط برای مشاهدهٔ دیسک/CDROM و ترتیب بوت استفاده کن؛ در Proxmox، سخت‌افزار و Options همون VM رو ببین. عنوان‌ها با نسخه فرق دارن. قبل از eject مطمئن شو نصاب هنوز در حال نصب نیست؛ بعد ISO رو جدا و از دیسک boot کن.

In VirtualBox inspect Settings → Storage and System → Boot Order; with libvirt, use virsh dumpxml vm-lab to inspect disk/CD-ROM and boot order; in Proxmox inspect that VM’s Hardware and Options. Labels vary by version. Confirm installation is finished before ejecting, then detach the ISO and boot from disk.

اگه حالا guest بالا آمد و /etc/os-release و findmnt / سیستم نصب‌شده رو نشان دادند، فرضیهٔ ترتیب بوت/media تأیید شد. اگه هنوز bootable دستگاه نیست، دیسک attachment، firmware حالت و EFI/BIOS boot فایل‌ها رو بررسی کن. دیسک مجازی رو delete یا initialize نکن؛ اون کار شاهد و داده رو نابود می‌کنه.

If the guest now boots and /etc/os-release plus findmnt / show the installed system, the media/order hypothesis is supported. If there is still no bootable device, inspect disk attachment, firmware mode, and EFI/BIOS boot files. Do not delete or initialize the virtual disk; that destroys evidence and data.

لاگ میزبان با لاگ مهمان فرق دارهHost logs and guest logs answer different questions

وقتی VM اصلاً start نمی‌شه، لاگ مهمان شاید هنوز وجود نداشته باشه. VirtualBox در پوشهٔ VM، زیر Logs/VBox.log رویدادها و تنظیمات اجرای hypervisor رو نگه می‌داره. libvirt/QEMU task و daemon لاگ رو روی host ثبت می‌کنه. Proxmox در Tasks همون node/VM نتیجه و لاگ هر عملیات رو داره. اول لاگ نزدیک همون زمان خرابی رو بخون؛ کل فایل رو بی‌هدف نریز.

If a VM never starts, guest logs may not exist yet. VirtualBox records hypervisor events and configuration in Logs/VBox.log under the VM folder. libvirt/QEMU records host-side task and daemon logs. Proxmox exposes each operation’s result and log under node/VM Tasks. Start with the log nearest the failure, not a blind dump of everything.

journalctl -b --no-pager | grep -Ei 'libvirt|qemu|kvm'
virsh domstate vm-lab --reason
qm status 101

واحدهای systemd و فرمان‌ها به distro و نسخه وابسته‌اند؛ برخی libvirtها daemonهای جدا مثل virtqemud دارن و برخی هنوز libvirtd. اگه لاگ پیدا نشد، systemctl list-units '*virt*' و اتصال URI رو بررسی کن. virsh domstate و qm status فقط وضعیت/domain رو می‌گن، نه علت نهایی یا boot سلامت guest.

Systemd units and commands vary by distro/version; some libvirt installations use split daemons such as virtqemud, while others still use libvirtd. If no log appears, inspect systemctl list-units '*virt*' and the connection URI. virsh domstate and qm status report state, not the final cause or guest boot health.

روی Proxmox، task خراب رو باز کن و متن عملیات رو بخون؛ «start خراب» هنوز تشخیص نیست. روی VirtualBox، آخرین بخش VBox.log و خطاهای Host/VT-x/AMD-V رو ببین. لاگها ممکنه مسیر، نام VM یا اطلاعات حساس داشته باشن؛ قبل از اشتراک‌گذاری redact کن.

On Proxmox open the failed task and read the operation details; “start failed” is not a diagnosis. In VirtualBox inspect the end of VBox.log and host/VT-x/AMD-V errors. Logs may contain paths, VM names, or sensitive details; redact before sharing.

خرابی دوم: VM بالا هست ولی شبکه ندارهFault two: the VM runs but has no network

از ping به Google شروع نکن؛ اول معلوم کن کدوم قسمت از مسیر کار می‌کنه. داخل Linux guest این‌ها فقط‌خواندنیاند:

Do not begin by pinging Google; first identify which part of the path works. These Linux guest checks are read-only:

ip -br link
ip -br address
ip route
getent hosts example.com
ss -ltn

ip -br link link رو نشون می‌ده؛ address و پیش‌فرض route مرحله‌های بعدند؛ getent نام رو از resolver سیستم می‌پرسه؛ ss فقط listener محلی رو می‌بینه. نبود IP به DHCP/adapter اشاره می‌کنه؛ IP بدون route به gateway؛ IP و route با شکست resolve به DNS؛ و resolve موفق با پورت بسته به سرویس/فایروال. هر خروجی فقط همون لایه رو محدود می‌کنه.

ip -br link shows link; address and default route follow; getent asks the system resolver; ss shows local listeners only. No IP points toward DHCP/adapter; IP without route toward gateway; address/route with failed resolution toward DNS; successful resolution but closed port toward service/firewall. Each result narrows only its own layer.

حالا hypervisor رو تطبیق بده: در VirtualBox، Cable وصل و NAT/Bridged/Host-only؛ در libvirt، virsh domiflist vm-lab و شبکه مورد اتصال؛ در Proxmox، bridge NIC مثل vmbr0 و IP/DHCP شبکه. «کارت متصل هست» تضمین نمی‌کنه uplink یا DHCP کار می‌کنه. bridge مدیریتی host رو برای آزمایش تغییر نده.

Now compare hypervisor settings: VirtualBox Cable Connected and NAT/Bridged/Host-only; libvirt virsh domiflist vm-lab and its network; Proxmox NIC bridge such as vmbr0 and the network’s DHCP/IP policy. “NIC connected” does not guarantee uplink or DHCP. Do not alter the host management bridge for an experiment.

آزمون layerبه‌layer: gateway شناخته‌شده رو ping کن اگه ICMP مجاز هست؛ سپس با یک IP سرویس مجاز و در آخر hostname رو امتحان کن. اگه ICMP بسته باشه، شکست ping الزاماً قطع شبکه نیست؛ TCP request مناسب‌تر هست. برای تعمیر عمدی این lab، فقط NIC VM آزمایشی رو موقتاً disconnected یا به شبکهٔ ایزولهٔ اشتباه وصل کن، شواهد رو بگیر و همون NIC رو برگردان.

Test layer by layer: ping a known gateway if ICMP is allowed, then test an approved service IP, then a hostname. If ICMP is blocked, failed ping does not necessarily mean broken networking; a TCP request is more useful. For the lab fault, disconnect only a disposable VM’s NIC or attach it to the wrong isolated network, collect evidence, then restore that NIC.

خرابی سوم: KVM acceleration یا مجوزFault three: KVM acceleration or permissions

روی Linux host، libvirt می‌گه KVM unavailable یا شروع VM خیلی کند هست. قبل از chmod یا اجرای همه‌چیز با root، CPU virtualization و دستگاه رو بررسی کن:

On a Linux host, libvirt reports KVM unavailable or the VM is unusually slow. Before chmod or running everything as root, inspect CPU virtualization and device access:

grep -E -m1 'vmx|svm' /proc/cpuinfo
ls -l /dev/kvm
id
lsmod | grep -E '^kvm'

پرچم vmx/svm پشتیبانی CPU رو نشون می‌ده؛ /dev/kvm و groupها دسترسی کاربر رو. نبود پرچم ممکنه firmware virtualization خاموش یا VM بالادستی بدون nested virtualization باشه. وجود پرچم و دستگاه به‌تنهایی ثابت نمی‌کنه hypervisor فعلی اجازهٔ استفاده می‌ده؛ task لاگ و nested settings رو هم بخون.

The vmx/svm flag indicates CPU capability; /dev/kvm ownership and groups indicate user access. A missing flag may mean firmware virtualization is disabled or an outer VM does not expose nested virtualization. Flags and device alone do not prove the active hypervisor permits use; inspect task logs and nested settings too.

اگه کاربر عضو گروه لازم نیست، سیاست همون distro/libvirt رو بخون و با روش supported دسترسی بده؛ chmod 666 /dev/kvm راه‌حل دائمی یا امن نیست. اضافه‌کردن group ممکنه نیاز به login مجدد داشته باشه. روی VM تو در تو، میزبان بیرونی هم باید capability رو در اختیار guest بذاره؛ داخل مهمان دستکاری kernel module ممکنه اصلاً ممکن نباشه.

If the user lacks the required group, follow that distro/libvirt’s supported permission procedure; chmod 666 /dev/kvm is not a safe permanent fix. Group changes may require a new login. In nested virtualization, the outer host must expose the capability; changing modules inside the guest may not be possible.

خرابی چهارم: VM کند شده و دیسک جا ندارهFault four: the VM is slow and storage is tight

کندی رو به «CPU کم هست» تقلیل نده. داخل guest، uptime و free -h فشار همون سیستم رو نشون می‌دن؛ روی host مصرف واقعی RAM/CPU و swap رو در ابزار hypervisor/OS میزبان ببین. guest می‌تونه حافظهٔ آزاد نشون بده درحالی‌که host زیر فشار هست یا storage در حال swap شدید هست.

Do not reduce slowness to “not enough CPU.” In the guest, uptime and free -h show pressure there; inspect actual host RAM/CPU and swapping in host/hypervisor tools. A guest may report free memory while the host is pressured or storage is thrashing.

uptime
free -h
df -hT
df -i
lsblk -f

df -hT block usage رو می‌سنجد و df -i inode؛ دیسک مجازی بزرگ‌تر از فایل host هم می‌تونه thin باشه و با نوشتن guest رشد کنه. Storage pool hypervisor رو جدا بررسی کن. snapshotهای زیاد/زنجیره‌ای ممکنه فضای host رو بگیرن و I/O رو کند کنند؛ snapshot رو تصادفی delete نکن، چون merge و storage رفتار وابسته به محصول هست.

df -hT checks block use and df -i inode use. A virtual disk can be thin: guest writes make its host file grow. Inspect hypervisor storage separately. Many/long snapshot chains can consume host space and slow I/O; do not delete snapshots randomly because merge behavior depends on the product.

برای VirtualBox، پوشهٔ VM و Logs/Snapshots رو ببین؛ libvirt، virsh pool-list --all و pool مسیر/space؛ Proxmox، storage وضعیت و taskها. لاگ مهمان رو هم برای OOM، دیسک خطاها یا سرویس timeout بخون. به دیسک host پر، با پاک‌کردن snapshot یا فایل ناشناس واکنش نده؛ اول مشخص کن کدوم داده لازمه.

For VirtualBox inspect VM, Logs, and Snapshots folders; for libvirt use virsh pool-list --all and check pool path/space; for Proxmox inspect storage status and tasks. Guest logs may reveal OOM, disk errors, or service timeouts. Do not respond to a full host disk by deleting snapshots or unknown files; identify needed data first.

زمان guest می‌پرد؟ ابزار مهمان رو قبل از reinstall بررسی کنGuest time drifts? Check guest tools before reinstalling

زمان غلط، TLS و لاگها رو عجیب می‌کنه. در Linux guest timedatectl status، timezone و sync رو نشون می‌ده؛ سپس ساعت host، pause/suspend طولانی و time-sync یکپارچه‌سازی ابزار hypervisor رو بررسی کن. درست بودن timezone به‌تنهایی ساعت درست رو ثابت نمی‌کنه.

Incorrect time makes TLS and logs confusing. In a Linux guest, timedatectl status reports timezone and synchronization; then inspect host clock, long pause/suspend, and hypervisor time-sync integration. A correct timezone alone does not prove the clock is correct.

اگه مشکل فقط auto-resize، clipboard یا time sync هست، Guest Additions/Guest Tools ممکنه نصب‌نشده، قدیمی یا ناسازگار با kernel مهمان باشه. نسخهٔ host و guest tools رو مقایسه و لاگ سرویس مهمان رو ببین. این ابزارها علت boot خرابی یا شبکه DHCP رو خودکار حل نمی‌کنن.

If only auto-resize, clipboard, or time sync fails, Guest Additions/Guest Tools may be missing, outdated, or incompatible with the guest kernel. Compare host and guest-tool versions and inspect the guest service log. These tools do not automatically fix boot failures or DHCP.

کی snapshot، clone یا backup به کار میاد؟When should you use a snapshot, clone, or backup?

اگه یک تغییر تازه و معلوم علت مشکل هست و snapshot سالمِ قبل از اون داری، rollback می‌تونه آزمایش خوبی باشه؛ قبل از اون دادهٔ جدید و وابستگی snapshot chain رو بررسی کن. clone برای ساخت نسخهٔ جدا جهت آزمایش مناسب هست، ولی ممکنه IP/hostname تکراری داشته باشه. backup برای بازسازی در storage/host دیگر هست و باید restore test شده باشه. هیچ‌کدوم جای لاگ و علت‌یابی رو برای مسئلهٔ تکرارشونده نمی‌گیرن.

If a known recent change caused the issue and you have a good pre-change snapshot, rollback may be a useful test; first consider newer data and snapshot-chain dependencies. A clone gives an isolated copy for experiments but may duplicate IP/hostname. A backup supports recovery on another host/storage and should be restore-tested. None replaces diagnosis of a recurring fault.

اگه تعمیر ساده‌تر از restore هست، تعمیر کن و همون آزمون اولیه رو تکرار کن. اگه restore لازم شد، روی ID/destination تازه برگردان، NIC رو قبل از اتصال بررسی کن و فایل یا سرویس موردنیاز رو بخون. «VM بالا آمد» کافی نیست؛ acceptance test برنامه رو هم دوباره اجرا کن.

If repair is safer than restore, repair and rerun the original test. If restoration is needed, use a new ID/destination, inspect its NIC before connecting it, and verify the required file/service. “The VM booted” is not enough; rerun the application acceptance test.

آزمایشگاه تعمیرگاه: چهار خرابی، چهار بار اثباتRepair-bay lab: four faults, four proofs

روی یک VM آزمایشی و ترجیحاً snapshotشده کار کن؛ شبکهٔ مدیریت host، فایل‌های اصلی یا VM کاری رو دستکاری نکن. قبل از هر تغییر، symptom، وضعیت و لاگ مربوط رو ثبت کن. اگه محیط/نسخه‌ات گزینه‌ای نداره، تفاوت رو یادداشت کن و همون لایه رو با شاهد معادل بررسی کن.

Use a disposable, preferably snapshotted VM. Do not alter host management networking, real files, or a work VM. Before each change, record symptom, state, and relevant log. If your version lacks an option, document the difference and inspect the equivalent layer.

  1. Boot خرابی: ISO رو دوباره وصل یا دیسک رو بعد از DVD قرار بده. ابتدا تصویر/تنظیمات رو ثبت کن، سبعد از VM خودت در UI یا CLI media و ترتیب بوت رو بخون. بعد از eject/اصلاح، guest باید از دیسک boot بشه؛ findmnt / و نسخه رو بررسی کن.
  2. Boot fault: reattach the ISO or move disk after DVD. Record settings, inspect media/order, then eject/fix and boot from disk; verify release and findmnt /.
  3. Network خرابی: فقط NIC مهمان رو disconnect کن یا به isolated شبکه دیگری ببر. نبود address/link رو داخل guest و attach رو در hypervisor ببین؛ NIC رو به شبکهٔ lab قبلی برگردان و address/route/سرویس رو تکرار کن.
  4. Network fault: disconnect only the guest NIC or move it to another isolated network. Observe link/address in guest and attachment in hypervisor; restore it and retest address/route/service.
  5. KVM خرابی: اگه Linux host آزمایشگاهی در دسترس هست، دسترسی کاربر مجاز به /dev/kvm رو در VM آزمایشی تغییر بده یا capability nested رو پنهان کن. خطای task، دستگاه و groups رو ثبت؛ سیاست درست رو برگردان و start acceleration رو بررسی کن. روی host روزمره chmod یا module unload اجرا نکن.
  6. KVM fault: on a lab Linux host, alter permitted user access to /dev/kvm in a disposable setup or hide nested capability. Record task error, device, and groups; restore supported permissions and verify accelerated start. Do not chmod or unload modules on a daily-use host.
  7. Resource/storage خرابی: فقط روی guest آزمایشی، از ابزار درون guest یک پارتیشن کوچکِ آزمایشی پرشده رو بررسی کن یا RAM تخصیص‌داده‌شده رو محدود کن؛ هرگز دیسک واقعی host رو پر نکن. df -hT/free -h داخل guest رو با storage/monitor میزبان مقایسه و علت رو ثبت کن. برای پرکردن عمداً دیسک VM اگه مطمئن نیستی انجام نده؛ مشاهدهٔ وضعیت کم‌فضا کافیه.
  8. Resource/storage fault: in a disposable guest, inspect an intentionally small test filesystem or reduce its assigned RAM; never fill the host disk. Compare guest df -hT/free -h with host storage/monitoring. If you cannot safely induce a full VM disk, observing a low-space state is enough.

گزارش تعمیر: برای هر مورد symptom، وضعیت، شاهد، فرضیه، یک تعمیر و همون بررسی اولیه رو بنویس. «دوباره ساختم و درست شد» بدون توضیح اینکه چه شاهدی علت رو تأیید کرد، گزارش کامل نیست.

Repair report: For each case record symptom, state, evidence, hypothesis, one repair, and the original verification. “I rebuilt it and it works” is incomplete without evidence for the cause.

کدوم شاهد رو اول باز می‌کنی؟

Which evidence do you open first?

پاسخ

Task لاگ همون start و وضعیت/سخت‌افزار همون VM؛ عبارت کلی خراب علت مشخص نیست.

The start task log and that VM’s state/hardware; a generic failure label is not a cause.

۶. IP نیست

اول guest رو reinstall می‌کنی؟

Do you reinstall first?

پاسخ

نه؛ link، NIC attachment، DHCP و حالت شبکه رو از guest و hypervisor بخون.

No. Inspect link, NIC attachment, DHCP, and network mode from both guest and hypervisor.

۷. IP هست، route نیست

DNS اولین مظنون هست؟

Is DNS the first suspect?

پاسخ

نه؛ پیش‌فرض route/gateway رو بررسی کن. DNS بعد از مسیر IP میاد.

No. Check default route/gateway first; DNS comes after IP routing.

۸. hostname resolve نمی‌شه

IP مستقیم جواب می‌ده؛ کدوم لایه رو می‌سنجی؟

The IP responds directly. Which layer do you test?

پاسخ

resolver/DNS با getent hosts؛ ping IP، name resolution رو ثابت نمی‌کنه.

Resolver/DNS with getent hosts; pinging an IP does not prove name resolution.

۹. ping شکست خورد

آیا حتماً شبکه قطع هست؟

Is the network necessarily down?

پاسخ

نه؛ ممکنه ICMP بسته باشه. TCP روی سرویس مجاز و route رو جدا امتحان کن.

No; ICMP may be blocked. Test an allowed TCP service and route separately.

۱۰. KVM unavailable

چرا chmod 666 /dev/kvm تعمیر مناسبی نیست؟

Why is chmod 666 /dev/kvm a poor repair?

پاسخ

دسترسی دستگاه رو بیش از حد باز می‌کنه و ممکنه پایدار هم نماند؛ capability و group سیاست supported رو پیدا کن.

It overexposes the device and may not persist; use the supported capability/group policy.

۱۱. host مهمان nested

KVM داخل VM در دسترس نیست؛ کدوم دو سطح رو بررسی می‌کنی؟

KVM is missing inside a VM. Which two layers do you inspect?

پاسخ

host فیزیکی و تنظیمات hypervisor بالادستی برای در دسترس بذارهکردن nested virtualization؛ بعد guest/دستگاه.

Physical host and outer hypervisor’s nested-virtualization exposure, then the guest/device.

۱۲. کندی بدون CPU زیاد

کدوم شواهد رو کنار هم می‌ذاری؟

Which evidence do you combine?

پاسخ

guest load/free، host CPU/RAM/swap، دیسک I/O و وضعیت storage/snapshot؛ یک counter علت رو ثابت نمی‌کنه.

Guest load/memory, host CPU/RAM/swap, disk I/O, and storage/snapshots; no single counter proves cause.

۱۳. df می‌گه full

چه تفاوتی بین df -hT و df -i هست؟

How do df -hT and df -i differ?

پاسخ

اولی blockها، دومی inodeها؛ هر دو رو برای کمبود فضای مهمان بخون و pool میزبان رو جدا بسنج.

The first reports blocks, the second inodes; inspect both in the guest and check host pool separately.

۱۴. snapshot زیاد

چرا حذف تصادفی snapshot خطر داره؟

Why is random snapshot deletion risky?

پاسخ

chain/merge و storage رفتار محصول‌محور هست و ممکنه داده یا فضای بیشتری درگیر بشه؛ ابتدا وضعیت و backup رو بررسی کن.

Chain/merge and storage behavior is product-specific and may affect data/space; inspect state and backup first.

۱۵. ساعت اشتباه

timezone درست هست ولی TLS خراب می‌شه. چه می‌سنجی؟

Timezone is right but TLS fails. What do you inspect?

پاسخ

timedatectl، ساعت واقعی host، time sync guest tools و ساعت گواهی؛ timezone به‌تنهایی زمان رو تصحیح نمی‌کنه.

Check timedatectl, host clock, guest time sync, and certificate time; timezone alone does not fix the clock.

۱۶. auto-resize خرابه

guest بالا هست و شبکه داره. چه ابزار رو بررسی می‌کنی؟

The guest boots and networks. Which tools do you inspect?

پاسخ

Guest Additions/Tools، نسخه و سرویس/لاگ اون؛ این مشکل رو از boot خرابی جدا نگه دار.

Guest Additions/Tools, version, and service/log; keep this separate from boot failure.

۱۷. rollback یا تعمیر؟

تغییر معلوم علت شده و snapshot قبلش داری؛ چی رو قبل از rollback می‌سنجی؟

A known change caused the issue and you have a prior snapshot. What before rollback?

پاسخ

دادهٔ تازه، chain/dependency و امکان backup؛ سپس rollback آزمایشی و اجرای همون acceptance test.

Recent data, chain/dependency, and backup; then rollback as a test and rerun acceptance checks.

۱۸. گزارش تعمیر

یک VM کند هست: guest حافظه آزاد کم، host swap زیاد، دیسک 100% و snapshotهای زیادی داره. تشخیص و اولین کار؟

A VM is slow: low guest free memory, high host swap, disk at 100%, many snapshots. Diagnosis and first move?

معیار پاسخ

هم فشار RAM میزبان و هم storage پر محتمل‌اند؛ task و snapshot chain/data رو ثبت، pool و df/inode رو جدا بررسی و داده/backup رو مشخص کن. حذف snapshot تصادفی یا افزایش RAM قبل از حل storage، شواهد و مشکل رو ممکنه بدتر کند.

Host memory pressure and full storage are both plausible. Record tasks/snapshot chain, inspect pool and guest block/inode use, and identify data/backups. Random snapshot deletion or adding RAM before addressing storage may worsen the problem.

همون آزمون اول، آخر کار هم اجرا می‌شهRepeat the original test at the end

اگه VM دوباره boot شد، فقط تعمیر boot رو ثابت کرده‌ای؛ اگه ping آمد، فقط همون مسیر ICMP رو. آزمون اولیه رو دقیق تکرار کن: سرویس، hostname، دسترسی، زمان یا بار کاریای که کاربر واقعاً از دست داده بود. سپس host و guest logs رو با زمان تعمیر نگه دار تا اگه مشکل برگشت، نقطهٔ شروع تازه داشته باشی.

If the VM boots again, you proved only the boot repair; if ping returns, only that ICMP path. Repeat the original test exactly: the service, hostname, access, time, or workload the user actually lost. Keep host and guest logs with the repair time so a recurrence has a useful starting point.

آخر تعمیر همون آزمایشی رو اجرا کن که اول خراب بود. boot شدن، ping شدن یا سبز شدن یک log به‌تنهایی کافی نیست. فصل بعد دیگه سناریوی آماده نداریم؛ خودت باید اولین VM قابل‌تحویل رو از صفر بسازی.

If you restored, verify data under a new ID and inspect networking before connecting it. If the cause is still uncertain, state that in the handoff; rebuilding may only hide the problem temporarily. For version-specific behavior, consult VirtualBox troubleshooting, libvirt debug logs, and the Proxmox documentation alongside local evidence.
