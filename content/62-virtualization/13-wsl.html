WSL2 و مک

WSL2 and macOS

WSL2 و Docker Desktop حس می‌دن Linux همین‌جاست؛ ولی چند مرز مهم هنوز وسطه. مسیر فایل، شبکه و معماری CPU رو دنبال می‌کنیم تا بفهمیم چرا «روی سیستم من کار می‌کنه» همیشه کافی نیست.

You run Linux on Windows with WSL2; on a Mac, Docker Desktop also provides a Linux environment. Both are useful, but “it is just native Linux” overstates the case. Learn the boundaries so you know which differences matter.

روی لپ‌تاپ اجرا می‌شه؛ چرا روی سرور فرق داره؟It runs on the laptop. Why is the server different?

اسکریپت Linux روی WSL کار می‌کنه. پروژه رو در /mnt/c گذاشته‌ای، کانتینرها رو با Docker Desktop بالا آورده‌ای و API روی localhost جواب می‌ده. هم‌تیمی روی Windows دیگر می‌گه فایل watcher کند هست؛ روی Mac هم image بالا نمیاد چون معماری فرق داره. آیا پروژه خراب هست؟ شاید محیط‌ها رو یکی فرض کردیم.

A Linux script works in WSL. Your project lives under /mnt/c, containers run through Docker Desktop, and the API answers on localhost. A Windows teammate reports slow file watching; a Mac teammate cannot start an image because the architecture differs. Is the project broken—or did we assume the environments were identical?

WSL2 یک Linux kernel واقعی رو در VM سبکِ مدیریت‌شده اجرا می‌کنه؛ توزیع Linux ابزارها و فایل‌های فضای کاربر رو می‌ده. Docker Desktop هم daemon و کانتینرهای Linux رو در محیط VM خودش اجرا می‌کنه. روی macOS هم کانتینر Linux مستقیماً از kernel Darwin استفاده نمی‌کنه. «یک ترمینال Linux دارم» دربارهٔ kernel، فایل‌سیستم، شبکه و معماری همه‌چیز رو نمی‌گه.

WSL2 runs a real Linux kernel in a managed lightweight VM; the Linux distribution supplies user-space tools and files. Docker Desktop runs its daemon and Linux containers in its own VM environment. On macOS, Linux containers do not use the Darwin kernel directly. Having a Linux-looking terminal tells us little about kernel, filesystem, network, and architecture boundaries.

دو میزبان، دو مرز مهمانTwo hosts, two guest boundaries

این شکل معماری رو خلاصه می‌کنه؛ جزئیات شبکه و sharing با نسخه، تنظیم و ابزار عوض می‌شه. WSL2 توزیع رو بدون مدیریت دستی یک VM معمولی بالا می‌آورد. Docker Desktop روی Mac یک Linux VM مدیریت می‌کنه؛ UTM می‌تونه VM Linux کامل بسازد. در هر مسیر، guest و host دو سیستم‌عامل با قراردادهای متفاوت‌اند.

The diagram summarizes architecture; networking and sharing details vary by version, settings, and tool. WSL2 starts a distro without requiring you to manage a conventional VM manually. Docker Desktop on Mac manages a Linux VM; UTM can create a full Linux VM. In each case, host and guest remain different systems with different contracts.

پروژه روی کدوم فایل‌سیستم هست؟Which filesystem holds the project?

در WSL، مسیر Windows مثل C:\work\app داخل Linux معمولاً زیر /mnt/c/work/app دیده می‌شه. ولی برای کارهای فایل-heavy که ابزار Linux اجرا می‌کنه، گذاشتن repo زیر home توزیع—مثلاً ~/src/app—معمولاً سریع‌تر و سازگارتر هست؛ خصوصاً برای تعداد زیادی فایل کوچک و inotify. این دربارهٔ مرز فایل‌سیستم هست، نه برتری مطلق یک دیسک.

In WSL, a Windows path such as C:\work\app commonly appears as /mnt/c/work/app. For file-heavy work done by Linux tools, keeping the repo under the distro’s Linux home—such as ~/src/app—is usually faster and more compatible, especially for many small files and inotify. This is about the filesystem boundary, not an absolute ranking of disks.

pwd
df -T .
uname -r
uname -m

از پوشهٔ پروژه df -T . فایل‌سیستم و uname -m معماری رو نشون می‌ده. در /mnt/c و home لینوکسی این شواهد رو مقایسه کن. اختلاف سرعت بسته به بار کاری و نسخه هست؛ یک بار time git status یا فایل scan محدود رو مقایسه کن، نه benchmark بی‌قاعده. اگه پروژه روی Windows می‌مونه، Explorer می‌تونه فایل‌های Linux رو با مسیر \\wsl.localhost ببینه؛ دو نسخهٔ کپی‌شدهٔ repo رو هم‌زمان تغییر نده.

From the project folder, df -T . reports filesystem and uname -m reports architecture. Compare in /mnt/c and Linux home. Speed depends on workload and version; compare one bounded operation such as time git status or a small file scan, not an uncontrolled benchmark. Windows Explorer can access Linux files through \\wsl.localhost; do not edit two copied repos at once.

برای آزمایش کنترل‌شده، یک repo آزمایشی رو در هر دو طرف بساز و یک فرمان ثابت فایل-heavy رو اجرا کن. انتظار می‌ره Linux-side repo برای Linux tools بهتر باشه، ولی خروجی تو به host، WSL به‌روزرسانی، Defender/antivirus و تعداد فایل‌ها بستگی داره. اگه نتیجه برعکس شد، مسیر واقعی، فایل‌سیستم و پردازههای پس‌زمینه رو بررسی کن.

For a controlled check, place a disposable repo on both sides and run the same file-heavy command. Linux-side files are generally preferable for Linux tools, but results depend on host, WSL update, antivirus, and file count. If your result differs, verify actual paths, filesystem type, and background processes.

localhost در WSL همیشه یک داستان نیستLocalhost in WSL is not always one story

در حالت پیش‌فرض NAT، سرویس guest که روی پورت 3000 گوش می‌ده معمولاً از Windows با http://localhost:3000 در دسترس هست؛ localhost forwarding معمولاً فعال هست. ولی درخواست برعکس—از WSL به سرویسی که فقط روی Windows گوش می‌ده—ممکنه به IP میزبان نیاز داشته باشه. روی Windows 11 نسخهٔ 22H2 به بعد، mirrored networking با تنظیم WSL جدیدتر می‌تونه ارتباط localhost دوطرفه رو بهتر کند. قابلیت و فایروال رو روی نسخهٔ خودت بررسی کن؛ «WSL2» به‌تنهایی حالت رو مشخص نمی‌کنه.

With default NAT, a guest service listening on port 3000 is commonly reachable from Windows at http://localhost:3000; localhost forwarding is usually enabled. The reverse direction—from WSL to a service listening only on Windows—may require the host IP. On Windows 11 version 22H2 and later, mirrored networking in a recent WSL can improve localhost connectivity in both directions. Verify mode and firewall on your version; “WSL2” alone does not identify the network mode.

اول نسخه و توزیع رو ببین:

Start by checking versions and installed distros:

wsl --version
wsl --list --verbose

در PowerShell، ستون VERSION باید برای توزیع هدف 2 باشه. اگه لازم شد، WSL رو به‌روز کن و بعد از تغییر تنظیمات با wsl --shutdown instanceها رو خاموش کن. این فرمان data distro رو حذف نمی‌کنه، ولی تمام WSL sessionهای در حال اجرا رو می‌بندد؛ فایل ذخیره‌نشده رو اول save کن.

In PowerShell, the target distro should show VERSION 2. Update WSL if needed, and after configuration changes use wsl --shutdown to stop instances. It does not delete distro data, but closes running WSL sessions; save work first.

در WSL، یک web سرور کوچک رو از پوشهٔ آزمایشی با bind مناسب اجرا و از Windows با curl.exe http://localhost:8080 امتحان کن. پاسخ HTTP ثابت می‌کنه مسیر همین host→guest و پورت در اون لحظه کار می‌کنه؛ دسترسی LAN/عمومی، فایروال یا مسیر WSL→Windows رو ثابت نمی‌کنه. اگه خرابی شد listener bind address، پورت، WSL حالت و Windows فایروال رو جدا بررسی کن.

Run a small web server from a disposable directory in WSL and test it from Windows with curl.exe http://localhost:8080. An HTTP response proves this host-to-guest path and port worked at that moment; it does not prove LAN/public access, firewall policy, or the reverse direction. If it fails, inspect bind address, port, WSL mode, and Windows firewall separately.

systemd و Docker Desktop در WSLsystemd and Docker Desktop in WSL

WSL قدیمی‌تر با رفتار Linux سرور معمولی یکی نبود؛ نسخه‌های جدید WSL از systemd پشتیبانی می‌کنن، ولی باید WSL به‌روز و گزینه برای همون distro فعال باشه. فایل /etc/wsl.conf مخصوص یک توزیع هست؛ برای فعال‌سازی، بخش boot رو تنظیم کن و WSL رو shutdown/restart کن:

Older WSL did not behave like a conventional Linux server. Recent WSL supports systemd, but WSL must be updated and the setting enabled per distro. /etc/wsl.conf is distro-specific; set its boot option, then shut down and restart WSL:

[boot]
systemd=true
ps -p 1 -o comm=
systemctl is-system-running

اگه PID 1 برابر systemd هست، init فعال رو تأیید کرده‌ای؛ این به معنی systemd روی هر نسخه یا اجرای تمام سرویسها نیست. اگه تشخیص نشد، wsl --version، محتوای conf و restart واقعی رو بررسی کن. تنظیمات عمومی VM سبک WSL مثل حافظه/CPU در .wslconfig هست؛ تنظیم per-distro مثل systemd در /etc/wsl.conf. این دو رو جابه‌جا نکن.

If PID 1 is systemd, you verified the active init; this does not imply every WSL version supports it or every service will run. If it is absent, inspect WSL version, config, and whether WSL was restarted. Global lightweight-VM settings such as memory/CPU live in .wslconfig; distro-specific systemd settings live in /etc/wsl.conf. Do not swap their roles.

Docker Desktop می‌تونه WSL2 رو backend کند و یکپارچه‌سازی رو برای distroهای انتخابی روشن کنه؛ Docker Engine و daemon در محیط مدیریت‌شدهٔ Desktop هستن و CLI در WSL به اون وصل می‌شه. اگه داخل همون distro یک daemon مستقل هم نصب و فعال کنی، دو context/socket ممکنه قاطی بشن. اول docker context ls و docker info رو بخون و مشخص کن کدوم Engine پاسخ می‌ده. فایل پروژهٔ Docker رو در Linux فایل‌سیستم بذار تا bind mount و فایل watching دردسر کمتری داشته باشه.

Docker Desktop can use WSL2 as its backend and enable integration for selected distros; the Engine/daemon lives in Desktop’s managed environment while the WSL CLI connects to it. Installing and running a second independent daemon in the same distro can cause context/socket confusion. Inspect docker context ls and docker info to identify the responding Engine. Keep Docker project files in the Linux filesystem for smoother bind mounts and file watching.

Mac: معماری CPU رو قبل از دانلود image بخونMac: check CPU architecture before pulling an image

Macهای Intel معمولاً x86_64 هستن؛ Apple Silicon معمولاً arm64/aarch64. Linux VM سریع معمولاً معماری مهمان همسان host می‌خواد. UTM می‌تونه با virtualization ماشین هم‌معماری بسازد و در بعضی حالت‌ها با QEMU معماری دیگر رو emulate کند؛ شبیه‌سازی عموماً کندتر هست و نباید با virtualization هم‌معنی بشه. Apple Virtualization framework هم Linux image رو متناسب با CPU می‌خواد؛ Rosetta می‌تونه در سناریوهای مشخص باینریهای Intel رو داخل Linux ARM ترجمه کنه، ولی به معنی boot کامل یک Intel Linux distro روی Apple Silicon نیست.

Intel Macs commonly report x86_64; Apple Silicon commonly reports arm64/aarch64. A fast Linux VM generally uses the host’s matching architecture. UTM can virtualize a matching guest and, in some configurations, emulate another architecture with QEMU; emulation is usually slower and is not the same as virtualization. Apple’s Virtualization framework expects Linux images suited to the CPU. Rosetta can translate Intel binaries inside ARM Linux in supported scenarios, but that does not mean booting a full Intel Linux distro on Apple Silicon.

uname -m
docker image inspect --format '{{.Os}}/{{.Architecture}}' IMAGE

اولی معماری محیط Linux رو می‌گه؛ دومی معماری image موجود رو. اگه باینری اجرا نمی‌شه یا image pull با platform mismatch مواجه هست، این دو رو مقایسه کن. گزینهٔ --platform linux/amd64 می‌تونه در محیط پشتیبانی‌شده شبیه‌سازی رو وارد کند؛ تضمین سرعت یا سازگاری کامل نیست. برای build قابل‌انتشار، target platform رو آگاهانه انتخاب و روی معماری واقعی مقصد تست کن.

The first reports the Linux environment architecture; the second reports the image’s platform. Compare them when a binary fails or an image has a platform mismatch. --platform linux/amd64 may invoke emulation where supported; it does not guarantee speed or complete compatibility. Choose build targets deliberately and test on the deployment architecture.

روی Mac، Docker Desktop برای Linux کانتینرها یک Linux VM سبک مدیریت می‌کنه؛ کانتینر، kernel macOS رو نمی‌بینه. برای Linux VM کامل، UTM یا ابزار مجازی‌سازی دیگری با ISO arm64 روی Apple Silicon و x86_64 روی Intel انتخاب کن. GPU و USB رو تضمین‌شده فرض نکن: پشتیبانی به دستگاه، ابزار، guest و نسخه وابسته هست. WSL USB passthrough نیز مسیر و ابزار جدا می‌خواد؛ این فصل وارد راه‌اندازی اون نمی‌شه.

On Mac, Docker Desktop manages a lightweight Linux VM for Linux containers; containers do not see the macOS kernel. For a full Linux VM, choose UTM or another virtualization tool, using arm64 ISO on Apple Silicon and x86_64 on Intel. Do not assume GPU or USB access; support depends on device, tool, guest, and version. WSL USB passthrough also needs separate tooling and setup, beyond this chapter.

آزمایش: مسیر host تا سرویس guest رو ثابت کنLab: prove the host-to-guest service path

اگه Windows داری، از WSL2 استفاده کن. اگه Mac داری، Docker Desktop برای سرویس نمونه و UTM برای تجربهٔ Linux VM کامل مناسب‌اند. روی هر دو لازم نیست همهٔ مسیرها رو نصب کنی؛ branch میزبان خودت رو اجرا کن و branch دیگر رو در حد مقایسه بخون.

On Windows, use WSL2. On a Mac, use Docker Desktop for the sample service and UTM for a full Linux VM experience. You do not need every branch on one host; execute your branch and compare the other.

  1. معماری و kernel رو ثبت کن: uname -m، uname -r؛ در Windows هم wsl --version و distro حالت رو ذخیره کن.
  2. Record architecture and kernel with uname -m and uname -r; on Windows also save wsl --version and distro mode.
  3. در WSL، پروژهٔ آزمایشی رو یک‌بار در home لینوکس و یک‌بار زیر /mnt/c بساز؛ فایل‌سیستم type و یک فایل-heavy check محدود رو مقایسه کن.
  4. In WSL, place a disposable project once in Linux home and once under /mnt/c; compare filesystem type and one bounded file-heavy check.
  5. از پوشهٔ خالی یک web سرویس روی پورت 8080 راه بینداز. در Windows از localhost درخواست بزن و response code/body رو ثبت کن.
  6. Start a web service on port 8080 from an empty directory. Request localhost from Windows and record response code/body.
  7. اگه WSL networking حالت رو تغییر می‌دی، نسخه و فایروال رو ثبت کن؛ سپس shutdown/restart و همون آزمون رو تکرار کن.
  8. If changing WSL networking mode, record version and firewall state, restart WSL, and repeat the same test.
  9. روی Mac، image معماری رو با host مقایسه کن و Docker Desktop رو با پورت منتشر فقط روی loopback اجرا کن؛ از Mac با curl پاسخ بگیر. برای UTM، مهمان هم‌معماری بساز و IP/interface خود guest رو ثبت کن.
  10. On Mac, compare image and host architecture, run Docker Desktop with a loopback-only published port, and curl it from macOS. For UTM, create a matching-architecture guest and record its IP/interface.
  11. یک بار عمدی image/فایل باینری معماری دیگر انتخاب کن؛ معماری شاهد رو بخون، target درست رو انتخاب و آزمون رو تکرار کن.
  12. Deliberately select an image/binary for another architecture; inspect architecture evidence, choose the correct target, and repeat.

تحویل: host/guest، معماری، فایل‌سیستم، شبکه، فرمان سرویس و شاهد درخواست موفق؛ محدودیت نسخه یا دستگاه دسترسی رو هم یادداشت کن.

Deliverable: Host/guest, architecture, filesystem, network, service command, and proof of the successful request; note version or device-access limitations.

۱۸. گزارش محیط

What evidence helps reproduce a bug across Windows and Mac?

معیار پاسخ

OS/نسخه، WSL حالت یا virtualization app، kernel، CPU معماری، فایل‌سیستم/مسیر، Docker context/image platform، شبکه و فرمان دقیق.

OS/version, WSL mode or VM app, kernel, CPU architecture, filesystem/path, Docker context/image platform, network, and exact command.

نام محیط رو کافی ندان؛ مرزش رو ثبت کنDo not stop at the environment’s name

وقتی چیزی کند یا ناسازگار هست، اول بپرس ابزار کجا اجرا می‌شه و فایل کجا قرار داره: kernel کدوم هست؟ معماری چیست؟ request از کدوم سمت شبکه میاد؟ Docker CLI به کدوم Engine وصل شده؟ این سؤال‌ها از «WSL باگ داره» یا «Mac پشتیبانی نمی‌کنه» تشخیص دقیق‌تری می‌دن.

When something is slow or incompatible, ask where the tool runs and where its files live: which kernel and architecture? Which direction does the request travel? Which Engine does Docker CLI target? These questions diagnose more than “WSL is buggy” or “Mac is unsupported.”

اگه چیزی فقط روی یک لپ‌تاپ کار کرد، قبل از متهم‌کردن پروژه بپرس فایل کجاست، kernel مال کدوم محیطه، درخواست از کدوم شبکه میاد و معماری CPU چیه. فصل بعد همین عادت رو تبدیل می‌کنیم به روش عیب‌یابی VM.

For current details, match the official WSL docs, Docker Desktop WSL integration, and Apple’s Virtualization framework to your versions. WSL and Docker Desktop are excellent daily development tools; when you need an exact Linux server kernel, bridge, or service behavior, a full VM remains the better tool.
