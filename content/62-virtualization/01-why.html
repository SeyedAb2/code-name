باید یک توزیع دیگر را امتحان کنی، ولی نه روی سیستم اصلیYou need another Linux distribution—but not on your main system

فرض کن روی لپ‌تاپت Ubuntu داری و لازم است دستوری را روی Debian یا Rocky Linux امتحان کنی. می‌توانی دیسک را پارتیشن‌بندی کنی، dual boot راه بیندازی و امیدوار باشی چیزی را اشتباه نزنی؛ یا سیستم دوم را داخل یک ماشین جدا اجرا کنی، شبکه‌اش را محدود کنی و اگر خراب شد آن را خاموش کنی.

Suppose your laptop runs Ubuntu but you need to test a command on Debian or Rocky Linux. You could repartition a disk, configure dual boot, and hope nothing goes wrong—or run the second system in an isolated machine, restrict its network, and shut it down if it breaks.

آن ماشین مجازی واقعاً یک کامپیوتر دوم نیست؛ اما فقط هم یک process معمولی نیست. نرم‌افزارِ میزبان برایش CPU، RAM، دیسک و device مجازی فراهم می‌کند. داخل guest، یک سیستم‌عامل جدا boot می‌شود و kernel خودش را دارد. برای فهمیدن این مرز، باید لایه‌ها را از پایین به بالا ببینیم.

A virtual machine is not literally a second physical computer, but it is more than an ordinary process. Host software presents virtual CPUs, memory, disks, and devices. A separate guest operating system boots inside it and runs its own kernel. To understand that boundary, follow the layers from the bottom up.

چه چیزی واقعاً مجازی می‌شود؟What is actually virtualised?

برنامهٔ داخل VM از دید خودش CPU، حافظه، دیسک و کارت شبکه دارد. hypervisor درخواست‌های guest را به منابع واقعی میزبان وصل می‌کند و دسترسی‌ها را میان ماشین‌ها مدیریت می‌کند. CPU هنوز همان CPU فیزیکی است؛ hypervisor ماشین فیزیکی جدیدی خلق نمی‌کند. بخشی از کار با hardware virtualization extension انجام می‌شود و بخشی—مثل deviceهای مجازی و I/O—با همکاری نرم‌افزار میزبان پیش می‌رود.

From inside the VM, software sees CPUs, memory, disks, and a network card. The hypervisor connects guest requests to host resources and manages access among VMs. The CPU is still the physical CPU; the hypervisor does not create new hardware. Hardware virtualisation extensions handle part of the work, while software and the host manage virtual devices and I/O.

فلش‌ها لایهٔ پایین‌دستِ منابع را نشان می‌دهند. «نوع ۱/۲» دسته‌بندی مفید است، نه تعریف کاملی از تمام پیاده‌سازی‌های امروزی.

Arrows show the resource layer beneath each component. “Type 1/2” is a useful category, not a complete description of every modern implementation.

در دسته‌بندی کلاسیک، Type 1 مستقیم‌تر روی hardware قرار می‌گیرد؛ Type 2 داخل یک host OS معمولی اجرا می‌شود. VirtualBox معمولاً نمونهٔ hosted است. Hyper-V و ESXi نمونه‌های Type 1 به شمار می‌آیند. KVM به kernel لینوکس متکی است و به‌همین‌خاطر مرز «hypervisor یا سیستم‌عامل؟» در معماری مدرن همیشه آن‌قدر تمیز نیست که اسم دسته‌بندی القا می‌کند. رابط گرافیکیِ مدیریت VM به‌تنهایی نوع hypervisor را تعیین نمی‌کند.

In the classic taxonomy, Type 1 sits more directly on hardware; Type 2 runs within a general-purpose host OS. VirtualBox is commonly hosted. Hyper-V and ESXi are commonly described as Type 1. KVM relies on the Linux kernel, so the boundary between “hypervisor” and “operating system” is not always as neat as the labels suggest. A graphical VM manager alone does not determine the hypervisor type.

پیش از ساخت VM، میزبان واقعاً چه قابلیتی دارد؟Before creating a VM, what does the host actually support?

پردازنده‌های x86 معمولاً extensionهایی مثل Intel VT-x یا AMD-V دارند تا اجرای guest با کمک hardware کارآمدتر شود. اینکه CPU چنین قابلیتی دارد کافی نیست: firmware ممکن است آن را خاموش کرده باشد، سیستم‌عامل میزبان ممکن است آن را برای خودش گرفته باشد، یا VM تو در cloud اجازهٔ nested virtualization نداشته باشد.

x86 processors commonly provide extensions such as Intel VT-x or AMD-V to accelerate guest execution. CPU support alone is not enough: firmware may disable it, the host OS may already own it, or a cloud VM may not expose nested virtualisation.

روی Linux این دو دستور یک سرنخ می‌دهند:

On Linux, these commands provide clues:

lscpu | grep -i virtualization
grep -m1 -Eo '\b(vmx|svm)\b' /proc/cpuinfo

خروجی نمونهٔ `Virtualization: VT-x` یا `vmx` برای Intel، و `AMD-V` یا `svm` برای AMD نشان می‌دهد قابلیت در این سیستم قابل‌مشاهده است. نبودن این رشته‌ها ثابت نمی‌کند CPU سخت‌افزارش را ندارد؛ ممکن است firmware یا لایهٔ مجازی‌ساز بالادستی آن را پنهان کرده باشد. روی Windows می‌توانی Task Manager → Performance → CPU را برای وضعیت virtualization ببینی؛ متن و محل دقیق بسته به نسخه فرق می‌کند.

Representative `Virtualization: VT-x` or `vmx` output on Intel, and `AMD-V` or `svm` on AMD, shows the capability is visible to this system. Missing flags do not prove the CPU lacks support; firmware or an upstream hypervisor may hide them. On Windows, Task Manager → Performance → CPU exposes a virtualization status, though labels and placement vary by version.

اگر VM داخل VM می‌سازی، مسئله nested virtualization است: hypervisor بیرونی باید extensionهای لازم را به guest پاس بدهد. این قابلیت در همهٔ CPUها، providerها یا planها تضمین‌شده نیست؛ پیش از نصب distro، وضعیت VM میزبان را بررسی کن.

Running a VM inside another VM is nested virtualisation: the outer hypervisor must expose the required extensions to its guest. Not every CPU, provider, or plan guarantees this; check the host VM capability before starting a distro installation.

اجرای مجازی با شبیه‌سازی یکی نیستVirtualisation is not the same as emulation

اگر host و guest از معماری instruction-set سازگار استفاده کنند، hypervisor می‌تواند بیشتر کد guest را با کمک CPU اجرا کند و deviceها را مجازی‌سازی کند. اگر بخواهی برنامهٔ ARM را روی CPU x86 اجرا کنی، ممکن است emulator لازم باشد که instructionهای معماری دیگر را ترجمه یا تفسیر می‌کند؛ معمولاً هزینهٔ کار بیشتر است. این مرز مطلق نیست: QEMU می‌تواند emulation یا با KVM شتاب‌دهی hardware داشته باشد و گزینهٔ درست به guest، host و تنظیم اجرا بستگی دارد.

When host and guest use compatible instruction-set architectures, a hypervisor can run most guest code with CPU assistance while virtualising devices. Running ARM software on an x86 CPU may require an emulator that translates or interprets another architecture’s instructions, usually at additional cost. The boundary is not absolute: QEMU can emulate or use KVM acceleration, depending on guest, host, and configuration.

پس «کند است» را فوراً به RAM کم نسبت نده. ابتدا بپرس guest روی همان معماری اجرا می‌شود یا emulation می‌شود، extensionها قابل‌استفاده‌اند یا نه، و کدام workload گلوگاه است. تنظیم این جزئیات را در فصل KVM/QEMU می‌بینیم؛ فعلاً مدل را درست نگه دار.

So do not immediately blame low RAM when a guest is slow. Ask whether it runs on the same architecture or is emulated, whether acceleration is available, and which workload is the bottleneck. We will inspect these settings in the KVM/QEMU chapter; for now, keep the model straight.

حالا ادعای «VM فقط container سنگین‌تر است» را بسنجیمNow test the claim: “a VM is just a heavier container”

ظاهرشان شبیه است: هر دو محیط جدا به برنامه می‌دهند. مرز kernel اما فرق دارد. VM یک guest OS boot می‌کند و kernel خودش را دارد. container فرایندهایی است که با isolationهایی مثل namespace و محدودیت منابع، اما با kernel سیستم میزبان کار می‌کند. image کانتینر می‌تواند user space متفاوت داشته باشد، ولی kernel جدا داخلش boot نمی‌شود.

They look similar because both give software a separated environment. Their kernel boundary differs. A VM boots a guest OS with its own kernel. A container is a set of processes isolated with mechanisms such as namespaces and resource controls, while using the host system’s kernel. A container image may have a different user space, but it does not boot a separate kernel.

در سمت VM برای هر مهمان kernel جدا boot می‌شود؛ containerهای سمت راست یک kernel میزبان را share می‌کنند.

Each VM boots its own guest kernel; the containers on the right share one host kernel.

بیایید به‌جای حفظ‌کردن این جمله، شاهد بگیریم. روی Linux host و داخل یک container دستور `uname -r` را اجرا کن:

Instead of memorising the claim, collect evidence. Run `uname -r` on a Linux host and inside a container:

uname -r
docker run --rm alpine uname -r

در Linux معمولاً هر دو kernel release یکسانی نشان می‌دهند؛ این همان kernel مشترک است. اما روی macOS یا Windows با Docker Desktop، containerهای Linux در یک Linux VM اجرا می‌شوند؛ در آن حالت kernel گزارش‌شده متعلق به محیط Linux میزبان کانتینر است، نه kernel بومی macOS/Windows. پس مقایسه را با دانستن مرز host انجام بده.

On Linux, both commands commonly report the same kernel release, showing the shared kernel. On macOS or Windows using Docker Desktop, Linux containers run inside a Linux VM; the reported kernel belongs to that Linux environment, not the native macOS/Windows kernel. Interpret the comparison with the host boundary in mind.

اگر یک VM آماده داری، داخل guest هم `uname -r` بزن. نسخهٔ kernel guest می‌تواند مستقل از host باشد. این شاهد تفاوت kernel boundary را نشان می‌دهد، نه اینکه VMها از هر نظر امن‌ترند یا هیچ فایل و شبکه‌ای share نمی‌کنند.

If you already have a VM, run `uname -r` inside its guest too. The guest kernel version can be independent from the host. This demonstrates a kernel boundary, not that VMs are automatically safer or share no files or networks.

VM چه هزینه‌ای دارد و چه مزیتی می‌خری؟What does a VM cost—and what do you gain?

guest OS برای boot و سرویس‌های خودش RAM، دیسک و CPU می‌خواهد. VM کندتر یا سبک‌تر بودنش به workload، storage، driver، معماری و تنظیم منابع بستگی دارد؛ قاعدهٔ «هر VM فلان مقدار RAM» وجود ندارد. VM وقتی ارزش دارد که به kernel، boot process، distro یا boundary سیستم‌عامل جدا نیاز داری؛ برای processهای هم‌kernel و انتشار سریع، container اغلب ساده‌تر است.

A guest OS needs memory, disk, and CPU for boot and its own services. Whether a VM is slower or lighter depends on workload, storage, drivers, architecture, and allocation; there is no universal RAM-per-VM rule. A VM is useful when you need a separate kernel, boot process, distribution, or OS boundary; containers are often simpler for same-kernel processes and quick packaging.

جداسازی VM هم به معنی sandbox کامل نیست. VM می‌تواند shared folder، clipboard، USB، bridge network یا passthrough داشته باشد؛ host و hypervisor هم ممکن است آسیب‌پذیر باشند. قبل از اجرای فایل ناشناس، integrationها را محدود و شبکه را جدا کن. snapshot برگشت سریع می‌دهد، اما backup خارج از همان دیسک نیست و به‌تنهایی دادهٔ مهم را نجات نمی‌دهد.

VM isolation is not a perfect sandbox. A VM may have shared folders, clipboard, USB, bridged networking, or device passthrough; the host and hypervisor can also have vulnerabilities. Restrict integrations and isolate the network before running unknown files. A snapshot enables quick rollback, but it is not an off-disk backup and cannot alone protect important data.

آزمایش: سه `uname` و یک تصور غلطLab: three `uname` results and one false model

روی Linux host این سه مورد را مقایسه کن: kernel میزبان، container موجود، و اگر در دسترس است guest VM. قبل از اجرا پیش‌بینی‌ات را بنویس. اگر Docker نداری، دو مورد اول را بگذار برای وقتی که container environment آماده شد و فعلاً host/guest را مقایسه کن.

Compare three environments on a Linux host: host kernel, a container, and—if available—a guest VM. Write your prediction before running commands. If Docker is unavailable, defer the first comparison and compare host/guest for now.

uname -r
docker run --rm alpine uname -r
# inside an existing VM guest:
uname -r

معمولاً host و container روی Linux یک release می‌دهند؛ guest VM می‌تواند release دیگری داشته باشد. اگر Docker Desktop استفاده می‌کنی، container را با kernel Linux VM مقایسه می‌کنی. output به‌تنهایی نوع hypervisor یا کیفیت isolation را ثابت نمی‌کند؛ فقط می‌گوید command در کدام kernel environment اجرا شده است.

On Linux, host and container commonly report one release; a guest VM may report another. With Docker Desktop, the container is being compared to the Linux VM’s kernel. Output alone proves neither hypervisor type nor isolation quality; it only identifies the kernel environment in which the command ran.

حالا ادعای «VM فقط container سنگین‌تر است» را بررسی کن: VM را خاموش کن. guest OS متوقف می‌شود و بعد از boot دوباره kernel خودش را بالا می‌آورد؛ container را متوقف کن و processها تمام می‌شوند، ولی host kernel باقی است. فرق را در report با یک شاهد از هر سمت بنویس.

Now test the claim “a VM is just a heavier container”: shut down the VM. Its guest OS stops and boots its own kernel again next time; stop a container and its processes exit while the host kernel remains. Record one piece of evidence for each side.

برای مرحلهٔ بعدی، فقط قابلیت میزبان را بررسی کن؛ هنوز hypervisor نصب نکن. `lscpu` و وضعیت firmware را ثبت کن و اگر extensionها دیده نمی‌شوند، مشخص کن احتمال خاموش‌بودن firmware، محدودیت میزبان بالادستی یا سخت‌افزار ناسازگار کدام است. بدون reboot یا تغییر BIOS این chapter را تمام کن.

For the next step, inspect host capability without installing a hypervisor yet. Record `lscpu` and firmware status; if extensions are missing, distinguish possible firmware disablement, upstream-host restrictions, and unsupported hardware. Finish this chapter without rebooting or changing BIOS settings.

۱۸ تمرین؛ کدام مرز را واقعاً لازم داری؟18 exercises: which boundary do you actually need?

۱. آزمایش توزیع دیگر

می‌خواهی package manager مربوط به Debian را امتحان کنی ولی host تو Fedora است. چه چیزی VM را برای این کار مناسب می‌کند؟

You want to test Debian’s package manager on a Fedora host. Why might a VM fit?

پاسخ

guest Debian با user space و kernel خودش boot می‌شود و لازم نیست host را تبدیل یا reboot کنی. VM هم مصرف RAM/disk دارد و shared folders/network را باید آگاهانه محدود کرد.

A Debian guest boots its own user space and kernel without replacing or rebooting the host. It still consumes resources, and shared folders/networking need deliberate limits.

۲. flag گم‌شده

`grep vmx /proc/cpuinfo` چیزی نشان نمی‌دهد. آیا CPU حتماً virtualization را پشتیبانی نمی‌کند؟

`grep vmx /proc/cpuinfo` prints nothing. Does the CPU definitely lack virtualisation support?

پاسخ

نه؛ شاید CPU AMD باشد و `svm` داشته باشد، BIOS خاموش کرده یا میزبان بالادستی flag را پنهان کرده. vendor، `lscpu` و تنظیم firmware/provider را بررسی کن.

No. It may be AMD with `svm`, disabled in firmware, or hidden by an upstream host. Check vendor, `lscpu`, and firmware/provider settings.

۳. `uname` یکسان

روی Linux host و container هر دو `6.x` چاپ می‌کنند. چه نتیجه‌ای می‌گیری؟

A Linux host and container both print `6.x`. What can you conclude?

پاسخ

با container مشترک kernel سازگار است. اما به‌تنهایی isolationهای دیگر یا نحوهٔ اجرای container را ثابت نمی‌کند.

It is consistent with a shared container kernel. It does not establish other isolation properties or the full runtime setup.

۴. VM و kernel

guest VM kernel version دیگری دارد. این شاهد کدام تفاوت را نشان می‌دهد؟

A guest VM has a different kernel version. Which difference does that demonstrate?

پاسخ

guest OS kernel خودش را boot کرده؛ با این حال shared folder یا network همچنان ممکن است داشته باشد.

The guest OS booted its own kernel, though shared folders or networking may still connect it to the host.

۵. hosted یا bare metal؟

VirtualBox را از داخل Windows باز می‌کنی. آیا UI ثابت می‌کند همهٔ virtualization داخل یک process معمولی انجام می‌شود؟

You launch VirtualBox from Windows. Does the UI prove all virtualisation happens inside an ordinary process?

پاسخ

نه؛ UI فقط برنامهٔ مدیریتی را نشان می‌دهد. drivers و kernel components هم می‌توانند بخشی از stack باشند؛ دسته‌بندی را از معماری محصول بررسی کن.

No. The UI is only the manager. Drivers and kernel components can also participate; inspect the product architecture for classification.

۶. Type 1 یعنی بی‌واسطه؟

کسی می‌گوید Type 1 یعنی هیچ OS یا software دیگری بین guest و hardware نیست. این تعریف چرا زیادی ساده است؟

Someone says Type 1 means no OS or software exists between guest and hardware. Why is this too simple?

پاسخ

مدیریت device، control plane یا پارتیشن مدیریتی می‌تواند وجود داشته باشد و در معماری modern دسته‌بندی‌ها overlap دارند. نکتهٔ اصلی جایگاه hypervisor نسبت به host OS است، نه نبودن مطلق software.

Device management, control planes, or management partitions may exist, and modern architectures blur categories. The useful distinction is the hypervisor’s relation to a host OS, not an absolute absence of software.

۷. host OS برابر guest OS

میزبان Linux است و VM هم Linux. آیا guest بودن kernel بی‌فایده می‌شود؟

The host is Linux and the VM is also Linux. Does that make the guest kernel boundary pointless?

پاسخ

نه؛ guest همچنان kernel مستقل boot می‌کند و می‌تواند distro/version متفاوتی داشته باشد. فقط خانوادهٔ OS مشابه است.

No. The guest still boots an independent kernel and can use another distro or version; only the OS family is similar.

۸. ARM روی x86

چرا اجرای guest ARM روی host x86 ممکن است از VM معمولی کندتر باشد؟

Why might an ARM guest on an x86 host be slower than a conventional VM?

پاسخ

ممکن است emulation لازم شود تا instruction-set دیگری ترجمه شود. مقدار overhead به emulator، workload و hardware وابسته است.

Instruction translation may require emulation. Overhead depends on emulator, workload, and hardware.

۹. nested VM در cloud

داخل VM ابری، hypervisor می‌گوید extension در دسترس نیست. چه کسی باید قابلیت را expose کند؟

Inside a cloud VM, the hypervisor reports no extensions. Who must expose the capability?

پاسخ

provider/hypervisor میزبان بالادستی؛ نصب package در guest نمی‌تواند hardware virtualization پنهان‌شده را به‌تنهایی آشکار کند.

The provider/upstream hypervisor must expose it; installing a guest package cannot reveal hidden hardware acceleration by itself.

۱۰. container با user space دیگر

container image بر پایه Alpine است، ولی میزبان Ubuntu. آیا kernel هم Alpine شده؟

A container image is based on Alpine, but the host runs Ubuntu. Did the kernel become Alpine’s?

پاسخ

نه؛ Alpine user space در container است و kernel را میزبان container runtime فراهم می‌کند. در Docker Desktop ممکن است آن host، Linux VM باشد.

No. Alpine provides the container user space; the runtime’s host provides the kernel. With Docker Desktop, that host may be a Linux VM.

۱۱. VM snapshot

VM پیش از تغییر خراب snapshot دارد. آیا حالا backup خارج از میزبان هم لازم نیست؟

A VM has a snapshot from before a risky change. Is an off-host backup now unnecessary?

پاسخ

نه؛ snapshot معمولاً به storage همان VM وابسته است و از خرابی دیسک/host محافظت کامل نمی‌کند. فایل مهم را جداگانه backup کن و restore را بیازما.

No. A snapshot usually depends on the same VM storage and does not fully protect against host/disk loss. Back up important data separately and test restoration.

۱۲. فایل ناشناس و shared folder

می‌خواهی installer ناشناس را در VM اجرا کنی، ولی shared folder خانه‌ات writable است. چه تغییری می‌دهی؟

You want to run an unknown installer in a VM, but your home directory is a writable shared folder. What do you change?

پاسخ

shared folder، clipboard و passthroughهای غیرلازم را خاموش کن، شبکه را internal یا قطع کن و snapshot را فقط برای rollback در نظر بگیر؛ VM تضمین sandbox کامل نیست.

Disable unnecessary shared folders, clipboard, and passthroughs; use an internal or disconnected network. Treat snapshots as rollback, not proof of a perfect sandbox.

۱۳. فقط RAM بیشتر؟

VM کند است. پیش از زیادکردن RAM سه عامل دیگر را نام ببر.

A VM is slow. Name three factors to check before allocating more RAM.

پاسخ

emulation در برابر hardware acceleration، storage I/O، CPU contention/overcommit، guest workload و driverها. اندازه‌گیری bottleneck را از حدس جدا می‌کند.

Emulation versus hardware acceleration, storage I/O, CPU contention/overcommit, guest workload, and drivers. Measurement distinguishes bottlenecks from guesses.

۱۴. Type 2 از نظر امنیتی

آیا Type 2 حتماً ناامن‌تر از Type 1 است؟

Is a Type 2 hypervisor necessarily less secure than Type 1?

پاسخ

نه؛ امنیت به threat model، implementation، patch، تنظیم device و مرز اعتماد بستگی دارد. اسم دسته‌بندی به‌تنهایی حکم امنیتی نیست.

No. Security depends on threat model, implementation, patching, devices, and trust boundaries. The category label alone is not a security verdict.

۱۵. virtualization خاموش است

Task Manager says virtualisation is disabled, but the CPU is recent. What next?

پاسخ

firmware UEFI/BIOS و وضعیت hypervisor بالادستی/cloud را با دستگاه خودت بررسی کن. پیش از تغییر firmware backup و recovery مسیر را بشناس؛ این فصل از تو نمی‌خواهد تنظیم host را عوض کنی.

Check UEFI/BIOS settings and upstream/cloud hypervisor exposure for your device. Know recovery options before firmware changes; this chapter does not ask you to alter the host.

۱۶. انتخاب برای CI

CI فقط می‌خواهد یک برنامهٔ Linux را روی Linux host اجرا و package کند؛ آیا VM همیشه انتخاب بهتر است؟

CI only needs to run and package a Linux program on a Linux host. Is a VM always the better choice?

پاسخ

نه؛ container می‌تواند محیط قابل‌تکرار و سبک بدهد چون kernel سازگار است. VM وقتی بهتر است که kernel، boot یا OS boundary جدا لازم باشد.

No. A container can provide a repeatable, lighter environment when the kernel is compatible. A VM fits when a separate kernel, boot, or OS boundary is required.

۱۷. شاهد چه چیزی را ثابت نمی‌کند؟

`systemd-detect-virt` خروجی `kvm` می‌دهد. چه چیزی فهمیدی و چه چیزی هنوز نامعلوم است؟

`systemd-detect-virt` reports `kvm`. What did you learn, and what remains unknown?

پاسخ

سیستم فعلی خود را داخل virtualization تشخیص می‌دهد. این به‌تنهایی تضمین نمی‌کند nested virtualization فعال است، نوع hypervisor را کامل توضیح نمی‌دهد یا VM امن پیکربندی شده.

The current system detects itself as virtualised. This alone does not prove nested virtualisation is available, fully identify the architecture, or show the VM is securely configured.

۱۸. طراحی آزمایشگاه

برای تست تنظیم شبکه‌ای که ممکن است route host را خراب کند، VM انتخاب می‌کنی. دو مرز isolation و یک محدودیت snapshot را پیش از شروع بنویس.

You choose a VM to test a network change that could break host routing. Name two isolation boundaries and one snapshot limitation before starting.

معیار پاسخ

مثلاً VM NIC روی internal network و بدون shared folder؛ guest kernel جدا از host. Snapshot روی storage همان host است و backup بیرونی نیست؛ پس config و دادهٔ لازم را جدا نگه دار.

For example, attach the VM only to an internal network and disable shared folders; its guest kernel is separate from the host. A snapshot lives on the same host storage and is not an off-host backup, so preserve needed config/data separately.

کدام ماشین، با کدام مرز؟Which machine, with which boundary?

اگر guest OS و kernel مستقل می‌خواهی، VM بساز؛ اگر فقط process جدا با kernel سازگار لازم داری، container را بررسی کن. Type 1/2 و نام ابزار سرنخ‌اند، نه جواب کامل دربارهٔ کارایی یا امنیت. مهم این است بدانی guest به چه منابعی دسترسی دارد، کدام featureهای integration روشن‌اند و کدام نتیجه را واقعاً اندازه گرفته‌ای.

Choose a VM when you need a separate guest OS and kernel; consider a container when isolated processes sharing a compatible kernel are enough. Type 1/2 and product names are clues, not complete answers about performance or security. Know which resources the guest can access, which integration features are enabled, and what you actually measured.
