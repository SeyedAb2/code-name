What virtualisation is

قبل از اینکه اسم hypervisorها رو حفظ کنیم، می‌خوایم بفهمیم وقتی یک VM روشن می‌کنی دقیقاً چی جدا می‌شه و چی هنوز مال همون میزبان اصلیه.

Type 1 and type 2 hypervisors, and how this differs from a container.

باید یک توزیع دیگر رو امتحان کنی، ولی نه روی سیستم اصلیYou need another Linux distribution—but not on your main system

فرض کن روی لپ‌تاپت Ubuntu داری و لازمه دستوری رو روی Debian یا Rocky Linux امتحان کنی. می‌تونی دیسک رو پارتیشن‌بندی کنی، dual boot راه بیندازی و امیدوار باشی چیزی رو اشتباه نزنی؛ یا سیستم دوم رو داخل یک ماشین جدا اجرا کنی، شبکه‌اش رو محدود کنی و اگه خراب شد اون رو خاموش کنی.

Suppose your laptop runs Ubuntu but you need to test a command on Debian or Rocky Linux. You could repartition a disk, configure dual boot, and hope nothing goes wrong—or run the second system in an isolated machine, restrict its network, and shut it down if it breaks.

اون ماشین مجازی واقعاً یک کامپیوتر دوم نیست؛ ولی فقط هم یک پردازه معمولی نیست. نرم‌افزارِ میزبان برایش CPU، RAM، دیسک و دستگاه مجازی فراهم می‌کنه. داخل guest، یک سیستم‌عامل جدا boot می‌شه و kernel خودش رو داره. برای فهمیدن این مرز، باید لایه‌ها رو از پایین به بالا ببینیم.

A virtual machine is not literally a second physical computer, but it is more than an ordinary process. Host software presents virtual CPUs, memory, disks, and devices. A separate guest operating system boots inside it and runs its own kernel. To understand that boundary, follow the layers from the bottom up.

چی واقعاً مجازی می‌شه؟What is actually virtualised?

برنامهٔ داخل VM از دید خودش CPU، حافظه، دیسک و کارت شبکه داره. hypervisor درخواست‌های guest رو به منابع واقعی میزبان وصل می‌کنه و دسترسی‌ها رو میان ماشین‌ها مدیریت می‌کنه. CPU هنوز همون CPU فیزیکی هست؛ hypervisor ماشین فیزیکی جدیدی خلق نمی‌کنه. بخشی از کار با قابلیت مجازی‌سازی سخت‌افزاری انجام می‌شه و بخشی—مثل دستگاه‌های مجازی و I/O—با همکاری نرم‌افزار میزبان پیش می‌ره.

From inside the VM, software sees CPUs, memory, disks, and a network card. The hypervisor connects guest requests to host resources and manages access among VMs. The CPU is still the physical CPU; the hypervisor does not create new hardware. Hardware virtualisation extensions handle part of the work, while software and the host manage virtual devices and I/O.

فلش‌ها لایهٔ پایین‌دستِ منابع رو نشون می‌دن. «نوع ۱/۲» دسته‌بندی مفید هست، نه تعریف کاملی از تمام پیاده‌سازی‌های امروزی.

Arrows show the resource layer beneath each component. “Type 1/2” is a useful category, not a complete description of every modern implementation.

در دسته‌بندی کلاسیک، Type 1 مستقیم‌تر روی سخت‌افزار قرار می‌گیره؛ Type 2 داخل یک host OS معمولی اجرا می‌شه. VirtualBox معمولاً نمونهٔ hosted هست. Hyper-V و ESXi نمونه‌های Type 1 حساب می‌شن. KVM به kernel لینوکس متکی هست و برای همین مرز «hypervisor یا سیستم‌عامل؟» در معماری مدرن همیشه اون‌قدر تمیز نیست که اسم دسته‌بندی القا می‌کنه. رابط گرافیکیِ مدیریت VM به‌تنهایی نوع hypervisor رو تعیین نمی‌کنه.

In the classic taxonomy, Type 1 sits more directly on hardware; Type 2 runs within a general-purpose host OS. VirtualBox is commonly hosted. Hyper-V and ESXi are commonly described as Type 1. KVM relies on the Linux kernel, so the boundary between “hypervisor” and “operating system” is not always as neat as the labels suggest. A graphical VM manager alone does not determine the hypervisor type.

قبل از ساخت VM، میزبان واقعاً چه قابلیتی داره؟Before creating a VM, what does the host actually support?

پردازنده‌های x86 معمولاً قابلیت‌هایی مثل Intel VT-x یا AMD-V دارن تا اجرای guest با کمک سخت‌افزار کارآمدتر بشه. اینکه CPU چنین قابلیتی داره کافی نیست: firmware ممکنه اون رو خاموش کرده باشه، سیستم‌عامل میزبان ممکنه اون رو برای خودش گرفته باشه، یا VM تو در cloud اجازهٔ nested virtualization نداشته باشه.

x86 processors commonly provide extensions such as Intel VT-x or AMD-V to accelerate guest execution. CPU support alone is not enough: firmware may disable it, the host OS may already own it, or a cloud VM may not expose nested virtualisation.

روی Linux این دو دستور یک سرنخ می‌دن:

On Linux, these commands provide clues:

lscpu | grep -i virtualization
grep -m1 -Eo '\b(vmx|svm)\b' /proc/cpuinfo

خروجی نمونهٔ `Virtualization: VT-x` یا `vmx` برای Intel، و `AMD-V` یا `svm` برای AMD نشون می‌ده قابلیت در این سیستم قابل‌مشاهده هست. نبودن این رشته‌ها ثابت نمی‌کنه CPU سخت‌افزارش رو نداره؛ ممکنه firmware یا لایهٔ مجازی‌ساز بالادستی اون رو پنهان کرده باشه. روی Windows می‌تونی Task Manager → Performance → CPU رو برای وضعیت virtualization ببینی؛ متن و محل دقیق بسته به نسخه فرق می‌کنه.

Representative `Virtualization: VT-x` or `vmx` output on Intel, and `AMD-V` or `svm` on AMD, shows the capability is visible to this system. Missing flags do not prove the CPU lacks support; firmware or an upstream hypervisor may hide them. On Windows, Task Manager → Performance → CPU exposes a virtualization status, though labels and placement vary by version.

اگه VM داخل VM می‌سازی، مسئله nested virtualization هست: hypervisor بیرونی باید قابلیت‌های لازم رو به guest پاس بده. این قابلیت در همهٔ CPUها، providerها یا طرح‌ها تضمین‌شده نیست؛ قبل از نصب distro، وضعیت VM میزبان رو بررسی کن.

Running a VM inside another VM is nested virtualisation: the outer hypervisor must expose the required extensions to its guest. Not every CPU, provider, or plan guarantees this; check the host VM capability before starting a distro installation.

اجرای مجازی با شبیه‌سازی یکی نیستVirtualisation is not the same as emulation

اگه host و guest از معماری مجموعه‌دستور سازگار استفاده کنن، hypervisor می‌تونه بیشتر کد guest رو با کمک CPU اجرا کنه و دستگاه‌ها رو مجازی‌سازی کنه. اگه بخوای برنامهٔ ARM رو روی CPU x86 اجرا کنی، ممکنه شبیه‌ساز لازم باشه که instructionهای معماری دیگر رو ترجمه یا تفسیر می‌کنه؛ معمولاً هزینهٔ کار بیشتر هست. این مرز مطلق نیست: QEMU می‌تونه شبیه‌سازی یا با KVM شتاب‌دهی سخت‌افزار داشته باشه و گزینهٔ درست به guest، host و تنظیم اجرا بستگی داره.

When host and guest use compatible instruction-set architectures, a hypervisor can run most guest code with CPU assistance while virtualising devices. Running ARM software on an x86 CPU may require an emulator that translates or interprets another architecture’s instructions, usually at additional cost. The boundary is not absolute: QEMU can emulate or use KVM acceleration, depending on guest, host, and configuration.

پس «کند هست» رو فوراً به RAM کم نسبت نده. ابتدا بپرس guest روی همون معماری اجرا می‌شه یا شبیه‌سازی می‌شه، قابلیت‌ها قابل‌استفاده‌اند یا نه، و کدوم بار کاری گلوگاه هست. تنظیم این جزئیات رو در فصل KVM/QEMU می‌بینیم؛ فعلاً مدل رو درست نگه دار.

So do not immediately blame low RAM when a guest is slow. Ask whether it runs on the same architecture or is emulated, whether acceleration is available, and which workload is the bottleneck. We will inspect these settings in the KVM/QEMU chapter; for now, keep the model straight.

حالا ادعای «VM فقط کانتینر سنگین‌تر هست» رو بسنجیمNow test the claim: “a VM is just a heavier container”

ظاهرشان شبیه هست: هر دو محیط جدا به برنامه می‌دن. مرز kernel ولی فرق داره. VM یک guest OS boot می‌کنه و kernel خودش رو داره. کانتینر فرایندهایی هست که با جداسازیهایی مثل namespace و محدودیت منابع، ولی با kernel سیستم میزبان کار می‌کنه. image کانتینر می‌تونه فضای کاربر متفاوت داشته باشه، ولی kernel جدا داخلش boot نمی‌شه.

They look similar because both give software a separated environment. Their kernel boundary differs. A VM boots a guest OS with its own kernel. A container is a set of processes isolated with mechanisms such as namespaces and resource controls, while using the host system’s kernel. A container image may have a different user space, but it does not boot a separate kernel.

در سمت VM برای هر مهمان kernel جدا boot می‌شه؛ کانتینرهای سمت راست یک kernel میزبان رو share می‌کنن.

Each VM boots its own guest kernel; the containers on the right share one host kernel.

بیاید به‌جای حفظ‌کردن این جمله، شاهد بگیریم. روی Linux host و داخل یک کانتینر دستور `uname -r` رو اجرا کن:

Instead of memorising the claim, collect evidence. Run `uname -r` on a Linux host and inside a container:

uname -r
docker run --rm alpine uname -r

در Linux معمولاً هر دو kernel نسخه یکسانی نشون می‌دن؛ این همون kernel مشترک هست. ولی روی macOS یا Windows با Docker Desktop، کانتینرهای Linux در یک Linux VM اجرا می‌شن؛ در اون حالت kernel گزارش‌شده متعلق به محیط Linux میزبان کانتینر هست، نه kernel بومی macOS/Windows. پس مقایسه رو با دانستن مرز host انجام بده.

On Linux, both commands commonly report the same kernel release, showing the shared kernel. On macOS or Windows using Docker Desktop, Linux containers run inside a Linux VM; the reported kernel belongs to that Linux environment, not the native macOS/Windows kernel. Interpret the comparison with the host boundary in mind.

اگه یک VM آماده داری، داخل guest هم `uname -r` بزن. نسخهٔ kernel guest می‌تونه مستقل از host باشه. این شاهد تفاوت kernel مرز رو نشون می‌ده، نه اینکه VMها از هر نظر امن‌ترند یا هیچ فایل و شبکه‌ای share نمی‌کنن.

If you already have a VM, run `uname -r` inside its guest too. The guest kernel version can be independent from the host. This demonstrates a kernel boundary, not that VMs are automatically safer or share no files or networks.

VM چه هزینه‌ای داره و چه مزیتی می‌خری؟What does a VM cost—and what do you gain?

guest OS برای boot و سرویس‌های خودش RAM، دیسک و CPU می‌خواد. VM کندتر یا سبک‌تر بودنش به بار کاری، storage، درایور، معماری و تنظیم منابع بستگی داره؛ قاعدهٔ «هر VM فلان مقدار RAM» وجود نداره. VM وقتی ارزش داره که به kernel، boot پردازه، distro یا مرز سیستم‌عامل جدا نیاز داری؛ برای پردازههای هم‌kernel و انتشار سریع، کانتینر اغلب ساده‌تر هست.

A guest OS needs memory, disk, and CPU for boot and its own services. Whether a VM is slower or lighter depends on workload, storage, drivers, architecture, and allocation; there is no universal RAM-per-VM rule. A VM is useful when you need a separate kernel, boot process, distribution, or OS boundary; containers are often simpler for same-kernel processes and quick packaging.

جداسازی VM هم به معنی محیط ایزوله کامل نیست. VM می‌تونه پوشهٔ مشترک، clipboard، USB، bridge شبکه یا passthrough داشته باشه؛ host و hypervisor هم ممکنه آسیب‌پذیر باشن. قبل از اجرای فایل ناشناس، یکپارچه‌سازیها رو محدود و شبکه رو جدا کن. snapshot برگشت سریع می‌ده، ولی backup خارج از همون دیسک نیست و به‌تنهایی دادهٔ مهم رو نجات نمی‌ده.

VM isolation is not a perfect sandbox. A VM may have shared folders, clipboard, USB, bridged networking, or device passthrough; the host and hypervisor can also have vulnerabilities. Restrict integrations and isolate the network before running unknown files. A snapshot enables quick rollback, but it is not an off-disk backup and cannot alone protect important data.

آزمایش: سه `uname` و یک تصور غلطLab: three `uname` results and one false model

روی Linux host این سه مورد رو مقایسه کن: kernel میزبان، کانتینر موجود، و اگه در دسترس هست guest VM. قبل از اجرا پیش‌بینی‌ات رو بنویس. اگه Docker نداری، دو مورد اول رو بذار برای وقتی که کانتینر environment آماده شد و فعلاً host/guest رو مقایسه کن.

Compare three environments on a Linux host: host kernel, a container, and—if available—a guest VM. Write your prediction before running commands. If Docker is unavailable, defer the first comparison and compare host/guest for now.

uname -r
docker run --rm alpine uname -r
# inside an existing VM guest:
uname -r

معمولاً host و کانتینر روی Linux یک نسخه می‌دن؛ guest VM می‌تونه نسخه دیگری داشته باشه. اگه Docker Desktop استفاده می‌کنی، کانتینر رو با kernel Linux VM مقایسه می‌کنی. خروجی به‌تنهایی نوع hypervisor یا کیفیت جداسازی رو ثابت نمی‌کنه؛ فقط می‌گه دستور در کدوم kernel environment اجرا شده.

On Linux, host and container commonly report one release; a guest VM may report another. With Docker Desktop, the container is being compared to the Linux VM’s kernel. Output alone proves neither hypervisor type nor isolation quality; it only identifies the kernel environment in which the command ran.

حالا ادعای «VM فقط کانتینر سنگین‌تر هست» رو بررسی کن: VM رو خاموش کن. guest OS متوقف می‌شه و بعد از boot دوباره kernel خودش رو بالا می‌آورد؛ کانتینر رو متوقف کن و پردازهها تمام می‌شن، ولی host kernel باقی هست. فرق رو در گزارش با یک شاهد از هر سمت بنویس.

Now test the claim “a VM is just a heavier container”: shut down the VM. Its guest OS stops and boots its own kernel again next time; stop a container and its processes exit while the host kernel remains. Record one piece of evidence for each side.

برای مرحلهٔ بعدی، فقط قابلیت میزبان رو بررسی کن؛ هنوز hypervisor نصب نکن. `lscpu` و وضعیت firmware رو ثبت کن و اگه قابلیت‌ها دیده نمی‌شن، مشخص کن احتمال خاموش‌بودن firmware، محدودیت میزبان بالادستی یا سخت‌افزار ناسازگار کدوم هست. بدون reboot یا تغییر BIOS این chapter رو تمام کن.

For the next step, inspect host capability without installing a hypervisor yet. Record `lscpu` and firmware status; if extensions are missing, distinguish possible firmware disablement, upstream-host restrictions, and unsupported hardware. Finish this chapter without rebooting or changing BIOS settings.

۱۸ تمرین؛ کدوم مرز رو واقعاً لازم داری؟18 exercises: which boundary do you actually need?

۱. آزمایش توزیع دیگر

می‌خوای مدیر بسته مربوط به Debian رو امتحان کنی ولی host تو Fedora هست. چی VM رو برای این کار مناسب می‌کنه؟

You want to test Debian’s package manager on a Fedora host. Why might a VM fit?

پاسخ

guest Debian با فضای کاربر و kernel خودش boot می‌شه و لازم نیست host رو تبدیل یا reboot کنی. VM هم مصرف RAM/دیسک داره و پوشهٔ مشترکs/شبکه رو باید آگاهانه محدود کرد.

A Debian guest boots its own user space and kernel without replacing or rebooting the host. It still consumes resources, and shared folders/networking need deliberate limits.

۲. flag گم‌شده

`grep vmx /proc/cpuinfo` چیزی نشون نمی‌ده. آیا CPU حتماً virtualization رو پشتیبانی نمی‌کنه؟

`grep vmx /proc/cpuinfo` prints nothing. Does the CPU definitely lack virtualisation support?

پاسخ

نه؛ شاید CPU AMD باشه و `svm` داشته باشه، BIOS خاموش کرده یا میزبان بالادستی flag رو پنهان کرده. vendor، `lscpu` و تنظیم firmware/provider رو بررسی کن.

No. It may be AMD with `svm`, disabled in firmware, or hidden by an upstream host. Check vendor, `lscpu`, and firmware/provider settings.

۳. `uname` یکسان

روی Linux host و کانتینر هر دو `6.x` چاپ می‌کنن. چه نتیجه‌ای می‌گیری؟

A Linux host and container both print `6.x`. What can you conclude?

پاسخ

با کانتینر مشترک kernel سازگار هست. ولی به‌تنهایی جداسازیهای دیگر یا نحوهٔ اجرای کانتینر رو ثابت نمی‌کنه.

It is consistent with a shared container kernel. It does not establish other isolation properties or the full runtime setup.

۴. VM و kernel

guest VM kernel version دیگری داره. این شاهد کدوم تفاوت رو نشون می‌ده؟

A guest VM has a different kernel version. Which difference does that demonstrate?

پاسخ

guest OS kernel خودش رو boot کرده؛ با این حال پوشهٔ مشترک یا شبکه همچنان ممکنه داشته باشه.

The guest OS booted its own kernel, though shared folders or networking may still connect it to the host.

۵. hosted یا bare metal؟

VirtualBox رو از داخل Windows باز می‌کنی. آیا UI ثابت می‌کنه همهٔ virtualization داخل یک پردازه معمولی انجام می‌شه؟

You launch VirtualBox from Windows. Does the UI prove all virtualisation happens inside an ordinary process?

پاسخ

نه؛ UI فقط برنامهٔ مدیریتی رو نشون می‌ده. drivers و kernel components هم می‌تونن بخشی از مجموعهٔ ابزارها باشن؛ دسته‌بندی رو از معماری محصول بررسی کن.

No. The UI is only the manager. Drivers and kernel components can also participate; inspect the product architecture for classification.

۶. Type 1 یعنی بی‌واسطه؟

کسی می‌گه Type 1 یعنی هیچ OS یا نرم‌افزار دیگری بین guest و سخت‌افزار نیست. این تعریف چرا زیادی ساده هست؟

Someone says Type 1 means no OS or software exists between guest and hardware. Why is this too simple?

پاسخ

مدیریت دستگاه، لایهٔ کنترل یا پارتیشن مدیریتی می‌تونه وجود داشته باشه و در معماری امروزی دسته‌بندی‌ها overlap دارن. نکتهٔ اصلی جایگاه hypervisor نسبت به host OS هست، نه نبودن مطلق نرم‌افزار.

Device management, control planes, or management partitions may exist, and modern architectures blur categories. The useful distinction is the hypervisor’s relation to a host OS, not an absolute absence of software.

۷. host OS برابر guest OS

میزبان Linux هست و VM هم Linux. آیا guest بودن kernel بی‌فایده می‌شه؟

The host is Linux and the VM is also Linux. Does that make the guest kernel boundary pointless?

پاسخ

نه؛ guest همچنان kernel مستقل boot می‌کنه و می‌تونه distro/version متفاوتی داشته باشه. فقط خانوادهٔ OS مشابه هست.

No. The guest still boots an independent kernel and can use another distro or version; only the OS family is similar.

۸. ARM روی x86

چرا اجرای guest ARM روی host x86 ممکنه از VM معمولی کندتر باشه؟

Why might an ARM guest on an x86 host be slower than a conventional VM?

پاسخ

ممکنه شبیه‌سازی لازم بشه تا مجموعه‌دستور دیگری ترجمه بشه. مقدار هزینهٔ اضافه به شبیه‌ساز، بار کاری و سخت‌افزار وابسته هست.

Instruction translation may require emulation. Overhead depends on emulator, workload, and hardware.

۹. nested VM در cloud

داخل VM ابری، hypervisor می‌گه قابلیت در دسترس نیست. چه کسی باید قابلیت رو در اختیار guest بذاره؟

Inside a cloud VM, the hypervisor reports no extensions. Who must expose the capability?

پاسخ

provider/hypervisor میزبان بالادستی؛ نصب بسته در guest نمی‌تونه سخت‌افزار virtualization پنهان‌شده رو به‌تنهایی آشکار کنه.

The provider/upstream hypervisor must expose it; installing a guest package cannot reveal hidden hardware acceleration by itself.

۱۰. کانتینر با فضای کاربر دیگر

کانتینر image بر پایه Alpine هست، ولی میزبان Ubuntu. آیا kernel هم Alpine شده؟

A container image is based on Alpine, but the host runs Ubuntu. Did the kernel become Alpine’s?

پاسخ

نه؛ Alpine فضای کاربر در کانتینر هست و kernel رو میزبان کانتینر runtime فراهم می‌کنه. در Docker Desktop ممکنه اون host، Linux VM باشه.

No. Alpine provides the container user space; the runtime’s host provides the kernel. With Docker Desktop, that host may be a Linux VM.

۱۱. VM snapshot

VM قبل از تغییر خراب snapshot داره. آیا حالا backup خارج از میزبان هم لازم نیست؟

A VM has a snapshot from before a risky change. Is an off-host backup now unnecessary?

پاسخ

نه؛ snapshot معمولاً به storage همون VM وابسته هست و از خرابی دیسک/host محافظت کامل نمی‌کنه. فایل مهم رو جداگانه backup کن و restore رو امتحان کن.

No. A snapshot usually depends on the same VM storage and does not fully protect against host/disk loss. Back up important data separately and test restoration.

۱۲. فایل ناشناس و پوشهٔ مشترک

می‌خوای نصاب ناشناس رو در VM اجرا کنی، ولی پوشهٔ مشترک خانه‌ات قابل‌نوشتن هست. چه تغییری می‌دی؟

You want to run an unknown installer in a VM, but your home directory is a writable shared folder. What do you change?

پاسخ

پوشهٔ مشترک، clipboard و passthroughهای غیرلازم رو خاموش کن، شبکه رو internal یا قطع کن و snapshot رو فقط برای rollback در نظر بگیر؛ VM تضمین محیط ایزوله کامل نیست.

Disable unnecessary shared folders, clipboard, and passthroughs; use an internal or disconnected network. Treat snapshots as rollback, not proof of a perfect sandbox.

۱۳. فقط RAM بیشتر؟

VM کند هست. قبل از زیادکردن RAM سه عامل دیگر رو نام ببر.

A VM is slow. Name three factors to check before allocating more RAM.

پاسخ

شبیه‌سازی در برابر شتاب‌دهی سخت‌افزاری، storage I/O، CPU contention/overcommit، guest بار کاری و درایورها. اندازه‌گیری گلوگاه رو از حدس جدا می‌کنه.

Emulation versus hardware acceleration, storage I/O, CPU contention/overcommit, guest workload, and drivers. Measurement distinguishes bottlenecks from guesses.

۱۴. Type 2 از نظر امنیتی

آیا Type 2 حتماً ناامن‌تر از Type 1 هست؟

Is a Type 2 hypervisor necessarily less secure than Type 1?

پاسخ

نه؛ امنیت به مدل تهدید، پیاده‌سازی، patch، تنظیم دستگاه و مرز اعتماد بستگی داره. اسم دسته‌بندی به‌تنهایی حکم امنیتی نیست.

No. Security depends on threat model, implementation, patching, devices, and trust boundaries. The category label alone is not a security verdict.

۱۵. virtualization خاموش هست

Task Manager می‌گه virtualization disabled، ولی CPU جدید هست. گام بعدی چیست؟

Task Manager says virtualisation is disabled, but the CPU is recent. What next?

پاسخ

firmware UEFI/BIOS و وضعیت hypervisor بالادستی/cloud رو با دستگاه خودت بررسی کن. قبل از تغییر firmware backup و recovery مسیر رو بشناس؛ این فصل از تو نمی‌خواد تنظیم host رو عوض کنی.

Check UEFI/BIOS settings and upstream/cloud hypervisor exposure for your device. Know recovery options before firmware changes; this chapter does not ask you to alter the host.

۱۶. انتخاب برای CI

CI فقط می‌خواد یک برنامهٔ Linux رو روی Linux host اجرا و بسته کند؛ آیا VM همیشه انتخاب بهتره؟

CI only needs to run and package a Linux program on a Linux host. Is a VM always the better choice?

پاسخ

نه؛ کانتینر می‌تونه محیط قابل‌تکرار و سبک بده چون kernel سازگار هست. VM وقتی بهتره که kernel، boot یا OS مرز جدا لازم باشه.

No. A container can provide a repeatable, lighter environment when the kernel is compatible. A VM fits when a separate kernel, boot, or OS boundary is required.

۱۷. شاهد چی رو ثابت نمی‌کنه؟

`systemd-detect-virt` خروجی `kvm` می‌ده. چی فهمیدی و چی هنوز نامعلوم هست؟

`systemd-detect-virt` reports `kvm`. What did you learn, and what remains unknown?

پاسخ

سیستم فعلی خود رو داخل virtualization تشخیص می‌ده. این به‌تنهایی تضمین نمی‌کنه nested virtualization فعال هست، نوع hypervisor رو کامل توضیح نمی‌ده یا VM امن پیکربندی شده.

The current system detects itself as virtualised. This alone does not prove nested virtualisation is available, fully identify the architecture, or show the VM is securely configured.

۱۸. طراحی آزمایشگاه

برای تست تنظیم شبکه‌ای که ممکنه route host رو خراب کنه، VM انتخاب می‌کنی. دو مرز جداسازی و یک محدودیت snapshot رو قبل از شروع بنویس.

You choose a VM to test a network change that could break host routing. Name two isolation boundaries and one snapshot limitation before starting.

معیار پاسخ

مثلاً VM NIC روی internal شبکه و بدون پوشهٔ مشترک؛ guest kernel جدا از host. Snapshot روی storage همون host هست و backup بیرونی نیست؛ پس تنظیمات و دادهٔ لازم رو جدا نگه دار.

For example, attach the VM only to an internal network and disable shared folders; its guest kernel is separate from the host. A snapshot lives on the same host storage and is not an off-host backup, so preserve needed config/data separately.

کدوم ماشین، با کدوم مرز؟Which machine, with which boundary?

اگه guest OS و kernel مستقل می‌خوای، VM بساز؛ اگه فقط پردازه جدا با kernel سازگار لازم داری، کانتینر رو بررسی کن. Type 1/2 و نام ابزار سرنخ‌اند، نه جواب کامل دربارهٔ کارایی یا امنیت. مهم اینه که بدونی guest به چه منابعی دسترسی داره، کدوم قابلیت‌های یکپارچه‌سازی روشن‌اند و کدوم نتیجه رو واقعاً اندازه گرفته‌ای.

Choose a VM when you need a separate guest OS and kernel; consider a container when isolated processes sharing a compatible kernel are enough. Type 1/2 and product names are clues, not complete answers about performance or security. Know which resources the guest can access, which integration features are enabled, and what you actually measured.

فصل بعد دیگه دربارهٔ VM حرف نمی‌زنیم؛ یکی واقعاً می‌سازیم. VirtualBox رو می‌آریم وسط و همین مرزها رو روی ISO، دیسک، boot order و شبکه با چشم می‌بینیم.
