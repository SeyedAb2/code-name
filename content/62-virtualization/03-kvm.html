KVM and QEMU

از اینجا می‌ریم سراغ مسیر بومی Linux: QEMU، KVM، libvirt و virt-manager؛ چهار اسم که اگه مرزشون رو نفهمی، موقع خرابی نمی‌دونی باید کجا رو نگاه کنی.

Native Linux virtualisation with virt-manager.

۱۸تمرینexercises

VM ساخته شده، ولی کند هست—و معلوم نیست اصلاً KVM استفاده می‌شهA VM exists, but it is slow—and you are not sure KVM is active

در VirtualBox ماشین ساختی. روی Linux host می‌خوای از KVM/QEMU استفاده کنی؛ نصب بسته‌ها تمام شده، ولی `virt-manager` باز نمی‌شه یا guest با سرعت عجیبی اجرا می‌شه. قبل از تغییر CPU/RAM بپرس: QEMU اجرا شده؟ KVM در kernel حاضر هست؟ کاربر اجازه داره به اون دسترسی بگیره؟

You created a VM in VirtualBox. On a Linux host you want KVM/QEMU; packages installed, but virt-manager will not connect or the guest runs unusually slowly. Before changing CPU or memory, ask: is QEMU running, is KVM available in the kernel, and is your user allowed to access it?

اسم این مجموعهٔ ابزارها رو مثل چهار قطعه بخون، نه چهار نام برای یک برنامه: QEMU مدل ماشین و دستگاه‌ها رو می‌سازه؛ KVM قابلیت virtualization داخل Linux kernel هست؛ libvirt API و چرخهٔ عمر رو مدیریت می‌کنه؛ `virt-manager` و `virsh` رابط‌های کاربرند. اگه یک قطعه خراب بشه، بقیه ممکنه هنوز نصب باشن ولی VM درست بالا نیاد.

Read the stack as four components, not four names for one program: QEMU provides a machine and device model; KVM is the Linux kernel virtualisation facility; libvirt manages the API and lifecycle; `virt-manager` and `virsh` are user-facing tools. One component can fail while the others remain installed.

فلش‌های بالا درخواست مدیریت رو نشون می‌دن؛ مسیر پایین دسترسی QEMU به KVM و CPU رو. QEMU حذف نمی‌شه—KVM شتاب‌دهندهٔ اون هست.

Top arrows show management requests; the lower path shows QEMU’s access to KVM and the CPU. KVM accelerates QEMU; it does not replace it.

QEMU می‌تونه بدون KVM هم اجرا بشه؛ ولی همون کار رو نمی‌کنهQEMU can run without KVM—but not in the same way

QEMU یک ماشین model کامل داره: CPU، حافظه و دستگاه‌های emulated. روی Linux سازگار می‌تونه برای اجرای guest روی CPU میزبان از KVM استفاده کنه. اگه شتاب‌دهنده در دسترس نباشه، QEMU ممکنه از TCG برای شبیه‌سازی استفاده کنه؛ این حالت برای معماری‌های متفاوت هم مفید هست، ولی معمولاً کندتر هست. QEMU با TCG «خراب» نیست؛ فقط مسیر اجرا متفاوت هست.

QEMU provides a machine model with emulated CPUs, memory, and devices. On a compatible Linux host, it can use KVM to run guest CPU work with hardware assistance. Without an accelerator, QEMU may use TCG emulation, which can support different architectures but is generally slower. QEMU with TCG is not broken; it is using a different execution path.

KVM به virtualization extensions و `/dev/kvm` وابسته هست. روی Intel معمولاً ماژول `kvm_intel` و روی AMD `kvm_amd` کنار `kvm` دیده می‌شه؛ نام‌ها و دسترس‌پذیری با معماری فرق می‌کنه. وجود module در `lsmod` به‌تنهایی ثابت نمی‌کنه کاربر مجوز داره یا guest با KVM accelerator ساخته شده.

KVM depends on virtualisation extensions and `/dev/kvm`. Intel systems commonly show `kvm_intel`; AMD commonly shows `kvm_amd`, alongside `kvm`. Names and availability vary by architecture. A loaded module alone does not prove the user has access or a guest is using KVM acceleration.

libvirt به تو storage pool، شبکه و domain می‌ده. domain یعنی تعریف و چرخهٔ عمر یک VM؛ XML اون CPU، RAM، دیسک، NIC و دستگاه‌ها رو شرح می‌ده. Storage pool مکانی برای managed دیسکهاست؛ شبکه مثل پیش‌فرض NAT می‌تونه guest رو بیرون ببرد. این مفاهیم رو می‌توان با GUI دید و با `virsh` بررسی کرد.

libvirt exposes storage pools, networks, and domains. A domain is the definition and lifecycle of a VM; its XML describes CPU, memory, disks, NICs, and devices. A storage pool manages disk volumes; a network such as the default NAT network connects guests outward. You can inspect these concepts in a GUI or with `virsh`.

اول شاهد جمع کن: قابلیت، module و دستگاهCollect evidence first: extensions, module, and device

روی Ubuntu/Debian host این بررسی‌ها رو قبل از نصب یا دستکاری انجام بده. `kvm-ok` از بستهٔ `cpu-checker` سرنخی دربارهٔ سخت‌افزار پشتیبانی می‌ده؛ `lsmod` دربارهٔ moduleهای loadشده؛ `/dev/kvm` و حالت/owner دربارهٔ دستگاه node. هیچ‌کدوم به‌تنهایی دسترسی کامل به VM رو ثابت نمی‌کنن.

On an Ubuntu/Debian host, run these checks before installing or changing anything. `kvm-ok` from `cpu-checker` reports hardware-support clues; `lsmod` shows loaded modules; `/dev/kvm` and its mode/owner show the device node. None alone proves complete VM access.

lscpu | grep -i virtualization
lsmod | grep -E '^kvm|^kvm_'
ls -l /dev/kvm
id

دنبال VT-x/AMD-V (یا قابلیت معماری خودت)، module مناسب، و `/dev/kvm` بگرد. اگه node وجود نداره، firmware یا host بالادستی رو بررسی کن؛ اگه هست ولی مجوز رد می‌شه، حالت/group/ACL و عضویت نشست ورود رو بسنج. `chmod 666 /dev/kvm` راه‌حل امن نیست—دسترسی اجرای VM رو به همهٔ کاربران باز می‌کنه.

Look for the host’s virtualisation extension, relevant modules, and `/dev/kvm`. If the node is missing, investigate firmware or the upstream host; if it exists but permission is denied, inspect mode/group/ACL and the current login session. `chmod 666 /dev/kvm` is not a safe fix—it grants every local user VM access.

برای host تازه، مسیر Ubuntu معمولاً با `qemu-kvm`, `libvirt-daemon-system`, `virt-manager` و ابزار بررسی `cpu-checker` شروع می‌شه. نام بسته و daemon در distroهای دیگر فرق داره. بعد از نصب، `virsh -c qemu:///system list --all` رو اجرا کن؛ اتصال موفق به system libvirt رو ثابت می‌کنه، نه فعال‌بودن acceleration هر VM.

On a fresh Ubuntu host, a common starting set is `qemu-kvm`, `libvirt-daemon-system`, `virt-manager`, and `cpu-checker`. Package and daemon names differ on other distributions. After installation, `virsh -c qemu:///system list --all` tests the system libvirt connection; it does not prove each VM uses acceleration.

sudo apt update
sudo apt install qemu-kvm libvirt-daemon-system virt-manager cpu-checker
kvm-ok
virsh -c qemu:///system list --all

خروجی `kvm-ok` که می‌گه KVM acceleration can be used یک آزمون capability هست. اگه `virsh` مجوز denied داد، خود متن خطا، اتصال URI و `id` رو ثبت کن؛ با `sudo virt-manager` دورش نزن. کاربر privileged می‌تونه VM و شبکه سطح سیستم رو تغییر دهد.

A `kvm-ok` message that KVM acceleration can be used is a capability check. If `virsh` reports permission denied, record the error, connection URI, and `id`; do not bypass it with `sudo virt-manager`. A privileged user can alter system-wide VMs and networks.

دو اتصال libvirt ممکنه دو جهان متفاوت ببینندTwo libvirt connections may see different worlds

`qemu:///system` به daemon سیستمی و منابع مشترک host وصل می‌شه؛ `qemu:///session` به VMهای کاربر فعلی و منابع همون کاربر. `virsh uri` می‌گه CLI الان به کدوم اتصال وصل هست. اگه `virt-manager` فهرست خالی نشون می‌ده، شاید نه VMها گم شده‌اند و نه نصب خراب هست—ممکنه GUI به URI دیگری وصل باشه.

`qemu:///system` connects to the system daemon and host-wide resources; `qemu:///session` manages the current user’s VMs and resources. `virsh uri` reports the CLI’s active connection. If virt-manager shows an empty list, VMs may not be missing and installation may be fine—the GUI could be connected to another URI.

virsh uri
virsh -c qemu:///system list --all
virsh -c qemu:///session list --all

اگه کاربر رو به گروه `libvirt` اضافه می‌کنی، این یک امتیاز مدیریتی مهم هست؛ فقط کاربری رو عضو کن که به hostهای مجازی و شبکه‌های system-wide اعتماد داری. در بعضی Ubuntuها عضو sudo دسترسی مناسب می‌گیره و نیازی به تغییر گروه نیست؛ سیاست distro و ACL بسته رو بررسی کن. عضویت گروه بعد از logout/login تازه می‌شه، نه لزوماً در shell فعلی.

Adding a user to the `libvirt` group is a significant administrative privilege; grant it only to users trusted with system-wide VMs and networks. Some Ubuntu setups grant suitable access to sudo users already, so inspect the distro’s policy rather than changing groups automatically. Group membership may require a new login session.

برای وضعیت daemon در نصب‌های جدید libvirt ممکنه unitها modular و socket-activated باشن؛ به‌جای فرض یک اسم واحد مثل `libvirtd`، `systemctl list-units '*libvirt*'` و `virsh uri` رو با نسخهٔ سیستم خودت تطبیق بده.

Recent libvirt installations may use modular, socket-activated units. Instead of assuming one service name such as `libvirtd`, inspect `systemctl list-units '*libvirt*'` and `virsh uri` on your system.

اولین domain رو با virt-manager بساز؛ بعد با virsh بخونCreate the first domain in virt-manager, then inspect it with virsh

روی Linux سیستم کاری با GUI، `virt-manager` رو باز و اتصال `QEMU/KVM – system` رو انتخاب کن. New VM رو بساز، Ubuntu ISO بده، ۲ vCPU و RAM متناسب با host انتخاب کن و دیسک رو در pool پیش‌فرض ذخیره کن. Network پیش‌فرض معمولاً NAT هست؛ interface `default` باید active باشه. Wizard مقدارها رو نشون می‌ده، ولی install موفق رو فقط guest boot ثابت می‌کنه.

On a Linux workstation with a GUI, open virt-manager and select `QEMU/KVM – system`. Create a VM, choose an Ubuntu ISO, assign 2 vCPUs and host-appropriate memory, and store the disk in the default pool. The default network is commonly NAT; network `default` should be active. The wizard displays settings, but only a booted guest proves installation.

اگه host سرور بدون GUI هست، از `virt-install` استفاده یا virt-manager رو از سیستم کاری از راه SSH به libvirt host وصل کن. GUI رو روی محیط عملیاتی سرور نصب‌کردن لازم نیست. دوربین، USB و shared مسیر رو اضافه نکن مگر پروژه واقعاً نیاز داشته باشه.

On a headless server, use `virt-install` or connect virt-manager from a workstation to the libvirt host over SSH. A production server does not need a desktop GUI. Do not add camera, USB, or shared paths unless the project needs them.

بعد از install، نام domain رو از `virsh list --all` بردار و مشخصات رو بخون:

After installation, get the domain name from `virsh list --all` and inspect its details:

virsh list --all
virsh dominfo lab-kvm
virsh dumpxml lab-kvm
virsh pool-list --all
virsh net-list --all

`dominfo` وضعیت و مقدار منابع رو می‌گه؛ `dumpxml` نشون می‌ده interface به چه شبکه وصل هست و دیسک کجا قرار داره؛ pool و شبکه list مدیریت منابع libvirt رو نشون می‌دن. این‌ها تنظیمات رو ثابت می‌کنن، نه اینکه route یا اینترنت داخل guest حتماً کار می‌کنه؛ داخل guest `ip -br address` و `ip route` رو هم بخون.

`dominfo` reports state and resource settings; `dumpxml` shows the network attachment and disk path; pool/network listings reveal managed resources. These establish configuration, not that guest routes or internet work; inspect `ip -br address` and `ip route` inside the guest too.

از کجا بفهمیم این domain واقعاً KVM هست؟How do we know this domain actually uses KVM?

فقط دیدن CPU usage یا سرعت boot کافی نیست. libvirt domain XML برای VM شتاب‌گرفته معمولاً `` داره؛ QEMU پردازه هم بالا هست و دسترسی `/dev/kvm` لازمه. `virsh dumpxml` تنظیمات انتخاب‌شده رو نشون می‌ده؛ `/dev/kvm` و moduleها capability میزبان رو؛ با هم نتیجهٔ قوی‌تری می‌دن.

CPU usage or boot speed alone is not proof. A libvirt XML domain configured for accelerated KVM commonly has ``; a QEMU process is still present and needs `/dev/kvm`. `virsh dumpxml` shows the configured domain type; `/dev/kvm` and modules show host capability. Together they provide stronger evidence.

virsh dumpxml lab-kvm | grep -m1 '<domain type='
ps -eo pid,comm,args | grep '[q]emu-system'
ls -l /dev/kvm

اگه XML نوع `qemu` یا domain start لاگ دربارهٔ KVM خطا داره، guest ممکنه به شبیه‌سازی/مسیر دیگری رفته باشه. برای اندازه‌گیری performance یک عدد ثابت نداریم: بار کاری، دیسک، حافظه و دستگاه model اثر دارن. QEMU با TCG مفید هست ولی CPU شبیه‌سازی معمولاً کندتر هست؛ عملکرد رو با بار کاری یکسان بسنج، نه با یک حس کلی.

If XML uses type `qemu` or startup logs mention KVM errors, the guest may be using emulation or another path. There is no universal performance number: workload, disk, memory, and device model matter. QEMU with TCG remains useful but CPU emulation is generally slower; compare the same workload instead of relying on impressions.

خرابی عمدی: KVM نصب هست، ولی دسترسی denied می‌شهDeliberate failure: KVM is installed, but access is denied

در یک Linux VM تو‌در‌تو یا host lab، عضو گروهی با دسترسی به `/dev/kvm` نباش. قبل از تعمیر، `lsmod`, `ls -l /dev/kvm`, `id`, `virsh uri` و خطای `virsh list` رو جمع کن. سؤال این هست: module نیامده، دستگاه وجود نداره، یا فقط مجوز session کم هست؟

On a nested Linux VM or lab host, use an account without access to `/dev/kvm`. Before repair, capture `lsmod`, `ls -l /dev/kvm`, `id`, `virsh uri`, and the `virsh list` error. Is the module missing, the device absent, or only the session permission wrong?

اگه دستگاه node هست ولی مجوز رد می‌شه، حالت/group/ACL و اتصال system/session رو بخون. راه امن، استفاده از سیاست مجاز همون distro—برای کاربر مورداعتماد—و آغاز نشست ورود تازه هست. حالت رو به `666` تغییر نده و GUI رو با root اجرا نکن؛ این کار تشخیص رو پنهان می‌کنه و دسترسی رو بی‌جهت گسترش می‌ده.

If the node exists but access is denied, inspect mode/group/ACL and whether the client uses system or session libvirt. Use the distro’s intended policy for a trusted account and start a fresh login session. Do not chmod the device to `666` or run the GUI as root; that hides the diagnosis and expands access needlessly.

اگه `/dev/kvm` وجود نداره یا `kvm-ok` می‌گه unavailable، module و kernel لاگ رو ببین، بعد firmware virtualization و اگه host خودش VM هست nested virtualization رو بررسی کن. نصب مجدد `virt-manager` قابلیت گم‌شدهٔ CPU رو جادویی اضافه نمی‌کنه.

If `/dev/kvm` is absent or `kvm-ok` reports unavailable, inspect modules and kernel logs, then check firmware virtualisation and nested-virtualisation exposure if the host is itself a VM. Reinstalling virt-manager cannot reveal hidden CPU extensions.

lab: یک domain، سه نوع شاهدLab: one domain, three kinds of evidence

روی سیستم کاری لینوکسی آزمایشگاهی، ابتدا capability میزبان رو ثبت کن: قابلیت، module، `/dev/kvm` و دسترسی کاربر. اگه host KVM نداره، این بخش رو روی VM nested آزمایشی یا Linux host واقعی انجام بده؛ به‌زور setting host رو تغییر نده. سپس بسته‌های Ubuntu رو نصب و از virt-manager VM Ubuntu بساز.

On a Linux lab workstation, record host capability first: extensions, modules, `/dev/kvm`, and user access. If the host lacks KVM, use a disposable nested VM or a real Linux host; do not force host settings. Install Ubuntu packages and create an Ubuntu guest with virt-manager.

بعد از boot، سه لایه رو جدا ثبت کن: host `lsmod` و `/dev/kvm`؛ libvirt `virsh dominfo` و `dumpxml`; guest `uname -r`, `ip -br address` و `ip route`. این گزارش نشون می‌ده KVM برای host حاضر هست، domain چه نوعی داره و guest خودش چه می‌بینه. یک خط سبز به‌تنهایی کافی نیست.

After boot, capture three layers separately: host `lsmod` and `/dev/kvm`; libvirt `virsh dominfo` and `dumpxml`; guest `uname -r`, `ip -br address`, and `ip route`. This shows host KVM availability, domain type, and guest view. One green line alone is not enough.

برای خرابی، حسابی با مجوز محدود یا lab nestedای انتخاب کن که `/dev/kvm` رو پنهان می‌کنه. خروجی‌ها رو مقایسه کن و تشخیص بده مشکل مجوز هست یا capability. سپس فقط اگه account مورداعتماد هست، سیاست مجاز رو به‌کار بگیر؛ logout/login کن و `virsh` رو دوباره اجرا کن. نصب بسته‌ها رو از اول تکرار نکن مگر شاهد بسته missing باشه.

For failure, use an account without the required permission or a nested lab hiding `/dev/kvm`. Compare outputs and decide whether the issue is access or capability. Apply the intended policy only for a trusted account, log in again, and rerun `virsh`. Do not reinstall packages unless evidence shows they are missing.

۱۸ تمرین؛ QEMU، KVM یا libvirt؟18 exercises: QEMU, KVM, or libvirt?

۱. QEMU یا KVM؟

می‌خوای guest CPU رو شتاب بدی ولی دستگاه‌های مجازی رو هم لازم داری. هر قطعه چه نقشی داره؟

You need accelerated guest CPU execution and virtual devices. What does each component do?

پاسخ

KVM مسیر kernel/شتاب‌دهی سخت‌افزاری رو می‌ده؛ QEMU ماشین/دستگاه model رو نگه می‌داره و با KVM همکاری می‌کنه.

KVM provides the kernel/hardware acceleration path; QEMU retains the machine/device model and works with it.

۲. QEMU بدون KVM

`/dev/kvm` نیست، ولی QEMU guest رو boot می‌کنه. چه توضیحی محتمل هست؟

There is no `/dev/kvm`, but QEMU boots a guest. What is a likely explanation?

پاسخ

ممکنه TCG/CPU شبیه‌سازی استفاده بشه. این نشون نمی‌ده KVM فعال هست؛ domain type، QEMU args/لاگ و کارایی رو بررسی کن.

It may be using TCG/CPU emulation. That does not mean KVM is active; inspect domain type, QEMU arguments/logs, and performance.

۳. `lsmod` خالی

`lsmod | grep kvm` هیچ خروجیی نداره. کدوم دو عامل رو قبل از نصب مجدد بررسی می‌کنی؟

`lsmod | grep kvm` prints nothing. Which two factors do you check before reinstalling?

پاسخ

آیا module به‌تازگی load نشده یا kernel/CPU قابلیت/firmware اجازه نمی‌ده؟ `modprobe` لاگ، `kvm-ok`, `lscpu` و kernel لاگ رو ببین.

Is the module simply not loaded, or do kernel/CPU extensions/firmware prevent it? Check `modprobe` output, `kvm-ok`, `lscpu`, and kernel logs.

۴. دستگاه هست، ولی مجوز denied

`/dev/kvm` وجود داره و حالت اون `crw-rw---- root kvm` هست. کاربر خطای مجوز می‌گیره. قدم بعد چیست؟

`/dev/kvm` exists with mode `crw-rw---- root kvm`. The user gets permission denied. What next?

پاسخ

`id`, ACL و نشست ورود رو ببین؛ membership تازه شاید هنوز اعمال نشده. `chmod 666` نزن و فقط دسترسی سیاست مجاز رو به کاربر مورداعتماد بده.

Inspect `id`, ACL, and login session; new group membership may not be active. Do not chmod to `666`; grant only the approved access policy to a trusted user.

۵. دو URI

`qemu:///session` فهرست خالی داره ولی `qemu:///system` domain نشون می‌ده. VM گم شده؟

`qemu:///session` is empty while `qemu:///system` shows a domain. Is the VM missing?

پاسخ

احتمالاً نه؛ دو اتصال منابع جدا می‌بینن. `virsh uri` رو بخون و virt-manager رو به URI هدف وصل کن.

Probably not; the two connections expose different resources. Check `virsh uri` and connect virt-manager to the intended URI.

۶. libvirt یا QEMU؟

`virsh list --all` connect نمی‌شه و `qemu-system` پردازه هم نیست. کدوم لایه رو اول بررسی می‌کنی؟

`virsh list --all` cannot connect and no `qemu-system` process exists. Which layer do you inspect first?

پاسخ

URI و daemon/socket libvirt؛ اگه VM اصلاً start نشده، نبودن QEMU پردازه طبیعی هست. ابتدا خطا و اتصال URI رو ببین.

Check the URI and libvirt daemon/socket; if the VM never started, no QEMU process is expected. Start with the error and connection URI.

۷. domain

`virsh list --all` یک `Shut off` domain نشون می‌ده. آیا دیسک هم حذف شده؟

`virsh list --all` shows a `Shut off` domain. Was its disk deleted?

پاسخ

نه؛ چرخهٔ عمر وضعیت خاموش هست. `dominfo`, `dumpxml` و دیسک source رو ببین؛ خاموش‌بودن مساوی حذف نیست.

No; the domain is powered off. Inspect `dominfo`, `dumpxml`, and disk source; shutoff does not mean deletion.

۸. storage pool غیرفعال

VM start نمی‌شه و XML دیسک source در pool پیش‌فرض هست؛ `pool-list --all` اون رو inactive نشون می‌ده. چه رابطه‌ای محتمل هست؟

The VM will not start; its disk source is in the default pool, which `pool-list --all` shows as inactive. What is a likely relationship?

پاسخ

libvirt pool برای مدیریت volumeهاست و ممکنه pool mount/مسیر در دسترس نباشه. pool info و مسیر/permissions رو بخون؛ دیسک رو از نو نساز.

The libvirt pool manages volumes and its path/mount may be unavailable. Inspect pool info and path/permissions; do not recreate the disk.

۹. network default inactive

guest boot می‌شه ولی IP نمی‌گیره؛ `net-list --all` پیش‌فرض رو inactive نشون می‌ده. این چه فرضیه‌ای می‌سازه؟

The guest boots but gets no IP; `net-list --all` shows default inactive. What hypothesis does this create?

پاسخ

NAT/DHCP شبکه libvirt اجرا نیست. شبکه info/autostart/وضعیت رو بررسی کن؛ guest boot شدن ثابت نمی‌کنه NIC شبکه فعال هست.

The libvirt NAT/DHCP network may be stopped. Check its info/autostart/state; a booted guest does not prove the NIC network is active.

۱۰. pool در برابر دیسک

آیا storage pool خودش همون VDI/qcow2 فایل هست؟

Is a storage pool itself the VDI/qcow2 file?

پاسخ

نه؛ pool مدیریت محل و volumeهاست؛ دیسک image یک volume/فایل مشخص درون اون می‌تونه باشه. `pool-list` و `vol-list` رو جدا بخون.

No. A pool manages storage locations/volumes; a disk image may be one volume/file inside it. Inspect pools and volumes separately.

۱۱. فقط QEMU پردازه؟

پردازه `qemu-system` وجود داره. آیا ثابت شد domain acceleration با KVM انجام می‌شه؟

A `qemu-system` process exists. Does that prove KVM acceleration?

پاسخ

نه؛ QEMU می‌تونه TCG باشه. domain XML type، لاگ/arguments و دسترسی KVM رو کنار هم بررسی کن.

No; QEMU can use TCG. Inspect domain type, logs/arguments, and KVM access together.

۱۲. `kvm-ok` موفق

`kvm-ok` موفق هست، ولی guest type=qemu هست. چی ثابت شد و چی نه؟

`kvm-ok` succeeds, but the guest type is qemu. What is established and what is not?

پاسخ

host capability قابل‌استفاده به نظر می‌رسه؛ تنظیمات این domain هنوز KVM type رو نشون نمی‌ده. XML و libvirt logs رو بررسی و با شاهد همون VM تعمیر کن.

Host capability appears available; this domain’s config does not show KVM type. Inspect XML and libvirt logs, then repair this VM based on evidence.

۱۳. کاربر به libvirt گروه اضافه شد

`usermod -aG libvirt` اجرا شد، ولی `id` در terminal قدیمی گروه رو نشون نمی‌ده. چه می‌کنی؟

`usermod -aG libvirt` ran, but `id` in the old terminal does not show the group. What now?

پاسخ

عضویت گروه برای نشست ورود جدید هست؛ دوباره login کن و بعد بررسی. قبل از اون مطمئن شو این امتیاز system-wide برای کاربر مناسب هست.

Group membership applies to a new login session; log in again and verify. First ensure system-wide VM privilege is appropriate for that user.

۱۴. QEMU روی معماری دیگر

می‌خوای ARM guest روی x86 host بدون سخت‌افزار پشتیبانی اجرا بشه. انتظار چه tradeoffی داری؟

You want an ARM guest on x86 without matching hardware support. What trade-off do you expect?

پاسخ

QEMU ممکنه TCG instructionها رو emulate کند؛ compatibility معماری بیشتر می‌شه ولی CPU throughput می‌تونه پایین‌تر باشه. نسخه/target و بار کاری رو بررسی کن.

QEMU may use TCG to emulate instructions, broadening architecture compatibility but reducing CPU throughput. Check target/version and workload.

۱۵. nested KVM

KVM داخل یک cloud VM می‌خوای، ولی `/dev/kvm` absent هست. آیا `apt install qemu-kvm` حتماً کافیه؟

You need KVM inside a cloud VM, but `/dev/kvm` is absent. Is `apt install qemu-kvm` definitely enough?

پاسخ

نه؛ provider باید nested virtualization رو در اختیار guest بذاره. بسته‌ها kernel یکپارچه‌سازی رو فراهم می‌کنن، ولی قابلیت پنهان‌شده رو نه.

No; the provider must expose nested virtualisation. Packages provide software integration but cannot reveal hidden extensions.

۱۶. GUI به root اجرا شد

برای حل مجوز خطا، `sudo virt-manager` اجرا می‌کنی. چرا انتخاب بدی هست؟

You run `sudo virt-manager` to solve a permission error. Why is this a poor choice?

پاسخ

GUI با اختیار root فایل‌ها و display/socketهای کاربر رو می‌بینه و ممکنه ownership ناخواسته بسازد. URI، group/ACL و daemon دسترسی رو درست تشخیص بده.

The GUI now has root access to user files and display/sockets and may create ownership problems. Diagnose URI, group/ACL, and daemon access correctly.

۱۷. session یا system برای سرور؟

VM آزمایشگاهی باید بعد از logout کاربر همچنان مدیریت‌پذیر باشه و از NAT سیستمی استفاده کنه. کدوم URI رو بررسی می‌کنی؟

A lab VM must remain manageable after a user logs out and use system NAT. Which URI do you inspect?

پاسخ

`qemu:///system` معمولاً مناسب‌تر هست؛ privilege و ownership بالاتر داره، پس دسترسی رو محدود کن. تأیید کن `virsh uri` واقعاً به اون وصل هست.

`qemu:///system` is usually the closer fit, with greater privilege/ownership implications. Restrict access and confirm the active URI.

۱۸. incident از چهار شاهد

domain start خراب می‌شه؛ `lsmod` module داره، `/dev/kvm` موجود هست، `id` مجوز رو نداره و `virsh uri` روی session هست. علت محتمل و بررسی رو بنویس.

Domain startup fails; `lsmod` shows modules, `/dev/kvm` exists, `id` lacks access, and `virsh uri` is session. State a likely cause and verification.

معیار پاسخ

capability kernel حاضر هست، ولی کاربر دسترسی و URI با system domain/مجوز لازم جور نیست. سیاست دسترسی مجاز رو بررسی کن، session تازه بساز و به URI هدف وصل شو؛ سپس `virsh list`, `dominfo` و guest boot رو تکرار کن.

Kernel capability exists, but user access and URI do not match the intended system domain. Check approved access policy, start a fresh session, connect to the intended URI, then repeat `virsh list`, `dominfo`, and guest boot checks.

سرعت رو از مسیر تشخیص بده، نه از اسم ابزارDiagnose performance from the execution path, not the tool’s name

QEMU guest رو می‌سازه و دستگاه‌ها رو مدل می‌کنه؛ KVM می‌تونه اجرای CPU رو با kernel و سخت‌افزار شتاب بده؛ libvirt منابع و چرخهٔ عمر رو مدیریت می‌کنه؛ virt-manager و virsh همون مجموعهٔ ابزارها رو از دو رابط نشون می‌دن. بسته نصب‌شده، module loadشده و VM روشن‌شده هرکدام ادعای جدا هستن—با مدرک مناسب وصلشان کن.

QEMU creates the guest model and devices; KVM can accelerate CPU execution through the kernel and hardware; libvirt manages resources and lifecycle; virt-manager and virsh expose the same stack through different interfaces. Installed packages, loaded modules, and a running VM are separate claims—connect them with evidence.

از اینجا به بعد اگه VM کند شد، دیگه جوابمون «KVM مشکل داره» نیست. می‌پرسیم دقیقاً کدوم لایه و کدوم منبع درگیره. فصل بعد همین سؤال رو با CPU، RAM و دیسک دنبال می‌کنیم.

Next we tune VM resources: CPU, memory, disk, and overcommit. When a guest feels slow, you will not blame everything on KVM—you will ask which boundary and resource is actually constrained.
