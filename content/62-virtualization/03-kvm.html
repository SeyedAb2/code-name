VM ساخته شده، اما کند است—و معلوم نیست اصلاً KVM استفاده می‌شودA VM exists, but it is slow—and you are not sure KVM is active

در VirtualBox ماشین ساختی. روی Linux host می‌خواهی از KVM/QEMU استفاده کنی؛ نصب packageها تمام شده، اما `virt-manager` باز نمی‌شود یا guest با سرعت عجیبی اجرا می‌شود. قبل از تغییر CPU/RAM بپرس: QEMU اجرا شده؟ KVM در kernel حاضر است؟ کاربر اجازه دارد به آن دسترسی بگیرد؟

You created a VM in VirtualBox. On a Linux host you want KVM/QEMU; packages installed, but virt-manager will not connect or the guest runs unusually slowly. Before changing CPU or memory, ask: is QEMU running, is KVM available in the kernel, and is your user allowed to access it?

اسم این stack را مثل چهار قطعه بخوان، نه چهار نام برای یک برنامه: QEMU مدل ماشین و deviceها را می‌سازد؛ KVM قابلیت virtualization داخل Linux kernel است؛ libvirt API و lifecycle را مدیریت می‌کند؛ `virt-manager` و `virsh` رابط‌های کاربرند. اگر یک قطعه fail شود، بقیه ممکن است هنوز نصب باشند ولی VM درست بالا نیاید.

Read the stack as four components, not four names for one program: QEMU provides a machine and device model; KVM is the Linux kernel virtualisation facility; libvirt manages the API and lifecycle; `virt-manager` and `virsh` are user-facing tools. One component can fail while the others remain installed.

فلش‌های بالا درخواست مدیریت را نشان می‌دهند؛ مسیر پایین دسترسی QEMU به KVM و CPU را. QEMU حذف نمی‌شود—KVM شتاب‌دهندهٔ آن است.

Top arrows show management requests; the lower path shows QEMU’s access to KVM and the CPU. KVM accelerates QEMU; it does not replace it.

QEMU می‌تواند بدون KVM هم اجرا شود؛ اما همان کار را نمی‌کندQEMU can run without KVM—but not in the same way

QEMU یک machine model کامل دارد: CPU، memory و deviceهای emulated. روی Linux سازگار می‌تواند برای اجرای guest روی CPU میزبان از KVM استفاده کند. اگر شتاب‌دهنده در دسترس نباشد، QEMU ممکن است از TCG برای emulation استفاده کند؛ این حالت برای معماری‌های متفاوت هم مفید است، اما معمولاً کندتر است. QEMU با TCG «خراب» نیست؛ فقط مسیر اجرا متفاوت است.

QEMU provides a machine model with emulated CPUs, memory, and devices. On a compatible Linux host, it can use KVM to run guest CPU work with hardware assistance. Without an accelerator, QEMU may use TCG emulation, which can support different architectures but is generally slower. QEMU with TCG is not broken; it is using a different execution path.

KVM به virtualization extensions و `/dev/kvm` وابسته است. روی Intel معمولاً ماژول `kvm_intel` و روی AMD `kvm_amd` کنار `kvm` دیده می‌شود؛ نام‌ها و دسترس‌پذیری با architecture فرق می‌کند. وجود module در `lsmod` به‌تنهایی ثابت نمی‌کند کاربر مجوز دارد یا guest با KVM accelerator ساخته شده.

KVM depends on virtualisation extensions and `/dev/kvm`. Intel systems commonly show `kvm_intel`; AMD commonly shows `kvm_amd`, alongside `kvm`. Names and availability vary by architecture. A loaded module alone does not prove the user has access or a guest is using KVM acceleration.

libvirt به تو storage pool، network و domain می‌دهد. domain یعنی تعریف و چرخهٔ عمر یک VM؛ XML آن CPU، RAM، disk، NIC و deviceها را شرح می‌دهد. Storage pool مکانی برای managed diskهاست؛ network مثل default NAT می‌تواند guest را بیرون ببرد. این مفاهیم را می‌توان با GUI دید و با `virsh` بررسی کرد.

libvirt exposes storage pools, networks, and domains. A domain is the definition and lifecycle of a VM; its XML describes CPU, memory, disks, NICs, and devices. A storage pool manages disk volumes; a network such as the default NAT network connects guests outward. You can inspect these concepts in a GUI or with `virsh`.

اول شاهد جمع کن: extension، module و deviceCollect evidence first: extensions, module, and device

روی Ubuntu/Debian host این بررسی‌ها را پیش از نصب یا دستکاری انجام بده. `kvm-ok` از بستهٔ `cpu-checker` سرنخی دربارهٔ hardware support می‌دهد؛ `lsmod` دربارهٔ moduleهای loadشده؛ `/dev/kvm` و mode/owner دربارهٔ device node. هیچ‌کدام به‌تنهایی دسترسی کامل به VM را ثابت نمی‌کنند.

On an Ubuntu/Debian host, run these checks before installing or changing anything. `kvm-ok` from `cpu-checker` reports hardware-support clues; `lsmod` shows loaded modules; `/dev/kvm` and its mode/owner show the device node. None alone proves complete VM access.

lscpu | grep -i virtualization
lsmod | grep -E '^kvm|^kvm_'
ls -l /dev/kvm
id

دنبال VT-x/AMD-V (یا extension معماری خودت)، module مناسب، و `/dev/kvm` بگرد. اگر node وجود ندارد، firmware یا host بالادستی را بررسی کن؛ اگر هست ولی permission رد می‌شود، mode/group/ACL و عضویت login session را بسنج. `chmod 666 /dev/kvm` راه‌حل امن نیست—دسترسی اجرای VM را به همهٔ کاربران باز می‌کند.

Look for the host’s virtualisation extension, relevant modules, and `/dev/kvm`. If the node is missing, investigate firmware or the upstream host; if it exists but permission is denied, inspect mode/group/ACL and the current login session. `chmod 666 /dev/kvm` is not a safe fix—it grants every local user VM access.

برای host تازه، مسیر Ubuntu معمولاً با `qemu-kvm`, `libvirt-daemon-system`, `virt-manager` و ابزار بررسی `cpu-checker` شروع می‌شود. نام بسته و daemon در distroهای دیگر فرق دارد. پس از نصب، `virsh -c qemu:///system list --all` را اجرا کن؛ اتصال موفق به system libvirt را ثابت می‌کند، نه فعال‌بودن acceleration هر VM.

On a fresh Ubuntu host, a common starting set is `qemu-kvm`, `libvirt-daemon-system`, `virt-manager`, and `cpu-checker`. Package and daemon names differ on other distributions. After installation, `virsh -c qemu:///system list --all` tests the system libvirt connection; it does not prove each VM uses acceleration.

sudo apt update
sudo apt install qemu-kvm libvirt-daemon-system virt-manager cpu-checker
kvm-ok
virsh -c qemu:///system list --all

خروجی `kvm-ok` که می‌گوید KVM acceleration can be used یک آزمون capability است. اگر `virsh` permission denied داد، خود متن خطا، connection URI و `id` را ثبت کن؛ با `sudo virt-manager` دورش نزن. کاربر privileged می‌تواند VM و network سطح سیستم را تغییر دهد.

A `kvm-ok` message that KVM acceleration can be used is a capability check. If `virsh` reports permission denied, record the error, connection URI, and `id`; do not bypass it with `sudo virt-manager`. A privileged user can alter system-wide VMs and networks.

دو اتصال libvirt ممکن است دو جهان متفاوت ببینندTwo libvirt connections may see different worlds

`qemu:///system` به daemon سیستمی و منابع مشترک host وصل می‌شود؛ `qemu:///session` به VMهای user فعلی و منابع همان user. `virsh uri` می‌گوید CLI الان به کدام connection وصل است. اگر `virt-manager` فهرست خالی نشان می‌دهد، شاید نه VMها گم شده‌اند و نه نصب خراب است—ممکن است GUI به URI دیگری وصل باشد.

`qemu:///system` connects to the system daemon and host-wide resources; `qemu:///session` manages the current user’s VMs and resources. `virsh uri` reports the CLI’s active connection. If virt-manager shows an empty list, VMs may not be missing and installation may be fine—the GUI could be connected to another URI.

virsh uri
virsh -c qemu:///system list --all
virsh -c qemu:///session list --all

اگر user را به گروه `libvirt` اضافه می‌کنی، این یک امتیاز مدیریتی مهم است؛ فقط کاربری را عضو کن که به hostهای مجازی و شبکه‌های system-wide اعتماد داری. در بعضی Ubuntuها عضو sudo دسترسی مناسب می‌گیرد و نیازی به تغییر گروه نیست؛ سیاست distro و ACL package را بررسی کن. عضویت گروه پس از logout/login تازه می‌شود، نه لزوماً در shell فعلی.

Adding a user to the `libvirt` group is a significant administrative privilege; grant it only to users trusted with system-wide VMs and networks. Some Ubuntu setups grant suitable access to sudo users already, so inspect the distro’s policy rather than changing groups automatically. Group membership may require a new login session.

برای status daemon در نصب‌های جدید libvirt ممکن است unitها modular و socket-activated باشند؛ به‌جای فرض یک اسم واحد مثل `libvirtd`، `systemctl list-units '*libvirt*'` و `virsh uri` را با نسخهٔ سیستم خودت تطبیق بده.

Recent libvirt installations may use modular, socket-activated units. Instead of assuming one service name such as `libvirtd`, inspect `systemctl list-units '*libvirt*'` and `virsh uri` on your system.

اولین domain را با virt-manager بساز؛ بعد با virsh بخوانCreate the first domain in virt-manager, then inspect it with virsh

روی Linux workstation با GUI، `virt-manager` را باز و connection `QEMU/KVM – system` را انتخاب کن. New VM را بساز، Ubuntu ISO بده، ۲ vCPU و RAM متناسب با host انتخاب کن و disk را در pool پیش‌فرض ذخیره کن. Network default معمولاً NAT است؛ interface `default` باید active باشد. Wizard مقدارها را نشان می‌دهد، اما install موفق را فقط guest boot ثابت می‌کند.

On a Linux workstation with a GUI, open virt-manager and select `QEMU/KVM – system`. Create a VM, choose an Ubuntu ISO, assign 2 vCPUs and host-appropriate memory, and store the disk in the default pool. The default network is commonly NAT; network `default` should be active. The wizard displays settings, but only a booted guest proves installation.

اگر host server بدون GUI است، از `virt-install` استفاده یا virt-manager را از workstation از راه SSH به libvirt host وصل کن. GUI را روی production server نصب‌کردن لازم نیست. دوربین، USB و shared path را اضافه نکن مگر پروژه واقعاً نیاز داشته باشد.

On a headless server, use `virt-install` or connect virt-manager from a workstation to the libvirt host over SSH. A production server does not need a desktop GUI. Do not add camera, USB, or shared paths unless the project needs them.

پس از install، نام domain را از `virsh list --all` بردار و مشخصات را بخوان:

After installation, get the domain name from `virsh list --all` and inspect its details:

virsh list --all
virsh dominfo lab-kvm
virsh dumpxml lab-kvm
virsh pool-list --all
virsh net-list --all

`dominfo` state و مقدار منابع را می‌گوید؛ `dumpxml` نشان می‌دهد interface به چه network وصل است و disk کجا قرار دارد؛ pool و network list مدیریت منابع libvirt را نشان می‌دهند. این‌ها config را ثابت می‌کنند، نه اینکه route یا اینترنت داخل guest حتماً کار می‌کند؛ داخل guest `ip -br address` و `ip route` را هم بخوان.

`dominfo` reports state and resource settings; `dumpxml` shows the network attachment and disk path; pool/network listings reveal managed resources. These establish configuration, not that guest routes or internet work; inspect `ip -br address` and `ip route` inside the guest too.

از کجا بفهمیم این domain واقعاً KVM است؟How do we know this domain actually uses KVM?

فقط دیدن CPU usage یا سرعت boot کافی نیست. libvirt domain XML برای VM شتاب‌گرفته معمولاً `` دارد؛ QEMU process هم بالا است و دسترسی `/dev/kvm` لازم است. `virsh dumpxml` config انتخاب‌شده را نشان می‌دهد؛ `/dev/kvm` و moduleها capability میزبان را؛ با هم نتیجهٔ قوی‌تری می‌دهند.

CPU usage or boot speed alone is not proof. A libvirt XML domain configured for accelerated KVM commonly has ``; a QEMU process is still present and needs `/dev/kvm`. `virsh dumpxml` shows the configured domain type; `/dev/kvm` and modules show host capability. Together they provide stronger evidence.

virsh dumpxml lab-kvm | grep -m1 '<domain type='
ps -eo pid,comm,args | grep '[q]emu-system'
ls -l /dev/kvm

اگر XML نوع `qemu` یا domain start log دربارهٔ KVM خطا دارد، guest ممکن است به emulation/مسیر دیگری رفته باشد. برای اندازه‌گیری performance یک عدد ثابت نداریم: workload، disk، memory و device model اثر دارند. QEMU با TCG مفید است ولی CPU emulation معمولاً کندتر است؛ عملکرد را با workload یکسان بسنج، نه با یک حس کلی.

If XML uses type `qemu` or startup logs mention KVM errors, the guest may be using emulation or another path. There is no universal performance number: workload, disk, memory, and device model matter. QEMU with TCG remains useful but CPU emulation is generally slower; compare the same workload instead of relying on impressions.

خرابی عمدی: KVM نصب است، ولی دسترسی denied می‌شودDeliberate failure: KVM is installed, but access is denied

در یک Linux VM تو‌در‌تو یا host lab، عضو گروهی با دسترسی به `/dev/kvm` نباش. قبل از repair، `lsmod`, `ls -l /dev/kvm`, `id`, `virsh uri` و خطای `virsh list` را جمع کن. سؤال این است: module نیامده، device وجود ندارد، یا فقط مجوز session کم است؟

On a nested Linux VM or lab host, use an account without access to `/dev/kvm`. Before repair, capture `lsmod`, `ls -l /dev/kvm`, `id`, `virsh uri`, and the `virsh list` error. Is the module missing, the device absent, or only the session permission wrong?

اگر device node هست ولی permission رد می‌شود، mode/group/ACL و اتصال system/session را بخوان. راه امن، استفاده از policy مجاز همان distro—برای user مورداعتماد—و آغاز login session تازه است. mode را به `666` تغییر نده و GUI را با root اجرا نکن؛ این کار تشخیص را پنهان می‌کند و access را بی‌جهت گسترش می‌دهد.

If the node exists but access is denied, inspect mode/group/ACL and whether the client uses system or session libvirt. Use the distro’s intended policy for a trusted account and start a fresh login session. Do not chmod the device to `666` or run the GUI as root; that hides the diagnosis and expands access needlessly.

اگر `/dev/kvm` وجود ندارد یا `kvm-ok` می‌گوید unavailable، module و kernel log را ببین، بعد firmware virtualization و اگر host خودش VM است nested virtualization را بررسی کن. نصب مجدد `virt-manager` extension گم‌شدهٔ CPU را جادویی اضافه نمی‌کند.

If `/dev/kvm` is absent or `kvm-ok` reports unavailable, inspect modules and kernel logs, then check firmware virtualisation and nested-virtualisation exposure if the host is itself a VM. Reinstalling virt-manager cannot reveal hidden CPU extensions.

lab: یک domain، سه نوع شاهدLab: one domain, three kinds of evidence

روی workstation لینوکسی آزمایشگاهی، ابتدا capability میزبان را ثبت کن: extension، module، `/dev/kvm` و access user. اگر host KVM ندارد، این بخش را روی VM nested disposable یا Linux host واقعی انجام بده؛ به‌زور setting host را تغییر نده. سپس packageهای Ubuntu را نصب و از virt-manager VM Ubuntu بساز.

On a Linux lab workstation, record host capability first: extensions, modules, `/dev/kvm`, and user access. If the host lacks KVM, use a disposable nested VM or a real Linux host; do not force host settings. Install Ubuntu packages and create an Ubuntu guest with virt-manager.

پس از boot، سه لایه را جدا ثبت کن: host `lsmod` و `/dev/kvm`؛ libvirt `virsh dominfo` و `dumpxml`; guest `uname -r`, `ip -br address` و `ip route`. این گزارش نشان می‌دهد KVM برای host حاضر است، domain چه نوعی دارد و guest خودش چه می‌بیند. یک خط سبز به‌تنهایی کافی نیست.

After boot, capture three layers separately: host `lsmod` and `/dev/kvm`; libvirt `virsh dominfo` and `dumpxml`; guest `uname -r`, `ip -br address`, and `ip route`. This shows host KVM availability, domain type, and guest view. One green line alone is not enough.

برای failure، حسابی با permission محدود یا lab nestedای انتخاب کن که `/dev/kvm` را پنهان می‌کند. خروجی‌ها را مقایسه کن و تشخیص بده مشکل permission است یا capability. سپس فقط اگر account مورداعتماد است، policy مجاز را به‌کار بگیر؛ logout/login کن و `virsh` را دوباره اجرا کن. نصب packageها را از اول تکرار نکن مگر شاهد package missing باشد.

For failure, use an account without the required permission or a nested lab hiding `/dev/kvm`. Compare outputs and decide whether the issue is access or capability. Apply the intended policy only for a trusted account, log in again, and rerun `virsh`. Do not reinstall packages unless evidence shows they are missing.

۱۸ تمرین؛ QEMU، KVM یا libvirt؟18 exercises: QEMU, KVM, or libvirt?

۱. QEMU یا KVM؟

می‌خواهی guest CPU را شتاب بدهی ولی deviceهای مجازی را هم لازم داری. هر قطعه چه نقشی دارد؟

You need accelerated guest CPU execution and virtual devices. What does each component do?

پاسخ

KVM مسیر kernel/hardware acceleration را می‌دهد؛ QEMU machine/device model را نگه می‌دارد و با KVM همکاری می‌کند.

KVM provides the kernel/hardware acceleration path; QEMU retains the machine/device model and works with it.

۲. QEMU بدون KVM

`/dev/kvm` نیست، ولی QEMU guest را boot می‌کند. چه توضیحی محتمل است؟

There is no `/dev/kvm`, but QEMU boots a guest. What is a likely explanation?

پاسخ

ممکن است TCG/CPU emulation استفاده شود. این نشان نمی‌دهد KVM فعال است؛ domain type، QEMU args/log و کارایی را بررسی کن.

It may be using TCG/CPU emulation. That does not mean KVM is active; inspect domain type, QEMU arguments/logs, and performance.

۳. `lsmod` خالی

`lsmod | grep kvm` هیچ outputی ندارد. کدام دو عامل را پیش از نصب مجدد بررسی می‌کنی؟

`lsmod | grep kvm` prints nothing. Which two factors do you check before reinstalling?

پاسخ

آیا module به‌تازگی load نشده یا kernel/CPU extension/firmware اجازه نمی‌دهد؟ `modprobe` log، `kvm-ok`, `lscpu` و kernel log را ببین.

Is the module simply not loaded, or do kernel/CPU extensions/firmware prevent it? Check `modprobe` output, `kvm-ok`, `lscpu`, and kernel logs.

۴. device هست، ولی permission denied

`/dev/kvm` وجود دارد و mode آن `crw-rw---- root kvm` است. کاربر خطای permission می‌گیرد. قدم بعد چیست؟

`/dev/kvm` exists with mode `crw-rw---- root kvm`. The user gets permission denied. What next?

پاسخ

`id`, ACL و login session را ببین؛ membership تازه شاید هنوز اعمال نشده. `chmod 666` نزن و فقط access policy مجاز را به user مورداعتماد بده.

Inspect `id`, ACL, and login session; new group membership may not be active. Do not chmod to `666`; grant only the approved access policy to a trusted user.

۵. دو URI

`qemu:///session` فهرست خالی دارد ولی `qemu:///system` domain نشان می‌دهد. VM گم شده است؟

`qemu:///session` is empty while `qemu:///system` shows a domain. Is the VM missing?

پاسخ

احتمالاً نه؛ دو connection منابع جدا می‌بینند. `virsh uri` را بخوان و virt-manager را به URI هدف وصل کن.

Probably not; the two connections expose different resources. Check `virsh uri` and connect virt-manager to the intended URI.

۶. libvirt یا QEMU؟

`virsh list --all` connect نمی‌شود و `qemu-system` process هم نیست. کدام لایه را اول بررسی می‌کنی؟

`virsh list --all` cannot connect and no `qemu-system` process exists. Which layer do you inspect first?

پاسخ

URI و daemon/socket libvirt؛ اگر VM اصلاً start نشده، نبودن QEMU process طبیعی است. ابتدا error و connection URI را ببین.

Check the URI and libvirt daemon/socket; if the VM never started, no QEMU process is expected. Start with the error and connection URI.

۷. domain

`virsh list --all` یک `Shut off` domain نشان می‌دهد. آیا disk هم حذف شده؟

`virsh list --all` shows a `Shut off` domain. Was its disk deleted?

پاسخ

نه؛ lifecycle state خاموش است. `dominfo`, `dumpxml` و disk source را ببین؛ خاموش‌بودن مساوی حذف نیست.

No; the domain is powered off. Inspect `dominfo`, `dumpxml`, and disk source; shutoff does not mean deletion.

۸. storage pool غیرفعال

VM start نمی‌شود و XML disk source در pool پیش‌فرض است؛ `pool-list --all` آن را inactive نشان می‌دهد. چه رابطه‌ای محتمل است؟

The VM will not start; its disk source is in the default pool, which `pool-list --all` shows as inactive. What is a likely relationship?

پاسخ

libvirt pool برای مدیریت volumeهاست و ممکن است pool mount/path در دسترس نباشد. pool info و path/permissions را بخوان؛ disk را از نو نساز.

The libvirt pool manages volumes and its path/mount may be unavailable. Inspect pool info and path/permissions; do not recreate the disk.

۹. network default inactive

guest boot می‌شود ولی IP نمی‌گیرد؛ `net-list --all` default را inactive نشان می‌دهد. این چه فرضیه‌ای می‌سازد؟

The guest boots but gets no IP; `net-list --all` shows default inactive. What hypothesis does this create?

پاسخ

NAT/DHCP network libvirt اجرا نیست. network info/autostart/state را بررسی کن؛ guest boot شدن ثابت نمی‌کند NIC network فعال است.

۱۶. GUI به root اجرا شد

GUI با اختیار root فایل‌ها و display/socketهای user را می‌بیند و ممکن است ownership ناخواسته بسازد. URI، group/ACL و daemon access را درست تشخیص بده.

۱۷. session یا system برای server؟

VM آزمایشگاهی باید پس از logout کاربر همچنان مدیریت‌پذیر باشد و از NAT سیستمی استفاده کند. کدام URI را بررسی می‌کنی؟

A lab VM must remain manageable after a user logs out and use system NAT. Which URI do you inspect?

پاسخ

`qemu:///system` معمولاً مناسب‌تر است؛ privilege و ownership بالاتر دارد، پس access را محدود کن. تأیید کن `virsh uri` واقعاً به آن وصل است.

`qemu:///system` is usually the closer fit, with greater privilege/ownership implications. Restrict access and confirm the active URI.

۱۸. incident از چهار شاهد

domain start fail می‌شود؛ `lsmod` module دارد، `/dev/kvm` موجود است، `id` مجوز را ندارد و `virsh uri` روی session است. علت محتمل و verification را بنویس.

Domain startup fails; `lsmod` shows modules, `/dev/kvm` exists, `id` lacks access, and `virsh uri` is session. State a likely cause and verification.

معیار پاسخ

capability kernel حاضر است، اما user access و URI با system domain/permission لازم جور نیست. policy دسترسی مجاز را بررسی کن، session تازه بساز و به URI هدف وصل شو؛ سپس `virsh list`, `dominfo` و guest boot را تکرار کن.

Kernel capability exists, but user access and URI do not match the intended system domain. Check approved access policy, start a fresh session, connect to the intended URI, then repeat `virsh list`, `dominfo`, and guest boot checks.

سرعت را از مسیر تشخیص بده، نه از اسم ابزارDiagnose performance from the execution path, not the tool’s name

QEMU guest را می‌سازد و deviceها را مدل می‌کند؛ KVM می‌تواند اجرای CPU را با kernel و hardware شتاب بدهد؛ libvirt منابع و lifecycle را مدیریت می‌کند؛ virt-manager و virsh همان stack را از دو رابط نشان می‌دهند. package نصب‌شده، module loadشده و VM روشن‌شده هرکدام ادعای جدا هستند—با مدرک مناسب وصلشان کن.

QEMU creates the guest model and devices; KVM can accelerate CPU execution through the kernel and hardware; libvirt manages resources and lifecycle; virt-manager and virsh expose the same stack through different interfaces. Installed packages, loaded modules, and a running VM are separate claims—connect them with evidence.

در فصل بعد منابع VM را تنظیم می‌کنیم: CPU، RAM، disk و overcommit. وقتی حالا کندی می‌بینی، دیگر همه‌چیز را به KVM نسبت نمی‌دهی؛ می‌پرسی کدام مرز و کدام resource واقعاً مشغول است.

Next we tune VM resources: CPU, memory, disk, and overcommit. When a guest feels slow, you will not blame everything on KVM—you will ask which boundary and resource is actually constrained.
