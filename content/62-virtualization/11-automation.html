این VM رو دفعهٔ بعد چطور دوباره می‌سازی؟How will you rebuild this VM next time?

روی لپ‌تاپت یک Ubuntu VM کار می‌کنه: دو CPU، شبکهٔ خصوصی، یک بسته نصب‌شده و یک فایل تنظیم. می‌خوای برای هم‌تیمی‌ات هم بسازی. می‌گی «مثل دفعهٔ قبل کلیک کن». او می‌پرسه: کدوم ISO؟ کدوم IP؟ کدوم کاربر؟ فایل کجا بود؟ این‌ها رو از تصویر نمی‌شه مطمئن فهمید.

An Ubuntu VM works on your laptop: two CPUs, private networking, a package, and a config file. You want a teammate to recreate it and say, “Click like I did.” They ask: which ISO, which IP, which user, and where was the file? Screenshots cannot answer reliably.

اینجا دو ابزار با دو مسئولیت متفاوت داریم. Vagrant محیط VM رو تعریف و چرخهٔ عمر اون رو مدیریت می‌کنه؛ cloud-init داخل guest، دادهٔ آغازین رو می‌خونه و تنظیم‌هایی مثل کاربر یا بسته رو در boot انجام می‌ده. ممکنه یک پروژه فقط یکی رو به‌کار ببرد. در این فصل هر دو رو جدا می‌آزماییم تا مرزشان معلوم بمونه.

Two tools have different jobs here. Vagrant describes the VM environment and manages its lifecycle; cloud-init reads instance data inside the guest and applies first-boot settings such as users or packages. A project may use either one alone. We will test both separately so their boundary stays clear.

دو لایهٔ خودکارسازی، یک ماشینTwo automation layers, one machine

Vagrantfile می‌گه چه box و providerای به‌کار بره، چند ماشین بسازد و شبکه/پوشه‌ها چه باشن. provider جزئیات ماشین مجازی رو می‌سازه. cloud-init در خود guest، کاربر-data و meta-data رو از یک datasource می‌گیره؛ datasource می‌تونه cloud، دیسک seed یا محیط دیگری باشه. صرف نصب cloud-init تضمین نمی‌کنه در هر VM داده‌ای به دستش برسه.

A Vagrantfile selects a box and provider, machine count, networking, and folders. The provider creates the VM. Inside the guest, cloud-init obtains user-data and meta-data from a datasource such as a cloud API, seed disk, or another environment. Merely installing cloud-init does not guarantee that every VM supplies it with data.

اول ماشین رو از روی Vagrantfile بسازFirst, create a VM from a Vagrantfile

یک پوشهٔ تازه برای پروژه بساز و داخلش فایل Vagrantfile قرار بده. نمونهٔ زیر یک Ubuntu box، دو CPU، شبکهٔ خصوصی با DHCP و یک port-forward محدود به loopback host تعریف می‌کنه. box نام و نسخه داره؛ فهرست و provider رو برای سیستم خودت بررسی کن و در پروژهٔ تیمی نسخه رو pin کن. اسم provider می‌تونه با نصب‌ها فرق کنه.

Create a clean project directory with a Vagrantfile. This example selects an Ubuntu box, two CPUs, a private DHCP network, and a port forward bound to host loopback. Boxes are versioned artifacts; check the catalog and provider for your platform, and pin a version in team projects. Provider names vary by installation.

Vagrant.configure("2") do |config|
  config.vm.box = "ubuntu/jammy64"
  config.vm.network "private_network", type: "dhcp"
  config.vm.network "forwarded_port",
    guest: 8080, host: 18080, host_ip: "127.0.0.1"
  config.vm.provider "virtualbox" do |vb|
    vb.cpus = 2
    vb.memory = 2048
  end
end

اگه VirtualBox provider نداری، همین خط بی‌دلیل اون رو نصب نمی‌کنه؛ Vagrant و provider نرم‌افزارهای جدا هستن. قبل از ساخت ماشین، vagrant validate خطای syntax ساده رو می‌گیره. سپس vagrant up box رو می‌آورد و provider رو صدا می‌زند؛ دانلود اولیه ممکنه طول بکشه.

If the VirtualBox provider is missing, this line does not install it; Vagrant and providers are separate software. Run vagrant validate to catch basic syntax errors, then vagrant up downloads the box if needed and calls the provider. The first download can take time.

vagrant validate
vagrant up
vagrant status
vagrant ssh

در وضعیت دنبال ماشین فعال بگرد؛ با ssh وارد guest شو و hostnamectl یا ip -br address رو ببین. این ثابت می‌کنه VM بالا آمده و می‌تونی به اون وصل شوی؛ هنوز ثابت نمی‌کنه تنظیمات برنامه یا شبکهٔ موردنظرت درست‌اند. اگه provider خطا داد، اول provider نصب‌شده، virtualization میزبان و پیام دقیق رو بررسی کن.

In status, look for a running machine; use SSH to enter the guest and inspect hostnamectl or ip -br address. This proves the VM started and is reachable, not that application or network configuration is correct. If the provider fails, inspect the installed provider, host virtualization support, and exact error.

شبکه و پوشهٔ مشترک هم تصمیم‌اندNetworking and shared folders are also choices

Vagrant معمولاً برای ارتباط خودش به guest یک مسیر NAT نگه می‌داره؛ خصوصی شبکه راهی برای دسترسی خصوصی یا ارتباط ماشین‌هاست و رفتار دقیق به provider/OS بستگی داره. IP ثابت رو از subnet همسایه انتخاب نکن. اگه فقط از host به web آزمایشگاهی می‌رسی، port-forward روی 127.0.0.1 exposure رو محدودتر از bind روی همهٔ interfaceها نگه می‌داره.

Vagrant generally keeps a NAT path for guest communication; a private network offers private access or machine-to-machine connectivity, with details depending on provider and OS. Do not choose a static address that overlaps another subnet. If only the host needs to reach a lab web service, forwarding on 127.0.0.1 limits exposure compared with binding all interfaces.

پوشهٔ پروژه معمولاً در guest به‌صورت synced folder در /vagrant دیده می‌شه. این مسیر convenience هست، نه فایل‌سیستم محیط عملیاتی: مجوز، case sensitivity، symlink، فایل watching و performance می‌تونن با host فرق کنند. دادهٔ مهم ماشین رو فقط اونجا ذخیره نکن و فایل حساس رو ناخواسته share نکن.

The project directory is commonly synced into the guest at /vagrant. This is convenient, not a production filesystem: permissions, case sensitivity, symlinks, file watching, and performance can differ from the host. Do not keep the VM’s important state only there or accidentally share secrets.

برای دیدن مرز دو طرف، در host یک فایل آزمایشی بساز و از guest بخون؛ بعد ماشین رو destroy و دوباره بساز. فایل host باید بمونه، ولی تغییر داخل فایل‌سیستم خود guest معمولاً همراه VM از بین می‌ره. قبل از vagrant destroy وضعیت و نام پروژه رو دوباره ببین؛ این دستور دیسک ماشین مدیریت‌شده رو حذف می‌کنه.

To see the boundary, create a test file on the host and read it from the guest, then destroy and recreate the VM. The host file should remain, while changes in the guest’s own filesystem are normally removed with that machine. Before vagrant destroy, verify project and status; it deletes the managed VM disk.

Provisioning: ماشین بالا هست، ولی سرویس هنوز نیستProvisioning: the VM is up, but the service is not

حالا یک مرحله به Vagrantfile اضافه می‌کنیم تا بسته و فایل نمونه نصب بشن. shell provisioner داخل guest اجرا می‌شه. نسخهٔ اول عمداً ساده هست: بسته رو نصب می‌کنه و یک خط به فایل اضافه می‌کنه. اگه provision دوباره اجرا بشه، چه اتفاقی می‌افته؟

Now add a step that installs a package and writes a sample file. The shell provisioner runs inside the guest. This first version is intentionally naive: it installs a package and appends a line. What happens when provisioning runs again?

config.vm.provision "shell", inline: <<-SHELL
  apt-get update
  apt-get install -y nginx
  echo "lab ready" | tee -a /var/tmp/lab-state.txt
SHELL

اجرای اول با vagrant up --provision انجام می‌شه؛ بار دوم همون فرمان رو تکرار کن و فایل رو بخون. اگه «lab ready» دوبار آمده، شاهد داریم که append idempotent نیست. install بسته با -y به‌تنهایی تضمین نمی‌کنه کل اسکریپت در همهٔ distroها امنِ تکرار هست.

Run it with vagrant up --provision, repeat the command, and read the file. If “lab ready” appears twice, the append is not idempotent. Installing a package with -y does not make the whole script safely repeatable across distros.

نسخهٔ اصلاح‌شده باید وضعیت مطلوب رو بسازد، نه هر بار به وضعیت قبلی چیزی بچسباند. برای فایل ساده از بازنویسی یا منطق «اگه موجود نیست» استفاده کن؛ مدیر بسته هم باید از بسته‌های declarative و قابل‌تکرار استفاده کنه. در تیم بزرگ‌تر، provisionerهای configuration management مناسب‌تر می‌شن، ولی برای این آزمایش shell کافیه.

The fixed version should converge on the desired state rather than append to whatever exists. For a simple file, overwrite it or guard creation; package installation should use declarative package-manager operations. Larger teams may prefer configuration-management provisioners, but shell is enough for this lab.

echo "lab ready" | sudo tee /var/tmp/lab-state.txt
sudo wc -l /var/tmp/lab-state.txt
sudo cat /var/tmp/lab-state.txt

بعد از اجرای تکراری باید یک خط باشه. این آزمایش روی فایل کوچک idempotence رو نشون می‌ده؛ برای تمام side effectهای اسکریپت، شبکه و بسته repository تضمین عمومی نمی‌ده. اگه خراب شد، خروجی provisioner و لاگ داخل guest رو کنار هم ببین.

After repeated provisioning, the file should contain one line. This demonstrates idempotence for a tiny file operation, not every script side effect, network call, or package repository. If it fails, inspect provisioner output and guest logs together.

cloud-init داخل guest چه می‌خونه؟What does cloud-init read inside the guest?

cloud-init هنگام آغاز guest می‌تونه از datasource، user-data و meta-data رو بگیره. کاربر-data می‌گه چه تنظیمی انجام بشه؛ meta-data هویت instance و hostname رو توصیف می‌کنه. قالب و محل رساندن این داده به محیط وابسته هست. در تمرین محلی Ubuntu cloud image، می‌توان از NoCloud seed ISO استفاده کرد؛ این روش رو با قابلیت خودکار Vagrant یکی ندان.

At guest startup, cloud-init can obtain user-data and meta-data from a datasource. User-data describes configuration; meta-data identifies the instance and hostname. Delivery format and source depend on the environment. For a local Ubuntu cloud-image exercise, use a NoCloud seed ISO; do not confuse this with built-in Vagrant cloud-init orchestration.

یک کاربر-data نمونه با header لازم cloud-تنظیمات، کاربر و عمومی key می‌سازه، nginx رو نصب و صفحه‌ای می‌نویسه. خصوصی key رو اینجا قرار نده. برای آزمایشی VM می‌توان کلید عمومی آزمایشگاهی داشت؛ در سرور واقعی اطلاعات محرمانه و دسترسی SSH رو با سیاست امن همون محیط مدیریت کن.

This user-data example declares a user and public key, installs nginx, and writes a page. Never put a private key here. A disposable VM can use a lab public key; real servers need environment-appropriate secret and SSH-access policies.

#cloud-config
users:
  - name: learner
    groups: [sudo]
    shell: /bin/bash
    sudo: ["ALL=(ALL) NOPASSWD:ALL"]
    ssh_authorized_keys:
      - ssh-ed25519 AAAA...REPLACE_WITH_YOUR_PUBLIC_KEY
ssh_pwauth: false
packages:
  - nginx
write_files:
  - path: /var/www/html/index.html
    owner: root:root
    permissions: "0644"
    content: "Hello from cloud-init"
runcmd:
  - [systemctl, enable, --now, nginx]

فایل‌های کاربر-data و meta-data رو کنار هم در پوشهٔ موقت نگه دار؛ سپس seed رو بساز:

Keep user-data and meta-data together in a temporary directory, then build the seed:

cloud-localds seed.iso user-data meta-data

sudo بدون password در این مثال فقط برای VM آزمایشی و راحتی آزمایش هست؛ برای بار کاری واقعی دسترسی رو محدودتر طراحی کن. meta-data متناظر یک instance-id تازه و hostname می‌ده. instance-id رو برای ماشین جدید عوض کن تا رفتار once-per-instance درست آزمایش بشه.

Passwordless sudo here is only for a disposable lab VM. Restrict access for real workloads. The matching meta-data supplies a new instance-id and hostname. Use a fresh instance-id for a new machine so once-per-instance behavior can be tested correctly.

instance-id: iid-lab-001
local-hostname: cloud-lab

در تمرین، Ubuntu cloud image و ابزار ساخت NoCloud seed مثل cloud-localds لازمه؛ نصب این ابزار و اتصال seed ISO به CD/DVD دوم به host و hypervisor وابسته هست. بعد از اولین boot، cloud-init status --wait و cloud-init status --long رو ببین؛ بعد کاربر، hostname، بسته و صفحهٔ nginx رو بررسی کن. وضعیت موفق فقط اجرای cloud-init رو گزارش می‌کنه، نه درستی تمام نیازهای برنامه.

This lab needs an Ubuntu cloud image and a NoCloud seed utility such as cloud-localds; installing it and attaching the seed as a second CD/DVD depends on host and hypervisor. After first boot, inspect cloud-init status --wait and cloud-init status --long, then verify user, hostname, package, and nginx page. A successful status reports cloud-init completion, not correctness of every application requirement.

برای عیب‌یابی از /var/log/cloud-init.log و /var/log/cloud-init-output.log استفاده کن و مطمئن شو image واقعاً cloud-init و datasource مورد انتظار رو داره. اجرای مجدد بی‌هدف cloud-init clean می‌تونه رفتار اولین بوت رو تغییر دهد؛ فقط روی VM آزمایشی و بعد از فهم اثرش سراغ اون برو.

For diagnosis, inspect /var/log/cloud-init.log and /var/log/cloud-init-output.log, and confirm the image contains cloud-init and supports the expected datasource. Running cloud-init clean casually changes first-boot behavior; use it only on a disposable VM after understanding the effect.

Vagrant و cloud-init رو به‌جای هم نگذارDo not substitute Vagrant for cloud-init

Vagrant از بیرون guest دستور می‌ده: box رو انتخاب کن، provider رو صدا بزن، SSH بگیر، provision رو اجرا کن و چرخهٔ عمر رو نگه دار. cloud-init داخل guest می‌دونه این instance با چه meta-data و کاربر-dataای بالا آمده. ممکنه Vagrant از cloud-init استفاده نکنه؛ ممکنه provider یا image خاصی اون رو یکپارچه کنه. قبل از طراحی، یکپارچه‌سازی همون نسخه و provider رو بررسی کن.

Vagrant orchestrates from outside the guest: choose a box, call a provider, connect over SSH, run provisioners, and manage lifecycle. cloud-init inside the guest consumes instance metadata and user-data. Vagrant may not use cloud-init; a particular provider or image may integrate it. Verify the integration for the chosen versions before designing around it.

آزمایش: ماشین رو از نو بسازLab: rebuild the machine from scratch

این دو مسیر رو جدا اجرا کن تا مرز ابزارها روشن بمونه. مسیر اول Vagrant با box/provider موجود در سیستمت هست. مسیر دوم VM مبتنی بر Ubuntu cloud image با NoCloud seed هست. اگه host یا provider تو امکان seed ISO رو نداره، همین cloud-init بخش رو در cloud/VM پشتیبانی‌شده انجام بده و محدودیت رو در تحویل بنویس؛ کاربر-data رو به‌عنوان Vagrantfile جا نزن.

Run the paths separately to keep their boundaries clear. Path one uses Vagrant with a box/provider available on your system. Path two uses an Ubuntu cloud image and NoCloud seed. If your host/provider cannot attach a seed ISO, run the cloud-init portion in a supported cloud/VM and document the limitation; do not present user-data as a Vagrantfile.

  1. در پوشهٔ خالی Vagrantfile رو بساز، syntax رو validate و یک VM بالا بیاور.
  2. Create the Vagrantfile in a clean folder, validate its syntax, and start one VM.
  3. داخل guest hostname، IP و پوشهٔ synced رو ببین؛ یک فایل host بساز و از guest بخون.
  4. Inspect hostname, IP, and synced folder; create a host file and read it in the guest.
  5. provisioner رو دو بار اجرا کن. تکرار خط رو در فایل پیدا کن؛ بعد append رو به بازنویسی/guard تبدیل و دوباره اجرا کن.
  6. Run the provisioner twice. Find duplicated lines, replace append with overwrite/guard, and rerun.
  7. یک cloud image آزمایشی و seed شامل meta-data و کاربر-data بساز؛ boot کن و cloud-init وضعیت، کاربر، بسته و صفحهٔ web رو بررسی کن.
  8. Create a disposable cloud image and seed with metadata/user-data; boot it and verify cloud-init status, user, package, and web page.
  9. ماشین Vagrant رو destroy و دوباره up کن؛ نتیجه رو با فایل تعریف مقایسه کن. فایل synced host باید باقی بمونه.
  10. Destroy and recreate the Vagrant VM; compare it with the definition. The host synced file should remain.

تحویل: Vagrantfile، کاربر-data/meta-data، خروجی validate/وضعیت، شاهد اجرای تکراری provision و یادداشت provider/datasource نسخه‌حساس.

Deliverable: Vagrantfile, user-data/meta-data, validate/status output, proof of repeated provisioning, and notes on provider/datasource caveats.

تمرین‌هاExercises

۱. ماشین بی‌فایل

چی رو در Vagrantfile ثبت می‌کنی تا VM قابل‌بازتولیدتر بشه؟

What belongs in a Vagrantfile to make a VM more reproducible?

پاسخ

box/version، provider setting، شبکه، منابع و provisioning موردنیاز؛ credential و وضعیت خصوصی رو نه.

Box/version, provider settings, networking, resources, and provisioning—not credentials or private state.

۲. box گم‌شده

Vagrant نمی‌تونه box رو پیدا کنه؛ ابتدا چه بررسی می‌کنی؟

Vagrant cannot find the box. What do you check first?

پاسخ

نام/نسخه و فهرست box، دسترسی شبکه و provider سازگار؛ متن خطای resolve رو بخون.

Check box name/version, catalog, network access, and provider compatibility; inspect the resolution error.

۳. Provider نیست

Vagrant نصب هست ولی VirtualBox provider خطا می‌ده. آیا Vagrant خودش hypervisor هست؟

Vagrant is installed but the VirtualBox provider fails. Is Vagrant itself a hypervisor?

پاسخ

نه؛ ابزار مدیریت چرخهٔ عمر هست و provider موتور ساخت VM رو فراهم می‌کنه.

No. Vagrant manages lifecycle; the provider supplies VM creation.

۴. port publish

چرا port-forward رو روی 127.0.0.1 می‌بندی؟

Why bind a forwarded port to 127.0.0.1?

پاسخ

تا دسترسی رو به host محدود کنی، نه همهٔ interfaceهای شبکه؛ provider/host رفتار رو بررسی کن.

To limit access to the host rather than all network interfaces; verify provider/host behavior.

۵. private IP

static IP در Vagrant روی subnet شبکهٔ خانه افتاده. چه خطری داره؟

A Vagrant static IP overlaps your home subnet. What can happen?

پاسخ

route/IP collision و دسترسی ناپایدار؛ subnet رو با host و شبکهٔ محلی تطبیق بده.

Routing/IP conflicts and unreliable reachability; check host and LAN ranges.

۶. synced folder

چرا /vagrant رو storage دائمی محیط عملیاتی حساب نمی‌کنی؟

Why not treat /vagrant as production persistent storage?

پاسخ

folder sync مرز host/guest هست و رفتار/مجوز/performance به provider بستگی داره؛ ماشین رو با وضعیت اون یکی نگیر.

It is a host/guest sync boundary with provider-specific permissions and performance, not the VM’s durable state.

۷. فایل host ناپدید نمی‌شه

بعد از vagrant destroy چرا فایل داخل پروژه می‌مونه؟

Why does the project file survive vagrant destroy?

پاسخ

فایل منبع روی host هست و synced folder اون رو نمایش می‌ده؛ دیسک خود guest جداست.

The source file is on the host and merely synced into the guest; the guest disk is separate.

۸. provisioning کِی اجرا شد؟

چطور provisioner رو دوباره اجرا می‌کنی بدون ساخت مجدد VM؟

How can you rerun provisioning without recreating the VM?

پاسخ

vagrant provision یا vagrant up --provision؛ خروجی رو ببین و فرض نکن هر provisioner خودکار idempotent هست.

Use vagrant provision or vagrant up --provision; inspect output and do not assume every provisioner is idempotent.

۹. append تکراری

اسکریپت هر بار به فایل خط اضافه می‌کنه. تکرارش چه ایرادی داره؟

A script appends a line on every run. What is wrong with repetition?

پاسخ

نتیجه با تعداد اجرا فرق می‌کنه؛ فایل رو به وضعیت مطلوب بازنویسی کن یا creation رو guard کن.

The result depends on run count; converge to the desired file or guard creation.

۱۰. cloud-init اجرا نشد

cloud-init نصب هست ولی کاربر ساخته نشده. سه شاهد؟

cloud-init is installed but no user was created. Three checks?

پاسخ

datasource شناسایی‌شده، کاربر-data واقعاً تحویل‌شده/اعتبار YAML، و cloud-init وضعیت/لاگ.

Detected datasource, delivered/valid user-data, and cloud-init status/logs.

۱۱. کاربر-data و meta-data

فرق نقش این دو چیست؟

What is their role difference?

پاسخ

کاربر-data تنظیم رو درخواست می‌کنه؛ meta-data اطلاعات هویت instance/محیط رو می‌ده. جزئیات وابسته به datasource هست.

User-data requests configuration; metadata describes instance/environment identity. Details depend on datasource.

۱۲. instance-id ثابت

seed تازه ساختی ولی همون instance-id رو نگه داشتی. چرا ممکنه cloud-init اون رو instance قبلی بداند؟

You made a new seed but reused the instance-id. Why might cloud-init treat it as the same instance?

پاسخ

اجرای برخی ماژول‌ها once-per-instance هست؛ برای ماشین جدید identity یکتا و رفتار datasource رو بررسی کن.

Some modules run once per instance; use a unique identity for a new machine and inspect datasource behavior.

۱۳. بسته نصب شد

cloud-init وضعیت done هست ولی nginx بالا نیست. کجا رو می‌خونی؟

cloud-init says done but nginx is down. What do you inspect?

پاسخ

وضعیت تفصیلی و لاگهای cloud-init، سپس بسته/سرویس وضعیت و system journal؛ done به معنی خدمت‌دهی موفق نیست.

Detailed status/logs, then package/service state and journal; completion does not mean the service is serving correctly.

۱۴. خصوصی key در کاربر-data

همکارت خصوصی SSH key رو داخل کاربر-data گذاشته. اصلاح چیست؟

A teammate placed a private SSH key in user-data. What is the correction?

پاسخ

کلید خصوصی رو حذف/در صورت افشا rotate کن؛ فقط عمومی key رو در این lab بذار و اطلاعات محرمانهها رو مطابق محیط امن تحویل بده.

Remove it and rotate if exposed; put only a public key in this lab and deliver secrets through the environment’s secure mechanism.

۱۵. تغییر Vagrantfile

بعد از تغییر RAM چی رو امتحان می‌کنی و چی ممکنه لازم باشه؟

After changing RAM, what do you try and what might be required?

پاسخ

reload/وضعیت رو طبق provider بررسی کن؛ برخی تغییرها نیازمند خاموشی‌اند، برخی provider-specific هستن. نتیجه رو با تنظیم واقعی VM بررسی کن.

Check reload/status for the provider; some changes require shutdown or are provider-specific. Verify the actual VM setting.

۱۶. destroy امن

قبل از destroy چی رو تأیید می‌کنی؟

What do you confirm before destroy?

پاسخ

پوشه و VM هدف، دادهٔ guest لازم، synced فایل‌ها و backup؛ دستور رو فقط در محیط پروژهٔ آزمایشی اجرا کن.

Project and target VM, needed guest data, synced files, and backups; run it only for the intended disposable environment.

۱۷. provider به‌تنهایی

Vagrantfile روی سیستم همکارت هست ولی vagrant up شکست می‌خوره. چرا فایل به‌تنهایی کافی نیست؟

A teammate has the Vagrantfile but vagrant up fails. Why is the file alone insufficient?

پاسخ

Vagrant باینری، provider سازگار، host virtualization، دسترسی box و منابع host هم لازم‌اند.

Vagrant, a compatible provider, host virtualization, box access, and host resources are also required.

۱۸. انتخاب ابزار

فقط روی cloud VM می‌سازی و provider از کاربر-data پشتیبانی می‌کنه. آیا Vagrant اجباری هست؟

You create only cloud VMs and the provider accepts user-data. Is Vagrant mandatory?

معیار پاسخ

نه؛ cloud-init می‌تونه guest رو آماده کنه و API/IaC خود cloud چرخهٔ عمر رو بسازد. Vagrant وقتی ارزش داره که workflow چند provider یا developer VM رو یکدست کند.

No. cloud-init can initialize the guest while the cloud API/IaC manages lifecycle. Vagrant helps when standardizing developer VMs or workflows across providers.

فایل تعریف جای تصویر رو می‌گیره—با چند شرطA definition file replaces screenshots—with caveats

Vagrantfile می‌گه چه VMای می‌خوای و چطور چرخهٔ عمر اون رو مدیریت کنی. cloud-init می‌گه guest در اولین بوت چه تنظیم‌هایی بگیره. box، provider، نسخه، datasource و شبکه هنوز پیش‌نیازند؛ فایل به‌تنهایی hypervisor یا منابع host تولید نمی‌کنه. provisioning رو هم تکرارپذیر بنویس و با اجرای دوباره ثابت کن.

A Vagrantfile describes the VM and its lifecycle. cloud-init describes guest initialization. Boxes, providers, versions, datasources, and network support remain prerequisites; a file does not create a hypervisor or host resources. Make provisioning repeatable and prove it by running it again.
