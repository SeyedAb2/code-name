توزیع‌های لینوکس

Linux distributions

پنج VM همگی Linux‌اند، اما package، سرویس، libc و برنامهٔ پشتیبانی‌شان یکی نیست. به‌جای جنگ سلیقه‌ها، انتخاب را به نیاز فنی وصل می‌کنیم.

Five VMs all run Linux, but their packages, services, libc, and support models differ. Instead of debating taste, we connect the choice to engineering needs.

همه Linux هستند؛ چرا فرمان یکسان کار نمی‌کند؟They all run Linux. Why does the same command fail?

روی Ubuntu با `apt install nginx` بسته نصب می‌کنی. فرمان را به Alpine می‌بری؛ `apt: not found`. بعد می‌خواهی سرویس را با `systemctl` ببینی؛ آن هم وجود ندارد. کسی می‌گوید «Alpine خراب است»، دیگری می‌گوید «Arch فقط برای حرفه‌ای‌هاست». شاید هیچ‌کدام تشخیص درستی نداشته باشند—داریم فرض‌های یک توزیع را روی توزیع دیگری اجرا می‌کنیم.

On Ubuntu you install a package with `apt install nginx`. You try the same on Alpine and get `apt: not found`. Then `systemctl` is also missing. Someone says “Alpine is broken,” someone else “Arch is only for experts.” Neither may be the right diagnosis—we are applying one distribution’s assumptions to another.

توزیع Linux فقط رنگ desktop نیست. همه از Linux kernel استفاده می‌کنند، اما userland، package format/repository، مدیر سرویس، libc، defaultهای امنیتی و چرخهٔ انتشار می‌توانند فرق کنند. اگر این اختلاف‌ها را بشناسیم، قبل از نصب تصادفی package می‌فهمیم کدام تصمیم طراحی پشت خطاست.

A Linux distribution is more than a desktop theme. They all use the Linux kernel, but userland, package formats/repositories, service managers, libc, security defaults, and release cadence can differ. Knowing those choices lets us diagnose a failed assumption before randomly installing packages.

اول اسم سیستم را بخوان، بعد دستور بدهIdentify the system before choosing commands

داخل هر VM اول `/etc/os-release` را بخوان؛ `ID` و `VERSION_ID` سیستم پایه را نشان می‌دهند. `uname -r` kernel در حال اجرا را می‌گوید، نه release توزیع؛ این دو را یکی نگیر. در guest معمولی هر VM kernel خودش را دارد؛ container برعکس، kernel میزبان را share می‌کند، موضوعی که این فصل واردش نمی‌شود.

Inside each VM, start with `/etc/os-release`; `ID` and `VERSION_ID` identify the base system. `uname -r` reports the running kernel, not the distribution release—do not confuse the two. A normal guest VM has its own kernel; a container shares the host kernel, which is beyond this chapter’s scope.

cat /etc/os-release
uname -r
cat /proc/1/comm
for x in apt-get dnf pacman apk; do command -v "$x"; done
for x in systemctl rc-service; do command -v "$x"; done
ls -l /lib/ld-linux* /lib/ld-musl* 2>/dev/null

`/proc/1/comm` نام process شمارهٔ ۱ را می‌گوید؛ در systemd معمولاً `systemd` می‌بینی، در Alpine/OpenRC process پایه می‌تواند چیز دیگری باشد. `command -v` نشان می‌دهد کدام package/service ابزار در PATH هست؛ نبودن فرمان به‌تنهایی ثابت نمی‌کند package manager خراب است—ممکن است ابزار نصب نشده یا init دیگری استفاده شود. مسیر loader سرنخی از libc می‌دهد، ولی همیشه همهٔ جزئیات ABI را تعیین نمی‌کند.

`/proc/1/comm` gives the name of process 1; with systemd it commonly says `systemd`, while Alpine/OpenRC may use another init process. `command -v` reveals which package/service tools are on PATH; a missing command alone does not mean the package manager is broken—it may be absent by design or another init may be in use. The loader path hints at libc but does not establish every ABI detail.

این بررسی read-only است؛ خروجی‌ها را برای هر VM جدا ذخیره کن. اگر prompt داخل container یا chroot است، `/etc/os-release` می‌تواند container userland را نشان دهد ولی kernel همان host باشد. قبل از تغییر، مشخص کن دقیقاً کدام environment را inspect می‌کنی.

These checks are read-only; save one result per VM. If the prompt is inside a container or chroot, `/etc/os-release` may describe its userland while the kernel still belongs to the host. Confirm which environment you are inspecting before changing anything.

These are common defaults, not promises for every image or spin; verify package manager, init, and libc on the actual image. Ubuntu and Debian both use APT but differ in repositories and release policies. Rocky belongs to the Enterprise Linux family, where minor releases, support horizon, and package ecosystem matter. Arch stays current, but partial upgrades are unsupported—`pacman -Syu` reflects its model better than installing one package alone. Alpine’s musl and BusyBox can make it small, but small does not mean every application is automatically compatible.

نسخهٔ تازه‌تر همیشه انتخاب بهتر نیستThe newest release is not always the better fit

Ubuntu نسخه‌های عادی را هر شش ماه منتشر می‌کند و LTS دورهٔ پشتیبانی طولانی‌تری دارد؛ مدت دقیق به release و نوع maintenance بستگی دارد. Debian بین stable، testing و unstable فرق می‌گذارد؛ stable برای production معمولاً پیشنهاد پروژه است، درحالی‌که testing و unstable را نباید فقط به‌خاطر package جدیدتر با stable یکی گرفت. Rocky هم برای شاخه‌های major چرخهٔ طولانی دارد ولی باید minor پشتیبانی‌شده را نگه داشت.

Ubuntu publishes interim releases every six months and provides LTS releases with longer maintenance; exact support depends on release and maintenance tier. Debian distinguishes stable, testing, and unstable; stable is the project’s usual production recommendation, while testing and unstable are not interchangeable with stable just because they contain newer packages. Rocky offers long-lived major lines, but you still need to remain on a supported minor release.

Arch rolling release است: نصب اولیه به نسخهٔ سالانه قفل نمی‌شود، ولی سیستم را باید کامل و هماهنگ upgrade کرد. package database را sync و بعد فقط یک package را ارتقا نده؛ dependencyها ممکن است دیگر با libraryهای قدیمی جور نباشند. Alpine هم branchها و دورهٔ پشتیبانی خودش را دارد؛ release آن را با Ubuntu/Debian فرض نکن.

Arch is rolling release: an installation is not pinned to an annual version, but the system must be upgraded as a coordinated whole. Do not sync package databases and then upgrade only one package; dependencies may no longer match older libraries. Alpine has its own branches and support windows; do not assume its lifecycle matches Ubuntu or Debian.

برای انتخاب server، سه سؤال از نسخه بپرس: تا چه تاریخی security update می‌گیرم؟ آیا نسخهٔ package و ABI با برنامه match است؟ آیا تیم واقعاً می‌تواند آن را در پنجرهٔ نگهداری patch کند؟ پاسخ را از release lifecycle همان پروژه و image/provider خودت بخوان؛ وعدهٔ کلی «ده سال پشتیبانی» ممکن است add-on یا subscription شرط داشته باشد.

For a server, ask three release questions: until when do security updates arrive? Do package versions and ABI fit the application? Can the team patch it within a maintenance window? Read the project’s lifecycle for the exact release and image/provider; a broad “ten years of support” claim may depend on add-ons or subscriptions.

libc: همان Linux، اما binary شاید اجرا نشودlibc: still Linux, but the binary may not run

برنامهٔ Linux فقط به kernel نیاز ندارد؛ executable می‌تواند به dynamic loader و symbolهای یک libc مشخص هم وابسته باشد. Ubuntu، Debian، Rocky و Arch معمولاً glibc دارند؛ Alpine از musl استفاده می‌کند. اگر binary برای glibc و loader path مثل `/lib64/ld-linux-x86-64.so.2` ساخته شده ولی این interpreter در Alpine نیست، ممکن است shell بگوید فایل هست اما اجرا نمی‌شود. این لزوماً خراب‌بودن CPU architecture یا خود kernel نیست.

A Linux program needs more than a kernel; an executable can depend on a specific dynamic loader and libc symbols. Ubuntu, Debian, Rocky, and Arch commonly use glibc; Alpine uses musl. A binary built for glibc and a loader path such as `/lib64/ld-linux-x86-64.so.2` may fail on Alpine when that interpreter is absent—even when the file exists. That does not necessarily mean the CPU architecture or kernel is wrong.

این تفاوت به معنی «Alpine ناسازگار است» هم نیست: برنامهٔ static، build مخصوص musl یا compatibility layer می‌تواند جواب بدهد؛ native extensionهای Node/Python و binaryهای vendor را باید برای همان libc/architecture بسازی یا بگیری. قبل از انتخاب image کوچک‌تر، test integration را روی image نهایی اجرا کن؛ کاهش اندازه اگر build/runner را می‌شکند، صرفه‌جویی نیست.

This does not mean Alpine is “incompatible”: a static program, musl-specific build, or compatibility layer may work. Vendor binaries and Node/Python native extensions should be built or obtained for the target libc/architecture. Run integration tests on the final image before choosing a smaller base; a size reduction that breaks the build or runtime is no saving.

برای binary مشکوک، `file ./app` و `readelf -l ./app` (اگر ابزار موجود است) دربارهٔ format، architecture و interpreter اطلاعات می‌دهند. `ldd` روی بعضی binaryهای ناشناس را به‌عنوان ابزار بی‌خطر فرض نکن؛ روش inspect باید با اعتماد و ابزار موجود تناسب داشته باشد. بعد package و libc image مقصد را جدا تأیید کن.

For a suspect binary, `file ./app` and `readelf -l ./app` (if installed) report format, architecture, and interpreter. Do not assume `ldd` is a harmless inspection tool for every untrusted binary; choose inspection methods appropriate to the trust level and available tools. Then confirm the target image’s packages and libc separately.

file ./app
readelf -l ./app | grep -i interpreter
cat /etc/os-release
ls -l /lib/ld-linux* /lib/ld-musl* 2>/dev/null

اسم package یک چیز است؛ اسم service شاید چیز دیگرA package name and service name may differ

روی Debian-based معمولاً package را با `apt` نصب می‌کنی؛ Rocky از `dnf` و RPM ecosystem استفاده می‌کند، Arch `pacman` دارد و Alpine `apk`. نام package هم همیشه با دیگری یکی نیست: OpenSSH server ممکن است service unit `sshd` داشته باشد، هرچند package در distro نام دیگری دارد. قبل از نصب، `ID` را بخوان و package manager همان سیستم را search کن.

On Debian-based systems, install packages with `apt`; Rocky uses `dnf` and the RPM ecosystem, Arch uses `pacman`, and Alpine uses `apk`. Package names may also differ from one another: an OpenSSH server may provide a service named `sshd`, even if the package has another name. Read `ID` and search with the system’s package manager before installing.

خرابی عمدی: داخل Alpine اجرا کن `systemctl status sshd`. اگر `systemctl: not found` دیدی، هنوز ثابت نکردی SSH package نصب نیست؛ فقط command systemd در PATH نیست. `/etc/os-release`, `cat /proc/1/comm`, `command -v apk`, `command -v rc-service` و فایل‌های `/etc/init.d/` را بررسی کن. در Alpine از فرمان‌های OpenRC استفاده می‌شود، مثل `rc-service sshd status`—البته فقط اگر package/service نصب شده باشد.

Deliberate fault: on Alpine, run `systemctl status sshd`. If it says `systemctl: not found`, you have not proved OpenSSH is missing; only that the systemd command is absent. Check `/etc/os-release`, `/proc/1/comm`, `command -v apk`, `command -v rc-service`, and `/etc/init.d/`. Alpine uses OpenRC commands such as `rc-service sshd status`—if that service package is installed.

برای Debian/Ubuntu/Rocky/Arch معمولاً `systemctl status sshd` یا `ssh` (بسته به unit) را می‌بینی؛ از `systemctl list-unit-files '*ssh*'` و package files استفاده کن، نه حدس. نصب، enable و start هم سه کارند: package موجود بودن، service در boot فعال شدن و همین حالا اجرا بودن را جدا verify کن. در Alpine، `rc-update` برای runlevel و `rc-service` برای کنترل فعلی است.

On Debian/Ubuntu/Rocky/Arch, you will commonly use `systemctl status sshd` or `ssh`, depending on the unit. Check `systemctl list-unit-files '*ssh*'` and package files instead of guessing. Installed, enabled at boot, and currently running are three separate states. On Alpine, `rc-update` manages runlevels and `rc-service` controls current service state.

برای کار انتخاب کن، نه برای برنده‌کردن بحثChoose for the job, not to win an argument

Ubuntu LTS وقتی ecosystem vendor، tooling رایج و طول maintenance مهم است گزینهٔ طبیعی‌ای می‌شود؛ Debian stable برای کسانی که release با مجموعهٔ package نسبتاً ثابت می‌خواهند مناسب است؛ Rocky وقتی سازگاری با Enterprise Linux ecosystem یا support cadence آن سازمان مهم است؛ Arch وقتی می‌خواهی packageهای تازه و کنترل دقیق داشته باشی و upgrade کامل را مدیریت می‌کنی؛ Alpine وقتی footprint کم و musl/BusyBox با برنامه سازگار است. هیچ‌کدام بدون context «بهترین Linux» نیست.

Ubuntu LTS is a natural option when vendor ecosystem, common tooling, and maintenance horizon matter. Debian stable fits teams wanting a release with a relatively fixed package set. Rocky fits an Enterprise Linux ecosystem or organisational support cadence. Arch fits those who want current packages and fine control and can manage coordinated upgrades. Alpine fits when a small footprint matters and musl/BusyBox are compatible. None is the “best Linux” without context.

برای server، desktop یا container base هم معیار یکسان نیست. desktop نیاز به driver/GUI ecosystem دارد؛ server نیاز به lifecycle، remote administration و support دارد؛ container image ممکن است فقط userland مینیمال داشته باشد، نه init کامل. قبل از جابه‌جایی distro، فهرست package، service، libc و آموزش عملی تیم را هم در هزینه حساب کن.

The criteria also differ for desktop, server, and container base images. A desktop needs a driver/GUI ecosystem; a server needs lifecycle, remote administration, and support; a container base may need only minimal userland, not a full init. Before switching, include packages, services, libc, and team operating knowledge in the cost.

آزمایش: یک چک‌لیست، چند userlandLab: one checklist, several userlands

در این آزمایش می‌توانی از VMهای کوچک فصل‌های قبل استفاده کنی یا برای شروع containerهای یک‌بارمصرف بگیری. container برای شناخت userland سریع است، اما kernel و init PID 1 ممکن است مانند VM نباشد؛ اگر سؤال دربارهٔ service manager یا systemd boot است، VM واقعی لازم داری. روی Ubuntu، Debian، Rocky، Arch و Alpine که خودت انتخاب کرده‌ای این موارد را ثبت کن:

For this lab, use the small VMs from earlier chapters or disposable containers for a quick userland comparison. A container is convenient, but its kernel and PID-1 init may differ from a real VM; use actual VMs when testing service managers or systemd boot. Record the following for the Ubuntu, Debian, Rocky, Arch, and Alpine systems you selected:

cat /etc/os-release
uname -r
cat /proc/1/comm
for x in apt-get dnf pacman apk; do command -v "$x"; done
for x in systemctl rc-service; do command -v "$x"; done
ls -l /lib/ld-linux* /lib/ld-musl* 2>/dev/null
echo "$SHELL"

جدولت باید «شاهد» داشته باشد، نه فقط اسم distro از روی wallpaper. در یک VM، command manager را عمداً اشتباه انتخاب کن؛ مثلاً `apt install curl` روی Alpine. پیام خطا را نگه دار، `/etc/os-release` و `command -v apk` را بخوان، بعد package را با ابزار درست search/install کن. اسم package ممکن است فرق کند؛ از `apk search` یا repository metadata استفاده کن.

Your comparison should record evidence, not just a distro name from the wallpaper. In one VM, deliberately choose the wrong package command—for example `apt install curl` on Alpine. Save the error, read `/etc/os-release` and `command -v apk`, then search/install the package with the right tool. Package names may differ; use `apk search` or repository metadata.

برای پایان، یک binary کوچک را روی glibc distro build و روی Alpine اجرا کن، یا binary آماده‌ای را با مقصد بررسی کن. اگر اجرا نشد، interpreter/architecture و خطای دقیق را ثبت کن. بی‌حساب symlink ساختگی برای loader نساز و برای دورزدن ناسازگاری، libc را از اینترنت به root filesystem کپی نکن؛ build صحیح یا base مناسب را انتخاب کن.

Finally, build a small binary on a glibc distribution and try it on Alpine, or inspect a trusted prebuilt binary against the target. If it fails, record its interpreter/architecture and exact error. Do not create a fake loader symlink or copy libc from a random download into the root filesystem; choose a correct build or compatible base.

تحویل آزمایش: یک matrix با distro/release، package manager/package format، PID 1/init، libc/loader، package install command و security lifecycle link. ستون «نام فرمانی که خطا داد» را هم نگه دار تا دفعهٔ بعد فرضت را سریع‌تر چک کنی.

Lab deliverable: A matrix of distro/release, package manager/format, PID 1/init, libc/loader, package-install command, and security-lifecycle link. Keep the failed command too, so you can identify the assumption faster next time.

تمرین‌هاExercises

۱. اسم kernel

`uname -r` روی Ubuntu و Rocky یکسان است. آیا ثابت شد distributionهایشان یکی است؟

`uname -r` is the same on Ubuntu and Rocky. Does that prove the distributions are identical?

پاسخ

نه؛ این نسخهٔ kernel در حال اجراست. `/etc/os-release` userland/release را می‌گوید.

No. It reports the running kernel. `/etc/os-release` identifies the userland/release.

۲. package managerها

کدام ابزار را برای packageهای Ubuntu، Rocky، Arch و Alpine بررسی می‌کنی؟

Which tools do you inspect for packages on Ubuntu, Rocky, Arch, and Alpine?

پاسخ

معمولاً `apt`, `dnf`, `pacman`, `apk`. وجود واقعی هرکدام را با `command -v` و `/etc/os-release` verify کن.

Commonly `apt`, `dnf`, `pacman`, and `apk`. Verify each with `command -v` and `/etc/os-release`.

۳. Debian سه کانال

تفاوت کلی stable و testing/unstable Debian چیست؟

What is the broad distinction between Debian stable and testing/unstable?

پاسخ

stable release رسمی و production recommendation است؛ testing و unstable چرخهٔ package و سطح تغییر متفاوت دارند. current release/support را از صفحهٔ رسمی همان زمان بررسی کن.

Stable is the official release and production recommendation; testing and unstable have different package flow and change profiles. Check current releases/support on the official page.

۴. Arch package install

چرا `pacman -Sy package` روش مناسبی برای نصب یک package تنها نیست؟

Why is `pacman -Sy package` not a good way to install one package alone?

پاسخ

partial upgradeهای Arch پشتیبانی نمی‌شود؛ database جدید با بخشی از libraryهای قدیمی mismatch می‌شود. upgrade هماهنگ کامل، معمولاً `pacman -Syu`, را دنبال کن.

Arch does not support partial upgrades; a new database can mismatch older libraries. Follow a coordinated full upgrade, commonly `pacman -Syu`.

۵. Alpine command not found

در Alpine، `systemctl` وجود ندارد. اولین تشخیص چیست؟

On Alpine, `systemctl` is absent. What is the first diagnosis?

پاسخ

این سیستم معمولاً OpenRC دارد؛ `/etc/os-release`, `/proc/1/comm`, `rc-service` و init script را بررسی کن، نه اینکه systemd را کورکورانه نصب کنی.

Alpine commonly uses OpenRC. Inspect `/etc/os-release`, `/proc/1/comm`, `rc-service`, and init scripts rather than installing systemd blindly.

۶. libc

کدام تفاوت مهم بین Alpine و سه distro دیگر برای اجرای native binaryهاست؟

What libc difference matters when running native binaries on Alpine versus the other three distributions?

پاسخ

Alpine معمولاً musl دارد؛ Ubuntu/Debian/Rocky معمولاً glibc. interpreter و ABI binary باید با target سازگار باشند.

Alpine commonly uses musl; Ubuntu/Debian/Rocky commonly use glibc. The binary’s interpreter and ABI must match the target.

۷. binary پیدا می‌شود اما اجرا نه

فایل executable هست، اما خطای «No such file or directory» می‌بینی. چه چیزی ممکن است واقعاً missing باشد؟

The executable file exists, but you see “No such file or directory.” What might actually be missing?

پاسخ

dynamic loader/interpreter در مسیر ELF یا dependency. `file` و `readelf -l` را روی binary قابل‌اعتماد بخوان و libc/architecture مقصد را مقایسه کن.

Its ELF interpreter/dynamic loader or a dependency. Inspect a trusted binary with `file` and `readelf -l`, then compare target libc/architecture.

۸. package با service

package OpenSSH نصب است، اما `systemctl status sshd` می‌گوید unit پیدا نشد. دو احتمال را فهرست کن.

OpenSSH is installed, but `systemctl status sshd` says the unit is missing. Name two possibilities.

پاسخ

اسم unit ممکن است متفاوت باشد یا package server/service نصب نشده باشد؛ همچنین init ممکن است systemd نباشد. `command -v`, package file list و init را بررسی کن.

The unit name may differ, the server/service package may be absent, or the init may not be systemd. Inspect command availability, package files, and init.

۹. Rocky minor update

چرا گفتن «Rocky 9 پشتیبانی می‌شود» برای وضعیت production کافی نیست؟

Why is “Rocky 9 is supported” insufficient for a production status check?

پاسخ

minor release جاری و support lifecycle مهم است؛ فقط آخرین minor پشتیبانی می‌شود. release page و `dnf upgrade` plan را بررسی کن.

Current minor release and support lifecycle matter; only the latest minor is supported. Check the release page and update plan.

۱۰. LTS یعنی چه؟

همکار می‌گوید Ubuntu LTS تا ابد security update می‌گیرد. چه اصلاحی لازم است؟

A teammate says Ubuntu LTS receives security updates forever. What needs correction?

پاسخ

پشتیبانی تا تاریخ و tier مشخصی است و ممکن است Ubuntu Pro/add-on شرط داشته باشد. همان release و package coverage را در چرخهٔ رسمی بررسی کن.

Support has defined dates and tiers, sometimes with Ubuntu Pro/add-ons. Check the exact release and package coverage on the official lifecycle page.

۱۱. `apt` روی Alpine

`apt: not found` در Alpine. چرا نباید اولین کار symlink کردن `apt` به `apk` باشد؟

`apt: not found` on Alpine. Why is symlinking `apt` to `apk` a bad first fix?

پاسخ

syntax، repository و package semantics متفاوت‌اند؛ symlink command mismatch را حل نمی‌کند و ممکن است اسکریپت را گمراه کند. distro را شناسایی و دستور native را استفاده کن.

Syntax, repositories, and package semantics differ; a symlink does not translate commands and can mislead scripts. Identify the distro and use its native tool.

۱۲. server یا desktop

برای VM server headless نیاز به GUI نداری. کدام دو معیار مهم‌تر از نام distro می‌شوند؟

A headless server VM does not need a GUI. Which two criteria matter more than the distro name?

پاسخ

release/security lifecycle و سازگاری stack/program، به‌علاوه توان تیم برای patch/operate. server/desktop نوع image و package set است، نه رتبه‌بندی distroها.

Release/security lifecycle and application compatibility, plus the team’s ability to patch/operate it. Server/desktop describes image/package choices, not a distro ranking.

۱۳. BusyBox commandها

یک script به گزینهٔ `ps` خاص GNU وابسته است و در Alpine رفتار متفاوت دارد. چه فرضی را بررسی می‌کنی؟

A script relies on a GNU-specific `ps` option and behaves differently on Alpine. Which assumption do you inspect?

پاسخ

Alpine ممکن است BusyBox applet بدهد که همهٔ GNU optionها را ندارد. dependency را اعلام/نصب کن یا script را با interface portable‌تر بنویس.

Alpine may provide a BusyBox applet without every GNU option. Declare/install the dependency or write the script against a more portable interface.

۱۴. package format

یک `.rpm` مستقیم داری و می‌خواهی روی Ubuntu با `dpkg -i` نصبش کنی. مشکل چیست؟

You have an `.rpm` and want to install it on Ubuntu with `dpkg -i`. What is the issue?

پاسخ

`dpkg` برای `.deb` است و `.rpm` متعلق به ecosystem دیگری است؛ بهتر است package/repository مناسب Ubuntu را بگیری نه convert/install تصادفی.

`dpkg` manages `.deb`, while `.rpm` belongs to another package ecosystem. Obtain the Ubuntu package/repository rather than converting/installing blindly.

۱۵. container inspection

در container، `/etc/os-release` Alpine نشان می‌دهد اما `uname -r` برابر kernel میزبان است. تناقض؟

Inside a container, `/etc/os-release` says Alpine but `uname -r` matches the host kernel. Is that contradictory?

پاسخ

نه؛ container userland از Alpine است و kernel را با host share می‌کند. VM معمولی kernel guest جدا دارد.

No. The container has Alpine userland while sharing the host kernel. A normal VM has its own guest kernel.

۱۶. release متغیر

مستند قدیمی می‌گوید Debian stable نسخهٔ ۱۲ است؛ امروز از کجا جواب معتبر می‌گیری؟

Old documentation says Debian stable is version 12. Where do you find the current answer?

پاسخ

صفحهٔ رسمی Debian Releases و `/etc/os-release` image مشخص را بررسی کن. شماره/تاریخ را به‌عنوان fact همیشگی داخل راهنمای عمومی hardcode نکن.

Check Debian’s official releases page and `/etc/os-release` for the exact image. Do not hard-code a dated version fact into general guidance.

۱۷. package manager یا libc؟

`apk add curl` موفق است ولی binary سرویس vendor start نمی‌شود. کدام موضوع را بعد بررسی می‌کنی؟

`apk add curl` works, but a vendor service binary does not start. What do you inspect next?

پاسخ

architecture، dynamic interpreter، native dependencies و سازگاری musl/glibc. نصب موفق curl فقط package manager/network را ثابت می‌کند.

Inspect architecture, dynamic interpreter, native dependencies, and musl/glibc compatibility. A successful curl install only proves the package path worked.

۱۸. انتخاب برای تیم

تیم یک vendor-supported service با binary رسمی glibc و نیاز به patch window مشخص دارد. Alpine کوچک‌تر است. آیا خودکار انتخابش می‌کنی؟

A team has a vendor-supported service with an official glibc binary and a defined patch window. Alpine is smaller. Do you choose it automatically?

معیار پاسخ

نه؛ ابتدا vendor support، libc/ABI و security lifecycle را تطبیق بده. Ubuntu/Debian/Rocky می‌توانند گزینه باشند بسته به matrix پشتیبانی و عملیات تیم؛ Alpine فقط پس از تست رسمی binary/compatibility و نگهداری مناسب.

No. First match vendor support, libc/ABI, and security lifecycle. Ubuntu/Debian/Rocky may fit depending on the support matrix and team operations; use Alpine only after validating vendor binaries/compatibility and maintenance.

توزیع را با چهار سؤال انتخاب کنChoose a distribution with four questions

برنامه چه libc و packageهایی می‌خواهد؟ چه service manager و ابزار عملیاتی روی image هست؟ چه مدت security update می‌گیریم؟ تیم می‌تواند release cadence آن را با اطمینان نگه دارد؟ این سؤال‌ها از «کدام distro بهتر است؟» جواب عملی‌تری می‌دهند.

Which libc and packages does the application need? Which service manager and operational tools are in the image? How long will security updates arrive? Can the team maintain the release cadence confidently? These questions produce a more useful answer than “which distro is best?”

در آزمایشگاه، هر VM را با `/etc/os-release` بشناس، package manager و init را از روی شواهد پیدا کن و اگر binary fail شد loader/ABI را هم بررسی کن. فصل بعد توزیع‌ها را واقعاً نصب می‌کنیم؛ پیش از دانلود ISO، حالا می‌دانی دنبال چه تفاوتی می‌گردی و چرا اسم distro به‌تنهایی کافی نیست.

In the lab, identify each VM from `/etc/os-release`, verify package manager and init from evidence, and inspect loader/ABI if a binary fails. Next we install the distributions for real; before downloading ISOs, you now know which differences to look for and why a distro name alone is not enough.
