نصب چند توزیع

Installing several distributions

نصب توزیع یعنی چند بار Next زدن نیست. از firmware و دیسک تا bootloader و اولین boot رو دنبال می‌کنیم و آخرش ثابت می‌کنیم ماشین واقعاً از دیسک خودش بالا اومده.

Installing an operating system is a chain of choices: firmware, disk layout, bootloader, user, and network. Then we must prove the VM boots from disk.

۹۰دقیقهminutes
۱۸تمرینexercises

ISO بوت شد؛ ولی نصب به مقصد نمی‌رسهThe ISO booted, but installation does not reach its destination

VM رو ساخته‌ای، ISO اوبونتو رو وصل کرده‌ای و نصب تمام شده. دفعهٔ بعد VM دوباره نصاب رو باز می‌کنه—یا bootable دستگاه پیدا نمی‌شه. کسی می‌گه «ISO خراب هست». فعلاً این تشخیص رو قبول نکنیم.

You created a VM, attached an Ubuntu ISO, and finished installation. Next time the installer opens again—or no bootable device is found. Someone says “the ISO is broken.” Let us not accept that diagnosis yet.

نصاب فقط فایل‌ها رو کپی نمی‌کنه: firmware باید bootloader سازگار رو پیدا کنه؛ bootloader، kernel و initramfs رو می‌آورد؛ kernel ریشهٔ فایل‌سیستم رو mount می‌کنه و فضای کاربر رو بالا می‌آورد. اول از VM و ترتیب بوت شاهد می‌گیریم.

An installer does more than copy files: firmware finds a compatible bootloader; it loads the kernel and initramfs; the kernel mounts root and starts userspace. We will inspect the VM and boot order first.

از firmware تا اولین ورودFrom firmware to first login

UEFI معمولاً فایل EFI رو از EFI System Partition می‌خونه؛ BIOS قدیمی‌تر bootloader رو جور دیگری می‌یابد. اگه حالت نصب و boot بعدی فرق کنه، فایل‌ها ممکنه سالم باشن ولی firmware ورودی رو پیدا نکنه.

UEFI commonly reads an EFI file from the EFI System Partition; legacy BIOS locates a bootloader differently. If installation and later boot modes differ, files may be intact while firmware cannot find the entry.

VM آزمایشگاهی کوچک و قابل‌حذفA small, disposable lab VM

برای Ubuntu Server و Debian یا Rocky دو VM جدا بساز؛ مثل lab-ubuntu و lab-debian. ISO رسمیِ معماری سازگار بگیر و unattended installation رو خاموش کن. دو vCPU، RAM متناسب با نصاب و دیسک مجازی با فضای کافی نقطهٔ شروع‌اند؛ اندازه به host بستگی داره. دیسک مهمان فایل میزبان هست، ولی فضای پوشهٔ VM رو هم چک کن.

Create separate Ubuntu Server and Debian or Rocky VMs, such as lab-ubuntu and lab-debian. Get an official ISO for a compatible architecture and disable unattended installation. Two vCPUs, suitable RAM, and a roomy virtual disk are starting points; sizing depends on the host. The guest disk is a host file, but check VM-folder space.

برای UEFI گزینهٔ EFI رو در تنظیمات VM روشن کن؛ جای اون نسخه‌حساس هست. هر دو رو با firmware یکسان نصب کن تا مقایسه منصفانه باشه. بعد از نصب ISO رو eject کن. دستور زیر تنظیمات VM رو روی host نشون می‌ده؛ نام fieldها نسخه‌حساس هست و سلامت guest رو ثابت نمی‌کنه.

Enable EFI in VM settings for UEFI; its location varies by version. Use the same firmware on both VMs for a fair comparison. Eject the ISO after install. This host-side command reports VM settings; field names vary and it does not prove guest health.

VBoxManage showvminfo "lab-ubuntu" --machinereadable

تقسیم دیسک نسخهٔ واحد ندارهThere is no universal disk layout

برای VM تمرینی guided چیدمان معمولاً معقول هست، اگه بفهمی چه ساخته. UEFI معمولاً GPT و EFI System Partition می‌خواد. / ریشه هست؛ جداکردن /home دادهٔ کاربر رو جدا می‌کنه ولی اندازه‌گذاری بد رو نجات نمی‌ده. swap می‌تونه پارتیشن یا فایل باشه؛ نیاز hibernation و سیاست توزیع مهم‌اند.

For a practice VM, guided layout is often reasonable if you understand it. UEFI commonly uses GPT and an EFI System Partition. / is root; a separate /home isolates user data but cannot rescue poor sizing. Swap can be a partition or file; hibernation needs and distro policy matter.

پارتیشن بیشتر لزوماً بهتر نیست؛ / ممکنه پر بشه و /home خالی بمونه. یک VM رو guided نصب و mountها رو ثبت کن؛ در VM آزمایشی دوم، فقط اگه دلیل داری چیدمان دستی بساز. قبل از تأیید مطمئن شو مقصد دیسک مجازی آزمایشگاهی هست.

More partitions are not automatically better; / may fill while /home stays empty. Install one VM with guided layout and record mounts; use manual partitioning on a second disposable VM only for a reason. Confirm the target is the lab virtual disk before applying changes.

lsblk -f
findmnt / /boot /boot/efi /home
df -hT

lsblk -f فایل‌سیستم، UUID و mountpoint رو نشون می‌ده؛ findmnt mount واقعی رو؛ df فضای مصرفی رو. ESP ممکنه در /boot/efi یا جای دیگر باشه. این خروجی چیدمان رو نشون می‌ده، نه مناسب‌بودنش برای هر بار کاری.

lsblk -f shows filesystem, UUID, and mountpoint; findmnt shows actual mounts; df reports usage. The ESP may be at /boot/efi or elsewhere. This reveals layout, not whether it fits every workload.

دو نصاب، سؤال‌های مشترکTwo installers, shared questions

در Ubuntu Server زبان، keyboard، شبکه، mirror، storage، hostname/کاربر و بسته‌های آغازین رو ثبت کن. وقتی استفاده از کل دیسک مجازی پیشنهاد می‌شه، نام و اندازه رو با تنظیمات VM تطبیق بده. خلاصهٔ تغییرات رو بخون؛ تأیید اون دادهٔ قبلی همون دیسک رو پاک می‌کنه.

In Ubuntu Server, record language, keyboard, network, mirror, storage, hostname/user, and initial packages. Match the offered disk to VM settings and read the change summary; confirming erases prior data on that disk.

در VM جدا Debian یا Rocky رو نصب و انتخاب‌ها رو مقایسه کن. سؤال‌ها: کدوم دیسک و firmware؟ چه فایل‌سیستم و mountهایی؟ کدوم کاربر؟ رمز یکتا بذار و در Git یا تصویر عمومی ذخیره نکن. NAT برای به‌روزرسانی دسترسی خروجی می‌ده، نه انتشار خودکار SSH. «وصل» هم DNS و route رو ثابت نمی‌کنه.

Install Debian or Rocky separately and compare choices: which disk and firmware, filesystems and mounts, and login user? Use a unique password; keep it out of Git and public screenshots. NAT gives outbound update access, not automatic SSH exposure. “Connected” does not prove DNS or routing.

اولین boot رو با شاهد تأیید کنVerify first boot with evidence

ISO رو جدا کن و از دیسک مجازی boot کن. موفقیت نصاب کافی نیست؛ وارد سیستم شو و نسخه، firmware، mountها و شبکه رو بررسی کن.

Detach the ISO and boot from the virtual disk. Installer success is not enough; log in and inspect release, firmware, mounts, and network.

cat /etc/os-release
uname -r
test -d /sys/firmware/efi && echo UEFI || echo BIOS
lsblk -f
findmnt /
ip -br address
ip route

/etc/os-release توزیع رو می‌گه؛ uname -r kernel رو؛ وجود /sys/firmware/efi معمولاً نشانهٔ UEFI هست؛ findmnt / دستگاه ریشه رو. اگه نصاب برگشت ISO و ترتیب بوت رو چک کن. برای No bootable medium attachment دیسک، firmware و boot فایل‌ها رو جدا بسنج.

/etc/os-release identifies distro; uname -r reports kernel; /sys/firmware/efi usually indicates UEFI; findmnt / shows root. If installer returns, check ISO and boot order. For No bootable medium, inspect disk attachment, firmware, and boot files separately.

به‌روزرسانی رو با مدیر بسته همون distro انجام بده؛ Arch به‌روزرسانی هماهنگ کل سیستم می‌خواد. موفقیت فرمان فقط همون عملیات رو ثابت می‌کنه، نه آمادگی سرویس‌های آینده رو. snapshot آزمایشگاهی backup مستقل نیست.

Update with the distro’s package manager; Arch expects coordinated full-system updates. Success proves only that operation, not readiness for future services. A lab snapshot is not an independent backup.

root پر شد؛ اول اندازه بگیرRoot filled; measure first

در VM آزمایشی، به‌روزرسانی با No space left on device شکست خورده. قبل از پاک‌کردن VM بفهم کدوم فایل‌سیستم پر هست و داده‌ای لازم داری یا نه.

In a disposable VM, an update failed with No space left on device. Before deleting it, identify the full filesystem and whether any data matters.

df -hT
df -i
lsblk -f
findmnt /

df -hT blockها و df -i inodeها رو می‌سنجد؛ یکی ممکنه پر باشه و دیگری نه. findmnt و lsblk مسیر رو به partition وصل می‌کنن. نصب دوبارهٔ VM بی‌داده امن هست؛ روی سیستم واقعی اول داده و backup رو مشخص کن. متن خطا به‌تنهایی لایهٔ مشکل رو نمی‌گه.

df -hT measures blocks and df -i inodes; either may fill independently. findmnt and lsblk map paths to partitions. Reinstalling an empty lab VM is safe; identify data and backups on real systems. The error alone does not identify the layer.

آزمایش: دو VM، دو مسیر نصبLab: two VMs, two installation paths

Ubuntu Server و VM جدا با Debian یا Rocky نصب کن. هر دو رو با UEFI یا هر دو رو BIOS بالا بیاور تا تفاوت نصاب و firmware قاطی نشه. guided چیدمان رو ثبت کن؛ در VM کاملاً آزمایشی یک چیدمان دستی ساده هم تمرین کن. root رو اون‌قدر کوچک نگیر که نصب تمام نشه.

Install Ubuntu Server and a separate Debian or Rocky VM. Use the same firmware mode to separate installer from firmware differences. Record guided layout; practise a simple manual layout on a disposable VM. Do not make root too small for installation to finish.

  1. ISO، معماری، firmware، RAM، vCPU و ظرفیت دیسک رو ثبت کن.
  2. Record ISO, architecture, firmware, RAM, vCPU, and disk size.
  3. قبل از تأیید storage، partition، فایل‌سیستم، swap و mountpointها رو یادداشت کن.
  4. Before confirming storage, record partitions, filesystems, swap, and mounts.
  5. hostname و کاربر عادی بساز؛ بسته‌های آغازین رو محدود نگه دار.
  6. Set hostname and regular user; keep initial packages minimal.
  7. ISO رو eject کن؛ از دیسک boot کن و شاهدها رو ذخیره کن.
  8. Eject the ISO, boot from disk, and save the evidence.
  9. به‌روزرسانی رو اجرا و نتیجه یا خطا رو ثبت کن.
  10. Run updates and record the result or failure.

تحویل: دو برگهٔ نصب، جدول partition/mount و شاهد boot از دیسک. هر reinstall رو با firmware، ترتیب بوت یا چیدمان توضیح بده.

Deliverable: Two installation records, partition/mount table, and proof of disk boot. Explain any reinstall using firmware, boot order, or layout.

تمرین‌هاExercises

۱. نصاب برگشت

دو بررسی کم‌خطر؟

Two low-risk checks?

پاسخ

ISO وصل هست یا دیسک در ترتیب بوت عقب هست. جداکردن ISO فرضیه رو می‌سنجد، نه سلامت guest رو.

Check ISO attachment and disk boot order. Detaching it tests the hypothesis, not guest health.

۲. UEFI layout

ترکیب متداول چیست؟

What is common?

پاسخ

GPT و EFI System Partition؛ GPT به‌تنهایی boot entry رو ثابت نمی‌کنه.

GPT and an EFI System Partition; GPT alone does not prove the boot entry.

۳. EFI path

وجود /sys/firmware/efi چه می‌گه؟

What does it indicate?

پاسخ

معمولاً UEFI boot؛ نه تنظیم دقیق Secure Boot.

Usually UEFI boot, not a specific Secure Boot configuration.

۴. home جدا

همیشه بهتره؟

Always better?

پاسخ

نه؛ mountها ظرفیت مستقل دارن و یکی می‌تونه پر و دیگری خالی بمونه.

No; mounts have independent capacity and can fill unevenly.

۵. root device

چرا findmnt / و lsblk -f رو ترکیب می‌کنی؟

Why combine these commands?

پاسخ

mount ریشه رو به UUID، فایل‌سیستم و دستگاه مربوط می‌کنن؛ اسم دستگاه به‌تنهایی پایدار نیست.

They map root mount to UUID, filesystem, and device; a device name alone is not stable.

۶. kernel یا distro؟

uname -r و /etc/os-release؟

What does each show?

پاسخ

kernel اجراشده؛ و توزیع/نسخه، به‌ترتیب.

Running kernel; distribution/release, respectively.

۷. thin disk

ظرفیت ۴۰ GiB، فایل host برابر ۹ GiB؛ تناقض؟

40 GiB capacity, 9 GiB host file; contradiction?

پاسخ

نه؛ تخصیص پویاست ولی رشد فضای واقعی host می‌خواد.

No; allocation is dynamic, but growth requires real host space.

۸. حالت ناسازگار

نصب UEFI بود و boot بعدی BIOS. فرض اول؟

Install UEFI, later boot BIOS. First hypothesis?

پاسخ

حالتها جور نیستن؛ firmware و boot فایل‌ها رو بررسی کن و یک تغییر رو تست کن.

The modes disagree; inspect firmware and boot files, testing one change.

۹. mirror resolve نمی‌شه

سه بررسی شبکه؟

Three network checks?

پاسخ

link/address، پیش‌فرض route، DNS؛ نشانگر وصل همه رو ثابت نمی‌کنه.

Link/address, default route, and DNS; “connected” proves none fully.

۱۰. به‌روزرسانی موفق

آیا سرویس آینده آماده هست؟

Is a future service ready?

پاسخ

نه؛ فقط به‌روزرسانی موفق شده. سرویس و سازگاری رو جدا بررسی کن.

No; only the update succeeded. Check services and compatibility separately.

۱۱. root پر، home خالی

اول چه می‌کنی؟

What first?

پاسخ

df -hT و findmnt رو برای تشخیص mount و مصرف بخون.

Inspect df -hT and findmnt to identify mount and usage.

۱۲. معماری ISO

host ARM هست و ISO x86_64 بالا نمیاد؛ اول چه رو می‌سنجی؟

An ARM host cannot boot x86_64 ISO. First check?

پاسخ

سازگاری guest و معماری ISO؛ partition علت اول نیست.

Guest support and ISO architecture; partition is not first.

۱۳. اثبات نصب

چطور boot از دیسک نصب‌شده رو ثابت می‌کنی؟

How do you prove boot from the installed disk?

پاسخ

ISO رو جدا کن؛ boot کن؛ /etc/os-release و findmnt / رو ببین.

Detach ISO, boot, inspect /etc/os-release and findmnt /.

۱۴. دیسک host

نصاب مهمان دیسک فیزیکی host رو می‌بینه. قدم بعد؟

Guest installer sees the host disk. Next?

پاسخ

توقف، خاموش‌کردن VM و بررسی passthrough؛ partition فقط دیسک مجازی تأییدشده.

Stop, power off, inspect passthrough; partition only a confirmed virtual disk.

۱۵. swap

آیا باید برابر RAM باشه؟

Must swap equal RAM?

پاسخ

نه؛ hibernation، بار کاری و سیاست توزیع مهم‌اند.

No; hibernation, workload, and distro policy matter.

۱۶. hostname تکراری

چی مبهم می‌شه؟

What becomes ambiguous?

پاسخ

prompt، لاگ و SSH؛ hostname یکتا جای IP رو نمی‌گیره.

Prompts, logs, and SSH; unique hostname does not replace IP.

۱۷. No bootable medium

ISO جداست؛ چه شاهدی attachment، ترتیب بوت و firmware رو تفکیک می‌کنه؟

ISO is detached; what evidence separates attachment, order, and firmware?

معیار پاسخ

مسیر دیسک، ترتیب بوت، EFI/BIOS و ESP/bootloader. یک فرضیه رو در هر نوبت تست کن.

Disk path, boot order, EFI/BIOS, and ESP/bootloader. Test one hypothesis at a time.

۱۸. طرح تکرارپذیر

برای آزمایش SSH روی Ubuntu Server چه طرحی می‌دی که چیدمان جهان‌شمول ادعا نکنه؟

Plan Ubuntu Server for SSH without claiming a universal layout.

معیار پاسخ

ISO رسمی و سازگار، دیسک مجازی آزمایشی، firmware ثبت‌شده، guided چیدمان بازبینی‌شده، کاربر/hostname و شبکهٔ متناسب؛ سپس eject ISO و بررسی mount، route و SSH.

Official compatible ISO, disposable disk, recorded firmware, reviewed guided layout, user/hostname, suitable network; eject ISO and verify mounts, routes, and SSH.

نصب وقتی تمام هست که boot رو ثابت کرده باشیInstallation is complete after you prove the boot

firmware، چیدمان، فایل‌سیستم، کاربر و شبکه تعیین می‌کنن سیستم چطور بالا بیاد. اگه boot نشد زنجیره رو دنبال کن: VM دیسک درست رو می‌بینه؟ firmware با boot فایل‌ها می‌خونه؟ root mount می‌شه؟ kernel و فضای کاربر بالا میان؟

Firmware, layout, filesystem, user, and networking shape startup. If boot fails, follow the chain: does the VM see the right disk? Does firmware match the boot files? Does root mount? Do kernel and userspace start?

نصب وقتی تمومه که ISO رو کنار بذاری، ماشین از دیسک خودش بالا بیاد و تو بتونی kernel، mountها و شبکه رو بررسی کنی. فصل بعد همین تصمیم‌ها رو از حافظه‌مون بیرون می‌کشیم و می‌ذاریم توی فایل.

Next we will create these machines automatically; record hostname, firmware, disk size, and installation choices. A good installation is a bounded set of explainable decisions you can verify after boot.
