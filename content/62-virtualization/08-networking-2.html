Networking 2

حالا سه VM را روی یک شبکهٔ خصوصی می‌گذاریم، به هرکدام IP و نام قابل‌پیش‌بینی می‌دهیم و ارتباطشان را با route، neighbor و یک service واقعی ثابت می‌کنیم.

Now we place three VMs on a private network, assign predictable addresses and names, and prove connectivity using routes, neighbour entries, and a real service.

۱۸تمرینexercises

سه VM بالا هستند؛ چرا ping گاهی جواب می‌دهد؟Three VMs are up. Why does ping only work sometimes?

بعد از فصل قبل، هر سه VM را روی یک شبکهٔ خصوصی گذاشته‌ای. یکی `10.77.0.20` است و دیگری `10.77.0.30`. اول ping جواب می‌دهد، بعد timeout؛ SSH هم گاهی به machine اشتباه می‌رسد. این بار mode را عوض نکنیم. اول ببینیم هر ماشین دقیقاً چه IP، prefix و routeای دارد و همسایه را با کدام MAC پیدا کرده.

After the previous chapter, you placed all three VMs on a private network. One is `10.77.0.20`, another `10.77.0.30`. Ping works once, then times out; SSH sometimes reaches the wrong machine. Let us not switch modes yet. First inspect each machine’s address, prefix, routes, and the MAC address it learned for its neighbour.

یک شبکهٔ داخلی یعنی یک segment لایهٔ دوم؛ خودش IP، DHCP یا gateway نمی‌سازد مگر hypervisor/DHCP server جداگانه‌ای تنظیم کنی. برای آزمایش اول static address موقت می‌دهیم، روی هر سه VM یکسان subnet می‌سازیم و gateway را خالی می‌گذاریم چون در این segment خروج به جای دیگری نداریم.

An internal network is a layer-2 segment; it does not create IP addresses, DHCP, or a gateway unless you configure a hypervisor/DHCP service separately. For the first experiment, we assign temporary static addresses, put all three VMs on the same subnet, and leave the gateway empty because this segment has nowhere else to go.

سه ماشین، یک virtual switch، یک subnetThree machines, one virtual switch, one subnet

در VirtualBox برای هر سه VM، Adapter 2 را روی Internal Network با نام یکسان مثل `lab-private` بگذار؛ Internal Network name باید دقیقاً match شود. اگر کارت اول NAT است، فعلاً آن را خاموش نگه دار تا معلوم باشد کدام interface داریم آزمایش می‌کنیم. سه VM روی یک virtual switch هستند و یک subnet IP را مشترک می‌سازند.

In VirtualBox, set Adapter 2 on all three VMs to Internal Network with the same name, such as `lab-private`; the network name must match exactly. If Adapter 1 is NAT, leave it disabled for now so the tested interface is unambiguous. All three VMs share one virtual switch and one IP subnet.

فلش‌های سه VM فقط اتصال NIC به switch خصوصی را نشان می‌دهند. لینک NAT اختیاری به gateway است؛ بدون فعال‌کردن IP forwarding و تنظیم firewall/NAT داخل gateway، VMهای دیگر از آن اینترنت نمی‌گیرند.

The three VM arrows show NICs attached to the private switch. The optional NAT uplink belongs to the gateway; without IP forwarding and suitable firewall/NAT rules inside it, the other VMs do not gain Internet access.

در libvirt هم یک virtual network می‌سازی و همهٔ VMها را به آن وصل می‌کنی؛ network XML تعیین می‌کند DHCP یا forwarding هست یا نه. `default` معمولاً NAT است، نه شبکهٔ داخلی بدون upstream. در هر hypervisor از تعریف network و adapter شروع کن، نه از تشابه اسم‌ها.

With libvirt, create a virtual network and attach all VMs to it; its network definition determines DHCP and forwarding. `default` is commonly NAT, not an isolated internal segment. In either hypervisor, start from the network and adapter definitions rather than matching labels by name.

در یک subnet، route جداگانه معمولاً لازم نیستWithin one subnet, a separate route is usually unnecessary

در شبکهٔ آزمایشی `10.77.0.0/24`، سه آدرس را یکتا انتخاب می‌کنیم: A برابر `.20`، B برابر `.30` و C برابر `.130`. `/24` یعنی ۲۴ بیت prefix شبکه مشترک است و hostها در همین on-link subnet هستند. برای مقصد هم‌شبکه، kernel مستقیماً همسایه را با ARP پیدا می‌کند؛ default gateway لازم نیست.

On the lab subnet `10.77.0.0/24`, choose three unique addresses: A is `.20`, B is `.30`, and C is `.130`. `/24` means the first 24 bits are the shared network prefix, so all hosts are on-link. For an on-link destination, the kernel discovers the neighbour through ARP; no default gateway is needed.

اول نام interface را از `ip -br link` پیدا کن؛ `enp0s8` در مثال فقط placeholder است. بعد روی هر VM به interface داخلی address موقت بده، مثلاً روی A:

First identify the interface with `ip -br link`; `enp0s8` is only a placeholder. Then assign a temporary address to the internal NIC on each VM. For A, for example:

ip -br link
sudo ip link set dev enp0s8 up
sudo ip address replace 10.77.0.20/24 dev enp0s8
ip -br address show dev enp0s8
ip route

روی B آدرس `.30/24` و روی C آدرس `.130/24` بگذار. `ip address replace` آدرس را روی interface اصلاح می‌کند و تا reboot/net-manager change پایدار نیست. در خروجی دنبال آدرس درست با `/24` و routeای مثل `10.77.0.0/24 dev enp0s8 proto kernel scope link` بگرد. آن route می‌گوید kernel مقصدهای subnet را مستقیم می‌فرستد؛ اینترنت را ثابت نمی‌کند.

Assign `.30/24` to B and `.130/24` to C. `ip address replace` changes the interface address but is temporary and may disappear after reboot or a network-manager change. Look for the expected `/24` and a route like `10.77.0.0/24 dev enp0s8 proto kernel scope link`. It says the kernel treats subnet destinations as directly connected; it does not prove Internet access.

برای route یک مقصد را پیش‌بینی کن و بعد `ip route get 10.77.0.130` بزن. انتظار `dev enp0s8 src 10.77.0.20` را داری و معمولاً عبارت `via` نمی‌آید، چون مسیر مستقیم است. اگر `unreachable` دیدی یا interface دیگری انتخاب شد، address/prefix، interface state و routeهای دیگر را بررسی کن.

Predict the route to a peer, then run `ip route get 10.77.0.130`. Expect `dev enp0s8 src 10.77.0.20`, usually without `via`, because the path is direct. If it says unreachable or chooses another interface, inspect address/prefix, link state, and competing routes.

ip route get 10.77.0.130

ping، ARP و SSH هرکدام شاهد متفاوت‌اندPing, ARP, and SSH are different kinds of evidence

از A به B، ابتدا route lookup می‌کنی، بعد چند ping محدود می‌فرستی و جدول neighbor را می‌خوانی:

From A to B, inspect route selection first, then send a bounded number of pings and check the neighbour table:

ip route get 10.77.0.30
ping -c 3 -W 1 10.77.0.30
ip neigh show dev enp0s8

اگر neighbor برای `.30` یک MAC واقعی و state `REACHABLE` یا `STALE` نشان دهد، ARP resolution انجام شده یا قبلاً انجام شده؛ این ثابت نمی‌کند ICMP یا SSH مجاز است. ping جواب‌دار، ICMP round-trip در آن لحظه را ثابت می‌کند؛ باز هم SSH listener/authentication را نه. برای service، از B پورت را باز کن و از A `ssh` یا `nc -vz` را تست کن.

A neighbour entry for `.30` with a MAC and state such as `REACHABLE` or `STALE` shows that ARP resolution happened or had happened earlier; it does not prove ICMP or SSH is allowed. A successful ping proves an ICMP round trip at that moment, not an SSH listener or authentication. For a service test, open its port on B and try `ssh` or `nc -vz` from A.

برای نام‌های قابل‌خواندن، سه VM disposable را می‌توانی با `/etc/hosts` نگاشت کنی: `10.77.0.20 vm-a`, `.30 vm-b`, `.130 vm-c`. این فقط همان فایل روی همان VM را تغییر می‌دهد؛ نام را برای دیگر دستگاه‌ها منتشر نمی‌کند. برای lab کوچک خوب است؛ DHCP DNS یا DNS server سازمانی راه‌حل‌های دیگری هستند و واردشان در فصل شبکهٔ بعدی می‌شویم.

For readable names, add mappings to `/etc/hosts` on each disposable VM: `10.77.0.20 vm-a`, `.30 vm-b`, `.130 vm-c`. This changes only that VM’s local lookup file; it does not publish names to other devices. It is fine for a small lab. DHCP DNS and a DNS server are other approaches, beyond this chapter’s scope.

gateway فقط وقتی لازم است که از subnet بیرون برویYou need a gateway only to leave the subnet

سه VM در یک subnet route مستقیم دارند؛ برای همین default gateway ندارند. اگر subnet دوم اضافه کنی، برای رسیدن به آن باید router و route مناسب داشته باشی. اگر gateway VM یک adapter خصوصی و یک adapter NAT دارد، داشتن دو کارت به‌تنهایی routing نمی‌سازد: forwarding باید فعال شود، firewall/NAT rule لازم است و return path باید درست باشد.

Three VMs on one subnet have direct routes, so they do not need a default gateway. Add a second subnet and you need a router and suitable routes to reach it. A gateway VM with one private and one NAT adapter does not route automatically: forwarding must be enabled, firewall/NAT rules are needed, and the return path must work.

در این دوره uplink را optional می‌گذاریم تا private segment تصادفی به LAN/Internet نشت نکند. اگر فقط خود gateway باید package update بگیرد، می‌توانی adapter دوم NAT را فقط به همان VM وصل کنی؛ اما guestهای دیگر همچنان route ندارند. اگر می‌خواهی آن‌ها هم از gateway اینترنت بگیرند، باید آگاهانه routing/NAT را پیاده‌سازی و ruleها را محدود کنی—با اضافه‌کردن NIC این رفتار خودکار نمی‌شود.

The uplink stays optional so the private segment cannot accidentally leak to the LAN/Internet. If only the gateway needs package updates, you can attach a second NAT NIC to that VM alone; the other guests still have no route. To give them Internet through the gateway, deliberately configure routing/NAT and restrict the rules—adding a NIC does not do this automatically.

یادت بماند: adapter دوم ممکن است مسیر پیش‌فرض یا DNS guest را عوض کند. بعد از افزودنش `ip route` و `resolvectl status` را بخوان و مطمئن شو ترافیک private lab از interface درست خارج می‌شود. روی شبکهٔ واقعی forwarding/NAT را بدون مجوز فعال نکن.

Remember: A second adapter can change default routes or guest DNS. After adding it, inspect `ip route` and `resolvectl status` and verify private lab traffic uses the intended interface. Do not enable forwarding/NAT on a real network without authorisation.

دو خرابی عمدی: آدرس تکراری و prefix اشتباهTwo deliberate faults: duplicate address and wrong prefix

پیش از تغییر، از هر سه VM `ip -br address`, `ip route` و `ip neigh` بگیر. خرابی اول را فقط در شبکهٔ داخلی disposable بساز: به VM B موقتاً IP برابر A بده (`10.77.0.20/24`). از A و C به آن ping بزن و neighbor table را چند بار بخوان. ممکن است MAC مربوط به `.20` بین کارت A و B تغییر کند؛ نتیجه می‌تواند متناوب باشد و اگر ARP cache قدیمی مانده باشد فوراً دیده نشود.

Before changing anything, capture `ip -br address`, `ip route`, and `ip neigh` on all three VMs. Create the first fault only on the disposable internal network: temporarily assign B the same `10.77.0.20/24` as A. Ping it from A and C and inspect neighbour tables repeatedly. The MAC for `.20` may alternate between A and B; behaviour can be intermittent and an old ARP cache may delay the symptom.

اصلاح را با مشاهده انجام بده: هر دو guest که یک address نشان می‌دهند را پیدا کن، به B یک IP آزاد و یکتا بده و سپس neighbor state و ping را تکرار کن. فقط پاک‌کردن ARP cache بدون حذف IP تکراری، درمان نیست؛ مشکل دوباره برمی‌گردد.

Repair from evidence: find both guests claiming the same address, assign B a unique free IP, then retest neighbour state and ping. Clearing the ARP cache without removing the duplicate address is not a fix; the conflict will return.

خرابی دوم را جدا بساز: همهٔ VMها را به آدرس‌های اصلی برگردان، اما prefix ماشین C را `/25` کن در حالی‌که C با آدرس `.130` و A با `.20` باید در `/24` یکسان باشند. `ip route get 10.77.0.20` روی C را قبل از ping پیش‌بینی کن. C تصور می‌کند peer بیرون subnet محلی است و gateway ندارد؛ route lookup و پیام `Network is unreachable` ممکن است علت را روشن کند.

Create the second fault separately: restore unique addresses, but change C’s prefix to `/25` while C at `.130` and A at `.20` are meant to share `/24`. Predict `ip route get 10.77.0.20` on C before pinging. C now considers the peer outside its local subnet and has no gateway; route lookup or `Network is unreachable` may reveal why.

prefix C را به `/24` اصلاح و همان route lookup/ping را تکرار کن. اگر route درست شد ولی ping نه، مشکل بعدی را از neighbor table، interface state و ICMP firewall جدا کن. یک repair موفق روی route، service یا firewall را به‌تنهایی ثابت نمی‌کند.

Restore C’s `/24` prefix and repeat the same route lookup and ping. If the route is correct but ping still fails, inspect the neighbour table, link state, and ICMP firewall separately. A repaired route alone does not prove the service or firewall is correct.

آزمایش نهایی: سه VM خصوصی، با مدرک اتصالFinal lab: three private VMs, with proof of reachability

سه VM disposable را به Internal Network یکسان `lab-private` وصل کن. در هر VM نام interface دوم را با `ip -br link` پیدا کن؛ اگر interface management/NAT هم داری، آن را با NIC خصوصی اشتباه نگیر. آدرس‌های یکتا و prefix یکسان تنظیم کن: A `.20/24`, B `.30/24`, C `.130/24`. default route برای segment آزمایش لازم نیست.

Attach three disposable VMs to the same `lab-private` Internal Network. Find each second interface with `ip -br link`; if a management/NAT NIC exists, do not confuse it with the private NIC. Assign unique addresses with a common prefix: A `.20/24`, B `.30/24`, C `.130/24`. The lab segment needs no default route.

از هر ماشین `ip -br address`, `ip route`, `ip neigh` ذخیره کن. A به B و C ping بزند؛ B به C؛ بعد یک service موقت روی B اجرا کن، مثلاً SSH موجود یا `python3 -m http.server 8080 --bind 10.77.0.30`, و از A اتصال TCP/HTTP واقعی بگیر. اگر Python server استفاده می‌کنی آن را با Ctrl+C متوقف کن؛ service را فقط روی IP خصوصی bind کن.

Save `ip -br address`, `ip route`, and `ip neigh` from every VM. Ping B and C from A, then C from B. Start a temporary service on B—an existing SSH server or `python3 -m http.server 8080 --bind 10.77.0.30`—and make a real TCP/HTTP request from A. Stop the Python server with Ctrl+C and bind it only to the private address.

در یک اجرا IP تکراری B را بساز، route/neighbour/ping را ضبط و repair کن. بعد خرابی prefix C را جدا بساز، پیش از fix route lookup را ذخیره و پس از fix همان اندازه‌گیری را تکرار کن. آزمایش وقتی قبول است که هر سه VM با IP و hostname مشخص در private segment باشند، هیچ‌کدام default route تصادفی نداشته باشند و تو بتوانی یک service را از VM دیگر reach کنی.

In one run, create B’s duplicate IP, record route/neighbour/ping evidence, and repair it. Then introduce C’s wrong prefix separately, save the route lookup before the fix, and repeat the same measurement after repair. Pass when all three VMs have unique identities on the private segment, no accidental default route, and one service is reachable from another VM.

پایان کار کارت‌های اضافهٔ آزمایشی را به حالت قبلی برگردان؛ اگر NAT روی gateway فعال کردی و دیگر لازم نیست، آن adapter یا forwarding rule را بردار. network خصوصی را نگه دار چون آزمایشگاه پروژه‌های بعدی است، اما مطمئن شو LAN/Internet به آن bridge نشده است.

At the end, restore extra test adapters to their prior state. If you enabled a NAT gateway or forwarding rule and no longer need it, remove that adapter/rule. Keep the private network for later projects, but verify it has not been bridged to the LAN/Internet.

تمرین‌هاExercises

۱. یک شبکهٔ داخلی

سه VM روی Internal Network با نام‌های `lab-a`, `lab-b`, `lab-c` تنظیم شده‌اند. فقط `lab-a` و `lab-b` ارتباط دارند. اولین موردی که بررسی می‌کنی چیست؟

Three VMs are configured on Internal Networks named `lab-a`, `lab-b`, and `lab-c`; only A and B communicate. What do you check first?

پاسخ

اسم Internal Network هر adapter دقیقاً یکی است یا نه؛ سپس link/address و firewall. تفاوت نام یعنی VMها روی switchهای جدا هستند.

Check whether every adapter uses the exact same Internal Network name, then inspect link, address, and firewall. Different names mean separate virtual switches.

۲. آدرس‌های یکتا

روی `10.77.0.0/24` سه IP برای VMها پیشنهاد بده و gateway را لازم است؟

Choose three VM addresses on `10.77.0.0/24`. Is a gateway required?

پاسخ

مثلاً `.20`, `.30`, `.130`, هرکدام یکتا و `/24`. برای ارتباط همان subnet gateway لازم نیست.

For example `.20`, `.30`, and `.130`, all unique with `/24`. Same-subnet communication does not need a gateway.

۳. مقصد هم‌شبکه

`ip route get 10.77.0.30` می‌گوید `dev enp0s8 src 10.77.0.20` و `via` ندارد. چه مسیر انتخاب شده؟

`ip route get 10.77.0.30` says `dev enp0s8 src 10.77.0.20` with no `via`. What path was selected?

پاسخ

مسیر on-link از interface داخلی؛ kernel مقصد را مستقیم با ARP resolve می‌کند. اینترنت یا SSH را ثابت نمی‌کند.

An on-link route through the private interface; the kernel resolves the peer directly with ARP. This proves neither Internet nor SSH reachability.

۴. ARP معلوم ولی ping ناموفق

neighbor table یک MAC معتبر نشان می‌دهد، اما ping timeout می‌شود. چه لایه‌ای را بعد بررسی می‌کنی؟

The neighbour table shows a valid MAC, but ping times out. Which layer do you inspect next?

پاسخ

ICMP/firewall یا وضعیت service مقصد را؛ ARP فقط resolution لایهٔ ۲ را نشان می‌دهد. ping هم service TCP را نمی‌آزماید.

Check ICMP/firewall and destination state. ARP shows layer-2 resolution only, and ping does not test a TCP service.

۵. دو ماشین، یک IP

دو MAC مختلف در نوبت‌های مختلف برای `10.77.0.20` دیده می‌شود. چه فرضیه‌ای جلو می‌آید؟

Two different MAC addresses appear at different times for `10.77.0.20`. What hypothesis comes first?

پاسخ

duplicate IP محتمل است. `ip -br address` را روی هر VM تطبیق بده و یکی را به آدرس یکتا تغییر بده؛ cache clearing به‌تنهایی fix نیست.

A duplicate IP is plausible. Compare `ip -br address` on every VM and give one a unique address; clearing caches alone is not a fix.

۶. /25 روی C

C برابر `10.77.0.130/25` و A برابر `10.77.0.20/24` است؛ C gateway ندارد. چرا C ممکن است A را unreachable بداند؟

C is `10.77.0.130/25`, A is `10.77.0.20/24`, and C has no gateway. Why might C consider A unreachable?

پاسخ

C subnet محلی را `10.77.0.128/25` می‌بیند و A بیرون آن است؛ برای ارسال به route نیاز دارد. اگر هدف یک segment `/24` است prefix را یکسان کن.

C sees its local subnet as `10.77.0.128/25`, placing A outside it, so it needs a route. If the intended segment is `/24`, use a consistent prefix.

۷. /24 در برابر /16

دو VM با IPهای `10.77.0.20/24` و `10.77.0.30/16` همدیگر را ping می‌کنند. آیا subnet config سالم است؟

Two VMs at `10.77.0.20/24` and `10.77.0.30/16` can ping each other. Is their subnet configuration sound?

پاسخ

ping موفق نشانهٔ خوب است ولی prefix ناسازگار می‌ماند و در مقصدهای دیگر رفتار route متفاوت می‌شود. هر دو mask را طبق طراحی یکسان کن.

A successful ping is useful but the prefixes remain inconsistent, which can change routing to other destinations. Align masks with the design.

۸. route نیست

VM IP درست دارد ولی `ip route get` می‌گوید `Network is unreachable`. چه دو موردی را بررسی می‌کنی؟

The VM has an expected IP, but `ip route get` reports `Network is unreachable`. What two things do you inspect?

پاسخ

prefix/connected route و link/interface status؛ اگر مقصد بیرون subnet است gateway/route مناسب هم لازم است.

Check the prefix/connected route and interface link state; a destination outside the subnet also needs a suitable gateway/route.

۹. default route در private lab

VMهای lab با هم ارتباط دارند ولی default route ندارند. آیا باید خودکار یکی اضافه کنی؟

Lab VMs communicate with each other but have no default route. Should you add one automatically?

پاسخ

نه؛ same-subnet communication نیازی ندارد. gateway فقط برای subnetهای دیگر/خروج لازم است؛ gateway تصادفی می‌تواند ترافیک را leak کند.

No. Same-subnet communication does not need one. A gateway is for other subnets or outbound access; a random default can leak traffic.

۱۰. `/etc/hosts` محلی

روی VM A خط `10.77.0.30 vm-b` اضافه کردی. آیا لپ‌تاپ host هم `vm-b` را resolve می‌کند؟

You added `10.77.0.30 vm-b` to VM A’s hosts file. Will the host laptop resolve `vm-b` too?

پاسخ

خیر؛ hosts file محلی همان OS است. برای host یا هر guest دیگری جداگانه map لازم است یا DNS مشترک.

No. A hosts file is local to that OS. The host and every other guest need their own mapping or shared DNS.

۱۱. host-only در برابر internal

می‌خواهی guestها با هم حرف بزنند ولی host interface به آن‌ها وصل نباشد. در VirtualBox کدام مفهوم نزدیک‌تر است؟

You want guests to talk to each other without a host interface attached to their network. Which VirtualBox concept is closer?

پاسخ

Internal Network؛ host-only معمولاً host adapter هم دارد. نام و رفتار تنظیمات نسخهٔ نصب را verify کن.

Internal Network. Host-only normally also has a host adapter. Verify the exact option and behaviour in your installed release.

۱۲. فقط DHCP لازم داری؟

برای سه VM آزمایشگاهی آدرس ثابت قابل‌پیش‌بینی می‌خواهی. DHCP از پیش فعال نیست؛ آیا این بن‌بست است؟

You want predictable addresses for three lab VMs, but DHCP is not enabled. Is this a blocker?

پاسخ

نه؛ static IP موقت روی NIC داخلی تنظیم کن یا DHCP محدود و آدرس‌دهی رزروشده راه‌اندازی کن. مراقب duplicate و overlap با host network باش.

No. Set temporary static addresses on the private NIC or configure scoped DHCP with reservations. Avoid duplicates and overlap with the host network.

۱۳. NAT NIC روی gateway

gateway VM یک NIC خصوصی و یک NIC NAT دارد. چرا VMهای دیگر هنوز اینترنت ندارند؟

The gateway VM has a private NIC and a NAT NIC. Why do the other VMs still lack Internet?

پاسخ

دو NIC به‌تنهایی router نمی‌سازد؛ IP forwarding، firewall/NAT rules و route برگشت لازم‌اند. تا وقتی قصد و policy روشن نیست، تنظیمشان نکن.

Two NICs alone do not create a router; IP forwarding, firewall/NAT rules, and a return route are needed. Do not configure them until the intent and policy are clear.

۱۴. IP هست، MAC نیست

route می‌گوید مقصد on-link است، اما `ip neigh` روی `INCOMPLETE` می‌ماند. چه لایه‌ای را می‌سنجی؟

The route says the peer is on-link, but `ip neigh` remains `INCOMPLETE`. Which layer do you investigate?

پاسخ

ARP/layer 2: Internal Network names, adapter link, VLAN/switch placement و IP target را بررسی کن. هنوز سراغ DNS نرو.

Investigate ARP/layer 2: Internal Network names, adapter link, VLAN/switch placement, and target IP. DNS is not the first suspect.

۱۵. ping هست، HTTP نیست

A می‌تواند B را ping کند ولی port 8080 بسته است. چه مدرکی روی B جمع می‌کنی؟

A can ping B, but port 8080 is closed. What evidence do you collect on B?

پاسخ

`ss -ltnp` برای listener، firewall rules و bind address. ping فقط ICMP را ثابت می‌کند؛ برنامه شاید روی loopback `127.0.0.1` bind شده باشد.

Check `ss -ltnp`, firewall rules, and bind address. Ping proves only ICMP; the app may be listening on loopback `127.0.0.1` only.

۱۶. دومین کارت، دومین default

پس از افزودن NAT NIC، اینترنت guest درست است ولی private peerها unreachable شدند. محتمل‌ترین سرنخ کدام است؟

After adding a NAT NIC, guest Internet works but private peers become unreachable. What is the leading clue?

پاسخ

interface/route table تغییر کرده یا NIC خصوصی down/subnet متفاوت شده. `ip -br address`, `ip route get` و metricها را مقایسه کن.

The interface/route table changed, or the private NIC is down/on another subnet. Compare `ip -br address`, `ip route get`, and route metrics.

۱۷. subnet با IP اتفاقی

A و B دو address معتبر دارند ولی یکی `/24` و دیگری `/25` است؛ ping فعلاً موفق می‌شود. آیا می‌توانی inconsistency را نادیده بگیری؟

A and B have valid addresses but use `/24` and `/25`; ping currently succeeds. Can you ignore the inconsistency?

پاسخ

نه؛ مقصدهای دیگر ممکن است از route متفاوت بروند و fault intermittent شود. prefix را طبق subnet design هماهنگ و routeها را verify کن.

No. Other destinations may follow different routes and create intermittent faults. Align prefixes to the subnet design and verify routes.

۱۸. گزارش تشخیص

C نمی‌تواند A را ببیند؛ C=`10.77.0.130/25`, A=`10.77.0.20/24`, gateway خالی، neighbor برای A ندارد. علت محتمل و repair را بنویس.

C cannot reach A: C is `10.77.0.130/25`, A is `10.77.0.20/24`, gateway is empty, and C has no neighbour entry for A. State the likely cause and repair.

معیار پاسخ

C با `/25`، A را خارج از on-link subnet می‌بیند و route‌ای برایش ندارد؛ prefix را به `/24` هماهنگ کن، `ip route get` را تکرار کن، سپس neighbor/ ping و service TCP را جدا verify کن.

With `/25`, C sees A outside its on-link subnet and has no route. Align the prefix to `/24`, repeat `ip route get`, then verify neighbour/ping and TCP service separately.

IP، route و neighbor باید یک داستان بگویندAddress, route, and neighbour should tell one story

برای سه VM روی یک شبکه، IP یکتا و prefix هماهنگ مسیر پایه را می‌سازند؛ route می‌گوید kernel packet را از کدام NIC بفرستد؛ ARP MAC مقصد را روی همان segment پیدا می‌کند. بعد ping فقط ICMP را می‌سنجد و SSH/HTTP باید جدا روی port و listener خودش آزمایش شود. اگر این شواهد با هم جور نیستند، mode را عوض‌کردن ممکن است فقط سرنخ‌ها را پنهان کند.

For three VMs on one network, unique addresses and a consistent prefix establish the basic path; routes tell the kernel which NIC to use; ARP finds the destination MAC on that segment. Ping then tests ICMP only, while SSH/HTTP must be tested against their own port and listener. If the evidence disagrees, switching network modes may only hide the clue.

آزمایشگاه خصوصی را کوچک و قابل‌پیش‌بینی نگه دار؛ IP تکراری را با نشانهٔ MAC پیدا کن و route گمشده را پیش از تغییر firewall تشخیص بده. فصل بعد سراغ توزیع‌های Linux می‌رویم تا همین سه ماشین را با سیستم‌عامل‌های مناسب برای تمرین‌های ادامهٔ مسیر آماده کنیم.

Keep the private lab small and predictable. Use MAC evidence to find duplicate addresses and diagnose missing routes before changing firewalls. Next we choose Linux distributions and prepare these three machines for the labs later in the track.
