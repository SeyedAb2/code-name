Networking 1

یک VM را روی NAT، bridge و host-only می‌گذاریم و هر بار از شواهد می‌پرسیم: مهمان به کجا می‌رسد و چه کسی می‌تواند به مهمان برسد؟

We place one VM on NAT, bridged, and host-only networking, asking from evidence each time: where can the guest reach, and who can reach the guest?

۱۸تمرینexercises

VM اینترنت دارد، ولی لپ‌تاپت به SSH آن نمی‌رسدThe VM has Internet, but your laptop cannot SSH into it

Ubuntu guest را روشن کرده‌ای؛ `apt update` موفق است، پس می‌گویی شبکه درست کار می‌کند. همکارت می‌خواهد از لپ‌تاپ به SSH مهمان وصل شود، اما timeout می‌گیرد. یک نشانهٔ دیگر: guest یک IP گرفته، ولی با IP میزبان فرق دارد. کدام قسمت شبکه کار می‌کند و کدام قسمت نه؟

Your Ubuntu guest is running; `apt update` succeeds, so you conclude networking works. A teammate tries to SSH from the laptop into the guest but gets a timeout. Another clue: the guest has an IP different from the host. Which part of networking works, and which does not?

«اینترنت دارد» و «از بیرون می‌شود به آن وصل شد» دو ادعای جدا هستند. DHCP می‌تواند IP بدهد، ولی service خاموش باشد؛ route باشد، ولی firewall ببندد؛ outbound کار کند، ولی inbound اصلاً route نداشته باشد. mode شبکه را با نشانهٔ درست می‌سنجیم.

“It has Internet” and “it is reachable from outside” are separate claims. DHCP may assign an IP while the service is stopped; a route may exist while a firewall blocks it; outbound may work while inbound has no route at all. We will test each mode with the right evidence.

NAT: مهمان بیرون را می‌بیند، بیرون معمولاً مهمان را نهNAT: the guest can see out; the outside usually cannot see in

در VirtualBox، adapter اول VM معمولاً NAT است. مهمان از DHCP داخلی IP خصوصی می‌گیرد؛ VirtualBox ترافیک خروجی را از شبکهٔ host به بیرون می‌فرستد. برای وب‌گردی و package update خوب است، اما VM به شکل host یا LAN addressable نیست. NAT را با bridge قاطی نکن: NAT ترافیک را به نمایندگی از مهمان عبور می‌دهد؛ bridge مهمان را به شبکهٔ لایهٔ دوم وصل می‌کند.

In VirtualBox, the first VM adapter commonly defaults to NAT. An internal DHCP service gives the guest a private address; VirtualBox forwards outbound traffic through the host. This suits web access and package updates, but the VM is not directly addressable as a host/LAN node. Do not confuse NAT with bridging: NAT forwards traffic on the guest’s behalf, while bridging attaches the guest to the layer-2 network.

فلش پیوسته مسیر خروجی را نشان می‌دهد. خط‌چین، مسیر inbound عادی‌ای است که وجود ندارد؛ فقط port forward انتخاب‌شده می‌تواند مسیر مشخصی بسازد.

The solid arrows show outbound traffic. The dashed path is ordinary inbound traffic that does not exist; only a selected port forward can add a specific path.

داخل guest `ip -br address` آدرس و link را می‌دهد؛ `ip route` مسیر default را. اگر default route و DNS کار کنند، guest ممکن است اینترنت داشته باشد. این خروجی‌ها نشان نمی‌دهند SSH روی port 22 گوش می‌دهد یا host می‌تواند به آن برسد؛ آن را جدا با `ss -ltnp` و یک اتصال واقعی آزمایش کن.

Inside the guest, `ip -br address` shows addresses and link state; `ip route` shows the default path. With a default route and working DNS, the guest may have Internet. These outputs do not show that SSH listens on port 22 or that the host can reach it; check `ss -ltnp` and test a connection separately.

ip -br address
ip route
getent hosts example.com
ss -ltnp

اگر host باید به SSH برسد ولی VM را exposed روی LAN نمی‌خواهی، یک port forward بساز. نمونهٔ VirtualBox با host loopback bind می‌شود تا همان لپ‌تاپ به `127.0.0.1:2222` وصل شود؛ port 22 مهمان به آن map می‌شود:

If the host needs SSH access but you do not want the VM exposed to the LAN, add a port forward. This VirtualBox example binds to host loopback so only the host connects to `127.0.0.1:2222`, which maps to guest port 22:

VBoxManage modifyvm "lab-vm" --nat-pf1 "guestssh,tcp,127.0.0.1,2222,,22"
ssh -p 2222 learner@127.0.0.1

قبلش guest باید SSH server اجرا کند و firewall اجازه دهد. اگر host port 2222 را برنامهٔ دیگری گرفته، rule fail می‌شود؛ با `ss -ltnp` روی host بررسی کن و یک port آزاد انتخاب کن. اگر bind address را خالی بگذاری، بسته به rule، host ممکن است روی interfaceهای بیشتری listen کند؛ برای آزمایش محلی `127.0.0.1` را صریح بنویس. این rule فقط یک service را expose می‌کند و NAT را به bridge تبدیل نمی‌کند.

The guest must run an SSH server and its firewall must allow it. If another host process owns port 2222, the rule can fail; inspect host `ss -ltnp` and choose a free port. If the bind address is empty, the rule may listen on more host interfaces; specify `127.0.0.1` for a local-only test. This exposes one service; it does not turn NAT into a bridge.

bridge: مهمان مثل یک دستگاه دیگر وارد LAN می‌شودBridged: the guest joins the LAN like another device

در bridged mode، hypervisor کارت مجازی guest را از مسیر کارت فیزیکی host به LAN وصل می‌کند. DHCP معمولاً از همان router/LAN IP می‌دهد؛ حالا دستگاه‌های LAN می‌توانند به guest وصل شوند اگر route، firewall و policy شبکه اجازه بدهند. این دسترسی مفید است برای server آزمایشی، اما سطح exposure را بالا می‌برد: guest تقریباً همان جایگاه شبکه‌ای یک لپ‌تاپ دیگر را می‌گیرد.

In bridged mode, the hypervisor connects the guest’s virtual NIC to the LAN through a physical host adapter. DHCP commonly comes from the same router/LAN. Other LAN devices may reach the guest if routing, firewall, and network policy allow it. This is useful for a test server but increases exposure: the guest occupies roughly the network position of another laptop.

host و guest دو IP از LAN می‌گیرند؛ bridge به‌خودی‌خود firewall یا router نیست. اگر شبکهٔ مهمان، Wi-Fi یا سازمانی client isolation دارد، نتیجه ممکن است فرق کند.

Host and guest receive separate LAN addresses; a bridge is neither a firewall nor a router. Guest Wi-Fi or corporate client-isolation policies can change the result.

بعد از تغییر mode، داخل guest `ip -br address` و `ip route` را دوباره بخوان. اگر DHCP lease تازه نیامد، interface را در guest renew یا VM را restart کن و logهای DHCP/network را ببین؛ حدس نزن که IP قبلی هنوز متعلق به VM است. از یک دستگاه دیگر در LAN به IP تازه ping یا SSH بزن؛ ping ممکن است بسته باشد، پس برای SSH، listening port و guest firewall را هم بسنج.

After changing modes, recheck `ip -br address` and `ip route` in the guest. If no new DHCP lease appears, renew the guest interface or restart it and inspect DHCP/network logs; do not assume the old IP still belongs to the VM. From another LAN device, try ping or SSH to the new address. Ping may be blocked, so also check the listening port and guest firewall.

در لپ‌تاپ‌های Wi-Fi یا بعضی نسخه‌های macOS/Windows، bridge به adapter/driver محدودیت دارد؛ اگر گزینه نیست یا guest lease نمی‌گیرد، host adapter انتخاب‌شده، driver مجازی‌سازی و policy access point را بررسی کن. NAT port forward ممکن است برای تنها یک سرویس، ساده‌تر و کم‌مواجهه‌تر باشد.

On Wi-Fi laptops and some macOS/Windows host configurations, bridging can be limited by adapters or drivers. If the option is missing or the guest gets no lease, inspect the selected host adapter, virtualisation driver, and access-point policy. A NAT port forward may be simpler and less exposed for one service.

host-only: شبکه‌ای خصوصی میان host و VMهاHost-only: a private network between the host and VMs

host-only یک interface مجازی روی host می‌سازد و VMهای متصل را در همان شبکه قرار می‌دهد. host و VMها می‌توانند با هم ارتباط بگیرند؛ معمولاً route مستقیمی به LAN/Internet ندارد. برای تمرین server/client یا اتصال laptop به guest خوب است، چون VM را مستقیماً وارد شبکهٔ فیزیکی نمی‌کند.

Host-only creates a virtual interface on the host and places attached VMs on that network. The host and VMs can communicate, but there is normally no direct route to the physical LAN/Internet. It suits server/client labs or host-to-guest access without placing the VM directly on the physical network.

شبکه عمداً به NIC فیزیکی وصل نیست. برای outbound اینترنت می‌توان adapter دوم NAT افزود، اما آن دو NIC مسیرها و firewall پیچیده‌تری می‌سازند؛ برای این آزمایش همان یک شبکه را نگه دار.

The network is intentionally disconnected from the physical NIC. A second NAT adapter could add Internet access, but two NICs introduce routing/firewall complexity; keep this lab on one network.

در VirtualBox، Host-only Network ممکن است DHCP server اختیاری داشته باشد؛ اگر آن خاموش است باید IPهای هم‌شبکه را خودت تنظیم کنی. آدرس host و guest را از `ip -br address` بگیر و مطمئن شو maskشان یکسان/هم‌پوشان نیست. در libvirt، معادل دقیق نام `host-only` پیش‌فرض وجود ندارد: شبکهٔ `default` معمولاً NAT است؛ شبکهٔ بدون forwarding یا bridge شبکه‌سازی متفاوتی می‌دهد و host access به تعریف آن بستگی دارد.

A VirtualBox Host-only Network may have an optional DHCP server; if it is off, configure addresses in the same subnet yourself. Read host and guest addresses with `ip -br address` and verify their masks place them in the intended subnet. libvirt has no exact default mode named `host-only`: its `default` network is commonly NAT, while a no-forward network or bridge has different semantics and host reachability depends on its definition.

On Ubuntu with libvirt, the `default` network is commonly NATed through the host; direct LAN access requires a separately configured bridge. Read your hypervisor’s mode and network definition rather than assuming “NAT” in VirtualBox and libvirt has identical details.

خرابی عمدی: از LAN به NAT guest وصل شوDeliberate failure: connect from the LAN to a NAT guest

برای اینکه رفتار inbound را ببینی، در یک VM disposable با adapter NAT، SSH server را روشن کن. از داخل guest `ip -br address`, `ss -ltnp` و firewall را بررسی کن؛ از host، به IP خصوصی guest روی port 22 وصل شو. بعد از یک دستگاه LAN دیگر هم همان آزمون را تکرار کن. نتیجهٔ مورد انتظار در NAT ساده: outbound guest کار می‌کند، ولی inbound مستقیم به IP خصوصی guest از host/LAN مسیر ندارد.

To observe inbound behaviour, enable an SSH server in a disposable NAT guest. Check `ip -br address`, `ss -ltnp`, and its firewall from inside. From the host, try port 22 at the guest’s private IP; repeat from another LAN device. With ordinary NAT, guest outbound works but direct inbound to its private address generally has no path.

اگر connection timeout شد، هنوز ثابت نکردی NAT علت قطعی است: ممکن است service/firewall هم دخیل باشد. شواهد را جمع کن و بعد یک port forward loopback بساز و از host با `ssh -p 2222 user@127.0.0.1` وصل شو. اگر forward کار کرد، این مسیر inbound انتخابی و محلی است؛ اگر نه، rule/port host، listener guest و SSH authentication را جدا بخوان.

A timeout does not prove NAT is the sole cause; the service or firewall may also be involved. Collect evidence, then add a loopback-only port forward and connect from the host using `ssh -p 2222 user@127.0.0.1`. If it works, this is a selected local inbound path; if not, inspect the rule/host port, guest listener, and SSH authentication separately.

از راه دور به host با پورت 2222 وصل شو فقط اگر عمداً می‌خواهی آن را روی interface LAN bind کنی و firewall میزبان را تنظیم کرده‌ای. پورت‌فوروارد اشتباه می‌تواند service آزمایشگاهی را برای شبکهٔ واقعی باز کند؛ rule را بعد از تمرین پاک کن.

Only bind the forward to a LAN-facing host interface if remote LAN access is intentional and the host firewall is configured. A careless forwarding rule can expose a lab service to a real network; remove the rule after testing.

آزمایش پیوسته: یک VM، سه مسیرContinuous lab: one VM, three paths

روی VM یک کارت شبکه نگه دار تا معلوم باشد هر بار کدام mode را می‌سنجی. پیش از هر تغییر یادداشت کن: mode، MAC، IP/prefix، default route، DNS، و از کجا آزمون اتصال می‌کنی. از `ip -br address`, `ip route`, `resolvectl status` و `ss -ltnp` خروجی بگیر؛ دادهٔ هر mode را جدا ذخیره کن.

Keep one NIC on the VM so each test clearly represents one mode. Before every change, record mode, MAC, address/prefix, default route, DNS, and the source of your connection test. Save output from `ip -br address`, `ip route`, `resolvectl status`, and `ss -ltnp` separately for each mode.

با NAT شروع کن: guest به host gateway و یک مقصد بیرونی می‌رود؛ host به guest مستقیم نمی‌رود؛ port forward لوکال SSH را بعداً اضافه کن. با bridged، guest باید از LAN address بگیرد؛ از میزبان و اگر اجازه داری از یک client دیگر، port سرویس را تست کن. اگر DHCP lease نمی‌آید، adapter/driver و policy شبکه را بررسی کن، نه اینکه IP static دلخواه بزنی.

Start with NAT: the guest reaches its gateway and an external destination; the host cannot directly reach the guest; add a local SSH forward afterward. With bridged mode, the guest should obtain a LAN address; test its service port from the host and, if permitted, another client. If DHCP fails, inspect the adapter/driver and network policy instead of guessing a static IP.

در پایان Host-only را تنظیم کن و host-to-guest و VM-to-VM را بررسی کن؛ نبودن default route را به‌عنوان نتیجه ثبت کن، نه الزاماً خرابی. بعد adapter را به حالت امن اولیه برگردان و اگر port forward ساخته‌ای حذفش کن. Acceptance test تو جدول سه‌ردیفی reachability و شاهد واقعی هر خانه است—نه فقط یک IP که در GUI دیده‌ای.

Finish by selecting Host-only and testing host-to-guest and VM-to-VM access; record the absence of a default route as expected behaviour, not necessarily a fault. Restore the original safe adapter mode and remove any test forward. Your acceptance test is a three-row reachability table with evidence in every cell—not merely an IP shown in a GUI.

حفاظت شبکه: bridge VM را روی LAN واقعی قرار می‌دهد. در شبکهٔ شرکت/دانشگاه یا Wi-Fi عمومی بدون اجازه امتحان نکن؛ از NAT یا host-only استفاده کن. Firewall guest و host را خاموش نکن تا «وصل شود»؛ rule محدود و قابل‌بازگشت بساز.

Network safety: Bridging places the VM on a real LAN. Do not try it on a corporate, campus, or public Wi-Fi network without permission; use NAT or host-only instead. Do not disable guest/host firewalls just to make a test pass—use a narrow, reversible rule.

تمرین‌هاExercises

۱. update موفق

guest روی NAT است و `apt update` جواب می‌دهد. آیا لپ‌تاپ دیگر در LAN می‌تواند به SSH مهمان وصل شود؟

A NAT guest runs `apt update` successfully. Can another laptop on the LAN SSH directly into it?

پاسخ

معمولاً نه؛ outbound کار می‌کند ولی inbound مستقیم مسیر ندارد. port forward یا bridged mode را با نیاز و exposure مناسب انتخاب کن.

Usually not. Outbound works, but direct inbound has no path. Choose port forwarding or bridged mode based on need and exposure.

۲. DHCP lease

guest آدرس DHCP گرفت اما هیچ hostی به service وصل نمی‌شود. lease چه چیزی را ثابت می‌کند؟

The guest obtained a DHCP address, but no host reaches its service. What does the lease prove?

پاسخ

فقط اینکه DHCP یک پیکربندی آدرس داده؛ route، listener، firewall و inbound reachability هنوز باید جدا بررسی شوند.

Only that DHCP supplied address configuration. Route, listener, firewall, and inbound reachability remain separate checks.

۳. NAT یا bridge؟

guest فقط باید package download کند و از LAN دیده نشود. کدام mode کم‌مواجهه‌تر است؟

The guest only needs package downloads and should not be visible on the LAN. Which mode has less exposure?

پاسخ

NAT معمولاً؛ outbound را فراهم می‌کند و inbound مستقیم را نمی‌دهد مگر port forward اضافه شود. firewallها همچنان مهم‌اند.

Usually NAT: it provides outbound connectivity without direct inbound access unless a forward is added. Firewalls still matter.

۴. host-only بدون اینترنت

دو guest در host-only همدیگر را ping می‌کنند، ولی `ip route` default route ندارد. خرابی است؟

Two host-only guests can ping each other, but `ip route` has no default route. Is that a failure?

پاسخ

نه لزوماً؛ host-only برای ارتباط خصوصی است و معمولاً upstream ندارد. اگر اینترنت لازم است، توپولوژی جداگانه طراحی کن، نه اینکه این mode را به bridge تعبیر کنی.

Not necessarily. Host-only is private and usually has no upstream. If Internet is needed, design another topology rather than treating host-only as bridged.

۵. port forward loopback

rule host `127.0.0.1:2222` را به guest `:22` map می‌کند. کدام دستگاه می‌تواند به endpoint میزبان وصل شود؟

A rule maps host `127.0.0.1:2222` to guest port 22. Which machine can reach the host endpoint?

پاسخ

به‌طور معمول خود host از loopback؛ این rule را با bind روی تمام interfaceها اشتباه نگیر. تست از دستگاه دیگر باید fail شود مگر rule دیگری وجود داشته باشد.

Normally the host itself through loopback. Do not confuse it with a bind on all interfaces; another device should fail unless another rule exists.

۶. host port اشغال است

port forward بالا نمی‌آید و host روی 2222 برنامه‌ای در حالت LISTEN دارد. چه کار می‌کنی؟

The port forward does not start, and a host process is listening on 2222. What do you do?

پاسخ

از `ss -ltnp` مالک port را تشخیص بده؛ یا port آزاد دیگری مثل 2223 انتخاب کن یا برنامه را فقط اگر لازم و امن است جابه‌جا کن. service موجود را بی‌دلیل kill نکن.

Use `ss -ltnp` to identify the owner. Choose another free port such as 2223, or move the existing service only if appropriate; do not kill it blindly.

۷. bridge IP گرفت

guest IP هم‌شبکهٔ لپ‌تاپ دارد. آیا از هر دستگاه LAN حتماً قابل‌دسترسی است؟

The bridged guest has an address on the same subnet as the laptop. Is it definitely reachable from every LAN device?

پاسخ

نه؛ guest firewall، router/AP client isolation، VLAN/ACL و listener اثر می‌گذارند. IP membership را ثابت می‌کند، نه اتصال application را.

No. Guest firewall, router/AP client isolation, VLAN/ACL, and service listener matter. Address membership does not prove application connectivity.

۸. bridge مثل router؟

همکارت می‌گوید «bridge یعنی VM یک router/NAT دارد». چه اصلاحی می‌دهی؟

A teammate says, “Bridging means the VM has a router/NAT.” How do you correct that?

پاسخ

bridge دستگاه را به همان شبکهٔ لایهٔ دوم وصل می‌کند؛ NAT/router نقش IP forwarding/translation دارد. topology و gateway هر mode را جدا بخوان.

A bridge attaches the guest to the same layer-2 network. NAT/router performs IP forwarding/translation. Inspect each mode’s topology and gateway separately.

۹. ping جواب نمی‌دهد

host ping به guest نمی‌رسد. آیا ثابت شد SSH هم بسته است؟

The host cannot ping the guest. Does this prove SSH is blocked too?

پاسخ

نه؛ ICMP و TCP قواعد جدا دارند. port 22 را با `ss` داخل guest و آزمون SSH/TCP بررسی کن.

No. ICMP and TCP have separate rules. Check the port-22 listener with `ss` and test SSH/TCP directly.

۱۰. libvirt default

در Ubuntu/libvirt network `default` active است. آیا guest همین حالا روی LAN bridge شده؟

Ubuntu/libvirt’s `default` network is active. Is the guest now bridged onto the LAN?

پاسخ

معمولاً خیر؛ `default` اغلب NATشده و از host بیرون می‌رود. تعریف network XML و interface domain را بررسی کن.

Usually not; `default` is commonly NATed through the host. Inspect the network XML and domain interface.

۱۱. اسم host-only در libvirt

می‌خواهی در libvirt دقیقاً checkboxی به نام host-only پیدا کنی. فرض درست چیست؟

You are looking for a libvirt checkbox exactly named host-only. What is the right assumption?

پاسخ

اسم‌ها/مدل‌ها یکی‌به‌یکی برابر نیستند؛ mode forwarding، bridge و دسترسی host را از network definition بسنج، نه از برچسب VirtualBox.

Names and models are not one-to-one. Inspect forwarding mode, bridge, and host access in the network definition rather than mapping a VirtualBox label directly.

۱۲. guest route ندارد

guest address دارد و `ip route` خالی است. کدام ارتباط ممکن است کار کند و کدام را نباید فرض بگیری؟

The guest has an address but `ip route` is empty. Which connection might still work, and which should not be assumed?

پاسخ

ارتباط همان subnet ممکن است کار کند؛ دسترسی به subnet دیگر/Internet به route نیاز دارد. route table و mode را اصلاح/بررسی کن.

Same-subnet communication may work; other subnets/Internet need a route. Inspect the route table and mode.

۱۳. NAT دو guest را جدا نگه می‌دارد؟

دو VM هر دو NAT دارند ولی همدیگر را نمی‌بینند. آیا این الزاماً خطاست؟

Two VMs both use NAT but cannot see one another. Is this necessarily a fault?

پاسخ

نه؛ VirtualBox NAT per-VM می‌تواند شبکه‌های خصوصی جدا بسازد. برای ارتباط مهمان‌ها NAT Network، host-only یا internal network را با هدف انتخاب کن.

No. VirtualBox per-VM NAT can create separate private networks. Choose NAT Network, host-only, or internal networking when guests need to communicate.

۱۴. bridge در Wi-Fi

روی Wi-Fi bridged guest DHCP نمی‌گیرد. اول چه چیزهایی را بررسی می‌کنی؟

A Wi-Fi bridged guest does not obtain DHCP. What do you inspect first?

پاسخ

adapter انتخاب‌شده، bridge driver و محدودیت access point/host OS را. DHCP static workaround را تا تشخیص لایه‌ها راه‌حل قطعی ندان.

Check the selected adapter, bridge driver, and access-point/host-OS restrictions. Do not treat a guessed static address as a definitive fix.

۱۵. DNS یا مسیر؟

guest IP بیرونی را curl می‌کند اما `getent hosts` نام را پیدا نمی‌کند. کدام لایه را جدا بررسی می‌کنی؟

The guest can curl an external IP, but `getent hosts` cannot resolve a name. Which layer do you inspect?

پاسخ

DNS resolver/configuration؛ default route به نظر می‌رسد مسیر IP را می‌دهد، اما DNS مستقل است. `resolvectl status` و DNS server دسترس‌پذیری را ببین.

Inspect DNS resolver/configuration. The default route appears to provide IP connectivity, but DNS is separate. Check `resolvectl status` and DNS-server reachability.

۱۶. host-only DHCP خاموش

host-only link up است ولی guest آدرس نگرفته. DHCP server خاموش است. دو راه چیست؟

Host-only link is up, but the guest has no address. Its DHCP server is off. What are two options?

پاسخ

DHCP همان host-only network را فعال کن یا IP استاتیک معتبر در subnet مشترک به host/guest بده؛ قبلش از overlap با LAN مطمئن شو.

Enable DHCP on that host-only network, or assign valid static addresses in a shared subnet to host and guest; first check for LAN overlap.

۱۷. بیشترین دسترسی لازم نیست

مهمان فقط باید SSH را از laptop host بگیرد. bridge عمومی انتخاب می‌کنی؟

The guest only needs SSH from the host laptop. Do you choose public LAN bridging?

پاسخ

نه؛ host-only یا NAT با forward محدود به loopback کفایت می‌کند و exposure کمتری دارد. mode را بر اساس مبدأ واقعی client انتخاب کن.

No. Host-only or NAT with a loopback-only forward should suffice with less exposure. Choose based on the actual client location.

۱۸. incident شبکه

guest IP و default route دارد، بیرون را می‌بیند، اما LAN SSH نمی‌گیرد. mode NAT است؛ SSH روی `0.0.0.0:22` گوش می‌دهد و firewall guest اجازه می‌دهد. علت محتمل و امن‌ترین قدم چیست؟

The guest has an IP and default route and can reach outside, but LAN SSH fails. It uses NAT; SSH listens on `0.0.0.0:22` and the guest firewall allows it. What is likely, and what is the safest next step?

معیار پاسخ

NAT inbound مستقیم ندارد؛ برای دسترسی فقط از host، loopback-bound port forward بساز و `ssh -p ... localhost` را verify کن. اگر همهٔ LAN باید وصل شود، bridged را فقط با اجازه و firewall میزبان/guest انتخاب کن.

Ordinary NAT has no direct inbound path. For host-only access, create a loopback-bound forward and verify with `ssh -p ... localhost`. If the whole LAN needs access, choose bridged mode only with permission and suitable host/guest firewalls.

به‌جای پرسیدن «شبکه کار می‌کند؟» مسیر را مشخص کنInstead of asking “does networking work?”, name the path

NAT معمولاً guest را برای outbound بیرون می‌برد ولی inbound مستقیم را نمی‌پذیرد؛ port forward یک استثنای محدود می‌سازد. bridge guest را به LAN می‌آورد و در عوض باید exposure و policy واقعی شبکه را در نظر بگیری. host-only ارتباط را بین host و مهمان‌ها نگه می‌دارد و معمولاً upstream ندارد. DHCP، IP و route هرکدام فقط بخشی از این مسیر را ثابت می‌کنند.

NAT commonly gives the guest outbound access without direct inbound reachability; a port forward adds one narrow exception. Bridging puts the guest on the LAN, so real network exposure and policy matter. Host-only keeps communication between host and guests and usually has no upstream. DHCP, address, and route each prove only part of the path.

دفعهٔ بعد timeout دیدی، مبدأ و مقصد را با port بنویس، بعد mode، address، route، listener و firewall را به ترتیب بررسی کن. فصل بعد route و چند adapter را دنبال می‌کنیم؛ حالا دیگر «یک IP گرفته» را با «از همه‌جا قابل‌دسترسی است» یکی نمی‌گیری.

Next time you see a timeout, write down source, destination, and port, then inspect mode, address, route, listener, and firewall in order. Next chapter follows routes and multiple adapters; for now, an assigned IP no longer means “reachable from everywhere.”
