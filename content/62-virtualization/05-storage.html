ذخیره‌سازی

Storage

وقتی guest می‌گوید «دیسک پر است»، هنوز نمی‌دانیم کدام لایه جا ندارد. این فصل یک نوشتن را از filesystem داخل VM تا image روی host دنبال می‌کند.

When a guest says “disk full,” we do not yet know which layer ran out. This chapter follows a write from the guest filesystem to the image on the host.

۱۸تمرینexercises

دیسک مجازی را بزرگ کردی؛ چرا `df` تغییر نکرد؟You enlarged the virtual disk. Why did `df` stay the same?

یک VM آزمایشگاهی می‌گوید `/` تقریباً پر است. دیسک مجازی را از ۲۰ به ۳۰ GiB افزایش می‌دهی. پنل host عدد تازه را نشان می‌دهد، ولی داخل Linux هنوز همان فضای قبلی در دسترس است. آیا تغییر اعمال نشده؟ نه لزوماً. بین دکمهٔ resize و فضای آزاد guest چند لایه قرار دارد.

A lab VM reports that `/` is nearly full. You grow its virtual disk from 20 to 30 GiB. The host panel shows the new size, but Linux still has the same free space. Did the resize fail? Not necessarily. Several layers sit between a resize control and free space inside the guest.

اول نام هر لایه را پیدا می‌کنیم، بعد یک دیسک دوم disposable می‌سازیم و آن را از ابتدا تا mount جلو می‌بریم. آخر کار فقط ظرفیت virtual disk را زیاد می‌کنیم تا عمداً با حالتی روبه‌رو شویم که دستگاه بزرگ‌تر شده، اما partition و filesystem هنوز اندازهٔ قبلی‌اند.

First we identify each layer, then create a disposable second disk and take it all the way to a mounted filesystem. At the end, we enlarge only the virtual device and deliberately observe the state where the device is larger but its partition and filesystem are not.

یک فایل، چند لایهOne file, several layers

داخل guest، برنامه به فایل می‌نویسد؛ filesystem آن را روی partition ثبت می‌کند؛ partition بخشی از virtual block device است؛ hypervisor آن device را به imageای مثل `qcow2` یا `raw` وصل می‌کند؛ و فایل image روی filesystem یا storage واقعی host قرار دارد. پرشدن یا خرابی هر لایه می‌تواند شبیه «دیسک پر است» دیده شود، پس `df` مهمان کل داستان نیست.

Inside the guest, an application writes a file; the filesystem records it on a partition; the partition sits on a virtual block device; the hypervisor maps that device to an image such as `qcow2` or `raw`; and the image itself lives on a host filesystem or storage system. A problem at any layer can look like “the disk is full,” so guest `df` is not the whole story.

فلش مسیر نگاشت دستگاه به فایل را نشان می‌دهد. برای بزرگ‌کردن فضای قابل‌استفادهٔ guest باید از سمت image به داخل حرکت کنیم: device، partition، filesystem.

Arrows show how a device maps to a file. To increase usable guest space, work from the image inward: device, partition, filesystem.

`lsblk -f` داخل guest می‌گوید partitionها و filesystemهای شناخته‌شده کدام‌اند؛ `df -hT` فقط filesystemهای mountشده و فضای آن‌ها را می‌سنجد. روی host، `qemu-img info` برای اندازهٔ مجازی و اندازهٔ مصرفی image مفید است. این سه خروجی دربارهٔ لایه‌های متفاوت حرف می‌زنند.

Inside the guest, `lsblk -f` lists recognised partitions and filesystems; `df -hT` reports mounted filesystems and their space. On the host, `qemu-img info` helps distinguish an image’s virtual size from its host disk usage. These outputs describe different layers.

raw و qcow2: ساده در برابر امکانات بیشترraw and qcow2: simplicity versus features

`raw` تصویر ساده‌ای از block device است و overhead فرمت کمی دارد؛ اما به‌تنهایی metadata فرمت‌دار، backing chain یا snapshot داخلی qcow2 را ندارد. اگر host filesystem از sparse file پشتیبانی کند، raw هم می‌تواند hole داشته باشد؛ پس «raw همیشه کل ظرفیت را از لحظهٔ اول می‌گیرد» درست نیست.

`raw` is a simple representation of a block device with little format overhead, but it does not provide qcow2’s format metadata, backing chains, or internal snapshots by itself. If the host filesystem supports sparse files, raw can also contain holes; “raw always consumes its full capacity immediately” is not universally true.

`qcow2` metadata و copy-on-write دارد و می‌تواند با نوشتن رشد کند. برای دیدن تفاوت ظرفیت مجازی و مصرف واقعی روی host، فقط image خاموش و غیرمشترک را بررسی کن:

`qcow2` has metadata and copy-on-write features, and it can grow as writes occur. To compare virtual capacity with host usage, inspect only an image that is offline and not shared:

qemu-img info /path/to/lab-data.qcow2
ls -lh /path/to/lab-data.qcow2
du -h /path/to/lab-data.qcow2

در خروجی `qemu-img info` فیلد `virtual size` ظرفیت guest و `disk size` اندازهٔ مصرفی گزارش‌شده است. `ls -lh` طول منطقی فایل را می‌گوید؛ `du` بلوک‌های host را که فایل واقعاً اشغال می‌کند تخمین می‌زند. نتیجه به host filesystem، allocation و featureهای image بستگی دارد. هیچ‌کدام سرعت disk را ثابت نمی‌کنند.

In `qemu-img info`, `virtual size` is guest-visible capacity and `disk size` is reported host use. `ls -lh` shows logical file length; `du` estimates host blocks actually occupied. Results depend on the host filesystem, allocation, and image features. None proves disk performance.

قانون image: `qemu-img` ابزار آفلاین است. image ماشین روشن یا هم‌زمان توسط process دیگری باز را با آن تغییر نده؛ metadata می‌تواند خراب شود یا داده از بین برود. پیش از هر عملیات تغییردهنده، VM را خاموش، نام و format image را دوباره تأیید و نسخهٔ پشتیبان قابل‌بازگشت داشته باش.

Image rule: `qemu-img` is an offline image tool. Do not modify an image used by a running VM or another process; metadata can be corrupted or data lost. Before any change, power off the VM, re-check the image path and format, and have a recoverable backup.

یک دیسک دوم بساز؛ دیسک سیستم را دست‌نزنAdd a second disk; leave the system disk alone

در `virt-manager` یک VM آزمایشگاهی را خاموش کن و از جزئیات آن یک storage volume تازهٔ ۴ GiB از نوع qcow2 بساز و به VM وصل کن. دیسک تازه باید خالی و disposable باشد. قبل از boot، `virsh domblklist vm-a --details` را روی host بزن تا ببینی کدام target به کدام source وصل شده؛ اسم‌ها ممکن است با نمونه فرق کنند.

Shut down a lab VM in virt-manager, create a fresh 4 GiB qcow2 storage volume from its details, and attach it. The new disk must be empty and disposable. Before booting, run `virsh domblklist vm-a --details` on the host to map each target to its source; names may differ from the example.

virsh domblklist vm-a --details

داخل guest، `lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS` بزن. دستگاه جدید معمولاً دیسک بدون partition مثل `/dev/vdb` است؛ در سیستم تو شاید نام دیگری داشته باشد. بر اساس «اندازه، TYPE=disk و نبودن mountpoint» پیدایش کن، نه با حفظ‌کردن نام. اگر دربارهٔ دستگاه شک داری، ادامه نده.

Inside the guest, run `lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS`. The new device is usually an unpartitioned disk such as `/dev/vdb`, but your system may use another name. Identify it by size, `TYPE=disk`, and absence of a mountpoint—not by memorising a name. If uncertain, stop.

قبل از ساخت partition، output را نگه دار و مطمئن شو دیسک تازه است. فرمان‌های بعدی جدول partition دستگاه انتخاب‌شده را می‌نویسند و هر دادهٔ قبلی آن را از دسترس خارج می‌کنند؛ فقط روی همان دیسک خالی آزمایش اجرا کن. در `parted`، GPT و یک partition از 1 MiB تا انتهای فضای مجازی می‌سازیم:

Save the output and confirm the disk is new before creating a partition. The next commands write a partition table and can make existing data inaccessible; run them only on that empty test disk. In `parted`, create GPT and one partition from 1 MiB to the end of the virtual device:

sudo parted --script /dev/vdb mklabel gpt
sudo parted --script /dev/vdb mkpart primary ext4 1MiB 100%
lsblk -f /dev/vdb

اگر دستگاه تو `/dev/vdb` نیست، هر دو فرمان را با نام درست جایگزین کن. `lsblk` باید partition تازه‌ای مثل `/dev/vdb1` نشان دهد؛ این فقط جدول partition را ثابت می‌کند، هنوز filesystem نداری. برای filesystem، target را دوباره بررسی کن و فقط partition جدید را format کن:

If your device is not `/dev/vdb`, substitute its verified name in both commands. `lsblk` should show a new partition such as `/dev/vdb1`; that proves the partition table, not a filesystem. Re-check the target, then format only the new partition:

sudo mkfs.ext4 /dev/vdb1
sudo mkdir -p /srv/labdata
sudo mount /dev/vdb1 /srv/labdata
findmnt /srv/labdata
df -hT /srv/labdata

`findmnt` باید source و mountpoint را نشان بدهد و `df -hT` نوع ext4 و ظرفیت را. اگر فقط `lsblk` partition می‌دیدی ولی `df` چیزی نداشت، mount انجام نشده بود. حالا یک فایل آزمایشی بساز و verify کن در همین mount نوشته شده است؛ بعد از unmount هم باید همچنان روی partition بماند.

`findmnt` should show the source and mountpoint; `df -hT` should show ext4 and its capacity. If `lsblk` showed a partition but `df` did not, it was not mounted. Write a test file and verify it lives on this mount; it should remain on the partition after unmounting.

printf 'storage lab\n' | sudo tee /srv/labdata/check.txt
findmnt -T /srv/labdata/check.txt
sudo umount /srv/labdata
sudo mount /dev/vdb1 /srv/labdata
cat /srv/labdata/check.txt

نام `/dev/vdb1` ممکن است بعد از تغییر ترتیب deviceها عوض شود. برای mount پایدار، UUID را از `blkid` بگیر و در `/etc/fstab` ثبت کن؛ UUID را از خروجی خودت بردار، مقدار ساختگی کپی نکن. پیش از reboot، با `mount -a` خطای syntax را بگیر و `findmnt` را دوباره verify کن.

A device name such as `/dev/vdb1` may change when device order changes. For a persistent mount, read its UUID with `blkid` and place that value in `/etc/fstab`; use your own UUID, not a copied example. Run `mount -a` before reboot to catch syntax errors, then verify with `findmnt`.

sudo blkid /dev/vdb1
# Add this form to /etc/fstab, replacing the UUID with your own:
UUID=YOUR-UUID /srv/labdata ext4 defaults 0 2
sudo mount -a
findmnt /srv/labdata

این مسیر تازه فقط یک disk مهمان را format می‌کند؛ هرگز `/dev/sda` یا `/dev/vda` را از روی این مثال فرض نکن. نام درست را با `lsblk`, `virsh domblklist` و ظرفیت مورد انتظار تطبیق بده؛ حتی `mkfs` را یک‌بار اشتباه اجرا کنی، می‌تواند سیستم‌عامل را خراب کند.

This procedure formats only the new guest disk. Never assume `/dev/sda` or `/dev/vda` from this example. Match the device using `lsblk`, `virsh domblklist`, and expected capacity; one mistaken `mkfs` can damage the operating system.

خرابی عمدی: image بزرگ شد، filesystem نهDeliberate fault: the image grew, not the filesystem

حالا قبل از resize، سه عدد ثبت کن: اندازهٔ image روی host، اندازهٔ block device در guest و ظرفیت `df` روی mount. VM را خاموش کن. مسیر image را از `virsh domblklist`/pool پیدا کن و با `qemu-img info` بررسی کن که format واقعاً qcow2 است و backing file ندارد. اگر روشن‌بودن، format، path یا زنجیرهٔ image مبهم است، دستور resize نزن.

Before resizing, record three values: image size on the host, guest block-device size, and `df` capacity on the mount. Shut down the VM. Find the image through `virsh domblklist`/the pool and use `qemu-img info` to confirm it is qcow2 and has no backing file. If VM state, format, path, or image chain is unclear, do not resize.

این آزمایش فقط برای volume دوم و disposable است؛ اول مطمئن شو فایل پشتیبان داری و مسیر دقیق همان volume است. volume را از ۴ به ۶ GiB بزرگ می‌کنیم، نه کوچک؛ چون image در pool libvirt مدیریت می‌شود، از `vol-resize` استفاده می‌کنیم:

This experiment is only for the second disposable volume; first ensure a backup exists and the exact path identifies that volume. Because libvirt manages this pool volume, use `vol-resize` to grow it from 4 to 6 GiB—never shrink it:

virsh vol-info lab-data.qcow2 --pool default
virsh vol-resize lab-data.qcow2 2G --pool default --delta
virsh vol-info lab-data.qcow2 --pool default
qemu-img info /var/lib/libvirt/images/lab-data.qcow2

`virsh vol-info` باید capacity برابر ۶ GiB نشان دهد؛ `qemu-img info` نیز `virtual size` تازه را نشان می‌دهد و `disk size` ممکن است همچنان کمتر باشد چون هنوز داده‌ای در بخش تازه ننوشته‌ای. اگر بعد از دستور host file length را ببینی، guest هنوز روشن نیست؛ VM را boot کن و `lsblk` و `df -hT /srv/labdata` را مقایسه کن. انتظار: device حدود ۶ GiB است، ولی partition و filesystem هنوز حدود ۴ GiB ظرفیت دارند.

`virsh vol-info` should show a 6 GiB capacity; `qemu-img info` should report the new virtual size, while disk size may remain smaller because no data has been written in the new area. Boot the VM and compare `lsblk` with `df -hT /srv/labdata`. Expected: the device is about 6 GiB, while the partition and filesystem still have about 4 GiB.

این دقیقاً همان جایی است که «disk resize نشد» معمولاً تشخیص درستی نیست: device بزرگ شده، اما partition انتهای قبلی را نگه داشته و filesystem هم روی همان partition جا دارد. برای Linux با یک partition انتهایی و ext4، بعد از ثبت backup، اول partition را تا انتها گسترش می‌دهیم. روی Ubuntu/Debian ابزار `growpart` معمولاً از بستهٔ `cloud-guest-utils` می‌آید؛ اگر نصب نیست، package را از منبع distro نصب کن و نام دیسک/شمارهٔ partition را دقیق جایگزین کن.

This is where “the disk resize failed” is often the wrong diagnosis: the device grew, but the partition still ends at its old boundary and the filesystem remains inside that partition. For Linux with one final partition and ext4, after confirming a backup, grow the partition to the end. On Ubuntu/Debian, `growpart` is commonly supplied by `cloud-guest-utils`; if absent, install the distro package and substitute the exact disk and partition number.

sudo growpart /dev/vdb 1
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS

اینجا `growpart` نام دیسک و شمارهٔ partition را جدا می‌گیرد: `/dev/vdb` و `1`، نه `/dev/vdb1`. پس از اجرا، partition باید نزدیک ۶ GiB شود. حالا filesystem ext4 را روی همان partition رشد بده و نتیجه را با `df` بسنج:

`growpart` takes the disk and partition number separately: `/dev/vdb` and `1`, not `/dev/vdb1`. Afterward, the partition should be close to 6 GiB. Grow the ext4 filesystem on that partition and verify with `df`:

sudo resize2fs /dev/vdb1
df -hT /srv/labdata
lsblk -f

حالا `df` باید ظرفیت تازه را نزدیک به ۶ GiB ببیند؛ چند بلوک را metadata مصرف می‌کند. اگر filesystem از نوع XFS بود، فرمان resize فرق می‌کند و معمولاً روی mountpoint اجرا می‌شود: `sudo xfs_growfs /srv/labdata`. فرمان filesystem را بر اساس `lsblk -f` انتخاب کن، نه با حدس. اگر GPT backup header دربارهٔ فضای تازه هشدار می‌دهد، ابزار partition را دوباره بررسی کن؛ فرمان format را تکرار نکن.

`df` should now report capacity close to 6 GiB; metadata consumes some blocks. If the filesystem were XFS, the command differs and is usually run on its mountpoint: `sudo xfs_growfs /srv/labdata`. Choose the filesystem operation from `lsblk -f`, not by guessing. If GPT reports a backup-header issue at the new end, inspect the partition tool; do not repeat the format command.

حذف فایل یعنی host حتماً فضا پس گرفت؟Does deleting a file always return space to the host?

نه همیشه. guest ممکن است sectorهای آزادشده را به virtual disk اطلاع ندهد؛ در نتیجه image thin روی host حتی بعد از حذف داده بزرگ بماند. TRIM/discard راهی برای اعلام بلوک‌های آزاد است، اما زنجیرهٔ filesystem مهمان، virtual controller، تنظیم hypervisor و storage میزبان باید پشتیبانی کند. آن را با `fstrim -av` در guest می‌توانی امتحان کنی؛ خروجی فقط مقدارهایی را گزارش می‌کند که قابل trim تشخیص داده شده‌اند.

Not always. The guest may not tell the virtual disk which sectors became free, so a thin host image can remain large after deletion. TRIM/discard communicates freed blocks, but the guest filesystem, virtual controller, hypervisor settings, and host storage must all support it. You can try `fstrim -av` in the guest; its output reports only ranges recognised as trim-capable.

پشتیبانی discard در `virt-manager`/libvirt به disk device و driver تنظیم‌شده و storage backend بستگی دارد. آن را فعال‌کردن تضمین نمی‌کند که فایل qcow2 فوراً به کوچک‌ترین اندازه برگردد؛ metadata، fragmentation، snapshotها و host filesystem هم اثر دارند. اندازه را با `qemu-img info` فقط وقتی VM خاموش است و با `du` روی host مقایسه کن. عملکرد هم به storage path و controller وابسته است، نه فقط اسم `qcow2` یا `raw`.

Discard support in virt-manager/libvirt depends on the disk device, driver configuration, and storage backend. Enabling it does not guarantee that a qcow2 file immediately shrinks to its smallest possible size; metadata, fragmentation, snapshots, and host filesystem behaviour matter too. Compare `qemu-img info` only while the VM is off and `du` on the host. Performance also depends on the storage path and controller, not just whether the format is `qcow2` or `raw`.

آزمایش پیوسته: از volume خالی تا فضای قابل‌استفادهA continuous lab: from an empty volume to usable space

از همان دیسک دوم استفاده کن؛ یک VM disposable، image پشتیبان، و مقصد mount `/srv/labdata`. پیش از هر تغییر وضعیت VM، device name و capacity را یادداشت کن. روند را به چهار checkpoint تقسیم کن: attached device، partition، filesystem/mount، و اندازهٔ جدید. اگر یکی از checkpointها شکست خورد، به مرحلهٔ قبلی برگرد و evidence را بخوان؛ چند فرمان تغییردهنده را پشت سر هم کورکورانه اجرا نکن.

Use the same second disk, a disposable VM, a backup image, and `/srv/labdata` as the mountpoint. Before each change, record VM state, device name, and capacity. Keep four checkpoints: attached device, partition, filesystem/mount, and grown capacity. If one fails, stop at that layer and inspect evidence; do not blindly run a series of modifying commands.

برای بررسی نهایی، فایل `check.txt` را از mount بخوان، `findmnt` را اجرا کن، UUID را با `blkid` مقایسه کن و `df -hT` را نگه دار. بعد VM را خاموش و `qemu-img info` را روی image اجرا کن. گزارش باید فرق `virtual size` و `disk size` را توضیح دهد و بگوید کدام فرمان اندازهٔ image، کدام فرمان partition و کدام فرمان filesystem را تغییر داد.

For final verification, read `check.txt` from the mount, run `findmnt`, compare the UUID with `blkid`, and save `df -hT`. Then shut down the VM and run `qemu-img info` on the image. Your report must distinguish `virtual size` from `disk size`, and identify which operation changed the image, the partition, and the filesystem.

اگر مسیر یا دستگاه مشکوک است، توقف کن. اسم device می‌تواند تغییر کند؛ عدد اندازه به‌تنهایی هویت را ثابت نمی‌کند. تا وقتی host target، guest device و ظرفیت آزمایشی با هم جور نیستند، `mkfs`, `qemu-img resize` یا `growpart` را اجرا نکن.

If the path or device is uncertain, stop. Device names can change, and size alone does not establish identity. Do not run `mkfs`, `qemu-img resize`, or `growpart` until host target, guest device, and expected test capacity agree.

پشتوانهٔ qcow2 را فقط بشناس؛ نوبتش فصل بعد استRecognise qcow2 backing files; their turn is next chapter

qcow2 می‌تواند فقط تغییرات را نسبت به image پایه در فایل دیگری نگه دارد. به آن backing file می‌گویند؛ اگر فایل پایه جابه‌جا یا حذف شود، زنجیرهٔ image ممکن است ناقص و داده ناخوانا شود. `qemu-img info --backing-chain` زنجیره را نشان می‌دهد. فعلاً زنجیره نساز یا rebase نکن؛ فصل بعد دربارهٔ clone و snapshot به آن برمی‌گردیم.

A qcow2 image can store only changes relative to a base image in another file, called a backing file. If that base is moved or deleted, the image chain may become incomplete and data unreadable. `qemu-img info --backing-chain` shows the chain. Do not create or rebase one yet; snapshots and clones are next chapter.

۱. سه اندازهٔ متفاوت

`qemu-img info` ظرفیت مجازی ۲۰ GiB، `du` مقدار ۷ GiB و `df` داخل guest مقدار ۱۲ GiB نشان می‌دهد. آیا خروجی‌ها با هم تناقض دارند؟

`qemu-img info` reports a 20 GiB virtual size, `du` reports 7 GiB, and guest `df` reports 12 GiB. Do these outputs conflict?

پاسخ

نه؛ به‌ترتیب ظرفیت device، مصرف فیزیکی تقریبی host و ظرفیت filesystem mountشده را می‌سنجند. مقدارها متعلق به سه لایه‌اند.

No. They report device capacity, approximate host allocation, and mounted guest filesystem capacity—three different layers.

۲. raw همیشه fully allocated؟

درست یا غلط: فایل raw همیشه از لحظهٔ ساخت تمام فضای virtual size را روی host مصرف می‌کند.

True or false: a raw image always consumes its full virtual size on the host immediately.

پاسخ

غلط؛ host filesystem ممکن است sparse file و hole داشته باشد. نوع فایل‌سیستم و شیوهٔ preallocation نتیجه را عوض می‌کند.

False. The host filesystem may support sparse files and holes. Filesystem and preallocation settings change the result.

۳. کدام دستگاه را format کنم؟

`lsblk` نشان می‌دهد `/dev/vda` روی `/` mount است و `/dev/vdb` خالی با ظرفیت ۴ GiB است. مقصد آزمایش کدام است؟

`lsblk` shows `/dev/vda` mounted at `/` and an empty 4 GiB `/dev/vdb`. Which device is the lab target?

پاسخ

فقط `/dev/vdb` disposable؛ قبل از format نام و ظرفیت را دوباره با `lsblk` و `virsh domblklist` تطبیق بده.

Only the disposable `/dev/vdb`. Reconfirm name and size with `lsblk` and `virsh domblklist` before formatting.

۴. partition بدون filesystem

`lsblk` partition `/dev/vdb1` نشان می‌دهد، اما `lsblk -f` نوعی ثبت نکرده و `df` آن را نمی‌بیند. چه چیزی کم است؟

`lsblk` shows `/dev/vdb1`, but `lsblk -f` shows no type and `df` does not list it. What is missing?

پاسخ

filesystem و mount. روی همان partition خالی آزمایش، filesystem بساز؛ سپس mount و `findmnt` را تأیید کن.

A filesystem and mount. Create a filesystem only on the confirmed empty lab partition, then mount it and verify with `findmnt`.

۵. format اشتباه

مهمان ext4 دارد ولی تو دستور `xfs_growfs` را روی آن اجرا می‌کنی. کدام مدرک باید انتخاب فرمان را تعیین کند؟

The guest has ext4, but you run `xfs_growfs`. Which evidence should determine the tool?

پاسخ

`lsblk -f` و `df -T` نوع filesystem را نشان می‌دهند؛ ext4 با `resize2fs` و XFS با `xfs_growfs` رشد می‌کند، با پیش‌شرط‌های متفاوت.

Use `lsblk -f` and `df -T` to identify the filesystem. ext4 uses `resize2fs`; XFS uses `xfs_growfs`, with different prerequisites.

۶. mount بعد از reboot گم شد

دیسک دستی mount می‌شود اما بعد از reboot نه. چه راهی پایدارتر است؟

The disk mounts manually but not after reboot. What is a more stable approach?

پاسخ

UUID را با `blkid` بگیر، در `/etc/fstab` ثبت کن، پیش از reboot `mount -a` را آزمایش و با `findmnt` verify کن. device name ممکن است تغییر کند.

Read the UUID with `blkid`, add it to `/etc/fstab`, test with `mount -a`, and verify with `findmnt` before reboot. Device names may change.

۷. guest فضای تازه نمی‌بیند

image از ۴ به ۶ GiB رسیده، `lsblk` هنوز ۴ GiB است. کدام مرز را اول بررسی می‌کنی؟

The image is now 6 GiB, but `lsblk` still shows 4 GiB. Which boundary do you inspect first?

پاسخ

آیا VM خاموش/روشن شده و hypervisor ظرفیت تازه را به block device guest نشان داده؟ `virsh domblklist` و `lsblk` را تطبیق بده؛ هنوز سراغ filesystem نرو.

Check whether the VM has been restarted and the hypervisor exposes the new capacity to the guest block device. Compare `domblklist` and `lsblk` before touching the filesystem.

۸. device بزرگ، partition قدیمی

`lsblk` دیسک ۶ GiB و partition ۴ GiB می‌بیند؛ `df` هم ۴ GiB است. چه لایه‌ای هنوز رشد نکرده؟

`lsblk` shows a 6 GiB disk and a 4 GiB partition; `df` also shows 4 GiB. Which layer has not grown?

پاسخ

partition هنوز انتهای قبلی را دارد؛ پس از backup و تأیید ساختار، partition را گسترش بده و بعد filesystem را جداگانه رشد بده.

The partition still ends at its old boundary. After backup and layout verification, grow the partition, then grow the filesystem separately.

۹. partition رشد کرد

`lsblk` partition را ۶ GiB نشان می‌دهد ولی `df` هنوز ۴ GiB است. قدم بعدی چیست؟

`lsblk` shows a 6 GiB partition, but `df` remains 4 GiB. What is next?

پاسخ

filesystem هنوز رشد نکرده؛ نوع آن را با `lsblk -f` تأیید و ابزار درست، مثل `resize2fs` برای ext4، را اجرا کن.

The filesystem has not grown. Confirm its type with `lsblk -f`, then use the matching tool, such as `resize2fs` for ext4.

۱۰. UUID بهتر از vdb1

چرا در `/etc/fstab` بهتر است UUID ثبت شود تا `/dev/vdb1`؟

Why is a UUID generally preferable to `/dev/vdb1` in `/etc/fstab`?

پاسخ

ترتیب deviceها ممکن است تغییر کند؛ UUID به filesystem مشخص وصل است. باز هم باید fstab را با `mount -a` آزمایش کرد.

Device ordering can change; a UUID identifies the filesystem. The fstab entry still needs testing with `mount -a`.

۱۱. image در حال استفاده

VM روشن است و می‌خواهی `qemu-img resize` را روی image آن اجرا کنی. مجاز است؟

The VM is running and you want to run `qemu-img resize` on its image. Is that safe?

پاسخ

نه؛ QEMU هشدار می‌دهد image درحال‌استفاده را با qemu-img تغییر نده. VM را خاموش کن و اگر live resize می‌خواهی، قابلیت و syntax libvirt/hypervisor خودت را جدا verify کن.

No. QEMU warns against modifying an image in use. Power off the VM; if you need live resize, verify your specific libvirt/hypervisor support and syntax first.

۱۲. thin یعنی نامحدود؟

چند qcow2 هرکدام ظرفیت مجازی ۱۰۰ GiB دارند اما host فقط ۸۰ GiB جا دارد. آیا همین الان امکان نوشتن ۳۰۰ GiB داده هست؟

Several qcow2 images each have 100 GiB virtual capacity, but the host has only 80 GiB free. Can you safely write 300 GiB?

پاسخ

نه؛ thin provisioning مصرف را عقب می‌اندازد، ظرفیت فیزیکی خلق نمی‌کند. رشد جمعی می‌تواند host را پر و همهٔ VMها را متأثر کند.

No. Thin provisioning delays allocation; it does not create physical capacity. Combined growth can fill the host and affect every VM.

۱۳. حذف فایل و فضای host

فایل بزرگی را از guest حذف کردی، ولی `du` روی qcow2 تقریباً تغییری نکرده. یک علت ممکن چیست؟

You deleted a large guest file, but host `du` barely changed for the qcow2 image. Give one possible reason.

پاسخ

guest بلوک‌های آزاد را با discard/TRIM اعلام نکرده، یا backend/زنجیره از آن پشتیبانی نمی‌کند؛ حذف guest به معنی کوچک‌شدن فوری image نیست.

The guest may not have signalled freed blocks via discard/TRIM, or the backend/stack may not support it. Guest deletion does not guarantee immediate image shrinkage.

۱۴. raw در برابر qcow2

برای image ساده با overhead کم و بدون نیاز به backing chain چه گزینه‌ای را بررسی می‌کنی؟ tradeoff چیست؟

For a simple image with low format overhead and no backing-chain need, what format might you consider, and what is the trade-off?

پاسخ

raw گزینه‌ای ساده است؛ قابلیت‌های qcow2 مثل metadata و backing image را به همان شکل ندارد. sparse بودن raw همچنان به host filesystem بستگی دارد.

Raw is a simple option, but it lacks qcow2 features such as its metadata and backing images. Whether raw is sparse still depends on the host filesystem.

۱۵. سرعت را از اندازه حدس نزن

image فقط ۲ GiB روی host اشغال کرده، اما guest کند است. آیا کم‌حجم‌بودن یعنی سریع است؟

The image occupies only 2 GiB on the host, but the guest is slow. Does its small size mean it is fast?

پاسخ

نه؛ اندازهٔ allocation با latency/IOPS یکی نیست. workload، host storage و queueing را جدا اندازه بگیر.

No. Allocation size is unrelated to latency/IOPS. Measure workload, host storage, and queueing separately.

۱۶. backing file پیدا شد

`qemu-img info --backing-chain` فایل پایه‌ای نشان می‌دهد. می‌توانی آن را حذف کنی چون guest هم‌اکنون بالا می‌آید؟

`qemu-img info --backing-chain` shows a base file. Can you delete it because the guest is currently running?

پاسخ

نه؛ child ممکن است برای بلوک‌های تغییرنکرده به base وابسته باشد. مسیر و زنجیره را حفظ کن؛ حذف/جابجایی بدون عملیات آگاه از backing chain می‌تواند داده را ناقص کند.

No. The child may depend on the base for unchanged blocks. Preserve the chain; moving/deleting files without a chain-aware operation can make data incomplete.

۱۷. mount نیست

`lsblk -f` ext4 و UUID را می‌بیند، اما `df -hT` filesystem را نشان نمی‌دهد. چه بررسی می‌کنی؟

`lsblk -f` shows ext4 and a UUID, but `df -hT` does not list the filesystem. What do you check?

پاسخ

filesystem ساخته شده ولی ممکن است mount نشده باشد. `findmnt`, `mount`, و ورودی `/etc/fstab` را ببین؛ format را دوباره اجرا نکن.

The filesystem exists but may not be mounted. Inspect `findmnt`, mounts, and `/etc/fstab`; do not format again.

۱۸. گزارش incident resize

host image را ۶ GiB گزارش می‌کند؛ guest block device هم ۶ GiB، partition چهار GiB، filesystem ext4 چهار GiB. مشکل کدام لایه است و verification بعدی چیست؟

The host image is 6 GiB; the guest block device is also 6 GiB, but the partition and ext4 filesystem are 4 GiB. Which layer is the issue, and what is your next verification?

معیار پاسخ

image و device درست رشد کرده‌اند؛ partition و سپس filesystem باید با ترتیب امن بزرگ شوند. پیش از تغییر، backup، GPT/layout و partition انتهایی را تأیید کن؛ بعد `growpart`, `resize2fs`, `lsblk`, `df -hT` را به‌ترتیب ثبت کن.

The image and device grew; the partition and then filesystem need safe expansion. Before changing anything, verify the backup, GPT/layout, and final partition. Then record `growpart`, `resize2fs`, `lsblk`, and `df -hT` in order.

هر resize را تا داخل guest دنبال کنTrace every resize all the way into the guest

اندازهٔ image روی host یک چیز است، ظرفیت block device چیز دیگر، partition مرز بعدی و filesystem همان جایی است که فایل‌ها فضای قابل‌استفاده می‌بینند. qcow2/raw و thin allocation توضیح می‌دهند host چه‌طور فایل را ذخیره می‌کند؛ آن‌ها جای partition یا filesystem را بزرگ نمی‌کنند. اگر فقط یک فرمان resize زده‌ای، هنوز کار تمام نشده.

Image size on the host is one value, block-device capacity another, the partition is the next boundary, and the filesystem is what makes space usable by files. qcow2/raw and thin allocation describe how the host stores the image; they do not grow a guest partition or filesystem. One resize command does not necessarily finish the job.

وقتی مسیر و device روشن نیست، توقف کن؛ وقتی روشن است، یک لایه را عوض کن و همان لایه را verify کن. در فصل بعد همین رابطهٔ لایه‌ای را برای snapshot و clone بررسی می‌کنیم: چه چیزی کپی می‌شود، چه چیزی مشترک می‌ماند و چه وقت یک image پایه را نمی‌شود پاک کرد.

When the path or device is uncertain, stop. When it is clear, change one layer and verify that layer. Next we apply the same layered thinking to snapshots and clones: what gets copied, what remains shared, and when a base image cannot be deleted.
