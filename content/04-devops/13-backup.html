backup و disaster recovery

Backup and disaster recovery

job می‌گه backup موفق بوده. روز خرابی می‌ریم سراغش و می‌بینیم فایل صفر بایته یا کلید رمزگشایی رو هیچ‌کس نداره. اون backup تا وقتی واقعاً restore نشده، فقط یه ادعاست. این فصل از اون طرف ماجرا شروع می‌کنیم: خراب می‌کنیم، برمی‌گردونیم و با مدرک ثابت می‌کنیم داده برگشته.

A backup that has never been restored is not a proven backup.

۱۸تمرینexercises

فایل نوشته شد؛ آیا داده برمی‌چرخه؟The file exists. Can the data come back?

پیام job می‌گه backup موفق هست؛ بعد از خرابی، فایل صفر بایت هست و اطلاعات دسترسی رمزگشایی پیدا نمی‌شه. این‌بار موفقیت رو با restore به مقصد جدا و پیدا کردن رکورد شناخته‌شده تعریف می‌کنیم.

A job says the backup succeeded. After an outage, the file is empty and the decryption key is missing. This time, success means restoring to a separate destination and finding a known record.

RPO می‌گه چه مقدار داده/زمان رو می‌توان از دست داد؛ RTO سقف زمان برگشت سرویس هست. اگه RPO یک ساعت باشه، فاصلهٔ backupها و replication lag باید با اون سازگار باشه. اگه RTO چهار ساعت هست، restore یک backup چند ترابایتی رو در lab اندازه بگیر؛ حدس نزن.

RPO is the tolerable data-loss window; RTO is the service recovery-time target. If RPO is one hour, backup cadence and replication lag must fit. If RTO is four hours, measure restoring a multi-terabyte backup in a representative environment rather than guessing.

Backup نسخهٔ قابل‌بازیابی برای زمان قبلی هست؛ snapshot تصویر سریع یک storage/volume هست و ممکن هست consistency برنامه رو تضمین نکنه؛ replication خرابی یا حذف اشتباه رو هم تکثیر می‌کنه. برای پایگاه داده از ابزار سازگار خودش و از تنظیمات/کلید لازم هم نسخه بگیر.

A backup is a recoverable point in time; a snapshot is a fast storage image and may not guarantee application consistency; replication may copy corruption or accidental deletion too. Use database-aware backups and preserve required configuration/keys.

کپی تنها کافی نیستOne copy is not a strategy

قاعدهٔ 3-2-1 راهنمای طراحی هست: چند نسخه، روی رسانه/مرزهای متفاوت، و یکی خارج محل. نسخهٔ full ساده‌تر فهمیده می‌شه؛ incremental حجم و زمان روزانه رو کم می‌کنه، اما chain restore و مدت نگه‌داری رو پیچیده‌تر می‌کنه. Encryption باید در انتقال و نگهداری و با کلیدی جدا از backup باشه. Object Lock/WORM حذف یا overwrite نسخه رو برای بازهٔ تعریف‌شده سخت می‌کنه، اما به‌تنهایی restore رو تضمین نمی‌کنه.

The 3-2-1 rule is a design guideline: multiple copies, different media/boundaries, and one offsite. Full backups are easier to reason about; incrementals reduce daily volume but complicate chains, restore, and retention. Encrypt in transit and at rest, keeping keys separate. Object Lock/WORM can prevent deletion/overwrite for a defined period, but does not prove a restore works.

Backup دو شاخه داره: نگهداری خارج مرز و تمرین restore جدا. هیچ فلشی به production برنمی‌چرخه تا تستِ بازیابی دادهٔ اصلی رو overwrite نکنه.

A backup has two paths: offsite retention and isolated restore testing. No arrow overwrites production, so a drill cannot damage live data.

backup پایگاه داده و restore کنار آنBack up a database and restore beside it

از PostgreSQL موقت در پروژهٔ آزمایش استفاده کن. یک رکورد marker بساز، بعد custom archive بگیر؛ pg_dump برای dump سازگار و transactional هست. بعد از دستور، اندازه و checksum رو ثبت کن. checksum برابر ثابت می‌کنه فایل در این آزمون عوض نشده، نه اینکه محتوا کامل یا decryptable هست.

Use a disposable PostgreSQL instance. Insert a marker row, then create a custom archive; pg_dump provides a consistent logical dump. Record size and checksum. A matching checksum proves the file did not change in this test, not that it is complete or decryptable.

example · credentials omitted
pg_dump -Fc -h localhost -U app -d orders -f orders.dump
sha256sum orders.dump
pg_restore --list orders.dump

خروجی list باید archive entries نشون بده. برای تمرین حذف/فساد، فقط در clone دورریختنی marker رو حذف کن؛ production رو لمس نکن. مقصد تازه بساز و restore کن.

The listing should show archive entries. To simulate loss, delete the marker only in a disposable clone—never production. Create a fresh target and restore there.

restore to isolated database
createdb -h localhost -U app orders_restore
pg_restore -h localhost -U app -d orders_restore --exit-on-error orders.dump
psql -h localhost -U app -d orders_restore -c "select id, note from backup_probe;"

رکورد marker در orders_restore مدرک restore منطقی هست. این تمرین object-level و تنظیمات/secrets یا زمان recovery production رو نمی‌سنجه؛ آن‌ها رو در runbook و تمرین جدا بگنجان. نسخه‌های ابزار client/server رو با مستندات PostgreSQL همون نسخه تطبیق بده.

The marker in orders_restore proves a logical restore. This test does not cover object-level state, configuration/secrets, or production recovery time; include those in separate runbooks/drills. Match client/server behavior to the PostgreSQL version docs in use.

سه حالت شکست که success سبز پنهان می‌کنهThree failures a green job can hide

فایل صفر بایت: اندازه و exit کد رو بررسی کن. checksum نداریم: معلوم نیست در انتقال تغییر کرده. restore خطا می‌ده: نسخهٔ ابزار، کلید رمزگشایی، وابستگی و destination رو جدا کن. مقصد restore نباید production باشه. زمان واقعی restore رو ثبت کن و با RTO مقایسه کن؛ اگه از هدف بیشتر شد، runbook/روش/ظرفیت نیاز به تغییر داره.

A zero-byte file: inspect size and exit status. No checksum: transfer integrity is unknown. Restore fails: isolate tool version, decryption key, dependencies, and destination. Never restore over production during a drill. Measure elapsed recovery time against RTO; if it misses, improve the runbook, method, or capacity.

مدت نگه‌داری رو مطابق الزام و نیاز تعیین کن؛ backup قدیمی ممکن هست کلید رمزگشایی نداشته باشه. کپی خارج سایت با همون admin اطلاعات دسترسی مستقل واقعی نیست. Object Lock در object store مشخصی رفتار نسخه/مدت نگه‌داری داره؛ اون رو به هر storage تعمیم نده.

Set retention to match requirements; an old backup may outlive its decryption key. An offsite copy controlled by the same administrator is not a strong independent boundary. Object Lock behavior depends on the object store and versioning; do not generalize it to every storage system.

What evidence first?

Exit status, size, stderr, and destination; a green job is insufficient.

۲. RPO دو ساعت

backup روزانه مناسب هست؟

Is a daily backup enough?

دلیل

نه؛ ممکن هست تا یک روز تغییر از دست بره. cadence/replication رو با RPO بسنج.

No; nearly a day of changes may be lost. Match cadence/replication to RPO.

۳. RTO یک ساعت

کدام کار رو زمان می‌گیری؟

What do you time?

راهنما

بازیابی کامل تا سرویس قابل‌استفاده، نه فقط زمان ساخت فایل dump.

Full recovery to usable service, not merely dump creation time.

۴. snapshot volume

آیا قطعاً DB-consistent هست؟

Is it necessarily database-consistent?

واقعیت

نه؛ باید quiesce/consistency سیاست و ابزار DB رو بدانیم.

No; verify quiescing/consistency policy and database tooling.

۵. replication

آیا حذف اشتباهی رو نجات می‌ده؟

Does replication save accidental deletion?

پاسخ

ممکن هست حذف رو هم replicate کنه؛ نقطهٔ زمانی و backup جدا لازمه.

It may replicate deletion too; retain point-in-time backups separately.

۶. فقط یک disk

چرا offsite لازم می‌شه؟

Why an offsite copy?

دلیل

خرابی یا compromise همون خطا دامنه رو از بین می‌بره.

A failure or compromise may destroy that same failure domain.

۷. 3-2-1

نسخه‌ها روی سه directory یک disk؛ کافی؟

Three directories on one disk—enough?

تفسیر

نه؛ media و خطا boundary مستقل نیستند. این قاعده راهنماست، نه عدد جادویی.

No; media and failure boundaries are not independent. The rule is guidance, not magic.

۸. checksum برابر

What is proven?

Byte equality to a reference—not restorability or database correctness.

۱۰. restore به live

Why not during a drill?

۱۲. incremental chain

کدام ریسک رو تمرین می‌کنی؟

Which risk do you test?

۱۳. Object Lock

آیا immutability صحت backup رو ثابت می‌کنه؟

Does immutability prove backup correctness?

پاسخ

نه؛ فقط تغییر/حذف رو طبق سیاست محدود می‌کنه، restore لازمه.

۱۴. retention نامحدود

چه trade-offی؟

What trade-off?

توضیح

هزینه/سطح حساسیت بالا؛ سیاست، legal hold و lifecycle رو تعیین کن.

Higher cost and sensitive-data exposure; define policy and lifecycle.

۱۵. backup encrypted

کلید رو کنار archive بگذاری؟

Store the key beside the archive?

تصمیم

نه؛ compromise یکجا همه‌چیز رو می‌ده. مسیر کلید و recovery access جدا باشه.

No; one compromise exposes both. Separate key custody and recovery access.

۱۶. restore شش ساعت

نتیجه

نه؛ هدف از دست رفته و باید cadence، architecture یا ظرفیت بهبود یابد.

No; the objective is missed. Improve cadence, architecture, or capacity.

۱۷. marker برگشت

Is a matching checksum enough?

پاسخ

No; verify the record and application behavior on the restored target.

۱۸. گزارش restore drill

آزمون واقعی، restore جداA real test, an isolated restore

آرشیو رو فهرست کردی، checksum گرفتی، به DB تازه restore کردی و رکورد marker رو دیدی. زمان رو با RTO و نقطهٔ داده رو با RPO مقایسه کن؛ اگه هدف نرسید، نتیجهٔ درست «فرایند backup ناموفق هست» هست، نه «فایل هست».
