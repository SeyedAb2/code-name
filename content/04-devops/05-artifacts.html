ساخت artifact و نسخه‌گذاریArtifacts and versioning

یک incident گزارش شده و می‌خواهیم نسخهٔ production را دوباره اجرا کنیم. مخزن source را داریم، tag می‌گوید `v1.4.0`، اما image registry عوض شده و کسی نمی‌داند build فعلی همان build روز انتشار است یا نه. کدام شناسه را باید پیدا می‌کردیم؟

An incident has been reported and we need to rerun the production version. We have the source repository and a `v1.4.0` tag, but the registry image has changed. Nobody knows whether it is the build from release day. Which identifier should we have recorded?

source را داریم؛ اما چیزی که اجرا شد کجاست؟We have the source—but where is what actually ran?

Git می‌گوید کد از کدام commit آمده. ولی artifact خروجی‌ای است که واقعاً اجرا یا نصب می‌شود: image، فایل package، binary یا bundle. اگر دوباره source را build کنیم، ممکن است نسخهٔ dependency، ابزار build یا زمان تولید فرق کند. commit شناسهٔ ورودی است؛ digest شناسهٔ محتوای artifact.

Git tells us which commit the code came from. An artifact is the output that is actually run or installed: an image, package, binary, or bundle. Rebuilding from source may use different dependencies, build tools, or timestamps. A commit identifies input; a digest identifies artifact content.

فصل قبل گفتیم یک artifact را از staging به production promotion بدهیم. این فصل می‌سازد و نگهداری همان artifact را کامل می‌کند: چه نامی برای آدم‌ها خواناست، چه شناسه‌ای محتوا را دقیق مشخص می‌کند، و چطور چند ماه بعد همان خروجی را retrieve کنیم.

Last chapter promoted one artifact from staging to production. This chapter completes its creation and retention: which name is readable to people, which identifier pins the exact content, and how to retrieve that output months later.

commit منبع را نشان می‌دهد؛ tag نام نسخه است؛ digest به محتوای مشخص artifact اشاره می‌کند. artifact در registry یا store می‌ماند تا محیط‌ها همان را بگیرند و rollback ممکن باشد.

The commit identifies source; a tag names a version; a digest identifies artifact content. A registry or store retains the artifact for deployments and rollback.

هیچ‌کدام این شناسه‌ها به‌تنهایی «build امن» را ثابت نمی‌کنند. برای زنجیرهٔ قابل‌اعتمادتر، commit، تنظیمات build، dependencyها و خروجی را به هم وصل می‌کنیم و در صورت نیاز SBOM یا provenance اضافه می‌کنیم.

None of these identifiers alone proves a build is safe. For stronger traceability, connect commit, build configuration, dependencies, and output—and add an SBOM or provenance when needed.

SemVer فقط وقتی معنا دارد که قرارداد نسخه داشته باشیSemVer matters only when a version has a contract

فرض کن package تو یک public API دارد که مصرف‌کننده‌ها به آن تکیه می‌کنند. SemVer به تغییر نسخه معنا می‌دهد: `MAJOR.MINOR.PATCH`. `1.4.2` یعنی major یک، minor چهار، patch دو؛ اما فقط اگر تیم واقعاً قرارداد سازگاری را رعایت کند.

Suppose your package exposes a public API that consumers depend on. SemVer gives version changes meaning: `MAJOR.MINOR.PATCH`. `1.4.2` has major 1, minor 4, and patch 2—but only if the team actually follows the compatibility contract.

بخش نسخهVersion partتغییر نمونهExample changeنسخهٔ پیشنهادیSuggested bump
MAJORتغییر ناسازگار در public API
A breaking change to the public API		1.4.2 → 2.0.0
MINORقابلیت تازه با سازگاری عقب‌رو
Backward-compatible new functionality		1.4.2 → 1.5.0
PATCHرفع باگ سازگار
A backward-compatible bug fix		1.4.2 → 1.4.3

این قانون برای هر فایل و هر container به‌طور خودکار برقرار نیست. اگر سرویسی API عمومی تعریف‌شده ندارد، ممکن است تیم از تقویم انتشار، SHA یا شمارهٔ build استفاده کند. SemVer هم تضمین نمی‌کند نویسنده درست تشخیص داده تغییر ناسازگار بوده یا نه؛ این قرارداد و آزمون سازگاری لازم دارد.

This rule does not automatically apply to every file or container. A service without a defined public API may use calendar releases, a SHA, or build numbers instead. SemVer cannot guarantee that a maintainer correctly identified a breaking change; that takes an explicit contract and compatibility checks.

پیش‌انتشارهایی مثل `2.0.0-rc.1` از نسخهٔ پایدار همان شماره پایین‌ترند. build metadata مثل `1.4.2+sha.a1b2c3d` اطلاعات build می‌دهد اما در تقدم SemVer دخالت ندارد. این رشتهٔ کامل را می‌توان در package metadata یا label ثبت کرد؛ هر مقصدی مجاز نیست آن را عیناً به‌عنوان tag قبول کند.

Prereleases such as `2.0.0-rc.1` have lower precedence than the corresponding stable version. Build metadata such as `1.4.2+sha.a1b2c3d` records build information but does not affect SemVer precedence. Store the full string in package metadata or a label; not every destination accepts it unchanged as a tag.

پرسش قبل از bump: آیا مصرف‌کننده‌ای به این API یا رفتار وابسته است؟ اگر بله، نوع تغییر را نسبت به قرارداد بسنج. اگر نه، اسم نسخهٔ «معنایی» لزوماً اطلاعات معنایی نمی‌دهد.Before a version bump, ask whether a consumer relies on this API or behaviour. If so, classify the change against that contract. If not, a “semantic” version label does not automatically carry semantic information.

tag خواناست؛ digest دقیق استA tag is readable; a digest is exact

در Docker image reference، registry می‌گوید کجا، repository می‌گوید کدام image، tag نامی خوانا برای انسان است و digest محتوای مشخص را می‌شناسد. اگر tag را دوباره به image دیگری بچسبانند، `service:1.4.0` ممکن است فردا بایت‌های دیگری بدهد. tag ذاتاً immutable نیست؛ registry policy می‌تواند نوشتن مجدد tag را ببندد، اما باید آن policy را بررسی کرد.

In a Docker image reference, the registry says where, the repository identifies the image, a tag is a human-readable name, and a digest identifies specific content. If someone moves the tag, `service:1.4.0` may return different bytes tomorrow. A tag is not inherently immutable; a registry policy may prevent retagging, but verify that policy.

یک ظرافت در Docker: tag grammar حروف، عدد، underscore، نقطه و خط تیره را می‌پذیرد، نه `+`. پس `1.4.2+sha.a1b2c3d` نسخهٔ معتبر SemVer است، اما همان رشته tag معتبر Docker نیست. آن را در label نگه دار و برای tag مثلاً `1.4.2` بگذار؛ commit و digest هم جدا ثبت شوند.

One Docker detail: its tag grammar allows letters, digits, underscore, dot, and hyphen—not `+`. Thus `1.4.2+sha.a1b2c3d` is valid SemVer but not a valid Docker tag. Keep it in a label, use a tag such as `1.4.2`, and record commit and digest separately.

digest هم همیشه فقط یک معماری CPU را نشان نمی‌دهد: image چندسکویی می‌تواند یک manifest index داشته باشد که برای هر platform به manifest دیگری می‌رسد. در سطح این فصل digest را به‌عنوان شناسهٔ registry image بخوان؛ وقتی platform مهم است، پلتفرم و digest مربوط را هم ثبت کن.

A digest does not always represent only one CPU architecture: a multi-platform image can have an index manifest pointing to platform-specific manifests. At this level, treat the digest as the registry image identifier; when platform matters, record the platform and relevant digest too.

نسخه، commit و metadata را روی image ثبت کنیمRecord version, commit, and metadata on the image

برای آزمایش یک image کوچک می‌سازیم که فقط فایل نسخه را چاپ می‌کند. دو label می‌گذاریم: نسخهٔ SemVer و Git revision. `ARG` فقط هنگام build وارد می‌شود؛ label metadata را روی image ثبت می‌کند، نه secret را. در پروژهٔ واقعی build باید از commit تمیز و lockfile/ dependencyهای ثبت‌شده بیاید.

We will build a tiny image that prints a version file. Two labels record the SemVer version and Git revision. `ARG` is supplied at build time; a label records metadata on the image, not a secret. In a real project, build from a clean commit and locked dependencies.

Dockerfile · tiny release specimen
FROM alpine:3.22
ARG APP_VERSION
ARG VCS_REF
ARG RELEASE_MARKER
LABEL org.opencontainers.image.version=$APP_VERSION \
      org.opencontainers.image.revision=$VCS_REF
RUN printf '%s\n' "${RELEASE_MARKER:-$APP_VERSION}" > /release.txt
CMD ["cat", "/release.txt"]

برای build، tag خوانا را بده و revision را از Git بگیر؛ برنامهٔ نمونه این دو را در label ثبت می‌کند و نسخه را چاپ می‌کند. این نمونه از `alpine:3.22` با tag استفاده می‌کند تا دستور کوتاه بماند؛ برای build بازتولیدپذیرتر، base image را هم با digest pin کن و آن را آگاهانه به‌روزرسانی کن.

Build with a readable tag and obtain the revision from Git; the sample records both as labels and prints its version. This short example uses `alpine:3.22` by tag; for more reproducible builds, pin the base image by digest and update it deliberately.

bash · build and inspect local metadata
REV=$(git rev-parse HEAD)
docker build \
  --build-arg APP_VERSION=1.4.2 \
  --build-arg VCS_REF="$REV" \
  -t hello-api:1.4.2 .
docker image inspect hello-api:1.4.2 \
  --format '{{json .Config.Labels}}'
docker run --rm hello-api:1.4.2

در labelها `version` و revision موردانتظار را ببین؛ اجرای container باید `1.4.2` چاپ کند. `.Id` محلی image و label commit دربارهٔ metadata می‌گویند، نه registry digest. چون هنوز push نکرده‌ایم، `RepoDigests` ممکن است خالی باشد؛ digest registry را بعد از push/pull می‌گیریم.

Check that the labels contain the expected version and revision; running the container should print `1.4.2`. The local image ID and commit label are not the registry digest. Before pushing, `RepoDigests` may be empty; we will obtain the registry digest after push or pull.

اگر Git repository نداری یا commit ثبت نشده، `git rev-parse HEAD` کار نمی‌کند. برای آزمایش می‌توان revision را رشتهٔ نمونه بگذاری، اما در artifact واقعی مقدار جعلی را به‌جای commit نگذار؛ این کار زنجیرهٔ ردیابی را خراب می‌کند.Without a Git repository or commit, `git rev-parse HEAD` cannot work. You may use a clearly labelled sample string for the lab, but never replace the real source revision with a fake value in a release artifact; that breaks traceability.

خرابی عمدی: `latest` به کدام build اشاره می‌کند؟Deliberate failure: which build does `latest` mean?

دو build متفاوت را با یک نام tag می‌سازیم. فقط روی image تمرینی این کار را انجام بده. اول شناسهٔ build اول را ثبت کن؛ بعد build دوم را دوباره با همان `demo:latest` نام‌گذاری کن. پیش از دیدن خروجی حدس بزن tag قبلی چه می‌شود.

We will build two different images under the same tag. Do this only with the practice image. Record the first build’s ID, then build a second one as `demo:latest` again. Predict what happens to the earlier tag before checking.

bash · move a disposable tag on purpose
docker build --build-arg APP_VERSION=1.4.2 --build-arg RELEASE_MARKER=build-A -t demo:latest .
docker image inspect demo:latest --format '{{.Id}}'
docker build --build-arg APP_VERSION=1.4.2 --build-arg RELEASE_MARKER=build-B -t demo:latest .
docker image inspect demo:latest --format '{{.Id}}'
docker run --rm demo:latest
docker image ls demo

دو image ID باید متفاوت باشند؛ اجرای `demo:latest` باید `build-B` چاپ کند. این مدرک نشان می‌دهد نام tag به محتوای تازه اشاره می‌کند و build قبلی را پیدا نمی‌کند. image قبلی را با نسخهٔ ثابت یا digest جست‌وجو کن؛ policy یک registry ممکن است push مجدد همین tag را محدود کند، اما tag به‌خودی‌خود immutable نیست.

The two image IDs should differ, and running `demo:latest` should print `build-B`. This proves the tag now points to new content and no longer locates the earlier build. Use a fixed version or digest to find the earlier image; a registry policy may block re-pushing the tag, but the tag itself is not immutable.

از این آزمایش نتیجه نگیر که باید از `latest` برای deploy استفاده کنی. نامش به‌تنهایی نه «جدیدترین» را تعریف می‌کند و نه rollback می‌سازد. tag نسخه‌دار برای آدم، digest برای انتخاب دقیق؛ هر دو را همراه commit ثبت کن.

Do not conclude that `latest` is suitable for deployment. The name alone defines neither “latest” nor a rollback. Use a version tag for people and a digest for exact selection; record both with the source commit.

artifact را نگه دار؛ نه فقط اسمش راRetain the artifact, not just its name

registry مثل انبار imageهاست: hostname/namespace/repository مسیر را مشخص می‌کنند و tag یا digest مورد را انتخاب می‌کند. login و push فقط وقتی لازم است که registry در scope آزمایش باشد؛ image خصوصی را عمومی push نکن. فرمان زیر شکل reference را نشان می‌دهد؛ `OWNER` را با namespace واقعی خودت عوض کن.

A registry stores images: hostname, namespace, and repository locate them, while a tag or digest selects one. Login and push are needed only if a registry is in scope; never push a private image publicly. The command below illustrates the reference—replace `OWNER` with your actual namespace.

bash · optional push to a registry you control
docker tag hello-api:1.4.2 ghcr.io/OWNER/hello-api:1.4.2
docker push ghcr.io/OWNER/hello-api:1.4.2
# The registry reports a digest; copy the real value from your output
docker pull ghcr.io/OWNER/hello-api:1.4.2
docker image inspect ghcr.io/OWNER/hello-api:1.4.2 \
  --format '{{json .RepoDigests}}'

در push/pull به خط `Digest: sha256:…` یا `RepoDigests` نگاه کن و مقدار واقعی را در release record ذخیره کن؛ این مقدار برای هر محتوا فرق می‌کند و نباید از نمونهٔ مستندات کپی شود. حالا می‌توان image را با `ghcr.io/OWNER/hello-api@sha256:REAL_DIGEST` pull کرد. digest محتوای انتخاب‌شده را pin می‌کند، نه اینکه image بی‌باگ یا خوش‌منشأ است.

In push/pull output, find `Digest: sha256:…` or `RepoDigests` and save the real value in the release record; it varies by content and must not be copied from documentation examples. The image can then be pulled as `ghcr.io/OWNER/hello-api@sha256:REAL_DIGEST`. A digest pins selected content; it does not prove the image is bug-free or trustworthy.

برای آزمایش بدون registry می‌توان image را archive کرد: `docker image save -o hello-api-1.4.2.tar hello-api:1.4.2` و checksum فایل را با `sha256sum` یا در PowerShell با `Get-FileHash -Algorithm SHA256` ثبت کرد. checksum archive، digest manifest registry نیست؛ هرکدام همان شیئی را شناسایی می‌کنند که hash شده است.

Without a registry, save the image as an archive with `docker image save -o hello-api-1.4.2.tar hello-api:1.4.2`, then record its checksum with `sha256sum` or PowerShell’s `Get-FileHash -Algorithm SHA256`. An archive checksum is not the registry manifest digest; each hash identifies the object it was calculated from.

retention را بر اساس زمان پشتیبانی و rollback تعیین کن: مثلاً چند نسخهٔ آخر و همهٔ نسخه‌هایی که هنوز در production هستند را نگه دار. اگر فقط tag را نگه داری ولی registry image را پاک کند، نام قابل‌خواندن مانده اما چیزی برای deploy نداری. قواعد cleanup را با owner و نیاز قانونی/عملیاتی هماهنگ کن.

Set retention according to support and rollback windows: keep, for example, recent versions and every version still running in production. If the registry image is deleted, a readable tag remains only as a name—you have nothing to deploy. Align cleanup with ownership and operational or legal requirements.

چه کسی ساختش و داخلش چیست؟Who built it, and what is inside?

label نسخه و commit دستی است و مفید؛ اما ممکن است اشتباه یا جعلی باشد. SBOM فهرست اجزای نرم‌افزاری artifact است؛ provenance اطلاعاتی دربارهٔ نحوه و ورودی‌های build می‌دهد. این‌ها به audit کمک می‌کنند، ولی SBOM به‌تنهایی vulnerability scan نیست و provenance هم تا وقتی امضا/منبعش را verify نکرده‌ای اعتماد قطعی نمی‌سازد.

Manually added version and commit labels are useful, but can be wrong or fabricated. An SBOM lists software components in an artifact; provenance describes how it was built and from which inputs. They help audits, but an SBOM is not a vulnerability scan and provenance is not trustworthy until its source or signature is verified.

در Buildx می‌توان برای buildای که مستقیم به registry می‌رود SBOM و provenance درخواست کرد. این بخش extension است؛ نسخهٔ Docker/Buildx و نوع image store مهم‌اند. در پیکربندی پیش‌فرض Engine ممکن است attestations در local image store باقی نمانند؛ پیش از تکیه‌کردن، خروجی registry و دستور inspect/verify همان نسخه را امتحان کن.

Buildx can request SBOM and provenance for an image pushed directly to a registry. This is an extension; Docker/Buildx version and image-store configuration matter. With the default Engine image store, attestations may not persist in the local store; test registry output and the version-specific inspection/verification path before relying on them.

bash · optional supply-chain metadata with Buildx
docker buildx build \
  --tag ghcr.io/OWNER/hello-api:1.4.2 \
  --sbom --provenance --push .

خطای `unknown flag` یا نبود attestation یعنی اول نسخهٔ Buildx، builder و مقصد را بررسی کن؛ آن را با اضافه‌کردن flagهای تصادفی حل نکن. اگر registry/policy این metadata را لازم نمی‌داند، فصل پایه همچنان کامل است: commit، version، digest و retention ثبت شده‌اند.

An `unknown flag` or missing attestation means first inspect Buildx version, builder, and destination; do not guess flags. If the registry or policy does not require this metadata, the core chapter is still complete with commit, version, digest, and retention recorded.

SBOM می‌گوید چه componentهایی شناخته شده‌اند، نه اینکه هیچ آسیب‌پذیری وجود ندارد. provenance می‌گوید build چگونه ادعا می‌شود انجام شده؛ verifier باید منبع attestation را هم ارزیابی کند.An SBOM says which components were identified, not that no vulnerabilities exist. Provenance describes how the build claims to have happened; a verifier must also evaluate the attestation’s source.

آزمایش: نسخهٔ یک را نگه دار و بعد دقیقاً همان را پس بگیرLab: retain version one, then retrieve that exact build

Dockerfile نمونه را بساز و build `1.4.2` را اجرا کن. پیش از هر تغییر، خروجی `docker image inspect` را برای image ID، tag و label ثبت کن؛ این دفتر کوچک بعداً کمک می‌کند بفهمیم archive از کدام build آمده.

Create the sample Dockerfile and build `1.4.2`. Before changing anything, record the image ID, tag, and labels from `docker image inspect`; this small record will later identify which build the archive came from.

حالا archive بساز و hash بگیر. PowerShell: `Get-FileHash .\hello-api-1.4.2.tar -Algorithm SHA256`. Bash/WSL: `sha256sum hello-api-1.4.2.tar`. مقدار کامل را کنار commit و زمان build ذخیره کن؛ این فقط archive فعلی را شناسایی می‌کند.

Now save an archive and calculate its hash. PowerShell: `Get-FileHash .\hello-api-1.4.2.tar -Algorithm SHA256`. Bash/WSL: `sha256sum hello-api-1.4.2.tar`. Record the full value with commit and build time; it identifies only this archive.

bash · archive, record, and restore the local build
docker image save -o hello-api-1.4.2.tar hello-api:1.4.2
sha256sum hello-api-1.4.2.tar
docker image rm hello-api:1.4.2
docker image load -i hello-api-1.4.2.tar
docker run --rm hello-api:1.4.2

پس از load باید نام image در خروجی بیاید؛ پس از run، متن `release.txt` را ببین. برای اینکه ثابت کنی archive واقعاً لازم بوده، در محیط تمرینی tag محلی را پاک کن و دوباره hash archive را مقایسه کن، سپس load را تکرار کن. این حذف فقط tag محلی آزمایش است؛ archive بیرونی را پاک نکن تا restore تأیید شود.

After load, the image name should appear; after run, inspect the release text. To prove the archive is needed, remove only the local practice tag, compare the archive hash again, then load it once more. This removes only a local lab tag; keep the external archive until restoration is confirmed.

اگر registry خصوصی داری، همین image را به repository خودت push کن، digest واقعی را ثبت کن، سپس pull با همان digest را امتحان کن. در پایان، `docker run` باید همان محتوا را چاپ کند و inspect باید label version و commit مورد انتظار را نشان بدهد. اگر دسترسی registry نداری، archive مسیر کامل و معتبر همین آزمایش است.

If you have a private registry, push this image to your repository, record its real digest, and pull by that digest. Finally, `docker run` should print the same content and inspect should show the expected version and commit labels. Without registry access, the archive is a complete and valid path for this lab.

تمرین‌ها: بعداً بتوانی همان خروجی را پیدا کنیExercises: make the exact output findable later

تمرین‌ها از اسم‌گذاری شروع می‌شوند و به incident می‌رسند. در جواب بگو کدام شاهد داری و کدام هنوز کم است.

The exercises begin with naming and end with an incident. State what evidence you have and what is still missing.

۰ / ۱۸

۱. source یا artifact؟1. Source or artifact?

برای اجرای دوبارهٔ production، چرا Git commit تنها چیزی نیست که می‌خواهی نگه داری؟

Why is a Git commit not the only thing you want to retain to rerun production?

توضیحExplanation

commit ورودی source است؛ artifact خروجی واقعی build است. ابزار، dependency یا زمان می‌تواند build دوباره را تغییر دهد، پس خود artifact و digest/run metadata را هم نگه دار.

A commit identifies source input; the artifact is the actual build output. Tools, dependencies, or time may change a rebuild, so retain the artifact and its digest/run metadata too.

۲. کدام بخش SemVer عوض شود؟2. Which SemVer component changes?

یک API عمومی فیلد اجباری تازه‌ای می‌گیرد که clientهای قدیمی نمی‌فرستند. نسخه را چطور بالا می‌بری؟

A public API gains a required field that old clients do not send. How do you bump the version?

پاسخAnswer

اگر واقعاً سازگاری شکسته، MAJOR بالا می‌رود، مثلاً `1.8.4` به `2.0.0`. اول قرارداد public API و دامنهٔ مصرف‌کننده را بررسی کن؛ عدد نسخه خودکار تشخیص نمی‌دهد.

If compatibility is genuinely broken, increment MAJOR, for example `1.8.4` to `2.0.0`. Verify the public API contract and consumers first; a version number cannot classify the change automatically.

۳. قابلیت سازگار3. A compatible feature

endpoint اختیاری جدید اضافه شده و رفتار قبلی حفظ است. کدام bump محتمل است؟

A new optional endpoint is added and previous behaviour remains. What bump is likely?

دلیلReasoning

MINOR، چون قابلیت تازه با سازگاری عقب‌رو آمده؛ مثلاً `1.8.4` به `1.9.0`. این تصمیم تنها وقتی SemVer است که همان قرارداد واقعاً برقرار باشد.

MINOR, because backward-compatible functionality was added, such as `1.8.4` to `1.9.0`. This is SemVer only if the compatibility contract applies.

۴. رفع باگ سازگار4. A compatible bug fix

باگ رفع شده و API سازگار مانده. کدام بخش بالا می‌رود؟

A bug is fixed without changing API compatibility. Which component increases?

پاسخAnswer

PATCH، مثل `1.8.4` به `1.8.5`. اگر «رفع» رفتار مورد انتظار مصرف‌کننده را شکسته، دوباره طبقه‌بندی کن؛ اسم bug fix خودبه‌خود patch معنی نمی‌دهد.

PATCH, such as `1.8.4` to `1.8.5`. If the “fix” breaks consumer expectations, reclassify it; calling something a bug fix does not automatically make it a patch.

۵. build metadata ترتیب را عوض می‌کند؟5. Does build metadata change precedence?

در SemVer، `1.2.3+build.7` از `1.2.3+build.8` بالاتر است؟

Does `1.2.3+build.8` outrank `1.2.3+build.7` under SemVer?

پاسخAnswer

نه؛ metadata بعد از `+` در تقدم SemVer نادیده گرفته می‌شود. اگر buildها را متمایز می‌کنی، commit/digest یا شناسهٔ دیگر را جدا نگه دار و ترتیب را از metadata استنتاج نکن.

No; metadata after `+` is ignored for SemVer precedence. Distinguish builds with commit/digest or another identifier; do not infer ordering from metadata.

۶. چرا `+` در image tag خطا می‌دهد؟6. Why does `+` fail in an image tag?

رشتهٔ `2.0.0+sha.abc123` SemVer معتبر است ولی registry آن را به عنوان Docker tag رد می‌کند. راه درست چیست؟

`2.0.0+sha.abc123` is valid SemVer, but the registry rejects it as a Docker tag. What should you do?

توضیحExplanation

گرامر Docker tag با SemVer یکی نیست و `+` را نمی‌پذیرد. نسخهٔ کامل را در OCI label/package metadata ثبت کن؛ از tag `2.0.0` و label revision یا digest استفاده کن.

Docker tag grammar differs from SemVer and disallows `+`. Store the full version in an OCI label or package metadata; use a tag such as `2.0.0` and record revision or digest separately.

۷. tag جابه‌جا شد7. A tag moved

دو بار pull از `app:1.2.0` انجام شده و image ID فرق دارد. اولین فرض‌ها؟

Two pulls of `app:1.2.0` return different image IDs. What are your first hypotheses?

پاسخAnswer

tag احتمالاً دوباره به artifact دیگری اشاره می‌کند یا platformها فرق دارند. digest، platform، registry و زمان pull را مقایسه کن؛ tag نسخه لزوماً immutable نیست.

The tag may have been reassigned, or platforms may differ. Compare digest, platform, registry, and pull time; a version tag is not inherently immutable.

۸. commit SHA و digest8. Commit SHA and digest

هر دو ثبت شده‌اند. هرکدام چه چیزی را نام‌گذاری می‌کند؟

Both are recorded. What does each identify?

پاسخAnswer

commit SHA snapshot در مخزن source را معرفی می‌کند؛ digest محتوا/manifest artifact را. commit به‌تنهایی build output را pin نمی‌کند و digest به‌تنهایی source یا builder را نمی‌گوید.

The commit SHA identifies a source repository snapshot; the digest identifies artifact or manifest content. A commit alone does not pin build output, and a digest alone does not identify source or builder.

۹. registry در reference9. The registry in an image reference

در `registry.example/team/api:1.4.2` کدام بخش registry، namespace، repository و tag است؟

Identify registry, namespace, repository, and tag in `registry.example/team/api:1.4.2`.

پاسخAnswer

registry=`registry.example`، namespace=`team`، repository=`api`، tag=`1.4.2`. اگر hostname را حذف کنی Docker معمولاً Docker Hub را پیش‌فرض می‌گیرد؛ مقصد را برای image خصوصی صریح کن.

Registry is `registry.example`, namespace `team`, repository `api`, and tag `1.4.2`. Without a hostname Docker defaults to Docker Hub; specify the destination for private images.

۱۰. local image ID را digest registry جا نزن10. Do not mistake a local image ID for a registry digest

`docker image inspect` برای image محلی `RepoDigests: []` نشان می‌دهد. آیا build شکست خورده؟

`docker image inspect` shows `RepoDigests: []` for a local image. Did the build fail?

توضیحExplanation

نه لزوماً؛ image محلی می‌تواند ID و tag داشته باشد ولی هنوز registry digest نداشته باشد. بعد از push یا pull inspect کن؛ digest registry را با `.Id` محلی یکی فرض نکن.

Not necessarily. A local image can have an ID and tag without a registry digest. Inspect after push or pull; do not equate registry digest with the local `.Id`.

۱۱. نسخهٔ `latest` برای rollback11. Using `latest` for rollback

release دو هفته پیش فقط با `latest` deploy شد. حالا rollback لازم است. چه مدرکی کم است؟

A release two weeks ago was deployed only as `latest`. Now you need rollback. What evidence is missing?

پاسخAnswer

reference دقیق image از release زمان‌دار، ترجیحاً digest، و artifact نگهداری‌شده کم است. registry history یا deployment record را جست‌وجو کن؛ اسم `latest` گذشته را بازسازی نمی‌کند.

The exact release-time image reference—preferably a digest—and retained artifact are missing. Search registry history or deployment records; the name `latest` cannot reconstruct the past.

۱۲. checksum archive چیست؟12. What does an archive checksum identify?

SHA256 فایل `image.tar` با SHA256 manifest registry برابر نیست. آیا تناقض است؟

The SHA256 of `image.tar` differs from the registry manifest digest. Is that a contradiction?

توضیحExplanation

نه؛ hash روی دو شیء متفاوت حساب شده: archive محلی و manifest registry. هر hash همان بایت‌هایی را شناسایی می‌کند که به آن داده شده؛ نوع شیء را در metadata بنویس.

No. They hash different objects: a local archive and a registry manifest. Each hash identifies the bytes it was calculated over; record the object type in metadata.

۱۳. artifact پاک شده13. The artifact was deleted

release note و digest مانده، اما registry manifest پاک شده. آیا digest برای deploy کافی است؟

The release note and digest remain, but the registry manifest was deleted. Is the digest enough to deploy?

پاسخAnswer

نه؛ digest نامی دقیق است، نه خودِ محتوا. باید registry یا archive پشتیبان artifact را هنوز داشته باشد. retention و حذف را طوری بساز که نسخهٔ فعال و rollback لازم پاک نشوند.

No; a digest identifies content but is not the content. The registry or a retained archive must still hold the artifact. Configure retention so active and rollback-needed versions are not deleted.

۱۴. کدام image را production گرفت؟14. Which image did production receive?

deployment record فقط commit `a1b2c3d` دارد. برای اثبات artifact کدام اطلاعات را می‌خواهی؟

The deployment record only has commit `a1b2c3d`. What else do you need to identify the artifact?

پاسخAnswer

registry/repository، version tag، digest، platform و شناسهٔ build/run. commit source است؛ بدون digest یا release record مشخص نیست build دقیقاً چه محتوایی داشته.

Registry/repository, version tag, digest, platform, and build/run ID. The commit is source; without a digest or release record, the exact build content is unknown.

۱۵. SBOM سبز یعنی امن؟15. Does a valid SBOM mean safe?

SBOM تولید شده و parser آن را قبول کرده. چه چیزی هنوز ثابت نشده؟

An SBOM was generated and parsed successfully. What remains unproven?

توضیحExplanation

فهرست معتبر وجود دارد؛ نبود vulnerability، درستی همهٔ componentها یا قابل‌اعتماد بودن builder ثابت نشده. SBOM را با scanner/policy مناسب و provenance قابل‌تأیید ترکیب کن.

A parseable inventory exists; absence of vulnerabilities, component correctness, and builder trust remain unproven. Combine it with suitable scanning/policy and verifiable provenance.

۱۶. provenance مبهم16. Unclear provenance

attestation می‌گوید builder مخزن دیگری بوده که تیم نمی‌شناسد. قدم بعدی چیست؟

An attestation names a builder repository the team does not recognise. What next?

پاسخAnswer

deploy را متوقف کن تا signer/builder و policy اعتماد را verify کنی. وجود provenance فقط metadata است؛ تا منبع معتبر و artifact target یکی نشده، آن را proof تلقی نکن.

Pause deployment and verify the signer/builder against the trust policy. Provenance is metadata; do not treat it as proof until its source and target artifact are validated.

۱۷. چند نسخه نگه داریم؟17. How many versions should we retain?

هزینهٔ storage بالا رفته. چه دو نیازی را پیش از پاک‌سازی متوازن می‌کنی؟

Storage costs are rising. Which two needs do you balance before cleanup?

پاسخAnswer

هزینه/سیاست نگهداری را با زمان rollback، نسخه‌های واقعاً در حال اجرا، و الزام audit/support مقایسه کن. بی‌هدف همه‌چیز را نگه‌داشتن و پاک‌کردن بی‌تمایز هر دو خطر دارند؛ owner و restore path لازم است.

Balance storage cost and retention policy against rollback windows, deployed versions, and audit/support needs. Keeping everything forever and deleting indiscriminately are both risky; define ownership and retrieval paths.

۱۸. incident: tag و digest ناسازگار18. Incident: tag and digest disagree

runbook می‌گوید `app:2.3.0`، اما digest deployment با digestی که release record ثبت کرده فرق دارد. deploy ادامه پیدا کند؟

The runbook says `app:2.3.0`, but the deployed digest differs from the release record. Should deployment continue?

تصمیم و دلیلDecision and reasoning

نه؛ tag می‌تواند جابه‌جا شده یا record اشتباه باشد. pull را متوقف کن، registry و platform را بررسی کن، image فعلی را با digest دقیق retrieve کن و run ID/commit را دوباره بسنج. بعد از تطبیق digest و verify همان artifact، promotion را از سر بگیر؛ اسم version تنها مدرک کافی نیست.

No; the tag may have moved or the record may be wrong. Stop the pull, inspect registry and platform, retrieve the exact digest, and recheck run ID/commit. Resume only after the digest matches and that artifact is verified; a version name alone is not enough.

اگر فقط یک دقیقه وقت داریIf you have only one minute

source commit با artifact فرق دارد. SemVer تغییر سازگاری API را نام‌گذاری می‌کند، اگر قراردادش را تعریف کرده باشی. tag خواناست اما شاید جابه‌جا شود؛ digest محتوای دقیق را pin می‌کند ولی خودش artifact یا منشأ را نگه نمی‌دارد. registry و retention لازم‌اند. commit، version، digest، platform و build/run ID را کنار هم ثبت کن؛ SBOM و provenance لایه‌های شواهدند، نه گواه بی‌خطری.

A source commit is not an artifact. SemVer names API-compatibility changes only when that contract exists. A tag is readable but may move; a digest pins exact content but stores neither the artifact nor its provenance. A registry and retention policy are required. Record commit, version, digest, platform, and build/run ID together; SBOM and provenance add evidence, not a safety guarantee.

برای rollback باید هم شناسهٔ دقیق را بدانی و هم artifact هنوز قابل‌دریافت باشد. digest بدون بایت‌های ذخیره‌شده، راه برگشت نیست.Rollback requires both an exact identifier and an artifact that is still retrievable. A digest without retained bytes is not a way back.
