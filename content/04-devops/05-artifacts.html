ساخت artifact و نسخه‌گذاریArtifacts and versioning

فرض کن نصف شب یه اختلال داریم و می‌خوایم دقیقاً همون نسخه‌ای رو که الان روی production هست دوباره بالا بیاریم. کد منبع رو داریم، tag هم `v1.4.0` رو نشون می‌ده، ولی registry عوض شده و هیچ‌کس مطمئن نیست build امروزی با build روز انتشار یکی باشه. پس دنبال کدیم یا دنبال چیزی که واقعاً اجرا شده؟

An incident has been reported and we need to rerun the production version. We have the source repository and a `v1.4.0` tag, but the registry image has changed. Nobody knows whether it is the build from release day. Which identifier should we have recorded?

کد منبع رو داریم؛ اما چیزی که اجرا شد کجاست؟We have the source—but where is what actually ran?

Git می‌گه کد از کدام commit آمده. ولی artifact خروجی‌ای هست که واقعاً اجرا یا نصب می‌شه: image، فایل package، binary یا bundle. اگه دوباره کد منبع رو build کنیم، ممکن هست نسخهٔ وابستگی، ابزار build یا زمان تولید فرق کنه. commit شناسهٔ ورودی هست؛ digest شناسهٔ محتوای artifact.

Git tells us which commit the code came from. An artifact is the output that is actually run or installed: an image, package, binary, or bundle. Rebuilding from source may use different dependencies, build tools, or timestamps. A commit identifies input; a digest identifies artifact content.

فصل قبل گفتیم یک artifact رو از staging به production ارتقای نسخه بدهیم. این فصل می‌سازه و نگهداری همون artifact رو کامل می‌کنه: چه نامی برای آدم‌ها خواناست، چه شناسه‌ای محتوا رو دقیق مشخص می‌کنه، و چطور چند ماه بعد همون خروجی رو retrieve کنیم.

Last chapter promoted one artifact from staging to production. This chapter completes its creation and retention: which name is readable to people, which identifier pins the exact content, and how to retrieve that output months later.

commit منبع رو نشون می‌ده؛ tag نام نسخه هست؛ digest به محتوای مشخص artifact اشاره می‌کنه. artifact در registry یا store می‌مونه تا محیط‌ها همون رو بگیرن و rollback ممکن باشه.

The commit identifies source; a tag names a version; a digest identifies artifact content. A registry or store retains the artifact for deployments and rollback.

هیچ‌کدام این شناسه‌ها به‌تنهایی «build امن» رو ثابت نمی‌کنن. برای زنجیرهٔ قابل‌اعتمادتر، commit، تنظیمات build، dependencyها و خروجی رو به هم وصل می‌کنیم و اگه نیاز SBOM یا provenance اضافه می‌کنیم.

None of these identifiers alone proves a build is safe. For stronger traceability, connect commit, build configuration, dependencies, and output—and add an SBOM or provenance when needed.

SemVer فقط وقتی معنا داره که قرارداد نسخه داشته باشیSemVer matters only when a version has a contract

فرض کن package تو یک public API داره که مصرف‌کننده‌ها به اون تکیه می‌کنن. SemVer به تغییر نسخه معنا می‌ده: `MAJOR.MINOR.PATCH`. `1.4.2` یعنی major یک، minor چهار، patch دو؛ اما فقط اگه تیم واقعاً قرارداد سازگاری رو رعایت کنه.

Suppose your package exposes a public API that consumers depend on. SemVer gives version changes meaning: `MAJOR.MINOR.PATCH`. `1.4.2` has major 1, minor 4, and patch 2—but only if the team actually follows the compatibility contract.

بخش نسخهVersion partتغییر نمونهExample changeنسخهٔ پیشنهادیSuggested bump
MAJORتغییر ناسازگار در public API
A breaking change to the public API		1.4.2 → 2.0.0
MINORقابلیت تازه با سازگاری عقب‌رو
Backward-compatible new functionality		1.4.2 → 1.5.0
PATCHرفع باگ سازگار
A backward-compatible bug fix		1.4.2 → 1.4.3

این قانون برای هر فایل و هر container به‌طور خودکار برقرار نیست. اگه سرویسی API عمومی تعریف‌شده نداره، ممکن هست تیم از تقویم انتشار، SHA یا شمارهٔ build استفاده کنه. SemVer هم تضمین نمی‌کنه نویسنده درست تشخیص داده تغییر ناسازگار بوده یا نه؛ این قرارداد و آزمون سازگاری لازم داره.

This rule does not automatically apply to every file or container. A service without a defined public API may use calendar releases, a SHA, or build numbers instead. SemVer cannot guarantee that a maintainer correctly identified a breaking change; that takes an explicit contract and compatibility checks.

پیش‌انتشارهایی مثل `2.0.0-rc.1` از نسخهٔ پایدار همون شماره پایین‌ترند. build metadata مثل `1.4.2+sha.a1b2c3d` اطلاعات build می‌ده اما در تقدم SemVer دخالت نداره. این رشتهٔ کامل رو می‌توان در package metadata یا label ثبت کرد؛ هر مقصدی مجاز نیست اون رو عیناً به‌عنوان tag قبول کنه.

Prereleases such as `2.0.0-rc.1` have lower precedence than the corresponding stable version. Build metadata such as `1.4.2+sha.a1b2c3d` records build information but does not affect SemVer precedence. Store the full string in package metadata or a label; not every destination accepts it unchanged as a tag.

پرسش قبل از bump: آیا مصرف‌کننده‌ای به این API یا رفتار وابسته هست؟ اگه بله، نوع تغییر رو نسبت به قرارداد بسنج. اگه نه، اسم نسخهٔ «معنایی» لزوماً اطلاعات معنایی نمی‌ده.Before a version bump, ask whether a consumer relies on this API or behaviour. If so, classify the change against that contract. If not, a “semantic” version label does not automatically carry semantic information.

tag خواناست؛ digest دقیق هستA tag is readable; a digest is exact

در Docker image reference، registry می‌گه کجا، repository می‌گه کدام image، tag نامی خوانا برای انسان هست و digest محتوای مشخص رو می‌شناسه. اگه tag رو دوباره به image دیگری بچسبانند، `سرویس:1.4.0` ممکن هست فردا بایت‌های دیگری بده. tag ذاتاً immutable نیست؛ registry سیاست می‌تونه نوشتن مجدد tag رو ببندد، اما باید اون سیاست رو بررسی کرد.

In a Docker image reference, the registry says where, the repository identifies the image, a tag is a human-readable name, and a digest identifies specific content. If someone moves the tag, `service:1.4.0` may return different bytes tomorrow. A tag is not inherently immutable; a registry policy may prevent retagging, but verify that policy.

May be moved in the registry.

یک ظرافت در Docker: tag grammar حروف، عدد، underscore، نقطه و خط تیره رو می‌پذیره، نه `+`. پس `1.4.2+sha.a1b2c3d` نسخهٔ معتبر SemVer هست، اما همون رشته tag معتبر Docker نیست. اون رو در label نگه دار و برای tag مثلاً `1.4.2` بگذار؛ commit و digest هم جدا ثبت بشن.

One Docker detail: its tag grammar allows letters, digits, underscore, dot, and hyphen—not `+`. Thus `1.4.2+sha.a1b2c3d` is valid SemVer but not a valid Docker tag. Keep it in a label, use a tag such as `1.4.2`, and record commit and digest separately.

digest هم همیشه فقط یک معماری CPU رو نشان نمی‌ده: image چندسکویی می‌تونه یک manifest index داشته باشه که برای هر platform به manifest دیگری می‌رسه. در سطح این فصل digest رو به‌عنوان شناسهٔ registry image بخوان؛ وقتی platform مهمه، پلتفرم و digest مربوط رو هم ثبت کن.

A digest does not always represent only one CPU architecture: a multi-platform image can have an index manifest pointing to platform-specific manifests. At this level, treat the digest as the registry image identifier; when platform matters, record the platform and relevant digest too.

نسخه، commit و metadata رو روی image ثبت کنیمRecord version, commit, and metadata on the image

برای آزمایش یک image کوچک می‌سازیم که فقط فایل نسخه رو چاپ می‌کنه. دو label می‌گذاریم: نسخهٔ SemVer و Git revision. `ARG` فقط هنگام build وارد می‌شه؛ label metadata رو روی image ثبت می‌کنه، نه secret رو. در پروژهٔ واقعی build باید از commit تمیز و lockfile/ dependencyهای ثبت‌شده بیاد.

We will build a tiny image that prints a version file. Two labels record the SemVer version and Git revision. `ARG` is supplied at build time; a label records metadata on the image, not a secret. In a real project, build from a clean commit and locked dependencies.

Dockerfile · tiny release specimen
FROM alpine:3.22
ARG APP_VERSION
ARG VCS_REF
ARG RELEASE_MARKER
LABEL org.opencontainers.image.version=$APP_VERSION \
      org.opencontainers.image.revision=$VCS_REF
RUN printf '%s\n' "${RELEASE_MARKER:-$APP_VERSION}" > /release.txt
CMD ["cat", "/release.txt"]

برای build، tag خوانا رو بده و revision رو از Git بگیر؛ برنامهٔ نمونه این دو رو در label ثبت می‌کنه و نسخه رو چاپ می‌کنه. این نمونه از `alpine:3.22` با tag استفاده می‌کنه تا دستور کوتاه بمونه؛ برای build بازتولیدپذیرتر، base image رو هم با digest pin کن و اون رو آگاهانه به‌روزرسانی کن.

Build with a readable tag and obtain the revision from Git; the sample records both as labels and prints its version. This short example uses `alpine:3.22` by tag; for more reproducible builds, pin the base image by digest and update it deliberately.

bash · build and inspect local metadata
REV=$(git rev-parse HEAD)
docker build \
  --build-arg APP_VERSION=1.4.2 \
  --build-arg VCS_REF="$REV" \
  -t hello-api:1.4.2 .
docker image inspect hello-api:1.4.2 \
  --format '{{json .Config.Labels}}'
docker run --rm hello-api:1.4.2

در labelها `نسخه` و revision موردانتظار رو ببین؛ اجرای container باید `1.4.2` چاپ کنه. `.Id` محلی image و label commit دربارهٔ metadata می‌گن، نه registry digest. چون هنوز push نکرده‌ایم، `RepoDigests` ممکن هست خالی باشه؛ digest registry رو بعد از push/pull می‌گیریم.

Check that the labels contain the expected version and revision; running the container should print `1.4.2`. The local image ID and commit label are not the registry digest. Before pushing, `RepoDigests` may be empty; we will obtain the registry digest after push or pull.

اگه Git repository نداری یا commit ثبت نشده، `git rev-parse HEAD` کار نمی‌کنه. برای آزمایش می‌توان revision رو رشتهٔ نمونه بگذاری، اما در artifact واقعی مقدار جعلی رو به‌جای commit نگذار؛ این کار زنجیرهٔ ردیابی رو خراب می‌کنه.Without a Git repository or commit, `git rev-parse HEAD` cannot work. You may use a clearly labelled sample string for the lab, but never replace the real source revision with a fake value in a release artifact; that breaks traceability.

خرابی عمدی: `latest` به کدام build اشاره می‌کنه؟Deliberate failure: which build does `latest` mean?

دو build متفاوت رو با یک نام tag می‌سازیم. فقط روی image تمرینی این کار رو انجام بده. اول شناسهٔ build اول رو ثبت کن؛ بعد build دوم رو دوباره با همون `demo:latest` نام‌گذاری کن. قبل از دیدن خروجی حدس بزن tag قبلی چه می‌شه.

We will build two different images under the same tag. Do this only with the practice image. Record the first build’s ID, then build a second one as `demo:latest` again. Predict what happens to the earlier tag before checking.

bash · move a disposable tag on purpose
docker build --build-arg APP_VERSION=1.4.2 --build-arg RELEASE_MARKER=build-A -t demo:latest .
docker image inspect demo:latest --format '{{.Id}}'
docker build --build-arg APP_VERSION=1.4.2 --build-arg RELEASE_MARKER=build-B -t demo:latest .
docker image inspect demo:latest --format '{{.Id}}'
docker run --rm demo:latest
docker image ls demo

دو image ID باید متفاوت باشن؛ اجرای `demo:latest` باید `build-B` چاپ کنه. این مدرک نشون می‌ده نام tag به محتوای تازه اشاره می‌کنه و build قبلی رو پیدا نمی‌کنه. image قبلی رو با نسخهٔ ثابت یا digest جست‌وجو کن؛ سیاست یک registry ممکن هست push مجدد همین tag رو محدود کنه، اما tag به‌خودی‌خود immutable نیست.

The two image IDs should differ, and running `demo:latest` should print `build-B`. This proves the tag now points to new content and no longer locates the earlier build. Use a fixed version or digest to find the earlier image; a registry policy may block re-pushing the tag, but the tag itself is not immutable.

از این آزمایش نتیجه نگیر که باید از `latest` برای استقرار استفاده کنی. نامش به‌تنهایی نه «جدیدترین» رو تعریف می‌کنه و نه rollback می‌سازه. tag نسخه‌دار برای آدم، digest برای انتخاب دقیق؛ هر دو رو همراه commit ثبت کن.

Do not conclude that `latest` is suitable for deployment. The name alone defines neither “latest” nor a rollback. Use a version tag for people and a digest for exact selection; record both with the source commit.

artifact رو نگه دار؛ نه فقط اسمش روRetain the artifact, not just its name

registry مثل انبار imageهاست: hostname/namespace/repository مسیر رو مشخص می‌کنن و tag یا digest مورد رو انتخاب می‌کنه. login و push فقط وقتی لازمه که registry در scope آزمایش باشه؛ image خصوصی رو عمومی push نکن. فرمان زیر شکل reference رو نشون می‌ده؛ `OWNER` رو با namespace واقعی خودت عوض کن.

A registry stores images: hostname, namespace, and repository locate them, while a tag or digest selects one. Login and push are needed only if a registry is in scope; never push a private image publicly. The command below illustrates the reference—replace `OWNER` with your actual namespace.

bash · optional push to a registry you control
docker tag hello-api:1.4.2 ghcr.io/OWNER/hello-api:1.4.2
docker push ghcr.io/OWNER/hello-api:1.4.2
# The registry reports a digest; copy the real value from your output
docker pull ghcr.io/OWNER/hello-api:1.4.2
docker image inspect ghcr.io/OWNER/hello-api:1.4.2 \
  --format '{{json .RepoDigests}}'

در push/pull به خط `Digest: sha256:…` یا `RepoDigests` نگاه کن و مقدار واقعی رو در سابقهٔ انتشار ذخیره کن؛ این مقدار برای هر محتوا فرق می‌کنه و نباید از نمونهٔ مستندات کپی بشه. حالا می‌توان image رو با `ghcr.io/OWNER/hello-api@sha256:REAL_DIGEST` pull کرد. digest محتوای انتخاب‌شده رو pin می‌کنه، نه اینکه image بی‌باگ یا خوش‌منشأ هست.

In push/pull output, find `Digest: sha256:…` or `RepoDigests` and save the real value in the release record; it varies by content and must not be copied from documentation examples. The image can then be pulled as `ghcr.io/OWNER/hello-api@sha256:REAL_DIGEST`. A digest pins selected content; it does not prove the image is bug-free or trustworthy.

برای آزمایش بدون registry می‌توان image رو archive کرد: `docker image save -o hello-api-1.4.2.tar hello-api:1.4.2` و checksum فایل رو با `sha256sum` یا در PowerShell با `Get-FileHash -Algorithm SHA256` ثبت کرد. checksum archive، digest manifest registry نیست؛ هرکدام همون شیئی رو شناسایی می‌کنن که hash شده هست.

Without a registry, save the image as an archive with `docker image save -o hello-api-1.4.2.tar hello-api:1.4.2`, then record its checksum with `sha256sum` or PowerShell’s `Get-FileHash -Algorithm SHA256`. An archive checksum is not the registry manifest digest; each hash identifies the object it was calculated from.

مدت نگه‌داری رو بر اساس زمان پشتیبانی و rollback تعیین کن: مثلاً چند نسخهٔ آخر و همهٔ نسخه‌هایی که هنوز در production هستن رو نگه دار. اگه فقط tag رو نگه داری ولی registry image رو پاک کنه، نام قابل‌خواندن مانده اما چیزی برای استقرار نداری. قواعد cleanup رو با owner و نیاز قانونی/عملیاتی هماهنگ کن.

Set retention according to support and rollback windows: keep, for example, recent versions and every version still running in production. If the registry image is deleted, a readable tag remains only as a name—you have nothing to deploy. Align cleanup with ownership and operational or legal requirements.

چه کسی ساختش و داخلش چیست؟Who built it, and what is inside?

label نسخه و commit دستی هست و مفید؛ اما ممکن هست اشتباه یا جعلی باشه. SBOM فهرست اجزای نرم‌افزاری artifact هست؛ provenance اطلاعاتی دربارهٔ نحوه و ورودی‌های build می‌ده. این‌ها به audit کمک می‌کنن، ولی SBOM به‌تنهایی vulnerability scan نیست و provenance هم تا وقتی امضا/منبعش رو verify نکرده‌ای اعتماد قطعی نمی‌سازه.

Manually added version and commit labels are useful, but can be wrong or fabricated. An SBOM lists software components in an artifact; provenance describes how it was built and from which inputs. They help audits, but an SBOM is not a vulnerability scan and provenance is not trustworthy until its source or signature is verified.

در Buildx می‌توان برای buildای که مستقیم به registry می‌ره SBOM و provenance درخواست کرد. این بخش extension هست؛ نسخهٔ Docker/Buildx و نوع image store مهم‌اند. در پیکربندی پیش‌فرض Engine ممکن هست attestations در local image store باقی نمانند؛ قبل از تکیه‌کردن، خروجی registry و دستور inspect/verify همون نسخه رو امتحان کن.

Buildx can request SBOM and provenance for an image pushed directly to a registry. This is an extension; Docker/Buildx version and image-store configuration matter. With the default Engine image store, attestations may not persist in the local store; test registry output and the version-specific inspection/verification path before relying on them.

bash · optional supply-chain metadata with Buildx
docker buildx build \
  --tag ghcr.io/OWNER/hello-api:1.4.2 \
  --sbom --provenance --push .

خطای `unknown flag` یا نبود attestation یعنی اول نسخهٔ Buildx، builder و مقصد رو بررسی کن؛ اون رو با اضافه‌کردن flagهای تصادفی حل نکن. اگه registry/سیاست این metadata رو لازم نمی‌دونه، فصل پایه همچنان کامل هست: commit، نسخه، digest و مدت نگه‌داری ثبت شدن.

An `unknown flag` or missing attestation means first inspect Buildx version, builder, and destination; do not guess flags. If the registry or policy does not require this metadata, the core chapter is still complete with commit, version, digest, and retention recorded.

SBOM می‌گه چه componentهایی شناخته شدن، نه اینکه هیچ آسیب‌پذیری نیست. provenance می‌گه build چطور ادعا می‌شه انجام شده؛ verifier باید منبع attestation رو هم ارزیابی کنه.An SBOM says which components were identified, not that no vulnerabilities exist. Provenance describes how the build claims to have happened; a verifier must also evaluate the attestation’s source.

آزمایش: نسخهٔ یک رو نگه دار و بعد دقیقاً همون رو پس بگیرLab: retain version one, then retrieve that exact build

Dockerfile نمونه رو بساز و build `1.4.2` رو اجرا کن. قبل از هر تغییر، خروجی `docker image inspect` رو برای image ID، tag و label ثبت کن؛ این دفتر کوچک بعداً کمک می‌کنه بفهمیم archive از کدام build آمده.

Create the sample Dockerfile and build `1.4.2`. Before changing anything, record the image ID, tag, and labels from `docker image inspect`; this small record will later identify which build the archive came from.

حالا archive بساز و hash بگیر. PowerShell: `Get-FileHash .\hello-api-1.4.2.tar -Algorithm SHA256`. Bash/WSL: `sha256sum hello-api-1.4.2.tar`. مقدار کامل رو کنار commit و زمان build ذخیره کن؛ این فقط archive فعلی رو شناسایی می‌کنه.

Now save an archive and calculate its hash. PowerShell: `Get-FileHash .\hello-api-1.4.2.tar -Algorithm SHA256`. Bash/WSL: `sha256sum hello-api-1.4.2.tar`. Record the full value with commit and build time; it identifies only this archive.

bash · archive, record, and restore the local build
docker image save -o hello-api-1.4.2.tar hello-api:1.4.2
sha256sum hello-api-1.4.2.tar
docker image rm hello-api:1.4.2
docker image load -i hello-api-1.4.2.tar
docker run --rm hello-api:1.4.2

بعد از load باید نام image در خروجی بیاد؛ بعد از run، متن `انتشار.txt` رو ببین. برای اینکه ثابت کنی archive واقعاً لازم بوده، در محیط تمرینی tag محلی رو پاک کن و دوباره hash archive رو مقایسه کن، بعد load رو تکرار کن. این حذف فقط tag محلی آزمایش هست؛ archive بیرونی رو پاک نکن تا restore تأیید بشه.

After load, the image name should appear; after run, inspect the release text. To prove the archive is needed, remove only the local practice tag, compare the archive hash again, then load it once more. This removes only a local lab tag; keep the external archive until restoration is confirmed.

اگه registry خصوصی داری، همین image رو به repository خودت push کن، digest واقعی رو ثبت کن، بعد pull با همون digest رو امتحان کن. در پایان، `docker run` باید همون محتوا رو چاپ کنه و inspect باید label نسخه و commit مورد انتظار رو نشان بده. اگه دسترسی registry نداری، archive مسیر کامل و معتبر همین آزمایش هست.

If you have a private registry, push this image to your repository, record its real digest, and pull by that digest. Finally, `docker run` should print the same content and inspect should show the expected version and commit labels. Without registry access, the archive is a complete and valid path for this lab.

تمرین‌ها: بعداً بتوانی همون خروجی رو پیدا کنیExercises: make the exact output findable later

تمرین‌ها از اسم‌گذاری شروع می‌شن و به رخداد می‌رسن. در جواب بگو کدام شاهد داری و کدام هنوز کم هست.

The exercises begin with naming and end with an incident. State what evidence you have and what is still missing.

۰ / ۱۸

۱. کد منبع یا artifact؟1. Source or artifact?

برای اجرای دوبارهٔ production، چرا Git commit تنها چیزی نیست که می‌خوای نگه داری؟

Why is a Git commit not the only thing you want to retain to rerun production?

توضیحExplanation

commit ورودی کد منبع هست؛ artifact خروجی واقعی build هست. ابزار build، نسخهٔ وابستگی‌ها یا حتی شرایط زمان ساخت می‌تونه خروجی build بعدی رو عوض کنه. برای همین فقط commit کافی نیست؛ خود artifact و digest و اطلاعات run رو هم نگه دار.

A commit identifies source input; the artifact is the actual build output. Tools, dependencies, or time may change a rebuild, so retain the artifact and its digest/run metadata too.

۲. کدام بخش SemVer عوض بشه؟2. Which SemVer component changes?

یک API عمومی فیلد اجباری تازه‌ای می‌گیره که clientهای قدیمی نمی‌فرستن. نسخه رو چطور بالا می‌بری؟

A public API gains a required field that old clients do not send. How do you bump the version?

پاسخAnswer

اگه واقعاً سازگاری شکسته، MAJOR بالا می‌ره، مثلاً `1.8.4` به `2.0.0`. اول قرارداد public API و دامنهٔ مصرف‌کننده رو بررسی کن؛ عدد نسخه خودکار تشخیص نمی‌ده.

If compatibility is genuinely broken, increment MAJOR, for example `1.8.4` to `2.0.0`. Verify the public API contract and consumers first; a version number cannot classify the change automatically.

۳. قابلیت سازگار3. A compatible feature

endpoint اختیاری جدید اضافه شده و رفتار قبلی حفظ هست. کدام bump محتمل هست؟

A new optional endpoint is added and previous behaviour remains. What bump is likely?

دلیلReasoning

MINOR، چون قابلیت تازه با سازگاری عقب‌رو آمده؛ مثلاً `1.8.4` به `1.9.0`. این تصمیم تنها وقتی SemVer هست که همون قرارداد واقعاً برقرار باشه.

MINOR, because backward-compatible functionality was added, such as `1.8.4` to `1.9.0`. This is SemVer only if the compatibility contract applies.

۴. رفع باگ سازگار4. A compatible bug fix

باگ رفع شده و API سازگار مانده. کدام بخش بالا می‌ره؟

A bug is fixed without changing API compatibility. Which component increases?

پاسخAnswer

PATCH، مثل `1.8.4` به `1.8.5`. اگه «رفع» رفتار مورد انتظار مصرف‌کننده رو شکسته، دوباره طبقه‌بندی کن؛ اسم bug fix خودبه‌خود patch معنی نمی‌ده.

PATCH, such as `1.8.4` to `1.8.5`. If the “fix” breaks consumer expectations, reclassify it; calling something a bug fix does not automatically make it a patch.

۵. build metadata ترتیب رو عوض می‌کنه؟5. Does build metadata change precedence?

در SemVer، `1.2.3+build.7` از `1.2.3+build.8` بالاتر هست؟

Does `1.2.3+build.8` outrank `1.2.3+build.7` under SemVer?

پاسخAnswer

نه؛ metadata بعد از `+` در تقدم SemVer نادیده گرفته می‌شه. اگه buildها رو متمایز می‌کنی، commit/digest یا شناسهٔ دیگر رو جدا نگه دار و ترتیب رو از metadata استنتاج نکن.

No; metadata after `+` is ignored for SemVer precedence. Distinguish builds with commit/digest or another identifier; do not infer ordering from metadata.

۶. چرا `+` در image tag خطا می‌ده؟6. Why does `+` fail in an image tag?

رشتهٔ `2.0.0+sha.abc123` SemVer معتبر هست ولی registry اون رو به‌عنوان Docker tag رد می‌کنه. راه درست چیست؟

`2.0.0+sha.abc123` is valid SemVer, but the registry rejects it as a Docker tag. What should you do?

توضیحExplanation

گرامر Docker tag با SemVer یکی نیست و `+` رو نمی‌پذیره. نسخهٔ کامل رو در OCI label/package metadata ثبت کن؛ از tag `2.0.0` و label revision یا digest استفاده کن.

Docker tag grammar differs from SemVer and disallows `+`. Store the full version in an OCI label or package metadata; use a tag such as `2.0.0` and record revision or digest separately.

۷. tag جابه‌جا شد7. A tag moved

دو بار pull از `app:1.2.0` انجام شده و image ID فرق داره. اولین فرض‌ها؟

Two pulls of `app:1.2.0` return different image IDs. What are your first hypotheses?

پاسخAnswer

tag احتمالاً دوباره به artifact دیگری اشاره می‌کنه یا platformها فرق دارن. digest، platform، registry و زمان pull رو مقایسه کن؛ tag نسخه لزوماً immutable نیست.

The tag may have been reassigned, or platforms may differ. Compare digest, platform, registry, and pull time; a version tag is not inherently immutable.

۸. commit SHA و digest8. Commit SHA and digest

هر دو ثبت شدن. هرکدام چه چیزی رو نام‌گذاری می‌کنه؟

Both are recorded. What does each identify?

پاسخAnswer

commit SHA snapshot در مخزن کد منبع رو معرفی می‌کنه؛ digest محتوا/manifest artifact رو. commit به‌تنهایی build output رو pin نمی‌کنه و digest به‌تنهایی کد منبع یا builder رو نمی‌گه.

The commit SHA identifies a source repository snapshot; the digest identifies artifact or manifest content. A commit alone does not pin build output, and a digest alone does not identify source or builder.

۹. registry در reference9. The registry in an image reference

در `registry.example/team/api:1.4.2` کدام بخش registry، namespace، repository و tag هست؟

Identify registry, namespace, repository, and tag in `registry.example/team/api:1.4.2`.

پاسخAnswer

registry=`registry.example`، namespace=`team`، repository=`api`، tag=`1.4.2`. اگه hostname رو حذف کنی Docker معمولاً Docker Hub رو پیش‌فرض می‌گیره؛ مقصد رو برای image خصوصی صریح کن.

Registry is `registry.example`, namespace `team`, repository `api`, and tag `1.4.2`. Without a hostname Docker defaults to Docker Hub; specify the destination for private images.

۱۰. local image ID رو digest registry جا نزن10. Do not mistake a local image ID for a registry digest

`docker image inspect` برای image محلی `RepoDigests: []` نشون می‌ده. آیا build شکست خورده؟

`docker image inspect` shows `RepoDigests: []` for a local image. Did the build fail?

توضیحExplanation

نه لزوماً؛ image محلی می‌تونه ID و tag داشته باشه ولی هنوز registry digest نداشته باشه. بعد از push یا pull inspect کن؛ digest registry رو با `.Id` محلی یکی فرض نکن.

Not necessarily. A local image can have an ID and tag without a registry digest. Inspect after push or pull; do not equate registry digest with the local `.Id`.

۱۱. نسخهٔ `latest` برای rollback11. Using `latest` for rollback

انتشار دو هفته پیش فقط با `latest` استقرار شد. حالا rollback لازمه. چه مدرکی کم هست؟

A release two weeks ago was deployed only as `latest`. Now you need rollback. What evidence is missing?

پاسخAnswer

reference دقیق image از انتشار زمان‌دار، ترجیحاً digest، و artifact نگهداری‌شده کم هست. registry history یا استقرار record رو جست‌وجو کن؛ اسم `latest` گذشته رو بازسازی نمی‌کنه.

The exact release-time image reference—preferably a digest—and retained artifact are missing. Search registry history or deployment records; the name `latest` cannot reconstruct the past.

۱۲. checksum archive چیست؟12. What does an archive checksum identify?

SHA256 فایل `image.tar` با SHA256 manifest registry برابر نیست. آیا تناقض هست؟

The SHA256 of `image.tar` differs from the registry manifest digest. Is that a contradiction?

توضیحExplanation

نه؛ hash روی دو شیء متفاوت حساب شده: archive محلی و manifest registry. هر hash همون بایت‌هایی رو شناسایی می‌کنه که به اون داده شده؛ نوع شیء رو در metadata بنویس.

No. They hash different objects: a local archive and a registry manifest. Each hash identifies the bytes it was calculated over; record the object type in metadata.

۱۳. artifact پاک شده13. The artifact was deleted

یادداشت انتشار و digest مانده، اما registry manifest پاک شده. آیا digest برای استقرار کافیه؟

The release note and digest remain, but the registry manifest was deleted. Is the digest enough to deploy?

پاسخAnswer

نه؛ digest نامی دقیق هست، نه خودِ محتوا. باید registry یا archive پشتیبان artifact رو هنوز داشته باشه. مدت نگه‌داری و حذف رو طوری بساز که نسخهٔ فعال و rollback لازم پاک نشوند.

No; a digest identifies content but is not the content. The registry or a retained archive must still hold the artifact. Configure retention so active and rollback-needed versions are not deleted.

۱۴. کدام image رو production گرفت؟14. Which image did production receive?

استقرار record فقط commit `a1b2c3d` داره. برای اثبات artifact کدام اطلاعات رو می‌خوای؟

The deployment record only has commit `a1b2c3d`. What else do you need to identify the artifact?

پاسخAnswer

registry/repository، نسخه tag، digest، platform و شناسهٔ build/run. commit کد منبع هست؛ بدون digest یا سابقهٔ انتشار مشخص نیست build دقیقاً چه محتوایی داشته.

Registry/repository, version tag, digest, platform, and build/run ID. The commit is source; without a digest or release record, the exact build content is unknown.

۱۵. SBOM سبز یعنی امن؟15. Does a valid SBOM mean safe?

SBOM تولید شده و parser اون رو قبول کرده. چه چیزی هنوز ثابت نشده؟

An SBOM was generated and parsed successfully. What remains unproven?

توضیحExplanation

فهرست معتبر هست؛ نبود vulnerability، درستی همهٔ componentها یا قابل‌اعتماد بودن builder ثابت نشده. SBOM رو با scanner/سیاست مناسب و provenance قابل‌تأیید ترکیب کن.

A parseable inventory exists; absence of vulnerabilities, component correctness, and builder trust remain unproven. Combine it with suitable scanning/policy and verifiable provenance.

۱۶. provenance مبهم16. Unclear provenance

attestation می‌گه builder مخزن دیگری بوده که تیم نمی‌شناسه. قدم بعدی چیست؟

An attestation names a builder repository the team does not recognise. What next?

پاسخAnswer

استقرار رو متوقف کن تا signer/builder و سیاست اعتماد رو verify کنی. وجود provenance فقط metadata هست؛ تا منبع معتبر و artifact مقصد یکی نشده، اون رو proof تلقی نکن.

Pause deployment and verify the signer/builder against the trust policy. Provenance is metadata; do not treat it as proof until its source and target artifact are validated.

۱۷. چند نسخه نگه داریم؟17. How many versions should we retain?

هزینهٔ storage بالا رفته. چه دو نیازی رو قبل از پاک‌سازی متوازن می‌کنی؟

Storage costs are rising. Which two needs do you balance before cleanup?

پاسخAnswer

هزینه/سیاست نگهداری رو با زمان rollback، نسخه‌های واقعاً در حال اجرا، و الزام audit/support مقایسه کن. بی‌هدف همه‌چیز رو نگه‌داشتن و پاک‌کردن بی‌تمایز هر دو خطر دارن؛ owner و restore path لازمه.

Balance storage cost and retention policy against rollback windows, deployed versions, and audit/support needs. Keeping everything forever and deleting indiscriminately are both risky; define ownership and retrieval paths.

۱۸. رخداد: tag و digest ناسازگار18. Incident: tag and digest disagree

runbook می‌گه `app:2.3.0`، اما digest استقرار با digestی که سابقهٔ انتشار ثبت کرده فرق داره. استقرار ادامه پیدا کنه؟

The runbook says `app:2.3.0`, but the deployed digest differs from the release record. Should deployment continue?

تصمیم و دلیلDecision and reasoning

نه؛ tag می‌تونه جابه‌جا شده یا record اشتباه باشه. pull رو متوقف کن، registry و platform رو بررسی کن، image فعلی رو با digest دقیق retrieve کن و run ID/commit رو دوباره بسنج. بعد از تطبیق digest و verify همون artifact، ارتقای نسخه رو از سر بگیر؛ اسم نسخه تنها مدرک کافی نیست.

No; the tag may have moved or the record may be wrong. Stop the pull, inspect registry and platform, retrieve the exact digest, and recheck run ID/commit. Resume only after the digest matches and that artifact is verified; a version name alone is not enough.

اگه فقط یک دقیقه وقت داریIf you have only one minute

کد منبع commit با artifact فرق داره. SemVer تغییر سازگاری API رو نام‌گذاری می‌کنه، اگه قراردادش رو تعریف کرده باشی. tag خواناست اما شاید جابه‌جا بشه؛ digest محتوای دقیق رو pin می‌کنه ولی خودش artifact یا منشأ رو نگه نمی‌دارد. registry و مدت نگه‌داری لازم‌اند. commit، نسخه، digest، platform و build/run ID رو کنار هم ثبت کن؛ SBOM و provenance لایه‌های شواهدند، نه گواه بی‌خطری.

A source commit is not an artifact. SemVer names API-compatibility changes only when that contract exists. A tag is readable but may move; a digest pins exact content but stores neither the artifact nor its provenance. A registry and retention policy are required. Record commit, version, digest, platform, and build/run ID together; SBOM and provenance add evidence, not a safety guarantee.

برای rollback باید هم شناسهٔ دقیق رو بدانی و هم artifact هنوز قابل‌دریافت باشه. digest بدون بایت‌های ذخیره‌شده، راه برگشت نیست.Rollback requires both an exact identifier and an artifact that is still retrievable. A digest without retained bytes is not a way back.

حالا می‌تونیم بگیم کدام image با کدام کد منبع ساخته شده و چطور دوباره پیدایش کنیم. قدم بعد همین ایده رو از artifact برنامه به زیرساخت می‌بره: اگه محیط staging و production با دست تنظیم شدن، چطور تفاوتشان رو ببینیم و تغییر رو قابل‌بررسی اعمال کنیم؟ فصل Terraform از IaC شروع می‌کنه، نه از حدس‌زدن در پنل سرور.
