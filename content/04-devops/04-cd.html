CD و محیط‌هاCD and environments

CI سبز شده و artifact آماده است. حالا کسی می‌گوید «روی staging خوب بود، پس production را جدا build می‌کنیم». همین‌جا مکث کن: اگر دوباره بسازیم، از کجا می‌دانیم همان چیزی است که آزمودیم؟

CI is green and an artifact is ready. Someone says, “It worked in staging, so we’ll build production separately.” Pause here: if we build again, how do we know it is what we tested?

staging موفق شد؛ production هم همان چیز را می‌گیرد؟Staging passed; will production get the same thing?

تیم یک نسخه از برنامه را در staging آزموده. روز بعد برای production دوباره source را build می‌کنند؛ dependency تازه resolve شده و خروجی با نمونهٔ آزموده یکی نیست. بعد خطا می‌آید، ولی کسی نمی‌داند دقیقاً کدام تفاوت مقصر بوده. محیط دوم را با build دوم حل نمی‌کنیم؛ یک build را بین محیط‌ها جابه‌جا می‌کنیم.

The team tested a build in staging. The next day, they rebuilt the source for production; a dependency resolved differently, so the output no longer matched what they tested. A failure follows, and nobody knows which difference caused it. We do not solve a second environment with a second build; we promote one build through environments.

فصل قبل CI را دیدیم: بررسی روی commit مشخص. CD ادامهٔ همان مسیر است و artifact را به محیط مقصد می‌رساند. «Continuous Delivery» معمولاً تغییر را آمادهٔ انتشار می‌کند ولی ممکن است برای production تأیید انسانی بخواهد؛ «Continuous Deployment» تغییر واجد شرط را بدون gate دستی خودکار به production می‌فرستد. در گفت‌وگوی روزمره CD گاهی هر دو معنا را می‌دهد، پس قرارداد تیم را صریح کن.

Last chapter used CI to check a specific commit. CD continues that path and moves its artifact to a target environment. “Continuous Delivery” generally keeps a change ready to release but may require human production approval; “Continuous Deployment” automatically sends qualifying changes to production without a manual gate. In everyday usage, CD can mean either, so make the team’s contract explicit.

Deployment یعنی artifact را در یک محیط مستقر کنیم؛ release یعنی قابلیت برای کاربر قابل‌استفاده شود. این دو همیشه هم‌زمان نیستند: کدی می‌تواند deploy شود اما پشت feature flag خاموش بماند. این جدایی به ما امکان می‌دهد نصب را بررسی کنیم، بعد جداگانه زمان آشکارشدن قابلیت را انتخاب کنیم.

Deployment places an artifact in an environment; release makes a capability available to users. They need not happen together: code can be deployed while a feature flag keeps it hidden. Separating the two lets us verify installation before choosing when users see the feature.

پیکان افقی حرکت همان artifact را نشان می‌دهد؛ پیکان‌های عمودی config محیط را نشان می‌دهند. artifact را با digest یا شناسهٔ immutable دنبال کن. اگر staging از commit A و production از rebuild commit A استفاده کند، یکی بودن شمارهٔ commit به‌تنهایی یکی بودن بایت‌های artifact را ثابت نمی‌کند.

The horizontal arrows show one artifact moving forward; the vertical arrows show environment-specific configuration. Track the artifact by digest or another immutable identifier. If staging uses an artifact from commit A and production uses a rebuild of commit A, matching commit IDs alone do not prove the artifact bytes match.

محیط‌ها فرق دارند؛ artifact را برای هرکدام عوض نکنEnvironments differ; do not rebuild the artifact for each

staging و production معمولاً URL، نام سرویس، کلید دسترسی و feature flag متفاوت دارند. این تفاوت‌ها باید در runtime یا مرحلهٔ استقرار تزریق شوند، نه با rebuild کردن برنامه داخل هر محیط. secret را هم داخل artifact، image یا log نگذار؛ تنظیم معمولی و secret هر دو خارج از source نگه داشته شوند، اما secret با دسترسی محدودتر.

Staging and production often have different URLs, service names, credentials, and feature flags. Inject these at runtime or deployment time instead of rebuilding the application in each environment. Keep secrets out of artifacts, images, and logs; both ordinary configuration and secrets live outside source, but secrets require tighter access.

متغیرهای محیطی به‌تنهایی راز را امن نمی‌کنند؛ مقدار ممکن است در process list، log یا crash report نشت کند. سازوکار secret باید متناسب با پلتفرم باشد و دسترسی‌اش محدود. این فصل قرارداد را می‌گوید، نه اینکه همهٔ سامانه‌های secret را آموزش دهد.

Environment variables alone do not secure a secret; values may leak through process listings, logs, or crash reports. Use the platform’s secret mechanism with narrow access. This chapter defines the contract, not every secret-management system.

promotion یعنی «همان خروجی را یک مرحله جلو ببر»Promotion means “move this exact output forward”

در فصل CI یک artifact ساختیم. برای CD باید همان خروجی را به staging بدهیم، نصب را verify کنیم و بعد از تأیید همان را به production ببریم. ساده‌ترین شاهد محلی، checksum فایل است. در سامانهٔ واقعی registry یا artifact store باید digest و شناسهٔ اجرای تولیدکننده را نگه دارد.

The CI chapter produced an artifact. CD should deploy that same output to staging, verify the installation, and then move it to production after approval. A local checksum is a simple piece of evidence. In a real system, the registry or artifact store should retain the digest and producing run ID.

bash · compare a build artifact, not source timestamps
sha256sum dist-bundle.tar.gz
# record the digest with the staging deployment
# download/promote the same stored artifact for production
sha256sum dist-bundle.tar.gz

دو digest باید برابر باشند؛ خروجی‌های دقیق checksum را ثابت فرض نکن، چون از محتوا می‌آیند. برابری می‌گوید بایت‌ها یکی‌اند، نه اینکه artifact امن است یا production درست پیکربندی شده. اگر digest فرق کرد، deployment را متوقف کن و run ID، artifact name، مسیر download و build مجدد را بررسی کن.

The two digests should match; do not assume a particular checksum because it depends on content. Equality proves the bytes are identical, not that the artifact is safe or production is configured correctly. If they differ, stop promotion and inspect run ID, artifact name, download path, and any rebuild.

artifact را در production دوباره نساز. build یک‌بار انجام می‌شود؛ config محیط را جدا تزریق کن. فصل بعد artifactها و نسخه‌گذاری را دقیق‌تر بررسی می‌کند.Do not rebuild the artifact for production. Build once and inject environment configuration separately. The next chapter examines artifacts and versioning in more depth.

gate دستی، دکمهٔ مبهم نیستA manual gate is not an arbitrary button

برای production، approval زمانی معنا دارد که reviewer بداند چه چیزی را می‌پذیرد: commit، digest، نتیجهٔ staging، migration یا smoke test، و مسئول برگشت. GitHub Actions environments می‌تواند روی job دارای `environment: production` شرط reviewer یا branch/tag policy بگذارد. این شرط‌ها در تنظیمات repository ساخته می‌شوند؛ فقط نوشتن نام environment در YAML یک gate امن ایجاد نمی‌کند.

Production approval is meaningful when the reviewer knows what they are approving: commit, digest, staging results, migrations or smoke tests, and rollback owner. GitHub Actions environments can add reviewer or branch/tag policies to a job with `environment: production`. These rules are configured in repository settings; merely naming an environment in YAML does not create a secure gate.

نمونهٔ جریان زیر build را یک‌بار انجام می‌دهد، artifact را در همان run نگه می‌دارد، staging را deploy و smoke test می‌کند و بعد job production را به environment وصل می‌کند. اگر تنظیم environment reviewer داشته باشد، job تا تأیید منتظر می‌ماند و secretهای همان environment پیش از عبور از protection rules در دسترس job نیستند.

The flow below builds once, stores the artifact in that run, deploys to staging and smoke-tests it, then binds the production job to an environment. If that environment requires a reviewer, the job waits for approval; its environment secrets are unavailable until protection rules pass.

.github/workflows/deploy.yml · same run, same artifact
name: Promote release candidate

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - name: Build once
        run: ./scripts/build-release.sh dist
      - name: Store exact output
        uses: actions/upload-artifact@v7
        with:
          name: app-${{ github.sha }}
          path: dist/
          if-no-files-found: error

  staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: app-${{ github.sha }}
          path: dist/
      - name: Deploy to staging
        run: ./scripts/deploy.sh staging dist/
      - name: Verify staging
        run: ./scripts/smoke-test.sh "$STAGING_URL"
        env:
          STAGING_URL: ${{ vars.STAGING_URL }}

  production:
    needs: staging
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: app-${{ github.sha }}
          path: dist/
      - name: Deploy the promoted output
        run: ./scripts/deploy.sh production dist/
      - name: Verify production
        run: ./scripts/smoke-test.sh "$PRODUCTION_URL"
        env:
          PRODUCTION_URL: ${{ vars.PRODUCTION_URL }}

نام artifact به `github.sha` وصل است و هر دو job از همان run آن را download می‌کنند. شرط `needs: staging` یعنی اگر staging یا smoke test fail شود، production اجرا نمی‌شود. دستورهای `deploy.sh` و `smoke-test.sh` باید در پروژه واقعاً پیاده‌سازی شوند؛ این نمونه الگوی کنترل جریان است و خودش سرور یا URL واقعی برایت نمی‌سازد.

The artifact name includes `github.sha`, and both jobs download it from the same run. `needs: staging` prevents production from running if staging or its smoke test fails. The project must implement `deploy.sh` and `smoke-test.sh`; this is a control-flow pattern, not a real server or URL.

در GitHub.com، artifactهای upload action از v4 به بعد immutable هستند: job دیگری نمی‌تواند آرام‌آرام همان artifact را دست‌کاری کند؛ اگر عمداً overwrite کنی، artifact قبلی حذف و نمونهٔ تازه ساخته می‌شود. این immutability به معنی نگهداری همیشگی نیست: expiration، حذف دستی یا حذف run/repository می‌تواند artifact را از بین ببرد. برای release، digest و run ID را هم ثبت کن.

On GitHub.com, artifacts uploaded with action v4 and later are immutable: another job cannot silently mutate the same artifact. An explicit overwrite deletes the old artifact and creates a new one. Immutability does not mean permanent retention: expiration, manual deletion, or deleting the run/repository can remove it. Record the digest and run ID for releases.

در تنظیمات GitHub، environmentهای `staging` و `production` را پیشاپیش بساز؛ برای production reviewer، جلوگیری از self-review، شاخه/tag مجاز و دسترسی secret را تنظیم کن. محیطی که فقط با YAML ساخته شود ممکن است protection rule نداشته باشد. availability required reviewers برای مخزن خصوصی به plan وابسته است و در GitHub Free/Pro/Team طبق مستندات فعلی فقط در repository عمومی در دسترس است. GitHub.com از upload artifact v4+ پشتیبانی می‌کند؛ این نسخه‌ها در GitHub Enterprise Server پشتیبانی نمی‌شوند و باید نسخهٔ سازگار با GHES را از مستندات خودش انتخاب کرد.Create `staging` and `production` environments in GitHub settings first. Configure production reviewers, prevent self-review, allowed branches/tags, and secret access. An environment created only by YAML may have no protection rules. Required-reviewer availability for private repositories depends on plan; current GitHub docs limit it to public repositories on Free/Pro/Team. GitHub.com supports upload artifact v4+; those versions are not supported on GitHub Enterprise Server, so choose a GHES-compatible version from its documentation.

staging خراب است؛ promotion باید همین‌جا بایستدStaging is wrong; promotion must stop here

برای آزمایش، در تنظیم staging آدرس API را عمداً به endpoint نادرست تغییر بده. deployment ممکن است موفق گزارش شود چون فایل‌ها upload شده‌اند؛ اما smoke test باید endpoint واقعی را درخواست کند و fail شود. تا قبل از دیدن شواهد، علت را حدس نزن: job deploy موفق بود؟ URL از کجا آمده؟ status code و log smoke test چیست؟

For the experiment, deliberately set staging’s API URL to a wrong endpoint. Deployment may report success because files were uploaded, but the smoke test should request the real endpoint and fail. Do not guess before checking evidence: did deployment succeed, where did the URL come from, and what status code and log did the smoke test return?

اگر job `staging` قرمز شود، `production` که به آن `needs` دارد باید skipped بماند. این پیکربندی جلوی promotion را می‌گیرد، اما شکست را فقط وقتی می‌گیرد که smoke test همان رفتار مهم را بررسی کند و failure را با exit code غیرصفر بیرون بدهد. تستی که همیشه 200 جعلی چاپ کند gate نیست.

If the `staging` job turns red, the dependent `production` job should remain skipped. This configuration stops promotion only when the smoke test checks meaningful behaviour and exits non-zero on failure. A test that always prints a fake 200 is not a gate.

آدرس staging را درست کن، run تازه را اجرا کن، و فقط پس از دیدن version/digest موردانتظار و smoke test موفق اجازهٔ production بده. config staging و production را جدا inspect کن تا secret یا آدرس محیط اشتباه جابه‌جا نشده باشد.

Fix the staging URL, run a fresh workflow, and allow production only after confirming the expected version/digest and a passing smoke test. Inspect staging and production configuration separately so secrets or environment URLs have not been crossed.

چه زمانی deploy می‌کنیم و اگر بد شد چطور برمی‌گردیم؟When do we deploy, and how do we roll back?

برای هر commit روی main می‌توان staging را خودکار به‌روز کرد و production را پشت approval گذاشت. اگر تیم release را با tag مشخص می‌کند، می‌تواند workflow جدا یا همین مسیر را برای tag نسخه اجرا کند. این الگو فقط trigger را نشان می‌دهد؛ برای استفادهٔ واقعی، staging، تأیید و policy محیط هم باید در همان run برقرار باشند.

A team may update staging automatically for every commit to main and keep production behind approval. If releases use tags, it can trigger a separate workflow or the same path for version tags. This snippet only shows a trigger; a real release run must still include staging, approval, and environment policies.

YAML · a version tag can start a release path
on:
  push:
    tags:
      - 'v*'

این pattern به معنی «هر کسی tag زد، production را منتشر کن» نیست. job باید tag و commit را بررسی کند، environment production فقط ref مجاز را بپذیرد، و reviewer روی digest آزموده‌شده تصمیم بگیرد. فیلتر trigger به‌تنهایی authorization یا approval نیست.

This pattern does not mean “anyone who pushes a tag can publish to production.” The job must verify the tag and commit, the production environment must accept only allowed refs, and the reviewer must approve the tested digest. A trigger filter alone is neither authorization nor approval.

Rollback هم deployment تازه است، نه پاک‌کردن اتفاق. باید نسخهٔ قبلیِ شناخته‌شده و artifact آن هنوز در registry باشد؛ مسیر rollback همان digest را دوباره به محیط می‌برد، config و migration سازگار را verify می‌کند و نتیجه را در تاریخچه ثبت می‌کند. source قدیمی را همین حالا rebuild نکن، چون ممکن است دیگر همان artifact نباشد.

Rollback is another deployment, not erasing what happened. The known-good previous version and its artifact must still exist in the registry; the rollback flow redeploys that same digest, verifies compatible configuration and migrations, and records the outcome. Do not rebuild old source now, because it may no longer produce the same artifact.

۱. CI و CD چه فرقی دارند؟1. How do CI and CD differ?

یک جمله برای هرکدام بگو و نشان بده چرا سبزشدن CI به معنی production نیست.

Give one sentence for each, then explain why green CI does not mean production.

توضیحExplanation

CI تغییر را به‌طور تکرارپذیر build و check می‌کند؛ CD artifact را به محیط‌ها می‌رساند. CI ممکن است pass شود بدون آنکه هیچ deploymentی انجام شده باشد.

CI repeatably builds and checks a change; CD moves an artifact through environments. CI can pass without any deployment happening.

۲. deploy شد، release شد؟2. Deployed means released?

کد روی production نصب شده اما feature flag خاموش است. چه اتفاقی افتاده؟

Code is installed in production, but its feature flag is off. What happened?

پاسخAnswer

deployment انجام شده، اما قابلیت هنوز release یا برای کاربر فعال نشده. این جدایی می‌تواند بررسی و آشکارسازی تدریجی را ممکن کند.

It has been deployed, but the capability has not been released or enabled for users. Separating the two can support verification and gradual exposure.

۳. چرا یک build؟3. Why build once?

staging و production از source یکسان build می‌شوند ولی dependency شناور است. خطر را توضیح بده.

Staging and production build from the same source, but a dependency is floating. Explain the risk.

توضیحExplanation

هر build ممکن است dependency یا محیط build متفاوتی بگیرد و بایت‌های نهایی فرق کنند. artifact را یک‌بار بساز و همان digest را ترویج کن؛ هنوز باید config محیط را جدا بررسی کرد.

Each build may resolve different dependencies or build environments, producing different bytes. Build once and promote the same digest; environment configuration still needs separate verification.

۴. کدام مقدار در artifact نیست؟4. Which value does not belong in the artifact?

بین `APP_VERSION`، آدرس staging و database password انتخاب کن و جای هرکدام را توضیح بده.

Place `APP_VERSION`, the staging URL, and a database password appropriately.

پاسخAnswer

نسخه یا metadata به artifact گره می‌خورد؛ URL از config محیط می‌آید؛ password فقط از secret store با دسترسی محدود در runtime تزریق می‌شود. secret را در artifact نمی‌گذاریم.

Version metadata is associated with the artifact; the URL comes from environment configuration; the password is injected at runtime from a restricted secret store. Never bake it into the artifact.

۵. دو checksum برابرند5. Two checksums match

چه چیزی را ثابت می‌کند و چه چیزی را نه؟

What does this prove, and what does it not?

پاسخAnswer

برای الگوریتم و فایل مورد مقایسه، بایت‌ها با احتمال بسیار بالا یکسان‌اند. امن یا سالم‌بودن artifact، config درست و موفقیت کاربر را ثابت نمی‌کند.

For the compared files and algorithm, the bytes are overwhelmingly likely identical. It does not prove the artifact is safe or correct, configuration is right, or users succeed.

۶. staging smoke test fail6. Staging smoke test fails

job production به `needs: staging` وابسته است. انتظار داری چه شود؟

The production job has `needs: staging`. What do you expect?

پاسخAnswer

If staging fails, production should not run and remains skipped. This is meaningful only if the smoke test reports real failures with a non-zero exit.

۷. artifact همنام، run متفاوت7. Same artifact name, different run

چرا صرف اینکه artifact هر دو محیط `release.zip` نام دارد، ثابت نمی‌کند یکی است؟

Why does naming both artifacts `release.zip` not prove they are the same?

توضیحExplanation

نام ثابت است ولی محتوا می‌تواند از buildهای مختلف آمده باشد. run ID و digest را مقایسه کن و artifact را از run تولیدکنندهٔ staging دانلود کن.

The name can stay the same while contents come from different builds. Compare run IDs and digests, and download from the run that produced the staged artifact.

۸. secret در environment8. An environment secret

چه مزیتی دارد که secret فقط در job با `environment: production` قرار بگیرد؟

Why scope a secret to the job using `environment: production`?

پاسخAnswer

دسترسی را از jobهای CI و staging جدا می‌کند؛ اگر environment protection دارد، secret فقط بعد از عبور ruleها به job می‌رسد. self-hosted runner یا log ناامن همچنان می‌تواند خطر باشد.

It separates access from CI and staging jobs; with protection rules, the secret is available only after those rules pass. An unsafe self-hosted runner or logs can still expose it.

۹. environment فقط در YAML ساخته شد9. The environment exists only from YAML

آیا نام `production` در YAML به‌تنهایی تأیید دستی می‌سازد؟ چه چیزی را باید inspect کنی؟

Does naming `production` in YAML create manual approval by itself? What should you inspect?

توضیحExplanation

نه؛ environment را در تنظیمات GitHub بررسی کن: required reviewers، self-review، branch/tag policy و availability طرح. محیطی که خودکار ایجاد شود ممکن است rule نداشته باشد.

No. Inspect GitHub environment settings: required reviewers, self-review, branch/tag policy, and plan availability. An implicitly created environment may have no rules.

۱۰. CD delivery یا deployment؟10. Continuous Delivery or Deployment?

یک تیم پس از staging منتظر approval انسانی production است. این الگو به کدام معنا نزدیک‌تر است؟

A team waits for human production approval after staging. Which meaning is this closer to?

پاسخAnswer

Continuous Delivery: تغییر آمادهٔ انتشار است، اما تصمیم production دستی است. واژهٔ CD گاهی عام‌تر استفاده می‌شود، پس قرارداد تیم باید روشن باشد.

Continuous Delivery: the change is release-ready, but production is a manual decision. CD is sometimes used more broadly, so make the team’s terminology explicit.

۱۱. trigger برای نسخه11. Triggering a release version

تیم نسخه‌ها را با tagهایی مثل `v2.1.0` معرفی می‌کند. چه چیزی را قبل از اجازهٔ deploy به production محدود می‌کنی؟

The team marks releases with tags such as `v2.1.0`. What do you restrict before allowing production deployment?

پاسخAnswer

push tag pattern و deployment branch/tag policy همان environment، همراه با permission و approval. pattern نام به‌تنهایی ثابت نمی‌کند tag را فرد مجاز ساخته یا به commit درست اشاره دارد.

Restrict the pushed tag pattern and the environment’s deployment branch/tag policy, along with permissions and approval. A name pattern alone does not prove an authorised person created the tag or that it points to the intended commit.

۱۲. deploy برابر release نیست12. Deployment is not release

چرا feature flag خاموش می‌تواند deployment را از release جدا کند؟ یک محدودیت را هم بگو.

How can a disabled feature flag separate deployment from release? Name one limitation.

توضیحExplanation

کد در محیط حاضر است اما قابلیت برای کاربر فعال نیست؛ می‌توان نصب را قبل از آشکارسازی بررسی کرد. flagها پیچیدگی config و مسیرهای شرطی اضافه می‌کنند و باید پاک‌سازی شوند.

The code is present but not enabled for users, allowing installation checks before exposure. Flags add configuration and conditional-path complexity and need cleanup.

۱۳. approval بدون مدرک13. Approval without evidence

تأییدکننده فقط عبارت «روی staging خوب بود» را می‌بیند. چه مواردی را برای تصمیم اضافه می‌کنی؟

The approver only sees “it worked in staging.” What evidence do you add?

پاسخAnswer

commit و artifact digest، نتیجهٔ smoke test و زمان آن، config/migration لازم، مقصد، برنامهٔ rollback و مسئول on-call. approval قرار نیست بر اساس برچسب سبز کور باشد.

Commit and artifact digest, smoke-test result and time, required config/migrations, target, rollback plan, and on-call owner. Approval should not be a blind response to a green badge.

۱۴. config بد در staging14. A bad staging configuration

فایل‌ها deploy شدند اما smoke test به API اشتباه وصل می‌شود. چه چیزی را اول مقایسه می‌کنی؟

Files deployed, but the smoke test calls the wrong API. What do you compare first?

تشخیصDiagnosis

URL resolveشده در staging، variable/environment منبع آن و log درخواست/status. اگر artifact digest مورد انتظار است، build را دوباره نساز؛ config را اصلاح و همان artifact را verify کن.

The resolved staging URL, its variable/environment source, and request/status log. If the artifact digest is correct, do not rebuild; fix configuration and verify the same artifact.

۱۵. rollback با rebuild15. Rollback by rebuilding

نسخهٔ قبلی را از source قدیمی دوباره build می‌کنند. چه شاهدی کم است؟

The team rebuilds the previous version from old source. What evidence is missing?

توضیحExplanation

باید artifact/digest قبلی شناخته‌شده را داشته باشند. source و tag ممکن است همان بایت‌ها را نسازند؛ rollback بهتر است همان artifact نگهداری‌شده را deploy و بعد verify کند.

They need the known previous artifact/digest. Source and tag may not reproduce identical bytes; rollback should deploy the retained artifact and verify it afterwards.

۱۶. محیط secret و plan16. Environment secrets and plans

مخزن خصوصی روی plan پایه است و required reviewers برای environment دیده نمی‌شود. آیا workflow خراب است؟

A private repository on a basic plan cannot see required reviewers for its environment. Is the workflow broken?

پاسخAnswer

ممکن است محدودیت plan باشد، نه YAML. availability فعلی را در GitHub Docs و تنظیم repository بررسی کن؛ تا gate واقعی قابل‌اثبات نیست، آن را دستی و بی‌صدا فرض نکن.

It may be a plan limitation, not YAML. Check current GitHub documentation and repository settings; do not silently assume a manual gate exists until verified.

۱۷. audit trail حداقلی17. A minimal audit trail

چه داده‌هایی را نگه می‌داری تا بعداً بفهمی چه کسی کدام version را به کجا فرستاد؟

What data do you retain to learn who sent which version where?

پاسخ نمونهExample answer

run ID، commit، artifact digest، environment، timestamp، approver و verification result. secretهای خام را ثبت نکن؛ log باید برای ردیابی کافی ولی کم‌افشا باشد.

Run ID, commit, artifact digest, environment, timestamp, approver, and verification result. Do not record raw secrets; logs should support traceability while minimising exposure.

۱۸. incident: staging سبز، digest فرق دارد18. Incident: staging is green, but the digest differs

smoke test staging موفق است اما digestی که job production دریافت کرده فرق می‌کند. آیا به production ادامه می‌دهی؟ برنامهٔ تشخیص را بنویس.

The staging smoke test passed, but the digest received by the production job differs. Do you proceed? Write your diagnosis plan.

تصمیمDecision

نه؛ promotion را متوقف می‌کنم. run ID، artifact name، upload/download source، احتمال rebuild و checksum هر دو محیط را بررسی می‌کنم. سپس production را از artifactی که staging واقعاً آزموده دوباره آماده می‌کنم و همان digest، config و smoke test را پیش از approval ثبت می‌کنم.

No; stop promotion. Inspect run IDs, artifact names, upload/download source, possible rebuilds, and both checksums. Prepare production from the artifact staging actually tested, then record the matching digest, configuration, and smoke test before approval.

اگر فقط یک دقیقه وقت داریIf you have only one minute

یک‌بار build کن و همان artifact را به staging و production promotion بده؛ config محیط را بیرون artifact نگه دار. staging باید رفتار واقعی را verify کند، نه فقط upload را. approval باید به شواهد وصل باشد. tag یا branch را با policy محیط محدود کن، rollback را از artifact قبلیِ نگهداری‌شده انجام بده و run، digest، approver و نتیجه را ثبت کن.

Build once and promote the same artifact to staging and production; keep environment configuration outside it. Staging must verify real behaviour, not merely upload. Tie approval to evidence. Restrict branch or tag with environment policy, roll back using a retained prior artifact, and record run, digest, approver, and outcome.

اگر digestها یکی نیستند، اگر staging smoke test شکست خورده یا اگر approval فقط یک دکمهٔ بی‌زمینه است، promotion را متوقف کن.Stop promotion if digests differ, the staging smoke test failed, or approval is just an unexplained button.

قدم بعد: artifact را چطور نسخه‌دار و ماندگار کنیم؟Next: how do we version and retain artifacts?

حالا جریان promotion را داریم، اما اگر artifact پاک شود یا نامش به build دیگری اشاره کند، rollback و audit trail روی هوا می‌مانند. فصل بعد دربارهٔ artifact، version و انتخاب شناسه‌ای است که هم آدم و هم سامانه بتوانند دقیقاً همان خروجی را دوباره پیدا کنند.

We now have a promotion path, but if an artifact is deleted or its name points to another build, rollback and audit trails become unreliable. Next, we will look at artifacts, versions, and identifiers that let people and systems find the exact same output again.
