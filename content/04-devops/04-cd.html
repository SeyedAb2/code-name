CD و محیط‌هاCD and environments

CI سبزه و artifact هم آماده‌ست. یکی می‌گه «عالیه؛ staging رو دیدیم، برای production دوباره build می‌گیریم». همین‌جا دست نگه دار. اگه دوباره بسازیم، از کجا مطمئنیم همون چیزیه که چند دقیقه پیش تستش کردیم؟

CI is green and an artifact is ready. Someone says, “It worked in staging, so we’ll build production separately.” Pause here: if we build again, how do we know it is what we tested?

staging موفق شد؛ production هم همون چیز رو می‌گیره؟Staging passed; will production get the same thing?

تیم یک نسخه از برنامه رو در staging آزموده. روز بعد برای production دوباره کد منبع رو build می‌کنن؛ وابستگی تازه resolve شده و خروجی با نمونهٔ آزموده یکی نیست. بعد خطا میاد، ولی کسی نمی‌دونه دقیقاً کدام تفاوت مقصر بوده. محیط دوم رو با build دوم حل نمی‌کنیم؛ یک build رو بین محیط‌ها جابه‌جا می‌کنیم.

The team tested a build in staging. The next day, they rebuilt the source for production; a dependency resolved differently, so the output no longer matched what they tested. A failure follows, and nobody knows which difference caused it. We do not solve a second environment with a second build; we promote one build through environments.

فصل قبل CI رو دیدیم: بررسی روی commit مشخص. CD ادامهٔ همون مسیر هست و artifact رو به محیط مقصد می‌رسونه. «Continuous Delivery» معمولاً تغییر رو آمادهٔ انتشار می‌کنه ولی ممکن هست برای production تأیید انسانی بخواهد؛ «Continuous استقرار» تغییر واجد شرط رو بدون gate دستی خودکار به production می‌فرسته. در گفت‌وگوی روزمره CD گاهی هر دو معنا رو می‌ده، پس قرارداد تیم رو صریح کن.

Last chapter used CI to check a specific commit. CD continues that path and moves its artifact to a target environment. “Continuous Delivery” generally keeps a change ready to release but may require human production approval; “Continuous Deployment” automatically sends qualifying changes to production without a manual gate. In everyday usage, CD can mean either, so make the team’s contract explicit.

استقرار یعنی artifact رو در یک محیط مستقر کنیم؛ انتشار یعنی قابلیت برای کاربر قابل‌استفاده بشه. این دو همیشه هم‌زمان نیستند: کدی می‌تونه استقرار بشه اما پشت قابلیت flag خاموش بمونه. این جدایی به ما امکان می‌ده نصب رو بررسی کنیم، بعد جداگانه زمان آشکارشدن قابلیت رو انتخاب کنیم.

Deployment places an artifact in an environment; release makes a capability available to users. They need not happen together: code can be deployed while a feature flag keeps it hidden. Separating the two lets us verify installation before choosing when users see the feature.

پیکان افقی حرکت همون artifact رو نشون می‌ده؛ پیکان‌های عمودی تنظیمات محیط رو نشون می‌دن. artifact رو با digest یا شناسهٔ immutable دنبال کن. اگه staging از commit A و production از rebuild commit A استفاده کنه، یکی بودن شمارهٔ commit به‌تنهایی یکی بودن بایت‌های artifact رو ثابت نمی‌کنه.

The horizontal arrows show one artifact moving forward; the vertical arrows show environment-specific configuration. Track the artifact by digest or another immutable identifier. If staging uses an artifact from commit A and production uses a rebuild of commit A, matching commit IDs alone do not prove the artifact bytes match.

محیط‌ها فرق دارن؛ artifact رو برای هرکدام عوض نکنEnvironments differ; do not rebuild the artifact for each

staging و production معمولاً URL، نام سرویس، کلید دسترسی و قابلیت flag متفاوت دارن. این تفاوت‌ها باید در runtime یا مرحلهٔ استقرار تزریق بشن، نه با rebuild کردن برنامه داخل هر محیط. secret رو هم داخل artifact، image یا لاگ نگذار؛ تنظیم معمولی و secret هر دو خارج از کد منبع نگه داشته بشن، اما secret با دسترسی محدودتر.

Staging and production often have different URLs, service names, credentials, and feature flags. Inject these at runtime or deployment time instead of rebuilding the application in each environment. Keep secrets out of artifacts, images, and logs; both ordinary configuration and secrets live outside source, but secrets require tighter access.

متغیرهای محیطی به‌تنهایی راز رو امن نمی‌کنن؛ مقدار ممکن هست در process list، لاگ یا crash report نشت کنه. سازوکار secret باید متناسب با پلتفرم باشه و دسترسی‌اش محدود. اینجا فقط قرارداد و مرز کار رو روشن می‌کنیم؛ قرار نیست همهٔ ابزارهای مدیریت secret رو یک‌جا یاد بگیریم.

Environment variables alone do not secure a secret; values may leak through process listings, logs, or crash reports. Use the platform’s secret mechanism with narrow access. This chapter defines the contract, not every secret-management system.

ارتقای نسخه یعنی «همون خروجی رو یک مرحله جلو ببر»Promotion means “move this exact output forward”

در فصل CI یک artifact ساختیم. برای CD باید همون خروجی رو به staging بدهیم، نصب رو verify کنیم و بعد از تأیید همون رو به production ببریم. ساده‌ترین شاهد محلی، checksum فایل هست. در سامانهٔ واقعی registry یا artifact store باید digest و شناسهٔ اجرای تولیدکننده رو نگه داره.

The CI chapter produced an artifact. CD should deploy that same output to staging, verify the installation, and then move it to production after approval. A local checksum is a simple piece of evidence. In a real system, the registry or artifact store should retain the digest and producing run ID.

bash · compare a build artifact, not source timestamps
sha256sum dist-bundle.tar.gz
# record the digest with the staging deployment
# download/promote the same stored artifact for production
sha256sum dist-bundle.tar.gz

دو digest باید برابر باشن؛ خروجی‌های دقیق checksum رو ثابت فرض نکن، چون از محتوا میان. برابری می‌گه بایت‌ها یکی‌اند، نه اینکه artifact امن هست یا production درست پیکربندی شده. اگه digest فرق کرد، استقرار رو متوقف کن و run ID، artifact name، مسیر download و build مجدد رو بررسی کن.

The two digests should match; do not assume a particular checksum because it depends on content. Equality proves the bytes are identical, not that the artifact is safe or production is configured correctly. If they differ, stop promotion and inspect run ID, artifact name, download path, and any rebuild.

artifact رو در production دوباره نساز. build یک‌بار انجام می‌شه؛ تنظیمات محیط رو جدا تزریق کن. فصل بعد artifactها و نسخه‌گذاری رو دقیق‌تر بررسی می‌کنه.Do not rebuild the artifact for production. Build once and inject environment configuration separately. The next chapter examines artifacts and versioning in more depth.

gate دستی، دکمهٔ مبهم نیستA manual gate is not an arbitrary button

برای production، تأیید زمانی معنا داره که بازبین بداند چه چیزی رو می‌پذیره: commit، digest، نتیجهٔ staging، migration یا smoke test، و مسئول برگشت. GitHub Actions environments می‌تونه روی job دارای `محیط: production` شرط بازبین یا branch/tag سیاست بگذارد. این شرط‌ها در تنظیمات repository ساخته می‌شن؛ فقط نوشتن نام محیط در YAML یک gate امن ایجاد نمی‌کنه.

Production approval is meaningful when the reviewer knows what they are approving: commit, digest, staging results, migrations or smoke tests, and rollback owner. GitHub Actions environments can add reviewer or branch/tag policies to a job with `environment: production`. These rules are configured in repository settings; merely naming an environment in YAML does not create a secure gate.

نمونهٔ جریان زیر build رو یک‌بار انجام می‌ده، artifact رو در همون run نگه می‌داره، staging رو استقرار و smoke test می‌کنه و بعد job production رو به محیط وصل می‌کنه. اگه تنظیم محیط بازبین داشته باشه، job تا تأیید منتظر می‌مونه و secretهای همون محیط قبل از عبور از protection rules در دسترس job نیستند.

The flow below builds once, stores the artifact in that run, deploys to staging and smoke-tests it, then binds the production job to an environment. If that environment requires a reviewer, the job waits for approval; its environment secrets are unavailable until protection rules pass.

.github/workflows/deploy.yml · same run, same artifact
name: Promote release candidate

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - name: Build once
        run: ./scripts/build-release.sh dist
      - name: Store exact output
        uses: actions/upload-artifact@v7
        with:
          name: app-${{ github.sha }}
          path: dist/
          if-no-files-found: error

  staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: app-${{ github.sha }}
          path: dist/
      - name: Deploy to staging
        run: ./scripts/deploy.sh staging dist/
      - name: Verify staging
        run: ./scripts/smoke-test.sh "$STAGING_URL"
        env:
          STAGING_URL: ${{ vars.STAGING_URL }}

  production:
    needs: staging
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: app-${{ github.sha }}
          path: dist/
      - name: Deploy the promoted output
        run: ./scripts/deploy.sh production dist/
      - name: Verify production
        run: ./scripts/smoke-test.sh "$PRODUCTION_URL"
        env:
          PRODUCTION_URL: ${{ vars.PRODUCTION_URL }}

نام artifact به `github.sha` وصل هست و هر دو job از همون run اون رو download می‌کنن. شرط `needs: staging` یعنی اگه staging یا smoke test fail بشه، production اجرا نمی‌شه. دستورهای `استقرار.sh` و `smoke-test.sh` باید در پروژه واقعاً پیاده‌سازی بشن؛ این نمونه الگوی کنترل جریان هست و خودش سرور یا URL واقعی برایت نمی‌سازه.

The artifact name includes `github.sha`, and both jobs download it from the same run. `needs: staging` prevents production from running if staging or its smoke test fails. The project must implement `deploy.sh` and `smoke-test.sh`; this is a control-flow pattern, not a real server or URL.

در GitHub.com، artifactهای upload action از v4 به بعد immutable هستن: job دیگری نمی‌تونه آرام‌آرام همون artifact رو دست‌کاری کنه؛ اگه عمداً overwrite کنی، artifact قبلی حذف و نمونهٔ تازه ساخته می‌شه. این immutability به معنی نگهداری همیشگی نیست: expiration، حذف دستی یا حذف run/repository می‌تونه artifact رو از بین ببرد. برای انتشار، digest و run ID رو هم ثبت کن.

On GitHub.com, artifacts uploaded with action v4 and later are immutable: another job cannot silently mutate the same artifact. An explicit overwrite deletes the old artifact and creates a new one. Immutability does not mean permanent retention: expiration, manual deletion, or deleting the run/repository can remove it. Record the digest and run ID for releases.

در تنظیمات GitHub، environmentهای `staging` و `production` رو پیشاپیش بساز؛ برای production بازبین، جلوگیری از self-بازبینی، شاخه/tag مجاز و دسترسی secret رو تنظیم کن. محیطی که فقط با YAML ساخته بشه ممکن هست protection rule نداشته باشه. availability required reviewers برای مخزن خصوصی به plan وابسته هست و در GitHub Free/Pro/Team طبق مستندات فعلی فقط در repository عمومی در دسترس هست. GitHub.com از upload artifact v4+ پشتیبانی می‌کنه؛ این نسخه‌ها در GitHub Enterprise Server پشتیبانی نمی‌شن و باید نسخهٔ سازگار با GHES رو از مستندات خودش انتخاب کرد.Create `staging` and `production` environments in GitHub settings first. Configure production reviewers, prevent self-review, allowed branches/tags, and secret access. An environment created only by YAML may have no protection rules. Required-reviewer availability for private repositories depends on plan; current GitHub docs limit it to public repositories on Free/Pro/Team. GitHub.com supports upload artifact v4+; those versions are not supported on GitHub Enterprise Server, so choose a GHES-compatible version from its documentation.

staging خراب هست؛ ارتقای نسخه باید همین‌جا بایستدStaging is wrong; promotion must stop here

برای آزمایش، در تنظیم staging آدرس API رو عمداً به endpoint نادرست تغییر بده. استقرار ممکن هست موفق گزارش بشه چون فایل‌ها upload شدن؛ اما smoke test باید endpoint واقعی رو درخواست کنه و fail بشه. تا قبل از دیدن شواهد، علت رو حدس نزن: job استقرار موفق بود؟ URL از کجا آمده؟ وضعیت کد و لاگ smoke test چیست؟

For the experiment, deliberately set staging’s API URL to a wrong endpoint. Deployment may report success because files were uploaded, but the smoke test should request the real endpoint and fail. Do not guess before checking evidence: did deployment succeed, where did the URL come from, and what status code and log did the smoke test return?

اگه job `staging` قرمز بشه، `production` که به اون `needs` داره باید skipped بمونه. این پیکربندی جلوی ارتقای نسخه رو می‌گیره، اما شکست رو فقط وقتی می‌گیره که smoke test همون رفتار مهم رو بررسی کنه و خطا رو با exit کد غیرصفر بیرون بده. تستی که همیشه 200 جعلی چاپ کنه gate نیست.

If the `staging` job turns red, the dependent `production` job should remain skipped. This configuration stops promotion only when the smoke test checks meaningful behaviour and exits non-zero on failure. A test that always prints a fake 200 is not a gate.

آدرس staging رو درست کن، run تازه رو اجرا کن، و فقط بعد از دیدن نسخه/digest موردانتظار و smoke test موفق اجازهٔ production بده. تنظیمات staging و production رو جدا inspect کن تا secret یا آدرس محیط اشتباه جابه‌جا نشده باشه.

Fix the staging URL, run a fresh workflow, and allow production only after confirming the expected version/digest and a passing smoke test. Inspect staging and production configuration separately so secrets or environment URLs have not been crossed.

چه زمانی استقرار می‌کنیم و اگه بد شد چطور برمی‌گردیم؟When do we deploy, and how do we roll back?

برای هر commit روی main می‌توان staging رو خودکار به‌روز کرد و production رو پشت تأیید گذاشت. اگه تیم انتشار رو با tag مشخص می‌کنه، می‌تونه workflow جدا یا همین مسیر رو برای tag نسخه اجرا کنه. این الگو فقط trigger رو نشون می‌ده؛ برای استفادهٔ واقعی، staging، تأیید و سیاست محیط هم باید در همون run برقرار باشن.

A team may update staging automatically for every commit to main and keep production behind approval. If releases use tags, it can trigger a separate workflow or the same path for version tags. This snippet only shows a trigger; a real release run must still include staging, approval, and environment policies.

YAML · a version tag can start a release path
on:
  push:
    tags:
      - 'v*'

این pattern به معنی «هر کسی tag زد، production رو منتشر کن» نیست. job باید tag و commit رو بررسی کنه، محیط production فقط ref مجاز رو بپذیرد، و بازبین روی digest آزموده‌شده تصمیم بگیره. فیلتر trigger به‌تنهایی authorization یا تأیید نیست.

This pattern does not mean “anyone who pushes a tag can publish to production.” The job must verify the tag and commit, the production environment must accept only allowed refs, and the reviewer must approve the tested digest. A trigger filter alone is neither authorization nor approval.

Rollback هم استقرار تازه هست، نه پاک‌کردن اتفاق. باید نسخهٔ قبلیِ شناخته‌شده و artifact اون هنوز در registry باشه؛ مسیر rollback همون digest رو دوباره به محیط می‌بره، تنظیمات و migration سازگار رو verify می‌کنه و نتیجه رو در تاریخچه ثبت می‌کنه. کد منبع قدیمی رو همین حالا rebuild نکن، چون ممکن هست دیگر همون artifact نباشد.

Rollback is another deployment, not erasing what happened. The known-good previous version and its artifact must still exist in the registry; the rollback flow redeploys that same digest, verifies compatible configuration and migrations, and records the outcome. Do not rebuild old source now, because it may no longer produce the same artifact.

۱. CI و CD چه فرقی دارن؟1. How do CI and CD differ?

یک جمله برای هرکدام بگو و نشان بده چرا سبزشدن CI به معنی production نیست.

Give one sentence for each, then explain why green CI does not mean production.

توضیحExplanation

CI تغییر رو به‌طور تکرارپذیر build و check می‌کنه؛ CD artifact رو به محیط‌ها می‌رسونه. CI ممکن هست pass بشه بدون آنکه هیچ deploymentی انجام شده باشه.

CI repeatably builds and checks a change; CD moves an artifact through environments. CI can pass without any deployment happening.

۲. استقرار شد، انتشار شد؟2. Deployed means released?

کد روی production نصب شده اما قابلیت flag خاموش هست. چه اتفاقی افتاده؟

Code is installed in production, but its feature flag is off. What happened?

پاسخAnswer

استقرار انجام شده، اما قابلیت هنوز انتشار یا برای کاربر فعال نشده. این جدایی می‌تونه بررسی و آشکارسازی تدریجی رو ممکن کنه.

It has been deployed, but the capability has not been released or enabled for users. Separating the two can support verification and gradual exposure.

۳. چرا یک build؟3. Why build once?

staging و production از کد منبع یکسان build می‌شن ولی وابستگی شناور هست. خطر رو توضیح بده.

Staging and production build from the same source, but a dependency is floating. Explain the risk.

توضیحExplanation

هر build ممکن هست وابستگی یا محیط build متفاوتی بگیره و بایت‌های نهایی فرق کنن. artifact رو یک‌بار بساز و همون digest رو ترویج کن؛ هنوز باید تنظیمات محیط رو جدا بررسی کرد.

Each build may resolve different dependencies or build environments, producing different bytes. Build once and promote the same digest; environment configuration still needs separate verification.

۴. کدام مقدار در artifact نیست؟4. Which value does not belong in the artifact?

بین `APP_VERSION`، آدرس staging و database password انتخاب کن و جای هرکدام رو توضیح بده.

Place `APP_VERSION`, the staging URL, and a database password appropriately.

پاسخAnswer

نسخه یا metadata به artifact گره می‌خورد؛ URL از تنظیمات محیط میاد؛ password فقط از secret store با دسترسی محدود در runtime تزریق می‌شه. secret رو در artifact نمی‌گذاریم.

Version metadata is associated with the artifact; the URL comes from environment configuration; the password is injected at runtime from a restricted secret store. Never bake it into the artifact.

چه چیزی رو ثابت می‌کنه و چه چیزی رو نه؟

What does this prove, and what does it not?

پاسخAnswer

برای الگوریتم و فایل مورد مقایسه، بایت‌ها با احتمال بسیار بالا یکسان‌اند. امن یا سالم‌بودن artifact، تنظیمات درست و موفقیت کاربر رو ثابت نمی‌کنه.

For the compared files and algorithm, the bytes are overwhelmingly likely identical. It does not prove the artifact is safe or correct, configuration is right, or users succeed.

۶. staging smoke test fail6. Staging smoke test fails

job production به `needs: staging` وابسته هست. انتظار داری چه بشه؟

The production job has `needs: staging`. What do you expect?

پاسخAnswer

اگه staging شکست بخورد، production اجرا نمی‌شه و skipped می‌مونه. این فقط وقتی gate معنادار هست که smoke test خطای واقعی رو با exit غیرصفر گزارش کنه.

If staging fails, production should not run and remains skipped. This is meaningful only if the smoke test reports real failures with a non-zero exit.

۷. artifact همنام، run متفاوت7. Same artifact name, different run

چرا صرف اینکه artifact هر دو محیط `انتشار.zip` نام داره، ثابت نمی‌کنه یکی هست؟

Why does naming both artifacts `release.zip` not prove they are the same?

توضیحExplanation

نام ثابت هست ولی محتوا می‌تونه از buildهای مختلف آمده باشه. run ID و digest رو مقایسه کن و artifact رو از run تولیدکنندهٔ staging دانلود کن.

The name can stay the same while contents come from different builds. Compare run IDs and digests, and download from the run that produced the staged artifact.

۸. secret در محیط8. An environment secret

چه مزیتی داره که secret فقط در job با `محیط: production` قرار بگیره؟

Why scope a secret to the job using `environment: production`?

پاسخAnswer

دسترسی رو از jobهای CI و staging جدا می‌کنه؛ اگه محیط protection داره، secret فقط بعد از عبور ruleها به job می‌رسه. self-hosted runner یا لاگ ناامن همچنان می‌تونه خطر باشه.

It separates access from CI and staging jobs; with protection rules, the secret is available only after those rules pass. An unsafe self-hosted runner or logs can still expose it.

۹. محیط فقط در YAML ساخته شد9. The environment exists only from YAML

آیا نام `production` در YAML به‌تنهایی تأیید دستی می‌سازه؟ چه چیزی رو باید inspect کنی؟

Does naming `production` in YAML create manual approval by itself? What should you inspect?

توضیحExplanation

نه؛ محیط رو در تنظیمات GitHub بررسی کن: required reviewers، self-بازبینی، branch/tag سیاست و availability طرح. محیطی که خودکار ایجاد بشه ممکن هست rule نداشته باشه.

No. Inspect GitHub environment settings: required reviewers, self-review, branch/tag policy, and plan availability. An implicitly created environment may have no rules.

۱۰. CD delivery یا استقرار؟10. Continuous Delivery or Deployment?

یک تیم بعد از staging منتظر تأیید انسانی production هست. این الگو به کدام معنا نزدیک‌تر هست؟

A team waits for human production approval after staging. Which meaning is this closer to?

پاسخAnswer

Continuous Delivery: تغییر آمادهٔ انتشار هست، اما تصمیم production دستی هست. واژهٔ CD گاهی عام‌تر استفاده می‌شه، پس قرارداد تیم باید روشن باشه.

Continuous Delivery: the change is release-ready, but production is a manual decision. CD is sometimes used more broadly, so make the team’s terminology explicit.

۱۱. trigger برای نسخه11. Triggering a release version

تیم نسخه‌ها رو با tagهایی مثل `v2.1.0` معرفی می‌کنه. چه چیزی رو قبل از اجازهٔ استقرار به production محدود می‌کنی؟

The team marks releases with tags such as `v2.1.0`. What do you restrict before allowing production deployment?

پاسخAnswer

push tag pattern و استقرار branch/tag سیاست همون محیط، همراه با permission و تأیید. pattern نام به‌تنهایی ثابت نمی‌کنه tag رو فرد مجاز ساخته یا به commit درست اشاره داره.

Restrict the pushed tag pattern and the environment’s deployment branch/tag policy, along with permissions and approval. A name pattern alone does not prove an authorised person created the tag or that it points to the intended commit.

۱۲. استقرار برابر انتشار نیست12. Deployment is not release

چرا قابلیت flag خاموش می‌تونه استقرار رو از انتشار جدا کنه؟ یک محدودیت رو هم بگو.

How can a disabled feature flag separate deployment from release? Name one limitation.

توضیحExplanation

کد در محیط حاضر هست اما قابلیت برای کاربر فعال نیست؛ می‌توان نصب رو قبل از آشکارسازی بررسی کرد. flagها پیچیدگی تنظیمات و مسیرهای شرطی اضافه می‌کنن و باید پاک‌سازی بشن.

The code is present but not enabled for users, allowing installation checks before exposure. Flags add configuration and conditional-path complexity and need cleanup.

۱۳. تأیید بدون مدرک13. Approval without evidence

تأییدکننده فقط عبارت «روی staging خوب بود» رو می‌بینه. چه مواردی رو برای تصمیم اضافه می‌کنی؟

The approver only sees “it worked in staging.” What evidence do you add?

پاسخAnswer

commit و artifact digest، نتیجهٔ smoke test و زمان آن، تنظیمات/migration لازم، مقصد، برنامهٔ rollback و مسئول on-call. تأیید قرار نیست بر اساس برچسب سبز کور باشه.

Commit and artifact digest, smoke-test result and time, required config/migrations, target, rollback plan, and on-call owner. Approval should not be a blind response to a green badge.

۱۴. تنظیمات بد در staging14. A bad staging configuration

فایل‌ها استقرار شدن اما smoke test به API اشتباه وصل می‌شه. چه چیزی رو اول مقایسه می‌کنی؟

Files deployed, but the smoke test calls the wrong API. What do you compare first?

تشخیصDiagnosis

URL resolveشده در staging، variable/محیط منبع اون و لاگ درخواست/وضعیت. اگه artifact digest مورد انتظار هست، build رو دوباره نساز؛ تنظیمات رو اصلاح و همون artifact رو verify کن.

The resolved staging URL, its variable/environment source, and request/status log. If the artifact digest is correct, do not rebuild; fix configuration and verify the same artifact.

۱۵. rollback با rebuild15. Rollback by rebuilding

نسخهٔ قبلی رو از کد منبع قدیمی دوباره build می‌کنن. چه شاهدی کم هست؟

The team rebuilds the previous version from old source. What evidence is missing?

توضیحExplanation

باید artifact/digest قبلی شناخته‌شده رو داشته باشن. کد منبع و tag ممکن هست همون بایت‌ها رو نسازند؛ rollback بهتر هست همون artifact نگهداری‌شده رو استقرار و بعد verify کنه.

They need the known previous artifact/digest. Source and tag may not reproduce identical bytes; rollback should deploy the retained artifact and verify it afterwards.

۱۶. محیط secret و plan16. Environment secrets and plans

مخزن خصوصی روی plan پایه هست و required reviewers برای محیط دیده نمی‌شه. آیا workflow خراب هست؟

A private repository on a basic plan cannot see required reviewers for its environment. Is the workflow broken?

پاسخAnswer

ممکن هست محدودیت plan باشه، نه YAML. availability فعلی رو در GitHub Docs و تنظیم repository بررسی کن؛ تا gate واقعی قابل‌اثبات نیست، اون رو دستی و بی‌صدا فرض نکن.

It may be a plan limitation, not YAML. Check current GitHub documentation and repository settings; do not silently assume a manual gate exists until verified.

۱۷. رد قابل‌پیگیری حداقلی17. A minimal audit trail

چه داده‌هایی رو نگه می‌داری تا بعداً بفهمی چه کسی کدام نسخه رو به کجا فرستاد؟

What data do you retain to learn who sent which version where?

پاسخ نمونهExample answer

run ID، commit، artifact digest، محیط، timestamp، approver و verification result. secretهای خام رو ثبت نکن؛ لاگ باید برای ردیابی کافی ولی کم‌افشا باشه.

Run ID, commit, artifact digest, environment, timestamp, approver, and verification result. Do not record raw secrets; logs should support traceability while minimising exposure.

۱۸. رخداد: staging سبز، digest فرق داره18. Incident: staging is green, but the digest differs

smoke test staging موفق هست اما digestی که job production دریافت کرده فرق می‌کنه. آیا به production ادامه می‌دهی؟ برنامهٔ تشخیص رو بنویس.

The staging smoke test passed, but the digest received by the production job differs. Do you proceed? Write your diagnosis plan.

تصمیمDecision

نه؛ ارتقای نسخه رو متوقف می‌کنم. run ID، artifact name، upload/download کد منبع، احتمال rebuild و checksum هر دو محیط رو بررسی می‌کنم. بعد production رو از artifactی که staging واقعاً آزموده دوباره آماده می‌کنم و همون digest، تنظیمات و smoke test رو قبل از تأیید ثبت می‌کنم.

No; stop promotion. Inspect run IDs, artifact names, upload/download source, possible rebuilds, and both checksums. Prepare production from the artifact staging actually tested, then record the matching digest, configuration, and smoke test before approval.

اگه فقط یک دقیقه وقت داریIf you have only one minute

یک‌بار build کن و همون artifact رو به staging و production ارتقای نسخه بده؛ تنظیمات محیط رو بیرون artifact نگه دار. staging باید رفتار واقعی رو verify کنه، نه فقط upload رو. تأیید باید به شواهد وصل باشه. tag یا branch رو با سیاست محیط محدود کن، rollback رو از artifact قبلیِ نگهداری‌شده انجام بده و run، digest، approver و نتیجه رو ثبت کن.

Build once and promote the same artifact to staging and production; keep environment configuration outside it. Staging must verify real behaviour, not merely upload. Tie approval to evidence. Restrict branch or tag with environment policy, roll back using a retained prior artifact, and record run, digest, approver, and outcome.

اگه digestها یکی نیستند، اگه staging smoke test شکست خورده یا اگه تأیید فقط یک دکمهٔ بی‌زمینه هست، ارتقای نسخه رو متوقف کن.Stop promotion if digests differ, the staging smoke test failed, or approval is just an unexplained button.

قدم بعد: artifact رو چطور نسخه‌دار و ماندگار کنیم؟Next: how do we version and retain artifacts?

حالا جریان ارتقای نسخه رو داریم، اما اگه artifact پاک بشه یا نامش به build دیگری اشاره کنه، rollback و رد قابل‌پیگیری روی هوا می‌مونن. فصل بعد دربارهٔ artifact، نسخه و انتخاب شناسه‌ای هست که هم آدم و هم سیستم بتونن دقیقاً همون خروجی رو دوباره پیدا کنن.

We now have a promotion path, but if an artifact is deleted or its name points to another build, rollback and audit trails become unreliable. Next, we will look at artifacts, versions, and identifiers that let people and systems find the exact same output again.
