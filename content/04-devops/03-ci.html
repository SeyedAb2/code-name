دواپس و CI/CD · فصل ۳DevOps & CI/CD · Chapter 3

CI: تست خودکار، lint، buildCI: automated tests, lint, build

فصل قبل گفتیم pull request باید برای همون تغییری که قراره merge بشه مدرک داشته باشه. حالا فرض کن هر نفر lint و test رو با نسخه یا دستور خودش اجرا کنه. یکی می‌گه «برای من سبز بود»، یکی دیگه می‌گه «روی سیستم من شکست خورد». این «سبز بود» دقیقاً یعنی چی؟ بیا یه runner تمیز بذاریم وسط که هر بار همون کارها رو، با همون ترتیب، از صفر انجام بده.

Last chapter established that a pull request needs evidence for the exact change being merged. But if everyone runs lint and tests with different commands or versions, what does “green” mean? We will ask a clean runner to perform the same checks every time.

«روی لپ‌تاپم سبز بود» کافی نیست“It was green on my laptop” is not enough

سارا تغییرش رو فرستاده، بازبین هم نگاه کرده و تأیید داده. merge می‌کنیم و تازه بعدش می‌فهمیم build اصلاً با نسخهٔ Node خود پروژه اجرا نشده. می‌شه سریع گفت «سارا حواسش نبود»، ولی سؤال بهتر اینه: چرا چیزی که باید هر بار یکسان انجام بشه، هنوز به حافظه و حواس آدم‌ها وابسته‌ست؟

Sara submitted a change. A reviewer approved it, but after merging we discover the build had not even run against the project’s Node version. Was Sara careless? Perhaps—but a better question is why the team had no repeatable check for every change.

CI یا Continuous Integration قرار نیست به کد «اعتماد» کنه. تغییر رو با دستورهای مشخص، روی محیطی مشخص، می‌سازه و نتیجه رو به commit مربوط می‌کنه. اگه lint یا test خطا بده، همون گام باید شکست بخورد تا وضعیت به PR برسه. CI فقط کیفیت بررسی‌های تعریف‌شده رو منظم می‌کنه؛ اشتباه بودن خودِ تعریف رو جبران نمی‌کنه.

Continuous Integration does not “trust” code. It runs explicit commands in a defined environment, building the change and attaching results to its commit. If lint or tests fail, that step must fail so the status reaches the PR. CI makes the chosen checks consistent; it cannot compensate for choosing the wrong checks.

شکل یک مسیر رو نشون می‌ده: trigger باعث اجرای job می‌شه؛ job روی runner کار می‌کنه و نتیجه‌اش وضعیت می‌شه؛ میزبان می‌تونه اون وضعیت رو شرط merge کنه. پیکانِ وضعیت check نمی‌گه «برنامه سالم هست»؛ فقط می‌گه دستورهای پیکربندی‌شده با exit موفق تمام شدن.

The diagram shows one path: a trigger starts a job, the job runs on a runner, and its result becomes a status that the host may require for merging. A passed check does not say “the application is healthy”; it says the configured commands exited successfully.

workflow از کجا شروع می‌شه؟Where does a workflow begin?

GitHub Actions فایل YAML رو از `.github/workflows/` می‌خونه. workflow می‌گه چه رویدادی شروعش کنه؛ jobها کارهای مستقل‌اند؛ هر job روی runner مشخصی اجرا می‌شه؛ و stepها دستور یا actionهای همون job هستن. این واژه‌ها رو روی یک نمونهٔ کوچک می‌خوانیم، نه حفظ می‌کنیم.

GitHub Actions reads YAML files from `.github/workflows/`. A workflow declares which events start it; jobs are units of work; each job runs on a selected runner; and steps are commands or actions inside that job. We will read these concepts in a small example rather than memorise a glossary.

یک فایل در مسیر زیر بسازیم. فعلاً trigger رو به push شاخهٔ `main` و pull request به همون شاخه محدود می‌کنیم. بعد از commit کردن workflow در GitHub، در تب Actions باید اجرای تازه رو ببینی؛ اجرای محلی YAML به‌تنهایی ثابت نمی‌کنه GitHub اون رو از مسیر درست خوانده هست.

Create this file at the path below. For now, limit triggers to pushes to `main` and pull requests targeting it. Once the workflow is committed to GitHub, a new run should appear in the Actions tab; locally parsing YAML does not prove GitHub read it from the right path.

.github/workflows/ci.yml · first shape
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - name: Check out repository
        uses: actions/checkout@v6
      - name: Show the revision under test
        run: git rev-parse --short HEAD

`permissions: contents: read` دسترسی پیش‌فرض `GITHUB_TOKEN` رو برای این workflow محدود می‌کنه؛ job بررسی کد برای نوشتن در مخزن نیازی نداره. `checkout` فایل‌ها رو در workspace runner میاره. گام آخر باید شناسهٔ کوتاهی چاپ کنه؛ این شاهد می‌گه چه revisionی در runner هست، نه اینکه آزمون‌ها موفق بودن.

`permissions: contents: read` limits this workflow’s `GITHUB_TOKEN`; a verification job does not need repository write access. `checkout` places repository files in the runner workspace. The last step should print a short revision ID; that identifies what is running, not whether tests passed.

نسخهٔ actionها رو هر از گاهی از مستندات رسمی بازبینی کن. در این نمونه از major tagهای رایج استفاده شده؛ برای زنجیرهٔ حساس، pin کردن action به commit SHA تغییرناپذیر و بازبینی ارتقا، کنترل قوی‌تری هست. runnerهای self-hosted هم باید runtime لازم رو داشته باشن و محافظت بشن.Periodically review action versions against official documentation. This example uses major tags; for sensitive pipelines, pinning actions to immutable commit SHAs and reviewing upgrades provides stronger control. Self-hosted runners must also have required runtimes and be secured.

یک برنامهٔ کوچک که واقعاً چیزی رو بررسی می‌کنهA tiny app that checks something real

فقط workflow داشتن چیزی رو بررسی نمی‌کنه. یک برنامهٔ خیلی کوچک می‌سازیم تا دستورهای محلی و CI یکسان باشن. `npm ci` به lockfile نیاز داره؛ یک‌بار محلی `npm install` اجرا کن و `package-lock.json` رو commit کن. بعد runner نسخهٔ دقیق dependencyهای ثبت‌شده رو نصب می‌کنه.

Having a workflow does not itself check anything. We will create a tiny app so local and CI commands match. `npm ci` requires a lockfile; run `npm install` locally once and commit `package-lock.json`. The runner then installs the exact dependency versions recorded there.

package.json · commands the team agrees to run
{
  "name": "hello-ci-lab",
  "private": true,
  "type": "module",
  "scripts": {
    "lint": "node --check src.mjs",
    "test": "node --test",
    "build": "node build.mjs"
  }
}

`lint` در این نمونه syntax فایل رو با Node بررسی می‌کنه؛ این جای lint معنایی مثل ESLint رو نمی‌گیره. تست‌ها با test runner داخلی Node اجرا می‌شن و build یک artifact کوچک می‌سازه. قبل از افزودن CI، محلی همون سه دستور رو اجرا کن: اگه در پوشهٔ پروژه fail می‌شن، runner هم باید fail بشه.

Here, `lint` checks JavaScript syntax with Node; it is not a substitute for a semantic linter such as ESLint. Tests use Node’s built-in test runner, and build creates a small artifact. Before adding CI, run the same three commands locally: if they fail in the project directory, the runner should fail too.

src.mjs · application function
export function greeting(name) {
  return `Hello, ${name}!`;
}
src.test.mjs · assertion can fail the process
import test from 'node:test';
import assert from 'node:assert/strict';
import { greeting } from './src.mjs';

test('greets the named person', () => {
  assert.equal(greeting('Sara'), 'Hello, Sara!');
});

اگه assertion برقرار نباشد، Node test runner با exit کد غیرصفر بیرون میاد. همین قرارداد مهمه: shell و GitHub Actions از exit کد می‌فهمن گام موفق بوده یا نه. متن قرمز در لاگ فقط ظاهر هست؛ exit وضعیت شاهدی هست که job بر اساسش fail می‌شه.

If the assertion fails, Node’s test runner exits with a non-zero code. That contract matters: the shell and GitHub Actions use the exit code to decide whether a step succeeded. Red text in a log is only appearance; the exit status is the evidence that fails the job.

build.mjs · a small build output
import { mkdir, writeFile } from 'node:fs/promises';
import { greeting } from './src.mjs';

await mkdir('dist', { recursive: true });
await writeFile('dist/greeting.txt', `${greeting('CI')}\n`);

حالا `npm install` و بعد `npm run lint`، `npm test` و `npm run build` رو اجرا کن. `dist/greeting.txt` باید ساخته بشه و در اون `Hello, CI!` باشه. این build نمونه فقط نشون می‌ده گام تولید خروجی کار می‌کنه؛ کیفیت یا سازگاری محصول واقعی رو نمی‌سنجه.

Now run `npm install`, followed by `npm run lint`, `npm test`, and `npm run build`. `dist/greeting.txt` should contain `Hello, CI!`. This toy build only proves the output step works; it says nothing about the quality or compatibility of a real product.

حالا همون بررسی رو به هر تغییر وصل کنیمNow attach the same checks to every change

workflow رو گسترش می‌دهیم: runtime مشخص، checkout، نصب از lockfile، lint، test و build. `setup-node` گزینهٔ cache برای npm داره؛ cache فقط زمان دانلود رو کم می‌کنه و وابستگی رو معتبر نمی‌کنه. `npm ci` همچنان از lockfile نصب پاک و قابل‌تکرار انجام می‌ده.

Expand the workflow with a defined runtime, checkout, lockfile-based install, lint, test, and build. `setup-node` can cache npm data; a cache only reduces download time and does not validate dependencies. `npm ci` still performs a clean, repeatable installation from the lockfile.

.github/workflows/ci.yml · lint, test, build and save artifact
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - name: Check out repository
        uses: actions/checkout@v6

      - name: Set up Node.js
        uses: actions/setup-node@v7
        with:
          node-version: '22'
          cache: npm

      - name: Install locked dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: Test
        run: npm test

      - name: Build
        run: npm run build

      - name: Save build output
        uses: actions/upload-artifact@v7
        with:
          name: hello-ci-build
          path: dist/
          if-no-files-found: error
          retention-days: 7

در Actions، گام ناموفق و لاگ همون گام رو پیدا کن؛ بعد commit رو با `git rev-parse` مقایسه کن تا مطمئن شوی همون تغییر بررسی شده. artifact خروجی build رو برای دریافت از همون اجرای workflow نگه می‌داره؛ استقرار خودکار نیست. اگه مسیر `dist/` ساخته نشود، `if-no-files-found: خطا` باعث می‌شه گام artifact پنهانی سبز نماند.

In Actions, locate the failed step and its log, then compare the commit with `git rev-parse` to ensure the intended change ran. The artifact keeps build output downloadable from that workflow run; it is not an automatic deployment. If `dist/` is missing, `if-no-files-found: error` prevents the artifact step from silently passing.

در نمونه، major tagهای action برای خوانایی آمده و نسخهٔ Node روی 22 ثابت هست. GitHub-hosted runnerها آماده‌اند؛ actionهای upload v7 و runtime جدیدش برای self-hosted runner به runner سازگار نیاز دارن. نسخه‌ها رو از مستندات رسمی روز بررسی کن؛ tag متحرک با SHA ثابت یکسان نیست. نمونه برای GitHub.com هست؛ پشتیبانی نسخه‌های artifact action در GHES می‌تونه فرق کنه.Major action tags keep the example readable, and Node is pinned to 22. GitHub-hosted runners are maintained for these workflows; upload v7 and its newer runtime require a compatible self-hosted runner. Check current official docs: a moving tag is not a fixed SHA. This example targets GitHub.com; artifact-action support can differ on GHES.

عمداً تست رو خراب کنیم؛ قرمزی رو ببینBreak a test deliberately and watch it turn red

تست رو طوری عوض کن که انتظار اشتباه باشه؛ مثلاً انتظار بده `Hello, Sara?` برگردد. قبل از push پیش‌بینی کن کدام گام باید fail بشه. بعد از push روی branch تمرینی، گام `Test` باید غیرصفر تمام بشه و job قرمز بشه. لاگ مقدارهای مورد انتظار و واقعی رو نشون می‌ده؛ این ثابت می‌کنه assertion اجرا شده و mismatch رو گرفته هست.

Change the test so it expects the wrong value—for example, `Hello, Sara?`. Before pushing to a practice branch, predict which step should fail. The `Test` step should exit non-zero and the job should turn red. Its log shows expected and actual values, proving the assertion ran and caught the mismatch.

حالا انتظار تست رو اصلاح کن یا implementation رو آگاهانه تغییر بده، commit تازه بزن و اجرای تازه رو باز کن. سبز شدن اجرای جدید برای commit تازه مهمه؛ سبز قدیمی روی commit قبلی شاهد این تغییر نیست. بعد از fix، گام‌های lint، test و build باید همگی اجرا و موفق بشن.

Now fix the expectation or deliberately change the implementation, commit again, and inspect the new run. A green run for the new commit matters; an old green result for an earlier commit is not evidence for this change. After the fix, lint, test, and build should all run successfully.

این آزمایش رو در branch یا fork تمرینی انجام بده، نه با خراب‌کردن شاخهٔ اصلی پروژه. اگه branch protection فعال هست، قرمز شدن وضعیت check باید merge رو ببندد؛ امکان دور زدن اون به تنظیم میزبان، مجوزها و سیاست تیم بستگی داره.Run this experiment on a practice branch or fork, not by breaking the project’s main branch. With branch protection enabled, a failed status check should block merging; bypass behaviour depends on host configuration, permissions, and team policy.

دام رایج: pipeline سبز هست، چون شکست رو پنهان کردیمA common trap: the pipeline is green because failure was hidden

یک workflow قدیمی چنین گامی داره: `npm test || echo "tests skipped"`. تیم می‌گه «تست اجرا شد، پس سبز بودن یعنی موفقیت». قبل از اصلاح، متن shell رو بخوان: اگه `npm test` شکست بخورد، دستور سمت راست اجرا می‌شه و `echo` معمولاً exit کد صفر می‌ده. runner شکست اصلی رو نمی‌بینه.

An old workflow contains `npm test || echo "tests skipped"`. The team says, “The tests ran, so green means success.” Read the shell expression first: if `npm test` fails, the right-hand command runs and `echo` normally exits zero. The runner never sees the original failure.

bash · reproduce the misleading success locally
npm test || echo "tests skipped"
echo "shell exit: $?"

# Compare with a command that propagates the failure
npm test

خط `shell exit: 0` در حالت شکست تست شاهد فریب هست. آخرین دستور بلوک، exit کد خودش رو برمی‌گرداند؛ برای دیدن درست نتیجه، خط دوم رو جدا اجرا کن یا shell رو طوری بنویس که خطا رو نبلعد. `continue-on-خطا: true` هم عمداً همین مرز رو تغییر می‌ده و برای check اجباری انتخاب مناسبی نیست.

A `shell exit: 0` line after a failing test is the misleading evidence. A shell block reports the final command’s status; run the comparison separately or write the shell so it propagates failures. `continue-on-error: true` deliberately changes the same boundary and is usually wrong for a required check.

حالا یک ایراد دوم: در پروژهٔ واقعی package داخل `web/` هست، اما CI از ریشه `npm test` می‌زنه. اگه آنجا package.json نباشد، لاگ باید خطای مسیر بده. `working-directory: web` یا `npm --prefix web test` مسیر واقعی رو روشن می‌کنه. دستور موفق در پوشهٔ غلط هم check مفیدی نیست.

Now a second bug: the real package is under `web/`, but CI runs `npm test` from the repository root. If there is no root package.json, the log should report a path-related error. Use `working-directory: web` or `npm --prefix web test` to make the intended location explicit. A successful command in the wrong directory is not a useful check.

اگه workflow شکست خورد، اول نام job و step، working directory، دستور دقیق و exit وضعیت رو بخوان. بعد همون دستور رو محلی با همون نسخهٔ runtime تکرار کن. لاگ رو بررسی کن؛ کلید یا secret رو چاپ نکن.When a workflow fails, first inspect the job and step name, working directory, exact command, and exit status. Then rerun that command locally with the same runtime version. Read logs without printing keys or secrets.

cache و artifact دو چیز متفاوت‌اندA cache and an artifact are different things

با بزرگ‌شدن dependencyها، نصب طول می‌کشه. cache داده‌ای قابل‌بازسازی مثل بسته‌های npm رو برای سریع‌تر شدن اجرای بعدی نگه می‌داره؛ artifact خروجی همون اجرای build مثل `dist/` هست که باید بررسی یا بعداً دریافت بشه. cache تضمین نمی‌کنه ورودی معتبر هست؛ lockfile و نصب پاک هنوز مرجع‌اند.

As dependencies grow, installation takes longer. A cache retains reproducible-to-regenerate data such as npm packages to speed later runs; an artifact is output from this build, such as `dist/`, that may need inspection or download. A cache does not guarantee valid inputs; the lockfile and clean install remain authoritative.

در مثال، `setup-node` cache رو بر اساس lockfile تنظیم می‌کنه. اگه وابستگی عوض بشه، کلید cache تغییر می‌کنه و دادهٔ قدیمی لزوماً استفاده نمی‌شه؛ اما حتی cache hit هم اثبات نمی‌کنه وابستگی بی‌خطر یا برنامه سالم هست. برای workflowهای ورودی از fork، cache رو جای محرمانه‌سازی اطلاعات نگذار؛ جریان‌های کم‌اعتماد ممکن هست به cacheهای قابل‌دسترسی برسن.

In the example, `setup-node` keys caching from the lockfile. When dependencies change, the cache key changes, so old data is not necessarily reused. Still, a cache hit does not prove a dependency is safe or the app is healthy. For workflows triggered by forks, do not treat caches as secret storage; lower-trust workflows may access available caches.

artifact رو فقط وقتی آپلود می‌کنیم که build موفق شده باشه و مسیر خروجی مشخص باشه. نام، مدت نگه‌داری و فایل‌های واردشده رو بررسی کن؛ artifact ممکن هست اطلاعاتی داشته باشه که انتشار عمومی‌اش مناسب نیست. مدت نگه‌داری کوتاه در تمرین کافیه؛ قواعد نگهداری به نیاز پروژه و تنظیم مخزن وابسته هست.

Upload an artifact only after the build succeeds and its output path is known. Inspect its name, retention, and included files; an artifact may contain information unsuitable for public distribution. Short retention is enough for a lab; retention policy depends on the project and repository settings.

secret رو وارد CI نکن مگر لازم باشهDo not put secrets in CI unless needed

workflow این فصل فقط lint و test و build می‌کنه؛ پس به password یا استقرار key احتیاج نداره. برای دسترسی به مخزن هم token فقط `contents: read` داره. هر secret اضافی، چیزی هست که لاگ، وابستگی مخرب یا تغییر workflow می‌تونه در معرض خطر بگذارد.

This chapter’s workflow only lints, tests, and builds, so it needs no password or deployment key. Repository access is limited to a `contents: read` token. Every extra secret is something that logs, a compromised dependency, or a workflow change could put at risk.

در triggerهای `pull_request` از fork، secretهای معمول مخزن در دسترس workflow نیستند؛ این حفاظت مهمه، نه مانع مطلق برای هر رویداد و هر طراحی. از `pull_request_target` برای اجرای کد بررسی‌نشده با اختیارهای حساس استفاده نکن. برای هر workflow، trigger، مجوز `GITHUB_TOKEN`، actionهای شخص ثالث و محل مصرف secret رو جدا بررسی کن.

For `pull_request` events from forks, ordinary repository secrets are not available to the workflow; this is an important safeguard, not a blanket guarantee for every event or design. Do not use `pull_request_target` to run untrusted code with sensitive privileges. Review each workflow’s triggers, `GITHUB_TOKEN` permissions, third-party actions, and secret use separately.

اگه بعدها استقرار key لازم شد، اون رو در secrets مخزن یا محیط محدود نگه دار، فقط در job موردنیاز تزریق کن و مقدارش رو چاپ نکن. این درس هنوز استقرار انجام نمی‌ده؛ اون کار موضوع فصل محیط‌هاست.If a deployment key is needed later, store it in repository or environment secrets with narrow access, expose it only to the required job, and never print it. This chapter does not deploy; that belongs to the environments chapter.

matrix رو کی اضافه کنیم؟ وضعیت رو کی gate کنیم؟When to add a matrix—and when to gate status

اگه برنامه فقط یک runtime پشتیبانی می‌کنه، matrix چند نسخه‌ای زمان و هزینه اضافه می‌کنه بی‌آنکه تصمیمی عوض کنه. وقتی واقعاً چند نسخه رو پشتیبانی می‌کنی، matrix همون job رو با ورودی‌های متفاوت تکرار می‌کنه؛ نتیجه باید روشن کنه کدام ترکیب شکست خورده. شروع کوچک رو پیش‌فرض بگیر.

If the app supports one runtime, a multi-version matrix adds time and cost without changing a decision. When several versions are genuinely supported, a matrix repeats the job with different inputs and identifies which combination failed. Start small by default.

در pull request یک وضعیت check ممکن هست برای merge اجباری بشه. نام check باید پایدار و یکتا باشه؛ branch protection رو بعد از اولین اجرای موفق تنظیم کن تا نام واقعی check رو انتخاب کنی. در تنظیمات میزبان ممکن هست merge queue یا شرط تازه‌بودن شاخه هم دخیل باشه. نسخهٔ قدیمی green رو برای commit جدید قبول نکن.

A status check can be required before a pull request merges. Keep check names stable and unique; configure branch protection after the first successful run so you can select the actual check name. Host settings may also involve merge queues or branch freshness. Do not accept an old green result for a new commit.

در commit تمرینی، یک assertion رو خراب کن و ببین وضعیت failed می‌شه. بعد workflow رو در مخزن GitHub فعال کن، از تنظیمات شاخه check درست رو required کن و PR بساز. این آزمایش ثابت می‌کنه سیاست میزبان جلوی merge رو در همون تنظیمات گرفته؛ اثبات نمی‌کنه runtime production یا همهٔ مسیرهای bypass ایمن‌اند.

Break one assertion in a practice commit and confirm the status fails. Then enable the workflow in a GitHub repository, require the correct check in branch settings, and open a PR. This demonstrates that the host policy blocks merging under those settings; it does not prove production runtime or every bypass path is secure.

تمرین‌ها: سبز بودن رو با شاهد بسنجExercises: judge green by its evidence

تمرین‌ها رو به‌ترتیب انجام بده: اول پیش‌بینی، بعد خواندن لاگ، و آخر طراحی یک check که شکست رو پنهان نکنه.

Work through the sequence: predict first, inspect logs next, and finish by designing a check that cannot hide failure.

۱. runner چیست؟1. What is a runner?

در workflow یک job روی `ubuntu-latest` اجرا می‌شه. این مقدار کدام بخش رو مشخص می‌کنه و کدام بخش رو نه؟

A job runs on `ubuntu-latest`. What does this select, and what does it not select?

توضیحExplanation

runner رو انتخاب می‌کنه؛ stepها و دستورهای job هنوز باید جدا تعریف بشن. این نام تضمین‌کنندهٔ یک snapshot تغییرناپذیر از سیستم‌عامل نیست؛ image runner به‌روز می‌شه.

It selects the runner environment; the job’s steps and commands still need defining. It does not pin an immutable operating-system snapshot; runner images evolve.

۲. workflow اجرا نشد2. The workflow did not run

فایل YAML در `scripts/ci.yml` قرار داره و GitHub هیچ workflowی نشان نمی‌ده. نخستین بررسی؟

The YAML file is at `scripts/ci.yml`, and GitHub shows no workflow. What do you inspect first?

پاسخAnswer

workflowها باید در `.github/workflows/` باشن. مسیر و branchی که فایل در اون commit شده، بعد syntax و trigger رویداد رو بررسی کن.

Workflows belong in `.github/workflows/`. Check the path and the branch containing the committed file, then validate syntax and event triggers.

۳. `push` یا `pull_request`؟3. `push` or `pull_request`?

می‌خوای نتیجه قبل از merge روی PR دیده بشه و بعد از commit مستقیم روی main هم اجرا بشه. چه دو triggerی لازمه؟

You want results visible on a PR before merge and also for direct commits to main. Which two triggers do you need?

پاسخAnswer

`pull_request` برای مقصد main و `push` برای شاخهٔ main. رفتار دقیق رویداد رو با branch filters و سیاست مخزن هماهنگ کن؛ اجرای workflow رو در Actions verify کن.

`pull_request` targeting main and `push` on main. Match filters to repository policy and verify actual runs in Actions.

۴. step شکست خورد، job سبز ماند4. A step failed, but the job stayed green

لاگ پیام test failed داره، اما step موفق هست. چه دو تنظیمی رو جست‌وجو می‌کنی؟

The log says a test failed, but the step passed. Which two settings do you search for?

توضیحExplanation

دستور shell ممکن هست خطا رو با `|| true` یا `echo` ببلعد؛ یا step از `continue-on-خطا` استفاده کنه. exit کد و تنظیم step رو بخوان و علت پنهان‌شدن رو حذف کن.

The shell command may swallow failure with `|| true` or `echo`, or the step may set `continue-on-error`. Inspect exit status and step configuration, then remove the cause.

۵. checkout جا افتاده5. Checkout is missing

runner در گام `npm ci` می‌گه package-lock پیدا نشد؛ workflow گام setup-node داره. چه گامی احتمالاً جا افتاده؟

The runner says it cannot find package-lock during `npm ci`; the workflow has setup-node. Which step is likely missing?

پاسخAnswer

`actions/checkout` باید قبل از نصب اجرا بشه تا فایل‌های مخزن وارد workspace بشن. setup-node فقط runtime رو آماده می‌کنه، کد رو checkout نمی‌کنه.

`actions/checkout` must run before installation to place repository files in the workspace. setup-node prepares the runtime; it does not check out code.

۶. `npm ci` روی لپ‌تاپ موفق نیست6. `npm ci` fails locally

CI می‌گه lockfile با package.json هماهنگ نیست. کجا باید اصلاح رو انجام دهی؟

CI says the lockfile is out of sync with package.json. Where should you fix it?

پاسخAnswer

dependencyها رو محلی با package manager درست همگام کن، lockfile رو commit کن و دوباره CI رو اجرا کن. lockfile رو حذف نکن تا CI از نسخه‌های حل‌شدهٔ تصادفی استفاده کنه.

Synchronise dependencies locally with the project’s package manager, commit the lockfile, and rerun CI. Do not remove the lockfile and let CI resolve arbitrary versions.

۷. CI در پوشهٔ اشتباه هست7. CI runs from the wrong directory

package در `web/` هست؛ workflow از ریشه `npm test` می‌زنه. خروجی لاگ و دو راه اصلاح رو بگو.

The package is in `web/`, but the workflow runs `npm test` at the root. What should the log show, and name two fixes.

توضیحExplanation

npm احتمالاً package.json رو پیدا نمی‌کنه. `working-directory: web` برای step یا `npm --prefix web test` مسیر رو صریح می‌کنه؛ مسیر لاگ باید اجرای همون package رو تأیید کنه.

npm will likely fail to find package.json. Set `working-directory: web` on the step or use `npm --prefix web test`; confirm the log targets that package.

۸. تست شکست خورد ولی shell صفر داد8. A failed test returned zero

توضیح بده چرا `npm test || echo ignored` خروجی گمراه‌کننده می‌ده.

Explain why `npm test || echo ignored` produces misleading success.

پاسخAnswer

بعد از شکست npm، shell دستور echo رو اجرا می‌کنه و exit کد آخرین دستور معمولاً صفر هست. بخش `|| echo` رو حذف کن و دوباره exit وضعیت رو مشاهده کن.

After npm fails, the shell runs echo, whose final exit status is usually zero. Remove the `|| echo` and inspect the resulting status.

۹. تست سبز برای کدام commit؟9. Green for which commit?

PR بعد از سبز شدن دو commit تازه گرفته هست. چه چیزی باید قبل از merge تازه بشه؟

The PR received two new commits after going green. What must be fresh before merging?

پاسخAnswer

وضعیت check باید به آخرین commit یا ترکیب نهایی merge مربوط باشه. شناسهٔ revision در run رو با PR مقایسه کن؛ وضعیت قبلی دیگر دربارهٔ تغییر تازه شاهد نیست.

The check must correspond to the latest commit or final merge candidate. Compare the run’s revision with the PR; an older status is not evidence for new changes.

۱۰. cache hit؛ پس وابستگی امن هست؟10. Cache hit—so dependencies are safe?

جواب کوتاه بده و بگو lockfile و `npm ci` هر کدام چه نقشی دارن.

Answer briefly and explain the separate roles of a lockfile and `npm ci`.

پاسخAnswer

نه. cache کارایی هست، نه گواه امنیت. lockfile نسخه‌ها رو ثبت می‌کنه؛ npm ci نصب رو مطابق اون از نو انجام می‌ده. بررسی آسیب‌پذیری و اعتماد به dependencyها مسئلهٔ جداست.

No. A cache is a performance feature, not a security certificate. The lockfile records versions; npm ci installs cleanly from it. Vulnerability review and dependency trust are separate concerns.

۱۱. matrix می‌ارزه؟11. Is a matrix worthwhile?

سرویس فقط Node 22 رو پشتیبانی می‌کنه؛ پیشنهاد می‌شه هر تغییر رو روی Node 20، 22 و 24 بسازی. چه تصمیمی می‌گیری؟

The service supports only Node 22, but someone proposes testing every change on 20, 22, and 24. What do you decide?

توضیحExplanation

فعلاً Node 22 رو verify کن. matrix وقتی می‌ارزه که نسخه‌های دیگر واقعاً قرارداد پشتیبانی باشن یا ریسک سازگاری رو پوشش دهند؛ هزینه و زمان بی‌دلیل اضافه نکن.

Verify Node 22 for now. A matrix is useful when other versions are part of the support contract or cover real compatibility risk; avoid needless cost and delay.

۱۲. artifact یا cache؟12. Artifact or cache?

می‌خوای `dist/` ساخته‌شده از یک run رو برای دانلود نگه داری. کدام قابلیت و چرا؟

You want to retain that run’s generated `dist/` for download. Which feature and why?

پاسخAnswer

artifact، چون خروجی همون build هست که باید به همون run وصل و دانلود بشه. cache برای بازاستفاده از ورودی قابل‌بازسازی جهت سرعت هست.

An artifact, because it is output from that build that should be attached to and downloaded from the run. A cache reuses regenerable input to improve speed.

۱۳. artifact خالی13. An empty artifact

upload-artifact سبز هست اما می‌گه هیچ فایلی نیافت. چه تغییری جلوی سبز کاذب رو می‌گیره؟

upload-artifact passes but says no files were found. What change prevents a false green?

پاسخAnswer

مسیر build رو verify کن و `if-no-files-found: خطا` بگذار. فقط وقتی فایل واقعاً تولید و در مسیر موردنظر هست، upload موفق می‌شه.

Verify the build output path and set `if-no-files-found: error`. Upload should pass only when the expected files exist at that path.

۱۴. secret در pull request از fork14. A secret in a fork pull request

PR از fork به secret دسترسی نداره. چه کار خطرناکی رو نباید برای دور زدن این محدودیت انجام دهی؟

A fork PR cannot access a secret. What dangerous workaround should you avoid?

پاسخ مسئولانهResponsible answer

کد بررسی‌نشده رو با privilege رویداد حساس مثل `pull_request_target` اجرا نکن و secret رو در لاگ یا ورودی ناامن نریز. طراحی trigger و مجوزها رو براساس threat model بازبینی کن.

Do not run untrusted code with a privileged event such as `pull_request_target`, or expose secrets in logs or unsafe inputs. Review triggers and permissions against the threat model.

۱۵. `contents: read` کافیه؟15. Is `contents: read` enough?

workflow فقط کد رو می‌خونه و test می‌کنه. چرا دسترسی write رو اضافه نکنیم؟

The workflow only reads code and runs tests. Why not grant write access?

توضیحExplanation

اصل کمترین اختیار: مجوزی بده که job واقعاً لازم داره. دسترسی write سطح حمله رو زیاد می‌کنه و برای lint/test/build لازم نیست.

Least privilege: grant only what the job needs. Write access expands the attack surface and is unnecessary for lint, tests, and build.

۱۶. workflow اجرا نمی‌شه16. The workflow never starts

YAML در مسیر درست هست، اما push به `قابلیت/a` اجرا نمی‌شه. trigger فقط `push: branches: [main]` داره. اشکال کجاست؟

The YAML is in the right path, but a push to `feature/a` does not run. The trigger only has `push: branches: [main]`. What is wrong?

پاسخAnswer

فیلتر شاخه push رو به main محدود کرده. اگه branchها هم باید بررسی بشن، trigger یا PR رو متناسب با سیاست گسترش بده؛ logی نیست چون اصلاً run ساخته نشده، پس رویداد filter رو ببین.

The push filter limits runs to main. Expand the trigger or use PR events according to policy; there is no run log because no run was created, so inspect event filters.

۱۷. check اجباری کدام هست؟17. Which check should be required?

در branch settings چند check نام مشابه دارن. چه می‌کنی تا مورد درست رو انتخاب کنی و بعد چه چیزی رو دوباره می‌سنجی؟

Several similarly named checks appear in branch settings. How do you identify the right one, and what do you verify afterwards?

پاسخAnswer

یک اجرای موفق PR رو باز کن و نام دقیق وضعیت/job رو از همون run انتخاب کن؛ بعد PR تازه رو با یک شکست کنترل‌شده آزمایش کن تا مطمئن شوی واقعاً merge رو می‌بنده. تنظیمات میزبان ممکن هست استثنا داشته باشه.

Open a successful PR run and select the exact status/job name; then test a controlled failure on a fresh PR to ensure it blocks merging. Host settings may provide exceptions.

۱۸. رخداد: همه‌چیز سبز، ولی build اشتباه18. Incident: green, but the wrong build

CI سبز هست؛ بعد معلوم می‌شه job از `docs/` اجرا شده و package برنامه در `web/` هست. برنامهٔ تشخیص و اصلاح رو با شواهد بنویس.

CI is green; then you discover the job ran from `docs/` while the app package is in `web/`. Write an evidence-based diagnosis and repair.

برنامهPlan

لاگ فرمان و working directory رو ثبت می‌کنم؛ آن‌ها نشون می‌دن اصلاً کدام package بررسی شده. مسیر رو با `working-directory: web` اصلاح می‌کنم، lockfile همون package رو commit و test شکست‌پذیر اضافه می‌کنم. اجرای تازه باید شناسهٔ commit درست و stepهای واقعی web رو نشون بده؛ سبز شدن دوباره فقط همون checks رو ثابت می‌کنه.

Record the command and working directory from the log; they show which package was checked. Set `working-directory: web`, commit that package’s lockfile, and add a test that can fail. The new run must show the correct commit and actual web steps; another green run proves only those checks.

اگه فقط یک دقیقه وقت داریIf you have only one minute

CI یک دستور تکرارپذیر رو روی commit مشخص اجرا می‌کنه. trigger، runner، job و step رو درست انتخاب کن؛ checkout، runtime، نصب lockfile و check واقعی لازم‌اند. شکست باید exit کد غیرصفر رو تا job برساند. cache رو با artifact اشتباه نگیر، برای check ساده secret نده و وضعیت سبز رو بیشتر از چیزی که واقعاً اجرا شده تفسیر نکن.

CI runs repeatable commands against a specific commit. Choose the right trigger, runner, job, and steps; checkout, runtime setup, lockfile installation, and meaningful checks matter. Failure must reach the job as a non-zero exit. Do not confuse cache with artifact, do not grant secrets to simple checks, and never claim a green status proves more than what ran.

قبل از اعتماد به وضعیت، سه شاهد بخواه: commit درست، دستورهای درست در پوشهٔ درست، و exit statusی که شکست رو پنهان نکرده باشه.Before trusting a status, require three pieces of evidence: the right commit, the right commands in the right directory, and exit statuses that do not hide failures.

قدم بعد: وقتی همه‌چیز سبز هست، به کدام محیط می‌ره؟Next: when everything is green, which environment gets it?

CI می‌گه این تغییر از بررسی‌های خودکار ما عبور کرده؛ هنوز نگفته کجا و چه زمانی استقرار بشه یا چه کسی production رو تأیید کنه. فصل بعد بین staging و production مرز می‌ذاره و جریان CD رو می‌چینه—بدون اینکه green رو با «منتشر شده» اشتباه بگیریم.

CI says this change passed our automated checks; it has not said where or when to deploy, or who approves production. Next, we will separate staging from production and shape the CD flow—without confusing green with “released.”
