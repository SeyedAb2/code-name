CI: تست خودکار، lint، buildCI: automated tests, lint, build

در فصل قبل گفتیم pull request باید برای همان تغییری که قرار است ادغام شود شاهد داشته باشد. اما اگر هر نفر lint و test را با دستور یا نسخه‌ای متفاوت اجرا کند، «سبز شد» یعنی چه؟ یک runner تمیز را وادار می‌کنیم هر بار همان بررسی‌ها را انجام دهد.

Last chapter established that a pull request needs evidence for the exact change being merged. But if everyone runs lint and tests with different commands or versions, what does “green” mean? We will ask a clean runner to perform the same checks every time.

«روی لپ‌تاپم سبز بود» کافی نیست“It was green on my laptop” is not enough

سارا یک تغییر فرستاده. reviewer آن را تأیید کرده، اما بعد از merge می‌بینیم build اصلاً روی نسخهٔ Node پروژه اجرا نشده بوده. آیا مشکل از بی‌دقتی سارا بود؟ شاید؛ ولی سؤال بهتر این است: چرا تیم برای هر تغییر یک بررسی تکرارپذیر نداشت؟

Sara submitted a change. A reviewer approved it, but after merging we discover the build had not even run against the project’s Node version. Was Sara careless? Perhaps—but a better question is why the team had no repeatable check for every change.

CI یا Continuous Integration قرار نیست به کد «اعتماد» کند. تغییر را با دستورهای مشخص، روی محیطی مشخص، می‌سازد و نتیجه را به commit مربوط می‌کند. اگر lint یا test خطا بدهد، همان گام باید شکست بخورد تا status به PR برسد. CI فقط کیفیت بررسی‌های تعریف‌شده را منظم می‌کند؛ اشتباه بودن خودِ تعریف را جبران نمی‌کند.

Continuous Integration does not “trust” code. It runs explicit commands in a defined environment, building the change and attaching results to its commit. If lint or tests fail, that step must fail so the status reaches the PR. CI makes the chosen checks consistent; it cannot compensate for choosing the wrong checks.

شکل یک مسیر را نشان می‌دهد: trigger باعث اجرای job می‌شود؛ job روی runner کار می‌کند و نتیجه‌اش status می‌شود؛ میزبان می‌تواند آن status را شرط merge کند. پیکانِ status check نمی‌گوید «برنامه سالم است»؛ فقط می‌گوید دستورهای پیکربندی‌شده با exit موفق تمام شدند.

The diagram shows one path: a trigger starts a job, the job runs on a runner, and its result becomes a status that the host may require for merging. A passed check does not say “the application is healthy”; it says the configured commands exited successfully.

workflow از کجا شروع می‌شود؟Where does a workflow begin?

GitHub Actions فایل YAML را از `.github/workflows/` می‌خواند. workflow می‌گوید چه رویدادی شروعش کند؛ jobها کارهای مستقل‌اند؛ هر job روی runner مشخصی اجرا می‌شود؛ و stepها دستور یا actionهای همان job هستند. این واژه‌ها را روی یک نمونهٔ کوچک می‌خوانیم، نه حفظ می‌کنیم.

GitHub Actions reads YAML files from `.github/workflows/`. A workflow declares which events start it; jobs are units of work; each job runs on a selected runner; and steps are commands or actions inside that job. We will read these concepts in a small example rather than memorise a glossary.

یک فایل در مسیر زیر بسازیم. فعلاً trigger را به push شاخهٔ `main` و pull request به همان شاخه محدود می‌کنیم. پس از commit کردن workflow در GitHub، در تب Actions باید اجرای تازه را ببینی؛ اجرای محلی YAML به‌تنهایی ثابت نمی‌کند GitHub آن را از مسیر درست خوانده است.

Create this file at the path below. For now, limit triggers to pushes to `main` and pull requests targeting it. Once the workflow is committed to GitHub, a new run should appear in the Actions tab; locally parsing YAML does not prove GitHub read it from the right path.

.github/workflows/ci.yml · first shape
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - name: Check out repository
        uses: actions/checkout@v6
      - name: Show the revision under test
        run: git rev-parse --short HEAD

`permissions: contents: read` دسترسی پیش‌فرض `GITHUB_TOKEN` را برای این workflow محدود می‌کند؛ job بررسی کد برای نوشتن در مخزن نیازی ندارد. `checkout` فایل‌ها را در workspace runner می‌آورد. گام آخر باید شناسهٔ کوتاهی چاپ کند؛ این شاهد می‌گوید چه revisionی در runner است، نه اینکه آزمون‌ها موفق بوده‌اند.

`permissions: contents: read` limits this workflow’s `GITHUB_TOKEN`; a verification job does not need repository write access. `checkout` places repository files in the runner workspace. The last step should print a short revision ID; that identifies what is running, not whether tests passed.

نسخهٔ actionها را هر از گاهی از مستندات رسمی بازبینی کن. در این نمونه از major tagهای رایج استفاده شده؛ برای زنجیرهٔ حساس، pin کردن action به commit SHA تغییرناپذیر و بازبینی ارتقا، کنترل قوی‌تری است. runnerهای self-hosted هم باید runtime لازم را داشته باشند و محافظت شوند.Periodically review action versions against official documentation. This example uses major tags; for sensitive pipelines, pinning actions to immutable commit SHAs and reviewing upgrades provides stronger control. Self-hosted runners must also have required runtimes and be secured.

یک برنامهٔ کوچک که واقعاً چیزی را بررسی می‌کندA tiny app that checks something real

فقط workflow داشتن چیزی را بررسی نمی‌کند. یک برنامهٔ خیلی کوچک می‌سازیم تا دستورهای محلی و CI یکسان باشند. `npm ci` به lockfile نیاز دارد؛ یک‌بار محلی `npm install` اجرا کن و `package-lock.json` را commit کن. بعد runner نسخهٔ دقیق dependencyهای ثبت‌شده را نصب می‌کند.

Having a workflow does not itself check anything. We will create a tiny app so local and CI commands match. `npm ci` requires a lockfile; run `npm install` locally once and commit `package-lock.json`. The runner then installs the exact dependency versions recorded there.

package.json · commands the team agrees to run
{
  "name": "hello-ci-lab",
  "private": true,
  "type": "module",
  "scripts": {
    "lint": "node --check src.mjs",
    "test": "node --test",
    "build": "node build.mjs"
  }
}

`lint` در این نمونه syntax فایل را با Node بررسی می‌کند؛ این جای lint معنایی مثل ESLint را نمی‌گیرد. تست‌ها با test runner داخلی Node اجرا می‌شوند و build یک artifact کوچک می‌سازد. پیش از افزودن CI، محلی همان سه دستور را اجرا کن: اگر در پوشهٔ پروژه fail می‌شوند، runner هم باید fail شود.

Here, `lint` checks JavaScript syntax with Node; it is not a substitute for a semantic linter such as ESLint. Tests use Node’s built-in test runner, and build creates a small artifact. Before adding CI, run the same three commands locally: if they fail in the project directory, the runner should fail too.

src.mjs · application function
export function greeting(name) {
  return `Hello, ${name}!`;
}
src.test.mjs · assertion can fail the process
import test from 'node:test';
import assert from 'node:assert/strict';
import { greeting } from './src.mjs';

test('greets the named person', () => {
  assert.equal(greeting('Sara'), 'Hello, Sara!');
});

اگر assertion برقرار نباشد، Node test runner با exit code غیرصفر بیرون می‌آید. همین قرارداد مهم است: shell و GitHub Actions از exit code می‌فهمند گام موفق بوده یا نه. متن قرمز در log فقط ظاهر است؛ exit status شاهدی است که job بر اساسش fail می‌شود.

If the assertion fails, Node’s test runner exits with a non-zero code. That contract matters: the shell and GitHub Actions use the exit code to decide whether a step succeeded. Red text in a log is only appearance; the exit status is the evidence that fails the job.

build.mjs · a small build output
import { mkdir, writeFile } from 'node:fs/promises';
import { greeting } from './src.mjs';

await mkdir('dist', { recursive: true });
await writeFile('dist/greeting.txt', `${greeting('CI')}\n`);

اکنون `npm install` و بعد `npm run lint`، `npm test` و `npm run build` را اجرا کن. `dist/greeting.txt` باید ساخته شود و در آن `Hello, CI!` باشد. این build نمونه فقط نشان می‌دهد گام تولید خروجی کار می‌کند؛ کیفیت یا سازگاری محصول واقعی را نمی‌سنجد.

Now run `npm install`, followed by `npm run lint`, `npm test`, and `npm run build`. `dist/greeting.txt` should contain `Hello, CI!`. This toy build only proves the output step works; it says nothing about the quality or compatibility of a real product.

حالا همان بررسی را به هر تغییر وصل کنیمNow attach the same checks to every change

workflow را گسترش می‌دهیم: runtime مشخص، checkout، نصب از lockfile، lint، test و build. `setup-node` گزینهٔ cache برای npm دارد؛ cache فقط زمان دانلود را کم می‌کند و dependency را معتبر نمی‌کند. `npm ci` همچنان از lockfile نصب پاک و قابل‌تکرار انجام می‌دهد.

Expand the workflow with a defined runtime, checkout, lockfile-based install, lint, test, and build. `setup-node` can cache npm data; a cache only reduces download time and does not validate dependencies. `npm ci` still performs a clean, repeatable installation from the lockfile.

.github/workflows/ci.yml · lint, test, build and save artifact
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - name: Check out repository
        uses: actions/checkout@v6

      - name: Set up Node.js
        uses: actions/setup-node@v7
        with:
          node-version: '22'
          cache: npm

      - name: Install locked dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: Test
        run: npm test

      - name: Build
        run: npm run build

      - name: Save build output
        uses: actions/upload-artifact@v7
        with:
          name: hello-ci-build
          path: dist/
          if-no-files-found: error
          retention-days: 7

در Actions، گام ناموفق و log همان گام را پیدا کن؛ بعد commit را با `git rev-parse` مقایسه کن تا مطمئن شوی همان تغییر بررسی شده. artifact خروجی build را برای دریافت از همان اجرای workflow نگه می‌دارد؛ deploy خودکار نیست. اگر مسیر `dist/` ساخته نشود، `if-no-files-found: error` باعث می‌شود گام artifact پنهانی سبز نماند.

In Actions, locate the failed step and its log, then compare the commit with `git rev-parse` to ensure the intended change ran. The artifact keeps build output downloadable from that workflow run; it is not an automatic deployment. If `dist/` is missing, `if-no-files-found: error` prevents the artifact step from silently passing.

در نمونه، major tagهای action برای خوانایی آمده و نسخهٔ Node روی 22 ثابت است. GitHub-hosted runnerها آماده‌اند؛ actionهای upload v7 و runtime جدیدش برای self-hosted runner به runner سازگار نیاز دارند. نسخه‌ها را از مستندات رسمی روز بررسی کن؛ tag متحرک با SHA ثابت یکسان نیست. نمونه برای GitHub.com است؛ پشتیبانی نسخه‌های artifact action در GHES می‌تواند فرق کند.Major action tags keep the example readable, and Node is pinned to 22. GitHub-hosted runners are maintained for these workflows; upload v7 and its newer runtime require a compatible self-hosted runner. Check current official docs: a moving tag is not a fixed SHA. This example targets GitHub.com; artifact-action support can differ on GHES.

عمداً تست را خراب کنیم؛ قرمزی را ببینBreak a test deliberately and watch it turn red

تست را طوری عوض کن که انتظار اشتباه باشد؛ مثلاً انتظار بده `Hello, Sara?` برگردد. قبل از push پیش‌بینی کن کدام گام باید fail شود. پس از push روی branch تمرینی، گام `Test` باید غیرصفر تمام شود و job قرمز شود. log مقدارهای مورد انتظار و واقعی را نشان می‌دهد؛ این ثابت می‌کند assertion اجرا شده و mismatch را گرفته است.

Change the test so it expects the wrong value—for example, `Hello, Sara?`. Before pushing to a practice branch, predict which step should fail. The `Test` step should exit non-zero and the job should turn red. Its log shows expected and actual values, proving the assertion ran and caught the mismatch.

حالا انتظار تست را اصلاح کن یا implementation را آگاهانه تغییر بده، commit تازه بزن و اجرای تازه را باز کن. سبز شدن اجرای جدید برای commit تازه مهم است؛ سبز قدیمی روی commit قبلی شاهد این تغییر نیست. پس از fix، گام‌های lint، test و build باید همگی اجرا و موفق شوند.

Now fix the expectation or deliberately change the implementation, commit again, and inspect the new run. A green run for the new commit matters; an old green result for an earlier commit is not evidence for this change. After the fix, lint, test, and build should all run successfully.

این آزمایش را در branch یا fork تمرینی انجام بده، نه با خراب‌کردن شاخهٔ اصلی پروژه. اگر branch protection فعال است، قرمز شدن status check باید merge را ببندد؛ امکان دور زدن آن به تنظیم میزبان، مجوزها و سیاست تیم بستگی دارد.Run this experiment on a practice branch or fork, not by breaking the project’s main branch. With branch protection enabled, a failed status check should block merging; bypass behaviour depends on host configuration, permissions, and team policy.

دام رایج: pipeline سبز است، چون شکست را پنهان کردیمA common trap: the pipeline is green because failure was hidden

یک workflow قدیمی چنین گامی دارد: `npm test || echo "tests skipped"`. تیم می‌گوید «تست اجرا شد، پس سبز بودن یعنی موفقیت». پیش از اصلاح، متن shell را بخوان: اگر `npm test` شکست بخورد، دستور سمت راست اجرا می‌شود و `echo` معمولاً exit code صفر می‌دهد. runner شکست اصلی را نمی‌بیند.

An old workflow contains `npm test || echo "tests skipped"`. The team says, “The tests ran, so green means success.” Read the shell expression first: if `npm test` fails, the right-hand command runs and `echo` normally exits zero. The runner never sees the original failure.

bash · reproduce the misleading success locally
npm test || echo "tests skipped"
echo "shell exit: $?"

# Compare with a command that propagates the failure
npm test

خط `shell exit: 0` در حالت شکست تست شاهد فریب است. آخرین دستور بلوک، exit code خودش را برمی‌گرداند؛ برای دیدن درست نتیجه، خط دوم را جدا اجرا کن یا shell را طوری بنویس که خطا را نبلعد. `continue-on-error: true` هم عمداً همین مرز را تغییر می‌دهد و برای check اجباری انتخاب مناسبی نیست.

A `shell exit: 0` line after a failing test is the misleading evidence. A shell block reports the final command’s status; run the comparison separately or write the shell so it propagates failures. `continue-on-error: true` deliberately changes the same boundary and is usually wrong for a required check.

حالا یک ایراد دوم: در پروژهٔ واقعی package داخل `web/` است، اما CI از ریشه `npm test` می‌زند. اگر آنجا package.json نباشد، log باید خطای مسیر بدهد. `working-directory: web` یا `npm --prefix web test` مسیر واقعی را روشن می‌کند. دستور موفق در پوشهٔ غلط هم check مفیدی نیست.

Now a second bug: the real package is under `web/`, but CI runs `npm test` from the repository root. If there is no root package.json, the log should report a path-related error. Use `working-directory: web` or `npm --prefix web test` to make the intended location explicit. A successful command in the wrong directory is not a useful check.

اگر workflow شکست خورد، اول نام job و step، working directory، دستور دقیق و exit status را بخوان. بعد همان دستور را محلی با همان نسخهٔ runtime تکرار کن. log را بررسی کن؛ کلید یا secret را چاپ نکن.When a workflow fails, first inspect the job and step name, working directory, exact command, and exit status. Then rerun that command locally with the same runtime version. Read logs without printing keys or secrets.

cache و artifact دو چیز متفاوت‌اندA cache and an artifact are different things

با بزرگ‌شدن dependencyها، نصب طول می‌کشد. cache داده‌ای قابل‌بازسازی مثل بسته‌های npm را برای سریع‌تر شدن اجرای بعدی نگه می‌دارد؛ artifact خروجی همان اجرای build مثل `dist/` است که باید بررسی یا بعداً دریافت شود. cache تضمین نمی‌کند ورودی معتبر است؛ lockfile و نصب پاک هنوز مرجع‌اند.

As dependencies grow, installation takes longer. A cache retains reproducible-to-regenerate data such as npm packages to speed later runs; an artifact is output from this build, such as `dist/`, that may need inspection or download. A cache does not guarantee valid inputs; the lockfile and clean install remain authoritative.

در مثال، `setup-node` cache را بر اساس lockfile تنظیم می‌کند. اگر dependency عوض شود، کلید cache تغییر می‌کند و دادهٔ قدیمی لزوماً استفاده نمی‌شود؛ اما حتی cache hit هم اثبات نمی‌کند dependency بی‌خطر یا برنامه سالم است. برای workflowهای ورودی از fork، cache را جای محرمانه‌سازی اطلاعات نگذار؛ جریان‌های کم‌اعتماد ممکن است به cacheهای قابل‌دسترسی برسند.

In the example, `setup-node` keys caching from the lockfile. When dependencies change, the cache key changes, so old data is not necessarily reused. Still, a cache hit does not prove a dependency is safe or the app is healthy. For workflows triggered by forks, do not treat caches as secret storage; lower-trust workflows may access available caches.

artifact را فقط وقتی آپلود می‌کنیم که build موفق شده باشد و مسیر خروجی مشخص باشد. نام، retention و فایل‌های واردشده را بررسی کن؛ artifact ممکن است اطلاعاتی داشته باشد که انتشار عمومی‌اش مناسب نیست. retention کوتاه در تمرین کافی است؛ قواعد نگهداری به نیاز پروژه و تنظیم مخزن وابسته است.

Upload an artifact only after the build succeeds and its output path is known. Inspect its name, retention, and included files; an artifact may contain information unsuitable for public distribution. Short retention is enough for a lab; retention policy depends on the project and repository settings.

secret را وارد CI نکن مگر لازم باشدDo not put secrets in CI unless needed

workflow این فصل فقط lint و test و build می‌کند؛ پس به password یا deploy key احتیاج ندارد. برای دسترسی به مخزن هم token فقط `contents: read` دارد. هر secret اضافی، چیزی است که log، dependency مخرب یا تغییر workflow می‌تواند در معرض خطر بگذارد.

This chapter’s workflow only lints, tests, and builds, so it needs no password or deployment key. Repository access is limited to a `contents: read` token. Every extra secret is something that logs, a compromised dependency, or a workflow change could put at risk.

در triggerهای `pull_request` از fork، secretهای معمول مخزن در دسترس workflow نیستند؛ این حفاظت مهم است، نه مانع مطلق برای هر رویداد و هر طراحی. از `pull_request_target` برای اجرای کد بررسی‌نشده با اختیارهای حساس استفاده نکن. برای هر workflow، trigger، مجوز `GITHUB_TOKEN`، actionهای شخص ثالث و محل مصرف secret را جدا بررسی کن.

For `pull_request` events from forks, ordinary repository secrets are not available to the workflow; this is an important safeguard, not a blanket guarantee for every event or design. Do not use `pull_request_target` to run untrusted code with sensitive privileges. Review each workflow’s triggers, `GITHUB_TOKEN` permissions, third-party actions, and secret use separately.

اگر بعدها deploy key لازم شد، آن را در secrets مخزن یا environment محدود نگه دار، فقط در job موردنیاز تزریق کن و مقدارش را چاپ نکن. این درس هنوز deploy انجام نمی‌دهد؛ آن کار موضوع فصل محیط‌هاست.If a deployment key is needed later, store it in repository or environment secrets with narrow access, expose it only to the required job, and never print it. This chapter does not deploy; that belongs to the environments chapter.

matrix را کی اضافه کنیم؟ status را کی gate کنیم؟When to add a matrix—and when to gate status

اگر برنامه فقط یک runtime پشتیبانی می‌کند، matrix چند نسخه‌ای زمان و هزینه اضافه می‌کند بی‌آنکه تصمیمی عوض کند. وقتی واقعاً چند نسخه را پشتیبانی می‌کنی، matrix همان job را با ورودی‌های متفاوت تکرار می‌کند؛ نتیجه باید روشن کند کدام ترکیب شکست خورده. شروع کوچک را پیش‌فرض بگیر.

If the app supports one runtime, a multi-version matrix adds time and cost without changing a decision. When several versions are genuinely supported, a matrix repeats the job with different inputs and identifies which combination failed. Start small by default.

در pull request یک status check ممکن است برای merge اجباری شود. نام check باید پایدار و یکتا باشد؛ branch protection را پس از اولین اجرای موفق تنظیم کن تا نام واقعی check را انتخاب کنی. در تنظیمات میزبان ممکن است merge queue یا شرط تازه‌بودن شاخه هم دخیل باشد. نسخهٔ قدیمی green را برای commit جدید قبول نکن.

A status check can be required before a pull request merges. Keep check names stable and unique; configure branch protection after the first successful run so you can select the actual check name. Host settings may also involve merge queues or branch freshness. Do not accept an old green result for a new commit.

در commit تمرینی، یک assertion را خراب کن و ببین status failed می‌شود. بعد workflow را در مخزن GitHub فعال کن، از تنظیمات شاخه check درست را required کن و PR بساز. این آزمایش ثابت می‌کند سیاست میزبان جلوی merge را در همان تنظیمات گرفته؛ اثبات نمی‌کند runtime production یا همهٔ مسیرهای bypass ایمن‌اند.

Break one assertion in a practice commit and confirm the status fails. Then enable the workflow in a GitHub repository, require the correct check in branch settings, and open a PR. This demonstrates that the host policy blocks merging under those settings; it does not prove production runtime or every bypass path is secure.

تمرین‌ها: سبز بودن را با شاهد بسنجExercises: judge green by its evidence

تمرین‌ها را به‌ترتیب انجام بده: اول پیش‌بینی، بعد خواندن log، و آخر طراحی یک check که شکست را پنهان نکند.

Work through the sequence: predict first, inspect logs next, and finish by designing a check that cannot hide failure.

۱. runner چیست؟1. What is a runner?

در workflow یک job روی `ubuntu-latest` اجرا می‌شود. این مقدار کدام بخش را مشخص می‌کند و کدام بخش را نه؟

A job runs on `ubuntu-latest`. What does this select, and what does it not select?

توضیحExplanation

runner را انتخاب می‌کند؛ stepها و دستورهای job هنوز باید جدا تعریف شوند. این نام تضمین‌کنندهٔ یک snapshot تغییرناپذیر از سیستم‌عامل نیست؛ image runner به‌روز می‌شود.

It selects the runner environment; the job’s steps and commands still need defining. It does not pin an immutable operating-system snapshot; runner images evolve.

۲. workflow اجرا نشد2. The workflow did not run

فایل YAML در `scripts/ci.yml` قرار دارد و GitHub هیچ workflowی نشان نمی‌دهد. نخستین بررسی؟

The YAML file is at `scripts/ci.yml`, and GitHub shows no workflow. What do you inspect first?

پاسخAnswer

workflowها باید در `.github/workflows/` باشند. مسیر و branchی که فایل در آن commit شده، سپس syntax و trigger رویداد را بررسی کن.

Workflows belong in `.github/workflows/`. Check the path and the branch containing the committed file, then validate syntax and event triggers.

۳. `push` یا `pull_request`؟3. `push` or `pull_request`?

می‌خواهی نتیجه قبل از merge روی PR دیده شود و بعد از commit مستقیم روی main هم اجرا شود. چه دو triggerی لازم است؟

You want results visible on a PR before merge and also for direct commits to main. Which two triggers do you need?

پاسخAnswer

`pull_request` برای مقصد main و `push` برای شاخهٔ main. رفتار دقیق رویداد را با branch filters و سیاست مخزن هماهنگ کن؛ اجرای workflow را در Actions verify کن.

`pull_request` targeting main and `push` on main. Match filters to repository policy and verify actual runs in Actions.

۴. step شکست خورد، job سبز ماند4. A step failed, but the job stayed green

log پیام test failed دارد، اما step موفق است. چه دو تنظیمی را جست‌وجو می‌کنی؟

The log says a test failed, but the step passed. Which two settings do you search for?

توضیحExplanation

دستور shell ممکن است خطا را با `|| true` یا `echo` ببلعد؛ یا step از `continue-on-error` استفاده کند. exit code و تنظیم step را بخوان و علت پنهان‌شدن را حذف کن.

The shell command may swallow failure with `|| true` or `echo`, or the step may set `continue-on-error`. Inspect exit status and step configuration, then remove the cause.

۵. checkout جا افتاده5. Checkout is missing

runner در گام `npm ci` می‌گوید package-lock پیدا نشد؛ workflow گام setup-node دارد. چه گامی احتمالاً جا افتاده؟

The runner says it cannot find package-lock during `npm ci`; the workflow has setup-node. Which step is likely missing?

پاسخAnswer

`actions/checkout` باید پیش از نصب اجرا شود تا فایل‌های مخزن وارد workspace شوند. setup-node فقط runtime را آماده می‌کند، کد را checkout نمی‌کند.

`actions/checkout` must run before installation to place repository files in the workspace. setup-node prepares the runtime; it does not check out code.

۶. `npm ci` روی لپ‌تاپ موفق نیست6. `npm ci` fails locally

CI می‌گوید lockfile با package.json هماهنگ نیست. کجا باید اصلاح را انجام دهی؟

CI says the lockfile is out of sync with package.json. Where should you fix it?

پاسخAnswer

dependencyها را محلی با package manager درست همگام کن، lockfile را commit کن و دوباره CI را اجرا کن. lockfile را حذف نکن تا CI از نسخه‌های حل‌شدهٔ تصادفی استفاده کند.

Synchronise dependencies locally with the project’s package manager, commit the lockfile, and rerun CI. Do not remove the lockfile and let CI resolve arbitrary versions.

۷. CI در پوشهٔ اشتباه است7. CI runs from the wrong directory

package در `web/` است؛ workflow از ریشه `npm test` می‌زند. خروجی log و دو راه اصلاح را بگو.

The package is in `web/`, but the workflow runs `npm test` at the root. What should the log show, and name two fixes.

توضیحExplanation

npm احتمالاً package.json را پیدا نمی‌کند. `working-directory: web` برای step یا `npm --prefix web test` مسیر را صریح می‌کند؛ مسیر log باید اجرای همان package را تأیید کند.

npm will likely fail to find package.json. Set `working-directory: web` on the step or use `npm --prefix web test`; confirm the log targets that package.

۸. تست شکست خورد ولی shell صفر داد8. A failed test returned zero

توضیح بده چرا `npm test || echo ignored` خروجی گمراه‌کننده می‌دهد.

Explain why `npm test || echo ignored` produces misleading success.

پاسخAnswer

بعد از شکست npm، shell دستور echo را اجرا می‌کند و exit code آخرین دستور معمولاً صفر است. بخش `|| echo` را حذف کن و دوباره exit status را مشاهده کن.

After npm fails, the shell runs echo, whose final exit status is usually zero. Remove the `|| echo` and inspect the resulting status.

۹. تست سبز برای کدام commit؟9. Green for which commit?

PR بعد از سبز شدن دو commit تازه گرفته است. چه چیزی باید پیش از merge تازه شود؟

The PR received two new commits after going green. What must be fresh before merging?

پاسخAnswer

status check باید به آخرین commit یا ترکیب نهایی merge مربوط باشد. شناسهٔ revision در run را با PR مقایسه کن؛ status قبلی دیگر دربارهٔ تغییر تازه شاهد نیست.

The check must correspond to the latest commit or final merge candidate. Compare the run’s revision with the PR; an older status is not evidence for new changes.

۱۰. cache hit؛ پس dependency امن است؟10. Cache hit—so dependencies are safe?

جواب کوتاه بده و بگو lockfile و `npm ci` هر کدام چه نقشی دارند.

Answer briefly and explain the separate roles of a lockfile and `npm ci`.

پاسخAnswer

نه. cache کارایی است، نه گواه امنیت. lockfile نسخه‌ها را ثبت می‌کند؛ npm ci نصب را مطابق آن از نو انجام می‌دهد. بررسی آسیب‌پذیری و اعتماد به dependencyها مسئلهٔ جداست.

No. A cache is a performance feature, not a security certificate. The lockfile records versions; npm ci installs cleanly from it. Vulnerability review and dependency trust are separate concerns.

۱۱. matrix ارزش دارد؟11. Is a matrix worthwhile?

سرویس فقط Node 22 را پشتیبانی می‌کند؛ پیشنهاد می‌شود هر تغییر را روی Node 20، 22 و 24 بسازی. چه تصمیمی می‌گیری؟

The service supports only Node 22, but someone proposes testing every change on 20, 22, and 24. What do you decide?

توضیحExplanation

فعلاً Node 22 را verify کن. matrix وقتی ارزش دارد که نسخه‌های دیگر واقعاً قرارداد پشتیبانی باشند یا ریسک سازگاری را پوشش دهند؛ هزینه و زمان بی‌دلیل اضافه نکن.

Verify Node 22 for now. A matrix is useful when other versions are part of the support contract or cover real compatibility risk; avoid needless cost and delay.

۱۲. artifact یا cache؟12. Artifact or cache?

می‌خواهی `dist/` ساخته‌شده از یک run را برای دانلود نگه داری. کدام قابلیت و چرا؟

You want to retain that run’s generated `dist/` for download. Which feature and why?

پاسخAnswer

artifact، چون خروجی همان build است که باید به همان run وصل و دانلود شود. cache برای بازاستفاده از ورودی قابل‌بازسازی جهت سرعت است.

An artifact, because it is output from that build that should be attached to and downloaded from the run. A cache reuses regenerable input to improve speed.

۱۳. artifact خالی13. An empty artifact

upload-artifact سبز است اما می‌گوید هیچ فایلی نیافت. چه تغییری جلوی سبز کاذب را می‌گیرد؟

upload-artifact passes but says no files were found. What change prevents a false green?

پاسخAnswer

مسیر build را verify کن و `if-no-files-found: error` بگذار. فقط وقتی فایل واقعاً تولید و در مسیر موردنظر است، upload موفق می‌شود.

Verify the build output path and set `if-no-files-found: error`. Upload should pass only when the expected files exist at that path.

۱۴. secret در pull request از fork14. A secret in a fork pull request

PR از fork به secret دسترسی ندارد. چه کار خطرناکی را نباید برای دور زدن این محدودیت انجام دهی؟

A fork PR cannot access a secret. What dangerous workaround should you avoid?

پاسخ مسئولانهResponsible answer

کد بررسی‌نشده را با privilege رویداد حساس مثل `pull_request_target` اجرا نکن و secret را در log یا ورودی ناامن نریز. طراحی trigger و مجوزها را براساس threat model بازبینی کن.

Do not run untrusted code with a privileged event such as `pull_request_target`, or expose secrets in logs or unsafe inputs. Review triggers and permissions against the threat model.

۱۵. `contents: read` کافی است؟15. Is `contents: read` enough?

workflow فقط کد را می‌خواند و test می‌کند. چرا دسترسی write را اضافه نکنیم؟

The workflow only reads code and runs tests. Why not grant write access?

توضیحExplanation

اصل کمترین اختیار: مجوزی بده که job واقعاً لازم دارد. دسترسی write سطح حمله را زیاد می‌کند و برای lint/test/build لازم نیست.

Least privilege: grant only what the job needs. Write access expands the attack surface and is unnecessary for lint, tests, and build.

۱۶. workflow اجرا نمی‌شود16. The workflow never starts

YAML در مسیر درست است، اما push به `feature/a` اجرا نمی‌شود. trigger فقط `push: branches: [main]` دارد. اشکال کجاست؟

The YAML is in the right path, but a push to `feature/a` does not run. The trigger only has `push: branches: [main]`. What is wrong?

پاسخAnswer

فیلتر شاخه push را به main محدود کرده. اگر branchها هم باید بررسی شوند، trigger یا PR را متناسب با سیاست گسترش بده؛ logی وجود ندارد چون اصلاً run ساخته نشده، پس event filter را ببین.

The push filter limits runs to main. Expand the trigger or use PR events according to policy; there is no run log because no run was created, so inspect event filters.

۱۷. check اجباری کدام است؟17. Which check should be required?

در branch settings چند check نام مشابه دارند. چه می‌کنی تا مورد درست را انتخاب کنی و بعد چه چیزی را دوباره می‌سنجی؟

Several similarly named checks appear in branch settings. How do you identify the right one, and what do you verify afterwards?

پاسخAnswer

یک اجرای موفق PR را باز کن و نام دقیق status/job را از همان run انتخاب کن؛ سپس PR تازه را با یک شکست کنترل‌شده آزمایش کن تا مطمئن شوی واقعاً merge را می‌بندد. تنظیمات میزبان ممکن است استثنا داشته باشد.

Open a successful PR run and select the exact status/job name; then test a controlled failure on a fresh PR to ensure it blocks merging. Host settings may provide exceptions.

۱۸. incident: همه‌چیز سبز، ولی build اشتباه18. Incident: green, but the wrong build

CI سبز است؛ بعد معلوم می‌شود job از `docs/` اجرا شده و package برنامه در `web/` است. برنامهٔ تشخیص و اصلاح را با شواهد بنویس.

CI is green; then you discover the job ran from `docs/` while the app package is in `web/`. Write an evidence-based diagnosis and repair.

برنامهPlan

log فرمان و working directory را ثبت می‌کنم؛ آن‌ها نشان می‌دهند اصلاً کدام package بررسی شده. مسیر را با `working-directory: web` اصلاح می‌کنم، lockfile همان package را commit و test شکست‌پذیر اضافه می‌کنم. اجرای تازه باید شناسهٔ commit درست و stepهای واقعی web را نشان دهد؛ سبز شدن دوباره فقط همان checks را ثابت می‌کند.

Record the command and working directory from the log; they show which package was checked. Set `working-directory: web`, commit that package’s lockfile, and add a test that can fail. The new run must show the correct commit and actual web steps; another green run proves only those checks.

اگر فقط یک دقیقه وقت داریIf you have only one minute

CI یک دستور تکرارپذیر را روی commit مشخص اجرا می‌کند. trigger، runner، job و step را درست انتخاب کن؛ checkout، runtime، نصب lockfile و check واقعی لازم‌اند. شکست باید exit code غیرصفر را تا job برساند. cache را با artifact اشتباه نگیر، برای check ساده secret نده و status سبز را بیشتر از چیزی که واقعاً اجرا شده تفسیر نکن.

CI runs repeatable commands against a specific commit. Choose the right trigger, runner, job, and steps; checkout, runtime setup, lockfile installation, and meaningful checks matter. Failure must reach the job as a non-zero exit. Do not confuse cache with artifact, do not grant secrets to simple checks, and never claim a green status proves more than what ran.

پیش از اعتماد به status، سه شاهد بخواه: commit درست، دستورهای درست در پوشهٔ درست، و exit statusی که شکست را پنهان نکرده باشد.Before trusting a status, require three pieces of evidence: the right commit, the right commands in the right directory, and exit statuses that do not hide failures.

قدم بعد: وقتی همه‌چیز سبز است، به کدام محیط می‌رود؟Next: when everything is green, which environment gets it?

CI می‌گوید این تغییر از بررسی‌های خودکار ما عبور کرده؛ هنوز نگفته کجا و چه زمانی deploy شود یا چه کسی production را تأیید کند. فصل بعد بین staging و production مرز می‌گذارد و جریان CD را می‌چیند—بدون اینکه green را با «منتشر شده» اشتباه بگیریم.

CI says this change passed our automated checks; it has not said where or when to deploy, or who approves production. Next, we will separate staging from production and shape the CD flow—without confusing green with “released.”
