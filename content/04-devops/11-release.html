Blue-green, canary, rollback

نسخهٔ تازه آماده‌ست. سؤال سخت این نیست که «چطور استقرار کنیم؟»؛ سؤال اینه که چقدر از ترافیک رو، چه زمانی، با چه نشونه‌ای ببریم سمت نسخهٔ تازه و اگه اوضاع بد شد دقیقاً چطور برگردیم. راه برگشت باید قبل از شروع انتشار آماده باشه، نه وسط بحران.

A release is a controlled change under observation. Prepare the way back before you begin.

۸۰دقیقهminutes
۱۸تمرینexercises

نسخهٔ تازه آماده هست؛ ترافیک رو کجا ببریم؟The new version is ready. Where does traffic go?

تصویر v2 ساخته و منتشر شده؛ حالا تعویض container قبلی آسان هست، ولی اگه v2 فقط زیر بار واقعی خطا بده چه؟ قبل از استقرار باید بدانیم ترافیک چطور جابه‌جا می‌شه، سلامت رو با چه نشانه‌ای می‌سنجیم و rollback به کدام artifact دقیق برمی‌چرخه.

Image v2 is built and published. Replacing the old container is easy—but what if v2 fails only under real traffic? Before deployment, define how traffic moves, which signal gates health, and the exact artifact to which rollback returns.

نسخه رو با tag ثابت یا digest ثبت کن؛ latest نامزد rollback نیست. rolling چند instance رو مرحله‌به‌مرحله عوض می‌کنه، blue-green محیط جدید رو کنار قبلی بالا میاره و بعد مسیر رو switch می‌کنه، canary سهم کوچکی از ترافیک رو برای سنجش می‌فرسته. هیچ‌کدام خودبه‌خود بی‌قطعی یا امن نیستند.

Record versions with immutable tags or digests; latest is not a rollback target. A rolling update replaces instances gradually, blue-green starts a second environment and then switches traffic, and a canary sends a small share for evaluation. None is automatically downtime-free or safe.

ترافیک کم‌سهم به candidate می‌ره؛ شواهد سلامت تصمیم ارتقای نسخه یا برگشت رو می‌سازن. rollback یعنی مسیر به artifact شناخته‌شده برگردد، نه اینکه دادهٔ ناسازگار خودبه‌خود ترمیم بشه.

A small traffic share reaches the candidate; health evidence informs promotion or rollback. Routing back to a known artifact does not automatically repair incompatible data.

Readiness gate یعنی قبل از گرفتن ترافیک، endpoint و وابستگی‌های لازم آماده باشن. Healthcheck سبز به‌تنهایی کیفیت همهٔ user journeyها رو ثابت نمی‌کنه؛ پس کنار اون نرخ خطا، latency، لاگ و آزمون واقعی درخواست رو ببین. در canary درصد ۱۰ با ۱۰ درخواست معنای آماری محکمی نداره.

A readiness gate means the endpoint and required dependencies are ready before receiving traffic. A green healthcheck does not prove every user journey works; pair it with error rate, latency, logs, and a real request test. A 10% canary receiving ten requests is not strong statistical evidence.

سوئیچ ترافیک در آزمایشگاهSwitch traffic in a lab

مثلاً stateless، دو backend با خروجی نسخه متفاوت پشت Nginx بگذار. Nginx به‌طور پیش‌فرض weighted round-robin داره؛ وزن ۹ به ۱ تقریباً نسبت ترافیک رو هدایت می‌کنه، نه تضمین دقیق در نمونهٔ کم یا connectionهای طولانی. فایل تنظیمات رو قبل از reload تست کن.

For a stateless example, put two version-reporting backends behind Nginx. Its default upstream method is weighted round-robin; weights 9 and 1 guide an approximate share, not an exact ratio for small samples or long-lived connections. Test the config before reloading.

nginx.conf · start as a 90/10 canary
http {
  upstream app_versions {
    server app_v1:8080 weight=9;
    server app_v2:8080 weight=1;
  }
  server {
    listen 80;
    location / {
      proxy_pass http://app_versions;
      proxy_set_header X-Request-ID $request_id;
    }
  }
}

قبل از route عمومی، nginx -t باید syntax سالم رو گزارش کنه. چند درخواست تکرار کن و header/body نسخه رو ببین؛ از ده درخواست نتیجهٔ آماری نگیر. در Compose نام سرویس معمولاً هنگام resolve تنظیمات نیاز به در دسترس بودن DNS داره؛ برای production، رفتار DNS/reload نسخهٔ Nginx و platform رو جدا بررسی کن.

Before routing traffic, nginx -t should report valid syntax. Send repeated requests and inspect the version in each response; do not infer statistical behavior from ten requests. In Compose, service DNS must resolve when Nginx loads configuration; verify DNS/reload behavior for the Nginx and platform versions used in production.

گیت بعدی مشاهده هست: خطای v2 رو عمداً بالا ببر و ببین متریک/logها چه می‌گن. وقتی 5xx یا p95 از حد توافق گذشت، وزن canary رو صفر کن یا upstream رو به v1 برگردان؛ همون درخواست آزمایشی رو دوباره بفرست و سلامت رو ثابت کن. rollback رو از روی digest/tag ثبت‌شده انجام بده، نه حدس از cache محلی.

The next gate is observation: deliberately make v2 return an error and inspect metrics/logs. When 5xx or p95 exceeds the agreed limit, set canary weight to zero or route back to v1; repeat the same test request and verify health. Roll back to the recorded tag/digest, not a guess about the local cache.

کد برگشت؛ داده هم؟Can code roll back while data cannot?

در lab stateless، route برگشت آسان هست. اما اگه v2 migrationای اجرا کنه که ستون قدیمی رو حذف کنه، v1 ممکن هست دیگر نتواند بخونه. الگوی expand/contract: اول schema افزایشی و سازگار بساز؛ نسخهٔ قدیم و جدید رو هم‌زمان پشتیبانی کن؛ داده رو backfill/verify کن؛ فقط در انتشار بعد از اطمینان ستون قدیمی رو حذف کن. backup جای سازگاری و restore-tested رو نمی‌گیره.

In a stateless lab, routing back is simple. But if v2 runs a migration that removes an old column, v1 may no longer read the database. With expand/contract, add a compatible schema first, support old and new versions together, backfill/verify, and remove the old column only in a later release. A backup does not replace compatibility or a tested restore.

قابلیت flag با ترافیک انتشار فرق داره: flag رفتار یک قابلیت رو در همون نسخه روشن/خاموش می‌کنه؛ canary سهم درخواست‌ها به artifact تازه رو عوض می‌کنه. rollback، ترافیک switch و flag سه اهرم متفاوت‌اند؛ owner و ثبت تغییر هرکدام رو معلوم کن.

A feature flag differs from traffic release: it toggles behavior inside a version, while a canary changes which artifact serves a request share. Rollback, traffic switching, and flags are distinct controls; assign an owner and record each change.

۱۸ تمرین؛ انتخاب، مشاهده، برگشت18 exercises: choose, observe, roll back

۱. artifact دقیق

چرا latest هدف rollback خوبی نیست؟

Why is latest a poor rollback target?

توضیح

قابل‌تغییر و مبهم هست؛ tag نسخه‌ای یا digest دقیق رو ثبت کن.

It is mutable and ambiguous; record a version tag or exact digest.

۲. rolling یا blue-green؟

می‌خوای محیط قبلی رو تا تأیید نگه داری؛ کدام مناسب‌تر هست؟

You want to retain the old environment until verification. Which fits?

پاسخ

Blue-green، با هزینهٔ ظرفیت اضافه و مدیریت state مشترک.

Blue-green, while accounting for extra capacity and shared state.

۳. 90/10

۱۰ درخواست فرستادی، هیچ‌کدام به v2 نرفت؛ آیا وزن غلط هست؟

None of ten requests hit v2. Is the weight broken?

تفسیر

نه لزوماً؛ sample کوچک و connection behavior می‌تونه نسبت مشاهده‌شده رو عوض کنه. تعداد بیشتر و توزیع واقعی رو ببین.

Not necessarily; small samples and connection behavior affect observed share. Use more requests and inspect actual distribution.

۴. v2 خطای ۵۰۰ می‌دهد

اولین پاسخ قابل اتکا برای rollback چیست؟

What is the first safe rollback action?

گام بعد

ترافیک candidate رو صفر/به v1 route کن، بعد متریک و درخواست واقعی رو دوباره verify کن؛ بعد علت رو بررسی کن.

Stop candidate traffic/route to v1, then verify metrics and a real request before investigating cause.

۵. readiness سبز

آیا همهٔ featureها سالم‌اند؟

Are all features healthy?

پاسخ

نه؛ فقط probe تعریف‌شده پاسخ داده. user journey و SLI جدا بررسی بشن.

No; only the configured probe answered. Verify user journeys and SLI separately.

۶. migration ستون

v2 ستون رو حذف کرد؛ چرا بازگرداندن image کافی نیست؟

v2 dropped a column. Why may restoring the image fail?

علت

داده/schema برگشت‌ناپذیر یا با v1 ناسازگار شده؛ migration باید expand/contract باشه.

The schema/data may be irreversible or incompatible with v1; use expand/contract migrations.

۷. CPU بالا، کاربر سالم

آیا خودکار rollback می‌کنی؟

Do you automatically roll back?

تصمیم

نه بدون معیار اثر؛ آستانه باید به سلامت/SLO و سیاست rollout وصل باشه.

Not without impact criteria; thresholds should connect to health/SLO and rollout policy.

۸. config قبل از reload

کدام آزمون قبل از reload Nginx؟

Which check before reloading Nginx?

پاسخ

nginx -t؛ syntax رو می‌سنجه نه دسترسی کامل کاربر.

nginx -t; it checks syntax, not the complete user path.

۹. candidate بدون metrics

ارتقای نسخه رو انجام بدهی؟

Should you promote?

تصمیم

نه؛ نبود مشاهده مدرک سلامت نیست. توقف کن تا scrape و درخواست آزمایشی قابل‌مشاهده بشن.

No. Missing telemetry is not proof of health. Wait until scraping and test requests are observable.

۱۰. Feature flag

flag خاموش هست؛ آیا به نسخهٔ قبلی برگشته‌ای؟

The flag is off. Did you return to the previous version?

دلیل

خیر؛ همون artifact ممکن هست هنوز سرو کنه. flag رفتاری هست، image/نسخه عوض نکرده.

No; the same artifact may still serve. A flag changes behavior, not the deployed image.

۱۱. 5xx یک spike

قبل از ارتقای نسخه یا rollback چه می‌سنجی؟

What do you inspect before promoting or rolling back?

بررسی

مقدار و مدت نسبت به وضعیت پایه، حجم نمونه، تقسیم نسخه و logهای همون درخواست.

Magnitude/duration against baseline, sample size, version split, and logs for affected requests.

۱۲. نسخه‌ها هم‌زمان

در rolling چه وابستگی‌ای باید سازگار بمونه؟

What must remain compatible during rolling updates?

پاسخ

API و database schema/تنظیمات که هر دو نسخه به اون دسترسی دارن.

The API and database schema/config used by both versions.

۱۳. user stickiness

canary برای همهٔ کاربرها یکسان نیست؛ چه چیزی رو بررسی می‌کنی؟

Canary exposure is uneven. What do you check?

تشخیص

load-balancer algorithm، connection pooling/stickiness و درخواست‌های قابل‌مقایسه؛ وزن Nginx لزوماً user ratio دقیق نیست.

Load-balancer algorithm, connection pooling/stickiness, and comparable requests; Nginx weight is not necessarily an exact user ratio.

۱۴. rollback به tag پیشین

tag موجود نیست؛ چه چیزی از قبل باید حفظ می‌شد؟

The tag is unavailable. What should have been retained?

پاسخ

artifact/digest و registry access معتبر، به‌علاوهٔ تنظیمات نسخه‌دار و روش بازگشت آزمایش‌شده.

The artifact/digest and registry access, plus versioned config and a tested rollback procedure.

۱۵. blue و green به یک volume

ریسک چیست؟

What is the risk?

احتیاط

هر دو ممکن هست هم‌زمان state رو تغییر دهند یا با schema ناسازگار برخورد کنن؛ isolation و migration strategy لازمه.

Both may mutate shared state concurrently or disagree on schema; isolation and migration planning matter.

۱۶. v2 سالم پس از ۵ دقیقه

ارتقای نسخه کامل؟

Promote fully?

پاسخ

بستگی به پوشش، حجم و peak workload داره؛ پنجرهٔ مشاهده رو با risk/ترافیک تعیین کن.

It depends on coverage, volume, and peak load; set the observation window against risk and traffic.

۱۷. test config pass

nginx -t موفق؛ route قطعاً کار می‌کنه؟

nginx -t passes. Does routing definitely work?

تفسیر

فقط parse تنظیمات سالم هست؛ DNS، upstream connectivity و درخواست end-to-end رو تست کن.

Only config parsing is proven; test DNS, upstream connectivity, and an end-to-end request.

۱۸. rollback runbook

چه شواهدی بعد از برگشت لازمه؟

What evidence is needed after rollback?

handoff

نسخهٔ زنده، پاسخ مسیر عمومی، health، متریک/لاگ، زمان تغییر و علت تصمیم رو ثبت کن.

Record live version, public-path response, health, metrics/logs, change time, and decision rationale.

برگشت هم انتشار هستRollback is also a release

قبل از cutover نسخهٔ قبلی رو نگه دار؛ تنظیمات رو validate کن؛ candidate رو با سهم کنترل‌شده روشن کن؛ health، متریک و لاگ رو در پنجرهٔ توافق‌شده ببین؛ بعد promote یا route رو برگردان و همون درخواست رو دوباره بیازما. این شواهد مسیر آزمایشی رو ثابت می‌کنه، نه تضمین zero downtime برای هر معماری.

Retain the previous version before cutover; validate config; expose the candidate to a controlled share; observe health, metrics, and logs for the agreed window; then promote or route back and repeat the same request. This proves the lab path, not zero downtime for every architecture.

اگه rollback آماده نیست، انتشار هنوز آماده نیست. نسخهٔ برنامه رو می‌توان برگرداند؛ schema ناسازگار، secret چرخیده یا دادهٔ حذف‌شده شاید نه.If rollback is not ready, the release is not ready. Code can be rolled back; an incompatible schema, rotated credential, or deleted data may not be.
