روی staging یه تنظیم جا افتاده. یکی می‌گه «هفتهٔ پیش من ساختمش»، یکی فایلش رو روی لپ‌تاپ داره، ولی روی ماشینی که باید اجرا بشه خبری ازش نیست. می‌تونیم دوباره همه‌چیز رو دستی بسازیم؛ سؤال اینه که دفعهٔ بعد از کجا بفهمیم محیط دقیقاً همون چیزیه که فکر می‌کنیم؟

A setting is missing in staging. Someone says, “I created it last week”; another has the file on a laptop, but the runtime machine has nothing. If we recreate it, how do we know this environment will match the previous one?

«فکر کنم مثل دفعهٔ قبل بود» مدرک نیست“I think it matched last time” is not evidence

فصل قبل artifact رو نسخه‌دار کردیم تا بدانیم چه چیزی رو تحویل می‌دهیم. حالا نظم مشابهی برای محیط می‌خوایم: configuration وضعیت مطلوب رو توصیف می‌کنه؛ provider می‌خونه و تغییر می‌ده؛ plan اختلاف و کار پیشنهادی رو نشون می‌ده؛ بعد از بررسی، apply اون رو اجرا می‌کنه.

Last chapter we versioned an artifact so we knew what we were shipping. Now we want similar discipline around the environment: configuration describes the desired setup; a provider reads and changes it; plan shows the difference and proposed actions; after review, apply executes them.

برای دیدن چرخه لازم نیست حساب cloud بسازی. این آزمایش فقط چند فایل رو در پوشهٔ موقت مدیریت می‌کنه. مفهوم‌ها واقعی‌اند، اما نه هزینهٔ cloud دارن و نه resource بیرونی می‌سازن. بعداً همین مدل می‌تونه VM یا شبکه رو مدیریت کنه.

You do not need a cloud account to see the cycle. This lab manages files inside a temporary directory. The concepts are real, but it creates no cloud costs or external resources. The same model can later manage a VM or network.

plan تصویر زمان بررسی رو نشون می‌ده، نه تضمین ثبات تا لحظهٔ apply. state هم binding بین آدرس‌های Terraform و objectهای واقعی هست، نه خود زیرساخت.

A plan describes what Terraform observed at planning time; it cannot guarantee nothing changes before apply. State maps Terraform addresses to real objects; it is not the infrastructure itself.

قانون این آزمایش: فقط از پوشهٔ موقت کار کن. هیچ‌وقت destroy یا پاک‌کردن state رو از پروژه یا محیط واقعی امتحان نکن.Lab rule: work only in the temporary directory. Never try destroy or state deletion from a real project or environment.

چهار اسم؛ چهار کار متفاوتFour names, four different jobs

provider راه ارتباط با یک پلتفرم یا API هست. resource چیزی هست که lifecycle اون رو مدیریت می‌کنیم. منبع داده فقط می‌خونه. variable ورودی قابل‌تنظیم هست و output نتیجه‌ای رو نشون می‌ده یا در اختیار بخش دیگری می‌ذاره. نوع resource و فیلدهایش رو مستندات همون provider تعیین می‌کنه؛ Terraform Core به‌تنهایی schema همهٔ cloudها رو نمی‌شناسه.

A provider integrates with a platform or API. A resource is something whose lifecycle we manage. A data source only reads. A variable is configurable input; an output displays a result or exposes it to another part. The provider defines resource types and fields; Terraform Core does not know every cloud schema on its own.

providerها جداگانه نسخه می‌گیرن. نسخهٔ قابل‌قبول رو محدود می‌کنیم و فایل .terraform.lock.hcl رو همراه کد نگه می‌داریم تا ماشین دیگر هم انتخاب قابل‌پیش‌بینی داشته باشه. file_permission در سیستم‌های POSIX مجوز فایل رو مشخص می‌کنه؛ Windows از ACLهای خودش استفاده می‌کنه.

Providers have independent releases. Constrain acceptable versions and keep .terraform.lock.hcl with the code for predictable selection on another machine.

یک آزمایشگاه محلی و بی‌هزینهA local, cost-free lab

نسخهٔ CLI رو ببین و یک پوشهٔ تازه بساز. اگه Terraform نصب نیست، طبق مستندات رسمی سیستم‌عامل نصبش کن. در PowerShell:

Check the CLI version and make a fresh directory. If Terraform is not installed, follow the official OS installation guide. In PowerShell:

PowerShell
terraform version
New-Item -ItemType Directory -Force terraform-playground
Set-Location terraform-playground
New-Item -ItemType Directory -Force generated

در Bash/WSL از mkdir -p terraform-playground/generated && cd terraform-playground استفاده کن. با Get-Location یا pwd مسیر رو تأیید کن. حالا main.tf بساز؛ این HCL دو فایل در همون lab می‌نویسه، یک فایل رو می‌خونه و متن رو خروجی می‌ده.

In Bash/WSL use mkdir -p terraform-playground/generated && cd terraform-playground. Confirm the path with Get-Location or pwd. Create main.tf; this HCL writes two files in the lab, reads one, and outputs its content.

main.tf · local-only resources
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

variable "banner_text" {
  description = "Text written into the lab file"
  type        = string
  default     = "hello from terraform"
}

resource "local_file" "banner" {
  filename        = "${path.module}/generated/banner.txt"
  content         = "${var.banner_text}\n"
  file_permission = "0644"
}

resource "local_file" "receipt" {
  filename        = "${path.module}/generated/receipt.txt"
  content         = "Managed banner: ${local_file.banner.filename}\n"
  file_permission = "0644"
}

data "local_file" "banner" {
  filename   = local_file.banner.filename
  depends_on = [local_file.banner]
}

output "rendered_banner" {
  description = "Content read from the generated file"
  value       = data.local_file.banner.content
}

resource دوم با ارجاع به filename، وابستگی خودکار به banner داره. منبع داده نیز همون resource رو با filename مشخص می‌کنه، اما چون این مقدار از قبل قابل‌محاسبه هست، خواندن فایل ممکن هست در مرحلهٔ plan انجام بشه؛ برای همین اینجا صریحاً depends_on گذاشتیم تا ابتدا فایل ساخته بشه. Terraform از referenceها گراف می‌سازه، نه ترتیب خط‌های فایل.

The second resource references the banner filename, creating an implicit dependency. The data source also uses that filename, but because it is known early, Terraform might read before creation during planning. Here an explicit depends_on defers the read until the file exists. Terraform builds a graph from references, not file-line order.

منبع داده فقط می‌خونه و lifecycle فایل رو مالک نیست. در پروژهٔ واقعی provider دقیق رو مستندات نسخه‌دارش بررسی کن؛ این lab به cloud وصل نمی‌شه.

A data source reads but does not own the file lifecycle. In a real project, consult versioned provider documentation; this lab does not contact a cloud.

init، fmt و validate؛ هنوز چیزی ساخته نشدهInit, fmt, and validate; nothing is created yet

init provider و backend رو آماده می‌کنه و lock file می‌سازه. بعد قالب و ساختار رو بررسی کن:

init prepares the provider and backend and creates the lock file. Then check formatting and configuration structure:

PowerShell or Bash
terraform init
terraform fmt -check
terraform validate

انتظار پیام successful initialization و valid configuration رو داریم. init resource نمی‌سازه؛ validate نحو و ارجاع‌ها رو بررسی می‌کنه، نه دسترسی عملیاتی یا سلامت سرویس رو. اگه provider دانلود نشد، شبکه/نسخه و lock file رو ببین؛ اگه HCL نامعتبر هست، خط گزارش‌شده رو بررسی کن.

Expect successful initialization and a valid-configuration result. Init creates no resources; validate checks syntax and references, not operational access or service health. For provider download errors, check network, version, and lock file; for invalid HCL, inspect the reported line.

state و plan رو در Git نگذار؛ ممکن هست حاوی secret باشن. در .gitignore موارد .terraform/، terraform.tfstate* و *.tfplan رو بگذار. lock file رو commit کن.Keep state and plans out of Git; they may contain secrets. Ignore .terraform/, terraform.tfstate*, and *.tfplan. Commit the lock file.

حدس بزن؛ بعد plan رو بخوانPredict, then read the plan

در پوشهٔ تازه دو resource داریم و هنوز state نیست. پیش‌بینی‌ات رو بنویس، بعد:

We have two resources in a fresh directory and no state. Write your prediction, then run:

PowerShell or Bash
terraform plan
Plan: 2 to add, 0 to change, 0 to destroy.

علامت + کنار هر local_file یعنی ساخت فایل پیشنهاد شده. این خروجی مدرک وضعیت مشاهده‌شده در همین لحظه هست، نه تضمین اینکه تا apply کسی محیط رو تغییر نمی‌ده. اگه destroy، replace یا مسیر ناآشنا دیدی apply نکن؛ پوشه، resource address، workspace و state رو بررسی کن.

A + beside each local_file means creation is proposed. This is evidence from the current observation, not a guarantee nobody changes the environment before apply. If you see destroy, replace, or an unfamiliar path, do not apply; inspect directory, resource addresses, workspace, and state.

در کار تیمی می‌توان plan رو در فایل ذخیره و همون خروجی مرورشده رو apply کرد، اما plan file هم ممکن هست دادهٔ حساس داشته باشه و بعد از تغییر ورودی یا state کهنه بشه. تازه plan بگیر و همون رو بررسی کن.

Teams may save a plan file and apply that reviewed plan, but plan files can contain sensitive data and become stale after inputs or state change. Generate and review a fresh plan.

تأیید آگاهانه و دیدن فایل‌هاApprove deliberately and inspect the files

اگه plan فقط دو فایلِ همین پوشه رو اضافه می‌کنه، apply رو اجرا کن. Terraform plan تازه می‌سازه و تأیید می‌خواد؛ فقط وقتی action و مسیر درست هست yes بزن.

If the plan adds only the two files in this directory, run apply. Terraform creates a fresh plan and asks for approval; type yes only when actions and paths are correct.

PowerShell
terraform apply
terraform output rendered_banner
Get-Content .\generated\banner.txt
Get-Content .\generated\receipt.txt

در Bash/WSL دو دستور آخر رو با cat generated/banner.txt و cat generated/receipt.txt اجرا کن. باید hello from terraform رو ببینی. بعد terraform state list دو resource و یک آدرس data.local_file.banner رو نشون می‌ده؛ منبع داده هم در state ثبت می‌شه، هرچند مالک lifecycle فایل نیست. terraform state show local_file.banner جزئیات resource رو می‌ده. فهرست state به‌تنهایی محتوای درست فایل رو ثابت نمی‌کنه؛ فایل رو هم بخوان.

In Bash/WSL, replace the last two commands with cat generated/banner.txt and cat generated/receipt.txt. You should see hello from terraform. terraform state list then shows two resources and a data.local_file.banner address; data sources are recorded in state even though they do not own the file lifecycle. terraform state show local_file.banner inspects the resource. State listing alone does not prove file contents; read the file too.

یک تغییر بیرون از TerraformA change outside Terraform

در lab فقط banner رو دستی عوض کن؛ این کار رو روی محیط واقعی نکن. بعد پیش‌بینی کن plan چه می‌گه.

In the lab only, manually change the banner; do not do this in a real environment. Predict what plan will report.

PowerShell
Set-Content -NoNewline .\generated\banner.txt 'edited outside terraform'
terraform plan

در Bash/WSL خط اول: printf '%s' 'edited outside terraform' > generated/banner.txt. plan باید اختلاف رو نشون بده و معمولاً هم می‌بینی local_file باید جایگزین بشه؛ شکل دقیق action رو با همون providerی که انتخاب کردی نگاه کن. اگه تغییر دستی عمدی هست، configuration رو هم با مقدار جدید هماهنگ کن؛ اگه مطلوب همون مقدار قبلی هست، plan رو بخوان و apply کن تا reconcile بشه.

In Bash/WSL, use printf '%s' 'edited outside terraform' > generated/banner.txt. Plan should show a difference and typically replacement of the local_file; inspect the exact action for your provider version. If the manual change is intentional, update configuration too; if the old value remains desired, review and apply the plan to reconcile.

این همون drift هست: واقعیت از configuration/state جدا شده. اگه در cloud تغییر دستی یک firewall عمدی و اضطراری بوده، کورکورانه apply نکن؛ owner و هدف تغییر رو روشن کن. plan پیشنهاد هست، تصمیم نهایی نیست.

This is drift: reality has diverged from configuration/state. If a manual cloud firewall change was intentional and urgent, do not blindly apply; clarify its owner and purpose. A plan is a proposal, not the final decision.

چرا state رو دارایی مهم حساب می‌کنیم؟Why treat state as an important asset?

state cache ساده نیست؛ آدرس‌هایی مثل local_file.banner رو به object واقعی وصل و metadata لازم برای مقایسه رو نگه می‌داره. بدون mapping ممکن هست Terraform نداند چه چیزی رو ساخته؛ با state اشتباه هم ممکن هست یک object رو دوبار مدیریت کنه. «state مقدس هست» یعنی محافظت و تغییر کنترل‌شده، نه اینکه هرگز تغییر نمی‌کنه.

State is not a simple cache. It maps addresses such as local_file.banner to real objects and stores metadata for comparisons. Without the mapping Terraform may not know what it created; with the wrong state it may manage one object twice. “State is sacred” means protect it and change it deliberately, not that it can never change.

backend پیش‌فرض local هست و state رو در terraform.tfstate می‌نویسه؛ برای lab تک‌نفره ساده هست، اما برای تیم دردسرِ stateهای جدا و رقابت می‌سازه. تیم‌ها remote backend به‌کار می‌برن تا state مشترک باشه و اگه backend پشتیبانی کنه، locking جلوی دو عملیات هم‌زمان رو بگیره.

The default local backend writes terraform.tfstate. It is simple for a solo lab, but separate states and concurrent work make it unsuitable for teams. Teams use a remote backend for shared state and, when supported, locking to prevent concurrent operations.

remote بودن خودبه‌خود امن نیست؛ backend تعیین می‌کنه دسترسی، encryption و locking چطور کار می‌کنه. state می‌تونه secret داشته باشه و plan file هم ممکن هست حساس باشه؛ دسترسی محدود، backup و بازیابی لازم‌اند. حساس‌علامت‌زدن مقدار معمولاً فقط نمایش رو پنهان می‌کنه، نه ذخیره‌اش رو.

Remote does not automatically mean secure; the backend determines access, encryption, and locking. State may contain secrets and plan files may be sensitive, so restrict access and plan backup/recovery. Marking a value sensitive usually redacts display, not storage.

state رو با ویرایشگر دستی اصلاح یا برای شروع دوباره حذف نکن. اگه state گم یا mismatch شد، apply و destroy رو نگه دار؛ پوشه، حساب، workspace و backend رو بررسی کن، backup درست رو پیدا کن و plan رو فقط برای مشاهده بخوان. import و moved ابزارهای تکمیلی‌اند، نه درمان فوری.Do not hand-edit state or delete it to start over. If state is lost or mismatched, stop apply and destroy; verify directory, account, workspace, and backend, locate the correct backup, and use plan for observation only. Import and moved are deliberate extensions, not emergency fixes.

خرابی عمدی، بدون پاک‌کردن چیزی: state از محیط دیگری هستA deliberate incident without deleting anything: state belongs elsewhere

هم‌تیمی به پوشهٔ تازه‌ای رفته و state محیط staging رو نداره. validate ممکن هست موفق باشه، چون فایل‌ها از نظر ساختاری درست‌اند؛ اما آیا apply امن هست؟ اول فقط زمینه رو شناسایی کن:

A teammate moved to a fresh directory and does not have staging state. Validate may pass because the files are structurally sound, but is apply safe? First inspect context only:

PowerShell or Bash · observe, do not apply
terraform workspace show
terraform state list
terraform plan

اگه plan می‌گه resourceهای مهم «to add» هستن، این شاید محیط خالی باشه یا state اشتباه/گم شده باشه. از روی عجله apply نکن. حساب، endpoint، workspace و backend رو طبق runbook مستقل تأیید کن؛ state backup یا مسئول backend رو پیدا کن. state دیگری رو جایگزین نکن و state رو پاک نکن.

If plan says important resources are “to add,” the environment may be empty—or state may be missing/wrong. Do not apply in a hurry. Independently verify account, endpoint, workspace, and backend against the runbook; locate a state backup or backend owner. Do not substitute or delete state.

در آزمایش محلی، به پوشهٔ اصلی برگرد و state list رو دوباره ببین. اگه موضوع cloud هست، عملیات رو متوقف و از مسئول زیرساخت کمک بگیر. هدف، تشخیص از روی نشانه هست؛ نه امتحان‌کردن دستورهای پرخطر.

In the local lab, return to the original directory and inspect state again. For cloud, stop and involve the infrastructure owner. The goal is evidence-based diagnosis, not trying risky commands.

وقتی resource از قبل هستWhen a resource already exists

اگه object بیرون Terraform ساخته شده، تعریف resource و apply ممکن هست duplicate یا conflict بسازد. اول مسئولیت و state رو روشن کن. اگه این state باید مالک object بشه، import یا import block می‌تونه binding رو ثبت کنه؛ بعد configuration و plan رو باید بازبینی کرد. برای تغییر آدرس در refactor، moved block می‌تونه جابه‌جایی رو اعلام کنه. این‌ها ابزار تکمیلی‌اند، نه میان‌بر برای دورزدن plan.

If an object was created outside Terraform, declaring it and applying may create a duplicate or conflict. Clarify ownership and state first. If this state should own it, import can record the binding; configuration and plan still need review. For an address refactor, a moved block can declare the move. These are extensions, not shortcuts around review.

No; only configuration structure is valid. Verify account, access, plan, and service health separately.

۴. شبکهٔ موجود 4. Existing network

شبکه متعلق به تیم دیگری هست؛ فقط ID لازم داری. resource یا منبع داده؟

Another team owns a network; you only need its ID. Resource or data source?

دلیل · Reasoning

منبع داده، چون فقط می‌خوانی و lifecycle شبکه رو مالک نیستی؛ resource برای object تازهٔ تحت مدیریت خودت.

A data source, because you only read an object you do not own; use a resource for something whose lifecycle you manage.

۵. ترتیب ساخت 5. Creation order

resource receipt به attribute از banner ارجاع داره. چطور ترتیب معلوم می‌شه؟

Receipt references a banner attribute. How is order determined?

پاسخ · Answer

ارجاع وابستگی graph خودکار می‌سازه. depends_on فقط برای وابستگی پنهان لازمه.

The reference creates an implicit graph dependency. Use depends_on only for hidden dependencies.

۶. provider requirement عوض شد 6. Provider requirement changed

کدام فرمان افزونه و lock رو آماده می‌کنه؟

Which command prepares the plugin and lock file?

پاسخ · Answer

init. بعد lock file diff رو ببین؛ validate به‌تنهایی provider تازه رو نصب نمی‌کنه.

init. Review the lock-file diff; validate does not install the new provider.

۷. destroy غیرمنتظره 7. Unexpected destroy

تغییر کوچکی دادی ولی plan یک firewall rule رو حذف می‌کنه. قدم امن؟

A small edit makes plan destroy a firewall rule. Safe next step?

تصمیم · Decision

apply رو متوقف کن؛ provider، address، state و diff کامل رو بررسی و با owner تأیید کن. علامت حذف رو نادیده نگیر.

Stop apply; inspect provider, address, state, and full diff with the owner. Do not ignore destruction.

۸. state list 8. State list

دو address دیدی. آیا محتوا درست هست؟

Two addresses appear. Is the content correct?

توضیح · Explanation

نه؛ list فقط addressها رو نشون می‌ده. state show و provider plan و خواندن فایل، مدرک‌های جدا هستن.

No; list shows addresses. State show, provider plan, and reading the file are different evidence.

۹. تغییر دستی عمدی 9. Intentional manual change

plan مقدار قبلی رو برمی‌گرداند، ولی مقدار تازه رو می‌خوایم. چه باید کرد؟

Plan restores the old value, but the new one is desired. What now?

پاسخ · Answer

منبع حقیقت رو روشن و configuration/variable رو به مقدار مطلوب تغییر بده؛ بعد plan تازه بگیر.

Clarify the source of truth, update configuration/variable to the desired value, then create a fresh plan.

۱۰. state در Git؟ 10. State in Git?

همکار می‌خواد tfstate رو commit کنه. چرا نه؟

A teammate wants to commit tfstate. Why not?

پاسخ · Answer

ممکن هست secret داشته باشه و Git کنترل دسترسی/locking مناسب state نیست. backend امن و مشترک با ویژگی‌های تأییدشده انتخاب کن.

It may contain secrets, and Git is not a suitable state backend with locking. Choose a secure shared backend with verified features.

۱۱. sensitive 11. Sensitive values

نمایش plan مخفی هست؛ آیا مقدار از state حذف شده؟

Plan output is redacted; is the value removed from state?

توضیح · Explanation

نه لزوماً؛ sensitive نمایش رو پنهان می‌کنه، اما state و plan رو همچنان محرمانه نگه دار.

Not necessarily. Sensitive redacts display; still protect state and plan files.

۱۲. سه state محلی 12. Three local states

سه نفر هرکدام local apply می‌زنن؛ خطر چیست؟

Three people each apply with local state. Risk?

تحلیل · Analysis

mapping جدا باعث duplicate یا تغییر متناقض می‌شه. backend مشترک و locking پشتیبانی‌شده لازمه.

Separate mappings can create duplicates or conflicting changes. Use shared backend and supported locking.

۱۳. lock مانده 13. A lock remains

آیا -lock=false راه‌حل پیش‌فرض هست؟

Is -lock=false the default fix?

تصمیم · Decision

نه؛ اول run فعال رو بررسی کن. force-unlock فقط با lock ID و اطمینان از نبود writer انجام بشه.

No. Check for an active run first. Force-unlock only with the lock ID and confirmation no writer is active.

۱۴. plan صبحگاهی 14. Morning plan

ظهر زیرساخت دستی تغییر کرد؛ apply فایل plan قدیمی؟

Infrastructure changed manually at noon. Apply the morning plan?

پاسخ · Answer

نه؛ دوباره مشاهده و plan تازه بساز و تغییر رو با owner بررسی کن.

No. Refresh observations, create a new plan, and review the change with its owner.

۱۵. DNS از قبل هست 15. DNS record already exists

plan ساخت duplicate می‌ده؛ چه کار می‌کنی؟

Plan proposes a duplicate. What do you do?

گام امن · Safe step

حساب و state رو تأیید کن؛ اگه مالکیت این state هست import رو بررسی کن، وگرنه منبع داده. duplicate apply نکن.

Verify account and state. If this state should own it, investigate import; otherwise use a data source. Do not apply a duplicate.

۱۶. label عوض شد 16. A resource label changed

فقط اسم address عوض شده ولی plan destroy/create می‌ده؛ چه چیزی رو بررسی می‌کنی؟

Only the address name changed, but plan shows destroy/create. What do you inspect?

پاسخ · Answer

moved block یا جابه‌جایی کنترل‌شدهٔ state؛ قبل از apply backup و plan رو بررسی کن.

A moved block or controlled state move may preserve the object. Review backup and plan before applying.

۱۷. incident روی firewall 17. Firewall incident

plan تغییر دستی تیم شبکه رو overwrite می‌کنه. چه مدرکی جمع می‌کنی؟

Plan would overwrite a network team’s manual change. What evidence do you gather?

گزارش حادثه · Incident response

حساب/workspace/backend، آدرس و diff rule، زمان تغییر و مالک اون رو ثبت می‌کنم؛ تا روشن‌شدن هدف، apply نمی‌کنم و بعد plan تازه می‌گیرم.

Record account/workspace/backend, address and rule diff, change time, and owner. Do not apply until intent is clear; then create a fresh plan.

۱۸. پاک‌سازی lab 18. Lab cleanup

چطور ثابت می‌کنی destroy فقط فایل‌های آزمایش رو حذف می‌کنه؟

How do you prove destroy removes only lab files?

پاسخ · Answer

مسیر و workspace رو ببین، plan -destroy رو بخوان و فقط دو local_file رو تأیید کن. موارد ناآشنا یعنی توقف.

Check directory and workspace; inspect plan -destroy and confirm only the two local_file resources. Stop if anything is unfamiliar.

این lab تمام هست؛ چرخهٔ فکری تازه شروع شدهThe lab ends; the reasoning cycle is yours to keep

قبل از cleanup، فایل‌ها و state رو مشاهده کن. بعد فقط از پوشهٔ مشخص lab، terraform plan -destroy بگیر؛ اگه فقط دو resource از نوع local_file برای فایل‌های generated دیده می‌شن، terraform destroy رو تأیید کن و نبود فایل‌ها و addressهای local_file.* رو بررسی کن. منبع داده ممکن هست تا وقتی در configuration هست در فهرست state دیده بشه؛ اون رو با resource قابل‌حذف اشتباه نگیر. اگه resource دیگری دیدی، اجرا نکن. برای پایان، پوشهٔ موقت رو با مسیر روشن از File Explorer پاک کن.

Before cleanup, inspect files and state. From the known lab directory run terraform plan -destroy; approve terraform destroy only if it lists the two local_file resources for generated files, then verify file absence and that no local_file.* resource addresses remain. The data source may remain listed while it is still configured; do not confuse it with a managed resource to destroy. Stop if another resource appears. Finally remove the temporary directory from File Explorer using its known path.

حالا وقتی کسی می‌گه «زیرساخت تغییر کرده»، به‌جای حدس می‌تونی بپرسی: کدام حساب و workspace؟ state کدام هست؟ plan چه actionی پیشنهاد می‌ده؟ چه کسی مالک resource هست؟ و بعد از تغییر، دقیقاً با چه مدرکی verify می‌کنیم؟

When someone says “the infrastructure changed,” you can now ask: which account and workspace? Which state? What action does the plan propose? Who owns the resource? What evidence will verify the result?
