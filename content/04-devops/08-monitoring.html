سرویس برای کاربر سالم است؟Is the service healthy for users?

دیروز deploy انجام شد و تیم گفت «همه‌چیز سبز است». امروز پشتیبانی می‌گوید صفحه دیر باز می‌شود و بعضی درخواست‌ها خطای ۵۰۰ می‌گیرند. سرور هنوز جواب می‌دهد و فرایند هم نمرده. پس این سبزی دقیقاً چه چیزی را ثابت می‌کند؟

Yesterday’s deployment was declared green. Today support says pages are slow and some requests return 500. The server still responds and the process is alive. So what, exactly, did that green indicator prove?

فصل قبل یاد گرفتیم میزبان‌ها را به وضعیت مطلوب برسانیم. اما یک عکس از وضعیت همین لحظه نمی‌گوید مشکل از چه زمانی شروع شد، نرخ خطا بالا می‌رود یا latency آرام‌آرام بدتر شده. برای دیدن روند، از برنامه چند مشاهدهٔ عددیِ زمان‌دار می‌خواهیم: متریک.

Last chapter brought hosts toward a desired state. A snapshot cannot tell us when trouble began, whether errors are rising, or whether latency is gradually worsening. To see a trend, we need time-stamped numeric observations from the program: metrics.

فعلاً قرار نیست «داشبورد بسازیم چون Grafana داریم». اول می‌پرسیم کاربر چه تجربه‌ای دارد: چند درخواست موفق‌اند؟ خطاها چه سهمی دارند؟ پاسخ معمولاً چقدر طول می‌کشد؟ ابزار فقط وقتی ارزش دارد که به این پرسش‌ها جواب بدهد.

We are not building a dashboard just because Grafana is available. First ask what users experience: how many requests succeed, what share fail, and how long responses take. Tools matter only when they help answer those questions.

چه کسی داده را می‌گیرد؟Who collects the data?

برنامه metric endpoint کوچکی می‌دهد؛ Prometheus هر چند ثانیه به آن سر می‌زند و نمونه‌ها را همراه زمان و برچسب‌ها ذخیره می‌کند. این مدل pull یا scrape است. exporter هم برنامه‌ای جداست که وضعیت چیزی مثل سیستم‌عامل یا پایگاه داده را به قالب متریک تبدیل می‌کند. برای اپ خودمان مستقیم instrumentation می‌گذاریم و exporter جدا لازم نیست.

The app exposes a small metrics endpoint. Prometheus visits it periodically and stores samples with timestamps and labels: a pull model called scraping. An exporter is a separate program that translates something like operating-system or database state into metrics. We instrument our own app directly, so no separate exporter is needed.

برنامه داده را عرضه می‌کند؛ Prometheus می‌کشد؛ PromQL آن را به پرسش تبدیل می‌کند؛ Grafana نتیجه را نمایش می‌دهد. فلش‌ها مسیر داده‌اند، نه تضمین سلامت کاربر.

The app exposes data; Prometheus pulls it; PromQL turns it into a query; Grafana displays the result. Arrows show data flow, not a guarantee of user health.

متریک معمولاً نام دارد، عدد دارد و می‌تواند label داشته باشد؛ مثلاً http_requests_total{method="GET",status="500"}. ترکیب نام متریک و همهٔ مقدارهای label یک time series جدا می‌سازد. بنابراین labelی مثل شناسهٔ کاربر یا URL خام می‌تواند میلیون‌ها سری بسازد و حافظه و دیسک Prometheus را بی‌دلیل مصرف کند. برای دسته‌بندی از مقدارهای محدود مثل routeهای شناخته‌شده استفاده کن.

A metric has a name and value, and may have labels—for example http_requests_total{method="GET",status="500"}. Each distinct metric-name/label-value combination creates a time series. A user ID or raw URL label can create millions of series and waste Prometheus memory and disk. Prefer bounded categories such as known routes.

Exporter هم جادو نمی‌کند: مثلاً node exporter می‌تواند دادهٔ میزبان را عرضه کند، اما از سبز بودن target نمی‌فهمیم صفحهٔ خرید برای کاربر درست کار می‌کند. متریک را نزدیک همان چیزی انتخاب کن که می‌خواهی درباره‌اش تصمیم بگیری.

An exporter is not magic: node exporter can expose host data, but an up target cannot tell us whether a user’s checkout works. Choose metrics close to the thing you need to make decisions about.

آزمایشگاه: سه سرویس و یک سؤالLab: three services, one question

پوشهٔ تازه‌ای به نام monitoring-lab بساز. یک app کوچک روی 8000 پاسخ می‌دهد و endpoint متریکش روی 8001 است. Prometheus فقط به پورت داخلی app وصل می‌شود؛ Grafana هم Prometheus را با نام سرویس Compose پیدا می‌کند. پورت‌ها فقط روی loopback میزبان منتشر می‌شوند، پس این نمونه را production deployment فرض نکن.

Create a fresh monitoring-lab directory. A tiny app serves HTTP on 8000 and metrics on 8001. Prometheus reaches the app’s internal metrics port; Grafana finds Prometheus by its Compose service name. Host ports bind to loopback, so this is not a production deployment.

۱. برنامهٔ قابل مشاهده1. An observable app

این برنامه برای هر درخواست چند route محدود ثبت می‌کند؛ query string و شناسهٔ دلخواه را label نمی‌کند. /slow برای دیدن latency کمی مکث دارد و /fail برای ساخت خطای قابل مشاهده است. /health صرفاً پاسخ زنده می‌دهد.

This app records requests using a small fixed set of route labels; it does not label by arbitrary query string or ID. /slow pauses to make latency visible, and /fail generates an observable error. /health is a simple liveness response.

app.py
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from time import perf_counter, sleep
from threading import Thread
from prometheus_client import Counter, Histogram, start_http_server

REQUESTS = Counter("http_requests_total", "Completed HTTP requests", ["route", "status"])
DURATION = Histogram("http_request_duration_seconds", "HTTP request duration", ["route"])

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        route = self.path.split("?", 1)[0]
        route = route if route in ("/", "/slow", "/fail", "/health") else "/other"
        if route == "/health":
            self.send_response(200); self.end_headers(); self.wfile.write(b"ok\n"); return
        started = perf_counter()
        status = 500 if route == "/fail" else 200
        try:
            if route == "/slow": sleep(0.35)
            self.send_response(status); self.end_headers()
            self.wfile.write(b"simulated failure\n" if status == 500 else b"hello from the lab\n")
        finally:
            DURATION.labels(route).observe(perf_counter() - started)
            REQUESTS.labels(route, str(status)).inc()

    def log_message(self, fmt, *args):
        print("http", self.address_string(), fmt % args, flush=True)

Thread(target=lambda: start_http_server(8001), daemon=True).start()
print("app listening on :8000; metrics on :8001", flush=True)
ThreadingHTTPServer(("0.0.0.0", 8000), Handler).serve_forever()

برنامه با prometheus-client نصب می‌شود. نسخه را برای تکرارپذیری pin کرده‌ایم؛ اگر مخزن بسته‌ات به اینترنت دسترسی ندارد، وابستگی را از قبل cache کن.

The app uses prometheus-client. We pin it for reproducibility; if your package mirror is offline, cache the dependency first.

scrape_interval را برای آزمایش ۵ ثانیه می‌گذاریم تا سریع نمودار ببینیم؛ در سامانهٔ واقعی مقدار را با نیاز، هزینه و بار endpoint تنظیم کن. نشانی target نام سرویس Compose است، نه localhost؛ داخل container، localhost به همان container اشاره می‌کند.

For this lab, a five-second scrape_interval makes graphs appear quickly. In a real system, choose it based on freshness needs, cost, and endpoint load. The target is the Compose service name, not localhost; inside a container, localhost means that same container.

۳. Compose و data source آماده3. Compose and a provisioned data source

Prometheus و Grafana روی شبکهٔ پیش‌فرض Compose هستند. volumeهای named دادهٔ هر دو را نگه می‌دارند؛ برای آزمایش ساده لازم نیست چیزی را پاک کنی. Grafana از فایل provisioning آدرس Prometheus را می‌گیرد؛ مرورگر کاربر قرار نیست به hostname داخلی Docker وصل شود، خود Grafana است که query می‌زند.

Prometheus and Grafana share Compose’s default network. Named volumes retain both services’ data, so there is no need to wipe anything during the lab. Grafana reads the Prometheus URL from provisioning; the browser does not need to resolve Docker’s internal hostname—Grafana itself queries Prometheus.

سبزشدن target چه چیزی را ثابت می‌کند؟What does a green target actually prove?

در Prometheus به http://localhost:9090/targets برو. برای job به نام codenames-web باید target برابر web:8001 و state برابر UP باشد. Prometheus توانسته endpoint متریک را scrape و parse کند. این به‌تنهایی نمی‌گوید endpoint اصلی کاربر خوب است، همهٔ routeها پاسخ می‌دهند یا latency قابل قبول است.

Open http://localhost:9090/targets. The codenames-web job should show target web:8001 as UP. Prometheus could scrape and parse the metrics endpoint. That does not prove the user-facing endpoint works, every route responds, or latency is acceptable.

اگر target DOWN است، به جای حدس‌زدن password یا restart، ستون Last scrape error را بخوان. نام سرویس، port داخلی، metrics_path و log سرویس را بررسی کن. depends_on ترتیب شروع را تعیین می‌کند، نه اینکه Prometheus تا آماده‌شدن app حتماً منتظر بماند؛ scrapeهای بعدی retry می‌کنند.

If the target is DOWN, read the Last scrape error instead of guessing passwords or restarting. Check the service name, internal port, metrics_path, and service logs. depends_on orders startup; it does not guarantee Prometheus waits for the app to be ready. Later scrapes retry.

از counter به نرخ برسیمTurn a counter into a rate

یک درخواست بفرست تا counter تغییر کند و endpoint متریک را هم ببین:

Send a request to change the counter, then inspect the metrics endpoint:

generate one successful and one failed request
curl -i http://localhost:8080/
curl -i http://localhost:8080/fail
curl -s http://localhost:8080/metrics | Select-String "http_requests_total"

در Bash به‌جای خط آخر می‌توانی از grep http_requests_total استفاده کنی. در خروجی مقدارهای route و status را می‌بینی؛ exporter متریک خام می‌دهد، نه پاسخ آمادهٔ «در دقیقه چند درخواست داریم؟».

In Bash, use grep http_requests_total instead of the final command. You should see route and status label values. The exporter gives raw metrics, not a ready-made answer to “how many requests per minute?”

در Prometheus بخش Graph، این query را اجرا کن:

In Prometheus’s Graph page, run this query:

PromQL · requests per second
sum(rate(http_requests_total[1m]))

rate تغییرات counter را در پنجرهٔ یک‌دقیقه‌ای به نرخ بر ثانیه تبدیل می‌کند؛ sum سری‌های route و status را جمع می‌زند. با scrape هر ۵ ثانیه، برای یک برآورد باثبات چند نمونه لازم است؛ پس نمودار بلافاصله معجزه نمی‌کند. اگر counter را مستقیم رسم کنیم، گراف شمارندهٔ تجمعی را نشان می‌دهد، نه بار فعلی. این اولین دام عمدی ماست: قبل از اصلاح، raw counter را رسم کن و توضیح بده چرا بالا ماندنش به معنی ادامهٔ همان نرخ نیست.

rate converts counter change over a one-minute window into a per-second rate; sum adds the route/status series. With five-second scrapes, a stable estimate needs multiple samples, so the graph is not instant magic. A raw counter graph shows a cumulative total, not current load. Here is our first deliberate trap: graph the raw counter before fixing it, and explain why its rising line does not mean the same request rate continues.

Grafana · login at localhost:3000, then Explore
sum(rate(http_requests_total{status="500"}[1m]))
histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

query اول نرخ خطای ۵۰۰ را می‌دهد. دومی p95 تقریبی latency را از bucketهای histogram حساب می‌کند. چون برای سادگی label وضعیت را به query دوم اضافه نکردیم، latency همهٔ routeهای ثبت‌شده در آن پنجره با هم است. histogram_quantile تخمین روی bucket است، نه صدک دقیق تک‌تک درخواست‌ها؛ bucketهای نامناسب هم نتیجه را کم‌فایده می‌کنند.

The first query gives the 500 response rate. The second estimates p95 latency from histogram buckets. Because we did not filter status in the second query, it combines all recorded routes in the window. histogram_quantile estimates from buckets; it is not an exact percentile over individual requests, and poor bucket boundaries make it less useful.

در Grafana Explore data source را Prometheus بگذار، query اول را اجرا و نمودار را به dashboard تازه اضافه کن. دو panel دیگر برای ۵xx و p95 بساز. عنوانی مثل «نرخ درخواست موفق/ثانیه» از اسم خام metric کمک‌کننده‌تر است؛ واحد، بازهٔ زمانی و این‌که نمودار برای چه تصمیمی است را هم معلوم کن.

In Grafana Explore, select the Prometheus data source, run the first query, and add its graph to a new dashboard. Add panels for 5xx rate and p95. A title like “Successful request rate / second” is more useful than a raw metric name; make the unit, time range, and intended decision clear too.

خرابی عمدی: خط رو به بالا همیشه خبر بد نیستDeliberate fault: an upward line is not always bad news

چند بار / و /fail را صدا بزن و raw http_requests_total را در پنل رسم کن. حالا درخواست‌ها را متوقف کن. خط چه می‌کند؟ مقدار counter روی عدد آخر می‌ماند؛ اگر به‌تنهایی ببینی، ممکن است فکر کنی نرخ هنوز بالاست. داده خراب نیست؛ سؤال نمودار اشتباه انتخاب شده.

Call / and /fail a few times and graph raw http_requests_total. Now stop sending requests. What happens? The counter stays at its last value; alone, it can look like the rate is still high. The data is not broken—the graph asks the wrong question.

قبل از تعمیر، پنجرهٔ زمانی و نوع متریک را با هم تطبیق بده: counter تجمعی است؛ نرخ را با rate(...[1m]) حساب کن. بعد از تغییر query، همان بازه را دوباره ببین و با ارسال چند درخواست جدید مطمئن شو نرخ بالا می‌رود و پس از توقف به نزدیک صفر برمی‌گردد. دادهٔ تاریخی پاک نمی‌شود، اما تفسیر درست می‌شود.

Before fixing it, match the metric type to the question: a counter is cumulative; calculate a rate with rate(...[1m]). Recheck the same time range, then send a few more requests and verify the rate rises and returns near zero when traffic stops. History is not erased; the interpretation is corrected.

اگر label متغیری مثل user_id یا مسیر خام درخواست اضافه کرده‌ای، آن را در app حذف و labelهای محدود مثل route="/slow" ثبت کن. فیلترکردن در Grafana cardinality را کم نمی‌کند؛ تعداد سری‌ها از instrumentation و relabeling می‌آید.If you added a variable label such as user_id or a raw request path, remove it in the app and use bounded labels such as route="/slow". Filtering in Grafana does not reduce cardinality; series are created by instrumentation and relabeling.

یک خرابی دیگر را هم تجربه کن: در prometheus.yml پورت target را موقتاً از 8001 به 9999 تغییر بده و سرویس را بازسازی/راه‌اندازی کن. در Targets باید DOWN و خطای اتصال ببینی؛ app هنوز ممکن است سالم باشد. پورت را برگردان، Prometheus را دوباره اجرا کن و تا UP شدن همان target صبر کن. این تفاوت «متریک نمی‌رسد» با «برنامه مرده» است.

Try one more fault: temporarily change the target port in prometheus.yml from 8001 to 9999, then restart the service. Targets should show DOWN and a connection error while the app may remain healthy. Restore the port, restart Prometheus, and wait for that same target to return to UP. “Metrics are unreachable” is not the same as “the app is dead.”

inspect before repair; restart only the changed service
docker compose logs --tail=30 prometheus
docker compose ps
docker compose restart prometheus

log می‌تواند خطای parse config را هم نشان بدهد. اگر فقط فایل config را mount کرده‌ای، restart ساده کافی است؛ اگر مسیر یا mount غلط است اول همان را درست کن. بعد از repair، موفقیت را در Targets و با query دوباره ثابت کن، نه با سبز دیدن صفحهٔ اصلی Prometheus.

Logs may also show a configuration parse error. If the config is mounted as shown, a restart is enough; if the path or mount is wrong, fix that first. After repair, verify in Targets and rerun the query—not by merely seeing Prometheus’s home page load.

از نمودار به پرسش عملیاتیFrom a graph to an operational question

برای یک سرویس وب، RED یک یادآور ساده است: Rate چند درخواست می‌آید، Errors چه تعداد/نسبتی شکست می‌خورند، Duration پاسخ چقدر طول می‌کشد. USE بیشتر برای منابع است: Utilization میزان استفاده، Saturation صف یا فشارِ منتظر، و Errors خطای منبع. این‌ها قانون کامل طراحی نیستند؛ راهی برای جا نینداختن پرسش‌های پایه‌اند.

For a web service, RED is a useful prompt: Rate of requests, Errors in count or ratio, and Duration of responses. USE is more resource-oriented: Utilization, Saturation such as queued work, and Errors in the resource. These are not a complete design law; they help us remember basic questions.

یک داشبورد، یک بازبینی انسانیOne dashboard, one human review

در dashboard سه panel را کنار هم بچین: نرخ کل، نرخ ۵xx و p95 latency؛ time range را مثلاً روی ۱۵ دقیقه تنظیم کن و عنوان/واحد هر panel را روشن بنویس. بعد /fail و /slow را فراخوانی کن و ببین کدام پنل تغییر می‌کند. اگر نمی‌توانی از روی نمودار بگویی چه رخ داده، عنوان، query یا metric را اصلاح کن؛ تعداد panelها هدف نیست.

Place three panels together: total request rate, 5xx rate, and p95 latency. Set a time range such as 15 minutes and give each panel a clear title and unit. Then call /fail and /slow and observe which panel moves. If the graph does not help explain what happened, improve its title, query, or metric—the number of panels is not the goal.

هشدار هم باید به یک اقدام برسد. پیش‌نمایش ذهنی: اگر نرخ ۵xx برای چند دقیقه از حد مورد توافق بالاتر ماند، صفحهٔ on-call را خبر کن؛ یک spike لحظه‌ای را شاید فقط ثبت کنیم. شرط زمانی جلوی واکنش به تک‌نمونه را می‌گیرد، اما آستانه باید با SLO و رفتار واقعی سرویس تعیین شود. راه‌اندازی Alertmanager و طراحی شیفت هشدار درس فصل‌های بعد است.

An alert should lead to an action. As a preview: if the 5xx rate stays above an agreed threshold for several minutes, notify on-call; a momentary spike may only be recorded. A pending duration avoids reacting to one sample, but thresholds must come from the service’s SLO and real behavior. Alertmanager and on-call design belong to later chapters.

۱۸ تمرین؛ از خواندن target تا طراحی پنل18 exercises—from targets to dashboard design

هر تمرین را اول خودت جواب بده، بعد پاسخ را باز کن. بعضی سؤال‌ها عمداً می‌پرسند چه چیزی هنوز ثابت نشده.

۱. سبزِ کدام بخش؟1. Which green indicator?

Prometheus target برابر UP است. آیا کاربر می‌تواند حتماً خرید کند؟

The Prometheus target is UP. Can users definitely check out?

توضیح · Reasoning

نه؛ فقط scrape موفق endpoint متریک ثابت شده. مسیر خرید باید جدا با آزمون کاربرمحور بررسی شود.

No. Only a successful scrape of the metrics endpoint is proven. Test the checkout path separately.

۲. localhost داخل Grafana2. localhost inside Grafana

Data source روی http://localhost:9090 است و خطای connection می‌دهد؛ Prometheus روی Compose است. آدرس درست چیست؟

The data source uses http://localhost:9090 and fails, while Prometheus is in Compose. What address should it use?

راه تشخیص · Diagnosis

http://prometheus:9090؛ نام service روی شبکهٔ Compose resolve می‌شود. localhost داخل container خود Grafana است.

http://prometheus:9090; the Compose service name resolves on the network. localhost is Grafana’s own container.

۳. Counter یا Gauge؟3. Counter or gauge?

تعداد connectionهای همین لحظه بالا و پایین می‌رود؛ کدام نوع مناسب‌تر است؟

The number of current connections rises and falls. Which metric type fits?

پاسخ · Answer

Gauge؛ مقدار جاری می‌تواند کم یا زیاد شود.

A gauge; the current value can move in either direction.

۴. پاسخ‌های پردازش‌شده4. Processed requests

مجموع درخواست‌هایی که از شروع process پاسخ داده‌ای؛ نوع metric؟

Total requests served since the process started: which metric type?

دلیل · Reasoning

Counter؛ با restart ممکن است reset شود و Prometheus برای محاسبهٔ نرخ reset را در rate لحاظ می‌کند.

A counter. It can reset on restart, and Prometheus accounts for resets when calculating rate.

۵. p95 از کجا می‌آید؟5. Where does p95 come from?

چرا histogram برای latency مفید است؟

Why is a histogram useful for latency?

توضیح · Reasoning

مشاهده‌ها را در bucketها می‌شمارد و از روی آن‌ها می‌توان سمت Prometheus صدک را تخمین زد؛ bucketها و تعداد مشاهده‌ها مهم‌اند.

It counts observations in buckets so Prometheus can estimate a quantile. Bucket boundaries and sample count matter.

۶. مسیر target اشتباه6. Wrong target port

Target برابر DOWN است و خطا connection refused به web:9999 می‌گوید؛ کدام دو مورد را اول بررسی می‌کنی؟

A target is DOWN with connection refused to web:9999. What two things do you check first?

گام بعد · Next

پورت listener واقعی metrics (اینجا 8001) و آدرس/پورت target در config؛ بعد log و restart همان Prometheus.

The actual metrics listener port (8001 here) and the configured target; then Prometheus logs and restart that service.

۷. درخواست در ثانیه7. Requests per second

برای نرخ کل درخواست‌ها کدام query؟

Which query gives total request rate?

پاسخ · Answer

sum(rate(http_requests_total[1m]))؛ پنجره را متناسب با scrape interval و نیاز تغییر بده.

sum(rate(http_requests_total[1m])); choose the window based on scrape interval and freshness needs.

۸. پرش ناگهانی counter8. Counter jumps

Counter از ۴۰ به ۰ برگشته و بعد رشد می‌کند. آیا حتماً داده خراب است؟

A counter fell from 40 to 0 and then rose. Is the data necessarily corrupt?

تفسیر · Interpretation

نه؛ احتمال restart process است. زمان restart/log را بررسی و روی counter از rate استفاده کن.

No; the process may have restarted. Check restart time/logs and use rate for a counter.

۹. Label پرهزینه9. Costly label

توسعه‌دهنده user_id را label کرده. خطر چیست؟

A developer added user_id as a label. What is the risk?

دلیل · Reasoning

هر user مقدار seriesهای جدا می‌سازد و cardinality/storage بالا می‌رود. شناسه را از metric label حذف کن؛ آن را به ابزار مناسب دیگری بسپار.

Each user creates distinct series, increasing cardinality and storage. Remove the ID from metric labels; use an appropriate other tool for it.

۱۰. URL خام به‌عنوان label10. Raw URL label

چطور endpointها را بدون label انفجاری دسته‌بندی می‌کنی؟

How can routes be grouped without a high-cardinality label?

راه مناسب · Safer model

route template یا دستهٔ محدود مثل /users/:id، نه path واقعی شامل ID.

Use a route template or bounded category such as /users/:id, not the actual ID-bearing path.

۱۱. نرخ ۵۰۰11. 500 response rate

یک query برای نرخ پاسخ‌های ۵۰۰ بنویس.

Write a query for the rate of 500 responses.

پاسخ · Answer

sum(rate(http_requests_total{status="500"}[1m])).

۱۲. نمودار raw counter12. Raw counter graph

ترافیک قطع شده اما نمودار raw counter افقی و بالا مانده؛ چه نتیجه‌ای می‌گیری؟

Traffic stopped, but the raw counter line remains high and flat. What do you conclude?

تفسیر · Interpretation

counter مجموع تاریخی است. برای بار جاری rate را رسم کن؛ افقی‌ماندن counter طبیعی است.

A counter is a historical total. Plot rate for current load; a flat counter is normal.

۱۳. واحد latency13. Latency unit

متریک duration بر حسب seconds است؛ پنل را چطور قابل خواندن می‌کنی؟

Duration is measured in seconds. How do you make the panel readable?

طراحی · Design

واحد panel را seconds یا milliseconds روشن کن و اگر به ms تبدیل می‌کنی این تبدیل را در query/عنوان صریح نشان بده.

Set the panel unit to seconds or milliseconds and make any conversion to ms explicit in the query/title.

۱۴. نمودار خالی14. Empty graph

Query خطا نمی‌دهد ولی داده ندارد. سه بررسی اول؟

A query has no error but returns no data. What are your first three checks?

عیب‌یابی · Diagnosis

Targets و scrape success، وجود نام metric/label در endpoint، و range/پنجرهٔ زمانی با تعداد sample کافی.

Target/scrape success, metric and labels in the endpoint, and a time range/window with enough samples.

۱۵. p95 نوسانی15. Noisy p95

در ساعت کم‌ترافیک p95 هر چند دقیقه از ۰ به ۳ ثانیه می‌پرد؛ آیا الزاماً برنامه بدتر شده؟

At low traffic, p95 jumps between zero and three seconds. Did the app necessarily get worse?

احتیاط · Caution

نه؛ نمونه کم، پنجره و bucketها را بررسی کن و کنار صدک، تعداد درخواست و تجربهٔ واقعی را ببین.

Not necessarily. Check sample count, window, and buckets; interpret the quantile alongside request volume and user experience.

۱۶. RED یا USE؟16. RED or USE?

برای API latency و برای CPU میزبان دنبال چه چارچوب پرسشی می‌روی؟

Which question set helps with API latency, and which with host CPU?

توضیح · Reasoning

RED برای rate/error/duration سرویس؛ USE برای utilization/saturation/errors منبع.

RED for service rate/errors/duration; USE for resource utilization/saturation/errors.

۱۷. هشدار یا نمودار؟17. Alert or dashboard?

۵xx برای چند ثانیه یک‌بار بالا رفت. پیش از alert فوری چه تصمیمی لازم است؟

5xx rose briefly for a few seconds. What decision comes before an immediate alert?

طراحی هشدار · Alert design

شدت، پنجرهٔ پایداری، آستانهٔ مبتنی بر SLO و اقدامِ دریافت‌کننده را تعیین کن؛ یک spike لزوماً page نیست.

Define severity, pending duration, an SLO-based threshold, and the recipient’s action; a spike is not automatically a page.

۱۸. target سبز، پاسخ خراب18. Green target, broken response

Target UP است، اما curl به / پاسخ نمی‌گیرد. گزارش incident را با چه دو بررسی ادامه می‌دهی؟

The target is UP, but curl to / fails. What two checks continue the incident?

گام بعد · Next

سلامت و log برنامه و مسیر/پورت درخواست کاربر را جدا بررسی کن؛ target فقط metrics endpoint را تأیید کرده است.

Check app health/logs and the user-facing request path/port separately; the target only verified the metrics endpoint.

ماموریت کوتاه: آیا deploy وضع را بدتر کرد؟Mini-mission: did the deployment make things worse?

همکارت می‌گوید بعد از deploy نرخ درخواست خوب است، ولی کاربران از کندی شکایت دارند. روی همین آزمایشگاه چند درخواست /slow و /fail بساز؛ سه panel را طوری بچین که نرخ، سهم خطا و p95 را کنار هم ببینی. در یک یادداشت کوتاه بگو کدام سیگنال تغییر کرد، چه چیزی را هنوز نمی‌دانی، و برای تأیید از چه آزمون مستقلی استفاده می‌کنی.

A teammate says request volume looks normal after a deployment, but users report slowness. Generate requests to /slow and /fail in this lab. Arrange three panels for rate, errors, and p95. Write which signal changed, what remains unknown, and which independent check would confirm it.

راهنمایی مرحله‌ایProgressive hint

اول target را از نظر scrape بررسی کن؛ بعد queryها را با route/status محدود کن؛ در آخر endpoint کاربر را با curl بزن. داشبورد مدرک روند است، نه جای آزمون درخواست.

First verify scraping; then narrow queries by route/status; finally call the user-facing endpoint with curl. A dashboard is trend evidence, not a replacement for a request test.

نمونهٔ جمع‌بندیExample review

«Target UP است؛ پس مسیر scrape سالم است. نرخ ۵۰۰ پس از /fail بالا رفت و p95 بعد از /slow افزایش داشت. این شبیه‌سازی فقط رفتار همین endpointها را نشان می‌دهد؛ برای deploy واقعی باید درخواست کاربرمحور، log برنامه و بازهٔ پیش/پس deploy را هم مقایسه کنیم.» بعد dashboard را ذخیره کن و یک بار دیگر /health و root را با curl تأیید کن.

“The target is UP, so scraping works. The 500 rate rose after /fail, and p95 rose after /slow. This simulation shows only these endpoints; for a real deployment, compare a user-level request, app logs, and pre/post-deploy windows.” Save the dashboard, then verify /health and the root endpoint once more with curl.

برای پاک‌سازی، اول مدرک‌ها را نگه دار؛ سپس stack را پایین بیاور. volumeها جدا می‌مانند و این عمدی است: دادهٔ metrics و dashboard با توقف container پاک نمی‌شود. فقط اگر واقعاً آزمایشگاه دورریختنی و backup لازم نیست، volumeهای همین پروژه را پاک کن.

Keep your evidence first, then stop the stack. Volumes remain, intentionally: stopping containers does not erase metrics or dashboards. Only if this lab is disposable and you need no backup should you remove this project’s volumes.
