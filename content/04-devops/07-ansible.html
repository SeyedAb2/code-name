دو تا سرور داریم که باید Nginx یکسانی داشته باشن. یکی تازه نصب شده، اون یکی چند بار دستی دستکاری شده. هر بار هم یکی با SSH می‌ره داخل و چندتا دستور رو از روی یه فایل متنی اجرا می‌کنه. اگه همین کار رو ده بار تکرار کنیم، سرورها واقعاً به یک وضعیت می‌رسن یا تغییرها کم‌کم روی هم تلنبار می‌شن؟

Two servers need the same Nginx setup. One is fresh, the other was changed by hand; someone SSHes in and repeats commands from notes. If we do it again, will they converge—or will changes pile up?

همون تغییر، همون نتیجه؟Same change, same result?

فصل قبل Terraform رو دیدیم: وضعیت مطلوب زیرساخت رو تعریف می‌کنه و state رو به objectها وصل می‌کنه. اینجا دو میزبان از قبل داریم و می‌خوایم تنظیماتشان همسان بمونه. Ansible از control node با SSH به managed nodeها وصل می‌شه و با moduleها کار می‌کنه.

Last chapter introduced Terraform: declare desired infrastructure and map it to objects through state. Here two hosts already exist and need consistent configuration. Ansible connects from a control node to managed nodes over SSH and uses modules to manage them.

سؤال مهم اینه: اگه مقصد از قبل درست باشه، اجرای بعدی چه چیزی رو عوض می‌کنه؟ بیشتر moduleهای استاندارد وضعیت رو می‌سنجن و از کار تکراری پرهیز می‌کنن؛ این رفتار idempotency هست. shell خام یا هر playbookی چنین تضمینی نداره.

The key question: if the target is already correct, what will another run change? Most standard modules inspect state and avoid unnecessary work; this is idempotency. Raw shell and arbitrary playbooks do not guarantee it.

inventory میزبان‌ها رو انتخاب می‌کنه، playbook وضعیت مطلوب رو می‌گه. تغییر template handler رو خبر می‌کنه؛ اجرای بعدی باید همون وضعیت رو حفظ کنه.

Inventory selects hosts and the playbook describes desired state. A changed template notifies a handler; another run should preserve the result.

دو VM دورریختنی، نه productionTwo disposable VMs, never production

کارگاه روی دو VM آزمایشی Ubuntu/Debian هست. control node رو Linux یا WSL بگذار و Ansible رو از راهنمای رسمی نصب کن. هر میزبان به SSH، کاربر استقرار، کلید عمومی و sudo نیاز داره؛ Python 3 هم باید موجود باشه. کلید خصوصی رو در inventory یا Git نگذار.

The lab uses two disposable Ubuntu/Debian VMs. Use Linux or WSL as control node and install Ansible from the official guide. Each host needs SSH, a deploy user, the public key, and sudo; Python 3 must be available. Never put a private key in inventory or Git.

IPهای 192.0.2.x نمونه‌اند؛ با IP VM خودت عوض کن. SSH رو مستقل امتحان کن؛ اگه اتصال مشکل داره هنوز playbook رو بررسی نمی‌کنیم.

The 192.0.2.x addresses are examples; replace them with VM IPs. Test SSH separately; if it fails, the playbook is not yet the problem.

alias نام Ansible هست؛ ansible_host مقصد اتصال. هر دو رو در گروه web می‌گذاریم. فایل group_vars/web.yml برای مقدار مشترک و host_vars/web2.yml برای استثنای یک میزبان هست؛ این پوشه‌ها رو کنار inventory یا playbook بگذار.

The alias is Ansible’s name; ansible_host is the connection destination. Put both in group web. Use group_vars/web.yml for shared values and host_vars/web2.yml for a host-specific override, beside inventory or playbook.

To give web2 its own message, create host_vars/web2.yml; the host-specific value takes precedence over the group value for that key.

وضعیت مطلوب رو توصیف کنیمDescribe the desired state

فایل site.yml پکیج رو نصب، دایرکتوری رو می‌سازه و دو template رو رندر می‌کنه. become برای taskهای نیازمند sudo هست؛ حساب اتصال همچنان استقرار می‌مونه. apt فقط برای Debian/Ubuntu هست.

site.yml installs the package, creates a directory, and renders two templates. Become enables sudo for tasks that need it; the connection user remains deploy. apt is for Debian/Ubuntu.

site.yml · Debian/Ubuntu disposable hosts
---
- name: Configure lab web hosts
  hosts: web
  become: true
  gather_facts: true
  tasks:
    - name: Install Nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true
        cache_valid_time: 3600
    - name: Create web directory
      ansible.builtin.file:
        path: /var/www/codenames
        state: directory
        owner: root
        group: root
        mode: '0755'
    - name: Render page
      ansible.builtin.template:
        src: templates/index.html.j2
        dest: /var/www/codenames/index.html
        owner: root
        group: root
        mode: '0644'
    - name: Render Nginx config
      ansible.builtin.template:
        src: templates/codenames.conf.j2
        dest: /etc/nginx/conf.d/codenames.conf
        owner: root
        group: root
        mode: '0644'
      notify: Restart Nginx
    - name: Ensure Nginx runs at boot
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
  handlers:
    - name: Restart Nginx
      ansible.builtin.service:
        name: nginx
        state: restarted

در templates/index.html.j2 از variable و facts استفاده کن. نام میزبان کمک می‌کنه پاسخ دو ماشین رو از هم تشخیص بدهی.

Use variables and facts in templates/index.html.j2. The host name lets us distinguish responses.

templates/index.html.j2
<!doctype html>
<meta charset="utf-8">
<title>Ansible lab</title>
<h1>{{ site_message }}</h1>
<p>Host: {{ inventory_hostname }}</p>
<p>OS: {{ ansible_distribution }} {{ ansible_distribution_version }}</p>

و تنظیمات در templates/codenames.conf.j2:

Put this in templates/codenames.conf.j2:

templates/codenames.conf.j2
server {
    listen {{ web_port }};
    server_name _;
    root /var/www/codenames;
    index index.html;

پورت 8080 جلوی تداخل با سایت پیش‌فرض 80 رو می‌گیره. conf.d در بسته‌های معمول Nginx روی Ubuntu/Debian بارگذاری می‌شه، اما در VM خودت تأییدش کن. تغییر تنظیمات handler رو خبر می‌کنه؛ تغییر HTML restart نمی‌خواد.

Port 8080 avoids the default port-80 site. Common Ubuntu/Debian Nginx packages load conf.d, but verify on your VM. Config changes notify the handler; HTML changes do not require restart.

یک بار تغییر؛ بار دوم سکونChange once; settle on the second run

اول روی یک میزبان check mode بگیر. این شبیه‌سازی هست و همهٔ moduleها/شرط‌ها کامل پشتیبانی نمی‌شن؛ diff نیز ممکن هست راز رو چاپ کنه. بعد از بررسی مسیرها، روی VMهای آزمایشی اجرا کن.

First use check mode on one host. It is a simulation, not all modules/conditionals fully support it, and diff may expose secrets. Review paths, then apply to disposable VMs.

preview, then apply and verify
ansible-playbook -i inventory.ini site.yml --check --diff --limit web1
ansible-playbook -i inventory.ini site.yml
curl http://192.0.2.21:8080
curl http://192.0.2.22:8080

در recap اجرای اول failed=0 و unreachable=0 رو ببین؛ changed طبیعی هست. curl باید نام هر میزبان رو برگرداند، اما recap به‌تنهایی پاسخ HTTP رو ثابت نمی‌کنه و curl هم TLS یا دسترسی عمومی رو نه.

In the first recap, check failed=0 and unreachable=0; changes are expected. Curl should show each hostname, but recap alone does not prove HTTP and curl does not prove TLS or public access.

web1 : ok=2 changed=5 unreachable=0 failed=0
web2 : ok=2 changed=5 unreachable=0 failed=0

این recap نمونه هست؛ count دقیق با وضعیت اولیهٔ VM و نسخهٔ بسته فرق می‌کنه. دنبال صفر بودن failed/unreachable و اجرای handler بعد از تغییر تنظیمات باش.

This recap is representative; exact counts vary with initial VM state and package version. Focus on zero failed/unreachable and the handler after a config change.

حالا بدون تغییر دوباره اجرا کن. انتظار changed=0 هست و چون template کانفیگ تغییر نکرده handler نباید restart کنه. این idempotency همین playbook روی همین دو میزبان رو نشون می‌ده، نه همهٔ Ansible tasks رو. اگه changed ماند، task و diff همون میزبان رو بررسی کن.

Rerun unchanged. Expect changed=0; because the config template did not change, its handler should not restart Nginx. This demonstrates idempotency for this playbook on these hosts, not every Ansible task. If changes remain, inspect that host’s task and diff.

web1 : ok=6 changed=0 unreachable=0 failed=0
web2 : ok=6 changed=0 unreachable=0 failed=0

خرابی عمدی: shell هر بار خط تازه‌ای می‌چسبونهDeliberate fault: shell appends another line each time

فقط در VMهای دورریختنی، همون ad-hoc shell رو دوبار برای یک فایل زیر /tmp اجرا کن؛ بعد تعداد خط‌ها رو بشمار. پیش‌بینی کن چرا اجرا موفق هست ولی تغییر تکراری می‌شه.

On disposable VMs only, run the same ad-hoc shell twice against a /tmp file, then count lines. Predict why it succeeds yet repeats the mutation.

non-idempotent on lab hosts only
ansible web -i inventory.ini -b -m ansible.builtin.shell -a "echo marker=ansible >> /tmp/codenames-marker.conf"
ansible web -i inventory.ini -b -m ansible.builtin.shell -a "echo marker=ansible >> /tmp/codenames-marker.conf"
ansible web -i inventory.ini -b -m ansible.builtin.command -a "wc -l /tmp/codenames-marker.conf"

هر بار changed می‌بینی و wc count رو بالا می‌بره: shell فقط فرمان رو اجرا می‌کنه و مطلوب «یک خط» رو نمی‌فهمه. برای یک خط از lineinfile استفاده کن؛ برای کل تنظیمات از template. راه‌حل رو روی فایل سیستمی امتحان نکن.

Each run reports changed and wc grows: shell executes a command but does not model “exactly one line.” Use lineinfile for a line and a template for a whole config. Do not test on system files.

repair.yml · idempotent module
---
- name: Keep one temporary marker
  hosts: web
  become: true
  tasks:
    - name: Ensure marker line exists once
      ansible.builtin.lineinfile:
        path: /tmp/codenames-marker.conf
        line: marker=ansible
        create: true
        state: present

اجرای اول باید duplicateها رو به یک خط برساند؛ اجرای بعدی changed=0. تأیید رو با wc و خواندن فایل انجام بده، نه از روی پیام موفقیت تنها.

The first run should reduce duplicates to one line; the next should be changed=0. Verify with wc and file contents, not just a success message.

restart فقط وقتی فایل واقعاً عوض شدRestart only when the config actually changed

handler task معمولی هست که notify اون رو در صف می‌ذاره و معمولاً آخر play اجرا می‌شه؛ چند notify یک handler رو معمولاً یک بار اجرا می‌کنن. اگه task بعد از تغییر فایل fail بشه، handler اون میزبان ممکن هست اجرا نشود؛ recap و سرویس وضعیت رو بررسی کن.

A handler is a normal task queued by notify and usually runs at play end; multiple notifications typically queue it once. If a later task fails after a file change, the handler may not run for that host; inspect recap and service state.

become دسترسی رو بالا می‌بره؛ رمز sudo رو در YAML آشکار نگذار. از prompt امن یا secret manager استفاده کن. Ansible Vault فایل حساس رو رمز می‌کنه، اما دسترسی به کلید Vault هم باید محافظت بشه. diff می‌تونه راز رو آشکار کنه.

Become escalates privileges; do not put sudo passwords in plain YAML. Use a secure prompt or secret manager. Ansible Vault encrypts sensitive files, but protect its key too. Diff can expose secrets.

roleها task، handler، template و default رو برای استفادهٔ دوباره منظم می‌کنن؛ خودشان idempotency نمی‌سازن. مرز ابزارها هم حفظ: Terraform برای lifecycle زیرساخت، Ansible برای پیکربندی میزبان‌های موجود.

Roles organize reusable tasks, handlers, templates, and defaults; they do not create idempotency automatically. Keep the boundary: Terraform manages infrastructure lifecycle; Ansible configures existing hosts.

سه مدرک جدا برای یک rolloutThree separate proofs for one rollout

recap اجرای اول، پاسخ HTTP هر دو میزبان و recap اجرای دوم رو نگه دار. اگه دور دوم changed=0 نیست، idempotency رو ادعا نکن؛ task و diff رو بررسی کن. اگه پاسخ HTTP غایب هست، Nginx وضعیت و لاگ رو ببین و همون درخواست رو بعد از repair تکرار کن. بعد VMهای آزمایش رو خاموش کن؛ cleanup رو به میزبان دیگر تعمیم نده.

Keep the first recap, both HTTP responses, and the second recap. If run two is not changed=0, do not claim idempotency; inspect task and diff. If HTTP is missing, inspect Nginx status and logs, then repeat the same request after repair. Shut down lab VMs; do not generalize cleanup.

recap می‌گه taskها چه کردند؛ curl پاسخ endpoint همین لحظه رو ثابت می‌کنه؛ اجرای بی‌تغییر نشون می‌ده این playbook روی این دو میزبان همگرا شده. هیچ‌کدام جای دیگری نیست.The recap reports task outcomes; curl proves the endpoint answered now; a no-change run shows convergence on these hosts.
