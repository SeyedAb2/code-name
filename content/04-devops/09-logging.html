لاگ متمرکز

Centralised logging

یه کاربر می‌گه ثبت سفارش خطا داده. web می‌گه درخواست رو فرستاده، orders می‌گه چیزی پیدا نمی‌کنه، و توی ترمینال سوم هم هزار خط دیگه ریخته. اگه برای پیدا کردن یک درخواست مجبور باشیم سه جا رو زیرورو کنیم، با ده سرویس عملاً گم می‌شیم. بیا کاری کنیم رد یک درخواست رو از اول تا آخر یک‌جا دنبال کنیم.

When one request crosses several services, you should not need to search three terminals separately.

۱۸تمرین با پاسخsolved exercises

خطا از کجا شروع شد؟Where did the failure begin?

کاربر می‌گه ثبت سفارش خطا داد. web می‌گه درخواست رو فرستاده؛ orders چیزی پیدا نمی‌کنه؛ در ترمینال سوم هم هزار خط دیگر هست. فصل قبل روند عددی رو دیدیم؛ حالا باید رویداد مشخصی رو پیدا کنیم: چه اتفاقی افتاد، برای کدام درخواست، در کدام سرویس؟

A user says an order failed. Web says it sent the request; orders finds nothing; a third terminal has a thousand unrelated lines. Last chapter showed numeric trends. Now we need one concrete event: what happened, to which request, in which service?

برنامه‌ها معمولاً روی stdout و stderr می‌نویسن. برای یک Compose محلی، لاگ کافیه؛ با چند میزبان و replica، جست‌وجوی دستی دوام نمیاره. collector یا agent لاگ رو از منبع می‌خونه و به مخزن مرکزی می‌فرسته؛ آن‌جا همهٔ سرویس‌ها رو با یک جست‌وجو می‌گردیم.

Applications commonly write to stdout and stderr. Compose logs may be enough locally; manual search does not scale across hosts and replicas. A collector or agent reads logs and forwards them to a central store, where one query can search across services.

شناسهٔ درخواست همراه رویداد از یک سرویس به بعدی می‌ره؛ Alloy جمع می‌کنه و Loki برای جست‌وجو نگه می‌داره.

The request ID travels with events across services; Alloy collects them and Loki stores them for search.

یک خط که بشه به اون اعتماد کردA line we can work with

متن آزاد برای آدم خواندنی هست، اما وقتی هر سرویس timestamp و level رو جور دیگری می‌نویسه جست‌وجو شکننده می‌شه. JSON با فیلدهای ثابت مثل timestamp، level، سرویس، request_id و رویداد زمینه رو از پیام جدا می‌کنه. ساعت میزبان‌ها رو هم sync نگه دار؛ زمان اشتباه ترتیب رویدادها رو به‌هم می‌زنه.

Free text is readable, but queries become fragile when every service formats timestamps and levels differently. JSON with stable fields such as timestamp, level, service, request_id, and event separates context from the message. Keep host clocks synchronised too; incorrect time can distort event order.

two events, one request
{"timestamp":"2026-09-30T08:15:30.120Z","level":"info","service":"web","request_id":"R-42","event":"forward_order"}
{"timestamp":"2026-09-30T08:15:30.148Z","level":"error","service":"orders","request_id":"R-42","event":"inventory_unavailable"}

دو خط می‌گن درخواست به orders رسیده و inventory در دسترس نبوده؛ علت نهایی رو ثابت نمی‌کنن. web شناسه رو بسازد یا از ورودی بگیره و در header درخواست بعدی بفرستد. شناسهٔ تصادفی بهتر از ایمیل یا شمارهٔ کاربر هست؛ دادهٔ هویتی رو به‌عنوان correlation ID به لاگ اضافه نکن.

The lines show that the request reached orders and inventory was unavailable; they do not prove the ultimate cause. Web should create or accept an ID and send it in the next request’s header. A random ID is safer than a user’s email or phone number; do not turn identity data into a correlation ID.

متریک روند رو نشون می‌ده؛ لاگ رویداد رو؛ trace مسیر زمانی درخواست رو. برای پیدا کردن علت، ممکن هست هر سه لازم بشن.

Metrics show trends, logs show events, and traces show a request’s timed path. Diagnosing a cause may require all three.

از stdout تا جست‌وجوی مرکزیFrom stdout to central search

برای lab، دو سرویس کوچک web و orders بساز: web header به‌نام X-درخواست-ID می‌فرسته؛ orders همون مقدار رو در JSON لاگ می‌کنه. هر دو لاگ رو روی stdout می‌نویسن. Collector لاگ Docker رو می‌خونه. یک نکتهٔ امنیتی رو پنهان نمی‌کنیم: Alloy با Docker socket می‌تونه اطلاعات مهمی از daemon بخونه و دسترسی‌اش حساس هست؛ این mount فقط برای ماشین آزمایشگاهی هست، نه الگویی برای production.

For the lab, create two tiny services, web and orders: web sends an X-Request-ID header and orders logs the same value as JSON. Both write to stdout, and a collector reads Docker logs. We will not hide a security caveat: Alloy with the Docker socket can access sensitive daemon information. This mount is for a disposable lab machine, not a production pattern.

Promtail در ۲ مارس ۲۰۲۶ به پایان عمر رسیده؛ برای نصب جدید از Grafana Alloy یا collector پشتیبانی‌شده استفاده کن. تنظیمات این ابزارها نسخه‌محورند. Loki در حالت تک‌گرهی می‌تونه برای یادگیری با filesystem کار کنه، اما این به معنی backup، high availability یا آمادگی عملیاتی نیست.

Promtail reached end of life on March 2, 2026; for a new setup, use Grafana Alloy or a supported collector. These configurations are version-sensitive. Loki can use filesystem storage in a single-node learning setup, but that does not provide backup, high availability, or production readiness.

Alloy configuration · Docker lab only
discovery.docker "lab" {
  host = "unix:///var/run/docker.sock"
}
loki.source.docker "lab" {
  host = "unix:///var/run/docker.sock"
  targets = discovery.docker.lab.targets
  labels = { job = "compose-lab" }
  forward_to = [loki.write.local.receiver]
}
loki.write "local" {
  endpoint {
    url = "http://loki:3100/loki/api/v1/push"
  }
}

این تنظیمات targetهای Docker رو پیدا می‌کنه و به Loki می‌فرسته. در Compose، سرویس‌ها رو روی شبکهٔ داخلی مشترک بگذار؛ Loki و Alloy رو public نکن و برای Grafana فقط loopback میزبان رو publish کن. بعد از بالا آمدن stack، کد منبع از نوع Loki در Grafana رو به http://loki:3100 وصل کن. اگه Grafana می‌گه منبع داده reachable نیست، لاگ خودش و DNS/شبکهٔ Compose رو بررسی کن.

This config discovers Docker targets and forwards their logs to Loki. Put services on a shared internal Compose network; do not expose Loki or Alloy publicly, and bind Grafana only to host loopback. After startup, configure a Loki data source in Grafana at http://loki:3100. If Grafana cannot reach it, inspect Grafana logs and Compose DNS/networking.

یک ID، دو سرویسOne ID, two services

یک درخواست بساز، درخواست ID رو از لاگ web بردار و در Grafana Explore این جست‌وجو رو اجرا کن. مقدار داخل مثال رو با ID واقعی جایگزین کن.

Generate a request, copy its ID from the web log, and run this query in Grafana Explore. Replace the example ID with the one you observed.

LogQL · parse a JSON field
{job="compose-lab"} | json | request_id="R-42"

باید رویدادهای web و orders رو ببینی. این فقط رسیدن دو لاگ رو ثابت می‌کنه، نه کامل‌بودن همهٔ رویدادها رو. اگه یکی نیست، اول جست‌وجو عمومی {job="compose-lab"} بزن، بعد مطمئن شو downstream همون header رو گرفته و collector container رو می‌بینه.

You should see events from web and orders. This proves those two logs arrived, not that all events are complete. If one is missing, query {job="compose-lab"} broadly, then check that the downstream service received the header and the collector discovered its container.

در Loki، متن بدنه مثل labelها index نمی‌شه. labelهای کم‌کاردینال مثل سرویس و محیط برای انتخاب stream خوب‌اند؛ درخواست ID و user ID رو label نکن. فیلدهای متغیر رو از JSON parse کن یا در نسخه و schema مناسب structured metadata به‌کار ببر. مدت نگه‌داری رو هم با سیاست و هزینه تنظیم کن؛ بی‌نهایت نگه‌داشتن هم بی‌نهایت هزینه داره.

In Loki, log bodies are not indexed like labels. Low-cardinality labels such as service and environment help select streams; do not label by request or user ID. Parse variable fields from JSON, or use structured metadata when the version and schema support it. Set retention to match policy and cost; keeping everything forever has a cost.

خرابی عمدی: multiline و secret ساختگیDeliberate fault: multiline and a fake secret

در orders یک بار پیام چندخطی چاپ کن و یک فیلد آزمایشی demo_token=not-a-real-secret اضافه کن. مقدار ساختگی هست و اطلاعات دسترسی واقعی نیست. قبل از اصلاح، همون جست‌وجو رو اجرا کن: چه فیلدی دیگر parse نمی‌شه؟ چرا یک stack trace پخش‌شده بین چند خط، دنبال‌کردن درخواست رو سخت‌تر می‌کنه؟

In orders, print a multiline message once and add the test-only field demo_token=not-a-real-secret. It is fake, not a credential. Before fixing it, run the same query: which field no longer parses? Why is a stack trace split across lines harder to correlate?

بعد به یک JSON معتبر در هر رویداد برگرد، token واقعی و header حساس رو از ابتدا وارد لاگ نکن، و همون جست‌وجو رو تکرار کن. اگه اطلاعات دسترسی واقعی در مخزن لاگ ظاهر شد، پاک‌کردن متن کافی نیست: اون رو revoke/rotate کن، دسترسی‌ها و نسخه‌های ذخیره‌شده رو بررسی کن. لاگ مرکزی هم دادهٔ حساس هست؛ مدت نگه‌داری و مجوز خواندنش باید روشن باشه.

Return to one valid JSON object per event, and never let real tokens or sensitive headers enter the log in the first place. Repeat the same query. If a real credential reached the store, deleting text is not enough: revoke/rotate it and review access and retained copies. A central log store is sensitive data too; access and retention must be deliberate.

برنامه معمولاً روی stdout/stderr می‌نویسه؛ collector انتقال می‌ده؛ Loki ذخیره و جست‌وجو می‌کنه. هیچ‌کدام به‌تنهایی تضمین نمی‌کنه لاگ کامل، امن یا بدون افت باشه.The app writes to stdout/stderr, a collector transports, and Loki stores and searches. None alone guarantees logs are complete, secure, or lossless.

۱۸ تمرین: از فرمت تا رخداد18 exercises: from format to incident

۱. Metrics یا logs؟

«نرخ ۵۰۰ در ده دقیقه» و «در درخواست R-42 چه شد؟» کدام داده؟

Which data answers “5xx rate over ten minutes” and “what happened in R-42”?

توضیح · Reasoning

اول متریک و دومی لاگ؛ روند با رویداد یکی نیست.

Metrics answer the first and logs the second; a trend is not an event.

۲. ID در درخواست بعدی

How does web preserve correlation when calling orders?

پاسخ · Answer

Send the ID in a header and have orders log the same value.

۳. JSON چه کمکی کرد؟

چرا فیلد ثابت از متن آزادی که هر سرویس متفاوت می‌نویسه بهتر هست؟

Why prefer stable fields to free text formatted differently by each service?

دلیل · Reasoning

parser و جست‌وجو روی schema مشخص قابل اتکاترند؛ پیام انسانی همچنان می‌تونه field جدا باشه.

Parsers and queries can rely on a schema while a human-readable message remains a separate field.

۴. stdout یا فایل؟

What is the usual logging destination for a containerized app?

پاسخ

stdout/stderr تا runtime و collector بتوانند جمع کنن؛ فایل فقط با نیاز روشن و مدیریت rotation.

stdout/stderr, so the runtime and collector can capture it; use files only with a clear need and rotation plan.

۵. فقط یک سرویس پیدا شد

Which boundaries do you check?

گام بعد

ارسال header، لاگ واقعی orders، discovery collector و time range.

Header propagation, orders’ raw log, collector discovery, and the time range.

۶. request ID به‌عنوان label

چرا Loki stream label مناسبی نیست؟

Why is it a poor Loki stream label?

پاسخ

مقدار یکتا تعداد stream رو منفجر می‌کنه؛ در body/JSON نگه‌دار و موقع جست‌وجو parse کن.

Unique values explode stream count; keep it in the JSON body and parse during query.

۷. دیسک رو به پرشدن

مدت نگه‌داری نامشخص هست؛ اولین تصمیم عملیاتی؟

Retention is undefined and disk is filling. What is the first operational decision?

تصمیم

سیاست و مدت لازم برای بررسی رو تعیین کن، مدت نگه‌داری و ظرفیت رو اندازه بگیر؛ قبل از حذف، ارزش و الزام نگهداری داده رو بپرس.

Define the investigation/policy window and measure retention and capacity; check data value and legal requirements before deletion.

۸. ترتیب زمان‌ها

orders قبل از web دیده می‌شه؛ ممکن هست چرا؟

Why might orders appear before web?

بررسی

ساعت‌ها ناهمگام‌اند، timezone parse غلط هست یا رویداد-time رو با ingest-time قاطی کرده‌ای.

Clocks differ, timezone parsing is wrong, or event time is confused with ingest time.

۹. multiline stack trace

چطور ارتباط رخدادها رو بهتر می‌کنی؟

How do you improve event correlation?

راهکار

Use a structured event with a stack field or tested multiline handling, not guessed regex over text.

۱۰. token لو رفت

۱۲. labelهای پایه

پاسخ

۱۳. سه host، سه ترمینال

What unifies the workflow?

collector هر میزبان و مخزن/جست‌وجو مشترک؛ stdout محلی به‌تنهایی کافی نیست.

A collector on each host and a shared store/query; local stdout alone is not enough.

۱۴. json parser چیزی نمی‌دهد

۱۵. redact چه چیزی را؟

۱۶. «request failed»

چرا برای شیفت پشتیبانی کافی نیست؟

۱۷. Loki تک‌دیسکی

آیا این backup و HA رو ثابت می‌کنه؟

Does this prove backup and HA?

واقعیت

No; it is a single-node lab. Durable storage, backups, and availability need separate architecture.

۱۸. سه نوع مدرک

متریک نرخ خطا رو بالا می‌بینه؛ لاگ یک درخواست رو در orders نشون می‌ده. علت قطعی هست؟

Metrics show a rising error rate; a log shows one request in orders. Is root cause certain?

جمع‌بندی

نه؛ روند و نمونهٔ رخداد با علت نهایی یکی نیستند. شواهد سرویس وابسته و زمان‌بندی رو بررسی کن.

No. A trend and one event do not establish the root cause. Check dependency evidence and timing.

یک شناسه، دو مدرکOne ID, two pieces of evidence

یک درخواست رو تا orders دنبال کن و دو رویداد رو با timestamp، سرویس و درخواست ID نگه دار. بعد عمداً فرمت رو خراب و همون جست‌وجو رو دوباره اجرا کن؛ بهبود فقط وقتی ثابت هست که همون جست‌وجو بعد از اصلاح نتیجه بده. در پایان از یادمان نرود مخزن لاگ هم دادهٔ حساس داره و socket آزمایش رو نباید به ماشین دیگر تعمیم داد.

Follow one request into orders and retain both events with timestamps, service, and request ID. Break the format deliberately and rerun the same query; the repair is proven only when the same search works again. Remember that the log store is sensitive and the lab socket mount must not be generalized to other machines.
