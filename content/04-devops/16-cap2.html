پروژهٔ ۲ — استقرار خودکار به staging

Project 2 — automated deploy to staging

CI سبزه. این بار اشتباه رایج بعدی رو نمی‌کنیم: روی staging دوباره build نمی‌گیریم. همون چیزی که ساختیم باید بره اونجا؛ با یه هویت دقیق که بعداً بتونیم بگیم کدوم artifact، از کدوم commit، روی کدوم محیط اجرا شده.

CI is green. Now deploy the exact thing we built to staging rather than building a lookalike there.

۷ایستگاهcheckpoints

مأموریت: artifact واحد، دروازهٔ روشنMission: one artifact, an explicit gate

pipeline پروژهٔ قبل تست‌ها رو اجرا می‌کنه. حالا باید image نسخه‌دار بسازد، اون رو به registry بفرستد و در محیط staging بالا بیاورد. قبل از هر محیط بعدی، یک انسان باید تأیید کنه. در این پروژه staging محیط واقعی production نیست و دسترسی استقرار نباید ناخواسته به production برسه.

The previous pipeline runs checks. Now build a versioned image, publish it to a registry, and run it in staging. A human approval gates any next environment. Staging is not production, and its deploy credential must not grant production access.

از یک برنامهٔ کوچک با /health و /نسخه استفاده کن. نسخه رو از commit SHA یا tag تغییرناپذیر بساز؛ tagهایی مثل latest به‌تنهایی برای ردیابی و rollback کافی نیستند. سرور staging باید همون image digest رو اجرا کنه که pipeline منتشر کرده هست.

Use a small app with /health and /version. Derive a version from the commit SHA or immutable tag; mutable tags such as latest alone are weak evidence for rollback. Staging should run the same image digest the pipeline published.

تأیید دستی بعد از دیدن نسخه و سلامت staging انجام می‌شه؛ صرف موفقیت build مجوز انتشار نیست.

Manual approval follows observed staging version and health; a successful build alone does not authorize promotion.

قیود دسترسی و artifactCredential and artifact constraints

اطلاعات دسترسی registry و staging رو در secret store پلتفرم نگه دار؛ در لاگ چاپ نکن. کلید استقرار staging باید فقط اجازهٔ تغییر همون محیط رو داشته باشه. هیچ کلید production در این مأموریت لازم نیست. سرور staging image رو pull می‌کنه؛ image اصلی رو دستی روی سرور build نکن. اگه provider اجازهٔ secret محدود و محیط تأیید نمی‌ده، این مرحله رو در محیط محلی موقت شبیه‌سازی و محدودیت رو ثبت کن.

Keep registry and staging credentials in the platform secret store and never print them. The staging credential must only affect staging; this mission needs no production key. The server pulls the image rather than building it. If your provider lacks scoped secrets or environment approvals, simulate the gate in a disposable local environment and document the limitation.

هفت ایستگاه استقرارSeven deployment checkpoints

۱ — قرارداد staging

مقصد، URL سلامت و پاسخ /نسخه رو تعیین کن. محیط جدا و قابل‌دورریختن بساز؛ هیچ دادهٔ واقعی/secret production وارد نکن. مدرک: URL پایه و پاسخ نسخهٔ اولیه.

Define destination, health URL, and /version response. Use an isolated disposable environment, with no production secrets or data. Evidence: base URL and initial version response.

۲ — ساخت و انتشار یک‌باره

CI بعد از lint/test image رو با SHA یکتا بسازد و push کنه. digest رو ثبت کن. مدرک باید ثابت کنه digest از همون commit آمده هست.

After lint/tests, build and push one image tagged with a unique SHA. Record its digest and prove it came from the tested commit.

۳ — credential محدود

credentialهای registry و مقصد رو به secrets/محیط بده. دسترسی‌شان رو محدود کن و مطمئن شو لاگ مقدارشان رو افشا نمی‌کنه. مدرک: تنظیم scope/permission، بدون نمایش secret.

Provide registry and target credentials through secrets/environment. Scope access and verify logs redact values. Evidence: permission scope without revealing the secret.

۴ — استقرار همان digest

staging image منتشرشده رو pull و اجرا کنه. از روی محیط مقصد، /نسخه رو بخوان و با SHA/digest build تطبیق بده؛ از روی صفحهٔ CI به‌تنهایی نتیجه نگیر.

Have staging pull and run the published image. Read /version from the target and match it to the build SHA/digest; CI output alone is not deployment evidence.

۵ — شکست عمدی verification

برای آزمایش، health path اشتباه یا نسخهٔ مورد انتظار ناهماهنگ بگذار. استقرار verification باید قرمز بشه و ارتقای نسخه متوقف بمونه. لاگ رو بررسی کن؛ بعد تنظیمات رو اصلاح کن و سلامت واقعی رو دوباره بخوان.

Deliberately use a wrong health path or expected version. Deployment verification must fail and block promotion. Inspect logs, correct the configuration, and verify the live target again.

راهنمای تشخیص

تفکیک کن container اصلاً بالا نیامده، route سلامت 404 می‌دهد، یا نسخه با artifact فرق دارد. هر کدام شاهد متفاوت می‌خواهد.

۶ — دروازهٔ تأیید انسانی

pipeline بعد از health/نسخه check منتظر تأیید بمونه. بازبین ابتدا run، commit، digest و نتیجهٔ staging رو می‌بینه. تأیید نباید خودکار از یک متغیر داخل همون commit عبور کنه.

Pause after health and version checks for human approval. The reviewer sees run, commit, digest, and staging result. Approval must not be bypassable by a variable changed in the same commit.

۷ — rollback و تحویل

نسخهٔ قبلی رو با tag/digest صریح دوباره استقرار کن. پاسخ /نسخه و /health رو از مقصد بخوان؛ image قبلی رو حدس نزن. README شامل run URL، current/previous نسخه، مسیر لاگ و روش rollback باشه.

Redeploy the previous explicit tag/digest. Query /version and /health on the target; do not guess which old image is cached. Document run URL, current/previous versions, logs, and rollback steps.

ترتیب اجرای مرجع

run رو به SHA وصل کن → تست سبز → یک image بساز و با SHA منتشر کن → digest رو به‌عنوان artifact ثبت کن → با اطلاعات دسترسی محدود staging رو به همون digest به‌روز کن → از خود مقصد health و نسخه رو بخوان → اگه ناسازگار بود fail و توقف → اگه موفقیت بازبین تأیید می‌ده → برای برگشت، digest قبلی رو صریح انتخاب و دوباره verify کن.

Bind the run to a SHA → pass tests → build one image and publish it by SHA → record its digest → deploy that digest to staging with scoped credentials → query health and version on the target → fail closed on mismatch → request reviewer approval after success → select the previous digest explicitly for rollback and verify again.

این صفحه عمداً وابسته به سرویس‌دهنده action یا دستور SSH ساختگی رو نسخهٔ نهایی معرفی نمی‌کنه؛ جزئیات استقرار به hosting مقصد بستگی داره. در پیاده‌سازی واقعی از action رسمی/اسکریپت محدود، محیط تأیید و secrets خود پلتفرم استفاده کن. موفقیت staging، سلامت production رو ثابت نمی‌کنه؛ فقط آمادگی برای بازبینی قدم بعدی رو نشون می‌ده.

This page does not pretend a provider-specific deploy action or SSH command is universal. Use maintained provider integrations, environment protection, and scoped secrets for the chosen target. A successful staging run does not prove production health; it proves readiness for the next review.
