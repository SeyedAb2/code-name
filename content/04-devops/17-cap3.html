پروژهٔ ۳ — از commit تا production با rollback خودکار

Project 3 — commit to production with automatic rollback

اینجا دیگه یه pipeline نمایشی نمی‌خوایم. یه commit باید نسخهٔ یکتا بسازه، از staging رد بشه، کم‌کم ترافیک بگیره و اگه نشونه‌ها بد شدن واقعاً rollback بشه. یعنی از اول مسیر رو طوری می‌چینیم که هم رفتن به production قابل‌اثبات باشه، هم برگشتن ازش.

A green CI run is no longer the finish line. A commit must create an immutable release, pass staging, receive limited traffic, and actually roll back when evidence turns bad.

مأموریت: انتشار قابل‌ردگیریMission: a traceable release

تیم یک انتشار کوچیک داره و می‌خواد مسیر commit تا production رو تمرین کنه: CI، image immutable، registry، staging، canary، health/metric gate، ارتقای نسخه، rollback و audit. در این دوره production رو در محیط موقت شبیه‌سازی می‌کنیم تا آزمایش نسخهٔ خراب به کاربر واقعی یا دادهٔ واقعی آسیب نزند.

The team must rehearse a complete path from commit through CI, immutable image, registry, staging, canary, health/metric gate, promotion, rollback, and audit. Here “production” is a disposable production-like environment so a broken release cannot harm real users or data.

سه مسیر جدا تعریف کن: stable و canary پشت reverse proxy، staging برای آزمون قبل از انتشار، و registry برای imageهای نسخه‌دار. canary سهم کوچک و محدود از درخواست‌های آزمایشی می‌گیره؛ metricها از همون درخواست‌های نشان‌دار جمع می‌شن. اگه خطا از حد تعیین‌شده گذشت، gate باید ارتقای نسخه رو متوقف و stable رو فعال کنه. این تمرین، تضمین zero downtime در هر معماری نیست.

Define separate stable and canary targets behind a reverse proxy, staging for pre-release checks, and a registry of versioned images. Canary receives a small, bounded share of marked test traffic; metrics are collected from that traffic. If errors cross a declared threshold, the gate stops promotion and routes back to stable. This does not guarantee zero downtime for every architecture.

متریک gate دو خروجی واقعی داره: ارتقای نسخه بعد از عبور از آستانه، یا برگشت ترافیک به stable. هر دو نتیجه با نسخه و زمان ثبت می‌شن.

The metric gate has two real outcomes: promote when thresholds pass, or route back to stable. Record both with version and time.

قواعد ایمنی قبل از اجراSafety rules before running

روی VPS عمومی یا حساب تولیدی واقعی این سناریو رو اجرا نکن. secret آزمایشی، دیتابیس موقت و دادهٔ ساختگی به کار ببر. CI secret رو فقط برای مرحله‌ای بده که لازم داره؛ image و artifact نباید secret داشته باشن. schema migration رو backward-compatible نگه دار: اول ستون/ساختار افزوده، بعد نسخهٔ جدید، و حذف ناسازگار رو به انتشار جدا موکول کن. rollback اپ الزاماً migration رو برنمی‌گرداند.

Do not run this drill against a public VPS or real production account. Use test secrets, disposable storage, and synthetic data. Scope CI secrets to the steps that need them; never bake them into images. Keep schema changes backward-compatible: add first, deploy compatible code, and defer destructive removal. Application rollback does not automatically reverse a migration.

ترافیک canary رو با load generator محدود تولید کن: نرخ/تعداد درخواست مشخص، timeout و سقف زمان. هرگز loop بدون حد یا فشارسنجی نامحدود اجرا نکن.

Generate bounded canary traffic with a fixed request count/rate, timeout, and duration. Never run an unbounded loop or stress test.

نه ایستگاه مأموریتNine mission checkpoints

۱ — مرزها و خط مبنا

محیط موقت، دامنه/local URL، stable نسخه و داشبورد یا فایل متریک ساده رو مشخص کن. قبل از تغییر، health و نرخ خطای وضعیت پایه رو ثبت کن. مدرک: معماری، آدرس‌ها و وضعیت پایه.

Define disposable targets, URLs, stable version, and a simple metric view. Record health and baseline errors before changes. Evidence: architecture, endpoints, and baseline.

۲ — CI و version یکتا

lint/test سبز شرط ساخت باشه. image رو با commit SHA یا نسخهٔ انتشار بساز، push کن و digest رو نگه دار. ثابت کن یک commit دقیقاً همون artifact رو به مراحل بعد می‌ده.

Require lint and tests before build. Tag the image with a commit SHA or release version, push it, and record its digest. Prove later stages consume that artifact from this commit.

۳ — staging

digest نسخهٔ 1.0.0 رو در staging اجرا کن. health، /نسخه و رفتار اصلی رو از مقصد بخوان؛ secret و DB رو از production جدا نگه دار.

Run the 1.0.0 digest in staging. Query health, /version, and a core behavior on the target; isolate its secrets and database from production.

۴ — promotion با دروازه

بعد از موفقیت staging یک تأیید انسانی قرار بده. ثبت کن چه کسی/کدام run کدام digest رو تأیید کرد. تا قبل از تأیید نباید مقصد stable تغییر کنه.

Require a human approval after staging succeeds. Record who approved which digest and run. Stable must remain unchanged before approval.

۵ — canary محدود

نسخهٔ 1.1.0 رو کنار stable بالا بیاور. روی محیط آزمایش، درصد/مسیر canary رو روشن و قابل‌مشاهده کن. تعداد محدودی درخواست علامت‌دار بفرست و پاسخ نسخه، latency و خطا رو ثبت کن.

Start 1.1.0 beside stable. Make the canary route or share visible in the test environment. Send a bounded set of marked requests and record version, latency, and errors.

۶ — metric gate و rollback خودکار

آستانه رو قبل از آزمایش بنویس: مثلاً سلامت endpoint باید موفق باشه و نرخ خطا در پنجرهٔ ثابت از وضعیت پایه + حد تعریف‌شده بالاتر نرود. نسخهٔ bad رو طوری بساز که /health خطا بده یا درخواست canary خطای نشان‌دار تولید کنه. gate باید canary رو رد کنه، ترافیک stable رو برگرداند، و لاگ دقیقاً نسخهٔ برگشتی رو ثبت کنه.

Declare thresholds before testing: for example, health must pass and canary errors over a fixed window must stay below a defined baseline-relative limit. Make a bad release fail health or produce marked canary errors. The gate must reject it, restore stable routing, and log the exact restored version.

اگر gate قرمز نشد

اول ثابت کن درخواست‌ها واقعاً به canary رفته‌اند، metric label از نسخه/مسیر درست می‌آید، پنجره به اندازهٔ کافی sample دارد و automation نتیجه را مصرف می‌کند. آستانه را بعد از دیدن نتیجه دستکاری نکن.

۷ — promotion و post-deploy check

برای اجرای سالم، همون gate رو بگذران و وزن/مسیر رو به نسخهٔ تازه منتقل کن. بعد از ارتقای نسخه، health، نسخه و درخواست کارکرد اصلی رو از بیرون مقصد تأیید کن. canary ترافیک محدود، به‌تنهایی کاربران واقعی رو نمایندگی نمی‌کنه.

For a good release, pass the same gate and shift routing to the new version. After promotion, verify health, version, and a core request from outside the target. A small synthetic canary is not a substitute for real-user coverage.

۸ — schema، secret و audit

یک تغییر schema افزایشی و سازگار رو مستند کن؛ rollback رو بدون downgrade مخرب ممکن نگه دار. audit record شامل commit، image digest، approver، زمان، نتیجهٔ gate و نسخهٔ نهایی باشه؛ هیچ مقدار secret چاپ نشود.

Document one additive, backward-compatible schema change that does not require destructive downgrade on rollback. Audit commit, image digest, approver, time, gate result, and final version without secret values.

۹ — رخداد و handoff

bad canary رو یک بار دیگر از شروع تا برگشت اجرا کن، شواهد run رو ذخیره کن و runbook کوتاه تحویل بده: چه چیزی هشدار می‌ده، rollback چطور تأیید می‌شه، و اگه gate/registry/health پاسخ نداد قدم بعد چیست؟

Repeat the bad-canary drill end to end, retain run evidence, and hand off a concise runbook: what alerts, how rollback is verified, and what to inspect when gate, registry, or health checks fail.

اگه دو نسخهٔ اپ پشت proxy اجرا کردی، نقش سرویس هنوز یکی هست ولی instanceها چندتا هستن. این نمونه می‌تونه جابه‌جایی بدون gap قابل‌مشاهده رو در تست نشون بده؛ تضمین zero downtime در همهٔ خطاها، migrationها و شبکه‌ها نمی‌ده. اگه فقط یک container رو عوض می‌کنی، دربارهٔ downtime صادق باش.

Two app instances behind a proxy are still one application service role. The drill may demonstrate no observable gap in its test, but cannot guarantee zero downtime across every failure, migration, and network condition. If replacing a single container, describe the interruption honestly.

راه‌حل مرجع و یادداشت مهندسیReference runbook and engineering note

ترتیب runbook

۱) SHA رو ثبت و CI اجرا کن؛ ۲) فقط بعد از lint/test image immutable بساز و digest ذخیره کن؛ ۳) digest رو به staging ببر و health/نسخه/test رو از مقصد بخوان؛ ۴) تأیید ثبت کن؛ ۵) نسخهٔ تازه رو در canary کنار stable اجرا کن؛ ۶) ترافیک آزمایشی محدود و علامت‌دار تولید کن؛ ۷) gate در پنجرهٔ ازپیش‌تعیین‌شده health و نرخ خطا رو ارزیابی کنه؛ ۸) در شکست، route رو به stable برگرداند و نسخه/دلیل رو ثبت کنه؛ در موفقیت ارتقای نسخه کنه؛ ۹) از بیرون مسیر نهایی رو بررسی و audit رو نگه‌داری کن.

1) Record SHA and run CI; 2) build an immutable image only after lint/tests and save its digest; 3) deploy that digest to staging and query health/version/tests on the target; 4) record approval; 5) run the candidate beside stable as canary; 6) send bounded marked traffic; 7) evaluate health and error rate over a predeclared window; 8) route back to stable and record version/reason on failure, or promote on success; 9) verify externally and retain the audit record.

پیاده‌سازی ابزار route-switch و متریک collector به محیط انتخابی وابسته هست؛ از proxy و CI رسمی همون محیط استفاده کن و تغییر route رو واقعاً اعمال کن. اسکریپتی که فقط «rollback» چاپ کنه قبولی نیست. migration rollback خودکار نداره مگر طراحی‌اش جداگانه و امن باشه. در این پروژه هیچ live database یا حساب تولیدی رو به خطر نینداز.

Routing and metric collection depend on the chosen environment; use its real proxy and CI integration and actually change routing. A script that merely prints “rollback” does not pass. Database migration is not automatically reversed unless explicitly designed to be safe. Do not risk a live database or production account in this project.

این capstone ثابت می‌کنه می‌تونی انتشار رو با هویت artifact، گیت‌های کیفیت، مشاهدهٔ canary، تصمیم ارتقای نسخه/rollback و سابقهٔ قابل‌رسیدگی اداره کنی. ثابت نمی‌کنه هر سیستم واقعی بی‌وقفه هست؛ مهندسی یعنی هم نتیجه رو نشون بدی، هم دقیق بگی این نتیجه چه چیزی رو ثابت نمی‌کنه.

This capstone proves you can operate a release with artifact identity, quality gates, canary observation, promotion/rollback decisions, and an auditable record. It does not prove every real system is interruption-free; engineering means stating both evidence and the limits of the claim.
