Git در عمل: branch، merge، rebaseGit in practice: branch, merge, rebase

یه تغییر کوچیک آماده‌ست، ولی دو نفر هم‌زمان دارن روی همون مخزن کار می‌کنن. یکی شاخه‌ش از main عقب افتاده، اون یکی چندتا تغییر تازه فرستاده. حالا چطور تغییر رو بازبینی کنیم، زود برگردونیمش به شاخهٔ اصلی و اگه وسط کار گیر کرد، بدون خراب کردن تاریخچهٔ بقیه جمعش کنیم؟

A small change is ready, but two people are working in the same repository. How do we review it, bring it back to the main line promptly, and recover from trouble without disrupting a teammate’s history?

وقتی شاخه‌ها دیر به هم می‌رسنWhen branches meet too late

هفتهٔ پیش نازنین قابلیت پیام خوشامد رو شروع کرد. امروز می‌خواد اون رو تحویل بده؛ اما از اون موقع سارا مسیر صفحهٔ اصلی رو هم عوض کرده. حالا تغییر نازنین روی نسخه‌ای قدیمی از پروژه نشسته. «فقط merge کن» جواب کافی نیست: چقدر از هم دور شدن و کدام نسخه باید واقعاً منتشر بشه؟

Last week, Nazanin started a welcome-message feature. Today she is ready to hand it off, but Sara has changed the home page since then. Nazanin’s work now sits on an older version of the project. “Just merge it” is not enough: how far have the branches diverged, and which version should actually ship?

در فصل اول دیدیم انتشار یک مسیر پیوسته تا رسیدن بازخورد کاربر هست. Git این مسیر رو به‌تنهایی کامل نمی‌کنه؛ کمک می‌کنه خودِ تغییر قابل‌ردیابی، قابل‌بازبینی و برای ادغام آماده بمونه. هرچه شاخه بیشتر جدا بمونه، تفاوت‌های بیشتری جمع می‌شه و تعارض رو دیرتر می‌بینیم.

Chapter 1 treated delivery as one path that continues until user feedback arrives. Git does not complete that path on its own; it helps keep a change traceable, reviewable, and ready to integrate. The longer a branch stays apart, the more differences accumulate—and the later we discover conflicts.

این شکل زمان رو نشون می‌ده، نه قانون قطعی: شاخهٔ کوتاه هم ممکن هست تعارض داشته باشه؛ شاخهٔ بلند هم شاید بی‌تعارض ادغام بشه. تفاوت این هست که ادغام زودتر، ناسازگاری رو زودتر به ما نشون می‌ده و کوچک‌تر نگه‌داشتن تغییر، بررسی رو آسان‌تر می‌کنه.

The diagram shows a tendency, not a law: a short branch can still conflict, and a long one can merge cleanly. Integrating sooner exposes incompatibilities earlier, while smaller changes are easier to review.

یک تغییر، یک شاخهٔ کوتاه‌عمرOne change, one short-lived branch

برای قابلیت پیام خوشامد، اول وضعیت رو می‌خوانیم تا چیزی رو تصادفی روی کار نیمه‌تمام نسازیم. شاخهٔ اصلی رو با نام تیم‌ها یکی فرض نکن؛ بعضی مخزن‌ها هنوز `master` دارن. این آزمایش مخزن تمرینی خودش رو می‌سازه.

For the welcome feature, first inspect the state so we do not build on unfinished work by accident. Do not assume every repository calls its main branch `main`; some still use `master`. This experiment creates its own practice repository.

bash · disposable team repo
mkdir delivery-git-lab && cd delivery-git-lab
git init -b main
git config user.name 'Nazanin Example'
git config user.email 'nazanin@example.test'
printf 'Welcome\n' > home.txt
git add home.txt
git commit -m 'Add home page'
git switch -c feature/welcome-message
printf 'Welcome, team!\n' > home.txt
git add home.txt
git commit -m 'Personalise welcome message'
git status --short --branch
git log --oneline --decorate --graph --all

در خروجی `وضعیت` دنبال `قابلیت/welcome-message` و working tree تمیز بگرد. در `لاگ` باید commit قابلیت رو بالای نقطهٔ شروع ببینی. این‌ها می‌گن تغییر ثبت شده و کجای تاریخچه هست؛ هنوز نمی‌گن درست کار می‌کنه یا هم‌تیمی اون رو بازبینی کرده.

In `status`, look for `feature/welcome-message` and a clean working tree. In `log`, the feature commit should sit above the starting point. This tells us the change is recorded and where it sits in history; it does not tell us that it works or has been reviewed.

اگه Git قدیمی‌تر از نسخه‌ای هست که `git switch` رو می‌شناسه، می‌تونی در این آزمایش از `git checkout -b قابلیت/welcome-message` استفاده کنی. در کار روزمره، اول `git وضعیت` رو بخوان؛ اسم شاخه به‌تنهایی تضمین نمی‌کنه جای درستی هستی.If your Git predates `git switch`, use `git checkout -b feature/welcome-message` for this experiment. In daily work, read `git status` first; a branch name alone does not guarantee you are in the right place.

شاخه یک کپی جدا از کل پروژه نیست؛ نامی هست که به یک commit اشاره می‌کنه. اینجا هدفش جداکردن یک تغییر محدود هست تا ساخت و بازبینی‌اش مستقل بمونه. وقتی مسیر تغییر روشن شد، شاخه رو زود ادغام می‌کنیم و حذفش می‌کنیم؛ نه اینکه ماه‌ها شاخهٔ موازی بسازیم.

A branch is not a separate copy of the whole project; it is a name pointing to a commit. Here it isolates one bounded change so it can be built and reviewed independently. Once the change is integrated, merge it and remove the branch rather than maintaining a parallel line for months.

Pull request یعنی گفت‌وگو قبل از ادغامA pull request is a conversation before integration

نازنین حالا تغییر رو push می‌کنه و pull request باز می‌کنه. در GitHub، pull request یک قابلیت میزبان مخزن هست، نه دستور Git. تیم می‌تونه آنجا هدف تغییر، محدودیت‌ها، آزمون و چیزی رو که بازبین باید بررسی کنه بنویسد. در GitLab یا ابزار دیگر، نام و جزئیات صفحه فرق می‌کنه؛ ایدهٔ بازبینی قبل از ادغام همون هست.

Nazanin now pushes the change and opens a pull request. On GitHub, a pull request is a repository-hosting feature, not a Git command. The team can describe the intent, constraints, tests, and what reviewers should inspect. GitLab and other hosts use different names and interfaces; the idea of review before integration remains.

در یک مخزن محلی می‌تونیم شکل بررسی رو با مقایسهٔ شاخه‌ها تمرین کنیم. اگه اون رو به مخزن واقعی می‌بری، remote رو فقط وقتی اضافه کن که آدرس درست و مجوز نوشتن داری؛ push کردن به remote واقعی بخشی از آزمایش بی‌خطر نیست.

In a local repository, we can practise the review shape by comparing branches. If you adapt this to a real repository, add a remote only when you have the correct URL and write permission; pushing to a real remote is not part of a harmless experiment.

bash · inspect before review
git diff main...feature/welcome-message
git diff --stat main...feature/welcome-message
git log --oneline main..feature/welcome-message

سه‌نقطه در `git diff main...قابلیت/welcome-message` تغییر شاخهٔ قابلیت رو از نقطهٔ مشترک دو شاخه نشون می‌ده؛ `--stat` اندازهٔ تغییر و `لاگ` commitهای جلوتر رو نشون می‌ده. برای فهمیدن کل وضعیت، باید خود diff رو هم بخوانی و آزمون‌ها رو اجرا کنی. تعداد خط کم، کیفیت رو ثابت نمی‌کنه.

In `git diff main...feature/welcome-message`, the three-dot form shows the feature branch’s changes since the branches’ common point; `--stat` gives the change size and `log` lists commits ahead. To understand the change, read the diff and run the checks too. A low line count does not prove quality.

بازبینی خوب دنبال «کد قشنگ هست؟» نمی‌مونه: آیا رفتار خواسته‌شده رو داره؟ چه چیزی ممکن هست بشکند؟ آزمون تازه چه چیزی رو ثابت می‌کنه؟ آیا راه بازگشت معلوم هست؟ در تیم کوچک، حتی یک بازبین که سؤال درست بپرسد از ادغام بی‌چشم بهتر هست.

A useful review asks more than “does the code look neat?” Does it implement the intended behavior? What could break? What does the new test prove? Is the way back understood? Even one thoughtful reviewer is better than merging without review.

در میزبان‌هایی مثل GitHub می‌توان main رو protected کرد تا merge از مسیر pull request و شرط‌هایی مثل بازبینی یا وضعیت check بگذرد. جزئیات در هر میزبان و طرح اشتراک فرق داره؛ protected branch خطای منطقی رو خودکار پیدا نمی‌کنه و جای آزمون رو نمی‌گیره.Hosts such as GitHub can protect `main` so changes go through pull requests and conditions such as reviews or status checks. Details vary by host and plan. Branch protection does not detect a logical bug or replace testing.

CI به PR چه کمکی می‌کنه؟What does CI add to a pull request?

بازبین می‌گه «روی سیستم من اجرا شد»؛ اما ما هنوز شاهدی نداریم که همون commit روی محیط تمیز build و test شده باشه. CI همین بررسی‌های تکراری رو روی تغییر اجرا می‌کنه و نتیجه رو به همون pull request وصل می‌کنه. فصل بعد خط لوله رو می‌سازیم؛ اینجا فقط می‌خوایم مرزش روشن باشه.

A reviewer says, “It ran on my machine,” but we still lack evidence that this exact commit was built and tested in a clean environment. CI runs repeatable checks on the change and attaches the result to the pull request. The next chapter builds the pipeline; here we only need to understand its role.

اگه commit بعد از سبزشدن آزمون عوض بشه، نتیجهٔ قبلی لزوماً دربارهٔ نسخهٔ تازه چیزی نمی‌گه. CI باید روی commit یا ترکیب نهایی‌ای که قراره ادغام بشه دوباره نتیجه بده. وضعیت check سبز هم فقط همون بررسی‌های تعریف‌شده رو ثابت می‌کنه؛ نه نبودن همهٔ خطاها رو.

If the commit changes after checks pass, the old result does not necessarily say anything about the new revision. CI needs to report on the commit—or final combination—that is going to be merged. A green status check proves only that the configured checks passed, not that every defect is absent.

merge یا rebase؛ تاریخچه رو برای چه کسی می‌خوانیم؟Merge or rebase: who is the history for?

سارا در همین زمان تغییر مستقلی به `main` ادغام کرده. شاخهٔ نازنین حالا عقب هست. دو راه متداول داریم؛ هیچ‌کدام دکمهٔ جادویی برای «حل همهٔ تعارض‌ها» نیست.

Sara has meanwhile integrated an independent change into `main`. Nazanin’s branch is now behind. There are two common ways forward; neither is a magic “resolve all conflicts” button.

انتخابChoiceچه می‌کنه؟What it doesمناسب وقتی…Useful when…مراقب چه باشیم؟Watch for…
merge mainدو خط تاریخچه رو نگه می‌داره و ممکن هست merge commit بسازد.
Preserves both lines of history and may create a merge commit.		شاخه مشترک هست، یا می‌خوایم نقطهٔ ادغام آشکار بمونه.
The branch is shared, or we want the integration point visible.		تاریخچه شاخه‌ای‌تر می‌شه.
History becomes more branched.
rebase maincommitهای محلی رو روی نوک تازهٔ main دوباره می‌چینه؛ شناسهٔ آن‌ها عوض می‌شه.
Replays local commits on the latest main; their commit IDs change.		شاخه شخصی هست و تاریخچهٔ خطی برای بازبینی می‌خوایم.
The branch is private and a linear review history is useful.		تعارض ممکن هست پیش بیاد؛ بازنویسی شاخهٔ منتشرشده هماهنگی می‌خواد.
Conflicts can still happen; rewriting a published branch needs coordination.

اگه شاخه هنوز فقط مال نازنین هست، rebase می‌تونه commitهایش رو روی `main` جدید بازچینی کنه. اگه سارا هم اون شاخه رو pull کرده و بر اساس commitهایش کار می‌کنه، تغییر شناسه‌ها برای او تاریخچهٔ متفاوتی می‌سازه. در اون وضعیت، merge یا هماهنگی روشن معمولاً دردسر کمتری داره. تاریخچهٔ مشترک رو بی‌خبر force-push نمی‌کنیم.

If the branch still belongs only to Nazanin, rebase can replay its commits on the latest `main`. If Sara has pulled that branch and built work on its commits, the changed IDs create a different history for her. In that case, merging or explicit coordination is usually less disruptive. Never force-push rewritten shared history without coordination.

یک تمرین امن برای دیدن فرق: روی شاخهٔ شخصی یک commit بساز، روی `main` هم commitی مستقل اضافه کن، بعد `git rebase main` رو اجرا کن. خروجی `git لاگ --oneline --graph --decorate --all` نشون می‌ده commit قابلیت حالا بعد از commit تازهٔ main قرار گرفته. فایل‌ها رو هم با `git diff main...HEAD` بررسی کن؛ شکل خطی گراف ثابت نمی‌کنه رفتار برنامه درست هست.

A safe way to see the difference: make a commit on a private branch, add an independent commit to `main`, then run `git rebase main`. `git log --oneline --graph --decorate --all` shows the feature commit now after the new main commit. Inspect files with `git diff main...HEAD` too; a linear graph does not prove the application behaves correctly.

در تعارض rebase، `git وضعیت` می‌گه کدام فایل‌ها موندن. فایل رو آگاهانه حل کن، `git add` بزن و `git rebase --continue` رو اجرا کن؛ اگه تصمیم گرفتی متوقف شوی، `git rebase --abort` برمی‌گرداند به وضعیت قبل از همین rebase. قبل از ادامه، diff رو بخوان؛ نشانگرهای تعارض نباید باقی مانده باشن.During a rebase conflict, `git status` identifies the remaining files. Resolve them deliberately, stage with `git add`, then run `git rebase --continue`; if you decide to stop, `git rebase --abort` returns to the state before this rebase. Read the diff before continuing and ensure conflict markers are gone.

تعارض، خبر بد نیست؛ تصمیمِ ثبت‌نشده هستA conflict is not bad news; it is an undecided change

برای دیدنش دو نسخه از یک جمله رو جداگانه تغییر می‌دهیم. این آزمایش فقط در مخزن دورریختنی ابتدای فصل انجام می‌شه؛ هرگز برای تمرین روی مخزن کاری یا فایل‌های بی‌پشتوانه دستورهای پاک‌کردن اجرا نکن.

To see one, we will change the same sentence independently. Run this only in the disposable repository created earlier; never practise destructive commands in a work repository or on files without a backup.

bash · deliberate conflict, local only
git switch main
printf 'Welcome, everyone.\n' > home.txt
git add home.txt && git commit -m 'Update home greeting'
git switch feature/welcome-message
printf 'Welcome, developers!\n' > home.txt
git add home.txt && git commit -m 'Address developers in greeting'
git switch main
git merge --no-ff feature/welcome-message

Git احتمالاً می‌گه هر دو شاخه یک خط رو متفاوت تغییر داده‌اند و merge کامل نشده. `git وضعیت` نام فایل متعارض رو نشون می‌ده؛ فایل رو باز کن و تصمیم بگیر متن نهایی چه باشه. انتخاب سمت `ours` یا `theirs` بدون فهم نیاز محصول، حل تعارض نیست.

Git will likely report that both branches changed the same line differently and the merge is incomplete. `git status` names the conflicted file; open it and decide what the final text should say. Choosing `ours` or `theirs` without understanding the product need is not a real resolution.

bash · inspect and finish the merge
git status
# Edit home.txt and remove all <<<<<<<, =======, and >>>>>>> markers
git diff --check
git add home.txt
git diff --cached
git commit -m 'Merge welcome message'

`git diff --check` برای فاصله‌های ناسازگار و بعضی نشانگرهای حل‌نشده هشدار می‌ده، اما صحت متن یا رفتار رو نمی‌فهمه. `git diff --cached` محتوایی رو نشون می‌ده که قراره commit بشه. بعد از commit، با `git وضعیت --short --branch` تمیزی درخت و با `git لاگ --graph` نتیجهٔ ادغام رو بررسی کن.

`git diff --check` warns about whitespace problems and some unresolved markers, but it cannot judge the text or behaviour. `git diff --cached` shows what is about to be committed. After committing, use `git status --short --branch` to confirm a clean tree and `git log --graph` to inspect the merge.

اگه وسط merge متوجه شدی اشتباه شروعش کرده‌ای و هنوز commit نشده، `git merge --abort` معمولاً merge رو کنار می‌ذاره. اگه فایل‌های محلیِ قبل از merge تغییر داشته‌اند، نتیجه رو حدس نزن؛ قبل از هر اقدامی وضعیت و diff رو بخوان.If you realise you started the wrong merge and have not committed, `git merge --abort` usually abandons it. If local files were already modified, do not guess what will happen; inspect status and diff before acting.

کدام راهبرد شاخه‌بندی به تیم می‌خورد؟Which branching style fits the team?

اسم راهبرد از تعداد branchها مهم‌تر نیست؛ زمان بازخورد، نوع انتشار و هزینهٔ ادغام مهمه. سه الگو رو به‌عنوان نقطهٔ شروع ببین، نه مذهب تیمی.

The strategy’s name matters less than feedback time, release shape, and integration cost. Treat these three patterns as starting points, not team religions.

اگه تیم هر هفته چندبار به production می‌ره، شاخهٔ انتشار طولانی شاید فقط فاصلهٔ بازخورد رو زیاد کنه. اگه نسخهٔ نصب‌شدهٔ مشتری باید ماه‌ها patch بگیره، شاخهٔ پایدار می‌تونه دلیل واقعی داشته باشه. از نیاز انتشار شروع کن، نه از نمودار محبوب اینترنت.

If the team deploys several times a week, a long-lived release branch may only delay feedback. If customer-installed versions need patches for months, a stable branch may have a genuine purpose. Start with release needs, not a popular internet diagram.

شاخهٔ انتشار رو فقط وقتی لازمه نگه دارKeep a release branch only when it is needed

وقتی باید یک نسخه رو برای مدت مشخص تثبیت کنی، `انتشار/2.4` می‌تونه محل رفع اشکال همون نسخه باشه؛ قابلیت‌های بعدی در مسیر اصلی می‌مونن. هر اصلاح لازمه به شاخهٔ اصلی هم برسه، وگرنه در نسخهٔ بعدی دوباره همون باگ برمی‌چرخه. اگه چنین نیاز نگهداری نداری، شاخهٔ انتشار دائمی فقط مسیر دیگری برای drift می‌سازه.

When a version must be stabilised for a period, `release/2.4` can hold fixes for that version while new features continue on the main line. Every relevant fix must also reach the main line or the bug may return in the next release. Without that maintenance need, a permanent release branch creates another place to drift.

ادغام شد؛ کدام نسخه رو منتشر کردیم؟Merged; which version did we release?

بعد از ادغام، یک نام نسخه روی commit انتشار می‌گذاریم تا آدم‌ها و ابزارها به یک نقطهٔ مشخص اشاره کنن. tag همون branch نیست: branch با commitهای تازه جلو می‌ره؛ tag معمولاً نامی ثابت برای نسخهٔ منتشرشده هست. برای نسخهٔ همراه توضیح، annotated tag بساز.

After integration, attach a version name to the release commit so people and tools can refer to one exact point. A tag is not a branch: a branch advances to newer commits; a tag is normally a fixed name for a release. Use an annotated tag when you want release metadata.

bash · tag the reviewed release commit
git switch main
git status --short --branch
git log -1 --oneline
git tag -a v1.0.0 -m 'Release 1.0.0'
git show --no-patch --decorate v1.0.0

قبل از tag، مطمئن شو روی commit نهایی main هستی و تغییر محلیِ ناخواسته نداری. `git show` باید پیام tag و commit هدف رو نشون بده. این نام‌گذاری کمک می‌کنه انتشار رو دوباره پیدا کنیم؛ به‌تنهایی ثابت نمی‌کنه artifact واقعاً همون commit هست یا production سالم هست. اگه مخزن remote داره، tag رو با دستور جداگانه push می‌کنن و باید مجوز و مقصد رو دوباره بررسی کرد.

Before tagging, confirm you are on the final `main` commit with no unintended local changes. `git show` should display the tag message and target commit. This makes the release easier to find; it does not prove an artifact was built from that commit or that production is healthy. In a remote repository, tags are pushed separately, so verify the destination and permissions first.

اگه tag رو اشتباه ساخته‌ای، قبل از جابه‌جایی یا حذفش بررسی کن آیا قبلاً منتشر شده و کسی به اون تکیه کرده هست. tag منتشرشده هم بخشی از قرارداد نسخه هست؛ بی‌خبر عوض‌کردنش می‌تونه هم‌تیمی یا سامانهٔ انتشار رو سردرگم کنه.If you created the wrong tag, check whether it has already been published and used before moving or deleting it. A published tag is part of the release contract; silently changing it can confuse teammates or deployment systems.

دردسر واقعی: شاخه سه هفته باز ماندهA real snag: the branch has been open for three weeks

نازنین می‌گه «فقط یک conflict دارم»؛ اما diff صدها خط داره و سارا می‌گه branch رو قبلاً pull کرده. هنوز `rebase` یا `push --force` نزن. اول شواهد رو جمع کن: روی کدام شاخه‌ایم، چند commit اختلاف هست، چه فایل‌هایی عوض شدن و آیا کسی از commitهای branch استفاده می‌کنه؟

Nazanin says, “I only have one conflict,” but the diff is hundreds of lines and Sara says she already pulled the branch. Do not run `rebase` or `push --force` yet. Gather evidence first: which branch are we on, how many commits differ, what files changed, and is anyone depending on this branch?

bash · read-only diagnosis first
git status --short --branch
git fetch origin
git log --oneline --graph --decorate --left-right origin/main...HEAD
git diff --stat origin/main...HEAD
git branch -vv

`fetch` فقط اطلاعات remote رو به‌روز می‌کنه و working tree رو merge نمی‌کنه. علامت‌های `<` و `>` در لاگ می‌گن کدام commit در یک طرف هست؛ `diff --stat` اندازهٔ تغییر رو خلاصه می‌کنه؛ `branch -vv` وضعیت upstream رو نشون می‌ده. این‌ها میزان واگرایی رو روشن می‌کنن، اما نمی‌گن چه کسی branch رو pull کرده؛ اون رو از هم‌تیمی‌ها بپرس.

`fetch` updates remote-tracking information without merging into the working tree. The `<` and `>` markers in the log show which commits belong to each side; `diff --stat` summarises change size; `branch -vv` shows upstream status. These reveal divergence but cannot tell us who has pulled the branch—ask teammates directly.

اگه branch فقط نزد نازنین هست، با هماهنگی می‌شه تغییر رو کوچک کرد، main تازه رو آورد و بعد بازبینی رو از نو انجام داد. اگه سارا روی commitهایش کار کرده، rebase کردن و force-push تاریخچهٔ مشترک رو عوض می‌کنه؛ اول با هم تصمیم بگیرید. گاهی امن‌ترین راه این هست که branch تازه‌ای از main بساز و تغییرهای لازم رو انتخابی منتقل کنید، نه اینکه تاریخچه رو کورکورانه بازنویسی کنید.

If only Nazanin has the branch, the team can coordinate, bring in current main, reduce the change, and review again. If Sara has built on its commits, rebasing and force-pushing rewrites shared history; agree first. Sometimes the safest route is to create a fresh branch from main and selectively bring over the needed changes rather than rewriting history blindly.

این وضعیت همون چیزی هست که شاخهٔ کوتاه‌عمر، PR کوچک و CI زودهنگام کم می‌کنن: مدت زمانی که اختلاف بی‌صدا رشد می‌کنه. هیچ‌کدام تضمین نمی‌کنن تعارضی پیش نمیاد؛ فقط زودتر متوجه می‌شویم و هزینهٔ تصمیم کوچک‌تر هست.

This is what short-lived branches, small pull requests, and early CI reduce: the time divergence can grow unnoticed. None guarantees a conflict-free merge; they help us notice sooner, while the decision is smaller.

تمرین‌ها: انتخاب کن، بعد شاهدش رو بگوExercises: choose, then name your evidence

پاسخ رو فقط با اسم دستور تمام نکن. بگو چه چیزی رو انتظار داری ببینی و اون خروجی چه چیزی رو ثابت نمی‌کنه.

۱. شاخه چه چیزی رو جدا می‌کنه؟1. What does a branch isolate?

همکارت می‌گه branch یک نسخهٔ کامل دوم از همهٔ فایل‌هاست. با مدل این فصل توضیح بده دقیقاً چه چیزی نام‌گذاری می‌شه.

A teammate says a branch is a second complete copy of every file. Explain what the name actually points to.

توضیحExplanation

branch نامی متحرک برای یک commit هست. فایل‌های کاری هنگام checkout از درخت اون commit پر می‌شن، اما خود branch کپی مستقل پروژه نیست؛ با commit تازه جلو می‌ره.

A branch is a movable name for a commit. Checking it out populates the working tree from that commit, but the branch is not an independent project copy; new commits move it forward.

۲. چرا شاخه رو کوتاه نگه داریم؟2. Why keep a branch short-lived?

یک قابلیت کوچک روی شاخه‌ای هست که سه هفته به‌روز نشده. دو هزینهٔ محتمل رو نام ببر.

A small feature sits on a branch that has not been updated for three weeks. Name two likely costs.

پاسخ نمونهExample answer

تغییرات main در اون جمع نشدن، پس تعارض و ناسازگاری دیر دیده می‌شه؛ diff بزرگ‌تر هم بازبینی رو سخت می‌کنه. کوتاه‌بودن تضمین بی‌تعارضی نیست، اما زمان کشف رو جلو میاره.

Changes from main have not been integrated, so conflicts and incompatibilities surface late; a larger diff is harder to review too. Short-lived does not guarantee no conflict, but moves discovery earlier.

۳. سه‌نقطه چه می‌پرسه؟3. What does the three-dot diff ask?

در بازبینی، چرا `git diff main...قابلیت` معمولاً از مقایسهٔ مستقیم دو نوک شاخه مفیدتر هست؟

Why is `git diff main...feature` often more useful in review than comparing the two branch tips directly?

توضیحExplanation

سه‌نقطه تغییر قابلیت رو از merge-base مشترک نشون می‌ده، یعنی آنچه branch از زمان جداشدن آورده. این شکل جای خواندن diff و اجرای آزمون رو نمی‌گیره.

The three-dot form shows feature’s changes since the common merge base—what the branch introduced after diverging. It does not replace reading the diff and running checks.

۴. pull request کجای کار هست؟4. Where does a pull request fit?

درست یا نادرست: pull request یکی از دستورهای Git هست که commitها رو ادغام می‌کنه.

True or false: a pull request is a Git command that merges commits.

پاسخAnswer

نادرست. PR قابلیت میزبان مخزن برای پیشنهاد، گفت‌وگو، بازبینی و اتصال بررسی‌ها به تغییر هست. ادغام ممکن هست از همون رابط یا با روش دیگری انجام بشه.

False. A PR is a repository-host feature for proposing, discussing, reviewing, and attaching checks to a change. Integration may happen through that interface or another method.

۵. CI سبز دقیقاً چه می‌گه؟5. What exactly does green CI say?

آزمون‌ها روی commit A سبز شدن؛ بعد نویسنده یک commit دیگر push می‌کنه. آیا نتیجهٔ قبلی دربارهٔ commit تازه کافیه؟

Checks passed on commit A; then the author pushes another commit. Is the previous result enough for the new one?

دلیلReasoning

نه لزوماً. نتیجه برای همون revision و همون آزمون‌هاست. باید روی commit تازه یا ترکیب نهایی‌ای که merge می‌شه وضعیت تازه داشته باشیم؛ حتی اون هم فقط دامنهٔ همون آزمون‌ها رو پوشش می‌ده.

Not necessarily. The result belongs to that revision and those checks. Require a fresh status for the new commit or final merge candidate; even then, it covers only those checks.

۶. merge چه چیزی رو حفظ می‌کنه؟6. What does merge preserve?

شاخهٔ قابلیت بین راه یک commit مستقل از main داره. اگه اون رو merge کنی، چه اطلاعاتی می‌تونه در گراف بمونه که rebase خطی نشان نمی‌ده؟

The feature branch has an independent commit alongside main. What can remain visible in the graph after merge that a linear rebase does not show?

توضیحExplanation

merge می‌تونه هر دو خط تاریخچه و نقطهٔ ادغام رو با merge commit حفظ کنه. این برای فهم زمان و ترکیب مسیرها مفید هست؛ در عوض گراف شاخه‌ای‌تر می‌شه.

A merge can preserve both lines and their integration point through a merge commit. This can clarify how the lines came together, at the cost of a more branched graph.

۷. rebase چه چیزی رو عوض می‌کنه؟7. What does rebase change?

چرا بعد از `git rebase main` شناسهٔ commitهای شاخهٔ قابلیت عوض می‌شه؟

Why do feature commit IDs change after `git rebase main`?

توضیحExplanation

rebase commitها رو با والد تازه دوباره می‌سازه؛ commit بخشی از هویت خود رو از والدش می‌گیره، پس شناسهٔ تازه داره. پیامد همین بازنویسی هست که برای شاخهٔ مشترک خطر هماهنگی می‌سازه.

Rebase recreates commits with a new parent; a commit’s identity depends partly on its parent, so it gets a new ID. That rewrite is why shared branches require coordination.

۸. شاخهٔ مشترک رو rebase کنیم؟8. Rebase a shared branch?

سه نفر از commitهای یک branch استفاده کردن. قبل از force-push چه باید کرد؟

Three people have based work on commits in one branch. What should happen before any force-push?

پاسخ مسئولانهResponsible answer

اول وضعیت رو بررسی و با همه هماهنگ کنیم؛ rebase شناسه‌ها رو عوض می‌کنه و commitهای تازهٔ همکارها رو از تاریخچهٔ جایگزین‌شده جدا می‌کنه. شاید merge یا branch تازه و انتقال انتخابی تغییرها کم‌خطرتر باشه.

Inspect the state and coordinate with everyone first. Rebase changes IDs and leaves teammates’ new commits based on the replaced history. A merge or fresh branch with selected changes may be safer.

۹. تعارض رو از کجا شروع کنیم؟9. Where do you start with a conflict?

merge متوقف شده و چند فایل نامشخص‌اند. اولین دو شاهدی که می‌خوانی چیست؟

A merge stopped and several files are unclear. What are the first two pieces of evidence you inspect?

پاسخAnswer

`git وضعیت` برای فایل‌های درگیر و مرحلهٔ merge؛ بعد خود فایل و `git diff` تا نیاز دو تغییر رو بفهمم. انتخاب خودکار یک سمت بدون درک محتوا کافی نیست.

`git status` for affected files and merge state, then the file and `git diff` to understand both changes. Automatically choosing one side without understanding the content is not enough.

۱۰. `diff --check` چه چیزی رو ثابت نمی‌کنه؟10. What does `diff --check` not prove?

بعد از حل تعارض، `git diff --check` خروجی نداره. چه بررسی‌هایی هنوز لازم‌اند؟

After resolving a conflict, `git diff --check` prints nothing. What checks are still needed?

توضیحExplanation

باید diff محتوایی رو بخوانیم، آزمون مناسب رو اجرا کنیم و رفتار مورد انتظار رو بررسی کنیم. این دستور ابزار محدودِ فاصله و برخی خطاهای متنی هست، نه داور منطق برنامه.

Read the content diff, run suitable tests, and verify expected behaviour. This command checks a limited set of whitespace and text problems; it does not judge program logic.

۱۱. main رو protected کنیم؟11. Should we protect main?

تیم می‌خواد بازبینی و آزمون اجباری باشه. protection چه کمکی می‌کنه و چه کاری رو نمی‌کنه؟

The team wants review and checks to be required. What can branch protection help enforce, and what can it not do?

توضیحExplanation

تنظیم میزبان می‌تونه direct push یا merge بدون شرط‌های انتخاب‌شده رو محدود کنه (جزئیات وابسته به میزبان و دسترسی هست). اما بازبینی سطحی یا آزمون ناقص رو باکیفیت نمی‌کنه و باگ رو خودکار کشف نمی‌کنه.

Host settings can restrict direct pushes or merges that lack selected conditions, depending on host and permissions. They cannot make a shallow review or weak test suite effective, nor automatically discover bugs.

۱۲. Trunk-based مناسب هست؟12. Is trunk-based a fit?

تیمی می‌تونه تغییر کوچک رو چند بار در روز ادغام کنه و آزمون سریع داره. چه مزیتی می‌گیره و چه شرطی رو نباید نادیده بگیره؟

A team can integrate small changes several times a day and has fast tests. What benefit can it gain, and what prerequisite must it not ignore?

پاسخAnswer

واگرایی کم و بازخورد زودتر؛ اما لازمه آزمون‌های قابل‌اعتماد، تغییر کوچک و راه مدیریت قابلیت ناتمام داشته باشه. ادغام پرتکرار بدون این‌ها می‌تونه خرابی رو پرتکرار کنه.

Less divergence and earlier feedback. It needs trustworthy checks, small changes, and a way to manage unfinished features; frequent integration without these can make breakage frequent too.

۱۳. شاخهٔ انتشار دلیل داره؟13. Is there a reason for a release branch?

محصول هر روز منتشر می‌شه، اما تیم می‌خواد همیشه شاخه‌های `develop`، `انتشار` و `hotfix` داشته باشه. چه پرسشی قبل از انتخاب ساختار می‌پرسی؟

The product deploys daily, but the team wants permanent `develop`, `release`, and `hotfix` branches. What would you ask before adopting that structure?

پاسخAnswer

آیا واقعاً چند نسخهٔ پشتیبانی‌شده یا پنجرهٔ تثبیت جدا داریم؟ اگه نه، این شاخه‌ها ممکن هست واگرایی و ادغام تکراری بسازند؛ ساختار باید از نیاز نگهداری بیاد.

Do we actually maintain multiple versions or need separate stabilisation windows? If not, those branches may create divergence and repeated merges; structure should follow maintenance needs.

۱۴. tag با branch چه فرقی داره؟14. How does a tag differ from a branch?

بعد از `v1.0.0` commit تازه‌ای روی main میاد. کدام نام جلو می‌ره؟

A new commit lands on main after `v1.0.0`. Which name moves?

پاسخAnswer

branch اصلی با commit جلو می‌ره؛ tag نسخه معمولاً همون commit انتشار رو نام‌گذاری می‌کنه و خودبه‌خود جابه‌جا نمی‌شه. اگه tag منتشر شده، تغییرش رو بی‌هماهنگی انجام نده.

The main branch advances; the release tag normally continues to name its release commit. Do not move a published tag without coordination.

۱۵. شاخهٔ شخصی عقب هست15. A private branch is behind

فقط خودت روی شاخهٔ قابلیت کار کرده‌ای؛ main یک commit جلو رفته. اگه تاریخچهٔ خطی می‌خوای، چه انتخابی معقول هست و چه چیزی رو بعدش بازبینی می‌کنی؟

Only you have worked on the feature branch; main has one new commit. If you want linear history, what is a reasonable choice, and what do you inspect afterwards?

پاسخAnswer

می‌توان `git rebase main` کرد؛ بعد `git وضعیت`، گراف لاگ، diff نسبت به main و آزمون‌ها رو بررسی کرد. rebase تضمین نمی‌کنه تغییر معنایی درست مانده باشه.

`git rebase main` is reasonable; then inspect status, the log graph, the diff against main, and tests. Rebase does not guarantee the change still makes semantic sense.

۱۶. CI روی چه چیزی باید اجرا بشه؟16. What should CI run against?

یک PR سبز هست اما main بعد از آخرین اجرا commit تازه گرفته. برای merge چه شاهدی لازم داری؟

A PR is green, but main got another commit after its last run. What evidence do you want before merging?

توضیحExplanation

بسته به تنظیم میزبان، باید PR با main تازه به‌روز بشه یا merge queue / آزمون میزبان، ترکیب نهایی رو بررسی کنه. نتیجهٔ قدیمی روی ترکیب دیگر لزوماً نمایندهٔ چیزی نیست که واقعاً ادغام می‌شه.

Depending on host settings, update the PR with current main or use a merge queue/check that validates the final combination. An old result for a different combination may not represent what will actually merge.

۱۷. branch مشترک و force-push17. A shared branch and force-push

`git branch -vv` نشون می‌ده شاخه upstream داره و همکارت می‌گه اون رو pull کرده. تو می‌خوای rebase کنی. قبل از تغییر چه می‌کنی؟

`git branch -vv` shows an upstream, and your teammate says they pulled it. You want to rebase. What do you do before changing anything?

پاسخ مسئولانهResponsible answer

توقف، بررسی دقیق گراف و هماهنگی با همکار. upstream داشتن به‌تنهایی معلوم نمی‌کنه کسی وابسته هست، اما گفتهٔ همکار این وابستگی رو تأیید می‌کنه. merge یا شاخهٔ تازه رو هم مقایسه کن؛ force-push بی‌خبر نزن.

Pause, inspect the graph, and coordinate. An upstream alone does not prove anyone depends on the branch, but the teammate’s report does. Compare merging or creating a fresh branch; do not force-push silently.

۱۸. رخداد: PR بزرگ و نسخهٔ نزدیک18. Incident: a large PR and a nearby release

PR سه هفته‌ای، ۴۰ فایل و CI ناقص هست؛ فردا انتشار داری. برنامهٔ کم‌خطر تو چیست و چه چیزی رو عمداً کنار می‌گذاری؟

The PR is three weeks old, touches 40 files, and CI is incomplete; the release is tomorrow. What is your low-risk plan, and what do you deliberately avoid?

برنامهٔ نمونهExample plan

اول با نویسنده و reviewerها محدودهٔ لازم برای انتشار رو مشخص می‌کنم؛ اگه شد قابلیت رو به PRهای کوچک و مستقل تقسیم می‌کنم، main تازه رو وارد و CI رو برای commit نهایی اجرا می‌کنم. اگه کیفیت قابل‌اثبات نیست، انتشار رو عقب می‌اندازم یا قابلیت رو از انتشار جدا می‌کنم. تاریخچهٔ مشترک رو در دقیقهٔ آخر بی‌هماهنگی بازنویسی نمی‌کنم.

First agree with the author and reviewers on what the release actually needs. Split into smaller independent PRs if feasible, integrate current main, and run CI on the final candidate. If quality cannot be demonstrated, delay or exclude the feature. Do not rewrite shared history at the last minute without coordination.

یادداشت انتشار: تغییر رو قابل‌ردیابی تحویل بدهRelease note: hand off a traceable change

در مخزن تمرینی، بعد از حل تعارض مطمئن شو روی `main` هستی، درخت کاری تمیز هست و `git لاگ --oneline --graph --decorate --all` تغییرها رو نشون می‌ده. بعد annotated tag رو روی commit موردنظر بساز. در تیم واقعی، کنار PR کوتاه بنویس: چه تغییری کرد، چه آزمونی اجرا شد، نتیجه کجاست، و چه چیزی هنوز معلوم نیست.

In the practice repository, confirm you are on `main`, the working tree is clean, and `git log --oneline --graph --decorate --all` shows the integration. Then create an annotated tag on the intended commit. In a real team, leave a concise PR handoff: what changed, which checks ran, where the results are, and what remains unknown.

این یادداشت، خودِ انتشار نیست. هنوز باید artifact ساخته و در محیط مقصد بررسی بشه؛ این رو در فصل‌های بعد دنبال می‌کنیم. اما حالا می‌دونیم تغییرِ قابل‌انتشار از مسیر branch و بازبینی و CI می‌گذرد، و نام نسخه به یک commit مشخص برمی‌چرخه.

This note is not the release itself. An artifact still needs to be built and checked in its target environment; later chapters follow that path. But we now know a release candidate passes through a branch, review, and CI, and its version name points to a specific commit.

اگه فقط یک دقیقه وقت داریIf you have only one minute

تغییر رو کوچک و شاخه رو کوتاه نگه دار تا بازخورد زود برسه. در PR diff رو بخوان و نتیجهٔ CI رو برای همون commit نهایی بخواه. `merge` مسیرهای واقعی رو نگه می‌داره؛ `rebase` commitهای محلی رو دوباره می‌چینه و شناسه‌شان رو عوض می‌کنه. تاریخچهٔ مشترک رو بی‌هماهنگی بازنویسی نکن. tag نسخه رو بعد از انتخاب commit انتشار بساز.

Keep changes small and branches short so feedback arrives early. Read the PR diff and require CI for the final commit. Merge preserves the actual lines of history; rebase replays local commits and changes their IDs. Never rewrite shared history without coordination. Tag the chosen release commit.

قبل از هر merge یا rebase: `git وضعیت`، مقصد تغییر، افراد وابسته و شاهد آزمون رو روشن کن. اگه مطمئن نیستی، اول فقط بخوان و از هم‌تیمی بپرس.Before any merge or rebase: confirm status, target, dependent teammates, and test evidence. If unsure, inspect first and ask the people involved.

قدم بعد: بررسی رو هر بار دستی تکرار نکنیمNext: stop repeating checks by hand

حالا تغییر کوچک، بازبینی و نتیجهٔ آزمون رو به یک commit قابل‌ردیابی وصل کرده‌ایم؛ اما هنوز کسی باید هر بار lint، test و build رو به‌خاطر بسپارد و اجرا کنه. فصل بعد CI رو از صفر راه می‌ندازه تا همین شاهدها با هر تغییر، خودکار و تکرارپذیر تولید بشن.

We have connected a small change, review, and test result to a traceable commit. But someone still has to remember to run lint, tests, and build every time. Next, we will set up CI from scratch so each change produces this evidence automatically and repeatably.
