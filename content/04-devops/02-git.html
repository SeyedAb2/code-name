Git در عمل: branch، merge، rebaseGit in practice: branch, merge, rebase

یک تغییر کوچک آماده است، اما دو نفر هم‌زمان روی همان مخزن کار می‌کنند. چطور تغییر را بازبینی کنیم، زود به شاخهٔ اصلی برگردانیم و اگر چیزی گیر کرد، بی‌آنکه تاریخچهٔ هم‌تیمی را به‌هم بریزیم از آن بیرون بیاییم؟

A small change is ready, but two people are working in the same repository. How do we review it, bring it back to the main line promptly, and recover from trouble without disrupting a teammate’s history?

وقتی شاخه‌ها دیر به هم می‌رسندWhen branches meet too late

هفتهٔ پیش نازنین قابلیت پیام خوشامد را شروع کرد. امروز می‌خواهد آن را تحویل بدهد؛ اما از آن موقع سارا مسیر صفحهٔ اصلی را هم عوض کرده. حالا تغییر نازنین روی نسخه‌ای قدیمی از پروژه نشسته. «فقط merge کن» جواب کافی نیست: چقدر از هم دور شده‌اند و کدام نسخه باید واقعاً منتشر شود؟

Last week, Nazanin started a welcome-message feature. Today she is ready to hand it off, but Sara has changed the home page since then. Nazanin’s work now sits on an older version of the project. “Just merge it” is not enough: how far have the branches diverged, and which version should actually ship?

در فصل اول دیدیم انتشار یک مسیر پیوسته تا رسیدن بازخورد کاربر است. Git این مسیر را به‌تنهایی کامل نمی‌کند؛ کمک می‌کند خودِ تغییر قابل‌ردیابی، قابل‌بازبینی و برای ادغام آماده بماند. هرچه شاخه بیشتر جدا بماند، تفاوت‌های بیشتری جمع می‌شود و تعارض را دیرتر می‌بینیم.

Chapter 1 treated delivery as one path that continues until user feedback arrives. Git does not complete that path on its own; it helps keep a change traceable, reviewable, and ready to integrate. The longer a branch stays apart, the more differences accumulate—and the later we discover conflicts.

این شکل زمان را نشان می‌دهد، نه قانون قطعی: شاخهٔ کوتاه هم ممکن است تعارض داشته باشد؛ شاخهٔ بلند هم شاید بی‌تعارض ادغام شود. تفاوت این است که ادغام زودتر، ناسازگاری را زودتر به ما نشان می‌دهد و کوچک‌تر نگه‌داشتن تغییر، بررسی را آسان‌تر می‌کند.

The diagram shows a tendency, not a law: a short branch can still conflict, and a long one can merge cleanly. Integrating sooner exposes incompatibilities earlier, while smaller changes are easier to review.

یک تغییر، یک شاخهٔ کوتاه‌عمرOne change, one short-lived branch

برای قابلیت پیام خوشامد، اول وضعیت را می‌خوانیم تا چیزی را تصادفی روی کار نیمه‌تمام نسازیم. شاخهٔ اصلی را با نام تیم‌ها یکی فرض نکن؛ بعضی مخزن‌ها هنوز `master` دارند. این آزمایش مخزن تمرینی خودش را می‌سازد.

For the welcome feature, first inspect the state so we do not build on unfinished work by accident. Do not assume every repository calls its main branch `main`; some still use `master`. This experiment creates its own practice repository.

bash · disposable team repo
mkdir delivery-git-lab && cd delivery-git-lab
git init -b main
git config user.name 'Nazanin Example'
git config user.email 'nazanin@example.test'
printf 'Welcome\n' > home.txt
git add home.txt
git commit -m 'Add home page'
git switch -c feature/welcome-message
printf 'Welcome, team!\n' > home.txt
git add home.txt
git commit -m 'Personalise welcome message'
git status --short --branch
git log --oneline --decorate --graph --all

در خروجی `status` دنبال `feature/welcome-message` و working tree تمیز بگرد. در `log` باید commit قابلیت را بالای نقطهٔ شروع ببینی. این‌ها می‌گویند تغییر ثبت شده و کجای تاریخچه است؛ هنوز نمی‌گویند درست کار می‌کند یا هم‌تیمی آن را بازبینی کرده.

In `status`, look for `feature/welcome-message` and a clean working tree. In `log`, the feature commit should sit above the starting point. This tells us the change is recorded and where it sits in history; it does not tell us that it works or has been reviewed.

اگر Git قدیمی‌تر از نسخه‌ای است که `git switch` را می‌شناسد، می‌توانی در این آزمایش از `git checkout -b feature/welcome-message` استفاده کنی. در کار روزمره، اول `git status` را بخوان؛ اسم شاخه به‌تنهایی تضمین نمی‌کند جای درستی هستی.If your Git predates `git switch`, use `git checkout -b feature/welcome-message` for this experiment. In daily work, read `git status` first; a branch name alone does not guarantee you are in the right place.

شاخه یک کپی جدا از کل پروژه نیست؛ نامی است که به یک commit اشاره می‌کند. اینجا هدفش جداکردن یک تغییر محدود است تا ساخت و بازبینی‌اش مستقل بماند. وقتی مسیر تغییر روشن شد، شاخه را زود ادغام می‌کنیم و حذفش می‌کنیم؛ نه اینکه ماه‌ها شاخهٔ موازی بسازیم.

A branch is not a separate copy of the whole project; it is a name pointing to a commit. Here it isolates one bounded change so it can be built and reviewed independently. Once the change is integrated, merge it and remove the branch rather than maintaining a parallel line for months.

Pull request یعنی گفت‌وگو پیش از ادغامA pull request is a conversation before integration

نازنین حالا تغییر را push می‌کند و pull request باز می‌کند. در GitHub، pull request یک قابلیت میزبان مخزن است، نه دستور Git. تیم می‌تواند آنجا هدف تغییر، محدودیت‌ها، آزمون و چیزی را که reviewer باید بررسی کند بنویسد. در GitLab یا ابزار دیگر، نام و جزئیات صفحه فرق می‌کند؛ ایدهٔ بازبینی پیش از ادغام همان است.

Nazanin now pushes the change and opens a pull request. On GitHub, a pull request is a repository-hosting feature, not a Git command. The team can describe the intent, constraints, tests, and what reviewers should inspect. GitLab and other hosts use different names and interfaces; the idea of review before integration remains.

در یک مخزن محلی می‌توانیم شکل بررسی را با مقایسهٔ شاخه‌ها تمرین کنیم. اگر آن را به مخزن واقعی می‌بری، remote را فقط وقتی اضافه کن که آدرس درست و مجوز نوشتن داری؛ push کردن به remote واقعی بخشی از آزمایش بی‌خطر نیست.

In a local repository, we can practise the review shape by comparing branches. If you adapt this to a real repository, add a remote only when you have the correct URL and write permission; pushing to a real remote is not part of a harmless experiment.

bash · inspect before review
git diff main...feature/welcome-message
git diff --stat main...feature/welcome-message
git log --oneline main..feature/welcome-message

سه‌نقطه در `git diff main...feature/welcome-message` تغییر شاخهٔ قابلیت را از نقطهٔ مشترک دو شاخه نشان می‌دهد؛ `--stat` اندازهٔ تغییر و `log` commitهای جلوتر را نشان می‌دهد. برای فهمیدن کل وضعیت، باید خود diff را هم بخوانی و آزمون‌ها را اجرا کنی. تعداد خط کم، کیفیت را ثابت نمی‌کند.

In `git diff main...feature/welcome-message`, the three-dot form shows the feature branch’s changes since the branches’ common point; `--stat` gives the change size and `log` lists commits ahead. To understand the change, read the diff and run the checks too. A low line count does not prove quality.

بازبینی خوب دنبال «کد قشنگ است؟» نمی‌ماند: آیا رفتار خواسته‌شده را دارد؟ چه چیزی ممکن است بشکند؟ آزمون تازه چه چیزی را ثابت می‌کند؟ آیا راه بازگشت معلوم است؟ در تیم کوچک، حتی یک reviewer که سؤال درست بپرسد از ادغام بی‌چشم بهتر است.

A useful review asks more than “does the code look neat?” Does it implement the intended behavior? What could break? What does the new test prove? Is the way back understood? Even one thoughtful reviewer is better than merging without review.

در میزبان‌هایی مثل GitHub می‌توان main را protected کرد تا merge از مسیر pull request و شرط‌هایی مثل review یا status check بگذرد. جزئیات در هر میزبان و طرح اشتراک فرق دارد؛ protected branch خطای منطقی را خودکار پیدا نمی‌کند و جای آزمون را نمی‌گیرد.Hosts such as GitHub can protect `main` so changes go through pull requests and conditions such as reviews or status checks. Details vary by host and plan. Branch protection does not detect a logical bug or replace testing.

CI به PR چه کمکی می‌کند؟What does CI add to a pull request?

reviewer می‌گوید «روی سیستم من اجرا شد»؛ اما ما هنوز شاهدی نداریم که همان commit روی محیط تمیز build و test شده باشد. CI همین بررسی‌های تکراری را روی تغییر اجرا می‌کند و نتیجه را به همان pull request وصل می‌کند. فصل بعد خط لوله را می‌سازیم؛ اینجا فقط می‌خواهیم مرزش روشن باشد.

A reviewer says, “It ran on my machine,” but we still lack evidence that this exact commit was built and tested in a clean environment. CI runs repeatable checks on the change and attaches the result to the pull request. The next chapter builds the pipeline; here we only need to understand its role.

اگر commit بعد از سبزشدن آزمون عوض شود، نتیجهٔ قبلی لزوماً دربارهٔ نسخهٔ تازه چیزی نمی‌گوید. CI باید روی commit یا ترکیب نهایی‌ای که قرار است ادغام شود دوباره نتیجه بدهد. status check سبز هم فقط همان بررسی‌های تعریف‌شده را ثابت می‌کند؛ نه نبودن همهٔ خطاها را.

If the commit changes after checks pass, the old result does not necessarily say anything about the new revision. CI needs to report on the commit—or final combination—that is going to be merged. A green status check proves only that the configured checks passed, not that every defect is absent.

merge یا rebase؛ تاریخچه را برای چه کسی می‌خوانیم؟Merge or rebase: who is the history for?

سارا در همین زمان تغییر مستقلی به `main` ادغام کرده. شاخهٔ نازنین حالا عقب است. دو راه متداول داریم؛ هیچ‌کدام دکمهٔ جادویی برای «حل همهٔ تعارض‌ها» نیست.

Sara has meanwhile integrated an independent change into `main`. Nazanin’s branch is now behind. There are two common ways forward; neither is a magic “resolve all conflicts” button.

انتخابChoiceچه می‌کند؟What it doesمناسب وقتی…Useful when…مراقب چه باشیم؟Watch for…
merge mainدو خط تاریخچه را نگه می‌دارد و ممکن است merge commit بسازد.
Preserves both lines of history and may create a merge commit.		شاخه مشترک است، یا می‌خواهیم نقطهٔ ادغام آشکار بماند.
The branch is shared, or we want the integration point visible.		تاریخچه شاخه‌ای‌تر می‌شود.
History becomes more branched.
rebase maincommitهای محلی را روی نوک تازهٔ main دوباره می‌چیند؛ شناسهٔ آن‌ها عوض می‌شود.
Replays local commits on the latest main; their commit IDs change.		شاخه شخصی است و تاریخچهٔ خطی برای بازبینی می‌خواهیم.
The branch is private and a linear review history is useful.		تعارض ممکن است رخ دهد؛ بازنویسی شاخهٔ منتشرشده هماهنگی می‌خواهد.
Conflicts can still happen; rewriting a published branch needs coordination.

اگر شاخه هنوز فقط مال نازنین است، rebase می‌تواند commitهایش را روی `main` جدید بازچینی کند. اگر سارا هم آن شاخه را pull کرده و بر اساس commitهایش کار می‌کند، تغییر شناسه‌ها برای او تاریخچهٔ متفاوتی می‌سازد. در آن وضعیت، merge یا هماهنگی روشن معمولاً دردسر کمتری دارد. تاریخچهٔ مشترک را بی‌خبر force-push نمی‌کنیم.

If the branch still belongs only to Nazanin, rebase can replay its commits on the latest `main`. If Sara has pulled that branch and built work on its commits, the changed IDs create a different history for her. In that case, merging or explicit coordination is usually less disruptive. Never force-push rewritten shared history without coordination.

یک تمرین امن برای دیدن فرق: روی شاخهٔ شخصی یک commit بساز، روی `main` هم commitی مستقل اضافه کن، بعد `git rebase main` را اجرا کن. خروجی `git log --oneline --graph --decorate --all` نشان می‌دهد commit قابلیت حالا پس از commit تازهٔ main قرار گرفته. فایل‌ها را هم با `git diff main...HEAD` بررسی کن؛ شکل خطی گراف ثابت نمی‌کند رفتار برنامه درست است.

A safe way to see the difference: make a commit on a private branch, add an independent commit to `main`, then run `git rebase main`. `git log --oneline --graph --decorate --all` shows the feature commit now after the new main commit. Inspect files with `git diff main...HEAD` too; a linear graph does not prove the application behaves correctly.

در تعارض rebase، `git status` می‌گوید کدام فایل‌ها مانده‌اند. فایل را آگاهانه حل کن، `git add` بزن و `git rebase --continue` را اجرا کن؛ اگر تصمیم گرفتی متوقف شوی، `git rebase --abort` برمی‌گرداند به وضعیت پیش از همین rebase. قبل از ادامه، diff را بخوان؛ نشانگرهای تعارض نباید باقی مانده باشند.During a rebase conflict, `git status` identifies the remaining files. Resolve them deliberately, stage with `git add`, then run `git rebase --continue`; if you decide to stop, `git rebase --abort` returns to the state before this rebase. Read the diff before continuing and ensure conflict markers are gone.

تعارض، خبر بد نیست؛ تصمیمِ ثبت‌نشده استA conflict is not bad news; it is an undecided change

برای دیدنش دو نسخه از یک جمله را جداگانه تغییر می‌دهیم. این آزمایش فقط در مخزن دورریختنی ابتدای فصل انجام می‌شود؛ هرگز برای تمرین روی مخزن کاری یا فایل‌های بی‌پشتوانه دستورهای پاک‌کردن اجرا نکن.

To see one, we will change the same sentence independently. Run this only in the disposable repository created earlier; never practise destructive commands in a work repository or on files without a backup.

bash · deliberate conflict, local only
git switch main
printf 'Welcome, everyone.\n' > home.txt
git add home.txt && git commit -m 'Update home greeting'
git switch feature/welcome-message
printf 'Welcome, developers!\n' > home.txt
git add home.txt && git commit -m 'Address developers in greeting'
git switch main
git merge --no-ff feature/welcome-message

Git احتمالاً می‌گوید هر دو شاخه یک خط را متفاوت تغییر داده‌اند و merge کامل نشده. `git status` نام فایل متعارض را نشان می‌دهد؛ فایل را باز کن و تصمیم بگیر متن نهایی چه باشد. انتخاب سمت `ours` یا `theirs` بدون فهم نیاز محصول، حل تعارض نیست.

Git will likely report that both branches changed the same line differently and the merge is incomplete. `git status` names the conflicted file; open it and decide what the final text should say. Choosing `ours` or `theirs` without understanding the product need is not a real resolution.

bash · inspect and finish the merge
git status
# Edit home.txt and remove all <<<<<<<, =======, and >>>>>>> markers
git diff --check
git add home.txt
git diff --cached
git commit -m 'Merge welcome message'

`git diff --check` برای فاصله‌های ناسازگار و بعضی نشانگرهای حل‌نشده هشدار می‌دهد، اما صحت متن یا رفتار را نمی‌فهمد. `git diff --cached` محتوایی را نشان می‌دهد که قرار است commit شود. بعد از commit، با `git status --short --branch` تمیزی درخت و با `git log --graph` نتیجهٔ ادغام را بررسی کن.

`git diff --check` warns about whitespace problems and some unresolved markers, but it cannot judge the text or behaviour. `git diff --cached` shows what is about to be committed. After committing, use `git status --short --branch` to confirm a clean tree and `git log --graph` to inspect the merge.

اگر وسط merge متوجه شدی اشتباه شروعش کرده‌ای و هنوز commit نشده، `git merge --abort` معمولاً merge را کنار می‌گذارد. اگر فایل‌های محلیِ قبل از merge تغییر داشته‌اند، نتیجه را حدس نزن؛ قبل از هر اقدامی status و diff را بخوان.If you realise you started the wrong merge and have not committed, `git merge --abort` usually abandons it. If local files were already modified, do not guess what will happen; inspect status and diff before acting.

کدام راهبرد شاخه‌بندی به تیم می‌خورد؟Which branching style fits the team?

اسم راهبرد از تعداد branchها مهم‌تر نیست؛ زمان بازخورد، نوع انتشار و هزینهٔ ادغام مهم است. سه الگو را به‌عنوان نقطهٔ شروع ببین، نه مذهب تیمی.

The strategy’s name matters less than feedback time, release shape, and integration cost. Treat these three patterns as starting points, not team religions.

اگر تیم هر هفته چندبار به production می‌رود، شاخهٔ release طولانی شاید فقط فاصلهٔ بازخورد را زیاد کند. اگر نسخهٔ نصب‌شدهٔ مشتری باید ماه‌ها patch بگیرد، شاخهٔ پایدار می‌تواند دلیل واقعی داشته باشد. از نیاز انتشار شروع کن، نه از نمودار محبوب اینترنت.

If the team deploys several times a week, a long-lived release branch may only delay feedback. If customer-installed versions need patches for months, a stable branch may have a genuine purpose. Start with release needs, not a popular internet diagram.

release branch را فقط وقتی لازم است نگه دارKeep a release branch only when it is needed

وقتی باید یک نسخه را برای مدت مشخص تثبیت کنی، `release/2.4` می‌تواند محل رفع اشکال همان نسخه باشد؛ قابلیت‌های بعدی در مسیر اصلی می‌مانند. هر اصلاح لازم است به شاخهٔ اصلی هم برسد، وگرنه در نسخهٔ بعدی دوباره همان باگ برمی‌گردد. اگر چنین نیاز نگهداری نداری، شاخهٔ release دائمی فقط مسیر دیگری برای drift می‌سازد.

When a version must be stabilised for a period, `release/2.4` can hold fixes for that version while new features continue on the main line. Every relevant fix must also reach the main line or the bug may return in the next release. Without that maintenance need, a permanent release branch creates another place to drift.

ادغام شد؛ کدام نسخه را منتشر کردیم؟Merged; which version did we release?

بعد از ادغام، یک نام نسخه روی commit انتشار می‌گذاریم تا آدم‌ها و ابزارها به یک نقطهٔ مشخص اشاره کنند. tag همان branch نیست: branch با commitهای تازه جلو می‌رود؛ tag معمولاً نامی ثابت برای نسخهٔ منتشرشده است. برای نسخهٔ همراه توضیح، annotated tag بساز.

After integration, attach a version name to the release commit so people and tools can refer to one exact point. A tag is not a branch: a branch advances to newer commits; a tag is normally a fixed name for a release. Use an annotated tag when you want release metadata.

bash · tag the reviewed release commit
git switch main
git status --short --branch
git log -1 --oneline
git tag -a v1.0.0 -m 'Release 1.0.0'
git show --no-patch --decorate v1.0.0

پیش از tag، مطمئن شو روی commit نهایی main هستی و تغییر محلیِ ناخواسته نداری. `git show` باید پیام tag و commit هدف را نشان دهد. این نام‌گذاری کمک می‌کند release را دوباره پیدا کنیم؛ به‌تنهایی ثابت نمی‌کند artifact واقعاً همان commit است یا production سالم است. اگر مخزن remote دارد، tag را با دستور جداگانه push می‌کنند و باید مجوز و مقصد را دوباره بررسی کرد.

Before tagging, confirm you are on the final `main` commit with no unintended local changes. `git show` should display the tag message and target commit. This makes the release easier to find; it does not prove an artifact was built from that commit or that production is healthy. In a remote repository, tags are pushed separately, so verify the destination and permissions first.

اگر tag را اشتباه ساخته‌ای، قبل از جابه‌جایی یا حذفش بررسی کن آیا قبلاً منتشر شده و کسی به آن تکیه کرده است. tag منتشرشده هم بخشی از قرارداد نسخه است؛ بی‌خبر عوض‌کردنش می‌تواند هم‌تیمی یا سامانهٔ انتشار را سردرگم کند.If you created the wrong tag, check whether it has already been published and used before moving or deleting it. A published tag is part of the release contract; silently changing it can confuse teammates or deployment systems.

دردسر واقعی: شاخه سه هفته باز ماندهA real snag: the branch has been open for three weeks

نازنین می‌گوید «فقط یک conflict دارم»؛ اما diff صدها خط دارد و سارا می‌گوید branch را قبلاً pull کرده. هنوز `rebase` یا `push --force` نزن. اول شواهد را جمع کن: روی کدام شاخه‌ایم، چند commit اختلاف هست، چه فایل‌هایی عوض شده‌اند و آیا کسی از commitهای branch استفاده می‌کند؟

Nazanin says, “I only have one conflict,” but the diff is hundreds of lines and Sara says she already pulled the branch. Do not run `rebase` or `push --force` yet. Gather evidence first: which branch are we on, how many commits differ, what files changed, and is anyone depending on this branch?

bash · read-only diagnosis first
git status --short --branch
git fetch origin
git log --oneline --graph --decorate --left-right origin/main...HEAD
git diff --stat origin/main...HEAD
git branch -vv

`fetch` فقط اطلاعات remote را به‌روز می‌کند و working tree را merge نمی‌کند. علامت‌های `<` و `>` در log می‌گویند کدام commit در یک طرف است؛ `diff --stat` اندازهٔ تغییر را خلاصه می‌کند؛ `branch -vv` وضعیت upstream را نشان می‌دهد. این‌ها میزان واگرایی را روشن می‌کنند، اما نمی‌گویند چه کسی branch را pull کرده؛ آن را از هم‌تیمی‌ها بپرس.

`fetch` updates remote-tracking information without merging into the working tree. The `<` and `>` markers in the log show which commits belong to each side; `diff --stat` summarises change size; `branch -vv` shows upstream status. These reveal divergence but cannot tell us who has pulled the branch—ask teammates directly.

اگر branch فقط نزد نازنین است، با هماهنگی می‌شود تغییر را کوچک کرد، main تازه را آورد و سپس بازبینی را از نو انجام داد. اگر سارا روی commitهایش کار کرده، rebase کردن و force-push تاریخچهٔ مشترک را عوض می‌کند؛ اول با هم تصمیم بگیرید. گاهی امن‌ترین راه این است که branch تازه‌ای از main بسازید و تغییرهای لازم را انتخابی منتقل کنید، نه اینکه تاریخچه را کورکورانه بازنویسی کنید.

If only Nazanin has the branch, the team can coordinate, bring in current main, reduce the change, and review again. If Sara has built on its commits, rebasing and force-pushing rewrites shared history; agree first. Sometimes the safest route is to create a fresh branch from main and selectively bring over the needed changes rather than rewriting history blindly.

این وضعیت همان چیزی است که شاخهٔ کوتاه‌عمر، PR کوچک و CI زودهنگام کم می‌کنند: مدت زمانی که اختلاف بی‌صدا رشد می‌کند. هیچ‌کدام تضمین نمی‌کنند تعارضی پیش نمی‌آید؛ فقط زودتر متوجه می‌شویم و هزینهٔ تصمیم کوچک‌تر است.

This is what short-lived branches, small pull requests, and early CI reduce: the time divergence can grow unnoticed. None guarantees a conflict-free merge; they help us notice sooner, while the decision is smaller.

تمرین‌ها: انتخاب کن، بعد شاهدش را بگوExercises: choose, then name your evidence

پاسخ را فقط با اسم دستور تمام نکن. بگو چه چیزی را انتظار داری ببینی و آن خروجی چه چیزی را ثابت نمی‌کند.

Do not stop at the command’s name. Say what you expect to see and what that output cannot prove.

۱. شاخه چه چیزی را جدا می‌کند؟1. What does a branch isolate?

توضیحExplanation

branch نامی متحرک برای یک commit است. فایل‌های کاری هنگام checkout از درخت آن commit پر می‌شوند، اما خود branch کپی مستقل پروژه نیست؛ با commit تازه جلو می‌رود.

A branch is a movable name for a commit. Checking it out populates the working tree from that commit, but the branch is not an independent project copy; new commits move it forward.

۲. چرا شاخه را کوتاه نگه داریم؟2. Why keep a branch short-lived?

یک قابلیت کوچک روی شاخه‌ای است که سه هفته به‌روز نشده. دو هزینهٔ محتمل را نام ببر.

پاسخ نمونهExample answer

تغییرات main در آن جمع نشده‌اند، پس تعارض و ناسازگاری دیر دیده می‌شود؛ diff بزرگ‌تر هم بازبینی را سخت می‌کند. کوتاه‌بودن تضمین بی‌تعارضی نیست، اما زمان کشف را جلو می‌آورد.

Changes from main have not been integrated, so conflicts and incompatibilities surface late; a larger diff is harder to review too. Short-lived does not guarantee no conflict, but moves discovery earlier.

۳. سه‌نقطه چه می‌پرسد؟3. What does the three-dot diff ask?

توضیحExplanation

سه‌نقطه تغییر feature را از merge-base مشترک نشان می‌دهد، یعنی آنچه branch از زمان جداشدن آورده. این شکل جای خواندن diff و اجرای آزمون را نمی‌گیرد.

The three-dot form shows feature’s changes since the common merge base—what the branch introduced after diverging. It does not replace reading the diff and running checks.

۴. pull request کجای کار است؟4. Where does a pull request fit?

درست یا نادرست: pull request یکی از دستورهای Git است که commitها را ادغام می‌کند.

True or false: a pull request is a Git command that merges commits.

پاسخAnswer

نادرست. PR قابلیت میزبان مخزن برای پیشنهاد، گفت‌وگو، review و اتصال بررسی‌ها به تغییر است. ادغام ممکن است از همان رابط یا با روش دیگری انجام شود.

False. A PR is a repository-host feature for proposing, discussing, reviewing, and attaching checks to a change. Integration may happen through that interface or another method.

۵. CI سبز دقیقاً چه می‌گوید؟5. What exactly does green CI say?

آزمون‌ها روی commit A سبز شده‌اند؛ بعد نویسنده یک commit دیگر push می‌کند. آیا نتیجهٔ قبلی دربارهٔ commit تازه کافی است؟

Checks passed on commit A; then the author pushes another commit. Is the previous result enough for the new one?

دلیلReasoning

نه لزوماً. نتیجه برای همان revision و همان آزمون‌هاست. باید روی commit تازه یا ترکیب نهایی‌ای که merge می‌شود status تازه داشته باشیم؛ حتی آن هم فقط دامنهٔ همان آزمون‌ها را پوشش می‌دهد.

Not necessarily. The result belongs to that revision and those checks. Require a fresh status for the new commit or final merge candidate; even then, it covers only those checks.

۶. merge چه چیزی را حفظ می‌کند؟6. What does merge preserve?

شاخهٔ feature بین راه یک commit مستقل از main دارد. اگر آن را merge کنی، چه اطلاعاتی می‌تواند در گراف بماند که rebase خطی نشان نمی‌دهد؟

The feature branch has an independent commit alongside main. What can remain visible in the graph after merge that a linear rebase does not show?

توضیحExplanation

merge می‌تواند هر دو خط تاریخچه و نقطهٔ ادغام را با merge commit حفظ کند. این برای فهم زمان و ترکیب مسیرها مفید است؛ در عوض گراف شاخه‌ای‌تر می‌شود.

A merge can preserve both lines and their integration point through a merge commit. This can clarify how the lines came together, at the cost of a more branched graph.

۷. rebase چه چیزی را عوض می‌کند؟7. What does rebase change?

چرا بعد از `git rebase main` شناسهٔ commitهای شاخهٔ قابلیت عوض می‌شود؟

Why do feature commit IDs change after `git rebase main`?

توضیحExplanation

rebase commitها را با والد تازه دوباره می‌سازد؛ commit بخشی از هویت خود را از والدش می‌گیرد، پس شناسهٔ تازه دارد. پیامد همین بازنویسی است که برای شاخهٔ مشترک خطر هماهنگی می‌سازد.

Rebase recreates commits with a new parent; a commit’s identity depends partly on its parent, so it gets a new ID. That rewrite is why shared branches require coordination.

۸. شاخهٔ مشترک را rebase کنیم؟8. Rebase a shared branch?

سه نفر از commitهای یک branch استفاده کرده‌اند. پیش از force-push چه باید کرد؟

Three people have based work on commits in one branch. What should happen before any force-push?

پاسخ مسئولانهResponsible answer

اول وضعیت را بررسی و با همه هماهنگ کنیم؛ rebase شناسه‌ها را عوض می‌کند و commitهای تازهٔ همکارها را از تاریخچهٔ جایگزین‌شده جدا می‌کند. شاید merge یا branch تازه و انتقال انتخابی تغییرها کم‌خطرتر باشد.

Inspect the state and coordinate with everyone first. Rebase changes IDs and leaves teammates’ new commits based on the replaced history. A merge or fresh branch with selected changes may be safer.

۹. تعارض را از کجا شروع کنیم؟9. Where do you start with a conflict?

merge متوقف شده و چند فایل نامشخص‌اند. اولین دو شاهدی که می‌خوانی چیست؟

A merge stopped and several files are unclear. What are the first two pieces of evidence you inspect?

پاسخAnswer

`git status` for affected files and merge state, then the file and `git diff` to understand both changes. Automatically choosing one side without understanding the content is not enough.

۱۰. `diff --check` چه چیزی را ثابت نمی‌کند؟10. What does `diff --check` not prove?

توضیحExplanation

Read the content diff, run suitable tests, and verify expected behaviour. This command checks a limited set of whitespace and text problems; it does not judge program logic.

۱۱. main را protected کنیم؟11. Should we protect main?

تیم می‌خواهد review و آزمون اجباری باشد. protection چه کمکی می‌کند و چه کاری را نمی‌کند؟

توضیحExplanation

تنظیم میزبان می‌تواند direct push یا merge بدون شرط‌های انتخاب‌شده را محدود کند (جزئیات وابسته به میزبان و دسترسی است). اما review سطحی یا آزمون ناقص را باکیفیت نمی‌کند و باگ را خودکار کشف نمی‌کند.

Host settings can restrict direct pushes or merges that lack selected conditions, depending on host and permissions. They cannot make a shallow review or weak test suite effective, nor automatically discover bugs.

۱۲. Trunk-based مناسب است؟12. Is trunk-based a fit?

تیمی می‌تواند تغییر کوچک را چند بار در روز ادغام کند و آزمون سریع دارد. چه مزیتی می‌گیرد و چه شرطی را نباید نادیده بگیرد؟

پاسخAnswer

واگرایی کم و feedback زودتر؛ اما لازم است آزمون‌های قابل‌اعتماد، تغییر کوچک و راه مدیریت قابلیت ناتمام داشته باشد. ادغام پرتکرار بدون این‌ها می‌تواند خرابی را پرتکرار کند.

Less divergence and earlier feedback. It needs trustworthy checks, small changes, and a way to manage unfinished features; frequent integration without these can make breakage frequent too.

۱۳. release branch دلیل دارد؟13. Is there a reason for a release branch?

محصول هر روز منتشر می‌شود، اما تیم می‌خواهد همیشه شاخه‌های `develop`، `release` و `hotfix` داشته باشد. چه پرسشی پیش از انتخاب ساختار می‌پرسی؟

The product deploys daily, but the team wants permanent `develop`, `release`, and `hotfix` branches. What would you ask before adopting that structure?

پاسخAnswer

Do we actually maintain multiple versions or need separate stabilisation windows? If not, those branches may create divergence and repeated merges; structure should follow maintenance needs.

۱۴. tag با branch چه فرقی دارد؟14. How does a tag differ from a branch?

بعد از `v1.0.0` commit تازه‌ای روی main می‌آید. کدام نام جلو می‌رود؟

A new commit lands on main after `v1.0.0`. Which name moves?

پاسخAnswer

branch اصلی با commit جلو می‌رود؛ tag نسخه معمولاً همان commit انتشار را نام‌گذاری می‌کند و خودبه‌خود جابه‌جا نمی‌شود. اگر tag منتشر شده، تغییرش را بی‌هماهنگی انجام نده.

The main branch advances; the release tag normally continues to name its release commit. Do not move a published tag without coordination.

۱۵. شاخهٔ شخصی عقب است15. A private branch is behind

فقط خودت روی شاخهٔ قابلیت کار کرده‌ای؛ main یک commit جلو رفته. اگر تاریخچهٔ خطی می‌خواهی، چه انتخابی معقول است و چه چیزی را بعدش بازبینی می‌کنی؟

Only you have worked on the feature branch; main has one new commit. If you want linear history, what is a reasonable choice, and what do you inspect afterwards?

پاسخAnswer

می‌توان `git rebase main` کرد؛ سپس `git status`، گراف log، diff نسبت به main و آزمون‌ها را بررسی کرد. rebase تضمین نمی‌کند تغییر معنایی درست مانده باشد.

`git rebase main` is reasonable; then inspect status, the log graph, the diff against main, and tests. Rebase does not guarantee the change still makes semantic sense.

۱۶. CI روی چه چیزی باید اجرا شود؟16. What should CI run against?

یک PR سبز است اما main بعد از آخرین اجرا commit تازه گرفته. برای merge چه شاهدی لازم داری؟

A PR is green, but main got another commit after its last run. What evidence do you want before merging?

توضیحExplanation

بسته به تنظیم میزبان، باید PR با main تازه به‌روز شود یا merge queue / آزمون میزبان، ترکیب نهایی را بررسی کند. نتیجهٔ قدیمی روی ترکیب دیگر لزوماً نمایندهٔ چیزی نیست که واقعاً ادغام می‌شود.

Depending on host settings, update the PR with current main or use a merge queue/check that validates the final combination. An old result for a different combination may not represent what will actually merge.

۱۷. branch مشترک و force-push17. A shared branch and force-push

`git branch -vv` نشان می‌دهد شاخه upstream دارد و همکارت می‌گوید آن را pull کرده. تو می‌خواهی rebase کنی. قبل از تغییر چه می‌کنی؟

`git branch -vv` shows an upstream, and your teammate says they pulled it. You want to rebase. What do you do before changing anything?

پاسخ مسئولانهResponsible answer

توقف، بررسی دقیق گراف و هماهنگی با همکار. upstream داشتن به‌تنهایی معلوم نمی‌کند کسی وابسته است، اما گفتهٔ همکار این وابستگی را تأیید می‌کند. merge یا شاخهٔ تازه را هم مقایسه کن؛ force-push بی‌خبر نزن.

Pause, inspect the graph, and coordinate. An upstream alone does not prove anyone depends on the branch, but the teammate’s report does. Compare merging or creating a fresh branch; do not force-push silently.

۱۸. incident: PR بزرگ و نسخهٔ نزدیک18. Incident: a large PR and a nearby release

PR سه هفته‌ای، ۴۰ فایل و CI ناقص است؛ فردا release دارید. برنامهٔ کم‌خطر تو چیست و چه چیزی را عمداً کنار می‌گذاری؟

The PR is three weeks old, touches 40 files, and CI is incomplete; the release is tomorrow. What is your low-risk plan, and what do you deliberately avoid?

برنامهٔ نمونهExample plan

اول با نویسنده و reviewerها محدودهٔ لازم برای release را مشخص می‌کنم؛ اگر شد قابلیت را به PRهای کوچک و مستقل تقسیم می‌کنم، main تازه را وارد و CI را برای commit نهایی اجرا می‌کنم. اگر کیفیت قابل‌اثبات نیست، انتشار را عقب می‌اندازم یا قابلیت را از release جدا می‌کنم. تاریخچهٔ مشترک را در دقیقهٔ آخر بی‌هماهنگی بازنویسی نمی‌کنم.

First agree with the author and reviewers on what the release actually needs. Split into smaller independent PRs if feasible, integrate current main, and run CI on the final candidate. If quality cannot be demonstrated, delay or exclude the feature. Do not rewrite shared history at the last minute without coordination.

یادداشت انتشار: تغییر را قابل‌ردیابی تحویل بدهRelease note: hand off a traceable change

در مخزن تمرینی، پس از حل تعارض مطمئن شو روی `main` هستی، درخت کاری تمیز است و `git log --oneline --graph --decorate --all` تغییرها را نشان می‌دهد. سپس annotated tag را روی commit موردنظر بساز. در تیم واقعی، کنار PR کوتاه بنویس: چه تغییری کرد، چه آزمونی اجرا شد، نتیجه کجاست، و چه چیزی هنوز معلوم نیست.

In the practice repository, confirm you are on `main`, the working tree is clean, and `git log --oneline --graph --decorate --all` shows the integration. Then create an annotated tag on the intended commit. In a real team, leave a concise PR handoff: what changed, which checks ran, where the results are, and what remains unknown.

این یادداشت، خودِ انتشار نیست. هنوز باید artifact ساخته و در محیط مقصد بررسی شود؛ این را در فصل‌های بعد دنبال می‌کنیم. اما حالا می‌دانیم تغییرِ قابل‌انتشار از مسیر branch و review و CI می‌گذرد، و نام نسخه به یک commit مشخص برمی‌گردد.

This note is not the release itself. An artifact still needs to be built and checked in its target environment; later chapters follow that path. But we now know a release candidate passes through a branch, review, and CI, and its version name points to a specific commit.

اگر فقط یک دقیقه وقت داریIf you have only one minute

تغییر را کوچک و شاخه را کوتاه نگه دار تا feedback زود برسد. در PR diff را بخوان و نتیجهٔ CI را برای همان commit نهایی بخواه. `merge` مسیرهای واقعی را نگه می‌دارد؛ `rebase` commitهای محلی را دوباره می‌چیند و شناسه‌شان را عوض می‌کند. تاریخچهٔ مشترک را بی‌هماهنگی بازنویسی نکن. tag نسخه را پس از انتخاب commit انتشار بساز.

Keep changes small and branches short so feedback arrives early. Read the PR diff and require CI for the final commit. Merge preserves the actual lines of history; rebase replays local commits and changes their IDs. Never rewrite shared history without coordination. Tag the chosen release commit.

قبل از هر merge یا rebase: `git status`، مقصد تغییر، افراد وابسته و شاهد آزمون را روشن کن. اگر مطمئن نیستی، اول فقط بخوان و از هم‌تیمی بپرس.Before any merge or rebase: confirm status, target, dependent teammates, and test evidence. If unsure, inspect first and ask the people involved.

قدم بعد: بررسی را هر بار دستی تکرار نکنیمNext: stop repeating checks by hand

حالا تغییر کوچک، بازبینی و نتیجهٔ آزمون را به یک commit قابل‌ردیابی وصل کرده‌ایم؛ اما هنوز کسی باید هر بار lint، test و build را به‌خاطر بسپارد و اجرا کند. فصل بعد CI را از صفر راه می‌اندازد تا همین شاهدها با هر تغییر، خودکار و تکرارپذیر تولید شوند.

We have connected a small change, review, and test result to a traceable commit. But someone still has to remember to run lint, tests, and build every time. Next, we will set up CI from scratch so each change produces this evidence automatically and repeatably.
