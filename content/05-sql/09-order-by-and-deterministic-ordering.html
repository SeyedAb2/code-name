ORDER BY و ترتیب قابل‌اعتماد

ORDER BY and deterministic ordering

فایل سفارش یک بار با ترتیب تاریخ میاد و بار دیگر ردیف‌ها جابه‌جا شده‌اند. برنامه هم می‌گه «SQL Server قاطی کرده». اما query اصلاً ترتیب خواسته بود؟ این بار قرارداد ترتیب رو صریح می‌نویسیم و tieها رو هم نادیده نمی‌گیریم.

An order export arrives sorted by date once, then rows move around on the next run. The application blames SQL Server—but did the query request an order at all? We will define the ordering contract and account for ties.

از یک سؤال واقعی شروع کنیمStart with a real question

یه همکار تازه‌وارد معمولاً SQL رو از روی syntax حفظ می‌کنه؛ ولی چند روز بعد که گزارش واقعی می‌رسه، نمی‌دونه از کجا شروع کنه. اینجا برعکس می‌ریم. اول سؤال گزارش رو روشن می‌کنیم، بعد برای «ORDER BY و ترتیب قابل‌اعتماد» query می‌نویسیم، خروجی رو نگاه می‌کنیم و اگه چیزی عجیب بود از روی همون نتیجه می‌فهمیم کجای مدل ذهنی‌مون ایراد داره.

A newcomer often memorises SQL syntax, then gets stuck on the first real report. We do the opposite: clarify the reporting question, use “ORDER BY and deterministic ordering” to answer it, inspect the result, and use any surprise as evidence that our mental model needs work.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

ردیف‌ها بدون درخواست مرتب‌سازی قولی نمی‌دهند / Rows make no ordering promise by default

جدول رابطه‌ای مجموعه‌ای از ردیف‌هاست، نه فهرست مرتب‌شده. اگه SELECT بدون ORDER BY اجرا بشه، ممکنه امروز خروجی ظاهراً مرتب باشه؛ plan، index، parallelism یا تغییر داده می‌تونه ترتیب مشاهده‌شده رو عوض کند. ترتیب قابل‌اتکا رو فقط ORDER BY در همان query درخواست می‌کنه.

A relational table is a set of rows, not a sorted list. A SELECT without ORDER BY may look ordered today; a different plan, index, parallelism, or data change can alter that observed order. Only ORDER BY in the query requests a result order.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

نام شهرها بدون قرارداد / Cities without an ordering contract
SELECT CustomerId, City
FROM shop.Customers;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

هر ترتیبی که ابزار نشان دهد، قرارداد query نیست. اگه کاربر می‌خواد نام شهر مرتب باشه، درخواست رو صریح کن. در خروجی‌های test هم ترتیب رو بنویس تا آزمون flaky نشه.

Whatever order the client displays is not a query contract. If users need cities sorted, ask for it explicitly. Tests should also define order to avoid flaky assertions.

یک کلید مرتب‌سازی همیشه tie رو نمی‌شکند / One sort key may leave ties

ORDER BY City شهرها رو مرتب می‌کنه؛ اما دو مشتری تهران برابرند. SQL Server برای ردیف‌هایی که همهٔ کلیدهای ORDER BYشان برابر هست ترتیب نهایی تضمین نمی‌کنه. کلید دوم اضافه کن و اگه پایداری کامل می‌خوای، تا یک کلید یکتا ادامه بده.

ORDER BY City sorts cities, but the two Tehran customers tie. SQL Server does not guarantee an internal order for rows equal on all ORDER BY keys. Add a second key and continue to a unique key when deterministic ordering matters.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

شکستن tie با شناسه / Break ties with an ID
SELECT CustomerId, City, FullName
FROM shop.Customers
ORDER BY City ASC, CustomerId ASC;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

ASC جهت پیش‌فرض است؛ می‌توانی اون رو بنویسی تا intent خواناتر بشه. DESC جهت رو برعکس می‌کنه. ترتیب چندکلیدی از چپ به راست هست: اول City، بعد فقط میان شهرهای برابر CustomerId.

ASC is the default direction, though writing it can make intent clearer. DESC reverses a key. Multi-column ordering is left to right: first City, then CustomerId among equal cities.

ترتیب می‌تونه از alias بیاید، ولی شمارهٔ ستون رو ترجیح نده / Sort by aliases, avoid positional ordinals

ORDER BY می‌تونه alias ساخته‌شده در SELECT رو بخواند؛ پس خروجی محاسباتی هم قابل‌مرتب‌سازی هست. نوشتن ORDER BY 2 هم در SQL Server کار می‌کنه، اما اگه فردا ستون دوم SELECT عوض بشه معنای مرتب‌سازی بی‌صدا عوض می‌شه. نام رو ترجیح بده. مرتب‌سازی متن هم تابع collation مؤثر هست.

ORDER BY can reference an alias from SELECT, including a calculated output. ORDER BY 2 also works, but changing the second SELECT column silently changes the sort. Prefer a name. Text ordering follows the effective collation.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

alias خوانا و ترتیب عددی / A named alias and numeric order
SELECT ProductName, UnitPrice * 0.9 AS DiscountPrice
FROM shop.Products
ORDER BY DiscountPrice ASC, ProductName ASC;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

اگه دو محصول قیمت محاسباتی برابر داشته باشند، نام tie رو می‌شکند. این نتیجهٔ مرتب‌شده است، نه اینکه قیمت‌ها در table عوض شده‌اند یا optimizer الزاماً به روش خاصی sort کرده.

If two products share a calculated price, name breaks the tie. This is an ordered result, not a table update or a guarantee of a particular physical sort implementation.

ترتیب کاری ممکنه الفبایی نباشه / Business order may not be alphabetical

وضعیت Pending، Paid و Cancelled ممکنه ترتیب کاری مشخصی داشته باشه. مرتب‌سازی الفبایی الزام گزارش رو بیان نمی‌کنه. با CASE در ORDER BY رتبهٔ مطلوب رو مشخص کن؛ فصل expressions بعداً CASE رو عمیق‌تر می‌کنه.

Pending, Paid, and Cancelled may have a business-defined sequence. Alphabetical order does not express that requirement. Use CASE in ORDER BY to assign the desired rank; a later expressions chapter explores CASE further.

ترتیب status برای تیم عملیات / Operational status order
SELECT OrderId, OrderStatus
FROM shop.Orders
ORDER BY CASE OrderStatus
           WHEN 'Pending' THEN 1
           WHEN 'Paid' THEN 2
           WHEN 'Cancelled' THEN 3
         END,
         OrderId;
GO

OrderId ترتیب درون هر گروه رو قطعی می‌کنه. اگه ردیفی status ناشناخته داشته باشه CASE اون رو NULL می‌سازه؛ در schema دادهٔ تمرینی این اتفاق با CHECK محدود شده، ولی در دادهٔ واقعی integrity رو هم بررسی کن.

OrderId makes order within each group deterministic. An unexpected status would yield NULL from CASE; the fixture constrains status, but inspect integrity in real data too.
