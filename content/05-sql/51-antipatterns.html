ضدالگوها: عادت‌هایی که هزینهٔ پنهان دارن

Anti-patterns: habits with hidden costs

در محیط توسعه query سریع است؛ روی production گزارش ناقص و متناقض می‌شه. کسی `NOLOCK` رو پیشنهاد می‌کنه. جایی دیگر `DISTINCT` جمع‌های اشتباه رو پنهان می‌کنه. این فصل فهرست ممنوعیت نیست: هر میان‌بُر رو می‌پرسیم چه مسئله‌ای حل می‌کنه و چه تضمینی رو قربانی می‌کنه.

A query is fast in development; in production the report is incomplete and inconsistent. Someone proposes NOLOCK. Elsewhere, DISTINCT hides inflated totals. This is not a ban list: for every shortcut, ask what it solves and which guarantee it sacrifices.

قبل از tuning، شاهد می‌خوایمBefore tuning, collect evidence

کاربر می‌گه «گزارش کند شده» و اولین وسوسه اینه که یه index بسازیم یا query رو از نو بنویسیم. نکن. توی «ضدالگوها: عادت‌هایی که هزینهٔ پنهان دارن» اول خط پایه می‌گیریم، بعد plan و تعداد ردیف و I/O رو می‌خونیم، یک فرضیه می‌سازیم و فقط یک چیز رو عوض می‌کنیم. اگه بهتر شد باید بتونیم بگیم چرا؛ اگه بدتر شد هم باید مدرک داشته باشیم.

A user says “the report is slow” and the first temptation is to add an index or rewrite the query. Do not. In “Anti-patterns: habits with hidden costs” we capture a baseline, read the plan and row counts, form one hypothesis, and change one thing. If it improves, we must explain why; if it regresses, we still need evidence.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

SELECT * قرارداد خروجی رو مبهم و پرهزینه می‌کنه / SELECT * makes output contracts broad and fragile

ستون‌های اضافی شبکه، حافظه و احتمال lookup رو زیاد می‌کنن؛ schema change هم می‌تونه خروجی client رو ناخواسته عوض کند. projection صریح خوانایی و امکان پوشش index رو بهتر می‌کنه. برای exploratory query یا ابزار داخلی شاید موقتاً اشکالی نداشته باشه؛ API و گزارش پایدار باید ستون لازم رو دقیق نام ببرد.

Extra columns increase network, memory, and possible lookup work; schema changes can unexpectedly alter client output. Explicit projection improves clarity and index coverage. SELECT * may be fine for temporary exploration, but stable APIs and reports should name required columns.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

خروجی موردنیاز رو صریح کن / Make the output explicit
-- Broad, fragile projection
SELECT * FROM Lab42.Ticket WHERE TenantId=7;
-- Stable projection
SELECT TicketId, Status, CreatedAt
FROM Lab42.Ticket WHERE TenantId=7;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

قبل از حذف ستون از projection، مصرف‌کننده و درستی رو بررسی کن. queryهای diagnostic یک‌باره از قرارداد API جدا هستن.

Before removing a projected column, check consumers and correctness. One-off diagnostic queries are different from an API contract.

NOLOCK می‌تونه دادهٔ نادرست بخواند؛ راه‌حل عمومی blocking نیست / NOLOCK can read inconsistent data; it is not a general blocking fix

READ UNCOMMITTED/NOLOCK ممکنه dirty data، rowهای تکراری یا جاافتاده برگرداند و هنوز می‌تونه با schema lock برخورد کند. پس «هیچ‌وقت منتظر نمی‌مونه» هم درست نیست. اگه blocking مسئله است، transaction length، access pattern، isolation و در صورت مناسب row-versioning رو بررسی کن.

READ UNCOMMITTED/NOLOCK can return dirty data, duplicate rows, or missing rows, and it can still encounter schema locks. It is not true that it never waits. For blocking, inspect transaction duration, access patterns, isolation, and whether row versioning fits.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

آزمایش فقط در دو session و دیتابیس آزمایشی و قابل‌حذف / Reproduce only with two lab sessions
-- Session A: update a lab row and pause before COMMIT.
BEGIN TRAN;
UPDATE Lab42.Ticket SET Status='Closed' WHERE TicketId=1;
WAITFOR DELAY '00:00:10';
ROLLBACK;
-- Session B during the pause: compare ordinary read and NOLOCK.
SELECT Status FROM Lab42.Ticket WHERE TicketId=1;
SELECT Status FROM Lab42.Ticket WITH (NOLOCK) WHERE TicketId=1;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

آزمایش باید با row آزمایشی باشه و session A حتماً rollback بشه. خروجی NOLOCK می‌تونه مقداری رو نشان دهد که هیچ‌وقت commit نشده؛ برای مالی یا شمارش قطعی، این trade-off خطرناک هست.

Use a lab row and ensure session A rolls back. NOLOCK may expose a value that was never committed—dangerous for financial or definitive counts.

DISTINCT و cursor گاهی علامت مدل اشتباه‌اند / DISTINCT and cursors can hide modeling problems

اگه JOIN fan-out ردیف رو چندبرابر کرده، DISTINCT ممکنه تکرار ظاهری رو حذف کند ولی جمع رو درست نکند یا ردیف‌های مشروع رو یکی کند. cardinality و کلید اتصال رو اصلاح کن. Cursor هم الزاماً ممنوع نیست؛ اما برای عملیات ردیفی بزرگ، set-based DML معمولاً از RBAR ارزان‌تر هست. cursor برای منطق ترتیبی که واقعاً وابسته به حالت قبلی هست ممکنه موجه باشه.

If join fan-out duplicates rows, DISTINCT may hide apparent duplicates without fixing inflated aggregates—or collapse legitimate rows. Correct join cardinality and keys. Cursors are not forbidden, but set-based DML is often cheaper for large row-by-row work. A cursor can be justified when logic truly depends on prior state.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

COUNT قبل و بعد از join رو مقایسه کن / Compare counts around a join
SELECT COUNT_BIG(*) AS JoinedRows,
       COUNT(DISTINCT o.OrderId) AS DistinctOrders,
       SUM(oi.Quantity * oi.UnitPriceAtSale) AS RawSum
FROM shop.Orders AS o
JOIN shop.OrderItems AS oi ON oi.OrderId=o.OrderId;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

SUM بالا در سطح line درسته اما اگه به‌جای آن ستون total سفارش رو روی هر line جمع کنیم، عدد باد می‌کنه. راه‌حل، aggregate کردن در grain درسته، نه افزودن DISTINCT به خروجی.

The line-level sum is valid, but summing an order-level total once per line inflates results. Fix the aggregation grain instead of adding DISTINCT to the output.

یه مکث کوتاه؛ واقعاً چی فهمیدیم؟Quick pause: what do we actually know now?

قبل از اینکه بریم بخش بعد، سعی کن بدون نگاه‌کردن به بالا در دو جمله بگی این فصل چه مسئله‌ای رو حل می‌کنه و از کدوم خروجی می‌فهمی راه‌حلت درست بوده. اگه فقط اسم دستورها یادت مونده، هنوز یه دور دیگه مثال قبلی رو با دادهٔ متفاوت اجرا کن.
