Tuning 1: measure, diagnose, treat

تیکت می‌گه «گزارش کند شده». کسی می‌خواد index بسازد، دیگری query رو بازنویسی کند. هنوز نمی‌دانیم کندی از SQL است، blocking، شبکه یا انتظار روی storage. توی این فصل قبل از درمان، خط پایه و زنجیرهٔ شواهد می‌سازیم.

A ticket says “the report is slow.” One person wants an index; another wants a rewrite. We do not yet know if the delay is SQL work, blocking, network, or storage waits. This chapter builds a baseline and evidence chain before treatment.

قبل از tuning، شاهد می‌خوایمBefore tuning, collect evidence

کاربر می‌گه «گزارش کند شده» و اولین وسوسه اینه که یه index بسازیم یا query رو از نو بنویسیم. نکن. توی «بهینه‌سازی ۱: اندازه‌گیری، تشخیص، درمان» اول خط پایه می‌گیریم، بعد plan و تعداد ردیف و I/O رو می‌خونیم، یک فرضیه می‌سازیم و فقط یک چیز رو عوض می‌کنیم. اگه بهتر شد باید بتونیم بگیم چرا؛ اگه بدتر شد هم باید مدرک داشته باشیم.

A user says “the report is slow” and the first temptation is to add an index or rewrite the query. Do not. In “Tuning 1: measure, diagnose, treat” we capture a baseline, read the plan and row counts, form one hypothesis, and change one thing. If it improves, we must explain why; if it regresses, we still need evidence.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

کندی رو تعریف کن، بعد اندازه بگیر / Define the slowdown before measuring it

زمان متوسط به‌تنهایی کافی نیست: p95، تعداد درخواست، خطای timeout و concurrency هم می‌تونه مهم باشه. query، پارامتر، بازهٔ زمانی، نسخه، database compatibility و بار کاری رو ثبت کن. خط پایه باید همان خروجی درست رو بدهد و تحت شرایط قابل‌مقایسه اجرا بشه.

Average duration alone is insufficient: p95, request volume, timeouts, and concurrency may matter. Record query, parameters, time window, version, compatibility, and workload. A baseline must return the correct result under comparable conditions.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

برای query نماینده، IO و زمان ثبت کن / Capture IO and time for a representative query
SET STATISTICS IO, TIME ON;
-- Execute the exact production-shaped query with representative parameters.
SELECT TenantId, COUNT_BIG(*) AS OpenCount
FROM Lab42.Ticket
WHERE Status='Open' AND CreatedAt >= '2026-01-01'
GROUP BY TenantId;
SET STATISTICS IO, TIME OFF;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

یک اجرای دستی فقط نمونه هست. اجرای اول ممکنه compile/cache متفاوت داشته باشه؛ زمان client هم شبکه و rendering رو شامل می‌شه. برای تشخیص، plan actual، logical reads، CPU، elapsed time و wait/blocking رو در کنار هم ببین.

One manual run is only a sample. The first execution may include different compile/cache behavior, and client time includes network/rendering. Diagnose with actual plan, logical reads, CPU, elapsed time, and waits/blocking together.

مصرف‌کنندهٔ زمان رو از علامت ظاهری جدا کن / Separate the time-consuming resource from the symptom

CPU بالا می‌تونه query پرکار یا compile پرتکرار باشه؛ elapsed بالا با CPU پایین ممکنه انتظار رو نشان دهد. logical reads زیاد به buffer cache pressure یا scan سنگین اشاره می‌کنه؛ blocking یعنی query منتظر lock است، نه اینکه الزاماً operator خودش کند باشه. در رخداد چند query همزمان و waitها رو بررسی کن.

High CPU can mean expensive query work or repeated compilation; high elapsed with low CPU may indicate waits. High logical reads can signal heavy scans or cache pressure; blocking means lock wait, not necessarily a slow operator. Inspect concurrent requests and waits during the incident.

از یک DMV به‌تنهایی نتیجهٔ نهایی نگیر. counters ممکنه reset شوند و نمونهٔ لحظه‌ای کلی علت یک درخواست رو نشان ندهد. Query Store و tracing باید با مجوز و retention مناسب تنظیم شوند؛ هر ابزار مشاهده هم هزینه داره.

Do not conclude from one DMV. Counters reset, and an aggregate snapshot may not identify one request's cause. Query Store and tracing need appropriate permissions and retention; observability itself has a cost.

هر بار یک تغییر؛ درستی رو هم دوباره ثابت کن / Change one thing at a time and re-prove correctness

یک فرضیهٔ قابل‌ابطال بنویس، یک تغییر آزمایشی بده، نتیجه رو با خط پایه برابر مقایسه کن و اگه بدتر شد برگرد. تغییر index ممکنه SELECT رو بهتر و UPDATE رو بدتر کند. تغییر query ممکنه plan رو بهتر اما NULL، duplicate یا boundary رو اشتباه کند؛ درستی بخشی از tuning هست.

Write a falsifiable hypothesis, make one test change, compare to the baseline, and revert if it regresses. An index may improve SELECT and hurt UPDATE. A rewrite may improve a plan but mishandle NULLs, duplicates, or boundaries; correctness is part of tuning.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

خروجی query رو دوطرفه مقایسه کن / Compare result sets in both directions
-- Run both versions in the lab, storing outputs in #Before and #After.
SELECT * FROM #Before EXCEPT SELECT * FROM #After;
SELECT * FROM #After EXCEPT SELECT * FROM #Before;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

EXCEPT تفاوت مجموعه‌ای رو پیدا می‌کنه و duplicate count رو حفظ نمی‌کنه؛ اگه multiplicity مهمه، با GROUP BY و COUNT(*) یا checksum منطقی مکمل بررسی کن. بعد performance رو اندازه بگیر.

EXCEPT finds set differences but does not preserve duplicate multiplicity; if duplicates matter, compare grouped counts or another suitable checksum. Then measure performance.

یه مکث کوتاه؛ واقعاً چی فهمیدیم؟Quick pause: what do we actually know now?

قبل از اینکه بریم بخش بعد، سعی کن بدون نگاه‌کردن به بالا در دو جمله بگی این فصل چه مسئله‌ای رو حل می‌کنه و از کدوم خروجی می‌فهمی راه‌حلت درست بوده. اگه فقط اسم دستورها یادت مونده، هنوز یه دور دیگه مثال قبلی رو با دادهٔ متفاوت اجرا کن.

Before moving on, explain in two sentences what problem this chapter solves and which output proves your solution is correct. If you only remember command names, rerun the previous example with different data.

چرخهٔ tuning باید قابل‌تکرار و قابل‌بازگشت باشه / A tuning cycle should be repeatable and reversible

Define user impact
  → capture baseline and correct result
  → inspect plan + IO/TIME + waits
  → state one hypothesis
  → change one thing in lab
  → prove correctness + measure
  → keep, revise, or roll back

اگه نتیجه فقط «احساس می‌کنم سریع‌تر شد» است، آزمایش کامل نیست. نسخهٔ query، پارامتر، dataset، تعداد تکرار، plan، logical reads، CPU/elapsed و شرایط رو ثبت کن. بهبود یک query رو با regression کل بار کاری عوض نکن.

“It feels faster” is not a complete experiment. Record query version, parameters, data, repetitions, plan, reads, CPU/elapsed, and conditions. Do not trade one query's improvement for an unmeasured workload regression.

تمرین: یک مشکل performance رو از حدس خارج کن / Exercises: make one performance issue evidence-based

آزمایش‌های سنگین رو فقط در lab انجام بده؛ production رو برای پاک‌کردن cache یا فشار مصنوعی دستکاری نکن.

Run expensive tests only in a lab; do not clear production cache or create artificial pressure.

بهینه‌سازی از خط پایه شروع می‌شه / Tuning starts with a baseline

اثر کاربر رو تعریف کن، نتیجهٔ درست رو ثابت کن، plan و IO/time/wait رو جمع کن، یک فرضیه و یک تغییر بساز، دوباره اندازه بگیر و قابلیت rollback رو نگه دار. اگه bottleneck بیرون SQL است، query rewrite کمکی نمی‌کنه؛ اگه تغییر metric بهتر اما بار کاری کلی بدتر شد، اون رو بهبود حساب نکن.

Define user impact, prove correct results, collect plan and IO/time/wait evidence, test one hypothesis and one change, then measure and preserve rollback. A rewrite cannot fix a bottleneck outside SQL; a better metric that harms the workload is not an improvement.
