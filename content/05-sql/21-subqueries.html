زیرکوئری؛ scalar، IN و EXISTS

Subqueries: scalar, IN, and EXISTS

تیم می‌پرسد کدوم محصول از میانگین قیمت محصولات گران‌تر است؛ یک query باید میانگین رو حساب کند و query دیگر اون رو مقایسه کند. به‌جای ذخیرهٔ دستی عدد و امید به اینکه داده عوض نشده، نتیجهٔ یک query رو مستقیماً ورودی query دیگر می‌کنیم.

The team asks which products cost more than the average product price. One query must calculate the average and another compare against it. Instead of copying a number and hoping data has not changed, we let one query feed another.

گزارش وقتی جدی می‌شه که فقط «لیست» نباشهA report becomes serious when it is more than a list

تا اینجا گرفتن چند ردیف آسون بود. درد واقعی وقتی شروع می‌شه که یکی می‌گه «فروش هر شهر رو بده، نسبت به ماه قبل مقایسه کن، فقط شهرهای بالای فلان عدد رو نگه دار و رتبه هم بده». «زیرکوئری؛ scalar، IN و EXISTS» رو برای همین جنس سؤال‌ها می‌خوایم. قدم‌به‌قدم می‌ریم جلو تا query هم درست باشه، هم بشه فهمید چرا درست کار می‌کنه.

Selecting rows is the easy part. Real reporting starts when someone asks for sales by city, a comparison with last month, a threshold, and a rank. “Subqueries: scalar, IN, and EXISTS” belongs to that kind of problem. We build the query step by step so it is not only correct but explainable.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

query به query دیگر جواب می‌ده / One query answers another

زیرکوئری می‌تونه یک مقدار، یک فهرست مقدار یا آزمون وجود یک ردیف برگرداند. شکل رو از سؤال انتخاب می‌کنیم: یک مقدار برای مقایسهٔ scalar؛ مجموعه برای IN؛ و فقط وجود یا نبود ردیف برای EXISTS. قبل از اجرا، نوع و تعداد نتیجهٔ داخلی رو حدس بزن.

A subquery can return one value, a list of values, or an existence test. Choose the form from the question: one scalar value, a set for IN, or whether any row exists for EXISTS. Predict the inner query’s shape before running it.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

یک مقدار: میانگین قیمت / One value: average price
SELECT ProductId, ProductName, UnitPrice
FROM shop.Products
WHERE UnitPrice > (SELECT AVG(UnitPrice) FROM shop.Products)
ORDER BY UnitPrice DESC;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

زیرکوئری داخل پرانتز باید یک مقدار بدهد. اگه اشتباهاً چند ردیف برگرداند، مقایسهٔ `>` معتبر نیست و SQL Server خطا می‌ده؛ scalar subquery رو با TOP بی‌ترتیب ساکت نکن، علت چندردیفی‌بودن رو پیدا کن.

The parenthesized subquery must produce one value. If it unexpectedly returns several rows, `>` cannot compare against it and SQL Server raises an error. Do not silence a multirow problem with unordered TOP; find why the subquery is not scalar.

IN برای عضویت در مجموعه / IN tests membership in a set

برای محصول‌هایی که در هر قلم سفارشی دیده شده‌اند، می‌توان شناسه رو با مجموعهٔ ProductIdهای OrderItems مقایسه کرد. IN می‌پرسد مقدار سمت چپ در مجموعه هست یا نه. این query خروجی جزئیات نمی‌ده؛ فقط ردیف بیرونی رو فیلتر می‌کنه.

To find products appearing in any order item, compare IDs against the set of OrderItems ProductIds. IN tests whether the left value belongs to the set. It filters outer rows; it does not return detail columns from the inner query.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

محصول‌های استفاده‌شده در سفارش / Products used in orders
SELECT p.ProductId, p.ProductName
FROM shop.Products AS p
WHERE p.ProductId IN
      (SELECT oi.ProductId FROM shop.OrderItems AS oi)
ORDER BY p.ProductId;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

اگه مجموعهٔ IN شامل NULL باشه و هیچ مقدار برابر پیدا نشه، نتیجه می‌تونه UNKNOWN بشه؛ به‌خصوص NOT IN در حضور NULL دام داره. در رابطه‌های واقعی، ستون کلید معمولاً NOT NULL است، اما اگه nullable باشه NULL رو صریح مدیریت کن.

If an IN set contains NULL and no equal value is found, the result can be UNKNOWN. NOT IN is especially tricky when NULL is present. Relationship keys are usually NOT NULL, but handle NULL explicitly if a source allows it.

EXISTS به مقدار علاقه نداره؛ به وجود ردیف علاقه داره / EXISTS cares whether a row exists

اگه سؤال اینه «آیا برای این مشتری سفارشی هست؟»، نیازی به join و ستون سفارش در خروجی نداریم. EXISTS با اولین ردیف واجد شرط از نظر منطقی TRUE می‌شه؛ optimizer آزاد هست اجرای کارآمدتری انتخاب کند. `SELECT 1` قرارداد خوانایی رایج است، نه اینکه مقدار ۱ در جایی ذخیره بشه.

If the question is “does this customer have an order?”, we do not need order columns in the output. EXISTS is logically true when a qualifying row exists; the optimizer can choose an efficient plan. `SELECT 1` is a readability convention, not a stored value.

مشتری‌های دارای سفارش / Customers that have orders
SELECT c.CustomerId, c.FullName
FROM shop.Customers AS c
WHERE EXISTS
(
  SELECT 1
  FROM shop.Orders AS o
  WHERE o.CustomerId = c.CustomerId
)
ORDER BY c.CustomerId;
GO

این زیرکوئری correlated هست: به `c.CustomerId` از query بیرونی اشاره می‌کنه. برای هر candidate باید رابطهٔ منطقی اون رو بفهمیم؛ ولی لازم نیست موتور حتماً query رو یک بار برای هر ردیف فیزیکی اجرا کند.

This is correlated: it references `c.CustomerId` from the outer query. Understand the logical relationship for each candidate; the engine is not required to physically execute it once per outer row.

NOT EXISTS برای «هیچ موردی پیدا نشه» / NOT EXISTS means “find no qualifying row”

برای مشتری بی‌سفارش، `NOT EXISTS` مستقیم می‌گه هیچ ردیف سفارش متناظری وجود نداشته باشه. برخلاف `NOT IN`، این الگو گرفتار NULL ناخواسته در فهرست داخلی نمی‌شه؛ شرط اتصال و nullable بودن کلیدها رو همچنان باید درست طراحی کنی.

For customers without orders, NOT EXISTS directly states that no matching order row exists. Unlike NOT IN, it is not poisoned by an unexpected NULL in the inner list; the relationship predicate and key nullability still need correct design.

مشتری‌های بدون سفارش / Customers without orders
SELECT c.CustomerId, c.FullName
FROM shop.Customers AS c
WHERE NOT EXISTS
(
  SELECT 1
  FROM shop.Orders AS o
  WHERE o.CustomerId = c.CustomerId
)
ORDER BY c.CustomerId;
GO

اگه query خالی شد، نتیجه رو با count پایه و join تشخیصی بررسی کن؛ خالی‌بودن الزاماً به معنی خطای زیرکوئری نیست. ممکنه همهٔ مشتری‌ها سفارش داشته باشند یا دادهٔ تمرینی متفاوت باشه.

If the query returns no rows, verify with base counts and a diagnostic join; an empty result is not necessarily a subquery bug. Perhaps every customer has an order, or the fixture differs.

چه وقت JOIN، چه وقت EXISTS؟ / When JOIN, when EXISTS?

اگه ستون‌های هر دو طرف رو لازم داری، JOIN بنویس. اگه فقط می‌پرسی «حداقل یک match وجود داره؟»، EXISTS اغلب قصد رو واضح می‌کنه و از تکثیر ردیف بیرونی در رابطهٔ یک‌به‌چند جلوگیری می‌کنه. این یک قاعدهٔ معناست، نه تضمین اینکه یکی همیشه سریع‌تر است؛ plan رو روی دادهٔ واقعی اندازه بگیر.

Use JOIN when you need columns from both sides. If you only ask whether at least one match exists, EXISTS often states intent clearly and avoids duplicating outer rows in one-to-many relationships. This is a semantic guideline, not a guarantee of speed; measure plans on real data.

هر محصول یک‌بار، اگه دست‌کم یک‌بار فروخته شده / Each product once if sold at least once
SELECT p.ProductId, p.ProductName
FROM shop.Products AS p
WHERE EXISTS
(
  SELECT 1 FROM shop.OrderItems AS oi
  WHERE oi.ProductId = p.ProductId
);
GO

اگه همین کار رو با JOIN انجام دهی، محصولی که در چند OrderItem آمده چند بار ظاهر می‌شه؛ بعد مجبور می‌شوی با DISTINCT تکرار رو جمع کنی. وقتی خروجی فقط موجودیت سمت بیرونی است، EXISTS معمولاً بیان مناسب‌تری هست.

A JOIN would repeat a product that appears in several OrderItems, then tempt you to add DISTINCT. When the output is only the outer entity, EXISTS is often a better expression.

سه شکل زیرکوئری، سه سؤال / Three subquery shapes, three questions

زیرکوئری رو بر اساس شکل نتیجهٔ لازم انتخاب کن؛ correlated بودن هم ارتباط منطقی با ردیف بیرونی رو می‌گه، نه الزاماً الگوریتم فیزیکی.

Choose the subquery form from the required result shape. Correlation describes logical dependence, not necessarily the physical algorithm.

شکل query داخلی رو قبل از انتخاب syntax مشخص کن / Choose syntax from the inner result shape

اگه یک مقدار لازم داری، scalar؛ اگه باید عضویت در یک فهرست رو بسنجی، IN؛ اگه فقط وجود match مهمه، EXISTS و اگه نبودنش مهمه، NOT EXISTS. تعداد ردیف‌های زیرکوئری scalar رو کنترل کن و NULLهای مجموعه رو مخصوصاً کنار NOT IN جدی بگیر. correlated بودن رو از نظر رابطه بخوان، نه به‌عنوان تضمین اجرای ردیف‌به‌ردیف.

For one value, use a scalar subquery; for membership, IN; for existence, EXISTS; for absence, NOT EXISTS. Ensure a scalar subquery returns at most one row and treat NULL in a set—especially with NOT IN—carefully. Read correlation as logical dependence, not a promise of row-by-row execution.

  • NOT EXISTS: آیا matchی نیست؟
