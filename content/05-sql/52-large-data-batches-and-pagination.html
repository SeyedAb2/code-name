دادهٔ حجیم، batch و صفحه‌بندی عمیق

Large datasets, batches, and deep pagination

صفحهٔ اول فهرست سریع میاد؛ صفحهٔ شمارهٔ ۲۰٬۰۰۰ مکث می‌کنه. query از ابتدا ردیف‌های زیادی رو skip می‌کنه. راه‌حل فقط «بزرگ‌ترکردن timeout» نیست. ترتیب پایدار، keyset pagination و اندازهٔ batch رو با دادهٔ کنترل‌شده می‌سنجیم.

The first page loads quickly; page 20,000 pauses while the query skips many rows. Increasing the timeout is not the only answer. We will measure stable ordering, keyset pagination, and batch size on controlled data.

قبل از tuning، شاهد می‌خوایمBefore tuning, collect evidence

کاربر می‌گه «گزارش کند شده» و اولین وسوسه اینه که یه index بسازیم یا query رو از نو بنویسیم. نکن. توی «دادهٔ حجیم، batch و صفحه‌بندی عمیق» اول خط پایه می‌گیریم، بعد plan و تعداد ردیف و I/O رو می‌خونیم، یک فرضیه می‌سازیم و فقط یک چیز رو عوض می‌کنیم. اگه بهتر شد باید بتونیم بگیم چرا؛ اگه بدتر شد هم باید مدرک داشته باشیم.

A user says “the report is slow” and the first temptation is to add an index or rewrite the query. Do not. In “Large datasets, batches, and deep pagination” we capture a baseline, read the plan and row counts, form one hypothesis, and change one thing. If it improves, we must explain why; if it regresses, we still need evidence.

OFFSET ردیف‌های قبلی رو نادیده می‌گیره؛ هزینه‌اش می‌تونه با عمق بالا برود / OFFSET skips prior rows; deeper pages can cost more

OFFSET/FETCH برای رابط صفحه‌ای ساده و رفتن مستقیم به صفحهٔ دلخواه مناسب است، اما موتور ممکنه برای رسیدن به offset، ردیف‌های زیادی رو بخواند و رد کند. ORDER BY باید یکتا و deterministic باشه؛ اگه tie-breaker نباشه، ردیف‌ها میان pageها جابه‌جا می‌شن.

OFFSET/FETCH suits simple page navigation and jumping to a page number, but the engine may read and discard many rows to reach the offset. ORDER BY must be unique and deterministic; without a tie-breaker, rows can shift between pages.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

صفحهٔ عمیق با ترتیب یکتا / A deep page with deterministic ordering
SELECT TicketId, CreatedAt, Status
FROM Lab42.Ticket
ORDER BY CreatedAt DESC, TicketId DESC
OFFSET 5000 ROWS FETCH NEXT 50 ROWS ONLY;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

CreatedAt ممکنه مساوی باشه؛ TicketId tie-breaker می‌ده. اگه داده هنگام پیمایش تغییر کند، حتی ترتیب یکتا هم نمونهٔ لحظه‌ای سازگار بین درخواست‌ها تضمین نمی‌کنه؛ isolation یا قرارداد cursor اپلیکیشن رو مشخص کن.

CreatedAt can tie, so TicketId is a tie-breaker. If rows change during paging, a unique order alone does not guarantee a consistent snapshot across requests; define the application's isolation or cursor contract.

Keyset از آخرین کلید صفحهٔ قبلی ادامه می‌ده / Keyset pagination continues from the last seen key

به‌جای شمردن offset، آخرین ترکیب مرتب‌شده رو به درخواست بعدی می‌دهیم. برای ترتیب نزولی `(CreatedAt, TicketId)`، شرط صفحهٔ بعد باید tuple کمتر از آخرین tuple باشه. index با همان ترتیب می‌تونه کمک کند؛ هر دو ستون باید در cursor باشند. این روش برای رفتن مستقیم به صفحهٔ عددی مناسب نیست، اما برای پیمایش پیوسته معمولاً هزینهٔ پایدارتری داره.

Instead of counting an offset, pass the last ordered key into the next request. For descending `(CreatedAt, TicketId)`, the next page uses a tuple below the last tuple. A matching index can help; both columns belong in the cursor. It is poor for jumping to an arbitrary page number but often steadier for sequential traversal.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

صفحهٔ بعد از آخرین کلید / Fetch the next page after the last key
DECLARE @LastCreatedAt datetime2 = '2026-03-01T10:00:00';
DECLARE @LastTicketId int = 500;
SELECT TOP (50) TicketId, CreatedAt, Status
FROM Lab42.Ticket
WHERE CreatedAt < @LastCreatedAt
   OR (CreatedAt = @LastCreatedAt AND TicketId < @LastTicketId)
ORDER BY CreatedAt DESC, TicketId DESC;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

برای صفحهٔ اول شرط cursor حذف می‌شه؛ برای sort صعودی operatorها برعکس‌اند. اگه cursor nullable باشه یا sort چندستونی پیچیده باشه، منطق lexicographic رو دقیق بنویس و با دادهٔ مساوی/NULL تست کن.

The first page omits the cursor predicate; ascending sort reverses comparisons. For nullable cursors or more complex sorts, implement lexicographic logic carefully and test ties/NULLs.

Batch اندازهٔ transaction رو کنترل می‌کنه، نه اینکه کار رو بی‌هزینه کند / Batches bound transaction size; they do not make work free

به‌روزرسانی یا حذف میلیون‌ها ردیف در یک transaction می‌تونه log، lock و rollback بزرگ بسازد. batch کوچک‌تر فشار هر transaction رو کم می‌کنه اما overhead تکرار داره و فاصلهٔ میان batchها semantics رو عوض می‌کنه. در یک کلید مرتب و predicate محدود، تعداد ردیف انجام‌شده رو ثبت کن و شرط پایان واضح داشته باش.

Updating or deleting millions of rows in one transaction can create large log, lock, and rollback work. Smaller batches bound per-transaction pressure but add repeated overhead and may change semantics between batches. Use a stable key and bounded predicate, record affected rows, and define an explicit stop condition.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

الگوی batch فقط برای جدول آزمایشی و قابل‌حذف / A batch pattern for a disposable table
DECLARE @Rows int = 1;
WHILE @Rows > 0
BEGIN
  DELETE TOP (500) FROM Lab52.EventArchive
  WHERE EventDate < '2020-01-01';
  SET @Rows = @@ROWCOUNT;
  -- In a real job, log progress and apply an intentional delay if needed.
END;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

حذف چند batch اتمیک کلی نیست؛ مصرف‌کننده ممکنه وضعیت میانی ببیند. retention requirement، FK، trigger، replication و backup رو پیش از production review کن. این کد در صفحهٔ آموزش بدون جدول آزمایشی و قابل‌حذف اجراشدنی نیست.

Multiple batches are not one globally atomic delete; consumers may observe intermediate state. Review retention requirements, foreign keys, triggers, replication, and backups before production. This example requires a disposable table.
