LEFT JOIN: preserve every left-side row

مدیر فروش می‌خواد فهرست همهٔ مشتری‌ها رو ببیند، نه فقط کسانی که سفارش دارن. گزارش فعلی با اضافه‌شدن INNER JOIN بعضی مشتری‌ها رو ناپدید کرده. این بار سمت چپ رو آگاهانه انتخاب می‌کنیم و یاد می‌گیریم NULL سمت راست چه چیزی می‌گه.

The sales manager needs every customer, not only customers who placed an order. The current report lost some customers after an INNER JOIN was added. This time we choose the preserved side deliberately and learn what NULLs on the right mean.

اول تعداد ردیف‌ها رو حدس بزنPredict the row count first

گزارش سفارش‌ها معمولاً از جایی سخت می‌شه که یک جدول دیگه وارد ماجرا می‌شه. سه سفارش داری، چهار مشتری داری، پنج ردیف سفارش هم داری؛ حالا JOIN می‌زنی و ناگهان خروجی دوازده ردیف می‌شه. توی «LEFT JOIN؛ حفظ همهٔ ردیف‌های سمت چپ» قبل از هر query اول حدس می‌زنیم چند ردیف باید برگرده، بعد اجرا می‌کنیم و از روی اختلاف حدسمون با واقعیت می‌فهمیم رابطه‌ها رو درست خوندیم یا نه.

Reports get interesting the moment another table enters the picture. You may have three orders, four customers, and five order lines, then a join suddenly returns twelve rows. In “LEFT JOIN: preserve every left-side row” we predict row counts before executing, then use any mismatch to diagnose our understanding of the relationships.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

گزارش باید مشتری بی‌سفارش رو هم نشان دهد / The report must include customers without orders

در INNER JOIN فقط جفت‌های matchشده می‌مانند. اما این ticket می‌گه «همهٔ مشتری‌ها»؛ پس `Customers` سمت چپ هست و `Orders` با LEFT JOIN به آن وصل می‌شه. اگه سفارش match نشه، ستون‌های سفارش NULL می‌شن، ولی ردیف مشتری باقی می‌مونه.

INNER JOIN keeps only matched pairs. But this ticket says “all customers,” so Customers goes on the left and Orders is attached with LEFT JOIN. If no order matches, order columns become NULL while the customer row remains.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

تعداد سفارش هر مشتری رو بعداً می‌سنجیم؛ فعلاً خود ردیف‌ها رو ببین / First inspect rows, not counts
SELECT c.CustomerId, c.FullName, o.OrderId, o.OrderStatus
FROM shop.Customers AS c
LEFT JOIN shop.Orders AS o
    ON o.CustomerId = c.CustomerId
ORDER BY c.CustomerId, o.OrderId;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

سمت چپ یعنی منبعی که همهٔ ردیف‌هایش باید حفظ بشه؛ «چپ» به ترتیب اجرای فیزیکی موتور اشاره نداره. اگه یک مشتری چند سفارش داشته باشه، در خروجی چند بار میاد. اگه هیچ سفارشی match نشه، یک ردیف با ستون‌های سفارش NULL می‌بینی.

The left side is the source whose rows must all be preserved; “left” does not describe physical execution order. A customer with several orders appears several times. A customer with no match appears once with NULL order columns.

NULL سمت راست، نشانهٔ «match پیدا نشد» هست / A right-side NULL can mean “no match”

بعد از LEFT JOIN، باید از ستونی برای تشخیص بی‌match بودن استفاده کنیم که در ردیف واقعی هیچ‌وقت NULL نیست؛ معمولاً کلید اصلی سمت راست انتخاب مناسبی هست. شرط `o.OrderId IS NULL` یعنی در این نتیجه ردیف سفارش متناظری پیدا نشده. با `= NULL` این تست رو ننویس؛ منطق NULL رو در فصل ۷ دیدیم.

After a LEFT JOIN, detect unmatched rows using a right-side column that cannot be NULL in a real row—usually its primary key. `o.OrderId IS NULL` means no matching order row was found. Do not write `= NULL`; Chapter 7 covered NULL logic.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

پیداکردن مشتری‌هایی که هیچ سفارشی ندارن / Find customers with no orders
SELECT c.CustomerId, c.FullName
FROM shop.Customers AS c
LEFT JOIN shop.Orders AS o
    ON o.CustomerId = c.CustomerId
WHERE o.OrderId IS NULL;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

این الگوی anti-join هست: از سمت چپ همه رو می‌گیریم و فقط مواردی رو نگه می‌داریم که سمت راست match نشده. اگه کلید سفارش nullable باشه، برای تشخیص از آن استفاده نکن؛ ستون NOT NULL واقعی باید.

This is an anti-join pattern: start with all left rows and retain those with no right-side match. If the order key were nullable, it would be a poor detector; use a real NOT NULL column.

فیلتر سمت راست رو در ON بگذاری یا WHERE؟ / Put a right-side filter in ON or WHERE?

ticket جدید می‌گه همهٔ مشتری‌ها رو نشان بده و اگه سفارش Paid دارن، جزئیاتش رو هم بیاور. شرط Paid بخشی از تعریف match است؛ اون رو در ON می‌گذاریم. انتقالش به WHERE مشتری بی‌سفارش رو حذف می‌کنه، چون برای او OrderStatus برابر NULL هست و شرط Paid نه TRUE می‌شه و نه از فیلتر عبور می‌کنه.

A new ticket asks for all customers and their Paid-order details when present. Paid defines which orders qualify as a match, so put it in ON. Moving it to WHERE removes customers without orders because their NULL OrderStatus does not pass the predicate.

همهٔ مشتری‌ها، فقط سفارش‌های Paid به‌عنوان match / All customers, Paid orders as matches
SELECT c.CustomerId, c.FullName, o.OrderId, o.OrderStatus
FROM shop.Customers AS c
LEFT JOIN shop.Orders AS o
    ON o.CustomerId = c.CustomerId
   AND o.OrderStatus = 'Paid'
ORDER BY c.CustomerId, o.OrderId;
GO
این نسخه خواسته رو عوض می‌کنه / This version changes the requirement
SELECT c.CustomerId, c.FullName, o.OrderId, o.OrderStatus
FROM shop.Customers AS c
LEFT JOIN shop.Orders AS o
    ON o.CustomerId = c.CustomerId
WHERE o.OrderStatus = 'Paid';
GO

نسخهٔ دوم فقط ردیف‌هایی رو نگه می‌داره که وضعیت سفارش Paid است؛ ردیف NULLشده از WHERE رد نمی‌شه و عملاً نتیجه به مشتری‌های دارای سفارش Paid محدود می‌شه. این query الزاماً «اشتباه» نیست؛ برای requirement دیگری درسته. جای شرط باید از خواستهٔ کسب‌وکار بیاید.

The second version keeps only rows where order status is Paid; NULL-extended rows fail WHERE, effectively limiting results to customers with a Paid order. It is not inherently wrong—it answers a different requirement. Predicate placement follows the business request.

LEFT JOIN هم می‌تونه ردیف رو چند برابر کند / LEFT JOIN can also multiply rows

LEFT JOIN تضمین نمی‌کنه هر مشتری دقیقاً یک بار بیاید. مشتری دارای سه سفارش سه ردیف داره. اگه بعداً سفارش رو به OrderItems هم وصل کنی، هر قلم سفارش یک ردیف دیگر می‌سازه. «حفظ سمت چپ» یعنی ردیف بی‌match رو دور نمی‌اندازیم؛ نه اینکه خروجی رو به یک ردیف در هر مشتری فشرده کنیم.

LEFT JOIN does not guarantee one row per customer. A customer with three orders yields three rows. Joining OrderItems can add a row per item. “Preserve the left side” means unmatched left rows are not discarded; it does not collapse the result to one row per customer.

یک مشتری، یک ردیف یا یک ردیف به‌ازای هر سفارش؟ سؤال رو روشن کن / Clarify the intended grain
SELECT c.CustomerId, c.FullName, o.OrderId, oi.ProductId
FROM shop.Customers AS c
LEFT JOIN shop.Orders AS o ON o.CustomerId = c.CustomerId
LEFT JOIN shop.OrderItems AS oi ON oi.OrderId = o.OrderId
ORDER BY c.CustomerId, o.OrderId, oi.ProductId;

این خروجی در سطح قلم سفارش هست. اگه گزارش باید یک ردیف برای مشتری داشته باشه، باید تصمیم بگیری سفارش‌ها رو aggregate کنی، انتخاب کنی یا به شکل دیگری نمایش دهی؛ DISTINCT درمان خودکار fan-out نیست.

This result is at order-item grain. If the report needs one row per customer, decide whether to aggregate, choose a specific order, or reshape the output. DISTINCT is not an automatic fan-out fix.

سمت چپ می‌مونه؛ سمت راست در صورت match پر می‌شه / Preserve the left; fill the right on a match

دیاگرام رفتار منطقی query رو نشان می‌ده. شرطی که در ON اضافه می‌کنی match رو محدود می‌کنه؛ شرط WHERE می‌تونه ردیف حفظ‌شده رو بعداً حذف کند.

The diagram shows logical query behavior. A predicate added to ON narrows matches; WHERE can later remove a preserved row.

سه پرسش پیش از انتخاب LEFT JOIN / Three questions before choosing LEFT JOIN

کدوم جدول باید کامل بمونه؟ چه چیزی match معتبر محسوب می‌شه؟ شرط بعد از اتصال قرار هست match رو محدود کند یا کل خروجی را؟ جواب روشن به این سه سؤال، هم جای ON و WHERE رو مشخص می‌کنه، هم کمک می‌کنه ردیف NULLشده رو درست بخوانی.

Which table must remain complete? What qualifies as a match? Should a predicate narrow matches or the whole result? Clear answers determine ON versus WHERE and help interpret NULL-extended rows correctly.

  • LEFT JOIN همهٔ ردیف‌های سمت چپ رو حفظ می‌کنه.
  • سمت راست می‌تونه برای نبود match با NULL پر بشه.
  • شرط WHERE روی سمت راست ممکنه ردیف حفظ‌شده رو حذف کند.
  • تکرار ردیف معمولاً از چند match میاد؛ DISTINCT درمان خودکار نیست.
