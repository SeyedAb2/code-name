Plan cache و حساسیت پارامتر در نسخه‌های مختلف

Plan cache and parameter sensitivity across versions

یک گزارش برای tenant کوچک سریع هست و برای tenant بزرگ ناگهان کند می‌شه؛ اجرای دوباره گاهی رفتار رو برعکس می‌کنه. query یکی است، داده یکی نیست. SQL Server plan رو compile و cache می‌کنه و هنگام compile مقدار پارامتر می‌تونه روی انتخاب اثر بگذارد. بیایید این رو با دادهٔ کنترل‌شده ببینیم و بعد مرز قابلیت‌های نسخه رو دقیق نگه داریم.

A report is fast for a small tenant and suddenly slow for a large one; a second execution may reverse the behavior. The query is the same, but the data is not. SQL Server compiles and caches plans, and parameter values can influence compilation. We will reproduce this with controlled data and keep version boundaries explicit.

قبل از tuning، شاهد می‌خوایمBefore tuning, collect evidence

کاربر می‌گه «گزارش کند شده» و اولین وسوسه اینه که یه index بسازیم یا query رو از نو بنویسیم. نکن. توی «Plan cache و حساسیت پارامتر در نسخه‌های مختلف» اول خط پایه می‌گیریم، بعد plan و تعداد ردیف و I/O رو می‌خونیم، یک فرضیه می‌سازیم و فقط یک چیز رو عوض می‌کنیم. اگه بهتر شد باید بتونیم بگیم چرا؛ اگه بدتر شد هم باید مدرک داشته باشیم.

A user says “the report is slow” and the first temptation is to add an index or rewrite the query. Do not. In “Plan cache and parameter sensitivity across versions” we capture a baseline, read the plan and row counts, form one hypothesis, and change one thing. If it improves, we must explain why; if it regresses, we still need evidence.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

یک plan cacheشده همیشه برای همهٔ مقدارها ایده‌آل نیست / One cached plan may not fit every parameter value

برای query پارامتری، optimizer با اطلاعات موجود در زمان compile تخمین می‌زند و plan رو می‌تونه برای اجرای بعدی reuse کند. اگه توزیع یکنواخت نباشه، مقدار اول ممکنه plan خوبی برای مقدارهای دیگر نسازد؛ به این مسئله معمولاً parameter sniffing/sensitivity می‌گن. خود sniffing باگ نیست؛ plan reuse مزیت است، اما skewed بار کاری تصمیم رو دشوار می‌کنه.

For a parameterized query, the optimizer estimates using information available at compilation and can reuse the plan later. With nonuniform data, the first value may produce a poor plan for others—often called parameter sniffing/sensitivity. Sniffing is not itself a bug; plan reuse is beneficial, but skew complicates the choice.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

دادهٔ skewed کنترل‌شده برای مقایسه / A bounded skewed fixture
IF SCHEMA_ID(N'Lab48') IS NULL EXEC(N'CREATE SCHEMA Lab48');
DROP TABLE IF EXISTS Lab48.Event;
CREATE TABLE Lab48.Event
 (EventId int IDENTITY PRIMARY KEY, TenantId int NOT NULL, Payload char(100) NOT NULL);
-- Populate a bounded test set with many rows for one tenant and few for another.
CREATE INDEX IX_Event_TenantId ON Lab48.Event(TenantId);
GO
CREATE OR ALTER PROCEDURE Lab48.GetEvents @TenantId int
AS
  SELECT EventId, Payload FROM Lab48.Event WHERE TenantId=@TenantId;
GO

هر workaround یک هزینه و قرارداد داره / Every workaround has a cost and contract

OPTION (RECOMPILE) هر بار compile می‌کنه و CPU/compile cost می‌ده، اما مقدار جاری رو برای همان اجرا می‌بینه. OPTIMIZE FOR UNKNOWN از تخمین عمومی‌تر استفاده می‌کنه و شاید برای همه بهتر نباشه. index یا query rewrite می‌تونه ریشهٔ هزینه باشه. هیچ hintی رو فقط با یک run انتخاب نکن.

OPTION (RECOMPILE) compiles each execution, trading CPU/compile cost for current-value information. OPTIMIZE FOR UNKNOWN uses a more generic estimate that may not suit everyone. Indexing or query rewrite may address the actual cost. Never choose a hint from one run.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

سه شکل رو در lab مقایسه کن / Compare three forms in the lab
-- Cached stored procedure plan
EXEC Lab48.GetEvents @TenantId=1;
EXEC Lab48.GetEvents @TenantId=2;
GO
-- Per-execution compile experiment
SELECT EventId, Payload FROM Lab48.Event
WHERE TenantId=2 OPTION (RECOMPILE);
GO
-- Generic estimate experiment
SELECT EventId, Payload FROM Lab48.Event
WHERE TenantId=2 OPTION (OPTIMIZE FOR UNKNOWN);
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

این‌ها گزینهٔ مقایسه‌اند، نه نسخهٔ یکسان درمان. recompile برای query بسیار پرتکرار ممکنه گران باشه؛ UNKNOWN ممکنه برای tenant خیلی بزرگ کم‌برآورد کند. اندازه‌گیری، concurrency و CPU رو بررسی کن.

These are comparison options, not equivalent cures. Recompile can be expensive for a high-frequency query; UNKNOWN may underestimate a very large tenant. Measure CPU, concurrency, and latency.

PSP چند plan ممکن می‌سازه، اما نسخه و eligibility مهمه / PSP can maintain multiple plans, but version and eligibility matter

Parameter Sensitive Plan optimization از SQL Server 2022 شروع شد و به compatibility level 160 وابسته است؛ برای predicateهای equality واجد شرایط روی توزیع نامتوازن ممکنه dispatcher و plan variant بسازد. همهٔ queryها eligible نیستند. SQL Server 2025 و compatibility 170 بهبودهایی از جمله پوشش DML و tempdb داره؛ اون رو به نسخه‌های قدیمی تعمیم نده.

Parameter Sensitive Plan optimization starts with SQL Server 2022 and depends on compatibility level 160; eligible equality predicates over skewed distributions may get a dispatcher and plan variants. Not every query qualifies. SQL Server 2025 with compatibility 170 adds improvements including DML and tempdb coverage; do not project this onto older versions.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

نسخه، compatibility و scoped configuration رو بخوان / Inspect version, compatibility, and configuration
SELECT @@VERSION AS EngineVersion;
SELECT name, compatibility_level
FROM sys.databases WHERE database_id=DB_ID();
SELECT name, value, value_for_secondary
FROM sys.database_scoped_configurations
WHERE name IN ('PARAMETER_SENSITIVE_PLAN_OPTIMIZATION','PARAMETER_SNIFFING');
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

برای اثبات PSP، actual plan، Query Store و اطلاعات dispatcher/variant رو در همان database بررسی کن؛ صرفاً روشن‌بودن config ثابت نمی‌کنه query شما از PSP استفاده کرده. تغییر compatibility یا configuration عملیاتی هست و باید با تست سازگاری انجام بشه.

To prove PSP use, inspect actual plans and Query Store dispatcher/variant evidence in the same database. An enabled setting alone does not prove your query used PSP. Changing compatibility or scoped configuration is an operational change requiring compatibility testing.
