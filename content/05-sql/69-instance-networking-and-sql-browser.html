شبکهٔ SQL Server و SQL Browser

SQL Server networking and SQL Browser

برنامه می‌گه SQL Server در دسترس نیست؛ از همان ماشین با SSMS وصل می‌شویم. این دو تجربه تناقض ندارن: shared memory، TCP، port، DNS، firewall و authentication مسیرهای جدا دارن. از نزدیک‌ترین لایه شروع می‌کنیم.

The application says SQL Server is unavailable, while SSMS works on the same machine. These can both be true: shared memory, TCP, ports, DNS, firewall, and authentication are separate layers. We start with the nearest one.

پیش‌نیاز: client/server، firewall و connection stringPrerequisites: client/server, firewall, connection stringsحدود ۹۰ دقیقه · ۱۸ تمرین / About 90 minutes · 18 exercises

اپ می‌گه «به دیتابیس وصل نمی‌شم»؛ از کجا شروع کنیم؟The app says “I cannot reach the database”; where do we start?

خطای اتصال یه اسم مشترک برای چند مشکل کاملاً متفاوته: DNS، پورت، TLS، instance، firewall یا خود login. توی «شبکهٔ SQL Server و SQL Browser» مسیر اتصال رو تکه‌تکه می‌کنیم. هر بار فقط یک لایه رو ثابت می‌کنیم تا به‌جای عوض‌کردن تصادفی تنظیمات، دقیقاً بدونیم شکست کجاست.

“Cannot connect” is one phrase for several different failures: DNS, port, TLS, instance discovery, firewall, or authentication. In “SQL Server networking and SQL Browser” we split the path into layers and prove one layer at a time instead of changing random settings.

قرارمون توی این فصلOur rule for this chapter

وصل‌شدن یک لایه نیست / A connection is not one layer

ابتدا hostname رو resolve کن؛ بعد TCP reachability، listener/port، TLS، login، database و مجوز رو بررسی کن. باز بودن port ثابت نمی‌کنه SQL Server پاسخ می‌ده یا login مجاز هست. خطای دقیق و زمان وقوع رو نگه دار.

Resolve the host first, then check TCP reachability, listener/port, TLS, login, database, and permissions. An open port does not prove SQL Server responds or the login is authorized. Preserve the exact error and timestamp.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

SQL Browser برای کشف instance هست / SQL Browser helps discover instances

default instance معمولاً روی TCP 1433 گوش می‌ده، اما پیکربندی قابل‌تغییر هست. named instance می‌تونه dynamic port داشته باشه. SQL Server Browser روی UDP 1434 به client کمک می‌کنه instance/port رو پیدا کند؛ اگه Browser خاموش است، endpoint صریح مثل tcp:host,port می‌تونه مسیر باشه. برای Browser پشت firewall هم UDP 1434 و هم TCP port لازم می‌شن.

A default instance commonly listens on TCP 1433, but configuration can differ. A named instance may use a dynamic port. SQL Server Browser on UDP 1434 helps clients discover the instance/port; with Browser stopped, an explicit endpoint such as tcp:host,port may work. Through a firewall, Browser discovery and SQL TCP traffic use separate ports.

از باز کردن Browser/SQL port برای کل اینترنت پرهیز کن. source IP، private network/VPN و host firewall رو هماهنگ کن؛ provider firewall لایهٔ جداگانه‌ای هست.

Do not expose Browser/SQL ports broadly to the internet. Scope source IPs, private networking/VPN, and host firewall; provider firewalls are a separate layer.
