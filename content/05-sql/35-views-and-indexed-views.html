View، indexed view و Row-Level Security

Views, indexed views, and row-level security

چند گزارش هر بار همان join رو می‌نویسند؛ از طرف دیگر، کاربر گزارش نباید ستون‌های حساس جدول اصلی رو ببیند. View می‌تونه یک سطح خواندن پایدار بسازد. اما آیا view خودش داده رو ذخیره می‌کنه؟ و آیا پنهان‌کردن ستون، مجوز واقعی است؟

Several reports repeat the same join, while a report user should not see sensitive base columns. A view can provide a stable read surface—but does it store data, and is hiding a column a real permission boundary?

تصمیمی که امروز کوچیکه، فردا توی هر query دیده می‌شهA small schema decision today appears in every query tomorrow

وقتی جدول فقط ده ردیف داره، تقریباً هر طراحی‌ای «کار می‌کنه». دردش چند ماه بعد معلوم می‌شه؛ وقتی داده تکراری شده، constraint نداری یا یه نوع داده اشتباه همهٔ queryها رو پیچیده کرده. توی «View، indexed view و Row-Level Security» قرار نیست فقط DDL بنویسیم؛ می‌خوایم بفهمیم هر تصمیم چه قانونی رو وارد خود دیتابیس می‌کنه و هزینهٔ اون تصمیم بعداً کجاست.

With ten rows, almost any design seems to work. The cost appears months later when data is duplicated, constraints are missing, or a poor data type infects every query. In “Views, indexed views, and row-level security” we are not merely writing DDL; we are deciding which rules the database itself enforces and what those choices cost later.

View معمولی query ذخیره‌شده است، نه نمونهٔ لحظه‌ای / A regular view stores a query, not a snapshot

یک view نامی برای query می‌ده و مصرف‌کننده رو از جزئیات زیرین جدا می‌کنه. به‌طور معمول خود ردیف‌های نتیجه رو ذخیره نمی‌کنه؛ هر بار query می‌شه و دادهٔ جاری رو می‌بینه. این abstraction مفید است، اما اگه query view کند باشه، اسم‌گذاشتن آن به‌تنهایی سریعش نمی‌کنه.

A view gives a query a name and separates consumers from underlying details. A regular view does not normally store result rows; it is evaluated against current data when queried. This abstraction helps, but naming a slow query does not make it fast.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

سطح گزارش با ستون‌های مجاز / A reporting surface with approved columns
CREATE OR ALTER VIEW reporting.vCustomerPaidSpend
AS
SELECT c.CustomerId, c.CustomerCode,
       SUM(oi.Quantity * oi.UnitPriceAtSale) AS PaidSpend
FROM shop.Customers AS c
JOIN shop.Orders AS o ON o.CustomerId=c.CustomerId
JOIN shop.OrderItems AS oi ON oi.OrderId=o.OrderId
WHERE o.OrderStatus=N'Paid'
GROUP BY c.CustomerId, c.CustomerCode;
GO

SELECT CustomerId, CustomerCode, PaidSpend
FROM reporting.vCustomerPaidSpend;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

View می‌تونه قرارداد ستون خروجی باشه؛ اما امنیتش رو باید با permission واقعی آزمایش کرد. اگه کاربر permission مستقیم روی base table داشته باشه، view چیزی رو از او پنهان نمی‌کنه.

A view can define a stable output contract, but security must be tested with actual permissions. A user with direct access to the base table is not restricted by the view.

دسترسی به view رو با کاربر واقعی بسنج / Test view permissions as the restricted user

الگوی رایج اینه که principal گزارش فقط SELECT روی view داشته باشه و permission مستقیم base table رو نداشته باشه. مالکیت مشترک می‌تونه مسئولship chaining رو برقرار کند، اما تنظیم schema، مالک‌ها و dynamic SQL اهمیت داره. با EXECUTE AS یا کاربر آزمایشی بررسی کن که query view کار می‌کنه و query مستقیم جدول رد می‌شه.

A common pattern grants a reporting principal SELECT on a view but not on base tables. Ownership chaining may permit the view query, while schema ownership and dynamic SQL affect the boundary. Test as the restricted user: the view should work and direct base access should fail.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

permission رو جدا بده / Grant the view, not the base table
-- In a disposable database, create a test user and role first.
CREATE ROLE reporting_reader;
GRANT SELECT ON OBJECT::reporting.vCustomerPaidSpend TO reporting_reader;
DENY SELECT ON OBJECT::shop.Customers TO reporting_reader;
DENY SELECT ON OBJECT::shop.Orders TO reporting_reader;
DENY SELECT ON OBJECT::shop.OrderItems TO reporting_reader;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

اسکریپت به مجوز مناسب نیاز داره و باید با user/role آزمایشی در دیتابیس آزمایشی و قابل‌حذف اجرا بشه. بعد با EXECUTE AS USER نتیجه رو بسنج و در پایان REVERT کن. از sysadmin برای آزمون محدودیت استفاده نکن؛ sysadmin عمداً راه دورزدن permission داره.

This requires appropriate permissions and belongs in a disposable database with a test principal. Use EXECUTE AS USER, inspect both paths, then REVERT. Do not test restrictions as sysadmin, which intentionally bypasses ordinary permissions.

Indexed view دادهٔ مشتق‌شده رو نگه می‌داره و نوشتن رو گران‌تر می‌کنه / An indexed view stores derived data and adds write cost

با schema binding و unique clustered index، view می‌تونه ذخیره بشه و هنگام تغییر base table نگه‌داری بشه. این قابلیت شرط‌های سخت‌گیرانه داره: نام‌گذاری دو‌بخشی، تابع‌های deterministic، SET optionهای مشخص، و در view گروه‌بندی‌شده COUNT_BIG و نداشتن HAVING. پس هر viewای قابل index نیست.

With schema binding and a unique clustered index, a view can be persisted and maintained as base tables change. Requirements are strict: two-part names, deterministic expressions, required SET options, and COUNT_BIG without HAVING for grouped definitions. Not every view can be indexed.

نمونهٔ aggregate ساده برای indexed view / A simple aggregate indexed-view pattern
SET ANSI_NULLS ON;
SET ANSI_PADDING ON;
SET ANSI_WARNINGS ON;
SET ARITHABORT ON;
SET CONCAT_NULL_YIELDS_NULL ON;
SET QUOTED_IDENTIFIER ON;
SET NUMERIC_ROUNDABORT OFF;
GO

CREATE VIEW reporting.vOrderCountByCustomer
WITH SCHEMABINDING
AS
SELECT o.CustomerId, COUNT_BIG(*) AS OrderCount
FROM shop.Orders AS o
GROUP BY o.CustomerId;
GO
CREATE UNIQUE CLUSTERED INDEX CIX_vOrderCountByCustomer
ON reporting.vOrderCountByCustomer(CustomerId);
GO

این نمونه به مسئول/schema و دادهٔ همان database وابسته هست. index روی view هزینهٔ INSERT و UPDATE و DELETE جدول Orders رو زیاد می‌کنه، چون aggregate باید نگه‌داری بشه. optimizer فقط وقتی مفید بداند اون رو انتخاب می‌کنه؛ actual plan و read/write بار کاری رو اندازه بگیر.

This depends on ownership, schemas, and tables in the same database. The view index adds work to INSERT, UPDATE, and DELETE on Orders because the aggregate must be maintained. The optimizer uses it only when beneficial; measure actual plans and read/write workload.

RLS ردیف‌ها رو بر اساس policy فیلتر می‌کنه / RLS filters rows according to a policy

Row-Level Security با filter predicate دیدن ردیف‌ها رو محدود می‌کنه و block predicate می‌تونه بعضی درج یا تغییرها رو رد کند. این از یک view مخفی‌کردن ستون متفاوت هست. policy باید بر اساس هویت قابل‌اعتماد باشه؛ اگه برنامه با یک login مشترک به DB وصل می‌شه، مقدار session زمینه رو فقط وقتی اعتماد کن که مرز برنامه اجازهٔ جعل اون رو نمی‌ده.

Row-Level Security uses filter predicates to restrict visible rows and block predicates to reject certain writes. This differs from hiding columns in a view. The policy must use trustworthy identity; with a shared application login, session context is safe only if the application boundary prevents users from spoofing it.

الگوی مفهومی predicate؛ فقط در دیتابیس آزمایشی و قابل‌حذف / Predicate pattern; disposable database only
CREATE FUNCTION security.fnTenantFilter(@TenantId int)
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN
  SELECT 1 AS allowed
  WHERE @TenantId = TRY_CONVERT(int, SESSION_CONTEXT(N'TenantId'));
GO
-- A SECURITY POLICY attaches FILTER and optional BLOCK predicates.
-- Test with separate principals and deliberately mismatched tenant context.
-- Do not deploy a tenant policy without a threat model and bypass tests.

این قطعه فقط الگوی predicate است؛ برای استفادهٔ واقعی باید schema security، policy، permission تغییر session زمینه، اتصال connection pool و مسیرهای admin رو هم طراحی و آزمایش کنی. هر request باید زمینه درست بگیرد و connection reuse نباید هویت قبلی رو نشت دهد.

This is only a predicate pattern. Production use also needs policy design, permission controls over session context, connection-pool handling, and administrative paths. Every request must set the correct context, and pooled connections must not leak a prior identity.

این‌ها جای هم نیستند. View برای abstraction، permission برای دسترسی، indexed view برای بار کاری اندازه‌گیری‌شده و RLS برای محدودیت سطری با هویت معتبر هست. با principal آزمایشی و query قابل‌مشاهده ثابت کن هرکدوم واقعاً چه می‌کنن.

These are not interchangeable. Views provide abstraction, permissions control access, indexed views target measured workloads, and RLS filters rows using trusted identity. Prove each behavior with a test principal and observable queries.

A regular view names a query; an indexed view persists derived data and adds write cost; permissions define object access; RLS filters rows under a policy. Test each claim with the right user, query, and plan.
