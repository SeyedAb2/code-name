گزارش از سطر به ستون؛ PIVOT و تجمیع شرطی

Pivoting rows into columns with PIVOT and conditional aggregation

تیم فروش گزارش ماهانه می‌خواد؛ اما داده‌ها سطری‌اند. قبل از انتخاب ابزار باید معلوم کنیم هر ردیف خروجی نمایندهٔ چیه. بعد سراغ CASE داخل aggregate یا PIVOT می‌رویم.

The sales team wants a monthly report, while source data is row-oriented. Define what one output row represents before choosing CASE inside an aggregate or PIVOT.

گزارش وقتی جدی می‌شه که فقط «لیست» نباشهA report becomes serious when it is more than a list

تا اینجا گرفتن چند ردیف آسون بود. درد واقعی وقتی شروع می‌شه که یکی می‌گه «فروش هر شهر رو بده، نسبت به ماه قبل مقایسه کن، فقط شهرهای بالای فلان عدد رو نگه دار و رتبه هم بده». «گزارش از سطر به ستون؛ PIVOT و تجمیع شرطی» رو برای همین جنس سؤال‌ها می‌خوایم. قدم‌به‌قدم می‌ریم جلو تا query هم درست باشه، هم بشه فهمید چرا درست کار می‌کنه.

Selecting rows is the easy part. Real reporting starts when someone asks for sales by city, a comparison with last month, a threshold, and a rank. “Pivoting rows into columns with PIVOT and conditional aggregation” belongs to that kind of problem. We build the query step by step so it is not only correct but explainable.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

گزارش شکل داده رو عوض می‌کنه، نه خود داده رو / A report changes shape, not stored data

مدیر هر ماه تعداد سفارش‌های هر وضعیت رو می‌خواد: یک ردیف برای هر ماه، ستون‌هایی مثل Paid و Pending. جدول سفارش‌ها چنین شکلی نداره؛ هر سفارش یک ردیف هست. گزارش باید ردیف‌ها رو جمع کند و در ستون‌های جدا نشان دهد. سؤال اول «PIVOT چه دستوری داره؟» نیست؛ بپرس: «یک ردیف خروجی دقیقاً متعلق به کدوم ماه یا مشتری است؟»

A manager wants order counts by month, with one output row per month and columns such as Paid and Pending. Orders have one row per order. Start by defining the output grain, not by memorizing syntax.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

این فقط طرح گزارش است، نه SQL اجرایی. در query تاریخ رو به ماه تبدیل می‌کنیم، معیار رو مشخص می‌کنیم و تصمیم می‌گیریم ستون‌ها ثابت‌اند یا زمان اجرا تغییر می‌کنن.

This is a report sketch, not executable SQL. The query derives a month, chooses a measure, and clarifies whether output columns are fixed or runtime-defined.

برای ستون‌های معلوم، تجمیع شرطی شفاف هست / For known columns, conditional aggregation is explicit

CASE برای هر وضعیت ۱ یا ۰ می‌سازه و SUM اون‌ها رو می‌شمارد. چون هر ردیف خروجی نمایندهٔ یک ماه است، فقط ماه رو گروه‌بندی می‌کنیم. اگه وضعیت تازه‌ای آمد، ستون مربوط به اون رو آگاهانه اضافه می‌کنیم.

CASE emits 1 or 0 for each status, and SUM counts them. Since one output row represents a month, group only by month. Add a new status column deliberately when the report contract changes.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

شمارش وضعیت‌ها برای هر ماه / Count statuses per month
;WITH MonthlyOrders AS
(
  SELECT DATEFROMPARTS(YEAR(OrderedAt), MONTH(OrderedAt), 1) AS MonthStart,
         OrderStatus
  FROM shop.Orders
)
SELECT MonthStart,
       SUM(CASE WHEN OrderStatus=N'Paid' THEN 1 ELSE 0 END) AS PaidCount,
       SUM(CASE WHEN OrderStatus=N'Pending' THEN 1 ELSE 0 END) AS PendingCount,
       SUM(CASE WHEN OrderStatus=N'Cancelled' THEN 1 ELSE 0 END) AS CancelledCount
FROM MonthlyOrders
GROUP BY MonthStart
ORDER BY MonthStart;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

اینجا هر سفارش یک بار شمرده می‌شه. اگه OrderItems رو join کنیم، سفارش چندقلمی چند بار ظاهر می‌شه؛ COUNT(*) تعداد ردیف‌های joinشده است، نه سفارش. اول در سطح سفارش aggregate کن یا آگاهانه COUNT(DISTINCT OrderId) به‌کار ببر.

Each order is counted once here. Joining OrderItems can repeat multi-line orders, making COUNT(*) count joined rows rather than orders. Aggregate to order grain first or deliberately use COUNT(DISTINCT OrderId).

مبلغ رو هم شرطی جمع کن؛ NULL رو با صفر یکی نکن / Conditional sums work for amounts; NULL is not zero

در گزارش مبلغ، CASE مبلغ رو برمی‌گردونه. ELSE 0 یعنی ردیف نامنطبق سهم صفر داره؛ بدون ELSE مقدار پیش‌فرض NULL هست. SUM مقدار NULL رو نادیده می‌گیره، اما نمایش صفر برای گروه بدون مقدار تصمیم معنایی گزارش هست.

For an amount report, CASE returns the amount. ELSE 0 gives nonmatching rows a zero contribution; without ELSE the default is NULL. SUM ignores NULL, but displaying zero for an empty measure is a semantic decision.

ابتدا مبلغ هر سفارش رو بساز / Aggregate line items to order totals first
;WITH OrderTotals AS
(
  SELECT o.OrderId, o.OrderedAt, o.OrderStatus,
         SUM(oi.Quantity * oi.UnitPriceAtSale) AS OrderTotal
  FROM shop.Orders AS o
  JOIN shop.OrderItems AS oi ON oi.OrderId = o.OrderId
  GROUP BY o.OrderId, o.OrderedAt, o.OrderStatus
)
SELECT DATEFROMPARTS(YEAR(OrderedAt), MONTH(OrderedAt), 1) AS MonthStart,
       SUM(CASE WHEN OrderStatus=N'Paid' THEN OrderTotal ELSE 0 END) AS PaidAmount,
       SUM(CASE WHEN OrderStatus=N'Pending' THEN OrderTotal ELSE 0 END) AS PendingAmount
FROM OrderTotals
GROUP BY DATEFROMPARTS(YEAR(OrderedAt), MONTH(OrderedAt), 1)
ORDER BY MonthStart;
GO

CTE هر سفارش رو به یک ردیف تبدیل کرده تا مبلغ اقلام تکراری جمع نشه. اگه مبلغ یا وضعیت NULL می‌پذیرد، رفتار رو جدا بررسی کن؛ COALESCE رو فقط وقتی به صفر تبدیل کن که صفر معنی درست باشه.

The CTE reduces each order to one row before reshaping, preventing repeated line amounts. Inspect nullable values explicitly; use COALESCE only when zero is the intended meaning.

PIVOT؛ ورودی رو کوچک و صریح نگه دار / PIVOT: keep its input narrow

PIVOT مقدارهای یک ستون رو به ستون خروجی تبدیل و یک معیار رو aggregate می‌کنه. ستون‌های دیگری که در ورودی مانده‌اند، گروه‌بندی ضمنی می‌شن. اگه OrderId رو بی‌دلیل نگه داری، گزارش ماهانه ممکنه برای هر سفارش ردیف جدا بسازد. ورودی رو به کلید گروه، کلید pivot و معیار محدود کن.

PIVOT turns values from one column into output columns while aggregating a measure. Other input columns become implicit grouping keys. Carrying OrderId into a monthly pivot can split the month into one row per order. Project only the intended group key, pivot key, and measure.

یک ردیف برای هر ماه / One row per month
;WITH PivotSource AS
(
  SELECT DATEFROMPARTS(YEAR(OrderedAt), MONTH(OrderedAt), 1) AS MonthStart,
         OrderStatus,
         OrderId
  FROM shop.Orders
)
SELECT MonthStart, [Paid], [Pending], [Cancelled]
FROM PivotSource
PIVOT
(
  COUNT(OrderId)
  FOR OrderStatus IN ([Paid], [Pending], [Cancelled])
) AS p
ORDER BY MonthStart;
GO

فهرست وضعیت‌ها ثابت است؛ مقدار جدید خودکار ستون نمی‌شه. باید query رو تغییر دهی یا برای نیاز واقعی سراغ dynamic SQL بروی. PIVOT ذاتاً از CASE سریع‌تر نیست؛ خوانایی، execution plan و اندازهٔ داده رو بسنج.

The status list is fixed; new values do not automatically become columns. Update the query or use dynamic SQL for a genuine runtime requirement. PIVOT is not inherently faster than CASE; compare readability, plans, and workload.

UNPIVOT شکل رو برمی‌گردونه، نه اطلاعات ازدست‌رفته رو / UNPIVOT reshapes data; it cannot restore lost meaning

UNPIVOT ستون‌هایی مثل Jan و Feb رو به ردیف‌های Month و Amount تبدیل می‌کنه. در SQL Server مقدار NULL ورودی برای UNPIVOT ردیف خروجی نمی‌سازه؛ پس نبودن ردیف ثابت نمی‌کنه مقدار اصلی صفر بوده. تغییر شکل، تاریخچه یا معنای حذف‌شده رو بازسازی نمی‌کنه.

UNPIVOT can turn columns such as Jan and Feb into Month and Amount rows. SQL Server does not emit output rows for NULL inputs, so a missing row does not prove the original value was zero. Reshaping cannot recover lost meaning.

ستون‌های ماهانه رو به ردیف باز کن / Reshape fixed month columns into rows
SELECT ProductId, MonthName, Amount
FROM dbo.MonthlySales
UNPIVOT
(
  Amount FOR MonthName IN ([Jan], [Feb], [Mar])
) AS u;
GO

برای دادهٔ ماهانه، نگهداری ماه به‌صورت مقدار در ردیف‌ها معمولاً از افزودن ستون برای هر ماه انعطاف‌پذیرتر هست. اگه NULL و صفر باید فرق داشته باشند، قرارداد داده رو قبل از تبدیل مشخص کن.

For monthly facts, storing month as a row value is usually more flexible than adding a column for each month. Define how NULL differs from zero before reshaping.

وقتی خروجی عجیب است، ستون‌های ورودی رو فهرست کن / When output looks wrong, list source columns

سه خطای پرتکرار: شمردن ردیف کالا به‌جای سفارش؛ باقی‌ماندن ستون اضافه و ساخت گروه ناخواسته؛ فرض اینکه مقدار غایب یعنی صفر. PIVOT فقط ردیف‌های ورودی رو تغییر شکل می‌ده و گروهی رو که ورودی نداره اختراع نمی‌کنه.

Common mistakes are counting lines instead of orders, leaving an extra column that creates unintended groups, and treating missing as zero. PIVOT only reshapes its input; it cannot invent absent groups.

کنترل مجموع پیش از pivot / Reconcile totals before pivoting
SELECT OrderStatus, COUNT(*) AS OrdersInStatus
FROM shop.Orders
GROUP BY OrderStatus;
GO

SELECT DATEFROMPARTS(YEAR(OrderedAt), MONTH(OrderedAt), 1) AS MonthStart,
       COUNT(*) AS TotalOrders
FROM shop.Orders
GROUP BY DATEFROMPARTS(YEAR(OrderedAt), MONTH(OrderedAt), 1)
ORDER BY MonthStart;
GO

اگه ستون‌های وضعیت با تعداد کل جور نیستند، وضعیت جاافتاده یا NULL رو بررسی کن. ماه بدون سفارش هم در ورودی نیست؛ برای نمایش همهٔ ماه‌ها، جدول تقویم بساز و پیش از pivot با LEFT JOIN وارد کن.

If status columns do not reconcile to totals, inspect omitted statuses and NULLs. A month without orders is absent; join a calendar table first if every month must appear.
