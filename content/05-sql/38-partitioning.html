Partitioning

جدول رویدادها هر ماه بزرگ‌تر می‌شه. حذف دادهٔ قدیمی با DELETE طولانی هست و بارگیری ماه تازه باید قابل‌کنترل باشه. تیم می‌گه «جدول رو partition کنیم تا همه‌چیز سریع بشه». قبل از قبول، می‌پرسیم: پارتیشن دقیقاً کدوم عملیات رو ساده می‌کنه و query از کجا می‌فهمه کدوم بخش رو بخواند؟

An events table grows every month. Deleting old data with DELETE is slow, and loading a new month should be controlled. The team says, “Partition it and everything gets faster.” Before agreeing, ask which operation partitioning simplifies and how a query knows which part to read.

تصمیمی که امروز کوچیکه، فردا توی هر query دیده می‌شهA small schema decision today appears in every query tomorrow

وقتی جدول فقط ده ردیف داره، تقریباً هر طراحی‌ای «کار می‌کنه». دردش چند ماه بعد معلوم می‌شه؛ وقتی داده تکراری شده، constraint نداری یا یه نوع داده اشتباه همهٔ queryها رو پیچیده کرده. توی «پارتیشن‌بندی» قرار نیست فقط DDL بنویسیم؛ می‌خوایم بفهمیم هر تصمیم چه قانونی رو وارد خود دیتابیس می‌کنه و هزینهٔ اون تصمیم بعداً کجاست.

With ten rows, almost any design seems to work. The cost appears months later when data is duplicated, constraints are missing, or a poor data type infects every query. In “Partitioning” we are not merely writing DDL; we are deciding which rules the database itself enforces and what those choices cost later.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

اول مسئلهٔ نگه‌داری رو تعریف کن / Start with a lifecycle problem, not a table size

پارتیشن‌بندی یک جدول یا index رو به بخش‌های منطقی بر اساس کلید تقسیم می‌کنه؛ مثلاً ماه ثبت. این ساختار می‌تونه archive، حذف بازه یا بارگیری بخش رو مدیریت‌پذیرتر کند. خودش تضمین نمی‌کنه query سریع بشه. اگه predicate کلید پارتیشن رو محدود نکند، ممکنه چندین پارتیشن خوانده بشه؛ و اگه جدول کوچک است، پیچیدگی اضافه معمولاً ارزش نداره.

Partitioning divides a table or index into logical pieces by a key such as event month. It can make archive, range removal, and loading easier. It does not guarantee faster queries. Without a predicate that restricts the partition key, many partitions may still be read; for a small table, the added complexity may not pay off.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

از metadata ببین جدول واقعاً partition شده یا نه / Inspect actual partition placement
SELECT t.name AS TableName, p.index_id, p.partition_number,
       p.rows, fg.name AS DataSpaceName
FROM sys.tables AS t
JOIN sys.indexes AS i ON i.object_id=t.object_id
JOIN sys.partitions AS p ON p.object_id=i.object_id AND p.index_id=i.index_id
LEFT JOIN sys.destination_data_spaces AS dds
  ON dds.partition_scheme_id=i.data_space_id
 AND dds.destination_id=p.partition_number
LEFT JOIN sys.filegroups AS fg ON fg.data_space_id=dds.data_space_id
WHERE t.name=N'EventLab' AND p.index_id IN (0,1)
ORDER BY p.partition_number;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

metadata و plan هر دو مهم‌اند: metadata نشان می‌ده مرز و تعداد پارتیشن چیه؛ actual plan نشان می‌ده query کدوم‌ها رو خوانده. یکی رو به‌جای دیگری تفسیر نکن.

Both metadata and plans matter: metadata shows boundaries and partition count; the actual plan shows what a query read. Do not substitute one for the other.

تابع مرز، scheme و جدول باید یک کلید واحد داشته باشند / Function, scheme, and table share a partition key

RANGE RIGHT یعنی خود boundary به بخش سمت راست می‌ره؛ RANGE LEFT برعکس هست. انتخاب مرز رو با تاریخ‌های واقعی تست کن، مخصوصاً نیمه‌شب و آخرین روز ماه. نمونه رو فقط در دیتابیس آموزشی اجرا کن؛ filegroupهای اضافی نیازمند storage آماده‌اند، پس برای تمرین از PRIMARY استفاده می‌کنیم.

With RANGE RIGHT, a boundary value belongs to the partition on its right; RANGE LEFT does the opposite. Test real dates, especially midnight and month-end. Run this only in a lab database; extra filegroups require prepared storage, so the exercise uses PRIMARY.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

ساخت مرز ماه‌ها در lab / Create monthly boundaries in a lab
IF SCHEMA_ID(N'Lab38') IS NULL EXEC(N'CREATE SCHEMA Lab38');
DROP TABLE IF EXISTS Lab38.EventLab;
DROP PARTITION SCHEME ps_EventLab;
DROP PARTITION FUNCTION pf_EventLab;
CREATE PARTITION FUNCTION pf_EventLab(date)
AS RANGE RIGHT FOR VALUES ('2026-02-01','2026-03-01','2026-04-01');
CREATE PARTITION SCHEME ps_EventLab
AS PARTITION pf_EventLab ALL TO ([PRIMARY]);
CREATE TABLE Lab38.EventLab
(
  EventDate date NOT NULL,
  EventId bigint NOT NULL,
  Payload nvarchar(100) NULL,
  CONSTRAINT PK_EventLab PRIMARY KEY (EventDate, EventId)
) ON ps_EventLab(EventDate);
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

کلید clustered/unique باید با قواعد پارتیشن سازگار باشه؛ در این نمونه EventDate داخل primary key آمده، پس uniqueness در جدول به ترکیب تاریخ و شناسه محدود هست. اگه EventId به‌تنهایی باید یکتا باشه، طراحی دیگری باید و ممکنه هزینه/قید دیگری بسازد.

The clustered/unique key must satisfy partitioning rules. Here EventDate is in the primary key, so uniqueness applies to the date-and-ID pair. If EventId must be globally unique by itself, the design needs another constraint or trade-off.

Partition elimination رو با predicate قابل‌تشخیص بسنج / Verify partition elimination from a sargable predicate

چند ردیف مرزی درج کن و query بازه‌ای رو با actual execution plan اجرا کن. predicate مستقیم روی EventDate معمولاً به بهینه‌ساز اجازه می‌ده بخش‌های نامربوط رو کنار بگذارد. اگه روی ستون تابعی مثل YEAR(EventDate) بگذاری، امکان تشخیص بازه رو سخت می‌کنی؛ plan رو ببین، حدس نزن.

Insert boundary rows and run a range query with the actual plan. A direct EventDate predicate usually lets the optimizer eliminate irrelevant partitions. Wrapping the column in a function such as YEAR(EventDate) can make range recognition harder; inspect the plan instead of guessing.

مرزها رو با یک query نیمه‌باز کنترل کن / Test a half-open time range
INSERT Lab38.EventLab (EventDate, EventId, Payload)
VALUES ('2026-01-31',1,N'jan'),('2026-02-01',2,N'feb'),
       ('2026-02-28',3,N'feb'),('2026-03-01',4,N'mar');
SELECT EventDate, EventId
FROM Lab38.EventLab
WHERE EventDate >= '2026-02-01' AND EventDate < '2026-03-01';
SELECT $PARTITION.pf_EventLab(EventDate) AS PartitionNumber, COUNT(*) AS RowsInPartition
FROM Lab38.EventLab GROUP BY $PARTITION.pf_EventLab(EventDate);
GO

$PARTITION برای مشاهدهٔ جای هر مقدار در تابع مفید است، اما جای بررسی row count و plan رو نمی‌گیره. اگه boundaryها آینده رو پوشش نمی‌دهند، پارتیشن انتهایی همچنان داده می‌گیره؛ split/merge باید با برنامه و بررسی اثر log/storage انجام بشه.

$PARTITION helps inspect value placement, but does not replace row counts and plan inspection. Values beyond the last boundary land in the end partition; split/merge operations need planning and log/storage impact review.

SWITCH سریع هست چون داده رو جابه‌جا می‌کنه؛ شرط‌هایش سخت‌اند / SWITCH is fast because it moves metadata—and its requirements are strict

برای بارگیری یک ماه، جدول stage رو با ساختار سازگار و خالی آماده می‌کنیم، دادهٔ همان بازه رو وارد می‌کنیم و سپس partition رو switch می‌کنیم. مقصد باید وجود داشته و خالی باشه؛ source و target و indexهای متناظر باید روی filegroup سازگار باشند، constraintها مرز رو ثابت کنند و محدودیت‌های دیگری هم برقرار باشه. SWITCH رو روی جدول تولیدی بدون rehearsal اجرا نکن.

For monthly loading, prepare a compatible empty staging table, load the matching range, then switch the partition. The target must exist and be empty; source, target, and corresponding indexes must align on filegroups, constraints must prove the range, and additional restrictions apply. Never run SWITCH on production without rehearsal.

شکل کلی دستور؛ اجرا فقط پس از هم‌ترازی کامل / Command shape—execute only after full alignment
-- Do not execute until source/target columns, indexes, CHECK constraints,
-- filegroups, and partition boundaries have been verified in a disposable lab.
ALTER TABLE Lab38.EventLab
SWITCH PARTITION 2 TO Lab38.EventArchive PARTITION 2;
GO

این نمونهٔ شکل دستور عمداً آمادهٔ اجرا نیست؛ جدول مقصد رو کامل نساخته‌ایم، چون نسخهٔ واقعی باید بر اساس همهٔ indexها و filegroupهای همان سیستم طراحی بشه. خطای SWITCH رو با کم‌کردن تصادفی constraint حل نکن؛ ابتدا شرط ناهماهنگ رو پیدا کن.

This syntax illustration is intentionally not executable as-is; the target is omitted because a real switch must match every index and filegroup in that environment. Do not “fix” a SWITCH error by randomly removing constraints—identify the mismatch.
