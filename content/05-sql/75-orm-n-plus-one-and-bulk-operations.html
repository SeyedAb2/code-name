ORM، N+1 و عملیات حجیم

ORMs, N+1, and bulk operations

صفحهٔ سفارش‌ها کند شده؛ query دستی سریع هست و ORM «تمیز» به نظر می‌رسه. اما برای هر سفارش یک query دیگر می‌فرسته. به‌جای سرزنش ORM، SQL تولیدشده، تعداد رفت‌وبرگشت و ردیف‌های برگشتی رو می‌شماریم.

The orders page is slow; a manual query is fast and the ORM looks clean, but it sends another query per order. Rather than blame the ORM, we count generated SQL, round trips, and returned rows.

مشکل همیشه خود SQL نیستThe database is not always the problem

ممکنه query خوب باشه و SQL Server هم سالم باشه، ولی برنامه هنوز کند یا ناپایدار باشه. pool، timeout، retry، ORM و migration بین اپ و دیتابیس رفتار واقعی سیستم رو می‌سازن. توی «ORM، N+1 و عملیات حجیم» از هر دو طرف نگاه می‌کنیم: هم SQL Server چی می‌بینه، هم اپ چه چیزی فکر می‌کنه اتفاق افتاده.

The query may be fine and SQL Server healthy while the application is still slow or fragile. Pools, timeouts, retries, ORMs, and migrations shape the real system between app and database. In “ORMs, N+1, and bulk operations” we observe both sides: what SQL Server sees and what the application believes happened.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

N+1 یعنی queryها با تعداد parent رشد می‌کنن / N+1 grows queries with parent count

یک query سفارش‌ها می‌خونه و برای هر سفارش query مشتری/آیتم اجرا می‌شه. با افزایش parentها round trip زیاد می‌شه. logging ORM یا profiler مجاز رو روشن کن و SQL واقعی رو بشمار؛ نام متد در کد نشان نمی‌ده چه query اجرا شده هست.

One query loads orders and then another query runs per order for customers/items. Round trips grow with parent count. Enable ORM logging or approved profiling and count actual SQL; a method name does not reveal generated queries.

یک query کمتر همیشه بهتر نیست / Fewer queries are not always better

eager loading ممکنه یک round trip رو کم کند اما join چند collection ردیف‌ها رو ضرب کند. projection فقط ستون لازم رو می‌گیره؛ pagination باید order پایدار و tie-breaker داشته باشه. plan، logical reads، network payload و تعداد ردیف رو با هم ببین.

Eager loading can reduce round trips but joining several collections can multiply rows. Projection selects needed columns; pagination requires deterministic ordering and a tie-breaker. Inspect plans, logical reads, network payload, and row count together.

bulk سریع‌تر است، ولی قرارداد رو دور می‌زند؟ / Bulk may be faster but bypass a contract

bulk insert/update می‌تونه هزینهٔ round trip رو کم کند، اما ممکنه validation، ORM hook یا domain logic برنامه رو اجرا نکند. constraint، transaction، row count و concurrency token رو بررسی کن. batch رو محدود کن تا lock/log/timeout کنترل بشه.

Bulk insert/update can reduce round trips but may bypass application validation, ORM hooks, or domain logic. Verify constraints, transaction, row counts, and concurrency tokens. Bound batch sizes to control locks, log, and timeouts.

abstraction رو با SQL واقعی ارزیابی کن / Evaluate abstractions by actual SQL

برای endpoint واقعی query count، زمان DB، تعداد row، logical reads و payload رو ثبت کن. خط پایه و نتیجه رو با داده و cache مشابه مقایسه کن. یک بار اجرا یا benchmark مصنوعی کوچک کافی نیست. ORM ابزار است؛ query plan همچنان متعلق به SQL Server هست.

For a real endpoint, record query count, database time, returned rows, logical reads, and payload. Compare baseline and change under similar data/cache conditions. One run or tiny synthetic benchmark is insufficient. The ORM is a tool; SQL Server still executes a query plan.
