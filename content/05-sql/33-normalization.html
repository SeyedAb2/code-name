نرمال‌سازی؛ از تکرار داده تا حذف anomaly

Normalization: from repeated facts to fewer anomalies

نام مدرس در ۴۰ ردیف تکرار شده. مدرس تغییر نام داده و فقط ۳۷ ردیف اصلاح شده‌اند. حالا یک کلاس هم بی‌دانشجو هست و نمی‌تونیم اطلاعاتش رو ثبت کنیم. مشکل از کمبود یک query نیست؛ چند واقعیت مستقل رو در یک ساختار قاطی کرده‌ایم.

An instructor’s name appears in 40 rows. After a rename, only 37 rows were corrected. An empty class cannot be recorded either. This is not a missing query; independent facts have been mixed into one structure.

تصمیمی که امروز کوچیکه، فردا توی هر query دیده می‌شهA small schema decision today appears in every query tomorrow

وقتی جدول فقط ده ردیف داره، تقریباً هر طراحی‌ای «کار می‌کنه». دردش چند ماه بعد معلوم می‌شه؛ وقتی داده تکراری شده، constraint نداری یا یه نوع داده اشتباه همهٔ queryها رو پیچیده کرده. توی «نرمال‌سازی؛ از تکرار داده تا حذف anomaly» قرار نیست فقط DDL بنویسیم؛ می‌خوایم بفهمیم هر تصمیم چه قانونی رو وارد خود دیتابیس می‌کنه و هزینهٔ اون تصمیم بعداً کجاست.

With ten rows, almost any design seems to work. The cost appears months later when data is duplicated, constraints are missing, or a poor data type infects every query. In “Normalization: from repeated facts to fewer anomalies” we are not merely writing DDL; we are deciding which rules the database itself enforces and what those choices cost later.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

اول anomaly رو با داده ببین / Observe the anomaly in data

در جدول زیر کلید ثبت‌نام ترکیبی هست: StudentId و CourseId. نام دانشجو به StudentId وابسته است، نام درس به CourseId و نمره به کل زوج. وقتی این‌ها در یک جدول جمع شده‌اند، هر واقعیت ممکنه چندبار تکرار بشه.

The enrollment key is the pair StudentId and CourseId. A student name depends on StudentId, a course title on CourseId, and a grade on the full pair. Combining them repeats independent facts.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

جدول denormalized آزمایشی / Disposable denormalized table
DROP TABLE IF EXISTS #EnrollmentWide;
CREATE TABLE #EnrollmentWide
(
  StudentId int NOT NULL,
  StudentName nvarchar(80) NOT NULL,
  CourseId int NOT NULL,
  CourseTitle nvarchar(100) NOT NULL,
  InstructorName nvarchar(80) NOT NULL,
  Grade decimal(5,2) NULL,
  PRIMARY KEY (StudentId, CourseId)
);
INSERT #EnrollmentWide VALUES
(1,N'Ava',10,N'SQL',N'Rana',90),
(2,N'Ben',10,N'SQL',N'Rana',85),
(1,N'Ava',20,N'Networks',N'Mina',92);
SELECT * FROM #EnrollmentWide;
GO

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

اگه Rana نامش عوض بشه، چند ردیف باید update شوند؛ جاافتادن یکی، تناقض می‌سازه: update anomaly. اگه درس جدید هنوز دانشجو نداره، کلید ترکیبی اجازهٔ ثبت Course بدون Student نمی‌ده: insert anomaly. اگه آخرین ثبت‌نام درس حذف بشه، عنوان درس هم از دست می‌ره: delete anomaly.

Renaming Rana requires updating multiple rows; missing one creates an update anomaly. A new course without a student cannot be inserted under the composite key: an insert anomaly. Deleting the last enrollment can erase the only stored course title: a delete anomaly.

وابستگی رو از خود دامنه استنتاج کن / Infer dependencies from the domain

functional dependency یعنی اگه مقدار X معلوم باشه، مقدار Y به‌طور یکتا تعیین بشه؛ با نماد X → Y. این ادعا دربارهٔ قانون دامنه است، نه فقط دادهٔ نمونه. در مثال StudentId → StudentName و CourseId → CourseTitle داریم، اما زوج StudentId, CourseId → Grade. اگه نام درس رو عوض کنیم، CourseId ثابت می‌مونه.

A functional dependency X → Y says a given X determines one Y. It is a domain rule, not merely a pattern in sample rows. Here StudentId determines StudentName, CourseId determines CourseTitle, and the pair determines Grade.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

تکرارهای واقعی رو پیدا کن / Find repeated facts in the fixture
SELECT CourseId, COUNT(DISTINCT CourseTitle) AS DifferentTitles,
       COUNT(DISTINCT InstructorName) AS DifferentInstructors
FROM #EnrollmentWide
GROUP BY CourseId;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

یک خروجی با مقدار یکتا، dependency رو اثبات نمی‌کنه؛ فقط تناقض فعلی رو پیدا می‌کنه. تعریف کسب‌وکار باید بگوید هر CourseId دقیقاً یک عنوان و instructor جاری داره یا instructor می‌تونه برای هر ترم متفاوت باشه.

A single distinct value does not prove the dependency; the query only detects current inconsistencies. The business definition must clarify whether each CourseId has one title and instructor, or instructors vary by term.

۱NF، ۲NF، ۳NF رو به مسئله وصل کن / Connect 1NF, 2NF, and 3NF to the problem

۱NF در مدل رابطه‌ای کلاسیک یعنی مقدار هر ستون اتمی نسبت به دامنهٔ استفاده باشه؛ فهرست چند course داخل یک سلول queryپذیری و قید رو سخت می‌کنه. ۲NF وقتی کلید مرکب داریم می‌پرسد آیا ستون غیرکلیدی به کل کلید وابسته هست یا فقط بخشی از آن. ۳NF وابستگی انتقالی میان ستون‌های غیرکلیدی رو بررسی می‌کنه. حفظ شمارهٔ فرم هدف نیست؛ حذف anomaly و بیان درست dependency هدف هست.

In the classical relational model, 1NF expects values atomic with respect to their domain of use; packing a list of courses into one cell complicates queries and constraints. With a composite key, 2NF asks whether non-key facts depend on the whole key or only part. 3NF examines transitive dependencies among non-key attributes. The goal is correct dependencies and fewer anomalies, not memorizing labels.

واقعیت‌ها رو نزد مالکشان نگه دار / Store each fact with its owner

جدول‌های جدا می‌سازیم: Student، Course و Enrollment. نام دانشجو فقط یک‌جا نگه داشته می‌شه؛ عنوان و مدرس در جدول درس؛ نمره در رابطهٔ ثبت‌نام. کلید خارجی رابطه رو حفظ می‌کنه و کلید مرکب از ثبت‌نام تکراری جلوگیری می‌کنه.

Split into Student, Course, and Enrollment. Student name lives once, course title and instructor with the course, and grade on the enrollment relation. Foreign keys preserve relationships; a composite key prevents duplicate enrollments.

تجزیهٔ بدون تکرار fact / Decompose repeated facts
DROP TABLE IF EXISTS #Enrollment, #Course, #Student;
CREATE TABLE #Student
(
  StudentId int PRIMARY KEY,
  StudentName nvarchar(80) NOT NULL
);
CREATE TABLE #Course
(
  CourseId int PRIMARY KEY,
  CourseTitle nvarchar(100) NOT NULL,
  InstructorName nvarchar(80) NOT NULL
);
CREATE TABLE #Enrollment
(
  StudentId int NOT NULL,
  CourseId int NOT NULL,
  Grade decimal(5,2) NULL,
  PRIMARY KEY (StudentId, CourseId)
);
INSERT #Student VALUES (1,N'Ava'),(2,N'Ben');
INSERT #Course VALUES (10,N'SQL',N'Rana'),(20,N'Networks',N'Mina');
INSERT #Enrollment VALUES (1,10,90),(2,10,85),(1,20,92);
SELECT s.StudentName, c.CourseTitle, c.InstructorName, e.Grade
FROM #Enrollment AS e
JOIN #Student AS s ON s.StudentId=e.StudentId
JOIN #Course AS c ON c.CourseId=e.CourseId;
GO

این join خروجی شبیه جدول قبلی می‌سازه، اما ذخیره‌سازی دیگر نام و عنوان رو در هر ثبت‌نام تکرار نمی‌کنه. تجزیهٔ خوب باید lossless باشه: با join دوباره بتوانیم دادهٔ معنادار قبلی رو بازسازی کنیم؛ و dependencyهای لازم رو هم تا جای ممکن enforce کنیم.

The join recreates a similar report without storing names and titles on every enrollment. A good decomposition is lossless: joins can reconstruct the meaningful original information, while relevant dependencies remain enforceable where possible.

نرمال‌سازی پایان طراحی نیست / Normalization is not the end of design

اگه گزارش همیشه یک نمونهٔ لحظه‌ای سریع لازم داره، ممکنه بعداً cache یا denormalized read model بسازیم؛ اما آن تصمیم باید آگاهانه باشه و قاعدهٔ همگام‌سازی داشته باشه. اول مدل درست و منبع حقیقت رو مشخص کن، بعد هزینهٔ query رو اندازه بگیر. شکستن قاعده بدون اندازه‌گیری، optimization نیست.

A frequently read report may later justify a cache or denormalized read model, but that requires an explicit synchronization rule. Establish the source of truth first, then measure query cost. Breaking normalization without evidence is not optimization.
