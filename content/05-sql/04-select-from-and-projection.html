SELECT، FROM و انتخاب ستون‌ها

SELECT, FROM, and projection

گزارش فروشگاه کند نیست؛ اما فایل خروجی‌اش پر از ستون‌هایی هست که هیچ‌کس نمی‌خونه. بعضی ستون‌ها هم اسم‌هایی مثل «(No column name)» دارن. پیش از اضافه‌کردن index، از خودمان بپرسیم: دقیقاً چه داده‌ای رو می‌خوایم ببینیم، از کجا، و با چه عنوانی؟

The shop report is not slow, but its export contains columns nobody reads. Some are even labeled “(No column name).” Before adding an index, ask: which data do we actually need, from where, and under what output names?

از یک سؤال واقعی شروع کنیمStart with a real question

یه همکار تازه‌وارد معمولاً SQL رو از روی syntax حفظ می‌کنه؛ ولی چند روز بعد که گزارش واقعی می‌رسه، نمی‌دونه از کجا شروع کنه. اینجا برعکس می‌ریم. اول سؤال گزارش رو روشن می‌کنیم، بعد برای «SELECT، FROM و انتخاب ستون‌ها» query می‌نویسیم، خروجی رو نگاه می‌کنیم و اگه چیزی عجیب بود از روی همون نتیجه می‌فهمیم کجای مدل ذهنی‌مون ایراد داره.

A newcomer often memorises SQL syntax, then gets stuck on the first real report. We do the opposite: clarify the reporting question, use “SELECT, FROM, and projection” to answer it, inspect the result, and use any surprise as evidence that our mental model needs work.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

اول خروجی رو ببین؛ بعد ستونی رو انتخاب کنLook at the output, then choose the columns

فصل قبل دادهٔ تمرینی ثابت Shop رو ساختیم. حالا یک query ساده می‌زنیم و ردیف‌ها رو می‌بینیم؛ مشتری، محصول و سفارش دادهٔ مشترک‌اند، اما هر گزارش قرار نیست همه‌چیز رو برداره. در SQL Server عبارت SELECT مشخص می‌کنه چه چیزی در نتیجه دیده بشه و FROM می‌گه منبع کدوم object هست.

Last chapter we built a stable Shop fixture. Now we query it: customers, products, and orders share the same data, but a report should not return everything. In SQL Server, SELECT defines what appears in the result and FROM identifies the source object.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

FROM shop.Products;

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

SELECT فقط شکل خروجی رو عوض می‌کنهSELECT changes the output shape

برای فهرست قیمت، شناسه شاید لازم نباشه؛ برای sync بین سیستم‌ها احتمالاً باید. projection یعنی انتخاب ستون‌هایی که این query در نتیجه‌اش نمایش می‌ده. انتخاب سه ستون از جدول، بقیهٔ ستون‌ها رو حذف نمی‌کنه و دادهٔ ذخیره‌شده رو هم تغییر نمی‌ده.

A price list may not need IDs, while a system sync probably does. Projection is the choice of columns a query returns. Selecting three columns does not delete the others from the table or modify stored data.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

یک خروجی کوچک‌تر و هدفمندA smaller, purposeful result
SELECT ProductName, UnitPrice
FROM shop.Products;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

این query هنوز هر چهار محصول رو می‌بینه، فقط شناسه و وضعیت فعال رو نمایش نمی‌ده. در گزارش مصرفی از SELECT * پرهیز کن: با اضافه‌شدن ستون، شکل خروجی بی‌خبر عوض می‌شه و دادهٔ غیرلازم هم منتقل می‌کنی. برای بازرسی سریع جدول، ستاره می‌تونه موقتاً مفید باشه؛ به عادت تبدیلش نکن.

This still reads all four products but does not display the ID or active flag. Avoid SELECT * in consumer-facing reports: adding a table column silently changes the result shape and may transfer unnecessary data. Star can be handy for a quick inspection, but should not become a habit.

اسم خروجی رو خودت انتخاب کنChoose a useful output name

نام ذخیره‌شدهٔ ستون گاهی برای خوانندهٔ گزارش خوب نیست. alias با AS نام همان ستون در خروجی رو عوض می‌کنه؛ نه schema رو تغییر می‌ده و نه نام فیزیکی ستون رو. برای فاصله یا واژهٔ خاص در عنوان، براکت T-SQL رو به‌کار ببر؛ در کد برنامه معمولاً alias ساده‌تر نگه‌داشتنی‌تر هست.

A stored column name is not always a good report label. AS renames a column in the result set; it does not alter the schema or physical column name. In T-SQL, brackets can delimit labels with spaces or reserved words, though simple aliases are usually easier for application code.

ستون محاسباتی با aliasA calculated column with an alias
SELECT ProductName,
       UnitPrice,
       UnitPrice * 0.90 AS [Price After 10% Discount]
FROM shop.Products
ORDER BY ProductId;
GO

قیمت تخفیف‌خورده فقط برای نمایش محاسبه می‌شه. اگه ماوس ۴۵۰ باشه خروجی فرضی ۴۰۵ است؛ جدول همچنان ۴۵۰ رو نگه می‌داره. پس این query ابزار محاسبه است، نه اصلاح قیمت و نه اجرای تخفیف واقعی.

The discounted price is calculated only for display. A mouse priced at 450 yields 405 in the result; the table still stores 450. This query calculates a value—it does not update a price or apply a real discount.

FROM منبع است؛ پیشوند schema مقصد رو روشن می‌کنهFROM names the source; schema qualification makes it explicit

در این دوره از shop.Products استفاده می‌کنیم، نه فقط Products. بخش اول schema و بخش دوم table هست. نام کامل‌تر مانع می‌شه query به schema پیش‌فرض حساب وابسته بمونه. هنوز database جاری هم مهمه؛ نام دو بخشی جای انتخاب database رو نمی‌گیره.

Throughout this course we write shop.Products, not just Products. The first part is the schema and the second is the table. Qualification avoids depending on an account’s default schema, though the current database still matters; a two-part name does not select a database.

زمینه و منبع رو با هم روشن کنMake context and source explicit
USE CodeNamesShopLab;
GO
SELECT p.ProductId, p.ProductName
FROM shop.Products AS p;
GO

alias جدول مثل p کمک می‌کنه نام ستون از منبعش معلوم باشه؛ وقتی JOINها رو شروع کنیم این تمایز حیاتی‌تر می‌شه. alias فقط در همین statement زنده هست و object جدیدی در database نمی‌سازه.

A table alias such as p makes a column’s source explicit; this becomes more valuable once we introduce joins. The alias exists only for this statement and creates no database object.

ترتیب نوشتن با ترتیب منطقی یکی نیستWritten order is not logical binding order

SQL رو با SELECT شروع می‌نویسیم، اما برای bind کردن query، SQL Server از FROM شروع می‌کنه. بعد از آن SELECT عبارت و alias رو تعریف می‌کنه؛ ORDER BY می‌تونه از alias خروجی استفاده کند. این ترتیب منطقی با physical execution یکی نیست: optimizer می‌تونه plan دیگری انتخاب کند، تا وقتی نتیجهٔ معنایی حفظ بشه.

We write a query starting with SELECT, but SQL Server logically binds FROM first. SELECT then defines expressions and aliases; ORDER BY can use an output alias. This logical order is not the physical execution order: the optimizer may choose a different plan as long as semantics are preserved.

این فلش‌ها ترتیب منطقی bind شدن رو نشان می‌دهند، نه زمان اجرای فیزیکی یا plan انتخابی optimizer.These arrows show logical binding order, not physical runtime or the optimizer’s selected plan.

همین مدل توضیح می‌ده چرا alias تعریف‌شده در SELECT رو نمی‌توان در WHERE همان سطح query به‌کار برد: WHERE زودتر bind می‌شه. اما ORDER BY دیرتر هست و alias رو می‌شناسد. اگه query با alias در WHERE خطا داد، نام expression رو آنجا تکرار کن؛ در فصل‌های بعد راه‌های ساختاری‌تر رو می‌بینیم.

This explains why a SELECT alias is unavailable to WHERE at the same query level: WHERE binds earlier. ORDER BY binds later and can see it. If an alias in WHERE fails, repeat the expression there; later chapters introduce more structured alternatives.

اگه ترتیب مهمه، ORDER BY بنویس. اگه فقط باید ردیف‌های واجد شرط رو ببینی، SELECT به‌تنهایی کافی نیست؛ WHERE مسئلهٔ بعدی ماست. اگه دنبال سریع‌ترشدن query هستی، چهار ردیف دادهٔ تمرینی برای نتیجه‌گیری performance کافی نیست.

If order matters, write ORDER BY. If you need only rows satisfying a condition, SELECT alone is not enough; WHERE is next. If performance is your concern, four fixture rows are not enough to draw conclusions.
