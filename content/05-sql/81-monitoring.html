پایش: خط پایه قبل از بحران

Monitoring: baseline before incidents

کاربر می‌گه گزارش کند شده، اما کسی نمی‌دونه کند نسبت به چه زمانی. DMV یک نمونهٔ لحظه‌ای می‌ده؛ بدون خط پایه، روند و خط زمانی استقرار علت رو نمی‌فهمیم. چند نشونه کاربردی رو ثبت می‌کنیم که هرکدوم یک اقدام بعدی دارن.

A user says a report is slow, but nobody knows compared with when. A DMV gives a snapshot; without baseline, trend, and deployment timeline we cannot find a cause. We collect actionable signals, each with a next step.

فرض کن این اتفاق ساعت سه صبح افتادهImagine this happened at 3 a.m.

فصل‌های عملیاتی وقتی ارزش دارن که روز خراب‌شدن سیستم به کارت بیان. برای «پایش: خط پایه قبل از بحران» قرار نیست فقط اسم DMV یا گزینهٔ backup رو حفظ کنیم. یه وضعیت قابل‌تکرار می‌سازیم، شواهد جمع می‌کنیم، تغییر رو کنترل‌شده انجام می‌دیم و آخرش ثابت می‌کنیم سیستم واقعاً برگشته؛ نه اینکه فقط یک command بدون خطا تموم شده.

Operations chapters matter when the system is actually broken at 3 a.m. In “Monitoring: baseline before incidents” we do not memorise DMV names or backup options. We create a reproducible state, collect evidence, make a controlled change, and prove recovery rather than trusting a command that merely completed without error.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

واحد اندازه‌گیری رو قبل از alert تعریف کن / Define a baseline before alerting

تأخیر، نرخ پردازش، نرخ خطا، blocking duration، مصرف منابع، عمر backup و نتیجهٔ job رو با بار کاری و بازهٔ زمانی ثبت کن. DMVهای cumulative مثل wait stats یا file stats رو به‌صورت نمونه‌های لحظه‌ای زمان‌دار بگیر و اختلاف محاسبه کن؛ عدد از زمان راه‌اندازی رو به‌عنوان بازهٔ جاری تفسیر نکن.

Record latency, throughput, errors, blocking duration, resources, backup age, and job outcomes with workload/time windows. Timestamp cumulative DMV snapshots and calculate deltas; do not mistake since-startup totals for current-window rates.

DMVها سرنخ‌اند، نه تاریخچهٔ کامل / DMVs are clues, not a complete history

sys.dm_exec_requests درخواست‌های فعال رو نشان می‌ده؛ sys.dm_os_wait_stats تجمعی است؛ file stats هم از زمان reset جمع می‌شن. مجوز لازم و اثر query پایش رو بررسی کن. برای تاریخچهٔ plan/query از Query Store در صورت پشتیبانی/فعال‌بودن استفاده کن و retention رو تنظیم کن.

sys.dm_exec_requests shows active requests; sys.dm_os_wait_stats is cumulative; file stats also accumulate until reset. Check permissions and monitoring-query overhead. Use Query Store for query/plan history when supported and enabled, with deliberate retention.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

درخواست فعال و blocker / Active requests and blockers
SELECT session_id,status,wait_type,wait_time,blocking_session_id,
       cpu_time,total_elapsed_time,database_id
FROM sys.dm_exec_requests
WHERE session_id<>@@SPID
ORDER BY total_elapsed_time DESC;

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

گرفتن متن query نیاز به join به DMVهای دیگر و مجوز مناسب داره. اطلاعات حساس رو در داشبورد عمومی نریز؛ نمونهٔ لحظه‌ای سریع ممکنه بعد از پایان blocker دیگر چیزی نشان ندهد.

Capturing SQL text requires other DMV joins and appropriate permissions. Do not expose sensitive text in public dashboards; a transient blocker may be gone before the snapshot.

تغییر سیستم رو روی خط زمانی ببین / Put system changes on a timeline

UTC timestamp، version برنامه، restart count، logs، backup/job و query performance رو کنار هم قرار بده. این خط زمانی بین regression بعد استقرار و مشکل ظرفیت قدیمی فرق می‌ذاره. سلامت سبز به‌تنهایی SLO، درستی یا backup موفق رو ثابت نمی‌کنه.

Correlate UTC timestamps, app version, restart count, logs, backups/jobs, and query performance. The timeline distinguishes a deployment regression from an older capacity issue. Green health alone proves neither SLO, correctness, nor backup success.

Actionable signals.
پاسخ و توضیحSolution and reasoning

دو نمونهٔ لحظه‌ای با فاصلهٔ زمانی بگیر. اگه counter تجمعیه، خود عدد دوم مهم نیست؛ اختلاف دو نمونهٔ لحظه‌ای رو حساب کن و زمان نمونه‌گیری رو هم کنار نتیجه نگه دار.

Take two timestamped snapshots. For cumulative counters, the second absolute value is less useful than the delta between the two samples.

عدد بدون خط پایه و مسئول، پایش نیست / A number without baseline and owner is not monitoring

نمونهٔ لحظه‌ای و cumulative counter رو جدا کردیم، نشونه رو به خط پایه و اقدام وصل کردیم و خط زمانی رو با استقرار/log هم‌بسته کردیم. فصل بعد برای رویدادهای کوتاه‌عمر از Extended Events و error log شواهد می‌گیره.

We distinguished snapshots from cumulative counters, tied signals to baselines/actions, and correlated the timeline with deploys/logs. Next we collect transient evidence with Extended Events and error logs.
