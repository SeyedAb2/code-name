JSON و XML

JSON and XML

سرویس بیرونی یک payload می‌فرسته: بعضی کلیدها همیشه هستن، بعضی فقط در رویدادهای خاص. اگه همه‌چیز رو ستون کنیم، schema با هر تغییر می‌لرزد؛ اگه همه‌چیز رو متن خام نگه داریم، query و constraint سخت می‌شن. مرز درست رو با شکل واقعی داده پیدا می‌کنیم.

An upstream service sends a payload: some keys are stable, others appear only for certain events. Turning every key into a column makes the schema brittle; keeping everything as raw text makes querying and validation hard. We will find the boundary from the actual data shape.

تصمیمی که امروز کوچیکه، فردا توی هر query دیده می‌شهA small schema decision today appears in every query tomorrow

وقتی جدول فقط ده ردیف داره، تقریباً هر طراحی‌ای «کار می‌کنه». دردش چند ماه بعد معلوم می‌شه؛ وقتی داده تکراری شده، constraint نداری یا یه نوع داده اشتباه همهٔ queryها رو پیچیده کرده. توی «JSON و XML» قرار نیست فقط DDL بنویسیم؛ می‌خوایم بفهمیم هر تصمیم چه قانونی رو وارد خود دیتابیس می‌کنه و هزینهٔ اون تصمیم بعداً کجاست.

With ten rows, almost any design seems to work. The cost appears months later when data is duplicated, constraints are missing, or a poor data type infects every query. In “JSON and XML” we are not merely writing DDL; we are deciding which rules the database itself enforces and what those choices cost later.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

JSON متنی رو اول اعتبارسنجی کن / Validate JSON text before extracting values

در بسیاری از نسخه‌ها JSON به‌صورت متن nvarchar ذخیره می‌شه و تابع‌های JSON روی آن کار می‌کنن. SQL Server 2025 نوع بومی json رو هم معرفی کرده، اما دسترسی و قابلیت‌های دقیق به نسخه و platform بستگی داره؛ این درس رو روی الگوی قابل‌حمل nvarchar(max) جلو می‌بریم. ISJSON فقط معتبر بودن syntax رو می‌سنجد، نه قرارداد کسب‌وکار رو.

In many versions, JSON is stored as nvarchar text and queried with JSON functions. SQL Server 2025 also introduces a native json type, but availability depends on version and platform; this lesson uses the broadly compatible nvarchar(max) pattern. ISJSON validates syntax, not the business contract.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

پیش از اعتماد به payload، syntax رو بسنج / Check syntax before trusting the payload
DECLARE @payload nvarchar(max) = N'{"orderId":42,"status":"paid","lines":[{"sku":"A-7","qty":2}]}';
SELECT ISJSON(@payload) AS IsValidJson,
       JSON_VALUE(@payload, '$.status') AS Status,
       JSON_VALUE(@payload, '$.orderId') AS OrderIdText;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

JSON_VALUE برای مقدار scalar است؛ برای آرایه یا object باید سراغ OPENJSON یا JSON_QUERY برویم. تبدیل به int رو هم صریح انجام بده و ورودی نامعتبر رو با TRY_CONVERT/validation مسیر خطا مدیریت کن، نه اینکه فرض کنی هر فرستنده داده درست می‌ده.

JSON_VALUE extracts a scalar; arrays and objects call for OPENJSON or JSON_QUERY. Convert to int explicitly and handle invalid input through validation or TRY_CONVERT rather than assuming every sender is correct.

OPENJSON سند رو به rowset قابل JOIN تبدیل می‌کنه / OPENJSON turns a document into a queryable rowset

وقتی payload آرایه‌ای از اقلام داره، OPENJSON هر عضو رو به یک ردیف تبدیل می‌کنه. WITH نوع و مسیر هر خروجی رو روشن می‌کنه؛ نام کلیدها در تطبیق پیش‌فرض حساس به حروف هست. برای object تودرتو از مسیر دقیق و در صورت نگه‌داشتن زیرسند از AS JSON استفاده کن.

When a payload contains an array of items, OPENJSON turns each element into a row. WITH declares output types and paths; default key matching is case-sensitive. Use explicit paths and AS JSON when retaining nested objects.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

آرایهٔ خطوط سفارش رو به ردیف تبدیل کن / Convert an order-lines array to rows
DECLARE @payload nvarchar(max) = N'{"orderId":42,"lines":[{"sku":"A-7","qty":2},{"sku":"B-3","qty":1}]}';
SELECT TRY_CONVERT(int, JSON_VALUE(@payload, '$.orderId')) AS OrderId,
       j.Sku, j.Quantity
FROM OPENJSON(@payload, '$.lines')
WITH (Sku nvarchar(40) '$.sku', Quantity int '$.qty') AS j;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

در محیط معمولی، OPENJSON به compatibility level 130 یا بالاتر نیاز داره. اگه تابع «شناخته نمی‌شه»، اول version و compatibility رو بررسی کن؛ عوض‌کردن تصادفی query راه‌حل نیست. بعد تعداد سطر، مقادیر NULL و تبدیل‌های ناموفق رو با ورودی edge case آزمایش کن.

In the common engine path, OPENJSON requires compatibility level 130 or higher. If SQL Server says the function is unknown, inspect version and compatibility before rewriting randomly. Then test row counts, missing values, and failed conversions with edge cases.

ساخت JSON و تغییر یک مسیر / Produce JSON and update one path

FOR JSON PATH خروجی رو با ساختار قابل‌کنترل می‌سازه. خروجی JSON همچنان قرارداد API هست: ترتیب، نام کلید، NULL و آرایه رو مطابق نیاز مصرف‌کننده بررسی کن. JSON_MODIFY یک متن JSON رو تغییر می‌ده؛ اگه داخل transaction یا update جدول است، شرط و همزمانی رو مثل هر دادهٔ دیگری مدیریت کن.

FOR JSON PATH builds output with controllable structure. JSON remains an API contract: verify key names, NULL behavior, and arrays for the consumer. JSON_MODIFY edits JSON text; when persisted in a table, manage predicates and concurrency like any other data.

خروجی صریح و تغییر کنترل‌شده / Explicit output and a targeted update
SELECT 42 AS orderId, N'paid' AS status
FOR JSON PATH, WITHOUT_ARRAY_WRAPPER;
GO
DECLARE @doc nvarchar(max) = N'{"status":"pending","attempt":1}';
SELECT JSON_MODIFY(@doc, '$.attempt', 2) AS UpdatedDocument;
GO

برای nested JSON، SQL Server ممکنه رشته رو escape کند؛ JSON_QUERY به موتور می‌گه متن معتبر رو به‌عنوان object/array در خروجی بگذارد. خروجی رو با ISJSON و مصرف‌کنندهٔ واقعی بسنج، نه فقط با نگاه به رشته.

For nested JSON, SQL Server may escape a string. JSON_QUERY marks valid JSON text as an object/array in the output. Validate with ISJSON and the actual consumer rather than visual inspection alone.

XML وقتی قرارداد XML و query ساختاری باید / Use XML when XML structure is part of the contract

XML یک نوع دادهٔ ساختاریافته با متدهایی مثل nodes، value و query داره. برای سندهای دارای namespace باید namespace رو در query اعلام کنی. اگه فقط یک payload JSON سبک داری، XML رو به‌خاطر «ساختاری بودن» انتخاب نکن؛ فرمت باید از قرارداد تبادل داده بیاید.

XML is a structured type with methods such as nodes, value, and query. Namespace-aware documents require namespace declarations in queries. Do not choose XML merely because it is structured when the interchange contract is JSON.

گره‌های XML رو به سطر تبدیل کن / Shred XML nodes into rows
DECLARE @x xml = N'<order id="42"><line sku="A-7" qty="2"/><line sku="B-3" qty="1"/></order>';
SELECT n.value('@sku', 'nvarchar(40)') AS Sku,
       n.value('@qty', 'int') AS Quantity
FROM @x.nodes('/order/line') AS T(n);
GO

نوع دادهٔ XML به‌تنهایی schema معنایی شما رو کامل نمی‌کنه؛ برای shape سخت‌گیرانه، XML schema collection رو بررسی کن. دادهٔ بیرونی رو با حجم و عمق کنترل‌شده بپذیر، چون payload بزرگ یا پیچیده هزینهٔ parse داره.

The XML type alone does not define your full semantic schema; consider an XML schema collection when strict shape validation is required. Bound external payload size and complexity because parsing has a cost.

هیچ‌کدوم از JSON و XML جای schema، permission، نوع‌دهی یا طراحی query رو حذف نمی‌کنن. اگه گزارش‌ها مدام یک کلید JSON رو فیلتر می‌کنن، اون رو به یک ستون محاسباتی/index یا مدل رابطه‌ای منتقل کن—اما بعد از اندازه‌گیری و با قرارداد migration.

JSON and XML do not remove schema, permissions, typing, or query-design concerns. If reports repeatedly filter one JSON key, consider a computed/indexed or relational representation—but measure first and migrate through an explicit contract.

تمرین: payload رو به دادهٔ قابل‌اعتماد تبدیل کن / Exercises: turn payloads into trustworthy rows

همهٔ آزمایش‌ها با متغیر محلی یا جدول آزمایشی و قابل‌حذف انجام شوند؛ payload بیرونی رو بدون اعتبارسنجی وارد جدول اصلی نکن.

Use local variables or disposable tables; never load an unvalidated external payload into a production table.
