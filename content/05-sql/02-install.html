نصب SQL Server و انتخاب ابزار درست

Installing SQL Server and choosing the right tools

فصل قبل مدل داده رو ساختیم؛ اما وقتی Query Editor باز هست و connection timeout می‌شه، هنوز نمی‌دانیم مشکل از نصب است، خود Server یا آدرسی که ابزار می‌زند. بیا یک محیط تمرینی نسخه‌دار بالا بیاوریم و هر حلقهٔ مسیر اتصال رو جدا ثابت کنیم.

Last chapter gave us a data model. But when a query editor is open and the connection times out, we still do not know whether installation, the server, or the target address is wrong. Let us start a versioned lab and prove each link in the connection path separately.

قبل از دستورها، اول زمین بازی رو بشناسBefore the commands, understand the ground you are standing on

فرض کن روز اول کاریته و یکی از بچه‌های تیم پروژه رو باز کرده و می‌گه «این دیتابیس ماست». قبل از اینکه چیزی حفظ کنی، باید بفهمی دقیقاً با چه چیزی طرفی، کجا قراره آزمایش کنی و چطور مطمئن بشی نتیجه‌ای که می‌بینی واقعاً از همون محیطیه که فکر می‌کنی. موضوع «نصب SQL Server و انتخاب ابزار درست» رو هم از همین زاویه جلو می‌بریم: کم‌کم، با دست خودمون و با خروجی‌ای که می‌شه بهش استناد کرد.

Imagine it is your first day on the team and someone opens the project and says, “this is our database.” Before memorising commands, you need to know what you are looking at, where the experiment runs, and how to prove the result came from the environment you think it did. We approach “Installing SQL Server and choosing the right tools” the same way: hands-on, incremental, and evidence-driven.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

Query Editor باز است؛ پس چرا وصل نمی‌شه؟The query editor is open—so why can it not connect?

یک نفر روی Windows دکمهٔ Connect رو می‌زند و انتظار داره فهرست databaseها رو ببیند. به‌جایش timeout می‌گیره. هم‌تیمی‌اش می‌گه «SQL Server نصب هست» و نفر سوم رمز sa رو عوض می‌کنه. اما هنوز یک سؤال پایه‌ای جواب نداره: Client دقیقاً به کدوم Server و کدوم پورت وصل می‌شه؟

A developer on Windows clicks Connect and expects to see databases, but gets a timeout. A teammate says, “SQL Server is installed,” and someone else changes the sa password. Yet a basic question remains unanswered: which server and port is the client actually trying to reach?

برای اینکه این حدس‌ها رو کنار بگذاریم، مسیر رو به چند بخش کوچک می‌شکنیم: Engine باید روشن باشه، container باید شروع بشه، خود SQL Server باید آمادهٔ پذیرش connection بشه، پورت میزبان باید به پورت Server برسد و در آخر Client باید با تنظیم درست وصل بشه. «نصب شد» و «connection موفق شد» یک اتفاق نیستند.

To replace guesses with evidence, split the path into smaller boundaries: the Engine must be running, the container must start, SQL Server must become ready for connections, the host port must reach the server port, and the client must connect with the right settings. “Installed” and “connected successfully” are not the same event.

سؤال این فصل:هر ابزار به کجا وصل می‌شه، از چه مسیری، و کدوم شاهد ثابت می‌کنه آن مرحله جواب داده؟ This chapter’s question:Where does each tool connect, over which path, and what evidence proves that step worked?

اول مسیر نصب رو با نیازت جور کنChoose an installation path that fits the job

برای این دوره یک راه واحد به همه تحمیل نمی‌کنیم. اگه فقط می‌خوای SQL Server رو برای تمرین بالا بیاوری، container نسخه‌دار محیط رو سریع پاک و بازسازی می‌کنه. اگه روی Windows به سرویس محلی و ابزارهای مدیریتی نیاز داری، نصب native با SQL Server Setup منطقی هست. روی Linux هم package رسمی رو برای همان توزیع و نسخه دنبال کن. راه‌های نصب رو قاطی نکن؛ هرکدوم چرخهٔ update و مسیر data خودش رو داره.

There is no single installation path for everyone. If you only need SQL Server for course exercises, a versioned container is easy to recreate and remove. If you need a local Windows service and administration tools, a native SQL Server Setup installation makes sense. On Linux, follow the package instructions for the exact supported distribution and release. Do not mix installation paths; each has its own update and data lifecycle.

The primary lab path uses the official image mcr.microsoft.com/mssql/server:2025-latest: SQL Server 2025, also known as 17.x. This tag advances, so each lab records the version reported by the server itself. When exact build reproducibility matters, share a specific CU tag or digest instead of assuming “latest” stays the same.

ابزار رو برای کار انتخاب کن، نه از روی عادتChoose a tool for the job, not out of habit

برای نوشتن query لازم نیست حتماً GUI داشته باشی. sqlcmd برای اتصال از terminal و اجرای script خوب است؛ SSMS رابط کامل مدیریت SQL Server هست و روی Windows اجرا می‌شه؛ افزونهٔ رسمی MSSQL در VS Code هم روی Windows، macOS و Linux برای نوشتن و اجرای T-SQL کار می‌کنه. هرکدوم به همان Server وصل می‌شن؛ فرقشان در ابزار و امکانات است، نه در موتور پایگاه‌داده.

You do not need a GUI to write queries. sqlcmd is useful for terminal connections and scripts; SSMS is the full SQL Server administration application for Windows; and Microsoft’s MSSQL extension for VS Code supports T-SQL development on Windows, macOS, and Linux. They all connect to the same server—the tools differ, not the database engine.

یک اصلاح به‌روز هم باید: Azure Data Studio در ۲۸ فوریهٔ ۲۰۲۶ بازنشسته شد و دیگر به‌روزرسانی امنیتی نمی‌گیره. برای کار تازه، VS Code با افزونهٔ MSSQL یا SSMS رو انتخاب کن. اگه پروژهٔ قدیمی‌ات هنوز ADS داره، فایل‌های query اون رو می‌توانی در VS Code باز کنی؛ بازنشستگی یعنی ابزار دیگر نگه‌داری نمی‌شه، نه اینکه فایل‌هایت ناگهان بی‌استفاده شوند.

One current correction matters: Azure Data Studio retired on February 28, 2026 and no longer receives security updates. For new work, choose VS Code with the MSSQL extension or SSMS. If an older project still uses ADS, its query files can be opened in VS Code; retirement means the tool is no longer maintained, not that your files suddenly stopped working.

یک محدودیت مهم قبل از PullOne important constraint before pulling the image

container رسمی SQL Server روی Linux فقط برای میزبان‌های Linux با پردازندهٔ Intel/AMD x86-64 پشتیبانی می‌شه. این image برای ARM64 نیست و اجرای آن با شبیه‌سازی‌هایی مثل QEMU یا Rosetta هم مسیر پشتیبانی‌شده‌ای نیست. پس اگه Mac یا Windows روی ARM داری، با زورکردن یک flag مشکل رو حل نکن: از ماشین x64 پشتیبانی‌شده یا SQL Server راه‌دور استفاده کن.

The official Linux SQL Server container is supported only on Linux hosts with Intel/AMD x86-64 processors. The image is not an ARM64 image, and emulation through QEMU or Rosetta is not a supported path. If you have an ARM Mac or Windows device, do not try to force it with a flag; use a supported x64 machine or a remote SQL Server.

حداقل حافظهٔ لازم برای شروع SQL Server روی Linux دو گیگابایت هست و برای اجرای راحت Docker Desktop هم خود میزبان منابع می‌خواد. پیش از Pull، معماری Docker Engine رو ببین؛ اگه معماری درست نیست، دانلود چند گیگابایتی صرفاً وقت تلف می‌کنه.

SQL Server on Linux requires at least 2 GB of memory to start, and Docker Desktop needs resources for the host environment as well. Check the Docker Engine architecture before pulling; downloading a large image cannot fix an unsupported architecture.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

اول Engine و معماری‌اش رو بشناسIdentify the Engine and its architecture first
docker version --format 'Server={{.Server.Os}}/{{.Server.Arch}}'
docker context ls

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

For this lab, the server should report linux/amd64. Record the active context too; on Windows, the Docker CLI might target the Engine inside Docker Desktop rather than a separate daemon in the current shell. If the Server section is missing, we have not reached SQL Server yet.

یک container محلی و دورریختنی بالا بیاورStart a local, disposable container

برای اینکه پورت 1433 میزبان با نصب SQL Server دیگری تداخل نکند، پورت آزاد 14333 رو روی loopback میزبان می‌گیریم و به 1433 داخل container می‌فرستیم. SQL Server داخل container روی 1433 می‌مونه؛ ابزار روی همین کامپیوتر به localhost,14333 وصل می‌شه. انتشار رو روی loopback محدود می‌کنیم تا این تمرین از شبکهٔ بیرونی قابل‌دسترسی نباشه.

To avoid colliding with another local SQL Server on host port 1433, use the free host port 14333 on loopback and forward it to 1433 in the container. SQL Server remains on port 1433 inside; a client on this computer connects to localhost,14333. Binding to loopback keeps this lab unavailable from outside the host.

رمز زیر فقط برای آزمایش یک‌بارمصرف هست.در container، متغیر محیطی می‌تونه در metadata و ابزارهای مدیریتی دیده بشه و فرمان هم ممکنه در history shell بمونه. این رمز رو هیچ‌جا دوباره استفاده نکن؛ فصل secretها روش مناسب‌تر رو می‌سازه. The password below is only for a disposable lab.A container environment variable can appear in metadata and management tools, and the command can remain in shell history. Never reuse this password; the secrets chapter will build a better pattern.
نسخهٔ اصلی دوره: SQL Server 2025 DeveloperCourse baseline: SQL Server 2025 Developer
docker pull mcr.microsoft.com/mssql/server:2025-latest

docker run -d --name sqlserver-lab \
  --hostname sqlserver-lab \
  -e ACCEPT_EULA=Y \
  -e MSSQL_PID=Developer \
  -e MSSQL_SA_PASSWORD='OnlyForDisposableLab!2026' \
  -p 127.0.0.1:14333:1433 \
  mcr.microsoft.com/mssql/server:2025-latest

این دستور چندخطی برای Bash و WSL است؛ بک‌اسلش در PowerShell ادامهٔ خط نیست. در PowerShell، همین فرمان رو یک‌خطی اجرا کن:

The multiline command is for Bash and WSL; backslash is not a PowerShell line continuation. In PowerShell, run the equivalent as one line:

docker run -d --name sqlserver-lab --hostname sqlserver-lab -e ACCEPT_EULA=Y -e MSSQL_PID=Developer -e MSSQL_SA_PASSWORD='OnlyForDisposableLab!2026' -p 127.0.0.1:14333:1433 mcr.microsoft.com/mssql/server:2025-latest

Developer برای توسعه و آزمایش است، نه production. اگه رمز با policy پیش‌فرض SQL Server جور نباشه، process راه‌اندازی می‌شه و بعد متوقف می‌شه؛ پس خطای رمز رو از خطای Docker daemon جدا می‌کنیم. دستور docker run اگه container ساخته بشه شناسه می‌ده، اما هنوز آماده‌بودن موتور رو ثابت نمی‌کنه.

Developer edition is for development and testing, not production. If the password fails SQL Server’s default policy, the process can start and then stop; distinguish that from a Docker daemon failure. A successful docker run returns a container ID, but still does not prove the engine is ready.

وضعیت container، log و پورت سه شاهد جدا هستنContainer state, logs, and port are separate signals
docker ps -a --filter name=sqlserver-lab
docker logs --tail 40 sqlserver-lab
docker port sqlserver-lab 1433
سه خروجی، سه شاهد جداThree outputs, three separate signals
STATUS          Up 38 seconds

127.0.0.1:14333

در log دنبال پیام SQL Server is now ready for client connections بگرد. وضعیت Up فقط زنده‌بودن process اصلی رو می‌گه؛ نگاشت پورت فقط می‌گه Docker چه مسیری ساخته. اگه Server هنوز شروع می‌شه، چند لحظه صبر کن و log رو دوباره بخوان؛ اگه خارج شده، docker logs از restart کورکورانه مفیدتر هست.

Look in the logs for SQL Server is now ready for client connections. Up only says the main process is alive; the port mapping only says Docker created a path. If the server is still starting, wait briefly and reread the logs; if it exited, docker logs is more useful than a blind restart.

با sqlcmd ثابت کن به کدوم Server رسیدیUse sqlcmd to prove which server you reached

image رسمی از نسخهٔ جدید ابزارهای Microsoft در مسیر /opt/mssql-tools18/bin استفاده می‌کنه. با docker exec یک Client داخل container اجرا می‌کنیم؛ در نتیجه آدرس مقصد localhost و پورت Server همان 1433 هست. -U sa نام login رو می‌ده و چون -P رو نمی‌نویسیم، ابزار رمز رو تعاملی می‌پرسد؛ رمز واردشده روی صفحه چاپ نمی‌شه.

The official image uses the newer Microsoft tools under /opt/mssql-tools18/bin. With docker exec, we run a client inside the container, so the target is localhost on the server’s own port 1433. -U sa selects the login; omitting -P makes the tool prompt for a password without echoing it.

اتصال تعاملی داخل containerInteractive connection inside the container
docker exec -it sqlserver-lab \
  /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -C

در prompt ابزار، query زیر رو وارد کن و بعد GO بزن. GO جداکنندهٔ batch در Client است؛ دستور T-SQL نیست که SQL Server اجرا کند.

At the client prompt, enter the query below and then send GO. GO is a client-side batch separator, not a T-SQL statement executed by the server.

نسخه، edition، نام Server و database جاریVersion, edition, server name, and current database
SELECT
  @@VERSION AS VersionBanner,
  SERVERPROPERTY('ProductVersion') AS ProductVersion,
  SERVERPROPERTY('Edition') AS Edition,
  @@SERVERNAME AS ServerName,
  DB_NAME() AS CurrentDatabase;
GO
ProductVersionEditionServerNameCurrentDatabase
17.x.xxxx.xDeveloper Editionsqlserver-labmaster

نسخهٔ patch ممکنه با به‌روزرسانی image فرق کند، پس به عبارت 17.x و edition واقعی نگاه کن، نه اینکه یک عدد نمونه رو حفظ کنی. در اتصال تازه DB_NAME() معمولاً master هست. این query ثابت می‌کنه همین session به یک SQL Server وصل شده؛ پورت منتشرشدهٔ میزبان رو هنوز با این اتصال داخلی آزمایش نکرده‌ایم.

The patch version can change as the image is updated, so inspect the 17.x product line and actual edition rather than memorising a sample number. A new connection normally starts in master. This query proves this session reached SQL Server, but because it used an internal connection, it has not tested the host’s published port.

چرا -C اینجاست؟در این آزمایش محلی، container گواهی‌ای داره که Client لزوماً اون رو به‌عنوان صادرشده از مرجع مورداعتماد نمی‌شناسد. -C برای همین آزمایش certificate رو trust می‌کنه؛ این میان‌بُر رو برای Server واقعی یا محیط production کپی نکن. آنجا باید گواهی معتبر و نام میزبان درست داشته باشی. Why is -C here?In this local lab, the container certificate may not chain to a certificate authority trusted by the client. -C trusts that certificate for this test; do not copy this shortcut to a real or production server. There, use a valid certificate and matching server name.

یه مکث کوتاه؛ واقعاً چی فهمیدیم؟Quick pause: what do we actually know now?

قبل از اینکه بریم بخش بعد، سعی کن بدون نگاه‌کردن به بالا در دو جمله بگی این فصل چه مسئله‌ای رو حل می‌کنه و از کدوم خروجی می‌فهمی راه‌حلت درست بوده. اگه فقط اسم دستورها یادت مونده، هنوز یه دور دیگه مثال قبلی رو با دادهٔ متفاوت اجرا کن.

Before moving on, explain in two sentences what problem this chapter solves and which output proves your solution is correct. If you only remember command names, rerun the previous example with different data.

حالا Client میزبان رو به همان پورت وصل کنNow connect a host client to that same port

در SSMS یا VS Code با افزونهٔ MSSQL، آدرس Server رو localhost,14333 بگذار؛ در SQL Server برای نوشتن port در این فرم از کاما استفاده می‌کنیم، نه دونقطه. Authentication رو روی SQL Login بگذار، user برابر sa و رمز همان رمز موقت آزمایش باشه. با docker exec که کار کرد، حالا این Client مسیر host port رو واقعاً می‌آزماید.

In SSMS or VS Code with the MSSQL extension, set the server to localhost,14333; SQL Server uses a comma in this server-and-port form, not a colon. Choose SQL Login, enter sa, and use the disposable lab password. The earlier docker exec test worked internally; this client now exercises host port publishing.

اگه ابزار از گواهی محلی شکایت کرد، در تنظیمات connection گزینهٔ Trust Server Certificate فقط برای همین محیط محلی رو فعال کن و encryption رو خاموش نکن. بعد در query editor این دستور رو اجرا کن:

If the tool complains about the local certificate, enable Trust Server Certificate for this local lab connection only; do not turn encryption off. Then run this in the query editor:

آزمون host → port → ServerTest host → port → server
SELECT @@VERSION AS VersionBanner, DB_NAME() AS CurrentDatabase;
GO

اگه query پاسخ داد، Client میزبان از نگاشت Docker عبور کرده و session داره. هنوز دربارهٔ ماندگاری database حرفی نزدیم و هنوز چیزی از Shop نساخته‌ایم؛ آن دو به‌ترتیب در فصل‌های داده و دادهٔ تمرینی میان. همین مرزبندی جلوی این نتیجهٔ اشتباه رو می‌گیره که «چون query جواب داد، نصب من برای همیشه آماده هست.»

If the query returns, the host client crossed Docker’s mapping and established a session. We have not tested database persistence or built the Shop fixture yet; those belong to the data and fixture chapters. This distinction prevents the false conclusion that one successful query proves a permanent, fully configured installation.

اگه مسیر native رو روی Windows می‌خوایIf you prefer a native Windows installation

از SQL Server Setup رسمی نسخهٔ انتخابی استفاده کن و برای یادگیری edition رایگان Developer رو انتخاب کن؛ این edition برای توسعه و test است، نه production. نصب Express هم برای تمرین‌های ساده ممکنه، اما محدودیت‌های edition رو در آزمایش‌های بعدی در نظر بگیر. Use the official SQL Server Setup for the selected release and choose the free Developer edition for learning; it is licensed for development and testing, not production. Express can also support simple exercises, but keep its edition limits in mind for later experiments. SSMS is installed separately; installing the Database Engine does not automatically install SSMS.

در نصب، instance name و سرویس رو یادداشت کن. برای default instance معمولاً نام کامپیوتر یا localhost رو می‌زنی؛ برای یک named instance مثل Express معمولاً فرم localhost\SQLEXPRESS استفاده می‌شه. اتصال named instance ممکنه به SQL Server Browser یا port ثابت وابسته بشه؛ تا وقتی Server محلی و ساده می‌خوای، container با port ثابت درس رو قابل‌بازتولیدتر نگه می‌داره.

Record the instance name and service during setup. A default instance is commonly reached by computer name or localhost; a named instance such as Express commonly uses localhost\SQLEXPRESS. Named-instance discovery can involve SQL Server Browser or a fixed port; for a simple local server, a container with an explicit port keeps this course more reproducible.

اگه در نقطه‌ای گیر کردیIf you get stuck
