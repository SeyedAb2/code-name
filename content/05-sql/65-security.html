امنیت SQL Server: هویت و مجوز

SQL Server security: identities and permissions

کاربر برنامه برای خواندن یک گزارش db_مسئول گرفته تا «مشکل دسترسی حل بشه». حالا همان credential می‌تونه داده رو حذف کند. اول login، database user، role و مجوز مؤثر رو از هم جدا می‌کنیم.

An application received db_owner to “fix a permission issue” for one report. That credential can now delete data. We will separate logins, database users, roles, and effective permissions.

این دفعه سؤال اینه: چه کسی اجازه داره؟This time the question is: who is allowed?

خیلی از دیتابیس‌ها از نظر query درستن ولی از نظر دسترسی نه؛ چون اپ با کاربری وصل می‌شه که تقریباً همه‌چیز بلده و همه‌چیز می‌تونه. «امنیت SQL Server: هویت و مجوز» رو با حساب محدود جلو می‌بریم. هر مجوزی که می‌دیم، با همون کاربر امتحانش می‌کنیم تا فرق «فکر می‌کنم بسته‌ست» با «واقعاً بسته‌ست» روشن بشه.

Many databases are query-correct but permission-wrong because the application connects with an account that can do almost anything. In “SQL Server security: identities and permissions” we work with restricted principals and test permissions as those principals so “I think it is locked down” becomes demonstrable behaviour.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

هویت server با هویت database یکی نیست / Server and database identities differ

login در سطح instance احراز هویت می‌شه؛ database user نمایندهٔ دسترسی در یک database هست. contained user و authentication روش‌های دیگری هم دارن. وجود login به‌تنهایی مجوز object نمی‌ده؛ role membership، grant، deny و مالکیت رو کنار هم بررسی کن.

A login authenticates at the instance; a database user represents access inside a database. Contained users and other authentication modes also exist. A login alone grants no object permission; inspect role membership, grants, denies, and ownership together.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

کاربران و roleها / Users and roles
SELECT name,type_desc,authentication_type_desc
FROM sys.database_principals
WHERE principal_id > 4
ORDER BY name;
SELECT r.name AS RoleName,m.name AS MemberName
FROM sys.database_role_members AS drm
JOIN sys.database_principals AS r ON r.principal_id=drm.role_principal_id
JOIN sys.database_principals AS m ON m.principal_id=drm.member_principal_id;

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

role کاربردی بساز، نه superuser کوچک / Build an app role, not a mini-superuser

اصل کمترین دسترسی یعنی فقط عملیات موردنیاز. به‌جای db_مسئول، role اختصاصی بساز و SELECT محدود یا EXECUTE روی procedureهای مجاز بده. مجوزهای inherited و دسترسی public رو هم حساب کن؛ GRANT محدود لزوماً DENY رو خنثی نمی‌کنه.

Least privilege means only required operations. Instead of db_owner, create a dedicated role and grant narrow SELECT or procedure EXECUTE. Account for inherited permissions and public access; a narrow GRANT does not simply cancel every DENY.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

مجوز procedure برای role / Grant procedure execution to a role
CREATE ROLE app_report_reader;
GRANT EXECUTE ON OBJECT::dbo.GetOrdersByCustomer TO app_report_reader;
-- Add the lab user to the role, then test as that principal.
SELECT HAS_PERMS_BY_NAME('dbo.GetOrdersByCustomer','OBJECT','EXECUTE') AS CanExecute;

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

HAS_PERMS_BY_NAME در زمینه فعلی جواب می‌ده؛ برای بررسی باید principal واقعی یا impersonation امن رو به‌کار ببری و در پایان REVERT کنی.

HAS_PERMS_BY_NAME reflects the current context; verify as the actual principal or through safe impersonation, then REVERT.

مجوز مؤثر رو با آزمون ثابت کن / Prove effective access with a test

roleها، schema permission، object grants، مسئولship chaining و execute زمینه نتیجه رو می‌سازند. از دیدن یک GRANT نتیجه نگیر. هم operation مجاز رو اجرا کن هم عملیاتی رو که باید رد بشه؛ بعد از EXECUTE AS، همیشه زمینه رو برگردان.

Roles, schema permissions, object grants, ownership chaining, and execution context combine into effective access. Do not infer from one GRANT. Test both allowed and denied operations; always restore context after EXECUTE AS.

یه مکث کوتاه؛ واقعاً چی فهمیدیم؟Quick pause: what do we actually know now?

Before moving on, explain in two sentences what problem this chapter solves and which output proves your solution is correct. If you only remember command names, rerun the previous example with different data.

credential رو در کد و log پخش نکن / Keep credentials out of code and logs

secret رو در source، query snippet مشترک یا log ثبت نکن. اگه لو رفت، حذف Git history کافی نیست؛ credential رو rotate کن. دسترسی‌های production رو با change management و audit سازمان هماهنگ کن. هیچ مثال این فصل مجوز واقعی سرور رو تغییر نمی‌ده.

Do not put secrets in source, shared query snippets, or logs. If exposed, deleting Git history is not enough; rotate the credential. Apply production permission changes through approved change control and audit. This chapter's examples must not alter a real server.

اسکریپت مجوز و query بررسی نهایی رو تحویل بده.

Deliver permission script and verification queries.

معیار موفقیت: با principal محدود وارد بشی و حداقل یک عمل مجاز و یک عمل غیرمجاز رو واقعاً امتحان کنی.

Success criterion: connect as the restricted principal and demonstrate at least one allowed and one denied action.

راهنما / HintHint
Least privilege must be tested.
پاسخ و توضیحSolution and reasoning

مجوز رو از حساب admin حدس نزن. با همون user/role تست کن و خروجی allow/deny رو نگه دار تا مرز دسترسی قابل‌اثبات باشه.

Do not infer permissions from an admin account. Test as the actual user/role and keep the allow/deny evidence.

دسترسی رو با شواهد محدود کن / Constrain access with evidence

login، user و role رو جدا کردیم، مجوز مؤثر رو از catalog و اجرای واقعی دیدیم و دسترسی رو به API محدود کردیم. خطای permission رو با sysadmin حل نمی‌کنیم؛ علت دقیق رو پیدا می‌کنیم. فصل بعد رمزنگاری، audit و مرز secret رو از هم باز می‌کنه.

We separated logins, users, and roles, checked effective access in catalogs and by execution, and narrowed privileges to the API. We do not solve permission errors with sysadmin; we find the exact cause. Next we distinguish encryption, auditing, and secret boundaries.
