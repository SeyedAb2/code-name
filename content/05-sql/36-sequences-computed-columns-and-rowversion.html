Sequence، computed column و rowversion

Sequences, computed columns, and rowversion

برای یک جدول سفارش، هم شمارهٔ سفارش می‌خوایم، هم مبلغ محاسبه‌شده، هم راهی بفهمیم رکورد از وقتی خوانده‌ایم عوض شده یا نه. وسوسه اینه که هر سه رو «ستون ویژه» بدانیم؛ اما هرکدوم مسئلهٔ جداگانه‌ای حل می‌کنه.

An orders table needs a generated order number, a calculated total, and a way to detect whether a row changed after it was read. They may all look like special columns, but each solves a different problem.

تصمیمی که امروز کوچیکه، فردا توی هر query دیده می‌شهA small schema decision today appears in every query tomorrow

وقتی جدول فقط ده ردیف داره، تقریباً هر طراحی‌ای «کار می‌کنه». دردش چند ماه بعد معلوم می‌شه؛ وقتی داده تکراری شده، constraint نداری یا یه نوع داده اشتباه همهٔ queryها رو پیچیده کرده. توی «Sequence، computed column و rowversion» قرار نیست فقط DDL بنویسیم؛ می‌خوایم بفهمیم هر تصمیم چه قانونی رو وارد خود دیتابیس می‌کنه و هزینهٔ اون تصمیم بعداً کجاست.

With ten rows, almost any design seems to work. The cost appears months later when data is duplicated, constraints are missing, or a poor data type infects every query. In “Sequences, computed columns, and rowversion” we are not merely writing DDL; we are deciding which rules the database itself enforces and what those choices cost later.

Sequence شماره می‌ده؛ تضمین پیوستگی نمی‌ده / A sequence generates values, not a gap-free business count

IDENTITY به درج یک جدول گره خورده هست. Sequence یک شیء جداست: می‌توانی مقدار بعدی رو پیش از INSERT بگیری یا بین چند جدول به اشتراک بگذاری. اما مقدار گرفته‌شده در rollback پس داده نمی‌شه و cache یا توقف سرور هم می‌تونه فاصله بسازد. پس برای شمارهٔ فاکتورِ الزاماً بی‌فاصله، این ابزار رو بدون بررسی الزام حقوقی انتخاب نکن.

IDENTITY belongs to an insert into one table. A sequence is independent: you can obtain a value before inserting or share it across tables. Values are not returned on rollback, and caching or interruption may leave gaps. Do not use it for a legally gap-free invoice number without investigating the requirement.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

آزمایش در schema آموزشی / Experiment in a lab schema
IF SCHEMA_ID(N'Lab36') IS NULL EXEC(N'CREATE SCHEMA Lab36');
DROP SEQUENCE IF EXISTS Lab36.OrderNumber;
CREATE SEQUENCE Lab36.OrderNumber AS bigint
  START WITH 1000 INCREMENT BY 1 CACHE 20;
SELECT NEXT VALUE FOR Lab36.OrderNumber AS AllocatedNumber;
SELECT NEXT VALUE FOR Lab36.OrderNumber AS NextNumber;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

خروجی دو عدد افزایشی است، ولی نه INSERTی رخ داده و نه تضمینی دربارهٔ استفادهٔ نهایی از هر عدد داریم. Sequence همزمانی رو مدیریت می‌کنه؛ قاعدهٔ یکتاییِ مقصد رو همچنان با PRIMARY KEY یا UNIQUE بساز.

The output contains increasing values, but no row was inserted and no value is guaranteed to be used. A sequence coordinates allocation; enforce destination uniqueness with a primary key or unique constraint.

Computed column یک expression وابسته به همان ردیف هست / A computed column derives a value from row columns

اگه مبلغ خط از تعداد و قیمت واحد به‌دست میاد، ذخیرهٔ دستی هر سه مقدار راهی برای ناسازگاری باز می‌کنه. computed column رابطه رو در schema ثبت می‌کنه. پیش‌فرض virtual است؛ با PERSISTED مقدار deterministic ذخیره می‌شه، اما فضا و هزینهٔ نوشتن می‌خواد. computed column جای DEFAULT یا ورودی دلخواه کاربر نیست.

If a line amount comes from quantity and unit price, storing all three independently invites inconsistency. A computed column records the formula in the schema. It is virtual by default; PERSISTED stores deterministic results, with storage and write costs. It is not a DEFAULT or an arbitrary user input.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

فرمول رو یک‌جا تعریف کن / Define the formula once
DROP TABLE IF EXISTS Lab36.OrderLine;
CREATE TABLE Lab36.OrderLine
(
  OrderLineId int IDENTITY PRIMARY KEY,
  Quantity int NOT NULL CHECK (Quantity > 0),
  UnitPrice decimal(12,2) NOT NULL CHECK (UnitPrice >= 0),
  LineTotal AS (CONVERT(decimal(14,2), Quantity * UnitPrice)) PERSISTED
);
INSERT Lab36.OrderLine (Quantity, UnitPrice) VALUES (3, 12.50);
SELECT Quantity, UnitPrice, LineTotal FROM Lab36.OrderLine;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

نوع عددی رو آگاهانه انتخاب کردیم تا دقت decimal از نوع‌های تقریبی جدا بمونه. اگه قیمت خرید تاریخی باید ثابت بمونه، UnitPrice همین ردیف باید نمونهٔ لحظه‌ای قیمت زمان فروش باشه؛ فرمول درست هم دادهٔ مبنای اشتباه رو نجات نمی‌ده.

We chose decimal deliberately rather than approximate numeric types. If historical purchase price must remain fixed, UnitPrice must be the sale-time snapshot; a correct formula cannot rescue incorrect source data.

rowversion ساعت نیست؛ token تغییر ردیف هست / rowversion is a change token, not a clock

نوع rowversion یک مقدار باینری ۸‌بایتی تولید می‌کنه که با درج یا به‌روزرسانی ردیف تغییر می‌کنه. زمان تقویمی نیست، ترتیب زمانی قابل‌تفسیر بین پایگاه‌داده‌ها نمی‌ده و برای رخدادنگاری جایگزین datetime2 نمی‌شه. کاربردش optimistic concurrency هست: update رو فقط وقتی انجام بده که token همان token خوانده‌شده باشه.

rowversion is an automatically generated 8-byte binary value that changes when a row is inserted or updated. It is not a date/time, does not express a portable timeline across databases, and cannot replace datetime2 for event timestamps. Use it for optimistic concurrency: update only if the token still matches what was read.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

تغییر همزمان رو با شرط token آشکار کن / Detect a concurrent update with the token
DROP TABLE IF EXISTS Lab36.Stock;
CREATE TABLE Lab36.Stock
(
  StockId int PRIMARY KEY,
  Quantity int NOT NULL,
  VersionToken rowversion
);
INSERT Lab36.Stock (StockId, Quantity) VALUES (1, 8);
DECLARE @seen binary(8) = (SELECT VersionToken FROM Lab36.Stock WHERE StockId = 1);
UPDATE Lab36.Stock SET Quantity = Quantity - 1
WHERE StockId = 1 AND VersionToken = @seen;
SELECT @@ROWCOUNT AS RowsChanged, StockId, Quantity, VersionToken FROM Lab36.Stock;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

اگه نشست دیگری ابتدا ردیف رو تغییر دهد، update ما صفر ردیف رو تغییر می‌ده؛ برنامه باید اون رو conflict بداند و دوباره بخواند یا تصمیم کاربری بگیرد. این token خودش retry یا ادغام تغییرها رو انجام نمی‌ده.

If another session changes the row first, our update affects zero rows. The application must treat that as a conflict and reread or ask for a decision. The token does not retry or merge changes by itself.
