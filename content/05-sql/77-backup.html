Backup: گرفتن کافی نیست

Backups: taking one is not enough

داشبورد می‌گه backup هر شب موفق است؛ اما فایل روی همان دیسک دیتابیس هست و کسی restore نکرده. پیش از اطمینان، نوع backup، زنجیره، مقصد، retention و restore رو با شواهد بررسی می‌کنیم.

A dashboard says nightly backups succeed, but the file is on the database disk and nobody has restored it. Before trusting it, inspect backup type, chain, destination, retention, and restore evidence.

پیش‌نیاز: database files، transaction log و بازیابی modelPrerequisites: database files, transaction log, recovery modelحدود ۹۵ دقیقه · ۱۸ تمرین / About 95 minutes · 18 exercises

فرض کن این اتفاق ساعت سه صبح افتادهImagine this happened at 3 a.m.

فصل‌های عملیاتی وقتی ارزش دارن که روز خراب‌شدن سیستم به کارت بیان. برای «Backup: گرفتن کافی نیست» قرار نیست فقط اسم DMV یا گزینهٔ backup رو حفظ کنیم. یه وضعیت قابل‌تکرار می‌سازیم، شواهد جمع می‌کنیم، تغییر رو کنترل‌شده انجام می‌دیم و آخرش ثابت می‌کنیم سیستم واقعاً برگشته؛ نه اینکه فقط یک command بدون خطا تموم شده.

Operations chapters matter when the system is actually broken at 3 a.m. In “Backups: taking one is not enough” we do not memorise DMV names or backup options. We create a reproducible state, collect evidence, make a controlled change, and prove recovery rather than trusting a command that merely completed without error.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

backup strategy به بازیابی model وابسته هست / Strategy depends on recovery model

full backup پایهٔ restore است؛ differential تغییرات پس از آخرین full backup رو نگه می‌داره؛ log backup در FULL/BULK_LOGGED به زنجیرهٔ log و بازیابی تا زمان مشخص کمک می‌کنه. SIMPLE امکان log backup معمول رو نداره. هدف زمانی و اندازهٔ دیتابیس تعیین می‌کنه چه schedule باید.

A full backup is a restore base; a differential captures changes since the last full; log backups in FULL/BULK_LOGGED support the log chain and point-in-time recovery. SIMPLE does not support ordinary log backups. Recovery objectives and database size shape the schedule.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

ساخت full backup در دیتابیس lab / Full backup in a lab database
BACKUP DATABASE ShopLab
TO DISK = 'D:\SqlBackups\ShopLab_full.bak'
WITH INIT, COMPRESSION, CHECKSUM, STATS=10;
GO
RESTORE VERIFYONLY
FROM DISK = 'D:\SqlBackups\ShopLab_full.bak'
WITH CHECKSUM;

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

مسیر نمونه برای SQL Server روی Windows فرض شده و service account باید اجازهٔ نوشتن داشته باشه. مقصد واقعی باید جدا از خرابی domain دیتابیس باشه. VERIFYONLY جای restore کامل و CHECKDB رو نمی‌گیره.

The sample assumes SQL Server on Windows and a path writable by the service account. Production storage should be outside the database failure domain. VERIFYONLY is not a full restore or CHECKDB substitute.

فایل تنها یک قطعه از زنجیره هست / A file is only one part of the chain

تاریخچهٔ msdb برای بررسی زمان و نوع مفید است، اما ممکنه پاک شده باشه و وجود رکورد، قابل‌خواندن بودن فایل رو اثبات نمی‌کنه. فایل رو off-host کپی کن، checksum/دسترسی رو کنترل و در restore environment جدا امتحان کن. backup رمزگذاری‌شده به certificate/key قابل‌بازیابی نیاز داره.

msdb history helps inspect time/type but can be purged; a record does not prove the file is readable. Copy off-host, verify integrity/access, and restore in an isolated environment. Encrypted backups require recoverable certificate/key material.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

تاریخچهٔ backup / Backup history
SELECT TOP (20) database_name,type,backup_start_date,backup_finish_date,
       backup_size,compressed_backup_size
FROM msdb.dbo.backupset
WHERE database_name=N'ShopLab'
ORDER BY backup_finish_date DESC;

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

restore test تنها اثبات بازیابی هست / A restore test proves recovery

RESTORE FILELISTONLY برای logical file name و RESTORE DATABASE با MOVE برای مسیر جدا استفاده می‌شه. دیتابیس مقصد آزمایشی و قابل‌حذف و نامش متفاوت باشه؛ روی تنها نسخهٔ زنده overwrite نکن. پس از restore، CHECKDB و query شناخته‌شده اجرا کن و زمان/حجم رو ثبت کن.

Use RESTORE FILELISTONLY for logical names and RESTORE DATABASE ... MOVE to isolated paths. Restore to a disposable database with a different name; never overwrite the only live copy. Run CHECKDB and known queries after restore and record duration/size.

تمرین: backup artifact رو restore کن / Exercises: restore the backup artifact

Write to a path accessible to the SQL Server service account; never overwrite a real database.
