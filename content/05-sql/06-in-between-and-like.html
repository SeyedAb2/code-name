IN, BETWEEN, and LIKE

تیم یک فهرست status می‌خواد، بازهٔ قیمت رو روی مرزها درست حساب کند و emailهایی رو با یک الگو پیدا کند. می‌شه همه‌چیز رو با OR و مقایسه‌های پراکنده نوشت؛ اما آیا راهی هست که intent روشن‌تر باشه و مرزها رو اشتباه نگیریم؟

The team needs a set of statuses, a price range with correct endpoints, and emails matching a pattern. We could scatter ORs and comparisons everywhere—but can we express intent more clearly and avoid boundary mistakes?

از یک سؤال واقعی شروع کنیمStart with a real question

یه همکار تازه‌وارد معمولاً SQL رو از روی syntax حفظ می‌کنه؛ ولی چند روز بعد که گزارش واقعی می‌رسه، نمی‌دونه از کجا شروع کنه. اینجا برعکس می‌ریم. اول سؤال گزارش رو روشن می‌کنیم، بعد برای «IN، BETWEEN و LIKE» query می‌نویسیم، خروجی رو نگاه می‌کنیم و اگه چیزی عجیب بود از روی همون نتیجه می‌فهمیم کجای مدل ذهنی‌مون ایراد داره.

A newcomer often memorises SQL syntax, then gets stuck on the first real report. We do the opposite: clarify the reporting question, use “IN, BETWEEN, and LIKE” to answer it, inspect the result, and use any surprise as evidence that our mental model needs work.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

سه شکل سؤال، سه شکل predicate / Three question shapes, three predicates

IN برای «یکی از این مقدارها»، BETWEEN برای «داخل این بازه» و LIKE برای «با این الگو جور هست» به‌کار میاد. هریک رو با مثال Shop می‌سنجیم؛ اسم کوتاه‌تر به‌تنهایی دلیل بهتر بودن نیست. مهمه بدانیم endpoint شامل هست یا wildcard چند نویسه رو می‌گیره.

IN expresses “one of these values,” BETWEEN expresses “inside this range,” and LIKE expresses “matches this pattern.” We will test each against Shop. Shorter syntax is not automatically better; know whether endpoints are included and how many characters a wildcard represents.

IN فهرست انتخاب‌ها رو خواناتر می‌کنه / IN makes a value set readable

برای statusهای Paid یا Pending، فهرست مقدارها از چند OR واضح‌تر هست. نوع مقدارهای داخل پرانتز باید با expression مقایسه‌شده سازگار باشه. برای فهرست چند هزار مقداری، query رو به یک دیوار متنی تبدیل نکن؛ مقدارها رو در جدول قرار بده و در فصل‌های JOIN و subquery از آن استفاده می‌کنیم.

For Paid or Pending statuses, a value list is clearer than repeated OR. Values should be compatible with the compared expression. Do not turn a list of thousands into a giant statement; store those values in a table and use later join/subquery techniques.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

دو انتخاب روشن / Two explicit choices
SELECT OrderId, OrderStatus
FROM shop.Orders
WHERE OrderStatus IN ('Paid', 'Pending')
ORDER BY OrderId;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

در دادهٔ تمرینی سه سفارش میان؛ سفارش Cancelled کنار می‌مونه. حواست به NULL باشه: NOT IN همراه NULL می‌تونه نتیجه‌ای غیرمنتظره بدهد، چون مقایسه UNKNOWN می‌شه. فصل ۷ منطق NULL و UNKNOWN رو با جدول truth باز می‌کنه؛ فعلاً مقادیر نامعلوم رو وارد فهرست نکن.

Three fixture orders return; Cancelled is excluded. Be careful with NULL: NOT IN combined with NULL can produce surprising results because the comparison becomes UNKNOWN. Chapter 7 develops NULL and UNKNOWN logic; for now do not add unknown values to the list.

BETWEEN هر دو سر بازه رو می‌گیره / BETWEEN includes both endpoints

نام BETWEEN ممکنه حس «وسط دو مقدار» بدهد، اما شرط شامل مرز پایین و بالا هست. روی قیمت 450 تا 800، هم ماوس 450 و هم پایهٔ مانیتور 800 باید برگردند. اگه خواسته exclusive باشه، عملگرهای > و < رو صریح بنویس.

BETWEEN may sound like “strictly in the middle,” but it includes the lower and upper endpoints. For prices from 450 through 800, both the 450 mouse and 800 stand should return. If endpoints must be excluded, write > and < explicitly.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

آزمایش endpointها / Test the endpoints
SELECT ProductName, UnitPrice
FROM shop.Products
WHERE UnitPrice BETWEEN 450 AND 800
ORDER BY UnitPrice;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

دو ردیف باید ببینی. برای datetime، BETWEEN انتهای دقیق رو هم شامل می‌کنه؛ اگه پایان رو تاریخ بدون ساعت بدهی، نیمه‌شب آن روز است، نه تمام روز. برای گزارش روزانه اغلب بازهٔ نیمه‌باز «از آغاز روز تا پیش از آغاز فردا» قابل‌اعتمادتر هست.

Expect two rows. For datetime, BETWEEN includes the exact endpoint; a date-only end is midnight at the start of that date, not the whole day. Daily reports are often safer as a half-open range: from the day’s start to before the next day’s start.

LIKE الگو می‌گیره، نه عبارت منظم / LIKE uses wildcards, not regular expressions

در T-SQL، درصد یعنی صفر یا چند نویسه؛ underscore یعنی دقیقاً یک نویسه. bracket مثل [PC] یک نویسه از مجموعه می‌گیره و قواعد مقایسه به collation وابسته‌اند. این زبان pattern ساده است، نه regex کامل.

In T-SQL, percent matches zero or more characters and underscore matches exactly one. A bracket set such as [PC] matches one listed character, with comparisons governed by collation. This is a pattern language, not a full regular expression engine.

پسوند email و آغاز status / Email suffix and status prefix
SELECT CustomerId, Email
FROM shop.Customers
WHERE Email LIKE '%@example.test';

SELECT OrderId, OrderStatus
FROM shop.Orders
WHERE OrderStatus LIKE '[PC]%'
ORDER BY OrderId;
GO

اولی domain رو با suffix پیدا می‌کنه؛ دومی statusهای آغازشونده با P یا C رو می‌گیره. اگه wildcard رو به ابتدا اضافه کنی، معمولاً seek ساده روی index سخت‌تر می‌شه؛ این هنوز نتیجهٔ قطعی performance نیست، باید plan و دادهٔ کافی رو بعدتر بسنجیم.

The first matches a domain suffix; the second finds statuses beginning with P or C. A leading wildcard often makes a simple index seek harder, but that is not a complete performance diagnosis—we will measure plans on larger data later.

وقتی خود wildcard داده است، اون رو escape کن / Escape a wildcard when it is data

گاهی مقدار واقعی شامل درصد یا underscore هست. اگه اون رو بی‌escape در pattern بگذاری، SQL Server اون رو wildcard می‌فهمه. در T-SQL می‌تونیم bracket notation یا ESCAPE clause رو به‌کار ببریم؛ این بار دادهٔ ثابت آزمایش می‌سازیم تا لازم نباشه دادهٔ تمرینی رو دست‌کاری کنیم.

Sometimes the stored value itself contains percent or underscore. Unescaped in a pattern, SQL Server treats it as a wildcard. T-SQL supports bracket notation and an ESCAPE clause; we will use a scalar test value so the shared fixture stays unchanged.

جست‌وجوی درصد literal / Search for a literal percent
SELECT N'تخفیف 10%' AS Offer
WHERE N'تخفیف 10%' LIKE N'%10!%%' ESCAPE N'!';
GO

یک ردیف برمی‌گرده: !% درصد واقعی هست و درصدهای بیرونی wildcard هستن. اگه ESCAPE رو حذف کنی، معنای pattern عوض می‌شه. عبارت escape باید درست و کامل باشه؛ escape انتهایی الگوی معتبری نمی‌سازه.

One row returns: !% represents a literal percent, while the outer percent signs are wildcards. Removing ESCAPE changes the pattern’s meaning. The escape sequence must be complete; a trailing escape character is not a valid pattern.

یک نام operator، رفتار هر نوع ستون رو یکسان نمی‌کنه / The operator name does not erase data-type details

مقایسهٔ string تابع collation است؛ بزرگ/کوچک‌حرف و ترتیب برخی حروف ممکنه با collation فرق کند. LIKE روی CHAR/NCHAR ممکنه padding انتهایی رو هم وارد مقایسه کند؛ اگه match غیرمنتظره شد، نوع ستون، نوع pattern و collation مؤثر رو بررسی کن. با دیدن یک خروجی، دربارهٔ همهٔ دیتابیس‌ها حکم نده.

String comparison follows collation, so case behaviour and character ordering can vary. LIKE with CHAR/NCHAR can also involve trailing padding; when a match surprises you, inspect the column type, pattern type, and effective collation. Do not generalise from one database’s result.
