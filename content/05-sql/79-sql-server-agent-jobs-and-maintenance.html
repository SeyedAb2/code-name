SQL Server Agent و Jobهای عملیاتی

SQL Server Agent and operational jobs

backup هر شب باید اجرا بشه، ولی کسی alert نمی‌گیره و تاریخچه فقط چند روز رو نگه می‌داره. Job ساخته‌شده به‌تنهایی عملیات قابل‌اعتماد نیست؛ مسئول، schedule، نتیجه، خروجی و notification رو بررسی می‌کنیم.

A backup should run nightly, but nobody receives alerts and history retains only a few days. A job alone is not reliable operations; we inspect owner, schedule, result, output, and notifications.

فرض کن این اتفاق ساعت سه صبح افتادهImagine this happened at 3 a.m.

فصل‌های عملیاتی وقتی ارزش دارن که روز خراب‌شدن سیستم به کارت بیان. برای «SQL Server Agent و Jobهای عملیاتی» قرار نیست فقط اسم DMV یا گزینهٔ backup رو حفظ کنیم. یه وضعیت قابل‌تکرار می‌سازیم، شواهد جمع می‌کنیم، تغییر رو کنترل‌شده انجام می‌دیم و آخرش ثابت می‌کنیم سیستم واقعاً برگشته؛ نه اینکه فقط یک command بدون خطا تموم شده.

Operations chapters matter when the system is actually broken at 3 a.m. In “SQL Server Agent and operational jobs” we do not memorise DMV names or backup options. We create a reproducible state, collect evidence, make a controlled change, and prove recovery rather than trusting a command that merely completed without error.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

Agent orchestrates tasks; it does not prove outcome / Agent کار را اجرا می‌کند، نه موفقیت کسب‌وکار را

SQL Server Agent service jobها رو با schedule اجرا می‌کنه؛ دسترسی و قابلیت آن به edition و محیط بستگی داره. step می‌تونه SQL، CmdExec یا subsystem دیگری باشه. status موفق فقط exit گزارش‌شدهٔ step است؛ backup artifact، row count یا نتیجهٔ business رو جدا بررسی کن.

SQL Server Agent runs scheduled jobs; availability and capabilities depend on edition/environment. A step can use SQL, CmdExec, or another subsystem. A “success” status is the step's reported exit, not business proof; verify backup artifacts, row counts, or business outcomes separately.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

job و stepها / Inspect jobs and steps
SELECT j.name,j.enabled,j.owner_sid,s.step_id,s.step_name,s.subsystem,s.database_name
FROM msdb.dbo.sysjobs AS j
LEFT JOIN msdb.dbo.sysjobsteps AS s ON s.job_id=j.job_id
ORDER BY j.name,s.step_id;

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

job با هویت مسئول یا proxy اجرا می‌شه / Jobs run under an execution context

job مسئول و subsystem تعیین می‌کنن چه کسی چه دسترسی داره. از sysadmin مسئول یا proxy برای راحتی استفاده نکن. credential در step command، history و output file ممکنه افشا بشه؛ secret رو command line نکن و دسترسی خروجی رو محدود کن.

The owner and subsystem determine execution authority. Do not use a sysadmin owner/proxy for convenience. Credentials can leak into step commands, history, and output files; avoid command-line secrets and restrict output access.

schedule، هم‌پوشانی و خرابی notification / Schedule, overlap, and failure alerts

schedule رو با timezone و maintenance window مقایسه کن. job طولانی ممکنه با run بعدی هم‌پوشانی کند؛ concurrency و lock فشار می‌آورد. retry محدود فقط برای خرابی گذرا و step idempotent مناسب هست. برای missed run، خرابی، duration غیرعادی و artifact نهایی alert طراحی کن.

Compare schedule to timezone and maintenance windows. A long job can overlap its next run, increasing concurrency and lock pressure. Bounded retry fits only transient failure and idempotent steps. Alert on missed runs, failures, unusual duration, and missing final artifacts.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

history job رو query کن / Query job history
SELECT TOP (50) j.name,h.run_date,h.run_time,h.run_status,h.run_duration,h.message
FROM msdb.dbo.sysjobhistory AS h
JOIN msdb.dbo.sysjobs AS j ON j.job_id=h.job_id
WHERE h.step_id=0
ORDER BY h.instance_id DESC;

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

run_date/time قالب عددی داره و history ممکنه purge بشه. برای خط زمانی دقیق‌تر output/پایش مستقل نگه دار.

run_date/time use numeric formats and history can be purged. Keep independent output/monitoring for a durable timeline.

فقط status فعلی Agent رو نبین. job history و schedule رو کنار هم بذار تا معلوم بشه اصلاً اجرا شده یا وسط کار شکست خورده.

Do not inspect only Agent status. Compare schedule and job history to distinguish “never ran” from “ran and failed.”

هر job باید مسئول، شواهد و alert داشته باشه / Every job needs an owner, evidence, and alert

job inventory، مسئول، schedule، زمینه، retry و history رو کنار نتیجهٔ نهایی بررسی کردیم. status سبز کافی نیست؛ artifact یا invariant باید بررسی بشه. فصل بعد routineهای نگهداری و trade-offهایشان رو می‌سنجد.

We reviewed inventory, owner, schedule, context, retry, and history alongside final outcomes. Green status is insufficient; verify the artifact or invariant. Next we assess maintenance routines and their trade-offs.
