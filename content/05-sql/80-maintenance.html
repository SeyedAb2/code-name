نگهداری SQL Server بر اساس شواهد

Evidence-based SQL Server maintenance

هر شب همهٔ indexها rebuild می‌شن و دیتابیس shrink می‌شه؛ صبح گزارش کندتر هست و log پر. maintenance checklist جای تشخیص نیست. هر کار رو به symptom، هزینه و معیار موفقیت وصل می‌کنیم.

Every night all indexes are rebuilt and the database is shrunk; in the morning, reports are slower and the log is full. A maintenance checklist is not diagnosis. We connect each action to a symptom, cost, and success measure.

فرض کن این اتفاق ساعت سه صبح افتادهImagine this happened at 3 a.m.

فصل‌های عملیاتی وقتی ارزش دارن که روز خراب‌شدن سیستم به کارت بیان. برای «نگهداری SQL Server بر اساس شواهد» قرار نیست فقط اسم DMV یا گزینهٔ backup رو حفظ کنیم. یه وضعیت قابل‌تکرار می‌سازیم، شواهد جمع می‌کنیم، تغییر رو کنترل‌شده انجام می‌دیم و آخرش ثابت می‌کنیم سیستم واقعاً برگشته؛ نه اینکه فقط یک command بدون خطا تموم شده.

Operations chapters matter when the system is actually broken at 3 a.m. In “Evidence-based SQL Server maintenance” we do not memorise DMV names or backup options. We create a reproducible state, collect evidence, make a controlled change, and prove recovery rather than trusting a command that merely completed without error.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

fragmentation به‌تنهایی دستور rebuild نیست / Fragmentation alone is not a rebuild command

اندازهٔ index، بار کاری، page density، storage و plan مهم‌اند. rebuild می‌تونه log، فضا، CPU و lock مصرف کند؛ نتیجهٔ statistics و plan رو هم عوض می‌کنه. reorganize کار متفاوت و عموماً سبک‌تری هست. threshold جهانی که همه‌جا درست باشه وجود نداره؛ query و تأخیر رو اندازه بگیر.

Index size, workload, page density, storage, and plan matter. Rebuild consumes log, space, CPU, and possibly locks; it also changes statistics/plans. Reorganize is a different, often lighter operation. There is no universal threshold; measure queries and latency.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

fragmentation رو با size و page count بخوان / Read fragmentation with size/page count
SELECT OBJECT_SCHEMA_NAME(ips.object_id) AS SchemaName,
       OBJECT_NAME(ips.object_id) AS TableName,i.name,
       ips.page_count,ips.avg_fragmentation_in_percent
FROM sys.dm_db_index_physical_stats(DB_ID(),NULL,NULL,NULL,'LIMITED') AS ips
JOIN sys.indexes AS i ON i.object_id=ips.object_id AND i.index_id=ips.index_id
WHERE ips.index_id>0
ORDER BY ips.page_count DESC;

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

DMV می‌تونه هزینهٔ اسکن داشته باشه و خروجی نمونهٔ لحظه‌ای هست. روی دیتابیس مجاز و زمان مناسب اجرا کن؛ برای index کوچک تصمیم maintenance رو فقط از درصد fragmentation نگیر.

The DMV can incur scan cost and returns a snapshot. Run it on an authorized database at a suitable time; do not decide maintenance for a tiny index from fragmentation percentage alone.

statistics، plan رو تغذیه می‌کنه / Statistics informs plans

statistics قدیمی می‌تونه تخمین رو منحرف کند، ولی update بی‌هدف هم compile/plan رو تغییر می‌ده و maintenance load داره. last_updated، modification count، query regression و plan رو کنار هم ببین. index rebuild در بعضی حالت‌ها statistics مربوط به index رو update می‌کنه؛ این رو با همهٔ statistics یکی نگیر.

Stale statistics can mislead estimates, but blind updates affect compilation/plans and add load. Correlate last update, modifications, regressions, and plans. Index rebuild updates its index statistics in relevant cases; that is not equivalent to updating all statistics.

integrity check و backup هرکدوم هدف خودشان رو دارن / Integrity checks and backups serve different goals

DBCC CHECKDB consistency ساختاری رو بررسی می‌کنه و می‌تونه پرهزینه باشه؛ برای آن schedule و ظرفیت مشخص کن. backup file سالم الزاماً دیتابیس سالم رو تضمین نمی‌کنه و CHECKDB هم جای restore drill رو نمی‌گیره. shrink معمولاً فضای آزاد رو به OS برمی‌گردونه ولی index fragmentation و رشد دوباره می‌سازه؛ فقط با علت و برنامهٔ رشد مشخص انجام بده.

DBCC CHECKDB validates structural consistency and can be resource-intensive; schedule it with capacity in mind. A readable backup does not guarantee a healthy database, and CHECKDB does not replace restore drills. Shrink may return free space to the OS but cause fragmentation and regrowth; use it only with a clear cause and growth plan.

log پر است؟ reuse wait رو تشخیص بده / Full log? Diagnose the reuse wait

قبل از shrink، بازیابی model و log_reuse_wait_desc رو بررسی کن؛ transaction باز، log backup جاافتاده، replication/availability feature یا عامل دیگر ممکنه مانع reuse باشه. حذف فایل log یا shrink فوری، علت رو حل نمی‌کنه. log backup رو متناسب با بازیابی objective زمان‌بندی کن.

Before shrinking, inspect recovery model and log_reuse_wait_desc. Open transactions, missing log backups, replication/availability features, or other causes may prevent reuse. Deleting the log file or shrinking immediately does not fix the cause. Schedule log backups to match recovery objectives.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.
