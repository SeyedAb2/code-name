Window functionها؛ OVER و PARTITION BY

Window functions: OVER and PARTITION BY

تحلیل‌گر می‌خواد کنار هر قلم سفارش، مجموع مبلغ همان سفارش و رتبهٔ قلم رو ببیند. `GROUP BY` مبلغ رو می‌ده، اما ردیف‌های قلم رو جمع می‌کنه. window function راه می‌ده خلاصه رو کنار جزئیات نگه داریم.

An analyst wants each order item beside its order total and line rank. GROUP BY can calculate the total, but collapses item rows. A window function lets us keep detail and summary together.

تا اینجا گرفتن چند ردیف آسون بود. درد واقعی وقتی شروع می‌شه که یکی می‌گه «فروش هر شهر رو بده، نسبت به ماه قبل مقایسه کن، فقط شهرهای بالای فلان عدد رو نگه دار و رتبه هم بده». «Window functionها؛ OVER و PARTITION BY» رو برای همین جنس سؤال‌ها می‌خوایم. قدم‌به‌قدم می‌ریم جلو تا query هم درست باشه، هم بشه فهمید چرا درست کار می‌کنه.

Selecting rows is the easy part. Real reporting starts when someone asks for sales by city, a comparison with last month, a threshold, and a rank. “Window functions: OVER and PARTITION BY” belongs to that kind of problem. We build the query step by step so it is not only correct but explainable.

گروه‌بندی جمع می‌کنه؛ پنجره جزئیات رو نگه می‌داره / GROUP BY collapses; a window preserves detail

`SUM(...) OVER (PARTITION BY OrderId)` جمع قلم‌های هر سفارش رو محاسبه می‌کنه، اما هر OrderItem همچنان یک ردیف باقی می‌مونه. PARTITION BY محدودهٔ هر محاسبه رو جدا می‌کنه؛ اگه حذف بشه، پنجره کل ورودی query هست.

`SUM(...) OVER (PARTITION BY OrderId)` calculates each order’s line total while keeping every OrderItem row. PARTITION BY divides calculation scope; without it, the window covers the query input.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

مبلغ کل در کنار هر قلم / Order total beside every line
SELECT oi.OrderId, oi.ProductId, oi.Quantity,
       oi.Quantity * oi.UnitPriceAtSale AS LineAmount,
       SUM(oi.Quantity * oi.UnitPriceAtSale)
           OVER (PARTITION BY oi.OrderId) AS OrderTotal
FROM shop.OrderItems AS oi
ORDER BY oi.OrderId, oi.ProductId;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

مبلغ OrderTotal در چند ردیف همان سفارش تکرار می‌شه؛ این مقدار جدیدی در جدول نیست. اگه بعداً همین خروجی رو دوباره SUM کنی، total رو به تعداد قلم‌ها می‌شماری. grain هنوز یک ردیف برای هر قلم هست.

OrderTotal repeats on each line for that order; it is not a new stored value. Summing that output again would count each order total once per item. The result grain remains one row per item.

PARTITION BY یعنی محاسبه رو از کجا دوباره شروع کن؟ / PARTITION BY defines where calculations restart

بدون PARTITION BY، مجموع روی کل مجموعهٔ OrderItems ساخته می‌شه و روی همهٔ ردیف‌ها تکرار می‌شه. با `PARTITION BY ProductId`، جمع به ازای محصول جداست؛ با چند ستون در partition، هر ترکیب آن ستون‌ها محدودهٔ خودش رو می‌سازه. partition ترتیب نهایی خروجی رو تعیین نمی‌کنه.

Without PARTITION BY, the sum covers the entire OrderItems input and repeats on every row. With `PARTITION BY ProductId`, it resets for each product; multiple columns define each partition by their combination. A partition does not order the final result.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

جمع سراسری و جمع هر محصول / Overall total and per-product total
SELECT oi.OrderId, oi.ProductId,
       SUM(oi.Quantity * oi.UnitPriceAtSale) OVER () AS AllSales,
       SUM(oi.Quantity * oi.UnitPriceAtSale)
           OVER (PARTITION BY oi.ProductId) AS ProductSales
FROM shop.OrderItems AS oi
ORDER BY oi.ProductId, oi.OrderId;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

`OVER()` پنجرهٔ کامل ورودی هست. ORDER BY بیرونی فقط ردیف‌های نمایش‌داده‌شده رو مرتب می‌کنه؛ داخل OVER اگه ORDER BY اضافه کنی، تعریف محاسبهٔ پنجره عوض می‌شه و فصل بعد frame رو دقیق‌تر می‌خوانیم.

`OVER()` means the full input window. The outer ORDER BY sorts displayed rows. Adding ORDER BY inside OVER changes the window calculation; the next chapter examines frames in more detail.

رتبه‌بندی پنجره‌ای ردیف‌ها رو حذف نمی‌کنه / Window ranking does not remove rows

`ROW_NUMBER` برای هر ردیف شمارهٔ یکتا می‌ده؛ `RANK` برای مقدارهای برابر رتبهٔ یکسان می‌ده و بعد شمارهٔ رتبه می‌پرد؛ `DENSE_RANK` رتبهٔ مساوی می‌ده اما پرش نداره. PARTITION BY رتبه رو برای هر سفارش از نو آغاز می‌کنه. برای شمارهٔ کاملاً قطعی، ترتیب پنجره رو تا کلید یکتا کامل کن.

ROW_NUMBER assigns each row a unique number; RANK gives ties the same rank and leaves gaps; DENSE_RANK gives ties the same rank without gaps. PARTITION BY restarts rankings per order. For deterministic numbering, complete the window order with a unique key.

رتبهٔ قیمت اقلام درون هر سفارش / Rank line prices within each order
SELECT oi.OrderId, oi.ProductId, oi.UnitPriceAtSale,
       ROW_NUMBER() OVER
           (PARTITION BY oi.OrderId
            ORDER BY oi.UnitPriceAtSale DESC, oi.ProductId) AS RowNum,
       RANK() OVER
           (PARTITION BY oi.OrderId
            ORDER BY oi.UnitPriceAtSale DESC) AS PriceRank,
       DENSE_RANK() OVER
           (PARTITION BY oi.OrderId
            ORDER BY oi.UnitPriceAtSale DESC) AS DensePriceRank
FROM shop.OrderItems AS oi
ORDER BY oi.OrderId, RowNum;
GO

ProductId در ROW_NUMBER tie رو می‌شکند؛ در دو رتبهٔ قیمتی عمداً فقط قیمت کلید هست تا قیمت‌های برابر tie بمانند. بدون ORDER BY بیرونی، ترتیب نمایش نتیجه تضمین نمی‌شه.

ProductId breaks ties for ROW_NUMBER. The two price ranks intentionally order only by price so equal prices remain ties. Without an outer ORDER BY, display order is not guaranteed.

دو پرسش، دو ابزار: خلاصهٔ گروه یا جزئیات با summary؟ / Two questions, two tools

اگه فقط یک ردیف در هر سفارش می‌خوای، GROUP BY مناسب هست. اگه هر قلم باید بمونه و total هم کنارش باشه، window function مناسب هست. این‌ها جایگزین مطلق هم نیستند؛ grain گزارش انتخاب رو تعیین می‌کنه.

If you need one row per order, use GROUP BY. If every item should remain beside its total, use a window function. Neither replaces the other universally; the report grain determines the choice.

مقایسهٔ خروجی در سطح سفارش و قلم / Order grain versus item grain
-- One row per order:
SELECT OrderId, SUM(Quantity * UnitPriceAtSale) AS Total
FROM shop.OrderItems GROUP BY OrderId;
GO

-- One row per item, with its order total:
SELECT OrderId, ProductId,
       SUM(Quantity * UnitPriceAtSale)
           OVER (PARTITION BY OrderId) AS Total
FROM shop.OrderItems;
GO

در نسخهٔ دوم Total تکرار می‌شه. اگه downstream aggregation داری، مراقب باش summary تکرارشده رو دوباره جمع نکنی. پنجره نتیجهٔ منطقی می‌سازه و به‌خودی‌خود داده رو ذخیره نمی‌کنه.

In the second query, Total repeats. If a downstream aggregation follows, do not sum the repeated summary again. The window produces a logical result; it does not store data.

یک پنجره روی گروه، چند ردیف جزئیات / One partition, multiple detail rows

عددها صرفاً نمایشی‌اند؛ نکته اینه که یک نتیجهٔ aggregate روی هر ردیف partition ظاهر می‌شه و grain جزئیات تغییر نمی‌کنه.

Numbers are illustrative; the point is that an aggregate appears on every row in its partition while detail grain remains unchanged.
