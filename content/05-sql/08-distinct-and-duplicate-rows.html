DISTINCT و سطرهای تکراری

DISTINCT and duplicate rows

مدیر فهرست شهرهای مشتری‌ها رو می‌خواد. query ساده چهار ردیف می‌ده و تهران دوبار تکرار شده. آیا یکی از مشتری‌ها رو حذف کنیم؟ نه؛ شاید فقط فهرست مقدارهای یکتا خواسته شده. اول باید مشخص کنیم تکرار رو در کدوم ستون یا ترکیب ستون‌ها می‌سنجیم.

A manager asks for the cities represented among customers. The simple query returns four rows and repeats Tehran. Should we delete a customer? No—the request may be for unique values. First define which column or combination of columns determines repetition.

Prerequisite: chapters 4–7SQL Server 2025 · Shop fixture۷۵ دقیقه · ۱۸ تمرین / 75 minutes · 18 exercises

از یک سؤال واقعی شروع کنیمStart with a real question

یه همکار تازه‌وارد معمولاً SQL رو از روی syntax حفظ می‌کنه؛ ولی چند روز بعد که گزارش واقعی می‌رسه، نمی‌دونه از کجا شروع کنه. اینجا برعکس می‌ریم. اول سؤال گزارش رو روشن می‌کنیم، بعد برای «DISTINCT و سطرهای تکراری» query می‌نویسیم، خروجی رو نگاه می‌کنیم و اگه چیزی عجیب بود از روی همون نتیجه می‌فهمیم کجای مدل ذهنی‌مون ایراد داره.

A newcomer often memorises SQL syntax, then gets stuck on the first real report. We do the opposite: clarify the reporting question, use “DISTINCT and duplicate rows” to answer it, inspect the result, and use any surprise as evidence that our mental model needs work.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

تکرار مقدار، الزاماً تکرار موجودیت نیست / Repeated values are not repeated entities

Customers چهار مشتری داره؛ دو نفرشان در تهران‌اند. اگه فقط City رو انتخاب کنی، تهران دو بار دیده می‌شه چون دو ردیف مشتری آن مقدار رو دارن. DISTINCT می‌گه از میان ردیف‌های projection انتخاب‌شده، نسخه‌های برابر رو یکی کن؛ نمی‌گه مشتری‌ها یکی‌اند.

Customers has four people, two of them in Tehran. Selecting only City repeats Tehran because two customer rows carry that value. DISTINCT removes equal rows from the chosen projection; it does not claim the customers are the same entity.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

قبل و بعد رو مقایسه کن / Compare before and after
SELECT City FROM shop.Customers;
SELECT DISTINCT City FROM shop.Customers ORDER BY City;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

اولی چهار ردیف است؛ دومی سه شهر. ORDER BY رو جدا اضافه کردیم چون DISTINCT ترتیب خروجی رو تضمین نمی‌کنه. این نتیجه مجوز حذف هیچ customer row نیست.

The first query has four rows; the second has three cities. ORDER BY is explicit because DISTINCT does not guarantee result ordering. This is no reason to delete a customer row.

DISTINCT کل projection رو مقایسه می‌کنه / DISTINCT compares the entire projection

حالا FullName رو هم انتخاب کن. اگه هدف شهرهای یکتا بود، افزودن نام سؤال رو عوض کرد: حالا زوج City و FullName باید تکراری باشه تا حذف بشه. چون هر مشتری نام متفاوت داره، چهار ردیف می‌مونه. SQL Server هر ستون رو مستقل deduplicate نمی‌کنه.

Now include FullName. If the goal was unique cities, adding a name changes the question: the City/FullName pair must now repeat to be removed. Since each customer has a different name, all four rows remain. SQL Server does not deduplicate each selected column independently.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

یک ستون اضافه، معیار متفاوت / One more column changes uniqueness
SELECT DISTINCT City, FullName
FROM shop.Customers
ORDER BY City, FullName;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

پس پیش از افزودن DISTINCT بپرس: «ردیف یکتا» در این گزارش یعنی یکتای چه چیزی؟ شناسهٔ مشتری، شهر، یا ترکیب سفارش و محصول؟ جواب از نیاز گزارش میاد، نه از شکل دادهٔ تکراری.

Before adding DISTINCT, ask what “unique row” means for this report: customer, city, or order/product pair? The answer comes from the report requirement, not merely from seeing repeated values.

وقتی عدد می‌خوای، تعداد رو مستقیم بپرس / Ask for a count when you need a count

گاهی فقط تعداد شهرهای یکتا باید. می‌توانی DISTINCT رو در aggregate به‌کار ببری. اگه تعداد افراد هر شهر رو می‌خوای، DISTINCT جواب نیست؛ باید گروه‌بندی کنی تا مقدار هر شهر و شمار اعضایش رو کنار هم ببینی. فصل ۱۹ GROUP BY رو عمیق‌تر می‌کنه.

Sometimes you need only the number of unique cities, which can be expressed with DISTINCT inside an aggregate. If you need people per city, DISTINCT is not the answer; group the rows to report each city and its count. Chapter 19 develops GROUP BY further.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

تعداد شهرهای یکتا / Count unique cities
SELECT COUNT(DISTINCT City) AS CityCount
FROM shop.Customers;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

خروجی ۳ هست. عدد ۳ به‌تنهایی فهرست شهرها رو نمی‌ده و تضمین نمی‌کنه دادهٔ مشتری‌ها کامل است؛ فقط تعداد مقدارهای متمایز غیر NULL رو در expression می‌گه.

The result is 3. The count alone does not list the cities or prove customer data is complete; it reports the distinct non-NULL values of that expression.

DISTINCT رو چسب زخم JOIN نکن / Do not use DISTINCT as a JOIN bandage

در فصل‌های JOIN می‌بینیم یک سفارش می‌تونه چند OrderItem داشته باشه. اگه گزارش یک ردیف به‌ازای هر سفارش می‌خواد ولی join پنج ردیف طبیعی می‌سازه، DISTINCT ممکنه ظاهراً تکرار رو پنهان کند، اما grain و مقدارهای درست رو معلوم نمی‌کنه. اول از رابطه بپرس چند ردیف باید وجود داشته باشه؛ بعد join یا aggregation رو اصلاح کن.

A later JOIN chapter will show that one order can have several OrderItems. If a report wants one row per order but the join naturally returns multiple lines, DISTINCT may hide repetition without defining the correct grain or values. First decide how many rows the relationship should produce; then fix the join or aggregation.

پنج line یعنی چه؟ / What do five lines mean?
SELECT o.OrderId, oi.ProductId
FROM shop.Orders AS o
JOIN shop.OrderItems AS oi ON oi.OrderId = o.OrderId
ORDER BY o.OrderId, oi.ProductId;
GO

پنج ردیف نتیجه با پنج line فروش سازگار است؛ این لزوماً duplicate اشتباه نیست. DISTINCT روی OrderId،ProductId هم زوج‌ها رو حذف نمی‌کنه چون هر line محصولی متفاوت در همان سفارش داره.

Five result rows match five sale lines; that is not necessarily an accidental duplicate. DISTINCT on OrderId/ProductId does not collapse them because each line has its own product within its order.
