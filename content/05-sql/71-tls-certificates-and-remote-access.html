TLS و certificate برای اتصال SQL Server

TLS certificates for SQL Server connections

port باز هست و login هم درست؛ اما client خطای certificate می‌ده. تیم می‌خواد TrustServerCertificate رو روشن کند تا «کار کند». اول می‌فهمیم TLS چه چیزی رو تأمین می‌کنه، بعد trust و hostname رو درست می‌کنیم.

The port is open and credentials are correct, but the client reports a certificate error. The team wants to enable TrustServerCertificate to “make it work.” We will understand TLS first, then fix trust and hostname validation.

اپ می‌گه «به دیتابیس وصل نمی‌شم»؛ از کجا شروع کنیم؟The app says “I cannot reach the database”; where do we start?

خطای اتصال یه اسم مشترک برای چند مشکل کاملاً متفاوته: DNS، پورت، TLS، instance، firewall یا خود login. توی «TLS و certificate برای اتصال SQL Server» مسیر اتصال رو تکه‌تکه می‌کنیم. هر بار فقط یک لایه رو ثابت می‌کنیم تا به‌جای عوض‌کردن تصادفی تنظیمات، دقیقاً بدونیم شکست کجاست.

“Cannot connect” is one phrase for several different failures: DNS, port, TLS, instance discovery, firewall, or authentication. In “TLS certificates for SQL Server connections” we split the path into layers and prove one layer at a time instead of changing random settings.

TLS اتصال رو رمز و peer رو اعتبارسنجی می‌کنه / TLS encrypts traffic and validates the peer

TCP فقط مسیر رو باز می‌کنه. TLS در مذاکرهٔ اتصال، نسخه و cipher رو انتخاب می‌کنه و certificate رو برای هویت سرور به client نشان می‌ده. encryption بدون بررسی trust و نام سرور می‌تونه در برابر حملهٔ واسط ضعیف باشه. port reachable با اتصال معتبر TLS یکی نیست.

TCP only establishes reachability. TLS negotiates protocol/cipher and presents the server certificate for client identity validation. Encryption without trust and hostname verification is weaker against interception. A reachable port is not a validated TLS connection.

certificate باید نام و زنجیرهٔ مورد اعتماد داشته باشه / Certificate needs a trusted name and chain

certificate باید شرایط SQL Server و محیط سازمان رو داشته باشه، hostname مورد استفادهٔ client رو پوشش دهد و زنجیره‌اش روی client trusted باشه. service account باید دسترسی لازم به private key داشته باشه. تاریخ انقضا و تمدید رو operational monitor کن؛ private key رو داخل image یا Git نگذار.

The certificate must meet SQL Server and organizational requirements, cover the client hostname, and chain to a client-trusted root. The service account needs access to the private key. Monitor expiry and renewal; never bake the private key into an image or Git.

تنظیم client رو با driver واقعی تست کن / Test the actual client driver

درایورها و نسخه‌ها default متفاوت دارن. connection string باید encryption رو درخواست کند و certificate رو validate کند؛ TrustServerCertificate معمولاً اعتبارسنجی گواهی رو دور می‌زند و راه‌حل production نیست. تنظیم server-side force encryption و client-side request رو جدا بررسی کن.

Drivers and versions can have different defaults. Configure the connection string to require encryption and validate the certificate. TrustServerCertificate bypasses certificate validation and is not a production fix. Verify server force-encryption and client request separately.

نمونهٔ query برای session رمز‌شده / Query encrypted session metadata
SELECT session_id,encrypt_option,auth_scheme,net_transport
FROM sys.dm_exec_connections
WHERE session_id=@@SPID;

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

دسترسی DMV و معنای ستون‌ها رو در نسخه/محیط هدف بررسی کن؛ نتیجه فقط session جاری رو نشان می‌ده و certificate trust سمت client رو به‌تنهایی اثبات نمی‌کنه.

Verify DMV access and columns for the target version. This describes the current session and does not by itself prove client certificate trust.

راه‌دور رو محدود و قابل‌چرخش نگه دار / Keep remote access scoped and rotatable

SQL port رو به subnet یا application host مشخص محدود کن؛ اگه ممکنه private network/VPN به‌کار ببر. certificate renewal رو با هم‌پوشانی و rollback برنامه‌ریزی کن. دسترسی public به 1433 و خاموش‌کردن validation برای رفع فوری، هر دو بدهی امنیتی می‌سازند.

Restrict SQL ports to known application subnets/hosts and prefer private networking/VPN. Plan certificate rotation with overlap and rollback. Public exposure of 1433 and disabling validation as a quick fix both create security debt.

اتصال امن، port باز به‌تنهایی نیست / A secure connection is more than an open port

TCP، handshake، trust chain، نام certificate، authentication و مجوز query رو جدا بررسی کردیم. میان‌بر خاموش‌کردن trust رو انتخاب نکردیم؛ certificate و driver رو اصلاح کردیم. بعدی Linked Server است؛ قابلیتی که با عبور از یک server دیگر، مرز دسترسی رو پیچیده‌تر می‌کنه.

We separated TCP, handshake, certificate chain/name, authentication, and query permission. Rather than disabling trust checks, we fixed the certificate and driver. Next is Linked Server, which complicates access boundaries across servers.
