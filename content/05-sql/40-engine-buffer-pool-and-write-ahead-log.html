Engine، buffer pool و ثبت پیش‌نویس تغییر

The engine, buffer pool, and write-ahead log

یک UPDATE تمام می‌شه و برنامه پاسخ موفق می‌گیره؛ آیا همان لحظه کل data page هم روی فایل داده نوشته شد؟ اگه سرور crash کند، موتور از کجا می‌فهمه چه چیزی رو دوباره انجام دهد و چه چیزی رو برگرداند؟ جواب رو با مسیر واقعی تغییر می‌سازیم، نه با عبارت مبهم «ذخیره شد».

An UPDATE completes and the application receives success—but was the entire data page written to the data file at that moment? If the server crashes, how does the engine know what to redo and undo? We follow the actual change path rather than saying vaguely that it was “saved.”

حالا بریم زیر کاپوتNow look under the hood

یه query از بیرون خیلی ساده‌ست: می‌فرستیش و جواب میاد. ولی وقتی کند می‌شه، دیگه اون نمای بیرونی کافی نیست. برای «Engine، buffer pool و ثبت پیش‌نویس تغییر» یه لایه پایین‌تر می‌ریم و مسیر داده رو دنبال می‌کنیم؛ نه برای حفظ‌کردن اصطلاحات داخلی، برای اینکه وقتی plan یا I/O رفتار عجیبی داشت بفهمیم SQL Server واقعاً داره چه کاری انجام می‌ده.

A query looks simple from the outside: send it, get rows back. Once it becomes slow, that view is not enough. In “The engine, buffer pool, and write-ahead log” we move one layer down and follow the data path—not to memorise internals, but to explain what SQL Server is actually doing when plans and I/O behave unexpectedly.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

page تغییرکرده ممکنه مدتی در buffer pool بمونه / A changed page can remain in the buffer pool

موتور pageهای موردنیاز رو در buffer pool نگه می‌داره. UPDATE نسخهٔ درون حافظه رو dirty می‌کنه؛ لازم نیست هر تغییر فوراً data file رو بازنویسی کند. همین بافرکردن I/O رو کارآمد می‌کنه، اما دوام transaction به مسیر log وابسته هست.

The engine keeps needed pages in the buffer pool. UPDATE marks the in-memory page dirty; the data file need not be rewritten immediately. Buffering improves I/O efficiency, while transaction durability relies on the log path.

UPDATE
  → buffer pool page becomes dirty
  → transaction log records the change
  → COMMIT waits for log flush (fully durable default)
  → checkpoint/background writer writes dirty data pages later

این تصویر ساده‌شده است؛ ممکنه چند log ثبت و page درگیر باشند. نکتهٔ اصلی ترتیب هست: log ثبت تغییر باید پیش از نوشتن dirty data page روی دیسک پایدار شده باشه؛ این رفتار write-ahead logging هست.

This is simplified; many records and pages may be involved. The important ordering is that a change's log record must be durable before its dirty data page is written to disk. This is write-ahead logging.

COMMIT لزوماً data page رو flush نمی‌کنه / COMMIT does not necessarily flush the data page

در حالت fully durable پیش‌فرض، COMMIT تا flush شدن log ثبتهای لازم به storage منتظر می‌مونه؛ لازم نیست همان لحظه data page مقصد هم flush بشه. بعد از crash، بازیابی تغییر committed رو redo و transaction ناتمام رو undo می‌کنه. دوام نهایی به storage و تنظیمات هم وابسته است؛ delayed durability قرارداد متفاوتی داره.

With default fully durable behavior, COMMIT waits for required log records to flush to storage; the corresponding data page need not flush at that moment. After a crash, recovery redoes committed changes and undoes incomplete transactions. Durability also depends on storage and configuration; delayed durability changes the contract.

تغییر محدود و قابل‌مشاهده / A bounded, observable update
IF OBJECT_ID(N'dbo.EngineLab', N'U') IS NOT NULL DROP TABLE dbo.EngineLab;
CREATE TABLE dbo.EngineLab (Id int PRIMARY KEY, Balance decimal(12,2) NOT NULL);
INSERT dbo.EngineLab VALUES (1, 100.00);
BEGIN TRANSACTION;
UPDATE dbo.EngineLab SET Balance = Balance - 10 WHERE Id = 1;
SELECT Balance AS InsideTransaction FROM dbo.EngineLab WHERE Id = 1;
COMMIT TRANSACTION;
SELECT Balance AS AfterCommit FROM dbo.EngineLab WHERE Id = 1;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

این آزمایش crash ایجاد نمی‌کنه و نباید هم ایجاد کند. برای شناخت بازیابی از شواهد مستند و database آزمایشی و قابل‌حذف استفاده می‌شه؛ COMMIT رو با «page همین الان در فایل داده هست» یکی نگیر.

This experiment does not—and should not—cause a crash. Study recovery with documented evidence and a disposable database; do not equate COMMIT with an immediate data-file page write.

Checkpoint dirty page رو می‌نویسه؛ backup نیست / A checkpoint writes dirty pages; it is not a backup

checkpoint نقطه‌ای برای شروع بازیابی می‌سازه و dirty pageهای database رو به data file می‌نویسه. log رو «خالی» نمی‌کنه و جای full/differential/log backup نیست. transaction باز طولانی می‌تونه بخش فعال log رو نگه داره. برای log بزرگ، علت رو پیدا کن؛ shrink فوری تشخیص نیست.

A checkpoint creates a recovery starting point and writes dirty pages to data files. It does not empty the log and is not a full, differential, or log backup. A long-running transaction can retain active log records. Diagnose a large log before considering shrink.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

وضعیت جاری log رو بخوان / Inspect current log state
SELECT total_log_size_in_bytes / 1048576.0 AS TotalLogMB,
       used_log_space_in_bytes / 1048576.0 AS UsedLogMB,
       used_log_space_in_percent
FROM sys.dm_db_log_space_usage;
GO
SELECT name, recovery_model_desc, log_reuse_wait_desc
FROM sys.databases WHERE database_id = DB_ID();
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

این query تاریخچهٔ رشد نیست. FULL بازیابی به log backup منظم و زنجیرهٔ restore نیاز داره؛ SIMPLE رفتار truncation متفاوتی داره. بازیابی model و reuse wait رو بخوان، transactionهای فعال و فضای دیسک رو بررسی کن و بعد علت رو رفع کن.

These queries do not show growth history. FULL recovery requires regular log backups and a restore chain; SIMPLE has different truncation behavior. Inspect recovery model, reuse wait, active transactions, and disk space before addressing the cause.

Recovery دو کار داره: redo و undo / Recovery performs redo and undo

بعد از توقف ناگهانی، موتور log رو بررسی می‌کنه: تغییرهای ثبت‌شدهٔ لازم که هنوز به data page نرسیده‌اند redo می‌شن؛ transaction بدون COMMIT undo می‌شه. checkpoint مقدار کار رو کم می‌کنه، نه اینکه اون رو حذف کند. زمان بازیابی به log فعال، I/O و transactionهای باز وابسته هست.

After an unexpected stop, the engine examines the log: required logged changes not yet on data pages are redone; transactions without COMMIT are undone. Checkpoints reduce work, not eliminate it. Recovery time depends on active log volume, I/O, and open transactions.

دوام transaction، نوشتن page و backup سه لایه‌اند. اشتباه‌گرفتن‌شان هم ادعای نادرست دربارهٔ crash بازیابی می‌سازه و هم ممکنه نقطهٔ بازیابی لازم رو از بین ببرد.

Transaction durability, page writing, and backups are separate layers. Confusing them creates false crash-recovery claims and can lose the required restore point.

دوام transaction با نوشتن data page یکی نیست / Transaction durability is not the same as flushing a data page

تغییر dirty page و log ثبت می‌سازه. WAL ترتیب رو حفظ می‌کنه؛ در full durability، COMMIT پس از flush log برمی‌گرده؛ checkpoint بعداً page رو می‌نویسه؛ بازیابی committed رو redo و ناتمام رو undo می‌کنه. backup همچنان باید.

A change creates a dirty page and log record. WAL preserves ordering; under full durability, COMMIT returns after log flush; a checkpoint writes pages later; recovery redoes committed work and undoes incomplete work. Backups are still required.

  • COMMIT رو با flush فوری data اشتباه نگرفته‌ام / COMMIT is not an immediate data-page flush.
  • checkpoint رو backup فرض نکرده‌ام / A checkpoint is not a backup.
  • log growth با شواهد بررسی می‌شه / Log growth is diagnosed with evidence.
