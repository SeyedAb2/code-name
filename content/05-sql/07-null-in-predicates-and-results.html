NULL در شرط و نتیجه

NULL in predicates and results

همکارمان برای مشتری‌های بدون email می‌نویسه Email = NULL و هیچ ردیفی نمی‌گیره. آیا دیتابیس خراب است، یا ما از «نامعلوم» انتظار یک مقدار عادی داریم؟

A teammate searches for customers without email using Email = NULL and gets no rows. Is the database broken, or are we treating “unknown” like an ordinary value?

از یک سؤال واقعی شروع کنیمStart with a real question

یه همکار تازه‌وارد معمولاً SQL رو از روی syntax حفظ می‌کنه؛ ولی چند روز بعد که گزارش واقعی می‌رسه، نمی‌دونه از کجا شروع کنه. اینجا برعکس می‌ریم. اول سؤال گزارش رو روشن می‌کنیم، بعد برای «NULL در شرط و نتیجه» query می‌نویسیم، خروجی رو نگاه می‌کنیم و اگه چیزی عجیب بود از روی همون نتیجه می‌فهمیم کجای مدل ذهنی‌مون ایراد داره.

A newcomer often memorises SQL syntax, then gets stuck on the first real report. We do the opposite: clarify the reporting question, use “NULL in predicates and results” to answer it, inspect the result, and use any surprise as evidence that our mental model needs work.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

نبودن داده رو در یک دادهٔ تمرینی کوچک بساز / Create a small missing-data fixture

جدول Shop عمداً email رو اجباری کرده؛ schema اصلی رو دست‌کاری نمی‌کنیم. جدول موقت session-local چهار حالت می‌سازه: مقدار عادی، رشتهٔ خالی، صفر و NULL. همهٔ تمرین‌ها رو در همین connection اجرا کن و تا پایان نبندش.

The Shop schema intentionally requires email, so we leave it unchanged. A session-local temp table gives us ordinary values, an empty string, zero, and NULL. Run the exercises in the same connection and keep it open.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

ساخت و دیدن داده / Create and inspect
DROP TABLE IF EXISTS #ContactProbe;
CREATE TABLE #ContactProbe
(
 ContactId int NOT NULL PRIMARY KEY,
 Email varchar(100) NULL,
 Score int NULL
);
INSERT #ContactProbe VALUES
 (1,'a@example.test',10),
 (2,'s@example.test',0),
 (3,'',5),
 (4,NULL,NULL);
SELECT * FROM #ContactProbe ORDER BY ContactId;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

چهار ردیف می‌بینی. ردیف ۳ رشتهٔ خالی داره؛ ردیف ۴ unknown. NULL نه صفر است، نه فاصله و نه رشتهٔ خالی.

Four rows appear. Row 3 has an empty string; row 4 is unknown. NULL is not zero, whitespace, or an empty string.

مقایسه با NULL سه‌حالته هست / Comparisons involving NULL have three outcomes

برای مقدارهای معلوم، مقایسه معمولاً TRUE یا FALSE می‌شه. با NULL نتیجه می‌تونه UNKNOWN باشه. WHERE فقط TRUE رو نگه می‌داره؛ FALSE و UNKNOWN رو حذف می‌کنه. برای همین Email = NULL آزمایش null بودن نیست.

For known values, comparisons are usually TRUE or FALSE. With NULL, the result can be UNKNOWN. WHERE keeps only TRUE and filters both FALSE and UNKNOWN. Therefore Email = NULL is not a nullness test.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

مقایسهٔ معمولی به‌جای آزمون NULL / Equality is not a NULL test
SELECT ContactId FROM #ContactProbe WHERE Email = NULL;
SELECT ContactId FROM #ContactProbe WHERE Email IS NULL;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

query اول هیچ ردیفی نمی‌ده؛ دومی فقط ردیف ۴ رو. برای مقدار خالی از Email = '' استفاده کن. این‌ها سه وضعیت متفاوت‌اند و تصمیم کسب‌وکار باید روشن کند هرکدوم چه معنایی داره.

The first query returns no rows; the second returns row 4. Use Email = '' for the empty string. These are three different states, and the business rule must say what each means.

NOT IN و NULL می‌توانند نتیجه رو خالی کنند / NULL can make NOT IN return nothing

اگه فهرست NOT IN شامل NULL باشه، نتیجهٔ مقایسه برای مقدارهای دیگر هم ممکنه UNKNOWN بشه. این رفتار از منطق سه‌حالته میاد. وقتی منبع فهرست می‌تونه NULL داشته باشه، شرط رو بی‌مدرک به NOT IN نسپار؛ در فصل subquery الگوهای دقیق‌تر رو می‌آزماییم.

If a NOT IN list contains NULL, comparisons for other values can also become UNKNOWN. This follows from three-valued logic. When the source may contain NULL, do not assume NOT IN behaves like a simple complement; later we test more precise subquery patterns.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

یک مورد قابل‌پیش‌بینی / A reproducible case
SELECT 1 AS Candidate WHERE 1 NOT IN (2, NULL);
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

خروجی خالی است؛ شرط TRUE نشده. جایگزین مناسب به خواسته بستگی داره، پس اول معنا رو مشخص کن و بعد query رو انتخاب کن.

The result is empty because the predicate never became TRUE. The right replacement depends on the requirement, so state the meaning before choosing a query.

یه مکث کوتاه؛ واقعاً چی فهمیدیم؟Quick pause: what do we actually know now?

قبل از اینکه بریم بخش بعد، سعی کن بدون نگاه‌کردن به بالا در دو جمله بگی این فصل چه مسئله‌ای رو حل می‌کنه و از کدوم خروجی می‌فهمی راه‌حلت درست بوده. اگه فقط اسم دستورها یادت مونده، هنوز یه دور دیگه مثال قبلی رو با دادهٔ متفاوت اجرا کن.

Before moving on, explain in two sentences what problem this chapter solves and which output proves your solution is correct. If you only remember command names, rerun the previous example with different data.

COUNT(*) و COUNT(column) دو سؤال می‌پرسند / COUNT(*) and COUNT(column) answer different questions

COUNT(*) ردیف‌ها رو می‌شمارد. COUNT(Email) مقدارهای non-NULL را؛ رشتهٔ خالی هم مقدار حساب می‌شه. اگه عددها فرق داشتند، الزاماً row گم نشده هست.

COUNT(*) counts rows. COUNT(Email) counts non-NULL values; an empty string still counts as a value. Different totals do not necessarily mean a row is missing.

تعداد ردیف و مقدار معلوم / Rows versus known values
SELECT COUNT(*) AS RowCount,
       COUNT(Email) AS KnownEmails,
       COUNT(Score) AS KnownScores
FROM #ContactProbe;
GO

خروجی ۴، ۳، ۳ هست. این عدد completeness اولیه رو نشان می‌ده؛ اما نمی‌گه چرا مقدار نامعلوم هست یا نبودنش قابل‌قبول هست.

The result is 4, 3, and 3. This is a basic completeness signal, but it does not explain why a value is unknown or whether that absence is acceptable.

برای «صفر یا ناموجود» بنویس Score = 0 OR Score IS NULL. عبارت Score <> 0 مقدار NULL رو شامل نمی‌شه. اگه این فرق در گزارش گم بشه، نتیجهٔ کسب‌وکار غلط هست.

For “zero or missing,” write Score = 0 OR Score IS NULL. Score <> 0 does not include NULL. Losing this distinction can produce a wrong business result.
