برنامهٔ اجرا ۲: Nested Loops، Hash و Merge Join

Execution plans 2: Nested Loops, Hash, and Merge Join

در دو plan، همان JOIN یک‌بار با Nested Loops و بار دیگر با Hash انجام می‌شه. کدوم‌یک اشتباهه؟ هیچ‌کدوم فقط به‌خاطر اسم. روش join به اندازهٔ ورودی‌ها، index و ترتیب داده وابسته است؛ خطای estimate می‌تونه باعث بشه انتخاب مناسب برای ورودی کوچک، برای ورودی بزرگ فاجعه بشه.

The same JOIN uses Nested Loops in one plan and Hash in another. Which is wrong? Neither by name alone. Join strategy depends on input sizes, indexes, and ordering; a bad estimate can make a good small-input choice disastrous for a large one.

A user says “the report is slow” and the first temptation is to add an index or rewrite the query. Do not. In “Execution plans 2: Nested Loops, Hash, and Merge Join” we capture a baseline, read the plan and row counts, form one hypothesis, and change one thing. If it improves, we must explain why; if it regresses, we still need evidence.

Nested Loops برای outer کوچک و inner قابل‌جست‌وجو خوب هست / Nested Loops can suit a small outer input and searchable inner side

Nested Loops هر ردیف ورودی outer رو می‌گیره و برایش inner رو جست‌وجو می‌کنه. اگه outer کوچک و روی inner index مناسب باشه، کم‌هزینه هست. اگه optimizer صد ردیف حدس بزند ولی صدها هزار ردیف برسد، inner operation بارها تکرار می‌شه. در plan تعداد Actual Executions و Actual Rows رو کنار estimated ببین.

Nested Loops takes each outer row and searches the inner input. It can be efficient when the outer side is small and the inner side has a useful index. If the optimizer estimates 100 rows but hundreds of thousands arrive, the inner operation repeats many times. Inspect actual executions and rows beside estimates.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

کاربرهای کمی از جدول کوچک، سفارش‌های زیادی پیدا کنند / Small customer set probes a larger order table

FROM Lab42.Ticket AS t
JOIN Lab42.Ticket AS o ON o.TenantId = t.TenantId
WHERE t.TicketId = 1;
GO

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

این دادهٔ تمرینی فقط شکل operator رو نشان می‌ده و join معنای کسب‌وکاری واقعی نداره؛ برای مطالعهٔ plan از Shop یا schema اختصاصی استفاده کن. نکته اینه که outer واقعی چند ردیف داره و inner چطور match رو پیدا می‌کنه.

Hash و Merge ورودی رو با روش متفاوت تطبیق می‌دهند / Hash and Merge match inputs differently

Hash Join معمولاً از یک ورودی hash table می‌سازه و ورودی دیگر رو probe می‌کنه؛ ورودی بزرگ یا estimate غلط می‌تونه memory grant ناکافی و spill به tempdb بسازد. Merge Join دو ورودی مرتب رو به‌صورت هم‌زمان پیش می‌برد؛ اگه ترتیب مناسب آماده نباشه، Sort هزینه اضافه می‌کنه. هیچ operator همیشه برنده نیست.

A Hash Join typically builds a hash table from one input and probes it with the other; large inputs or bad estimates can cause an insufficient memory grant and tempdb spill. A Merge Join advances through two ordered inputs; if useful ordering is absent, Sort adds cost. No operator always wins.

اگه spill دیدی، فقط memory grant رو بزرگ نکن. estimate، آمار، projection، همزمانی و فشار حافظه رو بررسی کن. plan actual warning یک سرنخ است؛ Query Store یا اندازه‌گیری تکرارشونده روند رو روشن می‌کنه.

When a spill appears, do not simply increase the memory grant. Inspect estimates, statistics, projection, concurrency, and memory pressure. An actual-plan warning is a clue; Query Store or repeated measurement reveals the pattern.

به optimizer نگو کدوم join رو بگیرد؛ اول شواهد رو بخوان / Do not force a join before reading the evidence

حذف index، تغییر cardinality و data distribution ممکنه physical operator رو عوض کند. query یکسان رو با plan، row estimate و actual rows ذخیره کن. hintهای join رو فقط برای آزمایش یا وقتی با دلیل مستند باید بررسی کن؛ hint راه معمول درمان plan بد نیست.

Removing an index, changing cardinality, or altering distribution can change the physical operator. Capture the same query with plan, estimated rows, and actual rows. Treat join hints as experiments or justified exceptions, not routine fixes.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

شواهد runtime رو با plan ذخیره کن / Capture runtime evidence with the plan
SET STATISTICS IO, TIME ON;
-- Run the representative JOIN and capture its Actual Execution Plan.
SELECT t.TenantId, COUNT_BIG(*) AS TicketCount
FROM Lab42.Ticket AS t
JOIN Lab42.Ticket AS openTicket
  ON openTicket.TenantId=t.TenantId
WHERE openTicket.Status='Open'
GROUP BY t.TenantId;
SET STATISTICS IO, TIME OFF;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

برای تمرین، دادهٔ skewed بساز و دو پارامتر متفاوت بده. اگه join operator عوض شد، بپرس آیا row estimate، index و memory grant با واقعیت هماهنگ‌اند؛ تغییر operator به‌تنهایی موفقیت یا regression رو ثابت نمی‌کنه.

For practice, create skewed data and test two parameter values. If the operator changes, inspect estimate, indexes, and memory grant; an operator change alone proves neither improvement nor regression.

Loops برای ورودی کوچک و probe ارزان، Hash برای ورودی‌های بزرگِ نامرتب، Merge برای ورودی مرتب می‌تونه مناسب باشه. estimate اشتباه باعث انتخاب نامتناسب یا grant نامناسب می‌شه. first divergence، actual rows، execution count و spill رو پیدا کن؛ join hint رو درمان پیش‌فرض ندان.

Loops may fit a small input with cheap probes, Hash large unsorted inputs, and Merge ordered inputs. Bad estimates can lead to poor strategy or grants. Find the first divergence, actual rows, executions, and spills; do not treat join hints as the default cure.
