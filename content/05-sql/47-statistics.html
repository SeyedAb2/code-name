آمار و تخمین cardinality

Statistics and cardinality estimates

plan می‌گه انتظار داشته ۲۰ ردیف ببیند، اما ۲۰۰ هزار ردیف آمده. این فاصله می‌تونه join، memory grant و ترتیب عملیات رو عوض کند. optimizer از کجا تخمین می‌زند؟ سرنخ اصلی statistics است؛ خلاصه‌ای از توزیع داده که مفید هست اما نسخهٔ کامل جدول نیست.

A plan expected 20 rows, but 200,000 arrived. This gap can change joins, memory grants, and operation order. Where do estimates come from? Statistics provide a summary of data distribution—useful, but not a complete copy of the table.

قبل از tuning، شاهد می‌خوایمBefore tuning, collect evidence

کاربر می‌گه «گزارش کند شده» و اولین وسوسه اینه که یه index بسازیم یا query رو از نو بنویسیم. نکن. توی «آمار و تخمین cardinality» اول خط پایه می‌گیریم، بعد plan و تعداد ردیف و I/O رو می‌خونیم، یک فرضیه می‌سازیم و فقط یک چیز رو عوض می‌کنیم. اگه بهتر شد باید بتونیم بگیم چرا؛ اگه بدتر شد هم باید مدرک داشته باشیم.

A user says “the report is slow” and the first temptation is to add an index or rewrite the query. Do not. In “Statistics and cardinality estimates” we capture a baseline, read the plan and row counts, form one hypothesis, and change one thing. If it improves, we must explain why; if it regresses, we still need evidence.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

Histogram توزیع یک ستون رو خلاصه می‌کنه / A histogram summarizes one column's distribution

statistics شامل تعداد ردیف و مقدارهای متمایز، density و histogram هست. histogram روی فقط اولین ستون statistics ساخته می‌شه و حداکثر ۲۰۰ step داره. پس statistics چندستونی همهٔ correlationهای ممکن رو کامل توضیح نمی‌ده. نمونه‌برداری هم ممکنه تخمین باشه، نه شمارش دقیق.

Statistics include row and distinct-value counts, density, and a histogram. The histogram covers only the first column of the statistics object and has at most 200 steps. Multi-column statistics do not fully describe every correlation; sampled values may also be estimates rather than exact counts.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

statistics رو ببین، بعد plan رو تفسیر کن / Inspect statistics before interpreting estimates
SELECT s.name AS StatsName, p.last_updated, p.rows,
       p.rows_sampled, p.modification_counter
FROM sys.stats AS s
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) AS p
WHERE s.object_id = OBJECT_ID(N'Lab42.Ticket');
GO
DBCC SHOW_STATISTICS (N'Lab42.Ticket', N'IX_Ticket_Tenant_Status')
WITH STAT_HEADER, DENSITY_VECTOR, HISTOGRAM;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

نام statistics رو از sys.stats پیدا کن؛ نام index همیشه نام آمار auto-created نیست. DBCC SHOW_STATISTICS به object و statistic مشخص نیاز داره و مجوز لازم رو می‌خواد. histogram رو به‌عنوان خلاصه بخوان، نه ردیف‌به‌ردیف حقیقت قطعی.

Find the statistics name in sys.stats; auto-created statistics need not share an index name. DBCC SHOW_STATISTICS requires a specific object/statistic and permissions. Treat the histogram as a summary, not row-by-row truth.

تخمین، تصمیم operatorهای بعدی رو شکل می‌ده / Estimates influence downstream operator choices

optimizer تعداد ردیف‌های مورد انتظار رو برای ساخت plan به‌کار می‌برد. تخمین کم می‌تونه Nested Loops برای ورودی واقعی بزرگ بسازد یا memory grant رو کم کند؛ تخمین زیاد هم grant و work اضافه می‌ده. اولین نقطهٔ اختلاف estimated/actual رو پیدا کن؛ divergence بعدی ممکنه فقط پیامد همان خطای اول باشه.

The optimizer uses expected row counts when building a plan. Underestimation can select Nested Loops for a large actual input or grant too little memory; overestimation can waste grants and work. Find the first estimated/actual divergence—later errors may be consequences.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

predicate و دادهٔ واقعی رو کنار statistics ببین / Compare predicate distribution with evidence
SELECT Status, COUNT_BIG(*) AS RowsPerStatus
FROM Lab42.Ticket GROUP BY Status ORDER BY RowsPerStatus DESC;
GO
-- Compare this distribution with the Actual Plan's estimated/actual rows.
SELECT COUNT_BIG(*) AS OpenTickets
FROM Lab42.Ticket WHERE Status = 'Open';
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

توزیع skewed ممکنه یک مقدار پرتکرار و چند مقدار نادر داشته باشه. میانگین density برای همهٔ مقدارها گاهی کافی نیست. histogram، predicate، پارامتر و plan رو با هم ببین؛ query count جدا هم ممکنه scan کند، پس روی production بی‌محابا اجرا نکن.

A skewed distribution may contain one common value and many rare ones. Average density may not represent each value well. Read histogram, predicate, parameter, and plan together; a separate count may scan, so use care in production.

UPDATE STATISTICS درمان همیشگی نیست / Updating statistics is not a universal cure

auto-update در بسیاری از بار کاریها نقطهٔ شروع درسته. UPDATE STATISTICS می‌تونه با دادهٔ تازه plan رو عوض کند و recompile بسازد؛ FULLSCAN روی جدول بزرگ هزینه داره. sampling رو فقط وقتی افزایش بده که شواهد نشان دهند توزیع مهم با sample فعلی خوب دیده نشده. آمار رو زیادی تازه‌سازی نکن.

Automatic updates are a sensible starting point for many workloads. UPDATE STATISTICS can change plans and trigger recompilation; FULLSCAN can be costly on large tables. Increase sampling only when evidence shows the relevant distribution is poorly represented. Do not refresh statistics excessively.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

در lab ابتدا metadata، بعد update هدفمند / In a lab, inspect metadata before a targeted update
UPDATE STATISTICS Lab42.Ticket IX_Ticket_Tenant_Status;
GO
-- A full scan is an explicit, potentially expensive choice:
UPDATE STATISTICS Lab42.Ticket IX_Ticket_Tenant_Status WITH FULLSCAN;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

قبل/بعد row estimate، actual rows، plan، compile time و runtime رو مقایسه کن. اگه plan بهتر نشد، علت می‌تونه correlation، parameter sensitivity، predicate غیرقابل‌استفاده یا طراحی نامناسب query باشه؛ statistics تازه تضمین plan خوب نیست.

Compare estimates, actual rows, plan, compile time, and runtime before and after. If the plan does not improve, correlation, parameter sensitivity, non-sargable predicates, or query design may be involved. Fresh statistics do not guarantee a good plan.
