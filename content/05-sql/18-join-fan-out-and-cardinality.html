تکثیر ردیف در JOIN و cardinality

JOIN fan-out and cardinality

بعد از join، مبلغ فروش دو برابر شده. کسی پیشنهاد می‌ده DISTINCT اضافه کنیم؛ دیگری می‌گه جمع اشتباه نیست، تعداد قلم‌ها بیشتر هست. قبل از هر patch باید grain گزارش و تعداد matchهای هر رابطه رو بفهمیم. این فصل یاد می‌ده ردیف اضافه رو از duplicate واقعی جدا کنیم.

After a join, reported sales doubled. One suggestion is to add DISTINCT; another says the sum is correct because there are more line items. Before patching, define the report’s grain and count matches per relationship. This chapter separates expected fan-out from genuine duplication.

اول تعداد ردیف‌ها رو حدس بزنPredict the row count first

گزارش سفارش‌ها معمولاً از جایی سخت می‌شه که یک جدول دیگه وارد ماجرا می‌شه. سه سفارش داری، چهار مشتری داری، پنج ردیف سفارش هم داری؛ حالا JOIN می‌زنی و ناگهان خروجی دوازده ردیف می‌شه. توی «تکثیر ردیف در JOIN و cardinality» قبل از هر query اول حدس می‌زنیم چند ردیف باید برگرده، بعد اجرا می‌کنیم و از روی اختلاف حدسمون با واقعیت می‌فهمیم رابطه‌ها رو درست خوندیم یا نه.

Reports get interesting the moment another table enters the picture. You may have three orders, four customers, and five order lines, then a join suddenly returns twelve rows. In “JOIN fan-out and cardinality” we predict row counts before executing, then use any mismatch to diagnose our understanding of the relationships.

یک ردیف خروجی نمایندهٔ چیه؟ / What does one result row represent?

پیش از نوشتن JOIN جمله رو کامل کن: «هر ردیف گزارش نمایندهٔ یک ___ هست.» در Shop، گزارش سفارش‌ها ممکنه یک ردیف برای هر سفارش داشته باشه؛ گزارش اقلام، یک ردیف برای هر OrderItem. وقتی سفارش رو به اقلام وصل می‌کنی، هر سفارش به تعداد اقلامش تکرار می‌شه؛ این fan-out مورد انتظار هست.

Before writing a join, complete this sentence: “Each report row represents one ___.” In Shop, an order report may have one row per order; a line report has one row per OrderItem. Joining orders to items repeats an order once per item—expected fan-out.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

تعداد سفارش در برابر تعداد ردیف سفارش / Orders versus order-item rows
SELECT COUNT_BIG(*) AS Orders FROM shop.Orders;
SELECT COUNT_BIG(*) AS OrderItems FROM shop.OrderItems;
GO

SELECT o.OrderId, oi.ProductId, oi.Quantity
FROM shop.Orders AS o
JOIN shop.OrderItems AS oi ON oi.OrderId=o.OrderId
ORDER BY o.OrderId, oi.ProductId;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

query سوم یک ردیف در هر قلم است، نه هر سفارش. پس اگه مبلغ سفارش رو روی هر ردیف قلم جمع کنی، مبلغ سفارش به تعداد اقلام تکرار شده و مجموع باد می‌کنه. با COUNT قبل و بعد و مشاهدهٔ کلیدهای ردیف، سطح گزارش رو ثابت کن.

The third query has one row per item, not per order. Summing an order-level amount on every item repeats that amount and inflates totals. Confirm the result grain using counts and row keys before aggregating.

یک‌به‌یک، یک‌به‌چند، چندبه‌چند / One-to-one, one-to-many, many-to-many

اگه هر کلید سمت راست حداکثر یک match داره، join می‌تونه برای هر ردیف چپ حداکثر یک نتیجه بدهد. اگه چند match داره، همان ردیف چپ چند بار تکرار می‌شه. در چندبه‌چند، تعداد جفت‌ها به حاصل‌ضرب matchهای هر کلید وابسته هست. کلید یکتا و constraintها شواهد cardinality هستن؛ ظاهر نام ستون کافی نیست.

If each right-side key has at most one match, a left row yields at most one result. With several matches, that left row repeats. In many-to-many relationships, pair counts depend on the product of matches per key. Unique keys and constraints provide evidence about cardinality; column names alone do not.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

پیش‌شماری تعداد matchهای هر سفارش / Count item matches per order
SELECT OrderId, COUNT_BIG(*) AS ItemCount
FROM shop.OrderItems
GROUP BY OrderId
ORDER BY OrderId;
GO

SELECT o.OrderId, COUNT_BIG(oi.ProductId) AS MatchedItems
FROM shop.Orders AS o
LEFT JOIN shop.OrderItems AS oi ON oi.OrderId=o.OrderId
GROUP BY o.OrderId
ORDER BY o.OrderId;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

در LEFT JOIN باید ستون سمت راست NOT NULL رو بشماری تا سفارش بی‌قلم صفر بگیرد. COUNT(*) ردیف حفظ‌شدهٔ سمت چپ رو هم می‌شمارد و در آن حالت یک می‌ده. تفاوت countها بخشی از معنای گزارش هست.

With LEFT JOIN, count a NOT NULL right-side key so an order with no items gets zero. COUNT(*) also counts the preserved left row and would return one. The count expression is part of the report’s meaning.

چرا JOIN می‌تونه جمع رو باد کند؟ / Why can a join inflate totals?

فرض کن جدول Orders مبلغ کل هر سفارش رو داره و OrderItems چند قلم برایش نگه می‌داره. بعد از join، `OrderTotal` برای هر قلم تکرار می‌شه. `SUM(o.OrderTotal)` مبلغ رو چندبار جمع می‌کنه. راه‌حل، DISTINCT روی مجموع نیست؛ باید aggregation رو روی grain مناسب انجام بدهی یا مبلغ قلم‌ها رو از UnitPriceAtSale × Quantity بسازی.

Suppose Orders stores a total per order while OrderItems has several rows per order. After joining, OrderTotal repeats per item. `SUM(o.OrderTotal)` sums it multiple times. The fix is not DISTINCT over the aggregate; aggregate at the proper grain or derive line amounts from UnitPriceAtSale × Quantity.

مبلغ واقعی اقلام رو در grain قلم حساب کن / Calculate line value at item grain
SELECT o.OrderId,
       SUM(oi.Quantity * oi.UnitPriceAtSale) AS CalculatedTotal
FROM shop.Orders AS o
JOIN shop.OrderItems AS oi ON oi.OrderId=o.OrderId
GROUP BY o.OrderId
ORDER BY o.OrderId;
GO

اگه باید ویژگی order-level رو هم کنار مجموع داشته باشی، اون رو با group key درست بیاور یا اول totals رو در یک CTE/subquery برای هر OrderId بساز و بعد وصل کن. فصل GROUP BY و subqueryها جزئیات رو ادامه می‌دهند.

If order-level attributes must accompany totals, group by the correct key or calculate one total per OrderId in a CTE/subquery before joining. The GROUP BY and subquery chapters develop those patterns further.

fan-out سطح خروجی رو عوض می‌کنه / Fan-out changes the result grain

سه قدم قبل از اصلاح جمع / Three steps before fixing an aggregate

اول grain هر ورودی و خروجی رو بنویس. دوم، تعداد matchها رو برای کلیدهای اتصال بشمار. سوم، aggregate رو روی grain درست بساز و بعد اون رو join کن. این ترتیب جلوی patchهای ظاهری مثل DISTINCT رو می‌گیره و توضیح می‌ده چرا عدد عوض شده.

First state the grain of each input and output. Second, count matches per join key. Third, aggregate at the proper grain and then join it. This avoids cosmetic patches like DISTINCT and explains why the number changed.
