Row versioning، Snapshot و RCSI

Row versioning, Snapshot, and RCSI

تیم می‌خواد خواندن گزارش‌ها writerها رو معطل نکند. یک نفر می‌گه «rowversion داریم، پس نمونهٔ لحظه‌ای آماده هست». این دو یکی نیستند: rowversion در یک ستون token تغییر است؛ row versioning موتور، نسخهٔ قدیمی داده رو برای isolation نگه می‌داره.

The team wants reports not to block writers. Someone says, “We have rowversion, so Snapshot is ready.” They are different: a rowversion column is a change token; engine row versioning stores older data versions for isolation.

یه query وقتی تنهاست ممکنه کاملاً بی‌نقص به نظر بیاد. مشکل از جایی شروع می‌شه که دو session هم‌زمان سراغ همون داده می‌رن. برای «Row versioning، Snapshot و RCSI» دو پنجره باز می‌کنیم، ترتیب دستورها رو دقیق نگه می‌داریم و می‌بینیم هر session چه چیزی می‌بینه، کجا منتظر می‌مونه و چه موقع کار به blocking یا deadlock می‌کشه.

A query can look perfect when it runs alone. The interesting behaviour starts when two sessions touch the same data. In “Row versioning, Snapshot, and RCSI” we use two windows, control statement order carefully, and observe what each session sees, where it waits, and when blocking or deadlock appears.

ستون rowversion با row version store فرق داره / The rowversion column is not the row-version store

نوع دادهٔ rowversion یک token ۸‌بایتی برای تشخیص تغییر ردیف است؛ زمان نیست و نسخهٔ قبلی row رو برای خواندن نگه نمی‌داره. Row versioning در موتور، نسخهٔ داده رو نگه می‌داره تا reader طبق isolation مناسب نسخهٔ سازگار رو بخواند. شباهت اسم رو به شباهت وظیفه تبدیل نکن.

A rowversion column is an 8-byte token for detecting row changes; it is not a clock and does not preserve old row contents for readers. Engine row versioning stores data versions so readers can access a consistent version under the chosen isolation. Similar names do not imply similar roles.

RCSI تعریف READ COMMITTED رو حفظ می‌کنه اما روش خواندن رو عوض می‌کنه / RCSI keeps READ COMMITTED semantics but changes the read mechanism

با READ_COMMITTED_SNAPSHOT ON، هر statement در READ COMMITTED نمونهٔ لحظه‌ای سازگار خودش رو می‌خونه و shared lockهای معمول برای read داده جای خود رو به versioning می‌دهند. statement بعدی ممکنه نسخهٔ جدیدتری ببیند؛ پس transaction-level نمونهٔ لحظه‌ای نیست. writerها هنوز با writerها رقابت و lock دارن.

With READ_COMMITTED_SNAPSHOT ON, each READ COMMITTED statement reads its own consistent snapshot using row versions rather than ordinary shared data locks. A later statement may see newer data; this is not a transaction-level snapshot. Writers still contend and lock against writers.

Enabling RCSI is a database-level change and may require connection planning in production. This lesson only inspects settings; practice enablement separately in a disposable database. The version store requires storage and cleanup capacity.

SNAPSHOT کل transaction رو از یک نقطهٔ زمانی می‌بینه / SNAPSHOT reads from a transaction-level view

با ALLOW_SNAPSHOT_ISOLATION ON و انتخاب isolation level SNAPSHOT، readهای transaction یک view سازگار از شروع transaction می‌گیرند. اگه دو transaction یک ردیف رو تغییر دهند، یکی می‌تونه در commit با update conflict شکست بخورد؛ versioning به معنی حل خودکار conflict نیست. برنامه باید دوباره بخواند یا پاسخ کسب‌وکاری بدهد.

With ALLOW_SNAPSHOT_ISOLATION ON and SNAPSHOT selected, reads in a transaction see a consistent view from transaction start. If two transactions modify the same row, one may fail with an update conflict at commit. Versioning does not resolve conflicts automatically; the application must reread or apply business logic.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

نسخه‌ها هم فضا و عمر دارن / Versions consume space and have a lifetime

transactionهای طولانی می‌توانند نگه‌داری versionهای قدیمی رو طولانی کنند. version store معمولاً در tempdb است؛ در SQL Server با Accelerated Database Recovery، persistent version store در user database می‌تونه مطرح باشه. محل و DMVها به feature و نسخه وابسته‌اند؛ monitor رو برای platform دقیق خود بساز.

Long-running transactions can extend retention of older row versions. The version store is commonly in tempdb; with Accelerated Database Recovery, a persistent version store in the user database may apply. Location and DMVs depend on feature and version; build monitoring for the actual platform.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

وجود transaction طولانی رو جست‌وجو کن / Look for long-running transactions
SELECT s.session_id, s.login_name, s.host_name,
       at.transaction_begin_time, at.transaction_type,
       DATEDIFF(minute, at.transaction_begin_time, SYSDATETIME()) AS AgeMinutes
FROM sys.dm_tran_active_transactions AS at
JOIN sys.dm_tran_session_transactions AS st ON st.transaction_id=at.transaction_id
JOIN sys.dm_exec_sessions AS s ON s.session_id=st.session_id
ORDER BY at.transaction_begin_time;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

سن transaction فقط سرنخ است؛ queryهای version store، growth و cleanup رو هم بررسی کن. tempdb رو با truncate یا پاک‌سازی دستی «آزاد» نکن؛ علت نسخه‌های قدیمی و transaction نگه‌دارنه رو پیدا کن.

Transaction age is a clue, not the whole diagnosis; inspect version-store usage, growth, and cleanup. Do not manually clear tempdb—find old versions and the transactions retaining them.

RCSI و SNAPSHOT رو با semantics انتخاب کن / Choose RCSI or SNAPSHOT for the required semantics

RCSI معمولاً statement-level read consistency می‌ده و تغییرهای connection-level کمتری نسبت به تغییر isolation session داره؛ SNAPSHOT consistency رو across statements در transaction می‌ده اما conflictهای write رو آشکار می‌کنه. هر دو به version-store هزینه دارن و هیچ‌کدوم writer-writer conflict رو حذف نمی‌کنن.

RCSI generally gives statement-level consistency and changes read behavior under READ COMMITTED; SNAPSHOT maintains consistency across statements in a transaction but exposes write conflicts. Both consume version-store resources and neither removes writer-writer contention.

یک query موفق کافی نیست: سناریوی reader/writer، writer/writer، transaction طولانی و ظرفیت version store رو تست کن؛ سپس database option، بازیابی/backup و observability رو review کن.

One successful query is not enough. Test reader/writer, writer/writer, long transactions, and version-store capacity; then review database options, operations, and monitoring.

نسخهٔ ردیفِ قدیمی رو با token ستونی اشتباه نگیر / Do not confuse stored row versions with a row token

rowversion column برای concurrency token است؛ RCSI statement نمونهٔ لحظه‌ای می‌ده؛ SNAPSHOT transaction نمونهٔ لحظه‌ای می‌ده. versionها فضا و cleanup می‌خواهند و writerها هنوز رقابت دارن. گزینه رو با تست دو نشست، update conflict و ظرفیت version store انتخاب کن.

A rowversion column is a concurrency token; RCSI gives statement snapshots; SNAPSHOT gives transaction snapshots. Versions consume space and need cleanup, while writers still contend. Choose through two-session tests, conflict tests, and capacity evidence.
