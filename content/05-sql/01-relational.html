مدل رابطه‌ای؛ قبل از کوئری، شکل داده را بفهم

The relational model: understand the data before the query

سفارش مشتری را در یک سلول اکسل می‌نویسیم؛ گزارش فروش اول درست به نظر می‌رسد، اما وقتی محصول یا آدرس عوض می‌شود عددها با هم نمی‌خوانند. قبل از اولین SELECT ببینیم جدول خوب چه مسئله‌ای را حل می‌کند.

A customer's order fits neatly into one spreadsheet cell. The sales report looks right at first, but once a product or address changes, the numbers disagree. Before our first SELECT, let's see what a good table structure solves.

یک ردیف، چند حقیقت متناقضOne row, several conflicting facts

فرض کن برای فروشگاه تیمی یک جدول داریم که در هر ردیف هم اطلاعات مشتری است، هم سفارش، هم محصول. اولش سریع است: همه‌چیز دم دست است. بعد مشتری یک سفارش دیگر می‌دهد و اسم محصول اصلاح می‌شود. حالا کدام ردیف را باید تغییر بدهیم؟

Imagine one shop table that stores the customer, order, and product together on each row. It feels quick at first: everything is at hand. Then the customer places another order and a product name is corrected. Which rows must we update?

سه ردیف می‌گویند این مشتری و این ایمیل سه بار ثبت شده‌اند، درحالی‌که فقط سه خط سفارش داریم. اگر آدرس ایمیل اشتباه باشد، باید چند ردیف را پیدا کنیم و به‌روزرسانی کنیم؛ جا انداختن یکی یعنی یک مشتری با دو ایمیل. اگر هنوز هیچ سفارشی برای مشتری جدید نداریم، اصلاً کجا اطلاعاتش را نگه داریم؟

Three rows make it look as if the customer and email were recorded three times, even though we have only three order lines. If the email is wrong, we must find and update several rows; miss one and the same customer now has two emails. And where do we store a new customer who has not placed an order yet?

این‌ها سه ایراد جدا نیستند؛ از یک تصمیم آمده‌اند: چند نوع واقعیت را در یک جا چپانده‌ایم. مدل رابطه‌ای کمک می‌کند هر واقعیت را یک‌بار و در جای خودش ثبت کنیم، بعد با رابطه‌ها دوباره کنار هم ببینیم.

These are not three unrelated bugs. They come from one decision: we packed several kinds of facts into one place. The relational model helps us store each fact once in the right place, then bring related facts together when needed.

جدول یعنی چه، و چه چیزی نیست؟What a table is—and what it is not

در یک جدول، هر ستون می‌گوید چه جور ویژگی‌ای ثبت می‌کنیم؛ هر ردیف یک نمونه از آن چیز را نشان می‌دهد. جدول مشتری‌ها پس دربارهٔ مشتری‌هاست، نه دربارهٔ سفارش‌ها. این به نظر بدیهی می‌آید تا وقتی وسوسه شوی ستون‌هایی مثل Order1 و Order2 به جدول مشتری اضافه کنی.

A table's columns describe which attributes we record; each row is one instance of that kind of thing. A Customers table is about customers, not orders. That sounds obvious until you are tempted to add columns named Order1 and Order2 to Customers.

در تصویر ذهنی جدول را مثل صفحهٔ گسترده می‌بینیم، ولی نباید یک ویژگی صفحه‌گسترده را به SQL نسبت بدهیم: ردیف‌ها ترتیب ذاتی ندارند. ترتیب نمایش فقط وقتی قرارداد دارد که query صریحاً ORDER BY بگوید؛ حتی اگر امروز نتیجه همیشه «اتفاقی» به یک شکل ظاهر شود. آن را در فصل مرتب‌سازی آزمایش می‌کنیم.

A table looks like a spreadsheet, but we must not import one spreadsheet assumption into SQL: rows have no inherent order. Display order is a contract only when a query explicitly uses ORDER BY, even if today's result happens to appear in the same order. We will test that in the sorting chapter.

یک مقدار، یک معنی

One value, one meaning

اگر ستون Quantity گاهی «۲» و گاهی «دو عدد، رنگ آبی» باشد، برنامه دیگر نمی‌تواند با اطمینان جمع بزند یا شرط بگذارد. هر ستون باید یک مفهوم روشن با نوع مقدارهای قابل‌قبول داشته باشد. بعداً در فصل نوع داده، فرق int، decimal، تاریخ و متن را در SQL Server دقیق‌تر می‌سنجیم.

If Quantity sometimes means 2 and sometimes “two items, blue,” a program can no longer sum or filter it reliably. Every column needs one clear meaning and a defined set of valid values. In the data-types chapter, we will examine SQL Server's int, decimal, date, and text types in detail.

چطور یک ردیف را دقیق پیدا کنیم؟How do we identify exactly one row?

برای اصلاح ایمیل نیلوفر، عبارت «ردیفی که اسمش نیلوفر است» کافی نیست؛ شاید چند نفر اسم یکسان داشته باشند. یک شناسهٔ پایدار لازم داریم که هر مشتری را از بقیه جدا کند.

“The row whose name is Niloofar” is not enough to correct her email; several people may share a name. We need a stable identifier that distinguishes each customer.

کلید اصلی (PRIMARY KEY) قراردادی برای یکتایی و نبود مقدار خالی در شناسهٔ هر ردیف است. مثلاً CustomerId می‌تواند کلید اصلی باشد. ایمیل هم شاید امروز یکتا به نظر برسد، ولی تغییرپذیر است و ممکن است بعداً سیاست کسب‌وکار اجازهٔ اشتراک یا خالی‌بودنش را بدهد؛ پس «به نظر یکتا می‌رسد» به‌تنهایی دلیل خوبی برای کلید اصلی نیست.

A primary key (PRIMARY KEY) is a contract that each row's identifier is unique and non-null. CustomerId can be that key. Email may look unique today, but it can change, and a later business rule may allow a shared or missing email. “It looks unique” alone is not a sound primary-key decision.

جدولیک واقعیتکلید پیشنهادی
Customersهر شخصی که از فروشگاه خرید می‌کندCustomerId
Ordersهر سفارش ثبت‌شدهOrderId
OrderItemsهر محصول داخل یک سفارش(OrderId, ProductId) یا شناسهٔ مستقل

کلید مرکب مثل (OrderId, ProductId) از بیش از یک ستون ساخته می‌شود. اگر یک محصول بتواند دوبار در یک سفارش بیاید—مثلاً با قیمت یا شمارهٔ ردیف متفاوت—این جفت دیگر یکتا نیست و باید مدل را عوض کنیم، مثلاً OrderItemId یا LineNumber هم وارد کلید شود. خود مدل باید قانون واقعی فروشگاه را نشان دهد، نه اینکه قانون را حدس بزند.

A composite key such as (OrderId, ProductId) uses more than one column. If the same product can appear twice in one order—for example at different prices or line numbers—that pair is no longer unique. We would need a different model, perhaps an OrderItemId or a LineNumber. The model must represent the shop's real rule, not guess it.

رابطه‌ها: شناسه به‌جای کپی‌کردن اطلاعاتRelationships: identifiers instead of copied facts

هر سفارش برای دانستن صاحبش به مشتری اشاره می‌کند؛ هر ردیف سفارش هم به یک سفارش و یک محصول اشاره می‌کند. این اشاره معمولاً با شناسه ذخیره می‌شود، نه با تکرار اسم مشتری و محصول. به این پیوند، کلید خارجی (FOREIGN KEY) می‌گوییم.

An order points to its customer; an order line points to an order and a product. We usually store these links as identifiers rather than copying customer and product names. This link is called a foreign key (FOREIGN KEY).

در این تصویر، مشتری و سفارش رابطهٔ یک‌به‌چند دارند. سفارش و محصول در عمل چندبه‌چندند: یک سفارش چند محصول دارد و یک محصول ممکن است در سفارش‌های زیادی باشد. جدول میانی OrderItems این رابطه را به دو رابطهٔ یک‌به‌چند تبدیل می‌کند و جا برای واقعیت‌هایی مثل تعداد و قیمت زمان خرید می‌دهد.

Here, customers and orders are one-to-many. Orders and products are many-to-many: an order can contain several products, and a product can appear in many orders. The bridge table OrderItems turns this into two one-to-many relationships and gives us a place for facts such as quantity and the price at purchase time.

قانون را به پایگاه‌داده بسپار، نه حافظهٔ تیمPut the rule in the database, not in the team's memory

اگر قرار است هر سفارش به مشتری واقعی وصل باشد، فقط ستون CustomerId ساختن کافی نیست. بدون محدودیت، ممکن است سفارشی با شناسهٔ مشتری ۹۹۹ ثبت شود، درحالی‌که چنین مشتری‌ای وجود ندارد. یک FOREIGN KEY می‌تواند این ناسازگاری را رد کند؛ کلید اصلی هم جلوی دو ردیف با یک شناسه را می‌گیرد.

If every order must belong to a real customer, merely adding a CustomerId column is not enough. Without a constraint, an order could refer to customer 999 even though no such customer exists. A FOREIGN KEY can reject that inconsistency; a primary key prevents two rows from claiming the same identifier.

به این قواعد declarative constraint می‌گوییم: به SQL Server می‌گویی چه چیزی باید درست بماند، نه اینکه برنامه دقیقاً با چه دستورهایی آن را کنترل کند. جزئیات PRIMARY KEY، FOREIGN KEY، UNIQUE و CHECK را در فصل خودش می‌سازیم. فعلاً یک سؤال را نگه دار: «اگر دو برنامه هم‌زمان داده بنویسند، قانون کجا اجرا می‌شود؟» اگر جواب فقط «توی کد اپ» باشد، هنوز همهٔ راه‌های ورود داده را پوشش نداده‌ای.

These are declarative constraints: we tell SQL Server what must remain true, not which exact steps an application must take to enforce it. We will build PRIMARY KEY, FOREIGN KEY, UNIQUE, and CHECK constraints in their own chapter. For now, keep one question in mind: “If two applications write at once, where is the rule enforced?” If the answer is only “in the app code,” we have not covered every path that can write data.

اول مدل را ببینیم، بعد چند خط SQLSee the model first, then run a little SQL

هنوز دیتابیس Shop دوره را نساخته‌ایم؛ آن کار فصل ۳ است. این fixture موقت را در SQL Server اجرا می‌کنیم تا رابطهٔ دو جدول را لمس کنیم. اگر هنوز SQL Server نداری، کد را نگه دار و بعد از فصل نصب برگرد.

یک مشتری در خروجی دو بار دیده می‌شود چون دو سفارش دارد؛ اینجا تکرار، خطای داده نیست. نام مشتری در جدول سفارش ذخیره نشده، اما با شناسه توانستیم هنگام خواندن دو واقعیت را کنار هم بگذاریم. در فصل‌های JOIN حساب می‌کنیم چرا تعداد ردیف‌ها این‌طور شده و چه زمانی همین تکثیر می‌تواند گزارش را خراب کند.

In the JOIN chapters, we will count why the result has this shape and when the same multiplication can corrupt a report.

سه علامت که می‌گویند جدول دارد زیادی کار می‌کندThree signs that one table is doing too much

وقتی اطلاعات مشتری را در هر خط سفارش تکرار می‌کنیم، سه اتفاق محتمل داریم: برای ساخت مشتری مجبوریم سفارش جعلی بسازیم؛ اصلاح ایمیل باید در چند ردیف تکرار شود؛ حذف آخرین سفارش ممکن است تنها نسخهٔ اطلاعات مشتری را هم پاک کند. به‌ترتیب این‌ها مشکل درج، به‌روزرسانی و حذف‌اند.

When customer details are repeated on every order line, three things can happen: creating a customer may force us to invent a fake order; correcting an email must be repeated across rows; deleting the last order may erase our only copy of the customer's details. These are insertion, update, and deletion anomalies.

راه سادهٔ ذهنی این است: هر جدول یک نوع چیز را توصیف کند؛ اگر واقعیت دیگری را می‌خواهی ثبت کنی، اول بپرس «این واقعیت متعلق به کدام چیز است؟» اسم مشتری به مشتری تعلق دارد، قیمت خرید آن روز به ردیف سفارش، و مبلغ پرداخت‌شده به پرداخت. این تفکیک پایهٔ طراحی است، نه قانون ظاهریِ «هر چیز یک جدول»؛ در فصل طراحی و نرمال‌سازی استثناها و trade-off را می‌سنجیم.

A useful first question is: “Which thing does this fact belong to?” A customer's name belongs to the customer, the price paid that day belongs to an order line, and the amount paid belongs to a payment. This is a design starting point, not the simplistic rule “one thing, one table”; we will examine exceptions and trade-offs in the design and normalization chapters.

آزمایشگاه: یک سفارش تازه، بدون کپی‌کاریMini-lab: add an order without copying customer facts

سارا تا امروز خریدی نداشته و حالا سفارش #۵۰۴ می‌دهد. می‌خواهیم سفارش را ثبت کنیم، بعد نام مشتری را هم در خروجی ببینیم؛ اما اسم و ایمیل را داخل جدول سفارش کپی نمی‌کنیم.

INSERT INTO #Orders (OrderId, CustomerId, Total)

WHERE o.OrderId = 504;

INSERT INTO #Orders (OrderId, CustomerId, Total)
VALUES (599, 999, 10.00);

SELECT o.OrderId, c.CustomerName
FROM #Orders AS o
JOIN #Customers AS c ON c.CustomerId = o.CustomerId
WHERE o.OrderId = 599;

DELETE FROM #Orders WHERE OrderId = 599;

504Sara640.00

سفارش ۵۰۴ با یک کلید خارجیِ معتبر نام مشتری را پیدا کرد. سفارش یتیم ۵۹۹ هنوز داخل #Orders بود، اما INNER JOIN ردیفی برایش پیدا نکرد؛ این به‌تنهایی آن داده را حذف نمی‌کند. برای جلوگیری از ثبت چنین اشارهٔ نامعتبری، باید constraint تعریف کنیم، نه اینکه امیدوار باشیم همهٔ queryها آن را پیدا کنند.

Order 504 found the customer's name through a valid identifier. Orphan 599 still existed in #Orders, but the INNER JOIN found no matching row for it; the join did not delete the bad data. To prevent invalid references from being inserted, we need a constraint—not a hope that every query will notice.

Write a query that returns only the three customer IDs and names.

One row returns: Niloofar and 1200.00. The order table does not duplicate the customer's name; the query links it at read time.

تمرین ۳Exercise 3۱۴ دقیقه · 4 min

فروش کل هر مشتری را با GROUP BY محاسبه کن. آیا مشتری بدون سفارش هم در نتیجه می‌آید؟

Calculate each customer's total sales with GROUP BY. Does a customer with no order appear?

پاسخ و دلیلSolution and why
SELECT c.CustomerId, c.CustomerName, SUM(o.Total) AS Sales
FROM #Customers AS c
JOIN #Orders AS o ON o.CustomerId = c.CustomerId
GROUP BY c.CustomerId, c.CustomerName;

دو مشتری در نتیجه‌اند؛ سارا فعلاً سفارش ندارد، چون JOIN داخلی فقط تطبیق‌ها را می‌دهد. در فصل JOIN تفاوت حفظ ردیف سمت چپ را آزمایش می‌کنیم.

Two customers appear. Sara has no orders yet, and an inner join returns only matches. We will test how another join preserves left-side rows in the JOIN chapters.

تمرین ۴Exercise 4۱۴ دقیقه · 4 min

سه جدول Customers، Orders و Products را از روی نامشان شناسایی کن و یک query بنویس که فقط OrderId و CustomerId سفارش‌ها را بخواند.

Use the names Customers, Orders, and Products to identify the source of order facts; write a query returning only order and customer IDs.

پاسخ اجراییExecutable answer
SELECT OrderId, CustomerId FROM #Orders;

query از جدول Orders می‌خواند؛ Customers و Products منبع این دو مقدار نیستند. اسم جدول به‌تنهایی constraint رابطه را ثابت نمی‌کند.

The query reads from Orders; Customers and Products are not the source of these two values. A table name alone does not enforce a relationship.

تمرین ۵Exercise 5۱۴ دقیقه · 4 min

یک query بنویس که شناسهٔ مشتری‌هایی را برگرداند که سفارش دارند؛ خروجی نباید مشتری دارای دو سفارش را دو بار نشان دهد.

Return the IDs of customers who have orders, without listing a customer twice.

پاسخ اجراییExecutable answer

دو شناسه می‌بینی: ۱ و ۲. DISTINCT تکرار نتیجه را حذف می‌کند؛ تعداد سفارش‌ها را تغییر نمی‌دهد و جایگزین طراحی درست رابطه هم نیست.

You see IDs 1 and 2. DISTINCT removes duplicate output values; it does not change the number of orders or replace a sound relationship design.

تمرین ۶Exercise 6۱۴ دقیقه · 4 min

یک OrderId تکراری در جدول موقت سفارش درج کن. خطا را بخوان و بعد با query ثابت کن جدول تغییر نکرده.

Try inserting a duplicate OrderId. Read the error, then query the table to prove it did not change.

پاسخ و تفسیرSolution and interpretation

INSERT به‌خاطر نقض PRIMARY KEY رد می‌شود؛ شمار ردیف‌ها همچنان ۳ است. خطای یکتایی را پایگاه‌داده تشخیص داده، نه برنامهٔ گزارش‌دهنده.

تمرین ۷Exercise 7۱۴ دقیقه · 4 min

یک ستون Email تکراری وارد کن. بعد تعداد ایمیل‌های یکتا را با query بخوان.

Try inserting a duplicate email, then query how many distinct emails exist.

پاسخ و تفسیرSolution and interpretation

VALUES (4, N'Mina', N'nilo@example.test');

INSERT پیش از اجرای SELECT به‌خاطر UNIQUE رد می‌شود؛ جدول همچنان سه ایمیل یکتا دارد. یکتایی ایمیل این fixture یک قانون انتخابی است، نه قانون همیشگی همهٔ کسب‌وکارها.

The INSERT is rejected by UNIQUE before the SELECT runs; the table still has three distinct emails. Email uniqueness is a chosen rule in this fixture, not a universal business rule.

تمرین ۸Exercise 8۱۵ دقیقه · 5 min

با query نشان بده یک مشتری می‌تواند چند سفارش داشته باشد؛ تعداد هر مشتری را برگردان.

Use a query to show that one customer can have multiple orders; return an order count per customer who ordered.

پاسخ اجراییExecutable answer
SELECT CustomerId, COUNT(*) AS Orders
FROM #Orders
GROUP BY CustomerId;

نتیجه برای شناسهٔ ۱ عدد ۲ و برای ۲ عدد ۱ است. این داده شاهد رابطهٔ یک‌به‌چند در fixture است، اما برای مشتری‌های بدون سفارش هنوز ردیفی نمی‌سازد.

Customer 1 has 2 and customer 2 has 1. This fixture demonstrates one-to-many, but it does not create rows for customers with no orders.

تمرین ۹Exercise 9۲۵ دقیقه · 5 min

قبل از JOIN پیش‌بینی کن چند ردیف داریم: سه مشتری و سه سفارش. سپس تعداد ردیف‌های JOIN را با query بشمار.

Predict the join size before running it: three customers and three orders. Then count the joined rows.

پاسخ و دلیلSolution and why
SELECT COUNT(*) AS JoinedRows
FROM #Customers AS c
JOIN #Orders AS o ON o.CustomerId = c.CustomerId;

عدد ۳ است، نه ۹؛ شرط اتصال فقط جفت‌های دارای شناسهٔ یکسان را نگه می‌دارد. اگر شرط ON حذف شود، موضوع CROSS JOIN فصل ۱۶ خواهد بود.

The answer is 3, not 9: the join predicate keeps only pairs with matching IDs. If ON were omitted, we would be discussing a cross join in Chapter 16.

تمرین ۱۰Exercise 10۲۵ دقیقه · 5 min

یک order یتیم با CustomerId برابر ۹۹۹ بساز، تعداد ردیف‌هایش را جدا از JOIN بخوان، سپس همان ردیف را حذف کن.

Create an orphan order for customer 999, count it without a join, and then remove it.

پاسخ امنSafe answer
INSERT INTO #Orders VALUES (700, 999, 1.00);
SELECT COUNT(*) AS StillStored FROM #Orders WHERE OrderId = 700;
DELETE FROM #Orders WHERE OrderId = 700;

StillStored برابر ۱ است؛ پس JOIN قبلی داده را پاک نکرده بود. این آزمایش فقط در جدول موقت همین نشست است. فصل constraint جلوی این ارجاع را می‌گیرد.

StillStored is 1, so the earlier join did not delete the row. This experiment is confined to session-scoped temporary data. The constraints chapter will prevent this reference.

تمرین ۱۱Exercise 11۲۵ دقیقه · 5 min

یک جدول موقت درست با CustomerId به‌عنوان کلید خارجی به #Customers بساز و درج شناسهٔ ۹۹۹ را امتحان کن.

Create a temporary table with CustomerId as a foreign key to #Customers, then try inserting ID 999.

پاسخ اجراییExecutable answer
CREATE TABLE #CheckedOrders (
  OrderId int PRIMARY KEY,
  CustomerId int NOT NULL,
  FOREIGN KEY (CustomerId) REFERENCES #Customers(CustomerId)
);
INSERT INTO #CheckedOrders VALUES (1, 999);

ساخت جدول مجاز است، ولی INSERT دوم به‌خاطر نبود مشتری ۹۹۹ رد می‌شود. این همان تفاوت «ستون با اسم شناسه» با «رابطهٔ enforceشده» است.

The table can be created, but the second statement is rejected because customer 999 does not exist. That is the difference between “a column named like an ID” and an enforced relationship.

تمرین ۱۲Exercise 12۲۶ دقیقه · 6 min

فرض کن نام مشتری در هر سفارش کپی شده. با query تعداد دفعات تکرار هر ایمیل را از جدول اصلی پیدا کن؛ بعد نتیجه را تفسیر کن.

Suppose customer names were copied into every order. Query how many orders belong to each email, then interpret what the count represents.

پاسخSolution

FROM #Customers AS c

برای نیلوفر ۲، آرمان ۱ و سارا ۰ است. LEFT JOIN این بار عمداً مشتری بدون سفارش را نگه می‌دارد؛ این query کپی‌کاری تاریخی را ثابت نمی‌کند، فقط وابستگی سفارش‌ها را نشان می‌دهد.

Niloofar has 2, Arman 1, and Sara 0. LEFT JOIN deliberately preserves a customer without orders. This query does not prove historical duplication; it shows the order relationship.

تمرین ۱۳Exercise 13۲۶ دقیقه · 6 min

خروجی گزارش را طوری بنویس که هر ردیف یک سفارش باشد و نام مشتری هم همراه آن بیاید. انتظار چند ردیف داریم؟

Write a report where each row is one order with its customer name. How many rows do you expect?

پاسخ و تفسیرSolution and interpretation
SELECT o.OrderId, c.CustomerName
FROM #Orders AS o
JOIN #Customers AS c ON c.CustomerId = o.CustomerId;

سه ردیف، چون grain یا دانه‌بندی گزارش «یک سفارش» است. نام مشتری در دو ردیف تکرار می‌شود و این با یکتایی جدول Customers تناقضی ندارد.

Three rows, because the report's grain is one order. A customer name repeats across two rows without violating uniqueness in Customers.

تمرین ۱۴Exercise 14۲۶ دقیقه · 6 min

برای هر سفارش تعداد مشتری‌های matchشده را با یک query بشمار. اگر یک order چند بار ظاهر شد، اول شرط رابطه را بررسی کن.

Count matching customers per order. If an order appears multiple times, inspect the relationship predicate first.

پاسخ اجراییExecutable answer
SELECT o.OrderId, COUNT(c.CustomerId) AS CustomerMatches
FROM #Orders AS o
LEFT JOIN #Customers AS c ON c.CustomerId = o.CustomerId
GROUP BY o.OrderId;

هر سفارش یک match دارد، چون CustomerId در Customers کلید یکتاست. اگر جدول مشتری چند ردیف برای همان شناسه داشته باشد، این خروجی تکثیر را آشکار می‌کند؛ در fixture، PRIMARY KEY اجازه‌اش را نمی‌دهد.

Each order has one match because CustomerId is unique in Customers. If Customers contained multiple rows for one ID, this result would expose fan-out; the fixture's primary key prevents that.

تمرین ۱۵Exercise 15۳۷ دقیقه · 7 min

یک جدول آدرس در fixture موقت طراحی کن که هر ردیف با کلید اصلی پیدا شود و به مشتری اشاره کند. DDL اجرایی را بنویس.

Design a temporary Addresses table whose rows have a primary key and reference a customer. Write executable DDL.

CREATE TABLE #Addresses (
  AddressId int NOT NULL PRIMARY KEY,
  CustomerId int NOT NULL,
  City nvarchar(60) NOT NULL,
  Street nvarchar(120) NOT NULL,

طراحی اجازه می‌دهد هر مشتری چند آدرس داشته باشد. اگر قانون فروشگاه فقط یک آدرس اصلی بخواهد، باید آن قانون جداگانه مدل شود؛ این DDL به‌تنهایی «اصلی بودن» را تعریف نکرده.

تمرین ۱۶Exercise 16۳۷ دقیقه · 7 min

برای ایمیل nilo@example.test یک query بنویس که ایمیل‌های تکراری را پیدا کند؛ خروجی صفر ردیف باید چه چیزی را بگوید؟

Write a query that finds duplicate emails. What does a zero-row result tell you?

SELECT Email, COUNT(*) AS Copies
FROM #Customers
GROUP BY Email
HAVING COUNT(*) > 1;

در fixture خروجی خالی است؛ یعنی در همین داده، هیچ ایمیلی بیش از یک بار ثبت نشده. این query جلوی درج بعدی را نمی‌گیرد؛ قید UNIQUE چنین کاری می‌کند.

تمرین ۱۷Exercise 17۳۸ دقیقه · 8 min

مشتری‌ای را پیدا کن که هنوز سفارش ندارد، آن هم با یک query. این بار نبودن رابطه بخشی از جواب است.

Use one query to find customers with no orders. Here, the missing relationship is part of the answer.

پاسخ اجراییExecutable answer
SELECT c.CustomerId, c.CustomerName
FROM #Customers AS c
WHERE NOT EXISTS (
  SELECT 1 FROM #Orders AS o WHERE o.CustomerId = c.CustomerId
);

فقط Sara برمی‌گردد. EXISTS مفهوم «حداقل یک تطبیق هست» را می‌سنجد؛ NOT EXISTS برعکسش را. فصل زیرکوئری این الگو را کامل‌تر باز می‌کند.

Only Sara returns. EXISTS tests whether at least one match exists; NOT EXISTS tests the opposite. The subquery chapter develops this pattern further.

جمع‌بندی؛ قبل از SQL از خودت چه بپرسی؟Takeaway: what to ask before writing SQL

هر جدول دربارهٔ یک نوع واقعیت حرف می‌زند. کلید کمک می‌کند همان واقعیت را بی‌ابهام پیدا کنیم؛ کلید خارجی می‌گوید پیوند به واقعیت دیگری معتبر است. رابطه‌ها را با شناسه نگه می‌داریم و هنگام query، با هم ترکیب می‌کنیم. این مدل جلوی خیلی از تناقض‌ها را می‌گیرد، اما همهٔ قانون‌های کسب‌وکار را خودش حدس نمی‌زند؛ باید constraint درست را تعریف کنیم.

Each table describes one kind of fact. A key identifies that fact without ambiguity; a foreign key says its link to another fact is valid. We store relationships as identifiers and combine them when querying. This model prevents many contradictions, but it cannot guess every business rule—we must define the right constraints.

سؤال تکراری این دورهA recurring course question

این ردیف دقیقاً نمایندهٔ چیست، و با چه کلیدی می‌فهمم دو ردیف یکی نیستند؟ وقتی جواب روشن شد، نوشتن query هم کمتر شبیه حدس‌زدن است. فصل بعد محیط SQL Server را راه می‌اندازیم تا این مدل را واقعاً بسازیم و خطاهایش را ببینیم.

What exactly does one row represent, and which key proves that two rows are different? Once that is clear, query writing becomes less like guesswork. Next we will start SQL Server so we can build this model and observe its constraints in action.
