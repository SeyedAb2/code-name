مدل رابطه‌ای؛ قبل از کوئری، شکل داده رو بفهم

The relational model: understand the data before the query

سفارش مشتری رو در یک سلول اکسل می‌نویسیم؛ گزارش فروش اول درست به نظر می‌رسه، اما وقتی محصول یا آدرس عوض می‌شه عددها با هم نمی‌خوانند. قبل از اولین SELECT ببینیم جدول خوب چه مسئله‌ای رو حل می‌کنه.

A customer's order fits neatly into one spreadsheet cell. The sales report looks right at first, but once a product or address changes, the numbers disagree. Before our first SELECT, let's see what a good table structure solves.

قبل از دستورها، اول زمین بازی رو بشناسBefore the commands, understand the ground you are standing on

فرض کن روز اول کاریته و یکی از بچه‌های تیم پروژه رو باز کرده و می‌گه «این دیتابیس ماست». قبل از اینکه چیزی حفظ کنی، باید بفهمی دقیقاً با چه چیزی طرفی، کجا قراره آزمایش کنی و چطور مطمئن بشی نتیجه‌ای که می‌بینی واقعاً از همون محیطیه که فکر می‌کنی. موضوع «مدل رابطه‌ای؛ قبل از کوئری، شکل داده رو بفهم» رو هم از همین زاویه جلو می‌بریم: کم‌کم، با دست خودمون و با خروجی‌ای که می‌شه بهش استناد کرد.

Imagine it is your first day on the team and someone opens the project and says, “this is our database.” Before memorising commands, you need to know what you are looking at, where the experiment runs, and how to prove the result came from the environment you think it did. We approach “The relational model: understand the data before the query” the same way: hands-on, incremental, and evidence-driven.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

یک ردیف، چند حقیقت متناقضOne row, several conflicting facts

فرض کن برای فروشگاه تیمی یک جدول داریم که در هر ردیف هم اطلاعات مشتری است، هم سفارش، هم محصول. اولش سریع هست: همه‌چیز دم دست هست. بعد مشتری یک سفارش دیگر می‌ده و اسم محصول اصلاح می‌شه. حالا کدوم ردیف رو باید تغییر بدهیم؟

Imagine one shop table that stores the customer, order, and product together on each row. It feels quick at first: everything is at hand. Then the customer places another order and a product name is corrected. Which rows must we update?

سه ردیف می‌گن این مشتری و این ایمیل سه بار ثبت شده‌اند، درحالی‌که فقط سه خط سفارش داریم. اگه آدرس ایمیل اشتباه باشه، باید چند ردیف رو پیدا کنیم و به‌روزرسانی کنیم؛ جا انداختن یکی یعنی یک مشتری با دو ایمیل. اگه هنوز هیچ سفارشی برای مشتری جدید نداریم، اصلاً کجا اطلاعاتش رو نگه داریم؟

Three rows make it look as if the customer and email were recorded three times, even though we have only three order lines. If the email is wrong, we must find and update several rows; miss one and the same customer now has two emails. And where do we store a new customer who has not placed an order yet?

این‌ها سه ایراد جدا نیستند؛ از یک تصمیم آمده‌اند: چند نوع واقعیت رو در یک جا چپانده‌ایم. مدل رابطه‌ای کمک می‌کنه هر واقعیت رو یک‌بار و در جای خودش ثبت کنیم، بعد با رابطه‌ها دوباره کنار هم ببینیم.

These are not three unrelated bugs. They come from one decision: we packed several kinds of facts into one place. The relational model helps us store each fact once in the right place, then bring related facts together when needed.

جدول یعنی چه، و چه چیزی نیست؟What a table is—and what it is not

در یک جدول، هر ستون می‌گه چه جور ویژگی‌ای ثبت می‌کنیم؛ هر ردیف یک نمونه از آن چیز رو نشان می‌ده. جدول مشتری‌ها پس دربارهٔ مشتری‌هاست، نه دربارهٔ سفارش‌ها. این به نظر بدیهی میاد تا وقتی وسوسه شوی ستون‌هایی مثل Order1 و Order2 به جدول مشتری اضافه کنی.

A table's columns describe which attributes we record; each row is one instance of that kind of thing. A Customers table is about customers, not orders. That sounds obvious until you are tempted to add columns named Order1 and Order2 to Customers.

در تصویر ذهنی جدول رو مثل صفحهٔ گسترده می‌بینیم، ولی نباید یک ویژگی صفحه‌گسترده رو به SQL نسبت بدهیم: ردیف‌ها ترتیب ذاتی ندارن. ترتیب نمایش فقط وقتی قرارداد داره که query صریحاً ORDER BY بگوید؛ حتی اگه امروز نتیجه همیشه «اتفاقی» به یک شکل ظاهر بشه. اون رو در فصل مرتب‌سازی آزمایش می‌کنیم.

A table looks like a spreadsheet, but we must not import one spreadsheet assumption into SQL: rows have no inherent order. Display order is a contract only when a query explicitly uses ORDER BY, even if today's result happens to appear in the same order. We will test that in the sorting chapter.

یک مقدار، یک معنی

One value, one meaning

اگه ستون Quantity گاهی «۲» و گاهی «دو عدد، رنگ آبی» باشه، برنامه دیگر نمی‌تونه با اطمینان جمع بزند یا شرط بگذارد. هر ستون باید یک مفهوم روشن با نوع مقدارهای قابل‌قبول داشته باشه. بعداً در فصل نوع داده، فرق int، decimal، تاریخ و متن رو در SQL Server دقیق‌تر می‌سنجیم.

If Quantity sometimes means 2 and sometimes “two items, blue,” a program can no longer sum or filter it reliably. Every column needs one clear meaning and a defined set of valid values. In the data-types chapter, we will examine SQL Server's int, decimal, date, and text types in detail.

چطور یک ردیف رو دقیق پیدا کنیم؟How do we identify exactly one row?

برای اصلاح ایمیل نیلوفر، عبارت «ردیفی که اسمش نیلوفر هست» کافی نیست؛ شاید چند نفر اسم یکسان داشته باشند. یک شناسهٔ پایدار لازم داریم که هر مشتری رو از بقیه جدا کند.

“The row whose name is Niloofar” is not enough to correct her email; several people may share a name. We need a stable identifier that distinguishes each customer.

کلید اصلی (PRIMARY KEY) قراردادی برای یکتایی و نبود مقدار خالی در شناسهٔ هر ردیف هست. مثلاً CustomerId می‌تونه کلید اصلی باشه. ایمیل هم شاید امروز یکتا به نظر برسد، ولی تغییرپذیر هست و ممکنه بعداً سیاست کسب‌وکار اجازهٔ اشتراک یا خالی‌بودنش رو بدهد؛ پس «به نظر یکتا می‌رسه» به‌تنهایی دلیل خوبی برای کلید اصلی نیست.

A primary key (PRIMARY KEY) is a contract that each row's identifier is unique and non-null. CustomerId can be that key. Email may look unique today, but it can change, and a later business rule may allow a shared or missing email. “It looks unique” alone is not a sound primary-key decision.

جدولیک واقعیتکلید پیشنهادی
Customersهر شخصی که از فروشگاه خرید می‌کنهCustomerId
Ordersهر سفارش ثبت‌شدهOrderId
OrderItemsهر محصول داخل یک سفارش(OrderId, ProductId) یا شناسهٔ مستقل

کلید مرکب مثل (OrderId, ProductId) از بیش از یک ستون ساخته می‌شه. اگه یک محصول بتواند دوبار در یک سفارش بیاید—مثلاً با قیمت یا شمارهٔ ردیف متفاوت—این جفت دیگر یکتا نیست و باید مدل رو عوض کنیم، مثلاً OrderItemId یا LineNumber هم وارد کلید بشه. خود مدل باید قانون واقعی فروشگاه رو نشان دهد، نه اینکه قانون رو حدس بزند.

A composite key such as (OrderId, ProductId) uses more than one column. If the same product can appear twice in one order—for example at different prices or line numbers—that pair is no longer unique. We would need a different model, perhaps an OrderItemId or a LineNumber. The model must represent the shop's real rule, not guess it.

رابطه‌ها: شناسه به‌جای کپی‌کردن اطلاعاتRelationships: identifiers instead of copied facts

هر سفارش برای دانستن صاحبش به مشتری اشاره می‌کنه؛ هر ردیف سفارش هم به یک سفارش و یک محصول اشاره می‌کنه. این اشاره معمولاً با شناسه ذخیره می‌شه، نه با تکرار اسم مشتری و محصول. به این پیوند، کلید خارجی (FOREIGN KEY) می‌گیم.

An order points to its customer; an order line points to an order and a product. We usually store these links as identifiers rather than copying customer and product names. This link is called a foreign key (FOREIGN KEY).

در این تصویر، مشتری و سفارش رابطهٔ یک‌به‌چند دارن. سفارش و محصول در عمل چندبه‌چندند: یک سفارش چند محصول داره و یک محصول ممکنه در سفارش‌های زیادی باشه. جدول میانی OrderItems این رابطه رو به دو رابطهٔ یک‌به‌چند تبدیل می‌کنه و جا برای واقعیت‌هایی مثل تعداد و قیمت زمان خرید می‌ده.

Here, customers and orders are one-to-many. Orders and products are many-to-many: an order can contain several products, and a product can appear in many orders. The bridge table OrderItems turns this into two one-to-many relationships and gives us a place for facts such as quantity and the price at purchase time.

قانون رو به پایگاه‌داده بسپار، نه حافظهٔ تیمPut the rule in the database, not in the team's memory

اگه قرار هست هر سفارش به مشتری واقعی وصل باشه، فقط ستون CustomerId ساختن کافی نیست. بدون محدودیت، ممکنه سفارشی با شناسهٔ مشتری ۹۹۹ ثبت بشه، درحالی‌که چنین مشتری‌ای وجود نداره. یک FOREIGN KEY می‌تونه این ناسازگاری رو رد کند؛ کلید اصلی هم جلوی دو ردیف با یک شناسه رو می‌گیره.

If every order must belong to a real customer, merely adding a CustomerId column is not enough. Without a constraint, an order could refer to customer 999 even though no such customer exists. A FOREIGN KEY can reject that inconsistency; a primary key prevents two rows from claiming the same identifier.

به این قواعد declarative constraint می‌گیم: به SQL Server می‌گویی چه چیزی باید درست بمونه، نه اینکه برنامه دقیقاً با چه دستورهایی اون رو کنترل کند. جزئیات PRIMARY KEY، FOREIGN KEY، UNIQUE و CHECK رو در فصل خودش می‌سازیم. فعلاً یک سؤال رو نگه دار: «اگه دو برنامه هم‌زمان داده بنویسند، قانون کجا اجرا می‌شه؟» اگه جواب فقط «توی کد اپ» باشه، هنوز همهٔ راه‌های ورود داده رو پوشش نداده‌ای.

These are declarative constraints: we tell SQL Server what must remain true, not which exact steps an application must take to enforce it. We will build PRIMARY KEY, FOREIGN KEY, UNIQUE, and CHECK constraints in their own chapter. For now, keep one question in mind: “If two applications write at once, where is the rule enforced?” If the answer is only “in the app code,” we have not covered every path that can write data.

یه مکث کوتاه؛ واقعاً چی فهمیدیم؟Quick pause: what do we actually know now?

قبل از اینکه بریم بخش بعد، سعی کن بدون نگاه‌کردن به بالا در دو جمله بگی این فصل چه مسئله‌ای رو حل می‌کنه و از کدوم خروجی می‌فهمی راه‌حلت درست بوده. اگه فقط اسم دستورها یادت مونده، هنوز یه دور دیگه مثال قبلی رو با دادهٔ متفاوت اجرا کن.

Before moving on, explain in two sentences what problem this chapter solves and which output proves your solution is correct. If you only remember command names, rerun the previous example with different data.

اول مدل رو ببینیم، بعد چند خط SQLSee the model first, then run a little SQL

هنوز دیتابیس Shop دوره رو نساخته‌ایم؛ آن کار فصل ۳ هست. این دادهٔ تمرینی موقت رو در SQL Server اجرا می‌کنیم تا رابطهٔ دو جدول رو لمس کنیم. اگه هنوز SQL Server نداری، کد رو نگه دار و بعد از فصل نصب برگرد.

این جدول‌های موقت با علامت # به نشست فعلی وصل‌اند؛ برای تمرین اول چیزی رو در دیتابیس دائمی تغییر نمی‌دهیم. PRIMARY KEY و UNIQUE همین‌جا جلوی دو شناسه یا ایمیل تکراری رو می‌گیرند. نکتهٔ مخصوص SQL Server: جدول موقت constraint کلید خارجیِ قابل‌اتکا نداره؛ SQL Server تعریف FK برای temp table رو نادیده می‌گیره. پس این دادهٔ تمرینی برای نشان‌دادن یکتایی خوب است، نه برای اثبات enforce شدن رابطه. در فصل دادهٔ تمرینی این آزمایش رو روی جدول دائمیِ دیتابیس تمرینی انجام می‌دهیم. مستند CREATE TABLE مایکروسافت.

The # marks temporary tables scoped to this session, so the first exercises do not change permanent data. PRIMARY KEY and UNIQUE reject duplicate IDs or emails. This fixture is useful for uniqueness, not for proving referential integrity. In the fixture chapter, we will test that rule on permanent tables in the disposable course database. A customer appears twice because she has two orders; this repetition is not a data error. The customer's name is not stored in Orders, yet the identifier lets us combine both facts when reading. In the JOIN chapters, we will count why the result has this shape and when the same multiplication can corrupt a report.

سه علامت که می‌گن جدول داره زیادی کار می‌کنهThree signs that one table is doing too much

وقتی اطلاعات مشتری رو در هر خط سفارش تکرار می‌کنیم، سه اتفاق محتمل داریم: برای ساخت مشتری مجبوریم سفارش جعلی بسازیم؛ اصلاح ایمیل باید در چند ردیف تکرار بشه؛ حذف آخرین سفارش ممکنه تنها نسخهٔ اطلاعات مشتری رو هم پاک کند. به‌ترتیب این‌ها مشکل درج، به‌روزرسانی و حذف‌اند.

When customer details are repeated on every order line, three things can happen: creating a customer may force us to invent a fake order; correcting an email must be repeated across rows; deleting the last order may erase our only copy of the customer's details. These are insertion, update, and deletion anomalies.

راه سادهٔ ذهنی این هست: هر جدول یک نوع چیز رو توصیف کند؛ اگه واقعیت دیگری رو می‌خوای ثبت کنی، اول بپرس «این واقعیت متعلق به کدوم چیز است؟» اسم مشتری به مشتری تعلق داره، قیمت خرید آن روز به ردیف سفارش، و مبلغ پرداخت‌شده به پرداخت. این تفکیک پایهٔ طراحی است، نه قانون ظاهریِ «هر چیز یک جدول»؛ در فصل طراحی و نرمال‌سازی استثناها و trade-off رو می‌سنجیم.

A useful first question is: “Which thing does this fact belong to?” A customer's name belongs to the customer, the price paid that day belongs to an order line, and the amount paid belongs to a payment. This is a design starting point, not the simplistic rule “one thing, one table”; we will examine exceptions and trade-offs in the design and normalization chapters.

آزمایشگاه: یک سفارش تازه، بدون کپی‌کاریMini-lab: add an order without copying customer facts

سارا تا امروز خریدی نداشته و حالا سفارش #۵۰۴ می‌ده. می‌خوایم سفارش رو ثبت کنیم، بعد نام مشتری رو هم در خروجی ببینیم؛ اما اسم و ایمیل رو داخل جدول سفارش کپی نمی‌کنیم.

Sara has never ordered before and now places order #504. We want to record it and show her name in the result, without copying her name and email into the Orders table.

  2. مدل رو با یک query نشان بدهProve the model with a query

    Use the customer identifier to join the two tables and show that the order belongs to Sara.

  3. یک دادهٔ یتیم بساز، اما فقط در دادهٔ تمرینی موقتCreate an orphan—but only in the temporary fixture

    چون هنوز FK تعریف نکرده‌ایم، یک سفارش با CustomerId=999 وارد کن و query اتصال رو دوباره اجرا کن. ببین چرا ردیف سفارش در خروجی نام‌دار ظاهر نمی‌شه. بعد آن سفارش آزمایشی رو پاک کن.

جمع‌بندی؛ قبل از SQL از خودت چه بپرسی؟Takeaway: what to ask before writing SQL

هر جدول دربارهٔ یک نوع واقعیت حرف می‌زند. کلید کمک می‌کنه همان واقعیت رو بی‌ابهام پیدا کنیم؛ کلید خارجی می‌گه پیوند به واقعیت دیگری معتبر هست. رابطه‌ها رو با شناسه نگه می‌داریم و هنگام query، با هم ترکیب می‌کنیم. این مدل جلوی خیلی از تناقض‌ها رو می‌گیره، اما همهٔ قانون‌های کسب‌وکار رو خودش حدس نمی‌زند؛ باید constraint درست رو تعریف کنیم.

Each table describes one kind of fact. A key identifies that fact without ambiguity; a foreign key says its link to another fact is valid. We store relationships as identifiers and combine them when querying. This model prevents many contradictions, but it cannot guess every business rule—we must define the right constraints.
