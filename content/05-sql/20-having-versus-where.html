HAVING در برابر WHERE

HAVING versus WHERE

گزارش باید مشتری‌هایی رو نشان بدهد که بیش از یک سفارش دارن. کسی شرط `COUNT(*) > 1` رو در WHERE می‌ذاره و SQL خطا می‌ده. مسئله این نیست که کلمهٔ درست رو حفظ کنیم؛ باید بدانیم هر شرط در کدوم مرحله به چه چیزی دسترسی داره.

A report should show customers with more than one order. Someone puts `COUNT(*) > 1` in WHERE and SQL rejects it. The task is not to memorize a keyword; we need to know what each stage can see.

گزارش وقتی جدی می‌شه که فقط «لیست» نباشهA report becomes serious when it is more than a list

تا اینجا گرفتن چند ردیف آسون بود. درد واقعی وقتی شروع می‌شه که یکی می‌گه «فروش هر شهر رو بده، نسبت به ماه قبل مقایسه کن، فقط شهرهای بالای فلان عدد رو نگه دار و رتبه هم بده». «HAVING در برابر WHERE» رو برای همین جنس سؤال‌ها می‌خوایم. قدم‌به‌قدم می‌ریم جلو تا query هم درست باشه، هم بشه فهمید چرا درست کار می‌کنه.

Selecting rows is the easy part. Real reporting starts when someone asks for sales by city, a comparison with last month, a threshold, and a rank. “HAVING versus WHERE” belongs to that kind of problem. We build the query step by step so it is not only correct but explainable.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

اول کدوم ردیف‌ها؟ بعد کدوم گروه‌ها؟ / Which rows first, then which groups?

WHERE روی ردیف‌های ورودی کار می‌کنه؛ هنوز گروه و COUNT نهایی ساخته نشده. GROUP BY ردیف‌های باقی‌مانده رو گروه می‌کنه. HAVING روی گروه‌های ساخته‌شده شرط می‌ذاره. پس شرط «فقط سفارش‌های Paid رو در گزارش حساب کن» معمولاً WHERE است؛ شرط «گروه‌هایی رو نشان بده که تعدادشان از یک بیشتر هست» HAVING.

WHERE filters input rows before groups and their final counts exist. GROUP BY forms groups from the remaining rows. HAVING filters those groups. “Count only Paid orders” is usually WHERE; “show groups whose count exceeds one” is HAVING.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

دو مرحله، دو predicate / Two stages, two predicates
SELECT o.CustomerId, COUNT_BIG(*) AS PaidOrderCount
FROM shop.Orders AS o
WHERE o.OrderStatus = 'Paid'
GROUP BY o.CustomerId
HAVING COUNT_BIG(*) > 0
ORDER BY o.CustomerId;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

WHERE سفارش‌های غیرPaid رو پیش از count کنار می‌ذاره. HAVING فقط گروهی رو نگه می‌داره که دست‌کم یک سفارش Paid در دادهٔ فیلترشده داره. توی این مثال HAVING > 0 کمی زائد است، چون گروهی بدون ردیف ساخته نمی‌شه؛ در تمرین بعد شرط مفیدترِ count بزرگ‌تر از یک رو می‌نویسیم.

WHERE removes non-Paid orders before counting. HAVING keeps only groups with at least one Paid order in the filtered input. HAVING > 0 is redundant here because an empty group is not created; the next example uses the more useful count-greater-than-one condition.

وقتی شرط به نتیجهٔ aggregate وابسته هست / When a predicate depends on an aggregate

برای دیدن مشتری‌های دارای بیش از یک سفارش، ابتدا سفارش‌ها رو بر اساس CustomerId گروه می‌کنیم و بعد تعداد هر گروه رو در HAVING می‌سنجیم. شرط aggregate در WHERE قابل‌استفاده نیست، چون WHERE قبل از محاسبهٔ آن اجرا می‌شه.

To find customers with more than one order, group orders by CustomerId and then test each count in HAVING. An aggregate predicate does not belong in WHERE because WHERE runs before the aggregate is calculated.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

گروه‌هایی با بیش از یک سفارش / Groups with more than one order
SELECT CustomerId, COUNT_BIG(*) AS OrderCount
FROM shop.Orders
GROUP BY CustomerId
HAVING COUNT_BIG(*) > 1
ORDER BY CustomerId;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

هر ردیف نتیجه یک CustomerId با چند سفارش هست. می‌توانی در SQL Server در بعضی عبارت‌ها به alias خروجی تکیه کنی، اما نوشتن خود aggregate در HAVING قصد رو شفاف نگه می‌داره. اگه شرط فقط روی یک ردیف است، اون رو بی‌دلیل به HAVING منتقل نکن.

Each result row is a CustomerId with multiple orders. SQL Server permits aliases in some query expressions, but repeating the aggregate in HAVING keeps intent clear. If a predicate concerns an input row, do not move it to HAVING without a reason.

جابه‌جایی شرط فقط تغییر جای متن نیست؛ ممکنه جواب عوض بشه / Moving a predicate can change the answer

می‌خوایم مشتری‌هایی رو پیدا کنیم که بیش از یک سفارش دارن و حداقل یک سفارششان Paid هست. WHERE روی Paid باعث می‌شه COUNT فقط سفارش‌های Paid رو بشمارد؛ اما اگه هدف «بیش از یک سفارش در کل، و دست‌کم یک Paid» باشه، باید count کل و شرط Paid رو جدا تعریف کنیم. یک predicate جابه‌جا‌شده می‌تونه تعریف metric رو عوض کند.

Suppose we want customers with more than one order and at least one Paid order. Filtering Paid in WHERE makes COUNT count only Paid orders. If the intent is “more than one order overall and at least one Paid,” the total count and Paid existence must be expressed separately. Moving a predicate can change the metric.

دو تعریف متفاوت رو جدا بنویس / Express two different definitions explicitly
-- بیش از یک سفارش Paid:
SELECT CustomerId, COUNT_BIG(*) AS PaidOrders
FROM shop.Orders
WHERE OrderStatus='Paid'
GROUP BY CustomerId
HAVING COUNT_BIG(*) > 1;
GO

-- بیش از یک سفارش در کل، و دست‌کم یک Paid:
SELECT CustomerId, COUNT_BIG(*) AS AllOrders,
       SUM(CASE WHEN OrderStatus='Paid' THEN 1 ELSE 0 END) AS PaidOrders
FROM shop.Orders
GROUP BY CustomerId
HAVING COUNT_BIG(*) > 1
   AND SUM(CASE WHEN OrderStatus='Paid' THEN 1 ELSE 0 END) > 0;
GO

نسخهٔ اول قبل از گروه‌بندی non-Paidها رو حذف می‌کنه؛ نسخهٔ دوم همهٔ سفارش‌ها رو می‌شمارد و Paid رو داخل گروه اندازه می‌گیره. اسم خروجی AllOrders و PaidOrders تفاوت رو قابل‌دیدن می‌کنه.

The first query removes non-Paid rows before grouping. The second counts all orders and measures Paid within each group. Output names make the difference visible.

LEFT JOIN و گروه بدون match رو هم حساب کن / Include groups with no match

اگه فهرست باید همهٔ مشتری‌ها رو داشته باشه، از Customers شروع می‌کنیم و Orders رو LEFT JOIN می‌کنیم. حالا COUNT روی کلید سفارش برای مشتری بی‌سفارش صفر می‌ده. فیلتر HAVING می‌تونه بعداً صفرها رو حذف کند؛ تصمیم بگیر آیا ticket همهٔ مشتری‌ها رو می‌خواد یا فقط مشتری‌های دارای سفارش.

If the report must include every customer, start from Customers and LEFT JOIN Orders. Counting the order key gives zero for customers without orders. HAVING can remove those zero groups; decide whether the ticket wants all customers or only customers with orders.

همهٔ مشتری‌ها با تعداد سفارش، حتی صفر / Every customer with a count, including zero
SELECT c.CustomerId, c.FullName,
       COUNT(o.OrderId) AS OrderCount
FROM shop.Customers AS c
LEFT JOIN shop.Orders AS o ON o.CustomerId=c.CustomerId
GROUP BY c.CustomerId, c.FullName
ORDER BY c.CustomerId;
GO

اگه همین query رو با `HAVING COUNT(o.OrderId) > 0` تکمیل کنی، مشتری بی‌سفارش حذف می‌شه. COUNT(*) رو جای COUNT(o.OrderId) نگذار: outer join یک ردیف NULLشده می‌سازه که COUNT(*) اون رو می‌شمارد.

Adding `HAVING COUNT(o.OrderId) > 0` removes customers without orders. Do not replace COUNT(o.OrderId) with COUNT(*): the outer join creates a NULL-extended row that COUNT(*) counts.

ترتیب منطقی رو برای انتخاب شرط به کار ببر / Use logical stages to place predicates

نمودار، ترتیب منطقی مفهومی رو نشان می‌ده، نه تضمین ترتیب فیزیکی اجرای موتور. optimizer ممکنه predicate رو بازآرایی کند، اما معنای query باید همان stage رو بیان کند.

یک جمله برای انتخاب WHERE یا HAVING / One sentence to choose WHERE or HAVING

از خودت بپرس: «این شرط هر ردیف ورودی رو می‌سنجد یا نتیجهٔ گروه را؟» اگه ردیف است، WHERE؛ اگه COUNT/SUM/AVG گروه است، HAVING. در LEFT JOIN هم مراقب باش شرط روی سمت راست، ردیف حفظ‌شده رو ناخواسته حذف نکند. اسم metric رو دقیق کن، چون محل شرط می‌تونه تعریف metric رو عوض کند.

Ask: “Does this predicate test an input row or a completed group?” For a row, use WHERE; for a group’s COUNT/SUM/AVG, use HAVING. With LEFT JOIN, ensure a right-side predicate does not accidentally remove preserved rows. Name the metric precisely because predicate placement can redefine it.

  • WHERE پیش از گروه‌بندی ردیف‌ها رو فیلتر می‌کنه.
  • HAVING گروه‌های ساخته‌شده رو فیلتر می‌کنه.
  • WHERE روی Paid یعنی فقط Paidها وارد aggregate می‌شن.
  • برای count صفر روی LEFT JOIN، ستون غیرNULL سمت راست رو بشمار.
