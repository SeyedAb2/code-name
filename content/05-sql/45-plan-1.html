برنامهٔ اجرا ۱: scan، seek و مسیر خواندن

Execution plans 1: scans, seeks, and access paths

دو query نتیجهٔ درستی می‌دهند اما یکی کند هست. دوستمان می‌گه «seek خوب، scan بد». این جمله برای شروع جذاب هست و برای production خطرناک. plan نقشهٔ عملیات انتخاب‌شده است؛ باید بپرسیم چه تعداد ردیف وارد هر operator شد، چه چیزی برآورد شده بود و هزینهٔ واقعی کجا دیده می‌شه.

Two queries return correct results, but one is slow. Someone says, “Seek good, scan bad.” It is a catchy start and a dangerous production rule. A plan is the chosen operations; ask how many rows flowed through each operator, what was estimated, and where actual cost appeared.

قبل از tuning، شاهد می‌خوایمBefore tuning, collect evidence

کاربر می‌گه «گزارش کند شده» و اولین وسوسه اینه که یه index بسازیم یا query رو از نو بنویسیم. نکن. توی «برنامهٔ اجرا ۱: scan، seek و مسیر خواندن» اول خط پایه می‌گیریم، بعد plan و تعداد ردیف و I/O رو می‌خونیم، یک فرضیه می‌سازیم و فقط یک چیز رو عوض می‌کنیم. اگه بهتر شد باید بتونیم بگیم چرا؛ اگه بدتر شد هم باید مدرک داشته باشیم.

A user says “the report is slow” and the first temptation is to add an index or rewrite the query. Do not. In “Execution plans 1: scans, seeks, and access paths” we capture a baseline, read the plan and row counts, form one hypothesis, and change one thing. If it improves, we must explain why; if it regresses, we still need evidence.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

Execution plan نشان می‌ده موتور چطور query رو اجرا می‌کنه / An execution plan shows how the engine executes a query

optimizer، query، schema/indexها و statistics رو می‌بینه و planی انتخاب می‌کنه. estimated plan compile-time و بدون اجرای query است؛ actual plan همان plan اجراشده به‌علاوهٔ اطلاعات runtime مثل actual rows و warningهاست. هزینه‌های درصدی در plan تخمین optimizer هستن، نه stopwatch و نه سهم قطعی CPU.

The optimizer considers the query, schema/indexes, and statistics, then chooses a plan. An estimated plan is compile-time and does not execute the query; an actual plan adds runtime facts such as actual rows and warnings. Relative cost percentages are optimizer estimates—not a stopwatch or definitive CPU attribution.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

یک query رو با plan واقعی بررسی کن / Inspect one query with runtime evidence
SET STATISTICS IO, TIME ON;
SELECT CustomerId, Email, City
FROM Lab41.CustomerClustered
WHERE Email = 'person@example.test';
SET STATISTICS IO, TIME OFF;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

در SSMS، Include Actual Execution Plan رو پیش از اجرا روشن کن. actual plan برای queryهای خواندنی امن است، ولی queryهای سنگین رو با احتیاط اجرا کن؛ actual بودن به معنی بی‌هزینه‌بودن capture نیست. plan XML رو برای مقایسهٔ دقیق ذخیره کن.

In SSMS, enable Include Actual Execution Plan before execution. Actual plans are safe for read-only queries, but run expensive queries carefully; collecting an actual plan is not free. Save plan XML for precise comparisons.

Seek نقطهٔ شروع پیدا می‌کنه؛ scan محدوده‌ای رو بررسی می‌کنه / A seek navigates to a range; a scan examines a structure

Index Seek می‌تونه با key به بخشی از B+ tree برسد، اما ممکنه range بزرگی رو بخواند. Index Scan کل یا بخشی از leaf رو می‌خونه؛ Table Scan در heap ردیف‌ها رو بررسی می‌کنه. اگه بیشتر ردیف‌ها لازم باشند، scan کارآمدتر هست. operator رو همراه actual rows، predicateهای seek/residual و logical reads بخوان.

An Index Seek navigates by key but may read a large range. An Index Scan reads all or part of a leaf; a Table Scan examines heap rows. If most rows are needed, scanning can be more efficient. Read operators with actual rows, seek/residual predicates, and logical reads.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

selective و nonselective query رو مقایسه کن / Compare selective and broad predicates
SELECT CustomerId FROM Lab41.CustomerClustered
WHERE Email = 'person@example.test';
SELECT CustomerId FROM Lab41.CustomerClustered
WHERE City LIKE N'A%';
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

اگه optimizer scan انتخاب کرد، اول بررسی کن چند درصد ردیف‌ها لازم‌اند، statistics تازه‌اند یا نه، و query چه ستون‌هایی می‌خواد. فقط بعد از شواهد سراغ index یا rewrite برو.

If the optimizer scans, first check the fraction of rows needed, statistics freshness, and requested columns. Change indexes or rewrite only after evidence.

از سمت راست به چپ، operatorها رو با جریان ردیف بخوان / Read operators with row flow, not visual guesswork

در graphical plan معمولاً داده از پایین به بالا جریان داره، اما ترتیب نمایش الزاماً ترتیب نوشتن query نیست. فلش ضخیم‌تر اغلب تعداد بیشتری row در آن مسیر رو نشان می‌ده؛ properties جزئیات مهم رو می‌دهند. Actual Rows با Estimated Rows رو در نقاط اصلی مقایسه کن تا اولین محل خطای estimate رو پیدا کنی.

In graphical plans, rows usually flow from bottom to top, but display order is not the SQL text order. Thicker arrows often indicate more rows; properties contain the details. Compare actual and estimated rows at key operators to find the first major estimation divergence.

Plan علت نهایی نیست؛ فرضیه می‌ده. اون رو با STATISTICS IO/TIME، waitها، blocking، پارامترها و تجربهٔ کاربر کامل کن. estimated plan هرگز actual row count نداره.

A plan suggests hypotheses; it is not the whole diagnosis. Pair it with IO/TIME, waits, blocking, parameters, and user impact. An estimated plan never contains actual row counts.
