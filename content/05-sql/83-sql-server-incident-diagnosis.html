Incident: از علامت تا علت و اثبات repair

Incidents: symptom, cause, and verified repair

صبح گزارش‌ها timeout می‌شن و کسی می‌گه «SQL Server خراب شده». این تشخیص نیست. symptom رو محدود می‌کنیم، شواهد رو حفظ می‌کنیم، فرضیه رو با تست جدا می‌سنجیم و بعد همان بررسی نهایی رو تکرار می‌کنیم.

Reports time out and someone says “SQL Server is broken.” That is not a diagnosis. We scope the symptom, preserve evidence, distinguish hypotheses with tests, then repeat the same verification.

پیش‌نیاز: پایش، XE، backup، query tuningPrerequisites: monitoring, XE, backups, tuningحدود ۱۱۰ دقیقه · ۱۸ تمرین / About 110 minutes · 18 exercises

فرض کن این اتفاق ساعت سه صبح افتادهImagine this happened at 3 a.m.

فصل‌های عملیاتی وقتی ارزش دارن که روز خراب‌شدن سیستم به کارت بیان. برای «Incident: از علامت تا علت و اثبات repair» قرار نیست فقط اسم DMV یا گزینهٔ backup رو حفظ کنیم. یه وضعیت قابل‌تکرار می‌سازیم، شواهد جمع می‌کنیم، تغییر رو کنترل‌شده انجام می‌دیم و آخرش ثابت می‌کنیم سیستم واقعاً برگشته؛ نه اینکه فقط یک command بدون خطا تموم شده.

Operations chapters matter when the system is actually broken at 3 a.m. In “Incidents: symptom, cause, and verified repair” we do not memorise DMV names or backup options. We create a reproducible state, collect evidence, make a controlled change, and prove recovery rather than trusting a command that merely completed without error.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

زنجیره رو با symptom شروع کن / Start the chain with a symptom

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

مسیر تشخیص / Diagnostic sequence
symptom → scope/time → state → error/logs → query/waits
        → resource/host → hypothesis → repair → same verification

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

اول impact رو بپرس: چه endpointی، از چه زمانی، چند کاربر، کدوم database/instance و چه تغییری نزدیک رخداد؟ «کند هست» رو به تأخیر/نرخ خطا و بازهٔ زمانی تبدیل کن. facts رو قبل از restart/kill/cleanup ثبت کن.

Scope impact first: which endpoint, since when, how many users, which database/instance, and what changed recently? Turn “slow” into latency/error rate over a time window. Record facts before restart, kill, or cleanup.

از کم‌خطرترین شواهد شروع کن / Start with low-risk evidence

container/service state، connection error، SQL error log، Agent history، XE، فعال requests، blocking و resource خط پایه رو در یک خط زمانی قرار بده. DMVهای live transient هستن؛ queryهای تشخیصی خودشان هم هزینه دارن. اول queryهای محدود و read-only اجرا کن و مجوز/نسخه رو در نظر بگیر.

Build a timeline from service state, connection errors, SQL error log, Agent history, XE, active requests, blocking, and resource baselines. Live DMVs are transient, and diagnostic queries have cost. Start with bounded read-only checks and account for permissions/version.

فرضیه رو طوری بنویس که ممکن باشه رد بشه / Make hypotheses falsifiable

«احتمالاً index باید» فرضیهٔ کافی نیست. بگو کدوم query، کدوم estimate یا I/O، چه تغییر و چه نتیجه‌ای اون رو تأیید/رد می‌کنه. یک بار یک عامل رو عوض کن و قبل از destructive containment هماهنگی رخداد lead رو بگیر. kill کردن session می‌تونه rollback طولانی و شواهد از‌دست‌رفته بسازد.

“Maybe it needs an index” is not enough. State the query, estimate/I/O evidence, proposed change, and result that would support or reject it. Change one factor at a time and coordinate destructive containment with the incident lead. Killing a session may trigger long rollback and lose evidence.

یه مکث کوتاه؛ واقعاً چی فهمیدیم؟Quick pause: what do we actually know now?

قبل از اینکه بریم بخش بعد، سعی کن بدون نگاه‌کردن به بالا در دو جمله بگی این فصل چه مسئله‌ای رو حل می‌کنه و از کدوم خروجی می‌فهمی راه‌حلت درست بوده. اگه فقط اسم دستورها یادت مونده، هنوز یه دور دیگه مثال قبلی رو با دادهٔ متفاوت اجرا کن.

Before moving on, explain in two sentences what problem this chapter solves and which output proves your solution is correct. If you only remember command names, rerun the previous example with different data.

repair با همان آزمون و همان معیار / Verify with the same test and metric

پس از repair، همان endpoint/query و شرایط مشابه رو دوباره اندازه بگیر؛ صحت داده، تأخیر، error، blocking و سلامت رو بررسی کن. اگه symptom بهتر شد ولی دلیل علت روشن نیست، اون رو «mitigation» بنویس نه root-cause fix. rollback و recurrence نشونه رو از گزارش حذف نکن.

After repair, rerun the same endpoint/query under comparable conditions and verify data correctness, latency, errors, blocking, and health. If the symptom improves but causality is uncertain, label it mitigation—not root-cause repair. Include rollback and recurrence signals.

Separate facts from hypotheses for each ticket and keep repair reversible.
