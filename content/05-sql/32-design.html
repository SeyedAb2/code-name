طراحی جدول؛ از نیاز تا schema

Table design: from requirements to schema

تیم یک جدول Customers می‌خواد؛ اما هنوز معلوم نیست «مشتری» در سیستم چه معنایی داره. آیا ایمیل شناسه است؟ آیا آدرس رو در یک رشته نگه داریم؟ چه چیزی با تغییر کسب‌وکار باید ثابت بمونه؟ طراحی جدول از انتخاب نوع داده شروع نمی‌شه؛ از پرسیدن سؤال درست دربارهٔ واقعیت شروع می‌شه.

The team asks for a Customers table, but “customer” is not yet defined. Is email an identifier? Should an address be one string? What must remain stable when the business changes? Table design starts with clarifying reality, not picking a type.

تصمیمی که امروز کوچیکه، فردا توی هر query دیده می‌شهA small schema decision today appears in every query tomorrow

وقتی جدول فقط ده ردیف داره، تقریباً هر طراحی‌ای «کار می‌کنه». دردش چند ماه بعد معلوم می‌شه؛ وقتی داده تکراری شده، constraint نداری یا یه نوع داده اشتباه همهٔ queryها رو پیچیده کرده. توی «طراحی جدول؛ از نیاز تا schema» قرار نیست فقط DDL بنویسیم؛ می‌خوایم بفهمیم هر تصمیم چه قانونی رو وارد خود دیتابیس می‌کنه و هزینهٔ اون تصمیم بعداً کجاست.

With ten rows, almost any design seems to work. The cost appears months later when data is duplicated, constraints are missing, or a poor data type infects every query. In “Table design: from requirements to schema” we are not merely writing DDL; we are deciding which rules the database itself enforces and what those choices cost later.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

قبل از CREATE TABLE، سؤال‌های دامنه رو بپرس / Ask domain questions before CREATE TABLE

چه چیزهایی هویت جدا دارن؟ هر سفارش چند قلم داره؟ ایمیل اجباری هست یا ممکنه تغییر کند؟ یک نفر می‌تونه چند آدرس داشته باشه؟ این پاسخ‌ها entity و رابطه رو تعیین می‌کنن. جدول رو از روی فرم UI کپی نکن؛ فرم برای ورود است، schema برای نگهداری حقیقت.

Which things have independent identity? How many lines can an order contain? Is email required and can it change? Can one person have multiple addresses? These answers define entities and relationships. Do not copy a UI form into the schema; forms capture input, schemas preserve facts.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

یک مدل کوچک رو از نیاز بساز / Derive a small model from requirements
IF SCHEMA_ID(N'DesignLab') IS NULL EXEC(N'CREATE SCHEMA DesignLab');
DROP TABLE IF EXISTS DesignLab.CustomerAddress, DesignLab.Customer;
GO

CREATE TABLE DesignLab.Customer
(
  CustomerId int IDENTITY(1,1) NOT NULL,
  CustomerCode varchar(20) NOT NULL,
  DisplayName nvarchar(120) NOT NULL,
  Email nvarchar(254) NULL,
  CreatedAt datetime2(0) NOT NULL
    CONSTRAINT DF_Customer_CreatedAt DEFAULT SYSUTCDATETIME(),
  CONSTRAINT PK_Customer PRIMARY KEY (CustomerId),
  CONSTRAINT UQ_Customer_Code UNIQUE (CustomerCode)
);
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

schema نام جدول رو از بقیهٔ objectها جدا می‌کنه. نام‌های مفرد و یکدست انتخاب کردیم؛ این قانون جهانی نیست، اما قاعدهٔ تیم باید ثابت باشه. Email رو unique نکردیم چون هنوز نگفته‌ایم ایمیل در این دامنه یکتا و اجباری هست.

A schema namespaces the table. We chose singular, consistent names; there is no universal naming law, but a team convention should be stable. We did not make Email unique because the domain has not established that it is required and unique.

کلید طبیعی یا مصنوعی؟ / Natural or surrogate key?

کلید طبیعی از دنیای کسب‌وکار میاد؛ مثل کد ملی یا کد قرارداد. کلید مصنوعی برای هویت پایدار داخلی ساخته می‌شه؛ مثل CustomerId. کلید طبیعی ممکنه تغییر کند، طولانی باشه یا معنی‌اش عوض بشه. surrogate هم به‌تنهایی هیچ قانون کسب‌وکار رو enforce نمی‌کنه؛ معمولاً هر دو رو نگه می‌داریم: surrogate برای reference و unique طبیعی برای invariant واقعی.

A natural key comes from the business domain, such as a contract code. A surrogate key is an internal stable identifier. Natural keys may change or grow in meaning. A surrogate does not enforce business rules by itself; often we use it for references and a separate UNIQUE constraint for the real invariant.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

تغییر کد کسب‌وکار بدون عوض‌شدن شناسه / Change a business code without changing internal identity
SELECT CustomerId, CustomerCode
FROM DesignLab.Customer;

-- If a business code is corrected, update the unique business key.
UPDATE DesignLab.Customer
SET CustomerCode = 'C-2026-0042'
WHERE CustomerId = 1;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

foreign keyهای دیگر جدول‌ها به CustomerId وصل می‌شن و تغییر کد مشتری مجبورشان نمی‌کنه. اما اگه CustomerCode خودِ قرارداد بیرونی است، uniqueness باید حفظ بشه؛ surrogate مجوز duplicate کد نیست.

Other tables reference CustomerId, so correcting a customer code does not rewrite every relationship. If CustomerCode is an external contract, its uniqueness still matters; a surrogate key does not permit duplicate codes.

یک سلول، یک واقعیت قابل‌جست‌وجو / Keep independently meaningful facts addressable

اگه مشتری چند آدرس داره، رشتهٔ «تهران، خیابان...» رو در ستون Addresses با جداکننده ذخیره نکن. جست‌وجو، تغییر و اعتبارسنجی هر آدرس دشوار می‌شه. رابطهٔ یک‌به‌چند رو جدول جدا نشان می‌ده. این هنوز درس کامل نرمال‌سازی نیست؛ فقط می‌پرسیم آیا هر ستون یک ویژگی از همان موجودیت است؟

If a customer has multiple addresses, do not pack them into one delimited Addresses string. Searching, editing, and validating each address becomes hard. A separate table models the one-to-many relation. This is not the full normalization lesson; we are checking whether each column describes its entity.

آدرس رو به موجودیت خودش تبدیل کن / Model addresses as their own rows
CREATE TABLE DesignLab.CustomerAddress
(
  CustomerAddressId int IDENTITY(1,1) NOT NULL,
  CustomerId int NOT NULL,
  Label nvarchar(30) NOT NULL,
  City nvarchar(80) NOT NULL,
  AddressLine nvarchar(250) NOT NULL,
  IsPrimary bit NOT NULL
    CONSTRAINT DF_CustomerAddress_IsPrimary DEFAULT (0),
  CONSTRAINT PK_CustomerAddress PRIMARY KEY (CustomerAddressId),
  CONSTRAINT FK_CustomerAddress_Customer
    FOREIGN KEY (CustomerId) REFERENCES DesignLab.Customer(CustomerId)
);
GO

حالا هر آدرس یک ردیف مستقل هست و کلید والدش مشخص هست. هنوز باید تصمیم بگیریم آیا هر مشتری فقط یک آدرس اصلی می‌تونه داشته باشه؛ این قانون رو می‌توان با filtered unique index مدل کرد، اما قبلش دقیقاً تعریف «اصلی» رو از محصول بپرس.

Each address now has its own row and parent key. We still need to decide whether each customer may have only one primary address. A filtered unique index could model that, but first clarify the business definition.

نام‌گذاری خوب هزینهٔ فهمیدن رو کم می‌کنه / Consistent names reduce cognitive load

نام جدول و ستون باید معنای پایدار داشته باشه؛ از نام‌های مبهم مثل Value، Data و Type دوری کن مگر دامنه اون رو روشن کند. schema رو در queryها صریح بیاور تا جست‌وجوی object و permission قابل‌پیش‌بینی باشه. نام قیدها رو هم معنادار انتخاب کن تا خطای استقرار خوانا بشه.

Table and column names should carry stable meaning. Avoid vague Value, Data, or Type names unless the domain clarifies them. Qualify objects with their schema for predictable lookup and permissions, and name constraints so deployment errors are understandable.

نام‌های یکدست رو از metadata ببین / Inspect the schema you actually created
SELECT s.name AS SchemaName, t.name AS TableName,
       c.column_id, c.name AS ColumnName, ty.name AS DataType,
       c.max_length, c.is_nullable
FROM sys.tables AS t
JOIN sys.schemas AS s ON s.schema_id = t.schema_id
JOIN sys.columns AS c ON c.object_id = t.object_id
JOIN sys.types AS ty ON ty.user_type_id = c.user_type_id
WHERE s.name = N'DesignLab'
ORDER BY t.name, c.column_id;
GO

metadata چیزی رو که واقعاً ساخته‌ای نشان می‌ده، نه چیزی رو که در ذهن داشتی. بعد از migration این query برای مرور نام، نوع و nullability مفید است؛ اما جای تست constraint و رفتار insert رو نمی‌گیره.

Metadata shows what was actually created, not what you intended. It helps review names, types, and nullability after a migration, but does not replace constraint and insert tests.

هیچ گزینه‌ای همیشه برنده نیست. مثال واقعی و عمر داده رو بساز، بعد schema رو طوری انتخاب کن که invariantها enforce شوند و تغییر محتمل، migration کنترل‌شده داشته باشه.

No option always wins. Model real examples and data lifetime, then choose a schema that enforces invariants and can evolve through controlled migrations.
