ایندکس ۱: B+ tree، clustered و nonclustered

Indexes 1: B+ trees, clustered and nonclustered

گزارش یک مشتری رو پیدا می‌کنه اما جدول بزرگ هست. ایندکس اضافه می‌کنیم، query کندتر می‌شه و insert هم هزینه می‌گیره. قبل از ساختن ایندکس دوم، باید بدانیم موتور از کجا جست‌وجو می‌کنه و وقتی ایندکس همهٔ ستون‌ها رو نداره چه مسیری طی می‌شه.

A report finds one customer in a large table. We add an index, but the query remains slow and inserts cost more. Before adding another index, understand how the engine searches and what happens when an index does not contain every requested column.

Rowstore index یک B+ tree است، نه فهرست جادویی / A rowstore index is a B+ tree, not magic

در rowstore، SQL Server ساختار B+ tree داره: ریشه مسیر رو به شاخه و سپس leaf هدایت می‌کنه. clustered index در leaf، خود ردیف‌های جدول رو نگه می‌داره؛ nonclustered index کلید خودش و locator ردیف پایه رو نگه می‌داره. این ساختار جست‌وجوی مرتب رو ممکن می‌کنه، اما optimizer هنوز باید بین seek، scan و lookup با توجه به تعداد ردیف و هزینه تصمیم بگیرد.

SQL Server rowstore indexes use a B+ tree: root and intermediate levels guide traversal to the leaf. A clustered index stores the table rows at its leaf; a nonclustered index stores its key and a locator to the base row. This enables ordered search, but the optimizer still chooses among seek, scan, and lookup based on estimated cost.

Root page
   ↓ key range
Intermediate page(s)
   ↓ narrower range
Leaf: clustered rows OR nonclustered keys + row locator

اندازهٔ واقعی درخت، fan-out و عمقش به اندازهٔ key و pageها بستگی داره. seek هم الزاماً ارزان‌تر از scan نیست: اگه query درصد بزرگی از جدول رو بخواهد، scan ممکنه انتخاب بهتری باشه.

Tree depth and fan-out depend on key and page sizes. A seek is not always cheaper than a scan; when a query needs a large fraction of the table, scanning can be preferable.

Heap و clustered تفاوت محل ردیف‌ها هستن / Heap and clustered describe how base rows are organized

جدول بدون clustered index یک heap است؛ ردیف‌ها بر اساس کلید مرتب‌شدهٔ clustered نیستند. clustered index در leaf ردیف‌های جدول رو به ترتیب کلید درخت نگه می‌داره. هر جدول حداکثر یک clustered index داره، اما می‌تونه چند nonclustered index داشته باشه. کلید clustered رو معمولاً کوتاه، پایدار و کم‌تغییر انتخاب کن، چون به locator ایندکس‌های nonclustered هم اثر می‌ذاره.

A table without a clustered index is a heap; its rows are not stored in clustered-key order. A clustered index stores table rows at the tree leaf. A table can have one clustered index and multiple nonclustered indexes. Keep the clustering key generally narrow, stable, and rarely changed because it affects nonclustered row locators too.

index_id صفر معمولاً heap رو نشان می‌ده و یک clustered index رو. در nonclustered index روی heap locator از RID استفاده می‌کنه؛ روی clustered table، clustering key locator می‌شه. پس عریض یا متغیر بودن کلید clustered روی secondary indexes هم اثر داره.

index_id 0 identifies a heap and 1 a clustered index. A nonclustered index on a heap uses a RID locator; on a clustered table, the clustering key acts as the locator. A wide or changing clustering key therefore affects secondary indexes too.

Lookup نتیجهٔ نداشتن ستون در index هست / A lookup retrieves columns missing from the index

اگه index روی Email باشه ولی query، City رو هم بخواهد، موتور می‌تونه Email رو در nonclustered tree پیدا کند و برای ستون جاافتاده به ردیف پایه برگردد. این عملیات lookup نام داره. برای یک ردیف شاید خوب باشه؛ برای هزاران ردیف می‌تونه lookupهای پرتعداد بسازد. actual plan، تعداد ردیف و logical reads رو ببین.

If an index contains Email but a query also needs City, the engine may find Email in the nonclustered tree and return to the base row for the missing column. That is a lookup. It can be fine for one row but expensive for thousands. Inspect actual rows, lookups, and logical reads.

The second query may scan instead; that alone does not mean the index is broken. Design for real query patterns and selectivity, not merely to see the word “seek” in a plan.

هر index با INSERT، UPDATE و DELETE باید نگه‌داری بشه؛ فضای ذخیره و cache هم می‌گیره. اگه بار کاری نوشتنی است، index اضافی می‌تونه همان سیستم رو کند کند. تصمیم رو با read benefit در کنار write cost بسنج.

Every index must be maintained by INSERT, UPDATE, and DELETE; it also consumes storage and cache. Extra indexes can slow write-heavy workloads. Evaluate read benefit against write cost.

ساختار رو برای query واقعی انتخاب کن / Choose the structure for the real query

B+ tree جست‌وجوی مرتب رو فراهم می‌کنه؛ heap ردیف‌ها رو بدون clustered order نگه می‌داره؛ clustered leaf خود داده است؛ nonclustered index ممکنه برای ستون جاافتاده lookup کند. plan و reads رو اندازه بگیر و هزینهٔ نوشتن رو هم حساب کن.

A B+ tree supports ordered search; a heap has no clustered order; clustered leaves are the data; a nonclustered index may look up missing columns. Measure plans and reads, and include write costs.

  • یک clustered index برای جدول / At most one clustered index per table.
  • seek لزوماً برنده نیست / A seek is not always cheaper.
  • locator به نوع ساختار پایه وابسته هست / Locator depends on the base structure.
  • ساخت index به بار کاری واقعی متصل هست / Index choice is tied to real workload.
