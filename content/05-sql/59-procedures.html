Stored procedure؛ قرارداد اجرایی پایگاه‌داده

Stored procedures as database APIs

یک query دستی جواب می‌ده؛ برنامه باید همان کار رو با ورودی‌های مختلف تکرار کند. procedure رو برای قرارداد قابل‌آزمون، کنترل خطا و واگذاری حداقلی دسترسی می‌سازیم، نه فقط مرتب‌کردن کد.

A manual query works; an application must repeat it with varying inputs. We use a procedure for a testable contract, error control, and least-privilege execution—not merely code organization.

وقتی منطق رو می‌بری داخل دیتابیس، باید دلیل داشته باشیIf logic moves into the database, have a reason

یه stored procedure یا trigger می‌تونه کار رو خیلی تمیز کنه؛ همون ابزار می‌تونه شش ماه بعد تبدیل بشه به چیزی که هیچ‌کس نمی‌دونه از کجا اجرا شده. توی «Stored procedure؛ قرارداد اجرایی پایگاه‌داده» فقط syntax نمی‌زنیم. می‌سنجیم این منطق چرا باید داخل SQL Server باشه، چطور خطاش رو می‌بینیم و چطور مطمئن می‌شیم رفتار پنهان درست نکردیم.

A stored procedure or trigger can make a design cleaner, and the same feature can become mysterious hidden behaviour six months later. In “Stored procedures as database APIs” we go beyond syntax: why should this logic live in SQL Server, how do we observe failures, and how do we avoid invisible side effects?

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

قرارداد رو قبل از بدنه مشخص کن / Define the contract first

برای جست‌وجوی سفارش باید ورودی، مقدار پیش‌فرض، ترتیب پایدار و رفتار ورودی نامعتبر معلوم باشه. procedure پارامتر typed می‌گیره، اما type به‌تنهایی اعتبار معنایی رو تضمین نمی‌کنه.

An order search needs explicit inputs, defaults, deterministic ordering, and invalid-input behavior. Typed parameters do not validate business meaning by themselves.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

نمونهٔ خواندن / A read procedure
CREATE OR ALTER PROCEDURE dbo.GetOrdersByCustomer
  @CustomerId int, @Since date = NULL
AS
BEGIN
  SET NOCOUNT ON;
  IF @CustomerId <= 0 THROW 50001, 'CustomerId must be positive.', 1;
  SELECT OrderId, OrderDate, Status FROM dbo.Orders
  WHERE CustomerId=@CustomerId AND (@Since IS NULL OR OrderDate >= @Since)
  ORDER BY OrderDate DESC, OrderId DESC;
END;
GO
EXEC dbo.GetOrdersByCustomer @CustomerId=42, @Since='2026-01-01';

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

این نمونه به schema فرضی وابسته هست. شرط optional ممکنه برای همهٔ مقدارها plan خوبی ندهد؛ Actual Plan و دادهٔ واقعی رو بسنج.

This sample assumes a particular schema. An optional predicate may not produce one ideal plan for every value; inspect actual plans and representative data.

نوشتن اتمی، خطای آشکار / Atomic writes, visible errors

در عملیات چندمرحله‌ای، validation، مرز transaction و انتقال خطا رو تعریف کن. XACT_ABORT در بسیاری از خطاهای runtime transaction رو به rollback می‌برد؛ CATCH باید وضعیت رو بررسی و خطا رو دوباره پرتاب کند. transaction داخلی مستقل از transaction caller نیست.

For multi-step writes, define validation, transaction ownership, and error propagation. XACT_ABORT aborts a transaction for many runtime errors; CATCH should inspect state and rethrow. A nested transaction is not independent of its caller.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

انتقال آزمایشی با کنترل هر دو update / A transfer with both writes checked
CREATE OR ALTER PROCEDURE dbo.TransferFunds
  @From int, @To int, @Amount decimal(12,2)
AS
BEGIN
 SET NOCOUNT ON; SET XACT_ABORT ON;
 IF @Amount <= 0 OR @From=@To THROW 50002,'Invalid transfer.',1;
 BEGIN TRY
  BEGIN TRAN;
  UPDATE dbo.Account SET Balance=Balance-@Amount WHERE AccountId=@From AND Balance >= @Amount;
  IF @@ROWCOUNT <> 1 THROW 50003,'Debit rejected.',1;
  UPDATE dbo.Account SET Balance=Balance+@Amount WHERE AccountId=@To;
  IF @@ROWCOUNT <> 1 THROW 50004,'Credit target missing.',1;
  COMMIT;
 END TRY
 BEGIN CATCH
  IF XACT_STATE() <> 0 ROLLBACK;
  THROW;
 END CATCH
END;

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

فقط روی accountهای آزمایشی و قابل‌حذف آزمایش کن. در سامانهٔ واقعی idempotency، audit، precision پول و timeout caller رو هم طراحی کن؛ retry کور می‌تونه پرداخت رو تکرار کند.

Test only with disposable accounts. A real system also needs idempotency, audit, money precision, and caller-timeout design; blind retries can duplicate a payment.

خروجی و خروجی هم API هستن / Results are part of the API

procedure می‌تونه خروجی، output parameter و return code بدهد. RETURN عدد صحیح می‌ده؛ دادهٔ کسب‌وکاری رو معمولاً با خروجی یا OUTPUT روشن‌تر منتقل می‌کنیم. تعداد و نام ستون‌ها رو پایدار نگه دار.

A procedure can return result sets, output parameters, and an integer return code. Business data is usually clearer as a result set or OUTPUT value. Keep result-set count and column names stable.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

OUTPUT و status رو مستقل بخوان / Read output and status independently
CREATE OR ALTER PROCEDURE dbo.CountOpenOrders @CustomerId int, @OpenCount int OUTPUT
AS
BEGIN
 SET NOCOUNT ON;
 SELECT @OpenCount=COUNT(*) FROM dbo.Orders WHERE CustomerId=@CustomerId AND Status='Open';
 RETURN 0;
END;
GO
DECLARE @n int,@rc int;
EXEC @rc=dbo.CountOpenOrders @CustomerId=42,@OpenCount=@n OUTPUT;
SELECT @rc AS ReturnCode,@n AS OpenCount;

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

SET NOCOUNT ON پیام‌های row-count رو کم می‌کنه، اما جای قرارداد خروجی یا مدیریت خطا رو نمی‌گیره.

SET NOCOUNT ON reduces row-count messages; it does not replace output contracts or error handling.

EXECUTE بده، دسترسی گسترده نه / Grant execution, not broad access

به principal برنامه فقط EXECUTE روی procedure لازم بده و مجوز رو با همان principal آزمایش کن. مالکیت و مسئولship chaining نتیجه رو تغییر می‌دهند. ورودی رو به dynamic SQL نچسبان؛ identifier متغیر باید allowlist و QUOTENAME داشته باشه.

Grant the application principal only required procedure execution and test as that principal. Ownership and chaining affect effective permissions. Avoid concatenating input into dynamic SQL; dynamic identifiers require an allowlist and QUOTENAME.

GRANT EXECUTE ON OBJECT::dbo.GetOrdersByCustomer TO app_reader;

تغییر procedure هم migration هست / Procedure changes are migrations

CREATE OR ALTER استقرار تکرارپذیر می‌ده، نه تغییر بی‌ریسک. نسخهٔ مصرف‌کننده، plan، مجوز و rollback رو بسنج.

CREATE OR ALTER enables repeatable deployment, not risk-free changes. Review callers, plans, permissions, and rollback.
