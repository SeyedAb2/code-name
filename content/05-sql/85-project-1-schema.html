پروژهٔ ۱ — schemaای که قانون رو enforce می‌کنه

Project 1 — a schema that enforces the rules

به تیمی تازه پیوستی. فروشگاه سفارش‌ها رو در یک فایل spreadsheet نگه می‌داره؛ نام مشتری‌ها تکراری است، مبلغ کل گاهی با ردیف‌ها نمی‌خونه و حذف محصول، تاریخچهٔ سفارش رو خراب می‌کنه. مأموریتت: نیاز مبهم رو به schema قابل‌اعتماد SQL Server تبدیل کنی و با query ثابت کنی قوانین واقعاً اجرا می‌شن.

You joined a small team storing orders in a spreadsheet. Customer names are duplicated, totals disagree with line items, and deleting a product can damage order history. Turn the vague requirements into a reliable SQL Server schema and prove the rules with queries.

پروژهٔ عملی · فقط SQL ServerHands-on project · SQL Server onlyتخمین: ۹۰ دقیقه · خروجی query محور / Estimated: 90 minutes · query-driven deliverable

مأموریت و مرز کار / Mission and scope

یک مدل برای Customer، Product، Order و OrderLine طراحی کن. کد برنامه لازم نیست؛ تحویل اصلی schema، constraint، دادهٔ تمرینی و queryهایی هست که مدل رو ثابت می‌کنن. مبلغ کل رو بی‌دلیل denormalize نکن و اگه تصمیم به ذخیره‌اش گرفتی، consistency rule رو روشن کن.

Model Customer, Product, Order, and OrderLine. No application code is required; deliver schema, constraints, fixtures, and queries that prove the model. Do not denormalize totals without reason; if you store one, define its consistency rule.

اول مسئله رو مثل یه همکار واقعی بخونRead the brief like a real teammate

قبل از ساختن اولین جدول، پنج دقیقه SQL رو کنار بذار. از متن نیازمندی فقط جمله‌های کسب‌وکاری رو دربیار: چه چیزهایی هویت مستقل دارن؟ کدوم رابطه یک‌به‌چنده؟ کجا «نباید» دادهٔ تکراری داشته باشیم؟ کجا تاریخچه مهم‌تر از راحتی delete کردنه؟ این مرحله شاید کد نداشته باشه، ولی کیفیت کل پروژه به همین چند تصمیم بستگی داره.

Before creating the first table, put SQL aside for five minutes. Extract business statements: which things have independent identity, which relationships are one-to-many, where duplicates are forbidden, and where history matters more than convenient deletion. This step may contain no SQL, but it determines the quality of the whole project.

قانون پروژهProject rule

هر تصمیم طراحی باید یک شاهد داشته باشه: constraint، query تأییدی یا test منفی. «به نظرم خوبه» مدرک نیست.

Every design decision needs evidence: a constraint, a verification query, or a negative test. “It looks fine” is not evidence.

تحویل‌دادنی‌ها / Deliverables

  • فایل 01_schema.sql: schema، کلیدها، constraintها و نام‌گذاری روشن / schema, keys, constraints, clear naming
  • فایل 02_seed.sql: دادهٔ کم اما پوشش‌دهندهٔ edge case / small seed data covering edge cases
  • فایل 03_بررسی.sql: queryهای invariant، join، aggregate و تست منفی / invariant, join, aggregate, and negative tests
  • README کوتاه: فرض‌ها، cardinality، delete/update policy و تصمیم‌های طراحی / assumptions, cardinality, delete/update policy, design decisions
  • یک cleanup script فقط برای دیتابیس آزمایشی و قابل‌حذف / cleanup script restricted to the disposable database

نام schema/database رو با پیشوند Project85 نگه دار تا با Shop فصل‌های قبل تداخل نکند. script باید دوباره اجراشدنی یا با precondition روشن باشه؛ دیتابیس واقعی رو پاک نکن.

Prefix objects with Project85 to avoid earlier Shop fixtures. Scripts should be repeatable or state clear preconditions. Never clean a real database.

نقطه‌های پیشرفت / Milestones

  1. نیازها رو به entity، attribute و relationship تبدیل کن؛ ابهام‌ها رو در README بنویس. / Derive entities, attributes, and relationships; record ambiguities.
  2. PK/FK و nullability رو طراحی و schema رو در database آزمایشی و قابل‌حذف بساز. / Design keys/nullability and create the schema in a disposable database.
  3. CHECK/UNIQUE و delete behavior رو اضافه کن؛ دادهٔ seed معتبر درج کن. / Add constraints/delete behavior and insert valid seed data.
  4. queryهای کسب‌وکار و تست‌های منفی بنویس؛ هر constraint رو با violation کنترل‌شده prove کن. / Write business queries and negative tests; prove each constraint with controlled violations.
  5. از ابتدا روی دیتابیس تازه اجرا کن و خروجی رو با reviewer تحویل بده. / Re-run from a clean disposable database and hand off evidence.

معیار پذیرش / Acceptance criteria

  • درج دادهٔ تمرینی معتبر موفق هست و هر FK به parent واقعی اشاره می‌کنه. / Valid fixtures insert and every FK points to a real parent.
  • duplicate key، تعداد منفی، قیمت غیرمجاز و FK یتیم با خطای مورد انتظار رد می‌شن. / Duplicate keys, invalid quantity/price, and orphan FKs are rejected.
  • یک query JOIN سفارش/مشتری/ردیف‌ها خروجی deterministic داره. / A joined order/customer/line query has deterministic ordering.
  • مجموع line amount با تعریف total گزارش‌شده سازگار هست. / Line totals reconcile with the defined order total.
  • حذف Product یا Customer مطابق policy مستند رفتار می‌کنه و تاریخچهٔ ناخواسته حذف نمی‌شه. / Product/customer deletion follows documented policy without accidental history loss.
  • ساختار از صفر با اسکریپت‌های تحویلی قابل‌بازتولید هست. / The delivered scripts reproduce the schema from an empty lab database.

راهنماهای بازشونده / Collapsible hints

از کجا طراحی رو شروع کنم؟ / Where should I start?

به column فکر نکن؛ جمله‌های کسب‌وکار رو به entity و رابطه تبدیل کن. یک مشتری چند سفارش داره؟ هر order line به کدوم parentها وابسته است؟

Start from business statements, not columns. Can a customer have multiple orders? Which parents does each order line depend on?

آیا total رو ذخیره کنم؟ / Should I store a total?

اگه از lineها قابل محاسبه است، اول محاسبهٔ query رو بسنج. اگه نمونهٔ لحظه‌ای قیمت/total در زمان خرید مهمه، نمونهٔ لحظه‌ای رو با معنای روشن نگه دار.

If it is derivable from lines, first query it. If a purchase-time price/total snapshot matters, store it with explicit semantics.

چطور test منفی امن باشه؟ / How do I make negative tests safe?

روی database آزمایشی و قابل‌حذف اجرا کن، هر statement رو در transaction قابل rollback قرار بده و نتیجهٔ ردشدن رو ثبت کن.

Use a disposable database, wrap test writes in rollback-capable transactions, and record the expected rejection.

طرح مرجع برای بازبینی، نه کپی کور / Reference shape for review, not blind copying

این اسکلت حداقل relationshipها رو نشان می‌ده؛ length، precision، status domain و audit policy رو براساس فرض‌های خودت تکمیل کن.

This skeleton shows the core relationships. Complete lengths, precision, status domain, and audit policy for your assumptions.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

Reference schema skeleton / اسکلت schema مرجع
CREATE SCHEMA Project85;
GO
CREATE TABLE Project85.Customer(
 CustomerId int IDENTITY PRIMARY KEY,
 Email nvarchar(254) NOT NULL UNIQUE,
 DisplayName nvarchar(120) NOT NULL
);
CREATE TABLE Project85.Product(
 ProductId int IDENTITY PRIMARY KEY,
 SKU nvarchar(40) NOT NULL UNIQUE,
 ProductName nvarchar(160) NOT NULL,
 CurrentPrice decimal(12,2) NOT NULL CHECK(CurrentPrice>=0)
);
CREATE TABLE Project85.SalesOrder(
 OrderId bigint IDENTITY PRIMARY KEY,
 CustomerId int NOT NULL REFERENCES Project85.Customer(CustomerId),
 CreatedAt datetime2 NOT NULL DEFAULT SYSUTCDATETIME(),
 Status varchar(20) NOT NULL
);
CREATE TABLE Project85.OrderLine(
 OrderId bigint NOT NULL REFERENCES Project85.SalesOrder(OrderId),
 LineNo smallint NOT NULL CHECK(LineNo>0),
 ProductId int NOT NULL REFERENCES Project85.Product(ProductId),
 Quantity int NOT NULL CHECK(Quantity>0),
 UnitPrice decimal(12,2) NOT NULL CHECK(UnitPrice>=0),
 CONSTRAINT PK_Project85_OrderLine PRIMARY KEY(OrderId,LineNo)
);

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

قیمت نمونهٔ لحظه‌ای در OrderLine هست تا تغییر قیمت کاتالوگ سفارش قدیمی رو عوض نکند. line amount از Quantity × UnitPrice حساب می‌شه. در production، سیاست لغو/حذف، concurrency و audit هنوز باید طراحی بشه.

UnitPrice is a line snapshot so catalog changes do not rewrite historical orders. Line amount is Quantity × UnitPrice. Production cancellation/deletion, concurrency, and audit policies still need design.

نیازمندی رو به جدول ترجمه نکن؛ اول به قانون تبدیلش کنDo not translate requirements straight into tables; turn them into rules first

یه اشتباه رایج اینه که متن نیازمندی رو خط‌به‌خط به column تبدیل کنیم. مثلاً «مشتری ایمیل داره» هنوز نمی‌گه ایمیل اجباریه، یکتاست یا قابل‌تغییره. «سفارش محصول داره» هم هنوز نمی‌گه قیمت امروز محصول باید روی سفارش قدیمی اثر بذاره یا نه. قبل از DDL، برای هر جمله سه سؤال بنویس: هویت این داده چیه؟ کدوم بخش باید همیشه درست بمونه؟ اگه داده تغییر کرد، تاریخچه باید چی بشه؟

A common mistake is translating each requirement sentence directly into a column. “A customer has an email” does not yet say whether it is required, unique, or mutable. “An order has products” does not say whether today’s product price should rewrite historical orders. Before DDL, ask three questions for every statement: what gives the data identity, which rule must always hold, and what should happen to history when data changes?

هر جدول رو با یک تست مثبت و یک تست منفی تحویل بدهDeliver every table with one positive and one negative test

فقط CREATE TABLE تحویل نده. بعد از ساخت schema، یه دادهٔ تمرینی کوچک بساز که چند حالت واقعی رو پوشش بده: مشتری با دو سفارش، سفارش چندردیفی، محصول غیرفعال و حداقل یک مشتری بدون سفارش. بعد برای هر constraint یه تست منفی بنویس. این تست‌ها باید داخل transaction باشن تا آخرش ROLLBACK بشن و محیط تمرین رو کثیف نکنن.

Do not deliver CREATE TABLE statements alone. Seed a small fixture with realistic cases: a customer with two orders, a multi-line order, an inactive product, and at least one customer with no order. Then write one negative test for each important constraint. Wrap destructive tests in transactions and roll them back so the lab remains clean.

Negative-test pattern / الگوی تست منفی
BEGIN TRANSACTION;

BEGIN TRY
    INSERT INTO Project85.OrderLine(OrderId, LineNo, ProductId, Quantity, UnitPrice)
    VALUES (1001, 1, 10, 0, 500000);
END TRY
BEGIN CATCH
    SELECT ERROR_NUMBER() AS ErrorNumber,
           ERROR_MESSAGE() AS ErrorMessage;
END CATCH;

ROLLBACK;

هدف این کد «خطا گرفتن» نیست؛ هدف اینه که ثابت کنی دیتابیس خودش جلوی state نامعتبر رو می‌گیره. اگه فقط اپلیکیشن validation داشته باشه، یه import یا script مستقیم می‌تونه قانون رو دور بزنه.

The point is not merely to produce an error. The point is to prove the database itself rejects an invalid state. Application-only validation can be bypassed by imports or direct scripts.

قبل از تحویل، خودت نقش reviewer رو بازی کنBefore handoff, act as your own reviewer

schema رو از روی یک دیتابیس خالی دوباره بساز. بعد scriptهای seed و بررسی رو به همون ترتیبی که تحویل می‌دی اجرا کن. اگه برای موفق‌شدن مجبور شدی چیزی رو دستی توی SSMS درست کنی، یعنی تحویلت هنوز کامل نیست. reviewer باید بتونه فقط با فایل‌های تو همون نتیجه رو بازتولید کنه.

Rebuild the schema from an empty database. Run seed and verification scripts in the exact order you plan to hand them off. If you need a manual SSMS fix, the deliverable is incomplete. A reviewer should reproduce the same result using only your files.

مرور نهایی / Final review

  • آیا هر requirement به constraint یا بررسی نهایی query وصل است؟ / Does every requirement map to a constraint or verification query?
  • آیا data types، NULL و uniqueness عمداً انتخاب شده‌اند؟ / Are data types, NULL, and uniqueness deliberate?
  • آیا خرابی testها فقط روی database آزمایشی و قابل‌حذف اجرا می‌شن؟ / Do failure tests run only on a disposable database?
  • آیا schema رو از صفر build کردی و نتیجهها رو ذخیره کردی؟ / Did you build from scratch and save results?
  • آیا assumptionها و محدودیت‌ها در README هستن؟ / Are assumptions and limitations in the README?

تحویل حرفه‌ای یعنی reviewer بتواند scriptها رو اجرا کند و خودش با query ببیند چه چیزی ثابت شده و چه چیزی هنوز فرض هست.

A professional handoff lets a reviewer run the scripts and distinguish what is proven from what remains an assumption.
