Lock، blocking و deadlock

Locks, blocking, and deadlocks

درخواست مشتری timeout شده اما CPU سرور پایین هست. یک transaction باز مانده و queryهای دیگر منتظرند. Restart کردن سرویس همه‌چیز رو پاک می‌کنه—تا رخداد بعدی. این بار blocker رو با session، wait و resource پیدا می‌کنیم و فرق blocking معمولی با deadlock رو می‌فهمیم.

A customer request times out while server CPU is low. An open transaction remains and other queries wait. Restarting clears things—until the next incident. We will identify the blocker through sessions, waits, and resources, then distinguish ordinary blocking from deadlock.

دو درخواست هم‌زمان؛ همین‌جا داستان سخت می‌شهTwo requests at once: this is where it gets interesting

یه query وقتی تنهاست ممکنه کاملاً بی‌نقص به نظر بیاد. مشکل از جایی شروع می‌شه که دو session هم‌زمان سراغ همون داده می‌رن. برای «Lock، blocking و deadlock» دو پنجره باز می‌کنیم، ترتیب دستورها رو دقیق نگه می‌داریم و می‌بینیم هر session چه چیزی می‌بینه، کجا منتظر می‌مونه و چه موقع کار به blocking یا deadlock می‌کشه.

A query can look perfect when it runs alone. The interesting behaviour starts when two sessions touch the same data. In “Locks, blocking, and deadlocks” we use two windows, control statement order carefully, and observe what each session sees, where it waits, and when blocking or deadlock appears.

Lock از سازگاری داده محافظت می‌کنه و می‌تونه منتظر بسازد / Locks protect consistency and can make work wait

خواندن/نوشتن بر اساس isolation و عملیات، lockهای مختلف می‌گیره. intent lock به موتور می‌گه پایین‌دست قفل وجود داره؛ key/page/object سطح‌های ممکن‌اند و lock escalation ممکنه چند قفل رو به سطح بالاتر ببرد. «یک SELECT بی‌خطر هست» درست نیست: مدت transaction، isolation و schema lock هم اثر دارن.

Reads and writes acquire locks according to isolation and operation. Intent locks describe lower-level locking; key, page, and object are possible granularities, and escalation may replace many locks with a higher-level one. “A SELECT is harmless” is false—transaction duration, isolation, and schema locks matter too.

نشست‌های منتظر و blocker رو مشاهده کن / Observe waiting requests and their blockers
SELECT r.session_id, r.blocking_session_id, r.status,
       r.wait_type, r.wait_time, r.wait_resource,
       DB_NAME(r.database_id) AS DatabaseName,
       SUBSTRING(t.text, (r.statement_start_offset/2)+1,
         ((CASE r.statement_end_offset WHEN -1 THEN DATALENGTH(t.text)
           ELSE r.statement_end_offset END-r.statement_start_offset)/2)+1) AS StatementText
FROM sys.dm_exec_requests AS r
OUTER APPLY sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE r.session_id <> @@SPID AND r.blocking_session_id <> 0;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

خروجی لحظه‌ای هست و ممکنه request پیش از اجرای query تمام بشه. برای root blocker، زنجیرهٔ blocking رو دنبال کن؛ session_id رو با connection درست تطبیق بده و قبل از KILL، مسئول و اثر rollback رو بفهم.

This is a momentary snapshot; a request may finish before the query runs. Follow the blocking chain to the root blocker, map session IDs to the right owner, and understand rollback impact before any KILL.

Blocking زنجیرهٔ انتظار است؛ همیشه deadlock نیست / Blocking is a wait chain, not necessarily a deadlock

در blocking، یک session resource رو نگه می‌داره و دیگری منتظر است؛ با پایان transaction blocker، منتظر می‌تونه ادامه دهد. در deadlock، A منتظر resource در اختیار B هست و B هم منتظر resource در اختیار A؛ موتور چرخه رو تشخیص می‌ده و یک victim رو rollback می‌کنه تا باقی پیش برود.

In blocking, one session holds a resource while another waits; once the blocker ends, the waiter may continue. In a deadlock, A waits for B's resource while B waits for A's; SQL Server detects the cycle and rolls back a victim so the other can proceed.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

یک blocking کوتاه و کنترل‌شده / A short, controlled blocking reproduction
-- Session A
BEGIN TRAN;
UPDATE Lab53.Account SET Balance=Balance-1 WHERE AccountId=1;
WAITFOR DELAY '00:00:15';
ROLLBACK;
-- During the delay, Session B runs:
UPDATE Lab53.Account SET Balance=Balance+1 WHERE AccountId=1;
GO

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

در زمان delay، query تشخیصی قبلی رو از session سوم اجرا کن. این آزمایش فقط چند ثانیه در lab هست و session A رو بعدش rollback می‌کنه. برای deadlock، دو session باید resourceها رو در ترتیب معکوس بگیرند؛ چنانچه اجرا شد، trace flag یا رخداد deadlock graph رو در محیط آزمایشی بخوان.

During the delay, run the diagnostic query from a third session. This is a brief lab-only test and session A rolls back. To reproduce a deadlock, have two sessions acquire resources in opposite order; inspect the deadlock graph in a test environment.

Deadlock رو با ترتیب دسترسی و retry امن درمان کن / Address deadlocks with consistent access order and safe retry

ترتیب ثابت دسترسی به ردیف‌ها می‌تونه چرخه رو حذف کند. transaction رو کوتاه کن، index مناسب بده تا lockهای غیرضروری کم بشه، و عملیات بیرونی رو از transaction بیرون ببر. retry باید محدود، با backoff و idempotent باشه؛ retry کور می‌تونه side effect رو دوباره انجام دهد.

A consistent resource access order can remove cycles. Keep transactions short, use appropriate indexes to reduce unnecessary locks, and move external work outside the transaction. Retries should be bounded, use backoff, and be idempotent; blind retries may repeat side effects.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Extended Event deadlock system_سلامت رو در محیط lab بررسی کن / Inspect deadlock evidence from system_health
SELECT CAST(event_data AS xml) AS DeadlockEvent
FROM sys.fn_xe_file_target_read_file
((SELECT TOP (1) CAST(target_data AS xml).value(
  '(EventFileTarget/File/@name)[1]', 'nvarchar(4000)')
  FROM sys.dm_xe_session_targets AS t
  JOIN sys.dm_xe_sessions AS s ON s.address=t.event_session_address
  WHERE s.name='system_health' AND t.target_name='event_file'), NULL, NULL, NULL)
WHERE object_name = 'xml_deadlock_report';
GO

Lock escalation رو با lock-count افسانه نساز / Do not diagnose escalation from a folklore lock count

موتور می‌تونه تعداد زیادی lock رو به table/partition level ارتقا دهد، اما trigger دقیق به memory pressure و موارد دیگر وابسته هست و نسخه/تنظیم مهم‌اند. lock escalation همیشه بد نیست؛ metadata و actual blocking رو بررسی کن. `ROWLOCK` hint تضمین نمی‌کنه escalation رخ ندهد.

The engine may escalate many locks to table/partition level, but triggers depend on memory pressure and other factors; version and settings matter. Escalation is not always bad. Inspect metadata and actual blocking. ROWLOCK does not guarantee escalation cannot happen.
