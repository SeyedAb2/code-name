Project 3 — take a production incident from guess to handoff

ساعت ۹:۱۲، endpoint سفارش کند شده؛ بعضی درخواست‌ها timeout می‌شن. هم‌زمان job شبانهٔ maintenance هنوز اجراست و گزارش‌ها هم کندند. کسی پیشنهاد restart و rebuild همهٔ indexها رو می‌ده. مأموریت تو: شواهد رو حفظ کن، علت رو از symptom جدا کن، repair محدود انجام بده و بازیابی رو بدون دست‌زدن به دیتابیس live ثابت کن.

At 09:12 the order endpoint slows and some requests time out. A maintenance job is still running, and reports are slow too. Someone proposes a restart and rebuilding every index. Preserve evidence, separate cause from symptom, apply a narrow repair, and prove recovery without touching a live database.

مأموریت / Mission

یک رخداد قابل‌بازتولید بساز یا از دادهٔ تمرینی کنترل‌شدهٔ course استفاده کن. حجم داده محدود اما کافی برای planهای معنادار باشه. سه شواهد track باید: کندی query/plan، blocking هم‌زمانی، و بازیابی از backup. هیچ‌کدوم رو روی دیتابیس customer واقعی اجرا نکن.

Create a reproducible incident or use a controlled course fixture. Keep data bounded but sufficient for meaningful plans. Collect three evidence tracks: query/plan slowdown, concurrency blocking, and backup recovery. Never run destructive steps on a real customer database.

اینجا دیگه کسی جواب رو بهت نمی‌گهHere nobody tells you the answer

این پروژه رو مثل رخداد واقعی ببین. چند علامت هم‌زمان داری و بعضی‌هاشون ممکنه ربطی به علت اصلی نداشته باشن. اولین کار restart نیست، اولین کار index ساختن هم نیست. خط زمانی درست کن، تغییر اخیر رو پیدا کن، درخواست‌های فعال و waitها رو ببین، plan رو با نسخهٔ سالم مقایسه کن و هر فرضیه رو یکی‌یکی رد یا تأیید کن.

Treat this like a real incident. Several symptoms appear at once and some may be unrelated to the root cause. The first action is not restart, and it is not creating an index. Build a timeline, find recent changes, inspect active requests and waits, compare plans with a healthy baseline, and test hypotheses one at a time.

پایان پروژه وقتی‌ـه که ثابتش کنیThe project ends when you prove recovery

کم‌شدن CPU یا سبزشدن سلامتcheck کافی نیست. query اصلی، blocking، backup/restore و دادهٔ کلیدی رو دوباره بررسی کن و بعد تحویل بده.

Lower CPU or a green health check is not enough. Re-verify the critical query, blocking state, backup/restore path, and known data before handoff.

محدودیت‌ها و قواعد ایمنی / Constraints and safety

  • فقط database با نام IncidentLab87؛ هر cleanup باید database آزمایشی و قابل‌حذف رو target کند. / Use only IncidentLab87; cleanup must target the disposable database.
  • ابتدا read-only شواهد؛ هیچ restart/kill/shrink/rebuild کور انجام نده. / Start with read-only evidence; no blind restart/kill/shrink/rebuild.
  • داده، بار کاری و concurrency محدود و سقف‌دار باشند. / Bound rows, workload, and concurrency.
  • هر secret ساختگی باشه؛ هیچ certificate/password واقعی در script/log ثبت نشه. / Use fake secrets only; do not log real credentials.
  • restore فقط به IncidentRestore87 با فایل و مسیر جدا انجام بشه. / Restore only to IncidentRestore87 using separate files/paths.
  • قبل/بعد رو با همان query، row count و معیار بسنج. / Compare before/after with the same query, row count, and metric.

شکل محیط / Lab shape

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

این پروژه service جدید production نمی‌سازه. Query Store/Extended Events/DMVها بسته به edition، permission و configuration در دسترس‌اند؛ جایگزین مجاز رو ثبت کن و از تفاوت محیط با نتیجه‌گیری اشتباه پرهیز کن.

This project does not build a new production service. Query Store, Extended Events, and DMVs vary by edition, permissions, and configuration; document approved substitutes and avoid overgeneralizing environment-specific results.

مراحل مأموریت / Mission milestones

  1. ثبت رخداد: impact، زمان UTC، endpoint/database، نرخ خطا و آخرین استقرار/job رو ثبت کن. / Capture impact, UTC time, endpoint/database, errors, and recent deploy/job.
  2. جمع‌آوری کم‌خطر: state، requests، waits، blocking، log/XE و resource نمونهٔ لحظه‌ای رو قبل از تغییر ذخیره کن. / Save state, requests, waits, blocking, logs/XE, and resource snapshots before changes.
  3. بازسازی کندی: query report رو با plan و STATISTICS IO/TIME اجرا و cardinality mismatch یا scan/sort رو پیدا کن. / Run the report with plan and IO/TIME; inspect estimates and operators.
  4. بازسازی blocking: دو session آزمایشی و قابل‌حذف رو طبق schedule کنترل‌شده اجرا؛ root blocker و wait resource رو شناسایی کن، نه اینکه بی‌درنگ kill کنی. / Run controlled sessions; find root blocker/resource rather than killing immediately.
  5. فرضیه و repair: یک اصلاح قابل‌برگشت انتخاب کن—query/index/transaction scope—و دلیلش رو پیش از اجرا بنویس. / Choose one reversible query/index/transaction-scope repair and state the hypothesis first.
  6. همان بررسی نهایی: report، concurrency schedule، درستی invariant و تأخیر رو دوباره اجرا کن. / Rerun report, concurrency schedule, correctness invariants, and latency.
  7. Recovery drill: backup بگیر، در database جدا restore کن، CHECKDB و رکورد/aggregate شناخته‌شده رو بررسی کن و زمان RPO/RTO رو ثبت کن. / Back up, restore separately, run CHECKDB and known-data checks, and record RPO/RTO.
  8. هندآف: خط زمانی، شواهد، cause، mitigation/fix، rollback، unknowns و پایش مسئول رو تحویل بده. / Hand off timeline, evidence, cause, mitigation/fix, rollback, unknowns, and monitoring owner.

معیار پذیرش با شاهد / Evidence-based acceptance

  • Incident خط زمانی حداقل یک خط پایه و زمان رخداد رو داره. / Timeline includes baseline and incident time.
  • blocking به root blocker و statement وصل شده؛ خروجی transient با محدودیت ثبت شده. / Blocking is linked to root blocker/statement with transient-evidence limits.
  • plan قبل/بعد ذخیره و تغییر operator/estimate با query مشخص توضیح داده شده. / Before/after plans are saved and changes explained for a specific query.
  • repair همان درستی invariant رو حفظ کرده و همان بار کاری بررسی نهایی رو پاس می‌کنه. / Repair preserves invariants and passes the same workload test.
  • backup artifact در database دیگری restore شده؛ DBCC CHECKDB و query شناخته‌شده موفق‌اند. / Backup is restored to another database; CHECKDB and a known query pass.
  • Observed RPO/RTO همراه با محدودیت‌ها گزارش شده، نه صرفاً target فرضی. / Observed RPO/RTO and limitations are reported.
  • هیچ اقدام destructive روی دادهٔ live اجرا نشده هست. / No destructive action ran on live data.

راهنمایی‌های بازشونده / Collapsible hints

اول restart کنم؟ / Should I restart first?

نه تا وقتی شواهد زنده رو جمع نکرده‌ای. restart می‌تونه wait، session و cache state رو از بین ببرد و مشکل رو موقتاً پنهان کند.

Not before collecting live evidence. Restart can erase session/wait context and temporarily hide the issue.

یک wait بالا یعنی علت؟ / Is a top wait the cause?

نه. wait رو با request، blocker، plan، زمان و بار کاری مرتبط کن. cumulative wait بدون اختلاف یا خط زمانی تشخیص رخداد نیست.

No. Correlate waits with requests, blockers, plans, time, and workload. Cumulative waits without deltas/timeline do not diagnose an incident.

backup بررسیonly سبز شد؛ تمام؟ / VERIFYONLY succeeded—done?

نه. restore کامل به database جدا، consistency check و query دادهٔ شناخته‌شده باید.

No. Perform a full isolated restore, consistency check, and known-data query.

پنج دقیقهٔ اول: دست نزن، خط زمانی بسازFirst five minutes: change nothing, build a timeline

رخداد از ۹:۱۲ شروع شده، اما این فقط اولین زمانی‌ـه که کاربر دیده. قبلش چه چیزی عوض شده؟ استقرار داشتیم؟ job از ۹:۰۰ شروع شده؟ SQL Server restart شده؟ حجم ورودی غیرعادی بوده؟ چهار ستون ساده بساز: زمان UTC، اتفاق، منبع شاهد و فرضیه. همین جدول کوچیک جلوی کلی حدس تصادفی رو می‌گیره.

The incident was noticed at 09:12, but that is only when a user saw it. What changed before then? A deployment? A 09:00 job? A SQL Server restart? Unusual traffic? Build four columns: UTC time, event, evidence source, and hypothesis. This small timeline prevents a surprising amount of random guessing.

از symptom به root blocker برو، نه برعکسMove from symptoms to the root blocker, not the other way around

اول درخواست‌های فعال، waitها و blocking chain رو ثبت کن. بعد متن query و plan رو بگیر. اگه یه session منتظر lockه، خودش لزوماً مقصر نیست؛ ممکنه session دیگه transaction رو باز گذاشته باشه. هر تصمیم باید به یک شاهد وصل باشه.

Capture active requests, waits, and the blocking chain first. Then collect query text and plan evidence. A session waiting on a lock is not necessarily the culprit; another session may have left a transaction open. Tie every action to evidence.

Snapshot the active incident / نمونهٔ رخداد فعال
SELECT session_id,
       status,
       wait_type,
       wait_time,
       blocking_session_id,
       cpu_time,
       total_elapsed_time
FROM sys.dm_exec_requests
WHERE session_id <> @@SPID
ORDER BY total_elapsed_time DESC;

این query فقط یک نمونهٔ لحظه‌ای لحظه‌ایه. برای deadlock یا رخدادهای خیلی کوتاه، Extended Events یا Query Store ممکنه شاهد بهتری بده. هیچ ابزار واحدی «علت» رو مستقیم تحویلت نمی‌ده.

This query is only a point-in-time snapshot. For deadlocks or very short events, Extended Events or Query Store may preserve better evidence. No single tool hands you the root cause automatically.

repair باید کوچک، قابل‌برگشت و قابل‌اندازه‌گیری باشهRepairs should be narrow, reversible, and measurable

اگه علت query بد بود، اول نسخهٔ اصلاحی رو در محیط آزمایشی با دادهٔ مشابه بسنج. اگه blocker بود، scope تراکنش یا ترتیب دسترسی رو اصلاح کن. اگه plan regression بود، قبل از force کردن plan دلیل تغییر رو بفهم. restart آخرین میان‌بره، چون کلی شاهد رو پاک می‌کنه و ممکنه فقط symptom رو موقتاً بخوابونه.

If the cause is a poor query, test the rewrite against representative data first. If it is blocking, repair transaction scope or access order. If it is a plan regression, understand the change before forcing a plan. Restart is a last-resort shortcut because it destroys evidence and may only hide the symptom temporarily.

آخر کار باید چهار چیز رو دوباره ثابت کنیAt the end, re-prove four things

  1. query اصلی به تأخیر قابل‌قبول برگشته و plan مورد انتظار رو داره. / The critical query is back within acceptable latency with the expected plan.
  2. blocking/deadlock غیرعادی از بین رفته یا به سطح خط پایه برگشته. / Abnormal blocking/deadlocks are gone or back to baseline.
  3. دادهٔ کلیدی درست مونده؛ repair درستی رو خراب نکرده. / Known data remains correct; the repair did not trade correctness for speed.
  4. backup/restore path هنوز قابل‌استفاده‌ست و artifact لازم برای rollback/DR مشخصه. / The backup/restore path is still usable and rollback/DR artifacts are known.

بعدش یه تحویل کوتاه بنویس: چی دیدیم، علت چی بود، چی عوض کردیم، چطور ثابت کردیم و برای اینکه دوباره تکرار نشه چه کاری مونده.

Then write a short handoff: what we observed, the cause, the change, how recovery was proven, and what remains to prevent recurrence.

تحویل عملیاتی / Operational handoff

  • آیا گزارشگر دیگری می‌تونه با README همان رخداد رو بازسازی کند؟ / Can another engineer reproduce the incident from the README?
  • آیا شواهد پیش از containment ذخیره شد؟ / Was evidence saved before containment?
  • آیا repair با یک علت و یک بررسی نهایی مشخص پیوند داره؟ / Is the repair tied to a cause and a specific verification?
  • آیا restore روی دیتابیس جدا انجام شد و data proof داره؟ / Was restore isolated and does it include data proof?
  • آیا unknownها، risk باقیمانده و rollback صادقانه نوشته شده‌اند؟ / Are unknowns, residual risks, and rollback stated honestly?

رخداد با green شدن داشبورد تمام نمی‌شه. وقتی داده درسته، سرویس به معیار توافق‌شده برگشته، بازیابی آزموده شده و نفر بعدی راهنمای عملیات قابل‌اجرا داره، رخداد رو تحویل بده.

A green dashboard does not close an incident. Hand it off when data is correct, service meets the agreed measure, recovery has been tested, and the next operator has an executable runbook.
