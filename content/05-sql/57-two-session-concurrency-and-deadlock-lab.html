آزمایش دو نشست: blocking و deadlock

Two-session lab: blocking and deadlocks

گزارش می‌گه دو پرداخت گاهی معطل می‌شن و گاهی یکی خطای deadlock می‌گیره. با یک query تنها نمی‌تونیم این رو ببینیم؛ باید دو connection رو هماهنگ کنیم، زمان شروع رو کنترل کنیم و بفهمیم هرکدوم کدوم resource رو نگه داشته‌اند.

Two payments sometimes wait and sometimes fail with a deadlock. One query cannot reproduce this; we need coordinated connections, controlled timing, and evidence of which resource each session holds.

دو درخواست هم‌زمان؛ همین‌جا داستان سخت می‌شهTwo requests at once: this is where it gets interesting

یه query وقتی تنهاست ممکنه کاملاً بی‌نقص به نظر بیاد. مشکل از جایی شروع می‌شه که دو session هم‌زمان سراغ همون داده می‌رن. برای «آزمایش دو نشست: blocking و deadlock» دو پنجره باز می‌کنیم، ترتیب دستورها رو دقیق نگه می‌داریم و می‌بینیم هر session چه چیزی می‌بینه، کجا منتظر می‌مونه و چه موقع کار به blocking یا deadlock می‌کشه.

A query can look perfect when it runs alone. The interesting behaviour starts when two sessions touch the same data. In “Two-session lab: blocking and deadlocks” we use two windows, control statement order carefully, and observe what each session sees, where it waits, and when blocking or deadlock appears.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

دو connection یعنی دو session مستقل / Two connections mean two independent sessions

در SSMS دو پنجرهٔ query باز کن، در هرکدوم `SELECT @@SPID` اجرا کن و شناسه‌ها رو یادداشت کن. از Lab53 استفاده می‌کنیم؛ قبل از آزمایش مقدارها رو query کن و پس از هر سناریو transaction count هر دو پنجره رو صفر نگه دار. اگه اتصال قطع شد، قبل از ادامه state رو بررسی کن.

Open two query windows, run `SELECT @@SPID` in each, and record the IDs. Use Lab53; inspect starting values and ensure both sessions end with transaction count zero. If a connection drops, inspect state before continuing.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

شناسه و وضعیت هر نشست رو ثبت کن / Record session and transaction state
SELECT @@SPID AS SessionId, @@TRANCOUNT AS TranCount,
       XACT_STATE() AS XactState;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

این خروجی فقط همین session رو توصیف می‌کنه. پنجرهٔ دیگری باید query خودش رو اجرا کند؛ copy کردن یک SPID به‌عنوان session دوم کافی نیست.

This output describes only the current session. The other window must execute its own query; copying an SPID does not create a second session.

اول blocking ساده رو بساز و شواهد بگیر / Reproduce simple blocking and collect evidence first

در پنجرهٔ A یک update رو داخل transaction نگه دار. پیش از ROLLBACK، در B همان row رو update کن. در پنجرهٔ C query تشخیصی blocking رو اجرا کن. باید blocking_session_id، wait_type و wait_resource رو به session A وصل کنی؛ بعد A رو rollback و B رو دوباره بررسی کن.

In A, hold an update open in a transaction. Before rollback, update the same row in B. In C, run the blocking diagnostic. Correlate blocking_session_id, wait_type, and wait_resource to A; then roll back A and observe B continue.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

A رو اجرا کن، سپس B و هم‌زمان C / Run A, then B, and C while B waits
-- Session A
BEGIN TRAN;
UPDATE Lab53.Account SET Balance=Balance-1 WHERE AccountId=1;
WAITFOR DELAY '00:00:20';
ROLLBACK;
-- Session B during the delay
UPDATE Lab53.Account SET Balance=Balance+1 WHERE AccountId=1;
-- Session C during the wait
SELECT session_id, blocking_session_id, wait_type, wait_time, wait_resource
FROM sys.dm_exec_requests WHERE blocking_session_id <> 0;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

اگه C هیچ ردیفی نشان نداد، شاید B پیش از query تمام شده، sessionها روی یک database نیستند یا predicateها به ردیف یکسان نرسیده‌اند. timing رو با delay کمی بیشتر در lab تنظیم کن، نه با ایجاد بار نامحدود.

If C returns no row, B may have finished, sessions may use different databases, or predicates may target different rows. Adjust the lab delay modestly; do not create unbounded load.

Deadlock چرخه است؛ اون رو با ترتیب معکوس می‌سازیم / A deadlock is a cycle; create it with reversed resource order

A اول account 1 رو قفل کند و سپس account 2 رو بخواهد؛ B برعکس. هر دو transaction رو هم‌زمان نگه دار. وقتی چرخه شکل بگیرد، SQL Server یک قربانی انتخاب می‌کنه. deadlock graph نشان می‌ده processها و resourceها چه بوده‌اند؛ پیام برنامه به‌تنهایی این جزئیات رو نداره.

A locks account 1 then requests account 2; B does the reverse. Hold both transactions concurrently. When a cycle forms, SQL Server chooses a victim. The deadlock graph shows processes and resources; the application error alone does not.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

دو پنجره رو مرحله‌ای اجرا کن؛ قربانی‌شدن یکی طبیعی هست / Coordinate both sessions; one victim is expected
-- Session A: run first, then pause before second update.
BEGIN TRAN;
UPDATE Lab53.Account SET Balance=Balance-1 WHERE AccountId=1;
WAITFOR DELAY '00:00:05';
UPDATE Lab53.Account SET Balance=Balance+1 WHERE AccountId=2;
COMMIT;
GO
-- Session B: start during A's delay; reverse account order.
BEGIN TRAN;
UPDATE Lab53.Account SET Balance=Balance-1 WHERE AccountId=2;
WAITFOR DELAY '00:00:05';
UPDATE Lab53.Account SET Balance=Balance+1 WHERE AccountId=1;
COMMIT;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

اگه deadlock بازتولید نشد، ترتیب زمان‌بندی رو تنظیم کن؛ این outcome زمان‌بندی‌محور هست. تراکنش قربانی rollback می‌شه و خطای 1205 برمی‌گرده. هر دو session رو از نظر @@TRANCOUNT/XACT_STATE بررسی و حساب‌ها رو query کن.

If no deadlock appears, adjust timing; the outcome is schedule-dependent. The victim rolls back with error 1205. Check @@TRANCOUNT/XACT_STATE in both sessions and query the accounts.

قبل از اینکه بریم بخش بعد، سعی کن بدون نگاه‌کردن به بالا در دو جمله بگی این فصل چه مسئله‌ای رو حل می‌کنه و از کدوم خروجی می‌فهمی راه‌حلت درست بوده. اگه فقط اسم دستورها یادت مونده، هنوز یه دور دیگه مثال قبلی رو با دادهٔ متفاوت اجرا کن.

Before moving on, explain in two sentences what problem this chapter solves and which output proves your solution is correct. If you only remember command names, rerun the previous example with different data.

ترتیب یکسان دسترسی رو اعمال و همان آزمون رو تکرار کن / Apply a consistent order and repeat the same test

هر دو transfer رو طوری بازنویسی کن که ابتدا حساب با شناسهٔ کوچک‌تر و سپس بزرگ‌تر به‌روزرسانی بشه. مقدار بدهی/بستانکاری رو بر اساس نقش حساب نگه دار، اما ترتیب lock رو ثابت کن. بعد همان دو نشست رو با همان داده و timing تکرار و graph/خطا رو مقایسه کن.

Rewrite both transfers to update the lower account ID first, then the higher one. Preserve debit/credit semantics while standardizing lock order. Repeat the same two-session schedule and compare graph/errors.

الگوی اصلاح‌شده باید در برنامه transaction باشه / Use a deterministic ordering in the transaction
-- Pseudocode: calculate each account's delta, then apply in ID order.
-- UPDATE account with MIN(@AccountA, @AccountB) first;
-- UPDATE account with MAX(@AccountA, @AccountB) second;
-- Check @@ROWCOUNT for both and commit only if both are exactly one.
GO

این الگو احتمال deadlock ناشی از همین دو ردیف رو کم می‌کنه، اما deadlockهای دیگر resourceها یا queryها رو ناممکن نمی‌کنه. retry محدود خطای 1205 و transaction idempotent رو در لایهٔ برنامه بررسی کن.

This reduces deadlocks for this two-row pattern but does not eliminate all possible deadlocks. Handle error 1205 with bounded retries and idempotent application behavior.
