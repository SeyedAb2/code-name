CROSS JOIN و ضرب دکارتی

CROSS JOIN and Cartesian products

گزارش جدید ناگهان ده‌هزار ردیف داره، درحالی‌که انتظار چند ده ردیف می‌رفت. حدس اول «داده خراب هست»؛ اما شاید رابطهٔ دو جدول رو اصلاً ننوشته‌ایم. CROSS JOIN همهٔ ترکیب‌ها رو می‌سازه؛ گاهی همین دقیقاً نیاز هست و گاهی خطای پرهزینه.

A new report suddenly has ten thousand rows where only dozens were expected. The first guess is “bad data,” but perhaps the relationship between two tables was never written. CROSS JOIN creates every combination—sometimes exactly what we need, sometimes an expensive mistake.

پیش‌نیاز: فصل‌های ۱۱ تا ۱۵ · Prerequisites: Chapters 11–15SQL Server 2025 · T-SQLحدود ۷۵ دقیقه · ۱۸ تمرین / About 75 minutes · 18 exercises

اول تعداد ردیف‌ها رو حدس بزنPredict the row count first

گزارش سفارش‌ها معمولاً از جایی سخت می‌شه که یک جدول دیگه وارد ماجرا می‌شه. سه سفارش داری، چهار مشتری داری، پنج ردیف سفارش هم داری؛ حالا JOIN می‌زنی و ناگهان خروجی دوازده ردیف می‌شه. توی «CROSS JOIN و ضرب دکارتی» قبل از هر query اول حدس می‌زنیم چند ردیف باید برگرده، بعد اجرا می‌کنیم و از روی اختلاف حدسمون با واقعیت می‌فهمیم رابطه‌ها رو درست خوندیم یا نه.

Reports get interesting the moment another table enters the picture. You may have three orders, four customers, and five order lines, then a join suddenly returns twelve rows. In “CROSS JOIN and Cartesian products” we predict row counts before executing, then use any mismatch to diagnose our understanding of the relationships.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

چرا تعداد ردیف‌ها ناگهان ضرب شد؟ / Why did the row count multiply?

قبل از عوض‌کردن query، تعداد دو ورودی رو بشمار. اگه مجموعهٔ A سه ردیف و B چهار ردیف داشته باشه، CROSS JOIN دوازده جفت می‌سازه. هر ردیف A با هر ردیف B ترکیب می‌شه. این نتیجهٔ تعریف اتصال است، نه خرابی یا duplicate تصادفی.

Before changing the query, count each input. If A has three rows and B has four, CROSS JOIN produces twelve pairs. Every A row combines with every B row. That is the definition of the join, not corruption or accidental duplication.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

ترکیب کامل دو مجموعهٔ کوچک / Every combination of two small sets
DROP TABLE IF EXISTS #Sizes, #Colors;
CREATE TABLE #Sizes (SizeName varchar(10) PRIMARY KEY);
CREATE TABLE #Colors (ColorName varchar(10) PRIMARY KEY);
INSERT #Sizes VALUES ('S'), ('M'), ('L');
INSERT #Colors VALUES ('Red'), ('Blue');

SELECT s.SizeName, c.ColorName
FROM #Sizes AS s
CROSS JOIN #Colors AS c
ORDER BY s.SizeName, c.ColorName;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

سه اندازه ضربدر دو رنگ، شش ترکیب هست. اگه یکی از ورودی‌ها خالی باشه، خروجی هم صفر ردیف می‌شه. پیش از اجرای CROSS JOIN روی مجموعهٔ بزرگ، اندازهٔ هر ورودی و تعداد حاصل‌ضرب رو تخمین بزن.

Three sizes times two colors equals six combinations. If either input is empty, the result has zero rows. Before a CROSS JOIN on large sets, estimate each input size and the product.

CROSS JOIN چه وقت خواستهٔ واقعی است؟ / When is CROSS JOIN intentional?

فروشگاه می‌خواد ماتریس همهٔ اندازه‌ها و رنگ‌ها رو برای ساخت کاتالوگ آماده کند؛ اینجا ترکیب هر اندازه با هر رنگ عمداً باید. همین‌طور می‌توان از آن برای ساخت تقویم نمونه یا تولید سناریوهای آزمون کوچک استفاده کرد. اما اگه هر محصول فقط رنگ‌های مشخص خودش رو داره، CROSS JOIN به‌تنهایی مدل رابطه رو بیان نمی‌کنه.

A shop wants a catalog matrix of every size and color; combining every size with every color is intentional. It can also help build small calendars or test scenarios. But if each product supports only certain colors, CROSS JOIN alone does not represent that relationship.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

سناریوی آزمون کنترل‌شده / A bounded test matrix
SELECT s.SizeName, c.ColorName,
       CONCAT(s.SizeName, '-', c.ColorName) AS SkuDraft
FROM #Sizes AS s
CROSS JOIN #Colors AS c
ORDER BY s.SizeName, c.ColorName;

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

این فقط draft می‌سازه؛ وجود ترکیب در ماتریس به معنی قابل‌فروش‌بودن آن نیست. قاعدهٔ کسب‌وکار ممکنه ترکیب‌هایی رو حذف کند یا موجودی رو جداگانه بررسی کند.

This creates drafts only; a combination in the matrix does not mean it is sellable. Business rules may exclude combinations or require a separate inventory check.

وقتی شرط رابطه جا افتاده / When the relationship predicate is missing

اگه قصدت اتصال رابطه‌ای هست و `ON` رو جا انداخته‌ای، SQL Server ممکنه query رو رد کند؛ اما گاهی با comma join یا شرط `ON 1=1` عملاً محصول دکارتی ساخته‌ای. اگه تعداد خروجی ناگهان زیاد شد، اول FROM و JOIN و شرط‌ها رو بخوان؛ DISTINCT رو برای کم‌کردن عدد اضافه نکن.

If you intended a relational join but omitted ON, SQL Server may reject the query; however, comma joins or `ON 1=1` can effectively create a Cartesian product. If row counts explode, inspect FROM/JOIN predicates first; do not add DISTINCT just to reduce the number.

این query همه‌چیز رو با همه‌چیز جفت می‌کنه / This pairs everything with everything
SELECT p.ProductId, c.CustomerId
FROM shop.Products AS p
CROSS JOIN shop.Customers AS c;
GO

-- برای گزارش سفارش، رابطهٔ واقعی را بیان کن:
SELECT o.OrderId, c.CustomerId
FROM shop.Orders AS o
JOIN shop.Customers AS c ON c.CustomerId = o.CustomerId;
GO

در گزارش دوم، کلید رابطه رو می‌نویسیم. اگه query عمداً آزمایش همهٔ محصول/مشتری‌هاست، CROSS JOIN قابل‌فهم است؛ برای فاکتور، معنای نادرستی داره. قصد رو با اسم alias و توضیح کوتاه روشن کن.

The second query states the relationship key. If the goal is deliberately to test every product/customer pair, CROSS JOIN is understandable; for invoices it is semantically wrong. Make intent clear with aliases and a short comment.

حاصل‌ضرب اندازهٔ ورودی‌ها / Multiply the input sizes

فرمول تعداد خروجی وقتی کلید یا فیلتر دیگری در کار نیست، `|A| × |B|` هست. شرط WHERE بعد از ساخت منطقی ترکیب‌ها ممکنه بخشی رو حذف کند؛ برای طراحی، از اول رابطهٔ درست رو مشخص کن.

With no additional predicate, output cardinality is `|A| × |B|`. A WHERE condition may filter combinations afterward; design by stating the intended relationship first.
