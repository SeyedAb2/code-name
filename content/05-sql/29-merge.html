MERGE و OUTPUT؛ همگام‌سازی کنترل‌شده

MERGE and OUTPUT: controlled synchronisation

فهرست قیمت تازه رسیده: بعضی محصول‌ها موجودند، بعضی تازه‌اند و بعضی در فایل نیستند. غیبت در فایل الزاماً مجوز حذف نیست. اول اختلاف‌ها رو می‌بینیم؛ بعد فقط تغییرهای مورد توافق رو اعمال می‌کنیم.

A new price feed arrives: some products exist, some are new, and some are absent. Absence is not automatically permission to delete. Inspect differences first, then apply only agreed changes.

اینجا اشتباه دیگه فقط خروجی بد نیستHere a mistake changes data, not just output

تا قبل از این، بدترین اتفاق معمولاً یه خروجی اشتباه بود. از اینجا به بعد query می‌تونه دادهٔ واقعی رو عوض کنه. برای «MERGE و OUTPUT؛ همگام‌سازی کنترل‌شده» عادت می‌کنیم قبل از تغییر، target رو با SELECT ببینیم، تغییر رو داخل transaction امن انجام بدیم، تعداد ردیف‌های اثرگرفته رو چک کنیم و تازه بعد تصمیم بگیریم COMMIT کنیم یا ROLLBACK.

Until now, the worst outcome was usually a wrong result set. From here on, a statement can change real data. With “MERGE and OUTPUT: controlled synchronisation” we preview the target rows, make the change inside a safe transaction, inspect affected rows, and only then decide whether to COMMIT or ROLLBACK.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

اول اختلاف رو پیدا کن / Start by finding the differences

MERGE دو مجموعه رو با شرط ON جفت می‌کنه. ردیف جفت‌شده می‌تونه update بشه؛ ردیف source بدون target می‌تونه insert بشه؛ و ردیف target بدون source رو می‌توان در شاخه‌ای جدا حذف کرد. همین شاخهٔ حذف می‌تونه خطرناک باشه: فایل شاید ناقص یا فقط بخشی از داده باشه.

MERGE matches two sets using ON. A matched row can be updated, a source-only row inserted, and a target-only row optionally deleted. That deletion branch is risky when the feed may be partial.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

محیط آزمایشی و بررسی دو طرف / Disposable fixture and source inspection
DROP TABLE IF EXISTS #T, #S;
CREATE TABLE #T
(
  ProductId int PRIMARY KEY,
  ProductName nvarchar(40) NOT NULL,
  UnitPrice decimal(10,2) NOT NULL
);
CREATE TABLE #S
(
  ProductId int PRIMARY KEY,
  ProductName nvarchar(40) NOT NULL,
  UnitPrice decimal(10,2) NOT NULL
);
INSERT #T VALUES (1,N'Keyboard',50),(2,N'Mouse',20);
INSERT #S VALUES (1,N'Keyboard',55),(3,N'Webcam',80);
SELECT * FROM #T ORDER BY ProductId;
SELECT * FROM #S ORDER BY ProductId;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

محصول ۱ در هر دو هست ولی قیمتش فرق داره؛ ۳ فقط در source است؛ ۲ فقط در target هست. هنوز معلوم نیست ۲ حذف شده یا این feed اصلاً کامل نیست. این تفاوت باید در قرارداد ورودی روشن بشه.

Product 1 exists on both sides with a different price; 3 is source-only; 2 is target-only. We do not yet know if 2 was retired or the feed is incomplete. The input contract must answer that.

کلید رو از مقدار جدا نگه دار / Separate identity matching from value changes

ON باید کلید هویت پایدار رو تطبیق دهد. شرط تغییر قیمت رو در WHEN MATCHED AND می‌گذاریم؛ اگه قیمت رو داخل ON ببری، رکورد موجود با قیمت تازه unmatched می‌شه و ممکنه insert تکراری بشه. قید یکتا هم در source و هم target محافظت مهمی هست.

ON should match a stable identity key. Put the price-change test in WHEN MATCHED AND; if price is part of ON, a changed value may look unmatched and become a duplicate insert. Unique keys on both source and target remain important.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

فقط درج تازه و به‌روزرسانی لازم / Insert new rows and update changed values
MERGE #T AS target
USING #S AS source
  ON target.ProductId = source.ProductId
WHEN MATCHED AND
     (target.UnitPrice <> source.UnitPrice
      OR target.ProductName <> source.ProductName)
  THEN UPDATE SET
       ProductName = source.ProductName,
       UnitPrice = source.UnitPrice
WHEN NOT MATCHED BY TARGET
  THEN INSERT (ProductId, ProductName, UnitPrice)
       VALUES (source.ProductId, source.ProductName, source.UnitPrice)
OUTPUT $action AS MergeAction,
       inserted.ProductId,
       deleted.UnitPrice AS OldPrice,
       inserted.UnitPrice AS NewPrice;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

MERGE باید با semicolon تمام بشه. OUTPUT با $action نوع عمل رو برای هر ردیف برمی‌گردونه؛ ترتیب ردیف‌های خروجی تضمین نیست. اگه statement خطا داد، OUTPUT احتمالی رو موفقیت قطعی فرض نکن؛ target رو دوباره query کن.

Terminate MERGE with a semicolon. OUTPUT with $action reports the action per row, but output order is not guaranteed. If the statement errors, do not treat returned output as proof of success; query the target again.

کلید تکراری در source رو پیش از تغییر پیدا کن / Detect duplicate source keys before mutation

دو ردیف source با یک ProductId نمی‌توانند به شکل مبهم یک ردیف target رو update کنند. به‌جای حدس‌زدن syntax، کیفیت staging رو بررسی و قانون رو روشن کن: ردکردن batch یا انتخاب رکورد برنده بر اساس زمان و کلید شکستن تساوی.

Two source rows with one ProductId cannot unambiguously update one target row. Do not search for a syntax trick; define a staging rule: reject the batch or select a winner using timestamp and a deterministic tie-breaker.

گزارش کلیدهای تکراری / Report duplicate keys
SELECT ProductId, COUNT(*) AS SourceRows
FROM #S
GROUP BY ProductId
HAVING COUNT(*) > 1;
GO

خروجی خالی فقط می‌گه در همین داده تکراری ندیدیم؛ قید unique روی staging این قاعده رو در ورودهای بعد هم enforce می‌کنه.

No rows means no duplicates were found in this batch. A unique constraint on staging enforces the rule for future loads too.

قبل از اینکه بریم بخش بعد، سعی کن بدون نگاه‌کردن به بالا در دو جمله بگی این فصل چه مسئله‌ای رو حل می‌کنه و از کدوم خروجی می‌فهمی راه‌حلت درست بوده. اگه فقط اسم دستورها یادت مونده، هنوز یه دور دیگه مثال قبلی رو با دادهٔ متفاوت اجرا کن.

دادهٔ غایب رو بی‌فکر حذف نکن / Do not delete merely because a row is absent

شاخهٔ WHEN NOT MATCHED BY SOURCE THEN DELETE ممکنه همهٔ targetهایی رو پاک کند که در feed فعلی نیستند. اگه ورودی صفحه‌بندی‌شده، ناقص یا محدود به منطقه باشه، نتیجه فاجعه هست. برای حذف باید ثابت کنی ورودی نمونهٔ لحظه‌ای کامل همان محدوده هست و دامنهٔ target رو هم محدود کنی.

WHEN NOT MATCHED BY SOURCE THEN DELETE can remove target rows absent from the current feed. A paginated, incomplete, or region-limited input makes this dangerous. Deletion requires proof that the feed is a complete snapshot for the exact target scope.

اول فهرست review بساز، نه DELETE / Build a review list before any delete
SELECT target.ProductId
FROM #T AS target
LEFT JOIN #S AS source ON source.ProductId = target.ProductId
WHERE source.ProductId IS NULL;
GO

در دادهٔ تمرینی فعلی محصول ۲ فقط در مقصد هست. گزارشش کن، تعداد و علت رو بررسی کن و تصمیم حذف رو جدا ثبت کن. «در فایل نیست» و «بازنشسته شده» یک معنی ندارن.

Product 2 is target-only in this fixture. Report it, inspect count and cause, and record deletion as a separate decision. “Not in this file” is not the same as “retired.”

MERGE انتخاب است، نه قانون همیشگی / MERGE is an option, not a universal rule

MERGE branchها رو کنار هم می‌آورد، اما برای منطق پیچیده یا هم‌زمانی حساس، UPDATE و INSERT جدا در تراکنش ممکنه ساده‌تر بررسی شوند. تصمیم رو با قیدهای یکتا، شرط‌ها، isolation، locking و رفتار نسخهٔ هدف بگیر؛ نه با شعار «همیشه» یا «هرگز».

MERGE combines branches, but separate UPDATE and INSERT statements in a transaction may be easier to reason about for complex rules or sensitive concurrency. Decide using constraints, predicates, isolation, locking, and target-version behavior—not “always” or “never.”

حتی با MERGE، unique key مقصد باید. برای رفتار concurrent، این query رو بعداً در دو session و با مفهوم transaction و lock آزمایش می‌کنیم.

Even with MERGE, a target unique key is essential. We will test concurrent behavior with two sessions when we study transactions and locks.
