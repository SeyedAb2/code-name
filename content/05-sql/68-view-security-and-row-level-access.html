View و دسترسی ردیفی

Views and row-level access

هر tenant فقط باید سفارش‌های خودش رو ببیند. ساختن view کافی نیست اگه user بتواند جدول پایه رو مستقیم بخواند؛ RLS هم کافی نیست اگه مسیر admin، session زمینه یا policy رو بررسی نکنیم. دسترسی رو با query مثبت و منفی ثابت می‌کنیم.

Each tenant should see only its own orders. A view is insufficient if users can read the base table directly; RLS is insufficient if admin paths, session context, or policy state are ignored. We prove access with positive and negative queries.

پیش‌نیاز: permission و schemaPrerequisites: permissions and schemaحدود ۹۰ دقیقه · ۱۸ تمرین / About 90 minutes · 18 exercises

این دفعه سؤال اینه: چه کسی اجازه داره؟This time the question is: who is allowed?

خیلی از دیتابیس‌ها از نظر query درستن ولی از نظر دسترسی نه؛ چون اپ با کاربری وصل می‌شه که تقریباً همه‌چیز بلده و همه‌چیز می‌تونه. «View و دسترسی ردیفی» رو با حساب محدود جلو می‌بریم. هر مجوزی که می‌دیم، با همون کاربر امتحانش می‌کنیم تا فرق «فکر می‌کنم بسته‌ست» با «واقعاً بسته‌ست» روشن بشه.

Many databases are query-correct but permission-wrong because the application connects with an account that can do almost anything. In “Views and row-level access” we work with restricted principals and test permissions as those principals so “I think it is locked down” becomes demonstrable behaviour.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

View تنها وقتی مرز هست که مجوز درست باشه / A view is a boundary only with correct permissions

View می‌تونه ستون یا ردیف رو محدود کند، اما مجوز روی جدول پایه، مالکیت و مسئولship chaining نتیجه رو عوض می‌کنن. با user واقعی view رو بخوان و SELECT مستقیم رو هم امتحان کن. SELECT * مرز شکننده‌ای است؛ ستون‌های لازم رو صریح بنویس.

A view can restrict columns or rows, but base-table permissions, ownership, and ownership chaining affect the result. Query as the intended user and test direct base-table access too. SELECT * is a fragile boundary; list required columns explicitly.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

View با projection روشن / Explicit view projection
CREATE OR ALTER VIEW reporting.OpenOrders AS
SELECT OrderId,OrderDate,Status
FROM dbo.Orders
WHERE Status='Open';
GO
GRANT SELECT ON OBJECT::reporting.OpenOrders TO report_reader;
-- Verify both view access and direct table access as report_reader.

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

RLS predicate باید با tenant identity جور باشه / The RLS predicate must match tenant identity

Row-Level Security با filter predicate ردیف‌های قابل‌خواندن رو فیلتر می‌کنه و block predicate می‌تونه نوشتن ناسازگار رو رد کند. predicate function ساده، schema-bound و قابل‌آزمون نگه دار. اگه از SESSION_CONTEXT استفاده می‌کنی، بدان چه جزء مورداعتماد اون رو تنظیم می‌کنه؛ مقدار client قابل‌اعتماد فرض نمی‌شه.

Row-Level Security filter predicates restrict visible rows; block predicates can reject inconsistent writes. Keep predicate functions simple, schema-bound, and testable. If using SESSION_CONTEXT, define which trusted component sets it; client-supplied state is not automatically trustworthy.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

الگوی مفهومی tenant predicate / Conceptual tenant predicate
CREATE FUNCTION Security.fn_tenant_access(@TenantId int)
RETURNS TABLE WITH SCHEMABINDING
AS RETURN
 SELECT 1 AS allowed
 WHERE @TenantId = TRY_CONVERT(int,SESSION_CONTEXT(N'TenantId'));
-- Attach through a SECURITY POLICY only in a disposable database.

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

نمونه رو قبل از اجرا با نسخهٔ SQL Server و مستند رسمی تطبیق بده. نبود زمینه باید fail closed باشه؛ tenant دیگر رو با principal محدود آزمایش کن. مدیرهای privileged ممکنه مسیر دسترسی متفاوتی داشته باشند.

Validate syntax and behavior for the target version. Missing context should fail closed; test another tenant as a restricted principal. Privileged administrators may have different access paths.

راه‌های دورزدن رو هم بیازما / Test bypass paths too

join، aggregate، export، procedure و userهای privileged رو بررسی کن. policy روشن است؟ predicate برای INSERT و UPDATE هم اعمال شده؟ مجوز DDL اجازهٔ خاموش‌کردن policy نمی‌ده؟ تست‌های مثبت و منفی رو خودکار کن. RLS جای authorization سطح برنامه یا حفاظت در برابر مدیر مجاز نیست.

Inspect joins, aggregates, exports, procedures, and privileged users. Is the policy enabled? Are INSERT/UPDATE paths covered? Can the principal alter/disable it? Automate positive and negative tests. RLS does not replace application authorization or protect against an authorized administrator.

کنترل امنیتی رو با مسیر منفی ثابت کن / Prove security with a negative path

View رو با SELECT مستقیم، و RLS رو با زمینه درست/غلط و عملیات نوشتن سنجیدیم. مجوزها، identity و مسیر admin بخشی از طراحی‌اند. تنها دیدن CREATE SECURITY POLICY یا GRANT اثبات جداسازی tenant نیست.

We tested views against direct access and RLS with valid/invalid context and writes. Permissions, identity, and admin paths are part of the design. Seeing CREATE SECURITY POLICY or GRANT is not proof of tenant isolation.
