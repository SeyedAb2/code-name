ایندکس ۲: ترتیب ستون، INCLUDE و filtered index

Indexes 2: key order, INCLUDE, and filtered indexes

تیم سه index ساخته اما query اصلی هنوز lookup داره. یکی همهٔ خروجی‌ها رو به key اضافه کرده، دیگری روی ستون کم‌تنوع هست. این بار از شکل query شروع می‌کنیم: کدوم ستون شرط جست‌وجو است، کدوم ترتیب می‌ده و کدوم فقط باید در خروجی باشه؟

The team created three indexes, yet the main query still performs lookups. One put every output column in the key; another targets a low-selectivity column. Start from the query: which columns filter, sort, join, and merely appear in the output?

حالا بریم زیر کاپوتNow look under the hood

یه query از بیرون خیلی ساده‌ست: می‌فرستیش و جواب میاد. ولی وقتی کند می‌شه، دیگه اون نمای بیرونی کافی نیست. برای «ایندکس ۲: ترتیب ستون، INCLUDE و filtered index» یه لایه پایین‌تر می‌ریم و مسیر داده رو دنبال می‌کنیم؛ نه برای حفظ‌کردن اصطلاحات داخلی، برای اینکه وقتی plan یا I/O رفتار عجیبی داشت بفهمیم SQL Server واقعاً داره چه کاری انجام می‌ده.

A query looks simple from the outside: send it, get rows back. Once it becomes slow, that view is not enough. In “Indexes 2: key order, INCLUDE, and filtered indexes” we move one layer down and follow the data path—not to memorise internals, but to explain what SQL Server is actually doing when plans and I/O behave unexpectedly.

ترتیب key مرکب، سمت چپ ایندکس رو تعیین می‌کنه / Composite-key order determines the useful left prefix

در index روی (A,B)، query روی A می‌تونه از ابتدای درخت شروع کند؛ query فقط روی B معمولاً همان مسیر مستقیم رو نداره. پس ترتیب رو از predicateهای equality، range، join و sort بار کاری بساز، نه از قانون عام «بیشترین distinct اول». توزیع داده و queryهای واقعی ممکنه انتخاب رو عوض کنند.

An index on (A,B) can seek from the left for A; a query on B alone generally cannot use the same direct path. Choose order from equality/range predicates, joins, and sorts—not a universal “highest distinctness first” rule. Data distribution and actual queries can change the choice.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

یک بار کاری ساختگی برای آزمون ترتیب / A small workload to test key order
IF SCHEMA_ID(N'Lab42') IS NULL EXEC(N'CREATE SCHEMA Lab42');
DROP TABLE IF EXISTS Lab42.Ticket;
CREATE TABLE Lab42.Ticket
 (TicketId int NOT NULL PRIMARY KEY, TenantId int NOT NULL,
  Status varchar(12) NOT NULL, CreatedAt datetime2 NOT NULL, Summary nvarchar(120) NOT NULL);
CREATE INDEX IX_Ticket_Tenant_Status ON Lab42.Ticket(TenantId, Status);
SELECT TicketId, CreatedAt FROM Lab42.Ticket
WHERE TenantId = 7 AND Status = 'Open' ORDER BY CreatedAt DESC;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

این index شرط‌ها رو پوشش می‌ده ولی ORDER BY یا خروجی رو لزوماً کامل نمی‌کنه. Actual plan و sort/lookup رو ببین. اگه query فقط Status رو فیلتر می‌کنه، ترتیب TenantId اول می‌تونه اون رو برای seek نامناسب کند.

This index supports the predicates but does not necessarily satisfy the ORDER BY or output. Inspect sorts and lookups in the actual plan. A query filtering only Status may not seek efficiently when TenantId leads.

ستون خروجی رو INCLUDE کن، نه لزوماً به key اضافه / INCLUDE output columns instead of bloating the key

nonclustered index می‌تونه ستون‌های nonkey رو در leaf با INCLUDE نگه داره. اگه query predicate و sort رو با key حل کند و ستون‌های خروجی هم در index باشند، ممکنه covering بشه و lookup حذف بشه. INCLUDE اندازهٔ key رو بزرگ نمی‌کنه، اما همچنان storage، cache و هزینهٔ DML داره؛ همهٔ ستون‌های جدول رو کورکورانه اضافه نکن.

A nonclustered index can store nonkey columns at the leaf using INCLUDE. If key columns serve predicates and ordering while included columns supply output, the index may cover the query and avoid a lookup. INCLUDE does not enlarge the key, but still costs storage, cache, and DML work—do not include the whole table blindly.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

نسخهٔ cover شده رو با همان query بسنج / Test a covering variant against the same query
CREATE INDEX IX_Ticket_Tenant_Status_Created
ON Lab42.Ticket(TenantId, Status, CreatedAt DESC)
INCLUDE (Summary);
SELECT TicketId, CreatedAt, Summary
FROM Lab42.Ticket
WHERE TenantId = 7 AND Status = 'Open'
ORDER BY CreatedAt DESC;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

TicketId ممکنه به‌خاطر clustered key به nonclustered index اضافه بشه؛ اگه table heap باشه locator متفاوت هست. همچنین query optimizer تضمین نمی‌کنه index تازه رو انتخاب کند. برنده رو از actual plan، logical reads و insert/update cost مشخص کن.

TicketId may be carried automatically as the clustered key; a heap uses a different locator. The optimizer is not required to choose the new index. Decide from actual plans, logical reads, and insert/update cost.

Filtered index فقط زیرمجموعهٔ روشن رو نگه می‌داره / A filtered index stores a well-defined subset

اگه تعداد زیادی ticket بسته شده‌اند اما داشبورد مرتب فقط ticketهای باز رو می‌خونه، filtered index می‌تونه کوچک‌تر و کم‌هزینه‌تر از index کل جدول باشه. شرط query باید با filter سازگار باشه تا optimizer بتواند ثابت کند index پاسخگوست. پارامتر generic یا شرطی که subset رو تضمین نمی‌کنه ممکنه filtered index رو نامناسب کند.

If many tickets are closed but a dashboard repeatedly reads open ones, a filtered index can be smaller and cheaper than indexing the whole table. The query predicate must imply the filter so the optimizer can prove the index is valid. Generic parameters or predicates that do not guarantee the subset can make it unusable.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

Filtered index برای کارهای باز / Index only the open-ticket subset
CREATE INDEX IX_Ticket_Open_Tenant_Created
ON Lab42.Ticket(TenantId, CreatedAt DESC)
INCLUDE (Summary)
WHERE Status = 'Open';
SELECT TicketId, CreatedAt, Summary
FROM Lab42.Ticket
WHERE TenantId = 7 AND Status = 'Open'
ORDER BY CreatedAt DESC;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

filtered index تضمین امنیت row-level نیست؛ فقط ساختار دسترسی هست. تعداد rowهای subset، query parameterization، plan و نگه‌داری هنگام تغییر Status رو تست کن. اگه ردیف Open به Closed تبدیل بشه، index هم باید تغییر کند.

A filtered index is not row-level security; it is an access structure. Test subset size, parameterization, plan choice, and maintenance when Status changes. Changing Open to Closed also changes index membership.

Key، INCLUDE و filter سه نقش جدا دارن / Key, INCLUDE, and filter have distinct roles

بخش / Partکارکرد / Roleمثال / Example
Keyجست‌وجو، ترتیب یا range / Search, order, rangeTenantId, Status, CreatedAt
INCLUDEستون خروجی در leaf / Output at leafSummary
WHERE filterمحدودکردن ردیف‌های index / Restrict indexed rowsStatus = 'Open'

طرح خوب کمینهٔ لازم برای بار کاری هست. کلیدهای بلند تعداد entry در page رو کم می‌کنن؛ INCLUDE بزرگ page و cache رو مصرف می‌کنه؛ index filtered هم هزینهٔ DML داره. قبل از حذف index موجود، usage و plan رو در بازهٔ عملیاتی کافی بررسی کن.

A good design is the minimum needed for the workload. Wide keys reduce entries per page; large INCLUDE lists consume pages and cache; filtered indexes still incur DML cost. Inspect usage and plans over a representative operational window before removing existing indexes.
