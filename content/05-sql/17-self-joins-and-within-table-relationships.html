Self JOIN و رابطهٔ یک جدول با خودش

Self joins and within-table relationships

در یک گزارش منابع انسانی، نام مدیر باید کنار نام هر کارمند باشه. هر دو نام در جدول Employees هستن؛ جدول دومی وجود نداره که به آن وصل شویم. هر alias یک نقش می‌گیره: یک بار کارمند، یک بار مدیر. رابطه با کلید self-reference خوانده می‌شه.

An HR report needs each employee’s manager beside the employee. Both names are stored in Employees; there is no second table to join. Each alias takes a role—employee and manager—and a self-referencing key connects them.

اول تعداد ردیف‌ها رو حدس بزنPredict the row count first

گزارش سفارش‌ها معمولاً از جایی سخت می‌شه که یک جدول دیگه وارد ماجرا می‌شه. سه سفارش داری، چهار مشتری داری، پنج ردیف سفارش هم داری؛ حالا JOIN می‌زنی و ناگهان خروجی دوازده ردیف می‌شه. توی «Self JOIN و رابطهٔ یک جدول با خودش» قبل از هر query اول حدس می‌زنیم چند ردیف باید برگرده، بعد اجرا می‌کنیم و از روی اختلاف حدسمون با واقعیت می‌فهمیم رابطه‌ها رو درست خوندیم یا نه.

Reports get interesting the moment another table enters the picture. You may have three orders, four customers, and five order lines, then a join suddenly returns twelve rows. In “Self joins and within-table relationships” we predict row counts before executing, then use any mismatch to diagnose our understanding of the relationships.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

جدول یکی است؛ نقش‌ها دو تا هستن / One table, two roles

برای مثال امن و قابل‌تکرار، جدول موقت می‌سازیم. ManagerId به EmployeeId همین جدول اشاره می‌کنه؛ برای مدیرعامل، ManagerId برابر NULL هست. هنگام اتصال، aliasها ضروری‌اند، چون SQL باید بداند EmployeeId یک‌بار نقش کارمند داره و بار دیگر نقش مدیر.

For a safe, repeatable example, create a temporary table. ManagerId references EmployeeId in the same table; the top executive has a NULL ManagerId. Aliases are essential because SQL must distinguish EmployeeId in the employee role from EmployeeId in the manager role.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

دادهٔ تمرینی سلسله‌مراتبی نشست / Session-local hierarchy fixture
DROP TABLE IF EXISTS #Employees;
CREATE TABLE #Employees
(
  EmployeeId int PRIMARY KEY,
  EmployeeName nvarchar(40) NOT NULL,
  ManagerId int NULL
);
INSERT #Employees (EmployeeId,EmployeeName,ManagerId) VALUES
 (1,N'Roya',NULL),(2,N'Iman',1),(3,N'Nilou',1),(4,N'Arman',2);

SELECT e.EmployeeName AS Employee,
       m.EmployeeName AS Manager
FROM #Employees AS e
LEFT JOIN #Employees AS m ON m.EmployeeId=e.ManagerId
ORDER BY e.EmployeeId;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

`e` و `m` دو نسخهٔ فیزیکی از جدول نیستند؛ دو نام برای دو نقش همان منبع در query هستن. LEFT JOIN باید تا مدیرعامل که ManagerId نداره حذف نشه. نام مدیر برای او NULL قراره باشه.

`e` and `m` are not two physical copies; they are aliases for two roles of the same source in the query. LEFT JOIN preserves the executive, whose ManagerId is NULL; the manager name is NULL for that row.

رابطهٔ خودارجاع و مرزهای آن / Self-reference and its boundaries

کلید خارجی self-reference می‌تونه تضمین کند ManagerId به یک کارمند موجود اشاره کند؛ اما این به‌تنهایی جلوی چرخهٔ مدیریتی رو نمی‌گیره. محدودیت‌های سازمانی مثل «هیچ‌کس مدیر خودش نباشه» یا «سلسله‌مراتب چرخه نداشته باشه» قواعد جدا هستن. self join یک سطح رابطه رو می‌خونه؛ برای چند سطح، recursion بحث دیگری هست.

A self-referencing foreign key can ensure ManagerId points to an existing employee, but does not by itself prevent managerial cycles. Rules such as “an employee cannot manage themselves” or “the hierarchy has no cycles” are separate. A self join reads one relationship level; multiple levels require a different recursive approach.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

پیداکردن مدیر نامعتبر با LEFT JOIN / Find invalid managers with LEFT JOIN
SELECT e.EmployeeId, e.EmployeeName, e.ManagerId
FROM #Employees AS e
LEFT JOIN #Employees AS m ON m.EmployeeId=e.ManagerId
WHERE e.ManagerId IS NOT NULL AND m.EmployeeId IS NULL;

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

این query managerId غیرNULL رو پیدا می‌کنه که در جدول match نداره. با primary key و foreign key ممکنه چنین داده‌ای نتواند وارد دادهٔ تمرینی اصلی بشه؛ در واردسازی ناقص یا دادهٔ تاریخی، بررسی تشخیصی هنوز مفید هست.

This finds a non-NULL ManagerId with no matching employee. A primary key and foreign key may prevent such data in a constrained schema, but the diagnostic remains useful for incomplete imports or historical data.

aliasها رو طوری انتخاب کن که نقش خوانده بشه / Choose aliases that communicate roles

در Self JOIN استفاده از aliasهای `a` و `b` query رو اجرا می‌کنه، اما توضیح نمی‌ده کدوم کارمند هست و کدوم مدیر. aliasهای معنادار خطاهای شرط رو زودتر آشکار می‌کنن. ستون‌هایی که اسم یکسان دارن باید qualification داشته باشند و بهتره خروجی هم نام‌های روشن بگیرد.

Aliases `a` and `b` may execute, but do not tell reviewers which is employee and which is manager. Meaningful aliases expose predicate mistakes sooner. Qualify same-named columns and give output columns clear names.

نام‌گذاری نقش‌ها / Name the roles
SELECT employee.EmployeeId,
       employee.EmployeeName AS EmployeeName,
       manager.EmployeeName AS ManagerName
FROM #Employees AS employee
LEFT JOIN #Employees AS manager
  ON manager.EmployeeId=employee.ManagerId;

ON دو نقش رو به‌واسطهٔ ManagerId وصل می‌کنه. اگه اشتباهاً `employee.EmployeeId = manager.EmployeeId` بنویسی، هر ردیف خودش رو match می‌کنه و گزارش ظاهراً پر می‌شه، اما مدیر رو نشان نمی‌ده.

ON connects the roles through ManagerId. If you mistakenly join employee ID to manager ID, each row can match itself; the report may look populated but does not show managers.

یک ستون به کلید اصلی همان جدول برمی‌گرده / A column points back to the same table’s key

دو جعبه نقش‌های منطقی‌اند، نه دو جدول جدا در schema. پیکان از مدیرِ ارجاع‌دهنده به شناسهٔ مدیر می‌ره.

The two boxes are logical roles, not separate schema tables. The reference points from the employee’s manager key to the manager’s identifier.

گزارش نقش‌ها / Role-aware reportSolution
SELECT e.EmployeeId,e.EmployeeName AS Employee,
       m.EmployeeName AS Manager,
       CASE WHEN EXISTS (SELECT 1 FROM #Employees AS r
                         WHERE r.ManagerId=e.EmployeeId)
            THEN 1 ELSE 0 END AS HasDirectReports
FROM #Employees AS e LEFT JOIN #Employees AS m
ON m.EmployeeId=e.ManagerId
ORDER BY e.EmployeeId;
