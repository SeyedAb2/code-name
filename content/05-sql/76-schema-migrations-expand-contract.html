Schema migration بدون شکستن نسخهٔ قبلی

Schema migrations with expand and contract

نسخهٔ تازهٔ برنامه ستون جدید می‌خواد؛ نسخهٔ قبلی هنوز روی چند instance اجراست. اگه ستون رو همین حالا rename کنیم، بخشی از ترافیک می‌شکند. تغییر schema رو مرحله‌بندی می‌کنیم تا هر لحظه برنامه و دیتابیس سازگار بمانند.

The new application version needs a new column while older instances still serve traffic. Renaming immediately breaks part of the fleet. We stage the schema change so each rollout step remains compatible.

پیش‌نیاز: app integration، transactions و استقرارPrerequisites: app integration, transactions, deploymentحدود ۹۵ دقیقه · ۱۸ تمرین / About 95 minutes · 18 exercises

مشکل همیشه خود SQL نیستThe database is not always the problem

ممکنه query خوب باشه و SQL Server هم سالم باشه، ولی برنامه هنوز کند یا ناپایدار باشه. pool، timeout، retry، ORM و migration بین اپ و دیتابیس رفتار واقعی سیستم رو می‌سازن. توی «Schema migration بدون شکستن نسخهٔ قبلی» از هر دو طرف نگاه می‌کنیم: هم SQL Server چی می‌بینه، هم اپ چه چیزی فکر می‌کنه اتفاق افتاده.

The query may be fine and SQL Server healthy while the application is still slow or fragile. Pools, timeouts, retries, ORMs, and migrations shape the real system between app and database. In “Schema migrations with expand and contract” we observe both sides: what SQL Server sees and what the application believes happened.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

schema هم قرارداد مصرف‌کننده‌هاست / Schema is a contract with consumers

برنامهٔ قدیمی ممکنه ستون رو بخواند یا بنویسد؛ job، report و integration هم consumer هستن. Expand/contract یعنی اول ساختار جدیدِ سازگار رو اضافه می‌کنیم، داده رو پر و مصرف‌کننده‌ها رو منتقل می‌کنیم؛ حذف ساختار قدیمی در release جدا و پس از اثبات انجام می‌شه.

Old application instances may read/write the old column; jobs, reports, and integrations are consumers too. Expand/contract first adds compatible structure, backfills it, and moves consumers; removal happens in a later release after evidence.

ستون rename؟ اول ستون دوم رو اضافه کن / Renaming? Add the replacement first

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

مرحلهٔ expand قابل‌برگشت / Reversible expand phase
ALTER TABLE dbo.Customer ADD DisplayName_v2 nvarchar(160) NULL;
GO
-- Backfill in bounded batches; repeat safely until no rows remain.
UPDATE TOP (500) dbo.Customer
SET DisplayName_v2=DisplayName
WHERE DisplayName_v2 IS NULL AND DisplayName IS NOT NULL;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

backfill واقعی باید resumable، قابل‌اندازه‌گیری و با semantics دقیق باشه؛ TOP بدون ترتیب برای انتخاب ردیف‌ها ترتیب قطعی نمی‌ده، اما شرط idempotent اینجا باعث می‌شه batchهای تکراری داده رو نپوشانند. روی جدول بزرگ lock/log و concurrency رو بسنج.

A production backfill must be resumable, measurable, and semantically correct. TOP without ordering does not choose deterministic rows, but this idempotent predicate allows batches to repeat without overwriting completed values. Measure locks, log, and concurrency on large tables.

dual-write کوتاه و consistency قابل‌سنجش / Keep dual-write short and measurable

در migration چندمرحله‌ای ممکنه مدتی هر دو ستون نوشته شوند. این پنجره باید محدود باشه و query consistency اختلاف رو پیدا کند. بعد از انتقال read path و استقرار همهٔ instanceها، dual-write رو حذف کن؛ نگه‌داشتن دائمی دو منبع حقیقت drift می‌سازه.

A staged migration may temporarily write both columns. Bound this window and use a consistency query to detect divergence. After reads move and all instances are deployed, remove dual-write; two permanent sources of truth drift.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

کنترل اختلاف داده / Detect divergent values
SELECT COUNT(*) AS Mismatches
FROM dbo.Customer
WHERE (DisplayName_v2<>DisplayName)
   OR (DisplayName_v2 IS NULL AND DisplayName IS NOT NULL)
   OR (DisplayName_v2 IS NOT NULL AND DisplayName IS NULL);

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

یه مکث کوتاه؛ واقعاً چی فهمیدیم؟Quick pause: what do we actually know now?

قبل از اینکه بریم بخش بعد، سعی کن بدون نگاه‌کردن به بالا در دو جمله بگی این فصل چه مسئله‌ای رو حل می‌کنه و از کدوم خروجی می‌فهمی راه‌حلت درست بوده. اگه فقط اسم دستورها یادت مونده، هنوز یه دور دیگه مثال قبلی رو با دادهٔ متفاوت اجرا کن.

Before moving on, explain in two sentences what problem this chapter solves and which output proves your solution is correct. If you only remember command names, rerun the previous example with different data.

استقرار script رو پیش از production ببین / Review the deployment plan first

با DACPAC/SqlPackage می‌توان استقرار script یا report تغییر تولید کرد و پیش از publish بررسی نمود؛ ابزار، تصمیم compatibility رو خودکار نمی‌کنه. تغییر rename/drop ممکنه data loss یا lock طولانی داشته باشه. migration user رو از runtime user جدا کن و backup/restore واقعی رو بخشی از rollout بدان.

DACPAC/SqlPackage can generate a deployment script/report for review before publishing; the tool does not decide compatibility for you. Rename/drop may cause data loss or long locks. Separate migration identity from runtime identity and include tested backup/restore in rollout planning.
