JOIN و شرط اتصال ON

JOIN and the ON predicate

گزارش سفارش‌ها شناسهٔ مشتری رو داره، اما نام مشتری رو نه. وسوسه می‌شویم همه‌چیز رو از یک جدول بخوانیم؛ اطلاعات در دو جدول هست و query باید رابطه‌شان رو درست بیان کند. این فصل از خودِ رابطه شروع می‌کنه، نه از حفظ‌کردن شکل دستور.

An order report has a customer ID, but not the customer’s name. The information lives in two tables, so the query must express their relationship. We start from that relationship, not from memorizing syntax.

اول تعداد ردیف‌ها رو حدس بزنPredict the row count first

گزارش سفارش‌ها معمولاً از جایی سخت می‌شه که یک جدول دیگه وارد ماجرا می‌شه. سه سفارش داری، چهار مشتری داری، پنج ردیف سفارش هم داری؛ حالا JOIN می‌زنی و ناگهان خروجی دوازده ردیف می‌شه. توی «JOIN و شرط اتصال ON» قبل از هر query اول حدس می‌زنیم چند ردیف باید برگرده، بعد اجرا می‌کنیم و از روی اختلاف حدسمون با واقعیت می‌فهمیم رابطه‌ها رو درست خوندیم یا نه.

Reports get interesting the moment another table enters the picture. You may have three orders, four customers, and five order lines, then a join suddenly returns twelve rows. In “JOIN and the ON predicate” we predict row counts before executing, then use any mismatch to diagnose our understanding of the relationships.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

شناسه داریم، نام نداریم / We have an ID, but no name

سفارش ۱۰۰۱ متعلق به مشتری ۱ است، اما نتیجهٔ گزارش باید نام و شهر مشتری رو هم نشان دهد. پس جدول سفارش‌ها و مشتری‌ها رو با کلید رابطه وصل می‌کنیم. این اتصال «ترکیب تصادفی همهٔ ردیف‌ها» نیست؛ باید شرطی داشته باشه که هر ردیف رو به شریک درستش برساند.

Order 1001 belongs to customer 1, but the report also needs the customer’s name and city. We connect orders and customers through their relationship key. A join is not a random combination of every row; it needs a predicate that finds the intended partner.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

هر جدول، یک نقش روشن / Give each table a clear role
SELECT o.OrderId, o.OrderStatus,
       c.CustomerId, c.FullName, c.City
FROM shop.Orders AS o
INNER JOIN shop.Customers AS c
    ON c.CustomerId = o.CustomerId
ORDER BY o.OrderId;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

`o` و `c` نام کوتاه هر منبع‌اند؛ prefix ستون‌ها رو روشن می‌کنه که هر مقدار از کدوم جدول آمده. شرط `ON` کلید خارجی سمت سفارش رو به کلید مشتری وصل می‌کنه. نام مشتری رو با نام شهر یا مقدار مشابه وصل نکن؛ رابطه باید بر کلید درست باشه.

`o` and `c` are aliases; prefixes make each column’s source explicit. ON connects the order’s foreign key to the customer key. Do not join by a name or a coincidentally similar value—the relationship should use the intended key.

قبل از نوشتن JOIN، رابطه رو روی کاغذ بگو / State the relationship before writing JOIN

برای هر ردیف Orders، حداکثر یک Customer با همان CustomerId داریم؛ پس هر سفارش با مشتری خودش جفت می‌شه. برعکس، یک مشتری می‌تونه چند سفارش داشته باشه. این تفاوت یک‌به‌چند روی تعداد خروجی اثر می‌ذاره و در فصل‌های بعدی دقیق‌تر سراغ cardinality می‌رویم.

Each Orders row has at most one customer with the same CustomerId, so an order pairs with its customer. One customer can have many orders. This one-to-many relationship affects output row counts; later chapters examine cardinality more deeply.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

ON رابطه رو تعریف می‌کنه؛ WHERE بعداً خروجی رو فیلتر می‌کنه / ON defines the match; WHERE filters the result
SELECT o.OrderId, o.OrderStatus, c.FullName
FROM shop.Orders AS o
INNER JOIN shop.Customers AS c
    ON c.CustomerId = o.CustomerId
WHERE o.OrderStatus = 'Paid'
ORDER BY o.OrderId;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

در INNER JOIN، انتقال شرط `o.OrderStatus = 'Paid'` از WHERE به ON معمولاً همان ردیف‌های matchشده رو نگه می‌داره، چون هر دو طرف باید match شوند. اما این عادت رو بی‌فکر به outer join تعمیم نده: در LEFT JOIN محل شرط می‌تونه تعیین کند ردیف سمت چپ حذف بشه یا فقط سمت راست match نشه.

With an INNER JOIN, moving `o.OrderStatus = 'Paid'` between WHERE and ON generally preserves the matching rows because both sides must match. Do not generalize this mechanically to outer joins: predicate placement can decide whether a left row disappears or merely has no right-side match.

یک شرط کوچک، دو معنای متفاوت در LEFT JOIN / One small predicate, two LEFT JOIN meanings

می‌خوایم همهٔ مشتری‌ها رو ببینیم، حتی اگه سفارش پرداخت‌شده نداشته باشند. اگه شرط Paid رو در ON بگذاریم، هر مشتری می‌مونه و فقط سفارش‌های Paid اجازهٔ match دارن. اگه اون رو در WHERE بگذاریم، ردیف‌های NULL سمت سفارش از فیلتر عبور نمی‌کنن؛ نتیجه عملاً مشتری‌های بی‌سفارش رو حذف می‌کنه. فصل ۱۳ این رفتار رو کامل می‌کنه.

We want all customers, including those with no paid order. Put the Paid condition in ON and every customer remains; only paid orders may match. Put it in WHERE and NULL-extended rows fail the predicate, effectively removing customers without a paid order. Chapter 13 develops this behavior fully.

همهٔ مشتری‌ها، با سفارش Paid در صورت وجود / All customers, with a paid order if one exists
SELECT c.CustomerId, c.FullName, o.OrderId, o.OrderStatus
FROM shop.Customers AS c
LEFT JOIN shop.Orders AS o
    ON o.CustomerId = c.CustomerId
   AND o.OrderStatus = 'Paid'
ORDER BY c.CustomerId, o.OrderId;
GO

قاعدهٔ ساده: از نیاز شروع کن. «فقط ردیف‌های دارای match» یعنی inner؛ «همهٔ ردیف‌های این سمت، حتی بی‌match» یعنی outer. بعد تصمیم بگیر شرط متعلق به خود match هست یا باید نتیجه رو حذف کند. فعلاً تعداد ردیف‌ها رو هم بعد از هر JOIN بشمار تا ضرب ناخواسته رو زود ببینی.

Start with the requirement. “Only rows with a match” calls for an inner join; “all rows from this side, even without a match” calls for an outer join. Then decide whether a predicate defines a match or filters the final result. Count rows after each join to catch accidental multiplication early.

رابطه پیش از ستون‌های خروجی / The relationship comes before the projection

پیکان می‌گه کدوم کلیدها شرط اتصال رو می‌سازند؛ به معنی اجرای فیزیکی از چپ به راست نیست. optimizer می‌تونه برنامهٔ اجرا رو خودش انتخاب کند.

قبل از ارسال گزارش / Before shipping the report

از خودت بپرس: این دو جدول واقعاً با کدوم کلید مرتبط‌اند؟ یک ردیف سمت چپ چند match ممکن داره؟ شرط من رابطه رو تعریف می‌کنه یا خروجی رو فیلتر می‌کنه؟ بعد با query کوچک و شمارش ردیف‌ها نتیجه رو بررسی کن.

Ask: Which key actually relates these tables? How many matches can one left-side row have? Does this predicate define a match or filter the result? Then verify with a small query and row counts.

  • INNER JOIN: فقط ردیف‌های matchشده.
