دادهٔ تمرینی Shop و محیط قابل‌بازتولید

The Shop fixture and a reproducible environment

فصل قبل موتور رو بالا آوردیم و اتصال رو با query ثابت کردیم. حالا سؤال عملی‌تری داریم: اگه هر نفر دادهٔ متفاوت داشته باشه، چطور بفهمیم تفاوت نتیجه از query هست یا از داده؟ یک فروشگاه کوچک می‌سازیم که در فصل‌های بعد هم همراه ما می‌مونه.

Last chapter we started the engine and proved the connection with a query. Now a more practical question: if everyone has different data, how can we tell whether a result changed because of the query or the data? We will create a small shop that stays with us through later chapters.

قبل از دستورها، اول زمین بازی رو بشناسBefore the commands, understand the ground you are standing on

فرض کن روز اول کاریته و یکی از بچه‌های تیم پروژه رو باز کرده و می‌گه «این دیتابیس ماست». قبل از اینکه چیزی حفظ کنی، باید بفهمی دقیقاً با چه چیزی طرفی، کجا قراره آزمایش کنی و چطور مطمئن بشی نتیجه‌ای که می‌بینی واقعاً از همون محیطیه که فکر می‌کنی. موضوع «دادهٔ تمرینی Shop و محیط قابل‌بازتولید» رو هم از همین زاویه جلو می‌بریم: کم‌کم، با دست خودمون و با خروجی‌ای که می‌شه بهش استناد کرد.

Imagine it is your first day on the team and someone opens the project and says, “this is our database.” Before memorising commands, you need to know what you are looking at, where the experiment runs, and how to prove the result came from the environment you think it did. We approach “The Shop fixture and a reproducible environment” the same way: hands-on, incremental, and evidence-driven.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

دو نفر یک query می‌زنند؛ چرا جواب‌ها فرق داره؟Two people run one query; why are the answers different?

تیم می‌گه query فروش ماهانه خراب هست. تو اجرا می‌کنی و عدد ۲۳ رو می‌بینی؛ همکارت ۲۷ می‌بینه. معلوم می‌شه هر دو روی جدول‌هایی با دادهٔ دستی خودشان کار می‌کرده‌اند. هنوز نمی‌دانیم query اشتباهه یا نمونه‌داده‌ها یکی نیستند.

The team says the monthly-sales query is broken. You run it and see 23; your teammate sees 27. It turns out each person used tables populated by hand. We still do not know whether the query is wrong or the sample data differs.

به‌جای اینکه از روی یک عدد حدس بزنیم، یک دادهٔ تمرینی می‌سازیم: schema مشخص، کلیدها و رابطه‌های روشن، دادهٔ کم اما حساب‌شده، و چند query که نتیجهٔ مورد انتظارشان رو می‌دانیم. دادهٔ تمرینی یعنی داده و ساختار کنترل‌شده‌ای که آزمایش رو قابل‌تکرار می‌کنه؛ نه دیتابیس production و نه مجموعه‌دادهٔ تصادفی.

Instead of guessing from one number, we create a fixture: a known schema, explicit keys and relationships, a small but deliberate dataset, and queries whose expected results we can calculate. A fixture is controlled structure and data for repeatable tests—not a production database and not random sample data.

قبل از ساخت جدول، مسئلهٔ فروشگاه رو کوچک کنیمKeep the shop problem small before creating tables

در این دوره یک فروشگاه ساده رو مدل می‌کنیم: مشتری، محصول، سفارش و ردیف‌های سفارش. یک سفارش به یک مشتری تعلق داره؛ هر سفارش یک یا چند ردیف داره؛ هر ردیف به یک محصول اشاره می‌کنه. قیمتِ ردیف، قیمت زمان خرید است، نه الزاماً قیمت امروز محصول. این تصمیم کوچک بعداً جلوی عوض‌شدن تاریخچهٔ فروش رو می‌گیره.

Our course shop has customers, products, orders, and order lines. Each order belongs to one customer; an order has one or more lines; each line refers to a product. The line price is the price at purchase time, not necessarily today’s product price. That small decision will keep sales history from changing later.

نام جدول‌ها رو در schema جداگانهٔ shop می‌گذاریم تا با objectهای سیستم یا مثال‌های بعدی قاطی نشوند. در SQL Server، database محل جداسازی داده و schema یک namespace داخل database است؛ فعلاً همین تفاوت رو در ساختار می‌بینیم و جزئیاتش رو بعداً باز می‌کنیم.

We place these tables in a dedicated shop schema so they do not collide with system objects or later examples. In SQL Server, a database separates data and a schema is a namespace inside it. We will explore the distinction later; for now, see how it shapes the fixture.

یک دیتابیس آزمایشگاهی با اسم آشکارA lab database with an unmistakable name

این دستورات رو در connection فصل قبل و با حسابی اجرا کن که اجازهٔ ساخت database داره. نام CodeNamesShopLab عمداً آزمایشگاهی هست. روی database واقعی یا سازمانی اجرا نکن. اگه این نام از قبل وجود داره، اول محتوایش رو بشناس؛ اسکریپت ما قرار نیست چیزی رو بی‌خبر حذف کند.

Run these statements through the previous chapter’s connection using an account allowed to create databases. CodeNamesShopLab is deliberately unmistakably a lab. Do not run this against a real or shared database. If that name already exists, inspect it first; our script will not silently delete anything.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

ساخت امن و یک‌بارهٔ محیط تمرینCreate the lab database once, without destructive reset

USE CodeNamesShopLab;

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

شرط DB_ID ساخت database رو در اجرای دوباره تکرار نمی‌کنه؛ اما این شرط به‌تنهایی ثابت نمی‌کنه دیتابیس موجود همان دادهٔ تمرینی سالم هست. بعد از USE زمینه رو بررسی کن. GO جداکنندهٔ batch در ابزارهایی مثل sqlcmd و SSMS است؛ خود SQL Server اون رو به‌عنوان دستور T-SQL نمی‌گیره.

The DB_ID guard avoids recreating the database on a second run, but it does not prove an existing database is the expected fixture. Verify context after USE. GO is a batch separator understood by clients such as sqlcmd and SSMS; SQL Server does not receive it as T-SQL.

جدول‌ها رو با رابطه و قید بسازیمBuild tables with relationships and constraints

هر جدول یک مسئولیت روشن داره. کلید اصلی هر ردیف رو یکتا می‌کنه؛ کلید خارجی جلوی سفارش برای مشتری ناموجود رو می‌گیره؛ CHECK تعداد و قیمت نامعتبر رو رد می‌کنه. این قیدها تزئین نیستند: اگه دادهٔ بد وارد بشه، گزارش‌های بعدی هم قابل‌اعتماد نمی‌مانند.

Each table has one clear responsibility. A primary key identifies a row; a foreign key prevents an order for a missing customer; CHECK rejects invalid quantities and prices. These constraints are not decoration: bad input would make later reports untrustworthy.

Fixture ساختار ShopShop fixture schema
USE CodeNamesShopLab;
GO

CREATE TABLE shop.Customers
(
    CustomerId   int IDENTITY(1,1) NOT NULL CONSTRAINT PK_Customers PRIMARY KEY,
    FullName     nvarchar(100) NOT NULL,
    Email        varchar(254) NOT NULL CONSTRAINT UQ_Customers_Email UNIQUE,
    City         nvarchar(80) NOT NULL,
    CreatedAt    datetime2(0) NOT NULL CONSTRAINT DF_Customers_CreatedAt DEFAULT SYSUTCDATETIME()
);
GO

CREATE TABLE shop.Products
(
    ProductId    int IDENTITY(1,1) NOT NULL CONSTRAINT PK_Products PRIMARY KEY,
    ProductName  nvarchar(120) NOT NULL,
    UnitPrice    decimal(10,2) NOT NULL CONSTRAINT CK_Products_UnitPrice CHECK (UnitPrice >= 0),
    IsActive     bit NOT NULL CONSTRAINT DF_Products_IsActive DEFAULT (1)
);
GO

CREATE TABLE shop.Orders
(
    OrderId      int IDENTITY(1,1) NOT NULL CONSTRAINT PK_Orders PRIMARY KEY,
    CustomerId   int NOT NULL,
    OrderedAt    datetime2(0) NOT NULL,
    OrderStatus  varchar(12) NOT NULL,
    CONSTRAINT FK_Orders_Customers FOREIGN KEY (CustomerId)
        REFERENCES shop.Customers(CustomerId),
    CONSTRAINT CK_Orders_Status CHECK (OrderStatus IN ('Pending', 'Paid', 'Cancelled'))
);
GO

CREATE TABLE shop.OrderItems
(
    OrderId        int NOT NULL,
    ProductId      int NOT NULL,
    Quantity       smallint NOT NULL CONSTRAINT CK_OrderItems_Quantity CHECK (Quantity > 0),
    UnitPriceAtSale decimal(10,2) NOT NULL
        CONSTRAINT CK_OrderItems_Price CHECK (UnitPriceAtSale >= 0),
    CONSTRAINT PK_OrderItems PRIMARY KEY (OrderId, ProductId),
    CONSTRAINT FK_OrderItems_Orders FOREIGN KEY (OrderId)
        REFERENCES shop.Orders(OrderId),
    CONSTRAINT FK_OrderItems_Products FOREIGN KEY (ProductId)
        REFERENCES shop.Products(ProductId)
);
GO

قیمت نمونهٔ لحظه‌ای در OrderItems رو از قیمت جاری Products جدا کردیم. ممکنه قیمت محصول بعداً عوض بشه، اما سفارش قبلی باید مبلغی رو نگه داره که مشتری واقعاً پرداخت کرده. جمع قیمت‌ها رو ذخیره نکردیم؛ از تعداد و قیمت هر ردیف حسابش می‌کنیم.

We separated the order-line price snapshot from the current product price. A product may become more expensive later, but an old order must retain what the customer actually paid. We did not store a duplicated line total; it can be calculated from quantity and price.

دادهٔ کم، اما با چند حالت مهمA small dataset with meaningful cases

نمونه‌داده باید سؤال بسازد. سه شهر، یک مشتری بدون سفارش، محصول غیرفعال، سفارش لغوشده و دو قیمت فروش متفاوت داریم. زمان‌ها رو صریح و به UTC می‌نویسیم تا نتیجه به ساعت کامپیوتر اجراکننده وابسته نشه. IDها رو با IDENTITY_INSERT کنترل می‌کنیم تا queryهای دوره روی خروجی یکسان بمانند.

A fixture should create useful questions. We include three cities, one customer without orders, an inactive product, a cancelled order, and two different sale prices. Timestamps are explicit UTC values so results do not depend on the learner’s local clock. We control IDs with IDENTITY_INSERT so later exercises see stable results.

ستون‌های IDENTITY شماره رو خودشان تولید می‌کنن؛ در این دادهٔ تمرینی برای ثابت‌ماندن مثال‌ها شمارهٔ کنترل‌شده می‌دهیم و بعد حالت ویژه رو خاموش می‌کنیم. اگه یک insert وسط کار خطا داد، batch بعدی رو ادامه نده؛ تعداد ردیف‌ها رو بررسی کن و علت رو حل کن.

The IDENTITY columns normally generate their own values. We temporarily provide fixed IDs so examples remain stable, then turn the special mode off. If an insert fails partway through, do not blindly continue with later batches; inspect row counts and resolve the cause.

یه مکث کوتاه؛ واقعاً چی فهمیدیم؟Quick pause: what do we actually know now?

قبل از اینکه بریم بخش بعد، سعی کن بدون نگاه‌کردن به بالا در دو جمله بگی این فصل چه مسئله‌ای رو حل می‌کنه و از کدوم خروجی می‌فهمی راه‌حلت درست بوده. اگه فقط اسم دستورها یادت مونده، هنوز یه دور دیگه مثال قبلی رو با دادهٔ متفاوت اجرا کن.

Before moving on, explain in two sentences what problem this chapter solves and which output proves your solution is correct. If you only remember command names, rerun the previous example with different data.

اگه نتیجه فرق داره، از خود داده شاهد بگیرIf results differ, inspect the data itself

دادهٔ تمرینی آماده است؛ قبل از رفتن سراغ queryهای پیچیده، اون رو از SQL Server بخوان. ترتیب ردیف‌ها بدون ORDER BY تضمین نمی‌شه. در این queryها ترتیب رو صریح می‌کنیم و ستون‌هایی رو می‌گیریم که برای بررسی لازم داریم، نه SELECT * مبهم.

The fixture is ready; inspect it through SQL Server before moving to complex queries. Without ORDER BY, row order is not guaranteed. We make ordering explicit and select the columns needed for inspection instead of using ambiguous SELECT *.

مشتری‌ها و سفارش‌هایشانCustomers and their orders
SELECT CustomerId, FullName, City
FROM shop.Customers
ORDER BY CustomerId;

SELECT OrderId, CustomerId, OrderedAt, OrderStatus
FROM shop.Orders
ORDER BY OrderId;
GO

اگه ID مشتری در جدول سفارش نیست، رابطهٔ مورد انتظار به هم خورده؛ اگه مشتری ۴ سفارش نداره، آن یک حالت عمدی هست که در فصل JOIN به کار میاد. دادهٔ آزمایشی خوب فقط مسیر موفق رو نشان نمی‌ده.

If an order references a missing customer, the expected relationship is broken. Customer 4 intentionally has no order; that case will matter in the JOIN chapter. A good fixture includes more than the happy path.

قابل‌بازتولید یعنی چه، و چه چیزی رو تضمین نمی‌کنه؟What reproducible means—and what it does not guarantee

وقتی نسخهٔ اسکریپت، نسخهٔ SQL Server، زمینه database و count ردیف‌ها معلوم است، می‌تونیم تفاوت نتیجه رو محدودتر کنیم. با این حال دادهٔ تمرینی کوچک جای دادهٔ واقعی و تست روی حجم production رو نمی‌گیره؛ نتیجهٔ performance رو از چهار ردیف تعمیم نده.

When the script version, SQL Server version, database context, and row counts are known, we can narrow down why results differ. Still, a tiny fixture is not a substitute for real data or production-scale testing; do not generalise performance from four rows.

آزمایشگاه: دادهٔ تمرینی رو بساز و مدرک تحویل بدهLab: build the fixture and hand off evidence

از database مخصوص تمرین استفاده کن. اسکریپت ساخت رو اجرا کن، query countها رو ذخیره کن، بعد رابطهٔ هر سفارش رو با مشتری و هر ردیف رو با محصول بررسی کن. یک گزارش کوتاه بنویس: نسخهٔ Server، database جاری، تعداد ردیف‌ها و یک مورد عمدی که دادهٔ دادهٔ تمرینی داره ولی دادهٔ واقعی ساده ممکنه نداشته باشه.

Use a dedicated lab database. Run the schema and seed scripts, save the row counts, then verify that every order maps to a customer and every line to a product. Write a short report with server version, current database, row counts, and one deliberate edge case that ordinary sample data might omit.

راهنمای اول: ردیف‌های بدون رابطه رو پیدا کنHint 1: find rows without a relationship
SELECT o.OrderId
FROM shop.Orders AS o
LEFT JOIN shop.Customers AS c ON c.CustomerId = o.CustomerId
WHERE c.CustomerId IS NULL;
GO

در دادهٔ تمرینی سالم این query باید صفر ردیف برگرداند؛ صفر در اینجا نتیجهٔ درسته، نه نبودن آزمایش.

A valid fixture returns zero rows here; zero is the expected result, not a missing test.

راهنمای دوم: فرق قیمت امروز و قیمت زمان خرید رو ببینHint 2: compare current and purchase-time prices
SELECT oi.OrderId, p.ProductName,
       p.UnitPrice AS CurrentPrice,
       oi.UnitPriceAtSale AS SalePrice
FROM shop.OrderItems AS oi
JOIN shop.Products AS p ON p.ProductId = oi.ProductId
ORDER BY oi.OrderId, p.ProductId;
