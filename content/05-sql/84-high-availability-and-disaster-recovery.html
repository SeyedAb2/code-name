HA و DR: availability بدون وعدهٔ جادویی

HA and DR without magical promises

یک node خاموش شده؛ برنامه باید همیشه بالا بمونه. اما «همیشه» یعنی چه؟ خرابی process، storage، rack و region یک خرابی domain نیستند. HA و DR رو از RPO/RTO و آزمایش failover تعریف می‌کنیم، نه از نام feature.

A node went down and the application is expected to stay available. But what does “always” mean? Process, storage, rack, and region failures are different domains. We define HA/DR through RPO/RTO and tested failover, not feature names.

فصل‌های عملیاتی وقتی ارزش دارن که روز خراب‌شدن سیستم به کارت بیان. برای «HA و DR: availability بدون وعدهٔ جادویی» قرار نیست فقط اسم DMV یا گزینهٔ backup رو حفظ کنیم. یه وضعیت قابل‌تکرار می‌سازیم، شواهد جمع می‌کنیم، تغییر رو کنترل‌شده انجام می‌دیم و آخرش ثابت می‌کنیم سیستم واقعاً برگشته؛ نه اینکه فقط یک command بدون خطا تموم شده.

Operations chapters matter when the system is actually broken at 3 a.m. In “HA and DR without magical promises” we do not memorise DMV names or backup options. We create a reproducible state, collect evidence, make a controlled change, and prove recovery rather than trusting a command that merely completed without error.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

HA خرابی نزدیک رو کم می‌کنه؛ DR از فاجعهٔ دامنه‌ای عبور می‌کنه / HA handles local failures; DR addresses site disasters

HA هدف کاهش interruption برای خرابیهای تعریف‌شده است؛ DR بازیابی پس از خرابی بزرگ‌تر مثل از دست‌رفتن site رو پوشش می‌ده. هر دو به dependencyهای خارج SQL Server نیاز دارن: DNS، credential، certificate، application، network و operator. replication خرابی منطقی یا حذف اشتباهی رو هم ممکنه replicate کند؛ backup مستقل هنوز باید.

HA reduces interruption for defined failures; DR covers larger events such as site loss. Both depend on systems beyond SQL Server: DNS, credentials, certificates, application, network, and operators. Replication can also copy logical corruption or accidental deletion, so independent backups remain essential.

AG ثانویه backup نیست. synchronous commit می‌تونه data-loss exposure رو برای سناریوهای مشخص کاهش دهد، اما تأخیر و شرایط failover مهم‌اند؛ asynchronous برای فاصلهٔ جغرافیایی مفید هست ولی commit شدن روی primary الزاماً به معنی رسیده‌بودن به secondary نیست.

An AG secondary is not a backup. Synchronous commit can reduce data-loss exposure under defined conditions, with latency/failover trade-offs. Asynchronous mode suits distance but a primary commit does not guarantee the secondary has received it.

failover خودکار، همهٔ خرابیها رو حل نمی‌کنه / Automatic failover does not handle every failure

Automatic failover شرایط پیکربندی‌شده و quorum/سلامت لازم داره؛ database corruption، dependency application یا قطع client ممکنه رفتار دیگری داشته باشه. پس از failover هم connection باید reconnect بشه، DNS/listener مسیر درست بدهد و job/backup به primary جدید توجه کند. failback رو بدون بررسی data movement اجرا نکن.

Automatic failover requires configured conditions and quorum/health; corruption, application dependencies, or client network loss may behave differently. After failover, clients must reconnect, DNS/listener must route correctly, and jobs/backups must follow the new primary. Do not fail back without checking data movement.

target رو با drill اندازه بگیر / Measure objectives with a drill

RPO رو با replica lag یا آخرین log/backup قابل‌بازیابی بسنج. RTO از detection تا validation و بازگشت consumerهاست. topology رو روی کاغذ سالم اعلام نکن؛ failover/failback، key availability، DNS و application behavior رو در test window مجاز تمرین کن. اگه آزمون نکرده‌ای، ادعا رو محدود بنویس.

Measure RPO from replica lag or the latest recoverable log/backup. RTO runs from detection through validation and restored consumers. Do not declare a diagram healthy: test failover/failback, key availability, DNS, and application behavior in an approved window. If not tested, state the limitation.

معیار موفقیت: backup رو در محیط جدا restore کنی و با یک ردیف یا query شناخته‌شده ثابت کنی داده واقعاً برگشته.

Success criterion: restore the backup into a separate environment and prove recovery with a known row or verification query.

راهنما / HintHint
No zero-downtime promises.
پاسخ و توضیحSolution and reasoning

وجود فایل backup کافی نیست. restore انجام بده، زمان بازیابی رو ثبت کن و چند دادهٔ شناخته‌شده رو با query بررسی کن.

A backup file alone is not proof. Restore it, record recovery time, and verify known data with queries.

replica زیاد، بازیابی اثبات‌شده نیست / More replicas do not prove recovery

HA/DR رو به خرابی domain، RPO/RTO، backup مستقل و test failover وصل کردیم. secondary جای backup رو نمی‌گیره و automatic failover وعدهٔ صفر downtime نیست. حالا سه پروژهٔ پایانی همهٔ این تصمیم‌ها رو در query و شواهد واقعی به کار می‌گیرند.

We tied HA/DR to failure domains, RPO/RTO, independent backups, and tested failover. A secondary is not a backup, and automatic failover is not a zero-downtime promise. The final three projects now apply these decisions through real SQL and evidence.
