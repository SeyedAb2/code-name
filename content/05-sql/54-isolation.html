Isolation levelها: چه چیزی رو از concurrent transaction می‌بینیم؟

Isolation levels: what can a concurrent transaction see?

دو نشست هم‌زمان یک موجودی رو می‌خوانند. هر دو می‌گن «۱۰ عدد هست» و هر دو ۸ می‌فروشند. مشکل از کجاست؟ isolation مشخص می‌کنه transactionهای هم‌زمان کدوم داده رو می‌بینن و چه تغییرهایی رو باید منتظر بمانند؛ انتخاب قوی‌تر هم هزینهٔ concurrency داره.

Two concurrent sessions read inventory. Both see 10 units and each sells 8. Where did the inconsistency enter? Isolation defines what concurrent transactions see and which changes they wait for; stronger guarantees also have concurrency costs.

دو درخواست هم‌زمان؛ همین‌جا داستان سخت می‌شهTwo requests at once: this is where it gets interesting

یه query وقتی تنهاست ممکنه کاملاً بی‌نقص به نظر بیاد. مشکل از جایی شروع می‌شه که دو session هم‌زمان سراغ همون داده می‌رن. برای «Isolation levelها: چه چیزی رو از concurrent transaction می‌بینیم؟» دو پنجره باز می‌کنیم، ترتیب دستورها رو دقیق نگه می‌داریم و می‌بینیم هر session چه چیزی می‌بینه، کجا منتظر می‌مونه و چه موقع کار به blocking یا deadlock می‌کشه.

A query can look perfect when it runs alone. The interesting behaviour starts when two sessions touch the same data. In “Isolation levels: what can a concurrent transaction see?” we use two windows, control statement order carefully, and observe what each session sees, where it waits, and when blocking or deadlock appears.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

Isolation رو از anomaly شروع کن / Start from the anomaly you need to prevent

dirty read یعنی دیدن تغییر commit‌نشده؛ nonrepeatable read یعنی همان ردیف در دو read یک transaction مقدار متفاوت بدهد؛ phantom یعنی query بازه‌ای بار دوم ردیف‌های تازه‌ای ببیند. این‌ها رو با دو query در یک session و تغییر در session دیگر می‌سازیم. هر آزمون باید دقیقاً بگوید کدوم نشست اول اجرا بشه.

A dirty read sees uncommitted work; a nonrepeatable read sees a changed value for the same row on a later read; a phantom sees new rows matching a range on a later query. We reproduce them with two sessions and explicit execution order.

جدول رفتار معمول transaction data در SQL Server رو خلاصه می‌کنه؛ READ COMMITTED می‌تونه با RCSI از row versioning استفاده کند، اما سطح نام isolation عوض نمی‌شه و نمونهٔ لحظه‌ای statement-scoped هست. حالت database رو قبل از نتیجه‌گیری بررسی کن.

This summarizes typical SQL Server data behavior. READ COMMITTED can use row versioning under RCSI while retaining the same isolation name; that snapshot is statement-scoped. Inspect database configuration before concluding.

Dirty read رو با دو نشست بازسازی کن / Reproduce a dirty read with two sessions

در session A transaction رو باز کن و balance رو کم کن، اما commit نکن. در همان فاصله از session B یک SELECT عادی و سپس READ UNCOMMITTED بخوان. خروجی دوم ممکنه تغییر نهایی‌نشده رو ببیند؛ بعد در A rollback کن و B دوباره بخوان.

In session A, begin a transaction and lower the balance without committing. During the pause, session B performs a normal SELECT and then reads under READ UNCOMMITTED. The latter may see the uncommitted value. Roll back in A and read again in B.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

Session A و B رو دقیقاً به همین ترتیب اجرا کن / Run sessions in this order
-- Session A
BEGIN TRAN;
UPDATE Lab53.Account SET Balance=Balance-100 WHERE AccountId=1;
-- Leave transaction open temporarily; then ROLLBACK.
ROLLBACK;
GO
-- Session B during A's open transaction
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT Balance FROM Lab53.Account WHERE AccountId=1;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

دستورهای دو نشست رو هم‌زمان در پنجره‌های جدا اجرا کن، نه پشت سر هم در یک batch. تنها در Lab53 این کار رو انجام بده و مطمئن شو session A rollback شده؛ dirty read می‌تونه نتیجه‌ای بدهد که هرگز commit نشده هست.

Run the sessions in separate windows during the open transaction, not sequentially in one batch. Use Lab53 only and ensure session A rolls back; a dirty read may show a value that never commits.

هر سطح چه چیزی رو نگه می‌داره و چه چیزی رو نه؟ / What does each level protect—and what remains possible?

READ COMMITTED معمولاً shared lock رو پس از statement آزاد می‌کنه؛ پس read دوم در همان transaction می‌تونه مقدار تازه ببیند. REPEATABLE READ lock ردیف‌های خوانده‌شده رو تا پایان نگه می‌داره، اما ردیف جدیدی که شرط range رو برآورده کند هنوز می‌تونه وارد بشه. SERIALIZABLE برای range هم حفاظت می‌گیره و blocking رو افزایش می‌ده.

READ COMMITTED typically releases shared locks after the statement, so a later read in the same transaction can see a new value. REPEATABLE READ retains locks on rows already read, but new rows can still enter the range. SERIALIZABLE protects ranges too, increasing blocking.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

تنظیم isolation نشست رو بخوان / Inspect session isolation
SELECT CASE transaction_isolation_level
  WHEN 0 THEN 'Unspecified' WHEN 1 THEN 'ReadUncommitted'
  WHEN 2 THEN 'ReadCommitted' WHEN 3 THEN 'RepeatableRead'
  WHEN 4 THEN 'Serializable' WHEN 5 THEN 'Snapshot'
END AS IsolationLevel
FROM sys.dm_exec_sessions WHERE session_id = @@SPID;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

این فقط isolation فعلی همان session رو گزارش می‌کنه؛ تضمین نمی‌کنه transaction خاصی anomaly ندیده هست. برای اثبات، نشست دوم رو زمان‌بندی کن و نتیجهٔ قبل/بعد رو ثبت کن.

This reports only the current session level; it does not prove a particular transaction avoided an anomaly. Schedule the second session and record before/after results to prove behavior.

Snapshot از versionهای داده می‌خونه؛ هزینهٔ version store داره / Snapshot reads versions and consumes version-store resources

SNAPSHOT یک نمای سازگار از زمان شروع transaction می‌ده؛ خواننده معمولاً writer رو برای همان rowها منتظر نمی‌ذاره، اما update conflict ممکنه در commit ظاهر بشه. فعال‌کردنش database option هست و row versionها در version store نگهداری می‌شن. برای بار کاری و فضای tempdb بررسی باید.

SNAPSHOT gives a transactionally consistent view from transaction start; readers generally do not block writers on those rows, but update conflicts can surface at commit. It requires a database option and stores row versions. Review workload and version-store capacity.

فقط metadata تنظیم رو ببین؛ بدون تأیید تغییر نده / Inspect the option; do not enable it without review
SELECT name, snapshot_isolation_state_desc,
       is_read_committed_snapshot_on
FROM sys.databases WHERE database_id=DB_ID();
GO

ALTER DATABASE برای فعال‌سازی روی production می‌تونه روی connectionها اثر بگذارد؛ این صفحه عمداً فقط query خواندنی نشان می‌ده. پس از انتخاب، دو نشست، update conflict و فشار version store رو در test environment بسنج.

Enabling an ALTER DATABASE option can affect production connections; this lesson intentionally shows only a read-only query. Test two-session behavior, update conflicts, and version-store pressure in a test environment first.

کمترین isolation کافی رو برای invariant انتخاب کن / Choose the least isolation that protects the invariant

سطح بالاتر همیشه پاسخ بهتر نیست؛ range lockها می‌توانند concurrency رو کم کنند و row-versioning فضای ذخیره و cleanup می‌خواد. گاهی constraint یا یک UPDATE اتمیک با predicate کافیه؛ گاهی transaction باید یک نمونهٔ لحظه‌ای سازگار داشته باشه. invariant رو تعریف و anomaly محتمل رو آزمایش کن.

Higher isolation is not always better: range locks reduce concurrency, and row versioning needs storage and cleanup. A constraint or atomic conditional UPDATE may suffice; another workflow may need a consistent snapshot. Define the invariant and test the relevant anomaly.

موجودی رو اتمیک کم کن / Decrement inventory atomically
UPDATE Lab53.Inventory
SET Quantity = Quantity - @Requested
WHERE ProductId = @ProductId AND Quantity >= @Requested;
SELECT @@ROWCOUNT AS RowsUpdated;
GO

اگه RowsUpdated یک است، شرط موجودی در همان statement برقرار بوده و تغییر انجام شده؛ اگه صفر است، محصول نیست یا موجودی کافی نیست و باید تفکیک لازم رو با query/قرارداد برنامه انجام دهی. statement اتمیک جایگاه درست race رو کوچک می‌کنه، اما تمام روند کار رو خودکار تضمین نمی‌کنه.

If RowsUpdated is one, the inventory predicate held at update time; zero means missing product or insufficient stock and the application must distinguish as required. Atomic DML narrows the race but does not guarantee an entire workflow automatically.

Isolation سطح ضمانت است، نه درجهٔ کیفیت / Isolation is a guarantee choice, not a quality score

READ COMMITTED dirty read رو می‌بندد اما تغییر بین statementها ممکنه؛ REPEATABLE READ ردیف خوانده‌شده رو نگه می‌داره اما phantom داره؛ SERIALIZABLE range رو هم حفاظت می‌کنه؛ SNAPSHOT نمای سازگار می‌ده اما versioning و update conflict داره. anomaly موردنیاز رو تعریف و concurrency cost رو اندازه بگیر.

READ COMMITTED prevents dirty reads but allows inter-statement changes; REPEATABLE READ retains read rows but allows phantoms; SERIALIZABLE protects ranges; SNAPSHOT provides a consistent view but has version-store and update-conflict costs. Define the anomaly and measure concurrency impact.
