INSERT؛ درج تکی، انبوه و از روی SELECT

INSERT: single rows, batches, SELECT, and IDENTITY

یک سفارش تازه باید وارد سیستم بشه. اگه ستون‌ها رو جا‌به‌جا بنویسی دادهٔ نادرست درج می‌شه؛ اگه شناسه رو حدس بزنی برخورد می‌کنی. پس ستون مقصد رو صریح می‌کنیم و نتیجه رو با query بررسی می‌کنیم.

A new order must enter the system. Misaligned columns can insert bad data, and guessed keys can collide. Name target columns explicitly and verify the result.

اینجا اشتباه دیگه فقط خروجی بد نیستHere a mistake changes data, not just output

تا قبل از این، بدترین اتفاق معمولاً یه خروجی اشتباه بود. از اینجا به بعد query می‌تونه دادهٔ واقعی رو عوض کنه. برای «INSERT؛ درج تکی، انبوه و از روی SELECT» عادت می‌کنیم قبل از تغییر، target رو با SELECT ببینیم، تغییر رو داخل transaction امن انجام بدیم، تعداد ردیف‌های اثرگرفته رو چک کنیم و تازه بعد تصمیم بگیریم COMMIT کنیم یا ROLLBACK.

Until now, the worst outcome was usually a wrong result set. From here on, a statement can change real data. With “INSERT: single rows, batches, SELECT, and IDENTITY” we preview the target rows, make the change inside a safe transaction, inspect affected rows, and only then decide whether to COMMIT or ROLLBACK.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

اول قرارداد ردیف رو روشن کن / First make the row contract explicit

نمونه‌های تغییر‌دهنده روی جدول موقت‌اند تا به دادهٔ اصلی وابسته نباشیم. فهرست ستون‌ها رو صریح می‌نویسیم؛ ترتیب مقدارها باید دقیقاً با همان فهرست هماهنگ باشه. به ترتیب فیزیکی ستون‌های جدول تکیه نکن.

Mutations use a temporary table so the experiment is isolated. Explicitly list target columns and align values with that list; do not depend on physical table order.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

درج یک ردیف / Insert one row
DROP TABLE IF EXISTS #NewOrders;
CREATE TABLE #NewOrders
(
  OrderId int IDENTITY(1,1) PRIMARY KEY,
  CustomerId int NOT NULL,
  OrderStatus nvarchar(20) NOT NULL,
  OrderedAt datetime2(0) NOT NULL
);

INSERT INTO #NewOrders (CustomerId, OrderStatus, OrderedAt)
VALUES (42, N'Pending', '2026-04-03T09:30:00');

SELECT OrderId, CustomerId, OrderStatus, OrderedAt
FROM #NewOrders;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

OrderId رو ندادیم؛ SQL Server اون رو تولید کرد. IDENTITY تضمین نمی‌کنه شماره‌ها بدون فاصله یا معنای زمانی داشته باشند. برای زمان، ستون زمان نگه دار؛ شناسه رو با زمان اشتباه نگیر.

OrderId was omitted, so SQL Server generated it. IDENTITY does not promise gap-free or chronological numbering. Store a timestamp when time matters.

چند ردیف معلوم رو یک‌جا درج کن / Insert a small known batch

چند tuple در VALUES برای مجموعهٔ کوچک خواناست. همهٔ ردیف‌ها باید نوع و قیدهای مقصد رو رعایت کنند. برای فایل‌های بزرگ، ابزار بارگذاری انبوه مناسب‌تر است؛ حجم زیاد VALUES جایگزین طراحی import نیست.

Multiple VALUES tuples are clear for a small set. Every row must satisfy target types and constraints. Large file imports need a bulk-loading path; a giant VALUES list is not an import strategy.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

درج چند ردیف / Insert multiple rows
INSERT INTO #NewOrders (CustomerId, OrderStatus, OrderedAt)
VALUES
  (7, N'Paid',    '2026-04-03T10:00:00'),
  (8, N'Pending', '2026-04-03T10:05:00'),
  (7, N'Paid',    '2026-04-03T10:10:00');

SELECT * FROM #NewOrders ORDER BY OrderId;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

برای یک شناسه، SCOPE_IDENTITY مقدار همان scope رو می‌ده؛ @@IDENTITY ممکنه مقدار ساخته‌شده در trigger رو هم ببیند. برای درج چندردیفی، OUTPUT INSERTED رو به table variable بفرست. برای ارتباط مطمئن ورودی و شناسهٔ تولیدشده، کلید correlation نیز ثبت کن؛ ترتیب خروجی به‌تنهایی نگاشت رو ثابت نمی‌کنه.

SCOPE_IDENTITY returns an identity generated in the same scope; @@IDENTITY can see values generated by triggers. For multi-row inserts, capture OUTPUT INSERTED into a table variable. Use a correlation key when mapping inputs to generated keys; output order alone is not a mapping contract.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

گرفتن کلیدهای تولیدشده / Capture generated keys
DECLARE @Inserted TABLE (OrderId int, CustomerId int);
INSERT INTO #NewOrders (CustomerId, OrderStatus, OrderedAt)
OUTPUT INSERTED.OrderId, INSERTED.CustomerId
  INTO @Inserted (OrderId, CustomerId)
VALUES (15, N'Pending', '2026-04-04T12:00:00'),
       (16, N'Paid',    '2026-04-04T12:05:00');
SELECT * FROM @Inserted;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

وقتی منبع query است، از INSERT SELECT استفاده کن / Use INSERT SELECT for query results

انتقال یا آرشیو معمولاً از مجموعه‌ای از ردیف‌ها میاد. query منبع رو اول جدا اجرا کن؛ بعد ستون‌های مقصد و نوع‌های سازگار رو بررسی کن. اگه مقصد identity داره، معمولاً آن ستون رو حذف می‌کنیم تا مقصد شناسه بسازد.

Transfers and archives often use query results. Run the source query alone first, then check destination columns and compatible types. Usually omit a destination identity column so it generates new keys.

انتقال کنترل‌شده به مقصد موقت / Copy a filtered set
DROP TABLE IF EXISTS #PaidOrders;
CREATE TABLE #PaidOrders
(
  OrderId int NOT NULL,
  CustomerId int NOT NULL,
  OrderedAt datetime2(0) NOT NULL
);
INSERT INTO #PaidOrders (OrderId, CustomerId, OrderedAt)
SELECT OrderId, CustomerId, OrderedAt
FROM shop.Orders
WHERE OrderStatus = N'Paid';
SELECT COUNT(*) AS CopiedRows FROM #PaidOrders;
GO

اگه الزاماً باید مقدار identity اصلی حفظ بشه، IDENTITY_INSERT رو کوتاه و آگاهانه روشن کن، ستون identity رو صریح در INSERT بیاور و بعد خاموشش کن. در هر session فقط یک جدول می‌تونه این حالت رو داشته باشه. این کار رو روی مقصد آزمایشی بررسی کن و مسیر خطا رو هم در نظر بگیر.

If preserving original identity values is required, enable IDENTITY_INSERT deliberately and briefly, name the identity column in INSERT, and turn it off. Only one table per session can have it enabled. Test against a disposable destination and account for error paths.

DEFAULT با NULL فرق داره / DEFAULT differs from NULL

حذف ستون از INSERT یعنی default جدول اعمال می‌شه؛ فرستادن NULL یعنی مقدار NULL بنویس، اگه مجاز باشه. این دو رو از تعریف ستون بخوان. DEFAULT صریح هم می‌توان نوشت.

Omitting a column applies its default; explicitly supplying NULL stores NULL if allowed. Read the column definition. DEFAULT can also be specified explicitly.

جدول آزمایشی برای default / Isolated default test
DROP TABLE IF EXISTS #Defaults;
CREATE TABLE #Defaults
(
  Id int IDENTITY PRIMARY KEY,
  Label nvarchar(30) NOT NULL,
  CreatedAt datetime2(0) NOT NULL DEFAULT SYSUTCDATETIME(),
  Note nvarchar(100) NULL
);
INSERT #Defaults (Label) VALUES (N'omitted note');
INSERT #Defaults (Label, Note) VALUES (N'explicit null', NULL);
INSERT #Defaults (Label, CreatedAt, Note)
VALUES (N'explicit default', DEFAULT, N'provided');
SELECT * FROM #Defaults;
GO

توی این مثال حذف CreatedAt و نوشتن DEFAULT از default استفاده می‌کنه. Note حذف‌شده NULL می‌شه چون nullable هست و default نداره. «حذف‌شده»، «NULL» و «پیش‌فرض» رو در قرارداد داده یکی فرض نکن.

Omitting CreatedAt and specifying DEFAULT both use its default. Omitted Note becomes NULL because it is nullable and has no default. Do not conflate absent, NULL, and default in the data contract.

درج رو با شاهد بررسی کن / Verify the insert with evidence

خطا نداشتن statement یک شاهد است، اما برای کار عملی تعداد ردیف، کلید یا نتیجهٔ OUTPUT رو نیز ببین. اگه constraint درج رو رد کرد، اون رو خاموش نکن؛ کلید تکراری، والد ناموجود، طول رشته و نوع ورودی رو بررسی کن. قیدها بخشی از صحت داده‌اند.

A statement without error is evidence, but also inspect inserted row counts, keys, or OUTPUT. If a constraint rejects the insert, do not disable it; inspect duplicate keys, missing parents, string length, and input types. Constraints protect data.

درج رو از مقصد تا منبع بازبینی کن / Review from target back to source

کدوم ستون‌ها اجباری، defaultدار یا identity هستن؟ نوع‌ها و ترتیب ورودی درست‌اند؟ در انتقال، دقیقاً کدوم ردیف‌ها انتخاب می‌شن؟ چه تعداد یا چه شناسه‌هایی واقعاً درج شدند؟ انتقال بزرگ علاوه بر INSERT به تکرارپذیری، خطاگیری و تراکنش هم نیاز داره.

Which columns are required, defaulted, or identity? Do types and mappings align? Which source rows qualify? What keys or counts prove the insert? Large transfers also need retry, error, and transaction design.

  • شناسه تولیدی حدس زده نشده / Generated IDs are not guessed.
  • منبع انتقال بازبینی شده / Transfer source was previewed.
  • DEFAULT و NULL معنای جدا دارن / DEFAULT and NULL remain distinct.
