نوع داده؛ انتخابی که روی معنا اثر می‌ذاره

Data types: choices that change meaning

نام «تهران» بعد از ورود به جدول به علامت سؤال تبدیل شده؛ قیمت هم گاهی یک سنت اختلاف داره. هر دو باگ شاید از query نباشند: ممکنه نوع ستون از ابتدا با داده سازگار نبوده باشه. قبل از طراحی جدول، معنای مقدار و دقت لازم رو مشخص کنیم.

A Persian city name turns into question marks, and a price is off by a cent. These may not be query bugs; the column type may not fit the data. Start with meaning and required precision before choosing storage.

تصمیمی که امروز کوچیکه، فردا توی هر query دیده می‌شهA small schema decision today appears in every query tomorrow

وقتی جدول فقط ده ردیف داره، تقریباً هر طراحی‌ای «کار می‌کنه». دردش چند ماه بعد معلوم می‌شه؛ وقتی داده تکراری شده، constraint نداری یا یه نوع داده اشتباه همهٔ queryها رو پیچیده کرده. توی «نوع داده؛ انتخابی که روی معنا اثر می‌ذاره» قرار نیست فقط DDL بنویسیم؛ می‌خوایم بفهمیم هر تصمیم چه قانونی رو وارد خود دیتابیس می‌کنه و هزینهٔ اون تصمیم بعداً کجاست.

With ten rows, almost any design seems to work. The cost appears months later when data is duplicated, constraints are missing, or a poor data type infects every query. In “Data types: choices that change meaning” we are not merely writing DDL; we are deciding which rules the database itself enforces and what those choices cost later.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

متن فارسی به Unicode نیاز داره / Persian text needs Unicode-aware storage

در SQL Server، nchar و nvarchar برای متن Unicode هستن؛ برای متن فارسی معمولاً nvarchar انتخاب سرراستی هست. literal فارسی رو هم با پیشوند N بنویس تا SQL Server اون رو Unicode تفسیر کند. varchar با collation مناسب UTF-8 هم می‌تونه Unicode داشته باشه، اما انتخابش وابسته به collation و نیاز سازگاری است؛ «varchar همیشه متن فارسی رو خراب می‌کنه» قانون دقیقی نیست.

In SQL Server, nchar and nvarchar are Unicode types; nvarchar is a straightforward choice for Persian. Prefix Unicode string literals with N. varchar can also store Unicode under a UTF-8 collation, so “varchar always breaks Persian” is not universally true—the collation and compatibility requirements matter.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

مقایسهٔ literal و نوع ستون / Compare Unicode literals and column types
DECLARE @City nvarchar(30) = N'تهران';
SELECT @City AS UnicodeCity, DATALENGTH(@City) AS StoredBytes;
GO
SELECT name, collation_name
FROM sys.databases
WHERE name = DB_NAME();
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

اگه متن فارسی از قبل با تبدیل خراب ذخیره شده باشه، عوض‌کردن نوع ستون به‌تنهایی حروف ازدست‌رفته رو بازسازی نمی‌کنه. اول منبع ورودی و collation رو بررسی کن؛ بعد با دادهٔ تازه و آزمایشی نتیجه رو ثابت کن.

Changing a column type cannot reconstruct characters already lost during conversion. Inspect the input path and collation, then prove behavior with fresh test data.

برای پول decimal؛ برای اندازه‌گیری تقریبی float / Use decimal for exact amounts, float for approximation

decimal(p,s) تعداد کل رقم‌ها رو با precision و رقم‌های اعشار رو با scale تعیین می‌کنه؛ مثلاً decimal(9,2) تا ۷ رقم پیش از ممیز و ۲ رقم بعد از آن داره. برای مبلغ قراردادی این رفتار قابل‌پیش‌بینی‌تر از float هست. float عدد تقریبی شناور هست و بعضی مقدارهای ده‌دهی دقیقاً نمایش‌پذیر نیستند؛ برای اندازه‌گیری‌هایی که تقریب پذیرفتنی هست کاربرد داره.

decimal(p,s) sets total precision and fractional scale; decimal(9,2) allows seven digits before and two after the point. That is predictable for contractual amounts. float is approximate: some decimal fractions have no exact binary representation, making it useful for measurements where approximation is acceptable.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

خطای جمع float رو ببین / Observe floating-point approximation
SELECT CAST(0.1 AS float) + CAST(0.2 AS float) AS ApproximateSum,
       CAST(0.1 AS decimal(3,1)) + CAST(0.2 AS decimal(3,1)) AS DecimalSum;
GO
SELECT CAST(123.456 AS decimal(6,2)) AS RoundedValue;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

تبدیل به scale کمتر می‌تونه گرد کند؛ مقدار بزرگ‌تر از ظرفیت هم می‌تونه سرریز بدهد. قبل از انتخاب decimal، بیشترین مقدار واقعی و دقت موردنیاز رو حساب کن. numeric و decimal در SQL Server هم‌معنا هستن.

Converting to a smaller scale can round; exceeding precision can overflow. Estimate real maximum values and required fractional digits before choosing decimal. numeric and decimal are synonyms in SQL Server.

طول نوع رو با طول داده اشتباه نگیر / Do not confuse declared length with actual data

nchar و char طول ثابت دارن و برای مقدار کوتاه‌تر padding می‌کنن؛ nvarchar و varchar طول متغیرند. ظرفیت‌های متنی هم در همهٔ انواع به یک واحد اندازه‌گیری نمی‌شن؛ byteها، جفت‌بایت‌ها و collation اهمیت دارن. طول رو براساس دادهٔ واقعی و قرارداد برنامه تعیین کن، نه با حدس بزرگ و بی‌پایان.

nchar and char are fixed-width and pad shorter values; nvarchar and varchar are variable-width. String capacity is not measured identically across types—bytes, byte-pairs, and collation matter. Choose lengths from the data contract, not an arbitrary unlimited guess.

طول منطقی رو با DATALENGTH بسنج / Inspect storage length
SELECT LEN(N'علی ') AS CharacterCount,
       DATALENGTH(N'علی ') AS ByteCount,
       LEN(CAST(N'علی ' AS nchar(8))) AS PaddedCharacterCount,
       DATALENGTH(CAST(N'علی ' AS nchar(8))) AS FixedByteCount;
GO

LEN فاصلهٔ انتهایی رو در شمارش نادیده می‌گیره؛ DATALENGTH بایت ذخیره‌شده رو نشان می‌ده. این دو سؤال متفاوتی جواب می‌دهند. برای قیاس ظرفیت رشتهٔ Unicode، فقط عدد LEN رو معیار نهایی نگذار.

LEN ignores trailing spaces, while DATALENGTH reports stored bytes. They answer different questions. Do not use LEN alone as the final measure of Unicode storage capacity.

زمان محلی، زمان UTC و offset رو از هم جدا کن / Distinguish local time, UTC, and offset

date فقط تاریخ رو نگه می‌داره؛ time فقط ساعت را؛ datetime2 تاریخ‌وساعت با دقت قابل‌تنظیم ذخیره می‌کنه اما timezone نداره. datetimeoffset مقدار offset رو هم همراه می‌آورد، ولی به‌تنهایی اسم منطقهٔ زمانی و قواعد تاریخی DST رو نگه نمی‌داره. اگه باید منطقهٔ زمانی اصلی رو بدانیم، اون رو جداگانه ثبت کن.

date stores a date; time stores a time; datetime2 stores a timestamp with configurable fractional precision but no timezone. datetimeoffset carries an offset, not a named time zone or its historical daylight-saving rules. Store the zone identifier separately if it matters.

یک لحظه با offset متفاوت / The same instant with different offsets
DECLARE @Local datetimeoffset(0) = '2026-04-03T12:00:00+03:30';
SELECT @Local AS OriginalOffset,
       SWITCHOFFSET(@Local, '+00:00') AS UtcView,
       CAST(@Local AS datetime2(0)) AS OffsetDiscarded;
GO

در ستون آخر offset حذف می‌شه؛ همان ساعت ۱۲ رو نباید بدون منطقه و offset، زمان جهانی فرض کرد. برای رخدادهای لحظه‌ای معمولاً UTC و سیاست روشن برای نمایش محلی کمک می‌کنه، اما انتخاب نهایی به قرارداد سامانه وابسته هست.

The last conversion discards the offset; 12:00 without zone context is not necessarily UTC. UTC storage plus an explicit display policy often helps for instants, but the application contract decides.

تبدیل ضمنی رو پیدا کن / Find implicit conversions

وقتی دو طرف مقایسه نوع متفاوت دارن، SQL Server ممکنه یکی رو ضمنی تبدیل کند. تبدیل روی ستون می‌تونه هم خطا بسازد و هم استفاده از index رو دشوارتر کند. نوع پارامتر رو با نوع ستون هماهنگ کن و execution plan رو در فصل tuning بررسی می‌کنیم.

When compared expressions have different types, SQL Server may implicitly convert one side. Conversion on a column can cause errors and may make index use harder. Match parameter types to column types; execution-plan effects are studied later.

نوع expressionها رو ببین / Inspect expression types
SELECT SQL_VARIANT_PROPERTY(CAST(12.34 AS decimal(6,2)), 'Precision') AS P,
       SQL_VARIANT_PROPERTY(CAST(12.34 AS decimal(6,2)), 'Scale') AS S;
GO
SELECT TRY_CONVERT(int, N'42') AS GoodValue,
       TRY_CONVERT(int, N'forty-two') AS FailedConversion;
GO

TRY_CONVERT برای ورودی نامعتبر NULL می‌ده؛ این کار خطا رو بی‌صدا می‌کنه، پس باید مقدارهای ناموفق رو جدا گزارش کنی. اگه NULL رو مثل موفقیت معمولی بپذیری، دادهٔ مسئله‌دار پنهان می‌شه.

TRY_CONVERT returns NULL for invalid input; this suppresses a conversion error, so failed values must be reported separately. Treating NULL as ordinary success can hide bad data.

این مقدار چه معنایی داره؟ بیشینه و کمینه‌اش چیه؟ تقریب قابل‌قبول هست یا نه؟ زمان متعلق به کدوم منطقه است؟ متن چه زبان‌هایی داره؟ بعد از پاسخ، نوع و مرز رو انتخاب کن و ورودی مرزی رو واقعاً اجرا کن. نوع داده یک ظرف خنثی نیست؛ بخشی از قانون صحت داده هست.

What does the value mean? What are its bounds? Is approximation acceptable? Which time zone applies? Which languages may appear? Choose the type after answering, then execute boundary tests. A data type is part of the integrity contract, not a neutral container.
