Connection pool، timeout و retry

Connection pools, timeouts, and retries

در بار زیاد، درخواست‌ها timeout می‌شن؛ تیم pool رو بزرگ و retry رو فوری می‌کنه. حالا connection بیشتر و ترافیک بیشتر هست. این فصل به‌جای «retry کن»، علت انتظار و مرز هر timeout رو اندازه می‌گیره.

Under load, requests time out; the team enlarges the pool and retries immediately. Now there are more connections and more traffic. Instead of “just retry,” we measure where waiting happens and what each timeout means.

مشکل همیشه خود SQL نیستThe database is not always the problem

ممکنه query خوب باشه و SQL Server هم سالم باشه، ولی برنامه هنوز کند یا ناپایدار باشه. pool، timeout، retry، ORM و migration بین اپ و دیتابیس رفتار واقعی سیستم رو می‌سازن. توی «Connection pool، timeout و retry» از هر دو طرف نگاه می‌کنیم: هم SQL Server چی می‌بینه، هم اپ چه چیزی فکر می‌کنه اتفاق افتاده.

The query may be fine and SQL Server healthy while the application is still slow or fragile. Pools, timeouts, retries, ORMs, and migrations shape the real system between app and database. In “Connection pools, timeouts, and retries” we observe both sides: what SQL Server sees and what the application believes happened.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

pool هزینهٔ ساخت connection رو amortize می‌کنه / A pool amortizes connection setup

pooling connectionهای فیزیکی رو برای استفادهٔ دوباره نگه می‌داره؛ برنامه معمولاً connection منطقی رو باز/بسته می‌کنه. connection رو dispose نکردن، transaction باز، یا session state آلوده می‌تونه pool رو خالی یا رفتار درخواست بعدی رو آلوده کند. pool size بزرگ‌تر الزاماً نرخ پردازش رو زیاد نمی‌کنه؛ SQL Server هم منابع محدود داره.

Pooling reuses physical connections while the application opens/closes logical connections. Not disposing, open transactions, or leaked session state can exhaust or contaminate the pool. A larger pool does not guarantee throughput; SQL Server resources are finite too.

timeoutها مرزهای متفاوت دارن / Timeouts cover different phases

connection timeout زمان برقراری اتصال رو محدود می‌کنه؛ command timeout زمان انتظار برای اجرای دستور رو. request timeout برنامه هم ممکنه قبل یا بعد از این‌ها رخ دهد. timeout یعنی caller دیگر منتظر نمی‌مونه؛ ثابت نمی‌کنه server کار رو rollback کرده یا commit نشده هست.

Connection timeout bounds connection establishment; command timeout bounds waiting for a command. An application request timeout is another boundary. A timeout means the caller stopped waiting, not that the server rolled back or did not commit.

retry می‌تونه outage رو بزرگ‌تر کند / Retries can amplify an outage

هر retry ظرفیت بیشتری مصرف می‌کنه؛ تعداد محدود، exponential backoff و jitter بگذار. فقط خطاهای transient رو retry کن. deadlock victim گاهی قابل retry است؛ invalid input، permission یا duplicate constraint نه. operation نوشتنی باید idempotent باشه یا نتیجهٔ قبلی قابل query باشه.

Every retry consumes more capacity; cap attempts and add exponential backoff with jitter. Retry only transient errors. Deadlock victims may be retryable; invalid input, permissions, and duplicate constraints are not. Writes need idempotency or a way to query the prior outcome.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

الگوی مفهومی retry / Retry design sketch
for attempt in 1..maxAttempts:
  try: execute(operationId, request)
  catch error:
    if not isTransient(error) or attempt == maxAttempts: raise
    wait(exponentialBackoff(attempt) + randomJitter())

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

این شبه‌کد است، نه API یک زبان خاص. تراکنش رو قبل از retry پاک/rollback کن و در سمت دیتابیس کلید operation یکتا enforce کن.

This is pseudocode, not a language API. Clean up/rollback before retrying and enforce operation-key uniqueness in the database.

pool wait رو از query کند تشخیص بده / Distinguish pool waits from slow queries

تأخیر endpoint، تعداد connection فعال، timeout، retry، pool wait و DMVهای SQL رو در یک خط زمانی کنار هم بگذار. اگه فقط تعداد connection رو بالا ببری، blocking و memory pressure ممکنه بدتر بشه. connection رو هنگام کار خارجی مثل HTTP داخل transaction نگه ندار.

Correlate endpoint latency, active connections, timeouts, retries, pool waits, and SQL DMVs on a timeline. Raising connection count alone may worsen blocking and memory pressure. Do not hold a database transaction while doing external work such as HTTP.

retry ابزار resilience است، نه درمان کندی / Retry is resilience, not a performance fix

pool رو lifecycle connection، timeout رو phase، و retry رو idempotency/backoff تعریف می‌کنه. برای تشخیص، client metrics رو با server waits کنار هم گذاشتیم. فصل بعد ORM و N+1 رو بررسی می‌کنه؛ جایی که تعداد queryها گاهی پشت abstraction پنهان هست.

Connection lifecycle defines pool behavior; phase defines timeout; idempotency/backoff define retry safety. We correlated client metrics with server waits. Next we examine ORMs and N+1, where query count can hide behind an abstraction.
