Restore، validation و RPO/RTO

Restore validation and RPO/RTO

backup شبانه موفق بوده، اما آخرین نسخه ۲۳ ساعت عقب هست و restore شش ساعت طول کشیده. آیا این با قول سرویس جور است؟ RPO و RTO رو از نیاز کسب‌وکار می‌گیریم، بعد با drill واقعی اندازه می‌گیریم.

The nightly backup succeeded, but the latest recoverable point is 23 hours old and restore took six hours. Does that meet the service promise? We define RPO/RTO from business needs, then measure them in a real drill.

پیش‌نیاز: full/differential/log backupPrerequisites: full/differential/log backupsحدود ۹۵ دقیقه · ۱۸ تمرین / About 95 minutes · 18 exercises

فرض کن این اتفاق ساعت سه صبح افتادهImagine this happened at 3 a.m.

فصل‌های عملیاتی وقتی ارزش دارن که روز خراب‌شدن سیستم به کارت بیان. برای «Restore، validation و RPO/RTO» قرار نیست فقط اسم DMV یا گزینهٔ backup رو حفظ کنیم. یه وضعیت قابل‌تکرار می‌سازیم، شواهد جمع می‌کنیم، تغییر رو کنترل‌شده انجام می‌دیم و آخرش ثابت می‌کنیم سیستم واقعاً برگشته؛ نه اینکه فقط یک command بدون خطا تموم شده.

Operations chapters matter when the system is actually broken at 3 a.m. In “Restore validation and RPO/RTO” we do not memorise DMV names or backup options. We create a reproducible state, collect evidence, make a controlled change, and prove recovery rather than trusting a command that merely completed without error.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

دو هدف رو با واژهٔ دقیق تعریف کن / Define two distinct objectives

RPO بیشترین دادهٔ قابل‌قبول برای از دست‌رفتن است؛ مثلاً «حداکثر ۱۵ دقیقه تغییر». RTO بیشترین زمان مجاز تا بازگشت سرویس است؛ detection، تصمیم، restore، validation و بازگشایی مصرف‌کننده‌ها رو هم شامل می‌شه. فاصلهٔ backup تنها یکی از عوامل RPO است؛ زمان restore تنها یکی از عوامل RTO.

RPO is the maximum acceptable data loss, such as 15 minutes of changes. RTO is the maximum time to restore service, including detection, decision, restore, validation, and reopening consumers. Backup interval is only one RPO factor; restore duration is only one RTO factor.

restore chain رو کامل و به‌ترتیب اجرا کن / Restore the complete chain in order

برای point-in-time بازیابی، full backup، differential لازم (در صورت استفاده) و log backupهای پیوسته رو آماده کن. log chain شکسته یا log backup جاافتاده ممکنه زمان هدف رو غیرقابل‌دسترسی کند. tail-log backup فقط وقتی source و وضعیت اجازه می‌ده؛ اون رو تضمین همیشگی فرض نکن.

Point-in-time recovery needs the full, optional differential, and continuous log backups. A broken chain or missing log backup can make a target time unreachable. Tail-log backup is conditional on source availability/state, not a universal guarantee.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

restore تا زمان هدف در دیتابیس جدا / Restore to a target time in a separate database
RESTORE DATABASE ShopRestoreLab
FROM DISK='D:\SqlBackups\Shop_full.bak'
WITH NORECOVERY, MOVE 'Shop' TO 'D:\SqlRestore\ShopRestoreLab.mdf',
     MOVE 'Shop_log' TO 'D:\SqlRestore\ShopRestoreLab_log.ldf';
-- Restore required differential/log backups in order.
-- Apply STOPAT to the final applicable log restore, then RECOVERY.

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

logical file name و گزینه‌های restore رو از FILELISTONLY و backup chain بگیر؛ متن بالا الگوی مفهومی است، نه script کامل برای هر محیط. منبع اصلی رو overwrite نکن.

Obtain logical names and restore options from FILELISTONLY and the actual chain. This is a conceptual pattern, not a universal full script. Never overwrite the source.

قابل restore بودن رو چند لایه ثابت کن / Prove restorability at multiple levels

VERIFYONLY می‌تونه بخشی از بررسی باشه، نه گواهی بازیابی. restore کامل رو اجرا، DBCC CHECKDB رو روی copy بسنج، queryهای شناخته‌شده و invariantهای کسب‌وکار رو بررسی کن، سپس login/job/permission وابسته رو بررسی کن. زمان هر مرحله و فاصلهٔ نقطهٔ بازیابی رو ثبت کن.

VERIFYONLY can contribute evidence but is not proof of recovery. Perform a full restore, run DBCC CHECKDB on the copy, verify known queries/business invariants, then inspect dependent logins/jobs/permissions. Record each phase duration and recovery-point age.

restore drill باید محیط جدا داشته باشه / A restore drill needs isolation

copy رو با نام جدا در شبکهٔ محدود بالا بیاور؛ worker و job آن نباید به سرویس live وصل شوند. رکورد شناخته‌شدهٔ تست رو بخوان و منبع backup رو دست‌نخورده نگه دار. اگه drill شکست خورد، علت، مسئول و موعد repair مشخص بشه.

Restore under a separate name in an isolated network; jobs/workers must not connect to live services. Read a known test record and keep source backups untouched. If a drill fails, assign a cause, owner, and repair date.

تمرین: زمان هدف و بازیابی رو با مدرک بسنج / Exercises: measure recovery against a target

تمام restoreها به database آزمایشی و قابل‌حذف؛ backup اصلی رو حذف یا overwrite نکن.

Restore only to disposable databases; never delete or overwrite the source backup.

A backup file alone is not proof. Restore it, record recovery time, and verify known data with queries.

backup داریم، حالا بازیابی رو ثابت کردیم؟ / We have backups; have we proven recovery?

RPO رو از دادهٔ پذیرفته‌شده و RTO رو از زمان کل بازیابی تعریف کردیم؛ chain رو جدا restore و هم consistency فنی و هم دادهٔ کسب‌وکار رو سنجیدیم. عدد هدف رو با عدد مشاهده‌شده مقایسه کن و شکاف رو پنهان نکن. عملیات روزمرهٔ SQL Server Agent موضوع فصل بعد هست.

We defined RPO from tolerable data loss and RTO from end-to-end recovery, restored an isolated chain, and checked technical consistency plus business data. Compare target to observation and report gaps honestly. Next is SQL Server Agent operations.
