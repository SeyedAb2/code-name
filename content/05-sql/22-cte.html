CTE؛ query چندمرحله‌ای خوانا

CTEs: readable multi-step queries

query فروش حالا هم جزئیات قلم رو جمع می‌کنه، هم مشتری رو پیدا می‌کنه، هم گروه‌های کم‌فروش رو کنار می‌ذاره. تو در توکردن همهٔ منطق خواندن رو سخت کرده. می‌تونیم نتیجهٔ هر مرحله رو با یک نام موقت در متن query معرفی کنیم: CTE، یا عبارت جدولی مشترک.

The sales query now aggregates item details, joins customer information, and excludes low-sales groups. Nesting everything makes it hard to read. We can name each intermediate result inside the statement with a CTE—a common table expression.

گزارش وقتی جدی می‌شه که فقط «لیست» نباشهA report becomes serious when it is more than a list

تا اینجا گرفتن چند ردیف آسون بود. درد واقعی وقتی شروع می‌شه که یکی می‌گه «فروش هر شهر رو بده، نسبت به ماه قبل مقایسه کن، فقط شهرهای بالای فلان عدد رو نگه دار و رتبه هم بده». «CTE؛ query چندمرحله‌ای خوانا» رو برای همین جنس سؤال‌ها می‌خوایم. قدم‌به‌قدم می‌ریم جلو تا query هم درست باشه، هم بشه فهمید چرا درست کار می‌کنه.

Selecting rows is the easy part. Real reporting starts when someone asks for sales by city, a comparison with last month, a threshold, and a rank. “CTEs: readable multi-step queries” belongs to that kind of problem. We build the query step by step so it is not only correct but explainable.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

به‌جای query توی query توی query، مرحله‌ها رو نام بگذار / Name the stages instead of nesting everything

ابتدا مبلغ هر سفارش رو از قلم‌هایش می‌سازیم؛ بعد اون رو به مشتری وصل می‌کنیم؛ در آخر شرط گزارش رو می‌زنیم. CTE با `WITH` شروع می‌شه و تا پایان یک statement در دسترس هست. نام مرحله کمک می‌کنه دربارهٔ grain و مسئولیت هر بخش حرف بزنیم.

First calculate each order’s total from its items, then attach its customer, and finally apply the report condition. A CTE begins with `WITH` and is available to one statement. Naming each stage makes its grain and responsibility easier to discuss.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

یک ردیف در هر سفارش، پیش از اتصال نهایی / One row per order before the final join
;WITH OrderTotals AS
(
    SELECT oi.OrderId,
           SUM(oi.Quantity * oi.UnitPriceAtSale) AS Total
    FROM shop.OrderItems AS oi
    GROUP BY oi.OrderId
)
SELECT o.OrderId, c.FullName, t.Total
FROM shop.Orders AS o
JOIN OrderTotals AS t ON t.OrderId = o.OrderId
JOIN shop.Customers AS c ON c.CustomerId = o.CustomerId
ORDER BY o.OrderId;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

semicolon پیش از WITH کمک می‌کنه اگه statement قبلی بدون `;` تمام شده باشه، شروع CTE درست parse بشه. CTE خودش داده رو تغییر نمی‌ده و فقط یک statement بعد از آن میاد. نامی که در AS می‌دهی باید داخل پرانتز یک query معتبر بسازد.

The semicolon before WITH helps when a prior statement was not terminated. The CTE does not change data, and one statement follows it. The query inside parentheses must be valid.

چند CTE رو از بالا به پایین بخوان / Read multiple CTEs from top to bottom

وقتی دو مرحلهٔ مستقل یا وابسته داریم، می‌تونیم هرکدوم رو نام‌گذاری کنیم. CTE پایین‌تر می‌تونه به CTE قبلی اشاره کند؛ CTE قبلی نمی‌تونه به نامی که هنوز تعریف نشده ارجاع دهد. نام‌ها رو بر اساس معنی نتیجه انتخاب کن، نه شمارهٔ مرحله.

When a query has multiple independent or dependent stages, name them. A later CTE can reference an earlier one, but an earlier CTE cannot reference a name defined later. Name each expression by what its result means, not by its step number.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

ابتدا جمع مشتری، سپس انتخاب مشتری‌های پرفروش / Aggregate by customer, then select high-sales customers
;WITH CustomerSales AS
(
    SELECT o.CustomerId,
           SUM(oi.Quantity * oi.UnitPriceAtSale) AS SalesTotal
    FROM shop.Orders AS o
    JOIN shop.OrderItems AS oi ON oi.OrderId = o.OrderId
    GROUP BY o.CustomerId
),
HighSales AS
(
    SELECT CustomerId, SalesTotal
    FROM CustomerSales
    WHERE SalesTotal > 1000
)
SELECT c.CustomerId, c.FullName, h.SalesTotal
FROM HighSales AS h
JOIN shop.Customers AS c ON c.CustomerId = h.CustomerId
ORDER BY h.SalesTotal DESC;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

CTE دوم از نتیجهٔ اول استفاده می‌کنه. این نام‌گذاری خوانایی می‌آورد، اما تضمین نمی‌کنه هر CTE جداگانه در حافظه materialize بشه؛ optimizer می‌تونه query رو بازنویسی کند. برای رفتار فیزیکی به execution plan نگاه می‌کنیم، نه به واژهٔ CTE.

The second CTE consumes the first. Naming improves readability but does not guarantee that each CTE is separately materialized in memory; the optimizer may transform the query. Inspect the execution plan rather than assuming physical behavior from the word CTE.

CTE جدول موقت نیست / A CTE is not a temporary table

CTE فقط در statement بلافاصله بعد از تعریفش قابل‌ارجاع است؛ بعد از `GO` یا query بعدی، نامش وجود نداره. اگه باید نتیجه رو چند بار بخوانی، index موقت بسازی یا بین statementها نگه داری، table variable یا temp table رو بر اساس نیاز و اندازه بررسی کن. CTE رو برای «ذخیرهٔ دائمی نتیجه» انتخاب نکن.

A CTE is visible only to the immediately following statement; after GO or the next query, its name is gone. If you must read the result repeatedly, index it, or preserve it across statements, consider a table variable or temp table according to workload and size. A CTE is not persistent result storage.

scope فقط یک statement / Scope lasts one statement
;WITH ActiveProducts AS
(
    SELECT ProductId, ProductName
    FROM shop.Products
    WHERE IsActive = 1
)
SELECT ProductId, ProductName FROM ActiveProducts;
GO

-- این statement مستقل است؛ ActiveProducts دیگر در scope نیست:
SELECT COUNT_BIG(*) FROM ActiveProducts;
GO

statement دوم خطا می‌ده، چون نام CTE پس از اولین SELECT تمام شده. اگه دو گزارش لازم‌اند، CTE رو دوباره تعریف کن یا نتیجه رو در ساختاری با عمر مناسب نگه دار.

The second statement fails because the CTE name expired after the first SELECT. Define it again for another report or store results in a structure with the required lifetime.

بازگشت: فقط وقتی رابطه واقعاً چندسطحی هست / Recursion: only for genuinely multi-level relationships

CTE بازگشتی می‌تونه رابطهٔ خودارجاع رو چند سطح دنبال کند، مثل مدیر و مدیرِ مدیر. ساختار آن یک بخش anchor برای شروع و یک بخش recursive برای ادامه داره. باید عمق و چرخه رو جدی بگیری؛ جدول‌های واقعی ممکنه رابطهٔ دوری داشته باشند. این درس فقط شکل و ایمنی رو معرفی می‌کنه، نه موتور سازمانی برای پیمایش دلخواه گراف.

A recursive CTE can follow a self-referencing relationship across levels, such as employee, manager, and manager’s manager. It has an anchor member and a recursive member. Depth and cycles matter because real hierarchies can contain loops. This lesson introduces the shape and safety, not a general graph-processing engine.

پیمایش محدود از یک مدیر در دادهٔ تمرینی موقت / Bounded traversal from one manager
;WITH Org AS
(
    SELECT EmployeeId, EmployeeName, ManagerId, 0 AS Depth
    FROM #Employees
    WHERE EmployeeId = 1
    UNION ALL
    SELECT e.EmployeeId, e.EmployeeName, e.ManagerId, o.Depth + 1
    FROM #Employees AS e
    JOIN Org AS o ON e.ManagerId = o.EmployeeId
    WHERE o.Depth < 10
)
SELECT EmployeeId, EmployeeName, ManagerId, Depth
FROM Org
ORDER BY Depth, EmployeeId
OPTION (MAXRECURSION 10);
GO

این نمونه به #Employees فصل ۱۷ نیاز داره و همان نشست باید دادهٔ تمرینی رو ساخته باشه. شرط عمق و MAXRECURSION جلوی پیمایش بی‌انتها رو می‌گیرند، اما چرخه رو «درست» نمی‌کنن؛ دادهٔ چرخه‌دار رو جدا تشخیص بده و دربارهٔ سقف مناسب تصمیم بگیر.

This example requires the Chapter 17 #Employees fixture in the same session. A depth predicate and MAXRECURSION bound traversal but do not repair cycles; detect cyclic data separately and choose a suitable limit.

هر نام، یک نتیجهٔ میانی با grain مشخص / Each name represents an intermediate result with a defined grain

قبل و بعد هر CTE، grain رو از روی GROUP BY بگو. اگه CTE دوم رو به سطح جزئیات join کنی، ممکنه fan-out دوباره برگردد.

State the grain before and after each CTE from its GROUP BY. Joining the second CTE back to detail rows can reintroduce fan-out.

CTE رو برای خوانایی بگیر؛ نه برای جادوی اجرا / Use CTEs for clarity, not execution magic

CTE وقتی ارزش داره که مرحله‌ای رو اسم‌گذاری کند، grain رو آشکار کند یا query تو‌در‌تو رو به بخش‌های قابل‌بازبینی بشکند. برای reuse چند statement، نگهداری نتیجه یا index موقت، ساختار دیگری باید. Recursive CTE رو با anchor روشن و سقف عمق اجرا کن و چرخه رو مسئلهٔ داده بدان.

A CTE helps when it names a stage, exposes grain, or breaks nesting into reviewable pieces. Cross-statement reuse, stored results, or temporary indexing may need another structure. Give recursive CTEs a clear anchor and depth bound; treat cycles as a data problem.
