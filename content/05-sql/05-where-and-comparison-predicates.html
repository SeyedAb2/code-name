WHERE و شرط‌های مقایسه‌ای

WHERE and comparison predicates

فهرست محصول گزارش می‌شه، اما کابل قدیمیِ غیرفعال هم وسط کالاهای فعال برگشته. query خطا نداده؛ شرطی که باید ردیف رو کنار می‌گذاشت، بد گروه‌بندی شده. این فصل دربارهٔ همین تصمیم هست: چه ردیفی واجد شرط هست و چه ردیفی نیست؟

The product report is supposed to show active items, yet the inactive old cable appears among them. The query did not error; the predicate was grouped incorrectly. This chapter asks which rows qualify—and which do not.

از یک سؤال واقعی شروع کنیمStart with a real question

یه همکار تازه‌وارد معمولاً SQL رو از روی syntax حفظ می‌کنه؛ ولی چند روز بعد که گزارش واقعی می‌رسه، نمی‌دونه از کجا شروع کنه. اینجا برعکس می‌ریم. اول سؤال گزارش رو روشن می‌کنیم، بعد برای «WHERE و شرط‌های مقایسه‌ای» query می‌نویسیم، خروجی رو نگاه می‌کنیم و اگه چیزی عجیب بود از روی همون نتیجه می‌فهمیم کجای مدل ذهنی‌مون ایراد داره.

A newcomer often memorises SQL syntax, then gets stuck on the first real report. We do the opposite: clarify the reporting question, use “WHERE and comparison predicates” to answer it, inspect the result, and use any surprise as evidence that our mental model needs work.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

یک OR کوچک، یک گزارش غلط / One OR, one wrong report

در فصل قبل ستون‌ها رو انتخاب کردیم؛ هنوز همهٔ محصول‌ها رو می‌دیدیم. حالا می‌خوایم محصولات فعال با قیمت حداقل ۸۰۰ رو بگیریم، به‌علاوهٔ محصولی با شناسهٔ خاص که مدیر خواسته. اگه شرط رو بی‌پرانتز بنویسیم، آیا آن محصول خاص باید از شرط فعال‌بودن عبور کند؟ قبل از اجرا حدس بزن.

Last chapter selected columns but still returned every product. Now we need active products priced at least 800, plus a specially requested ID. If we write the condition without parentheses, must that special product also be active? Predict before running it.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

نسخهٔ ظاهراً ساده / The deceptively simple version
SELECT ProductId, ProductName, IsActive, UnitPrice
FROM shop.Products
WHERE IsActive = 1 AND UnitPrice >= 800 OR ProductId = 13
ORDER BY ProductId;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

کابل قدیمی برمی‌گرده، با اینکه IsActive آن صفر هست. SQL Server، AND رو پیش از OR ارزیابی می‌کنه؛ شرط عملاً این هست: «(فعال و گران) یا شناسه ۱۳». query از نظر نحوی درسته، اما الزام گزارش رو اجرا نمی‌کنه.

The old cable appears even though IsActive is zero. SQL Server evaluates AND before OR, so the condition means “(active and expensive) or ID 13.” The statement is valid SQL but does not meet the report requirement.

WHERE ردیف‌ها رو فیلتر می‌کنه؛ SELECT شکل خروجی رو / WHERE filters rows; SELECT shapes columns

WHERE برای هر ردیف منبع شرط می‌سنجد و ردیف‌های غیرمنطبق رو از نتیجه کنار می‌ذاره. این کار داده رو حذف یا اصلاح نمی‌کنه. در این query از فصل قبل alias خروجی در WHERE قابل‌استفاده نیست؛ در همان سطح، WHERE پیش از SELECT از نظر منطقی bind می‌شه.

WHERE evaluates a predicate for source rows and excludes nonmatching rows from the result. It does not delete or update data. As in the previous chapter, a SELECT alias is unavailable in WHERE at the same query level because WHERE binds logically before SELECT.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

گروه‌بندی‌ای که واقعاً می‌خوایم / The grouping we intend
SELECT ProductId, ProductName
FROM shop.Products
WHERE IsActive = 1
  AND (UnitPrice >= 800 OR ProductId = 13)
ORDER BY ProductId;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

حالا محصول ۱۳ حذف می‌شه چون شرط بیرونی IsActive=1 برای هر دو شاخه باید. نتیجه دو ردیف داره: کیبورد و پایهٔ مانیتور. پرانتز تزئین نیست؛ بخشی از معنای درخواست هست. اگه نیاز مدیر «محصول ۱۳ حتی اگه غیرفعال باشه» بود، باید گروه‌بندی دیگری می‌نوشتیم.

Now product 13 is excluded because the outer IsActive=1 condition applies to both alternatives. Two rows remain: keyboard and monitor stand. Parentheses are not decoration; they express the requirement. If the request meant “include product 13 even when inactive,” the grouping would differ.

مقایسه رو با نوع داده و دامنه بساز / Match comparisons to types and ranges

برای عدد از عملگرهایی مثل =، <، >، <= و >= استفاده کن. برای متن، مقدار رو با literal متنی مقایسه کن؛ چون ستون نام Unicode است، پیشوند N رو می‌گذاریم. برای زمان‌ها، بازهٔ نیمه‌باز از آغاز بازه تا پیش از مرز بعدی معمولاً از پایان 23:59:59 دقیق‌تر هست.

Use =, <, >, <=, and >= for numeric comparisons. Compare text to a text literal; because the city column is Unicode, we prefix the literal with N. For dates, a half-open interval from the start up to—but excluding—the next boundary is safer than guessing the final 23:59:59 value.

فیلتر تاریخ با مرز روشن / A date filter with explicit boundaries
SELECT OrderId, OrderedAt
FROM shop.Orders
WHERE OrderedAt >= '2026-02-01T00:00:00'
  AND OrderedAt <  '2026-02-06T00:00:00'
ORDER BY OrderedAt;
GO

سه سفارش اول برمی‌گردند، چون زمانشان از نیمه‌شب اول فوریه شروع می‌شه و پیش از نیمه‌شب ششم فوریه هست. اگه به‌جای آن تا 23:59:59 بنویسی، دقت datetime و fraction ثانیه رو هم باید حساب کنی. هنوز وارد توابع تاریخ و timezone نشده‌ایم.

The first three orders match: they start at midnight on February 1 and precede midnight on February 6. If you use 23:59:59 instead, you must account for datetime precision and fractional seconds. Time functions and time zones are not the subject yet.

Before moving on, explain in two sentences what problem this chapter solves and which output proves your solution is correct. If you only remember command names, rerun the previous example with different data.

نتیجهٔ خالی و مقدار اشتباه یکی نیستند / An empty result is not a connection failure

اگه جست‌وجوی OrderStatus='Shipped' هیچ ردیفی ندهد، query اجرا شده و دادهٔ تمرینی موردی نداره. این رو با خطای اتصال یا database خالی اشتباه نگیر. بعد از اجرا، مقدارهای واقعاً موجود رو با DISTINCT در فصل ۸ بررسی می‌کنیم؛ فعلاً خروجی و فرض خودت رو کنار هم بگذار.

If OrderStatus='Shipped' returns no rows, the query ran but the fixture contains no such case. Do not confuse that with a connection failure or empty database. Chapter 8 will inspect actual values with DISTINCT; for now compare the result with your assumption.
