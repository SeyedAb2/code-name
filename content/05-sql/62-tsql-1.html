T-SQL ۱: متغیر، شرط و حلقه

T-SQL 1: variables, branches, and loops

گزارشی باید با چند شرط محاسبه بشه. اگه برای هر ردیف یک دستور جدا اجرا کنیم، هم کند و هم سخت‌ردیابی می‌شه. T-SQL ابزار procedural داره؛ اول می‌آموزیم کجا باید و کجا یک query مجموعه‌ای بهتره.

A report has conditional logic. Running a separate command per row can be slow and hard to reason about. T-SQL has procedural constructs; first we learn when to use them and when a set-based query is better.

وقتی منطق رو می‌بری داخل دیتابیس، باید دلیل داشته باشیIf logic moves into the database, have a reason

یه stored procedure یا trigger می‌تونه کار رو خیلی تمیز کنه؛ همون ابزار می‌تونه شش ماه بعد تبدیل بشه به چیزی که هیچ‌کس نمی‌دونه از کجا اجرا شده. توی «T-SQL ۱: متغیر، شرط و حلقه» فقط syntax نمی‌زنیم. می‌سنجیم این منطق چرا باید داخل SQL Server باشه، چطور خطاش رو می‌بینیم و چطور مطمئن می‌شیم رفتار پنهان درست نکردیم.

A stored procedure or trigger can make a design cleaner, and the same feature can become mysterious hidden behaviour six months later. In “T-SQL 1: variables, branches, and loops” we go beyond syntax: why should this logic live in SQL Server, how do we observe failures, and how do we avoid invisible side effects?

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

متغیر در یک batch عمر داره / Variables live in a batch

متغیر رو با نوع مشخص declare کن؛ assignment با SET یا SELECT ممکنه، اما رفتار چندردیفی SELECT assignment رو اشتباه نخوان. GO دستور موتور SQL Server نیست؛ ابزار client batch رو جدا می‌کنه، پس متغیر از مرز GO عبور نمی‌کنه.

Declare variables with explicit types. Assignment may use SET or SELECT, but do not misread multi-row SELECT assignment. GO is not a SQL Server engine statement; client tooling splits batches, so a variable does not cross that boundary.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

یک batch قابل پیش‌بینی / A predictable batch
DECLARE @MinimumTotal decimal(12,2)=100.00;
DECLARE @Matched int;
SELECT @Matched=COUNT(*) FROM dbo.Orders WHERE TotalAmount >= @MinimumTotal;
SELECT @MinimumTotal AS Threshold,@Matched AS MatchedCount;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

اگه query چند ردیف برای یک variable بدهد، SELECT assignment آخرین مقداری رو که پردازش شده می‌ذاره؛ ترتیب بدون ORDER BY قطعی نیست. برای scalar subquery، صفر ردیف و چند ردیف رو جدا مدیریت کن.

If a query returns multiple rows for a variable, SELECT assignment leaves a processed value; without ORDER BY the result is not deterministic. Handle zero and multiple rows explicitly when using scalar subqueries.

شرط خوب، branchهای کامل داره / A sound branch covers its cases

IF و ELSE رو با BEGIN/END بنویس تا با اضافه‌شدن statement، scope ناخواسته نسازد. شرط NULL رو جدا در نظر بگیر؛ مقایسه با NULL برابر true یا false معمولی نیست. در چند branch، ترتیب شرط‌ها بخشی از منطق هست.

Use BEGIN/END around IF/ELSE so later statements do not accidentally escape the branch. Treat NULL separately; it is not an ordinary true/false comparison. Predicate order matters when branches overlap.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

اعتبارسنجی و branch / Validation and branching
DECLARE @Total decimal(12,2)=125.00;
IF @Total IS NULL OR @Total < 0
BEGIN
  SELECT 'invalid' AS Result;
END
ELSE IF @Total = 0
BEGIN
  SELECT 'empty' AS Result;
END
ELSE
BEGIN
  SELECT 'billable' AS Result;
END;

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

برای دسته‌بندی سادهٔ ردیف‌ها، CASE در یک SELECT اغلب بهتر از loop است؛ branch procedural رو برای تصمیم جریان اجرا نگه دار.

For simple row classification, CASE in one SELECT is often better than a loop. Reserve procedural branching for control flow.

هر حلقه باید سقف و شرط پایان داشته باشه / Every loop needs a bound and exit

WHILE برای چند کار ترتیبی یا polling محدود مفید است، اما جایگزین set-based DML نیست. مقدار کنترل رو در هر دور تغییر بده، سقف iteration تعریف کن و در مسیر خطا هم transaction رو باز رها نکن.

WHILE can help with sequential work or bounded polling, but it is not a substitute for set-based DML. Advance the control value, cap iterations, and do not leave a transaction open on an error path.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

loop محدود و قابل‌پیش‌بینی / A bounded loop
DECLARE @i int=1,@sum int=0;
WHILE @i <= 5
BEGIN
  SET @sum += @i;
  SET @i += 1;
END;
SELECT @sum AS Total,@i AS NextValue;

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

برای کار روی میلیون‌ها ردیف، loop row-by-row معمولاً نشانهٔ طراحی نامناسب هست. روش batch فصل‌های قبل رو با اجرای یک query مجموعه‌ای مقایسه کن.

For millions of rows, a row-by-row loop is often a design smell. Compare it with a set-based statement or bounded batch from earlier chapters.

دادهٔ میانی رو با scope روشن نگه دار / Keep intermediate data within a clear scope

#temp در tempdb و در connection جاری ساخته می‌شه؛ table variable scope دیگری داره و تضمین حافظه‌ای بودن نیست. object موقت رو برای جریان چندمرحله‌ای استفاده کن، نه برای پنهان‌کردن query پیچیده. بعد از GO همان connection مهمه.

A local temp table lives in tempdb and the current connection; a table variable has a different scope and is not guaranteed memory-only. Use temporary objects for a multi-step flow, not to hide a complex query. The connection matters across GO.

دو مرحلهٔ موقت / Two temporary stages
CREATE TABLE #RecentOrders(OrderId int PRIMARY KEY, CustomerId int NOT NULL);
INSERT #RecentOrders
SELECT OrderId,CustomerId FROM dbo.Orders
WHERE OrderDate >= DATEADD(day,-7,CONVERT(date,SYSDATETIME()));
SELECT CustomerId,COUNT(*) AS Orders
FROM #RecentOrders GROUP BY CustomerId;
DROP TABLE #RecentOrders;
