ایندکس ۳: هزینه، fragmentation و نگه‌داری

Indexes 3: cost, fragmentation, and maintenance

هشدار مانیتورینگ می‌گه fragmentation یک index به ۴۰٪ رسیده؛ پیشنهاد فوری rebuild هست. اما index فقط ۳۰ page داره و بار کاری بیشتر write می‌کنه. این فصل یاد می‌ده پیش از اجرای maintenance، بپرسیم: کدوم هزینه رو حل می‌کنیم و چه چیزی رو با چه ریسکی تغییر می‌دهیم؟

Monitoring reports 40% fragmentation and suggests an immediate rebuild. The index is only 30 pages and the workload is write-heavy. Before maintenance, ask which cost we are solving and what we change at what risk.

حالا بریم زیر کاپوتNow look under the hood

یه query از بیرون خیلی ساده‌ست: می‌فرستیش و جواب میاد. ولی وقتی کند می‌شه، دیگه اون نمای بیرونی کافی نیست. برای «ایندکس ۳: هزینه، fragmentation و نگه‌داری» یه لایه پایین‌تر می‌ریم و مسیر داده رو دنبال می‌کنیم؛ نه برای حفظ‌کردن اصطلاحات داخلی، برای اینکه وقتی plan یا I/O رفتار عجیبی داشت بفهمیم SQL Server واقعاً داره چه کاری انجام می‌ده.

A query looks simple from the outside: send it, get rows back. Once it becomes slow, that view is not enough. In “Indexes 3: cost, fragmentation, and maintenance” we move one layer down and follow the data path—not to memorise internals, but to explain what SQL Server is actually doing when plans and I/O behave unexpectedly.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

هر index یک نسخهٔ قابل‌نگه‌داری از اطلاعات می‌سازه / Every index is another structure to maintain

با هر درج، حذف یا تغییر ستون‌های key/INCLUDE، index باید به‌روز بشه. هزینه در CPU، log، I/O، storage و cache دیده می‌شه. از طرف دیگر، index بد انتخاب‌شده می‌تونه seekهای بی‌مصرف، lookup و planهای گران بسازد. اول بار کاری و استفادهٔ واقعی رو اندازه بگیر.

Each insert, delete, or change to key/included columns maintains the index. Costs appear in CPU, log, I/O, storage, and cache. A poorly chosen index can also cause ineffective seeks, lookups, and expensive plans. Measure actual workload and usage first.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

usage counterها رو با محدودیتشان بخوان / Read usage counters with their limitations
SELECT OBJECT_SCHEMA_NAME(i.object_id) AS SchemaName,
       OBJECT_NAME(i.object_id) AS TableName, i.name,
       us.user_seeks, us.user_scans, us.user_lookups, us.user_updates
FROM sys.indexes AS i
LEFT JOIN sys.dm_db_index_usage_stats AS us
  ON us.database_id = DB_ID() AND us.object_id=i.object_id AND us.index_id=i.index_id
WHERE i.object_id = OBJECT_ID(N'Lab42.Ticket')
ORDER BY COALESCE(us.user_updates,0) DESC;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

شمارنده‌ها از زمان راه‌اندازی یا reset در دسترس‌اند و history دائمی نیستند. user_updates تعداد عملیات نگه‌داری رو تخمین می‌زند، نه تعداد rowهای دقیق. پیش از حذف index، uptime، دورهٔ کاری، queryهای فصلی و نقش constraint رو هم بررسی کن.

Counters cover only since startup/reset, not permanent history. user_updates approximates maintenance operations, not exact changed-row counts. Before dropping an index, check uptime, workload coverage, seasonal queries, and whether it supports a constraint.

درصد fragmentation به‌تنهایی دستور rebuild نیست / Fragmentation percentage alone is not a rebuild command

fragmentation می‌تونه ترتیب منطقی leaf pageها نسبت به ترتیب فیزیکی رو نشان دهد؛ در storage مدرن و بار کاریهای مختلف اثرش یکسان نیست. page count کم، scan کم‌حجم یا بار کاری کاملاً cacheشده ممکنه از rebuild سودی نبرد. page density، اندازهٔ index، query، I/O و هزینهٔ عملیات رو کنار هم ببین.

Fragmentation can describe the mismatch between logical and physical leaf-page order, but its impact varies by storage and workload. A small index, short scan, or cache-resident workload may gain nothing from a rebuild. Consider page count, density, queries, I/O, and operation cost together.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

DMV رو محدود و با mode سبک‌تر بررسی کن / Inspect a bounded object with a lightweight mode
SELECT OBJECT_NAME(ips.object_id) AS TableName,
       i.name AS IndexName, ips.index_type_desc,
       ips.page_count, ips.avg_fragmentation_in_percent,
       ips.avg_page_space_used_in_percent
FROM sys.dm_db_index_physical_stats
     (DB_ID(), OBJECT_ID(N'Lab42.Ticket'), NULL, NULL, 'LIMITED') AS ips
JOIN sys.indexes AS i
  ON i.object_id=ips.object_id AND i.index_id=ips.index_id
WHERE ips.index_id > 0;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

روی کل دیتابیس بزرگ، mode و دامنهٔ بررسی رو آگاهانه انتخاب کن. DMV هم نمونهٔ لحظه‌ای هست و شرایط بار کاری رو توضیح نمی‌ده. خروجی رو با actual plan و storage تأخیر کنار هم بگذار؛ یک آستانهٔ درصدی واحد برای همهٔ indexها قانون طبیعت نیست.

Choose scope and scan mode carefully on a large database. The DMV is a snapshot and does not explain workload impact. Pair it with actual plans and storage latency; one universal percentage threshold is not a law of nature.

Reorganize و rebuild هزینه و اثر متفاوت دارن / Reorganize and rebuild have different costs

REORGANIZE عملیات مرحله‌ای‌تر روی leaf level انجام می‌ده؛ معمولاً سبک‌تر اما محدودتر هست و statistics رو مثل rebuild تازه نمی‌کنه. REBUILD ساختار رو دوباره می‌سازه، فضای موقت و log/I/O می‌خواد و ممکنه lock یا resource pressure ایجاد کند؛ online بودن هم به نسخه، edition و ساختار بستگی داره. گزینه‌ها رو برای target دقیق بررسی کن.

REORGANIZE is a more incremental leaf-level operation, typically lighter but more limited, and does not refresh statistics like a rebuild. REBUILD reconstructs the structure and needs space, log, and I/O; it may cause locking or resource pressure. Online support depends on version, edition, and structure.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

این دو دستور رو پشت‌سرهم در production اجرا نکن. ابتدا اندازهٔ index، log capacity، blocking tolerance و backup/پایش رو بررسی کن. اگه مشکل statistics است، maintenance index رو به‌عنوان درمان خودکار فرض نکن؛ علت estimate رو جدا تشخیص بده.

Do not run both commands sequentially in production. Check index size, log capacity, blocking tolerance, and monitoring first. If the issue is statistics, do not assume index maintenance is an automatic cure; diagnose estimation separately.
