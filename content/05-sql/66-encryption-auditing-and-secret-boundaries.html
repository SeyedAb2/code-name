رمزگذاری، Audit و مرز secret

Encryption, auditing, and secret boundaries

تیمی می‌گه دیتابیس «امن شده» چون TDE روشن هست. اما کاربر مجاز هنوز داده رو می‌خونه، backup کلید لازم داره و secret در استقرار log افتاده. امنیت رو با تهدید مشخص می‌سنجیم، نه با تیک‌زدن feature.

A team says its database is “secure” because TDE is enabled. Authorized users can still query the data, backups need key material, and a secret leaked into deployment logs. Evaluate controls against a threat, not a feature checklist.

این دفعه سؤال اینه: چه کسی اجازه داره؟This time the question is: who is allowed?

خیلی از دیتابیس‌ها از نظر query درستن ولی از نظر دسترسی نه؛ چون اپ با کاربری وصل می‌شه که تقریباً همه‌چیز بلده و همه‌چیز می‌تونه. «رمزگذاری، Audit و مرز secret» رو با حساب محدود جلو می‌بریم. هر مجوزی که می‌دیم، با همون کاربر امتحانش می‌کنیم تا فرق «فکر می‌کنم بسته‌ست» با «واقعاً بسته‌ست» روشن بشه.

Many databases are query-correct but permission-wrong because the application connects with an account that can do almost anything. In “Encryption, auditing, and secret boundaries” we work with restricted principals and test permissions as those principals so “I think it is locked down” becomes demonstrable behaviour.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

اول بپرسیم از چه چیزی محافظت می‌کنیم / First identify the threat

TDE فایل data و log رو در حالت ذخیره‌شده رمز می‌کنه و شفاف است؛ query مجاز رو پنهان نمی‌کنه. Dynamic Data Masking نمایش بعضی مقدارها رو برای برخی کاربرها تغییر می‌ده، ولی کنترل محرمانگی cryptographic نیست. Always Encrypted رمزگشایی رو تا client دارای کلید محدود می‌کنه، با محدودیت نوع query و driver. این‌ها جای permission و مدیریت کلید رو نمی‌گیرند.

TDE encrypts data/log files at rest and is transparent; it does not hide results from authorized queries. Dynamic Data Masking changes presentation for selected users but is not cryptographic confidentiality. Always Encrypted keeps decryption at a key-holding client, with driver/query limitations. None replaces permissions or key management.

TDE فایل رو رمز می‌کنه، نه مجوز رو / TDE encrypts files, not permissions

TDE برای database encryption key و محافظ instance-level نیاز داره؛ backup/restore و جابه‌جایی دیتابیس به certificate/key material وابسته هست. کلید رو کنار backup نگذار. وضعیت encryption رو از catalog و عملیات backup/restore کنترل کن؛ روشن‌شدن option الزاماً به معنی پایان encryption scan نیست.

TDE requires a database encryption key protected by instance-level material; moving/restoring the database depends on certificates/keys. Do not store keys beside backups. Inspect catalog state and backup/restore behavior; enabling the option does not mean the encryption scan has finished.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

کلید، client و مجوز رو کنار هم طراحی کن / Design keys, clients, and permissions together

Always Encrypted معمولاً driver رو در client درگیر می‌کنه و عملیات مجاز روی ciphertext محدود است؛ به نسخهٔ driver، encryption mode و query نیازمند مقایسه/جست‌وجو توجه کن. Masking برای کاهش نمایش است، نه جایگزین deny/GRANT. principal privileged و مسیرهای export رو هم تست کن.

Always Encrypted involves a client driver and restricts operations on ciphertext; account for driver version, encryption mode, and query requirements such as comparison/search. Masking reduces casual exposure, not a substitute for GRANT/DENY. Test privileged principals and export paths too.

Audit ثبت می‌کنه؛ secret رو حفاظت می‌کنیم / Audit records; secrets need protection

SQL Audit رو روی actionهای مشخص، target امن، retention و دسترسی خواننده تنظیم کن. اگه خود audit file قابل تغییر/حذف باشه، شواهد ضعیف‌اند. secret رو در query text، application log یا history نگذار؛ اگه افشا شد rotate کن و فقط فایل رو پاک نکن. backup کلیدها باید قابل‌بازیابی و جدا از backup داده نگهداری بشه.

Configure SQL Audit for explicit actions, a protected target, retention, and reader permissions. Mutable/deletable audit output weakens evidence. Keep secrets out of query text, application logs, and history; rotate exposed credentials rather than merely deleting a file. Key backups must be recoverable and separate from data backups.

TDE برای فایل، Always Encrypted برای مرز plaintext، masking برای نمایش و Audit برای ثبت رویداد هست. هرکدوم محدودیت و نیاز کلید/مجوز خودش رو داره. threat model و restore test نشان می‌دهند کنترل واقعاً چه پوششی داره.

TDE protects files, Always Encrypted changes the plaintext boundary, masking affects presentation, and Audit records selected events. Each has distinct limits and key/permission needs. Threat modeling and restore tests show actual coverage.
