قیدها؛ قانون‌هایی که از خود داده محافظت می‌کنن

Constraints: rules enforced by the database

دو برنامهٔ مختلف به پایگاه‌داده وصل‌اند. یکی بررسی می‌کنه کد مشتری تکراری نباشه؛ دیگری یادش رفته. حالا دادهٔ تکراری وارد شده و گزارش‌ها دو مشتری نشان می‌دهند. قانون صحت داده نباید فقط در حافظهٔ یک برنامه زندگی کند؛ باید در خود schema ثبت بشه.

Two applications write to the same database. One checks that customer codes are unique; the other forgets. Duplicate customers enter and reports diverge. Data integrity should not live only in one application's memory; encode the rule in the schema.

تصمیمی که امروز کوچیکه، فردا توی هر query دیده می‌شهA small schema decision today appears in every query tomorrow

وقتی جدول فقط ده ردیف داره، تقریباً هر طراحی‌ای «کار می‌کنه». دردش چند ماه بعد معلوم می‌شه؛ وقتی داده تکراری شده، constraint نداری یا یه نوع داده اشتباه همهٔ queryها رو پیچیده کرده. توی «قیدها؛ قانون‌هایی که از خود داده محافظت می‌کنن» قرار نیست فقط DDL بنویسیم؛ می‌خوایم بفهمیم هر تصمیم چه قانونی رو وارد خود دیتابیس می‌کنه و هزینهٔ اون تصمیم بعداً کجاست.

With ten rows, almost any design seems to work. The cost appears months later when data is duplicated, constraints are missing, or a poor data type infects every query. In “Constraints: rules enforced by the database” we are not merely writing DDL; we are deciding which rules the database itself enforces and what those choices cost later.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

یک قانون، هر نویسندهٔ داده / One rule, every writer

با جدول آزمایشی مشتری و سفارش شروع می‌کنیم. قیدها تصمیم‌های schema هستن: primary key هویت ردیف رو تضمین می‌کنه، unique مقدار کسب‌وکار رو یکتا می‌کنه، check دامنهٔ معتبر می‌سازه، default مقدار پیش‌فرض می‌ده و foreign key رابطه رو نگه می‌داره.

Start with a disposable customer/order schema. Constraints are schema-level rules: a primary key identifies rows, UNIQUE enforces a business key, CHECK restricts valid values, DEFAULT supplies an omitted value, and a foreign key preserves relationships.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

جدول با قیدهای نام‌دار / Tables with named constraints
DROP TABLE IF EXISTS #Orders;
DROP TABLE IF EXISTS #Customers;
CREATE TABLE #Customers
(
  CustomerId int IDENTITY PRIMARY KEY,
  CustomerCode varchar(20) NOT NULL,
  Email nvarchar(200) NOT NULL,
  CONSTRAINT UQ_Customers_Code UNIQUE (CustomerCode),
  CONSTRAINT UQ_Customers_Email UNIQUE (Email)
);
CREATE TABLE #Orders
(
  OrderId int IDENTITY PRIMARY KEY,
  CustomerId int NOT NULL,
  Total decimal(10,2) NOT NULL,
  State varchar(12) NOT NULL
    CONSTRAINT DF_Orders_State DEFAULT ('Pending'),
  CONSTRAINT CK_Orders_Total CHECK (Total >= 0),
  CONSTRAINT CK_Orders_State CHECK (State IN ('Pending','Paid','Cancelled'))
);
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

نام‌گذاری قیدها پیام خطا و migration رو قابل‌فهم‌تر می‌کنه. بیشتر constraintها رو روی جدول موقت تمرین می‌کنیم؛ اما SQL Server روی temporary table، FOREIGN KEY رو پشتیبانی نمی‌کنه. آزمایش FK رو جداگانه و فقط در دیتابیس آزمایشی و قابل‌حذف انجام می‌دهیم.

Named constraints make errors and migrations easier to interpret. Most rules use temporary tables; SQL Server does not support FOREIGN KEY constraints on temporary tables. Test the FK separately and only in a disposable database.

PRIMARY KEY هویت ردیف است، نه جایگزین همهٔ قیدها / A primary key identifies a row; it does not replace every rule

primary key یکتا و NOT NULL هست و هر جدول فقط یک primary key داره؛ اما می‌تونه مرکب باشه. شناسهٔ identity یک راه تولید کلید مصنوعی است، نه تضمین یکتایی به‌تنهایی: خود primary key یا unique constraint باید اون رو enforce کند. کد مشتری مثل CustomerCode ممکنه natural/business key باشه و جداگانه unique بمونه.

A primary key is unique and NOT NULL; a table has one primary-key constraint, which may span multiple columns. IDENTITY generates surrogate values but does not itself enforce uniqueness—the key constraint does. A business key such as CustomerCode may also need a separate UNIQUE constraint.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

کلید مرکب روی جدول ارتباط / Composite key on a relationship table
CREATE TABLE #ProductTag
(
  ProductId int NOT NULL,
  TagId int NOT NULL,
  AddedAt datetime2(0) NOT NULL DEFAULT SYSUTCDATETIME(),
  CONSTRAINT PK_ProductTag PRIMARY KEY (ProductId, TagId)
);
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

این کلید اجازه نمی‌ده یک برچسب دوبار به همان محصول وصل بشه؛ اما همان TagId می‌تونه برای محصول دیگر تکرار بشه. قید رو با پرسش رابطه طراحی کن، نه صرفاً با اینکه «یک ستون عددی داشته باشیم».

This key prevents attaching the same tag twice to one product, while allowing that tag on another product. Design the constraint from the relationship rule, not from a habit of choosing one numeric column.

FOREIGN KEY و CHECK خطا رو نزدیک محل ورود می‌گیرند / Foreign keys and checks reject invalid writes at the boundary

foreign key تضمین می‌کنه مقدار فرزند به کلید موجود در والد اشاره کند، مگر NULL مجاز باشه. CHECK شرط هر ردیف رو enforce می‌کنه؛ برای مثال Total منفی یا State ناشناخته رو رد می‌کنه. این قیدها ورودی نامعتبر رو تشخیص می‌دهند، اما جای validation پیام‌دار در UI رو نمی‌گیرند.

A foreign key requires a child value to reference an existing parent key unless NULL is allowed. CHECK enforces a row predicate, rejecting negative totals or unknown states. These constraints reject invalid writes but do not replace user-friendly application validation.

ردشدن دادهٔ نامعتبر یک نشانهٔ مفید هست / A rejected write is useful evidence
-- FK constraints require ordinary tables. Run this section only in a disposable database.
DROP TABLE IF EXISTS dbo.ConstraintLab_Orders, dbo.ConstraintLab_Customers;
CREATE TABLE dbo.ConstraintLab_Customers
(
  CustomerId int NOT NULL PRIMARY KEY,
  CustomerCode varchar(20) NOT NULL UNIQUE
);
CREATE TABLE dbo.ConstraintLab_Orders
(
  OrderId int NOT NULL PRIMARY KEY,
  CustomerId int NOT NULL,
  Total decimal(10,2) NOT NULL CHECK (Total >= 0),
  CONSTRAINT FK_ConstraintLab_Orders_Customers FOREIGN KEY (CustomerId)
    REFERENCES dbo.ConstraintLab_Customers(CustomerId)
);
INSERT dbo.ConstraintLab_Customers VALUES (1,'C-1');
GO
INSERT #Customers (CustomerCode, Email)
VALUES ('C-1', N'a@example.test');

INSERT #Orders (CustomerId, Total, State)
VALUES (1, -5, 'Paid');       -- rejected by CHECK

INSERT dbo.ConstraintLab_Orders (OrderId, CustomerId, Total)
VALUES (1, 999, 20);          -- rejected by FOREIGN KEY
GO

اگه دو constraint هم‌زمان نقض شوند، ممکنه اول فقط یکی رو در خطا ببینی. اولین خطا رو اصلاح کن و دوباره اجرا کن؛ از متن خطا، نام قید و مقدار ورودی برای تشخیص استفاده کن.

When a row violates multiple constraints, the first reported failure may hide another. Fix the observed issue and rerun; use the constraint name and input value to diagnose.

UNIQUE و DEFAULT معنای کسب‌وکار رو ثبت می‌کنن / UNIQUE and DEFAULT encode business rules

UNIQUE از تکرار کلید کسب‌وکار جلوگیری می‌کنه. رفتار چند NULL به تعریف ستون و قید وابسته است؛ در SQL Server یک unique index عادی برای یک ستون معمولاً فقط یک NULL می‌پذیرد، پس nullable بودن و نیاز محصول رو جدا بررسی کن. DEFAULT تنها وقتی اعمال می‌شه که ستون حذف بشه یا DEFAULT صریح داده بشه؛ NULL صریح رو جایگزین نمی‌کنه.

UNIQUE prevents duplicate business keys. NULL behavior depends on the constraint and design; a regular single-column unique index in SQL Server generally permits only one NULL, so assess nullability and requirements explicitly. DEFAULT applies when a column is omitted or DEFAULT is specified; it does not replace explicit NULL.

default رو با حذف ستون آزمایش کن / Test a default by omitting the column
INSERT #Orders (CustomerId, Total)
VALUES (1, 25.00);
SELECT OrderId, CustomerId, Total, State FROM #Orders;
GO

در این INSERT، State مقدار Pending می‌گیره؛ چون حذف شده هست. اگه State رو صریح NULL بدهی، NOT NULL اون رو رد می‌کنه. این تفاوت رو در API و migration هم نگه دار.

State becomes Pending because it was omitted. An explicit NULL is rejected by NOT NULL. Preserve this distinction in APIs and migrations too.

قید تازه روی دادهٔ قدیمی / Adding a constraint to existing data

وقتی روی جدول موجود قید می‌گذاری، SQL Server باید ردیف‌های فعلی رو هم بررسی کند. اگه داده‌های قدیمی ناقض قانون باشند، اضافه‌کردن قید شکست می‌خورد. اول query پیدا‌کنندهٔ دادهٔ بد رو بنویس؛ اصلاح یا قرنطینه رو تعیین کن؛ بعد قید رو اضافه کن. گزینهٔ اعتماد به قید رو کورکورانه خاموش نکن.

When adding a constraint to an existing table, SQL Server validates existing rows. Bad legacy data can make the change fail. First query for violations, decide whether to repair or quarantine them, then add and validate the constraint. Do not disable trust blindly.

دادهٔ ناقض CHECK رو پیش از migration پیدا کن / Find CHECK violations before migration
SELECT OrderId, Total
FROM dbo.Orders
WHERE Total < 0;
GO

این query فقط دادهٔ فعلی رو می‌سنجد؛ تضمین نمی‌کنه writer دیگری هم‌زمان دادهٔ بد وارد نکند. migration باید کنترل هم‌زمانی و ترتیب استقرار رو هم در نظر بگیرد.

This query checks current rows; it does not stop another writer from inserting bad data concurrently. A migration also needs a deployment order and concurrency plan.

قانون رو نزدیک داده enforce کن / Enforce invariants close to the data

یک برنامه ممکنه validation رو فراموش کند؛ writer دیگر هم شاید اصلاً همان کد رو اجرا نکند. قید پایگاه‌داده همهٔ مسیرهای نوشتن رو پوشش می‌ده، اما پیام قابل‌فهم و تجربهٔ کاربر همچنان کار برنامه هست. قانون رو در DB enforce کن و خطای اون رو در لایهٔ برنامه درست ترجمه کن.

One application may skip validation, and another writer may not use that code at all. Database constraints cover every write path, while clear messaging and user experience remain application responsibilities. Enforce invariants in the database and translate errors at the application boundary.

  • کلید اصلی هویت ردیف رو حفظ می‌کنه / The primary key identifies each row.
  • قیدهای business key مقدار تکراری رو رد می‌کنن / Unique constraints reject duplicate business keys.
  • FK رابطهٔ واقعی رو enforce می‌کنه / Foreign keys enforce references.
  • CHECK و DEFAULT مرز مقدار رو روشن می‌کنن / CHECK and DEFAULT define valid-value rules.
  • دادهٔ قدیمی قبل از migration بررسی شده / Existing data is validated before migration.
