Page، extent و فایل‌های پایگاه‌داده

Pages, extents, and database files

یک query می‌گه scan بزرگی داره، مدیر سیستم می‌گه فضای فایل کم هست و کسی پیشنهاد می‌ده «یک ndf اضافه کنیم». برای جداکردن این مسئله‌ها، از واحدهایی شروع می‌کنیم که موتور می‌خونه و می‌نویسه: page، extent و فایل.

A query reports a large scan, operations reports low file space, and someone suggests adding an NDF. To separate these concerns, start with the units the engine reads and writes: pages, extents, and files.

حالا بریم زیر کاپوتNow look under the hood

یه query از بیرون خیلی ساده‌ست: می‌فرستیش و جواب میاد. ولی وقتی کند می‌شه، دیگه اون نمای بیرونی کافی نیست. برای «Page، extent و فایل‌های پایگاه‌داده» یه لایه پایین‌تر می‌ریم و مسیر داده رو دنبال می‌کنیم؛ نه برای حفظ‌کردن اصطلاحات داخلی، برای اینکه وقتی plan یا I/O رفتار عجیبی داشت بفهمیم SQL Server واقعاً داره چه کاری انجام می‌ده.

A query looks simple from the outside: send it, get rows back. Once it becomes slow, that view is not enough. In “Pages, extents, and database files” we move one layer down and follow the data path—not to memorise internals, but to explain what SQL Server is actually doing when plans and I/O behave unexpectedly.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

page واحد پایهٔ I/O فایل داده هست / A page is the basic data-file I/O unit

صفحهٔ داده در SQL Server اندازهٔ ۸ KiB داره؛ extent مجموعهٔ هشت page پیوسته و ۶۴ KiB هست. data page ردیف‌ها رو نگه می‌داره، index page ساختار index رو و pageهای سیستمی metadata تخصیص رو. این اعداد به معنی آن نیست که هر query دقیقاً یک extent می‌خونه؛ موتور pageهای لازم رو با الگوی I/O خودش می‌گیره.

A SQL Server data page is 8 KiB; an extent is eight contiguous pages, or 64 KiB. Data pages hold rows, index pages hold index structures, and system pages track allocation metadata. This does not mean every query reads exactly one extent; the engine requests pages according to its I/O pattern.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

فایل‌های دیتابیس جاری رو بخوان / Inspect files in the current database
SELECT DB_NAME() AS DatabaseName,
       file_id, name AS LogicalName, type_desc,
       physical_name, size * 8.0 / 1024 AS SizeMB,
       max_size, growth, is_percent_growth
FROM sys.database_files
ORDER BY file_id;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

size در این view برحسب pageهای ۸ KiB است؛ ضرب در ۸ و تقسیم بر ۱۰۲۴ مقدار MiB رو می‌ده. این query اندازهٔ تخصیص‌یافتهٔ فایل رو نشان می‌ده، نه فضای آزاد داخل فایل و نه فضای آزاد دیسک میزبان. برای آن پرسش‌ها شاهد جدا باید.

The size column counts 8-KiB pages; multiplying by 8 and dividing by 1024 yields MiB. This query shows allocated file size—not free space inside the file or on the host disk. Those questions need separate evidence.

data file و log file وظیفهٔ یکسان ندارن / Data and log files serve different structures

هر database دست‌کم یک data file و یک transaction log file داره. data file از pageها تشکیل می‌شه؛ log رشته‌ای از رکوردهاست و page/extent نداره. پسوندهای رایج mdf، ndf و ldf هستن، اما پسوند به‌تنهایی نوع رو تعیین نمی‌کنه؛ metadata و type_desc رو بخوان.

Each database has at least one data file and one transaction log file. Data files contain pages; the log is a sequence of records, not pages or extents. MDF, NDF, and LDF are common extensions, but inspect metadata rather than trusting the extension.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

filegroup منطقی رو از مسیر فیزیکی جدا کن / Inspect filegroups and physical placement
SELECT fg.name AS FilegroupName, fg.type_desc,
       df.name AS LogicalFileName, df.type_desc AS FileType,
       df.physical_name
FROM sys.filegroups AS fg
LEFT JOIN sys.database_files AS df
  ON df.data_space_id = fg.data_space_id
ORDER BY fg.name, df.file_id;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

filegroup ظرف منطقی فایل‌های data هست و می‌تونه به مدیریت placement و backup کمک کند؛ log به filegroup تعلق نداره. افزودن چند فایل هم خودبه‌خود بار کاری رو سریع نمی‌کنه؛ layout باید با storage و الگوی I/O هماهنگ باشه.

A filegroup logically groups data files and can help with placement and backup planning; logs do not belong to filegroups. Adding files does not automatically speed a workload—the layout must match storage and I/O patterns.

Autogrowth کمربند اضطراری است، نه برنامهٔ ظرفیت / Autogrowth is a safety net, not capacity planning

growth می‌تونه ثابت یا درصدی باشه. رشد درصدی با بزرگ‌شدن فایل increment بزرگ‌تری می‌سازه؛ رشد ثابت قابل‌پیش‌بینی‌تر هست. رشد مکرر می‌تونه مکث ایجاد کند، اما خاموش‌کردنش هم ممکنه write رو متوقف کند. هیچ مقدار جادویی برای همه وجود نداره.

Growth can be fixed-size or percentage-based. Percentage growth creates larger increments as a file grows; fixed growth is more predictable. Frequent growth can pause work, but disabling growth can stop writes. There is no universal magic setting.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

تنظیم فعلی رو مشاهده کن؛ بی‌دلیل تغییر نده / Observe current settings before changing anything
SELECT name, type_desc, size * 8.0 / 1024 AS SizeMB,
       growth, is_percent_growth,
       CASE WHEN growth = 0 THEN N'growth disabled'
            WHEN is_percent_growth = 1 THEN CONCAT(growth, N'%')
            ELSE CONCAT(growth * 8.0 / 1024, N' MB') END AS GrowthSetting
FROM sys.database_files;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

نرخ رشد، اندازهٔ فایل، فضای آزاد، اندازهٔ transaction و وقفهٔ قابل‌قبول رو بسنج. تغییر file growth یا افزودن فایل، اقدام عملیاتی هست و باید با capacity plan و پنجرهٔ نگه‌داری انجام بشه.

Consider growth rate, file size, free space, transaction size, and acceptable pauses. Changing growth or adding files is an operational change that belongs in capacity planning and a maintenance window.

در VM یا سرویس managed، مسیر فیزیکی و دیدن دیسک ممکنه با host فرق کند. مقدار filegroup، backup و alert فضای آزاد رو در همان محیط عملیاتی تأیید کن.

On VMs or managed services, physical paths and disk visibility may differ from the host. Verify filegroup, backup, and free-space alerts in the actual environment.
