SQL Server در Docker و اتصال بین hostها

SQL Server in Docker and cross-host connectivity

SQL Server داخل container سالم است، ولی برنامه از host دیگری وصل نمی‌شه. container port با host port اشتباه شده؟ آیا port publish، firewall باز و DNS درسته؟ هر مسیر رو جدا اندازه می‌گیریم.

SQL Server is healthy in a container, but a remote application cannot connect. Are container and host ports confused? Is the port published, firewall open, and DNS correct? We measure each path separately.

پیش‌نیاز: Docker network، port mapping، SQL TCPPrerequisites: Docker networks, port mapping, SQL TCPحدود ۹۰ دقیقه · ۱۸ تمرین / About 90 minutes · 18 exercises

اپ می‌گه «به دیتابیس وصل نمی‌شم»؛ از کجا شروع کنیم؟The app says “I cannot reach the database”; where do we start?

خطای اتصال یه اسم مشترک برای چند مشکل کاملاً متفاوته: DNS، پورت، TLS، instance، firewall یا خود login. توی «SQL Server در Docker و اتصال بین hostها» مسیر اتصال رو تکه‌تکه می‌کنیم. هر بار فقط یک لایه رو ثابت می‌کنیم تا به‌جای عوض‌کردن تصادفی تنظیمات، دقیقاً بدونیم شکست کجاست.

“Cannot connect” is one phrase for several different failures: DNS, port, TLS, instance discovery, firewall, or authentication. In “SQL Server in Docker and cross-host connectivity” we split the path into layers and prove one layer at a time instead of changing random settings.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

هر مبدأ endpoint خودش رو داره / Each client has its own endpoint

از host با host-published port می‌رویم. container هم‌شبکه از service DNS و port داخلی استفاده می‌کنه؛ localhost آنجا به خود container اشاره داره. client بیرونی به IP/DNS host و published port نیاز داره.

A host uses the published host port. A peer container uses service DNS and the internal port; localhost there means that container itself. An external client needs the host IP/DNS and published port.

publish کردن، سطح host رو تغییر می‌ده / Publishing changes host exposure

SQL Server معمولاً در container روی TCP 1433 گوش می‌ده. mapping می‌تونه host port دیگری انتخاب کند؛ host port رو با container port اشتباه نگیر. binding بدون IP ممکنه interfaceهای host رو در معرض بگذارد؛ برای lab محلی loopback رو انتخاب کن و firewall host و cloud رو جدا بررسی کن.

SQL Server commonly listens on TCP 1433 in the container. A mapping can use a different host port. An unspecified host binding may expose host interfaces; use loopback for a local lab and inspect host/cloud firewalls separately.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

mapping محدود برای lab / Restricted lab mapping

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

این فقط port mapping رو نشان می‌ده؛ password رو reuse نکن، image/version و مجوز رو برای محیط خودت بررسی کن و volume/resource limit رو هم در استقرار واقعی تنظیم کن.

This only illustrates mapping. Never reuse the sample password; validate image/version licensing and configure volumes/resource limits for a real deployment.

ارتباط serviceها رو private نگه دار / Keep service traffic private

در Compose، web با hostname سرویس db به port داخلی وصل می‌شه و port دیتابیس publish نمی‌شه. سلامتcheck/connection retry آمادگی SQL رو ثابت می‌کنه؛ start شدن container کافی نیست. داده رو در volume نگه دار تا recreate کردن container اون رو حذف نکند.

In Compose, web connects to the db service hostname and internal port without publishing the database. Healthchecks/connection retries prove SQL readiness; container start alone is insufficient. Persist data in a volume so container recreation does not erase it.

از نزدیک‌ترین لایه شروع کن / Start at the nearest layer

container state، engine سلامت، listener، Docker network، published port، DNS و firewall رو به‌ترتیب بسنج. TCP success هنوز login، TLS یا مجوز query رو ثابت نمی‌کنه. خطا رو با layer خودش تطبیق بده.

Check container state, engine health, listener, Docker network, published port, DNS, and firewall in order. TCP success does not prove login, TLS, or query permission. Match the error to its layer.

port container با port host یکی نیست / Container and host ports differ

service DNS و port داخلی برای ارتباط شبکهٔ Docker است؛ mapping مسیر host رو می‌سازه؛ client دور به DNS و firewall هم نیاز داره. بعد readiness، TLS و login رو جدا بررسی می‌کنیم. فصل بعد به certificate و encryption اتصال می‌رسه.

Service DNS and the internal port serve Docker peers; mapping creates a host path; remote clients also need DNS and firewall access. Readiness, TLS, and login are separate checks. Next we configure certificates and connection encryption.
