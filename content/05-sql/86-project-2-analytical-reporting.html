پروژهٔ ۲ — گزارشی که سریع هست و درست

Project 2 — analytics that are correct and fast

مدیر فروش سه گزارش می‌خواد: فروش ماهانه، top محصولات هر منطقه و میانگین متحرک مشتری. query اولیه کند هست و نتیجه با join اشتباه چندبرابر شده. مأموریت: خروجی درست بساز، cardinality رو ثابت کن و فقط بعد از شواهد سراغ index/plan برو.

A sales manager needs monthly sales, top products per region, and a customer moving average. The first query is slow and a bad join multiplies totals. Build correct outputs, prove cardinality, then tune only with evidence.

سناریو و حدود پروژه / Scenario and scope

از schema Project 1 یا دادهٔ تمرینی مستقل Project86 استفاده کن. دیتاست رو با generator محدود و reproducible بساز؛ seed و تعداد ردیف‌ها رو ثبت کن. تمرکز با query است، نه داشبورد یا application. هر report باید تعریف business metric، بازهٔ زمانی، NULL policy و tie-breaking روشن داشته باشه.

Use Project 1 schema or an isolated Project86 fixture. Generate bounded reproducible data and record seed/row counts. This is a SQL project, not a dashboard/application build. Every report needs explicit metric, time range, NULL policy, and tie-breaking semantics.

این پروژه فقط «گزارش بساز» نیستThis project is more than “build a report”

سناریو اینه: تیم محصول یه گزارش می‌خواد که هم عددش درست باشه هم وقتی داده بزرگ شد زمین‌گیر نشه. اول نسخهٔ ساده رو می‌سازی و درستی رو روی دادهٔ کم ثابت می‌کنی. بعد حجم رو بالا می‌بری، plan رو می‌خونی و تازه اون موقع سراغ index یا بازنویسی می‌ری. هدف این نیست که از همون اول query «باهوش» بنویسی؛ هدف اینه که مسیر تصمیم‌گیریت قابل‌دفاع باشه.

The product team needs a report that is correct and still usable at scale. Build the simple version first and prove correctness on small data. Then scale the data, inspect the plan, and only then consider indexes or rewrites. The goal is not clever SQL from the beginning; it is a defensible tuning process.

دو خروجی اجباریTwo required outputs

نسخهٔ قبل و بعد رو نگه دار: query، زمان/reads مناسب، plan و توضیح کوتاه. بدون مقایسه، «سریع‌تر شد» فقط یه حسه.

Keep before-and-after evidence: query, suitable time/reads, plan, and a short explanation. Without comparison, “it got faster” is only a feeling.

مراحل ساخت / Milestones

  1. دادهٔ تمرینی فروشگاهی reproducible و تعداد ردیف‌ها رو بساز. / Build a reproducible sales fixture and record counts.
  2. هر report رو بدون tuning بنویس و expected نتیجه رو با query مرجع تطبیق بده. / Write each report untuned and compare with a reference query.
  3. join fan-out و duplicate رو با کلیدها/aggregateهای میانی بررسی کن. / Inspect join fan-out and duplicates through keys/intermediate aggregates.
  4. Actual Plan، logical reads، elapsed time و estimates رو خط پایه بگیر. / Capture baseline plan, logical reads, elapsed time, estimates.
  5. فقط یک تغییر query/index در هر iteration بده و همان بار کاری رو دوباره بسنج. / Change one query/index factor per iteration and rerun the same workload.
  6. index غیرضروری رو حذف و صحت نهایی رو از ابتدا بررسی کن. / Remove unnecessary indexes and rerun correctness checks from scratch.

معیار پذیرش / Acceptance criteria

  • ماه‌های خالی و timezone/date boundary طبق قرارداد تعریف شده‌اند. / Empty months and time boundaries follow a documented contract.
  • Top-N tie behavior قطعی هست و window frame برای moving average روشن هست. / Top-N ties are deterministic and moving-average frame is explicit.
  • total هر report با query مستقل قابل تطبیق هست. / Each report total reconciles with an independent query.
  • execution plan پیش و پس از تغییر حفظ و تغییر operator/estimate توضیح داده شده هست. / Before/after plans are saved and operator/estimate changes explained.
  • اندازه‌گیری با تعداد ردیف، cache و شرایط یکسان انجام شده؛ یک timing منفرد مبنا نیست. / Measurements use consistent rows/cache conditions; one timing is not proof.
  • indexها با read benefit و write/storage cost توجیه شده‌اند. / Indexes are justified by read benefit and write/storage cost.

راهنمایی‌های بازشونده / Collapsible hints

total چندبرابر شده؛ اول کجا رو ببینم؟ / Totals multiplied—where first?

کلید join و تعداد ردیف هر سمت رو پیش از join aggregate کن. یک order با چند line و چند payment بعد از join ممکنه cross multiplication بسازد.

Check join keys and row counts per side before joining. Multiple lines and payments per order can multiply one another.

یک index اضافه کنم؟ / Should I add an index?

پیش از تغییر، operator، predicate، key order، reads و write pattern رو بخوان. missing-index suggestion تنها hypothesis هست.

Inspect operators, predicates, key order, reads, and write pattern first. A missing-index suggestion is only a hypothesis.

چطور زمان رو مقایسه کنم؟ / How do I compare timings?

query، row count و conditions رو ثابت نگه دار؛ چندبار اجرا کن و cache/cold run رو تفکیک کن. درستی قبل از performance هست.

Hold query, row count, and conditions steady; repeat runs and distinguish cache states. Correctness comes before performance.

الگوی مرجع محاسبه / Reference query patterns

قالب‌ها رو با schema خود تطبیق بده. اون‌ها جای تعریف metric و validation رو نمی‌گیرند.

Adapt these patterns to your schema; they do not replace metric definitions or validation.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

ماهانه و top-N / Monthly aggregate and top-N
SELECT DATEFROMPARTS(YEAR(o.CreatedAt),MONTH(o.OrderDate),1) AS MonthStart,
       COUNT(DISTINCT o.OrderId) AS Orders,
       SUM(ol.Quantity*ol.UnitPrice) AS Sales
FROM Project85.SalesOrder AS o
JOIN Project85.OrderLine AS ol ON ol.OrderId=o.OrderId
 GROUP BY DATEFROMPARTS(YEAR(o.CreatedAt),MONTH(o.CreatedAt),1)
ORDER BY MonthStart;

WITH ProductSales AS (
 SELECT o.CustomerId,l.ProductId,SUM(l.Quantity*l.UnitPrice) AS Sales
 FROM Project85.SalesOrder AS o
 JOIN Project85.OrderLine AS l ON l.OrderId=o.OrderId
 GROUP BY o.CustomerId,l.ProductId
), Ranked AS (
 SELECT *,DENSE_RANK() OVER(PARTITION BY CustomerId ORDER BY Sales DESC) AS rnk
 FROM ProductSales
)
SELECT CustomerId,ProductId,Sales,rnk FROM Ranked WHERE rnk<=3;

WITH DailySales AS (
 SELECT o.CustomerId,CONVERT(date,o.CreatedAt) AS SalesDay,
        SUM(l.Quantity*l.UnitPrice) AS Sales
 FROM Project85.SalesOrder AS o
 JOIN Project85.OrderLine AS l ON l.OrderId=o.OrderId
 GROUP BY o.CustomerId,CONVERT(date,o.CreatedAt)
)
SELECT CustomerId,SalesDay,Sales,
 AVG(Sales) OVER(PARTITION BY CustomerId ORDER BY SalesDay
   ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS MovingAverage7Rows
FROM DailySales
ORDER BY CustomerId,SalesDay;

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

Top-N عمداً tieها رو نگه می‌داره؛ اگه دقیقاً سه ردیف می‌خوای، ROW_NUMBER با ترتیب پایدار و قاعدهٔ tie انتخاب کن. MovingAverage7Rows میانگین ۷ ردیف موجود است، نه الزاماً ۷ روز تقویمی؛ برای روزهای خالی باید تقویم روزانه بسازی.

Top-N intentionally retains ties; use ROW_NUMBER with stable order and a tie rule for exactly three rows. MovingAverage7Rows averages seven existing rows, not necessarily seven calendar days; fill a date calendar to include empty days.

اول قرارداد گزارش رو بنویسWrite the report contract first

قبل از tuning معلوم کن هر report دقیقاً چه grainی داره. «فروش ماهانه» یعنی یک ردیف برای هر ماه؟ برای هر ماه و منطقه؟ برگشتی‌ها کم می‌شن یا جدا گزارش می‌شن؟ سفارش لغوشده چی؟ تا این سؤال‌ها روشن نباشن، سریع‌ترین query دنیا هم ممکنه عدد غلط بده. برای هر گزارش نمونهٔ خروجی پنج‌ردیفی بنویس و با دست حسابش کن.

Before tuning, define the exact grain of every report. Does “monthly sales” mean one row per month, or per month and region? Are returns subtracted or reported separately? What about cancelled orders? Until those rules are explicit, the fastest query can still be wrong. Write a five-row expected result and calculate it by hand.

قاعدهٔ این پروژهProject rule

اول درستی، بعد performance. اگه قبل از ثابت‌کردن عددها index بسازی، ممکنه فقط جواب غلط رو سریع‌تر تحویل بدی.

Correctness first, performance second. An index added before validating the numbers may simply return the wrong answer faster.

همون query رو روی سه اندازهٔ داده ببینRun the same query at three data scales

گزارش رو اول روی دادهٔ تمرینی کوچیک اجرا کن تا خروجی با چشم قابل‌بررسی باشه. بعد ۱۰ هزار و ۱ میلیون ردیف بساز و همون query رو دوباره اجرا کن. برای هر مرحله حداقل elapsed time و logical reads مناسب رو ثبت کن و plan رو ذخیره کن. اگه اختلافی ندیدی، قبل از نتیجه‌گیری cache و اندازهٔ داده رو بررسی کن.

Run the report first on a tiny fixture where the result can be inspected manually. Then generate 10K and 1M rows and run the same query again. Capture at least suitable elapsed time/logical reads and save the plan at each scale. If nothing changes, check cache effects and whether the dataset is large enough before concluding.

Measure before changing anything / قبل از هر تغییر اندازه بگیر
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- Run the original report here.

SET STATISTICS TIME OFF;
SET STATISTICS IO OFF;

این دو SET جواب performance رو به‌تنهایی نمی‌دن؛ فقط بخشی از شاهدن. actual execution plan و تعداد ردیف واقعی رو هم کنار اون‌ها نگه دار.

These SET options do not answer the performance question by themselves; they are only part of the evidence. Keep the actual execution plan and real row counts beside them.

هر بار فقط یک چیز رو عوض کنChange one thing at a time

ممکنه هم JOIN اشتباه داشته باشی، هم predicate غیر SARGable، هم index ناقص. همه رو باهم درست نکن. نسخهٔ صفر رو نگه دار، یک فرضیه انتخاب کن، تغییر رو اعمال کن و دوباره اندازه بگیر. اگه بهتر شد دلیلش رو از plan و reads توضیح بده. اگه فرقی نکرد، تغییر رو برگردون و فرضیهٔ بعدی رو امتحان کن.

The report may have a bad join, a non-SARGable predicate, and a weak index at the same time. Do not fix all three together. Keep version zero, choose one hypothesis, make one change, and measure again. If it improves, explain why using the plan and reads. If not, revert and test the next hypothesis.

  • آیا join fan-out و duplicate کنترل شده است؟ / Are join fan-out and duplicates controlled?
  • آیا درستی قبل/بعد tuning ثابت مانده؟ / Is correctness proven before and after tuning?
  • آیا plan و measurement شرایط قابل‌مقایسه دارن؟ / Are plans and measurements comparable?
  • آیا index write cost و storage رو هم حساب می‌کنه؟ / Does index review include write cost/storage?
  • آیا اسکریپت از صفر و بدون cleanup خطرناک اجرا می‌شه؟ / Does the project run from scratch without unsafe cleanup?

گزارش خوب فقط سریع نیست؛ خروجی‌اش تعریف‌شده، قابل‌تکرار و قابل‌ممیزی هست.

A good report is not merely fast; its output is defined, reproducible, and reviewable.
