FULL OUTER JOIN؛ پیدا کردن اختلاف دو سمت

FULL OUTER JOIN: reconcile both sides

دو سامانه فهرست کالا دارن؛ یکی از اون‌ها تازه به‌روزرسانی شده و تیم می‌خواد بداند چه چیزهایی match هستن و چه چیزهایی فقط در یکی از دو طرف مانده‌اند. INNER JOIN موارد یک‌طرفه رو پنهان می‌کنه و LEFT JOIN فقط یک سمت رو کامل نگه می‌داره. برای تطبیق دوطرفه سراغ FULL OUTER JOIN می‌رویم.

Two systems have product lists. One was recently updated, and the team needs to know what matches and what exists on only one side. INNER JOIN hides one-sided rows; LEFT JOIN preserves only one side. For a two-sided reconciliation, we use FULL OUTER JOIN.

اول تعداد ردیف‌ها رو حدس بزنPredict the row count first

گزارش سفارش‌ها معمولاً از جایی سخت می‌شه که یک جدول دیگه وارد ماجرا می‌شه. سه سفارش داری، چهار مشتری داری، پنج ردیف سفارش هم داری؛ حالا JOIN می‌زنی و ناگهان خروجی دوازده ردیف می‌شه. توی «FULL OUTER JOIN؛ پیدا کردن اختلاف دو سمت» قبل از هر query اول حدس می‌زنیم چند ردیف باید برگرده، بعد اجرا می‌کنیم و از روی اختلاف حدسمون با واقعیت می‌فهمیم رابطه‌ها رو درست خوندیم یا نه.

Reports get interesting the moment another table enters the picture. You may have three orders, four customers, and five order lines, then a join suddenly returns twelve rows. In “FULL OUTER JOIN: reconcile both sides” we predict row counts before executing, then use any mismatch to diagnose our understanding of the relationships.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

دو فهرست، سه وضعیت / Two lists, three possible outcomes

قبل از query، یک دادهٔ تمرینی کوچک می‌سازیم: کلید ۲ در هر دو منبع هست، ۱ فقط در SourceA و ۳ فقط در SourceB. FULL OUTER JOIN هر سه وضعیت رو نگه می‌داره. جدول‌های موقت‌اند؛ دادهٔ تمرینی اصلی دوره دست‌نخورده می‌مونه.

Before querying, create a small fixture: key 2 exists on both sides, 1 only in SourceA, and 3 only in SourceB. FULL OUTER JOIN preserves all three cases. These are temporary tables; the course fixture stays untouched.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

سه وضعیت تطبیق / Three reconciliation states
DROP TABLE IF EXISTS #SourceA, #SourceB;
CREATE TABLE #SourceA (Code int PRIMARY KEY, AValue varchar(20) NOT NULL);
CREATE TABLE #SourceB (Code int PRIMARY KEY, BValue varchar(20) NOT NULL);
INSERT #SourceA VALUES (1, 'old'), (2, 'same-key');
INSERT #SourceB VALUES (2, 'new'), (3, 'new-only');

SELECT COALESCE(a.Code, b.Code) AS Code, a.AValue, b.BValue
FROM #SourceA AS a
FULL OUTER JOIN #SourceB AS b ON b.Code = a.Code
ORDER BY COALESCE(a.Code, b.Code);
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

کلید matchشده در هر دو ستون هست؛ ردیف فقط-A ستون‌های B رو NULL داره و ردیف فقط-B ستون‌های A رو NULL. `COALESCE` اولین مقدار غیرNULL رو برمی‌گردونه تا کلید خروجی برای هر سه حالت دیده بشه.

The matched key appears on both sides. An A-only row has NULL B columns; a B-only row has NULL A columns. COALESCE returns the first non-NULL value so the output key is visible in all three cases.

از NULL برای طبقه‌بندی استفاده کن، نه برای حدس / Use NULL to classify, not to guess

برای گزارش مغایرت، مشخص می‌کنیم کدوم ورودی match نداشته. ستون انتخابی برای آزمون باید در ردیف واقعی NOT NULL باشه؛ در دادهٔ تمرینی، کلید اصلی این شرط رو داره. بعد می‌تونیم فقط موارد یک‌طرفه رو جدا کنیم یا همهٔ ردیف‌ها رو با label نگه داریم.

For a discrepancy report, identify which input did not match. The tested column must be NOT NULL in real rows; here, the primary key qualifies. Then we can isolate one-sided rows or label every row.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

label برای هر وضعیت / Label each outcome
SELECT COALESCE(a.Code, b.Code) AS Code,
       a.AValue, b.BValue,
       CASE
           WHEN a.Code IS NULL THEN 'Only in B'
           WHEN b.Code IS NULL THEN 'Only in A'
           ELSE 'Matched'
       END AS MatchStatus
FROM #SourceA AS a
FULL OUTER JOIN #SourceB AS b ON b.Code = a.Code
ORDER BY Code;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

مقایسهٔ `a.Code = b.Code` داخل ON است؛ بعد از اتصال، IS NULL تشخیص می‌ده کدوم سمت match نشده. اگه کلیدها چندستونی‌اند، تمام اجزای رابطه رو در ON بیاور. اگه از مقدار nullable برای طبقه‌بندی استفاده کنی، ممکنه «مقدار خالی» رو با «ردیف matchنشده» اشتباه بگیری.

The key equality belongs in ON; after the join, IS NULL identifies the unmatched side. For a composite key, include every relationship component. Testing a nullable payload can confuse “missing row” with “present row whose value is NULL.”

FULL JOIN برای reconciliation؛ نه جایگزین همهٔ joinها / Use FULL JOIN for reconciliation, not as a default

اگه فقط فاکتورهای دارای customer می‌خوای، INNER JOIN مناسب‌تر هست. اگه همهٔ customerها باید بمانند، LEFT JOIN. FULL OUTER JOIN وقتی معنی داره که هر دو فهرست مستقل‌اند و موارد یک‌طرفه هم برای گزارش لازم‌اند؛ در غیر این صورت ممکنه خروجی و منطق NULLها بی‌دلیل پیچیده بشه.

For invoices with customers, INNER JOIN is more suitable. To preserve all customers, use LEFT JOIN. FULL OUTER JOIN makes sense when two independent lists must both be reconciled and one-sided rows matter; otherwise it can add unnecessary output and NULL complexity.

فقط اختلاف‌ها / Only discrepancies
SELECT COALESCE(a.Code, b.Code) AS Code, a.AValue, b.BValue
FROM #SourceA AS a
FULL OUTER JOIN #SourceB AS b ON b.Code = a.Code
WHERE a.Code IS NULL OR b.Code IS NULL
ORDER BY Code;

این filter فقط ردیف‌های یک‌طرفه رو نگه می‌داره. در کار واقعی، قبل از merge یا حذف، مقدارها و کلیدها رو بررسی کن؛ پیدا شدن اختلاف مجوز خودکار برای overwrite نیست.

This filter keeps only one-sided rows. In real work, inspect values and keys before merging or deleting; detecting a discrepancy does not authorize an automatic overwrite.
