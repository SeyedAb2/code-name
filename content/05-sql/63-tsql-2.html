T-SQL 2: errors and transaction boundaries

در پرداخت، statement دوم خطا داده؛ آیا اولی commit شده؟ پاسخ رو از متن پیام حدس نمی‌زنیم: transaction state و داده رو query می‌کنیم و خطا رو به caller می‌رسانیم.

A payment's second statement failed; did the first commit? We will inspect transaction state and data rather than guess from the message, and propagate the error to the caller.

A stored procedure or trigger can make a design cleaner, and the same feature can become mysterious hidden behaviour six months later. In “T-SQL 2: errors and transaction boundaries” we go beyond syntax: why should this logic live in SQL Server, how do we observe failures, and how do we avoid invisible side effects?

خطا بخشی از قرارداد هست / Errors are part of the contract

TRY/CATCH بسیاری از خطاهای زمان اجرا رو می‌گیره، نه هر compile error، قطع connection یا خطای بیرون از scope رو. در CATCH، ERROR_NUMBER، ERROR_MESSAGE، ERROR_LINE و XACT_STATE رو بررسی کن؛ secret رو به client یا log عمومی نده.

TRY/CATCH handles many runtime errors, not every compile error, lost connection, or error outside its scope. Inspect ERROR_NUMBER, ERROR_MESSAGE, ERROR_LINE, and XACT_STATE; do not expose secrets to clients or public logs.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

rollback و انتقال خطا / Roll back and propagate
SET XACT_ABORT ON;
BEGIN TRY
 BEGIN TRAN;
 UPDATE dbo.Account SET Balance=Balance-10 WHERE AccountId=1;
 IF @@ROWCOUNT<>1 THROW 50010,'Debit rejected.',1;
 UPDATE dbo.Account SET Balance=Balance+10 WHERE AccountId=2;
 IF @@ROWCOUNT<>1 THROW 50011,'Credit rejected.',1;
 COMMIT;
END TRY
BEGIN CATCH
 SELECT ERROR_NUMBER() AS ErrorNumber,XACT_STATE() AS TransactionState;
 IF XACT_STATE()<>0 ROLLBACK;
 THROW;
END CATCH;

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

فقط در دادهٔ آزمایشی و قابل‌حذف اجرا کن. اگه CATCH پیام رو فقط SELECT کند و خطا رو دوباره پرتاب نکند، caller ممکنه موفقیت جعلی ببیند.

Use disposable rows. If CATCH only selects a message and does not rethrow, the caller may see false success.

XACT_STATE و @@TRANCOUNT فرق دارن / XACT_STATE differs from @@TRANCOUNT

XACT_STATE مقدار ۱ رو برای transaction قابل commit، صفر رو برای نبود transaction و منفی یک رو برای transaction غیرقابل commit می‌ده. @@TRANCOUNT فقط nesting count رو می‌گه؛ قابلیت commit رو ثابت نمی‌کنه. هر دو رو در خرابی path ببین و مالکیت transaction رو تعریف کن.

XACT_STATE returns 1 for a committable transaction, 0 for none, and -1 for an uncommittable one. @@TRANCOUNT is a nesting count, not proof that commit is possible. Inspect both and define transaction ownership.

XACT_ABORT کمک می‌کنه، اما همه‌چیز رو حل نمی‌کنه / XACT_ABORT helps, but does not solve everything

با XACT_ABORT ON بسیاری از runtime errorها transaction رو abort می‌کنن؛ رفتار دقیق رو با خطا و driver هدف تست کن. THROW و RAISERROR در تعامل با این تنظیم یکسان نیستند. savepoint نمی‌تونه transaction غیرقابل commit رو نجات دهد.

With XACT_ABORT ON, many runtime errors abort the transaction; test the exact error and driver. THROW and RAISERROR do not interact identically with the setting. A savepoint cannot rescue an uncommittable transaction.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

وضعیت پیش و پس از خطا / State before and after
SELECT @@TRANCOUNT AS BeforeCount,XACT_STATE() AS BeforeState;
BEGIN TRY
 BEGIN TRAN;
 SELECT 1/0;
 COMMIT;
END TRY
BEGIN CATCH
 SELECT ERROR_NUMBER() AS Err,@@TRANCOUNT AS TranCount,XACT_STATE() AS XState;
 IF XACT_STATE()<>0 ROLLBACK;
END CATCH;
SELECT @@TRANCOUNT AS AfterCount,XACT_STATE() AS AfterState;

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

retry فقط برای خطای گذرا / Retry only transient failures

خطای deadlock 1205 ممکنه retry محدود بخواهد، اما فقط اگه operation idempotent و backoffدار باشه. validation، duplicate key و permission با retry درست نمی‌شن. timeout client هم ثابت نمی‌کنه transaction سرور متوقف شده؛ قبل از تکرار وضعیت رو بررسی کن.

Deadlock error 1205 may merit a bounded retry, but only for idempotent work with backoff. Validation, duplicate-key, and permission failures are not fixed by retries. A client timeout does not prove the server transaction stopped; inspect before repeating.
