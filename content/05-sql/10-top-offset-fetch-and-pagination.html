TOP، OFFSET/FETCH و صفحه‌بندی

TOP, OFFSET/FETCH, and pagination

گزارش محصولات هزاران ردیف داره، اما صفحه فقط ده‌تا رو نشان می‌ده. تیم می‌گه «ده ردیف اول رو بده»؛ سؤال اینه: اولِ کدوم ترتیب؟ اینجا تعداد ردیف و جای صفحه رو از قرارداد مرتب‌سازی جدا می‌کنیم.

A report contains thousands of rows, but the screen shows ten at a time. “Give me the first ten” is incomplete: first according to which order? We will separate page size and offset from the ordering contract.

از یک سؤال واقعی شروع کنیمStart with a real question

یه همکار تازه‌وارد معمولاً SQL رو از روی syntax حفظ می‌کنه؛ ولی چند روز بعد که گزارش واقعی می‌رسه، نمی‌دونه از کجا شروع کنه. اینجا برعکس می‌ریم. اول سؤال گزارش رو روشن می‌کنیم، بعد برای «TOP، OFFSET/FETCH و صفحه‌بندی» query می‌نویسیم، خروجی رو نگاه می‌کنیم و اگه چیزی عجیب بود از روی همون نتیجه می‌فهمیم کجای مدل ذهنی‌مون ایراد داره.

A newcomer often memorises SQL syntax, then gets stuck on the first real report. We do the opposite: clarify the reporting question, use “TOP, OFFSET/FETCH, and pagination” to answer it, inspect the result, and use any surprise as evidence that our mental model needs work.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

ده ردیف اول، بدون ترتیب یعنی چه؟ / What does “first ten” mean without an order?

فرض کن برنامه برای صفحهٔ اول، ده محصول می‌خواد. اگه query فقط TOP (10) داشته باشه، تعداد رو محدود کرده‌ایم؛ اما نگفته‌ایم کدوم ده محصول. اگه ترتیب گزارش مهمه، کلید مرتب‌سازی رو صریح می‌نویسیم و tieها رو هم می‌شکنیم.

Suppose the application needs ten products for its first page. TOP (10) limits the count, but does not say which ten. If the report order matters, specify it and break ties.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

تعداد محدود، بدون قرارداد ترتیب / A row limit without an ordering contract
SELECT TOP (3) ProductId, ProductName, UnitPrice
FROM shop.Products;
GO

SELECT TOP (3) ProductId, ProductName, UnitPrice
FROM shop.Products
ORDER BY UnitPrice DESC, ProductId ASC;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

query اول فقط سقف سه ردیف رو می‌گه؛ روی این‌که کدوم سه‌تا باشند یا به چه ترتیبی برگردند حساب نکن. query دوم گران‌ترین‌ها رو می‌خواد و ProductId تساوی قیمت رو می‌شکند. TOP جای ORDER BY رو نمی‌گیره.

The first query caps the result at three rows, but promises neither which rows nor their order. The second requests the most expensive products and uses ProductId to break price ties. TOP does not replace ORDER BY.

TOP برای سقف تعداد است، نه شمارهٔ صفحه / TOP limits a count, not a page number

TOP وقتی مناسب هست که واقعاً یک بخش کوتاه می‌خوای: مثلاً پنج سفارش تازه. مرتب‌سازی باید معنای «تازه» رو مشخص کند. جهت و یک کلید یکتا رو نگه دار تا سفارش‌های هم‌زمان نتیجه رو مبهم نکنند.

TOP is useful when you need one short slice, such as the five newest orders. Ordering defines “newest.” Include a unique key so equal timestamps do not leave the result ambiguous.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

پنج سفارش تازه، با شکستن تساوی / Five newest orders with a tie-breaker
SELECT TOP (5) OrderId, OrderedAt, OrderStatus
FROM shop.Orders
ORDER BY OrderedAt DESC, OrderId DESC;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

در دادهٔ کوچک Shop شاید فقط چهار سفارش ببینی؛ محدودیت TOP حداقل تعداد تضمین‌شده نیست. اگه می‌خوای هر ردیفی که با ردیف مرزی در قیمت مساوی هست هم بیاید، WITH TIES رفتار دیگری داره.

The small Shop fixture may return only four orders; TOP is a maximum, not a promise that this many rows exist. WITH TIES changes the boundary behavior when rows share the last sort value.

WITH TIES می‌تونه بیشتر از N ردیف برگرداند / WITH TIES can return more than N rows
DROP TABLE IF EXISTS #TiePrices;
CREATE TABLE #TiePrices
(
    ItemId int NOT NULL PRIMARY KEY,
    ItemName nvarchar(30) NOT NULL,
    Price decimal(8,2) NOT NULL
);
INSERT INTO #TiePrices (ItemId, ItemName, Price)
VALUES (1, N'A', 100), (2, N'B', 90), (3, N'C', 90), (4, N'D', 80);

SELECT TOP (2) WITH TIES ItemId, ItemName, Price
FROM #TiePrices
ORDER BY Price DESC;
GO

چون ردیف دوم و سوم قیمت ۹۰ دارن، هر سه ردیف اول برمی‌گردند. WITH TIES به آخرین کلید ORDER BY نگاه می‌کنه؛ اگه ItemId رو هم به ORDER BY اضافه کنی، قیمت مساوی دیگر tie کامل نیست و ممکنه فقط دو ردیف بگیری. جدول موقت فقط برای همین نشست هست.

The second and third rows both cost 90, so all three boundary rows are returned. WITH TIES considers the complete ORDER BY key: adding ItemId makes those rows distinct in sort order and can reduce the result to two. The fixture is session-local.

OFFSET/FETCH می‌گه از کجا بخوان / OFFSET/FETCH says where to start

برای صفحه‌بندی شماره‌دار، OFFSET تعداد ردیف‌هایی رو که رد می‌کنی می‌گیره و FETCH اندازهٔ صفحه رو. این دستور در SQL Server به ORDER BY نیاز داره. اگه ترتیب یکتا نباشه، صفحه‌ها مرز قابل‌اتکایی ندارن.

For numbered pages, OFFSET is how many rows to skip and FETCH is the page size. SQL Server requires ORDER BY here. Without a unique order, page boundaries are not dependable.

صفحهٔ اول و دوم محصولات / First and second product pages
DECLARE @PageSize int = 2;
DECLARE @PageNumber int = 1;
DECLARE @Offset int = (@PageNumber - 1) * @PageSize;

SELECT ProductId, ProductName, UnitPrice
FROM shop.Products
ORDER BY ProductName ASC, ProductId ASC
OFFSET @Offset ROWS FETCH NEXT @PageSize ROWS ONLY;
GO

SET @PageNumber = 2;
SET @Offset = (@PageNumber - 1) * @PageSize;
SELECT ProductId, ProductName, UnitPrice
FROM shop.Products
ORDER BY ProductName ASC, ProductId ASC
OFFSET @Offset ROWS FETCH NEXT @PageSize ROWS ONLY;
GO

برای صفحهٔ یک offset صفر است؛ صفحهٔ دو، دو ردیف رو رد می‌کنه. فرمول رو با شمارهٔ صفحهٔ یک‌مبنا نوشته‌ایم، پس PageNumber باید حداقل ۱ و PageSize باید مثبت باشه. FETCH تعداد درخواستی است، نه تضمین وجود آن تعداد.

Page one has offset zero; page two skips two rows. This one-based formula requires PageNumber ≥ 1 and PageSize > 0. FETCH requests a maximum slice; it cannot create rows that do not exist.

مرتب‌سازی یکتا باید؛ اما تغییر داده هنوز می‌تونه صفحه رو جابه‌جا کند / Unique ordering helps, but changing data can still shift pages

فرض کن کاربر صفحهٔ اول رو گرفته و قبل از رفتن به صفحهٔ دوم، سفارش تازه‌ای درج بشه. OFFSET صفحهٔ دوم رو از موقعیت عددی تازه می‌خونه؛ در نتیجه ممکنه یک ردیف تکرار یا جاافتاده به نظر برسد. tie-breaker ابهام ترتیب ثابت رو حل می‌کنه، نه تغییر داده میان دو درخواست رو.

Suppose a user loads page one, then a new order is inserted before they request page two. OFFSET reads from the new numeric position, so a row may appear twice or be skipped. A tie-breaker solves ambiguous ordering, not changes between requests.

دو صفحهٔ متوالی رو با یک ترتیب کامل تعریف کن / Define each page with a complete order
DECLARE @PageSize int = 3;
DECLARE @PageNumber int = 1;
SELECT OrderId, OrderedAt, OrderStatus
FROM shop.Orders
ORDER BY OrderedAt DESC, OrderId DESC
OFFSET (@PageNumber - 1) * @PageSize ROWS
FETCH NEXT @PageSize ROWS ONLY;
GO

در گزارش‌های زنده، باید دربارهٔ سازگاری نمونهٔ لحظه‌ای یا روش ادامه از آخرین کلید تصمیم بگیریم؛ اون‌ها trade-off و طراحی جدا دارن و صرفاً با اضافه‌کردن OFFSET حل نمی‌شن. صفحه‌های خیلی عمیق هم ممکنه هزینه‌مند شوند، چون موتور باید از ردیف‌های ردشده عبور کند؛ اندازه‌گیری و index رو در فصل‌های performance دنبال می‌کنیم.

Live feeds may need snapshot consistency or continuation from the last key; those are separate design trade-offs, not fixed by adding OFFSET. Deep offsets can also be costly because skipped rows still have to be traversed. We will measure and index such workloads in the performance chapters.

سه پرسش جدا، سه بخش از query / Three separate questions in one query

این‌ها رو یکی نکن: ORDER BY می‌گه کدوم‌ها جلو هستن، OFFSET جای شروع رو می‌ده و TOP/FETCH سقف تعداد رو. اگه داده در میانهٔ کار عوض بشه، قرارداد صفحه‌بندی باید اون رو هم در نظر بگیرد.

Keep these questions separate: ORDER BY defines precedence, OFFSET chooses a starting position, and TOP/FETCH caps the count. If data changes mid-navigation, the pagination design must account for that too.

قبل از بستن ticket / Before closing the ticket

اگه فقط یک نکته یادت بمونه: TOP یا FETCH تعداد رو محدود می‌کنه؛ ORDER BY می‌گه کدوم ردیف‌ها جلو هستن. برای صفحه‌بندی قابل‌اتکا، ترتیب رو تا کلید یکتا کامل کن. این کار جلوی ابهام رو می‌گیره، نه لزوماً جابه‌جایی ناشی از تغییر داده بین دو درخواست رو.

Remember: TOP or FETCH limits a count; ORDER BY defines which rows come first. For dependable pagination, complete the order through a unique key. This removes ambiguity, but does not by itself prevent shifts caused by changes between requests.

  • TOP بدون ORDER BY: تعداد محدود، انتخاب و ترتیب بی‌قرارداد.
  • WITH TIES: بر اساس تمام کلیدهای ORDER BY ممکنه بیش از N ردیف دهد.
  • OFFSET/FETCH: نقطهٔ شروع و اندازهٔ صفحه؛ به ORDER BY نیاز داره.
  • ترتیب یکتا ≠ نمونهٔ لحظه‌ای ثابت در چند درخواست.
