Denormalization آگاهانه؛ تکرار با دلیل و قاعده

Deliberate denormalization: redundancy with a rule

نرمال‌سازی تکرار واقعیت رو کم کرد، اما داشبورد فروش برای هر بار نمایش چند join و aggregate می‌زند. تیم پیشنهاد می‌ده نام مشتری و جمع خرید رو کنار هم cache کند. این ممکنه خواندن رو ساده کند؛ اما چه کسی آن مقدار رو به‌روز نگه می‌داره؟

Normalization reduced repeated facts, but a dashboard performs joins and aggregation on every request. The team proposes caching customer name and spend together. That may simplify reads—but who keeps the copy current?

پیش‌نیاز: نرمال‌سازی و aggregate · Prerequisites: Chapters 19 and 33SQL Server 2025 · T-SQLحدود ۸۵ دقیقه · ۱۸ تمرین / About 85 minutes · 18 exercises

تصمیمی که امروز کوچیکه، فردا توی هر query دیده می‌شهA small schema decision today appears in every query tomorrow

وقتی جدول فقط ده ردیف داره، تقریباً هر طراحی‌ای «کار می‌کنه». دردش چند ماه بعد معلوم می‌شه؛ وقتی داده تکراری شده، constraint نداری یا یه نوع داده اشتباه همهٔ queryها رو پیچیده کرده. توی «Denormalization آگاهانه؛ تکرار با دلیل و قاعده» قرار نیست فقط DDL بنویسیم؛ می‌خوایم بفهمیم هر تصمیم چه قانونی رو وارد خود دیتابیس می‌کنه و هزینهٔ اون تصمیم بعداً کجاست.

With ten rows, almost any design seems to work. The cost appears months later when data is duplicated, constraints are missing, or a poor data type infects every query. In “Deliberate denormalization: redundancy with a rule” we are not merely writing DDL; we are deciding which rules the database itself enforces and what those choices cost later.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

اول هزینهٔ query رو اندازه بگیر / Measure before adding a copy

denormalize رو برای «شاید سریع بشه» انجام نمی‌دهیم. query منبع، تعداد ردیف، زمان و actual execution plan رو ثبت کن. اگه کندی از نبود index یا شرط نامناسب است، تکرار داده مشکل رو پنهان می‌کنه و هزینهٔ نوشتن رو بالا می‌برد.

Do not denormalize because it “might be faster.” Record source query, row count, timing, and actual plan. If the real issue is a missing index or poor predicate, duplicated data hides the cause and increases write cost.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

مرجع درست رو نگه دار / Keep the normalized query as the reference
SELECT c.CustomerId, c.CustomerCode,
       SUM(oi.Quantity * oi.UnitPriceAtSale) AS LifetimeSpend
FROM shop.Customers AS c
JOIN shop.Orders AS o ON o.CustomerId=c.CustomerId
JOIN shop.OrderItems AS oi ON oi.OrderId=o.OrderId
WHERE o.OrderStatus=N'Paid'
GROUP BY c.CustomerId, c.CustomerCode;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

این query تعریف معیار LifetimeSpend رو مشخص می‌کنه: فقط سفارش Paid و جمع مبلغ lineها. هر projection تکراری باید دقیقاً همین تعریف رو دنبال کند؛ وگرنه دو صفحهٔ محصول عددهای متفاوتی می‌گن.

This query defines LifetimeSpend: paid orders only, summed from order lines. Any duplicated projection must preserve this definition or different screens will disagree.

یک read model کوچک بساز / Build a small read model

برای نمایش پرتکرار می‌تونیم خروجی رو در جدول جدا نگه داریم. نامش رو طوری می‌گذاریم که معلوم باشه projection است، نه منبع حقیقت. در این دادهٔ تمرینی فقط یک بار با query منبع پرش می‌کنیم؛ این هنوز راه refresh در production نیست.

A frequently read report can be stored in a separate table. Name it as a projection, not the source of truth. This fixture populates it once; it is not yet a production refresh strategy.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

ساخت و پرکردن projection آزمایشی / Create and populate a disposable projection
DROP TABLE IF EXISTS #CustomerSpendRead;
CREATE TABLE #CustomerSpendRead
(
  CustomerId int NOT NULL PRIMARY KEY,
  CustomerCode varchar(30) NOT NULL,
  LifetimeSpend decimal(18,2) NOT NULL,
  RefreshedAt datetime2(0) NOT NULL
);

INSERT #CustomerSpendRead (CustomerId, CustomerCode, LifetimeSpend, RefreshedAt)
SELECT c.CustomerId, c.CustomerCode,
       COALESCE(SUM(oi.Quantity * oi.UnitPriceAtSale), 0),
       SYSUTCDATETIME()
FROM shop.Customers AS c
LEFT JOIN shop.Orders AS o
  ON o.CustomerId=c.CustomerId AND o.OrderStatus=N'Paid'
LEFT JOIN shop.OrderItems AS oi ON oi.OrderId=o.OrderId
GROUP BY c.CustomerId, c.CustomerCode;

SELECT * FROM #CustomerSpendRead;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

LEFT JOIN باعث می‌شه مشتری بدون خرید هم در projection با صفر دیده بشه؛ این policy رو باید با تعریف گزارش هماهنگ کنیم. RefreshedAt می‌گه این نسخه چه زمانی محاسبه شده، اما خودش تازه‌بودن داده رو تضمین نمی‌کنه.

LEFT JOIN keeps customers without purchases and represents their spend as zero; align that policy with report semantics. RefreshedAt tells when the projection was computed, not whether it is current enough.

هر تکرار یک سؤال سازگاری می‌سازه / Every copy creates a consistency question

اگه order تازه درج یا Paid شد، LifetimeSpend چه زمانی تغییر می‌کنه؟ synchronous refresh داخل همان transaction خواندن رو تازه نگه می‌داره، اما نوشتن رو سنگین‌تر و خطاپذیرتر می‌کنه. refresh غیرهم‌زمان نرخ پردازش رو بهتر می‌کنه، ولی نمایش ممکنه موقتاً stale باشه. این انتخاب باید در قرارداد محصول روشن باشه.

When a new order is inserted or becomes Paid, when does LifetimeSpend change? Synchronous maintenance in the same transaction keeps reads fresh but makes writes heavier. Asynchronous refresh can improve throughput while allowing staleness. The product contract must choose.

مدل نگه‌داری / Maintenanceتازگی / Freshnessهزینه / Cost
محاسبه در هر query / Compute per queryاز منبع فعلی / Current sourceهزینهٔ خواندن / Read cost
به‌روزرسانی هم‌زمان / Synchronous updateهمراه commit / At commitنوشتن پیچیده‌تر / More write work
refresh دوره‌ای / Periodic refreshممکنه stale / May be staleپنجرهٔ تأخیر / Staleness window

هیچ‌کدوم رایگان نیست. اگه قرار هست projection دیر به‌روز بشه، UI و گزارش باید زمان refresh رو نشان دهند و تیم بداند چه میزان تأخیر قابل‌قبول هست.

None is free. If refresh is delayed, expose its timestamp and define an acceptable staleness window with the team.

projection رو با منبع تطبیق بده / Reconcile the projection with its source

دادهٔ تکراری ممکنه drift کند؛ پس query تطبیق لازم داریم. اختلاف رو قبل از repair گزارش کن. اگه projection رو بی‌مدرک با query منبع overwrite کنی، شاید نشانهٔ خطای مسیر نوشتن رو پاک کرده باشی.

A duplicated projection can drift, so build a reconciliation query. Report discrepancies before repair; blindly overwriting the projection may erase evidence of a broken write path.

مقایسهٔ مقدار خواندنی با محاسبهٔ مرجع / Compare the projection to its canonical query
;WITH Canonical AS
(
  SELECT c.CustomerId,
         COALESCE(SUM(CASE WHEN o.OrderStatus=N'Paid'
                           THEN oi.Quantity * oi.UnitPriceAtSale END), 0) AS ExpectedSpend
  FROM shop.Customers AS c
  LEFT JOIN shop.Orders AS o ON o.CustomerId=c.CustomerId
  LEFT JOIN shop.OrderItems AS oi ON oi.OrderId=o.OrderId
  GROUP BY c.CustomerId
)
SELECT p.CustomerId, p.LifetimeSpend, x.ExpectedSpend,
       p.LifetimeSpend-x.ExpectedSpend AS Difference
FROM #CustomerSpendRead AS p
JOIN Canonical AS x ON x.CustomerId=p.CustomerId
WHERE p.LifetimeSpend <> x.ExpectedSpend;
GO

خروجی خالی یعنی در همین لحظه و همین تعریف معیار اختلافی پیدا نشد؛ اثبات نمی‌کنه refresh بعدی درسته. برای این کار، درج/تغییر وضعیت سفارش رو در دادهٔ تمرینی انجام بده، projection رو طبق قاعده refresh کن و query تطبیق رو دوباره اجرا کن.

No rows means no discrepancy was found now under this definition; it does not prove the next refresh is correct. Change an order in the fixture, refresh according to the chosen rule, and run reconciliation again.

چه وقت denormalization منطقی است؟ / When is denormalization justified?

وقتی bottleneck اندازه‌گیری شده، read pattern تکراری و ارزشمند است، منبع حقیقت روشن است، و refresh و reconciliation طراحی شده‌اند، تکرار می‌تونه انتخاب خوبی باشه. اگه هنوز query پایه درست نیست یا نمی‌دانی stale بودن چه اثری داره، فعلاً مدل نرمال‌شده رو نگه دار.

Duplication can be justified when a measured bottleneck affects a valuable repeated read, the source of truth is clear, and refresh plus reconciliation are designed. If the base query is not correct or staleness impact is unknown, keep the normalized model.
