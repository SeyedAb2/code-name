بهینه‌سازی ۲: SARGable، OR و تابع روی ستون

Tuning 2: SARGability, OR, and functions on columns

index روی تاریخ داریم، اما query ماهانه scan می‌کنه. شرط این هست: `YEAR(CreatedAt)=2026`. آیا optimizer نمی‌فهمه؟ شاید بتواند در برخی شرایط تبدیل کند، اما تکیه بر حدس درست نیست. شکل predicate رو طوری می‌نویسیم که بازهٔ داده روشن باشه و بعد معنای مرزها و plan رو ثابت می‌کنیم.

There is an index on the date, yet a monthly query scans. Its predicate is `YEAR(CreatedAt)=2026`. The optimizer may transform some expressions, but relying on guesswork is risky. We will express the range directly and prove boundary semantics and plan behavior.

قبل از tuning، شاهد می‌خوایمBefore tuning, collect evidence

کاربر می‌گه «گزارش کند شده» و اولین وسوسه اینه که یه index بسازیم یا query رو از نو بنویسیم. نکن. توی «بهینه‌سازی ۲: SARGable، OR و تابع روی ستون» اول خط پایه می‌گیریم، بعد plan و تعداد ردیف و I/O رو می‌خونیم، یک فرضیه می‌سازیم و فقط یک چیز رو عوض می‌کنیم. اگه بهتر شد باید بتونیم بگیم چرا؛ اگه بدتر شد هم باید مدرک داشته باشیم.

A user says “the report is slow” and the first temptation is to add an index or rewrite the query. Do not. In “Tuning 2: SARGability, OR, and functions on columns” we capture a baseline, read the plan and row counts, form one hypothesis, and change one thing. If it improves, we must explain why; if it regresses, we still need evidence.

Predicate رو با ستون خام قابل‌جست‌وجو نگه دار / Keep the indexed column searchable in the predicate

SARGable یعنی شرط به شکل جست‌وجوی قابل‌استفاده روی index نوشته شده باشه؛ تضمین seek نیست. تابع یا محاسبه روی ستون، مثل `YEAR(DateColumn)`، ممکنه استفاده از range index رو سخت کند. بازهٔ نیمه‌باز معمولاً دقیق‌تر هست و از مشکل زمان‌های fractional در انتهای روز جلوگیری می‌کنه.

SARGable means the predicate is shaped so an index can support a search; it does not guarantee a seek. A function or calculation on the column, such as `YEAR(DateColumn)`, can make index range use harder. A half-open range is usually precise and avoids end-of-day fractional-time mistakes.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

تابع‌دار رو با بازهٔ نیمه‌باز مقایسه کن / Compare a function predicate with a half-open range
-- Version A: function applied to the column
SELECT TicketId, CreatedAt FROM Lab42.Ticket
WHERE YEAR(CreatedAt) = 2026;
-- Version B: explicit range
SELECT TicketId, CreatedAt FROM Lab42.Ticket
WHERE CreatedAt >= '20260101' AND CreatedAt < '20270101';
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

دو query رو با دادهٔ دارای ۳۱ دسامبر، ۱ ژانویه و زمان‌های fractional مقایسه کن؛ EXCEPT به‌تنهایی duplicateها رو نشان نمی‌ده. actual plan، rows read و logical reads رو هم مقایسه کن. تبدیل implicit سمت ستون هم می‌تونه همین مشکل رو بسازد.

Compare both queries with rows at year boundaries and fractional times; EXCEPT alone does not preserve duplicates. Compare actual plans, rows read, and logical reads. An implicit conversion on the column side can create a similar issue.

OR رو به خاطر ظاهرش کورکورانه حذف نکن / Do not rewrite OR blindly

OR ممکنه با indexها از طریق Index Union یا راه‌های دیگر اجرا بشه؛ گاهی scan مناسب‌تر هست. تبدیل به UNION ALL وقتی درسته که دو شاخه هم‌پوشانی نداشته باشند؛ اگه ممکنه یک ردیف در هر دو شاخه بیفتد، خروجی duplicate می‌گیره. UNION هم duplicateها رو حذف می‌کنه و می‌تونه معنای query رو عوض کند.

OR may use indexes through Index Union or other strategies; sometimes a scan is preferable. UNION ALL is equivalent only if branches cannot overlap. Otherwise duplicates appear; UNION removes them and may change query semantics.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

برابری نتیجه رو قبل از سرعت ثابت کن / Prove result equivalence before performance
SELECT TicketId FROM Lab42.Ticket
WHERE Status='Open' OR TenantId=7;
-- A candidate rewrite; test overlap before relying on it.
SELECT TicketId FROM Lab42.Ticket WHERE Status='Open'
UNION ALL
SELECT TicketId FROM Lab42.Ticket WHERE TenantId=7 AND Status<>'Open';
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

نسخهٔ دوم شرط وضعیت NULL رو هم نیازمند تصمیم می‌کنه؛ `Status<>'Open'` برای NULL، UNKNOWN هست. پس حتی rewrite ظاهراً ساده باید منطق سه‌مقداری و هم‌پوشانی رو حفظ کند. plan و درستی هر دو لازم‌اند.

The second form also forces a decision about NULL: `Status <> 'Open'` is UNKNOWN for NULL. Even a simple rewrite must preserve three-valued logic and overlap semantics. Check both correctness and plan.

نوع پارامتر رو با ستون هماهنگ کن / Match parameter types to the indexed column

اگه ستون varchar هست اما برنامه nvarchar می‌فرسته، precedence نوع‌ها ممکنه تبدیل ضمنی بسازد. اینکه تبدیل روی کدوم طرف انجام می‌شه به نوع و collation وابسته است؛ plan رو بررسی کن و parameter رو با نوع ستون بساز. `CONVERT` رو کورکورانه اضافه نکن؛ ممکنه تبدیل رو روی ستون نگه داره.

If a varchar column is compared with an nvarchar parameter, type precedence may introduce an implicit conversion. Which side is converted depends on types and collation; inspect the plan and bind parameters using the column's type. Adding CONVERT blindly may leave conversion on the column.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

Index seek هدف مستقل نیست؛ هدف query درست با منابع متناسب هست. بعد از اصلاح predicate، ممکنه scan همچنان بهترین انتخاب باشه. اگه هزینهٔ اجرای query کمتر نشده، شکل زیباتر ارزش عملی نداره.

An index seek is not the goal; the goal is a correct query with proportionate resource use. A scan may still be best after the rewrite. A prettier predicate has no operational value if cost does not improve.
