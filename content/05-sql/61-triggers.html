Trigger؛ قدرت پنهان و هزینهٔ نگهداری

Triggers: hidden power and maintenance cost

کسی می‌گه trigger کار audit رو خودکار می‌کنه. چند هفته بعد update کند شده و کسی نمی‌دونه چه کد پنهانی در پاسخ اجرا می‌شه. trigger رو با هزینه و محدودیتش انتخاب می‌کنیم.

A trigger is proposed to automate auditing. Weeks later, updates slow down and nobody knows what hidden code runs. We will understand its cost and limits before choosing it.

وقتی منطق رو می‌بری داخل دیتابیس، باید دلیل داشته باشیIf logic moves into the database, have a reason

یه stored procedure یا trigger می‌تونه کار رو خیلی تمیز کنه؛ همون ابزار می‌تونه شش ماه بعد تبدیل بشه به چیزی که هیچ‌کس نمی‌دونه از کجا اجرا شده. توی «Trigger؛ قدرت پنهان و هزینهٔ نگهداری» فقط syntax نمی‌زنیم. می‌سنجیم این منطق چرا باید داخل SQL Server باشه، چطور خطاش رو می‌بینیم و چطور مطمئن می‌شیم رفتار پنهان درست نکردیم.

A stored procedure or trigger can make a design cleaner, and the same feature can become mysterious hidden behaviour six months later. In “Triggers: hidden power and maintenance cost” we go beyond syntax: why should this logic live in SQL Server, how do we observe failures, and how do we avoid invisible side effects?

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

trigger بخشی از همان statement هست / A trigger is part of the statement

DML trigger هنگام INSERT، UPDATE یا DELETE اجرا می‌شه و با statement محرک transaction مشترک داره. خطا یا کار طولانی‌اش عملیات اصلی رو rollback یا کند می‌کنه. trigger برای هر statement اجرا می‌شه، نه هر ردیف؛ inserted و deleted مجموعه‌اند و ممکنه چندین ردیف داشته باشند.

A DML trigger runs for INSERT, UPDATE, or DELETE and shares the triggering transaction. Errors or slow work can roll back or delay the original operation. It fires per statement, not per row; inserted and deleted are sets and may contain multiple rows.

پس نیاز رو دقیق کن: invariant معمولاً با CHECK/FK/UNIQUE روشن‌تر است؛ audit به actor و retention نیاز داره؛ کار پس‌زمینه بهتره قرارداد outbox/queue داشته باشه. trigger انتخاب پیش‌فرض نیست.

Clarify the need: CHECK/FK/UNIQUE often express invariants more clearly; auditing needs actor and retention; background work needs an outbox/queue contract. A trigger is not the default choice.

الگوی چندردیفی رو درست بنویس / Make the set-based pattern correct

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

audit درج چندردیفی / Multi-row insert audit
CREATE TABLE dbo.ItemLab(Id int PRIMARY KEY, Name nvarchar(80) NOT NULL);
CREATE TABLE dbo.ItemAudit(Id int NOT NULL, NameAfter nvarchar(80) NOT NULL, ChangedAt datetime2 NOT NULL);
GO
CREATE OR ALTER TRIGGER dbo.tr_ItemLab_Insert ON dbo.ItemLab AFTER INSERT AS
BEGIN
 SET NOCOUNT ON;
 INSERT dbo.ItemAudit(Id,NameAfter,ChangedAt)
 SELECT Id,Name,SYSUTCDATETIME() FROM inserted;
END;
GO
INSERT dbo.ItemLab VALUES (1,N'one'),(2,N'two');
SELECT * FROM dbo.ItemAudit ORDER BY Id;

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

برای UPDATE، inserted و deleted رو روی کلید join کن تا مقدار جدید و قدیم رو ثبت کنی. این audit ساده تاریخچهٔ قانونی کامل نیست؛ هویت actor، retention و محدودیت دسترسی هم لازم‌اند.

For UPDATE, join inserted and deleted on the key to capture new and old values. This simple audit is not a complete compliance history; actor identity, retention, and access controls also matter.

کار trigger باید کوچک و قابل‌مشاهده باشه / Keep trigger work small and visible

HTTP، انتظار یا پردازش سنگین رو داخل trigger نگذار؛ lock و تأخیر به caller تحمیل می‌شه. recursion و triggerهای تو‌در‌تو زنجیرهٔ پنهان می‌سازند. commit دیتابیس رو معادل تحویل پیام ندان؛ برای کار پس‌زمینه outbox و worker رو جدا طراحی کن.

Do not put HTTP calls, waits, or heavy processing in a trigger: locks and latency spill into the caller. Recursive/nested triggers create hidden chains. A database commit is not message delivery; design an outbox and worker for background work.

تعریف و وضعیت trigger رو query کن / Inspect trigger definition and status

در lab هم چندردیفی و هم خطای عمدی رو امتحان کن. برای عیب‌یابی production از ابزار مجاز استفاده کن؛ trigger رو با logging پنهان پیچیده‌تر نکن.

catalog triggerها / Trigger catalog
SELECT name,is_disabled,is_instead_of_trigger,OBJECT_NAME(parent_id) AS ParentObject
FROM sys.triggers WHERE parent_class_desc='OBJECT_OR_COLUMN'
ORDER BY ParentObject,name;

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

Design an outbox for background work and state transaction boundaries.

معیار موفقیت: تغییر رو داخل transaction کنترل کنی، قبل از COMMIT نتیجه رو ببینی و بتونی همون آزمایش رو با ROLLBACK برگردونی.

Success criterion: control the change inside a transaction, inspect it before COMMIT, and be able to repeat the lab with ROLLBACK.

راهنما / HintHint
Commit does not equal message delivery.
پاسخ و توضیحSolution and reasoning

قبل از COMMIT، دادهٔ تغییرکرده و @@TRANCOUNT/XACT_STATE رو جایی که لازم می‌شه ببین. هدف اینه که مرز transaction برات قابل‌دیدن باشه.

Before COMMIT, inspect changed data and transaction state where relevant. The goal is to make the transaction boundary observable.

تمرین ۶۱٫۱۷Exercise 61.17چالشیChallenge۱۲ دقیقه12 min

trigger آزمایشی و قابل‌حذف رو خاموش/روشن و تغییر رفتار رو query کن.

Disable/enable a lab trigger and query behavior.

معیار موفقیت: object یا statement رو اجرا کنی، یک حالت مرزی/خطا رو هم تست کنی و توضیح بدی چرا این منطق باید اینجا باشه.

Success criterion: execute the object or statement, test an edge case/failure, and explain why this logic belongs here.

راهنما / HintHint
Never do this casually in production.
پاسخ و توضیحSolution and reasoning

فقط happy path رو تست نکن. NULL، چندردیفی بودن، خطا یا ورودی غیرعادی رو هم امتحان کن تا رفتار پنهان نمونه.

Do not test only the happy path. Include NULL, multi-row input, an error, or another edge case so hidden behaviour becomes visible.

تمرین ۶۱٫۱۸Exercise 61.18چالشیChallenge۱۲ دقیقه12 min

شاهد SQL و تصمیم استفاده یا عدم استفاده رو تحویل بده.

Submit SQL evidence and a decision to use or avoid a trigger.

معیار موفقیت: object رو بسازی، اجراش کنی، یک edge case یا خطا رو هم امتحان کنی و رفتار رو توضیح بدی.

Success criterion: create and execute the object, test an edge case or failure, and explain the behaviour.

راهنما / HintHint
Include multi-row and failure cases.
پاسخ و توضیحSolution and reasoning

اول مسئله رو به یک خروجی قابل‌سنجش تبدیل کن، بعد query یا command رو اجرا کن. جواب خوب هم نتیجه رو نشون می‌ده، هم دو خط توضیح می‌ده چرا این نتیجه به‌دست اومده.

Turn the task into a measurable outcome before running anything. A strong answer shows the result and briefly explains why that result occurred.

رفتار پنهان رو به تصمیم آشکار تبدیل کن / Turn hidden behavior into an explicit decision

trigger مجموعه‌ای اجرا می‌شه، transaction caller رو شریک می‌شه و تأخیر/rollback رو به عملیات اصلی منتقل می‌کنه. اگه constraint یا منطق صریح کافیه، معمولاً ساده‌تر و قابل‌ردیابی‌تر هست. در غیر این صورت قرارداد و تست چندردیفی رو مستند کن.

A trigger is set-based, shares the caller transaction, and transfers latency/rollback to the original operation. Prefer constraints or explicit logic when they suffice; otherwise document the contract and multi-row tests.
