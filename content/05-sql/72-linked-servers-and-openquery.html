Linked Server و OPENQUERY

Linked servers and OPENQUERY

گزارش باید از یک SQL Server دیگر داده بخواند. linked server سریع راه می‌افته؛ اما query با کدوم credential می‌ره؟ provider کجا نصب است؟ اگه مقصد قطع بشه، transaction محلی چه وضعی داره؟ قبل از ساختن link، coupling و مرز اعتماد رو می‌سنجیم.

A report must read another SQL Server. A linked server seems quick, but which credentials travel, where is the provider installed, and what happens to the local transaction if the remote side fails? We assess coupling and trust before creating a link.

“Cannot connect” is one phrase for several different failures: DNS, port, TLS, instance discovery, firewall, or authentication. In “Linked servers and OPENQUERY” we split the path into layers and prove one layer at a time instead of changing random settings.

SQL Server به‌جای برنامه با provider حرف می‌زند / SQL Server talks through a provider

Linked Server مقصدی هست که Database Engine از طریق OLE DB provider به آن query می‌فرسته. provider باید روی host خود SQL Server نصب و برای service account قابل‌دسترسی باشه. مسیر معمول client → SQL Server محلی → provider → remote source است؛ بنابراین permission و network سمت server مهم‌اند.

A linked server is a target the Database Engine queries through an OLE DB provider. The provider must be installed and accessible to the SQL Server service account on the SQL host. The path is client → local SQL Server → provider → remote source, so server-side permissions and networking matter.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

OPENQUERY کد رو سمت مقصد اجرا می‌کنه / OPENQUERY executes text remotely

چهارقسمتی و OPENQUERY رفتار و قابلیت pushdown متفاوت دارن. OPENQUERY متن query رو به provider remote می‌فرسته و محدودیت طول/عبارت داره؛ ورودی کاربر رو به متن آن concatenate نکن. هر دو روش ممکنه نتایج و plan متفاوتی بسازند.

Four-part names and OPENQUERY differ in behavior and pushdown. OPENQUERY sends query text to the remote provider and has query-string limits; never concatenate user input into it. Either form can produce different results and plans.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

خواندن محدود / Bounded remote read
SELECT *
FROM OPENQUERY(RemoteSales,
 'SELECT TOP (100) OrderId,OrderDate
  FROM SalesDb.dbo.Orders
  ORDER BY OrderDate DESC,OrderId DESC');

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

نام RemoteSales باید قبلاً تنظیم شده باشه. قبل از query، remote permissions و row limit رو تأیید کن؛ SELECT * رو به قرارداد پایدار تبدیل کن.

RemoteSales must already be configured. Verify remote permissions and row bounds first; replace SELECT * with a stable contract.

login mapping یک credential قابل‌گسترش هست / Login mapping can broaden authority

mapping ثابت remote login ممکنه برای چند user محلی استفاده بشه؛ این رفتار ناخواسته دسترسی رو گسترش می‌ده. برای هر mapping principal remote کم‌دسترسی انتخاب کن و delegation رو جدا طراحی کن. رمز رو داخل script مشترک نگذار. در SQL Server 2025 و OLE DB Driver 19 تنظیم encryption/certificate صریح و حساس به نسخه است؛ docs همان نسخه رو بخوان.

A fixed remote-login mapping may serve multiple local users, broadening access unexpectedly. Use a least-privilege remote principal and design delegation deliberately. Keep passwords out of shared scripts. SQL Server 2025 with OLE DB Driver 19 has version-sensitive encryption/certificate requirements; consult that version's docs.

اتصال راه‌دور مرز شکست جدا داره / Remote queries have a separate failure boundary

remote timeout، network loss یا transaction خرابی ممکنه هزینه و وضعیت خاص خودش رو داشته باشه؛ distributed transaction رو با transaction محلی یکی نگیر. اگه query پرتکرار، حساس یا نوشتنی است، ETL، API یا replication معماری روشن‌تری می‌ده. یک distributed query رو جای integration design جا نزن.

Remote timeouts, network loss, and transaction failures have their own semantics; do not equate distributed transactions with local ones. For frequent, critical, or write-heavy integration, ETL, APIs, or replication may provide clearer architecture. A distributed query is not an integration strategy by itself.

پاسخ و توضیحSolution and reasoning

از بیرون به داخل جلو برو: name resolution، رسیدن به port، TLS و بعد authentication. هر بار فقط یک لایه رو تغییر بده.

Work from outside inward: name resolution, port reachability, TLS, then authentication. Change one layer at a time.

linked server رو با هزینهٔ coupling انتخاب کن / Choose linked servers with coupling in mind

provider، network سمت SQL Server، mapping و رفتار TLS رو شناختیم و query رو محدود کردیم. مجوز credential رو با remote principal سنجیدیم و خرابی/transaction رو جدا دیدیم. برای اتصال برنامه، connection pooling، timeout و retry معمولاً مسیر قابل‌کنترل‌تری می‌سازند.

We inspected provider, SQL-host networking, mappings, TLS behavior, and bounded queries. We evaluated remote credentials and failure/transaction boundaries. Application connections with deliberate pooling, timeouts, and retries often provide more control.
