SQL پویا: داده، کد نیست

Dynamic SQL: data is not code

گزارش باید بر اساس فیلتر انتخابی ساخته بشه. توسعه‌دهنده رشتهٔ query رو با ورودی کاربر می‌چسباند؛ یک apostrophe کافیه تا مرز داده و دستور به‌هم بخورد. اول روش ناامن رو فقط در محیط دورریختنی می‌بینیم، بعد با parameterization اصلاحش می‌کنیم.

A report needs selectable filters. The developer concatenates user input into SQL; one apostrophe can blur the boundary between data and command. We reproduce the unsafe form only in a disposable environment, then fix it with parameterization.

وقتی منطق رو می‌بری داخل دیتابیس، باید دلیل داشته باشیIf logic moves into the database, have a reason

یه stored procedure یا trigger می‌تونه کار رو خیلی تمیز کنه؛ همون ابزار می‌تونه شش ماه بعد تبدیل بشه به چیزی که هیچ‌کس نمی‌دونه از کجا اجرا شده. توی «SQL پویا: داده، کد نیست» فقط syntax نمی‌زنیم. می‌سنجیم این منطق چرا باید داخل SQL Server باشه، چطور خطاش رو می‌بینیم و چطور مطمئن می‌شیم رفتار پنهان درست نکردیم.

A stored procedure or trigger can make a design cleaner, and the same feature can become mysterious hidden behaviour six months later. In “Dynamic SQL: data is not code” we go beyond syntax: why should this logic live in SQL Server, how do we observe failures, and how do we avoid invisible side effects?

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

چرا dynamic SQL لازم می‌شه؟ / Why use dynamic SQL?

گاهی ساختار query واقعاً براساس انتخاب امن کاربر عوض می‌شه؛ مثلاً sort column یا فیلترهای optional. برای مقدارهای داده، query رو concatenate نکن. sp_executesql متن statement رو جدا از مقدار پارامتر می‌گیره و type/length رو مشخص می‌کنه.

Sometimes query structure legitimately varies, such as a chosen sort column or optional filters. Never concatenate data values. sp_executesql accepts statement text separately from parameter values, with explicit type and length.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

مقدار به‌صورت پارامتر / Value passed as data
DECLARE @sql nvarchar(max)=N'
 SELECT OrderId,CustomerId,TotalAmount
 FROM dbo.Orders WHERE CustomerId=@CustomerId;';
EXEC sys.sp_executesql @sql,
 N'@CustomerId int', @CustomerId=42;

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

پارامتری‌سازی جلوی تزریق از مسیر value رو می‌گیره، اما خودش authorization، validation دامنه یا کارایی خوب رو تضمین نمی‌کنه. دسترسی principal و plan رو جدا بررسی کن.

Parameterization prevents value-based injection through that input, but does not guarantee authorization, business validation, or good performance. Inspect principal permissions and plans separately.

نام ستون پارامتر scalar نیست / An identifier is not a scalar parameter

نام جدول و ستون رو نمی‌توان مثل مقدار با @Column پارامتری کرد. برای این بخش allowlist ثابت بساز؛ بعد identifier انتخاب‌شده رو با QUOTENAME quote کن. QUOTENAME به‌تنهایی مجوز نمی‌ده و رشتهٔ دلخواه رو امن نمی‌کنه.

Table and column names cannot be supplied as scalar @Column parameters. Use a fixed allowlist, then quote the selected identifier with QUOTENAME. QUOTENAME alone does not authorize or make arbitrary strings safe.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

allowlist به‌علاوهٔ پارامتر / Allowlist plus parameter
DECLARE @SortColumn sysname =
 CASE @RequestedSort WHEN N'date' THEN N'OrderDate'
                     WHEN N'total' THEN N'TotalAmount' END;
IF @SortColumn IS NULL THROW 50020,'Sort field is not allowed.',1;
DECLARE @sql nvarchar(max)=N'SELECT OrderId,OrderDate,TotalAmount
 FROM dbo.Orders WHERE CustomerId=@CustomerId ORDER BY '
 + QUOTENAME(@SortColumn) + N';';
EXEC sys.sp_executesql @sql,N'@CustomerId int',@CustomerId=42;

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

فقط identifier رو به متن query اضافه کردیم؛ CustomerId همچنان parameter هست. direction مثل ASC/DESC رو هم از دو مقدار ثابت انتخاب کن، نه از رشتهٔ خام.

Only the identifier enters query text; CustomerId remains a parameter. Choose direction such as ASC/DESC from fixed branches, never raw input.

روش ناامن رو فقط برای شناخت در lab ببین / Reproduce unsafe code only in a lab

اتصال رشته‌ای زیر شکل خطر رو نشان می‌ده؛ اون رو روی دادهٔ واقعی اجرا نکن. ورودی می‌تونه quote رو ببندد و بخش تازه‌ای از SQL بسازد. هدف این تمرین شناخت علت و اثبات اصلاح است، نه اجرای payload در سامانهٔ دیگران.

The concatenation below illustrates the risk; never run it against real data. Input can close a quote and introduce SQL syntax. The goal is to understand and prove the fix, not attack another system.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

نمونهٔ صرفاً آزمایشگاهی / Lab-only anti-pattern
-- UNSAFE: disposable database only; do not use in an application.
DECLARE @name nvarchar(100)=N''' OR 1=1--';
DECLARE @bad nvarchar(max)=N'SELECT Id FROM dbo.LabUsers WHERE Name=N'''
 + @name + N'''';
SELECT @bad AS ConstructedSql;
-- Repair by passing @name as a sp_executesql parameter.

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

خروجی رو فقط بررسی کن و روی جدول حساس اجرا نکن. پس از repair، همان ورودی باید به‌عنوان داده تفسیر بشه؛ تعداد ردیف و plan مورد انتظار رو assert کن.

Inspect the constructed text only; do not execute it against a sensitive table. After repair, the same input must be treated as a value; assert expected rows and plan behavior.

امنیت و performance دو بررسی جدا هستن / Security and performance are separate checks

parameterization امنیت value رو بهتر می‌کنه و می‌تونه plan reuse رو ممکن کند، اما تضمین performance نیست؛ توزیع پارامتر و plan sensitivity مهم‌اند. dynamic SQL ممکنه permission behavior متفاوتی با SQL استاتیک داشته باشه؛ با principal محدود واقعی آزمایش کن.

Parameterization improves value safety and may enable plan reuse, but does not guarantee performance; parameter distribution and plan sensitivity still matter. Dynamic SQL can have different permission behavior from static SQL; test with the actual limited principal.
