INNER JOIN؛ فقط matchها

INNER JOIN: matching rows only

پشتیبانی می‌گه «مشتری در سیستم هست، چرا در گزارش نیست؟» query دو جدول رو INNER JOIN کرده. شاید داده حذف نشده؛ شاید شرط اتصال هیچ matchی برای آن ردیف پیدا نکرده باشه. این فصل کمک می‌کنه خروجی اتصال رو پیش‌بینی کنیم، نه اینکه از روی نبودن ردیف حدس بزنیم.

Support says, “The customer exists, so why is it missing from the report?” The query uses an INNER JOIN. The data may not be deleted; the join may simply find no match. This chapter teaches us to predict join output instead of guessing from a missing row.

اول تعداد ردیف‌ها رو حدس بزنPredict the row count first

گزارش سفارش‌ها معمولاً از جایی سخت می‌شه که یک جدول دیگه وارد ماجرا می‌شه. سه سفارش داری، چهار مشتری داری، پنج ردیف سفارش هم داری؛ حالا JOIN می‌زنی و ناگهان خروجی دوازده ردیف می‌شه. توی «INNER JOIN؛ فقط matchها» قبل از هر query اول حدس می‌زنیم چند ردیف باید برگرده، بعد اجرا می‌کنیم و از روی اختلاف حدسمون با واقعیت می‌فهمیم رابطه‌ها رو درست خوندیم یا نه.

Reports get interesting the moment another table enters the picture. You may have three orders, four customers, and five order lines, then a join suddenly returns twelve rows. In “INNER JOIN: matching rows only” we predict row counts before executing, then use any mismatch to diagnose our understanding of the relationships.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

نبودن در خروجی، اثبات حذف‌شدن نیست / Absence from the result does not prove deletion

INNER JOIN فقط جفت‌هایی رو برمی‌گردونه که شرط ON برای هر دو سمت درست باشه. اگه ردیف مستقلی در یک سمت match نداشته باشه، در نتیجهٔ inner جایی نداره. برای همین اول باید روشن کنیم ticket دقیقاً «فقط موارد مرتبط» می‌خواد یا «همهٔ موارد یک طرف، حتی بی‌match»؛ دومی موضوع outer join هست.

INNER JOIN returns pairs for which the ON predicate matches both sides. An unmatched row has no place in an inner result. First clarify whether the ticket asks for “related rows only” or “every row from one side, even without a match”; the latter is an outer-join requirement.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

دو مجموعهٔ کوچک؛ نتیجهٔ inner فقط اشتراک matchهاست / Two small sets: only matching pairs survive
DROP TABLE IF EXISTS #LeftSet, #RightSet;
CREATE TABLE #LeftSet (Id int PRIMARY KEY, Label varchar(20));
CREATE TABLE #RightSet (Id int PRIMARY KEY, Note varchar(20));
INSERT #LeftSet VALUES (1, 'one'), (2, 'two'), (3, 'three');
INSERT #RightSet VALUES (2, 'matched'), (4, 'right-only');

SELECT l.Id, l.Label, r.Note
FROM #LeftSet AS l
INNER JOIN #RightSet AS r ON r.Id = l.Id
ORDER BY l.Id;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

فقط شناسهٔ ۲ در هر دو هست، پس یک ردیف خروجی داریم. شناسهٔ ۱ و ۳ سمت چپ و ۴ سمت راست حذف نشده‌اند؛ فقط این نوع query اون‌ها رو نمایش نمی‌ده. این جدول‌های موقت رو می‌توانی بدون دست‌زدن به Shop در همان نشست اجرا کنی.

Only ID 2 exists on both sides, so one row returns. IDs 1 and 3 on the left and 4 on the right are not deleted; this query type simply does not display them. These temporary tables can be tested without changing Shop.

از دادهٔ تمرینی فروشگاه، فقط رابطه‌های matchشده رو بخوان / Read only matched relationships from Shop

برای فاکتور، سفارش بدون مشتری متناظر نباید به‌عنوان یک فاکتور کامل گزارش بشه. INNER JOIN این نیاز رو بیان می‌کنه. شرط اتصال رو روی کلیدها نگه می‌داریم و فیلترهایی مثل وضعیت رو جداگانه در WHERE می‌گذاریم.

For an invoice, an order without a corresponding customer should not appear as a complete invoice. INNER JOIN expresses that requirement. Keep the relationship on keys and put separate filters, such as status, in WHERE.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

فقط سفارش‌های دارای مشتری / Only orders with a matching customer
SELECT o.OrderId, o.OrderStatus, c.FullName
FROM shop.Orders AS o
INNER JOIN shop.Customers AS c
    ON c.CustomerId = o.CustomerId
WHERE o.OrderStatus IN ('Paid', 'Pending')
ORDER BY o.OrderId;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

در دادهٔ تمرینی رابطه‌ها با constraint حفاظت شده‌اند، بنابراین سفارش یتیم معمولاً نمی‌توانی بسازی؛ اما در importهای ناقص، داده‌های مهاجرتی یا query با شرط اشتباه، خروجی باز هم ممکنه از چیزی که انتظار داری کمتر بشه. نبودن ردیف رو با جست‌وجوی مستقیم در جدول پایه و بررسی کلید match کن.

The fixture protects relationships with constraints, so you normally cannot create an orphaned order there. In incomplete imports, migrations, or a query with the wrong predicate, results can still be smaller than expected. Verify absence by querying the base table and checking the join key.

عیب‌یابی: ردیف پایه هست یا match؟ / Diagnose: is the base row present, and does it match?
SELECT o.OrderId, o.CustomerId
FROM shop.Orders AS o
WHERE o.OrderId = 1001;
GO

SELECT o.OrderId, c.CustomerId AS MatchedCustomerId, c.FullName
FROM shop.Orders AS o
LEFT JOIN shop.Customers AS c ON c.CustomerId = o.CustomerId
WHERE o.OrderId = 1001;
GO

LEFT JOIN دوم فقط ابزار تشخیصی هست: ردیف سفارش رو نگه می‌داره و اگه match نباشه، ستون‌های c برابر NULL می‌شن. این رو با query عملی فصل LEFT JOIN اشتباه نگیر؛ فعلاً از آن برای یافتن علت غیبت استفاده می‌کنیم.

The second LEFT JOIN is a diagnostic: it preserves the order and shows NULL customer columns if no match exists. Do not confuse it with the full LEFT JOIN lesson; here it helps explain an absent inner-join result.

دو خطای رایج: کلید اشتباه و matchهای چندگانه / Two common errors: wrong keys and multiple matches

اتصال با نام شهر یا متن توضیح شاید در نمونه جواب بدهد، اما رابطه نیست. از طرف دیگر، اتصال درست هم ممکنه چند خروجی بسازد اگه طرف match یکتا نباشه. INNER JOIN تضمین نمی‌کنه یک ردیف ورودی دقیقاً یک ردیف خروجی بسازد؛ تعداد matchها رو schema و داده تعیین می‌کنن.

Joining by city or a descriptive string may appear to work in a sample, but that is not the relationship. Conversely, even a correct join can produce multiple rows if the matching side is not unique. INNER JOIN does not promise one output per input row; schema and data determine match counts.

قبل و بعد رو اندازه بگیر / Measure before and after
SELECT COUNT_BIG(*) AS OrderCount FROM shop.Orders;
SELECT COUNT_BIG(*) AS JoinedCount
FROM shop.Orders AS o
INNER JOIN shop.Customers AS c ON c.CustomerId = o.CustomerId;
GO

اگه تعداد عوض شد، فوراً DISTINCT نگذار. اول بررسی کن آیا ردیف‌های بدون match حذف شده‌اند، یا یک کلید به چند ردیف match شده. DISTINCT ممکنه شواهد مسئله رو پنهان کند.

If the count changes, do not immediately add DISTINCT. First check whether unmatched rows disappeared or one key matched multiple rows. DISTINCT can hide evidence of the real problem.

INNER JOIN فقط بخش دارای match رو نگه می‌داره / INNER JOIN keeps the matching part

نمودار، مفهوم match رو نشان می‌ده، نه تعداد واقعی Shop و نه ترتیب اجرای فیزیکی. برای حفظ ردیف نامنطبق باید نوع اتصال دیگری انتخاب بشه.
