توابع تجمیعی و GROUP BY

Aggregate functions and GROUP BY

مدیر فروش به‌جای فهرست تمام سفارش‌ها، تعداد سفارش‌ها و میانگین مبلغ هر مشتری رو می‌خواد. اگه query رو بدون تعیین سطح گزارش بنویسیم، عددی می‌گیریم که نمی‌دانیم نمایندهٔ چیه. قبل از تابع تجمیعی، grain خروجی رو با یک جمله روشن می‌کنیم.

The sales manager wants order counts and average order value per customer, not a list of every order. If we query without defining the report’s level, we may get a number whose meaning is unclear. Before using an aggregate, we state the output grain in one sentence.

گزارش وقتی جدی می‌شه که فقط «لیست» نباشهA report becomes serious when it is more than a list

تا اینجا گرفتن چند ردیف آسون بود. درد واقعی وقتی شروع می‌شه که یکی می‌گه «فروش هر شهر رو بده، نسبت به ماه قبل مقایسه کن، فقط شهرهای بالای فلان عدد رو نگه دار و رتبه هم بده». «توابع تجمیعی و GROUP BY» رو برای همین جنس سؤال‌ها می‌خوایم. قدم‌به‌قدم می‌ریم جلو تا query هم درست باشه، هم بشه فهمید چرا درست کار می‌کنه.

Selecting rows is the easy part. Real reporting starts when someone asks for sales by city, a comparison with last month, a threshold, and a rank. “Aggregate functions and GROUP BY” belongs to that kind of problem. We build the query step by step so it is not only correct but explainable.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

از فهرست ردیف‌ها به یک عدد قابل‌توضیح / From rows to a meaningful number

COUNT، SUM، AVG، MIN و MAX چند ردیف رو به مقدار خلاصه تبدیل می‌کنن. بدون GROUP BY، هرکدوم معمولاً یک نتیجه برای کل ورودی می‌سازند؛ با GROUP BY، برای هر گروه یک نتیجه می‌گیریم. سؤال کلیدی هنوز این هست: «یک ردیف خروجی نمایندهٔ چیه؟»

COUNT, SUM, AVG, MIN, and MAX summarize multiple rows into values. Without GROUP BY, they generally produce one result for the whole input; with GROUP BY, they produce one result per group. The key question remains: “What does one output row represent?”

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

چند قلم و یک مجموع برای هر سفارش / Multiple items, one total per order
SELECT oi.OrderId,
       COUNT_BIG(*) AS LineCount,
       SUM(oi.Quantity * oi.UnitPriceAtSale) AS OrderTotal,
       AVG(oi.UnitPriceAtSale) AS AverageUnitPrice,
       MIN(oi.UnitPriceAtSale) AS CheapestUnitPrice,
       MAX(oi.UnitPriceAtSale) AS MostExpensiveUnitPrice
FROM shop.OrderItems AS oi
GROUP BY oi.OrderId
ORDER BY oi.OrderId;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

اینجا هر ردیف خروجی یک سفارش دارای قلم هست. تعداد قلم‌ها با تعداد محصول‌های یکتا یکی نیست. میانگین هم «میانگین قیمت واحد قلم‌ها» است، نه میانگین مبلغ سفارش. اسم aliasها باید دقیق بگوید کدوم تعریف رو انتخاب کرده‌ای.

Each output row represents an order with at least one item. Line count is not distinct product count. The average is the average unit price across lines, not average order value. Aliases should state exactly which definition you chose.

COUNT(*) با COUNT(column) یک سؤال نمی‌پرسند / COUNT(*) and COUNT(column) ask different questions

COUNT(*) تعداد ردیف‌های ورودی رو می‌شمارد. COUNT(column) فقط مقدارهای غیرNULL همان ستون رو می‌شمارد. بیشتر توابع تجمیعی دیگر هم NULLها رو نادیده می‌گیرند؛ بنابراین قبل از تفسیر عدد، بدان NULL در این ستون یعنی «نامعلوم»، «هنوز ثبت نشده» یا چیزی دیگر. مقدار NULL رو صفر فرض نکن.

COUNT(*) counts input rows. COUNT(column) counts only non-NULL values in that column. Most other aggregates also ignore NULLs, so understand whether NULL means unknown, not yet recorded, or something else before interpreting the number. Do not assume NULL means zero.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

آزمایش امن NULL و رشتهٔ خالی / A safe NULL and empty-string experiment
DECLARE @Probe table (Amount int NULL, Note nvarchar(20) NULL);
INSERT @Probe (Amount,Note) VALUES (10,N'ok'),(NULL,N''),(0,NULL);

SELECT COUNT_BIG(*) AS RowsTotal,
       COUNT(Amount) AS KnownAmounts,
       SUM(Amount) AS SumKnownAmounts,
       AVG(Amount) AS AverageKnownAmount,
       MIN(Amount) AS MinimumAmount,
       MAX(Amount) AS MaximumAmount,
       COUNT(Note) AS NonNullNotes
FROM @Probe;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

سه ردیف داریم، اما فقط دو Amount شناخته‌شده؛ SUM برابر ۱۰ هست و AVG برابر ۵، چون NULL در محاسبه کنار گذاشته می‌شه ولی صفر کنار گذاشته نمی‌شه. رشتهٔ خالی هم NULL نیست، پس COUNT(Note) اون رو می‌شمارد. اگه ورودی کاملاً خالی باشه، COUNT صفر و SUM/AVG/MIN/MAX معمولاً NULL می‌دهند؛ گروهی برای نمایش وجود نداره.

There are three rows but two known amounts. SUM is 10 and AVG is 5 because NULL is skipped while zero is included. An empty string is not NULL, so COUNT(Note) includes it. On an empty input, COUNT returns zero while SUM/AVG/MIN/MAX generally return NULL; there is no group row to display.

ستون غیرتجمیعی باید گروه رو تعریف کند / Every non-aggregated column defines the group

وقتی خروجی یک ردیف در هر مشتری است، CustomerId باید در GROUP BY بیاید و ستون‌های دیگر یا باید تابع تجمیعی باشند یا تابع کلید گروه. SQL Server معمولاً queryای رو که FullName رو بی‌تجمیع و بیرون GROUP BY انتخاب کند رد می‌کنه؛ این سخت‌گیری جلوی انتخاب مقدار تصادفی از گروه رو می‌گیره.

If output is one row per customer, CustomerId belongs in GROUP BY, and other selected columns must be aggregated or functionally tied to the group key. SQL Server rejects selecting FullName unaggregated and outside GROUP BY; this prevents an arbitrary value from being chosen for a group.

تعداد سفارش و مبلغ قلم‌ها برای هر مشتری / Order count and line sales by customer
SELECT c.CustomerId, c.FullName,
       COUNT(DISTINCT o.OrderId) AS OrderCount,
       SUM(oi.Quantity * oi.UnitPriceAtSale) AS SalesFromItems
FROM shop.Customers AS c
LEFT JOIN shop.Orders AS o ON o.CustomerId = c.CustomerId
LEFT JOIN shop.OrderItems AS oi ON oi.OrderId = o.OrderId
GROUP BY c.CustomerId, c.FullName
ORDER BY c.CustomerId;
GO

COUNT(DISTINCT OrderId) سفارش‌ها رو می‌شمارد، چون join به اقلام سفارش رو تکرار می‌کنه. SUM مبلغ قلم‌ها رو جمع می‌کنه. اگه مشتری سفارش نداشته باشه، SUM ممکنه NULL باشه؛ اگه در گزارش صفر باید، آگاهانه با COALESCE اون رو به صفر تبدیل کن و این تصمیم رو مستند کن.

COUNT(DISTINCT OrderId) counts orders because joining items repeats orders. SUM totals line values. A customer with no orders may have a NULL SUM; if the report requires zero, convert it deliberately with COALESCE and document that decision.

جمع بادکرده رو با DISTINCT آرایش نکن / Do not disguise an inflated sum with DISTINCT

اگه join ردیف‌ها رو چندبرابر کرده، DISTINCT ممکنه مقدارهای یکسان واقعی رو هم یکی کند و مشکل رو پنهان کند. اول grain رو مشخص کن؛ بعد بفهم هر match چه تعداد ردیف می‌آورد. اگه باید مبلغ سفارش رو کنار جزئیات بیاوری، اول مبلغ رو در سطح OrderId تجمیع کن و سپس به جدول‌های دیگر وصل کن.

If a join multiplied rows, DISTINCT may collapse legitimate equal values and hide the problem. State the grain first, then measure how many rows each match creates. If an order total must appear beside details, aggregate at OrderId first and then join it to other tables.

ابتدا aggregate سفارش، بعد اتصال به مشتری / Aggregate by order before attaching customer
WITH OrderTotals AS
(
  SELECT OrderId,
         SUM(Quantity * UnitPriceAtSale) AS OrderTotal
  FROM shop.OrderItems
  GROUP BY OrderId
)
SELECT o.OrderId, c.FullName, t.OrderTotal
FROM shop.Orders AS o
JOIN OrderTotals AS t ON t.OrderId = o.OrderId
JOIN shop.Customers AS c ON c.CustomerId = o.CustomerId
ORDER BY o.OrderId;
GO

CTE اینجا فقط یک ردیف برای هر سفارش می‌سازه؛ فصل‌های بعدی ساختار و کاربرد CTE رو جدا می‌کنن. مقدار نهایی رو با چند OrderId مشخص از قلم‌ها دوباره حساب کن؛ یک عدد کل برای اثبات کافی نیست.

The CTE creates one row per order; later chapters cover CTE structure and use separately. Recalculate several specific OrderIds from their lines; a grand total alone is not sufficient proof.

تابع تجمیعی، ردیف‌های هر گروه رو خلاصه می‌کنه / An aggregate summarizes rows inside each group

اول گروه رو تعریف کن، بعد دربارهٔ معنی هر ستون تجمیعی حرف بزن. اگه grain خروجی در ذهنت روشن نیست، هنوز نوبت نوشتن SUM نرسیده.

Define the group first, then state what each aggregate column means. If the output grain is unclear, it is too early to write the SUM.
