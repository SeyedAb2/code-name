Columnstore برای بار کاری تحلیلی

Columnstore for analytical workloads

جدول فروش ردیف‌های زیادی داره؛ گزارش ماهانه فقط چند ستون رو aggregate می‌کنه. rowstore برای دسترسی ردیفی مناسب بوده، اما scan و خواندن ستون‌های اضافی هزینه داره. آیا columnstore بهتره؟ پاسخ رو از شکل دسترسی، حجم داده، plan و هزینهٔ نوشتن درمی‌آوریم.

A sales table has many rows, while a monthly report aggregates only a few columns. Rowstore suits row access, but scans may read extra columns. Is columnstore better? We will decide from access shape, data size, plans, and write costs.

حالا بریم زیر کاپوتNow look under the hood

یه query از بیرون خیلی ساده‌ست: می‌فرستیش و جواب میاد. ولی وقتی کند می‌شه، دیگه اون نمای بیرونی کافی نیست. برای «Columnstore برای بار کاری تحلیلی» یه لایه پایین‌تر می‌ریم و مسیر داده رو دنبال می‌کنیم؛ نه برای حفظ‌کردن اصطلاحات داخلی، برای اینکه وقتی plan یا I/O رفتار عجیبی داشت بفهمیم SQL Server واقعاً داره چه کاری انجام می‌ده.

A query looks simple from the outside: send it, get rows back. Once it becomes slow, that view is not enough. In “Columnstore for analytical workloads” we move one layer down and follow the data path—not to memorise internals, but to explain what SQL Server is actually doing when plans and I/O behave unexpectedly.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

Rowstore برای ردیف؛ columnstore برای خواندن ستونی / Rowstore favors rows; columnstore favors analytical column access

rowstore page، مقدار ستون‌های یک ردیف رو کنار هم نگه می‌داره؛ برای lookup و OLTP اغلب مناسب هست. columnstore داده رو به گروه‌های ردیفی فشرده و به شکل ستونی سازمان می‌ده؛ queryهایی که تعداد زیادی ردیف و چند ستون رو scan/aggregate می‌کنن ممکنه از compression و اجرای batch بهره ببرند. «ممکنه» مهمه: اندازهٔ کم یا بار کاری نوشتنی نتیجه رو عوض می‌کنه.

Rowstore pages keep a row's values together and often suit lookups and OLTP. Columnstore organizes compressed row groups by column; scans and aggregates over many rows and few columns may benefit from compression and batch execution. “May” matters: small data or write-heavy access can change the result.

columnstore جایگزین همهٔ indexهای rowstore نیست؛ در بعضی طراحی‌ها کنار rowstore indexها کار می‌کنه. edition، نسخه، بار کاری و الگوی تغییرات رو برای محیط مقصد بررسی کن.

Columnstore does not replace every rowstore index; some designs combine it with rowstore indexes. Verify edition, version, workload, and modification patterns for the target environment.

یک گزارش رو روی دو شکل ذخیره‌سازی مقایسه کن / Compare one report across two storage shapes

دادهٔ نمونهٔ کوچک فقط syntax رو ثابت می‌کنه، نه performance. برای benchmark معنی‌دار، dataset بزرگ و توزیع واقع‌بینانه بساز؛ نتیجهٔ lab کوچک رو تعمیم نده.

A small fixture proves syntax, not performance. A meaningful benchmark needs a sufficiently large, realistic distribution; do not generalize from a tiny lab.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

دو جدول آزمایشی و قابل‌حذف با شکل مشابه / Two disposable tables with the same logical rows
IF SCHEMA_ID(N'Lab44') IS NULL EXEC(N'CREATE SCHEMA Lab44');
DROP TABLE IF EXISTS Lab44.SalesColumnstore, Lab44.SalesRowstore;
CREATE TABLE Lab44.SalesRowstore
 (SaleId bigint NOT NULL, SaleDate date NOT NULL, StoreId int NOT NULL,
  ProductId int NOT NULL, Quantity int NOT NULL, NetAmount decimal(12,2) NOT NULL,
  CONSTRAINT PK_SalesRowstore PRIMARY KEY CLUSTERED (SaleId));
CREATE TABLE Lab44.SalesColumnstore
 (SaleId bigint NOT NULL, SaleDate date NOT NULL, StoreId int NOT NULL,
  ProductId int NOT NULL, Quantity int NOT NULL, NetAmount decimal(12,2) NOT NULL);
CREATE CLUSTERED COLUMNSTORE INDEX CCI_SalesColumnstore ON Lab44.SalesColumnstore;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

جدول‌ها هنوز داده ندارن. با generator محدود و deterministic داده بساز، تعداد و توزیع رو برابر نگه دار، سپس یک query تحلیلی یکسان اجرا کن. ستون‌های انتخابی رو کم و predicate تاریخ رو واقعی نگه دار؛ actual plan، logical reads، CPU و زمان رو ثبت کن.

The tables are empty. Load bounded deterministic data with matching counts/distribution, then run the same analytical query. Select a few columns, use a realistic date predicate, and record actual plan, logical reads, CPU, and elapsed time.

نمونهٔ query تحلیلی / An analytical query shape
SELECT StoreId, SUM(NetAmount) AS Revenue, SUM(Quantity) AS Units
FROM Lab44.SalesColumnstore
WHERE SaleDate >= '2026-01-01' AND SaleDate < '2026-04-01'
GROUP BY StoreId;
GO

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

Rowgroup و اختلاف store روی رفتار بارگیری اثر دارن / Rowgroups and delta stores affect loading behavior

دادهٔ columnstore در rowgroupها و segmentهای ستونی سازمان می‌یابد. بارگیری ردیف‌های کم ممکنه ابتدا در اختلاف store قرار بگیرد؛ پس از بسته‌شدن rowgroup، compression ستونی انجام می‌شه. برای دیدن واقعیت از sys.dm_db_column_store_row_group_physical_stats و تعداد ردیف‌ها استفاده کن؛ روی دادهٔ تمرینی کوچک انتظار rowgroup فشردهٔ بزرگ نداشته باش.

Columnstore data is organized into rowgroups and column segments. Small inserts may first land in a delta store; compression occurs as rowgroups close. Inspect sys.dm_db_column_store_row_group_physical_stats and row counts; do not expect large compressed rowgroups from a tiny fixture.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

وضعیت rowgroup رو query کن / Inspect rowgroup state
SELECT object_id, index_id, partition_number, row_group_id,
       state_desc, total_rows, deleted_rows, trim_reason_desc
FROM sys.dm_db_column_store_row_group_physical_stats
WHERE object_id = OBJECT_ID(N'Lab44.SalesColumnstore')
ORDER BY row_group_id;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

dictionary، segment elimination و batch mode می‌توانند سود بسازند، اما actual plan و دادهٔ کافی باید. ترتیب load و اندازهٔ batch روی rowgroup کیفیت اثر می‌ذاره؛ عملیات maintenance رو از روی یک DMV بدون مشاهدهٔ بار کاری اجرا نکن.

Dictionaries, segment elimination, and batch mode can help, but require actual plans and enough data. Load order and batch size affect rowgroup quality; do not trigger maintenance from one DMV without workload context.

برای OLTP و analytics یک انتخاب اجباری وجود نداره / OLTP and analytics do not require one universal choice

اگه بیشتر درخواست‌ها یک رکورد رو می‌خوانند و چند ستون رو تغییر می‌دهند، rowstore معمولاً نقطهٔ شروع طبیعی هست. اگه گزارش‌ها بخش بزرگی از جدول و چند ستون رو aggregate می‌کنن، columnstore رو benchmark کن. در hybrid بار کاری، clustered columnstore با nonclustered rowstore index یا معماری جداگانه می‌تونه مطرح باشه؛ محدودیت‌های feature و write pattern رو بررسی کن.

For workloads that read one row and update a few columns, rowstore is a natural starting point. For reports aggregating many rows but few columns, benchmark columnstore. Hybrid workloads may combine clustered columnstore with nonclustered rowstore indexes or separate architectures; verify feature limits and write patterns.

مقایسهٔ منصفانه / Keep the comparison fair
-- Run the same predicate and projection against both tables.
SET STATISTICS IO, TIME ON;
SELECT StoreId, SUM(NetAmount)
FROM Lab44.SalesRowstore
WHERE SaleDate >= '2026-01-01' AND SaleDate < '2026-04-01'
GROUP BY StoreId;
SELECT StoreId, SUM(NetAmount)
FROM Lab44.SalesColumnstore
WHERE SaleDate >= '2026-01-01' AND SaleDate < '2026-04-01'
GROUP BY StoreId;
SET STATISTICS IO, TIME OFF;
GO

اول نتیجهٔ دو query رو از نظر درستی برابر کن؛ بعد performance رو بسنج. cache گرم/سرد، parallelism، edition، row count و parameterization نتیجه رو عوض می‌کنن. یک run برای تصمیم production کافی نیست.

First prove the two query results match; then compare performance. Cache state, parallelism, edition, row count, and parameterization affect results. One run is not enough for a production decision.

Columnstore رو با گزارش واقعی محک بزن / Validate columnstore against the real analytical workload

rowstore برای دسترسی ردیفی، columnstore برای scan و aggregate ستونی می‌تونه مناسب باشه. rowgroup و اختلاف store روی load اثر دارن؛ batch mode و compression نتیجه رو تضمین نمی‌کنن. درستی رو اول ثابت کن، سپس بار کاری کافی و شرایط قابل‌مقایسه رو benchmark کن.

Rowstore often suits row access; columnstore may suit column-oriented scans and aggregates. Rowgroups and delta stores affect loading; batch mode and compression do not guarantee a win. Prove correctness first, then benchmark enough representative data under comparable conditions.
