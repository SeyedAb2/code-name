Transaction: COMMIT، ROLLBACK و مرز واحد کار

Transactions: COMMIT, ROLLBACK, and the unit-of-work boundary

انتقال ۲۰۰ هزار تومان از حساب A به B دو UPDATE داره. اگه اولی انجام بشه و دومی fail بشه، پول از کجا میاد؟ مسئله فقط نوشتن دو statement نیست؛ باید مرزی بسازیم که هر دو تغییر با هم موفق شوند یا هیچ‌کدوم نمانند.

Transferring funds from account A to B requires two updates. If the first succeeds and the second fails, where did the money go? The problem is not just writing two statements; we need a boundary where both changes succeed together or neither remains.

دو درخواست هم‌زمان؛ همین‌جا داستان سخت می‌شهTwo requests at once: this is where it gets interesting

یه query وقتی تنهاست ممکنه کاملاً بی‌نقص به نظر بیاد. مشکل از جایی شروع می‌شه که دو session هم‌زمان سراغ همون داده می‌رن. برای «Transaction: COMMIT، ROLLBACK و مرز واحد کار» دو پنجره باز می‌کنیم، ترتیب دستورها رو دقیق نگه می‌داریم و می‌بینیم هر session چه چیزی می‌بینه، کجا منتظر می‌مونه و چه موقع کار به blocking یا deadlock می‌کشه.

A query can look perfect when it runs alone. The interesting behaviour starts when two sessions touch the same data. In “Transactions: COMMIT, ROLLBACK, and the unit-of-work boundary” we use two windows, control statement order carefully, and observe what each session sees, where it waits, and when blocking or deadlock appears.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

Transaction چند statement رو یک واحد می‌کنه / A transaction makes several statements one unit

در autocommit هر statement transaction خودش رو داره. با BEGIN TRANSACTION مرز صریح می‌گذاریم؛ COMMIT تغییرها رو نهایی می‌کنه، ROLLBACK تغییرهای آن transaction رو برمی‌گردونه. transaction جای validation یا constraint نیست؛ atomicity فقط تضمین می‌کنه مجموعهٔ تغییرها با هم commit/rollback بشه.

Under autocommit, each statement is its own transaction. BEGIN TRANSACTION creates an explicit boundary; COMMIT finalizes changes and ROLLBACK reverses that transaction's work. A transaction does not replace validation or constraints; atomicity ensures the group commits or rolls back together.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

انتقال امن در دیتابیس آزمایشی / A transfer in a disposable database
IF SCHEMA_ID(N'Lab53') IS NULL EXEC(N'CREATE SCHEMA Lab53');
DROP TABLE IF EXISTS Lab53.Account;
CREATE TABLE Lab53.Account
 (AccountId int PRIMARY KEY, Balance decimal(12,2) NOT NULL CHECK (Balance >= 0));
INSERT Lab53.Account VALUES (1,500.00),(2,100.00);
BEGIN TRANSACTION;
UPDATE Lab53.Account SET Balance=Balance-50 WHERE AccountId=1;
UPDATE Lab53.Account SET Balance=Balance+50 WHERE AccountId=2;
COMMIT TRANSACTION;
SELECT AccountId, Balance FROM Lab53.Account ORDER BY AccountId;
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

جمع balance قبل و بعد باید برابر بمونه. در برنامهٔ واقعی انتقال باید حساب مبدأ و مقصد، مبلغ مثبت، currency و concurrency هم validate بشه؛ transaction این قاعده‌های کسب‌وکار رو خودش حدس نمی‌زند.

The balance sum should match before and after. A real transfer must also validate source/destination, positive amount, currency, and concurrency; the transaction does not infer those business rules.

اگه statement دوم fail شد، مسیر خطا باید transaction رو تعیین تکلیف کند / If the second statement fails, error handling must resolve the transaction

صرفاً BEGIN/COMMIT نوشتن کافی نیست. خطای runtime می‌تونه transaction رو قابل‌commit یا غیرقابل‌commit کند؛ XACT_STATE مقدار ۱، ۰ یا ۱- رو می‌ده. با XACT_ABORT ON بسیاری از خطاهای runtime transaction رو abort می‌کنن، اما همهٔ خطاها/سناریوها رو با یک قاعده ساده فرض نکن.

BEGIN/COMMIT alone is insufficient. Runtime errors may leave a transaction committable or uncommittable; XACT_STATE returns 1, 0, or -1. With XACT_ABORT ON, many runtime errors abort the transaction, but do not assume every error scenario follows one simple rule.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

TRY/CATCH و rollback کامل در حالت لازم / TRY/CATCH with a full rollback when needed
SET XACT_ABORT ON;
BEGIN TRY
  BEGIN TRANSACTION;
  UPDATE Lab53.Account SET Balance=Balance-25 WHERE AccountId=1;
  UPDATE Lab53.Account SET Balance=Balance+25 WHERE AccountId=999; -- no row
  IF @@ROWCOUNT <> 1 THROW 50001, 'Destination account missing', 1;
  COMMIT TRANSACTION;
END TRY
BEGIN CATCH
  IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;
  SELECT ERROR_NUMBER() AS ErrorNumber, ERROR_MESSAGE() AS ErrorMessage,
         XACT_STATE() AS StateAfterRollback;
END CATCH;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

دستور THROW پس از بررسی row count خطا می‌سازه تا انتقال ناقص commit نشه. در production، catch باید خطا رو به لایهٔ برنامه منتقل یا ثبت کند؛ بلعیدن خطا و برگرداندن پاسخ موفق، integrity رو به ظاهر سالم نشان می‌ده.

THROW after checking row count prevents a partial transfer from committing. In production, CATCH should report or log the error for the application; swallowing it and returning success makes broken integrity look healthy.

Nested BEGINها transaction مستقل نمی‌سازند / Nested BEGIN does not create an independently manageable transaction

@@TRANCOUNT با BEGIN افزایش و با COMMIT یک واحد کم می‌شه، اما inner COMMIT به‌تنهایی چیزی رو durable نمی‌کنه. ROLLBACK بدون savepoint کل transaction بیرونی رو برمی‌گردونه. SAVE TRANSACTION نقطهٔ برگشت داخل transaction می‌سازه، ولی transaction غیرقابل‌commit رو نجات نمی‌ده و در distributed transaction محدودیت داره.

@@TRANCOUNT increments with BEGIN and decreases with COMMIT, but an inner COMMIT does not independently make data durable. ROLLBACK without a savepoint rolls back the outer transaction. SAVE TRANSACTION creates a rollback point, but cannot rescue an uncommittable transaction and has distributed-transaction limitations.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

Savepoint در سناریوی قابل‌برگشت / A savepoint for a recoverable sub-step
BEGIN TRANSACTION;
UPDATE Lab53.Account SET Balance=Balance-10 WHERE AccountId=1;
SAVE TRANSACTION BeforeOptionalFee;
UPDATE Lab53.Account SET Balance=Balance-5 WHERE AccountId=1;
-- If the optional step is rejected and the transaction remains committable:
ROLLBACK TRANSACTION BeforeOptionalFee;
COMMIT TRANSACTION;
SELECT @@TRANCOUNT AS OpenTransactionCount, XACT_STATE() AS TransactionState;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

بعد از آزمایش باید @@TRANCOUNT صفر باشه؛ transaction باز می‌تونه lock و log رو نگه داره. Savepoint رو جای transaction مستقل یا تضمین rollback هر نوع خطا معرفی نکن.

After the experiment, @@TRANCOUNT should be zero; an open transaction can retain locks and log. Do not present a savepoint as an independent transaction or a guarantee that every error can be partially rolled back.

Transaction رو کوتاه و مرزش رو نزدیک واحد کار نگه دار / Keep transactions short and aligned with the unit of work

transaction طولانی lockها رو نگه می‌داره، log رو فعال نگه می‌داره و بازیابی رو پرهزینه می‌کنه. داخل transaction منتظر کاربر، شبکه یا فایل نمان. محدودهٔ transaction رو با نیاز واقعی consistency هماهنگ کن و اگه چند سیستم بیرونی درگیرند، بدان transaction محلی اون‌ها رو اتمیک نمی‌کنه.

Long transactions retain locks, keep log records active, and increase recovery work. Do not wait for a user, network, or file inside a transaction. Align scope with actual consistency needs; a local database transaction does not make external systems atomic.

@@TRANCOUNT می‌گه چند سطح BEGIN ثبت شده؛ XACT_STATE قابلیت commit رو هم مشخص می‌کنه. این دو رو برای diagnosis کنار هم استفاده کن، نه به‌جای هم.

@@TRANCOUNT reports nested BEGIN count; XACT_STATE also reports whether commit is possible. Use both for diagnosis rather than treating them as interchangeable.

Transaction مرز سازگاری است؛ نه پاک‌کن خطاها / A transaction is a consistency boundary, not an error eraser

BEGIN/COMMIT چند تغییر مرتبط رو واحد می‌کنه؛ constraint و validation قانون رو تعریف می‌کنن؛ TRY/CATCH و XACT_STATE مسیر خطا رو می‌بندند. inner BEGIN مستقل نیست و transaction طولانی lock/log رو نگه می‌داره. هر transaction رو کوتاه، قابل‌مشاهده و هم‌راستا با یک واحد کار واقعی بساز.

BEGIN/COMMIT groups related changes; constraints and validation define rules; TRY/CATCH and XACT_STATE resolve failures. An inner BEGIN is not independent, and long transactions retain locks/log. Keep each transaction short, observable, and aligned with a real unit of work.

  • هر دو تغییر یا هیچ‌کدوم باقی می‌مانند / Both changes commit or neither remains.
  • row count و invariant بررسی می‌شن / Row counts and invariants are verified.
  • هیچ transaction بازی رها نمی‌شه / No transaction is left open.
