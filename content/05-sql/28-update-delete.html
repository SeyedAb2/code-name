UPDATE و DELETE؛ تغییر داده با ترمز

UPDATE and DELETE: change data with a safety brake

در گزارش، قیمت یک دسته اشتباه ثبت شده. پیش از UPDATE سریع، همان شرط رو با SELECT اجرا می‌کنیم تا ببینیم دقیقاً چه ردیف‌هایی هدف‌اند. این مکث کوتاه راه تشخیص اشتباه رو باز می‌ذاره.

A category has an incorrect price. Before a quick UPDATE, run its exact predicate as SELECT and inspect the target rows. This brief pause leaves room to catch mistakes.

پیش‌نیاز: WHERE، INSERT و constraintها · Prerequisites: WHERE, INSERT, constraintsSQL Server 2025 · T-SQLحدود ۹۰ دقیقه · ۱۸ تمرین / About 90 minutes · 18 exercises

اینجا اشتباه دیگه فقط خروجی بد نیستHere a mistake changes data, not just output

تا قبل از این، بدترین اتفاق معمولاً یه خروجی اشتباه بود. از اینجا به بعد query می‌تونه دادهٔ واقعی رو عوض کنه. برای «UPDATE و DELETE؛ تغییر داده با ترمز» عادت می‌کنیم قبل از تغییر، target رو با SELECT ببینیم، تغییر رو داخل transaction امن انجام بدیم، تعداد ردیف‌های اثرگرفته رو چک کنیم و تازه بعد تصمیم بگیریم COMMIT کنیم یا ROLLBACK.

Until now, the worst outcome was usually a wrong result set. From here on, a statement can change real data. With “UPDATE and DELETE: change data with a safety brake” we preview the target rows, make the change inside a safe transaction, inspect affected rows, and only then decide whether to COMMIT or ROLLBACK.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

همان شرط، اول SELECT / Same predicate, SELECT first

قبل از UPDATE یا DELETE، شرط رو جداگانه اجرا کن؛ ببین کلیدها، تعداد و مقدار فعلی درست‌اند. اگه پیش‌نمایش غافلگیرت کرد، داده هنوز تغییر نکرده هست.

Before UPDATE or DELETE, run the predicate separately. Check keys, row count, and current values. A surprising preview means no data has changed yet.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

پیش‌نمایش و تغییر با خروجی قبل و بعد / Preview, then capture before and after
SELECT ProductId, ProductName, UnitPrice
FROM shop.Products
WHERE CategoryId = 4 AND UnitPrice < 10;
GO

UPDATE shop.Products
SET UnitPrice = UnitPrice * 1.05
OUTPUT DELETED.ProductId, DELETED.UnitPrice AS OldPrice,
       INSERTED.UnitPrice AS NewPrice
WHERE CategoryId = 4 AND UnitPrice < 10;
GO

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

OUTPUT شاهد ردیف‌های همین statement است؛ backup یا تأیید تصمیم کسب‌وکار نیست. بعد از اجرا هم تعداد و کلیدها رو با پیش‌بینی تطبیق بده.

OUTPUT is evidence from this statement, not a backup or business approval. Reconcile affected keys and count with the preview.

WHERE جاافتاده همه رو هدف می‌گیره / A missing WHERE targets every row

UPDATE بدون WHERE همهٔ ردیف‌ها رو تغییر می‌ده؛ DELETE بدون WHERE همه رو حذف می‌کنه. روی جدول موقت تمرین می‌کنیم. حذف واقعی نیازمند مجوز، backup و برنامهٔ بازیابی متناسب است؛ برگشت حذف‌شده‌ها رو تضمین فرض نکن.

UPDATE without WHERE changes every row; DELETE without WHERE removes them all. Practice only on a temporary table. Real deletes require authorization and an appropriate backup and recovery plan; recovery is not guaranteed.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

حذف کنترل‌شده و ثبت ردیف‌های حذف‌شده / Delete selectively and capture removed rows
DELETE FROM #NewOrders
OUTPUT DELETED.OrderId, DELETED.CustomerId, DELETED.OrderStatus
WHERE OrderStatus = N'Cancelled';
GO

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

TRUNCATE TABLE برای خالی‌کردن کامل جدول هست و WHERE نداره؛ ممکنه با foreign key ارجاع‌دهنده مجاز نباشه. DELETE انتخابی هست و رفتار trigger و identity اون هم متفاوت هست. این دو رو جای هم به‌کار نبر.

TRUNCATE TABLE empties a table and has no WHERE; referencing foreign keys may prevent it. DELETE is selective and differs in trigger and identity behavior. Do not treat them as interchangeable.

تغییر آزمایشی رو rollback کن / Roll back a lab mutation

در دادهٔ تمرینی آزمایشی، تغییر رو در تراکنش انجام بده، بخوان و برگردان. ROLLBACK کار دیتابیسی همان تراکنش رو برمی‌گردونه اما الزاماً اثر بیرونی مثل ایمیل یا پیام ارسالی از trigger رو خنثی نمی‌کنه. آزمایش رو در محیط آزمایشی و قابل‌حذف و بدون side effect انجام بده.

In a lab fixture, mutate inside a transaction, inspect, and roll back. ROLLBACK reverses database work in that transaction, but may not undo external effects such as an email or message sent by a trigger. Use a disposable environment without side effects.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

تغییر، مشاهده، بازگشت / Mutate, inspect, roll back
BEGIN TRANSACTION;
UPDATE #NewOrders
SET OrderStatus = N'Paid'
OUTPUT DELETED.OrderId, DELETED.OrderStatus, INSERTED.OrderStatus
WHERE CustomerId = 42;

SELECT * FROM #NewOrders WHERE CustomerId = 42;
ROLLBACK TRANSACTION;
GO

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

تراکنش ابزار تمرین هست و جای preview رو نمی‌گیره. جزئیات isolation و commit رو در فصل خودش دنبال می‌کنیم.

A transaction is a lab tool, not a replacement for preview. Isolation and commit behavior have their own chapter.

قبل از اینکه بریم بخش بعد، سعی کن بدون نگاه‌کردن به بالا در دو جمله بگی این فصل چه مسئله‌ای رو حل می‌کنه و از کدوم خروجی می‌فهمی راه‌حلت درست بوده. اگه فقط اسم دستورها یادت مونده، هنوز یه دور دیگه مثال قبلی رو با دادهٔ متفاوت اجرا کن.

UPDATE از جدول دیگر؛ منبع باید یکتا باشه / UPDATE from another table requires an unambiguous source

در UPDATE مبتنی بر join، برای هر ردیف مقصد باید مقدار منبع مشخص و یکتا باشه. اگه چند ردیف منبع با یک کلید مقصد جور شوند، نتیجه رو نباید حدس زد. اول همان join رو SELECT کن و تکراری‌بودن کلید منبع رو بسنج.

For an update joined to another table, each target row needs one unambiguous source value. If several source rows match a target key, do not guess the result. Preview the join and verify source-key uniqueness.

اول join رو به شکل query ببین / Inspect the join as a query first
SELECT p.ProductId, p.UnitPrice, s.NewPrice
FROM shop.Products AS p
JOIN #PriceChanges AS s ON s.ProductId = p.ProductId;
GO

UPDATE p
SET UnitPrice = s.NewPrice
FROM shop.Products AS p
JOIN #PriceChanges AS s ON s.ProductId = p.ProductId;
GO

اگه #PriceChanges یک محصول رو چند بار داره، قبل از update قانون انتخاب یا تجمیع تعریف کن. syntax نمی‌تونه تصمیم کسب‌وکار رو جایگزین کند.

If the source contains a product more than once, define a winner or aggregation rule before updating. Syntax cannot replace the business rule.
