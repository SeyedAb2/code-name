tempdb، جدول موقت و spill

tempdb, temporary objects, and spills

می‌گن tempdb بزرگ شده. قبل از بزرگ‌کردن فایل باید بفهمیم چه چیزی نوشته: جدول موقت؟ نسخه‌های row-versioning؟ یا queryای که دادهٔ میانی‌اش در حافظه جا نشده و spill کرده؟

A report says tempdb has grown. Before enlarging its files, find what is writing: temporary objects, row versions, or a query whose intermediate data spilled because it did not fit in memory.

پیش‌نیاز: plan، transaction و isolation · Prerequisites: plans, transactions, and isolationفقط بار کاری محدود / Bounded workloadحدود ۹۵ دقیقه · ۱۸ تمرین / About 95 minutes · 18 exercises

دو درخواست هم‌زمان؛ همین‌جا داستان سخت می‌شهTwo requests at once: this is where it gets interesting

یه query وقتی تنهاست ممکنه کاملاً بی‌نقص به نظر بیاد. مشکل از جایی شروع می‌شه که دو session هم‌زمان سراغ همون داده می‌رن. برای «tempdb، جدول موقت و spill» دو پنجره باز می‌کنیم، ترتیب دستورها رو دقیق نگه می‌داریم و می‌بینیم هر session چه چیزی می‌بینه، کجا منتظر می‌مونه و چه موقع کار به blocking یا deadlock می‌کشه.

A query can look perfect when it runs alone. The interesting behaviour starts when two sessions touch the same data. In “tempdb, temporary objects, and spills” we use two windows, control statement order carefully, and observe what each session sees, where it waits, and when blocking or deadlock appears.

قرارمون توی این فصلOur rule for this chapter

هرجا query یا command می‌زنیم، همون‌جا می‌گیم چرا زدیمش، کدوم قسمت خروجی مهمه و اگه نتیجه فرق داشت اول چی رو چک کنی. قرار نیست چیزی رو فقط چون «معمولاً این‌طوریه» قبول کنیم.

Whenever we run a query or command, we state why, identify the important evidence, and say what to check first if the result differs. We do not accept behaviour merely because it is “usually like that.”

tempdb محل کار موقت است، نه سطل زباله / tempdb is workspace, not a trash can

SQL Server از tempdb برای objectهای موقت و کارهای داخلی استفاده می‌کنه. مصرف به‌تنهایی نشانهٔ خرابی نیست؛ رشد پیوسته یا کمبود فضا رو با session و نوع allocation بررسی کن. فایل دیتابیس رو دستی پاک نکن.

SQL Server uses tempdb for temporary objects and internal work. Usage alone is not a fault; investigate sustained growth and space pressure by session and allocation type. Never delete database files manually.

این تکه کد رو فقط کپی نکن. اول برای خودت بگو اگه مدل ذهنی‌مون درست باشه چه چیزی باید ببینیم، بعد اجراش کن.

Do not just copy this block. First state what you expect to observe if the mental model is correct, then run it.

allocation نشست‌ها رو بررسی کن / Inspect session allocations
SELECT session_id, user_objects_alloc_page_count, user_objects_dealloc_page_count,
       internal_objects_alloc_page_count, internal_objects_dealloc_page_count
FROM sys.dm_db_session_space_usage
ORDER BY (user_objects_alloc_page_count + internal_objects_alloc_page_count) DESC;

چیزی که باید از این مثال نگه داری اسم دستور نیست؛ رابطهٔ بین ورودی، خروجی و مدلیه که داریم می‌سازیم.

The thing to keep from this example is not the command name but the relationship between input, output, and the model we are building.

شمارنده‌ها allocation نشست رو نشان می‌دهند، نه علت قطعی یا تاریخچهٔ رشد. دسترسی DMV هم ممکنه به مجوز وابسته باشه.

Counters show session allocations, not definitive causes or growth history. DMV visibility depends on permissions.

عمر objectها رو با هم قاطی نکن / Do not confuse object lifetimes

جدول #temp در tempdb و در scope نشست یا procedure عمر داره. table variable هم «همیشه فقط در حافظه» نیست و ممکنه از storage پشتیبانی‌شده استفاده کند. CTE نام یک query expression است، نه تضمین materialization.

A #temp table lives in tempdb for its session or procedure scope. A table variable is not “always memory-only” and may use backed storage. A CTE names a query expression; it does not promise materialization.

اینجا هدف خود دستور نیست؛ داریم باهاش یک ادعا رو امتحان می‌کنیم. قبل از Run، نتیجهٔ مورد انتظار رو توی یک جمله بگو.

The command is not the point; it is an experiment. Before Run, state the expected observation in one sentence.

مقایسهٔ کوچک در همان نشست / A small same-session comparison
CREATE TABLE #Work (Id int NOT NULL PRIMARY KEY, Label varchar(40) NOT NULL);
INSERT #Work VALUES (1,'alpha'),(2,'beta');
DECLARE @Small TABLE (Id int PRIMARY KEY, Label varchar(40));
INSERT @Small VALUES (1,'alpha'),(2,'beta');
WITH NamedRows AS (SELECT Id,Label FROM #Work)
SELECT w.Id,w.Label,s.Label AS VariableLabel,c.Label AS CteLabel
FROM #Work AS w JOIN @Small AS s ON s.Id=w.Id
JOIN NamedRows AS c ON c.Id=w.Id;
DROP TABLE #Work;

اگه خروجی سیستم تو فرق داشت، سریع نتیجه نگیر که فصل غلطه. اول نسخه، دادهٔ تمرینی، database جاری و session رو چک کن؛ بعد سراغ فرضیهٔ بعدی برو.

If your output differs, do not jump to a conclusion. Check version, fixture, current database, and session state before changing the hypothesis.

انتخاب رو بر اساس تعداد ردیف، نیاز به index/statistics و عمر داده انجام بده. نسخهٔ SQL Server و شکل بار کاری می‌تونه رفتار plan رو عوض کند.

Choose based on cardinality, indexing/statistics needs, and lifetime. SQL Server version and workload shape can change plan behavior.

spill رو از Actual Plan پیدا کن / Find spills in the actual plan

Sort و hash ممکنه memory grant بگیرند. اگه grant کافی نباشه، کار میانی روی tempdb spill می‌کنه. warning و تخمین ردیف رو در Actual Execution Plan ببین؛ بعد توزیع داده، statistics و query رو بسنج. صرف مصرف tempdb مدرک spill نیست.

Sort and hash operators request memory grants. If the grant is insufficient, intermediate work can spill to tempdb. Inspect warnings and row estimates in the actual plan, then check data distribution, statistics, and query shape. tempdb usage alone is not proof of a spill.

قبل از اجرا یه حدس بزن: از خروجی این مثال دقیقاً دنبال چه نشونه‌ای هستی؟ عدد دقیق لازم نیست؛ فقط معلوم کن چی قراره ادعای این بخش رو تأیید یا رد کنه.

Before running this, predict what evidence you expect from the output. You do not need the exact value; decide what would support or reject the claim in this section.

query محدود؛ plan رو در SSMS بگیر / Bounded query; capture its plan in SSMS
SELECT TOP (5000) EventId, EventAt, Payload
FROM Lab48.Event
ORDER BY Payload, EventAt;
-- Enable Include Actual Execution Plan; inspect Sort/Hash warnings.

بعد از اجرا فقط دنبال «موفق شد» نباش. خروجی رو با حدسی که قبلش داشتی مقایسه کن؛ اگه فرق داشت، همون اختلاف بهترین نقطه برای ادامهٔ بررسیه.

Do not stop at “it succeeded.” Compare the output with your prediction; any mismatch is the best place to continue investigating.

این query فقط اگه داده و شرایط memory grant بخواهند spill می‌کنه. برای اجبار به spill، host رو تحت فشار نگذار و حجم نامحدود نساز. cache و اجرای هم‌زمان نتیجه رو تغییر می‌دهند.

This query spills only if data and grant conditions require it. Do not pressure the host or generate unbounded data to force one. Cache and concurrency affect results.

مصرف رو با نوع allocation و زمان بسنج / Diagnose by allocation type and time

مصرف tempdb می‌تونه از user object، internal object یا version store باشه. نمای فایل یک نمونهٔ لحظه‌ای هست و علت تاریخی رو ثابت نمی‌کنه؛ زمان ثبت رو نگه دار و در صورت نیاز چند نمونه بگیر.

tempdb use can come from user objects, internal objects, or the version store. A file view is a snapshot, not historical proof; timestamp it and collect repeated samples if needed.

فضای فعلی فایل‌های tempdb / Current tempdb file-space snapshot
USE tempdb;
SELECT SUM(user_object_reserved_page_count)*8.0/1024 AS user_mb,
       SUM(internal_object_reserved_page_count)*8.0/1024 AS internal_mb,
       SUM(version_store_reserved_page_count)*8.0/1024 AS version_mb,
       SUM(unallocated_extent_page_count)*8.0/1024 AS free_mb
FROM sys.dm_db_file_space_usage;

اگه خروجی با symptom جور نیست، session، query فعال، isolation و maintenance هم‌زمان رو بررسی کن. shrink دوره‌ای درمان علت نیست و ممکنه رشد مجدد پرهزینه بسازد.

If the snapshot does not match the symptom, inspect sessions, active queries, isolation, and concurrent maintenance. Routine shrinking does not fix the cause and can make regrowth expensive.
