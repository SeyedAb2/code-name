Redo، Undo، purge و checkpoint

Redo, Undo, Purge, and Checkpoints

بعد از crash، Server باید بفهمد کدام تغییرها را دوباره اعمال کند؛ در عین حال یک transaction قدیمی هنوز باید نسخهٔ قبلی ردیف را ببیند. این دو مسئله جواب یکسان ندارند. با یک update محدود و دو session، مسیر redo، undo و پاک‌سازی نسخه‌های قدیمی را از هم جدا می‌کنیم.

After a crash, the server must know which changes to reapply, while an old transaction may still need to see an earlier row version. Those are different problems. With a bounded update and two sessions, we’ll distinguish redo, undo, and removal of obsolete versions.

پیش‌نیازPrerequisite: فصل ۱۰ · page و buffer poolمحیط مرجعLab baseline: MySQL 9.7.2 · دو session InnoDBزمانTime: ۹۵ دقیقه · ۱۸ تمرین

سه سؤال شبیه، سه سازوکار متفاوتThree related questions, three different mechanisms

یک transaction عدد موجودی را از ۱۰ به ۹ تغییر می‌دهد. پیش از flush شدن page، Server ناگهان متوقف می‌شود. هم‌زمان یک transaction دیگر از قبل snapshot گرفته و هنوز باید مقدار ۱۰ را ببیند. بعد از commit و پایان همهٔ readerها هم، نسخهٔ قدیمی باید روزی پاک شود. redo، undo و purge هرکدام کدام بخش را حل می‌کنند؟

A transaction changes stock from 10 to 9. Before the page is flushed, the server stops unexpectedly. Another transaction already holds a snapshot and must still see 10. After commit and after every reader is done, the old version should eventually be removed. Which part belongs to redo, undo, and purge?

Redo اطلاعات لازم برای بازسازی تغییرهای ثبت‌شده را در crash recovery فراهم می‌کند. Undo تغییر را برای rollback و ساخت نسخهٔ قدیمی موردنیاز consistent read نگه می‌دارد. Purge بعدتر رکوردهای حذف‌علامت‌خورده و undoای را که دیگر برای transaction فعالی لازم نیست کنار می‌گذارد. Checkpoint هم فاصلهٔ redo و pageهای تغییرکرده را مدیریت می‌کند؛ خودِ checkpoint معادل backup نیست.

Redo provides information to reapply recorded changes during crash recovery. Undo supports rollback and reconstructs older versions for consistent reads. Purge later removes delete-marked records and undo no active transaction needs. Checkpointing coordinates redo progress and modified pages; a checkpoint is not a backup.

مسیر تغییر از buffer pool تا recoveryA change path from buffer pool to recovery

Redo می‌گوید چه تغییری دوباره اعمال شودRedo records changes to reapply

page تغییرکرده ممکن است مدتی فقط در buffer pool باشد. redo تغییرهای لازم را ثبت می‌کند تا پس از shutdown غیرمنتظره recovery بتواند از checkpoint جلو بیاید و تغییرهای ثبت‌شده‌ای را که هنوز در data file نیستند replay کند. این mechanism با binary log یکی نیست و جای backup هم نمی‌گیرد.

A changed page may remain in the buffer pool for a while. Redo records changes so recovery after an unexpected shutdown can start from a checkpoint and replay logged changes not yet present in data files. This is not the binary log and does not replace backups.

LSNها را فقط به‌عنوان پیشرفت log بخوانRead LSNs as log progress
SHOW GLOBAL STATUS LIKE 'Innodb_redo_log_%';
SHOW ENGINE INNODB STATUS;

مقادیر LSN و checkpoint نقطهٔ ثبت‌شدهٔ log را نشان می‌دهند. از یک snapshot نمی‌توان زمان crash یا دوام یک commit مشخص را اثبات کرد؛ تنظیم durability و وضعیت storage هم دخیل‌اند و در مبحث transaction/recovery دقیق‌تر بررسی می‌شوند.

LSN and checkpoint values show recorded log positions. One snapshot cannot prove the crash time or durability of a particular commit; durability settings and storage behavior also matter and are examined further in transaction/recovery topics.

Undo نسخهٔ قبلی را برای نیاز واقعی نگه می‌داردUndo retains earlier versions for a reason

در دو connection روی یک ردیف آزمایش کار می‌کنیم. Session A یک consistent read transaction را باز می‌کند و مقدار اولیه را می‌خواند. Session B مقدار را update و commit می‌کند. A تا پایان snapshot باید نسخهٔ سازگار قبلی را ببیند؛ reader تازه مقدار جدید را می‌بیند.

We use two connections against one lab row. Session A opens a consistent-read transaction and reads the original value. Session B updates and commits it. A continues seeing its snapshot version, while a new reader sees the new value.

نشست A — snapshot را باز نگه دارSession A — keep the snapshot open
USE codenames_engine_lab;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM txn_row WHERE id=1;
نشست B — update و commitSession B — update and commit
USE codenames_engine_lab;
UPDATE txn_row SET note='new committed value' WHERE id=1;
COMMIT;
SELECT * FROM txn_row WHERE id=1;

حالا در A همان SELECT را دوباره اجرا کن؛ تا وقتی transaction A باز است باید view قبلی‌اش را ببیند. سپس A را commit کن و از connection تازه مقدار جدید را بخوان. Undo برای rollback و consistent read مفید است؛ نگهداری نسخهٔ قدیمی تا وقتی reader لازم دارد، فضای بیشتری می‌خواهد.

Run the SELECT again in A; while its transaction remains open, it should retain its earlier read view. Commit A, then read from a fresh connection to see the new value. Undo supports rollback and consistent reads; keeping an older version while a reader needs it consumes space.

Purge زودتر از تمام‌شدن reader پاک نمی‌کندPurge waits until readers no longer need the version

بعد از commit نویسنده، نسخهٔ قدیمی الزاماً همان لحظه از storage حذف نمی‌شود. transactionهای باز ممکن است هنوز آن را لازم داشته باشند. Purge background نسخه‌های غیرضروری را در ادامه کنار می‌گذارد. transaction طولانی می‌تواند undo history را نگه دارد و History list length را بالا ببرد؛ آن مقدار نشانه است، نه علت قطعی یک مشکل performance.

After the writer commits, the old version is not necessarily removed immediately. Open transactions may still need it. Background purge later discards obsolete versions. A long-running transaction can retain undo history and increase History list length; that value is evidence, not by itself a complete performance diagnosis.

مدرک transaction و history را بخوانInspect transaction and history evidence
SHOW ENGINE INNODB STATUS;

بخش TRANSACTIONS را پیدا کن و snapshot را timestamp بزن. اگر history list length بالا رفت، transactionهای طولانی و workload نوشتن را بررسی کن؛ تنظیم purge را بی‌تشخیص بالا و پایین نکن.

Find TRANSACTIONS and timestamp the snapshot. If history-list length rises, inspect long-running transactions and write workload; do not tune purge settings blindly.

Checkpoint یک flush یک‌باره نیستA checkpoint is not one giant flush

InnoDB از fuzzy checkpointing استفاده می‌کند: pageهای dirty را در batchهای کوچک flush می‌کند تا لازم نباشد همهٔ buffer pool را یک‌جا متوقف و بنویسد. checkpoint نشان می‌دهد تا کجای تغییرها در data file قابل‌اتکا است؛ crash recovery از آن نقطه log را دنبال می‌کند. هرچه فاصلهٔ checkpoint و log بزرگ‌تر باشد، work recovery می‌تواند بیشتر شود؛ این به معنی از بین‌رفتن commitهای سالم نیست.

InnoDB uses fuzzy checkpointing, flushing dirty pages in small batches instead of stopping to write the entire buffer pool at once. A checkpoint indicates progress in what is reflected in data files; crash recovery follows the log from there. A larger distance can mean more recovery work, not that valid commits are necessarily lost.

برای مشاهدهٔ read-only، checkpoint LSN و current LSN را از status بخوان. مقدارها در طول workload حرکت می‌کنند. این فصل ظرفیت redo را تغییر نمی‌دهد؛ آن یک تصمیم tuning است که باید با disk، write workload و recovery expectations سنجیده شود.

For a read-only observation, inspect checkpoint and current LSNs. They move as work proceeds. This chapter does not resize redo capacity; that tuning decision must account for disk, write workload, and recovery expectations.

وضعیت recovery و checkpointRecovery and checkpoint status
SHOW ENGINE INNODB STATUS;
SHOW GLOBAL STATUS LIKE 'Innodb_redo_log_checkpoint_lsn';
SHOW GLOBAL STATUS LIKE 'Innodb_redo_log_current_lsn';

۱۸ تمرین SQL18 SQL exercises

آزمایش دو connection را روی schema codenames_engine_lab انجام بده. Session A را عمداً فقط تا پایان تمرین باز نگه دار؛ هیچ Serverی را kill یا restart نمی‌کنیم.

Run two-session exercises in codenames_engine_lab. Keep session A open only through the test; we do not kill or restart any server.

1) redo capacity را بخوان / Read redo capacity

ظرفیت پیکربندی‌شده را query کن.

Query configured redo capacity.

SQL / SQL
SELECT @@innodb_redo_log_capacity;

config است، نه اندازهٔ دقیق کار recovery در همین لحظه.

This is configuration, not a measurement of current recovery work.

2) LSNهای redo را ثبت کن / Record redo LSNs

current و checkpoint LSN را با status ثبت کن.

Record current and checkpoint LSN evidence.

SQL / SQL
SHOW ENGINE INNODB STATUS; SHOW GLOBAL STATUS LIKE 'Innodb_redo_log_%lsn';

این یک snapshot از progress است؛ تغییر بین دو snapshot را جدا بسنج.

This is a progress snapshot; measure changes between timestamped samples.

3) data file flush را از log جدا کن / Separate data-file flush from log

status را بخوان و checkpoint را از current LSN در گزارش جدا بنویس.

Inspect status and report checkpoint separately from current LSN.

SQL / SQL
SHOW ENGINE INNODB STATUS;

هرکدام شاهد متفاوتی از پیشرفت‌اند؛ checkpoint همان binlog position نیست.

They represent different progress evidence; a checkpoint is not a binlog position.

4) undo و rollback / Undo and rollback

در transaction یک update بزن و rollback کن؛ مقدار قبل/بعد را query کن.

Update inside a transaction, roll back, and query before/after.

SQL / SQL
SELECT note FROM codenames_engine_lab.txn_row WHERE id=1; START TRANSACTION; UPDATE codenames_engine_lab.txn_row SET note='uncommitted test' WHERE id=1; ROLLBACK; SELECT note FROM codenames_engine_lab.txn_row WHERE id=1;

مقدار بعد از rollback باید با مقدار قبلی برابر باشد.

The post-rollback value should match the original value.

5) دو snapshot را مقایسه کن / Compare two read views

A را با REPEATABLE READ باز کن، در B update/commit کن، سپس SELECT را در هر دو اجرا کن.

Open REPEATABLE READ in A, update/commit in B, then SELECT in both.

SQL دو نشست / Two-session SQL

در A:

SET TRANSACTION ISOLATION LEVEL REPEATABLE READ; START TRANSACTION; SELECT note FROM txn_row WHERE id=1;

In B:

UPDATE txn_row SET note='committed v2' WHERE id=1; COMMIT; SELECT note FROM txn_row WHERE id=1;

در A دوباره SELECT کن: snapshot همان مقدار قبلی را می‌بیند. بعد A را COMMIT کن؛ باز نگه‌داشتن transaction را طولانی نکن.

Query again in A: its snapshot still sees the old value. Then COMMIT A; do not keep the transaction open unnecessarily.

6) reader قدیمی را ببند / Release the old read view

در A transaction باز را commit کن و query تازه بزن.

Commit A’s open transaction and issue a fresh query.

SQL / SQL
COMMIT; SELECT note FROM codenames_engine_lab.txn_row WHERE id=1;

connection بعد از پایان snapshot مقدار commitشدهٔ فعلی را می‌بیند.

After the snapshot ends, the connection sees the current committed value.

7) History list length را پیدا کن / Find history-list length

از InnoDB status مقدار history list length را ثبت کن.

Record history-list length from InnoDB status.

SQL / SQL
SHOW ENGINE INNODB STATUS;

مقدار را همراه زمان و وضعیت transactionهای باز ثبت کن؛ مقدار به‌تنهایی diagnosis نیست.

Record it with timestamp and open-transaction context; it is not a diagnosis alone.

8) update و سپس status / Update then inspect

یک row را تغییر بده، commit کن و status را دوباره بخوان.

Update one row, commit, then inspect status again.

SQL / SQL
UPDATE codenames_engine_lab.txn_row SET note='observed commit' WHERE id=1; COMMIT; SHOW ENGINE INNODB STATUS;

این اثر هم‌زمان دیگر workloadها را هم شامل می‌شود.

The observation also includes concurrent workloads.

9) delete را با purge یکی نکن / Distinguish DELETE from purge

ردیف disposable بساز، حذفش کن و status را بخوان؛ حذف منطقی SQL را با آزادشدن فوری page یکی ندان.

Create and delete a disposable row, then inspect status; do not equate SQL deletion with immediate page reclamation.

SQL / SQL
INSERT INTO codenames_engine_lab.txn_row VALUES(90,'purge lab'); DELETE FROM codenames_engine_lab.txn_row WHERE id=90; SHOW ENGINE INNODB STATUS;

خود row برای query عادی حذف شده، اما پاک‌سازی فیزیکی undo/page می‌تواند بعدتر انجام شود.

The row is logically gone, while physical cleanup of undo/pages may happen later.

10) transaction طولانی را مشاهده کن / Observe a long read view

A را باز نگه دار، یک update محدود در B commit کن و بعد وضعیت transaction/history را ثبت کن.

Keep A open, commit one bounded update in B, then capture transaction/history status.

SQL دو نشست / Two-session SQL

در A:

START TRANSACTION; SELECT * FROM txn_row WHERE id=1;

In B:

UPDATE txn_row SET note='v3' WHERE id=1; COMMIT; SHOW ENGINE INNODB STATUS;

history را پس از مشاهده ثبت کن، سپس A را commit کن؛ عمداً version قدیمی را روی server مشترک انباشته نکن.

Capture history, then commit A; do not intentionally accumulate old versions on a shared server.

11) checkpoint و backup را جدا کن / Separate checkpoint and backup

LSN checkpoint را از status بگیر و یک جملهٔ دقیق بنویس که چرا این خروجی backup نیست.

Read checkpoint LSN and state precisely why it is not a backup.

SQL / SQL
SHOW ENGINE INNODB STATUS;

checkpoint داخل چرخهٔ recovery/flush است؛ نسخهٔ مستقل قابل‌بازیابی از همهٔ داده نمی‌سازد.

A checkpoint is part of recovery/flushing; it does not create an independent recoverable copy.

12) undo read view را بستن / End the reader’s view

در session A transaction را پایان بده و از A و یک connection تازه مقدار را بخوان.

End A’s transaction and read the value in A and a fresh connection.

SQL / SQL
COMMIT; SELECT note FROM txn_row WHERE id=1;

هر دو باید مقدار commitشدهٔ current را ببینند، مگر تغییر دیگری هم‌زمان انجام شود.

Both should now see the current committed value unless another change occurs concurrently.

13) dirty page و redo را یکی نکن / Distinguish dirty pages from redo

status را بخوان و تعداد modified db pages و current LSN را جدا گزارش کن.

Report modified-page count and current LSN separately.

SQL / SQL
SHOW ENGINE INNODB STATUS; SHOW GLOBAL STATUS LIKE 'Innodb_redo_log_current_lsn';

یکی pageهای تغییرکرده در buffer pool را توصیف می‌کند و دیگری پیشرفت redo را؛ واحدها و معنایشان یکی نیست.

One describes modified buffer-pool pages, the other redo progress; their units and meanings differ.

14) redo file metadata را query کن / Query redo-file metadata

در MySQL 9.7، فایل‌های active redo و اندازه‌شان را از Performance Schema بخوان.

On MySQL 9.7, inspect active redo files and sizes in Performance Schema.

SQL / SQL
SELECT FILE_ID,START_LSN,END_LSN,SIZE_IN_BYTES,IS_FULL FROM performance_schema.innodb_redo_log_files;

دسترسی و خروجی به نسخه و privilege وابسته است؛ جدول را فقط اگر موجود و مجاز است بخوان.

Availability and output depend on version and privileges; query it only when present and permitted.

15) commit و flush را برابر فرض نکن / Do not equate commit with a data-page flush

پس از commit، redo و status را بررسی کن و توضیح بده چرا data page ممکن است بعدتر flush شود.

After commit, inspect redo/status and explain why a data page may flush later.

SQL / SQL
UPDATE codenames_engine_lab.txn_row SET note='committed row' WHERE id=1; COMMIT; SHOW ENGINE INNODB STATUS;

redo و durability configuration در commit نقش دارند؛ این آزمایش flush فوری همهٔ data pageها را تضمین نمی‌کند.

Redo and durability configuration matter at commit; this test does not guarantee every data page is flushed immediately.

16) purge را با یک knob تنظیم نکن / Avoid blind purge tuning

queryی برای transactionهای جاری از Performance Schema بنویس و از روی نتیجه بگو چه transactionهایی ممکن است read view را نگه دارند.

Query active transactions from Performance Schema and identify which may retain a read view.

SQL / SQL
SELECT trx_id,trx_state,trx_started,trx_mysql_thread_id,trx_query FROM information_schema.innodb_trx ORDER BY trx_started;

فعال‌بودن transaction سرنخ است؛ برای تعیین اثر باید isolation، read view و workload را هم بشناسی.

An active transaction is a clue; determine its effect using isolation, read view, and workload context.

17) سه سازوکار را به یک query ربط بده / Connect mechanisms to one update

یک UPDATE کنترل‌شده بزن، آن را commit کن، سپس status و نسخهٔ قابل‌خواندن session A را ثبت کن.

Run and commit one controlled UPDATE, then capture status and what session A can read.

SQL / SQL
UPDATE codenames_engine_lab.txn_row SET note='mechanism check' WHERE id=1; COMMIT; SHOW ENGINE INNODB STATUS; SELECT note FROM codenames_engine_lab.txn_row WHERE id=1;

redo برای recovery، undo برای نسخه/rollback و purge برای پاک‌سازی بعد از بی‌نیازی کار می‌کند؛ status به‌تنهایی کل چرخه را ثابت نمی‌کند.

Redo supports recovery, undo supports versions/rollback, and purge cleans up after versions are no longer needed; status alone does not prove the entire lifecycle.

18) گزارش رخداد بنویس / Write a storage-lifecycle incident report

گزارش SQL بساز که LSN، buffer pool dirty pages، transactionهای باز و history list length را مستند کند؛ برای هر نتیجه یک محدودیت بنویس.

Build a SQL evidence report for LSN, dirty buffer pages, active transactions, and history-list length, with one limitation for each conclusion.

Query package / بستهٔ query
SHOW ENGINE INNODB STATUS; SHOW GLOBAL STATUS LIKE 'Innodb_redo_log_%lsn'; SELECT trx_id,trx_state,trx_started,trx_mysql_thread_id FROM information_schema.innodb_trx ORDER BY trx_started;

این snapshot علت دقیق کندی یا crash را ثابت نمی‌کند؛ زمان‌بندی، storage و error log هم برای incident واقعی لازم‌اند.

These snapshots do not prove the exact cause of a slowdown or crash; timestamps, storage, and error logs are also needed for a real incident.

نسخهٔ قدیمی را نگه می‌داریم، اما نه برای همیشهKeep old versions when needed—not forever

redo برای replay، undo برای rollback و snapshot خواندن، purge برای آزادکردن نسخهٔ بی‌نیاز، و checkpoint برای پیشرفت تدریجی pageهاست. هیچ‌کدام backup مستقل نیست. فصل بعد B+Tree و index پایه را از دید ساختار صفحه دنبال می‌کنیم؛ آن‌جا می‌بینیم چرا نوع دسترسی query به شکل درخت وابسته است.

Redo replays changes, undo supports rollback and read snapshots, purge frees versions no longer needed, and checkpointing gradually advances page flushing. None is an independent backup. Next we examine B+ trees and index basics to understand how query access depends on tree structure.
