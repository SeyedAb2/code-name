Redo، Undo، purge و checkpoint

Redo, Undo, Purge, and Checkpoints

بعد از crash، Server باید بفهمد کدام تغییرها رو دوباره اعمال کند؛ در عین حال یک transaction قدیمی هنوز باید نسخهٔ قبلی ردیف رو ببیند. این دو مسئله جواب یکسان ندارن. با یک update محدود و دو session، مسیر redo، undo و پاک‌سازی نسخه‌های قدیمی رو از هم جدا می‌کنیم.

After a crash, the server must know which changes to reapply, while an old transaction may still need to see an earlier row version. Those are different problems. With a bounded update and two sessions, we’ll distinguish redo, undo, and removal of obsolete versions.

سه سؤال شبیه، سه سازوکار متفاوتThree related questions, three different mechanisms

یک transaction عدد موجودی رو از ۱۰ به ۹ تغییر می‌ده. پیش از flush شدن page، Server ناگهان متوقف می‌شه. هم‌زمان یک transaction دیگر از قبل snapshot گرفته و هنوز باید مقدار ۱۰ رو ببیند. بعد از commit و پایان همهٔ readerها هم، نسخهٔ قدیمی باید روزی پاک شود. redo، undo و purge هرکدام کدام بخش رو حل می‌کنن؟

A transaction changes stock from 10 to 9. Before the page is flushed, the server stops unexpectedly. Another transaction already holds a snapshot and must still see 10. After commit and after every reader is done, the old version should eventually be removed. Which part belongs to redo, undo, and purge?

Redo اطلاعات لازم برای بازسازی تغییرهای ثبت‌شده رو در crash recovery فراهم می‌کنه. Undo تغییر رو برای rollback و ساخت نسخهٔ قدیمی موردنیاز consistent read نگه می‌دارد. Purge بعدتر رکوردهای حذف‌علامت‌خورده و undoای رو که دیگر برای transaction فعالی لازم نیست کنار می‌ذاره. Checkpoint هم فاصلهٔ redo و pageهای تغییرکرده رو مدیریت می‌کنه؛ خودِ checkpoint معادل backup نیست.

Redo provides information to reapply recorded changes during crash recovery. Undo supports rollback and reconstructs older versions for consistent reads. Purge later removes delete-marked records and undo no active transaction needs. Checkpointing coordinates redo progress and modified pages; a checkpoint is not a backup.

مسیر تغییر از buffer pool تا recoveryA change path from buffer pool to recovery

Redo می‌گه چه تغییری دوباره اعمال شودRedo records changes to reapply

page تغییرکرده ممکنه مدتی فقط در buffer pool باشه. redo تغییرهای لازم رو ثبت می‌کنه تا پس از shutdown غیرمنتظره recovery بتواند از checkpoint جلو بیاید و تغییرهای ثبت‌شده‌ای رو که هنوز در data file نیستند replay کند. این mechanism با binary log یکی نیست و جای backup هم نمی‌گیره.

A changed page may remain in the buffer pool for a while. Redo records changes so recovery after an unexpected shutdown can start from a checkpoint and replay logged changes not yet present in data files. This is not the binary log and does not replace backups.

LSNها رو فقط به‌عنوان پیشرفت log بخوانRead LSNs as log progress
SHOW GLOBAL STATUS LIKE 'Innodb_redo_log_%';
SHOW ENGINE INNODB STATUS;

مقادیر LSN و checkpoint نقطهٔ ثبت‌شدهٔ log رو نشان می‌دن. از یک snapshot نمی‌توان زمان crash یا دوام یک commit مشخص رو اثبات کرد؛ تنظیم durability و وضعیت storage هم دخیل‌اند و در مبحث transaction/recovery دقیق‌تر بررسی می‌شوند.

LSN and checkpoint values show recorded log positions. One snapshot cannot prove the crash time or durability of a particular commit; durability settings and storage behavior also matter and are examined further in transaction/recovery topics.

Undo نسخهٔ قبلی رو برای نیاز واقعی نگه می‌داردUndo retains earlier versions for a reason

در دو connection روی یک ردیف آزمایش کار می‌کنیم. Session A یک consistent read transaction رو باز می‌کنه و مقدار اولیه رو می‌خواند. Session B مقدار رو update و commit می‌کنه. A تا پایان snapshot باید نسخهٔ سازگار قبلی رو ببیند؛ reader تازه مقدار جدید رو می‌بیند.

We use two connections against one lab row. Session A opens a consistent-read transaction and reads the original value. Session B updates and commits it. A continues seeing its snapshot version, while a new reader sees the new value.

نشست A — snapshot رو باز نگه دارSession A — keep the snapshot open
USE codenames_engine_lab;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM txn_row WHERE id=1;
نشست B — update و commitSession B — update and commit
USE codenames_engine_lab;
UPDATE txn_row SET note='new committed value' WHERE id=1;
COMMIT;
SELECT * FROM txn_row WHERE id=1;

حالا در A همان SELECT رو دوباره اجرا کن؛ تا وقتی transaction A باز هست باید view قبلی‌اش رو ببیند. سپس A رو commit کن و از connection تازه مقدار جدید رو بخوان. Undo برای rollback و consistent read مفید است؛ نگهداری نسخهٔ قدیمی تا وقتی reader لازم دارد، فضای بیشتری می‌خواهد.

Run the SELECT again in A; while its transaction remains open, it should retain its earlier read view. Commit A, then read from a fresh connection to see the new value. Undo supports rollback and consistent reads; keeping an older version while a reader needs it consumes space.

Purge زودتر از تمام‌شدن reader پاک نمی‌کنهPurge waits until readers no longer need the version

بعد از commit نویسنده، نسخهٔ قدیمی الزاماً همان لحظه از storage حذف نمی‌شه. transactionهای باز ممکنه هنوز آن رو لازم داشته باشند. Purge background نسخه‌های غیرضروری رو حالا کنار می‌ذاره. transaction طولانی می‌تونه undo history رو نگه داره و History list length رو بالا ببرد؛ آن مقدار نشانه است، نه علت قطعی یک مشکل performance.

After the writer commits, the old version is not necessarily removed immediately. Open transactions may still need it. Background purge later discards obsolete versions. A long-running transaction can retain undo history and increase History list length; that value is evidence, not by itself a complete performance diagnosis.

مدرک transaction و history رو بخوانInspect transaction and history evidence
SHOW ENGINE INNODB STATUS;

بخش TRANSACTIONS رو پیدا کن و snapshot رو timestamp بزن. اگه history list length بالا رفت، transactionهای طولانی و workload نوشتن رو بررسی کن؛ تنظیم purge رو بی‌تشخیص بالا و پایین نکن.

Find TRANSACTIONS and timestamp the snapshot. If history-list length rises, inspect long-running transactions and write workload; do not tune purge settings blindly.

Checkpoint یک flush یک‌باره نیستA checkpoint is not one giant flush

InnoDB از fuzzy checkpointing استفاده می‌کنه: pageهای dirty رو در batchهای کوچک flush می‌کنه تا لازم نباشه همهٔ buffer pool رو یک‌جا متوقف و بنویسد. checkpoint نشان می‌ده تا کجای تغییرها در data file قابل‌اتکا است؛ crash recovery از آن نقطه log رو دنبال می‌کنه. هرچه فاصلهٔ checkpoint و log بزرگ‌تر باشه، work recovery می‌تونه بیشتر شود؛ این به معنی از بین‌رفتن commitهای سالم نیست.

InnoDB uses fuzzy checkpointing, flushing dirty pages in small batches instead of stopping to write the entire buffer pool at once. A checkpoint indicates progress in what is reflected in data files; crash recovery follows the log from there. A larger distance can mean more recovery work, not that valid commits are necessarily lost.

برای مشاهدهٔ read-only، checkpoint LSN و current LSN رو از status بخوان. مقدارها در طول workload حرکت می‌کنن. این فصل ظرفیت redo رو تغییر نمی‌ده؛ آن یک تصمیم tuning هست که باید با disk، write workload و recovery expectations سنجیده شود.

For a read-only observation, inspect checkpoint and current LSNs. They move as work proceeds. This chapter does not resize redo capacity; that tuning decision must account for disk, write workload, and recovery expectations.
