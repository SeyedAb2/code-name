یک DELETE اشتباه اجرا شد؛ backup دیشب کافی است؟

An accidental DELETE ran. Is last night's backup enough?

backup دیشب سالم هست اما از آن زمان سفارش‌های معتبر هم ثبت شده‌اند. restore کامل، آن داده‌های جدید رو عقب می‌برد؛ راه بازیابی نقطه‌ای این هست که backup پایه رو در محیط جدا restore کنیم و binlogهای بعد از آن رو تا لحظهٔ درست replay کنیم. اول زنجیره و coordinateها رو ثابت می‌کنیم؛ بعد فقط روی مقصد تمرینی اجرا می‌کنیم.

Last night's backup is good, but valid orders were written afterward. Restoring it loses those changes. Point-in-time recovery restores a base backup separately, then replays subsequent binary logs only up to the intended point. First prove the log chain and coordinates; replay only in an isolated target.

PITR به backup پایه و زنجیرهٔ binlog نیاز داردPITR needs a base backup and a complete binlog chain

backup وضعیت سرور رو در یک نقطه ثبت می‌کنه. binlog رویدادهای تغییردهندهٔ بعد از آن نقطه رو نگه می‌دارد. اگه فایل log گم، حذف یا ناقص باشه، فاصلهٔ زمانی قابل‌بازیابی محدود می‌شه. برای هر backup، موقعیت شروع replay، نام فایل‌های log، retention و مقصد restore رو ثبت کن.

A backup captures server state at one point. Binary logs retain subsequent change events. Missing, purged, or incomplete logs shrink the recoverable interval. Record the replay starting position, log filenames, retention, and restore target for every backup.

restore کامل به T0 می‌رسه؛ replay کنترل‌شده داده رو تا پیش از رویداد ناخواسته جلو می‌آورد.

The base restore reaches T0; controlled replay advances to just before the unwanted event.

پیش از replay، فایل و event رو بخوانInspect files and events before replay

نام log و موقعیت فعلی رو ثبت کن. mysqlbinlog رو برای بازهٔ محدود به فایل SQL قابل‌بررسی تبدیل کن و eventهای نزدیک زمان رخداد رو بخوان. timestamp از timezone و ساعت server تأثیر می‌گیره؛ برای توقف دقیق، موقعیت رویداد امن‌تر هست. schema و transaction boundaries رو هم بررسی کن.

Record log filenames and current position. Convert a bounded interval with mysqlbinlog into reviewable SQL and inspect events near the incident. Timestamps depend on server clock and timezone; event positions are more precise for stopping. Review schema and transaction boundaries too.

SHOW BINARY LOGS;
SHOW BINARY LOG STATUS;
mysqlbinlog --start-position=120 --stop-position=980 \
  mysql-bin.000123 > review.sql

عددها نمونه‌اند. position باید از backup و log واقعی تو بیاید. فایل SQL تولیدشده رو قبل از اعمال بررسی کن؛ آن رو به server اصلی pipe نکن.

Positions are illustrative; use those from your backup and logs. Review generated SQL before applying it; never pipe it into the production server.

زنجیره رو روی مقصد disposable بازسازی کنRebuild the chain on a disposable target

اول آخرین full backup پیش از رخداد رو به server جدا restore کن. بعد binlog رو از position ثبت‌شدهٔ backup تا position پیش از رویداد بد replay کن. اگه از چند log استفاده می‌کنی، ترتیب پیوسته و connection واحد مهم هست. سپس رکوردهای سالم بعد backup و نبودن اثر DELETE اشتباه رو query کن.

Restore the latest full backup before the incident into a separate server. Replay logs from the backup's recorded position to just before the bad event. With multiple logs, preserve order and use one connection. Query both valid post-backup records and the absence of the accidental deletion's effect.

mysqlbinlog --start-position=120 \
  --stop-position=980 mysql-bin.000123 \
  | mysql --host=restore.example.test --user=recovery_user -p

این فقط نمونهٔ آزمایش است؛ start/stop رو از event واقعی تعیین کن. از --database filter با فرض ساده استفاده نکن؛ رفتار statement-based و cross-database eventها می‌تونه غافلگیر کند.

This is a rehearsal pattern; derive positions from actual events. Do not assume a simple --database filter is safe: statement-based and cross-database events can behave unexpectedly.

PITR همه‌چیز رو خودکار درست نمی‌کنهPITR does not automatically solve everything

binlog فقط تغییرهای ثبت‌شده پس از backup رو replay می‌کنه؛ SELECTها رو ندارد و تضمین نمی‌کنه archive کامل هست. eventهای DDL و تغییرهای خارج از engine رو با دقت بررسی کن. اگه binlog روی server فعال یا به مقصد امن منتقل نشده، بازهٔ از دست‌رفته رو نمی‌توان از هیچ ساخت. بازیابی به مقصد جدا کمک می‌کنه زمان توقف production رو در حالی مدیریت کنی که نتیجه رو می‌سنجی.

Binary logs replay recorded changes after the backup; they do not contain SELECTs and cannot make an incomplete archive complete. Review DDL and nontransactional changes carefully. If logs were not enabled or archived safely, missing intervals cannot be recreated. An isolated restore lets you validate before changing production.

اول یه restore پایه بسازStart with a known-good base restore

PITR از هیچ شروع نمی‌شه. اول یه full backup قابل‌restore لازم داری، بعد binlogهای بعد از اون نقطه. اگه نقطهٔ پایه یا chain ناقص باشه، timestamp هدف به‌تنهایی کمکی نمی‌کنه.

Point-in-time recovery needs a proven base backup plus the binary logs that follow it. A target timestamp is useless when the chain is incomplete.
