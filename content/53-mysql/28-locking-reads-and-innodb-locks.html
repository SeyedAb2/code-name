دو نفر یک موجودی رو می‌خوانند؛ چه کسی می‌تونه آن رو تغییر دهد؟

Two sessions read stock; who can change it?

در فصل قبل دیدیم plain SELECT چطور snapshot می‌خواند. حالا یک مسئلهٔ دیگر داریم: برنامه موجودی کالا رو می‌خواند، بعد می‌خواهد کمش کند. اگه session دیگری بین این دو مرحله همان ردیف رو تغییر دهد، خواندن عادی جلوی race رو نمی‌گیره. این بار SELECT رو برای تغییر هماهنگ می‌کنیم.

The previous chapter showed how a plain SELECT reads a snapshot. Now the application reads inventory and then wants to decrement it. If another session changes the same row between those steps, an ordinary read does not prevent the race. This time we coordinate the read with a write.

دو سفارش‌دهنده، یک کالای باقی‌ماندهTwo buyers, one item left

فرض کن فقط یک کالا در انبار مانده. درخواست A موجودی رو ۱ می‌خواند و هنوز چیزی کم نکرده. هم‌زمان درخواست B هم ۱ رو می‌بیند. اگه هر دو بر اساس همین عدد فروش رو تأیید کنند، ممکنه یک موجودی دو بار فروخته شود. مسئله نه transaction به‌تنهایی هست و نه snapshot؛ باید ردیفی رو که قرار هست تصمیم بر اساس آن گرفته شود موقتاً قفل کنیم.

Suppose only one item remains. Request A reads quantity 1 but has not decremented it. Request B also sees 1. If both approve a sale based on that value, one unit may be sold twice. A transaction alone or a snapshot does not solve this; we need to lock the row on which the decision depends.

قفل‌خواندن رو فقط وقتی بگذار که واقعاً قرار هست بر اساس همان ردیف تصمیم نوشتنی بگیری. قفل تا پایان transaction می‌مونه، پس بعد از تصمیم سریع COMMIT یا ROLLBACK کن.

Use a locking read only when a write decision depends on the row. Its lock lasts until the transaction ends, so commit or roll back promptly after deciding.

دو connection، یک schemaTwo connections, one schema

FOR UPDATE: «این ردیف رو برای تغییر می‌خوانم»FOR UPDATE: “I am reading this row to change it”

در session A transaction رو باز کن و موجودی رو با FOR UPDATE بخوان. سپس در B همان ردیف رو با FOR UPDATE بخوان؛ B منتظر می‌مونه چون A هنوز قفل رو نگه داشته. این انتظار مدرک هماهنگی است، نه لزوماً بن‌بست یا خرابی.

In session A, start a transaction and read the row with FOR UPDATE. Then request the same row with FOR UPDATE in B. B waits while A holds the lock. That wait is evidence of coordination, not automatically a deadlock or failure.

USE codenames_lock_lab;
START TRANSACTION;
SELECT quantity FROM inventory WHERE item_id=1 FOR UPDATE;
حالا در session B؛ این دستور تا آزادشدن قفل منتظر می‌مونهNow in session B; this waits for the lock
USE codenames_lock_lab;

B رو باز نگه دار و به A برگرد. موجودی رو با شرط محافظتی کم کن، بعد commit کن. شرط quantity>0 هنوز مهم هست: قفل هماهنگی می‌ده، اما قانون کسب‌وکار رو باید خود query هم enforce کند.

Leave B waiting and return to A. Decrement with a defensive condition, then commit. The quantity>0 predicate still matters: locking coordinates access, but the query must also enforce the business rule.

در session A، سپس B ادامه می‌دهIn session A, then B resumes
UPDATE inventory
SET quantity=quantity-1
WHERE item_id=1 AND quantity>0;
SELECT ROW_COUNT() AS changed_rows;
COMMIT;

پس از commit A، query منتظرماندهٔ B باید مقدار تازهٔ ۰ رو برگردونه. حالا B تصمیم می‌گیره فروش دیگری مجاز نیست و transaction رو با ROLLBACK می‌بندد. به تغییر نسخهٔ قدیمی snapshot برای یک تصمیم نوشتنی تکیه نکردیم؛ locking read پس از انتظار مقدار فعلی رو می‌خواند.

After A commits, B’s waiting query should return the current value 0. B can now reject another sale and roll back. We did not rely on an old snapshot for a write decision; the locking read uses the current value after waiting.

FOR SHARE: بخوان، اما نگذار هم‌زمان عوض شودFOR SHARE: read while preventing concurrent changes

گاهی چند خواننده باید هم‌زمان مقدار رو ببینند، اما تا پایان بررسی نباید writer آن ردیف رو عوض کند. FOR SHARE قفل shared می‌گیره: خواننده‌های دیگر می‌تونن بخوانند، ولی تغییر ناسازگار باید منتظر بماند. این دستور هم transaction می‌خواهد و قفل تا پایان آن می‌مونه.

Sometimes several readers may inspect a value together, but a writer should not change it during the check. FOR SHARE takes a shared lock: other readers can read, while conflicting changes wait. It also needs a transaction, and the lock lasts until that transaction ends.

در A قفل shared بگیرTake a shared lock in A
START TRANSACTION;
SELECT quantity FROM inventory WHERE item_id=1 FOR SHARE;

در B یک plain SELECT امتحان کن؛ بعد UPDATE رو امتحان کن. plain خواندن می‌تونه انجام بشه، اما UPDATE باید تا commit یا rollback در A منتظر بماند. پایان آزمایش رو فراموش نکن تا B آزاد شود.

In B, try a plain SELECT, then try UPDATE. The ordinary read can proceed, but UPDATE waits until A commits or rolls back. End the experiment so B can continue.

در A قفل رو آزاد کنRelease the lock in A
COMMIT;

برای read-then-write معمولاً FOR UPDATE روشن‌تر هست. گرفتن FOR SHARE در دو session و بعد ارتقای هر دو به write می‌تونه به انتظار یا deadlock برسد؛ از الگوی «اول قفل shared، بعد ارتقا» بی‌فکر استفاده نکن.

For read-then-write logic, FOR UPDATE is usually clearer. Taking shared locks in two sessions and then upgrading both to writes can cause waits or deadlocks; do not use a shared-then-upgrade pattern casually.

منتظر بمانم، خطا بگیرم، یا ردیف قفل‌شده رو رد کنم؟Wait, fail immediately, or skip the locked row?

پیش‌فرض، انتظار برای قفل ردیف درخواستی هست. در MySQL 9.7 می‌تونی NOWAIT بخواهی تا به‌جای انتظار خطا بگیری، یا SKIP LOCKED تا ردیف‌های قفل‌شده از نتیجه حذف شوند. این‌ها فقط دربارهٔ row lock هستن؛ مجوز عبور از همهٔ نوع قفل‌ها نیستند.

By default, a locking read waits for the requested row lock. In MySQL 9.7, NOWAIT returns an error instead of waiting, while SKIP LOCKED omits locked rows from the result. These options concern row locks; they do not bypass every kind of lock.

NOWAIT رو فقط با ردیفی که عمداً قفل شده آزمایش کنTest NOWAIT against a deliberately locked row
SELECT quantity FROM inventory
WHERE item_id=1 FOR UPDATE NOWAIT;

اگه session دیگری قفل داشته باشه، باید خطای فوریِ lock wait ببینی؛ متن دقیق خطا رو از client خودت ثبت کن. این الگو برای جایی هست که برنامه می‌تونه سریع retry کند یا پاسخ کنترل‌شده بده.

If another session holds the lock, expect an immediate lock-wait error; record the exact message from your client. This suits applications that can retry or return a controlled response.

SKIP LOCKED رو برای queue-like work بسنج، نه گزارش عمومیConsider SKIP LOCKED for queue-like work, not general reports
SELECT item_id,quantity FROM inventory
FOR UPDATE SKIP LOCKED;

ردیف قفل‌شده از نتیجه حذف می‌شه و خروجی یک view ناسازگار از داده هست. برای چند worker روی صف می‌تونه مفید باشه؛ برای گزارش موجودی یا تصمیمی که «همهٔ ردیف‌ها» رو می‌خواهد، ممکنه جواب غلط کسب‌وکار بسازد.

Locked rows disappear from the result, so the query returns an inconsistent view. This can help multiple workers claim queue-like rows; it can produce a wrong business answer for inventory reports or queries that require every row.

قفل دقیقاً روی چه چیزی می‌افتد؟What exactly is being locked?

زبان روزمره می‌گه «ردیف رو قفل کردیم»، اما InnoDB با index recordهایی کار می‌کنه که query برایش scan می‌کنه. برای شرط مساوی روی primary key یکتا دامنه معمولاً محدودتر است؛ range یا predicate بدون index مناسب می‌تونه رکوردها یا فاصله‌های بیشتری رو درگیر کند. از روی SQL تنها اندازهٔ دقیق قفل رو حدس نزن؛ EXPLAIN، index و شواهد lock رو هم بررسی کن.

We casually say “the row is locked,” but InnoDB works with index records scanned by the query. Equality on a unique primary key is usually narrower; a range or poorly indexed predicate can involve more records or gaps. Do not infer the exact lock footprint from SQL alone; inspect the plan, indexes, and lock evidence.

قفل‌خواندن جای constraint، predicate محافظتی یا transaction کوتاه رو نمی‌گیره. برای کم‌کردن موجودی، شرط و تعداد ردیف تغییرکرده رو هم بررسی کن. قفل رو فقط برای داده‌ای بگیر که واقعاً در تصمیم شرکت دارد.

A locking read does not replace constraints, defensive predicates, or short transactions. For an inventory decrement, also check the condition and affected-row count. Lock only data that participates in the decision.
