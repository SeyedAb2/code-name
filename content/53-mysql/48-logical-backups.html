فایل dump داریم؛ آیا واقعاً می‌تونیم از آن برگردیم؟

We have a dump file. Can we actually restore from it?

تیم هر شب mysqldump اجرا می‌کنه و job سبز هست. اما شاید routineها و eventها جا افتاده باشند، snapshot وسط تغییر schema ناسازگار شده باشه یا فایل restore نشده باشه. از یک دیتابیس تمرینی dump می‌گیریم، اجزای فایل رو بررسی می‌کنیم و روی schema جدا restore می‌کنیم؛ backup تنها وقتی مدرک هست که مسیر برگشتش رو آزموده باشیم.

The team runs mysqldump nightly and the job is green. But routines and events may be missing, concurrent schema changes may have made the snapshot unsafe, or nobody may have restored it. We will dump a lab database, inspect the artifact, and restore to a separate schema; a backup is evidence only when recovery has been tested.

dump منطقی چه چیزی می‌سازد؟What does a logical dump contain?

mysqldump معمولاً statementهای SQL برای ساخت object و درج ردیف‌ها می‌نویسه. این فایل portable و قابل‌بازرسی است، اما اندازه‌اش ممکنه بزرگ و restore آن زمان‌بر باشه. dump یک database لزوماً userها و grantهای server یا همهٔ تنظیمات رو شامل نمی‌شه؛ scope رو دقیق انتخاب کن.

mysqldump typically writes SQL statements to recreate objects and rows. The artifact is inspectable and portable, but can be large and slow to restore. A database dump does not necessarily include server users, grants, or every configuration setting; define scope explicitly.

mysqldump --host=db.example.test --user=backup_user \
  --password --single-transaction \
  --routines --events \
  --databases codenames_lab \
  --result-file=codenames_lab.sql

رمز رو بعد از --password در command line ننویس؛ client prompt می‌کنه. دسترسی فایل backup رو محدود و مقصد رو رمزگذاری/محافظت کن. triggerها در حالت معمول dump می‌شوند؛ routine و event رو صریحاً لحاظ کرده‌ایم. credential و user objectها رو جداگانه برنامه‌ریزی کن.

Do not put a password value on the command line; the client prompts. Restrict access to the artifact and protect its storage. Triggers are normally included; routines and events are requested explicitly here. Plan credentials and user objects separately.

single-transaction محدودیت داردsingle-transaction has limits

گزینهٔ single-transaction برای snapshot تراکنشی هست و برای جدول‌های InnoDB مناسب است؛ جدول‌های غیرتراکنشی snapshot سازگار تضمین‌شده ندارن. هنگام dump از ALTER/DROP/RENAME روی جدول‌های موردنظر پرهیز کن؛ تغییر schema هم‌زمان می‌تونه خروجی رو خراب یا ناپایدار کند. زمان، version، engineها و هشدارهای ابزار رو نگه دار.

single-transaction provides a transactional snapshot and is appropriate for InnoDB tables; it does not guarantee a consistent snapshot for nontransactional tables. Avoid ALTER, DROP, or RENAME of dumped tables during the dump; concurrent schema changes can make output inconsistent or fail. Record version, engines, duration, and tool warnings.

قبل از restore، فایل رو بشناسInspect the artifact before restoring

dump رو با ابزار متنی در محیط محدود بررسی کن: نام databaseها، CREATE TABLE، routineها، eventها و درج داده. ممکنه دادهٔ حساس داشته باشه؛ آن رو در ticket یا repo نفرست. checksum، حجم، زمان، source version و exit code job رو کنار artifact نگه دار.

Inspect the dump in a controlled environment: schema names, CREATE TABLE statements, routines, events, and data inserts. It may contain sensitive data; do not attach it to a ticket or repository. Keep checksum, size, timestamp, source version, and job exit status with the artifact.

sha256sum codenames_lab.sql
grep -nE 'CREATE TABLE|CREATE PROCEDURE|CREATE EVENT' codenames_lab.sql

در Windows از ابزارهای معادل استفاده کن. grep یا checksum محتوای SQL رو اجرا نمی‌کنه و موفقیت restore رو ثابت نمی‌کنه.

Use equivalent tools on Windows. grep and checksums do not execute the SQL or prove that restoration works.

به مقصد جدا restore کن و query بزنRestore to a separate target and query it

برای تمرین، dump رو به یک server یا database مجزا وارد کن؛ منبع رو overwrite نکن. بعد از import، تعداد و چند مقدار کلیدی رو با query مقایسه کن، objectهای لازم رو فهرست کن و application رو با حساب محدود تست کن. اگه خطا وسط import رخ داد، مقصد تمرین رو دور بریز و علت رو پیدا کن؛ فایل رو سالم اعلام نکن.

For rehearsal, load the dump into a separate server or schema; never overwrite the source. Compare row counts and key values, list required objects, and test the app with its restricted account. If import fails, discard the lab target and diagnose the failure; do not label the artifact usable.

mysql --host=restore.example.test --user=restore_user \
  --password < codenames_lab.sql
SELECT COUNT(*) FROM codenames_lab.orders;

در Windows PowerShell عملگر < برای redirection رفتار متفاوت دارد؛ از روش import مستند همان shell یا client استفاده کن.

In Windows PowerShell, the < operator behaves differently; use the import method documented for that shell or client.

Dump خوب فقط فایل SQL نیست؛ یه نقطهٔ بازیابی تعریف‌شده‌ستA useful logical backup is more than a SQL file

Define what the logical backup must contain: schema, data, routines, triggers, events, and any metadata required by the recovery plan. Choose options from recovery needs, not memory.

برای InnoDB و backup آنلاین، consistency snapshot مهمه؛ برای engineهای مختلف فرض یکسان نداشته باش.

Online consistency assumptions differ by engine; do not generalize blindly.
