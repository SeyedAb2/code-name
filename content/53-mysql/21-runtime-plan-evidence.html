تخمین درست بود؟ query رو واقعاً اجرا کن

Was the estimate right? Run the query and observe

در فصل ۲۰، plan JSON رو مثل نقشه خواندیم؛ هنوز نمی‌دانستیم هر مرحله واقعاً چند ردیف داده و چند بار اجرا شده هست. همکار می‌گه: «optimizer گفته ۱۰ ردیف؛ پس ۱۰ ردیف پردازش شده.» بیا این ادعا رو روی دادهٔ کوچک و بی‌خطر امتحان کنیم.

Chapter 20 taught us to read JSON plans as maps, but not how many rows each operation actually produced or how often it ran. A teammate says, “The optimizer estimated 10 rows, so 10 rows were processed.” Let’s test that claim on a small, safe dataset.

پیش‌نیازPrerequisite: فصل ۲۰ · planهای JSONنسخهٔ مرجعReference: MySQL 9.7زمانTime: ۹۰ دقیقه · ۱۸ تمرین

plan گفته بود ۱۲؛ اجرا ۳۲۰۰ دادThe plan estimated 12; execution returned 3,200

گزارش کندی یک query رو داری. EXPLAIN FORMAT=JSON برای یک مرحله ۱۲ ردیف تخمین زده؛ اما تیم می‌گه هزاران نتیجه می‌بیند. آیا آمار کهنه است؟ آیا شرط آن‌قدر انتخاب‌پذیر نیست؟ یا این دو عدد دربارهٔ دو مرحلهٔ متفاوت‌اند؟ EXPLAIN ANALYZE کمک می‌کنه با مشاهدهٔ اجرای واقعی جواب رو محدود کنیم.

A slow-query report estimates 12 rows for one operation, while the team says it sees thousands. Are statistics stale? Is the predicate less selective than expected? Or are these numbers for different operations? EXPLAIN ANALYZE helps narrow the answer by observing a real execution.

اما نامش رو جدی بگیر: این دستور فقط نقشه چاپ نمی‌کنه؛ query رو اجرا می‌کنه. پس برای آزمایش، SELECT محدود و fixture خودمان رو انتخاب می‌کنیم، نه یک گزارش سنگین production یا دستوری که داده رو تغییر می‌ده.

Take the name seriously: this command does not only print a plan; it executes the statement. We will use a bounded SELECT on our own fixture, not a heavy production report or a data-changing statement.

داده بساز که اختلاف تخمین رو قابل دیدن کندCreate data that makes an estimate mismatch visible

fixture زیر ۱۰۰۰ ردیف دارد؛ بیشتر ردیف‌ها status برابر closed دارن و چندتایی open. همه‌چیز داخل schema اختصاصی هست. اگه چنین schemaای از قبل برای دادهٔ مهم داری، نام دیگری انتخاب کن؛ دستور DROP فقط برای همین آزمایش disposable هست.

This fixture has 1,000 rows: most are closed, with a smaller open group. Everything stays in a dedicated schema. If you already use that schema for valuable data, choose another name; the DROP below is only for this disposable experiment.

ساخت ۱۰۰۰ ردیف محدودCreate a bounded 1,000-row fixture
CREATE DATABASE IF NOT EXISTS codenames_runtime_plan_lab;
USE codenames_runtime_plan_lab;
DROP TABLE IF EXISTS task;

CREATE TABLE task (
  task_id INT NOT NULL PRIMARY KEY,
  team_id INT NOT NULL,
  state VARCHAR(12) NOT NULL,
  payload VARCHAR(80) NOT NULL,
  KEY ix_state(state),
  KEY ix_team_state(team_id,state)
) ENGINE=InnoDB;

INSERT INTO task(task_id,team_id,state,payload)
WITH RECURSIVE seq(n) AS (
  SELECT 1 UNION ALL SELECT n+1 FROM seq WHERE n < 1000
)
SELECT n,
       1 + MOD(n,10),
       CASE WHEN MOD(n,25)=0 THEN 'open' ELSE 'closed' END,
       CONCAT('task-',n)
FROM seq;

SELECT COUNT(*) AS total_rows,
       SUM(state='open') AS open_rows
FROM task;

باید ۱۰۰۰ ردیف و ۴۰ ردیف open ببینی. این COUNT مدرک اندازهٔ fixture است؛ نه زمان اجرا رو می‌گه و نه انتخاب optimizer رو. اگه recursive CTE در نسخهٔ سرورت محدودیت دارد، تعداد پایین‌تر بساز و انتظار عددها رو با همان داده تنظیم کن.

Expect 1,000 total rows and 40 open rows. COUNT proves fixture size; it says nothing about runtime or optimizer choice. If your server imposes a recursive-CTE limit, build fewer rows and adjust expectations to your actual data.

سه جور عدد رو با هم قاطی نکنKeep three kinds of numbers separate

حالا اول پیش‌بینی رو می‌گیریم و بعد اجرای واقعی رو مشاهده می‌کنیم. خروجی دقیق به آمار، نسخه و ماشین بستگی دارد؛ مهم، شکل مدرک هست: rows=... تخمین است، actual time و actual rows از اجرای انجام‌شده میان و loops تعداد تکرار iterator رو نشان می‌ده.

First capture a prediction, then observe execution. Exact output depends on statistics, version, and machine; read the evidence type: rows=... is an estimate, while actual time and actual rows come from execution, and loops counts iterator repetitions.

پیش‌بینی، سپس اجراPrediction, then execution
EXPLAIN FORMAT=TREE
SELECT task_id,payload FROM task
WHERE team_id=3 AND state='open';

EXPLAIN ANALYZE FORMAT=TREE
SELECT task_id,payload FROM task
WHERE team_id=3 AND state='open';

یک خروجی نماینده ممکنه چیزی شبیه این باشه؛ زمان و rows تخمینی رو عیناً از سرور خودت بخوان، نه از این نمونه:

Representative output may look like this; read actual timing and estimated rows from your own server rather than copying these sample values:

نمونهٔ ساختاری؛ عددها متغیرندStructural example; values vary
-> Index lookup on task using ix_team_state (...)
   (cost=... rows=...)
   (actual time=... .. ... rows=... loops=1)

actual rows در یک iterator الزاماً تعداد خروجی نهایی query نیست؛ فرزند ممکنه ردیف بیشتری تولید کند که مرحلهٔ بالاتر فیلتر یا join می‌کنه. اگه loops بیشتر از یک است، عدد زمان گزارش‌شده برای آن iterator میانگین هر loop هست. زمان iterator فرزند در محاسبهٔ زمان parent هم اثر می‌ذاره؛ زمان‌ها رو از روی همهٔ گره‌ها با هم جمع نکن.

An iterator’s actual rows is not necessarily the final query row count; a child may produce rows that an upper filter or join removes. If loops exceeds one, the reported iterator time is an average per loop. Child time contributes to its parent’s timing, so do not sum every node’s time.

از اختلاف عددها علت رو حدس نزن؛ سؤال بعدی رو انتخاب کنDo not guess the cause from a mismatch; choose the next question

اگه تخمین و مقدار واقعی فرق داشتند، این یک سرنخ است، نه حکم قطعی دربارهٔ index. اول مطمئن شو گرهٔ مقایسه‌شده همان iterator موردنظر است؛ بعد predicate، تعداد loopها و توزیع داده رو بررسی کن. شاید آمار نماینده نباشه، شاید شرط skew داشته باشه، یا شاید row estimate پایین‌دست با فیلتر مرحلهٔ بعد عوض شود.

A mismatch is a clue, not a verdict that an index is missing. Confirm you are comparing the intended iterator, then inspect predicates, loop counts, and data distribution. Statistics may be unrepresentative, a predicate may be skewed, or a later filter may change downstream row counts.

EXPLAIN ANALYZE دربارهٔ همان اجرای انجام‌شده مدرک می‌ده؛ اجرای دیگر ممکنه cache، concurrency و زمان متفاوتی داشته باشه. خروجی آزمایش کوچک رو مستقیم به production تعمیم نده و یک عدد زمان رو معیار قطعی کیفیت نکن.

EXPLAIN ANALYZE describes that particular execution. Another run may have different cache state, concurrency, and timing. Do not generalize a tiny lab result to production or treat one timing number as a definitive quality score.

ANALYZE TABLE نامش شبیه است؛ کارش فرق داردANALYZE TABLE sounds similar, but does different work

اینجا یک اسم گمراه‌کننده داریم. EXPLAIN ANALYZE SELECT ... خود query رو اجرا و زمان/ردیف iteratorها رو گزارش می‌کنه. ANALYZE TABLE task آمار optimizer رو برای جدول به‌روز می‌کنه و جدول وضعیت برمی‌گرداند؛ اجرای SELECT موردبحث نیست. در MySQL هم می‌توان برای بعضی ستون‌ها histogram ساخت، اما این فصل با refresh ساده شروع می‌کنه.

The similar names are misleading. EXPLAIN ANALYZE SELECT ... runs the query and reports iterator timing and rows. ANALYZE TABLE task refreshes optimizer statistics and returns a status result; it does not run the SELECT in question. MySQL also supports histograms for some columns, but we start with a plain refresh.

آمار رو تازه کن و همان plan رو تکرار کنRefresh statistics, then repeat the same plan
ANALYZE TABLE task;
EXPLAIN FORMAT=TREE
SELECT task_id,payload FROM task
WHERE team_id=3 AND state='open';

خروجی ANALYZE TABLE باید status موفق رو نشان بده. بعد plan رو با همان query مقایسه کن؛ ممکنه تغییر نکند، چون آمار تازه الزاماً انتخاب plan رو عوض نمی‌کنه. ANALYZE TABLE درمان تضمینی نیست و اگه مشکل از shape query یا نیاز workload باشه، باید همان رو جدا بررسی کرد.

ANALYZE TABLE should report a successful status. Compare the same query afterward; the plan may remain unchanged because fresher statistics do not force a different choice. ANALYZE TABLE is not a guaranteed fix; query shape and workload needs still require separate investigation.

دستورهای هم‌نام رو در گزارش دقیق بنویس. «ANALYZE رو اجرا کردم» کافی نیست: مشخص کن منظورت EXPLAIN ANALYZE SELECT بوده یا ANALYZE TABLE. اولی query رو اجرا می‌کنه؛ دومی آمار جدول رو به‌روز می‌کنه.Name the exact statement in an incident report.“I ran ANALYZE” is ambiguous. Say whether you ran EXPLAIN ANALYZE SELECT or ANALYZE TABLE: one executes a query; the other refreshes table statistics.

پیش از اجرا، هزینه و خطر رو بسنجAssess cost and risk before execution

EXPLAIN معمولی معمولاً مسیر تخمینی SELECT رو نشان می‌ده بی‌آن‌که SELECT رو اجرا کند. EXPLAIN ANALYZE برای سنجش واقعی آن رو اجرا می‌کنه و می‌تونه برای query بزرگ، پرهزینه باشه. از SELECT محدود، schema آزمایشی و بازهٔ کوچک شروع کن. روی UPDATE/DELETE آن رو مثل چاپ بی‌خطر plan فرض نکن؛ نسخهٔ جاری statementهای بیشتری رو پشتیبانی می‌کنه و معنای «اجرا می‌شه» همچنان مهم هست.

Ordinary EXPLAIN generally shows an estimated SELECT plan without running the SELECT. EXPLAIN ANALYZE executes it for measurement and can be expensive for a large query. Start with a bounded SELECT, a lab schema, and a small range. Do not treat it as harmless plan printing for UPDATE/DELETE; current releases support more statement forms, and execution still matters.

در این درس فقط SELECTهای read-only روی fixture رو اندازه می‌گیریم. اگه در محیط واقعی نیاز به DML diagnostic داری، اول اثرها، transaction و روش بازگردانی رو جداگانه بررسی کن؛ این آزمایش چنین مجوزی نمی‌ده.

This lesson measures only read-only SELECTs on a fixture. If you need DML diagnostics in a real environment, first assess side effects, transaction behavior, and recovery separately; this lab does not authorize that experiment.

وقتی خروجی برخلاف انتظار هستWhen the output differs from expectation

زمان هر گره رو جمع می‌زنی

You are summing every node’s time

زمان فرزند می‌تونه داخل زمان parent حساب شده باشه. مسیر درخت و مرز هر iterator رو بخوان؛ زمان‌ها رو جمع نکن.

actual rows با خروجی نهایی یکی نیست

actual rows differs from final output

ممکنه گرهٔ میانی ردیف‌های بیشتری بده و مرحلهٔ بالاتر آن‌ها رو حذف کند. یک سطح رو با سطح دیگر مقایسه نکن.

An intermediate node can emit rows that an upper stage removes. Do not compare different levels.

ANALYZE تغییر plan نداد

ANALYZE did not change the plan

این شکست نیست؛ optimizer با اطلاعات تازه هم ممکنه همان مسیر رو انتخاب کند. قبل/بعد رو برای query یکسان ذخیره کن و سراغ evidence بعدی برو.

That is not necessarily failure; the optimizer may keep the same path with refreshed information. Save before/after evidence for the same query and continue diagnosis.
