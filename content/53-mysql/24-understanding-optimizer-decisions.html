optimizer چرا این plan رو انتخاب کرد؟

Why did the optimizer choose this plan?

یک index تازه ساخته‌ایم، اما query هنوز آن رو انتخاب نمی‌کنه. سریع می‌گیم «optimizer اشتباه کرده» و دنبال hint می‌گردیم. یک قدم عقب برویم: شاید query بخش بزرگی از جدول رو برمی‌گرداند، شاید تخمین فرق دارد، یا شاید هزینهٔ مسیر index از scan بیشتر هست. این فصل دلیل رو با مدرک پیدا می‌کنه، نه با حدس.

We created a new index, but the query still does not use it. It is tempting to call the optimizer wrong and reach for a hint. Step back: perhaps the query returns much of the table, its estimate differs from reality, or the indexed path costs more than a scan. This chapter investigates the choice with evidence instead of guessing.

«index رو نادیده گرفت» هنوز تشخیص نیست“It ignored my index” is not a diagnosis

فصل‌های قبل تخمین rows، access type، اجرای واقعی و آمار رو جدا کردیم. حالا ticket می‌گه: «روی state ایندکس ساختم، ولی MySQL هنوز جدول رو می‌خواند.» پیش از تغییر چیزی سه پرسش داریم: query دقیقاً چه می‌خواهد؟ چند ردیف باید برگردد؟ optimizer چه تعداد ردیف رو تخمین زده؟

Earlier chapters separated estimated rows, access type, actual execution, and statistics. Now a ticket says: “I indexed state, but MySQL still scans the table.” Before changing anything, ask: what does the query request, how many rows actually match, and how many does the optimizer estimate?

«index هست» به معنی «index بهترین راه هست» نیست. اگه بیشتر جدول جواب می‌ده، خواندن پیوستهٔ جدول شاید از رفت‌وبرگشت میان index و ردیف‌ها ارزان‌تر باشه. optimizer هزینه رو تخمین می‌زند؛ تضمین نمی‌کنه که همیشه درست حدس بزند.

“The index exists” does not mean it is the cheapest access path. If most rows qualify, scanning the table can be cheaper than visiting an index and fetching many rows. The optimizer estimates cost; it does not guarantee a correct prediction.

یک توزیع قابل‌اندازه‌گیری بسازBuild a measurable distribution

در schema تمرینی جدا، حدود ۸۰ درصد ردیف‌ها رو open و بقیه رو closed می‌سازیم. این fixture کوچک benchmark تولیدی نیست؛ هدف این هست که بفهمیم plan چه چیزی رو تخمین می‌زند و داده واقعاً چه می‌گه.

In a separate lab schema, we make about 80% of rows open and the rest closed. This small fixture is not a production benchmark; it lets us compare plan estimates with the actual data.

فقط روی schema تمرینیDisposable schema only

دستور DROP فقط وقتی امن هست که مطمئن باشی codenames_optimizer_lab محیط disposable خودت هست. روی schema واقعی اجرا نکن.

DROP is safe only after confirming that codenames_optimizer_lab is your disposable environment. Never run it against a real schema.

fixture بساز و توزیع واقعی رو ببینBuild the fixture and inspect actual counts
CREATE DATABASE IF NOT EXISTS codenames_optimizer_lab;
USE codenames_optimizer_lab;
DROP TABLE IF EXISTS task;
CREATE TABLE task (
  task_id INT NOT NULL PRIMARY KEY,
  state VARCHAR(12) NOT NULL,
  owner_id INT NOT NULL,
  INDEX ix_state (state)
) ENGINE=InnoDB;

INSERT INTO task(task_id,state,owner_id)
WITH RECURSIVE seq(n) AS (
  SELECT 1 UNION ALL SELECT n+1 FROM seq WHERE n < 1000
)
SELECT n,
       CASE WHEN n <= 800 THEN 'open' ELSE 'closed' END,
       MOD(n,20)+1
FROM seq;

SELECT state,COUNT(*) AS actual_rows
FROM task GROUP BY state ORDER BY state;

باید ۸۰۰ open و ۲۰۰ closed ببینی. قبل از تحلیل plan، همین count رو مدرک تعداد واقعی بگیر؛ از روی مقدار rows در EXPLAIN خروجی واقعی رو حدس نزن.

Expect 800 open rows and 200 closed rows. Use these counts as actual evidence; do not infer the query result from EXPLAIN’s rows estimate.

یک query، دو selectivityOne query shape, two selectivities

برای هر مقدار، plan و count رو جدا می‌گیریم. اگه open بیشتر جدول رو بگیره، scan می‌تونه معقول باشه؛ اگه closed کم‌تعداد باشه، index ممکنه جذاب‌تر شود. اندازهٔ جدول، آمار، نسخه و cache نتیجه رو تغییر می‌دن، پس خروجی دقیق خودت رو بخوان.

For each value, capture the plan and count separately. A scan can be reasonable for open, which matches most rows; the index may be more attractive for the less common closed value. Table size, statistics, version, and cache can change the outcome, so inspect your own output.

وقتی EXPLAIN جواب «چرا» رو نمی‌دهWhen EXPLAIN does not answer “why”

EXPLAIN خلاصهٔ plan رو می‌ده. برای دیدن گام‌های تصمیم‌گیری، optimizer trace رو فقط در همین session روشن می‌کنیم. trace JSON هست و ممکنه بلند باشه؛ پرسش مشخصی داشته باش، مثلاً «optimizer کدام مسیرهای دسترسی رو مقایسه کرد؟»

EXPLAIN summarizes the plan. To inspect decision steps, enable optimizer tracing in this session only. The JSON trace can be long, so bring a specific question—for example, “Which access paths did the optimizer compare?”

یک query رو trace کن و خاموشش کنTrace one query, then turn it off
SET SESSION optimizer_trace='enabled=on';
SELECT task_id FROM task WHERE state='closed';
SELECT TRACE
FROM INFORMATION_SCHEMA.OPTIMIZER_TRACE\G
SET SESSION optimizer_trace='enabled=off';

ساختار trace به نسخه و query بستگی دارد. این داده توضیحی از مرحلهٔ optimization است، نه profile کامل storage engine؛ ثابت نمی‌کنه query سریع‌تر شد. برای rows و زمان اجرا به EXPLAIN ANALYZE فصل ۲۱ برگرد. اگه شکل trace فرق داشت، کلیدواژه‌ها و بخش تصمیم مربوط به query خودت رو پیدا کن.

Trace structure depends on version and statement. It describes optimization, not a full storage-engine profile, and does not prove that the query became faster. Return to Chapter 21’s EXPLAIN ANALYZE for actual rows and runtime. If the trace shape differs, locate the decision relevant to your statement.

trace رو با نتیجهٔ query یکی نگیرDo not confuse trace with query results

trace نشان می‌ده optimizer چه چیزهایی رو بررسی کرده؛ نتیجه و رفتار اجرا رو باید با اجرای query و مدرک مناسب دیگری بسنجی.

A trace shows what the optimizer considered; query results and runtime require executing the statement and collecting the right evidence.

hint ابزار آزمایش است، نه درمان پیش‌فرضA hint is an experiment, not a default cure

اگه فرضیه داری که index خاصی بهتر است، در محیط تمرینی plan عادی رو با plan دارای hint مقایسه کن. JOIN_INDEX در MySQL 9.7 روی مسیر دسترسی index اثر می‌ذاره. تغییر key فقط اثر hint بر plan رو نشان می‌ده؛ هنوز سرعت یا برابری نتیجه ثابت نشده هست.

If your hypothesis is that a particular index is better, compare the normal plan with a hinted plan in the lab. In MySQL 9.7, JOIN_INDEX influences index access. A changed key shows that the hint affected the plan; it does not yet prove better speed or equivalent results.

فقط plan رو مقایسه کنCompare plans only
EXPLAIN SELECT task_id FROM task WHERE state='closed';
EXPLAIN SELECT /*+ JOIN_INDEX(task ix_state) */ task_id
FROM task WHERE state='closed';

بعد، هر دو query رو با ORDER BY روشن اجرا کن، تعداد و مقدارها رو مقایسه کن و زمان واقعی رو جدا بسنج. hint ممکنه با تغییر داده یا نسخه انتخاب بدی شود. optimizer hint رو با index hint یا تغییر سراسری optimizer_switch یکی نگیر.

Then run both queries with explicit ordering, compare their rows, and measure runtime separately. A hint may become a poor choice as data or versions change. Do not confuse an optimizer hint with an index hint or a global optimizer_switch change.

فلگ‌ها رو فقط بخوان؛ یک‌جا بازنویسی نکنRead flags; do not replace the whole list
SELECT @@SESSION.optimizer_switch;

اگه تغییر session لازم شد، مقدار قبلی رو ثبت کن، فقط همان فلگ رو در محیط disposable آزمایش کن و برگردان. تغییر سراسری سرور، جواب امن یک query نامعلوم نیست.

If a session change is needed, record the previous value, test only the relevant flag in a disposable session, and restore it. A global server change is not a safe answer to one unexplained query.

روال ticket بعدیA workflow for the next ticket

  1. نسخه و query دقیق رو ثبت کن.
  2. Record the version and exact query.
  3. اندازه و توزیع داده رو بسنج.
  4. Measure data size and distribution.
  5. estimate، actual و زمان اجرا رو از هم جدا نگه دار.
  6. Keep estimates, actuals, and runtime distinct.
  7. فقط اگه سؤال «چرا؟» باقی است، trace محدود بگیر.
  8. Collect a narrow trace only if “why?” remains unanswered.
  9. یک فرضیه رو با یک تغییر و همان query بیازما.
  10. Test one hypothesis with one change and the same query.
  11. قبل از نگه‌داشتن hint، هزینهٔ نگه‌داری و تغییر workload رو بسنج.
  12. Consider maintenance and workload changes before keeping a hint.

اگه تخمین غلط است، آمار رو بررسی کن؛ اگه اجرا بد است، زمان و rows واقعی رو بسنج؛ اگه plan با داده عوض شده، این به‌تنهایی bug نیست. علت رو فقط به لایه‌ای نسبت بده که مدرکش رو داری.

If estimates are wrong, inspect statistics. If execution is poor, measure runtime and actual rows. A plan that changes with the data is not automatically a bug. Attribute causes only to the layer supported by evidence.
