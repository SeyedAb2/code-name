optimizer واقعاً می‌دونه داده‌ها چه شکلی‌اند؟

Does the optimizer know the shape of the data?

در فصل قبل دیدیم type و Extra حکم قطعی نیستند. حالا یک علت رایج برای تخمین بد رو بررسی می‌کنیم: جدول می‌گه ۱۰۰۰ ردیف دارد، اما ستون state به‌هیچ‌وجه یکنواخت نیست؛ ۹۰۰ ردیف common، ۹۰ تا rare و فقط ۱۰ تا critical هستن. اگه optimizer این تفاوت رو نبیند، تخمین selectivity ممکنه از واقعیت دور شود.

Chapter 22 showed that type and Extra are not verdicts. Now we investigate a common source of poor estimates: a table has 1,000 rows, but state is far from uniform—900 common, 90 rare, and only 10 critical. If the optimizer cannot see that skew, its selectivity estimate can miss reality.

پیش‌نیازPrerequisite: فصل‌های ۱۹ تا ۲۲نسخهٔ مرجعReference: MySQL 9.7زمانTime: ۹۰ دقیقه · ۱۸ تمرین

چرا شرط یکسان برای دو مقدار، یک اندازهٔ نتیجه نمی‌ده؟Why does the same predicate produce different result sizes?

پرس‌وجو روی critical کند نیست چون عبارت SQL فرق کرده؛ مقدار داده فرق کرده هست. اگه مدل optimizer از توزیع اطلاع نداشته باشه، ممکنه برای مقدارهای مختلف تخمین مشابهی بزند. این‌جا histogram وارد می‌شه: خلاصه‌ای تقریبی از توزیع یک ستون که optimizer می‌تونه برای تخمین بعضی شرط‌ها به کار ببرد.

The query on critical is not slow because the SQL expression changed; the data value did. Without useful distribution information, the optimizer may estimate different values similarly. A histogram is an approximate summary of one column’s distribution that the optimizer can use for certain predicate estimates.

دقت کن: histogram داده رو index نمی‌کنه، ردیفی رو پیدا نمی‌کنه و query رو اجرا نمی‌کنه. قرار نیست همهٔ planها رو بهتر کند؛ هدفش این هست که optimizer در موارد مناسب تخمین ردیف دقیق‌تری داشته باشه.

Important distinction: a histogram does not index the data, locate rows, or execute a query. It will not improve every plan; its purpose is to help the optimizer estimate rows more accurately when applicable.

توزیع نامتوازن رو خودمان بسازیمCreate a skewed distribution ourselves

schema جدا می‌سازیم تا هیچ تغییر آماری به دیتابیس کاری نرسد. جدول ۱۰۰۰ ردیف دارد، اما state به سه گروه نابرابر تقسیم شده. قبل از DROP نام schema رو بررسی کن؛ این آزمایش فقط برای محیط disposable هست.

We use a dedicated schema so no statistics changes touch a work database. The table has 1,000 rows split unevenly across three state values. Verify the schema before DROP; this experiment is for a disposable environment only.

ساخت توزیع قابل‌مشاهدهBuild a visible skew
CREATE DATABASE IF NOT EXISTS codenames_histogram_lab;
USE codenames_histogram_lab;
DROP TABLE IF EXISTS work_item;

CREATE TABLE work_item (
  item_id INT NOT NULL PRIMARY KEY,
  state VARCHAR(12) NOT NULL,
  score INT NOT NULL,
  team_id INT NOT NULL
) ENGINE=InnoDB;

INSERT INTO work_item(item_id,state,score,team_id)
WITH RECURSIVE seq(n) AS (
  SELECT 1 UNION ALL SELECT n+1 FROM seq WHERE n < 1000
)
SELECT n,
       CASE WHEN n<=900 THEN 'common'
            WHEN n<=990 THEN 'rare' ELSE 'critical' END,
       n,
       1+MOD(n,8)
FROM seq;

SELECT state,COUNT(*) AS rows_per_state
FROM work_item GROUP BY state ORDER BY rows_per_state DESC;

خروجی رو باید خودت ببینی: common برابر ۹۰۰، rare برابر ۹۰ و critical برابر ۱۰. این توزیع واقعی جدول است؛ هنوز نمی‌دونیم optimizer آن رو چطور برآورد می‌کنه.

Verify the result yourself: common has 900 rows, rare 90, and critical 10. This is the table’s actual distribution; we have not yet seen what the optimizer estimates.

پیش از histogram: تخمین رو ثبت کنBefore the histogram: capture the estimate

برای دو مقدار نامتوازن، EXPLAIN می‌گیریم و شمارش واقعی رو جدا انجام می‌دیم. در خروجی جدولی، rows و filtered تخمین‌های plan هستن؛ COUNT عدد واقعی ردیف‌های منطبق رو می‌ده. اندازهٔ دقیق plan به نسخه و آمار server وابسته است، پس خروجی خودت رو حفظ کن.

We explain two skewed values and count matching rows separately. In traditional output, rows and filtered are plan estimates; COUNT returns the actual matching rows. Exact plan values depend on server version and statistics, so preserve your own output.

یک شرط common و یک شرط criticalOne common and one rare predicate
ANALYZE TABLE work_item;
EXPLAIN FORMAT=TRADITIONAL
SELECT item_id FROM work_item WHERE state='common';
EXPLAIN FORMAT=TRADITIONAL
SELECT item_id FROM work_item WHERE state='critical';
SELECT state,COUNT(*) FROM work_item
WHERE state IN ('common','critical') GROUP BY state;

این‌جا هنوز histogram نساخته‌ایم. تخمین‌ها ممکنه نزدیک یا دور باشند؛ مسئله رو با یک عدد ثابت از پیش تعیین نمی‌کنیم. نکته این هست که همان ستون، selectivityهای بسیار متفاوتی دارد و COUNT مدرک مقدار واقعی رو فراهم می‌کنه.

We have not created a histogram yet. Estimates may be close or far off; we do not prescribe a fixed plan number. The key fact is that this column has very different selectivities, and COUNT provides actual evidence.

histogram یک خلاصهٔ ستونی است، نه indexA histogram summarizes one column; it is not an index

با ANALYZE TABLE ... UPDATE HISTOGRAM برای ستون state خلاصهٔ توزیع می‌سازیم. چون این ستون سه مقدار متمایز دارد و bucket کافی می‌خوایم، MySQL می‌تونه histogram از نوع singleton تولید کند؛ یعنی برای مقدارهای مجزا bucket داشته باشه. برای مقدارهای یکتای زیادتر از bucketها، قالب equi-height بازه‌ها رو خلاصه می‌کنه.

We create a distribution summary for state with ANALYZE TABLE ... UPDATE HISTOGRAM. Because this column has three distinct values and we request enough buckets, MySQL can produce a singleton histogram, with buckets for individual values. When distinct values exceed the bucket count, equi-height summarizes ranges instead.

histogram بساز و metadata رو بخوانCreate the histogram and inspect metadata
ANALYZE TABLE work_item
UPDATE HISTOGRAM ON state WITH 16 BUCKETS;

SELECT TABLE_SCHEMA,TABLE_NAME,COLUMN_NAME,
       JSON_EXTRACT(HISTOGRAM,'$."histogram-type"') AS histogram_type,
       JSON_LENGTH(JSON_EXTRACT(HISTOGRAM,'$.buckets')) AS bucket_count,
       JSON_EXTRACT(HISTOGRAM,'$."last-updated"') AS last_updated,
       JSON_EXTRACT(HISTOGRAM,'$."sampling-rate"') AS sampling_rate
FROM INFORMATION_SCHEMA.COLUMN_STATISTICS
WHERE TABLE_SCHEMA=DATABASE()
  AND TABLE_NAME='work_item' AND COLUMN_NAME='state';

در metadata، نوع histogram و تعداد bucketها رو می‌بینی؛ sampling_rate می‌گه چه سهمی از داده برای ساخت خلاصه خوانده شده. histogram تقریبی هست و ممکنه sample همهٔ مقدارهای مهم رو نگیرد. این خروجی metadata است، نه تضمین استفادهٔ optimizer در هر query.

Metadata shows the histogram type and bucket count; sampling_rate reports the fraction of data read to build the summary. A histogram is approximate, and a sample can miss important values. This output proves metadata exists, not that the optimizer will use it for every query.

بعد از ساخت، همان سؤال رو دوباره بپرسAfter creating it, ask the same question again

برای مقایسه، queryها رو عوض نمی‌کنیم؛ فقط plan همان predicateها رو دوباره می‌گیریم. اگه تخمین یا filtered تغییر کرد، اثر metadata رو دیده‌ایم. اگه تغییر نکرد، هنوز اشتباه نکرده‌ایم: optimizer ممکنه از range estimate استفاده کند، histogram برای شکل query قابل‌اعمال نباشه یا مقدار قبلی‌اش کافی بوده باشه.

For a fair comparison, keep the predicates unchanged and capture the plans again. If estimates or filtered change, we observed an effect from the metadata. If not, that does not mean the experiment failed: the optimizer may use range estimates, the histogram may not apply to the query shape, or the previous estimate may already have been sufficient.

همان plan و همان COUNTRepeat the same plans and counts
EXPLAIN FORMAT=TRADITIONAL
SELECT item_id FROM work_item WHERE state='common';
EXPLAIN FORMAT=TRADITIONAL
SELECT item_id FROM work_item WHERE state='critical';
SELECT state,COUNT(*) FROM work_item
WHERE state IN ('common','critical') GROUP BY state;

نتیجهٔ plan رو کنار COUNT واقعی بگذار؛ اگه اختلاف کم شد، این نمونه نشان می‌ده تخمین با histogram بهتر شده، نه این‌که query حتماً سریع‌تر اجرا می‌شه. برای زمان اجرا باید شواهد فصل ۲۱ رو جدا بگیری.

Compare plan estimates with actual counts. If the mismatch narrows, this sample shows improved estimation—not necessarily a faster query. Measure runtime separately using Chapter 21’s evidence.

histogram چه چیزهایی رو نمی‌بیند؟What does a histogram not see?

histogram برای یک ستون خلاصه می‌سازد. به‌تنهایی رابطهٔ بین state و team_id رو ثبت نمی‌کنه؛ اگه critical بیشتر در یک تیم باشه، تخمین شرط ترکیبی می‌تونه باز هم خطا کند. برای ستون‌های indexed هم optimizer ممکنه estimate مربوط به range/index dive رو ترجیح بده. histogram جای index، آمار index یا شناخت workload رو نمی‌گیره.

A histogram summarizes one column. It does not by itself capture the relationship between state and team_id; if critical is concentrated in one team, a combined predicate can still be misestimated. For indexed columns, the optimizer may prefer range or index-dive estimates. A histogram does not replace an index, index statistics, or workload knowledge.

ساخت histogram روی درخواست انجام می‌شه و پس از تغییر داده ممکنه کهنه شود. MySQL 9.7 به‌طور پیش‌فرض آن رو در حالت MANUAL UPDATE نگه می‌دارد؛ یعنی باید آگاهانه دوباره بسازی/به‌روز کنی. AUTO UPDATE گزینه‌ای جداست و رفتار نگه‌داری رو عوض می‌کنه، نه این‌که histogram رو به index تبدیل کند.

Histogram generation is on demand, so it can become stale after data changes. MySQL 9.7 defaults to MANUAL UPDATE: you deliberately regenerate it. AUTO UPDATE is a separate maintenance choice; it does not turn a histogram into an index.

هر histogram رو بی‌فکر روی هر ستون نساز. اول بپرس کدام query ثابت واقعاً به estimate آن ستون حساس است، ستون indexed هست یا نه، و داده چقدر تغییر می‌کنه. بعد metadata، plan و actual رو با هم مقایسه کن.Do not create histograms indiscriminately.First identify a real query sensitive to estimates for that column, whether it is indexed, and how often its data changes. Then compare metadata, plan, and actuals.

مدیریت histogram در محدودهٔ آزمایشManage the histogram within the lab boundary

در MySQL 9.7 می‌توان histogram یک ستون رو دوباره ساخت یا حذف کرد. در این lab، آن رو روی schema disposable می‌آزماییم. DROP HISTOGRAM داده و جدول رو حذف نمی‌کنه؛ فقط خلاصهٔ ستونی رو برمی‌دارد. پیش از هر دستور، schema جاری رو تأیید کن.

MySQL 9.7 can rebuild or drop a column histogram. We test that only in our disposable schema. DROP HISTOGRAM removes the column summary, not table data. Verify the current schema before each statement.

histogram رو تازه کن و سپس حذف کنRefresh, then remove the histogram
ANALYZE TABLE work_item
UPDATE HISTOGRAM ON state WITH 16 BUCKETS MANUAL UPDATE;

SELECT COLUMN_NAME,
       JSON_EXTRACT(HISTOGRAM,'$."histogram-type"') AS kind
FROM INFORMATION_SCHEMA.COLUMN_STATISTICS
WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='work_item';

ANALYZE TABLE work_item DROP HISTOGRAM ON state;

SELECT COUNT(*) AS remaining_rows FROM work_item;

پس از حذف باید histogram state از metadata ناپدید شود، اما remaining_rows همچنان ۱۰۰۰ هست. دو query آخر فرق «حذف آمار» و «حذف داده» رو ثابت می‌کنن. برای schema واقعی، حذف histogram رو فقط با فهم اثر روی plan انجام بده.

After dropping it, the state histogram should disappear from metadata while remaining_rows is still 1,000. The last checks distinguish removing statistics from deleting data. On a real schema, drop a histogram only after understanding the plan impact.

یک تیم گزارش داده تخمین ردیف‌های critical عجیب هست و کسی پیشنهاد ساخت index یا histogram داده. تو اول شواهد رو جمع می‌کنی. fixture رو بساز، توزیع رو با GROUP BY ثبت کن، plan و COUNT رو قبل از histogram نگه دار، خلاصه رو بساز و همان queryها رو دوباره اجرا کن. اگه تخمین تغییر نکرد، باز هم نتیجهٔ معتبر داری: از خودت بپرس آیا histogram برای این plan کاربرد داشته است؟

A team reports a surprising estimate for critical and someone suggests an index or histogram. Start with evidence. Build the fixture, record its distribution with GROUP BY, save plan and COUNT before the histogram, create the summary, then repeat the same queries. If the estimate does not change, ask whether the histogram applied to this plan; that is still a valid finding.

  1. تعداد actual هر state رو ثبت کن.
  2. Record actual counts for each state.
  3. plan و تخمین قبل رو ذخیره کن.
  4. Save the baseline plan and estimate.
  5. histogram رو بساز و metadata، sampling و زمان update رو بخوان.
  6. Create the histogram and inspect metadata, sampling, and update time.
  7. همان predicateها رو دوباره explain کن و با COUNT مقایسه کن.
  8. Explain the same predicates again and compare with COUNT.
  9. بنویس چه چیزی بهتر شد و چه چیزی هنوز ثابت نشده هست.
  10. Report what improved and what remains unproven.

قبولی یعنی بین estimate بهتر و query سریع‌تر فرق بگذاری؛ بین histogram و index هم مرز نگه داری. فقط اگه مدرک نشان داد خلاصه مفید بوده و برنامهٔ نگه‌داریش روشن است، آن رو نگه دار.

Passing means distinguishing a better estimate from a faster query, and a histogram from an index. Keep it only when evidence shows it is useful and its maintenance is understood.
