JSON در MySQL

JSON in MySQL

محصول‌ها چند ویژگی ثابت دارند؛ اما رویدادهای کلیک، مشخصات اختیاری و پاسخ سرویس هم‌شکل نیستند. تیم می‌خواهد همه‌چیز را در یک ستون متن بریزد. قبل از قبول این پیشنهاد، ببینیم نوع JSON در MySQL چه تضمینی می‌دهد و چه چیزی را به عهدهٔ طراحی ما می‌گذارد.

Products have stable attributes, but click events, optional details, and service responses do not share one shape. The team proposes putting everything in a text column. Before accepting that, let’s see what MySQL’s JSON type guarantees—and what remains our design responsibility.

پیش‌نیازPrerequisite: فصل ۶ · دادهٔ موقت و scopeمحیط مرجعLab baseline: MySQL 9.7.2 · InnoDBزمانTime: ۹۰ دقیقه · ۱۸ تمرین

مقدار ذخیره‌شده واقعاً JSON معتبر است؟Is the stored value actually valid JSON?

در گزارش پشتیبانی، برنامه گاهی JSON درست می‌فرستد و گاهی رشته‌ای ناقص. وقتی ستون از نوع TEXT باشد، ممکن است دادهٔ خراب تا زمان مصرف‌کنندهٔ بعدی بی‌صدا بماند. در MySQL نوع JSON هنگام ذخیره اعتبار سند را بررسی می‌کند؛ اما معتبر بودن syntax به معنی معتبر بودن شکل کسب‌وکار نیست.

The support pipeline sometimes sends valid JSON and sometimes a malformed string. In a TEXT column, bad data may survive until a later consumer fails. MySQL’s JSON type validates a document when stored—but valid syntax does not mean the business shape is valid.

MySQL سند JSON را در قالب داخلی بهینه‌شده نگه می‌دارد و امکان دسترسی به مسیرهای داخلی را می‌دهد. ستون JSON را مثل یک schema relational با constraintهای کامل تصور نکن: لازم است خودمان keyهای ضروری، نوع مقدار و قواعد تغییر را بررسی کنیم. JSON هم خودکار index نمی‌شود؛ برای queryهای پرتکرار، طراحی مسیر index جداگانه مطرح است.

MySQL stores JSON in an optimized internal representation and supports path access. Do not mistake a JSON column for a complete relational schema with every constraint: required keys, value types, and update rules still need deliberate checks. JSON is not automatically indexed; frequently queried paths may need a separate index design.

یک event کوچک و قابل‌تکرارA small, repeatable event fixture

به‌جای تبدیل همهٔ داده به JSON، هویت event و زمان را relational نگه می‌داریم و جزئیات متغیر را در payload قرار می‌دهیم. این مدل وقتی قابل‌دفاع است که payload واقعاً متغیر باشد؛ برای ستون‌های ثابت و پرتکرار مثل مشتری و قیمت، relational بودن اغلب query و constraint را روشن‌تر می‌کند.

Rather than moving everything into JSON, we keep event identity and time relational and put variable details in the payload. This is defensible when the payload truly varies; stable, frequently queried attributes such as customer and price are often clearer as relational columns.

ساخت fixtureCreate the fixture
CREATE TABLE IF NOT EXISTS product_event (
  event_id BIGINT PRIMARY KEY,
  created_at DATETIME NOT NULL,
  payload JSON NOT NULL
) ENGINE=InnoDB;

INSERT INTO product_event(event_id,created_at,payload) VALUES
(101,'2026-10-01 10:00:00',
 JSON_OBJECT('kind','view','product_id',42,'source','search')),
(102,'2026-10-01 10:05:00',
 JSON_OBJECT('kind','cart_add','product_id',42,'quantity',2)),
(103,'2026-10-01 10:10:00',
 JSON_OBJECT('kind','view','product_id',77,'source','campaign'));

SELECT event_id,JSON_PRETTY(payload)
FROM product_event ORDER BY event_id;

JSON_OBJECT مقدارها را به JSON تبدیل می‌کند و از به‌هم‌چسباندن دستی quote و escape جلوگیری می‌کند. خروجی را با JSON_PRETTY خواناتر می‌کنیم؛ این فقط نمایش است و شکل storage را تغییر نمی‌دهد.

JSON_OBJECT constructs JSON values and avoids manual quote/escape concatenation. JSON_PRETTY makes the output easier to inspect; it changes presentation, not stored structure.

path می‌خوانیم؛ نوع خروجی را هم می‌پرسیمRead a path—and ask what type came back

مسیر $.kind یعنی key سطح اول kind. JSON_EXTRACT یک JSON value برمی‌گرداند، نه لزوماً SQL string معمولی. عملگر ->> معادل استخراج و unquote است و برای مقایسهٔ متنی مناسب‌تر است. با query زیر هر دو شکل را کنار هم ببین.

The path $.kind selects the top-level kind key. JSON_EXTRACT returns a JSON value, not necessarily an ordinary SQL string. The ->> operator extracts and unquotes, which is more convenient for text comparisons. Compare both forms below.

استخراج یک مسیرExtract one path
SELECT event_id,
       payload->'$.kind' AS kind_json,
       payload->>'$.kind' AS kind_text,
       JSON_TYPE(payload->'$.quantity') AS quantity_type
FROM product_event
ORDER BY event_id;

در event اول، kind_json مقدار JSON رشته‌ای دارد و kind_text متن unquote شده است. برای eventهایی که quantity ندارند، نتیجهٔ path غایب با SQL NULL یکی نیست که بدون بررسی با JSON null قاطی کنیم؛ presence را با JSON_CONTAINS_PATH یا آزمون مناسب جدا کن.

For the first event, kind_json is a JSON string while kind_text is unquoted text. A missing path is not something to casually conflate with a JSON null literal; test presence with JSON_CONTAINS_PATH or another deliberate check.

تفاوت key غایب و مقدار حاضرDistinguish an absent key from a present value
SELECT event_id,
       JSON_CONTAINS_PATH(payload,'one','$.quantity') AS has_quantity,
       JSON_TYPE(payload->'$.quantity') AS quantity_json_type,
       payload->>'$.quantity' AS quantity_text
FROM product_event ORDER BY event_id;

از JSON scalar به مقدار SQL با نوع روشنConvert a JSON scalar to an explicitly typed SQL value

اگر quantity را برای محاسبه لازم داری، مقایسهٔ متن با عدد نتیجهٔ قابل‌اتکایی نیست. JSON_VALUE در نسخهٔ مرجع این دوره می‌تواند مقدار را به نوعی مثل UNSIGNED برگرداند. نوع RETURNING را صریح می‌کنیم و رفتار key غایب یا مقدار نامعتبر را تعیین می‌کنیم؛ اگر نسخهٔ مقصد فرق دارد، syntax و پشتیبانی را همان‌جا بسنج.

If quantity drives arithmetic, comparing text with a number is not a reliable model. In this course’s reference version, JSON_VALUE can return a value as a type such as UNSIGNED. We specify RETURNING and decide what happens for a missing key or invalid value; check syntax and support on a different target release.

تبدیل با نوع صریحConvert using an explicit type
SELECT event_id,
       JSON_VALUE(payload,'$.quantity' RETURNING UNSIGNED
         NULL ON EMPTY ERROR ON ERROR) AS quantity
FROM product_event ORDER BY event_id;

ردیف view مقدار NULL برای key غایب دارد؛ این تصمیم query است. اگر برنامه باید رویداد cart_add را حتماً quantityدار بداند، فقط NULL کافی نیست: constraint یا validation برنامه باید این قاعدهٔ وابسته به kind را enforce کند.

View events return NULL for the missing key because that is the query’s chosen behavior. If cart_add must always include quantity, NULL handling alone is not enough; a constraint or application validation must enforce the kind-specific rule.

تغییر یک مسیر را با JSON_SET بسنجChange a path with JSON_SET

فرض کن منبع قبلی نام کلید را با source ثبت می‌کرده و قرارداد تازه channel می‌خواهد. روی fixture یک ردیف را تغییر می‌دهیم و قبل و بعد را می‌خوانیم. JSON_SET مسیر موجود را عوض می‌کند و مسیر تازه را اضافه می‌کند؛ اگر مقدار کامل را رشته‌سازی کنی، escaping و نوع JSON را خودت باید درست مدیریت کنی.

Suppose an older producer used source while the new contract wants channel. We modify one lab row and inspect before and after. JSON_SET replaces an existing path and adds a new one; if you build the whole value as a string, you must manage escaping and JSON types yourself.

یک تغییر محدود و قابل‌بررسیMake one bounded, inspectable change
SELECT event_id,payload FROM product_event WHERE event_id=101;
UPDATE product_event
SET payload = JSON_SET(payload,'$.channel',payload->'$.source')
WHERE event_id=101;
SELECT event_id,JSON_PRETTY(payload)
FROM product_event WHERE event_id=101;

این query channel را به‌صورت JSON string می‌سازد، چون مقدار source از JSON استخراج شده؛ پس از تغییر، source هم هنوز هست. اگر می‌خواهی key قبلی حذف شود، باید آن را صریح با JSON_REMOVE برداری و بعد assertion بگیری.

This query creates channel from the extracted JSON source value, so source remains present. If the old key should disappear, remove it explicitly with JSON_REMOVE and assert the resulting shape.

Syntax معتبر، قرارداد کامل نیستValid syntax is not a complete contract

نوع JSON malformed document را رد می‌کند؛ اما سند {"kind":"cart_add"} از نظر JSON معتبر است، حتی اگر cart_add الزاماً quantity بخواهد. قاعدهٔ وابسته به نوع event را باید جدا enforce کنی. یک query تشخیصی می‌تواند دادهٔ ناسازگار را پیدا کند، حتی اگر مسیر نوشتن فعلی قرار است جلوی آن را بگیرد.

The JSON type rejects malformed documents, but {"kind":"cart_add"} is valid JSON even if cart_add requires quantity. A kind-dependent rule needs separate enforcement. A diagnostic query can find inconsistent rows even when today’s write path is supposed to prevent them.

یافتن event ناسازگارFind inconsistent events
SELECT event_id,payload
FROM product_event
WHERE payload->>'$.kind'='cart_add'
  AND JSON_CONTAINS_PATH(payload,'one','$.quantity')=0;

خروجی خالی یعنی در دادهٔ فعلی موردی پیدا نشد؛ اثبات نمی‌کند همهٔ clientها آینده را هم درست می‌نویسند. آزمون invalid JSON را در statement جدا انجام بده، چون خطای درج ممکن است اجرای batch را متوقف کند.

An empty result means no current violation was found; it does not prove every future client will write correctly. Test invalid JSON as a separate statement because an insert error may stop a batch.

چرا JSON را مستقیم index نمی‌کنیم؟Why not index the JSON document directly?

در MySQL ستون JSON را مثل یک ستون scalar معمولی مستقیماً index نمی‌کنیم. اگر روی path مشخصی بارها filter می‌زنی، generated column یا قابلیت index مرتبط را با plan و نسخه بررسی می‌کنیم؛ این موضوع فصل‌های index است، نه یک index جادویی برای کل document. فعلاً query و تعداد ردیف بررسی‌شده را با EXPLAIN ثبت کن تا مسئله را اندازه بگیریم.

MySQL does not index a JSON column directly like an ordinary scalar column. If a path is filtered repeatedly, evaluate a generated column or the relevant indexing feature with plans and version evidence; this is an indexing design, not a magic index over the whole document. For now, inspect the query with EXPLAIN and measure the actual issue.

دیدن plan بدون ادعای performanceInspect a plan without claiming performance
EXPLAIN
SELECT event_id,created_at
FROM product_event
WHERE payload->>'$.kind'='view';

EXPLAIN طرح تخمینی را نشان می‌دهد، نه به‌تنهایی زمان واقعی همهٔ workloadها. در فصل‌های بعد یک مسیر JSON پرتکرار را به index قابل‌اندازه‌گیری تبدیل می‌کنیم؛ آن‌جا هزینهٔ نوشتن و نگهداری هم باید کنار latency خواندن دیده شود.

EXPLAIN shows an estimated plan, not the real latency of every workload. Later chapters will turn a frequently queried JSON path into a measurable index; write and maintenance costs must be considered alongside read latency.

۱۸ تمرین SQL18 SQL exercises

همهٔ تمرین‌ها را روی جدول product_event اجرا کن؛ ردیف‌های درج‌شدهٔ تازه را با شناسه‌های بالاتر از ۲۰۰ نگه دار تا fixture پایه دست‌نخورده بماند.

Use product_event for every exercise. Give new rows IDs above 200 so the original fixture remains unchanged.

1) سند را با constructor بساز / Build a document with a constructor

یک event آزمایشی با kind و product_id بساز و خروجی JSON را بخوان.

Create a test event with kind and product_id and inspect the JSON value.

SQL / SQL
INSERT INTO product_event VALUES(201,NOW(),JSON_OBJECT('kind','view','product_id',88)); SELECT payload FROM product_event WHERE event_id=201;

constructor نوع و escape را مدیریت می‌کند؛ NOW فقط timestamp ردیف relational است.

The constructor handles JSON typing and escaping; NOW is only the relational row timestamp.

2) JSON خراب را رد کن / Reject malformed JSON

در statement مستقل رشتهٔ JSON ناقص درج کن و خطای سرور را ثبت کن.

In a separate statement, insert malformed JSON and record the server error.

SQL / SQL
INSERT INTO product_event VALUES(202,NOW(),'{"kind":');

نوع JSON باید سند نامعتبر را رد کند؛ اگر client پیش از ارسال escape کرده، متن دقیق خطا را تفسیر کن.

The JSON type should reject the invalid document; account for any client-side escaping when reading the exact error.

3) مقدار JSON و متن را مقایسه کن / Compare JSON and text extraction

برای هر event kind را با هر دو عملگر استخراج کن.

Extract kind with both operators for every event.

SQL / SQL
SELECT event_id,payload->'$.kind' AS json_value,payload->>'$.kind' AS text_value FROM product_event ORDER BY event_id;

یکی JSON value و دیگری text unquoted می‌دهد؛ نوع مصرف‌کننده را مشخص کن.

One returns a JSON value and the other unquoted text; choose based on the consumer.

4) path سطح اول / Read a top-level path

product_id رویدادها را استخراج و بر اساس آن مرتب کن.

Extract and order events by product_id.

SQL / SQL
SELECT event_id,JSON_VALUE(payload,'$.product_id' RETURNING UNSIGNED) AS product_id FROM product_event ORDER BY product_id;

تبدیل typed باعث می‌شود خروجی برای مقایسه عددی روشن باشد.

Typed extraction makes numeric comparison explicit.

5) key غایب را پیدا کن / Find a missing key

eventهایی را پیدا کن که quantity ندارند اما kind آن‌ها cart_add است.

Find cart_add events missing quantity.

SQL / SQL
SELECT event_id FROM product_event WHERE payload->>'$.kind'='cart_add' AND JSON_CONTAINS_PATH(payload,'one','$.quantity')=0;

این بررسی shape فعلی است، نه constraint دائمی برای writer.

This checks current shape; it is not a permanent constraint on writers.

6) نوع value را query کن / Query the JSON value type

نوع JSON product_id و quantity را کنار event_id بخوان.

Read the JSON types of product_id and quantity beside each event ID.

SQL / SQL
SELECT event_id,JSON_TYPE(payload->'$.product_id'),JSON_TYPE(payload->'$.quantity') FROM product_event;

NULL path را از نوع JSON scalar حاضر تفکیک کن.

Distinguish an absent path from a present JSON scalar type.

7) آرایه را بساز / Construct an array

با JSON_ARRAY دو tag بساز و طول آن را query کن.

Build two tags with JSON_ARRAY and query its length.

SQL / SQL
SELECT JSON_ARRAY('new','sale') AS tags,JSON_LENGTH(JSON_ARRAY('new','sale')) AS tag_count;

خروجی count دو است؛ آرایه با رشتهٔ comma-joined یکی نیست.

The count is two; an array is not a comma-joined string.

8) filter روی kind / Filter by kind

فقط view eventها را با عملگر text برگردان.

Return only view events using text extraction.

SQL / SQL
SELECT event_id FROM product_event WHERE payload->>'$.kind'='view' ORDER BY event_id;

در این اندازهٔ fixture کارایی را نتیجه نگیر؛ فصل index آن را بررسی می‌کند.

Do not infer performance from this tiny fixture; the indexing chapters investigate that.

9) یک path را تغییر بده / Modify one path

برای event ۱۰۱ کلید channel را با JSON_SET اضافه کن و قبل/بعد را بخوان.

Add channel to event 101 with JSON_SET and inspect before and after.

SQL / SQL
UPDATE product_event SET payload=JSON_SET(payload,'$.channel','search') WHERE event_id=101; SELECT payload FROM product_event WHERE event_id=101;

فقط ردیف مشخص تغییر می‌کند؛ predicate را حذف نکن.

Only the selected row changes; keep the predicate.

10) key را حذف کن / Remove a key

source را از event ۱۰۱ حذف کن و presence را assert بگیر.

Remove source from event 101 and assert its absence.

SQL / SQL
UPDATE product_event SET payload=JSON_REMOVE(payload,'$.source') WHERE event_id=101; SELECT JSON_CONTAINS_PATH(payload,'one','$.source') FROM product_event WHERE event_id=101;

صفر یعنی path دیگر وجود ندارد.

Zero means the path is absent.

11) شرط typed بنویس / Write a typed predicate

cart_addهایی با quantity بزرگ‌تر از یک را پیدا کن.

Find cart_add events with quantity above one.

SQL / SQL
SELECT event_id FROM product_event WHERE payload->>'$.kind'='cart_add' AND JSON_VALUE(payload,'$.quantity' RETURNING UNSIGNED NULL ON EMPTY ERROR ON ERROR)>1;

نوع خروجی را صریح کردیم؛ malformed value باید با سیاست مشخص برخورد شود.

The result type is explicit; malformed values need a deliberate policy.

12) JSON_TABLE در رابطه با ردیف‌ها / Project values into rows

payload دو event را به ستون‌های relational تبدیل کن.

Project two event payloads into relational columns.

SQL / SQL
SELECT e.event_id,j.kind,j.product_id FROM product_event e JOIN JSON_TABLE(e.payload,'$' COLUMNS(kind VARCHAR(20) PATH '$.kind',product_id BIGINT PATH '$.product_id')) AS j;

JSON_TABLE شکل قابل query برای این statement می‌سازد؛ دادهٔ پایه را به table دائمی تبدیل نمی‌کند.

JSON_TABLE exposes a queryable row shape for this statement; it does not create a permanent base table.

13) scalar را با JSON_VALUE بازیابی کن / Extract a scalar with JSON_VALUE

product_id را به BIGINT تبدیل کن و رویدادهای محصول ۴۲ را بیاب.

Convert product_id to BIGINT and find events for product 42.

SQL / SQL
SELECT event_id FROM product_event WHERE JSON_VALUE(payload,'$.product_id' RETURNING UNSIGNED)=42;

تبدیل نوع را در خود expression روشن کرده‌ایم؛ predicate را با نوع واقعی داده هماهنگ نگه دار.

The conversion is explicit; keep the predicate aligned with the actual data type.

14) اندازهٔ سند را بررسی کن / Inspect document storage size

اندازهٔ storage JSON را برای هر event گزارش کن.

Report JSON storage size for every event.

SQL / SQL
SELECT event_id,JSON_STORAGE_SIZE(payload) AS bytes FROM product_event ORDER BY bytes DESC;

این مقدار را با حجم TEXT در یک جدول دیگر یکی نگیر؛ قالب و overhead متفاوت‌اند.

Do not equate this with a TEXT column’s size; representation and overhead differ.

15) تغییر کنترل‌شده و storage_free / Measure after update

یک مقدار کوتاه را با JSON_SET عوض کن و اندازه/فضای آزاد را query کن.

Replace a short value with JSON_SET and query size/free-space functions.

SQL / SQL
UPDATE product_event SET payload=JSON_SET(payload,'$.channel','web') WHERE event_id=101; SELECT JSON_STORAGE_SIZE(payload),JSON_STORAGE_FREE(payload) FROM product_event WHERE event_id=101;

مقدارها وابسته به سند و partial update هستند؛ از یک ردیف نتیجهٔ قطعی دربارهٔ دیسک کل سیستم نگیر.

Values depend on the document and partial-update behavior; one row does not prove whole-system disk usage.

16) plan را ثبت کن / Record the query plan

EXPLAIN را برای filter روی kind اجرا کن و access type و estimated rows را بنویس.

Run EXPLAIN for the kind filter and record access type and estimated rows.

SQL / SQL
EXPLAIN SELECT event_id FROM product_event WHERE payload->>'$.kind'='view';

بدون index path، plan ممکن است scan باشد؛ خروجی تخمینی است و اندازهٔ داده را هم باید در نظر گرفت.

Without an indexed path, the plan may scan; estimates and dataset size both matter.

17) malformed و نامعتبر از نظر business را جدا کن / Separate syntax errors from business violations

یک query برای سند نامعتبر از نظر kind/quantity بنویس؛ بعد یک INSERT با syntax خراب را جداگانه اجرا کن.

Write a query for kind/quantity business violations, then run a malformed-JSON insert separately.

SQL / SQL
SELECT event_id FROM product_event WHERE payload->>'$.kind'='cart_add' AND JSON_CONTAINS_PATH(payload,'one','$.quantity')=0; INSERT INTO product_event VALUES(203,NOW(),'not json');

اول syntaxهای معتبر اما ناسازگار را می‌یابد؛ دومی باید در ستون JSON رد شود. دو خطا دو لایهٔ متفاوت‌اند.

The query finds syntactically valid but inconsistent documents; the insert should fail JSON validation. These are different failure layers.

18) تصمیم طراحی را با evidence تحویل بده / Submit a design decision with evidence

برای kind پرتکرار تصمیم بگیر JSON نگهش داری یا ستون relational بسازی؛ query، plan و یک مدرک shape را تحویل بده.

Decide whether a frequently used kind remains in JSON or becomes relational; submit a query, plan, and shape evidence.

نمونهٔ مدرک / Example evidence
EXPLAIN SELECT event_id FROM product_event WHERE payload->>'$.kind'='view'; SELECT JSON_TYPE(payload->'$.kind'),COUNT(*) FROM product_event GROUP BY JSON_TYPE(payload->'$.kind');

تصمیم باید هم فراوانی query و هم ثبات attribute را در نظر بگیرد؛ JSON معتبر جای schema کسب‌وکار را نمی‌گیرد.

The choice must consider query frequency and attribute stability; valid JSON does not replace the business schema.

انعطاف JSON را با بی‌ساختاری اشتباه نگیرDo not confuse JSON flexibility with having no structure

حالا می‌دانیم نوع JSON syntax را کنترل می‌کند، pathها را queryپذیر می‌کند و برای ruleهای business به طراحی جدا نیاز داریم. اگر key خاصی مرتب filter می‌شود، باید اثر index را اندازه بگیریم؛ قبل از آن فصل بعد سراغ storage engine می‌رویم تا بفهمیم داده و index در چه بستری قرار می‌گیرند.

The JSON type validates syntax, makes paths queryable, and still leaves business rules to explicit design. If a key is filtered often, we need to measure an index strategy. First, next chapter looks at storage engines—the foundation beneath rows and indexes.
