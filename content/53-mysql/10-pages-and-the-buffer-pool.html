Pageها و Buffer Pool

Pages and the Buffer Pool

یک query برای بار دوم سریع‌تر به نظر می‌رسد. آیا query بهتر شد، یا داده از قبل در حافظه بوده؟ InnoDB داده و index را در pageهایی به نام buffer pool cache می‌کند. با دو مشاهدهٔ جدا یاد می‌گیریم چه چیزی را می‌توان از این نشانه فهمید و چه چیزی را نه.

A query appears faster the second time. Did the query improve, or was its data already in memory? InnoDB caches data and index pages in the buffer pool. With two separate observations, we’ll learn what the evidence tells us—and what it does not.

پیش‌نیازPrerequisite: فصل ۹ · clustered و secondary indexمحیط مرجعLab baseline: MySQL 9.7.2 · InnoDBزمانTime: ۸۵ دقیقه · ۱۸ تمرین

دفعهٔ دوم سریع‌تر شد؛ علت را می‌دانیم؟The second run was faster—do we know why?

تیم یک SELECT را دوبار می‌زند و بار دوم latency کمتر است. نتیجه‌گیری فوری: «index جدید لازم نداریم». اما بار دوم شاید pageهای data و index در RAM بوده‌اند، سیستم‌عامل cache گرم‌تری داشته، یا workload دیگری تمام شده باشد. یک مشاهدهٔ خوش‌شانس، مدرک پایدار برای تصمیم tuning نیست.

The team runs a SELECT twice and sees lower latency the second time. The quick conclusion is “we do not need a new index.” But data and index pages may already be in RAM, the OS cache may be warmer, or another workload may have finished. One lucky observation is not durable tuning evidence.

Buffer pool حافظهٔ InnoDB برای cache صفحه‌های table و index است. page واحد مدیریت و خواندن/نوشتن است و ممکن است چند ردیف را در خود جا دهد. وقتی فضا لازم شود، الگوریتمی شبیه LRU صفحه‌های کم‌استفاده‌تر را بیرون می‌گذارد؛ بنابراین دسترسی گرم/سرد بخشی از رفتار مشاهده‌شده است.

The buffer pool is InnoDB memory for caching table and index pages. A page is a read/write management unit and may hold multiple rows. When space is needed, an LRU-like algorithm evicts less-used pages, so warm versus cold access affects observations.

اندازه‌گیری را از baseline شروع کنStart measurement with a baseline

اول Server و اندازهٔ buffer pool را بخوان. سپس از SHOW ENGINE INNODB STATUS فقط بخش BUFFER POOL AND MEMORY را بررسی کن. خروجی این دستور بزرگ و global است؛ همین‌جا آن را به table آزمایش یا یک query خاص نسبت نده.

First inspect the server and buffer-pool size. Then examine the BUFFER POOL AND MEMORY section of SHOW ENGINE INNODB STATUS. The output is broad and global; do not attribute it to one lab table or query.

خط مبنای buffer poolBuffer-pool baseline
SELECT VERSION(),
       @@innodb_buffer_pool_size AS configured_bytes;

SHOW ENGINE INNODB STATUS;

در خروجی representative ممکن است خط‌هایی مثل Buffer pool size، Free buffers، Database pages، Modified db pages و Buffer pool hit rate ببینی. تعداد page با byte یکی نیست؛ اندازهٔ page را هم با @@innodb_page_size بپرس. اعداد با workload و زمان عوض می‌شوند.

Representative output may include Buffer pool size, Free buffers, Database pages, Modified db pages, and Buffer pool hit rate. Page count is not bytes; also inspect @@innodb_page_size. Values change with workload and time.

تفسیر واحدهاInterpret the units
SELECT @@innodb_page_size AS page_bytes,
       @@innodb_buffer_pool_size AS pool_bytes,
       @@innodb_buffer_pool_size / @@innodb_page_size AS approx_pages;

تقسیم بالا تخمین تعداد pageهای پیکربندی‌شده را می‌دهد؛ سربارها، چند instance و وضعیت runtime را با یک عدد دقیق و تضمینی یکی نکن.

This division estimates configured pages; do not treat overhead, instances, and runtime state as an exact guaranteed count.

Page گرم یعنی احتمال I/O کمتر، نه query بهینهA warm page can reduce I/O; it does not prove an optimal query

یک query کوچک را روی fixture اجرا کن و پیش و پس از آن snapshot بگیر. table آزمایشی ممکن است از قبل در buffer pool باشد؛ در محیط مشترک pageهای دیگر هم هم‌زمان وارد یا خارج می‌شوند. بنابراین هدف، خواندن شاهد و شناخت محدودیت آن است؛ ساختن benchmark قابل‌اعتماد در این فصل نیست.

Run a small query on the fixture and capture snapshots before and after. The lab table may already be cached; on a shared server other pages enter and leave simultaneously. The goal is to read evidence and its limits, not to create a reliable benchmark here.

دو snapshot برای مقایسهTwo snapshots for comparison
SHOW ENGINE INNODB STATUS;
SELECT COUNT(*) FROM codenames_innodb_layout.product_lookup;
SHOW ENGINE INNODB STATUS;

اگر Reads یا hit rate تغییر کرد، فقط یک رخداد global دیده‌ایم؛ نمی‌توانیم بگوییم همهٔ تفاوت از این SELECT آمده است. benchmark باید با dataset نماینده، query ثابت، concurrency کنترل‌شده و چند تکرار طراحی شود؛ این پروژه در فصل‌های tuning ادامه دارد.

A change in reads or hit rate is a global observation; it does not prove this SELECT caused the entire difference. A benchmark needs representative data, a fixed query, controlled concurrency, and repeated runs; later tuning chapters take that further.

Modified page یعنی هنوز باید نوشته شودA modified page still needs flushing

UPDATE ابتدا می‌تواند page حافظه را تغییر دهد و آن را dirty کند؛ بعداً InnoDB آن را به data file می‌نویسد. مقدار Modified db pages یا pending writes شاهدی از کار buffer pool است، نه تعداد rowهای commitنشده و نه اثبات از دست‌رفتن داده. redo و checkpoint را در فصل بعد جدا می‌کنیم.

An UPDATE can modify an in-memory page and mark it dirty before InnoDB later writes it to the data file. Modified-page and pending-write counts describe buffer-pool work, not uncommitted row counts or proof of data loss. The next chapter separates redo and checkpoints.

یک update محدود و مشاهدهMake one bounded update and observe
UPDATE codenames_innodb_layout.product_lookup
SET title='Buffer pool lab'
WHERE product_id=101;

SHOW ENGINE INNODB STATUS;

در محیط مشترک status ممکن است تغییرهای همهٔ connectionها را شامل شود. هیچ‌وقت برای دیدن dirty page سرور را kill نکن؛ آزمایش خاموشی ناگهانی خارج از scope این فصل است.

On a shared server, status may include changes from every connection. Never kill the server to observe dirty pages; crash testing is outside this chapter’s scope.

hit rate را به‌تنهایی هدف نکنDo not optimize the hit rate alone

hit rate بالا گاهی برای workload خوب است، اما می‌تواند از cache گرم حتی برای query بد هم بیاید. یک full scan ممکن است cache را با pageهای کم‌فایده پر کند. latency، read workload، page reads، تعداد row بررسی‌شده، plan و فشار حافظه را با هم بخوان؛ یک ratio بدون بازهٔ زمانی و زمینه تصمیم نیست.

A high hit rate can be good for a workload, but a poor query can also benefit from a warm cache. A full scan may pollute the cache with low-value pages. Read latency, read workload, page reads, examined rows, plan, and memory pressure together; a ratio without time window and context is not a decision.

برای فهرست صفحه‌های buffer pool، جدول‌های INNODB_BUFFER_PAGE و INNODB_BUFFER_PAGE_LRU وجود دارند، اما query کردن آن‌ها می‌تواند performance را تحت تأثیر قرار دهد. در production بی‌بررسی سراغشان نرو؛ ابتدا یک instance آزمایش را انتخاب کن.

InnoDB exposes buffer-page and LRU tables, but querying them can affect performance. Do not inspect them casually in production; reproduce the question on a test instance first.

آمار کم‌خطرتر از statusA lower-impact status check
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_pages%';

مقادیر status counter ممکن است cumulative باشند. اگر اختلاف می‌گیری، زمان شروع/پایان و restartهای بین دو نمونه را ثبت کن و چند query هم‌زمان را به یک query نسبت نده.

Status counters may be cumulative. When comparing deltas, record the interval and any restart between samples; do not attribute concurrent queries to one statement.

۱۸ تمرین SQL18 SQL exercises

تمرین‌ها مشاهده‌ای هستند؛ هیچ‌کدام نیاز به تغییر global buffer pool یا restart server ندارند. اگر مجوز status نداری، خطا را ثبت کن و از مدیر محیط راه دسترسی آزمایش را بخواه.

These are observation exercises; none requires changing the global buffer pool or restarting the server. If you lack status privileges, record the denial and request an approved lab method.

1) اندازهٔ page / Read page size

اندازهٔ InnoDB page را query کن.

Query the InnoDB page size.

SQL / SQL
SELECT @@innodb_page_size;

واحد byte است؛ این مقدار را با تعداد page اشتباه نگیر.

The value is in bytes; do not confuse it with a page count.

2) اندازهٔ pool را بخوان / Read pool size

buffer pool پیکربندی‌شده را برحسب byte گزارش کن.

Report configured buffer-pool bytes.

SQL / SQL
SELECT @@innodb_buffer_pool_size;

تنظیم پیکربندی به‌تنهایی utilization لحظه‌ای یا فشار کل RAM را نمی‌گوید.

Configuration alone does not show live utilization or total RAM pressure.

3) تخمین page count / Estimate page count

تعداد page پیکربندی‌شده را از size/page size حساب کن.

Estimate configured page count from size and page size.

SQL / SQL
SELECT @@innodb_buffer_pool_size/@@innodb_page_size AS approximate_pages;

این تخمین ظرفیت است، نه تعداد pageهای دادهٔ فعال.

This estimates capacity, not active data pages.

4) status را بگیر / Capture InnoDB status

و بخش buffer pool را پیدا کن.

Capture the buffer-pool section.

SQL / SQL
SHOW ENGINE INNODB STATUS;

بخش global است و محدود به یک table نیست.

The output is global, not scoped to one table.

5) free pageها را تفسیر کن / Interpret free pages

از status تعداد free buffers و database pages را ثبت کن.

Record free buffers and database pages from status.

مدرک / Evidence
SHOW ENGINE INNODB STATUS;

این‌ها page count هستند؛ از آن‌ها اندازهٔ کل دیتابیس روی دیسک را نتیجه نگیر.

These are page counts; they do not reveal total database size on disk.

6) dirty page را پیدا کن / Find modified pages

Modified db pages و pending writes را در خروجی status ثبت کن.

Record modified pages and pending writes.

مدرک / Evidence
SHOW ENGINE INNODB STATUS;

این‌ها کار flush را نشان می‌دهند، نه transaction commit نشده را.

They describe flushing work, not uncommitted transactions.

7) قبل و بعد یک query / Before and after one query

status بگیر، query ثابت روی fixture اجرا کن و status دوم را با زمان ثبت کن.

Capture status, run a fixed fixture query, then capture a second timestamped status.

SQL / SQL
SHOW ENGINE INNODB STATUS; SELECT COUNT(*) FROM codenames_innodb_layout.product_lookup; SHOW ENGINE INNODB STATUS;

تغییر global دیده می‌شود؛ attribution قطعی به query ممکن نیست.

The global change is visible, but attribution to this query is not certain.

8) شمارنده‌های read را بخوان / Read read counters

counterهای buffer pool read را query کن.

Query buffer-pool read counters.

SQL / SQL
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';

نام counter و بازهٔ زمانی را ثبت کن؛ مقدار cumulative را rate لحظه‌ای نخوان.

Record counter names and interval; do not read cumulative values as an instantaneous rate.

9) buffer pages را به‌صورت aggregate ببین / Inspect buffer-page aggregates

در test instance تعداد pageهای یک fixture را بررسی کن؛ روی production اجرا نکن.

On a test instance, inspect pages for a fixture; do not run this on production.

SQL / SQL
SELECT PAGE_TYPE,COUNT(*) AS pages FROM information_schema.INNODB_BUFFER_PAGE WHERE TABLE_NAME LIKE '%product_lookup%' GROUP BY PAGE_TYPE;

این query می‌تواند اثر performance داشته باشد و نتیجه snapshot است؛ در محیط تمرینی اجرا کن.

This query can affect performance and returns a snapshot; use a lab environment.

10) LRU جایگاه page را ببین / Inspect LRU positions

در test instance تعداد pageهای table را از LRU metadata بشمار.

Count table pages in LRU metadata on a test instance.

SQL / SQL
SELECT COUNT(*) FROM information_schema.INNODB_BUFFER_PAGE_LRU WHERE TABLE_NAME LIKE '%product_lookup%';

این شمارش تمام هزینه‌ها و pageهای file cache سیستم‌عامل را پوشش نمی‌دهد.

This count does not include every cost or the operating system’s file cache.

11) repeated run را با احتیاط مقایسه کن / Compare repeated runs cautiously

همان SELECT را سه بار اجرا و زمان client و query plan را ثبت کن.

Run the same SELECT three times and record client timing and query plan.

SQL / SQL
EXPLAIN SELECT * FROM codenames_innodb_layout.product_lookup WHERE product_id=101; SELECT * FROM codenames_innodb_layout.product_lookup WHERE product_id=101;

گرم‌شدن cache یکی از علت‌های تفاوت است؛ زمان‌سنجی client و بار محیط هم دخیل‌اند.

Cache warming is one possible cause; client timing and environment load also matter.

12) config را با occupancy قاطی نکن / Separate configuration and occupancy

اندازهٔ buffer pool و database pages را با دو منبع مختلف ثبت کن.

Record configured pool size and active database pages from separate sources.

SQL / SQL
SELECT @@innodb_buffer_pool_size; SHOW ENGINE INNODB STATUS;

اولی config byte است؛ دومی runtime page metrics را گزارش می‌کند.

The first is configured bytes; the second reports runtime page metrics.

13) پس از UPDATE status را ببین / Observe after an update

یک row آزمایش را تغییر بده و status را دوباره بگیر.

Update one lab row and capture status again.

SQL / SQL
UPDATE codenames_innodb_layout.product_lookup SET title='pool observation' WHERE product_id=101; SHOW ENGINE INNODB STATUS;

ممکن است dirty page و شمارنده‌ها تغییر کنند؛ عددها global و زمان‌مندند.

Dirty-page counts or counters may change; values are global and time-dependent.

14) فضای page را به byte تبدیل کن / Convert pages to bytes

تعداد page را در page size ضرب کن و برچسب approximate را نگه دار.

Multiply page count by page size and label the estimate approximate.

SQL / SQL
SELECT @@innodb_page_size*100 AS bytes_for_100_pages;

این فقط ظرفیت page payload را تخمین می‌زند، نه overhead کل buffer pool.

This estimates page capacity, not total buffer-pool overhead.

15) یک ratio را از زمینه جدا نکن / Preserve metric context

hit rate را از status ثبت کن و timestamp، workload و queryهای هم‌زمان را کنار آن بنویس.

Record hit rate from status alongside timestamp, workload, and concurrent queries.

مدرک / Evidence
SHOW ENGINE INNODB STATUS;

عدد تنها حکم کیفیت query یا کمبود/زیادی RAM نیست.

The number alone does not diagnose query quality or memory sizing.

16) دسترسی page inspection را ایمن نگه دار / Keep page inspection safe

در test instance query صفحه را اجرا کن؛ اگر روی محیط مشترک هستی آن را اجرا نکن و grant/runtime policy را بررسی کن.

Run page inspection on a test instance; on shared production, do not run it casually—check access and impact policy.

SQL / SQL
SELECT COUNT(*) FROM information_schema.INNODB_BUFFER_PAGE;

این table کل buffer pool را می‌کاود و خود inspection ممکن است پرهزینه باشد.

This scans buffer-pool metadata and the inspection itself can be costly.

17) علت سرعت بهتر را با شواهد تفکیک کن / Separate possible causes of faster timing

برای query ثابت EXPLAIN و status قبل/بعد بنویس و دو توضیح رقیب برای latency کمتر ارائه کن.

Capture EXPLAIN and status around a fixed query, then give two competing explanations for lower latency.

SQL / SQL
EXPLAIN SELECT * FROM codenames_innodb_layout.product_lookup WHERE product_id=101; SHOW ENGINE INNODB STATUS;

page گرم و تفاوت بار محیط هر دو ممکن‌اند؛ یک اجرای دوباره علت را ثابت نمی‌کند.

A warm page and changed environment load are both possible; one repeat does not prove causality.

18) گزارش buffer pool بنویس / Produce a buffer-pool report

یک query package بده که config، page size، status و plan query را جمع کند و برای هر مدرک یک محدودیت بنویسد.

Provide a query package collecting configuration, page size, status, and a query plan; state one limitation per evidence source.

SQL و تفسیر / SQL and interpretation
SELECT @@innodb_buffer_pool_size,@@innodb_page_size; SHOW ENGINE INNODB STATUS; EXPLAIN SELECT COUNT(*) FROM codenames_innodb_layout.product_lookup;

این package محیط را توصیف می‌کند؛ برای تصمیم tuning هنوز dataset نماینده، بازهٔ workload و measurement تکرارشده لازم است.

This describes the environment; tuning decisions still need representative data, workload intervals, and repeated measurements.

Cache علت است، اما همهٔ علت نیستCache matters, but it is not the whole explanation

حالا می‌توانی page size، وضعیت buffer pool و محدودیت hit rate را بخوانی، بدون آنکه از یک counter نتیجهٔ بزرگ بگیری. تغییر pageهای حافظه برای دوام هم باید روی دیسک و redo ثبت شود؛ فصل بعد سراغ redo، undo، purge و checkpoint می‌رویم تا مسیر تغییر از حافظه تا بازیابی را دنبال کنیم.

You can now read page size, buffer-pool state, and hit-rate limits without overclaiming from one counter. Durable changes also involve redo and disk writes; next we examine redo, undo, purge, and checkpoints to follow changes from memory into recovery.
