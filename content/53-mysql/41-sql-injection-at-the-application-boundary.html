یک apostrophe در نام مشتری؛ آیا query برنامه می‌شکند؟

An apostrophe in a customer name. Does the query break?

فرم جست‌وجو با نام معمولی کار می‌کنه، اما ورودی مثل O'Neil نتیجه رو خراب می‌کنه. راه درست این نیست که هر کاربر رو دستی escape کنیم؛ متن query ثابت می‌مونه و مقدار جدا bind می‌شه. نمونه‌ها توی این فصل روی دیتابیس تمرینی‌اند.

A search form works for ordinary names, but an input such as O'Neil breaks it. The answer is not to hand-escape every input: keep the SQL text fixed and bind the value separately. All examples use a lab database.

ورودی داده است؛ تا وقتی به syntax نچسبانیمInput is data until we splice it into syntax

چسباندن ورودی به رشتهٔ SQL می‌تونه quote و delimiter رو به بخشی از دستور تبدیل کند. prepared query مقدار رو جدا می‌فرستد. این کار injection در valueها رو مهار می‌کنه، اما validation، مجوز دسترسی و محدودیت طول رو جایگزین نمی‌کنه.

Concatenating input into SQL can turn quotes and delimiters into part of the statement. A prepared query sends values separately. This prevents injection through bound values, but does not replace validation, authorization, or length limits.

placeholder برای value است؛ نام جدول و ستون رو جایگزین نمی‌کنه.

A placeholder binds a value; it does not replace a table or column name.

با API واقعی driver پارامتر bind کنBind using the driver's API

در mysql2 از execute برای query پارامتری استفاده می‌کنیم. متن SQL ثابت هست و مقدار جداگانه در آرایه میاد. ورودی شبیه SQL همچنان یک value هست. کد زیر به بستهٔ mysql2 نیاز دارد.

In mysql2, use execute for a parameterized query. SQL stays fixed and values are passed in an array. SQL-like input remains a value. This code requires the mysql2 package.

import mysql from 'mysql2/promise';

const pool = mysql.createPool({
  host: process.env.DB_HOST,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME
});

const name = String(req.query.name ?? '');
const [rows] = await pool.execute(
  'SELECT customer_id, display_name FROM customers WHERE display_name = ?',
  [name]
);

secret رو log نکن. placeholder از value محافظت می‌کنه، ولی ورودی خالی، طول و مجوز هنوز قانون برنامه می‌خوان.

Do not log secrets. Binding protects the value, but empty input, length, and authorization still need application rules.

نام ستون پویاست؟ از allowlist انتخاب کنDynamic column? Select from an allowlist

placeholder نمی‌تونه نام ستون یا keyword رو bind کند. ورودی خام رو به query نچسبان؛ آن رو به یکی از انتخاب‌های ثابت کد نگاشت کن. جهت مرتب‌سازی نیز فقط از گزینه‌های مجاز انتخاب می‌شه.

A placeholder cannot bind a column name or keyword. Do not concatenate raw input; map it to a fixed code-owned choice. Sort direction must also come from allowed values.

const sortColumns = {
  newest: 'created_at',
  name: 'display_name'
};
const sortColumn = sortColumns[String(req.query.sort)];
if (!sortColumn) throw new Error('unsupported sort');

const direction = req.query.direction === 'asc' ? 'ASC' : 'DESC';
const limit = Math.min(Math.max(Number(req.query.limit) || 20, 1), 100);
const sql = 'SELECT customer_id, display_name FROM customers ORDER BY '
  + sortColumn + ' ' + direction + ' LIMIT ?';
const [rows] = await pool.execute(sql, [limit]);

identifierها فقط از map ثابت آمده‌اند؛ limit پس از parse و محدودشدن bind می‌شه. برای ورودی نامعتبر می‌تونی به‌جای default خطای 400 بدهی.

Identifiers come only from a fixed map; the parsed and bounded limit is bound. Invalid keys can instead produce HTTP 400.

parameterization مجوز دسترسی نیستParameterization is not authorization

اگه کاربر customer_id رو عوض کند و دادهٔ مشتری دیگری رو ببیند، این مشکل مجوز object-level هست. query رو طوری بنویس که مالکیت هم بررسی شود، حساب DB کم‌مجوز باشه و خطای جزئی در response عمومی نیاید. query امن می‌تونه همچنان از نظر منطق کسب‌وکار اشتباه باشه.

If changing customer_id lets someone read another customer's data, that is an object-level authorization failure. Check ownership in the query, use a restricted database account, and do not expose detailed errors publicly. A safely parameterized query can still be logically wrong.

Value باید parameter باشه، نه تکه‌ای از SQLValues belong in parameters, not SQL string fragments

Injection از جایی شروع می‌شه که دادهٔ کاربر رو بخشی از syntax می‌کنیم. برای اینکه فرقش ملموس بشه، همون input بدقلق رو یه بار با concatenation ذهنی نگاه کن و یه بار واقعاً bind کن.

Injection begins when user data becomes SQL syntax. Bind the same hostile-looking value as a parameter and observe that it remains data.

وقتی bind می‌کنی، apostrophe دیگه دستور جدید نمی‌سازه؛ فقط بخشی از value می‌مونه.

A quote inside a bound value does not become a new SQL command.

PREPARE s FROM 'SELECT customer_id,email FROM customers WHERE email = ?';
