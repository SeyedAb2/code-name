سرور، دیتابیس و schema در MySQL

Servers, databases, and schemas in MySQL

فصل قبل به Server وصل شدیم؛ اما اتصال موفق به‌تنهایی نمی‌گوید query بعدی روی کدام database اجرا می‌شود. این ابهام کوچک می‌تواند migration را به مقصد اشتباه ببرد. بیا مقصد را از خود نشست بپرسیم و بعد نام‌ها را صریح کنیم.

Last chapter we connected to a server, but a successful connection alone does not tell us which database the next query will use. That small ambiguity can send a migration to the wrong target. Let’s ask the session where it is, then make names explicit.

پیش‌نیازPrerequisite: فصل ۲ · اتصال TCP به MySQL محیط مرجعLab baseline: MySQL 9.7.2 · Docker زمانTime: ۸۰ دقیقه · ۱۸ تمرین

اتصال درست است؛ ولی مقصد query کجاست؟The connection works—but where will this query run?

برنامه به سرور وصل شده و `SELECT 1` هم جواب داده. توسعه‌دهنده migration را اجرا می‌کند؛ چند لحظه بعد متوجه می‌شود tableها را در database اشتباهی ساخته. سرور سالم بود، اتصال هم برقرار بود؛ چیزی که معلوم نبود context نشست بود.

The application connected and `SELECT 1` returned a result. A developer ran a migration, then noticed the tables landed in the wrong database. The server was healthy and the connection worked; the missing evidence was the session’s current context.

در MySQL یک Server می‌تواند چند database داشته باشد. در مستندات و دستورهای MySQL، واژهٔ `SCHEMA` مترادف `DATABASE` است؛ یعنی اینجا schema یک لایهٔ جدا و تو‌در‌تو مثل SQL Server نیست. این تفاوت را جدی بگیریم، چون عبارت آشنای «schema جدا بساز» در MySQL ممکن است معنی دیگری بدهد.

One MySQL server can host multiple databases. In MySQL statements and documentation, `SCHEMA` is a synonym for `DATABASE`; it is not a separate nested namespace layer as it is in SQL Server. That distinction matters because “create another schema” can mean something different depending on the product.

سه مرز که نباید یکی‌شان کنیمThree boundaries we should not collapse

Client با یک نشست به Server می‌رسد. نشست ممکن است database پیش‌فرض داشته باشد یا نداشته باشد. وقتی database انتخاب شده، نام کوتاه table در همان مقصد resolve می‌شود؛ نام کامل‌شده مثل `shop_lab.Products` مقصد را در خود query روشن می‌کند. هر دو شکل به همان Server و همان نشست مربوط‌اند، اما یکی به context پنهان‌تری تکیه دارد.

A client reaches a server through a session. A session may or may not have a default database. With one selected, a short table name resolves there; a qualified name such as `shop_lab.Products` makes the target explicit in the query. Both still use the same server and session, but one relies on more implicit context.

اول context را بپرس؛ بعد `USE` کنAsk for context first; then use `USE`

در lab فصل قبل database برابر `connect_lab` بود. حالا از همان connection این query را اجرا کن. `DATABASE()` نام database جاری را برمی‌گرداند؛ اگر `NULL` باشد، session database پیش‌فرض انتخاب‌شده ندارد. این وضعیت الزاماً خطا نیست، اما نام table بدون qualifier در چنین contextی معمولاً resolve نمی‌شود.

The previous chapter’s lab used `connect_lab`. Run this query in that connection. `DATABASE()` returns the current database name; if it returns `NULL`, the session has no default database selected. That is not necessarily an error, but an unqualified table name generally cannot resolve in that context.

پرسیدن مقصد از نشستAsk the session where it is
SELECT DATABASE() AS CurrentDatabase,
       SCHEMA() AS SameValueInMySQL,
       CURRENT_USER() AS AuthenticatedAccount;
SELECT @@hostname AS ServerHost,
       @@port AS ServerPort,
       VERSION() AS ServerVersion;

در MySQL، `SCHEMA()` هم‌معنی `DATABASE()` است. اما `CURRENT_USER()` accountای را نشان می‌دهد که سرور برای privilegeها به کار می‌برد؛ با `USER()` که هویت login سمت client را گزارش می‌کند یکی نیست. فعلاً نام‌ها را می‌خوانیم؛ فصل امنیت این تفاوت account را عمیق‌تر می‌کند.

In MySQL, `SCHEMA()` is synonymous with `DATABASE()`. `CURRENT_USER()` reports the account the server uses for privilege checking; it is not the same as `USER()`, which reports the client login identity. We only inspect these names here; the security chapter will examine account matching in depth.

`USE` فقط context نشست فعلی را عوض می‌کند؛ نه دیتابیس را rename می‌کند، نه نشست‌های دیگر را. در Client جدید، مقدار را دوباره بپرس. برنامه‌ای که connection pool دارد ممکن است نشست‌های متفاوتی تحویل بگیرد؛ نباید context یک connection را به connection دیگر نسبت بدهی.

`USE` changes only the current session’s context; it neither renames a database nor changes other sessions. Ask again from a new client. An application using a connection pool may receive different sessions, so do not assume one connection’s context carries over to another.

`IF NOT EXISTS` avoids an “already exists” error on rerun, but it does not change the settings of an existing database. If you get a warning, read it; then query metadata to verify whether the existing database has the settings you intend.

تلهٔ واژهٔ schema در MySQLThe MySQL meaning of “schema”

اگر از SQL Server آمده‌ای، ممکن است بخواهی `CREATE SCHEMA shop;` بزنی و داخلش `shop.Products` بسازی. در MySQL این کار databaseای به نام `shop` می‌سازد؛ `shop.Products` یعنی tableای به نام Products داخل همان database. پس یک سطح namespace جدا مثل schemaهای SQL Server ایجاد نشده است.

If you come from SQL Server, you might try `CREATE SCHEMA shop;` and expect to create `shop.Products` within it. In MySQL, that statement creates a database named `shop`; `shop.Products` means the Products table in that database. It does not add a separate namespace layer like SQL Server schemas.

دو واژه، یک کار در MySQLTwo keywords, one operation in MySQL
CREATE DATABASE schema_keyword_lab
  CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

CREATE SCHEMA IF NOT EXISTS schema_keyword_lab;

SELECT SCHEMA_NAME
FROM INFORMATION_SCHEMA.SCHEMATA
WHERE SCHEMA_NAME = 'schema_keyword_lab';

این آزمایش نشان می‌دهد `SCHEMA` نام جایگزین `DATABASE` است. خط دوم چون database از قبل ساخته شده warning می‌دهد و همان را دوباره می‌شناسد. در lab واقعی لازم نیست برای اثبات این نکته database اضافه بسازی؛ query مستندات و رفتار server کافی است. اگر ساختی، فقط همان database مشخص آزمایش را بعداً پاک کن.

This test shows that `SCHEMA` is an alternate keyword for `DATABASE`. The second statement warns that the database already exists and refers to the same object. You do not need an extra database in the main lab to prove the point; the documented behavior is enough. If you created it, remove only that named disposable database later.

نام کوتاه یا نام کامل؟ انتخاب را آگاهانه کنShort or qualified names? Choose deliberately

وقتی `USE codenames_shop_lab` انجام شده، `Products` نام کوتاه است. `codenames_shop_lab.Products` مقصد را صریح می‌کند. برای گزارش و اسکریپت چند-databaseای، نام کامل می‌تواند اشتباه context را کمتر کند. ولی qualifier مجوز دورزدن دسترسی نیست؛ privilege همان account هنوز بررسی می‌شود.

After `USE codenames_shop_lab`, `Products` is a short name. `codenames_shop_lab.Products` states its target explicitly. Qualified names can reduce context mistakes in reports and scripts that touch multiple databases. But qualification does not bypass access control; the account’s privileges still apply.

The metadata query is not scoped to the selected database, though the account’s visibility is still limited. The new database does not yet contain the Shop tables; later chapters add structure and data in stages. Here we have only established the target boundary.

حروف بزرگ و کوچک؛ روی لپ‌تاپت شرط نبندLetter case: do not bet on your laptop’s filesystem

رفتار case در نام database و table در MySQL می‌تواند به operating system و مقدار `lower_case_table_names` وابسته باشد. بنابراین queryای که روی Windows با `products` جواب می‌دهد ممکن است روی Linux با `Products` شکست بخورد. اسم را در همهٔ migrationها و queryها دقیقاً یکسان بنویس و تنظیم را برای حل اختلاف، وسط راه عوض نکن؛ این متغیر در شروع Server اثر دارد و تغییرش کار migration بی‌خطر نیست.

Case behavior for database and table names can depend on the operating system and `lower_case_table_names`. A query that works as `products` on Windows may fail as `Products` on Linux. Use identical spelling in migrations and queries, and do not change the variable midstream to “fix” a mismatch; it affects server initialization and is not a casual migration toggle.

تنظیم مؤثر را فقط بخوانInspect the effective setting; do not change it here

       @@lower_case_file_system AS LowerCaseFileSystem;

عدد خروجی را ثبت کن؛ آن را با حدس از سیستم‌عامل جایگزین نکن. تنظیم نصب‌شده را بین محیط‌ها یکسان و از اول هماهنگ نگه‌دار. خود آزمایش این مقدار را تغییر نمی‌دهد.

Record the returned values; do not infer them only from the operating system. Keep the initialized setting consistent across environments. This experiment does not change it.

چرا فهرست databaseها برای دو account فرق دارد؟Why can two accounts see different database lists?

یک همکار `SHOW DATABASES` می‌زند و database تو را نمی‌بیند؛ اولین حدس «سرور اشتباه است» است. اما MySQL فهرست را با privilege account محدود می‌کند: معمولاً فقط databaseهایی دیده می‌شوند که account روی آن‌ها دسترسی دارد، مگر privilege گستردهٔ لازم را داشته باشد. پس خروجی خالی، شاهد نبودن database نیست.

A teammate runs `SHOW DATABASES` and cannot see your database; the first guess is “wrong server.” But MySQL filters the list by account privileges: usually an account sees databases on which it has privileges, unless it has the broader privilege. An empty list is therefore not proof that the database is absent.

فهرست قابل‌مشاهده و مقصد دقیقVisible databases and the exact target

FROM INFORMATION_SCHEMA.SCHEMATA

`SHOW GRANTS` فقط مجوز account جاری را نشان می‌دهد. برای این فصل دسترسی مدیریتی را گسترده‌تر نکن؛ فصل ۳۹ ساخت account و privilege را جداگانه آزمایش می‌کند. اگر دیتابیس را نمی‌بینی، همین Server، account، host part و مجوز را با شاهد بررسی کن.

`SHOW GRANTS` displays the current account’s grants. Do not broaden permissions just to make this chapter’s list look complete; chapter 39 tests account and privilege design properly. If a database is invisible, verify the server, account, host part, and grants with evidence.

وقتی table «پیدا نمی‌شود»، هنوز drop نکنWhen a table is “missing,” do not drop anything yet

خطای `No database selected` با `Table doesn't exist` یکی نیست. اول context را بپرس؛ بعد databaseهای قابل‌مشاهده را ببین؛ در آخر metadata جدول را در مقصد مشخص query کن. این مسیر علت‌ها را جدا می‌کند و جلوی ساخت مجدد یا حذف اشتباه را می‌گیرد.

`No database selected` is not the same as `Table doesn't exist`. First inspect context, then visible databases, then query table metadata for the exact target. This separates causes and avoids recreating or deleting the wrong object.

FROM INFORMATION_SCHEMA.SCHEMATA
WHERE SCHEMA_NAME = 'ex3_lab';

پیش از اجرا مطمئن شو release هدف از این collation پشتیبانی می‌کند؛ دستور idempotent تنظیم database از قبل موجود را تغییر نمی‌دهد.

Check that the target release supports this collation; the idempotent statement does not alter settings on an existing database.

۶) schema در MySQL6) Schema in MySQL

با query نشان بده نام `schema_keyword_lab` در MySQL به‌صورت database ثبت شده است.

Use a query to show that `schema_keyword_lab` is registered as a database in MySQL.

اطلاعات schema/databaseSchema/database metadata
CREATE SCHEMA IF NOT EXISTS schema_keyword_lab;
SELECT SCHEMA_NAME
FROM INFORMATION_SCHEMA.SCHEMATA
WHERE SCHEMA_NAME = 'schema_keyword_lab';

`CREATE SCHEMA` مترادف `CREATE DATABASE` است؛ با SQL Server یک معنی ندارد.

`CREATE SCHEMA` is synonymous with `CREATE DATABASE`; it does not mean the same thing as in SQL Server.

۷) databaseهای قابل‌مشاهده7) Visible databases

فهرست databaseهایی که account فعلی اجازهٔ دیدنشان دارد را بگیر و نام آزمایش را جست‌وجو کن.

List databases visible to the current account and look for the lab database.

فهرست مشروط به privilegeA privilege-filtered list
SHOW DATABASES LIKE 'codenames_shop_lab';
SHOW GRANTS;

نبودن ردیف می‌تواند محدودیت visibility باشد. `SHOW GRANTS` account را بررسی می‌کند؛ privilege گسترده نده.

No row may reflect visibility limits. `SHOW GRANTS` inspects the account; do not add broad privileges.

۸) sessionها را از هم جدا کن8) Distinguish sessions

از دو Client query بزن که connection id و database جاری را برگرداند؛ دو مقدار را مقایسه کن.

From two clients, query the connection ID and current database, then compare the results.

اثر دو نشست فعالObserve two active sessions
SELECT CONNECTION_ID() AS SessionId,
       DATABASE() AS CurrentDatabase;

connection ID باید برای نشست‌های جدا فرق کند؛ database را هر نشست مستقل انتخاب می‌کند.

Separate sessions should have different connection IDs; each selects its own database.

۹) نام کامل table9) Qualify a table name

یک query بنویس که بدون `USE`، metadata جدول‌های database مشخص را بخواند.

Write a query that reads table metadata for an explicit database without using `USE`.

مقصد در خود شرطPut the target in the predicate
SELECT TABLE_SCHEMA, TABLE_NAME
FROM INFORMATION_SCHEMA.TABLES
WHERE TABLE_SCHEMA = 'connect_lab';

این query به current database وابسته نیست، اما خروجی‌اش همچنان به privilege بستگی دارد.

This query does not depend on the current database, but visibility still depends on privileges.

۱۰) schema پیش‌فرض هم‌معنی‌اش را مقایسه کن10) Compare the synonymous functions

queryای بنویس که `DATABASE()` و `SCHEMA()` را کنار هم برگرداند.

Write a query returning `DATABASE()` and `SCHEMA()` side by side.

مترادف در این محصولSynonyms in this product
USE connect_lab;
SELECT DATABASE() AS CurrentDatabase,
       SCHEMA() AS CurrentSchema;

در MySQL مقدارها برابرند؛ این را به SQL Server تعمیم نده.

The values match in MySQL; do not generalise this to SQL Server.

۱۱) تنظیم collation را تشخیص بده11) Diagnose a collation setting

اگر database موجود با collation دیگری ساخته شده، query کن و پیش از تغییر، مقدار ثبت‌شده را گزارش بده.

If an existing database has another collation, query and report its stored value before changing anything.

اول metadata، نه حدسMetadata before guessing
SELECT SCHEMA_NAME, DEFAULT_COLLATION_NAME
FROM INFORMATION_SCHEMA.SCHEMATA
WHERE SCHEMA_NAME = 'codenames_shop_lab';

ساخت با `IF NOT EXISTS` collation را عوض نمی‌کند. هر تغییر را با اثر روی مقایسهٔ متن و migration جداگانه طراحی کن.

`IF NOT EXISTS` does not change collation. Plan any change separately, considering text comparisons and migrations.

۱۲) حروف نام table12) Table-name case

مقدار مؤثر `lower_case_table_names` را بخوان و یک توضیح کوتاه در قالب comment SQL ثبت کن که چرا naming باید در migrationها ثابت باشد.

Read the effective `lower_case_table_names` and add an SQL comment explaining why migrations should keep naming consistent.

تنظیم را فقط بخوانRead, do not change, the setting
SELECT @@lower_case_table_names;
-- Keep database and table identifier casing identical across environments.

خروجی به محیط وابسته است؛ مقدار را اینجا تغییر نده، چون startup و فایل‌های داده را درگیر می‌کند.

The value depends on the environment. Do not change it here; doing so affects initialization and data files.

۱۳) خطای context را بازسازی کن13) Reproduce a context error

بدون `USE` یک نام کوتاه را امتحان کن، سپس همان query را با نام database کامل کن. هر دو را فقط در fixture بسنج.

Without `USE`, try a short name and then qualify it with the database. Test both only in the fixture.

مرز error و qualifierObserve the error boundary and qualification
SELECT * FROM Products;
SELECT * FROM codenames_shop_lab.Products;

در حال حاضر جدول Products را هنوز نساخته‌ایم، پس هر دو می‌توانند خطای نبود جدول بدهند. این آزمایش وجود table را تست نمی‌کند؛ برای context، `DATABASE()` را بخوان. فصل‌های بعد table را می‌سازند.

We have not created Products yet, so both may report a missing table. This does not test table existence; inspect context with `DATABASE()`. Later chapters create the table.

۱۴) یک database اضافه را امن بساز و پاک کن14) Safely create and remove one extra database

فقط database نام‌گذاری‌شدهٔ `ex3_disposable` را بساز، metadataاش را ببین و بعد از تأیید نام دقیق، حذفش کن.

Create only the named `ex3_disposable` database, inspect its metadata, then remove it after confirming its exact name.

هدف را قبل از DROP ثابت کنVerify the target before DROP
CREATE DATABASE ex3_disposable;
SELECT SCHEMA_NAME FROM INFORMATION_SCHEMA.SCHEMATA
WHERE SCHEMA_NAME = 'ex3_disposable';
DROP DATABASE ex3_disposable;

`DROP DATABASE` برگشت ساده ندارد؛ این فقط برای database خالی‌ای است که همین تمرین ساخته. روی اسم متغیر یا database مشترک اجرا نکن.

`DROP DATABASE` is not trivially reversible; this is only for the empty database created by this exercise. Never use a variable or shared database name here.

۱۵) فرق server port و host port15) Server port versus host port

یک query بنویس که port Server را ثبت کند و کنار گزارش بنویس برای اتصال host در فصل قبل کدام port را استفاده کردی.

Query the server port and report separately which host port you used in chapter 2.

دو سمت mapping را قاطی نکنKeep both sides of the mapping distinct
SELECT @@port AS ContainerServerPort;

خروجی معمولاً 3306 است؛ host port 3307 را Docker mapping می‌کند و SQL Server از مقدار آن باخبر نیست.

The result is normally 3306; Docker maps host port 3307, which the MySQL server itself does not know about.

۱۶) فهرست خالی را incident فرض نکن16) Do not treat an empty list as an incident

برای account محدود، دو query بنویس که فهرست قابل‌دیدن و grant جاری را جمع کند؛ از ساخت account تازه صرف‌نظر کن.

For a restricted account, write two queries to collect visible databases and current grants; do not create another account.

شواهد privilege-awarePrivilege-aware evidence
SHOW DATABASES;
SHOW GRANTS;

فهرست ممکن است محدود باشد. تشخیص را با account، host و grant بساز؛ برای دیدن همهٔ نام‌ها privilege global نده.

The list may be filtered. Diagnose with account, host, and grants; do not grant a global privilege merely to reveal every name.

۱۷) session تازه17) A fresh session

در Client دوم بدون تعیین database وصل شو؛ با یک query ثابت کن connection سالم است اما context انتخاب نشده. سپس context را برای همان نشست تنظیم کن.

Connect from a second client without a database; prove the connection works but no context is selected, then set context for that session.

اتصال و context دو بررسی‌اندConnection and context are separate checks
SELECT 1 AS Connected, DATABASE() AS CurrentDatabase;
USE connect_lab;
SELECT DATABASE() AS CurrentDatabase;

ابتدا نتیجهٔ `Connected=1` و database برابر NULL، سپس `connect_lab` است. `USE` باید در هر نشست تازه تکرار شود.

First expect `Connected=1` with a NULL database, then `connect_lab`. Run `USE` in every new session.

۱۸) گزارش مقصد برای migration18) A migration-target report

یک query برای گزارش یک‌خطی بنویس که قبل از migration database، host، port، version و connection ID را ثبت کند.

Write a one-row pre-migration report containing database, host, port, version, and connection ID.

مدرک مقصد پیش از تغییرTarget evidence before a change
SELECT DATABASE() AS CurrentDatabase,
       @@hostname AS ServerHost,
       @@port AS ServerPort,
       VERSION() AS ServerVersion,
       CONNECTION_ID() AS SessionId;

این query مقصد و نشست فعلی را ثبت می‌کند، اما مجوز اجرای migration یا سازگاری خود migration را ثابت نمی‌کند؛ آن‌ها را جدا بررسی کن.

This records the current target and session, but does not prove migration privileges or migration compatibility; verify those separately.

حالا database Shop مقصد مشخصی داردThe Shop database now has an explicit home

فهمیدیم Server، database و context نشست سه چیز نزدیک اما یکی نیستند؛ و در MySQL، `schema` را نباید بی‌فکر مثل SQL Server معنی کنیم. از اینجا به بعد Shop را در database مشخص نگه می‌داریم. قدم بعدی طبیعی است: وقتی ساختار برنامه عوض می‌شود، چطور schema را بدون خراب‌کردن داده تغییر بدهیم؟ فصل بعد با Generated Column و تغییر table سراغ همین مسئله می‌رود.

We separated server, database, and session context, and learned not to import SQL Server’s meaning of `schema` into MySQL. From here on, Shop will live in an explicit database. The next practical question is how to evolve its structure without damaging data. The next chapter uses generated columns and table changes to explore that problem.
