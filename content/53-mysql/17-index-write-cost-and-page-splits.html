هزینهٔ نوشتن و Page Split

Index Write Cost and Page Splits

query خواندن سریع‌تر شده، اما بعد از اضافه‌کردن چند index، بار import کندتر هست. این تناقض نیست: هر insert باید ساختارهای لازم رو هم به‌روز نگه داره. اگه page مقصد جا نداشته باشه، درخت ممکنه page رو split کند. این فصل هزینه رو از روی مسیر تغییر می‌فهمد، نه با ادعای دیدن split قطعی از یک آزمایش کوچک.

A read query improved, but imports slowed after several indexes were added. That is not a contradiction: each insert must maintain the relevant structures. If the target page has no room, the tree may split a page. We will reason about that cost from the write path, without claiming a tiny experiment proves a specific split occurred.

هر query تازه، یک تعهد تازهEvery new index is another obligation

فرض کن جدولی با کلید اصلی و چهار secondary index داریم. INSERT دیگر فقط یک ردیف در یک جای خیالی نمی‌ذاره: clustered record باید ساخته شود، و ورودی هر secondary index که مقدارش به تغییر مربوط هست هم باید سازگار بماند. UPDATE یک ستون indexشده می‌تونه ورودی قبلی رو حذف و جای تازه‌ای ثبت کند.

Suppose a table has a primary key and four secondary indexes. INSERT does not simply place one row in an abstract location: the clustered record is created, and each affected secondary index must remain consistent. Updating an indexed column may remove an old entry and add a new one.

تعداد indexها تنها عامل نیست؛ pageها از buffer pool یا disk خوانده می‌شوند، مقدارها ترتیب و توزیع خود رو دارن، و InnoDB می‌تونه بعضی تغییرهای secondary index رو با change buffer عقب بیندازد. پس latency یک statement رو به «تعداد index» تقلیل نده؛ اما ساختار اضافه قطعاً تعهد نگهداری دارد.

Index count is not the only factor: pages may come from buffer pool or disk, values have ordering and distribution, and InnoDB can defer some secondary-index changes through the change buffer. Do not reduce statement latency to “number of indexes,” but recognize that every additional structure creates maintenance obligations.

اگه مقدار tenant_id یا created_at عوض شود، کلید composite آن ردیف هم عوض شده هست. اگه event_type عوض شود، index آن هم باید به‌روز شود. حتی اگه query جدیدی از یک index استفاده نکند، DML همچنان باید درستی آن رو حفظ کند.

Page Split: وقتی ورودی در page جا نمی‌شهPage splits: when an entry no longer fits

B+ Tree از pageهای محدوداندازه ساخته شده هست. اگه insert در محدوده‌ای برسد که leaf page فضای کافی ندارد، InnoDB ممکنه page رو تقسیم و پیوندها و اطلاعات مسیر رو به‌روز کند. این کار بخشی از حفظ درخت مرتب است؛ رخ‌دادنش رو نمی‌شه از روی «id نامرتب» به‌تنهایی قطعی دانست، چون اندازهٔ page، occupancy، cache و الگوریتم storage دخیل‌اند.

A B+ tree consists of bounded-size pages. If an insert targets a range whose leaf has insufficient room, InnoDB may split the page and update links and navigation metadata. This preserves the ordered tree; an “out-of-order ID” alone does not prove a split, because page size, occupancy, cache, and engine behavior all matter.

درج ترتیبی و تصادفی می‌تونن الگوی pageها و locality متفاوتی بسازند، اما یک script کوتاه با چند ردیف سندِ وقوع split نیست. benchmark باید تعداد ردیف نماینده، warm-up، چند تکرار، وضعیت cache و هزینهٔ indexها رو کنترل کند.

Sequential and random inserts can produce different page and locality patterns, but a short script with a few rows is not proof that a split occurred. A benchmark needs representative row counts, warm-up, repeated runs, cache context, and index costs.

Change buffer ممکنه بخشی از کار رو عقب بیندازدThe change buffer may defer part of the work

اگه secondary-index page در buffer pool نباشه، InnoDB در شرایط پشتیبانی‌شده می‌تونه بعضی تغییرها رو در change buffer ثبت کند و بعدتر هنگام load شدن page merge کند. این سازوکار برای کاهش random I/O طراحی شده، نه حذف هزینهٔ index؛ merge بعداً هم CPU و I/O می‌خواهد. جزئیات به نوع index و شرایط نسخه وابسته هست.

If a secondary-index page is not in the buffer pool, InnoDB can, under supported conditions, record some changes in the change buffer and merge them later when the page is loaded. This is designed to reduce random I/O, not eliminate index cost; merging still consumes CPU and I/O later. Details depend on index type and version conditions.

تنظیم رو فقط بخوان؛ اینجا tuning نمی‌کنیمInspect configuration only; do not tune here
SHOW VARIABLES LIKE 'innodb_change_buffering';
SHOW GLOBAL STATUS LIKE 'Innodb_ibuf%';
SHOW ENGINE INNODB STATUS;

ممکنه متغیرها یا counterها در نسخه و workload تفاوت داشته باشند. از یک عدد ibuf به‌تنهایی میزان latency یک table یا ضرورت حذف index رو نتیجه نگیر. این فصل فقط مرز مفهومی رو می‌سازد؛ تنظیم change buffer tuning جدا می‌خواهد.

Variables and counters can vary with version and workload. One ibuf number does not establish a table’s latency or prove an index should be removed. This chapter sets the conceptual boundary; change-buffer tuning is a separate topic.

هزینه رو چطور اندازه بگیریم؟How should we measure the cost?

یک جدول قبل/بعد می‌سازد که فقط یک چیز عوض می‌کنه. همان داده، همان statementها، batch یکسان، اندازهٔ مشابه buffer pool و چند run. latency، throughput و write amplification رو از گزارش سیستم خودت ثبت کن؛ SHOW INDEX فقط ساختار رو نشان می‌ده، نه سرعت رو.

Build a before/after comparison that changes one thing at a time. Keep data, statements, batch size, and buffer-pool conditions comparable, and run several trials. Record latency, throughput, and write amplification from your system; SHOW INDEX reports structure, not speed.

قبل از حذف index از همهٔ مصرف‌کننده‌ها خبر بگیر.Check every consumer before dropping an index.

queryهای کم‌تکرار، گزارش زمان‌بندی‌شده، replicaها، ابزارهای داخلی و کلیدهای constraint رو بررسی کن. اگه هدف سنجش اثر plan است، invisible index برای آزمایش برگشت‌پذیر مناسب‌تر از DROP فوری هست.

Check infrequent queries, scheduled reports, replicas, internal tools, and constraint keys. If the goal is to test plan impact, an invisible index is a more reversible experiment than an immediate DROP.
