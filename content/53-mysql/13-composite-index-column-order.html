Composite Index و ترتیب ستون‌ها

Composite Indexes and Column Order

گزارش پشتیبانی می‌خواهد سفارش‌های یک مشتری را بر اساس وضعیت و بازهٔ زمانی پیدا کند. سه ستون در شرط دیده می‌شود؛ آیا باید سه index جدا بسازیم؟ یا یک index چندستونی؟ این بار ترتیب ستون‌ها تعیین می‌کند کدام درخواست‌ها مسیر مستقیم دارند و کدام‌ها نه.

A support report needs one customer’s orders filtered by status and a time range. Three columns appear in the predicate. Should we build three separate indexes or one multi-column index? This time, column order determines which requests have a direct path and which do not.

پیش‌نیازPrerequisite: فصل ۱۲ · B+ Tree و index پایهمحیط مرجعReference environment: MySQL 9.7 · InnoDBزمانTime: ۹۰ دقیقه · ۱۸ تمرین

سه ستون در query، اما یک ترتیب در درختThree predicate columns, one ordering in the tree

درخواست چنین است: «سفارش‌های مشتری ۱۰۱ که وضعیتشان paid است و بعد از یک تاریخ ثبت شده‌اند». query ساده به نظر می‌رسد. اما یک index مرتبِ (customer_id, status, created_at) با (status, customer_id, created_at) یکسان نیست؛ دومی هم همان سه ستون را دارد، اما ترتیب پیمایشش فرق می‌کند.

The request is: “Show paid orders for customer 101 created after a given date.” The query looks simple. But an ordered index on (customer_id, status, created_at) is not equivalent to (status, customer_id, created_at). It contains the same columns, but its traversal order differs.

بیایید workload را قبل از index تعریف کنیم. ابتدا fixture کوچک و قابل‌تکرار می‌سازیم؛ بعد هر query را جداگانه می‌نویسیم و از optimizer می‌پرسیم چه indexی را انتخاب کرده. روی چند ردیف ممکن است انتخاب‌ها برای کاهش کار مفید نباشند؛ تمرین دربارهٔ قابلیت ساختار است، نه مسابقهٔ سرعت.

Let’s define the workload before the index. We will create a small reproducible fixture, write each query separately, and ask the optimizer which index it chose. With only a few rows, choices may not reduce work. This is about structural capability, not a speed contest.

ساخت دادهٔ آزمایش و دو ترتیب indexCreate the fixture and two index orders

دو index موازی را برای مقایسه ساخته‌ایم؛ در یک سیستم واقعی معمولاً بدون دلیل هر دو را نگه نمی‌داریم، چون هرکدام storage و هزینهٔ نوشتن دارند. پس از آزمایش نتیجه می‌گیریم کدام workload واقعاً نیازمند کدام ترتیب است.

We created two parallel indexes for comparison. In a real system, we would not keep both without justification because each adds storage and write cost. We will use the experiments to decide which workload genuinely needs which order.

قانون سرنخ: از چپِ index شروع کنThe clue: start from the index’s left edge

index را مثل واژه‌نامه‌ای مرتب با کلید ترکیبی تصور کن: اول بر اساس ستون اول، داخل مقدار برابر بر اساس ستون دوم، و سپس بر اساس ستون سوم. اگر ستون اول معلوم نباشد، یک مقدار از ستون دوم در کل درخت لزوماً در یک بازهٔ پیوسته نیست. برای همین leftmost prefix مهم است.

Think of the index as a dictionary ordered by a compound key: first by column one, then within equal values by column two, and then by column three. Without the first column, a value from column two is not necessarily one contiguous range in the whole tree. That is why the leftmost prefix matters.

این قاعده را با زبان دقیق نگه داریم: optimizer می‌تواند از leftmost prefix برای lookup استفاده کند. روی شرط غیر-prefix، ممکن است scan یا روش دیگری انتخاب شود؛ پس نگوییم «هیچ‌وقت index استفاده نمی‌شود» و از یک plan کوچک هم قانون کلی استخراج نکنیم.

Keep the rule precise: the optimizer can use a leftmost prefix for lookup. For a non-prefix predicate, it may scan or use another strategy. Avoid saying an index is “never used,” and do not derive a universal rule from one tiny-table plan.

Equality قبل از range؛ بعد از range انتظار متفاوتEquality before a range; expectations change after it

در query مشتری و وضعیت، هر دو مقدار equality مشخص دارند و تاریخ یک range است. ترتیب (customer_id, status, created_at) اجازه می‌دهد ابتدا محدودهٔ مشتری، بعد status، و درون همان بخش بازهٔ تاریخ را پیدا کنیم. اگر شرط تاریخ range شد، استفاده از ستون‌های بعدی برای محدودکردن lookup به همان شکل ساده نیست؛ جزئیات plan را باید بررسی کرد.

The customer and status predicates are equalities, while date is a range. The order (customer_id, status, created_at) lets the engine narrow by customer, then status, then scan the date range within that section. Once a range is encountered, later columns do not narrow the lookup in the same straightforward way; inspect the actual plan.

query موردنیاز تیم پشتیبانیThe support team’s query
EXPLAIN SELECT order_id, total
FROM orders_lab
WHERE customer_id=101
  AND status='paid'
  AND created_at >= '2026-02-01'
ORDER BY created_at;

SELECT order_id, total
FROM orders_lab
WHERE customer_id=101
  AND status='paid'
  AND created_at >= '2026-02-01'
ORDER BY created_at;

جواب باید سفارش‌های ۳ و ۷ را بدهد، مرتب‌شده بر اساس زمان. EXPLAIN ممکن است هرکدام از دو index را انتخاب کند یا با توجه به حجم کم scan کند. اگر این query هدف اصلی است، index متناظر را باید در مقیاس و workload واقعی ارزیابی کنیم.

The result should contain orders 3 and 7, ordered by time. EXPLAIN may choose either index or scan the tiny table. If this is the primary workload, evaluate the matching index at realistic scale and with the real workload.

وقتی شرط اولِ index حذف می‌شودRemove the index’s first predicate
EXPLAIN SELECT order_id
FROM orders_lab
WHERE status='paid';

EXPLAIN SELECT order_id
FROM orders_lab
WHERE customer_id=101 AND created_at >= '2026-02-01';

query اول از ستون دوم index اول شروع می‌کند و left-prefix ندارد. query دوم ستون اول را دارد ولی ستون میانی status را جا انداخته؛ ستون سوم همچنان به همان شکل یک بازهٔ پیوستهٔ کامل با customer نمی‌سازد. index دوم وضعیت دیگری دارد. ستون‌ها باید بر اساس queryهای واقعی و ترتیب شرط‌های قابل‌استفاده چیده شوند، نه صرفاً بر اساس «مهم‌ترین ستون».

The first query starts at the second column of the first index and has no left prefix. The second has the first column but skips the middle status column; the third column does not form the same straightforward contiguous range with customer. The second index has a different ordering. Choose order from real query patterns, not merely from the “most important column.”

دو ترتیب، دو خانوادهٔ queryTwo orders, two query families

برای درخواست «همهٔ سفارش‌های paid در کل فروشگاه» ترتیب (status, customer_id, created_at) نقطهٔ شروع مستقیم‌تری دارد. برای «سفارش‌های یک customer در statusهای مختلف» ترتیب customer-first مناسب‌تر است. یک index نمی‌تواند برای هر workload بهترین باشد؛ و indexهای متعدد، هزینهٔ نگهداری را جمع می‌کنند.

For “all paid orders across the store,” (status, customer_id, created_at) provides a more direct starting prefix. For “all statuses for one customer,” customer-first is a more natural fit. One index cannot be best for every workload, and multiple indexes accumulate maintenance cost.

توجه: equalityهای همهٔ ستون‌ها در بعضی queryها می‌توانند باعث شوند هر دو ترتیب گزینه باشند. اما برای queryهایی که فقط بخشی از ستون‌ها را دارند، جایگاه چپ تعیین‌کننده می‌شود. انتخاب نهایی را با ماتریس queryهای پرتکرار، selectivity، ترتیب لازم و هزینهٔ write انجام بده؛ فصل بعد selectivity و covering را جداگانه باز می‌کند.

When a query has equality predicates for every indexed column, both orders can be candidates. But for queries using only a subset, left position matters. Choose from frequent query patterns, selectivity, required ordering, and write cost; the next chapter examines selectivity and covering separately.

ستون index و ORDER BYIndex columns and ORDER BY

ترتیب index ممکن است برای filter و sort با هم مفید باشد. برای نمونه، پس از ثابت‌کردن customer و status، خواندن تاریخ‌ها به ترتیب طبیعی index ممکن است sort جداگانه را غیرضروری کند. اما اگر query ترتیب نامرتبطی بخواهد یا ستون‌های لازم را جا بیندازد، optimizer ممکن است filesort انجام دهد. نام filesort به‌تنهایی به معنی نوشتن حتمی روی دیسک نیست.

Index order may help both filtering and sorting. After fixing customer and status, dates in index order may avoid a separate sort. But an unrelated order or skipped columns may require filesort. The term filesort alone does not mean a disk write is guaranteed.

یک ترتیبِ مطابق با query و یک ترتیب متفاوتA matching order and a different one
EXPLAIN SELECT order_id, created_at
FROM orders_lab
WHERE customer_id=101 AND status='paid'
ORDER BY created_at;

EXPLAIN SELECT order_id, created_at
FROM orders_lab
WHERE customer_id=101 AND status='paid'
ORDER BY total;

در ستون Extra و بخش‌های plan به نشانه‌های sort توجه کن؛ جزئیات خروجی نسخه‌محور است. query اول با ترتیب index سازگارتر است. دومی ترتیب total می‌خواهد که در این دو index نیست. برای نتیجهٔ درست همیشه ORDER BY صریح را نگه دار، حتی اگر index امروز ترتیب را فراهم کند.

Inspect Extra and plan details for sort indicators; output varies by version. The first query aligns more closely with index order. The second orders by total, absent from these indexes. Keep ORDER BY explicit for correctness even if an index currently supplies that order.

ترتیب را از ماتریس workload بیرون بکشDerive order from the workload matrix

پیش از ساخت index، چند query پرتکرار را روی یک برگه جمع کن. برای هرکدام مشخص کن equality کدام است، range کدام است، sort چه می‌خواهد و چند ردیف معمولاً برمی‌گردد. indexی را انتخاب کن که بیشترین کار مهم را پوشش دهد، نه آنکه صرفاً ستون‌ها را کنار هم فهرست کند.

Before building an index, list frequent queries. For each, mark equality predicates, ranges, required ordering, and typical result size. Choose an index that supports the important work, rather than merely listing columns together.

These outputs connect schema, data, and plan. A plan on a tiny fixture is useful for learning estimated rows; a real decision also needs table size, value distribution, and write load.

سه برداشت وسوسه‌انگیز اما نادقیقThree tempting but inaccurate conclusions

«ستون کم‌تکرار باید اول باشد»

“The least repetitive column must come first”

selectivity مهم است، اما جای prefixهای پرتکرار، sort، range و هزینهٔ نوشتن را نمی‌گیرد. query workload تعیین می‌کند کدام ترتیب مفید است.

Selectivity matters, but it does not replace prefix patterns, sorting, ranges, and write cost. The workload determines which order is useful.

«شرط‌ها را هر جور بنویسم index ترتیبش را نادیده می‌گیرد»

“Predicate text order makes index order irrelevant”

نوشتن WHERE status='paid' AND customer_id=101 یا جابه‌جایی متن شرط‌ها معمولاً مفهوم منطقی را عوض نمی‌کند؛ ترتیب ستون‌های index همچنان ساختار مرتب را تعیین می‌کند.

Writing the predicates in a different textual order usually does not change their logic; index column order still defines the ordered structure.

«چون هر دو ستون index دارند، composite لازم نیست»

“Both columns have indexes, so a composite one is unnecessary”

optimizer ممکن است Index Merge یا یک index منفرد را انتخاب کند. این مسیر الزاماً معادل یک composite index برای فیلتر هم‌زمان و ترتیب خروجی نیست؛ plan واقعی را مقایسه کن.

The optimizer may use Index Merge or one single-column index. That is not necessarily equivalent to a composite index for combined filtering and output order; compare real plans.

WHERE customer_id=102 AND status='paid'
AND created_at >= '2026-02-01';

ترتیب customer/status/date در fixture موجود است. index تکراری نساز؛ اگر plan scan نشان داد، اندازهٔ کم جدول را هم در تفسیر وارد کن.

The fixture already has customer/status/date order. Do not add a duplicate index; if the plan scans, account for the tiny table size.

۱۲) sort را با شرط‌های ثابت هماهنگ کن / Align sorting after fixed predicates

سفارش‌های customer/status را بر اساس created_at مرتب کن و سپس plan را بررسی کن.

Order a customer/status result by created_at and inspect its plan.

SQL / SQL
EXPLAIN SELECT order_id, created_at FROM orders_lab
WHERE customer_id=101 AND status='paid'
ORDER BY created_at;

پس از ثابت‌کردن دو ستون اول، تاریخ با ترتیب سوم هم‌راستا است. plan کوچک جدول همچنان معیار performance نیست.

After fixing the first two columns, date aligns with the third key. A tiny-table plan is still not a performance measure.

۱۳) sort نامنطبق را پیدا کن / Find a mismatched sort

همان فیلتر را بر اساس total مرتب کن و plan را کنار query قبلی بگذار.

Use the same filter but order by total; compare its plan with the prior query.

SQL / SQL
EXPLAIN SELECT order_id, total FROM orders_lab
WHERE customer_id=101 AND status='paid'
ORDER BY total;

total در indexهای موجود نیست؛ احتمال sort جدا وجود دارد. ORDER BY را برای correctness حفظ کن.

Total is absent from these indexes, so a separate sort may be needed. Keep ORDER BY for correctness.

۱۴) خروجی واقعی را از plan جدا نگه دار / Separate output from plan

همان query status-first را یک بار EXPLAIN و یک بار اجرا کن؛ هر دو مدرک را ثبت کن.

Explain and execute the same status-first query; record both kinds of evidence.

SQL / SQL
EXPLAIN SELECT order_id FROM orders_lab WHERE status='paid';
SELECT order_id FROM orders_lab WHERE status='paid';

اولی برآورد مسیر، دومی ردیف‌های واقعی را نشان می‌دهد. هیچ‌کدام به‌تنهایی زمان پاسخ production را ثابت نمی‌کند.

The first gives a planned path; the second returns actual rows. Neither alone proves production latency.

۱۵) هزینهٔ دو index را در metadata بشمار / Count the index obligations

همهٔ indexها را ثبت کن و نام هر indexی را که insert/update باید حفظ کند فهرست کن.

Record all indexes and list which structures inserts/updates must maintain.

SQL / SQL
SHOW INDEX FROM orders_lab;

کلید اصلی و هر دو composite index باید با تغییر ردیف سازگار بمانند. metadata اندازهٔ write amplification یا latency را نشان نمی‌دهد.

The primary key and both composite indexes must remain consistent after row changes. Metadata does not quantify write amplification or latency.

۱۶) یک query جاافتاده طراحی کن / Design for a missing query

نیاز «همهٔ سفارش‌های customer=103، هر status، تازه‌ترین ابتدا» را به query تبدیل کن و index فعلی مناسب را با SHOW INDEX پیدا کن.

Turn “all orders for customer 103, any status, newest first” into SQL and identify a suitable current index.

SQL / SQL
SHOW INDEX FROM orders_lab;
SELECT order_id, status, created_at FROM orders_lab
WHERE customer_id=103
ORDER BY created_at DESC;

customer-first prefix دارد، ولی status در میانهٔ index اول است و در query ثابت نشده؛ بررسی sort و range لازم است. نام index به‌تنهایی تضمین سازگاری کامل نیست.

Customer-first supplies a prefix, but status is an unfixed middle column in the first index; evaluate range and sort behavior. The index name alone does not guarantee a perfect fit.

۱۷) مجبورکردن optimizer را راه‌حل نکن / Do not make forcing the optimizer the fix

دو query با indexهای موجود explain کن و یک دلیل قابل‌آزمایش برای انتخاب scan احتمالی بنویس.

Explain two queries with existing indexes and state a testable reason for a possible scan.

SQL / SQL
EXPLAIN SELECT order_id FROM orders_lab WHERE customer_id=101;
EXPLAIN SELECT order_id FROM orders_lab WHERE status='paid';

داده کم است و scan ارزان برآورد می‌شود؛ اول حجم و توزیع نماینده و آمار را فراهم کن، نه اینکه فوراً FORCE INDEX بزنی.

The dataset is tiny and a scan may be estimated cheaper. Start with representative scale, distribution, and statistics, not an immediate FORCE INDEX.

۱۸) تصمیم index را با query اثبات کن / Prove an index decision with queries

دو query پرتکرار فرضی را اجرا کن، ترتیب index مناسب هرکدام را از SHOW INDEX نشان بده و محدودیت مدرکت را بنویس.

Run two representative queries, show the matching index orders, and state the evidence limit.

SQL / SQL
SHOW INDEX FROM orders_lab;
EXPLAIN SELECT order_id FROM orders_lab
WHERE customer_id=101 AND status='paid';
EXPLAIN SELECT order_id FROM orders_lab
WHERE status='paid' AND customer_id=101;

هر دو شرط equality دارند و هر دو index ممکن است گزینه باشند؛ برای subsetها prefixها فرق می‌کنند. plan و benchmark روی workload لازم است تا انتخاب را توجیه کنیم.

Both predicates are equalities, so both index orders may be candidates; subsets have different prefixes. Plans and workload benchmarks are still needed to justify a choice.

آزمایش پایانی: به‌جای سه index تصادفی، workload را مدل کنClosing lab: model the workload instead of adding three arbitrary indexes

یک تیم با سه endpoint کار می‌کند: صفحهٔ customer، صف status، و گزارش customer/status/date. قرار نیست برای هر ستون یک index جداگانه بسازی. queryهای سه endpoint را بنویس، indexهای موجود را ببین، سپس تصمیم بگیر کدام composite indexها لازم‌اند و چه هزینه‌ای می‌آورند.

A team has three endpoints: a customer page, a status queue, and a customer/status/date report. You are not asked to add one index per column. Write the three queries, inspect existing indexes, then decide which composite indexes are justified and what they cost.

  1. queryها را با filter، range، sort و projection جدا ثبت کن.
  2. Record each query’s filters, range, sort, and projection separately.
  3. leftmost prefixهای هر index را از SHOW INDEX استخراج کن.
  4. Derive each index’s leftmost prefixes from SHOW INDEX.
  5. EXPLAIN و نتیجهٔ واقعی را کنار هم بگذار؛ scan روی fixture را باگ تلقی نکن.
  6. Compare EXPLAIN with actual rows; do not label a fixture scan a bug.
  7. اگر index تازه پیشنهاد می‌دهی، queryی را که بهتر پشتیبانی می‌شود و هزینهٔ write را مشخص کن.
  8. If proposing an index, name the query it supports better and the write cost it adds.

معیار تحویل، indexهای بیشتر نیست؛ توضیح قابل‌بررسی از ارتباط query، ترتیب ستون‌ها و شواهد است. فصل بعد کمک می‌کند selectivity و covering را هم وارد همین تصمیم کنیم.

Success is not “more indexes”; it is a reviewable explanation connecting query patterns, column order, and evidence. The next chapter adds selectivity and covering to that decision.
