قیمت سه کالا عوض شد؛ چطور رد هر سه تغییر رو نگه داریم؟

Three prices changed; how do we record every change?

در فصل قبل Function رو وقتی انتخاب کردیم که خود query یک مقدار می‌خواست. حالا یک نیاز متفاوت داریم: هر بار قیمت واقعاً تغییر کرد، یک ردیف audit هم ثبت بشه؛ حتی اگه یک UPDATE چند کالا رو با هم عوض کند. Trigger با رخداد ردیف فعال می‌شه، اما چون پنهان و خودکار هست باید بفهمیم دقیقاً کِی اجرا می‌شه و اثرش چه‌طور با statement اصلی همراه می‌مونه.

In the previous chapter, we used a function when the query needed a value. Now we have a different requirement: whenever a price changes, record an audit row—even when one UPDATE changes several products. A trigger activates on row events, but because it is automatic and hidden, we must understand exactly when it runs and how its effects relate to the original statement.

یک statement، چند ردیف، چند ردپاOne statement, many rows, many audit records

کسی قیمت دو کالا رو در یک statement تغییر می‌ده. اگه برنامه فقط بعد از UPDATE یک audit دستی بنویسد، ممکنه تعداد ردیف‌ها رو اشتباه ثبت کند یا بخشی از رخدادها رو از قلم بیندازد. اگه logic رو در Trigger بگذاریم، database به‌ازای هر ردیفی که عملیاتش رخ می‌ده Trigger رو اجرا می‌کنه. اول پیش‌بینی کنیم: UPDATE دو ردیف، چند audit row می‌سازد؟

Someone changes two product prices in one statement. If the application writes one manual audit record afterward, it may record the wrong count or omit some changes. If the logic lives in a trigger, the database runs it for every row operation. Predict first: how many audit rows should an UPDATE of two rows produce?

یک UPDATE می‌تونه چند ردیف بسازد؛ Trigger در این مدل برای هر row اجرا می‌شه و OLD/NEW همان ردیف رو می‌بیند.

One UPDATE can affect many rows; in this model, the trigger runs once per row and sees that row’s OLD and NEW values.

Trigger جایگزین audit دستی برنامه نیست مگر تصمیم گرفته باشیم این مسئولیت واقعاً در database باشه. Trigger ردپا رو نزدیک به داده نگه می‌دارد، اما رفتار رو از روی متن UPDATE پنهان می‌کنه؛ هرکس جدول رو تغییر دهد همان اثر رو فعال می‌کنه.

A trigger is not automatically a replacement for application-level auditing; we must deliberately choose to own this responsibility in the database. It keeps the audit close to the data, but hides behavior from the UPDATE text: whoever changes the table activates it.

جدول قیمت و audit رو در schema تمرینی آماده کنPrepare product prices and an audit table in the lab schema

از fixture فصل ۳۲ استفاده می‌کنیم؛ اگه آن رو نداری، setup زیر جدول‌ها و سه قیمت معلوم رو می‌سازد. audit table فقط مقدار قبلی، مقدار تازه و زمان ثبت رو نگه می‌دارد تا بتوانیم شمار ردیف‌های واقعی رو مقایسه کنیم.

We reuse Chapter 32’s fixture; if it is missing, this setup creates the tables and three known prices. The audit table stores only the old value, new value, and timestamp so we can compare the number of actual row changes.

فقط روی schema تمرینی کار کنWork only in the lab schema

داده‌های این فصل با codenames_deadlock_lab محدود شده‌اند. جدول audit رو پیش از تست خالی می‌کنیم؛ پیش از هر DELETE نام database و table رو بررسی کن و این دستورها رو روی دادهٔ واقعی اجرا نکن.

This chapter is scoped to codenames_deadlock_lab. We clear the audit table before tests; verify the database and table names before any DELETE, and never run these commands on real data.

baseline رو از خود جدول بخوانRead the baseline from the table
USE codenames_deadlock_lab;
CREATE TABLE IF NOT EXISTS product_price (
  product_id INT PRIMARY KEY,
  product_name VARCHAR(40) NOT NULL,
  base_price DECIMAL(10,2) NOT NULL CHECK (base_price >= 0)
) ENGINE=InnoDB;
CREATE TABLE IF NOT EXISTS price_audit (
  audit_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  product_id INT NOT NULL,
  old_price DECIMAL(10,2) NOT NULL,
  new_price DECIMAL(10,2) NOT NULL,
  changed_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;
INSERT INTO product_price VALUES
  (1,'Notebook',120.00),(2,'Keyboard',80.00),(3,'Lamp',45.50)
ON DUPLICATE KEY UPDATE
  product_name=VALUES(product_name),base_price=VALUES(base_price);
SELECT product_id,product_name,base_price
FROM product_price ORDER BY product_id;

سه قیمت باید ۱۲۰، ۸۰ و ۴۵٫۵۰ باشند. این «baseline» از مقدارهای فعلی میاد، نه از حدس ما؛ اگه قیمت‌ها فرق دارن، قبل از وصل‌کردن Trigger آن‌ها رو آگاهانه به fixture برگردان.

The three prices should be 120, 80, and 45.50. This baseline comes from current values, not our assumptions; if they differ, deliberately reset the fixture before adding the trigger.

BEFORE یا AFTER؟ INSERT، UPDATE یا DELETE؟BEFORE or AFTER? INSERT, UPDATE, or DELETE?

Trigger به table وصل هست و زمان و رخدادش رو باهم انتخاب می‌کنیم. BEFORE UPDATE وقتی مناسب هست که می‌خوایم مقدار ردیف تازه رو از طریق NEW تغییر بدهیم؛ AFTER UPDATE برای ثبت audit مناسب‌تر است، چون تغییر ردیف موفق شده و OLD و NEW رو کنار هم می‌بینیم.

A trigger belongs to a table and has both a timing and an event. BEFORE UPDATE is useful when we need to change the incoming NEW value. AFTER UPDATE is a better fit for this audit example because the row operation succeeded and we can record OLD and NEW together.

AFTER به معنی اجرای بعد از COMMIT نیست؛ یعنی بعد از عملیات همان ردیف، ولی هنوز داخل statement و transaction فراخواننده. برای جدول‌های InnoDB، audit row و تغییر قیمت می‌تونن با هم commit یا rollback شوند.

AFTER does not mean “after COMMIT.” It means after that row operation, but still inside the invoking statement and transaction. With InnoDB tables, the audit row and price update can commit or roll back together.

Trigger رو بساز و پیش‌بینی‌مان رو آزمایش کنCreate the trigger and test our prediction

هر بار قیمت تغییر کرد، یک رویداد با OLD و NEW ثبت می‌کنیم. شرط OLD.base_price <> NEW.base_price کمک می‌کنه UPDATEهایی که مقدار قیمت رو واقعاً عوض نکرده‌اند audit اضافی نسازند. این شرط دربارهٔ price است، نه هر تغییری در نام کالا.

Whenever a price changes, we record one event using OLD and NEW. The OLD.base_price <> NEW.base_price condition avoids an extra audit entry when an UPDATE does not actually change the price. The condition tracks price, not name changes.

Trigger چند statementی رو در mysql CLI تعریف کنDefine the multi-statement trigger in the mysql CLI
USE codenames_deadlock_lab;
DROP TRIGGER IF EXISTS trg_product_price_audit;
DELIMITER //
CREATE TRIGGER trg_product_price_audit
AFTER UPDATE ON product_price
FOR EACH ROW
BEGIN
  IF OLD.base_price <> NEW.base_price THEN
    INSERT INTO price_audit(product_id,old_price,new_price)
    VALUES (OLD.product_id,OLD.base_price,NEW.base_price);
  END IF;
END//
DELIMITER ;

DELIMITER فرمان client است، همان‌طور که در Stored Procedure دیدیم. Trigger چند statement داخلی دارد، پس mysql CLI نباید در اولین ; تعریف رو قطع کند. در ابزار migration دیگر، روش فرستادن کل CREATE رو مطابق همان ابزار تنظیم کن.

As with stored procedures, DELIMITER is a client command. This trigger has several internal statements, so the mysql CLI must not split the CREATE at the first semicolon. With another migration tool, submit the complete CREATE using that tool’s mechanism.

audit رو خالی کن، بعد دو قیمت رو در یک statement عوض کنClear the audit, then change two prices in one statement
DELETE FROM price_audit;
UPDATE product_price
SET base_price=base_price+5
WHERE product_id IN (1,2);
SELECT product_id,old_price,new_price
FROM price_audit ORDER BY audit_id;

باید دو audit row ببینی: ۱۲۰ به ۱۲۵ و ۸۰ به ۸۵. این خروجی شواهدی هست که Trigger برای هر row تغییرکرده اجرا شده؛ تعداد statementها رو نشمرده. اگه یک ردیف دیدی، شرط WHERE یا baseline رو بخوان؛ اگه هیچ‌کدام نیامد، Trigger و schema فعال رو بررسی کن.

Expect two audit rows: 120 to 125 and 80 to 85. This evidence shows the trigger ran for each changed row, not once per SQL statement. If you see one row, inspect the predicate and baseline; if none appear, verify the trigger and active schema.

OLD و NEW فقط برای رخداد مناسب معنا دارنOLD and NEW depend on the triggering event

در UPDATE می‌تونیم مقدار پیش از تغییر رو با OLD و مقدار پس از آن رو با NEW بخوانیم. در INSERT فقط NEW وجود دارد؛ در DELETE فقط OLD. OLD فقط خواندنی هست. در BEFORE می‌تونیم بعضی ستون‌های NEW رو با SET تغییر بدهیم؛ در AFTER دیگر ردیف ذخیره شده و این assignment اثری ندارد.

For UPDATE, OLD refers to the value before the change and NEW to the value afterward. INSERT has only NEW; DELETE has only OLD. OLD is read-only. In BEFORE, we can assign certain NEW columns with SET; in AFTER, the row is already stored, so such an assignment has no effect.

یک BEFORE UPDATE نام رو trim می‌کنه؛ بعد مقدار ذخیره‌شده رو بخوانA BEFORE UPDATE trims the name; then inspect the stored value
DROP TRIGGER IF EXISTS trg_product_name_trim;
DELIMITER //
CREATE TRIGGER trg_product_name_trim
BEFORE UPDATE ON product_price
FOR EACH ROW
SET NEW.product_name=TRIM(NEW.product_name)//
DELIMITER ;
UPDATE product_price SET product_name='  Notebook  '
WHERE product_id=1;
SELECT product_name,LENGTH(product_name)
FROM product_price WHERE product_id=1;

نام باید بدون فاصلهٔ ابتدا و انتها ذخیره بشه. بعد از دیدن نتیجه نام fixture رو برگردان. این فقط نشان می‌ده BEFORE می‌تونه NEW رو تغییر بده؛ برای پاک‌سازی ورودی معمولاً بهتر هست client و constraint هم قرارداد رو روشن کنند، نه این‌که همه‌چیز پنهان بماند.

The stored name should have no leading or trailing spaces. Restore the fixture name after inspecting it. This demonstrates that BEFORE can modify NEW; input cleanup should still be explicit in clients and constraints where possible, rather than hidden entirely in a trigger.

آیا audit هم با UPDATE rollback می‌شه؟Does the audit row roll back with the UPDATE?

هر دو جدول InnoDB هستن و Trigger ردیف audit رو در همان transaction ایجاد می‌کنه. پس می‌تونیم statement رو اجرا کنیم، هنوز COMMIT نکنیم، audit رو از همان session ببینیم و بعد ROLLBACK کنیم. پیش‌بینی: بعد از rollback چه مقدار در جدول قیمت و audit می‌مونه؟

Both tables use InnoDB, and the trigger inserts audit data into the same transaction. We can update a row, inspect the audit in that session before commit, and then roll back. Predict: after rollback, what remains in the price table and audit table?

یک update رو شروع کن و عمداً rollback کنUpdate one row, then deliberately roll back
START TRANSACTION;
UPDATE product_price SET base_price=base_price+7
WHERE product_id=3;
SELECT base_price FROM product_price WHERE product_id=3;
SELECT old_price,new_price FROM price_audit
WHERE product_id=3 ORDER BY audit_id DESC LIMIT 1;
ROLLBACK;
SELECT base_price FROM product_price WHERE product_id=3;
SELECT COUNT(*) AS audit_rows_for_product
FROM price_audit WHERE product_id=3;

داخل transaction، قیمت تازه و audit تازه رو می‌بینی؛ بعد از ROLLBACK قیمت باید به ۴۵٫۵۰ برگردد و audit row این تغییر هم نباید باقی بماند. اگه table غیرتراکنشی بود، rollback چنین تضمینی نمی‌داد؛ به همین دلیل هر دو engine رو verify کن.

Inside the transaction, you should see the new price and its audit entry. After ROLLBACK, the price returns to 45.50 and the audit row for that change should disappear. A nontransactional table would not provide this rollback guarantee, so verify both engines.

engine دو جدول رو بررسی کنVerify both table engines
SELECT TABLE_NAME,ENGINE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA='codenames_deadlock_lab'
  AND TABLE_NAME IN ('product_price','price_audit');

هر دو باید InnoDB باشند. موفقیت همین آزمایش rollback رو برای این دو جدول ثابت می‌کنه؛ این خروجی دربارهٔ جدول‌های دیگری که Trigger شاید به آن‌ها بنویسد چیزی نمی‌گه.

Both should be InnoDB. This experiment verifies rollback for these two tables; it says nothing about other tables a different trigger might write.

یک UPDATE چندردیفی، چه چیزی رو می‌شمارد؟What does a multi-row UPDATE count?

FOR EACH ROW یعنی body برای هر ردیفِ متاثر اجرا می‌شه. پس audit table در مثال ما شمار تغییرهای price رو می‌ده، نه شمار statementها. شرط‌های UPDATE هم مهم‌اند: اگه WHERE هیچ ردیفی رو هدف نگیرد، نباید انتظار audit row داشته باشیم.

FOR EACH ROW means the body runs once for each affected row. Our audit table therefore counts price changes, not SQL statements. The UPDATE predicate matters: if WHERE matches no rows, no audit row should be expected.

سه ردیف رو عوض کن و شمارش رو با ردیف‌های اصلی تطبیق بدهChange three rows and compare audit count with source rows
DELETE FROM price_audit;
UPDATE product_price SET base_price=base_price+1
WHERE product_id IN (1,2,3);
SELECT COUNT(*) AS audit_count,COUNT(DISTINCT product_id) AS products
FROM price_audit;
SELECT product_id,old_price,new_price
FROM price_audit ORDER BY product_id;

انتظار سه audit row و سه product یکتا داریم. اگه مقدار قیمت رو عمداً برابر همان مقدار بگذاری، شرط Trigger audit نمی‌سازد؛ این قرارداد این فصل هست. اگه تغییر نام رو هم باید audit کنیم، شرط و ستون‌های audit رو گسترش بده یا event دیگری طراحی کن.

Expect three audit rows and three distinct products. If you deliberately assign the same price, the trigger condition creates no audit record; that is this chapter’s contract. If name changes also need auditing, extend the condition and audit columns or design another event.

اگه Trigger وسط multi-row statement خطا بده چه؟What if a trigger fails midway through a multi-row statement?

Trigger مخفی نباید باعث شود statement نیمه‌موفق رو بدون بررسی فرض کنیم. روی جدول‌های InnoDB، خطای Trigger statement رو fail می‌کنه و تغییرهای همان statement rollback می‌شوند. یک آزمایش کنترل‌شده می‌سازیم: Trigger دوم روی INSERT audit رو عمداً برای یک قیمت نامعتبر رد می‌کنه؛ سپس update چندردیفی رو اجرا و هر دو جدول رو بررسی می‌کنیم.

Hidden trigger logic must not make us assume a statement partially succeeded without checking. With InnoDB tables, a trigger error fails the statement and rolls back that statement’s changes. We will create a controlled experiment: a second trigger rejects an audit insert for an invalid price, then we inspect both tables after a multi-row update.

Trigger خطا رو از همان statement بیرون می‌دهThe trigger error reaches the invoking statement

آزمایش فقط در schema تمرینی انجام می‌شه و trigger آزمایشی بعدش حذف می‌کنیم. اگه client خروجی error داد، همان خطا رو نگه دار؛ برای verify از connection تازه SELECT بگیر تا مطمئن شوی rollback انجام شده.

Run this only in the lab schema and remove the temporary trigger afterward. Preserve the client error; verify the rollback with SELECT from a fresh connection.

خطای آزمایشی رو بسازCreate a deliberate test failure
DELIMITER //
CREATE TRIGGER trg_reject_bad_audit
BEFORE INSERT ON price_audit
FOR EACH ROW
BEGIN
  IF NEW.new_price > 126.00 THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='lab audit limit';
  END IF;
END//
DELIMITER ;
UPDATE product_price SET base_price=base_price+10
WHERE product_id IN (1,2,3);

حداقل یک ردیف از شرط ۱۲۶ عبور می‌کنه و statement خطا می‌ده. بعد از خطا، قیمت‌ها و شمار audit رو با connection تازه بخوان؛ همهٔ اثر همین UPDATE باید برگشته باشه. اگه فقط بخشی باقی مانده، engine جدول‌ها رو بررسی کن و نتیجه رو به MyISAM یا table دیگری تعمیم نده.

At least one row crosses the 126 threshold, so the statement should fail. After the error, read prices and audit count from a fresh connection; all effects of that UPDATE should be rolled back. If anything remains, inspect the table engines and do not generalize the result to MyISAM or other tables.

Trigger آزمایشی رو حذف و fixture رو بررسی کنRemove the failing trigger and inspect the fixture
DROP TRIGGER IF EXISTS trg_reject_bad_audit;
SELECT product_id,base_price FROM product_price ORDER BY product_id;
SELECT COUNT(*) AS audit_count FROM price_audit;

Trigger چه کارهایی نمی‌کنه؟What triggers do not do

Trigger رو با برنامهٔ زمان‌بندی یا event scheduler اشتباه نگیر؛ فقط در واکنش به INSERT/UPDATE/DELETE ردیف فعال می‌شه. TRUNCATE TABLE مثل DELETE ردیف‌به‌ردیف نیست و Trigger حذف رو اجرا نمی‌کنه. اقدام‌های cascade مربوط به foreign key نیز به‌طور پیش‌فرض Triggerهای child رو فعال نمی‌کنن.

Do not confuse a trigger with a scheduler or event. It activates in response to row operations such as INSERT, UPDATE, and DELETE. TRUNCATE TABLE is not a row-by-row DELETE and does not fire DELETE triggers. Cascaded foreign-key actions also do not activate child triggers by default.

Trigger نمی‌تونه transaction مستقل رو start یا commit کند. اگه statement اصلی rollback شود، side effect روی جدول InnoDB هم rollback می‌شه. برای external side effect مثل HTTP یا ارسال ایمیل از Trigger استفاده نکن؛ این side effect با transaction پایگاه‌داده اتمیک نیست و معمولاً باید از outbox یا لایهٔ برنامه بهره گرفت.

A trigger cannot start or commit an independent transaction. If the invoking statement rolls back, its InnoDB side effects roll back too. Do not use a trigger for external effects such as HTTP or email; those effects are not atomic with the database transaction and usually belong in an outbox or application layer.

constraint رو پیش از Trigger بررسی کنConsider a constraint before a trigger

اگه شرطی مثل «قیمت منفی نباشه» است، CHECK constraint روشن‌تر و قابل‌دیدن‌تر از Trigger مخفی هست. Trigger رو برای کاری نگه دار که واقعاً به رخداد ردیف و OLD/NEW نیاز دارد، مثل ثبت snapshot قیمت.

For a rule such as “price cannot be negative,” a CHECK constraint is clearer and more visible than a hidden trigger. Reserve triggers for work that genuinely needs a row event and OLD/NEW values, such as recording a price snapshot.

تعریف Trigger رو هم از server بخوانRead the trigger definition from the server

مثل Procedure و Function، فایل migration تنها مدرک نیست. تعریف موجود رو با SHOW CREATE TRIGGER یا INFORMATION_SCHEMA ببین. اگه Trigger اجرا نمی‌شه، schema/table، event، timing، enabled definer privilege و شرط بدنه رو یکی‌یکی بررسی کن.

As with procedures and functions, the migration file is not the only evidence. Inspect the stored definition with SHOW CREATE TRIGGER or INFORMATION_SCHEMA. If it does not fire, check schema/table, event, timing, definer privileges, and the body condition one at a time.

تعریف و metadata رو verify کنVerify the definition and metadata
SHOW CREATE TRIGGER codenames_deadlock_lab.trg_product_price_audit\G
SELECT TRIGGER_NAME,EVENT_MANIPULATION,ACTION_TIMING,
       EVENT_OBJECT_TABLE,DEFINER
FROM information_schema.TRIGGERS
WHERE TRIGGER_SCHEMA='codenames_deadlock_lab';

metadata نشان می‌ده server چه چیزی ثبت کرده؛ خروجی آن ثابت نمی‌کنه Trigger برای query خاصی واقعاً شرطش رو پاس کرده. برای آن، یک تغییر کنترل‌شده اجرا کن و OLD/NEW ثبت‌شده رو با مقدار جدول تطبیق بده.

Metadata shows what the server stored; it does not prove the trigger’s condition passed for a particular query. For that, run a controlled change and compare the recorded OLD/NEW values with the table.

وقتی تغییر باید در زمانی مشخص اجرا بشهWhen work must run at a scheduled time

Trigger برای رخداد ردیف است، نه برای کاری که باید هر شب یا هر ساعت اجرا بشه. اگه عملیات زمان‌بندی‌شده می‌خوایم، سراغ Event Scheduler می‌ریم؛ اما قبلش باید مرز زمان server، فعال‌بودن scheduler و مدرک اجرای event رو بشناسیم. فصل بعد از همین سؤال شروع می‌کنه.

A trigger responds to row events, not to work that must run nightly or hourly. For scheduled work, we turn to the Event Scheduler—but first we need to understand server time, scheduler state, and evidence that an event ran. That is where the next chapter begins.
