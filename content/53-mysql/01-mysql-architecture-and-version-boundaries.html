معماری MySQL، نسخه و مرز سازگاری

MySQL architecture, versions, and compatibility boundaries

برنامه روی لپ‌تاپ همکارمون به دیتابیس وصل می‌شه، اما روی محیط آزمایشی همان برنامه خطای تازه‌ای می‌ده. هر دو نفر می‌گن «MySQL داریم». همین جمله فعلاً چیزی رو ثابت نمی‌کنه: نسخه، محصول، تنظیمات و حتی مقصد اتصال ممکنه یکی نباشه. قبل از عوض‌کردن query، بیا از خود سرور مدرک بگیریم.

An application connects to the database on a teammate’s laptop, but the same application raises a new error in the test environment. Both people say, “We have MySQL.” That sentence proves very little: the version, product, configuration, or even connection target may differ. Before changing a query, let’s ask the server for evidence.

پیش‌نیازPrerequisite: SQL پایه آزمایشLab: MySQL 9.7.2 زمانTime: ۷۵ دقیقه

«MySQL روی هر دو هست»؛ پس چرا نتیجه فرق می‌کنه؟

“Both machines have MySQL”—so why are the results different?

تصور کن migration روی لپ‌تاپ اجرا شده، اما در CI با خطا متوقف می‌شه. اولین واکنش معمولاً این هست که syntax رو دست‌کاری کنیم یا سرور رو دوباره بالا بیاوریم. هنوز زوده. شاید CI به سرور دیگری وصل شده باشه؛ شاید آن سرور نسخه یا توزیع دیگری داشته باشه؛ شاید هم هر دو یک نسخه باشند و تفاوت از تنظیمات یا مجوز حساب بیاید.

Imagine a migration that succeeds on a laptop but fails in CI. The first impulse is often to tweak the syntax or restart the server. That is too soon. CI may be reaching a different server; that server may run another version or distribution; or both versions may match while settings or account privileges differ.

پس سؤال بهتر این نیست که «چرا MySQL خرابه؟» سؤال اینه: برنامه دقیقاً به کدام Server وصل شده و آن Server خودش رو چه معرفی می‌کنه؟ اسم برنامهٔ Client، نام سرویس در Compose و نسخه‌ای که روی لپ‌تاپ نصب کرده‌ای، به‌تنهایی جواب این سؤال نیست.

A better question is not “Why is MySQL broken?” It is: which server did the application actually reach, and how does that server identify itself? The client program’s name, a Compose service name, and the version installed on a laptop do not answer that by themselves.

قاعدهٔ این دوره: هر وقت رفتار نسخه‌حساس دیدیم، اول نسخه و محصول رو از همان connectionی می‌خونیم که مسئله در آن رخ داده هست. Rule for this course: Whenever behaviour may depend on a version, identify the product and version through the same connection where the problem occurs.

Client و Server یکی نیستند

The client and server are not the same thing

دستور mysql یک Client است؛ کارش ساختن connection و فرستادن درخواست هست. پردازش query، مدیریت connection و دسترسی به داده روی mysqld، یعنی Server، انجام می‌شه. Client می‌تونه روی لپ‌تاپ باشه و Server داخل container یا روی یک ماشین دیگر. پس نسخهٔ Client الزاماً نسخهٔ Server نیست.

The mysql command is a client: it opens a connection and sends requests. Query processing, connection handling, and data access happen in mysqld, the server. The client can run on a laptop while the server runs in a container or another machine. The client version is therefore not necessarily the server version.

این شکل عمداً ساده هست. Server فقط یک «لایهٔ واسط» نیست: حساب‌ها، مجوزها، متغیرهای session و server، optimizer و وضعیت connection هم در تصمیمی که می‌بینی نقش دارن. Storage Engine هم مرز مهمی است؛ حالأ دوره می‌بینیم چرا خیلی از رفتارهای تراکنشی و فیزیکی به InnoDB مربوط‌اند.

The diagram is deliberately simplified. The server is more than a pass-through: accounts, privileges, session and server variables, the optimizer, and connection state all affect observed behaviour. The storage-engine boundary matters too; later chapters show why many transactional and physical behaviours belong specifically to InnoDB.

نسخه رو از همان connection بخوان

Read the version through the connection in question

اگه خطا در برنامه رخ می‌ده، query تشخیصی رو از همان مسیر اتصال اجرا کن؛ نه فقط از terminal خودت. در MySQL می‌تونیم چند نشانه رو کنار هم بخوانیم:

If the failure happens in the application, run the diagnostic query through that same connection path—not only from your own terminal. In MySQL, read several signals together:

داخل Client متصل به ServerIn a client connected to the server
SELECT
  VERSION() AS server_version,
  @@version_comment AS distribution,
  @@version_compile_os AS compiled_for,
  @@version_compile_machine AS compiled_arch;

SHOW VARIABLES LIKE 'version%';

VERSION() نسخه‌ای رو که Server گزارش می‌کنه می‌ده؛ @@version_comment سرنخی دربارهٔ build یا توزیع هست. خروجی دوم متغیرهای مرتبط رو نشان می‌ده. این‌ها شناسنامهٔ کل ماشین یا سیستم‌عامل میزبان نیستند؛ فقط اطلاعاتی‌اند که همین Server ارائه می‌کنه.

VERSION() reports the server version; @@version_comment provides a clue about the build or distribution. The second statement lists related variables. These are not an inventory of the host machine or its operating system; they are information exposed by this server.

خروجی نمونه، فقط برای تشخیص شکل نتیجهRepresentative output, to show the shape
server_version  distribution
9.7.2            MySQL Community Server - GPL

Variable_name          Value
version                9.7.2
version_comment        MySQL Community Server - GPL
version_compile_os     Linux
version_compile_machine x86_64

مقدار واقعی ممکنه فرق کند؛ نکته این هست که خروجی رو از connection درست بگیری. اگه ترمینال 9.7 رو نشان می‌ده ولی برنامه رفتار دیگری دارد، هنوز نمی‌دونیم برنامه به همان Server وصل هست. host، port، socket، نام سرویس Compose و تنظیمات driver رو جداگانه بررسی می‌کنیم؛ این فصل فقط هویت Server رو روشن می‌کنه.

Real values may differ; the important point is to collect them from the correct connection. If the terminal reports 9.7 but the application behaves differently, we still do not know that the application reached the same server. Host, port, socket, Compose service name, and driver settings need separate checks; this chapter establishes server identity only.

شمارهٔ نسخه فقط تزئین نیست

A version number is not decoration

در زمان آماده‌سازی این فصل، مستندات رسمی MySQL دو مسیر انتشار رو توضیح می‌دن: LTS برای محیط‌هایی که مجموعهٔ قابلیت‌های باثبات‌تری می‌خوان، و Innovation برای دریافت زودتر تغییرهای تازه. مستندات فعلی MySQL 9.7 رو آخرین خط با الگوی شماره‌گذاری قبلی و 26.7 رو نمونهٔ شماره‌گذاری تقویمی معرفی می‌کنن. مدل انتشار ممکنه عوض شود؛ پس این جمله رو قانون همیشگی ندان، صفحهٔ رسمی رو هنگام انتخاب نسخه دوباره بخوان.

At the time this chapter is prepared, the official MySQL documentation describes two release tracks: LTS for environments seeking a more stable feature set, and Innovation for earlier access to new changes. Current documentation describes MySQL 9.7 as the final line using the previous numbering model and 26.7 as an example of calendar versioning. Release policy can change, so recheck the official page when selecting a version rather than treating this as timeless.

برای آزمایش این دوره، image رسمی mysql:9.7.2 رو pin می‌کنیم. این نسخه در زمان بررسی در فهرست imageهای رسمی دیده می‌شه؛ «نسخهٔ تمرین» بودنش به معنی توصیه برای production یا ارتقای خودکار سیستم تو نیست. محیط واقعی باید با سیاست پشتیبانی، driver، افزونه‌ها، backup قابل‌بازیابی و برنامهٔ بازگشت خودش انتخاب بشه.

For this course’s reproducible lab, we pin the official mysql:9.7.2 image. That tag appears in the official image listing at the time checked. Calling it the lab version is not a production recommendation or permission to upgrade automatically. A real environment must account for its support policy, drivers, plugins, restorable backups, and rollback plan.

برای مرز بین دو محصول هم یک اصل ساده نگه دار: اسم «MySQL-compatible» به‌تنهایی تضمین نمی‌کنه رفتار JSON، replication، authentication، storage engine یا syntax در هر نسخه یکی باشه. در این دوره محصول هدف MySQL است؛ اگه تفاوتی با MariaDB مطرح شد، آن رو مشخص و نسخه‌دار می‌گیم و وارد درس MariaDB نمی‌شویم.

Keep one simple rule about product boundaries: the label “MySQL-compatible” alone does not guarantee identical JSON, replication, authentication, storage-engine, or syntax behaviour in every version. This course targets MySQL; if a MariaDB difference matters, we will name it explicitly and version it without turning this into the MariaDB course.

آزمایش: ببینیم واقعاً به کدام Server وصل شدیم

Lab: identify the server we actually reached

اگه MySQL داری، همان connection خودت رو بررسی کن. اگه نداری، یک container موقت بالا می‌آوریم. این container هیچ portی روی میزبان منتشر نمی‌کنه و داده‌اش آزمایشی هست. رمز داخل دستور فقط برای همین محیط محلی است؛ آن رو برای سرور واقعی یا فایل پروژه استفاده نکن.

If you already have MySQL, inspect that connection. Otherwise, start a temporary container. It publishes no port on the host and holds disposable lab data. The password in the command is only for this local experiment; do not reuse it on a real server or put it in a project file.

This starts a specific image. Wait for the server to become ready; a running container alone does not prove that the database accepts queries. For this chapter, retry the connection:

اتصال با Client داخل containerConnect with the client inside the container

رمز رو وقتی prompt خواست وارد کن تا در history دستور ننشیند. بعد query نسخهٔ بالا رو اجرا کن. خروجی رو یادداشت کن و با برچسب image مقایسه کن. اگه هر دو 9.7.2 هستن، این فقط یک تطبیق نسخه است؛ صحت migration یا سازگاری برنامه رو هنوز ثابت نکرده‌ای.

Enter the password when prompted so it is not placed in command history. Run the version query above, record the result, and compare it with the image tag. If both say 9.7.2, that proves only a version match; it does not prove that a migration or application is compatible.

Know the cleanup boundary: The second command stops and removes the container; run it only after the first command confirms its name and image identify this disposable lab. If you renamed it, substitute that exact name. No volume or real data is removed here.

از خروجی چه نتیجه‌ای می‌گیریم—و چه نتیجه‌ای نه؟

What does the output establish—and what does it not?

وقتی query نسخه جواب می‌ده، می‌دونیم همان session به یک MySQL Server رسیده و Server این مشخصات رو گزارش کرده هست. هنوز دربارهٔ مقصد برنامه، تنظیمات schema، مجوز کاربر، charset، SQL mode یا قابل‌ارتقا بودن داده‌ها چیزی ثابت نشده. هر کدام مدرک خودش رو می‌خواهد.

When the version query succeeds, we know that this session reached a MySQL server and that the server reported these attributes. We have not established the application’s destination, schema settings, user privileges, character set, SQL mode, or whether the data can be upgraded safely. Each needs its own evidence.

همین مرزبندی جلوی یک خطای پرهزینه رو می‌گیره: دیدن یک شمارهٔ نسخه در لپ‌تاپ و فرض‌کردن همان نسخه در همه‌جا. فصل بعد محیط نصب و اتصال رو بازتولید می‌کنیم؛ بعدتر هم سراغ database، schema و رفتارهای خود MySQL می‌ریم.

This boundary prevents an expensive mistake: seeing a version number on a laptop and assuming every environment runs the same one. The next chapter makes installation and connection reproducible; later chapters investigate databases, schemas, and MySQL-specific behaviour.

تمرین‌ها: قبل از تغییر، مدرک جمع کن

Exercises: collect evidence before changing anything

همهٔ تمرین‌ها رو روی connection آزمایشی اجرا کن. خروجی‌های نسخه‌محور رو ثبت کن؛ مقدار دقیق ممکنه با image یا نصب تو فرق داشته باشه.

Run every exercise against a lab connection. Record version-dependent output; exact values may differ with your image or installation.

These are not prose-only questions. Every exercise should end in runnable SQL/commands, observable output, a reproducible error, or inspectable state. Predict first, run it, then conclude from evidence.

قبل از گفتن «MySQL مشکل دارد»

Before saying “MySQL is broken”

حالا اگه query روی یک محیط جواب بده و روی یکی دیگر نه، اولین حرکت‌مان حدس‌زدن نیست: از همان connection نسخه و build رو می‌خونیم، session رو ثبت می‌کنیم و بعد سراغ تفاوت بعدی می‌ریم. Client، Server و image سه نشانهٔ متفاوت‌اند؛ هیچ‌کدام رو جای دیگری جا نمی‌زنیم. فصل بعد خود محیط رو بازتولید می‌کنیم تا اتصال هم از یک حدس به یک مسیر روشن تبدیل بشه.

When a query works in one environment but not another, our first move is not a guess: read the version and build through the same connection, record the session, and then investigate the next difference. Client, server, and image are three different signals; none substitutes for another. In the next chapter we make the environment reproducible, turning connection setup from a guess into a visible path.
