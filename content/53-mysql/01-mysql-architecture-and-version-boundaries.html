معماری MySQL، نسخه و مرز سازگاری

MySQL architecture, versions, and compatibility boundaries

برنامه روی لپ‌تاپ همکارمان به دیتابیس وصل می‌شود، اما روی محیط آزمایشی همان برنامه خطای تازه‌ای می‌دهد. هر دو نفر می‌گویند «MySQL داریم». همین جمله فعلاً چیزی را ثابت نمی‌کند: نسخه، محصول، تنظیمات و حتی مقصد اتصال ممکن است یکی نباشد. قبل از عوض‌کردن query، بیایید از خود سرور مدرک بگیریم.

An application connects to the database on a teammate’s laptop, but the same application raises a new error in the test environment. Both people say, “We have MySQL.” That sentence proves very little: the version, product, configuration, or even connection target may differ. Before changing a query, let’s ask the server for evidence.

پیش‌نیازPrerequisite: SQL پایه آزمایشLab: MySQL 9.7.2 زمانTime: ۷۵ دقیقه

«MySQL روی هر دو هست»؛ پس چرا نتیجه فرق می‌کند؟

“Both machines have MySQL”—so why are the results different?

تصور کن migration روی لپ‌تاپ اجرا شده، اما در CI با خطا متوقف می‌شود. اولین واکنش معمولاً این است که syntax را دست‌کاری کنیم یا سرور را دوباره بالا بیاوریم. هنوز زوده. شاید CI به سرور دیگری وصل شده باشد؛ شاید آن سرور نسخه یا توزیع دیگری داشته باشد؛ شاید هم هر دو یک نسخه باشند و تفاوت از تنظیمات یا مجوز حساب بیاید.

Imagine a migration that succeeds on a laptop but fails in CI. The first impulse is often to tweak the syntax or restart the server. That is too soon. CI may be reaching a different server; that server may run another version or distribution; or both versions may match while settings or account privileges differ.

پس سؤال بهتر این نیست که «چرا MySQL خرابه؟» سؤال اینه: برنامه دقیقاً به کدام Server وصل شده و آن Server خودش را چه معرفی می‌کند؟ اسم برنامهٔ Client، نام سرویس در Compose و نسخه‌ای که روی لپ‌تاپ نصب کرده‌ای، به‌تنهایی جواب این سؤال نیست.

A better question is not “Why is MySQL broken?” It is: which server did the application actually reach, and how does that server identify itself? The client program’s name, a Compose service name, and the version installed on a laptop do not answer that by themselves.

قاعدهٔ این دوره: هر وقت رفتار نسخه‌حساس دیدیم، اول نسخه و محصول را از همان connectionی می‌خوانیم که مسئله در آن رخ داده است. Rule for this course: Whenever behaviour may depend on a version, identify the product and version through the same connection where the problem occurs.

Client و Server یکی نیستند

The client and server are not the same thing

دستور mysql یک Client است؛ کارش ساختن connection و فرستادن درخواست است. پردازش query، مدیریت connection و دسترسی به داده روی mysqld، یعنی Server، انجام می‌شود. Client می‌تواند روی لپ‌تاپ باشد و Server داخل container یا روی یک ماشین دیگر. پس نسخهٔ Client الزاماً نسخهٔ Server نیست.

The mysql command is a client: it opens a connection and sends requests. Query processing, connection handling, and data access happen in mysqld, the server. The client can run on a laptop while the server runs in a container or another machine. The client version is therefore not necessarily the server version.

این شکل عمداً ساده است. Server فقط یک «لایهٔ واسط» نیست: حساب‌ها، مجوزها، متغیرهای session و server، optimizer و وضعیت connection هم در تصمیمی که می‌بینی نقش دارند. Storage Engine هم مرز مهمی است؛ در ادامهٔ دوره می‌بینیم چرا خیلی از رفتارهای تراکنشی و فیزیکی به InnoDB مربوط‌اند.

The diagram is deliberately simplified. The server is more than a pass-through: accounts, privileges, session and server variables, the optimizer, and connection state all affect observed behaviour. The storage-engine boundary matters too; later chapters show why many transactional and physical behaviours belong specifically to InnoDB.

نسخه را از همان connection بخوان

Read the version through the connection in question

اگر خطا در برنامه رخ می‌دهد، query تشخیصی را از همان مسیر اتصال اجرا کن؛ نه فقط از terminal خودت. در MySQL می‌توانیم چند نشانه را کنار هم بخوانیم:

If the failure happens in the application, run the diagnostic query through that same connection path—not only from your own terminal. In MySQL, read several signals together:

داخل Client متصل به ServerIn a client connected to the server
SELECT
  VERSION() AS server_version,
  @@version_comment AS distribution,
  @@version_compile_os AS compiled_for,
  @@version_compile_machine AS compiled_arch;

SHOW VARIABLES LIKE 'version%';

VERSION() نسخه‌ای را که Server گزارش می‌کند می‌دهد؛ @@version_comment سرنخی دربارهٔ build یا توزیع است. خروجی دوم متغیرهای مرتبط را نشان می‌دهد. این‌ها شناسنامهٔ کل ماشین یا سیستم‌عامل میزبان نیستند؛ فقط اطلاعاتی‌اند که همین Server ارائه می‌کند.

VERSION() reports the server version; @@version_comment provides a clue about the build or distribution. The second statement lists related variables. These are not an inventory of the host machine or its operating system; they are information exposed by this server.

خروجی نمونه، فقط برای تشخیص شکل نتیجهRepresentative output, to show the shape
server_version  distribution
9.7.2            MySQL Community Server - GPL

Variable_name          Value
version                9.7.2
version_comment        MySQL Community Server - GPL
version_compile_os     Linux
version_compile_machine x86_64

مقدار واقعی ممکن است فرق کند؛ نکته این است که خروجی را از connection درست بگیری. اگر ترمینال 9.7 را نشان می‌دهد ولی برنامه رفتار دیگری دارد، هنوز نمی‌دانیم برنامه به همان Server وصل است. host، port، socket، نام سرویس Compose و تنظیمات driver را جداگانه بررسی می‌کنیم؛ این فصل فقط هویت Server را روشن می‌کند.

Real values may differ; the important point is to collect them from the correct connection. If the terminal reports 9.7 but the application behaves differently, we still do not know that the application reached the same server. Host, port, socket, Compose service name, and driver settings need separate checks; this chapter establishes server identity only.

شمارهٔ نسخه فقط تزئین نیست

A version number is not decoration

در زمان آماده‌سازی این فصل، مستندات رسمی MySQL دو مسیر انتشار را توضیح می‌دهند: LTS برای محیط‌هایی که مجموعهٔ قابلیت‌های باثبات‌تری می‌خواهند، و Innovation برای دریافت زودتر تغییرهای تازه. مستندات فعلی MySQL 9.7 را آخرین خط با الگوی شماره‌گذاری قبلی و 26.7 را نمونهٔ شماره‌گذاری تقویمی معرفی می‌کنند. مدل انتشار ممکن است عوض شود؛ پس این جمله را قانون همیشگی ندان، صفحهٔ رسمی را هنگام انتخاب نسخه دوباره بخوان.

At the time this chapter is prepared, the official MySQL documentation describes two release tracks: LTS for environments seeking a more stable feature set, and Innovation for earlier access to new changes. Current documentation describes MySQL 9.7 as the final line using the previous numbering model and 26.7 as an example of calendar versioning. Release policy can change, so recheck the official page when selecting a version rather than treating this as timeless.

برای آزمایش این دوره، image رسمی mysql:9.7.2 را pin می‌کنیم. این نسخه در زمان بررسی در فهرست imageهای رسمی دیده می‌شود؛ «نسخهٔ تمرین» بودنش به معنی توصیه برای production یا ارتقای خودکار سیستم تو نیست. محیط واقعی باید با سیاست پشتیبانی، driver، افزونه‌ها، backup قابل‌بازیابی و برنامهٔ بازگشت خودش انتخاب شود.

For this course’s reproducible lab, we pin the official mysql:9.7.2 image. That tag appears in the official image listing at the time checked. Calling it the lab version is not a production recommendation or permission to upgrade automatically. A real environment must account for its support policy, drivers, plugins, restorable backups, and rollback plan.

برای مرز بین دو محصول هم یک اصل ساده نگه دار: اسم «MySQL-compatible» به‌تنهایی تضمین نمی‌کند رفتار JSON، replication، authentication، storage engine یا syntax در هر نسخه یکی باشد. در این دوره محصول هدف MySQL است؛ اگر تفاوتی با MariaDB مطرح شد، آن را مشخص و نسخه‌دار می‌گوییم و وارد درس MariaDB نمی‌شویم.

Keep one simple rule about product boundaries: the label “MySQL-compatible” alone does not guarantee identical JSON, replication, authentication, storage-engine, or syntax behaviour in every version. This course targets MySQL; if a MariaDB difference matters, we will name it explicitly and version it without turning this into the MariaDB course.

آزمایش: ببینیم واقعاً به کدام Server وصل شدیم

Lab: identify the server we actually reached

اگر MySQL داری، همان connection خودت را بررسی کن. اگر نداری، یک container موقت بالا می‌آوریم. این container هیچ portی روی میزبان منتشر نمی‌کند و داده‌اش آزمایشی است. رمز داخل دستور فقط برای همین محیط محلی است؛ آن را برای سرور واقعی یا فایل پروژه استفاده نکن.

If you already have MySQL, inspect that connection. Otherwise, start a temporary container. It publishes no port on the host and holds disposable lab data. The password in the command is only for this local experiment; do not reuse it on a real server or put it in a project file.

ساخت محیط آزمایشیCreate the lab environment
docker run --name mysql97-lab -e MYSQL_ROOT_PASSWORD=lab-only-change-me -d mysql:9.7.2

این دستور image مشخص را اجرا می‌کند. منتظر آماده‌شدن Server بمان؛ زنده‌بودن container به ‌تنهایی ثابت نمی‌کند دیتابیس پذیرای query است. برای این فصل، تلاش اتصال را تکرار می‌کنیم:

This starts a specific image. Wait for the server to become ready; a running container alone does not prove that the database accepts queries. For this chapter, retry the connection:

اتصال با Client داخل containerConnect with the client inside the container
docker exec -it mysql97-lab mysql -uroot -p

رمز را وقتی prompt خواست وارد کن تا در history دستور ننشیند. بعد query نسخهٔ بالا را اجرا کن. خروجی را یادداشت کن و با برچسب image مقایسه کن. اگر هر دو 9.7.2 هستند، این فقط یک تطبیق نسخه است؛ صحت migration یا سازگاری برنامه را هنوز ثابت نکرده‌ای.

Enter the password when prompted so it is not placed in command history. Run the version query above, record the result, and compare it with the image tag. If both say 9.7.2, that proves only a version match; it does not prove that a migration or application is compatible.

پاک‌سازی فقط همین آزمایشClean up only this lab
docker inspect --format '{{.Name}} | {{.Config.Image}}' mysql97-lab
docker rm -f mysql97-lab
مرز پاک‌سازی را یادت بماند: فرمان دوم container را متوقف و حذف می‌کند؛ فقط وقتی اجراش کن که فرمان اول نام و image همین محیط disposable را نشان می‌دهد. اگر نامش را عوض کردی، نام دقیق خودت را جایگزین کن. volume یا دادهٔ واقعی را اینجا پاک نمی‌کنیم. Know the cleanup boundary: The second command stops and removes the container; run it only after the first command confirms its name and image identify this disposable lab. If you renamed it, substitute that exact name. No volume or real data is removed here.

از خروجی چه نتیجه‌ای می‌گیریم—و چه نتیجه‌ای نه؟

What does the output establish—and what does it not?

وقتی query نسخه جواب می‌دهد، می‌دانیم همان session به یک MySQL Server رسیده و Server این مشخصات را گزارش کرده است. هنوز دربارهٔ مقصد برنامه، تنظیمات schema، مجوز کاربر، charset، SQL mode یا قابل‌ارتقا بودن داده‌ها چیزی ثابت نشده. هر کدام مدرک خودش را می‌خواهد.

When the version query succeeds, we know that this session reached a MySQL server and that the server reported these attributes. We have not established the application’s destination, schema settings, user privileges, character set, SQL mode, or whether the data can be upgraded safely. Each needs its own evidence.

همین مرزبندی جلوی یک خطای پرهزینه را می‌گیرد: دیدن یک شمارهٔ نسخه در لپ‌تاپ و فرض‌کردن همان نسخه در همه‌جا. در فصل بعد محیط نصب و اتصال را بازتولید می‌کنیم؛ بعدتر هم سراغ database، schema و رفتارهای خود MySQL می‌رویم.

This boundary prevents an expensive mistake: seeing a version number on a laptop and assuming every environment runs the same one. The next chapter makes installation and connection reproducible; later chapters investigate databases, schemas, and MySQL-specific behaviour.

جاهایی که زود گول می‌خوریم

Easy assumptions to fall for

نسخهٔ Client را با Server یکی می‌گیریم Confusing client and server versions

Client فقط ابزار اتصال است؛ نسخهٔ Server را از session مقصد بخوان.

The client is only the connection tool; read the server version through the destination session.

به image tag اعتماد کامل می‌کنیم Trusting an image tag as complete proof

container قدیمی یا volume دادهٔ موجود می‌تواند داستان جداگانه‌ای داشته باشد؛ Server واقعی را query کن.

An old container or existing data volume may tell a different story; query the actual server.

MySQL و MariaDB را یک محصول فرض می‌کنیم Treating MySQL and MariaDB as one product

شباهت syntax، تضمین یکسان‌بودن همهٔ رفتارها نیست. محصول و نسخه را ثبت کن.

Similar syntax does not guarantee identical behaviour. Record the product and version.

از یک query، سازگاری کامل نتیجه می‌گیریم Inferring full compatibility from one query

موفق‌شدن SELECT VERSION() فقط اتصال و پاسخ همین query را ثابت می‌کند.

A successful SELECT VERSION() proves only the connection and response to this query.

تمرین‌ها: قبل از تغییر، مدرک جمع کن

Exercises: collect evidence before changing anything

همهٔ تمرین‌ها را روی connection آزمایشی اجرا کن. خروجی‌های نسخه‌محور را ثبت کن؛ مقدار دقیق ممکن است با image یا نصب تو فرق داشته باشد.

Run every exercise against a lab connection. Record version-dependent output; exact values may differ with your image or installation.

۱) همین Server خودش را چطور معرفی می‌کند؟1) How does this server identify itself?

سه مقدار نسخه، توضیح build و نسخهٔ کوتاه‌شده را در یک query برگردان. هدف، داشتن یک مدرک قابل الصاق به گزارش خطاست.

Return the version, build comment, and short version string in one query. The goal is evidence you can attach to a bug report.

راه‌حل و دلیلSolution and reasoning 
SELECT VERSION(), @@version_comment, @@version;

VERSION() و @@version معمولاً نسخهٔ Server را نشان می‌دهند و comment سرنخ build است. این خروجی مقصد برنامه را ثابت نمی‌کند مگر از connection خود برنامه گرفته شده باشد.

VERSION() and @@version normally report the server version; the comment hints at the build. This does not prove the application’s destination unless collected through its connection.

۲) Client محلی را با Server مقایسه کن2) Compare the local client with the server

نسخهٔ Client را از terminal و نسخهٔ Server را از SQL بگیر. دو مقدار را کنار هم ثبت کن و بگو کدام‌یک به مقصد متصل مربوط است.

Read the client version in a terminal and the server version through SQL. Record both and identify which belongs to the connected destination.

راه‌حل و دلیلSolution and reasoning 
mysql --version
SELECT VERSION();

اولی ابزار محلی و دومی Server متصل را توصیف می‌کند. برابر نبودنشان به‌تنهایی خطا نیست؛ ناسازگاری را باید با سناریوی واقعی اتصال و قابلیت driver سنجید.

The first describes the local tool; the second describes the connected server. A mismatch is not automatically an error; assess compatibility in the actual connection scenario and driver.

۳) تگ image چه چیزی را می‌گوید؟3) What does the image tag tell you?

container آزمایش را با image مشخص اجرا کن و نسخهٔ داخل Server را query کن. خروجی را با tag مقایسه کن و یک محدودیت این مقایسه را بنویس.

Start the lab container from the pinned image and query the server version. Compare it with the tag and state one limitation of that comparison.

راه‌حل و دلیلSolution and reasoning 
docker inspect --format '{{.Config.Image}}' mysql97-lab
docker exec -it mysql97-lab mysql -uroot -p
# At the mysql> prompt:
SELECT VERSION();

خط اول image انتخابی برای container را می‌دهد؛ query را پس از ورود تعاملی اجرا کن تا رمز روی command line نرود. tag یک نام متحرک هم می‌تواند باشد؛ این تمرین از tag نسخه‌دار استفاده می‌کند و باز هم hash دقیق image را جداگانه می‌شود ثبت کرد.

The first line reports the container’s selected image; the second reads the server version. Tags can be movable names. This lab uses a versioned tag, and the exact image digest can still be recorded separately.

۴) Server برای چه سیستم‌عاملی build شده؟4) For which platform was the server built?

مقادیر build را query کن. خروجی را با سیستم‌عامل میزبان یکی فرض نکن؛ توضیح بده دقیقاً چه چیزی را نشان می‌دهد.

Query the build attributes. Do not equate them with the host operating system; explain precisely what they show.

راه‌حل و دلیلSolution and reasoning 
SELECT @@version_compile_os, @@version_compile_machine;

این‌ها اطلاعات build گزارش‌شده از Server هستند، نه الزاماً مشخصات kernel میزبان یا معماری پردازنده‌ای که client روی آن اجرا می‌شود.

These are server-reported build attributes, not necessarily the host kernel or the architecture on which the client runs.

۵) کدام storage engineها موجود و فعال‌اند؟5) Which storage engines are available and enabled?

فهرست engineها را بخوان و ردیف InnoDB را پیدا کن. وضعیتش را برای گزارش محیط ثبت کن.

List the engines and find the InnoDB row. Record its status for the environment report.

راه‌حل و دلیلSolution and reasoning 
SHOW ENGINES;

در ستون Support وضعیت InnoDB را می‌بینی؛ مثلاً DEFAULT یا YES. این فهرست دربارهٔ همین Server است و به‌تنهایی نمی‌گوید هر جدول واقعاً از کدام engine استفاده می‌کند.

The Support column shows InnoDB’s status, such as DEFAULT or YES. This list describes this server and does not by itself tell you which engine each table uses.

۶) Server روی کدام پورت گوش می‌دهد؟6) Which port does the server listen on?

متغیر پورت را بخوان و نتیجه را با port منتشرشده در Docker جدا نگه دار؛ این دو یکی نیستند.

Read the server port variable and keep it distinct from a Docker-published host port; they are not the same thing.

راه‌حل و دلیلSolution and reasoning 
SHOW VARIABLES LIKE 'port';

این پورت داخلی Server است. اگر Docker port mapping داشته باشی، سمت میزبان می‌تواند عدد دیگری باشد؛ mapping را با docker port mysql97-lab بررسی کن.

This is the server’s internal port. With Docker port mapping, the host-side number may differ; inspect that mapping with docker port mysql97-lab.

۷) encoding connection را ثبت کن7) Record the connection character set

character setهای client، connection و نتیجه را با یک query ببین. اگر متن فارسی خراب شد، این فقط یکی از مرزهایی است که باید بررسی کنی.

Inspect the client, connection, and result character sets in one query. If Persian text is corrupted, this is one boundary to investigate.

راه‌حل و دلیلSolution and reasoning 
SELECT
  @@character_set_client,
  @@character_set_connection,
  @@character_set_results;

سه مقدار مسیر متن در session را روشن می‌کنند. این نتیجه به‌تنهایی collation ستون‌ها یا encoding فایل برنامه را ثابت نمی‌کند.

The three values describe the session’s text path. They do not establish column collations or the application file’s encoding.

۸) SQL mode این session چیست؟8) What is this session’s SQL mode?

SQL mode را از Server بخوان و آن را به گزارش reproducing یک خطا اضافه کن؛ در این تمرین چیزی را تغییر نده.

Read the SQL mode and add it to a bug reproduction report; do not change it in this exercise.

راه‌حل و دلیلSolution and reasoning 
SELECT @@SESSION.sql_mode, @@GLOBAL.sql_mode;

مقدار session همان چیزی است که queryهای این connection می‌بینند؛ global مقدار پیش‌فرض برای sessionهای تازه را نشان می‌دهد. تغییر global وسط incident بدون فهم اثرش کار درستی نیست.

The session value is what this connection uses; the global value is the default for new sessions. Changing the global value during an incident without understanding its impact is unsafe.

۹) autocommit این session را بررسی کن9) Inspect this session’s autocommit

مقدار session و global را بخوان. چرا ثبت مقدار session برای بازتولید رفتار transaction مفیدتر است؟

Read session and global values. Why is recording the session value more useful when reproducing transaction behaviour?

راه‌حل و دلیلSolution and reasoning 
SELECT @@SESSION.autocommit, @@GLOBAL.autocommit;

transaction جاری به تنظیم session وابسته است؛ دو connection روی یک Server می‌توانند session state متفاوت داشته باشند. این query فقط مقدار را می‌خواند و تغییری ایجاد نمی‌کند.

The current transaction depends on session state; two connections to one server may differ. This query is read-only and changes nothing.

۱۰) کاربر و host حساب فعلی را ببین10) Inspect the current account and host

هویت login و هویت‌ای که Server برای session انتخاب کرده را کنار هم برگردان. هنوز مجوزها را تغییر نده.

Return the login identity and the identity selected by the server for this session. Do not change privileges yet.

راه‌حل و دلیلSolution and reasoning 
SELECT USER(), CURRENT_USER();

USER() اطلاعات کاربر/مبدأ اتصال را گزارش می‌کند؛ CURRENT_USER() accountای را نشان می‌دهد که در بررسی مجوزها به کار رفته. در MySQL، بخش host بخشی از هویت account است.

USER() reports the connection user and origin; CURRENT_USER() identifies the account used for privilege checking. In MySQL, the host component is part of an account’s identity.

۱۱) Server به چه شکلی connection گرفته؟11) How was this connection established?

متغیرهای host و socket را بخوان و با نوع اتصال خودت مقایسه کن. خروجی variableها به‌تنهایی مسیر فعلی connection را مشخص نمی‌کند؛ یک شاهد دیگر پیدا کن.

Read the host and socket variables and compare them with your connection. Variables alone do not identify the current connection path; find another signal.

راه‌حل و دلیلSolution and reasoning 
SHOW VARIABLES WHERE Variable_name IN ('hostname', 'port', 'socket');
\s

\s فرمان داخلی Client است و معمولاً نوع connection را هم گزارش می‌کند. hostname Server با آدرس مقصدی که Client استفاده کرده یکی نیست؛ این تمایز جلوی تشخیص اشتباه DNS را می‌گیرد.

\s is a client command and commonly reports the connection type. The server hostname is not necessarily the address the client used; keeping them distinct helps avoid a false DNS diagnosis.

۱۲) databaseهای قابل مشاهده را فهرست کن12) List databases visible to this account

فهرست databaseها را بگیر و توضیح بده چرا این فهرست لزوماً کل databaseهای Server نیست.

List databases and explain why this may not be the complete set on the server.

راه‌حل و دلیلSolution and reasoning 
SHOW DATABASES;

نتیجه تحت‌تأثیر مجوزهای account است؛ نادیده‌بودن یک database به‌تنهایی وجودنداشتن آن را ثابت نمی‌کند. اینجا عمداً مفاهیم database و schema را از دورهٔ SQL دوباره آموزش نمی‌دهیم.

The result is affected by the account’s privileges; an absent database does not prove it does not exist. This course does not reteach database and schema fundamentals from the SQL track.

۱۳) نسخهٔ واقعی container را با دو شاهد ثبت کن13) Record the container’s actual version using two signals

برای container تمرینی، مقدار image و خروجی Server را بگیر. اگر متفاوت بودند، قبل از اقدام چه مدرک سومی می‌خواهی؟

For the lab container, collect the image reference and server output. If they differ, what third piece of evidence would you gather before acting?

راه‌حل و دلیلSolution and reasoning 
docker inspect --format '{{.Config.Image}}' mysql97-lab
docker exec -it mysql97-lab mysql -uroot -p
# At the mysql> prompt:
SELECT VERSION(), @@version_comment;

اولی تنظیم container را می‌خواند؛ query را بعد از ورود تعاملی اجرا کن تا رمز در argumentها قرار نگیرد. در اختلاف، container ID، زمان ساخته‌شدن، digest image و احتمال اتصال به Server دیگری را بررسی کن؛ هیچ‌کدام را با حذف داده حل نکن.

The first reads the container configuration; the second queries the live server. If they differ, inspect the container ID, creation time, image digest, and possibility of a different server connection—do not “fix” it by deleting data.

۱۴) چرا یک Server، دو تصویر متفاوت می‌دهد؟14) Why can one server give two different pictures?

در دو connection، SQL mode و charset session را query کن. تفاوت را با SQL نشان بده و نتیجه بگیر آیا الزاماً دو Server داریم؟

Query session SQL mode and character sets in two connections. Show any difference with SQL and decide whether it necessarily means two servers.

راه‌حل و دلیلSolution and reasoning 
SELECT CONNECTION_ID(), @@SESSION.sql_mode,
       @@character_set_connection, @@collation_connection;

روی هر دو connection اجرا کن. اختلاف sessionها ممکن است از تنظیم client یا مقداردهی connection pool باشد؛ شناسهٔ متفاوت connection هم به‌تنهایی نشانهٔ دو Server نیست.

Run it in both connections. Session differences may come from client setup or a connection pool; different connection IDs alone do not mean there are two servers.

۱۵) خطای «قابلیت ناشناخته» را نسخه‌محور بررسی کن15) Investigate an “unknown feature” error by version

فرض کن یک migration از قابلیت نسخه‌حساس استفاده می‌کند. یک query آماده کن که نسخه و محصول گزارش‌شده را کنار هم ثبت کند؛ migration را روی دیتابیس واقعی دوباره اجرا نکن.

Suppose a migration uses a version-sensitive feature. Prepare a query that records the reported version and product clue together; do not rerun the migration on production.

راه‌حل و دلیلSolution and reasoning 
SELECT VERSION() AS server_version,
       @@version_comment AS product_build,
       @@version_compile_os AS build_os;

این snapshot نقطهٔ شروع است، نه پاسخ نهایی. بعد باید مستندات همان نسخه و وضعیت migration را در محیط disposable بررسی کرد؛ برچسب «MySQL-compatible» به‌تنهایی مجوز اجرای دوباره نیست.

This snapshot is a starting point, not the final answer. Next, check documentation for that version and inspect migration state in a disposable environment; “MySQL-compatible” is not permission to rerun it.

۱۶) یک گزارش قابل‌بازتولید بساز16) Build a reproducible environment report

گزارش کوتاهی با query بساز که نسخه، build، SQL mode، charset session و کاربر جاری را در یک نتیجه ثبت کند.

Write one query that captures version, build, session SQL mode, connection character set, and the current account in a compact report.

راه‌حل و دلیلSolution and reasoning 
SELECT VERSION() AS server_version,
       @@version_comment AS product_build,
       @@SESSION.sql_mode AS session_sql_mode,
       @@character_set_connection AS connection_charset,
       CURRENT_USER() AS privilege_account;

یک ردیف قابل ضمیمه به issue می‌گیری. secret یا رشتهٔ اتصال را در گزارش عمومی نگذار؛ این query هم مقصد host را به‌طور کامل ثابت نمی‌کند.

You get one row suitable for an issue attachment. Do not include secrets or a connection string in a public report; this query also does not fully prove the destination host.

۱۷) قبل از ارتقا چه چیزهایی را baseline می‌کنی؟17) What do you baseline before an upgrade?

یک query قابل اجرا بنویس که نسخهٔ Server و مهم‌ترین تنظیم‌های session را برای مقایسهٔ پیش/پس از ارتقا برگرداند. در این تمرین ارتقایی انجام نمی‌شود.

Write a runnable query returning the server version and key session settings for a before/after upgrade comparison. Do not perform an upgrade in this exercise.

راه‌حل و دلیلSolution and reasoning 
SELECT VERSION() AS server_version,
       @@SESSION.sql_mode AS sql_mode,
       @@SESSION.autocommit AS autocommit,
       @@character_set_connection AS charset_connection,
       @@collation_connection AS collation_connection;

این baseline بخشی از رفتار session را ثبت می‌کند. پیش از upgrade واقعی باید backup قابل restore، آزمون برنامه، extensionها و compatibility را هم بررسی کرد؛ این چند مقدار کافی نیست.

This baseline records part of session behaviour. A real upgrade also requires a restorable backup, application tests, extension checks, and compatibility review; these values alone are insufficient.

۱۸) تشخیص زودهنگام را متوقف کن18) Stop an early diagnosis

برنامه خطای syntax می‌دهد. terminal تو mysql --version برابر 9.7.2 نشان می‌دهد؛ اما query برنامه هنوز اجرا نشده. با یک دستور SQL از چه چیزی مطمئن می‌شوی و چه چیزی همچنان نامعلوم می‌ماند؟

The application reports a syntax error. Your terminal says mysql --version is 9.7.2, but no query has run through the application. What can one SQL statement establish, and what remains unknown?

راه‌حل و دلیلSolution and reasoning 
SELECT VERSION(), @@version_comment, CONNECTION_ID();

این را از همان connection برنامه اجرا کن؛ نسخه و هویت build گزارش‌شده و یک شناسهٔ connection می‌گیری. با آن هنوز host/port مقصد یا compatibility قابلیت موردنظر ثابت نمی‌شود؛ تنظیمات اتصال و مستند همان نسخه را هم باید بررسی کنی.

Run it through the application’s connection; it returns the reported version/build and a connection ID. It still does not prove the destination host/port or feature compatibility; inspect connection settings and documentation for that version too.

قبل از گفتن «MySQL مشکل دارد»

Before saying “MySQL is broken”

حالا اگر query روی یک محیط جواب بدهد و روی یکی دیگر نه، اولین حرکت‌مان حدس‌زدن نیست: از همان connection نسخه و build را می‌خوانیم، session را ثبت می‌کنیم و بعد سراغ تفاوت بعدی می‌رویم. Client، Server و image سه نشانهٔ متفاوت‌اند؛ هیچ‌کدام را جای دیگری جا نمی‌زنیم. در فصل بعد خود محیط را بازتولید می‌کنیم تا اتصال هم از یک حدس به یک مسیر روشن تبدیل شود.

When a query works in one environment but not another, our first move is not a guess: read the version and build through the same connection, record the session, and then investigate the next difference. Client, server, and image are three different signals; none substitutes for another. In the next chapter we make the environment reproducible, turning connection setup from a guess into a visible path.
