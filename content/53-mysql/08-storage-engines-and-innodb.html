Storage Engineها و InnoDB

Storage Engines and InnoDB

یک عملیات مالی نصفه شکست خورده، اما بخشی از تغییرها در جدول مانده هست. قبل از اینکه query رو مقصر بدانیم، engine هر جدول رو می‌خونیم. در MySQL، انتخاب engine فقط تنظیم ظاهری نیست؛ روی transaction، lock و رفتار بازیابی اثر می‌ذاره.

A financial operation fails halfway, yet some changes remain in a table. Before blaming the query, inspect each table’s engine. In MySQL, an engine is not cosmetic; it affects transactions, locking, and recovery behavior.

ROLLBACK زدیم؛ چرا ردیف باقی ماند؟We rolled back—why is a row still there?

برنامه ابتدا موجودی رو کم می‌کنه، بعد ردیف سفارش می‌سازد. مرحلهٔ دوم خطا می‌ده و کد ROLLBACK اجرا می‌کنه. موجودی سر جایش برگشته؛ اما سفارش هم انگار ثبت شده. احتمال دارد دو table از دو engine متفاوت باشند. بیا همین رفتار رو در database آزمایشی بازتولید کنیم.

The application decrements inventory, then creates an order. The second step fails and the code runs ROLLBACK. Inventory is restored, but the order seems to remain. The tables may use different engines. Let’s reproduce the behavior in a lab database.

Storage Engine مسئول روش ذخیره و برخی رفتارهای دسترسی به دادهٔ table هست. در MySQL 9.7، InnoDB engine پیش‌فرض ساخت table جدید است؛ ولی default رو فرض نمی‌کنیم، چون تنظیم Server قابل تغییر هست. هر table رو جداگانه از metadata بررسی می‌کنیم.

A storage engine controls how a table stores data and some of its access behavior. In MySQL 9.7, InnoDB is the default for new tables, but we do not assume that: a server setting can change. Inspect every table’s metadata.

اول از Server بپرس، بعد از خود tableAsk the server, then inspect the table

یک Server ممکنه engineهای مختلفی پشتیبانی کند. SHOW ENGINES فهرست و وضعیت پشتیبانی رو می‌ده؛ بعد SHOW CREATE TABLE یا information_schema.TABLES engine واقعی object رو روشن می‌کنه. «پشتیبانی می‌شه» با «برای این table استفاده شده» یکی نیست.

A server may support several engines. SHOW ENGINES lists support; SHOW CREATE TABLE or information_schema.TABLES shows the engine actually used by an object. “Supported” does not mean “used by this table.”

وضعیت engineها و defaultEngine support and default
SHOW ENGINES;
SELECT @@default_storage_engine AS default_engine;

SELECT TABLE_NAME,ENGINE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA=DATABASE()
  AND TABLE_TYPE='BASE TABLE'
ORDER BY TABLE_NAME;

در خروجی به ردیف InnoDB و ستون SUPPORT نگاه کن؛ مقدار DEFAULT در این ستون نشان می‌ده کدام engine پیش‌فرض هست. بعد برای table خودت به ستون ENGINE نگاه کن. view در فهرست base table جای نمی‌گیره و قرار نیست engine مستقل داشته باشه.

Inspect the InnoDB row and SUPPORT column; DEFAULT identifies the default engine. Then inspect ENGINE for the specific table. A view is not a base table and does not have its own storage engine.

آزمایش rollback رو فقط در disposable schema انجام بدهRun the rollback experiment only in a disposable schema

برای مقایسه دو table هم‌شکل می‌سازیم. در transaction روی هر دو ردیف درج می‌کنیم و rollback می‌زنیم. هیچ دادهٔ واقعی در کار نیست. انتظارمان این هست که InnoDB تغییر transaction رو برگردونه؛ MyISAM transaction ندارد، پس rollback همان ضمانت رو نمی‌ده.

We create two structurally similar tables, insert into both within a transaction, and roll back. No production data is involved. We expect InnoDB to undo transactional changes; MyISAM does not provide that transaction guarantee.

دو engine، یک آزمایشTwo engines, one experiment
CREATE DATABASE IF NOT EXISTS codenames_engine_lab;
USE codenames_engine_lab;
CREATE TABLE txn_row(id INT PRIMARY KEY,note VARCHAR(30)) ENGINE=InnoDB;
CREATE TABLE non_txn_row(id INT PRIMARY KEY,note VARCHAR(30)) ENGINE=MyISAM;
INSERT INTO txn_row VALUES(1,'initial value');

START TRANSACTION;
INSERT INTO txn_row VALUES(2,'rolled back');
INSERT INTO non_txn_row VALUES(1,'engine has no transaction');
ROLLBACK;

SELECT * FROM txn_row WHERE id=2;
SELECT * FROM non_txn_row;

انتظار داریم SELECT اول ردیفی ندهد و SELECT دوم ردیف MyISAM رو نشان دهد. این آزمایش رو با یک statement جدا برای هر نتیجه اجرا کن تا اگه client روی خطا متوقف شد، برداشت اشتباه نکنی. rollback فقط روی engineهای transaction-aware و تغییرهای داخل همان transaction ضمانت دارد.

The first SELECT should return no row; the second should show the MyISAM row. Run the result checks separately if your client stops on errors. Rollback guarantees apply to transaction-aware engines and changes made within that transaction.

در production این آزمایش رو تکرار نکن.MyISAM table دائمی هست و rollback تغییرش رو پاک نمی‌کنه. برای هر آزمایش مخرب، database دورریختنی و نام مشخص لازم هست.Do not repeat this on production.The MyISAM table is permanent and rollback does not undo its change. Destructive tests belong in a disposable database with explicit names.

چرا InnoDB انتخاب پیش‌فرض است؟Why is InnoDB the default choice?

InnoDB transaction، foreign key، MVCC و crash recovery دارد. این‌ها برای دادهٔ مهم برنامه رفتار قابل‌اتکاتری فراهم می‌کنن؛ ولی «داشتن recovery» جای backup رو نمی‌گیره و «transaction» هم اشتباه منطقی داخل transaction رو خودکار کشف نمی‌کنه. اگه برنامه یک مبلغ غلط ولی معتبر commit کند، engine نمی‌فهمد که business rule نقض شده هست.

InnoDB provides transactions, foreign keys, MVCC, and crash recovery. These features offer stronger behavior for important application data, but crash recovery does not replace backups, and transactions do not detect logical mistakes. If an application commits a wrong but valid amount, the engine cannot know the business rule was violated.

EngineTransaction / FKLocking model (simplified)Use it only when…
InnoDBYes / YesRow-level locking with MVCC behaviorDefault general-purpose transactional data
MyISAMNo / NoTable-level lockingA specific legacy/read-mostly need has been measured and accepted
MEMORYNo durable rows / No FKTable-level lockingVolatile in-memory table behavior is intentional
Other engineEngine-dependentVerify its documented behaviorThe requirement matches its documented tradeoffs

این خلاصه جای مستندات هر engine نیست. MyISAM هنوز در بعضی نصب‌ها موجود است، اما default نیست؛ MEMORY هم با restart دادهٔ durable نمی‌ده و نباید جای database اصلی جا زده شود. engine رو بر اساس نیاز اندازه‌گیری‌شده انتخاب می‌کنیم، نه نامی که قدیمی یا سریع به نظر می‌رسه.

This summary does not replace each engine’s documentation. MyISAM may still be available but is not the default; MEMORY does not provide durable rows across restart and is not a substitute for the primary database. Choose an engine from measured requirements, not from a name that sounds old or fast.

ترکیب engineها مرز transaction رو می‌شکندMixing engines can break the transaction boundary

عملیات business وقتی چند table رو تغییر می‌ده، فقط وقتی یک transaction واحد می‌تونه همه رو برگردونه که tableها و statementها با ضمانت transaction سازگار باشند. اگه جدول MyISAM وسط کار تغییر کند، rollback آن رو مثل InnoDB برنمی‌گرداند. قبل از اعتماد به migration یا routine، engine هر table رو بررسی کن.

A business operation spanning multiple tables can be rolled back as one transaction only when the tables and statements support the needed transaction semantics. A MyISAM change is not undone like an InnoDB change. Inspect every table’s engine before trusting a migration or routine.

پیدا کردن engineهای ناسازگارFind non-InnoDB tables
SELECT TABLE_SCHEMA,TABLE_NAME,ENGINE
FROM information_schema.TABLES
WHERE TABLE_TYPE='BASE TABLE'
  AND TABLE_SCHEMA='codenames_engine_lab'
  AND ENGINE <> 'InnoDB';

این query tableهای lab غیر InnoDB رو پیدا می‌کنه؛ روی schema برنامه هم می‌تونی گزارش مشابه بگیری، اما پیش از هر تبدیل باید اندازه، downtime، lock و backup رو برنامه‌ریزی کنی. دستور ALTER TABLE ... ENGINE=InnoDB رو بی‌ارزیابی روی جدول بزرگ اجرا نکن.

This query finds non-InnoDB lab tables. You can report on an application schema similarly, but plan size, downtime, locks, and backups before conversion. Do not run ALTER TABLE ... ENGINE=InnoDB on a large table without assessing impact.

DDL و metadata دو شاهد مکمل‌اندDDL and metadata provide complementary evidence

metadata سریع هست و چند table رو یک‌جا نشان می‌ده؛ SHOW CREATE TABLE تعریف دقیق object رو برای review می‌ده. هر دو رو کنار هم بگیر تا default سرور رو با engine ذخیره‌شدهٔ table اشتباه نکنی.

Metadata quickly reports many tables; SHOW CREATE TABLE gives the exact object definition for review. Use both so you do not confuse the server default with a table’s stored engine.

engine خود table رو تأیید کنVerify the table’s actual engine
SHOW CREATE TABLE txn_row;
SHOW TABLE STATUS FROM codenames_engine_lab LIKE 'txn_row';

SELECT TABLE_NAME,ENGINE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA='codenames_engine_lab'
  AND TABLE_NAME='txn_row';

اگه default سرور رو تغییر داده باشند، tableهای قبلی خودکار migrate نمی‌شوند. ملاک، metadata همان table هست. بعد از هر migration، همان query رو دوباره اجرا کن و نتیجهٔ پس از تغییر رو با baseline مقایسه کن.

Changing the server default does not migrate existing tables. The table’s own metadata is the evidence. After a migration, rerun the same checks and compare them with the baseline.
