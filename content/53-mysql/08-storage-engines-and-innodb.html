Storage Engineها و InnoDB

Storage Engines and InnoDB

یک عملیات مالی نصفه شکست خورده، اما بخشی از تغییرها در جدول مانده است. قبل از اینکه query را مقصر بدانیم، engine هر جدول را می‌خوانیم. در MySQL، انتخاب engine فقط تنظیم ظاهری نیست؛ روی transaction، lock و رفتار بازیابی اثر می‌گذارد.

A financial operation fails halfway, yet some changes remain in a table. Before blaming the query, inspect each table’s engine. In MySQL, an engine is not cosmetic; it affects transactions, locking, and recovery behavior.

پیش‌نیازPrerequisite: فصل ۷ · JSON و ساختار دادهمحیط مرجعLab baseline: MySQL 9.7.2زمانTime: ۸۵ دقیقه · ۱۸ تمرین

ROLLBACK زدیم؛ چرا ردیف باقی ماند؟We rolled back—why is a row still there?

برنامه ابتدا موجودی را کم می‌کند، بعد ردیف سفارش می‌سازد. مرحلهٔ دوم خطا می‌دهد و کد ROLLBACK اجرا می‌کند. موجودی سر جایش برگشته؛ اما سفارش هم انگار ثبت شده. احتمال دارد دو table از دو engine متفاوت باشند. بیایید همین رفتار را در database آزمایشی بازتولید کنیم.

The application decrements inventory, then creates an order. The second step fails and the code runs ROLLBACK. Inventory is restored, but the order seems to remain. The tables may use different engines. Let’s reproduce the behavior in a lab database.

Storage Engine مسئول روش ذخیره و برخی رفتارهای دسترسی به دادهٔ table است. در MySQL 9.7، InnoDB engine پیش‌فرض ساخت table جدید است؛ ولی default را فرض نمی‌کنیم، چون تنظیم Server قابل تغییر است. هر table را جداگانه از metadata بررسی می‌کنیم.

A storage engine controls how a table stores data and some of its access behavior. In MySQL 9.7, InnoDB is the default for new tables, but we do not assume that: a server setting can change. Inspect every table’s metadata.

اول از Server بپرس، بعد از خود tableAsk the server, then inspect the table

یک Server ممکن است engineهای مختلفی پشتیبانی کند. SHOW ENGINES فهرست و وضعیت پشتیبانی را می‌دهد؛ بعد SHOW CREATE TABLE یا information_schema.TABLES engine واقعی object را روشن می‌کند. «پشتیبانی می‌شود» با «برای این table استفاده شده» یکی نیست.

A server may support several engines. SHOW ENGINES lists support; SHOW CREATE TABLE or information_schema.TABLES shows the engine actually used by an object. “Supported” does not mean “used by this table.”

وضعیت engineها و defaultEngine support and default
SHOW ENGINES;
SELECT @@default_storage_engine AS default_engine;

SELECT TABLE_NAME,ENGINE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA=DATABASE()
  AND TABLE_TYPE='BASE TABLE'
ORDER BY TABLE_NAME;

در خروجی به ردیف InnoDB و ستون SUPPORT نگاه کن؛ مقدار DEFAULT در این ستون نشان می‌دهد کدام engine پیش‌فرض است. بعد برای table خودت به ستون ENGINE نگاه کن. view در فهرست base table جای نمی‌گیرد و قرار نیست engine مستقل داشته باشد.

Inspect the InnoDB row and SUPPORT column; DEFAULT identifies the default engine. Then inspect ENGINE for the specific table. A view is not a base table and does not have its own storage engine.

آزمایش rollback را فقط در disposable schema انجام بدهRun the rollback experiment only in a disposable schema

برای مقایسه دو table هم‌شکل می‌سازیم. در transaction روی هر دو ردیف درج می‌کنیم و rollback می‌زنیم. هیچ دادهٔ واقعی در کار نیست. انتظارمان این است که InnoDB تغییر transaction را برگرداند؛ MyISAM transaction ندارد، پس rollback همان ضمانت را نمی‌دهد.

We create two structurally similar tables, insert into both within a transaction, and roll back. No production data is involved. We expect InnoDB to undo transactional changes; MyISAM does not provide that transaction guarantee.

دو engine، یک آزمایشTwo engines, one experiment
CREATE DATABASE IF NOT EXISTS codenames_engine_lab;
USE codenames_engine_lab;
CREATE TABLE txn_row(id INT PRIMARY KEY,note VARCHAR(30)) ENGINE=InnoDB;
CREATE TABLE non_txn_row(id INT PRIMARY KEY,note VARCHAR(30)) ENGINE=MyISAM;
INSERT INTO txn_row VALUES(1,'initial value');

START TRANSACTION;
INSERT INTO txn_row VALUES(2,'rolled back');
INSERT INTO non_txn_row VALUES(1,'engine has no transaction');
ROLLBACK;

SELECT * FROM txn_row WHERE id=2;
SELECT * FROM non_txn_row;

انتظار داریم SELECT اول ردیفی ندهد و SELECT دوم ردیف MyISAM را نشان دهد. این آزمایش را با یک statement جدا برای هر نتیجه اجرا کن تا اگر client روی خطا متوقف شد، برداشت اشتباه نکنی. rollback فقط روی engineهای transaction-aware و تغییرهای داخل همان transaction ضمانت دارد.

The first SELECT should return no row; the second should show the MyISAM row. Run the result checks separately if your client stops on errors. Rollback guarantees apply to transaction-aware engines and changes made within that transaction.

در production این آزمایش را تکرار نکن.MyISAM table دائمی است و rollback تغییرش را پاک نمی‌کند. برای هر آزمایش مخرب، database دورریختنی و نام مشخص لازم است.Do not repeat this on production.The MyISAM table is permanent and rollback does not undo its change. Destructive tests belong in a disposable database with explicit names.

چرا InnoDB انتخاب پیش‌فرض است؟Why is InnoDB the default choice?

InnoDB transaction، foreign key، MVCC و crash recovery دارد. این‌ها برای دادهٔ مهم برنامه رفتار قابل‌اتکاتری فراهم می‌کنند؛ ولی «داشتن recovery» جای backup را نمی‌گیرد و «transaction» هم اشتباه منطقی داخل transaction را خودکار کشف نمی‌کند. اگر برنامه یک مبلغ غلط ولی معتبر commit کند، engine نمی‌فهمد که business rule نقض شده است.

InnoDB provides transactions, foreign keys, MVCC, and crash recovery. These features offer stronger behavior for important application data, but crash recovery does not replace backups, and transactions do not detect logical mistakes. If an application commits a wrong but valid amount, the engine cannot know the business rule was violated.

EngineTransaction / FKLocking model (simplified)Use it only when…
InnoDBYes / YesRow-level locking with MVCC behaviorDefault general-purpose transactional data
MyISAMNo / NoTable-level lockingA specific legacy/read-mostly need has been measured and accepted
MEMORYNo durable rows / No FKTable-level lockingVolatile in-memory table behavior is intentional
Other engineEngine-dependentVerify its documented behaviorThe requirement matches its documented tradeoffs

این خلاصه جای مستندات هر engine نیست. MyISAM هنوز در بعضی نصب‌ها موجود است، اما default نیست؛ MEMORY هم با restart دادهٔ durable نمی‌دهد و نباید جای database اصلی جا زده شود. engine را بر اساس نیاز اندازه‌گیری‌شده انتخاب می‌کنیم، نه نامی که قدیمی یا سریع به نظر می‌رسد.

This summary does not replace each engine’s documentation. MyISAM may still be available but is not the default; MEMORY does not provide durable rows across restart and is not a substitute for the primary database. Choose an engine from measured requirements, not from a name that sounds old or fast.

ترکیب engineها مرز transaction را می‌شکندMixing engines can break the transaction boundary

عملیات business وقتی چند table را تغییر می‌دهد، فقط وقتی یک transaction واحد می‌تواند همه را برگرداند که tableها و statementها با ضمانت transaction سازگار باشند. اگر جدول MyISAM وسط کار تغییر کند، rollback آن را مثل InnoDB برنمی‌گرداند. قبل از اعتماد به migration یا routine، engine هر table را بررسی کن.

A business operation spanning multiple tables can be rolled back as one transaction only when the tables and statements support the needed transaction semantics. A MyISAM change is not undone like an InnoDB change. Inspect every table’s engine before trusting a migration or routine.

پیدا کردن engineهای ناسازگارFind non-InnoDB tables
SELECT TABLE_SCHEMA,TABLE_NAME,ENGINE
FROM information_schema.TABLES
WHERE TABLE_TYPE='BASE TABLE'
  AND TABLE_SCHEMA='codenames_engine_lab'
  AND ENGINE <> 'InnoDB';

این query tableهای lab غیر InnoDB را پیدا می‌کند؛ روی schema برنامه هم می‌توانی گزارش مشابه بگیری، اما پیش از هر تبدیل باید اندازه، downtime، lock و backup را برنامه‌ریزی کنی. دستور ALTER TABLE ... ENGINE=InnoDB را بی‌ارزیابی روی جدول بزرگ اجرا نکن.

This query finds non-InnoDB lab tables. You can report on an application schema similarly, but plan size, downtime, locks, and backups before conversion. Do not run ALTER TABLE ... ENGINE=InnoDB on a large table without assessing impact.

DDL و metadata دو شاهد مکمل‌اندDDL and metadata provide complementary evidence

metadata سریع است و چند table را یک‌جا نشان می‌دهد؛ SHOW CREATE TABLE تعریف دقیق object را برای review می‌دهد. هر دو را کنار هم بگیر تا default سرور را با engine ذخیره‌شدهٔ table اشتباه نکنی.

Metadata quickly reports many tables; SHOW CREATE TABLE gives the exact object definition for review. Use both so you do not confuse the server default with a table’s stored engine.

engine خود table را تأیید کنVerify the table’s actual engine
SHOW CREATE TABLE txn_row;
SHOW TABLE STATUS FROM codenames_engine_lab LIKE 'txn_row';

SELECT TABLE_NAME,ENGINE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA='codenames_engine_lab'
  AND TABLE_NAME='txn_row';

اگر default سرور را تغییر داده باشند، tableهای قبلی خودکار migrate نمی‌شوند. ملاک، metadata همان table است. بعد از هر migration، همان query را دوباره اجرا کن و نتیجهٔ پس از تغییر را با baseline مقایسه کن.

Changing the server default does not migrate existing tables. The table’s own metadata is the evidence. After a migration, rerun the same checks and compare them with the baseline.

۱۸ تمرین SQL18 SQL exercises

همهٔ تغییرهای داده‌ای را داخل codenames_engine_lab انجام بده. تمرین rollback روی جدول MyISAM عمداً اثری باقی می‌گذارد؛ cleanup آن را صریح انجام بده.

Keep data changes inside codenames_engine_lab. The rollback exercise on MyISAM intentionally leaves a row; clean it up explicitly.

1) engine پیش‌فرض را query کن / Query the default engine

default فعلی را پیدا کن.

Find the current default.

SQL / SQL
SELECT @@default_storage_engine;

این مقدار برای table تازه و بدون ENGINE clause مهم است؛ engine table قدیمی را ثابت نمی‌کند.

It matters for a new table without ENGINE; it does not prove an existing table’s engine.

2) پشتیبانی engine را ببین / Inspect engine support

وضعیت InnoDB و MyISAM را از Server بخوان.

Read server support for InnoDB and MyISAM.

SQL / SQL
SHOW ENGINES;

ستون SUPPORT را با default مقایسه کن؛ پشتیبانی با انتخاب table فرق دارد.

Compare SUPPORT with the default; availability differs from a table’s choice.

3) engine دو table را مقایسه کن / Compare two table engines

engine tableهای آزمایش را query کن.

Query the engines of the lab tables.

SQL / SQL
SELECT TABLE_NAME,ENGINE FROM information_schema.TABLES WHERE TABLE_SCHEMA='codenames_engine_lab' AND TABLE_TYPE='BASE TABLE';

هر table را جدا می‌خوانیم؛ یک default مشترک برای همه فرض نمی‌کنیم.

Inspect each table separately; do not assume one default applies to all.

4) rollback روی InnoDB را ثابت کن / Prove InnoDB rollback

یک row آزمایش درج و rollback کن، سپس وجودش را query کن.

Insert a lab row, roll back, and query whether it remains.

SQL / SQL
START TRANSACTION; INSERT INTO txn_row VALUES(2,'temporary'); ROLLBACK; SELECT * FROM txn_row WHERE id=2;

نبود ردیف با rollback transactional سازگار است.

No row is consistent with transactional rollback.

5) rollback روی MyISAM را ببین / Observe MyISAM rollback behavior

یک ردیف محدود درج و rollback کن؛ بعد SELECT و cleanup را اجرا کن.

Insert one bounded row, roll back, then query and clean up.

SQL / SQL
START TRANSACTION; INSERT INTO non_txn_row VALUES(2,'remains'); ROLLBACK; SELECT * FROM non_txn_row WHERE id=2; DELETE FROM non_txn_row WHERE id=2;

ردیف می‌تواند باقی بماند، چون MyISAM transaction نمی‌دهد؛ DELETE پاک‌سازی fixture است.

The row may remain because MyISAM is nontransactional; DELETE cleans the fixture.

6) query چند table را audit کن / Audit all tables involved

engine همهٔ tableهای یک database آزمایشی را فهرست کن.

List engines for every base table in a lab database.

SQL / SQL
SELECT TABLE_NAME,ENGINE FROM information_schema.TABLES WHERE TABLE_SCHEMA='codenames_engine_lab' AND TABLE_TYPE='BASE TABLE' ORDER BY TABLE_NAME;

اگر یک عملیات چند table را تغییر می‌دهد، همهٔ آن‌ها را بررسی کن.

If an operation updates multiple tables, inspect every one.

7) table definition را بخوان / Read the table definition

DDL table InnoDB را ثبت کن.

Record the InnoDB table DDL.

SQL / SQL
SHOW CREATE TABLE txn_row;

ENGINE clause، constraints و نوع table را می‌بینی.

Inspect the ENGINE clause, constraints, and table definition.

8) وضعیت ذخیره‌سازی را query کن / Query table status

engine و آمار table را از SHOW TABLE STATUS بخوان.

Read engine and table status information.

SQL / SQL
SHOW TABLE STATUS FROM codenames_engine_lab LIKE 'txn_row';

آمار می‌تواند تقریبی یا وابسته به engine باشد؛ تعریف engine را با این عددها یکی نکن.

Statistics can be approximate or engine-dependent; do not confuse them with engine identity.

9) foreign key را روی InnoDB بساز / Add a foreign key on InnoDB

دو table disposable بساز و FK را اجرا کن.

Create two disposable tables and add a foreign key.

SQL / SQL
CREATE TABLE parent_lab(id INT PRIMARY KEY) ENGINE=InnoDB; CREATE TABLE child_lab(id INT PRIMARY KEY,parent_id INT,CONSTRAINT fk_child_parent FOREIGN KEY(parent_id) REFERENCES parent_lab(id)) ENGINE=InnoDB;

هر دو engine سازگارند و کلید والد وجود دارد؛ نتیجه را با SHOW CREATE TABLE بخوان.

Both engines support the relation and the parent key exists; verify with SHOW CREATE TABLE.

10) insert یتیم را رد کن / Reject an orphan row

child با parent ناموجود درج و خطا را ثبت کن.

Insert a child with a missing parent and record the error.

SQL / SQL
INSERT INTO child_lab VALUES(1,999);

FK در InnoDB باید جلوی نقض رابطه را بگیرد.

The InnoDB foreign key should reject the invalid relationship.

11) MEMORY را با دوام اشتباه نگیر / Do not equate MEMORY with durability

جدول MEMORY بساز، یک ردیف درج کن و engine را از metadata بررسی کن؛ restart سرور را روی محیط واقعی انجام نده.

Create a MEMORY table, insert a row, and inspect its engine; do not restart a real server for this exercise.

SQL / SQL
CREATE TABLE memory_lab(id INT PRIMARY KEY) ENGINE=MEMORY; INSERT INTO memory_lab VALUES(1); SELECT TABLE_NAME,ENGINE FROM information_schema.TABLES WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='memory_lab';

وجود row در همین نشست دوام پس از restart را ثابت نمی‌کند؛ MEMORY برای دادهٔ durable جایگزین InnoDB نیست.

A row now does not prove durability across restart; MEMORY is not a durable replacement for InnoDB.

12) table قدیمی از default پیروی نمی‌کند / Existing tables do not follow a new default

default نشست را موقت تغییر بده، table بدون ENGINE بساز و engineاش را بخوان؛ سپس table آزمایشی را حذف کن.

Change the session default, create a table without ENGINE, inspect it, then remove the test table.

SQL / SQL
SET SESSION default_storage_engine=InnoDB; CREATE TABLE default_probe(id INT); SELECT ENGINE FROM information_schema.TABLES WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='default_probe'; DROP TABLE default_probe;

تنظیم session روی ساخت جدید اثر دارد؛ tableهای قبلی را تبدیل نمی‌کند.

The session setting affects new tables; it does not convert existing ones.

13) تفاوت MyISAM را از metadata تأیید کن / Verify MyISAM’s capabilities

متادیتای engine را برای جدول MyISAM با SHOW ENGINES بخوان.

Inspect MyISAM engine capabilities using SHOW ENGINES.

SQL / SQL
SHOW ENGINES;

از ردیف MyISAM پشتیبانی transaction و FK را بررسی کن؛ اطلاعات را برای نسخهٔ سرور خودت ثبت کن.

Check transaction and FK support for MyISAM and record the server’s own output.

14) engineهای nontransactional را پیدا کن / Find nontransactional tables

یک query بنویس که tableهای غیر InnoDB را در lab پیدا کند.

Write a query finding non-InnoDB tables in the lab.

SQL / SQL
SELECT TABLE_NAME,ENGINE FROM information_schema.TABLES WHERE TABLE_SCHEMA='codenames_engine_lab' AND TABLE_TYPE='BASE TABLE' AND ENGINE<>'InnoDB';

این فهرست نقطهٔ شروع audit است، نه به‌تنهایی حکم تبدیل table.

This list starts an audit; it is not by itself a mandate to convert tables.

15) یک backup policy را با engine بسنج / Assess backup implications

engine tableهای lab را query کن و یک گزارش SQL بساز که تعداد tableها را برحسب engine می‌شمارد.

Query lab engines and report table counts grouped by engine.

SQL / SQL
SELECT ENGINE,COUNT(*) AS table_count FROM information_schema.TABLES WHERE TABLE_SCHEMA='codenames_engine_lab' AND TABLE_TYPE='BASE TABLE' GROUP BY ENGINE;

ترکیب engineها می‌تواند روش backup و consistency را پیچیده کند؛ برنامهٔ backup باید ابزارش را جدا ارزیابی کند.

Mixed engines can complicate backup consistency; assess the backup tool separately.

16) تبدیل را کورکورانه اجرا نکن / Inspect before conversion

پیش از تبدیل non_txn_row، table و engine فعلی را با دو شاهد بخوان؛ دستور تبدیل را فقط در گزارش بنویس و اجرا نکن.

Before converting non_txn_row, inspect its definition and metadata; write but do not run the conversion.

SQL / SQL
SHOW CREATE TABLE non_txn_row; SELECT TABLE_NAME,ENGINE FROM information_schema.TABLES WHERE TABLE_SCHEMA='codenames_engine_lab' AND TABLE_NAME='non_txn_row';

تبدیل می‌تواند زمان‌بر و پراثر باشد؛ backup، حجم، constraintها و downtime باید پیش از اجرا بررسی شوند.

Conversion can be expensive; assess backups, size, constraints, and downtime first.

17) اثر engine بر عملیات دو-table را تحلیل کن / Diagnose a two-table operation

در query قابل‌اجرا engine دو table رابطه را گزارش کن و FK موجود را inspect کن.

Write runnable checks reporting both table engines and inspect the foreign key.

SQL / SQL
SELECT TABLE_NAME,ENGINE FROM information_schema.TABLES WHERE TABLE_SCHEMA='codenames_engine_lab' AND TABLE_NAME IN ('parent_lab','child_lab'); SHOW CREATE TABLE child_lab;

اگر engineها فرق دارند، فرض transaction اتمیک روی هر دو را بدون بررسی نپذیر.

If engines differ, do not assume one atomic transaction covers both without checking.

18) گزارش تصمیم Engine را تحویل بده / Submit an engine decision

یک table تمرینی را بساز، engine را صریح تعیین کن، سپس با metadata و رفتار rollback تصمیم را ثابت کن.

Create a lab table with an explicit engine, then support the choice with metadata and a rollback test.

نمونهٔ SQL / Example SQL
CREATE TABLE decision_probe(id INT PRIMARY KEY,note VARCHAR(40)) ENGINE=InnoDB; SELECT TABLE_NAME,ENGINE FROM information_schema.TABLES WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='decision_probe'; START TRANSACTION; INSERT INTO decision_probe VALUES(1,'test'); ROLLBACK; SELECT * FROM decision_probe;

DDL و دو query آخر به‌ترتیب انتخاب و رفتار transaction را نشان می‌دهند؛ هیچ‌کدام backup یا correctness business را ثابت نمی‌کنند.

The DDL and final checks show the choice and transaction behavior; neither proves backup quality or business correctness.

قبل از index، باید بستر table را بشناسیمUnderstand the table’s foundation before its indexes

حالا می‌دانی یک Server چند engine دارد، default با engine یک table یکی نیست و rollback فقط وقتی کار می‌کند که storage از آن پشتیبانی کند. فصل بعد وارد ساختار index در InnoDB می‌شویم؛ همان‌جا تصمیم‌های این فصل را روی layout واقعی index دنبال می‌کنیم.

You now know that one server can offer multiple engines, the default is not the same as a table’s engine, and rollback depends on engine support. Next we’ll inspect InnoDB index layout and follow these choices into the physical index structure.
