B+ Tree و index پایه

B+ Trees and Basic Indexes

گزارش کالاها بزرگ شده و هر بار پیدا کردن یک SKU زمان می‌برد. تیم می‌گه «روی ستون index بگذاریم و تمام». اما کدام index؟ آیا برای هر query مفید است؟ یک جدول کوچک می‌سازیم، مسیر جست‌وجو رو رسم می‌کنیم و با EXPLAIN فرقِ ساختار قابل‌استفاده و انتخاب واقعی optimizer رو می‌سنجیم.

The product report has grown, and finding an SKU takes longer than it used to. Someone says, “Add an index to the column and we’re done.” Which index? Does it help every query? We will build a small table, trace the search path, and use EXPLAIN to distinguish a usable structure from the optimizer’s actual choice.

پیش‌نیازPrerequisite: فصل ۹ · clustered و secondary indexمحیط مرجعReference environment: MySQL 9.7 · InnoDBزمانTime: ۸۵ دقیقه · ۱۸ تمرین

اول سؤال رو دقیق کنیمStart by making the question precise

فرض کن دنبال محصولی با SKU برابر SKU-0042 می‌گردی. بدون index، MySQL ممکنه ردیف‌ها رو یکی‌یکی بررسی کند. با index هم قرار نیست جادو شود: باید از ساختار index به نقطهٔ درست برسد، و شاید برای ستون‌های دیگر به خود ردیف مراجعه کند. پیش از ساخت index حدس بزن مسیر کدام هست.

Suppose you need the product whose SKU is SKU-0042. Without a suitable index, MySQL may examine rows one by one. An index is not magic: the engine must navigate to the right place, and it may still need to visit the row for other columns. Predict the path before creating anything.

در فصل ۹ دیدیم InnoDB ردیف‌ها رو در clustered index نگه می‌دارد و secondary index ورودی‌هایی دارد که به کلید اصلی وصل می‌شوند. اینجا جزئیات همان مسیر رو دوباره از اول درس نمی‌دیم؛ یک لایه عقب‌تر می‌ریم: خود درخت مرتب چه قابلیت‌هایی به query می‌ده؟

Chapter 9 showed that InnoDB stores rows in the clustered index and that secondary-index entries lead through the primary key. We will not reteach that path. We are stepping back one layer: what can a sorted tree structure do for a query?

محیط مستقل این فصلAn isolated fixture for this chapter
CREATE DATABASE IF NOT EXISTS codenames_btree_lab;
USE codenames_btree_lab;

DROP TABLE IF EXISTS products;
CREATE TABLE products (
  product_id BIGINT NOT NULL,
  sku VARCHAR(16) NOT NULL,
  category_id INT NOT NULL,
  price DECIMAL(8,2) NOT NULL,
  product_name VARCHAR(80) NOT NULL,
  PRIMARY KEY (product_id),
  UNIQUE KEY uq_products_sku (sku)
) ENGINE=InnoDB;

INSERT INTO products VALUES
(10,'SKU-0010',1,12.50,'Notebook'),
(20,'SKU-0020',1,18.00,'Blue pen'),
(30,'SKU-0030',2,45.00,'Desk lamp'),
(40,'SKU-0040',2,45.00,'Reading light'),
(50,'SKU-0050',3,79.00,'Travel mug'),
(60,'SKU-0060',3,120.00,'Backpack'),
(70,'SKU-0070',1,8.00,'Pencil'),
(80,'SKU-0080',2,35.00,'Cable organizer');

این fixture عمداً کوچک هست تا جواب‌ها رو راحت ببینی؛ اندازه‌اش برای نتیجه‌گیری دربارهٔ performance واقعی کافی نیست. همچنین sku همین حالا به‌خاطر UNIQUE KEY index دارد. قبل از آزمایش آن رو دوباره نساز.

This fixture is intentionally small so results are easy to inspect; it is not large enough for real performance conclusions. Also, sku is already indexed by its UNIQUE KEY. Do not create a duplicate index for the lab.

B+ Tree رو مثل فهرست مرتب بخوانRead a B+ tree as an ordered directory

درخت رو مثل دفتر تلفن مرتب تصور کن: به‌جای اینکه همهٔ نام‌ها رو از ابتدا بخوانی، از صفحه‌های راهنما پایین می‌روی تا به محدودهٔ مناسب برسی. در B+ Tree، صفحه‌های داخلی راه رو انتخاب می‌کنن و ورودی‌های برگ (leaf) داده‌های مرتب index رو نگه می‌دارن. leafها به هم پیوند دارن؛ پس بعد از پیدا کردن ابتدای یک بازه، پیمایش چند مقدار بعدی طبیعی هست.

Think of a tree like an ordered directory: rather than reading every name from the beginning, you follow guide pages into the right range. In a B+ tree, internal pages direct the search and leaf pages hold ordered index entries. Leaf pages are linked, so scanning forward from the beginning of a range is natural.

این شکل دلیل مهمی رو نشان می‌ده: یک ساختار مرتب فقط برای = نیست. جست‌وجوی بازه، مقایسه‌های بزرگ‌تر/کوچک‌تر، مرتب‌سازی سازگار با ترتیب index و بعضی جست‌وجوهای prefix هم می‌تونن از ترتیب استفاده کنند. اینکه optimizer واقعاً index رو انتخاب کند، سؤال جداگانه‌ای هست.

The diagram explains an important point: an ordered structure is useful beyond =. Range comparisons, compatible ordering, and some prefix searches can use that order. Whether the optimizer actually chooses the index is a separate question.

index رو از روی query موجود بسازیمBuild an index from a real query

SKU انتخابی هست چون پیدا کردن یک SKU مشخص، نیاز واقعی و روشن هست. اما fixture همین حالا index یکتا دارد. اول تعریف و plan رو بخوان؛ بعد با ستون بدون index یک مقایسهٔ کنترل‌شده بساز.

SKU is a good starting point because looking up one known SKU is a clear requirement. But the fixture already has a unique index. Inspect its definition and plan, then create a controlled comparison using an unindexed column.

تعریف index و plan queryInspect the index definition and query plan
SHOW INDEX FROM products;
EXPLAIN SELECT product_id, sku, product_name
FROM products
WHERE sku = 'SKU-0040';

در EXPLAIN، possible_keys فهرست گزینه‌هایی هست که optimizer می‌تونه در نظر بگیره؛ key index انتخاب‌شده هست. مقدارهای دقیق rows و حتی انتخاب plan با نسخه، آمار و اندازهٔ داده عوض می‌شوند. روی جدول هشت‌ردیفی ممکنه full scan ارزان‌تر برآورد شود؛ این به‌تنهایی نشانهٔ خراب‌بودن index نیست.

In EXPLAIN, possible_keys lists candidates the optimizer could consider; key is the chosen index. Exact rows estimates and even plan choice vary with version, statistics, and data size. On an eight-row table, a full scan may be estimated cheaper; that alone does not mean the index is broken.

یک index آزمایشی با نیاز دومAdd a test index for a second query
CREATE INDEX ix_products_category ON products(category_id);
SHOW INDEX FROM products;

EXPLAIN SELECT product_id, category_id, product_name
FROM products
WHERE category_id = 2;

یک index مرتب‌شده کپی‌ای از مقدار ستون و ارجاع لازم برای رسیدن به ردیف رو نگه می‌دارد. در InnoDB این طراحی با clustered key گره می‌خورد؛ جزئیات رو در فصل ۹ دیدیم. هزینه‌اش هم واقعی هست: insert/update/delete باید index رو به‌روز کند، فضا می‌گیره و optimizer باید میان گزینه‌ها تصمیم بگیره.

An ordered index stores copies of column values and the reference needed to reach rows. In InnoDB, that design interacts with the clustered key, covered in Chapter 9. It also has real costs: inserts, updates, and deletes maintain it, it consumes space, and the optimizer must choose among candidates.

ترتیب به چه شرطی قابل‌استفاده است؟When can the order help?

مقایسهٔ مستقیم معمولاً مسیر روشنی می‌ده. prefix ثابت هم می‌تونه بازه‌ای از مقادیر مرتب رو مشخص کند. اما وقتی روی هر ردیف تابعی اجرا می‌کنی، یا wildcard ابتدای pattern است، همان ترتیب ساده دیگر لزوماً راهنمای جست‌وجو نیست. تفاوت رو با plan ببین، نه با قانون حفظی.

A direct comparison usually gives the optimizer a clear path. A fixed prefix can also describe a range of ordered values. But applying a function to every row, or starting a pattern with a wildcard, no longer gives the same straightforward navigation. Compare plans instead of memorizing a slogan.

سه شکل predicate رو با هم مقایسه کنCompare three predicate forms
EXPLAIN SELECT product_id FROM products WHERE sku = 'SKU-0040';
EXPLAIN SELECT product_id FROM products WHERE sku LIKE 'SKU-00%';
EXPLAIN SELECT product_id FROM products WHERE sku LIKE '%0040';

pattern اول از ابتدای رشته شروع می‌شه؛ محدوده‌ای پیوسته در ترتیب index قابل تصور هست. pattern آخر از ابتدا چیزی معلوم نمی‌کنه، پس range شروع مشخصی ندارد. با این حال optimizer ممکنه به‌خاطر جدول بسیار کوچک هرکدام رو scan کند. plan روی دادهٔ آموزشی حکم عمومی برای production نیست.

The first pattern begins at the start of the string, so it can describe a contiguous range in index order. The last pattern gives no known starting prefix and therefore no obvious range start. Still, on a tiny table the optimizer may scan for any of them. A lab plan is not a universal production verdict.

تابع روی ستون رو از مقایسهٔ مستقیم جدا کنSeparate a function-wrapped column from a direct comparison
EXPLAIN SELECT product_id FROM products WHERE sku = 'SKU-0040';
EXPLAIN SELECT product_id FROM products WHERE LOWER(sku) = 'sku-0040';

در query دوم دیگر شرط مستقیم روی مقدار indexشده نداریم؛ موتور باید اثر LOWER رو در نظر بگیره. بعضی نسخه‌ها و طراحی‌ها می‌تونن با functional index یا generated column راهی بسازند، اما آن بحث فصل ۱۵ هست. فعلاً query رو بی‌جهت بازنویسی نکن: collation ممکنه از قبل مقایسهٔ بدون حساسیت به بزرگی حروف انجام دهد؛ SHOW FULL COLUMNS و collation رو هم بررسی کن.

The second query no longer compares the indexed value directly; the engine must account for LOWER. Some versions and designs can support this through a functional index or generated column, covered in Chapter 15. Do not rewrite blindly: the column’s collation may already be case-insensitive. Inspect it with SHOW FULL COLUMNS and check the collation.

از index انتظار ترتیبِ تضمین‌شده نداشته باشDo not assume an index guarantees result order

درخت مرتب است، ولی خروجی SQL بدون ORDER BY ترتیب قراردادی ندارد. Optimizer ممکنه امروز index بخواند و فردا با آمار تازه مسیر دیگری انتخاب کند. اگه برنامه به ترتیب نیاز دارد، آن رو در query درخواست کن.

The tree is ordered, but SQL does not promise result order without ORDER BY. The optimizer may read an index today and choose another path after statistics change. If the application needs ordering, ask for it in the query.

ترتیب رو صریح و کامل کنRequest a deterministic order
SELECT product_id, price, product_name
FROM products
ORDER BY price, product_id;

EXPLAIN SELECT product_id, price, product_name
FROM products
ORDER BY price, product_id;

اکنون جواب query ترتیب مشخص دارد؛ plan فقط توضیح می‌ده موتور چگونه آن رو به دست می‌آورد. شاید sort کند، شاید از index مناسب استفاده کند. برای نتیجهٔ پایدار در میان قیمت‌های برابر، کلید دوم لازم است؛ ستون یکتا ambiguity رو می‌بندد.

The query now has a defined result order; the plan only explains how the engine obtains it. It may sort, or use a suitable index. A second key makes ties deterministic; a unique column removes ambiguity.

چه چیزی رو EXPLAIN ثابت نمی‌کنه؟What EXPLAIN does not prove

EXPLAIN پیش‌بینی optimizer از اجرای query است، نه stopwatch و نه آزمایش روی حجم واقعی. key می‌گه کدام index انتخاب شده، اما ثابت نمی‌کنه پاسخ سریع‌تر هست. rows تخمین است، نه شمارش تضمین‌شده. برای اندازه‌گیری باید دادهٔ نماینده، warm/cold cache قابل‌کنترل، چند اجرای تکراری و هزینهٔ نوشتن رو هم در نظر بگیریم؛ موضوع فصل‌های plan و tuning هست.

EXPLAIN is the optimizer’s plan, not a stopwatch or a test at production scale. key says which index was selected, not that the result is faster. rows is an estimate, not a guaranteed count. Measurement needs representative data, controlled cache conditions, repeated runs, and write-cost context; later plan and tuning chapters cover that work.

index بیشتر همیشه بهتر نیست.More indexes are not always better.

هر index فضای storage و کار نوشتن اضافه می‌کنه. اگه workload queryهای خواندن و نوشتن دارد، قبل/بعد رو روی همان workload بسنج؛ index رو فقط چون یک ستون «مهم به نظر می‌رسه» اضافه نکن.

Each index consumes storage and adds write work. If the workload includes reads and writes, measure before and after on that workload; do not index a column just because it “looks important.”
