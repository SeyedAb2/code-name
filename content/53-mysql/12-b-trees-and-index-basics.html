B+ Tree و index پایه

B+ Trees and Basic Indexes

گزارش کالاها بزرگ شده و هر بار پیدا کردن یک SKU زمان می‌برد. تیم می‌گوید «روی ستون index بگذاریم و تمام». اما کدام index؟ آیا برای هر query مفید است؟ یک جدول کوچک می‌سازیم، مسیر جست‌وجو را رسم می‌کنیم و با EXPLAIN فرقِ ساختار قابل‌استفاده و انتخاب واقعی optimizer را می‌سنجیم.

The product report has grown, and finding an SKU takes longer than it used to. Someone says, “Add an index to the column and we’re done.” Which index? Does it help every query? We will build a small table, trace the search path, and use EXPLAIN to distinguish a usable structure from the optimizer’s actual choice.

پیش‌نیازPrerequisite: فصل ۹ · clustered و secondary indexمحیط مرجعReference environment: MySQL 9.7 · InnoDBزمانTime: ۸۵ دقیقه · ۱۸ تمرین

اول سؤال را دقیق کنیمStart by making the question precise

فرض کن دنبال محصولی با SKU برابر SKU-0042 می‌گردی. بدون index، MySQL ممکن است ردیف‌ها را یکی‌یکی بررسی کند. با index هم قرار نیست جادو شود: باید از ساختار index به نقطهٔ درست برسد، و شاید برای ستون‌های دیگر به خود ردیف مراجعه کند. پیش از ساخت index حدس بزن مسیر کدام است.

Suppose you need the product whose SKU is SKU-0042. Without a suitable index, MySQL may examine rows one by one. An index is not magic: the engine must navigate to the right place, and it may still need to visit the row for other columns. Predict the path before creating anything.

در فصل ۹ دیدیم InnoDB ردیف‌ها را در clustered index نگه می‌دارد و secondary index ورودی‌هایی دارد که به کلید اصلی وصل می‌شوند. اینجا جزئیات همان مسیر را دوباره از اول درس نمی‌دهیم؛ یک لایه عقب‌تر می‌رویم: خود درخت مرتب چه قابلیت‌هایی به query می‌دهد؟

Chapter 9 showed that InnoDB stores rows in the clustered index and that secondary-index entries lead through the primary key. We will not reteach that path. We are stepping back one layer: what can a sorted tree structure do for a query?

محیط مستقل این فصلAn isolated fixture for this chapter
CREATE DATABASE IF NOT EXISTS codenames_btree_lab;
USE codenames_btree_lab;

DROP TABLE IF EXISTS products;
CREATE TABLE products (
  product_id BIGINT NOT NULL,
  sku VARCHAR(16) NOT NULL,
  category_id INT NOT NULL,
  price DECIMAL(8,2) NOT NULL,
  product_name VARCHAR(80) NOT NULL,
  PRIMARY KEY (product_id),
  UNIQUE KEY uq_products_sku (sku)
) ENGINE=InnoDB;

INSERT INTO products VALUES
(10,'SKU-0010',1,12.50,'Notebook'),
(20,'SKU-0020',1,18.00,'Blue pen'),
(30,'SKU-0030',2,45.00,'Desk lamp'),
(40,'SKU-0040',2,45.00,'Reading light'),
(50,'SKU-0050',3,79.00,'Travel mug'),
(60,'SKU-0060',3,120.00,'Backpack'),
(70,'SKU-0070',1,8.00,'Pencil'),
(80,'SKU-0080',2,35.00,'Cable organizer');

SHOW INDEX FROM products;

این fixture عمداً کوچک است تا جواب‌ها را راحت ببینی؛ اندازه‌اش برای نتیجه‌گیری دربارهٔ performance واقعی کافی نیست. همچنین sku همین حالا به‌خاطر UNIQUE KEY index دارد. قبل از آزمایش آن را دوباره نساز.

This fixture is intentionally small so results are easy to inspect; it is not large enough for real performance conclusions. Also, sku is already indexed by its UNIQUE KEY. Do not create a duplicate index for the lab.

B+ Tree را مثل فهرست مرتب بخوانRead a B+ tree as an ordered directory

درخت را مثل دفتر تلفن مرتب تصور کن: به‌جای اینکه همهٔ نام‌ها را از ابتدا بخوانی، از صفحه‌های راهنما پایین می‌روی تا به محدودهٔ مناسب برسی. در B+ Tree، صفحه‌های داخلی راه را انتخاب می‌کنند و ورودی‌های برگ (leaf) داده‌های مرتب index را نگه می‌دارند. leafها به هم پیوند دارند؛ پس بعد از پیدا کردن ابتدای یک بازه، پیمایش چند مقدار بعدی طبیعی است.

Think of a tree like an ordered directory: rather than reading every name from the beginning, you follow guide pages into the right range. In a B+ tree, internal pages direct the search and leaf pages hold ordered index entries. Leaf pages are linked, so scanning forward from the beginning of a range is natural.

این شکل دلیل مهمی را نشان می‌دهد: یک ساختار مرتب فقط برای = نیست. جست‌وجوی بازه، مقایسه‌های بزرگ‌تر/کوچک‌تر، مرتب‌سازی سازگار با ترتیب index و بعضی جست‌وجوهای prefix هم می‌توانند از ترتیب استفاده کنند. اینکه optimizer واقعاً index را انتخاب کند، سؤال جداگانه‌ای است.

The diagram explains an important point: an ordered structure is useful beyond =. Range comparisons, compatible ordering, and some prefix searches can use that order. Whether the optimizer actually chooses the index is a separate question.

index را از روی query موجود بسازیمBuild an index from a real query

SKU انتخابی است چون پیدا کردن یک SKU مشخص، نیاز واقعی و روشن است. اما fixture همین حالا index یکتا دارد. اول تعریف و plan را بخوان؛ بعد با ستون بدون index یک مقایسهٔ کنترل‌شده بساز.

SKU is a good starting point because looking up one known SKU is a clear requirement. But the fixture already has a unique index. Inspect its definition and plan, then create a controlled comparison using an unindexed column.

تعریف index و plan queryInspect the index definition and query plan
SHOW INDEX FROM products;
EXPLAIN SELECT product_id, sku, product_name
FROM products
WHERE sku = 'SKU-0040';

در EXPLAIN، possible_keys فهرست گزینه‌هایی است که optimizer می‌تواند در نظر بگیرد؛ key index انتخاب‌شده است. مقدارهای دقیق rows و حتی انتخاب plan با نسخه، آمار و اندازهٔ داده عوض می‌شوند. روی جدول هشت‌ردیفی ممکن است full scan ارزان‌تر برآورد شود؛ این به‌تنهایی نشانهٔ خراب‌بودن index نیست.

In EXPLAIN, possible_keys lists candidates the optimizer could consider; key is the chosen index. Exact rows estimates and even plan choice vary with version, statistics, and data size. On an eight-row table, a full scan may be estimated cheaper; that alone does not mean the index is broken.

یک index آزمایشی با نیاز دومAdd a test index for a second query
CREATE INDEX ix_products_category ON products(category_id);
SHOW INDEX FROM products;

EXPLAIN SELECT product_id, category_id, product_name
FROM products
WHERE category_id = 2;

یک index مرتب‌شده کپی‌ای از مقدار ستون و ارجاع لازم برای رسیدن به ردیف را نگه می‌دارد. در InnoDB این طراحی با clustered key گره می‌خورد؛ جزئیات را در فصل ۹ دیدیم. هزینه‌اش هم واقعی است: insert/update/delete باید index را به‌روز کند، فضا می‌گیرد و optimizer باید میان گزینه‌ها تصمیم بگیرد.

An ordered index stores copies of column values and the reference needed to reach rows. In InnoDB, that design interacts with the clustered key, covered in Chapter 9. It also has real costs: inserts, updates, and deletes maintain it, it consumes space, and the optimizer must choose among candidates.

ترتیب به چه شرطی قابل‌استفاده است؟When can the order help?

مقایسهٔ مستقیم معمولاً مسیر روشنی می‌دهد. prefix ثابت هم می‌تواند بازه‌ای از مقادیر مرتب را مشخص کند. اما وقتی روی هر ردیف تابعی اجرا می‌کنی، یا wildcard ابتدای pattern است، همان ترتیب ساده دیگر لزوماً راهنمای جست‌وجو نیست. تفاوت را با plan ببین، نه با قانون حفظی.

A direct comparison usually gives the optimizer a clear path. A fixed prefix can also describe a range of ordered values. But applying a function to every row, or starting a pattern with a wildcard, no longer gives the same straightforward navigation. Compare plans instead of memorizing a slogan.

سه شکل predicate را با هم مقایسه کنCompare three predicate forms
EXPLAIN SELECT product_id FROM products WHERE sku = 'SKU-0040';
EXPLAIN SELECT product_id FROM products WHERE sku LIKE 'SKU-00%';
EXPLAIN SELECT product_id FROM products WHERE sku LIKE '%0040';

pattern اول از ابتدای رشته شروع می‌شود؛ محدوده‌ای پیوسته در ترتیب index قابل تصور است. pattern آخر از ابتدا چیزی معلوم نمی‌کند، پس range شروع مشخصی ندارد. با این حال optimizer ممکن است به‌خاطر جدول بسیار کوچک هرکدام را scan کند. plan روی دادهٔ آموزشی حکم عمومی برای production نیست.

The first pattern begins at the start of the string, so it can describe a contiguous range in index order. The last pattern gives no known starting prefix and therefore no obvious range start. Still, on a tiny table the optimizer may scan for any of them. A lab plan is not a universal production verdict.

تابع روی ستون را از مقایسهٔ مستقیم جدا کنSeparate a function-wrapped column from a direct comparison
EXPLAIN SELECT product_id FROM products WHERE sku = 'SKU-0040';
EXPLAIN SELECT product_id FROM products WHERE LOWER(sku) = 'sku-0040';

در query دوم دیگر شرط مستقیم روی مقدار indexشده نداریم؛ موتور باید اثر LOWER را در نظر بگیرد. بعضی نسخه‌ها و طراحی‌ها می‌توانند با functional index یا generated column راهی بسازند، اما آن بحث فصل ۱۵ است. فعلاً query را بی‌جهت بازنویسی نکن: collation ممکن است از قبل مقایسهٔ بدون حساسیت به بزرگی حروف انجام دهد؛ SHOW FULL COLUMNS و collation را هم بررسی کن.

The second query no longer compares the indexed value directly; the engine must account for LOWER. Some versions and designs can support this through a functional index or generated column, covered in Chapter 15. Do not rewrite blindly: the column’s collation may already be case-insensitive. Inspect it with SHOW FULL COLUMNS and check the collation.

از index انتظار ترتیبِ تضمین‌شده نداشته باشDo not assume an index guarantees result order

درخت مرتب است، ولی خروجی SQL بدون ORDER BY ترتیب قراردادی ندارد. Optimizer ممکن است امروز index بخواند و فردا با آمار تازه مسیر دیگری انتخاب کند. اگر برنامه به ترتیب نیاز دارد، آن را در query درخواست کن.

The tree is ordered, but SQL does not promise result order without ORDER BY. The optimizer may read an index today and choose another path after statistics change. If the application needs ordering, ask for it in the query.

ترتیب را صریح و کامل کنRequest a deterministic order
SELECT product_id, price, product_name
FROM products
ORDER BY price, product_id;

EXPLAIN SELECT product_id, price, product_name
FROM products
ORDER BY price, product_id;

اکنون جواب query ترتیب مشخص دارد؛ plan فقط توضیح می‌دهد موتور چگونه آن را به دست می‌آورد. شاید sort کند، شاید از index مناسب استفاده کند. برای نتیجهٔ پایدار در میان قیمت‌های برابر، کلید دوم لازم است؛ ستون یکتا ambiguity را می‌بندد.

The query now has a defined result order; the plan only explains how the engine obtains it. It may sort, or use a suitable index. A second key makes ties deterministic; a unique column removes ambiguity.

چه چیزی را EXPLAIN ثابت نمی‌کند؟What EXPLAIN does not prove

EXPLAIN پیش‌بینی optimizer از اجرای query است، نه stopwatch و نه آزمایش روی حجم واقعی. key می‌گوید کدام index انتخاب شده، اما ثابت نمی‌کند پاسخ سریع‌تر است. rows تخمین است، نه شمارش تضمین‌شده. برای اندازه‌گیری باید دادهٔ نماینده، warm/cold cache قابل‌کنترل، چند اجرای تکراری و هزینهٔ نوشتن را هم در نظر بگیریم؛ موضوع فصل‌های plan و tuning است.

EXPLAIN is the optimizer’s plan, not a stopwatch or a test at production scale. key says which index was selected, not that the result is faster. rows is an estimate, not a guaranteed count. Measurement needs representative data, controlled cache conditions, repeated runs, and write-cost context; later plan and tuning chapters cover that work.

index بیشتر همیشه بهتر نیست.More indexes are not always better.

هر index فضای storage و کار نوشتن اضافه می‌کند. اگر workload queryهای خواندن و نوشتن دارد، قبل/بعد را روی همان workload بسنج؛ index را فقط چون یک ستون «مهم به نظر می‌رسد» اضافه نکن.

Each index consumes storage and adds write work. If the workload includes reads and writes, measure before and after on that workload; do not index a column just because it “looks important.”

۱۸ تمرین اجرایی18 runnable exercises

همهٔ تمرین‌ها را در schema مستقل codenames_btree_lab اجرا کن. fixture هشت ردیف دارد؛ جواب query را می‌شود دید، اما plan و سرعت آن را به production تعمیم نده. هر جواب باید یک query یا تغییر SQL و مدرک قابل‌مشاهده داشته باشد.

Run the exercises in the isolated codenames_btree_lab schema. The fixture has eight rows: results are inspectable, but its plans and speed do not generalize to production. Every solution includes SQL work and observable evidence.

۱) آیا sku index دارد؟ / Is sku indexed?

با metadata ثابت کن آیا ساخت index دیگری لازم است یا نه.

Use metadata to prove whether another index is needed.

SQL و نتیجه / SQL and reading
SHOW INDEX FROM products WHERE Column_name = 'sku';

یک ردیف با نام uq_products_sku می‌بینی؛ ایجاد index تکراری فقط هزینه می‌سازد.

You should see uq_products_sku; a duplicate index would only add cost.

۲) یکتایی SKU را آزمایش کن / Test SKU uniqueness

در fixture تلاش کن SKU تکراری وارد کنی و خطا را بخوان. بعد وضعیت ردیف اصلی را query کن.

Attempt a duplicate SKU, inspect the error, then query the original row.

SQL / SQL
INSERT INTO products VALUES (90,'SKU-0040',9,1.00,'duplicate test');
SELECT product_id, sku FROM products WHERE sku='SKU-0040';

INSERT به‌خاطر unique index رد می‌شود و ردیف id=40 باقی می‌ماند. در محیطی که client پس از خطا متوقف می‌شود، SELECT را جداگانه اجرا کن.

The unique index rejects the INSERT, leaving id 40 intact. If your client stops after an error, run the SELECT separately.

۳) مسیر query دقیق را ببین / Inspect the exact lookup

برای SKU-0030 plan بگیر و ستون‌های possible_keys و key را ثبت کن.

Explain the SKU-0030 lookup and record possible_keys and key.

SQL / SQL
EXPLAIN SELECT product_id, product_name
FROM products WHERE sku='SKU-0030';

اگر optimizer به‌خاطر کوچکی جدول scan کرد، metadata وجود index را با SHOW INDEX جدا ثابت کن؛ این دو سؤال یکی نیستند.

If the optimizer scans this tiny table, prove index existence separately with SHOW INDEX; those are different questions.

۴) شرط برابری و بازه / Equality and range

برای قیمت برابر ۴۵ و قیمت از ۳۵ به بالا دو query بنویس و تعداد ردیف‌های هرکدام را بشمار.

Write queries for price equal to 45 and price at least 35; count each result.

SQL / SQL
SELECT COUNT(*) FROM products WHERE price=45.00;
SELECT COUNT(*) FROM products WHERE price>=35.00;

اولی ۲ و دومی ۵ ردیف می‌دهد. هنوز روی price index نساخته‌ایم؛ درست‌بودن نتیجه و انتخاب index مسئله‌های جدا هستند.

The first returns 2 and the second 5. No price index has been added; result correctness and index selection are separate concerns.

۵) index بازهٔ قیمت را بساز / Index the price range

برای query قیمت یک index بساز، metadata را بخوان و سپس همان query را EXPLAIN کن.

Add an index for price, inspect metadata, then explain the same query.

SQL / SQL
CREATE INDEX ix_products_price ON products(price);
SHOW INDEX FROM products WHERE Key_name='ix_products_price';
EXPLAIN SELECT product_id FROM products WHERE price>=35.00;

metadata ساخته‌شدن index را ثابت می‌کند؛ plan انتخاب را نشان می‌دهد. روی ۸ ردیف انتظار نداریم optimizer حتماً index را برگزیند.

Metadata proves the index exists; the plan shows the choice. Do not expect the optimizer to prefer it on eight rows.

۶) جست‌وجوی prefix / Prefix lookup

دو query برای SKU-00% و %0040 بساز و planها را کنار هم بگذار.

Explain searches for SKU-00% and %0040 and compare them.

SQL / SQL
EXPLAIN SELECT product_id FROM products WHERE sku LIKE 'SKU-00%';
EXPLAIN SELECT product_id FROM products WHERE sku LIKE '%0040';

اولی prefix ثابت دارد؛ دومی نقطهٔ شروع مرتب ندارد. plan واقعی به تخمین هزینه و collation هم وابسته است.

The first has a fixed prefix; the second has no ordered starting point. The actual plan also depends on cost estimates and collation.

۷) تابع روی ستون چه تغییری می‌دهد؟ / What changes when a function wraps the column?

مقایسهٔ مستقیم SKU را با LOWER(sku) توضیح بده و metadata collation را هم جمع کن.

Compare a direct SKU predicate with LOWER(sku), and inspect collation metadata.

SQL / SQL
SHOW FULL COLUMNS FROM products LIKE 'sku';
EXPLAIN SELECT product_id FROM products WHERE sku='SKU-0040';
EXPLAIN SELECT product_id FROM products WHERE LOWER(sku)='sku-0040';

خروجی plan را روی نسخهٔ خودت بخوان. predicate تابع‌دار ممکن است استفاده از index عادی را دشوار کند؛ collation تعیین می‌کند مقایسهٔ حروف چطور است.

Read the plan on your version. A function-wrapped predicate may make an ordinary index harder to use; collation determines case-comparison behavior.

۸) ترتیب نتیجه را تضمین کن / Guarantee result order

قیمت‌های برابر را با tie-breaker مرتب کن؛ بعد همان query را بدون ORDER BY اجرا و تفاوت قرارداد را توضیح بده.

Order tied prices with a tie-breaker, then run without ORDER BY and explain the contract difference.

SQL / SQL
SELECT product_id, price FROM products ORDER BY price, product_id;
SELECT product_id, price FROM products;

فقط query اول ترتیب تضمین‌شده می‌خواهد. اینکه اجرای فعلی query دوم مرتب به‌نظر برسد، قرارداد SQL نیست.

Only the first query requests a guaranteed order. If the second happens to look sorted, that is not its SQL contract.

۹) scan کامل را بشناس / Recognize a table scan

با EXPLAIN شرط روی product_name را بررسی کن؛ فعلاً برای هر ستون index نساز.

Explain a predicate on product_name; do not index every column yet.

SQL / SQL
EXPLAIN SELECT product_id FROM products WHERE product_name='Desk lamp';

در این fixture index نام نداریم؛ table scan قابل‌انتظار است. برای تصمیم افزودن index باید query پرتکرار، تعداد ردیف‌ها و هزینهٔ نوشتن را بشناسی.

There is no name index in this fixture, so a table scan is expected. Decide about an index only after understanding query frequency, table size, and write cost.

۱۰) index یک query دیگر را حذف نکن / Preserve another workload

یک query برای category بساز. index آن را ایجاد کن و قبل از تغییر بعدی وجودش را با metadata ثابت کن.

Create a category query, add its index, and prove the index exists before changing anything else.

SQL / SQL
CREATE INDEX ix_products_category ON products(category_id);
SHOW INDEX FROM products WHERE Key_name='ix_products_category';
SELECT product_id, product_name FROM products WHERE category_id=2;

دو ردیف گروه ۲ برمی‌گردند. اگر index از قبل ساخته شده، دوباره اجرا نکن؛ ابتدا SHOW INDEX را ببین.

Two rows from category 2 are returned. If the index already exists, do not recreate it; inspect SHOW INDEX first.

۱۱) duplicate index را پیدا کن / Find a duplicate index

فهرست indexهای SKU و کلید اصلی را بخوان و برای این دو نیاز جداگانه دلیل بنویس.

Inspect the SKU and primary-key indexes and state the distinct need each serves.

SQL / SQL
SHOW INDEX FROM products;
SELECT product_id FROM products WHERE sku='SKU-0020';
SELECT product_id FROM products WHERE product_id=20;

هر lookup نیاز متفاوتی دارد: SKU یکتا و کلید اصلی. index دوم روی همان SKU اضافه نیست؛ اما یک index تکراری دیگر روی SKU لازم نیست.

These lookups serve different keys: unique SKU and primary key. A second index duplicating SKU is unnecessary.

۱۲) ارزان‌ترین plan الزاماً index نیست / The cheapest plan may not use an index

برای شرطی که تقریباً همهٔ ردیف‌ها را برمی‌گرداند EXPLAIN بگیر و علت احتمالی انتخاب scan را در یک query قابل‌اجرا بررسی کن.

Explain a predicate matching most rows and use a runnable query to inspect why a scan may be chosen.

SQL / SQL
EXPLAIN SELECT product_id FROM products WHERE category_id IN (1,2,3);
SELECT COUNT(*) AS matched FROM products WHERE category_id IN (1,2,3);

هر ۸ ردیف match می‌شوند. خواندن index و سپس برگشتن به ردیف‌ها می‌تواند از scan همهٔ جدول گران‌تر باشد؛ برآورد optimizer و اندازهٔ واقعی تعیین‌کننده‌اند.

All eight rows match. Reading an index and then visiting rows can cost more than scanning the table; estimates and real scale matter.

۱۳) فقط بعضی ستون‌ها را درخواست کن / Request only needed columns

query مربوط به SKU را با projection کوچک و سپس SELECT * مقایسه کن؛ plan هر دو را ثبت کن.

Compare a narrow projection with SELECT * for the SKU lookup and record both plans.

SQL / SQL
EXPLAIN SELECT product_id, sku FROM products WHERE sku='SKU-0010';
EXPLAIN SELECT * FROM products WHERE sku='SKU-0010';

خروجی دقیق وابسته به نسخه و metadata است. projection کوچک‌تر می‌تواند دادهٔ کمتری بخواهد؛ از این آزمایش کوچک نتیجهٔ اندازه‌گیری واقعی نگیر.

Exact output depends on version and metadata. A narrower projection may need less data, but this tiny experiment is not a real benchmark.

۱۴) آمار را از تعریف index جدا کن / Separate index definition from statistics

تعریف index و plan را ثبت کن؛ هیچ indexی را حذف نکن. خروجی را با تمرین ۳ مقایسه کن.

Record index definitions and the plan without dropping anything; compare with exercise 3.

SQL / SQL
SHOW INDEX FROM products;
EXPLAIN SELECT product_id, product_name FROM products WHERE sku='SKU-0030';

SHOW INDEX ساختار موجود را می‌گوید، EXPLAIN تصمیم فعلی را. تغییر در یکی را بدون شاهد به دیگری نسبت نده.

SHOW INDEX reports structure; EXPLAIN reports the current choice. Do not infer a causal change without evidence.

۱۵) مرتب‌سازی range را آزمایش کن / Test range plus ordering

قیمت از ۳۵ به بالا را همراه ترتیب مشخص query کن و plan را بخوان.

Query prices from 35 upward with an explicit order, then inspect the plan.

SQL / SQL
EXPLAIN SELECT product_id, price FROM products
WHERE price>=35.00 ORDER BY price, product_id;
SELECT product_id, price FROM products
WHERE price>=35.00 ORDER BY price, product_id;

query خروجی مرتب درخواست می‌کند. اینکه index قیمت تمام sort را حذف کند به ترتیب index و کلیدهای لازم وابسته است؛ plan را به‌جای حدس بخوان.

The query requests ordered output. Whether the price index avoids all sorting depends on index order and required keys; inspect the plan.

۱۶) هزینهٔ write را با یک تغییر محدود ببین / Account for write maintenance

یک ردیف آزمایشی وارد و حذف کن؛ indexهای موجود را پیش و پس از عملیات ثبت کن.

Insert and delete one test row, recording index definitions before and after.

SQL / SQL
SHOW INDEX FROM products;
INSERT INTO products VALUES (95,'SKU-0095',4,5.00,'write test');
DELETE FROM products WHERE product_id=95;
SHOW INDEX FROM products;

تعریف indexها عوض نمی‌شود، اما هرکدام باید با insert/delete سازگار بمانند. SHOW INDEX زمان این هزینه را اندازه نمی‌گیرد؛ این تمرین فقط چرایی هزینهٔ نگهداری را نشان می‌دهد.

Index definitions remain unchanged, but each index must stay consistent through insert/delete. SHOW INDEX does not measure the cost; the exercise illustrates why maintenance exists.

۱۷) Full scan را فوری خرابی ننام / Do not label every scan a failure

یک query که همهٔ دسته‌ها را می‌خواند اجرا کن، plan و شمار ردیف را کنار هم بگذار و تصمیم بگیر index اینجا چه کمکی می‌کند.

Run a query over all categories, compare its plan and row count, and decide whether an index helps.

SQL / SQL
EXPLAIN SELECT product_id, category_id FROM products;
SELECT COUNT(*) FROM products;

اگر تمام ردیف‌ها لازم‌اند، scan می‌تواند انتخاب معقولی باشد. هدف کاهش کار غیرضروری است، نه مجبورکردن optimizer به استفاده از index.

If every row is needed, a scan can be reasonable. The goal is reducing unnecessary work, not forcing an index.

۱۸) گزارش تصمیم index بنویس / Write an index decision query

یک query واقعی از fixture انتخاب کن؛ SQL آن، plan، index موجود و محدودیت شواهد را در یک خروجی قابل‌تکرار جمع کن.

Choose a real fixture query and capture its SQL, plan, existing index, and evidence limits in a reproducible result.

SQL / SQL
SHOW INDEX FROM products;
EXPLAIN SELECT product_id, product_name
FROM products WHERE category_id=2;
SELECT product_id, product_name
FROM products WHERE category_id=2;

این سه دستور ساختار، برآورد مسیر و نتیجهٔ داده‌ای را جدا می‌کنند. برای ادعای سریع‌ترشدن باید workload بزرگ و نماینده را هم اندازه بگیری.

These three statements separate structure, estimated path, and returned data. A speed claim still needs measurement on a representative workload.

آزمایش پایانی: درخواست کالا، نه فهرست indexهاClosing lab: serve a product lookup, not an index list

تیم محصول می‌خواهد سه درخواست را پشتیبانی کند: یافتن SKU دقیق، فهرست قیمت‌های بالای یک حد، و گزارش یک دسته. اول queryها را بنویس، بعد ببین کدام نیاز الان پوشش دارد. index جدید فقط وقتی اضافه می‌شود که یک query واقعی و مدرک لازم داشته باشی.

The product team needs three requests: exact SKU lookup, prices above a threshold, and a category report. Write the queries first, then inspect which needs are already covered. Add an index only when a real query and evidence justify it.

  1. سه query را اجرا و EXPLAIN کن؛ خروجی داده و ستون key را ذخیره کن.
  2. Run and explain the three queries; save result rows and the key column.
  3. indexهای موجود را با SHOW INDEX فهرست کن و یک index آزمایشی فقط برای نیازِ بی‌پوشش بساز.
  4. List existing indexes and add one test index only for an uncovered requirement.
  5. queryها و planها را دوباره اجرا کن. بنویس چه چیزی تغییر کرد و چرا این دادهٔ کم، ادعای performance را ثابت نمی‌کند.
  6. Rerun the queries and plans. Record what changed and why this small dataset cannot prove a performance improvement.
