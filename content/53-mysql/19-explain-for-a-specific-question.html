EXPLAIN برای یک سؤال مشخص

EXPLAIN for a Specific Question

یک endpoint کند شده و کسی می‌گه «type=ALL یعنی index خراب هست». قبل از نسخه‌دادن، همان query رو EXPLAIN می‌کنیم و می‌پرسیم هر ستون چه شاهدی می‌ده. plan پیش‌بینی optimizer است، نه نتیجهٔ اجرای واقعی؛ باید آن رو به سؤال مشخص وصل کنیم و بدانیم چه چیزی رو هنوز ثابت نکرده.

An endpoint slowed down and someone says, “type=ALL means the index is broken.” Before prescribing a fix, we run EXPLAIN on the exact query and ask what each field tells us. A plan is the optimizer’s prediction, not actual runtime; connect it to a specific question and note what remains unproven.

EXPLAIN جواب کدام سؤال رو می‌ده؟Which question does EXPLAIN answer?

فرض کن می‌خوای ticketهای یک تیم رو با وضعیت باز پیدا کنی. یک index روی team و state داریم؛ آیا optimizer آن رو به کار می‌گیره؟ چند ردیف رو تخمین می‌زند؟ آیا برای هر ردیف به table برمی‌گردد؟ این‌ها سؤال‌های مناسب EXPLAIN هستن. «دقیقاً چند میلی‌ثانیه طول می‌کشد؟» سؤال آن نیست.

Suppose you need open tickets for one team. An index exists on team and state; will the optimizer use it? How many rows does it estimate? Does it visit the table for each row? These are EXPLAIN questions. “Exactly how many milliseconds will this take?” is not.

در MySQL 9.7، قالب پیش‌فرض می‌تونه با explain_format تعیین شود. برای اینکه تمرین خروجی جدولی مشخصی داشته باشه از FORMAT=TRADITIONAL استفاده می‌کنیم. نسخهٔ server رو ثبت کن؛ متن و جزئیات plan بین نسخه‌ها و داده‌ها فرق دارد.

In MySQL 9.7, the default format can be controlled by explain_format. To make the exercise explicitly tabular, we use FORMAT=TRADITIONAL. Record the server version; plan text and details vary across versions and data.

جواب داده‌ای در این fixture، ticketهای ۱ و ۳ هست. حالا plan همان query رو می‌خونیم. چون جدول فقط هشت ردیف دارد، table scan می‌تونه منطقی باشه؛ وجود index پاسخ سؤال «انتخاب شد؟» رو از پیش تعیین نمی‌کنه.

The fixture returns tickets 1 and 3. Now inspect the plan for that same query. With only eight rows, a table scan can be reasonable; an existing index does not predetermine whether it is chosen.

اول مسیر رو یک‌جا بخوانRead the plan as a whole first

plan جدولی و نتیجهٔ queryTabular plan and query result
EXPLAIN FORMAT=TRADITIONAL
SELECT ticket_id,subject
FROM support_ticket
WHERE team_id=10 AND state='open';

SELECT ticket_id,subject
FROM support_ticket
WHERE team_id=10 AND state='open';

plan برای هر table access یک ردیف دارد. این fixture ممکنه type=ALL نشان دهد و key خالی باشه، چون خواندن هشت ردیف از table از رفتن به index و برگشت به row ارزان‌تر برآورد می‌شه. نتیجهٔ query دوم باید درست بماند؛ خروجی EXPLAIN جای اجرای خود query نیست.

The plan has a row for each table access. This fixture may show type=ALL with no selected key because scanning eight rows may be estimated cheaper than navigating the index and fetching rows. The second query should still return correct results; EXPLAIN does not replace executing the query.

برای خواندن rows و filtered از تخمین حرف بزن. مثلاً تخمین ۲۰ ردیف با filtered=۵۰٪ یعنی optimizer انتظار دارد حدود نیمی از ردیف‌های آن مرحله از شرط عبور کنند؛ نه اینکه query قطعاً ۱۰ ردیف خواهد خواند یا ۱۰ نتیجه خواهد داد.

Treat rows and filtered as estimates. For example, 20 estimated rows with filtered=50% means the optimizer expects about half of that step’s rows to pass the condition—not that the query will definitely read 10 rows or return 10 results.

type رو از متن query جدا نخوانDo not read type apart from the query

مقدارهایی مثل ALL، range، ref یا const نام access method هستن. هیچ‌کدام به‌تنهایی مهر کیفیت نیستند. ALL روی جدول هشت‌ردیفی شاید بهترین باشه؛ range روی جدول میلیاردردیفی هم اگه تخمین بسیار بزرگ باشه هنوز پرهزینه می‌شه. ردیف plan، index، rows estimate و نیاز خروجی رو با هم ببین.

Values such as ALL, range, ref, and const name access methods. None is a quality stamp by itself. ALL may be best for an eight-row table; range can still be expensive on a billion-row table if the estimate is huge. Read plan row, index, estimated rows, and required output together.

یک query selective و یک query broadOne selective query and one broad query
EXPLAIN FORMAT=TRADITIONAL
SELECT ticket_id FROM support_ticket
WHERE ticket_id=3;

EXPLAIN FORMAT=TRADITIONAL
SELECT ticket_id FROM support_ticket
WHERE state='open';

SELECT COUNT(*) FROM support_ticket WHERE state='open';

اولی primary key رو هدف می‌گیره و دومی بخش بزرگ‌تری از جدول رو می‌خواهد. حتی اگه planها access type متفاوتی نشان دهند، نتیجهٔ عملی به cardinality، data size و row lookup cost وابسته هست.

The first targets the primary key; the second asks for a larger share of the table. Even if access types differ, practical cost depends on cardinality, data size, and row-lookup cost.

Extra هم باید در context خوانده شودRead Extra in context too

Using where می‌گه شرطی برای فیلتر باقی مانده؛ لزوماً نشانهٔ اشکال نیست. Using index می‌تونه پوشش index رو نشان دهد. Using filesort می‌گه sort از مسیر index حل نشده، اما اسمش تضمین نمی‌کنه فایل موقت روی disk ساخته شده. معنی دقیق رو با projection، order، حجم داده و قالب plan تطبیق بده.

Using where indicates a condition remains for filtering; it is not automatically a problem. Using index can indicate index coverage. Using filesort says sorting was not resolved from index order, but the name does not guarantee a disk temporary file. Interpret it with projection, ordering, data size, and plan format.

فیلتر و sort رو جدا بسنجInspect filtering and sorting separately
EXPLAIN FORMAT=TRADITIONAL
SELECT ticket_id,created_at
FROM support_ticket
WHERE team_id=10 AND state='open'
ORDER BY created_at;

EXPLAIN FORMAT=TRADITIONAL
SELECT ticket_id,subject
FROM support_ticket
WHERE team_id=10 AND state='open'
ORDER BY subject;

ترتیب query اول با ستون سوم composite index هماهنگ‌تر است؛ دومی subject رو می‌خواهد که index ندارد. روی جدول کوچک ممکنه هر دو plan ساده باشند؛ خروجی رو صرفاً به‌خاطر نام Extra خوب یا بد اعلام نکن.

The first order aligns more closely with the third composite-index column; the second orders by subject, which is not indexed. On a tiny table both plans may be simple; do not label them good or bad from Extra alone.

SHOW WARNINGS رو در همان session بخوانRead SHOW WARNINGS in the same session

پس از EXPLAIN ممکنه extended information با SHOW WARNINGS قابل‌دسترسی باشه. این diagnostic به آخرین statement همان session مربوط است؛ بین EXPLAIN و SHOW WARNINGS یک query عادی اجرا نکن، و انتظار نداشته باش در همهٔ queryها خروجی مفیدی بده.

After EXPLAIN, extended information may be available through SHOW WARNINGS. This diagnostic refers to the most recent statement in the same session; do not run an ordinary query between EXPLAIN and SHOW WARNINGS, and do not expect useful output for every query.

دستورها رو پشت‌سرهم اجرا کنRun the statements consecutively
EXPLAIN FORMAT=TRADITIONAL
SELECT ticket_id FROM support_ticket WHERE team_id=10;
SHOW WARNINGS;

ممکنه note/rewritten query ببینی یا خروجی محدود باشه. SHOW WARNINGS نتیجهٔ SELECT رو نمی‌ده و جای خواندن plan رو نمی‌گیره.

You may see notes or a rewritten query, or only limited output. SHOW WARNINGS does not return the SELECT result and does not replace plan reading.
