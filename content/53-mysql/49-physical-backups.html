Physical backup can be fast, but only with a compatible snapshot method, tool, version, and restore procedure.

backup فیزیکی فایل خام است؛ هماهنگی‌اش مهم هستPhysical backups copy raw files; consistency is the hard part

backup فیزیکی data fileها و metadata مربوط رو نگه می‌دارد و برای مجموعه‌های بزرگ می‌تونه restore سریعتری داشته باشه. در عوض به نسخه و محیط نزدیک‌تری وابسته هست و artifact آن رو نمی‌توان مثل SQL dump به‌آسانی ویرایش کرد. کپی خام از server خاموش ساده‌تر است؛ برای backup آنلاین از ابزار سازگار یا snapshot هماهنگ با دیتابیس استفاده کن.

A physical backup preserves data files and related metadata and can restore large datasets faster. It is more dependent on compatible versions and environments, and is not as easy to inspect or edit as SQL. Copying files from a stopped server is simpler; for online backup, use a compatible tool or a database-coordinated snapshot.

Clone Plugin ابزار backup همه‌چیز نیستThe Clone Plugin is not a complete backup solution

Clone Plugin می‌تونه InnoDB data رو در محدودهٔ سازگاری نسخه clone کند و برای provisioning یا ساخت recipient مناسب باشه. اما تنظیمات server و binary logها رو clone نمی‌کنه؛ engineهای غیر InnoDB هم پوشش کامل ندارن. عملیات remote روی recipient می‌تونه دادهٔ موجود آن رو جایگزین کند. این کار رو فقط روی recipient خالی و disposable انجام بده و قبلش مستندات مقصد رو بخوان.

The Clone Plugin can clone InnoDB data within supported version boundaries and is useful for provisioning a recipient. It does not clone server configuration or binary logs, and non-InnoDB data is not fully covered. A remote clone can replace existing recipient data. Use only an empty disposable recipient and read target-version documentation first.

کپی مستقیم datadir وسط نوشتن ممنوعNever copy a live datadir while writes continue

کپی فایل به فایل هنگام کار server می‌تونه ترکیبی از زمان‌های مختلف بسازد. برای file-system backup یا server رو طبق runbook متوقف کن، یا از snapshot و مراحل prepare سازگار با engine استفاده کن؛ storage snapshot خام بدون هماهنگی دیتابیس به‌خودی‌خود تضمین consistency نیست. بعد از backup هم restore رو روی مقصد جدا اجرا کن.

Copying files one by one while the server is active can capture different moments. For filesystem backup, stop MySQL according to a runbook, or use a storage snapshot and engine-aware prepare process; a raw storage snapshot alone does not guarantee database consistency. Restore separately afterward.

نسخه، فهرست فایل و آزمون restore رو نگه دارKeep version, artifact inventory, and restore evidence

backup فیزیکی باید مشخص کند از چه نسخه، کدام مسیر datadir، کدام storage engine و کدام ابزار گرفته شده. فایل‌های keyring و encryption، config، certificate، plugin و binary log ممکنه بیرون از backup اصلی باشند. runbook باید بگوید هرکدام کجا هستن و چه ترتیبی برای restore دارن؛ secret رو داخل artifact عمومی نگذار.

A physical backup should identify source version, data paths, storage engines, and tool. Keyring and encryption files, configuration, certificates, plugins, and binary logs may live outside the main backup. The runbook must state where they are and how restoration is ordered; do not publish secrets with the artifact.
