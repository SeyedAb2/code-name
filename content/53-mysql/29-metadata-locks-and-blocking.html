چرا ALTER TABLE پشت یک SELECT منتظر مانده؟

Why is ALTER TABLE waiting behind a SELECT?

یک نفر می‌گه «فقط SELECT زدم»، اما تغییر schema در session دیگری جلو نمی‌ره. فصل قبل row lock رو دیدیم و شاید فکر کنیم باید دنبال همان قفل بگردیم. این‌جا انتظار از metadata هست: MySQL باید مطمئن شود جدول در میانهٔ استفاده، ساختارش عوض نمی‌شه.

Someone says, “I only ran a SELECT,” yet a schema change in another session does not proceed. We just studied row locks, so we might search for the same lock. This wait concerns metadata: MySQL must ensure that a table’s structure does not change while a transaction is using it.

تغییر ساختار گیر کرده؛ اما کسی قفل ردیف نمی‌گیرهDDL is stuck, but nobody requested a row lock

توسعه‌دهندهٔ A یک transaction باز کرده، جدول رو خوانده و بعد سراغ کار دیگری رفته هست. DBA در B می‌خواهد یک ستون اضافه کند. ALTER TABLE منتظر می‌مونه، چون transaction A هنوز با آن جدول کار دارد. لازم نیست A از FOR UPDATE استفاده کرده باشه؛ استفاده از جدول در transaction هم می‌تونه metadata lock رو تا پایان transaction نگه داره.

Developer A opened a transaction, read a table, and moved on to something else. The DBA in B tries to add a column, but ALTER TABLE waits because A’s transaction still uses the table. A did not need FOR UPDATE; using a table in a transaction can hold its metadata lock until that transaction ends.

این قفل از row lock جداست: row lock دسترسی به دادهٔ مشخص رو هماهنگ می‌کنه؛ metadata lock جلوی تغییر ساختار object رو در زمان استفاده می‌گیره. اگه نوع lock رو اشتباه تشخیص بدهی، ممکنه ساعت‌ها دنبال مدرک در جدول اشتباه بگردی.

This is distinct from a row lock: row locks coordinate access to data records; metadata locks protect an object’s structure while it is in use. If you misclassify the lock, you may search the wrong evidence for hours.

سه connection: نگه‌دارنه، منتظر و ناظرThree sessions: holder, waiter, observer

A جدول رو در transaction می‌خواند و metadata lock نگه می‌دارد. B دستور ALTER رو اجرا می‌کنه و منتظر می‌مونه. C از Performance Schema می‌پرسد چه lockهایی برای همان جدول ثبت شده‌اند. اگه فقط دو session داری، می‌تونی query ناظر رو بعد از بازکردن پنجرهٔ سوم اجرا کنی؛ connection C باید به همان server وصل باشه.

A reads the table inside a transaction and holds metadata access. B issues ALTER and waits. C queries Performance Schema for locks on that object. If you have only two sessions, open a third observer connection; C must reach the same server.

آزمایش روی schema جداUse a separate lab schema

schema تمرینی codenames_mdl_lab رو بساز. ALTER فقط یک ستون آزمایشی اضافه می‌کنه و DROP پایانی فقط همان schema رو پاک می‌کنه؛ نام رو پیش از حذف تأیید کن.

Create the disposable codenames_mdl_lab schema. ALTER adds only a lab column; the final DROP removes only this schema. Verify the name before cleanup.

یک جدول ساده بسازCreate a small table
CREATE DATABASE IF NOT EXISTS codenames_mdl_lab;
USE codenames_mdl_lab;
DROP TABLE IF EXISTS note;
CREATE TABLE note (
  note_id INT PRIMARY KEY,
  body VARCHAR(100) NOT NULL
) ENGINE=InnoDB;
INSERT INTO note VALUES (1,'lab row');
SELECT * FROM note;

انتظار رو در دو session بازتولید کنReproduce the wait across two sessions

در A یک transaction صریح باز کن و جدول رو بخوان. هنوز COMMIT نکن. حتی اگه SELECT تمام شده باشه، transaction تمام نشده و metadata lock می‌تونه تا پایان آن باقی بماند.

In A, open an explicit transaction and read the table. Do not commit yet. The SELECT statement may have finished, but its transaction has not; the metadata lock can remain until the transaction ends.

session A: جدول رو بخوان و transaction رو باز نگه دارSession A: read the table and keep the transaction open
USE codenames_mdl_lab;
START TRANSACTION;
SELECT * FROM note WHERE note_id=1;

حالا در B یک تغییر ساختاری محدود بزن. B ممکنه منتظر بماند؛ این رو نشانهٔ همان wait بدان، نه این‌که بی‌دلیل client رو kill کنی.

Now issue a small schema change in B. It may wait; treat that as evidence of the wait, not a reason to kill the client immediately.

session B: DDL منتظر می‌مونه تا A تمام شودSession B: DDL waits for A to finish
USE codenames_mdl_lab;
ALTER TABLE note ADD COLUMN tag VARCHAR(20) NULL;

از connection C وضعیت رو می‌خونیم. دنبال OBJECT_NAME='note' و LOCK_STATUS='PENDING' بگرد؛ این نشانه می‌ده درخواست lock هنوز اعطا نشده. یک یا چند ردیف GRANTED هم ممکنه نشان دهد چه sessionهایی lock دارن. مقدارها و تعداد ردیف‌ها بسته به queryهای فعال فرق می‌کنه.

From C, inspect the lock state. Look for OBJECT_NAME='note' and LOCK_STATUS='PENDING' to find an ungranted request. One or more GRANTED rows may show existing holders. Exact rows vary with active statements.

session C: lockهای metadata همین objectSession C: metadata locks for this object
SELECT ml.OBJECT_TYPE,ml.OBJECT_SCHEMA,ml.OBJECT_NAME,
       ml.LOCK_TYPE,ml.LOCK_DURATION,ml.LOCK_STATUS,
       th.PROCESSLIST_ID,th.PROCESSLIST_INFO
FROM performance_schema.metadata_locks AS ml
LEFT JOIN performance_schema.threads AS th
  ON th.THREAD_ID=ml.OWNER_THREAD_ID
WHERE ml.OBJECT_SCHEMA='codenames_mdl_lab'
  AND ml.OBJECT_NAME='note'
ORDER BY ml.LOCK_STATUS,th.PROCESSLIST_ID;

اگه خروجی خالی است، اول permission، schema/object درست و این‌که ALTER واقعاً هنوز pending هست رو بررسی کن. ممکنه Performance Schema قابل‌خواندن نباشه یا B پیش از query ناظر آزاد شده باشه. خالی‌بودن این query به‌تنهایی ثابت نمی‌کنه lockی وجود نداشته.

If the result is empty, first check privileges, the object name, and whether ALTER is still pending. Performance Schema may be inaccessible, or B may have resumed before the observer query. An empty result alone does not prove that no lock was involved.

راه‌حل، transaction باز رو پیدا کنResolve it by finding the open transaction

اگه A به کارش پایان داده، در همان session COMMIT یا ROLLBACK بزن. قفل آزاد می‌شه و ALTER در B ادامه پیدا می‌کنه. اگه transaction لازم است، به‌جای commitکردن کورکورانه، با صاحب session هماهنگ کن؛ پایان transaction می‌تونه تغییرهایش رو ماندگار کند یا لغو کند.

If A is done, COMMIT or ROLLBACK in that session. The lock is released and B’s ALTER proceeds. If the transaction is still needed, coordinate with its owner rather than committing blindly; ending it may preserve or discard changes.

session A: مرز رو آگاهانه ببندSession A: end the boundary deliberately
COMMIT;

بعد از ادامهٔ B، در C دوباره وضعیت رو بخوان و در B ستون رو بررسی کن. اگه ALTER کامل شد و ستون tag دیده شد، مسیر انتظار رو حل کرده‌ایم. این آزمایش نشان نمی‌ده که هر ALTER سریع است؛ فقط blocker این مورد رو پیدا کرد.

After B resumes, query C again and inspect the column in B. If ALTER completed and tag appears, we resolved this wait. The experiment does not prove every ALTER is fast; it identified this incident’s blocker.

در B پس از پایان ALTERIn B after ALTER completes
SHOW COLUMNS FROM note;

چرا یک SELECT کوتاه معمولاً همین مشکل رو نمی‌سازد؟Why does a short autocommit SELECT usually not cause this?

در autocommit، هر statement به‌تنهایی transaction کامل است؛ metadata lock عادی همان statement معمولاً در پایانش آزاد می‌شه. مشکل وقتی رایج می‌شه که transaction صریح باز باشه و application بعد از query هنوز COMMIT/ROLLBACK نکرده باشه، حتی اگه connection ظاهراً idle دیده بشه.

With autocommit, each statement is effectively its own transaction, so the statement’s metadata lock is usually released when it ends. The common problem is an explicit transaction that remains open after the query, even if the connection looks idle.

پس فقط طول زمان query رو نگاه نکن؛ عمر transaction رو هم ببین. یک SELECT یک‌میلی‌ثانیه‌ای در transaction ده‌دقیقه‌ای می‌تونه DDL رو ده دقیقه معطل کند.

Do not inspect query duration alone; inspect transaction age too. A one-millisecond SELECT inside a ten-minute transaction can keep DDL waiting for ten minutes.

metadata lock رو با row lock قاطی نکنDo not confuse metadata and row locks
