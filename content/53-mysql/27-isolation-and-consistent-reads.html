چرا دو session یک عدد متفاوت می‌بینند؟

Why do two sessions see different values?

در فصل قبل دو مرحله رو در یک transaction مدیریت کردیم. حالا دو connection داریم: یکی مقدار رو می‌خواند و دیگری آن رو تغییر می‌ده. آیا خواننده باید هر تغییر تازه رو ببیند؟ جواب به نوع خواندن و isolation level بستگی دارد. بیا با دو پنجرهٔ واقعی آن رو ببینیم.

The previous chapter managed multiple steps in one transaction. Now two connections are involved: one reads while the other changes a value. Should the reader see every new change? The answer depends on the read type and isolation level. Let’s observe it with two real sessions.

یک گزارشگر هنوز عدد قبلی رو می‌بیندA report still sees the previous value

گزارشگر transaction رو باز می‌کنه و موجودی ۱۰ رو می‌خواند. هم‌زمان یک session دیگر مقدار رو به ۱۱ تغییر می‌ده و commit می‌کنه. گزارشگر دوباره SELECT می‌زند؛ باید ۱۰ ببیند یا ۱۱؟ این‌جا داریم دربارهٔ یک plain SELECT در InnoDB حرف می‌زنیم، نه SELECT ... FOR UPDATE.

A reporting session opens a transaction and reads balance 10. Another session changes it to 11 and commits. The reporter selects again: should it see 10 or 11? We are discussing a plain InnoDB SELECT, not SELECT ... FOR UPDATE.

ایزوله‌سازی یک پیچ تنظیم برای رفتار transactionهای هم‌زمان هست. «بالاتر» همیشه یعنی «بهتر برای هر workload» نیست؛ باید بدانیم چه snapshot و چه قفل‌هایی لازم داریم و چه هزینه‌ای می‌پذیریم.

Isolation is a control over how concurrent transactions interact. “Higher” is not automatically “better for every workload”; decide which snapshots and locks you need and what cost you can accept.

دو session باز کنOpen two sessions

دو ترمینال یا دو tab در client دیتابیس باز کن. اولی رو A و دومی رو B بنام. هر دو باید به همان MySQL server وصل باشند؛ اگه server یکی نباشه، تغییر B در snapshot A ظاهر نمی‌شه و نتیجه گمراه‌کننده هست.

Open two terminals or database-client tabs. Call them A and B. Both must connect to the same MySQL server; otherwise B’s change cannot affect A’s snapshot and the experiment becomes misleading.

REPEATABLE READ: snapshot ثابت برای خواندن‌های عادیREPEATABLE READ: a stable snapshot for consistent reads

در InnoDB، REPEATABLE READ سطح پیش‌فرض هست. در transaction A، اولین consistent read یک snapshot می‌گیره؛ plain SELECTهای بعدی همان transaction همان snapshot رو می‌خوانند. تغییر commitشدهٔ بعدی session B لزوماً در همان transaction A دیده نمی‌شه.

REPEATABLE READ is InnoDB’s default. In transaction A, the first consistent read establishes a snapshot; later plain SELECTs in that transaction read the same snapshot. A subsequently committed change from B is not necessarily visible to A until its transaction ends.

ابتدا در session AFirst, in session A
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT value_num FROM reading WHERE id=1;

A باید ۱۰ ببیند. حالا transaction A رو باز نگه دار و در session B مقدار رو تغییر بده و commit کن.

A should read 10. Keep its transaction open, then update and commit the value in session B.

در session BIn session B
START TRANSACTION;
UPDATE reading SET value_num=11 WHERE id=1;
COMMIT;
SELECT value_num FROM reading WHERE id=1;

B باید ۱۱ ببیند؛ حالا دوباره همان SELECT رو در A بزن. انتظار داریم A هنوز ۱۰ ببیند. این تفاوت خطا نیست: A در snapshot خودش مانده هست. پس transaction A رو commit کن و بیرون transaction دوباره بخوان؛ حالا مقدار ۱۱ دیده می‌شه.

B should see 11. Run the same SELECT again in A; it should still see 10 because A is reading its existing snapshot. Commit A, then read outside that transaction; now it sees 11.

پایان در session AFinish in session A
SELECT value_num FROM reading WHERE id=1;
COMMIT;
SELECT value_num FROM reading WHERE id=1;

این آزمایش روی plain consistent read هست. locking readها، UPDATE/DELETE و رفتار قفل‌ها رو نباید از نتیجهٔ این SELECTها حدس بزنی؛ فصل بعد قفل‌ها رو جدا می‌سازد.

This experiment concerns plain consistent reads. Do not infer locking-read, UPDATE/DELETE, or lock behavior from these SELECTs; the next chapter examines locks separately.

READ COMMITTED: هر خواندن عادی snapshot تازهREAD COMMITTED: each consistent read gets a fresh snapshot

حالا همان story رو با READ COMMITTED تکرار می‌کنیم. سطح رو پیش از بازکردن transaction در A تنظیم کن. در این سطح هر consistent read یک snapshot تازه از تغییرهای commitشده می‌گیره؛ بنابراین A می‌تونه در یک transaction مقدار متفاوتی رو در SELECT دوم ببیند.

Repeat the same story under READ COMMITTED. Set the level in A before starting the transaction. Each consistent read gets a fresh snapshot of committed changes, so A can see a different value in its second SELECT within the same transaction.

در session A، پیش از transactionIn session A, before the transaction
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT value_num FROM reading WHERE id=1;

بعد در B مقدار رو از ۱۱ به ۱۲ تغییر بده و commit کن؛ سپس در A همان SELECT رو تکرار کن. بار دوم A باید ۱۲ رو ببیند، چون این consistent read snapshot تازه‌ای گرفته هست. A هنوز transaction رو باز دارد؛ خواندن تازه یعنی دادهٔ commitشدهٔ تازه، نه این‌که transaction تمام شده.

Update the value from 11 to 12 in B and commit, then repeat the SELECT in A. A should now see 12 because this consistent read gets a fresh snapshot. A’s transaction is still open: a fresh read does not mean the transaction ended.

در session BIn session B
UPDATE reading SET value_num=12 WHERE id=1;
COMMIT;
دوباره در session A و بعد پایانBack in A, then finish
SELECT value_num FROM reading WHERE id=1;
COMMIT;

اگه در READ COMMITTED به snapshot ثابت نیاز داری، فرض نکن plain SELECTها این کار رو می‌کنن. راه‌حل به نیاز برنامه بستگی دارد؛ می‌تونه طراحی query/transaction یا نوع locking read باشه. انتخاب رو با مسئلهٔ واقعی هماهنگ کن.

Do not assume plain SELECTs give a stable snapshot in READ COMMITTED. The right approach depends on the application and may involve transaction/query design or a locking read. Match the choice to the actual requirement.
