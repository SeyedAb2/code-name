ستون‌های محاسباتی و تکامل جدول در MySQL

Generated Columns and Table Evolution in MySQL

قیمت نهایی هر محصول از قیمت پایه و تخفیف به دست می‌آید. اگر برنامه این فرمول را در پنج جای مختلف تکرار کند، دیر یا زود یکی‌شان با بقیه فرق می‌کند. اینجا می‌بینیم MySQL چطور می‌تواند چنین مقداری را از خود ردیف محاسبه کند؛ و چه وقت ذخیره‌کردن نتیجه ارزش هزینه‌اش را دارد.

A product’s final price comes from its base price and discount. If five parts of an application repeat that formula, one will eventually drift. We’ll see how MySQL can compute a value from the row itself—and when storing that result is worth the cost.

پیش‌نیازPrerequisite: فصل ۳ · database و context در MySQL محیط مرجعLab baseline: MySQL 9.7.2 · InnoDB زمانTime: ۸۵ دقیقه · ۱۸ تمرین

یک فرمول، چند نسخهٔ متفاوتOne formula, several conflicting copies

تیم فروش می‌گوید قیمت قابل‌نمایش باید بعد از تخفیف محاسبه شود. صفحهٔ محصول از یک فرمول استفاده می‌کند، گزارش ماهانه فرمول دیگری، و خروجی انبار تخفیف را اصلاً کم نمی‌کند. دادهٔ پایه یکسان است؛ نتیجه‌ها نه. می‌خواهیم ببینیم آیا این مقدار واقعاً باید در table ذخیره شود، یا می‌تواند تعریف روشنی داشته باشد که هر مصرف‌کننده همان را ببیند.

Sales says the displayed price must reflect the discount. The product page uses one formula, the monthly report another, and the warehouse export forgets the discount entirely. The base data is the same; the results are not. Should the value be stored, or can the table define it once for every consumer?

MySQL به generated column اجازه می‌دهد مقداری را از ستون‌های همان ردیف بسازد. این ویژگی جای هر business rule یا query را نمی‌گیرد: expression باید محدودیت‌های خود MySQL را رعایت کند و generated column هم خودش به‌تنهایی تضمین نمی‌کند فرمول از نظر کسب‌وکار درست انتخاب شده باشد.

MySQL generated columns compute a value from columns in the same row. They do not replace every business rule or query: the expression must follow MySQL’s restrictions, and the feature cannot decide whether the business formula itself is correct.

مقدار ورودی را از مقدار مشتق‌شده جدا کنSeparate inputs from derived values

در جدول زیر unit_price و discount_pct دادهٔ ورودی‌اند. final_price از آن‌ها به دست می‌آید؛ پس موقع INSERT مقدارش را نمی‌فرستیم. نوع اعشاری را هم صریح انتخاب می‌کنیم تا قیمت به دقت تقریبی FLOAT وابسته نباشد.

Here unit_price and discount_pct are inputs. final_price is derived, so INSERT does not supply it. We choose a decimal type explicitly so money does not depend on approximate FLOAT arithmetic.

ساخت fixture مستقلCreate an isolated fixture
CREATE DATABASE IF NOT EXISTS codenames_mysql_ch04;
USE codenames_mysql_ch04;

CREATE TABLE product_offer (
  offer_id BIGINT PRIMARY KEY,
  title VARCHAR(100) NOT NULL,
  unit_price DECIMAL(10,2) NOT NULL,
  discount_pct DECIMAL(5,2) NOT NULL,
  final_price DECIMAL(10,2)
    GENERATED ALWAYS AS (
      ROUND(unit_price * (1 - discount_pct / 100), 2)
    ) STORED,
  CONSTRAINT chk_discount_range
    CHECK (discount_pct BETWEEN 0 AND 100)
) ENGINE=InnoDB;

INSERT INTO product_offer (offer_id, title, unit_price, discount_pct)
VALUES (1, 'Notebook', 125000.00, 12.00),
       (2, 'Pen set',    40000.00,  0.00);

SELECT offer_id, unit_price, discount_pct, final_price
FROM product_offer
ORDER BY offer_id;

ردیف اول باید 110000.00 را نشان دهد. دقت کن که INSERT فقط ورودی‌ها را می‌گیرد؛ MySQL مقدار generated را محاسبه می‌کند. اگر بخواهی مستقیماً final_price را به عدد دلخواه set کنی، سرور اجازه نمی‌دهد؛ تغییر ورودی‌هاست که نتیجه را عوض می‌کند.

The first row should show 110000.00. Notice that INSERT provides only the inputs; MySQL computes the generated value. You cannot set final_price to an arbitrary number—the inputs determine it.

این table فقط fixture آموزشی است.در database مشترک یا واقعی، نام را عوض کن و پیش از DDL از مالک محیط اجازه بگیر. دستورهای بعدی این مسیر را تغییر می‌دهند، نه دیتابیس اصلی برنامه را.This table is a learning fixture.On a shared or real database, use an approved name and get the owner’s permission before DDL. The following statements modify this lab, not an application’s production database.

VIRTUAL یا STORED؟ هزینه را در جای درست ببینVIRTUAL or STORED? Put the cost in the right place

اگر نوع را مشخص نکنی، MySQL ستون را VIRTUAL در نظر می‌گیرد. مقدار virtual در زمان خواندن محاسبه می‌شود و برای خود مقدار فضای ردیف نمی‌گیرد. در STORED مقدار هنگام INSERT یا UPDATE محاسبه و ذخیره می‌شود؛ خواندن آن می‌تواند از محاسبهٔ دوباره بی‌نیاز شود، اما فضا و کار نوشتن بیشتری می‌خواهد.

If you omit the storage keyword, MySQL treats the column as VIRTUAL. Its value is computed when read and does not occupy row storage for the value itself. A STORED value is computed on insert or update and persisted; reads can avoid recomputing it, but storage and write work increase.

ChoiceWhen computedStorageIndex note
VIRTUALWhen readNo value stored in the rowInnoDB supports secondary indexes on virtual generated columns
STOREDOn insert or updateValue occupies storageCan be indexed
Neither keywordVirtual behaviorNo stored valueMake the choice explicit when it matters to the design

هیچ‌کدام «همیشه سریع‌تر» نیست. تصمیم را با الگوی واقعی خواندن/نوشتن، اندازهٔ داده و plan می‌سنجیم؛ یک جدول کوچک آزمایشگاهی معیار کافی برای production نیست. در InnoDB می‌توان روی virtual generated column هم secondary index ساخت، اما خود index همچنان فضا می‌گیرد و تغییر ورودی‌ها هزینهٔ نگهداری دارد.

Neither is “always faster.” Base the decision on the real read/write pattern, data size, and plan; a tiny lab table is not a production benchmark. InnoDB can index a virtual generated column, but that index still consumes space and must be maintained when inputs change.

Expression هرچیزی را قبول نمی‌کندGenerated expressions have boundaries

expression باید deterministic باشد: برای دادهٔ یکسان، نتیجهٔ قابل‌پیش‌بینی بدهد. تابع‌هایی مثل NOW() یا CURRENT_USER() به زمان یا نشست وابسته‌اند و برای این تعریف مناسب نیستند. subquery، متغیر و routine ذخیره‌شده هم در expression مجاز نیستند. یک generated column می‌تواند به generated column قبلی در تعریف جدول ارجاع دهد، نه ستونی که بعدتر آمده است.

The expression must be deterministic: the same row data should produce a predictable result. Functions such as NOW() or CURRENT_USER() depend on time or session state and do not fit. Subqueries, variables, and stored routines are also disallowed. A generated column can refer to an earlier generated column in the definition, not one declared later.

metadata را شاهد بگیرUse metadata as evidence
SELECT COLUMN_NAME, DATA_TYPE, EXTRA, GENERATION_EXPRESSION
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'product_offer'
ORDER BY ORDINAL_POSITION;

SHOW CREATE TABLE product_offer;

در metadata دنبال STORED GENERATED و expression متناظر بگرد. SHOW CREATE TABLE تعریف کامل‌تری می‌دهد و برای بازبینی DDL مفید است. با دسترسی محدود ممکن است metadata همهٔ objectها را نبینی؛ نبود ردیف همیشه اثبات نمی‌کند جدول وجود ندارد.

Look for STORED GENERATED and its expression in metadata. SHOW CREATE TABLE gives the fuller definition and is useful for reviewing DDL. A restricted account may not see every object, so a missing metadata row does not always prove that a table does not exist.

تغییر جدول را مثل تغییر قرارداد ببینTreat table evolution as a contract change

فرض کن جدول قدیمی فقط قیمت پایه دارد. قبل از افزودن ستون محاسباتی، اثر را در محیط آزمایشی بسنج: نسخهٔ Server، حجم جدول، نوع storage و برنامه‌هایی که از SELECT * استفاده می‌کنند. تغییر شکل خروجی می‌تواند مصرف‌کننده‌ای را که به ترتیب/تعداد ستون‌ها وابسته است بشکند.

Suppose a legacy table has only a base price. Before adding a generated column, assess the server version, table size, storage engine, and applications using SELECT *. A changed result shape can break consumers that depend on column order or count.

افزودن و سپس بررسی ستونAdd, then inspect the column
ALTER TABLE product_offer
  ADD COLUMN price_band VARCHAR(12)
  GENERATED ALWAYS AS (
    CASE
      WHEN final_price >= 100000 THEN 'premium'
      ELSE 'standard'
    END
  ) VIRTUAL;

SELECT offer_id, final_price, price_band
FROM product_offer
ORDER BY offer_id;

SHOW CREATE TABLE product_offer;

این تغییر به generated column قبلی ارجاع می‌دهد؛ چون final_price زودتر در تعریف آمده است. پیش از rollout باید DDL و lock/زمان اجرای آن را روی همان نسخه و حجمی که به محیط مقصد نزدیک است آزمایش کنی. قابلیت تغییر Online و هزینه‌اش به عمل ALTER، نسخه و شرایط جدول وابسته است؛ از روی این مثال قول «بدون قفل» نمی‌دهیم.

This expression refers to the earlier generated column final_price. Before rollout, test the DDL and its locking/runtime on a version and table size close to the target. Online behavior and cost depend on the ALTER operation, version, and table conditions; this example does not promise a lock-free change.

از نیاز شروع کن، نه از جذابیت featureStart with the need, not the feature

generated column وقتی مفید است که یک مقدار از دادهٔ همان ردیف، با قاعده‌ای پایدار و deterministic به دست می‌آید و چند query باید همان تعریف را ببینند. اگر مقدار وابسته به نرخ روز، هویت کاربر، جدول دیگری یا وضعیت بیرونی است، آن را با این ستون جا نزن. ابتدا مشخص کن مالک قاعده کجاست و آیا باید نتیجه ذخیره شود یا هنگام گزارش محاسبه شود.

A generated column helps when a value comes from the same row using a stable, deterministic rule and multiple queries need the same definition. If it depends on today’s exchange rate, the current user, another table, or external state, this feature is not the fit. First identify who owns the rule and whether the result belongs in storage or in a report query.

QuestionGenerated column may fitLook elsewhere when…
Where does the value come from?Other columns in the same rowIt needs a lookup or subquery
Does it change on its own?No; inputs determine itTime or session state should change it
Do many consumers repeat the rule?A shared row-level definition may helpThe rule is a report-specific aggregate
Which storage mode?Choose after testing read/write needsDo not infer speed from the keyword alone

1) محاسبه را خودت پیش‌بینی کن / Predict the generated value

For a price of 80,000 with a 15% discount, predict final_price, insert a lab row, and inspect the result.

SELECT unit_price, discount_pct, final_price FROM product_offer WHERE offer_id=3;

2) ورودی با مقدار مشتق‌شده فرق دارد / Separate input from output

INSERT بنویس که قیمت پایه و تخفیف را بدهد اما ستون generated را حذف کند.

Write an INSERT supplying base price and discount while omitting the generated column.

SQL و تفسیر / SQL and interpretation
INSERT INTO product_offer (offer_id,title,unit_price,discount_pct) VALUES (4,'Marker',25000,4);
SELECT offer_id, final_price FROM product_offer WHERE offer_id=4;

این مسیر طبیعی است؛ سرور خروجی را از ورودی‌ها می‌سازد.

This is the intended path; the server derives the output from its inputs.

3) تغییر ورودی چه می‌کند؟ / What changes when an input changes?

تخفیف ردیف ۴ را عوض کن و مقدار generated را دوباره بخوان.

Change row 4’s discount and read the generated value again.

SQL و تفسیر / SQL and interpretation
UPDATE product_offer SET discount_pct=10 WHERE offer_id=4;
SELECT unit_price, discount_pct, final_price FROM product_offer WHERE offer_id=4;

مقدار جدید از ورودی تازه محاسبه می‌شود؛ ستون جداگانه‌ای را دستی update نکردیم.

The new value follows the changed input; no separate output column was manually updated.

4) آزمون مقدار مستقیم / Test a direct assignment

در fixture دورریختنی امتحان کن چرا نمی‌توانی قیمت نهایی را دلخواه درج کنی. اگر statement رد شد، پیام خطا را نگه دار.

In the disposable fixture, test why you cannot insert an arbitrary final price. Keep the error if the statement is rejected.

SQL و تفسیر / SQL and interpretation
INSERT INTO product_offer (offer_id,title,unit_price,discount_pct,final_price) VALUES (5,'Test',100,0,1);

ستون generated ورودی عادی نیست؛ برای INSERT/UPDATE صریح فقط DEFAULT پذیرفته می‌شود.

A generated column is not an ordinary input; an explicit insert/update may supply only DEFAULT.

5) constraint تخفیف را ببین / Observe the discount constraint

ورودی تخفیف ۱۰۱ را در fixture امتحان کن و خطا یا رفتار SQL mode را ثبت کن.

Try a discount of 101 in the fixture and record the constraint result.

SQL و تفسیر / SQL and interpretation
INSERT INTO product_offer (offer_id,title,unit_price,discount_pct) VALUES (6,'Invalid',100,101);

The CHECK should reject an out-of-range value; verify behavior on the target version rather than assuming another release.

6) نوع دادهٔ قیمت را inspect کن / Inspect the price type

metadata را query کن تا نوع و nullability قیمت نهایی را ببینی.

7) STORED را از metadata ثابت کن / Prove the column is STORED

فقط ستون final_price را بخوان و وضعیت generated آن را پیدا کن.

8) تعریف کامل جدول را بخوان / Read the complete table definition

DDL مؤثر جدول را نمایش بده و generated column و CHECK را پیدا کن.

Display the effective DDL and locate the generated column and CHECK.

SQL و تفسیر / SQL and interpretation

این خروجی برای بازبینی schema مفید است؛ تنظیمات همهٔ connectionهای برنامه را اثبات نمی‌کند.

This helps review schema; it does not prove settings for every application connection.

9) مقدار virtual را مقایسه کن / Compare a VIRTUAL value

جدول دوم کوچک بساز که مقدار مشتق‌شده‌اش virtual باشد و همان ردیف را مقایسه کن.

Create a second small table with a virtual derived value and compare the same row.

SQL و تفسیر / SQL and interpretation
CREATE TABLE offer_virtual (price DECIMAL(10,2), discount DECIMAL(5,2), final DECIMAL(10,2) AS (ROUND(price*(1-discount/100),2)) VIRTUAL);
INSERT INTO offer_virtual(price,discount) VALUES(125000,12);
SELECT * FROM offer_virtual;

خروجی برابر است، ولی ذخیره‌سازی متفاوت است؛ برابری نتیجه به معنی یکسان‌بودن هزینه نیست.

The result matches but storage differs; equal output does not mean equal cost.

10) ستون virtual را index کن / Index a virtual column

روی جدول دوم index بساز و تعریف آن را ببین.

Index the second table’s virtual column and inspect the index definition.

SQL و تفسیر / SQL and interpretation
CREATE INDEX ix_offer_virtual_final ON offer_virtual(final);
SHOW INDEX FROM offer_virtual;

وجود index یعنی خود index storage و نگهداری دارد؛ virtual بودن مقدار این هزینه را حذف نمی‌کند.

The index still consumes storage and maintenance; virtual value storage does not remove that cost.

11) update ورودی و index / Change an input behind the index

قیمت پایهٔ ردیف virtual را عوض کن و مقدار نهایی را دوباره بخوان.

Change the virtual row’s base price and read the final value again.

SQL و تفسیر / SQL and interpretation
UPDATE offer_virtual SET price=200000 WHERE price=125000;
SELECT price, discount, final FROM offer_virtual;

سرور expression و index مربوط را متناسب با تغییر ورودی نگه می‌دارد؛ اندازه‌گیری را روی workload واقعی انجام بده.

The server maintains the expression and related index as inputs change; measure with a real workload.

12) expression غیرقطعی را در schema آزمایش رد کن / Test a nondeterministic expression

در fixture تلاش کن generated column وابسته به NOW() بسازی؛ متن خطا را ثبت کن و بگو چرا نتیجه به دادهٔ ردیف محدود نیست.

In the fixture, attempt a generated column based on NOW(); record the error and explain why its value is not limited to row data.

DDL و تفسیر / DDL and interpretation
ALTER TABLE product_offer ADD COLUMN attempted_time DATETIME AS (NOW()) STORED;

سرور باید تعریف را رد کند: نتیجه با زمان عوض می‌شود، حتی اگر ردیف ورودی تغییر نکرده باشد. این شکست DDL است؛ ستون اضافه نشده است.

The server should reject it because time changes independently of the input row. This is a failed DDL statement; the column was not added.

13) subquery را از generated جدا کن / Keep a lookup out of a generated expression

در آزمایش، ساخت ستون generated با subquery را امتحان کن؛ سپس همان ایده را با JOIN قابل‌اجرا بنویس و تعداد نرخ‌های matchشده را کنترل کن.

Attempt a generated column with a subquery, then express the idea with a runnable JOIN and check how many rates match.

دو query و تفسیر / Two queries and interpretation
ALTER TABLE product_offer ADD COLUMN attempted_rate DECIMAL(8,4) AS ((SELECT rate FROM lab_rate LIMIT 1)) VIRTUAL; SELECT p.offer_id,p.final_price*r.rate AS converted_price FROM product_offer AS p JOIN lab_rate AS r ON r.rate_date='2026-10-01';

تعریف generated به expression مجاز همان ردیف محدود است؛ subquery رد می‌شود. JOIN مقدار جدول دیگر را می‌آورد، اما باید روشن کنی اگر چند نرخ match شد چه معنایی دارد.

A generated definition is limited to an allowed expression over the row; a subquery is rejected. JOIN can read another table, but you must define what multiple matching rates mean.

14) افزودن ستون را در آزمایش بسنج / Test a schema addition

یک generated virtual آزمایشی با نام label اضافه و سپس خروجی را بررسی کن.

Add a test virtual generated column named label, then inspect the result.

SQL و تفسیر / SQL and interpretation
ALTER TABLE product_offer ADD COLUMN label VARCHAR(120) AS (CONCAT(title, ' · ', price_band)) VIRTUAL;
SELECT offer_id,label FROM product_offer ORDER BY offer_id;

در صورت وجود نام، ابتدا metadata را بررسی کن؛ ALTER را کورکورانه تکرار نکن.

If the name already exists, inspect metadata first; do not blindly repeat ALTER.

15) مصرف‌کنندهٔ SELECT * را پیدا کن / Find the SELECT-star risk

یک query صریح با نام ستون‌ها بنویس که به تغییر ستون‌های table وابسته نباشد.

Write an explicit projection that does not rely on the table’s changing column list.

SQL و تفسیر / SQL and interpretation
SELECT offer_id, title, unit_price, discount_pct, final_price FROM product_offer ORDER BY offer_id;

ستون‌های موردنیاز روشن‌اند؛ قرارداد برنامه را قبل از افزودن ستون جدید هم باید آزمایش کرد.

The required columns are explicit; still test application contracts before schema changes.

16) generator را با INSERT خراب نکن / Avoid inserting generated values

یک INSERT معتبر برای offer جدید بنویس و نتیجه را با SELECT ثابت کن.

Write a valid insert for a new offer and prove the result with SELECT.

SQL و تفسیر / SQL and interpretation

ورودی‌ها را ثبت می‌کنیم و نتیجه را از خود Server می‌خوانیم.

We store the inputs and read the derived value from the server.

17) نرخ روز ارز را با query مدل کن / Model a daily FX lookup with SQL

یک جدول نرخ آزمایشی بساز و قیمت را برای یک روز با JOIN تبدیل کن؛ بعد بگو چرا نرخ را generated column مستقل نمی‌کنی.

Create a lab rate table and convert a price for one date with a JOIN; explain why the rate is not a standalone generated column.

SQL و تفسیر / SQL and interpretation
CREATE TABLE IF NOT EXISTS lab_rate(rate_date DATE PRIMARY KEY,rate DECIMAL(10,4)); INSERT INTO lab_rate VALUES('2026-10-01',1.1250); SELECT p.offer_id,p.final_price,r.rate,p.final_price*r.rate AS converted_price FROM product_offer AS p JOIN lab_rate AS r ON r.rate_date='2026-10-01';

نرخ از جدول و تاریخ بیرونی می‌آید؛ generated expression برای subquery نیست و تغییرات زمانی نرخ باید صریح مدل شود.

The rate comes from another table and selected date; generated expressions cannot use subqueries, and rate changes over time need explicit modeling.

18) تصمیم طراحی را با شاهد تحویل بده / Submit a decision with evidence

برای final_price بین virtual، stored یا محاسبه در query انتخاب کن. پاسخ باید شامل workload فرضی، DDL یا query، metadata و محدودیت انتخاب باشد.

Choose virtual, stored, or query-time calculation for final_price. Include an assumed workload, DDL or query, metadata evidence, and a limitation.

There is no universal answer; weigh reads, writes, storage, and application contracts together.

قبل از رفتن به فصل بعدBefore moving on

حالا می‌توانی ورودی را از مقدار مشتق‌شده جدا کنی، تفاوت virtual و stored را توضیح بدهی و از metadata برای اثبات تعریف واقعی استفاده کنی. فصل بعد از این model استفاده می‌کند تا دربارهٔ view به‌عنوان رابط داده و مرز دسترسی صحبت کنیم؛ سؤال همچنان همان است: کدام قاعده یک‌بار تعریف می‌شود و چه کسی مجاز است نتیجه را ببیند؟
