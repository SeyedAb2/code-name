FULLTEXT و جست‌وجوی الگو

FULLTEXT and Pattern Search

کاربر دنبال واژهٔ «buffer» در راهنمای فنی می‌گردد. LIKE '%buffer%' ساده است، اما با بزرگ‌شدن متن چه می‌شه؟ آیا B+ Tree همان راه‌حل جست‌وجوی متن است؟ با corpus کوچک، جست‌وجوی exact، prefix و متن کامل رو از هم جدا می‌کنیم و می‌بینیم FULLTEXT هم قواعد tokenizer و stopword خودش رو دارد.

A user wants to find the word “buffer” in a technical guide. LIKE '%buffer%' is simple, but what happens as text grows? Is a B+ tree the same thing as full-text search? With a small corpus, we will distinguish exact, prefix, and full-text searches—and see that FULLTEXT has its own tokenizer and stopword rules.

سه درخواست که شبیه هم نیستندThree requests that are not the same

«مقاله‌ای که دقیقاً این slug رو دارد»، «مقاله‌هایی که URLشان با /guide شروع می‌شه»، و «مقاله‌هایی که دربارهٔ buffer pool حرف می‌زنند» سه query متفاوت‌اند. اولی equality، دومی prefix، سومی جست‌وجوی واژه در متن هست. اگه مسئله رو با یک LIKE حل کنیم، ممکنه برای corpus کوچک کافی باشه، اما شکل query و index باید با نیاز واقعی هم‌خوان باشه.

“The article with this exact slug,” “articles whose URL starts with /guide,” and “articles discussing the buffer pool” are different queries. The first is equality, the second a prefix, and the third a word search in text. A LIKE may be sufficient for a small corpus, but query shape and index must match the actual requirement.

FULLTEXT در InnoDB و MyISAM برای ستون‌های متنی CHAR/VARCHAR/TEXT فراهم هست. آن رو با جست‌وجوی substring یا تحلیل زبان طبیعی پیشرفته یکی نگیریم. FULLTEXT متن رو tokenize می‌کنه؛ قواعد parser، stopword، حد اندازهٔ token و collation می‌تونه نتیجه رو تغییر دهد.

FULLTEXT is available for CHAR/VARCHAR/TEXT columns in InnoDB and MyISAM. It is neither substring search nor advanced natural-language understanding. FULLTEXT tokenizes text; parser, stopword, token-size, and collation rules can affect results.

FULLTEXT index پیش از query ایجاد شده تا متن‌های fixture در index ثبت شوند. اگه تنظیم tokenizer رو تغییر دهی، ممکنه لازم باشه index بازسازی شود؛ این فصل تنظیمات global رو عوض نمی‌کنه.

LIKE برای چه چیزی مناسب است؟What is LIKE suited for?

برای slug دقیق، equality طبیعی و index یکتا حاضر هست. برای prefix URL، الگوی ثابت از چپ ممکنه از B-tree استفاده کند. اما LIKE '%buffer%' ابتدای ثابت ندارد؛ B-tree مرتب نقطهٔ شروع مشخصی نمی‌بیند و ممکنه متن‌ها رو بررسی کند.

For an exact slug, equality is natural and a unique index already exists. A fixed left prefix may use a B-tree. But LIKE '%buffer%' has no fixed starting point; the ordered tree has no clear range start and the engine may inspect text rows.

سه شکل جست‌وجو، سه queryThree search shapes, three queries
EXPLAIN SELECT article_id FROM article
WHERE slug='innodb-buffer-pool';

EXPLAIN SELECT article_id FROM article
WHERE slug LIKE 'innodb-%';

EXPLAIN SELECT article_id FROM article
WHERE body LIKE '%buffer%';

SELECT article_id,title FROM article
WHERE body LIKE '%buffer%';

در fixture، query substring احتمالاً دو مقاله پیدا می‌کنه. به‌خاطر هشت ردیف، ممکنه حتی queryهای indexدار هم scan شوند. این محدودیت‌ها رو از هم نگه دار: index قابل‌استفاده، انتخاب‌شدن توسط optimizer و سریع‌ترشدن روی حجم واقعی سه ادعای متفاوت‌اند.

The substring query likely finds two articles in this fixture. With only eight rows, even indexed queries may scan. Keep these claims separate: an index being usable, being selected, and being faster at real scale are different statements.

جست‌وجوی natural languageNatural-language search

در natural-language mode، عبارت جست‌وجو به‌عنوان واژه‌های متن تحلیل می‌شه. تابع MATCH(title,body) باید با ستون‌های FULLTEXT index سازگار باشه. score یک relevance value است؛ عدد ثابت یا معیار کامل کیفیت نتیجه نیست و با corpus و نسخه فرق می‌کنه.

In natural-language mode, the search phrase is analyzed as text tokens. The columns in MATCH(title,body) must correspond to the FULLTEXT index. The score is a relevance value, not a fixed number or complete quality metric; it varies with corpus and version.

واژهٔ موردنظر و score رو ببینInspect a search term and its score
SELECT article_id,title,
       MATCH(title,body) AGAINST ('buffer pool') AS relevance
FROM article
WHERE MATCH(title,body) AGAINST ('buffer pool')
ORDER BY relevance DESC;

در این fixture احتمالاً مقاله‌های ۱ و ۶ match می‌شوند. عنوان و بدنه هر دو در MATCH آمده‌اند چون index روی هر دو ساخته شد. فهرست دقیق stopword و token-size به تنظیمات Server و parser مربوط است؛ اگه واژه‌ای انتظارش رو داری نیست، پیش از تغییر تنظیمات، tokenization و متن رو بررسی کن.

Articles 1 and 6 are likely matches in this fixture. Both title and body appear in MATCH because the index covers both. Exact stopwords and token-size behavior depend on server settings and parser; if an expected word is absent, inspect tokenization and text before changing configuration.

Boolean mode: شرط واژه‌ها رو صریح‌تر کنBoolean mode: express term requirements

boolean mode عملگرهایی برای الزام، حذف یا ترجیح واژه‌ها دارد. این syntax زبان query کامل نیست و معنای عملگرها قواعد خودش رو دارد. برای شروع، علامت + واژهٔ لازم رو مشخص می‌کنه و - واژه رو کنار می‌ذاره؛ query رو با دادهٔ واقعی اجرا و نتیجه رو بخوان.

Boolean mode supports operators to require, exclude, or favor terms. It is not a full query language and its operators have specific semantics. To begin, + marks a required term and - excludes one; execute against actual data and inspect results.

اجباری‌کردن یک token و حذف دیگریRequire one token and exclude another
SELECT article_id,title
FROM article
WHERE MATCH(title,body)
AGAINST ('+buffer -recovery' IN BOOLEAN MODE);

SELECT article_id,title,
       MATCH(title,body)
       AGAINST ('+buffer -pool' IN BOOLEAN MODE) AS score
FROM article
WHERE MATCH(title,body)
AGAINST ('+buffer -pool' IN BOOLEAN MODE);

در query اول، buffer باید باشه و recovery نباید باشه. query دوم هر دو token رو لازم می‌گیره. واژه‌های کوتاه یا stopword ممکنه در FULLTEXT index نباشند، پس یک نتیجهٔ خالی رو فوراً باگ parser یا database ننام؛ ابتدا تنظیمات و وجود token رو بررسی کن.

The first query requires buffer and excludes recovery. The second requires both tokens. Short terms or stopwords may not be indexed, so do not immediately call an empty result a parser or database bug; first inspect settings and token presence.

چرا MATCH باید با FULLTEXT index جور باشه؟Why must MATCH align with the FULLTEXT index?

FULLTEXT index روی ترکیب مشخصی از ستون‌ها ساخته می‌شه. queryهای MATCH(title,body) و MATCH(body) لزوماً از همان index استفاده نمی‌کنن و ممکنه دومی خطا بده اگه FULLTEXT key سازگار وجود نداشته باشه. metadata رو بخوان؛ اسم «متنی» ستون به‌تنهایی index مناسب نمی‌سازد.

A FULLTEXT index is built for a specific set of columns. MATCH(title,body) and MATCH(body) do not necessarily use the same index, and the latter may fail if no compatible FULLTEXT key exists. Inspect metadata; a column being “text” does not create the right index by itself.

index و MATCH رو با هم تطبیق بدهMatch index definition to MATCH columns
SHOW INDEX FROM article;
EXPLAIN SELECT article_id FROM article
WHERE MATCH(title,body)
AGAINST ('checkpoint');

اگه ستون‌های MATCH عوض شوند، تعریف FULLTEXT و رفتار query رو دوباره بررسی کن. از افزودن کل بدنه به یک index معمولی B-tree برای حل جست‌وجوی واژه استفاده نکن؛ مسئله از نوع دیگری هست.

If MATCH columns change, recheck the FULLTEXT definition and query behavior. Do not add the entire body to a normal B-tree index to solve word search; it is a different problem.

FULLTEXT جای موتور جست‌وجوی زبانی نیستFULLTEXT is not a linguistic search engine

FULLTEXT بر اساس token و تنظیمات parser کار می‌کنه. stem، مترادف، غلط املایی، تحلیل زبان فارسی یا رتبه‌بندی محصولی پیچیده رو خودبه‌خود حل نمی‌کنه. query کوتاه ممکنه به محدودیت token-size یا stopword بخورد. اگه نیاز زبان‌شناختی یا جست‌وجوی typo داری، مسئله رو جدا تعریف کن؛ شاید سرویس جست‌وجوی تخصصی لازم باشه، اما خارج از scope این فصل هست.

FULLTEXT works through tokens and parser settings. It does not automatically solve stemming, synonyms, typos, Persian-language analysis, or complex product ranking. Short terms may encounter token-size or stopword rules. Define linguistic and typo-tolerance requirements separately; a specialized search service may be needed, but that is outside this chapter.

تنظیمات global رو برای یک query آزمایشی عوض نکن.Do not change global settings for one test query.

تغییر stopword یا token-size می‌تونه نیازمند restart/rebuild index باشه و روی workloadهای دیگر اثر بگذارد. ابتدا خروجی، نسخه، parser و تنظیمات فعلی رو ثبت کن.

Changing stopwords or token size may require restart or index rebuild and can affect other workloads. First record output, version, parser, and current settings.
