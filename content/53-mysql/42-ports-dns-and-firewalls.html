رمز درست است، اما client اصلاً به MySQL نمی‌رسه

The password is right, but the client cannot reach MySQL

اپلیکیشن timeout می‌شه. کسی رمز رو عوض می‌کنه، کسی دیگر به firewall دست می‌زند و هیچ‌کس هنوز نمی‌دونه DNS به کدام IP می‌رسه یا server روی کدام interface گوش می‌ده. ترتیب رو برعکس می‌کنیم: از نام و مسیر شبکه شروع می‌کنیم، بعد listener و firewall رو می‌سنجیم و فقط وقتی اتصال برقرار شد سراغ authentication می‌ریم.

The application times out. Someone changes the password, another edits a firewall, and nobody knows which IP DNS returns or which interface the server listens on. We will trace the path in order: name resolution, routing, listener, firewall, and only then authentication.

قبل از password، مسیر رو ثابت کنProve the path before changing a password

برای اتصال TCP باید نام درست resolve شود، مسیر IP برقرار باشه، process روی port مورد انتظار گوش بده و firewall اجازه دهد. بعد از آن تازه MySQL account رو تطبیق و احراز هویت می‌کنه. پیام timeout، refused و access denied یک علت ندارن؛ هرکدام در بخش متفاوتی از مسیر ظاهر می‌شوند.

A TCP connection needs a name that resolves correctly, a route, a process listening on the expected port, and a firewall that permits traffic. Only then does MySQL match an account and authenticate it. Timeout, refused, and access denied are different symptoms from different stages.

خطای مرحلهٔ آخر رو با ابزار مرحلهٔ اول درمان نکن؛ نقطهٔ شکست رو جدا پیدا کن.

Do not use a first-stage tool to fix a last-stage error; locate the failing boundary.

localhost همیشه TCP روی port نیستlocalhost does not always mean TCP to a port

در برخی سیستم‌ها mysql client برای localhost از Unix socket استفاده می‌کنه و گزینهٔ port ممکنه اثری نداشته باشه. برای آزمایش TCP، مقصد IP loopback و protocol رو صریح کن. در Docker هم localhost داخل container به همان container برمی‌گردد؛ برای سرویس دیگر، DNS شبکهٔ Docker و نام سرویس لازم هست.

On some systems, the mysql client uses a Unix socket for localhost, so the port option may not apply. For a TCP test, specify a loopback IP and protocol. In Docker, localhost inside a container points back to that container; another service requires the Docker network and service DNS.

mysql --protocol=TCP --host=127.0.0.1 --port=3306 --user=app -p
SELECT @@hostname, @@port;

داخل container، نام host باید از پیکربندی شبکهٔ همان محیط بیاید. port published میزبان با port داخلی container ممکنه یکی نباشه.

Inside a container, choose the host using that environment's network configuration. A host-published port may differ from the container's internal port.

server روی کدام interface گوش می‌ده؟Which interface is the server listening on?

port به‌تنهایی کافی نیست. bind_address تعیین می‌کنه server روی کدام آدرس‌ها اتصال TCP بپذیرد؛ bind شدن به 127.0.0.1 اتصال remote رو نمی‌پذیرد. پیش از تغییر این تنظیم، خطر exposure رو بسنج و از بازکردن server روی همهٔ interfaceها به‌عنوان راه‌حل سریع پرهیز کن.

The port alone is not enough. bind_address determines which addresses accept TCP; binding to 127.0.0.1 excludes remote connections. Assess exposure before changing it, and do not bind to every interface as a quick fix.

SHOW VARIABLES WHERE Variable_name IN
('port','bind_address','skip_networking');

از سمت OS هم listener رو بررسی کن؛ مجوز OS و ابزار مشاهده ممکنه محدود باشه.

Inspect the operating-system listener too; your OS permissions and tools may limit visibility.

ss -ltn
getent hosts db.example.test

Firewall رو دقیق باز کن؛ نه برای همهOpen the firewall narrowly, not to everyone

اگه معماری اجازه می‌ده، دیتابیس رو public نکن؛ اپلیکیشن از private network وصل شود. اگه اتصال راه دور واقعاً لازم است، منبع رو به subnet یا IP مجاز محدود کن، TLS رو طبق فصل قبل اجباری کن و access logها رو نگه دار. هم firewall سیستم‌عامل و هم firewall ارائه‌دهنده رو جدا بررسی کن.

Keep the database private when the architecture permits; let the application connect over a private network. If remote access is necessary, restrict sources to approved addresses, require TLS as appropriate, and retain access evidence. Check both the host and provider firewalls separately.
