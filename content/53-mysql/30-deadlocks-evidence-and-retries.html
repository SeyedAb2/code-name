هر دو transaction منتظرند؛ کدام‌یک باید عقب‌نشینی کند؟

Both transactions are waiting; which one should back off?

در فصل قبل دیدیم قفل یک ردیف چطور درخواست دیگری رو منتظر می‌ذاره. حالا دو درخواست داریم که هرکدام چیزی رو نگه داشته و چیزی رو می‌خواهد که دست دیگری هست. بن‌بست رو با حدس‌زدن حل نمی‌کنیم: چرخه رو می‌سازیم، خطای server رو می‌خونیم و retry رو در مرز درست انجام می‌دیم.

The previous chapter showed how one row lock can make another request wait. Now two requests each hold something the other needs. We will not guess our way out: we will reproduce the cycle, read the server’s error, and retry at the correct boundary.

دو انتقال کوچک که هیچ‌کدام تمام نمی‌شهTwo small transfers that cannot finish

فرض کن دو حساب داریم: A و B. درخواست اول موجودی A رو کم می‌کنه و بعد B رو زیاد می‌کنه. هم‌زمان درخواست دوم اول B رو کم می‌کنه و بعد A رو زیاد می‌کنه. هرکدام مرحلهٔ اول رو انجام داده‌اند؛ وقتی به مرحلهٔ دوم می‌رسن، باید منتظر قفلی بمانند که transaction دیگر گرفته هست.

Suppose we have accounts A and B. One request debits A and then credits B. At the same time, another debits B and then credits A. Each has completed its first step. At the second step, each must wait for a lock held by the other transaction.

این فقط «کندی» نیست. اگه هیچ‌کدام قفلش رو آزاد نکند، هر دو برای همیشه منتظر می‌مونن. InnoDB این چرخه رو تشخیص می‌ده و یکی از transactionها رو قربانی می‌کنه تا دیگری بتواند ادامه دهد. نکتهٔ عملی این هست که برنامه باید انتظار چنین قربانی‌شدن و اجرای دوبارهٔ کل کار رو داشته باشه.

This is not merely slowness. If neither transaction releases its lock, both can wait forever. InnoDB detects the cycle and rolls back one transaction so the other can proceed. The practical lesson is that an application must expect this victimization and be prepared to run the complete transaction again.

هر transaction یک ردیف رو نگه داشته و برای ردیف دیگر منتظر است؛ این دو انتظار، چرخه می‌سازند.

Each transaction holds one row and waits for the other; together, the waits form a cycle.

اول مرز آزمایش رو بسازیمFirst, establish a safe lab boundary

برای دیدن deadlock به دو connection هم‌زمان روی یک MySQL server نیاز داریم. آزمایش رو در schema مستقل انجام بده؛ قرار نیست روی حساب یا جدول واقعی کسی قفل بگیریم. اگه دسترسی ساخت database نداری، همین جدول رو با نامی که مجوزش رو داری داخل یک محیط محلی/آزمایشی بساز.

To observe a deadlock, we need two concurrent connections to the same MySQL server. Use a separate schema; this is not an experiment for real accounts or production tables. If you cannot create a database, use a local or test environment and a schema you are authorized to modify.

این schema فقط برای تمرین هستThis schema is disposable

The cleanup at the end removes only codenames_deadlock_lab. Check the active database name before running it; never substitute a real schema.

CREATE DATABASE IF NOT EXISTS codenames_deadlock_lab;

The starting result should show two rows with balance 100. If you ran the experiment before, this setup recreates the lab table, so run it only in this disposable schema.

چرخه رو با دو session بسازCreate the cycle with two sessions

ترتیب اجرا مهم هست. در A ردیف حساب A رو تغییر بده و transaction رو باز نگه دار. در B ردیف B رو تغییر بده. حالا A برای B و B برای A منتظر می‌شوند. هر دو session باید به همان server وصل باشند؛ دو پنجره به دو سرور متفاوت، هیچ چرخه‌ای نمی‌سازد.

The order matters. In A, update account A and leave the transaction open. In B, update account B. Now A waits for B, while B waits for A. Both sessions must connect to the same server; two windows connected to different servers cannot form this cycle.

session A — اول قفل ردیف ASession A — lock row A first
USE codenames_deadlock_lab;
START TRANSACTION;
UPDATE account SET balance = balance - 10 WHERE account_id = 'A';
session B — اول قفل ردیف BSession B — lock row B first
USE codenames_deadlock_lab;
START TRANSACTION;
UPDATE account SET balance = balance - 20 WHERE account_id = 'B';

حالا در A سراغ B برو. این دستور معمولاً تا وقتی B تمام شود wait می‌کنه؛ cancelش نکن و session رو باز نگه دار. درحالی‌که A منتظر است، در B هم ردیف A رو update کن. همین درخواست دوم چرخه رو کامل می‌کنه.

Now update B from A. This statement should wait for B to finish; do not cancel it or close the session. While A is waiting, update A from B. That second request completes the cycle.

session A — حالا منتظر قفل B می‌مونهSession A — now waits for B’s lock
UPDATE account SET balance = balance + 10 WHERE account_id = 'B';
session B — چرخه رو کامل می‌کنهSession B — completes the cycle
UPDATE account SET balance = balance + 20 WHERE account_id = 'A';

یکی از دو دستور خطای ERROR 1213 (40001) می‌گیره. لازم نیست از قبل پیش‌بینی کنیم کدام session victim می‌شه؛ انتخاب victim به وضعیت transactionها بستگی دارد. session دیگر معمولاً ادامه می‌ده. بعد از خطا، وضعیت رو با یک connection تازه یا پس از پایان هر دو session بخوان.

One statement receives ERROR 1213 (40001). We should not predict which session will be the victim; the choice depends on transaction state. The other session can usually proceed. After the error, inspect the balances from a fresh connection or after both sessions have finished.

موجودی نهایی رو بررسی کنCheck the final balances
SELECT account_id,balance FROM codenames_deadlock_lab.account
ORDER BY account_id;

در این آزمایش، transaction برنده دو update خودش رو commit می‌کنه و transaction قربانی کامل rollback می‌شه؛ بنابراین مانده‌ها نشان می‌دن فقط انتقال یکی از دو درخواست کامل شده. اگه خروجی با این انتظار نمی‌خواند، هر دو session رو بررسی کن: شاید یکی از آن‌ها هنوز transaction باز دارد یا ترتیب اجرا دقیقاً مطابق مراحل نبوده هست.

In this experiment, the surviving transaction commits both updates and the victim transaction is fully rolled back, so the balances show that only one transfer completed. If the result differs, inspect both sessions: one may still have an open transaction, or the steps may not have been interleaved as described.

1213 چه چیزی رو ثابت می‌کنه؟What does error 1213 prove?

شمارهٔ ۱۲۱۳ با SQLSTATE برابر 40001 خطای deadlock در InnoDB هست. برخلاف یک lock wait معمولی که هنوز ممکنه ادامه پیدا کند، server برای شکستن چرخه یکی از transactionها رو rollback می‌کنه. retry فقط همان statement آخر نیست؛ باید منطق کامل transaction قربانی دوباره اجرا بشه تا invariant کسب‌وکار از ابتدا برقرار شود.

Error 1213 with SQLSTATE 40001 is InnoDB’s deadlock error. Unlike an ordinary lock wait that may still complete, the server rolls back one transaction to break the cycle. Retrying only the last statement is not enough; rerun the victim transaction’s complete business operation so its invariants are re-established from the beginning.

آخرین deadlock ثبت‌شده رو ببینInspect the most recent recorded deadlock
SHOW ENGINE INNODB STATUS\G

در بخش LATEST DETECTED DEADLOCK دنبال هر دو transaction، query منتظرمانده، قفل‌هایی که هرکدام نگه داشته‌اند و خطی مثل WE ROLL BACK TRANSACTION بگرد. قالب و شناسه‌ها با نسخه و workload فرق می‌کنن. این خروجی آخرین deadlock رو نشان می‌ده، نه الزاماً همهٔ رخدادها؛ در سامانهٔ شلوغ ممکنه رخداد تازه‌تری جای آن رو بگیره.

In LATEST DETECTED DEADLOCK, look for both transactions, their waiting statements, the locks each holds, and a line such as WE ROLL BACK TRANSACTION. Formatting and identifiers vary by version and workload. This is the latest recorded deadlock, not necessarily every event; a busy server may replace it with a newer one.

خطا، شاهد است؛ اما شرح کامل واقعه نیستThe error is evidence, not a full incident report

خطای ۱۲۱۳ می‌گه deadlock رخ داده و transaction قربانی rollback شده است؛ به‌تنهایی نمی‌گه ترتیب کسب‌وکار درست بوده، retry امن است، یا کدام درخواست باید از دید محصول اولویت داشته باشه. برای علت‌یابی، statementها، ترتیب lock و شناسهٔ درخواست رو کنار هم نگه دار.

Error 1213 tells us a deadlock occurred and the victim transaction was rolled back. By itself, it does not prove the business ordering was correct, that a retry is safe, or which request should have product priority. Preserve the statements, lock order, and request identifiers for diagnosis.

deadlock با timeout یکی نیستA deadlock is not the same as a timeout

اگه یک transaction منتظر قفلی باشه و صاحب آن دیر تمام کند، ممکنه به lock-wait timeout برسیم: معمولاً خطای 1205. این خطا فقط ثابت می‌کنه انتظار از مهلت تنظیم‌شده عبور کرده؛ الزاماً چرخه‌ای وجود ندارد. در تنظیم پیش‌فرض innodb_rollback_on_timeout=OFF، statement منتظرمانده rollback می‌شه، نه کل transaction. این تفاوت مهمی با ۱۲۱۳ دارد که victim transaction رو کامل rollback می‌کنه.

If a transaction waits for a lock holder that takes too long, it may hit a lock-wait timeout, commonly error 1205. That proves the wait exceeded its configured limit; it does not prove there was a cycle. With the default innodb_rollback_on_timeout=OFF, the waiting statement is rolled back, not the whole transaction. That differs materially from 1213, which rolls back the victim transaction.

پس «هر بار خطای قفل دیدم کل عملیات رو کورکورانه اجرا می‌کنم» قاعدهٔ امنی نیست. نوع خطا، وضعیت transaction و این‌که درخواست قبلی واقعاً commit شده یا نه رو تشخیص بده. به‌خصوص پس از قطع ارتباط، retry خودکار می‌تونه side effect بیرونی مثل ارسال پیام یا پرداخت تکراری بسازد.

So “whenever I see a lock error, blindly rerun everything” is not a safe rule. Identify the error type, transaction state, and whether the previous request actually committed. After a connection failure, an automatic retry may duplicate an external side effect such as a message or payment.

retry در مرز کامل transactionRetry at the complete transaction boundary

کد برنامه باید فقط خطاهای گذرا و شناخته‌شده رو با تعداد تلاش محدود retry کند. برای ۱۲۱۳، transaction تازه باز کن و همهٔ queryهای همان واحد کاری رو از ابتدا اجرا کن. بین تلاش‌ها کمی تأخیر تصادفی کمک می‌کنه دو درخواست هم‌زمان دوباره دقیقاً با همان زمان‌بندی به هم نخورند؛ اما retry بی‌نهایت، latency و فشار server رو بدتر می‌کنه.

Application code should retry only known transient failures, with a bounded attempt count. For 1213, start a fresh transaction and rerun every query in that unit of work. A small randomized delay can keep concurrent requests from colliding in exactly the same schedule again; unbounded retries only worsen latency and server pressure.

شبه‌کد یک retry محدود؛ فقط اسکلت مرزهاA bounded retry outline; transaction boundaries only
for attempt in 1..3:
    begin_transaction()
    try:
        debit_source()
        credit_destination()
        write_transfer_record()
        commit()
        return success
    catch deadlock_1213:
        rollback_if_still_open()
        if attempt == 3: raise
        sleep(random_short_backoff())

این شبه‌کد جای پیاده‌سازی connector نیست؛ API مدیریت transaction و تشخیص error code بین زبان‌ها فرق می‌کنه. نکتهٔ مهم این هست که عملیات بیرون از database رو وسط transaction تکرارشونده انجام ندهی. ثبت پیام در صف یا تماس با سرویس پرداخت رو با الگوی مناسب و کلید idempotency هماهنگ کن.

This pseudocode is not a connector implementation; transaction APIs and error-code handling differ by language. The key point is not to perform repeatable external side effects inside the retry loop. Coordinate queue publication or payment calls with an appropriate pattern and idempotency key.

به‌جای خاموش‌کردن تشخیص، احتمال چرخه رو کم کنReduce cycles instead of disabling detection

پیشگیری به معنی تضمین نبودن deadlock نیست. اما چند تغییر طراحی احتمال برخورد رو کم می‌کنه: transactionها کوتاه باشند؛ همهٔ مسیرهای کاری ردیف‌ها رو با ترتیب یکسان بگیرن؛ شرط‌های update و locking read روی ستون‌های مناسب index داشته باشند؛ و منطق محاسبه یا تماس شبکه رو بیرون از بخش قفل‌دار انجام بدهی. سطح isolation به‌تنهایی درمان deadlock نیست؛ deadlock معمولاً از ترتیب lockهای نوشتن میاد.

Prevention does not guarantee that deadlocks disappear. But several design choices reduce collisions: keep transactions short; acquire rows in a consistent order across code paths; index predicates used by updates and locking reads; and do computation or network calls outside the lock-holding section. Isolation level alone is not a deadlock cure; deadlocks commonly arise from write-lock ordering.

ترتیب ثابت: همیشه A بعد BConsistent order: always A then B
START TRANSACTION;
UPDATE account SET balance = balance - 10 WHERE account_id = 'A';
UPDATE account SET balance = balance + 10 WHERE account_id = 'B';
COMMIT;

اگه همهٔ انتقال‌ها—even انتقال از B به A—ابتدا ردیف A و بعد B رو قفل کنند، چرخهٔ معکوس این مثال از بین می‌ره. در کد واقعی، برای تعیین ترتیب، دو شناسه رو sort کن و همان ترتیب رو برای lock/update همهٔ مسیرها رعایت کن؛ مراقب باش منطق بدهکار و بستانکار رو با ترتیب قفل‌گیری اشتباه نگیری.

If every transfer—including B-to-A transfers—locks A and then B, the reverse-order cycle from this example disappears. In real code, sort the two identifiers to determine lock order and use it consistently across all paths; do not confuse lock order with debit/credit business meaning.

ایندکس هم مهم هست: اگه شرط update ردیف هدف رو دقیق پیدا نکند، InnoDB ممکنه برای کار لازم محدودهٔ بزرگ‌تری رو بررسی و قفل کند. با EXPLAIN و شناخت indexهای شرط، دامنه رو بسنج؛ صرف دیدن primary key در این مثال ساده ثابت نمی‌کنه همهٔ queryهای برنامه دامنهٔ کوچکی دارن.

Indexes matter too: if an update predicate cannot find its target precisely, InnoDB may examine and lock a broader range as needed. Use EXPLAIN and inspect predicate indexes to assess the scope; the primary key in this simple example does not prove every application query has a narrow locking range.

وقتی علامت رو با علت اشتباه می‌گیریمWhen a symptom is mistaken for its cause

«دو query کندند، پس deadlock هست»

اگه server چرخه رو تشخیص دهد معمولاً یکی از transactionها با ۱۲۱۳ rollback می‌شه؛ انتظار طولانی به‌تنهایی می‌تونه lock wait معمولی یا مشکل دیگری باشه. error code و lock evidence رو بخوان.

“Two queries are slow, so it must be a deadlock.”

When the server detects a cycle, one transaction is normally rolled back with 1213. A long wait alone may be an ordinary lock wait or something else. Read the error and lock evidence.

«فقط همان UPDATE رو تکرار می‌کنم»

برای ۱۲۱۳، کل transaction قربانی rollback شده هست. فقط update دوم می‌تونه بخشی از منطق رو جا بیندازد؛ کل واحد کاری رو از ابتدا اجرا کن.

“I will retry only the UPDATE that failed.”

For 1213, the victim transaction was rolled back. Retrying only its second update can skip part of the business operation; rerun the unit of work from the beginning.

«1205 هم همان 1213 هست»

timeout ثابت نمی‌کنه چرخه‌ای بوده و با تنظیم پیش‌فرض فقط statement آخر rollback می‌شه. مرز transaction رو صریح بررسی کن.

“1205 is the same as 1213.”

A timeout does not prove a cycle, and by default it rolls back only the waiting statement. Inspect the transaction boundary explicitly.

«تشخیص deadlock رو خاموش کنیم»

خاموش‌کردن detector چرخه رو رفع نمی‌کنه؛ انتظار می‌تونه تا timeout ادامه پیدا کند. اول ترتیب lock و طول transaction رو بررسی کن.

“Let’s disable deadlock detection.”

Disabling the detector does not remove the cycle; sessions may wait until timeout instead. Inspect lock ordering and transaction duration first.
