نگهداری index و آمار

Index Maintenance and Statistics

query بعد از تغییر بزرگ داده plan دیگری گرفته و تیم می‌گه «همهٔ indexها رو rebuild کن». این دو کار یکی نیستند: شاید optimizer آمار تازه لازم دارد؛ شاید storage واقعاً نیازمند بازآرایی است؛ شاید هم plan قبلی از اول درست بوده. اول evidence رو جدا می‌کنیم، بعد دربارهٔ ANALYZE یا OPTIMIZE تصمیم می‌گیریم.

After a large data change, a query has a different plan and the team says, “Rebuild every index.” These are not the same problem: the optimizer may need fresh statistics, storage may need reorganization, or the prior plan may have been fine. We will separate evidence before choosing ANALYZE or OPTIMIZE.

«rebuild همه‌چیز» جواب تشخیصی نیست“Rebuild everything” is not a diagnosis

بعد از import، تخمین ردیف‌ها تغییر کرده و یک query کندتر شده. اگه فقط ANALYZE TABLE لازم باشه، بازسازی فیزیکی کل جدول هزینهٔ بی‌دلیل دارد. اگه نیاز به بازآرایی storage باشه، تازه‌کردن آمار به‌تنهایی فضای فیزیکی رو دوباره سازمان نمی‌ده. باید بپرسیم دقیقاً کدام نشانه رو داریم.

After an import, row estimates changed and one query slowed down. If only ANALYZE TABLE is needed, rebuilding the whole table adds needless cost. If storage needs reorganization, refreshing statistics alone does not reorganize physical layout. We need to ask which signal we actually have.

InnoDB optimizer statistics تخمین‌هایی دربارهٔ جدول و indexها هستن و روی انتخاب plan اثر می‌گذارند. ANALYZE TABLE این آمار رو به‌روزرسانی می‌کنه. OPTIMIZE TABLE برای InnoDB به بازسازی table و index مربوط می‌شه و می‌تونه زمان، I/O، فضای موقت و اثر عملیاتی داشته باشه. این‌ها رو با repair فساد یا backup اشتباه نگیریم.

InnoDB optimizer statistics estimate table and index characteristics and influence plan selection. ANALYZE TABLE refreshes statistics. For InnoDB, OPTIMIZE TABLE involves rebuilding the table and indexes and can consume time, I/O, temporary space, and operational capacity. Neither is a repair for corruption nor a backup.

ANALYZE: آمار تازه، نه index تازهANALYZE: fresh statistics, not a new index

وقتی حجم یا توزیع داده به‌طور معنادار عوض شده، optimizer ممکنه از تخمین قدیمی استفاده کند. baseline رو با EXPLAIN و metadata ثبت می‌کنیم، ANALYZE می‌زنیم و همان query رو دوباره می‌سنجیم. تغییر plan ممکنه رخ بده یا نه؛ ANALYZE دستور «index استفاده کن» نیست.

After significant data-volume or distribution changes, the optimizer may be using stale estimates. Capture EXPLAIN and metadata, run ANALYZE, and inspect the same query again. The plan may change or remain the same; ANALYZE is not a command to “use the index.”

قبل، بعد و دادهٔ واقعیBefore, after, and actual data
EXPLAIN SELECT ticket_id FROM ticket
WHERE team_id=2 AND state='open';
SHOW INDEX FROM ticket;

ANALYZE TABLE ticket;

EXPLAIN SELECT ticket_id FROM ticket
WHERE team_id=2 AND state='open';
SELECT COUNT(*) FROM ticket
WHERE team_id=2 AND state='open';

تعداد واقعی query آخر رو از plan جدا نگه دار. cardinality در SHOW INDEX تخمینی هست و بعد از ANALYZE هم تضمین نمی‌شه دقیقاً با COUNT برابر شود. اگه هنوز query کند است، plan details و data distribution رو بررسی کن؛ تکرار ANALYZE بدون تغییر evidence درمان نیست.

Keep the final query’s actual count separate from the plan. SHOW INDEX cardinality is an estimate and is not guaranteed to equal COUNT after ANALYZE. If the query remains slow, inspect plan details and distribution; repeating ANALYZE without new evidence is not a cure.

OPTIMIZE: کار فیزیکی بزرگ‌تری هستOPTIMIZE: a larger physical operation

مستندات MySQL توضیح می‌ده که OPTIMIZE TABLE برای InnoDB به بازسازی table (از جمله ALTER TABLE ... FORCE) نگاشت می‌شه؛ جزئیات و محدودیت‌ها به نسخه و نوع table وابسته‌اند. عملیات ممکنه I/O زیادی مصرف کند و در شرایط خاص روش copy به‌کار رود. آن رو برای دیدن خروجی روی fixture اجرا می‌کنیم، نه به‌عنوان cron سراسری.

MySQL documentation describes OPTIMIZE TABLE for InnoDB as mapping to a table rebuild (including ALTER TABLE ... FORCE); details and restrictions depend on version and table type. It may consume substantial I/O, and under some conditions a copy method is used. We run it on the fixture to inspect output, not as a universal cron job.

خروجی status/note نتیجهٔ عملیات رو می‌ده، نه اینکه حتماً query خاصی سریع‌تر شده. InnoDB مقداری فضای آزاد رو برای رشد آینده نگه می‌دارد؛ وجود space خالی به‌تنهایی fragmentation زیان‌بار رو ثابت نمی‌کنه. قبل و بعد باید روی همان query و workload اندازه‌گیری شود.

Status/note output reports the operation, not that a particular query became faster. InnoDB leaves some free space for future growth; free space alone does not prove harmful fragmentation. Measure the same query and workload before and after.

روی جدول بزرگ، اول پیامد رو بررسی کن.Assess impact before touching a large table.

زمان اجرا، مصرف دیسک موقت، replication lag، I/O، قفل‌های کوتاه metadata و محدودیت‌های FULLTEXT/online DDL رو در نسخهٔ خودت بررسی کن. برای تغییر production، backup معتبر و برنامهٔ rollback داشته باش.

Check runtime, temporary disk use, replication lag, I/O, brief metadata locks, and FULLTEXT/online-DDL restrictions for your version. For production, have a verified backup and rollback plan.
