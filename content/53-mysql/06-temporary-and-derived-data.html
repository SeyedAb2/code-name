Temporary table و دادهٔ موقت در MySQL

Temporary Tables and Transient Data in MySQL

گزارش ماهانه به یک مجموعهٔ میانی نیاز دارد. ساختن جدول دائمی برای داده‌ای که چند دقیقه بعد دور ریخته می‌شه، هم دردسر پاک‌سازی دارد و هم ممکنه اسمش با جدول برنامه برخورد کند. اما temporary table دقیقاً تا کی زنده می‌مونه؟ جواب رو با دو connection واقعی پیدا می‌کنیم.

A monthly report needs an intermediate result. A permanent table for data discarded minutes later creates cleanup work and can collide with application tables. How long does a temporary table actually live? We will find out with two real connections.

پیش‌نیازPrerequisite: فصل ۵ · view و scope دسترسیمحیط مرجعLab baseline: MySQL 9.7.2 · دو connection جدازمانTime: ۸۵ دقیقه · ۱۸ تمرین

نتیجهٔ میانی کجا باید زندگی کند؟Where should an intermediate result live?

یک analyst می‌خواهد فروش یک روز رو مرتب کند، چند مرحله روی نتیجه انجام دهد و بعد گزارش رو تحویل بده. ساخت table دائمی ممکنه دادهٔ موقت رو برای نفر بعد باقی بگذارد؛ یک SELECT تو‌در‌تو هم می‌تونه خوانایی رو سخت کند. پیش از انتخاب ابزار، باید بفهمیم نتیجهٔ میانی چه طول عمری لازم دارد.

An analyst needs to sort one day of sales, apply a few steps, and produce a report. A permanent table may leave transient data for the next person; a deeply nested SELECT may be hard to read. Before choosing a tool, determine how long the intermediate result must live.

در MySQL، جدول TEMPORARY به connection فعلی تعلق دارد و با بستن همان session خودکار حذف می‌شه. CTE فقط در یک statement نام دارد و derived table یک query در FROM هست. optimizer هم ممکنه برای اجرای query خودش temporary storage بسازد؛ آن با جدول موقت ساخته‌شده توسط کاربر یکی نیست.

In MySQL, a TEMPORARY table belongs to the current connection and is dropped when that session closes. A CTE exists for one statement; a derived table is a query in FROM. The optimizer may also use internal temporary storage, which is not the same as a user-created temporary table.

یک اسم، دو connection، دو دنیای جداOne name, two connections, separate worlds

دو client مستقل رو به همان MySQL server و database وصل کن و آن‌ها رو A و B بنام. دو tab در یک ابزار همیشه دو connection نیستند؛ شناسه رو query کن. اگه ID متفاوت باشه، دو session جدا داری.

Connect two independent clients to the same MySQL server and database; call them A and B. Two tabs do not always mean two connections, so query the ID. Different IDs prove separate sessions.

در هر دو نشست اجرا کنRun in both sessions
SELECT CONNECTION_ID() AS session_id,
       DATABASE() AS current_database,
       VERSION() AS server_version;

در A، جدول موقت و ردیف‌های یک query محدود رو بساز؛ سپس همان SELECT رو در B اجرا کن. اگه B خطای نبودن table داد، اول IDهای نشست رو مقایسه کن؛ restart یا ساخت دوبارهٔ database تشخیص درستی نیست.

In A, create a temporary table from a bounded query result, then run the same SELECT in B. If B says the table does not exist, compare session IDs first; restarting or recreating the database is not a useful diagnosis.

در نشست AIn session A
USE codenames_mysql_ch04;
CREATE TEMPORARY TABLE daily_offer_work (
  offer_id BIGINT PRIMARY KEY,
  title VARCHAR(100) NOT NULL,
  final_price DECIMAL(10,2) NOT NULL
) ENGINE=InnoDB;
INSERT INTO daily_offer_work
SELECT offer_id,title,final_price
FROM product_offer WHERE final_price > 0;
SELECT * FROM daily_offer_work ORDER BY offer_id;

در A باید ردیف‌ها دیده شوند؛ در B انتظار داریم table پیدا نشود. این مرز session است، نه مرز database: هر دو به یک database وصل‌اند، ولی temporary object فقط در یکی ساخته شده.

A should see the rows; B should not find the table. This is a session boundary, not a database boundary: both use the same database, but the temporary object exists in only one session.

در نشست BIn session B
SELECT CONNECTION_ID(),DATABASE();
SELECT * FROM daily_offer_work;

اسم هم‌نام، جدول دائمی رو پنهان می‌کنهA same-name temporary table hides the permanent one

اگه در یک session، temporary table با نام یک table دائمی بسازی، همان نام در آن session به جدول موقت اشاره می‌کنه و جدول اصلی پنهان می‌شه تا temporary حذف یا connection بسته شود. برای دیدن رفتار از نام اختصاصی در fixture استفاده کن؛ هیچ‌وقت این ترفند رو روی جدول برنامه امتحان نکن.

If a session creates a temporary table with the name of a permanent table, that name resolves to the temporary table in that session. The permanent table is hidden until the temporary one is dropped or the connection closes. Demonstrate this only with a dedicated lab name.

آزمایش نام هم‌پوشان در database تمرینیTest name shadowing in the lab database
CREATE TABLE name_probe (source_label VARCHAR(20));
INSERT INTO name_probe VALUES ('permanent');
CREATE TEMPORARY TABLE name_probe (source_label VARCHAR(20));
INSERT INTO name_probe VALUES ('temporary');
SELECT * FROM name_probe;
DROP TEMPORARY TABLE name_probe;
SELECT * FROM name_probe;

دو خروجی رو کنار هم نگه دار: اولی باید temporary و دومی permanent باشه. این تفاوت نشان می‌ده اسم یکسان به‌تنهایی هویت object رو ثابت نمی‌کنه؛ context session هم مهم هست.

Keep both outputs: the first should be temporary, the second permanent. The same name does not identify the object by itself; session context matters.

Temporary table، CTE یا derived table؟Temporary table, CTE, or derived table?

اگه نتیجه فقط در یک statement لازم است، CTE ممکنه ساده‌تر باشه؛ query کوچک داخل FROM می‌تونه derived table بماند. temporary table رو زمانی بررسی کن که چند statement در همان connection باید نتیجهٔ واسط مشترکی رو reuse یا تغییر دهند.

If a result is needed for one statement, a CTE may be simpler; a small query in FROM can remain a derived table. Consider a temporary table when multiple statements in one connection must reuse or modify the same intermediate result.

CTE به یک statement محدود هستA CTE belongs to one statement
WITH daily AS (
  SELECT offer_id,title,final_price
  FROM codenames_mysql_ch04.product_offer
  WHERE final_price > 0
)
SELECT offer_id,title,final_price
FROM daily ORDER BY final_price DESC;

بعد از تمام‌شدن statement، نام daily برای query بعدی وجود ندارد. «temporary» هم الزاماً به معنی «فقط RAM» نیست؛ اندازه، engine، تنظیمات و نیاز optimizer می‌تونن storage موقت رو درگیر کنند. جدول بزرگ رایگان نیست و ممکنه دیسک مصرف کند.

After the statement ends, daily is unavailable to the next query. “Temporary” does not mean “RAM only”; size, engine, configuration, and optimizer needs can involve temporary storage. A large temporary table is not free and may consume disk.

connection pool مرز عمر رو عوض نمی‌کنهA connection pool does not change the lifetime boundary

در برنامه، هر request ممکنه connection متفاوتی بگیره؛ temporary table ساخته‌شده در درخواست اول الزاماً برای درخواست بعدی در دسترس نیست. برعکس، connection reuseشده ممکنه temporary table قدیمی رو نگه داشته باشه. از cleanup روشن استفاده کن و خطاهای میانی رو هم مدیریت کن.

An application request may receive a different connection, so a temporary table from the first request is not necessarily available to the next. Conversely, a reused connection may retain an old temporary table. Use explicit cleanup and handle intermediate failures.

شروع پاک و پایان روشنStart clean and finish explicitly
DROP TEMPORARY TABLE IF EXISTS offer_stage;
CREATE TEMPORARY TABLE offer_stage AS
SELECT offer_id,title,final_price
FROM codenames_mysql_ch04.product_offer
WHERE final_price > 0;
SELECT COUNT(*) AS staged_rows FROM offer_stage;
DROP TEMPORARY TABLE offer_stage;

cleanup صریح جای بستن connection یا مسیر finally در برنامه رو نمی‌گیره. همچنین عمر table رو با transaction اشتباه نگیر: COMMIT به‌خودی‌خود temporary table رو حذف نمی‌کنه.

Explicit cleanup does not replace connection management or a finally path in the application. Do not confuse table lifetime with a transaction: COMMIT does not itself drop the temporary table.

وقتی جدول «پیدا نمی‌شه»، اول نشست رو ببینWhen the table is missing, inspect the session first

در MySQL، SHOW TABLES temporary tableها رو فهرست نمی‌کنه. پس نبودن اسم در این خروجی ثابت نمی‌کنه SELECT در همان session شکست می‌خورد. ID اتصال رو ثبت کن، خود query رو اجرا کن و هر دو مدرک رو کنار هم بخوان.

In MySQL, SHOW TABLES does not list temporary tables. Their absence from that output does not prove a SELECT in the same session will fail. Record the connection ID, run the query itself, and interpret both pieces of evidence together.

آزمون در همان connectionTest in the same connection

SHOW TABLES LIKE 'offer_stage';
SELECT COUNT(*) FROM offer_stage;
