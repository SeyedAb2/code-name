اگه فقط یک مرحله رو بخواهیم پس بگیریم چه؟

What if we need to undo only one step?

انتقال اصلی موفق شده، اما یک کار اختیاری—مثلاً افزودن هزینهٔ جانبی—باید لغو شود. اگه ROLLBACK کامل بزنیم، کار اصلی هم از بین می‌ره؛ اگه COMMIT کنیم، تغییر ناخواسته می‌مونه. فصل قبل مرز کلی transaction رو ساختیم. حالا یک نقطهٔ بازگشت داخل همان مرز می‌ذاریم.

The main transfer succeeded, but an optional step—such as adding a fee—must be canceled. A full ROLLBACK would undo the main work; COMMIT would keep the unwanted change. The previous chapter established the transaction boundary. Now we add a recovery point inside that same boundary.

کار اصلی رو از هزینهٔ اختیاری جدا کنیمSeparate the core transfer from an optional fee

دو حساب داریم. انتقال ۱۰ واحدی باید انجام بشه؛ بعد برنامه یک هزینهٔ جانبی ۲ واحدی رو هم امتحان می‌کنه. آن مرحلهٔ دوم به مشکل می‌خورد، اما نمی‌خوایم انتقال سالم رو هم لغو کنیم. پیش از مرحلهٔ اختیاری، یک savepoint می‌ذاریم. اگه لازم شد، فقط تا همان نقطه عقب می‌ریم و transaction رو باز نگه می‌داریم.

We have two accounts. A transfer of 10 units must complete, then the application attempts an optional fee of 2. That second step has a problem, but we do not want to cancel the valid transfer. We create a savepoint before the optional step. If needed, we roll back to that point while keeping the transaction open.

SAVEPOINT transaction تازه‌ای تو در تو نمی‌سازد؛ فقط یک نام برای جای مشخصی در transaction فعلی ثبت می‌کنه. هنوز باید در پایان تصمیم بگیریم کل تغییرهای باقی‌مانده COMMIT شوند یا ROLLBACK.

SAVEPOINT does not create a nested transaction. It names a point in the current transaction. We still decide at the end whether to COMMIT or roll back all remaining changes.

نقطهٔ بازگشت رو بعد از کار اصلی بگذارPlace the savepoint after the core work

اول transfer رو انجام می‌دیم، بعد savepoint می‌ذاریم و هزینهٔ اختیاری رو کم می‌کنیم. پیش‌بینی کن بعد از ROLLBACK TO چه عددهایی باید ببینیم. یادت باشه ROLLBACK TO خودش transaction رو نمی‌بندد.

First we transfer, then create a savepoint and subtract the optional fee. Predict the balances after ROLLBACK TO. Remember: ROLLBACK TO does not end the transaction.

اجرا در یک connectionRun in one connection
START TRANSACTION;
UPDATE account SET balance=balance-10 WHERE account_id=1;
UPDATE account SET balance=balance+10 WHERE account_id=2;
SAVEPOINT transfer_done;
UPDATE account SET balance=balance-2 WHERE account_id=1;
SELECT * FROM account ORDER BY account_id;
ROLLBACK TO SAVEPOINT transfer_done;
SELECT * FROM account ORDER BY account_id;
COMMIT;
SELECT * FROM account ORDER BY account_id;

قبل از rollback موضعی، مقدار موقت حساب اول ۸۸ و حساب دوم ۶۰ هست. پس از آن باید ۹۰ و ۶۰ ببینی: transfer باقی مانده و هزینهٔ اختیاری برگشته هست. بعد از COMMIT همین ۹۰ و ۶۰ پایدار می‌مونن.

Before the partial rollback, the temporary values are 88 and 60. Afterward, expect 90 and 60: the transfer remains while the optional fee is undone. COMMIT makes those remaining values permanent.

این خروجی ثابت نمی‌کنه transaction تمام شده؛ فقط SELECTهای بعدی و در پایان COMMIT آن رو نشان می‌دن. اگه بعد از ROLLBACK TO تغییر دیگری بزنی، آن تغییر همچنان در همان transaction هست.

This output does not show that the transaction ended. Later statements and the final COMMIT establish that. Any further changes after ROLLBACK TO still belong to the same transaction.

اگه چند savepoint بسازی و به نقطهٔ قدیمی‌تر برگردی، savepointهای جدیدتر حذف می‌شوند. اگه همان نام رو دوباره بسازی، نقطهٔ قبلی با نقطهٔ تازه جایگزین می‌شه. نام اشتباه یا نقطه‌ای که دیگر وجود ندارد خطا می‌ده؛ پس از خطا، نام‌ها و وضعیت transaction رو بررسی کن.

If you create several savepoints and roll back to an earlier one, later savepoints are discarded. Reusing a name replaces its previous point. A misspelled or unavailable name raises an error; inspect the names and transaction state before proceeding.

rollback موضعی به معنی آزادشدن همهٔ قفل‌ها نیستA partial rollback does not mean every lock is released

InnoDB هنگام ROLLBACK TO الزاماً همهٔ row lockهایی رو که بعد از savepoint گرفته شده‌اند آزاد نمی‌کنه. پس savepoint راهی برای کوتاه‌کردن همهٔ قفل‌ها یا کاهش قطعی contention نیست؛ transaction رو به‌اندازهٔ لازم کوتاه نگه دار.

InnoDB does not necessarily release every row lock acquired after a savepoint when rolling back to it. A savepoint is not a guaranteed way to shorten locks or eliminate contention; keep transactions as short as practical.

وقتی savepoint پیدا نمی‌شهWhen the savepoint cannot be found

فرض کن برنامه خطای SAVEPOINT ... does not exist می‌گیره. به‌جای ساختن همان نام بی‌درنگ، چند احتمال رو بررسی کن: آیا در همان connection هستی؟ transaction رو قبلاً commit یا rollback نکرده‌ای؟ آیا نام رو درست نوشته‌ای؟ آیا یک DDL ناخواسته مرز transaction رو نبسته؟

Suppose the application reports that a SAVEPOINT does not exist. Before recreating the name, check: are you in the same connection? Did an earlier COMMIT or full ROLLBACK end the transaction? Is the name correct? Did DDL implicitly close the transaction?

The middle statement should report a missing savepoint; the final ROLLBACK closes the boundary. A statement error is not the same as the whole transaction state. After an error, inspect the session and deliberately commit or roll back.

این nested transaction نیستThis is not a nested transaction

ممکنه برنامه‌ای چند تابع داشته باشه و هرکدام خیال کنند transaction جداگانه‌ای شروع کرده‌اند. SAVEPOINT فقط نقطهٔ برگشت در همان transaction است؛ COMMIT داخلی نمی‌تونه «فقط بخش تابع» رو commit کند. اگه COMMIT بزنی، کل transaction جاری بسته می‌شه و savepointها از بین می‌رن.

An application may have several functions, each behaving as if it opened an independent transaction. A SAVEPOINT is only a rollback marker within one transaction; an inner COMMIT cannot commit only one function’s portion. COMMIT closes the current transaction and removes its savepoints.

DDL رو هم وسط این کار نگذار. در MySQL بسیاری از statementهای DDL implicit commit می‌کنن؛ atomic بودن خود DDL به معنی rollbackشدن آن با transaction قبلی نیست.

Do not put DDL in the middle of this workflow. Many MySQL DDL statements implicitly commit; the DDL statement’s atomicity does not make it rollbackable within the prior transaction.

نقطهٔ میانی، پایان transaction نیستA savepoint is not the end of a transaction
