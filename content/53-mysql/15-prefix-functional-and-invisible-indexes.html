Prefix، functional و invisible index

Prefix, Functional, and Invisible Indexes

یک جست‌وجوی رشته‌ای با LOWER(email) داریم، یک آدرس طولانی که index کاملش پهن است، و یک index مشکوک که شاید دیگر لازم نباشد. DROP کردنش در production تصمیم پرریسکی است. هر سه مسئله را در fixture جدا می‌کنیم: prefix فقط ابتدای مقدار را نگه می‌دارد، functional مقدار expression را index می‌کند، و invisible index برای optimizer پنهان می‌شود اما حذف نمی‌شود.

We have a string search using LOWER(email), a long URL whose full index is wide, and a suspicious index that may no longer be needed. Dropping it in production is risky. We will separate the problems in a fixture: a prefix stores only the start of a value, a functional index indexes an expression, and an invisible index is hidden from the optimizer without being dropped.

قبل از دست‌کاری، مسئلهٔ query را جدا کنSeparate the query problem before changing an index

«روی رشته index بگذار» یک درخواست دقیق نیست. آیا equality روی کل email داریم؟ جست‌وجو بر اساس نسخهٔ lowercase است؟ prefix ثابت URL را می‌خواهیم؟ یا داریم بررسی می‌کنیم index فعلی برای workload دیگری لازم نیست؟ هرکدام ساختار متفاوتی می‌خواهد و هیچ‌کدام با نام پرزرق‌وبرق index خودبه‌خود سریع نمی‌شود.

“Index the string” is not a precise requirement. Do we compare the full email? Search a lowercase expression? Match a fixed URL prefix? Or test whether an existing index is still needed by the workload? Each asks for a different structure, and none becomes fast just because its index has a fancy name.

Prefix index فقط بخشی از مقدار را نگه می‌داردA prefix index stores only part of a value

اگر query با چند نویسهٔ آغازین سروکار دارد، می‌توان prefix رشته را index کرد. این کار index را کوچک‌تر می‌کند، اما prefix ممکن است بین چند مقدار مشترک باشد. در جست‌وجوی کامل، موتور می‌تواند prefix را برای پیدا کردن candidateها به‌کار ببرد و بقیهٔ مقدار را از row بررسی کند؛ prefix index معادل UNIQUE روی کل مقدار نیست.

If queries use leading characters, a string prefix can be indexed. That makes the index smaller, but multiple values may share the prefix. For a full-value search, the engine can use the prefix to find candidates and check the remaining value from rows; a prefix index is not equivalent to uniqueness on the full value.

فقط ۸ نویسهٔ اول URL را index کنIndex only the first 8 URL characters
CREATE INDEX ix_page_url_prefix ON contact(page_url(8));
SHOW INDEX FROM contact WHERE Key_name='ix_page_url_prefix';

EXPLAIN SELECT contact_id FROM contact
WHERE page_url LIKE 'https://docs%';

در SHOW INDEX مقدار Sub_part طول prefix را نشان می‌دهد. طول برای رشته‌های متنی برحسب character تعریف می‌شود، در حالی که محدودیت‌های storage برحسب byte هستند؛ charset چندبایتی را فراموش نکن. اگر term از prefix بلندتر باشد، engine ممکن است candidateها را محدود کند و مقدار کامل را بررسی کند.

In SHOW INDEX, Sub_part reports the prefix length. For nonbinary strings the declared length is in characters, while storage limits are measured in bytes; account for multibyte character sets. If a search term exceeds the prefix, the engine may narrow candidates and then check the full value.

Prefix خیلی کوتاه ممکن است collision زیادی بسازد؛ prefix بلندتر index را پهن می‌کند. طول مناسب را از توزیع واقعی prefixها و queryها بسنج، نه از حدس روی این شش ردیف.

A prefix that is too short may create many collisions; a longer one makes the index wider. Choose length from real prefix distribution and queries, not from these six rows.

وقتی خود expression در شرط استWhen the predicate uses an expression

query LOWER(email)=... روی expression نتیجه می‌گیرد؛ index عادی روی email لزوماً همان expression را index نکرده. در نسخه‌های امروزی MySQL می‌توان functional key part ساخت. expression باید در syntax با پرانتز مشخص شود و از محدودیت‌های expressionهای مجاز برای generated columns پیروی می‌کند.

A predicate such as LOWER(email)=... compares an expression; a plain index on email does not necessarily index that expression. Current MySQL versions support functional key parts. The expression must be parenthesized in the syntax and obeys restrictions that apply to generated-column expressions.

یک functional index هم‌راستا با queryA functional index aligned with the query
CREATE INDEX ix_email_lower ON contact ((LOWER(email)));
SHOW INDEX FROM contact WHERE Key_name='ix_email_lower';

EXPLAIN SELECT contact_id FROM contact
WHERE LOWER(email)='ava@example.test';

SELECT contact_id FROM contact
WHERE LOWER(email)='ava@example.test';

انتظار داریم ردیف ۱ برگردد؛ plan را در نسخهٔ خودت ببین. شکل expression در query باید با expression index سازگار باشد و collation هم می‌تواند رفتار مقایسه را تغییر دهد. functional index برای هر تابع دلخواه مجاز نیست؛ expressionهایی با subquery، variable یا stored function را این‌طور index نکن.

The expected row is 1; inspect the plan on your version. The query expression must match the indexed expression, and collation can affect comparisons. Not every function is permitted; do not try to index expressions involving subqueries, variables, or stored functions this way.

درون MySQL functional key part به virtual generated column پنهان متکی است؛ index همچنان فضای خودش را می‌گیرد و به‌روزرسانی مقدار پایه باید آن را نگه دارد. این قابلیت، هزینهٔ write را حذف نمی‌کند.

Internally, a functional key part relies on a hidden virtual generated column; the index still consumes space and must be maintained when source values change. This feature does not eliminate write cost.

Invisible یعنی optimizer فعلاً آن را انتخاب نکندInvisible means the optimizer does not choose it normally

اگر indexی شاید بلااستفاده باشد، حذف فوری آن می‌تواند queryهای کم‌تکرار یا مسیرهای ناشناخته را خراب کند. MySQL اجازه می‌دهد یک secondary index را invisible کنیم و planها را بدون آن بسنجیم. index هنوز وجود دارد و writeها همچنان باید آن را نگه دارند؛ invisible به معنی حذف فضا یا هزینهٔ نوشتن نیست.

If an index may be unused, dropping it immediately can break infrequent or unknown query paths. MySQL lets us make a secondary index invisible and inspect plans without it. The index still exists and writes still maintain it; invisibility does not remove storage or write cost.

آزمایش برگشت‌پذیر روی index تاریخA reversible test on a date index
CREATE INDEX ix_created_at ON contact(created_at);
EXPLAIN SELECT contact_id FROM contact
WHERE created_at >= '2026-01-04 00:00:00';

ALTER TABLE contact ALTER INDEX ix_created_at INVISIBLE;
SHOW INDEX FROM contact WHERE Key_name='ix_created_at';
EXPLAIN SELECT contact_id FROM contact
WHERE created_at >= '2026-01-04 00:00:00';

ALTER TABLE contact ALTER INDEX ix_created_at VISIBLE;

ستون Visible در SHOW INDEX باید NO و بعد YES باشد. در حالت invisible، optimizer آن را برای queryهای معمولی در نظر نمی‌گیرد، اما index ساخته‌شده و به‌روزشونده باقی می‌ماند. plan ممکن است به primary یا table scan تغییر کند؛ روی fixture کوچک تغییر را قطعی فرض نکن.

The Visible column should show NO and then YES. While invisible, the optimizer does not consider it for ordinary queries, but the built index remains and is maintained. The plan may switch to the primary key or a table scan; do not expect a visible change on this tiny fixture.

آزمایش را با مرز امن انجام بده.Keep the experiment bounded and safe.

قبل از پایان تمرین index را visible کن. در production، تمام workloadها، replicaها، queryهای زمان‌بندی‌شده و مسیرهای کم‌تکرار را بررسی کن. invisible index آزمایش اثر plan است، نه اثبات اینکه حذف نهایی بی‌خطر است.

Make the index visible again before finishing. In production, account for all workloads, replicas, scheduled queries, and infrequent paths. An invisible-index test probes plan impact; it does not prove that permanent removal is safe.

این سه قابلیت را با هم قاطی نکنDo not conflate these three features

نام قابلیت را از نیاز query انتخاب کن. برای expression، functional index؛ برای ابتدای رشته، prefix؛ برای آزمایش plan بدون حذف، invisible. در هر سه حالت، قبل و بعد را با query و metadata ثبت کن.

Choose the feature from the query need: functional for an expression, prefix for leading string characters, invisible for plan testing without dropping. In all three cases, record before and after with queries and metadata.

۵) رشتهٔ چندبایتی را فراموش نکن / Account for multibyte strings

۸) query را با expression index هم‌راستا کن / Align query with the expression index

EXPLAIN و نتیجهٔ LOWER(email) را ذخیره کن.

WHERE LOWER(email)='lee@example.test';

id=4 برمی‌گردد. اگر index انتخاب نشد، expression و collation و هزینهٔ جدول را بررسی کن؛ استفاده را از روی نام index حدس نزن.

It returns id 4. If the index is not chosen, inspect expression, collation, and table cost; do not infer usage from the index name.

۹) expression نامجاز را اجرا نکن؛ query مجاز طراحی کن / Design an allowed expression

۱۷) یکتایی prefix را ادعا نکن / Do not claim prefix uniqueness

دو URL هم‌دامنه را query کن و ثابت کن prefix یکسان، مقدار کامل را یکی نمی‌کند.

چند id برمی‌گردد، هرچند prefix کوتاه index مشترک است. برای equality کامل، مقدار کامل را مقایسه کن.

Multiple IDs match despite sharing a short indexed prefix. Compare the complete value for exact equality.

آزمایش پایانی: یک index مشکوک، بدون حذف عجولانهClosing lab: investigate a suspicious index without dropping it

فرض کن تیم می‌گوید query تاریخ دیگر اجرا نمی‌شود و index شاید اضافی باشد. قرار نیست بی‌مدرک آن را حذف کنیم. baseline بگیر، invisible کن، plan را دوباره ثبت کن، visibility را برگردان و بعد نتیجه را با محدودیت‌های آزمایش گزارش بده.

Suppose the team says the date query is gone and the index may be redundant. Do not drop it without evidence. Capture a baseline, make it invisible, record the plan again, restore visibility, and report the test’s limits.

prefix index برای ابتدای رشته است؛ functional index برای expression؛ invisible index برای آزمودن انتخاب optimizer. اگر مسئله جست‌وجوی واژه‌ها در متن باشد، این‌ها جای FULLTEXT را نمی‌گیرند. فصل بعد فرق جست‌وجوی pattern و جست‌وجوی متن را با queryهای واقعی روشن می‌کند.

A prefix index targets leading characters, a functional index targets an expression, and an invisible index tests optimizer choice. None replaces FULLTEXT when the problem is searching words in text. The next chapter distinguishes pattern matching from full-text search.
