Read the plan; do not grade its labels

همکار عکس EXPLAIN رو فرستاده: type برابر ALL هست و در Extra هم Using filesort دیده می‌شه. یکی می‌گه «پس هر دو خراب‌اند.» قبل از پیشنهاد index، سؤال دقیق‌تر این هست: هر برچسب در این query چه کاری رو توصیف می‌کنه؟

A teammate sends an EXPLAIN screenshot: type is ALL and Extra says Using filesort. Someone concludes “both are broken.” Before proposing an index, ask a better question: what does each label describe for this query?

پیش‌نیازPrerequisite: فصل‌های ۱۹ تا ۲۱نسخهٔ مرجعReference: MySQL 9.7زمانTime: ۹۰ دقیقه · ۱۸ تمرین

ALL همیشه مشکل نیست؛ filesort هم الزاماً فاجعه نیستALL is not always a problem; filesort is not automatically a disaster

روی جدول کوچکی که همهٔ ردیف‌هایش رو می‌خوای، scan کامل شاید ارزان‌ترین انتخاب باشه. مرتب‌سازی چند ده ردیف هم ممکنه قابل قبول باشه. از آن طرف، scan کامل جدول دوم یک join می‌تونه برای هر ردیف ورودی تکرار شود و هزینه رو بالا ببرد. خود کلمه حکم نیست؛ query، اندازهٔ داده، جای گره در join و شواهد اجرا زمینه رو می‌سازند.

A full scan may be cheapest when you need every row from a tiny table. Sorting a few dozen rows may be acceptable. On the other hand, scanning a second join table may repeat for each incoming row and become expensive. The label is not a verdict; query shape, data size, join position, and execution evidence provide context.

توی این فصل plan جدولی رو می‌خونیم. ترتیب ردیف‌های EXPLAIN برای join می‌گه optimizer از کدام access شروع می‌کنه؛ الزاماً ترتیب نوشتن tableها در SQL نیست. Extra هم پیام تکمیلی است، نه رتبه‌بندی خطاها.

This chapter reads the tabular plan. For joins, EXPLAIN row order shows where the optimizer starts, not necessarily the order in which tables were written in SQL. Extra contains supplementary notes, not a severity ranking.

جدول شش ردیف دارد. optimizer ممکنه برای بعضی queryها scan کامل رو انتخاب کند؛ روی دادهٔ کوچک این به‌خودی‌خود باگ نیست. برای قضاوت دربارهٔ workload واقعی به اندازه و توزیع نماینده نیاز داریم.

The table has six rows. The optimizer may choose a full scan for some queries; on this tiny dataset that is not automatically a bug. Real workload decisions need representative size and distribution.

type می‌گه ردیف‌ها چطور پیدا می‌شوندtype describes how rows are found

در خروجی traditional، type ــ و در JSON معمولاً access_type ــ روش دسترسی به table رو توصیف می‌کنه. این چند مقدار رو مثل نشانه بخوان، نه ترتیب قطعی از بهترین تا بدترین:

In traditional output, type—and commonly access_type in JSON—describes how a table is accessed. Read these values as clues, not as a guaranteed best-to-worst ranking:

این فهرست همهٔ typeها نیست. حتی ALL می‌تونه برای query درست باشه: اگه همهٔ ستون‌ها و ردیف‌های جدول کوچک لازم‌اند، scan ممکنه از lookupهای زیاد ارزان‌تر شود.

This is not the full list. Even ALL can be right: if a query needs every column and row from a tiny table, a scan may be cheaper than many lookups.

سه سؤال، سه planThree questions, three plans

خروجی دقیق رو از server خودت بخوان؛ کلید اصلی کامل، index غیر یکتا و scan کامل موقعیت‌های متفاوت‌اند. با شش ردیف ممکنه optimizer چند مسیر رو نزدیک به هم ببیند.

Read exact output from your server; a full primary key, a nonunique index, and a full scan are different access patterns. With six rows, several paths may look similarly attractive.

ترتیب plan رو از SQL حدس نزنDo not infer plan order from SQL text

در INNER JOIN، جدول‌ها در FROM نوشته می‌شوند ولی optimizer می‌تونه ترتیب دسترسی رو عوض کند. ردیف‌های table در EXPLAIN رو کنار key، ref و type بخوان؛ فقط یک ستون برای فهم join کافی نیست.

An INNER JOIN lists tables in FROM, but the optimizer may choose a different access order. Read the table rows in EXPLAIN alongside key, ref, and type; one column is not enough to understand a join.

ترتیب access پیشنهادی optimizerOptimizer access order
EXPLAIN FORMAT=TRADITIONAL
SELECT t.ticket_id,tm.team_name
FROM ticket AS t
JOIN team AS tm ON tm.team_id=t.team_id
WHERE t.state='open';

EXPLAIN معمولاً برای هر table access یک ردیف دارد. اگه team قبل از ticket آمده، optimizer از آن مسیر شروع می‌کنه؛ این به معنای غلط‌بودن SQL نیست. در outer join محدودیت معنایی داریم و ترتیب رو نمی‌توان بی‌قید عوض کرد.

EXPLAIN commonly has one row per table access. If team appears before ticket, the optimizer starts with that path; this does not mean the SQL is wrong. Outer joins impose semantic constraints, so their order cannot be freely changed.

Extra یک پیام است؛ آن رو با context بخوانExtra is a note; read it in context

Using where می‌گه شرطی برای نگه‌داشتن ردیف‌ها اعمال می‌شه؛ این به‌تنهایی نمی‌گه query بد هست. Using index یعنی query می‌تونه از index به‌صورت covering استفاده کند؛ تضمین نمی‌کنه همه‌چیز سریع‌تر شده. Using filesort می‌گه ترتیب با مسیر index حل نشده و عملیات sort لازم است؛ اسمش ثابت نمی‌کنه حتماً دیسک نوشته شده یا latency نامقبول هست.

Using where indicates a filtering condition; it does not by itself say the query is bad. Using index means the query can use a covering index; it does not guarantee everything is faster. Using filesort says ordering was not satisfied by the index path and sorting is needed; the name does not prove disk I/O or unacceptable latency.

برای هر پیام، query، تعداد ردیف، هزینهٔ fetch و زمان واقعی رو در نظر بگیر. پیام‌های Extra ممکنه با نسخه و plan فرق کنند؛ نبودن یک عبارت هم اثبات نمی‌کنه هزینه‌ای وجود ندارد.

For each note, consider the query, row count, fetch cost, and measured runtime. Extra messages vary by version and plan; a missing label does not prove there is no cost.

مرتب‌سازی رو مقایسه کنCompare ordering paths
EXPLAIN FORMAT=TRADITIONAL

ORDER BY ticket_id;
EXPLAIN FORMAT=TRADITIONAL

شرط و ترتیب sort رو با index definition کنار هم بگذار. برای نتیجهٔ قابل اتکا، plan رو روی دادهٔ نماینده بخوان و اگه مسئله زمان است، فصل ۲۱ رو برای actual rows و زمان اجرا به کار ببر.

Compare predicates and sort order with index definitions. For a meaningful conclusion, use representative data and Chapter 21’s actual rows and timing when runtime is the question.

از query شروع کن، نه از برچسبStart with the query, not the label

  1. SQL دقیق و هدف خروجی رو ثبت کن.
  2. Record exact SQL and intended results.
  3. schema و indexها رو ببین.
  4. Inspect schema and indexes.
  5. ردیف‌های plan رو به ترتیب بخوان؛ type، key و Extra رو کنارهم تفسیر کن.
  6. Read plan rows in order and interpret type, key, and Extra together.
  7. اندازهٔ داده و COUNT واقعی رو بسنج.
  8. Measure data size and actual counts.
  9. اگه پرسش دربارهٔ زمان است، query محدود رو با EXPLAIN ANALYZE بسنج.
  10. If runtime is the question, measure a bounded query with EXPLAIN ANALYZE.

بعد از هر تغییر، همان query و همان evidence رو دوباره بگیر. عوض‌نشدن type به‌تنهایی شکست رو ثابت نمی‌کنه؛ نیاز workload و نتیجهٔ قابل‌اندازه‌گیری مهم‌اند.

After a change, collect the same query and evidence again. An unchanged type does not prove failure; workload needs and measurable outcomes matter.
