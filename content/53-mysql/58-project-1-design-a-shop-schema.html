پروژهٔ ۱ — سرویس تراکنشی با MySQL

Project 1 — A transactional service with MySQL

تیم یک API سادهٔ سفارش دارد؛ endpoint گاهی پرداخت رو ثبت می‌کنه اما موجودی رو کم نمی‌کنه. مأموریت تو ساختن یک هستهٔ تراکنشی قابل‌اثبات هست.

A team has a small order API. Sometimes payment is recorded but inventory is not reduced. Your mission is to build a provable transactional core.

پیش‌نیاز: فصل‌های ۱ تا 57 · Prerequisites: Chapters 1–57پروژهٔ عملی · Practical projectکد و مدرک تحویل · Code and proof required

ماموریتMission

با InnoDB، constraintها، transaction، queryهای پارامتری و حساب کم‌دسترسی یک سرویس سفارش کوچک بساز. پاسخ پروژه باید SQL و شواهد اجرایی باشه، نه توضیح کلی.

Build a small order service using InnoDB, constraints, transactions, parameterized queries, and a least-privilege account. Deliver runnable SQL and execution evidence, not generic prose.

دادهٔ تمرین رو خودت بساز و فایل راه‌اندازی رو طوری تحویل بده که نفر دیگری بتواند از صفر آن رو اجرا کند. secret واقعی رو در Git یا فایل SQL قرار نده.

Create your own test data and provide setup files another engineer can run from scratch. Never commit real secrets to Git or SQL files.

تحویل‌ها و معیار قبولیDeliverables and acceptance criteria

  • README دوزبانه یا دست‌کم روشن با نسخهٔ server، پیش‌نیاز و دستور اجرا / README with server release, prerequisites, and run commands
  • SQL setup، seed، queryها و اسکریپت verify / SQL setup, seed, queries, and verification script
  • خروجی واقعی commandها و توضیح محدودیت‌ها / Real command output and documented limitations
  • دادهٔ disposable، بدون credential واقعی / Disposable data; no real credentials

امتیاز فقط برای «اجرا شد» نیست؛ correctness، مسیر شکست، امنیت و قابلیت تکرار هم بررسی می‌شوند.

“It ran” is not enough: correctness, failure handling, security, and reproducibility are also reviewed.

گام‌های پروژهProject milestones

1) مدل داده1) Data model

برای customers، products، orders و order_items schema بساز؛ قیمت و تعداد باید constraint مناسب داشته باشند.

Create schemas for customers, products, orders, and order_items with appropriate constraints for price and quantity.

CREATE TABLE products (id BIGINT PRIMARY KEY, sku VARCHAR(40) NOT NULL UNIQUE, stock INT NOT NULL CHECK (stock >= 0), price DECIMAL(10,2) NOT NULL CHECK (price >= 0)) ENGINE=InnoDB;

مدرک قبولی: schema و SHOW CREATE TABLE رو تحویل بده.

Proof: Submit the schema and SHOW CREATE TABLE output.

راهنماییHint

راه‌حل رو با کلیدها و constraintها شروع کن؛ منطق موجودی رو فقط در برنامه رها نکن.

Start with keys and constraints; do not leave inventory integrity only to application code.

2) خرید اتمیک2) Atomic purchase

یک سفارش دو قلمی ایجاد کن؛ اگه موجودی قلم دوم کافی نیست، هیچ بخشی نباید commit شود.

Create an order with two items; if the second item lacks stock, nothing may commit.

START TRANSACTION; SELECT stock FROM products WHERE id IN (10,20) FOR UPDATE; -- validate, insert, decrement, COMMIT/ROLLBACK

مدرک قبولی: خروجی موفق و شکست اتمیک رو با دو نشست/دادهٔ تست prove کن.

Proof: Prove both successful and atomic-failure cases with test data.

راهنماییHint

ترتیب قفل‌گیری رو برای همهٔ مسیرها یکسان نگه دار.

Keep lock acquisition order consistent across all transaction paths.

3) queryهای کاربردی3) Operational queries

گزارش سفارش مشتری و موجودی باقی‌مانده رو با join و aggregate بنویس.

Write customer-order and remaining-stock reports with joins and aggregation.

SELECT o.id, SUM(oi.quantity * oi.unit_price) AS total FROM orders o JOIN order_items oi ON oi.order_id=o.id GROUP BY o.id;

مدرک قبولی: نتیجهٔ query و explain رو ضمیمه کن.

Proof: Attach query output and EXPLAIN evidence.

راهنماییHint

از دادهٔ ساختگی قابل‌تکرار استفاده کن.

Use deterministic, reproducible fixture data.

4) مرز برنامه4) Application boundary

یک endpoint کوچک بساز که از prepared statements استفاده کند و transaction رو مدیریت کند.

Build a small endpoint using prepared statements and managed transactions.

conn.execute('UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?', [qty, id, qty]);

مدرک قبولی: کد باید rollback رو در exception و پاسخ مناسب رو در شکست نشان دهد.

Proof: Show rollback on exceptions and a deliberate failure response.

راهنماییHint

مقادیر رو bind کن؛ نام ستون/ترتیب رو با allowlist انتخاب کن.

Bind values; choose column names and sort options from an allowlist.

5) بازبینی و تحویل5) Review and handoff

شکست هم‌زمان، duplicate request، permissionها و backup/restore آزمایشی رو مرور کن.

Review concurrency, duplicate requests, permissions, and a test backup/restore.

SHOW GRANTS FOR 'app_user'@'%';

مدرک قبولی: README شامل راه‌اندازی، SQL تست، نتیجهٔ concurrency و محدودیت‌ها باشه.

Proof: README must include setup, test SQL, concurrency result, and limitations.

راهنماییHint

فقط خروجی سبز رو تحویل نده؛ مسیر شکست رو هم نشان بده.

Do not hand off only the green path; demonstrate the failure path too.

نقطهٔ شروع — یه API داریم که transactionش قابل‌اعتماد نیستStarting point — an API with an untrusted transaction boundary

قبل از schema نوشتن، invariantها رو روی کاغذ بیار: موجودی منفی نشه، payment دوبار ثبت نشه و order نصفه ساخته نشه. این‌ها قراره با constraint، transaction و test قابل‌اثبات بشن.

Before designing the schema, write down the invariants: inventory must not go negative, payment must not be duplicated, and an order must not be half-created. These must be provable with constraints, transactions, and tests.

SELECT VERSION(), @@transaction_isolation;

این رو فقط اجرا نکن و رد نشو. قبلش حدس بزن چه چیزی باید ببینی، بعد از اجرا هم همون خط یا state مهم رو جدا کن. اگه نتیجه با حدست فرق داشت، همون اختلاف سؤال بعدی ماست.

Do not merely run this and move on. Predict the important result first, then preserve the line or state that matters. If reality differs from the prediction, use that mismatch as the next debugging question.

Failure drill — وسط ثبت سفارش خطا بسازFailure drill — fail halfway through order creation

عمداً بعد از کم‌کردن موجودی failure بساز. بعد check کن transaction کل عملیات رو برگردونده یا نه. اگه بخشی از state موند، پروژه هنوز قبول نیست.

Deliberately fail after inventory changes, then prove that the transaction leaves no partial business state.

START TRANSACTION;
-- perform the order steps in your schema
-- deliberately trigger one failure
ROLLBACK;

این رو فقط اجرا نکن و رد نشو. قبلش حدس بزن چه چیزی باید ببینی، بعد از اجرا هم همون خط یا state مهم رو جدا کن. اگه نتیجه با حدست فرق داشت، همون اختلاف سؤال بعدی ماست.

Do not merely run this and move on. Predict the important result first, then preserve the line or state that matters. If reality differs from the prediction, use that mismatch as the next debugging question.

تحویل — نفر بعد باید از صفر تکرارش کنهHandoff — another engineer must reproduce it from zero

setup، seed، verify و cleanup رو جدا کن. یه نفر دیگه باید بدون تاریخچهٔ لپ‌تاپ تو بتونه محیط رو بسازه و proofها رو دوباره بگیره.

Separate setup, seed, verification, and cleanup so another engineer can reproduce the evidence without your local history.

SELECT COUNT(*) FROM orders;
SHOW CREATE TABLE orders;

این رو فقط اجرا نکن و رد نشو. قبلش حدس بزن چه چیزی باید ببینی، بعد از اجرا هم همون خط یا state مهم رو جدا کن. اگه نتیجه با حدست فرق داشت، همون اختلاف سؤال بعدی ماست.

بازبینی نهاییFinal review

قبل از تحویل، setup رو از محیط تمیز اجرا کن، تمام proofها رو دوباره بگیر، فایل‌های artifact رو از دادهٔ حساس پاک کن و روش rollback رو واضح بنویس. پروژه وقتی تمام هست که نفر دیگری بتواند نتیجه رو مستقل تکرار کند.

Before handoff, run setup from a clean environment, recapture every proof, scrub sensitive data from artifacts, and document rollback. The project is complete only when another person can reproduce the result independently.
