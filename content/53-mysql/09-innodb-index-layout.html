ساختار index در InnoDB

InnoDB Index Layout

query با secondary index، کلید را پیدا می‌کند؛ اما ردیف کامل کجاست؟ در InnoDB پاسخ این است: index دوم معمولاً کلید اصلی را هم دارد و با آن به clustered index می‌رسد. وقتی این مسیر را ببینیم، می‌فهمیم انتخاب Primary Key روی همهٔ indexهای جدول سایه می‌اندازد.

A secondary-index query finds a key—but where is the complete row? In InnoDB, a secondary index record also carries the primary key and uses it to reach the clustered index. Once we see that path, it becomes clear why the primary-key choice affects every other index.

پیدا کردن نام یک محصول، دو مسیر داردFinding a product name can take two paths

در جدول محصول، جست‌وجو با SKU انجام می‌شود اما صفحهٔ محصول چندین ستون دیگر می‌خواهد. optimizer از index مربوط به SKU شروع می‌کند. برای بازگرداندن ردیف کامل، آیا خود secondary index تمام ستون‌ها را دارد؟ نه؛ در InnoDB معمولاً کلید اصلی به رکورد secondary اضافه می‌شود تا lookup به clustered index انجام شود.

The product table is searched by SKU, while the product page needs several other columns. The optimizer starts with the SKU index. Does that secondary index contain every column? No; InnoDB normally adds the primary key to a secondary record so it can look up the row in the clustered index.

این یک مدل فیزیکی-منطقی برای فهم مسیر است، نه تضمین اینکه pageها روی دیسک کنار هم باشند. InnoDB از B-tree و pageها استفاده می‌کند؛ فصل‌های بعد سراغ B+Tree، page و buffer pool می‌روند. اینجا فقط دو لایهٔ اصلی را دنبال می‌کنیم.

This is a logical/physical model for understanding the lookup path, not a promise that pages sit next to one another on disk. InnoDB uses B-tree pages; later chapters examine B+ trees, pages, and the buffer pool. Here we focus on the two main index layers.

Clustered index محل خود ردیف استThe clustered index holds the row

اگر Primary Key تعریف کنی، InnoDB از آن برای clustered index استفاده می‌کند. leaf recordهای این index دادهٔ ردیف را دارند. اگر جدول Primary Key نداشته باشد، InnoDB اول یک UNIQUE index مناسب با همهٔ key columnهای NOT NULL را در نظر می‌گیرد؛ وگرنه یک شناسهٔ داخلی برای clustered index می‌سازد. به این fallback تکیه نکن: کلید اصلی روشن و عمدی، قرارداد schema را بهتر می‌کند.

When you define a primary key, InnoDB uses it for the clustered index. Its leaf records hold row data. Without a primary key, InnoDB first considers a suitable UNIQUE index whose key columns are all NOT NULL; otherwise it creates an internal clustered identifier. Do not rely on that fallback: an explicit primary key makes the schema contract deliberate.

کلید اصلی داخل secondary index هم هزینه داردThe primary key has a cost inside secondary indexes too

هر secondary index علاوه بر ستون‌های خودش، کلید اصلی را برای ارجاع به ردیف نگه می‌دارد. پس اگر Primary Key چندستونی یا رشته‌ای بلند باشد، بخش کلید اصلی در همهٔ secondary indexها هم بزرگ‌تر می‌شود. این به معنی «هر Primary Key رشته‌ای بد است» نیست؛ معنی‌اش این است که اندازه، تعداد indexها و الگوی workload را با هم بسنجی.

Each secondary index stores the primary key columns along with its own key so it can reference the row. A wide composite or long string primary key therefore enlarges the primary-key portion repeated in every secondary index. This does not mean every string key is bad; measure key width, index count, and workload together.

این فصل index انتخاب نمی‌کند و performance benchmark نمی‌دهد. هدف این است که ساختار ذخیره‌سازی را بفهمی تا فصل‌های بعد وقتی index اضافه می‌کنی، هزینهٔ PK تکرارشده غافلگیرت نکند.

This chapter does not choose an index or provide a performance benchmark. Its goal is to explain the storage structure so later index choices account for the repeated primary-key cost.

چه چیزی را می‌توانیم واقعاً inspect کنیم؟What can we actually inspect?

در fixture زیر یک جدول با Primary Key و secondary index می‌سازیم. SHOW INDEX نام و ستون‌های تعریف‌شدهٔ index را گزارش می‌کند. خروجی الزاماً suffix ضمنی PK در leaf recordهای secondary را به‌شکل ستون صریح فهرست نمی‌کند؛ آن بخش را از مستندات InnoDB می‌آموزیم، نه با ادعای نادرست دربارهٔ SHOW INDEX.

We create a table with a primary key and a secondary index. SHOW INDEX reports the defined index columns. Its output does not necessarily list the implicit primary-key suffix in secondary leaf records as an explicit column; that behavior comes from InnoDB’s documented model, not a false claim about SHOW INDEX.

ساخت و بررسی indexهای fixtureCreate and inspect fixture indexes
CREATE DATABASE IF NOT EXISTS codenames_innodb_layout;
USE codenames_innodb_layout;
CREATE TABLE product_lookup (
  product_id BIGINT PRIMARY KEY,
  sku VARCHAR(24) NOT NULL,
  title VARCHAR(100) NOT NULL,
  category_id INT NOT NULL,
  UNIQUE KEY uq_product_sku (sku),
  KEY ix_product_category (category_id)
) ENGINE=InnoDB;

INSERT INTO product_lookup(product_id,sku,title,category_id) VALUES
(101,'SKU-001','Coffee mug',5),
(102,'SKU-002','Tea cup',5),
(201,'SKU-003','Desk lamp',9);

SHOW INDEX FROM product_lookup;
SHOW CREATE TABLE product_lookup;

دادهٔ کوچک برای دیدن تعریف کافی است، نه برای سنجش performance. اگر query فقط sku و product_id می‌خواهد، ممکن است secondary index نتیجه را از خودش پوشش دهد؛ اگر title هم لازم شود، ممکن است lookup به clustered index انجام شود. نتیجهٔ واقعی را با EXPLAIN و query مشخص بررسی می‌کنیم، نه از ظاهر DDL حدس می‌زنیم.

A tiny dataset is enough to inspect definitions, not benchmark performance. A query needing only SKU and product_id may be covered by the secondary index; adding title may require a clustered lookup. Check the actual query with EXPLAIN rather than guessing from DDL.

دو projection متفاوتCompare two projections
EXPLAIN SELECT product_id,sku FROM product_lookup WHERE sku='SKU-001';
EXPLAIN SELECT product_id,sku,title FROM product_lookup WHERE sku='SKU-001';

Primary Key بخشی از طراحی کل table استThe primary key is a table-wide design choice

کلید خوب باید یکتا، NOT NULL و تا حد ممکن پایدار باشد. اگر کلید طبیعی طولانی است، مقایسهٔ یک surrogate numeric key در کنار UNIQUE constraint روی مقدار طبیعی می‌تواند گزینه باشد؛ اما انتخاب به semantics و قرارداد بیرونی بستگی دارد. از یک آزمایش کوچک نمی‌توان گفت auto-increment همیشه بهتر است.

A useful primary key is unique, NOT NULL, and preferably stable. If a natural key is long, a surrogate numeric key alongside a UNIQUE constraint may be an option, but semantics and external contracts matter. A small lab does not prove auto-increment is always better.

دو طراحی را با metadata مقایسه کنCompare two key designs with metadata
CREATE TABLE narrow_key (
  id BIGINT PRIMARY KEY,
  external_code VARCHAR(80) NOT NULL,
  KEY ix_external_code(external_code)
) ENGINE=InnoDB;

CREATE TABLE wide_key (
  tenant_code CHAR(24) NOT NULL,
  external_code VARCHAR(80) NOT NULL,
  payload VARCHAR(100),
  PRIMARY KEY(tenant_code,external_code),
  KEY ix_payload(payload)
) ENGINE=InnoDB;

SHOW INDEX FROM narrow_key;
SHOW INDEX FROM wide_key;

تعریف‌ها را مقایسه می‌کنی، نه bytes واقعی روی دیسک. برای storage واقعی باید جدول با اندازهٔ نماینده، آمار InnoDB و workload داشته باشی. این اندازه‌گیری در فصل‌های صفحات و buffer pool ادامه پیدا می‌کند.

You are comparing definitions, not exact disk bytes. Actual storage measurement needs representative row counts, InnoDB statistics, and a workload. Later chapters examine pages and buffer-pool effects.

۱۸ تمرین SQL18 SQL exercises

روی schema آزمایشی codenames_innodb_layout کار کن. طراحی‌ها را مقایسه کن، اما از جدول کوچک نتیجهٔ سرعت production نگیر.

Use the disposable codenames_innodb_layout schema. Compare designs, but do not infer production speed from a tiny table.

1) Primary Key table را پیدا کن / Identify the primary index

indexهای product_lookup را بخوان و PRIMARY را مشخص کن.

Inspect product_lookup indexes and identify PRIMARY.

SQL / SQL
SHOW INDEX FROM product_lookup;

Key_name=PRIMARY مسیر clustered index را روی تعریف table روشن می‌کند.

Key_name=PRIMARY identifies the declared clustered-index key.

2) ترتیب ستون index را بخوان / Read index columns

نام و ترتیب ستون‌های هر index را query کن.

Query each index’s name and column order.

SQL / SQL
SELECT INDEX_NAME,SEQ_IN_INDEX,COLUMN_NAME,NON_UNIQUE FROM information_schema.STATISTICS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='product_lookup' ORDER BY INDEX_NAME,SEQ_IN_INDEX;

این تعریف صریح را نشان می‌دهد؛ suffix داخلی PK در secondary ممکن است اینجا به‌عنوان ستون تعریف‌شده ظاهر نشود.

This shows declared columns; the internal PK suffix may not appear as a declared column here.

3) engine و کلید را با هم بازبینی کن / Review engine and key

DDL را بخوان و engine و Primary Key را گزارش کن.

Read the DDL and report its engine and primary key.

SQL / SQL
SHOW CREATE TABLE product_lookup;

Engine=InnoDB و product_id PRIMARY KEY باید در تعریف دیده شوند.

The definition should show InnoDB and product_id as primary key.

4) query با PK را explain کن / Explain a primary-key lookup

EXPLAIN برای یک product_id مشخص اجرا کن.

Run EXPLAIN for a specific product_id.

SQL / SQL
EXPLAIN SELECT * FROM product_lookup WHERE product_id=101;

plan باید به مسیر PRIMARY اشاره کند؛ تخمین ردیف روی fixture کوچک معیار benchmark نیست.

The plan should use the primary path; row estimates on a tiny fixture are not a benchmark.

5) query با secondary را explain کن / Explain a secondary lookup

query با SKU را explain کن و key انتخاب‌شده را گزارش بده.

Explain a SKU lookup and report the chosen key.

SQL / SQL
EXPLAIN SELECT product_id,sku FROM product_lookup WHERE sku='SKU-001';

optimizer ممکن است unique secondary index را برگزیند؛ داده و آمار می‌توانند انتخاب را تغییر دهند.

The optimizer may choose the unique secondary index; data and statistics can change that choice.

6) projection را گسترش بده / Expand the projection

query title را هم بخواهد؛ plan جدید را کنار قبلی ثبت کن.

Add title to the query and compare the new plan.

SQL / SQL
EXPLAIN SELECT product_id,sku,title FROM product_lookup WHERE sku='SKU-001';

secondary record معمولاً همهٔ title را ندارد؛ برای row کامل clustered lookup لازم می‌شود، مگر index query را پوشش دهد.

The secondary record does not normally contain title; a clustered lookup may be needed unless an index covers the query.

7) کلید اصلی را از secondary جدا کن / Distinguish primary from secondary keys

با metadata نوع unique و نام indexها را برای sku و category_id گزارش کن.

Use metadata to report uniqueness and index names for sku and category_id.

SQL / SQL
SELECT INDEX_NAME,COLUMN_NAME,NON_UNIQUE FROM information_schema.STATISTICS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='product_lookup' ORDER BY INDEX_NAME,SEQ_IN_INDEX;

uq_product_sku unique است؛ ix_product_category secondary غیر unique است.

uq_product_sku is unique; ix_product_category is a nonunique secondary index.

8) table بدون PK را پیدا کن / Find a table without a declared PK

یک fixture بدون primary بساز و از metadata نبودن PRIMARY را بررسی کن.

Create a fixture without a primary key and inspect metadata for PRIMARY.

SQL / SQL
CREATE TABLE no_pk_lab(code VARCHAR(30),note VARCHAR(40)) ENGINE=InnoDB; SHOW INDEX FROM no_pk_lab;

نبودن PRIMARY در metadata به معنی نبود clustered index نیست؛ InnoDB ممکن است fallback داخلی داشته باشد.

No declared PRIMARY does not mean no clustered index; InnoDB can use an internal fallback.

9) UNIQUE مناسب را بیازما / Test a suitable UNIQUE fallback

روی table disposable یک unique index با NOT NULL بساز و تعریف را inspect کن.

Add a NOT NULL unique index to a disposable table and inspect its definition.

SQL / SQL
ALTER TABLE no_pk_lab MODIFY code VARCHAR(30) NOT NULL, ADD UNIQUE KEY uq_code(code); SHOW INDEX FROM no_pk_lab;

InnoDB در نبود PK می‌تواند چنین unique indexی را clustered کند؛ برای schema برنامه همچنان PK صریح روشن‌تر است.

Without a primary key, InnoDB can use this suitable unique key as clustered; an explicit PK is clearer for application schemas.

10) nullable unique را با فرض PK اشتباه نگیر / Do not treat nullable UNIQUE as a PK

nullable بودن ستون را با metadata بررسی و تفاوت شرط suitable UNIQUE را گزارش کن.

Inspect nullability and report why a suitable UNIQUE fallback requires non-null key columns.

SQL / SQL
SELECT COLUMN_NAME,IS_NULLABLE FROM information_schema.COLUMNS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='no_pk_lab';

برای clustered fallback، همهٔ ستون‌های کلید unique باید NOT NULL باشند.

For the clustered fallback, all columns in the unique key must be NOT NULL.

11) عرض دو کلید را از DDL مقایسه کن / Compare key width from DDL

narrow_key و wide_key را inspect کن و اجزای PK هرکدام را فهرست کن.

Inspect narrow_key and wide_key and list each primary-key component.

SQL / SQL
SHOW CREATE TABLE narrow_key; SHOW CREATE TABLE wide_key;

این عرض تعریف را نشان می‌دهد، نه اندازهٔ دقیق صفحات یا اثر performance.

This shows declared width, not exact page size or performance impact.

12) secondaries را بشمار / Count secondary indexes

تعداد indexهای non-primary دو table را query کن.

Count nonprimary indexes on the two tables.

SQL / SQL
SELECT TABLE_NAME,COUNT(DISTINCT INDEX_NAME) AS secondary_count FROM information_schema.STATISTICS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME IN ('narrow_key','wide_key') AND INDEX_NAME<>'PRIMARY' GROUP BY TABLE_NAME;

اگر PK بزرگ باشد، اثر تکرارشونده می‌تواند روی همهٔ این secondaryها بیاید.

A wide PK can have a repeated effect across these secondary indexes.

13) یک query پوشش‌پذیر را بررسی کن / Inspect a potentially covered query

EXPLAIN queryی را اجرا کن که فقط sku و product_id می‌خواهد.

Explain a query that needs only sku and product_id.

SQL / SQL
EXPLAIN SELECT product_id,sku FROM product_lookup WHERE sku='SKU-001';

ممکن است index نتیجه را پوشش دهد؛ از Extra و type به‌عنوان plan evidence استفاده کن، نه تضمین همهٔ داده‌ها.

The index may cover the query; use plan fields as evidence, not a guarantee for all data.

14) کلید مرکب را از metadata بخوان / Inspect a composite primary key

ستون‌ها و ترتیب PK در wide_key را query کن.

Query columns and order of wide_key’s primary key.

SQL / SQL
SELECT SEQ_IN_INDEX,COLUMN_NAME FROM information_schema.STATISTICS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='wide_key' AND INDEX_NAME='PRIMARY' ORDER BY SEQ_IN_INDEX;

هر دو جزء به کلید ردیف تعلق دارند و می‌توانند در secondaryها تکرار شوند.

Both parts identify the row and can be repeated in secondary entries.

15) انتخاب key را با workload توجیه کن / Justify a key for a workload

یک جدول آزمایشی با surrogate PK و UNIQUE natural key بساز و هر دو را inspect کن.

Create a lab table with a surrogate PK and unique natural key; inspect both.

SQL / SQL
CREATE TABLE key_choice(id BIGINT PRIMARY KEY,external_code VARCHAR(80) NOT NULL UNIQUE) ENGINE=InnoDB; SHOW INDEX FROM key_choice;

این یک گزینه است، نه پاسخ همیشگی؛ کلید باید با معنا و مسیرهای lookup برنامه جور باشد.

This is one option, not a universal answer; choose keys to fit identity and lookup patterns.

16) تغییر Primary Key را پرهزینه بدان / Treat a primary-key change as structural

DDL و indexهای wide_key را ثبت کن و یک دستور تغییر PK پیشنهادی را فقط در گزارش بیاور؛ اجرا نکن.

Record wide_key DDL and indexes, then document—but do not run—a proposed PK change.

SQL / SQL
SHOW CREATE TABLE wide_key; SHOW INDEX FROM wide_key;

تغییر clustered key ممکن است table را بازسازی کند و روی secondaries اثر بگذارد؛ ابتدا backup، حجم و عملیات DDL را ارزیابی کن.

Changing the clustered key can rebuild the table and affect secondary indexes; assess backup, size, and DDL behavior first.

17) ادعای disk adjacency را رد کن / Reject a physical-adjacency claim

queryی بنویس که metadata index را بخواند و در گزارش فرق «ترتیب B-tree بر اساس key» و «کنار هم بودن فایل روی دیسک» را توضیح بده.

Query index metadata and explain the difference between B-tree key order and physical adjacency on disk.

SQL و تفسیر / SQL and interpretation
SELECT TABLE_NAME,INDEX_NAME,SEQ_IN_INDEX,COLUMN_NAME FROM information_schema.STATISTICS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='product_lookup';

metadata تعریف و ترتیب key را نشان می‌دهد؛ فاصلهٔ فیزیکی pageها را ثابت نمی‌کند.

Metadata shows declared keys and order; it does not prove physical page adjacency.

18) مسیر lookup را با SQL بازسازی کن / Reconstruct the lookup path

query با sku را اجرا کن، EXPLAIN و SHOW INDEX را ثبت کن و بگو کدام بخش‌ها را metadata نشان می‌دهد و کدام اصل از مدل InnoDB می‌آید.

Run a SKU lookup, record EXPLAIN and SHOW INDEX, and separate what metadata shows from what follows from InnoDB’s model.

SQL / SQL
EXPLAIN SELECT product_id,sku,title FROM product_lookup WHERE sku='SKU-001'; SHOW INDEX FROM product_lookup;

plan index انتخاب‌شده را می‌دهد؛ SHOW INDEX تعریف صریح را. حضور PK در secondary leaf طبق مستندات engine است و لازم نیست وانمود کنیم SHOW INDEX آن را مستقیم فهرست کرده.

The plan reports the chosen index; SHOW INDEX reports declared keys. The PK in secondary leaf records is an engine behavior, not something SHOW INDEX must list explicitly.

حالا مسیر جست‌وجو را می‌بینیم؛ نوبت page استWe can now follow the lookup; next comes the page

مسیر از secondary key به Primary Key و سپس به clustered row می‌رسد. فهمیدیم چرا PK بلند در secondaryها تکرار می‌شود، ولی هنوز دربارهٔ اندازه و رفت‌وآمد pageها حرف نزدیم. فصل بعد سراغ pageهای InnoDB و buffer pool می‌رویم تا بفهمیم دادهٔ index چطور در حافظه و دیسک رفت‌وآمد می‌کند.

The path goes from a secondary key to the primary key and then to the clustered row. We saw why a wide PK is repeated in secondary indexes, but not yet how pages move through memory and disk. Next we examine InnoDB pages and the buffer pool.
