نصب و اتصال به سرور MySQL

Installing and Connecting to the MySQL Server

یک برنامه می‌گه به MySQL وصل نمی‌شه. هنوز نمی‌دونیم رمز اشتباه است، Server بالا نیامده، پورت دیگری رو نشانه گرفته‌ایم یا اصلاً Docker به daemon خودش دسترسی ندارد. این بار به‌جای دست‌کاری تصادفی تنظیمات، مسیر اتصال رو از اول تا آخر مدرک‌دار می‌کنیم.

An application says it cannot connect to MySQL. We do not yet know whether the password is wrong, the server is not ready, the client targets the wrong port, or Docker cannot reach its daemon. This time we will trace the connection path end to end instead of changing settings at random.

پیش‌نیازPrerequisite: فصل ۱، Client و Server محیط آزمایشLab image: mysql:9.7.2 زمانTime: ۸۰ دقیقه · 18 تمرین

«رمز رو عوض کن» هنوز تشخیص نیست

“Change the password” is not a diagnosis yet

خطای اتصال معمولاً آدم رو وسوسه می‌کنه همان اول رمز رو عوض کند. اما اگه Server اصلاً گوش ندهد، رمز هیچ نقشی در آن شکست ندارد. اگه فرمان docker به Engine وصل نشود، حتی درخواست ساخت container هم به MySQL نرسیده هست. پس اول می‌پرسیم: شکست دقیقاً بین کدام دو جزء رخ داده؟

A connection error often tempts us to change the password first. But if the server is not listening, the password is not involved in that failure. If the Docker CLI cannot reach the Engine, a container creation request has not reached MySQL at all. So first ask: exactly which boundary failed?

در فصل ۱ یاد گرفتیم Client و Server یکی نیستند. حالا آن مدل رو به مسیر واقعی وصل می‌کنیم: Docker CLI باید به daemon برسد؛ container باید ساخته و آماده شود؛ پورت میزبان باید به پورت داخلی Server راه داشته باشه؛ بعد Client احراز هویت می‌کنه و database رو انتخاب می‌کنه. هر مرحله شاهد خودش رو می‌خواهد.

Chapter 1 separated the client from the server. Now we attach that model to a real path: the Docker CLI must reach its daemon; the container must start and become ready; the host port must forward to the server’s container port; then the client authenticates and selects a database. Each boundary needs its own evidence.

قاعدهٔ عیب‌یابی:اولین مرحله‌ای رو پیدا کن که شاهد موفقیت ندارد؛ فقط همان مرز رو بررسی کن. «همه‌چیز رو restart کردم و درست شد» توضیح نمی‌ده چه چیزی خراب بوده. Troubleshooting rule:Find the first boundary without evidence of success and investigate that boundary only. “I restarted everything and it worked” does not explain what was broken.

برای یادگیری، محیط تکرارپذیر می‌خوایم

For learning, we want a reproducible environment

MySQL رو می‌شه با نصب‌کنندهٔ رسمی یا بسته‌های توزیع Linux نصب کرد. مسیر دقیق به سیستم‌عامل و نسخه بستگی دارد؛ در Windows نسخه‌های جدید از MySQL Configurator همراه بستهٔ MSI/ZIP استفاده می‌کنن و نباید راهنمای قدیمی MySQL Installer مربوط به 8.0 رو بی‌بررسی به نسخه‌های جدید تعمیم داد. در Linux هم مخلوط‌کردن مخزن سیستم‌عامل با مخزن Oracle می‌تونه نسخه و چرخهٔ به‌روزرسانی رو مبهم کند.

MySQL can be installed with Oracle’s installer or Linux distribution packages. The exact path depends on the operating system and release. Current Windows packages use MySQL Configurator with the MSI/ZIP distribution; do not blindly apply the older MySQL Installer instructions for 8.0 to newer releases. On Linux, mixing distribution and Oracle repositories can make versions and update ownership unclear.

برای این دوره، image رسمی با tag مشخص انتخاب می‌کنیم تا همه دقیقاً یک نسخه رو آزمایش کنند. Docker جایگزین همیشگی نصب native نیست؛ فقط برای یک آزمایش قابل‌حذف و قابل‌بازتولید انتخاب مناسبی هست. از فصل قبل می‌دونیم tag نسخه رو تعیین می‌کنه، اما اجرای موفق image هنوز ثابت نمی‌کنه Server آمادهٔ پذیرش connection شده هست.

For this course, we choose an official image with an explicit tag so everyone tests the same version. Docker is not a universal replacement for native installation; it is simply a good fit for a disposable, reproducible lab. From the previous chapter, we know the tag identifies a version, but a successful image launch still does not prove that the server is ready to accept connections.

پیش از MySQL، خود Docker رو بررسی کن

Before MySQL, check Docker itself

CLI می‌تونه نصب باشه ولی Engine اجرا نشود. این دو دستور از دو بخش متفاوت مدرک می‌گیرن: docker version باید هم بخش Client و هم Server رو نشان دهد؛ docker context ls می‌گه CLI درخواست‌ها رو به کدام context می‌فرستد. در Docker Desktop، WSL یا چند context ممکنه مقصد فعال آن چیزی نباشه که انتظار داری.

The CLI may be installed while the Engine is stopped. These commands collect evidence from different parts: docker version should show both Client and Server sections; docker context ls shows which context receives CLI requests. With Docker Desktop, WSL, or multiple contexts, the active target may not be the one you expect.

آیا CLI به Engine می‌رسه؟Can the CLI reach the Engine?
docker version
docker context ls

اگه فقط Client چاپ شد یا خطای اتصال به daemon آمد، هنوز به MySQL نرسیده‌ایم. Engine رو در محیط مربوط روشن کن و دوباره همان بررسی رو انجام بده؛ تغییر رمز MySQL یا بازکردن پورت در این مرحله بی‌ربط هست. در WSL هم بررسی کن context و integration با Docker Desktop همان محیطی باشه که CLI رو از آن اجرا می‌کنی.

If only the Client appears or the command reports a daemon connection error, we have not reached MySQL yet. Start the Engine in the relevant environment and repeat the same check; changing a MySQL password or opening a port is unrelated at this stage. In WSL, also verify that the context and Docker Desktop integration match the environment where you run the CLI.

یک Server آزمایشی با مرز روشن

A disposable server with a clear boundary

حالا یک container یک‌بارمصرف می‌سازیم. پورت 3307 روی خود میزبان رو فقط روی loopback منتشر می‌کنیم و آن رو به 3306 داخل container وصل می‌کنیم. برای Client آزمایش، کاربر محدود می‌سازیم؛ root رو از میزبان در دسترس نمی‌ذاریم. رمزهای زیر فقط برای همین محیط دورریختنی‌اند، برای دادهٔ واقعی استفاده‌شان نکن و در کار واقعی هم رمز رو در تاریخچهٔ shell نگذار.

Now create a disposable container. Publish host port 3307 on loopback only and forward it to port 3306 inside the container. Create a limited account for the client test; do not expose root to the host. The passwords below are only for this throwaway lab—never use them for real data, and avoid placing real passwords in shell history.

ساخت محیط تمرینیCreate the lab environment
docker run -d --name mysql-connect-lab \
  -p 127.0.0.1:3307:3306 \
  -e MYSQL_ROOT_PASSWORD=lab-root-only \
  -e MYSQL_DATABASE=connect_lab \
  -e MYSQL_USER=lab_user \
  -e MYSQL_PASSWORD=lab-user-only \
  mysql:9.7.2

این فرمان درخواستی به Engine می‌ده؛ پاسخ موفقِ docker run معمولاً شناسهٔ container است، نه گواه آماده‌بودن MySQL. image رسمی ممکنه برای راه‌اندازی اولیه چند لحظه زمان بخواهد. پس حالا وضعیت، log و نگاشت پورت رو جداگانه می‌خونیم.

This command asks the Engine to create a container; a successful docker run response is usually a container ID, not proof that MySQL is ready. The official image may need a little time for first-time initialization. So next we inspect state, logs, and port mapping separately.

سه شاهد برای سه سؤالThree signals, three questions
docker ps --filter name=mysql-connect-lab
docker logs --tail 30 mysql-connect-lab
docker port mysql-connect-lab

در docker ps دنبال وضعیت container بگرد؛ در log پیام آماده‌شدن Server رو بخوان؛ و در docker port نگاشت 3306 رو پیدا کن. هیچ‌کدام به‌تنهایی موفقیت login رو تضمین نمی‌کنه. اگه container هنوز در حال راه‌اندازی است، چند ثانیه صبر کن و همان شاهد رو دوباره بگیر؛ اگه متوقف شده، log علت نزدیک‌تر رو نشان می‌ده.

In docker ps, inspect container state; in the logs, look for the server-ready message; in docker port, find the mapping for 3306. None alone guarantees a successful login. If initialization is still underway, wait briefly and collect the same evidence again; if the container stopped, its logs are the nearer clue.

از میزبان با TCP وصل شو

Connect from the host over TCP

اگه MySQL Client روی میزبان نصب است، مقصد رو صریح می‌کنیم. گزینهٔ --protocol=TCP جلوی این ابهام رو می‌گیره که Client برای localhost سراغ socket محلی برود. با 127.0.0.1 هم روشن می‌کنیم منظورمان loopback میزبان هست. گزینهٔ -p رمز رو تعاملی می‌پرسد تا خود رمز بخشی از command line نشود.

If the MySQL client is installed on the host, make the destination explicit. --protocol=TCP avoids ambiguity about a client choosing a local socket for localhost. Using 127.0.0.1 makes the host loopback target explicit as well. The -p option prompts for the password so the password itself is not part of the command line.

اتصال به پورت منتشرشدهConnect to the published host port
mysql --protocol=TCP --host=127.0.0.1 --port=3307 \
  --user=lab_user -p connect_lab

پس از ورود، این query رو اجرا کن تا Server مقصد و database جاری رو ببینی:

After login, run this query to inspect the server reached and the selected database:

مدرک از همان connectionEvidence from this connection
SELECT VERSION(), CURRENT_USER(), DATABASE(), @@hostname, @@port;

نسخه باید با محیط این فصل سازگار باشه؛ DATABASE() باید connect_lab و پورت Server داخل container معمولاً 3306 باشه. عدد 3307 فقط پورت میزبان هست. اگه host CLI نصب نیست، می‌تونی SQL رو با docker exec -it mysql-connect-lab mysql --user=lab_user -p connect_lab اجرا کنی؛ اما این مسیر معمولاً socket داخل container است، پس موفقیتش ثابت نمی‌کنه پورت میزبان درست منتشر شده هست.

The version should match this chapter’s environment; DATABASE() should be connect_lab, and the server port inside the container is normally 3306. Port 3307 belongs only to the host side. If the host client is unavailable, run SQL with docker exec -it mysql-connect-lab mysql --user=lab_user -p connect_lab; that path normally uses a socket inside the container, so its success does not prove that host port publishing works.

root رو برای راحتی از راه دور باز نکن.image رسمی MySQL به‌طور پیش‌فرض root رو برای اتصال محلی container تنظیم می‌کنه. این آزمایش به کاربر محدود lab_user نیاز دارد، نه تنظیمی مثل MYSQL_ROOT_HOST برای دسترسی root از میزبان. Do not expose root for convenience.The official MySQL image configures root for local container connections by default. This test needs the limited lab_user, not a setting such as MYSQL_ROOT_HOST to allow host access as root.

اگه نصب native لازم داری

When a native installation is needed

برای کار روزمره روی یک میزبان، نصب native می‌تونه منطقی باشه؛ فقط نسخه و روش نگهداری رو از ابتدا مشخص کن. از مستند رسمی همان نسخه برای Windows یا توزیع Linux استفاده کن، سرویس رو بعد از نصب با ابزار همان سیستم‌عامل بررسی کن و Client رو جدا از Server بشناس. نصب بسته، ساخت حساب، انتخاب پورت و firewall رفتارهای سیستم‌عامل‌اند؛ فرمان‌هایشان رو بین Windows و Linux جابه‌جا نکن.

A native installation can make sense for daily work on one host; just choose the version and maintenance path deliberately. Follow the official guide for that release and operating system, check the service with that OS’s tools, and keep the client distinct from the server. Package installation, account creation, port selection, and firewall behaviour are operating-system-specific; do not copy commands between Windows and Linux.

برای تمرین‌های این دوره، container نسخه‌ثابت مسیر پیش‌فرض ماست چون پاک‌سازی و بازسازی‌اش روشن‌تر هست. این انتخاب به معنی مناسب‌بودن container برای هر نصب production نیست و جای backup یا طراحی درست نگهداری داده رو نمی‌گیره.

For this course’s labs, a pinned container is the default because cleanup and recreation are explicit. That does not mean a container is automatically the right choice for every production installation, nor does it replace backup or a sound data-retention design.

چند خطای رایج، بدون حدس‌زدن

Common failures without guesswork

CLI فقط Client رو نشان می‌دهOnly the CLI section appears

مسئله فعلاً Docker Engine یا context هست. قبل از بررسی MySQL، خروجی docker version رو کامل کن.

The issue is currently Docker Engine or context. Complete the docker version check before investigating MySQL.

اتصال فوراً رد می‌شهConnection is refused immediately

آدرس و پورت Client، نگاشت docker port و آماده‌بودن Server رو بررسی کن. هنوز خطای password نیست.

Check the client address and port, docker port mapping, and server readiness. This is not yet a password error.

ERROR 1045 میادYou get ERROR 1045

به همان user و رمز تعاملی برگرد؛ دنبال بازکردن root یا دادن مجوزهای گسترده نرو. مقصد صحیح رو هم با command قبلی ثابت کن.

Recheck the username and prompted password; do not expose root or grant broad privileges. Also confirm the target with the previous checks.

از داخل container وصل می‌شوی، از میزبان نهIt connects inside, but not from the host

آزمایش socket داخلی با پورت میزبان یکی نیست. نگاشت، loopback میزبان، تداخل پورت و firewall رو بررسی کن.

An internal socket test is not the same as host port publishing. Check the mapping, host loopback, port conflicts, and firewall.

آزمایش فصل: اتصال رو از ابتدا ثابت کن

Chapter lab: prove the connection end to end

هدف این نیست که فقط یک prompt ببینی؛ باید بتوانی نشان بدهی CLI به Engine وصل شده، Server آماده است، پورت درست نگاشت شده و SQL از همان مسیر موردنظر پاسخ می‌ده. یک برگهٔ کوتاه بساز و برای هر مرحله فرمان و شاهدش رو ثبت کن.

The goal is not merely to see a prompt. You should be able to show that the CLI reached the Engine, the server became ready, the correct port was mapped, and SQL answered through the intended path. Make a short record of each stage, its command, and its evidence.

  1. با docker version و docker context ls دسترسی CLI به Engine و مقصد context رو ثبت کن.Record CLI-to-Engine access and the selected context with docker version and docker context ls.
  2. container رو با فرمان بخش قبل اجرا کن؛ ID رو با «آماده هست» اشتباه نگیر.Start the container with the earlier command; do not confuse its ID with readiness.
  3. وضعیت، logهای انتهایی و نگاشت پورت رو جمع کن. اگه initialization ادامه دارد، همان شواهد رو پس از مکث کوتاه دوباره بخوان.Collect state, recent logs, and port mapping. If initialization continues, repeat those checks after a short wait.
  4. با Client میزبان از TCP به 127.0.0.1:3307 وصل شو و query تشخیصی رو اجرا کن. اگه Client نداری، مسیر docker exec رو جداگانه ثبت کن و محدودیتش رو بنویس.Connect from the host over TCP to 127.0.0.1:3307 and run the diagnostic query. If you lack a host client, record the docker exec path separately and note its limitation.
  5. در صورت نیاز، فقط روی همین آزمایش رمز اشتباه یا پورت اشتباه رو امتحان کن. خروجی رو به یکی از مرزهای جدول عیب‌یابی نسبت بده، بعد تنظیم رو برگردان و همان query رو دوباره اجرا کن.If useful, try a wrong password or port only against this lab. Map the result to a boundary in the troubleshooting table, restore the setting, and run the same query again.
راهنمای بیشترMore help

ترتیب خوب این هست: Docker daemon → container state و startup log → host port mapping → TCP handshake → account authentication → database انتخاب‌شده. با هر خطا یک مرحله عقب برو، نه اینکه همهٔ لایه‌ها رو هم‌زمان عوض کنی.

A useful order is: Docker daemon → container state and startup logs → host port mapping → TCP handshake → account authentication → selected database. For each error, step back one boundary rather than changing every layer at once.

تمرین‌ها: مدرک بعدی رو انتخاب کن

Exercises: choose the next piece of evidence

همهٔ تمرین‌ها رو روی آزمایش یک‌بارمصرف انجام بده. هر پاسخ باید یک دستور قابل اجرا و توضیحی کوتاه دربارهٔ چیزی که هنوز ثابت نشده داشته باشه.

Use the disposable lab for all exercises. Every answer must include a runnable command and a short note about what it still does not prove.

اینجا جواب تشریحیِ خالی نداریم. هر تمرین باید به SQL/command قابل‌اجرا، خروجی، خطای قابل‌بازتولید یا state قابل‌بررسی ختم بشه. اول حدس بزن، بعد اجرا کن، بعد از روی مدرک نتیجه بگیر.

These are not prose-only questions. Every exercise should end in runnable SQL/commands, observable output, a reproducible error, or inspectable state. Predict first, run it, then conclude from evidence.

۱) Docker یا MySQL؟1) Docker or MySQL?

فرمان docker run خطای اتصال به daemon می‌ده. دو دستور بنویس که قبل از هر بررسی MySQL اجرا می‌کنی و بگو دنبال چه نشانه‌ای هستی.

The docker run command reports a daemon connection error. Write two checks to run before any MySQL investigation and state what evidence you seek.

تحویلیه SQL/command قابل‌اجرا + خروجی یا state قابل‌بررسی + یه توضیح کوتاه که بگه دقیقاً چی ثابت شد.DeliverableA runnable SQL/command artifact, observable output/state, and a short explanation of exactly what it proves.
راه‌حل و دلیلSolution and reasoning
docker version
docker context ls

بخش Server در version و context فعال مرز CLI→Engine رو بررسی می‌کنن. هنوز چیزی دربارهٔ MySQL نگفته‌ایم؛ تا این مرز درست نشود، database diagnostics بی‌معناست.

The Server section and active context check the CLI-to-Engine boundary. This says nothing about MySQL yet; database diagnostics are premature until this boundary works.

فقط سبزشدن command رو جواب حساب نکن. از خروجی یه نشونهٔ مشخص بیرون بکش و بنویس این نشونه دربارهٔ مسئلهٔ تمرین چی رو ثابت می‌کنه و چی رو هنوز ثابت نمی‌کنه.

Do not treat command success as the answer. Extract one concrete piece of evidence and state what it proves about the exercise—and what it still does not prove.

A connection is a path, not a password

حالا اگه برنامه نتواند وصل شود، از daemon شروع می‌کنیم، بعد state و log و پورت رو می‌خونیم، و فقط وقتی Server پاسخ‌گو شد سراغ account و database می‌ریم. فرق 3307 میزبان با 3306 داخل container رو هم با مدرک نگه می‌داریم. فصل بعد که Server در دسترس شد، می‌تونیم به‌جای زیرساخت اتصال، روی خود database و schema کار کنیم.

When an application cannot connect, we start with the daemon, then inspect state, logs, and ports, and only investigate accounts and databases once the server responds. We keep host port 3307 distinct from container port 3306 using evidence. With the server available, the next chapter can focus on databases and schemas rather than connection infrastructure.
