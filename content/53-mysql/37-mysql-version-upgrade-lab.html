نسخهٔ جدید آماده است؛ از کجا بفهمیم ارتقا امن است؟

A new release is available. How do we know an upgrade is safe?

تیم می‌خواهد MySQL رو ارتقا دهد. سرویس فعلی کار می‌کنه، اما نمی‌دونیم مسیر ارتقا پشتیبانی می‌شه، برنامه با رفتار تازه سازگار هست یا بازیابی از backup واقعاً جواب می‌ده. به دادهٔ اصلی دست نمی‌زنیم؛ اول روی کپی تمرین می‌کنیم و برای هر تصمیم مدرک جمع می‌کنیم.

The team wants to upgrade MySQL. We do not know whether the path is supported, the application tolerates changed behavior, or a backup can actually be restored. We will leave production alone, rehearse on a copy, and collect evidence.

یک ارتقای ساده که ساده نیستAn upgrade is not just a version change

«فقط image رو عوض می‌کنیم» وسوسه‌کننده هست. سرور تازه می‌تونه فرمت داده، تنظیم، احراز هویت یا تصمیم optimizer رو تغییر دهد. حتی اگه MySQL بالا بیاید، برنامه شاید نتیجهٔ دیگری بگیره یا کندتر شود. از این پرسش شروع می‌کنیم: دقیقاً از کدام نسخه به کدام نسخه، با چه روش و چه راه بازیابی؟

“We will just change the image” sounds tempting. A new server can change data formats, settings, authentication, or optimizer decisions. Even if MySQL starts, the application may behave differently or slow down. Start precisely: which source and target, which method, and what recovery path?

اگه یکی از ایستگاه‌ها مدرک ندارد، جواب «هنوز نه» هست.

If a gate has no evidence, the answer is “not yet.”

اول مسیر پشتیبانی‌شده رو پیدا کنFirst establish a supported path

شمارهٔ بزرگ‌تر به‌تنهایی مجوز ارتقا نیست. خانوادهٔ انتشار، مبدأ و مقصد، روش نصب و نسخهٔ ابزار مهم‌اند. مسیر رو از مستند همان نسخه ثبت کن؛ میان‌بُر رو حدس نزن.

A larger version number is not permission to upgrade. Release series, source and target, installation method, and tool version matter. Record the path from the matching manual; do not guess a shortcut.

SELECT VERSION() AS server_version,
       @@version_comment AS distribution,
       @@version_compile_os AS server_os;
SHOW VARIABLES LIKE 'sql_mode';

نسخهٔ mysql client لزوماً نسخهٔ server نیست. تنظیم session رو با global قاطی نکن و خروجی رو کنار نسخهٔ برنامه و connector نگه دار.

The mysql client version is not necessarily the server version. Keep session and global settings distinct, and record this with application and connector versions.

backup وقتی ارزش دارد که restore آن رو دیده باشیمA backup matters when its restore is proven

پیش از تغییر، backup کامل و قابل‌خواندن بساز. وجود فایل اثبات بازیابی نیست: در مقصد جداگانه restore کن، چند جدول و رکورد کلیدی رو query کن و زمان رو ثبت کن. هیچ‌وقت تنها کپی داده رو برای آزمایش به server تازه وصل نکن.

Before changing anything, create a complete, readable backup. A file is not proof of recovery: restore to a separate target, query representative objects and rows, and record the time. Never attach the only data copy to a new server for rehearsal.

عقب‌بردن image، rollback دیتابیس نیستReverting an image is not a database rollback

بعد از تغییر فرمت یا ساختار، اجرای image قدیمی الزاماً server رو برنمی‌گرداند. بعضی downgradeها پشتیبانی نمی‌شن؛ راه برگشت ممکنه restore و پذیرش نقطهٔ بازیابی باشه. این رو از قبل بنویس.

After data format or structure changes, running the old image does not necessarily reverse the server. Some downgrades are unsupported; recovery may require restoring a backup. Document this first.

Replace the table with your fixture; these queries matter only after a real isolated restore.

checker خودکار حکم نهایی نیستAn automated checker is not the final verdict

MySQL Shell ابزار Upgrade Checker دارد که بخشی از ناسازگاری‌های مقصد رو گزارش می‌کنه. روی کپی تمرینی اجرا کن، گزارش رو نگه دار و برای هر هشدار تصمیم بنویس. خروجی بدون هشدار تضمین نمی‌کنه برنامه یا کارایی‌اش درست هست.

MySQL Shell's Upgrade Checker reports a set of target-release incompatibilities. Run it against a rehearsal copy, save the report, and record a decision for every warning. A clean report does not prove application correctness or performance.

util.checkForServerUpgrade({

  outputFormat: "TEXT"

نسخهٔ هدف نمونه است؛ مقصد واقعی و MySQL Shell سازگار رو انتخاب کن. اطلاعات اتصال رو در گزارش عمومی نگذار. هشدار بی‌مالک حل‌شده نیست.

The target is illustrative; use the real destination and compatible Shell. Do not expose credentials. An unowned warning is not resolved.

برنامه رو با workload خودش امتحان کنTest the application with its own workload

در staging و روی کپی داده، با connector و مجوز واقعی برنامه مسیرهای مهم رو اجرا کن: اتصال، خواندن و نوشتن، transaction، گزارش پرتکرار و job زمان‌بندی‌شده. خطاهای برنامه رو با log سرور هم‌زمان کن. plan و زمان queryهای کلیدی رو با baseline مقایسه کن؛ یک اجرا نتیجهٔ قطعی نیست.

In staging, use copied data, the real connector, and application grants to exercise connections, reads, writes, transactions, common reports, and scheduled jobs. Correlate application failures with server logs. Compare key query plans and timings with a baseline; one run is not conclusive.

تصمیم go/no-go رو مستند کنDocument the go/no-go decision

نسخهٔ مبدأ و مقصد، مسیر پشتیبانی‌شده، گزارش checker، نتیجهٔ restore، آزمون برنامه، queryهای حساس، زمان توقف و مسئول برگشت رو ثبت کن. اگه downgrade پشتیبانی نمی‌شه، rollback یعنی restore backup طبق هدف بازیابی توافق‌شده، نه اجرای image قبلی روی دادهٔ جدید.

Record source and target, supported path, checker report, restore result, application tests, sensitive queries, expected outage, and rollback owner. If downgrade is unsupported, rollback means restoring a backup under agreed recovery objectives, not running the old image against new data.

decision: GO only when required proof is present

شماره‌ها نمونه‌اند. مسیر واقعی رو از مستند مقصد تأیید کن. در Docker هم pull کردن image جای دستورالعمل ارتقای MySQL رو نمی‌گیره؛ روی کپی volume تمرین کن و نسخهٔ دقیق یا digest رو ثبت کن.

Versions are illustrative; verify the real path in the target manual. In Docker, pulling an image does not replace MySQL's upgrade procedure. Rehearse on a copied volume and record the exact version or digest.

قبل از عوض‌کردن نسخه، یه عکس از وضعیت فعلی بگیرCapture the current state before changing the version

Upgrade خوب از target شروع نمی‌شه؛ از این شروع می‌شه که دقیقاً بدونی الان چی داری. نسخهٔ Server، sql_mode، charset/collation، pluginهای مهم و چند query حساس رو ثبت کن. اگه بعد از upgrade چیزی عوض شد، بدون baseline فقط می‌دونی «فرق کرده»؛ نمی‌دونی کجا و چرا.

A good upgrade starts by documenting the current system, not by pulling the target image. Capture server version, SQL mode, character set/collation, important plugins, and a small set of critical queries.

برای چند query مهم فقط زمان نگیر. plan، تعداد ردیف و نتیجهٔ منطقی رو هم نگه دار. ممکنه query هنوز جواب درست بده ولی optimizer مسیر دیگری انتخاب کنه و latency بالا بره.

For key queries, preserve more than elapsed time. Save the plan, row counts, and correctness checks so a post-upgrade regression can be compared against real evidence.

SELECT VERSION(), @@version_comment, @@sql_mode;
SHOW VARIABLES WHERE Variable_name IN ('character_set_server','collation_server','time_zone');

Upgrade رو روی کپی تمرین کن، نه روی امیدRehearse the upgrade on a copy, not on hope

A blank staging server proves little. Rehearse against a disposable copy with representative schema/data and the real application connector.

Rollback رو قبل از GO بنویسWrite rollback before the GO decision

وقتی upgrade شروع شد، تازه وقت فکرکردن به rollback نیست. مشخص کن برگشت یعنی restore از backup، برگشت traffic، یا ساخت دوبارهٔ instance قبلی. «image قبلی رو بالا میاریم» فقط وقتی معتبره که format داده و مسیر downgrade واقعاً پشتیبانی بشه.

Rollback must be designed before the cutover. State whether rollback means restoring a tested backup, redirecting traffic, or rebuilding the previous instance. Running an older image against upgraded data is not a generic rollback plan.
