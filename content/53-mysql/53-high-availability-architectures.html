معماری‌های دسترس‌پذیری بالا در MySQLMySQL high-availability architectures

Replication ناهمگام ممکنه آخرین commitها رو نرسانده باشه؛ failover خودکار می‌تونه دادهٔ ازدست‌رفته یا دو primary بسازد اگه fencing و topology روشن نباشه. Group Replication/InnoDB Cluster برای عضویت و انتخاب primary ابزار می‌دن، اما مسیر client و سیاست backup/restore همچنان لازم است؛ خود Group Replication clientهای متصل به عضو خراب رو جابه‌جا نمی‌کنه. MySQL Router یا لایهٔ برنامه باید routing رو انجام دهد. Availability رو با RPO (تحمل از دست‌رفتن داده) و RTO (زمان بازیابی) تعریف کن و failover رو در staging تمرین کن.

Asynchronous replication can miss recent commits. Automatic failover can lose data or create two primaries if fencing and topology are unclear. Group Replication/InnoDB Cluster provide membership and primary-election mechanisms, but client routing and backup/restore policy remain necessary; Group Replication itself does not move clients connected to a failed member. MySQL Router or the application layer must handle routing. Define availability using RPO (acceptable data loss) and RTO (recovery time), then rehearse failover in staging.
