اگه انتقال پول وسط راه قطع شود چه؟

What if a transfer stops halfway?

فرض کن باید از حساب A کم کنیم و به حساب B اضافه کنیم. اگه UPDATE اول موفق شود ولی برنامه قبل از UPDATE دوم قطع شود، یک طرف پول کم کرده و طرف دیگر چیزی نگرفته. مسئله این نیست که کدام query رو حفظ کنیم؛ باید مرز یک کار کامل رو تعریف کنیم. این‌جا transaction وارد می‌شه.

Suppose we debit account A and credit account B. If the first UPDATE succeeds but the application stops before the second, one account loses money and the other receives nothing. The problem is not memorizing an UPDATE; we need a boundary around the complete operation. That is where a transaction comes in.

دو تغییر، یک نتیجهٔ کسب‌وکارTwo changes, one business outcome

در یک transfer، کم‌کردن موجودی و اضافه‌کردن به حساب مقصد باید یک کار واحد باشه. اگه مرحلهٔ دوم شکست خورد، تغییر مرحلهٔ اول نباید باقی بماند. این یعنی transaction فقط چند query پشت سر هم نیست؛ مرزی هست که می‌گه کدام تغییرها با هم موفق یا ناموفق‌اند.

In a transfer, debiting the source and crediting the destination form one business operation. If the second step fails, the first must not remain. A transaction is not merely several queries in sequence; it defines which changes succeed or fail together.

در MySQL این درس رو با InnoDB می‌سازیم. اول engine رو بررسی می‌کنیم؛ صرف نوشتن START TRANSACTION تضمین نمی‌کنه هر جدول و هر اثر جانبی در همان transaction شرکت کند.

We use InnoDB for this lesson. First verify the engine: writing START TRANSACTION does not guarantee that every table or side effect participates in the transaction.

یک شکست رو عمداً قبل از COMMIT ببینObserve a failure before COMMIT

در یک connection بنویسیم: «از حساب اول کم کن»، بعد نتیجه رو پیش از پایان transaction بخوانیم. سپس به‌جای commit، rollback می‌کنیم. پرسش ما این هست: پس از rollback، آیا اثر UPDATE مانده؟

In one connection, debit the first account, inspect the uncommitted result, then roll back instead of committing. The question is whether the UPDATE remains visible afterward.

در همان session اجرا کنRun in the same session
START TRANSACTION;
UPDATE account SET balance=balance-20 WHERE account_id=1;
SELECT * FROM account ORDER BY account_id;
ROLLBACK;
SELECT * FROM account ORDER BY account_id;

در همان session، قبل از rollback عدد ۸۰ رو می‌بینی؛ بعد از آن باید دوباره ۱۰۰ باشه. ROLLBACK اثر تغییرهای تراکنشی این transaction رو لغو کرد. این آزمایش فقط وقتی معنا دارد که جدول InnoDB و هر دو statement در همان connection باشند.

In the same session, the balance is 80 before rollback and should return to 100 afterward. ROLLBACK cancels transactional changes in this transaction. This experiment depends on InnoDB and both statements running in the same connection.

ACID یک بستهٔ لفظی جادویی نیست. atomicity رو با rollback همین آزمایش لمس کردیم؛ consistency به constraint و منطق دامنه وابسته است؛ isolation رو بعدتر در transactionهای هم‌زمان می‌بینیم؛ durability هم به مسیر commit و تنظیمات واقعی server مربوط می‌شه.

ACID is not a magic slogan. We observed atomicity with rollback; consistency depends on constraints and domain logic; concurrency behavior belongs to later isolation experiments; durability depends on the commit path and actual server configuration.

حالا همان transfer رو کامل کنNow complete the transfer

این بار دو UPDATE رو در یک transaction قرار می‌دیم. شرط WHERE شمارهٔ حساب رو مشخص می‌کنه؛ در برنامهٔ واقعی باید بررسی کنی هر UPDATE دقیقاً همان یک ردیف مورد انتظار رو تغییر داده. اگه مقصد وجود نداشت یا قاعده نقض شد، باید rollback کنی.

This time both UPDATEs belong to one transaction. WHERE identifies each account; a real application must verify that each statement changed exactly the expected row. If the destination is missing or an invariant fails, roll back.

انتقال ۲۰ واحدی و ثبت نهاییTransfer 20 and commit
START TRANSACTION;
UPDATE account SET balance=balance-20 WHERE account_id=1;
UPDATE account SET balance=balance+20 WHERE account_id=2;
SELECT SUM(balance) AS total_balance FROM account;
COMMIT;
SELECT * FROM account ORDER BY account_id;

پس از commit، حساب‌ها باید ۸۰ و ۷۰ باشند و جمع همچنان ۱۵۰ بماند. COMMIT مرز ثبت این تغییرهاست. اگه query دوم خطا داد، COMMIT نکن؛ وضعیت رو بررسی و در صورت نیاز ROLLBACK کن.

After commit, balances should be 80 and 70 while the total remains 150. COMMIT is the boundary that accepts these changes. If the second statement fails, do not commit; inspect the state and roll back when appropriate.

چرا ROLLBACK همیشه عقب‌گرد نمی‌کنه؟Why does ROLLBACK not always undo a change?

MySQL معمولاً با autocommit روشن کار می‌کنه. بیرون transaction صریح، هر statement موفق تغییرش رو ثبت می‌کنه؛ بنابراین ROLLBACK بعدی آن statement تمام‌شده رو برنمی‌گرداند. transaction رو پیش از اولین statement تغییر‌دهنده شروع کن و مرز آن رو واضح تمام کن.

MySQL normally runs with autocommit enabled. Outside an explicit transaction, each successful statement commits its change, so a later ROLLBACK cannot undo it. Start the transaction before the first modifying statement and end the boundary explicitly.

وضعیت session رو بخوانRead the session setting
SELECT @@SESSION.autocommit;

برای یک کار چندمرحله‌ای معمولاً لازم نیست autocommit رو در کل session خاموش کنی؛ START TRANSACTION یک مرز روشن می‌ده و پس از COMMIT/ROLLBACK رفتار قبلی برمی‌گردد. connection poolها هم session رو دوباره استفاده می‌کنن، پس تنظیمات باقی‌مانده خطرناک‌اند.

For a multi-step operation, you usually do not need to disable autocommit for the whole session; START TRANSACTION creates a clear boundary and the previous mode resumes after COMMIT or ROLLBACK. Connection pools reuse sessions, so lingering settings can be dangerous.

DDL و جدول غیرتراکنشی مرز رو می‌شکنندDDL and nontransactional tables break the expected boundary

ROLLBACK دکمهٔ undo سراسری نیست. برخی دستورهای DDL مثل CREATE و ALTER پیش از اجرا transaction فعال رو implicit commit می‌کنن؛ atomic DDL یعنی خود همان دستور ساختاری اتمیک است، نه این‌که بتوان آن رو داخل transaction کاربری rollback کرد. همین‌طور جدول MyISAM تغییرهایش رو مثل InnoDB rollback نمی‌کنه. این فصل برای دادهٔ تراکنشی از InnoDB استفاده می‌کنه.

ROLLBACK is not a universal undo button. Many DDL statements such as CREATE and ALTER implicitly commit an active transaction first. Atomic DDL means that the DDL statement itself is atomic, not that it can be rolled back as part of a user transaction. A MyISAM table also does not roll back changes like InnoDB. This chapter uses InnoDB for transactional data.

COMMIT ناخواسته رو با DROP آزمایش نکنDo not test implicit commits with DROP

در همین ذهن نگه دار که DDL می‌تونه مرز رو ببندد؛ برای آزمایش، دادهٔ مهم رو در transaction باز نگذار و statement ساختاری رو وسط کار اجرا نکن.

Remember that DDL can close the boundary. Never leave important data in an open transaction and run schema-changing statements mid-operation as an experiment.
