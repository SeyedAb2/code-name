یک انتقال بانکی رو هر بار از نو ننویسیم

Stop rewriting the same transfer every time

بعد از فصل deadlock شاید بگویی حالا که transaction رو می‌شناسیم، یک عملیات چندمرحله‌ای رو چطور به‌شکل یک interface قابل‌فراخوانی در server نگه داریم؟ Stored Procedure همین امکان رو می‌ده؛ ولی رایگان نیست: باید مرز مسئولیت، مجوز اجرا و رفتار transaction رو آگاهانه انتخاب کنیم.

After the deadlock chapter, we may ask: now that we understand transactions, how can we keep a multi-step operation behind a callable server-side interface? A stored procedure provides that interface, but not for free: we must deliberately choose its responsibility boundary, execution privileges, and transaction behavior.

همهٔ clientها باید یک قانون رو رعایت کنندEvery client must follow the same rule

یک انتقال ساده سه کار دارد: از حساب مبدأ کم کند، به مقصد اضافه کند و یک مدرک انتقال ثبت کند. اگه هر client این سه statement رو جداگانه بفرستد، ممکنه یکی ثبت رو فراموش کند یا فقط نصف مسیر رو اجرا کند. Stored Procedure می‌تونه نامی ثابت برای این عملیات بسازد و ورودی‌هایش رو در یک نقطه بگیره.

A simple transfer has three steps: debit the source, credit the destination, and record the transfer. If every client sends the three statements independently, one may forget the record or execute only half the flow. A stored procedure can give the operation a stable name and accept its inputs in one place.

اما Procedure قرار نیست هر منطق برنامه رو به database منتقل کند. باید دلیل داشته باشیم: مثلاً invariant داده‌ای، کاهش round trip یا یک عملیات مشترک که چند client باید یکسان اجرا کنند. برای UI، تماس شبکه، workflow طولانی یا منطق پرتغییر شاید لایهٔ برنامه انتخاب بهتری باشه.

But a procedure is not a reason to move all application logic into the database. We need a concrete reason: a data invariant, fewer round trips, or a shared operation that multiple clients must execute consistently. UI behavior, network calls, long workflows, or frequently changing logic may belong in the application layer instead.

چرا موقع CREATE، delimiter رو عوض می‌کنیم؟Why change the delimiter while creating it?

بدنهٔ Procedure چند statement دارد و هرکدام با ; تمام می‌شه. اگه با mysql command-line client همان ; هم علامت پایان خود CREATE باشه، client تعریف رو وسط بدنه قطع می‌کنه. دستور DELIMITER // فقط به mysql client می‌گه پایان statement ورودی رو موقتاً // بداند؛ این دستور SQL نیست و server آن رو دریافت نمی‌کنه.

A procedure body contains multiple statements, each ending in ;. If the same semicolon also ends the CREATE statement in the mysql command-line client, the client splits the definition in the middle. DELIMITER // tells only the mysql client to treat // as the end of the submitted input; it is not SQL and is not sent to the server.

delimiter وابسته به ابزار هستThe delimiter is client-specific

این syntax برای mysql CLI و ابزارهایی که فرمان delimiter رو می‌شناسند کاربرد دارد. در migration tool، driver یا SQL editor ممکنه لازم باشه متن CREATE رو به روش مخصوص همان ابزار بفرستی؛ اگه DELIMITER رو به driver خام بدهی، ممکنه syntax error بگیری.

This syntax applies to the mysql CLI and tools that understand its delimiter command. Migration tools, drivers, and SQL editors may require their own way to submit a CREATE body; sending DELIMITER directly to a raw driver may cause a syntax error.

Procedure با IN و OUTA procedure with IN and OUT parameters

Procedure زیر مبلغ رو از caller می‌گیره، دو حساب رو با ترتیب ثابت قفل می‌کنه و نتیجهٔ اجرای transfer رو در پارامتر OUT می‌ذاره. برای سادگی، اگه ورودی نامعتبر یا موجودی ناکافی باشه با SIGNAL خطا می‌ده. handler هر خطا رو rollback می‌کنه و دوباره همان خطا رو به caller می‌فرستد.

The procedure below accepts an amount, locks the two accounts in a stable order, and returns the new transfer identifier through an OUT parameter. For clarity, it signals an error for invalid input or insufficient funds. A handler rolls back on error and resends the condition to the caller.

تعریف رو در mysql CLI اجرا کنCreate it in the mysql CLI
DELIMITER //
CREATE PROCEDURE codenames_deadlock_lab.transfer_funds(
  IN p_source CHAR(1),
  IN p_destination CHAR(1),
  IN p_amount INT,
  OUT p_transfer_id BIGINT
)
SQL SECURITY INVOKER
MODIFIES SQL DATA
BEGIN
  DECLARE v_source_balance INT;
  DECLARE v_other_balance INT;
  DECLARE v_first CHAR(1);
  DECLARE v_second CHAR(1);
  DECLARE v_transaction_started BOOLEAN DEFAULT FALSE;
  DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN
    IF v_transaction_started THEN
      ROLLBACK;
    END IF;
    RESIGNAL;
  END;

  START TRANSACTION;
  SET v_transaction_started = TRUE;

  IF p_source = p_destination OR p_amount <= 0 THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='invalid transfer input';
  END IF;

  SET v_first = LEAST(p_source, p_destination);
  SET v_second = GREATEST(p_source, p_destination);
  SELECT balance INTO v_other_balance
    FROM codenames_deadlock_lab.account
    WHERE account_id = v_first FOR UPDATE;
  IF v_other_balance IS NULL THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='unknown account';
  END IF;
  SET v_other_balance = NULL;
  SELECT balance INTO v_other_balance
    FROM codenames_deadlock_lab.account
    WHERE account_id = v_second FOR UPDATE;
  IF v_other_balance IS NULL THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='unknown account';
  END IF;
  SELECT balance INTO v_source_balance
    FROM codenames_deadlock_lab.account
    WHERE account_id = p_source;

  IF v_source_balance IS NULL OR v_source_balance < p_amount THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='insufficient funds or unknown source';
  END IF;

  UPDATE codenames_deadlock_lab.account
    SET balance = balance - p_amount WHERE account_id = p_source;
  UPDATE codenames_deadlock_lab.account
    SET balance = balance + p_amount WHERE account_id = p_destination;

  INSERT INTO codenames_deadlock_lab.transfer(source_id,destination_id,amount)
    VALUES (p_source,p_destination,p_amount);
  SET p_transfer_id = LAST_INSERT_ID();
  COMMIT;
  SET v_transaction_started = FALSE;
END//
DELIMITER ;

این نسخه برای روشن‌بودن transaction مرز آن رو داخل Procedure می‌سازد و commit می‌کنه. در برنامهٔ واقعی باید قرارداد مالکیت transaction روشن باشه؛ اگه caller قرار هست چند کار رو در یک transaction بزرگ‌تر کنترل کند، Procedure نباید بی‌خبر transaction او رو commit کند. اجرای Procedure ممکنه پایان transaction موجود رو تحمیل کند؛ آن رو کنار مرزهای application طراحی و آزمایش کن.

This version owns and commits its transaction to make the boundary visible. In an application, transaction ownership must be explicit; if the caller controls a larger transaction, the procedure must not unexpectedly commit it. Procedure execution can affect an existing transaction boundary, so design and test it with the application’s transaction model.

SELECT ... FOR UPDATE این‌جا فقط مبدأ رو قفل می‌کنه. اگه چند انتقال هم‌زمان در هر دو جهت داریم، بهتر هست هر دو ردیف رو طبق ترتیب شناسه lock کنیم و سپس balance مبدأ رو از نتیجه برداریم. این مثال رو برای تمرین ورودی/خروجی ساده نگه می‌داریم؛ در production همان ترتیب ثابت فصل قبل رو پیاده کن.

The SELECT ... FOR UPDATE here locks only the source. If transfers can run concurrently in both directions, lock both rows in a stable identifier order, then read the source balance from the result. We keep this example focused on parameter flow; in production, apply the consistent ordering from the previous chapter.

با CALL اجرا و نتیجه رو بررسی کنInvoke it with CALL and inspect the result

پارامترهای IN مقدار می‌گیرن؛ برای OUT یک user variable در همان connection می‌دیم و بعد از CALL آن رو می‌خونیم. @transfer_id متغیر session است، نه متغیر محلی Procedure؛ در connection دیگری مقدارش رو نمی‌بینی.

IN parameters receive values; for OUT, pass a user variable on the same connection and read it after CALL. @transfer_id is a session variable, not a procedure-local variable; another connection will not see its value.

Expect a transfer identifier, balances of 85 for A and 115 for B, and one transfer row. These pieces of evidence matter together: the OUT value alone does not prove both balances and the transfer record changed consistently.

Procedure بدون پارامتر هم باید پرانتز خالی داشته باشه. نام پارامتر رو از نام ستون‌ها واضح جدا کن؛ نام‌گذاری مبهم می‌تونه در queryهای داخل routine باعث شود معلوم نباشه منظور ستون هست یا متغیر.

A parameterless procedure still uses empty parentheses. Clearly distinguish parameter names from column names; ambiguous naming can make it unclear whether a routine query refers to a column or a local variable.

تعریف ذخیره‌شده رو از خود server بخوانRead the stored definition back from the server

فایل SQL که در editor ساختی الزاماً همان چیزی نیست که روی server ذخیره شده. با SHOW CREATE PROCEDURE تعریف واقعی رو بخوان. برای دیدن routineهای همین database هم از INFORMATION_SCHEMA استفاده کن.

The SQL file in your editor is not necessarily the definition stored on the server. Read the actual routine with SHOW CREATE PROCEDURE. To list routines in the current database, query INFORMATION_SCHEMA.

اگه procedure دیده نمی‌شه، اول database/schema، نام دقیق و مجوزهای metadata رو بررسی کن. نبودن نتیجه در query فهرست لزوماً ثابت نمی‌کنه routine وجود ندارد؛ بعضی metadataها بر اساس privilege قابل‌مشاهده‌اند.

If the procedure is missing, check the schema, exact name, and metadata privileges first. An empty listing query does not necessarily prove the routine does not exist; metadata visibility can depend on privileges.

چه کسی اجازهٔ ساختن دارد و با مجوز چه کسی اجرا می‌شه؟Who can create it, and whose privileges does it use?

ساخت Stored Procedure به privilege مربوط به CREATE ROUTINE نیاز دارد و فراخوانی آن به EXECUTE. گزینهٔ SQL SECURITY INVOKER یعنی privilegeهای caller برای دسترسی به objectهای داخل routine بررسی می‌شه؛ حالت DEFINER از context تعریف‌کننده استفاده می‌کنه. انتخاب اشتباه می‌تونه routine رو ناخواسته به راه میان‌بُر privilege تبدیل کند.

Creating a stored procedure requires CREATE ROUTINE, and calling it requires EXECUTE. With SQL SECURITY INVOKER, access to objects inside the routine is checked using the caller’s privileges; DEFINER uses the definer’s security context. A careless choice can turn a routine into an unintended privilege shortcut.

در درس، INVOKER رو انتخاب کردیم تا Procedure فقط با دسترسی خود caller کار کند. برای production، least privilege، account تعریف‌کننده، مالکیت routine و migration رو جداگانه بررسی کن؛ از root برای ساخت routineهای روزمره استفاده نکن.

We chose INVOKER in the lab so the procedure uses the caller’s own access. For production, review least privilege, the definer account, routine ownership, and migrations separately; do not use root for routine day-to-day creation.

سه اشتباه رایج پیش از آن‌که deploy کنیمThree mistakes to catch before deployment

DELIMITER رو به driver می‌فرستم

delimiter فرمان client است، نه SQL server. migration ابزار باید کل CREATE رو به روش خودش به‌عنوان یک statement ارسال کند.

I send DELIMITER to the driver

DELIMITER is a client command, not server SQL. The migration tool must submit the complete CREATE using its own statement handling.

OUT رو از connection دیگری می‌خوانم

user variable مثل @transfer_id به session تعلق دارد. CALL و SELECT رو در همان connection انجام بده.

I read OUT from another connection

A variable such as @transfer_id belongs to the session. Run CALL and SELECT on the same connection.

Procedure رو اتمی فرض می‌کنم

نام routine تضمین transaction نیست. بدنه، engine، handler و مرز COMMIT رو بخوان؛ آزمایش کن خطا چه چیزی رو rollback می‌کنه.

I assume the procedure is atomic

A routine name does not guarantee a transaction. Inspect its body, storage engine, handler, and commit boundary; test what an error rolls back.

DEFINER رو بی‌دلیل انتخاب می‌کنم

security context روی privilegeها اثر دارد. انتخابش باید دلیل، مالک مشخص و تست با account محدود داشته باشه.

I choose DEFINER without a reason

The security context affects privileges. It needs a reason, a managed owner, and tests with a restricted account.

فقط سبزشدن command رو جواب حساب نکن. از خروجی یه نشونهٔ مشخص بیرون بکش و بنویس این نشونه دربارهٔ مسئلهٔ تمرین چی رو ثابت می‌کنه و چی رو هنوز ثابت نمی‌کنه.

Do not treat command success as the answer. Extract one concrete piece of evidence and state what it proves about the exercise—and what it still does not prove.

آزمایش: یک رابط بساز، خطایش رو هم امتحان کنLab: build an interface and test its failure

Procedure انتقال رو در schema تمرینی بساز، با مبلغ کوچک CALL کن و هم‌زمان سه چیز رو verify کن: شناسهٔ OUT، ماندهٔ هر دو حساب و ردیف ثبت‌شده. بعد مبلغی بیشتر از مانده بفرست؛ خطا باید به client برسد و هیچ‌کدام از سه اثر نیمه‌کاره نماند. در پایان SHOW CREATE بگیر و قرارداد رو با هم‌تیمی‌ات مرور کن.

Create the transfer procedure in the lab schema, call it with a small amount, and verify three things: the OUT identifier, both balances, and the transfer record. Then request more than the available balance; the error should reach the client and none of the three effects should be partial. Finish with SHOW CREATE and review the contract with a teammate.

این lab هنوز raceهای واقعی رو کامل پوشش نمی‌ده. نسخهٔ production باید هر دو ردیف رو با ترتیب ثابت قفل کند، transaction رو در لایه‌ها دوباره‌کاری نکند، رفتار timeout/deadlock رو مدیریت کند و با حساب کم‌دسترسی تست شود.

This lab does not fully cover production races. A production version must lock both rows in a stable order, avoid duplicated transaction ownership across layers, handle timeout/deadlock behavior, and be tested with a restricted account.

وقتی مقدار رو می‌خوایم، شاید Procedure ابزار درست نباشهWhen we need a value, a procedure may not be the right tool

Procedure برای اجرای یک عملیات و حتی برگردونهن چند نتیجه مناسب هست. اما گاهی query باید درون یک expression مقدار واحدی بخواند؛ مثلاً مبلغ نهایی یا دسته‌بندی یک رکورد. آن‌جا Stored Function مطرح می‌شه و محدودیت‌های متفاوتی دارد. فصل بعد همین مرز رو با queryهای واقعی می‌سنجیم.

A procedure is suited to performing an operation and can return multiple results. Sometimes a query needs a single value inside an expression, such as a final amount or record category. That is where a stored function enters, with different constraints. In the next chapter, we will test that boundary with real queries.
