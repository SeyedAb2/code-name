View، DEFINER و SQL SECURITY در MySQL

Views, DEFINER, and SQL SECURITY in MySQL

گزارشگر فروش باید نام محصول و قیمت نهایی را ببیند؛ اما نباید به همهٔ ستون‌های جدول اصلی دسترسی داشته باشد. یک view می‌تواند شکل دادهٔ قابل‌مشاهده را محدود کند. حالا باید دقیق بفهمیم وقتی همان گزارش را کاربر محدود می‌خواند، MySQL مجوز چه کسی را بررسی می‌کند.

A sales reporter needs product names and final prices, but not every column in the base table. A view can shape what is exposed. Now we need to determine whose privileges MySQL checks when that restricted user reads the report.

پیش‌نیازPrerequisite: فصل ۴ · ستون‌های generated محیط مرجعLab baseline: MySQL 9.7.2 · حساب‌های disposable زمانTime: ۷۵ دقیقه · ۱۸ تمرین

گزارش لازم است؛ دسترسی کامل نهThe report is needed; full table access is not

مسئول پشتیبانی باید عنوان و قیمت نهایی محصول را بررسی کند. جدول اصلی علاوه بر این‌ها، داده‌هایی دارد که برای این کار لازم نیست. اگر به او دسترسی مستقیم به جدول بدهیم، مرز دسترسی از نیازش بزرگ‌تر می‌شود. اگر یک view بسازیم، هنوز یک سؤال باقی است: view با مجوز تعریف‌کننده اجرا می‌شود یا مجوز کسی که آن را می‌خواند؟

Support needs to inspect product titles and final prices. The base table also contains data this task does not require. Direct table access would exceed the need. A view can narrow the interface, but one question remains: does it run under the definer’s privileges or the reader’s?

view نتیجهٔ یک SELECT را به‌شکل یک object قابل‌خواندن ارائه می‌کند؛ خود view یک کپی مستقل از ردیف‌ها نیست. همچنین روی view به‌تنهایی index نمی‌سازیم: plan به view و tableهای زیرین وابسته است. پس view ابزار رابط و کنترل دسترسی است، نه جایگزین طراحی index یا backup.

A view exposes a SELECT as a queryable object; it is not an independent copy of the rows. You do not index the view itself: plans depend on the view and underlying tables. A view is an interface and access-control tool, not a substitute for index design or backups.

دادهٔ کم اما واقعی برای آزمونA small but useful test fixture

از جدول همین مسیر استفاده می‌کنیم. یک ستون حساس فرضی به آن اضافه می‌کنیم تا تفاوت «دیدن view» و «خواندن table پایه» واضح باشد. همهٔ این دستورها در database آزمایشی‌اند.

We use the table from this track and add a deliberately sensitive example column so the difference between reading the view and reading the base table is visible. These statements belong only in the lab database.

آماده‌سازی و ساخت رابط گزارشPrepare the report interface
USE codenames_mysql_ch04;

ALTER TABLE product_offer
  ADD COLUMN supplier_note VARCHAR(120) NULL;

UPDATE product_offer
SET supplier_note = 'internal supplier detail'
WHERE offer_id = 1;

CREATE OR REPLACE
  ALGORITHM = UNDEFINED
  SQL SECURITY DEFINER
VIEW v_offer_report AS
SELECT offer_id, title, final_price
FROM product_offer
WHERE final_price > 0;

SELECT * FROM v_offer_report ORDER BY offer_id;
SHOW CREATE VIEW v_offer_report;

در تعریف view فهرست ستون‌ها را صریح نوشتیم؛ SELECT * قرارداد مبهمی می‌سازد. MySQL تعریف view را هنگام ساخت ثبت می‌کند؛ ستون‌های تازه‌ای که بعداً به table اضافه شوند خودکار به projection موجود اضافه نمی‌شوند. در این مثال یادداشت تأمین‌کننده عمداً از view بیرون مانده است.

The view names its columns explicitly; SELECT * would create a less deliberate contract. MySQL records the view definition when it is created; later base-table columns do not automatically enter its projection. The supplier note is intentionally excluded.

این view را به‌عنوان دیوار امنیتی جادویی فرض نکن.رفتار مؤثر به privilegeهای خود view، DEFINER معتبر، SQL SECURITY، مجوزهای account و امکان دسترسی از مسیرهای دیگر بستگی دارد. با همان account محدود آزمایش کن.Do not treat a view as a magical security wall.Effective behavior depends on view privileges, a valid definer, SQL SECURITY, account grants, and other access paths. Test as the restricted account itself.

DEFINER یعنی مجوز کدام account؟DEFINER: whose privileges?

در SQL SECURITY DEFINER، هنگام دسترسی به objectهای زیر view، MySQL privilegeها را بر اساس account تعریف‌کننده بررسی می‌کند. خواننده هنوز باید اجازهٔ استفاده از خود view را داشته باشد، اما برای table پایه لزوماً grant مستقیم نمی‌گیرد. در SQL SECURITY INVOKER، privilegeهای invoker برای objectهای زیرین بررسی می‌شود. اگر clause را ننویسی، پیش‌فرض view در MySQL، DEFINER است.

With SQL SECURITY DEFINER, MySQL checks access to underlying objects using the definer account. The reader still needs permission to use the view, but does not necessarily receive a direct grant on the base table. With SQL SECURITY INVOKER, the invoker’s privileges are used for underlying objects. If omitted, MySQL’s view default is DEFINER.

SettingPrivilege context for base objectsTypical question
DEFINERThe view’s definer accountCan a restricted reader use a curated interface without direct table grants?
INVOKERThe account querying the viewDoes the caller independently have the needed base-object privileges?
OmittedDEFINER defaultWhat context was actually stored? Inspect it rather than infer.

برای آزمایش به مجوز ساخت account و اعطای privilege نیاز داری؛ روی Server مشترک این کار را نکن. administrator محیط disposable دو حساب می‌سازد: یکی view را تعریف می‌کند، دیگری فقط باید گزارش مجاز را بخواند.

This test requires authority to create accounts and grant privileges; do not do it on a shared server. An administrator in a disposable environment creates one account to define the view and another that should read only the approved report.

حداقل grant برای آزمون DEFINERMinimum grants for the DEFINER test
CREATE USER 'report_owner'@'%' IDENTIFIED BY 'replace-in-lab';
CREATE USER 'report_reader'@'%' IDENTIFIED BY 'replace-in-lab';

GRANT SELECT ON codenames_mysql_ch04.product_offer
  TO 'report_owner'@'%';
GRANT CREATE VIEW, SHOW VIEW ON codenames_mysql_ch04.*
  TO 'report_owner'@'%';

GRANT SELECT ON codenames_mysql_ch04.v_offer_report
  TO 'report_reader'@'%';

SHOW GRANTS FOR 'report_reader'@'%';

در محیط تمرین، view را با account مجاز تعریف کن و بعد با reader آزمایش کن. رمزهای بالا نمونه‌اند؛ secret واقعی را داخل فایل آموزشی، history مشترک یا مخزن قرار نده. بسته به نسخه و سیاست account host، روش اتصال reader ممکن است متفاوت باشد.

In the lab, create the view with the authorized account, then test as the reader. These passwords are placeholders; never place real secrets in course files, shared history, or a repository. The reader’s connection method can differ by version and host-account policy.

با account درست، دسترسی را ثابت کنProve access with the intended account

از نشست report_reader اول view را بخوان؛ بعد دسترسی مستقیم به table را امتحان کن. نتیجهٔ موفق view و ردشدن table پایه، اگر مجوزها همان‌طور تنظیم شده باشند، مدرک مرز موردنظر است. خروجی administrator به‌تنهایی اثبات نمی‌کند reader هم همین دسترسی را دارد.

From a report_reader session, query the view, then try the base table directly. A successful view read and a denied base-table read—under the intended grants—is evidence for this boundary. An administrator’s output does not prove the reader has the same access.

دو query، دو نتیجهٔ مورد انتظارTwo queries, two expected outcomes
SELECT CURRENT_USER(), USER();
SELECT offer_id, title, final_price
FROM codenames_mysql_ch04.v_offer_report
ORDER BY offer_id;

SELECT supplier_note
FROM codenames_mysql_ch04.product_offer
WHERE offer_id = 1;

query آخر باید با privilege محدود رد شود. اگر موفق شد، از SHOW GRANTS و account مؤثر شروع کن؛ احتمال دارد reader از نقش، host account متفاوت، یا grant گسترده‌تری مجوز گرفته باشد. اگر query اول رد شد، DEFINER، مجوز SELECT روی view و دسترسی definer به table را جداگانه بررسی کن.

The final query should be denied under the intended restricted grants. If it succeeds, inspect SHOW GRANTS and the matched account; the reader may have a role, a different host account, or a broader grant. If the first query fails, inspect the definer, SELECT on the view, and the definer’s base-table access separately.

همان view با INVOKER چه فرقی دارد؟What changes with INVOKER?

یک view دوم با همان SELECT اما SQL SECURITY INVOKER بساز. حالا اگر reader به table پایه دسترسی نداشته باشد، query روی view هم ممکن است رد شود؛ زیرا privilegeهای خود invoker برای object زیرین اهمیت دارند.

Create a second view with the same SELECT but SQL SECURITY INVOKER. If the reader lacks access to the base table, querying this view may also be denied because the invoker’s privileges apply to the underlying object.

ساختن و بررسی view با invokerCreate and inspect the invoker view
CREATE OR REPLACE
  SQL SECURITY INVOKER
VIEW v_offer_report_invoker AS
SELECT offer_id, title, final_price
FROM product_offer
WHERE final_price > 0;

SHOW CREATE VIEW v_offer_report_invoker;
GRANT SELECT ON codenames_mysql_ch04.v_offer_report_invoker
  TO 'report_reader'@'%';

حالا از نشست reader دوباره SELECT کن و خطا را با DEFINER مقایسه کن. اگر برای نمایش view به خواننده grant داده‌ای اما table پایه را نداده‌ای، تفاوت رفتار را می‌بینی. «view امن است» نتیجهٔ مناسبی نیست؛ باید security mode و privilegeهای واقعی را گزارش کنی.

Query it again as the reader and compare the error with the DEFINER view. If the reader can use the view but lacks base-table grants, the security mode changes the result. “The view is secure” is not a sufficient conclusion; report the mode and actual privileges.

View چه چیزی را حل نمی‌کند؟What a view does not solve

view داده را materialize نمی‌کند، index مستقل ندارد و همهٔ viewها قابل UPDATE نیستند. اگر definition شامل aggregate، group، بعضی joinها یا constructهای دیگر باشد، update از view ممکن است ممنوع شود. همچنین view با DEFINER نامعتبر می‌تواند بعداً به مشکل بخورد؛ account تعریف‌کننده را حذف یا بی‌دلیل بسیار قدرتمند نکن.

A view does not materialize rows, has no independent index, and is not always updatable. Definitions with aggregates, grouping, some joins, or other constructs may prohibit updates through the view. An invalid definer can also cause later trouble; do not remove the defining account or make it unnecessarily powerful.

با SHOW CREATE VIEW definition مؤثر را بازبینی کن. اگر DDL با SELECT * ساخته شده، بعداً تغییر ستون‌های table را فرض نکن؛ projection view در زمان تعریف ثبت شده است و تغییرات schema باید با برنامهٔ مصرف‌کننده هماهنگ شوند.

Review the effective definition with SHOW CREATE VIEW. If it was created with SELECT *, do not assume later base-table columns appear automatically; the view projection is recorded at definition time, and schema changes must be coordinated with consumers.

قانون عملیبرای API داده، ستون‌ها و security mode را صریح بنویس؛ بعد با accountی که قرار است مصرف کند تست کن.Practical ruleFor a data interface, name the columns and security mode explicitly, then test as the account that will consume it.

۱۸ تمرین SQL18 SQL exercises

تمرین‌ها روی database آزمایشی فصل ۴ هستند. برای آزمایش accountها از محیط disposable استفاده کن؛ روی سرور واقعی user و grant آزمایشی نساز.

Exercises use chapter 4’s lab database. Test accounts only in a disposable environment; do not create practice users or grants on a real server.

1) گزارش کمینه بساز / Create a minimal report

viewی بساز که فقط شناسه، عنوان و قیمت نهایی را نشان دهد.

Create a view exposing only the identifier, title, and final price.

SQL / SQL
CREATE OR REPLACE VIEW v_offer_minimal AS SELECT offer_id,title,final_price FROM product_offer;

فهرست ستون‌ها صریح است و یادداشت تأمین‌کننده بیرون می‌ماند.

The projection is explicit and omits the supplier note.

2) مصرف view / Query the view

گزارش را با ترتیب قیمت نزولی بخوان.

Read the report ordered by descending price.

SQL / SQL
SELECT offer_id,title,final_price FROM v_offer_minimal ORDER BY final_price DESC;

ORDER BY متعلق به query مصرف‌کننده است، مگر در قرارداد دیگری صریح شود.

ORDER BY belongs to the consuming query unless another contract says otherwise.

3) base table در view نیست / Confirm the sensitive field is absent

تعریف view و projection آن را inspect کن.

Inspect the view definition and its projection.

SQL / SQL
SHOW CREATE VIEW v_offer_minimal;

نبودن ستون در خروجی را بررسی می‌کنیم؛ این به‌تنهایی دسترسی مستقیم table را لغو نمی‌کند.

We verify the column is absent; this alone does not revoke direct table access.

4) تعریف view را از metadata بخوان / Read view metadata

نام view، definer و security type را از information_schema.VIEWS بخوان.

Read the view name, definer, and security type from information_schema.VIEWS.

SQL / SQL
SELECT TABLE_NAME,DEFINER,SECURITY_TYPE,VIEW_DEFINITION FROM information_schema.VIEWS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='v_offer_minimal';

metadata ممکن است طبق privilege account محدود باشد؛ با account مناسب تکرار کن.

Metadata visibility can be privilege-limited; repeat with an appropriately authorized account.

5) default امنیت را اثبات کن / Prove the stored security mode

برای view ساخته‌شده بدون clause، مقدار امنیت ثبت‌شده را پیدا کن.

Find the recorded security mode of a view created without a clause.

SQL / SQL
SELECT TABLE_NAME,SECURITY_TYPE FROM information_schema.VIEWS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='v_offer_minimal';

در MySQL default view برابر DEFINER است؛ باز هم مقدار object را از خود سرور می‌خوانیم.

MySQL defaults views to DEFINER; still inspect the object on the server.

6) نقش account جاری / Identify the matched account

در نشست محدود، هویت login و account مؤثر privilege را ببین.

In the restricted session, inspect login identity and the effective privilege account.

SQL / SQL
SELECT USER(),CURRENT_USER(); SHOW GRANTS;

CURRENT_USER برای بررسی accountی که grantها به آن match شده‌اند مهم است.

CURRENT_USER helps identify which account’s grants matched.

7) grant فقط روی view / Grant only the view

در آزمایش disposable، SELECT روی view بده و grantها را بررسی کن.

In a disposable lab, grant SELECT on the view and inspect the grants.

SQL / SQL
GRANT SELECT ON codenames_mysql_ch04.v_offer_minimal TO 'report_reader'@'%'; SHOW GRANTS FOR 'report_reader'@'%';

هر grant باقی‌ماندهٔ گسترده می‌تواند آزمون را بی‌معنا کند.

Any broader existing grant can invalidate the test.

8) access مسیر مجاز / Test the intended read path

به‌عنوان reader view را بخوان و نتیجه را ثبت کن.

As the reader, query the view and record the result.

SQL / SQL
SELECT offer_id,title,final_price FROM codenames_mysql_ch04.v_offer_minimal;

این آزمون باید با privilegeهای واقعی همان account انجام شود.

This must run under that account’s actual privileges.

9) مسیر مستقیم را امتحان کن / Test direct base-table access

با reader تلاش کن ستون حساس را از table اصلی بخوانی.

As the reader, try to read the sensitive column from the base table.

SQL / SQL
SELECT supplier_note FROM codenames_mysql_ch04.product_offer;

در طراحی محدود باید رد شود؛ اگر موفق شد، SHOW GRANTS و account مؤثر را بررسی کن.

Under the intended restricted design, it should fail; inspect grants and matched account if it succeeds.

10) INVOKER بساز / Create an INVOKER view

view هم‌شکل بساز که privilegeهای caller را به‌کار ببرد.

Create an equivalent view that uses the caller’s privileges.

SQL / SQL
CREATE OR REPLACE SQL SECURITY INVOKER VIEW v_offer_invoker AS SELECT offer_id,title,final_price FROM product_offer;

security type را با metadata تأیید کن.

Verify the security type in metadata.

11) فرق دو حالت را query کن / Compare both modes

DEFINER و INVOKER را کنار هم از metadata بخوان.

Read DEFINER and INVOKER metadata side by side.

SQL / SQL
SELECT TABLE_NAME,DEFINER,SECURITY_TYPE FROM information_schema.VIEWS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME IN ('v_offer_minimal','v_offer_invoker');

نام viewها کافی نیست؛ mode بخشی از قرارداد دسترسی است.

Names alone are insufficient; the mode is part of the access contract.

12) DEFINER واقعی را بررسی کن / Inspect the actual definer

از SHOW CREATE VIEW بفهم object با کدام account تعریف شده است.

Use SHOW CREATE VIEW to see which account defined the object.

SQL / SQL
SHOW CREATE VIEW v_offer_minimal;

اگر account نامعتبر یا حذف‌شده باشد، وابستگی عملیاتی ثبت کن؛ definer را حدس نزن.

If the account is missing or invalid, record the operational dependency; do not guess the definer.

13) چرا view index ندارد؟ / Why can’t the view be indexed?

به‌جای ساخت index خیالی روی view، indexهای table زیرین را inspect کن.

Instead of assuming an index can be created on the view, inspect its base-table indexes.

SQL / SQL
SHOW INDEX FROM product_offer;

index روی table پایه است؛ plan query مصرف‌کننده تعیین می‌کند استفاده شود یا نه.

Indexes belong to base tables; the consumer’s plan determines whether they are used.

14) projection را صریح نگه دار / Keep the projection explicit

view دیگری با ستون‌های لازم تعریف کن؛ از SELECT * استفاده نکن.

Define another view with the needed columns and avoid SELECT *.

SQL / SQL
CREATE OR REPLACE VIEW v_offer_titles (id,title) AS SELECT offer_id,title FROM product_offer;

ستون‌های قرارداد خوانا و قابل‌بازبینی‌اند.

The interface’s columns are visible and reviewable.

15) view را با DDL بررسی کن / Review view DDL

تعریف view تازه را بخوان و security mode را در گزارش بیاور.

Read the new view definition and include its security mode in your report.

SQL / SQL
SHOW CREATE VIEW v_offer_titles;

نسخهٔ server و تعریف واقعی را مستند کن، نه فقط متن اولیهٔ فایل.

Document server version and effective definition, not just the original file.

16) تغییر schema و view / Reason about a later column

اگر فردا به table ستون تازه اضافه شود، آیا خودکار به view فعلی اضافه می‌شود؟ با SHOW CREATE VIEW استدلالت را بررسی کن.

If a new base-table column is added tomorrow, will it automatically appear in this view? Use SHOW CREATE VIEW to support your answer.

SQL و تفسیر / SQL and interpretation
SHOW CREATE VIEW v_offer_titles;

نه؛ projection در definition ثبت‌شدهٔ view ثابت است تا وقتی آن را تغییر دهی.

No; the stored view projection remains until you change its definition.

17) خطای privilege را با query محدود کن / Narrow a privilege failure with queries

برای خطای SELECT reader روی view، queryهایی اجرا کن که account جاری، grantها، SECURITY_TYPE/DEFINER و definition مؤثر را نشان دهند.

For a reader’s failed view SELECT, run queries showing the current account, grants, SECURITY_TYPE/DEFINER, and effective definition.

SQL و تفسیر / SQL and interpretation
SELECT USER(),CURRENT_USER(); SHOW GRANTS; SELECT TABLE_NAME,DEFINER,SECURITY_TYPE FROM information_schema.VIEWS WHERE TABLE_SCHEMA='codenames_mysql_ch04' AND TABLE_NAME='v_offer_report'; SHOW CREATE VIEW codenames_mysql_ch04.v_offer_report;

این شواهد account واقعی، مجوز reader، security context و definition را جدا می‌کنند؛ بعد دسترسی definer به table پایه را از نشست مدیریتی مجاز بررسی کن.

These checks separate the matched account, reader grants, security context, and definition; then verify the definer’s base-table access under an authorized account.

18) رابط داده را تحویل بده / Deliver a data interface

یک view مناسب گزارش تعریف کن و package مدرک تحویل بده: DDL، account هدف، grant، تست مجاز و تست ردشده.

Define a reporting view and submit evidence: DDL, intended account, grants, an allowed test, and a denied test.

نمونهٔ بررسی / Review query
SHOW CREATE VIEW v_offer_report;
SHOW GRANTS FOR 'report_reader'@'%';
SELECT TABLE_NAME,DEFINER,SECURITY_TYPE FROM information_schema.VIEWS WHERE TABLE_SCHEMA=DATABASE();

بدون آزمون از account واقعی مصرف‌کننده، ادعای محدودبودن دسترسی کامل نیست.

Without testing as the actual consumer account, the access-control claim is incomplete.

رابط خوب، دسترسی روشنA useful interface with an explicit boundary

حالا view را نه به‌عنوان میان‌بُر syntax، بلکه به‌عنوان قراردادی میان داده و مصرف‌کننده می‌بینی. در فصل بعد سراغ داده‌ای می‌رویم که اصلاً قرار نیست عمرش از connection بیشتر شود: temporary table و scope آن. تا آن موقع، این گزارش را با همان accountی که قرار است بخواند اجرا کن و نتیجهٔ واقعی را ثبت کن.

You can now treat a view as a contract between data and its consumer, not merely a syntax shortcut. Next we’ll look at data that should not outlive its connection: temporary tables and scope. Until then, run this report as the intended reader and record the actual result.
