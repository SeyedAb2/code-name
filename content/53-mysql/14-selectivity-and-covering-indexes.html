Selectivity و covering index

Selectivity and Covering Indexes

دو index برای query در دسترس‌اند. یکی روی ستون پرتکرار، یکی روی کلید دقیق‌تر. آیا هرچه مقدارها متنوع‌تر باشند index بهتر است؟ و اگر index پاسخ query را کامل داشته باشد چه کاری حذف می‌شود؟ با یک dataset تکرارپذیر هم توزیع را می‌سنجیم، هم پوشش را از روی plan می‌خوانیم.

Two indexes are available for a query: one on a frequently repeated column and one on a more discriminating key. Does more distinctness always mean a better index? And what work can be avoided when an index contains everything the query needs? We will inspect both distribution and coverage with a reproducible dataset.

پیش‌نیازPrerequisite: فصل ۱۳ · composite indexمحیط مرجعReference environment: MySQL 9.7 · InnoDBزمانTime: ۹۰ دقیقه · ۱۸ تمرین

index انتخاب شده، ولی کار زیادی باقی ماندهThe index is chosen, but much work remains

یک query روی status='open' index دارد، اما بیشتر جدول را برمی‌گرداند. query دیگری فقط چند ردیف را پیدا می‌کند، ولی برای هرکدام به data row برمی‌گردد تا دو ستون دیگر را بخواند. پس دو سؤال جدا داریم: «شرط چقدر انتخاب‌گر است؟» و «آیا خود index همهٔ دادهٔ لازم را دارد؟»

A query on status='open' has an index but returns most of the table. Another query finds only a few rows, yet visits each data row to fetch two more columns. These are separate questions: “How selective is the predicate?” and “Does the index itself contain everything the query needs?”

Selectivity را به زبان ساده می‌توان سهم ردیف‌هایی دانست که شرط نگه می‌دارد؛ مقدار کمتر معمولاً ردیف‌های کمتری باقی می‌گذارد. Cardinality در metadata تخمینی از تعداد مقدارهای متمایز index است و همان selectivity نهایی query نیست. بعد از آن هم باید ببینیم query ستون‌های خارج از index لازم دارد یا نه.

In simple terms, selectivity is the fraction of rows retained by a predicate; a smaller fraction usually leaves fewer rows. Cardinality in metadata estimates distinct index values and is not the query’s final selectivity. Then we must ask whether the query needs columns outside the index.

fixture چهارصد ردیفی بسازBuild a 400-row fixture
CREATE DATABASE IF NOT EXISTS codenames_selectivity_lab;
USE codenames_selectivity_lab;
DROP TABLE IF EXISTS support_event;

CREATE TABLE support_event (
  event_id BIGINT NOT NULL,
  customer_id INT NOT NULL,
  status VARCHAR(10) NOT NULL,
  created_at DATETIME NOT NULL,
  amount DECIMAL(8,2) NOT NULL,
  note VARCHAR(40) NOT NULL,
  PRIMARY KEY(event_id),
  KEY ix_status(status),
  KEY ix_customer_status_date(customer_id,status,created_at)
) ENGINE=InnoDB;

INSERT INTO support_event
WITH RECURSIVE seq(n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM seq WHERE n < 400
)
SELECT
  n,
  MOD(n,40)+1,
  CASE MOD(n,10)
    WHEN 0 THEN 'closed'
    WHEN 1 THEN 'waiting'
    ELSE 'open'
  END,
  TIMESTAMP('2026-01-01 00:00:00') + INTERVAL n HOUR,
  MOD(n * 17, 5000) / 100,
  CONCAT('event-', n)
FROM seq;

SELECT COUNT(*) AS total_rows FROM support_event;

CTE بازگشتی اعداد ۱ تا ۴۰۰ را برای fixture می‌سازد؛ اگر نسخه یا محیطت این syntax را محدود کرده، fixture را با روش seed مورد تأیید محیط بساز، اما همان توزیع status را حفظ کن. این داده ساختگی است و برای سنجش latency واقعی نیست.

The recursive CTE generates values 1 through 400. If your version or environment restricts this syntax, seed an equivalent fixture using an approved method while preserving the status distribution. This is synthetic data, not a real latency benchmark.

قبل از نگاه به index، توزیع را query کنQuery the distribution before inspecting indexes

به‌جای حدس از روی اسم ستون، تعداد کل و سهم هر مقدار را حساب کن. در fixture ما بیشتر رویدادها open هستند، پس شرط open انتخاب‌گر نیست؛ status='closed' ردیف‌های بسیار کمتری نگه می‌دارد.

Rather than guessing from a column name, count total rows and each value’s share. Most fixture events are open, so that predicate is not selective; status='closed' retains far fewer rows.

شمارش و نسبت واقعی روی همین دادهCounts and actual fractions for this dataset
SELECT status, COUNT(*) AS rows_kept,
       COUNT(*) / (SELECT COUNT(*) FROM support_event) AS fraction
FROM support_event
GROUP BY status
ORDER BY rows_kept DESC;

SELECT COUNT(DISTINCT status) AS distinct_status,
       COUNT(*) AS total_rows
FROM support_event;

SHOW INDEX FROM support_event;

اینجا open حدود ۸۰٪، و دو وضعیت دیگر هرکدام حدود ۱۰٪ از داده‌اند. status فقط سه مقدار متمایز دارد؛ اما یک query خاص می‌تواند انتخاب‌گر باشد یا نباشد. خروجی Cardinality در SHOW INDEX هم تخمینی است و ممکن است با آمار تازه تغییر کند.

Here, open is about 80%, while each other status is about 10%. There are only three distinct status values, but selectivity depends on the particular predicate. Cardinality in SHOW INDEX is an estimate and can change after statistics are refreshed.

انتخاب‌گری یک ویژگی ستون به‌تنهایی نیستSelectivity is not a property of a column alone

یک ستون ممکن است مقدارهای زیادی داشته باشد اما query محدوده‌ای بخواهد که بیشتر ردیف‌ها را پوشش دهد؛ یا ستون کم‌تنوعی مثل status برای شرطی که مقدار نادر می‌خواهد مفید باشد. selectivity را برای predicate واقعی و توزیع واقعی حساب کن. cardinality index فقط سرنخی برای optimizer است، نه حکم قطعی.

A column can have many distinct values while a particular range still matches most rows. Or a low-cardinality column such as status may help for a rare-value predicate. Calculate selectivity for the actual predicate and distribution. Index cardinality is an optimizer clue, not a verdict.

دو predicate روی indexهای موجودTwo predicates against the existing indexes
EXPLAIN SELECT event_id FROM support_event WHERE status='open';
EXPLAIN SELECT event_id FROM support_event WHERE status='closed';
EXPLAIN SELECT event_id FROM support_event WHERE customer_id=17;

احتمال دارد open به‌خاطر match زیاد scan شود و closed از index بهره ببرد؛ اما تعداد کل جدول و هزینهٔ تخمینی مهم‌اند. برای customer_id هم index composite با این ستون در ابتدا prefix دارد. جواب قطعی را از plan نسخهٔ خودت بخوان و با شمارش واقعی تطبیق بده.

Open may scan because it matches many rows, while closed may benefit from the index; table size and estimated cost matter. The composite index also begins with customer_id. Read your version’s plan and compare it with actual counts.

covering یعنی نیاز query داخل index جا شدهCovering means the index contains what the query needs

اگر query فقط ستون‌هایی را لازم داشته باشد که از index قابل‌خواندن‌اند، موتور شاید مجبور نباشد برای هر ورودی secondary index به clustered row برگردد. به این وضعیت covering می‌گوییم. در InnoDB کلید اصلی هم در secondary index حضور دارد، پس query زیر از customer، status، created_at و event_id استفاده می‌کند؛ این جزئیات را با metadata و plan خودت بررسی کن.

If a query needs only columns available from an index, the engine may avoid returning to the clustered row for each secondary-index entry. This is called covering. In InnoDB, the primary key is also present in secondary indexes, so the query below uses customer, status, created_at, and event_id; verify this with your metadata and plan.

query پوشیده و query نیازمند ستون اضافهA covered query and one needing an extra column
EXPLAIN SELECT event_id, created_at
FROM support_event
WHERE customer_id=17 AND status='closed';

EXPLAIN SELECT event_id, created_at, note
FROM support_event
WHERE customer_id=17 AND status='closed';

در قالب سنتی، Extra ممکن است برای query اول Using index نشان دهد؛ معنی‌اش استفاده از خود index برای پوشش ستون‌های query است، نه اینکه هر قسمت از query یا هر plan حتماً بهتر شده. query دوم به note نیاز دارد که در index نیست و ممکن است lookup به row داشته باشد. قالب TREE/JSON واژه‌ها و جزئیات دیگری دارد.

In traditional format, Extra may show Using index for the first query: the index covers the query’s columns. This does not mean every part of the query or every plan is necessarily better. The second query needs note, absent from the index, and may visit the row. TREE/JSON formats use different wording and detail.

Coverage به معنی «index همه‌چیز را حل کرد» نیست.Coverage does not mean “the index solved everything.”

ممکن است query تعداد زیادی index entry بخواند، predicate دیگری را filter کند یا sort جدا داشته باشد. covering می‌تواند مراجعه به row را کم کند، اما selectivity و plan کلی همچنان مهم‌اند.

The query may still read many index entries, filter another predicate, or perform a separate sort. Coverage can reduce row lookups, but selectivity and the full plan still matter.

برای covering، index را بی‌حساب پهن نکنDo not widen an index indiscriminately for coverage

وسوسه می‌شویم هر ستونی که query می‌خواهد به index اضافه کنیم. اما index عریض‌تر صفحه‌های بیشتری می‌خواهد، cache را پُرتر می‌کند و نوشتن را گران‌تر. گاهی این trade-off می‌ارزد، گاهی query کم‌تکرار است و هزینهٔ دائمی index از منفعتش بیشتر می‌شود. بر اساس workload تصمیم بگیر.

It is tempting to append every requested column to an index. But a wider index needs more pages, occupies more cache, and makes writes costlier. Sometimes the tradeoff is worthwhile; sometimes a rare query does not justify a permanent index cost. Decide from the workload.

یک index پوشاننده را فقط در lab بسازBuild a covering candidate only in the lab
CREATE INDEX ix_customer_status_date_amount
ON support_event(customer_id,status,created_at,amount);

SHOW INDEX FROM support_event;

EXPLAIN SELECT event_id, created_at, amount
FROM support_event
WHERE customer_id=17 AND status='closed'
ORDER BY created_at;

این index هم ترتیب filter را دارد و هم amount را اضافه می‌کند؛ event_id به‌عنوان کلید اصلی InnoDB در secondary index قابل‌دسترسی است. حالا آن را با query قبلی و هزینهٔ نگهداری مقایسه کن؛ صرف دیدن Using index به معنی پیشنهاد production نیست.

This index preserves filter order and adds amount; InnoDB’s primary key makes event_id available in the secondary index. Compare it with the previous query and its maintenance cost. Seeing Using index alone is not a production recommendation.

Cardinality را تخمین بخوان، نه شمارش قطعیRead cardinality as an estimate, not an exact count

SHOW INDEX عدد cardinality تخمینی نشان می‌دهد. برای اینکه آمار از دادهٔ تازه عقب نماند می‌توان ANALYZE TABLE اجرا کرد، اما این دستور داده را تغییر نمی‌دهد و تخمین را به حقیقت دقیق تبدیل نمی‌کند. در جدول کوچک نوسان estimate طبیعی است؛ برای همین شمارش مستقیم را کنار metadata می‌گذاریم.

SHOW INDEX reports estimated cardinality. ANALYZE TABLE can refresh statistics from current data, but it does not change table rows or make estimates exact truth. Estimates can be noisy on small tables, so we compare metadata with direct counts.

آمار را تازه کن و هر دو شاهد را بخوانRefresh statistics and inspect both forms of evidence
ANALYZE TABLE support_event;
SHOW INDEX FROM support_event;
SELECT COUNT(DISTINCT customer_id), COUNT(DISTINCT status)
FROM support_event;

آمار query optimizer را تغذیه می‌کند؛ تعداد distinct واقعی را SELECT می‌سنجد. بعد از تغییر بزرگ داده ممکن است refresh مفید باشد، اما اجرای تکراری آن درمان خودکار query کند نیست. در production زمان، هزینه و اثر عملیات را طبق مستندات و فرایند تغییر بررسی کن.

Statistics inform the optimizer; the SELECT counts actual distinct values. A refresh may help after major data changes, but rerunning it is not an automatic cure for a slow query. In production, assess timing and operational impact according to documentation and change procedures.

۱) توزیع status را بشمار / Count the status distribution

شمار هر وضعیت و نسبت آن از کل را query کن.

Query each status count and its fraction of the total.

SQL / SQL
SELECT status, COUNT(*) AS n,
 COUNT(*)/(SELECT COUNT(*) FROM support_event) AS fraction
FROM support_event GROUP BY status;

open حدود ۳۲۰ ردیف از ۴۰۰ است؛ status به‌تنهایی برای این مقدار شرط خیلی انتخاب‌گری نیست.

Open is about 320 of 400 rows, so this status predicate is not very selective.

۲) تعداد مقدارهای متمایز را جدا بگیر / Count distinct values separately

تعداد status و customer را بسنج؛ این را با selectivity یک query یکی نگیر.

Count distinct statuses and customers; do not equate this with a query’s selectivity.

SQL / SQL
SELECT COUNT(DISTINCT status) AS statuses,
 COUNT(DISTINCT customer_id) AS customers
FROM support_event;

سه status و چهل customer داریم. selectivity هر شرط از تعداد ردیف‌های واقعی matchشده هم به دست می‌آید.

There are three statuses and forty customers. Predicate selectivity also depends on actual matching row counts.

۳) دو status را با EXPLAIN مقایسه کن / Compare two statuses with EXPLAIN

برای open و closed plan بگیر و تعداد ردیف واقعی را هم query کن.

Explain open and closed and query their actual row counts.

SQL / SQL
EXPLAIN SELECT event_id FROM support_event WHERE status='open';
EXPLAIN SELECT event_id FROM support_event WHERE status='closed';
SELECT status, COUNT(*) FROM support_event GROUP BY status;

plan یک تخمین و شمارش، واقعیت فعلی fixture است. روی ۴۰۰ ردیف optimizer ممکن است برای هر دو تصمیم یکسان بگیرد.

The plan is an estimate; the count is the fixture’s current truth. On 400 rows the optimizer may choose the same path for both.

۴) Cardinality تخمینی را بخوان / Read estimated cardinality

metadata index status و customer را استخراج کن.

Inspect cardinality metadata for status and customer indexes.

SQL / SQL
SHOW INDEX FROM support_event;

Cardinality تخمین مقدارهای متمایز است، نه شمار دقیق rows و نه نسبت selectivity شرط open.

Cardinality estimates distinct values; it is not an exact row count or the selectivity of open.

۵) predicate انتخاب‌گرتر را پیدا کن / Find the more selective predicate

شمار ردیف‌های status closed و customer 17 را مقایسه کن.

Compare counts for status closed and customer 17.

SQL / SQL
SELECT COUNT(*) FROM support_event WHERE status='closed';
SELECT COUNT(*) FROM support_event WHERE customer_id=17;

هر دو نتیجه با توزیع fixture سنجیده می‌شوند؛ انتخاب‌گری property query+داده است، نه فقط تعریف datatype.

Both results depend on fixture distribution; selectivity belongs to the query and data, not merely the datatype.

۶) پوشش query را در plan بخوان / Read coverage in a plan

query فقط event_id و created_at را می‌خواهد؛ plan قالب traditional را بگیر.

The query needs only event_id and created_at; inspect traditional EXPLAIN.

SQL / SQL
EXPLAIN SELECT event_id,created_at
FROM support_event
WHERE customer_id=17 AND status='closed';

در صورت پوشش ممکن است Extra شامل Using index باشد. خروجی دقیق plan به نسخه و هزینه بستگی دارد.

If covered, Extra may contain Using index. Exact plan output depends on version and cost.

۷) یک ستون بیرون از index بخواه / Request a column outside the index

به همان query ستون note را اضافه و دو plan را مقایسه کن.

Add note to the same query and compare both plans.

SQL / SQL
EXPLAIN SELECT event_id,created_at,note
FROM support_event
WHERE customer_id=17 AND status='closed';

note در index تعریف‌شده نیست؛ برای خواندن آن ممکن است lookup به clustered row لازم شود.

Note is not in the defined index, so retrieving it may require a clustered-row lookup.

۸) row count را با selectivity ترکیب کن / Combine row count and selectivity

نسبت status closed به کل را محاسبه کن.

Calculate the fraction of all rows matching closed.

SQL / SQL
SELECT SUM(status='closed') AS matched,
 COUNT(*) AS total,
 SUM(status='closed')/COUNT(*) AS selectivity
FROM support_event;

با fixture فعلی حدود ۱۰٪ می‌شود؛ این مقدار به داده و زمان query وابسته است.

With the current fixture it is about 10%; it depends on data and time.

۹) پس از ANALYZE دوباره metadata را بخوان / Recheck metadata after ANALYZE

آمار را refresh کن و metadata را دوباره query کن؛ دقت تخمین را تضمین نکن.

Refresh statistics and inspect metadata again without claiming exact estimates.

SQL / SQL
ANALYZE TABLE support_event;
SHOW INDEX FROM support_event;

ANALYZE می‌تواند تخمین optimizer را تازه کند، نه اینکه Cardinality را تضمیناً دقیق کند.

ANALYZE can refresh optimizer estimates; it does not guarantee exact cardinality.

۱۰) query پرحجم را به index تحمیل نکن / Do not force an index for a broad query

همهٔ openها را بشمار و plan بگیر؛ FORCE INDEX استفاده نکن.

Count all open rows and explain the query without FORCE INDEX.

SQL / SQL
EXPLAIN SELECT event_id FROM support_event WHERE status='open';
SELECT COUNT(*) FROM support_event WHERE status='open';

وقتی بیشتر جدول لازم است، scan می‌تواند منطقی باشد. هدف استفادهٔ اجباری از index نیست.

When most of the table is needed, a scan can be reasonable. Forcing index use is not the goal.

۱۱) یک candidate پوشاننده بساز / Build a covering candidate

index ترکیبی شامل amount را در fixture بساز و plan query سه‌ستونی را بخوان.

Create a composite candidate including amount and inspect a three-column query.

SQL / SQL
CREATE INDEX ix_customer_status_date_amount
ON support_event(customer_id,status,created_at,amount);
EXPLAIN SELECT event_id,created_at,amount
FROM support_event WHERE customer_id=17 AND status='closed';

index باید فقط یک بار ساخته شود. اگر از قبل وجود دارد، SHOW INDEX را اجرا کن؛ coverage مزیت ممکن است، نه مجوز نگهداری بی‌دلیل.

Create it only once. If it exists, inspect SHOW INDEX; coverage is a possible benefit, not a reason to keep it without justification.

۱۲) هزینهٔ index پهن را ثبت کن / Record the cost of a wider index

تعریف index قبل/بعد را بخوان و تعداد کل indexهای جدول را گزارش کن.

Inspect definitions and report the number of indexes.

SQL / SQL
SHOW INDEX FROM support_event;

metadata نشان می‌دهد چه ساختارهایی باید نگهداری شوند؛ bytes، cache footprint و write latency را از این خروجی به دست نمی‌آوری.

Metadata shows maintained structures; it does not provide bytes, cache footprint, or write latency.

۱۳) query با coverage و بدون coverage / Compare covered and uncovered projections

دو projection متفاوت برای همان شرط بساز؛ خروجی plan هر دو را ذخیره کن.

Create two projections for the same predicate and save both plans.

SQL / SQL
EXPLAIN SELECT event_id,created_at,amount FROM support_event
WHERE customer_id=17 AND status='closed';
EXPLAIN SELECT event_id,created_at,note FROM support_event
WHERE customer_id=17 AND status='closed';

amount در candidate اضافه‌شده هست، note نیست. از Extra یا TREE evidence بگیر؛ در نتیجهٔ واقعی rowها را هم مقایسه کن.

Amount is in the added candidate; note is not. Inspect Extra or TREE evidence and compare actual returned rows too.

۱۴) شرط ترکیبی را اندازه بگیر / Measure a combined predicate

نسبت customer 17 و status closed را از کل محاسبه کن.

Calculate the fraction matching customer 17 and closed.

SQL / SQL
SELECT COUNT(*) AS matched,
 COUNT(*)/(SELECT COUNT(*) FROM support_event) AS fraction
FROM support_event
WHERE customer_id=17 AND status='closed';

این query selectivity شرط ترکیبی را می‌سنجد، نه فقط مقدارهای distinct هر ستون را.

This measures combined-predicate selectivity, not merely each column’s distinct count.

۱۵) order_id از کجا در secondary index می‌آید؟ / Where does order_id come from?

ساختار را بخوان و توضیح را با query covering اجراشدنی پشتیبانی کن.

Inspect the structure and support the explanation with an executable covering query.

SQL / SQL
SHOW CREATE TABLE support_event;
EXPLAIN SELECT event_id,created_at FROM support_event
WHERE customer_id=17 AND status='closed';

InnoDB secondary index کلید اصلی را هم نگه می‌دارد؛ با این حال جزئیات plan را نسخه‌محور بخوان و از SHOW CREATE TABLE برای شناخت schema استفاده کن.

InnoDB secondary indexes also carry the primary key. Still read plan details by version and use SHOW CREATE TABLE to verify the schema.

۱۶) کدام شاخص نادرست تفسیر شده؟ / Which metric is misread?

Cardinality status را کنار count واقعی closed بگذار و یک query برای هر دو شاهد بنویس.

Compare status cardinality with actual closed count using SQL for both.

SQL / SQL
SHOW INDEX FROM support_event WHERE Key_name='ix_status';
SELECT status,COUNT(*) FROM support_event GROUP BY status;

Cardinality تخمین distinct values است؛ COUNT ردیف‌های واقعی هر مقدار را می‌دهد. این دو را با هم اشتباه نکن.

Cardinality estimates distinct values; COUNT returns actual rows per value. They are not interchangeable.

۱۷) scan را با پوشش اشتباه نگیر / Do not confuse a scan with coverage

query تمام ستون‌ها و query فقط index columns را explain کن؛ سؤال کن آیا پوشش جلوی خواندن تعداد زیادی entry را می‌گیرد.

Explain a full-row query and an index-column-only query; ask whether coverage avoids scanning many entries.

SQL / SQL
EXPLAIN SELECT * FROM support_event WHERE status='open';
EXPLAIN SELECT status FROM support_event WHERE status='open';

دومی ممکن است index-only باشد، اما هنوز تعداد زیادی entry را می‌خواند. covering الزاماً selectivity را بهتر نمی‌کند.

The second may be index-only, but can still read many entries. Coverage does not necessarily improve selectivity.

۱۸) تصمیم را با سه مدرک جمع کن / Conclude with three kinds of evidence

برای query مشتری/status، توزیع داده، index metadata و plan را با SQL جمع کن.

For a customer/status query, collect data distribution, index metadata, and plan in SQL.

SQL / SQL
SELECT customer_id,status,COUNT(*) AS n
FROM support_event GROUP BY customer_id,status;
SHOW INDEX FROM support_event;
EXPLAIN SELECT event_id,created_at,amount FROM support_event
WHERE customer_id=17 AND status='closed';

این سه شاهد توزیع، تعریف و انتخاب plan را جدا می‌کنند؛ ادعای latency هنوز به benchmark نماینده نیاز دارد.

These separate distribution, definition, and plan choice; a latency claim still needs a representative benchmark.

آزمایش پایانی: index پهن‌تر واقعاً می‌ارزد؟Closing lab: is the wider index worth it?

یک endpoint فقط شناسه و تاریخ می‌خواهد؛ endpoint دوم علاوه بر آن مبلغ را نشان می‌دهد. سه query را با index پایه و candidate پوشاننده مقایسه کن. قرار نیست یک خروجی ثابت از EXPLAIN حفظ کنی؛ باید نشان بدهی چه ستون‌هایی پوشش دارند، چه تعداد ردیف match می‌شود و index اضافه چه هزینهٔ ساختاری ایجاد می‌کند.

One endpoint needs only ID and date; another also displays the amount. Compare three queries against the base and covering candidate. Do not memorize a fixed EXPLAIN output; demonstrate which columns are covered, how many rows match, and what structural cost the added index creates.

  1. فراوانی status و customer را query کن.
  2. Query status and customer distributions.
  3. هر دو projection را با EXPLAIN و نتیجهٔ واقعی اجرا کن.
  4. Run both projections with EXPLAIN and actual results.
  5. index candidate را یک بار بساز؛ metadata را ثبت کن.
  6. Create the candidate once and record metadata.
  7. مزیت پوشش احتمالی را در برابر هزینهٔ storage/write گزارش کن؛ سرعت را بدون benchmark ادعا نکن.
  8. Report possible coverage benefits against storage/write costs; do not claim speed without a benchmark.
