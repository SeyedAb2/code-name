Selectivity و covering index

Selectivity and Covering Indexes

دو index برای query در دسترس‌اند. یکی روی ستون پرتکرار، یکی روی کلید دقیق‌تر. آیا هرچه مقدارها متنوع‌تر باشند index بهتر است؟ و اگه index پاسخ query رو کامل داشته باشه چه کاری حذف می‌شه؟ با یک dataset تکرارپذیر هم توزیع رو می‌سنجیم، هم پوشش رو از روی plan می‌خونیم.

Two indexes are available for a query: one on a frequently repeated column and one on a more discriminating key. Does more distinctness always mean a better index? And what work can be avoided when an index contains everything the query needs? We will inspect both distribution and coverage with a reproducible dataset.

پیش‌نیازPrerequisite: فصل ۱۳ · composite indexمحیط مرجعReference environment: MySQL 9.7 · InnoDBزمانTime: ۹۰ دقیقه · ۱۸ تمرین

index انتخاب شده، ولی کار زیادی باقی ماندهThe index is chosen, but much work remains

یک query روی status='open' index دارد، اما بیشتر جدول رو برمی‌گرداند. query دیگری فقط چند ردیف رو پیدا می‌کنه، ولی برای هرکدام به data row برمی‌گردد تا دو ستون دیگر رو بخواند. پس دو سؤال جدا داریم: «شرط چقدر انتخاب‌گر است؟» و «آیا خود index همهٔ دادهٔ لازم رو دارد؟»

A query on status='open' has an index but returns most of the table. Another query finds only a few rows, yet visits each data row to fetch two more columns. These are separate questions: “How selective is the predicate?” and “Does the index itself contain everything the query needs?”

Selectivity رو به زبان ساده می‌توان سهم ردیف‌هایی دانست که شرط نگه می‌دارد؛ مقدار کمتر معمولاً ردیف‌های کمتری باقی می‌ذاره. Cardinality در metadata تخمینی از تعداد مقدارهای متمایز index هست و همان selectivity نهایی query نیست. بعد از آن هم باید ببینیم query ستون‌های خارج از index لازم دارد یا نه.

In simple terms, selectivity is the fraction of rows retained by a predicate; a smaller fraction usually leaves fewer rows. Cardinality in metadata estimates distinct index values and is not the query’s final selectivity. Then we must ask whether the query needs columns outside the index.

fixture چهارصد ردیفی بسازBuild a 400-row fixture
CREATE DATABASE IF NOT EXISTS codenames_selectivity_lab;
USE codenames_selectivity_lab;
DROP TABLE IF EXISTS support_event;

CREATE TABLE support_event (
  event_id BIGINT NOT NULL,
  customer_id INT NOT NULL,
  status VARCHAR(10) NOT NULL,
  created_at DATETIME NOT NULL,
  amount DECIMAL(8,2) NOT NULL,
  note VARCHAR(40) NOT NULL,
  PRIMARY KEY(event_id),
  KEY ix_status(status),
  KEY ix_customer_status_date(customer_id,status,created_at)
) ENGINE=InnoDB;

INSERT INTO support_event
WITH RECURSIVE seq(n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM seq WHERE n < 400
)
SELECT
  n,
  MOD(n,40)+1,
  CASE MOD(n,10)
    WHEN 0 THEN 'closed'
    WHEN 1 THEN 'waiting'
    ELSE 'open'
  END,
  TIMESTAMP('2026-01-01 00:00:00') + INTERVAL n HOUR,
  MOD(n * 17, 5000) / 100,
  CONCAT('event-', n)
FROM seq;

SELECT COUNT(*) AS total_rows FROM support_event;

CTE بازگشتی اعداد ۱ تا ۴۰۰ رو برای fixture می‌سازد؛ اگه نسخه یا محیطت این syntax رو محدود کرده، fixture رو با روش seed مورد تأیید محیط بساز، اما همان توزیع status رو حفظ کن. این داده ساختگی هست و برای سنجش latency واقعی نیست.

The recursive CTE generates values 1 through 400. If your version or environment restricts this syntax, seed an equivalent fixture using an approved method while preserving the status distribution. This is synthetic data, not a real latency benchmark.

قبل از نگاه به index، توزیع رو query کنQuery the distribution before inspecting indexes

به‌جای حدس از روی اسم ستون، تعداد کل و سهم هر مقدار رو حساب کن. در fixture ما بیشتر رویدادها open هستن، پس شرط open انتخاب‌گر نیست؛ status='closed' ردیف‌های بسیار کمتری نگه می‌دارد.

Rather than guessing from a column name, count total rows and each value’s share. Most fixture events are open, so that predicate is not selective; status='closed' retains far fewer rows.

شمارش و نسبت واقعی روی همین دادهCounts and actual fractions for this dataset
SELECT status, COUNT(*) AS rows_kept,
       COUNT(*) / (SELECT COUNT(*) FROM support_event) AS fraction
FROM support_event
GROUP BY status
ORDER BY rows_kept DESC;

SELECT COUNT(DISTINCT status) AS distinct_status,
       COUNT(*) AS total_rows
FROM support_event;

SHOW INDEX FROM support_event;

اینجا open حدود ۸۰٪، و دو وضعیت دیگر هرکدام حدود ۱۰٪ از داده‌اند. status فقط سه مقدار متمایز دارد؛ اما یک query خاص می‌تونه انتخاب‌گر باشه یا نباشه. خروجی Cardinality در SHOW INDEX هم تخمینی هست و ممکنه با آمار تازه تغییر کند.

Here, open is about 80%, while each other status is about 10%. There are only three distinct status values, but selectivity depends on the particular predicate. Cardinality in SHOW INDEX is an estimate and can change after statistics are refreshed.

انتخاب‌گری یک ویژگی ستون به‌تنهایی نیستSelectivity is not a property of a column alone

یک ستون ممکنه مقدارهای زیادی داشته باشه اما query محدوده‌ای بخواهد که بیشتر ردیف‌ها رو پوشش دهد؛ یا ستون کم‌تنوعی مثل status برای شرطی که مقدار نادر می‌خواهد مفید باشه. selectivity رو برای predicate واقعی و توزیع واقعی حساب کن. cardinality index فقط سرنخی برای optimizer است، نه حکم قطعی.

A column can have many distinct values while a particular range still matches most rows. Or a low-cardinality column such as status may help for a rare-value predicate. Calculate selectivity for the actual predicate and distribution. Index cardinality is an optimizer clue, not a verdict.

دو predicate روی indexهای موجودTwo predicates against the existing indexes
EXPLAIN SELECT event_id FROM support_event WHERE status='open';
EXPLAIN SELECT event_id FROM support_event WHERE status='closed';
EXPLAIN SELECT event_id FROM support_event WHERE customer_id=17;

احتمال دارد open به‌خاطر match زیاد scan شود و closed از index بهره ببرد؛ اما تعداد کل جدول و هزینهٔ تخمینی مهم‌اند. برای customer_id هم index composite با این ستون در ابتدا prefix دارد. جواب قطعی رو از plan نسخهٔ خودت بخوان و با شمارش واقعی تطبیق بده.

Open may scan because it matches many rows, while closed may benefit from the index; table size and estimated cost matter. The composite index also begins with customer_id. Read your version’s plan and compare it with actual counts.

covering یعنی نیاز query داخل index جا شدهCovering means the index contains what the query needs

اگه query فقط ستون‌هایی رو لازم داشته باشه که از index قابل‌خواندن‌اند، موتور شاید مجبور نباشه برای هر ورودی secondary index به clustered row برگردد. به این وضعیت covering می‌گیم. در InnoDB کلید اصلی هم در secondary index حضور دارد، پس query زیر از customer، status، created_at و event_id استفاده می‌کنه؛ این جزئیات رو با metadata و plan خودت بررسی کن.

If a query needs only columns available from an index, the engine may avoid returning to the clustered row for each secondary-index entry. This is called covering. In InnoDB, the primary key is also present in secondary indexes, so the query below uses customer, status, created_at, and event_id; verify this with your metadata and plan.

query پوشیده و query نیازمند ستون اضافهA covered query and one needing an extra column
EXPLAIN SELECT event_id, created_at
FROM support_event
WHERE customer_id=17 AND status='closed';

EXPLAIN SELECT event_id, created_at, note
FROM support_event
WHERE customer_id=17 AND status='closed';

در قالب سنتی، Extra ممکنه برای query اول Using index نشان دهد؛ معنی‌اش استفاده از خود index برای پوشش ستون‌های query است، نه اینکه هر قسمت از query یا هر plan حتماً بهتر شده. query دوم به note نیاز دارد که در index نیست و ممکنه lookup به row داشته باشه. قالب TREE/JSON واژه‌ها و جزئیات دیگری دارد.

In traditional format, Extra may show Using index for the first query: the index covers the query’s columns. This does not mean every part of the query or every plan is necessarily better. The second query needs note, absent from the index, and may visit the row. TREE/JSON formats use different wording and detail.

Coverage به معنی «index همه‌چیز رو حل کرد» نیست.Coverage does not mean “the index solved everything.”

ممکنه query تعداد زیادی index entry بخواند، predicate دیگری رو filter کند یا sort جدا داشته باشه. covering می‌تونه مراجعه به row رو کم کند، اما selectivity و plan کلی همچنان مهم‌اند.

The query may still read many index entries, filter another predicate, or perform a separate sort. Coverage can reduce row lookups, but selectivity and the full plan still matter.

برای covering، index رو بی‌حساب پهن نکنDo not widen an index indiscriminately for coverage

وسوسه می‌شویم هر ستونی که query می‌خواهد به index اضافه کنیم. اما index عریض‌تر صفحه‌های بیشتری می‌خواهد، cache رو پُرتر می‌کنه و نوشتن رو گران‌تر. گاهی این trade-off می‌ارزد، گاهی query کم‌تکرار هست و هزینهٔ دائمی index از منفعتش بیشتر می‌شه. بر اساس workload تصمیم بگیر.

It is tempting to append every requested column to an index. But a wider index needs more pages, occupies more cache, and makes writes costlier. Sometimes the tradeoff is worthwhile; sometimes a rare query does not justify a permanent index cost. Decide from the workload.

یک index پوشاننده رو فقط در lab بسازBuild a covering candidate only in the lab
CREATE INDEX ix_customer_status_date_amount
ON support_event(customer_id,status,created_at,amount);

SHOW INDEX FROM support_event;

EXPLAIN SELECT event_id, created_at, amount
FROM support_event
WHERE customer_id=17 AND status='closed'
ORDER BY created_at;

این index هم ترتیب filter رو دارد و هم amount رو اضافه می‌کنه؛ event_id به‌عنوان کلید اصلی InnoDB در secondary index قابل‌دسترسی هست. حالا آن رو با query قبلی و هزینهٔ نگهداری مقایسه کن؛ صرف دیدن Using index به معنی پیشنهاد production نیست.

This index preserves filter order and adds amount; InnoDB’s primary key makes event_id available in the secondary index. Compare it with the previous query and its maintenance cost. Seeing Using index alone is not a production recommendation.

Cardinality رو تخمین بخوان، نه شمارش قطعیRead cardinality as an estimate, not an exact count

SHOW INDEX عدد cardinality تخمینی نشان می‌ده. برای اینکه آمار از دادهٔ تازه عقب نماند می‌توان ANALYZE TABLE اجرا کرد، اما این دستور داده رو تغییر نمی‌ده و تخمین رو به حقیقت دقیق تبدیل نمی‌کنه. در جدول کوچک نوسان estimate طبیعی است؛ برای همین شمارش مستقیم رو کنار metadata می‌ذاریم.

SHOW INDEX reports estimated cardinality. ANALYZE TABLE can refresh statistics from current data, but it does not change table rows or make estimates exact truth. Estimates can be noisy on small tables, so we compare metadata with direct counts.

آمار رو تازه کن و هر دو شاهد رو بخوانRefresh statistics and inspect both forms of evidence
ANALYZE TABLE support_event;
SHOW INDEX FROM support_event;
SELECT COUNT(DISTINCT customer_id), COUNT(DISTINCT status)
FROM support_event;

آمار query optimizer رو تغذیه می‌کنه؛ تعداد distinct واقعی رو SELECT می‌سنجد. بعد از تغییر بزرگ داده ممکنه refresh مفید باشه، اما اجرای تکراری آن درمان خودکار query کند نیست. در production زمان، هزینه و اثر عملیات رو طبق مستندات و فرایند تغییر بررسی کن.

Statistics inform the optimizer; the SELECT counts actual distinct values. A refresh may help after major data changes, but rerunning it is not an automatic cure for a slow query. In production, assess timing and operational impact according to documentation and change procedures.
