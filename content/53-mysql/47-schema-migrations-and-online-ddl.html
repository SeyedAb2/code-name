می‌خوایم یک ستون اضافه کنیم؛ آیا ALTER حتماً بی‌وقفه است؟

We need a new column. Is ALTER guaranteed to be nonblocking?

تغییر schema روی سیستم زنده فقط یک دستور SQL نیست. نسخهٔ قدیمی اپ ممکنه هنوز در حال نوشتن باشه، migration برای metadata lock منتظر بماند یا عملیات index فضای موقت زیادی بخواهد. اصطلاح online DDL تضمین «هیچ lock و هیچ قطعی» نیست. تغییر رو روی جدول تمرینی می‌سنجیم و rollout برنامه رو سازگار نگه می‌داریم.

A live schema change is more than one SQL statement. An older app version may still write, a migration may wait for a metadata lock, or index creation may need substantial temporary space. “Online DDL” does not guarantee no locks or interruption. We will measure on a lab table and keep application rollout compatible.

تغییر کوچک schema، چند نسخهٔ فعال اپA small schema change, multiple app versions

می‌خوایم customer_code رو اضافه کنیم. اگه ابتدا ستون رو NOT NULL کنیم، اپ قدیمی که این ستون رو نمی‌شناسد شاید insertهایش رو خراب کند. migration امن معمولاً مرحله‌ای هست: ستون سازگار رو اضافه کن، اپ رو به نسخهٔ جدید ببَر، دادهٔ قدیمی رو با batch پر کن، صحت رو بسنج و فقط وقتی همهٔ writerها آماده‌اند constraint نهایی رو فعال کن.

We want to add customer_code. If it is immediately NOT NULL, an older app that does not know the column may fail its inserts. A safer migration is staged: add a compatible column, deploy the new app, backfill old rows in batches, verify, and enforce the final constraint only after all writers are compatible.

برنامه و schema باید در تمام مرحله‌ها با هم سازگار بمانند.

Application and schema must remain compatible at every stage.

ALGORITHM و LOCK رو حدس نزنDo not guess ALGORITHM or LOCK

InnoDB برای بعضی تغییرها الگوریتم instant یا inplace دارد و برای بعضی نیاز به copy. قابلیت دقیق به نوع ALTER، نسخه و engine بستگی دارد. می‌تونی ALGORITHM و LOCK رو صریح تعیین کنی تا درخواست ناسازگار fail شود، اما نام clause تضمین نمی‌کنه عملیات بی‌وقفه باشه. در مستند همان دستور و جدول قابلیت‌ها رو بررسی کن.

InnoDB supports instant or in-place algorithms for some changes and requires a copy for others. Exact support depends on ALTER operation, version, and engine. Explicit ALGORITHM and LOCK can make an unsupported request fail, but clause names do not guarantee a zero-interruption operation. Check the capability table for the exact statement.

ALTER TABLE codenames_lab.customers
  ADD COLUMN customer_code VARCHAR(32) NULL,
  ALGORITHM=INSTANT;

INSTANT رو فقط وقتی مستند مقصد همین تغییر و همین نسخه رو تأیید کرده استفاده کن؛ اگه پشتیبانی نشود، خطا بهتر از fallback ناخواسته هست.

Use INSTANT only when the target version documents support for this exact operation; an error is safer than an unexpected fallback.

Online DDL هم metadata lock می‌گیرهOnline DDL still needs metadata locks

تراکنش طولانی می‌تونه metadata lock رو نگه داره. ALTER منتظر می‌مونه؛ درخواست‌های بعدی هم ممکنه پشت درخواست DDL صف بکشند. قبل از migration، transactionهای باز رو بررسی کن؛ در زمان اجرا SHOW FULL PROCESSLIST و Performance Schema رو ببین و برای مدت انتظار، فضای disk و توقف عملیات حد داشته باش.

A long transaction can hold a metadata lock. ALTER waits, and later requests may queue behind the pending DDL. Inspect open transactions before migration; during execution use SHOW FULL PROCESSLIST and Performance Schema, and bound wait time, disk use, and operational impact.

FROM performance_schema.metadata_locks
WHERE OBJECT_SCHEMA = 'codenames_lab';

Verify Performance Schema access and columns for the installed version. Reproduce waits in a lab session; do not deliberately lock production.

migration رو با اپ هم‌زمان deploy کنCoordinate migrations with application rollout

migration فایل versioned و یک‌باره است؛ اجرای دوباره باید به کمک migration history تشخیص داده شود، نه اینکه از روی حدس دوباره ALTER شود. DDLهای MySQL معمولاً implicit commit دارن؛ پس transaction اپ wrapper تضمین rollback schema نیست. طرح retry و rollback باید مشخص کند کدام مرحله reversible هست و کدام نیازمند forward-fix یا restore هست.

A migration is versioned and applied once; migration history, not guesswork, should prevent accidental reapplication. MySQL DDL commonly causes implicit commits, so wrapping it in an app transaction does not guarantee schema rollback. Define which steps are reversible and which require a forward fix or restore.

DDL روی جدول بزرگ یعنی عملیات productionDDL on a large table is a production operation

ALTER TABLE روی جدول کوچیک آزمایشگاهی شاید در یک لحظه تمام شه، ولی روی جدول بزرگ می‌تونه lock، copy یا فشار I/O بسازه. قبل از اجرا size، version، الگوریتم پشتیبانی‌شده و window تغییر رو مشخص کن.

An ALTER TABLE that is instant in a toy database can become an operational event on a large table. Record table size, version, supported algorithm, and change window before execution.

واژهٔ online به معنی «بدون هیچ اثری» نیست. metadata lock و phaseهای کوتاه blocking هنوز می‌تونن مهم باشن.

“Online” does not mean “zero impact”; metadata locks and brief blocking phases can still matter.
