قرار بود دیشب پاک‌سازی اجرا بشه؛ از کجا بفهمیم واقعاً شد؟

A cleanup was scheduled for last night. How do we know it ran?

فصل قبل Trigger رو دیدیم: تغییر ردیف، اجرای فوری. اما پاک‌سازی شبانه به یک ردیف مشخص وابسته نیست. Event Scheduler می‌تونه SQL رو در زمان تعیین‌شده اجرا کند؛ بااین‌حال وجود تعریف Event به معنی اجرای موفق نیست. وضعیت Scheduler، زمان، مجوز definer و مدرک نتیجه رو جدا بررسی می‌کنیم.

The previous chapter used a trigger: a row change causes immediate work. A nightly cleanup is not tied to one row. MySQL’s Event Scheduler can run SQL at a specified time, but a definition is not proof of successful execution. We will inspect scheduler state, timing, definer privileges, and evidence separately.

کار دستی دوباره جا ماندThe manual job was missed again

تیم هر شب نشست‌های منقضی رو پاک می‌کنه؛ اما هر بار باید کسی وارد سرور شود. پیش از انتخاب ابزار بپرس: کار باید در واکنش به تغییر یک ردیف انجام بشه یا در ساعت مشخص؟ Trigger برای اولی است؛ Event برای دومی. اگه کار به ایمیل، سرویس بیرونی یا retry پیچیده نیاز دارد، Event به‌تنهایی کافی نیست.

The team removes expired sessions nightly, but someone must connect and run the command. First ask: should work respond to a row change, or happen at a particular time? A trigger fits the first; an Event fits the second. If the job needs email, external services, or complex retries, an Event alone is not enough.

Event Scheduler جایگزین زمان‌بند سیستم‌عامل برای هر نوع کار بیرونی نیست؛ کارش اجرای SQL زمان‌بندی‌شده روی سرور MySQL هست.

The Event Scheduler is not a general replacement for an operating-system scheduler; it runs scheduled SQL on the MySQL server.

اول ببین Scheduler فعال هستFirst check whether the scheduler is running

Event حتی اگه درست تعریف شده باشه، با Scheduler خاموش اجرا نمی‌شه. مقدار واقعی رو بخوان؛ default مستندشده جای مشاهدهٔ سرور خودت رو نمی‌گیره.

A correctly defined Event will not run while the scheduler is off. Read the actual value; a documented default is not a substitute for inspecting your server.

متغیر و thread رو بررسی کنInspect the variable and scheduler thread
SHOW GLOBAL VARIABLES LIKE 'event_scheduler';
SHOW FULL PROCESSLIST;

در MySQL 9.7 مقدار پیش‌فرض مستندشده ON است، اما نسخه، تنظیم startup یا سرویس مدیریت‌شده می‌تونه متفاوت باشه. وقتی ON است، thread زمان‌بند در PROCESSLIST دیده می‌شه؛ دیدنش نیاز به PROCESS دارد. فعال‌سازی با SET GLOBAL event_scheduler=ON هم مجوز تغییر متغیر global می‌خواهد و ممکنه در سرویس مدیریت‌شده مجاز نباشه. اگه مقدار DISABLED است، تنظیم startup/provider رو پیگیری کن؛ مجوز رو دور نزن.

MySQL 9.7 documents ON as the default, but version, startup configuration, or a managed service may differ. When ON, the scheduler thread appears in PROCESSLIST; viewing it requires PROCESS. Enabling it with SET GLOBAL event_scheduler=ON requires authority to change a global variable and may be prohibited by a provider. If it is DISABLED, use the startup/provider configuration rather than bypassing permissions.

ساخت، تغییر و حذف Event به privilege به‌نام EVENT در schema نیاز دارد. هنگام اجرا، بدنه با privilege حساب definer اجرا می‌شه؛ پس مجوز ساخت Event تضمین نمی‌کنه که آن حساب بتواند جدول مقصد رو بنویسد.

Creating, altering, and dropping Events requires the schema-level EVENT privilege. At execution, the body uses the definer’s privileges; permission to create an Event does not prove that account can write to the target table.

برای اجرای واقعی مدرک بسازCreate evidence of a real execution

خروجی SELECT داخل Event به ترمینال session تو برنمی‌گردد. Event در connection جدا اجرا می‌شه؛ متغیر sessionای که در mysql CLI ساخته‌ای هم به آن منتقل نمی‌شه. نتیجه رو در جدول ثبت می‌کنیم تا بعداً قابل‌خواندن باشه.

A SELECT inside an Event does not return output to your terminal session. The Event runs in a separate connection; a session variable from your mysql CLI is not carried over. We will persist a row so the result can be inspected later.

جدول ثبت و Event یک‌باره رو بسازCreate a run log and one-time Event
USE codenames_deadlock_lab;
CREATE TABLE IF NOT EXISTS event_run_log (
  run_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  event_name VARCHAR(64) NOT NULL,
  ran_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  effective_account VARCHAR(288) NOT NULL
) ENGINE=InnoDB;

DROP EVENT IF EXISTS lab_event_once;
CREATE EVENT lab_event_once
  ON SCHEDULE AT CURRENT_TIMESTAMP + INTERVAL 10 SECOND
  ON COMPLETION PRESERVE
  COMMENT 'One-time scheduler lab'
  DO INSERT INTO event_run_log(event_name,effective_account)
     VALUES ('lab_event_once',CURRENT_USER());

موعد با timezone session زمان ساخت تفسیر می‌شه. PRESERVE تعریف رو بعد از موعد نگه می‌دارد تا metadata رو بخوانیم؛ این به معنی اجرای دوباره نیست. پیش از اجرا باید EVENT privilege رو داشته باشی و حساب definer باید اجازهٔ INSERT در جدول داشته باشه.

The due time is interpreted using the creating session’s time zone. PRESERVE keeps the definition after its schedule completes so we can inspect metadata; it does not make the Event run again. The creator needs EVENT privilege, and the definer needs INSERT on the log table.

تعریف، وضعیت و نتیجه رو کنار هم بخوانInspect definition, status, and result together
SHOW EVENTS FROM codenames_deadlock_lab LIKE 'lab_event_once';
SELECT EVENT_NAME,STATUS,LAST_EXECUTED,DEFINER,TIME_ZONE
FROM information_schema.EVENTS
WHERE EVENT_SCHEMA='codenames_deadlock_lab'
  AND EVENT_NAME='lab_event_once';
SELECT event_name,ran_at,effective_account
FROM codenames_deadlock_lab.event_run_log
WHERE event_name='lab_event_once';

پیش از موعد انتظار داریم log خالی باشه؛ بعد از موعد باید LAST_EXECUTED و ردیف ثبت رو ببینیم. اگه موعد گذشت و log خالی بود، Scheduler، Status، timezone و privilege definer رو بررسی کن. ردیف metadata فقط تعریف رو ثابت می‌کنه، نه موفقیت بدنه رو.

Before the due time, an empty log is expected; afterward, inspect LAST_EXECUTED and the run row. If the time passed but the log is empty, check scheduler state, Event status, time zone, and definer privileges. A metadata row proves a definition exists, not that its body succeeded.

کار تکراری رو تا جای ممکن idempotent طراحی کن؛ اجرای دوباره نباید داده رو خراب کند. Event تضمین کسب‌وکاریِ «دقیقاً یک‌بار در همه‌جا» برای اثر بیرونی نمی‌ده. اگه retry، صف کار یا پایش جدی لازم داری، worker بیرونی ممکنه انتخاب مناسب‌تری باشه.

Make recurring work idempotent where practical so a repeated run does not corrupt data. An Event does not provide a business-level “exactly once everywhere” guarantee for external effects. If you need retries, queues, or rich monitoring, an external worker may fit better.
