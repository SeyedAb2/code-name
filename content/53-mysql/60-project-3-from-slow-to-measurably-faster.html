Project 3 — MySQL recovery and replication

یک DELETE اشتباه اجرا شده و replica هم آن رو گرفته. backup شب قبل سالم است؛ مأموریت، بازیابی قابل‌اثبات و handoff عملیاتی هست.

A mistaken DELETE ran and reached the replica too. Last night's backup is intact; your mission is a provable recovery and operational handoff.

ماموریتMission

روی محیط disposable، backup پایه و binlog رو برای بازیابی نقطه‌ای به کار ببر، replication رو با GTID/status پایش کن و RPO/RTO و مسیر بازگشت رو بنویس. هرگز تنها دیتابیس واقعی رو برای تمرین overwrite نکن.

In a disposable environment, use a base backup and binary logs for point-in-time recovery, monitor replication with GTIDs/status, and document RPO/RTO and rollback. Never overwrite the only real database for practice.

دادهٔ تمرین رو خودت بساز و فایل راه‌اندازی رو طوری تحویل بده که نفر دیگری بتواند از صفر آن رو اجرا کند. secret واقعی رو در Git یا فایل SQL قرار نده.

Create your own test data and provide setup files another engineer can run from scratch. Never commit real secrets to Git or SQL files.

  • README دوزبانه یا دست‌کم روشن با نسخهٔ server، پیش‌نیاز و دستور اجرا / README with server release, prerequisites, and run commands
  • SQL setup، seed، queryها و اسکریپت verify / SQL setup, seed, queries, and verification script
  • خروجی واقعی commandها و توضیح محدودیت‌ها / Real command output and documented limitations
  • دادهٔ disposable، بدون credential واقعی / Disposable data; no real credentials

امتیاز فقط برای «اجرا شد» نیست؛ correctness، مسیر شکست، امنیت و قابلیت تکرار هم بررسی می‌شوند.

“It ran” is not enough: correctness, failure handling, security, and reproducibility are also reviewed.

گام‌های پروژهProject milestones

1) طرح رخداد1) Incident plan

زمان حادثه، آخرین backup سالم، binlogهای موجود و توقف مجاز رو مشخص کن.

Define incident time, last good backup, available binary logs, and acceptable stop point.

SHOW BINARY LOGS;

مدرک قبولی: جدول زمانی و gapهای نامعلوم رو ثبت کن.

Proof: Record a timeline and unknown gaps.

راهنماییHint

زمان‌ها و timezone رو با منبع داده مشخص کن.

Record timestamps and time zones together with their source.

2) هدف restore2) Restore target

مقصد جدا با نسخهٔ سازگار و فضای کافی بساز؛ هویت مقصد رو verify کن.

Create a separate target with a compatible release and sufficient space; verify its identity.

SELECT @@hostname, @@server_uuid, VERSION();

مدرک قبولی: هیچ دستور restore به endpoint production اشاره نکند.

Proof: No restore command may target production.

راهنماییHint

از hostname و UUID استفاده کن، نه اعتماد به prompt.

Use hostname and server UUID as evidence instead of trusting the shell prompt.

3) بازیابی پایه3) Base restore

آخرین backup رو restore و رکوردهای سالم پیش از incident رو بررسی کن.

Restore the latest backup and validate records known to predate the incident.

-- restore to isolated target; run validation SELECTs

مدرک قبولی: نسخهٔ backup و coordinateهای binlog رو ثبت کن.

Proof: Record backup ID and binary-log coordinates.

راهنماییHint

backup رو قبل از replay دستکاری نکن.

Keep the base backup immutable before replay.

4) بررسی binlog4) Inspect logs

event اشتباه رو در فایل‌های محدود پیدا و مرز stop امن رو تعیین کن.

Find the bad event in bounded logs and determine a safe stop boundary.

mysqlbinlog --start-position=... --stop-position=... mysql-bin.000123 > review.sql

مدرک قبولی: فایل SQL رو قبل از اعمال inspect کن.

Proof: Inspect generated SQL before applying it.

راهنماییHint

موقعیت‌ها نمونه‌اند؛ از شواهد واقعی استفاده کن.

Example positions are placeholders; use real recovery evidence.

5) Replay5) Replay

تغییرهای معتبر رو فقط تا قبل از DELETE اشتباه روی مقصد اعمال کن.

Replay valid changes only up to just before the accidental DELETE on the target.

mysqlbinlog --stop-position=... mysql-bin.000123 | mysql --host=restore-lab ...

مدرک قبولی: دستور نهایی باید مقصد lab رو واضح کند.

Proof: Make the lab target explicit in the command.

راهنماییHint

ابتدا تمرین، سپس change plan برای production.

Rehearse first, then write a production change plan.

6) اعتبار داده6) Data validation

رکورد سالم بعد backup حاضر و حذف اشتباه هنوز اعمال‌نشده رو prove کن.

Prove a valid post-backup row exists and the bad deletion was not replayed.

SELECT ...; -- compare expected IDs and totals

مدرک قبولی: خروجی مستقل و query validation رو ذخیره کن.

Proof: Save independent output and validation SQL.

راهنماییHint

فقط exit code ابزار کافی نیست.

A successful tool exit code alone is not enough evidence.

7) Replication evidence7) Replication

در توپولوژی آزمایشگاه وضعیت receiver/applier و GTID progress رو ثبت کن.

In the lab topology, capture receiver/applier state and GTID progress.

SHOW REPLICA STATUS\\G; SELECT @@GLOBAL.gtid_executed;

مدرک قبولی: lag، error و row marker رو کنار هم بسنج.

Proof: Compare lag, errors, and a tagged row.

راهنماییHint

replica جای backup نیست.

A replica is not a replacement for backup.

8) آزمایش restore8) Restore drill

از artifact بازیابی‌شده یک بار دیگر در محیط تازه restore کن.

Restore the artifact once more into a fresh environment.

-- restore into a second disposable target; rerun validation queries

مدرک قبولی: این تست قابلیت تکرار روش رو اثبات می‌کنه.

Proof: This proves the procedure is repeatable.

راهنماییHint

هرگز روی تنها live database آزمایش نکن.

Never rehearse on the only live database.

9) گزارش تحویل9) Handoff

گزارش symptom/evidence/diagnosis/repair/verification و RPO/RTO رو جمع کن.

Compile symptom/evidence/diagnosis/repair/verification plus RPO/RTO.

-- include backup ID, binlog range, GTID/status, validation output

مدرک قبولی: موارد نامطمئن رو هم صریح بنویس.

Proof: State uncertainties explicitly.

راهنماییHint

secret، دادهٔ شخصی و credential رو حذف کن.

Remove secrets, personal data, and credentials from handoff artifacts.

حادثه — DELETE اشتباه به replica هم رسیدهIncident — the mistaken DELETE reached the replica

این پروژه رو با restore شروع کن، نه failover. replica کپی تازه‌تری از اشتباهه؛ history مستقل نیست. backup پایه و binlog chain رو پیدا کن و target time رو قبل از replay مشخص کن.

Start with recovery, not failover. The replica contains a fresher copy of the same mistake; use the base backup and binary-log chain to define a recovery target.

SHOW BINARY LOGS;
SHOW REPLICA STATUS\G

این رو فقط اجرا نکن و رد نشو. قبلش حدس بزن چه چیزی باید ببینی، بعد از اجرا هم همون خط یا state مهم رو جدا کن. اگه نتیجه با حدست فرق داشت، همون اختلاف سؤال بعدی ماست.

Do not merely run this and move on. Predict the important result first, then preserve the line or state that matters. If reality differs from the prediction, use that mismatch as the next debugging question.
