Project 2 — MySQL analytics and tuning

گزارش فروش ماهانه از زمان‌بندی خارج شده. تیم index می‌خواهد، اما کسی baseline، plan یا هزینهٔ write رو ثبت نکرده.

The monthly sales report is missing its schedule. The team wants an index, but nobody recorded a baseline, plan, or write cost.

پیش‌نیاز: فصل‌های ۱ تا 58 · Prerequisites: Chapters 1–58پروژهٔ عملی · Practical projectکد و مدرک تحویل · Code and proof required

ماموریتMission

روی dataset ساختگی اما معنادار، query گزارش رو بازتولید کن؛ با EXPLAIN و اندازه‌گیری، یک یا چند تغییر کنترل‌شده رو ثابت کن. سرعت رو بدون سنجش correctness و هزینهٔ نوشتن اعلام نکن.

Reproduce the report query on a meaningful synthetic dataset; use EXPLAIN and measurements to prove controlled changes. Do not claim a speedup without checking correctness and write cost.

دادهٔ تمرین رو خودت بساز و فایل راه‌اندازی رو طوری تحویل بده که نفر دیگری بتواند از صفر آن رو اجرا کند. secret واقعی رو در Git یا فایل SQL قرار نده.

Create your own test data and provide setup files another engineer can run from scratch. Never commit real secrets to Git or SQL files.

تحویل‌ها و معیار قبولیDeliverables and acceptance criteria

  • README دوزبانه یا دست‌کم روشن با نسخهٔ server، پیش‌نیاز و دستور اجرا / README with server release, prerequisites, and run commands
  • SQL setup، seed، queryها و اسکریپت verify / SQL setup, seed, queries, and verification script
  • خروجی واقعی commandها و توضیح محدودیت‌ها / Real command output and documented limitations
  • دادهٔ disposable، بدون credential واقعی / Disposable data; no real credentials

امتیاز فقط برای «اجرا شد» نیست؛ correctness، مسیر شکست، امنیت و قابلیت تکرار هم بررسی می‌شوند.

“It ran” is not enough: correctness, failure handling, security, and reproducibility are also reviewed.

گام‌های پروژهProject milestones

1) ساخت داده1) Generate data

جدول orders و order_items با تاریخ، مشتری و مقدارها بساز و حجم کافی اما محدود تولید کن.

Create orders and order_items with dates, customers, and amounts; generate enough but bounded data.

CREATE INDEX ix_orders_created ON orders(created_at);

مدرک قبولی: seed script و countهای قابل‌تکرار رو ثبت کن.

Proof: Record a repeatable seed script and row counts.

راهنماییHint

داده باید توزیع ناهمگون و بازه‌های زمانی داشته باشه.

Use data with skewed distributions and realistic time ranges.

2) baseline2) Baseline

query ماهانهٔ فعلی رو با ورودی ثابت، نتیجه، EXPLAIN و چند زمان‌گیری ثبت کن.

Capture the current monthly query, fixed parameters, result, EXPLAIN, and repeated timings.

EXPLAIN ANALYZE SELECT ... WHERE created_at >= ? AND created_at < ?;

مدرک قبولی: میانه و پراکندگی رو گزارش کن، نه فقط بهترین اجرا رو.

Proof: Report median and spread, not only the fastest run.

راهنماییHint

cache و concurrency رو تا جای ممکن ثابت کن.

Keep cache state and concurrency as comparable as practical.

3) صحت نتیجه3) Correctness

نتیجهٔ query بهینه و مرجع رو برای همان بازه مقایسه کن.

Compare optimized and reference results for the same interval.

-- compare row sets and aggregate totals

مدرک قبولی: اختلاف خروجی یعنی tuning ناموفق حتی اگه سریع‌تر باشه.

Proof: Different output means tuning failed even if it is faster.

راهنماییHint

rounding و nullها رو هم بررسی کن.

Verify rounding behavior and NULL handling as well.

4) فرضیهٔ index4) Index hypothesis

بر اساس predicate و plan یک index مرکب پیشنهاد بده؛ ترتیب ستون‌ها رو توجیه کن.

Propose a composite index from the predicate and plan; justify column order.

CREATE INDEX ix_orders_status_created ON orders(status, created_at);

مدرک قبولی: قبل/بعد rows examined و انتخاب access path رو ثبت کن.

Proof: Record rows examined and chosen access path before/after.

راهنماییHint

صرفاً به قاعدهٔ selectivity تکیه نکن؛ query رو بخوان.

Do not rely on selectivity rules alone; read the actual query and plan.

5) گزارش aggregate5) Aggregate report

join و group by رو بررسی کن و دادهٔ اضافی رو زودتر محدود کن.

Inspect joins and GROUP BY; reduce irrelevant rows early.

EXPLAIN ANALYZE SELECT customer_id, SUM(total) FROM orders WHERE created_at >= ? GROUP BY customer_id;

مدرک قبولی: sort، temporary work و loopها رو توضیح بده.

Proof: Explain sorting, temporary work, and loops.

راهنماییHint

ساختار query رو با محدودیت معنایی حفظ کن.

Preserve the query’s business semantics while changing its structure.

6) هزینهٔ تغییر6) Change cost

اثر index رو روی insert/update و اندازهٔ storage اندازه بگیر.

Measure the index's impact on inserts/updates and storage.

-- run the same bounded write workload with/without the candidate index

مدرک قبولی: گزارش باید trade-off خواندن/نوشتن رو روشن کند.

Proof: Make read/write trade-offs explicit.

راهنماییHint

یک query سریع‌تر کافی نیست.

One faster query is not enough; check the rest of the workload.

7) تصمیم و handoff7) Decision and handoff

تغییر رو نگه دار یا rollback کن و نتیجه رو با evidence مستند کن.

Keep or roll back the change and document the decision with evidence.

SHOW INDEX FROM orders;

مدرک قبولی: README شامل baseline، نسخهٔ نهایی، دستورهای تست و محدودیت‌هاست.

Proof: README includes baseline, final design, test commands, and limitations.

راهنماییHint

دادهٔ تمرین رو در dump کوچک و بدون secret تحویل بده.

Hand off a small reproducible dump with no secrets.

Baseline — قبل از tuning عدد بدهBaseline — measure before tuning

سه query واقعی گزارش رو انتخاب کن. result correctness، plan و زمان رو ثبت کن. پروژه‌ای که فقط نسخهٔ سریع‌تر رو تحویل بده ولی baseline نداشته باشه، tuning قابل‌دفاعی نداره.

Choose three representative analytical queries and record correctness, plans, and timing before changing indexes or SQL.

EXPLAIN ANALYZE SELECT customer_id, SUM(total) FROM orders GROUP BY customer_id;

این رو فقط اجرا نکن و رد نشو. قبلش حدس بزن چه چیزی باید ببینی، بعد از اجرا هم همون خط یا state مهم رو جدا کن. اگه نتیجه با حدست فرق داشت، همون اختلاف سؤال بعدی ماست.

Do not merely run this and move on. Predict the important result first, then preserve the line or state that matters. If reality differs from the prediction, use that mismatch as the next debugging question.

یک تغییر، یه آزمایشOne change, one experiment

برای هر index یا rewrite دقیق بنویس فرضیه‌ت چی بود. بعد فقط همون تغییر رو اعمال کن و query رو با شرایط مشابه دوباره اجرا کن.

For every index or rewrite, state the hypothesis, make one change, and rerun the same query under comparable conditions.

SHOW INDEX FROM orders;
ANALYZE TABLE orders;

Regression hunt — read سریع‌تر، write چی؟Regression hunt — reads got faster; what happened to writes?

گزارش خوب فقط latency SELECT رو نمی‌گه. هزینهٔ index روی insert/update و storage رو هم بسنج. ممکنه یه بهبود محلی، workload کل رو بدتر کرده باشه.

A good report includes write and storage cost, not only SELECT latency. A local read improvement can still be a poor workload decision.

SELECT TABLE_NAME,DATA_LENGTH,INDEX_LENGTH FROM information_schema.tables WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='orders';

این رو فقط اجرا نکن و رد نشو. قبلش حدس بزن چه چیزی باید ببینی، بعد از اجرا هم همون خط یا state مهم رو جدا کن. اگه نتیجه با حدست فرق داشت، همون اختلاف سؤال بعدی ماست.

بازبینی نهاییFinal review

قبل از تحویل، setup رو از محیط تمیز اجرا کن، تمام proofها رو دوباره بگیر، فایل‌های artifact رو از دادهٔ حساس پاک کن و روش rollback رو واضح بنویس. پروژه وقتی تمام هست که نفر دیگری بتواند نتیجه رو مستقل تکرار کند.

Before handoff, run setup from a clean environment, recapture every proof, scrub sensitive data from artifacts, and document rollback. The project is complete only when another person can reproduce the result independently.
