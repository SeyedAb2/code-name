وب و دیتابیس هر دو Running هستن؛ چرا اتصال برقرار نمی‌شه؟

Web and database are running. Why can they not connect?

در Compose هر دو سرویس بالا هستن، اما web به localhost:3306 وصل می‌شه. در اینجا localhost یعنی خود container وب، نه container دیتابیس. نام سرویس و شبکهٔ مشترک رو جای IP ثابت می‌ذاریم، port داخلی رو از host port جدا می‌کنیم و بعد DNS، TCP و آمادگی DB رو با هم قاطی نمی‌کنیم.

Both Compose services are running, but web connects to localhost:3306. Here localhost means the web container itself, not the database container. We will use a service name on a shared network, separate internal from host ports, and distinguish DNS, TCP, and database readiness.

نام سرویس، IP پایدار نیست؛ نقطهٔ اتصال پایدار هستThe service name is stable; the container IP is not

Compose هر پروژه رو به شبکهٔ پیش‌فرضش وصل می‌کنه و سرویس‌ها رو با نام service در همان network پیدا می‌کنه. پس web به host برابر db و port داخلی MySQL وصل می‌شه. وقتی container عوض شود IP می‌تونه تغییر کند اما نام سرویس همان می‌مونه؛ connectionهای باز هم ممکنه قطع شوند و app باید دوباره resolve و وصل شود.

Compose connects a project to its default network and makes each service discoverable by its service name. Web uses host db and MySQL's container port. A recreated container may get a new IP while the service name remains stable; existing connections can still drop, so the app must resolve and reconnect.

host port فقط برای رسیدن از host بیرون شبکه است؛ سرویس وب به DB با port داخلی وصل می‌شه.

The host port is for access from outside; web reaches DB through its internal port.

ports دو سمت دارد؛ داخل شبکه از سمت درست استفاده کنPorts have two sides; use the right one inside the network

در mapping مثل 13306:3306، عدد اول port روی host هست و عدد دوم port داخل container. از host می‌تونی به localhost:13306 وصل شوی؛ web container باید به db:3306 وصل شود. لازم نیست دیتابیس port عمومی داشته باشه تا دو سرویس روی شبکهٔ مشترک با هم حرف بزنند.

In a mapping such as 13306:3306, the first port is on the host and the second is inside the container. The host may connect to localhost:13306; the web container uses db:3306. The database need not publish a public port for services on a shared network to communicate.

services:
  web:
    environment:
      DB_HOST: db
      DB_PORT: "3306"
  db:
    image: mysql:9.7
    # No public ports mapping

این فقط نمونهٔ networking است؛ secret و volume دیتابیس رو حذف نکن. tag نسخه رو با نسخهٔ هدف خودت تطبیق بده و دیتابیس تمرینی رو به volume مهم production وصل نکن.

This is a networking fragment, not a complete secure deployment; retain secret and volume configuration. Pin the intended image version and never attach a lab database to production data.

DNS، TCP و آماده‌بودن MySQL سه آزمون‌اندDNS, TCP, and MySQL readiness are separate tests

از خود web container نام db رو resolve کن، بعد port رو امتحان کن و در آخر با client به MySQL login کن. وجود DNS رکورد، بازبودن TCP رو ثابت نمی‌کنه؛ بازبودن TCP هم login یا آماده‌بودن schema رو ثابت نمی‌کنه. اگه container موقت client لازم است، آن رو به همان Compose network وصل کن و پس از آزمایش حذفش کن.

Resolve db from the web container, test the port, then authenticate with a MySQL client. A DNS record does not prove TCP reachability; an open port does not prove login or schema readiness. If a temporary client container is needed, attach it to the same Compose network and remove it after the test.

docker compose exec web getent hosts db
docker compose exec web nc -vz db 3306
docker compose exec web mysql --protocol=TCP --host=db --port=3306 -u app -p

اگه ابزارها در image وب نصب نیستند، برای debug از container موقت یا ابزار موجود استفاده کن؛ image production رو فقط برای داشتن ping یا nc سنگین نکن.

If the web image lacks these tools, use a temporary diagnostic container or available tooling; do not bloat production merely to add ping or nc.

شبکهٔ سالم، DB آماده رو تضمین نمی‌کنهA working network does not guarantee a ready database

DNS ممکنه از لحظهٔ ساخت network کار کند، در حالی که MySQL هنوز initialization می‌کنه. healthcheck و شرط depends_on فصل‌های قبل رو به کار ببر؛ حتی آن‌ها جای retry و reconnect برنامه رو نمی‌گیرن، چون DB ممکنه پس از شروع web هم موقتاً قطع شود. DB_HOST رو داخل container به localhost تنظیم نکن.

DNS may work as soon as the network exists while MySQL is still initializing. Apply the prior healthcheck and depends_on pattern; neither removes the need for application retries because the DB may become temporarily unavailable later. Do not configure DB_HOST as localhost inside the app container.

services:
  web:
    environment:
      DB_HOST: db
      DB_PORT: "3306"
    depends_on:
      db:
        condition: service_healthy
  db:
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1"]
      interval: 5s
      timeout: 3s
      retries: 10

healthcheck واقعی باید account/schema موردنیاز اپ رو تا جای ممکن بسنجد؛ نمونهٔ mysqladmin صرفاً زنده‌بودن سرور رو بررسی می‌کنه. health و منطق reconnect رو جدا طراحی کن.

A real healthcheck should validate the app's required account or schema where practical; this mysqladmin example only checks server responsiveness. Design health and reconnect logic separately.

localhost داخل container یعنی خود همون containerlocalhost inside a container means that container

این یکی از باگ‌های کلاسیکه: app داخل containerه و connection string روی localhost:3306 تنظیم شده، در حالی که MySQL توی container دیگه اجرا می‌شه. localhost هیچ‌وقت اسم جادویی «ماشین من» نیست؛ loopback همون network namespace فعلیه.

A classic container bug is using localhost from the application container while MySQL runs in another container. Loopback refers to the current container network namespace.

از داخل container برنامه DNS اسم service رو resolve کن و بعد TCP رو همون‌جا test کن.

Published port با service-to-service path فرق دارهPublished ports are different from service-to-service traffic
