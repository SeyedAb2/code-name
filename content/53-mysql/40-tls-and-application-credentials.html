رمز رو درست فرستادیم؛ آیا مسیر شبکه هم امن است؟

We sent the right password. Is the network path secure too?

برنامه از لپ‌تاپ توسعه‌دهنده یا یک سرویس دیگر به MySQL وصل می‌شه. password درست هست و login موفق؛ اما آیا ترافیک رمزگذاری شده؟ آیا client مطمئن شده به همان server موردنظر وصل است؟ این دو پرسش یکی نیستند. اول وضعیت session رو می‌خونیم، بعد TLS و مدیریت credential رو جدا می‌کنیم.

An application connects to MySQL from a developer laptop or another service. The password is correct and login works—but is traffic encrypted, and did the client verify it reached the intended server? These are different questions. We will inspect the session, then treat TLS and credential handling separately.

رمزگذاری، احراز هویت server و مدیریت رمز سه موضوع‌اندEncryption, server identity, and secret handling are separate

TLS ترافیک رو رمز می‌کنه؛ اعتبارسنجی گواهی کمک می‌کنه client هویت server رو بررسی کند؛ secret هم باید امن نگهداری و rotate شود. اتصال رمزگذاری‌شده بدون اعتبارسنجی درست گواهی می‌تونه در برابر server جعلی کافی نباشه. از سوی دیگر، credential قوی هم ترافیک بی‌رمز رو امن نمی‌کنه.

TLS encrypts traffic; certificate validation helps the client verify the server identity; credentials must also be stored and rotated safely. Encryption without correct certificate validation may not protect against an impostor server. A strong password does not secure unencrypted traffic either.

هر سه مرز مستقل‌اند؛ یکی جای دیگری رو پر نمی‌کنه.

These controls are independent; none substitutes for another.

اول اتصال جاری رو با شاهد بخوانRead evidence from the current connection

بعد از اتصال، cipher و نسخهٔ TLS همان session رو بخوان. مقدار cipher خالی نشانهٔ این هست که این connection رمزگذاری TLS ندارد. مقدار پر هم فقط رمزگذاری رو ثابت می‌کنه؛ گواهی و نام server باید با تنظیم client بررسی شوند.

After connecting, inspect the cipher and TLS version for this session. An empty cipher indicates this connection is not using TLS encryption. A populated value proves encryption only; the client configuration must verify the certificate and server name.

SHOW SESSION STATUS LIKE 'Ssl_cipher';
SHOW SESSION STATUS LIKE 'Ssl_version';
SHOW VARIABLES LIKE 'require_secure_transport';

متغیر آخر سیاست server رو نشان می‌ده، نه اینکه session حتماً با هویت درست وصل شده. clientهایی که TCP، socket یا named pipe استفاده می‌کنن رفتار transport متفاوتی دارن.

The last variable reports server policy, not whether this session verified the right identity. TCP, socket, and named-pipe transports have different security properties.

client باید CA و نام server رو بررسی کندThe client should validate the CA and server name

برای mysql client، حالت‌های SSL از DISABLED تا VERIFY_IDENTITY فرق دارن. REQUIRED رمزگذاری می‌خواهد؛ VERIFY_CA زنجیرهٔ CA رو بررسی می‌کنه؛ VERIFY_IDENTITY علاوه بر CA نامی رو که client استفاده کرده با هویت گواهی می‌سنجد. برای connector برنامه، گزینه و پیش‌فرض همان driver رو از مستند خودش پیدا کن؛ اسم گزینه‌ها در کتابخانه‌ها ممکنه فرق کند.

The mysql client supports modes from DISABLED to VERIFY_IDENTITY. REQUIRED requests encryption; VERIFY_CA validates the CA chain; VERIFY_IDENTITY also checks the hostname used by the client against the certificate identity. For application connectors, consult that driver's own documentation because option names and defaults can differ.

mysql --host=db.example.test --user=app_user \
  --ssl-mode=VERIFY_IDENTITY \
  --ssl-ca=/run/secrets/mysql-ca.pem \
  --password

از IP استفاده نکن مگر گواهی آن IP رو پوشش دهد. password رو بدون مقدار کنار --password نده تا client آن رو تعاملی بپرسد؛ در برنامه از secret store استفاده کن، نه command line یا source code.

Do not connect by IP unless the certificate covers that IP. Omit the password value so the client prompts interactively; applications should use a secret manager, not command-line arguments or source code.

TLS اجباری رو با برنامهٔ واقعی هماهنگ کنCoordinate mandatory TLS with real clients

server می‌تونه transport امن رو اجباری کند و account هم می‌تونه REQUIRE SSL داشته باشه. این سیاست‌ها رو پس از آماده‌کردن گواهی و آزمون connector فعال کن؛ ترتیب برعکس باعث قطعی می‌شه. تغییر رو از یک client آزمایشی شروع کن، سپس گزارش وضعیت session و log خطاها رو بررسی کن.

The server can require secure transport, and an account can require SSL. Prepare certificates and test connector support before enforcing policy; reversing that order can cause an outage. Start with a test client, then inspect session evidence and error logs.

ALTER USER 'app_user'@'10.20.%' REQUIRE SSL;
SHOW CREATE USER 'app_user'@'10.20.%';
-- Server-wide policy is an administrative change:
-- SET PERSIST require_secure_transport = ON;

این دستور مدیریتی رو فقط با برنامهٔ تغییر و امکان recovery اجرا کن. برای account/host خودت جایگزین بگذار؛ نمونه رو کورکورانه روی server اصلی اجرا نکن.

Treat this as an administrative change with a rollout and recovery plan. Substitute your exact account and host; do not run the example blindly in production.

credential بخشی از تنظیم محیط هستCredentials belong to managed configuration

password رو داخل query، Dockerfile، Git، log یا URL اتصال ثبت نکن. دسترسی فایل secret رو محدود کن، secret رو به process مناسب تحویل بده و در log مقدارش رو mask کن. rotate کردن password باید deployment app و database رو هماهنگ کند؛ برای secret فعال، تغییر یک‌طرفه می‌تونه همهٔ connectionها رو قطع کند.

Do not put passwords in queries, Dockerfiles, Git, logs, or connection URLs. Restrict secret-file access, deliver the secret only to the right process, and redact it from logs. Rotation must coordinate the app and database; changing only one side can break every connection.
