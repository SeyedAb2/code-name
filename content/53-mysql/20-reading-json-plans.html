وقتی plan از جدول به درخت تبدیل می‌شه

When a plan becomes a tree

در فصل قبل، plan جدولی رو برای یک سؤال مشخص خواندیم. حالا همان پرس‌وجو چند join و شرط دارد و می‌خوایم رابطهٔ مرحله‌ها رو ببینیم. JSON جزئیات بیشتری می‌ده؛ اما جزئیات بیشتر به‌تنهایی جواب بهتر یا زمان اجرای واقعی نیست.

The previous chapter read a tabular plan for a specific question. Now a query has joins and filters, and we want to see how its operations relate. JSON gives more structure, but more detail is neither a better answer by itself nor actual runtime.

پیش‌نیازPrerequisite: فصل ۱۹ · EXPLAINنسخهٔ مرجعReference: MySQL 9.7زمانTime: ۸۵ دقیقه · ۱۸ تمرین

یک جدول خوب است؛ تا وقتی سؤال چندمرحله‌ای نشدهA table is fine until the question has several stages

تیم پشتیبانی می‌خواهد ticketهای باز هر تیم رو همراه نام مشتری ببیند. کوئری جواب درست می‌ده، ولی کسی می‌پرسد: «اول مشتری‌ها خوانده می‌شوند یا ticketها؟ فیلتر کجا اعمال می‌شه؟» خروجی جدولی فصل قبل برای شروع مفید بود، اما شکل رابطهٔ عملیات رو خوب نشان نمی‌داد.

The support team needs each team’s open tickets with customer names. The query returns correct rows, but someone asks: “Are customers or tickets read first? Where is the filter applied?” The previous chapter’s table was a useful start, but it did not show the relationships between operations as clearly.

پس plan JSON می‌گیریم و آن رو مثل یک نقشه می‌خونیم. پیش از تفسیر، نسخهٔ سرور و نسخهٔ قالب JSON رو می‌بینیم؛ چون شکل سند میان نسخه‌ها تفاوت دارد. سؤال ما «کدام مرحله به کدام مرحله داده می‌ده؟» است، نه «چطور کل JSON رو حفظ کنم؟»

We ask for a JSON plan and read it as a map. First we check the server and JSON-format versions, because the document shape differs. Our question is “Which operation feeds which?”—not “How do I memorize the whole document?”

محیط کوچک و قابل تکرار بسازیمCreate a small, repeatable fixture

همهٔ تغییرهای این آزمایش داخل schema جداگانه می‌مونه. اگه این نام رو قبلاً برای دادهٔ مهم استفاده کرده‌ای، اسم تازه‌ای انتخاب کن؛ دستور حذف جدول‌ها فقط برای محیط تمرینی هست.

All changes stay in a separate schema. If you already use this name for valuable data, choose another one; the table drops below are for this disposable fixture only.

ساخت دادهٔ آزمایشیBuild the fixture
CREATE DATABASE IF NOT EXISTS codenames_json_plan_lab;
USE codenames_json_plan_lab;
DROP TABLE IF EXISTS support_ticket;
DROP TABLE IF EXISTS customer;

CREATE TABLE customer (
  customer_id INT NOT NULL PRIMARY KEY,
  team_id INT NOT NULL,
  customer_name VARCHAR(80) NOT NULL,
  KEY ix_customer_team(team_id)
) ENGINE=InnoDB;

CREATE TABLE support_ticket (
  ticket_id INT NOT NULL PRIMARY KEY,
  customer_id INT NOT NULL,
  state VARCHAR(12) NOT NULL,
  created_at DATE NOT NULL,
  KEY ix_ticket_customer_state(customer_id,state),
  KEY ix_ticket_state_created(state,created_at)
) ENGINE=InnoDB;

INSERT INTO customer VALUES
(1,10,'Ava'),(2,10,'Reza'),(3,20,'Mina'),(4,20,'Omid');
INSERT INTO support_ticket VALUES
(101,1,'open','2026-01-01'),(102,1,'closed','2026-01-02'),
(103,2,'open','2026-01-03'),(104,3,'open','2026-01-04'),
(105,4,'waiting','2026-01-05'),(106,4,'open','2026-01-06');

SELECT c.team_id,c.customer_name,t.ticket_id,t.created_at
FROM customer AS c
JOIN support_ticket AS t ON t.customer_id=c.customer_id
WHERE c.team_id=10 AND t.state='open'
ORDER BY t.created_at;

باید سه ردیف ببینی. این نتیجهٔ SELECT است؛ هنوز دربارهٔ مسیر اجرای آن چیزی نگفته‌ایم. تعداد کم ردیف‌ها عمدی هست تا آزمایش سریع و امن بماند، ولی optimizer ممکنه به‌خاطر کوچکی داده‌ها هر دو جدول رو scan کند. از پیش انتظار استفاده از index نداشته باش.

You should see three rows. That is the SELECT result; it says nothing yet about the execution path. The tiny fixture keeps the experiment quick and safe, but the optimizer may scan either table because the data is small. Do not assume an index must be chosen.

قبل از خواندن JSON، نسخه‌اش رو شناسایی کنIdentify the JSON format before reading it

در MySQL 9.7، متغیر session به نام explain_json_format_version شکل خروجی JSON رو تعیین می‌کنه؛ مقدار پیش‌فرض ۲ هست. نسخهٔ ۱ ساختار قدیمی‌تر و خطی‌تری دارد؛ نسخهٔ ۲ plan رو بر پایهٔ access path نمایش می‌ده و شمارهٔ قالب رو هم در خروجی می‌آورد. بنابراین مسیرهای JSON رو بدون دانستن نسخه کپی نکن.

In MySQL 9.7, the session variable explain_json_format_version controls JSON shape and defaults to 2. Version 1 is the older, more linear structure; version 2 represents access paths and includes its format version in the output. Do not copy JSON paths without knowing which format produced them.

نسخه و plan فعلیCheck the version and plan
SELECT VERSION(), @@session.explain_json_format_version;
EXPLAIN FORMAT=JSON
SELECT c.customer_name,t.ticket_id
FROM customer AS c
JOIN support_ticket AS t ON t.customer_id=c.customer_id
WHERE c.team_id=10 AND t.state='open';

به نسخهٔ server و مقدار متغیر توجه کن. در خروجی، JSON v1 معمولاً از query_block شروع می‌شه و اطلاعات table رو زیر آن می‌بینی؛ v2 کلیدهایی مثل json_schema_version و query_plan دارد و عملیات رو به‌صورت تو‌در‌تو نشان می‌ده. نام و ترتیب بعضی جزئیات به query، داده و نسخه وابسته هست.

Note the server version and variable. Version 1 commonly starts with query_block and places table information below it. Version 2 has keys such as json_schema_version and query_plan, with nested operations. Some details and their order depend on the query, data, and server version.

plan رو از سؤال به جزئیات بخوانRead the plan from the question down to details

برای این join چهار پرسش کافی هست: کدام tableها حاضرند؟ ترتیب یا رابطهٔ عملیات چیست؟ optimizer برای هر مسیر چه cardinality و costی برآورد کرده؟ کدام شرط‌ها یا indexها در plan دیده می‌شوند؟ ابتدا گرهٔ بیرونی رو بخوان، بعد فرزندانش رو دنبال کن. شکل تو‌در‌تو می‌تونه چند مفهوم رو کنار هم نشان دهد؛ آن رو به یک «رتبهٔ خوب/بد» تبدیل نکن.

For this join, start with four questions: which tables appear? How are operations related? What cardinality and cost does the optimizer estimate? Which predicates or indexes are represented? Read the outer node, then follow its children. A nested shape can express several concepts; do not reduce it to a good/bad score.

در v1 ممکنه rows_examined_per_scan و rows_produced_per_join رو ببینی. در v2 نام‌هایی مثل estimated_rows و estimated_total_cost در مسیرها دیده می‌شه. cost واحد میلی‌ثانیه نیست و rows هم شمارش قطعی نتیجه نیست؛ این‌ها تخمین optimizer با آمار و اطلاعات موجودند. برای مشاهدهٔ رفتار اجرا، به فصل بعد می‌رسیم.

Version 1 may show rows_examined_per_scan and rows_produced_per_join. Version 2 may expose fields such as estimated_rows and estimated_total_cost on paths. Cost is not milliseconds, and rows are not a guaranteed result count; they are optimizer estimates based on available statistics. Runtime evidence belongs in the next chapter.

یک عادت مفید: اول query و schema دقیق رو نگه دار؛ بعد plan رو با همان‌ها بخوان. اگه فقط بخشی از JSON رو کپی کرده‌ای، ممکنه رابطهٔ parent و child یا اطلاعات cost رو از دست داده باشی.A useful habit:Keep the exact query and schema, then read the plan alongside them. Copying only a JSON fragment can hide parent-child relationships or cost context.

JSON رو در session بگیر و بررسی کنCapture JSON in the session and inspect it

در MySQL 9.7 می‌توان plan قالب JSON v2 رو با INTO @plan در متغیر همان session گذاشت و سپس با تابع JSON پرس‌وجو کرد. این روش برای ابزارسازی و مقایسه مفید است؛ متغیر user به session محدود هست و با اتصال تازه منتقل نمی‌شه. مقدار مسیر رو از ساختار واقعی خروجی انتخاب کن.

MySQL 9.7 can store a version-2 JSON plan in a session user variable with INTO @plan, then query it with JSON functions. This helps tooling and comparison; a user variable belongs to the current session and is not carried to a new connection. Choose paths from the actual output structure.

ثبت و کنترل سند JSONCapture and validate the JSON document
SET @saved_json_version = @@session.explain_json_format_version;
SET SESSION explain_json_format_version = 2;

EXPLAIN FORMAT=JSON INTO @plan
SELECT c.customer_name,t.ticket_id
FROM customer AS c
JOIN support_ticket AS t ON t.customer_id=c.customer_id
WHERE c.team_id=10 AND t.state='open';

SELECT JSON_VALID(@plan) AS valid_json,
       JSON_EXTRACT(@plan,'$.json_schema_version') AS format_version,
       JSON_EXTRACT(@plan,'$.query_plan') IS NOT NULL AS has_query_plan;

SET SESSION explain_json_format_version = @saved_json_version;

در این نسخهٔ مرجع انتظار داریم JSON معتبر و نسخهٔ schema برابر ۲ باشه و query_plan وجود داشته باشه؛ متن کامل plan وابسته به داده و optimizer هست. اگه نسخهٔ سرور قدیمی‌تر هست یا متغیر رو ندارد، از EXPLAIN FORMAT=JSON عادی استفاده کن و خروجی رو مستقیماً بخوان؛ دستور INTO رو برای همهٔ MySQLها تعمیم نده.

For this reference version, expect valid JSON, schema version 2, and a query_plan; the full plan text depends on data and optimizer choices. On an older server without this variable or feature, use ordinary EXPLAIN FORMAT=JSON and inspect its output directly. Do not generalize INTO to every MySQL release.

تنظیم رو در سطح session نگه دار. این آزمایش مقدار global رو تغییر نمی‌ده. در کار واقعی، اگه ترتیب دستورها قطع شد یا اتصال رو عوض کردی، مقدار session رو دوباره بررسی کن؛ پایان اسکریپت رو راه بازگرداندن تنظیم تلقی نکن.Keep the setting session-scoped.This experiment does not change the global value. In real work, if execution is interrupted or the connection changes, check the session value again; do not assume the script reached its restore statement.

سه برداشت اشتباه از JSONThree common misreadings of JSON

«JSON طولانی‌تر است، پس دقیق‌تر جواب می‌ده»

“JSON is longer, so it answers more precisely”

قالب فقط جزئیات بیشتری از تخمین optimizer می‌ده. اندازهٔ سند، کیفیت آمار و درستی پیش‌بینی رو تضمین نمی‌کنه.

The format exposes more optimizer estimates. Document size guarantees neither good statistics nor accurate predictions.

«cost برابر زمان هست»

“Cost equals elapsed time”

cost امتیاز/مدل داخلی برای مقایسهٔ planهاست، نه میلی‌ثانیه‌ای که کاربر تجربه می‌کنه. latency، رقابت منابع و cache سؤال‌های جداگانه‌اند.

Cost is an internal model for comparing plans, not user-observed milliseconds. Latency, resource contention, and cache state are separate questions.

«یک JSON path برای همیشه معتبر هست»

“One JSON path is valid forever”

نسخهٔ قالب و خود plan مهم‌اند. مسیر رو با JSON_EXTRACT روی سند همان سرور آزمایش کن و اگه خروجی خالی شد، اول شکل سند رو بررسی کن.

The format version and plan shape matter. Test paths with JSON_EXTRACT against that server’s document; if a value is missing, inspect the document shape first.

تمرین‌ها — دست به کیبورد، نه حفظیاتExercises — hands on keyboard, not memorization

از fixture همین فصل استفاده کن. برای هر plan، نسخهٔ سرور و قالب رو کنار query نگه دار. خروجی‌های plan ممکنه فرق کنند؛ پاسخ‌ها باید از نوع مدرک رو بخوانند، نه یک خط خروجی ثابت رو حفظ کنند.

Use this chapter’s fixture. Keep server and format versions with each query plan. Plan output can differ; learn to read the evidence type rather than memorize one exact line.

These are not prose-only questions. Every exercise should end in runnable SQL/commands, observable output, a reproducible error, or inspectable state. Predict first, run it, then conclude from evidence.
