یک خطا وسط انتقال افتاد؛ باید ادامه بدهیم یا همه‌چیز رو برگردانیم؟

An error interrupted a transfer. Should we continue or roll everything back?

در فصل قبل query پویا رو اجرا کردیم؛ اما وقتی اجرای Procedure به خطا می‌خورد، caller فقط متن خطا رو می‌بیند و نمی‌دونه داده تا کجا تغییر کرده. Handler می‌تونه مسیر خطا رو اداره کند، ولی اگه آن رو برای «بی‌صدا رد شدن» بنویسیم، یک شکست واقعی رو شبیه موفقیت نشان می‌دیم. این‌جا با دو آزمایش کوچک تفاوت CONTINUE و EXIT رو می‌بینیم و بعد خطا رو ثبت، rollback و دوباره به caller منتقل می‌کنیم.

The previous chapter ran dynamic SQL, but when a procedure fails, the caller may see only an error and not know how far the data changed. A handler can manage the failure path, but if we use it to silently skip errors, a real failure can look like success. We will compare CONTINUE and EXIT, then capture diagnostics, roll back, and propagate the error to the caller.

فرض کنیم یک مرحله شکست بخوردSuppose one step fails

Procedure مقدار حساب رو زیاد می‌کنه، بعد رویداد رو ثبت می‌کنه. اگه درج مدرک شکست بخورد چه؟ ممکنه افزایش حساب بماند، یا کل عملیات rollback شود، یا خطا بلعیده شود و پاسخ موفق برگردد. قبل از نوشتن handler باید قراردادمان رو روشن کنیم: عملیات یک واحد است؛ اگه یکی از بخش‌های transaction شکست خورد، هیچ تغییر نیمه‌کاره‌ای نمی‌خوایم.

A procedure increments an account and then records an event. What if inserting the record fails? The balance might remain changed, the entire operation might roll back, or the error might be swallowed and reported as success. Before writing a handler, define the contract: the operation is one unit, so a failed transactional step must not leave partial changes.

فلش مسیر condition رو نشان می‌ده: خطا به handler می‌رسه، state بررسی می‌شه، تغییرهای transaction خودمان rollback می‌شوند و خطا دوباره به caller می‌رسه.

The arrows show condition flow: the error reaches the handler, diagnostics are captured, our transaction is rolled back, and the error is rethrown to the caller.

Handler جایگزین تصمیم‌گیری نیست. گاهی CONTINUE برای خطای مورد انتظار مناسب است؛ گاهی EXIT و RESIGNAL لازم‌اند. انتخاب اشتباه می‌تونه حلقه رو بی‌نهایت کند، ادامهٔ ناسازگار بسازد یا caller رو از شکست بی‌خبر بگذارد.

A handler is not a substitute for a policy decision. CONTINUE can fit an expected condition; other failures need EXIT and RESIGNAL. The wrong choice can loop forever, continue in an inconsistent state, or hide a failure from the caller.

مرز transaction رو جدی بگیرTreat transaction ownership as a contract

Procedure نمونه خودش START TRANSACTION می‌کنه. در MySQL شروع transaction تازه می‌تونه transaction قبلی connection رو commit کند؛ پس caller نباید با transaction باز و تغییرهای ذخیره‌نشده وارد این lab شود. در برنامهٔ واقعی توافق کن transaction رو caller مدیریت می‌کنه یا procedure.

The sample procedure starts its own transaction. In MySQL, starting a new transaction can commit an existing transaction on the connection; do not call this lab procedure while the caller has uncommitted work. In a real design, explicitly decide whether the caller or procedure owns the transaction.

CONTINUE خطا رو نمی‌زدایدCONTINUE does not erase the error

برای دیدن فرق، خطای duplicate key رو در جدول تمرینی تولید می‌کنیم. CONTINUE یعنی بعد از اجرای handler، برنامه از statement بعدی ادامه می‌ده؛ statement شکست‌خورده دوباره اجرا نمی‌شه. EXIT یعنی از بلوکی که handler در آن تعریف شده بیرون برو، حتی اگه شرط در بلوک داخلی رخ داده باشه. UNDO در MySQL پشتیبانی نمی‌شه.

We will raise a duplicate-key error in a lab table. CONTINUE means execution proceeds after the handler; it does not retry the failed statement. EXIT leaves the BEGIN...END block where the handler was declared, even if the condition occurred in an inner block. UNDO is not supported in MySQL.

ادامه رو با متغیر قابل مشاهده کنMake continuation visible
CREATE TABLE IF NOT EXISTS handler_unique_lab (
  id INT PRIMARY KEY
) ENGINE=InnoDB;
INSERT IGNORE INTO handler_unique_lab VALUES (1);
DROP PROCEDURE IF EXISTS continue_probe;
DELIMITER //
CREATE PROCEDURE continue_probe()
BEGIN
  DECLARE CONTINUE HANDLER FOR 1062 SET @duplicate_seen=1;
  SET @after_insert=0;
  INSERT INTO handler_unique_lab VALUES (1);
  SET @after_insert=2;
END//
DELIMITER ;
CALL continue_probe();
SELECT @duplicate_seen,@after_insert;
DROP PROCEDURE continue_probe;

در خروجی @after_insert باید ۲ باشه. اگه Handler نبود، خطا اجرای Procedure رو همان‌جا متوقف می‌کرد و SET آخر اجرا نمی‌شد. CONTINUE رو فقط وقتی انتخاب کن که ادامه بعد از آن شرط واقعاً درست باشه.

The result should show @after_insert as 2. Without a handler, the error would stop the procedure there and the final SET would not run. Use CONTINUE only when continuing after that condition is genuinely correct.

ترتیب declarationها و معنی scopeDeclaration order and handler scope

در هر بلوک BEGIN...END اول variableها و conditionها رو تعریف می‌کنیم، بعد cursorها و در پایان handlerها. Handler در همان block و scopeهای داخلی آن فعال هست. اگه چند handler با هم جور باشند، MySQL بر اساس قواعد اولویت انتخاب می‌کنه؛ در طراحی ساده شرط مشخص‌تر رو جدا بنویس تا معلوم باشه کدام سیاست اجرا می‌شه.

Within a BEGIN...END block, declare variables and conditions first, cursors next, and handlers last. A handler applies in its block and nested scopes. If multiple handlers match, MySQL follows precedence rules; keep conditions specific so the selected policy is understandable.

خطا رو بخوان؛ سپس تصمیم بگیر پنهانش کنی یا برگردانیInspect the error, then decide whether to handle or propagate it

داخل handler می‌تونیم SQLSTATE، کد MySQL و متن خطا رو بگیریم. اگه بعد از خطا statement دیگری اجرا بشه، diagnostics جاری ممکنه عوض شود. برای condition فعال‌کنندهٔ handler، GET STACKED DIAGNOSTICS مدرک قابل‌اتکاتری هست چون diagnostics مربوط به خطای اصلی رو نگه می‌دارد.

Inside a handler, we can capture SQLSTATE, the MySQL error number, and message text. A later statement may change the current diagnostics area. GET STACKED DIAGNOSTICS is the reliable way to read the condition that activated the handler.

Procedure با rollback و RESIGNALA procedure that rolls back and resignal
DROP PROCEDURE IF EXISTS adjust_counter;
DELIMITER //
CREATE PROCEDURE adjust_counter(
  IN p_id INT,
  IN p_delta INT,
  IN p_force_error BOOLEAN
)
BEGIN
  DECLARE v_tx_started BOOLEAN DEFAULT FALSE;
  DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN
    GET STACKED DIAGNOSTICS CONDITION 1
      @lab_sqlstate = RETURNED_SQLSTATE,
      @lab_errno = MYSQL_ERRNO,
      @lab_message = MESSAGE_TEXT;
    IF v_tx_started THEN
      ROLLBACK;
    END IF;
    RESIGNAL;
  END;

  IF p_delta <= 0 THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT='increment must be positive';
  END IF;

  START TRANSACTION;
  SET v_tx_started=TRUE;
  UPDATE counter_state SET value=value+p_delta WHERE id=p_id;
  IF ROW_COUNT()=0 THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT='counter row not found';
  END IF;
  IF p_force_error THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT='lab failure after update';
  END IF;
  COMMIT;
  SET v_tx_started=FALSE;
END//
DELIMITER ;

در مسیر خطا اول stacked diagnostics رو در user variable می‌گیریم؛ بعد فقط اگه همین Procedure transaction رو شروع کرده باشه rollback می‌کنیم؛ در پایان RESIGNAL خطا رو به client برمی‌گرداند. client هم error می‌بیند و هم می‌تونه در همان connection مقدارهای @lab_* رو بخواند. این session variables گزارش پایدار نیستند.

On failure, we first copy stacked diagnostics into user variables, roll back only if this procedure started the transaction, then RESIGNAL to the client. The client sees the error and can inspect @lab_* values in the same connection. These session variables are not durable logs.

یک بار موفق و یک بار ناموفق اجرا کنRun once successfully and once with a deliberate failure

بعد از اجرای موفق مقدار از ۱۰ به ۱۵ می‌رسه. اجرای ناموفق دوباره افزایش رو امتحان می‌کنه، اما handler آن رو rollback می‌کنه و client خطا می‌گیره؛ مقدار باید ۱۵ بماند. این اثبات فقط برای InnoDB و این transaction کنترل‌شده هست.

The successful call changes 10 to 15. The failing call attempts another increment, but the handler rolls it back and the client receives an error; the value should remain 15. This evidence applies to this controlled InnoDB transaction.

SIGNAL خطای تازه می‌سازد؛ RESIGNAL خطای جاری رو منتقل می‌کنهSIGNAL creates a condition; RESIGNAL propagates the active one

برای ورودی نامعتبر یا invariant نقض‌شده، SIGNAL می‌تونه خطای دامنه‌ای بسازد؛ مثل SQLSTATE 45000. در handler اگه می‌خوایم خطای اصلی به caller برسد، RESIGNAL می‌کنیم. اگه پیام رو عوض کنیم، اطلاعات اصلی رو پیش از آن capture کن؛ وگرنه جزئیاتی که caller می‌دید تغییر می‌کنه.

For invalid input or a violated invariant, SIGNAL can raise an application error such as SQLSTATE 45000. In a handler, RESIGNAL passes the active error to the caller. If you change the outward message, capture original details first or the caller will see a modified condition.

Handler خالی با CONTINUE که هر SQLEXCEPTION رو نادیده بگیره، تقریباً همیشه خطرناک هست: client موفقیت ظاهری می‌بیند و ادامهٔ عملیات شاید روی وضعیت نیمه‌کاره کار کند. error رو فقط وقتی handle کن که دقیقاً می‌دانی بعد از آن چه رفتاری درست هست.

An empty CONTINUE handler that ignores every SQLEXCEPTION is usually dangerous: the client may see apparent success and later work may use partial state. Handle an error only when you know exactly what behavior is correct afterward.
