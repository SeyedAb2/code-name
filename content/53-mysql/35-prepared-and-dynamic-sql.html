نام کالا ورودی کاربر است؛ query رو چطور امن بسازیم؟

A product name comes from a user. How do we build the query safely?

جست‌وجو باید مقدار Keyboard رو پیدا کند و گزارش هم گاهی یکی از دو جدول رو بخواند. مقدار کاربر داده هست و placeholder می‌پذیرد؛ نام جدول جزئی از دستور SQL هست و placeholder نمی‌شه. اگه این دو رو قاطی کنیم یا query ناامن می‌شه یا تصور می‌کنیم marker کار می‌کنه، درحالی‌که جای identifier نیست.

A search must find a value such as Keyboard, while a report may read from one of two tables. A user value is data and can use a placeholder; a table name is part of SQL syntax and cannot. Confusing them either makes a query unsafe or leads us to expect a marker where identifiers are not supported.

دو ورودی، دو جنس متفاوتTwo inputs, two different kinds

نام کالا ممکنه از فرم بیاید؛ مقدار رو نباید با چسباندن متن وارد SQL کنیم. نام جدول هم شاید بین چند گزارش فرق کند، اما آن رو نمی‌توان با FROM ? فرستاد. توی این فصل هر دو مسیر رو آزمایش می‌کنیم تا مرز داده و ساختار دستور روشن شود.

A product name may come from a form; we should not splice it into SQL text. A report may select among tables, but FROM ? cannot bind a table name. We will test both paths so the boundary between data and SQL structure is clear.

placeholder جای مقدار رو می‌گیره؛ identifier باید ثابت یا از گزینه‌های مجاز انتخاب بشه.

A placeholder binds a value; an identifier must be fixed or chosen from allowed options.

اول query ثابت رو با مقدار متغیر اجرا کنStart with fixed SQL and a changing value

این رابط SQL برای آزمایش در mysql client هست. برنامه‌ها معمولاً باید از API پارامتری connector استفاده کنند. query یک‌بار آماده می‌شه؛ مقدار جداگانه میاد؛ بعد statement آزاد می‌شه.

This SQL interface is useful for experiments in the mysql client. Applications should normally use their connector’s parameterized API. Prepare the query once, supply the value separately, then release the statement.

نام کالا رو bind کنBind a product name
SET @product_name = 'Keyboard';
PREPARE find_product
  FROM 'SELECT product_id,product_name,base_price
        FROM codenames_deadlock_lab.product_price
        WHERE product_name = ?';
EXECUTE find_product USING @product_name;
DEALLOCATE PREPARE find_product;

علامت ? بیرون quote هست و جای value رو نشان می‌ده. تعداد متغیرهای USING باید دقیقاً با markerها برابر باشه. statement به session تعلق دارد؛ اگه connection باز می‌مونه، آن رو صریح آزاد کن. بسته‌شدن connection آن رو پاک می‌کنه، اما به cleanup ضمنی تکیه نکن.

The unquoted ? marks a value position. The number of variables in USING must exactly match the markers. The statement belongs to the session; explicitly release it when the connection stays open. Closing the connection frees it, but do not rely on implicit cleanup.

پارامتری‌سازی ساختار query رو از داده جدا می‌کنه؛ اما مجوز، طول ورودی و قواعد کسب‌وکار رو به‌جای تو بررسی نمی‌کنه. این مرز رو با مثال بعدی مقایسه کن.

Parameterization separates query structure from data, but it does not check permissions, input length, or business rules for you. Compare that boundary with the next example.

نام جدول مقدار نیستA table name is not a value

MySQL marker رو برای مقدار می‌پذیرد، نه keyword و identifier. پس نام جدول باید در متن statement قرار بگیره؛ اما ورودی خام رو به CONCAT نمی‌دیم. نام رو به یک انتخاب محدود نگاشت می‌کنیم و باقی مقدارها رو همچنان bind می‌کنیم.

MySQL markers bind values, not keywords or identifiers. A table name must therefore appear in the statement text, but raw input must not flow into CONCAT. Map the request to a constrained choice and keep all ordinary values bound.

شناسهٔ مجاز رو انتخاب کنChoose an allowed identifier
SET @requested_source = 'product_price';
SET @table_name = CASE @requested_source
  WHEN 'product_price' THEN 'codenames_deadlock_lab.product_price'
  WHEN 'price_audit' THEN 'codenames_deadlock_lab.price_audit'
  ELSE NULL
END;
SET @sql_text = IF(
  @table_name IS NULL,
  'SELECT ''invalid source'' AS message',
  CONCAT('SELECT * FROM ', @table_name, ' LIMIT 20')
);
PREPARE read_allowed_source FROM @sql_text;
EXECUTE read_allowed_source;
DEALLOCATE PREPARE read_allowed_source;

این نمونه نام رو از دو ثابت انتخاب می‌کنه؛ برای جدول‌هایی با ستون‌های متفاوت، یک SELECT واحد شاید معنای مشترکی نداشته باشه. در برنامهٔ واقعی از enum یا نگاشت کد استفاده کن و schema/table/column رو جداگانه محدود کن. quoteکردن نام به‌تنهایی allowlist نیست.

This maps the request to one of two constants; tables with different columns may not share a meaningful SELECT. In an application, use an enum or controlled mapping and constrain schema, table, and column separately. Quoting a name alone is not an allowlist.

Dynamic SQL در Procedure، نه Function یا TriggerDynamic SQL in a procedure, not a function or trigger

MySQL SQL پویا رو در Stored Procedure می‌پذیرد، اما Function و Trigger اجازهٔ PREPARE و EXECUTE ندارن. یک مرز دیگر هم هست: prepared statement در سطح session است؛ پارامتر و متغیر local routine داخل scope آن نیستند. برای مقدار از user variable استفاده می‌کنیم.

MySQL permits dynamic prepared SQL in stored procedures, but functions and triggers cannot use PREPARE and EXECUTE. There is another boundary: a prepared statement is session-scoped, so routine-local parameters and variables are outside its scope. Use a user variable for the bound value.

نمونهٔ محدود و cleanup صریحA bounded example with explicit cleanup
DELIMITER //
CREATE PROCEDURE codenames_deadlock_lab.find_price(IN p_name VARCHAR(40))
BEGIN
  SET @bound_name = p_name;
  SET @sql_text =
    'SELECT product_id,base_price
     FROM codenames_deadlock_lab.product_price
     WHERE product_name = ?';
  PREPARE price_stmt FROM @sql_text;
  EXECUTE price_stmt USING @bound_name;
  DEALLOCATE PREPARE price_stmt;
END//
DELIMITER ;

CALL codenames_deadlock_lab.find_price('Keyboard');
DROP PROCEDURE codenames_deadlock_lab.find_price;

پارامتر مستقیماً داخل رشتهٔ SQL قرار نگرفت؛ مقدارش bind شد. در routine واقعی، برای مسیر خطا هم cleanup و handler طراحی کن، چون statement آماده‌شده session-wide هست و ممکنه پس از خروج از Procedure باقی بماند.

The parameter was not inserted into the SQL string; its value was bound. In a real routine, design cleanup and an error handler for failure paths too, because the prepared statement is session-wide and can outlive the procedure call.
