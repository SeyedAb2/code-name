برنامه فقط گزارش می‌خواند؛ چرا account آن می‌تونه جدول بسازد؟

The app only reads reports. Why can its account create tables?

بعد از حل اتصال، می‌بینیم account برنامه مجوزهای زیادی دارد. شاید زمانی برای رفع خطا ALL گرفته، یا چند کاربر نیاز مشابهی داشته‌اند و grantها کپی شده‌اند. به‌جای حسابرسی دستی هر account، مجوزها رو با roleهای کوچک و روشن سازمان می‌دیم؛ بعد هم با همان account ثابت می‌کنیم چه کاری مجاز هست و چه کاری نه.

After fixing connectivity, we discover the application account has too many privileges. Perhaps it received ALL to fix an old error, or similar grants were copied across users. We will organize permissions into small, clear roles, then prove what the actual account can and cannot do.

مجوز رو با نیاز شغلی بسنج، نه با عنوان accountMeasure privileges against the account's actual job

حساب report معمولاً باید از چند view بخواند؛ نوشتن schema یا مدیریت user بخشی از کارش نیست. role نام‌دار، مجموعهٔ مجوزی رو قابل‌بررسی و قابل‌استفادهٔ دوباره می‌کنه. اما role فقط وقتی مؤثر هست که به account داده و در session فعال باشه. پس هم grant رو می‌بینیم، هم نقش فعال رو.

A reporting account may need to read a few views; changing schema or managing users is not part of its job. A named role makes a permission set reviewable and reusable. But a role matters only when granted to an account and active in the session. We will inspect both grants and active roles.

مجوز روی role است، اما account باید آن role رو بگیره و نقش در نشست مؤثر باشه.

Privileges belong to the role, but the account must receive it and have it active.

role رو کوچک و قابل‌فهم بسازBuild a narrow, understandable role

نمونه فقط برای schema آزمایشی هست. ابتدا role گزارش‌خوان رو می‌سازیم و فقط SELECT روی view لازم می‌دیم. سپس آن رو به یک account اختصاص می‌دیم، default می‌کنیم و با ورود همان account بررسی می‌کنیم. دسترسی مستقیم account می‌تونه جدا از role باقی بماند؛ پس هر دو لایه رو audit کن.

This example is for a lab schema only. Create a reporting role with SELECT on one required view, grant it to an account, make it a default role, then reconnect as that account. Direct account privileges can exist separately from role grants, so audit both layers.

CREATE ROLE 'report_reader';
GRANT SELECT ON codenames_lab.monthly_report
  TO 'report_reader';
GRANT 'report_reader' TO 'reporter'@'localhost';
SET DEFAULT ROLE 'report_reader'
  TO 'reporter'@'localhost';
SHOW GRANTS FOR 'reporter'@'localhost';
SHOW GRANTS FOR 'reporter'@'localhost'
  USING 'report_reader';

بعد از login مجدد، این‌ها رو با کاربر reporter اجرا کن. برای آزمایش می‌تونی نقش رو موقتاً عوض کنی؛ SET ROLE فقط نشست فعلی رو تغییر می‌ده.

Reconnect as reporter before testing. You can switch roles for an experiment; SET ROLE changes only the current session.

SELECT CURRENT_USER(), CURRENT_ROLE();
SET ROLE NONE;
SELECT CURRENT_ROLE();
SET ROLE DEFAULT;
SELECT CURRENT_ROLE();

دسترسی زیاد رو با REVOKE کم کن؛ بدون حدسReduce excess access with REVOKE, based on evidence

پیش از revoke، از account موردنظر SHOW GRANTS بگیر و dependency برنامه رو مشخص کن. اگه مجوز مستقیم و role هر دو دسترسی می‌دن، حذف یکی ممکنه هیچ اثری نداشته باشه. تغییر رو در محیط آزمایشی اعمال کن، مسیرهای لازم و ممنوع رو با query واقعی بسنج و خروجی نهایی grants رو نگه دار.

Before revoking, capture SHOW GRANTS for the actual account and identify application dependencies. If both a direct grant and a role provide access, removing one may change nothing. Test in a rehearsal environment, verify required and forbidden operations, and retain the resulting grants.

REVOKE CREATE, DROP ON codenames_lab.*
  FROM 'reporter'@'localhost';
SHOW GRANTS FOR 'reporter'@'localhost';

مجوزهای server-wide رو با عجله حذف نکن. نقش مدیریتی، role عضوشده، نقش پیش‌فرض و مجوز مستقیم می‌تونن زنجیره بسازند. هر بار یک تغییر و یک آزمون قابل‌تکرار.

Do not rush to remove server-wide privileges. Administrative roles, nested role grants, defaults, and direct grants can form a chain. Change one thing at a time and run a reproducible test.

اول ببین account الان واقعاً چه مجوزی دارهStart with the account's effective grants

قبل از اینکه GRANT جدید بزنی، وضعیت فعلی رو بخون. خیلی وقت‌ها یه role قدیمی یا grant روی *.* باعث شده account بیشتر از چیزی که فکر می‌کنیم دسترسی داشته باشه.

Before granting anything new, inspect the existing effective privileges. Old roles or broad grants can explain surprising access.

اصل least privilege یعنی نیاز واقعی برنامه رو به operationهای مشخص تبدیل کنی، نه اینکه یه role با اسم قشنگ بسازی و خیال کنی محدود شده.

Least privilege means translating application needs into concrete operations, not trusting the name of a role.

Role رو با رفتار واقعی امتحان کنVerify a role through real behavior

Role وقتی مفیده که مجموعهٔ مجوزها رو قابل‌مدیریت کنه. یه role خواندنی بساز، به account بده، فعالش کن و با query مجاز و query غیرمجاز هر دو رو تست کن.

Roles help manage privilege sets, but they still need behavioral verification. Test both an allowed read and a denied write.

فقط موفق‌شدن SELECT کافی نیست؛ باید failure مورد انتظارِ write هم ثبت بشه. همون failure ثابت می‌کنه مرز دسترسی واقعاً وجود داره.

REVOKE رو هم مثل تغییر production ببینTreat REVOKE as a production change

کم‌کردن privilege می‌تونه سرویس رو بشکنه. قبلش از usage واقعی و مسیرهای برنامه evidence بگیر، بعد revoke رو توی lab/staging اجرا کن و endpointهای مهم رو دوباره تست کن.

Removing privileges can break a service. Capture actual usage, rehearse the revoke, and rerun critical application paths.
