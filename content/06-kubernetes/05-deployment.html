Deployments and ReplicaSets

سه replica می‌خوایم؛ controllerها تلاش می‌کنن واقعیت رو به همین عدد نزدیک کنند.

We want three replicas; controllers keep reconciling reality toward that number.

۱۸تمرینexercises

یک Pod کافی نیست؛ ولی سه تا رو چه کسی نگه می‌داره؟One Pod is not enough; who maintains three?

یه Pod ساختیم و همه‌چیز خوبه؛ تا وقتی که حذفش کنیم. اگه قرار باشه سه نسخه از اپ همیشه زنده باشن، نمی‌خوای هر بار خودت بشمری و جای خالی رو پر کنی. Deployment میاد همین «تعداد و نسخه‌ای که می‌خوام» رو تبدیل می‌کنه به کاری که controller مدام دنبالش می‌کنه.

We created a Pod with kubectl. Delete it and nothing necessarily replaces it. Now we need three replicas, a gradual rollout, and a way to detect a bad image and return safely.

Deployment وضعیت مطلوب رو تعریف می‌کنه. Deployment یک ReplicaSet می‌سازه/مدیریت می‌کنه و ReplicaSet تعداد Podهای مطابق selector رو نگه می‌داره. در rollout نسخهٔ جدید، ReplicaSet تازه ساخته می‌شه و قبلی تا پایان گذار باقی می‌مونه. ReplicaSet رو دستی مدیریت نکن؛ Deployment صاحب تاریخچه و rollout است.

A Deployment declares desired state. It manages a ReplicaSet, which maintains the selected number of Pods. During rollout, a new ReplicaSet appears while the old one remains through the transition. Do not manage ReplicaSets manually; the Deployment owns rollout and revision history.

label و selector اتصال‌اند: selector اشتباه ممکن است Podهای ناخواسته رو بگیرد یا هیچ Podی رو نگیرد.

Labels and selectors are the link: a bad selector may match unintended Pods or none at all.

labels رشتهٔ مالکیت رو می‌سازنLabels form the ownership link

اینجا label دیگه فقط یه برچسب خوشگل نیست. Deployment و ReplicaSet با selector می‌فهمن «کدوم Pod مال منه». اگه این اتصال رو اشتباه بسازی، controller ممکنه هیچ Podی رو نبینه یا بدتر، چیزی رو بگیره که اصلاً مال خودش نیست.

A Deployment’s spec.selector must match template labels. Choose stable identity labels rather than a version label that changes on each rollout. A manually created Pod with matching labels may be counted by the ReplicaSet.

replicas: 3 رو اعمال کن و kubectl get deployment,replicaset,pods -l app=demo رو ببین. AVAILABLE باید پس از آماده‌شدن به 3 برسد؛ CREATED فقط تعداد objectهای ایجادشده. اگه Pending ماند، describe و eventها رو بخوان.

Apply replicas: 3 and inspect the Deployment, ReplicaSet, and Pods with a selector. AVAILABLE should reach 3 when ready; CREATED only reports object count. If Pods stay Pending, inspect describe and events.

kubectl apply -f deployment.yaml -n lab
kubectl get deployment,rs,pods -l app=demo -n lab
kubectl scale deployment/demo --replicas=4 -n lab

scale درخواست مطلوب رو تغییر می‌ده ولی منبع حقیقت پایدار فایل manifest است. برای کار تیمی مقدار spec رو هم در Git اصلاح کن تا apply بعدی اون رو به عدد قدیم برنگرداند.

scale changes live desired state, but the manifest is the durable source for a team. Update spec in Git too, or a later apply may restore the old count.

نسخهٔ تازه رو با rollout ببینObserve a rolling update

نسخه تازه رو مثل تعویض یک لامپ نبین که قبلی خاموش شه و جدیدی روشن. rollout یه گذاره؛ مدتی قدیمی و جدید کنار هم هستن. بیا از روی ReplicaSetها و وضعیت rollout ببینیم Kubernetes دقیقاً چطور این گذار رو جلو می‌بره و کِی باید برگردیم.

Change the image tag and run rollout status for the Deployment. Watch ReplicaSets and Pods to see the transition. Inspect revision history; it records Pod template changes, not every scale-only update.

maxSurge و maxUnavailable کنترل می‌کنن هنگام rolling update چند Pod بیشتر یا کمتر از desired مجاز است. مقادیر default و گردکردن درصدی به تنظیم و اندازهٔ replica وابسته‌اند؛ آن‌ها رو بخوان و برای lab صریح تعیین کن. ظرفیت node، readiness و زمان pull image تعیین می‌کنن گذار چه‌قدر طول بکشد.

maxSurge and maxUnavailable bound how many Pods may exceed or fall below desired count during a rolling update. Defaults and percentage rounding depend on configuration and replica count; inspect them and set explicit lab values. Node capacity, readiness, and image-pull time affect rollout duration.

شکست عمدی: tag ناموجود رو به‌عنوان نسخهٔ v2 اعمال کن. rollout ممکن است گیر کند، ولی ReplicaSet قبلی بخشی از Podها رو نگه می‌داره طبق strategy و سلامتشان. get/describe/events خطای pull رو نشان می‌ده. بعد rollout undo و status رو اجرا کن؛ باید image قبلی برگردد، ولی این به معنی rollback دیتابیس نیست.

Deliberately apply a nonexistent image tag as v2. The rollout may stall while the old ReplicaSet retains Pods according to strategy and readiness. get/describe/events should expose the pull error. Run rollout undo and verify status and image; this does not roll back a database.

kubectl rollout status deployment/demo -n lab
kubectl rollout history deployment/demo -n lab
kubectl rollout undo deployment/demo -n lab
kubectl rollout status deployment/demo -n lab

Deployment نسخه رو نگه می‌داره؛ Service مسیر می‌دهA Deployment manages versions; a Service provides access

Deployment می‌گه چند Pod با چه نسخه‌ای می‌خوای و سعی می‌کنه همون رو نگه داره. ولی هنوز یه مشکل داریم: Podها عوض می‌شن و IPها هم باهاشون. فصل بعد Service رو می‌سازیم تا کلاینت مجبور نباشه دنبال Podها بدوه.

A Deployment manages replica intent and template; a ReplicaSet maintains one template generation; Pods run the workload. Clients should not chase changing Pod IPs. Next we add a Service for stable access to selected Pods.
