Deployments and ReplicaSets

سه replica می‌خواهیم؛ controllerها تلاش می‌کنند واقعیت را به همین عدد نزدیک کنند.

We want three replicas; controllers keep reconciling reality toward that number.

یک Pod کافی نیست؛ اما سه تا را چه کسی نگه می‌دارد؟One Pod is not enough; who maintains three?

با kubectl یک Pod ساختیم. اگر آن را حذف کنی، کسی لزوماً جایش را پر نمی‌کند. حالا سه replica می‌خواهیم، نسخهٔ جدید را تدریجی منتشر می‌کنیم و اگر image اشتباه بود باید زود بفهمیم و برگردیم.

We created a Pod with kubectl. Delete it and nothing necessarily replaces it. Now we need three replicas, a gradual rollout, and a way to detect a bad image and return safely.

Deployment وضعیت مطلوب را تعریف می‌کند. Deployment یک ReplicaSet می‌سازد/مدیریت می‌کند و ReplicaSet تعداد Podهای مطابق selector را نگه می‌دارد. در rollout نسخهٔ جدید، ReplicaSet تازه ساخته می‌شود و قبلی تا پایان گذار باقی می‌ماند. ReplicaSet را دستی مدیریت نکن؛ Deployment صاحب تاریخچه و rollout است.

A Deployment declares desired state. It manages a ReplicaSet, which maintains the selected number of Pods. During rollout, a new ReplicaSet appears while the old one remains through the transition. Do not manage ReplicaSets manually; the Deployment owns rollout and revision history.

label و selector اتصال‌اند: selector اشتباه ممکن است Podهای ناخواسته را بگیرد یا هیچ Podی را نگیرد.

Labels and selectors are the link: a bad selector may match unintended Pods or none at all.

labels رشتهٔ مالکیت را می‌سازندLabels form the ownership link

در Deployment، spec.selector باید با labelهای template سازگار باشد. selector نمی‌تواند با تغییر Podها عوض شود؛ labelهایی انتخاب کن که هویت workload را توضیح دهند، نه نسخه‌ای که در هر rollout عوض می‌شود. اگر Pod دستی همان label را بگیرد، ممکن است داخل مجموعهٔ ReplicaSet شمرده شود.

A Deployment’s spec.selector must match template labels. Choose stable identity labels rather than a version label that changes on each rollout. A manually created Pod with matching labels may be counted by the ReplicaSet.

replicas: 3 را اعمال کن و kubectl get deployment,replicaset,pods -l app=demo را ببین. AVAILABLE باید پس از آماده‌شدن به 3 برسد؛ CREATED فقط تعداد objectهای ایجادشده است. اگر Pending ماند، describe و eventها را بخوان.

Apply replicas: 3 and inspect the Deployment, ReplicaSet, and Pods with a selector. AVAILABLE should reach 3 when ready; CREATED only reports object count. If Pods stay Pending, inspect describe and events.

kubectl apply -f deployment.yaml -n lab
kubectl get deployment,rs,pods -l app=demo -n lab
kubectl scale deployment/demo --replicas=4 -n lab

scale درخواست مطلوب را تغییر می‌دهد اما منبع حقیقت پایدار فایل manifest است. برای کار تیمی مقدار spec را هم در Git اصلاح کن تا apply بعدی آن را به عدد قدیم برنگرداند.

scale changes live desired state, but the manifest is the durable source for a team. Update spec in Git too, or a later apply may restore the old count.

نسخهٔ تازه را با rollout ببینObserve a rolling update

image tag را تغییر بده و kubectl rollout status deployment/demo -n lab را اجرا کن. برای مشاهدهٔ روند، kubectl get rs,pods -l app=demo -w بزن. revision history را با rollout history ببین. هر revision فقط تغییرات template را ثبت می‌کند؛ تغییر سادهٔ replicas لزوماً revision تازه نمی‌سازد.

Change the image tag and run rollout status for the Deployment. Watch ReplicaSets and Pods to see the transition. Inspect revision history; it records Pod template changes, not every scale-only update.

maxSurge و maxUnavailable کنترل می‌کنند هنگام rolling update چند Pod بیشتر یا کمتر از desired مجاز است. مقادیر default و گردکردن درصدی به تنظیم و اندازهٔ replica وابسته‌اند؛ آن‌ها را بخوان و برای lab صریح تعیین کن. ظرفیت node، readiness و زمان pull image تعیین می‌کنند گذار چه‌قدر طول بکشد.

maxSurge and maxUnavailable bound how many Pods may exceed or fall below desired count during a rolling update. Defaults and percentage rounding depend on configuration and replica count; inspect them and set explicit lab values. Node capacity, readiness, and image-pull time affect rollout duration.

شکست عمدی: tag ناموجود را به‌عنوان نسخهٔ v2 اعمال کن. rollout ممکن است گیر کند، اما ReplicaSet قبلی بخشی از Podها را نگه می‌دارد طبق strategy و سلامتشان. get/describe/events خطای pull را نشان می‌دهد. بعد rollout undo و status را اجرا کن؛ باید image قبلی برگردد، اما این به معنی rollback دیتابیس نیست.

Deliberately apply a nonexistent image tag as v2. The rollout may stall while the old ReplicaSet retains Pods according to strategy and readiness. get/describe/events should expose the pull error. Run rollout undo and verify status and image; this does not roll back a database.

kubectl rollout status deployment/demo -n lab
kubectl rollout history deployment/demo -n lab
kubectl rollout undo deployment/demo -n lab
kubectl rollout status deployment/demo -n lab

Deployment نسخه را نگه می‌دارد؛ Service مسیر می‌دهدA Deployment manages versions; a Service provides access

Deployment تعداد replica و template را مدیریت می‌کند؛ ReplicaSet نسل مشخصی از template را نگه می‌دارد؛ Podها اجرا را انجام می‌دهند. اما client نباید دنبال IP متغیر Podها بگردد. فصل بعد Service را می‌سازیم تا دسترسی پایدار به مجموعهٔ Podهای انتخاب‌شده داشته باشیم.

A Deployment manages replica intent and template; a ReplicaSet maintains one template generation; Pods run the workload. Clients should not chase changing Pod IPs. Next we add a Service for stable access to selected Pods.
