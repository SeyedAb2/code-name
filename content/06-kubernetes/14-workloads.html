When a Deployment is the wrong shape.

همه‌چیز replica دائمی نیستNot every workload is a set of permanent replicas

تا اینجا بیشتر چیزها رو با Deployment دیدیم، ولی همه کارها «چند replica بی‌هویت که همیشه زنده باشن» نیستن. یه log agent باید روی هر node باشه، یه migration باید یه بار تا موفقیت اجرا بشه و دیتابیس شاید هویت و storage مخصوص هر replica بخواد. پس controller رو از روی چرخه عمر کار انتخاب می‌کنیم.

So far Deployments have kept web servers running. Now we need a node-local cache on each machine, a one-time migration that retries to completion, and database replicas with stable identities and storage. One controller may be the wrong fit for these different lifecycles.

انتخاب رو با این سؤال شروع کن: workload باید همیشه replicaهای بی‌هویت داشته باشه، برای هر node نمونه‌ای بسازد، یا کاری رو تمام کند و خارج بشه؟ جواب، controller رو راهنمایی می‌کنه.

Start with the lifecycle question: should the workload maintain interchangeable replicas, run one copy per node, or finish a task and exit? The answer guides the controller choice.

controller رفتار چرخهٔ عمر رو تعریف می‌کنه؛ انتخاب اشتباه ممکن است کار رو تکرار یا بی‌هویت کند.

A controller defines lifecycle behavior; the wrong choice can repeat work or erase required identity.

StatefulSet هویت رو نگه می‌داره، نه سلامت عملیات روStatefulSet preserves identity, not operational safety

StatefulSet اسم و ترتیب پایدار می‌ده و می‌تونه برای هر replica PVC جدا بسازه؛ ولی از دیتابیس آدم عاقل‌تری نمی‌سازه. replication، backup، failover و سازگاری داده هنوز مسئله‌های خود برنامه و عملیاتن.

StatefulSet fits Pods needing stable ordinal identity, ordered startup/termination, or per-replica storage. A headless Service commonly provides per-Pod DNS identity, and volumeClaimTemplates create separate claims. Stable names and persistent claims do not automate database backup, replication, safe failover, or schema upgrades.

DaemonSet: یک نمونه روی هر node واجد شرایطDaemonSet: one Pod on each eligible node

log agent، node exporter یا network helper می‌تونه روی nodeهای منتخب یک Pod لازم داشته باشه. DaemonSet نمونه‌ها رو بر اساس nodeها می‌سازه؛ taint/toleration، selector و policy تعیین می‌کنن کدوم node واجد شرایط است. این به معنی دقیقاً یک Pod روی تک‌تک nodeها در هر لحظه نیست. Deployment با replicas=N تعداد رو نگه می‌داره ولی ذاتاً «یکی برای هر node» نمی‌گه.

A log agent, node exporter, or networking helper may need a Pod on selected nodes. DaemonSet places Pods according to node eligibility; taints/tolerations, selectors, and policy determine where. It does not mean exactly one on every node at all times. A Deployment with N replicas maintains a count, not per-node coverage.

Job تمام می‌شه؛ CronJob زمان می‌دهA Job completes; a CronJob schedules it

Job برای کاریه که باید تموم بشه؛ CronJob فقط زمان‌بندی ساخت همون Jobهاست. اگه کاری باید همیشه زنده بمونه، Job انتخاب اشتباهیه. اگه کاری باید یک بار تموم بشه، Deployment هم ممکنه هی دوباره اجراش کنه و دردسر بسازه.

A Job tracks successful completions and retry/backoff policy; a finished process should stay complete, not restart forever like a Deployment. CronJob creates Jobs on a schedule. concurrencyPolicy can Allow, Forbid, or Replace overlapping runs. Schedule timing depends on timezone/version/controller reconciliation; it is not a precise-second guarantee. Consider missed runs, suspension, and job history too.

شکست عمدی این فصل: node agent رو با Deployment دو replica مدل کن؛ ممکن است هر دو روی یک node بنشینند و node دیگر بدون agent بماند. یا migration پایان‌پذیر رو با Deployment اجرا کن؛ پس از موفقیت دوباره اجرا می‌شه. ابتدا placement/completion رو از get/describe ببین، بعد controller درست رو انتخاب کن.

Deliberate mismatch: model a node agent as a two-replica Deployment; both may land on one node while another has none. Or run a finite migration as a Deployment, which restarts it after success. Inspect placement/completion first, then choose the matching controller.

چهار workload رو روی cluster آزمایشی مقایسه کنCompare four workload shapes in a disposable cluster

در namespace lab برای StatefulSet یک image ساده و headless Service بساز و نام Podها رو ببین؛ claim واقعی مهم رو وارد نکن. DaemonSet رو با node selector مناسب اجرا و تعدادش رو با nodeهای eligible بسنج. Job یک command محدود مثل چاپ و exit اجرا کند؛ status succeeded رو ببین. CronJob زمان‌بندی آزمایشی با concurrencyPolicy مشخص و تاریخچهٔ کوتاه بساز.

In namespace lab, create a StatefulSet with a simple image and headless Service, and inspect Pod names; do not attach valuable data. Run a DaemonSet with a suitable node selector and compare its Pods with eligible nodes. Let a Job print and exit, then inspect succeeded status. Create a CronJob with a test schedule, explicit concurrencyPolicy, and short history.

در هر مورد apply و get به‌تنهایی کافی نیست: describe/events رو بخوان؛ DaemonSet selector/toleration، Job backoff/completion، CronJob schedule و controller delay رو ببین. در پایان jobهای تکراری رو suspend/پاک کن و namespace آزمایش رو حذف کن.

For each, apply/get is insufficient: inspect describe/events, DaemonSet selectors/tolerations, Job completion/backoff, CronJob schedule, and controller delay. At the end suspend/delete recurring jobs and remove the lab namespace.

controller باید با پایان کار هماهنگ باشهThe controller should match the work’s lifecycle

اسم controller مهم نیست؛ چرخه عمر مهمه. بپرس این کار باید همیشه زنده بمونه، روی هر node باشه، هویت پایدار داشته باشه یا یه بار تموم بشه؟ جواب معمولاً controller درست رو جلو پات می‌ذاره.

Use Deployment for interchangeable replicas, StatefulSet for stable identities/claims, DaemonSet for each eligible node, and Job/CronJob for finite work. StatefulSet does not secure a database, and CronJob does not guarantee a valid backup. Next we package configurable, versioned manifests with Helm.
