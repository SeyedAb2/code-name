When a Deployment is the wrong shape.

همه‌چیز replica دائمی نیستNot every workload is a set of permanent replicas

تا حالا Deploymentها web server را زنده نگه می‌داشتند. حالا سه نیاز تازه داریم: cache node-local روی هر ماشین، migration یک‌باره تا موفقیت، و replicaهای database با هویت/volume مشخص. یک controller برای همهٔ این‌ها ممکن است رفتار اشتباه بسازد.

So far Deployments have kept web servers running. Now we need a node-local cache on each machine, a one-time migration that retries to completion, and database replicas with stable identities and storage. One controller may be the wrong fit for these different lifecycles.

انتخاب را با این سؤال شروع کن: workload باید همیشه replicaهای بی‌هویت داشته باشد، برای هر node نمونه‌ای بسازد، یا کاری را تمام کند و خارج شود؟ جواب، controller را راهنمایی می‌کند.

Start with the lifecycle question: should the workload maintain interchangeable replicas, run one copy per node, or finish a task and exit? The answer guides the controller choice.

controller رفتار چرخهٔ عمر را تعریف می‌کند؛ انتخاب اشتباه ممکن است کار را تکرار یا بی‌هویت کند.

A controller defines lifecycle behavior; the wrong choice can repeat work or erase required identity.

StatefulSet هویت را نگه می‌دارد، نه سلامت عملیات راStatefulSet preserves identity, not operational safety

StatefulSet برای Podهایی است که هویت پایدار/ordinal، ترتیب startup/termination یا storage مستقل برای هر replica می‌خواهند. معمولاً headless Service هویت DNS هر Pod را فراهم می‌کند، و volumeClaimTemplates claim جدا می‌سازد. اسم ثابت و PVC ماندگار database backup، replication درست، failover امن یا upgrade schema را خودکار نمی‌کند.

StatefulSet fits Pods needing stable ordinal identity, ordered startup/termination, or per-replica storage. A headless Service commonly provides per-Pod DNS identity, and volumeClaimTemplates create separate claims. Stable names and persistent claims do not automate database backup, replication, safe failover, or schema upgrades.

DaemonSet: یک نمونه روی هر node واجد شرایطDaemonSet: one Pod on each eligible node

log agent، node exporter یا network helper می‌تواند روی nodeهای منتخب یک Pod لازم داشته باشد. DaemonSet نمونه‌ها را بر اساس nodeها می‌سازد؛ taint/toleration، selector و policy تعیین می‌کنند کدام node واجد شرایط است. این به معنی دقیقاً یک Pod روی تک‌تک nodeها در هر لحظه نیست. Deployment با replicas=N تعداد را نگه می‌دارد ولی ذاتاً «یکی برای هر node» نمی‌گوید.

A log agent, node exporter, or networking helper may need a Pod on selected nodes. DaemonSet places Pods according to node eligibility; taints/tolerations, selectors, and policy determine where. It does not mean exactly one on every node at all times. A Deployment with N replicas maintains a count, not per-node coverage.

Job تمام می‌شود؛ CronJob زمان می‌دهدA Job completes; a CronJob schedules it

Job تعداد completion موفق را دنبال می‌کند و failure policy/backoff دارد؛ process تمام‌شده باید در پایان بماند، نه اینکه مثل Deployment دوباره همیشه اجرا شود. CronJob بر اساس schedule Job می‌سازد. concurrencyPolicy می‌تواند اجراهای هم‌زمان را Allow، Forbid یا Replace کند. schedule به time zone/نسخه و controller timing وابسته است؛ به‌معنی اجرای دقیق ثانیه‌ای نیست. missed run، suspend و تاریخچهٔ jobها را هم در نظر بگیر.

A Job tracks successful completions and retry/backoff policy; a finished process should stay complete, not restart forever like a Deployment. CronJob creates Jobs on a schedule. concurrencyPolicy can Allow, Forbid, or Replace overlapping runs. Schedule timing depends on timezone/version/controller reconciliation; it is not a precise-second guarantee. Consider missed runs, suspension, and job history too.

شکست عمدی این فصل: node agent را با Deployment دو replica مدل کن؛ ممکن است هر دو روی یک node بنشینند و node دیگر بدون agent بماند. یا migration پایان‌پذیر را با Deployment اجرا کن؛ پس از موفقیت دوباره اجرا می‌شود. ابتدا placement/completion را از get/describe ببین، بعد controller درست را انتخاب کن.

Deliberate mismatch: model a node agent as a two-replica Deployment; both may land on one node while another has none. Or run a finite migration as a Deployment, which restarts it after success. Inspect placement/completion first, then choose the matching controller.

چهار workload را روی cluster disposable مقایسه کنCompare four workload shapes in a disposable cluster

در namespace lab برای StatefulSet یک image ساده و headless Service بساز و نام Podها را ببین؛ claim واقعی مهم را وارد نکن. DaemonSet را با node selector مناسب اجرا و تعدادش را با nodeهای eligible بسنج. Job یک command محدود مثل چاپ و exit اجرا کند؛ status succeeded را ببین. CronJob زمان‌بندی آزمایشی با concurrencyPolicy مشخص و تاریخچهٔ کوتاه بساز.

In namespace lab, create a StatefulSet with a simple image and headless Service, and inspect Pod names; do not attach valuable data. Run a DaemonSet with a suitable node selector and compare its Pods with eligible nodes. Let a Job print and exit, then inspect succeeded status. Create a CronJob with a test schedule, explicit concurrencyPolicy, and short history.

در هر مورد apply و get به‌تنهایی کافی نیست: describe/events را بخوان؛ DaemonSet selector/toleration، Job backoff/completion، CronJob schedule و controller delay را ببین. در پایان jobهای تکراری را suspend/پاک کن و namespace آزمایش را حذف کن.

For each, apply/get is insufficient: inspect describe/events, DaemonSet selectors/tolerations, Job completion/backoff, CronJob schedule, and controller delay. At the end suspend/delete recurring jobs and remove the lab namespace.

controller باید با پایان کار هماهنگ باشدThe controller should match the work’s lifecycle

Deployment برای replicaهای بی‌هویت، StatefulSet برای هویت/claimهای پایدار، DaemonSet برای هر node واجد شرایط و Job/CronJob برای کار پایان‌پذیر انتخاب می‌شوند. StatefulSet پایگاه‌داده را امن نمی‌کند و CronJob هم backup معتبر را تضمین نمی‌کند. فصل بعد Helm را می‌بینیم: چطور manifestهای یک برنامه را قابل‌پیکربندی و قابل‌نسخه‌گذاری بسته‌بندی کنیم.

Use Deployment for interchangeable replicas, StatefulSet for stable identities/claims, DaemonSet for each eligible node, and Job/CronJob for finite work. StatefulSet does not secure a database, and CronJob does not guarantee a valid backup. Next we package configurable, versioned manifests with Helm.
