One Deployment and one Service on a local cluster.

۷۰دقیقهminutes
۵ایستگاهcheckpoints

مأموریت: Running کافی نیستMission: Running is not enough

اینجا دیگه تمرین تک‌دستوری نداریم. مأموریتت اینه: یه اپ نسخه‌دار رو روی cluster بالا بیاری، از Service بهش برسی، یه Pod رو عمداً بکشی و با مدرک نشون بدی Deployment جاش رو پر کرده. بعد نسخه رو عوض می‌کنی و یه خرابی واقعی رو از روی شواهد پیدا می‌کنی.

Run a versioned app on a local cluster, reach it through a Service, deliberately delete a Pod, and prove the Deployment replaces it. Update the version, then diagnose a selector or image fault from evidence. The mission is incomplete until a fresh request returns the expected result.

از kind، minikube یا cluster محلی موجود استفاده کن. پیش از هر mutation context رو بخوان. workload فقط دادهٔ ساختگی داره؛ cluster production یا namespace مشترک تیم رو هدف نگیر.

Use kind, minikube, or an existing local cluster. Read the context before every mutation. Use synthetic data only; do not target production or a shared team namespace.

Service labelها رو انتخاب می‌کنه؛ Deployment تعداد/نسخهٔ Podها رو نگه می‌داره.

The Service selects by labels; the Deployment maintains Pod count and version.

شرط‌های قبولیAcceptance criteria

قبل از شروع چند خط قرمز داریم: cluster محلی یا آزمایشی، namespace جدا، داده ساختگی و نگاه‌کردن به context قبل از هر کار مخرب. هدف این پروژه یادگرفتن رفتار سیستم هست، نه شجاعت روی production.

Two or three Ready replicas, a precise selector, a ClusterIP Service, and a versioned response through localhost port-forward. Deleting a Pod must produce a replacement; an image update must create a new rollout. Logs must be available, and one deliberate fault must be diagnosed from get/describe/events/logs. Running alone does not pass.

پنج ایستگاه مأموریتFive mission checkpoints

۱ — cluster درست را انتخاب کن

پروژه رو مثل یه مأموریت چند ایستگاهی برو. هر ایستگاه فقط وقتی تمومه که شاهد داشته باشی: object ساخته شده، درخواست جواب داده، جایگزین اتفاق افتاده یا rollout واقعاً آماده شده. «به نظرم کار کرد» مدرک حساب نمی‌شه.

Record context, nodes, and namespace lab. Evidence: current-context and get nodes. If no cluster exists, create a local one using its official guide before applying manifests.

راهنمایی

اسم context کافی نیست؛ مطمئن شو همان local cluster است و credentials دسترسی admin ناخواسته به محیط دیگری نمی‌دهند.

۲ — app و Deployment

image نسخه‌دار مثل http-echo با متن v1 انتخاب کن. Deployment دو replica، label app=hello و port درست داشته باشه. get/describe و rollout status رو ثبت کن؛ API accept و Pod Ready دو شاهد جدا هستن.

Choose a versioned image such as an HTTP echo server returning v1. Create a two-replica Deployment with app=hello and the correct port. Record get/describe and rollout status; API acceptance and Pod readiness are different evidence.

hint

اگر container شروع نشد، Events/log را بخوان؛ image/args را از حدس تغییر نده.

۳ — Service و درخواست

Service selector رو با label Pod جور کن و پورت app رو targetPort بده. port-forward موقت اجرا و پاسخ v1 رو بخوان. مدرک: Service، EndpointSlice و response؛ این ثابت می‌کنه مسیر آزمایش کار کرده، نه exposure عمومی.

Match the Service selector to Pod labels and set the app’s targetPort. Use a temporary port-forward and read v1. Evidence: Service, EndpointSlice, and response; this proves the lab path, not public exposure.

۴ — خودترمیمی و rollout

یکی از Podهای Deployment رو delete کن، هم‌زمان get pods -w ببین و name/IP جدید رو ثبت کن. سپس image/text رو به v2 تغییر بده؛ rollout status و پاسخ v2 رو از Service بررسی کن. جایگزین ممکن است هویت شبکهٔ تازه داشته باشه.

Delete one Deployment Pod while watching get pods -w; record the new name/IP. Change image/text to v2, then verify rollout and v2 response through the Service. A replacement may have a new network identity.

معیار اثبات

Desired replicas دوباره حاضر باشند و درخواست از Service نسخهٔ تازه را برگرداند؛ صرفاً Pod تازه دیدن کافی نیست.

۵ — selector یا image خراب

برای یک بار Service selector رو غلط یا image tag رو ناموجود کن. پیش از اصلاح get، describe، events و logs رو ثبت کن. علت رو مشخص کن، فقط همان مقدار رو درست کن و rollout/EndpointSlice/request رو دوباره بررسی کن. runbook کوتاه رو تحویل بده.

Once, break the Service selector or use a nonexistent image tag. Capture get, describe, events, and logs before fixing. Identify the cause, change only that value, then verify rollout/EndpointSlice/request again. Hand off a short runbook.

راهنمای تشخیص

Service بدون endpoint معمولاً selector/labels است؛ ImagePullBackOff را در Pod Events ببین. علامت را با علت یکی نگیر.

راه‌حل مرجع و تحویلReference solution and handoff

هستهٔ manifest
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  namespace: lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: hello
  template:
    metadata:
      labels:
        app: hello
    spec:
      containers:
      - name: app
        image: hashicorp/http-echo:1.0.0
        args: ["-text=v1"]
        ports:
        - containerPort: 5678
---
apiVersion: v1
kind: Service
metadata:
  name: hello
  namespace: lab
spec:
  selector:
    app: hello
  ports:
  - port: 80
    targetPort: 5678

راه‌حل مرجع رو آخر کار بخون، نه اولش. اول خودت مسیر رو برو و هرجا گیر کردی از event و log سؤال بپرس. جواب مرجع برای مقایسه مدل ذهنیه، نه برای کپی‌کردن commandها.

Sequence: context → namespace → apply → rollout/get/describe → port-forward request → delete Pod and observe replacement → update image and request v2 → inject fault, capture evidence, fix and verify → clean up only namespace lab. Image availability can change; verify the official registry and tag before the lab.

در تحویل بنویس چند replica Ready بود، Service چه endpointی داشت، Pod حذف‌شده چطور جایگزین شد، نسخهٔ زنده چیست و چه شاهدی خطای عمدی رو توضیح داد. فصل بعد این الگو رو به سه سرویس و یک Ingress گسترش می‌ده.

Handoff the Ready replica count, Service endpoints, replacement evidence, live version, and diagnosis of the deliberate fault. Next we extend this pattern to three services behind an Ingress.
