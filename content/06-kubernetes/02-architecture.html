یک apply؛ درخواست کجا می‌ره؟One apply: where does the request go?

یک kubectl apply زدی و ترمینال گفت درخواست قبول شد. خب بعدش چی؟ فایل YAML که بال درنمیاره بره روی یک node بنشینه. بیا مسیرش رو مثل یک بسته دنبال کنیم؛ از لحظه‌ای که به API می‌رسه تا جایی که آخرش یک process داخل container اجرا می‌شه.

kubectl apply returned, but the app is not running yet. YAML is not copied directly to a node; the API server and separate components reconcile desired state toward execution.

با یک کلاستر محلی آزمایشی کار کن. قبل از هر تغییر kubectl config current-context رو ببین. خروجی context انتخاب‌شده رو نشان می‌ده، نه اینکه مقصد حتماً امن یا production باشه.

Use a disposable local cluster. Before changing anything, check kubectl config current-context. It shows the selected context, not that the destination is safe or production-ready.

Control plane هماهنگ می‌کنه؛ node اجرا می‌کنهThe control plane coordinates; nodes run workloads

برای اینکه معماری کلاستر تو ذهنت شلوغ نشه، فعلاً دو طرف قصه رو نگه دار: control plane تصمیم و هماهنگی، node اجرا. بقیه اسم‌ها رو هم یکی‌یکی سر جاشون می‌ذاریم، نه اینکه یک لیست حفظ کنیم.

The API server is the Kubernetes request front door. etcd backs cluster data and is used by the API server; ordinary users should not edit it directly. The controller manager runs control loops that reconcile desired and current state. The scheduler selects a suitable node for an unassigned Pod.

روی هر node، kubelet با API هماهنگ می‌شه تا workloadهای سپرده‌شده اجرا بشن. container runtime خود containerها رو اجرا می‌کنه. توزیع کلاستر تعیین می‌کنه control plane کجا و چطور اجرا بشه؛ بعضی جزءها static Pod هستن و در محیط managed ممکن است بیرون دسترس کاربر باشن.

On each node, kubelet coordinates with the API to ensure assigned workloads run; the container runtime starts containers. The cluster distribution determines where and how control-plane components run. Some are static Pods, while managed environments may hide them from user access.

kubectl get nodes -o wide و kubectl get pods -n kube-system رو امتحان کن. نام componentها و اینکه به‌شکل Pod دیده بشن به kind/minikube/provider بستگی داره؛ نبودن یک اسم مورد انتظار ثابت نمی‌کنه وظیفه‌ای غایب است.

Try kubectl get nodes -o wide and kubectl get pods -n kube-system. Component names and whether they appear as Pods vary by kind, minikube, and provider; a missing expected name does not prove a function is absent.

از apply تا process، یک زنجیرهٔ همکاریFrom apply to process: components cooperate

حالا قطعه‌ها رو به هم وصل کنیم. درخواست وارد API server می‌شه، وضعیت ذخیره می‌شه، scheduler برای Pod جا پیدا می‌کنه و kubelet روی node کار رو جلو می‌بره. هر مرحله یه شاهد از خودش می‌ذاره؛ همین شاهدها بعداً موقع عیب‌یابی نجاتمون می‌دن.

The API server validates and records the object. Controllers reconcile required objects; the scheduler places unassigned Pods; kubelet receives the specification and asks the runtime to start containers. Controllers coordinate through the API; this is not a linear script where every component runs once.

etcd backing store است و scheduler مستقیماً به runtime فرمان نمی‌ده.

etcd is a backing store; the scheduler does not directly command the runtime.

شبکهٔ Pod با Service یکی نیستPod networking differs from a Service

CNI ابزار و قراردادی برای پیاده‌سازی شبکهٔ Podهاست. Service راه پایدار دسترسی به مجموعه‌ای از Podها فراهم می‌کنه. kube-proxy در بسیاری کلاسترها بخش‌هایی از Service رو با قواعد شبکه اجرا می‌کنه، ولی بعضی network pluginها proxy هم‌ارز دارن و kube-proxy لازم نیست. پس اون رو جزء همگانی فرض نکن.

CNI is a plugin/interface for implementing Pod networking. A Service provides stable access to a set of Pods. kube-proxy implements parts of Service behavior in many clusters, but some network plugins provide equivalent proxying, so kube-proxy is not universal.

kubectl get nodes به‌تنهایی کارکرد شبکه رو ثابت نمی‌کنه؛ برای مشکل ارتباط باید plugin، Pod address، policy و log رو بررسی کرد. جزئیات network plugin از توزیع و انتخاب اپراتور وابسته است.

kubectl get nodes alone does not prove networking works. For connectivity problems inspect the plugin, Pod address, policies, and logs. Network plugin behavior depends on distribution and operator choice.

یک manifest آزمایشی و eventهایشA small manifest and its events

در کلاستر آزمایشی، فایل arch-demo.yaml رو با Deployment دو replica بساز. هدف شناخت مسیر کنترل است، نه درس عمیق Pod. قبل از apply context رو چک کن.

In a disposable cluster, create a two-replica Deployment in arch-demo.yaml. The goal is control-flow, not an in-depth Pod lesson. Check context before applying.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: arch-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: arch-demo
  template:
    metadata:
      labels:
        app: arch-demo
    spec:
      containers:
      - name: web
        image: nginx:1.27

kubectl apply پاسخ API رو می‌ده، ولی ممکن است image هنوز pull نشده باشه. با kubectl get deployment,pods و kubectl describe pod NAME، replica، node assignment، condition و Events رو دنبال کن. Scheduled/Pulled/Created/Started سرنخ‌اند؛ نه تضمین پاسخ HTTP.

kubectl apply reports an API response, but the image may not yet be pulled. Use kubectl get deployment,pods and kubectl describe pod NAME to inspect replicas, node assignment, conditions, and events. Scheduled/Pulled/Created/Started are clues, not proof of HTTP behavior.

حالا یک Pod متعلق به این Deployment رو حذف کن و در ترمینال دیگر kubectl get pods -w اجرا کن. controller باید جایگزین بسازد؛ نام و IP ممکن است عوض بشه. owner reference و تعداد replica رو ببین. این کار رو روی workload آزمایشی انجام بده؛ Pod مستقل controller والد نداره و ممکن است برنگردد.

Delete a Pod owned by the Deployment while watching kubectl get pods -w in another terminal. The controller should replace it; name and IP may change. Inspect owner reference and replica count. Use only a disposable workload; a standalone Pod has no parent controller and may remain deleted.

kubectl get pods -l app=arch-demo -w
kubectl delete pod POD_NAME
kubectl get events --sort-by=.metadata.creationTimestamp

اگه Pod تازه Pending ماند یا image pull نشد، API درخواست رو پذیرفته ولی اجرای workload گیر کرده. «کنترلر خواسته‌اش رو ثبت کرد» با «کاربر سرویس سالم گرفت» فرق داره؛ describe و eventها قدم بعدی‌اند.

If the new Pod stays Pending or cannot pull the image, the API accepted intent but execution is stuck. “The controller recorded its desired result” differs from “users received a healthy service”; inspect describe output and events.

هر لایه شاهد خودش رو دارهEach layer has its own evidence

اگه معماری رو فقط به‌صورت اسم حفظ کنی، اولین خرابی همه‌چیز قاطی می‌شه. چیزی که می‌خوایم اینه: بدونیم درخواست الان دست کدوم لایه‌ست و برای هر لایه کجا باید دنبال شاهد بگردیم. از فصل بعد این زنجیره رو با خود Pod لمس می‌کنیم.

One apply does not perform everything at once. API, controllers, scheduler, kubelet, runtime, and networking each own part of the path; diagnose each failure with evidence from that layer. Next we focus on the Pod, the smallest unit Kubernetes schedules.
