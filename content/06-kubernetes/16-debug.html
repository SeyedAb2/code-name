Debugging: CrashLoopBackOff, Pending, ImagePullBackOff

هر وضعیت سرنخی داره؛ هیچ‌کدوم به‌تنهایی تشخیص کامل نیست.

Every status is a clue; none is a full diagnosis by itself.

۸۵دقیقهminutes
۱۸تمرینexercises

اولین واکنش: Pod رو پاک نکنFirst response: do not delete the Pod

پیام میاد: «اپ بالا نیست». سه Pod جلوت هستن: یکی CrashLoopBackOff، یکی Pending و یکی ImagePullBackOff. اولین واکنش خیلی‌ها delete کردنه. نکن. قبل از اینکه صحنه رو تمیز کنی، شواهد رو جمع کن؛ هرکدوم از این وضعیت‌ها مسیر بررسی خودش رو داره.

The team reports the app is down. get shows one Pod in CrashLoopBackOff, another Pending, and a third ErrImagePull. Deleting all three may erase logs, events, and last-container state—and each symptom has a different cause.

CrashLoopBackOff یک phase نیست؛ reason/waiting حالت container است که retryها با تأخیر افزایشی انجام می‌شن. Pending phase یعنی Pod هنوز schedule/startup path رو کامل نکرده. ImagePullBackOff هم وضعیت تلاش مجدد برای image است. نام status مسیر بعدی رو پیشنهاد می‌کنه، نه علت قطعی رو.

CrashLoopBackOff is not a Pod phase; it is a container waiting reason with backoff between retries. Pending means scheduling/startup has not completed. ImagePullBackOff indicates image retrieval retries. A status suggests the next diagnostic path, not the final cause.

جمع‌آوری شواهد قبل از mutation؛ بعد علت رو با تغییر کوچک حل و همان معیار رو دوباره بسنج.

Collect evidence before mutation; make the smallest cause-specific change and rerun the same verification.

در خرابی این ترتیب رو نگه دارKeep a consistent incident sequence

وقتی سیستم خراب شده، ترتیب کار از تعداد commandها مهم‌تره. اول context و namespace، بعد وضعیت کلی، بعد describe و event، بعد log و spec واقعی. هر مرحله باید یه فرض رو تأیید یا رد کنه؛ نه اینکه فقط دستور بیشتری اجرا کرده باشی.

1) get Pods -o wide and confirm context/namespace; 2) describe the Pod and inspect Events; 3) read current/previous container logs; 4) inspect actual image, command, env, resources, probe, and ServiceAccount; 5) check node allocatable and image credentials. Each command should test a hypothesis. Running or Ready alone does not prove a user HTTP path works.

logs --previous رو قبل از restart/delete بگیر؛ ممکن است container قبلی جایگزین شده و log قدیمی در دسترس نباشه. اگه log خالی است، status و events هنوز شاهدند. YAML فعلی API هم ممکن است با فایل local به‌خاطر defaulting تفاوت داشته باشه؛ هر دو رو تطبیق بده.

Capture logs --previous before restart/delete; an older instance may be replaced and unavailable later. Empty logs do not erase value from status/events. Current API YAML may differ from local files because of defaults; compare both.

چهار failure قابل‌بازتولیدFour reproducible failures

حالا چهار خرابی رو خودمون می‌سازیم. عمدی خراب می‌کنیم، ولی هر بار فقط یه چیز رو. بعد از روی status، event و log می‌فهمیم کدوم لایه اعتراض کرده. این بهترین راهه که اسم خطاها از حالت حفظی دربیاد.

All examples use a disposable cluster and namespace lab. Apply them one at a time, infer the cause before opening the solution, and record evidence.

۱. command خراب

image: busybox:1.36
command: ["sh", "-c", "missing-binary"]

نشانه: restartها زیاد می‌شن. شواهد لازم: get status، describe last state، logs و logs --previous. هنوز Pod رو حذف نکن.

Symptom: restart count rises. Collect get status, last state, current and previous logs before deleting.

پس از بررسی: تشخیص و اصلاح

process با command ناموجود exit می‌کنه؛ command معتبر یا image مناسب انتخاب کن، بعد rollout و log تازه رو بررسی کن.

The process exits because the command is missing. Choose a valid command/image, then verify the rollout and fresh logs.

۲. image یا credential

image: example.invalid/private/app:missing

نشانه: ErrImagePull یا ImagePullBackOff. event معمولاً registry/name/tag/auth رو دقیق‌تر می‌گه؛ private registry credentials رو بیرون manifest ثبت کن.

Symptom: ErrImagePull or ImagePullBackOff. Events often distinguish registry/name/tag/auth; keep private credentials out of the manifest.

پس از بررسی: تشخیص و اصلاح

در این مثال registry/tag ساختگی است. image معتبر رو به‌کار ببر؛ اگه private است imagePullSecret/RBAC رو طبق سیاست cluster تنظیم کن و pull رو بررسی کن.

This example uses a fake registry/tag. Use a valid image; for private images configure imagePullSecrets according to cluster policy and verify pulling.

۳. درخواست جا نمی‌شود

resources:
  requests:
    cpu: "64"
    memory: 128Gi

نشانه: Pending و FailedScheduling. node allocatable و event رو بخوان؛ بالا بردن limit علت جا نشدن request رو حل نمی‌کنه.

Symptom: Pending with FailedScheduling. Inspect node allocatable and events; increasing a limit does not solve an unschedulable request.

پس از بررسی: تشخیص و اصلاح

واحد CPU 64 core و حافظهٔ 128Gi از lab node بیشتر است. مقدار واقع‌بینانهٔ اندازه‌گیری‌شده انتخاب کن، سپس Pod Ready شدن رو بررسی کن.

The request asks for 64 CPU cores and 128Gi, beyond the lab node. Choose measured, realistic values, then verify the Pod becomes Ready.

۴. probe یا config

readinessProbe:
  httpGet:
    path: /missing-health
    port: 8080

نشانه: process Running ولی Ready نیست، Service endpoint خالی. describe probe events، app port/path و ConfigMap/Secret reference رو با spec واقعی تطبیق بده.

Symptom: process is Running but not Ready; Service has no endpoint. Compare probe events, app port/path, and config references with the actual spec.

پس از بررسی: تشخیص و اصلاح

path نمونه نیست؛ readiness endpoint واقعی و ارزان رو تنظیم کن؛ process رو به‌خاطر readiness fail بی‌دلیل restart نکن. endpoint membership و درخواست رو دوباره بسنج.

The example path does not exist. Configure a real, cheap readiness endpoint; do not restart solely for readiness failure. Recheck endpoint membership and a request.

Service no endpoints معمولاً selector/label یا readiness است؛ DNS رو پیش از دیدن EndpointSlice مقصر نکن. مشکل DNS/network فقط وقتی دنبال بشه که evidence از اون مسیر باشه.

A Service with no endpoints often points to selector/labels or readiness; inspect EndpointSlices before blaming DNS. Follow DNS/network only when evidence points there.

پس از جمع‌آوری شواهد، حداقل تغییر لازم رو انجام بده. سپس همان نشانه رو بررسی کن: Pod Ready؟ revision درست؟ endpoint حاضر؟ user-path پاسخ می‌ده؟ در خاتمه log/eventهای مهم و root-cause hypothesis رو نگه دار و بعد cleanup کن.

After collecting evidence, apply the smallest fix. Recheck the same symptom: Ready Pod, correct revision, endpoint present, and user path responding? Preserve useful logs/events and root-cause hypothesis before cleanup.

هر بار از شاهد شروع کنStart from evidence every time

عیب‌یابی Kubernetes مسابقه سرعت در delete و restart نیست. از شاهد شروع کن، یه فرض بساز، کمترین تغییر لازم رو بده و دوباره همون معیار رو بسنج. اگه فقط «سبز شد» ولی نمی‌دونی چرا، هنوز ماجرا تموم نشده.

Status only suggests a path. get locates state, describe/events add context, logs and lastState reveal process behavior, and spec/node capacity test hypotheses. Capture evidence before deleting objects, then verify the smallest fix with the same test. The next project applies this discipline while building an app on a cluster.
