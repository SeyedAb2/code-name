Debugging: CrashLoopBackOff, Pending, ImagePullBackOff

Every status is a clue; none is a full diagnosis by itself.

اولین واکنش: Pod را پاک نکنFirst response: do not delete the Pod

تیم پیام می‌دهد «اپ بالا نیست». get می‌گوید یک Pod CrashLoopBackOff است، دومی Pending و سومی ErrImagePull. اگر همه را delete کنی، شاید log، event یا وضعیت آخرین container را از بین ببری؛ هر کدام علت متفاوتی دارد.

The team reports the app is down. get shows one Pod in CrashLoopBackOff, another Pending, and a third ErrImagePull. Deleting all three may erase logs, events, and last-container state—and each symptom has a different cause.

CrashLoopBackOff یک phase نیست؛ reason/waiting حالت container است که retryها با تأخیر افزایشی انجام می‌شوند. Pending phase یعنی Pod هنوز schedule/startup path را کامل نکرده. ImagePullBackOff هم وضعیت تلاش مجدد برای image است. نام status مسیر بعدی را پیشنهاد می‌کند، نه علت قطعی را.

CrashLoopBackOff is not a Pod phase; it is a container waiting reason with backoff between retries. Pending means scheduling/startup has not completed. ImagePullBackOff indicates image retrieval retries. A status suggests the next diagnostic path, not the final cause.

جمع‌آوری شواهد قبل از mutation؛ بعد علت را با تغییر کوچک حل و همان معیار را دوباره بسنج.

Collect evidence before mutation; make the smallest cause-specific change and rerun the same verification.

در incident این ترتیب را نگه دارKeep a consistent incident sequence

۱) get pods -o wide و context/namespace؛ ۲) describe Pod و Events؛ ۳) container current/previous logs؛ ۴) spec واقعی image, command, env, request/limit, probe, serviceAccount؛ ۵) node allocatable و image credential. هر فرمان می‌تواند یک فرضیه را رد کند. status Ready یا Running به‌تنهایی مسیر HTTP کاربر را ثابت نمی‌کند.

1) get Pods -o wide and confirm context/namespace; 2) describe the Pod and inspect Events; 3) read current/previous container logs; 4) inspect actual image, command, env, resources, probe, and ServiceAccount; 5) check node allocatable and image credentials. Each command should test a hypothesis. Running or Ready alone does not prove a user HTTP path works.

logs --previous را قبل از restart/delete بگیر؛ ممکن است container قبلی جایگزین شده و log قدیمی در دسترس نباشد. اگر log خالی است، status و events هنوز شاهدند. YAML فعلی API هم ممکن است با فایل local به‌خاطر defaulting تفاوت داشته باشد؛ هر دو را تطبیق بده.

Capture logs --previous before restart/delete; an older instance may be replaced and unavailable later. Empty logs do not erase value from status/events. Current API YAML may differ from local files because of defaults; compare both.

چهار failure قابل‌بازتولیدFour reproducible failures

همهٔ مثال‌ها در namespace lab و cluster disposable هستند. هر manifest را جدا apply کن؛ علت را پیش از دیدن solution حدس بزن و شاهد را ثبت کن.

All examples use a disposable cluster and namespace lab. Apply them one at a time, infer the cause before opening the solution, and record evidence.

۱. command خراب

image: busybox:1.36
command: ["sh", "-c", "missing-binary"]

نشانه: restartها زیاد می‌شوند. شواهد لازم: get status، describe last state، logs و logs --previous. هنوز Pod را حذف نکن.

Symptom: restart count rises. Collect get status, last state, current and previous logs before deleting.

پس از بررسی: تشخیص و اصلاح

process با command ناموجود exit می‌کند؛ command معتبر یا image مناسب انتخاب کن، بعد rollout و log تازه را verify کن.

The process exits because the command is missing. Choose a valid command/image, then verify the rollout and fresh logs.

۲. image یا credential

image: example.invalid/private/app:missing

نشانه: ErrImagePull یا ImagePullBackOff. event معمولاً registry/name/tag/auth را دقیق‌تر می‌گوید؛ private registry credentials را بیرون manifest ثبت کن.

Symptom: ErrImagePull or ImagePullBackOff. Events often distinguish registry/name/tag/auth; keep private credentials out of the manifest.

پس از بررسی: تشخیص و اصلاح

در این مثال registry/tag ساختگی است. image معتبر را به‌کار ببر؛ اگر private است imagePullSecret/RBAC را طبق سیاست cluster تنظیم کن و pull را verify کن.

This example uses a fake registry/tag. Use a valid image; for private images configure imagePullSecrets according to cluster policy and verify pulling.

۳. درخواست جا نمی‌شود

resources:
  requests:
    cpu: "64"
    memory: 128Gi

نشانه: Pending و FailedScheduling. node allocatable و event را بخوان؛ بالا بردن limit علت جا نشدن request را حل نمی‌کند.

Symptom: Pending with FailedScheduling. Inspect node allocatable and events; increasing a limit does not solve an unschedulable request.

پس از بررسی: تشخیص و اصلاح

واحد CPU 64 core و حافظهٔ 128Gi از lab node بیشتر است. مقدار واقع‌بینانهٔ اندازه‌گیری‌شده انتخاب کن، سپس Pod Ready شدن را verify کن.

The request asks for 64 CPU cores and 128Gi, beyond the lab node. Choose measured, realistic values, then verify the Pod becomes Ready.

۴. probe یا config

readinessProbe:
  httpGet:
    path: /missing-health
    port: 8080

نشانه: process Running ولی Ready نیست، Service endpoint خالی. describe probe events، app port/path و ConfigMap/Secret reference را با spec واقعی تطبیق بده.

Symptom: process is Running but not Ready; Service has no endpoint. Compare probe events, app port/path, and config references with the actual spec.

پس از بررسی: تشخیص و اصلاح

path نمونه وجود ندارد؛ readiness endpoint واقعی و ارزان را تنظیم کن؛ process را به‌خاطر readiness fail بی‌دلیل restart نکن. endpoint membership و درخواست را دوباره بسنج.

The example path does not exist. Configure a real, cheap readiness endpoint; do not restart solely for readiness failure. Recheck endpoint membership and a request.

پس از جمع‌آوری شواهد، حداقل تغییر لازم را انجام بده. سپس همان symptom را verify کن: Pod Ready؟ revision درست؟ endpoint حاضر؟ user-path پاسخ می‌دهد؟ در خاتمه log/eventهای مهم و root-cause hypothesis را نگه دار و بعد cleanup کن.

After collecting evidence, apply the smallest fix. Recheck the same symptom: Ready Pod, correct revision, endpoint present, and user path responding? Preserve useful logs/events and root-cause hypothesis before cleanup.

هر بار از شاهد شروع کنStart from evidence every time

Status فقط مسیر را پیشنهاد می‌کند. get وضعیت را پیدا می‌کند، describe/eventها زمینه می‌دهند، logs و lastState دربارهٔ فرایند می‌گویند و spec/node capacity فرضیه را می‌آزمایند. قبل از پاک‌کردن object شواهد لازم را ثبت کن؛ بعد تغییر کوچک را با همان آزمون verify کن. پروژهٔ بعدی همین انضباط را هنگام ساخت اولین اپ روی کلاستر به کار می‌گیرد.

Status only suggests a path. get locates state, describe/events add context, logs and lastState reveal process behavior, and spec/node capacity test hypotheses. Capture evidence before deleting objects, then verify the smallest fix with the same test. The next project applies this discipline while building an app on a cluster.
