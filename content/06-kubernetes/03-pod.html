Pods: the smallest unit

چرا Kubernetes یک Pod رو زمان‌بندی می‌کنه، نه یک container تنها؟

Why does Kubernetes schedule a Pod rather than a lone container?

۷۵دقیقهminutes
۱۸تمرینexercises

دو process باید کنار هم زندگی کنندTwo processes need to live side by side

فرض کن یه وب‌سرور داری و کنار دستش یه helper که هر چند ثانیه یه فایل براش می‌سازه. این دوتا قرار نیست مستقل از هم زندگی کنن؛ باید کنار هم بیان بالا، کنار هم جابه‌جا بشن و از یه شبکه محلی مشترک استفاده کنن. Pod دقیقاً از همین سؤال به‌وجود میاد: «کوچک‌ترین چیز مشترکی که باید باهم زمان‌بندی بشه چیه؟»

A web server reads a file generated by a helper. If both are always created, scheduled, and removed together, Kubernetes can put them in one unit: a Pod. If they release and scale independently, they may belong apart.

یک Pod یک یا چند container هم‌بسته داره. همهٔ containerهایش روی یک node زمان‌بندی می‌شن و network namespace مشترک دارن؛ از localhost به هم می‌رسن، البته پورت‌ها نباید conflict کنند. volumeای که هر دو mount کنند فایل رو شریک می‌کنه.

A Pod holds one or more closely related containers. They are scheduled onto one node and share a network namespace, so they can reach each other via localhost without port conflicts. Mounting one volume in both also shares files.

یک container در هر Pod رایج است، نه قانون. sidecar/init وقتی معنی داره که واقعاً چرخهٔ عمر یا فایل/شبکهٔ مشترک لازم باشه.

One container per Pod is common, not a rule. A sidecar or init container is useful when shared lifecycle, files, or networking are actually needed.

Pod و IP اون موقتی‌اندPods and their IPs are ephemeral

حالا یه نکته‌ای که اول کار خیلی‌ها رو غافلگیر می‌کنه: Pod رو مثل سرور دائمی نبین. ممکنه حذف بشه و یکی دیگه جاش بیاد؛ اسم، UID و IP هم می‌تونن عوض بشن. اگه چیزی باید ماندگار باشه، نباید امیدت رو به عمر خود Pod گره بزنی.

A recreated Pod may have a different name, UID, and IP. Do not treat its IP as permanent; a Service provides stable access later. emptyDir lasts for the Pod, not as durable storage. A replacement does not inherit files from a container’s writable layer.

restartPolicy در PodSpec رفتار kubelet رو هنگام پایان container مشخص می‌کنه. restart container با ساخت Pod تازه یکی نیست؛ controllerای مثل Deployment ممکن است Pod حذف‌شده رو جایگزین کند. sidecar فقط وقتی توجیه داره که helper با برنامه همکاری نزدیک داشته باشه؛ log agent برای کل node شاید جای دیگری باشه.

PodSpec restartPolicy describes kubelet behavior when a container exits. Restarting a container differs from creating a new Pod; a controller such as Deployment may replace a deleted Pod. A sidecar fits a closely cooperating helper; a node-wide log agent may belong elsewhere.

هم localhost رو ببین، هم volume مشترک روSee localhost and a shared volume

تا اینجا حرف زدیم؛ حالا با دست ببینیمش. دو container رو توی یک Pod می‌ذاریم، از localhost به هم وصلشون می‌کنیم و یه volume مشترک می‌دیم. بعد عمداً Pod رو عوض می‌کنیم تا ببینیم چه چیزهایی می‌مونن و چه چیزهایی می‌پرن.

In a disposable local cluster, create a simple Pod with nginx and a helper. They mount a shared volume; the helper writes HTML and nginx serves it. The image tags are lab examples; choose maintained, verified versions in real use.

apiVersion: v1
kind: Pod
metadata:
  name: pod-demo
spec:
  volumes:
  - name: shared
    emptyDir: {}
  containers:
  - name: web
    image: nginx:1.27
    volumeMounts:
    - name: shared
      mountPath: /usr/share/nginx/html
      readOnly: true
  - name: helper
    image: busybox:1.36
    command: ["sh", "-c", "while true; do date -u > /shared/index.html; sleep 5; done"]
    volumeMounts:
    - name: shared
      mountPath: /shared

بعد از apply، kubectl get pod pod-demo -w رو ببین. هر دو container باید Ready بشن. با kubectl exec pod-demo -c web -- cat /usr/share/nginx/html/index.html خواندن فایل مشترک رو ثابت کن؛ برای localhost از port-forward به پورت nginx استفاده کن. اگه image ابزار curl نداره، آزمون رو از میزبان انجام بده. این خروجی دوام فایل بعد از حذف Pod رو ثابت نمی‌کنه.

After apply, watch kubectl get pod pod-demo -w. Both containers should become Ready. Read the shared file through the web container; use port-forward to reach nginx via localhost. If the image lacks curl, test from the host. This proves sharing, not persistence after Pod deletion.

حالا در همین Pod آزمایشی یک marker رو داخل مسیر موقتی /tmp بنویس، بخوان و name/IP رو یادداشت کن. Pod رو حذف و manifest رو دوباره apply کن. marker در writable layer container قبلی بوده و برنمی‌گردد؛ جایگزین filesystem تازه داره. این شکست عمدی فقط دلیل نیاز به storage پایدار رو نشان می‌ده، نه راه‌حل فصل ۹ رو.

Write a marker in /tmp in this disposable Pod, read it, and note name/IP. Delete and recreate the Pod. The marker lived in the old container’s writable layer and is gone; the replacement has a fresh filesystem. This demonstrates the need for durable storage without teaching Chapter 9’s solution.

فقط دادهٔ ساختگی رو حذف کن؛ این آزمایش رو روی Pod دارای دادهٔ واقعی اجرا نکن.

Delete only synthetic data; never run this on a Pod holding real data.

Pod مرز همکاری است، نه ماندگاریA Pod is a cooperation boundary, not persistence

Pod خونه دائمی برنامه نیست؛ مرز همکاری چند containerه. وقتی اینو جا بندازی، خیلی از سؤال‌های بعدی درباره IP، storage و جایگزین خودشون روشن‌تر می‌شن. فصل بعد می‌ریم سراغ ابزاری که باهاش این چیزها رو می‌بینیم: kubectl.

Containers in a Pod share networking and mounted volumes, but the Pod and its IP are temporary. Service access and durable storage solve different problems. Next we use kubectl to inspect objects and observe state rather than guess.
