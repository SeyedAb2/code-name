Pods: the smallest unit

چرا Kubernetes یک Pod را زمان‌بندی می‌کند، نه یک container تنها؟

Why does Kubernetes schedule a Pod rather than a lone container?

۷۵دقیقهminutes
۱۸تمرینexercises

دو process باید کنار هم زندگی کنندTwo processes need to live side by side

وب‌سرور فایلی را می‌خواند که helper هر چند ثانیه تولید می‌کند. اگر این دو همیشه با هم ساخته، زمان‌بندی و حذف شوند، Kubernetes می‌تواند آن‌ها را در یک واحد بگذارد: Pod. اگر مستقل منتشر و مقیاس می‌گیرند، شاید باید جدا بمانند.

A web server reads a file generated by a helper. If both are always created, scheduled, and removed together, Kubernetes can put them in one unit: a Pod. If they release and scale independently, they may belong apart.

یک Pod یک یا چند container هم‌بسته دارد. همهٔ containerهایش روی یک node زمان‌بندی می‌شوند و network namespace مشترک دارند؛ از localhost به هم می‌رسند، البته پورت‌ها نباید conflict کنند. volumeای که هر دو mount کنند فایل را شریک می‌کند.

A Pod holds one or more closely related containers. They are scheduled onto one node and share a network namespace, so they can reach each other via localhost without port conflicts. Mounting one volume in both also shares files.

یک container در هر Pod رایج است، نه قانون. sidecar/init وقتی معنی دارد که واقعاً چرخهٔ عمر یا فایل/شبکهٔ مشترک لازم باشد.

One container per Pod is common, not a rule. A sidecar or init container is useful when shared lifecycle, files, or networking are actually needed.

Pod و IP آن موقتی‌اندPods and their IPs are ephemeral

با حذف و ساخت دوبارهٔ Pod، نام، UID و IP ممکن است عوض شوند. IP را آدرس همیشگی فرض نکن؛ Service بعداً دسترسی پایدار می‌دهد. emptyDir با عمر Pod همراه است، نه storage پایدار. اگر فایل مهم را فقط داخل writable layer container بگذاری، replacement آن را به ارث نمی‌برد.

A recreated Pod may have a different name, UID, and IP. Do not treat its IP as permanent; a Service provides stable access later. emptyDir lasts for the Pod, not as durable storage. A replacement does not inherit files from a container’s writable layer.

restartPolicy در PodSpec رفتار kubelet را هنگام پایان container مشخص می‌کند. restart container با ساخت Pod تازه یکی نیست؛ controllerای مثل Deployment ممکن است Pod حذف‌شده را جایگزین کند. sidecar فقط وقتی توجیه دارد که helper با برنامه همکاری نزدیک داشته باشد؛ log agent برای کل node شاید جای دیگری باشد.

PodSpec restartPolicy describes kubelet behavior when a container exits. Restarting a container differs from creating a new Pod; a controller such as Deployment may replace a deleted Pod. A sidecar fits a closely cooperating helper; a node-wide log agent may belong elsewhere.

هم localhost را ببین، هم volume مشترک راSee localhost and a shared volume

در کلاستر محلی disposable، Pod ساده‌ای با nginx و helper بساز. هر دو volume مشترک دارند؛ helper فایل HTML می‌نویسد و nginx آن را می‌خواند. image tag آموزشی نمونه است؛ برای کار واقعی نسخهٔ پشتیبانی‌شده و معتبر را انتخاب کن.

In a disposable local cluster, create a simple Pod with nginx and a helper. They mount a shared volume; the helper writes HTML and nginx serves it. The image tags are lab examples; choose maintained, verified versions in real use.

apiVersion: v1
kind: Pod
metadata:
  name: pod-demo
spec:
  volumes:
  - name: shared
    emptyDir: {}
  containers:
  - name: web
    image: nginx:1.27
    volumeMounts:
    - name: shared
      mountPath: /usr/share/nginx/html
      readOnly: true
  - name: helper
    image: busybox:1.36
    command: ["sh", "-c", "while true; do date -u > /shared/index.html; sleep 5; done"]
    volumeMounts:
    - name: shared
      mountPath: /shared

بعد از apply، kubectl get pod pod-demo -w را ببین. هر دو container باید Ready شوند. با kubectl exec pod-demo -c web -- cat /usr/share/nginx/html/index.html خواندن فایل مشترک را ثابت کن؛ برای localhost از port-forward به پورت nginx استفاده کن. اگر image ابزار curl ندارد، آزمون را از میزبان انجام بده. این خروجی دوام فایل بعد از حذف Pod را ثابت نمی‌کند.

After apply, watch kubectl get pod pod-demo -w. Both containers should become Ready. Read the shared file through the web container; use port-forward to reach nginx via localhost. If the image lacks curl, test from the host. This proves sharing, not persistence after Pod deletion.

حالا در همین Pod آزمایشی یک marker را داخل مسیر موقتی /tmp بنویس، بخوان و name/IP را یادداشت کن. Pod را حذف و manifest را دوباره apply کن. marker در writable layer container قبلی بوده و برنمی‌گردد؛ replacement filesystem تازه دارد. این شکست عمدی فقط دلیل نیاز به storage پایدار را نشان می‌دهد، نه راه‌حل فصل ۹ را.

Write a marker in /tmp in this disposable Pod, read it, and note name/IP. Delete and recreate the Pod. The marker lived in the old container’s writable layer and is gone; the replacement has a fresh filesystem. This demonstrates the need for durable storage without teaching Chapter 9’s solution.

فقط دادهٔ ساختگی را حذف کن؛ این آزمایش را روی Pod دارای دادهٔ واقعی اجرا نکن.

Delete only synthetic data; never run this on a Pod holding real data.

Pod مرز همکاری است، نه ماندگاریA Pod is a cooperation boundary, not persistence

containerهای یک Pod شبکه و volumeهای mountشده را شریک‌اند، اما خود Pod/IP موقتی است. Service برای دسترسی پایدار و storage برای دوام داده مسئله‌های جدا هستند. فصل بعد kubectl را به کار می‌گیریم تا objectها را بخوانیم و به‌جای حدس‌زدن، وضعیت را پیدا کنیم.

Containers in a Pod share networking and mounted volumes, but the Pod and its IP are temporary. Service access and durable storage solve different problems. Next we use kubectl to inspect objects and observe state rather than guess.
