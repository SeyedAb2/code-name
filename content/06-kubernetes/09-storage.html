Persistent data: PV, PVC, StorageClass

وقتی Pod می‌میرد، داده نباید بمیرد.

When a Pod dies, its data should not.

۸۰دقیقهminutes
۱۸تمرینexercises

Pod تازه آمده؛ فایل‌ها کجا رفتند؟A fresh Pod arrived; where did the files go?

اپت یه فایل مهم نوشته، همه‌چیز هم خوبه. Pod رو حذف می‌کنی، یکی تازه جاش میاد و فایل نیست. برای cache شاید دقیقاً همین رو می‌خواستیم؛ برای دیتابیس یا فایل کاربر فاجعه‌ست. پس باید عمر داده رو از عمر Pod جدا کنیم.

The app writes files inside its container. The Pod is replaced, and the files disappear. That is fine for temporary cache, not for customer uploads or a database. Data lifecycle must be separated from Pod lifecycle.

Volume mount فضای فایل رو به Pod می‌ده. PersistentVolume (PV) منبع storage در کلاستر است؛ PersistentVolumeClaim (PVC) درخواست/claim workload برای اون است؛ StorageClass راه و پارامترهای فراهم‌کردن storage رو تعریف می‌کنه. در dynamic provisioning، PVC می‌تونه provisioner رو وادار کند PV تازه بسازد.

A volume mount exposes filesystem space to a Pod. A PersistentVolume is a cluster storage resource; a PersistentVolumeClaim is a workload’s request for it; a StorageClass describes how storage is provisioned. With dynamic provisioning, a PVC can cause a provisioner to create a new PV.

PVC و داده ممکن است بعد از حذف Pod بمانند؛ حذف claim و reclaim policy می‌تونه رفتار دیگری داشته باشه.

A claim and its data may outlive a Pod; deleting the claim and reclaim policy can change the outcome.

درخواست باید با توان backend بخواندA claim must fit what the backend can provide

PVC فقط می‌گه «من این مقدار storage با این ویژگی‌ها می‌خوام». اینکه واقعاً چی پشتش ساخته بشه به StorageClass و backend بستگی داره. اگه درخواست و توان backend با هم نخونن، claim می‌مونه Pending و باید از همون‌جا شروع به پرسیدن سؤال کنیم.

A PVC requests capacity, access mode, and sometimes a StorageClass. Binding shows that a claim matched a PV; a missing class, incompatible capacity, or unavailable provisioner can leave it Pending. Inspect PVCs, PVs, StorageClasses, and describe output; object creation alone does not prove binding.

Access modeها capability declaration هستن، نه همهٔ قفل‌های هم‌زمانی. ReadWriteOnce معمولاً mount read-write از یک node است، نه الزولیً یک Pod؛ چند Pod روی همان node ممکن است به اون دسترسی داشته باشن. ReadWriteMany یعنی چند node می‌تونن mount کنند اگه driver پشتیبانی کند. ReadWriteOncePod دسترسی رو به یک Pod محدود می‌کنه و پشتیبانی CSI/نسخه لازم داره. همیشه قابلیت storage driver رو بررسی کن.

Access modes declare capabilities, not every concurrency lock. ReadWriteOnce generally means read-write mount by one node, not necessarily one Pod; multiple Pods on that node may use it. ReadWriteMany permits multi-node mounts only if the driver supports them. ReadWriteOncePod restricts access to a single Pod and requires compatible CSI/version support. Verify the actual storage driver.

StorageClass با volumeBindingMode و provisioner رفتار binding/provisioning رو شکل می‌ده. reclaimPolicy در PV می‌گه بعد از حذف PVC با PV/data چه بشه؛ Delete می‌تونه storage رو حذف کند و Retain نیازمند مدیریت دستی است. قبل از delete پرسش اصلی: این volume چه داده‌ای داره و backup/restore آزمایش‌شده‌اش کجاست؟

A StorageClass and its provisioner/binding mode shape provisioning. A PV reclaimPolicy determines what happens after claim release; Delete can remove backing storage, while Retain requires manual handling. Before deletion ask what data lives there and where its tested backup is.

lab: Pod عوض بشه، marker بماندLab: replace a Pod, keep the marker

بیا یه marker بنویسیم، Pod رو عوض کنیم و بعد ببینیم marker هنوز هست یا نه. این آزمایش خیلی ساده‌ست، ولی دقیقاً مرز بین storage موقتی و ماندگار رو جلوی چشممون می‌ذاره.

In a disposable cluster, inspect StorageClasses first and record the default and provisioner; clusters differ. Create a small PVC compatible with the backend and choose its class explicitly or use the default. Wait for Bound. If it stays Pending, stop and inspect describe/events.

Podای بساز که PVC رو روی /data mount کند؛ marker رو بنویس و از داخل Pod بخوان. Pod رو حذف و با همان claim Pod تازه بالا بیاور. mount دوباره باید marker رو نشان دهد؛ این آزمایش دوام در برابر جایگزین همان Pod رو ثابت می‌کنه، نه دوام در برابر خرابی node، backend یا حذف PVC.

Create a Pod mounting the PVC at /data, write and read a marker, then delete that Pod and start a replacement with the same claim. The marker should remain. This proves survival of Pod replacement, not survival of node/backend failure or PVC deletion.

شکست عمدی: PVC رو به storageClassName ناموجود یا access mode ناسازگار ببند. Pending رو از events/describe تشخیص بده، نه با زیادکردن بی‌هدف ظرفیت. class و capability واقعی driver رو اصلاح کن و بعد Bound، volume mount و marker رو دوباره بررسی کن. در پایان اول مطمئن شو داده آزمایشی مهمی نیست؛ سپس PVC آزمایشی رو حذف کن و reclaim behavior رو ثبت کن.

Deliberately request a nonexistent StorageClass or incompatible access mode. Diagnose Pending from events and describe rather than blindly increasing size. Correct the class/mode from actual driver capabilities, then verify Bound, mount, and marker again. Before cleanup confirm the data is disposable; delete only the test claim and record reclaim behavior.

Persistence جای backup رو نمی‌گیرهPersistence is not a backup

PVC ممکن است با حذف Pod بماند، ولی اشتباه کاربر، حذف namespace، خرابی storage یا خراب‌شدن داده همچنان ممکن است. snapshot هم لزوماً application-consistent نیست. برای database از backup سازگار و restore test استفاده کن. StatefulSet می‌تونه برای identity/storage هر replica مفید باشه؛ جزئیاتش رو جلوتر می‌خونیم، ولی خودش backup نیست.

A PVC may survive Pod deletion, but operator error, namespace deletion, storage failure, and corruption still happen. A snapshot may not be application-consistent. Use database-aware backups and restore tests. StatefulSet can provide per-replica identity/storage; it is covered later and is not a backup.

local-path معمولاً به یک node محلی گره خورده و با انتقال Pod به node دیگر یا خرابی اون machine رفتار production storage چند-node رو نداره. روی local cluster برای آزمایش خوب است، ولی دسترس‌پذیری و backup رو از اون نتیجه نگیر.

local-path storage is commonly tied to one node and does not provide production multi-node storage behavior when a Pod moves or that machine fails. It can be useful locally, but does not prove availability or backup.

دوام یعنی چه چیزی زنده می‌مونه؟Durability always has a failure boundary

Persistence یعنی داده از مرگ Pod جان سالم به‌در ببره؛ backup یعنی اگه خود داده خراب یا پاک شد، بتونی برش گردونی. این دوتا رو قاطی نکن. PVC داشتن هنوز به این معنی نیست که خیالت از بازیابی راحته.

PV/PVC separates data from Pod lifetime, but durability depends on the driver, node, reclaim policy, and backup operations. Do not extrapolate a successful Pod replacement to disk failure or claim deletion. Next we examine resources: why requests leave Pods Pending and how limits constrain runtime behavior.
