Persistent data: PV, PVC, StorageClass

وقتی Pod می‌میرد، داده نباید بمیرد.

When a Pod dies, its data should not.

۸۰دقیقهminutes
۱۸تمرینexercises

Pod تازه آمده؛ فایل‌ها کجا رفتند؟A fresh Pod arrived; where did the files go?

اپ در container فایل می‌نویسد. Pod حذف و جایگزین می‌شود؛ فایل‌ها هم ناپدیدند. رفتار درست برای cache موقتی است، اما برای عکس سفارش یا دیتابیس نه. باید چرخهٔ عمر داده را از چرخهٔ عمر Pod جدا کنیم.

The app writes files inside its container. The Pod is replaced, and the files disappear. That is fine for temporary cache, not for customer uploads or a database. Data lifecycle must be separated from Pod lifecycle.

Volume mount فضای فایل را به Pod می‌دهد. PersistentVolume (PV) منبع storage در کلاستر است؛ PersistentVolumeClaim (PVC) درخواست/claim workload برای آن است؛ StorageClass راه و پارامترهای فراهم‌کردن storage را تعریف می‌کند. در dynamic provisioning، PVC می‌تواند provisioner را وادار کند PV تازه بسازد.

A volume mount exposes filesystem space to a Pod. A PersistentVolume is a cluster storage resource; a PersistentVolumeClaim is a workload’s request for it; a StorageClass describes how storage is provisioned. With dynamic provisioning, a PVC can cause a provisioner to create a new PV.

PVC و داده ممکن است بعد از حذف Pod بمانند؛ حذف claim و reclaim policy می‌تواند رفتار دیگری داشته باشد.

A claim and its data may outlive a Pod; deleting the claim and reclaim policy can change the outcome.

درخواست باید با توان backend بخواندA claim must fit what the backend can provide

PVC ظرفیت، access mode و گاهی StorageClass می‌خواهد. binding نشان می‌دهد claim به PV متصل شده؛ اگر class وجود ندارد، capacity نمی‌خواند یا provisioner در دسترس نیست، claim Pending می‌ماند. kubectl get pvc,pv,storageclass و describe pvc را بخوان؛ صرف دیدن PVC ساخته‌شده binding را ثابت نمی‌کند.

A PVC requests capacity, access mode, and sometimes a StorageClass. Binding shows that a claim matched a PV; a missing class, incompatible capacity, or unavailable provisioner can leave it Pending. Inspect PVCs, PVs, StorageClasses, and describe output; object creation alone does not prove binding.

Access modeها capability declaration هستند، نه همهٔ قفل‌های هم‌زمانی. ReadWriteOnce معمولاً mount read-write از یک node است، نه الزاماً یک Pod؛ چند Pod روی همان node ممکن است به آن دسترسی داشته باشند. ReadWriteMany یعنی چند node می‌توانند mount کنند اگر driver پشتیبانی کند. ReadWriteOncePod دسترسی را به یک Pod محدود می‌کند و پشتیبانی CSI/نسخه لازم دارد. همیشه قابلیت storage driver را بررسی کن.

Access modes declare capabilities, not every concurrency lock. ReadWriteOnce generally means read-write mount by one node, not necessarily one Pod; multiple Pods on that node may use it. ReadWriteMany permits multi-node mounts only if the driver supports them. ReadWriteOncePod restricts access to a single Pod and requires compatible CSI/version support. Verify the actual storage driver.

StorageClass با volumeBindingMode و provisioner رفتار binding/provisioning را شکل می‌دهد. reclaimPolicy در PV می‌گوید بعد از حذف PVC با PV/data چه شود؛ Delete می‌تواند storage را حذف کند و Retain نیازمند مدیریت دستی است. قبل از delete پرسش اصلی: این volume چه داده‌ای دارد و backup/restore آزمایش‌شده‌اش کجاست؟

A StorageClass and its provisioner/binding mode shape provisioning. A PV reclaimPolicy determines what happens after claim release; Delete can remove backing storage, while Retain requires manual handling. Before deletion ask what data lives there and where its tested backup is.

lab: Pod عوض شود، marker بماندLab: replace a Pod, keep the marker

در کلاستر disposable، ابتدا kubectl get storageclass را اجرا کن. اسم default و provisioner را ثبت کن؛ هر cluster متفاوت است. PVC با access mode و capacity کوچک مطابق backend بساز، StorageClass را explicit یا default انتخاب کن و منتظر Bound بمان. اگر Pending شد، همین‌جا توقف و describe/events را بخوان.

In a disposable cluster, inspect StorageClasses first and record the default and provisioner; clusters differ. Create a small PVC compatible with the backend and choose its class explicitly or use the default. Wait for Bound. If it stays Pending, stop and inspect describe/events.

Podای بساز که PVC را روی /data mount کند؛ marker را بنویس و از داخل Pod بخوان. Pod را حذف و با همان claim Pod تازه بالا بیاور. mount دوباره باید marker را نشان دهد؛ این آزمایش دوام در برابر replacement همان Pod را ثابت می‌کند، نه دوام در برابر خرابی node، backend یا حذف PVC.

Create a Pod mounting the PVC at /data, write and read a marker, then delete that Pod and start a replacement with the same claim. The marker should remain. This proves survival of Pod replacement, not survival of node/backend failure or PVC deletion.

شکست عمدی: PVC را به storageClassName ناموجود یا access mode ناسازگار ببند. Pending را از events/describe تشخیص بده، نه با زیادکردن بی‌هدف ظرفیت. class و capability واقعی driver را اصلاح کن و بعد Bound، volume mount و marker را دوباره verify کن. در پایان اول مطمئن شو داده آزمایشی مهمی نیست؛ سپس PVC disposable را حذف کن و reclaim behavior را ثبت کن.

Deliberately request a nonexistent StorageClass or incompatible access mode. Diagnose Pending from events and describe rather than blindly increasing size. Correct the class/mode from actual driver capabilities, then verify Bound, mount, and marker again. Before cleanup confirm the data is disposable; delete only the test claim and record reclaim behavior.

Persistence جای backup را نمی‌گیردPersistence is not a backup

PVC ممکن است با حذف Pod بماند، اما اشتباه کاربر، حذف namespace، خرابی storage یا خراب‌شدن داده همچنان ممکن است. snapshot هم لزوماً application-consistent نیست. برای database از backup سازگار و restore test استفاده کن. StatefulSet می‌تواند برای identity/storage هر replica مفید باشد؛ جزئیاتش را جلوتر می‌خوانیم، اما خودش backup نیست.

A PVC may survive Pod deletion, but operator error, namespace deletion, storage failure, and corruption still happen. A snapshot may not be application-consistent. Use database-aware backups and restore tests. StatefulSet can provide per-replica identity/storage; it is covered later and is not a backup.

local-path معمولاً به یک node محلی گره خورده و با انتقال Pod به node دیگر یا خرابی آن machine رفتار production storage چند-node را ندارد. روی local cluster برای آزمایش خوب است، اما دسترس‌پذیری و backup را از آن نتیجه نگیر.

local-path storage is commonly tied to one node and does not provide production multi-node storage behavior when a Pod moves or that machine fails. It can be useful locally, but does not prove availability or backup.

دوام یعنی چه چیزی زنده می‌ماند؟Durability always has a failure boundary

PV/PVC داده را از عمر Pod جدا می‌کند، اما دوام دقیق به driver، node، reclaim policy و عملیات backup وابسته است. موفقیت آزمایش replacement را به خرابی دیسک یا حذف claim تعمیم نده. فصل بعد به منبع دیگری می‌رسیم: چرا Pod با request زیاد Pending می‌ماند و limit چه‌طور رفتار runtime را محدود می‌کند.

PV/PVC separates data from Pod lifetime, but durability depends on the driver, node, reclaim policy, and backup operations. Do not extrapolate a successful Pod replacement to disk failure or claim deletion. Next we examine resources: why requests leave Pods Pending and how limits constrain runtime behavior.
