Resources: requests, limits and QoS

Why your Pod is Pending and why that other one got killed.

۷۵دقیقهminutes
۱۸تمرینexercises

یکی جا نمی‌شود؛ یکی OOMKilled شدهOne does not fit; another was OOMKilled

دو تیم می‌گویند «cluster خراب است»: Pod اول Pending مانده و دومی exit کرده. اولی شاید منابع درخواستی‌اش در هیچ node جا نشود؛ دومی شاید از سقف حافظه عبور کرده. این دو وضعیت از دو قرارداد متفاوت می‌آیند.

Two teams say the cluster is broken: one Pod stays Pending; another exited. The first may not fit the requested resources on any node. The second may have exceeded its memory ceiling. These outcomes come from different contracts.

request به scheduler می‌گوید برای جاگذاری چه مقدار حساب کند. limit حد runtime است. درخواست بیشتر از allocatable ظرفیت می‌تواند Pod را unschedulable کند؛ memory limit می‌تواند با OOM kill فرایند را بکشد. CPU limit معمولاً CPU را throttle می‌کند، نه اینکه process را به‌خاطر مصرف زیاد CPU بکشد.

A request tells the scheduler how much to account for placement. A limit is a runtime ceiling. A request beyond available allocatable capacity can leave a Pod unschedulable; a memory limit can trigger an OOM kill. CPU limits typically throttle CPU rather than kill the process for using too much CPU.

عددها چه واحدی دارند؟What do the quantities mean?

CPU با core و millicore سنجیده می‌شود: 1000m برابر یک CPU منطقی است؛ 250m یعنی یک‌چهارم. حافظه را با باینری Mi/Gi یا ده‌دهی M/G می‌نویسند؛ 128Mi و 128M برابر نیستند. مقدار حافظهٔ درخواست‌شده را با allocatable node بسنج، نه کل RAM روی برچسب ماشین؛ سیستم و daemonها هم سهم دارند.

CPU is measured in cores and millicores: 1000m is one logical CPU; 250m is a quarter. Memory uses binary Mi/Gi or decimal M/G; 128Mi and 128M are not equal. Compare requests with node allocatable, not advertised RAM; system daemons also need capacity.

request تضمین نمی‌کند برنامه همین‌قدر مصرف می‌کند؛ limit هم به‌تنهایی ظرفیت node را نمی‌سازد. شروع را با اندازه‌گیری و رفتار بار واقعی تنظیم کن.

A request does not guarantee the app consumes that amount, and a limit does not create node capacity. Tune using measurements and representative workload.

scheduler حساب می‌کند؛ runtime محدود می‌کندThe scheduler accounts; the runtime enforces

scheduler درخواست Podها را با allocatable nodeها مقایسه می‌کند. اگر جا نباشد، Pod Pending می‌ماند و describe/events می‌تواند FailedScheduling نشان دهد؛ بالا بردن limit لزوماً کمکی نمی‌کند، چون جاگذاری بر اساس request است. درخواست کوچک‌تر از واقعیت هم می‌تواند node را شلوغ کند.

The scheduler compares Pod requests against node allocatable. If nothing fits, the Pod remains Pending and describe/events may show FailedScheduling. Raising a limit may not help because placement uses requests; requests far below reality can overpack a node.

در زمان اجرا limitها از طریق سازوکارهای OS/container runtime مانند cgroups اعمال می‌شوند. CPU فراتر از limit می‌تواند throttle شود و latency بالا برود. memory فراتر از سقف ممکن است فرایند را OOM-kill کند؛ مقدار current usage پایین پس از crash علت گذشته را رد نمی‌کند. lastState، exit/reason و node events را کنار هم ببین.

At runtime, limits are enforced through OS/container mechanisms such as cgroups. CPU beyond its limit can be throttled and increase latency. Memory above its ceiling may cause an OOM kill; low current usage after a crash does not disprove past overuse. Correlate lastState, exit/reason, and node events.

QoS بر پایهٔ درخواست/حدود containerها تعیین می‌شود: Guaranteed وقتی شرط‌های request=limit برای CPU و memory در همهٔ containerها برقرار است؛ BestEffort وقتی هیچ request/limit مؤثری تعیین نشده؛ بقیه Burstable هستند. QoS پیش‌بینی مطلق حذف‌شدن نیست؛ فشار node و priority نیز دخیل‌اند.

QoS derives from container requests and limits: Guaranteed requires CPU and memory requests to equal limits for every container; BestEffort has no effective requests or limits; other Pods are Burstable. QoS is not a complete eviction prediction—node pressure and priority matter too.

محدودیت‌های namespaceNamespace-level guardrails

LimitRange می‌تواند مقدار پیش‌فرض یا بازهٔ مجاز request/limit برای objectها تعریف کند؛ ResourceQuota مصرف مجموع namespace را محدود می‌کند. این‌ها guardrail هستند، نه اندازه‌گیری ظرفیت واقعی. metrics-server یا ابزار metrics لازم است تا بفهمی مصرف و throttling چگونه‌اند؛ kubectl top در همهٔ clusterها بدون metrics provider کار نمی‌کند و داده‌اش آنی نیست.

LimitRange can define defaults or allowed per-object request/limit ranges; ResourceQuota caps aggregate namespace consumption. They are guardrails, not a measurement of actual capacity. Metrics-server or another provider is needed to inspect usage; kubectl top does not work on every cluster without metrics and is not instantaneous.

آزمایش امن: Pending و OOMSafe lab: Pending and OOM

برای Pending، در cluster محلی یک Pod آزمایشی با request حافظه‌ای بالاتر از allocatable همهٔ nodeها تعریف کن، نه limit host-wide. قبل از apply، ظرفیت را ببین و request را محدود به مقداری انتخاب کن که قطعاً از node آموزشی بیشتر باشد اما روی میزبان فشار ایجاد نکند؛ Pod تا یافتن node مناسب اجرا نمی‌شود. describe/events باید scheduling علت را نشان دهد. پس از ثبت، workload را پاک کن.

To produce Pending, define a disposable Pod with a memory request above every local node’s allocatable amount, not a host-wide limit. Inspect capacity first and choose a value that cannot fit the lab node but does not create host pressure; the Pod will not start. describe/events should explain scheduling. Capture evidence and remove the test.

برای OOM از Pod دیگری با memory limit کوچک و یک allocation یک‌بارهٔ bounded استفاده کن؛ مثلاً سقف 64Mi و درخواست allocation بزرگ‌تر اما ثابت 96Mi. فقط یک Pod را اجرا کن و workloadهای دیگر را متوقف کن. پس از خاتمه، kubectl describe pod و get -o jsonpath برای lastState.terminated.reason / exitCode را بررسی کن. OOMKilled شاهد runtime است؛ صرف exit 137 به‌تنهایی کافی نیست.

For OOM, use one disposable Pod with a small memory limit and a single bounded allocation, for example a 64Mi ceiling and a fixed 96Mi allocation. Run only one and stop other lab workloads. After termination inspect describe and lastState.terminated.reason/exitCode. OOMKilled is runtime evidence; exit 137 alone is insufficient.

اگر metrics-server حاضر نیست، kubectl top جواب نمی‌دهد؛ این با نبودن resource request فرق دارد. آزمایش محدود را فقط روی کلاستر disposable اجرا کن و هرگز memory pressure نامحدود یا fork bomb نساز.

Without metrics-server, kubectl top may fail; that differs from missing resource requests. Run bounded experiments only on disposable clusters. Never create unbounded memory pressure or a fork bomb.

request به جاگذاری کمک می‌کند؛ limit رفتار runtime را محدود می‌کند. Pending و OOMKilled را با شواهد متفاوت تحلیل کن. QoS و quota راهنمای رفتارند، نه جانشین اندازه‌گیری. فصل بعد HPA از متریک برای تغییر تعداد replica استفاده می‌کند؛ بدون request و metric معتبر، autoscaling هم حدس خواهد بود.

Requests guide placement; limits constrain runtime. Diagnose Pending and OOMKilled with different evidence. QoS and quotas guide behavior, not replace measurement. Next, HPA uses metrics to change replica counts; without requests and valid metrics, autoscaling is guesswork.
