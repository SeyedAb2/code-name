مأموریت: «بالا است» برای تحویل کافی نیستMission: “it is up” is not a handoff

اپ پروژه قبل بالا میاد؛ خوبه، ولی برای تحویل جدی هنوز سؤال‌های سخت مونده. چه کسی اجازه deploy داره؟ Pod از کجا می‌فهمه آماده‌ست؟ زیر بار تا کجا scale می‌شه؟ نسخه خراب چطور برمی‌گرده؟ این پروژه همون اپ رو می‌گیره و وادارت می‌کنه این سؤال‌ها رو با شواهد جواب بدی.

The previous three-service app works, but the next team asks: who can deploy? When is the app ready? How far can it scale? What if the new release is broken? Harden the same app toward production, inject a failure, and hand it off with a verified rollback and clear evidence.

این پروژه روی cluster آزمایشی جدا اجرا می‌شه؛ نسخه و storage رو با محیط واقعی یکی فرض نکن. پایش اینجا یعنی metrics/status/logs و چند مشاهدهٔ روشن، نه سولینهٔ کامل Prometheus/Grafana. داده ساختگی باشه و پیش از هر عملیات مخرب context رو دوباره بخوان.

Use a separate test cluster; do not assume its versions or storage match production. Monitoring here means useful metrics, status and logs—not a full Prometheus/Grafana platform. Use synthetic data and re-check context before destructive operations.

مسیر ترافیک با حلقه‌های کنترل فرق داره: HPA تعداد replica رو تنظیم می‌کنه، RBAC مجوز رو، و probe سلامت/آمادگی رو گزارش می‌ده.

Traffic flow is distinct from control loops: HPA adjusts replicas, RBAC governs permissions, and probes report health/readiness.

خط قرمزهای مأموریتMission constraints

اینجا هم ادعای «production-ready» رو راحت خرج نمی‌کنیم. روی cluster آزمایشی کار می‌کنیم و فقط بخش‌هایی رو که واقعاً ساختیم و سنجیدیم گزارش می‌کنیم. metrics/status/logs داریم؛ قرار نیست وانمود کنیم یک پلتفرم کامل مانیتورینگ سازمانی ساخته‌ایم.

Use an isolated namespace; a least-privilege ServiceAccount; realistic requests and limits; startup/readiness/liveness checks suited to the app; HPA only when the Metrics API is available; versioned images; private persistent DB; Ingress/TLS supported by the cluster; and a reversible rollout. None alone guarantees full security or availability.

نه ایستگاه تا تحویلNine checkpoints to handoff

۱ — baseline را ثبت کن

نه ایستگاه داریم و هرکدوم یه تکه از داستان تحویل رو می‌بنده: دسترسی، resource، probe، autoscaling، rollout، خرابی و بازیابی. هرجا تغییری می‌دی، قبل و بعدش مدرک نگه دار تا آخر کار بتونی بگی دقیقاً چی بهتر شد.

Record context, version, nodes, add-ons and current service state. Capture one successful request and the live version. This snapshot is a comparison baseline, not proof of production readiness.

۲ — هویت و namespace را محدود کن

namespace جدید و ServiceAccount اختصاصی بساز. Role رو فقط به منابع و verb لازم محدود کن؛ عمداً دسترسی غیرلازم رو امتحان کن و باید Forbidden بگیری. مدرک allow و deny رو ثبت کن. اگه workload API رو صدا نمی‌زند، token خودکار رو بی‌دلیل mount نکن.

Create a new namespace and dedicated ServiceAccount. Limit its Role to required resources and verbs; deliberately test an unneeded action and expect Forbidden. Record both allowed and denied checks. If the workload does not call the API, do not mount a token without reason.

راهنمایی

kubectl auth can-i را با همان ServiceAccount و namespace هدف بپرس؛ مجوز کاربر خودت نتیجهٔ workload را ثابت نمی‌کند.

۳ — app را کم‌امتیاز و قابل‌پیش‌بینی کن

image رو با UID غیر root، read-only filesystem در صورت سازگاری، مسیر نوشتنی مشخص، request/limit و startup/readiness/liveness تنظیم کن. یک بار مسیر لازم رو عمدی read-only کن تا شکست رو ببینی؛ از event و log علت رو بیاب و فقط مسیر لازم رو writable کن.

Configure a non-root image, read-only filesystem where compatible, explicit writable paths, requests/limits and startup/readiness/liveness probes. Deliberately make a required path read-only, diagnose from Events/logs, and make only the necessary path writable.

یادت باشد

readiness ناموفق ترافیک را از endpoint حذف می‌کند؛ liveness ناموفق ممکن است restart کند. از probe برای چک عمیق dependency استفاده نکن.

۴ — مرز منابع را بسنج

برای app request و limit متناسب با اندازه‌گیری بگذار؛ workload ساختگی و محدود اجرا کن. مقدار درخواست‌شده روی scheduling اثر داره و limit رفتار runtime رو محدود می‌کنه. Pod رو با describe/top بررسی کن. خروجی top بدون Metrics API موجود نیست؛ OOM هم به‌تنهایی علت کاربردی رو تشخیص نمی‌ده.

Set measured app requests and limits, then run a bounded synthetic workload. Requests affect scheduling; limits constrain runtime behavior. Inspect with describe/top. Metrics commands require a working Metrics API, and OOM alone does not diagnose the application cause.

۵ — HPA را با شاهد راه بینداز

اگه Metrics API آماده است، target CPU و بازهٔ min/max منطقی تعریف کن. یک بار scale زیر بار محدود رو مشاهده کن و بعد بار رو قطع کن تا رفتار scale-down هم دیده بشه. مدرک: current/desired replicas و resource metrics. HPA بدون metrics یا بدون CPU request مناسب، پیش‌بینی‌پذیر کار نمی‌کنه.

If the Metrics API is ready, define a sensible CPU target and replica bounds. Observe scale-up under bounded load, then stop load and observe scale-down. Evidence: current/desired replicas and resource metrics. HPA is not predictable without metrics or appropriate CPU requests.

ایمنی

ترافیک آزمایشی را محدود و زمان‌دار نگه دار؛ ابزار بارساز را بیرون cluster روی endpoint عمومی اجرا نکن.

۶ — داده، Ingress و handoff پایش

DB رو private نگه دار، PVC و backup/restore checkpoint رو ثبت کن. Ingress/TLS رو با قابلیت واقعی cluster تنظیم کن. runbook باید به این‌ها پاسخ بدهد: نسخهٔ زنده چیست؟ app و DB آماده‌اند؟ restart چه وقت رخ داده؟ دیسک/claim چقدر جا داره؟ backup آخر کجاست؟

Keep the DB private, record its PVC and a backup/restore checkpoint, and configure Ingress/TLS for the actual cluster. The runbook must answer: what version is live? Are app and DB ready? When did a restart occur? How much storage remains? Where is the latest backup?

۷ — نسخهٔ سالم را rollout کن

image رو از tag شناور به نسخهٔ دقیق تغییر بده. قبل/بعد rollout status و پاسخ endpoint رو نگه دار. readiness gate باید قبل از ادامهٔ rollout معنی‌دار باشه. deployment history قابل‌مشاهده است، ولی تضمین نمی‌کنه rollback دادهٔ ناسازگار DB رو برگرداند.

Pin the image to an explicit version. Capture rollout status and endpoint response before and after. Readiness must meaningfully gate rollout progression. Deployment history is useful but cannot roll back incompatible database changes.

۸ — نسخهٔ خراب را تشخیص بده و rollback کن

حالا image عمدیِ خراب یا probe path نامعتبر بده. پیش از دست‌کاری، rollout status، Pod conditions، Events، restart count و log رو جمع کن. علت رو حدس نزن. به revision سالم rollback کن، readiness و پاسخ نسخه رو از بیرون namespace آزمایش کن و مدرک پس از rollback بگیر.

Now deploy a deliberately broken image or invalid probe path. Before changing anything, capture rollout status, Pod conditions, Events, restart count and logs. Diagnose before guessing. Roll back to the known-good revision, then verify readiness and versioned response from outside the namespace.

راهنمایی مرحله‌ای

ImagePullBackOff، readiness failure و CrashLoop شواهد متفاوت دارند. Events علت زمان‌بندی‌شده را نشان می‌دهند؛ log ممکن است خالی باشد اگر process فرصت شروع نداشته.

۹ — runbook را به نفر بعد تحویل بده

مجوزها، resource budget، probeها، HPA، route، DB/PVC، backup، version و فرمان rollback رو خلاصه کن. یک نفر دیگر باید با همین شواهد بتواند وضعیت رو بفهمد و خطای تکراری رو تشخیص دهد. namespace آزمایشی رو فقط پس از جمع‌آوری مدرک پاک کن.

Summarize permissions, resource budget, probes, HPA, routes, DB/PVC, backup, version and rollback command. Another operator should understand the system and diagnose a repeat incident from this handoff. Delete the test namespace only after evidence is collected.

معیار قبولی نهاییFinal acceptance

درخواست بیرونی به نسخهٔ مورد انتظار می‌رسه؛ DB port عمومی نداره؛ workload با هویت کم‌دسترسی اجرا می‌شه؛ app و DB health دارن؛ request/limit و HPA شواهد قابل‌خواندن دارن؛ رکورد از تعویض Pod جان سالم می‌برد؛ rollout خراب تشخیص و rollback می‌شه؛ و runbook پاسخ پرسش‌های اپراتوری رو می‌ده. «همه‌چیز Running است» هیچ‌یک از این‌ها رو به‌تنهایی ثابت نمی‌کنه.

An external request reaches the expected version; the DB has no public port; workload identity is least-privilege; app and DB are healthy; requests/limits and HPA have readable evidence; a record survives Pod replacement; a broken rollout is diagnosed and rolled back; and the runbook answers operator questions. “Everything is Running” proves none of these by itself.

ترتیب عملیات

راه‌حل مرجع این پروژه بیشتر از اینکه لیست دستور باشه، ترتیب فکرکردنه: baseline بگیر، تغییر بده، خراب کن، شاهد جمع کن، برگردون و دوباره همون معیار رو بسنج. اگه این چرخه رو یاد بگیری، از خود YAMLها مهم‌تره.

1) Context and baseline; 2) namespace and RBAC; 3) least-privilege app, probes and resources; 4) metrics and HPA; 5) DB/PVC/backup and Ingress; 6) roll out a good version; 7) record request and version; 8) inject a fault and gather evidence; 9) rollback and external verification; 10) hand off the runbook and scoped cleanup.

kubectl config current-context
kubectl -n production-lab get deploy,pods,svc,ingress,pvc
kubectl -n production-lab rollout status deploy/app
kubectl -n production-lab describe pod POD_NAME
kubectl -n production-lab get events --sort-by=.lastTimestamp
kubectl -n production-lab logs deploy/app --all-pods=true --tail=80
kubectl -n production-lab rollout undo deploy/app
kubectl -n production-lab rollout status deploy/app

نام namespace، controller، storage و روش TLS وابسته به محیط‌اند. HPA نیازمند Metrics API سازگار است؛ مقادیر request/limit رو از اندازه‌گیری بگیر، نه از این نمونه. rollback نسخهٔ برنامه لزوماً migration پایگاه‌داده رو برنمی‌گرداند. در یادداشت تحویل، مرز این تضمین‌ها رو صریح بنویس.

Namespace, controller, storage and TLS setup are environment-dependent. HPA needs a compatible Metrics API; derive resource values from measurement, not this example. Rolling back an app version does not necessarily reverse a database migration. State these limits explicitly in the handoff.

این پروژه کلاستر رو جادویی یا خودبسنده نمی‌کنه؛ ثابت می‌کنه می‌تونی سیگنال‌های متفاوت رو از هم جدا کنی، تغییر رو محدود کنی و پس از خرابی همان نتیجه رو دوباره آزمایش کنی. از اینجا به بعد سراغ مهندسی عملیات واقعی می‌ری.

This project does not make a cluster magical or self-sufficient. It proves you can distinguish signals, constrain change and repeat the same verification after failure. From here, you are ready for real operational engineering.
