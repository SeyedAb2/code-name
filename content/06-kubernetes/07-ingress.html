دو Service، یک نشانی عمومیTwo Services, one public address

web و api داخل کلاستر Service دارند؛ کاربر اما یک host عمومی می‌خواهد که /web و /api را جدا route کند. NodePort جدا برای هر سرویس، DNS و firewall را شلوغ می‌کند. مسئله حالا مسیریابی HTTP است.

Web and API have in-cluster Services, but users want one public host that routes /web and /api separately. Separate NodePorts multiply DNS and firewall work. This is now an HTTP routing problem.

Ingress resource قانون‌ها را ثبت می‌کند؛ Ingress controller آن‌ها را می‌خواند و با proxy واقعی اجرا می‌کند. ساختن resource به‌تنهایی traffic را route نمی‌کند. باید controller فعال، IngressClass مناسب و network path تا controller وجود داشته باشد.

An Ingress resource stores routing rules; an Ingress controller reads and implements them with a real proxy. Creating the resource alone does not route traffic. A working controller, matching IngressClass, and network path to it are required.

resource قانون را می‌گوید، controller اجرا می‌کند و Service backendهای Pod را پیدا می‌کند.

The resource declares rules, the controller implements them, and Services locate Pod backends.

Class و path type را از روی کلاستر بخوانInspect class and path type

API استاندارد networking.k8s.io/v1، Service و port مقصد را برای هر backend می‌خواهد. Prefix مسیر را در مرز segmentها match می‌کند؛ Exact کل path را دقیق می‌سنجد؛ ImplementationSpecific به controller وابسته است. ingressClassName باید به IngressClassای اشاره کند که controller نصب‌شده می‌پذیرد. اسم class را حدس نزن.

The networking.k8s.io/v1 API specifies a Service and port for each backend. Prefix matches on path-segment boundaries; Exact requires an exact path; ImplementationSpecific depends on the controller. ingressClassName must reference a class handled by the installed controller. Do not guess it.

annotationهای rewrite و tuning همگانی نیستند؛ controller-specific هستند. Gateway API استاندارد مرتبط و جدیدتر است، اما موضوع این فصل را عوض نمی‌کنیم. path rewrite هم لازم نیست اگر برنامه خودش زیرمسیر را درست سرو کند.

Rewrite and tuning annotations are controller-specific, not portable. Gateway API is a related newer standard, but it does not replace this chapter’s focus. Rewrites are unnecessary if the app serves its path correctly.

TLS ورودی، پایان رمزنگاری نیستIngress TLS is not the whole encryption story

در الگوی معمول، controller TLS را با Secret نوع kubernetes.io/tls خاتمه می‌دهد. Secret باید در namespace همان Ingress باشد. اتصال proxy به Service ممکن است HTTP باشد؛ backend TLS پیکربندی جدا می‌خواهد. self-signed certificate برای آزمایش محلی است و مرورگرهای عمومی به آن اعتماد نمی‌کنند.

Commonly the controller terminates TLS using a kubernetes.io/tls Secret in the same namespace as the Ingress. Proxy-to-Service may still be HTTP; backend TLS needs separate configuration. A self-signed certificate is for local testing and is not trusted by public browsers.

local cluster ممکن است tunnel، port-forward یا mapping مخصوص توزیع برای رسیدن به controller بخواهد. resource بدون controller هم می‌تواند در API ثبت شود و با این حال آدرس عمومی نداشته باشد. اول class، log controller و Service backend را ببین؛ بعد سراغ DNS برو.

A local cluster may need a tunnel, port-forward, or distribution-specific mapping to reach the controller. An object can be accepted without a working controller and still have no public address. Inspect class, controller logs, and backend before blaming DNS.

lab: دو مسیر و یک گواهی آزمایشیLab: two paths and a test certificate

در کلاستر محلی controller پشتیبانی‌شده را با دستور رسمی همان توزیع فعال کن؛ روش kind/minikube/provider فرق می‌کند و عمداً یک فرمان جهان‌شمول نمی‌سازیم. get ingressclass و Podهای controller را ببین. دو Service سالم را با host demo.local و مسیرهای /web و /api به Ingress وصل کن.

Enable a supported controller using your distribution’s official guide; kind, minikube, and provider steps differ, so there is no pretend universal install command here. Inspect ingressclass and controller Pods. Route demo.local paths /web and /api to two working Services.

اگر Ingress دیده می‌شود اما درخواست شکست می‌خورد، صرفاً وجود object را ثابت کرده‌ای. controller logs، class، Host header، pathType، Service name/port و EndpointSlice را تطبیق بده. عمدی نام backend را غلط کن و با همین شواهد تشخیص بده؛ سپس اصلاح کن و هر دو مسیر را از بیرون controller verify کن.

If the object exists but requests fail, only object creation is proven. Compare controller logs, class, Host header, pathType, Service name/port, and EndpointSlices. Deliberately mistype a backend and diagnose it with this evidence; fix it and verify both routes through the controller.

برای TLS یک dev certificate self-signed بساز و به Secret همان namespace بده؛ TLS host و rule host باید یکی باشند. curl با غیرفعال‌کردن certificate validation فقط آزمایش محلی است، نه روش production. دامنهٔ واقعی به DNS، گواهی trusted و renew خودکار/مدیریت‌شده نیاز دارد.

Create a self-signed development certificate and store it in a Secret in the same namespace; TLS host and rule host must match. Disabling certificate verification in curl is local-only, never production practice. A real domain needs DNS, a trusted certificate, and managed renewal.

resource قانون است، controller مجریThe resource declares; the controller implements

resource، class، controller، Service و network path باید کنار هم درست باشند. دیدن object فقط وجود قانون را ثابت می‌کند، نه رسیدن request را. فصل بعد ConfigMap و Secret را جدا می‌کنیم تا برنامه با config تازه اجرا شود، بدون اینکه دادهٔ حساس را در Git جا بگذاریم.

The resource, class, controller, Service, and network path must all align. Seeing the object proves only that a rule exists, not that requests reach it. Next we separate ConfigMaps and Secrets so configuration can change without leaking sensitive values into Git.
