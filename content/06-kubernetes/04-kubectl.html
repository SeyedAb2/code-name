«کار نمی‌کنه»؛ خب کجایش؟“It doesn’t work”—which part?

یه نفر توی تیم می‌گه: «اپ کار نمی‌کنه.» این جمله تقریباً هیچ اطلاعاتی بهمون نمی‌ده. قبل از اینکه چیزی رو delete کنیم یا دوباره apply بزنیم، باید سؤال رو ریز کنیم: به کدوم cluster وصل شدیم؟ object اصلاً ساخته شده؟ Pod کجاست؟ event چی گفته؟ log چی گفته؟ kubectl قراره همین سؤال‌ها رو یکی‌یکی جواب بده.

A teammate says the app is unavailable. If you immediately delete and reapply, you may erase the evidence that explains why. First find which cluster kubectl targets, what objects exist, where they were placed, and which events or logs were recorded.

در تمام آزمایش‌ها از cluster محلی و namespace جدا استفاده کن. دستور تغییر‌دهنده رو پس از دیدن context اجرا کن؛ نام cluster رو با چشم بخوان، نه با امید. برای درخواست read-only معمولاً get امن‌تر است، ولی نتیجه همچنان تابع RBAC دسترسی توست.

Use a local cluster and isolated namespace for every experiment. Inspect the context before mutating commands; read its name rather than hoping it is right. get is generally read-only, but results still depend on your RBAC permissions.

اول مقصد، بعد دستورTarget first, command second

اولین عادت خوب خیلی ساده‌ست: قبل از دستور مهم، مقصد رو ببین. اشتباه‌زدن یک دستور درست روی cluster اشتباه از خود دستور خطرناک‌تره. پس current-context رو مثل نگاه‌کردن به آدرس قبل از ارسال بسته ببین.

kubectl config current-context prints the active context. List choices with kubectl config get-contexts. A context groups cluster, identity, and default namespace settings; it does not grant permission. If it is wrong, select the intended context explicitly and verify again.

kubectl config current-context
kubectl config get-contexts
kubectl config set-context --current --namespace=lab

برای آزمایش namespace بساز: kubectl create namespace lab. خروجی created پذیرش درخواست رو نشان می‌ده، نه مجوز در همهٔ namespaceها. دستورهای بعدی رو با -n lab اجرا کن یا namespace پیش‌فرض همین context رو فقط در cluster آزمایشی تغییر بده.

Create a lab namespace with kubectl create namespace lab. “created” shows the request was accepted, not that you can access every namespace. Use -n lab for later commands or change this context’s default only in a disposable cluster.

از خلاصه به شاهد دقیق‌تر بروMove from summary to more specific evidence

عیب‌یابی رو از دور شروع کن و کم‌کم زوم کن. اول get برای تصویر کلی، بعد describe برای condition و event، بعد اگر لازم شد log و جزئیات spec. این ترتیب کمک می‌کنه قبل از دست‌زدن به سیستم، داستانش رو بخونی.

get lists resources. kubectl get pods -n lab -o wide shows name, readiness, status, restarts, and node. A missing object may be a selector or namespace issue. For a problematic status, describe that Pod; Conditions and Events provide time-local clues.

kubectl get pods -n lab -o wide
kubectl describe pod NAME -n lab
kubectl get events -n lab --sort-by=.metadata.creationTimestamp

describe «علت» رو خودکار حدس نمی‌زند؛ event مثل FailedScheduling، ErrImagePull یا probe failure مسیر بررسی بعدی می‌ده. eventها موقتی‌اند و retention کلاستر محدود است؛ هنگام خرابی زود ثبتشان کن.

describe does not automatically diagnose root cause; events such as FailedScheduling, ErrImagePull, or probe failure point to the next check. Events expire according to cluster retention; capture them early during an incident.

وقتی خروجی تمام YAML رو می‌خوای، kubectl get deployment NAME -n lab -o yaml رو بگیر. این وضعیت فعلی API رو نشان می‌ده، نه الزولیً دقیقاً همان فایل محلی که اعمال کردی؛ defaultها و تغییر admission ممکن است در object باشن. برای فیلد محدود از jsonpath استفاده کن و اون رو با متن کامل اشتباه نگیر.

For the full API object, use kubectl get deployment NAME -n lab -o yaml. It shows current API state, not necessarily the exact local file you applied; defaults and admission changes may appear. jsonpath helps extract a field but is not the full object.

چه گفت و داخلش چه می‌بینیم؟What did it say, and what is inside?

kubectl logs pod-demo -c web -n lab می‌خونه stdout/stderr کانتینر مشخص‌شده. اگه container restart شده، --previous لاگ اجرای قبلی رو می‌گیره؛ ممکن است بعد از restartهای متعدد در دسترس نباشه. لاگ فعلی که خالی است ثابت نمی‌کنه برنامه هیچ‌وقت خطا نداده.

kubectl logs pod-demo -c web -n lab reads stdout/stderr from the named container. If it restarted, --previous requests the prior container instance’s logs; repeated restarts may make older logs unavailable. Empty current logs do not prove the app never failed.

kubectl exec -it pod-demo -c web -n lab -- sh برای مشاهدهٔ درون container است؛ image ممکن است shell نداشته باشه. از exec برای بررسی کوتاه استفاده کن، نه تغییر دستی که در manifest ثبت نمی‌شه. خروج از shell وضعیت رو اصلاح نمی‌کنه؛ تغییر پایدار باید در image یا spec باشه.

kubectl exec -it pod-demo -c web -n lab -- sh opens a shell if the image includes one. Use exec for short inspection, not unrecorded manual changes. Exiting the shell does not fix state; durable changes belong in the image or manifest.

YAML رو قبل از apply مقایسه کنCompare YAML before applying it

manifest اعلام خواسته است: apiVersion، kind، metadata و spec. selector/labelها باید با هم سازگار باشن؛ indentation در YAML معنا داره. kubectl diff -f app.yaml تفاوت پیشنهادی با object موجود رو نشان می‌ده. exit code در diff ممکن است تفاوت رو اعلام کند، پس خروجی رو بخوان و هر تغییر رو بفهم.

A manifest declares intent through apiVersion, kind, metadata, and spec. Selectors and labels must agree; YAML indentation matters. kubectl diff -f app.yaml shows proposed differences from current objects. Its exit code may signal a diff, so inspect the output rather than treating every nonzero as an apply failure.

بعد از review، kubectl apply -f app.yaml رو اجرا کن. پیام configured/created دربارهٔ object است؛ rollout و readiness رو جدا با get/describe پیگیری کن. برای اطمینان از namespace و فایل، قبل از apply این‌ها رو چک کن؛ در محیط حساس تغییر رو در Git review کن.

After review, apply the file. “configured” or “created” describes the object, not a healthy rollout; follow readiness separately with get/describe. Check file and namespace first, and review changes in Git for sensitive environments.

برای شکست عمدی، image رو به tag ناموجود تغییر بده و apply کن. قبل از هر repair، get، describe و event رو ثبت کن؛ ErrImagePull/ImagePullBackOff علت مسیر image رو می‌ده. بعد tag رو درست، diff رو ببین، apply و status رو بررسی کن. حذف و ساخت دوباره اولین ابزار تشخیص نیست.

For a deliberate fault, change the image to a nonexistent tag and apply. Before repairing, capture get, describe, and events; ErrImagePull/ImagePullBackOff indicates an image retrieval problem. Correct the tag, review diff, apply, and verify status. Delete-and-recreate is not the first diagnostic tool.

kubectl diff -f app.yaml -n lab
kubectl apply -f app.yaml -n lab
kubectl get pods -n lab -w

kubectl delete -f app.yaml شیء تعریف‌شده در فایل رو حذف می‌کنه؛ قبلش مطمئن شو فایل همان چیزهایی رو نداره که حفظشان می‌خوای. برای تمرین namespace آزمایشی رو کامل پاک کن، نه context اشتباه رو.

kubectl delete -f app.yaml removes resources defined by the file; check what the file contains first. For cleanup, delete only the disposable namespace rather than risking the wrong context.

get/describe معمولاً API object رو می‌خونه؛ logs/exec به مسیر node می‌رسن. مسیر ساده‌شده و توزیع‌ها جزئیات متفاوت دارن.

get/describe read API objects; logs/exec reach the node path. This is simplified, and distributions vary in details.

هر دستور باید یک سؤال رو جواب بدهدEvery command should answer a question

از این فصل یه عادت با خودت ببر: هر دستور باید جواب یک سؤال مشخص باشه. اگه نمی‌دونی چرا داری دستور می‌زنی، احتمالاً هنوز سؤال رو درست نساختی. فصل بعد همین نگاه رو روی Deployment امتحان می‌کنیم.

get shows which objects you see; describe and events suggest why; logs reveal process output; exec is a temporary inspection window. apply records a change, not a guarantee of health. Next, Deployment explains how desired replicas are maintained and versions rolled out.
