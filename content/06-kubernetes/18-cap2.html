پروژهٔ ۲ — اپ سه‌سرویسه با Ingress

Project 2 — three services behind an Ingress

سه سرویس، پیکربندی، دادهٔ ماندگار و یک نقطهٔ ورود.

Three services, configuration, persistent data and one entry point.

۱۱۰دقیقهminutes
۷ایستگاهcheckpoints

مأموریت: سه جزء، یک برنامهMission: three parts, one application

این بار یه سرویس تنها نداریم. web، API و دیتابیس باید با هم کار کنن، ولی فقط ورودی وب از بیرون دیده بشه. داده هم باید بعد از جایگزینی Pod بمونه. مأموریت وقتی تمومه که یه درخواست واقعاً از Ingress رد بشه، به API برسه و داده‌ای که نوشتیم بعد از خرابی ساختگی هنوز سر جاش باشه.

The team wants a web app, API and database delivered together. Only web traffic should enter from outside; other communication stays inside the cluster. Data must survive Pod replacement. The mission is not complete until a request traverses Ingress and a record survives a Pod replacement.

از cluster محلی با Ingress controller و StorageClass پویا استفاده کن. اسم قابلیت‌ها به‌تنهایی تضمین نصب‌شدنشان نیست: پیش از شروع، controller و provisioner رو بررسی کن. namespace جدا و دادهٔ ساختگی بساز؛ روی cluster مشترک یا production تمرین نکن.

Use a local cluster with an Ingress controller and dynamic StorageClass. A Kubernetes API object does not install its controller: verify the controller and provisioner before starting. Use an isolated namespace and synthetic data, never a shared or production cluster.

Ingress مسیر HTTP است، نه خودِ controller؛ PVC هم درخواست ذخیره‌سازی است، نه تضمین backup.

Ingress describes HTTP routing; it is not the controller. A PVC requests storage; it is not a backup.

مرزهای کارConstraints

مرزها رو از اول روشن کنیم: cluster آزمایشی، namespace جدا، Ingress controller و StorageClass واقعی و داده ساختگی. اینکه یه resource تو YAML داریم ثابت نمی‌کنه controller یا provisioner پشتش واقعاً کار می‌کنه؛ باید قبل از شروع از خود cluster بپرسیم.

Build three roles: web, API and PostgreSQL. Give network paths their own Services; do not expose the database publicly. Put ordinary settings in a ConfigMap and sensitive values in a Secret, while remembering that a Secret alone does not guarantee encryption at rest or restricted access. Give the database a PVC and the app probes and reasonable resource requests.

هفت ایستگاهSeven checkpoints

۱ — کلاستر را آماده کن

هفت ایستگاه داری و هرکدوم یه سؤال: مسیر شبکه کجاست؟ config از کجا میاد؟ Secret کی می‌تونه بخونه؟ PVC واقعاً Bound شده؟ Ingress controller قانون رو گرفته؟ با این سؤال‌ها جلو برو تا پروژه تبدیل به «یه عالمه YAML» نشه.

Record context, nodes, Ingress controller and StorageClass. Install or enable missing components in the local environment first. Evidence must show the controller and default StorageClass; a CRD alone is not enough.

راهنمایی

برای هر افزونه بپرس چه controllerی object را اجرا می‌کند و کجا داده provision می‌شود.

۲ — مرز namespace و پیکربندی

namespace اختصاصی بساز. آدرس DB، نام پایگاه و تنظیم غیرمحرمانه رو جدا از image تعریف کن؛ رمز رو در Secret بساز و فایل محلی‌اش رو وارد Git نکن. مدرک: objectها در namespace موردنظرند و مقدار حساس در manifest/image چاپ نشده.

Create a dedicated namespace. Keep DB host, database name and non-secret settings outside the image; create the password Secret without committing its local source file. Evidence: objects are namespaced and the sensitive value is absent from manifests and image.

نکته

Secret در API قابل‌دریافت است؛ RBAC و تنظیمات cluster همچنان مهم‌اند.

۳ — PostgreSQL و دیسک

StatefulSet یا workload مناسب image رسمی PostgreSQL بساز، با Secret، Service داخلی، probe و claim ذخیره‌سازی. پیش از نوشتن داده status PVC و eventهایش رو بخوان. مدرک: claim Bound و دیتابیس Ready؛ Bound هنوز backup رو ثابت نمی‌کنه.

Create PostgreSQL from its official image with a Secret, internal Service, probe and persistent claim. Check PVC status and Events before writing data. Evidence: Bound claim and Ready database; Bound does not prove a backup exists.

راهنمای تشخیص

Pending را با افزایش کورکورانهٔ حجم حل نکن؛ StorageClass، provisioner و Events را بخوان.

۴ — API را به DB وصل کن

API رو با config جدا و اتصال به نام Service پایگاه‌داده اجرا کن؛ داخل Pod، localhost خود همان Pod است. مدرک: log اتصال موفق، health و یک درخواست API. اگه اتصال نیست، مقادیر Secret، DNS، port و network policy رو به‌ترتیب بررسی کن.

Run the API with separate configuration and connect to the database Service name; localhost inside a Pod refers to that Pod. Evidence: successful connection log, health and an API request. If it fails, inspect Secret, DNS, port and NetworkPolicy in order.

۵ — وب، selector و DNS

web رو طوری تنظیم کن که API رو با DNS داخلی صدا بزند. عمدی selector سرویس API رو از labelها جدا کن. پیش از fix، مدرک بگیر: Service هست ولی EndpointSlice خالی است. فقط selector رو اصلاح کن و درخواست داخلی رو تکرار کن.

Configure web to call the API through internal DNS. Deliberately make the API Service selector differ from Pod labels. Before fixing, capture evidence: Service exists but its EndpointSlice is empty. Correct only the selector and retry internally.

چرا این مهم است؟

نام Service حل‌شدن DNS را ثابت می‌کند، نه وجود backend سالم را.

۶ — Ingress را از بیرون بیازمای

یک Ingress برای web بنویس و host آزمایشی رو با port-forward به controller یا روش محیط محلی resolve کن. مسیر رو عمداً غلط کن؛ با status، controller log و پاسخ HTTP تشخیص بده. بعد مسیر رو اصلاح کن. Ingress object بدون controller ترافیکی جابه‌جا نمی‌کنه.

Create an Ingress for web and resolve a test host through the local controller using the environment’s supported method. Break the path deliberately; diagnose with status, controller logs and HTTP response, then repair it. An Ingress object without a controller routes no traffic.

مرز TLS

گواهی آزمایشی محلی با HTTPS عمومی و اعتماد مرورگر یکی نیست. برای TLS معتبر عمومی، DNS و issuer/controller واقعی لازم است.

۷ — داده را بعد از تعویض ثابت کن

از مسیر Ingress رکورد یکتایی بساز. API Pod رو حذف کن و رکورد رو دوباره بخوان؛ سپس PostgreSQL Pod رو در همین محیط آزمایشی جایگزین کن و دوباره بررسی کن. مدرک: رکورد پیش و پس از جایگزین و PVC متصل. در پایان از دادهٔ آزمایش backup artifact بگیر و فقط namespace lab رو پاک کن.

Create a unique record through Ingress. Delete the API Pod and read it again; then replace the PostgreSQL Pod in this disposable environment and check again. Evidence: record before and after replacement and attached PVC. Back up the lab data and clean up only the lab namespace.

احتیاط

حذف Pod با حذف PVC یکی نیست؛ دستور cleanup را قبل از اجرا بخوان و دادهٔ مهم را هدف نگیر.

قبولی یعنی مسیر کامل کار کندAcceptance means the full path works

تحویل شامل نمودار معماری، manifestها، خروجی درخواست از Ingress، DNS داخلی API، EndpointSliceها، وضعیت probeها، نام PVC و مدرک باقی‌ماندن رکورد پس از جایگزینی Pod است. یک فهرست objectهای Running کافی نیست. بگو هر شاهد چه چیزی رو ثابت می‌کنه و چه چیزی رو نه.

Handoff the architecture, manifests, response through Ingress, internal API DNS, EndpointSlices, probe states, PVC name and proof that a record survived Pod replacement. A list of Running objects is insufficient. State what each piece of evidence proves—and what it does not.

راه‌حل مرجع و تحویلReference runbook

ترتیب اجرای پیشنهادی

تو راه‌حل مرجع دنبال یه نسخه جادویی نباش. چیزی که مهمه ترتیب شواهد و مرز مسئولیت‌هاست: Ingress ورودی، Service کشف مقصد، workload اجرا و storage ماندگاری. اگه این زنجیره رو بتونی توضیح بدی، پروژه رو واقعاً فهمیدی.

Context and add-ons → namespace → Secret/ConfigMap → PVC and DB → API and Service → web and Service → Ingress → request and create a record → break selector and route → diagnose from EndpointSlices/logs/status → repair → replace a Pod and read data → backup → scoped cleanup.

kubectl -n lab get deploy,sts,svc,ingress,pvc,pods
kubectl -n lab get endpointslices
kubectl -n lab describe ingress web
kubectl -n lab logs deploy/api --tail=50
kubectl -n lab port-forward svc/ingress-controller 8080:80

نام controller و روش port-forward به توزیع محلی وابسته است؛ فرمان آخر رو با مستندات همان محیط تطبیق بده. نسخهٔ PostgreSQL و app رو ثابت کن و برای دادهٔ مهم، restore رو جداگانه آزمایش کن. فصل بعد همین اجزا رو با RBAC، HPA و سیاست منابع وارد تمرین عملیاتی می‌کنه.

Controller names and port-forward details vary by local distribution; adapt the last command to its documentation. Pin PostgreSQL and app versions, and test restore separately for valuable data. The final project adds RBAC, HPA and resource policy to this application.
