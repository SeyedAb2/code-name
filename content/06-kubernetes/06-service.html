Service و انواعش

Services and their types

Podها می‌آیند و می‌روند؛ Service نام و مسیر پایدار است.

Pods come and go; a Service provides a stable name and route.

کلاینت دنبال Pod گمشده می‌گرددA client is chasing a vanished Pod

Deployment سه Pod دارد. کلاینت IP یکی را در config گذاشته؛ rollout انجام می‌شود، Pod عوض می‌شود و درخواست‌ها به آدرس مرده می‌روند. راه‌حل این نیست که client هر بار IPها را حدس بزند؛ باید یک نام/مقصد پایدار جلوی مجموعهٔ Podها باشد.

A Deployment has three Pods. The client hard-coded one IP; a rollout replaces the Pod and requests go nowhere. The client should not guess changing addresses. Put a stable name and destination in front of the selected Pods.

Service selector را با label Podها جور می‌کند و EndpointSliceها مقصدهای فعلی را نگه می‌دارند. data plane کلاستر ترافیک را به endpointهای آماده می‌رساند. Service خود برنامه یا process تازه نمی‌سازد؛ اگر selector چیزی را نگیرد، backend ندارد.

A Service selector matches Pod labels, and EndpointSlices represent current destinations. The cluster data plane routes traffic to eligible endpoints. A Service does not create an app process; with a selector matching nothing, it has no backends.

IPهای Pod ممکن است عوض شوند؛ DNS و virtual address مربوط به Service تا وقتی خود Service و DNS کلاستر برقرارند، ثابت‌تر می‌ماند.

Pod IPs can change; the Service name and virtual address remain stable while the Service and cluster DNS exist.

port و targetPort دو جای مختلف‌اندport and targetPort are different sides

port پورتی است که Service در معرض مصرف‌کننده‌هایش می‌گذارد؛ targetPort پورت مقصد در Pod است. مقدار targetPort می‌تواند نام پورت container هم باشد. اگر service port=80 و targetPort=8080 باشد، کلاینت Service:80 را می‌زند، اما backend باید واقعاً روی 8080 گوش کند. قبول YAML ثابت نمی‌کند listener وجود دارد.

port is the Service-facing port; targetPort is the destination port on the Pod and may refer to a named container port. If port=80 and targetPort=8080, clients use Service:80 while the backend must actually listen on 8080. Accepted YAML does not prove a listener exists.

ClusterIP نوع پیش‌فرض برای دسترسی درون کلاستر است. DNS معمولاً نام service را در namespace خودش resolve می‌کند؛ از namespace دیگر FQDN می‌تواند شکل web.lab.svc.cluster.local داشته باشد، اما cluster domain قابل‌تغییر است. NodePort روی nodeها یک پورت باز می‌کند؛ این به‌تنهایی firewall یا اینترنت عمومی را تنظیم نمی‌کند. LoadBalancer از integration محیط برای load balancer بیرونی درخواست می‌دهد؛ روی cluster محلی ممکن است pending بماند مگر provider/implementation داشته باشی.

ClusterIP is the default for in-cluster access. DNS usually resolves a Service name within its namespace; cross-namespace FQDNs often look like web.lab.svc.cluster.local, though cluster domain can vary. NodePort opens a port on nodes but does not configure firewall or public reachability by itself. LoadBalancer asks the environment integration for an external balancer; locally it may remain pending without an implementation.

Headless یعنی بدون virtual IPHeadless means no virtual IP

با clusterIP: None Service virtual IP معمول ندارد؛ DNS به‌جای یک مقصد مجازی، رکوردهای مربوط به endpointها را می‌دهد. این برای بعضی سامانه‌های stateful یا discovery سطح پایین مفید است، اما بار انتخاب/تعادل مقصد می‌تواند به client منتقل شود. Service هم HTTP path/host routing انجام نمی‌دهد؛ آن موضوع فصل بعد است.

With clusterIP: None, the Service has no normal virtual IP; DNS returns records for endpoints instead. This can fit some stateful or low-level discovery needs, but client-side endpoint selection may be required. A Service also does not route HTTP by path or host; that belongs to the next chapter.

lab: IPها عوض شوند، درخواست نهLab: let Pod IPs change, not the request

یک Deployment سه‌تایی در namespace lab بساز و label app=web بده. Service ClusterIP با selector همان label، port 80 و targetPort واقعی برنامه تعریف کن. قبل از آزمون، get service و get endpointslices را ببین؛ Service وجود دارد ولی اگر endpoint list خالی است، selector یا readiness مسئله دارد.

Create a three-replica Deployment in namespace lab with label app=web. Define a ClusterIP Service selecting that label, with port 80 and the app’s real targetPort. Inspect the Service and EndpointSlices before testing; an empty endpoint list points to selector or readiness, not DNS first.

apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: lab
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
  - name: http
    port: 80
    targetPort: 8080

از Pod موقتی داخل lab، درخواست http://web را چند بار بفرست و پاسخ/نسخهٔ backend را ثبت کن. بعد یکی از Podها را حذف کن و EndpointSlice و IPهای تازه را ببین؛ client همچنان همان DNS name را می‌زند. اتصال موفق ثابت می‌کند مسیر در آن لحظه کار کرده، نه اینکه همهٔ نسخه‌ها یا failureها تست شده‌اند.

From a temporary client Pod in lab, request http://web repeatedly and record backend responses. Delete one backend and inspect EndpointSlices and new Pod IPs; the client still uses the same DNS name. A successful request proves that path worked then, not that every version or failure mode was tested.

شکست عمدی: selector Service را به app=typo تغییر بده. kubectl get endpointslices -n lab باید مقصدی نشان ندهد و DNS همچنان می‌تواند نام Service را resolve کند. اگر curl timeout شد، اول selector، label Pod و EndpointSlice را بررسی کن، نه DNS. selector را اصلاح و با درخواست تازه verify کن.

Deliberate fault: change the Service selector to app=typo. EndpointSlices should show no matching backends, while DNS can still resolve the Service name. If a request times out, inspect selector, Pod labels, and EndpointSlices before blaming DNS. Fix the selector and verify with a new request.

نوع را با مرز دسترسی انتخاب کنChoose the type for the access boundary

نوع / Typeمناسب برای / Useمرز / Boundary
ClusterIPارتباط داخلیبه‌تنهایی public نیست
NodePortآزمایش/دسترسی از node address در محیط کنترل‌شدهfirewall و public routing را خودت بررسی کن
LoadBalancerدرخواست load balancer بیرونی از providerنیازمند integration و ممکن است هزینه‌دار باشد
Headlessکشف مستقیم endpointهابدون ClusterIP معمول؛ client باید جزئیات را مدیریت کند

NodePort و LoadBalancer را روی cluster واقعی بدون بررسی دسترسی/هزینه روشن نکن. نوع Service دربارهٔ exposure تصمیم می‌گیرد؛ مجوز، firewall، TLS و سیاست عمومی هنوز جدا هستند.

Do not enable NodePort or LoadBalancer on a real cluster without checking access and cost. Service type influences exposure, but authorization, firewall, TLS, and public policy remain separate.

Service نام پایدار است؛ نه مسیریاب HTTPA Service stabilizes access; it is not an HTTP router

ClusterIP، NodePort و LoadBalancer مرزهای مختلف دسترسی می‌سازند؛ selector و EndpointSlice backendها را دنبال می‌کنند. Service به‌تنهایی بر اساس host/path درخواست را تقسیم نمی‌کند. فصل بعد ورودی HTTP و routing را جدا بررسی می‌کنیم.

ClusterIP, NodePort, and LoadBalancer provide different access boundaries; selectors and EndpointSlices track backends. A Service alone does not route requests by host/path. Next we look at HTTP ingress and routing.
