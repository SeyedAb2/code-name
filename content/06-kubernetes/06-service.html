Services and their types

کلاینت دنبال Pod گمشده می‌گرددA client is chasing a vanished Pod

سه Pod سالم داری و کلاینت هم مستقیم IP یکی‌شون رو ذخیره کرده. rollout می‌کنی، اون Pod می‌ره و ناگهان کلاینت داره به یه آدرس مرده زنگ می‌زنه. قرار نیست مصرف‌کننده هر بار فهرست Podها رو حدس بزنه. Service یه مقصد پایدار جلوی این مجموعه می‌ذاره.

A Deployment has three Pods. The client hard-coded one IP; a rollout replaces the Pod and requests go nowhere. The client should not guess changing addresses. Put a stable name and destination in front of the selected Pods.

Service selector رو با label Podها جور می‌کنه و EndpointSliceها مقصدهای فعلی رو نگه می‌دارن. data plane کلاستر ترافیک رو به endpointهای آماده می‌رساند. Service خود برنامه یا process تازه نمی‌سازه؛ اگه selector چیزی رو نگیرد، backend نداره.

A Service selector matches Pod labels, and EndpointSlices represent current destinations. The cluster data plane routes traffic to eligible endpoints. A Service does not create an app process; with a selector matching nothing, it has no backends.

IPهای Pod ممکن است عوض بشن؛ DNS و virtual address مربوط به Service تا وقتی خود Service و DNS کلاستر برقرارند، ثابت‌تر می‌مونه.

Pod IPs can change; the Service name and virtual address remain stable while the Service and cluster DNS exist.

port و targetPort دو جای مختلف‌اندport and targetPort are different sides

اینجا دو پورت داریم که خیلی راحت قاطی می‌شن. port دری هست که Service به کلاینت نشون می‌ده؛ targetPort دری هست که برنامه داخل Pod واقعاً پشتش گوش می‌ده. بیایم مسیر یه درخواست رو از اول تا آخر دنبال کنیم تا این دوتا تو ذهنمون جابه‌جا نشن.

port is the Service-facing port; targetPort is the destination port on the Pod and may refer to a named container port. If port=80 and targetPort=8080, clients use Service:80 while the backend must actually listen on 8080. Accepted YAML does not prove a listener exists.

ClusterIP نوع پیش‌فرض برای دسترسی درون کلاستر است. DNS معمولاً نام service رو در namespace خودش resolve می‌کنه؛ از namespace دیگر FQDN می‌تونه شکل web.lab.svc.cluster.local داشته باشه، ولی cluster domain قابل‌تغییر است. NodePort روی nodeها یک پورت باز می‌کنه؛ این به‌تنهایی firewall یا اینترنت عمومی رو تنظیم نمی‌کنه. LoadBalancer از integration محیط برای load balancer بیرونی درخواست می‌ده؛ روی cluster محلی ممکن است pending بماند مگر provider/implementation داشته باشی.

ClusterIP is the default for in-cluster access. DNS usually resolves a Service name within its namespace; cross-namespace FQDNs often look like web.lab.svc.cluster.local, though cluster domain can vary. NodePort opens a port on nodes but does not configure firewall or public reachability by itself. LoadBalancer asks the environment integration for an external balancer; locally it may remain pending without an implementation.

Headless یعنی بدون virtual IPHeadless means no virtual IP

با clusterIP: None Service virtual IP معمول نداره؛ DNS به‌جای یک مقصد مجازی، رکوردهای مربوط به endpointها رو می‌ده. این برای بعضی سولینه‌های stateful یا discovery سطح پایین مفید است، ولی بار انتخاب/تعادل مقصد می‌تونه به client منتقل بشه. Service هم HTTP path/host routing انجام نمی‌ده؛ اون موضوع فصل بعد است.

With clusterIP: None, the Service has no normal virtual IP; DNS returns records for endpoints instead. This can fit some stateful or low-level discovery needs, but client-side endpoint selection may be required. A Service also does not route HTTP by path or host; that belongs to the next chapter.

lab: IPها عوض بشن، درخواست نهLab: let Pod IPs change, not the request

وقتشه ثابت کنیم Service واقعاً برای «Pod مشخص» ساخته نشده. درخواست می‌فرستیم، یکی از Podها رو حذف می‌کنیم، صبر می‌کنیم جایگزین بیاد و دوباره همون Service رو می‌زنیم. اگه طراحی درست باشه، کلاینت لازم نیست چیزی درباره IP جدید بدونه.

Create a three-replica Deployment in namespace lab with label app=web. Define a ClusterIP Service selecting that label, with port 80 and the app’s real targetPort. Inspect the Service and EndpointSlices before testing; an empty endpoint list points to selector or readiness, not DNS first.

apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: lab
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
  - name: http
    port: 80
    targetPort: 8080

از Pod موقتی داخل lab، درخواست http://web رو چند بار بفرست و پاسخ/نسخهٔ backend رو ثبت کن. بعد یکی از Podها رو حذف کن و EndpointSlice و IPهای تازه رو ببین؛ client همچنان همان DNS name رو می‌زند. اتصال موفق ثابت می‌کنه مسیر در اون لحظه کار کرده، نه اینکه همهٔ نسخه‌ها یا failureها تست شده‌اند.

From a temporary client Pod in lab, request http://web repeatedly and record backend responses. Delete one backend and inspect EndpointSlices and new Pod IPs; the client still uses the same DNS name. A successful request proves that path worked then, not that every version or failure mode was tested.

شکست عمدی: selector Service رو به app=typo تغییر بده. kubectl get endpointslices -n lab باید مقصدی نشان ندهد و DNS همچنان می‌تونه نام Service رو resolve کند. اگه curl timeout شد، اول selector، label Pod و EndpointSlice رو بررسی کن، نه DNS. selector رو اصلاح و با درخواست تازه بررسی کن.

Deliberate fault: change the Service selector to app=typo. EndpointSlices should show no matching backends, while DNS can still resolve the Service name. If a request times out, inspect selector, Pod labels, and EndpointSlices before blaming DNS. Fix the selector and verify with a new request.

نوع رو با مرز دسترسی انتخاب کنChoose the type for the access boundary

نوع / Typeمناسب برای / Useمرز / Boundary

NodePortآزمایش/دسترسی از node address در محیط کنترل‌شدهfirewall و public routing را خودت بررسی کن
LoadBalancerدرخواست load balancer بیرونی از providerنیازمند integration و ممکن است هزینه‌دار باشد

NodePort و LoadBalancer رو روی cluster واقعی بدون بررسی دسترسی/هزینه روشن نکن. نوع Service دربارهٔ exposure تصمیم می‌گیره؛ مجوز، firewall، TLS و سیاست عمومی هنوز جدا هستن.

Do not enable NodePort or LoadBalancer on a real cluster without checking access and cost. Service type influences exposure, but authorization, firewall, TLS, and public policy remain separate.

Service نام پایدار است؛ نه مسیریاب HTTPA Service stabilizes access; it is not an HTTP router

پس Service یه اسم و مقصد پایدار برای یه مجموعه Pod می‌ده؛ نه اینکه خودش مسیریابی HTTP بر اساس path و host انجام بده. وقتی بخوایم چند سرویس رو پشت یک ورودی عمومی جمع کنیم، می‌رسیم به فصل بعد: Ingress.

ClusterIP, NodePort, and LoadBalancer provide different access boundaries; selectors and EndpointSlices track backends. A Service alone does not route requests by host/path. Next we look at HTTP ingress and routing.
