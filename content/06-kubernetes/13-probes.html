Probes: liveness, readiness, startup

«بالا هست» با «آمادهٔ ترافیک است» یکی نیست.

“It is up” is not the same as “it is ready for traffic.”

healthcheck که restart loop ساختThe health check that created a restart loop

برنامهٔ تازه ۴۰ ثانیه برای بارگذاری model لازم دارد. liveness بعد از ۵ ثانیه endpoint را می‌زند و در پاسخ‌نگرفتن container را restart می‌کند. برنامه هیچ‌وقت به مرحلهٔ آماده‌شدن نمی‌رسد. Probe بد می‌تواند از نبود probe خطرناک‌تر باشد.

A new app needs 40 seconds to load its model. A liveness probe checks after five seconds and restarts the container when no response arrives. The app never finishes startup. A bad probe can be worse than no probe.

سه پرسش جدا داریم: startup «آیا startup تمام شد؟»، readiness «آیا الان ترافیک بگیرم؟»، liveness «آیا باید container را restart کنم؟» از یک endpoint برای هر سه استفاده نکن مگر معنایشان واقعاً یکی باشد.

There are three questions: startup—has initialization completed? readiness—should I receive traffic now? liveness—should this container restart? Do not reuse one endpoint for all three unless their meanings genuinely match.

ترتیب probeها تعیین‌کننده استProbe sequencing matters

اگر startupProbe تعریف شود، تا موفق‌شدنش liveness و readiness اجرا نمی‌شوند. پس برای برنامهٔ کند، startup زمان راه‌اندازی را پوشش می‌دهد؛ readiness بعد از آن gate ترافیک است؛ liveness فقط وقتی شکست ماندگار نشان می‌دهد process گیر کرده، restart می‌کند. readiness failure process را restart نمی‌کند.

When startupProbe exists, liveness and readiness checks wait until it succeeds. Startup covers slow initialization; readiness then gates traffic; liveness restarts only when a persistent failure indicates the process is stuck. Readiness failure does not restart the process.

شکست readiness راه ترافیک را می‌بندد؛ شکست liveness پس از threshold به restart می‌رسد.

Readiness failure stops routing; liveness failure restarts after its threshold.

Probe باید ارزان و معنادار باشدA probe should be cheap and meaningful

HTTP probe status code موفق می‌خواهد؛ TCP فقط اتصال پورت را می‌سنجد؛ exec فرمان را داخل container اجرا می‌کند و gRPC health check در نسخه/clusterهای پشتیبان ممکن است. انتخاب را با health behavior برنامه جور کن. HTTP 200 روی root شاید فقط static page را ثابت کند، نه آماده‌بودن dependency ضروری را؛ از طرف دیگر چک عمیق database در liveness می‌تواند خرابی dependency را به restart storm تبدیل کند.

HTTP probes expect a successful status; TCP checks whether a port accepts a connection; exec runs a command in the container; gRPC health checks depend on cluster/version support. Match the probe to application semantics. HTTP 200 on root may prove only a static page, while a deep database check in liveness can turn a dependency outage into a restart storm.

initialDelaySeconds، periodSeconds، timeoutSeconds، successThreshold و failureThreshold رفتار را شکل می‌دهند. Probe بیش‌ازحد تهاجمی false failure می‌سازد؛ interval بزرگ recovery را دیر می‌بیند. startupProbe می‌تواند حداکثر زمان startup را با period×failureThreshold تعریف کند؛ مقدار را از اندازه‌گیری cold start انتخاب کن، نه حدس.

initialDelaySeconds, periodSeconds, timeoutSeconds, successThreshold, and failureThreshold shape behavior. Aggressive probes cause false failures; long intervals delay detection. A startupProbe can bound startup with period × failureThreshold; choose it from measured cold starts, not guesswork.

آزمایش: آماده‌شدن کند و dependency موقتLab: slow startup and temporary dependency failure

برنامهٔ آزمایشی disposable را با endpointهای /startup، /ready و /live بالا بیاور؛ startup تا پایان init ناموفق، readiness وابسته به آماده‌بودن درخواست‌پذیری، و liveness فقط گیرکردن process را بسنجد. Probeهای HTTP را با timeout و threshold متناسب تنظیم کن. برای startup حدود راه‌اندازی را با cold start چندباره اندازه بگیر و Pod status/event را مشاهده کن.

Run a disposable app with /startup, /ready, and /live endpoints: startup remains false during initialization, readiness reflects whether requests can be served, and liveness detects a stuck process only. Set HTTP probes with measured timeouts and thresholds. Measure cold starts and watch Pod status/events.

حالت dependency را موقتاً fail کن. readiness باید false شود و endpoint از Service خارج شود؛ process باید روشن بماند. dependency که برگشته، readiness باید دوباره true شود. این ثابت نمی‌کند کارکرد business همهٔ مسیرها درست است؛ فقط contract probe را می‌سنجد.

Temporarily fail the dependency. Readiness should become false and the endpoint should leave the Service, while the process stays alive. When the dependency recovers, readiness should return. This proves the probe contract, not every business path.

حالا liveness را عمداً با timeout/threshold بسیار تهاجمی روی endpoint کند بگذار. restart count باید بالا برود و lastState/events زمان failure را نشان دهند. شواهد را ذخیره کن، config را برگردان: startupProbe برای init طولانی، readiness برای traffic، liveness سبک برای deadlock. سپس rollout و endpoint membership را verify کن.

Now make liveness deliberately aggressive against the slow endpoint. Restart count should rise and lastState/events show failures. Capture evidence, then fix the design: startup for long initialization, readiness for traffic, and a cheap liveness check for deadlock. Verify rollout and endpoint membership.
