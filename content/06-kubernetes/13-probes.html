“It is up” is not the same as “it is ready for traffic.”

healthcheck که restart loop ساختThe health check that created a restart loop

برنامه برای بالا اومدن ۴۰ ثانیه وقت می‌خواد. liveness از ثانیه پنجم شروع می‌کنه به زدن endpoint و چون جواب نمی‌گیره، container رو restart می‌کنه. نتیجه؟ برنامه هیچ‌وقت فرصت نمی‌کنه سالم بشه. یعنی یه healthcheck بد می‌تونه خودش عامل خرابی بشه.

A new app needs 40 seconds to load its model. A liveness probe checks after five seconds and restarts the container when no response arrives. The app never finishes startup. A bad probe can be worse than no probe.

سه پرسش جدا داریم: startup «آیا startup تمام شد؟»، readiness «آیا الان ترافیک بگیرم؟»، liveness «آیا باید container رو restart کنم؟» از یک endpoint برای هر سه استفاده نکن مگر معنایشان واقعاً یکی باشه.

There are three questions: startup—has initialization completed? readiness—should I receive traffic now? liveness—should this container restart? Do not reuse one endpoint for all three unless their meanings genuinely match.

ترتیب probeها تعیین‌کننده استProbe sequencing matters

سه سؤال رو از هم جدا کن: «startup تموم شد؟»، «الان آماده گرفتن ترافیکه؟»، «اون‌قدر گیر کرده که باید restart بشه؟». startup، readiness و liveness جواب همین سه سؤالن. وقتی یکی رو جای اون یکی استفاده کنی، رفتار عجیب کاملاً قابل انتظار می‌شه.

When startupProbe exists, liveness and readiness checks wait until it succeeds. Startup covers slow initialization; readiness then gates traffic; liveness restarts only when a persistent failure indicates the process is stuck. Readiness failure does not restart the process.

شکست readiness راه ترافیک رو می‌بندد؛ شکست liveness پس از threshold به restart می‌رسه.

Readiness failure stops routing; liveness failure restarts after its threshold.

Probe باید ارزان و معنادار باشهA probe should be cheap and meaningful

Probe باید هم ارزون باشه، هم معنی‌دار. endpointی که برای هر check پنج dependency بیرونی رو صدا می‌زنه، ممکنه با یه اختلال کوچک کل سرویس رو از مدار بندازه. healthcheck خوب کمترین کاری رو می‌کنه که همون سؤال مشخص رو جواب بده.

HTTP probes expect a successful status; TCP checks whether a port accepts a connection; exec runs a command in the container; gRPC health checks depend on cluster/version support. Match the probe to application semantics. HTTP 200 on root may prove only a static page, while a deep database check in liveness can turn a dependency outage into a restart storm.

initialDelaySeconds، periodSeconds، timeoutSeconds، successThreshold و failureThreshold رفتار رو شکل می‌دن. Probe بیش‌ازحد تهاجمی false failure می‌سازه؛ interval بزرگ recovery رو دیر می‌بینه. startupProbe می‌تونه حداکثر زمان startup رو با period×failureThreshold تعریف کند؛ مقدار رو از اندازه‌گیری cold start انتخاب کن، نه حدس.

initialDelaySeconds, periodSeconds, timeoutSeconds, successThreshold, and failureThreshold shape behavior. Aggressive probes cause false failures; long intervals delay detection. A startupProbe can bound startup with period × failureThreshold; choose it from measured cold starts, not guesswork.

آزمایش: آماده‌شدن کند و dependency موقتLab: slow startup and temporary dependency failure

برنامهٔ آزمایشی آزمایشی رو با endpointهای /startup، /ready و /live بالا بیاور؛ startup تا پایان init ناموفق، readiness وابسته به آماده‌بودن درخواست‌پذیری، و liveness فقط گیرکردن process رو بسنجد. Probeهای HTTP رو با timeout و threshold متناسب تنظیم کن. برای startup حدود راه‌اندازی رو با cold start چندباره اندازه بگیر و Pod status/event رو مشاهده کن.

Run a disposable app with /startup, /ready, and /live endpoints: startup remains false during initialization, readiness reflects whether requests can be served, and liveness detects a stuck process only. Set HTTP probes with measured timeouts and thresholds. Measure cold starts and watch Pod status/events.

حالت dependency رو موقتاً fail کن. readiness باید false بشه و endpoint از Service خارج بشه؛ process باید روشن بماند. dependency که برگشته، readiness باید دوباره true بشه. این ثابت نمی‌کنه کارکرد business همهٔ مسیرها درست است؛ فقط contract probe رو می‌سنجد.

Temporarily fail the dependency. Readiness should become false and the endpoint should leave the Service, while the process stays alive. When the dependency recovers, readiness should return. This proves the probe contract, not every business path.

حالا liveness رو عمداً با timeout/threshold بسیار تهاجمی روی endpoint کند بگذار. restart count باید بالا برود و lastState/events زمان failure رو نشان دهند. شواهد رو ذخیره کن، config رو برگردان: startupProbe برای init طولانی، readiness برای traffic، liveness سبک برای deadlock. سپس rollout و endpoint membership رو بررسی کن.

Now make liveness deliberately aggressive against the slow endpoint. Restart count should rise and lastState/events show failures. Capture evidence, then fix the design: startup for long initialization, readiness for traffic, and a cheap liveness check for deadlock. Verify rollout and endpoint membership.

Startup gives initialization time; readiness gates traffic; liveness detects stuck processes and restarts. Cheap endpoints with distinct meanings prevent restart loops. Next we match workload controllers to the job they actually perform.
