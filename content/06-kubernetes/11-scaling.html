ترافیک دو برابر شد؛ تعداد Podها هنوز یکی استTraffic doubled; the replica count did not

ترافیک دو برابر شده و هنوز فقط یه Pod داری. می‌گی «CPU بالاست، پس HPA خودش حلش می‌کنه». شاید؛ ولی اول باید بدونیم این CPU از کجا میاد، نسبت به چی حساب می‌شه و اصلاً node جا برای replica تازه داره یا نه. Autoscaling هم یه حلقه اندازه‌گیری و تصمیمه، نه دکمهٔ جادو.

A Deployment serves traffic with one Pod. Load and latency rise. “CPU is high, add Pods” may be right or useless: where does the metric come from, what is it relative to, and is there node capacity?

HorizontalPodAutoscaler (HPA) یک control loop است که metric رو می‌خونه و replica مطلوب target رو تغییر می‌ده. Deployment همان Podها رو می‌سازه/کم می‌کنه. HPA خودش node جدید نمی‌سازه و برای cold start یا وابستگی کند معجزه نمی‌کنه.

A HorizontalPodAutoscaler (HPA) is a control loop that reads metrics and changes a target’s desired replica count. The Deployment creates or removes Pods. HPA does not create nodes and cannot erase cold starts or slow dependencies.

مقیاس‌دادن حلقهٔ بازخورد است؛ metric با تأخیر می‌رسه و replica تازه هم زمان می‌خواد آماده بشه.

Scaling is a feedback loop; metrics arrive with delay and new replicas take time to become ready.

درصد CPU نسبت به request استCPU utilization is relative to its request

عدد ۶۰٪ تو HPA یعنی ۶۰٪ کل CPU ماشین نیست. برای CPU utilization، مصرف رو نسبت به request همون containerها می‌سنجه. اگه request درست نداشته باشی، درصدی که فکر می‌کنی داری عملاً پایه محکمی نداره.

For CPU utilization, average Pod CPU use is compared with its CPU request. averageUtilization: 60 targets roughly 60% of requests, not 60% of the whole machine. Without CPU requests for relevant containers, HPA cannot calculate utilization reliably and the metric may be unknown. Revisit the previous chapter’s units and manifests.

فرمول تقریبی تصمیم متناسب است: replica پیشنهادی برابر ceil(current replicas × current metric / target metric). این تخمین به metric موجود، حداقل/حداکثر، readiness و behavior limits محدود است؛ تعداد رو بی‌درنگ و بی‌نوسان تضمین نمی‌کنه.

A rough recommendation is ceil(current replicas × current metric / target metric). Actual scaling is bounded by metric availability, min/max replicas, readiness, and behavior rules; it is not instantaneous or oscillation-free.

kubectl describe hpa web -n lab
kubectl get deployment web -n lab

در HPA، current/target و Events رو ببین. اگه target unknown است، get hpa خطا می‌ده یا metrics-server/provider حاضر نیست یا request ناقص است. kubectl top pods فقط دادهٔ فوری/تقریبی می‌ده و به‌تنهایی نشان نمی‌ده چرا HPA تصمیم گرفت.

Inspect current/target metrics and Events. An unknown target may mean the metrics provider is absent or requests are incomplete. kubectl top gives a recent view, but alone does not explain the HPA decision.

حداقل، حداکثر و آرام‌شدن حلقهMinimums, maximums, and smoothing the loop

حلقه‌ای که سریع بالا و پایین بپره خودش مشکل می‌سازه. برای همین حداقل، حداکثر و رفتار scale-up/scale-down مهمه. می‌خوای سیستم واکنش نشون بده، ولی نه اینکه با هر نوسان کوچیک تعداد Podها رو مثل آسانسور بالا پایین کنه.

minReplicas is the floor and maxReplicas caps capacity/cost. Behavior and stabilization policies can smooth changes; defaults and API details vary by version, so inspect the cluster’s HPA spec and versioned docs. Scale-in may wait through a stabilization window.

متریک‌های custom یا external نیازمند adapter/API و منبعی هستن که آن‌ها رو عرضه کند؛ metrics-server به‌تنهایی CPU/Memory resource metrics رو می‌ده، نه هر Prometheus query دلخواه رو. مقیاس‌پذیری رو با capacity planning، load test و بررسی dependencyها همراه کن.

Custom and external metrics need an adapter/API and a source that serves them. metrics-server provides resource metrics such as CPU/memory, not arbitrary Prometheus queries by itself. Pair autoscaling with capacity planning, load tests, and dependency analysis.

lab: بار محدود، متریک قابل‌مشاهدهLab: bounded load, visible metrics

روی کلاستر local آزمایشی، metrics-server یا provider سازگار رو با راهنمای همان توزیع فعال کن. Deployment آزمایشی CPU request مشخص، health مناسب و چند replica max داشته باشه. HPA با min=1، max=4 و target utilization محدود بساز. ابتدا وضعیت metrics و HPA رو ببین؛ اگه unknown است، پیش از تولید بار provider و request رو تعمیر کن.

On a disposable local cluster, enable metrics-server or a compatible provider using the distribution guide. Use a test Deployment with CPU requests, health checks, and a small replica ceiling. Create an HPA with min=1, max=4, and a bounded utilization target. Inspect metrics first; if unknown, fix provider/request before load.

بار تولید رو با loop محدود، timeout و تعداد درخواست ثابت انجام بده؛ هیچ تست نامحدود اجرا نکن. هر چند ثانیه kubectl get hpa و deployment رو بخوان و زمان تا scale-out و Ready شدن Pod تازه رو ثبت کن. سپس بار رو متوقف و رفتار scale-in رو در پنجرهٔ زمانی cluster ببین.

Generate bounded load with a fixed request count and timeout; never run an unbounded test. Watch HPA and Deployment every few seconds, recording time to scale out and Pod readiness. Stop load and observe scale-in over the cluster’s stabilization window.

شکست عمدی: CPU request رو از container هدف بردار یا metrics provider رو در محیط آزمایشی از کار بینداز. HPA باید metric unknown/error نشان دهد یا تصمیم نگیرد؛ describe events شواهد رو می‌ده. علت رو اصلاح و دوباره load محدود اجرا کن. در پایان workload و هر تغییر cluster رو پاک کن.

Deliberately remove the target container’s CPU request or disable the metrics provider in the disposable environment. HPA should show an unknown/error metric or fail to decide; describe/events are evidence. Fix the cause, rerun bounded load, then remove the workload and lab changes.

Autoscaling ظرفیت رو طراحی نمی‌کنهAutoscaling does not design capacity for you

HPA می‌تونه تعداد replica رو با metric تنظیم کنه؛ ظرفیت node، سرعت startup و معماری برنامه رو برات طراحی نمی‌کنه. اگه گلوگاه جای دیگه‌ست، اضافه‌کردن Pod فقط صف رو از یه جا به جای دیگه می‌بره.

HPA helps when metrics, requests, bounds, and readiness behavior are sound. It changes replica count only; nodes, databases, and dependencies may remain bottlenecks. Next we move from scaling to access boundaries: namespaces, ServiceAccounts, and RBAC.
