Why Kubernetes; what Docker alone cannot do

کِی لازم است و — مهم‌تر — کِی لازم نیست.

When you need it and — more importantly — when you do not.

۷۵دقیقهminutes
۱۸تمرینexercises

روی یک لپ‌تاپ عالی بود؛ حالا پنجاه تا شدهOne laptop was easy; now there are fifty

روی لپ‌تاپ، docker compose up جواب می‌داد. حالا سرویس روی سه ماشین اجراست، یکی از ماشین‌ها پر شده، یک کانتینر مرده و نسخهٔ تازه باید بدون گم‌شدن ترافیک منتشر شود. اپراتور در حال چک‌کردن چند terminal است و فهرست کارها هر دقیقه بلندتر می‌شود.

On a laptop, docker compose up was enough. Now the service spans three machines, one is full, a container has died, and a new release must arrive without losing traffic. An operator is checking multiple terminals while the checklist grows.

قبل از اسم‌بردن از Kubernetes، تخمین بزن: اگر پنجاه container روی ده ماشین باشد، چه کسی باید محل هرکدام، سلامتشان، جایگزین‌شدن نسخهٔ خراب و مقصد ترافیک را هماهنگ کند؟ Docker یک container را اجرا می‌کند؛ به‌تنهایی مدیرِ ناوگان چندماشینه و سیاست استقرار شما نیست.

Before naming Kubernetes, estimate the work: with fifty containers across ten machines, who coordinates placement, health, replacement, and traffic? Docker runs containers; by itself it is not your multi-machine fleet manager or deployment policy.

چک‌لیست دستی را واقعاً بشمارCount the manual work

برای یک سرویس سه replica روی دو host، اگر یکی متوقف شد، باید بفهمی کدام بود، ظرف تازه کجا اجرا شود، مقصد شبکه چطور به‌روز شود و نسخهٔ درست کدام است. حالا این کار را برای ده‌ها سرویس و چند رخداد هم‌زمان تصور کن. شکست عمدی این فصل همین‌جاست: کانتینر را متوقف می‌کنیم و می‌بینیم چه کسی آن replica را برمی‌گرداند. روی یک ماشین disposable انجام بده؛ هنوز production را دست نمی‌زنیم.

For a service with three replicas across two hosts, a failure requires identifying the instance, finding a place for a replacement, updating network destinations, and selecting the right version. Now imagine dozens of services and simultaneous incidents. Our deliberate failure is to stop one container and see who restores the replica. Use a disposable machine; production is out of scope.

docker ps
docker stop demo-web-2
docker ps -a

دستور stop فقط همان container را متوقف می‌کند. خروجی Exited ثابت می‌کند process تمام شده؛ ثابت نمی‌کند replica جایگزین شده یا کاربر همچنان سرویس می‌گیرد. با اجرای دستی run می‌توانی آن را دوباره بالا بیاوری، اما حالا مسئولیت، حافظهٔ ماشین‌ها، network و تکرارپذیری هم دستی‌اند.

stop halts that container. Exited proves the process ended; it does not prove a replacement exists or users still have service. You can run another container manually, but placement, machine capacity, networking, and repeatability remain your responsibility.

اگر آزمایش را انجام می‌دهی نام container را با نمونهٔ خودت عوض کن و فقط workload disposable را متوقف کن. روی سرویس کاری یا production اجرا نکن.

Use your disposable container name and stop only that workload. Do not run this against a work service or production.

Kubernetes دنبال شکل مطلوب می‌گرددKubernetes keeps reconciling toward a desired shape

به‌جای اینکه بگویی «این container را یک‌بار اجرا کن»، یک شیء اعلام می‌کند: این workload باید سه replica داشته باشد. controllerها وضعیت فعلی را می‌خوانند و هرجا با خواسته فرق دارد، برای نزدیک‌شدن به آن اقدام می‌کنند. اگر Pod تحت مدیریت Deployment حذف شود، کنترلر می‌کوشد replica را به تعداد موردنظر برگرداند.

Instead of saying “run this container once,” an object declares that a workload should have three replicas. Controllers observe current state and act when it differs from intent. If a Pod managed by a Deployment disappears, its controller attempts to restore the requested replica count.

این «تلاش برای هماهنگ‌سازی» جادو نیست: اگر node ظرفیت ندارد، image pull نمی‌شود یا storage خراب است، desired state هنوز برقرار نشده. Kubernetes خرابی برنامه را تعمیر نمی‌کند؛ می‌تواند Pod را دوباره بسازد یا restart کند، اما علت را باید از event، status و log پیدا کنی.

Reconciliation is not magic. If there is no node capacity, an image cannot be pulled, or storage is broken, the desired state remains unmet. Kubernetes does not repair application defects; it may recreate or restart a Pod, but you still diagnose the cause from events, status, and logs.

control loop پیوسته اختلاف خواسته و وضعیت را می‌سنجد؛ یک فرمان یک‌باره نیست. «دو Pod حاضر است» با «سه Pod آمادهٔ پاسخ‌گویی‌اند» فرق دارد.

A control loop repeatedly compares intent and reality; it is not a one-time command. “Two Pods exist” differs from “three Pods are ready to serve.”

کلاستر هم خودش محصولی برای اداره‌کردن است: control plane، nodeها، upgrade، دسترسی، هزینه و عیب‌یابی. Kubernetes نه برنامهٔ درست طراحی می‌کند، نه backup قابل‌بازیابی را تضمین می‌کند، نه به‌طور خودکار همهٔ nodeها را از خرابی سخت‌افزار نجات می‌دهد.

The cluster is itself a system to operate: control plane, nodes, upgrades, access, cost, and troubleshooting. Kubernetes does not design a correct app, guarantee recoverable backups, or magically rescue every hardware failure.

گاهی جواب درست، Compose استSometimes Compose is the right answer

برای یک اپ کوچک روی یک VPS، اگر یک نفر deploy می‌کند و downtime کوتاه پذیرفتنی است، Docker Compose ممکن است ساده‌تر، قابل‌فهم‌تر و ارزان‌تر باشد. Kubernetes وقتی ارزش دارد که نیاز واقعی به هماهنگی چند ماشین، تعداد replica، rollout، خودترمیمی یا استاندارد مشترک تیم داری و برای ادارهٔ خود کلاستر هم وقت/توان گذاشته‌ای. «شرکت‌های بزرگ استفاده می‌کنند» دلیل فنی کافی نیست.

For a small app on one VPS, with one operator and acceptable short downtime, Docker Compose may be simpler, clearer, and cheaper. Kubernetes earns its cost when you need multi-node coordination, replicas, rollouts, self-healing, or a team-wide platform—and can operate the cluster itself. “Large companies use it” is not a technical reason.

kind یا minikube ابزار تمرین کلاستر محلی‌اند، نه خود مفهوم Kubernetes و نه مدرک production readiness. kind معمولاً nodeها را به شکل container اجرا می‌کند؛ minikube هم محیط محلی یادگیری/توسعه فراهم می‌کند. جزئیات نصب و runtime را از مستند رسمی گزینه‌ات بگیر؛ بسته به سیستم و نسخه فرق دارد.

kind and minikube are local learning tools, not Kubernetes itself and not proof of production readiness. kind commonly runs nodes as containers; minikube provides a local learning/development cluster. Follow the selected tool's official install guide because runtime and platform details vary.

برای شروع، فقط کلاستر disposable بساز و context/nodeها را ببین. هنوز workload ایجاد نمی‌کنیم؛ فصل بعد اجزای معماری را باز می‌کنیم. اگر نصب cluster شکست خورد، ثبت کن کدام پیش‌نیاز/محدودیت میزبان مانع شد، نه اینکه آن را با ارتقای بی‌دلیل لپ‌تاپ حل کنی.

For now, create only a disposable cluster and inspect its context and nodes. We will not create workloads yet; the next chapter examines cluster architecture. If setup fails, identify the host prerequisite or limitation rather than upgrading your laptop without evidence.

۱۸ تمرین؛ از تشخیص نیاز تا انتخاب ابزار18 exercises, from needs to tool choice

۱. کانتینر متوقف‌شده

docker stop را زدی و container در Exited است. چه چیزی را فهمیدی و چه چیزی را هنوز نمی‌دانی؟

You ran docker stop and see Exited. What do you know, and what remains unknown?

پاسخ و دلیل

process آن container تمام شده؛ دربارهٔ جایگزینی، دسترسی کاربر یا علت توقف چیزی ثابت نشده.

That container's process ended; replacement, user access, and the reason for stopping remain unproven.

۲. یک VPS، دو سرویس

یک سایت و PostgreSQL روی یک VPS داری. با چه پرسش‌هایی تصمیم می‌گیری Compose کافی است؟

A site and PostgreSQL run on one VPS. What questions help decide whether Compose is enough?

پاسخ

نیاز واقعی به چند node/replica، تحمل downtime، تعداد اپراتورها، هزینهٔ عملیات و مهارت نگهداری کلاستر را بسنج؛ ممکن است Compose مناسب باشد.

Assess multi-node/replica needs, downtime tolerance, operators, operational cost, and cluster expertise. Compose may fit.

۳. Desired state

اعلام کرده‌ای replicas=3 ولی فقط دو Pod حاضرند. کنترلر چه اختلافی می‌بیند؟

You declared replicas=3 but only two Pods exist. What difference does the controller see?

پاسخ

وضعیت مشاهده‌شده با خواسته یکی نیست؛ کنترلر تلاش می‌کند کمبود را جبران کند، اگر منابع و سایر قیود اجازه دهند.

Observed state differs from intent; a controller attempts to reconcile if capacity and constraints permit.

۴. جایگزینی موفق نشده

Replica تازه در Pending مانده. آیا می‌توان نتیجه گرفت self-healing کار نمی‌کند؟

A replacement replica is Pending. Can you conclude self-healing is broken?

پاسخ

نه؛ کنترلر ممکن است تلاش کرده باشد اما ظرفیت، scheduler constraint، image یا volume مانع اجراست. علت را از status/events بررسی کن.

No. Reconciliation may be working while capacity, scheduling constraints, image, or storage block startup. Inspect status/events.

۵. Self-healing چه چیزی را درست نمی‌کند؟

برنامه هر بار با exception خراب می‌شود و Kubernetes آن را دوباره اجرا می‌کند. مشکل حل شده؟

The app throws an exception each time and Kubernetes restarts it. Is the problem fixed?

پاسخ

نه؛ restart علت نرم‌افزاری را درمان نمی‌کند. crash loop را با status و log تحلیل کن.

No. Restart does not repair the application defect. Diagnose the crash loop from status and logs.

۶. scheduling

کدام تصمیم به scheduler مربوط است: انتخاب node برای Pod یا انتخاب route HTTP؟

Which is scheduling: selecting a node for a Pod or selecting an HTTP route?

پاسخ

انتخاب node؛ تقسیم/مسیریابی درخواست وظیفهٔ شبکه و Service/proxy است.

Node placement. Request routing belongs to networking and Service/proxy mechanisms.

۷. Service discovery

چرا client نباید IP اتفاقی یک Pod را ثابت داخل config بگذارد؟

Why should a client not hard-code a Pod's transient IP?

پاسخ

Podها عوض می‌شوند؛ Service نام/نشانی پایدارتر و مسیر دسترسی به مجموعهٔ endpointها می‌دهد.

Pods are replaced; a Service provides a more stable name/address over a set of endpoints.

۸. Rollout

آیا rollout موفق فقط یعنی manifest پذیرفته شد؟

Does a successful rollout mean only that a manifest was accepted?

پاسخ

نه؛ پذیرش شیء با آماده‌شدن نسخه فرق دارد. وضعیت rollout و readiness لازم است؛ کارکرد کاربر هم ممکن است جدا نیاز به آزمون داشته باشد.

No. Object acceptance differs from a ready rollout; rollout/readiness evidence is needed, and user behavior may need separate testing.

۹. ده ماشین، ده نسخه؟

یک نسخه باید روی چند node پخش شود. Kubernetes چه هماهنگی‌ای را ساده‌تر می‌کند؟

One release must run across several nodes. What coordination does Kubernetes simplify?

پاسخ

اعلام تعداد/نسخهٔ مطلوب، scheduling و پیگیری rollout؛ اما image، config، ظرفیت و تست باید درست باشند.

Declaring desired replicas/version, scheduling, and rollout tracking—while image, config, capacity, and tests remain your responsibility.

۱۰. چند کانتینر دستی

چهار container را دستی روی دو host پخش کرده‌ای. هنگام مرگ یکی، سه کار پس از تشخیص چیست؟

You manually spread four containers across two hosts. After one dies, name three follow-up tasks.

پاسخ

جایگزینی/ظرفیت، ثبت نسخه و config، و به‌روزرسانی مقصد ترافیک؛ بسته به سیستم کارهای بیشتری هم هست.

Replacement/capacity, version/config consistency, and updating traffic destinations; more work may remain.

۱۱. کلاستر خالی

kubectl get nodes موفق شد. آیا برنامه‌ات deploy شده؟

kubectl get nodes succeeded. Is your app deployed?

پاسخ

نه؛ فقط API/context به کلاستر پاسخ داده و nodeها گزارش شده‌اند؛ workload هنوز ساخته نشده.

No. The API/context responded and nodes were listed; no workload has been created.

۱۲. kind یا minikube؟

برای تست محلی کلاستر و برای تمرین سادهٔ یک node، کدام گزینه‌ها را بررسی می‌کنی؟

Which options would you compare for local cluster testing and a simple single-node lab?

پاسخ

kind برای nodeهای container-based و minikube برای کلاستر محلی؛ محدودیت host و هدف آزمایش تعیین‌کننده است. مستند جاری ابزار را دنبال کن.

kind for container-based nodes and minikube for a local cluster; host constraints and lab goals decide. Follow current tool documentation.

۱۳. هزینهٔ پنهان

تیم کوچک، اپ کم‌ترافیک و بدون on-call دارد. چه هزینه‌هایی را قبل از مهاجرت به Kubernetes حساب می‌کنی؟

A small team has a low-traffic app and no on-call. What costs should it assess before adopting Kubernetes?

پاسخ

مدیریت/ارتقای کلاستر، امنیت، شبکه، storage، پایش، incident response و زمان یادگیری؛ هزینه فقط VM نیست.

Cluster operation/upgrades, security, networking, storage, monitoring, incident response, and learning—not just VM cost.

۱۴. Kubernetes چه چیزی را تضمین نمی‌کند؟

سه موردی را بگو که صرف نصب Kubernetes حل نمی‌شوند.

Name three problems that installing Kubernetes does not solve by itself.

پاسخ

باگ اپ، طراحی backup/restore، امنیت کامل، یا ظرفیت nodeها؛ انتخاب هر سه کافی است.

Application bugs, backup/restore design, complete security, or node capacity; any three suffice.

۱۵. شکست برنامه یا node؟

یک Pod crash کرده ولی node سالم است. چه تفاوتی در تحلیل داری؟

A Pod crashes while its node is healthy. How does diagnosis differ?

پاسخ

برنامه، command، config، dependency و log را بررسی کن؛ خرابی node را علت پیش‌فرض نگیر.

Inspect app, command, config, dependencies, and logs; do not assume node failure.

۱۶. rollout برگشت‌پذیر

چرا داشتن rollback در controller به معنی بازگرداندن دادهٔ ناسازگار نیست؟

Why does controller rollback not imply incompatible data can be restored?

پاسخ

rollback معمولاً نسخهٔ workload را برمی‌گرداند، نه اثر migration مخرب یا داده‌ای که حذف شده.

Rollback usually restores workload version, not destructive migration effects or deleted data.

۱۷. مسئله را خودکار کن

از چک‌لیست چندماشینهٔ داستان، یک کار تکراری بنویس که desired state می‌تواند مدیریت‌پذیرتر کند.

From the fleet checklist, name one repetitive task a desired-state system can manage.

پاسخ نمونه

حفظ replica count یا rollout نسخه روی replicaها، مشروط به سلامت controller و ظرفیت.

Maintaining replica count or rolling a version across replicas, assuming a functioning controller and capacity.

۱۸. توصیه به تیم

تیم از تو می‌خواهد «چون مد شده» Kubernetes بیاورد. پاسخ مهندسی دوطرفه بنویس.

A team wants Kubernetes “because it is popular.” Write a balanced engineering response.

پاسخ نمونه

اول نیاز چندماشینه، دسترس‌پذیری و عملیات را بسنجیم. اگر Compose نیاز فعلی را با هزینهٔ کمتر برآورده می‌کند، فعلاً همان؛ اگر fleet coordination درد واقعی است و توان نگهداری داریم، آزمایش محدود طراحی کنیم.

Assess multi-node, availability, and operational needs first. If Compose meets them at lower cost, keep it. If fleet coordination is a real pain and we can operate the platform, design a limited trial.

آزمایش کوتاه: چرا یک node کافی نیست؟Small lab: why is one node not the whole story?

این فصل فقط زیرساخت تمرین را آماده می‌کند. با kind، minikube یا playground محلی، یک context بساز و kubectl config current-context و kubectl get nodes اجرا کن. نام context و تعداد nodeها شاهدند که client به cluster جواب‌گو وصل است؛ این نه برنامه deploy می‌کند و نه آمادگی production را ثابت می‌کند. برای اجرا از دستور فعلی راهنمای رسمی ابزار انتخابی استفاده کن؛ از دستور نصب نسخه‌قدیمی کپی نکن.

This chapter only prepares the practice environment. Create a context with kind, minikube, or a local playground, then run kubectl config current-context and kubectl get nodes. Context and node output prove the client reached a cluster; they do not deploy an app or prove production readiness. Use the selected tool’s current official quick start rather than copying stale installation commands.

اگر ماشینت منابع کافی ندارد، playground را انتخاب کن؛ لازم نیست برای این فصل cluster چندماشینهٔ واقعی بخری. در گزارش آزمایش بنویس چه چیزی پاسخ داد، چه چیزی را هنوز امتحان نکردی، و چرا آن workload دستی می‌توانست انتخاب اشتباهی باشد.

If your machine lacks resources, use a playground; you do not need to buy a multi-node cluster for this chapter. Record what responded, what remains untested, and why Kubernetes might still be the wrong choice for the manual workload.

از نیاز شروع کن، نه از manifestStart from the need, not a manifest

Kubernetes وقتی به‌درد می‌خورد که مسئلهٔ هماهنگی را داری: وضعیت مطلوب، جایگزینی، زمان‌بندی و rollout در چند node. اما اگر اپ و عملیاتت کوچک‌اند، پیچیدگی خودش هزینه و سطح خرابی تازه‌ای می‌سازد. حالا که دلیل استفاده و محدودیتش روشن شد، فصل بعد به اجزای کلاستر نگاه می‌کنیم تا بدانیم این هماهنگی پشت صحنه از کجا می‌آید.

Kubernetes helps when you have a coordination problem: desired state, replacement, scheduling, and rollout across nodes. But for a small app and operation, its complexity creates new cost and failure modes. With the motivation and limits clear, the next chapter examines the cluster components behind that coordination.
