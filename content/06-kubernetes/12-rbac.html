Who is allowed to do what.

اپ فقط باید ConfigMap بخواندThe app only needs to read a ConfigMap

اپ فقط باید یه ConfigMap رو بخونه. برای اینکه سریع راه بیفته، بهش دسترسی زیادی دادی و حالا همون هویت می‌تونه Pod حذف کنه. اینجا سؤال «وصل می‌شه یا نه» نیست؛ سؤال دقیق‌تره: این هویت روی این resource، دقیقاً چه فعلی اجازه داره؟

A workload gets cluster credentials to read configuration, but that identity can also delete Pods and inspect other namespaces. The question is not whether access works—it is exactly which actions we granted.

Authentication می‌گه درخواست از چه هویتی است؛ authorization تصمیم می‌گیره اون هویت چه عملی روی چه resourceای انجام دهد. Namespace منابع رو گروه‌بندی و scope می‌کنه، ولی به‌تنهایی مرز امنیتی کامل نیست؛ دسترسی شبکه، node و control plane جداگانه‌اند.

Authentication identifies the caller; authorization decides which action it may perform on which resource. Namespaces group and scope resources, but are not a complete security boundary by themselves; network, node, and control-plane access are separate concerns.

Identity → Binding → Rule → تصمیم APIIdentity → binding → rules → API decision

RBAC رو با چهار تکه نگه دار: هویت کیه، binding به کدوم نقش وصلش کرده، rule چه resource و verbهایی رو اجازه داده و API در نهایت چی تصمیم می‌گیره. هر وقت دسترسی عجیب شد، همین زنجیره رو از اول بخون.

A ServiceAccount is a workload identity. A Role defines namespace-scoped permissions using apiGroups, resources, and verbs; a RoleBinding attaches it to users, groups, or ServiceAccounts. ClusterRole is cluster-wide/reusable; ClusterRoleBinding grants it cluster-wide. A RoleBinding may also bind a ClusterRole but only within one namespace.

identity به‌تنهایی مجوز نیست؛ binding اون رو به ruleها وصل می‌کنه.

Identity alone grants no permission; a binding attaches it to rules.

lab: خواندن مجاز؛ حذف ممنوعLab: read allowed, deletion denied

یه ServiceAccount می‌سازیم که ConfigMap رو بخونه، ولی نتونه حذفش کنه. بعد با auth can-i هر دو حالت رو امتحان می‌کنیم. این yes/no خیلی ارزشمندتر از اینه که فقط به YAML نگاه کنیم و حدس بزنیم دسترسی درست بسته شده.

Create a ServiceAccount in a disposable namespace named lab. Give it only get/list/watch on ConfigMaps in the empty (core) API group, and bind that Role to the account. No wildcards are needed.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: config-reader
  namespace: lab
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list", "watch"]
---

RoleBinding باید subject رو با kind ServiceAccount، name و namespace کامل معرفی کند. بعد kubectl auth can-i list configmaps --as=system:serviceaccount:lab:reader -n lab باید yes بدهد؛ delete pods باید no باشه. این دستور policy رو برای هویت شبیه‌سازی‌شده می‌پرسد، نه اینکه برنامه واقعاً request موفق زده باشه. Caller باید اجازهٔ impersonation داشته باشه.

The RoleBinding subject must name the ServiceAccount and namespace. Then auth can-i should answer yes for listing ConfigMaps and no for deleting Pods. This asks authorization for a simulated identity; it does not prove the app made a successful request. The caller needs permission to impersonate.

شکست عمدی: ClusterRole view رو با ClusterRoleBinding به این حساب بده و kubectl auth can-i list pods --all-namespaces --as=... رو بررسی کن. حالا دسترسی از نیاز ConfigMap در lab بسیار گسترده‌تر است. binding پهن رو حذف، Role محدود رو نگه‌دار و دوباره list ConfigMaps و list Pods در namespaceهای دیگر رو تست کن. خروجی yes/no رو برای هر عمل ثبت کن.

Deliberate overgrant: bind the built-in view ClusterRole to this account with a ClusterRoleBinding, then test list Pods across namespaces. Its access is much broader than reading one namespace’s ConfigMaps. Remove the broad binding, retain the narrow Role, and retest listing ConfigMaps and Pods elsewhere. Record each allow/deny result.

توکن ServiceAccount رو چاپ یا در log نگذار. رفتار automount token در نسخه‌ها و تنظیم‌ها فرق کرده: tokenهای projected کوتاه‌عمر در clusterهای جدید رایج‌اند، ولی automount رو می‌توان بست و توزیع‌ها جزئیات دارن. اگه برنامه API نمی‌خونه، token لازم نیست؛ دسترسی رو غیرفعال کن.

Never print or log a ServiceAccount token. Token automount behavior varies by version and configuration: short-lived projected tokens are common in modern clusters, but automount can be disabled and distributions differ. If the app does not call the API, it does not need a token; disable access.

از مجوز گسترده به مجوز لازمFrom broad permission to the permission needed

قاعدهٔ کمترین دسترسی با resource و verb مشخص نوشته می‌شه. Role با get روی configmaps اجازهٔ list نمی‌ده؛ اگه اپ list لازم داره، جداگانه اضافه کن. verbs شامل get/list/watch/create/update/patch/delete هستن. RBAC allow rule داره، نه deny rule؛ مجوزی که match نیست رد می‌شه.

Least privilege names resources and verbs. A Role with get on ConfigMaps does not grant list; add it only if the app needs it. Common verbs include get/list/watch/create/update/patch/delete. RBAC defines allow rules rather than deny rules; unmatched requests are denied.

مجوز cluster-wide رو فقط وقتی بده که کار واقعی به اون نیاز داره. ServiceAccount برای workload است، user identity معمولاً از provider/credential دیگری میاد. secret token رو در YAML یا Git ذخیره نکن. Namespace هم tenancy کامل نیست؛ network policy، admission policy و node isolation لایه‌های دیگری هستن.

Grant cluster-wide access only for a real need. ServiceAccounts serve workloads; human identity commonly comes from another provider/credential system. Do not store token secrets in YAML or Git. A namespace is not complete tenancy; network, admission, and node isolation are other layers.

دسترسی رو با آزمون yes/no تحویل بدهHand off permissions with yes/no evidence

دسترسی رو با «فکر کنم محدوده» تحویل نده. با همون هویتی که workload استفاده می‌کنه سؤال مشخص بپرس و جواب yes/no بگیر. کمترین دسترسی وقتی معنی داره که واقعاً امتحانش کرده باشی.

Namespace scopes resources, ServiceAccount identifies workloads, Role defines rules, and Binding attaches identity. Before handoff ask exactly what the identity can do, and prove selected allow/deny cases with can-i. Next we distinguish liveness, readiness, and startup with probes.
