Model Binding؛ درخواست چطور به ورودی endpoint تبدیل می‌شود؟

Model binding: how does a request become endpoint input?

کلاینت می‌گوید page=3 را فرستاده، ولی endpoint عدد صفر می‌بیند؛ یا body ظاهراً JSON درست است اما درخواست ۴۰۰ می‌گیرد. قبل از دست‌کاری validation، بفهمیم ASP.NET Core هر پارامتر را از کجا می‌خواند و شکست کدام مرز است.

A client says it sent page=3, but the endpoint sees zero; or valid-looking JSON gets a 400. Before changing validation, trace where ASP.NET Core reads each parameter and identify the failed boundary.

درخواست درست به‌نظر می‌رسد؛ چرا action مقدار دیگری می‌بیند؟The request looks right; why does the action see something else?

در GET /orders/42?page=3 عدد ۴۲ بخشی از مسیر است و ۳ در query آمده. فریم‌ورک متن درخواست را به نوع مقصد تبدیل می‌کند؛ انتخاب منبع و تبدیل، Model Binding است. اما باید قرارداد endpoint روشن کند هر مقدار دقیقاً از کجا می‌آید.

In GET /orders/42?page=3, 42 is in the route and 3 is in the query. The framework converts request text to target types; source selection and conversion are model binding. The endpoint contract must make each source explicit.

درخواست آزمایشی · Sample request
GET /orders/42?page=3 HTTP/1.1
Host: localhost:5080
Accept: application/json

اگر مسیر ۴۲ باشد اما query شامل id=99 باشد، کدام شناسه مدنظر است؟ در MVC منبع را روشن کن؛ این پاسخ باید ۴۲ و ۳ باشد، اما هنوز وجود سفارش یا مجازبودن دسترسی را ثابت نمی‌کند.

If the route contains 42 while the query has id=99, which identifier is intended? Make the source explicit in MVC. The response should contain 42 and 3, but that does not prove the order exists or access is authorized.

MVC controller · binding صریح
[HttpGet("orders/{id:int}")]
public IActionResult GetOrder(
    [FromRoute] int id,
    [FromQuery] int page = 1)
{
    return Ok(new { id, page });
}

با integration test درخواست واقعی بفرست و JSON را assert کن. فراخوانی مستقیم متد action، route matching و binding را امتحان نمی‌کند.

Send a real request in an integration test and assert the JSON. Calling the action method directly does not exercise route matching or binding.

چهار منبع را از جای مقدار تشخیص بدهIdentify the four sources by where the value appears

route برای هویت منبع در مسیر؛ query برای جست‌وجو و صفحه‌بندی؛ header برای metadata درخواست؛ body برای payload ساختاریافته. وقتی مقدار نادرست است اول request واقعی را ببین، نه اسم parameter را.

A route carries resource identity; a query carries search and pagination; headers carry request metadata; a body carries structured payload. When a value is wrong, inspect the actual request before trusting a parameter name.

منبعنمونهکاربردSource / example / purpose
FromRoute/orders/42شناسه در مسیرPath identity
FromQuery?page=3&state=openفیلتر و صفحه‌بندیFiltering and pagination
FromHeaderX-Request-Idmetadata درخواستRequest metadata
FromBody{ "title": "draft" }دادهٔ ایجاد یا تغییرCreate/update payload
سه منبع در MVC · Three MVC sources
[HttpGet("orders/{id:int}")]
public IActionResult Search(
    [FromRoute] int id,
    [FromQuery] string? state,
    [FromHeader(Name = "X-Request-Id")] string? requestId)
{
    return Ok(new { id, state, requestId });
}

نام C# الزاماً نام روی wire نیست؛ header را با نام قراردادی‌اش تست کن. موفقیت binding فقط می‌گوید مقدار به پارامتر رسیده، نه این‌که از نظر دامنه معتبر است.

A C# name is not necessarily the wire name; test the header using its contract name. Successful binding proves only that a value reached the parameter, not that it is domain-valid.

Minimal API و MVC قواعد یکسانی ندارندMinimal APIs and MVC do not share identical inference rules

Minimal API هم route، query، header، body و service دارد، اما منبع پارامتر گاهی استنتاج می‌شود. نوع ساده معمولاً از route/query می‌آید؛ نوع پیچیدهٔ ثبت‌نشده در DI معمولاً از body، ولی نوع ثبت‌شده ممکن است service باشد. برای قرارداد مهم source را روشن کن و روی نسخهٔ هدف integration test بگذار.

Minimal APIs also use route, query, headers, body, and services, but parameter sources may be inferred. Simple values commonly come from route/query; an unregistered complex type commonly comes from the body, while a DI-registered type may resolve as a service. Make important sources explicit and test the target framework version.

Minimal API · ورودی روشن
app.MapGet("/orders/{id:int}",
    ([FromRoute] int id, [FromQuery] int page) =>
        Results.Ok(new { id, page }));

app.MapPost("/orders",
    ([FromBody] CreateOrderRequest request) =>
        Results.Created("/orders/42", request));

این مثال صریح‌نویسی را برای خوانایی نشان می‌دهد؛ نه این‌که همهٔ پارامترها همیشه attribute لازم دارند. ثبت یک type در DI می‌تواند inference را تغییر دهد. body inference برای GET، HEAD، OPTIONS و DELETE را مفروض نگیر؛ قرارداد را صریح و تست‌شده انتخاب کن.

This example makes sources explicit for clarity; it does not mean every parameter always requires an attribute. Registering a type in DI can change inference. Do not assume body inference for GET, HEAD, OPTIONS, or DELETE; choose an explicit, tested contract.

درخواست body فقط JSON نیست؛ Content-Type هم مهم استA body is not just JSON; Content-Type matters too

در MVC، [FromBody] معمولاً از input formatter متناسب با Content-Type استفاده می‌کند. اگر درخواست رد شد، وجود body، header و formatter را جدا بررسی کن. media type پشتیبانی‌نشده ممکن است ۴۱۵ بدهد؛ JSON خراب یا تبدیل ناموفق معمولاً خطای ۴۰۰ می‌سازد. خروجی نسخهٔ واقعی را مشاهده کن.

In MVC, [FromBody] typically uses an input formatter selected by Content-Type. If rejected, inspect body presence, header, and formatter separately. An unsupported media type may yield 415; malformed JSON or conversion commonly yields 400. Observe the actual framework version.

درخواست POST · POST request
curl -i -X POST http://localhost:5080/orders \
  -H 'Content-Type: application/json' \
  -d '{"customerId":12,"note":"first order"}'

یک body را به یک پارامتر body نسبت بده. stream درخواست یک‌بار مصرف است؛ دو پارامتر مستقل FromBody همان stream را از ابتدا نمی‌خوانند. فیلدها را در DTO واحد بگذار. DTO bind‌شده هنوز می‌تواند قانون دامنه را نقض کند.

Bind one request body to one body parameter. The request stream is consumed; two independent FromBody parameters cannot each read it from the start. Put fields in one DTO. A bound DTO can still violate a domain rule.

یک DTO برای یک body · One DTO per body
public sealed record CreateOrderRequest(
    int CustomerId,
    string Note,
    IReadOnlyList<CreateOrderLine> Lines);

[HttpPost("orders")]
public IActionResult Create([FromBody] CreateOrderRequest request)
{
    return Created("/orders/42", new { request.CustomerId });
}

مفقود، نامعتبر و خالی سه وضعیت متفاوت‌اندMissing, invalid, and empty are three different states

بدون page ممکن است مقدار پیش‌فرض استفاده شود؛ page=abc تبدیل int را می‌شکند؛ page= رشتهٔ خالی است و به نوع و تنظیمات binding وابسته است. سه درخواست جدا بساز و status و response body را مقایسه کن.

Without page, a default may apply; page=abc breaks integer conversion; page= is empty and behavior depends on type and binding settings. Send three separate requests and compare status and response bodies.

مقایسهٔ ورودی‌ها · Compare inputs
curl -i 'http://localhost:5080/orders/42'
curl -i 'http://localhost:5080/orders/42?page=abc'
curl -i 'http://localhost:5080/orders/42?page='

در MVC با [ApiController] خطای ModelState معمولاً پیش از action پاسخ ۴۰۰ خودکار می‌دهد؛ ممکن است breakpoint action اصلاً نخورد. بعد body response و log را بخوان. این قاعده را به همهٔ Minimal APIها تعمیم نده.

With MVC [ApiController], invalid ModelState commonly produces an automatic 400 before the action; its breakpoint may never hit. Inspect the response body and logs. Do not generalize this behavior to every Minimal API.

ترتیب تشخیص: URL/header واقعی ← body خام ← Content-Type ← status و response ← آیا action اجرا شد؟ ← تبدیل و binding ← validation دامنه. هر گام مرز دیگری را جدا می‌کند.

Debugging order: actual URL/headers ← raw body ← Content-Type ← response ← did the action run? ← conversion/binding ← domain validation. Each step isolates a different boundary.

آزمایشگاه: قرارداد HTTP را با درخواست واقعی محکم کنLab: harden the HTTP contract with real requests

API کوچکی برای سفارش بساز: GET با شناسهٔ route، فیلتر state در query، request id در header و POST از JSON. برای هر مرحله تستی داشته باش که درخواست را از بیرون endpoint بفرستد.

Build a small orders API: GET by route id, filter by query state, accept a request-id header, and create from JSON. At each step, test by sending a request through the endpoint boundary.

  1. منبع ورودی‌های GET را صریح کن و مقدارهای route و query را جدا assert کن.
  2. Declare GET sources explicitly and assert route and query values separately.
  3. POST معتبر بفرست؛ سپس Content-Type را حذف و JSON را خراب کن؛ پاسخ‌ها را کنار هم ثبت کن.
  4. Send a valid POST, then omit Content-Type and corrupt JSON; record responses side by side.
  5. body خالی و object خالی را جدا تست کن؛ نتیجه به DTO و تنظیمات پروژه بستگی دارد.
  6. Test absent body and empty object separately; behavior depends on the DTO and project settings.
  7. در MVC با ApiController ثابت کن خطای تبدیل می‌تواند پیش از اجرای action پاسخ داده شود.
  8. In MVC with ApiController, prove a conversion error can be returned before action execution.
  9. یک JSON معتبر با quantity منفی بساز تا binding موفق و قانون دامنه ناموفق شود.
  10. Send valid JSON with negative quantity so binding succeeds while a domain rule fails.

محدودیت: response نسخه و تنظیمات فعلی برنامه را ثابت می‌کند، نه رفتار همهٔ clientها و proxyها را. secret یا دادهٔ واقعی را در log آزمایش ثبت نکن.

Boundary: the response proves behavior of this framework/configuration, not every client or proxy. Do not log real secrets or user data.

۱۸ تمرین؛ هر جواب request، کد یا evidence می‌خواهد18 exercises: every answer requires a request, code, or evidence

۱. route و query

برای /products/18?currency=EUR action بنویس که هر مقدار را فقط از منبع درست بخواند؛ integration test مقدار response را assert کند.

Write an action for /products/18?currency=EUR that reads each value from the intended source; assert the response in an integration test.

راهنمای حل

FromRoute برای id و FromQuery برای currency. فراخوانی مستقیم متد action routing را پوشش نمی‌دهد.

Use FromRoute for id and FromQuery for currency. Direct method invocation does not test routing.

۲. مقدار پیش‌فرض

page پیش‌فرض ۱ دارد؛ درخواست بدون query و با page=4 بساز و نتیجه را assert کن.

Give page a default of 1; send requests without a query and with page=4, then assert both.

راهنمای حل

امضا را int page=1 و منبع را query قرار بده. این حد مجاز صفحه را ثابت نمی‌کند؛ آن را جدا validate کن.

Declare int page=1 from query. This does not validate allowed page bounds; test those separately.

۳. مقدار abc

page=abc بفرست؛ status، response body و اجرای action را ثبت کن.

Send page=abc; capture status, response body, and whether the action ran.

راهنمای حل

تبدیل int شکست می‌خورد. MVC با ApiController معمولاً پیش از action پاسخ ۴۰۰ می‌دهد؛ نسخه و تنظیمات پروژه را verify کن.

Integer conversion fails. MVC ApiController commonly returns 400 before the action; verify the project version and configuration.

۴. header سفارشی

X-Request-Id را bind کن و با curl مقدار req-123 بفرست؛ نتیجه را در تست بررسی کن.

Bind X-Request-Id, send req-123 with curl, and inspect the result in a test.

راهنمای حل

از FromHeader با Name صریح استفاده کن. اسم پارامتر جای قرارداد HTTP را نمی‌گیرد.

Use FromHeader with an explicit Name. A parameter name does not replace the HTTP contract.

۵. media type نامناسب

JSON را یک بار application/json و بار دیگر text/plain بفرست؛ statusها را ثبت کن.

Send JSON once as application/json and once as text/plain; record both statuses.

راهنمای حل

formatter JSON معمولاً با نوع دوم انتخاب نمی‌شود و ممکن است ۴۱۵ برگردد. response واقعی معیار است.

The JSON formatter commonly rejects the second media type with 415. The actual response is the evidence.

۶. JSON ناقص

body ناقص بفرست و ثابت کن failure parsing با business rejection یکی نیست.

Send malformed JSON and prove parsing failure differs from business rejection.

راهنمای حل

ورود action را با marker تست کن؛ سپس JSON معتبر با مقدار ممنوع بفرست و response دو حالت را مقایسه کن.

Mark action entry, then send valid JSON with a disallowed value and compare the two responses.

۷. دو پارامتر FromBody

امضای دارای دو FromBody را با یک request type جایگزین کن و POST را تست کن.

Replace a signature with two FromBody parameters by one request type and test the POST.

راهنمای حل

یک DTO شامل هر دو فیلد بساز؛ body stream یک‌بار مصرف است.

Create one DTO containing both fields; the request body stream is consumed once.

۸. body غایب و object خالی

هر دو payload را بفرست و پاسخ‌ها را ثبت کن؛ تفاوت احتمالی را از schema توضیح بده.

Send both payloads and record responses; explain differences based on the schema.

راهنمای حل

body غایب با {} یکی نیست. nullable بودن، validation و تنظیمات endpoint را بررسی کن.

An absent body differs from {}. Inspect nullability, validation, and endpoint configuration.

۹. constraint مسیر

برای route با id:int یک id متنی بفرست و مشخص کن ۴۰۴ routing است یا خطای binding.

Send a textual id to an id:int route and determine whether 404 came from routing or binding.

راهنمای حل

constraint ممکن است route را پیش از action رد کند. marker ورود action و درخواست عددی مقایسه‌ای بساز.

The constraint may reject the route before the action. Add an action-entry marker and a numeric control request.

۱۰. DI و Minimal API

یک نوع پیچیده را با و بدون ثبت DI آزمایش کن و منبع binding مشاهده‌شده را بنویس.

Test a complex type with and without DI registration and record the observed binding source.

راهنمای حل

ثبت DI ممکن است آن را service کند؛ type ثبت‌نشده ممکن است body شود. source صریح و integration test مانع غافلگیری است.

DI registration may make it a service; an unregistered type may bind from body. Explicit sources and integration tests prevent surprises.

۱۱. جست‌وجوی GET

جست‌وجو را با query طراحی کن و عبارت دارای فاصله را URL-encode کرده response را assert کن.

Design search with a query parameter; URL-encode a term containing spaces and assert the response.

راهنمای حل

body در GET بین client و واسطه قابل اتکا نیست؛ query را با encoding درست ارسال و decode‌شدن مقدار را test کن.

GET bodies are unreliable across clients and intermediaries; send an encoded query and test the decoded value.

۱۲. binding در برابر قانون دامنه

quantity=-4 را از JSON معتبر bind کن ولی با قانون دامنه رد کن؛ test نشان دهد parsing موفق بوده است.

Bind quantity=-4 from valid JSON but reject it by a domain rule; prove parsing succeeded.

راهنمای حل

نوع و JSON معتبرند، پس binding موفق است. پاسخ رد دامنه را با ۴۰۰ parsing اشتباه نکن.

The type and JSON are valid, so binding succeeds. Do not confuse domain rejection with a parsing 400.

۱۳. ApiController خودکار

با ورودی نامعتبر ثابت کن پاسخ ۴۰۰ پیش از اجرای action تولید شده است.

Prove that invalid input produces a 400 before action execution.

راهنمای حل

شمارندهٔ ورود action را در تست ثبت کن؛ انتظار ۴۰۰ و شمارندهٔ ثابت است. این نتیجه را به همهٔ Minimal APIها تعمیم نده.

Count action entry in the test; expect 400 and an unchanged count. Do not generalize to all Minimal APIs.

۱۴. query تکراری

tag=api&tag=dotnet را به scalar و collection بده و تفاوت را با response نشان بده.

Bind tag=api&tag=dotnet to a scalar and a collection; show the difference in responses.

راهنمای حل

collection قرارداد چندمقداری را بهتر نشان می‌دهد؛ هر دو مقدار را assert کن و رفتار scalar را بدون test فرض نگیر.

A collection expresses multiple values more clearly; assert both and do not assume scalar behavior without a test.

۱۵. نام property JSON

customer_id را برای CustomerId بفرست؛ naming policy یا JsonPropertyName را بررسی و mapping را با test ثابت کن.

Send customer_id for CustomerId; inspect naming policy or JsonPropertyName and prove mapping with a test.

راهنمای حل

رفتار serializer پیکربندی‌شده را ملاک بگیر؛ response یا state را assert کن، نه صرفاً نام C# را.

Use the configured serializer behavior; assert response or state rather than relying on the C# name.

۱۶. تفکیک ۴۱۵ و ۴۰۰

JSON معتبر با media type غلط و JSON خراب با media type درست بفرست؛ status و response را ثبت کن.

Send valid JSON with the wrong media type and malformed JSON with the right one; capture status and response.

راهنمای حل

اولی مشکل formatter/media type و دومی parsing است؛ معمولاً ۴۱۵ در برابر ۴۰۰، اما پاسخ نسخهٔ جاری را تأیید کن.

The first is a formatter/media-type issue and the second parsing; commonly 415 versus 400, but verify the current version.

۱۷. قرارداد endpoint

برای جست‌وجوی سفارش signature و سه request بنویس؛ یکی باید fail شود و test علت را با شواهد تفکیک کند.

Define a search signature and three requests; one must fail and a test must isolate the reason with evidence.

راهنمای حل

route، query و header را explicit کن. response body و ورود endpoint را هم بررسی کن؛ status تنها تشخیص نیست.

Make route, query, and header explicit. Inspect response body and endpoint entry; status alone is not a diagnosis.

۱۸. ticket از موبایل

«Postman کار می‌کند، موبایل ۴۰۰ می‌گیرد». یک test executable بساز که method، URL، header، Content-Type و body را ثبت کند؛ یک تفاوت را عوض و همان تست را تکرار کن.

“Postman works; mobile gets 400.” Build an executable test capturing method, URL, headers, Content-Type, and body; change one difference and rerun it.

راهنمای حل

درخواست موبایل را بازتولید کن، encoding، نام property و media type را یکی‌یکی مقایسه کن. دادهٔ واقعی یا secret را log نکن.

Reproduce the mobile request and compare encoding, property names, and media type one at a time. Do not log real data or secrets.

جمع‌بندی: منبع، تبدیل، معناWrap-up: source, conversion, meaning

اول request واقعی را ببین؛ بعد منبع و تبدیل را پیدا کن؛ پس از ساخته‌شدن DTO، validation و قانون دامنه هنوز باقی‌اند. MVC و Minimal API را یکسان فرض نکن و قرارداد را با integration test نگه دار. حالا که ورودی به مدل تبدیل شده، فصل بعد سراغ اعتبارسنجی می‌رود.

Inspect the actual request first, then trace source and conversion. After a DTO is created, validation and domain rules remain. Do not treat MVC and Minimal APIs as identical; protect the contract with integration tests. Now that input becomes a model, the next chapter tackles validation.
