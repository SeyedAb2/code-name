پیکربندی، محیط و secret؛ مقدار از کجا آمد؟

Configuration, environments, and secrets: where did the value come from?

روی لپ‌تاپ آدرس سرویس درست است؛ در staging برنامه به endpoint دیگری می‌رود و تیم نمی‌داند کدام فایل برنده شده. password هم برای رفع سریع داخل appsettings.json گذاشته شده. بیایید مقدار مؤثر را از ترتیب providerها پیدا کنیم و secret را از کد جدا کنیم.

The address is correct locally, but staging calls another endpoint and nobody knows which file won. A password was also placed in appsettings.json as a quick fix. We will trace the effective value through provider precedence and separate secrets from source code.

یک key، چند منبع؛ کدام مقدار استفاده شد؟One key, several sources: which value was used?

ASP.NET Core تنظیمات را از providerهای مرتب‌شده می‌خواند. در default configuration معمولاً command line بالاترین اولویت را دارد، بعد environment variable، سپس User Secrets در Development، appsettings محیط و بعد appsettings عمومی. آخرین providerای که همان key را دارد برنده می‌شود. پس فایل‌ها را حدسی ویرایش نکن؛ منبع و محیط مؤثر را پیدا کن.

ASP.NET Core reads settings from ordered providers. In default application configuration, command-line values generally have highest priority, followed by environment variables, User Secrets in Development, environment-specific appsettings, then base appsettings. The last provider containing a key wins. Do not edit files by guesswork; identify the active environment and source.

این مسیر برای default application configuration است؛ افزودن provider سفارشی می‌تواند ترتیب را تغییر دهد.

This is the default application-configuration order; adding custom providers can change precedence.

ترتیب خواندن از پایین به بالا در نمودار اولویت را زیاد می‌کند؛ یک appsettings محیطی از فایل عمومی جلوتر است. اما host configuration مثل انتخاب خود environment قواعد خودش را دارد. برای رفع ابهام، اسم مؤثر محیط و providerها را ثبت کن؛ secret value را چاپ نکن.

The diagram moves from lower to higher precedence; environment-specific appsettings overrides the base file. Host configuration, including environment selection, has its own rules. Log the effective environment and provider names to investigate; never print secret values.

Development و Production فقط اسم پوشه نیستندDevelopment and Production are more than filenames

environment در startup انتخاب می‌شود و هم appsettings.{Environment}.json را مشخص می‌کند، هم رفتار برنامه را. وقتی environment variableها تنظیم نشده باشند، environment پیش‌فرض Production است. launchSettings.json برای اجرای local tooling است و خودش deployment configuration سرور نیست. در WebApplication و hosting modelهای قدیمی precedence نام environment می‌تواند متفاوت باشد؛ هم‌زمان DOTNET_ENVIRONMENT و ASPNETCORE_ENVIRONMENT را بی‌دلیل تنظیم نکن و مقدار نهایی را مشاهده کن.

The environment is selected at startup and controls both appsettings.{Environment}.json and application behaviour. When environment variables are unset, Production is the default. launchSettings.json is for local tooling, not server deployment configuration. Precedence between DOTNET_ENVIRONMENT and ASPNETCORE_ENVIRONMENT differs across WebApplication and older hosting models; do not set both casually, and inspect the effective value.

نام محیط در shellهای مختلف
# PowerShell, current session
$env:ASPNETCORE_ENVIRONMENT = "Staging"

# Bash, current shell
export ASPNETCORE_ENVIRONMENT=Staging

dotnet run

اگر در production اشتباهاً Development فعال شود، صفحهٔ خطای توسعه می‌تواند جزئیات داخلی را افشا کند. environment را از startup log تأیید کن؛ به نام branch یا فایل launch profile تکیه نکن.

If Development is accidentally enabled in production, the developer exception page can expose internals. Verify the environment from startup logs; do not infer it from a branch name or launch profile.

یک key منطقی، چند شکل در فایل و shellOne logical key, several file and shell representations

JSON از objectهای تو‌در‌تو استفاده می‌کند؛ environment variableها برای همان hierarchy معمولاً از دو underscore به‌جای colon کمک می‌گیرند. مقایسه را روی key منطقی انجام بده، نه شکل نوشتاری‌اش. حروف بزرگ/کوچک در keyها اغلب case-insensitive است، اما بهتر است تیم یک convention ثابت داشته باشد.

JSON uses nested objects; environment variables commonly use double underscores instead of colons for the same hierarchy. Compare logical keys, not their textual spelling. Keys are generally case-insensitive, but teams should adopt a consistent convention.

یک مقدار آزمایشی، دو provider
// appsettings.json (non-secret value only)
{
  "Catalog": {
    "BaseAddress": "https://dev.example.test"
  }
}

# PowerShell overrides Catalog:BaseAddress
$env:Catalog__BaseAddress = "https://staging.example.test"

در برنامه می‌توانی builder.Configuration["Catalog:BaseAddress"] را بخوانی یا آن را به Options ببندی؛ فصل قبل validation را ساخت. برای اطمینان مقدار نهایی را در debugger امن یا تست integration بررسی کن، اما URL شامل token و خود secret را در log ننویس.

Read builder.Configuration["Catalog:BaseAddress"] or bind it to Options; the previous chapter covered validation. Verify the effective value with a safe debugger or integration test, but do not log URLs containing tokens or secret values.

منبع را ببین، مقدار محرمانه را نهInspect the source without exposing its secret

برای فهمیدن اینکه کدام providerها ثبت شده‌اند، IConfigurationRoot.Providers را enumerate کن. این کار نام providerها را نشان می‌دهد، نه اینکه کدام مقدار secret را دارد. Debug View یا dump کردن همهٔ key/valueها می‌تواند credential را در terminal، log یا screenshot لو بدهد؛ در production چنین خروجی‌ای را منتشر نکن.

Enumerating IConfigurationRoot.Providers reveals registered provider names, not which one supplied a secret. A debug view or dumping all key/value pairs can leak credentials into terminals, logs, or screenshots; never publish that output from production.

نام providerها، بدون valueها
if (builder.Configuration is IConfigurationRoot root)
{
    foreach (var provider in root.Providers)
        app.Logger.LogInformation("Configuration provider: {Provider}",
            provider.GetType().Name);
}

حتی نام منبع می‌تواند بخشی از معماری داخلی را لو بدهد؛ این log را برای تشخیص کنترل‌شده به‌کار ببر و سطح دسترسی log را در نظر بگیر. برای آزمایش precedence، مقدارهای ساختگی و بی‌خطر در دو provider بگذار و نتیجه را با assert بررسی کن.

Even provider names can reveal internal architecture; use this log for controlled diagnosis and consider log access. To test precedence, set harmless synthetic values in two providers and assert the result.

User Secrets برای توسعه است، نه vault productionUser Secrets is for development, not a production vault

برای local development، Secret Manager می‌تواند مقدار را بیرون از پوشهٔ پروژه نگه دارد؛ به source control commit نمی‌شود، اما فایل ذخیره‌شده رمزنگاری‌شده نیست و نباید trusted production store حساب شود. در محیط واقعی از secret manager یا mechanism امن همان پلتفرم استفاده کن و دسترسی را محدود کن. appsettings را برای تنظیم غیرمحرمانه نگه دار و اگر secret قبلاً commit شده، فقط حذف فایل کافی نیست؛ credential را rotate کن.

For local development, Secret Manager stores values outside the project directory and avoids source control, but the stored file is not encrypted and is not a trusted production store. Use the platform's secure secret manager in real environments and restrict access. Keep appsettings for non-secret configuration; if a secret was committed, deleting the file is insufficient—rotate the credential.

فقط با مقدار ساختگی در پروژهٔ توسعه
dotnet user-secrets init
dotnet user-secrets set "Catalog:ApiKey" "LOCAL-DEMO-VALUE-NOT-A-REAL-KEY"
dotnet user-secrets list

خروجی list مقدار secret را نشان می‌دهد؛ این را فقط در محیط local و با demo value اجرا کن و خروجی را در گزارش عمومی نگذار. User Secrets به‌طور پیش‌فرض در Development بارگذاری می‌شود؛ deployment secret را باید از provider مناسب محیط واقعی بگیرد.

The list command prints secret values; run it only locally with a demo value and never publish the output. User Secrets loads by default in Development; deployment secrets must come from a provider suited to the real environment.

provider سفارشی را با قصد اضافه کنAdd custom providers deliberately

هر AddJsonFile یا providerای که بعداً اضافه کنی می‌تواند روی keyهای قبلی اولویت پیدا کند. اگر رفتار ترتیب مهم است، جایی که builder ساخته می‌شود ثبت providerها را پیدا کن؛ provider را برای یک مقدار تصادفی به انتهای فهرست اضافه نکن. بعد از تغییر source، تست کن کدام مقدار برنده شد و آیا reload موردنیاز فعال است.

A later AddJsonFile or provider can override earlier keys. If order matters, inspect where the builder registers providers; do not append a provider casually for one value. After changing sources, test which value wins and whether required reload behaviour is enabled.

پیکربندی را مثل زنجیرهٔ منبع ردیابی کنTrace configuration as a source chain

اول محیط startup را پیدا کن؛ بعد providerهای موجود و ترتیبشان را بررسی کن و برای یک key بی‌خطر، override را با آزمایش ثابت کن. User Secrets فقط برای local development است و چاپ debug view می‌تواند secret را لو بدهد. حالا که منبع و precedence را می‌شناسی، فصل بعد مقدارهای خام را به Options معتبر و قابل‌تزریق وصل می‌کند.

Find the startup environment first, then inspect providers and their order; prove overrides with a harmless test key. User Secrets is for local development, and debug views can expose secrets.
