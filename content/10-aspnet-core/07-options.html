تنظیمات برنامه را چطور امن و قابل‌اعتبارسنجی نگه داریم؟

How do we keep application settings valid and safe?

برنامه deploy شده ولی سرور با URL خالی به سرویس بیرونی وصل می‌شود؛ خطا تازه وسط یک درخواست واقعی دیده می‌شود. تنظیمات را از stringهای پراکنده به قرارداد Options تبدیل می‌کنیم، هنگام شروع اعتبارسنجی می‌کنیم و بعد متناسب با نیاز، snapshot یا reload را انتخاب می‌کنیم.

The app is deployed, but an empty URL makes it call an external service; the failure appears during a real request. We will turn scattered strings into an Options contract, validate it at startup, then choose snapshot or reload behaviour deliberately.

خطای تنظیمات را همان لحظهٔ شروع پیدا کنFind configuration mistakes at startup

Configuration providerها مقدار را از فایل، environment یا منبع دیگر می‌آورند؛ Options آن مقدارها را به یک مدل strongly typed وصل می‌کند. مدل باید قرارداد باشد: نام کلید، default، قید و رفتار در محیط‌های مختلف معلوم. اگر مقدار لازم نداریم، برنامه بهتر است همان startup fail کند تا بعداً برای کاربر خطای مبهم بسازد.

Configuration providers supply values from files, environment variables, or other sources; Options binds them to a strongly typed model. Treat the model as a contract: keys, defaults, constraints, and environment behaviour are explicit. If a required value is missing, fail at startup rather than returning a vague error to a user later.

بخش تنظیمات را bind و validate کنBind and validate a configuration section

مدل و ثبت Options
public sealed class CatalogOptions
{
    public const string SectionName = "Catalog";
    public required Uri BaseAddress { get; init; }
    public int TimeoutSeconds { get; init; } = 5;
}

builder.Services.AddOptions<CatalogOptions>()
    .Bind(builder.Configuration.GetSection(CatalogOptions.SectionName))
    .Validate(x => x.BaseAddress.IsAbsoluteUri,
        "Catalog:BaseAddress must be an absolute URL.")
    .Validate(x => x.TimeoutSeconds is > 0 and <= 60,
        "TimeoutSeconds must be between 1 and 60.")
    .ValidateOnStart();

مدل را با keyهای configuration در محیط واقعی تطبیق بده و default را فقط برای مقدارهایی بگذار که واقعاً اختیاری‌اند. required در C# به‌تنهایی جای validation تنظیمات را نمی‌گیرد؛ bind و validation را در startup تست کن. validation سفارشی هم باید خطای واضح بدهد، نه اینکه secret یا مقدار کامل حساس را در exception چاپ کند.

Match the model to real configuration keys and use defaults only for truly optional values. C# required alone does not replace configuration validation; test binding and validation at startup. Custom validation should be clear without printing secrets or sensitive values in exceptions.

IOptions، Snapshot و Monitor یک چیز نیستندIOptions, Snapshot, and Monitor are not interchangeable

نوعTypeمصرفConsumptionتغییر مقدارChange behaviourنکتهNote
IOptions<T>هر lifetimeمقدار cacheشدهساده؛ برای reload زنده نیست
IOptionsSnapshot<T>Scopedمحاسبهٔ مجدد در scope بعدیدر singleton مستقیم تزریق نکن
IOptionsMonitor<T>Singleton-friendlyمقدار جاری و تغییرات پشتیبانی‌شدهprovider باید reload/change notification بدهد

Snapshot در هر request scope مقدار resolveشده را نگه می‌دارد، اما تضمین نمی‌کند هر provider منبع را زنده reload کند. Monitor برای consumer بلندعمر و notification مناسب است؛ بااین‌حال منبع configuration باید change token بدهد. رفتار را روی provider واقعی تست کن، نه فقط در حافظه.

Snapshot caches a resolved value within a request scope, but does not make every provider reload live. Monitor suits long-lived consumers and change notifications; the configuration source must emit change tokens. Test the actual provider, not only an in-memory setup.

چند نمونه از یک نوع؟ Named OptionsSeveral instances of one type? Named options

اگر برنامه با چند endpoint بیرونی کار می‌کند، دو کلاس تنظیمات تقریباً یکسان نساز. named options می‌تواند یک نوع را برای چند نام پیکربندی کند؛ consumer باید نام درست را بخواهد و هر نام را جدا validate کنی. اگر تنظیمات مستقل و معناهای متفاوت‌اند، مدل‌های جدا خواناترند.

If an app calls several external endpoints, do not create nearly identical settings classes by default. Named options can configure one type under several names; consumers must request the right name and each name needs validation. Separate models may be clearer when meanings truly differ.

نمونهٔ named configuration
builder.Services.AddOptions<RemoteApiOptions>("catalog")
    .BindConfiguration("RemoteApis:Catalog")
    .Validate(x => x.BaseAddress is not null)
    .ValidateOnStart();

builder.Services.AddOptions<RemoteApiOptions>("billing")
    .BindConfiguration("RemoteApis:Billing")
    .Validate(x => x.BaseAddress is not null)
    .ValidateOnStart();

اگر consumer نام را اشتباه بزند، ممکن است default named options را بگیرد یا پیکربندی نامنتظره ببیند؛ نام را در factory/registration مرکزی نگه دار و هر دو config را در تست startup بررسی کن.

A consumer requesting the wrong name may receive default or unexpected options; centralize the name in a factory/registration and validate both configurations in startup tests.

Options ظرف مقدار است، نه محل امن secretOptions is a value model, not a secret store

Bind کردن password به Options آن را امن نمی‌کند. secret را از فایل commitشده یا log بیرون نگه دار؛ برای توسعه User Secrets و برای محیط واقعی secret manager یا مکانیزم امن deploy را به‌کار ببر. environment variableها هم برای secret در همهٔ زیرساخت‌ها بهترین گزینه نیستند؛ مدل تهدید و نحوهٔ دسترسی process را بسنج.

Binding a password into Options does not make it secure. Keep secrets out of committed files and logs; use User Secrets for development and a secret manager or secure deployment mechanism in production. Environment variables are not universally the best secret mechanism; assess the threat model and process access.

تنظیمات هم قرارداد است، هم بخشی از startupConfiguration is a contract and part of startup

Options نام‌های پراکنده را به قرارداد typed تبدیل می‌کند؛ validation خطا را نزدیک شروع برنامه آشکار می‌کند.
