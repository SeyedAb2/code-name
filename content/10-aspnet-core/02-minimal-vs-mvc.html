Minimal API یا Controller؟

Minimal APIs versus controllers

تیم فروشگاه می‌خواهد مسیر GET /orders را اضافه کند. یک نفر می‌گوید «Minimal API کوتاه‌تر است، پس همیشه همان»؛ نفر دیگر می‌گوید «API واقعی حتماً Controller می‌خواهد». هر دو از یک نمونهٔ کوچک نتیجهٔ کلی گرفته‌اند. بیایید همان endpoint را دو بار بسازیم و ببینیم تفاوت کجا مهم می‌شود.

A shop team needs GET /orders. One developer says “Minimal APIs are shorter, so always use those”; another says “real APIs need controllers.” Both generalise from a small sample. Let’s build the same endpoint both ways and see where the difference matters.

کوتاه‌تر بودن تنها معیار نیستShorter is not the only criterion

در فصل قبل درخواست را از host تا endpoint دنبال کردیم. حالا endpoint باید یک کار واقعی انجام دهد: سفارش‌ها را از یک سرویس بگیرد و JSON برگرداند. می‌توانیم route را در Program.cs تعریف کنیم، یا action را در Controller بگذاریم. هر دو روی ASP.NET Core اجرا می‌شوند؛ انتخاب، مرز سازمان‌دهی و قابلیت‌هایی است که تیم لازم دارد.

Last chapter traced a request from host to endpoint. Now an endpoint must do real work: obtain orders from a service and return JSON. We can declare the route in Program.cs or put the action in a controller. Both run on ASP.NET Core; the choice is about organisation and capabilities the team needs.

Minimal API یک مدل endpoint سبک و صریح است، نه API ناقص. Controller-based API هم جایگزین معتبر است، نه شکل «حرفه‌ای‌تر» به‌صورت خودکار. راهنمای فعلی Microsoft Minimal APIs را برای پروژه‌های جدید توصیه می‌کند؛ controllerها همچنان برای تیم‌ها و برنامه‌هایی با الگوی MVC یا نیازهای مشخص گزینه‌اند.

A Minimal API is a lightweight, explicit endpoint model, not an incomplete API. Controller-based APIs remain a valid alternative, not automatically the more professional form. Current Microsoft guidance recommends Minimal APIs for new projects; controllers remain useful for teams and applications with MVC conventions or specific needs.

یک endpoint با Minimal APIAn endpoint with a Minimal API

نسخهٔ اول را با یک handler مستقیم می‌نویسیم. هدف نمایش کوچک‌ترین شکل ممکن نیست؛ می‌خواهیم مرز HTTP را از سرویس سفارش جدا نگه داریم. Handler پارامتر را می‌گیرد، کار را به collaborator می‌سپارد و نتیجهٔ HTTP را مشخص می‌کند.

We write the first version with a direct handler. The goal is not the smallest possible syntax; it is to keep the HTTP boundary separate from order logic. The handler receives a collaborator, delegates work, and describes the HTTP result.

برنامهٔ Minimal API
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSingleton<IOrderReader, DemoOrderReader>();

var app = builder.Build();
app.MapGet("/orders", (IOrderReader reader) =>
    Results.Ok(reader.GetRecent()));
app.Run();

public interface IOrderReader
{
    IReadOnlyList<OrderSummary> GetRecent();
}

Minimal API از DI برای پارامتر سرویس استفاده می‌کند. با رشد routeها می‌توان endpointها را در extension method یا گروه route مرتب کرد؛ برنامه مجبور نیست تمام handlerها را در یک Program.cs بزرگ نگه دارد. جزئیات routing، parameter binding و response type در فصل‌های خودشان می‌آیند.

Minimal APIs use DI for service parameters. As routes grow, endpoint registration can move into extension methods or route groups; the app is not forced to keep every handler in one large Program.cs. Routing, parameter binding, and response types are covered in their own chapters.

همان کار در ControllerThe same work in a controller

حالا سرویس همان است اما مرز HTTP در یک class قرار دارد. باید سرویس MVC را اضافه کنیم و controllerها را map کنیم. Controller مسئول ترجمهٔ درخواست به تصمیم HTTP است؛ query و تصمیم کسب‌وکار را به سرویس می‌سپارد تا action به انبار همه‌چیز تبدیل نشود.

Now the service remains the same, but the HTTP boundary lives in a class. We register MVC controllers and map them. A controller translates a request into an HTTP decision; queries and business decisions stay in services so the action does not become a dumping ground.

ثبت و تعریف Controller
builder.Services.AddControllers();
var app = builder.Build();
app.MapControllers();
app.Run();

[ApiController]
[Route("orders")]
public sealed class OrdersController(IOrderReader reader) : ControllerBase
{
    [HttpGet]
    public ActionResult<IReadOnlyList<OrderSummary>> GetRecent()
        => Ok(reader.GetRecent());
}

[ApiController] و MVC رفتارهای قراردادی اضافه می‌کنند که بعداً در model binding و validation می‌بینیم. class بودن به‌تنهایی کد را تمیز نمی‌کند؛ اگر controller database query، قواعد کسب‌وکار و تبدیل response را خودش انجام دهد، فقط پیچیدگی را به فایل دیگری منتقل کرده‌ایم.

[ApiController] and MVC add conventions explored later in model binding and validation. A class does not automatically make code clean; if the controller performs database queries, business rules, and response transformation, we have only moved complexity to another file.

مقایسه را در نقطهٔ درست انجام بدهCompare at the right boundary

هر دو روش routing، DI، middleware، authorization و testing را پشتیبانی می‌کنند؛ گزینه‌های دقیق و تجربهٔ کدنویسی‌شان یکسان نیست. Controllerها conventionهای MVC و سازمان‌دهی actionها را می‌دهند. Minimal APIs declaration نزدیک route را ساده می‌کنند و با گروه‌ها، filterها و سرویس‌ها برای برنامه‌های بزرگ هم ساختار می‌سازند.

Both approaches work with routing, DI, middleware, authorization, and testing, though exact APIs and authoring experience differ. Controllers provide MVC conventions and action organisation. Minimal APIs simplify declarations near routes and can still be structured with groups, filters, and services in larger apps.

معیار انتخاب قابل دفاعA defensible selection criterion

آیا تیم قراردادهای Controller و فیلترهای MVC موجود دارد؟ آیا routeها محدود و قابل گروه‌بندی‌اند؟ آیا پروژه از viewها و مدل MVC استفاده می‌کند یا API کوچک و متمرکز است؟ جواب این‌ها بهتر از «این syntax مد روزتر است» تصمیم را هدایت می‌کند.

Does the team already use controller conventions and MVC filters? Are routes focused and groupable? Does the app use views and MVC models, or is it a focused API? These answers are better decision guides than “this syntax is trendier.”

وقتی دو مدل را نصفه با هم ترکیب می‌کنیمWhen the two models are mixed carelessly

یک برنامه می‌تواند Minimal API و Controller را کنار هم داشته باشد؛ اما اضافه‌کردن هر دو فقط برای «احتیاط» هزینه دارد: ثبت سرویس و route باید روشن بماند و تیم باید بداند هر endpoint کجا تعریف شده. خطاهایی مثل فراموشی AddControllers یا MapControllers معمولاً مسیر controller را از نقشه حذف می‌کنند، نه اینکه برنامه حتماً compile error بدهد.

An app can contain both Minimal APIs and controllers, but adding both “just in case” has a cost: service registration and route mapping must remain clear, and the team needs to know where each endpoint lives. Missing AddControllers or MapControllers can leave controller routes out of the app without necessarily causing a compile error.

اگر Controller route پاسخ نمی‌دهد
builder.Services.AddControllers();
var app = builder.Build();
app.MapControllers();
app.Run();

route را با HTTP method و مسیر واقعی آزمایش کن و log routing را در صورت نیاز بالا ببر. اگر فقط Minimal APIها کار می‌کنند، بررسی کن app.MapControllers واقعاً اجرا شده و controller در assembly برنامه discover می‌شود. هنوز سراغ پایگاه‌داده نرو؛ ممکن است handler هرگز انتخاب نشده باشد.

Test the actual path and HTTP method, and increase routing logs if needed. If only Minimal APIs work, verify app.MapControllers ran and the controller is discoverable in the app assembly. Do not jump to the database; the action may never have been selected.

آزمایشگاه: یک قرارداد، دو پیاده‌سازیLab: one contract, two implementations

در یک پروژهٔ موقت endpoint سفارش را هر دو شکل بساز. هر دو باید از IOrderReader یکسان استفاده کنند تا بفهمیم تفاوت در HTTP boundary است، نه در منطق business یا منبع داده.

In a disposable project, implement the order endpoint both ways. Both must use the same IOrderReader so the difference remains at the HTTP boundary, not in business logic or data source.

  1. یک IOrderReader ساده با دادهٔ ثابت ثبت کن و Minimal API GET /orders را بساز.Register a simple IOrderReader with fixed data and create Minimal API GET /orders.
  2. Controller را اضافه کن و service registration و route mapping لازم را انجام بده.Add a controller and configure required service registration and route mapping.
  3. هر دو مسیر را با client HTTP صدا بزن؛ status، JSON و log انتخاب‌شدن handler را مقایسه کن.Call both routes with an HTTP client; compare status, JSON, and handler-selection logs.
  4. یکی از MapControllers یا AddControllers را موقت بردار و نتیجه را ثبت کن؛ سپس برگردان.Temporarily remove MapControllers or AddControllers, record the outcome, then restore it.
  5. نام پروژه را بزرگ کن: ثبت هر route را در دو شکل تقسیم‌بندی کن و از هم‌تیمی بخواه مسیر endpoint را پیدا کند.Scale the sample: organise route registration in both styles and ask a teammate to locate an endpoint.
  6. با معیارهای واقعی تیم، یکی را برای یک بخش تازه انتخاب کن و تصمیم را در چند جمله مستند کن.Choose one approach for a new feature using real team criteria and document the choice briefly.

گزارش شامل کدهای مسیر، تنظیمات لازم، نتیجهٔ درخواست و معیار انتخاب است. «کوتاه‌تر بود» معیار نهایی نیست؛ خوانایی تیم، قراردادهای موجود و هزینهٔ نگهداری را هم بنویس.

Report route code, required setup, request results, and selection criteria. “It was shorter” is not enough; include team readability, existing conventions, and maintenance cost.

ابزار، شکل‌ساز endpoint است؛ تصمیم معماری نیستThe tool shapes the endpoint; it is not the architecture

Minimal API و Controller دو راه معتبر برای ساخت HTTP endpoint هستند. اگر نیاز ساده و مستقیم است، Minimal API می‌تواند سطح ceremony را کم کند. اگر قراردادهای MVC و سازمان‌دهی action به تیم کمک می‌کند، Controller انتخاب معقولی است. هیچ‌کدام مجوز قاطی‌کردن transport، منطق کسب‌وکار و data access در یک فایل نیست.

Minimal APIs and controllers are both valid ways to create HTTP endpoints. For focused needs, Minimal APIs can reduce ceremony. If MVC conventions and action organisation help the team, controllers are reasonable. Neither justifies mixing transport, business logic, and data access in one file.

برای feature فروشگاه، هر دو را با یک سرویس مشترک ساختیم؛ پس تفاوت واقعی را در route declaration و convention دیدیم. قبل از انتخاب، یک درخواست واقعی را اجرا کن، wiring لازم را ثبت کن و از هم‌تیمی بخواه endpoint را پیدا کند. معماری خوب فقط در README قابل‌فهم نیست؛ در لحظهٔ عیب‌یابی هم باید مرزش را پیدا کرد.

For the shop feature, we used the same service in both styles and compared actual route declaration and conventions. Before choosing, run a real request, record wiring, and ask a teammate to locate the endpoint. Good architecture must be understandable not just in a README but also during an incident.
