Filter؛ منطق مشترک را کجا بگذاریم؟

Filters: where should shared logic live?

تیم برای هر action یک قطعه کد مشابه می‌نویسد: زمان‌گیری، ثبت اطلاعات یا بررسی ورودی. بعد middlewareای می‌سازد که به جزئیات action نیاز دارد. حالا باید ابزار را در لایه‌ای بگذاریم که واقعاً context لازم را دارد، نه اینکه هر منطق مشترکی را filter بنامیم.

The team repeats timing, logging, or input checks in every action, then builds middleware that needs action-specific context. Put the behaviour at the layer that has the required context; not every shared concern is a filter.

منطق مشترک هست؛ اما در کدام لایه؟The concern is shared, but which layer owns it?

Middleware کل HTTP pipeline را می‌بیند و برای همهٔ درخواست‌ها مناسب است. Filterهای MVC در چرخهٔ اجرای controller/action قرار می‌گیرند و به context همان مرحله دسترسی دارند. Endpoint Filter به delegate و آرگومان‌های Minimal API نزدیک است. انتخاب درست یعنی کوچک‌ترین لایه‌ای که اطلاعات لازم را دارد و اجرای مورد انتظار را پوشش می‌دهد.

Middleware sees the HTTP pipeline and can apply to all requests. MVC filters run in the controller/action lifecycle and see that stage's context. Endpoint filters sit close to Minimal API delegates and arguments. Choose the smallest layer that has the needed information and covers the intended execution.

Middleware برای مرز درخواست است؛ filter برای lifecycle endpoint/action. هر دو را بی‌دلیل روی یک رفتار سوار نکن.

Middleware concerns the request boundary; filters concern endpoint/action execution. Do not stack both on the same behaviour without a reason.

Filterهای MVC دور action می‌چرخندMVC filters wrap action execution

MVC چند نوع filter دارد: authorization زودتر از بخش‌های دیگر تصمیم می‌گیرد؛ resource filter بخش بزرگی از اجرای MVC را دربرمی‌گیرد؛ action filter پیش و پس از action اجرا می‌شود؛ exception filter به خطاهای بخشی از اجرای MVC می‌رسد؛ result filter دور اجرای result است. ترتیب و scope مهم‌اند: global، controller و action می‌توانند filterهای متفاوتی داشته باشند.

MVC has several filter types: authorization runs early; resource filters wrap much of MVC execution; action filters run before and after an action; exception filters handle certain exceptions within MVC; result filters wrap result execution. Order and scope matter: global, controller, and action scopes can compose different filters.

نمونهٔ action filter
public sealed class TimingFilter : IAsyncActionFilter
{
    private readonly ILogger<TimingFilter> _logger;

    public TimingFilter(ILogger<TimingFilter> logger) => _logger = logger;

    public async Task OnActionExecutionAsync(
        ActionExecutingContext context,
        ActionExecutionDelegate next)
    {
        var started = Stopwatch.GetTimestamp();
        await next();
        _logger.LogInformation("Action {Action} took {Elapsed}ms",
            context.ActionDescriptor.DisplayName,
            Stopwatch.GetElapsedTime(started).TotalMilliseconds);
    }
}

برای inject کردن dependency، filter را با DI ثبت و روش مناسب scope را انتخاب کن. اگر filter می‌خواهد response را بر اساس policy تغییر دهد، authorization filter نیست مگر واقعاً تصمیم مجوز بگیرد؛ هر نوع را برای lifecycle و قرارداد خودش استفاده کن.

Register filters through DI when they need dependencies, choosing an appropriate scope. A filter that changes a response is not an authorization filter unless it actually makes an access decision; use each type for its lifecycle and contract.

Endpoint Filter برای ورودی/خروجی Minimal APIEndpoint filters for Minimal API inputs and outputs

Endpoint Filter می‌تواند قبل و بعد از اجرای handler Minimal API کار کند و آرگومان‌های bindingشده را ببیند. برای validation اختصاصی endpoint یا ثبت metadataمحور مناسب است. این filter کل درخواست‌های static file یا middlewareهای قبل از endpoint را نمی‌بیند؛ اگر نگرانی برای همهٔ HTTP درخواست‌هاست، مرز middleware را بررسی کن.

An endpoint filter can run before and after a Minimal API handler and inspect bound arguments. It fits endpoint-specific validation or metadata-driven behaviour. It does not see static-file requests or middleware that terminates before the endpoint; use middleware for truly request-wide concerns.

اعتبارسنجی ورودی handler
app.MapPost("/orders", (CreateOrder request) => Results.Created("/orders/1", request))
   .AddEndpointFilter(async (context, next) =>
   {
       var input = context.GetArgument<CreateOrder>(0);
       if (input.Lines.Count == 0)
           return Results.ValidationProblem(new Dictionary<string, string[]>
           {
               ["lines"] = ["At least one line is required."]
           });

       return await next(context);
   });

در برنامهٔ واقعی، validation را در abstraction قابل‌آزمایش نگه دار و خطای ورودی را با قرارداد API هماهنگ برگردان. Filter نباید business rule را پنهانی جایگزین منطق domain کند؛ خطا را برای caller قابل‌فهم و برای تست قابل‌اثبات نگه دار.

In a real app, keep validation in a testable abstraction and return errors consistent with the API contract. A filter should not silently replace domain rules; make failures understandable to callers and verifiable in tests.

Exception Filter برای exceptionهای MVC است و تمام خطاهای pipeline را جایگزین middleware سراسری نمی‌کند. خطایی که در middleware زودتر یا خارج از محدودهٔ MVC رخ دهد ممکن است به آن نرسد؛ برای مرز عمومی، exception-handling middleware را در جای درست نگه دار.

An exception filter handles MVC exceptions; it does not replace global pipeline error handling. Errors in earlier middleware or outside MVC may never reach it; keep exception-handling middleware at the appropriate outer boundary.

وقتی filter اجرا نمی‌شود، scope و pipeline را بررسی کنWhen a filter does not run, inspect scope and pipeline

اول روشن کن endpoint از Minimal API است یا MVC Controller. بعد ثبت filter، scope، ordering و اینکه request اصلاً به مرحلهٔ endpoint رسیده را بررسی کن. اگر response پیش از routing کوتاه شده، action filter مقصر نیست. یک log کوتاه با نام filter و endpoint بگذار و با درخواست قابل‌تکرار تست کن؛ body یا token را log نکن.

First identify whether the endpoint is a Minimal API or MVC controller. Then inspect registration, scope, ordering, and whether the request reached endpoint execution. If a response short-circuited before routing, the action filter is not the cause. Add a concise filter/endpoint log and test a reproducible request; do not log bodies or tokens.

منطق مشترک را در لایهٔ صاحب context بگذارPut shared behaviour where its context lives

Middleware درخواست را در سطح HTTP می‌بیند؛ MVC filter چرخهٔ action و Endpoint Filter آرگومان و handler Minimal API را. business rule را هم در filter مخفی نکن. اگر filter اجرا نشد، قبل از تغییر کد ببین request به مرحلهٔ آن رسیده، scope درست است و filter ثبت شده؛ بعد رفتار را با یک درخواست تکرارپذیر ثابت کن.

Middleware sees the HTTP request boundary; MVC filters see action lifecycle, and Endpoint Filters see Minimal API arguments and handlers. Do not hide business rules in filters. When a filter does not run, verify the request reached that stage, scope is correct, and registration exists before changing code; then prove behaviour with a reproducible request.
