FluentValidation؛ قانون‌های پیچیده را بیرون DTO نگه دار

FluentValidation: keep complex rules outside the DTO

DTO با چند attribute ساده شروع شد؛ حالا قانون‌ها شرطی شده‌اند، به هم وابسته‌اند و باید مستقل test شوند. اگر همه‌چیز را در controller بنویسی، هر endpoint یک نسخه از قانون خودش می‌سازد. بیایید validator جدا بسازیم، ثبتش کنیم و آگاهانه اجرا کنیم.

The DTO began with a few simple attributes; now rules are conditional, related, and need independent tests. If everything lives in controllers, each endpoint grows its own copy. Build a separate validator, register it, and invoke it deliberately.

قانون‌ها در controller تکثیر شده‌اندRules have been duplicated across controllers

فرض کن ساخت سفارش از دو endpoint ممکن است؛ یکی برای سایت و یکی برای اپراتور. شرط customer، سقف quantity و وضعیت تخفیف کم‌کم در هر دو action تکرار می‌شوند. بعد یک مسیر قانون تازه می‌گیرد و دیگری نه. ما می‌خواهیم قانون‌های مربوط به خود ورودی یک‌جا باشند، اما بررسی موجودی و مجوز همچنان در use case بمانند.

An order can be created through two endpoints, one for customers and one for operators. Customer, quantity, and discount rules start repeating in both actions. One path gets a new rule while the other does not. Put input rules in one place, but keep inventory and authorization in the use case.

مرزبندی: validator پاسخ می‌دهد «این command از نظر ورودی شکل قابل‌قبول دارد؟»؛ application/domain پاسخ می‌دهد «با وضعیت فعلی سیستم اجازهٔ این کار را داریم؟»

Boundary: a validator answers whether the command's input is acceptable; application/domain logic decides whether the operation is allowed in current system state.

قانون را در کلاس مستقل بخوانRead the rules in a dedicated validator

هر validator از AbstractValidator<T> ارث می‌برد و زنجیرهٔ RuleFor روی property موردنظر می‌نویسد. نام property در خروجی خطا هم نقش دارد؛ پس آن را با request contract و client هماهنگ نگه دار.

A validator derives from AbstractValidator<T> and builds RuleFor chains for properties. Property names also appear in error output, so align them with the request contract and client.

قانون‌های مستقل از HTTP · Rules independent of HTTP
public sealed class CreateOrderValidator
    : AbstractValidator<CreateOrderRequest>
{
    public CreateOrderValidator()
    {
        RuleFor(x => x.CustomerName)
            .NotEmpty()
            .MinimumLength(2)
            .MaximumLength(80);

        RuleFor(x => x.Quantity)
            .InclusiveBetween(1, 50);

        RuleFor(x => x.ContactEmail)
            .EmailAddress()
            .When(x => !string.IsNullOrWhiteSpace(x.ContactEmail));
    }
}

زنجیرهٔ ruleها خواناتر از چند if است، ولی جادویی نیست: EmailAddress قالب ساده را بررسی می‌کند، نه این‌که mailbox واقعاً وجود دارد. validator را با valid و invalid input اجرا کن و خطاهای property را بخوان.

A rule chain is easier to read than scattered conditionals, but it is not magic: EmailAddress checks a simple format, not whether a mailbox exists. Run the validator with valid and invalid input and inspect property errors.

اجرای validator در unit test
var validator = new CreateOrderValidator();
var result = validator.TestValidate(new CreateOrderRequest
{
    CustomerName = "A",
    Quantity = 0,
    ContactEmail = "not-an-email"
});

result.ShouldHaveValidationErrorFor(x => x.Quantity);
result.ShouldHaveValidationErrorFor(x => x.ContactEmail);

این تست قانون‌های validator را ثابت می‌کند؛ route، DI registration و پاسخ HTTP را نه. برای آن‌ها integration test لازم است.

This test proves the validator rules, not routing, DI registration, or HTTP response behavior. Those need integration tests.

validator را مثل سرویس واقعی ثبت کنRegister validators as real services

در برنامه validator را دستی ثبت کن یا برای assembly مشخص scan انجام بده. scan راحت است، اما typeهای پیدا‌شده را پنهانی ثبت می‌کند؛ lifetime را آگاهانه انتخاب کن. validator معمولاً نباید state قابل‌تغییر بین درخواست‌ها نگه دارد.

Register validators explicitly or scan a known assembly. Scanning is convenient, but hides which types are registered; choose lifetime deliberately. A validator normally should not hold mutable state across requests.

ثبت با extension رسمی DI
builder.Services.AddValidatorsFromAssemblyContaining<CreateOrderValidator>();

این API از package FluentValidation.DependencyInjectionExtensions است. registration به‌صورت پیش‌فرض scoped است. اگر validator وابستگی scoped دارد، آن را singleton نکن؛ و در startup/integration test بررسی کن container واقعاً IValidator<CreateOrderRequest> را resolve می‌کند.

This API comes from FluentValidation.DependencyInjectionExtensions. Registration defaults to scoped. Do not make a validator with scoped dependencies a singleton; verify in startup/integration tests that the container resolves IValidator<CreateOrderRequest>.

در endpoint، async را صریح اجرا کنInvoke asynchronous validation explicitly in the endpoint

برای API جدید، الگوی manual validation شفاف است: endpoint validator را می‌گیرد، ValidateAsync را با CancellationToken صدا می‌زند و اگر خطا بود response ساختاریافته می‌دهد. این کار کمی کد روشن اضافه می‌کند، اما زمان اجرا، logging و async rule را پنهان نمی‌کند.

For a new API, manual validation is explicit: inject the validator, call ValidateAsync with the request cancellation token, and return a structured response when invalid. It adds visible code but does not hide execution, logging, or async rules.

Minimal API · اجرای صریح
app.MapPost("/orders", async (
    CreateOrderRequest request,
    IValidator<CreateOrderRequest> validator,
    CancellationToken cancellationToken) =>
{
    var result = await validator.ValidateAsync(
        request, cancellationToken);

    if (!result.IsValid)
        return Results.ValidationProblem(result.ToDictionary());

    return Results.Accepted();
});

در controller هم همین validator را inject کن و await کن؛ نتیجه را به contract خطای برنامه نگاشت کن. اگر validator قانون async دارد، Validate صدا نزن: FluentValidation 11 به بعد اجرای sync آن را exception می‌کند. مسیرهای async را همیشه با ValidateAsync اجرا کن.

In a controller, inject and await the same validator, then map the result to the API error contract. If any rule is asynchronous, never call Validate: FluentValidation 11+ throws when such a validator is invoked synchronously. Always use ValidateAsync for async-capable validators.

Auto-validation قدیمی: اتصال به pipeline همگام MVC دیگر برای پروژهٔ تازه توصیه نمی‌شود؛ async rule در آن قابل اجرا نیست و برای Minimal API هم کاربرد ندارد. اگر سیستم legacy از آن استفاده می‌کند، migration را آگاهانه انجام بده، نه این‌که package قدیمی را برای راحتی کپی کنی.

Legacy auto-validation: synchronous MVC-pipeline integration is no longer recommended for new projects; it cannot run async rules and does not apply to Minimal APIs. Migrate legacy usage deliberately rather than copying an older package setup.

شرط، مجموعه و خطای قابل‌فهمConditions, collections, and useful errors

قانون شرطی را با When محدود کن؛ برای itemهای مجموعه از RuleForEach و child validator استفاده کن. پیام خطا باید به field و action قابل‌اصلاح اشاره کند، اما اطلاعات حساس یا جزئیات داخلی ندهد.

Use When for conditional rules and RuleForEach with a child validator for collections. An error should point to the field and corrective action without exposing sensitive or internal details.

قانون شرطی و itemهای سفارش
RuleFor(x => x.DiscountCode)
    .NotEmpty()
    .When(x => x.HasDiscount)
    .WithMessage("A discount code is required.");

RuleForEach(x => x.Lines)
    .SetValidator(new CreateOrderLineValidator());

اگر تخفیف به موجودبودن campaign یا تعداد استفاده وابسته است، این شرط صرفاً syntax نیست و به state سیستم نیاز دارد؛ آن را به application service ببر. تکرار همان پیام محلی در چند endpoint نشانهٔ اشتباه‌بودن boundary است.

If a discount depends on campaign availability or redemption count, the rule needs system state; move it to an application service. Repeating that stateful rule across endpoints signals a misplaced boundary.

Async rule را برای دسترسی بیرونی با احتیاط بسازUse asynchronous rules for external checks carefully

FluentValidation از MustAsync پشتیبانی می‌کند، اما هر درخواست بیرونی هزینه، timeout و failure دارد. بررسی «این شناسه احتمالاً آزاد است» فقط راهنمایی است؛ قید unique پایگاه‌داده همچنان مرجع نهایی می‌ماند. CancellationToken را پاس بده و خطای در دسترس نبودن DB را با invalid input یکی نکن.

FluentValidation supports MustAsync, but every external call adds latency, timeout, and failure modes. Checking that an identifier appears available is advisory; the database unique constraint remains authoritative. Propagate cancellation and do not confuse database unavailability with invalid input.

قانون async · Async rule
RuleFor(x => x.UserName)
    .MustAsync(async (name, cancellationToken) =>
        !await users.ExistsAsync(name, cancellationToken))
    .WithMessage("This user name is unavailable.");

این فقط تجربهٔ پیام را بهتر می‌کند؛ دو درخواست هم‌زمان می‌توانند هر دو از check عبور کنند. هنگام ذخیره constraint را handle کن و خطای duplicate را به پاسخ کنترل‌شده تبدیل کن. در تست async، repository را fake کن یا از دیتابیس آزمایشی استفاده کن.

This improves messaging only; concurrent requests can both pass the check. Handle the constraint at persistence time and map duplicates to a controlled response. Fake the repository or use a test database for async tests.

آزمایشگاه: validator مستقل، endpoint روشنLab: an independent validator and an explicit endpoint

ساخت سفارش فصل قبل را ادامه بده. ruleهای محلی را به FluentValidation منتقل کن، validator را از DI بگیر و دستی await کن. بعد یک check بیرونی را عمدی fail کن و ثابت کن به‌عنوان خطای سیستم دیده می‌شود، نه پیام invalid معمولی.

Continue the previous order endpoint. Move local rules into FluentValidation, resolve it from DI, and await it manually. Then deliberately fail an external check and prove it is treated as a system error, not ordinary invalid input.

  1. packageهای لازم و registration را اضافه کن؛ resolve شدن validator را در startup یا integration test ثابت کن.
  2. Add required packages and registration; prove validator resolution in startup or an integration test.
  3. برای نام، تعداد، شرط تخفیف و آیتم‌های سفارش rule بساز و unit test مرزها را بنویس.
  4. Add rules for name, quantity, discount condition, and order lines; write boundary unit tests.
  5. در endpoint از ValidateAsync با token درخواست استفاده و خطاها را به ValidationProblem نگاشت کن.
  6. Call ValidateAsync with the request token and map failures to ValidationProblem.
  7. در تست، rule async را اجرا کن؛ یک بار cancellation و یک بار repository unavailable را بررسی کن.
  8. Exercise the async rule; test cancellation and repository unavailability separately.
  9. ثبت duplicate هم‌زمان را با قید unique آزمایش کن؛ pre-check را تضمین جا نزن.
  10. Test concurrent duplicate creation against a unique constraint; do not present the pre-check as a guarantee.

Use the DependencyInjectionExtensions package. Keep scoped lifetime unless justified; exercise the endpoint in an integration test.

۵. تبدیل خطا به HTTP

نتیجهٔ نامعتبر را با Results.ValidationProblem برگردان و JSON structure و status را assert کن.

Return invalid results with Results.ValidationProblem and assert status and JSON structure.

راهنما

ToDictionary نتیجه را به ساختار خطا تبدیل می‌کند. response را با endpoint واقعی بسنج؛ unit test validator به‌تنهایی mapping HTTP را ثابت نمی‌کند.

ToDictionary converts errors to a response shape. Test through the real endpoint; a validator unit test does not prove HTTP mapping.

۶. controller و async

validator injectشده را در action با ValidateAsync اجرا کن؛ token لغو را هم پاس بده و cancellation را تست کن.

Invoke the injected validator with ValidateAsync in an action; pass the cancellation token and test cancellation.

راهنما

از Validate sync استفاده نکن. cancellation باید propagation شود و به پیام ورودی نامعتبر تبدیل نشود.

Do not call synchronous Validate. Propagate cancellation rather than converting it to an invalid-input message.

۷. rule async و اجرای sync

MustAsync اضافه کن و عمداً در test Validate را صدا بزن؛ exception مشاهده‌شده را ثبت و سپس ValidateAsync را جایگزین کن.

Add MustAsync, deliberately call Validate in a test, record the exception, then replace it with ValidateAsync.

راهنما

نسخه‌های جدید FluentValidation اجرای validator دارای async rule به شکل sync را رد می‌کنند. رفتار واقعی نسخهٔ package را در test ببین.

Newer FluentValidation versions reject synchronous execution when async rules exist. Observe the package version's behavior in a test.

۸. شناسهٔ تکراری

MustAsync برای check اولیه بساز، اما هم‌زمانی را با unique constraint تست کن و conflict را کنترل‌شده برگردان.

Use MustAsync for a pre-check, but test concurrency with a unique constraint and return a controlled conflict.

راهنما

validator ضمانت هم‌زمانی نمی‌دهد. دو درخواست رقیب و state نهایی DB را در دیتابیس disposable بررسی کن.

The validator cannot guarantee concurrency. Test competing requests and final DB state in a disposable database.

۹. ruleSet برای مسیر متفاوت

قانون‌های Create و Update را جدا کن و مشخص کن کدام ruleSet هنگام هر عملیات اجرا می‌شود.

Separate Create and Update rules and specify which ruleset runs for each operation.

راهنما

قانون مشترک را دوباره ننویس؛ IncludeProperties یا RuleSet را مطابق قرارداد انتخاب و نتیجهٔ هر مسیر را تست کن.

Avoid duplicating shared rules; choose IncludeProperties or RuleSet for the contract and test both paths.

۱۰. قانون خارج از validator

بررسی active بودن محصول را از validator به use case منتقل کن؛ برای inactive پاسخ و عدم تغییر state را assert کن.

Move product-active checking from validator to the use case; assert response and unchanged state for inactive products.

راهنما

قانون به state فعلی وابسته است و application آن را می‌داند. validator محلی ورودی را بررسی کند؛ use case نتیجهٔ عملیات را.

This rule depends on current state known to the application. Keep local input rules in the validator and operation decisions in the use case.

۱۱. scope اشتباه

validator را singleton کن درحالی‌که repository scoped می‌گیرد؛ startup/test باید خطای lifetime را آشکار کند، سپس registration را اصلاح کن.

Make a validator singleton while it depends on a scoped repository; expose the lifetime error and fix registration.

راهنما

singleton نباید scoped dependency را capture کند. scoped یا transient مناسب انتخاب کن و resolve در scope request را تست کن.

A singleton must not capture a scoped dependency. Use scoped or transient appropriately and test resolution in a request scope.

۱۲. error message contract

پیام خطا را در test به key و متن مورد انتظار محدود کن؛ exception داخلی را در response یا log وارد نکن.

Assert an error key and intended message; keep internal exceptions out of response and logs.

راهنما

WithMessage متن کاربرپسند می‌دهد؛ خطاها باید ساختاریافته بمانند. اطلاعات حساس را وارد placeholder نکن.

WithMessage supplies user-facing text; retain structured errors and never put sensitive values in placeholders.

۱۳. async dependency خراب است

repository را طوری fake کن که timeout دهد؛ response را از validation failure متمایز و log را بدون query حساس نگه دار.

Fake a repository timeout; distinguish the response from a validation failure and keep sensitive queries out of logs.

راهنما

خطای I/O نشان نمی‌دهد ورودی نادرست است. exception را در مرز مناسب handle کن و trace id برای پیگیری بده.

An I/O failure does not mean input is invalid. Handle it at the right boundary and include a trace ID.

۱۴. test مستقل یا HTTP؟

برای یک rule و یک mapping پاسخ، مشخص کن کدام unit و کدام integration test لازم است؛ هر دو را اجرا کن.

For one rule and one response mapping, decide which need unit versus integration tests; run both.

راهنما

rule با TestValidate سریع است؛ HTTP mapping فقط از endpoint/host واقعی معلوم می‌شود. هر تست یک فرضیهٔ متفاوت را ثابت می‌کند.

TestValidate is fast for rules; HTTP mapping is proven through the real host/endpoint. Each test proves a different hypothesis.

۱۷. nested rule گم شده

child validator را عمداً از RuleForEach حذف کن، test شکست‌خورده را ببین، سپس SetValidator را اضافه و همان تست را تکرار کن.

Does DI registration alone mean the parent runs the child? No; wire the child explicitly or use the supported registration pattern and prove it in a test.

۱۸. بازبینی معماری قانون‌ها

سه rule از API موجودت انتخاب کن؛ برای هرکدام unit test، integration test یا use-case test مناسب بنویس و دلیل boundary را در PR description مستند کن.

Choose three rules from an API; write the right unit, integration, or use-case tests and document each boundary in a PR description.

راهنما

ساختار/محدوده → validator؛ state و مجوز → use case/policy؛ یکتایی قطعی → قید DB. شواهد هر تست را به ادعای خودش محدود نگه دار.

Shape/range belongs in validators; state and authorization in use cases/policies; authoritative uniqueness in DB constraints. Keep each test's claim within its evidence.

جمع‌بندی: validator قانون را می‌سنجد، سیستم حقیقت راWrap-up: validators check rules; the system owns the truth

FluentValidation وقتی قانون‌ها از attribute ساده پیچیده‌ترند، خوانایی و test مستقل می‌دهد. DI registration را verify کن، async rule را همیشه با ValidateAsync اجرا کن و در API جدید برای auto-validation همگام legacy طراحی نکن. قانون‌های stateful و امنیتی جای دیگری‌اند و قید DB حرف آخر را می‌زند. وقتی ورودی معتبر شد، فصل بعد می‌پرسد چطور آن را به DTO خروجی و مدل‌های دیگر نگاشت کنیم.

FluentValidation improves readability and isolated testing when rules outgrow simple attributes. Verify DI registration, always call ValidateAsync for async-capable validators, and avoid designing new APIs around legacy synchronous auto-validation. Stateful and security rules belong elsewhere, and database constraints remain authoritative. Once input is valid, the next chapter asks how to map it to output DTOs and other models.
