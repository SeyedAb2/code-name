Middleware؛ ترتیب، مسیر درخواست را عوض می‌کند

Middleware: order changes the request path

کاربر می‌گوید خطای سرور دیده، اما لاگ سفارشی تیم اصلاً اجرا نشده. route در فصل قبل درست بود؛ پس درخواست در کدام لایه متوقف شده؟ این‌بار با middleware مثل چند تابع «قبل و بعد» برخورد می‌کنیم و مسیر واقعی را قدم‌به‌قدم می‌خوانیم.

A user saw a server error, but the team's custom log never ran. Routing was correct in the previous chapter, so where did the request stop? We will treat middleware as nested “before and after” functions and trace the actual path.

درخواست وارد برنامه می‌شود؛ اما کجا بیرون می‌رود؟A request enters the app, but where does it leave?

Middlewareها به ترتیبی که ثبت شده‌اند درخواست را می‌بینند؛ اگر یکی پاسخ بدهد و next را صدا نزند، زنجیره همان‌جا کوتاه می‌شود. اگر به next برسد، پاسخ از همان مسیر برمی‌گردد و بخش بعد از next به‌ترتیب معکوس اجرا می‌شود. همین نکته علت خیلی از خطاهای «چرا لاگ/هدر/خطا را ندیدم؟» است.

Middleware sees a request in registration order. If one writes a response without calling next, the chain short-circuits. If it calls next, the response unwinds in reverse order, running code after next on the way back. This explains many “why did my log/header/error handler not run?” incidents.

رفت: به ترتیب ثبت. برگشت: از endpoint به middlewareهای قبلی. Middlewareای که زودتر پاسخ را کوتاه کند، endpoint را نمی‌بیند.

Inbound: registration order. Outbound: endpoint back through earlier middleware. A middleware that short-circuits prevents later components from seeing the request.

Use ادامه می‌دهد، Run تمام می‌کند، Map شاخه می‌سازدUse continues, Run terminates, Map branches

Use به delegate بعدی دسترسی می‌دهد؛ می‌توانی پیش یا پس از آن کاری انجام بدهی. Run terminal است و next ندارد. Map برای مسیر matching شاخه می‌سازد؛ مراقب باش مسیر branch در ادامه چطور دیده می‌شود و شاخه ناخواسته fallback همه‌چیز نشود.

Use exposes the next delegate, so code can run before and after it. Run is terminal and has no next. Map creates a branch for matching paths; understand the branch path and avoid making an unintended catch-all.

ثبت زمان در دو سوی next
app.Use(async (context, next) =>
{
    var started = Stopwatch.GetTimestamp();
    await next();
    var elapsed = Stopwatch.GetElapsedTime(started);
    app.Logger.LogInformation("{Method} {Path} {Status} {ElapsedMs}ms",
        context.Request.Method, context.Request.Path,
        context.Response.StatusCode, elapsed.TotalMilliseconds);
});

این middleware فقط وقتی به خط ثبت log می‌رسد که next برگردد؛ اگر exception بالا بیاید و handle نشود، کد بعد از next اجرا نمی‌شود. برای ثبت پایان در همهٔ حالت‌ها از ساختار try/finally استفاده کن، ولی مراقب باش حین exception پاسخ را ناخواسته تغییر ندهی.

This middleware reaches the log after next returns; an unhandled exception can skip that code. Use try/finally when you must record completion in every case, while avoiding accidental response mutation during exception handling.

ترتیب را از نیاز بخوان، نه از حفظDerive order from requirements, not memorization

برای برنامهٔ معمول، exception handling باید دور middlewareهایی باشد که باید خطاهایشان را بگیرد. Routing باید قبل از middlewareهایی باشد که endpoint metadata می‌خوانند؛ authentication هویت را می‌سازد و authorization تصمیم دسترسی می‌گیرد. CORS هم ترتیب مشخصی با authentication/authorization و cache دارد. اما WebApplication بعضی middlewareهای routing، authentication و authorization را در شرایطی خودکار اضافه می‌کند؛ پس اول کد و رفتار نسخهٔ پروژه را ببین، بعد ترتیب را تغییر بده.

In a typical app, exception handling should wrap components whose failures it must catch. Routing precedes middleware that reads endpoint metadata; authentication establishes identity, and authorization makes access decisions. CORS also has ordering requirements relative to authentication/authorization and caching. However, WebApplication can add routing, authentication, and authorization middleware automatically in some conditions; inspect the project and version before changing order.

یک pipeline صریح برای بحث
app.UseExceptionHandler("/error");
app.UseHttpsRedirection();
app.UseRouting();
app.UseCors("frontend");
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

این نمونه الگوی عمومی است، نه نسخهٔ کپی برای همهٔ برنامه‌ها. در Minimal Hosting ممکن است بعضی مرحله‌ها خودکار باشند؛ CORS policy، rate limiting مبتنی بر metadata، static files و antiforgery هم به سناریو وابسته‌اند. ترتیب واقعی را با مستندات رسمی و نیاز endpointهای همان پروژه بسنج.

This is a general explicit pattern, not a universal copy-paste recipe. Minimal hosting may insert some stages automatically; CORS, metadata-based rate limiting, static files, and antiforgery are scenario-dependent. Check the official documentation and the requirements of your endpoints.

کوتاه‌شدن زنجیره همیشه باگ نیستShort-circuiting is not always a bug

Static-file middleware معمولاً اگر فایل عمومی را پیدا کند خودش پاسخ می‌دهد و ادامه نمی‌دهد؛ این رفتار مفید است. اما همین یعنی فایلی که آنجا سرو می‌شود، از مسیر authorization endpoint نمی‌گذرد. فایل خصوصی را صرفاً زیر wwwroot قرار نده و فرض نکن authentication بعداً جلوی دسترسی را می‌گیرد.

Static-file middleware typically handles a found public file and stops the chain; that is useful. It also means the file does not pass through endpoint authorization. Do not place private files under wwwroot and assume later authentication will protect them.

توقف ناخواستهAn unintended terminal component

اگر endpointها 404 می‌شوند، ببین middleware سفارشی قبل از routing پاسخ نداده یا next را جا نینداخته باشد. اگر همهٔ مسیرها یک متن ثابت می‌دهند، terminal Run یا branch گسترده را بررسی کن.

If endpoints return 404, check whether custom middleware responded before routing or forgot to call next. If every path returns the same text, inspect a terminal Run or overly broad branch.

pipeline را با دو log ساده قابل‌دیدن کنMake the pipeline visible with two simple logs

برای تشخیص ترتیب، موقتاً قبل و بعد از next نام middleware، path، status و زمان را ثبت کن. در log مقدارهای حساس مثل token یا body کامل را ننویس. بعد یک درخواست موفق، یک 404 و یک exception کنترل‌شده بفرست؛ تفاوت مسیرها نشان می‌دهد کدام middleware اجرا شده و کجا کوتاه شده است.

To diagnose order, temporarily log the middleware name, path, status, and duration before and after next. Do not log sensitive values such as tokens or full bodies. Send one successful request, one 404, and one controlled exception; compare which components ran and where the chain stopped.

ترتیب middleware بخشی از رفتار برنامه استMiddleware order is part of application behaviour

درخواست در pipeline خطی و سپس برگشت‌خورنده حرکت می‌کند؛ یک short-circuit می‌تواند همهٔ لایه‌های بعدی را حذف کند. برای هر «چرا اجرا نشد؟» اول pipeline واقعی را ثبت کن، بعد middlewareهای terminal و ترتیب وابستگی‌ها را بررسی کن. چون WebApplication بخشی از pipeline را خودکار می‌چیند، کد و مستندات همان نسخه را ملاک بگیر.

Requests move through a linear pipeline and unwind on the way back; a short-circuit can bypass every later component. When asking “why did this not run?”, first record the real pipeline, then inspect terminal components and ordering dependencies. Because WebApplication can add parts automatically, use the code and documentation for the relevant version.
