پاسخ HTTP را بخوانیم

Reading an HTTP response

API می‌گوید «۲۰۰ برگشت». اما صفحهٔ سفارش هنوز چیزی نشان نمی‌دهد. قبل از اینکه endpoint را دست‌کاری کنیم، خود پاسخ را باز می‌کنیم: status چه گفته، headerها چه قراردادی ساخته‌اند و body واقعاً چه چیزی دارد؟

The API team says, “It returned 200.” Yet the order page is still blank. Before changing an endpoint, let’s open the response itself: what did the status say, what contract did the headers establish, and what is actually in the body?

«۲۰۰ بود» گزارش عیب‌یابی نیست“It was 200” is not a diagnosis

در فصل قبل درخواست سفارش را ساختیم و دیدیم client چه چیزی می‌فرستد. این بار همان مسیر را از سمت برگشت دنبال می‌کنیم. همکارمان فقط status را دیده؛ نه header را، نه body را. ممکن است پاسخ موفق باشد اما داده‌ای که صفحه لازم دارد در آن نباشد.

Last chapter we built an order request and inspected what the client sends. Now we follow the return path. Our teammate saw only the status—not the headers or body. A response may be successful while still omitting the data the page needs.

حدس بزن اگر سرور این پاسخ را بدهد، client چه چیزی نمایش می‌دهد:

Predict what the client can display if the server returns this:

پاسخ نمونه · نمایش متنی HTTP/1.1
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 2

{}

status می‌گوید درخواست با موفقیت پردازش شده؛ body اما فقط یک شیء خالی است. اگر UI دنبال `orderNumber` و `total` باشد، «۲۰۰» چیزی دربارهٔ وجود آن propertyها ثابت نمی‌کند. موفقیت HTTP و کامل‌بودن پاسخ طبق قرارداد API دو سؤال جدا هستند.

The status says the request succeeded, but the body is only an empty object. If the UI expects `orderNumber` and `total`, “200” proves neither property exists. HTTP success and API-contract completeness are separate questions.

مدل این فصلOur model

پاسخ را یک‌جا بخوان: status نتیجهٔ کلی را طبقه‌بندی می‌کند؛ headerها metadata و قرارداد تفسیر را می‌دهند؛ body داده یا توضیح خطا را حمل می‌کند. هیچ‌کدام جای دیگری را پر نمی‌کند.

Read a response as a whole: the status classifies the outcome; headers provide metadata and interpretation rules; the body carries data or an error explanation. None substitutes for the others.

سه شاهد، سه پرسشThree signals, three questions

در HTTP/1.1 ممکن است پاسخ را به شکل خط status، چند header، یک خط خالی و بعد content ببینی. در HTTP/2 و HTTP/3 روی شبکه همین قالب خطی را نداریم؛ ابزارهایی مثل curl هنوز status و headerها را برای خواندن نمایش می‌دهند. پس خروجی ترمینال را با wire format همهٔ نسخه‌ها اشتباه نگیر.

With HTTP/1.1, a response can be represented as a status line, headers, a blank line, then content. HTTP/2 and HTTP/3 do not use that same line-oriented wire format; tools such as curl still present status and headers in a readable form. Do not mistake terminal presentation for every protocol version’s wire format.

در پاسخ بالا `Content-Type` می‌گوید body را چطور تفسیر کنیم؛ `Content-Length` اندازهٔ content را در آن پیام متنی نمونه گزارش می‌کند. در همهٔ پاسخ‌ها وجود این headerها تضمین نشده و framing در نسخه‌ها و شرایط مختلف می‌تواند فرق کند. برای فهم API، اول خود پاسخ و قرارداد endpoint را با هم بخوان.

In the sample, `Content-Type` tells the client how to interpret the body; `Content-Length` reports the content size in this illustrative message. These headers are not guaranteed on every response, and framing can vary by version and situation. To understand an API, read the response alongside the endpoint contract.

status کُد است، نه داستان کاملA status code is a signal, not the whole story

status code سه‌رقمی است و رقم اول یک خانواده را نشان می‌دهد. این خانواده کمک می‌کند client واکنش اولیه را انتخاب کند؛ اما معنی دقیق پاسخ را باید با method درخواست، headerها و body کنار هم فهمید. عبارت `OK` بعد از کد، reason phrase است و client نباید برای منطق برنامه به متن آن تکیه کند.

A status code is a three-digit value whose first digit identifies a class. That class helps a client choose an initial reaction, but the precise meaning depends on the request method, headers and body together. The text after the code, such as `OK`, is a reason phrase; application logic should not depend on it.

این خانواده‌بندی مجوز حدس‌زدن علت نیست. مثلاً ۵۰۳ می‌گوید سرویس در حال حاضر آمادهٔ انجام درخواست نیست؛ به‌تنهایی نمی‌گوید علت deployment است یا وابستگی یا محدودیت ظرفیت. برای آن به log و telemetry نیاز داریم که در فصل‌های بعد سراغشان می‌رویم.

The class is not permission to guess a cause. A 503 says the service cannot currently fulfill the request; it does not tell us whether deployment, a dependency or capacity caused it. We will use logs and telemetry in later chapters to investigate causes.

مراقب ۲۰۰ فریبنده باشBeware a misleading 200

یک endpoint ممکن است خطای business را داخل body برگرداند ولی status را ۲۰۰ بگذارد. clientای که فقط status را می‌سنجد موفقیت کاذب می‌بیند. قرارداد را روشن کن: از status متناسب استفاده کن و شکل پاسخ خطا را پایدار نگه دار؛ جزئیات استاندارد خطا در فصل ProblemDetails می‌آید.

An endpoint can put a business failure in the body while returning 200. A client that checks only the status sees false success. Make the contract explicit: use an appropriate status and a stable error shape; the ProblemDetails chapter will cover standardized error responses.

با curl پاسخ را لایه‌لایه باز کنUse curl to inspect the response in layers

برای اینکه به اینترنت یا سرویس بیرونی وابسته نباشیم، یک بخش خیلی کوچک به CodeNames Shop API اضافه می‌کنیم. همین پروژه را از فصل قبل نگه دار و routeهای زیر را به آن وصل کن؛ فعلاً منطق فروشگاه یا دیتابیس نداریم، فقط شکل پاسخ را آشکار می‌کنیم.

To avoid depending on the internet or an external service, add a tiny response surface to the same CodeNames Shop API from last chapter. Keep that project and add these routes; there is no shop logic or database yet—we are making response shapes visible.

Program.cs · ASP.NET Core 10 Minimal API
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/api/products/42", () =>
    Results.Ok(new { id = 42, name = "Keyboard", price = 1250000 }));
app.MapGet("/api/products/missing", () => Results.NotFound());
app.MapGet("/api/maintenance", () =>
    Results.Problem("Inventory is temporarily unavailable.", statusCode: 503));
app.MapGet("/api/save", () => Results.NoContent());

app.Run();

`Results.Ok` یک پاسخ موفق با داده می‌سازد؛ `NotFound` پاسخ ۴۰۴؛ `Problem` پاسخ خطای ۵۰۳ با توضیح؛ و `NoContent` پاسخ موفق بدون content. این‌ها انتخاب‌های برنامه‌اند، نه تشخیص خودکار علت. قبل از اجرا مطمئن شو پروژهٔ ASP.NET Core فصل قبل را باز کرده‌ای و با `dotnet run --urls http://127.0.0.1:5080` فقط روی loopback اجرا می‌کنی.

`Results.Ok` creates a successful response with data; `NotFound` returns 404; `Problem` returns a 503 with an explanation; and `NoContent` returns success without content. These are application choices, not automatic diagnoses. Run the same ASP.NET Core project from Chapter 1 with `dotnet run --urls http://127.0.0.1:5080`, bound only to loopback.

حالا سؤال اول: status و headerها را بدون اینکه بدنه وسط خروجی گم شود چطور ببینیم؟

First question: how can we inspect status and headers without losing track of the body?

ترمینال · پاسخ محصول
curl -i http://127.0.0.1:5080/api/products/42
خروجی نمونه · مقدار headerها ممکن است فرق کند
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Date: ...
Server: Kestrel

{"id":42,"name":"Keyboard","price":1250000}

با `-i` curl headerهای پاسخ را هم کنار body نشان می‌دهد. خط اول کد ۲۰۰ را می‌دهد؛ `Content-Type` می‌گوید داده JSON است؛ و JSON پایین، سه property واقعی را نشان می‌دهد. `Date` و `Server` ممکن است بسته به میزبان یا تنظیمات نباشند؛ برای منطق client روی حضورشان شرط نگذار.

With `-i`, curl prints response headers alongside the body. The first line gives 200; `Content-Type` identifies JSON; and the JSON contains three actual properties. `Date` and `Server` can vary by host or configuration, so do not make client logic depend on them.

اگر می‌خواهی header و body را جدا نگه داری، از `-D` و `-o` استفاده کن. `-w` هم نتیجهٔ انتقال را بعد از درخواست چاپ می‌کند؛ این مقدارها را با body اشتباه نگیر.

If you want separate files for headers and body, use `-D` and `-o`. `-w` prints transfer metadata after the request; do not confuse it with the response body.

ترمینال · جداسازی شواهد
curl -sS -D response-headers.txt -o response-body.json -w 'HTTP %{http_code} · content-type %{content_type}\n' http://127.0.0.1:5080/api/products/42
Get-Content response-headers.txt
Get-Content response-body.json

روی PowerShell، `Get-Content` فایل‌های شواهد را می‌خواند. ممکن است قالب دقیق status line یا headerهای پیش‌فرض با نسخه فرق کند؛ بخش پایدار برای ما کد، نوع محتوا و JSON است. از `-sS` فقط خروجی progress را جمع می‌کنیم و خطای curl را همچنان می‌بینیم.

On PowerShell, `Get-Content` reads the evidence files. The exact status-line formatting or default headers may vary by version; the stable evidence we care about is the code, media type and JSON. `-sS` suppresses the progress meter while preserving curl errors.

هر پاسخ موفقی body نداردNot every successful response has a body

اگر برنامه می‌گوید «ذخیره شد»، لازم نیست همیشه نسخهٔ کامل منبع را دوباره بفرستد. `204 No Content` موفقیت را اعلام می‌کند و content ندارد. در طرف مقابل، `404` یا `503` معمولاً می‌توانند body توضیحی داشته باشند؛ کد به‌تنهایی وجود یا شکل دقیق آن را تضمین نمی‌کند.

When an application says “saved,” it does not always need to send the full resource again. `204 No Content` signals success without response content. By contrast, a `404` or `503` can carry an explanatory body; the code alone does not guarantee its exact presence or shape.

ترمینال · پاسخ بدون content
curl -i http://127.0.0.1:5080/api/save
خروجی نمونه
HTTP/1.1 204 No Content
Date: ...
Server: Kestrel

بعد از headerها bodyای نمی‌آید؛ این نقص ابزار نیست. پاسخ ۲۰۴ طبق معنا content ندارد. از ساختن body برایش خودداری کن و برای اندازهٔ پیام هم `Content-Length` را در این status انتظار نداشته باش. در آزمایشگاه، body خالی را کنار status ثبت می‌کنیم تا «چیزی ندیدم» را با «درخواست شکست خورد» یکی نگیریم.

No body follows the headers; that is not a tool failure. A 204 response has no content by definition. Do not attach a body or expect `Content-Length` for this status. In the lab we record the empty body beside the status so “I saw nothing” is not confused with “the request failed.”

برای `HEAD` هم استاندارد HTTP می‌گوید پاسخ content ندارد، هرچند headerها تا حد ممکن اطلاعاتی را می‌دهند که پاسخ `GET` می‌داد. رفتار دقیق route را در framework با نسخهٔ خود آزمایش کن؛ این فصل وارد طراحی endpointهای `HEAD` یا cache نمی‌شود.

HTTP also specifies that a `HEAD` response has no content, while its headers generally describe what a `GET` response would provide. Test exact route behavior with your framework version; this chapter does not teach `HEAD` endpoint design or caching.

وقتی status و body با هم نمی‌خوانندWhen status and body seem to disagree

حالا endpoint گم‌شده و وضعیت نگهداری را می‌فرستیم. به‌جای گفتن «خطا بود»، چهار شاهد را کنار هم می‌گذاریم: status، نوع محتوا، body و اینکه پاسخ اصلاً از برنامه رسیده یا نه.

Now request a missing product and the maintenance route. Instead of saying “it errored,” collect four signals: status, media type, body and whether a response arrived from the application at all.

ترمینال · مقایسهٔ پاسخ‌ها
curl -i http://127.0.0.1:5080/api/products/missing
curl -i http://127.0.0.1:5080/api/maintenance

برای route گم‌شده، status مورد انتظار ۴۰۴ است و با `Results.NotFound()` ممکن است body خالی باشد. route نگهداری، ۵۰۳ و پاسخ Problem Details می‌دهد. body خطای دوم کمک می‌کند client بفهمد چه رخ داده؛ ولی متنش را برای جزئیات داخلی، stack trace یا secretها محل مناسبی نکن.

The missing route should return 404; `Results.NotFound()` may have an empty body. The maintenance route returns 503 with a Problem Details response. That body helps a client understand the failure, but it must not expose internals, stack traces or secrets.

اگر درخواست به port خاموش برود، پاسخ ۵۰۳ نمی‌گیری؛ اصلاً پاسخ HTTP دریافت نمی‌شود. این فرق برای عیب‌یابی حیاتی است: status فقط وقتی هست که یک پاسخ HTTP از یک server یا intermediary رسیده باشد. بنابراین خطای شبکهٔ curl را مثل status برنامه گزارش نکن.

A request to a closed port does not receive 503; it receives no HTTP response at all. This distinction matters: a status exists only if an HTTP response arrived from a server or intermediary. Do not report a curl network error as an application status.

آزمایشگاه: گزارش «۲۰۰ ولی صفحه خالی است» را حل کنLab: investigate “200, but the page is blank”

تیم پشتیبانی می‌گوید سفارش ثبت شده و API هم ۲۰۰ داده، اما UI چیزی نشان نمی‌دهد. قرار نیست فوراً کد UI یا endpoint را تغییر بدهی؛ اول response را طوری جمع می‌کنی که نفر بعدی بتواند نتیجه‌ات را بازبینی کند.

Support says an order was submitted and the API returned 200, but the UI shows nothing. Do not immediately change the UI or endpoint. First collect a response record another engineer can review.

  1. پروژهٔ Shop API فصل قبل را نگه دار؛ route محصول، محصول گم‌شده، نگهداری و save را اضافه کن و روی loopback اجرا کن.
  2. Keep the Shop API from the previous chapter, add the product, missing-product, maintenance and save routes, then run it on loopback.
  3. برای هر route یک‌بار `curl -i` و یک‌بار جداسازی header/body با `-D` و `-o` را اجرا کن. چهار فایل evidence را در پوشهٔ موقت آزمایش نگه دار.
  4. For each route, run `curl -i` and then separate headers/body with `-D` and `-o`. Keep the four evidence files in a temporary lab folder.
  5. برای محصول سالم، propertyهای body را با قرارداد صفحه مقایسه کن. برای `{}` عمداً body endpoint را خالی کن؛ نشان بده چرا status ۲۰۰ به تنهایی UI را نجات نمی‌دهد.
  6. Compare the successful product body’s properties with the page contract. Deliberately change the endpoint body to `{}` and show why 200 alone cannot fix the UI.
  7. خروجی `204` را ثبت کن و ثابت کن body خالی در این مورد خطا نیست. سپس سرویس را متوقف و درخواست را تکرار کن تا خطای اتصال را از پاسخ HTTP جدا کنی.
  8. Record the 204 and prove an empty body is expected here. Then stop the server and retry to distinguish a connection failure from an HTTP response.
  9. گزارش نهایی: request URL، status، `Content-Type`، خلاصهٔ body، اولین مرز شکست و چیزی که هنوز ثابت نشده؛ مثلاً ذخیره‌شدن سفارش در پایگاه‌داده.
  10. Hand off: request URL, status, `Content-Type`, body summary, first failing boundary and one unproven claim—for example, whether the order reached the database.
راهنمای بازبینیReview notes

گزارش خوب ممکن است بگوید: «GET به route محصول با status ۲۰۰ پاسخ گرفت؛ `Content-Type` برابر JSON بود اما body برابر `{}` شد، پس transport موفق است ولی قرارداد دادهٔ UI تأمین نشده. route گم‌شده ۴۰۴ داد؛ maintenance پاسخ ۵۰۳ با توضیح داد؛ save پاسخ ۲۰۴ بدون body داد. بعد از توقف listener، curl دیگر status نگرفت، پس این یک خطای اتصال بود نه پاسخ ۵xx.»

A good report might say: “The product GET returned 200 with JSON, but the body was `{}`; transport succeeded while the UI data contract was not met. The missing route returned 404; maintenance returned 503 with an explanation; save returned 204 without content. After stopping the listener, curl received no status, so this was a connection failure, not a 5xx response.”

این آزمایش فقط رفتار route و response را ثابت می‌کند. دربارهٔ مجوز کاربر، اعتبار سفارش یا ذخیره‌شدن در DB چیزی ثابت نکرده‌ایم. فایل‌های response را تا پایان بررسی نگه دار؛ cleanup یعنی حذف پوشهٔ آزمایش خودت، نه پاک‌کردن source پروژه.

This experiment proves only route and response behavior. It says nothing about user authorization, order validity or database persistence. Keep response files until review is complete; cleanup means deleting your own lab folder, not the project source.

پاسخ و دلیلSolution and reasoning

status در خط اول است، `Content-Type` در headerها، خط خالی مرز header/body و JSON بعد از آن content است. متن `Server` اگر وجود داشته باشد header است، نه body. ثبت این چهار مرز جلوی این اشتباه را می‌گیرد که status را از JSON parse کنیم.

The status is on the first line, `Content-Type` is a header, the blank line separates headers from content, and the JSON is the content. `Server`, if present, is a header—not body data. Marking these boundaries prevents trying to parse status from JSON.

۲) ۲۰۰ خالی را بازتولید کن2) Reproduce an empty 200

موقتاً پاسخ route محصول را به `Results.Ok(new { })` تغییر بده. درخواست را بفرست و شواهد status و body را ثبت کن. چرا client نمی‌تواند فقط با دیدن ۲۰۰ موفق شود؟

Temporarily change the product result to `Results.Ok(new { })`. Send the request and record status and body. Why can’t the client succeed based only on 200?

پاسخ و دلیلSolution and reasoning

curl باید ۲۰۰ و یک JSON خالی نشان دهد. status موفقیت پردازش را می‌گوید، نه اینکه propertyهای موردنیاز UI حاضرند. route را به قرارداد محصول برگردان و body را هم در smoke test بررسی کن؛ سپس تغییر آزمایشی را حذف کن.

Curl should show 200 and an empty JSON object. The status reports successful handling, not the presence of properties the UI requires. Restore the product contract and assert on the body in a smoke test; then remove the deliberate change.

۳) خانوادهٔ status را بخوان3) Read the status class

برای routeها statusهای ۲۰۰، ۳۰۲، ۴۰۴ و ۵۰۳ را ببین. یک درخواست واقعی برای هرکدام از ۳xxها بفرست یا نمونهٔ پاسخ را ثبت کن و فقط برداشت اولیهٔ خانواده را بنویس.

Observe 200, 302, 404 and 503. Send a real request for a 3xx response or record a response sample, and write only the class-level interpretation for each.

راهنمای پاسخSolution guidance

۲xx موفقیت، ۳xx اقدام/مقصد بعدی، ۴xx مسئله در درخواست فعلی، ۵xx ناتوانی server را نشان می‌دهد. این دسته علت دقیق یا رفتار UI را ثابت نمی‌کند؛ برای redirect باید `Location` را هم ببینی و برای خطا body را.

2xx indicates success, 3xx further action/another target, 4xx a problem with the current request, and 5xx server inability. Classes do not prove the exact cause or UI behavior; inspect `Location` for redirects and the body for errors.

۴) دلیل phrase را حذف کن4) Ignore the reason phrase

در دو خروجی response، متن بعد از کد را مقایسه کن. کد client را طوری بنویس که بر اساس عدد status تصمیم بگیرد، نه عبارت `OK` یا متن محلی سرور.

Compare the text after the code in two response outputs. Write client-side pseudocode that branches on the numeric status, not `OK` or a server-local phrase.

نمونهٔ پاسخExample answer
تصمیم بر اساس کد
if (statusCode >= 200 && statusCode < 300) {
    handleSuccess();
} else {
    handleNonSuccess(statusCode);
}

reason phrase می‌تواند حذف یا محلی‌سازی شود. عدد status بخش پایدارتر قرارداد است؛ خود body و headerهای لازم را هم مطابق نیاز endpoint بخوان.

A reason phrase can be omitted or localized. The numeric status is the stable contract signal; still read the body and required headers for the endpoint.

۵) Content-Type را از body حدس نزن5) Do not infer Content-Type from the body

headerهای route محصول را جدا ذخیره کن و مقدار `Content-Type` را گزارش بده. بعد بگو اگر همین JSON با `text/plain` برگردد، کدام قرارداد برای client مبهم می‌شود.

Save the product route’s headers separately and report `Content-Type`. Explain what becomes ambiguous to a client if the same JSON is labeled `text/plain`.

پاسخ و دلیلSolution and reasoning

خروجی معمول `application/json; charset=utf-8` است. اگر media type متن ساده باشد، client دیگر نمی‌تواند بر اساس metadata مطمئن باشد که باید JSON parser اجرا کند؛ ظاهر متن به‌تنهایی قرارداد نیست. serializer را طوری نگه دار که نوع پاسخ با داده هم‌خوان باشد.

A typical value is `application/json; charset=utf-8`. If the media type says plain text, the client cannot reliably choose a JSON parser from metadata; appearance alone is not the contract. Keep the response serializer and declared media type aligned.

۶) ۲۰۴ را بدون body اثبات کن6) Prove that 204 has no body

برای `/api/save` از `-D` و `-o` استفاده کن. status و اندازهٔ فایل body را ثبت کن. چرا صفر بودن body اینجا موفقیت را نقض نمی‌کند؟

Use `-D` and `-o` for `/api/save`. Record the status and body-file size. Why does a zero-length body not contradict success here?

پاسخ و دلیلSolution and reasoning

status باید ۲۰۴ و فایل body خالی باشد. معنا خود status است: موفقیت بدون content. اگر client بعد از هر موفقیت JSON parse کند، برای این قرارداد خطا می‌سازد؛ اول status/قرارداد را بررسی کند.

The status should be 204 and the body file empty. The code means successful completion without content. A client that parses JSON after every success will fail this contract; it should branch on the status/contract first.

۷) ۴۰۴ خالی را درست تفسیر کن7) Interpret an empty 404 correctly

route گم‌شده را بزن. اگر body خالی است، گزارش بنویس که چه چیزی را می‌دانی و چه چیزی را نمی‌دانی. پیشنهاد بده برای تجربهٔ client چه چیزی می‌توان بهتر کرد.

Call the missing route. If the body is empty, report what you know and do not know, then suggest one improvement for the client experience.

پاسخ و دلیلSolution and reasoning

می‌دانیم پاسخ HTTP با ۴۰۴ رسیده و resource در قرارداد این route پیدا نشده؛ نمی‌دانیم علت typo، حذف منبع یا پیکربندی route بوده. یک پاسخ خطای سازگار با شناسه/پیام امن می‌تواند client را راهنمایی کند؛ stack trace یا دادهٔ حساس را وارد نکن.

We know an HTTP 404 arrived and the resource was not found for this route; we do not know whether this was a typo, missing data or route configuration. A consistent safe error response can guide the client; do not include stack traces or sensitive data.

۸) خطای اتصال را status نساز8) Do not turn a connection error into a status

سرور را متوقف کن و curl را تکرار کن. آیا می‌توانی آن را ۵۰۳ گزارش کنی؟ خروجی واقعی و اولین لایهٔ شکست را ثبت کن.

Stop the server and retry curl. Can you report it as 503? Record the actual output and the first failing layer.

پاسخ و دلیلSolution and reasoning

خیر؛ اگر اتصال برقرار نشود، پاسخ HTTP و status دریافت نشده است. curl خطای اتصال/اتمام مهلت می‌دهد. process، آدرس bind و port را بررسی کن؛ status ۵۰۳ فقط وقتی گزارش می‌شود که server یا واسطه واقعاً آن پاسخ را فرستاده باشد.

No. Without a connection, no HTTP response or status was received; curl reports a connection/timeout error. Check the process, bind address and port. Report 503 only if a server or intermediary actually sent it.

۹) headerها را به فایل جدا بفرست9) Save headers separately

یک فرمان curl بنویس که body محصول را در `product.json`، headerها را در `product.headers` ذخیره کند و status code را چاپ کند. خروجی هر سه را بررسی کن.

Write a curl command that saves the product body to `product.json`, headers to `product.headers` and prints the status code. Inspect all three outputs.

یک راه‌حلOne solution
PowerShell / curl.exe
curl.exe -sS -D product.headers -o product.json -w "%{http_code}`n" http://127.0.0.1:5080/api/products/42
Get-Content product.headers
Get-Content product.json

`-D` و `-o` مقصدهای جدا می‌سازند و `-w` status را روی خروجی استاندارد چاپ می‌کند. نسخهٔ PowerShell و curl ممکن است در نقل‌قول فرق کند؛ در Windows صریحاً `curl.exe` بزن تا alias احتمالی دخالت نکند.

`-D` and `-o` create separate destinations, while `-w` prints the status to standard output. PowerShell/curl quoting can vary; on Windows, call `curl.exe` explicitly to avoid a possible alias.

۱۰) body پاسخ Problem را بخوان10) Read the Problem response body

پاسخ maintenance را با `curl -i` بگیر. کد، media type و دو فیلد توضیحی body را یادداشت کن. چرا body خطا نباید جزئیات داخلی را افشا کند؟

Fetch maintenance with `curl -i`. Record the code, media type and two explanatory body fields. Why should an error body avoid internal details?

پاسخ و دلیلSolution and reasoning

انتظار ۵۰۳ و معمولاً `application/problem+json` با فیلدهایی مثل `status`, `title`, `detail` را داریم؛ قالب واقعی را از خروجی نسخهٔ خود بخوان. پیام امن به client اقدام مناسب می‌دهد، اما path سرور، connection string یا stack trace ممکن است اطلاعات حساس لو بدهد.

Expect 503 and commonly `application/problem+json` with fields such as `status`, `title` and `detail`; verify your version’s actual output. A safe message helps the client, while server paths, connection strings or stack traces can expose sensitive information.

۱۱) خطای body و status را از هم جدا کن11) Separate an error body from its status

در کد route، status را ۲۰۰ نگه دار ولی body را `{ "error": "not found" }` کن. با curl ثابت کن چرا client عمومی این قرارداد را به‌عنوان موفقیت می‌بیند؛ سپس آن را به ۴۰۴ اصلاح کن.

Keep status 200 but return `{ "error": "not found" }`. Use curl to show why a generic client treats this as success, then change it to 404.

پاسخ و دلیلSolution and reasoning

ابزار status ۲۰۰ نشان می‌دهد و body فقط یک property خطا دارد؛ clientهایی که `IsSuccessStatusCode` را می‌سنجند آن را موفق می‌دانند. به‌جای قرارداد دوپهلو، status مناسب و یک قالب خطای پایدار برگردان. متن body به‌تنهایی جای status را نمی‌گیرد.

The tool shows 200 while the body contains an error property; clients checking `IsSuccessStatusCode` will treat it as success. Return an appropriate status and stable error shape instead. Body text alone does not replace the status.

۱۲) Location را در پاسخ redirect پیدا کن12) Find Location in a redirect

برای یک نمونهٔ ۳۰۲ از سرویس محلی یا یک response ساختگی ثبت‌شده استفاده کن. `Location` را جدا از body بخوان و توضیح بده چرا بدون آن مقصد بعدی ممکن است روشن نباشد.

Use a local 302 response or a recorded response sample. Read `Location` separately from the body and explain why the next target may otherwise be unclear.

پاسخ و دلیلSolution and reasoning
نمونهٔ پاسخ
HTTP/1.1 302 Found
Location: /login
Content-Length: 0

۳xx خبر از اقدام/مقصد دیگر می‌دهد و `Location` مقصد را مشخص می‌کند. یک فایل HTML در body ممکن است توضیح بدهد، اما جای header قراردادی را نمی‌گیرد. اینکه curl خودکار redirect را دنبال کند به گزینهٔ اجرا وابسته است؛ پیش‌فرض و `-L` را جدا بررسی کن.

3xx signals another action/target, and `Location` identifies it. An HTML body may explain the response but does not replace the contract header. Whether curl follows the redirect depends on options; compare the default with `-L`.

۱۳) `-L` چه چیزی را عوض کرد؟13) What did `-L` change?

یک URL که redirect می‌کند را یک بار بدون `-L` و یک بار با آن درخواست بده. تعداد پاسخ‌ها و status نهایی را ثبت کن؛ آیا پاسخ اول ناپدید شده است؟

Call a redirecting URL once without `-L` and once with it. Record response count and final status. Did the first response disappear?

پاسخ و دلیلSolution and reasoning

بدون `-L` معمولاً پاسخ redirect اولیه را می‌بینی؛ با `-L` curl مقصد را هم دنبال می‌کند و خروجی نهایی را می‌گیرد (جزئیات نمایش با نسخه و گزینه‌ها فرق دارد). برای عیب‌یابی، redirect chain را پنهان نکن؛ `-v` یا header dump کمک می‌کند هر hop دیده شود.

Without `-L`, you usually see the initial redirect; with it, curl follows the target and reports the final result (display details vary by version/options). Do not hide the redirect chain while debugging; verbose output or header dumps can expose each hop.

۱۴) ۲۰۴ را به JSON parser نفرست14) Do not feed 204 to a JSON parser

یک client کوچک یا pseudocode بنویس که فقط وقتی پاسخ content دارد JSON بخواند. روی `/api/save` اجرا/شبیه‌سازی کن و نشان بده نسخهٔ قبلی چه خطایی می‌کرد.

Write a small client or pseudocode that parses JSON only when the response has content. Run or simulate it against `/api/save` and show the previous failure.

پاسخ و دلیلSolution and reasoning
منطق client
if (response.StatusCode == HttpStatusCode.NoContent) {
    return;
}
var payload = await response.Content.ReadFromJsonAsync<Product>();

204 یعنی content برای parse کردن نیست. فراخوانی بی‌قید `ReadFromJsonAsync` می‌تواند با بدنهٔ خالی شکست بخورد. شرط باید مطابق قرارداد endpoint باشد؛ برای پاسخ‌های دیگر هم status خطا را پیش از deserialize مدیریت کن.

204 means there is no content to parse. An unconditional `ReadFromJsonAsync` can fail on an empty body. Branch according to the endpoint contract; handle error statuses before deserializing other responses too.

۱۵) پاسخ وصل است یا نه؟15) Did an HTTP response arrive?

سه حالت را کنار هم ثبت کن: محصول سالم، route گم‌شده، و server متوقف. برای هرکدام بگو آیا status HTTP وجود دارد و چه فرمان/مدرکی این ادعا را پشتیبانی می‌کند.

Record three cases: healthy product, missing route and stopped server. For each, say whether an HTTP status exists and cite the command/evidence supporting your claim.

پاسخ و دلیلSolution and reasoning

دو مورد اول response دارند: ۲۰۰ و ۴۰۴. مورد سوم خطای اتصال curl دارد و statusی از برنامه دریافت نمی‌شود. این مرزبندی مشخص می‌کند بعدی سراغ body برویم یا listener/port را بررسی کنیم.

The first two have responses: 200 and 404. The third produces a curl connection error and no application status. This boundary tells us whether to inspect a body or check the listener/port next.

۱۶) نمایش curl را با نسخهٔ پروتکل یکی نکن16) Do not confuse curl output with the wire protocol

با curl محلی یک بار HTTP/1.1 و در محیطی که پشتیبانی دارد یک بار HTTP/2 درخواست بفرست. بخش status را مقایسه کن و یادداشت کن کدام قسمت صرفاً نمایش ابزار است.

Send one local request over HTTP/1.1 and, where supported, another over HTTP/2. Compare the status presentation and note which part is tool formatting.

پاسخ و دلیلSolution and reasoning

curl هر دو را برای انسان به شکل متنی نمایش می‌دهد؛ HTTP/2 روی wire خط `HTTP/2 200` به قالب HTTP/1.1 ندارد. اجرای واقعی به پشتیبانی curl و سرور نیاز دارد؛ اگر negotiation نشد، ادعای آزمون HTTP/2 نکن و نتیجه را محدود گزارش کن.

Curl renders both for people; HTTP/2 does not put an HTTP/1.1-style `HTTP/2 200` line on the wire. A real test requires client and server support; if negotiation fails, do not claim an HTTP/2 test and report the limitation.

۱۷) آزمون smoke پاسخ طراحی کن17) Design a response smoke test

برای GET محصول آزمونی بنویس که status، media type و دو property لازم را بررسی کند. توضیح بده چرا چک کردن فقط status کافی نیست و چرا بررسی قیمت business rule کامل نیست.

این assertionها شکل قرارداد HTTP و دادهٔ حداقلی را ثابت می‌کنند، نه محاسبهٔ قیمت، دسترسی یا persistence. برای آن‌ها آزمون جدا و fixture مناسب لازم است.

These assertions prove the HTTP contract and minimum data shape, not price calculation, authorization or persistence. Those need separate tests and suitable fixtures.

۱۸) گزارش نهایی incident را تحویل بده18) Hand off a final incident report

یک پاسخ عمدی خراب بساز: status ۲۰۰ با body خالی برای clientای که محصول می‌خواهد. گزارش را با request، پاسخ واقعی، قرارداد مورد انتظار، اصلاح و verification کامل کن.

Verification: the same request now has 200, `application/json`, and `id`/`name`. Limit: this does not prove database persistence or authorization.
