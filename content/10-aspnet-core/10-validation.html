Validation: well-formed input is not necessarily valid data

درخواست JSON بدون خطا parse شده و object هم ساخته شده؛ اما quantity منفی است و تاریخ پایان قبل از شروع. اینجا binding کارش را درست انجام داده. حالا باید مشخص کنیم کدام قانون را کجا بررسی کنیم و پاسخ خطا چه قراردادی با client دارد.

The JSON parsed and an object was created, but quantity is negative and the end date precedes the start. Binding did its job. Now decide which rules belong where and what error contract the client should receive.

از فصل قبل می‌دانیم Model Binding فقط دادهٔ درخواست را به شکل پارامتر یا DTO درمی‌آورد. مثلاً quantity=-3 عدد معتبری است و JSON هم درست است؛ ولی برای سفارش معتبر نیست. اعتبارسنجی باید این دو سؤال را جدا کند: «آیا ورودی از نظر ساختار و قواعد ساده قابل قبول است؟» و «آیا این عملیات در وضعیت فعلی سیستم مجاز است؟»

From the previous chapter, model binding only turns request data into parameters or a DTO. For example, quantity=-3 is a valid integer and valid JSON, but not a valid order. Validation separates two questions: “Is this input structurally and locally acceptable?” and “Is this operation allowed in the system's current state?”

این نمودار قانون همیشگی HTTP برای همهٔ APIها نیست؛ قرارداد endpoint را ما تعریف می‌کنیم. الگوی رایج این است که ورودی نامعتبر ۴۰۰ و وضعیت ناسازگار دامنه پاسخ مناسب خودش را بگیرد. مهم این است که failure را درست دسته‌بندی کنیم و state را تغییر ندهیم.

The diagram is not a universal HTTP law; we define the endpoint contract. A common pattern is 400 for invalid input and a suitable domain response for conflicting state. What matters is categorizing the failure correctly and not changing state.

DataAnnotations برای قانون‌های محلی و قابل‌فهمUse DataAnnotations for local, understandable rules

برای فیلدهای لازم، طول، بازهٔ عددی و قالب ساده می‌توانی attribute بگذاری. این قانون‌ها نزدیک DTO دیده می‌شوند و برای فرم یا API مفیدند؛ اما جای مجوز دسترسی، موجودبودن محصول یا وضعیت فعلی سفارش را نمی‌گیرند.

Attributes can express required fields, length, numeric ranges, and simple formats. These rules are visible near the DTO and help forms or APIs, but they do not replace authorization, product availability, or current order state checks.

DTO با محدودیت ورودی · DTO constraints
public sealed class CreateOrderRequest
{
    [Required, StringLength(80, MinimumLength = 2)]
    public string? CustomerName { get; init; }

    [Range(1, 50)]
    public int Quantity { get; init; }

    [EmailAddress]
    public string? ContactEmail { get; init; }
}

به نکتهٔ subtle دقت کن: int غیرnullable اگر از JSON نیاید می‌تواند default یعنی صفر بگیرد؛ [Range(1, 50)] صفر را رد می‌کند. در مقابل، [Required] روی value type غیرnullable به‌تنهایی نبودن property را از مقدار default به‌سادگی جدا نمی‌کند. ورودی missing و صفر را با test مستقل بسنج.

Notice a subtlety: a missing non-nullable int can become its default, zero; [Range(1, 50)] rejects zero. By itself, [Required] on a non-nullable value type does not cleanly distinguish an omitted property from its default. Test missing and zero separately.

برای ASP.NET Core MVC و controller دارای [ApiController]، خطای ModelState معمولاً پیش از اجرای action پاسخ ۴۰۰ می‌دهد؛ body پیش‌فرض از جنس ValidationProblemDetails است. در فصل ۹ دیدیم action ممکن است اصلاً اجرا نشود. پس پاسخ را با request ثبت‌شده بررسی کن، نه با حدس از breakpoint.

For ASP.NET Core MVC controllers marked [ApiController], invalid ModelState commonly produces a 400 before the action runs; the default response uses ValidationProblemDetails. As Chapter 9 showed, the action may never execute. Inspect the actual response rather than inferring behavior from a breakpoint.

آزمایش invalid model · Invalid model request
curl -i -X POST http://localhost:5080/orders \
  -H 'Content-Type: application/json' \
  -d '{"customerName":"A","quantity":0}'

در تست response status و مسیر خطا مثل Quantity را بررسی کن. خودکار بودن پاسخ ۴۰۰ مربوط به رفتار MVC و ApiController است؛ آن را بی‌بررسی به Minimal API یا endpoint دستی تعمیم نده.

Assert the status and an error path such as Quantity. Automatic 400 is MVC ApiController behavior; do not transfer it to a Minimal API or manually handled endpoint without checking.

اگر برای نام کاربری اول query بزنی «وجود ندارد» و بعد insert کنی، دو درخواست هم‌زمان می‌توانند هر دو جواب «آزاد است» بگیرند. قید unique در پایگاه‌داده داور نهایی است؛ pre-check فقط می‌تواند پیام دوستانه‌تری بدهد. exception قید را به پاسخ امن و قابل‌فهم تبدیل کن، نه این‌که خطای داخلی را لو بدهی.

If two requests both query that a username is absent before inserting, both can see it as available. The database unique constraint is authoritative; a pre-check only improves messaging. Translate a constraint violation into a safe, understandable response rather than exposing an internal error.

client محل اعتماد نیست: validation سمت مرورگر تجربه را بهتر می‌کند، ولی قابل دورزدن است. API باید همان ورودی را سمت سرور بررسی کند و قانون امنیتی را صرفاً به JavaScript نسپارد.

Do not trust the client: browser validation improves UX but can be bypassed. The API must validate server-side; never delegate a security rule only to JavaScript.

وقتی دو فیلد با هم معنا دارندWhen two fields only make sense together

قانون «تاریخ پایان بعد از شروع باشد» به property منفرد تعلق ندارد. می‌توانی آن را با validation سطح مدل یا در use case پیاده کنی. هرجا قرارش می‌دهی، یک تست برای حالت درست و دو تست مرزی بساز تا timezone و مقدار null ناخواسته پنهان نماند.

“End date follows start date” does not belong to one property. Implement it at model validation or in the use case. Wherever it lives, test a valid case and boundary cases so timezone and null handling are not hidden.

اعتبارسنجی سطح مدل · Model-level rule
public sealed class BookingRequest : IValidatableObject
{
    public DateOnly Start { get; init; }
    public DateOnly End { get; init; }

    public IEnumerable<ValidationResult> Validate(
        ValidationContext context)
    {
        if (End < Start)
        {
            yield return new ValidationResult(
                "End must be on or after Start.",
                new[] { nameof(End), nameof(Start) });
        }
    }
}

این validation فقط مقایسهٔ دو تاریخ را انجام می‌دهد؛ ظرفیت اتاق، تعطیلی تقویم یا مجازبودن رزرو را نمی‌داند. اگر قانون به دیتابیس یا سرویس بیرونی وابسته است، آن را به attribute همگام و query پنهان داخل validation تبدیل نکن؛ orchestration و خطای I/O باید معلوم بمانند.

This rule compares two dates only; it knows nothing about room capacity, calendar closures, or booking authorization. If a rule depends on a database or remote service, do not hide synchronous I/O inside an attribute; keep orchestration and I/O failures explicit.

نکتهٔ نسخه‌ای: اعتبارسنجی Minimal API در .NET 10Version note: Minimal API validation in .NET 10

در ASP.NET Core 10، اعتبارسنجی Minimal API از زیرساخت Microsoft.Extensions.Validation استفاده می‌کند و با builder.Services.AddValidation() فعال می‌شود؛ این رفتار را با MVC یکی ندان. مستند رسمی می‌گوید این package در MVC/Razor Pages پشتیبانی نمی‌شود و source-generated metadata در Minimal API مهم است؛ بدون metadata موردنیاز، validation خودکار ممکن است اصلاً اجرا نشود.

In ASP.NET Core 10, Minimal API validation uses Microsoft.Extensions.Validation and is enabled with builder.Services.AddValidation(); this is not the MVC pipeline. The official guide says the package is not supported for MVC/Razor Pages and source-generated metadata matters for Minimal APIs. Without required metadata, automatic validation may not run.

ثبت سرویس اعتبارسنجی در .NET 10
builder.Services.AddValidation();

app.MapPost("/orders", (CreateOrderRequest request) =>
{
    // Input validation has run before this handler
    return Results.Accepted();
});

در .NET 10 مستند رسمی یک محدودیت شناخته‌شده هم ذکر می‌کند: برخی nullable value typeها در Minimal API هنگام null بودن با attributeها validate نمی‌شوند. اگر nullable value type پارامتر داری، test موردی بنویس و نتیجه را از روی رفتار runtime بگیر؛ در این فصل آن را تضمین فرض نمی‌کنیم. MVC را هم با این limitation اشتباه نکن.

The .NET 10 official guide also notes a known limitation: some nullable value-type Minimal API parameters are not validated by attributes when null. If you use one, add a focused test and rely on observed runtime behavior; this chapter does not promise otherwise. Do not confuse this with MVC behavior.

برای یک course که چند نسخه را پوشش می‌دهد، نسخهٔ هدف را کنار مثال بنویس. «در ASP.NET Core همیشه همین است» معمولاً ادعای امنی نیست.

For a course spanning versions, label the target version beside the example. “ASP.NET Core always behaves this way” is rarely a safe claim.

آزمایشگاه: ثبت سفارش و پاسخ قابل‌مصرف برای clientLab: validate an order and return client-usable errors

endpoint فصل ۹ را ادامه بده. سفارش باید نام مشتری، تعداد و دو تاریخ داشته باشد. سه دسته failure بساز: JSON/parsing، محدودیت محلی DTO، و قانون وابسته به وضعیت دامنه. برای هرکدام response قابل‌فهم و test مستقل بنویس.

Continue the Chapter 9 endpoint. An order has a customer name, quantity, and two dates. Create three failure classes: JSON/parsing, local DTO constraints, and a state-dependent domain rule. Give each a clear response and an independent test.

  1. DataAnnotations برای نام و quantity بگذار؛ یک درخواست معتبر و دو درخواست نامعتبر ارسال کن.
  2. Add DataAnnotations for name and quantity; send one valid and two invalid requests.
  3. برای start/end قانون cross-field بنویس و خطا را به fieldهای مربوط وصل کن.
  4. Implement a cross-field start/end rule and associate the error with relevant fields.
  5. در MVC با ApiController پاسخ خودکار را ثبت کن؛ status، content type و ساختار ProblemDetails را assert کن.
  6. Capture MVC ApiController's automatic response; assert status, content type, and ProblemDetails shape.
  7. یک rule دامنه مثل محصول غیرفعال را در use case بررسی کن؛ آن را به DTO attribute منتقل نکن.
  8. Check a domain rule such as an inactive product in the use case; do not move it into a DTO attribute.
  9. اگر unique بودن لازم است، قید DB و دو درخواست هم‌زمان یا تست repository را بررسی کن؛ pre-check را تضمین ندان.
  10. For uniqueness, test the database constraint and concurrent attempts; do not treat a pre-check as a guarantee.

محدودهٔ ایمنی: برای تست هم‌زمانی از دیتابیس آزمایشی و دادهٔ دورریختنی استفاده کن؛ روی production رکورد واقعی را دست‌کاری نکن.

Safety boundary: use a disposable test database for concurrency checks; never mutate real production records.

۸. نام تکراری و race

راهنما

۹. پیام خطای امن

۱۰. DTO با domain entity

راهنما

۱۳. async validation را کجا بگذاریم؟

قانونی بنویس که نیاز به پرس‌وجوی DB دارد؛ آن را از attribute synchronously اجرا نکن و failure دیتابیس را از رد ورودی تفکیک کن.

Implement a rule that queries a database; do not run it synchronously in an attribute and distinguish DB failure from invalid input.

راهنما

بررسی را در use case یا validator async قابل‌آزمایش بگذار. timeout/عدم دسترسی DB خطای سیستم است، نه این‌که ورودی کاربر حتماً نامعتبر باشد.

راهنما

DataAnnotations checks data, not identity or ownership. Test policy/resource authorization and verify state remains unchanged.

۱۷. regression برای قانون اصلاح‌شده

پس از تغییر محدودیت، testهای valid، نامعتبر و boundary را بساز تا افزایش سقف از ۵۰ به ۱۰۰ ناخواسته نشود.

After changing a constraint, add valid, invalid, and boundary tests so an accidental limit change from 50 to 100 is caught.

راهنما

داده‌های ۱، ۵۰، ۵۱ و مقادیر null/حذف را طبق قرارداد تست کن. هر test باید درخواست واقعی یا validator را روی مدل بسازد.

Test 1, 50, 51, and null/omission cases according to the contract. Each test should send a request or invoke the validator with a concrete model.

۱۸. incident: ۴۰۰های ناگهانی

بعد از انتشار، clientها ۴۰۰ بیشتری می‌بینند. test/diagnostic بنویس که خطای binding، DataAnnotations و رد دامنه را جدا گزارش کند؛ secret یا payload کامل کاربر را ثبت نکن.

After release, clients see more 400s. Build a test/diagnostic that separates binding errors, DataAnnotations failures, and domain rejection without logging secrets or full user payloads.

راهنما

requestهای نمونهٔ حداقلی، status، ProblemDetails path و marker ورود handler را کنار هم بگیر. یک نمودار شمارش بر اساس دستهٔ خطا بساز و سپس همان request را پس از fix تکرار کن.

Capture minimal requests, status, ProblemDetails paths, and handler-entry markers. Count by failure category, then repeat the same request after the fix.

جمع‌بندی: دادهٔ معتبر، قانون، پاسخWrap-up: input, rules, response

DataAnnotations برای قانون‌های محلی است؛ شرط چندفیلدی به مدل/دامنه تعلق دارد؛ وضعیت و مجوز را use case می‌فهمد؛ constraint پایگاه‌داده هم مرجع نهایی یکتایی است. Client-side فقط راهنمایی می‌کند. برای هر failure response ساختاریافته بده و test کن که state عوض نشده. فصل بعد سؤال تازه‌ای می‌سازد: وقتی DTO بیرونی با مدل دامنه فرق دارد، چطور آن‌ها را تبدیل کنیم بدون این‌که مرزها قاطی شوند؟

DataAnnotations fit local rules; cross-field invariants belong to model/domain logic; use cases know state and authorization; database constraints remain authoritative for uniqueness. Client-side checks only assist users. Return structured errors and test that failure leaves state unchanged.
