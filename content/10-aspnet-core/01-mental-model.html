مدل ذهنی: host، pipeline و DI

The mental model: host, pipeline, and DI

یک کاربر می‌گوید صفحهٔ سفارش باز نمی‌شود. از بیرون فقط می‌دانیم مرورگر درخواست فرستاده و پاسخ درست نگرفته است. هنوز نمی‌دانیم درخواست به برنامه رسیده، middleware آن را متوقف کرده، endpoint اجرا نشده یا کد پایگاه‌داده خطا داده. اگر مرزها را بشناسیم، به‌جای دست‌کاری تصادفی کد، مسیر همان درخواست را دنبال می‌کنیم.

A user says the order page will not load. From the outside, we only know that the browser sent a request and did not get the expected response. We do not yet know whether it reached the app, middleware stopped it, the endpoint did not run, or database code failed. Knowing the boundaries lets us trace this request instead of changing code at random.

سفارش در کدام مرز گم شد؟Where did the order disappear?

در یک فروشگاه کوچک endpoint فهرست سفارش‌ها جواب 500 می‌دهد. developer مستقیم سراغ query می‌رود؛ اما log نشان می‌دهد endpoint اصلاً اجرا نشده. middleware احراز هویت قبل‌تر درخواست را متوقف کرده است. سؤال درست دیگر «کدام query خراب است؟» نیست؛ «درخواست تا کدام مرحله رسید و چه چیزی آن را متوقف کرد؟» است.

A small shop’s order-list endpoint returns 500. The developer jumps to the query, but logs show the endpoint never ran. Authentication middleware stopped the request earlier. The useful question is no longer “which query broke?” but “how far did the request travel, and what stopped it?”

ASP.NET Core برنامهٔ وب را دور چند نقش می‌سازد. host عمر برنامه و منابعی مثل configuration، logging و dependency injection را هماهنگ می‌کند. server مثل Kestrel اتصال HTTP را می‌پذیرد و request را به قالب HttpContext در اختیار برنامه می‌گذارد. pipeline زنجیره‌ای از middlewareهاست؛ بعضی ادامه می‌دهند، بعضی پاسخ می‌سازند و زنجیره را تمام می‌کنند. اگر درخواست به endpoint برسد، منطق آن اجرا می‌شود.

ASP.NET Core web apps are built around several roles. The host coordinates application lifetime and resources such as configuration, logging, and dependency injection. A server such as Kestrel accepts HTTP connections and exposes requests to the app through HttpContext. The pipeline is a chain of middleware; some continue, some produce a response and end the chain. If a request reaches an endpoint, its logic runs.

host نگهبان عمر برنامه استThe host owns application lifetime

در templateهای جدید، Program.cs معمولاً با WebApplication.CreateBuilder(args) شروع می‌شود. builder تنظیمات، سرویس‌ها و server را آماده می‌کند؛ Build یک WebApplication می‌سازد؛ Run آن را اجرا و برای درخواست‌ها آماده نگه می‌دارد. host همچنین shutdown را هماهنگ می‌کند. لازم نیست برای هر برنامه کلاس Startup یا HostBuilder قدیمی بسازیم؛ الگوی پیش‌فرض فعلی همین مدل کم‌کد است.

In current templates, Program.cs commonly starts with WebApplication.CreateBuilder(args). The builder prepares configuration, services, and the server; Build creates a WebApplication; Run starts it and keeps it ready for requests. The host also coordinates shutdown. You do not need to create a legacy Startup or HostBuilder structure for every app; the current default is streamlined.

حداقل API برای دیدن چرخه
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/", () => Results.Text("Shop is alive"));

app.Run();

اگر همین برنامه Run نشود، تعریف MapGet به‌تنهایی process را زنده نگه نمی‌دارد. اگر Run اجرا شد ولی URL یا port آن چیزی نیست که انتظار داری، سراغ hosting configuration می‌رویم؛ endpoint و binding دو تصمیم جدا هستند.

Without Run, defining MapGet alone does not keep the process serving requests. If it runs but listens on an unexpected URL or port, inspect hosting configuration; endpoint mapping and server binding are separate decisions.

Kestrel درخواست را می‌پذیرد؛ منطق کسب‌وکار نیستKestrel accepts requests; it is not business logic

Kestrel سرور HTTP کراس‌پلتفرم ASP.NET Core است. ممکن است مستقیم در دسترس باشد یا پشت reverse proxy قرار بگیرد؛ در هر دو حالت درخواست داخل برنامه به pipeline می‌رسد. اگر proxy بیرونی 502 می‌دهد، هنوز نمی‌دانیم Kestrel اجراست یا نه. log برنامه، port شنونده و اتصال proxy به upstream شاهدهای جدا هستند.

Kestrel is ASP.NET Core’s cross-platform HTTP server. It can be exposed directly or sit behind a reverse proxy; either way, a request entering the app reaches its pipeline. If the external proxy returns 502, we still do not know whether Kestrel is running. App logs, listening port, and proxy-to-upstream connectivity are separate evidence.

یک HttpContext برای درخواستOne HttpContext per request

HttpContext نمای درخواست جاری است: method، path، headers، user، request/response و featureهای server. با پایان درخواست، آن context را برای کار پس‌زمینه ذخیره نکن؛ lifetime درخواست و کار پس‌زمینه یکی نیست.

HttpContext represents the current request: method, path, headers, user, request/response, and server features. Do not retain it for background work after the request; request lifetime and background-work lifetime differ.

pipeline فقط یک فهرست middleware نیستThe pipeline is more than a list of middleware

middleware معمولاً سه انتخاب دارد: قبل از ادامه کاری انجام دهد، next را صدا بزند تا درخواست جلو برود، و بعد از بازگشت پاسخ کاری انجام دهد. اگر next را صدا نزند، short-circuit کرده است. ترتیب ثبت در Program.cs ترتیب درخواست را می‌سازد؛ مسیر برگشت پاسخ برعکس می‌شود. جزئیات middleware و ترتیب امنیتی آن فصل ۴ است؛ امروز فقط از آن برای یافتن مرز درخواست استفاده می‌کنیم.

Middleware can do work before continuing, call next to pass the request onward, and do work after the response returns. If it does not call next, it short-circuits. Registration order in Program.cs defines request order; response unwinds in reverse. Chapter 4 studies middleware ordering and security in depth; here we use the concept to locate request boundaries.

middleware مشاهده‌گر برای آزمایش
app.Use(async (context, next) =>
{
    Console.WriteLine($">> {context.Request.Method} {context.Request.Path}");
    await next();
    Console.WriteLine($"<< {context.Response.StatusCode}");
});

app.MapGet("/orders", () => Results.Ok(new[] { "A-101" }));

به کنسول باید خط درخواست و سپس status پاسخ را ببینی. اگر endpoint یا middleware بعدی exception بدهد، خط دوم ممکن است بدون try/finally اجرا نشود؛ middleware واقعی برای ثبت پایان درخواست باید exception و cancellation را هم در طراحی ببیند. این نمونه فقط آزمایش مشاهده است، نه قالب کامل logging production.

The console should show a request line followed by the response status. If a later endpoint or middleware throws, the second line may not run without try/finally; production request logging must account for exceptions and cancellation. This is an observation experiment, not a complete production logging template.

endpoint منطق مسیر است؛ DI همکارهایش را می‌دهدAn endpoint owns route logic; DI supplies collaborators

endpoint می‌گوید برای این route چه کاری انجام شود. سرویس‌های ثبت‌شده در container را می‌توان با constructor injection یا پارامترهای پشتیبانی‌شده گرفت. در Minimal API، binding پارامترها قواعد خودش را دارد و فصل‌های بعدی آن را جدا می‌کنند. در این فصل فقط می‌بینیم endpoint مستقیماً Kestrel یا ساختن دستی کل وابستگی‌ها را مدیریت نمی‌کند.

An endpoint defines what happens for a route. Registered services can be supplied through constructor injection or supported parameters. Minimal API parameter binding has its own rules, covered in later chapters. For now, notice that an endpoint does not manage Kestrel or manually construct every collaborator.

سرویس ساده و endpoint
builder.Services.AddSingleton<Clock>();
var app = builder.Build();

app.MapGet("/time", (Clock clock) =>
    Results.Ok(new { utc = clock.UtcNow }));

app.Run();

public sealed class Clock
{
    public DateTimeOffset UtcNow => DateTimeOffset.UtcNow;
}

در این مثال DI سرویس Clock را به handler می‌دهد. singleton برای این نمونهٔ بی‌حالت امن است؛ سرویس واقعی با state، request data یا DbContext را کورکورانه singleton نکن. طول عمر سرویس‌ها در فصل ۶ دقیق بررسی می‌شود.

Here DI supplies Clock to the handler. Singleton is safe for this stateless example; do not blindly make a stateful, request-aware service or DbContext singleton. Service lifetimes are examined carefully in Chapter 6.

پاسخ هم بخشی از همان مسیر استThe response is part of the same path

endpoint می‌تواند status، header و body بسازد. middlewareهای قبلی پس از برگشت next فرصت دارند response را مشاهده یا تکمیل کنند؛ بنابراین اگر status نهایی با چیزی که endpoint ساخت فرق دارد، ممکن است exception handler یا middleware دیگری آن را تغییر داده باشد. ثبت status نهایی در مرز بیرونی معمولاً از حدس‌زدن داخل handler مفیدتر است.

An endpoint can produce status, headers, and body. Earlier middleware can inspect or complete the response after next returns; if the final status differs from what the endpoint produced, an exception handler or another middleware may have changed it. Observing final status at an outer boundary is often more useful than guessing inside the handler.

آزمایشگاه: درخواست را با log دنبال کنLab: trace a request with logs

یک برنامهٔ خالی Minimal API بساز. می‌خواهیم سه route را طوری بسنجیم که تفاوت پاسخ endpoint، short-circuit و خطای startup دیده شود. هر تغییر را در همان پروژهٔ تمرینی نگه دار.

Create an empty Minimal API app. We will test three routes to distinguish endpoint responses, short-circuiting, and startup failure. Keep all changes in the practice project.

  1. route /health را با status 200 و route /missing را بدون handler اجرا و تفاوت status را ثبت کن.Run /health with status 200 and /missing without a handler; record the status difference.
  2. middleware مشاهده‌گر را قبل از endpointها اضافه کن و ترتیب log درخواست/پاسخ را ببین.Add the observer middleware before endpoints and inspect request/response log order.
  3. یک middleware موقت برای /blocked بساز که next را صدا نزند و پاسخ 403 بدهد. ثابت کن endpoint بعدی اجرا نشده است.Add temporary middleware that does not call next for /blocked and returns 403. Prove the later endpoint did not run.
  4. برای یک route سرویس Clock را از DI بگیر. سرویس را مستقیم در handler new نکن؛ تفاوت registration و use را بنویس.Inject Clock into a route. Do not construct it with new in the handler; explain registration versus use.
  5. فرایند را با Ctrl+C متوقف کن و ببین host چه زمانی shutdown را گزارش می‌کند. یک exception داخل endpoint ایجاد کن و آن را از startup failure جدا کن.Stop with Ctrl+C and observe host shutdown. Cause an endpoint exception and distinguish it from startup failure.

گزارش باید برای هر درخواست بگوید: به server رسید؟ middleware کدام بود؟ endpoint اجرا شد؟ چه status نهایی برگشت؟ این چهار پاسخ کمک می‌کنند در فصل‌های بعد routing، filters و exception handling را در جای درست قرار دهی.

For each request, report: did it reach the server, which middleware ran, did the endpoint execute, and what final status returned? These answers help place routing, filters, and exception handling correctly in later chapters.

تمرین‌ها: درخواست تا کجا پیش رفت؟Exercises: how far did the request get?

در هر سناریو مرز شکست را مشخص کن؛ اگر هنوز شاهد کافی نیست، فرمان یا log بعدی را پیشنهاد بده.

Identify the failing boundary in each scenario; if evidence is insufficient, name the next command or log to collect.

آیا درخواست HTTP می‌تواند به endpoint رسیده باشد؟ چه چیزی را اول می‌بینی؟

Could an HTTP request have reached an endpoint? What do you inspect first?

پاسخAnswer

خیر اگر process/host شروع نشده باشد. startup log و binding server را ببین.

Not if the process/host never started. Inspect startup logs and server binding.

۲) Kestrel روی پورت دیگری گوش می‌دهد2) Kestrel listens on another port

این مشکل route است یا binding؟

Is this a route issue or a binding issue?

توضیحExplanation

اول binding/configuration و listener را بررسی کن؛ endpoint فقط پس از رسیدن درخواست به server اهمیت دارد.

۳) middleware پاسخ 403 داد3) Middleware returned 403

آیا endpoint لازم است اجرا شده باشد؟

Must the endpoint have run?

پاسخAnswer

نه؛ middleware می‌تواند short-circuit کند. log endpoint را بررسی کن.

No; middleware can short-circuit. Check endpoint logs.

۴) endpoint 500 می‌دهد4) Endpoint returns 500

کدام مرزها را می‌دانی که رد شده؟

Which boundaries do you know were crossed?

پاسخAnswer

اگر log endpoint داریم، درخواست از server و middlewareهای پیشین عبور کرده و endpoint شروع شده؛ DI و کد endpoint را بررسی کن.

If endpoint logs exist, the request passed the server and prior middleware and began endpoint execution; inspect DI and endpoint code.

۵) Run فراموش شده5) Run was omitted

MapGet در کد هست اما سرویس درخواست نمی‌پذیرد. چرا؟

MapGet exists, but the app serves no requests. Why?

پاسخAnswer

تعریف endpoint به‌تنهایی host را اجرا نمی‌کند؛ Run باید lifecycle را آغاز کند.

Defining an endpoint does not run the host; Run starts the lifetime.

۶) کار پس‌زمینه HttpContext را ذخیره کرد6) Background work retained HttpContext

مشکل طراحی چیست؟

What is the design problem?

توضیحExplanation

HttpContext به درخواست و lifetime آن وابسته است؛ پس از پاسخ، دادهٔ لازم را به شیء مستقل منتقل کن و context را نگه ندار.

HttpContext belongs to a request lifetime; copy required data into an independent object and do not retain the context.

۷) پاسخ از middleware برگشت7) Response returned through middleware

چرا ترتیب log پیش و پس از next برعکس به نظر می‌رسد؟

Why do before/after next logs appear to reverse?

پاسخAnswer

درخواست به جلو می‌رود و response از stack middlewareهای قبلی به عقب برمی‌گردد.

The request moves forward; the response unwinds through prior middleware in reverse.

۸) Kestrel یا business logic؟8) Kestrel or business logic?

کدام log کمک می‌کند اتصال به server از خطای endpoint جدا شود؟

Which logs separate server reachability from endpoint failure?

پاسخAnswer

startup/listening log و log مرزی middleware در کنار log endpoint.

Startup/listening logs and boundary middleware logs alongside endpoint logs.

۹) Reverse proxy خطای 502 داد9) Reverse proxy returned 502

آیا این ثابت می‌کند endpoint پاسخ نداده؟

Does this prove the endpoint failed to respond?

پاسخAnswer

نه؛ proxy ممکن است به Kestrel نرسیده باشد. process، listener و اتصال upstream را جدا بررسی کن.

No; the proxy may not have reached Kestrel. Check process, listener, and upstream connectivity separately.

۱۰) DI نتوانست سرویس را بسازد10) DI could not create a service

این خطا معمولاً پیش از منطق endpoint کجاست؟

Where does this error usually occur relative to endpoint logic?

During dependency resolution. Inspect registration and dependency chain; lifetime details come in the DI chapter.

۱۱) singleton دارای state درخواست است11) Singleton stores request state

چه خطری ایجاد می‌شود؟

What risk does this create?

پاسخAnswer

درخواست‌های همزمان می‌توانند داده را نشت بدهند یا race بسازند؛ state هر درخواست را در singleton مشترک ذخیره نکن.

۱۲) endpoint تعریف شده ولی route پیدا نیست12) Endpoint is defined but route is not found

به جای تغییر database، کدام مرز را بررسی می‌کنی؟

Which boundary do you inspect instead of changing the database?

Route, method, and endpoint mapping; routing details are in Chapter 3.

۱۳) HttpContext در log نیست13) No HttpContext log

چه چیزی را قبل از نتیجه‌گیری دربارهٔ endpoint می‌سنجی؟

What do you check before drawing conclusions about the endpoint?

پاسخAnswer

رسیدن درخواست به Kestrel و اجراشدن middleware مشاهده‌گر؛ شاید درخواست اصلاً به این process نرسیده است.

Whether the request reached Kestrel and the observer middleware; it may never have reached this process.

۱۴) endpoint status 200 ساخته14) Endpoint created status 200

اما client 500 دیده؛ چه لایه‌ای ممکن است دخیل باشد؟

But the client saw 500; which layer might be involved?

بررسیCheck

middleware بعدی/قبلی، exception یا reverse proxy. status نهایی را در مرز بیرونی و log proxy مقایسه کن.

Middleware, an exception, or reverse proxy. Compare final status at the outer boundary with proxy logs.

۱۵) سرویس دستی ساخته شده15) Service constructed manually

چه چیزی از DI container را از دست می‌دهی؟

۱۶) host shutdown شد16) Host is shutting down

آیا احتمالاً مشکل routing است؟

Is routing the likely issue?

پاسخAnswer

نه ابتدا lifetime، signal توقف و host log را ببین؛ اگر server متوقف است routeها فرصت اجرا ندارند.

No; inspect lifetime, stop signal, and host logs first. If the server stopped, routes cannot execute.

۱۷) status در middleware ثبت نمی‌شود17) Middleware misses final status

What might prevent code after next from running?

پاسخAnswer

exception یا cancellation. برای telemetry واقعی try/finally و semantics خطا را آگاهانه مدیریت کن.

An exception or cancellation. For real telemetry, handle try/finally and error semantics deliberately.

۱۸) incident را مسیرمحور گزارش کن18) Report the incident by boundary

چه چهار پرسش کوتاهی پاسخ را از حدس جدا می‌کند؟

Which four questions separate evidence from guesses?

چهار پرسشFour questions

host زنده بود؟ server درخواست را گرفت؟ کدام middleware اجرا/متوقف کرد؟ endpoint چه status و logی ساخت؟

Was the host alive? Did the server receive the request? Which middleware ran or stopped it? What status and logs did the endpoint produce?

حالا درخواست را به‌جای حدس، دنبال می‌کنیNow you trace requests instead of guessing

host برنامه و lifetime را هماهنگ می‌کند؛ Kestrel HTTP را می‌پذیرد؛ HttpContext درخواست جاری را نمایندگی می‌کند؛ middlewareها مسیر را می‌سازند؛ endpoint رفتار route را انجام می‌دهد؛ DI همکارهای endpoint را فراهم می‌کند. یک درخواست ممکن است قبل از endpoint متوقف شود و پاسخ در مسیر برگشت دوباره از middlewareها عبور کند.

The host coordinates app lifetime; Kestrel accepts HTTP; HttpContext represents the current request; middleware forms the path; an endpoint handles route behaviour; DI supplies its collaborators. A request may stop before an endpoint, and the response travels back through middleware.

اگر کاربر خطا دید، اول ثابت کن درخواست به process رسیده و host فعال بوده. بعد log مرزی و endpoint را کنار هم بگذار. تا مرز خراب معلوم نشده سراغ query یا DI نرو؛ فصل‌های بعد هر کدام یک بخش این مسیر را عمیق می‌کنند: routing، middleware، DI و response.

When a user sees an error, first prove the request reached the process and the host was active. Then compare boundary and endpoint logs. Do not jump to a query or DI until the failing boundary is known; later chapters deepen routing, middleware, DI, and response handling.
