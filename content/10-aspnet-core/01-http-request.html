درخواست HTTP از نزدیک

An HTTP request up close

تیم می‌گوید «API خراب است»، ولی هنوز معلوم نیست برنامه چه چیزی دریافت کرده. شاید path اشتباه باشد، شاید query نرسیده باشد، شاید body اصلاً فرستاده نشده. پیش از اینکه سراغ route و middleware برویم، خود درخواست را از نزدیک بخوانیم: چه کسی چه چیزی را از کجا می‌خواهد و چه داده‌ای همراهش می‌فرستد؟

The team says “the API is broken,” but we do not yet know what the application received. Perhaps the path is wrong, a query parameter is missing, or no body was sent. Before routes and middleware, let us inspect the request itself: who is asking for what, where, and with which data?

قبل از endpoint، ببین درخواست چه می‌گویدBefore the endpoint, read what the request says

فرض کن می‌خواهی دو عدد از یک سفارش را برای صفحهٔ فروشگاه بگیری. به‌جای اینکه بگویی «یه درخواست بفرست»، مشخص کن چه چیزی را می‌خواهی و چه اطلاعاتی برای انتخاب نتیجه لازم است. در HTTP این قصد در شکل یک پیام قابل‌انتقال بیان می‌شود؛ سرور آن را می‌خواند و بر اساس method، مقصد و headerها تصمیم می‌گیرد.

Suppose a shop page needs two values from an order. “Send a request” is too vague: we need to say what we want and what information selects the result. HTTP expresses that intent as a transferable message; the server interprets its method, target and headers.

یک درخواست HTTP/1.1 ساده · نمونهٔ نمایشی
GET /api/orders/742?includeItems=true HTTP/1.1
Host: localhost:5080
Accept: application/json
User-Agent: curl/8.x

این شکل متنی برای فهمیدن پیام HTTP/1.1 است؛ همهٔ نسخه‌های HTTP روی سیم دقیقاً به همین شکل متن خط‌به‌خط نیستند. خط اول method، request target و نسخهٔ پروتکل را دارد. خط‌های بعدی header هستند. این GET نمونه body ندارد؛ پایان headerها با یک خط خالی مشخص می‌شود. پاسخِ سرور پیام جداگانه‌ای است، نه ادامهٔ همین خط اول.

This text form helps us understand an HTTP/1.1 message; not every HTTP version is transmitted as line-by-line text. The first line contains the method, request target and protocol version. Following lines are headers. This GET has no body; a blank line ends the header section. The server response is a separate message, not a continuation of the request line.

HTTP را از همین‌جا به ASP.NET Core وصل می‌کنیم: سرور وب پیام را دریافت می‌کند؛ بعدتر می‌بینیم Kestrel و pipeline چطور آن را به endpoint می‌رسانند. فعلاً route نداریم و frameworkی را برای جادویی‌کردن درخواست صدا نمی‌زنیم؛ فقط اجزای قرارداد را می‌خوانیم.

This is where HTTP will connect to ASP.NET Core: a web server receives the message; later we will follow Kestrel and the pipeline as they carry it to an endpoint. We have no route yet and will not ask a framework to make the request feel magical. For now, we read the contract.

مقصد را از روی URL پیدا کنRead the target from the URL

در URL زیر، قبل از اینکه دربارهٔ controller فکر کنیم، بخش‌ها را جدا کنیم:

query string بخشی از URL است؛ header نیست و body هم نیست. مقدارهایش متن‌اند: اگر `includeStock=true` بفرستی، برنامه یا framework بعداً باید آن متن را به نوع مناسب تبدیل کند و ورودی بد را مدیریت کند. وجود `?` و `&` قالب مقصد را می‌سازد؛ این علامت‌ها به‌تنهایی تضمین نمی‌کنند که برنامه پارامتر را می‌فهمد.

A query string is part of the URL—not a header and not a body. Its values are text: if you send `includeStock=true`, the application or framework later has to convert that text and handle invalid input. `?` and `&` form the target; they do not guarantee that the application understands a parameter.

path هم با نام فایل روی دیسک یکی نیست. `/api/products/42` یک شناسهٔ منبع در قرارداد HTTP است؛ اینکه ASP.NET Core آن را به کدام handler وصل کند، کار routing است که در فصل ۱۳ می‌آید. این جداسازی جلوی یک حدس رایج را می‌گیرد: هر URL لزوماً فایل یا پوشهٔ واقعی نیست.

A path is not necessarily a file-system path. `/api/products/42` identifies a resource in the HTTP contract; ASP.NET Core routing will decide which handler receives it in Chapter 13. A URL does not imply a real file or directory.

method قصد را می‌گوید؛ header زمینه می‌دهدThe method carries intent; headers add context

دو درخواست می‌توانند به path یکسان بروند، ولی قصدشان یکی نباشد. method را جدا از URL بخوان. اینکه GET و POST و PUT و PATCH و DELETE دقیقاً چه semantics دارند و retry چه خطری دارد، فصل ۳ باز می‌کند؛ فعلاً همین را نگه داریم که method بخشی از قرارداد است، نه یک اسم دلخواه برای endpoint.

Two requests can target the same path and still express different intent. Read the method separately from the URL. Chapter 3 will examine the semantics of GET, POST, PUT, PATCH, DELETE and the risks of retrying; for now, remember that the method is part of the contract, not an arbitrary endpoint label.

headerها اطلاعاتی دربارهٔ درخواست می‌دهند. `Accept` می‌گوید client چه representationهایی را می‌تواند بپذیرد؛ `User-Agent` دربارهٔ client است. وقتی خودمان JSON می‌فرستیم، `Content-Type` قالب همان محتوای ارسالی را اعلام می‌کند. این سه را یکی نکن: `Accept` دربارهٔ چیزی است که می‌خواهی دریافت کنی؛ `Content-Type` دربارهٔ چیزی است که فرستاده‌ای. فصل‌های ۴ و ۵ مثال‌های دقیق‌تری دارند.

Headers add information about a request. `Accept` describes representations the client can accept; `User-Agent` describes the client. When we send JSON, `Content-Type` identifies the format of that request content. Do not collapse these: `Accept` concerns what you want back; `Content-Type` concerns what you sent. Chapters 4 and 5 will go deeper.

HTTP/1.1 · درخواست دارای content
POST /api/orders HTTP/1.1
Host: localhost:5080
Accept: application/json
Content-Type: application/json

{"productId":42,"quantity":2}

body بعد از جداکنندهٔ headerها می‌آید و در این مثال JSON است. header `Content-Type` کمک می‌کند گیرنده بداند بدنه را چطور تفسیر کند؛ اما اعتبارسنجی نمی‌کند که `quantity` مثبت یا موجودی کافی است. قالب پیام با اعتبار داده یکی نیست.

The body follows the header separator and is JSON here. `Content-Type` helps the receiver interpret it; it does not validate that `quantity` is positive or stock is available. Message format and data validity are separate concerns.

یک جمله برای جلوگیری از سردرگمیOne sentence to prevent confusion

method می‌گوید چه عملی می‌خواهی؛ path می‌گوید روی کدام منبع؛ query و headerها زمینه می‌دهند؛ body محتوایی است که با semantics همان method فرستاده می‌شود.

The method says what action is intended; the path identifies the resource; query and headers add context; the body carries content interpreted according to that method's semantics.

با curl یک درخواست قابل‌مشاهده بفرستSend an inspectable request with curl

تا اینجا پیام را خواندیم؛ حالا یک request واقعی بفرستیم و headerهای پاسخ را هم ببینیم. `curl` یک client خط فرمان است. در این آزمایش GET عمومی و بدون تغییر وضعیت می‌فرستیم؛ پاسخ واقعی ممکن است با زمان، مسیر شبکه یا میزبان فرق کند.

We have read a message; now send a real request and display the response headers too. `curl` is a command-line client. This experiment sends a public, non-mutating GET; the actual response may vary by time, network path or server.

terminal · GET و header پاسخ
curl -i https://example.com/

در خروجی دنبال خط وضعیت مثل `HTTP/2 200` یا `HTTP/1.1 200 OK` و headerهایی مثل `content-type` بگرد؛ نسخه و headerهای دقیق را از قبل تضمین نمی‌کنیم. گزینهٔ `-i` headerهای پاسخ را کنار body نشان می‌دهد. اگر DNS یا شبکه در دسترس نباشد، شکست curl هنوز چیزی دربارهٔ handler محلی تو ثابت نمی‌کند.

Look for a status line such as `HTTP/2 200` or `HTTP/1.1 200 OK`, and response fields such as `content-type`; we do not promise the exact version or headers. `-i` displays response headers with the body. If DNS or the network is unavailable, curl's failure says nothing about a local handler.

حالا verbose را هم اضافه کن تا جزئیات ارتباط client را ببینی. خروجی verbose را با headerهای پاسخ اشتباه نگیر؛ این‌ها لزوماً همهٔ یک نوع شاهد نیستند.

Now add verbose mode to inspect client-side connection details. Do not mistake verbose diagnostics for response headers; they are not all the same kind of evidence.

terminal · تشخیص client
curl -v --http1.1 https://example.com/

`-v` جزئیات را روی stderr می‌نویسد؛ خطوط فرستاده‌شده را با `>` و headerهای دریافت‌شده را با `<` می‌بینی. `--http1.1` از curl می‌خواهد HTTP/1.1 را به‌کار ببرد، اما TLS و گواهی همچنان متعلق به ارتباط HTTPS هستند. اگر گزینه را حذف کنی، curl ممکن است نسخهٔ دیگری را با توجه به build و مذاکره انتخاب کند. برای شکل سادهٔ خط‌به‌خط HTTP/1.1 همین دستور مفید است؛ نه اینکه HTTP/2/3 هم روی سیم همین متن باشند.

`-v` writes diagnostics to stderr; sent lines are marked with `>` and received fields with `<`. `--http1.1` asks curl to use HTTP/1.1, while TLS and certificate handling still belong to the HTTPS connection. Without the option, curl may negotiate another version depending on its build and the peer. This is useful for inspecting HTTP/1.1 text, not evidence that HTTP/2 or HTTP/3 use the same wire format.

curl موفق شد؛ پس برنامه سالم است؟ نه هنوز.curl succeeded; is the application healthy? Not yet.

این درخواست فقط می‌گوید از این ماشین، این client توانسته از مسیر انتخاب‌شده به این میزبان پاسخ بگیرد. هنوز route داخلی، مجوز کاربر، رفتار دیتابیس، یا اینکه response همان چیزی است که Shop API باید بدهد ثابت نشده است. برای هر ادعا، درخواست و شاهد متناسب خودش را لازم داریم.

This request shows that this client on this machine received a response from this host over the selected path. It does not prove application routing, user authorization, database behavior, or that the response matches the Shop API contract. Each claim needs its own request and evidence.

استاندارد HTTP پیام را request یا response می‌داند و برای هرکدام control data، header و در صورت نیاز content تعریف می‌کند. این مدل بین نسخه‌ها مشترک است، هرچند شکل انتقال HTTP/1.1 با HTTP/2 و HTTP/3 یکی نیست. منبع دقیق semantics را می‌توانی در RFC 9110 بخوانی؛ این فصل قرار نیست استاندارد را خط‌به‌خط حفظ کند.

HTTP defines a message as a request or response, each with control data, headers and optional content. Those semantics are shared across versions even though HTTP/1.1, HTTP/2 and HTTP/3 differ on the wire. The primary reference is RFC 9110; this course does not ask you to memorize the standard line by line.

یک probe کوچک، نه API فروشگاهA small probe, not the shop API

برای اینکه query و headerی را که خودمان ساخته‌ایم ببینیم، یک برنامهٔ محلی موقت می‌سازیم. این برنامه فقط request را بازتاب می‌دهد؛ سفارش ذخیره نمی‌کند، احراز هویت ندارد و قرارداد محصول نیست. نقش آن در این فصل مثل چراغ‌قوه است، نه شروع پیاده‌سازی کل فروشگاه.

To inspect a query and header we control, we will create a temporary local program. It only reflects request details; it does not persist orders, authenticate users or define the product contract. It is a flashlight for this chapter, not the start of the complete shop implementation.

terminal · نیازمند .NET 10 SDK
dotnet new web --framework net10.0 --name ShopWireLab
cd ShopWireLab

پروژه را بساز و محتوای `Program.cs` را با کد زیر جایگزین کن. endpoint از `HttpRequest` داده می‌خواند تا تفاوت path، query، header و body را با چشم ببینی. هنوز دربارهٔ middleware و routing توضیح کامل نمی‌دهیم؛ فقط از مسیر آمادهٔ framework برای آزمایش پیام استفاده می‌کنیم.

Create the project and replace `Program.cs` with the code below. The endpoint reads from `HttpRequest` so you can observe path, query, headers and body separately. We are not teaching middleware or routing yet; we are using the framework's request object as a probe.

Program.cs · probe محلی
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapPost("/probe/orders", async (HttpRequest request) =>
{
    using var reader = new StreamReader(request.Body);
    var body = await reader.ReadToEndAsync();

    return Results.Json(new
    {
        method = request.Method,
        path = request.Path.Value,
        query = request.QueryString.Value,
        accept = request.Headers["Accept"].ToString(),
        contentType = request.ContentType,
        body
    });
});

app.Run();

این endpoint فقط POST را می‌پذیرد. از ریشهٔ پروژه، در یک ترمینال دیگر برنامه را روی loopback اجرا کن؛ آدرس `127.0.0.1` باعث می‌شود این probe برای دستگاه‌های دیگر شبکه منتشر نشود:

This endpoint accepts only POST. From the project directory, start it on loopback in one terminal; `127.0.0.1` keeps this probe from being exposed to other devices on the network:

PowerShell
$env:ASPNETCORE_URLS = "http://127.0.0.1:5080"
dotnet run --no-launch-profile

curl -i -X POST "http://127.0.0.1:5080/probe/orders?source=lab" -H "Accept: application/json" -H "Content-Type: application/json" --data '{"productId":42,"quantity":2}'

پاسخ نمونه چیزی شبیه این است؛ spacing و headerهای اضافی ممکن است فرق کنند:

The response should resemble this; whitespace and extra headers can differ:

این خروجی نشان می‌دهد request به endpoint رسیده و هر قطعه جدا قابل خواندن بوده. اما JSON داخل `body` اینجا هنوز یک رشته است؛ probe آن را به order تبدیل یا اعتبارسنجی نکرد. در فصل‌های ۲۲ تا ۲۵ می‌بینیم framework چطور ورودی را bind و validate می‌کند، و وقتی Shop API را ساختیم پاسخ دیگر صرفاً بازتاب متن نخواهد بود.

This output shows the request reached the endpoint and each part can be read separately. The JSON inside `body` is still a string; the probe did not bind or validate an order. Chapters 22–25 will cover binding and validation, and the eventual Shop API will do more than echo text.

اگر پاسخ نگرفتی، حدس نزن. اول ببین `dotnet run` چه URLی را اعلام کرده، آیا همان process هنوز در حال اجراست و curl دقیقاً به همان port می‌رود یا نه. اگر `Connection refused` دیدی، درخواست هنوز به endpoint نرسیده؛ پس body و JSON علت اولین شکست نیستند.

If no response arrives, do not guess. Check the URL printed by `dotnet run`, whether the process is still running, and whether curl targets the same port. A `Connection refused` means the request did not reach the endpoint, so JSON is not the first failure boundary.

تمرین‌ها: request را بخوان، حدس را حذف کنExercises: read the request, remove the guesswork

هر تمرین باید به یک درخواست قابل اجرا، یک تغییر در probe یا یک شاهد از curl برسد. برای تمرین‌های محلی، برنامهٔ probe بالا را اجرا کن؛ برای آزمایش‌های عمومی فقط GET بفرست. خروجی نسخهٔ خودت را با نمونه مقایسه کن، نه اینکه تفاوت headerهای متغیر را باگ فرض کنی.

Each exercise should produce a runnable request, a probe change or evidence from curl. Use the local probe for local experiments and send only GET requests to public hosts. Compare your output with the representative sample; do not treat variable headers as bugs.

۱) خط درخواست را تجزیه کن1) Parse the request line

از درخواست نمونهٔ فصل، method، path به‌همراه query و نسخه را جدا بنویس. بعد یک POST محلی با `productId=42` در query بساز و با `curl -i` بفرست. query را از body جدا گزارش کن.

From the sample request, separate the method, path with query, and version. Send a local POST with `productId=42` in the query using `curl -i`. Report the query separately from the body.

پاسخ و دلیلSolution and reasoning

در پیام خام، method برابر GET، target برابر `/api/orders/742?includeItems=true` و نسخه HTTP/1.1 است. برای درخواست قابل‌اجرای probe از این استفاده کن: `curl -i -X POST "http://127.0.0.1:5080/probe/orders?productId=42" -H "Content-Type: application/json" --data '{}'`. خروجی باید POST و query جدا را نشان دهد؛ این probe وجود محصول را بررسی نمی‌کند.

The raw message uses GET, target `/api/orders/742?includeItems=true`, and HTTP/1.1. For a runnable probe request, use `curl -i -X POST "http://127.0.0.1:5080/probe/orders?productId=42" -H "Content-Type: application/json" --data '{}'`. The output should show POST and the query separately; the probe does not check whether the product exists.

۲) path را از query جدا کن2) Separate path from query

در `/api/products/42?currency=IRR&includeStock=true` دو نسخه بساز: یکی شناسه را در path عوض کند و یکی فقط query را. برای هر درخواست یادداشت کن کدام بخش منبع را مشخص می‌کند و کدام بخش نمایش را تغییر می‌دهد.

Create two variants of `/api/products/42?currency=IRR&includeStock=true`: one changes the path ID and one changes only the query. Record which part identifies the resource and which shapes its representation.

یک پاسخ ممکنOne possible answer

`/42` را به `/43` تغییر بده تا منبع عوض شود؛ `currency=IRR` را به `currency=USD` تغییر بده تا ورودی نمایشی عوض شود. این قرارداد API طراحی‌شده را ثابت نمی‌کند؛ فقط اجزای URL را از هم جدا می‌کند.

Change `/42` to `/43` to target a different resource; change `currency=IRR` to `currency=USD` to vary a representation input. This does not establish an API design rule; it distinguishes URL components.

۳) GET را با curl بفرست و status را ثبت کن3) Send a GET with curl and record the status

`curl -i https://example.com/` را اجرا کن. فقط خط status و `content-type` را ثبت کن؛ آیا موفقیت این درخواست پاسخ Shop API را ثابت می‌کند؟

Run `curl -i https://example.com/`. Record only the status line and `content-type`; does its success prove the Shop API response?

پاسخ و دلیلSolution and reasoning

status و قالب پاسخ متعلق به میزبان عمومی هستند و ممکن است با زمان تغییر کنند. این فقط مسیر client تا همان میزبان را می‌سنجد؛ برای API خودت باید URL محلی و قرارداد مورد انتظار را دوباره آزمایش کنی.

The status and representation belong to the public host and can vary over time. This checks only the client-to-host path; test your own local URL and expected contract separately.

۴) دو header را جابه‌جا نکن4) Do not swap the two headers

در درخواست POST probe، یک بار `Accept: application/json` و یک بار `Content-Type: application/json` را حذف کن. کد probe چه مقدارهایی گزارش می‌کند؟ حذف هر header لزوماً یعنی server درخواست را رد کند؟

For a POST to the probe, remove `Accept: application/json` once and `Content-Type: application/json` once. What does the probe report? Does removing either header necessarily mean the server rejects the request?

پاسخ و دلیلSolution and reasoning

header حذف‌شده معمولاً به رشتهٔ خالی یا مقدار null/خالی در probe تبدیل می‌شود. probe ما فقط آن را بازتاب می‌دهد و اعتبارسنجی ندارد؛ پس نتیجه را به رفتار همهٔ serverها تعمیم نده. `Accept` ترجیح پاسخ است و `Content-Type` نوع محتوای ارسالی.

A missing field is typically reflected as an empty or null value. Our probe merely echoes it and performs no validation, so do not generalize to every server. `Accept` expresses response preference; `Content-Type` describes sent content.

۵) body را از query بیرون بکش5) Move data from the query into the body

همان `productId` و `quantity` را یک بار در query و یک بار در JSON body بفرست. در خروجی probe نشان بده هر نسخه کجا دیده می‌شود و چرا هنوز هیچ‌کدام order معتبر محسوب نمی‌شوند.

Send the same `productId` and `quantity` once in the query and once in a JSON body. Show where each appears in the probe and why neither is yet a valid order.

پاسخ و دلیلSolution and reasoning
درخواست نمونه
curl -i -X POST "http://127.0.0.1:5080/probe/orders?productId=42&quantity=2" -H "Content-Type: application/json" --data '{"productId":42,"quantity":2}'

خروجی query را در `query` و بدنه را در `body` به‌صورت متن می‌بیند. probe ما schema، موجودی یا قیمت را بررسی نمی‌کند؛ فقط انتقال داده را نشان می‌دهد.

The probe shows query in `query` and the body as text in `body`. It checks no schema, stock or price; it only demonstrates transmission.

۶) خط خالی را در پیام raw پیدا کن6) Find the blank line in a raw message

در نمونهٔ POST، خطی را مشخص کن که headerها را از body جدا می‌کند. در فایل `.http` خودت یک خط خالی را حذف کن؛ client چطور پیام را تفسیر می‌کند؟ نتیجه را از ابزار خودت ثبت کن و تفاوت clientها را بپذیر.

Identify the line separating headers from content in the POST example. Remove the blank line in your `.http` file; how does your client interpret it? Record the behavior and note that clients may differ.

پاسخ و دلیلSolution and reasoning

خط خالی مرز بخش header و محتوای پیام است. بعضی editorها request را ناقص می‌دانند یا body را درست جدا نمی‌کنند؛ این رفتار ابزار است. فایل را به شکل استاندارد برگردان و request ثبت‌شده را با curl مقایسه کن.

The blank line separates headers from message content. An editor may flag the request or fail to separate the body; that is client behavior. Restore the standard form and compare the request with curl.

۷) مقصد curl را عمداً خراب کن7) Deliberately break the curl target

در URL probe عدد port را از 5080 به 5081 تغییر بده. پیام خطا را ثبت کن. آیا درخواست به endpoint رسید؟ اول کدام شاهد را بررسی می‌کنی؟

Change the probe port from 5080 to 5081. Record the error. Did the request reach the endpoint, and what evidence should you check first?

پاسخ و دلیلSolution and reasoning

اگر listenerی روی 5081 نیست، معمولاً `Connection refused` می‌بینی؛ endpoint چیزی دریافت نکرده. URL چاپ‌شده توسط سرور و port واقعی را بررسی کن، بعد همان درخواست را روی port درست تکرار کن. body را هنوز عیب‌یابی نکن.

With no listener on 5081, curl commonly reports `Connection refused`; the endpoint received nothing. Check the server's actual URL and port, then repeat the same request. Do not debug the body yet.

۸) path نادرست را از port نادرست تشخیص بده8) Distinguish a wrong path from a wrong port

به port درست وصل شو ولی به `/probe/items` درخواست بده. response را با حالتی که port اشتباه است مقایسه کن. کدام شکست بعد از برقراری اتصال رخ می‌دهد؟

Use the correct port but request `/probe/items`. Compare that response with a wrong-port failure. Which failure occurs after a connection is established?

پاسخ و دلیلSolution and reasoning

درخواست به پورت درست ممکن است از server پاسخ 404 بگیرد؛ این یعنی اتصال برقرار شده ولی endpoint مطابق پیدا نشده. port اشتباه پیش از HTTP و معمولاً در اتصال شکست می‌خورد. status دقیق probe یا middleware ممکن است فرق کند؛ مرز شکست مهم است.

The correct port may return a server-side 404, meaning the connection succeeded but no matching endpoint was found. A wrong port fails before HTTP, at connection setup. The exact status can vary; the failure boundary is the evidence.

۹) مقدار query خراب را ببین9) Observe a malformed query value

به probe مقدار `quantity=two` بده. آیا probe خطای تبدیل می‌دهد؟ بعد توضیح بده وقتی مقدارها فقط از `Request.QueryString` بازتاب می‌شوند چه چیزی هنوز انجام نشده است.

Send `quantity=two` to the probe. Does it report a conversion error? Explain what has not happened when values are only echoed from `Request.QueryString`.

پاسخ و دلیلSolution and reasoning

نه؛ probe کل query را رشته نگه می‌دارد. تبدیل به integer و validation اصلاً انجام نشده. بعدتر model binding این مرز را شفاف می‌کند، اما validation دامنه مثل مثبت‌بودن quantity همچنان تصمیم جداگانه می‌خواهد.

No; the probe keeps the whole query as a string. Integer conversion and validation have not run. Later model binding will expose conversion behavior, while a domain rule such as positive quantity still needs separate validation.

۱۰) دو مقدار هم‌نام در query بفرست10) Send a repeated query key

درخواست `?tag=book&tag=gift` بساز. curl یا HTTP file را اجرا کن و شکل خام query را ثبت کن. چرا نباید فرض کنی هر کلاینت یا handler فقط یک مقدار می‌بیند؟

Send `?tag=book&tag=gift`. Run it with curl or an HTTP file and record the raw query. Why should you not assume every client or handler sees only one value?

پاسخ و دلیلSolution and reasoning

query خام شامل هر دو occurrence است؛ بعضی APIها چندمقداری می‌خوانند و بعضی binderها ممکن است policy انتخابی داشته باشند. تا وقتی binding را یاد نگرفته‌ای، ادعای تبدیل نکن؛ در probe رشتهٔ خام را مقایسه کن.

The raw target contains both occurrences. APIs can expose multiple values, while a binder may apply its own behavior. Until we study binding, do not assume conversion; compare the raw query in the probe.

۱۱) کاراکترهای URL را encode کن11) Encode URL characters

یک مقدار جست‌وجوی شامل فاصله و `&` را با `curl -v --get --data-urlencode "q=کیبورد & ماوس" https://example.com/` بفرست. در خروجی verbose request target را ثبت کن. چرا چسباندن متن خام به URL خطر تفسیر اشتباه دارد؟

Send a search value containing a space and `&` with `curl -v --get --data-urlencode "q=کیبورد & ماوس" https://example.com/`. Record the request target from verbose output. Why can raw text concatenated into a URL be misinterpreted?

پاسخ و دلیلSolution and reasoning

با `--get`، curl دادهٔ encodeشده را به query می‌برد و method همچنان GET است. `&` داخل مقدار باید encode شود تا پارامتر تازه‌ای نسازد؛ به شکل دقیق `%XX` وابسته نشو و معنای request target را بخوان. این آزمایش encoding سمت client را نشان می‌دهد، نه تفسیر server مقصد را.

With `--get`, curl appends encoded data to the query and still sends GET. The `&` inside the value must be encoded so it does not create another parameter. Do not depend on one exact `%XX` form; read the request target. This proves client-side encoding, not how the remote server interprets it.

۱۲) verbose را به‌عنوان مدرک client بخوان12) Read verbose output as client evidence

`curl -v --http1.1 https://example.com/` را اجرا کن. یک خط با `>` و یک خط با `<` پیدا کن. این علامت‌ها دربارهٔ جهت چه می‌گویند و چه چیزی را تضمین نمی‌کنند؟

Run `curl -v --http1.1 https://example.com/`. Find a line beginning with `>` and one with `<`. What direction do they indicate, and what do they not guarantee?

پاسخ و دلیلSolution and reasoning

`>` خط‌های ارسالی client و `<` داده‌های دریافتی را در verbose curl نشان می‌دهد. این خروجی کمک می‌کند client-side exchange را ببینی؛ اما نمی‌گوید برنامهٔ مقصد داده را درست پردازش کرده یا response از handler مورد انتظار آمده.

`>` marks client-sent lines and `<` marks received data in curl's verbose output. It exposes the client-side exchange but does not prove the application processed it correctly or that the expected handler produced the response.

۱۳) header را در probe اضافه کن13) Add a header to the probe

کد probe را تغییر بده تا `X-Request-Source` را هم در JSON برگرداند. با `curl -H "X-Request-Source: exercise"` بفرست و output قبل و بعد را مقایسه کن.

Change the probe to return `X-Request-Source` in its JSON. Send it with `curl -H "X-Request-Source: exercise"` and compare before and after.

پاسخ و دلیلSolution and reasoning
تغییر در پاسخ probe
requestSource = request.Headers["X-Request-Source"].ToString(),

پاسخ باید `exercise` را در property جدید نشان دهد. header را با query قاطی نکن: در URL نیست و از collection جداگانهٔ headerها خوانده می‌شود. این آزمایش فقط خواندن header را ثابت می‌کند، نه قابل‌اعتمادبودن محتوایش.

The response should contain `exercise` in the new property. A header is not a query parameter; it is read from a separate collection. This proves it can be read, not that its value is trustworthy.

۱۴) probe را فقط روی loopback نگه دار14) Keep the probe on loopback

آدرس bind برنامه را از `127.0.0.1` به `0.0.0.0` تغییر بده، فقط مفهوم و خروجی listen را مقایسه کن؛ آن را روی شبکهٔ عمومی منتشر نکن. چه تغییری در سطح دسترسی شبکه‌ای ایجاد شد؟

Change the bind address from `127.0.0.1` to `0.0.0.0` and compare the listening address, but do not expose it publicly. What changed in network reachability?

پاسخ و دلیلSolution and reasoning

loopback فقط اتصال محلی همان میزبان را می‌پذیرد؛ `0.0.0.0` یعنی روی interfaceهای IPv4 محلی گوش‌دادن. این کار به‌تنهایی firewall را باز نمی‌کند، اما سطحی که ممکن است به آن دسترسی بگیرد بزرگ‌تر می‌شود؛ برای probe آموزشی از loopback استفاده کن.

Loopback accepts connections from the same host; `0.0.0.0` listens on local IPv4 interfaces. It does not itself open a firewall, but it broadens potential reachability. Keep this teaching probe on loopback.

۱۵) method را با endpoint اشتباه نگیر15) Do not confuse the method with the endpoint

به `/probe/orders` با GET درخواست بفرست، درحالی‌که برنامه فقط `MapPost` دارد. status و response را ثبت کن. آیا این به معنی خراب‌بودن body JSON است؟

Send GET to `/probe/orders` although the app maps only `MapPost`. Record the status and response. Does this mean the JSON body is broken?

پاسخ و دلیلSolution and reasoning

GET handler تعریف نشده و معمولاً 405 یا پاسخ routing مشابه می‌گیری؛ status دقیق به پیکربندی بستگی دارد. درخواست به منطق خواندن body ما نرسیده، پس body هنوز بررسی نشده است. در فصل‌های ۱۲–۱۵ تفکیک method و routing را دقیق می‌کنیم.

No GET handler is mapped, so the framework commonly returns 405 or a related routing response; exact behavior depends on configuration. The request did not reach our body-reading logic, so the body has not been tested. Chapters 12–15 will examine methods and routing.

۱۶) Content-Type نامعتبر را مشاهده کن16) Observe a misleading Content-Type

به probe بدنهٔ JSON بفرست ولی header را `Content-Type: text/plain` بگذار. آیا probe هنوز آن را می‌خواند؟ این نتیجه دربارهٔ binder آینده چه چیزی را ثابت نمی‌کند؟

Send a JSON-looking body to the probe but label it `Content-Type: text/plain`. Does the probe still read it? What does that prove—or not prove—about a future binder?

پاسخ و دلیلSolution and reasoning

بله؛ probe جریان بایت‌ها را مستقیم به رشته می‌خواند و Content-Type را فقط گزارش می‌کند. این ثابت نمی‌کند JSON input formatter هم با این media type آن را deserialize می‌کند؛ آن رفتار به framework و قرارداد endpoint مربوط است.

Yes; the probe reads bytes as text and merely reports Content-Type. That does not prove a JSON input formatter will deserialize the payload with this media type; that depends on framework behavior and endpoint contract.

۱۷) Connection refused را قبل از JSON عیب‌یابی کن17) Diagnose connection refusal before JSON

سرور را با Ctrl+C متوقف کن و همان curl را تکرار کن. خروجی را ثبت کن و سه شاهد اتصال را نام ببر که پیش از دست‌کاری بدنه بررسی می‌کنی.

Stop the server with Ctrl+C and repeat the same curl request. Record the failure and name three connection facts to check before changing the body.

پاسخ و دلیلSolution and reasoning

معمولاً connection refused می‌آید چون listenerی نیست. process سرور، bind address و port URL را بررسی کن. این خطا قبل از route و JSON رخ می‌دهد؛ اصلاح body نمی‌تواند listener خاموش را تعمیر کند.

Curl commonly reports connection refusal because no listener is available. Check the server process, bind address and URL port. This fails before routing or JSON parsing; changing the body cannot repair a stopped listener.

۱۸) یک گزارش request قابل‌بررسی تحویل بده18) Hand off an inspectable request report

برای probe یک درخواست بساز که source در query، نوع پاسخ در Accept، قالب بدنه در Content-Type و یک quantity در JSON داشته باشد. خود request، پاسخ و چهار مشاهدهٔ تفکیک‌شده را ثبت کن؛ کدام قسمت هنوز معنای business را validate نمی‌کند؟

Create a probe request with source in the query, response preference in Accept, body format in Content-Type and a quantity in JSON. Record the request, response and four distinct observations; which part still does not validate business meaning?

یک گزارش ممکنOne possible report
request · نمونه
curl -i -X POST "http://127.0.0.1:5080/probe/orders?source=exercise" -H "Accept: application/json" -H "Content-Type: application/json" --data '{"quantity":-1}'

گزارش باید method=POST، query شامل source، Accept و Content-Type جدا و body شامل quantity منفی را نشان دهد. پاسخ 200 probe می‌گوید پیام بازتاب داده شد؛ منفی‌بودن quantity هنوز رد نشده. پس شواهد HTTP را با اعتبارسنجی دامنه یکی نکن.

The report should show method POST, a source query, separate Accept and Content-Type fields, and a negative quantity in the body. A 200 from the probe means the message was echoed; the negative value was not rejected. HTTP evidence is not domain validation.

آزمایشگاه: یک درخواست فروشگاه را از روی شواهد بازسازی کنLab: reconstruct a shop request from evidence

همکارت می‌گوید «سفارش به API نرسیده»، اما اسکرین‌شاتش فقط JSON body را نشان می‌دهد. هدف تو این نیست که حدس بزنی کدام framework option را عوض کند؛ باید request کامل و مرز شکست را ثبت کنی.

A teammate says “the order never reached the API,” but the screenshot shows only a JSON body. Your job is not to guess a framework option; capture the complete request and identify the failure boundary.

  1. probe محلی را طبق این فصل روی loopback اجرا کن و اول یک POST سالم بفرست.
  2. Run the local loopback probe and send one successful POST.
  3. در درخواست دوم path را اشتباه کن؛ در درخواست سوم port را اشتباه. خروجی‌ها را کنار هم بگذار و بگو کدام شکست اتصال و کدام شکست بعد از اتصال است.
  4. In a second request mistype the path; in a third, mistype the port. Compare the outputs and classify which failed at connection and which after connection.
  5. یک HTTP file ذخیره کن که method، URL، Accept، Content-Type و body را نشان دهد؛ همان درخواست را با curl هم بفرست.
  6. Save an HTTP file containing method, URL, Accept, Content-Type and body, then send the same request with curl.
  7. گزارش کوتاهی تحویل بده: درخواست دقیق، پاسخ هر حالت، اولین لایه‌ای که شکست، و چیزی که آزمایش هنوز ثابت نکرده—مثلاً اعتبار order یا دسترسی کاربر.
  8. Hand off a short report: exact request, response for each case, first failing layer, and one claim the experiment did not prove—such as order validity or user authorization.
راهنمای بررسیReview hints

در درخواست سالم، probe باید اجزای جدا را بازتاب دهد. port خراب معمولاً پیش از HTTP شکست می‌خورد؛ path خراب وقتی اتصال برقرار است از server پاسخ می‌گیرد. پاسخ 200 probe تأیید نمی‌کند سفارش معتبر یا ذخیره شده، چون آزمایشگاه اصلاً دیتابیس ندارد. در پایان با Ctrl+C فقط process آزمایش را متوقف کن؛ پوشهٔ source را اگر برای فصل بعد لازم داری نگه دار.

The successful probe should echo distinct request parts. A bad port usually fails before HTTP; a bad path receives a server response after connection. A 200 from the probe does not validate or persist an order—the lab has no database. Stop only the test process with Ctrl+C; keep the source folder if you want it for later experiments.

این فصل عمداً وارد جزئیات پیاده‌سازی ASP.NET Core نمی‌شود. برای semantics خود HTTP به RFC 9110 رجوع کن؛ شکل پیام HTTP/1.1 در RFC 9112 آمده است. راهنمای `curl` رفتار گزینه‌های خط فرمان را توضیح می‌دهد. نمونهٔ محلی با .NET 10 نوشته شده؛ مستند رسمی Minimal API برای همین نسخه را کنار کد نگه دار، چون قالب‌ها و APIها ممکن است در نسخه‌های بعد تغییر کنند.

This chapter deliberately avoids deeper ASP.NET Core implementation details. RFC 9110 defines HTTP semantics; RFC 9112 describes HTTP/1.1 message syntax. The curl manual documents command-line options. The local probe targets .NET 10; keep the versioned Minimal API documentation beside the code because templates and APIs can change across releases.

اگر در Windows PowerShell دستورهای `curl` گیج‌کننده شدند، یادت باشد `curl` ممکن است alias باشد و نقل‌قول JSON هنگام فرستادن آرگومان به `curl.exe` هم بسته به نسخه فرق کند. برای POST محلی، این جایگزین PowerShell را اجرا کن؛ JSON را parse می‌کند و نتیجهٔ probe را نشان می‌دهد.

If `curl` behaves unexpectedly in Windows PowerShell, remember it may be an alias, and JSON quoting passed to `curl.exe` can vary by PowerShell version. For the local POST, this PowerShell alternative parses and displays the probe response.

PowerShell · درخواست POST محلی
$payload = '{"productId":42,"quantity":2}'
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:5080/probe/orders?source=lab" -Headers @{ Accept = "application/json" } -ContentType "application/json" -Body $payload | ConvertTo-Json -Compress
