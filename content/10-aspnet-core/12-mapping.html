نگاشت شیء؛ AutoMapper، Mapperly یا کد دستی؟

Object mapping: AutoMapper, Mapperly, or handwritten code?

API ورودی را به DTO می‌گیرد و مدل دامنه با همان شکل ساخته نمی‌شود؛ خروجی هم نباید همهٔ فیلدهای داخلی را لو بدهد. حالا چند راه برای تبدیل داریم. سؤال این نیست که کدام کتابخانه محبوب‌تر است؛ سؤال این است که کدام تبدیل را می‌توانیم ببینیم، تست کنیم و هنگام تغییر امن نگه داریم.

An API accepts a request DTO that does not match the domain model, and its response must not expose every internal field. Several mapping options exist. The question is not which library is most popular, but which transformation we can inspect, test, and safely evolve.

چرا entity را مستقیم به client ندهیم؟Why not return the entity directly to the client?

مدل دیتابیس شامل internal note، foreign key و وضعیت پردازشی است؛ client فقط id، نام مشتری و total را لازم دارد. اگر entity را مستقیم serialize کنیم، با تغییر schema قرارداد API هم ناخواسته تغییر می‌کند و ممکن است دادهٔ داخلی افشا شود. DTO مرز قرارداد را نگه می‌دارد؛ mapping تبدیل میان دو مدل است، نه مجوزی برای درهم‌ریختن لایه‌ها.

The persistence model contains an internal note, foreign key, and processing state; the client needs only an ID, customer name, and total. Returning the entity directly couples schema changes to the API contract and can expose internal data. A DTO protects the boundary; mapping transforms models but does not justify mixing layers.

نگاشت دستی · Handwritten mapping
public static OrderResponse ToResponse(Order order) => new(
    order.Id,
    order.Customer.DisplayName,
    order.Lines.Sum(line => line.Quantity * line.UnitPrice));

public sealed record OrderResponse(
    Guid Id, string CustomerName, decimal Total);

با کد دستی یک نگاه می‌فهمیم دقیقاً چه چیزی بیرون می‌رود. برای دو DTO ساده شاید همین بهترین انتخاب باشد. وقتی ده‌ها تبدیل تکراری شد، abstraction می‌تواند ارزش داشته باشد؛ اما خطاهای پنهان و نگه‌داری mapping هم هزینه‌اند.

Handwritten code makes the outgoing data obvious. It may be the best choice for a couple of simple DTOs. When dozens of repetitive mappings accumulate, an abstraction may help—but hidden behavior and mapping maintenance are costs too.

سه گزینه، سه trade-offThree options, three trade-offs

روشقوتهزینه/خطرApproach / strength / cost
کد دستیشفاف، ساده برای debugتکرار و فراموش‌شدن propertyExplicit and easy to debug; repetitive and easy to omit fields
AutoMapperقراردادهای convention و profileپیکربندی runtime و مجوز نسخهٔ جاریConvention/profile-based; runtime configuration and current licensing
Mapperlyتولید کد در build و دیدن implementationنیاز به دنبال‌کردن generated code و analyzerBuild-time generated code; inspect generated output and analyzer diagnostics

AutoMapper 15 طبق مستند فعلی license key می‌خواهد؛ قبل از انتخاب برای پروژهٔ تازه، مجوز و شرایط استفاده را از upstream بررسی کن و key را secret نگه دار. نسخه‌های قدیمی‌تر رفتار و شرط دیگری داشته‌اند؛ شمارهٔ نسخه را به توصیهٔ قدیمی تبدیل نکن.

AutoMapper 15 currently requires a license key according to its official guide. Before adopting it in a new project, verify upstream licensing terms and keep the key secret. Older versions differ; do not apply old advice without checking the version.

Mapperly با source generator در build کد mapping تولید می‌کند؛ می‌توانی implementation را در IDE ببینی یا generated files را موقتاً روی دیسک emit کنی. کد تولیدشده جادو نیست و باید build diagnostics و تست خروجی را بخوانی.

Mapperly uses a source generator to emit mapping code at build time; inspect implementations in the IDE or emit generated files temporarily. Generated code is not magic—read build diagnostics and test the output.

AutoMapper: Profile بساز و پیکربندی را verify کنAutoMapper: create a profile and verify configuration

Profile جایی برای تعریف نگاشت‌های مشخص است. تست configuration کمک می‌کند property مقصدی که هیچ source ندارد بی‌صدا null نماند. اما تست معتبر بودن configuration ثابت نمی‌کند محاسبهٔ total یا قرارداد business درست است؛ برای خروجی واقعی test جدا لازم است.

A Profile is where explicit maps live. Configuration validation helps catch destination members without a source before they silently remain unset. But valid configuration does not prove that total calculation or business behavior is correct; test actual output separately.

Profile و تست پیکربندی
public sealed class OrderProfile : Profile
{
    public OrderProfile()
    {
        CreateMap<Order, OrderResponse>()
            .ForMember(d => d.CustomerName,
                o => o.MapFrom(s => s.Customer.DisplayName))
            .ForMember(d => d.Total,
                o => o.MapFrom(s => s.Lines.Sum(
                    line => line.Quantity * line.UnitPrice)));
    }
}

// In a test:
configuration.AssertConfigurationIsValid();

در AutoMapper 15 registration و ساخت configuration با API نسخهٔ فعلی انجام می‌شود و نیاز license را باید در محیط سازمانی بررسی کرد. license key را داخل repository نگذار؛ configuration validation را در CI اجرا کن تا خطا پیش از deploy دیده شود.

With AutoMapper 15, use the current registration/configuration API and verify licensing for your organization. Do not commit the license key; run configuration validation in CI so failures appear before deployment.

ReverseMap را بی‌فکر نزن: نگاشت response به entity الزاماً عملیات update معتبر نیست. client نباید بتواند با reverse map فیلدهایی مثل owner، status یا price را تعیین کند. command ورودی جدا و تغییر دامنه کنترل‌شده بساز.

Do not reverse-map blindly: mapping a response back to an entity is not automatically a valid update. Clients must not set owner, status, or price through a reverse map. Use a separate command and controlled domain operation.

Mapperly: تولید کد، نه کشف خطا در runtimeMapperly: generated code instead of runtime discovery

Mapperly mapper را به شکل class یا interface با [Mapper] و methodهای partial تعریف می‌کند. generator بر اساس typeها implementation تولید می‌کند و analyzer می‌تواند mapping ناقص یا تبدیل خطرناک را هشدار دهد. generated source را در IDE باز کن؛ اگر یک فیلد حساس جا افتاده، فقط با دیدن annotation خیال‌ات راحت نشود.

Mapperly defines a mapper as a class/interface marked with [Mapper] and partial methods. Its generator emits implementations from types, and analyzers can report incomplete or risky mappings. Open the generated source; annotations alone do not prove a sensitive field was handled correctly.

Mapperly · mapper مشخص
[Mapper]
public static partial class OrderMapper
{
    [MapProperty(
        nameof(Order.Customer.DisplayName),
        nameof(OrderResponse.CustomerName))]
    public static partial OrderResponse ToResponse(Order source);
}

نام/نسخهٔ package و API دقیق را با مستند Mapperly و target framework پروژه هماهنگ کن. فایل generated را معمولاً لازم نیست commit کنی؛ اگر برای بازبینی موقت emit کردی، مسیر obj یا پوشهٔ خروجی را با git status کنترل کن.

Match package version and API to the Mapperly docs and target framework. Generated files usually do not need committing; if emitted for review, inspect git status and keep build artifacts out of source control unless the team intentionally tracks them.

وقتی query است، کل entity را اول نکش بالاFor a query, do not load the whole entity graph first

برای صفحهٔ فهرست فقط چند ستون لازم است. اگر همهٔ entity و navigationها را load کنی و بعد map کنی، ممکن است داده و حافظهٔ اضافه مصرف شود. برای projection database-aware مثل AutoMapper ProjectTo یا LINQ Select را بررسی کن؛ SQL تولیدشده را ببین و مطمئن شو provider expression را ترجمه کرده، نه این‌که کل محاسبه client-side شده باشد.

A list page may need only a few columns. Loading every entity and navigation before mapping can fetch excess data. Consider database-aware projection such as AutoMapper ProjectTo or LINQ Select; inspect generated SQL and verify the provider translated the expression rather than moving the work client-side.

projection مستقیم با LINQ
var rows = await db.Orders
    .Where(order => order.CreatedAt >= from)
    .OrderByDescending(order => order.CreatedAt)
    .Select(order => new OrderListItem(
        order.Id,
        order.Customer.DisplayName,
        order.Lines.Sum(line =>
            line.Quantity * line.UnitPrice)))
    .ToListAsync(cancellationToken);

برای اثبات به query log یا SQL capture نگاه کن؛ output DTO به‌تنهایی نمی‌گوید چند ستون یا چند ردیف از DB خوانده شد. projection خوب query را محدود می‌کند، اما منطق پیچیدهٔ business را نباید برای راحتی داخل expression مخفی کرد.

Inspect query logs or captured SQL; the DTO output alone does not reveal how many columns or rows were fetched. Projection narrows queries, but business logic should not be hidden inside expressions merely for convenience.

آزمایشگاه: نگاشت خروجی و command ورودیLab: map an output and keep input commands separate

یک Order با Customer و Lines بساز. سه پیاده‌سازی خروجی بساز: دستی، AutoMapper Profile و Mapperly. برای هرکدام همان fixture و test را اجرا کن؛ سپس تصمیم بگیر کدام را نگه می‌داری. هدف benchmark بی‌معنا نیست؛ شفافیت و رفتار قراردادی را مقایسه کن.

Create an Order with Customer and Lines. Implement output mapping by hand, with an AutoMapper Profile, and with Mapperly. Run the same fixture and tests for each, then choose one. The goal is not a meaningless benchmark; compare clarity and contract behavior.

  1. Response DTO را طوری تعریف کن که internal note، owner id و persistence state در آن نباشند.
  2. Define a response DTO that excludes internal note, owner ID, and persistence state.
  3. total را از lineها حساب کن و برای صفر، چند ردیف و quantity مرزی تست بنویس.
  4. Calculate total from lines and test zero, multiple lines, and boundary quantities.
  5. اگر AutoMapper انتخاب شد، AssertConfigurationIsValid را در test اجرا و مجوز نسخه را مستند کن.
  6. If choosing AutoMapper, run AssertConfigurationIsValid and document the version's license.
  7. اگر Mapperly انتخاب شد، generated implementation را بازبینی و warningهای analyzer را رفع کن.
  8. If choosing Mapperly, inspect generated implementation and resolve analyzer warnings.
  9. update command جدا بساز؛ یک request دستکاری‌شده ثابت کند client فیلد read-only را تغییر نمی‌دهد.
  10. Create a separate update command; prove a tampered request cannot change a read-only field.
  11. برای فهرست DB projection بساز و SQL/ستون‌های انتخاب‌شده را ثبت کن.
  12. Project the database list query and capture selected SQL columns.

ملاک انتخاب: mappingها کم و حساس‌اند؟ دستی بنویس. قراردادها زیاد و conventionدارند؟ کتابخانه ارزش بررسی دارد. query به DB می‌رود؟ projection و SQL را جدا ارزیابی کن.

Choose deliberately: few sensitive maps favor handwritten code; many conventional contracts may justify a library. Database queries require separate projection and SQL evaluation.

۱۸ تمرین کدنویسی و شواهد18 coding and evidence exercises

۱. قرارداد response

از entity سفارش response DTO بساز که سه فیلد مجاز و دو فیلد داخلی غیرمجاز داشته باشد؛ serialization را تست کن.

Map an order entity to a response DTO with three allowed and two forbidden internal fields; test serialization.

راهنما

DTO را صریح تعریف و mapping دستی بنویس. JSON نهایی را assert کن؛ تست compile به‌تنهایی افشای داده را نمی‌سنجد.

Define the DTO explicitly and map by hand. Assert final JSON; compilation alone does not detect data exposure.

۲. mapping ناقص

property جدیدی به مقصد اضافه کن؛ در AutoMapper configuration test را اجرا و failure را رفع کن.

Add a destination property; run the AutoMapper configuration test and fix the failure.

راهنما

AssertConfigurationIsValid اعضای مقصد map‌نشده را نشان می‌دهد؛ بعد رفتار مقدار را نیز در test خروجی assert کن.

AssertConfigurationIsValid identifies unmapped destination members; then assert the member's output behavior too.

۳. policy نام‌گذاری

Name در source را به DisplayName مقصد map کن و test دو مقدار متفاوت بنویس.

Map source Name to destination DisplayName and test two distinct values.

راهنما

برای mapping دستی assignment روشن؛ برای AutoMapper ForMember/MapFrom؛ برای Mapperly MapProperty. خروجی هر سه را مقایسه کن.

Use an explicit assignment, AutoMapper ForMember/MapFrom, or Mapperly MapProperty. Compare outputs.

۴. محاسبهٔ total

total را از quantity و unit price محاسبه و با چند خط سفارش تست کن؛ rounding policy را مشخص کن.

Calculate total from quantity and unit price across lines; test multiple lines and specify rounding policy.

راهنما

یک fixture معلوم بساز و decimal دقیق را assert کن. mapping نباید محاسبهٔ مهم مالی را بی‌تست پشت convention پنهان کند.

Use a known fixture and assert exact decimal output. Do not hide important financial calculations behind untested conventions.

۵. ReverseMap ناامن

response DTO فیلد OwnerId دارد. کد reverse map را با update command مقایسه و تست کن client نتواند مالکیت را تغییر دهد.

The response DTO contains OwnerId. Compare reverse mapping with an update command and prove clients cannot change ownership.

راهنما

ورودی update را جدا و فقط قابل‌ویرایش‌ها را بپذیر. مجوز مالکیت از identity سرور/DB بیاید، نه DTO بازگشتی.

Use a separate update input with only writable fields. Ownership must come from server identity/state, not a round-tripped DTO.

۶. License نسخهٔ AutoMapper

نسخهٔ انتخابی را inspect و policy مجوز را ثبت کن؛ اگر key لازم است از environment secret بخوان، نه فایل Git.

Inspect the selected version and document licensing; if a key is required, load it from a secret environment source, not Git.

راهنما

طبق مستند جاری AutoMapper 15 نیاز license دارد. package version را در lock/restore evidence مشخص کن و key واقعی را وارد خروجی یا log نکن.

Current AutoMapper 15 docs require a license. Record package version from restore/lock evidence and never expose the real key in output or logs.

۷. generated source در Mapperly

mapping بساز و implementation تولیدشده را در IDE پیدا کن؛ یک هشدار را عمداً ایجاد و رفع کن.

Create a map and inspect generated implementation in the IDE; introduce and fix one warning.

راهنما

source generator کد build-time می‌دهد. diagnostics را بخوان و خروجی generated را مبنای debug کن، نه اینکه فرض کنی runtime reflection انجام می‌شود.

The source generator emits build-time code. Read diagnostics and debug generated output rather than assuming runtime reflection.

۸. projection و SQL

فهرست سفارش را با Select به DTO projection کن؛ SQL log را بررسی و ستون‌های اضافه را حذف کن.

Project an order list with Select into a DTO; inspect SQL logs and remove unnecessary columns.

راهنما

DTO خروجی تعداد ستون‌ها را ثابت نمی‌کند. SQL capture یا command logging لازم است و cancellation token را تا query پاس بده.

The DTO does not prove selected columns. Capture SQL or command logs and pass cancellation through to the query.

۹. ReverseMap و flatten

Customer.DisplayName را به CustomerName flatten کن؛ reverse map را فقط در fixture آزمایشی اجرا و ببین چه stateای تغییر می‌کند.

Flatten Customer.DisplayName to CustomerName; run reverse mapping only in a test fixture and inspect changed state.

راهنما

unflattening ممکن است navigation را تغییر دهد. از آن به‌عنوان write API استفاده نکن مگر هر فیلد و invariant صریحاً بررسی شده باشد.

Unflattening may mutate navigation state. Do not use it as a write API unless every field and invariant is explicitly controlled.

۱۰. null navigation

Customer را null کن و mapping response را اجرا کن؛ قرارداد null یا fallback را تعیین و test کن.

Set Customer to null and map the response; define and test the null/fallback contract.

راهنما

استثنا را پنهانی به رشتهٔ خالی تبدیل نکن. nullability، query include/projection و رفتار serializer را هماهنگ کن.

Do not silently turn exceptions into empty strings. Align nullability, query loading/projection, and serializer behavior.

۱۱. map چندتایی

Customer، Lines و Order را به response واحد تبدیل کن؛ child mapها را مستقل تست و سپس composition را verify کن.

Map Customer, Lines, and Order into one response; test child maps independently, then verify composition.

راهنما

برای mappingهای تکرارشونده helper/child map مفید است، اما total و filtering باید خروجی مورد انتظار را داشته باشند.

Reusable child maps help, but total and filtering still need explicit output assertions.

۱۲. enum با مقدارهای متفاوت

enum داخلی و API مقادیر عددی ناسازگار دارند؛ mapping by-name یا conversion صریح بنویس و مورد ناشناخته را تست کن.

Internal and API enums use different numeric values; map by name or explicitly and test unknown values.

راهنما

cast عددی خام می‌تواند status غلط بسازد. برای value ناشناخته تصمیم کنترل‌شده بگیر و آن را در contract test پوشش بده.

A raw numeric cast can produce the wrong status. Define a controlled unknown-value behavior and cover it with a contract test.

۱۳. create در برابر update

دو request DTO و دو مسیر mapping بساز؛ فیلدهایی که فقط هنگام ایجاد معنا دارند در update پذیرفته نشوند.

Create separate request DTOs and mappings; reject fields meaningful only during creation from update input.

راهنما

یک map دوطرفهٔ عمومی معمولاً این تفاوت را گم می‌کند. قرارداد هر operation را جدا نگه دار و assignmentهای مجاز را assert کن.

A generic bidirectional map often erases this distinction. Keep operation contracts separate and assert allowed assignments.

۱۴. generated artifact ناخواسته

generated files را emit کن و git status را ببین؛ آن‌ها را پاک‌سازی هدفمند کن یا ignore مناسب اضافه و نتیجه را ثبت کن.

Emit generated files and inspect git status; clean them deliberately or add an appropriate ignore, then record the result.

راهنما

مسیر پیش‌فرض معمولاً زیر obj است؛ حذف را به همان پوشهٔ build مشخص محدود کن و source دستی را دست نزن.

The default is commonly under obj; scope cleanup to that build output and preserve handwritten source.

۱۵. عمق query

دو روش materialize-then-map و projection را روی fixture یکسان اجرا؛ SQL، تعداد ستون و زمان را ثبت کن.

Run materialize-then-map and projection on the same fixture; capture SQL, columns, and elapsed time.

راهنما

یک اندازه‌گیری واحد حکم قطعی نیست؛ query shape و حجم ثابت نگه دار. نتیجه را به همان سناریو محدود کن.

One measurement is not universal proof; keep query shape and data volume fixed and scope the conclusion to this scenario.

۱۶. benchmark تصمیم mapping

برای ۱۰هزار object، سه پیاده‌سازی را با BenchmarkDotNet یا stopwatch آزمایشی مقایسه کن؛ allocation را هم گزارش کن.

Compare three approaches over 10,000 objects with BenchmarkDotNet or a controlled stopwatch test; report allocations too.

راهنما

warmup، Release و دادهٔ برابر لازم است. اختلاف کوچک را بزرگ‌نمایی نکن و benchmark را جای معیار خوانایی/مجوز نگذار.

Use warmup, Release, and equal input. Do not exaggerate small differences or substitute benchmarks for clarity/licensing decisions.

۱۷. regression برای فیلد حساس

یک فیلد داخلی را به entity اضافه کن؛ test serialization ثابت کند response ناخواسته تغییر نکرده است.

Add an internal entity field; a serialization test must prove the public response did not change unexpectedly.

راهنما

snapshot یا assertion صریح JSON استفاده کن و ممنوع‌بودن فیلد را بررسی کن. DTO عمداً whitelist است، نه انعکاس entity.

Use explicit JSON assertions or a snapshot and verify the field is absent. The DTO is an intentional whitelist, not an entity mirror.

۱۸. review تصمیم

یک PR فرضی برای mapping جدید بازبینی کن: آیا دستی، AutoMapper یا Mapperly مناسب است؟ یک test پیکربندی، یک test داده و یک ملاحظهٔ مجوز/SQL ارائه بده.

Review a mapping PR: should it be handwritten, AutoMapper, or Mapperly? Provide a configuration test, data test, and licensing/SQL consideration.

راهنما

نوع mapping، حساسیت fieldها، projection، نسخه و هزینهٔ نگه‌داری را با evidence بنویس؛ محبوبیت کتابخانه دلیل کافی نیست.

Use evidence about mapping shape, sensitive fields, projection, version, and maintenance cost; popularity alone is not a reason.

جمع‌بندی: تبدیل روشن از قرارداد به قراردادWrap-up: explicit transformation from one contract to another

entity را مستقیم منتشر نکن؛ DTO مرز API است. کد دستی برای تبدیل کم و حساس اغلب شفاف‌ترین راه است؛ AutoMapper با config test و توجه به مجوز نسخه؛ Mapperly با بررسی generated code و analyzer. برای query، projection و SQL را جدا ببین. reverse mapping خودبه‌خود update امن نمی‌سازد. حالا که ورودی validate و به مدل نگاشت شد، قدم بعد persistence واقعی و مرزهای EF Core است.

Do not expose entities directly; DTOs define the API boundary. Handwritten code is often clearest for a few sensitive maps; AutoMapper needs configuration tests and version-license awareness; Mapperly needs generated-code and analyzer review. For queries, inspect projection and SQL. Reverse mapping does not create a safe update. With validated and mapped input, the next step is persistence and EF Core boundaries.
