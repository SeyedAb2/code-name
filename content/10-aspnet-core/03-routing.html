مسیریابی؛ کدام endpoint پاسخ می‌دهد؟

Routing: which endpoint handles the request?

فروشگاه endpoint /products/{id} دارد؛ بعد که /products/search را اضافه می‌کند، یک نفر آن را با id برابر search تفسیر می‌کند. در endpoint routing معمولاً مسیر literal خاص‌تر اولویت بهتری از پارامتر عمومی دارد، اما routeهای مبهم، method اشتباه و constraintهای نامناسب هنوز می‌توانند نتیجهٔ اشتباه بسازند. بیایید خود درخواست را با method و path دنبال کنیم.

The shop has /products/{id}; after adding /products/search, someone thinks it is treated as id=search. In endpoint routing, a specific literal usually outranks a general parameter, but ambiguous routes, wrong methods, and unsuitable constraints can still produce surprising results. Let’s trace the actual method and path.

تیم یک URL ساخته، اما route دیگری جواب دادهThe team built one URL, but another route responded

صفحهٔ جست‌وجوی محصولات باید از /products/search?term=lamp استفاده کند. developer مسیر را اضافه می‌کند، اما پاسخ جزئیات محصول را می‌بیند. قبل از تغییر endpoint، request واقعی را ثبت کن: HTTP method چیست؟ path کدام است؟ query string کدام بخش است؟ Router با path و method endpoint را انتخاب می‌کند؛ query مقدار جداگانه‌ای است.

Product search should use /products/search?term=lamp. A developer adds the route, but sees a product-detail response. Before changing handlers, capture the real request: what is the HTTP method, which part is the path, and which part is the query string? Routing selects endpoints from path and method; query data is separate.

هر endpoint یک واحد اجرایی است که در startup ثبت می‌شود. در Minimal API با MapGet/MapPost و در Controller با route attribute یا convention معرفی می‌شود. Router درخواست را match می‌کند، route valueها را استخراج می‌کند و endpoint مناسب را انتخاب می‌کند. پارامترهای query/body و تبدیل نوع، binding هستند و فصل‌های بعد جداگانه بررسی می‌شوند.

An endpoint is an executable unit configured at startup. Minimal APIs declare it with MapGet/MapPost; controllers use route attributes or conventions. Routing matches the request, extracts route values, and selects an endpoint. Query/body parameter binding and conversion are separate topics for later chapters.

literal، پارامتر و queryLiteral, parameter, and query

در template زیر id از path جدا می‌شود و term از query می‌آید. ترتیب declaration به‌تنهایی راه‌حل همهٔ رقابت‌ها نیست؛ routeهای ممکن را روی requestهای واقعی آزمایش کن. literal مشخصی مثل search معمولاً از پارامتر عمومی id اولویت دارد، چون template خاص‌تر است.

In the template below, id comes from the path and term from the query. Declaration order is not a universal fix; test candidate routes with real requests. A literal such as search normally outranks a general id parameter because the template is more specific.

Minimal API با route group
var products = app.MapGroup("/products");

products.MapGet("/{id:int}", (int id) =>
    Results.Ok(new { productId = id }));

products.MapGet("/search", (string? term) =>
    Results.Ok(new { searchTerm = term }));

MapGroup پیشوند مشترک را یک‌جا تعریف می‌کند و endpointها را زیر آن سازمان می‌دهد. درخواست GET /products/42 مقدار route value برابر 42 می‌دهد؛ GET /products/search?term=lamp endpoint جست‌وجو را انتخاب می‌کند و term از query می‌آید.

MapGroup defines a shared prefix once and organises endpoints beneath it. GET /products/42 yields route value 42; GET /products/search?term=lamp selects search, with term coming from the query.

constraint برای انتخاب route است، نه اعتبارسنجی کاربرConstraints select routes; they are not user validation

constraint مثل int یا guid می‌گوید این template فقط وقتی match شود که segment شکل مشخصی دارد. این برای جداکردن /orders/{id:int} از یک route دیگر مفید است. اما اگر کاربر /orders/abc بفرستد، constraint ممکن است route را رد کند و نتیجه 404 شود؛ برای پیام خطای ورودی مناسب 400، route را عمومی‌تر بگیر و مقدار را در validation بررسی کن.

A constraint such as int or guid says a template matches only when the segment has a particular shape. This helps distinguish /orders/{id:int} from another route. But if a user sends /orders/abc, the constraint may reject the route and produce 404; for a useful 400 input error, use a broader route and validate the value.

نه لزوماً؛ endpoint ممکن است با constraint رد شود یا middleware عمداً درخواست را پنهان کند. method نادرست برای path موجود هم می‌تواند 405 بدهد، بسته به endpointهای mapشده. متن response و routing logs را کنار هم بخوان.

Not always; a constraint may reject a candidate or middleware may intentionally hide it. A wrong method for a known path can return 405, depending on mapped endpoints. Read the response alongside routing logs.

Controller route از دو قطعه ساخته می‌شودController routes combine two pieces

در controller-based API، route attribute کلاس و action می‌توانند ترکیب شوند. این به تیم امکان می‌دهد پیشوند را یک‌جا و path هر عملیات را کنار action نگه دارد. Actionهای public هم conventionهای خودشان را دارند؛ اگر endpoint ناخواسته discover شده، [NonAction] و attributeهای route را بررسی کن.

In controller APIs, a class route attribute and an action route can combine. This lets a team keep a shared prefix on the class and each operation’s path near its action. Public actions follow conventions; if an unintended endpoint was discovered, inspect [NonAction] and route attributes.

پیشوند و action
[ApiController]
[Route("api/orders")]
public sealed class OrdersController : ControllerBase
{
    [HttpGet("{id:guid}")]
    public IActionResult GetById(Guid id) => Ok(id);

    [HttpGet("recent")]
    public IActionResult Recent() => Ok();
}

در این مثال actionها زیر api/orders قرار می‌گیرند. متد GET /api/orders/recent نباید به‌عنوان Guid تفسیر شود؛ literal recent خاص‌تر است. مسیر و method را با HTTP client آزمایش کن، نه فقط با نگاه‌کردن به attributeها.

Both actions live under api/orders. GET /api/orders/recent should not be treated as a Guid; the literal recent is more specific. Test paths and methods with an HTTP client instead of relying only on attribute inspection.

ساخت URL را از چسباندن رشته جدا کنGenerate URLs instead of concatenating strings

اگر route را دستی در چند فایل string کنی، با تغییر prefix لینک قدیمی می‌ماند. نام‌گذاری endpoint یا link generation می‌تواند URL را بر اساس route values بسازد. این کار برای 201 Created و لینک‌دادن به منبع تازه‌ساخته‌شده مفید است؛ اما تست کن که route name یکتا و route valueها کامل باشند.

If route paths are concatenated across files, a prefix change leaves stale links. Endpoint names and link generation can produce URLs from route values. This helps with 201 Created and linking to a newly created resource, but verify endpoint names are unique and route values are complete.

برای انتخاب بین مسیر literal و پارامتر، precedence را به کار ببر؛ برای ساخت URL، generation را. این دو سمت routing هستند: یکی درخواست را به endpoint می‌رساند، دیگری مسیر را از endpoint و مقدارها می‌سازد. جزئیات named route و LinkGenerator را طبق نیاز پروژه ادامه بده.

Use precedence to select between literal and parameter routes; use generation to create URLs. These are two sides of routing: one maps a request to an endpoint, the other creates a path from an endpoint and values. Explore named routes and LinkGenerator as the project requires.

Router با شاهد جلو می‌رودRouting works from evidence

Router method و path را با endpointهای ثبت‌شده تطبیق می‌دهد، route value را استخراج و endpoint مناسب را انتخاب می‌کند. query و body بخش‌های دیگری از درخواست‌اند و binding آن‌ها جداست. literalهای خاص معمولاً از پارامترهای عمومی اولویت دارند؛ constraint برای disambiguation است، نه جایگزین validation کاربر.

Routing matches method and path to configured endpoints, extracts route values, and selects a handler. Query and body are separate request inputs with their own binding. Specific literals normally outrank generic parameters; constraints disambiguate routes, not replace user-input validation.

اگر 404 دیدی، بررسی کن template چرا candidate نشده. اگر 405 دیدی، method را با endpoint mapشده مقایسه کن. اگر route درست است اما مقدار handler غلط است، حالا سراغ binding برو. این مرزها را جدا نگه دار تا پایگاه‌داده را برای خطایی که هنوز به آن نرسیده‌ای متهم نکنی.

For 404, ask why the template did not become a candidate. For 405, compare the method with mapped endpoints. If the route is right but the handler value is wrong, inspect binding. Keep these boundaries separate; do not blame the database before the request reaches it.

در فصل بعد middleware را کنار همین Router می‌گذاریم. ترتیب اشتباه می‌تواند باعث شود middleware اطلاعات endpoint را نبیند یا درخواست پیش از انتخاب مسیر متوقف شود؛ حالا ابزار لازم را داری که آن مسیر را روی کاغذ و در log دنبال کنی.

Next we place middleware around this router. Wrong order can hide endpoint metadata or stop the request before route selection; you now have the tools to trace that path on paper and in logs.
