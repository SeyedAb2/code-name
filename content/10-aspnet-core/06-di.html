DI و طول عمر؛ سرویس کجا ساخته می‌شود؟

DI and lifetimes: where is a service created?

دو درخواست هم‌زمان وارد API می‌شوند و هر دو یک object مشترک را تغییر می‌دهند. یکی می‌گوید «پس همه را transient ثبت کن»؛ دیگری scoped را داخل singleton می‌گذارد. برای انتخاب lifetime، اول عمر واقعی داده و مصرف‌کننده را رسم می‌کنیم.

Two concurrent API requests mutate the same object. One developer says “make everything transient”; another injects a scoped service into a singleton. To choose a lifetime, first map the real lifetimes of data and consumers.

یک شیء مشترک، دو درخواست مستقلOne shared object, two independent requests

Dependency Injection یعنی consumer وابستگی را از container دریافت می‌کند، نه اینکه خودش implementation را بسازد. ثبت service فقط می‌گوید چه چیزی برای چه abstractionی ساخته شود؛ lifetime می‌گوید یک instance چه مدت و در چه scopeای به اشتراک گذاشته می‌شود. پس انتخاب lifetime تصمیمی دربارهٔ state، هم‌زمانی و disposal است.

Dependency Injection means a consumer receives dependencies from a container rather than constructing implementations itself. Registration maps a service to an abstraction; lifetime defines how long an instance is shared. It is therefore a decision about state, concurrency, and disposal.

Scoped یعنی در یک request scope مشترک، بین درخواست‌های جدا متفاوت؛ نه «یک بار برای کل برنامه».

Scoped means shared within one request scope and distinct across requests—not one instance for the whole app.

Singleton ممکن است هم‌زمان از چند درخواست صدا زده شود؛ state mutable بدون synchronization خطرناک است. Transient هم الزاماً ارزان یا بی‌عمر نیست؛ اگر dependency قابل‌dispose گرفته‌ای، مالکیت را بفهم. Container معمولاً instanceهایی را که خودش ساخته dispose می‌کند، اما عمر scope باید درست ساخته و بسته شود.

A singleton can be called concurrently by many requests; mutable state without synchronization is unsafe. Transient does not mean cheap or resource-free; understand ownership of disposable dependencies. The container disposes instances it creates, but scopes must be created and closed correctly.

Abstraction را ثبت کن، implementation را تزریق کنRegister an abstraction, inject the implementation

برای سرویس application، قرارداد و implementation را جدا نگه دار تا consumer به جزئیات ساخت وابسته نشود. constructor injection وابستگی لازم را آشکار می‌کند و تست را ساده‌تر می‌سازد. service locator یا resolve کردن از container داخل هر متد، وابستگی را پنهان می‌کند؛ آن را به الگوی پیش‌فرض تبدیل نکن.

Separate application contracts from implementations so consumers do not depend on construction details. Constructor injection makes required dependencies visible and simplifies testing. Resolving from the container inside every method hides dependencies; do not make service location the default.

ثبت تکراری یک abstraction می‌تواند برای resolve تک‌سرویسی آخرین registration را برگرداند و برای IEnumerable<T> همهٔ آن‌ها را؛ این رفتار را آگاهانه استفاده کن و registration را بی‌دلیل تکرار نکن.

Singleton نباید scoped را در خودش زندانی کندA singleton must not capture a scoped service

Singleton برای تمام عمر container می‌ماند؛ Scoped برای یک request scope. اگر constructor یک singleton، scoped service بگیرد، آن dependency عملاً طولانی‌تر از عمر موردنظر نگه داشته می‌شود: همان captive dependency. scope validation در محیط توسعه کمک می‌کند بعضی اشتباه‌ها را زود پیدا کنی، اما طراحی درست جای خودش را دارد.

A singleton lives for the container; a scoped service lives for one request scope. If a singleton constructor captures a scoped service, it effectively retains that dependency longer than intended: a captive dependency. Scope validation in development catches some mistakes early, but good design is still required.

برای کار پس‌زمینه scope بساز
public sealed class QueueWorker(IServiceScopeFactory scopeFactory)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = scopeFactory.CreateAsyncScope();
            var handler = scope.ServiceProvider.GetRequiredService<IMessageHandler>();
            await handler.ProcessNextAsync(stoppingToken);
        }
    }
}

Worker singleton است و request scope خودکار ندارد؛ برای هر واحد کار scope مناسب بساز و dispose کن. اگر عملیات خیلی کوتاه نیست، حلقه باید delay/انتظار واقعی داشته باشد تا CPU را بی‌وقفه مصرف نکند؛ این نمونه روی lifetime تمرکز دارد، نه طراحی کامل صف.

A worker is singleton and has no automatic request scope; create and dispose an appropriate scope per unit of work. A real loop also needs proper waiting so it does not spin; this sample focuses on lifetime, not complete queue design.

تست‌ها را با قرارداد lifetime بنویسTest the lifetime contract

برای scoped، دو resolve در یک scope باید همان instance و دو scope جدا باید instance متفاوت بدهند. برای singleton، دو scope به یک instance مشترک می‌رسند. این تست‌ها فقط رفتار container را نشان می‌دهند؛ thread-safety singleton یا درست‌بودن منطق business را ثابت نمی‌کنند.

For scoped services, two resolutions in one scope should return the same instance, while separate scopes should differ. A singleton resolves to the same instance across scopes. These tests verify container behaviour, not singleton thread safety or business correctness.

Lifetime را از عمر state و مصرف‌کننده دربیاورDerive lifetime from consumer and state lifetime

Transient یعنی resolve تازه؛ Scoped یعنی instance در یک scope؛ Singleton یعنی instance مشترک در طول container. هیچ‌کدام به‌تنهایی طراحی را درست نمی‌کنند: singleton باید concurrency-safe باشد، scoped در worker به scope نیاز دارد و disposableها مالک روشن می‌خواهند. dependency graph را از مصرف‌کننده تا پایین دنبال کن و lifetime را با تست ثابت کن.

Transient means a new resolution; scoped means one instance per scope; singleton means one shared instance for the container. None guarantees correct design: singletons need concurrency safety, workers need explicit scopes, and disposable resources need clear ownership. Trace the graph from consumer downward and verify lifetime with tests.
