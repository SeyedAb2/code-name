پیکربندی، DI و لاگ در برنامهٔ میزبان‌شده

Configuration, DI, and logging in hosted applications

کارمند پشتیبانی می‌گوید برنامه به آدرس آزمایشی وصل شده، با اینکه همان binary در production اجراست. هم‌زمان هیچ logی نمی‌گوید کدام environment بالا آمده است. می‌توانیم رشتهٔ اتصال را در کد عوض کنیم و build تازه بدهیم؛ اما راه درست این است بفهمیم host پیکربندی را از کجا می‌خواند، سرویس را چه‌وقت می‌سازد و رخداد را کجا ثبت می‌کند.

Support says the app connects to a test address even though the same binary runs in production. No log says which environment started. We could change the connection string in code and rebuild; instead, find out where the host reads configuration, when it creates the service, and where it records the event.

یک binary، دو environmentOne binary, two environments

برنامه را یک بار build کرده‌ایم و همان فایل را در staging و production می‌گذاریم. تفاوت باید در configuration باشد، نه در دو نسخهٔ source. host می‌تواند چند provider را به ترتیب بخواند؛ providerهایی که دیرتر اضافه شده‌اند معمولاً مقدار قبلی را override می‌کنند. اگر ترتیب را ندانی، «چرا مقدار فایل نادیده گرفته شد؟» تبدیل به حدس می‌شود.

We build once and deploy the same files to staging and production. The difference should be configuration, not two source versions. The host reads multiple providers in order; later providers commonly override earlier values. Without knowing precedence, “why was the file value ignored?” becomes guesswork.

همین host، container وابستگی‌ها را هم می‌سازد و ILogger را فراهم می‌کند. بنابراین سه موضوع جدا اما متصل‌اند: config مقدار را از منبع می‌گیرد؛ DI سرویس را با مقدار لازم می‌سازد؛ logging نشان می‌دهد نتیجهٔ تصمیم چه شد. secret را config می‌خواند، اما این به معنی چاپ‌کردن آن در log نیست.

The same host also builds the dependency container and provides ILogger. These are separate but connected: configuration reads a value from a source; DI constructs a service with that value; logging shows what happened as a result. A secret can be read from configuration without being printed to a log.

پیکربندی، زنجیرهٔ providerهاستConfiguration is a chain of providers

در الگوی پیش‌فرض Host.CreateApplicationBuilder، فایل appsettings.json و فایل environment-specific خوانده می‌شوند؛ در Development ممکن است user secrets نیز وارد شوند؛ متغیر محیطی و آرگومان command line هم می‌توانند مقدارها را override کنند. ترتیب دقیق را با نوع builder و providerهای افزوده‌شده تطبیق بده؛ «فایل همیشه برنده است» قاعده نیست.

With the default Host.CreateApplicationBuilder pattern, appsettings.json and an environment-specific file are read; in Development, user secrets may also participate; environment variables and command-line arguments can override values. Match the exact order to builder type and added providers—“the file always wins” is not a rule.

فایل محیط توسعه، بدون credential واقعی
{
  "Report": {
    "Endpoint": "https://localhost:7040",
    "TimeoutSeconds": 8
  }
}

Report__Endpoint=https://staging.example.invalid

در متغیر محیطی، دو underscore معمولاً جای جداکنندهٔ مسیر کلیدهای تودرتو را می‌گیرد؛ پس Report__Endpoint به کلید Report:Endpoint می‌رسد. مقدار environment را در process واقعی بررسی کن؛ shell یک پنجره با container یا سرویس production یکی نیست.

In environment variables, double underscores commonly represent separators in hierarchical keys, so Report__Endpoint maps to Report:Endpoint. Inspect the value in the actual process environment; your shell is not the same as a container or production service.

User Secrets رمزگذاری‌شده نیستUser Secrets are not encrypted

ابزار User Secrets برای نگه‌داشتن secretهای توسعه بیرون از repository است، نه خزانهٔ production و نه encryption. secret واقعی را commit نکن؛ در production از سازوکار secret مناسب محیط استفاده کن.

User Secrets keeps development secrets outside the repository; it is not a production vault or encryption. Never commit real secrets; use the environment’s appropriate secret mechanism in production.

تنظیمات پراکنده را به قرارداد تایپ‌شده تبدیل کنTurn scattered settings into a typed contract

اگر هر سرویس رشتهٔ config را دستی بخواند، typo فقط هنگام اجرا خود را نشان می‌دهد. Options یک کلاس برای گروه تنظیمات می‌سازد و آن را از Configuration bind می‌کند. اینجا فقط مرز host را می‌بینیم؛ اعتبارسنجی، reload و IOptions variantها را در مسیر ASP.NET عمیق‌تر بررسی می‌کنیم.

If every service reads configuration strings manually, a typo may appear only at runtime. Options gives a settings group a class and binds it from Configuration. Here we focus on the host boundary; validation, reload, and IOptions variants are explored further in the ASP.NET track.

Options ساده و registration
public sealed class ReportOptions
{
    public const string SectionName = "Report";
    public string Endpoint { get; set; } = "";
    public int TimeoutSeconds { get; set; }
}

builder.Services.Configure<ReportOptions>(
    builder.Configuration.GetSection(ReportOptions.SectionName));

کلاس Options به‌تنهایی مقدار را از جادو پیدا نمی‌کند؛ registration آن را به section وصل می‌کند. برای اجرای برنامه endpoint و timeout را با environment واقعی بخوان و مقادیر حساس را هنگام log کردن حذف کن.

An options class does not magically find its values; registration binds it to a section. Read endpoint and timeout in the actual environment, and omit sensitive values from logs.

DI، محل ساخت و lifetime سرویس‌هاDI defines construction and service lifetime

registrationها پیش از Build در builder.Services ثبت می‌شوند؛ container هنگام resolution شیء را می‌سازد و lifetime ثبت‌شده را رعایت می‌کند. transient هر بار resolve ساخته می‌شود؛ scoped یک نمونه در scope دارد؛ singleton یک نمونه برای عمر container. انتخاب lifetime قرارداد concurrency، حافظه و disposal هم هست، نه فقط بهینه‌سازی ساخت.

Registrations are added to builder.Services before Build; the container constructs services on resolution and follows their lifetime. Transient creates on each resolution; scoped is one instance per scope; singleton is one instance for the container lifetime. Lifetime is also a concurrency, memory, and disposal contract—not merely a construction optimisation.

constructor injection را پیش‌فرض بگیر؛ در constructor سرویس را دستی new نکن و service locator نساز. اگر hosted singleton به dependency scoped نیاز دارد، IServiceScopeFactory بگیر و برای هر واحد کار scope بساز و آزاد کن. این همان پلی است که فصل قبل بین عمر worker و scope کوتاه‌عمر معرفی کردیم.

Prefer constructor injection; do not manually new dependencies or create a service locator. If a hosted singleton needs a scoped dependency, inject IServiceScopeFactory and create/dispose a scope per unit of work. This is the bridge between worker lifetime and a short-lived scope introduced last chapter.

log رخداد را ثبت می‌کند، نه هر متغیر راLogs record events, not every variable

ILogger از container می‌آید؛ providerها مقصد log را تعیین می‌کنند. Console معمولاً stdout را نشان می‌دهد و برای توسعه یا container ساده است؛ در محیط دیگر providerهای متفاوت ممکن‌اند. پیام ساخت‌یافته با placeholder نام‌دار، فیلتر level و category قابل‌جست‌وجو می‌سازد. secret، token و دادهٔ شخصی را در message یا scope ننویس.

ILogger comes from DI; providers determine where logs go. Console commonly writes to stdout and is useful for development or a simple container; other environments may use different providers. Structured messages with named placeholders make level and category searchable. Never log secrets, tokens, or personal data.

log مفید و ساخت‌یافته
logger.LogInformation(
    "Report {ReportId} queued for {Destination}",
    reportId,
    destinationHost);

از نوشتن logger.LogInformation($"report {reportId}") پرهیز کن وقتی provider می‌تواند قالب را ساخت‌یافته نگه دارد. level را با اهمیت رخداد هماهنگ کن و یک بار رخداد را در مرز مناسب ثبت کن؛ تکرار exception در هر لایه نویز می‌سازد. log قرار نیست جای metric، trace یا audit data را بگیرد.

Avoid interpolating every message when the provider can preserve a structured template. Match level to event importance and log once at the right boundary; logging the same exception at every layer creates noise. Logs do not replace metrics, traces, or audit data.

یک سرویس، سه شاهدOne service, three evidence points

حالا همان ReportOptions را به یک ReportClient بده و endpoint را log کن. فایل مقدار پایه است؛ environment آن را override می‌کند؛ DI مقدار نهایی را به سرویس می‌دهد؛ log فقط hostname غیرحساس را ثبت می‌کند. اگر یکی از این مراحل را حذف کنیم، اختلاف production دوباره مبهم می‌شود.

Bind the same ReportOptions into a ReportClient and log an endpoint call. The file supplies a base value; environment overrides it; DI provides the final setting to the service; logging records only a non-sensitive host. Missing any step makes the production discrepancy ambiguous again.

ثبت سرویس و خواندن تنظیمات
builder.Services.AddOptions<ReportOptions>()
    .Bind(builder.Configuration.GetSection("Report"));
builder.Services.AddTransient<ReportClient>();

app.MapGet("/reports/check", async (ReportClient client) =>
    Results.Ok(await client.CheckAsync()));

برای عیب‌یابی، مقدار نهایی endpoint را از IConfiguration در startup چاپ نکن اگر secret دارد؛ hostname یا نام provider کافی است. به جای log تمام configuration، فقط کلیدهای بی‌خطر لازم برای تشخیص را ثبت کن و برای هر environment یک آزمایش بگیر.

For diagnosis, do not dump the final configuration at startup if it contains secrets; a hostname or source label may suffice. Log only safe keys needed for diagnosis, and test each environment separately.

آزمایشگاه: staging مقدار production را نمی‌بیندLab: staging reads the production value

یک Worker یا Console Host disposable بساز. مقدار Report:Endpoint را در appsettings.json قرار بده، سپس با environment variable آن را override کن. از مقصد جعلی .invalid استفاده کن تا هیچ درخواست واقعی ارسال نشود.

Create a disposable Worker or Console Host. Put Report:Endpoint in appsettings.json, then override it with an environment variable. Use an .invalid destination so no real request is sent.

  1. ReportOptions را bind کن و در سرویس از طریق IOptions دریافت کن.Bind ReportOptions and inject it into a service through IOptions.
  2. مقدار base را ثبت و مقدار نهایی را بدون secret در console نشان بده.Record the base value and print the final non-secret setting.
  3. در PowerShell مقدار Report__Endpoint را برای همان process تنظیم و دوباره اجرا کن؛ precedence را ثابت کن.Set Report__Endpoint for that process in PowerShell, rerun, and prove precedence.
  4. سرویس ReportClient را transient ثبت کن و با log ساخت‌یافته یک عملیات آزمایشی را ثبت کن.Register ReportClient as transient and log one test operation structurally.
  5. عمداً کلید را غلط بنویس. نتیجه را تشخیص بده و به‌جای چاپ همهٔ configuration، فقط کلید امن را مشاهده کن.Deliberately misspell a key. Diagnose it while observing only safe configuration, not a full dump.
  6. برای hosted worker یک dependency scoped اضافه کن؛ ابتدا direct injection را در محیط Development ببین که validation رد می‌کند، سپس با IServiceScopeFactory scope کوتاه بساز.Add a scoped dependency to a hosted worker; observe Development validation reject direct injection, then create a short scope with IServiceScopeFactory.

تحویل آزمایشگاه: source مقدار پایه، provider برنده، نوع registration و lifetime، log ثبت‌شده و مدرک عدم چاپ secret. این پنج شاهد incident اول را از «روی ماشین من کار می‌کند» به یک گزارش قابل‌تکرار تبدیل می‌کنند.

Submit the base source, winning provider, registration/lifetime, emitted log, and evidence that no secret was printed. These five points turn the original incident from “works on my machine” into a repeatable report.

سه تصمیم که در یک incident به هم می‌رسندThree decisions meet in one incident

providerها تعیین می‌کنند تنظیم از کجا می‌آید؛ Options آن را به شکل تایپ‌شده می‌بندد؛ DI سرویس را با lifetime مشخص می‌سازد؛ ILogger نتیجهٔ امن و مفید را ثبت می‌کند. اگر staging مقدار production را دید، به‌جای build متفاوت ترتیب provider و environment process را بررسی کن.

Providers decide where settings come from; Options binds them to typed values; DI constructs services with a deliberate lifetime; ILogger records a safe, useful result. If staging sees production’s value, inspect provider order and process environment instead of building a different binary.

اگر host یک worker را با سرویس scoped وصل می‌کند، scope را صریح بساز. اگر log لازم داری، provider واقعی محیط را بررسی کن و secret را چاپ نکن. این سه عادت، پایهٔ diagnostics فصل بعد هستند: وقتی process کند یا پرمصرف شد، باید بتوانیم اطلاعات امن و قابل‌اندازه‌گیری جمع کنیم.

If a host worker needs a scoped service, create a scope explicitly. If logs matter, inspect the environment’s actual provider and keep secrets out. These habits prepare for diagnostics: when a process is slow or resource-heavy, collect safe, measurable evidence.
