برنامه را به مقصد چطور تحویل بدهیم؟

How should we deliver the application?

روی لپ‌تاپ برنامه اجرا می‌شود؛ روی سرور مقصد خطا می‌دهد که runtime پیدا نشد. باید بین فراهم‌کردن runtime روی میزبان و بردن آن همراه برنامه تصمیم بگیریم. جواب فقط «کدام پوشه کوچک‌تر است» نیست؛ مالکیت patch و مقصد اجرا هم مهم‌اند.

The app runs on the laptop but the target says the runtime is missing. We must choose between providing the runtime on the host and shipping it with the app. The answer is not just “which folder is smaller”; patch ownership and the target matter too.

runtime روی میزبان یا کنار برنامه؟Runtime on the host or beside the app?

در حالت framework-dependent، خروجی برنامه را می‌دهد و میزبان باید runtime سازگار .NET را داشته باشد. در self-contained همان runtime هم همراه برنامه منتشر می‌شود. هیچ‌کدام همیشه بهتر نیست: اول ببین چه کسی runtime را نصب و patch می‌کند و میزبان دقیقاً چه OS و معماری‌ای دارد.

Framework-dependent output ships the app while the host provides a compatible .NET runtime. Self-contained output bundles that runtime. Neither is always better: identify who installs and patches the runtime and the exact target OS/architecture.

مدلModelنیاز میزبانHost needsمسئول patchPatch owner
framework-dependentruntime سازگاراپراتور میزبان
self-containedruntime جدا لازم نیستتیم برنامه در release

self-contained یعنی runtime داخل artifact است، نه اینکه خروجی cross-platform باشد. framework-dependent هم به معنی اجرای همه‌جا نیست؛ TFM/runtime و native dependency باید با مقصد جور باشند. از .NET 8 به بعد صرف تعیین RID دیگر self-contained را به‌طور ضمنی انتخاب نمی‌کند؛ mode را واضح مشخص کن.

Self-contained means the runtime is in the artifact, not that it is cross-platform. Framework-dependent does not run everywhere either: TFM/runtime and native dependencies must match the target. Since .NET 8, a RID alone no longer implicitly selects self-contained; state the mode explicitly.

انتشار را برای یک مقصد واقعی بسازPublish for a real target

RID را از catalog رسمی انتخاب کن، framework را در پروژه‌های چندهدفه مشخص کن و خروجی را روی همان OS/معماری smoke test کن. فرمان موفق، سازگاری مقصد را ثابت نمی‌کند.

Choose a RID from the official catalog, specify the framework for multi-targeted projects, and smoke-test on the target OS/architecture. A successful command does not prove target compatibility.

دو مدل برای Linux x64
dotnet publish -c Release -f net10.0 -r linux-x64 --self-contained false
dotnet publish -c Release -f net10.0 -r linux-x64 --self-contained true

اگر برنامه فقط یک TFM دارد، -f را حذف کن. برای حالت framework-dependent میزبان باید runtime سازگار داشته باشد؛ برای self-contained فایل اجرایی همان target را از پوشهٔ publish اجرا کن. در هر دو حالت فایل‌های native را هم بررسی کن.

If the app has one TFM, omit -f. Framework-dependent needs a compatible host runtime; for self-contained, run the target executable from the publish folder. Inspect native files in either case.

انتخاب مدل، انتخاب مسئولیت استChoosing a model assigns responsibility

اگر میزبان چند برنامه دارد و تیم زیرساخت runtime را وصله می‌کند، framework-dependent انتشار سبک‌تر و مدیریت متمرکز می‌دهد. اگر نصب runtime روی مقصد ممکن نیست، self-contained کمک می‌کند اما runtime داخل artifact با patch میزبان به‌روز نمی‌شود؛ باید با SDK/runtime جدید دوباره publish و deploy کنی. ثبت کن کدام تیم و کدام چرخه این کار را انجام می‌دهد.

If a host runs several apps and infrastructure patches the runtime, framework-dependent can simplify releases and centralize management. If the target cannot install a runtime, self-contained helps, but host patches do not update the bundled runtime; republish and deploy with an updated SDK/runtime. Record which team and cadence own this.

یک artifact برای همهٔ ماشین‌ها فرض نکنDo not assume one artifact fits every machine

Windows در برابر Linux یا x64 در برابر ARM64 می‌تواند RID و dependency بومی متفاوت بخواهد. خروجی را از پوشهٔ publish همان build بردار، نه از bin عمومی؛ نسخه و دستور اجرای مقصد را کنار artifact نگه دار.

Windows versus Linux or x64 versus ARM64 can require different RIDs and native dependencies. Take output from that build's publish folder, not a generic bin directory; record target version and run command with the artifact.

قبل از انتخاب، این چهار سؤال را جواب بدهAnswer four questions before choosing

runtime را چه کسی patch می‌کند؟ مقصد دقیقاً کدام OS/معماری است؟ native dependency داریم؟ اندازهٔ artifact چقدر مهم است؟ جواب‌ها مدل را تعیین می‌کنند؛ single-file، trimming و AOT گزینه‌های جدا با محدودیت‌های خودشان هستند و فصل بعد بررسی می‌شوند.

Who patches the runtime? Which exact OS/architecture is targeted? Are there native dependencies? How important is artifact size? The answers determine the model; single-file, trimming, and AOT are separate options with their own constraints, covered next.

framework-dependent runtime را به میزبان می‌سپارد؛ self-contained آن را در خروجی می‌آورد و patch را به چرخهٔ برنامه منتقل می‌کند. TFM، RID، معماری، native dependency و دستور اجرا را ثبت کن. انتشار وقتی تمام است که همان artifact در محیط هدف آزمایش شود، نه وقتی فرمان publish سبز شد.

Framework-dependent delegates runtime provision to the host; self-contained bundles it and moves patching into the app release cycle. Record TFM, RID, architecture, native dependencies, and run command. Publishing is complete after the artifact is tested on its target, not when the command turns green.
