وقتی برنامه کند می‌شود، چه مدرکی جمع کنیم؟

When an application slows down, what evidence should we collect?

سرویس کند شده و حدس‌ها شروع شده‌اند: «حتماً GC است»، «احتمالاً شبکه است». قبل از تغییر کد، process درست را پیدا می‌کنیم، یک نشانهٔ کم‌هزینه می‌گیریم و بعد سراغ trace یا dump می‌رویم؛ هر ابزار جواب سؤال متفاوتی را می‌دهد.

A service is slow and guesses begin: “It must be the GC,” “probably the network.” Before changing code, identify the right process, collect a low-cost signal, then use a trace or dump. Each tool answers a different question.

سرویس کند است؛ از کجا شروع کنیم؟The service is slow; where do we start?

روی ماشین چند برنامهٔ دات‌نت اجراست. اگر فقط اسم ابزارها را حفظ کرده باشی، ممکن است از process اشتباه dump بگیری یا ساعت‌ها trace جمع کنی که اصلاً پاسخ سؤال را نمی‌دهد. زنجیرهٔ ما این است: process → سؤال → ابزار کم‌هزینه → شاهد دقیق‌تر → تفسیر.

Several .NET applications run on the machine. Knowing tool names is not enough: you might dump the wrong process or collect a trace that cannot answer your question. Our chain is process → question → low-cost tool → focused evidence → interpretation.

از signal سبک شروع کن. Trace رفتار در طول زمان را نشان می‌دهد؛ dump تصویری از یک لحظه است.

Start with a lightweight signal. A trace records behaviour over time; a dump is a snapshot.

ابزارها را معمولاً به‌صورت dotnet tool نصب می‌کنی؛ برای دیدن processهای قابل‌مشاهده هم از dotnet-diagnostic استفاده می‌شود. نسخهٔ ابزار و runtime باید با محیط سازگار باشد و دسترسی سیستم‌عامل به process مقصد لازم است. در کانتینرها ممکن است PID داخل کانتینر با PID میزبان فرق کند؛ از همان namespace و محیط درست نگاه کن.

Install the tools as dotnet tools. The diagnostic tool can list processes visible to it. Tool and runtime versions must be compatible, and the operating system must permit access to the target process. In containers, a container PID can differ from a host PID; inspect from the correct namespace and environment.

اول روند را ببین، نه یک عدد تنهاLook at a trend, not one isolated number

وقتی نمی‌دانی مشکل CPU است، allocation یا طول صف، dotnet-counters کمک می‌کند چند counter را زنده ببینی. اول process را با نام و PID تأیید کن؛ بعد مانیتور را کوتاه اجرا کن و زمان رخداد را یادداشت کن.

When you do not yet know whether the issue is CPU, allocation, or queue growth, dotnet-counters provides a live view of selected counters. Confirm the process by name and PID, monitor briefly, and note when the symptom occurs.

یک snapshot کوتاه
dotnet-counters ps
dotnet-counters monitor --process-id 1234
dotnet-counters collect --process-id 1234 --duration 00:00:30

PID نمونه را با PID واقعی عوض کن. نام counterها بین نسخه‌ها و runtimeها تغییر می‌کند؛ خروجی را با نسخهٔ .NET خودت بخوان. یک مقدار بالای CPU به‌تنهایی نمی‌گوید کدام تابع مقصر است؛ counterها جهت می‌دهند تا سؤال trace را دقیق‌تر کنی.

Replace the sample PID with the real one. Counter names vary by runtime and version, so interpret output for your .NET version. A high CPU value alone does not identify the responsible method; counters help refine the question for a trace.

snapshot با روند یکی نیستA snapshot is not a trend

یک عدد حافظه ممکن است حاصل زمان‌بندی GC یا بار لحظه‌ای باشد. چند نمونه در بازهٔ رخداد، کنار latency و لاگ، معنی‌دارتر است. ابزار تشخیصی جای معیار محصول یا پایش بلندمدت را نمی‌گیرد.

A single memory value may reflect GC timing or a transient load. Samples across the incident, correlated with latency and logs, are more useful. Diagnostic tools are not a substitute for product metrics or long-term monitoring.

وقتی سؤال دربارهٔ زمان است، trace بگیرWhen the question is about timing, collect a trace

مثلاً می‌دانی CPU بالا رفته، اما نه اینکه کاربرها کدام مسیر را می‌زنند و threadها کجا وقت می‌گذرانند. dotnet-trace رخدادهای runtime را برای یک بازه ثبت می‌کند. بازه را کوتاه و سناریو را قابل‌تکرار نگه دار؛ فایل trace می‌تواند بزرگ و حاوی اطلاعات حساس عملیاتی باشد.

Suppose CPU is high, but you do not know which operations users trigger or where threads spend time. dotnet-trace records runtime events over an interval. Keep the interval short and the scenario reproducible; traces can be large and may contain sensitive operational details.

ثبت محدود و هدفمند
dotnet-trace collect --process-id 1234 --duration 00:00:20 --output incident.nettrace

این دستور را در محیط آزمایش یا با مجوز عملیاتی اجرا کن. trace را با ابزار viewer سازگار باز کن، بازهٔ زمانی رخداد را پیدا کن و نتیجه را با درخواست و لاگ متناظر مقایسه کن. trace همبستگی نشان می‌دهد؛ هر رخداد به‌تنهایی اثبات علت نیست.

Run this in a lab or with operational approval. Open the trace in a compatible viewer, locate the incident window, and correlate it with the matching request and logs. A trace reveals correlations; an event alone does not prove causation.

dump حافظه است؛ با آن مثل دادهٔ حساس رفتار کنA dump is memory; treat it as sensitive data

اگر برنامه hang کرده یا می‌خواهی وضعیت threadها و heap را در همان لحظه بررسی کنی، dotnet-dump می‌تواند dump بگیرد. این فایل ممکن است توکن، رمز، دادهٔ کاربر و محتوای درخواست را در حافظه داشته باشد. مسیر ذخیره، دسترسی، انتقال و حذف امنش را از قبل مشخص کن.

If an application is hung or you need to inspect thread and heap state at one moment, dotnet-dump can capture a dump. It may contain tokens, passwords, user data, and request contents. Decide where it will be stored, who can access it, how it will be transferred, and how it will be securely removed.

فقط روی process مجاز
dotnet-dump collect --process-id 1234 --output incident.dmp
dotnet-dump analyze incident.dmp

گرفتن dump ممکن است مکث و مصرف دیسک ایجاد کند و attach همیشه مجاز یا بی‌خطر نیست. dump را روی سیستم واقعی بی‌هدف نگیر؛ در محیط production از فرایند incident و مجوزهای تیم پیروی کن. بعد از تحلیل، فایل و کپی‌های موقت را طبق سیاست سازمان پاک کن.

Capturing a dump can pause the process and consume disk, and attaching is not always permitted or harmless. Do not collect one casually in production; follow the incident process and team authorization. After analysis, remove the dump and temporary copies according to policy.

از شاهد تا فرضیه؛ نه از ابزار تا حکمFrom evidence to hypothesis, not tool to verdict

نشانهSignalگام بعدNext stepچیزی که هنوز ثابت نشدهNot yet proven
CPU بالا در counterstrace کوتاه در همان بازهیک متد خاص علت است
heap بزرگ در dumpنوع اشیا و rootها را بررسی کنحتماً memory leak است
GC زیادallocation rate و latency را کنار هم ببینتنظیم GC راه‌حل است
threadهای منتظروابستگی، قفل و I/O را بررسی کنافزایش thread مشکل را حل می‌کند

اول فرضیهٔ قابل‌آزمون بنویس: «در بازهٔ کندی، allocation بالا می‌رود و بعد مکث GC با latency هم‌زمان است». یک متغیر را تغییر بده و همان درخواست و همان اندازه‌گیری را تکرار کن. اگر شاهد با فرضیه جور نیست، فرضیه را عوض کن؛ به زور ابزار را تأیید نکن.

Write a testable hypothesis first: “During the slowdown, allocation rises and a GC pause coincides with latency.” Change one variable and repeat the same request and measurement. If evidence disagrees, revise the hypothesis instead of forcing the tool to confirm it.

تمرین‌ها: هر ابزار برای کدام سؤال؟Exercises: which tool answers which question?

For each incident, state what remains unknown, then choose the least costly next piece of evidence.

Diagnostic tool version, target runtime, and execution environment; test against the actual runtime.

۱۴) heap بزرگ بعد از بار14) Heap remains large after load

Post-GC trend, object types and roots, allocation, and a repeatable test; one large heap is not proof of a leak.

Not immediately; inspect the I/O dependency, timeouts, queue, and async pattern. More threads may worsen contention.

۱۷) بعد از تغییر، مشکل ناپدید شد17) The issue disappeared after a change

Same scenario and load, before/after versions, counters and latency, logs, and observation period; simultaneous changes obscure causality.

۱۸) گزارش تشخیصی incident18) An incident diagnostic report

پاسخ / Answer

Symptom/time, process/version, evidence and collection method, hypothesis and next test; never attach a sensitive dump publicly.

ابزار تشخیصی جواب را به‌جای تو نمی‌دهدA diagnostic tool does not answer on your behalf

process را درست انتخاب کن، یک سؤال محدود بپرس و از ارزان‌ترین شاهد شروع کن. counters روند می‌دهند، trace زمان را باز می‌کند و dump وضعیت یک لحظه را نگه می‌دارد. هر سه ممکن است دادهٔ حساس یا هزینهٔ عملیاتی داشته باشند؛ خروجی را تفسیر کن، فرضیه را آزمایش کن و نتیجه را با همان سناریو دوباره بسنج.

Select the right process, ask a narrow question, and start with the cheapest evidence. Counters show trends, traces reveal timelines, and dumps preserve one moment. Each can carry sensitive data or operational cost; interpret the output, test a hypothesis, and verify with the same scenario.
