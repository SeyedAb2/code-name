NuGet، restore و نسخه‌های قابل‌تکرار

NuGet restore and repeatable dependencies

روی لپ‌تاپ تو build موفق است؛ در CI همان commit با خطای dependency متوقف می‌شود. قبل از اینکه پوشهٔ bin را برای هم‌تیمی بفرستی، بیایید بفهمیم restore چه چیزی را حل می‌کند، کدام فایل تصمیمش را ثبت می‌کند و چرا «همان PackageReference» همیشه یعنی «همان graph» نیست.

The build succeeds on your laptop, but CI stops on the same commit with a dependency error. Before sending a teammate your bin folder, let’s find out what restore resolves, which file records that decision, and why the same PackageReference does not always mean the same graph.

همان commit، دو نتیجهOne commit, two outcomes

تیم یک commit را روی لپ‌تاپ build کرده و در CI هم همان commit را گرفته است. روی لپ‌تاپ موفق، در CI خطای package پیدا نشد یا asset سازگار نیست می‌آید. هنوز معلوم نیست مشکل از کد است، شبکه، منبع package، نسخهٔ SDK یا تصمیم restore؛ پاک‌کردن cache فقط یکی از فرضیه‌ها را امتحان می‌کند.

The team built one commit on a laptop and checked out the same commit in CI. The laptop succeeds; CI reports a missing package or incompatible asset. We do not yet know whether the cause is code, network, package source, SDK version, or restore resolution. Clearing the cache tests only one hypothesis.

در فصل قبل دیدیم csproj ورودی build را تعریف می‌کند. وقتی آن ورودی PackageReference دارد، NuGet باید وابستگی مستقیم را پیدا کند، وابستگی‌های بعدی را حل کند و asset مناسب target framework را انتخاب کند. restore همین graph را آماده می‌کند؛ نه اینکه برنامه را compile کند و نه اینکه تضمین کند package از منبع مورد اعتماد آمده است.

In the previous chapter, we saw that csproj defines build inputs. When it contains PackageReference, NuGet must find direct dependencies, resolve their dependencies, and select assets compatible with the target framework. restore prepares that graph; it does not compile the app or guarantee that a package came from a trusted source.

restore چه چیزی می‌سازد؟What does restore produce?

در پروژهٔ جدید SDK-style، وابستگی را معمولاً در فایل پروژه می‌بینی. فایل project.assets.json زیر obj گزارش ماشین‌خوان restore برای build بعدی است: targetها، packageها و assetهایی که انتخاب شده‌اند. آن را ویرایش نکن و معمولاً وارد Git هم نکن؛ اگر ناپدید شود، restore می‌تواند دوباره بسازد.

In a modern SDK-style project, dependencies are usually declared in the project file. project.assets.json under obj is restore’s machine-readable input for the next build: targets, packages, and selected assets. Do not edit it, and normally do not commit it; restore can regenerate it if it disappears.

در پوشهٔ نمونهٔ موقت
dotnet new console -n RestoreProbe
cd RestoreProbe
dotnet add package Spectre.Console --version 0.49.1
dotnet restore
Test-Path .\obj\project.assets.json
Get-ChildItem "$env:USERPROFILE\.nuget\packages\spectre.console"

خروجی مورد انتظار، True برای فایل assets و پوشه‌ای با نسخهٔ package در cache است. مسیر cache را NuGet می‌تواند تغییر بدهد؛ پس مسیر بالا پیش‌فرض رایج Windows است، نه قانون همگانی. در Linux معمولاً cache زیر ~/.nuget/packages است. وجود package در cache نمی‌گوید پروژه به آن وابسته است؛ csproj و assets را کنار هم بخوان.

Expected evidence is True for the assets file and a versioned package directory in the cache. NuGet settings can change the cache path, so the command shows a common Windows default, not a universal location. Linux commonly uses ~/.nuget/packages. A cached package alone does not prove the project depends on it; inspect the project file and assets together.

cache با lock file یکی نیستA cache is not a lock file

cache کمک می‌کند package دوباره دانلود نشود. packages.lock.json برای ثبت graph انتخاب‌شده است. حذف cache نباید dependency declaration را تغییر بدهد؛ حذف lock file می‌تواند تکرارپذیری نسخه‌ها را از بین ببرد.

A cache avoids downloading a package again. packages.lock.json records a selected dependency graph. Removing the cache should not change dependency declarations; removing a lock file can remove version repeatability.

نسخه در PackageReference همیشه نسخهٔ نهایی نیستA PackageReference version is not always the final version

اگر dependency را با Version="4.2.0" بنویسی، NuGet آن را طبق قواعد version range تفسیر می‌کند؛ نسخهٔ حداقل ممکن است تنها انتخاب ممکن نباشد. با floating version مثل 4.* عمداً نسخه‌های تازه‌تر را هم مجاز می‌کنی. declaration درخواست توست؛ resolved version نتیجهٔ restore است.

A dependency written with Version="4.2.0" is interpreted using NuGet version-range rules; a minimum version may not be the only possible selection. With a floating version such as 4.*, you intentionally allow newer matches. The declaration is your request; the resolved version is restore’s result.

اگر نسخه‌ای روی feed اضافه یا حذف شود، یا floating range داشته باشی، resolve می‌تواند تغییر کند. پس اگر build باید در CI و لپ‌تاپ همان graph را ببیند، فقط به حافظهٔ تیم از شماره‌نسخه‌ها تکیه نکن؛ lock file را آگاهانه وارد workflow کن.

When a version is added to or removed from a feed, or when you use a floating range, resolution may change. If laptop and CI should use the same graph, do not rely on the team remembering version numbers; use a lock file deliberately.

قفل نسخه، نه قفل‌کردن توسعهLocking versions without freezing development

برای برنامهٔ اجرایی، می‌خواهیم restore معمولی همان graph ثبت‌شده را به کار ببرد. property زیر را در پروژه اضافه کن و restore بزن؛ NuGet فایل packages.lock.json را می‌سازد. این فایل برای application معمولاً باید وارد version control شود تا CI همان تصمیم‌ها را ببیند.

For an executable app, we want ordinary restore to use the recorded graph. Add the property below and run restore; NuGet creates packages.lock.json. For an application, this file is commonly checked into version control so CI sees the same decisions.

فعال‌کردن lock file
<PropertyGroup>
  <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
</PropertyGroup>

dotnet restore

در CI، dotnet restore --locked-mode را اجرا کن. اگر declaration پروژه با lock سازگار نباشد، restore باید خطا بدهد، نه اینکه بی‌سروصدا فایل را به‌روز کند. برای ارتقای عمدی dependency، lock را آگاهانه بازتولید کن، diff را بازبینی کن و تست‌ها را اجرا کن؛ بعد CI را دوباره در locked mode نگه دار.

In CI, run dotnet restore --locked-mode. If project declarations no longer match the lock, restore should fail instead of silently updating it. To intentionally upgrade a dependency, regenerate the lock deliberately, review the diff, and run tests; then keep CI in locked mode.

نکتهٔ کتابخانه‌هاA note about libraries

lock file یک library معمولاً graph نهایی برنامهٔ مصرف‌کننده را تعیین نمی‌کند؛ مصرف‌کننده dependency graph خودش را حل می‌کند. قاعدهٔ «همهٔ پروژه‌ها حتماً lock file را commit کنند» درست نیست؛ نوع پروژه و سیاست تیم را مشخص کن.

A library’s lock file usually does not determine the final graph of an application consuming it; the consumer resolves its own graph. “Every project must commit a lock file” is not universal; decide based on project type and team policy.

package از کدام منبع می‌آید؟Which source supplies a package?

فایل NuGet.Config می‌تواند feedها و تنظیمات restore را تعریف کند. وقتی هم feed عمومی و هم خصوصی داری، باید بدانی هر package از کدام منبع مجاز است دریافت شود. Package Source Mapping کمک می‌کند package IDها به feedهای مشخص محدود شوند؛ اما فقط مسیر دانلود در restore/install/update را فیلتر می‌کند و جای بررسی امنیتی package را نمی‌گیرد.

NuGet.Config can define feeds and restore settings. When you use both public and private feeds, know which source is allowed to supply each package. Package Source Mapping can constrain package IDs to specified feeds, but it filters package downloads during restore/install/update and does not replace package security review.

نمونهٔ آزمایشی NuGet.Config
<configuration>
  <packageSources>
    <clear />
    <add key="nuget.org" value="https://api.nuget.org/v3/index.json" />
  </packageSources>
  <packageSourceMapping>
    <packageSource key="nuget.org">
      <package pattern="*" />
    </packageSource>
  </packageSourceMapping>
</configuration>

این نمونه فقط وقتی درست است که همهٔ packageها از nuget.org بیایند. با private feed باید mapping همهٔ packageهای مستقیم و transitive را پوشش بدهد؛ mapping ناقص می‌تواند restore را متوقف کند. credential واقعی را داخل فایل مخزن نگذار.

This example is appropriate only when every package comes from nuget.org. With a private feed, mappings must cover all direct and transitive packages; an incomplete mapping can stop restore. Do not put real credentials in a repository file.

وقتی restore شکست می‌خورد، cache را اول پاک نکنWhen restore fails, do not clear the cache first

خطا را دسته‌بندی کن: package پیدا نشده، feed در دسترس نیست، احراز هویت رد شده، نسخه‌ها ناسازگارند، یا asset با TFM جور نیست؟ هرکدام شاهد متفاوت می‌خواهد. خروجی verbose می‌تواند source و درخواست را روشن کند؛ در مقابل، --force dependencyها را دوباره resolve می‌کند، پس برای «شاید درست شود» بی‌هدف اجرا نکن.

Classify the failure: package not found, feed unavailable, authentication rejected, version conflict, or an asset incompatible with the TFM? Each needs different evidence. Verbose output can reveal the source and request; --force re-resolves dependencies, so do not run it blindly as a maybe-this-fixes-it attempt.

شاهد گرفتن پیش از تغییر
dotnet restore -v:diag
dotnet nuget list source
dotnet msbuild -getProperty:TargetFramework
dotnet list package --include-transitive

اگر SDK قدیمی گزینهٔ include-transitive را نشناخت، از package manager محیط یا project.assets.json استفاده کن. خروجی diagnostic ممکن است مسیر خصوصی یا جزئیات محیط داشته باشد؛ پیش از انتشار آن را بازبینی کن.

If an older SDK does not recognise include-transitive, use the environment’s package manager or inspect project.assets.json. Diagnostic output may expose private paths or environment details; review it before sharing.

آزمایشگاه: restore قابل‌تکرار برای یک برنامهٔ کوچکLab: repeatable restore for a small app

یک پروژهٔ موقت بساز. هدف نصب packageهای زیاد نیست؛ می‌خواهیم declaration، graph، cache و lock file را از هم تشخیص بدهیم و ببینیم CI چطور از drift جلوگیری می‌کند.

Create a disposable project. The goal is not to install many packages; distinguish declarations, graph, cache, and lock file, then see how CI prevents drift.

Run dotnet restore and dotnet build separately, recording each result.

RestorePackagesWithLockFile را فعال کن، restore بزن و diff packages.lock.json را بخوان. یک dependency transitive را پیدا کن و بگو چرا در csproj اصلی ندیدی.Enable RestorePackagesWithLockFile, restore, and inspect the packages.lock.json diff. Find a transitive dependency and explain why it was absent from the original csproj.
  4. dotnet restore --locked-mode را اجرا کن. بعد نسخهٔ مستقیم را عمداً در csproj تغییر بده، locked restore را دوباره اجرا و خطای مورد انتظار را ثبت کن؛ سپس پروژه را به حالت سالم برگردان.Run dotnet restore --locked-mode. مدرک قبولی: build موفق پس از حذف obj، lock file ثبت‌شده، خطای موردانتظار در locked mode پس از تغییر declaration و گزارشی که direct، transitive، cache و source را درست به‌کار ببرد.

Evidence of completion: a successful build after removing obj, a recorded lock file, the expected locked-mode failure after changing a declaration, and a report that uses direct, transitive, cache, and source correctly.

تمرین‌ها: از خطای CI تا تصمیم restoreExercises: from a CI failure to a restore decision

برای هر مورد بگو چه می‌دانی و چه چیزی حدس است؛ بعد شاهد بعدی را انتخاب کن.

For each case, state what is known and what is still a guess; then choose the next evidence to collect.

۱) مستقیم یا transitive؟1) Direct or transitive?

کد از WebClient استفاده می‌کند اما csproj فقط Contoso.Client را نشان می‌دهد. dependency دیگر را کجا می‌یابی؟

Code uses WebClient, but csproj lists only Contoso.Client. Where do you find the other dependency?

راهنماHint

project.assets.json یا خروجی فهرست packageها را بررسی کن؛ ممکن است transitive باشد. namespace به‌تنهایی package ID را ثابت نمی‌کند.

Inspect project.assets.json or package-list output; it may be transitive. A namespace alone does not prove a package ID.

۲) package cache2) The package cache

package در cache هست ولی در csproj نیست. حذف آن از cache dependency برنامه را حذف می‌کند؟

A package is cached but absent from csproj. Does deleting it remove the app’s dependency?

پاسخAnswer

نه؛ cache فقط ذخیرهٔ محلی است. restore از declarationها graph را می‌سازد و در صورت نیاز package را دوباره دریافت می‌کند.

No. The cache is local storage. Restore builds the graph from declarations and downloads the package again if needed.

۳) assets گم شده3) Missing assets

build می‌گوید project.assets.json نیست. اولین اقدام کم‌خطر چیست؟

Build says project.assets.json is missing. What is the first low-risk action?

اقدامAction

از مسیر درست پروژه dotnet restore بزن یا build را برای restore ضمنی اجرا کن. فایل را دستی نساز؛ اگر خطا ماند source و TFM را بررسی کن.

Run dotnet restore from the correct project path or let build restore implicitly. Do not hand-create the file; inspect sources and TFM if it persists.

۴) نسخهٔ نهایی را پیدا کن4) Find the resolved version

PackageReference یک بازهٔ نسخه دارد. کدام مدرک نسخهٔ واقعی را نشان می‌دهد؟

PackageReference specifies a version range. Which evidence shows the resolved version?

پاسخAnswer

packages.lock.json در صورت فعال‌بودن و project.assets.json پس از restore. csproj declaration است، نه لزوماً graph نهایی.

Use packages.lock.json when enabled and project.assets.json after restore. csproj is the declaration, not necessarily the final graph.

۵) جلوگیری از drift در CI5) Prevent drift in CI

CI نباید lock file را بی‌صدا به‌روز کند. چه فرمانی اجرا می‌کنی؟

CI must not silently update the lock file. Which command do you run?

پاسخAnswer
CI restore
dotnet restore --locked-mode

اگر declaration و lock ناسازگار باشند، restore شکست می‌خورد تا تغییر بررسی شود.

If declarations and the lock disagree, restore fails so the change can be reviewed.

۶) کتابخانه و lock6) Library and lock

آیا lock file کتابخانه همیشه نسخهٔ نهایی برنامهٔ مصرف‌کننده را تعیین می‌کند؟

Does a library lock file always determine the final versions in a consuming app?

توضیحExplanation

نه؛ برنامهٔ آغازگر graph نهایی خودش را resolve می‌کند. lock کتابخانه جای lock برنامه را نمی‌گیرد.

No. The application at the start of the dependency chain resolves its final graph. The library lock does not replace the app lock.

۷) package در feed پیدا نمی‌شود7) Package missing from a feed

قبل از پاک‌کردن cache، دو شاهدی که می‌گیری چیست؟

What two pieces of evidence do you collect before clearing the cache?

بررسیInvestigation

sourceهای فعال و خروجی diagnostic restore را ببین؛ بعد URL، دسترسی، احراز هویت و package ID را بررسی کن.

Inspect active sources and diagnostic restore output; then check URL, access, authentication, and package ID.

۸) mapping ناقص8) Incomplete mapping

mapping فقط package مستقیم را پوشش می‌دهد و restore برای dependency آن fail شده. چرا؟

Mapping covers only the direct package, and restore fails for its dependency. Why?

توضیحExplanation

packageهای transitive هم باید به sourceهای مجاز نگاشت شوند؛ mapping فقط برای directها نیست.

Transitive packages also need mappings to allowed sources; mapping is not limited to direct dependencies.

۹) commit کردن obj9) Committing obj

همکارت می‌خواهد project.assets.json را commit کند تا CI restore نکند. ایراد چیست؟

A teammate wants to commit project.assets.json so CI skips restore. What is wrong?

پاسخAnswer

فایل تولیدی restore است، نه منبع حقیقت وابستگی‌ها. CI باید از declaration و lock restore کند.

It is generated restore output, not the source of truth. CI should restore from declarations and the lock.

۱۰) floating version10) Floating version

نسخهٔ 5.* چه اثری بر restoreهای بعدی دارد؟

How can 5.* affect later restores?

پاسخAnswer

نسخه‌های تازه‌تر مطابق بازه مجازند و resolve ممکن است تغییر کند. lock و locked mode graph فعلی را تثبیت می‌کنند، نه اینکه floating declaration را حذف کنند.

New matching versions are allowed, so resolution can change. A lock and locked mode preserve the current graph without removing the floating declaration.

۱۱) restore سبز، compile قرمز11) Restore green, compile red

آیا restore موفق سازگاری source code با API package را ثابت می‌کند؟

Does successful restore prove source compatibility with the package API?

توضیحExplanation

نه؛ restore graph و asset می‌سازد. compile و تست‌ها سازگاری API و رفتار را می‌سنجند؛ نسخهٔ حل‌شده و TFM را ثبت کن.

No; restore resolves a graph and assets. Compilation and tests check API and behaviour compatibility; record the resolved version and TFM.

۱۲) خطای دسترسی source12) Source access failure

CI خطای دسترسی به feed دارد. آیا --force اولین آزمایش است؟

CI cannot access a feed. Is --force the first experiment?

پاسخAnswer

نه معمولاً؛ --force credential، network یا URL را درست نمی‌کند. اول source و احراز هویت را بررسی کن.

Usually not; --force does not fix credentials, network, or URL. Inspect the source and authentication first.

۱۳) restore جداگانه13) Separate restore

چه زمانی restore را جدا از build اجرا می‌کنی؟

When would you run restore separately from build?

نمونهExample

برای عیب‌یابی feed/graph، locked-mode در CI یا جداکردن زمان dependency از compile. پس از restore می‌توان build را با --no-restore اجرا کرد.

For feed/graph diagnosis, locked-mode CI, or separating dependency time from compilation. After restore, build can use --no-restore.

۱۴) lock diff بزرگ است14) A large lock diff

یک dependency مستقیم عوض شده ولی ده‌ها خط lock تغییر کرده. چه چیزهایی را مقایسه می‌کنی؟

One direct dependency changed, but dozens of lock lines changed. What do you compare?

بازبینیReview

transitiveها، TFMها، SDK/restore و source را بررسی کن؛ lock کل graph را دارد. تغییر را با دلیل و تست تأیید کن.

Inspect transitives, TFMs, SDK/restore, and sources; the lock records the whole graph. Validate the change with rationale and tests.

۱۵) package داخلی و عمومی15) Internal and public package IDs

package ID داخلی روی nuget.org هم وجود دارد. چه قابلیتی source مجاز را هنگام restore محدود می‌کند و یک محدودیتش چیست؟

An internal package ID also exists on nuget.org. Which feature constrains its source during restore, and what is one limitation?

پاسخAnswer

۱۷) ارتقای عمدی package17) An intentional package upgrade

ترتیب امن به‌روزرسانی dependency و lock چیست؟

What is a safe sequence for updating a dependency and its lock?

ترتیبSequence

declaration را تغییر بده، restore عادی بزن، lock را بازبینی کن، build و تست بگیر و پروژه و lock را با هم commit کن؛ CI locked-mode بماند.

Change the declaration, run ordinary restore, review the lock, build and test, then commit project and lock together; keep CI in locked mode.

۱۸) incident را triage کن18) Triage the incident

CI می‌گوید dependency restore نمی‌شود؛ developer می‌گوید «NuGet خراب است». یک triage برای جداکردن source، lock، SDK و خطای دقیق طراحی کن.

CI cannot restore a dependency; a developer says “NuGet is broken.” Design a triage that separates source, lock, SDK, and exact error.

Classify the failure as authentication/network, package ID/version, lock drift, or incompatible TFM. Change one hypothesis and rerun the same command; “NuGet is broken” is not testable.

حالا build از روی شواهد بازتولید می‌شودNow the build can be repeated from evidence

csproj می‌گوید پروژه چه dependency مستقیمی می‌خواهد. restore وابستگی‌های transitive را هم حل می‌کند و asset مناسب را در project.assets.json می‌نویسد. cache فایل دانلودشده را نگه می‌دارد؛ lock file graph انتخاب‌شده را ثبت می‌کند. این‌ها نقش‌های متفاوت‌اند و جای هم را نمی‌گیرند.

csproj declares direct dependencies. Restore resolves transitive dependencies and writes selected assets to project.assets.json. The cache stores downloaded files; the lock records the selected graph. These have different roles and are not substitutes.

اگر CI package را نمی‌یابد، source و دسترسی را ببین. اگر locked mode رد می‌کند، declaration و lock را مقایسه کن. اگر compiler API نمی‌یابد، نسخهٔ حل‌شده و TFM را ببین. مرحله را از روی پیام جدا کن و شاهد همان مرحله را جمع کن؛ پاک‌کردن cache لازم نیست اولین واکنش باشد.

If CI cannot find a package, inspect source and access. If locked mode rejects restore, compare declarations and lock. If the compiler cannot find an API, inspect resolved version and TFM. Identify the failing stage and collect its evidence; clearing the cache need not be the first reaction.

در فصل بعد dependency graph حاضر است؛ حالا سؤال این است که dotnet build دقیقاً چه مراحلی را اجرا می‌کند و کدام artifact حاصل compile است. از restore به مسیر build می‌رویم، بدون اینکه مرز این دو را گم کنیم.

With the dependency graph ready, next we ask which stages dotnet build runs and which artifacts come from compilation. We will follow the build path without blurring it with restore.
