حافظهٔ مدیریت‌شده؛ GC چه چیزی را آزاد می‌کند؟

Managed memory: what does the GC release?

سرویس بعد از چند ساعت حافظهٔ بیشتری گرفته است. یک نفر می‌گوید «GC خراب است» و دیگری می‌خواهد هرجا شد GC.Collect() بزند. قبل از هر دو کار، ببینیم کدام شیء هنوز زنده است، چه چیزی مرتب allocation می‌کند و آیا اصلاً بحث ما حافظه است یا منبعی مثل فایل و socket.

A service uses more memory after running for hours. One person blames the GC; another wants to call GC.Collect() everywhere. Before either response, find which objects remain alive, what keeps allocating, and whether the resource is memory or something like a file or socket.

حافظه بالا رفته؛ ولی هنوز علت را نمی‌دانیمMemory rose, but we do not know why yet

در .NET، اشیای managed روی heap قرار می‌گیرند و GC بر اساس دسترسی‌پذیری آن‌ها تصمیم می‌گیرد چه حافظه‌ای را پس بگیرد. «دیگر به این شیء احتیاج ندارم» برای ما کافی نیست؛ اگر از یک ریشه هنوز قابل‌دسترسی باشد، از نگاه runtime زنده است.

In .NET, managed objects live on the heap and the GC reclaims memory based on reachability. “I no longer need this object” is not enough: if it is still reachable from a root, the runtime considers it alive.

GC دربارهٔ reachability حافظهٔ managed تصمیم می‌گیرد؛ مالکیت فایل و اتصال شبکه را با الگوی dispose روشن کن.

The GC reasons about managed-memory reachability. Release owned files and network connections through disposal.

این‌که شیء از نظر برنامه قابل‌استفاده نیست ولی هنوز root آن را نگه داشته، یک علت رایج رشد heap است. علت دیگر allocation زیاد در هر درخواست است که حتی اگر اشیا بعداً جمع شوند، فشار و کار GC ایجاد می‌کند. این دو را از نگه‌داشتن منبع unmanaged جدا کن.

An object that is logically obsolete but still reachable is a common reason for heap growth. Another is excessive per-request allocation, which creates GC work even when objects are later reclaimed. Distinguish both from an unmanaged resource that must be released.

نسل‌ها یک فرض عملی‌اند، نه قول دربارهٔ عمر شیءGenerations are a working assumption, not a lifetime promise

GC نسل‌های ۰، ۱ و ۲ را برای تمرکز جمع‌آوری بر اشیایی به‌کار می‌برد که معمولاً عمرهای متفاوت دارند: اشیای کوتاه‌عمر اغلب زودتر می‌میرند و اشیای ماندگارتر ممکن است به نسل‌های بالاتر برسند. این یک راهبرد runtime است، نه قراردادی که برنامه بتواند زمان دقیق جمع‌آوری را از آن نتیجه بگیرد.

The GC uses generations 0, 1, and 2 to focus collection on objects with commonly different lifetimes: short-lived objects often die sooner, while longer-lived objects may be promoted. This is a runtime strategy, not a contract from which an application can predict exact collection times.

مقایسهٔ دو snapshot بدون یک workload مشابه می‌تواند گمراه‌کننده باشد. برای هر بررسی، اندازهٔ heap، زمان نمونه، بار درخواست و رخداد GC را کنار هم ثبت کن. «حافظه بعد از درخواست صفر نشد» به‌تنهایی leak نیست؛ runtime ممکن است حافظه را برای استفادهٔ بعد نگه دارد.

Comparing snapshots under different workloads can mislead. Record heap size, sample time, request load, and GC events together. “Memory did not return to zero after a request” is not proof of a leak; the runtime may retain memory for reuse.

GC جای Dispose را نمی‌گیردThe GC does not replace Dispose

GC حافظهٔ managed را پس می‌گیرد؛ اما فایل، stream، socket، connection و handleهای سیستم‌عامل منابع محدود بیرونی‌اند. هر نوع خودش ممکن است finalizer داشته باشد، ولی زمان اجرای آن قابل‌پیش‌بینی نیست. اگر مالک منبع هستی، الگوی IDisposable و using را برای آزادسازی قطعی به‌کار ببر.

The GC reclaims managed memory, but files, streams, sockets, connections, and operating-system handles are finite external resources. A type may have a finalizer, but its timing is nondeterministic. If you own the resource, use IDisposable and using for deterministic release.

عمر منبع را محدود کن
await using var stream = File.OpenRead(path);
var result = await JsonSerializer.DeserializeAsync<Payload>(stream, cancellationToken: ct);

برای typeهای async-disposable از await using استفاده کن. مالکیت را روشن نگه دار: کسی که resource را می‌سازد یا دریافت می‌کند باید بداند چه کسی آن را می‌بندد. هم‌زمان GC.Collect() را به‌عنوان راه‌حل عمومی فراخوانی نکن؛ معمولاً اندازه‌گیری و اصلاح lifetime/allocation درست‌تر است.

Use await using for async-disposable types. Make ownership explicit: the code that creates or receives a resource must know who closes it. Do not call GC.Collect() as a general fix; measure and correct lifetime or allocation instead.

قبل از بهینه‌سازی، یک خط مبنا بسازEstablish a baseline before optimizing

سناریوی تکرارپذیر تعریف کن: تعداد درخواست ثابت، مدت مشخص، نسخهٔ یکسان. allocation rate، heap پس از GC، latency و نرخ خطا را اندازه بگیر. اگر فقط حافظهٔ process را ببینی، نمی‌فهمی اشیا زنده‌اند یا runtime فضای آزاد را برای رشد بعدی نگه داشته است.

Define a reproducible scenario: fixed request count, known duration, same version. Measure allocation rate, post-GC heap, latency, and error rate. Process memory alone cannot tell whether objects remain live or the runtime retains free space for later use.

اندازه‌گیری به‌جای حدس
dotnet-counters monitor --process-id 1234
dotnet-trace collect --process-id 1234 --duration 00:00:20 --output allocation.nettrace

اسم و موجودبودن counterها را با نسخهٔ runtime بررسی کن. اگر ابزار نشان داد allocation بالاست، allocationهای پرتکرار را پیدا کن؛ اگر heap زنده رشد می‌کند، ریشه‌های ارجاع را دنبال کن. تنظیمات GC را برای پنهان‌کردن علامت قبل از فهم علت تغییر نده.

Verify counter names and availability for the runtime version. If allocation is high, find repeated allocations; if live heap grows, inspect reference roots. Do not change GC settings to hide a symptom before understanding its cause.

سه برداشت اشتباه که diagnosis را خراب می‌کندThree assumptions that derail diagnosis

یک: هر رشد حافظه leak است. دو: با GC دستی فوراً حافظه به سیستم‌عامل برمی‌گردد. سه: چون GC داریم، دیگر لازم نیست فایل و connection را ببندیم. هر سه غلط‌اند. ابتدا مشخص کن «حافظهٔ managed زنده»، «فضای heap نگه‌داشته‌شده» یا «منبع بیرونی بسته‌نشده» را اندازه گرفته‌ای.

First, every memory increase is a leak. Second, forcing GC immediately returns memory to the OS. Third, a GC means files and connections need no disposal. All are wrong. Determine whether you measured live managed objects, retained heap space, or an undisposed external resource.

LOH و جمع‌آوری اجباری نسخهٔ جادویی ندارندThere is no magic LOH or forced-collection switch

Large Object Heap و compaction رفتارهای تخصصی runtime هستند. آن‌ها را فقط با شاهد و روی workload واقعی بررسی کن. force کردن collection می‌تواند مکث بسازد و الگوی عادی برنامه را عوض کند.

The Large Object Heap and compaction are runtime details. Investigate them only with evidence under a representative workload. Forced collection can introduce pauses and change normal application behaviour.

اول بدان چه چیزی رشد می‌کندFirst identify what is growing

GC حافظهٔ managed غیرقابل‌دسترسی را جمع می‌کند، نه هر چیزی را که ما از نظر ذهنی «دیگر لازم نداریم». allocation زیاد با leak فرق دارد؛ نگه‌داشتن heap با object زنده فرق دارد؛ فایل باز با managed memory فرق دارد. شاهد متناسب بگیر، مالکیت resource را روشن کن و بعد همان workload را برای اثبات بهبود تکرار کن.

The GC reclaims unreachable managed memory, not everything we consider “no longer needed.” High allocation differs from a leak; retained heap differs from live objects; an open file differs from managed memory. Collect relevant evidence, clarify resource ownership, and repeat the workload to verify improvement.
