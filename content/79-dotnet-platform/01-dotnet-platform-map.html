نقشهٔ پلتفرم .NET

The .NET platform map

کد C# را بلدی؛ احتمالاً قبلاً هم `dotnet run` زده‌ای. اما وقتی یک همکار می‌گوید «SDK نصب است» و برنامه باز اجرا نمی‌شود، این جمله به‌تنهایی جواب نیست. بیایید ببینیم هر تکهٔ .NET چه مسئولیتی دارد و از کدام خروجی می‌شود درباره‌اش حرف زد.

You know C# and have probably run `dotnet run`. But when a teammate says “the SDK is installed” and the application still will not start, that sentence is not enough. Let’s map each part of .NET to its responsibility and the evidence that tells us about it.

«SDK دارم» دقیقاً چه چیزی را ثابت می‌کند؟What does “I have the SDK” actually prove?

تیم CodeNames Shop یک ابزار خط فرمان کوچک تحویل داده. روی سیستم سازنده اجرا می‌شود؛ روی ماشین همکار، پیغام می‌گوید نسخهٔ لازم برای اجرا پیدا نشد. همکار می‌گوید: «ولی .NET نصب است!» قبل از نصب‌مجدد یا پاک‌کردن packageها، باید سؤال دقیق‌تری بپرسیم: کدام بخش .NET نصب است، و برنامه دقیقاً کدام بخش را لازم دارد؟

The CodeNames Shop team delivered a small command-line tool. It runs on the developer’s machine, but a teammate’s machine reports that the required version for execution is missing. “But .NET is installed!” Before reinstalling everything or clearing packages, ask a sharper question: which part of .NET is installed, and which part does this app require?

در دورهٔ C# مسیر کلی source تا اجرای برنامه را دیدیم. اینجا همان تصویر را از سمت عملیات باز می‌کنیم: SDK، runtime و کتابخانه‌ها را روی همین سیستم پیدا می‌کنیم و می‌فهمیم هر خروجی چه ادعایی را پشتیبانی می‌کند. هنوز وارد جزئیات build، انتخاب runtime یا فایل‌های publish نمی‌شویم؛ آن‌ها مسئله‌های فصل‌های بعدند.

The C# course introduced the broad path from source to execution. Here we inspect that map operationally: locate the SDK, runtime, and libraries on this machine, then decide which claims each output supports. We will not yet unpack build internals, runtime selection, or publish files; those are later problems.

یک جمله، چند مسئولیتOne name, several responsibilities

وقتی می‌گوییم «.NET نصب است»، ممکن است منظورمان ابزار ساخت، runtime اجرای برنامه، یا هر دو باشد. نصب SDK معمولاً runtime متناظر را هم همراه دارد، اما این دو واژه هم‌معنی نیستند و وجودشان را باید جدا بررسی کرد.

“.NET is installed” might mean the build tools, an application runtime, or both. Installing an SDK commonly brings a corresponding runtime, but the terms are not synonyms, and their presence should be checked separately.

چه کسی می‌سازد و چه کسی اجرا می‌کند؟Who builds, and who runs?

فرض کن از روی پروژه، یک برنامه می‌خواهی. `dotnet` در خط فرمان نقطهٔ ورود کار توست؛ SDK مجموعهٔ ابزارهای توسعه است و کارهایی مثل هماهنگ‌کردن build، فراخوانی compiler و کار با dependencyها را ممکن می‌کند. compiler کد C# را به assembly تبدیل می‌کند. خروجی build خودِ SDK نیست؛ artifact برنامه است.

Suppose you want to produce an application from a project. `dotnet` is your command-line entry point; the SDK is the development toolset that enables work such as coordinating a build, invoking the compiler, and handling dependencies. The compiler turns C# source into an assembly. The build output is an application artifact, not the SDK itself.

runtime برنامه را اجرا می‌کند و کتابخانه‌های پایه قابلیت‌هایی مثل رشته، فایل و JSON را در اختیار برنامه می‌گذارند. بعضی کتابخانه‌ها همراه shared framework می‌آیند و بعضی dependencyها از NuGet وارد پروژه می‌شوند؛ همهٔ packageها بخشی از runtime نیستند. جزئیات assembly و dependency resolution را در فصل ۸ باز می‌کنیم.

The runtime executes the app, while libraries provide capabilities such as strings, files, and JSON. Some libraries come with a shared framework; other dependencies enter through NuGet. Not every package is part of the runtime. Chapter 8 examines assemblies and dependency resolution.

SDK و runtime را جای هم ننشانDo not substitute SDK for runtime

روی ماشین توسعه معمولاً SDK لازم است. برای اجرای یک برنامهٔ framework-dependent روی سرور ممکن است runtime کافی باشد و اصلاً compiler لازم نباشد. برعکس، runtime به‌تنهایی `dotnet build` را برایت انجام نمی‌دهد. مدل‌های انتشار و نیاز مقصد را در فصل ۱۳ با artifact واقعی می‌سنجیم.

A development machine usually needs the SDK. A server running a framework-dependent app may need only the runtime and no compiler. Conversely, the runtime alone does not perform `dotnet build`. Chapter 13 will test deployment modes and target requirements using real artifacts.

به‌جای حدس، نصب همین سیستم را فهرست کنInventory this machine instead of guessing

بیایید ببینیم روی ماشینی که الان با آن کار می‌کنی چه چیزی نصب است. این فرمان‌ها چیزی نصب یا حذف نمی‌کنند؛ فقط از driver دات‌نت می‌خواهند اطلاعات محیط، SDKها و runtimeها را گزارش کند.

Let’s inspect what is installed on the machine you are using. These commands install and remove nothing; they ask the .NET driver to report environment information, SDKs, and runtimes.

PowerShell، Bash یا ترمینال
dotnet --info
dotnet --list-sdks
dotnet --list-runtimes

در این محیط نمونه، بخش‌های مهم خروجی شبیه این‌اند؛ شمارهٔ نسخه و مسیر روی سیستم تو ممکن است فرق کند:

On this sample machine, the important output looks like this; versions and paths may differ on yours:

`--list-sdks` نسخه‌های SDK قابل‌مشاهده برای همین معماری را نشان می‌دهد. `--list-runtimes` فهرست shared frameworkهای نصب‌شده را می‌دهد؛ اینجا `Microsoft.NETCore.App` و `Microsoft.AspNetCore.App` دو نام جدا هستند. `--version` می‌گوید فرمان‌های CLI در این پوشه کدام SDK را انتخاب کرده‌اند؛ وجود چند SDK به معنی اجرای هم‌زمان همهٔ آن‌ها نیست.

`--list-sdks` shows SDK versions visible to this installation and architecture. `--list-runtimes` lists installed shared frameworks; here `Microsoft.NETCore.App` and `Microsoft.AspNetCore.App` are distinct names. `--version` reports which SDK the CLI selected in this directory; having several SDKs does not mean they all run at once.

`dotnet --info` اطلاعات گسترده‌تری مثل نسخهٔ host، معماری و مسیر پایه می‌دهد. اگر CI روی x64 اجرا می‌شود ولی خروجی این فرمان از dotnet معماری دیگری آمده، فهرست SDKها را با محیط درست مقایسه نکرده‌ای. در .NET 10 گزینهٔ `--arch` برای درخواست فهرست معماری مشخص هم وجود دارد؛ فعلاً همان خروجی پیش‌فرض را با معماری فرمانی که اجرا کرده‌ای تفسیر کن.

`dotnet --info` reports more, including the host version, architecture, and base path. If CI runs x64 but this output came from a different-architecture `dotnet`, you have not compared the right SDK inventory. .NET 10 also supports `--arch` for requesting a specific architecture; for now, interpret the default list in the context of the `dotnet` executable you ran.

سه برداشت عجولانه را همین‌جا کنار بگذاریمThree premature conclusions to avoid

اگر SDK 10 در فهرست هست، فقط می‌دانیم SDK این نصب آن را گزارش کرده. هنوز از آن نمی‌فهمیم پروژهٔ موردنظر به چه targetی ساخته شده یا روی ماشین مقصد runtime سازگار دارد. این را باید از فایل پروژه و خطای واقعی اجرای همان artifact پیدا کنیم؛ نه با حدس از روی یک فهرست.

If SDK 10 appears in the list, we know only that this installation reports it. We still do not know the target of a particular project or whether the destination has a compatible runtime. Inspect the project and the actual artifact’s startup error rather than inferring from one list.

اگر `Microsoft.NETCore.App` نصب است، این به‌تنهایی معنی «همهٔ .NET نصب است» نمی‌دهد. یک برنامهٔ desktop یا ASP.NET ممکن است shared framework دیگری بخواهد. این دوره APIهای آن frameworkها را آموزش نمی‌دهد؛ فقط می‌خواهیم نام چیزی را که واقعاً نصب شده با نیاز برنامه اشتباه نگیریم.

Seeing `Microsoft.NETCore.App` does not mean “all of .NET is installed.” A desktop or ASP.NET application may require a different shared framework. This course does not teach those app-stack APIs; it teaches us not to confuse an installed framework’s name with the app’s actual requirement.

و اگر `dotnet --info` موفق شد، ثابت شده همین driver توانسته اطلاعات محیط را چاپ کند. ثابت نشده پروژه restore یا build شده، process برنامه بالا آمده، یا سرویس پاسخ می‌دهد. برای هر ادعا باید شاهد همان مرحله را بگیریم.

If `dotnet --info` succeeds, we have proved that this driver could report environment information. We have not proved that a project restored or built, that its process started, or that a service responds. Each claim needs evidence from that stage.

قبل از نصب‌کردن، مسیر خرابی را پیدا کنLocate the failing boundary before installing anything

خطای `dotnet` موقع اجرای فرمان CLI با پیغام runtime موقع شروع یک فایل برنامه یک مسئله نیست. اول عین فرمان و عین پیام را نگه دار؛ بعد بپرس شکست در انتخاب SDK، restore/build، یا شروع برنامه رخ داده. فصل‌های بعد برای هر مرز مدرک مخصوص خودش را می‌سازند.

A failure in a `dotnet` CLI command is not the same problem as a runtime error while starting an application file. Preserve the exact command and message first; then locate whether the failure happened during SDK selection, restore/build, or application startup. Later chapters gather evidence for each boundary.

۱) دو فهرست، دو سؤال1) Two lists, two questions

`dotnet --list-sdks` و `dotnet --list-runtimes` را اجرا کن. یک نسخه را که فقط در یکی از فهرست‌ها آمده ثبت کن و بگو از آن چه می‌فهمی و چه چیزی را هنوز نمی‌فهمی.

Run `dotnet --list-sdks` and `dotnet --list-runtimes`. Record one version that appears in only one list and state what that tells you—and what it does not.

یک گزارش ممکنOne possible report

در محیط نمونه، SDKهای 8.0.416 و 10.0.101 دیده شدند؛ runtimeهای .NET شامل 6.0.36، 8.0.22 و 10.0.0/10.0.1 بودند. این دو فهرست انواع نصب متفاوت را نشان می‌دهند. از اختلافشان نمی‌شود target یک پروژهٔ خاص را حدس زد؛ باید فایل پروژه یا نیاز artifact را دید.

The sample machine reports SDKs 8.0.416 and 10.0.101, and .NET runtimes 6.0.36, 8.0.22, and 10.0.0/10.0.1. The lists describe different installed components. Their difference does not reveal a particular project’s target; inspect its project file or artifact requirements.

۲) معماری host را گزارش کن2) Report the host architecture

`dotnet --info` را اجرا کن و OS، معماری و base path را در گزارش محیطت بیاور. چرا این سه مورد برای مقایسهٔ لپ‌تاپ و CI مهم‌اند؟

Run `dotnet --info` and record the OS, architecture, and base path. Why do these matter when comparing a laptop with CI?

پاسخ با شاهدEvidence-based answer

این بخش‌ها نشان می‌دهند کدام نصب dotnet و کدام معماری را بررسی کرده‌ای. اگر CI روی Linux x64 است و خروجی لپ‌تاپ Windows x64، فهرست‌ها مستقیماً قابل جایگزینی نیستند. این گزارش هنوز نمی‌گوید artifact برای کدام RID ساخته شده؛ آن را در فصل ۶ بررسی می‌کنیم.

These fields identify the `dotnet` installation and architecture you inspected. If CI is Linux x64 and your laptop is Windows x64, the inventories are not interchangeable. This report does not tell you the artifact’s RID; Chapter 6 investigates that.

۳) SDK انتخاب‌شده را پیدا کن3) Find the selected SDK

`dotnet --version` را از پوشهٔ فعلی اجرا کن و همان را در پوشهٔ یک پروژهٔ دیگر هم اجرا کن. اگر دو مقدار فرق داشتند، قبل از تغییر فایل‌ها چه چیزی را باید ثبت کنی؟

Run `dotnet --version` in the current directory and in another project directory. If the values differ, what should you record before changing files?

یک مسیر تشخیصA diagnostic path

فرمان نسخهٔ SDK انتخاب‌شده را گزارش می‌کند. مسیر پوشه، خروجی هر دو فرمان و وجود `global.json` در مسیر والد را ثبت کن؛ فایل انتخاب SDK در فصل ۱۵ عمیق‌تر می‌آید. هنوز نتیجه نگیر یک پروژه خراب است، چون SDK متفاوت انتخاب شده ممکن است عمدی باشد.

The command reports the selected SDK version. Record both working directories, outputs, and whether a parent path contains `global.json`; SDK selection is covered more deeply in Chapter 15. Do not yet call a project broken—choosing different SDKs may be intentional.

۴) runtime را با اسم کاملش بخوان4) Read the runtime’s full name

از `dotnet --list-runtimes` دست‌کم دو نام framework را رونویسی کن. چرا گزارش «نسخهٔ 10 دارم» برای تشخیص ماشین مقصد کافی نیست؟

Copy at least two framework names from `dotnet --list-runtimes`. Why is “I have version 10” insufficient for diagnosing a target machine?

پاسخ و دلیلSolution and reasoning

ممکن است فهرست `Microsoft.NETCore.App 10.0.1` و `Microsoft.AspNetCore.App 10.0.1` داشته باشد؛ این دو shared framework نام‌های متفاوت دارند. برنامه باید با framework موردنیازش تطبیق داده شود. این هنوز چیزی دربارهٔ native dependency یا معماری artifact نمی‌گوید.

The list may contain both `Microsoft.NETCore.App 10.0.1` and `Microsoft.AspNetCore.App 10.0.1`; they are distinct shared frameworks. Match the app’s requirement to the needed framework. This still says nothing about native dependencies or the artifact’s architecture.

۵) روی ماشین توسعه چه چیزی لازم داری؟5) What does a development machine need?

برای هم‌تیمی تازه‌وارد، از خروجی `dotnet --list-sdks` و `--list-runtimes` یک چک پیش‌پرواز بنویس. مشخص کن کدام مقدارها prerequisite توسعه‌اند و چرا فهرست runtime به‌تنهایی کافی نیست.

Write a preflight check for a new teammate using `dotnet --list-sdks` and `--list-runtimes`. Identify the development prerequisite and explain why the runtime list alone is insufficient.

نمونهٔ چکSample check

برای build از SDK سازگار با target پروژه شروع کن؛ فهرست runtime نشان می‌دهد اجرای shared framework چه نسخه‌هایی حاضرند، نه اینکه compiler و ابزار build حاضرند. target واقعی را از پروژه می‌خوانیم؛ شمارهٔ نصب هم‌تیمی را نباید از روی این فصل حدس زد.

Start with an SDK compatible with the project target for building; the runtime list shows which shared frameworks are present, not whether the compiler and build tools exist. Read the actual project target rather than guessing a teammate’s required version from this chapter.

۶) روی سرور فقط اجرا لازم است؟6) Does a server need only execution support?

تیمت می‌خواهد یک برنامه را روی سروری اجرا کند و build در CI انجام می‌شود. با `dotnet --list-runtimes` و `dotnet --info` روی سرور شواهد جمع کن و یک نیاز را که هنوز از خروجی نمی‌توان تعیین کرد، نام ببر.

Your team builds an app in CI and wants to run it on a server. Gather evidence there with `dotnet --list-runtimes` and `dotnet --info` and name one requirement the output cannot determine.

پاسخ مهندسیEngineering answer

برای اجرای framework-dependent، runtime سازگار لازم است و معمولاً compiler لازم نیست. خروجی نمونه: `Microsoft.NETCore.App 10.0.1` در فهرست. این سطر حضور runtime را نشان می‌دهد، اما مدل انتشار، target framework، architecture و native dependency را ثابت نمی‌کند. artifact و خطای واقعی شروع را هم باید بررسی کرد.

A framework-dependent deployment needs a compatible runtime and usually no compiler. The inventory can show installed runtimes, but does not establish the publish mode, target framework, architecture, or native dependencies. Inspect the artifact and its actual startup result too.

۷) مرز compiler کجاست؟7) Where is the compiler boundary?

اگر `dotnet --list-sdks` خالی است ولی runtime فهرست می‌شود، یک خط تشخیص برای همکارت بنویس و با همان دو فرمان شاهد بگذار. آیا این خروجی می‌گوید فایل برنامه اجرا نمی‌شود؟

If `dotnet --list-sdks` is empty but runtimes are listed, write a one-line diagnosis for your teammate and cite both commands. Does this prove the app cannot run?

تشخیص کوتاهShort diagnosis

«runtime نصب است، اما این نصب SDK گزارش نمی‌کند؛ بنابراین ابزار build را از runtime نتیجه نگیر.» برنامهٔ framework-dependent هنوز ممکن است اجرا شود. معماری و نسخهٔ runtime لازم را با artifact تطبیق بده؛ خالی‌بودن SDK به‌تنهایی آن را رد نمی‌کند.

“A runtime is installed, but this installation reports no SDK; do not infer build tools from a runtime.” A framework-dependent app may still run. Match architecture and required runtime to the artifact; an absent SDK alone does not rule it out.

۸) artifact با ابزار توسعه یکی نیست8) An artifact is not a development tool

در پروژهٔ کنسولی‌ای که قبلاً از دورهٔ C# ساخته‌ای، فایل DLL یا executable را در پوشهٔ خروجی پیدا کن و مسیرش را کنار خروجی `dotnet --info` ثبت کن. کدام‌یک artifact برنامه است و کدام‌یک ابزار ماشین؟

In a console project you previously built in the C# course, locate the DLL or executable in its output folder and record its path beside `dotnet --info`. Which is the app artifact, and which is a machine tool?

روش تفکیکHow to distinguish them

برای نمونه، `OrderProbe.dll` در `bin/Debug/net10.0/` artifact است، اما مسیر SDK در `dotnet --info` مثل `C:\Program Files\dotnet\sdk\10.0.101\` به ابزار ماشین اشاره می‌کند و ابزار ساخت است. مسیرها را از خروجی `dotnet --info` و فهرست فایل‌ها ثبت کن. وجود DLL به‌تنهایی نمی‌گوید مقصد runtime لازم را دارد.

The app file belongs to the project or delivered artifact; the SDK lives under the `dotnet` installation path and is a build tool. Record paths from `dotnet --info` and a file listing. A DLL’s presence does not prove the target has the required runtime.

۹) shared framework را تشخیص بده9) Identify a shared framework

خروجی `dotnet --list-runtimes` را برای `Microsoft.NETCore.App` و `Microsoft.AspNetCore.App` فیلتر کن. یک توضیح به همکار بده که چرا اسم framework بخشی از تشخیص است.

Filter `dotnet --list-runtimes` for `Microsoft.NETCore.App` and `Microsoft.AspNetCore.App`. Explain to a teammate why the framework name matters diagnostically.

پاسخ و مرز آنAnswer and its boundary

هر سطر نام و نسخهٔ یک shared framework را گزارش می‌کند. نیاز برنامه باید با نام و نسخهٔ لازم مقایسه شود؛ عدد نسخه به‌تنهایی کافی نیست. این تمرین برنامهٔ ASP.NET یا API آن را آموزش نمی‌دهد و فقط فهرست runtime را می‌خواند.

Each line reports a shared framework name and version. Compare the app’s requirement with both; a version number alone is insufficient. This does not teach ASP.NET or its APIs—it only reads the runtime inventory.

۱۰) چند نسخه یعنی چند انتخاب؟10) Do multiple versions mean multiple selections?

اگر دو SDK در فهرست هستند، `dotnet --version` را اجرا کن و خروجی را کنار فهرست بنویس. چه چیزی انتخاب شده و چه چیزی فقط نصب است؟

If two SDKs are listed, run `dotnet --version` and record it beside the inventory. What is selected, and what is merely installed?

تفسیرInterpretation

فهرست نشان‌دهندهٔ نسخه‌های نصب‌شده است؛ `--version` نسخهٔ انتخاب‌شده برای CLI در این directory را نشان می‌دهد. انتخاب ممکن است به تنظیمات مسیر وابسته باشد؛ فصل ۱۵ رفتار `global.json` را بررسی می‌کند. این عدد runtime انتخابی برنامه نیست.

The list shows installed versions; `--version` reports the SDK selected for the CLI in this directory. Selection can depend on path configuration; Chapter 15 examines `global.json`. This number is not the app’s selected runtime.

۱۱) ادعای «روی همه‌جا اجرا می‌شود» را محدود کن11) Bound the claim “it runs everywhere”

با `dotnet --info` محیط خودت را ثبت کن. از روی همین خروجی، جملهٔ «این artifact روی همهٔ سیستم‌ها اجرا می‌شود» را بازنویسی کن تا فقط چیزی را بگوید که شاهد ثابت می‌کند.

Record your environment with `dotnet --info`. Rewrite “this artifact runs everywhere” so it claims only what the evidence supports.

یک جملهٔ دقیق‌ترA more precise statement

«این نصب dotnet روی این سیستم، host و معماری گزارش‌شده را دارد.» این خروجی هنوز دربارهٔ artifact، target، dependency native یا مقصد دیگری چیزی ثابت نمی‌کند. برای portability باید artifact را روی مقصد مشخص آزمایش کنیم.

“This `dotnet` installation reports the host and architecture shown on this system.” It proves nothing yet about the artifact, its target, native dependencies, or another machine. Test portability on a defined target.

۱۲) کدام خروجی به کدام سؤال؟12) Which output answers which question?

برای سه سؤال «چه SDK نصب است؟»، «چه runtime نصب است؟»، «host از کجا اجرا می‌شود؟» فرمان مناسب را بنویس و هر سه را اجرا کن. یک سؤال را هم مشخص کن که این فرمان‌ها پاسخ نمی‌دهند.

Choose and run commands for “Which SDK is installed?”, “Which runtime is installed?”, and “Where is the host running from?” Name one question they do not answer.

فرمان‌ها و تفسیرCommands and interpretation
CLI
dotnet --list-sdks
dotnet --list-runtimes
dotnet --info

دو فهرست اول به ترتیب SDK و runtime را نشان می‌دهند؛ `--info` جزئیات نصب و host را می‌دهد. هیچ‌کدام صحت business logic، status سرویس یا وجود runtime روی سرور دیگری را ثابت نمی‌کند.

The first two lists report SDKs and runtimes; `--info` adds installation and host details. None proves business logic, service status, or runtime availability on a different server.

۱۳) یک runtime قدیمی را بیش‌ازحد تفسیر نکن13) Do not over-interpret an older runtime

اگر مقصد فقط `Microsoft.NETCore.App 8.0.x` دارد و همکار می‌گوید برنامه روی net10.0 ساخته شده، خروجی `--list-runtimes` را نگه دار و سؤال بعدی‌ات را بنویس. آیا می‌توانی از همین فهرست نتیجه بگیری اجرای آن حتماً ممکن است؟

If the target lists only `Microsoft.NETCore.App 8.0.x` and the teammate says the app targets net10.0, preserve the runtime output and write your next question. Can you conclude from this list that it will run?

قدم تشخیصی بعدیNext diagnostic step

نه. باید target و publish mode را از پروژه/artifact بپرسی و خطای دقیق startup را بگیری. برای framework-dependent ممکن است runtime سازگار لازم باشد؛ self-contained رفتار دیگری دارد. لیست runtime یک شاهد مهم است، اما بدون دانستن artifact پاسخ نهایی نیست.

No. Ask for the target and publish mode from the project or artifact, then capture the exact startup error. A framework-dependent app may need a compatible runtime; self-contained output behaves differently. The runtime list is useful evidence, not a final answer without the artifact context.

۱۴) تفاوت SDK و runtime را با دو فرمان ثابت کن14) Prove the SDK/runtime distinction with two commands

برای هم‌تیمی‌ای که می‌گوید «runtime دارم، پس می‌توانم build کنم»، دو فرمانی بنویس که ادعا را می‌آزمایند. خروجی مورد انتظار و محدودیت هر شاهد را ضمیمه کن.

For a teammate who says “I have the runtime, so I can build,” choose two commands to test that claim. Include expected evidence and each command’s limitation.

گزارش تشخیصDiagnostic report

`dotnet --list-sdks` و `dotnet --list-runtimes` را جدا اجرا کن. اگر runtime هست و SDK نیست، اجرای بعضی artifactها ممکن است اما build از این نصب پشتیبانی نمی‌شود. فهرست‌ها به‌تنهایی نشان نمی‌دهند compiler دیگری در PATH هست یا ابزار خارجی نصب شده.

Run `dotnet --list-sdks` and `dotnet --list-runtimes` separately. With a runtime but no SDK, some artifacts may run while this installation cannot build projects. The lists do not rule out another compiler on PATH or external build tools.

۱۵) خروجی خالی را هم تفسیر کن15) Interpret an empty result too

روی یک ماشین آزمایشی یا با خروجی نمونهٔ گزارش، حالت خالی‌بودن `dotnet --list-runtimes` را تحلیل کن. پیش از نصب runtime چه دو بررسی‌ای انجام می‌دهی؟ سیستم اصلی را دست‌کاری نکن.

On a test machine or with a sample report, analyze an empty `dotnet --list-runtimes` result. What two checks would you make before installing a runtime? Do not alter your main system.

بررسی امنSafe checks

اول مطمئن شو همان dotnet و معماری درست را اجرا کرده‌ای (`where.exe dotnet` در Windows یا `which dotnet` در Unix)، بعد خروجی `dotnet --info` و مسیر host را ببین. خروجی خالی می‌تواند نشانهٔ نصب ناقص یا بررسی نصب دیگری باشد؛ بدون تشخیص، بسته‌ای را پاک یا نصب نکن.

First confirm you ran the intended `dotnet` and architecture (`where.exe dotnet` on Windows or `which dotnet` on Unix), then inspect `dotnet --info` and the host path. An empty list may indicate an incomplete install or a different installation; do not remove or install packages before diagnosing it.

۱۶) گزارش نصب را برای همکار بازتولیدپذیر کن16) Make an installation report reproducible

سه فرمان این فصل را پشت‌سرهم اجرا و خروجی را در یک فایل متنی ذخیره کن. زمان، سیستم‌عامل، معماری و پوشهٔ جاری را هم بنویس تا نفر بعد بداند گزارش مربوط به کدام محیط است.

Run the three commands from this chapter and save the output to a text file. Include the time, OS, architecture, and working directory so another person knows which environment the report describes.

نمونهٔ قالب گزارشSample report shape

گزارش باید عین خروجی `dotnet --info`، فهرست SDK و runtime، و زمینهٔ اجرای فرمان را داشته باشد. مسیرهای شخصی یا نام کاربری را قبل از اشتراک‌گذاری بررسی کن. این گزارش محیط را توصیف می‌کند، نه نتیجهٔ build یا اجرای برنامه را.

Include the exact `dotnet --info` output, SDK and runtime lists, and command context. Review personal paths or usernames before sharing. The report describes an environment, not a build or application run result.

۱۷) پیام را در مرز درست دسته‌بندی کن17) Classify the message at the right boundary

از یک همکار بخواه عین فرمان و پیام خطای `dotnet` را بفرستد. آن‌ها را کنار `dotnet --info` بگذار و بگو فعلاً شواهد به کدام مرز اشاره می‌کنند: پیدا نشدن CLI، کمبود SDK، یا startup برنامه؟

Ask a teammate for the exact `dotnet` command and error. Compare them with `dotnet --info` and say which boundary the evidence currently points to: missing CLI, missing SDK, or application startup.

روش، نه حدسA method, not a guess

اگر shell خود فرمان را پیدا نمی‌کند، بررسی PATH و host مقدم است؛ اگر فرمان build درخواست شده و SDK نیست، فهرست SDK مهم است؛ اگر فایل برنامه اجرا شده و runtime پیام ناسازگاری می‌دهد، باید artifact و runtime مقصد را تطبیق داد. بدون متن واقعی خطا، این دسته‌بندی هنوز فرضیه است.

If the shell cannot find the command, inspect PATH and the host first; if a build was requested and no SDK is present, the SDK list matters; if an app file starts and reports a runtime mismatch, compare the artifact with the target runtime. Without the actual message, this classification remains a hypothesis.

۱۸) پاسخ رخداد را با مدرک تحویل بده18) Hand off an evidence-based incident response

ماشین همکارت برنامه را اجرا نمی‌کند. یک گزارش کوتاه بساز که شامل فرمان‌های لازم، خروجی‌های SDK/runtime، نام و نسخهٔ target موردنیاز (اگر می‌دانی)، و یک سؤال بی‌پاسخ باشد. به‌جای «دات‌نت خرابه»، نتیجه‌گیری محدود و قابل‌بررسی بنویس.

Your teammate’s machine will not run the app. Create a short report with the commands to run, SDK/runtime output, the required target name and version if known, and one unresolved question. Replace “.NET is broken” with a bounded, testable conclusion.

نمونهٔ handoffSample handoff

«روی Windows x64، `dotnet --list-runtimes` فقط `Microsoft.NETCore.App 8.0.22` را گزارش می‌کند. هنوز target و publish mode برنامه را نداریم؛ لطفاً فایل runtimeconfig یا خروجی publish و متن کامل خطای startup را بفرست.» این گزارش شاهد و مجهول را جدا می‌کند؛ هنوز علت قطعی اعلام نمی‌کند.

“On Windows x64, `dotnet --list-runtimes` reports only `Microsoft.NETCore.App 8.0.22`. We do not yet know the app’s target or publish mode; please send its runtimeconfig or publish output and the full startup error.” This separates evidence from unknowns rather than declaring a root cause.

  2. From a directory where you can identify a C# project, run `dotnet --info` and record the OS, architecture, host version, and base path in `environment-report.txt`.
  3. `dotnet --list-sdks` و `dotnet --list-runtimes` را جداگانه به گزارش اضافه کن. نسخه‌ها را حذف یا مرتب‌سازی مجدد نکن؛ می‌خواهیم خروجی خام قابل‌مقایسه بماند.
  4. Add `dotnet --list-sdks` and `dotnet --list-runtimes` separately. Do not remove or reorder versions; keep the raw output comparable.
  5. از روی شواهد دو جمله بنویس: «این ماشین برای توسعه چه ابزارهایی گزارش می‌کند؟» و «برای اجرای کدام shared frameworkها شاهد داریم؟» اگر target برنامه را نمی‌دانی، صریحاً نامعلوم بگذار.

معیار بررسی گزارشReport review criteria

گزارش خوب command و زمینهٔ اجرا را دارد، SDK را از runtime جدا می‌کند، frameworkها را با نام کامل می‌نویسد و نسخه را به‌جای target پروژه نمی‌نشاند. برای CI، همان سه فرمان را روی عامل واقعی یا image واقعی اجرا کن؛ حدس دربارهٔ نصبش کافی نیست. گزارش نصب هم تضمین نمی‌کند build یا برنامه موفق شود؛ مرحلهٔ بعد باید با همان پروژه آزمایش شود.

A good report includes commands and execution context, separates SDKs from runtimes, uses full framework names, and does not substitute an installed version for the project target. For CI, run the same commands on the actual agent or image; guessing its installation is not enough. An inventory does not guarantee a successful build or run—the next stage must test the actual project.
