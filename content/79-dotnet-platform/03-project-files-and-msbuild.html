فایل پروژه و MSBuild

Project files and MSBuild

`dotnet build` سبز شده، اما معلوم نیست چرا این فایل وارد خروجی شد، چرا `Release` با `Debug` فرق دارد، یا target سفارشی تیم کجا اجرا می‌شود. بیایید به‌جای حدس، همان فایلی را باز کنیم که به build شکل می‌دهد: `.csproj`.

`dotnet build` is green, but we do not know why a file entered the output, how `Release` differs from `Debug`, or where the team’s custom target runs. Instead of guessing, let’s open the file that shapes the build: the `.csproj`.

یک build موفق، چند سؤال بازA successful build still leaves questions

در فصل قبل دیدیم `dotnet build` پشت صحنه به چند مرحله تکیه می‌کند. حالا تصور کن برنامه درست build می‌شود، ولی فایل `settings.json` در خروجی نیست. یک نفر می‌گوید «فایل را کنار exe کپی کن»، یکی دیگر پیشنهاد می‌دهد پوشهٔ `obj` را پاک کنیم. هیچ‌کدام هنوز علت را پیدا نکرده‌اند.

In the previous chapter, we saw that `dotnet build` relies on several stages behind the scenes. Now imagine the app builds, but `settings.json` is missing from the output. One teammate says “copy it beside the executable”; another suggests deleting `obj`. Neither has found the cause yet.

فایل پروژه فقط فهرست تنظیمات برنامه نیست. این فایل ورودی MSBuild است: مشخص می‌کند پروژه چه هدفی دارد، چه چیزهایی ورودی build هستند و چه کارهایی در چه مرحله‌ای انجام شوند. بخشی از رفتار هم از فایل‌هایی می‌آید که SDK به‌طور ضمنی وارد می‌کند؛ بنابراین `.csproj` کوتاه است، اما build نهایی از چند فایل و چند تصمیم ساخته می‌شود.

A project file is more than a list of app settings. It is an MSBuild input: it describes the project’s target, the inputs to the build, and work to run at particular stages. Some behaviour also comes from files the SDK imports implicitly. The `.csproj` may be short, while the final build is shaped by several files and decisions.

امروز چه چیزی را ثابت می‌کنیم؟What will we prove today?

قرار نیست کل زبان MSBuild را حفظ کنیم. یک property را تغییر می‌دهیم، یک item را وارد خروجی می‌کنیم، و یک target را به نقطهٔ درست build وصل می‌کنیم. هر بار اثر را با خروجی یا فایل تولیدشده می‌سنجیم.

We are not going to memorise the whole MSBuild language. We will change a property, include an item in output, and attach a target to the right point in the build. Each time, we will verify the effect through output or a generated file.

اول ببین SDK-style واقعاً چه‌قدر کوتاه استFirst, see how small an SDK-style project can be

با همان پروژهٔ کنسولی سادهٔ فصل ۲ کار می‌کنیم. در `.csproj` دنبال یک فهرست بلند از همهٔ فایل‌های C# نگرد؛ در پروژه‌های SDK-style، فایل‌های source معمولاً با الگوهای پیش‌فرض پیدا می‌شوند. خود SDK هم targetها و taskهای لازم برای build را فراهم می‌کند.

We will use the same small console project from Chapter 2. Do not expect a long list of every C# file in its `.csproj`; SDK-style projects usually discover source files through default patterns. The SDK also supplies the targets and tasks needed to build.

نمونهٔ فایل پروژه · Shop.Cli.csproj
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>

خط `Sdk="Microsoft.NET.Sdk"` مثل یک shorthand است. هنگام ارزیابی، MSBuild فایل‌های `Sdk.props` و `Sdk.targets` را در ابتدا و انتهای پروژه وارد می‌کند. پس این فایل کوچک جای همهٔ تنظیمات SDK را نگرفته؛ دارد به SDK می‌گوید پروژه را با قواعد خودش گسترش بدهد.

`Sdk="Microsoft.NET.Sdk"` is shorthand. During evaluation, MSBuild brings in `Sdk.props` near the beginning and `Sdk.targets` near the end. This small file has not replaced all SDK configuration; it asks the SDK to expand the project using its rules.

پروژهٔ گسترش‌یافته، بیرون از پوشهٔ پروژه
dotnet msbuild Shop.Cli.csproj -preprocess:../expanded.xml

فایل `expanded.xml` یک نمای تشخیصی از پروژه و importهاست؛ build اجرا نمی‌شود. داخلش دنبال `Sdk.props`، `Sdk.targets` و محل تعریف یک خاصیت بگرد. فایل بزرگ می‌شود، چون بخش زیادی از آن متعلق به SDK است؛ این خروجی را برای فهم مرزها باز می‌کنیم، نه اینکه دستی ویرایشش کنیم.

`expanded.xml` is a diagnostic view of the project and its imports; no build is run. Search it for `Sdk.props`, `Sdk.targets`, and where a property is defined. It becomes large because much of it belongs to the SDK. Use it to understand boundaries, never as a file to edit.

Property مقدار می‌دهد؛ item ورودی معرفی می‌کندA property carries a value; an item declares an input

در فایل پروژه، `PropertyGroup` معمولاً مقدارهای تکی مثل target framework یا نام assembly را نگه می‌دارد. با `$(PropertyName)` به مقدار اشاره می‌کنی. `ItemGroup` مجموعه‌ای از ورودی‌های نوع‌دار می‌سازد؛ مثلاً فایل‌های `Compile` یا `None`. با `@(Compile)` می‌توان از فهرست itemها در taskها استفاده کرد.

In a project file, `PropertyGroup` usually holds scalar values such as the target framework or assembly name. Reference one with `$(PropertyName)`. `ItemGroup` creates typed collections of inputs, such as `Compile` or `None` files. Tasks can use the item list through `@(Compile)`.

برای اینکه `settings.json` در خروجی کپی شود، فقط اسم فایل را به‌صورت property اضافه نمی‌کنیم. آن فایل یک item از نوع `None` است و metadata رفتار کپی را تنظیم می‌کند:

To copy `settings.json` to the output, we do not add its filename as a property. It is a `None` item, and metadata controls its copy behaviour:

تغییر کنترل‌شده در Shop.Cli.csproj
<ItemGroup>
  <None Update="settings.json">
    <CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>
  </None>
</ItemGroup>

`Update` یک item موجود را تغییر می‌دهد؛ اینجا به‌خاطر الگوهای پیش‌فرض SDK، فایل از قبل به‌عنوان `None` شناخته شده است. اگر فایل واقعاً در فهرست نبود، `Update` آن را از هیچ نمی‌سازد و باید علت را جدا پیدا کنی. بعد build کن و خود فایل را بررسی کن:

`Update` modifies an existing item; here the SDK’s default patterns already classify the file as `None`. If the file was not in the collection, `Update` would not create it from nothing, so investigate that separately. Build, then inspect the file itself:

شاهد مورد انتظار
dotnet build
Test-Path .\bin\Debug\net10.0\settings.json
True

`True` نشان می‌دهد فایل در مسیر خروجی مورد انتظار هست؛ هنوز ثابت نمی‌کند برنامه آن را از همان مسیر می‌خواند یا محتوایش معتبر است. این دو ادعای جدا، آزمایش خودشان را می‌خواهند.

`True` proves the file exists at the expected output path; it does not prove that the app reads from that path or that the contents are valid. Those are separate claims and need separate tests.

ارزیابی با اجرای کار یکی نیستEvaluation is not the same as doing the work

MSBuild ابتدا فایل پروژه و importها را ارزیابی می‌کند: propertyها، itemها و شرط‌ها را می‌خواند و مدل build را می‌سازد. بعد، برای target درخواستی مثل `Build`، targetهای وابسته را پیدا می‌کند و taskها را اجرا می‌کند. ارزیابی عمدتاً پاسخ می‌دهد «چه چیزی قرار است وجود داشته باشد؟»؛ اجرا پاسخ می‌دهد «چه کاری واقعاً انجام شد؟».

MSBuild first evaluates the project and its imports: it reads properties, items, and conditions to form a build model. It then finds the targets required for a request such as `Build` and executes their tasks. Evaluation mostly answers “what is configured to exist?”; execution answers “what work actually ran?”

این تفاوت یک خطای رایج را توضیح می‌دهد: اگر شرط یک `ItemGroup` در زمان ارزیابی false باشد، آن فایل اصلاً وارد آن فهرست نمی‌شود. اگر شرط یک `Target` هنگام اجرا false باشد، target انتخاب شده اما بدنه‌اش اجرا نمی‌شود. جملهٔ «فایل هست، پس باید کپی شود» بدون دیدن item و target، نتیجه‌گیری زودهنگام است.

This distinction explains a common mistake: if an `ItemGroup` condition is false during evaluation, that file never enters the collection. If a target’s condition is false at execution time, the target was selected but its body did not run. “The file exists, so it must be copied” is premature without inspecting the item and target.

Configuration و itemهای ارزیابی‌شده را بپرس
dotnet msbuild Shop.Cli.csproj -getProperty:Configuration,TargetFramework,OutputPath
dotnet msbuild Shop.Cli.csproj -getItem:Compile,None

در SDK 10 این پرس‌وجوها می‌توانند مقدار property و itemهای ارزیابی‌شده را به شکل JSON نشان دهند. خروجی را به‌عنوان تصویر لحظه‌ای همین پروژه و همین invocation بخوان؛ با عوض‌کردن `-p:Configuration=Release`، پروژه یا import، پاسخ هم عوض می‌شود. فهرست item به‌تنهایی تضمین نمی‌کند target مربوط به آن اجرا شده باشد.

With SDK 10, these queries can report evaluated properties and items as JSON. Treat the output as a snapshot of this project and invocation; changing `-p:Configuration=Release`, the project, or an import can change it. An item list alone does not prove that a target using it ran.

شرط‌ها به جایگاه بستگی دارندConditions depend on where they appear

شرطی مثل `Condition="'$(Configuration)' == 'Release'"` در `PropertyGroup` سطح پروژه هنگام ارزیابی آن قسمت بررسی می‌شود؛ شرط روی task داخل target وقتی target اجرا می‌شود. اگر property قبل از خط شرط هنوز مقدار نگرفته باشد، ممکن است رشتهٔ خالی شود و شرط خلاف انتظار دربیاید. جای تعریف را در expanded project و مقدار نهایی را در log بررسی کن.

A condition such as `Condition="'$(Configuration)' == 'Release'"` on a top-level `PropertyGroup` is checked while that part is evaluated; a condition on a task inside a target is checked when the target runs. If a property has not been set before the condition, it can expand to an empty string and behave unexpectedly. Check its location in the expanded project and its final value in the log.

یک مقدار را فقط برای همین build عوض کن
dotnet build -c Release -p:BuildLabel=release-check

`-p:` مقدار MSBuild property را برای این invocation می‌فرستد. این تغییر دائمی در `.csproj` نیست. اگر source یا target از `BuildLabel` استفاده نکرده باشد، دیدن موفقیت build هم به معنی اثرکردن label نیست؛ مقدار را با `-getProperty:BuildLabel` یا پیام target مشاهده کن.

`-p:` passes an MSBuild property value for this invocation. It does not permanently edit the `.csproj`. If no source or target consumes `BuildLabel`, a successful build does not mean the label had an effect; inspect it with `-getProperty:BuildLabel` or a target message.

وقتی چند پروژه یک قاعده دارندWhen several projects share a rule

اگر سه پروژه در یک repository همگی باید هشدارها را سخت‌گیرانه‌تر بگیرند یا metadata نسخهٔ مشترک داشته باشند، کپی‌کردن همان `PropertyGroup` در سه `.csproj` کم‌کم دردسر می‌شود. `Directory.Build.props` و `Directory.Build.targets` امکان تنظیم در سطح پوشه را می‌دهند؛ اولی زودتر وارد می‌شود، دومی دیرتر.

If three projects in one repository need stricter warnings or shared version metadata, copying the same `PropertyGroup` into three `.csproj` files becomes tedious. `Directory.Build.props` and `Directory.Build.targets` allow folder-level customization: the former is imported earlier, the latter later.

MSBuild از محل پروژه رو به پوشه‌های والد جست‌وجو می‌کند و در حالت معمول نزدیک‌ترین `Directory.Build.props` را پیدا می‌کند؛ فرض نکن همهٔ فایل‌های هم‌نام در تمام والدها خودکار با هم ادغام می‌شوند. در Linux بزرگی و کوچکی حروف مهم است، پس نام فایل را دقیق بنویس. فایل‌های آزمایش را در یک پوشهٔ موقت بساز، نه ریشهٔ پروژهٔ CodeNames؛ وگرنه ممکن است ناخواسته buildهای دیگر را هم تغییر بدهی.

MSBuild searches from the project toward parent directories and normally uses the nearest `Directory.Build.props`; do not assume every same-named file in every ancestor is automatically merged. On Linux, filename casing matters. Create experiment files in a temporary folder, not the CodeNames repository root, or you could change unrelated builds.

یک target کوچک، با نقطهٔ اتصال روشنA small target with an explicit hook

تیم می‌خواهد بعد از build نام پروژه و مسیر خروجی را در log ببیند. یک target سفارشی می‌تواند taskهایی مثل `Message` را اجرا کند. target خودش «تابعی نیست که هر وقت تعریف شد اجرا شود»؛ باید مستقیم درخواست شود یا به dependency/نقطهٔ اتصال یک target دیگر وصل شود.

The team wants the build log to show the project name and output path. A custom target can run tasks such as `Message`. A target is not “a function that runs just because it was defined”; it must be requested directly or connected to another target’s dependency or hook.

در آزمایشگاه موقت: Directory.Build.targets
<Project>
  <Target Name="ReportBuildIdentity" AfterTargets="Build">
    <Message Importance="high"
             Text="Built $(MSBuildProjectName) in $(Configuration); output=$(TargetPath)" />
  </Target>
</Project>

حالا `dotnet build -c Release` را اجرا کن. باید بعد از خط مسیر assembly پیام `Built ... in Release` را ببینی. `AfterTargets="Build"` می‌گوید target پس از هدف Build اجرا شود؛ خود target پایه همچنان مسئول compile است. `TargetPath` مقدار مسیری است که SDK برای assembly خروجی محاسبه کرده، نه لزوماً کل پوشهٔ publish.

Run `dotnet build -c Release`. After the assembly path, you should see a `Built ... in Release` message. `AfterTargets="Build"` hooks this target after `Build`; the original target still owns compilation. `TargetPath` is the path the SDK calculated for the output assembly, not necessarily a publish directory.

خروجی نمونه از SDK 10 · مسیر ماشین فرق می‌کند
Shop.Cli -> ...\bin\Release\net10.0\Shop.Cli.dll
Built Shop.Cli in Release; output=...\bin\Release\net10.0\Shop.Cli.dll

اگر پیام target را دیدی، می‌دانیم این build به نقطهٔ اتصال رسیده و propertyها در task گسترش یافته‌اند. هنوز اثبات نمی‌کند فایل‌های دیگری وارد publish شده‌اند یا مقصد نهایی برنامه درست است؛ برای آن‌ها خروجی همان مرحله را بررسی کن.

Seeing the target message tells us this build reached the hook and expanded the properties in the task. It does not prove that other files entered publish output or that a deployment destination is correct; inspect the output of those stages separately.

هدف تعریف شده، اما پیامش هیچ‌وقت نمی‌آیدThe target is defined, but its message never appears

بیایید یک typo واقعی بسازیم: `AfterTargets="Buid"` را به‌جای `Build` بنویس. build ممکن است همچنان موفق شود، اما پیام گزارش ناپدید می‌شود. این یک سرنخ است: شکست compile نداریم؛ احتمالاً hook اشتباه است یا شرط target برقرار نشده.

Let’s introduce a real typo: write `AfterTargets="Buid"` instead of `Build`. The build may still succeed, but the report message disappears. That is a clue: compilation did not fail; perhaps the hook is wrong or the target condition was false.

فرمان تشخیصی؛ binlog در پوشهٔ فعلی
dotnet build -c Release -bl:broken-hook.binlog -v:normal

اول خود فایل `Directory.Build.targets` را بخوان و املای `AfterTargets` را با نام target واقعی مقایسه کن. بعد binlog را با یک Structured Log Viewer باز کن و در درخت targetها دنبال `ReportBuildIdentity` بگرد. اگر اصلاً اجرا نشده، سراغ task Message نرو؛ مسئله در انتخاب target یا hook است. binlog می‌تواند importها، targetهای اجراشده و پیام‌ها را نشان بدهد، اما خودش علت را به زبان ساده تشخیص نمی‌دهد.

First inspect `Directory.Build.targets` and compare the `AfterTargets` spelling with the real target name. Then open the binlog in a Structured Log Viewer and search the target tree for `ReportBuildIdentity`. If it never ran, do not debug the `Message` task yet; the issue is target selection or the hook. A binlog can expose imports, executed targets, and messages, but it does not diagnose the cause in plain language.

حالا hook را به `Build` برگردان و همان فرمان را دوباره اجرا کن. اگر پیام برگشت، قبل و بعد از اصلاح یکسان آزمایش کرده‌ای و علت را جدا کرده‌ای. اگر target اجرا می‌شود ولی مقدار output خالی است، آن‌وقت property یا ترتیب import را بررسی کن؛ هر علامت، مرز بررسی متفاوتی دارد.

Restore the hook to `Build` and run the same command again. If the message returns, you have repeated the same test before and after the fix. If the target runs but the output value is empty, inspect the property or import order instead; each symptom points to a different boundary.

binlog را عمومی منتشر نکنDo not publish a binlog casually

binary log می‌تواند متن فایل‌های importشده و مقدار propertyها را در خود داشته باشد. پیش از به‌اشتراک‌گذاری برای همکار یا پیوست‌کردن به issue، secret، مسیر خصوصی و اطلاعات حساس را بررسی کن. برای build کوچک، فقط وقتی لازم است بسازش؛ در پروژهٔ بزرگ هم اندازه و هزینهٔ ثبت را در نظر بگیر.

A binary log can contain imported project text and property values. Before sharing it with a teammate or attaching it to an issue, check for secrets, private paths, and sensitive data. For a small build, create one only when useful; for a large build, consider its size and logging overhead.

آزمایشگاه: بفهمیم فایل پروژه چه قولی دادهLab: find out what the project actually promises

یک نسخهٔ کپی از پروژهٔ CLI فصل قبل بساز یا یک پروژهٔ کنسولی موقت با `dotnet new console --framework net10.0` ایجاد کن. تمام فایل‌های `Directory.Build.*` و target خراب را فقط همان‌جا بساز؛ آزمایش قرار نیست تنظیمات repository اصلی را تغییر بدهد.

Copy the Chapter 2 CLI project or create a disposable console project with `dotnet new console --framework net10.0`. Create every `Directory.Build.*` file and the broken target there only; this experiment must not alter the main repository.

  1. خط پایه: `dotnet build` را اجرا کن و مسیر output را یادداشت کن. بعد `dotnet msbuild -getProperty:TargetFramework,Configuration,OutputPath` بزن. propertyها با همان مسیر هماهنگ‌اند؟Baseline: run `dotnet build` and note the output path. Then run `dotnet msbuild -getProperty:TargetFramework,Configuration,OutputPath`. Do the properties match that path?
  2. در ریشهٔ موقت `Directory.Build.props` بساز و یک property بی‌خطر مثل `Company` تعریف کن. با `-getProperty:Company` ثابت کن فایل دیده شده؛ بعد پروژهٔ دیگری را در زیرپوشه بساز و دامنهٔ اثر را بررسی کن.Create a `Directory.Build.props` at the temporary root and define a harmless property such as `Company`. تمرین‌ها: از XML تا مدرک buildExercises: from XML to build evidence

همهٔ تمرین‌ها را در همان پروژهٔ موقت انجام بده. هر پاسخ باید یک مدرک داشته باشد: خروجی فرمان، فایل ساخته‌شده یا بخشی از log. هیچ‌کدام به تغییر پروژهٔ اصلی نیاز ندارند.

شاهد و دلیلEvidence and reasoning

dotnet msbuild Shop.Cli.csproj -getItem:Compile

اولی مقدار property را برمی‌گرداند؛ دومی مجموعه‌ای از itemها را. اگر `Program.cs` در Compile دیده شد، فقط عضویت آن در مدل ارزیابی‌شده ثابت شده، نه اینکه compiler بدون خطا اجرا شده باشد.

۲) چرا فایل source در csproj فهرست نشده؟2) Why is the source file absent from the csproj?

تفسیرInterpretation

An SDK-style project uses default source-file patterns, so a file can be an item without an explicit Include line in the csproj. Its defining-project path in the SDK or project is a clue. A removed or excluded file would produce a different result.

۳) configuration واقعاً عوض شده؟3) Did the configuration actually change?

The first is usually `Debug` with a path containing `bin\Debug\`; the second reports `Release` and `bin\Release\`. This proves the configuration reached evaluation; no build artifact has been produced yet.

۴) یک property محلی اضافه کن4) Add a local project property

۵) تنظیم فقط برای Release5) A setting for Release only

یک property به نام `BuildLabel` اضافه کن که فقط وقتی Configuration برابر Release است مقدار `ship-check` بگیرد. هر دو configuration را با `-getProperty` امتحان کن.

Add a `BuildLabel` property that is set to `ship-check` only when Configuration is Release. Query it under both configurations.

  <BuildLabel>ship-check</BuildLabel>
</PropertyGroup>

با Debug ممکن است property خالی باشد و با Release مقدار داشته باشد. این آزمایش جای شرط را می‌سنجد؛ اگر Configuration پیش از این گروه مقداردهی نشده باشد، شرط می‌تواند نتیجهٔ دیگری بدهد. مقدار واقعی را query کن، حدس نزن.

Under Debug the property may be empty, while Release has a value. This tests the condition’s placement; if Configuration has not been assigned before this group, the condition can behave differently. Query the actual value instead of guessing.

۶) item را ببین، بعد کپی را ثابت کن6) Inspect an item, then prove it was copied

`settings.json` را بساز، آن را با `None Update` و `PreserveNewest` تنظیم کن. قبل از build خروجی `-getItem:None` و بعد از build نتیجهٔ `Test-Path` را نگه دار.

Create `settings.json` and configure it using `None Update` and `PreserveNewest`. Keep `-getItem:None` before build and `Test-Path` after build.

دو مدرک، دو ادعاTwo pieces of evidence, two claims

item query عضویت و metadata را نشان می‌دهد؛ وجود فایل در `bin` اثر target کپی را. اگر item query درست است ولی فایل نیست، configuration/path و log اجرای target را بررسی کن. نتیجهٔ مثبت هم فقط وجود فایل را ثابت می‌کند، نه خوانده‌شدنش توسط برنامه.

The item query shows membership and metadata; the file in `bin` proves the copy target’s effect. If the item is correct but the file is absent, inspect configuration/path and target execution logs. A positive result proves existence, not that the app reads it.

۷) property را از command line تزریق کن7) Pass a property from the command line

یک target آزمایشی بساز که `$(BuildLabel)` را چاپ کند. بدون `-p` و با `-p:BuildLabel=from-cli` build بگیر و دو log را مقایسه کن.

Create a test target that prints `$(BuildLabel)`. Build without `-p` and with `-p:BuildLabel=from-cli`, then compare both logs.

تفسیر درستCorrect interpretation

پیام دوم باید `from-cli` را نشان بدهد؛ این مقدار به همان invocation تعلق دارد. برای invocation بعدی دوباره باید آن را بدهی یا در فایل پروژه تعریفش کنی. موفقیت build بدون پیام مصرف‌کننده، به‌تنهایی اثر property را ثابت نمی‌کند.

The second message should show `from-cli`; that value belongs to the invocation. Supply it again next time or define it in a project file. A successful build without a consumer message does not prove the property had an effect.

۸) import پنهان را پیدا کن8) Find an implicit import

`dotnet msbuild -preprocess:expanded.xml` اجرا کن و در فایل به دنبال `Sdk.props`، `Sdk.targets` و `Microsoft.NET.Sdk.DefaultItems.props` بگرد. نام فایل و اطراف تعریف Compile را یادداشت کن.

Run `dotnet msbuild -preprocess:expanded.xml` and search the file for `Sdk.props`, `Sdk.targets`, and `Microsoft.NET.Sdk.DefaultItems.props`. Record the filenames around the Compile definition.

چرا فایل گسترش‌یافته بزرگ است؟Why is the expanded file large?

SDK shorthand importهای زیادی را به مدل پروژه اضافه می‌کند؛ فایل preprocess نسخهٔ گسترش‌یافته را بدون اجرای build نشان می‌دهد. این فایل ابزار فهم ترتیب و منشأ تنظیم‌هاست، نه نسخه‌ای که باید مستقیماً تغییر بدهی.

The SDK shorthand adds many imports to the project model; preprocess shows the expanded form without running a build. It is a tool for understanding order and provenance, not a file to edit directly.

۹) فرق ارزیابی و اجرا را با مدرک توضیح بده9) Prove the difference between evaluation and execution

یک item را با `-getItem` نشان بده، اما targetی که از آن استفاده می‌کند را به hook اشتباه وصل کن. build را اجرا کن و توضیح بده چرا «item دیده شد» با «کار target انجام شد» یکی نیست.

Show an item with `-getItem`, but attach the target that consumes it to the wrong hook. Run the build and explain why “the item exists” differs from “the target did its work.”

مدل پاسخReasoning

`-getItem` مدل ارزیابی را گزارش می‌کند؛ hook نادرست مانع اجرای target می‌شود. اگر artifact تولید نشده، binlog را برای target اجراشده و پیام task بررسی کن. این دو شاهد مرحله‌های متفاوتی را پوشش می‌دهند.

`-getItem` reports the evaluated model; a wrong hook prevents the target from running. If the artifact is absent, inspect the binlog for the executed target and task message. These pieces of evidence cover different stages.

۱۰) یک target گزارش‌گر بساز10) Build a reporting target

در `Directory.Build.targets` targetی بساز که پس از Build نام پروژه، configuration و `TargetPath` را چاپ کند. در Debug و Release اجرا کن و log را تحویل بده.

In `Directory.Build.targets`, create a target that prints project name, configuration, and `TargetPath` after Build. Run it in Debug and Release and keep the logs.

چرا این نقطهٔ اتصال؟Why this hook?

`AfterTargets="Build"` گزارش را پس از هدف Build اجرا می‌کند؛ `$(Configuration)` و `$(TargetPath)` در پیام جایگزین می‌شوند. مسیر output در دو configuration متفاوت است. این گزارش فقط خروجی build را می‌گوید، نه publish را.

`AfterTargets="Build"` runs the report after Build; `$(Configuration)` and `$(TargetPath)` are expanded in the message. Output paths differ between configurations. This report describes build output, not publish.

۱۱) hook خراب را از روی نشانه تشخیص بده11) Diagnose a broken hook from its symptom

نام hook را عمداً `Buid` بنویس. اگر build موفق است ولی پیام target نمی‌آید، log معمولی و binlog را بررسی کن. پیش از اصلاح، بنویس آیا مشکل در compile است یا انتخاب target.

Deliberately write the hook as `Buid`. If build succeeds but the target message is absent, inspect the normal log and binlog. Before fixing it, state whether the failure is in compilation or target selection.

تشخیص و repairDiagnosis and repair

نبودن پیام همراه build موفق یعنی هنوز مدرکی از اجرای target نداریم؛ compile به‌تنهایی مسئله نیست. `Buid` را به `Build` اصلاح کن، همان فرمان را دوباره بزن و برگشت پیام را ثابت کن. اگر همچنان غایب بود، شرط و import را هم بررسی کن.

A missing message with a successful build means we lack evidence that the target ran; compilation is not the issue by itself. Change `Buid` to `Build`, rerun the same command, and prove the message returned. If it is still absent, inspect the condition and import too.

۱۲) یک property مشترک، دو پروژه12) One shared property, two projects

دو پروژه در یک پوشهٔ موقت بساز و یک `Directory.Build.props` در والدشان قرار بده که `Company` را تعیین کند. از هر دو مسیر `-getProperty:Company` اجرا کن و بعد یکی را بیرون آن درخت بساز.

Create two projects under a temporary parent and place one `Directory.Build.props` there to set `Company`. Query the property from both, then create a third project outside that tree.

دامنه را از خروجی بخوانRead the scope from output

دو پروژهٔ زیرشاخه باید مقدار مشترک را ببینند؛ پروژهٔ بیرونی معمولاً نمی‌بیند. این نتیجه از ساختار پوشه و جست‌وجوی فایل می‌آید، نه از نام course یا solution. برای چند سطح import، رفتار را با preprocess بررسی کن.

The two child projects should see the shared value; the outside project normally will not. This follows the directory tree and file search, not a course or solution name. For multi-level imports, inspect the behaviour with preprocess.

۱۳) چرا props مقدار مورد انتظار را ندید؟13) Why did props miss the value?

در `Directory.Build.props` شرطی بنویس که `$(TargetFramework)` را بررسی کند، سپس مقدارش را در project هم تنظیم کن. در `-getProperty` و expanded file دنبال ترتیب اثر بگرد.

In `Directory.Build.props`, add a condition that checks `$(TargetFramework)`, then set the property in the project too. Use `-getProperty` and the expanded file to inspect the order.

نکتهٔ ترتیبOrdering matters

`Directory.Build.props` زود وارد می‌شود؛ در نقطه‌ای که شرط ارزیابی شده ممکن است TargetFramework هنوز مقدار نگرفته باشد. برای قاعده‌ای که به مقدار نهایی پروژه وابسته است، زمان/محل مناسب‌تری مثل target یا props مخصوصاً طراحی‌شده انتخاب کن. فقط منتقل‌کردن خط بدون دیدن مقدار نهایی کافی نیست.

`Directory.Build.props` is imported early; TargetFramework may not yet have a value where the condition is evaluated. For a rule that depends on the project’s final value, choose a more suitable location or timing, such as a target or deliberately designed props. Moving a line without checking the final value is not enough.

۱۴) Condition فقط برای Release14) A condition for Release only

در `Directory.Build.targets` پیامی قرار بده که فقط وقتی `Configuration` برابر Release است چاپ شود. یک بار Debug و یک بار Release build بگیر و هر دو log را نگه دار.

Add a message in `Directory.Build.targets` that appears only when Configuration is Release. Build once in Debug and once in Release, keeping both logs.

چه چیزی ثابت شد؟What did you prove?

پیام فقط در Release نشان می‌دهد شرط task یا target در زمان اجرا ارزیابی شده و configuration آن invocation درست رسیده. این ثابت نمی‌کند خود اسمبلی رفتار متفاوتی دارد؛ برای آن باید artifact یا رفتار برنامه را مقایسه کنی.

A message only in Release shows that the task or target condition was evaluated at execution time and received that invocation’s configuration. It does not prove the assembly behaves differently; compare the artifact or app behaviour for that.

۱۵) یک binlog بساز و رازهایش را بررسی کن15) Create a binlog and inspect its contents

برای build موقت `-bl:inspect.binlog` اضافه کن و در viewer نام target گزارش‌گر را جست‌وجو کن. پیش از به‌اشتراک‌گذاری فایل، propertyها و importهای ثبت‌شده را از نظر دادهٔ حساس بازبینی کن.

Add `-bl:inspect.binlog` to a disposable build and search for the reporting target in a viewer. Before sharing it, review recorded properties and imports for sensitive data.

ارزش و محدودیت binlogBinlog value and limits

binlog جزئیات رویدادها، targetها، taskها و importها را برای بررسی ساختاری ذخیره می‌کند. می‌تواند نشان دهد target اجرا شده یا property کجا تغییر کرده؛ تفسیر درست همچنان با توست. فایل ممکن است اطلاعات داخلی پروژه داشته باشد، پس آن را مثل خروجی عمومی منتشر نکن.

A binlog stores build events, targets, tasks, and imports for structured inspection. It can show whether a target ran or where a property changed; interpretation is still your job. It may contain internal project information, so do not publish it as a public artifact.

۱۶) خروجی diagnostic را کوچک نگه دار16) Keep diagnostic output focused

یک build را با verbosity عادی و یکی را با `-v:diag` بگیر؛ تعداد تقریبی خط‌ها را مقایسه کن و برای هرکدام یک پرسش تشخیصی مناسب بنویس.

Build once with normal verbosity and once with `-v:diag`; compare approximate line counts and write one suitable diagnostic question for each.

چه وقت کدام؟When to use each?

خروجی عادی برای فهم نتیجهٔ کلی مناسب است؛ diagnostic برای دنبال‌کردن جزئیات و مقدارها. حجم زیاد ممکن است سرنخ اصلی را دفن کند، پس پرسش مشخص داشته باش و در صورت نیاز binlog را در viewer فیلتر کن. verbosity بیشتر به‌تنهایی علت را معلوم نمی‌کند.

Normal output is useful for the overall result; diagnostic verbosity exposes detailed steps and values. A large log can bury the clue, so start with a specific question and filter a binlog if needed. More verbosity alone does not identify the cause.

۱۷) imported target را از پروژهٔ خودت جدا کن17) Separate an imported target from your own project

در expanded project محل تعریف `Build` و `ReportBuildIdentity` را پیدا کن. برای هرکدام `DefiningProjectFullPath` یا comment اطراف import را ثبت کن.

In the expanded project, locate the definitions of `Build` and `ReportBuildIdentity`. Record `DefiningProjectFullPath` or the import comments around each.

چرا منشأ مهم است؟Why provenance matters

`Build` معمولاً از SDK targets می‌آید؛ target آزمایشی از `Directory.Build.targets`. اگر target سفارشی در expanded project نیست، احتمالاً فایل به‌خاطر نام یا جای پوشه وارد نشده. اگر هست اما اجرا نشده، hook/condition را بررسی کن.

`Build` usually comes from SDK targets; the custom target comes from `Directory.Build.targets`. If the custom target is absent from the expanded project, the file may not have been imported because of its name or location. If present but not run, inspect its hook or condition.

۱۸) گزارش رخداد بساز، نه حدس18) Write an incident report, not a guess

همکارت می‌گوید: «build موفق است ولی `settings.json` نیست.» item، metadata، Configuration، مسیر output و اجرای target کپی را بررسی کن. یک تشخیص کوتاه همراه فرمان بعدی بنویس.

A teammate says: “The build succeeds, but `settings.json` is missing.” Inspect the item, metadata, Configuration, output path, and copy target execution. Write a short diagnosis and the next command.

ترتیب بررسی پیشنهادیA useful investigation order
چند شاهد کنار هم
dotnet msbuild Shop.Cli.csproj -getProperty:Configuration,OutputPath
dotnet msbuild Shop.Cli.csproj -getItem:None
dotnet build -bl:copy-check.binlog -v:normal

اگر فایل در None نیست، الگوی فایل یا Include/Update را اصلاح کن. اگر item و metadata درست‌اند، مسیر Configuration را با مقصدی که نگاه می‌کنی تطبیق بده و در binlog دنبال targetهای Copy بگرد. پس از اصلاح همان `Test-Path` را تکرار کن. پاک‌کردن `obj` پیش از این شواهد، احتمالاً فقط سرنخ را حذف می‌کند.

If the file is absent from None, fix the pattern or Include/Update. If the item and metadata are correct, match the configuration path to the directory you inspected and search the binlog for copy targets. Repeat the same `Test-Path` after repair. Deleting `obj` before collecting this evidence may only remove clues.

حالا فایل پروژه را می‌خوانی، نه اینکه از رویش رد شویNow you can read the project instead of skimming past it

`PropertyGroup` مقدارهای build را نگه می‌دارد؛ `ItemGroup` ورودی‌های نوع‌دار را؛ و `Target` کارهایی را که در ترتیب build اجرا می‌شوند. SDK با importهای ضمنی قواعد پایه را می‌آورد. ارزیابی مدل می‌سازد و execution همان مدل را به taskهای واقعی تبدیل می‌کند. `Directory.Build.props` و `Directory.Build.targets` این قواعد را در سطح پوشه گسترش می‌دهند، اما محل import تعیین می‌کند چه چیزی را می‌بینند و چه چیزی را override می‌کنند.

`PropertyGroup` holds build values, `ItemGroup` holds typed inputs, and `Target` describes work in the build sequence. The SDK brings baseline rules through implicit imports. Evaluation forms the model; execution turns it into tasks. `Directory.Build.props` and `Directory.Build.targets` extend those rules across a folder, but import position determines what they can see and override.

اگر build خراب شد، اول مشخص کن کدام ادعا مسئله دارد: property اشتباه است؟ item وارد مدل نشده؟ شرط false شده؟ target اصلاً اجرا نشده؟ یا task خطا داده؟ expanded project و binlog برای جواب‌دادن به همین سؤال‌ها هستند، نه برای ساختن logهای حجیم و بی‌هدف.

When a build breaks, first identify the failing claim: is a property wrong, an item missing from the model, a condition false, a target not executed, or a task failing? The expanded project and binlog answer these questions; they are not an excuse to produce huge, unfocused logs.

حالا می‌دانیم پروژه چه ورودی‌هایی به build می‌دهد و MSBuild چه targetهایی را اجرا می‌کند. اما این ورودی‌ها package هم دارند؛ چرا restore دقیقاً آن نسخه‌ها و assetها را انتخاب کرده؟ فصل بعد سراغ NuGet می‌رویم و فایل `project.assets.json` را مثل گزارش تصمیم‌های restore می‌خوانیم.

We now know what inputs the project gives to the build and which targets MSBuild runs. But those inputs can include packages: why did restore select those versions and assets? Next we will inspect NuGet and read `project.assets.json` as evidence of restore decisions.
