از build تا artifact

From build to artifacts

CI نوشته build موفق بود؛ پس چرا فایل اجرایی پیدا نیست؟ چون build یک اتفاق جادویی با یک خروجی واحد نیست. ورودی‌ها ارزیابی می‌شوند، dependencyها آماده‌اند، compiler کد را ترجمه می‌کند و MSBuild خروجی‌ها را در مسیرهایی می‌چیند که باید از روی تنظیمات پروژه پیدا کنیم.

CI says the build succeeded; why can’t we find the executable? Because build is not magic with one output. Inputs are evaluated, dependencies are prepared, the compiler translates code, and MSBuild places outputs where we must locate them from project settings.

build سبز است، ولی دنبال چه چیزی می‌گردیم؟The build is green, but what are we looking for?

همکار می‌گوید «فایل exe را برای من بفرست». تو پوشهٔ پروژه را باز می‌کنی و چیزی که انتظار داشتی نیست. شاید پروژه framework-dependent است و خروجی اصلی DLL است؛ شاید Configuration یا TFM دیگری ساخته‌ای؛ شاید هم فقط output مربوط به build را با پوشهٔ publish اشتباه گرفته‌ای.

A teammate says, “Send me the executable.” You open the project folder and the expected file is not there. Perhaps the project is framework-dependent and its main output is a DLL; perhaps you built another configuration or TFM; or perhaps you mistook build output for the publish directory.

فصل قبل دیدیم restore graph dependencyها را آماده می‌کند. حالا مسیر build را دنبال می‌کنیم: evaluation مدل را می‌سازد؛ targetها و taskها مرحله‌ها را اجرا می‌کنند؛ compiler assembly می‌سازد؛ و چند فایل پشتیبان کنار آن می‌آیند. شکل دقیق خروجی به نوع پروژه و تنظیمات بستگی دارد، پس مسیر را از فرمان و propertyهای همین build پیدا می‌کنیم.

Last chapter showed restore preparing the dependency graph. Now we follow build: evaluation forms the model; targets and tasks perform stages; the compiler creates an assembly; and supporting files accompany it. Exact outputs depend on project type and settings, so we locate them from this build’s command and properties.

یک فرمان، چند مرحلهٔ پشت‌سرهمOne command, several stages

در پروژهٔ موقت فصل قبل این دو فرمان را پشت‌سرهم اجرا کن. build معمولاً restore را ضمنی اجرا می‌کند؛ گزینهٔ no-restore فقط وقتی درست است که dependencyها از قبل برای همین ورودی‌ها restore شده باشند.

In the disposable project from last chapter, run these commands in sequence. Build normally performs restore implicitly; no-restore is appropriate only when dependencies have already been restored for these inputs.

خط پایه و خروجی Release
dotnet build
dotnet build -c Release
dotnet msbuild -getProperty:Configuration,TargetFramework,OutputPath,TargetPath

باید build موفق و propertyهای configuration و مسیر خروجی را ببینی. مقدار OutputPath به‌تنهایی همهٔ فایل‌های جانبی را فهرست نمی‌کند؛ TargetPath مسیر اصلی target است. اگر پروژه چند TFM داشته باشد، خروجی هرکدام می‌تواند شاخهٔ جدا داشته باشد.

Expect a successful build and values for configuration and output paths. OutputPath does not list every companion file; TargetPath is the main target path. A multi-targeted project may have a separate output branch per TFM.

Debug و Release دو اسم جادویی نیستندDebug and Release are not magic labels

این configurationها مجموعه‌ای از propertyها و رفتار build هستند که پروژه یا SDK تعیین می‌کند. اسم Release به‌تنهایی تضمین نمی‌کند برنامه سریع، امن یا آمادهٔ production است.

These configurations are sets of properties and build behaviour defined by the project or SDK. The name Release alone does not guarantee that an app is fast, secure, or production-ready.

compiler کجا وارد می‌شود؟Where does the compiler enter?

در build معمول C#، taskهای SDK/MSBuild ورودی‌های کامپایل را جمع می‌کنند و compiler آن‌ها را به assemblyهای .NET تبدیل می‌کند. سورس C# معمولاً مستقیماً به کد ماشین بومی تبدیل نمی‌شود؛ فایل DLL خروجی عموماً IL و metadata دارد و runtime بعداً آن را اجرا می‌کند. جزئیات مهم مثل generatorها یا resourceها هم می‌توانند پیش از compile یا در کنار آن دخیل باشند.

In an ordinary C# build, SDK/MSBuild tasks collect compiler inputs and the compiler turns them into .NET assemblies. C# source is not normally compiled straight into native machine code; an output DLL commonly contains IL and metadata that the runtime later executes. Generators and resources can also participate before or alongside compilation.

نمایی از targetهای پروژه، نه قرارداد ثابت
dotnet build -v:normal
dotnet build -bl:build.binlog

خروجی normal پیام‌های اصلی را نشان می‌دهد. binlog برای دیدن targetها، taskها، propertyها و فایل‌های importشده مفید است؛ آن را به‌عنوان دادهٔ تشخیصی نگه دار و قبل از ارسال عمومی بررسی کن، چون ممکن است مسیرها یا مقدارهای حساس داخلش باشد. نام و ترتیب targetها بین نوع پروژه و SDK فرق می‌کند.

Normal verbosity shows the main messages. A binlog helps inspect targets, tasks, properties, and imports; treat it as diagnostic data and review it before sharing because it may contain paths or sensitive values. Target names and order vary by project type and SDK.

وقتی خطای compiler داری، اولین سؤال این نیست که «چه چیزی را clean کنیم؟»؛ ببین کدام پروژه، کدام TFM و کدام فایل ورودی خطا داده. وقتی compiler موفق است ولی فایل نیست، مرحلهٔ copy یا مسیر خروجی را بررسی کن؛ این دو incident متفاوت‌اند.

With a compiler error, do not start by asking what to clean; identify the project, TFM, and source input that failed. If compilation succeeds but a file is absent, inspect the copy step or output path—these are different incidents.

فهرست بالا نمونه‌ای است، نه تضمین. خروجی یک class library با executable فرق دارد؛ تنظیمات symbols و publish هم فایل‌ها را تغییر می‌دهد. برای همین با فرمان‌های بعدی مسیرهای واقعی را بگیر و پوشه را فهرست کن.

This is illustrative, not guaranteed. A class library differs from an executable, and symbols or publish settings change outputs. Use the next commands to obtain real paths and list the directory.

بازرسی خروجی این build
dotnet msbuild -getProperty:TargetPath,OutputPath
Get-ChildItem .\bin\Debug\net10.0
Get-ChildItem .\obj\Debug\net10.0

اگر مسیرها با این نمونه فرق دارند، property و Directory.Build.props را بررسی کن؛ SDKهای جدید امکان سازمان‌دهی خروجی زیر artifacts را هم دارند. هیچ‌وقت فقط چون مسیر آشنا نیست، کل bin/obj را از repository اصلی پاک نکن.

If paths differ from this example, inspect properties and Directory.Build.props; newer SDKs can also organise outputs under artifacts. Do not delete all bin/obj from the main repository merely because a path looks unfamiliar.

از روی علامت، مرحلهٔ شکست را پیدا کنUse the symptom to locate the failing stage

اگر restore خطا داد، به فصل قبل برگرد: source، graph و lock را ببین. اگر compiler خطا داد، message و ورودی source را بخوان. اگر build موفق شد اما فایل content غایب بود، item و metadata کپی را بررسی کن. اگر فایل هست ولی اجرا نمی‌شود، آن دیگر سؤال host/runtime و مدل انتشار است که در فصل‌های بعد پی می‌گیریم.

If restore fails, return to the previous chapter: inspect sources, graph, and lock. If compilation fails, read the message and source input. If build succeeds but content is missing, inspect its item and copy metadata. If the file exists but will not run, that is a host/runtime and deployment-model question for later chapters.

یک build قابل‌ردیابی در پروژهٔ آزمایشی
dotnet build -c Release -v:normal
dotnet msbuild -getProperty:Configuration,TargetFramework,OutputPath,TargetPath
dotnet build -c Release -bl:release.binlog

هر بار فقط یک متغیر را عوض کن: configuration، TFM یا property. اگر هم‌زمان clean، upgrade و تغییر مسیر انجام بدهی، حتی build سبز هم علت مشکل اولیه را روشن نمی‌کند. یک آزمایش تکرارپذیر یعنی فرمان پیش/پس از تغییر ثابت بماند.

Change one variable at a time: configuration, TFM, or property. If you clean, upgrade, and change paths all at once, even a green build will not explain the original failure. A repeatable experiment keeps the command identical before and after the change.

آزمایشگاه: artifact را از میان فایل‌ها پیدا کنLab: find the artifact among the files

از RestoreLab فصل قبل استفاده کن یا یک پروژهٔ console موقت بساز. خروجی را پاک نکن تا وقتی شواهد را ثبت کرده‌ای؛ هدف این است بفهمی build چه ساخت و هر فایل در کدام مرز قرار دارد.

Use RestoreLab from the previous chapter or create a disposable console project. Do not clean output before collecting evidence; discover what build produced and which boundary each file belongs to.

  1. dotnet build -c Debug بزن؛ سپس propertyهای Configuration، TargetFramework، OutputPath و TargetPath را بخوان.Run dotnet build -c Debug, then inspect Configuration, TargetFramework, OutputPath, and TargetPath.
  2. فایل‌های bin و obj را فهرست کن. DLL، PDB، deps و runtimeconfig را از روی پسوند نام‌گذاری کن؛ اگر فایلی وجود ندارد، نبودنش را هم ثبت کن.List bin and obj. Identify DLL, PDB, deps, and runtimeconfig by name; record absent files too.
  3. build را با Release تکرار کن و تفاوت مسیر و فایل‌ها را ثبت کن؛ اسم Release را به‌تنهایی شاهد بهینه‌بودن ندان.Repeat with Release and record path/file differences; do not treat the Release label alone as proof of optimisation.
  4. به فایل JSON بی‌خطر در پروژه metadata کپی به output اضافه کن. بعد از build در مسیر درست جست‌وجو کن و فرمانی را که مسیر واقعی را اثبات می‌کند در گزارش بیاور.Add copy-to-output metadata for a harmless JSON file. Search the correct output after build and report the command that proves the actual path.
  5. در نسخهٔ موقت metadata را خراب کن. build را اجرا کن، خطا/غیبت فایل را تشخیص بده و پس از یک اصلاح، همان آزمون را تکرار کن.Break the metadata in the disposable version. Run build, diagnose the error or missing file, and repeat the same test after one repair.
  6. در صورت نیاز یک binlog بگیر و target copy را پیدا کن. فایل log را پیش از اشتراک از نظر مسیر و مقدار حساس بازبینی کن.If useful, capture a binlog and locate the copy target. Review paths and sensitive values before sharing it.

تحویل آزمایشگاه یک جدول کوچک است: فرمان، Configuration/TFM، مسیر TargetPath، فایل‌های مهم و مرز ادعایی هرکدام. واژهٔ artifact را برای هر فایل تصادفی به‌کار نبر؛ خروجی build با بستهٔ آمادهٔ استقرار یکی نیست.

Submit a small table: command, Configuration/TFM, TargetPath, important files, and what each proves. Do not call every random file an artifact; build output is not the same as a deployment package.

تمرین‌ها: build دقیقاً چه چیزی را ثابت کرد؟Exercises: what did the build actually prove?

پاسخ را با تشخیص مرحله و شاهد بعدی شروع کن، نه با حدس زدن نام یک پوشه.

Start each response with the failing stage and next evidence, not a guessed folder name.

۱) exe پیدا نیست1) No executable found

build موفق است ولی exe نداری. چه خروجی‌هایی را بررسی می‌کنی پیش از اینکه build را خراب اعلام کنی؟

Build succeeds but there is no exe. Which outputs do you inspect before calling build broken?

راهنماHint

TargetPath، نوع پروژه، TFM و فایل‌های کنار DLL را بررسی کن. executable مستقل/host در همهٔ مدل‌ها یا سیستم‌ها یکسان نیست.

Inspect TargetPath, project type, TFM, and files beside the DLL. An apphost executable is not identical across all deployment models or operating systems.

۳) obj را برای deploy فرستاده‌اند3) obj was sent for deployment

چرا obj معمولاً انتخاب خوبی برای تحویل اجرایی نیست؟

Why is obj usually a poor deployment handoff?

توضیحExplanation

بیشتر محتوایش intermediate یا generated input است. خروجی build یا publish را بر اساس هدف تحویل انتخاب کن، نه فایل‌های میانی.

It mostly contains intermediate or generated inputs. Choose build or publish output based on the handoff goal, not intermediate files.

۴) DLL را با library اشتباه نگیریم4) A DLL is not always a library

یک DLL خروجی می‌تواند executable باشد یا library؟ برای فهمیدن چه اطلاعاتی جمع می‌کنی؟

Can an output DLL be an executable or a library? What evidence do you collect?

پاسخAnswer

هر دو ممکن‌اند. OutputType، project file، وجود runtimeconfig و روش اجرا را بررسی کن؛ پسوند به‌تنهایی نقش را ثابت نمی‌کند.

Both are possible. Inspect OutputType, project file, runtimeconfig, and launch method; the extension alone does not prove the role.

۵) PDB کجاست؟5) Where is the PDB?

PDB تولید نشده. چه چیزهایی را می‌سنجی و از نبودنش چه نتیجه‌ای نمی‌گیری؟

No PDB was emitted. What do you inspect, and what should you not infer?

راهنماHint

تنظیمات symbols و build را بررسی کن. نبود PDB ثابت نمی‌کند compile انجام نشده؛ وجود PDB هم تضمین نمی‌کند source مناسب در دسترس است.

Inspect symbol and build settings. No PDB does not prove compilation did not happen; a PDB does not guarantee matching source is available.

۶) compile موفق، فایل JSON غایب6) Compile succeeds, JSON is missing

کدام مرز را بررسی می‌کنی: compiler یا copy-to-output؟

Which boundary do you inspect: compiler or copy-to-output?

پاسخAnswer

اگر compiler موفق و فقط content غایب است، item، metadata و مسیر output را بررسی کن؛ compile علت اول نیست.

If compilation succeeds and only content is missing, inspect the item, metadata, and output path; compilation is not the first suspect.

۷) deps و lock file7) deps versus lock

چرا MyApp.deps.json جای packages.lock.json را نمی‌گیرد؟

Why is MyApp.deps.json not a replacement for packages.lock.json?

توضیحExplanation

deps بخشی از خروجی وابستگی مورد استفادهٔ host/runtime است؛ lock برای تثبیت restore graph در فرایند NuGet است.

deps is runtime dependency output used by the host/runtime; a lock file controls NuGet restore graph repeatability.

۸) چند TFM، چند مسیر8) Multiple TFMs, multiple paths

کجا دنبال assembly net10.0 می‌گردی و چرا نباید اولین DLL پوشهٔ bin را تصادفی انتخاب کنی؟

Where do you find the net10.0 assembly, and why not pick the first DLL under bin?

راهنماHint

TFM فعال و TargetPath را بخوان. خروجی TFM دیگر ممکن است API یا runtime requirement متفاوتی داشته باشد.

Read the active TFM and TargetPath. Another TFM’s output may have different APIs or runtime requirements.

۹) خطای compiler9) Compiler error

پیش از پاک‌کردن bin/obj کدام جزئیات error را نگه می‌داری؟

Which error details do you preserve before cleaning bin/obj?

شواهدEvidence

نام پروژه/TFM، فایل و شمارهٔ خط، فرمان و configuration، و خطاهای restore قبلی. بعد علت ورودی/compiler را بررسی کن؛ clean فقط وقتی برای فرضیهٔ مشخص لازم است.

Project/TFM, file and line, command and configuration, and prior restore errors. Then inspect compiler inputs; clean only when it tests a specific hypothesis.

۱۰) Runtimeconfig در library نیست10) No runtimeconfig in a library

آیا نبود runtimeconfig در class library نشانهٔ build ناقص است؟

Does the absence of runtimeconfig in a class library prove an incomplete build?

پاسخAnswer

نه لزوماً؛ runtimeconfig معمولاً به executable مربوط است. نوع پروژه و خروجی موردانتظار را بررسی کن.

Not necessarily; runtimeconfig is commonly associated with an executable. Check project type and expected outputs.

۱۱) مسیر output عوض شده11) Output path changed

تیم با .NET SDK جدید پوشهٔ artifacts می‌بیند. آیا build فایل‌ها را جا انداخته؟

With a newer .NET SDK, the team sees an artifacts folder. Did build omit files?

بررسیCheck

نه الزاماً؛ UseArtifactsOutput یا ArtifactsPath ممکن است مسیر را سازمان‌دهی کند. propertyها و Directory.Build.props را بررسی کن.

Not necessarily; UseArtifactsOutput or ArtifactsPath may organise outputs differently. Inspect properties and Directory.Build.props.

۱۲) Release یعنی آمادهٔ انتشار؟12) Does Release mean ready to ship?

همکارت می‌گوید فایل Release را مستقیم روی سرور کپی کن. کدام ادعا هنوز اثبات نشده؟

A teammate says to copy Release output straight to the server. What has not yet been proved?

توضیحExplanation

مدل انتشار، وابستگی runtime، فایل‌های همراه، مقصد و تنظیمات باید جدا بررسی شوند. build موفق مساوی بستهٔ deploy-tested نیست.

Publishing model, runtime dependencies, companion files, target, and settings still need checking. A successful build is not a deployment-tested package.

۱۳) binlog حاوی اطلاعات حساس13) A binlog may contain sensitive data

آیا می‌توانی binlog را بی‌بررسی در issue عمومی بگذاری؟

Can you attach a binlog to a public issue without review?

پاسخAnswer

نه؛ propertyها، مسیرها یا ورودی‌ها ممکن است اطلاعات حساس داشته باشند. پیش از اشتراک، محتوایش را بازبینی و redaction کن.

No. Properties, paths, or inputs may expose sensitive data. Review and redact it before sharing.

۱۴) خروجی stale14) Stale output

فایل جدیدی در source ساخته شده ولی در bin نیست. چه شواهدی بین «item وارد نشده» و «مسیر اشتباه را نگاه می‌کنم» فرق می‌گذارد؟

A new source file is absent from bin. What evidence distinguishes a missing item from inspecting the wrong path?

پاسخAnswer

فهرست Compile با msbuild، TFM/TargetPath و فهرست همان output را کنار هم بررسی کن؛ یک شاهد برای ورودی مدل و یک شاهد برای مقصد لازم است.

Inspect Compile items, TFM/TargetPath, and the exact output listing together; collect evidence for both model input and destination.

۱۵) build فقط یک پروژه را می‌زند15) Only one project built

از کجا می‌فهمی فرمان روی پروژهٔ موردنظر یا solution اجرا شده است؟

How do you tell whether the command built the intended project or solution?

راهنماHint

مسیر جاری، فایل solution/project انتخاب‌شده و فهرست پروژه‌های log را ثبت کن؛ نام پوشه به‌تنهایی کافی نیست.

Record working directory, selected solution/project, and project list in the log; the folder name alone is not enough.

۱۶) copy target اجرا نشده16) Copy target did not run

فایل محتوا در پروژه هست ولی خروجی ندارد. مرحلهٔ بعدی تو چیست؟

A content file exists in the project but not in output. What is your next step?

بررسیCheck

item و metadata کپی را بررسی کن، مسیر مقصد را از TargetPath بگیر و در صورت ابهام target copy را در binlog پیدا کن.

Inspect item and copy metadata, obtain the destination from TargetPath, and locate copy targets in a binlog if needed.

۱۷) clean چه چیزی را ثابت نمی‌کند؟17) What does clean not prove?

پس از dotnet clean build موفق شد. آیا این ثابت می‌کند علت قبلی cache خراب بود؟

After dotnet clean, build succeeds. Does that prove the cache caused the original problem?

۱۸) گزارش build برای تیم18) A build report for the team

یک build موفق باید چه اطلاعاتی داشته باشد تا همکار بداند دنبال چه artifact بگردد؟

What should a successful build report include so a teammate knows which artifact to find?

پاسخ نمونهSample answer

فرمان، SDK، configuration، TFM، TargetPath، فایل‌های همراه و اینکه این خروجی build است یا publish. اگر اجرا روی مقصد مهم است، آن را جداگانه اجرا و نتیجه را ثبت کن.

Command, SDK, configuration, TFM, TargetPath, companion files, and whether this is build or publish output. If target execution matters, run and record that separately.

یک build سبز، یک ادعاست؛ نه همهٔ ادعاهاA green build proves one thing, not everything

حالا می‌توانی مسیر را جدا کنی: restore graph را آماده می‌کند، MSBuild target و taskها را اجرا می‌کند، compiler assembly می‌سازد و مسیر خروجی از propertyهای همان پروژه می‌آید. obj معمولاً میانی است؛ bin خروجی build است؛ publish مرحلهٔ تحویل جداگانه‌ای است که بعداً بررسی می‌کنیم.

You can now separate the path: restore prepares the graph, MSBuild runs targets and tasks, the compiler creates assemblies, and output paths come from that project’s properties. obj is usually intermediate; bin is build output; publish is a separate delivery stage we will examine later.

اگر فایل را نمی‌بینی، اول TargetPath و TFM را بگیر. اگر content غایب است، item و copy target را بررسی کن. اگر compiler خطا می‌دهد، خطا و ورودی را نگه دار. clean را فقط وقتی اجرا کن که فرضیه‌ات به فایل‌های میانی مربوط است؛ قبلش evidence را ثبت کن تا سرنخ از دست نرود.

If you cannot find a file, obtain TargetPath and TFM first. If content is missing, inspect the item and copy target. If compilation fails, preserve the error and input. Clean only when your hypothesis concerns intermediate files; collect evidence first so you do not erase clues.

خروجی فعلی هنوز به ماشینی با runtime سازگار تکیه می‌کند یا باید runtime را همراه ببرد؟ فصل بعد Target Framework و Runtime Identifier را کنار هم می‌گذاریم؛ همان‌جا می‌بینیم سازگاری API و مقصد اجرا چگونه مسیر restore و build را عوض می‌کنند.

Does this output still rely on a compatible runtime being installed, or must it carry one? Next we will compare Target Framework and Runtime Identifier and see how API compatibility and execution target change restore and build.
