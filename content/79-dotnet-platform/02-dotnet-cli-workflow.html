چرخهٔ کار با dotnet CLI

The dotnet CLI workflow

فصل قبل دیدیم SDK ابزار ساخت است و runtime برنامه را اجرا می‌کند. حالا یک پروژهٔ کوچک می‌سازیم و از خود CLI می‌پرسیم: وقتی فقط یک فرمان می‌زنم، چه مرحله‌هایی پشت صحنه جلو می‌روند؟

Last chapter separated the SDK’s build tools from the runtime that executes an app. Now we will create a small project and ask the CLI: when I type one command, which stages actually happen behind the scenes?

«فقط run زدم»؛ اما چند کار انجام شد؟“I only ran it”—how much actually happened?

همکارت می‌گوید برنامه را اجرا کرده، اما پوشهٔ پروژه تغییر کرده و بار اول هم چند ثانیه طول کشیده. بعد کد را عوض کرده و دوباره run زده؛ این بار تقریباً فوری تمام شده. آیا بار دوم اصلاً build انجام شده؟ قبل از حدس، یک محیط کوچک و قابل‌اندازه‌گیری می‌سازیم.

A teammate says they ran the app, but project files appeared and the first run took a few seconds. They changed the code and ran it again; this time it finished almost immediately. Did the second command build anything at all? Instead of guessing, let’s create a small environment we can inspect.

در این فصل عمداً با یک پروژهٔ کنسولی جلو می‌رویم. هر فرمان یک «درِ ورودی» برای بخشی از کار است؛ بعضی درها وقتی لازم باشد مراحل قبل را هم صدا می‌زنند. از خروجی و پوشه‌های پروژه شاهد جمع می‌کنیم تا فرق «فرمان را اجرا کردم» با «مرحله واقعاً تازه اجرا شد» روشن شود.

We will use one console project throughout. Each command is an entry point to part of the workflow; some entry points invoke earlier stages when needed. We will collect evidence from output and project folders so “I ran the command” is not confused with “that stage ran afresh.”

اول پروژه را از template بسازیمStart by creating a project from a template

یک پوشهٔ خالی به نام lab انتخاب کن. template فقط یک فایل کد نمی‌سازد؛ اسکلت پروژه و فایل تنظیمات لازم را می‌سازد. خروجی فرمان را نگه دار، چون اسم template و پوشهٔ مقصد بعداً برای عیب‌یابی مهم‌اند.

Choose an empty folder named lab. A template creates more than a source file: it lays down the project structure and its configuration. Keep the command output because the selected template and destination matter when debugging later.

در نسخه‌های جدید SDK، ساخت پروژه ممکن است restore اولیه را هم به‌عنوان کار پس از ساخت انجام دهد؛ برای همین template می‌تواند از همان اول obj بسازد. متن دقیق خروجی با SDK و زبان سیستم فرق دارد. نکتهٔ قابل اتکا این است که پروژهٔ تولیدشده را بررسی کنیم، نه اینکه فرض کنیم هر بار restore دیده‌ایم.

With current SDKs, project creation can also run an initial restore as a post-creation action, which is why a new project may already contain obj. Exact wording varies by SDK and language. The reliable step is to inspect the generated project rather than assume a restore happened every time.

PowerShell · فایل پروژه و پوشه‌ها
Get-Content .\Shop.Cli.csproj
Get-ChildItem -Force

در csproj چارچوب هدف مثل net10.0 و تنظیمات پروژه را می‌بینی. obj محل فایل‌های میانی و state لازم برای مراحل بعدی است؛ bin هنوز ممکن است وجود نداشته باشد. خود template، restore یا وجود obj ثابت نمی‌کند برنامه build یا اجرا شده است.

The csproj shows the target framework, such as net10.0, and project settings. obj holds intermediate files and state used by later stages; bin may not exist yet. A template, restore, or obj directory does not prove that the app has been built or run.

مسیر را از پوشهٔ فعلی بخوانRead paths relative to the current directory

وقتی از پوشهٔ والد دستور ساخت را زدی، خروجی در Shop.Cli ساخته شد؛ بعد از cd، دستورهای بعدی در همان پروژه اجرا می‌شوند. اگر چند csproj کنار هم باشند، مسیر صریح بده تا CLI پروژهٔ اشتباه را انتخاب نکند.

The creation command ran from the parent, so its output went into Shop.Cli. After cd, later commands run in that project. If several csproj files are nearby, pass an explicit path so the CLI does not choose the wrong project.

restore دقیقاً چه چیزی را آماده می‌کند؟What does restore actually prepare?

بار اول template احتمالاً restore کرده؛ این بار آن را صریح می‌زنیم تا فرمان و اثرش را جدا ببینیم. restore وابستگی‌های تعریف‌شده را حل می‌کند و state تولیدشدهٔ NuGet/MSBuild را در obj می‌نویسد. برای پروژهٔ بدون package هم فایل‌های ارزیابی پروژه می‌توانند در obj ایجاد شوند.

The template likely restored once; now run it explicitly so we can separate the command from its effect. Restore resolves declared dependencies and writes NuGet/MSBuild state under obj. Even a project without package references can have evaluated project state there.

Shop.Cli
dotnet restore
Get-ChildItem obj

عبارت up-to-date یعنی state restore از نگاه ابزار نیاز به تغییر نداشته؛ به‌معنی build موفق نیست. project.assets.json ورودی‌های resolveشده و targetهای انتخاب‌شده را ثبت می‌کند. فایل را نگه دار، ولی آن را خروجی نهایی قابل‌انتشار فرض نکن.

“Up-to-date” means restore found no state to change; it does not mean the project built successfully. project.assets.json records resolved inputs and selected targets. Inspect it when needed, but do not mistake it for a deployable artifact.

restore فقط وقتی لازم است implicit می‌شودImplicit restore runs when needed

در workflow عادی معمولاً build، run، test و publish اگر restore لازم باشد آن را خودشان فراخوانی می‌کنند. اجرای جداگانهٔ restore در CI وقتی مفید است که بخواهیم زمان دسترسی شبکه و مرحلهٔ dependency را کنترل کنیم. دوباره‌کاری بی‌هدف، شاهد تازه‌ای تولید نمی‌کند.

In ordinary workflows, build, run, test, and publish invoke restore when it is needed. An explicit restore is useful in CI when we want to control network access and the dependency stage. Repeating it without a reason may produce no new evidence.

build: restore لازم، بعد خروجی کامپایلBuild: restore if needed, then compile output

حالا می‌خواهیم بفهمیم کد واقعاً قابل‌کامپایل است یا نه. build را از داخل پوشهٔ پروژه اجرا کن؛ در اولین build معمولاً restore هم لازم می‌شود. بعد bin و obj را کنار هم ببین تا خروجی نهایی را با فایل‌های میانی قاطی نکنی.

Now we want evidence that the source can compile. Run build from the project directory; the first build usually needs restore too. Then inspect bin and obj side by side so final output is not confused with intermediate files.

dotnet build
Get-ChildItem bin\Debug\net10.0

Build succeeded یعنی همین پروژه و همین configuration/TFM در این ماشین compile شدند. وجود DLL به‌تنهایی نمی‌گوید برنامه چه رفتاری دارد؛ برای رفتار باید اجرا یا تست کنیم. deps و runtimeconfig هم فایل‌های جانبی اجرای برنامه‌اند، نه نسخهٔ دیگری از source.

“Build succeeded” means this project, configuration, and TFM compiled on this machine. A DLL alone says nothing about the app’s behavior; run it or test it. deps and runtimeconfig are runtime support files, not another copy of the source.

اگر فقط warning دیدی، build می‌تواند موفق باشد؛ warning را با error یکی نگیر. اگر تعداد Errorها بیشتر از صفر است، خطا را از همان اولین diagnostic بخوان. پاک‌کردن bin و obj قبل از شناخت failure، معمولاً فقط شاهد را حذف می‌کند.

A build can succeed while reporting warnings; do not equate warnings with errors. If the error count is nonzero, start with the first diagnostic. Deleting bin and obj before understanding a failure usually removes evidence.

run راحت است، چون چند مرحله را پشت پرده جمع می‌کندRun is convenient because it combines stages

می‌خواهیم خروجی برنامه را ببینیم، نه اینکه دستی DLL را پیدا کنیم. dotnet run برای کار روزمره از source اجرا می‌کند و به build وابسته است؛ اگر restore یا build لازم باشد، آن‌ها را هم جلو می‌برد. همین راحتی سبب می‌شود یک فرمان را اشتباهاً معادل یک مرحله بدانیم.

We want to see the app’s output, not locate a DLL by hand. dotnet run is a convenient source-based development command and depends on build; when restore or build is needed, it advances those stages too. That convenience can make one command look like one stage when it is not.

Shop.Cli · Program.cs پیش‌فرض
dotnet run
خروجی برنامهApplication output
Hello, World!

این خروجی ثابت می‌کند کد اجراشده به Console نوشته؛ build موفق در گذشته به‌تنهایی این را ثابت نمی‌کرد. خروجی فرمان معمولاً بخش build را هم نشان می‌دهد یا می‌گوید همه‌چیز به‌روز است؛ این دو پیام یعنی الزاماً compiler در همان لحظه کار سنگینی کرده؟ نه.

This output proves that the executed code wrote to Console; an earlier successful build alone did not. Command output may show build progress or report everything up to date. Neither means the compiler necessarily did substantial work at that moment.

Shop.Cli · تغییر کنترل‌شده
# Program.cs را تغییر بده تا Order A-42 چاپ شود

اگر متن تازه را دیدی، می‌دانیم run خروجی به‌روز را اجرا کرده؛ اما اینکه همهٔ فایل‌ها از صفر compile شده‌اند نتیجه نمی‌گیریم. buildها incremental هستند و ممکن است از artifact به‌روز استفاده کنند. برای فهم دقیق جزئیات، فصل build/MSBuild جای درست ماست.

Seeing the new text tells us that run executed current output; it does not prove every file was compiled from scratch. Builds are incremental and can reuse up-to-date artifacts. Chapter 3 is where we will inspect build/MSBuild details.

test و publish مقصدهای متفاوت دارندTest and publish have different destinations

run برای اجرای برنامهٔ توسعه است. test باید یک پروژهٔ تست پیدا کند، آن را build کند و runner را برای اجرای تست‌ها به‌کار بگیرد. publish هم خروجی مناسب تحویل به مقصد می‌سازد. این‌ها سه جور نام برای یک کار نیستند.

run is for executing the development app. test must locate a test project, build it, and invoke a runner. publish prepares output for delivery. These are not three names for the same task.

یک پوشهٔ تست در کنار پروژهٔ برنامه
dotnet new xunit --framework net10.0 --output Shop.Cli.Tests
dotnet add Shop.Cli.Tests/Shop.Cli.Tests.csproj reference Shop.Cli/Shop.Cli.csproj
dotnet test Shop.Cli.Tests/Shop.Cli.Tests.csproj

template تست packageهای runner را به پروژه اضافه می‌کند و restore لازم دارد؛ اولین اجرا ممکن است به شبکه وابسته باشد. dotnet test بدون project صریح، وقتی چند پروژه نزدیک هم هستند انتخاب مبهمی است. اجرای صریح مسیر، شاهد را به همان مجموعه تست وصل می‌کند.

The test template adds runner packages and needs restore; the first run may require network access. With multiple nearby projects, dotnet test without an explicit project can be ambiguous. Passing the path ties the evidence to the intended test project.

خروجی خلاصه / Representative output

Passed ثابت می‌کند تست‌های کشف‌شده با همین build و محیط اجرا شده‌اند؛ ثابت نمی‌کند همهٔ نیازهای محصول پوشش داده شده‌اند. اگر 0 tests found دیدی، اول مطمئن شو command را روی پروژهٔ تست زدی و adapter/runner در پروژه وجود دارد.

“Passed” proves the discovered tests ran against this build in this environment; it does not prove all product requirements are covered. If you see “0 tests found,” first confirm you targeted the test project and that it has a test adapter/runner.

publish موفق می‌گوید فرآیند آماده‌سازی خروجی انجام شده؛ هنوز اجرای آن روی ماشین مقصد را ثابت نکرده‌ایم. publish را از build معمولی جدا نگه دار: این خروجی قرار است بستهٔ قابل‌تحویل باشد و بعداً با آزمایش مقصد ارزیابی شود.

A successful publish proves that output preparation completed; it does not prove the files run on the target machine. Keep publish distinct from an ordinary build: this is a delivery bundle to be evaluated later on its destination.

no-build و no-restore میان‌بُرند، نه تعمیرno-build and no-restore are shortcuts, not repairs

حالا همکارت می‌خواهد CI سریع‌تر شود و همه‌جا no-build می‌گذارد. این گزینه‌ها فقط وقتی امن‌اند که مرحلهٔ لازم قبلاً برای همان پروژه و تنظیمات انجام شده باشد. اگر state قدیمی یا ناقص باشد، میان‌بُر می‌تواند خطای تازه بسازد یا برنامهٔ قدیمی را اجرا کند.

A teammate wants faster CI and adds no-build everywhere. These flags are safe only when the required stage already ran for the same project and settings. With stale or incomplete state, a shortcut can create a new error or run old output.

Safe experiment: after changing Program.cs, compare a normal run with no-build. If the latter prints old text, that stale output is useful evidence: no-build skipped compilation as requested. dotnet run is not broken.

نوشتن no-restore در همهٔ jobها سرعت‌بخشی تضمینی نیستAdding no-restore everywhere is not a guaranteed speedup

اگر restore در job قبلی روی cache یا working directory دیگری انجام شده، پروژهٔ فعلی ممکن است project.assets.json مناسب نداشته باشد. نتیجه می‌تواند خطای assetها باشد. اول stageها و مسیر artifact را درست کن، بعد زمان را اندازه بگیر.

If restore ran in another job, cache, or working directory, this project may not have the required project.assets.json. That can cause missing-assets errors. Correct stage ordering and artifact paths first, then measure whether a shortcut helps.

نقشهٔ ذهنی: فرمان، مرحله نیستMental model: a command is not necessarily one stage

برای تشخیص «کدام مرحله خراب است؟» اسم آخرین فرمان کافی نیست. پیام restore، diagnostic کامپایلر، خروجی برنامه و گزارش تست هرکدام مرز متفاوتی را بررسی می‌کنند. فصل بعد از همین جا وارد csproj و MSBuild می‌شود تا ببینیم build چطور تصمیم می‌گیرد چه کاری انجام دهد.

The last command name is not enough to answer “which stage failed?” Restore messages, compiler diagnostics, application output, and test reports inspect different boundaries. Next we will open the csproj and MSBuild model to see how build decides what to do.

تمرین‌ها: از روی شاهد مرحله را پیدا کنExercises: locate the stage from evidence

هر تمرین خروجی قابل اجرا می‌خواهد. از یک پوشهٔ آزمایش جدا استفاده کن و چیزی را از پروژهٔ اصلی حذف نکن. خروجی نماینده است؛ نسخهٔ SDK و سیستم‌عامل ممکن است متن دقیق را تغییر دهند.

Each exercise asks for runnable evidence. Use a separate lab directory and do not delete anything from the main project. Outputs are representative; SDK and operating-system versions may change exact wording.

در پوشهٔ خالی، دستور console با net10.0 را اجرا کن. نام فایل پروژه، فایل کد و هر پیام restore را از خروجی ثبت کن.

In an empty folder, create a console project targeting net10.0. Record the project file, source file, and any restore message.

یک پاسخ ممکنOne possible solution

Expect a csproj and Program.cs; obj may already exist because of post-creation restore. This proves template output, not application execution.

۲) نام template را حدس نزن2) Do not guess a template name

فهرست templateهای نصب‌شده را بگیر و کمک دستور console را بخوان. خروجی را به یک فایل متنی گزارش کن؛ این آزمایش را در پوشهٔ پروژه انجام نده.

راه بررسیInspection
Terminal

list shows templates available in the selected SDK; help shows that template’s options. Installed templates are not the same as every template searchable on NuGet.

۳) restore سبز را درست تفسیر کن3) Interpret a green restore correctly

روی پروژهٔ تازه dotnet restore بزن و وجود project.assets.json را بررسی کن. بعد بگو کدام ادعا را می‌توانی و کدام را هنوز نمی‌توانی مطرح کنی.

Run dotnet restore on a fresh project and inspect project.assets.json. State what you can and cannot conclude.

پاسخ و دلیلSolution and reasoning
PowerShell
dotnet restore
Test-Path obj/project.assets.json

true بودن مسیر و up-to-date بودن، state restore را نشان می‌دهد. هنوز build، اجرای برنامه یا پوشش تست را ثابت نکرده‌ای.

A true path and up-to-date restore indicate restore state. They do not prove build success, execution, or test coverage.

۴) restore را عمداً جا بینداز4) Deliberately skip restore

در یک پروژهٔ موقت، پوشهٔ obj را فقط در همان پروژهٔ disposable کنار بگذار و build --no-restore را اجرا کن. diagnostic را ثبت و بعد پروژه را از نو بساز؛ این کار را در repository واقعی انجام نده.

In a disposable project only, move its obj directory aside and run build --no-restore. Record the diagnostic, then recreate the project. Do not do this in a real repository.

تفسیر خطاReading the error

وقتی فایل‌های assets لازم در دسترس نیستند، build نمی‌تواند dependency state را از حدس بسازد و خطای assets می‌دهد. این نشان می‌دهد no-restore فقط restore را حذف کرده؛ مشکل با اجرای دوبارهٔ همان میان‌بُر حل نمی‌شود.

Without required assets, build cannot invent dependency state and reports a missing-assets error. no-restore skipped restore; repeating the same shortcut cannot repair that condition.

۵) stageها را جداگانه در CI ثبت کن5) Record stages separately in CI

سه دستور restore، build --no-restore و test --no-build را برای jobهای جدا فهرست کن. پیش‌نیاز artifact و package cache هر job را یادداشت کن و توضیح بده کدام ترتیب معتبر است.

Plan restore, build --no-restore, and test --no-build as separate CI jobs. Note required artifacts and package-cache state for each job and explain the valid order.

ترتیب و شرطOrder and condition
CI steps
dotnet restore App.sln
dotnet build App.sln --no-restore
dotnet test Tests/Tests.csproj --no-build

اگر هر job ماشین تمیز جدا دارد، باید obj و خروجی build را منتقل کند یا مراحل را در یک job اجرا کند؛ cache package به‌تنهایی project.assets.json یا DLL را جایگزین نمی‌کند.

If each job uses a clean machine, it must transfer obj/build output or run the stages together. A package cache alone does not replace project.assets.json or the built DLL.

۶) build با warning را از failure جدا کن6) Separate a warning from failure

در پروژهٔ آزمایش warning قابل‌رفع بساز یا از warning موجود استفاده کن. build و exit code را ثبت کن و مشخص کن چه وقت pipeline باید fail شود.

Create or use a fixable warning in a lab project. Record build output and exit code, then state when the pipeline should fail.

نمونهٔ خواندن خروجیReading the result
Representative output
Build succeeded.
1 Warning(s)
0 Error(s)
exit code: 0

این build موفق است، ولی سیاست تیم ممکن است warning خاصی را با TreatWarningsAsErrors به failure تبدیل کند. از کلمهٔ succeeded نتیجه نگیر که warning بی‌اهمیت است؛ متن warning را بررسی کن.

The build succeeded, though team policy can promote selected warnings to errors with TreatWarningsAsErrors. Do not infer that a warning is harmless from “succeeded”; inspect its text.

۷) run واقعاً به build وابسته است؟7) Does run depend on build?

یک متن را در Program.cs چاپ کن، run بزن، سپس متن را عوض و دوباره run کن. خروجی و زمان هر مرحله را ثبت کن؛ زمان را شاهد قطعی cache فرض نکن.

Print a message from Program.cs, run it, change the message, and run again. Record output and timing, but do not treat timing as definitive cache evidence.

استدلالReasoning

run برنامه را از source اجرا می‌کند و به build وابسته است. خروجی تازه شاهد اجرای کد تازه است؛ اما فقط log تشخیصی build یا مقایسهٔ artifact می‌تواند دربارهٔ کار incremental بیشتر بگوید.

run executes from source and depends on build. New output proves the new code ran; build diagnostics or artifact comparison are needed for stronger claims about incremental work.

۸) خروجی قدیمی را با no-build پیدا کن8) Find stale output with no-build

برنامه را build کن، متن source را تغییر بده و run --no-build را اجرا کن. خروجی را با run عادی مقایسه کن.

Build the app, change source text, then run with --no-build. Compare it with a normal run.

خروجی و محدودیتOutput and limitation

no-build ممکن است متن قبلی را چاپ کند، چون compile جدیدی انجام نداده و از خروجی موجود استفاده کرده است. همین مثال نشان می‌دهد shortcut فقط وقتی درست است که artifact از source فعلی ساخته شده باشد.

no-build can print the old text because it did not compile the new source and reused existing output. The shortcut is valid only when the artifact already matches current source.

۹) test را روی پروژهٔ درست اجرا کن9) Run tests against the intended project

کنار برنامه یک پروژهٔ xUnit بساز و مسیر csproj تست را صریح به dotnet test بده. تعداد تست‌های کشف‌شده را ثبت کن.

Create an xUnit project beside the app and pass its csproj explicitly to dotnet test. Record the number of discovered tests.

مدرک مورد انتظارExpected evidence
Representative result
Passed! - Failed: 0, Passed: 1, Skipped: 0

ردیف Passed count تست کشف‌شده و موفق را نشان می‌دهد. این نتیجه دربارهٔ پروژهٔ تست انتخاب‌شده است، نه همهٔ پروژه‌های solution.

The Passed count reports discovered successful tests. It applies to the selected test project, not every project in a solution.

۱۰) 0 tests found را تشخیص بده10) Diagnose “0 tests found”

دستور test را یک بار روی پروژهٔ برنامه و یک بار روی پروژهٔ تست اجرا کن. تفاوت خروجی را نگه دار و علت را بدون تغییر source توضیح بده.

Run test once against the app project and once against the test project. Keep both outputs and explain the difference without changing source.

علت محتملLikely cause

پروژهٔ برنامه معمولاً test adapter ندارد و تستی کشف نمی‌شود؛ پروژهٔ تست packageهای لازم را دارد. قبل از نوشتن تست بیشتر، مسیر csproj و test runner انتخاب‌شده را بررسی کن.

The app project usually has no test adapter, so no tests are discovered; the test project includes the required packages. Check the csproj path and selected test runner before writing more tests.

۱۱) publish را از bin جدا نگه دار11) Keep publish separate from bin

با Release یک مسیر publish بیرون پوشهٔ پروژه بساز و فایل‌هایش را با bin مقایسه کن. سه نام فایل مشترک/متفاوت را ثبت کن.

Publish Release output outside the project directory and compare it with bin. Record three shared or different filenames.

فرمان و نتیجهCommand and result
Terminal
dotnet publish -c Release -o ../artifacts/Shop.Cli

خروجی publish برای تحویل آماده می‌شود و فایل‌های dependency/runtime configuration را کنار assembly می‌آورد. این مقایسه هنوز portability روی سیستم مقصد را اثبات نمی‌کند.

Publish prepares delivery output and places dependency/runtime configuration files beside the assembly. This comparison does not prove portability on the target machine.

۱۲) publish تکراری را بیرون پروژه انجام بده12) Keep repeated publish output outside the project

یک بار publish به ../artifacts و بار دوم به پوشهٔ publish داخل خود پروژه انجام بده. ساختار پوشه را بررسی کن و nested output را بازسازی کن.

Publish once to ../artifacts and once to a publish folder inside the project. Inspect the directory tree and reproduce nested output.

چرا مسیر مهم استWhy the path matters

فایل‌های داخل پوشهٔ پروژه ممکن است در ارزیابی بعدی وارد ورودی‌های پروژه شوند؛ publishهای تکراری می‌توانند خروجی تو‌در‌تو بسازند. مقصد بیرونی انتخاب کن یا پوشه را آگاهانه از ورودی‌ها کنار بگذار.

Files under the project can be considered by later project evaluation; repeated publishes may nest output. Choose an external destination or deliberately exclude that folder from project inputs.

۱۳) no-restore را با state اشتباه بشناس13) Catch a no-restore state mismatch

در یک پروژهٔ آزمایش، TFM را عوض کن، build --no-restore بزن و خطا را ذخیره کن. سپس restore و build عادی را تکرار کن.

Change the TFM in a disposable project, run build --no-restore, and save the error. Then restore and build normally.

نتیجهResult

state قبلی restore ممکن است برای target جدید کافی نباشد. restore پس از تغییر project inputs سازگاری state را دوباره می‌سازد؛ خطای no-restore مدرک ناسازگاری است، نه دلیل پاک‌کردن سراسری cache.

Previous restore state may not cover the new target. Restore recalculates state after project inputs change; the no-restore error is evidence of a mismatch, not a reason to clear every cache.

۱۴) مرحلهٔ کند را اندازه بگیر، نه حدس بزن14) Measure the slow stage instead of guessing

زمان restore و build را جدا با Stopwatch ثبت کن؛ دفعهٔ اول و دوم را جدا بنویس. توضیح بده چرا زمان دوم به‌تنهایی benchmark معتبر نیست.

Time restore and build separately with a stopwatch; record first and second runs. Explain why the second timing alone is not a valid benchmark.

تفسیرInterpretation

cache، سیستم فایل، build server و بار ماشین روی زمان اثر دارند. این اندازه‌گیری برای یافتن مرحلهٔ مظنون مفید است، نه مقایسهٔ عملکرد عمومی. برای ادعای کارایی آزمایش کنترل‌شده لازم است.

Caches, filesystem, build servers, and machine load affect timing. This measurement can identify a suspect stage, not establish general performance. A controlled benchmark is needed for performance claims.

۱۵) از پوشهٔ اشتباه دستور بزن15) Run a command from the wrong directory

از پوشهٔ والدِ دو پروژه run را بدون مسیر اجرا کن؛ سپس با --project مسیر درست را مشخص کن. خطای اول و خروجی دوم را مقایسه کن.

From a parent containing two projects, run without a path, then specify the correct path with --project. Compare the first error with the second output.

رفع ابهامRemoving ambiguity
Terminal
dotnet run --project Shop.Cli/Shop.Cli.csproj

خطای پیدا نکردن پروژه یا ابهام از مرحلهٔ انتخاب project است، نه الزاماً compile. مسیر صریح مرز را مشخص می‌کند؛ بعد اگر خطای compile ماند، آن را جدا بررسی کن.

A missing/ambiguous project error occurs during project selection, not necessarily compilation. An explicit path clarifies the boundary; investigate any later compile error separately.

۱۶) --no-build را در تست فقط با خروجی تازه بزن16) Use --no-build for tests only with fresh output

تست را عادی اجرا کن، source تست را تغییر بده، سپس test --no-build بزن و نتیجه را با اجرای عادی مقایسه کن. چه چیزی ممکن است stale باشد؟

Run tests normally, change test source, then use test --no-build and compare with a normal run. What might be stale?

تفسیرInterpretation

assembly تست و discovery metadata ممکن است نسخهٔ قبل باشد چون build کنار گذاشته شده. no-build برای وقتی است که همان configuration و source قبلاً build شده، نه برای دور زدن خطای compile.

The test assembly and discovery metadata may be from the previous version because build was skipped. no-build is for an already-built matching configuration, not a way around compile errors.

۱۷) خروجی publish را واقعاً اجرا کن17) Actually run the published output

از مسیر publish فایل‌های خروجی را فهرست کن و assembly را با dotnet اجرا کن. ثبت کن این آزمایش چه چیزی را ثابت می‌کند و چه چیزی را نه.

List publish output and execute its assembly with dotnet. Record what this test proves and what it does not.

شاهد و حد آنEvidence and its limit
Terminal
dotnet ../artifacts/Shop.Cli/Shop.Cli.dll

موفقیت نشان می‌دهد این ماشین می‌تواند این خروجی را با runtime نصب‌شده اجرا کند. هنوز اجرای مقصدی با OS/architecture دیگر را ثابت نکرده‌ای؛ آن موضوع به TFM/RID و مدل publish مربوط است.

Success shows this machine can run the output with its installed runtime. It does not prove execution on a different OS or architecture; that belongs to TFM/RID and publish-model decisions.

۱۸) رخداد build را گزارش کن18) Report a build incident

همکارت می‌گوید «run خراب است». یک بار خروجی کامل فرمان را ذخیره کن، failure را میان restore، build و خود برنامه دسته‌بندی کن، و فرمان بعدی را طوری انتخاب کن که همان مرز را بیازماید.

A teammate says “run is broken.” Capture the full command output, classify the failure as restore, build, or app execution, and choose a next command that tests that boundary.

گزارش نمونهSample incident note
PowerShell
dotnet run 2>&1 | Tee-Object run.log

اگر خطای NuGet پیش از compiler دیده می‌شود، restore boundary را پیگیری کن؛ diagnostic کد یعنی build boundary؛ پیام خطای بعد از شروع process یعنی رفتار برنامه. فرمان بعدی باید اطلاعات همین مرز را بیشتر کند، نه اینکه بی‌دلیل همهٔ پوشه‌ها را پاک کند.

A NuGet error before the compiler points to restore; a code diagnostic points to build; an error after process start points to application behavior. The next command should add evidence at that boundary, not indiscriminately delete folders.

جمع‌بندی: فرمان سطح بالا، کار مرحله‌ای را پنهان می‌کندReview: a high-level command hides staged work

new پروژه و فایل‌های اولیه را می‌سازد؛ restore dependency state را آماده می‌کند؛ build کد را compile می‌کند؛ run برنامهٔ source را برای توسعه اجرا می‌کند؛ test تست‌های کشف‌شده را می‌سازد و اجرا می‌کند؛ publish مجموعهٔ خروجی قابل‌تحویل را آماده می‌کند. restore/build ممکن است وقتی لازم باشند ضمنی اجرا شوند، پس پیام «up-to-date» را با اجرای کامل از صفر اشتباه نگیر.

new creates project files; restore prepares dependency state; build compiles code; run executes a source project for development; test builds and runs discovered tests; publish prepares a delivery set. Restore/build may run implicitly when needed, so do not mistake “up-to-date” for a full clean execution.

no-restore و no-build فقط قرارداد مرحله‌ها را به caller منتقل می‌کنند: «state لازم را خودت آماده کرده باش». اگر ترتیب یا target عوض شده، state قبلی را معتبر فرض نکن. حالا که می‌دانیم CLI چه درهایی را باز می‌کند، فصل بعد csproj و MSBuild را باز می‌کنیم تا داخل تصمیم‌های build برویم.

no-restore and no-build move responsibility to the caller: “you provide the required state.” If ordering or targets changed, do not assume old state is valid. Now that we know which doors the CLI opens, next we will inspect the csproj and MSBuild decisions behind build.

منابع رسمی و محدودهٔ نسخهOfficial references and version scope

این مثال‌ها برای SDKهای جدید .NET و target net10.0 هستند. متن خروجی بسته به SDK تغییر می‌کند؛ قرارداد گزینه‌ها را از راهنمای همان فرمان بخوان و برای خطای واقعی به اولین diagnostic توجه کن.

These examples use a current .NET SDK and target net10.0. Output wording can vary; consult the command’s reference for option semantics and use the first diagnostic for real failures.
