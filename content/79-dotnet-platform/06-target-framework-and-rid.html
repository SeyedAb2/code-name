Target Framework و Runtime Identifier

Target frameworks and runtime identifiers

برنامه روی سیستم توسعه اجرا می‌شود، اما روی سرور Linux فایل native لازم را پیدا نمی‌کند. شاید TFM و مقصد runtime را یکی گرفته‌ایم. یکی می‌گوید کدام APIهای .NET در دسترس‌اند؛ دیگری می‌گوید خروجی و packageهای وابسته به کدام سیستم‌عامل و معماری نزدیک‌اند.

The app runs on the development machine, but on the Linux server a native file is missing. Perhaps we confused the TFM with the runtime target. One describes which .NET APIs are available; the other identifies the operating system and architecture for runtime-specific output and packages.

یک فایل، دو سؤال متفاوتOne file, two different questions

یک کتابخانهٔ تیم از API تازه‌ای استفاده کرده، ولی مصرف‌کننده‌ای با نسخهٔ قدیمی‌تر .NET دیگر build نمی‌شود. هم‌زمان package حاوی فایل native است و روی سیستم‌عامل مقصد load نمی‌شود. این‌ها یک مشکل نیستند: اولی دربارهٔ قرارداد API و TFM است؛ دومی دربارهٔ RID و assetهای platform-specific.

A team library uses a newer API, and a consumer on an older .NET version no longer builds. At the same time, a package contains a native file that fails to load on the target OS. These are not one problem: the first concerns the API contract and TFM; the second concerns RID and platform-specific assets.

در پروژه TFM را معمولاً با TargetFramework می‌نویسیم، مثل net10.0. این انتخاب مجموعهٔ APIهایی را که compiler می‌شناسد و سازگاری package را شکل می‌دهد. RID مثل linux-x64 یا win-arm64 مقصد runtime را مشخص می‌کند؛ به‌تنهایی نسخهٔ APIهای .NET را بالا نمی‌برد.

A project usually declares its TFM through TargetFramework, such as net10.0. This shapes the APIs known to the compiler and package compatibility. A RID such as linux-x64 or win-arm64 identifies the runtime target; it does not raise the .NET API level by itself.

TFM یعنی قرارداد API، نه نسخهٔ نصب‌شدهA TFM is an API contract, not an installed version

در csproj می‌توانی یک TFM یا چند TFM تعریف کنی. برنامه با TargetFramework معمولاً یک هدف دارد؛ کتابخانه ممکن است TargetFrameworks داشته باشد تا چند مصرف‌کننده را پشتیبانی کند. چندهدفه‌سازی هزینه هم دارد: کد، dependency و تست باید برای هر هدف سازگار باشد.

A csproj can declare one or multiple TFMs. An app commonly has one TargetFramework; a library may use TargetFrameworks to support multiple consumers. Multi-targeting has a cost: code, dependencies, and tests must work for each target.

یک library آزمایشی
<PropertyGroup>
  <TargetFrameworks>net10.0;netstandard2.0</TargetFrameworks>
</PropertyGroup>

dotnet build -f net10.0
dotnet build -f netstandard2.0

اگر API فقط در net10.0 موجود باشد، compile هدف netstandard2.0 ممکن است شکست بخورد. این نشانهٔ خرابی compiler نیست؛ قرارداد دوم عمداً APIهای محدودتری دارد. با شرط‌های TFM می‌توان کد یا dependency را جدا کرد، اما هر branch باید تست شود و نباید سازگاری را با خاموش‌کردن warning وانمود کرد.

If an API exists only in net10.0, compilation for netstandard2.0 may fail. This is not a broken compiler; the second contract intentionally exposes fewer APIs. TFM conditions can separate code or dependencies, but test every branch rather than hiding compatibility problems with suppressed warnings.

TFM را از Runtime version جدا نگه دارKeep TFM separate from runtime version

برنامهٔ framework-dependent می‌تواند با TFM مشخص build شود و روی ماشینی اجرا شود که runtime سازگار را دارد. TFM به‌تنهایی نمی‌گوید runtime نصب است یا برنامه self-contained منتشر شده؛ این‌ها تصمیم‌های انتشارند.

A framework-dependent app can be built for a TFM and run on a machine with a compatible runtime. The TFM alone does not say whether that runtime is installed or whether the app was published self-contained; those are publishing decisions.

RID برای assetهای وابسته به پلتفرمA RID selects platform-specific assets

packageهای دارای native library یا فایل مخصوص OS می‌توانند assetهای مختلف داشته باشند. RID به restore/publish کمک می‌کند گزینهٔ مناسب مقصد را انتخاب کند. نمونه‌های متداول شامل linux-x64، linux-arm64، win-x64 و osx-arm64 هستند. برای انتخاب نهایی، فهرست رسمی و قابل‌حمل RIDها را ببین؛ به اسم توزیع/نسخه‌ای که دیگر در graph پیش‌فرض پشتیبانی نمی‌شود بی‌دلیل قفل نشو.

Packages containing native libraries or OS-specific files can ship different assets. A RID helps restore/publish select assets for the target. Common examples include linux-x64, linux-arm64, win-x64, and osx-arm64. For final selection, consult the official portable RID list; do not pin to a distribution/version-specific name without a reason.

آزمایش در پوشهٔ موقت
dotnet restore -r linux-x64
dotnet build -r linux-x64 --no-restore
dotnet publish -r linux-x64

RID را هنگام restore صریح وارد کردی؛ اگر بعداً --no-restore بزنی باید assets برای همان ورودی وجود داشته باشد. publish ممکن است restore ضمنی مناسب RID را اجرا کند. خروجی linux-x64 را روی Windows اجرا نکن و از موفقیت build cross-target نتیجه نگیر که native dependency روی مقصد حتماً load می‌شود.

You passed the RID explicitly to restore; a later --no-restore requires assets for those same inputs. Publish can run an implicit restore for the RID. Do not run linux-x64 output on Windows or infer that a native dependency will definitely load just because cross-target build succeeded.

آزمایشگاه: دو بُعد را جداگانه تغییر بدهLab: change the two dimensions separately

یک class library موقت بساز و برای دو TFM build بگیر. سپس یک RID را اضافه کن. هر بار فقط یکی از دو بُعد را تغییر بده تا معلوم شود اختلاف از API contract است یا asset مقصد.

Create a disposable class library and build for two TFMs. Then add a RID. Change only one dimension at a time so you can tell whether the difference comes from the API contract or target asset.

  1. در پروژه TFMهای net10.0 و netstandard2.0 را تعریف کن و هر دو را جدا build بگیر. اگر API ناسازگار است، خطا را ثبت کن؛ آن را با تغییر هر دو هدف پنهان نکن.Declare net10.0 and netstandard2.0 and build each separately. Record an API incompatibility instead of hiding it by changing both targets.
  2. یک شرط بر پایهٔ TFM برای کد یا PackageReference بساز و هر دو هدف را دوباره build کن. بگو هر شرط کدام قرارداد را تغییر می‌دهد.Add a TFM condition for code or PackageReference and build both targets again. Explain which contract each condition changes.
  3. برای برنامهٔ نمونه restore با یک RID قابل‌حمل مقصد بگیر و فهرست runtime-specific assets را بررسی کن.Restore the sample app for a portable target RID and inspect runtime-specific assets.
  4. فرمان --no-restore را یک بار با همان TFM/RID و یک بار با RID متفاوت اجرا کن؛ تفاوت خطا یا خروجی را ثبت کن.Run --no-restore once with the same TFM/RID and once with a different RID; record output or errors.
  5. publish برای مقصد را اجرا و خروجی را روی همان سیستم‌عامل/معماری یا ماشین CI مناسب بررسی کن. build موفق را جای اجرای مقصد نگذار.Publish for the target and inspect output on a matching OS/architecture or suitable CI machine. Do not substitute a successful build for target execution.

تحویل: مقدار TFM، مقدار RID، فرمان restore، نام asset وابسته به پلتفرم، و یک جمله دربارهٔ چیزی که آزمایش هنوز ثابت نکرده است. اگر مقصد واقعی در دسترس نیست، محدودیت را صریح بنویس.

Submit the TFM, RID, restore command, platform-specific asset name, and one statement about what the test has not proved. If the real target is unavailable, state that limitation explicitly.

تمرین‌ها: API یا پلتفرم؟Exercises: API or platform?

اول بُعد ناسازگاری را حدس بزن، بعد بگو کدام فایل یا فرمان حدست را می‌آزماید.

First identify the likely compatibility dimension, then name the file or command that tests your hypothesis.

۵) TFM کتابخانه5) A library TFM

چرا library ممکن است چند TFM داشته باشد ولی app فقط یکی؟

Why might a library target multiple TFMs while an app has one?

توضیحExplanation

library می‌خواهد چند consumer را پشتیبانی کند؛ app معمولاً برای محیط مصرف نهایی خودش ساخته می‌شود. چندهدفه‌سازی هزینهٔ سازگاری و تست دارد.

A library may serve multiple consumers; an app is commonly built for its deployment context. Multi-targeting adds compatibility and test cost.

۶) build برای RID، publish نه6) RID build, but no publish

build موفق برای linux-x64 چه چیزی را هنوز ثابت نمی‌کند؟

What does a successful linux-x64 build still not prove?

اجرای واقعی روی مقصد، load شدن native dependencyها یا کامل بودن بستهٔ deployment را ثابت نمی‌کند.

It does not prove target execution, native dependency loading, or deployment package completeness.

۷) TFM در برابر runtime نصب‌شده7) TFM versus installed runtime

آیا net10.0 در csproj ثابت می‌کند مقصد runtime .NET 10 نصب دارد؟

Does net10.0 in csproj prove .NET 10 runtime is installed on the target?

پاسخAnswer

نه؛ TFM compile target است. runtime نصب‌شده و مدل framework-dependent/self-contained جدا بررسی می‌شوند.

No; TFM is a compile target. Installed runtime and framework-dependent/self-contained model are separate checks.

۸) restore با یک RID، build با یکی دیگر8) Restore and build use different RIDs

چرا --no-restore ممکن است شکست بخورد؟

Why might --no-restore fail?

توضیحExplanation

assets برای ورودی‌های restore قبلی ساخته شده‌اند؛ RID دیگری graph و runtime-specific assets متفاوت می‌خواهد.

Assets were generated for the earlier restore inputs; a different RID can require another graph and runtime-specific assets.

۹) package compatible نیست9) Package is incompatible

NU1202 می‌آید. چه چیزهایی را کنار هم می‌گذاری؟

NU1202 appears. What do you compare?

بررسیCheck

TFM پروژه و گروه‌های TFM package، نسخهٔ package و پیام restore را بررسی کن. تغییر RID درمان ناسازگاری API target نیست.

Compare project TFM, package TFM groups, package version, and restore message. Changing RID does not fix an API target incompatibility.

۱۰) net10.0-windows10) net10.0-windows

این پسوند چه چیزی اضافه می‌کند که linux-x64 نمی‌کند؟

What does this suffix add that linux-x64 does not?

پاسخAnswer

platform-specific TFM برای APIهای Windows را محدود/فعال می‌کند؛ RID مقصد اجراست. این دو مفهوم حتی اگر هر دو نام پلتفرم داشته باشند متفاوت‌اند.

It opts into Windows-specific TFM APIs; a RID identifies the runtime target. They remain different concepts even when both mention a platform.

۱۱) multi-target failure11) A multi-target failure

net10.0 build موفق و netstandard2.0 fail است. کدام branch را اصلاح می‌کنی؟

net10.0 succeeds and netstandard2.0 fails. Which branch do you fix?

راهنماHint

خطا را برای هدف قدیمی بخوان و تصمیم بگیر library واقعاً باید آن را پشتیبانی کند یا نه. اگر باید، API/PackageReference را با شرط یا پیاده‌سازی سازگار کن و هر دو را تست کن.

Read the older target’s error and decide whether the library must support it. If so, condition APIs/dependencies or implement compatible code and test both.

۱۲) RID توزیع‌محور قدیمی12) An old distro-specific RID

SDK warning می‌دهد RID توزیع‌محور قدیمی است. قدم بعدی چیست؟

The SDK warns about an old distro-specific RID. What next?

پاسخAnswer

RID portable مناسب مثل linux-x64 را در catalog رسمی بررسی کن و packageهای native را روی محیط مقصد آزمایش کن؛ صرفاً warning را suppress نکن.

Check the official catalog for an appropriate portable RID such as linux-x64 and test native packages on target; do not merely suppress the warning.

۱۳) ARM و x6413) ARM versus x64

خروجی linux-x64 روی سرور linux-arm64 حتماً درست اجرا می‌شود؟

Will linux-x64 output necessarily run on linux-arm64?

پاسخAnswer

نه؛ معماری process و native asset اهمیت دارد. RID مناسب و آزمون روی مقصد لازم است.

No; process architecture and native assets matter. Use the appropriate RID and test on target.

۱۵) انتخاب بین TFMها15) Choosing between TFMs

یک library فقط consumerهای net10.0 دارد. آیا اضافه‌کردن netstandard2.0 همیشه کیفیت را بیشتر می‌کند؟

A library has only net10.0 consumers. Does adding netstandard2.0 always improve it?

توضیحExplanation

نه؛ اهداف بیشتر سطح تست، dependency و نگهداری را زیاد می‌کنند. TFM را بر اساس consumer واقعی انتخاب کن.

No; more targets increase test, dependency, and maintenance surface. Choose based on actual consumers.

۱۶) فایل native در publish نیست16) Native file missing from publish

What do you inspect before copying the file manually?

Inspect restore/publish RID, package runtime assets, architecture, and copy/publish settings. A manual copy may work on only one machine.

۱۷) نسخهٔ runtime17) Runtime version

آیا RID یعنی نسخهٔ دقیق runtime نصب‌شده؟

Does a RID specify the exact installed runtime version?

پاسخAnswer

نه؛ RID شناسهٔ سیستم‌عامل و معماری/محیط مقصد برای انتخاب asset است. runtime version و roll-forward موضوع‌های جدا هستند.

No; a RID identifies the OS and architecture/environment for asset selection. Runtime version and roll-forward are separate topics.

۱۸) گزارش سازگاری18) A compatibility report

برای تحویل artifact به تیم عملیات چه بُعدهایی را در یک خط ثبت می‌کنی؟

Which dimensions do you record in one line when handing an artifact to operations?

نمونهٔ پاسخSample answer

نوع برنامه، TFM، RID، معماری، مدل publish و runtime موردنیاز؛ سپس شاهد اجرای واقعی روی مقصد یا یادداشت محدودیت آن.

App type, TFM, RID, architecture, publish model, and runtime requirement; then target execution evidence or an explicit limitation.

دو انتخاب، دو قراردادTwo choices, two contracts

TFM می‌گوید برنامه یا library برای کدام API contract ساخته می‌شود. RID می‌گوید assetهای runtime را برای کدام سیستم و معماری می‌خواهیم. هر دو ممکن است restore/build را تغییر دهند، اما یکی را با دیگری درمان نکن.

TFM says which API contract the app or library targets. RID says which system and architecture need runtime assets. Both can affect restore/build, but do not use one to “fix” the other.

اگر package ناسازگار است، target و گروه‌های TFM آن را مقایسه کن. اگر native library load نمی‌شود، RID و معماری و فایل واقعی را ببین. اگر روی مقصد runtime نیست، سراغ مدل انتشار برو؛ این هنوز از روی TFM به‌تنهایی معلوم نمی‌شود.

For an incompatible package, compare target and package TFM groups. For a native load failure, inspect RID, architecture, and actual file. If the target lacks a runtime, examine the publishing model; the TFM alone cannot answer that.

حالا خروجی و مقصدش را می‌شناسیم. فصل بعد از فایل‌ها به شروع process می‌رویم: چه چیزی apphost را اجرا می‌کند، hostfxr چطور runtime را پیدا می‌کند و entry point از کجا کنترل را می‌گیرد.
