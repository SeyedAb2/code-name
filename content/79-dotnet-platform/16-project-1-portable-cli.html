پروژهٔ ۱ — ابزار گزارش runtime قابل‌حمل

Project 1 — a portable runtime-report CLI

یک برنامه روی لپ‌تاپ سازنده اجرا می‌شود، اما همکار شیفت بعد نمی‌داند روی سرور کدام runtime و معماری واقعاً استفاده شده. مأموریت تو ساخت ابزاری کوچک است که واقعیت process خودش را گزارش کند، خروجی قابل‌استفاده برای انسان و ماشین بدهد و با artifact منتشرشده روی محیطی دیگر هم قابل‌آزمایش باشد.

An application runs on the developer's laptop, but the next shift cannot tell which runtime and architecture the server actually uses. Build a small tool that reports facts about its own process, emits output for people and machines, and can be verified from a published artifact on another environment.

مأموریت: گزارش بده این process واقعاً کجا اجرا شدهMission: report where this process actually runs

ابزار runtime-report باید نسخهٔ runtime، سیستم‌عامل، معماری process، مسیر executable و base directory را گزارش کند. نسخهٔ runtime را با target framework یکی نگیر؛ هر دو را جدا نشان بده. برنامه باید text یا JSON تولید کند و با ورودی نامعتبر کد خروج غیرصفر بدهد.

The runtime-report tool reports runtime version, operating system, process architecture, executable path, and base directory. Do not conflate runtime version and target framework; report them separately. Support text or JSON output and return a nonzero exit code for invalid input.

مرز امن: همهٔ environment variableها، command line کامل یا مقدار secret را چاپ نکن. فقط فیلدهای allowlistشده را نشان بده؛ مسیرها ممکن است نام کاربر یا ساختار داخلی سرور را افشا کنند، پس برای خروجی production گزینهٔ redact در نظر بگیر.

Security boundary: never dump all environment variables, the full command line, or secret values. Show only allowlisted fields; paths can expose usernames or server layout, so consider redaction for production output.

قرارداد ابزار را ببندDefine the tool contract

  • --format text|json و --output PATH داشته باشد؛ پیش‌فرض روی stdout است.
  • Support --format text|json and --output PATH; default output is stdout.
  • --help بدون فایل یا secret اجرا شود و usage واقعی را نشان دهد.
  • --help works without files or secrets and documents actual usage.
  • خطای syntax یا مسیر خروجی در stderr نوشته شود و exit code غیرصفر بدهد.
  • Syntax or output-path errors go to stderr and return a nonzero exit code.
  • log عملیاتی از JSON ماشینی جدا باشد؛ گزارش را با متن log قاطی نکن.
  • Operational logs stay separate from machine-readable JSON.
  • assembly version، target framework، runtime، OS، architecture و مسیرها نام‌های غیرمبهم داشته باشند.
  • Distinguish assembly version, target framework, runtime, OS, architecture, and paths with unambiguous field names.
  • unit test برای قرارداد و integration test برای اجرای CLI یا parse JSON داشته باش.
  • Add unit tests for the contract and integration tests that run the CLI or parse JSON.

شش مرحله؛ هرکدام با شاهدSix milestones, each with evidence

  1. Baseline: پروژه را با SDK مشخص بساز و خروجی dotnet --info را در README ثبت کن؛ این اطلاعات SDK سازنده است، نه runtime برنامهٔ منتشرشده.
  2. Baseline: build with a chosen SDK and record dotnet --info; that describes the build machine's SDK, not the published app runtime.
  3. مدل گزارش: DTO خروجی و تفاوت target framework/runtime/assembly version را تعریف و با unit test ثابت کن.
  4. Report model: define the output DTO and test the distinction between target framework, runtime, and assembly version.
  5. CLI: help، format، output path، validation، stdout/stderr و exit code را پیاده کن.
  6. CLI: implement help, format, output path, validation, stdout/stderr, and exit-code behaviour.
  7. نسخهٔ قابل‌تکرار: Release build/test و artifact publish را با TFM/RID ثبت‌شده تولید کن؛ framework-dependent و self-contained را جدا بساز.
  8. Repeatable release: produce Release tests and publish artifacts with recorded TFM/RID; build framework-dependent and self-contained outputs separately.
  9. شکست کنترل‌شده: target اشتباه و مسیر output غیرقابل‌نوشتن را آزمایش کن؛ پیش از repair شاهد جمع کن.
  10. Controlled failure: test a wrong target and unwritable output path; collect evidence before repair.
  11. تحویل: artifact را در VM یا محیط تمیز با شرایط ثبت‌شده اجرا و گزارش واقعی را با نمونه مقایسه کن.
  12. Handoff: run the artifact in a clean VM/environment with recorded conditions, then compare its report with an expected sample.

قبولی با خروجی قابل‌بررسیPass with inspectable output

runtime-report --help

  • JSON با parser واقعی خوانده شود و runtime در دو مدل انتشار، روی همان محیط مقایسه شود.
  • Parse JSON with a real parser and compare runtime fields for both deployment modes on the same environment.
  • فایل خروجی دوباره خوانده شود؛ ناقص نباشد و ورودی را overwrite نکند.
  • Read the output file back; it is complete and does not overwrite input.
  • روی مقصد دوم، OS/architecture/process path با واقعیت تطبیق داده شود؛ exit code صفر به‌تنهایی کافی نیست.
  • On a second target, compare OS/architecture/process path with reality; exit code zero alone is insufficient.
  • با variable آزمایشی secret-like ثابت کن که ابزار environmentها را dump نمی‌کند.
  • Use a synthetic secret-like variable to prove the tool does not dump the environment.

پنج failure drillFive failure drills

۱) RID مقصد اشتباه استThe artifact has the wrong RID

برای معماری دیگر publish کن و در محیط مجاز اجرا را امتحان کن. command، OS، architecture و خطا را ثبت کن؛ با RID درست publish و همان تست را تکرار کن.

Publish for another architecture and try it in an authorized environment. Record command, OS, architecture, and error; republish for the correct RID and repeat the same test.

راهنماHint

موفقیت publish فقط می‌گوید SDK artifact ساخته، نه اینکه target می‌تواند اجرا کند.

A successful publish proves the SDK produced an artifact, not that the target can run it.

۲) مسیر خروجی موجود نیستOutput parent does not exist

با parent ناموجود اجرا کن؛ باید پیام روشن و exit code غیرصفر بدهد. مسیر را اصلاح و همان فرمان را تکرار کن و stderr و status shell را نگه دار.

Run with a missing parent; expect a clear message and nonzero exit code. Fix the path, repeat the same command, and retain stderr and shell status.

راهنماHint

متن خطا به‌تنهایی ثابت نمی‌کند برنامه exit code درست داده است.

The error text alone does not prove the program returned the correct exit code.

۳) فیلد حساس در گزارش ظاهر می‌شودA sensitive field appears in the report

یک variable آزمایشی secret-like تعریف کن و ثابت کن ابزار آن را چاپ نمی‌کند؛ سپس allowlist فیلدها را بازبینی کن.

Set a synthetic secret-like variable and prove it is not printed; then review the output-field allowlist.

راهنماHint

گرفتن همهٔ environmentها و حذف چند کلید، شکننده است؛ فقط فیلدهای مجاز را انتخاب کن.

Dumping all environment variables and removing a few keys is fragile; select only approved fields.

۴) dotnet --info با گزارش برنامه فرق داردdotnet --info disagrees with the app report

هر دو را روی میزبان هدف اجرا و مشخص کن کدام نسخه SDK و کدام runtime خود process را نشان می‌دهد. label خروجی را اصلاح کن؛ فرمان و گزارش بعد از اصلاح را نگه دار.

Run both on the target and identify which reports the SDK and which reports the process runtime. Fix the labels and retain the command and corrected report.

راهنماHint

SDK و runtime یک مفهوم نیستند؛ executable self-contained هم ممکن است runtime باندل‌شده داشته باشد.

SDK and runtime are different; a self-contained executable may use its bundled runtime.

۵) JSON با log قاطی شدهJSON is mixed with logs

log را موقتاً روی stdout بفرست و JSON را با parser واقعی بخوان. channelها را جدا و همان integration test را دوباره اجرا کن.

Temporarily send logs to stdout and parse the JSON with a real parser. Separate channels and rerun the same integration test.

راهنماHint

خروجی ماشین‌خوان باید channel تمیز داشته باشد؛ operational log را به stderr بفرست.

Machine-readable output needs a clean channel; send operational logs to stderr.

راهنمای مرحله‌ایStaged hints

راهنما ۱ — نسخه‌ها را جدا کنHint 1 — separate version concepts

از metadata اسمبلی یا دادهٔ build برای TFM استفاده کن؛ Environment.Version runtime جاری را می‌گوید و لزوماً همان TFM نیست.

Use assembly/build metadata for the TFM; Environment.Version reports the running runtime, not necessarily the TFM.

راهنما ۲ — مدل خروجی مستقلHint 2 — independent output model

DTO typed بساز و اطلاعات process را از text/JSON presentation جدا کن.

Create a typed DTO and separate process facts from text/JSON presentation.

راهنما ۳ — artifact را در مقصد اجرا کنHint 3 — run the artifact on target

artifact name، RID، self-contained بودن و runtime مقصد را در گزارش آزمایش ثبت کن؛ build machine جای target نیست.

Record artifact, RID, self-contained mode, and target runtime; the build machine is not the target.

طرح مرجع — بعد از پیاده‌سازی خودت مقایسه کنReference design — compare after your implementation

  1. Core: سازندهٔ report مستقل از Console و فایل است و فقط داده‌های allowlistشده می‌گیرد.
  2. Core: report creation is independent of console/files and accepts only allowlisted fields.
  3. CLI: parser آرگومان، ورودی نامعتبر را پیش از I/O رد می‌کند؛ help موفق و کوتاه است.
  4. CLI: argument parsing rejects invalid input before I/O; help is concise and successful.
  5. Output: serializer مدل را به JSON تبدیل می‌کند؛ فایل موقت و policy روشن برای overwrite دارد.
  6. Output: a serializer converts the model to JSON; file output uses a temporary file and explicit overwrite policy.
  7. Verification: unit test مدل، integration test اجرای CLI و smoke test artifact روی target.
  8. Verification: unit tests for the model, a CLI integration test, and a target smoke test for the artifact.

معیار، یک شکل ثابت خروجی نیست؛ قرارداد روشن، عدم افشای داده و مدرک اجرای artifact در مقصد است.

The output shape is not prescribed; the criteria are a clear contract, no data exposure, and evidence from the target.
