Assemblyها و پیدا کردن وابستگی‌ها

Assemblies and dependency resolution

build موفق است و process هم شروع می‌شود؛ چند ثانیه بعد برنامه می‌گوید assembly پیدا نشد. این بار NuGet احتمالاً کارش را تمام کرده، اما runtime هنگام اجرا باید وابستگی را در مسیرهای مجاز پیدا کند. بیایید از متن خطا تا فایل خروجی پیش برویم، نه اینکه DLL تصادفی را کنار برنامه کپی کنیم.

Build succeeds and the process starts; seconds later, the app says an assembly cannot be found. NuGet may have finished its work, but at runtime the loader must find the dependency in allowed locations. Let’s follow the error to the output files instead of copying a random DLL beside the app.

restore package را پیدا کرد؛ runtime چه؟Restore found the package; what about runtime?

یک برنامه در CI build می‌شود و روی سرور بالا می‌آید؛ اما با اولین درخواست به نوعی از package خطای FileNotFoundException می‌دهد. package در cache توسعه‌دهنده هست، پس کسی می‌گوید «NuGet دانلود نکرده». این فقط یک فرض است: cache توسعه‌دهنده هنگام اجرای سرور حضور ندارد و وجود فایل در cache اصلاً تضمین نمی‌کند در خروجی publish باشد.

An app builds in CI and starts on the server, but its first request throws FileNotFoundException for a package type. The package exists in the developer’s cache, so someone says “NuGet did not download it.” That is only a guess: the developer cache is not on the server, and a cached file does not prove it was included in publish output.

assembly، واحدی مانند DLL است که typeها و metadata را در خود دارد. اما سؤال «کدام DLL را کپی کنم؟» از این مهم‌تر است: dependency graph برنامه چیست و host/runtime بر اساس چه metadata و مسیرهایی آن را بار می‌کند؟ در خروجی معمول framework-dependent، فایل deps.json بخشی از نقشهٔ dependencyهای برنامه و framework است؛ AssemblyLoadContext پیش‌فرض در resolve کردن assemblyهای managed نقش دارد.

An assembly, often a DLL, contains types and metadata. More important than “which DLL should I copy?” is: what is the app’s dependency graph, and which metadata and paths does the host/runtime use to load it? In a typical framework-dependent output, deps.json describes application and framework dependencies; the default AssemblyLoadContext participates in resolving managed assemblies.

deps.json نقشه است، نه خود dependencydeps.json is a map, not the dependency itself

اگر deps.json می‌گوید dependency هست ولی فایل در پوشهٔ خروجی نیست، باید مدل deployment و probing را بررسی کنی. اگر فایل حاضر است ولی نسخهٔ اشتباه load می‌شود، نام assembly، مسیر واقعی و context بارگذاری را به دست بیاور. فایل deps را دستی دستکاری نکن؛ از project reference/package reference و publish درست استفاده کن.

If deps.json describes a dependency but the file is absent from output, inspect deployment mode and probing. If a file exists but the wrong version loads, identify assembly name, actual path, and load context. Do not edit deps by hand; fix project/package references and publish correctly.

فهرست dependencyهای پروژه
dotnet list package --include-transitive
Get-ChildItem .\bin\Release\net10.0
Get-Content .\bin\Release\net10.0\MyApp.deps.json -TotalCount 35

فرمان package list graph درخواستی/resolveشده را از دید project نشان می‌دهد؛ فهرست فایل‌ها نشان می‌دهد در output چه داریم؛ deps metadata اجرای runtime را شرح می‌دهد. هر سه را کنار هم بخوان، چون هیچ‌کدام به‌تنهایی ثابت نمی‌کند سرور همان پوشه را اجرا می‌کند.

The package list shows the project dependency graph; the file listing shows what output contains; deps describes runtime dependency metadata. Read all three together: none alone proves the server is running that exact directory.

managed و native خطاهای متفاوت‌اندManaged and native failures differ

FileNotFoundException یا FileLoadException برای assembly managed را با DllNotFoundException برای library native یکی نگیر. native file به RID، معماری، OS و جست‌وجوی سیستم‌عامل هم وابسته است.

Do not conflate managed assembly FileNotFoundException/FileLoadException with native-library DllNotFoundException. A native file also depends on RID, architecture, OS, and operating-system search behaviour.

AssemblyLoadContext: مرز بارگذاریAssemblyLoadContext: a loading boundary

برنامهٔ معمولی از AssemblyLoadContext پیش‌فرض استفاده می‌کند. این context وابستگی‌ها را می‌یابد و cache می‌کند. یک context نمی‌تواند برای یک نام سادهٔ assembly چند instance مستقل را بی‌قید نگه دارد؛ اگر نسخهٔ بارشده با نیاز جدید سازگار نباشد، ممکن است resolve شکست بخورد.

An ordinary app uses the default AssemblyLoadContext. It locates and caches dependencies. One context does not freely hold multiple independent instances for the same simple assembly name; if the loaded version cannot satisfy a later request, resolution may fail.

چند context بیشتر در سناریوهای plugin و بارگذاری پویا اهمیت پیدا می‌کند؛ هدف جداسازی dependencyهاست، نه راه‌حل عمومی برای هر خطای DLL. یک context سفارشی هم sandbox امنیتی نیست. موضوع plugin loading را در فصل C# مربوط به assemblyها عمیق‌تر دیدی؛ اینجا فقط برای خواندن خطا و مرزبندی لازم است.

Multiple contexts matter mainly for plugins and dynamic loading; their purpose is dependency isolation, not a universal DLL-error fix. A custom context is not a security sandbox. The C# assembly chapter covered plugin loading in depth; here we need only the boundary for diagnosis.

چه چیزی را از runtime loader بخواهیم؟Ask the runtime loader for evidence

اول خطای کامل را نگه دار: اسم سادهٔ assembly، نسخه، culture و stack trace. بعد working directory، مسیر executable، پوشهٔ publish، deps و معماری process را کنار هم ثبت کن. اگر با این شواهد هنوز معلوم نیست loader کجا جست‌وجو کرده، tracing host/loader را فقط در یک اجرای کنترل‌شده فعال کن؛ log verbose را پیش از انتشار بازبینی کن.

Preserve the full error first: simple assembly name, version, culture, and stack trace. Then record working directory, executable path, publish folder, deps, and process architecture. If evidence still does not show where loading searched, enable host/loader tracing for a controlled run; review verbose logs before sharing.

فعال‌سازی موقت host trace در PowerShell
$env:DOTNET_HOST_TRACE="1"
$env:DOTNET_HOST_TRACE_VERBOSITY="4"
dotnet .\MyApp.dll
Remove-Item Env:DOTNET_HOST_TRACE
Remove-Item Env:DOTNET_HOST_TRACE_VERBOSITY

host trace به startup و resolve host کمک می‌کند؛ برای هر خطای بعد از ورود به managed code کافی نیست. برای loadهای پویا یا managed assembly، رویدادهای loader را با ابزار تشخیصی مناسب بررسی کن. tracing را بعد از آزمایش خاموش کن تا خروجی عادی دوباره قابل‌خواندن باشد.

Host tracing helps with startup and host resolution; it is not sufficient for every failure after managed code begins. For dynamic or managed assembly loads, inspect loader events with an appropriate diagnostic tool. Disable tracing after the experiment so normal output remains readable.

آزمایشگاه: فایل هست، اما برنامه پیدایش نمی‌کندLab: the file exists, but the app cannot find it

دو پروژهٔ disposable بساز: یک برنامه و یک library محلی که برنامه به آن reference دارد. خروجی را publish کن، سپس فقط در نسخهٔ کپی‌شده یک فایل را rename کن. مخزن واقعی یا cache کاربر را دستکاری نکن.

Create two disposable projects: an app and a local library it references. Publish the output, then rename a file only in the copied output. Do not modify the real repository or user cache.

  1. برنامه را build و publish کن؛ فهرست package و فایل‌های خروجی را ذخیره کن.Build and publish the app; save the package listing and output file list.
  2. بررسی کن dependency library هم در output هست و deps آن را توصیف می‌کند.Verify the library dependency is in output and described by deps.
  3. برنامه را اجرا و موفقیت را ثبت کن؛ بعد DLL کپی‌شده را rename کن و همان اجرا را تکرار کن.Run the app and record success; rename the copied DLL and repeat the same launch.
  4. خطای کامل را بخوان و مشخص کن قبل یا بعد از entry point رخ داده است.Read the full error and identify whether it occurred before or after the entry point.
  5. فایل را برگردان؛ در صورت ابهام host trace بگیر و آن را خاموش کن.Restore the file; if needed, capture host trace and disable it afterward.
  6. خروجی را دوباره از publish بساز و اجرای سالم را تکرار کن؛ به کپی دستی DLL در پروژهٔ اصلی متوسل نشو.Republish and repeat the healthy launch; do not resort to manually copying a DLL into the main project.

گزارش باید با چهار ستون تمام شود: خطای دقیق، dependency مورد انتظار، شاهد فایل/metadata، علت و تعمیر. این فرم کوچک جلوی توصیهٔ «همهٔ DLLها را کنار exe بریز» را می‌گیرد.

Finish with four fields: exact error, expected dependency, file/metadata evidence, and cause/fix. This small report prevents the blanket advice to copy every DLL beside the executable.

از resolve زمان build تا بارگذاری زمان اجراFrom build-time resolution to runtime loading

NuGet در restore dependency graph را حل می‌کند؛ build و publish فایل‌ها و metadata را تولید می‌کنند؛ runtime هنگام اجرا از deps و probing برای یافتن وابستگی managed استفاده می‌کند. native library مسیر و محدودیت‌های دیگری دارد. cache، deps و publish output سه چیز متفاوت‌اند.

NuGet resolves the graph during restore; build and publish produce files and metadata; the runtime uses deps and probing to locate managed dependencies. Native libraries have additional paths and constraints. Cache, deps, and publish output are different things.

اگر فایل پیدا نمی‌شود، متن کامل خطا و محل اجرای process را ثبت کن. اگر فایل هست اما load نمی‌شود، هویت و نسخه و context را بسنج. اگر native است، RID و architecture را وارد تشخیص کن. هیچ‌کدام را با کپی بی‌قاعده یا پاک‌کردن cache جایگزین نکن.

If a file is missing, record the full error and process location. If present but not loadable, inspect identity, version, and context. If native, include RID and architecture. Do not replace diagnosis with random copying or cache deletion.
