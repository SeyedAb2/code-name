برنامهٔ .NET چطور شروع می‌شود؟

How a .NET application starts

روی ماشین توسعه dotnet run جواب می‌دهد؛ روی سرور پیام «runtime مناسب پیدا نشد» می‌بینی. این هنوز خطای business logic نیست. process باید از یک ورودی native شروع شود، host باید runtime مناسب را پیدا کند، فایل‌های برنامه و dependencyها را بخواند و در آخر کنترل را به entry point بدهد.

dotnet run works on the development machine; the server says no compatible runtime was found. This is not yet a business-logic error. A process starts from a native entry, the host locates a compatible runtime, reads application and dependency files, and eventually transfers control to the entry point.

قبل از Main، چند مرز را رد می‌کنیمSeveral boundaries come before Main

یک برنامهٔ framework-dependent را publish کرده‌ای. روی ویندوز با فایل executable اجرا می‌شود، اما هم‌تیمی می‌گوید فقط DLL را برده و دستور dotnet MyApp.dll خطای runtime داده است. سؤال «کدام خط برنامه خراب است؟» هنوز زود است: شاید host نتوانسته runtime سازگار را پیدا کند.

You published a framework-dependent app. It starts through its executable on Windows, but a teammate copied only the DLL and dotnet MyApp.dll reports a runtime error. “Which application line is broken?” is premature: perhaps the host could not find a compatible runtime.

در مسیر معمول، apphost یا dotnet host شروع می‌شود. hostfxr در انتخاب و فعال‌کردن runtime نقش دارد؛ بعد runtime پیکربندی و dependencyهای برنامه را می‌خواند، assembly ورودی را بار می‌کند و entry point اجرا می‌شود. این نقشه برای عیب‌یابی است، نه تضمین اینکه هر نوع publish دقیقاً همین فایل‌ها و همین مسیر را داشته باشد.

In a common path, apphost or the dotnet host starts. hostfxr participates in selecting and activating the runtime; the runtime then reads application configuration and dependencies, loads the entry assembly, and executes its entry point. This is a troubleshooting map, not a promise that every publish mode has the same files and exact path.

دو راه رایج برای اجرای framework-dependentTwo common ways to launch framework-dependent apps

در خروجی معمول framework-dependent ممکن است هم apphost platform-specific داشته باشی و هم DLL قابل‌اجرا از طریق dotnet. apphost اجرای مستقیم با نام برنامه را فراهم می‌کند؛ راه dotnet DLL هم همچنان معتبر است، مشروط به اینکه فایل‌های همراه و runtime سازگار حاضر باشند.

A typical framework-dependent output may include both a platform-specific apphost and a DLL runnable through dotnet. The apphost supports direct launch by app name; dotnet DLL remains valid when companion files and a compatible runtime are present.

دو راه اجرا، در پوشهٔ خروجی
dotnet MyApp.dll
.\MyApp.exe

روی Linux اجرای apphost معمولاً با ./MyApp است و permission اجرا هم لازم است. اگر apphost را غیرفعال کرده باشی، فایل اجرایی native تولید نمی‌شود و باید DLL را با dotnet اجرا کنی. پس پیش از انتقال فقط یک فایل، خروجی publish را کامل و آگاهانه انتخاب کن.

On Linux, launching apphost commonly uses ./MyApp and requires executable permission. If apphost is disabled, no native executable is produced and you run the DLL with dotnet. Before copying a single file, choose and inspect the complete publish output.

host چه runtimeی را انتخاب می‌کند؟How does the host select a runtime?

در framework-dependent app، runtime باید روی محیط اجرا موجود باشد. host نسخهٔ درخواستی برنامه و runtimeهای نصب‌شده را با سیاست انتخاب/roll-forward تطبیق می‌دهد. بنابراین پیام runtime not found را از خطای داخل Main جدا کن: تا runtime فعال نشود، کد برنامه شروع نشده است.

A framework-dependent app needs a runtime on the target. The host matches the app’s framework request against installed runtimes and selection/roll-forward policy. Separate runtime-not-found from errors inside Main: application code has not started until the runtime is activated.

وضعیت محیط اجرا
dotnet --info
dotnet --list-sdks
dotnet --list-runtimes

SDK ابزار build است و runtime ابزار اجرای برنامه؛ ممکن است سرور runtime داشته باشد ولی SDK نداشته باشد، یا چند نسخه نصب شده باشد. نتیجهٔ dotnet را در همان user، معماری و محیطی بگیر که process واقعی اجرا می‌شود؛ خروجی لپ‌تاپ مدرک وضعیت سرور نیست.

The SDK builds; the runtime executes. A server can have a runtime but no SDK, or multiple versions. Capture dotnet output under the same user, architecture, and environment as the real process; laptop output is not evidence about the server.

به roll-forward به چشم تعمیر جادویی نگاه نکنRoll-forward is not a magic repair

سیاست roll-forward می‌تواند انتخاب نسخهٔ نصب‌شده را تغییر دهد، اما ناسازگاری API یا native dependency را حذف نمی‌کند. آن را فقط با شناخت سازگاری برنامه تنظیم کن.

Roll-forward can change which installed runtime is selected, but it does not remove API or native dependency incompatibilities. Configure it only after validating app compatibility.

این‌ها نشانه‌اند نه حکم قطعی. خطای file not found می‌تواند از مسیر relative یا working directory هم باشد؛ assembly load هم گاهی وابستگی native را درگیر می‌کند. پیام کامل، working directory و فهرست فایل‌ها را کنار هم نگه دار.

These are clues, not verdicts. File-not-found can also come from a relative path or working directory; assembly-load failures can involve native dependencies. Keep the full message, working directory, and file listing together.

آزمایشگاه: جداکردن شکست host از شکست برنامهLab: separate host failure from app failure

در یک پروژهٔ console موقت، publish framework-dependent بگیر. روی ماشین فعلی اجرا کن، بعد با runtimeconfig و list-runtimes توضیح بده چرا اجرا شد. اگر محیط دومی داری که runtime ندارد، از آن برای مشاهدهٔ مرز شکست استفاده کن؛ runtime سیستمت را برای آزمایش حذف نکن.

Publish a temporary console app framework-dependent. Run it locally, then explain success using runtimeconfig and list-runtimes. If you have a second environment without the runtime, use it to observe the failure boundary; do not uninstall your system runtime as an experiment.

  1. dotnet publish -c Release اجرا کن و فایل‌های publish را فهرست کن.Run dotnet publish -c Release and list publish files.
  2. dotnet MyApp.dll و apphost را جدا اجرا کن؛ خروجی و exit code را ثبت کن.Run dotnet MyApp.dll and apphost separately; record output and exit code.
  3. runtimeconfig را بخوان و با dotnet --list-runtimes در همان محیط مقایسه کن.Read runtimeconfig and compare it with dotnet --list-runtimes in the same environment.
  4. نسخهٔ موقت app را طوری تغییر بده که هنگام startup exception بدهد. تفاوت پیام host با log برنامه را ثبت کن.Modify the disposable app to throw during startup. Record how the host message differs from the app log.
  5. فایل DLL یا apphost را در پوشهٔ کپی موقت rename کن و خطای مسیر را ببین؛ سپس فایل را برگردان.Rename the DLL or apphost in a temporary copy to observe a path failure, then restore it.

گزارش باید بگوید کد برنامه شروع شده یا نه، کدام فایل شاهد است و کدام runtime در محیط آزمایش نصب بود. هر خطایی که پیش از اولین log برنامه رخ می‌دهد را خودکار به کد business نسبت نده.

Report whether application code started, which file is evidence, and which runtime was installed in the test environment. Do not automatically attribute every failure before the first app log to business code.

برای incident سرور چه داده‌ای کمک می‌کند علت را از host تا Main دنبال کنی؟

Which data helps trace a server incident from host to Main?

پاسخ نمونهSample answer

فرمان/مسیر اجرا، معماری، runtimeconfig، list-runtimes همان محیط، فایل‌های publish، working directory و اینکه اولین log برنامه ظاهر شده یا نه.

اگر Main شروع نشده، کد برنامه را متهم نکنIf Main never started, do not blame application code

apphost یا dotnet process را آغاز می‌کند؛ hostfxr در پیدا و فعال‌کردن runtime نقش دارد؛ runtime فایل‌های پیکربندی و dependency را می‌خواند؛ بعد entry point اجرا می‌شود. مدل انتشار می‌تواند فایل‌ها را تغییر دهد، پس این زنجیره را با پوشهٔ واقعی تطبیق بده.

apphost or dotnet starts the process; hostfxr helps locate and activate the runtime; the runtime reads configuration and dependencies; then the entry point runs. Publishing mode can change files, so match this chain to the actual output.

runtime not found را با runtimeconfig و runtimeهای نصب‌شده بررسی کن. apphost اجرا نشد؟ مسیر، permission و معماری را ببین. خطا پس از اولین log است؟ حالا سراغ exception و log برنامه برو. این ترتیب ساده جلوی تغییرهای تصادفی deployment را می‌گیرد.

For runtime-not-found, compare runtimeconfig with installed runtimes. If apphost did not launch, inspect path, permission, and architecture. If the error follows the first app log, investigate application exceptions and logs. This sequence prevents random deployment changes.
