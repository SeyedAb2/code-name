How do we upgrade safely and reversibly?

یک هشدار امنیتی برای dependency آمده و نسخهٔ runtime هم به پایان پشتیبانی نزدیک است. کسی همهٔ packageها را یک‌جا به آخرین نسخه می‌برد؛ build سبز می‌شود، ولی integration testها و رفتار مقصد هنوز بررسی نشده‌اند. ارتقا را از «عوض‌کردن عدد نسخه» به یک تغییر قابل‌ردیابی تبدیل می‌کنیم.

A dependency security advisory arrives while the runtime approaches end of support. Someone upgrades every package to the latest version; the build passes, but integration tests and target behaviour remain unchecked. We will turn an upgrade from “changing version numbers” into a traceable change.

اول بفهم چه چیزی در خطر استFirst identify what is at risk

سه چیز را جدا کن: پشتیبانی runtime و SDK، advisory امنیتی یک package، و نسخهٔ جدیدی که فقط feature دارد. اقدام هرکدام فرق می‌کند. از فهرست dependencyهای مستقیم و transitive شروع کن، منبع هشدار را بخوان و محدودهٔ اثر را مشخص کن؛ «یک نسخهٔ جدید هست» به‌تنهایی incident امنیتی نیست.

Separate three things: runtime/SDK support, a package security advisory, and a feature-only update. They call for different actions. Start with direct and transitive dependency inventories, read the advisory source, and establish impact; “a newer version exists” is not by itself a security incident.

گراف dependency را ببین؛ فقط csproj را نهInspect the dependency graph, not only the project file

package مستقیم را خودت انتخاب کرده‌ای؛ transitive را dependency دیگری وارد کرده است. audit را برای هر دو اجرا کن و فایل lock/restore را کنار گزارش نگه دار تا بفهمی build دقیقاً کدام نسخه‌ها را resolve کرده است. SDKهای قدیمی‌تر ممکن است شکل فرمان متفاوتی داشته باشند؛ نسخهٔ SDK تیم را هماهنگ کن.

You choose direct packages; other dependencies bring in transitive ones. Audit both and retain lock/restore data with the report so you know exactly what the build resolved. Older SDKs may use a different command form; align on the team's SDK version.

گزارش نسخه و vulnerability
dotnet package list --include-transitive --vulnerable --format json
dotnet package list --include-transitive --outdated

در SDK قبل از .NET 10، شکل verb-first یعنی dotnet list package را بررسی کن. فهرست vulnerability به feed و منبع audit وابسته است؛ خروجی خالی را بدون اطمینان از تنظیم sourceها «همه‌چیز امن است» تفسیر نکن.

With SDKs before .NET 10, use the older verb-first form, dotnet list package. Vulnerability results depend on feeds and audit sources; do not interpret an empty report as “everything is safe” until source configuration is verified.

ارتقا را کوچک و قابل‌اندازه‌گیری نگه دارKeep upgrades small and measurable

ابتدا baseline از build، unit/integration tests و publish مقصد بگیر. بعد packageهای امنیتی یا runtime را در تغییرهای قابل‌فهم جلو ببر. تغییر major و dependencyهای حساس را از patchهای عادی جدا کن؛ API breaking و رفتار runtime ممکن است از build عبور کند ولی در اجرا تفاوت داشته باشد.

Capture a baseline of build, unit/integration tests, and target publish. Then update security packages or runtime in understandable increments. Separate major changes and sensitive dependencies from routine patches; breaking APIs and runtime behaviour can differ even when compilation passes.

تغییر package آسیب‌پذیر در SDK جدید
dotnet package update --vulnerable
dotnet restore --locked-mode
dotnet test

فرمان update ممکن است فایل‌های پروژه را تغییر دهد؛ diff را بخوان و نسخهٔ مقصد را ثبت کن. اگر SDK از فرمان جدید پشتیبانی نمی‌کند، package را آگاهانه در فایل پروژه update کن. هیچ فرمان ارتقایی جای review و test واقعی را نمی‌گیرد.

The update command may modify project files; inspect the diff and record the resulting version. If the SDK lacks the newer command, update the project file deliberately. No upgrade command replaces review and real tests.

پشتیبانی یعنی برنامهٔ ارتقا داشته باشیSupport status requires an upgrade plan

برای .NET و ASP.NET Core تاریخ پشتیبانی را از صفحهٔ رسمی lifecycle و releaseهای فعلی چک کن؛ به نوشتهٔ قدیمی در README تکیه نکن. LTS و STS فقط برچسب نیستند: زمان ارتقا، تعداد نسخه‌های runtime روی میزبان و هزینهٔ نگهداری را با release schedule بسنج. SDK نصب‌شده را با dotnet --info ثبت کن و در CI نسخهٔ مورد انتظار را pin کن.

Check current .NET and ASP.NET Core support dates on the official lifecycle and release pages; do not trust an old README. LTS and STS affect upgrade cadence, runtimes on hosts, and maintenance cost. Record the SDK with dotnet --info and pin the expected SDK in CI.

به پایان پشتیبانی رسیدن، باگ runtime را ثابت نمی‌کندEnd of support does not prove a runtime bug

اما یعنی دیگر نباید پچ‌های معمول همان release را فرض کنی. ریسک، سازگاری dependencyها و زمان مهاجرت را ثبت کن و مسیر پشتیبانی‌شده را با آزمایش طی کن.

It does mean you should not assume that release will keep receiving normal patches. Record risk, dependency compatibility, and migration timing, then test the supported path.

نسخهٔ امن فقط با بازتولیدپذیری معنا داردA secure version needs reproducibility

قفل‌کردن dependencyها، SDK مشخص، منبع package کنترل‌شده و artifact قابل‌ردیابی کمک می‌کند بفهمی دقیقاً چه چیزی build شده. اگر feed audit اطلاعات vulnerability ندارد، هشدار source را پیگیری کن. checksum و provenance را طبق نیاز تیم نگه دار؛ secret یا credential feed را وارد Git نکن.

Locked dependencies, a pinned SDK, controlled package sources, and traceable artifacts help establish exactly what was built. If an audit feed lacks vulnerability data, investigate the source warning. Keep checksums/provenance as required, and never commit feed credentials.

ارتقای خوب، قابل‌ردیابی و قابل‌برگشت استA good upgrade is traceable and reversible

منبع رسمی support را ببین، گراف مستقیم و transitive را audit کن، تغییر را کوچک نگه دار و با همان artifact مقصد را آزمایش کن. هشدار امنیتی را بدون بررسی exposure نادیده نگیر؛ از طرف دیگر هر نسخهٔ تازه را هم بی‌چون‌وچرا وارد production نکن. تصمیم، شواهد و مسیر rollback را کنار هم ثبت کن.

Check official support sources, audit direct and transitive dependencies, keep changes small, and test the target artifact. Do not ignore a security advisory without assessing exposure, and do not blindly ship every new version either. Record the decision, evidence, and rollback path together.
