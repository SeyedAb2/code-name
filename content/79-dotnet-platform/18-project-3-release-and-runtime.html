پروژهٔ ۳ — انتشار و تحویل برنامهٔ .NET

Project 3 — publish and deliver a .NET application

برنامه روی ماشین سازنده اجرا می‌شود؛ اما پوشه‌ای که برای هم‌تیمی فرستاده‌اند ناقص است و معلوم نیست runtime باید از قبل نصب باشد یا نه. مأموریت این است: برای یک مقصد واقعی artifact نسخه‌دار بساز، پیش‌نیازها را روشن کن و همان خروجی را بیرون از محیط build اجرا و اثبات کن.

The application runs on the developer's machine, but the folder sent to a teammate is incomplete and nobody knows whether a runtime must be installed. Build a versioned artifact for a real target, document its prerequisites, and prove that exact output runs outside the build environment.

مأموریت: artifact را به کسی بده که SDK نداردMission: deliver an artifact to a machine without the SDK

یک برنامهٔ کوچک CLI یا Worker از پروژه‌های قبل انتخاب کن. نسخه و مقصد را تعیین کن؛ مثلاً Linux x64 یا Windows x64. بعد تصمیم بگیر framework-dependent مناسب است یا self-contained. خروجی باید قابل‌شناسایی، قابل‌اجرا و قابل‌ردیابی باشد.

Choose a small CLI or Worker from the earlier projects. Define a version and target, such as Linux x64 or Windows x64, then decide whether framework-dependent or self-contained publishing fits. The output must be identifiable, runnable, and traceable.

قول اضافه نده: framework-dependent بودن یعنی مقصد باید runtime سازگار داشته باشد؛ self-contained بودن runtime را همراه می‌برد، اما سیستم‌عامل، معماری، native dependency، مجوز فایل و تنظیمات مقصد را جادویی حل نمی‌کند. artifact هر RID را روی محیط متناسب آزمایش کن.

No overclaim: framework-dependent output requires a compatible runtime on the target. Self-contained output carries the runtime, but does not magically solve OS, architecture, native dependencies, file permissions, or target configuration. Test each RID on a compatible environment.

محدوده و تصمیم‌های انتشارScope and release decisions

  • نسخهٔ برنامه، TFM، RID، configuration و مدل انتشار را README ثبت کن.
  • Record application version, TFM, RID, configuration, and publish model.
  • نسخه را در artifact name یا metadata قابل‌مشاهده کن؛ فایل خروجی مبهم نماند.
  • Make the version visible in artifact naming or metadata; avoid an ambiguous output folder.
  • خروجی publish را از سورس و bin/obj جدا نگه دار و فقط artifact لازم را بسته‌بندی کن.
  • Keep publish output separate from source and bin/obj; package only required artifacts.
  • یک راه‌اندازی یا smoke test داشته باش که خروجی واقعی را اجرا کند، نه پروژهٔ source را.
  • Provide a startup or smoke test that runs the published output, not the source project.
  • تنظیمات قابل‌تغییر در زمان اجرا را از داخل image/artifact ثابت جدا کن؛ secret در بسته نگذار.
  • Separate runtime-adjustable configuration from the immutable artifact; never package secrets.
  • Single-file، trimming و Native AOT اختیاری‌اند؛ تنها با اندازه‌گیری و تست featureها اضافه‌شان کن.
  • Single-file, trimming, and Native AOT are optional; use them only after measurement and feature tests.

هفت مرحله با خروجی قابل‌بررسیSeven milestones with inspectable outputs

  1. Baseline: testها را اجرا کن و برنامه را از source با ورودی ثابت اجرا کن؛ خروجی مورد انتظار را ثبت کن.
  2. Baseline: run tests and execute from source with fixed input; record expected output.
  3. Target: مقصد را دقیق انتخاب کن: OS، architecture، TFM و نیازمندی native را بنویس.
  4. Target: choose OS, architecture, TFM, and native prerequisites explicitly.
  5. انتخاب publish: framework-dependent و self-contained را برای مخاطب تحویل مقایسه و دلیل انتخاب را ثبت کن.
  6. Publish choice: compare framework-dependent and self-contained for the recipient and document the decision.
  7. Build نسخه‌دار: Release publish بساز و فرمان، نسخه و RID را در log تحویل بگذار.
  8. Versioned build: publish Release and record command, version, and RID in the handoff log.
  9. بازرسی: فهرست فایل‌ها، حجم، مجوز اجرا و فایل‌های runtime/config را بررسی کن.
  10. Inspect: check file list, size, executable permission, and runtime/config files.
  11. محیط تمیز: artifact را روی ماشین/VM متناسب که source و SDK در آن نیست اجرا کن.
  12. Clean target: run it on a compatible machine/VM without the source or SDK.
  13. تحویل: checksum، دستور اجرا، نیازمندی‌ها، محدودیت‌ها و روش rollback به نسخهٔ قبلی را مستند کن.
  14. Handoff: document checksum, run command, prerequisites, limitations, and rollback to the prior version.

۹ معیار پذیرشNine acceptance checks

  1. نسخه و RID در گزارش تحویل دقیقاً مشخص است.
  2. The handoff identifies the exact version and RID.
  3. همهٔ تست‌های solution پیش از انتشار سبز هستند.
  4. All solution tests pass before publishing.
  5. فرمان publish تکرارپذیر است و خروجی پاک/قابل‌شناسایی تولید می‌کند.
  6. The publish command is reproducible and produces an identifiable clean output.
  7. نیاز runtime مقصد با انتخاب framework-dependent/self-contained سازگار است.
  8. Target runtime requirements match the framework-dependent/self-contained choice.
  9. همان artifact پس از انتقال اجرا می‌شود و smoke test پاسخ مورد انتظار می‌گیرد.
  10. The same artifact runs after transfer and passes its smoke test.
  11. فایل اجرایی، config و مجوزها برای OS مقصد درست‌اند.
  12. Executable, configuration, and permissions fit the target OS.
  13. checksum فایل تحویلی با فایل آزمایش‌شده برابر است.
  14. The delivered file checksum matches the tested artifact.
  15. هیچ secret یا فایل محلی ناخواسته‌ای در بسته نیست.
  16. No secrets or unintended local files are packaged.
  17. روش بازگشت به artifact نسخهٔ قبلی مستند و قابل اجراست.
  18. Rollback to the previous artifact is documented and executable.
نمونهٔ فرمان؛ متناسب با TFM/RID خودت تغییر بده
dotnet test
dotnet publish src/Tool/Tool.csproj -c Release -r linux-x64 --self-contained false -o artifacts/tool-1.2.0-linux-x64
Get-ChildItem artifacts/tool-1.2.0-linux-x64
Get-FileHash artifacts/tool-1.2.0-linux-x64/Tool.dll -Algorithm SHA256

فرمان نمونه برای PowerShell است و نام project، TFM و RID را باید با مقصد واقعی عوض کنی. فرمان publish موفق فقط ساخت artifact را ثابت می‌کند؛ smoke test روی سیستم مقصد هنوز لازم است.

The sample uses PowerShell; replace project name, TFM, and RID for your actual target. A successful publish proves artifact creation only; a target-side smoke test is still required.

سه failure drill، بدون حدسThree failure drills, diagnosed with evidence

فایل اجرا نمی‌شود

artifact لینوکس بعد انتقال permission اجرا ندارد. قبل از chmod، OS، RID، نام فایل و permission را ثبت کن و سپس اصلاح را روی نسخهٔ کپی‌شده امتحان کن.

The Linux artifact lacks execute permission after transfer. Record OS, RID, filename, and permissions before changing anything; test the fix on a copy.

راهنما

فرمان اجرا و خروجی file/ls -l را با artifact مورد انتظار مقایسه کن. permission فقط یکی از فرضیه‌هاست؛ binary با معماری اشتباه با chmod درست نمی‌شود.

Compare the run command and file/permission evidence with the intended artifact. Permissions are only one hypothesis; chmod cannot fix a wrong-architecture binary.

runtime گم‌شده

مقصد می‌گوید framework Microsoft.NETCore.App پیدا نشد. خروجی publish و نصب runtime مقصد را بررسی و مدل تحویل را اصلاح کن.

The target reports that Microsoft.NETCore.App was not found. Inspect publish output and target runtime, then correct the delivery model.

راهنما

برای framework-dependent runtime سازگار لازم است؛ گزینهٔ دیگر publish self-contained برای RID صحیح و آزمایش دوباره روی محیط متناسب است. صرفاً نسخهٔ بالاتر runtime را تضمین فرض نکن.

Framework-dependent output needs a compatible runtime; alternatively publish self-contained for the correct RID and retest on a matching target. Do not assume any newer runtime guarantees compatibility.

برنامه فقط روی build machine کار می‌کند

پوشهٔ خروجی را روی VM تمیز اجرا کن. هر dependency یا config گمشده را با همان artifact آزمایش‌شده رفع و checksum را دوباره ثبت کن.

Run the output on a clean VM. Repair missing dependencies or configuration using the same tested artifact, then record its checksum again.

راهنما

source را کپی نکن تا اشتباهاً dotnet run جای artifact اجرا نشود. خطا، نسخهٔ OS/runtime و متغیرهای محیط را ثبت کن؛ اصلاح باید در publish/release قابل تکرار باشد.

Do not copy source, which could accidentally replace the artifact test with dotnet run. Record the error, OS/runtime, and environment; make the correction reproducible in the release process.

راهنمای تصمیم، نه جواب آمادهDecision hints, not a prebuilt answer

مقصد runtime نصب‌شده دارد؟Does the target have a runtime?

اگر بله و کنترل نسخه دست توست، framework-dependent می‌تواند بسته را کوچک‌تر کند. اگر نه، self-contained را برای RID مقصد بسنج؛ حجم بیشتر و مسئولیت به‌روزرسانی runtime همراه بسته را هم حساب کن.

If it does and you control its version, framework-dependent may reduce package size. Otherwise evaluate self-contained for the target RID, accounting for size and runtime-update responsibility.

Trimming یا AOT را فعال کنم؟Should I enable trimming or AOT?

فقط وقتی اندازه یا startup مسئلهٔ سنجیده‌شده است. reflection، serializer و dynamic loading را تست کن، هشدارهای analyzer را حل کن و artifact نهایی را روی مقصد اجرا کن.

Only when size or startup is a measured concern. Test reflection, serializers, and dynamic loading, resolve analyzer warnings, and run the final artifact on the target.

بستهٔ تحویل به نفر بعدHandoff to the next operator

در README بنویس: نسخه، commit منبع، TFM، RID، مدل انتشار، فرمان build، checksum، نیازمندی‌های مقصد، تنظیمات بدون secret، فرمان اجرا، smoke-test output، failureهای شناخته‌شده و روش برگشت به نسخهٔ قبلی. build موفق کافی نیست؛ نفر بعد باید بتواند از روی همین سند همان artifact را اجرا و هویت آن را تأیید کند.

Document version, source commit, TFM, RID, publish model, build command, checksum, target prerequisites, non-secret configuration, run command, smoke-test output, known failures, and rollback. A successful build is not enough; the next operator must reproduce the run and verify artifact identity from this handoff.

محدودهٔ دورهٔ پلتفرم اینجا کامل می‌شود: از project/build تا runtime، diagnostics و تحویل artifact. برای انتشار سرویس وب، reverse proxy، health و عملیات سرور وارد قلمرو ASP.NET و استقرار می‌شویم.

This completes the platform track: project/build, runtime, diagnostics, and artifact delivery. Publishing a web service with a reverse proxy, health, and server operations belongs to ASP.NET and deployment.
