خروجی کوچک‌تر، اما با چه محدودیتی؟

A smaller deployment, but with which trade-offs?

تیم می‌خواهد artifact را کوچک کند و startup را سریع‌تر کند. همکارش هم‌زمان single-file، trim و AOT را روشن می‌کند؛ برنامه بالا می‌آید، اما typeهایی که با reflection پیدا می‌شدند ناپدید شده‌اند. این سه گزینه را یکی نمی‌گیریم: هرکدام مسئله‌ای جدا و هزینه‌ای جدا دارند.

The team wants a smaller artifact and faster startup. Someone enables single-file, trimming, and AOT at once; the app starts, but types discovered through reflection are missing. These are separate options with separate goals and costs.

سه گزینه، سه مسئلهٔ متفاوتThree options, three different problems

Single-file فایل‌های publish را در قالب بسته‌بندی متفاوت می‌دهد. Trimming تلاش می‌کند کد managed استفاده‌نشده را حذف کند؛ اگر استفاده فقط در runtime و از راه reflection معلوم شود، تحلیل ایستا ممکن است آن را نبیند. Native AOT برنامه را پیش از اجرا به native code کامپایل می‌کند و محدودیت سازگاری/پلتفرم پررنگ‌تری دارد. برای سرعت startup هم ReadyToRun گزینهٔ دیگری است؛ هدفش trim یا AOT نیست.

Single-file changes how publish files are packaged. Trimming attempts to remove unused managed code; statically invisible reflection can hide required code. Native AOT compiles the app to native code ahead of time and has stronger compatibility/platform constraints. ReadyToRun is another startup-oriented option, not a synonym for trimming or AOT.

هر بار یک گزینه را روشن کنEnable one option at a time

اول baseline بساز: artifact عادی، اندازه، زمان startup، تست‌های integration و مسیرهای reflection. بعد فقط یک publish property را اضافه و هشدارهای trim را بازبینی کن. اگر چند property را هم‌زمان فعال کنی، وقتی تستی شکست خورد نمی‌فهمی کدام تغییر علت بوده.

Establish a baseline first: ordinary artifact, size, startup time, integration tests, and reflection paths. Then add one publish property and review trim warnings. Enabling several properties at once makes failures hard to attribute.

آزمایش جداگانه و برای RID مشخص
dotnet publish -c Release -r linux-x64 --self-contained true -p:PublishSingleFile=true
dotnet publish -c Release -r linux-x64 --self-contained true -p:PublishTrimmed=true
dotnet publish -c Release -r linux-x64 -p:PublishReadyToRun=true
dotnet publish -c Release -r linux-x64 -p:PublishAot=true

این‌ها چهار آزمایش مستقل‌اند، نه فرمانی که هر چهار را پشت‌سرهم برای deploy اجرا کنی. برای هر خروجی پوشهٔ جدا بساز، warningها را ذخیره کن و روی target واقعی تست کامل اجرا کن. trimming/AOT می‌تواند نیازمند self-contained باشد؛ انتخاب را در فرمان و پروژه صریح نگه دار.

These are four independent experiments, not a checklist to enable all at once. Use separate output directories, retain warnings, and run full tests on the real target. Trimming/AOT may require self-contained publishing; state the choice explicitly in command and project configuration.

هشدار linker را به سکوت تبدیل نکنDo not silence linker warnings

serializerها، pluginها، DI دستی و بارگذاری type با نام string می‌توانند به اطلاعاتی تکیه کنند که linker در زمان build نمی‌بیند. هشدار یعنی analyzer مطمئن نیست بخشی از برنامه حذف‌شدنی است یا نه. اول APIهای دارای annotation یا source-generation را ترجیح بده، نیاز dynamic را دقیق اعلام کن و warning را فقط وقتی suppress کن که دلیل و تست پوشش‌دهنده ثبت شده باشد.

Serializers, plugins, manual DI, and type loading by string can rely on information the linker cannot see at build time. A warning means the analyzer cannot prove whether code is safe to remove. Prefer annotated APIs or source generation, declare dynamic requirements precisely, and suppress warnings only with a documented reason and covering tests.

برنامه ممکن است compile شود و در اجرا ناقص باشدA program can compile and still fail at runtime

تست مسیرهای عادی کافی نیست؛ مسیرهای plugin، serialization، configuration و featureهای کم‌استفاده را هم اجرا کن. خروجی trimشده و AOTشده را جداگانه در محیطی شبیه مقصد واقعی بگذار.

Happy-path tests are insufficient; exercise plugins, serialization, configuration, and rarely used features. Run trimmed and AOT artifacts separately in an environment resembling the real target.

بهبود را اندازه بگیر، از روی اسم گزینه حدس نزنMeasure the benefit instead of trusting option names

اندازهٔ compressed artifact، زمان startup، مصرف حافظه و زمان build را قبل/بعد مقایسه کن. ReadyToRun ممکن است startup را بهتر کند اما حجم را بالا ببرد؛ AOT می‌تواند deployment را ساده کند اما build و سازگاری را محدودتر کند. معیار را مطابق مشکل واقعی انتخاب کن و نتایج را روی سخت‌افزار/سیستم‌عامل مقصد ثبت کن.

Compare compressed artifact size, startup, memory, and build duration. ReadyToRun may improve startup while increasing size; AOT can simplify deployment while constraining builds and compatibility. Choose metrics tied to the real problem and measure on target hardware/OS.

بهینه‌سازی را به deploy واقعی وصل کنConnect optimization to the real deployment

بسته‌بندی، حذف کد، جلو انداختن JIT و کامپایل native چهار ایدهٔ یکسان نیستند. baseline بساز، هر تغییر را جدا اعمال کن، warningها را بفهم و artifact نهایی را روی مقصد آزمایش کن. کوچک‌تر یا سریع‌تر فقط وقتی پیشرفت است که featureها سالم بمانند و هزینهٔ نگهداری‌اش معلوم باشد.

Packaging, code removal, moving JIT work earlier, and native compilation are not the same idea. Establish a baseline, apply one change at a time, understand warnings, and test the final artifact on target. Smaller or faster is progress only if features remain correct and maintenance cost is understood.
