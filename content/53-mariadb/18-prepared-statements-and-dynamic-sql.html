جست‌وجو باید روی چند ستون و sort متفاوت اجرا شود؛ تیم اسم ستون رو با ? bind کرده و query خطا می‌ده.

Search must support different columns and sort orders. The team tried binding a column name with ?, and the query failed.

Prepared statement یک مشکل رو خیلی خوب حل می‌کنه: جداکردن data از SQL syntax. ولی ? جادو نیست و اسم table یا ستون رو parameter نمی‌کنه. این فصل دقیقاً مرز value و identifier رو باز می‌کنه.

Prepared statements solve one problem very well: separating data values from SQL syntax. But ? is not magic and does not parameterize table or column names. This chapter makes the value/identifier boundary explicit.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: مرز parameter و dynamic SQL امن. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is the boundary between parameters and safe dynamic SQL. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

Value رو bind کن، syntax رو نهBind values, not SQL syntax

WHERE id = ? درست هست چون placeholder جای یک value می‌نشیند. FROM ? درست نیست چون نام table بخشی از grammar هست. همین فرق ساده پایهٔ dynamic SQL امن هست.

با PREPARE و EXECUTE یک value رو bind می‌کنیم و بعد نمونهٔ identifier رو عمداً خراب می‌کنیم تا error خودش مرز رو نشان بدهد.

WHERE id = ? works because the placeholder represents a value. FROM ? does not, because a table name is part of SQL grammar. That simple distinction is the foundation of safe dynamic SQL.

Bind a value with PREPARE/EXECUTE, then deliberately try an identifier placeholder so the failure makes the boundary visible.

SET @s='SELECT ? + 1'; PREPARE p FROM @s; SET @v=3; EXECUTE p USING @v;

این کد رو روی lab اجرا کن و فقط به «بدون خطا تمام شد» اکتفا نکن. خروجی یا state بعدش باید دربارهٔ مرز parameter و dynamic SQL امن یک چیز مشخص بهت بگه؛ همون چیز رو در پاسخ ثبت کن.

Identifier پویا یعنی allowlistDynamic identifiers require an allowlist

اگه کاربر می‌تونه sort رو بین created_at و total انتخاب کند، ورودی خام رو به SQL نچسبان. یک map ثابت از نام‌های مجاز به identifier واقعی بساز.

همین کار رو برای جهت sort هم بکن. ASC/DESC هم value نیستن؛ بخشی از syntax هستن و باید از مجموعهٔ محدود انتخاب شوند.

If a user can choose sorting by created_at or total, never concatenate raw input. Map a small set of public choices to fixed internal identifiers.

Do the same for sort direction. ASC and DESC are syntax, not values, so select them from a fixed allowlist.

Prepared statement به session وصل استPrepared statements have session scope

در SQL سطح server، statement آماده‌شده به همان session وابسته هست. اگه connection pool داری، نباید فرض کنی PREPARE در connection A روی connection B هم وجود داره.

همین scope روی cleanup هم اثر داره؛ statement رو بعد استفاده DEALLOCATE کن یا lifecycle connection رو روشن نگه دار.

At the SQL level, a prepared statement belongs to its session. With connection pooling, do not assume a statement prepared on connection A exists on connection B.

That scope also matters for cleanup. Deallocate statements when appropriate and understand the lifetime of the connection that owns them.

SET @s='SELECT ? IS NULL AS is_null';
PREPARE p FROM @s;
SET @v=NULL;
EXECUTE p USING @v;
DEALLOCATE PREPARE p;

امنیت رو با payload بد آزمایش کنTest the boundary with hostile input

به‌جای اینکه فقط بنویسیم «SQL Injection بد است»، روی fixture یک ورودی با quote و syntax اضافه می‌فرستیم. نسخهٔ parameterized باید آن رو data ببیند، نه command.

همان ورودی رو در string concatenation خطرناک مقایسه می‌کنیم، ولی فقط روی محیط دورریختنی. هدف exploit نیست؛ دیدن مرز parser هست.

Instead of merely saying “SQL injection is bad,” send hostile-looking input to a disposable fixture. The parameterized version should treat it as data, not executable SQL.

Compare that with unsafe string concatenation only in the lab. The goal is not exploitation; it is making the parser boundary observable.

SELECT TABLE_NAME
FROM information_schema.TABLES
WHERE TABLE_SCHEMA=DATABASE()
  AND TABLE_NAME IN ('customers','orders');

این query قرار نیست چیزی رو تعمیر کنه؛ فقط state رو قابل‌دیدن می‌کنه. مقدارهای مرتبط با parse/execute behavior، allowlist و نتیجهٔ ورودی خطرناک رو ثبت کن و قبل از هر تغییر بعدی snapshot رو نگه دار.

This query is observational. Capture the relevant state before changing anything so later conclusions about the boundary between parameters and safe dynamic SQL can be tied to evidence.
