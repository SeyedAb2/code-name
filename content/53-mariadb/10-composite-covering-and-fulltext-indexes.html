Searching by title and status is slow. Two separate indexes exist, but the query still sorts.

دو index جدا همیشه جواب query چندستونی نیست. این فصل ترتیب ستون‌های composite index، covering شدن query و جست‌وجوی FULLTEXT رو با workload واقعی کنار هم می‌گذارد؛ نه اینکه سه feature رو جداگانه حفظ کنیم.

Two separate indexes are not automatically the right answer for a multi-column query. This chapter connects composite-key order, covering behavior, and FULLTEXT search to concrete workloads instead of teaching three disconnected features.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: طراحی composite/covering/FULLTEXT بر اساس workload. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is workload-driven composite, covering, and FULLTEXT design. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

ترتیب ستون‌ها از شکل query میادColumn order comes from query shape

برای queryی که customer_id equality داره و بعد روی زمان sort/range می‌کنه، ترتیب index مهم هست. index رو از روی اسم ستون‌ها نمی‌چینیم؛ از روی predicate و order واقعی query می‌چینیم.

بعد عمداً queryی می‌زنیم که فقط ستون دوم index رو داره تا ببینیم چرا composite index یک «کیسهٔ سه‌ستونی» نیست که هر ستونش مستقل کار کند.

For a query that uses equality on customer_id and then sorts or ranges by time, key order matters. Design the index from the real predicates and ordering, not from a list of columns.

Then deliberately query only the second key column to show why a composite index is not a bag of independently searchable columns.

CREATE INDEX ix_order_customer_status_created ON orders(customer_id,status,created_at);

ساختن index هنوز پایان تمرین نیست. همون query قبلی رو دوباره اجرا کن و از روی plan، ترتیب کلید، covering behavior و هزینهٔ write ثابت کن این index واقعاً چه چیزی رو عوض کرده.

Creating the index is not the result. Re-run the original query and show how the observed plan or runtime changed before claiming a benefit.

Covering یعنی table access کمتر؛ نه رایگانCovering can reduce lookups, but it is not free

اگه query فقط ستون‌هایی رو بخواهد که در index هستن، engine ممکن هست بدون برگشتن به table جواب بدهد. این می‌تونه عالی باشد، مخصوصاً روی readهای پرتکرار.

ولی هر ستون اضافه index رو پهن‌تر می‌کنه. پس covering رو فقط وقتی می‌خوایم که read benefit آن روی workload واقعی، storage و write cost رو توجیه کند.

If every required column is available from the index, the engine may answer without returning to the base table. That can be valuable for frequent reads.

But every extra indexed value widens the structure. Use covering indexes when measured read benefits justify their storage and write cost.

EXPLAIN SELECT customer_id,created_at FROM orders WHERE customer_id=7;

FULLTEXT جای %word% نیست؛ مدل دیگری استFULLTEXT is a different search model

LIKE '%data%' و FULLTEXT دو سؤال یکسان رو با دو implementation متفاوت نمی‌پرسند. FULLTEXT tokenization، stopword و modeهای خودش رو داره؛ پس نباید فقط به خاطر سرعت، معنی جست‌وجو رو عوض کنی.

چند عبارت کوتاه و boolean mode رو روی fixture مشخص اجرا می‌کنیم تا بفهمیم چه چیز match می‌شه و چه چیز نه.

LIKE '%data%' and FULLTEXT do not necessarily express identical search semantics. FULLTEXT has tokenization, stop-word behavior, and search modes of its own, so performance is not a reason to silently change what “search” means.

Use a small controlled fixture and test short terms and boolean mode so matches and non-matches are observable.

Index overlap رو به حال خودش رها نکنDo not ignore overlapping indexes

بعد از چند ماه tuning ممکن هست customer_id، (customer_id,status) و (customer_id,status,created_at) کنار هم مانده باشند. بعضی‌شان شاید هنوز لازم باشند، بعضی شاید فقط write cost بدهند.

قبل از حذف، usage و constraintها رو بررسی کن. حذف index هم یک تغییر production هست؛ نه housekeeping بی‌خطر.

Months of tuning can leave several overlapping indexes behind. Some may still be justified; others may only add write and storage cost.

Inspect usage and constraint dependencies before dropping anything. Removing an index is a production change, not harmless housekeeping.
