یک batch سفارش ممکن هست وسط کار روی SKU نامعتبر fail شود؛ خطا رو چطور به rollback و خروجی قابل‌فهم تبدیل کنیم؟

A batch order may fail halfway on an invalid SKU. How do we turn that into rollback and a useful result?

Stored routine وقتی خوب هست که یک مرز مشخص از منطق رو نزدیک data نگه داره؛ وقتی بد هست که تبدیل شود به جایی که هر rule پنهانی رو توش می‌ریزیم. این فصل procedure، function و handler رو با خطای واقعی و transaction واقعی جلو می‌برد.

Stored routines are useful when they provide a clear data-side boundary, and painful when they become a hiding place for every rule. This chapter teaches procedures, functions, and handlers through real failures and transaction behavior.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: routine قابل‌پیش‌بینی با handler و transaction روشن. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is predictable routines with explicit handlers and transaction ownership. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

Procedure رو با contract شروع کنStart a procedure from its contract

اول بگو ورودی چیست، خروجی چیست و failure چه شکلی برمی‌گردد. بعد procedure رو بنویس. اگه این سه چیز معلوم نیست، signature هم هنوز طراحی نشده.

پارامترهای IN, OUT و result set رو روی مثال کوچک می‌بینیم و با SHOW CREATE PROCEDURE تعریف واقعی رو ثبت می‌کنیم.

Define inputs, outputs, and failure behavior before writing a procedure. If those are unclear, the routine's contract is not designed yet.

Use a small example to observe IN, OUT, and result-set behavior, then preserve the actual definition with SHOW CREATE PROCEDURE.

CREATE PROCEDURE list_stock() SELECT id,quantity FROM stock;

این object عمداً کوچک و آزمایشیه تا behavior رو بدون سر و صدای production ببینیم. بعد از ساخت، با metadata یا یک query مستقل ثابت کن چیزی که می‌خواستیم واقعاً ساخته شده.

The object is intentionally small and disposable. After creating it, use independent metadata or a query to prove that the intended behavior really exists.

Handler رو با خطای عمدی یاد بگیرLearn handlers through a deliberate error

Handler وقتی معنی پیدا می‌کنه که error واقعی داشته باشیم. یک constraint رو می‌شکنیم، handler رو وارد مسیر می‌کنیم و می‌بینیم کدام state باید rollback شود و چه چیزی باید به caller برگردد.

هدف این نیست که هر خطایی رو swallow کنیم. بعضی errorها باید بعد از cleanup دوباره بالا بروند تا برنامه بفهمد operation انجام نشده.

A handler becomes meaningful only when there is a real error to handle. Break a constraint deliberately, route it through a handler, and observe which state must roll back and what the caller should receive.

The goal is not to swallow every error. Some failures should be re-signaled after cleanup so the application knows the operation did not complete.

DECLARE EXIT HANDLER FOR SQLEXCEPTION ROLLBACK;

به ترتیب اجرا دقت کن. این تمرین دربارهٔ syntax نیست؛ دربارهٔ state قبل و بعد transactionه. بعد از پایان، یک SELECT مستقل بزن تا چیزی که commit یا rollback شده با چشم دیده بشه.

Focus on state before and after the transaction. Finish with an independent query so commit/rollback behavior is observable.

Function رو side effect free نگه دار تا جای ممکنKeep functions predictable

Function رو برای تبدیل/محاسبه‌ای که داخل expression استفاده می‌شه می‌خوایم. اگه function شروع کند به تغییر state پنهانی، خواندن query خیلی سخت می‌شه.

DETERMINISTIC رو فقط وقتی بنویس که واقعاً از ورودی‌های یکسان نتیجهٔ یکسان می‌گیری؛ این keyword قول تو به server هست، نه دکمهٔ افزایش سرعت.

Functions are most useful for predictable computation inside expressions. Hidden state changes make queries much harder to reason about.

Mark a function DETERMINISTIC only when equal inputs really produce equal results. The keyword is a contract with the server, not a performance switch.

CREATE FUNCTION twice(x INT) RETURNS INT DETERMINISTIC RETURN x*2;

این object عمداً کوچک و آزمایشیه تا behavior رو بدون سر و صدای production ببینیم. بعد از ساخت، با metadata یا یک query مستقل ثابت کن چیزی که می‌خواستیم واقعاً ساخته شده.

The object is intentionally small and disposable. After creating it, use independent metadata or a query to prove that the intended behavior really exists.

Transaction boundary باید یک صاحب داشته باشدGive the transaction boundary one owner

یکی از سؤال‌های مهم این هست که transaction رو routine مدیریت می‌کنه یا caller. اگه هر دو بدون قرارداد روشن commit/rollback کنند، رفتار سیستم مبهم می‌شه.

در lab یک مسیر موفق و یک failure می‌سازیم، state رو بعد هرکدام می‌خونیم و contract رو کنار routine مستند می‌کنیم.

One important design choice is whether the routine owns the transaction or the caller does. If both commit and roll back without an explicit contract, behavior becomes ambiguous.

In the lab, run one successful path and one failure path, inspect state afterwards, and document the transaction contract beside the routine.

CALL safe_adjust(999,-1);
