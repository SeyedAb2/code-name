MariaDB · فصل 7MariaDB · Chapter 7

یک جدول cache بعد از shutdown ناگهانی برگشته، اما جدول sessionها بخشی از تغییراتش رو از دست داده. آیا Aria همان InnoDB هست؟

After an abrupt shutdown, a cache table recovered while a session table lost changes. Is Aria equivalent to InnoDB?

Aria رو خیلی راحت می‌شه با «InnoDB سبک‌تر» اشتباه گرفت، مخصوصاً وقتی گزینه‌ای به اسم TRANSACTIONAL می‌بینی. این فصل دقیقاً همین برداشت رو می‌شکند: crash-safety، rollback و ACID یک چیز نیستن.

Aria is easy to misread as a lighter InnoDB, especially when an option named TRANSACTIONAL appears. This chapter breaks that assumption: crash safety, rollback behavior, and full ACID transactions are not the same thing.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: فرق Aria، InnoDB و engineهای قدیمی. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is the differences among Aria, InnoDB, and legacy engines. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

اول قابلیت رو از metadata بخوانRead capabilities from metadata first

به‌جای اینکه از اسم engine نتیجه بگیریم، information_schema.ENGINES رو می‌خونیم. ستون‌های transaction و savepoint سریع نشان می‌دن کدام engine چه قراردادی داره.

همین عادت جلوی خیلی از migrationهای خطرناک رو می‌گیره. اگه table روی engine قدیمی هست، اول نیاز workload رو می‌فهمیم؛ بعد تصمیم می‌گیریم تبدیل لازم هست یا نه.

Instead of inferring behavior from an engine name, inspect information_schema.ENGINES. Transaction and savepoint capabilities make the contract explicit.

This habit prevents dangerous migrations. If a table uses a legacy engine, understand the workload requirement first and only then decide whether conversion is necessary.

TRANSACTIONAL=1 رو درست بخوانRead `TRANSACTIONAL=1` carefully

در Aria این گزینه دربارهٔ crash-safe بودن operationها و log خودش هست؛ آن رو با transactionهای InnoDB یکی نکن. بهترین راه فهمیدن این فرق یک آزمایش کوچک با START TRANSACTION و ROLLBACK روی table دورریختنی هست.

اگه چیزی rollback نشد، از روی اسم گزینه تعجب نکن؛ قراردادی رو که engine واقعاً ارائه می‌ده ملاک بگیر.

For Aria, the TRANSACTIONAL option relates to its crash-safety behavior and logging; it does not turn Aria into InnoDB. A small disposable START TRANSACTION/ROLLBACK experiment makes the difference concrete.

If a change does not roll back, do not let the option name override observed behavior. Use the guarantees the engine actually provides.

START TRANSACTION; INSERT INTO a_tx VALUES(1,1); ROLLBACK;

Focus on state before and after the transaction. Finish with an independent query so commit/rollback behavior is observable.

Aria و MyISAM رو موزه نکنDo not turn legacy engines into a museum tour

لازم نیست ده‌ها engine رو حفظ کنی. کافی هست بفهمی چرا یک engine غیرتراکنشی ممکن هست هنوز در schema قدیمی یا بعضی استفاده‌های خاص دیده شود، و چه محدودیتی برای writerهای هم‌زمان و recovery داره.

تمرکز ما decision است: برای data اصلی برنامه، نیاز durability و concurrency چیست؟ برای data بازتولیدپذیر یا جدول موقت چه چیزهایی قابل‌قبول هست؟

You do not need to memorize every historical engine. Understand why a non-transactional engine may still appear in older schemas or specialized workloads, and what that means for concurrent writers and recovery.

Focus on decisions: what durability and concurrency guarantees are required for primary application data, and what compromises are acceptable for disposable or rebuildable data?

تبدیل رو با before/after ثابت کنProve an engine conversion before and after

وقتی Aria رو به InnoDB تبدیل می‌کنی، فقط Query OK رو نگه ندار. قبل و بعد engine، row count، DDL و چند query مهم رو ثبت کن.

اگه table بزرگ هست، duration، فضای آزاد و lock رو هم اندازه بگیر. مهاجرت engine یک تغییر storage هست، نه فقط تغییر یک کلمه در DDL.

When converting Aria to InnoDB, do not keep only Query OK as evidence. Record engine metadata, row counts, DDL, and key query results before and after.

For large tables, also measure duration, free space, and locking. An engine migration is a storage operation, not merely a one-word DDL edit.
