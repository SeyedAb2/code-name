File/position replication works, but GTIDs make it easier to identify transaction streams across a more complex topology. Trouble begins when similarly named GTID variables are treated as interchangeable.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: GTID و recovery بدون حدس position. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is GTID-based recovery without guessing positions. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

GTID رو به سه جزء بشکنBreak GTID into its three parts

در MariaDB GTID معمولاً شکل domain-server-sequence داره. domain stream منطقی رو جدا می‌کنه، server origin رو مشخص می‌کنه و sequence ترتیب داخل stream رو جلو می‌بره.

با چند مقدار واقعی این سه بخش رو می‌خونیم تا GTID از یک رشتهٔ مرموز تبدیل به مدل قابل‌فهم بشه.

A MariaDB GTID typically has the form domain-server-sequence. The domain identifies a logical stream, the server component records origin, and the sequence advances within that stream.

Read several real values and separate the components so GTID stops looking like an opaque string.

SELECT @@global.gtid_slave_pos,@@global.gtid_binlog_pos,@@global.gtid_current_pos;

slave_pos, binlog_pos, current_pos یکی نیستنThe GTID position variables are not interchangeable

Replica-applied state، locally logged state و ترکیب current state سؤال‌های متفاوتی هستن. قبل از هر recovery باید بدونی داری کدوم رو می‌خونی.

یک local write روی replica lab می‌زنیم و تفاوت positionها رو observe می‌کنیم تا خطر استفادهٔ کور از current_pos روشن بشه.

Replica-applied state, locally logged state, and combined current state answer different questions. Recovery steps must use the variable that matches the intended semantics.

Introduce a controlled local write on a lab replica and observe how positions differ. That makes the danger of blindly choosing current_pos concrete.

System table رو دستی دستکاری نکنDo not hand-edit GTID system state

اینکه mysql.gtid_slave_pos table هست به معنی این نیست که باید با UPDATE درستش کنی. از commandها و procedure مستند replication استفاده کن.

Manual edits خیلی راحت topology رو وارد stateی می‌کنن که ظاهراً جلو افتاده ولی data واقعاً apply نشده.

The fact that mysql.gtid_slave_pos is represented as data does not make manual UPDATE a safe recovery technique. Use documented replication controls.

Hand-editing positions can make topology metadata appear advanced even though the corresponding data was never applied.

بعد از reconnect، status و GTIDها رو می‌خونیم، ولی یک row marker هم لازم داریم. metadata سالم بدون data درست هنوز recovery کامل نیست.
