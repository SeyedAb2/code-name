قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: View به‌عنوان contract و مرز دسترسی. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is views as contracts and permission boundaries. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

View رو مثل قرارداد خروجی ببینTreat a view as an output contract

گزارش‌گیر فقط id و display_name می‌خواهد. پس به‌جای دادن SELECT روی table کامل، view کوچکی می‌سازیم که فقط همان ستون‌ها رو بیرون می‌ده.

اینجا SELECT * عمداً انتخاب بدی هست. اگه فردا ستون حساس تازه‌ای به table اضافه شود، contract view نباید بی‌خبر بزرگ شود.

A reporting user only needs id and display_name. Instead of granting access to the full table, create a narrow view that exposes exactly those columns.

This is one place where SELECT * is intentionally a poor choice. Adding a sensitive column to the base table later should not silently expand the view's contract.

CREATE VIEW public_customers AS SELECT id,display_name FROM customers;

این object عمداً کوچک و آزمایشیه تا behavior رو بدون سر و صدای production ببینیم. بعد از ساخت، با metadata یا یک query مستقل ثابت کن چیزی که می‌خواستیم واقعاً ساخته شده.

The object is intentionally small and disposable. After creating it, use independent metadata or a query to prove that the intended behavior really exists.

با همان کاربر محدود تست کنTest with the restricted account

SHOW GRANTS لازم هست ولی کافی نیست. بعد از ساخت view با account گزارش‌گیر وصل شو، view رو query کن و بعد عمداً table پایه رو بخوان. یکی باید موفق شود و یکی رد.

همین failure کنترل‌شده از ده خط توضیح بهتر ثابت می‌کنه مرز دسترسی واقعاً کار می‌کنه.

SHOW GRANTS is necessary but not sufficient. Connect as the reporting user, query the view, then deliberately query the base table. One should succeed and the other should fail.

That controlled failure proves the permission boundary more clearly than a page of description.

DEFINER و INVOKER رو قاطی نکنDo not blur DEFINER and INVOKER

View می‌تونه با context امنیتی definer یا invoker کار کند. این انتخاب مشخص می‌کنه privilege چه کسی موقع resolve کردن objectهای زیر view مهم هست.

SHOW CREATE VIEW رو بخوان و owner/definer رو مستند کن. account حذف‌شده یا privilege تغییرکرده می‌تونه بعداً view رو بشکند.

A view can execute with definer or invoker security context. That choice determines whose privileges matter when underlying objects are accessed.

Inspect SHOW CREATE VIEW and document ownership/definer state. Dropped accounts or changed privileges can break a view later.

View رو performance fix فرض نکنA view is not automatically a performance fix

View معمولی فقط query رو پشت اسم دیگری می‌گذارد؛ optimizer هنوز باید query واقعی رو حل کند. پس اگه report کند هست، اسمش رو view کردن مشکل رو جادویی حل نمی‌کنه.

Plan و indexها رو همان‌طور که برای query پایه بررسی می‌کنی بررسی کن. View ابزار abstraction و security هست؛ performance نتیجهٔ plan واقعی هست.

A normal view puts a name around a query; the optimizer still has to execute the underlying logic. Turning a slow report into a view does not magically tune it.

Inspect plans and indexes exactly as you would for the underlying query. Views provide abstraction and security; performance still comes from the actual execution plan.
