indexها زیاد شده‌اند و insertها کندترند، ولی کسی نمی‌داند کدام index واقعاً استفاده می‌شه.

There are many indexes and inserts are slower, but nobody knows which indexes are actually used.

وقتی indexها زیاد می‌شن، مشکل از «کمبود index» تبدیل می‌شه به «نمی‌دونیم کدام‌شان واقعاً ارزش دارن». این فصل maintenance رو از rebuild زمان‌بندی‌شده جدا می‌کنه و برمی‌گرداند به workload و مدرک.

Once indexes accumulate, the problem changes from “we need an index” to “we no longer know which indexes earn their cost.” This chapter separates real index maintenance from scheduled rebuild rituals and returns the discussion to workload evidence.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: maintenance مبتنی بر workload، نه ritual. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is workload-driven maintenance rather than rituals. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

Inventory قبل از tuningInventory before tuning

اول SHOW INDEX، اندازهٔ table/index و uptime رو ثبت می‌کنیم. بدون این baseline حتی نمی‌فهمی counter usage چند ساعت یا چند ماه history داره.

Performance Schema می‌تونه سرنخ usage بدهد، ولی restart یا reset history رو پاک می‌کنه. صفر بودن counter به‌تنهایی حکم حذف نیست.

Start by recording SHOW INDEX, table/index size, and uptime. Without that baseline, you do not even know whether a usage counter represents hours or months of history.

Performance Schema can provide useful usage evidence, but restarts and resets clear history. A zero counter by itself is not a drop decision.

Statistics با fragmentation یکی نیستStatistics and fragmentation are different problems

وقتی plan تخمین بد داره، شاید statistics مهم باشد. وقتی page layout مشکل داره، موضوع دیگری هست. این دو رو با یک maintenance job ثابت حل نمی‌کنیم.

ANALYZE TABLE رو با فرضیه اجرا کن و plan رو قبل و بعد مقایسه کن؛ نه اینکه هر شب بدون سؤال روی همهٔ tableها اجرا شود.

Bad cardinality estimates may point to statistics. Page layout or storage behavior is a different concern. Do not treat them as one problem solved by the same nightly maintenance job.

Run ANALYZE TABLE because you have a hypothesis, and compare the plan before and after rather than scheduling it blindly everywhere.

EXPLAIN SELECT * FROM orders WHERE customer_id=7;

بعد از اجرا فقط دنبال اسم index نگرد. plan رو کنار query بخون و روی usage counter، uptime، اندازهٔ index و baseline plan تمرکز کن. اگه plan با چیزی که پیش‌بینی کردی فرق داشت، همین اختلاف سؤال بعدی ماست.

Do not stop at the chosen index name. Read the plan in the context of the query and focus on usage counters, uptime, index size, and the baseline plan. Any mismatch with your prediction becomes the next investigation question.

Index بی‌صاحب رو پیدا کن، بعد آزمایش کنFind ownerless indexes, then test

برای هر index بنویس کدام query، constraint یا ordering به آن نیاز داره. اگه هیچ‌کس نتوانست جواب بدهد، candidate حذف هست؛ هنوز حذف نشده.

روی clone یا staging index رو بردار، queryهای مهم و write workload رو تکرار کن و فقط بعد از مشاهده تصمیم بگیر.

For each index, identify the query, constraint, or ordering requirement that depends on it. If no one can explain its purpose, it becomes a candidate for removal—not an automatic drop.

Remove it on a clone or staging environment, repeat critical reads and writes, and decide from observed behavior.

Maintenance خوب report قابل‌تکرار دارهGood maintenance is reproducible

یک گزارش خوب می‌گه چه baselineی داشتیم، چه indexی رو تغییر دادیم، چه queryهایی رو دوباره اجرا کردیم و چه عددی بهتر یا بدتر شد.

این مدل باعث می‌شه maintenance از «کارهایی که DBA همیشه انجام می‌ده» تبدیل شود به تغییر مهندسی قابل review.

A useful maintenance report states the baseline, the index change, the queries re-tested, and the metrics that improved or regressed.

That turns maintenance from inherited DBA ritual into an engineering change that can be reviewed and reproduced.
