فهرست سفارش‌ها کند هست؛ ستون customer_id index داره ولی query هنوز full scan می‌زند.

The order list is slow. customer_id is indexed, yet the query still scans the table.

این فصل از یکی از بدترین عادت‌های tuning شروع می‌کنه: «ستون index داره، پس query باید سریع باشد». نه. Index فقط یک مسیر ممکن هست؛ optimizer باید قانع شود که استفاده از آن از بقیهٔ مسیرها ارزان‌تر هست.

This chapter starts by breaking a common tuning habit: “the column is indexed, therefore the query must be fast.” An index is only a possible access path; the optimizer still decides whether using it is cheaper than the alternatives.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: مسیر دسترسی index و تصمیم optimizer. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is index access paths and optimizer choice. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

EXPLAIN جواب نیست؛ شاهد استEXPLAIN is evidence, not an answer

اول query رو بدون تغییر EXPLAIN می‌کنیم و چهار چیز رو کنار هم می‌خونیم: access type، key، برآورد rows و Extra. هیچ‌کدام به‌تنهایی حکم «خوب/بد» نیستن.

روی table خیلی کوچک full scan کاملاً منطقی هست. برعکس، دیدن اسم index هم تضمین نمی‌کنه query واقعاً کم‌هزینه هست. plan رو همیشه کنار اندازهٔ داده و predicate بخوان.

Start by explaining the unchanged query and reading access type, key, estimated rows, and Extra together. None of these fields alone is a universal good/bad verdict.

A full scan can be perfectly sensible on a tiny table. Likewise, seeing an index name does not guarantee a cheap query. Read plans in the context of data size and predicates.

EXPLAIN SELECT * FROM orders WHERE customer_id=42;

بعد از اجرا فقط دنبال اسم index نگرد. plan رو کنار query بخون و روی type، key، rows و Extra در plan تمرکز کن. اگه plan با چیزی که پیش‌بینی کردی فرق داشت، همین اختلاف سؤال بعدی ماست.

Do not stop at the chosen index name. Read the plan in the context of the query and focus on type, key, rows, and Extra in the plan. Any mismatch with your prediction becomes the next investigation question.

Index تک‌ستونی رو با query واقعی بسنجTest an index against the real query

یک index روی customer_id می‌سازیم، plan رو دوباره می‌گیریم و فقط بعد از مقایسه نتیجه می‌گیریم. این قبل/بعد مهم‌تر از خود CREATE INDEX هست.

بعد composite index می‌سازیم و عمداً فقط ستون دوم رو شرط می‌کنیم. اینجا leftmost-prefix از یک جملهٔ حفظی تبدیل می‌شه به چیزی که در plan می‌بینی.

Create an index on customer_id, explain the same query again, and draw conclusions only after comparing the plans. The before/after evidence matters more than the CREATE INDEX statement itself.

Then build a composite index and deliberately filter only on its second column. The leftmost-prefix rule becomes something visible in the plan instead of a memorized sentence.

CREATE INDEX ix_orders_customer_status ON orders(customer_id,status);

ساختن index هنوز پایان تمرین نیست. همون query قبلی رو دوباره اجرا کن و از روی type، key، rows و Extra در plan ثابت کن این index واقعاً چه چیزی رو عوض کرده.

Creating the index is not the result. Re-run the original query and show how the observed plan or runtime changed before claiming a benefit.

Index فقط یکی از مسیرهای ممکنه؛ optimizer با توجه به query و آمار انتخابش می‌کنه.

An index is only one possible access path; the optimizer chooses based on the query and statistics.

تابع روی ستون می‌تونه مسیر رو خراب کندA function on the column can change access

YEAR(created_at)=2026 برای آدم خواناست، ولی optimizer ممکن هست نتواند همان range مستقیم index رو استفاده کند. همان شرط رو به بازهٔ تاریخ تبدیل می‌کنیم و planها رو کنار هم می‌ذاریم.

این فصل قرار نیست واژهٔ SARGable رو جادویی کند. مدل ساده‌تر این است: آیا predicate اجازه می‌ده engine از نقطه‌ای در index شروع کند و یک range محدود بخواند، یا باید مقدار هر ردیف رو حساب کند؟

YEAR(created_at)=2026 is readable to a person, but it may prevent the optimizer from using a direct index range. Rewrite it as a date range and compare the plans.

Do not turn “SARGable” into magic vocabulary. Ask a simpler question: can the engine navigate directly to a bounded range in the index, or must it evaluate a function for rows first?

هزینهٔ write رو هم در صورت‌حساب بیاورInclude write cost in the decision

هر index تازه یعنی structure دیگری که INSERT و UPDATE باید نگه دارن. پس «این SELECT سریع‌تر شد» هنوز تصمیم نهایی نیست.

برای index جدی، queryهای صاحبش، فضای اضافه، write workload و overlap با indexهای قبلی رو ثبت کن. Index بی‌صاحب خیلی زود تبدیل به بدهی می‌شه.

Every new index is another structure that writes must maintain. “This SELECT became faster” is not yet a complete decision.

For a serious index, record which queries depend on it, its storage cost, write workload impact, and overlap with existing indexes. An index with no known owner quickly becomes operational debt.

مینی‌لب — از حدس تا مدرکMini-lab — from assumption to evidence

حالا سه checkpoint رو پشت‌سرهم اجرا کن. ترتیب مهمه: اول baseline، بعد یک تغییر یا مشاهدهٔ دقیق، بعد verification. وسط کار چیزی رو «درست» فرض نکن؛ هر مرحله باید خروجی مرحلهٔ بعد رو قابل‌تفسیرتر کنه.

Run three checkpoints as one small story. Order matters: establish a baseline, make one controlled observation/change, then verify. Do not assume success between steps; each checkpoint should make the next result easier to interpret.
