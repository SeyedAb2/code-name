جدول رخدادها به صدها میلیون ردیف رسیده؛ آیا partition همهٔ queryها رو سریع می‌کنه؟

The events table has hundreds of millions of rows. Will partitioning speed up every query?

Partitioning وقتی جذاب به نظر می‌رسه که table خیلی بزرگ شده، ولی یک دام کلاسیک داره: فکر کنیم خودش query رو سریع می‌کنه. این فصل partition رو بیشتر به‌عنوان ابزار تقسیم data و عملیات می‌بیند؛ سرعت فقط وقتی میاد که pruning و workload واقعاً هم‌راستا باشند.

Partitioning becomes attractive when a table grows very large, but it comes with a classic trap: assuming partitioning automatically makes queries fast. This chapter treats partitioning primarily as a data/operations boundary; performance benefits appear only when pruning and workload align.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: partition pruning و هزینهٔ عملیاتی جدول بزرگ. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is partition pruning and large-table operational cost. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

اول سؤال عملیاتی رو مشخص کنStart with the operational problem

ممکن هست مشکل اصلی query نباشد؛ شاید retention داری و باید هر ماه data قدیمی رو سریع کنار بگذاری. یا maintenance روی table چندصد میلیون ردیفی سخت شده. این‌ها دلیل‌های بهتری برای partitioning هستن تا جملهٔ «جدول بزرگ است».

قبل از ساخت partition، pattern دسترسی و lifecycle داده رو بنویس: بیشتر queryها روی چه بازه‌ای هستن و data قدیمی چه زمانی حذف می‌شه؟

The main problem may not be query speed at all. Perhaps old data must be retired monthly, or maintenance on a hundreds-of-millions-row table has become painful. Those are stronger reasons for partitioning than “the table is large.”

Before partitioning, document access patterns and data lifecycle: which ranges are commonly queried, and when should old data leave the system?

Pruning رو با plan ثابت کنProve pruning with the plan

همان query رو یک بار با predicate روی partition key و یک بار بدون آن اجرا می‌کنیم و EXPLAIN PARTITIONS رو می‌خونیم. اگه همهٔ partitionها باز می‌شن، هنوز مزیت pruning نگرفتی.

Predicate هم باید با تعریف partition هم‌خوان باشد. صرف اینکه created_at جایی در WHERE هست به‌تنهایی تضمین pruning نیست.

Run the same query with and without a useful predicate on the partition key and inspect EXPLAIN PARTITIONS. If every partition is touched, you have not earned a pruning benefit.

The predicate must align with the partition definition. Merely mentioning created_at somewhere in WHERE does not guarantee pruning.

EXPLAIN PARTITIONS SELECT COUNT(*) FROM event_part;

Partition جای index رو نمی‌گیرهPartitioning does not replace indexing

بعد از انتخاب partition، داخل هر بخش هنوز باید row مناسب پیدا شود. queryهای واقعی ممکن هست همچنان index بخواهند. بنابراین partition و index رو دو لایهٔ جدا ببین.

در lab indexهای table partitioned رو همان‌طور که روی table معمولی می‌خونی inspect کن و queryهای بدون date predicate رو هم اندازه بگیر.

After choosing partitions, the engine still needs to locate rows inside the selected data. Real queries can still require indexes, so treat partitioning and indexing as separate layers.

Inspect indexes on the partitioned table just as you would on a normal table, and measure queries that lack the partition-key predicate too.

DROP PARTITION عملیات حذف داده استDROP PARTITION deletes data

DROP PARTITION برای retention سریع جذاب هست چون می‌تونه حجم زیادی data رو یک‌جا کنار بگذارد. دقیقاً به همین دلیل خطرناک هم هست. قبلش row count همان partition و backup/recovery boundary رو ثبت کن.

این command رو فقط روی fixture اجرا می‌کنیم و بعد metadata رو دوباره می‌خونیم. روی production «اسم partition درست به نظر می‌رسه» مدرک کافی نیست.

DROP PARTITION is attractive for retention because it can remove a large data range efficiently. That same property makes it destructive. Record the target partition's row count and recovery boundary first.

Run it only on a fixture here, then inspect metadata again. In production, a partition name that “looks right” is not enough evidence.
