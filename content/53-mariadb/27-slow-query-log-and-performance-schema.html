گزارش کاربران می‌گه صفحه کند هست؛ server log پر از query هست. کدام query رو واقعاً باید بررسی کنیم؟

Users report a slow page and the server log is full of queries. Which query should we investigate?

وقتی می‌گیم «دیتابیس کند شده»، اولین سؤال باید این باشد: کدام query، چند بار، از چه زمانی و با چه هزینه‌ای؟ Slow Query Log و Performance Schema دو پنجرهٔ متفاوت برای جواب‌دادن به همین سؤال‌اند.

When someone says “the database is slow,” the first questions should be: which query, how often, since when, and at what cost? The slow query log and Performance Schema provide different views of that evidence.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: slow query evidence و instrumentation. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is slow-query evidence and instrumentation. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

Slow log رو قبل از روشن‌کردن بشناسUnderstand the slow log before enabling it

long_query_time فقط یک threshold هست و destination هم مهم هست. اگه logging رو بدون retention و privacy روشن کنی، شاید disk رو پر یا data حساس رو ثبت کنی.

اول variableهای مربوط رو inventory می‌کنیم: روشن/خاموش بودن، مقصد، threshold و rate limit. بعد یک query کنترل‌شده تولید می‌کنیم.

long_query_time is only one threshold, and log destination matters too. Enabling logging without retention and privacy controls can fill disks or capture sensitive data.

Inventory the relevant variables first: enabled state, destination, threshold, and sampling/rate options. Then generate a controlled slow query.

Digest می‌گه shape چقدر تکرار شدهDigests reveal repeated query shapes

Performance Schema statement digest literalها رو normalize می‌کنه تا query shapeهای پرتکرار رو ببینی. این برای پیدا کردن «هزار query کوچک» خیلی مفیدتر از نگاه‌کردن به یک log line هست.

COUNT_STAR و cumulative wait رو کنار هم بخوان؛ پرتکرارترین query لزوماً پرهزینه‌ترین query نیست.

Performance Schema statement digests normalize literals so repeated query shapes become visible. This is especially useful for finding thousands of individually small queries.

Read execution count and cumulative wait together; the most frequent query is not necessarily the most expensive query.

SHOW VARIABLES LIKE 'slow_query_log';

Rows examined رو کنار result size ببینCompare rows examined with useful rows

Query ممکن هست 10 ردیف برگرداند ولی میلیون‌ها ردیف examine کند. این نسبت سرنخ خوبی برای predicate/index نامناسب هست.

بعد همان query رو با ANALYZE FORMAT=JSON می‌بریم سراغ plan تا log رو به علت فنی نزدیک کنیم.

A query may return 10 rows after examining millions. That ratio is a strong clue for an inefficient predicate or access path.

Then inspect the same statement with ANALYZE FORMAT=JSON to connect log evidence to actual plan behavior.

SELECT DIGEST_TEXT,COUNT_STAR,SUM_TIMER_WAIT
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

Instrumentation هم هزینه و حریم خصوصی دارهInstrumentation has cost and privacy boundaries

هرچه بیشتر collect کنی، data و overhead بیشتری داری. قرار نیست همه‌چیز رو برای همیشه با بالاترین جزئیات نگه داری.

Retention، rotation، redaction و دسترسی به log رو کنار tuning بنویس. Observability بخشی از system هست، نه فایل فراموش‌شده در /var/log.

More instrumentation means more stored data and some overhead. The goal is not to capture everything forever at maximum detail.

Design retention, rotation, redaction, and log access along with tuning. Observability is part of the system, not a forgotten file under /var/log.

ANALYZE FORMAT=JSON SELECT * FROM lab_items WHERE id=1;

این مرحله فقط plan تخمینی نیست؛ execution واقعی هم وارد ماجرا می‌شه. خروجی رو نگه دار و threshold، digest، rows examined و cumulative wait رو با baseline قبلی مقایسه کن.

This step includes actual execution evidence rather than estimates alone. Preserve the output and compare it with the previous baseline while reasoning about slow-query evidence and instrumentation.
