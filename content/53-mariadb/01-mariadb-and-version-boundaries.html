MariaDB چیست و با MySQL چه نسبتی داره؟

What is MariaDB, and how is it related to MySQL?

برنامه روی لپ‌تاپ یکی از هم‌تیمی‌ها جواب می‌ده؛ روی سرور آزمایشی نه. هر دو می‌گن «MySQL داریم». قبل از تغییر query، بیا از خود مقصد بپرسیم دقیقاً چه محصول و نسخه‌ای آنجاست؛ اسم Client و برچسب image به‌تنهایی کافی نیست.

An application works on a teammate’s laptop but fails on the test server. Both say, “We have MySQL.” Before changing the query, let’s ask the actual target which product and version it runs; a client name or image label alone is not enough.

پیش‌نیازPrerequisite: SQL پایه و مفاهیم connection نسخهٔ مبنای دورهCourse baseline: MariaDB 11.8.9 · LTS زمانTime: ۹۵ دقیقه · ۱۸ تمرین

«روی هر دو MySQL داریم»؛ پس چرا رفتار فرق داره؟“Both run MySQL”—so why does behaviour differ?

یک migration با `JSON` روی لپ‌تاپ می‌گذرد. همان فایل روی سرور دیگر اجرا می‌شه، اما تعریف table چیزی نیست که تیم انتظار داشته. یکی می‌گه «نسخه‌ها رو یکی کن»، دیگری می‌گه «پس MariaDB همان MySQL است». هنوز هیچ‌کدام رو با مدرک ثابت نکردیم.

A migration using `JSON` succeeds on one laptop. The same file runs on another server, but the resulting table definition is not what the team expected. One person says “align the versions”; another says “MariaDB is just MySQL.” Neither claim has been proven yet.

MariaDB از دل تاریخ MySQL آمده، اما سال‌هاست مسیر توسعه و نسخه‌بندی خودش رو داره. بعضی پروتکل‌ها، Clientها و دستورها نزدیک‌اند؛ این نزدیکی به معنی یکسان‌بودن storage، optimizer، replication یا قابلیت‌های نسخه نیست. در این دوره هر تفاوت رو دقیق و با نسخه می‌گیم، نه با شعار «سازگار است».

MariaDB has historical roots in MySQL, but it has followed its own development and release path for years. Some protocols, clients, and commands are similar; that does not make storage, optimization, replication, or version-specific features identical. In this course we will name each difference precisely and attach it to a version—not rely on the slogan “compatible.”

اول هویت Server رو ثبت کنیمFirst, record the server’s identity

This means version-sensitive examples are interpreted against this series—not that every older install or future release behaves identically. Client، Server و image سه مدرک جدا هستنClient, server, and image are three different pieces of evidence

یک سیستم می‌تونه Client سازگار با MySQL داشته باشد و به MariaDB وصل شود. بنابراین `mariadb --version` نسخهٔ Client رو گزارش می‌کنه؛ `SELECT VERSION()` نسخهٔ Server را. در Docker هم tagی که `docker inspect` نشان می‌ده هویت image تنظیم‌شده هست، نه لزوماً نسخهٔ Serverی که query واقعاً به آن رسیده.

A machine can have a MySQL-compatible client connected to MariaDB. Therefore `mariadb --version` reports the client, while `SELECT VERSION()` reports the server. In Docker, the image tag shown by `docker inspect` identifies the configured image—not necessarily the server your query actually reached.

سه شاهد رو کنار هم بگذارPut three signals side by side
mariadb --version
docker inspect --format '{{.Config.Image}}' mariadb-course-lab
docker exec -it mariadb-course-lab mariadb -uroot -p -e "SELECT VERSION(), @@version_comment, @@hostname, @@port;"

نمونهٔ خروجی Client می‌تونه چیزی شبیه `Distrib 11.8.9-MariaDB` باشد؛ image برابر `mariadb:11.8.9` هست؛ و query از داخل همان container نسخه و host خود Server رو نشان می‌ده. این‌ها باید با هم جور باشند، ولی هر کدام سؤال جداگانه‌ای رو پاسخ می‌دن.

A representative client output might contain `Distrib 11.8.9-MariaDB`; the image can be `mariadb:11.8.9`; and the query inside that container reports the server’s own version and hostname. These should be consistent, but each answers a different question.

نسبت تاریخی نزدیک هست؛ قرارداد فنی رو باز هم آزمایش کنThe historical relationship is close; still test the technical contract

بخش‌هایی از اکوسیستم مشترک‌اند: ابزارهای اتصال زیادی با هر دو کار می‌کنن و شکل queryهای پایه آشناست. اما سازگاری باید در سطح موردنیاز برنامه سنجیده شود: نوع داده، collation، تابع، plugin احراز هویت، SQL mode، engine، رفتار replication و دستورهای مدیریت. یک `SELECT 1` فقط پاسخ‌گویی یک نشست رو ثابت می‌کنه؛ نه سازگاری migration را.

Parts of the ecosystem overlap: many connection tools work with both, and basic query shapes look familiar. But compatibility must be tested at the level the application depends on: data types, collations, functions, authentication plugins, SQL mode, engines, replication behaviour, and administration commands. A `SELECT 1` proves only that one session answered—not that a migration is compatible.

یک تفاوت واقعی رو با metadata ببین؛ وارد آموزش JSON نمی‌شیمObserve one real difference without turning this into the JSON lesson

برای اینکه «رفتارها فرق می‌کنن» حرف مبهمی نماند، یک نمونهٔ کوچک می‌سازیم. در MariaDB 11.8.9، نوع `JSON` aliasای برای `LONGTEXT` هست و تعریف table یک قید اعتبارسنجی JSON داره. MySQL نوع JSON بومی خودش رو داره. اینجا فقط DDL رو می‌بینیم؛ query و طراحی JSON فصل ۴ هست.

To keep “behaviour differs” from being vague, let’s inspect one small example. In MariaDB 11.8.9, `JSON` is an alias for `LONGTEXT`, and the table definition includes JSON validation. MySQL has its own native JSON type. We inspect only the DDL here; JSON queries and design belong to chapter 4.

در خروجی دنبال `longtext` و `json_valid(payload)` بگرد. این‌ها شاهد پیاده‌سازی در MariaDB 11.8 هستن؛ به معنی «JSON فقط متن هست و هیچ بررسی‌ای نداره» نیست، چون قید validation هم وجود داره. در MySQL همین تعریف رو روی Server MySQL جدا اجرا و `SHOW CREATE TABLE` رو مقایسه کن؛ دو Server رو با یک Client هم‌زمان اشتباه نگیر.

نسخه فقط یک عدد نیست؛ شاخه و هدف دوره رو نگه‌دارA version is more than a number; keep the series and target visible

MariaDB نسخه‌های LTS و انتشارهای کوتاه‌چرخه داره. این دوره برای مسیر اصلی روی MariaDB 11.8.9 می‌مونه؛ قابلیت‌های تازه‌تر یا رفتار release دیگر رو بی‌علامت وسط مثال وارد نمی‌کنیم. وقتی در فصل‌های بعد قابلیت نسخه‌محور شد، همان‌جا نسخهٔ شروع و محدودیتش رو می‌نویسیم.

MariaDB has LTS and shorter-cycle releases. The primary course path stays on MariaDB 11.8.9; we will not silently mix in newer features or another release’s behaviour. When a later chapter depends on a particular version, it will identify the version and its limits there.

نسخه رو در گزارش محیط همراه connection ثبت کنInclude the server version in an environment report

`@@sql_mode` و collation کمک می‌کنن تفاوت محیط رو پیدا کنیم؛ با این حال همین چند مقدار همهٔ تنظیمات رو پوشش نمی‌دن. اگه دو خروجی فرق دارن، به‌جای تغییر هم‌زمان همه چیز، یک تفاوت رو انتخاب و اثرش رو در lab بازتولید کن.

`@@sql_mode` and collation help expose environment differences, but these few values are not a complete configuration report. If two outputs differ, choose one difference and reproduce its effect in the lab instead of changing everything at once.

آزمایشگاه: «MySQL» رو به یک گزارش قابل‌اعتماد تبدیل کنLab: turn “MySQL” into a verifiable environment report

فرض کن همکار می‌گه migration در «MySQL» اجرا شده. پیش از تشخیص، از همان connection نسخه، comment محصول، host، port، SQL mode و collation رو بگیر. بعد روی Server دورریختنی MariaDB 11.8.9 همان گزارش رو اجرا و تفاوت رو ثبت کن. آخرش DDL آزمایشی `json_probe` رو ببین و توضیح بده کدام بخش از سازگاری فقط در سطح واژه هست و کدام بخش نیاز به تست واقعی داره.

A teammate says the migration ran on “MySQL.” Before diagnosing, collect version, product comment, host, port, SQL mode, and collation from that same connection. Then run the same report on the disposable MariaDB 11.8.9 server and record the differences. Finally inspect the `json_probe` DDL and explain which compatibility is only at the keyword level and which requires a real test.

Version and comment identify the product; SQL mode and collation are effective settings; DDL shows the resulting table definition. None replaces running the migration and testing the application.

۱) به Server سؤال کن، نه به نام برنامه1) Ask the server, not the application name

یک query بنویس که نسخه و comment محصول Server رو از همان connection برگرداند.

Write a query that returns the server version and product comment through the same connection.

مدرک ServerServer evidence
SELECT VERSION(), @@version_comment;

دنبال 11.8.x و MariaDB بگرد. نام Client یا متغیر تنظیم‌شده در فایل برنامه پاسخ قطعی نیست.

Look for 11.8.x and MariaDB. The client name or an application config variable is not definitive evidence.

۲) Client و Server رو جدا گزارش کن2) Report client and server separately

یک فرمان shell برای نسخهٔ Client و یک query برای نسخهٔ Server بساز؛ خروجی‌ها رو به یک عنوان مشترک نچسبان.

Use one shell command for the client version and one query for the server version; do not collapse them into one label.

دو لایه، دو فرمانTwo layers, two commands
mariadb --version
SELECT VERSION() AS ServerVersion;

اولی باینری Client رو گزارش می‌کنه؛ دومی از Server میاد. اختلاف نسخه لزوماً خطا نیست، اما باید سازگاری‌شان بررسی شود.

The first reports the client binary; the second comes from the server. A version mismatch is not automatically an error, but compatibility should be checked.

۳) مقصد رو ثبت کن3) Record the target

گزارش نسخه رو با hostname، پورت و connection ID کامل کن.

Extend the version report with hostname, port, and connection ID.

از همان نشستFrom the same session

این گزارش مقصدی رو که این نشست دیده ثبت می‌کنه، نه الزاماً مسیری که همهٔ برنامه‌ها استفاده می‌کنن.

This records the target seen by this session, not necessarily the route used by every application.

۴) SQL mode رو در دو Server مقایسه کن4) Compare SQL mode across two servers

روی دو محیط query بزن و مقدار مؤثر `sql_mode` رو کنار نسخه ثبت کن.

Query both environments and record effective `sql_mode` beside the version.

تفاوت رو با query پیدا کنFind the difference with a query
SELECT VERSION() AS ServerVersion, @@sql_mode AS EffectiveSqlMode;

اگه migration متفاوت رفتار می‌کنه، SQL mode یکی از فرضیه‌هاست؛ این خروجی به‌تنهایی علت رو ثابت نمی‌کنه.

If a migration behaves differently, SQL mode is one hypothesis; this output alone does not prove causation.

۵) engine پیش‌فرض رو بخوان5) Inspect the default engine

اولی پیش‌فرض ساخت‌های بعدی رو نشان می‌ده؛ دومی engine واقعی tableهای قابل‌مشاهده رو می‌خونه.

The first reports the default for new objects; the second queries the actual engines of visible tables.

تعریف فعلی، نه تمام تاریخچهCurrent definition, not full history
SHOW CREATE TABLE mariadb_identity_lab.json_probe\G

DDL فعلی نوع و قید رو نشان می‌ده، اما به‌تنهایی نمی‌گه table کجا و چه زمانی ساخته شده یا قبلاً تغییر کرده هست.

Current DDL shows type and constraints, but not where or when the table was created or how it changed before.

۱۳) تفاوت محصول رو در migration ثبت کن13) Record product identity in a migration report

یک query یک‌ردیفی برای گزارش محصول، نسخه و SQL mode بنویس.

Write a one-row report for product, version, and SQL mode.

هویت به‌علاوهٔ یک تنظیمIdentity plus one setting
SELECT @@version_comment AS Product,
       VERSION() AS ServerVersion,
       @@sql_mode AS SqlMode;

این رو کنار log migration ذخیره کن؛ credential یا دادهٔ حساس رو به گزارش اضافه نکن.

Save it beside migration logs; do not add credentials or sensitive data to the report.

۱۴) image رو با Server تطبیق بده14) Compare image identity with the server

نام image container رو از Docker بگیر و نسخه رو با query داخل همان container ثبت کن.

Read the container’s image name and compare it with a version query inside that same container.

دو فرمان بیرون و داخلOne check outside, one inside
docker inspect --format '{{.Config.Image}}' mariadb-course-lab
docker exec mariadb-course-lab mariadb -uroot -p -e "SELECT VERSION();"

اگه این‌ها ناسازگارند، اول نام container و مقصد connection رو ثابت کن؛ image tag به‌تنهایی query رو به آن وصل نمی‌کنه.

If they disagree, verify the container name and connection target first; an image tag does not route a query to that container by itself.

۱۵) Aria موجود هست یا default؟15) Is Aria available or the default?

با query متادیتا ثابت کن Aria در فهرست engineها هست و default واقعی Server رو هم جدا بخوان.

Use metadata to check whether Aria is listed, and separately read the server’s actual default engine.

فهرست engine و default جداستEngine inventory and default are separate
SHOW ENGINES;
SELECT @@default_storage_engine;

وجود Aria به معنی انتخاب خودکار آن برای tableهای جدید نیست؛ فصل ۵ تفاوت رو با آزمایش engine روشن می‌کنه.

Aria being available does not mean new tables use it automatically; chapter 5 tests engine choice directly.

۱۶) failure رو قبل از دست‌کاری schema تشخیص بده16) Diagnose before changing the schema

یک برنامه می‌گه JSON table رو نمی‌خونه. سه شاهد جمع کن که محصول، نسخه و تعریف table رو جدا کند.

An application says it cannot read a JSON table. Collect three signals that distinguish product, version, and table definition.

سه شاهد تشخیصیThree diagnostic signals
SELECT VERSION(), @@version_comment;
SHOW CREATE TABLE mariadb_identity_lab.json_probe\G
SELECT @@sql_mode;

این‌ها شروع عیب‌یابی‌اند، نه تشخیص نهایی driver یا query؛ خطای اصلی برنامه و نسخهٔ Client رو هم لازم داری.

These begin the diagnosis but do not identify the driver or query root cause; collect the application’s actual error and client version too.

۱۷) assertion نسخه برای script بنویس17) Write a version assertion for a script

queryای بنویس که نسخهٔ Server رو برگرداند تا migration runner بتواند پیش از تغییر آن رو ثبت کند؛ در توضیح بگو چرا string compare ساده کافی نیست.

Write a query returning the server version for a migration runner to record before changes; explain why a naive string comparison is insufficient.

نسخه رو ثبت کن، policy رو بیرون query بسازCollect version; keep policy outside the query
SELECT VERSION() AS ServerVersion;

نسخه می‌تونه suffix داشته باشد و ترتیب رشته‌ای همیشه ترتیب عددی نیست. runner باید componentهای نسخه رو parse کند و فقط نسخه‌های آزموده‌شده رو بپذیرد.

Versions can include suffixes, and lexical ordering is not numeric ordering. The runner should parse components and allow only tested versions.

۱۸) گزارش آمادهٔ مقایسه تحویل بده18) Hand off a comparison-ready report

یک query نهایی بنویس که محصول، نسخه، host، port، database و engine default رو در یک ردیف بدهد؛ بگو کدام موارد حساس رو نباید در ticket عمومی گذاشت.

Write a final query returning product, version, host, port, database, and default engine in one row; identify sensitive fields that should not go in a public ticket.

گزارش حداقلی محیطA minimal environment report
SELECT @@version_comment AS Product,
       VERSION() AS Version,
       @@hostname AS Host,
       @@port AS Port,
       DATABASE() AS CurrentDatabase,
       @@default_storage_engine AS DefaultEngine;

hostname یا نام database ممکن هست اطلاعات داخلی باشد. پیش از انتشار گزارش، اون‌ها رو بررسی یا mask کن؛ هیچ passwordی در خروجی query نیست.

Hostname or database names may be internal information. Review or mask them before sharing; the query does not expose a password.

حالا می‌دونیم با کدام Server حرف می‌زنیمNow we know which server we are talking to

MariaDB و MySQL ریشه‌های تاریخی مشترک و اکوسیستم نزدیک دارن، اما یکی‌گرفتنشان تصمیم امنی نیست. محصول و نسخه رو از همان connection خواندیم و یک تفاوت JSON رو در DDL دیدیم؛ هنوز رفتار برنامه رو کامل آزمایش نکردیم. فصل بعد Server رو در محیط تکرارپذیر بالا می‌آوریم و Client، port و readiness رو از هم جدا می‌کنیم.

MariaDB and MySQL share historical roots and a nearby ecosystem, but treating them as identical is not a safe assumption. We read product and version from the same connection and saw a JSON difference in DDL; application behaviour is not fully tested yet. Next we will run the server reproducibly and separate client, port, and readiness evidence.
