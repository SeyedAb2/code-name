MariaDB چیست و با MySQL چه نسبتی دارد؟

What is MariaDB, and how is it related to MySQL?

برنامه روی لپ‌تاپ یکی از هم‌تیمی‌ها جواب می‌دهد؛ روی سرور آزمایشی نه. هر دو می‌گویند «MySQL داریم». قبل از تغییر query، بیا از خود مقصد بپرسیم دقیقاً چه محصول و نسخه‌ای آنجاست؛ اسم Client و برچسب image به‌تنهایی کافی نیست.

An application works on a teammate’s laptop but fails on the test server. Both say, “We have MySQL.” Before changing the query, let’s ask the actual target which product and version it runs; a client name or image label alone is not enough.

پیش‌نیازPrerequisite: SQL پایه و مفاهیم connection نسخهٔ مبنای دورهCourse baseline: MariaDB 11.8.9 · LTS زمانTime: ۹۵ دقیقه · ۱۸ تمرین

«روی هر دو MySQL داریم»؛ پس چرا رفتار فرق دارد؟“Both run MySQL”—so why does behaviour differ?

یک migration با `JSON` روی لپ‌تاپ می‌گذرد. همان فایل روی سرور دیگر اجرا می‌شود، اما تعریف table چیزی نیست که تیم انتظار داشته. یکی می‌گوید «نسخه‌ها را یکی کن»، دیگری می‌گوید «پس MariaDB همان MySQL است». هنوز هیچ‌کدام را با مدرک ثابت نکرده‌ایم.

A migration using `JSON` succeeds on one laptop. The same file runs on another server, but the resulting table definition is not what the team expected. One person says “align the versions”; another says “MariaDB is just MySQL.” Neither claim has been proven yet.

MariaDB از دل تاریخ MySQL آمده، اما سال‌هاست مسیر توسعه و نسخه‌بندی خودش را دارد. بعضی پروتکل‌ها، Clientها و دستورها نزدیک‌اند؛ این نزدیکی به معنی یکسان‌بودن storage، optimizer، replication یا قابلیت‌های نسخه نیست. در این دوره هر تفاوت را دقیق و با نسخه می‌گوییم، نه با شعار «سازگار است».

MariaDB has historical roots in MySQL, but it has followed its own development and release path for years. Some protocols, clients, and commands are similar; that does not make storage, optimization, replication, or version-specific features identical. In this course we will name each difference precisely and attach it to a version—not rely on the slogan “compatible.”

اول هویت Server را ثبت کنیمFirst, record the server’s identity

مبنای آزمایش‌های این دوره MariaDB 11.8.9 است؛ شاخهٔ 11.8 یک LTS جامعه است. این انتخاب یعنی مثال‌های نسخه‌حساس را روی همین شاخه تفسیر می‌کنیم، نه اینکه هر نصب قدیمی یا هر انتشار بعدی رفتار یکسانی دارد. image رسمی Docker هم tag نسخه‌دار دارد؛ `latest` را برای آزمایش قابل‌بازتولید انتخاب نمی‌کنیم.

The course baseline is MariaDB 11.8.9, in the community LTS 11.8 series. This means version-sensitive examples are interpreted against this series—not that every older install or future release behaves identically. The official Docker image has versioned tags; we do not use `latest` for a reproducible lab.

Client، Server و image سه مدرک جدا هستندClient, server, and image are three different pieces of evidence

یک سیستم می‌تواند Client سازگار با MySQL داشته باشد و به MariaDB وصل شود. بنابراین `mariadb --version` نسخهٔ Client را گزارش می‌کند؛ `SELECT VERSION()` نسخهٔ Server را. در Docker هم tagی که `docker inspect` نشان می‌دهد هویت image تنظیم‌شده است، نه لزوماً نسخهٔ Serverی که query واقعاً به آن رسیده.

A machine can have a MySQL-compatible client connected to MariaDB. Therefore `mariadb --version` reports the client, while `SELECT VERSION()` reports the server. In Docker, the image tag shown by `docker inspect` identifies the configured image—not necessarily the server your query actually reached.

سه شاهد را کنار هم بگذارPut three signals side by side
mariadb --version
docker inspect --format '{{.Config.Image}}' mariadb-course-lab
docker exec -it mariadb-course-lab mariadb -uroot -p -e "SELECT VERSION(), @@version_comment, @@hostname, @@port;"

نمونهٔ خروجی Client می‌تواند چیزی شبیه `Distrib 11.8.9-MariaDB` باشد؛ image برابر `mariadb:11.8.9` است؛ و query از داخل همان container نسخه و host خود Server را نشان می‌دهد. این‌ها باید با هم جور باشند، ولی هر کدام سؤال جداگانه‌ای را پاسخ می‌دهند.

A representative client output might contain `Distrib 11.8.9-MariaDB`; the image can be `mariadb:11.8.9`; and the query inside that container reports the server’s own version and hostname. These should be consistent, but each answers a different question.

نسبت تاریخی نزدیک است؛ قرارداد فنی را باز هم آزمایش کنThe historical relationship is close; still test the technical contract

بخش‌هایی از اکوسیستم مشترک‌اند: ابزارهای اتصال زیادی با هر دو کار می‌کنند و شکل queryهای پایه آشناست. اما سازگاری باید در سطح موردنیاز برنامه سنجیده شود: نوع داده، collation، تابع، plugin احراز هویت، SQL mode، engine، رفتار replication و دستورهای مدیریت. یک `SELECT 1` فقط پاسخ‌گویی یک نشست را ثابت می‌کند؛ نه سازگاری migration را.

Parts of the ecosystem overlap: many connection tools work with both, and basic query shapes look familiar. But compatibility must be tested at the level the application depends on: data types, collations, functions, authentication plugins, SQL mode, engines, replication behaviour, and administration commands. A `SELECT 1` proves only that one session answered—not that a migration is compatible.

یک تفاوت واقعی را با metadata ببین؛ وارد آموزش JSON نمی‌شویمObserve one real difference without turning this into the JSON lesson

برای اینکه «رفتارها فرق می‌کنند» حرف مبهمی نماند، یک نمونهٔ کوچک می‌سازیم. در MariaDB 11.8.9، نوع `JSON` aliasای برای `LONGTEXT` است و تعریف table یک قید اعتبارسنجی JSON دارد. MySQL نوع JSON بومی خودش را دارد. اینجا فقط DDL را می‌بینیم؛ query و طراحی JSON فصل ۴ است.

To keep “behaviour differs” from being vague, let’s inspect one small example. In MariaDB 11.8.9, `JSON` is an alias for `LONGTEXT`, and the table definition includes JSON validation. MySQL has its own native JSON type. We inspect only the DDL here; JSON queries and design belong to chapter 4.

در خروجی دنبال `longtext` و `json_valid(payload)` بگرد. این‌ها شاهد پیاده‌سازی در MariaDB 11.8 هستند؛ به معنی «JSON فقط متن است و هیچ بررسی‌ای ندارد» نیست، چون قید validation هم وجود دارد. در MySQL همین تعریف را روی Server MySQL جدا اجرا و `SHOW CREATE TABLE` را مقایسه کن؛ دو Server را با یک Client هم‌زمان اشتباه نگیر.

These are evidence of MariaDB 11.8’s implementation; they do not mean “JSON is just unchecked text,” because a validation constraint is present. Run the same definition on a separate MySQL server and compare `SHOW CREATE TABLE`; do not mistake one client for two server products.

نسخه فقط یک عدد نیست؛ شاخه و هدف دوره را نگه‌دارA version is more than a number; keep the series and target visible

MariaDB نسخه‌های LTS و انتشارهای کوتاه‌چرخه دارد. این دوره برای مسیر اصلی روی MariaDB 11.8.9 می‌ماند؛ قابلیت‌های تازه‌تر یا رفتار release دیگر را بی‌علامت وسط مثال وارد نمی‌کنیم. وقتی در فصل‌های بعد قابلیت نسخه‌محور شد، همان‌جا نسخهٔ شروع و محدودیتش را می‌نویسیم.

MariaDB has LTS and shorter-cycle releases. The primary course path stays on MariaDB 11.8.9; we will not silently mix in newer features or another release’s behaviour. When a later chapter depends on a particular version, it will identify the version and its limits there.

نسخه را در گزارش محیط همراه connection ثبت کنInclude the server version in an environment report
SELECT VERSION() AS Version,
       @@version_comment AS Distribution,
       @@sql_mode AS EffectiveSqlMode,

`@@sql_mode` و collation کمک می‌کنند تفاوت محیط را پیدا کنیم؛ با این حال همین چند مقدار همهٔ تنظیمات را پوشش نمی‌دهند. اگر دو خروجی فرق دارند، به‌جای تغییر هم‌زمان همه چیز، یک تفاوت را انتخاب و اثرش را در lab بازتولید کن.

`@@sql_mode` and collation help expose environment differences, but these few values are not a complete configuration report. If two outputs differ, choose one difference and reproduce its effect in the lab instead of changing everything at once.

آزمایشگاه: «MySQL» را به یک گزارش قابل‌اعتماد تبدیل کنLab: turn “MySQL” into a verifiable environment report

فرض کن همکار می‌گوید migration در «MySQL» اجرا شده. پیش از تشخیص، از همان connection نسخه، comment محصول، host، port، SQL mode و collation را بگیر. بعد روی Server دورریختنی MariaDB 11.8.9 همان گزارش را اجرا و تفاوت را ثبت کن. آخرش DDL آزمایشی `json_probe` را ببین و توضیح بده کدام بخش از سازگاری فقط در سطح واژه است و کدام بخش نیاز به تست واقعی دارد.

A teammate says the migration ran on “MySQL.” Before diagnosing, collect version, product comment, host, port, SQL mode, and collation from that same connection. Then run the same report on the disposable MariaDB 11.8.9 server and record the differences. Finally inspect the `json_probe` DDL and explain which compatibility is only at the keyword level and which requires a real test.

Version and comment identify the product; SQL mode and collation are effective settings; DDL shows the resulting table definition. None replaces running the migration and testing the application.

۱) به Server سؤال کن، نه به نام برنامه1) Ask the server, not the application name

یک query بنویس که نسخه و comment محصول Server را از همان connection برگرداند.

Write a query that returns the server version and product comment through the same connection.

مدرک ServerServer evidence
SELECT VERSION(), @@version_comment;

دنبال 11.8.x و MariaDB بگرد. نام Client یا متغیر تنظیم‌شده در فایل برنامه پاسخ قطعی نیست.

Look for 11.8.x and MariaDB. The client name or an application config variable is not definitive evidence.

۲) Client و Server را جدا گزارش کن2) Report client and server separately

یک فرمان shell برای نسخهٔ Client و یک query برای نسخهٔ Server بساز؛ خروجی‌ها را به یک عنوان مشترک نچسبان.

Use one shell command for the client version and one query for the server version; do not collapse them into one label.

دو لایه، دو فرمانTwo layers, two commands
mariadb --version
SELECT VERSION() AS ServerVersion;

اولی باینری Client را گزارش می‌کند؛ دومی از Server می‌آید. اختلاف نسخه لزوماً خطا نیست، اما باید سازگاری‌شان بررسی شود.

The first reports the client binary; the second comes from the server. A version mismatch is not automatically an error, but compatibility should be checked.

۳) مقصد را ثبت کن3) Record the target

گزارش نسخه را با hostname، پورت و connection ID کامل کن.

Extend the version report with hostname, port, and connection ID.

از همان نشستFrom the same session

این گزارش مقصدی را که این نشست دیده ثبت می‌کند، نه الزاماً مسیری که همهٔ برنامه‌ها استفاده می‌کنند.

This records the target seen by this session, not necessarily the route used by every application.

۴) SQL mode را در دو Server مقایسه کن4) Compare SQL mode across two servers

روی دو محیط query بزن و مقدار مؤثر `sql_mode` را کنار نسخه ثبت کن.

Query both environments and record effective `sql_mode` beside the version.

تفاوت را با query پیدا کنFind the difference with a query
SELECT VERSION() AS ServerVersion, @@sql_mode AS EffectiveSqlMode;

اگر migration متفاوت رفتار می‌کند، SQL mode یکی از فرضیه‌هاست؛ این خروجی به‌تنهایی علت را ثابت نمی‌کند.

If a migration behaves differently, SQL mode is one hypothesis; this output alone does not prove causation.

۵) engine پیش‌فرض را بخوان5) Inspect the default engine

اولی پیش‌فرض ساخت‌های بعدی را نشان می‌دهد؛ دومی engine واقعی tableهای قابل‌مشاهده را می‌خواند.

The first reports the default for new objects; the second queries the actual engines of visible tables.

تعریف فعلی، نه تمام تاریخچهCurrent definition, not full history
SHOW CREATE TABLE mariadb_identity_lab.json_probe\G

DDL فعلی نوع و قید را نشان می‌دهد، اما به‌تنهایی نمی‌گوید table کجا و چه زمانی ساخته شده یا قبلاً تغییر کرده است.

Current DDL shows type and constraints, but not where or when the table was created or how it changed before.

۱۳) تفاوت محصول را در migration ثبت کن13) Record product identity in a migration report

یک query یک‌ردیفی برای گزارش محصول، نسخه و SQL mode بنویس.

Write a one-row report for product, version, and SQL mode.

هویت به‌علاوهٔ یک تنظیمIdentity plus one setting
SELECT @@version_comment AS Product,
       VERSION() AS ServerVersion,
       @@sql_mode AS SqlMode;

این را کنار log migration ذخیره کن؛ credential یا دادهٔ حساس را به گزارش اضافه نکن.

Save it beside migration logs; do not add credentials or sensitive data to the report.

۱۴) image را با Server تطبیق بده14) Compare image identity with the server

نام image container را از Docker بگیر و نسخه را با query داخل همان container ثبت کن.

Read the container’s image name and compare it with a version query inside that same container.

دو فرمان بیرون و داخلOne check outside, one inside
docker inspect --format '{{.Config.Image}}' mariadb-course-lab
docker exec mariadb-course-lab mariadb -uroot -p -e "SELECT VERSION();"

اگر این‌ها ناسازگارند، اول نام container و مقصد connection را ثابت کن؛ image tag به‌تنهایی query را به آن وصل نمی‌کند.

If they disagree, verify the container name and connection target first; an image tag does not route a query to that container by itself.

۱۵) Aria موجود است یا default؟15) Is Aria available or the default?

با query متادیتا ثابت کن Aria در فهرست engineها هست و default واقعی Server را هم جدا بخوان.

Use metadata to check whether Aria is listed, and separately read the server’s actual default engine.

فهرست engine و default جداستEngine inventory and default are separate
SHOW ENGINES;
SELECT @@default_storage_engine;

وجود Aria به معنی انتخاب خودکار آن برای tableهای جدید نیست؛ فصل ۵ تفاوت را با آزمایش engine روشن می‌کند.

Aria being available does not mean new tables use it automatically; chapter 5 tests engine choice directly.

۱۶) failure را قبل از دست‌کاری schema تشخیص بده16) Diagnose before changing the schema

یک برنامه می‌گوید JSON table را نمی‌خواند. سه شاهد جمع کن که محصول، نسخه و تعریف table را جدا کند.

An application says it cannot read a JSON table. Collect three signals that distinguish product, version, and table definition.

سه شاهد تشخیصیThree diagnostic signals
SELECT VERSION(), @@version_comment;
SHOW CREATE TABLE mariadb_identity_lab.json_probe\G
SELECT @@sql_mode;

این‌ها شروع عیب‌یابی‌اند، نه تشخیص نهایی driver یا query؛ خطای اصلی برنامه و نسخهٔ Client را هم لازم داری.

These begin the diagnosis but do not identify the driver or query root cause; collect the application’s actual error and client version too.

۱۷) assertion نسخه برای script بنویس17) Write a version assertion for a script

queryای بنویس که نسخهٔ Server را برگرداند تا migration runner بتواند پیش از تغییر آن را ثبت کند؛ در توضیح بگو چرا string compare ساده کافی نیست.

Write a query returning the server version for a migration runner to record before changes; explain why a naive string comparison is insufficient.

نسخه را ثبت کن، policy را بیرون query بسازCollect version; keep policy outside the query
SELECT VERSION() AS ServerVersion;

نسخه می‌تواند suffix داشته باشد و ترتیب رشته‌ای همیشه ترتیب عددی نیست. runner باید componentهای نسخه را parse کند و فقط نسخه‌های آزموده‌شده را بپذیرد.

Versions can include suffixes, and lexical ordering is not numeric ordering. The runner should parse components and allow only tested versions.

۱۸) گزارش آمادهٔ مقایسه تحویل بده18) Hand off a comparison-ready report

یک query نهایی بنویس که محصول، نسخه، host، port، database و engine default را در یک ردیف بدهد؛ بگو کدام موارد حساس را نباید در ticket عمومی گذاشت.

Write a final query returning product, version, host, port, database, and default engine in one row; identify sensitive fields that should not go in a public ticket.

گزارش حداقلی محیطA minimal environment report
SELECT @@version_comment AS Product,
       VERSION() AS Version,
       @@hostname AS Host,
       @@port AS Port,
       DATABASE() AS CurrentDatabase,
       @@default_storage_engine AS DefaultEngine;

hostname یا نام database ممکن است اطلاعات داخلی باشد. پیش از انتشار گزارش، آن‌ها را بررسی یا mask کن؛ هیچ passwordی در خروجی query نیست.

Hostname or database names may be internal information. Review or mask them before sharing; the query does not expose a password.

حالا می‌دانیم با کدام Server حرف می‌زنیمNow we know which server we are talking to

MariaDB و MySQL ریشه‌های تاریخی مشترک و اکوسیستم نزدیک دارند، اما یکی‌گرفتنشان تصمیم امنی نیست. محصول و نسخه را از همان connection خواندیم و یک تفاوت JSON را در DDL دیدیم؛ هنوز رفتار برنامه را کامل آزمایش نکردیم. فصل بعد Server را در محیط تکرارپذیر بالا می‌آوریم و Client، port و readiness را از هم جدا می‌کنیم.

MariaDB and MySQL share historical roots and a nearby ecosystem, but treating them as identical is not a safe assumption. We read product and version from the same connection and saw a JSON difference in DDL; application behaviour is not fully tested yet. Next we will run the server reproducibly and separate client, port, and readiness evidence.
