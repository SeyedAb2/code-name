EXPLAIN تخمین می‌زند صدها ردیف خوانده می‌شه، اما query در عمل ثانیه‌ها طول می‌کشد. تخمین و اجرا رو چطور جدا می‌کنی؟

EXPLAIN estimates a few hundred rows, but the query takes seconds. How do you separate estimates from execution?

EXPLAIN یک پیش‌بینی هست. این فصل لحظه‌ای رو می‌سازه که پیش‌بینی optimizer رو کنار چیزی که واقعاً موقع اجرا اتفاق افتاده می‌ذاری. همین فاصله خیلی وقت‌ها سرنخ اصلی کندی هست.

EXPLAIN is a prediction. This chapter puts the optimizer's estimate next to what actually happened during execution. The gap between the two is often the most useful clue in a slow query.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: فاصلهٔ estimate و اجرای واقعی. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is the gap between estimates and actual execution. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

Estimated و actual رو جدا نگه دارKeep estimated and actual evidence separate

با EXPLAIN هنوز query اجرا نشده. با ANALYZE در MariaDB query واقعاً اجرا می‌شه و plan با آمار runtime برمی‌گردد. همین یک فرق دلیل خوبی هست که ANALYZE رو روی statement خطرناک یا dataset ناشناخته کورکورانه نزنی.

روی SELECT امن، rows رو با r_rows و تعداد اجرا رو با r_loops مقایسه می‌کنیم. اگه estimate چند مرتبهٔ بزرگی خطا داره، سؤال بعدی statistics و توزیع داده هست.

EXPLAIN does not execute the query. MariaDB's ANALYZE does execute it and annotates the plan with runtime statistics. That distinction is exactly why ANALYZE must not be fired blindly at unsafe statements or unknown workloads.

On a safe SELECT, compare estimated rows with r_rows, and inspect r_loops. Large estimation errors point toward statistics and data distribution as the next line of investigation.

EXPLAIN SELECT * FROM orders WHERE customer_id=7;

بعد از اجرا فقط دنبال اسم index نگرد. plan رو کنار query بخون و روی estimate در برابر r_rows/r_loops و زمان واقعی تمرکز کن. اگه plan با چیزی که پیش‌بینی کردی فرق داشت، همین اختلاف سؤال بعدی ماست.

Do not stop at the chosen index name. Read the plan in the context of the query and focus on estimates versus r_rows/r_loops and actual timing. Any mismatch with your prediction becomes the next investigation question.

عدد زمان رو بدون context نخوانDo not read timing without context

اجرای اول ممکن هست cold cache باشد، اجرای دوم warm. هم‌زمان ممکن هست lock wait داشته باشی. پس یک عدد 420 ms به‌تنهایی چیز زیادی نمی‌گه.

پارامتر رو ثابت کن، چند بار اندازه بگیر، processlist رو کنار query ببین و اگه اختلاف زیاد بود دنبال علت بیرون از plan هم بگرد.

The first execution may use a cold cache while the next is warm. A lock wait can also dominate elapsed time. A single 420 ms number has little meaning by itself.

Keep parameters fixed, repeat measurements, inspect the process list, and look outside the plan when runtime variance suggests blocking or resource pressure.

SHOW TABLE STATUS LIKE 'orders';

این query قرار نیست چیزی رو تعمیر کنه؛ فقط state رو قابل‌دیدن می‌کنه. مقدارهای مرتبط با estimate در برابر r_rows/r_loops و زمان واقعی رو ثبت کن و قبل از هر تغییر بعدی snapshot رو نگه دار.

This query is observational. Capture the relevant state before changing anything so later conclusions about the gap between estimates and actual execution can be tied to evidence.

Statistics رو فقط وقتی لازم هست دست بزنRefresh statistics for a reason

ANALYZE TABLE رو به‌عنوان طلسم tuning اجرا نمی‌کنیم. اول اختلاف estimate/actual رو می‌بینیم، بعد اگه stale یا نامناسب بودن statistics فرضیهٔ منطقی بود refresh می‌کنیم و همان query رو دوباره اندازه می‌گیریم.

اگه plan هیچ تغییری نکرد هم نتیجه داریم: فرضیهٔ ما شاید اشتباه بوده. tuning خوب یعنی حاضر باشی فرضیه رو رد کنی.

Do not run ANALYZE TABLE as a tuning ritual. First observe an estimation problem; only then refresh statistics if stale statistics are a plausible hypothesis, and re-run the same query.

If the plan does not change, that is still useful evidence: the hypothesis may have been wrong. Good tuning is willing to falsify its own assumptions.

ANALYZE FORMAT=JSON
SELECT * FROM orders WHERE customer_id=7;

این مرحله فقط plan تخمینی نیست؛ execution واقعی هم وارد ماجرا می‌شه. خروجی رو نگه دار و estimate در برابر r_rows/r_loops و زمان واقعی رو با baseline قبلی مقایسه کن.

This step includes actual execution evidence rather than estimates alone. Preserve the output and compare it with the previous baseline while reasoning about the gap between estimates and actual execution.

JSON plan رو برای مقایسه نگه دارPreserve JSON plans for comparison

ANALYZE FORMAT=JSON خروجی‌ای می‌ده که می‌شه قبل و بعد تغییر ذخیره و مقایسه کرد. برای incident یا code review این خیلی بهتر از جملهٔ «به نظرم بهتر شد» هست.

مهم‌ترین بخش گزارش tuning همین است: query ثابت، dataset معلوم، قبل، تغییر واحد، بعد. هرچیزی غیر از این خیلی راحت با حدس قاطی می‌شه.

ANALYZE FORMAT=JSON gives you output that can be stored and compared before and after a change. That is much stronger evidence for incidents or reviews than “it seems faster now.”

A useful tuning report keeps the query and dataset stable, records a baseline, changes one thing, and measures again. Anything looser is easy to confuse with intuition.

SET @started = NOW(6);
SELECT COUNT(*) FROM orders WHERE customer_id=7;
SELECT TIMESTAMPDIFF(MICROSECOND,@started,NOW(6)) AS elapsed_us;

این کد رو روی lab اجرا کن و فقط به «بدون خطا تمام شد» اکتفا نکن. خروجی یا state بعدش باید دربارهٔ فاصلهٔ estimate و اجرای واقعی یک چیز مشخص بهت بگه؛ همون چیز رو در پاسخ ثبت کن.

مینی‌لب — از حدس تا مدرکMini-lab — from assumption to evidence

حالا سه checkpoint رو پشت‌سرهم اجرا کن. ترتیب مهمه: اول baseline، بعد یک تغییر یا مشاهدهٔ دقیق، بعد verification. وسط کار چیزی رو «درست» فرض نکن؛ هر مرحله باید خروجی مرحلهٔ بعد رو قابل‌تفسیرتر کنه.

Run three checkpoints as one small story. Order matters: establish a baseline, make one controlled observation/change, then verify. Do not assume success between steps; each checkpoint should make the next result easier to interpret.
