فایل JSON از MySQL به MariaDB منتقل شده و برنامه ناگهان روی نوع ستون و مقایسهٔ مقدارها اختلاف می‌بیند.

A JSON dataset moved from MySQL to MariaDB, and the application now sees differences in column type and value comparisons.

اسم ستون هنوز JSON هست، ولی این شباهت اسم نباید گول‌مون بزند. در MariaDB این نوع روی LONGTEXT سوار هست؛ پس قبل از مهاجرت، باید خود DDL، اعتبار سند، مقدار استخراج‌شده و رفتار مقایسه رو ببینیم. این فصل قرار نیست فقط چند تابع JSON حفظ کنیم؛ می‌خوایم بفهمیم دقیقاً چه چیزی بین MariaDB و MySQL شبیه هست و چه چیزی فقط شبیه به نظر می‌رسه.

The column is still called JSON, but the familiar name is not a compatibility guarantee. In MariaDB it is implemented on top of LONGTEXT, so a migration has to inspect the actual DDL, validation, extraction, and comparison behavior. The goal here is not to memorize JSON functions; it is to learn which similarities are real and which are only superficial.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: رفتار واقعی JSON و مرز سازگاری با MySQL. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is actual JSON behavior and the MySQL compatibility boundary. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

اسم یکی هست؛ storage یکی نیستSame name, different storage

فرض کن schema رو از MySQL آوردی و migration هم بدون خطا تمام شده. وسوسه می‌شی بگویی «پس تمام شد». هنوز نه. اولین کاری که می‌کنیم این هست که از خود MariaDB می‌پرسیم ستون رو واقعاً چطور ساخته. SHOW CREATE TABLE اینجا از اسم type مهم‌تر هست.

در MariaDB، JSON برای سازگاری اسم آشنایی داره، ولی پشت صحنه aliasی از LONGTEXT با validation هست. این فرق روی formatting خام، replication، بعضی comparisonها و migrationهایی که روی storage باینری MySQL حساب کرده‌اند اثر می‌گذارد.

Imagine importing a schema from MySQL and seeing the migration complete successfully. That is not enough evidence. The first useful check is to ask MariaDB how the column was actually created; SHOW CREATE TABLE is more informative than the type name alone.

In MariaDB, JSON is a compatibility-oriented alias built on LONGTEXT with validation. That difference matters for raw formatting, replication boundaries, some comparisons, and migrations that assumed MySQL's binary JSON storage.

CREATE TABLE json_lab(id INT PRIMARY KEY, doc JSON);

این object عمداً کوچک و آزمایشیه تا behavior رو بدون سر و صدای production ببینیم. بعد از ساخت، با metadata یا یک query مستقل ثابت کن چیزی که می‌خواستیم واقعاً ساخته شده.

The object is intentionally small and disposable. After creating it, use independent metadata or a query to prove that the intended behavior really exists.

اول سند معتبر؛ بعد pathValidate first, then query paths

حالا یک سند کوچک می‌ذاریم داخل جدول و دو سؤال جدا می‌پرسیم: «این متن JSON معتبر هست؟» و «مقدار plan چیست؟». این دو سؤال یکی نیستن. JSON_VALID دربارهٔ شکل سند حرف می‌زند؛ JSON_EXTRACT دربارهٔ یک مسیر داخل همان سند.

وقتی خروجی JSON_EXTRACT رو می‌بینی حواست باشد مقدار JSON با scalar معمولی یکی نیست. برای رشته‌ها معمولاً لازم هست با JSON_UNQUOTE یا تابع مناسب، مقدار متنی رو از نمایش JSON جدا کنی. همین جزئیات کوچک خیلی وقت‌ها منبع bug مهاجرت هست.

Put a small document into the table and ask two separate questions: “Is this text valid JSON?” and “What is the value at plan?” JSON_VALID answers the first question; JSON_EXTRACT answers the second.

The value returned by JSON_EXTRACT is still a JSON value, not automatically the same thing as an ordinary SQL scalar. For strings, JSON_UNQUOTE or an equivalent function often makes that distinction visible. Small differences like this frequently surface during migrations.

NULL رو با null قاطی نکنDo not confuse SQL NULL with JSON null

یکی از جاهایی که خیلی راحت query ظاهراً درست، نتیجهٔ عجیب می‌ده همین‌جاست. SQL NULL یعنی «مقدار SQL نداریم». JSON null یک token داخل سند هست. این دو تا رو کنار هم اجرا می‌کنیم تا فرق‌شان رو با چشم ببینی، نه اینکه فقط تعریفش رو حفظ کنی.

همین منطق رو برای path غایب و duplicate key هم آزمایش می‌کنیم. هدف این نیست که از این رفتارها خوشمان بیاید؛ هدف این هست که موقع migration از روی حدس تصمیم نگیریم.

A common source of surprising queries is the difference between SQL NULL and the JSON token null. The former means there is no SQL value; the latter is a token inside a document. Run them side by side so the distinction becomes observable instead of theoretical.

Use the same approach for missing paths and duplicate keys. The point is not to prefer one behavior; it is to stop making migration decisions from assumptions.

مهاجرت رو با row count تمام نکنA migration is more than a row count

اینکه قبل و بعد هر دو طرف COUNT(*) = 10000 دارن فقط می‌گه تعداد ردیف‌ها یکی هست. نمی‌گه JSONها یک معنی می‌دن، pathها همان مقدار رو برمی‌گردانند یا replication با format انتخابی امن هست.

برای تحویل واقعی، چند سند مرزی بساز: رشته، عدد، boolean، null، path غایب و duplicate key. بعد DDL و queryهای کلیدی رو روی نسخهٔ هدف اجرا کن و نتیجه رو کنار هم نگه دار. این می‌شه مدرک مهاجرت، نه جملهٔ «با MySQL سازگاره».

Matching row counts only prove that the number of rows matches. They do not prove equivalent JSON semantics, path results, or safe replication behavior.

For a real migration check, keep a small boundary fixture: strings, numbers, booleans, null, missing paths, and duplicate keys. Run the same DDL and key queries on the target release and preserve the results. That is migration evidence, not the slogan “compatible with MySQL.”
