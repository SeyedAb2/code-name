یک session time_zone متفاوت داره و فقط همان درخواست timestamp عجیب می‌سازه؛ تنظیم در کدام scope هست؟

One session has a different time_zone, and only its requests show odd timestamps. Which scope owns the setting?

دو connection به یک MariaDB وصل‌اند ولی رفتارشان فرق داره. قبل از اینکه بگوییم «server config عوض شده»، باید scope رو بفهمیم: بعضی variableها session دارن، بعضی فقط global هستن، و تغییر runtime لزوماً بعد restart باقی نمی‌مونه.

Two connections can talk to the same MariaDB server and still behave differently. Before blaming “server configuration,” understand scope: some variables have session values, some are global-only, and runtime changes do not necessarily survive a restart.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: scope و lifecycle تنظیمات Server/Session. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is server/session setting scope and lifecycle. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

GLOBAL پیش‌فرض connectionهای تازه هست، نه جادو روی همهGLOBAL usually affects new sessions, not every open one

برای متغیری مثل time_zone مقدار global و session رو کنار هم می‌خونیم. Session جاری می‌تونه مقدار خودش رو داشته باشد و تغییر global معمولاً connectionهای باز رو بازنویسی نمی‌کنه.

این دقیقاً جایی هست که connection pool می‌تونه گیج‌کننده شود: connection قدیمی با state قدیمی دوباره از pool بیرون میاد.

For a variable such as time_zone, read global and session values side by side. The current session can have its own value, and changing the global default generally does not rewrite existing connections.

This becomes especially confusing with connection pools, where an old connection can reappear carrying earlier session state.

SELECT @@global.time_zone,@@session.time_zone;

همهٔ variableها SESSION ندارنNot every variable has session scope

مثلاً max_connections یک تنظیم global server هست؛ نمی‌تونی آن رو مثل sql_mode یا time_zone برای یک session معنی‌دار بخوانی/ست کنی. scope بخشی از خود variable هست.

information_schema.SYSTEM_VARIABLES رو برای READ_ONLY و origin بررسی می‌کنیم تا از روی documentation ذهنی حدس نزنیم.

A variable such as max_connections is server-global; it is not a meaningful per-session setting like sql_mode or time_zone. Scope is part of the variable's contract.

Inspect information_schema.SYSTEM_VARIABLES for attributes such as mutability and origin rather than guessing from memory.

Runtime change با persistent config فرق دارهRuntime state is not persistent configuration

SET GLOBAL می‌تونه همان لحظه behavior رو عوض کند، ولی restart ممکن هست مقدار رو از option file دوباره بیاورد. پس برای تغییر عملیاتی باید هم current state و هم startup source رو بفهمی.

در lab restart دورریختنی می‌کنیم و قبل/بعد مقدار رو می‌خونیم. همین آزمایش جلوی خیلی از «چرا برگشت؟»ها رو می‌گیره.

SET GLOBAL can change behavior immediately, while a restart may reload a different value from option files. Operational changes therefore need both current-state and startup-source understanding.

Restart a disposable server in the lab and compare before/after values. That simple experiment prevents many later “why did it revert?” incidents.

SELECT VARIABLE_NAME,GLOBAL_VALUE_ORIGIN

Session state رو در app آشکار کنMake application session state observable

برای queryهای حساس، CONNECTION_ID() و session settingهای مهم رو موقع debugging ثبت کن. اگه فقط server global رو ببینی، ممکن هست مشکل همان connection رو از دست بدهی.

وقتی pool داری، reset/recycle connection بخشی از تست تغییر config هست؛ نه جزئیات بی‌اهمیت driver.

For sensitive behavior, record CONNECTION_ID() and relevant session settings while debugging. Looking only at server-global values can miss the state of the exact connection with the problem.

With pooling, resetting or recycling connections is part of configuration testing, not an irrelevant driver detail.
