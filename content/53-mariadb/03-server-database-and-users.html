Server، database و کاربرها

Servers, databases, and users

برنامه وصل می‌شه، اما هنوز نمی‌دونیم دقیقاً به کدام database وصل هست و با چه دسترسی‌ای. گاهی هم تیم برای حل یک SELECT ناموفق، به حساب برنامه دسترسی کامل می‌ده. بیا اول نقشهٔ مقصد رو روشن کنیم، بعد با یک حساب محدود، مجوز واقعی رو از خود MariaDB بپرسیم.

The application connects, but we do not yet know which database it reached or what permissions it has. Teams sometimes grant an application full access just to fix a failed SELECT. Let’s identify the target, then ask MariaDB what a restricted account can actually do.

یک اتصال، چند لایهٔ مستقل / One connection, several distinct scopes

MariaDB Server می‌تونه چند database داشته باشد. database هم tableها و objectهای خودش رو نگه می‌داره. حساب کاربری موجودیت دیگری است: نام account همراه host تعریف می‌شه و مجوزش می‌تونه در scopeهای متفاوتی اعمال شود. پس «به MariaDB وصل شدم» هنوز نمی‌گه database درست انتخاب شده یا دسترسی حداقلی هست.

A MariaDB server can contain several databases. Each database owns its tables and other objects. An account is a separate entity: its name is paired with a host, and privileges can apply at different scopes. “I connected to MariaDB” does not prove the right database is selected or access is least-privileged.

Server چند database رو میزبانی می‌کنه. این حساب فقط SELECT روی database آزمایش داره؛ نام حساب به‌تنهایی مجوزش رو نشان نمی‌ده.A server hosts multiple databases. This account has SELECT only on the lab database; its name alone does not reveal its privileges.

نکتهٔ مهم: account در MariaDB معمولاً به شکل 'user'@'host' شناخته می‌شه. بخش host می‌گه اتصال از کجا match می‌شه؛ بنابراین 'shop_reader'@'localhost' و 'shop_reader'@'%' دو account definition جدا هستن. wildcard رو اینجا فقط برای lab container به‌کار می‌بریم و فصل امنیت دربارهٔ محدودکردنش برمی‌گردد.

An account is commonly identified as 'user'@'host'. The host part affects which connection matches, so 'shop_reader'@'localhost' and 'shop_reader'@'%' are separate account definitions. We use a wildcard only for this isolated container lab; the security chapter revisits tighter host restrictions.

database را با defaultهای روشن بساز / Create a database with explicit defaults

به‌جای اینکه بعداً حدس بزنیم متن فارسی با چه character set و collation ذخیره می‌شه، همان موقع ساخت database اون‌ها رو مشخص می‌کنیم. utf8mb4 متن Unicode رو پوشش می‌ده؛ collation روی مقایسه و مرتب‌سازی اثر داره. بعد از ساخت، از خود MariaDB تعریف ثبت‌شده رو می‌خونیم.

Rather than guessing later how Persian text is encoded and compared, specify the database character set and collation when creating it. utf8mb4 supports Unicode text; collation affects comparison and ordering. After creation, inspect the definition MariaDB stored.

ساخت schema آزمایش / Create the lab schema
CREATE DATABASE shop_access_lab CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
SHOW CREATE DATABASE shop_access_lab;
SELECT DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME
FROM information_schema.SCHEMATA
WHERE SCHEMA_NAME = 'shop_access_lab';

در خروجی به نام database، character set و collation نگاه کن. IF NOT EXISTS جلوی خطای وجود قبلی رو می‌گیره، اما وجود قبلی رو به معنی یکسان‌بودن تنظیم‌ها نمی‌کنه؛ اگه از آن استفاده کردی، SHOW CREATE DATABASE رو هم بخوان. ساخت database تنظیم charset جدول‌های موجود رو عقب‌گردی عوض نمی‌کنه.

Inspect the database name, character set, and collation. IF NOT EXISTS avoids an error when the database already exists, but does not prove its settings match; if you use it, still run SHOW CREATE DATABASE. Creating a database does not retroactively change existing table encodings.

حساب محدود را واقعاً وارد کن / Actually log in as a restricted account

حساب admin می‌تونه خیلی کارها انجام دهد، برای همین موفقیت query او چیزی دربارهٔ دسترسی برنامه ثابت نمی‌کنه. اول حسابی بسازیم که فقط database همین lab رو بخواند. رمز نمونه هست و روی محیط دورریختنی اجرا می‌شه؛ برای secret واقعی این فرمان رو در shell history یا فایل Git نگه ندار.

An admin can do many things, so a successful admin query says little about application access. Create an account that can read only this lab database. The password is a placeholder for a disposable environment; never keep real credentials in shell history or Git.

ایجاد حساب و مجوز حداقلی / Create a user with a narrow grant
CREATE USER 'shop_reader'@'%' IDENTIFIED BY 'reader-lab-only';
GRANT SELECT ON shop_access_lab.* TO 'shop_reader'@'%';
SHOW GRANTS FOR 'shop_reader'@'%';

مجوز SELECT فقط روی shop_access_lab.* هست؛ نه روی همهٔ server. در خروجی SHOW GRANTS دنبال همان scope بگرد. بعد باید با خود reader وارد شویم و مجوز رو آزمایش کنیم؛ دیدن فرمان موفق در نشست admin به‌تنهایی کافی نیست.

The SELECT privilege applies only to shop_access_lab.*, not the entire server. Check that exact scope in SHOW GRANTS. Then log in as the reader and test the privilege; seeing a successful GRANT command from an admin session is not enough.

نکتهٔ host:در این Docker lab بخش % اتصال از آدرس شبکهٔ container رو match می‌کنه. این انتخاب عمداً ساده شده؛ روی سرور واقعی host رو تا جای ممکن محدود کن و userهای هم‌نام با hostهای مختلف رو جدا بررسی کن.Host note:In this Docker lab, % matches the container network source. This is intentionally simplified; on a real server, restrict hosts where possible and inspect same-named accounts with different hosts separately.

اجازهٔ خواندن را ثابت کن؛ بعد یک کار را عمداً رد کن / Prove reads, then deliberately deny a write

یک جدول کوچک بساز و یک محصول آزمایشی وارد کن. سپس connection جداگانه‌ای با حساب reader باز کن. آنجا SELECT باید جواب بدهد؛ INSERT باید رد شود. این دو نتیجه کنار هم بهتر از یک فهرست grant نشان می‌دن حساب واقعاً چه می‌تونه بکند.

Create a small table and insert one test product. Then open a separate connection as the reader. SELECT should succeed; INSERT should be denied. These two observations show effective access better than a grant list alone.

فقط از نشست admin آزمایشگاه / In the disposable admin session
USE shop_access_lab;
CREATE TABLE products (product_id INT PRIMARY KEY, title VARCHAR(100) NOT NULL);
INSERT INTO products VALUES (1, 'دفترچه');
SELECT * FROM products;
از میزبان، حساب reader / From the host as the reader
mariadb --protocol=TCP --host=127.0.0.1 --port=3307 --user=shop_reader --password shop_access_lab

در prompt reader اجرا کن: SELECT product_id,title FROM products; و بعد INSERT INTO products VALUES (2,'نباید ثبت شود');. انتظار داریم اولی یک ردیف و دومی خطای privilege بدهد. اگه هر دو موفق شدند، grant وسیع‌تری یا account دیگری match شده؛ SELECT USER(), CURRENT_USER(); SHOW GRANTS; رو همان‌جا اجرا کن.

At the reader prompt, run SELECT product_id,title FROM products;, then try INSERT INTO products VALUES (2,'must not persist');. Expect one row from the first and a privilege error from the second. If both succeed, a broader grant or different matched account is involved; run SELECT USER(), CURRENT_USER(); SHOW GRANTS; in that same session.

وقتی نام database درست است ولی query رد می‌شود / When the database is right but a query is denied

مقصد نشست، account وصل‌شده و account انتخاب‌شده رو یک‌جا ثبت کن. DATABASE() context رو نشان می‌ده، USER() هویت ارائه‌شده را، و CURRENT_USER() حسابی رو که privilege check با آن انجام شده. این‌ها رو با SHOW GRANTS کنار هم بگذار؛ هنوز سراغ restart یا grant سراسری نرو.

Record the session target, presented identity, and matched account together. DATABASE() shows context; USER() shows presented identity; CURRENT_USER() shows the account used for privilege checks. Compare these with SHOW GRANTS before restarting or adding a global grant.

یک snapshot تشخیصی / One diagnostic snapshot
SELECT DATABASE(), USER(), CURRENT_USER(), @@hostname, @@port;
SHOW GRANTS;

یک نکتهٔ دیگر: CREATE DATABASE IF NOT EXISTS ممکن هست warning بدهد و کار رو ادامه دهد؛ این به معنی اعمال دوبارهٔ charset دلخواه تو نیست. warningها رو بخوان و metadata رو بررسی کن. رفتار قابل‌اعتماد از شواهد میاد، نه از فرض اینکه اسم‌ها همه‌جا یکسان‌اند.

One more detail: CREATE DATABASE IF NOT EXISTS may emit a warning and continue; that does not mean your preferred character set was reapplied. Read warnings and inspect metadata. Reliable conclusions come from evidence, not assumptions about matching names.

پاک‌سازی محدود و قابل‌ردیابی / Scoped, traceable cleanup

این فصل database اختصاصی shop_access_lab و یک account آزمایش ساخته. بعد از ثبت خروجی‌ها، دسترسی reader رو حذف و database رو فقط در محیط دورریختنی پاک کن. اگه database یا account رو برای فصل‌های بعدی می‌خوای نگه داری، این cleanup رو اجرا نکن؛ حذف database یعنی حذف داده‌های داخلش.

This chapter created a dedicated shop_access_lab database and a lab account. After saving evidence, remove the reader and drop the database only in the disposable environment. If later labs reuse it, do not run cleanup; dropping a database deletes its contents.

فقط پس از بررسی محیط آزمایش / Only after verifying the lab target
DROP USER 'shop_reader'@'%';
DROP DATABASE shop_access_lab;
پیش از DROP بپرس:این داده فقط lab هست؟ اگه جواب قطعی نیست، حذف نکن. فرمان رو همواره روی Server مقصد با SELECT @@hostname; تطبیق بده.Before DROP, ask:Is this data definitely disposable? If not, do not delete it. Confirm the target server with SELECT @@hostname;.

۱۸ تمرین اجرایی / 18 hands-on exercises

1) ساخت database با encoding روشن / Create a database with explicit encoding

یک database آزمایش بساز و charset/collation رو مشخص کن.

Create a lab database with an explicit character set and collation.

Query و تفسیر / Query and interpretation
CREATE DATABASE shop_access_lab CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci; SHOW CREATE DATABASE shop_access_lab;

خروجی SHOW CREATE تعریف مؤثر رو نشان می‌ده؛ از default نامعلوم سرور حدس نزدیم.

SHOW CREATE reports the effective definition; we did not guess server defaults.

2) شناخت مقصد نشست / Identify the session target

database جاری و Server مقصد رو در یک query ببین.

Read the current database and target server in one query.

Query و تفسیر / Query and interpretation
SELECT DATABASE(), @@hostname, @@port, VERSION();

اگه DATABASE برابر NULL هست، هنوز schema انتخاب نشده؛ Server ممکن هست سالم باشد.

If DATABASE is NULL, no schema is selected; the server may still be healthy.

3) ایجاد جدول و ردیف نمونه / Create a table and sample row

جدول products آزمایش رو با کلید اصلی بساز.

Create the lab products table with a primary key.

Query و تفسیر / Query and interpretation
USE shop_access_lab; CREATE TABLE products (product_id INT PRIMARY KEY, title VARCHAR(100) NOT NULL); INSERT INTO products VALUES (1,'کتاب'); SELECT * FROM products;

این فقط fixture همین database رو تغییر می‌ده؛ روی محیط شخصی آزمایش کن.

This changes only the lab database; keep it in a disposable environment.

4) حساب محدود / A restricted account

حساب reader بساز که فقط database آزمایش رو بخواند.

Create a reader limited to the lab database.

Query و تفسیر / Query and interpretation
CREATE USER 'shop_reader'@'%' IDENTIFIED BY 'reader-lab-only'; GRANT SELECT ON shop_access_lab.* TO 'shop_reader'@'%';

scope مجوز database هست؛ wildcard host برای آزمایش container هست و الگوی production نیست.

The privilege scope is one database; wildcard host is for the container lab, not production.

5) دیدن مجوز مؤثر / Inspect effective grants

مجوز حساب رو بخوان و محدودبودنش رو ثابت کن.

Read the account grants and prove they are limited.

Query و تفسیر / Query and interpretation
SHOW GRANTS FOR 'shop_reader'@'%';

دنبال SELECT روی shop_access_lab.* بگرد؛ ALL PRIVILEGES یا *.* لازم نیست.

Look for SELECT on shop_access_lab.*; ALL PRIVILEGES or *.* is unnecessary.

6) مجوزهای حساب جاری / Inspect current account grants

از نشست reader مجوز جاری رو بخوان.

Read current grants from the reader session.

Query و تفسیر / Query and interpretation
SHOW GRANTS;

این دستور از همان account می‌خونه؛ خروجی admin جای آزمون reader رو نمی‌گیره.

This reads the current account; an admin's output is not a substitute for testing the reader.

7) آزمون SELECT مجاز / Test an allowed SELECT

با reader نام و محصول رو بخوان.

Use the reader to query the products.

Query و تفسیر / Query and interpretation
SELECT product_id, title FROM shop_access_lab.products;

ردیف‌ها دسترسی خواندن رو ثابت می‌کنن، نه توان نوشتن را.

Returned rows prove read access, not write access.

8) آزمون INSERT غیرمجاز / Test a denied INSERT

با reader تلاش کن ردیفی اضافه کنی؛ نتیجه رو تفسیر کن.

Try inserting a row as reader and interpret the result.

Query و تفسیر / Query and interpretation
INSERT INTO shop_access_lab.products VALUES (2,'نامجاز');

باید با خطای privilege رد شود؛ بعد با admin ثابت کن ردیف ساخته نشده.

Expect a privilege error; then verify as admin that no row was created.

9) مقایسه USER و CURRENT_USER / Compare USER and CURRENT_USER

هویت وصل‌شده و account انتخاب‌شده رو query کن.

Query connection identity and matched account.

Query و تفسیر / Query and interpretation
SELECT USER(), CURRENT_USER();

این دو می‌تونن فرق کنند؛ CURRENT_USER برای تشخیص grantهای اعمال‌شده مهم هست.

They can differ; CURRENT_USER helps identify the grants actually applied.

10) انتخاب database برای نشست / Select a database for the session

database رو انتخاب و context رو دوباره بخوان.

Select a database and re-check session context.

Query و تفسیر / Query and interpretation
USE shop_access_lab; SELECT DATABASE();

USE فقط context نشست رو عوض می‌کنه و مجوز تازه نمی‌سازه.

USE changes session context; it does not create privileges.

11) database وجود دارد یا نه؟ / Check whether a database exists

وجود schema رو از metadata بخوان.

Check schema existence through metadata.

Query و تفسیر / Query and interpretation
SELECT SCHEMA_NAME FROM information_schema.SCHEMATA WHERE SCHEMA_NAME='shop_access_lab';

یک ردیف یعنی schema هست؛ نبود ردیف می‌تونه نام اشتباه یا مجوز دید محدود باشد.

A row means it exists; no row may mean a wrong name or limited metadata visibility.

12) charset/collation واقعی / Inspect actual charset and collation

defaultهای خود database رو بخوان.

Read the database's own defaults.

Query و تفسیر / Query and interpretation
SELECT DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME FROM information_schema.SCHEMATA WHERE SCHEMA_NAME='shop_access_lab';

این database رو می‌سنجد، نه فقط متغیرهای Server.

This inspects the database, not merely server variables.

13) یکسان نبودن defaults / Prove defaults are not all the same

charset Server و database رو کنار هم گزارش کن.

Report server and database character sets side by side.

Query و تفسیر / Query and interpretation
SELECT @@character_set_server, @@collation_server; SELECT DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME FROM information_schema.SCHEMATA WHERE SCHEMA_NAME='shop_access_lab';

دو scope مستقل‌اند؛ انتخاب explicit برای schema migration رو قابل‌بازتولیدتر می‌کنه.

These are distinct scopes; explicit schema defaults make migrations more reproducible.

14) اصلاح title اجباری / Repair a required title

یک query بنویس که ستون title رو NOT NULL بودنش از metadata ثابت کند.

Query metadata to verify title is NOT NULL.

Query و تفسیر / Query and interpretation
SELECT COLUMN_NAME, IS_NULLABLE, COLUMN_TYPE FROM information_schema.COLUMNS WHERE TABLE_SCHEMA='shop_access_lab' AND TABLE_NAME='products';

IS_NULLABLE=NO شاهد تعریف ستون هست.

IS_NULLABLE=NO is evidence of the column definition.

15) DROP را بدون اجرا بررسی کن / Inspect DROP risk without executing it

فرمان حذف database رو در گزارش بنویس، اما اجرا نکن؛ روش ایمن‌تر بررسی وجود چیست؟

Write the DROP command in your report but do not run it; how can you safely check existence?

Query و تفسیر / Query and interpretation
SHOW DATABASES LIKE 'shop_access_lab';

وجود رو با query بررسی می‌کنیم؛ DROP غیرقابل‌بازگشت این تمرین نیست.

Use a query to inspect existence; DROP is not part of this exercise.

16) محدودهٔ grant را تنگ کن / Keep the grant scope narrow

به‌جای global grant، فقط SELECT روی database آزمایش بده.

Grant SELECT only on the lab database, not globally.

Query و تفسیر / Query and interpretation
GRANT SELECT ON shop_access_lab.* TO 'shop_reader'@'%'; SHOW GRANTS FOR 'shop_reader'@'%';

دستور دوم نتیجه رو تأیید می‌کنه؛ grant سراسری به *.* بیش از نیاز هست.

The second statement verifies it; a global grant on *.* exceeds the requirement.

17) گزارش عیب‌یابی دسترسی / Write an access-diagnosis query

یک query بنویس که database جاری، user ظاهرشده و account مؤثر رو گزارش کند.

Write a query reporting current database, presented user, and effective account.

Query و تفسیر / Query and interpretation
SELECT DATABASE() AS current_db, USER() AS presented_user, CURRENT_USER() AS effective_account;

اگه database درست هست اما SELECT رد می‌شه، grant همان account رو با SHOW GRANTS بسنج.

If the database is right but SELECT is denied, inspect that account's grants.

18) آزمون نهایی reader / Final reader acceptance test

یک query بساز که نسخه و ردیف‌های products رو با reader نشان دهد.

Write a final query that shows server version and product rows as reader.

Query و تفسیر / Query and interpretation
SELECT VERSION(); SELECT product_id, title FROM shop_access_lab.products ORDER BY product_id;

موفقیت هر دو، مسیر اتصال و خواندن رو ثابت می‌کنه؛ نوشتن همچنان عمداً بسته هست.

Both succeeding proves connection and read access; writes remain intentionally denied.
