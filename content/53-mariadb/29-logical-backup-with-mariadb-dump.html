Possessing a .sql file is not the same as having recoverability. A mariadb-dump becomes trustworthy only when you know what it contains, how consistent the snapshot is, and—most importantly—can restore it elsewhere.

This chapter does not begin with syntax. The problem is logical backup and provable restore. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

Logical backup یعنی SQL قابل‌حملLogical backup is portable SQL

Dump schema و data رو به statementهایی تبدیل می‌کنه که دوباره قابل اجرا هستن. همین portability مزیت بزرگی هست، ولی روی database حجیم می‌تونه کند و پرحجم باشد.

نسخهٔ client رو ثبت کن و فایل رو inspect کن؛ backup artifact جعبهٔ سیاه نیست.

A logical dump turns schema and data into SQL statements that can be executed again. That portability is valuable, but it can be slow and large for substantial databases.

Record the client version and inspect the file; a backup artifact should not be treated as an opaque box.

Consistency رو با engine و DDL بسنجConsistency depends on workload and schema changes

برای InnoDB، --single-transaction می‌تونه snapshot خوبی بدهد بدون اینکه tableها رو برای کل dump lock کند؛ ولی concurrent DDL می‌تونه assumptions رو خراب کند.

پس backup procedure فقط command نیست. Window تغییر schema و workload هم بخشی از قرارداد backup هست.

For InnoDB, --single-transaction can provide a useful consistent snapshot without holding broad table locks for the whole dump, but concurrent DDL can still invalidate assumptions.

A backup procedure is therefore more than a command; schema-change policy and workload conditions are part of the contract.

Restore drill بخشی از backup استA restore drill is part of the backup

یک database جدا مثل restore_lab بساز، dump رو آنجا import کن و چند مقدار شناخته‌شده رو verify کن. اگه restore رو هیچ‌وقت تمرین نکردی، فقط امیدوار هستی.

Checksum artifact خوب هست، permission فایل مهم هست، ولی آخرین مدرک همان data قابل‌خواندن بعد از restore هست.

Restore into a separate database such as restore_lab and verify known values. If the restore path has never been exercised, recoverability is still an assumption.

Checksums and file permissions matter, but the strongest evidence is readable, validated data after an isolated restore.

SHOW TRIGGERS FROM restore_lab;

این query قرار نیست چیزی رو تعمیر کنه؛ فقط state رو قابل‌دیدن می‌کنه. مقدارهای مرتبط با artifact، checksum، object inventory و data بعد restore رو ثبت کن و قبل از هر تغییر بعدی snapshot رو نگه دار.

This query is observational. Capture the relevant state before changing anything so later conclusions about logical backup and provable restore can be tied to evidence.
