قیمت قرارداد از اول ماه معتبر بوده اما شرکت اصلاحش رو روز دهم وارد سیستم کرده؛ «چه زمانی معتبر بود؟» با «چه زمانی فهمیدیم؟» یکی نیست.

A contract price was valid from the first of the month, but entered into the system on the tenth. “When was it valid?” differs from “When did we know?”

دو سؤال زمانی داریم که ظاهرشان شبیه هست ولی جواب‌شان یکی نیست: «این قیمت از چه تاریخی برای مشتری معتبر بود؟» و «database چه تاریخی این اصلاح رو ثبت کرد؟». Application-time و system-time دقیقاً برای جداکردن همین دو محورند.

Two temporal questions may sound similar while requiring different answers: “When was this price valid for the customer?” and “When did the database record this correction?” Application time and system time model those two axes separately.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: application time، system time و مدل bitemporal. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is application time, system time, and the bitemporal model. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

Application time رو خود کسب‌وکار تعریف می‌کنهApplication time belongs to the business

در MariaDB یک PERIOD FOR روی دو ستون زمانی تعریف می‌کنی. Server حد پایین و بالا رو به‌عنوان یک بازه می‌شناسد و نامعتبر بودن ترتیب بازه رو هم رد می‌کنه.

اما این period به‌خودی‌خود یک SELECT ... AS OF عمومی مثل system versioning نمی‌سازه. برای پرسیدن «در تاریخ D کدام ردیف معتبر بود؟» شرط بازهٔ کسب‌وکار رو صریح می‌نویسیم.

In MariaDB, PERIOD FOR defines an application-time interval over two temporal columns. The server understands the lower and upper bounds and rejects invalid ranges.

But this period does not create a general SELECT ... AS OF syntax like system versioning. To ask which row was business-valid on date D, express the interval predicate explicitly.

CREATE TABLE price_history(sku INT,valid_from DATE,valid_to DATE,PERIOD FOR valid_period(valid_from,valid_to));

این object عمداً کوچک و آزمایشیه تا behavior رو بدون سر و صدای production ببینیم. بعد از ساخت، با metadata یا یک query مستقل ثابت کن چیزی که می‌خواستیم واقعاً ساخته شده.

The object is intentionally small and disposable. After creating it, use independent metadata or a query to prove that the intended behavior really exists.

FOR PORTION OF برای تغییر بخشی از بازه استFOR PORTION OF changes part of an interval

جذاب‌ترین بخش application-time این هست که UPDATE ... FOR PORTION OF یا DELETE ... FOR PORTION OF می‌تونه فقط بخش مشخصی از بازه رو تغییر دهد و MariaDB لازم باشد ردیف رو split کند.

روی fixture کوچک این کار رو می‌کنیم و قبل/بعد rowها رو می‌شماریم. اگه row count زیاد شد، bug نیست؛ نتیجهٔ شکستن interval برای حفظ بخش‌های بیرون از محدوده هست.

A powerful application-time feature is UPDATE ... FOR PORTION OF or DELETE ... FOR PORTION OF, which can modify only part of an interval and cause MariaDB to split rows.

Run it on a small fixture and count rows before and after. An increased row count can be the correct result of preserving the portions outside the changed interval.

INSERT INTO price_history(sku, valid_from, valid_to)
VALUES (1001, DATE '2026-01-01', DATE '2026-02-01');

UPDATE price_history
FOR PORTION OF valid_period
FROM '2026-01-10' TO '2026-01-20'
SET sku = 1002
WHERE sku = 1001;

SELECT sku, valid_from, valid_to
FROM price_history
ORDER BY valid_from;

System time محور «چه زمانی فهمیدیم» استSystem time records when the database knew it

وقتی همان table system-versioned هم باشد، یک اصلاح عقب‌نگر دو زمان داره: business validity شاید از اول ماه باشد، ولی database روز دهم آن رو ثبت کرده.

برای گزارش bitemporal اول system snapshot رو با FOR SYSTEM_TIME AS OF محدود می‌کنیم، بعد داخل همان دید، شرط valid-from/valid-to رو برای زمان کسب‌وکار اعمال می‌کنیم.

When the same table is also system-versioned, a retroactive correction has two times: it may be business-valid from the first of the month while the database recorded it on the tenth.

For a bitemporal report, first constrain the system snapshot with FOR SYSTEM_TIME AS OF, then apply the business validity predicate over the application-time columns.

ALTER TABLE price_history ADD SYSTEM VERSIONING;

SET @before_change = CURRENT_TIMESTAMP(6);
DO SLEEP(0.05);

UPDATE price_history
SET sku = 1003
WHERE sku = 1002;

SELECT ROW_START, ROW_END, sku, valid_from, valid_to
FROM price_history FOR SYSTEM_TIME ALL
ORDER BY ROW_START;

SELECT sku, valid_from, valid_to
FROM price_history FOR SYSTEM_TIME AS OF TIMESTAMP @before_change
WHERE valid_from <= DATE '2026-01-15'
  AND valid_to   > DATE '2026-01-15';

Overlap رو rule صریح کنMake overlap rules explicit

اگه برای یک SKU دو قیمت هم‌زمان معتبر باشند، report چه باید بکند؟ این دیگر سؤال syntax نیست؛ rule مدل هست. MariaDB در نسخه‌های جدید امکان constraintهای period مثل WITHOUT OVERLAPS داره، ولی availability و syntax رو روی نسخهٔ هدف چک کن.

حتی با constraint، convention بازه رو روشن نگه دار؛ مثلاً [from,to) تا مرز دو دوره دقیقاً تعریف شود.

If two prices for one SKU are valid at the same business time, what should a report do? That is a model rule, not merely syntax. Recent MariaDB releases support period constraints such as WITHOUT OVERLAPS; verify syntax and availability on the target release.

Even with constraints, keep interval conventions explicit—for example [from,to)—so adjoining periods have unambiguous boundaries.

ALTER TABLE price_history
  ADD UNIQUE (sku, valid_period WITHOUT OVERLAPS);

این تغییر رو فقط روی fixture انجام بده و before/after رو نگه دار. موفق‌شدن statement به‌تنهایی کافی نیست؛ نتیجهٔ واقعی رو با بازهٔ valid-time، row splitting و system snapshot verify کن.

Run the change only on the fixture and preserve before/after evidence. A successful statement alone does not prove the desired end state.
