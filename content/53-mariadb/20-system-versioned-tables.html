کاربر می‌گه آدرس هفتهٔ قبل فرق داشته؛ audit table دستی فقط مقدار فعلی رو نشان می‌ده.

A user says their address was different last week. The manual audit table shows only the current value.

گاهی سؤال کاربر این نیست که «الان مقدار چیست؟»؛ می‌پرسد «سه‌شنبهٔ قبل چه مقداری داشتیم؟». System-versioned table همین تاریخچهٔ ثبت‌شده توسط server رو نگه می‌داره. ولی تاریخچه داشتن با backup داشتن یکی نیست.

Sometimes the question is not “what is the value now?” but “what value did the database have last Tuesday?” System-versioned tables preserve that server-recorded history. Historical rows, however, are not a replacement for backups.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: تاریخچهٔ system-time و مرز آن با backup. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is system-time history and its boundary with backup. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

Current row فقط نصف داستان استThe current row is only half the story

یک table کوچک با WITH SYSTEM VERSIONING می‌سازیم، ردیف رو چند بار تغییر می‌دهیم و اول query معمولی رو اجرا می‌کنیم. همان‌طور که انتظار داری فقط نسخهٔ فعلی رو می‌بینی.

بعد FOR SYSTEM_TIME ALL رو اضافه می‌کنیم و تاریخچه ظاهر می‌شه. این لحظه مدل ذهنی فصل است: current state و historical versions دو view متفاوت از یک entity هستن.

Create a small WITH SYSTEM VERSIONING table, change a row several times, and query it normally. As expected, only the current version appears.

Then add FOR SYSTEM_TIME ALL and the historical versions become visible. That is the chapter's core model: current state and stored history are different views of the same entity.

CREATE TABLE v(id INT PRIMARY KEY,x INT) WITH SYSTEM VERSIONING;

این object عمداً کوچک و آزمایشیه تا behavior رو بدون سر و صدای production ببینیم. بعد از ساخت، با metadata یا یک query مستقل ثابت کن چیزی که می‌خواستیم واقعاً ساخته شده.

The object is intentionally small and disposable. After creating it, use independent metadata or a query to prove that the intended behavior really exists.

AS OF یعنی «آن لحظه database چه می‌دانست؟»AS OF asks what the database knew at that time

با timestamp می‌تونیم state رو در یک لحظهٔ ثبت‌شده ببینیم. حواست باشد این system time هست؛ یعنی زمان ثبت تغییر در database، نه لزوماً زمانی که آن واقعیت در دنیای کسب‌وکار معتبر بوده.

فصل بعد همین فرق رو با application-time باز می‌کنیم. اینجا فقط system clock رو تمیز نگه می‌داریم.

An AS OF timestamp lets you inspect state at a recorded system time. This is system time: when the database stored a version, not necessarily when that fact was valid in the business world.

The next chapter introduces application time. Here, keep the system-time model deliberately clear.

SELECT * FROM v FOR SYSTEM_TIME AS OF TIMESTAMP'2026-01-01 12:00:00' WHERE id=1;

System versioning چند نسخهٔ ثبت‌شده رو روی محور زمان server نگه می‌داره.

System versioning preserves recorded row versions along server time.

History هم storage و permission می‌خواهدHistory has storage and permission costs

هر update می‌تونه version تازه نگه داره. پس retention، index و دسترسی به تاریخچه باید طراحی شود. داده‌ای که از current table حذف شده ممکن هست هنوز در history قابل‌خواندن باشد.

برای اطلاعات حساس، privilege تاریخچه رو مثل data فعلی جدی بگیر. «از صفحه حذف شد» به معنی «دیگر در database نیست» نیست.

Each update can retain another row version, so retention, indexing, and historical access need design. Data removed from the current view may still exist in history.

Treat access to historical sensitive data as seriously as access to current data. “It disappeared from the UI” does not mean it disappeared from the database.

DELETE FROM v WHERE id=1; SELECT * FROM v FOR SYSTEM_TIME ALL WHERE id=1;

این تغییر فقط روی دادهٔ دورریختنیه. قبلش target رو با SELECT مشخص کن، بعد تغییر رو اجرا کن و دوباره state رو بخون؛ row count یا پیام Query OK جای verification رو نمی‌گیره.

Keep the change inside disposable data. Inspect the target first, make the change, then query the resulting state; an affected-row count is not sufficient verification.

Versioning رو backup جا نزنVersioning is not backup

اگه database file از بین برود یا corruption گسترده داشته باشی، history داخل همان database هم در خطر هست. Backup یک copy مستقل برای recovery می‌ده؛ system versioning تاریخچهٔ منطقی داخل همان system هست.

برای همین در تمرین عمداً restore جدا رو به‌عنوان شاهد backup نگه می‌داریم. دو feature دو failure model متفاوت رو پوشش می‌دن.

If the database files are lost or broadly corrupted, history stored in the same database is also at risk. Backups provide an independent recovery copy; system versioning provides logical history inside the database.

That is why the lab treats an isolated restore as backup evidence. The two features protect against different failure modes.

SHOW VARIABLES LIKE 'system_versioning_alter_history';

این query قرار نیست چیزی رو تعمیر کنه؛ فقط state رو قابل‌دیدن می‌کنه. مقدارهای مرتبط با current row، historical rows و timestampهای system رو ثبت کن و قبل از هر تغییر بعدی snapshot رو نگه دار.

This query is observational. Capture the relevant state before changing anything so later conclusions about system-time history and its boundary with backup can be tied to evidence.
