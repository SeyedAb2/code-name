در قطعی شبکه دو node از سه node همدیگر رو نمی‌بینند؛ آیا هر دو باید write بپذیرند؟

During a network split, two of three nodes cannot communicate. Should both accept writes?

سه node داریم و شبکه نصف شده. سؤال مهم این نیست که mariadbd روی کدام node هنوز process داره؛ سؤال این هست که کدام component quorum داره و حق write داره. Galera دقیقاً اینجا معنی پیدا می‌کنه.

With three nodes and a network partition, the important question is not which node still has a running mariadbd process. The important question is which component retains quorum and is allowed to accept writes. That is where the Galera model matters.

Process up با cluster healthy فرق دارهA running process is not a healthy cluster

روی هر node wsrep_cluster_status, size, local state و readiness رو می‌خونیم. یک node می‌تونه process سالم داشته باشه ولی component غیرPrimary باشه و write رو نپذیره.

این distinction برای health check خیلی مهمه؛ tcp/3306 open معیار کافی برای write readiness نیست.

Inspect wsrep_cluster_status, cluster size, local state, and readiness on every node. A server process can be alive while the node belongs to a non-Primary component and cannot safely accept writes.

This distinction matters for health checks: an open TCP/3306 port is not enough evidence of write readiness.

Quorum برای جلوگیری از دو حقیقت استQuorum prevents competing writable histories

در split شبکه، اگه هر دو طرف مستقل write بپذیرن، دو history diverge می‌شن. Galera از Primary Component و quorum استفاده می‌کنه تا فقط بخش واجد اکثریت writable بمونه.

یک partition کنترل‌شده در lab می‌سازیم و refusal سمت بدون quorum رو به‌عنوان رفتار ایمنی می‌بینیم، نه failure اضافی.

During a partition, allowing both sides to write would create diverging histories. Galera uses a Primary Component and quorum so only the valid majority side remains writable.

Create a controlled partition in the lab and treat write refusal on the non-quorate side as safety behavior, not as an extra failure.

Flow control یعنی سرعت cluster به کندترین مسیر هم حساس استFlow control exposes cluster backpressure

اگه یک node apply رو عقب بندازه، Galera می‌تونه برای حفظ consistency فشار رو به بقیه برگردونه. wsrep_flow_control_paused سرنخ می‌ده که cluster چقدر pause شده.

پس latency write فقط داستان client و node محلی نیست؛ state بقیهٔ cluster هم می‌تونه دخیل باشه.

If a node cannot keep up with apply work, Galera can propagate backpressure to protect cluster consistency. wsrep_flow_control_paused helps show how much the cluster has been throttled.

Write latency is therefore not only about the client and local node; the rest of the cluster can influence it.

بعد از اینکه همهٔ nodeها پایین اومدن، انتخاب node برای bootstrap باید از recovered state و جدیدترین position بیاد. «این server همیشه primary بود» دلیل فنی نیست.

After all nodes are down, choosing a bootstrap node must come from recovered state and the most advanced position. “This machine used to be primary” is not sufficient evidence.
