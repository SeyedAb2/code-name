فیلتر روی JSON path و محاسبهٔ قیمت query رو کند کرده؛ آیا expression رو مستقیم می‌توان index کرد؟

Filtering on a JSON path and computed price is slow. Can the expression be indexed directly?

گاهی query کند نیست چون index نداریم؛ کند هست چون مقداری که می‌خوایم index کنیم اصلاً ستون مستقیم نیست. Generated column می‌تونه یک expression مثل JSON path رو به چیزی تبدیل کند که هم قابل‌دیدن هست هم قابل index شدن.

Sometimes a query is not slow because an index is missing, but because the searchable value is hidden inside an expression. A generated column can expose a value such as a JSON path as something visible and indexable.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: generated value قابل‌اندازه‌گیری و قابل index. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is measurable, indexable generated values. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

Expression رو اول قابل‌مشاهده کنMake the expression observable first

قبل از ساختن generated column، expression رو مستقیم روی چند ردیف اجرا کن. برای JSON باید path غایب، NULL و type نامنتظره رو هم ببینی. اگه expression از اول معنی درستی نداره، index فقط خطا رو سریع‌تر می‌کنه.

بعد همان expression رو به ستون generated تبدیل می‌کنیم و با SHOW CREATE TABLE و information_schema.COLUMNS ثابت می‌کنیم تعریف واقعی چیست.

Before creating a generated column, run the expression directly over representative rows. For JSON, include missing paths, NULL, and unexpected types. If the expression is semantically wrong, indexing it only makes the wrong answer faster.

Then turn that expression into a generated column and inspect SHOW CREATE TABLE and information_schema.COLUMNS to verify the actual definition.

ALTER TABLE events ADD COLUMN kind VARCHAR(40) AS (JSON_UNQUOTE(JSON_EXTRACT(payload,'$.kind'))) PERSISTENT;

این تغییر رو فقط روی fixture انجام بده و before/after رو نگه دار. موفق‌شدن statement به‌تنهایی کافی نیست؛ نتیجهٔ واقعی رو با DDL generated column، plan قبل/بعد و storage/write cost verify کن.

Run the change only on the fixture and preserve before/after evidence. A successful statement alone does not prove the desired end state.

VIRTUAL و PERSISTENT یک trade-off هستنVIRTUAL and PERSISTENT are trade-offs

Generated value می‌تونه موقع read محاسبه شود یا به‌شکل persistent نگه داشته شود، بسته به نوع و نسخه. سؤال اصلی این هست که هزینه رو کجا می‌خوای بدهی: write/storage یا read/computation.

برای columnی که قرار هست index شود، syntax و محدودیت نسخه رو دقیق بررسی کن. اینجا اسم feature کافی نیست؛ DDL واقعی نسخهٔ هدف مهم هست.

A generated value may be calculated on read or stored persistently, depending on the definition and release. The design question is where you want to pay the cost: writes/storage or reads/computation.

For an indexed generated column, verify syntax and version restrictions on the actual target release. The feature name alone is not enough.

EXPLAIN SELECT id FROM events WHERE kind='purchase';

بعد از اجرا فقط دنبال اسم index نگرد. plan رو کنار query بخون و روی DDL generated column، plan قبل/بعد و storage/write cost تمرکز کن. اگه plan با چیزی که پیش‌بینی کردی فرق داشت، همین اختلاف سؤال بعدی ماست.

Do not stop at the chosen index name. Read the plan in the context of the query and focus on generated-column DDL, before/after plans, and storage/write cost. Any mismatch with your prediction becomes the next investigation question.

Plan قبل و بعد رو کنار هم بگذارCompare the access path before and after

یک query مستقیم روی JSON_EXTRACT می‌زنیم، بعد همان شرط رو روی generated column indexشده اجرا می‌کنیم. EXPLAIN به ما می‌گه آیا تغییر واقعاً مسیر دسترسی رو عوض کرده یا نه.

اگه plan عوض نشد، فوراً index دیگری نساز. selectivity، type، collation و مقدارهای واقعی رو بررسی کن.

Run one query directly against JSON_EXTRACT, then express the same predicate through the indexed generated column. EXPLAIN shows whether the change actually altered the access path.

If the plan does not change, do not immediately add another index. Check selectivity, data type, collation, and the real values first.

SELECT JSON_EXTRACT('{}','$.kind');

این کد رو روی lab اجرا کن و فقط به «بدون خطا تمام شد» اکتفا نکن. خروجی یا state بعدش باید دربارهٔ generated value قابل‌اندازه‌گیری و قابل index یک چیز مشخص بهت بگه؛ همون چیز رو در پاسخ ثبت کن.

Run this in the lab and require an observable result. The output or resulting state should prove one specific point about measurable, indexable generated values.

هزینهٔ migration رو فراموش نکنDo not forget migration cost

اضافه‌کردن generated column و index روی table بزرگ ممکن هست DDL سنگینی باشد. duration، lock و replica impact رو روی staging اندازه بگیر.

بعد هم rollback واقعی رو بنویس: اگه مجبور شدی index/column رو برداری، data اصلی payload باید هنوز سالم باشد.

Adding a generated column and index to a large table can be a substantial DDL operation. Measure duration, locking, and replica impact in staging.

Also define a real rollback path: if the generated column/index must be removed, the original source data should remain intact.

SELECT DATA_LENGTH,INDEX_LENGTH FROM information_schema.TABLES WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='events';

این query قرار نیست چیزی رو تعمیر کنه؛ فقط state رو قابل‌دیدن می‌کنه. مقدارهای مرتبط با DDL generated column، plan قبل/بعد و storage/write cost رو ثبت کن و قبل از هر تغییر بعدی snapshot رو نگه دار.

This query is observational. Capture the relevant state before changing anything so later conclusions about measurable, indexable generated values can be tied to evidence.
