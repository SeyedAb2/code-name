پروژهٔ ۲ — tuning و engine در MariaDB

Project 2 — MariaDB tuning and storage engines

گزارش روزانه کند هست و تیم می‌خواهد جدول رو به engine دیگری ببرد؛ اول باید بدانیم bottleneck واقعاً کجاست.

A daily report is slow and the team wants another storage engine. First find the actual bottleneck.

عملی · Practicalتحویل با evidence · Evidence-based handoff

ماموریتMission

با دادهٔ ساختگی، plan و زمان baseline بساز، یک تغییر query/index کنترل‌شده آزمایش کن و سپس engine رو فقط بر اساس نیاز transaction/recovery/concurrency ارزیابی کن.

Create a baseline plan and timings on synthetic data, test a controlled query/index change, then evaluate engines against transaction, recovery, and concurrency needs.

پروژه رو روی دادهٔ disposable انجام بده. پاسخ تشریحی به‌تنهایی قبولی نیست؛ query، خروجی، فایل artifact یا تست باید قابل‌بررسی باشد.

Use disposable data. Explanations alone do not pass; queries, outputs, artifacts, or tests must be reviewable.

تحویل و معیار قبولیDeliverables and acceptance

  • README شامل نسخه، پیش‌نیاز، دستور اجرا و rollback / README with release, prerequisites, run, and rollback steps
  • SQL/scripts و data fixtures بدون secret واقعی / SQL/scripts and fixtures without real secrets
  • خروجی‌های واقعی و نتیجهٔ verify / Actual outputs and verification result
  • محدودیت‌ها و موردهای آزمایش‌نشده مشخص / Limitations and untested assumptions stated

مراحل مأموریتMission milestones

1) dataset و baseline1) Dataset and baseline

دادهٔ توزیع‌دار بساز و query report رو چند بار با ورودی ثابت اجرا کن.

Create a distributed dataset and run the report several times with fixed parameters.

EXPLAIN SELECT customer_id,SUM(total) FROM orders GROUP BY customer_id;

مدرک: median، rows و نتیجهٔ query رو ثبت کن.

Proof: Record median, rows, and result correctness.

راهنماییHint

یک اجرای سریع رو معیار نگذار.

Do not judge by one fast run.

2) فرضیهٔ tuning2) Tuning hypothesis

از plan یک تغییر مشخص انتخاب کن و فقط همان رو عوض کن.

Choose one change from the plan and change only that.

CREATE INDEX ix_orders_date_customer ON orders(created_at,customer_id);

مدرک: plan و زمان قبل/بعد رو compare کن.

Proof: Compare plans and timings.

راهنماییHint

اگه خروجی فرق کند، تغییر رد هست.

Reject changes that alter results.

3) Engine نیازها3) Engine requirements

نیازهای transaction، locking، crash recovery و write rate رو فهرست کن.

List transaction, locking, crash recovery, and write-rate requirements.

SHOW ENGINES;

مدرک: InnoDB و Aria/MyISAM رو از guarantee واقعی مقایسه کن.

Proof: Compare actual guarantees across engines.

راهنماییHint

نام سریع‌تر در benchmark عمومی دلیل کافی نیست.

A generic benchmark is not sufficient evidence.

4) آزمایش محدود4) Bounded experiment

جدول disposable رو در engineهای مجاز بساز و workload یکسان اجرا کن.

Create disposable tables on supported engines and run the same workload.

SHOW TABLE STATUS LIKE 'bench_%';

مدرک: زمان، خطا و رفتار rollback رو ثبت کن.

Proof: Record timing, errors, and rollback behavior.

راهنماییHint

خاموشی اجباری فقط در lab.

Forced shutdown only in a lab.

5) تصمیم مهندسی5) Engineering decision

تغییر رو نگه دار/rollback کن و trade-off رو تحویل بده.

Keep or roll back the change and report trade-offs.

-- README with plans, output, engine rationale, rollback

مدرک: مسیر آزمایش از ابتدا قابل اجرا باشد.

Proof: The experiment is reproducible from scratch.

راهنماییHint

correctness بر سرعت مقدم هست.

Correctness comes before speed.

۶) مقایسهٔ کنترل‌شده6) Controlled comparison

query و dataset رو ثابت نگه دار و گزینهٔ index رو با baseline مقایسه کن.

Keep query and dataset fixed, then compare the index candidate with the baseline.

EXPLAIN SELECT customer_id,SUM(total) FROM orders WHERE created_at >= '2026-01-01' GROUP BY customer_id;

plan، زمان‌های تکراری و correctness رو ضمیمه کن.

Attach the plan, repeated timings, and correctness check.

راهنماییHint

یک بار سریع کافی نیست.

One fast run is not enough.

۷) هزینهٔ write7) Write cost

اثر candidate index رو روی batch insert اندازه بگیر.

Measure the candidate index's effect on a bounded insert batch.

SHOW INDEX FROM orders;
-- compare identical inserts on disposable tables with and without the candidate index

تعداد row و شرایط اجرا یکسان باشد؛ فضا و سرعت write رو هم گزارش کن.

Keep row count and conditions equal; report write speed and storage too.

راهنماییHint

سرعت read به‌تنهایی معیار تصمیم نیست.

Read speed alone is not the decision criterion.

بازبینی تحویلHandoff review

پروژه رو از صفر در محیط تمیز اجرا کن. مطمئن شو artifact قابل‌خواندن و restore هست، secret جا نمانده و شخص دیگری می‌تونه نتیجه رو تکرار کند.

Run the project from scratch in a clean environment. Verify the artifact is readable and restorable, no secret remains, and another person can reproduce the result.
