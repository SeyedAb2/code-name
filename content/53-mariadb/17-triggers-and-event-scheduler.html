موجودی بعد از import ناگهان تغییر کرده؛ نه API این کار رو کرده و نه job برنامه. آیا trigger پنهانی وجود داره؟

Stock changed after an import. Neither the API nor an application job did it. Could a hidden trigger be responsible?

گاهی API هیچ UPDATEی نزده ولی table دیگری عوض شده. اینجا باید دنبال رفتار پنهان بگردیم: trigger یا event. این فصل اول اثر رو می‌بینیم، بعد owner آن رو پیدا می‌کنیم.

Sometimes the application did not issue an UPDATE, yet another table changed. That is a signal to look for hidden server-side behavior such as triggers or scheduled events. This chapter starts from the effect and traces it back to its owner.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: رفتار پنهان trigger و event. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is hidden trigger and event behavior. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

Trigger رو inventory کن قبل از حدسInventory triggers before guessing

SHOW TRIGGERS و information_schema.TRIGGERS سریع می‌گن چه چیزی به table وصل هست. اسم trigger کافی نیست؛ timing، event و body رو هم با SHOW CREATE TRIGGER ببین.

این عادت در incident مهم هست. قبل از اینکه app developer رو متهم کنی، ببین database خودش چه side effectهایی تعریف کرده.

SHOW TRIGGERS and information_schema.TRIGGERS tell you what is attached to a table. A trigger name is not enough; inspect timing, event, and body with SHOW CREATE TRIGGER.

This matters during incidents. Before blaming application code, check whether the database itself defines hidden side effects.

OLD و NEW رو روی تغییر واقعی ببینObserve OLD and NEW on real changes

برای UPDATE، trigger هم مقدار قبل رو داره هم بعد را. یک ردیف رو تغییر می‌دهیم و audit row رو می‌خونیم تا دقیقاً بفهمیم OLD.status و NEW.status کجا معنی دارن.

بعد یک UPDATE چندردیفی می‌زنیم. trigger row-level برای هر ردیف matchشده اجرا می‌شه؛ پس code trigger باید از اول multi-row workload رو تحمل کند.

For an UPDATE trigger, both old and new row values are available. Modify one row and inspect the audit result so OLD.status and NEW.status become concrete.

Then run a multi-row UPDATE. Row-level triggers fire for each affected row, so trigger code must be designed for real multi-row workloads from the start.

SELECT * FROM audit_log WHERE item_id=1;

Event Scheduler یک worker پنهان داخل database استThe Event Scheduler is an in-server worker

Event Scheduler وقتی فعال باشد می‌تونه job زمان‌دار اجرا کند، حتی اگه app خاموش باشد. همین قدرت یعنی owner، schedule و cleanup باید روشن باشد.

یک event یک‌بارهٔ کوتاه می‌سازیم، marker رو می‌بینیم، بعد event رو disable و حذف می‌کنیم. lab خوب resource باقی‌مانده نداره.

When enabled, the Event Scheduler can run scheduled work even if the application is not running. That power makes ownership, schedule, and cleanup important.

Create a short one-time event, observe its marker, then disable and remove it. A good lab does not leave background resources behind.

Hidden behavior هزینهٔ عملیاتی دارهHidden behavior has operational cost

Trigger و event می‌تونن مفید باشند، ولی چون از روی request code جلوی چشم نیستن، debugging رو سخت‌تر می‌کنن. برای همین باید inventory، naming و documentation جدی داشته باشند.

اگه rule رو می‌شه واضح‌تر در application یا یک job قابل‌مشاهده نگه داشت، این trade-off رو صریح مقایسه کن؛ نه اینکه trigger رو پیش‌فرض انتخاب کنی.

Triggers and events can be useful, but because their behavior is not visible in request code they increase debugging cost. Inventory, naming, and documentation therefore matter.

If a rule can live more transparently in application code or a visible job system, compare that trade-off explicitly rather than defaulting to a trigger.
