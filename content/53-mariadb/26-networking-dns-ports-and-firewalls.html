روی خود سرور اتصال موفق هست، اما برنامهٔ remote خطای timeout می‌ده؛ آیا مشکل password هست؟

A local connection works, but the remote application times out. Is the password the problem?

Access denied و timeout هر دو برای کاربر «وصل نشد» هستن، ولی در دو نقطهٔ کاملاً متفاوت شکست خورده‌اند. این فصل مسیر connection رو لایه‌به‌لایه دنبال می‌کنه تا به‌جای تغییر random password بفهمیم failure کجاست.

Access denied and a network timeout both look like “connection failed” to a user, but they fail at very different boundaries. This chapter follows the connection layer by layer so diagnosis replaces random password changes.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: مسیر DNS تا authentication و تشخیص محل failure. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is the path from DNS to authentication and failure localization. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

مسیر رو از اسم تا login بشکنBreak the path into stages

ترتیب ساده‌ای داریم: DNS → route → firewall → listener/port → TLS → account host match → authentication → privilege. هر error فقط بعضی از این مراحل رو رد یا تأیید می‌کنه.

با همین نقشه، Connection refused و Access denied دیگر دو پیام مبهم نیستن؛ هرکدام محل جست‌وجوی بعدی رو محدود می‌کنن.

Use a simple path: DNS → route → firewall → listener/port → TLS → account host match → authentication → privilege. Each error proves or rules out only part of that path.

With that model, Connection refused and Access denied stop being generic failures; each narrows the next useful check.

getent hosts db.example.test
# or
nslookup db.example.test

این command فقط یک مرز از مسیر رو تست می‌کنه. مقصد، زمان و نتیجهٔ دقیق رو نگه دار؛ موفقیت این مرحله هنوز لایه‌های بعدی مثل TLS یا authentication رو ثابت نمی‌کنه.

This command tests only one boundary. Record the exact target and result; success here does not prove later layers such as TLS or authentication.

localhost همیشه TCP نیست`localhost` may not mean TCP

Client MariaDB ممکن هست برای localhost از Unix socket استفاده کند. پس اینکه mariadb -h localhost کار می‌کنه، لزوماً port 3306 رو ثابت نمی‌کنه.

با --protocol=tcp -h 127.0.0.1 مسیر TCP رو مجبور می‌کنیم و بعد listener و firewall رو جدا می‌سنجیم.

MariaDB clients can use a Unix socket for localhost. A successful local connection therefore does not necessarily prove TCP port 3306 works.

Force TCP with --protocol=tcp -h 127.0.0.1, then inspect the listener and firewall separately.

mariadb --protocol=tcp -h 127.0.0.1 -P 3306 -u app -p

این کد رو روی lab اجرا کن و فقط به «بدون خطا تمام شد» اکتفا نکن. خروجی یا state بعدش باید دربارهٔ مسیر DNS تا authentication و تشخیص محل failure یک چیز مشخص بهت بگه؛ همون چیز رو در پاسخ ثبت کن.

از همان namespace برنامه تست کنTest from the application's network namespace

روی host ممکن هست DNS و port سالم باشند ولی container برنامه route یا DNS دیگری داشته باشد. تست باید از جایی اجرا شود که request واقعی شروع می‌شه.

در Docker نام service رو از داخل app container resolve می‌کنیم. localhost داخل container خودش هست، نه host و نه database container.

DNS and ports can work from the host while the application container has a different route or resolver. Run the test from the same place the real application connection originates.

In Docker, resolve the database service name from inside the application container. localhost inside that container refers to itself, not the host or database container.

Error رو با زمان و مقصد ثبت کنRecord the exact error, target, and elapsed time

Timeout بعد از چند ثانیه با refusal فوری یک معنی نداره. برای incident، hostname، IP resolved، port، source، timestamp و متن کامل error رو نگه دار.

این اطلاعات باعث می‌شه تیم network، DBA و app دربارهٔ یک connection واحد حرف بزنند، نه سه حدس متفاوت.

A multi-second timeout means something different from an immediate refusal. For incidents, record hostname, resolved IP, port, source, timestamp, elapsed time, and exact error text.

That makes the network, database, and application teams reason about the same connection rather than three different guesses.
