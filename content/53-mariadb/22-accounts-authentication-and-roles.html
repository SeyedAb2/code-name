گزارش‌گیر به کل دیتابیس دسترسی داره چون برنامه با root وصل می‌شه؛ چطور دسترسی رو محدود کنیم؟

A reporting app can access the whole database because it connects as root. How do we restrict accounts and roles?

اگه برنامه با root وصل می‌شه، تقریباً هر باگ برنامه تبدیل می‌شه به باگی با قدرت administrator. MariaDB account فقط اسم کاربر نیست؛ ترکیب user و host هست. این فصل دسترسی رو از حالت «کار می‌کنه» به «دقیقاً همین‌قدر اجازه داره» می‌برد.

If an application connects as root, almost every application bug inherits administrator power. A MariaDB account is not just a username; it is the combination of user and host. This chapter moves access control from “it works” to “it has exactly the permissions it needs.”

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: account واقعی، role و least privilege. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is real accounts, roles, and least privilege. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

user@host یک هویت کامل است`user`@`host` is the account identity

app@localhost و app@10.% دو account جدا هستن، حتی اگه password یکسان داشته باشند. موقع خطای Access denied فقط username رو نگاه نکن؛ source connection و CURRENT_USER() هم مهم‌اند.

یک account محدود می‌سازیم، با همان account وصل می‌شیم و فرق USER() و CURRENT_USER() رو در سناریوی host matching می‌بینیم.

app@localhost and app@10.% are different accounts even if they share a password. When investigating Access denied, do not inspect only the username; source host and CURRENT_USER() matter too.

Create a restricted account, log in with it, and use USER() versus CURRENT_USER() to make host matching visible.

CREATE USER 'app_read'@'localhost' IDENTIFIED BY 'replace-outside-lab';

این object عمداً کوچک و آزمایشیه تا behavior رو بدون سر و صدای production ببینیم. بعد از ساخت، با metadata یا یک query مستقل ثابت کن چیزی که می‌خواستیم واقعاً ساخته شده.

The object is intentionally small and disposable. After creating it, use independent metadata or a query to prove that the intended behavior really exists.

Role فقط وقتی مفید هست که grant واقعی رو ساده کندRoles should simplify real privilege sets

به‌جای پخش‌کردن ده GRANT روی چند account، role رو برای یک مسئولیت واقعی مثل read_orders می‌سازیم. بعد role رو به user می‌دهیم و default role رو روشن می‌کنیم.

ولی باز هم SHOW GRANTS پایان کار نیست. باید با همان user یک کار مجاز و یک کار غیرمجاز رو اجرا کنی.

Instead of duplicating many grants across accounts, define a role around a real responsibility such as read_orders. Assign it to the user and configure the default role as needed.

But SHOW GRANTS is not the end of the test. Log in as that user and perform one allowed action and one denied action.

SET DEFAULT ROLE read_orders FOR 'app_read'@'localhost';

این کد رو روی lab اجرا کن و فقط به «بدون خطا تمام شد» اکتفا نکن. خروجی یا state بعدش باید دربارهٔ account واقعی، role و least privilege یک چیز مشخص بهت بگه؛ همون چیز رو در پاسخ ثبت کن.

Run this in the lab and require an observable result. The output or resulting state should prove one specific point about real accounts, roles, and least privilege.

کمترین دسترسی یعنی object و operation مشخصLeast privilege means specific objects and operations

گاهی برنامه فقط باید status سفارش رو update کند. دادن UPDATE روی کل schema راحت‌تر هست، ولی blast radius رو بی‌دلیل بزرگ می‌کنه.

هرجا MariaDB اجازه می‌ده، privilege رو تا object یا حتی column لازم محدود کن و بعد سناریوی واقعی برنامه رو با همان account اجرا کن.

An application may only need to update an order's status. Granting UPDATE over an entire schema is simpler, but unnecessarily expands the blast radius.

Where practical, restrict privileges to the required object or column and then run the real application operation using that account.

SELECT CURRENT_USER(),USER();
SHOW GRANTS;

این query قرار نیست چیزی رو تعمیر کنه؛ فقط state رو قابل‌دیدن می‌کنه. مقدارهای مرتبط با CURRENT_USER()، SHOW GRANTS و allowed/denied operation رو ثبت کن و قبل از هر تغییر بعدی snapshot رو نگه دار.

This query is observational. Capture the relevant state before changing anything so later conclusions about real accounts, roles, and least privilege can be tied to evidence.

Credential provisioning رو از SQL نمونه جدا نگه دارKeep credential provisioning out of course literals

در lab می‌تونی password ساختگی داشته باشی، ولی course نباید عادت بدهد secret واقعی رو در migration، git یا shell history بچسبانی.

برای production، روش provisioning و rotation باید جدا از source code طراحی شود. SQL فصل فقط contract account و privilege رو نشان می‌ده.

Disposable labs can use fake passwords, but the course must not teach developers to commit real credentials into migrations, Git, or shell history.

In production, provisioning and rotation belong to a separate secret-management boundary. The SQL here demonstrates account and privilege semantics.

SELECT User,Host,plugin FROM mysql.user WHERE User='app_read';
