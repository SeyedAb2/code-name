یک CREATE TABLE اجرا شده، اما تیم نمی‌داند جدول transactional هست یا crash recovery چه رفتاری داره.

A CREATE TABLE succeeded, but the team does not know whether the table is transactional or how crash recovery behaves.

در MariaDB یک CREATE TABLE شبیه هم می‌تونه روی engineهای متفاوت، تضمین‌های متفاوتی بدهد. پس قبل از اینکه دربارهٔ transaction، crash recovery یا قفل حرف بزنیم، باید بفهمیم داده واقعاً دست کدام Storage Engine هست.

Two visually similar CREATE TABLE statements can end up with very different guarantees because MariaDB supports multiple storage engines. Before reasoning about transactions, crash recovery, or locking, identify which engine actually owns the data.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: قرارداد Storage Engine و چیزی که واقعاً از table تضمین می‌گیری. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is the storage-engine contract and actual table guarantees. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

SQL Server نیست؛ یک لایهٔ SQL و چند engine داریمOne SQL layer, multiple engines

MariaDB parser و optimizer رو از storage engine جدا می‌کنه. یعنی SQL رو server می‌فهمد، ولی بخش مهمی از نگه‌داری داده، index، locking و recovery رو engine انجام می‌ده. به همین خاطر اولین سؤال عملی این فصل SHOW ENGINES هست.

اسم engine رو از حافظه حدس نمی‌زنیم. information_schema.ENGINES و metadata جدول به ما می‌گن چه چیزی فعال هست، transaction داره یا نه و table واقعاً روی چه engineی ساخته شده.

MariaDB separates much of the SQL layer from the storage-engine layer. The server parses and optimizes SQL, while storage, indexing, locking, and recovery semantics depend heavily on the chosen engine. That is why the first useful question is SHOW ENGINES.

Do not guess engine capabilities from memory. information_schema.ENGINES and table metadata tell you what is available, which capabilities are exposed, and which engine a table actually uses.

Default فقط default استA default is only a default

default_storage_engine به ما می‌گه اگه در DDL چیزی ننویسیم چه انتخابی انجام می‌شه. ولی یک schema قدیمی، dump یا migration می‌تونه engine رو صریحاً تعیین کرده باشد. پس default هیچ‌وقت جای بررسی SHOW CREATE TABLE رو نمی‌گیره.

این فرق وقتی مهم می‌شه که یک جدول قدیمی MyISAM یا Aria وسط یک workload تراکنشی پیدا می‌کنی. ظاهر queryها یکی هست، ولی رفتار rollback و هم‌زمانی لزوماً یکی نیست.

default_storage_engine tells you what MariaDB chooses when DDL does not specify an engine. Existing schemas, dumps, and migrations can override it explicitly, so the default never replaces SHOW CREATE TABLE.

This becomes important when a legacy MyISAM or Aria table appears inside an otherwise transactional workload. The SQL may look identical while rollback and concurrency behavior differ.

Engine رو از روی نیاز انتخاب کنChoose an engine from required guarantees

برای بیشتر workloadهای تراکنشی عمومی، InnoDB نقطهٔ شروع منطقی هست؛ ولی جملهٔ «InnoDB همیشه سریع‌تر است» هم به‌اندازهٔ جملهٔ «Aria سبک‌تر هست پس بهتر است» بی‌مدرک هست. سؤال درست این است: atomicity می‌خوای؟ چند writer داری؟ crash recovery چقدر مهم هست؟

فصل بعد InnoDB رو عمیق‌تر باز می‌کنیم. اینجا فقط می‌خوایم عادت کنیم هر تصمیم engine رو به یک نیاز و یک آزمایش وصل کنیم.

For general transactional workloads, InnoDB is the normal starting point. But “InnoDB is always faster” is no more useful than “Aria is lighter, therefore better.” Ask what guarantees the workload needs: atomicity, concurrent writers, crash recovery, and operational tooling.

The next chapter dives into InnoDB. Here the goal is to build the habit of tying every engine choice to a concrete requirement and an observable test.

تبدیل engine یک rename ساده نیستChanging engines is not a rename

ALTER TABLE ... ENGINE=... می‌تونه جدول رو بازسازی کند، زمان ببرد، فضای موقت بخواهد و روی lock یا replication اثر بگذارد. روی جدول واقعی فقط چون command کوتاه هست، آن رو کم‌هزینه فرض نکن.

قبل و بعدِ تبدیل، row count، DDL، engine و queryهای مهم رو نگه دار. اگه قرار هست این کار روی دادهٔ حجیم انجام شود، staging و زمان‌بندی عملیاتی بخشی از خود تغییر هست.

ALTER TABLE ... ENGINE=... can rebuild a table, consume temporary space, take time, and affect locking or replication. A short command is not evidence of a cheap operation.

Preserve row counts, DDL, engine metadata, and key query results before and after conversion. On a large table, staging tests and an operational rollout plan are part of the change itself.
