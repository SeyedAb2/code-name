تغییر نام ستون ساده به نظر می‌رسه، اما نسخهٔ فعلی اپ هنوز همان ستون رو می‌خونه؛ ترتیب rollout چیست؟

Renaming a column seems simple, but the current app still reads it. What is the rollout order?

اسم Online DDL آدم رو گول می‌زنه: online یعنی الزاماً «بدون lock، بدون IO و بدون اثر روی replica» نیست. این فصل migration رو مثل rollout چندنسخه‌ای application می‌بینه، نه فقط اجرای یک ALTER TABLE.

The phrase Online DDL can be misleading: online does not mean zero locking, zero I/O, or zero replica impact. This chapter treats schema migration as a multi-version application rollout, not merely an ALTER TABLE command.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: Online DDL به‌عنوان rollout چندمرحله‌ای. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is Online DDL as a staged rollout. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

نوع operation و algorithm رو روی نسخهٔ هدف چک کنVerify operation and algorithm on the target release

یک ADD COLUMN و یک DROP COLUMN الزاماً cost یکسان ندارن. پشتیبانی INSTANT, INPLACE یا rebuild به operation و version بستگی داره.

قبل از production، DDL واقعی رو روی schema و dataset شبیه staging اجرا کن و duration و metadata lock رو ببین.

An ADD COLUMN and DROP COLUMN do not necessarily have the same cost. Support for INSTANT, INPLACE, or rebuilding depends on the operation and release.

Run the exact DDL against representative staging schema/data and observe duration and metadata locking before production.

Expand قبل از contractExpand before contract

برای rename ناسازگار، اول ستون جدید nullable اضافه می‌کنیم، app نسخهٔ سازگار deploy می‌شه، data backfill می‌شه، write/read switch می‌شه و تازه آخر کار ستون قدیمی حذف می‌شه.

این ترتیب باعث می‌شه مدتی دو نسخهٔ app بتونن هم‌زمان کار کنن. Migration خوب deployment order رو هم تعریف می‌کنه.

For an incompatible rename, first add the new nullable column, deploy compatible application code, backfill data, switch reads/writes, and only later remove the old column.

That sequence allows old and new application versions to overlap safely. A good migration defines deployment order as well as DDL.

Backfill رو batch و observable کنMake backfills bounded and observable

یک UPDATE میلیاردردیفی می‌تونه transaction، replication lag و lock pressure بسازه. backfill رو chunk کن و progress قابل query داشته باش.

در هر batch هم idempotency مهمه؛ اگه job وسط کار افتاد باید دوباره اجراشدن امن باشه.

A single massive UPDATE can create long transactions, replica lag, and lock pressure. Backfill in bounded chunks and expose measurable progress.

Each batch should also be restart-safe so a failed migration job can resume without corrupting data.
