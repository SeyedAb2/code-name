backup سالم هست اما چند سفارش درست هم بعد از آن ثبت شده؛ restore کامل دادهٔ خوب رو هم عقب می‌برد.

The backup is good, but valid orders were placed afterward. A full restore would roll those back too.

گاهی backup سالمه، ولی آخرین backup مربوط به دیشبه و از دیشب تا الان کلی data درست وارد شده. Restore کامل همهٔ آن data خوب رو هم عقب می‌بره. PITR برای همین فاصله است: backup پایه + binlogهای پیوسته + توقف دقیق قبل از رخداد خراب.

A backup can be healthy and still be too old. Restoring last night's backup may discard valid changes made since then. Point-in-time recovery closes that gap by combining a base backup with continuous binlogs and stopping just before the bad event.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: PITR با backup و binlog پیوسته. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is PITR with a base backup and continuous binlogs. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

PITR بدون backup پایه معنی ندارهPITR starts from a known base backup

اول باید یک state سالم داشته باشی که می‌دونی از کجا آمده. Binlog به‌تنهایی قرار نیست از صفر database کاملت رو بسازه؛ معمولاً روی backup پایه replay می‌شه.

برای هر backup، coordinate مرتبط با binlog یا metadata لازم رو نگه دار. روز incident نباید تازه دنبال نقطهٔ شروع بگردی.

You first need a known-good base state. Binlogs are usually replayed on top of a base backup; they are not a substitute for having a recoverable starting point.

Preserve the relevant binlog coordinates with each backup. An incident is the wrong time to discover where replay should begin.

Event بد رو پیدا کن، نه اینکه با ساعت حدس بزنیLocate the bad event instead of guessing from the clock

--stop-datetime راحت به نظر می‌رسه، ولی timezone، clock و مرز transaction می‌تونن تصمیم رو مبهم کنن. اگه ممکنه event و position رو inspect کن و transaction کامل رو بشناس.

هدف این نیست که «حدوداً قبل از 14:30» برگردیم؛ می‌خوای دقیقاً آخرین state سالم قبل از تغییر خراب رو بسازی.

--stop-datetime looks convenient, but time zones, clock assumptions, and transaction boundaries can make it ambiguous. Whenever possible, inspect events and positions and understand complete transaction boundaries.

The goal is not to recover to “roughly before 14:30”; it is to reconstruct the last valid state before the damaging change.

اول review، بعد replayReview before replay

Replay رو روی recovery_lab انجام می‌دیم و قبل از هر تصمیم production چند query اعتبارسنجی اجرا می‌کنیم.

Render binlog events into reviewable output first. Inspect the bad event, surrounding transaction boundaries, and affected schemas. Piping unreviewed binlog output directly into production is not disciplined recovery.

Replay into an isolated recovery target and run validation queries before making any production decision.

Retention باید RPO رو پوشش بدهBinlog retention must support the RPO

اگه backup هفتگی داری ولی binlog فقط 24 ساعت نگه می‌داری، PITR روز ششم زنجیرهٔ کاملی نداره. retention رو از روی recovery target طراحی کن، نه صرفاً فضای disk.

تمرین آخر این فصل report کوتاهی می‌خواد: backup ID، binlog range، stop coordinate و queryهایی که state بازیابی‌شده رو ثابت کردن.

If full backups are weekly but binlogs are retained for only 24 hours, point-in-time recovery on day six has a gap. Retention should follow recovery objectives, not just disk pressure.
