A multi-hour dump misses the recovery target. A physical backup may be faster, but raw backup files are not ready to restore.

وقتی logical dump چند ساعت طول می‌کشد، physical backup جذاب می‌شه. ولی directory خامی که mariadb-backup ساخته هنوز چیزی نیست که همین‌طور copy کنی و server رو روشن کنی. مرحلهٔ prepare بخشی از recovery هست.

When logical dumps take hours, physical backups become attractive. But a raw directory produced by mariadb-backup is not something to copy blindly into a server. The prepare phase is part of recovery.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: physical backup، prepare و restore chain. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is physical backup, prepare, and restore chains. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

نسخهٔ tool و server رو جفت کنMatch backup tooling to the server

Physical backup به format داخلی storage نزدیک‌تر هست، پس compatibility نسخه مهم‌تر از logical SQL dump هست. قبل از هر چیز نسخهٔ mariadb-backup و server source رو ثبت کن.

Upgrade/migration رو با restore physical بدون بررسی compatibility قاطی نکن. Chapter 37 این مرز رو دوباره باز می‌کنه.

Physical backups are closer to internal storage formats, so version compatibility matters more than with portable SQL dumps. Record both mariadb-backup and source server versions.

Do not combine a version upgrade or migration with an unverified physical restore. Chapter 37 revisits that boundary.

Backup خام باید prepare شودA raw backup must be prepared

Online backup ممکن هست pageهایی رو در لحظه‌های متفاوت کپی کرده باشد و log لازم برای یک state سازگار رو هم همراه داشته باشد. --prepare recovery رو روی backup انجام می‌ده تا target قابل restore شود.

وجود فایل‌ها با find فقط می‌گه چیزی نوشته شده؛ موفقیت prepare و بعد restore چیزی هست که recoverability رو نزدیک‌تر ثابت می‌کنه.

An online physical backup can copy pages at different moments while preserving the log needed to reconcile them. --prepare applies recovery to the backup so it becomes suitable for restore.

Seeing files with find only proves that files were written. Successful preparation and an actual restore are much stronger evidence.

Incremental یک زنجیره استIncremental backups form a chain

Incremental backup به full/base وابسته هست. اگه یکی از حلقه‌ها گم شود، داشتن آخرین directory به‌تنهایی نجاتت نمی‌ده.

LSN/metadata هر مرحله رو نگه دار و در restore drill دقیقاً همان order apply رو تمرین کن. Backup chain چیزی نیست که روز incident برای اولین بار کشفش کنی.

An incremental backup depends on its full/base backup. If a link in the chain is missing, the latest incremental directory alone cannot recover the database.

Preserve LSN/metadata for every step and rehearse the exact apply order. A backup chain should not be discovered for the first time during an incident.

Restore رو فقط روی target دورریختنی تمرین کنRehearse restore on an isolated target

--copy-back با datadir واقعی بازی می‌کنه. Server مقصد باید متوقف باشد، مسیر درست و خالی باشد و ownership بعد restore درست شود.

این‌ها رو روی instance دورریختنی انجام می‌دهیم، بعد server رو بالا می‌آوریم و rowهای شناخته‌شده رو query می‌کنیم. هیچ تمرینی ارزش ریسک production data رو نداره.

--copy-back operates on a real data directory. The target server must be stopped, the destination must be correct, and ownership must be restored properly afterwards.

Practice all of this on an isolated instance, start it, and query known rows. No training exercise justifies risking production data.
