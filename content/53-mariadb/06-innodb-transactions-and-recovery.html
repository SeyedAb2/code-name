MariaDB · فصل 6MariaDB · Chapter 6

یک تراکنش پول رو از حساب اول کم کرده اما به حساب دوم اضافه نکرده. چه چیزی باید تضمین می‌کرد؟

A transfer debited one account but failed to credit the other. What should have guaranteed atomicity?

یک انتقال پول دو UPDATE داره، ولی از دید کسب‌وکار فقط یک کار هست. اگه وسطش برنامه بمیرد، یا هر دو تغییر باید بمانند یا هیچ‌کدام. این فصل InnoDB رو از همین درد شروع می‌کنه: transaction فقط چند دستور بین START و COMMIT نیست؛ یک مرز درست برای تغییر داده هست.

A money transfer may require two UPDATE statements, but the business sees a single operation. If the process dies halfway through, either both changes survive or neither does. This chapter starts InnoDB from that problem: a transaction is not just syntax between START and COMMIT; it is a correctness boundary.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: درستی transaction، rollback و قفل‌های InnoDB. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is transaction correctness, rollback, and InnoDB locking. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

اول invariant رو مشخص کنStart with the invariant

قبل از SQL بگو چه چیزی نباید خراب شود. در مثال حساب‌ها، جمع پول نباید فقط به خاطر خطای وسط کار عوض شود. وقتی invariant روشن شد، تازه می‌تونیم بررسی کنیم transaction درست دور کدام statementها قرار می‌گیره.

دو حساب کوچک می‌سازیم، مقدار قبل رو می‌خونیم، انتقال رو commit می‌کنیم و دوباره جمع رو چک می‌کنیم. اینجا query تأیید نهایی بخشی از درس هست، نه تزئین بعد از command.

Before writing SQL, state what must remain true. In the account example, the total amount should not change just because a failure occurs halfway through the transfer. Once the invariant is explicit, the transaction boundary becomes easier to reason about.

Create two small accounts, read the baseline, commit a transfer, and verify both rows and the total afterwards. The verification query is part of the lesson, not decoration after the command.

CREATE TABLE accounts(id INT PRIMARY KEY,balance DECIMAL(10,2) NOT NULL) ENGINE=InnoDB;

این object عمداً کوچک و آزمایشیه تا behavior رو بدون سر و صدای production ببینیم. بعد از ساخت، با metadata یا یک query مستقل ثابت کن چیزی که می‌خواستیم واقعاً ساخته شده.

The object is intentionally small and disposable. After creating it, use independent metadata or a query to prove that the intended behavior really exists.

ROLLBACK رو واقعاً ببینMake rollback observable

خیلی‌ها rollback رو می‌شناسند ولی فقط از روی تعریف. اینجا عمداً balance رو به مقدار بدی تغییر می‌دهیم و قبل از commit برمی‌گردیم. بعد با SELECT ثابت می‌کنیم state قبلی برگشته.

SAVEPOINT هم «transaction داخل transaction» نیست. یک نقطهٔ برگشت داخل همان transaction هست. این فرق بعداً وقتی workflow چندمرحله‌ای می‌سازی مهم می‌شه.

Many developers know what rollback means without having watched it restore state. Here, deliberately make an unwanted change, roll it back before commit, and prove the original value with a query.

A SAVEPOINT is not a nested independent transaction. It is a recovery point inside the same transaction. That distinction matters in multi-step workflows.

قفل تا وقتی transaction باز هست، مال توستLocks live with the transaction

SELECT ... FOR UPDATE رو در Session A اجرا می‌کنیم و transaction رو باز نگه می‌داریم. Session B که بخواهد همان ردیف رو تغییر بدهد، منتظر می‌مونه. این انتظار خودش بخشی از semantics هست؛ database خراب نشده.

ولی transaction بازِ طولانی خیلی زود تبدیل به مشکل عملیاتی می‌شه. پس قاعدهٔ ذهنی‌مان این است: data رو دیر قفل کن، کار لازم رو انجام بده، زود commit/rollback کن و هیچ interaction کاربر رو وسط transaction نگه ندار.

Run SELECT ... FOR UPDATE in Session A and keep the transaction open. When Session B tries to modify the same row, it waits. That wait is part of the concurrency model; it does not mean the database is broken.

Long-lived transactions quickly become operational problems. Acquire locks as late as practical, do the required work, commit or roll back promptly, and never hold a transaction open while waiting for user interaction.

Crash recovery با business retry فرق دارهCrash recovery is not business retry

InnoDB می‌تونه بعد از crash ساختار تراکنشی خودش رو recover کند، ولی این به معنی این نیست که برنامه می‌داند درخواست کاربر بالاخره انجام شد یا نه. اگه connection وسط commit قطع شود، client ممکن هست از نتیجه مطمئن نباشد.

اینجا پای idempotency و retry حساب‌شده وسط میاد. retry کور روی انتقال پول می‌تونه همان کار رو دوبار انجام دهد. recovery دیتابیس و semantics درخواست برنامه دو مسئلهٔ جدا هستن.

InnoDB can recover its transactional state after a crash, but that does not tell an application whether a client request definitely completed. A connection can disappear around commit and leave the caller uncertain.

That is where idempotency and carefully designed retries matter. Blindly retrying a payment or transfer can apply the business operation twice. Database recovery and application request semantics are separate problems.
