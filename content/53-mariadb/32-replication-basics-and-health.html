یک write روی primary موفق شد اما replica هنوز مقدار قبلی رو می‌ده؛ آیا channel خراب هست؟

A write succeeded on the primary, but the replica still shows the old value. Is the channel broken?

Replication وقتی سالم به نظر می‌رسه که data می‌رسه؛ ولی حتی replication سالم هم لزوماً فوری نیست. این فصل بین «خراب شده» و «هنوز نرسیده» فرق می‌ذاره و status رو به row واقعی وصل می‌کنه.

Replication can be healthy without being instantaneous. This chapter separates “broken” from “not applied yet” and connects status fields to an actual row moving through the topology.

جریان data رو از primary تا apply ببینFollow the data from source to apply

مدل ساده‌مون اینه: write روی primary → binlog → receiver روی replica → relay/apply → table replica. هر نقطه failure خودش رو داره.

SHOW ... STATUS رو مثل یک دیوار فیلد نمی‌خونیم؛ اول می‌پرسیم receiver وصل هست؟ apply thread جلو می‌ره؟ آخرین error چیست؟

Use a simple model: write on the primary → binlog → replica receiver → relay/apply → replica table. Each boundary has its own failure modes.

Do not read replication status as a wall of fields. Ask focused questions: is the receiver connected, is the applier progressing, and what is the last error?

Lag طبیعی هست؛ consistency requirement جداستLag is normal; consistency requirements are separate

در replication ناهمگام، write ممکنه روی primary commit شده باشه ولی replica هنوز نرسیده باشه. این یعنی read-after-write از replica باید آگاهانه طراحی بشه.

یک marker row می‌نویسیم و زمان رسیدنش رو می‌بینیم. این آزمایش از هر تعریف نظری بهتر latency واقعی lab رو نشون می‌ده.

With asynchronous replication, a write can commit on the primary before the replica has applied it. That means read-after-write behavior must be designed deliberately.

Write a marker row and observe when it becomes visible on the replica. This makes actual lab lag more concrete than a definition.

Replica backup نیستA replica is not a backup

اگه DELETE اشتباه از primary وارد binlog بشه، replica هم می‌تونه با وفاداری کامل همون اشتباه رو اعمال کنه. replication availability می‌ده، نه history مستقل.

برای همین فصل replication به backup فصل‌های قبلی وصل می‌شه؛ دو ابزار failure model متفاوتی دارن.

If an accidental DELETE is written to the primary binlog, a healthy replica can faithfully apply the same mistake. Replication improves availability, not independent historical recovery.

That is why this chapter connects replication back to backup chapters: the two mechanisms protect against different failures.
