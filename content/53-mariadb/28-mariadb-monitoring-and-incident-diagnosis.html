پس از تغییر اپ، timeoutها زیاد شده‌اند ولی server هنوز پاسخ می‌ده. قبل از restart چه شواهدی لازم هست؟

After an application change, timeouts increase even though the server responds. What evidence is needed before a restart?

اولین واکنش به incident خیلی وقت‌ها restart هست چون سریع به نظر می‌رسه. مشکل اینجاست که restart ممکن هست مهم‌ترین شاهدها رو پاک کند. این فصل از symptom شروع می‌کنه و قبل از repair، snapshot می‌گیره.

Restarting is a tempting first reaction during an incident because it feels fast. The problem is that a restart can erase the most useful evidence. This chapter starts from symptoms and captures state before making repairs.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: incident diagnosis قبل از restart. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is incident diagnosis before restart. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

Scope رو قبل از علت مشخص کنDefine scope before cause

چند endpoint کندند؟ همهٔ clientها یا فقط یک subnet؟ از چه دقیقه‌ای شروع شده؟ error rate بالا رفته یا فقط latency؟ این‌ها قبل از هر فرضیه لازم‌اند.

Version، hostname و زمان رو ثبت می‌کنیم تا evidenceهای بعدی به یک server و window مشخص وصل باشند.

Which endpoints are slow? All clients or one subnet? When did it begin? Is the problem error rate or latency? Those questions come before guessing a cause.

Record version, hostname, and time so every later observation belongs to a specific server and incident window.

Active work رو snapshot بگیرSnapshot active work

SHOW FULL PROCESSLIST، lock state، transactionهای طولانی و replication status می‌تونن چیزی نشان بدهند که یک دقیقه بعد ناپدید می‌شه.

قبل از kill، restart یا reset counter، خروجی رو نگه دار. اگه بعداً repair جواب داد، می‌خوای بدانی دقیقاً چه چیزی رو تغییر داده‌ای.

SHOW FULL PROCESSLIST, lock state, long transactions, and replication status can expose conditions that disappear a minute later.

Preserve them before killing sessions, restarting, or resetting counters. If a repair later works, you need to know what state actually changed.

Database رو از host جدا نبینDo not isolate the database from its host

CPU، memory، disk latency، inode و container limit می‌تونن symptom دیتابیس بسازند. error 137 رو هم نباید بدون kernel/container evidence فوراً «MariaDB OOM شد» بنامی.

DB counters و host metrics رو روی همان timeline کنار هم بگذار. Correlation هنوز proof نیست، ولی محدودهٔ فرضیه رو کوچک می‌کنه.

CPU, memory, disk latency, inode exhaustion, and container limits can all surface as database symptoms. Even exit code 137 should not be labeled “MariaDB OOM” without host/container evidence.

Place database counters and host metrics on the same timeline. Correlation is not proof, but it narrows useful hypotheses.

یک تغییر، همان test، دوبارهOne change, then repeat the same test

Repair رو محدود کن. اگه هم query رو rewrite کنی، هم pool رو عوض کنی، هم restart کنی، بعداً نمی‌فهمی کدام کار اثر داشت.

بعد از تغییر، همان client request و همان query baseline رو دوباره اجرا کن. Incident وقتی بسته می‌شه که verification قابل‌تکرار داشته باشی.

Keep repairs narrow. If you rewrite the query, change pooling, and restart at the same time, you cannot tell which action mattered.

After the change, repeat the original client request and query baseline. An incident is not closed until verification is reproducible.
