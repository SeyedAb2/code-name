یک کاربر ناشناس ستون حساس رو خوانده؛ چه evidenceای داریم؟

An unknown account read a sensitive column. Is query history enough to explain what happened?

Least privilege می‌گه چه کسی چه کاری می‌تونه بکند؛ audit می‌گه چه اتفاقی افتاد. این دو رو اگه قاطی کنیم، هم دسترسی بد طراحی می‌شه هم log بی‌هدف پر می‌شه.

Least privilege answers who is allowed to do what; auditing answers what actually happened. Mixing the two leads to both poor authorization design and noisy logs.

قبل از کد، مسئله رو درست ببینFrame the problem before the code

این فصل رو با syntax شروع نمی‌کنیم. مسئله اینه: least privilege و audit قابل‌استناد. اول یه پیش‌بینی می‌سازیم، بعد با query یا command کوچیک آزمایشش می‌کنیم. هر جا خروجی خلاف انتظار بود، همون‌جا درس اصلی شروع می‌شه.

This chapter does not begin with syntax. The problem is least privilege and defensible audit evidence. We will form a prediction, test it with a small query or command, and treat unexpected output as the beginning of the investigation.

اول سؤال audit رو بنویسWrite the audit question first

«Audit روشن باشد» requirement خوبی نیست. می‌خوای loginها رو ببینی؟ تغییر role؟ DDL؟ خواندن table حساس؟ هرکدام event و حجم متفاوتی داره.

قبل از plugin یا config، یک incident مشخص بنویس و بگو چه فیلدهایی برای پاسخ‌دادن لازم‌اند: account، host، زمان، object، operation و نتیجه.

“Enable auditing” is not a useful requirement. Do you need logins, privilege changes, DDL, or reads of sensitive data? Each has different event volume and evidence.

Before choosing a plugin or setting, write a concrete incident question and list the fields needed to answer it: account, host, time, object, operation, and outcome.

SHOW GRANTS FOR 'api_user'@'10.%';

این query قرار نیست چیزی رو تعمیر کنه؛ فقط state رو قابل‌دیدن می‌کنه. مقدارهای مرتبط با grant snapshot، audit event و retention boundary رو ثبت کن و قبل از هر تغییر بعدی snapshot رو نگه دار.

This query is observational. Capture the relevant state before changing anything so later conclusions about least privilege and defensible audit evidence can be tied to evidence.

مجوز فعلی رو snapshot کنSnapshot current privileges

قبل از revoke یا role change، SHOW GRANTS رو با timestamp نگه دار. بعد از تغییر همان command رو تکرار کن تا معلوم باشد دقیقاً چه چیزی کم شده.

این before/after خیلی مهم‌تر از جملهٔ «دسترسی‌ها محدود شد» هست.

Before revoking access or changing roles, preserve SHOW GRANTS with a timestamp. Run it again afterwards so the exact privilege delta is visible.

That before/after evidence is much stronger than saying “permissions were tightened.”

Audit log خودش data حساس استAudit logs are sensitive data too

Log ممکن هست username، query text یا حتی value حساس داشته باشد. پس retention، filesystem permission، rotation و دسترسی به خود log باید طراحی شود.

اگه audit باعث پرشدن disk شود، ابزار امنیتی می‌تونه خودش incident بسازد. حجم و failure mode رو در lab بشناس.

Audit logs can contain usernames, query text, and potentially sensitive values. Retention, filesystem permissions, rotation, and access to the log itself need design.

If auditing fills the disk, the security mechanism can create an outage. Understand volume and failure modes in a lab.

CREATE ROLE audit_viewer;

این object عمداً کوچک و آزمایشیه تا behavior رو بدون سر و صدای production ببینیم. بعد از ساخت، با metadata یا یک query مستقل ثابت کن چیزی که می‌خواستیم واقعاً ساخته شده.

The object is intentionally small and disposable. After creating it, use independent metadata or a query to prove that the intended behavior really exists.

Audit جای prevention رو نمی‌گیرهAuditing does not replace prevention

اینکه بعداً می‌تونی ببینی چه کسی table رو خوانده، دلیل نمی‌شه privilege وسیع بدهی. اول least privilege، بعد audit برای مشاهده و پاسخ‌گویی.

در تمرین یک user رو محدود می‌کنیم، allowed/denied action رو تست می‌کنیم و بعد می‌بینیم audit چه چیزی از همان اتفاق ثبت کرده.

Being able to see who read a table later is not a reason to grant broad access now. Apply least privilege first, then use auditing for observation and accountability.

In the lab, restrict a user, test allowed and denied actions, and then inspect what the audit mechanism records about those events.

REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'old_app'@'%';

بعد از تغییر privilege با account هدف reconnect کن. یک operation مجاز و یک operation غیرمجاز اجرا کن؛ security وقتی ثابت می‌شه که failure موردانتظار رو هم ببینی.

Reconnect as the target account and test both an allowed and a denied operation. Security is best proven by the expected success and the expected failure.
