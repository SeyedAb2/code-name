Debugging 403/502/504

«سایت خوابیده.» یکی می‌گوید Nginx خراب شده و دیگری می‌خواهد سرویس را restart کند. هنوز هیچ‌کدام تشخیص نیست. اول می‌فهمیم درخواست کجا گیر کرده، بعد همان مرز را بررسی می‌کنیم.

“The site is down.” One person says Nginx is broken; another wants to restart it. Neither is a diagnosis yet. First we find where the request stopped, then inspect that boundary.

سایت بالا نمی‌آید؛ هنوز نمی‌دانیم چراThe site is down; we do not know why yet

دیروز صفحه باز می‌شد؛ امروز مرورگر ۵۰۲ می‌دهد. «Nginx را restart کن» پیشنهاد سریعی است، اما اگر برنامه خاموش باشد، DNS اشتباه باشد یا فایل تنظیمات تازه خراب شده باشد، restart شاید مدرک را پاک کند یا وقفه را بیشتر کند.

The page worked yesterday; today the browser shows 502. “Restart Nginx” is quick advice, but if the app is stopped, DNS is wrong, or the new config is broken, a restart may erase evidence or extend the outage.

از فصل قبل می‌دانیم timeout فقط زمان انتظار یک مرز را محدود می‌کند. حالا همان نگاه را به incident می‌بریم: یک درخواست، status، زمان وقوع، log همان بازه، بعد آزمون مستقیم مرز مشکوک. خطای مرورگر به‌تنهایی نمی‌گوید Nginx مقصر است.

From the previous chapter, we know a timeout only bounds waiting at one boundary. We bring that view to an incident: one request, status, timestamp, logs from that window, then a direct test of the suspected boundary. A browser error alone does not prove Nginx is at fault.

قبل از تغییر، خطا را یک بار بازتولید و ساعت دقیقش را یادداشت کن. بعد بپرس: چه مشاهده‌ای این فرضیه را از بقیه جدا می‌کند؟Before changing anything, reproduce the error once and note its exact time. Then ask: what observation would distinguish this hypothesis from the others?

کد پاسخ جهت می‌دهد، علت را امضا نمی‌کندA status code points a direction; it does not certify a cause

۴۰۳ یعنی دسترسی مجاز نشده؛ دلیل می‌تواند قانون access یا دسترسی فایل باشد. ۵۰۲ یعنی Nginx پاسخ قابل‌قبولی از gateway/upstream نگرفته؛ اتصال refused فقط یک احتمال است. ۵۰۴ یعنی upstream در بازهٔ انتظار پاسخ لازم را نداده؛ این به‌تنهایی نمی‌گوید برنامه از کار افتاده.

403 means access was not allowed; an access rule or file permissions may be involved. 502 means Nginx did not receive an acceptable gateway/upstream response; connection refusal is one possibility. 504 means the upstream did not respond within the configured wait; that alone does not prove the app is dead.

خود اپ هم می‌تواند این statusها را برگرداند؛ پس status را کنار access log، error log و بدنهٔ پاسخ بخوان، نه تنها.

The app itself can return these statuses, so read status alongside access/error logs and the response body, not alone.

مدرک‌ها را با یک درخواست هم‌زمان کنAlign the evidence to one request

زمان و مسیر دقیق را ثبت کن. access log معمولاً درخواست و status را نشان می‌دهد؛ error log جزئیات دسترسی یا upstream را. محل log به package و config وابسته است؛ فرض نکن همه‌چیز زیر /var/log/nginx است.

Record the exact time and path. The access log usually shows the request and status; the error log may reveal access or upstream details. Log locations depend on package/config; do not assume everything is under /var/log/nginx.

inspect the active installation before changing it
sudo nginx -t
sudo nginx -T 2>&1 | less
sudo tail -n 80 /var/log/nginx/error.log
sudo tail -n 80 /var/log/nginx/access.log

nginx -t نحو و قابل‌بارگذاری بودن config را می‌سنجد؛ upstream را تست نمی‌کند. nginx -T config مؤثر و includeها را نشان می‌دهد؛ پیش از share کردن، secretها و نام‌های داخلی را پاک کن. مسیر log را از directiveهای error_log/access_log پیدا کن.

nginx -t checks syntax/loadability, not upstream health. nginx -T shows effective config and includes; redact secrets/internal names before sharing. Find log paths in the error_log/access_log directives.

اگر nginx -t شکست خورد، reload/restart نکن. خطا و شمارهٔ فایل را نگه دار و اول همان را اصلاح کن.If nginx -t fails, do not reload/restart. Keep the error and file/line, and fix that first.

روی systemd نصب، systemctl status nginx و journalctl -u nginx --since '10 minutes ago' --no-pager وضعیت process یا خطای startup/reload را نشان می‌دهند. Active بودن، سلامت HTTP یا upstream را ثابت نمی‌کند.

On systemd installations, systemctl status nginx and journalctl -u nginx --since '10 minutes ago' --no-pager show process state or startup/reload errors. Active does not prove HTTP/upstream health.

از پاسخ شروع کن، اما همان‌جا متوقف نشوStart with the response, but do not stop there

این درخت آزمون بعدی را انتخاب می‌کند، نه علت را از روی status اعلام. فلش‌ها ترتیب پرسش‌اند؛ هر شاخه به مدرک نیاز دارد.

This tree chooses the next test; it does not declare a cause from status alone. Arrows show question order; every branch needs evidence.

هر شاخه به یک قاعده می‌رسد: اصلاح را با همان درخواست و مسیر دوباره بسنج. «دیگر خطا ندیدم» بدون آزمون تکراری مدرک بازیابی نیست.

Every branch leads to one rule: retest the same request through the same path. “I have not seen another error” is not recovery evidence without a retest.

حادثهٔ اول: ۴۰۳ از کجا می‌آید؟Incident one: where does 403 come from?

سایت استاتیک برای /locked/، ۴۰۳ می‌دهد. شاید مجوز فایل باشد، شاید index وجود نداشته باشد یا قانون deny درخواست را گرفته باشد. درخواست و error log را کنار هم می‌گذاریم.

A static site returns 403 for /locked/. It may be permissions, a missing index, or a deny rule. Align the request with the error log.

reproduce once and inspect the matching log
curl -i http://127.0.0.1:18013/locked/
tail -n 20 "$LAB/logs/error.log"
HTTP/1.1 403 Forbidden
[error] ... directory index of ".../site/locked/" is forbidden

این خط می‌گوید پوشه پیدا شده اما index قابل‌سرو ندارد و directory listing خاموش است. فایل گمشده معمولاً ۴۰۴ می‌دهد. در نصب واقعی مسیر را با root/alias مؤثر تطبیق بده؛ worker باید از parentها عبور کند و فایل را بخواند.

This says the directory exists but has no servable index, and listing is off. A missing file normally gives 404. Compare the real path with effective root/alias; the worker must traverse parents and read the file.

inspect path and worker, not broad permissions
namei -l /path/from/error/log/index.html
ps -eo user,pid,cmd | grep '[n]ginx: worker'
stat /path/from/error/log/index.html

اگر پوشه‌ای مجوز x برای عبور ندارد یا فایل خواندنی نیست، فقط مالکیت/گروه/مجوز لازم را اصلاح کن. chmod -R 777 دسترسی بی‌دلیل می‌دهد و مالکیت را پنهان می‌کند. اگر مجوز Unix درست است اما سیستم enforcing است، SELinux/AppArmor و audit را ببین؛ policy را خاموش نکن. root اشتباه اغلب ۴۰۴ می‌سازد، پس از روی آن ۴۰۳ نتیجه نگیر.

If a directory lacks execute/traverse permission or the file is unreadable, fix only the needed owner/group/mode. chmod -R 777 grants needless access and hides ownership. If Unix permissions look right on an enforcing host, inspect SELinux/AppArmor and audit; do not disable policy. A wrong root often yields 404, so do not infer 403 from it.

در لَب علت را پوشهٔ بدون index می‌گذاریم چون تکرارپذیر است. index را می‌سازیم و همان URL را دوباره می‌زنیم؛ ۲۰۰ فقط این مسیر را ثابت می‌کند.

The lab uses a directory without an index because it is reproducible. Add the index and retry the same URL; 200 proves only this path.

حادثهٔ دوم: ۵۰۲ و upstreamی که گوش نمی‌دهدIncident two: 502 and an upstream not listening

درخواست /api/ ۵۰۲ است. برنامه شاید خاموش باشد، port اشتباه باشد، نام resolve نشود یا پاسخ protocol دیگری داشته باشد. از error log شروع می‌کنیم و از همان میزبان به upstream درخواست می‌زنیم.

The /api/ request returns 502. The app may be stopped, the port wrong, the name unresolved, or the response protocol unexpected. Start with the error log and request upstream from the same host.

distinguish a closed upstream from a stopped proxy
tail -n 30 "$LAB/logs/error.log"
ss -lntp | grep -E ':(18013|19013|19999)\b' || true
curl -i --max-time 2 http://127.0.0.1:19013/
[error] ... connect() failed (111: Connection refused) while connecting to upstream
LISTEN ... 127.0.0.1:18013 ... nginx
curl: (7) Failed to connect to 127.0.0.1 port 19013

اینجا proxy گوش می‌دهد اما upstream نه؛ فرضیهٔ خرابی خود Nginx ضعیف می‌شود. مقصد را از proxy_pass مؤثر بردار. ss فقط همین host/network namespace را می‌بیند، نه container یا میزبان دیگر را.

Here the proxy listens but upstream does not, weakening the Nginx-failure hypothesis. Take the target from effective proxy_pass. ss sees only its own host/network namespace, not another container or host.

اگر مقصد hostname است، در محیط Nginx با getent hosts بررسی کن. نام resolveنشده ممکن است هنگام startup بارگذاری config را fail کند؛ DNS پویا و resolver به config/نسخه وابسته است. اگر اتصال برقرار ولی پاسخ نامعتبر است، با curl -v scheme و protocol را بسنج؛ HTTP به port منتظر TLS هم می‌تواند ۵۰۲ بسازد.

If the target is a hostname, use getent hosts in Nginx’s environment. An unresolved name may fail config loading at startup; dynamic DNS and resolver depend on config/version. If connected but response is invalid, check scheme/protocol with curl -v; HTTP sent to a TLS port can also produce 502.

در آزمایش، proxy را به port خالی می‌بریم، log/socket را می‌خوانیم و مقصد را برمی‌گردانیم. فقط پس از nginx -t reload کن؛ direct upstream و همان مسیر proxy باید دوباره ۲۰۰ بدهند.

In the lab, point proxy at an unused port, inspect logs/sockets, then restore the target. Reload only after nginx -t; direct upstream and the same proxy path should return 200 again.

حادثهٔ سوم: ۵۰۴؛ کند با قطع فرق داردIncident three: 504; slow is not unreachable

برای /slow، error log از timeout می‌گوید. اتصال برقرار شده اما داده به‌موقع نرسیده. proxy_read_timeout فاصلهٔ مجاز بین خواندن‌های متوالی را محدود می‌کند، نه کل عمر پاسخ. علت می‌تواند کد کند، صف یا dependency باشد.

For /slow, the error log reports a timeout. A connection was made, but data did not arrive in time. proxy_read_timeout bounds the gap between successive reads, not total response lifetime. Slow code, a queue, or dependency may be responsible.

compare a bounded direct request with the proxied request
curl -i --max-time 4 http://127.0.0.1:19013/slow
time curl -i --max-time 4 http://127.0.0.1:18013/slow
tail -n 20 "$LAB/logs/error.log"
# Direct: HTTP 200 after about 2 seconds
# Proxy with 500ms timeout: HTTP 504
[error] ... upstream timed out while reading response header

اگر direct هم از deadline عبور کرد، اپ/dependency را بررسی کن؛ اگر direct سریع و proxy کند است، مسیر/config را. بالا بردن timeout شاید درخواست‌های بیشتری را باز نگه دارد. فقط پس از شناخت زمان قابل‌قبول تغییرش بده و همان دو درخواست را تکرار کن.

If direct also exceeds its deadline, investigate app/dependency; if direct is fast but proxy is slow, inspect path/config. Raising timeout may hold more requests open. Change it only after establishing acceptable latency, then repeat both requests.

ساعت‌ها را هم‌تراز کنAlign the clocks

خطای Nginx و برنامه فقط وقتی مرتبط‌اند که زمان و درخواستشان بخواند. timezone، ساعت سیستم و قالب timestamp را بررسی کن؛ اگر request ID داری، همان را دنبال کن.

Nginx and app errors correlate only when time and request align. Check timezone, system clock, timestamp formats, and follow a request ID if present.

inspect a narrow time window
date -Is
timedatectl status
sudo journalctl -u nginx --since '10 minutes ago' --no-pager
sudo grep '10:11:' /var/log/nginx/access.log | tail -n 20

قالب و timezone فایل access می‌تواند فرق کند؛ journal هم الزاماً فایل access را ندارد. در نمونه، 10:11: را با دقیقهٔ واقعی عوض کن. ساعت container/میزبان دیگر را جدا بسنج؛ timestamp نزدیک به‌تنهایی هویت درخواست را ثابت نمی‌کند.

Access-log format/timezone may differ, and the journal may not contain file access logs. Replace 10:11: in the example with the actual minute. Check clocks in other containers/hosts separately; nearby timestamps alone do not identify a request.

فرمان بعدی باید دو فرضیه را از هم جدا کندThe next command should distinguish hypotheses

برای ۵۰۲، ss و curl مستقیم می‌پرسند آیا مقصد گوش می‌دهد و پاسخ درست می‌دهد. برای ۴۰۳، namei -l و config مسیر و دسترسی را روشن می‌کنند. برای ۵۰۴، direct request با deadline و زمان‌های log محل تأخیر را محدود می‌کنند.

For 502, ss and direct curl ask whether the target listens and responds correctly. For 403, namei -l and config clarify path/access. For 504, a direct request with deadline and log timing narrow where delay occurs.

آزمون مستقیم را از همان host/namespace بزن که Nginx از آن به upstream می‌رسد. موفقیت لپ‌تاپ DNS یا firewall سرور را ثابت نمی‌کند. پیش از share، token، cookie و header احراز هویت را پاک کن.

Test directly from the same host/namespace Nginx uses. Laptop success proves nothing about server DNS/firewall. Redact tokens, cookies, and authentication headers before sharing.

هر اصلاح یک فرضیه را هدف می‌گیرد؛ بعد همان درخواست را از ابتدا تا انتها اجرا کن. اگر علامت تغییر نکرد، تغییر بی‌اثر را برگردان و سراغ مرز بعدی برو.Each repair targets one hypothesis; then repeat the same end-to-end request. If the symptom remains, revert the ineffective change and move to the next boundary.

تمرین‌ها: از کد خطا تا آزمون بعدیExercises: from status to the next test

در جواب بگو چه مدرکی فرضیه را تقویت می‌کند و بعد از اصلاح چه چیزی را دوباره می‌سنجی.

State what evidence supports your hypothesis and what you will retest after repair.

۱. ۴۰۳ و پوشهٔ خالی1. 403 and an empty directory

GET /docs/ برابر ۴۰۳ است و log می‌گوید directory index ممنوع است. اول چه می‌کنی؟

GET /docs/ returns 403; log says directory index is forbidden. First?

مسیر و index را ببین · Check path and index

root/alias مؤثر و index را بررسی می‌کنم. listing را بی‌فکر روشن نمی‌کنم؛ index موردنظر را می‌سازم و همان URL را تکرار می‌کنم.

I check effective root/alias and index. I do not casually enable listing; I add the intended index and repeat the URL.

۲. status تنها2. Status alone

«هر ۵۰۲ یعنی app خاموش است.» دو شاهدت چیست؟

“Every 502 means the app is down.” What two pieces of evidence?

log و direct curl · Log and direct curl

error log هم‌زمان و curl به مقصد config؛ ss listener را نشان می‌دهد. ۵۰۲ از پاسخ نامعتبر، DNS یا protocol هم می‌آید.

Matching error log and curl to configured target; ss shows listeners. Invalid response, DNS, or protocol can also cause 502.

۳. syntax خراب3. Broken syntax

nginx -t unexpected brace می‌دهد؛ restart؟

nginx -t reports unexpected brace; restart?

نه؛ اول خط گزارش‌شده · No; fix the reported line first

خط را اصلاح و test را تکرار می‌کنم تا موفق شود. restart config نامعتبر را درمان نمی‌کند.

I repair that line and rerun the test until it passes. Restart does not fix invalid config.

۴. DNS دوگانه4. Two DNS views

نام از لپ‌تاپ resolve می‌شود ولی سرور ۵۰۲ می‌دهد. کجا بررسی؟

The name resolves on your laptop but server returns 502. Where check?

از محیط Nginx · From Nginx environment

از همان host/container با getent و curl تست می‌کنم. اگر resolve شد و وصل نشد، listener/firewall را جدا می‌سنجم.

I use getent and curl from that host/container. If resolution works but connection fails, inspect listener/firewall separately.

۵. پورت خاموش5. Closed port

log می‌گوید refused؛ ss proxy را نشان می‌دهد نه upstream. محتمل‌ترین فرضیه؟

Log says refused; ss shows proxy, not upstream. Strongest hypothesis?

upstream listener ندارد · No upstream listener

اپ خاموش یا روی address/port دیگری است. config و وضعیت سرویس را می‌سنجم و port را فقط با مدرک عوض می‌کنم.

The app is stopped or bound elsewhere. I inspect config/service and change the port only with evidence.

۶. deadline کلاینت6. Client deadline

curl --max-time 1 قطع می‌شود ولی proxy timeout شصت ثانیه است؛ Nginx حتماً ۵۰۴ داده؟

Curl times out at 1s but proxy timeout is 60s; did Nginx necessarily return 504?

نه؛ client زودتر تمام شد · No; the client ended first

نه؛ log همان request را بیاب و direct test را با deadline مناسب تکرار کن.

No; find that request in logs and repeat direct test with a suitable deadline.

۷. فایل ۶۴۴، هنوز ۴۰۳7. Mode 644, still 403

stat فایل را ۶۴۴ می‌گوید. چه بررسی بعدی؟

stat shows mode 644. What next?

parentها و user worker · Parents and worker user

namei -l را روی مسیر کامل بزن؛ worker باید از تمام پوشه‌ها عبور کند. بعد root/alias و policy سیستم‌عامل را بررسی کن.

Run namei -l on the full path; worker must traverse all parents. Then check root/alias and OS policy.

۸. فایل config اشتباه8. Wrong config file

ویرایش کردی اما رفتار عوض نشد. nginx -T چه می‌افزاید؟

You edited config but behavior did not change. What does nginx -T add?

includeهای فعال را نشان می‌دهد · Shows active includes

می‌فهمم فایل دیگری load یا directive در context دیگری override شده. خروجی را redact می‌کنم؛ این فرمان upstream را آزمایش نمی‌کند.

It may reveal another file loaded or a directive overridden in another context. Redact output; this does not test upstream.

۹. نام هنگام startup پیدا نیست9. Name missing at startup

nginx -t host not found می‌دهد. قدم نخست؟

nginx -t reports host not found. First step?

resolver همان میزبان · Resolver on that host

با getent از همان namespace نام را بررسی و سپس رفتار resolver را در مستند نسخه می‌سنجم؛ directive کورکورانه DNS را درست نمی‌کند.

I resolve the name from that namespace, then check version docs for resolver behavior; a blind directive cannot fix DNS.

۱۰. port منتظر TLS10. Port expects TLS

port باز است ولی HTTP پاسخ معتبر نمی‌گیرد. چه mismatch؟

Port is open but HTTP gets no valid response. What mismatch?

scheme/protocol · Scheme/protocol

ممکن است backend TLS بخواهد؛ با scheme درست مستقیم تست کن. port باز نوع protocol را ثابت نمی‌کند.

The backend may expect TLS; test directly with the right scheme. An open port does not prove protocol.

۱۱. فقط proxy کند؟11. Only proxy is slow?

direct پاسخ ۰٫۲ثانیه‌ای می‌دهد، proxy ۵۰۴. سه مدرک بعدی؟

Direct responds in 0.2s, proxy gives 504. Three next evidence items?

مقصد، log هم‌زمان، زمان upstream · Target, matching log, upstream timing

proxy_pass مؤثر، error log و timing را بخوان و از میزبان Nginx direct بزن؛ route/network دو آزمون شاید یکی نباشد.

Inspect effective proxy_pass, error log, timings, and curl from Nginx’s host; route/network may differ.

۱۲. process فعال، درخواست خراب12. Active process, broken request

systemctl Active است اما health request fail؛ تناقض؟

systemctl is Active but health request fails; contradiction?
