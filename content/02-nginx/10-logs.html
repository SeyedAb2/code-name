لاگ و آنالیز

Logs and analysis

کاربر می‌گوید «سایت کند است». از کجا بفهمیم؟ access log یک درخواست آهسته ثبت کرده، ولی آیا برنامه کند بوده، کاربر دیر فرستاده یا Nginx دیر پاسخ را تحویل داده؟ این فصل را با پرسیدن سؤال از شاهد ماجرا پیش می‌بریم: log.

A user says, “The site is slow.” How can we tell? The access log records a slow request, but was the app slow, did the client send slowly, or did Nginx take time to deliver the response? We will investigate by questioning the witness: the log.

«کند است» هنوز تشخیص نیست“It is slow” is not a diagnosis yet

در فصل قبل، status و زمان پاسخ را برای rate limit کنار هم گذاشتیم. حالا یک 200 داریم که کاربر می‌گوید هفت ثانیه طول کشیده؛ access log فعلی فقط status و مسیر را نشان می‌دهد. اگر فوراً سراغ upstream برویم، شاید اشتباه را جای دیگری جست‌وجو کنیم.

In the previous chapter, we compared statuses and response times while tuning rate limits. Now we have a 200 that a user says took seven seconds; the current access log shows only status and path. If we blame the upstream immediately, we may investigate the wrong boundary.

دو log اصلی را از هم جدا کنیم. access_log هنگام پایان پردازش هر درخواست اطلاعاتی مثل status، بایت و زمان را می‌نویسد. error_log رویدادها و مشکل‌های خود Nginx را با شدت‌های مختلف ثبت می‌کند؛ تضمین نمی‌کند برای هر پاسخ 4xx یک خط داشته باشیم.

Separate the two main logs. access_log writes per-request information such as status, bytes, and timing when processing ends. error_log records Nginx events and problems at different severities; it does not guarantee one line for every 4xx response.

شدت error_log از debug تا emerg مرتب است؛ وقتی سطحی مثل warn می‌گذاری، warning و شدت‌های بالاتر نوشته می‌شوند. سطح پیش‌فرض error است. debug فقط وقتی build مناسب باشد کار می‌کند و log بسیار پرحجم می‌سازد؛ برای عیب‌یابی محدود و کوتاه نگهش دار.

Nginx error levels range from debug through emerg; setting a level such as warn records warnings and more severe events. The default is error. Debug logging requires a suitable build and can produce a large volume; keep it targeted and brief.

یک عدد زمان، دو مسیر متفاوت را قاطی می‌کندOne timing number mixes two different paths

برای درخواست proxied، Nginx هم از client داده می‌گیرد، هم به upstream وصل می‌شود، هم پاسخ را به client می‌فرستد. $request_time کل عمر درخواست در Nginx را پوشش می‌دهد؛ $upstream_response_time زمان دریافت پاسخ upstream را. اولی را با دومی مقایسه می‌کنیم، نه اینکه یکی را جای دیگری بنشانیم.

For a proxied request, Nginx reads from the client, talks to the upstream, and sends the response back. $request_time covers the request’s lifetime in Nginx; $upstream_response_time measures receiving the upstream response. Compare them—do not substitute one for the other.

فلش‌های رو به راست request و فلش‌های برگشت response هستند. نوار بلند زمان کل از دید Nginx را نشان می‌دهد؛ بازهٔ بنفش فقط مسیر دریافت پاسخ upstream است. تأخیر client می‌تواند اولی را زیاد کند بی‌آنکه دومی بالا برود.

Right-pointing arrows are requests; left-pointing arrows are responses. The long bar is total time as observed by Nginx; the violet interval is only the upstream response. Client delay can raise the first without raising the second.

زمان upstream هم «زمان اجرای CPU برنامه» نیست؛ شامل مرحله‌هایی از ارتباط و دریافت پاسخ است که Nginx اندازه می‌گیرد. اگر چند upstream امتحان شده باشند، مقدارها ممکن است با جداکننده‌های چندگانه بیایند؛ نتیجه را بی‌بررسی به یک عدد تبدیل نکن.

Upstream time is not “app CPU time”; it includes communication and response-receiving phases measured by Nginx. If several upstream attempts occurred, values may appear with separators; do not flatten them into one number without understanding the attempts.

آزمایشگاه: سه پاسخ، سه زمان متفاوتLab: three responses, three different timings

یک برنامهٔ مصنوعی می‌سازیم که مسیر سریع، کند و خطادار دارد و یک POST آزمایشی را هم می‌پذیرد. هیچ فایل مهمی را نمی‌نویسد. برنامه و Nginx روی loopback هستند؛ این آزمایش برای production نیست و فقط به پوشهٔ موقتی که خودمان می‌سازیم دست می‌زند.

We will create a synthetic app with fast, slow, and failing paths plus a test POST. It writes no important files. Both app and Nginx bind to loopback; this is not a production test and touches only a temporary directory we create.

پیش از شروع، پورت‌های 18100 و 19100 را بررسی کن. اگر اشغال‌اند، سرویس موجود را متوقف نکن؛ شمارهٔ آزاد دیگری انتخاب کن و همه‌جا یکسان جایگزینش کن.

Before starting, check ports 18100 and 19100. If they are occupied, do not stop the existing service; choose different free ports and replace them consistently.

نام مسیر متغیر است. آن را در همان shell نگه دار. اگر نمی‌توانی پورت‌ها را بررسی کنی، فرمان اجرای برنامه را نگه دار تا بعداً متوقفش کنی؛ به‌جای حذف یا توقف سرویس ناشناس، پورت دیگری انتخاب کن.

The path varies. Keep it in the same shell. If you cannot inspect ports, keep the process-start command so you can stop it later; choose another port rather than deleting or stopping an unknown service.

برنامهٔ آزمایش به /fast فوری جواب می‌دهد، /slow را حدود ۳۵۰ میلی‌ثانیه نگه می‌دارد و /fail را با 500 پاسخ می‌دهد. مسیر POST فقط تعداد بایت را بازمی‌گرداند؛ payload را ذخیره نمی‌کند.

The test app answers /fast immediately, holds /slow for about 350 milliseconds, and returns 500 for /fail. Its POST path only reports a byte count; it stores no payload.

create a bounded loopback app with visible slow and error paths
cat > "$LOG_LAB/app.py" <<'PY'
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import urlsplit
import sys
import time

port = int(sys.argv[1])

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        path = urlsplit(self.path).path
        if path == "/slow":
            time.sleep(0.35)
        status = 500 if path == "/fail" else 200
        body = f"test path={path}\n".encode()
        self.send_response(status)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def do_POST(self):
        size = int(self.headers.get("Content-Length", "0"))
        self.rfile.read(size)
        body = f"received={size} bytes; not stored\n".encode()
        self.send_response(200)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

ThreadingHTTPServer(("127.0.0.1", port), Handler).serve_forever()
PY

python3 -u "$LOG_LAB/app.py" 19100 > "$LOG_LAB/app.log" 2>&1 &
echo $! > "$LOG_LAB/pids/app.pid"
sleep 0.3

پاسخ مستقیم 500 از خود برنامه می‌آید؛ هنوز Nginx در مسیر نیست. این baseline کمک می‌کند خطایی را که upstream ساخته با خطای proxy اشتباه نگیریم. اگر curl مستقیم نمی‌رسد، app.log و پورت را بررسی کن.

The direct 500 comes from the app; Nginx is not in the path yet. This baseline helps us distinguish an upstream-generated error from a proxy error. If direct curl fails, inspect app.log and the port.

یک access log که به سؤال جواب بدهدAn access log that answers the question

به log موجود چند نشانهٔ هدفمند اضافه می‌کنیم: زمان کل، زمان اتصال به upstream، زمان تا header پاسخ upstream و زمان دریافت پاسخ. کنارشان status، بایت بدنه و کل بایت‌های فرستاده‌شده، referer و user-agent می‌آیند. user-agent و referer را client می‌فرستد؛ این‌ها دادهٔ قابل‌جعل‌اند، نه هویت معتبر.

Add targeted signals to the access log: total time, upstream connect time, time to upstream response headers, and upstream response time. Include status, body bytes and total bytes sent, referer, and user-agent. The client supplies referer and user-agent; they are forgeable data, not authenticated identity.

فرمت را در http تعریف می‌کنیم، بعد آن را با اسمش در access_log انتخاب می‌کنیم. نام variableها را دقیق نگه دار؛ مقدار - یعنی آن نشانه برای درخواست حاضر وجود نداشته، نه صفر ثانیه.

Define the format in http, then select it by name in access_log. Keep variable names exact; a - means the signal was unavailable for that request, not zero seconds.

configure access and error logs under the temporary prefix
cat > "$LOG_LAB/nginx.conf" <<'NGINX'
worker_processes 1;
pid run/nginx.pid;
error_log logs/error.log warn;
events { worker_connections 128; }

http {
    log_format timed
        'ts=$time_iso8601 client=$remote_addr method=$request_method '
        'path=$uri status=$status body_bytes=$body_bytes_sent sent_bytes=$bytes_sent '
        'rt=$request_time connect=$upstream_connect_time '
        'header=$upstream_header_time urt=$upstream_response_time '
        'ustatus=$upstream_status ref="$http_referer" ua="$http_user_agent"';
    access_log logs/access.log timed;

    server {
        listen 127.0.0.1:18100;
        server_name localhost;
        location / {
            proxy_pass http://127.0.0.1:19100;
        }
    }
}

Nginx فقط نحو و فایل‌های تنظیم را بررسی کرده؛ backend و فرمت مفهومی log هنوز با درخواست آزموده نشده‌اند. error_log ... warn یعنی warning و شدت‌های بالاتر را ثبت کن. اگر خطای permission دیدی، پیش از chmod کردن پوشه، مالکیت و کاربری master/worker را بررسی کن.

Nginx has checked config syntax and files only; the backend and the meaning of the log format are not yet tested by a request. error_log ... warn records warnings and more severe events. If permissions fail, inspect directory ownership and the master/worker account before changing modes.

یک عدد بزرگ؛ اما مقصر کیست؟A large number—but who is responsible?

مسیر /slow واقعاً backend کندی داشت؛ پس اگر rt بزرگ باشد، حتماً backend مقصر است؟ نه لزوماً. request_time از وقتی Nginx اولین بایت درخواست را از client می‌گیرد تا وقتی فرستادن پاسخ به client تمام می‌شود اندازه‌گیری می‌شود. برای درخواست proxyشده، upstream_response_time فقط بازهٔ ارتباط با upstream را نشان می‌دهد. بیایید درخواست را عمداً آهسته بفرستیم.

The /slow route really did have a slow backend. So does a large rt always blame the backend? No. request_time spans from Nginx reading the first client-request byte until it finishes sending the response. For a proxied request, upstream_response_time measures the upstream exchange. Let’s deliberately send a request slowly.

bounded slow upload: 32 KiB at about 4 KiB/s
head -c 32768 /dev/zero > "$LOG_LAB/upload.bin"
curl -sS -o /dev/null --limit-rate 4k \
  --data-binary @"$LOG_LAB/upload.bin" \
  http://127.0.0.1:18100/upload
tail -n 1 "$LOG_LAB/logs/access.log"
... path=/upload status=200 ... rt=8.01 ... header=0.001 urt=0.001 ...

این آزمایش محدود است: فقط ۳۲ KiB داده می‌فرستد و چند ثانیه طول می‌کشد. اگر rt نزدیک ۸ ثانیه شد ولی urt نزدیک صفر ماند، زمان عمدتاً صرف رسیدن بدنهٔ درخواست از client شده؛ شواهد فعلی backend را کند نشان نمی‌دهند. تنظیم buffering، اندازهٔ بدنه و شبکه هم روی این رفتار اثر دارند، پس این یک تشخیص برای همین درخواست است، نه حکم کلی دربارهٔ همهٔ مسیرها.

This experiment is bounded: it sends only 32 KiB and takes a few seconds. If rt is near eight seconds while urt stays near zero, most of the time was spent receiving the body from the client; the current evidence does not show a slow backend. Buffering, body size, and the network also affect this behavior, so this diagnoses this request—not every route.

اگر فقط یک عدد را به تیم نشان بدهی و بگویی «backend هشت ثانیه طول کشید»، گزارش گمراه‌کننده است. زمان کل درخواست و زمان upstream را کنار هم بخوان؛ هیچ‌کدام به‌تنهایی زمان CPU برنامه را ثابت نمی‌کنند.Showing one number and saying “the backend took eight seconds” would be misleading. Read total request time beside upstream time; neither one proves application CPU time by itself.

پیدا کردن کندترین مسیر، نه طولانی‌ترین خطFind the slowest route, not the longest log line

لاگ ما فیلدها را به شکل key=value نوشته. با یک فیلتر کوچک می‌توانیم زمان upstream را از مسیر جدا کنیم. این نمونه فقط مقدار عددی urt را رتبه‌بندی می‌کند؛ درخواست بدون upstream یا با چند تلاش ممکن است مقدار متفاوتی داشته باشد و باید جداگانه بررسی شود.

Our log writes fields as key=value. A small filter can pair upstream time with the route. This ranks only numeric urt values; requests without an upstream or with multiple attempts may have different values and deserve separate inspection.

rank observed upstream response times
awk '{
  path="?"; time="-";
  for (i=1; i<=NF; i++) {
    if ($i ~ /^path=/) path=$i;
    if ($i ~ /^urt=/) time=$i;
  }
  if (time ~ /^urt=[0-9.]+$/) {
    sub(/^path=/, "", path); sub(/^urt=/, "", time);
    print time, path
  }
}' "$LOG_LAB/logs/access.log" | sort -nr | head
0.351 /slow
0.001 /upload
0.001 /fail
0.001 /fast

عدد اول در هر ردیف زمان بزرگ‌تر به کوچک‌تر است؛ این نمونه می‌گوید در دادهٔ آزمایش، /slow کندترین پاسخ upstream بوده. این روش ساده فرض می‌کند مقدار زمان یک عدد است و فیلد مسیر با فاصله شکسته نمی‌شود؛ برای log format پیچیده یا JSON از parser متناسب استفاده کن. چند بار نمونه‌گیری هم از یک درخواست منفرد قابل‌اعتمادتر است.

The first column is sorted from largest to smallest; in this sample, /slow had the slowest upstream response. This simple filter assumes a numeric time and a path without whitespace. Use a parser suited to a more complex format or JSON, and prefer repeated samples over one request.

زنده دیدن لاگ و محدود کردن دامنهWatch logs live and narrow their scope

برای دیدن خط‌های تازه، tail -f فایل بازشده را دنبال می‌کند. هنگام چرخش فایل، ممکن است همان فایل قدیمی را دنبال کند. tail -F نام فایل را دوباره بازبینی می‌کند و بعد از جابه‌جایی فایل معمولاً انتخاب مناسب‌تری است. اول چند خط آخر را ببین تا موج تازه را با تاریخچهٔ قدیمی قاطی نکنی.

Use tail -f to watch new lines in an open file. During rotation it may keep following the old file. tail -F retries by name and is often a better fit after a rename. Start with a few existing lines so old history does not blur the new signal.

follow only the disposable lab's access log
tail -n 5 "$LOG_LAB/logs/access.log"
tail -F "$LOG_LAB/logs/access.log"

اگر Nginx را به‌صورت service نصب کرده‌ای، ممکن است بخشی از خطاها در فایل تعریف‌شده یا در system journal باشند؛ نام unit و مسیر log بین توزیع‌ها فرق می‌کند. تنظیم واقعی را با nginx -T ببین و برای journal، unit موجود را با systemctl status پیدا کن؛ حدس نزن که همه‌جا یک مسیر ثابت دارد.

With a packaged Nginx service, errors may go to a configured file or the system journal; unit names and paths vary by distribution. Inspect effective configuration with nginx -T, and identify the installed unit with systemctl status rather than assuming one universal path.

لاگ را می‌توانی در http برای حالت عمومی، در server برای یک virtual server، یا در location برای مسیر خاص تنظیم کنی. اگر سطح پایین‌تر تعریف داشته باشد، تنظیم قبلی را به ارث نمی‌برد؛ برای نوشتن در هر دو مقصد، هر دو را در همان سطح پایین‌تر بنویس.

You can configure logs in http for the general case, in server for one virtual server, or in location for one path. A lower-level definition does not inherit the prior access-log setting; declare both destinations at the lower level if you need both.

لاگ جدا پیدا کردن سیگنال را آسان می‌کند، اما فایل و حجم بیشتری می‌سازد و ممکن است دادهٔ حساس ثبت کند. برای همیشه همهٔ headerها، query stringها یا اطلاعات شخصی را لاگ نکن؛ فقط چیزی را ثبت کن که برای عیب‌یابی لازم است و دسترسی و نگهداری‌اش را مشخص کن.

A separate log makes a signal easier to find, but creates more files and volume and may capture sensitive data. Do not log every header, query string, or personal detail by default; record what troubleshooting needs and define access and retention.

لاگ باید جا داشته باشد؛ دیسک نامحدود نیستLogs need room; disks are not infinite

در آزمایش کوچک، فایل دست‌نخورده می‌ماند؛ روی سرور واقعی، access log می‌تواند هر روز بزرگ‌تر شود. اگر فایل را فقط rename کنی، Nginx ممکن است همچنان روی file descriptor قدیمی بنویسد. الگوی رایج این است: فایل را جابه‌جا کن، فایل تازه بساز، بعد به master بگو فایل‌های log را دوباره باز کند.

Our tiny lab leaves its file alone; on a real server, access logs can grow every day. If you only rename a file, Nginx may keep writing through its old file descriptor. A common sequence is: move the file, create a new one, then ask the master to reopen log files.

rotate only the disposable lab log, then reopen it
mv "$LOG_LAB/logs/access.log" "$LOG_LAB/logs/access.log.1"
: > "$LOG_LAB/logs/access.log"
nginx -s reopen -p "$LOG_LAB/" -c nginx.conf
curl -sS -o /dev/null http://127.0.0.1:18100/fast
wc -l "$LOG_LAB/logs/access.log" "$LOG_LAB/logs/access.log.1"
1 .../access.log
4 .../access.log.1

پس از درخواست تازه، خط باید در فایل جدید دیده شود؛ خط‌های قبلی در فایل چرخانده‌شده می‌مانند. اگر فایل تازه خالی ماند، اول خروجی reopen و error.log را بخوان. این فرمان برای Nginx همین آزمایش است؛ روی سرویس زنده، rotation را با ابزار و سیاست همان میزبان هماهنگ کن.

After the new request, its line should appear in the new file; earlier lines remain in the rotated file. If the new file stays empty, inspect the reopen result and error.log first. This command targets our lab Nginx; coordinate live rotation with the host’s own tooling and policy.

در بسیاری از Linuxها logrotate و timer یا cron چرخش را زمان‌بندی می‌کنند، اما نصب و زمان‌بندی در همهٔ توزیع‌ها یکسان نیست. برای دیدن timerهای همین میزبان، این بررسی فقط اطلاعات می‌خواند:

Many Linux systems use logrotate with a timer or cron, but installation and scheduling vary by distribution. This read-only check lists timers on this host:

discover the local rotation schedule before changing it
systemctl list-timers --all | grep -i logrotate || true
logrotate -d /etc/logrotate.conf
... debug mode: configuration read; no files are rotated ...

حالت -d برای بررسی پیکربندی است؛ به‌جای آزمایش روی فایل‌های سیستم از آن استفاده کن. روش rename و reopen معمولاً از copytruncate روشن‌تر است؛ copytruncate بین کپی و کوتاه‌کردن فایل فاصله‌ای دارد که ممکن است چند خط از دست بروند. جزئیات بسته و hookهای سرویس را پیش از تغییر سیاست واقعی بخوان.

The -d mode inspects configuration; use it instead of experimenting on system logs. Rename-and-reopen is generally clearer than copytruncate, which has a window between copying and truncating in which lines can be lost. Read the package and service hooks before changing a live policy.

اگر log ناپدید یا خالی شد، permission و فضای همان filesystem را هم بررسی کن. df -h بلوک‌های آزاد و df -i inodeهای آزاد را نشان می‌دهد؛ هر دو می‌توانند مانع ساخت فایل شوند. برای permission، مالکیت پوشهٔ والد و کاربر worker مهم است؛ chmod 777 درمان مناسبی نیست.

If a log disappears or stays empty, inspect permissions and the filesystem’s free space too. df -h shows free blocks; df -i shows free inodes. Either can prevent file creation. For permissions, inspect the parent directory and worker identity; chmod 777 is not a sound repair.

read-only checks for path permissions and both kinds of capacity
namei -l "$LOG_LAB/logs/access.log"
df -h "$LOG_LAB"
df -i "$LOG_LAB"
... drwx------ ... nginx-logs.xxxxxx
... drwxr-xr-x ... logs
... -rw-r--r-- ... access.log
Filesystem  Size Used Avail Use% Mounted on
...          ...  ...  ...   ...  ...

اگر بلوک خالی هست اما inodeها ۱۰۰٪ مصرف شده‌اند، فایل تازه ساخته نمی‌شود. اگر مسیر یکی از پوشه‌های والد اجازهٔ عبور برای worker نداشته باشد، وجود خود فایل هم کمکی نمی‌کند. خروجی واقعی را با user/group پردازش worker مقایسه کن؛ روی محیط تولید، مالکیت را طبق ساختار همان بسته و سرویس تنظیم کن.

If blocks remain but inodes are exhausted, a new file still cannot be created. If a parent directory lacks traversal permission for the worker, the file’s own mode does not help. Compare actual ownership with the worker’s user/group; on production, follow that package and service’s ownership model.

JSON مفید است، اگر واقعاً JSON بماندJSON helps only if it remains valid JSON

وقتی ابزار تحلیل باید فیلدها را جدا بخواند، قالب ساخت‌یافته کمک می‌کند. نسخه‌های امروزی Nginx در log_format امکان escape=json دارند؛ اگر روی نسخهٔ قدیمی‌تری هستی، قبل از کپی تنظیم با nginx -v و مستندات همان نسخه سازگاری را بررسی کن. متغیرهایی مثل user-agent ممکن است نقل‌قول یا نویسهٔ کنترلی داشته باشند، پس escape را حذف نکن.

Structured output helps when an analysis tool needs separate fields. Current Nginx versions support escape=json in log_format; on an older version, check nginx -v and that version’s documentation before copying the directive. Values such as user-agent may contain quotes or control characters, so do not remove escaping.

an escaped JSON access format
log_format json_access escape=json
    '{"time":"$time_iso8601","remote":"$remote_addr",'
    '"request":"$request","status":"$status",'
    '"bytes":"$body_bytes_sent","request_time":"$request_time",'
    '"upstream_time":"$upstream_response_time",'
    '"referer":"$http_referer","user_agent":"$http_user_agent"}';
access_log logs/access.jsonl json_access;

مقادیر متغیرها را رشته گذاشتیم؛ برای نمونه بعضی زمان‌ها می‌توانند - باشند، که عدد JSON نیست. پس از ساخت یک خط، اگر jq نصب است، اعتبارش را بررسی کن. نبودن jq به معنی خراب بودن Nginx نیست؛ فقط این ابزار بررسی در دسترس نیست.

We encoded variable values as strings; some timing fields can be -, which is not a JSON number. Validate a produced line with jq if installed. Missing jq does not mean Nginx is broken; only this validation tool is unavailable.

validate one emitted line, if jq is available
tail -n 1 "$LOG_LAB/logs/access.jsonl" | jq -e .
{
  "time": "...",
  "status": "200",
  "request_time": "0.002"
}

خروجی ساخت‌یافته، درستی معنای داده را تضمین نمی‌کند: user-agent و referer از client می‌آیند و می‌توانند جعلی باشند. همچنین IP و URL ممکن است دادهٔ حساس داشته باشند. دسترسی، مدت نگهداری و نیاز واقعی به هر فیلد را مشخص کن. JSON را بهانه‌ای برای ثبت بی‌حد اطلاعات نکن.

Structured syntax does not make data truthful: user-agent and referer come from the client and can be forged. IPs and URLs may also contain sensitive data. Define access, retention, and a reason for every field; JSON is not a reason to log everything.

تمرین؛ شاهد را از حدس جدا کنExercises: separate evidence from guesses

در هر تمرین، قبل از تعمیر بگو کدام شاهد بین دو احتمال فرق می‌گذارد. بعضی سؤال‌ها چند پاسخ قابل‌قبول دارند؛ مهم این است که نتیجه از داده جلوتر نرود.

Before proposing a fix, identify which evidence distinguishes the competing explanations. Some prompts allow more than one reasonable answer; the important thing is not to claim more than the data supports.

۱. کدام log؟Which log?

client پاسخ 404 می‌گیرد و error log خط تازه‌ای ندارد. اولین جا برای بررسی چیست؟

A client receives 404, but the error log has no new line. Where do you look first?

پاسخ و دلیلAnswer and reasoning

Access log را ببین؛ پاسخ HTTP معتبر، حتی 404، معمولاً در access log ثبت می‌شود. نبود خط در error log ثابت نمی‌کند که درخواست به Nginx نرسیده.

Check the access log: a valid HTTP response, including 404, is normally an access event. No error-log line does not prove the request never reached Nginx.

۲. سطح هشدارSeverity level

با error_log ... warn چه سطح‌هایی ثبت می‌شوند؟

With error_log ... warn, which severities are recorded?

پاسخAnswer

هشدار و شدت‌های بالاتر، مثل error و crit. تغییر به debug فقط برای دیدن همه‌چیز راه‌حل بی‌هزینه نیست؛ build مناسب و کنترل حجم لازم است.

Warnings and more severe levels such as error and crit. Switching to debug is not a free way to see everything; it requires a suitable build and volume control.

۳. پاسخ موفق، زمان مشکوکSuccessful response, suspicious timing

یک خط می‌گوید status=200 rt=0.8 urt=0.79. زمان بیشتر کجا گذشته؟ چه چیزی هنوز معلوم نیست؟

A line says status=200 rt=0.8 urt=0.79. Where was most time spent, and what remains unknown?

تفسیرInterpretation

تقریباً بیشتر بازه داخل upstream بوده. این به‌تنهایی نمی‌گوید برنامه CPU مصرف کرده، منتظر DB بوده یا شبکهٔ upstream کند بوده؛ لاگ خود برنامه و dependency را هم لازم داریم.

Most of the interval was inside the upstream exchange. This alone cannot tell whether the app used CPU, waited on a database, or encountered network delay; application and dependency logs are also needed.

۴. بدنهٔ کندA slow request body

برای آپلود، rt=8.0 و urt=0.01 می‌بینی. آیا backend هشت ثانیه مشغول بوده؟

For an upload you see rt=8.0 and urt=0.01. Was the backend busy for eight seconds?

پاسخAnswer

این شواهد چنین چیزی را نشان نمی‌دهد؛ بیشتر زمان بیرون از upstream گذشت. زمان ارسال body، پاسخ‌دهی client و جزئیات buffering را بررسی کن.

The evidence does not show that; most time was outside the upstream interval. Investigate client body transfer, response delivery, and buffering details.

۵. ترتیب کندترین‌هاRank the slowest

از 0.03، 0.7 و 0.2 کدام پاسخ upstream کندتر است؟ چرا sort الفبایی خطرناک است؟

Which upstream response is slowest: 0.03, 0.7, or 0.2? Why can lexical sorting mislead?

پاسخAnswer

0.7؛ مرتب‌سازی متنی می‌تواند مقدارهای اعشاری را طبق نویسه‌ها مرتب کند نه عدد. از sort عددی مثل sort -nr استفاده کن و ورودی را هم بررسی کن.

0.7. Text sorting can order decimal strings lexically instead of numerically. Use numeric sorting such as sort -nr and inspect the input too.

۶. backend اصلاً پاسخ ندادهThe upstream never replied

access log وضعیت 502 دارد و ustatus=-. چه نتیجه‌ای می‌گیری؟

The access log shows 502 and ustatus=-. What can you conclude?

تفسیرInterpretation

این خط پاسخ HTTP upstream را نشان نمی‌دهد؛ برای علت دقیق error log و خطای اتصال/timeout را بخوان. هنوز نمی‌دانیم backend خاموش، آدرس اشتباه یا شبکه مسدود بوده.

This line shows no upstream HTTP status. Read the error log for connection or timeout details. We do not yet know whether the backend was down, misaddressed, or blocked by networking.

۷. چرا 404 در error log نیست؟Why is a 404 absent from error.log?

آیا باید سطح error log را debug کنی تا همهٔ 404ها ثبت شوند؟

Should you enable debug error logging to capture every 404?

پاسخAnswer

نه؛ access log برای درخواست و status آن است. error log برای خطاهای عملیاتی Nginx است. debug ممکن است بسیار پرحجم شود و برای یک پاسخ عادی ابزار مناسبی نیست.

No. The access log records requests and their status; the error log records Nginx operational errors. Debug can be very noisy and is not the right tool for an ordinary response.

۸. لاگ زنده بعد از rotationFollowing a log after rotation

بعد از rename، tail -f خط‌های فایل تازه را نشان نمی‌دهد. چه گزینه‌ای را امتحان می‌کنی؟

After a rename, tail -f does not show lines from the new file. What do you try?

پاسخAnswer

tail -F نام را دوباره دنبال می‌کند. ولی اول مطمئن شو Nginx هم فایل log را reopen کرده و درخواست جدید در فایل تازه نوشته شده.

tail -F follows the name again. Also verify that Nginx reopened its log and that a new request was written to the new file.

۹. فرمت ناقصAn incomplete format

تیم می‌خواهد «کندترین route» را پیدا کند. چه فیلدهایی را کنار هم نگه می‌داری؟

A team wants to find the slowest route. Which fields do you keep together?

پاسخ پیشنهادیSuggested answer

route یا request، status، زمان کل، upstream time و در صورت proxy چند upstream timing/status. زمان، واحد/فرمت و امکان مقدار - را هم مستند کن؛ اگر فیلد مسیر را حذف کنی، زمان به درخواست مشخصی وصل نمی‌شود.

Keep route or request, status, total time, upstream time, and—when proxying—upstream timing/status. Document formatting and possible - values; without a route field, a duration cannot be tied to a request.

۱۰. یک log یا دو تا؟One log or two?

فقط /checkout را موقتاً جدا می‌کنی. چه نکته‌ای دربارهٔ ارث‌بری باید بررسی شود؟

You temporarily separate only /checkout. What inheritance detail must you check?

پاسخAnswer

تعریف access_log در location، تنظیم بالاتر را به ارث نمی‌برد. اگر هم access log عمومی و هم checkout log را می‌خواهی، هر دو مقصد را داخل همان location تعریف کن؛ بعد حجم و نگهداری را بازبینی کن.

An access_log at location scope does not inherit the higher-level setting. Declare both destinations in that location if you need the general and checkout logs, then review volume and retention.

۱۱. خط در فایل نیستThe line is missing

Nginx بالا است ولی فایل جدید ساخته نشده. دو بررسی امن را نام ببر.

Nginx is running but the new file was not created. Name two safe checks.

پاسخAnswer

error log را برای open() ... failed بخوان و مالکیت/اجازهٔ پوشهٔ والد و worker را بررسی کن؛ سپس df -h و df -i را برای filesystem مقصد ببین. هنوز سراغ chmod عمومی نرو.

Look for open() ... failed in the error log and inspect parent-directory permissions and worker identity; then check df -h and df -i for the target filesystem. Do not start with broad chmod.

۱۲. بستن سریع مشکل دیسک؟A quick disk-space fix?

فایل access log بزرگ شده. حذفش می‌کنی؟ قبلش چه چیزی را می‌سنجی؟

The access log grew large. Would you delete it? What do you check first?

پاسخAnswer

نه بی‌تشخیص. اندازه و روند رشد، فضای بلوک و inode، سیاست rotation و نیاز نگهداری را بررسی کن. حذف فایل باز ممکن است فضا را هم آزاد نکند تا descriptor بسته شود و شواهد حادثه را از بین می‌برد.

Not without diagnosis. Check size and growth, blocks and inodes, rotation policy, and retention needs. Deleting an open file may not free space until its descriptor closes, and it destroys incident evidence.

۱۳. کاربر عجیب در JSONA strange value in JSON

یک user-agent نقل‌قول دارد و JSON خط نامعتبر شده. چه چیزی را بررسی می‌کنی؟

A user-agent contains quotes and the JSON line is invalid. What do you inspect?

پاسخAnswer

مطمئن شو log_format ... escape=json فعال است و خط واقعی را با parser بررسی کن. قالب دستی بدون escaping می‌شکند؛ user-agent را هم ورودی قابل‌اعتماد فرض نکن.

Ensure log_format ... escape=json is enabled and validate the actual line with a parser. Hand-built formatting without escaping breaks; do not trust user-agent as authoritative data.

۱۴. چرخش بدون reopenRotation without reopen

فایل تازه وجود دارد اما خط‌ها در فایل .1 اضافه می‌شوند. محتمل‌ترین بخش جاافتاده چیست؟

The new file exists, but lines keep appearing in .1. What step was likely missed?

پاسخAnswer

Nginx هنوز descriptor قدیمی را نگه داشته؛ پس از rename و ساخت فایل تازه، master باید logها را reopen کند، مثلاً با nginx -s reopen در context درست یا hook بستهٔ سیستم.

Nginx still holds the old descriptor. After rename and file creation, the master must reopen logs—for example with nginx -s reopen in the correct context or the system package’s hook.

۱۵. زمان چند upstreamMultiple upstream timings

مقدار urt شامل چند عدد جداشده با ویرگول است. آن را یک عدد اعشاری حساب می‌کنی؟

The urt value contains comma-separated timings. Treat it as one decimal?

تفسیرInterpretation

نه؛ چند تلاش یا گروه upstream می‌تواند چند مقدار بسازد. مقدار خام، statusهای upstream و error log را کنار هم بخوان تا retry یا چند مرحله را ببینی؛ فیلتر عددی سادهٔ ما برای این مورد کافی نیست.

No. Retries or upstream groups can produce multiple values. Read the raw value with upstream statuses and the error log to identify retries or stages; our simple numeric filter is not sufficient here.

۱۶. debug را روشن کنیم؟Should we enable debug?

مشکل فقط یک درخواست نادر است. آیا debug دائمی انتخاب خوبی است؟

The issue affects a rare request. Is permanent debug logging a good choice?

پاسخAnswer

معمولاً نه: حجم و دادهٔ حساس ممکن است زیاد شود و build هم باید از debug پشتیبانی کند. ابتدا access/error log فعلی و یک بازهٔ محدود را بررسی کن؛ اگر debug لازم شد، دامنه و زمانش را محدود و بعد خاموش کن.

Usually not: volume and sensitive data can increase, and the build must support debug. Start with existing access/error logs and a narrow time window; if debug is necessary, constrain its scope and duration, then turn it off.

۱۷. referer حقیقت قطعی است؟Is the referer definitive truth?

گزارش بر اساس referer می‌گوید همهٔ درخواست‌ها از یک سایت خاص آمده‌اند. چه احتیاطی لازم است؟

A report based on referer says every request came from one site. What caution applies?

پاسخAnswer

referer را client می‌فرستد؛ ممکن است خالی، حذف‌شده یا جعل شود. برای تحلیل سرنخ است، نه مرز اعتماد یا اثبات هویت. اطلاعات را حداقلی نگه دار.

Referer is client-provided; it can be absent, stripped, or forged. It is a clue for analysis, not an identity proof or trust boundary. Keep collection minimal.

۱۸. گزارش رخدادIncident summary

مسیر /slow برای مشتری کند است؛ یک access line چه فیلدهایی باید داشته باشد تا بررسی اول را ممکن کند؟ محدودیت نتیجه‌گیری را هم بنویس.

Customers report that /slow is slow. Which fields should one access line include for an initial investigation? State the limit of the conclusion too.

یک پاسخ معقولOne reasonable answer

زمان، method/path، status، request_time، upstream timing/status و زمان‌بندی دریافت/ارسال اگر مسئله آپلود یا پاسخ بزرگ است. چند درخواست را مقایسه و error/app log را هم بررسی می‌کنم. access log به‌تنهایی علت داخل برنامه، DB یا تجربهٔ واقعی همهٔ clientها را اثبات نمی‌کند.

Include time, method/path, status, request_time, upstream timing/status, and transfer details if uploads or large responses are involved. Compare multiple requests and inspect error/application logs too. An access log alone cannot prove an internal app or database cause, or represent every client’s experience.

ماموریت: کندترین مسیر را با شاهد پیدا کنMission: find the slowest route with evidence

تیم پشتیبانی می‌گوید «سرور کند شده»، اما نمی‌داند پاسخ از Nginx دیر شده یا برنامه. با همین محیط جدا، گزارشی بنویس که یک همکار بتواند نتیجه‌اش را بازبینی کند: درخواست، زمان کل، upstream، status و محدودیت تشخیص.

Support says “the server got slow,” but cannot tell whether the delay is in Nginx or the application. Use this isolated environment to write a reviewable report: request, total time, upstream, status, and diagnostic limits.

  1. یک بار هر سه مسیر /fast، /slow و /fail را درخواست کن.
  2. کندترین upstream را از روی دادهٔ واقعی پیدا کن؛ خط آپلود آهسته را هم جدا نگه دار.
  3. یک خطای permission بساز فقط در فایل/پوشهٔ آزمایش، بعد error log را بخوان و مالکیت را اصلاح کن.
  4. خط‌ها را به فایل پشتیبان منتقل کن، فایل تازه بساز و با nginx -s reopen ادامهٔ ثبت را ثابت کن.
  5. گزارش کوتاه بنویس: چه دیدی، چه چیزی محتمل است، چه چیزی هنوز ثابت نشده، و قدم بعدی چیست.
  1. Request /fast, /slow, and /fail once each.
  2. Find the slowest upstream from actual data; keep the slow-upload line separate.
  3. Create a permissions failure only inside the lab’s file/directory, read the error log, then repair ownership.
  4. Move the lines to a rotated file, create a fresh file, and prove logging continues with nginx -s reopen.
  5. Write a short report: what you observed, what is likely, what is unproven, and the next check.
راهنمایی؛ اول خطی را پیدا کن که بین دو علت فرق می‌گذاردHint: first find the line that distinguishes two causes

rt و urt را کنار هم بخوان. برای permission، error log از access log کمک‌کننده‌تر است. بعد از rotation یک درخواست تازه بساز؛ وجود فایل به‌تنهایی ثابت نمی‌کند Nginx در آن می‌نویسد.

Read rt beside urt. For permissions, the error log is more useful than the access log. After rotation, make a fresh request; a file’s existence alone does not prove Nginx is writing to it.

راه‌حل نمونه؛ گزارش را از چیزی که خط‌ها ثابت می‌کنند جلوتر نبرSample resolution: do not claim more than the lines prove

در خروجی نمونه، /slow هم rt و هم urt نزدیک ۰٫۳۵ دارد؛ در همان محیط، تأخیر upstream با مسیر کند سازگار است. آپلود محدود rt حدود ۸ ثانیه اما urt نزدیک ۰٫۰۰۱ دارد؛ پس کندی عمدتاً در بازهٔ client/Nginx بوده. برای 500، مقدار ustatus=500 می‌گوید upstream پاسخ خطا داده. هیچ‌کدام به‌تنهایی علت درونی برنامه را مشخص نمی‌کند. بعد از rotation، یک درخواست تازه و خطش در فایل جدید، شاهد reopen موفق است.

In the sample, /slow has both rt and urt near 0.35, consistent with upstream delay in this environment. The bounded upload has roughly eight seconds of rt but near 0.001 urt, so most delay was in the client/Nginx interval. For the 500, ustatus=500 shows the upstream returned an error. None identifies the application’s internal cause by itself. A new request appearing in the fresh file after rotation is evidence of a successful reopen.

جمع‌کردن آزمایش، بدون دست‌زدن به سرویس دیگرClean up without touching another service

پیش از پایان، لاگ‌ها را برای گزارش نگه دار؛ بعد فقط Nginx همین prefix را متوقف کن. اگر PID برنامه به مسیر اسکریپت همین پوشه اشاره نمی‌کند، آن را نکش. این بررسی جلوی اشتباه گرفتن PID آزمایش با یک برنامهٔ دیگر را می‌گیرد.

Keep the logs until you have the evidence for your report, then stop only the Nginx instance using this prefix. Do not kill the app PID unless its command points to the script in this exact lab directory; this prevents confusing it with another process.

verify process identity before stopping, then inspect the exact temp path
nginx -s quit -p "$LOG_LAB/" -c nginx.conf || true
MASTER_PID_FILE="$LOG_LAB/run/nginx.pid"
for _ in $(seq 1 50); do
  [ -s "$MASTER_PID_FILE" ] || break
  MASTER_PID=$(cat "$MASTER_PID_FILE")
  kill -0 "$MASTER_PID" 2>/dev/null || break
  sleep 0.1
done
APP_PID=$(cat "$LOG_LAB/pids/app.pid")
APP_ARGS=$(ps -p "$APP_PID" -o args= 2>/dev/null || true)
case "$APP_ARGS" in
  *"$LOG_LAB/app.py"*) kill "$APP_PID" ;;
  *) echo "App PID does not match this lab; leaving it untouched." ;;
esac
if [ -s "$MASTER_PID_FILE" ] && kill -0 "$(cat "$MASTER_PID_FILE")" 2>/dev/null; then
  echo 'Nginx has not exited; keep the lab directory and inspect it.'
elif [ -n "$APP_ARGS" ] && kill -0 "$APP_PID" 2>/dev/null; then
  echo 'App is still running; keep the lab directory and inspect it.'
else
case "$LOG_LAB" in
  /tmp/nginx-logs.*)
    printf 'Lab directory to remove: %s\n' "$LOG_LAB"
    read -r -p 'Type REMOVE to delete this lab directory: ' CONFIRM
    [ "$CONFIRM" = REMOVE ] && rm -rf -- "$LOG_LAB"
    ;;
  *) echo 'Unexpected path; not removing anything.' ;;
esac
fi

اگر برنامه یا Nginx هنوز زنده است، پیش از حذف پوشه دلیلش را پیدا کن؛ پوشهٔ log را وقتی descriptor باز است پاک نکن. اگر خواستی خروجی را نگه داری، فقط همین مسیر آزمایش را حذف نکن و فایل‌ها را در محل امن خودت کپی کن. هیچ‌کدام از فرمان‌ها مجوز پاک‌کردن logهای واقعی سیستم را نمی‌دهند.

If the app or Nginx is still alive, understand why before removing the directory; do not delete log files while descriptors are open. To retain evidence, keep this lab directory or copy its files to a safe location. None of these commands authorizes deleting real system logs.

حالا می‌توانیم از روی log بفهمیم درخواست کجا زمان برد و Nginx چه پاسخی ثبت کرد. اما بعضی اتصال‌ها مثل یک درخواست کوتاه تمام نمی‌شوند؛ WebSocket پس از handshake باز می‌ماند، و آپلود حجیم هم رفتار زمانی و اندازهٔ خودش را دارد. فصل بعد می‌رویم سراغ همین مرزها، بدون اینکه هر اتصال طولانی را با یک عدد لاگ ساده قضاوت کنیم.

We can now use logs to see where a request spent time and what response Nginx recorded. But some connections do not end like a short request: a WebSocket stays open after its handshake, and a large upload has its own timing and size behavior. Next we’ll examine those boundaries without judging every long-lived connection by one simple log number.
