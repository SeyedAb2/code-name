Load balancing and upstreams

حالا که برنامه پشت Nginx است، یک نمونهٔ دیگر هم بالا آورده‌ای. هر دو سالم‌اند؛ اما درخواست بعدی باید به کدام برسد؟ اگر یکی از کار بیفتد، Nginx از کجا می‌فهمد؟ با سه برنامهٔ کوچک جواب را از روی درخواست‌های واقعی پیدا می‌کنیم.

Now that the app sits behind Nginx, you have brought up another instance. Both are healthy—but where should the next request go? If one fails, how would Nginx know? We will answer by watching real requests reach three tiny apps.

سه برنامه، یک نشانی برای کاربرThree apps, one address for the client

در فصل قبل دیدیم Nginx درخواست را می‌گیرد و خودش به برنامه وصل می‌شود. حالا سه نمونه از همان برنامه داریم؛ هرکدام روی پورت خودش. اگر کاربر مجبور شود نشانی هر سه را بداند، چیزی حل نکرده‌ایم. او یک نشانی می‌خواهد و Nginx باید یکی از مقصدها را انتخاب کند.

In the previous chapter, Nginx accepted a request and opened its own connection to an app. Now we have three instances of that app, each on its own port. If clients must know all three addresses, we have not solved the problem. They need one address; Nginx must choose a destination.

هر فلش آبی یک مسیر ممکن برای یک درخواست است؛ سه فلش یعنی سه مقصد ممکن، نه اینکه درخواست در هر سه کپی شود. پاسخ از مقصد انتخاب‌شده به Nginx و سپس client برمی‌گردد.

Each blue arrow is a possible route for a request; three arrows mean three destinations, not that a request is copied to all of them. The response returns through Nginx to the client.

این گروه مقصدها در Nginx اسم دارد: upstream. بعد در proxy_pass به همان اسم اشاره می‌کنیم. انتخاب مقصد برای هر درخواست انجام می‌شود؛ قرار نیست کاربر مستقیم به پورت داخلی برنامه وصل شود.

Nginx gives this group of destinations a name: an upstream. We refer to that name in proxy_pass. Nginx selects a destination per request; clients do not connect directly to the apps’ internal ports.

قبل از انتخاب الگوریتم، مقصد را قابل‌شناسایی کنMake each destination identifiable first

اگر هر سه برنامه پاسخ یکسان بدهند، نمی‌فهمیم کدام جواب داده. برنامهٔ آزمایش نام نمونه‌اش را برمی‌گرداند. مسیر /slow هم کمی مکث می‌کند تا فرق تعداد درخواست و اتصال فعال را ببینیم.

If all three apps return the same response, we cannot tell which one answered. Our test app returns its instance name. The /slow path waits briefly so we can distinguish request counts from active connections.

آزمایشگاه در پوشه‌ای موقت و روی loopback می‌ماند: برنامه‌ها روی 19091 تا 19093 و Nginx روی 18084. پیش از اجرا پورت‌ها را بررسی کن؛ اگر اشغال‌اند، آزمایش را روی آن‌ها اجرا نکن و شمارهٔ آزاد را در همه‌جا یکسان جایگزین کن.

Keep the lab in a temporary directory on loopback: apps on 19091 through 19093, and Nginx on 18084. Check the ports first; if occupied, do not use them and replace them consistently with free ports.

from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import urlsplit
import sys
import time

name, port = sys.argv[1], int(sys.argv[2])

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        path = urlsplit(self.path).path
        if path.endswith('/slow'):
            time.sleep(1.5)
        body = f"instance={name} path={self.path} peer={self.client_address[0]}\n".encode()
        print(body.decode().strip(), flush=True)
        self.send_response(200)
        self.send_header('Content-Type', 'text/plain; charset=utf-8')
        self.send_header('Content-Length', str(len(body)))
        self.end_headers()
        self.wfile.write(body)

ThreadingHTTPServer(('127.0.0.1', port), Handler).serve_forever()

If one does not answer, inspect that instance’s log and port, not the algorithm. Nginx cannot make an app that is not listening healthy.

اولین انتخاب: نوبتی، با وزن برابرFirst choice: rotate across equal peers

سه مقصد مستقیم جواب می‌دهند. اگر Nginx دلیل دیگری نداشته باشد، درخواست را چطور پخش می‌کند؟ روش پیش‌فرض گروه upstream، weighted round-robin است؛ چون وزن‌ها برابرند، نتیجه شبیه نوبتی برابر می‌شود.

All three destinations answer directly. With no other signal, how will Nginx distribute requests? The default upstream method is weighted round-robin; with equal weights, it looks like an even rotation.

configure one listener and one named group
cat > "$LAB_DIR/nginx.conf" <<'NGINX'
worker_processes 1;
pid logs/nginx.pid;
error_log logs/error.log notice;
events { worker_connections 128; }

http {
    log_format upstream '$request status=$status peer=$upstream_addr time=$upstream_response_time';
    access_log logs/access.log upstream;
    upstream demo_round_robin {
        server 127.0.0.1:19091 max_fails=1 fail_timeout=8s;
        server 127.0.0.1:19092 max_fails=1 fail_timeout=8s;
        server 127.0.0.1:19093 max_fails=1 fail_timeout=8s;
    }
    server {
        listen 127.0.0.1:18084;
        server_name _;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 2s;
        proxy_read_timeout 5s;
        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_next_upstream_tries 3;
        location / { proxy_pass http://demo_round_robin; }
    }
}
NGINX

نام‌های a تا c نشان می‌دهند کدام نمونه پاسخ داده و $upstream_addr peer ثبت‌شده را. این دستهٔ کوچک چرخش را نشان می‌دهد؛ قول نمی‌دهد در هر بازه تعداد hitها دقیقاً برابر باشد. درخواست‌های کند، وزن‌ها و خرابی مقصد توزیع را عوض می‌کنند. log هم درستی body را ثابت نمی‌کند؛ پاسخ برنامه را کنار آن بخوان.

The names a through c show which instance answered, while $upstream_addr records the peer. This small batch shows rotation; it does not promise exactly equal hits in every window. Slow requests, weights, and failed peers change distribution. The log does not prove the body is correct; read the app response too.

درخواست با اتصال TCP ماندگار یکی نیست؛ Nginx peer را برای هر درخواست انتخاب می‌کند. اگر نتیجه متفاوت است، اول reload و access log را بررسی کن و بعد همان URL را دوباره بفرست.

همهٔ مقصدها توان یکسان ندارندNot every backend has the same capacity

یک نمونه قوی‌تر است و دو نمونه کوچک‌ترند. چرخش برابر از هرکدام سهم یکسان می‌خواهد؛ اگر ظرفیت فرق دارد، می‌توانی وزن بدهی. وزن یعنی سهم نسبی در انتخاب، نه درصد تضمین‌شده در هر دقیقه.

One instance is stronger and two are smaller. Equal rotation asks each to take the same share; when capacities differ, you can assign weights. A weight is a relative selection share, not a guaranteed percentage in every minute.

فقط تعریف گروه را عوض می‌کنیم: برای a وزن ۳ و برای دو نمونهٔ دیگر وزن ۱. در ۱۰ درخواست کوتاه انتظار داریم a سهم بیشتری بگیرد. نتیجهٔ دستهٔ کوچک را قانون قطعی ندان؛ config، reload، log و شمار بیشتری درخواست را بررسی کن.

Change only the group: give a weight 3 and leave the others at 1. Across ten short requests, we expect a to receive a larger share. Do not turn a small batch into a universal rule; check the config, reload, logs, and a larger sample.

weight peers, reload, and count responses
# Replace only the demo_round_robin block with:
    upstream demo_round_robin {
        server 127.0.0.1:19091 weight=3 max_fails=1 fail_timeout=8s;
        server 127.0.0.1:19092 weight=1 max_fails=1 fail_timeout=8s;
        server 127.0.0.1:19093 weight=1 max_fails=1 fail_timeout=8s;
    }

نمونه با نسبت 3:1:1 جور است؛ وزن ظرفیت واقعی یا حد اتصال را نمی‌سنجد. اگر شمارش تو فرق کرد، از ده درخواست قانون نساز؛ مطمئن شو Nginx reload شده و peer ناموفق یا درخواست هم‌زمان در کار نبوده است.

The sample matches a 3:1:1 ratio, but weight measures neither actual capacity nor a connection limit. If your counts differ, do not make a rule from ten requests; confirm Nginx reloaded and no peer failure or concurrency affected the batch.

وزن را با نیاز واقعی تنظیم کنChoose weights for a real reason

وزن بیشتر ورودی بیشتری می‌سازد، نه منابع بیشتر. بعد از تغییر اندازهٔ سرورها یا نوع درخواست‌ها، توزیع و زمان پاسخ را دوباره اندازه بگیر؛ عدد مناسب امروز ممکن است بعداً گلوگاه شود.

A higher weight sends more work; it does not add resources. After changing server sizes or request mix, measure distribution and response time again; a useful number today can later become a bottleneck.

اگر مهم باشد اتصال‌ها چقدر باز می‌مانند چه؟What if connection duration matters?

round-robin نمی‌داند هر درخواست چند ثانیه طول می‌کشد. اگر یک نمونه هنوز چند اتصال کند را نگه داشته، نوبت بعدی ممکن است باز هم به آن برسد. least_conn تعداد اتصال‌های فعالی را که Nginx برای هر peer می‌بیند در انتخاب دخالت می‌دهد.

Round-robin does not know how long each request will take. If one instance is holding several slow connections, the next turn may still go there. least_conn considers the active connections Nginx sees for each peer.

این معیار CPU، پاسخ سالم‌تر یا صف داخلی برنامه نیست؛ فقط اتصال‌های فعال را مقایسه می‌کند. برای دیدنش، گروه را به least_conn تغییر بده و ۹ درخواست /slow را هم‌زمان بفرست؛ هرکدام فقط ۱٫۵ ثانیه مکث دارند. توزیع دقیق به زمان ورود درخواست‌ها بستگی دارد.

This is not CPU, response health, or the app’s internal queue; it compares active connections only. To observe it, change the group to least_conn and send nine /slow requests concurrently; each waits only 1.5 seconds. Exact distribution depends on arrival timing.

انتظار داریم درخواست‌های کند بین نمونه‌ها پخش شوند، نه اینکه حتماً نسبت دقیق ۳-۳-۳ ببینیم؛ درخواست‌ها دقیقاً هم‌زمان نمی‌رسند. اگر همه فوری باشند، اتصال قبلی ممکن است پیش از انتخاب بعدی بسته شود و تفاوتی نبینی. مقصد ثبت‌شده را بخوان و دربارهٔ latency فقط با اندازه‌گیری بار واقعی نتیجه بگیر.

We expect slow requests to spread, not necessarily an exact 3-3-3 split; arrivals are not perfectly simultaneous. With immediate requests, the previous connection may close before the next selection and the difference may be invisible. Read the recorded peer, and draw latency conclusions only from real load measurements.

اگر weight هم فعال باشد، least_conn آن را در انتخاب دخالت می‌دهد. این directive نمی‌گوید کدام نمونه CPU آزادتر دارد یا در صف داخلی‌اش چند کار مانده؛ الگوریتم جای آزمون ظرفیت نیست.

If weights are also configured, least_conn accounts for them. It does not know which instance has more free CPU or how many jobs are queued inside it; a balancing method is not a capacity test.

چرا درخواست‌های یک نفر گاهی باید به همان نمونه برسند؟Why might one client need the same instance?

یک برنامهٔ قدیمی session را فقط در حافظهٔ همان پردازه نگه می‌دارد. کاربر وارد شده؛ درخواست بعدی به نمونهٔ دیگری می‌رود و آن نمونه او را ناشناس می‌شناسد. تا وقتی برنامه بازطراحی شود، شاید بخواهی درخواست‌های یک IP را به مقصد باثبات‌تری بفرستی.

An older app stores sessions only in its own process memory. A user signs in, but the next request lands on another instance that treats them as anonymous. Until the app is redesigned, you may want requests from one IP to reach a more stable peer.

نشانی‌ای که Nginx به‌عنوان client می‌بیند کلید انتخاب می‌شود. چند کاربر پشت NAT ممکن است یک کلید مشترک داشته باشند؛ اگر مقصد از دسترس خارج شود، چسبندگی هم می‌تواند تغییر کند.

The client address Nginx sees becomes the selection key. Users behind the same NAT may share a key; if the peer becomes unavailable, affinity can change too.

با ip_hash، همان IPای که Nginx می‌بیند به همان peer نگاشت می‌شود، مگر آن peer در دسترس نباشد. در IPv4 سه بخش اول نشانی و در IPv6 کل نشانی به کار می‌رود. در آزمایش ما همهٔ درخواست‌های curl از 127.0.0.1 می‌آیند، پس انتظار داریم به یک نمونه برسند.

With ip_hash, the same IP as seen by Nginx maps to the same peer unless it is unavailable. IPv4 uses its first three octets; IPv6 uses the full address. In our lab every curl request comes from 127.0.0.1, so we expect one instance to be selected.

ثابت‌ماندن نمونه فقط می‌گوید همین IP با این گروه یک انتخاب ثابت داده است؛ sticky cookie نداریم و session میان برنامه‌ها کپی نشده. NAT، تغییر IP یا خرابی peer نتیجه را عوض می‌کند. در طراحی تازه بهتر است session بیرون از حافظهٔ یک نمونه باشد تا affinity شرط کارکرد نباشد.

A stable instance proves only that this IP maps consistently with this group; there is no sticky cookie and sessions were not copied between apps. NAT, an IP change, or peer failure can change the result. A new design should keep sessions outside one instance’s memory so affinity is not required for correctness.

چسبندگی می‌تواند ایراد معماری را پنهان کندAffinity can hide an architectural problem

اگر session فقط وقتی پیدا می‌شود که کاربر به همان نمونه برگردد، از دست‌رفتن یا جایگزینی آن نمونه مشکل را برمی‌گرداند. ip_hash ذخیره‌سازی مشترک نمی‌سازد و تداوم session را تضمین نمی‌کند؛ فقط سیاست انتخاب را عوض می‌کند.

If a session exists only when a user returns to the same instance, losing or replacing it brings the problem back. ip_hash creates no shared storage and does not guarantee session continuity; it only changes peer selection.

وقتی نمونه‌ای می‌میرد، Nginx چه چیزی می‌فهمد؟When an instance dies, what can Nginx know?

یک نفر پردازهٔ app-b را متوقف کرده و کاربر گاهی 502 می‌بیند. قبل از اینکه بگوییم «Nginx خودش همه‌چیز را می‌فهمد»، بپرسیم خرابی چه زمانی برایش قابل‌مشاهده می‌شود: وقتی درخواست واقعی به آن نمونه می‌رسد و ارتباط شکست می‌خورد.

Someone stopped app-b, and users sometimes see a 502. Before saying “Nginx figures everything out,” ask when the failure becomes visible: when a real request reaches that instance and communication fails.

ردیف بالا مسیر passive است: درخواست زنده خطای ارتباط را آشکار می‌کند و تنظیم‌های server تعیین می‌کنند peer چه مدت کنار گذاشته شود. جعبهٔ پایین یادآوری می‌کند که این کار probe مستقل و دوره‌ای نیست.

The top row is passive: a live request exposes a communication failure, and server parameters determine how long the peer is avoided. The lower callout reminds us this is not an independent periodic probe.

در Nginx متن‌باز، بررسی upstream به‌صورت passive است: شکست درخواست واقعی شمرده می‌شود. max_fails تعداد شکست‌ها در بازهٔ fail_timeout را تعیین می‌کند؛ پس از رسیدن به حد، peer برای مدت fail_timeout نامناسب در نظر گرفته می‌شود. بعد از آن، یک درخواست واقعی دوباره فرصت امتحانش را می‌دهد؛ probe پس‌زمینه‌ای HTTP خودکار اجرا نمی‌شود.

Open-source Nginx uses passive upstream failure checks: failures from real requests are counted. max_fails sets the number of unsuccessful attempts within the fail_timeout window; after the threshold, the peer is considered unavailable for fail_timeout. After that, a real request can try it again; no background HTTP probe runs automatically.

چه خطایی شمرده شود به proxy_next_upstream مربوط است. پیکربندی ما ارتباط ناموفق، timeout و چند status را برای retry تعریف کرده و تا سه تلاش اجازه می‌دهد. این آزمایش فقط GET بی‌خطر است؛ retry یک POST غیرقابل‌تکرار ممکن است اثر جانبی را دوباره اجرا کند، پس directive را کورکورانه کپی نکن.

Which failures count depends on proxy_next_upstream. Our config allows retries for communication errors, timeouts, and selected statuses, with up to three attempts. This lab uses harmless GETs; retrying a non-idempotent POST can repeat a side effect, so do not copy the directive blindly.

خرابی را بازتولید می‌کنیم، اما اول PID نمونهٔ b و فرمانش را می‌خوانیم. فقط اگر همان فایل آزمایش را اجرا می‌کند متوقفش کن. پاسخ مستقیم باید شکست بخورد؛ درخواست Nginx می‌تواند با retry روی peer دیگری موفق شود. اگر PID جور نبود، متوقف نشو و چیزی را دست نزن.

The evidence shows the direct request to port 19092 was refused; the error log records the failed attempt and the access log may show both failed and replacement peers. A later request usually gets a healthy response; if every peer is broken or retries are exhausted, the client sees an error. After eight seconds, a real request may try b again.

این active health check نیست. پردازه می‌تواند زنده باشد ولی پاسخ نادرست بدهد؛ حتی endpoint سلامت ممکن است 200 بدهد درحالی‌که پایگاه‌داده قطع است. قابلیت HTTP health_check در upstream در مستند NGINX Plus آمده، نه به‌عنوان دستور عمومی Nginx متن‌باز. اگر آن را به config سادهٔ OSS اضافه کنی، با unknown directive روبه‌رو می‌شوی.

This is not an active health check. A process can be alive but return the wrong response; even its health endpoint may return 200 while the database is disconnected. The upstream HTTP health_check feature is documented for NGINX Plus, not as a general open-source directive. Adding it to a basic OSS config can produce unknown directive.

حتی statusی که در retry شمرده می‌شود، معادل سلامت کامل سرویس نیست. اگر می‌خواهی 503 مقصد را کنار بگذارد، باید status در سیاست باشد و اثر تکرار درخواست را بفهمی. برای write واقعی، idempotency و قرارداد برنامه را پیش از retry بررسی کن.

Even a status counted for retry is not equivalent to full service health. To avoid a peer after 503, that status must be in the policy and you must understand replay consequences. Before retrying a real write, verify idempotency and the app contract.

تمرین ۱ · مقصد پنهانExercise 1 · The hidden peer

The app responds with instance=c. Which config and log evidence tells you why Nginx selected c?

Find the upstream group and selection method, such as least_conn or ip_hash, then compare an access log containing $upstream_addr with the response. The name c proves which app answered, but not by itself which method was active or why it selected that peer.

Three servers have default weight 1. What pattern do you expect for three short requests, and why not say “always exactly equal”?

انتظار معقول این است که هر peer یک درخواست بگیرد. اما این فقط پیش‌بینی برای وضعیت ساده است؛ هم‌زمانی، وزن، peer ناموفق و بازهٔ شمارش نتیجه را عوض می‌کنند. body و access log همین اجرا را بخوان تا آن را ثابت کنی.

A reasonable expectation is one request per peer. But that is a prediction for a simple setup; concurrency, weights, failed peers, and the counting window can change results. Read this run’s bodies and access log to prove what happened.

سه peer وزن‌های ۴، ۲ و ۲ دارند. در تعداد درخواست کافی، سهم نسبی مورد انتظار هرکدام چیست؟

The ratio 4:2:2 reduces to 2:1:1: about half for the first peer and a quarter for each other peer over a suitable sample. This does not guarantee exact scheduling in every window or replace capacity measurement.

تمرین ۴ · وزن یا سقف اتصال؟Exercise 4 · Weight or connection cap?

همکارت بعد از تنظیم weight=5 می‌گوید «پس این سرور پنج اتصال هم‌زمان می‌گیرد». کدام بخش حرفش اشتباه است؟

After setting weight=5, a teammate says, “So this server gets five simultaneous connections.” What is wrong?

پاسخ را ببینShow solution

weight سهم نسبی انتخاب peer است، نه سقف اتصال و نه تعداد هم‌زمان. برای رفتار هم‌زمان باید اتصال‌های فعال را مشاهده کرد؛ این دستور منابع سرور را زیاد نمی‌کند.

Weight is a relative peer-selection share, not a connection cap or concurrency count. Observe active connections to understand concurrency; this directive adds no server resources.

تمرین ۵ · درخواست کندExercise 5 · The slow request

یک peer سه اتصال ۲۰ثانیه‌ای دارد و دو peer دیگر آزادند. چرا least_conn ممکن است برای درخواست بعدی مناسب‌تر باشد؟

One peer has three 20-second connections while two peers are idle. Why might least_conn be preferable for the next request?

این روش تعداد اتصال فعال را دخالت می‌دهد و ممکن است peer آزاد را انتخاب کند؛ round-robin فقط نوبت را می‌چرخاند. اما CPU، latency یا صف داخلی را نمی‌سنجد، پس نتیجه را با اندازه‌گیری درخواست واقعی بررسی کن.

It considers active connection counts and may choose an idle peer; round-robin just rotates. It does not measure CPU, latency, or an internal queue, so verify the result with real request measurements.

تمرین ۶ · همه اتصال‌ها کوتاه‌اندExercise 6 · All connections are brief

Requests are immediate and you see no difference between least_conn and round-robin. Does this prove the directive did not load?

Hundreds of users share a company NAT address and ip_hash is enabled. What distribution risk do you see?

همه ممکن است برای hash یک IP دیده شوند و به یک peer بچسبند؛ بار نامتوازن می‌شود. affinity بر پایهٔ IP هویت یکتای کاربر نیست. log و الگوی NAT را بسنج و اگر لازم است session مشترک بساز تا انتخاب متوازن‌تر ممکن شود.

They may all appear as one IP to the hash and stick to one peer, creating uneven load. IP affinity is not unique user identity. Measure logs and NAT patterns, and consider shared sessions to allow more balanced selection.

قبل از Nginx یک load balancer هست و ip_hash همه را به یک نمونه می‌فرستد. کدام مدرک فصل قبل مرتبط است؟

درخواست مستقیم به backend، connection refused می‌دهد؛ از Nginx پاسخ 200 با نام نمونهٔ دیگری می‌بینی. چه چیزی محتمل است؟

A direct request to a backend gets connection refused; through Nginx you get 200 from another instance. What likely happened?

پاسخ را ببینShow solution

Nginx احتمالاً peer خاموش را امتحان کرده، شکست ارتباط را دیده و درخواست GET را به peer دیگری retry کرده است. log را برای مقصد هر تلاش بخوان. پاسخ 200 ثابت نمی‌کند peer خراب تعمیر شده؛ فقط درخواست از مقصد دیگری پاسخ گرفته.

پردازه زنده است اما هر پاسخ 200 در body می‌گوید «database unavailable». آیا passive failure حتماً آن peer را کنار می‌گذارد؟

The process is alive, but each 200 body says “database unavailable.” Must passive failure handling remove that peer?

نه؛ ارتباط موفق و status موردقبول ممکن است برای Nginx شکست نباشد، هرچند body از نظر برنامه بد است. قرارداد status و proxy_next_upstream را بررسی کن. معنای پاسخ را فقط از بازبودن socket نمی‌شود فهمید.

Nginx stops with unknown directive \"health_check\". What should you check first?

تمرین ۱۳ · پنجرهٔ شکستExercise 13 · Failure window

تنظیم max_fails=2 fail_timeout=10s است. آیا Nginx هر ۱۰ ثانیه دو بار backend را ping می‌کند؟

The config uses max_fails=2 fail_timeout=10s. Does Nginx ping the backend twice every ten seconds?

پاسخ را ببینShow solution

نه. شکست‌های ارتباطی درخواست‌های زنده شمرده می‌شوند؛ دو شکست در بازهٔ ۱۰ثانیه‌ای peer را برای مدتی نامناسب می‌کند. این directive زمان‌بند probe نیست؛ پس از آن بازه، درخواست زنده می‌تواند دوباره آن را بیازماید.

No. Communication failures from live requests are counted; two failures in the 10-second window make the peer unavailable for a period. This directive schedules no probes; after the interval, a live request may try the peer again.

تمرین ۱۴ · POST را retry کنیم؟Exercise 14 · Retry the POST?

POST پرداختی آغاز شده، ارتباط حین پاسخ قطع می‌شود و Nginx می‌خواهد آن را به peer بعدی بفرستد. پیش از فعال‌کردن retry چه چیزی را بررسی می‌کنی؟

A payment POST starts, the connection fails while waiting for a response, and Nginx may send it to another peer. What do you check before enabling that retry?

پاسخ را ببینShow solution

باید بدانیم درخواست اول تا کجا اجرا شده و عملیات idempotent یا دارای idempotency key هست یا نه. اگر پرداخت انجام شده ولی پاسخ گم شده باشد، retry می‌تواند هزینهٔ دوم بسازد. قرارداد برنامه و سرویس پرداخت را بررسی کن؛ directive را کورکورانه تغییر نده.

Establish how far the first request ran and whether the operation is idempotent or protected by an idempotency key. If payment succeeded but its response was lost, a retry could charge twice. Check the app and payment-service contract; do not change the directive blindly.

تمرین ۱۶ · peer برگشتهExercise 16 · The peer has returned

backend بعد از fail_timeout روشن شده. چرا دقیق‌تر است بگویی «یک درخواست واقعی دوباره امتحانش می‌کند» نه «Nginx health check می‌زند»؟

A backend restarts after fail_timeout. Why is “a real request may try it again” more accurate than “Nginx runs a health check”?

پاسخ را ببینShow solution

در passive checking، Nginx probe مستقل و زمان‌بندی‌شده نمی‌فرستد؛ درخواست عادی است که دوباره به peer می‌رسد و مدرک تازه می‌سازد. روشن‌شدن پردازه به‌تنهایی به Nginx خبر نمی‌دهد.

With passive checking, Nginx sends no independent scheduled probe. An ordinary request reaches the peer and supplies new evidence. The process restarting alone does not notify Nginx.

تمرین ۱۷ · session محلیExercise 17 · Local session state

کاربران با ip_hash کمتر logout می‌شوند. peer دارای session محلی از دسترس خارج می‌شود. چرا تداوم session هنوز تضمین نیست؟

Users see fewer logouts after enabling ip_hash. The peer holding local sessions becomes unavailable. Why is session continuity still not guaranteed?

پاسخ را ببینShow solution

Nginx می‌تواند درخواست را به نمونه‌ای دیگر بفرستد که آن session را ندارد. affinity فقط تا وقتی peer موجود و IP ثابت است کمک می‌کند. برای تداوم واقعی، state را مشترک/بیرونی کن یا برنامه را stateless بساز.

Nginx can send the request to another instance that lacks the session. Affinity helps only while the peer stays available and the IP is stable. Real continuity needs shared/external state or a stateless app.

تمرین ۱۸ · تصمیم برای ترافیک واقعیExercise 18 · Choose for real traffic

یک backend قوی‌تر است، بعضی درخواست‌ها چند ثانیه باز می‌مانند و session در حافظهٔ هر نمونه است. چه روش‌هایی را می‌آزمایی و پیش از production چه چیزی را تغییر می‌دهی؟

One backend is stronger, some requests stay open for seconds, and sessions live in each instance’s memory. What would you test, and what would you change before production?

پاسخ را ببینShow solution

ظرفیت را با weight بازتاب می‌دهم و اگر اتصال‌های فعال متفاوت‌اند least_conn را زیر بار نماینده می‌سنجم. session محلی مسئله‌ای جداست: ip_hash affinity موقت می‌دهد، نه تداوم هنگام خرابی. پیش از production session را بیرونی/مشترک می‌کنم و latency و خطا را می‌سنجم.

Reflect capacity with weights and test least_conn under representative load if active connections vary. Local sessions are separate: ip_hash provides temporary affinity, not continuity through failure. Before production, move sessions to shared/external storage and measure latency and errors.
