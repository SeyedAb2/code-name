پروژهٔ ۳ — gateway کامل

Project 3 — a complete gateway

این پروژه جمع‌بندی دوره است: سه سرویس با رفتار متفاوت، یک ورودی عمومی. باید routing، TLS، کش، load balancing، rate limiting و لاگ را طوری کنار هم بچینی که هر کدام مرز خودش را داشته باشد. بعد عمداً چند خرابی ایجاد می‌کنیم تا معلوم شود gateway فقط در روز خوب کار نمی‌کند؛ در روز بد هم قابل فهم و قابل برگشت است.

This capstone combines the course: three services with different behavior behind one public entry point. Routing, TLS, caching, load balancing, rate limiting, and logging must each have a clear boundary. Then we deliberately break several pieces to prove the gateway is understandable and recoverable on bad days, not only functional on good ones.

مأموریت: سه سرویس، یک درِ ورودیMission: three services, one front door

سه سرویس داری و فقط یک ورودی باید به کاربر نشان داده شود. چالش اصلی نوشتن چند location نیست؛ این است که سیاست هر مسیر با رفتار همان سرویس جور باشد. catalog می‌تواند کش شود، API باید بین دو peer پخش شود و login باید بودجهٔ درخواست داشته باشد. از همین ابتدا هر مسیر را با یک آزمون پذیرش جدا تعریف کن.

You have three services and only one entry point should be visible to users. The main challenge is not writing several locations; it is matching each route’s policy to that service. Catalog may be cached, API must spread across two peers, and login needs a request budget. Define a separate acceptance test for each route from the start.

فلش‌ها مسیر درخواست‌اند؛ شاخهٔ API دو مقصد هم‌نقش دارد و Nginx بینشان انتخاب می‌کند. کادر شبکه مرز دسترسی backendهاست؛ تنها پورت‌های Nginx روی host منتشر می‌شوند.

Arrows show request paths. The API branch has two equivalent targets for Nginx to select between. The network boundary keeps backends private; only Nginx publishes host ports.

برای اینکه روی لپ‌تاپ هم قابل تکرار باشد، در این مأموریت از TLS خودامضاشده استفاده می‌کنیم و در درخواست آزمایشگاهی از curl -k کمک می‌گیریم. این فقط رمزگذاری مسیر تا Nginx را برای آزمایش نشان می‌دهد؛ گواهی مورداعتماد مرورگر یا اثبات مالکیت دامنه نیست. برای HTTPS عمومی باید دامنه و گواهی معتبر پروژهٔ ۱ را جایگزین کنی.

For repeatable local work, this mission uses a self-signed certificate and curl -k for lab requests. That demonstrates encryption to Nginx, not browser trust or domain ownership. Public HTTPS requires a real domain and the trusted certificate from Project 1.

این gateway یک نمونهٔ آموزشی است، نه فایل آمادهٔ محیط عملیاتی. هر shortcut را صریح نگه می‌داریم: گواهی self-signed، backendهای کوچک و limiter مبتنی بر IP. ارزش پروژه در این است که بدانی این انتخاب‌ها کجا معتبرند و اگر محیط عوض شد کدام فرض باید دوباره بررسی شود.

This gateway is a teaching system, not a production-ready file. Its shortcuts are explicit: a self-signed certificate, tiny backends, and an IP-based limiter. The value of the project is knowing where those assumptions are valid and which ones must be revisited when the environment changes.

نقطهٔ ۱: سرویس‌ها را قبل از proxy بشناسCheckpoint 1: know the services before proxying

سه backend بساز یا از starter همین پروژه استفاده کن. هرکدام باید نام خودش را در خروجی برگرداند؛ catalog علاوه بر آن یک مقدار ثابتِ قابل مشاهده مثل catalog revision 1 بدهد. دو نمونهٔ API خروجی متفاوت api-1 و api-2 داشته باشند. login هم پاسخ سادهٔ موفق برگرداند. هیچ‌کدام را هنوز از host منتشر نکن.

Create the three backends or use this project’s starter. Each returns its own name; catalog also returns a visible fixed value such as catalog revision 1. The two API instances return distinct api-1 and api-2 identifiers. Login returns a simple success response. Do not publish any backend port to the host.

قبل از نوشتن Nginx، از داخل شبکهٔ پروژه endpoint هر سرویس را بزن. این تست ثابت می‌کند سرویس و DNS داخلی کار می‌کنند؛ هنوز چیزی دربارهٔ TLS، مسیرهای Nginx یا دسترسی از اینترنت نمی‌گوید.

Before writing Nginx config, request each service from inside the project network. This proves the service and internal DNS work; it says nothing yet about TLS, Nginx routing, or internet reachability.

record one direct response from every backend
docker compose ps
docker compose exec nginx wget -qO- http://catalog:8080/catalog/featured
docker compose exec nginx wget -qO- http://api-1:8080/api/whoami
docker compose exec nginx wget -qO- http://login:8080/login/
{"service": "catalog", "item": "featured", "revision": "catalog revision 1"}
{"service": "api-1", "instance": "api-1"}
{"service": "login", "result": "login ready"}

اگر Nginx image ابزار wget نداشت، اشکالی ندارد: از container آزمایش موقت متصل به همان network استفاده کن. ابزار تشخیصی را به image نهایی اضافه نکن فقط برای راحتی این مرحله.

If the Nginx image lacks wget, use a disposable diagnostic container attached to the same network. Do not add troubleshooting tools to the final image merely for this step.

نقطهٔ ۲: فقط Nginx رو به بیرونCheckpoint 2: expose only Nginx

در Compose فقط برای Nginx نگاشت 8080:80 و 8443:443 بگذار. سه backend و دو نمونهٔ API باید روی شبکهٔ داخلی باشند و ports نداشته باشند. پیش از ادامه، این را از پیکربندی مؤثر و از host بررسی کن؛ «من پورت را در مرورگر ندیدم» مدرک کافی نیست.

In Compose, publish 8080:80 and 8443:443 only for Nginx. The three backends and both API instances stay on the internal project network with no ports. Verify effective config and host listeners before continuing; “I did not see the port in a browser” is not enough proof.

inspect published bindings from both Docker and the host
docker compose ps
docker compose port nginx 80
docker compose port nginx 443
ss -lnt
127.0.0.1:8080
127.0.0.1:8443
backend services have no published host bindings

برای آزمایش روی همان ماشین، پورت‌ها را به 127.0.0.1 bind کن تا از شبکهٔ بیرونی در دسترس نباشند. اگر با ماشین مجازی جدا کار می‌کنی، برای آزمون از host میزبان مسیر دسترسی را آگاهانه تنظیم کن؛ فایروال جایگزین bind محدود نیست.

For a same-machine lab, bind published ports to 127.0.0.1 so they are not reachable from external interfaces. With a separate VM, deliberately arrange a path from the host for testing; a firewall is not a substitute for a narrow bind.

نقطهٔ ۳: مسیرها و TLS را وصل کنCheckpoint 3: wire routes and TLS

گواهی آزمایشگاهی بساز و سه location را به نام سرویس Compose وصل کن. برای هر مسیر URL یکتا و پاسخ backend را یادداشت کن؛ فعلاً کش و rate limit خاموش بمانند تا اگر مسیر اشتباه بود، علت‌ها را قاطی نکنی.

Create the lab certificate and connect three locations to Compose service names. Record one URL and backend response per route. Leave caching and rate limiting off for now so a routing mistake is not confused with another control.

self-signed certificate for local-only testing
mkdir -p ./lab-certs
openssl req -x509 -nodes -newkey rsa:2048 -days 7 \
  -keyout ./lab-certs/server.key \
  -out ./lab-certs/server.crt \
  -subj '/CN=localhost' \
  -addext 'subjectAltName=DNS:localhost,IP:127.0.0.1'
chmod 600 ./lab-certs/server.key

حالا سه درخواست بزن و گواهی را صریحاً به‌عنوان خودامضاشده ببین. -k فقط اعتبارسنجی گواهی را دور می‌زند؛ آن را در دستور واقعی دامنه به کار نبر.

Now make three requests and inspect the certificate as self-signed. -k skips certificate verification; never use it for a real public-domain acceptance test.

verify TLS handshake and route response
curl -k -i https://localhost:8443/catalog/featured
curl -k -i https://localhost:8443/api/whoami
curl -k -i https://localhost:8443/login/
HTTP/1.1 200 OK
{"service": "catalog", "item": "featured", "revision": "catalog revision 1"}
{"service": "api-1", "instance": "api-1"}
{"service": "login", "result": "login ready"}

اگر status، بدنه و backend نامنتظره است، URL را از Nginx لاگ خطا تا proxy_pass دنبال کن؛ با تغییر هم‌زمان چند location چیزی یاد نمی‌گیری. گواهی خودامضا ممکن است warning بدهد، اما handshake و نام سرویس مسیر شده باید دیده شود.

If status, body, or backend is unexpected, trace that URL from the Nginx error log to proxy_pass; changing several locations at once obscures the lesson. A self-signed warning is expected, but the handshake and routed service should be visible.

نقطهٔ ۴: کش را فقط روی پاسخ بی‌خطر امتحان کنCheckpoint 4: cache only a safe response

کش را فقط جایی فعال کن که پاسخ واقعاً عمومی و غیرشخصی است. قبل از پیکربندی، دو درخواست یکسان و یک نشانهٔ قابل‌دیدن برای HIT/MISS تعریف کن. اگر نمی‌توانی بگویی چه داده‌ای نباید کش شود، هنوز وقت proxy_cache نیست.

Enable caching only where responses are truly public and non-personal. Before configuring it, define two identical requests and a visible HIT/MISS signal. If you cannot state what data must never be cached, it is not yet time for proxy_cache.

compare the cache indicator across two identical GETs
curl -k -sS -D - -o /dev/null https://localhost:8443/catalog/featured
curl -k -sS -D - -o /dev/null https://localhost:8443/catalog/featured
X-Cache-Status: MISS
X-Cache-Status: HIT

در /login/ و مسیرهای کاربرمحور کش نگذار. هیچ‌وقت پاسخ دارای نشست یا دادهٔ شخصی را به‌خاطر یک تست موفق کش نکن. اگر origin هدرهای Set-Cookie یا Cache-Control می‌فرستد، رفتار کش را دوباره بررسی کن؛ این آزمایش ساده جای سیاست محصول را نمی‌گیرد.

Do not cache /login/ or user-specific paths. Never cache a response containing session or personal data just because a test worked. If an origin emits Set-Cookie or Cache-Control, review the cache behavior; this small test is not a product policy.

نقطهٔ ۵: توزیع بار را با مدرک ببینCheckpoint 5: observe load distribution

برای load balancing، دو backend باید خودشان را معرفی کنند. چند درخواست بفرست و توزیع را ثبت کن، بعد یکی را خاموش کن. سیستم کامل نیست مگر اینکه هم رفتار عادی و هم رفتار یک peer خراب را بتوانی از روی پاسخ و لاگ توضیح بدهی.

For load balancing, both backends must identify themselves. Send several requests and record the distribution, then stop one peer. The system is not complete until you can explain both normal behavior and a failed peer from responses and logs.

send sequential requests and preserve the returned instance IDs
for i in $(seq 1 8); do
  curl -k -sS https://localhost:8443/api/whoami
done
{"service": "api-1", "instance": "api-1"}
{"service": "api-2", "instance": "api-2"}
{"service": "api-1", "instance": "api-1"}
{"service": "api-2", "instance": "api-2"}
...

برای آزمایش passive failure، فقط یک نمونه را متوقف کن، چند بار API را بخوان و سپس همان نمونه را برگردان. Nginx متن‌باز با خطاهای درخواست واقعی، برای مدتی backend خراب را از انتخاب کنار می‌گذارد؛ این active healthcheck دوره‌ایِ NGINX Plus نیست و تا رسیدن درخواست خطادار هم ممکن است خرابی را نداند.

For a passive-failure drill, stop exactly one instance, request the API several times, then restore that instance. Open-source Nginx uses failures from real requests to avoid a failed backend for a period; this is not NGINX Plus active health checking, and failure may remain unknown until a request encounters it.

stop one disposable API instance, observe, and bring it back
docker compose stop api-2
for i in $(seq 1 5); do curl -k -sS -w '\nstatus=%{http_code}\n' https://localhost:8443/api/whoami; done
docker compose start api-2
docker compose ps

ممکن است کاربر همچنان ۲۰۰ ببیند، چون Nginx برای خطای قابل retry سراغ peer سالم بعدی می‌رود؛ پس فقط status را نگاه نکن. بدنه باید نام api-1 را نشان بدهد و لاگ دسترسی و خطا نشانی و status تلاش upstream را ثبت کند. اگر peer سالمی نمانده یا retry ممکن نباشد، ۵۰۲ هم ممکن است. بعد از بالا آمدن backend، Nginx معمولاً با درخواست واقعی دوباره موفقیت را می‌بیند؛ یک health endpoint تنها، تضمین فعال بودن backend در لحظهٔ بعد نیست.

The client may still see 200 because Nginx can retry a retryable failure against the other peer, so do not inspect status alone. The body should identify api-1, and access/error logs should show the upstream address and attempt status. If no healthy peer remains or retry is not possible, 502 is possible. After the backend returns, Nginx generally sees success again through a real request; one health endpoint is not a guarantee about the next instant.

نقطهٔ ۶: مسیر حساس را آرام‌تر کنCheckpoint 6: slow down the sensitive route

مسیر login را محدود می‌کنیم، ولی عدد کم این لَب را با سیاست محیط عملیاتی اشتباه نگیر. هدف دیدن رفتار limiter است: درخواست‌های پذیرفته‌شده، burst و 429. بعد در یادداشت بنویس IP به‌عنوان key در حضور NAT یا proxy چه محدودیتی دارد.

We limit the login route, but do not mistake the small lab number for a production policy. The goal is to observe limiter behavior: accepted requests, burst, and 429. Then document the limitation of using IP as a key behind NAT or another proxy.

compare a normal request with a short burst
for i in $(seq 1 12); do
  curl -k -sS -o /dev/null -w '%{http_code} ' https://localhost:8443/login/
done
printf '\n'
docker compose logs --tail=20 nginx
200 200 200 200 429 429 ...
... REJECTED ... status=429 ... uri="/login/"

تعداد دقیق پاسخ‌های ۲۰۰ ممکن است با فاصلهٔ درخواست، burst و IP دیده‌شده عوض شود. در لاگ مقدار $limit_req_status را ببین؛ اگر پشت proxy دیگری هستی و Nginx همه را یک IP می‌بیند، پیش از اعتماد به limit باید real-IP فقط از پروکسی‌های مورداعتماد تنظیم شود. هدر کلاینت قابل‌جعل را بی‌قیدوشرط مبنا نگذار.

The exact number of 200 responses varies with request spacing, burst, and the IP Nginx sees. Inspect $limit_req_status in logs. If another proxy sits in front and Nginx sees one shared IP, configure real-IP only for trusted proxies before relying on the limit. Do not blindly trust a spoofable client header.

نقطهٔ ۷: لاگ باید سؤال را جواب بدهدCheckpoint 7: make logs answer questions

برای هر درخواست زمان، درخواست id، مسیر، status، آدرس و status upstream، زمان upstream، وضعیت کش و نتیجهٔ rate limit را ثبت کن. این یک لاگ متنیِ قابل‌جست‌وجوست، نه metrics سامانه‌ای آماده؛ با آن می‌توانی علت یک پاسخ را کنار backend انتخاب‌شده ببینی.

Log request time, request ID, path, status, upstream address/status/time, cache status, and rate-limit result. This is searchable text, not a ready-made metrics system; it lets you correlate a response with the selected backend.

follow a few requests and correlate fields from one line
docker compose logs --since=2m nginx
curl -k -sS https://localhost:8443/api/whoami
curl -k -sS https://localhost:8443/catalog/featured
... rid=... status=200 upstream=api-1:8080 upstream_status=200 upstream_time=0.002 cache=- limit=-
... rid=... status=200 upstream=- upstream_status=- upstream_time=- cache=HIT limit=-

در کش HIT، upstreamی صدا نشده؛ پس خط لاگ می‌تواند برای آدرس و زمان upstream علامت - داشته باشد. اگر درخواست API هنگام خرابی peer retry شود، ممکن است چند upstream status در همان خط ثبت شوند. اگر کلاینت پاسخ خطا دید، همان زمان و درخواست id را پیدا کن؛ journal سرویس‌های آزمایشی چیزی دربارهٔ خطایی که Nginx پیش از رسیدن به backend داده نمی‌گوید. لاگ سرنخ است، نه علت قطعی به‌تنهایی.

On a cache HIT, no upstream was contacted, so the log may show - for upstream address and time. If an API request retries after a peer failure, one log line may contain multiple upstream statuses. When a client sees an error, find its time and request ID; demo-service journals cannot explain an error Nginx returned before reaching a backend. A log is a clue, not a definitive cause by itself.

نقطهٔ ۸: خرابی را قبل از reload متوقف کنCheckpoint 8: stop a bad config before reload

حالا پیکربندی را عمداً می‌شکنیم، اما این‌بار خطا نباید به سرویس زنده برسد. nginx -t باید دیوار قبل از reload باشد. خروجی خطا را نگه دار، فایل را اصلاح کن و فقط بعد از test موفق همان درخواست‌های پذیرش را تکرار کن.

Now deliberately break the configuration, but the error must never reach the live service. nginx -t is the wall before reload. Keep the failure output, fix the file, and only after a passing test repeat the same acceptance requests.

برای خرابی دوم، فایل bind-mounted فعال را پس از backup عمداً با directive نادرست تغییر بده، اما reload نکن. nginx -t باید candidate را رد کند؛ workerهای موجود هنوز پیکربندی بارگذاری‌شدهٔ قبلی را دارند و باید پاسخ بدهند. فایل known-good را برگردان، بعد test و reload امن را انجام بده.

For the second fault, back up and deliberately misspell a directive in the active bind-mounted file, but do not reload. nginx -t must reject the candidate; existing workers still hold the previously loaded config and should answer. Restore the known-good file, then test and safely reload.

validate the candidate first; preserve the running config until it passes
docker compose exec nginx nginx -t
curl -k -sS -o /dev/null -w '%{http_code}\n' https://localhost:8443/catalog/featured
nginx: [emerg] unknown directive "proxy_passs" ...
200

این مدرک می‌گوید پیکربندی فعال قبلی پاسخ داده و پیکربندی خراب رد شده؛ دربارهٔ درست بودن همهٔ مسیرها یا سلامت backendها چیزی ثابت نمی‌کند. پس از repair، دوباره nginx -t، reload کنترل‌شده و همان آزمون‌های مسیر/TLS/کش/rate را اجرا کن.

This proves the old active config served a response while the invalid candidate was rejected; it does not prove every route or backend is healthy. After repair, rerun nginx -t, perform a controlled reload, and repeat the same route/TLS/cache/rate tests.

نقطهٔ ۹: تحویل فنی، نه فقط «کار می‌کند»Checkpoint 9: hand off evidence, not just “it works”

تحویل فنی یک عکس از صفحه نیست. برای هر مسیر بنویس مقصدش چیست، کدام policy روی آن اعمال می‌شود، چه logی برایش می‌خوانیم و rollback چگونه انجام می‌شود. کسی که فردا on-call است باید از روی این گزارش بتواند سیستم را بفهمد.

Technical handoff is not a screenshot. For each route, document its destination, applied policy, relevant logs, and rollback path. Tomorrow’s on-call engineer should be able to understand the system from this report.

کنار یادداشت، خروجی آزمون‌ها را نگه دار. فقط screenshot صفحهٔ اصلی کافی نیست: نتیجهٔ کش، هر دو شناسهٔ API، نرخ محدودشده، درخواست پس از توقف یک backend، گواهی TLS و رد شدن پیکربندی غلط باید مدرک داشته باشند.

Keep test output with the note. A screenshot of the home page is not enough: preserve proof of cache behavior, both API IDs, throttling, a request during backend failure, the TLS certificate, and rejection of invalid config.

راهنمایی‌ها را به‌ترتیب باز کنOpen hints progressively

۱. ۵۰۲ می‌بینی، اما کدام مرز خراب است؟1. You see 502; which boundary failed?

اول مستقیم از شبکهٔ Compose به سرویس بزن. بعد Nginx لاگ خطا و $upstream_addr را با نام و پورت واقعی مقایسه کن. reload بی‌دلیل کمکی نمی‌کند.

First request the service directly from the Compose network. Then compare the Nginx error log and $upstream_addr with the actual service name and port. A blind reload does not help.

۲. کش هیچ‌وقت HIT نمی‌شود2. Cache never becomes HIT

مطمئن شو دو درخواست GET دقیقاً یک key دارند، origin پاسخ cacheable می‌دهد و cookie یا دستور منع کش در پاسخ نیست. کش را از URLهای login حذف کن.

Ensure both GETs use the same key, the origin response is cacheable, and no cookie or cache-prevention directive is present. Keep login URLs out of the cache.

۳. هر درخواست login از یک IP دیده می‌شود3. Every login request appears to come from one IP

ممکن است همهٔ درخواست‌ها از یک proxy بیایند. real-IP را فقط با فهرست پروکسی‌های مورداعتماد تنظیم کن؛ X-Forwarded-For دلخواه از اینترنت را معتبر فرض نکن.

A proxy may be the source of every request. Configure real-IP only with a trusted proxy list; never assume arbitrary internet-supplied X-Forwarded-For is trustworthy.

۴. دستور خراب از test گذشت4. The bad change passed config test

اگر فقط شمارهٔ port یا مقصد منطقی اشتباه باشد، parser خطای نحو نمی‌بیند. درخواست واقعی، upstream address و اتصال backend این دو نوع خطا را از هم جدا می‌کنند.

A wrong port or logically wrong target can still be valid syntax. A real request, upstream address, and backend connectivity distinguish this from a parser error.

backend آزمایشیDemo backend

backend/server.py — no data writes; distinguish each instance
from http.server import BaseHTTPRequestHandler, HTTPServer
import os
import json
import time

NAME = os.environ.get("SERVICE_NAME", "backend")
class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/catalog/featured":
            body = {"service": NAME, "item": "featured", "revision": "catalog revision 1"}
        elif self.path == "/api/whoami":
            body = {"service": NAME, "instance": NAME}
        elif self.path == "/login/":
            body = {"service": NAME, "result": "login ready"}
        else:
            self.send_error(404)
            return
        raw = json.dumps(body).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(raw)))
        self.end_headers()
        self.wfile.write(raw)
        print(f"{time.time():.3f} {self.client_address[0]} GET {self.path} 200", flush=True)

    def log_message(self, fmt, *args):
        print(f"{time.time():.3f} {self.client_address[0]} {fmt % args}", flush=True)

HTTPServer(("0.0.0.0", 8080), Handler).serve_forever()

این server تک‌ریسمانی برای آزمون ساده است، نه برنامه محیط عملیاتی. backendها در Compose شبکهٔ جداگانه دارند؛ binding به همهٔ interfaceهای داخل container لازم است تا Nginx به آن‌ها وصل شود، اما چون host port منتشر نشده، این به‌تنهایی پورت عمومی host نمی‌سازد.

This single-threaded server is a test fixture, not a production app. It binds all interfaces inside its container so Nginx can connect on the private network; with no host port published, that does not by itself expose the host port publicly.

سه service role پشت Nginx داریم: catalog، API و login؛ API برای نمایش load balancing دو نمونهٔ فیزیکی دارد. Nginx هم خود یک service جداست. depends_on در این scaffold فقط ترتیب ایجاد را کمک می‌کند؛ readiness را ثابت نمی‌کند و اینجا healthcheck برای backend ننوشته‌ایم. پورت‌های منتشرشده به loopback محدودند تا آزمایش عمومی تصادفی نشود.

There are three backend service roles behind Nginx: catalog, API, and login; the API has two physical instances to demonstrate balancing. Nginx is a separate service. In this scaffold, depends_on only helps creation order; it does not prove readiness, and these demo backends have no healthchecks. Published ports bind to loopback to avoid accidental public exposure.

Nginx: دروازه، نه یک مشت directiveNginx: a gateway, not a pile of directives

در لاگ دسترسی فیلدهای upstream و کنترل‌ها را کنار درخواست id می‌گذاریم. لاگ format و zoneها در http هستند؛ مسیرها در server/location. نام image را با نسخهٔ Nginx خودت ثابت کن و پیش از هر reload تست بگیر.

The access log places upstream and control fields beside a request ID. Log format and zones live in http; routes live in server/location. Pin the Nginx image version you actually use and test before every reload.

nginx/nginx.conf — local TLS, safe cache scope, passive upstream failure
events {}
http {
    log_format edge '$time_iso8601 rid=$request_id method=$request_method uri="$request_uri" '
                    'status=$status upstream=$upstream_addr upstream_status=$upstream_status '
                    'upstream_time=$upstream_response_time request_time=$request_time '
                    'cache=$upstream_cache_status limit=$limit_req_status';
    access_log /var/log/nginx/access.log edge;
    error_log  /var/log/nginx/error.log warn;

    proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=public_catalog:10m
                     max_size=32m inactive=1m use_temp_path=off;
    limit_req_zone $binary_remote_addr zone=login_per_ip:1m rate=2r/s;
    limit_req_status 429;

    upstream api_pool {
        server api-1:8080 max_fails=1 fail_timeout=5s;
        server api-2:8080 max_fails=1 fail_timeout=5s;
    }

    server {
        listen 80;
        server_name localhost;
        return 301 https://localhost:8443$request_uri;
    }

    server {
        listen 443 ssl;
        server_name localhost;
        ssl_certificate     /etc/nginx/certs/server.crt;
        ssl_certificate_key /etc/nginx/certs/server.key;

        location /catalog/ {
            proxy_pass http://catalog:8080;
            proxy_set_header Host $host;
            proxy_set_header X-Request-ID $request_id;
            proxy_cache public_catalog;
            proxy_cache_valid 200 20s;
            proxy_cache_key "$scheme$proxy_host$request_uri";
            add_header X-Cache-Status $upstream_cache_status always;
        }

        location /api/ {
            proxy_pass http://api_pool;
            proxy_set_header Host $host;
            proxy_set_header X-Request-ID $request_id;
        }

        location /login/ {
            limit_req zone=login_per_ip burst=3 nodelay;
            proxy_pass http://login:8080;
            proxy_set_header Host $host;
            proxy_set_header X-Request-ID $request_id;
        }
    }
}

عمداً پاسخ ۴۰۴ و ۵۰۲ را کش نمی‌کنیم؛ فقط status ۲۰۰ برای catalog و ۲۰ ثانیه. کلید شامل host و URI است. endpoint آزمایشی نه cookie دارد نه هویت کاربر. هدر X-Cache-Status روی پاسخ خطا هم برای تشخیص می‌آید؛ لاگ، دلیل را کامل‌تر نشان می‌دهد. nodelay burst را فوری می‌فرستد و فراتر از ظرفیت، رد می‌کند؛ rate limit ضدربات کامل نیست.

Only catalog 200 responses are cached, for 20 seconds; 404/502 are excluded. The key includes host and URI. The fixture has no cookies or user identity. X-Cache-Status is emitted even on errors for diagnosis; logs provide more context. nodelay sends the configured burst immediately and rejects excess; this is not complete bot protection.

تنظیم passive failure در upstream با درخواست واقعی backend خراب را موقتاً کنار می‌گذارد؛ اگر فقط یک backend سالم باقی بماند، آن یکی پاسخ می‌دهد. وقتی تنها یک سرور در گروه باشد یا همه خراب باشند، نتیجه می‌تواند خطای ۵۰۲ باشد. Nginx Open Source اینجا probe دوره‌ای یا health endpoint خودکار انجام نمی‌دهد؛ مستندات NGINX Plus را با قابلیت رایگان اشتباه نگیر.

Passive upstream failure temporarily avoids a backend after real request failures; if one peer remains healthy, it can answer. With one peer or all peers failed, clients may get 502. This Open Source config does not perform periodic probes or automatically call a health endpoint; do not confuse NGINX Plus documentation with free-edition behavior.

اعمال امن، rollback، و آزمون دوبارهSafe apply, rollback, and retest

قبل از reload یک کپی از فایل پیکربندی بگیر. در container آزمایش، nginx -t را اجرا کن؛ اگر موفق شد reload کن. اگر candidate رد شد، چیزی reload نکن و درخواست سالم قبلی را دوباره بزن. پیکربندی نحو را می‌سنجد، نه دسترس‌پذیری همهٔ سرویس‌ها.

Back up the config before reload. Run nginx -t in the test container; reload only if it passes. If the candidate is rejected, do not reload and retest the previous working request. Config test checks syntax and referenced files, not reachability of every service.

keep a named known-good config, then test and reload
cp nginx/nginx.conf nginx/nginx.conf.known-good
docker compose exec nginx nginx -t
docker compose exec nginx nginx -s reload
curl -k -i https://localhost:8443/catalog/featured

برای rollback، فقط فایل Nginx را از نسخهٔ known-good برگردان، دوباره test و reload کن و همان مجموعهٔ acceptance test را اجرا کن. volume یا دادهٔ سرویس‌ها را پاک نکن؛ rollback یک تغییر proxy نباید lifecycle داده را دست‌کاری کند.

For rollback, restore only the known-good Nginx file, test and reload again, then repeat the same acceptance tests. Do not remove volumes or service data; rolling back a proxy change must not alter data lifecycle.

این نمونه با Composeِ محلی برای تمرین است. مسیر `/var/cache/nginx` داخل container قرار دارد و پس از جایگزینی container ممکن است کش خالی شود؛ این برای کش قابل بازسازی قابل‌قبول است. لاگ‌های container را با docker compose logs می‌خوانی و رفتار نگهداری آن‌ها به ثبت لاگ driver میزبان بستگی دارد.

This is a local Compose lab. The cache under `/var/cache/nginx` is inside the container and may be empty after replacement; that is acceptable for rebuildable cache. Read container logs with docker compose logs; retention behavior depends on the host logging driver.

یادداشت incident: سیستم چه چیزی را ثابت کرد؟Incident note: what did the system prove?

پایان پروژه یک یادداشت incident است، نه جمع‌بندی تزئینی. سه خرابی را ثبت کن و برای هرکدام چهار چیز داشته باش: نشانه، شواهد، فرضیهٔ ردشده و آزمون بعد از repair. اگر فقط «مشکل حل شد» بنویسی، مهم‌ترین بخش مأموریت را از دست داده‌ای.

The project ends with an incident note, not a decorative summary. Record three failures and, for each, include the symptom, evidence, a rejected hypothesis, and the post-repair test. Writing only “issue resolved” misses the most important part of the mission.
