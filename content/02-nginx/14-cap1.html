Project 1 — a static site with HTTPS

حالا دیگر تمرین جداگانه نداریم؛ یک سایت واقعی تحویل می‌دهیم. از یک پوشهٔ فایل شروع می‌کنی و باید به جایی برسی که دامنه، HTTPS، کش، فشرده‌سازی، لاگ و rollback کنار هم کار کنند. هر مرحله فقط وقتی تمام است که بتوانی با یک آزمون مشخص نشان بدهی درست شده.

Now the isolated exercises stop and a real site must be delivered. You start with a folder of files and finish with DNS, HTTPS, caching, compression, logging, and rollback working together. A checkpoint is complete only when a concrete test demonstrates that it works.

مأموریت: از پوشه تا آدرس عمومیMission: from a folder to a public address

یک پوشهٔ آماده داری و یک دامنه که باید تا پایان مأموریت واقعاً به همان محتوا برسد. قرار نیست فصل‌های قبلی را دوباره تعریف کنیم؛ هر checkpoint بخشی از همان سیستم است. وقتی چیزی شکست، از همان عادت دوره استفاده کن: درخواست مشخص، نشانهٔ مشخص، یک تغییر، و دوباره همان آزمون.

You have a ready folder and a domain that must genuinely serve that content by the end of the mission. We will not reteach the previous chapters; every checkpoint is part of one system. When something breaks, use the same habit as the course: one specific request, one signal, one change, then the same test again.

در فصل‌های قبلی فایل استاتیک، TLS، لاگ و عیب‌یابی را جدا دیده‌ای. حالا قرار نیست درسشان را تکرار کنیم؛ باید در یک سیستم واقعی کنار هم درست کار کنند.

Earlier chapters covered static files, TLS, logs, and diagnosis separately. We will not repeat those lessons; now you must make them work together on a real system.

فلش افقی یعنی resolve دامنه و رسیدن درخواست؛ فلش عمودی یعنی خواندن فایل از root. کلید خصوصی TLS جزو محتوا یا Git نیست.

The horizontal arrow is DNS resolution and the request arriving; the vertical arrow is Nginx reading from the document root. The TLS private key is not site content or a Git artifact.

نقطهٔ ۲: ریشهٔ فایل و پاسخ HTTPCheckpoint 2: document root and HTTP response

مسیر روشن انتخاب کن، مثلاً /var/www/codenames. deploy user باید بنویسد و worker Nginx باید بخواند/از parentها عبور کند؛ پوشه را world-writable نکن. پیش از کپی، vhostهای فعال را ببین تا default site را ناخواسته overwrite نکنی.

Choose a clear path such as /var/www/codenames. The deploy user must write, and the Nginx worker must read/traverse; do not make it world-writable. Inspect active vhosts before copying so you do not overwrite the default site accidentally.

inspect first; adapt group and layout to this host
sudo nginx -t
sudo nginx -T 2>&1 | less
sudo ls -la /etc/nginx/sites-enabled/
sudo install -d -o "$USER" -g www-data -m 0755 /var/www/codenames
sudo install -d -o "$USER" -g www-data -m 0755 /var/www/codenames/assets
install -m 0644 site/index.html /var/www/codenames/index.html
install -m 0644 site/assets/site.1.css /var/www/codenames/assets/site.1.css

install -d مالکیت و mode پوشه‌های جدید را مشخص می‌کند و فایل‌ها ۰۶۴۴ می‌شوند. اگر group میزبان فرق دارد، user worker را از پیکربندی/پردازه واقعی پیدا کن؛ ۷۷۷ راه‌حل نیست.

install -d sets ownership/mode on new directories; files are 0644. If the host uses another group, identify the actual worker from config/processes; 777 is not a fix.

از host مستقل curl -i http://DOMAIN/ را بزن و asset را هم جدا بگیر. ۲۰۰ و متن صفحه رسیدن به فایل را ثابت می‌کند، نه درست‌بودن CSS.

From another host, run curl -i http://DOMAIN/ and fetch the asset separately. A 200 and page text prove the file was reached, not that CSS works.

برای اینکه مرحلهٔ بعد بازتولیدپذیر باشد، پیش از گواهی یک vhost سادهٔ HTTP با همان root و مسیر challenge بساز؛ فعلاً redirect نگذار تا پاسخ عادی را از بیرون ببینی.

For a reproducible next step, create a simple HTTP vhost with the same root and challenge path before requesting a certificate; do not redirect yet, so you can verify normal content externally.

bootstrap HTTP vhost; replace domain, test, then reload
server {
    listen 80;
    server_name example.org www.example.org;
    root /var/www/codenames;
    index index.html;
    location ^~ /.well-known/acme-challenge/ {
        root /var/www/codenames;
        default_type text/plain;
    }
    location / { try_files $uri $uri/ =404; }
}
sudo nginx -t && sudo systemctl reload nginx
curl -i http://example.org/

نقطهٔ ۳: دامنه و گواهی واقعیCheckpoint 3: real domain and certificate

پیش از Certbot، DNS را از resolver عمومی ببین و از بیرون مطمئن شو port 80 به Nginx می‌رسد. A و AAAA را جدا بسنج؛ AAAA قدیمی می‌تواند بخشی از کاربران را به میزبان اشتباه بفرستد.

Before Certbot, inspect DNS through a public resolver and confirm from outside that port 80 reaches Nginx. Check A and AAAA separately; a stale AAAA can send some users elsewhere.

replace the hostname with a domain you control
DOMAIN=example.org
dig +short A "$DOMAIN"
dig +short AAAA "$DOMAIN"
curl -i --max-time 5 "http://$DOMAIN/"
sudo certbot --version

دستور نصب Certbot را از راهنمای رسمی همان OS و روش نصب بگیر؛ packageها و renewal timer ممکن است فرق کنند. وقتی DNS، HTTP و فایروال آماده‌اند، webroot روش صدور را با فایل challenge در همان document root انجام می‌دهد.

Get Certbot installation steps from the official instructions for your OS/install method; packages and renewal timers vary. Once DNS, HTTP, and firewalls are ready, the webroot authenticator validates using a challenge file in that document root.

اگر نمی‌خواهی نام www هم داشته باشی، آن را از هر دو جا حذف کن؛ هر نامی که در cert می‌آید باید DNS و HTTP درست داشته باشد.

If you do not want a www name, remove it from both places; every name on the certificate needs working DNS and HTTP reachability.

issue only for real domains; Certbot may ask for email and consent
sudo certbot certonly --webroot -w /var/www/codenames -d "$DOMAIN" -d "www.$DOMAIN"

پس از موفقیت مسیر fullchain و privkey را در TLS server block بگذار. کلید خصوصی معمولاً root-readable است؛ permission آن را باز نکن و به Git نفرست. مدرک: hostname واقعی در فهرست گواهی و challenge قابل‌دسترسی. self-signed در VM فقط TLS محلی را نشان می‌دهد، نه اعتماد عمومی.

After issuance, use the fullchain/private-key paths in the TLS server block. The private key is normally root-readable; do not loosen access or commit it. Evidence: the real hostname appears in the certificate listing and the challenge is reachable. A self-signed VM cert demonstrates local TLS, not public trust.

نقطهٔ ۴: HTTPS، gzip و کشCheckpoint 4: HTTPS, gzip, and caching

HTTP را به HTTPS هدایت کن، اما مسیر /.well-known/acme-challenge/ را برای اعتبارسنجی/تمدید سروشدنی نگه دار. حالا عمداً یک قانون کش بد وارد کن: همهٔ فایل‌ها، حتی HTML، یک سال immutable باشند. با هدر پاسخ توضیح بده چرا صفحهٔ اصلی بعد از deploy ممکن است کهنه بماند.

Redirect HTTP to HTTPS, but keep /.well-known/acme-challenge/ available for validation/renewal. Now deliberately add a bad cache rule: every file, including HTML, is immutable for a year. Use response headers to explain why the homepage may remain stale after deployment.

observe headers before repairing the cache rule
curl -sSI "https://$DOMAIN/" | grep -iE '^(HTTP/|cache-control:|location:)'
curl -sSI "https://$DOMAIN/assets/site.1.css" | grep -iE '^(HTTP/|cache-control:)'
sudo nginx -t

HTML باید دوباره بررسی شود؛ asset نسخه‌دار می‌تواند کش طولانی بگیرد. پیکربندی خوب را بیرون web root backup کن، فقط rule را جدا کن، test و reload بگیر، بعد همان هدرها را دوباره ببین. برای gzip از CSS starter که از حداقل نمونه بزرگ‌تر است با Accept-Encoding: gzip درخواست کن و Content-Encoding/Vary را بخوان. gzip روی فایل کوچک هم ممکن است سربار اضافه کند؛ نبود هدر برای پاسخ زیر gzip_min_length الزاماً خطا نیست.

HTML should revalidate; versioned assets can use longer caching. Back up known-good config outside the web root, change only that rule, test/reload, and inspect the same headers again. Request the starter CSS, which exceeds the sample minimum, with Accept-Encoding: gzip and inspect Content-Encoding/Vary. Gzip can add overhead to tiny files; a missing header below gzip_min_length is not automatically a fault.

verify redirect, normal certificate validation, gzip, and renewal path
curl -sSI "http://$DOMAIN/"
curl -sSI "https://$DOMAIN/"
curl -sD - -o /dev/null -H 'Accept-Encoding: gzip' "https://$DOMAIN/assets/site.1.css"
sudo certbot renew --dry-run

از HTTP باید Location: https://... ببینی؛ curl بدون گزینهٔ دورزدن گواهی، hostname/chain را بررسی می‌کند. dry-run تمدید، مسیر آزمایشی را می‌سنجد نه تمدید فوری cert تولیدی را. exit code و timer واقعی package را ثبت کن.

HTTP should show a Location: https://.... Curl without certificate-bypass options validates hostname/chain. Renewal dry-run tests the staging renewal path; it does not renew the production certificate now. Record exit status and the package’s actual timer.

نقطهٔ ۵: لاگ، خرابی عمدی و rollbackCheckpoint 5: logs, deliberate fault, and rollback

حالا بخشی را خراب می‌کنیم که معمولاً دیر خودش را نشان می‌دهد: سیاست کش HTML. یک نسخهٔ سالم را کنار نگه دار، تغییر بد را اعمال کن، هدر اشتباه را ثبت کن و بعد rollback کن. هدف فقط برگشتن سایت نیست؛ باید بتوانی نشان بدهی قبل و بعد دقیقاً چه چیزی عوض شد.

Now we break a part that often fails quietly: the HTML cache policy. Keep a known-good configuration, apply the bad change, capture the wrong header, then roll back. The goal is not merely to restore the site; show exactly what changed before and after.

save the known-good config and inspect this vhost’s logs
sudo cp /etc/nginx/sites-available/codenames.conf \
  "$HOME/codenames.conf.known-good"
sudo tail -n 30 /var/log/nginx/codenames.access.log
sudo tail -n 30 /var/log/nginx/codenames.error.log

پس از تشخیص، پیکربندی سالم را برگردان، nginx -t بگیر و فقط در صورت موفقیت reload کن. اگر test fail شد، reload نکن. همان curl HTTPS و هدر را تکرار کن و خروجی را ثبت کن. rollback هم باید مدرک داشته باشد.

After diagnosis, restore the known-good config, run nginx -t, and reload only if it passes. If the test fails, do not reload. Repeat the same HTTPS/header curl and record it. Rollback needs evidence too.

معیار تحویل: هر ادعا یک شاهد می‌خواهدAcceptance: every claim needs evidence

تحویل را با جملهٔ «برای من باز شد» قبول نکن. برای DNS، HTTP→HTTPS، certificate، فایل اصلی، asset، کش، gzip، لاگ و rollback یک شاهد کوتاه داشته باش. اگر همکار دیگری با همین گزارش نتواند نتیجه را تکرار کند، runbook هنوز ناقص است.

Do not accept “it opened for me” as delivery. Keep a small piece of evidence for DNS, HTTP→HTTPS, certificate, main HTML, asset caching, gzip, logs, and rollback. If another engineer cannot reproduce the result from the report, the runbook is incomplete.

۱. دامنه به IP نمی‌رسد1. Domain does not reach the IP

A و AAAA را جدا ببین. فایروال میزبان و ارائه‌دهنده دو مرزند. پیش از UFW، SSH را مجاز بگذار.

Inspect A and AAAA separately. Host/provider firewalls are distinct. Allow SSH before enabling UFW.

۲. ۴۰۳ یا ۴۰۴2. 403 or 404

همان URL را با لاگ خطا تطبیق بده؛ root، وجود index و دسترسی worker به parentها را بررسی کن. این دو status را یکی فرض نکن.

Correlate the URL with error logs; check root, index, and worker traversal of parents. Do not treat the statuses as the same.

۳. Certbot شکست می‌خورد3. Certbot fails

challenge باید از اینترنت روی port 80 به webroot درست برسد. DNS، location challenge و هر دو فایروال را بررسی کن. اگر کنترل دامنه نداری، محدودیت را ثبت کن.

The challenge must reach the correct webroot from the internet on port 80. Check DNS, challenge location, and both firewalls. If you lack domain control, document the limit.

۴. CSS قدیمی است4. CSS is stale

هدر صفحه و asset را جدا ببین. فایل immutable را با overwrite همان نام تازه نمی‌کنی؛ filename نسخه‌دار جدید بده و HTML را revalidate کن.

Inspect page and asset headers separately. Overwriting an immutable filename does not refresh it; publish a new versioned name and revalidate HTML.

مرجع پیاده‌سازی: پس از ساخت خودت مقایسه کنReference implementation: compare after your build

راه‌حل مرجع را مثل جواب امتحان نخوان؛ آن را بعد از اجرای خودت باز کن و اختلاف‌ها را پیدا کن. مسیرها و includeهای نصب تو ممکن است فرق کنند، پس کپی‌کردن این فایل بدون تطبیق با nginx -T دقیقاً خلاف چیزی است که در فصل ۱ یاد گرفتیم.

Do not read the reference as an answer sheet. Open it after your own implementation and compare differences. Your installation paths and includes may differ, so copying it without reconciling nginx -T would violate the habit built in Chapter 1.

vhost reference; use the actual domain/cert paths
server {
    listen 80;
    server_name example.org www.example.org;
    root /var/www/codenames;
    index index.html;
    location ^~ /.well-known/acme-challenge/ {
        root /var/www/codenames;
        default_type text/plain;
    }
    location / { return 301 https://example.org$request_uri; }
}

server {
    listen 443 ssl;
    server_name example.org www.example.org;
    root /var/www/codenames;
    index index.html;
    ssl_certificate     /etc/letsencrypt/live/example.org/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.org/privkey.pem;
    access_log /var/log/nginx/codenames.access.log;
    error_log  /var/log/nginx/codenames.error.log warn;

    gzip on;
    gzip_vary on;
    gzip_min_length 20;
    gzip_types text/plain text/css application/javascript application/json image/svg+xml;

    location ^~ /.well-known/acme-challenge/ {
        root /var/www/codenames;
        default_type text/plain;
    }
    location = / {
        add_header Cache-Control "no-cache";
        try_files /index.html =404;
    }
    # Use immutable only while filenames are versioned and never overwritten.
    location /assets/ {
        try_files $uri =404;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }
    location / {
        try_files $uri $uri/ =404;
        add_header Cache-Control "no-cache";
    }
    location ~ /\.(?!well-known) { deny all; }
}

add_header وراثتش به directiveهای location والد/فرزند وابسته است؛ به همین دلیل هر location اینجا هدر موردنظرش را می‌گوید. MIME types را از include سراسری نصب تأمین کن. پیکربندی را بیرون web root backup بگیر؛ اگر symlink از قبل هست، مقصدش را بررسی کن و دوباره نساز.

add_header inheritance depends on parent/child location directives, so each location states its intended header. Use the installation’s global MIME types include. Back up config outside the web root; if a symlink already exists, inspect its target rather than recreating it.

فایل را در sites-available بگذار. اگر symlink فعال وجود ندارد بساز؛ اگر هست، مقصدش را اول بررسی کن. بعد test باید پیش از reload موفق شود.

Place the file in sites-available. Create the enabled symlink only if it is absent; inspect an existing target first. Config test must pass before reload.

enable only when the expected link is absent
sudo install -m 0644 codenames.conf /etc/nginx/sites-available/codenames.conf
if [ ! -e /etc/nginx/sites-enabled/codenames.conf ]; then
  sudo ln -s /etc/nginx/sites-available/codenames.conf /etc/nginx/sites-enabled/codenames.conf
else
  sudo readlink -f /etc/nginx/sites-enabled/codenames.conf
fi
sudo nginx -t && sudo systemctl reload nginx
test before reload; rollback only the named config file
sudo cp /etc/nginx/sites-available/codenames.conf \
  "$HOME/codenames.conf.before-change"
sudo nginx -T 2>&1 | less
