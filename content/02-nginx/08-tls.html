HTTPS، Let's Encrypt، تمدید خودکار

HTTPS, Let's Encrypt, auto-renewal

سایت باز می‌شود، اما مرورگر کنار نشانی هشدار می‌دهد. «قفل» فقط یعنی داده رمز شده؟ گواهی از کجا می‌فهماند به همان دامنه وصل شده‌ایم، و اگر چند ماه بعد تمدید نشود چه؟ این بار مسیر را از handshake تا تمدید دنبال می‌کنیم.

The site opens, but the browser warns beside its address. Does the lock only mean the data is encrypted? How does a certificate show that we reached the intended hostname, and what happens if it is not renewed months later? We will follow the path from handshake to renewal.

هشدار مرورگر را با یک دستور خاموش نکنیمDo not silence the browser warning with one flag

در فصل قبل درخواست را از Nginx به چند برنامه رساندیم. حالا کاربر از اینترنت به Nginx می‌رسد، اما مرورگر مطمئن نیست اتصال واقعاً به دامنهٔ موردنظر ختم شده باشد. شاید گواهی خودامضاست، نامش نمی‌خواند یا زنجیره ناقص است. هرکدام علت متفاوتی دارد.

In the previous chapter, Nginx routed requests to several apps. Now a user reaches Nginx over the internet, but the browser cannot confirm that the connection belongs to the intended hostname. The certificate may be self-signed, its name may not match, or its chain may be incomplete. Each has a different cause.

اول یک گواهی خودامضای محلی می‌سازیم تا Nginx را روی TLS تنظیم کنیم. این گواهی برای دامنهٔ عمومی اعتماد مرورگر نمی‌سازد؛ فقط آزمایش می‌کنیم وقتی خودمان گواهی را به ابزار اعتماد می‌دهیم، چه چیزی عوض می‌شود.

First we will make a local self-signed certificate and configure Nginx for TLS. It does not create browser trust for a public site; we will only see what changes when we explicitly tell a tool to trust this certificate.

این گزینه راه‌حل HTTPS نیستThis flag is not an HTTPS fix

در آزمایش‌ها گاهی curl -k می‌بینی. این گزینه بررسی گواهی را کنار می‌گذارد؛ پس فقط برای دیدن رفتار یک سرویس آزمایشی به کارش می‌بریم، نه برای اعلام «سایت امن شد». اگر بررسی نام و اعتماد برایت مهم است، درخواست معتبر را بدون -k بفرست.

Some tests use curl -k. It skips certificate verification, so we use it only to inspect a disposable test service—not to claim a site is secure. When hostname and trust matter, make a verified request without -k.

TLS کجا تمام می‌شود؟Where does TLS end?

کاربر به Nginx وصل می‌شود و Nginx گواهی را ارائه می‌کند. اگر برنامه پشت آن HTTP باشد، رمزگشایی در Nginx تمام می‌شود و درخواست تا برنامه روی مسیر داخلی رمزگذاری نشده است. این معماری رایج است، اما باید بدانیم مرز رمزگذاری دقیقاً کجاست.

The client connects to Nginx, which presents the certificate. If the upstream app uses HTTP, TLS ends at Nginx and the internal hop is not encrypted. This is common, but we should know exactly where the encryption boundary lies.

فلش آبی اتصال HTTPS مرورگر تا Nginx است؛ Nginx در این نقطه TLS را تمام می‌کند. فلش خاکستری مسیر جداگانه تا برنامه است و در آزمایش ما HTTP است. TLS روی مسیر داخلی انتخاب دیگری است، نه ادامهٔ خودکار اتصال اول.

The blue arrow is the browser’s HTTPS connection to Nginx; TLS ends there. The gray arrow is a separate hop to the app and uses HTTP in this lab. TLS on the internal hop is a separate choice, not an automatic continuation of the first connection.

در handshake، Nginx گواهی و مدرکی وابسته به کلید خصوصی ارائه می‌کند. مرورگر نام دامنه را با نام‌های ثبت‌شده در گواهی می‌سنجد و زنجیره را تا یک مرجع مورداعتماد دنبال می‌کند. کلید خصوصی باید فقط روی سرور بماند؛ گواهی عمومی را می‌شود منتشر کرد، اما کلید را نه.

During the handshake, Nginx presents a certificate and proves possession of the corresponding private key. The browser checks the hostname against names in the certificate and builds a chain to a trusted authority. The private key stays on the server; the public certificate may be shared, but the key must not.

اول یک گواهی محلی بسازیمFirst, make a local certificate

گواهی عمومی نیازمند دامنه و دسترسی از اینترنت است؛ هنوز به آن مرحله نرسیده‌ایم. برای فهم تنظیم Nginx یک گواهی کوتاه‌عمر برای localhost می‌سازیم و همه‌چیز را داخل پوشهٔ موقت نگه می‌داریم.

A public certificate requires a domain and internet reachability; we are not there yet. To understand the Nginx configuration, we will create a short-lived certificate for localhost and keep everything in a temporary directory.

این آزمایش به Linux، OpenSSL و Nginx نیاز دارد. پیش از ساخت فایل‌ها نسخهٔ OpenSSL و آزادبودن دو پورت آزمایش را بررسی کن. اگر پورت اشغال است، آزمایش را متوقف کن و شماره‌های تازه را در همهٔ فرمان‌ها یکسان جایگزین کن.

This experiment needs Linux, OpenSSL, and Nginx. Before creating files, check the OpenSSL version and whether both test ports are free. If a port is occupied, stop and choose new numbers consistently throughout the commands.

check local prerequisites and create an isolated directory
openssl version
nginx -v
if command -v ss >/dev/null; then
  ss -ltn | grep -E ':(18080|18443)([[:space:]]|$)' || true
fi
TLS_LAB=$(mktemp -d /tmp/nginx-tls.XXXXXX)
chmod 700 "$TLS_LAB"
mkdir -p "$TLS_LAB/logs" "$TLS_LAB/run"
printf 'Temporary lab: %s\n' "$TLS_LAB"
OpenSSL 3.x.x ...
nginx version: nginx/1.x.x
Temporary lab: /tmp/nginx-tls.A1b2C3

عدد نسخه و نام پوشه برای هر سیستم فرق می‌کند. اگر پورت‌ها در خروجی ss بودند، سراغ kill کردن پردازه نرو؛ پورت‌های آزاد دیگری انتخاب کن. اگر Nginx یا OpenSSL در دسترس نیست، فعلاً فرمان نصب را از مستند رسمی همان توزیع پیدا کن، نه یک بستهٔ تصادفی.

The versions and directory name vary. If ss shows either port, do not kill the process; choose different free ports. If Nginx or OpenSSL is unavailable, consult the official instructions for your distribution rather than installing a random package.

اکنون گواهی و کلید را می‌سازیم. نام localhost در Subject Alternative Name قرار می‌گیرد؛ مرورگرهای امروزی برای تطبیق نام به SAN نگاه می‌کنند، نه فقط Common Name قدیمی.

Now create the certificate and key. The name localhost goes into Subject Alternative Name (SAN); modern clients use SAN for hostname matching, not only the older Common Name field.

create a short-lived self-signed test certificate
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout "$TLS_LAB/localhost.key" \
  -out "$TLS_LAB/localhost.crt" \
  -days 2 -subj '/CN=localhost' \
  -addext 'subjectAltName=DNS:localhost,IP:127.0.0.1'
chmod 600 "$TLS_LAB/localhost.key"
openssl x509 -in "$TLS_LAB/localhost.crt" -noout \
  -subject -issuer -dates -ext subjectAltName
subject=CN = localhost
issuer=CN = localhost
notBefore=...
notAfter=...
X509v3 Subject Alternative Name:
    DNS:localhost, IP Address:127.0.0.1

یکسان بودن issuer و subject می‌گوید گواهی خودامضاست؛ تاریخ‌ها عمر کوتاهش را نشان می‌دهند و SAN نام‌هایی را که برایشان صادر شده مشخص می‌کند. این خروجی هنوز نمی‌گوید Nginx آن را ارائه می‌کند یا کلاینت به آن اعتماد دارد.

Matching issuer and subject indicate a self-signed certificate; the dates show its short lifetime, and SAN lists the names it covers. This output does not yet prove Nginx serves it or that a client trusts it.

حالا Nginx را روی پورت‌های loopback تنظیم می‌کنیم. فرمان‌ها از prefix موقت استفاده می‌کنند تا فایل‌های تنظیم، PID و log در مسیر آزمایش بمانند؛ به تنظیم Nginx سیستم دست نمی‌زنیم.

Now configure Nginx on loopback ports. These commands use a temporary prefix so the config, PID, and logs stay in the lab; they do not modify the system Nginx configuration.

configure a private local HTTP-to-HTTPS redirect and TLS endpoint
cat > "$TLS_LAB/nginx.conf" <<'NGINX'
worker_processes 1;
pid run/nginx.pid;
error_log logs/error.log notice;
events { worker_connections 64; }
http {
    access_log logs/access.log;
    server {
        listen 127.0.0.1:18080;
        server_name localhost;
        return 301 https://localhost:18443$request_uri;
    }
    server {
        listen 127.0.0.1:18443 ssl;
        server_name localhost;
        ssl_certificate     localhost.crt;
        ssl_certificate_key localhost.key;
        ssl_protocols TLSv1.2 TLSv1.3;
        location / { return 200 "TLS ends at Nginx\n"; }
    }
}
NGINX
nginx -t -p "$TLS_LAB/" -c nginx.conf
nginx: the configuration file .../nginx.conf syntax is ok
nginx: configuration file .../nginx.conf test is successful

دو خط ssl_certificate فایل گواهی و کلید را می‌خوانند؛ چون مسیر نسبی است، Nginx آن‌ها را زیر prefix آزمایش پیدا می‌کند. nginx -t نحو و فایل‌ها را می‌سنجد، اما هنوز handshake یا نام دامنه را ثابت نمی‌کند. اگر خطا دیدی مسیر و دسترسی فایل کلید را بررسی کن.

The two ssl_certificate directives load the certificate and key; because the paths are relative, Nginx finds them under the lab prefix. nginx -t checks syntax and files, but proves neither a handshake nor hostname validation. If it fails, inspect paths and key-file permissions.

قبل از start، test موفق را شرط می‌گذاریم. بعد درخواست را با CAای که همین حالا ساخته‌ایم می‌فرستیم. این بار اعتبارسنجی خاموش نمی‌شود: خودمان گواهی self-signed را به‌عنوان مرجع اعتماد همین درخواست معرفی می‌کنیم.

We require the successful config test before starting. Then we send a request using the certificate we just created as the trust anchor for this request. Verification stays enabled: we explicitly trust this self-signed certificate for this test.

start, verify TLS and hostname, then inspect the redirect
nginx -p "$TLS_LAB/" -c nginx.conf
curl --cacert "$TLS_LAB/localhost.crt" \
  --resolve localhost:18443:127.0.0.1 \
  https://localhost:18443/
curl -sSI http://127.0.0.1:18080/hello
TLS ends at Nginx
HTTP/1.1 301 Moved Permanently
Location: https://localhost:18443/hello

درخواست HTTPS بدون خطای اعتبارسنجی و متن پاسخ، اتصال به همین گواهی و endpoint را ثابت می‌کند؛ درخواست HTTP هم Location مقصد را نشان می‌دهد. این هنوز گواهی مورداعتماد عمومی نیست، و redirect هم به‌تنهایی رمزگذاری را ثابت نمی‌کند.

The verified HTTPS request and response body prove this endpoint works with the explicitly trusted certificate; the HTTP request shows its redirect target. This is not a publicly trusted certificate, and a redirect alone does not prove encryption.

گواهی به یک نام می‌خورد، نه به هر نشانیA certificate covers names, not every address

TLS محلی جواب داد، اما آیا هر نامی که به همان IP برسد معتبر است؟ عمداً همان سرور را با نامی دیگر صدا می‌زنیم. پیش از دیدن خروجی حدس بزن: چون Nginx همان گواهی را می‌فرستد، کدام بررسی باید شکست بخورد؟

Local TLS worked, but is the certificate valid for every name that reaches the same IP? We will deliberately contact the same server with another hostname. Predict before running it: since Nginx serves the same certificate, which check should fail?

keep trust verification on and deliberately use the wrong hostname
curl --cacert "$TLS_LAB/localhost.crt" \
  --resolve other.test:18443:127.0.0.1 \
  https://other.test:18443/
curl: (60) SSL: no alternative certificate subject name matches
target hostname 'other.test'

اتصال شبکه برقرار شد، اما نام other.test در SAN گواهی نیست؛ به همین دلیل curl قبل از فرستادن درخواست HTTP آن را رد کرد. این مدرک می‌گوید نام با گواهی نمی‌خواند، نه اینکه کلید خراب است یا Nginx خاموش است. آدرس IP، server_name و SAN را از یک مسیر بررسی کن.

The network connection succeeded, but other.test is not in the certificate SAN, so curl rejected it before sending the HTTP request. This proves a hostname mismatch, not a broken key or a stopped Nginx process. Check the requested name, server_name, and SAN together.

برای دیدن گواهی‌ای که واقعاً از سرور برگشته، SNI را هم مشخص می‌کنیم. اگر چند سایت روی یک IP باشند، مقدار -servername تعیین می‌کند Nginx کدام virtual server را برای handshake انتخاب کند.

To inspect the certificate actually returned by the server, set SNI too. When several sites share an IP, -servername helps Nginx select the virtual server during the handshake.

inspect the served leaf certificate and its names
openssl s_client -connect 127.0.0.1:18443 \
  -servername localhost -showcerts </dev/null 2>/dev/null |
  openssl x509 -noout -subject -issuer -dates -ext subjectAltName
subject=CN = localhost
issuer=CN = localhost
notBefore=...
notAfter=...
X509v3 Subject Alternative Name:
    DNS:localhost, IP Address:127.0.0.1

این فرمان گواهی‌ای را که handshake تحویل داده می‌خواند؛ تاریخ‌ها، نام صادرکننده و SAN را می‌بینی. اگر خروجی خالی بود، ممکن است اتصال TLS اصلاً شکل نگرفته باشد یا چیزی جز گواهی موردانتظار پاسخ داده باشد؛ اول خطای s_client را جداگانه ببین.

This reads the certificate delivered by the handshake; inspect its dates, issuer, and SAN. If the output is empty, TLS may not have completed or the endpoint may have returned a different certificate. First inspect the s_client error on its own.

چرا یک گواهی تنها گاهی کافی نیست؟Why is one certificate sometimes not enough?

مرورگر معمولاً از قبل ریشه‌های مورداعتماد را دارد. گواهی سایت ممکن است با یک گواهی میانی امضا شده باشد؛ سرور باید زنجیرهٔ لازم را بفرستد تا کلاینت بتواند از گواهی دامنه به ریشهٔ شناخته‌شده برسد. کلید خصوصی عضو این زنجیرهٔ عمومی نیست.

Browsers usually already have trusted roots. A site certificate may be signed by an intermediate certificate; the server needs to send the required chain so the client can link the domain certificate to a known root. The private key is not part of this public chain.

فلش‌ها رابطهٔ امضا و بررسی زنجیره را نشان می‌دهند، نه اینکه کلید خصوصی میان این گواهی‌ها جابه‌جا شود. Nginx فایل full chain را می‌فرستد؛ کلاینت ریشه را از trust store خودش پیدا می‌کند.

Arrows show the certificate-signing and validation path, not private-key transfer. Nginx serves the full chain; the client finds the root in its own trust store.

در Nginx معمولاً ssl_certificate باید به fullchain.pem اشاره کند و ssl_certificate_key به privkey.pem. فرستادن فقط گواهی سایت می‌تواند روی دستگاهی که intermediate را cache ندارد خطای chain بسازد. نام فایل‌ها را از Certbot یا روش نصب خودت بخوان؛ مسیر یک توزیع را قانون همگانی فرض نکن.

In Nginx, ssl_certificate normally points to fullchain.pem, and ssl_certificate_key to privkey.pem. Serving only the leaf can break chain validation on clients that have not cached the intermediate. Read the paths from your Certbot or installation method; do not treat one distro’s paths as universal.

Let’s Encrypt از کجا می‌فهمد دامنه دست توست؟How does Let’s Encrypt know you control the domain?

مرورگر به گواهی اعتماد می‌کند، اما مرجع صدور باید پیش از آن مطمئن شود درخواست‌کننده کنترل دامنه را دارد. ACME این رفت‌وبرگشت را خودکار می‌کند. در روش HTTP-01، کلاینت ACME یک پاسخ کوتاه زیر مسیر ویژه قرار می‌دهد و Let’s Encrypt آن را از اینترنت می‌خواند.

The browser trusts the certificate, but the certificate authority first needs evidence that the requester controls the domain. ACME automates that exchange. With HTTP-01, the ACME client places a short response under a special path, and Let’s Encrypt fetches it from the internet.

فلش آبی مسیر گذاشتن challenge است؛ فلش خاکستری درخواست اعتبارسنج از اینترنت به سرور را نشان می‌دهد. موفقیت فقط وقتی ممکن است که DNS و دسترسی عمومی واقعاً به همین Nginx برسند.

The blue arrow is the challenge setup; the gray arrow is the validation fetch from the internet. Validation can succeed only when public DNS and network access reach this Nginx.

HTTP-01 از اینترنت و پورت ۸۰ شروع می‌شود؛ بازبودن 443 جای آن را نمی‌گیرد. دامنه باید به IP همین سرور برسد و درخواست مسیر challenge را همین Nginx یا front end موردانتظار پاسخ دهد. اگر رکورد AAAA داری، آن مسیر IPv6 هم باید درست و قابل‌دسترسی باشد؛ رکورد قدیمی IPv6 می‌تواند اعتبارسنجی را به جای دیگری ببرد.

HTTP-01 starts from the internet on port 80; an open 443 does not replace it. The hostname must resolve to this server, and this Nginx or the intended frontend must serve the challenge path. If an AAAA record exists, its IPv6 route must also be correct and reachable; a stale IPv6 record can send validation elsewhere.

پورت ۸۰ را برای همیشه نبند. HTTP می‌تواند فقط redirect بدهد، ولی لازم است درخواست challenge به شکل درست پاسخ بگیرد. Let’s Encrypt redirectهای محدود به HTTP/HTTPS روی پورت‌های ۸۰ و ۴۴۳ را دنبال می‌کند؛ روی redirect به پورت دلخواه تکیه نکن. اگر پورت ۸۰ واقعاً قابل‌استفاده نیست، به‌جای دستکاری فایروال از روش چالش مناسب مثل DNS-01 استفاده می‌شود.

Do not permanently close port 80. HTTP can serve only a redirect, but the challenge still needs a valid response. Let’s Encrypt follows a limited set of HTTP/HTTPS redirects on ports 80 and 443; do not rely on redirects to arbitrary ports. If port 80 is genuinely unavailable, use a suitable alternative such as DNS-01 instead of weakening the firewall.

Certbot چند جور می‌تواند challenge را انجام دهدCertbot can answer the challenge in several ways

اصل ماجرا یکی است—باید مدرک کنترل دامنه منتشر شود—اما جای نوشتن token فرق می‌کند. قبل از انتخاب، بپرس Nginx الان چطور فایل عمومی را جواب می‌دهد و چه کسی اجازه دارد تنظیم را reload کند.

The requirement is the same—a proof of domain control must be published—but the token can be placed in different ways. Before choosing, ask how Nginx serves public files now and who is allowed to reload its configuration.

Our main Linux-with-Nginx path uses Certbot’s Nginx plugin. Installation varies by distribution; follow Certbot’s current instructions for your system and do not mix package and snap installations without checking. اگر انتخابت webroot یا standalone است، شکل فرمان را مستند همان نسخه بگیر؛ معمولاً باید مسیر webroot را با -w بدهی یا مطمئن شوی پورت ۸۰ برای standalone آزاد است. این‌ها روش‌های جایگزین‌اند، نه فرمان‌هایی که پشت‌سرهم برای یک دامنه اجرا شوند.

If you choose webroot or standalone, get the exact command shape from your installed version’s docs; webroot usually needs a -w path, while standalone needs port 80 free. These are alternatives, not commands to run one after another for the same hostname.

حالا دامنهٔ واقعی را از بیرون بررسی کنیمNow check the real domain from outside

گواهی عمومی با نام دلخواه صادر نمی‌شود؛ باید کنترل نام دامنه ثابت شود. این بخش برای سرور Linux دارای دامنهٔ واقعی است. اگر فقط روی لپ‌تاپ یا VM محلی کار می‌کنی، آزمایش خودامضا کافی است و این فرمان‌های عمومی را اجرا نکن.

A public certificate is not issued for an arbitrary name; control of the hostname must be proven. This section is for a Linux server with a real domain. If you are working only on a laptop or local VM, the self-signed experiment is enough—do not run these public commands.

اول DNS و مسیر HTTP را بسنج. به‌جای اینکه حدس بزنی دامنه به سرور رسیده، رکوردها و پاسخ را ببین. نام دامنه را با دامنهٔ خودت جایگزین کن؛ example.com در این صفحه فقط نمونه است.

First test DNS and the HTTP path. Inspect records and responses instead of assuming the domain reaches the server. Replace the example name with your own; example.com on this page is only a placeholder.

verify public DNS, port 80 listener, and HTTP reachability
DOMAIN=www.example.com
dig +short A "$DOMAIN"
dig +short AAAA "$DOMAIN"
sudo ss -ltnp | grep -E ':(80|443)([[:space:]]|$)' || true
curl -sSI --max-time 5 "http://$DOMAIN/"
203.0.113.10
HTTP/1.1 200 OK
Server: nginx

نشانی 203.0.113.10 در نمونه برای مستندسازی است و IP واقعی تو نیست. رکورد A باید به IP عمومی سرور برسد؛ اگر AAAA داری، آن هم باید درست باشد. Nginx باید روی 80 گوش بدهد و firewall سرور و firewall شرکت میزبان راه HTTP را باز گذاشته باشند. اگر یکی از این‌ها غلط است، فعلاً Certbot را اجرا نکن.

The 203.0.113.10 value is documentation-only, not your server’s IP. The A record must reach the public server; any AAAA record must be correct too. Nginx must listen on port 80, and both the host and provider firewalls must allow HTTP. If any check is wrong, do not run Certbot yet.

وقتی HTTP از اینترنت جواب می‌دهد، Certbot می‌تواند challenge را با Nginx انجام دهد و تنظیم TLS را هم تغییر دهد. ابتدا از تنظیم‌ها نسخهٔ پشتیبان بگیر و آماده باش diff فایل را بخوانی؛ plugin کار را ساده می‌کند، اما جای بازبینی تنظیم تولیدی را نمی‌گیرد.

Once HTTP responds from the internet, Certbot can use Nginx for the challenge and edit the TLS configuration. Back up the relevant config and be ready to review the diff; the plugin simplifies the work but does not replace production review.

request and install a certificate for names you control
sudo certbot --nginx -d www.example.com
Congratulations! Your certificate and chain have been saved ...
Successfully deployed certificate for www.example.com to ...

در خروجی واقعی مسیرها و تاریخ‌ها فرق می‌کنند. گواهی فقط برای نام‌هایی صادر می‌شود که با -d آورده‌ای؛ اگر دامنهٔ اصلی و www هر دو لازم‌اند، هر دو را صریح اضافه کن. Certbot ممکن است برای redirect کردن HTTP به HTTPS سؤال کند؛ فقط بعد از اطمینان از پاسخ درست HTTPS گزینهٔ redirect را انتخاب کن. پیام موفقیت پایان کار نیست: تنظیم Nginx و پاسخ هر دو نشانی را بررسی می‌کنیم.

Paths and dates differ in real output. A certificate covers only the names passed with -d; list both the apex and www if you need both. Certbot may ask whether to redirect HTTP to HTTPS; choose that only after confirming HTTPS works. The success message is not the finish: inspect Nginx’s config and both URL responses.

برای دیدن نام‌ها و زمان انقضا از خود Certbot بپرس، بعد config و handshake عمومی را بررسی کن. verify return code: 0 نشانهٔ موفقیت بررسی OpenSSL است؛ به‌تنهایی درست‌بودن محتوای برنامه یا redirect را ثابت نمی‌کند.

Ask Certbot for the managed names and expiry, then check the config and public handshake. verify return code: 0 shows OpenSSL verification succeeded; it does not prove the app content or redirect is correct.

inspect the installed certificate and verify the public TLS endpoint
sudo certbot certificates
sudo nginx -t
curl -sSI "http://$DOMAIN/"
curl -sSI "https://$DOMAIN/"
openssl s_client -connect "$DOMAIN:443" \
  -servername "$DOMAIN" -verify_return_error </dev/null 2>&1 |
  grep -E 'subject=|issuer=|Verify return code'
HTTP/1.1 301 Moved Permanently
Location: https://www.example.com/...
HTTP/1.1 200 OK
Verify return code: 0 (ok)

این سه مدرک را جدا بخوان: 301 یعنی مسیر HTTP redirect می‌دهد؛ پاسخ 200 روی HTTPS یعنی همان URL با TLS جواب داده؛ verify code صفر یعنی زنجیره برای این OpenSSL قابل‌اعتبارسنجی است. اگر redirect مقصد دیگری داشت، پاسخ برنامه نبود یا گواهی نامناسب بود، همان مرز را جدا عیب‌یابی کن.

Read these as separate evidence: 301 means HTTP redirects; 200 over HTTPS means that URL answered with TLS; verify code zero means this OpenSSL instance could validate the chain. If the redirect target, app response, or certificate is wrong, debug that boundary separately.

گواهی صادر شد؛ حالا چه کسی مراقب انقضایش است؟The certificate is issued; who watches its expiry?

صدور یک‌بارِ گواهی آسان‌ترین قسمت است. چند ماه بعد ممکن است سرور عوض شده، DNS تغییر کرده یا تمدیدکننده خاموش باشد. تمدید خودکار یک فرمان جادویی نیست؛ یک زمان‌بند باید Certbot را اجرا کند و مسیر challenge همچنان باید کار کند.

One-time issuance is the easy part. Months later, the server may have changed, DNS may have moved, or the renewer may be disabled. Automatic renewal is not magic: a scheduler must run Certbot, and the challenge path must still work.

راهنمای رسمی Certbot برای بستهٔ انتخابی تو cron یا systemd timer معرفی می‌کند. اسم timer و روش نصب می‌تواند با توزیع و snap/package فرق داشته باشد؛ وجودش را از خروجی سیستم خودت ثابت کن، نه از حفظ‌کردن نام یک سرویس.

Certbot’s official instructions identify the cron job or systemd timer for your chosen package. Timer names and installation methods can differ between distributions and snap/package installs; prove what exists on your system rather than memorizing one service name.

find the renewal scheduler and rehearse renewal safely
systemctl list-timers --all | grep -i certbot || true
sudo certbot renew --dry-run
... certbot ... timer ...
Congratulations, all simulated renewals succeeded

خروجی timer نشان می‌دهد چه زمانی اجرا خواهد شد؛ --dry-run تمرین را با محیط آزمایشی انجام می‌دهد و گواهی production را عوض نمی‌کند. اگر timer پیدا نشد، cron و روش نصب را مطابق مستند Certbot همان سیستم بررسی کن. dry-run موفق، دسترسی ماه‌های آینده به DNS یا پورت ۸۰ را تضمین نمی‌کند؛ فقط تنظیم فعلی را تمرین می‌کند.

The timer output shows when the scheduler is expected to run; --dry-run rehearses against the staging environment without replacing the production certificate. If no timer appears, check cron and the installation method using Certbot’s instructions for that system. A successful dry run cannot guarantee future DNS or port-80 reachability; it tests the current setup.

روش نصب روی renewal هم اثر دارد. اگر Certbot با نصب‌کنندهٔ Nginx certificate را deploy می‌کند، رفتار همان renewal configuration را بررسی کن. اگر certonly داری، خودت باید بعد از صدور موفق Nginx را طوری reload کنی که گواهی تازه را بخواند؛ deploy hook یا روش مدیریت سرویس را مشخص و آزمایش کن. بدون reload، فایل تازه روی دیسک است ولی پردازه ممکن است هنوز گواهی قبلی را ارائه کند.

The installation mode also affects renewal. If Certbot’s Nginx installer deploys the certificate, inspect that renewal configuration. With certonly, arrange for Nginx to reload after a successful renewal—using a tested deploy hook or service-management method. Without a reload, the new file may be on disk while the running process still serves the old certificate.

«فایل تازه» با «گواهی تازه در حال سرو» فرق دارد“New file” is not the same as “new certificate served”

بعد از تغییر certificate، nginx -t و reload موفق را بررسی کن؛ سپس از بیرون دوباره تاریخ گواهی‌ای را که سرور ارائه می‌دهد بخوان. تمدید روی دیسک، پاسخ TLS پردازهٔ زنده را به‌تنهایی ثابت نمی‌کند.

After certificate changes, verify nginx -t and a successful reload, then inspect the dates on the certificate served externally. A renewed file on disk alone does not prove what the running TLS endpoint presents.

اگر تمرین renewal شکست خورد، پیش از restart کردن سرور چهار چیز را جدا کن: نام‌هایی که گواهی برایشان صادر شده، پاسخ DNS فعلی، دسترسی HTTP-01 از بیرون، و تنظیم renewal ذخیره‌شده. یک پیام timeout بیشتر به مسیر شبکه/DNS اشاره می‌کند؛ خطای config به Nginx؛ و خطای دسترسی فایل به کاربری که Certbot یا Nginx با آن اجرا می‌شود.

If the renewal rehearsal fails, separate four checks before restarting anything: names on the certificate, current DNS answers, external HTTP-01 reachability, and the saved renewal configuration. A timeout points toward network/DNS; a config error toward Nginx; and a file-access error toward the account running Certbot or Nginx.

inspect renewal configuration and recent Certbot evidence
sudo certbot certificates
sudo certbot renew --dry-run -v
sudo nginx -t
sudo journalctl --since '24 hours ago' --no-pager |
  grep -i certbot || true
sudo tail -n 30 /var/log/letsencrypt/letsencrypt.log
... simulated renewals succeeded ...
... certificate name and expiry ...
... inspect only logs that exist on this installation ...

ممکن است مسیر log یا جزئیات journal با بسته فرق کند؛ اگر فایل گفته‌شده وجود ندارد، مسیر نصب واقعی را پیدا کن، نه اینکه خروجی نمونه را عیناً انتظار داشته باشی. خطای dry-run و خطای روزمره را کنار هم بگذار و همان مرحلهٔ شکست‌خورده را پس از اصلاح تکرار کن.

Log paths and journal details can vary by package. If the shown file does not exist, find the path used by your installation rather than expecting sample output literally. Compare the dry-run error with the normal scheduler evidence, fix that boundary, and repeat the failed check.

HSTS را زودتر از آمادگی همهٔ دامنه فعال نکنDo not enable HSTS before every covered name is ready

redirect می‌گوید «این درخواست را به HTTPS بفرست». HSTS به مرورگر می‌گوید «دفعه‌های بعد خودت HTTPS را اجباری کن و هشدار گواهی را دور نزن». این دو یکی نیستند؛ مرورگر ممکن است دستور HSTS را مدتی به خاطر بسپارد.

A redirect says, “Send this request to HTTPS.” HSTS tells the browser, “Use HTTPS yourself next time and do not bypass certificate warnings.” They are different; the browser can remember an HSTS policy for a while.

قبل از افزودنش، دامنهٔ اصلی، renewal، redirect و همهٔ مسیرهای مورد استفاده را با HTTPS درست کن. اول فقط روی server مربوط به 443 و با زمان آزمایشی کوتاه شروع کن؛ includeSubDomains و preload را تا وقتی تک‌تک زیر‌دامنه‌ها آماده نیستند اضافه نکن.

Before adding it, make HTTPS work for the main hostname, renewal, redirects, and every required path. Start only on the 443 server with a short test duration; do not add includeSubDomains or preload until every subdomain is ready.

start with a short HSTS policy only after HTTPS works
# Inside the TLS (listen 443 ssl) server only:
add_header Strict-Transport-Security "max-age=300" always;

این مقدار پنج‌دقیقه‌ای فقط برای آزمایش است. اگر مرورگر آن را دریافت کرد، تا پایان max-age درخواست HTTP همان host را خودکار ارتقا می‌دهد؛ خطای گواهی هم دیگر راه دورزدن معمول ندارد. مقدار بلندمدت و مخصوصاً سیاست زیر‌دامنه‌ها یا preload می‌تواند دسترسی را تا رفع HTTPS در همهٔ دامنه‌های پوشش‌داده‌شده مختل کند.

This five-minute value is only for testing. Once a browser receives it, HTTP requests to that host are upgraded until max-age expires, and the usual certificate-error bypass is unavailable. A long-lived policy—especially subdomains or preload—can disrupt access until HTTPS is fixed for every covered hostname.

برای حذف سیاست، سرور باید روی HTTPS هدر max-age=0 بفرستد و مرورگر آن را دریافت کند؛ خاموش‌کردن header در config از راه HTTP به‌تنهایی سیاست ذخیره‌شده را پاک نمی‌کند. پس اول HSTS کوتاه، بعد مشاهده، و فقط پس از آمادگی کامل زمان بیشتر.

To clear a remembered policy, the server must send max-age=0 over HTTPS and the browser must receive it; merely removing the header from config cannot clear stored state over HTTP. Start short, observe, and lengthen it only when every covered name is ready.

No. First check the configured path, permissions, and nginx -t output. Reissuing does not magically restore the existing key and may consume issuance limits unnecessarily.

DNS reaches the right server, but curl reports a hostname error. Which three things do you compare?

URL درخواستی، SAN گواهی ارائه‌شده و virtual server انتخاب‌شده با SNI. یک IP درست تضمین نمی‌کند Nginx گواهی مربوط به همان hostname را فرستاده باشد.

Compare the requested URL, the served certificate’s SAN, and the virtual server selected through SNI. A correct IP does not guarantee Nginx served the certificate for that hostname.

تمرین ۴ · فقط leaf فرستاده شدهExercise 4 · Only the leaf was served

روی یک لپ‌تاپ سایت باز می‌شود ولی روی کلاینت تازه خطای chain می‌گیری. چه تفاوتی می‌تواند علت باشد؟

The site works on one laptop but a fresh client reports a chain error. What difference could explain it?

The older laptop may have cached an intermediate. Check that Nginx serves the full chain and use openssl s_client -showcerts to inspect what the server actually sends.

تمرین ۵ · دو اتصالExercise 5 · Two connections

TLS روی Nginx تمام می‌شود و upstream با HTTP است. کدام مسیر رمزگذاری نشده؟

TLS ends at Nginx and the upstream uses HTTP. Which hop is not encrypted?

پاسخ را ببینShow solution

مسیر جداگانهٔ Nginx تا برنامه. مرورگر تا Nginx HTTPS دارد، اما TLS خودبه‌خود از آن اتصال به upstream منتقل نمی‌شود؛ اگر threat model مسیر داخلی را لازم می‌داند، آن hop هم باید جداگانه امن شود.

The separate Nginx-to-app hop. The browser-to-Nginx connection uses HTTPS, but TLS does not automatically continue to the upstream; secure that hop separately if the threat model requires it.

تمرین ۶ · redirect کجا می‌رود؟Exercise 6 · Where does the redirect go?

HTTP returns 301, but the target is https://old.example. Is the setup ready?

پاسخ را ببینShow solution

نه؛ مقصد redirect را بررسی کن و ببین نام درست و گواهی معتبر دارد. 301 فقط مقصد را گزارش می‌کند و سلامت TLS آن مقصد را ثابت نمی‌کند.

No. Inspect the redirect target and verify its hostname and certificate. A 301 reveals the destination; it does not validate TLS there.

تمرین ۷ · 443 باز استExercise 7 · Port 443 is open

Certbot با HTTP-01 timeout می‌شود؛ مدیر می‌گوید پورت 443 باز است. کدام مسیر را باید بررسی کنی؟

Certbot times out with HTTP-01; an administrator says port 443 is open. Which path should you check?

پاسخ را ببینShow solution

HTTP-01 از پورت 80 می‌آید. رکورد A/AAAA، listener پورت 80، هر دو firewall و پاسخ مسیر challenge را بررسی کن؛ 443 جای پورت 80 را نمی‌گیرد.

HTTP-01 uses port 80. Check A/AAAA records, the port-80 listener, both firewalls, and the challenge path; 443 does not replace port 80.

IPv4 reaches the new VPS while IPv6 points to an old server. Why might issuance be unreliable?

پاسخ را ببینShow solution

اعتبارسنجی ممکن است از مسیر IPv6 به سرور دیگری برسد که challenge را ندارد. رکورد نادرست AAAA را اصلاح یا حذف کن و از چند resolver و مسیر بیرونی دوباره بررسی کن.

Validation may reach a different server over IPv6, where the challenge is absent. Fix or remove the stale AAAA record, then check again through external resolvers and paths.

تمرین ۹ · تنظیم‌ها دست خودم باشدExercise 9 · Keep config under my control

نمی‌خواهی Certbot فایل Nginx را ویرایش کند و webroot در دسترس عمومی است. کدام روش را بررسی می‌کنی؟

You do not want Certbot to edit Nginx config, and a public webroot is available. Which mode would you consider?

پاسخ را ببینShow solution

روش certonly --webroot را بررسی می‌کنم؛ token باید از مسیر .well-known/acme-challenge قابل‌خواندن باشد. مسیر webroot را حدس نمی‌زنم؛ با درخواست بیرونی ثابتش می‌کنم.

Consider certonly --webroot; the token must be reachable under .well-known/acme-challenge. Do not guess the webroot path—prove it with an external request.

تمرین ۱۰ · پورت ۸۰ اشغال استExercise 10 · Port 80 is busy

روش standalone انتخاب شده اما Nginx همین حالا روی پورت ۸۰ گوش می‌دهد. چرا شکست می‌خورد؟

Standalone mode is selected, but Nginx already listens on port 80. Why does it fail?

پاسخ را ببینShow solution

Certbot می‌خواهد موقتاً خودش همان پورت را بگیرد و نمی‌تواند تا وقتی Nginx مالک آن است bind کند. از Nginx/webroot plugin استفاده کن یا توقف برنامه‌ریزی‌شده و بازراه‌اندازی امن را طراحی کن؛ سرویس را ناگهانی متوقف نکن.

Certbot needs to bind that port temporarily and cannot while Nginx owns it. Use the Nginx/webroot plugin or plan a controlled stop and restart; do not interrupt the service blindly.

تمرین ۱۱ · dry-run موفقExercise 11 · Dry run succeeded

چه چیزی را ثابت می‌کند و چه چیزی را تضمین نمی‌کند؟

What does a successful dry run prove, and what does it not guarantee?

پاسخ را ببینShow solution

تنظیم فعلی renewal در محیط آزمایشی توانسته فرایند را طی کند. آیندهٔ DNS، firewall، دسترسی به حساب یا زنده‌بودن timer را تضمین نمی‌کند؛ آن‌ها را جدا بررسی کن.

The current renewal setup completed a rehearsal against the staging service. It does not guarantee future DNS, firewall, account access, or scheduler operation; verify those separately.

تمرین ۱۲ · timer پیدا نشدExercise 12 · No timer found

دستور systemctl list-timers | grep certbot چیزی نشان نمی‌دهد. آیا قطعاً تمدید خودکار نداریم؟

The timer search shows nothing. Does that prove automatic renewal is absent?

پاسخ را ببینShow solution

نه؛ شاید cron یا سازوکار بستهٔ snap/package استفاده شود، یا grep نام را پیدا نکرده باشد. نصب واقعی Certbot، cron و مستند همان سیستم را بررسی کن و بعد dry-run را اجرا کن.

Not necessarily; a cron job or package-specific scheduler may be used, or the search may miss its name. Inspect the actual Certbot installation, cron, and system-specific instructions, then run a dry run.

تمرین ۱۳ · گواهی تمدید شد ولی تاریخ بیرونی قدیمی استExercise 13 · Renewed file, old served date

روی دیسک تاریخ تازه می‌بینی ولی openssl s_client تاریخ قبلی را نشان می‌دهد. قدم بعدی؟

The disk file has a new expiry, but openssl s_client shows the old date. What next?

پاسخ را ببینShow solution

بررسی کن renewal مسیر deploy/reload دارد یا نه؛ بعد nginx -t و reload موفق را از journal ببین و دوباره endpoint بیرونی را inspect کن. فایل تازه به معنی خوانده‌شدن آن توسط پردازه نیست.

Check whether renewal has a deploy/reload step, then verify nginx -t and the reload in logs before inspecting the external endpoint again. A fresh file does not mean the running process loaded it.

تمرین ۱۴ · تاریخ انقضاExercise 14 · Expiry date

برای دیدن تاریخ گواهی‌ای که همین حالا سرور ارائه می‌کند چه ابزاری می‌زنی؟

Which tool can show the dates on the certificate currently served by the endpoint?

پاسخ را ببینShow solution

با openssl s_client به hostname و پورت وصل می‌شوم، SNI را می‌فرستم و گواهی برگشتی را به openssl x509 -noout -dates می‌دهم. این گواهی زنده را می‌سنجد، نه فقط فایل روی دیسک.

Connect with openssl s_client to the hostname and port, send SNI, and pipe the returned certificate to openssl x509 -noout -dates. This checks the live certificate, not merely a disk file.

تمرین ۱۵ · HSTS کوتاهExercise 15 · Short HSTS

چرا شروع با max-age=300 از یک‌سال کم‌ریسک‌تر است؟

Why is starting with max-age=300 lower risk than one year?

پاسخ را ببینShow solution

اگر redirect یا گواهی مشکل داشته باشد، مدت اجبار کوتاه‌تر در مرورگر ذخیره می‌شود و آزمایش برگشت‌پذیرتر است. این تضمین رفع فوری مشکل نیست؛ مرورگر باید زمان یا هدر پاک‌سازی را دریافت کند.

If the redirect or certificate is wrong, the browser remembers the policy for less time, making the test more reversible. It does not guarantee immediate recovery; the browser must wait or receive a clearing header.

تمرین ۱۶ · زیر‌دامنه‌های ناآمادهExercise 16 · Unready subdomains

دامنهٔ اصلی HTTPS دارد اما legacy.example.com فقط HTTP است. چه گزینه‌ای را فعلاً اضافه نمی‌کنی؟

The apex has HTTPS, but legacy.example.com is HTTP-only. Which option should you avoid for now?

پاسخ را ببینShow solution

includeSubDomains و در پی آن preload را اضافه نکن؛ ممکن است مرورگر legacy را هم مجبور به HTTPS کند. اول همهٔ زیر‌دامنه‌های مشمول را آماده و بررسی کن.

Do not add includeSubDomains or preload; browsers may force HTTPS on the legacy host too. Prepare and verify every covered subdomain first.

تمرین ۱۷ · گواهی صادر نمی‌شودExercise 17 · Issuance fails

خروجی challenge خطای 404 می‌دهد. به‌ترتیب چه مدرکی جمع می‌کنی؟

The challenge request returns 404. What evidence do you collect, in order?

پاسخ را ببینShow solution

نام و DNS resolve شده را ثبت کن؛ بعد از بیرون همان challenge URL را بخوان، listener و virtual server انتخاب‌شده را بررسی کن و در access/error log مسیر واقعی را پیدا کن. 404 بیشتر می‌گوید درخواست به server رسیده ولی مسیر فایل/route درست سرو نشده؛ هنوز مسئلهٔ TLS نیست.

Record the hostname and resolved DNS, fetch the same challenge URL externally, check the listener and selected virtual host, then inspect the actual path in access/error logs. A 404 suggests the request reached a server but the path was not served correctly; this is not yet a TLS failure.

تمرین ۱۸ · «یک بار کار کرد»Exercise 18 · “It worked once”

صدور موفق بوده، dry-run هم هفتهٔ قبل پاس شده، اما امروز موعد تمدید گذشته. سه بررسی جدا برای تشخیص؟

Issuance succeeded and last week’s dry run passed, but renewal is now overdue. What three separate checks help diagnose it?

پاسخ را ببینShow solution

زمان‌بند واقعاً اجرا شده؟ journal/cron و زمان آخرین اجرا را ببین. چالش امروز از اینترنت می‌رسد؟ DNS A/AAAA و port 80/path را دوباره بسنج. پس از تمدید احتمالی، Nginx گواهی جدید را سرو می‌کند؟ تاریخ endpoint بیرونی و reload را بررسی کن.

Did the scheduler actually run? Check cron/journal and its last execution. Can today’s challenge reach the server? Recheck A/AAAA, port 80, and the path. If renewal occurred, is Nginx serving the new certificate? Inspect the external expiry and reload evidence.

ماموریت: هشدار فردا صبحMission: tomorrow morning’s expiry warning

صبح تیم هشدار گرفته که HTTPS یکی از سایت‌ها به‌زودی منقضی می‌شود. یکی می‌گوید «Certbot خودش تمدید می‌کند»، دیگری می‌خواهد HSTS طولانی فعال کند. تو باید با مدرک بفهمی چه چیزی سرو می‌شود، تمدید خودکار واقعاً کار می‌کند یا نه، و بدون ریسک بی‌دلیل سرویس را به حالت سالم برگردانی.

The team receives a warning that a site’s HTTPS certificate will expire soon. One person says “Certbot renews automatically”; another wants long-lived HSTS. Use evidence to determine what is being served, whether renewal really works, and how to restore a healthy state without unnecessary risk.

  1. نام دامنه و تاریخ گواهی endpoint بیرونی را ثبت کن؛ آن را با certbot certificates مقایسه کن.Record the hostname and the external certificate dates; compare them with certbot certificates.
  2. DNS، listener و پاسخ HTTP-01 را از بیرون بررسی کن. در این مرحله config یا firewall را حدسی تغییر نده.Check DNS, listeners, and the HTTP-01 response externally. Do not change config or firewall by guesswork.
  3. زمان‌بند واقعی و renewal configuration را پیدا کن؛ certbot renew --dry-run را اجرا و خطای دقیق را ثبت کن.Find the actual scheduler and renewal configuration; run certbot renew --dry-run and record the exact failure.
  4. فقط مرز خراب را اصلاح کن؛ nginx -t، renewal rehearsal و پاسخ HTTPS را دوباره بگیر.Fix only the failed boundary; repeat nginx -t, the renewal rehearsal, and the HTTPS request.
  5. تا وقتی HTTPS و زیر‌دامنه‌های لازم آماده نیستند، HSTS بلندمدت یا includeSubDomains فعال نکن.Until HTTPS and required subdomains are ready, do not enable long-lived HSTS or includeSubDomains.
سرنخ‌ها را به‌ترتیب باز کنReveal hints in order

گواهی فایل‌سیستم با گواهی ارائه‌شده از 443 یکی نیست. اگر چالش 404 است، مسیر و virtual host را ببین؛ اگر timeout است، DNS، firewall و listener را بسنج. اگر dry-run موفق است ولی تاریخ بیرونی کهنه مانده، مسیر deploy/reload را دنبال کن.

A certificate on disk is not necessarily the one served on 443. For a 404 challenge, inspect the path and virtual host; for a timeout, check DNS, firewalls, and listeners. If dry-run succeeds but the external date is old, trace deployment and reload.

نمونهٔ گزارش و معیار قبولیSample report and acceptance criteria

گزارش باید hostname، issuer/SAN و تاریخ endpoint بیرونی را ثبت کند؛ مدرک DNS و پاسخ HTTP-01 را نشان دهد؛ نام timer یا cron واقعی و نتیجهٔ dry-run را بیاورد؛ و پس از اصلاح، پاسخ HTTPS معتبر و reload/config آزموده‌شده را ثابت کند. پیام «Certbot نصب است» یا دیدن فایل جدید به‌تنهایی قبولی نیست.

The report records the hostname, issuer/SAN, and external certificate dates; shows DNS and HTTP-01 evidence; names the actual timer or cron and dry-run result; and proves a valid HTTPS response plus tested config/reload after repair. “Certbot is installed” or a new file alone does not pass.

آزمایش محلی را امن جمع کنیمClean up the local lab safely

اگر Nginx محلی را بالا آوردی، اول فقط همان نمونهٔ دارای prefix آزمایش را متوقف کن. مسیر کلید و گواهی را از TLS_LAB جدا نکن و هرگز پوشهٔ واقعی /etc/letsencrypt را برای پاک‌سازی این آزمایش هدف نگیر.

If you started the local Nginx instance, stop only that instance using the lab prefix. Keep the key and certificate inside TLS_LAB, and never target the real /etc/letsencrypt directory while cleaning this experiment.

verify the lab path, stop its Nginx, then confirm before deletion
printf 'Lab path: %s\n' "$TLS_LAB"
if [ -f "$TLS_LAB/run/nginx.pid" ]; then
  nginx -s quit -p "$TLS_LAB/" -c nginx.conf
fi
sleep 0.3
if [ -e "$TLS_LAB/run/nginx.pid" ]; then
  echo 'Nginx PID file still exists; inspect before cleanup.'
else
  read -r -p 'Type REMOVE to delete only this temporary lab: ' confirm
  if [ "$confirm" = REMOVE ] &&
     [[ "$TLS_LAB" =~ ^/tmp/nginx-tls\.[A-Za-z0-9]{6}$ ]] &&
     [ ! -L "$TLS_LAB" ]; then
    rm -r -- "$TLS_LAB"
  else
    echo 'Confirmation/path check failed; nothing removed.'
  fi
fi

پیش از واردکردن REMOVE، مسیر چاپ‌شده را بخوان و مطمئن شو همان پوشهٔ موقت است. اگر Nginx هنوز زنده است یا PID file پاک نشده، چیزی را حذف نکن؛ اول علت را پیدا کن. این cleanup فقط برای آزمایش محلی است.

Before typing REMOVE, read the printed path and confirm it is the temporary lab. If Nginx is still alive or its PID file remains, delete nothing; investigate first. This cleanup is only for the local experiment.
