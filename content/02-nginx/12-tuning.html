Tuning: workers, buffers, timeouts

سایت زیر بار کند شده و همکار پیشنهاد داده worker را چهار برابر و buffer را خیلی بزرگ کنیم. قبل از دست‌زدن به config، باید بفهمیم کدام صف یا منبع واقعاً تنگ است؛ اگر اندازه نگیریم، شاید فقط فشار را از یک جا به جای دیگر منتقل کنیم.

The site slows under load, and a teammate suggests quadrupling workers and making buffers huge. Before touching the config, we need to find which queue or resource is actually constrained; without measurement we may only move pressure elsewhere.

قبل از تنظیم، سؤال را دقیق کنیمMake the question precise before tuning

تیم می‌گوید «با ۳۰ کاربر هم‌زمان کند می‌شود». این جمله هنوز نمی‌گوید Nginx کم آورده، upstream دیر جواب داده، benchmark client توانش را ندارد یا ماشین CPU/دیسک محدودی دارد. فصل قبل WebSocket و bodyهای بزرگ را دیدیم؛ آن اتصال‌ها هم worker connection و file descriptor مصرف می‌کنند و در نتیجهٔ ظرفیت مهم‌اند.

The team says, “It slows down with 30 concurrent users.” That does not tell us whether Nginx is constrained, the upstream is slow, the benchmark client is saturated, or the machine has limited CPU/disk. Last chapter we saw WebSockets and large bodies; those connections also consume worker connection slots and file descriptors, so they matter to capacity.

این‌بار اول یک baseline می‌گیریم: همان مسیر، همان تعداد درخواست، همان concurrency، همان upstream و همان ماشین. یک عدد را تغییر می‌دهیم و دوباره همان آزمون را اجرا می‌کنیم. نتیجه را با خطای درخواست، throughput و latency می‌سنجیم؛ «عدد requests/sec بالاتر شد» به‌تنهایی پیروزی نیست اگر خطا یا latency بدتر شده باشد.

This time we first establish a baseline: same route, request count, concurrency, upstream, and machine. We change one value and repeat the same test. We compare failures, throughput, and latency; a higher requests-per-second number is not a win if errors or latency got worse.

هدف tuning «زیاد کردن عددها» نیست. هدف این است که محدودیت اندازه‌گیری‌شده را پیدا کنیم، کوچک‌ترین تغییر مرتبط را بدهیم و همان شواهد را دوباره بسنجیم. اگر baseline گلوگاهی نشان نداد، دست‌نزدن تصمیم مهندسی معتبری است.Tuning is not about increasing numbers. Find a measured constraint, make the smallest relevant change, and measure the same evidence again. If the baseline shows no bottleneck, leaving the config alone is a valid engineering decision.

درخواست از چند مرز عبور می‌کندA request crosses several boundaries

در proxy، هر درخواست از benchmark client می‌آید، یک اتصال client به Nginx می‌گیرد، worker آن را پردازش می‌کند و معمولاً یک اتصال دیگر به upstream باز می‌شود. بعد CPU، حافظه، شبکه و دیسک هم می‌توانند سقف بسازند. اندازه‌گیری را در چند نقطه می‌گذاریم تا صف را با کندی برنامه اشتباه نگیریم.

With a proxy, each request comes from a benchmark client, uses a client-to-Nginx connection, is handled by a worker, and usually opens another connection to the upstream. CPU, memory, network, and disk can impose further limits. We measure at several points so we do not confuse a queue with a slow app.

فلش‌های بالا مسیر درخواست، proxy و پاسخ‌اند؛ کارت‌های پایین نقطه‌های مشاهده‌اند، نه سرویس جدید. اگر upstream کند باشد، بزرگ‌کردن workerهای Nginx فقط درخواست‌های بیشتری را منتظر همان upstream نگه می‌دارد.

Top arrows show the request, proxy, and response paths; lower cards are observation points, not extra services. If the upstream is slow, more Nginx workers may only queue more requests behind it.

worker بیشتر همیشه سریع‌تر نیستMore workers are not always faster

در بیشتر نصب‌ها worker_processes auto; نقطهٔ شروع معقولی است: Nginx تعداد CPUهای در دسترس را تشخیص می‌دهد. اما هر worker پردازش جداست و worker اضافه هزینهٔ حافظه و زمان‌بندی دارد؛ اگر کار CPU-bound یا upstream-bound است، عدد بزرگ‌تر لزوماً ظرفیت مفید نمی‌سازد.

On many installations, worker_processes auto; is a reasonable starting point: Nginx detects available CPUs. Each worker is a separate process and adds memory/scheduling cost; when work is CPU-bound or upstream-bound, a larger number does not necessarily add useful capacity.

برای nginx -V نسخه و build options مهم‌اند؛ nginx -T تنظیم مؤثر را چاپ می‌کند و ممکن است مسیرها یا secretهای config را لو بدهد، پس خروجی را عمومی نکن. فهرست processها هم فقط وضعیت یک لحظه است. اگر CPU workerها بیکارند ولی upstream کند است، worker بیشتر سراغ علت نمی‌رود.

For nginx -V, build options and version matter; nginx -T prints effective config and may reveal paths or secrets, so do not publish its output. Process rows are only a point-in-time view. If Nginx workers are idle while the upstream is slow, adding workers does not address the cause.

worker_connections تعداد کاربر نیستworker_connections is not a user count

هر worker حداکثر تعداد connection هم‌زمانی را می‌پذیرد که در worker_connections آمده؛ این مقدار، تعداد request در ثانیه نیست. در reverse proxy معمولاً یک درخواست هم‌زمان دست‌کم یک socket از client و یکی از upstream می‌خواهد. connectionهای idle، WebSocket و socketهای داخلی هم در ظرفیت سهم دارند.

Each worker can open up to the configured number of simultaneous connections; that is not a requests-per-second limit. A proxied active request commonly needs at least one client socket and one upstream socket. Idle keep-alive connections, WebSockets, and internal sockets consume capacity too.

دو فلش socketهای یک درخواست proxyشده را نشان می‌دهند. برای یک worker با ۱۰۰ connection، نمی‌توان ۱۰۰ client فعال proxyشده را تضمین کرد؛ حد واقعی با FDها، listenerها و سایر اتصال‌ها کمتر می‌شود.

The two arrows show sockets for one proxied request. A worker configured for 100 connections cannot guarantee 100 active proxied clients; file-descriptor limits, listeners, and other sockets reduce the real ceiling.

حاصل‌ضرب workerها در connectionها فقط سقف نظری شروع بحث است. هر worker هم حد file descriptor دارد؛ اگر worker_connections را بالا ببری ولی RLIMIT_NOFILE پایین بماند، ظرفیت مؤثر همان حد پایین‌تر است. تنظیم بی‌دلیل هر دو عدد را بالا نبر.

Workers multiplied by connections is only a theoretical starting ceiling. Each worker also has a file-descriptor limit; raising worker_connections while RLIMIT_NOFILE stays low leaves the lower limit in effect. Do not raise both numbers without evidence.

دو جور keepalive را قاطی نکنDo not confuse the two kinds of keepalive

keepalive_timeout می‌گوید Nginx چقدر یک اتصال idle سمت client را برای درخواست بعدی نگه دارد. مقدار طولانی‌تر می‌تواند handshakeهای تازه را کم کند، اما connection idle هم جای worker و FD می‌گیرد. keepalive به upstream تنظیم جدا دارد؛ این دو مقصد را یکی حساب نکن.

keepalive_timeout controls how long Nginx keeps an idle client-side connection available for another request. A longer value may avoid new handshakes, but idle connections still occupy worker and file-descriptor capacity. Upstream keepalive is configured separately; do not treat the two sides as one setting.

upstream keepalive is a per-worker cache of idle connections
upstream app_pool {
    server 127.0.0.1:19200;
    keepalive 16;
}
server {
    location / {
        proxy_pass http://app_pool;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}

در این مثال اتصال‌های idle upstream برای استفادهٔ دوباره cache می‌شوند؛ عدد 16 به‌ازای هر worker است، نه سقف اتصال‌های فعال کل app. قبل از افزودنش، بررسی کن backend واقعاً از reuse سود می‌برد و protocol/headerها برایش درست‌اند. تا وقتی داده دلیل دیگری ندهد، default ساده معمولاً بهتر است.

This example caches idle upstream connections for reuse; 16 is per worker, not a global cap on active app connections. Before enabling it, verify the backend benefits from reuse and the protocol/headers are correct. Until measurements say otherwise, the simpler default is often preferable.

bufferها سرعت‌ساز جادویی نیستندBuffers are not magic speed knobs

در پاسخ proxyشده، proxy_buffer_size فضای خواندن بخش اول پاسخ upstream را مشخص می‌کند که معمولاً headerها هستند؛ proxy_buffers bufferهای بدنهٔ پاسخ را برای هر connection تعریف می‌کند. اگر پاسخ از آن‌ها جا نشود و buffering روشن باشد، بخشی از پاسخ می‌تواند به فایل موقت برود. اندازهٔ پیش‌فرض به نسخه و صفحهٔ سیستم وابسته است؛ اول header یا هشدار واقعی را پیدا کن.

For a proxied response, proxy_buffer_size holds the first part read from upstream, usually its headers; proxy_buffers defines response-body buffers per connection. If a response does not fit and buffering is enabled, part may spill to a temporary file. Defaults depend on version and system page size; first find an actual header-size issue or warning.

این سه را یکی نکن: buffer پاسخ با body آپلود client فرق دارد. برای پاسخ‌های بزرگ، تنظیمات cache و temp file هم در داستان‌اند؛ buffer بزرگ‌تر به معنی کمترشدن زمان اجرای upstream یا CPU کمتر نیست.

Do not conflate these: response buffers are different from an uploaded client body. For large responses, cache and temporary-file behavior may matter too; larger buffers do not make the upstream execute faster or use less CPU.

timeout را به رخداد موردنظر وصل کنTie each timeout to the event it measures

timeout یک مهلت برای همهٔ request نیست؛ هر کدام روی انتظار متفاوتی می‌نشیند. افزایش یک timeout ممکن است فقط connection بیشتری را طولانی‌تر نگه دارد و صف upstream را بزرگ‌تر کند.

A timeout is not one deadline for every request; each directive governs a different wait. Increasing one may simply keep more connections open longer and grow the upstream queue.

timeoutهای I/O در Nginx معمولاً فاصلهٔ بی‌فعالیت بین دو عملیات را می‌سنجند، نه مجموع مدت انتقال. قبل از تغییر، timestamp و مرحلهٔ شروع/پایان را از log جمع کن؛ اگر فقط یک upstream دیر پاسخ می‌دهد، worker یا timeout client را بی‌دلیل تغییر نده.

Nginx I/O timeouts generally measure inactivity between operations, not total transfer duration. Before changing them, collect timestamps and the start/end stage from logs; if one upstream is merely slow to answer, do not change worker or client timeouts without evidence.

خرابی عمدی: «بزرگش کن که دیگر خطا ندهد»Deliberate bad idea: “Make it huge so errors stop”

این config را اجرا نمی‌کنیم؛ فقط هزینه‌اش را حساب می‌کنیم. فرض کن کسی برای یک header بزرگ این‌ها را گذاشته:

We will not run this config; we will calculate its cost instead. Imagine someone set these values to silence one large-header symptom:

intentionally excessive example — do not copy into production
proxy_buffer_size 1m;
proxy_buffers 256 1m;
proxy_read_timeout 24h;

اگر همهٔ bufferهای تعریف‌شده برای یک connection پر شوند، بودجهٔ بالقوه نزدیک 257 MiB برای هر connection می‌شود؛ ۱۰۰ connection هم‌زمان می‌توانند ده‌ها GiB تقاضای حافظه بسازند. Nginx همهٔ bufferها را از همان اول برای همهٔ اتصال‌ها یک‌جا تخصیص نمی‌دهد؛ این سقف بدترین‌حالت است، اما باز هم ضرب در هم‌زمانی واقعی مهم است. timeout یک‌روزه هم socketهای منتظر را بی‌دلیل طولانی نگه می‌دارد.

If every configured buffer for one connection is filled, the potential budget is about 257 MiB per connection; 100 concurrent connections could demand tens of GiB. Nginx does not eagerly allocate every buffer for every connection, so this is a worst-case budget—not an immediate reservation—but real concurrency still multiplies the risk. A one-day timeout also keeps waiting sockets around unnecessarily.

اگر header upstream بزرگ است، اول اندازه و منبعش را اندازه بگیر و فقط header buffer لازم را تغییر بده؛ اگر upstream گیر می‌کند، timeout را با latency واقعی و هدف سرویس تنظیم کن. رفع علامت با عدد غول‌آسا ممکن است تبدیل به پرشدن حافظه یا connectionهای معطل شود.

If an upstream header is large, measure its size and source first, then adjust only the required header buffer. If the upstream stalls, choose a timeout from observed latency and service goals. Hiding a symptom with huge numbers can turn it into memory pressure or long-lived stalled connections.

در این فصل benchmark فقط روی loopback خودت است. به سرویس عمومی، VPS یا سامانه‌ای که مالک/مسئولش نیستی بار آزمایشی نفرست؛ حتی تست کوتاه می‌تواند rate limit یا اختلال بسازد.All benchmarks in this chapter target your own loopback. Do not load-test a public service, VPS, or system you do not own or administer; even a short test can trigger rate limits or disruption.

آزمایش کنترل‌شده را روی loopback آماده کنیمPrepare a controlled loopback experiment

برای جداکردن Nginx از برنامه، یک upstream مصنوعی روی loopback می‌سازیم که پاسخ کوچکی با تأخیر ثابت ۲۰ میلی‌ثانیه می‌دهد. آزمون فقط ۱۲۰ درخواست و حداکثر ۸ اتصال هم‌زمان دارد. این بارگذاری کوچک برای دیدن تفاوت config آزمایشگاهی است، نه پیش‌بینی ظرفیت production.

To separate Nginx from the app, we will create a synthetic loopback upstream that returns a small response after a fixed 20 ms delay. The test is limited to 120 requests and at most eight concurrent connections. This small load illustrates lab configuration behavior; it does not predict production capacity.

اول پورت‌های آزمایش را بررسی کن و limit فایل را بخوان. اگر پورت اشغال است، سرویسش را نکش؛ شمارهٔ آزاد دیگری انتخاب کن و در همهٔ فرمان‌ها عوضش کن. اگر ulimit -n از 128 کمتر است، benchmark را اجرا نکن تا limit آزمایشگاه را متناسب و امن انتخاب کنی.

First inspect the test ports and file limit. If a port is occupied, do not kill its service; choose another free port and change it consistently. If ulimit -n is below 128, do not run the benchmark until you choose a suitable safe lab limit.

inspect first, then create an isolated temporary directory
ulimit -n

The limit and path are illustrative. If ss prints no listener, it only means none was observed at that moment—not that the ports are guaranteed free for the whole experiment. Keep using the same shell so the variable and PIDs remain available.

upstream این پاسخ کوتاه و مشخص را می‌دهد و بدنه را روی دیسک نمی‌نویسد. Python فقط برای شبیه‌سازی پاسخ است؛ اگر پورت یا dependency خطا داشت، پیش از آزمون Nginx آن را جدا رفع کن.

The upstream returns a small predictable response and writes no body to disk. Python is only used to simulate the response; resolve any port or dependency problem before testing Nginx.

create and start a tiny delayed upstream on loopback
cat > "$TUNE_LAB/app.py" <<'PY'
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
import time

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        time.sleep(0.02)
        body = b"controlled upstream response\n"
        self.send_response(200)
        self.send_header("Content-Type", "text/plain")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

ThreadingHTTPServer(("127.0.0.1", 19200), Handler).serve_forever()
PY
python3 -m py_compile "$TUNE_LAB/app.py"
python3 -u "$TUNE_LAB/app.py" > "$TUNE_LAB/app.log" 2>&1 &
echo $! > "$TUNE_LAB/pids/app.pid"
sleep 0.3
curl -i http://127.0.0.1:19200/
HTTP/1.0 200 OK
...
controlled upstream response

این پاسخ مستقیم baseline برنامه است؛ پس اگر Nginx بعداً 502 داد، اول مطمئن می‌شویم app هنوز روی loopback پاسخ می‌دهد. تأخیر ۲۰ ms ساختگی و ثابت است؛ نتایج واقعی هر سیستم متفاوت‌اند.

This direct response is the app baseline, so if Nginx later returns 502, we can first verify that the loopback app still responds. The 20 ms delay is synthetic and fixed; real results vary by machine.

قبل از tuning، baseline را ثبت کنRecord a baseline before tuning

Nginx آزمایش را با یک worker و ۶۴ connection بالا می‌آوریم. log زمان کل و upstream را می‌گیرد تا اگر benchmark کند شد، بدانیم زمان در کدام بازه است. تنظیم‌ها در فایل موقت‌اند و به service اصلی دست نمی‌زنند.

We start lab Nginx with one worker and 64 connections. Its log records total and upstream time so we can tell where a slow benchmark spends its time. Settings live in a temporary file and do not touch the main service.

write a disposable proxy config with a measurable baseline
cat > "$TUNE_LAB/nginx.conf" <<'NGINX'
worker_processes 1;
pid run/nginx.pid;
error_log logs/error.log warn;
events { worker_connections 64; }
http {

تمرین؛ اول bottleneck را نام ببرExercises: identify the bottleneck before the setting

در سؤال‌های سناریویی، جواب خوب فقط اسم directive نیست؛ بگو کدام اندازه‌گیری تصمیم را عوض می‌کند و چه چیزی را هنوز نمی‌دانیم.

For scenario questions, a good answer is more than a directive name: say which measurement changes the decision and what remains unknown.

۱. پیش‌بینی workerهاPredict the worker count

روی ماشینی با ۴ CPU در دسترس، worker_processes auto; را می‌بینی. چه عددی احتمالاً انتخاب می‌شود، و چرا نباید آن را ظرفیت تضمین‌شده فرض کرد؟

On a machine with four available CPUs you see worker_processes auto;. What count is likely selected, and why is that not a capacity guarantee?

پاسخAnswer

معمولاً تلاش می‌کند CPUهای در دسترس را تشخیص دهد، پس حدود چهار worker محتمل است. بار، دیسک، upstream، limitها و build هم اثر دارند؛ تعداد worker به‌تنهایی throughput را تضمین نمی‌کند.

It generally attempts to detect available CPUs, so about four workers is plausible. Load, disk, upstream, limits, and build also matter; worker count alone does not guarantee throughput.

۲. چهار connection یا چهار request؟Four connections or four requests?

یک worker با worker_connections 4 دارد proxy می‌کند. آیا می‌تواند چهار client فعال را هم‌زمان سرویس دهد؟

One worker has worker_connections 4 while proxying. Can it serve four active clients at once?

تفسیرInterpretation

این را تضمین نکن؛ client و upstream socketها هر دو شمرده می‌شوند، listenerها و اتصال‌های دیگر هم جا می‌گیرند. یک درخواست proxyشده اغلب حداقل دو slot نیاز دارد.

Do not assume so: both client and upstream sockets count, as do listeners and other connections. One proxied request often needs at least two slots.

۳. کدام limit تنگ‌تر است؟Which limit is tighter?

worker_connections 4096 است ولی worker فقط 512 file descriptor مجاز دارد. کدام عدد برای ظرفیت واقعی مهم‌تر است؟

worker_connections is 4096, but the worker may open only 512 file descriptors. Which value matters more for real capacity?

پاسخAnswer

حد پایین‌تر، همراه با descriptorهای مصرف‌شده برای listener و فایل‌های log. بالا بردن worker_connections بدون اصلاح و اثبات limit فایل کمکی نمی‌کند.

The lower limit, minus descriptors already used by listeners and log files. Raising worker_connections without verifying the file limit does not help.

۴. ulimit کدام فرایند؟Which process does ulimit describe?

shell تو ulimit -n برابر 2048 است؛ آیا همین limit حتماً برای Nginx systemd هم هست؟

Your shell reports ulimit -n as 2048. Does that necessarily apply to systemd’s Nginx service?

پاسخAnswer

نه؛ service می‌تواند limit متفاوتی از unit بگیرد. systemctl show nginx -p LimitNOFILE و در صورت نیاز اطلاعات فرایند فعال را بررسی کن.

No. The service may receive a different unit limit. Inspect systemctl show nginx -p LimitNOFILE and, if needed, the running process’s limits.

۵. upstream idle poolThe upstream idle pool

در keepalive 16 برای هر worker، چه چیزی ۱۶ تا است؟

In keepalive 16 for each worker, what is capped at 16?

توضیحExplanation

تعداد upstream connectionهای idle که pool آن worker نگه می‌دارد، نه مجموع connectionهای فعال برنامه. اگر backend reuse سودی نداشته باشد، این تنظیم ارزش خودکار ندارد.

It caps idle upstream connections cached by that worker, not all active app connections. If the backend does not benefit from reuse, the setting has no automatic value.

۶. buffer header یا body؟Header or body buffer?

error log می‌گوید header پاسخ upstream از buffer اول بزرگ‌تر است. کدام شاهد را پیش از تغییر جمع می‌کنی؟

The error log says an upstream response header is larger than the first buffer. What evidence do you collect before changing it?

قدم اولFirst step

اندازه و منبع header، مسیر و تعداد درخواست‌های اثرپذیرفته را پیدا کن. سپس فقط proxy_buffer_size لازم را با concurrency واقعی بسنج؛ بزرگ‌کردن همهٔ proxy_buffers بدنه را هم متورم می‌کند.

Find header size/source, route, and affected request count. Then measure the required proxy_buffer_size against real concurrency; enlarging every proxy_buffers also expands body buffering.

۷. client body bufferClient body buffer

آپلود فایل از Nginx عبور می‌کند. آیا proxy_buffers تنظیم اصلی برای body ورودی است؟

An upload passes through Nginx. Are proxy_buffers the main setting for its incoming body?

پاسخAnswer

نه؛ proxy_buffers برای پاسخ upstream است. body ورودی، buffering و فایل موقت مسیر client را دارد؛ فصل قبل سقف body و proxy_request_buffering را دیدیم.

No. proxy_buffers apply to the upstream response. Incoming bodies have their own client-body buffering and temporary files; last chapter covered body limits and proxy_request_buffering.

۸. timeout اتصالConnect timeout

Nginx نمی‌تواند TCP connection به upstream بسازد. بالا بردن proxy_read_timeout چه اثری دارد؟

Nginx cannot establish a TCP connection to upstream. What does increasing proxy_read_timeout change?

دلیلReason

هیچ‌چیز دربارهٔ مرحلهٔ اتصال؛ read timeout بعد از برقراری connection روی انتظار داده اثر دارد. اتصال، آدرس و خطای error log را بررسی کن؛ directive درست را فقط پس از تشخیص انتخاب کن.

Nothing about connection establishment; read timeout governs waiting for data after a connection exists. Check reachability, address, and error log, then choose a directive based on the stage.

۹. read timeout یعنی کل پاسخ؟Does read timeout cover the whole response?

proxy_read_timeout 30s است. آیا پاسخ ۴۰ ثانیه‌ای حتماً قطع می‌شود؟

proxy_read_timeout 30s is set. Must a 40-second response be cut off?

پاسخAnswer

نه اگر upstream در فاصله‌های کمتر از ۳۰ ثانیه داده بفرستد؛ timeout فاصلهٔ بین readهای پیاپی را می‌سنجد، نه زمان کل پاسخ.

Not if upstream sends data at intervals under 30 seconds; the timeout measures the gap between successive reads, not total response duration.

۱۰. keepalive در دو سمتKeepalive on both sides

client keepalive فعال است. آیا این یعنی اتصال upstream هم reuse می‌شود؟

Client keepalive is enabled. Does that mean upstream connections are reused too?

پاسخAnswer

خیر؛ اتصال client و pool اتصال idle upstream تنظیم‌های جدا دارند. برای upstream reuse، block مربوط به upstream و headerهای proxy را هم بررسی کن.

No. Client connections and the upstream idle-connection pool are configured separately. For upstream reuse, inspect the upstream block and proxy headers too.

۱۱. throughput بالاتر، latency بدترHigher throughput, worse latency

پس از تغییر، requests/sec بالا رفته اما p95 latency دو برابر شده. آیا tuning موفق است؟

After a change, requests/sec rises but p95 latency doubles. Is the tuning successful?

ارزیابیAssessment

نه تا وقتی هدف سرویس و خطاها را مقایسه نکنی. ممکن است صف بزرگ‌تر شده یا درخواست‌ها در tail معطل باشند؛ throughput را جدا از latency قضاوت نکن.

Not until you compare service goals and errors. The queue may have grown or tail requests may be stalled; do not judge throughput separately from latency.

۱۲. benchmark client محدود استThe benchmark client is constrained

benchmark روی همان ماشین اجرا می‌شود و CPU client به ۱۰۰٪ می‌رسد. عدد requests/sec چه مشکلی دارد؟

The benchmark runs on the same host and client CPU reaches 100%. What is wrong with the requests-per-second result?

تفسیرInterpretation

client شاید قبل از Nginx اشباع شده؛ آزمون ظرفیت سرور را جدا نکرده. با concurrency پایین‌تر یا load generator مستقل در محیط مجاز تکرار کن و هم‌زمان CPU/latency را ثبت کن.

The client may saturate before Nginx, so the test does not isolate server capacity. Repeat at lower concurrency or with a separate authorized load generator, recording CPU and latency together.

۱۳. دو اجرا قابل مقایسه‌اند؟Are the two runs comparable?

run اول ۱۲۰ request با concurrency=8 روی route سریع است؛ run دوم ۱۲۰۰ درخواست با concurrency=80 روی route کند. می‌توانی سرعت configها را مقایسه کنی؟

Run one uses 120 requests at concurrency 8 on a fast route; run two uses 1,200 at concurrency 80 on a slow route. Can you compare the configs?

پاسخAnswer

نه؛ چند متغیر هم‌زمان فرق دارد. تعداد، concurrency، route، داده، ماشین و ابزار را ثابت کن و فقط config مورد بررسی را تغییر بده.

No; several variables changed at once. Hold request count, concurrency, route, data, machine, and tool constant; change only the config under test.

۱۴. worker بیکار، upstream پرکارIdle worker, busy upstream

Nginx CPU پایینی دارد، اما $upstream_response_time بالا و app CPU بالا است. چه چیزی را اول tune می‌کنی؟

Nginx CPU is low, but $upstream_response_time and app CPU are high. What do you tune first?

استدلالReasoning

اول ظرفیت و رفتار app را بررسی می‌کنم؛ worker بیشتر Nginx احتمالاً فقط صف upstream را بزرگ می‌کند. log و benchmark همان route را با app مستقل مقایسه کن.

I would investigate app capacity first; more Nginx workers may only enlarge the upstream queue. Compare route logs and the benchmark with the app path directly.

۱۵. FD warning زیر بارFD warning under load

Nginx error log از نبود connection slot می‌گوید و limit فایل worker از مقدار config پایین‌تر است. آیا فقط worker_connections را بالا می‌بری؟

Nginx logs a connection-slot warning, and the worker’s file limit is below the configured connection count. Would you only raise worker_connections?

پاسخ محتاطانهCautious answer

نه؛ هر دو سقف و descriptorهای مصرف‌شده را بسنج. limit service و سیستم‌عامل را هم با مجوز عملیاتی بررسی کن؛ افزایش یکی در حالی که دیگری پایین است، سقف را جابه‌جا نمی‌کند.

No; measure both ceilings and descriptors already in use. Check service and OS limits within operational authority; raising one while the other stays low does not move the effective cap.

۱۶. صدای timeout بزرگThe cost of a huge timeout

تیمی proxy_read_timeout 24h گذاشته تا هیچ clientی قطع نشود. چه منابعی را نگه می‌دارد و چه چیزی را حل نمی‌کند؟

A team sets proxy_read_timeout 24h so no client disconnects. What resources may it retain, and what does it not solve?

پاسخAnswer

socket، connection slot و FDهای منتظر می‌توانند طولانی‌تر نگه داشته شوند. این کار upstream خراب یا peer مرده را تعمیر نمی‌کند؛ heartbeat و الگوی واقعی سکوت را بسنج و timeout را محدود انتخاب کن.

Waiting sockets, connection slots, and file descriptors may be held longer. This does not repair a broken upstream or dead peer; measure heartbeat and real idle patterns, then choose a bounded timeout.

۱۷. buffer عظیم برای یک خطاHuge buffers for one warning

یک header بزرگ مشکل دارد و پیشنهاد شده proxy_buffers 256 1m تنظیم شود. چرا این تغییر نامرتبط و پرهزینه است؟

One large header causes trouble, and someone proposes proxy_buffers 256 1m. Why may this be irrelevant and costly?

توضیحExplanation

proxy_buffers برای body پاسخ است؛ header اول با proxy_buffer_size مرتبط است. bufferهای بزرگ می‌توانند بودجهٔ بالقوهٔ هر connection و فشار حافظه را با concurrency بالا ببرند.

proxy_buffers serve the response body; the first response header relates to proxy_buffer_size. Large buffers can multiply the potential per-connection memory budget under concurrency.

۱۸. یادداشت تغییر برای همکارA change note for a teammate

یک run محلی نشان داده warning connectionها با ۴ slot می‌آید و پس از بازگشت به ۶۴ رفع می‌شود؛ چه چیزی را در handoff می‌نویسی؟

A local run shows connection warnings at 4 slots and none after restoring 64. What do you write in the handoff?

پاسخ قابل بازبینیReviewable answer

شرایط آزمون، تعداد/concurrency، تنظیم قبل/بعد، error log، failed requests، throughput/latency و CPU را می‌نویسم. نتیجه فقط دربارهٔ همان lab است؛ production را با بار و limit واقعی خودش می‌سنجم و اگر bottleneck دیگری است، این عدد را بی‌دلیل تغییر نمی‌دهم.

Record test conditions, count/concurrency, before/after settings, error logs, failures, throughput/latency, and CPU. The result applies only to this lab; measure production with its real load and limits, and do not change this value if another bottleneck dominates.

آزمایش را جمع کن؛ logها را اول نگه دارClean up, but preserve logs first

پیش از cleanup، خروجی benchmark و دو log را برای یادداشتت بردار. بعد Nginx را با prefix همین آزمایش متوقف کن و فقط برنامه‌ای را بکش که command line آن به app.py همین مسیر اشاره می‌کند. اگر PID یا مسیر غیرمنتظره بود، توقف و حذف نکن.

Before cleanup, capture benchmark output and both logs for your notes. Then stop only the Nginx instance using this lab prefix and kill only a process whose command line points to this directory’s app.py. If the PID or path is unexpected, do not stop or remove anything.
