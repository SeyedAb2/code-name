منطق location و اولویت‌ها

Location matching and priority

درخواست به server درست می‌رسد، اما هنوز پاسخ عجیبی می‌گیری: چرا /docs/api/report.css از قاعدهٔ عمومی regex جواب می‌گیرد، نه از prefix بلندترش؟ این فصل را مثل معمای مسیریابی حل می‌کنیم: پیش‌بینی، درخواست، نشانهٔ برنده، و بعد اصلاح قاعده.

The request reaches the right server, but the response is still surprising: why does /docs/api/report.css match a general regex instead of its longer prefix? We will solve location selection as a routing puzzle: predict, request, inspect the winning marker, then adjust the rule.

فصل قبل با Host درخواست را به server block درست رساندیم. حالا همان سایت چند مسیر دارد: صفحهٔ سلامت، API، اسناد و فایل‌های media. همکارمان می‌گوید برای هرکدام یک location نوشته، اما درخواست فایل CSS زیرمسیر API با پاسخ دیگری برمی‌گردد.

The previous chapter used Host to reach the correct server block. Now that site has several paths: a health page, an API, documentation, and media files. A teammate says they wrote a location for each, yet a CSS request under the API path receives an unexpected response.

قبل از خواندن config حدس بزن: اگر /docs/api/ از / طولانی‌تر است، آیا این به‌تنهایی تضمین می‌کند که آن block پاسخ دهد؟ فعلاً جواب را نگه دار. همین URL را در آزمایشگاه با نشانگرهای متفاوت می‌فرستیم تا Nginx خودش انتخابش را لو بدهد.

Predict before reading the config: if /docs/api/ is longer than /, does that alone guarantee its block will answer? Hold the answer for now. We will send that URL to a lab with distinct markers so Nginx reveals its choice.

قبل از locationBefore location matching

این فصل از این‌جا شروع می‌کند که request قبلاً وارد server block درست شده است. انتخاب server بر اساس listener و نام درخواست را با انتخاب location بر اساس URI قاطی نکن؛ دو تصمیم جدا هستند.

This chapter assumes the request has already entered the intended server block. Do not mix server selection by listener and request name with location selection by URI; they are two separate decisions.

یک آزمایشگاه، چند پاسخ قابل‌تشخیصOne lab, several identifiable responses

برای دیدن انتخاب Nginx، محتوای واقعی لازم نداریم؛ هر location یک برچسب یکتا برمی‌گرداند. config را در پوشهٔ موقت می‌سازیم و فقط روی loopback گوش می‌دهیم. این نمونه روی نصب Nginx خودت اجرا می‌شود، اما config سرویس موجود را دست‌کاری نمی‌کند.

We do not need real content to observe Nginx’s choice; each location returns a unique label. We will build the config in a temporary directory and listen only on loopback. The lab uses your Nginx binary but does not modify the existing service config.

این دستورها برای پوستهٔ Bash در Linux، macOS یا WSL نوشته شده‌اند؛ در PowerShell اجرا نمی‌شوند. اول پوشه را بساز و مسیرش را نگه دار. اگر فرمان شکست خورد، جلو نرو؛ پاک‌سازی بعدی فقط باید همین مسیر آزمایش را هدف بگیرد.

First create the directory and keep its path. If this command fails, stop; later cleanup must target only this lab path.

create a disposable lab
LAB_DIR=$(mktemp -d "${TMPDIR:-/tmp}/nginx-location.XXXXXX")
mkdir -p "$LAB_DIR/logs"
printf 'Lab directory: %s\n' "$LAB_DIR"

config زیر عمداً پاسخ‌ها را به فایل وابسته نمی‌کند؛ تنها سؤال این است که کدام location برنده شد. مقصد آزمایش 127.0.0.1:18081 است تا با default سایت فصل قبل تداخل نکند. اگر پورت اشغال است، پیش از ادامه یک پورت آزاد انتخاب کن و همهٔ 18081ها را یکسان تغییر بده.

The config below does not depend on files; our only question is which location won. The lab uses 127.0.0.1:18081 to avoid the previous chapter’s default port. If it is occupied, choose a free port before continuing and change every 18081 consistently.

the first location map
cat > "$LAB_DIR/nginx.conf" <<'NGINX'
worker_processes 1;
pid logs/nginx.pid;
error_log logs/error.log notice;

events { worker_connections 64; }

http {
    access_log off;
    default_type text/plain;

    server {
        listen 127.0.0.1:18081 default_server;
        server_name _;

        location = /health {
            return 200 "EXACT: health\n";
        }

        location ^~ /media/ {
            return 200 "PREFIX: media, regex skipped\n";
        }

        location /docs/api/ {
            return 200 "PREFIX: longest docs api\n";
        }

        location /docs/ {
            return 200 "PREFIX: docs\n";
        }

        location /assets/ {
            return 200 "PREFIX: assets\n";
        }

        location ~* \.(css|js)$ {
            return 200 "REGEX: static, first match\n";
        }

        location ~ \.php$ {
            return 200 "REGEX: php\n";
        }

        location / {
            return 200 "PREFIX: catch-all slash\n";
        }
    }
}
NGINX
nginx -t -p "$LAB_DIR/" -c nginx.conf

چند نکته را قبل از start ببین: همهٔ locationها داخل یک server هستند؛ پس Host دیگری وارد داستان نمی‌شود. nginx -t syntax و فایل‌های لازم را بررسی می‌کند، اما نه اشغال‌بودن پورت را تضمین می‌کند و نه انتخاب مسیر برای درخواست واقعی را. اول همین آزمون را بگیر، بعد سرویس آزمایشی را بالا بیاور.

Notice a few things before starting: every location is inside one server, so host selection is out of the picture. nginx -t checks syntax and required files, but does not guarantee the port is free or predict which location a real request will use. Run the test, then start the lab service.

start only if the lab port is free
if command -v ss >/dev/null && ss -ltn | grep -q ':18081 '; then
  echo 'Port 18081 is occupied; choose another port first.'
else
  nginx -p "$LAB_DIR/" -c nginx.conf
fi

اگر خروجی گفت پورت اشغال است، این branch عمداً Nginx را اجرا نمی‌کند. port را در config و درخواست‌ها عوض کن و -t را دوباره اجرا کن. اگر ابزار ss نداری، از ابزار سیستم خودت برای بررسی listener استفاده کن؛ خط را کورکورانه حذف نکن.

If the output says the port is occupied, this branch intentionally does not start Nginx. Change the port in both config and requests, then rerun -t. If ss is unavailable, use your system’s listener-inspection tool; do not remove the check blindly.

اول استثنای دقیق، بعد prefixهاFirst an exact exception, then prefixes

در آزمایشگاه /health یک location دقیق دارد. پیش‌بینی کن: /health?verbose=1 هم همان را می‌گیرد؟ و /health/ چطور؟

In the lab, /health has an exact location. Predict: does /health?verbose=1 use it too? What about /health/?

compare exact URI, query, and trailing slash
curl -i 'http://127.0.0.1:18081/health'
curl -i 'http://127.0.0.1:18081/health?verbose=1'
curl -i 'http://127.0.0.1:18081/health/'

locationها URI درخواست را می‌سنجند، نه query string را؛ بنابراین دو URL اول برای تطبیق URI یکسان /health دارند. /health/ مسیر دیگری است و exact match نمی‌شود؛ پس در این config به location / می‌افتد. «exact» یعنی مسیر دقیق، نه تطبیق byte-for-byte با کل URL شامل query.

Locations match the request URI, not its query string, so the first two URLs have the same matching URI: /health. /health/ is a different path and does not exact-match; in this config it falls through to location /. “Exact” means the exact URI, not a byte-for-byte match of the whole URL including its query.

قاعدهٔ location = /health اگر پیدا شود جست‌وجو را همان‌جا تمام می‌کند؛ prefix یا regex دیگری دیگر برنده نمی‌شود. این راهی روشن برای یک endpoint دقیق است، مثل مسیر سلامت. حالا اگر exact نداشته باشیم، نوبت prefixهاست.

If location = /health matches, the search ends there; no other prefix or regex can win. This is a clear way to define one exact endpoint, such as a health path. Without an exact match, Nginx considers prefixes next.

بلندترین prefix پیدا می‌شود؛ ولی هنوز قطعی نیستThe longest prefix is found—but not necessarily final

سه prefix داریم: /، /docs/ و /docs/api/. برای /docs/api/users هر سه ابتدای URI هستند. پیش‌بینی تو چیست؟ prefix بلندتر مستقل از ترتیب نوشته‌شدن در فایل پیدا می‌شود.

We have three prefixes: /, /docs/, and /docs/api/. For /docs/api/users, all three match the start of the URI. What do you predict? The longer prefix is found regardless of the order in which these blocks appear in the file.

این نمودار مسیر کلاسیک را نشان می‌دهد: exact پایان زودهنگام دارد؛ بعد بلندترین prefix ذخیره می‌شود. ^~ مرحلهٔ regex را کنار می‌زند؛ در غیر این صورت اولین regex مطابق برنده است و اگر match نشود، prefix ذخیره‌شده به کار می‌رود. نسخه‌های جدیدتر predicate location هم دارند؛ یادداشت نسخه را ببین.

This diagram shows the classic path: an exact match ends the search; then the longest prefix is remembered. ^~ skips regex checks; otherwise the first matching regex wins, and the remembered prefix is used if none match. Newer versions also have predicate locations; see the version note.

قاعدهٔ prefix واقعاً «بلندترین» است، نه «اولین خط فایل». برای اینکه ترتیب را با چشم ببینی، این سه URL را بفرست و متن پاسخ را بخوان:

The prefix rule really is “longest,” not “first line in the file.” To see it directly, send these three URLs and read their response bodies:

این سه پاسخ نشان می‌دهند prefixهای عمومی‌تر کنار می‌روند و خاص‌ترین موردِ مطابق برای مرحلهٔ بعد ذخیره می‌شود. اما واژهٔ «ذخیره» مهم است: هنوز regexها می‌توانند نتیجه را عوض کنند. این همان جایی است که حدسِ «بلندترین همیشه برنده است» می‌شکند.

These responses show that broader prefixes give way to the most specific matching candidate. But “candidate” matters: a regex may still change the result. This is where the guess “the longest always wins” breaks down.

regex بعد از prefix می‌آید، اما می‌تواند برنده شودRegex runs after prefixes, but it can still win

برای /docs/api/report.css بلندترین prefix همان /docs/api/ است. قبل از curl انتخابت چیست؟ جواب config فعلی: regex فایل‌های CSS/JS بعد از prefixها بررسی می‌شود و اگر match شود، پاسخ را می‌گیرد.

For /docs/api/report.css, the longest prefix is /docs/api/. What is your prediction before curl? With the current config, the CSS/JS regex is checked after prefixes and takes the request if it matches.

بدنهٔ اول ثابت می‌کند regex از prefix بلندتر جلو زده؛ درخواست دوم هم regexِ PHP را نشان می‌دهد، با اینکه همان prefixها match هستند. regexها به ترتیب ظاهرشان در config سنجیده می‌شوند و اولین regex مطابق، پایان جست‌وجو است؛ «طولانی‌ترین regex» مفهومی در این الگوریتم نیست.

The first body proves a regex beat the longer prefix; the second shows the PHP regex winning even though the same prefixes match. Regex locations are tested in config order, and the first matching regex ends the search. There is no “longest regex” rule here.

نمونهٔ CSS از ~* استفاده می‌کند؛ پس پسوند .CSS هم match می‌شود. اگر همان قاعده با ~ نوشته شود، تطبیق regex به بزرگی/کوچکی حرف حساس است. بعداً در decision table خواهیم دید query string در انتخاب دخالت نمی‌کند: regex روی URI است، نه ?download=1.

The CSS rule uses ~*, so an uppercase .CSS suffix also matches. With ~, regex matching is case-sensitive. The decision table will also show that the query string does not participate: regex sees the URI, not ?download=1.

پس ^~ دقیقاً چه چیزی را می‌بندد؟So what exactly does ^~ suppress?

یک مسیر media داریم که نباید regex عمومی CSS آن را بگیرد. modifier را روی prefix بلندترِ /media/ می‌گذاریم. اگر همان طولانی‌ترین prefix باشد، Nginx regexها را بررسی نمی‌کند و همان block را استفاده می‌کند.

We have a media path that should not be captured by the general CSS regex. Put the modifier on the longer /media/ prefix. If it is the longest matching prefix, Nginx skips regex checks and uses that block.

the media prefix wins with ^~
curl -i http://127.0.0.1:18081/media/app.css
HTTP/1.1 200 OK
...
PREFIX: media, regex skipped

حواست باشد ^~ جلوی exact match را نمی‌گیرد و regex را به‌طور سراسری خاموش نمی‌کند؛ فقط وقتی همان prefix طولانی‌ترین مورد مطابق باشد، مرحلهٔ بررسی regex را برای آن درخواست کنار می‌زند. اگر prefix بلندتری بدون ^~ پیدا شود، نتیجه دوباره فرق می‌کند.

Note that ^~ does not override an exact match and does not disable regex globally. It skips regex checks for a request only when that prefix is the longest matching prefix. A still-longer prefix without ^~ can change the result again.

نسخهٔ فشردهٔ الگوریتم کلاسیکThe classic algorithm, compactly

اول exact؛ اگر نبود، بلندترین prefix را پیدا کن. اگر آن prefix ^~ داشت، همان برنده است و regex/predicate بررسی نمی‌شود. وگرنه regexها به ترتیب config می‌آیند؛ اولین match برنده است. در الگوریتم کلاسیک، اگر regexای نخورد، به prefix ذخیره‌شده برمی‌گردیم. از Nginx 1.31.5 به بعد یک مرحلهٔ predicate location هم پس از regexها وجود دارد؛ اگر از آن syntax استفاده می‌کنی، مرحلهٔ آن را هم پیش از fallback به prefix بررسی کن.

First check exact; otherwise find the longest prefix. If it has ^~, it wins and regex/predicate checks are skipped. Otherwise test regexes in config order; the first match wins. In the classic algorithm, if no regex matches, fall back to the remembered prefix. Since Nginx 1.31.5, there is also a predicate-location stage after regexes; if you use that syntax, check that stage before falling back to the prefix.

بدنهٔ REGEX: static خلاف انتظار است، اما با الگوریتم جور درمی‌آید: prefix بلندتر پیدا و ذخیره شد؛ چون ^~ نداشت، regexها هم بررسی شدند؛ regex اول CSS را گرفت. هنوز هیچ‌چیز را تغییر نده. اگر config مؤثر با چیزی که می‌خوانی یکی است، این پاسخ نتیجهٔ مستقیم ترتیب تصمیم است، نه تصادف.

The REGEX: static body is surprising but consistent with the algorithm: the longer prefix was found and remembered; because it lacked ^~, regex checks continued; the first CSS regex matched. Do not change anything yet. If the effective config is the one you read, this response follows directly from the decision order—it is not random.

Now make just one change: turn location /docs/api/ into location ^~ /docs/api/. Test syntax and reload only the lab. Predict: which block will return this CSS request now?

Because we sent the same URL to the same port after one controlled change, the different body is evidence of ^~’s effect. This does not prove any API works; we only changed location selection. Exact matches still take precedence.

^~ را چسب زخم نکنDo not use ^~ as a bandage

اگر regex به مسیر اشتباه می‌رسد، اول روشن کن کدام درخواست باید در کدام قاعده باشد. ^~ فقط regexها را پس از بلندترین prefix کنار می‌زند؛ اگر prefixها هم بد طراحی شده باشند، این modifier علت اصلی را پنهان می‌کند. در production همان config مؤثر و یک درخواست نمونه را بررسی کن.

If a regex reaches the wrong path, first clarify which requests should use which rule. ^~ only skips regexes after the longest prefix; if the prefixes are poorly designed, the modifier can hide the real problem. Inspect the effective config and one representative request in production.

location خود URL کامل را نمی‌بیندA location does not see the full URL

دیدیم query string را نمی‌سنجد. پیش از آن هم URI برای تطبیق به شکل نرمال‌شده استفاده می‌شود: بخش‌های percent-encoded decode می‌شوند، اجزای نقطه‌ای مسیر حل می‌شوند و با تنظیم پیش‌فرض، slashهای پشت‌سرهم به یک slash تبدیل می‌شوند. پس گاهی رشته‌ای که در مرورگر تایپ شده دقیقاً رشته‌ای نیست که prefix/regex می‌بیند.

We saw that the query string is not tested. Before matching, the URI is also normalized: percent-encoded parts are decoded, dot path components are resolved, and—by default—repeated slashes are compressed. So the string typed in the browser is not always exactly the string a prefix or regex sees.

این جزئیات برای خواندن مثال‌ها مهم است، نه دعوت به ساختن مسیرهای مبهم. برای یک بررسی کنترل‌شده می‌توانی شکل خام و پاسخ را کنار هم ثبت کنی؛ اما اگر ورودی encoded یا slashهای تکراری داری، config را با نسخهٔ Nginx خودت آزمایش کن. خاموش‌کردن merge_slashes تصمیم امنیتی/سازگاری است، نه راه معمول رفع مشکل.

This matters when reading examples; it is not an invitation to create ambiguous paths. For a controlled check, record the raw request and response together. If encoded input or repeated slashes matter to your application, test with your installed Nginx version. Turning off merge_slashes is a security/compatibility decision, not a routine fix.

root مسیر را اضافه می‌کند؛ alias prefix را جایگزینroot appends the URI; alias replaces its prefix

فرض کن location درست را پیدا کرده‌ای، ولی فایل وجود ندارد. ممکن است قاعدهٔ انتخاب درست باشد و مسیر دیسک غلط ساخته شود. تفاوت root و alias همین‌جا مهم می‌شود؛ این دو مسیر فایل را می‌سازند، نه اینکه location برنده را انتخاب کنند.

Suppose you found the right location, but the file is missing. The rule may be correct while the filesystem path is wrong. That is where the difference between root and alias matters; they build a file path, not the winning location.

در مثال root، URI به مسیر root افزوده می‌شود؛ در مثال alias، بخش منطبق location با مسیر alias جایگزین می‌شود. فلش‌ها تبدیل مسیر را نشان می‌دهند، نه جریان شبکه را.

With root, the URI is appended to the root path; with alias, the matching location prefix is replaced by the alias path. Arrows show path construction, not network traffic.

برای prefixای مثل /img/، با root /srv/site تکهٔ /img/ هم به مسیر دیسک می‌آید؛ با alias /data/images/ آن prefix حذف و با مسیر جایگزین می‌شود. در الگوی رایجِ location و alias، slash پایانی دو طرف را هماهنگ نگه دار. اگر 404 دیدی، اول با یک نشانگر جدا ثابت کن کدام location انتخاب شده؛ بعد مسیر نهایی و وجود و دسترسی فایل را بررسی کن.

دام کوچکِ slash را هم ببین: در location /img/ اگر مقدار را alias /data/images بنویسی، بخش باقی‌ماندهٔ URI ممکن است بی‌فاصله به انتهای مسیر بچسبد؛ برای /img/logo.svg مسیر مورد انتظار /data/images/logo.svg است، نه یک رشتهٔ چسبیده. slash پایانی alias را نگه دار و مسیر را با درخواست آزمایشی و وجود فایل روی دیسک تأیید کن.

There is also a small trailing-slash trap: with location /img/, writing alias /data/images can concatenate the remaining URI suffix directly to the path. For /img/logo.svg, the intended path is /data/images/logo.svg, not a concatenated string. Keep the alias trailing slash and verify the mapping with a test request and the file on disk.

For a prefix such as /img/, root /srv/site keeps /img/ in the filesystem path; alias /data/images/ removes that prefix and substitutes the new path. In the common location/alias pattern, keep trailing slashes aligned. If you get a 404, first prove the winner with a distinct marker, then inspect the resulting path and file existence/permissions.

یک دام رایج این است که از روی نام location فکر کنیم فایل حتماً زیر پوشه‌ای هم‌نام قرار می‌گیرد. بعد از محاسبهٔ مسیر، از ابزار سیستم خودت وجود فایل را بررسی کن؛ root و alias رفتار یکسانی ندارند و جایگزین هم نیستند. در فصل فایل استاتیک، مسیر فایل، index و رفتار پاسخ را مفصل‌تر دنبال می‌کنیم.

A common trap is assuming the file must live under a same-named directory just because the location has that name. Verify the computed path with your system tools; root and alias do not behave the same way and are not interchangeable. The static-files chapter will go deeper into file paths, index handling, and response behavior.

دو نکتهٔ کوتاه دربارهٔ locationهای پیشرفته‌ترTwo short notes on more advanced locations

همهٔ locationها مستقیماً با URL تطبیق داده نمی‌شوند. location نام‌دار با @name تعریف می‌شود و معمولاً مقصدی داخلی برای redirectهای خود Nginx است؛ کاربر نمی‌تواند با URLای مثل /@fallback مستقیماً آن را انتخاب کند. مثال‌های این فصل را عمداً تو‌در‌تو نکردیم تا ترتیب اصلی را جدا بفهمیم.

Not every location is matched directly against a URL. Named locations use @name and are usually internal targets for Nginx redirects; a client cannot select one directly with a URL such as /@fallback. Our examples stay flat so we can learn the main order separately.

locationهای تو‌در‌تو می‌توانند جست‌وجوی regex را در محدوده‌های مختلف پیچیده کنند؛ پس الگوریتم سادهٔ این صفحه را بی‌قیدوشرط به blockهای تو‌در‌تو تعمیم نده. اگر از nesting استفاده می‌کنی، درخت را دقیق بخوان و همان پیکربندی را با nginx -T و curl بیازما. میان‌بر ذهنیِ ساده بهتر از یک قانون نادرست نیست.

Nested locations can make regex searches across scopes more subtle; do not apply this page’s flat algorithm to nested blocks without qualification. If you use nesting, inspect the tree carefully and test that exact config with nginx -T and curl. A simple but false shortcut is not a useful mental model.

یادداشت نسخهVersion note

مستند جاری Nginx علاوه بر prefix و regex، predicate location بر پایهٔ متغیر را هم فهرست می‌کند؛ syntax آن در Nginx 1.31.5 اضافه شده است. این rule با location $variable نوشته می‌شود و پس از regexها بررسی می‌شود؛ اولین predicate مطابق می‌تواند برنده شود. اگر بلندترین prefix ^~ داشته باشد، predicateها هم بررسی نمی‌شوند. چون این قابلیت تازه‌تر و خارج از آزمایش مقدماتی ماست، syntax و محدودیتش را از مستند همان نسخه بخوان.

Current Nginx docs also list variable-based predicate locations; this syntax appeared in Nginx 1.31.5. Written as location $variable, it is checked after regexes, and the first matching predicate can win. If the longest prefix has ^~, predicates are skipped too. Because this feature is newer and outside our introductory lab, consult the docs for your exact version before using its syntax and constraints.

تمرین‌ها: پیش از دیدن پاسخ، location برنده را حدس بزنExercises: predict the winning location before opening the answer

از پیش‌بینی ساده شروع می‌کنیم، اما آخر تمرین‌ها فقط حفظ ترتیب کافی نیست: باید evidence را بخوانی، خرابی را از مرز درست تشخیص بدهی و امن‌ترین آزمایش بعدی را انتخاب کنی.

We begin with simple predictions, but memorizing the order is not enough by the end. You will need to read evidence, locate the failing boundary, and choose the safest next experiment.

۱. یک exact در میان prefixها1. One exact among prefixes

config شامل location = /health، location / و regex عمومی است. برای URI برابر /health چه کسی برنده است؟

The config has location = /health, location /, and a general regex. Which wins for URI /health?

پاسخ را ببینShow solution

exact، چون match دقیق جست‌وجو را تمام می‌کند. نه طولانی‌ترین prefix و نه regex عمومی بعد از آن فرصت برنده‌شدن ندارند. یک درخواست curl با body یکتا تأییدش می‌کند.

The exact location, because an exact match ends the search. Neither the longest prefix nor the general regex gets a chance to win. Verify with curl and a unique body.

۲. query را از مسیر جدا کن2. Separate the query from the path

برای /health?detail=1 آیا location = /health match می‌شود؟ توضیح بده کدام بخش URI location را انتخاب می‌کند.

Does location = /health match /health?detail=1? Explain which part selects the location.

پاسخ را ببینShow solution

بله. برای انتخاب location، query arguments ملاک نیستند؛ URI مسیر /health است. این به معنی نادیده‌گرفته‌شدن query برای کل برنامه نیست؛ فقط location matching را انتخاب نمی‌کند.

Yes. Query arguments do not participate in location selection; the path URI is /health. That does not mean the application ignores the query entirely—only that it does not select the location.

۳. prefix بلندتر3. The longer prefix

سه rule داری: /، /docs/ و /docs/api/. برای /docs/api/users کدام prefix candidate می‌شود؟

You have three rules: /, /docs/, and /docs/api/. Which prefix becomes the candidate for /docs/api/users?

پاسخ را ببینShow solution

بلندترین prefix مطابق، یعنی /docs/api/. این پاسخ هنوز برندهٔ نهایی را تضمین نمی‌کند؛ اگر ^~ ندارد، regexهای بعدی ممکن است انتخاب را عوض کنند.

The longest matching prefix, /docs/api/. This does not yet guarantee the final winner; without ^~, a later regex may change the selection.

۴. دو regex، یک URI4. Two regexes, one URI

ابتدا location ~* \.css$ و بعد location ~* \.(css|js)$ آمده‌اند. برای /app.css کدام برنده است و چرا؟

First comes location ~* \.css$, followed by location ~* \.(css|js)$. Which wins for /app.css, and why?

پاسخ را ببینShow solution

اولی، چون هر دو match می‌شوند ولی regexها به ترتیب config بررسی و با اولین match متوقف می‌شوند. این با prefixها فرق دارد که بلندترین انتخاب می‌شود، نه اولین خط.

The first one, because both match but regexes are tested in config order and stop at the first match. This differs from prefixes, where the longest is selected rather than the first line.

۵. حساسیت به حروف5. Case sensitivity

یک rule با ~ \.css$ داری. آیا /APP.CSS را می‌گیرد؟ اگر رفتار بدون حساسیت به case می‌خواهی چه modifierی را بررسی می‌کنی؟

You have a ~ \.css$ rule. Will it match /APP.CSS? Which modifier would you consider for case-insensitive behavior?

پاسخ را ببینShow solution

نه؛ ~ برای regex حساس به بزرگی/کوچکی حروف است. ~* حالت case-insensitive می‌دهد. بااین‌حال پیش از تغییر، مطمئن شو URI نرمال‌شده واقعاً همان suffix را دارد و ترتیب regex دیگری زودتر برنده نشده.

No. ~ makes regex matching case-sensitive. ~* is case-insensitive. Before changing it, confirm the normalized URI has that suffix and no earlier regex wins first.

۶. ^~ در کجای انتخاب اثر می‌کند؟6. Where does ^~ take effect?

location ^~ /media/ و location ~* \.css$ هر دو با /media/app.css جورند. چه چیزی را انتظار داری؟

Both location ^~ /media/ and location ~* \.css$ match /media/app.css. What do you expect?

پاسخ را ببینShow solution

اگر /media/ بلندترین prefix است، همان برنده است و regex بررسی نمی‌شود. ^~ regex را globally خاموش نمی‌کند؛ اثرش مشروط به این است که این prefix بلندترین مورد باشد.

If /media/ is the longest prefix, it wins and regex checks are skipped. ^~ does not disable regex globally; it applies only when this is the longest matching prefix.

۷. regex را جابه‌جا کنیم؟7. Should we reorder the regexes?

برای /docs/api/file.css می‌خواهی prefix API پاسخ دهد، نه regex عمومی فایل‌ها. یک راه ^~ است. آیا جابه‌جاکردن regex CSS به پایین هم کافی است؟ فرق این دو راه را بگو.

For /docs/api/file.css, you want the API prefix to answer instead of the general file regex. One option is ^~. Would moving the CSS regex lower also be enough? Explain the difference.

پاسخ را ببینShow solution

نه لزوماً؛ اگر regex دیگری هم match شود، پایین‌بردن یک regex فقط ترتیب را بین regexها عوض می‌کند. ^~ روی بلندترین prefix می‌گوید برای آن مسیر اصلاً regex مرحلهٔ بعد را نسنج. انتخاب درست به قرارداد مسیرهای API و فایل وابسته است؛ درخواست را قبل و بعد با body یکتا آزمایش کن.

Not necessarily. Another regex may still match; moving one regex only changes order among regexes. ^~ on the longest prefix says not to test the next regex stage for that path. Choose based on the API/file routing contract and verify the same request with unique bodies before and after.

۸. 404 یا winner اشتباه؟8. A 404 or the wrong winner?

یک 404 می‌بینی و می‌خواهی regex را تغییر بدهی. چطور اول تشخیص می‌دهی location درست انتخاب شده ولی فایل نیست، یا location دیگری پاسخ داده؟

You see a 404 and want to change a regex. How do you first distinguish “the right location won but the file is missing” from “a different location answered”?

پاسخ را ببینShow solution

موقتاً برای ruleهای موردنظر پاسخ یکتا (body یا header آزمایشگاهی) می‌گذارم یا log/config مؤثر را بررسی می‌کنم. بعد از ثابت‌کردن winner، مسیر دیسک، root/alias، وجود و دسترسی فایل را می‌سنجم. status به‌تنهایی انتخاب location را نشان نمی‌دهد.

Temporarily give candidate rules distinct lab responses or inspect effective config/logs. After proving the winner, check the filesystem path, root/alias, file existence, and permissions. Status alone does not identify the selected location.

۹. root چه مسیری می‌سازد؟9. What path does root build?

یک location /img/ با root /srv/site; داری. درخواست /img/logo.svg کدام مسیر را می‌جوید؟

You have location /img/ with root /srv/site;. Which path is checked for /img/logo.svg?

پاسخ را ببینShow solution

مسیر با افزودن URI به root ساخته می‌شود: /srv/site/img/logo.svg. اگر فایل در /srv/site/logo.svg است، root و ساختار مسیر باهم جور نیستند؛ برای mapping جایگزین ممکن است alias مناسب باشد.

The URI is appended to root: /srv/site/img/logo.svg. If the file is at /srv/site/logo.svg, the root and path structure do not align; alias may be appropriate for a replacement mapping.

۱۰. alias چه چیزی را حذف می‌کند؟10. What does alias replace?

با location /img/ { alias /data/images/; } درخواست /img/logo.svg چه مسیر فایلی می‌سازد؟

With location /img/ { alias /data/images/; }, what filesystem path does /img/logo.svg map to?

پاسخ را ببینShow solution

prefix منطبق /img/ با /data/images/ جایگزین می‌شود، پس مسیر /data/images/logo.svg است. برای اطمینان، slashهای پایانی دو طرف و مسیر واقعی فایل را کنار هم بررسی کن.

The matching /img/ prefix is replaced with /data/images/, yielding /data/images/logo.svg. Check both trailing slashes and the real file path to confirm the mapping.

۱۱. query روی regex اثر گذاشت؟11. Did the query affect the regex?

location ~ \.php$ داری. آیا /index.php?mode=css این regex را می‌گیرد؟ چرا؟

You have location ~ \.php$. Does it match /index.php?mode=css? Why?

پاسخ را ببینShow solution

بله؛ regex روی URI path یعنی /index.php اعمال می‌شود و query ?mode=css جزو رشتهٔ تطبیق نیست. در عمل می‌توانی با body یکتا یا curl -i این را ببینی، اما نگذار query گمراهت کند.

Yes. The regex is applied to the URI path, /index.php; ?mode=css is not part of the match string. A unique body or curl -i can verify it, but do not let the query mislead you.

۱۲. «اولین prefix» اشتباه است12. “First prefix” is wrong

دو prefix مطابق‌اند: خط اول location / و خط پایین‌تر location /docs/. برای /docs/start کدام را می‌گیری؟

Two prefixes match: first location /, then a later location /docs/. Which one handles /docs/start?

پاسخ را ببینShow solution

/docs/ چون بلندتر است، مستقل از ترتیب تعریف prefixها. ترتیب config برای regexها مهم است؛ برای prefixها طول مهم است، مگر exact یا رفتار modifierها تصمیم را عوض کند.

/docs/, because it is longer, regardless of prefix declaration order. Config order matters for regexes; prefix length matters for prefixes unless exact matching or modifiers change the decision.

۱۳. /media/app.css13. /media/app.css

هم location ^~ /media/ و هم regex اول location ~* \.css$ match هستند. دقیقاً کدام marker باید برگردد؟

Both location ^~ /media/ and the first location ~* \.css$ regex match. Which marker should be returned?

پاسخ را ببینShow solution

marker مربوط به ^~ /media/؛ چون آن prefix بلندترین match است، مرحلهٔ regex انجام نمی‌شود. اگر response از regex آمد، بررسی کن واقعاً همین config بار شده و prefixهای دیگری طولانی‌تر نیستند.

The ^~ /media/ marker. Because it is the longest match, the regex stage is skipped. If the regex response appears, confirm this config is loaded and no longer prefix changes the candidate.

۱۴. شش regex در یک config14. Six regexes in one config

در چند regex، دو قاعدهٔ اول هر دو URI را match می‌کنند؛ قاعدهٔ دلخواهت سوم است. آیا سوم به‌علت «خاص‌تر بودن» برنده می‌شود؟

Several regexes match, and your preferred rule is third. Does it win because it is “more specific”?

پاسخ را ببینShow solution

نه؛ regexها با ترتیب config سنجیده می‌شوند و اولین match تمام می‌کند. خودت قاعده‌ها را طوری مرتب کن که قرارداد روشن باشد، یا prefix/دسته‌بندی را بازطراحی کن؛ «خاص‌تر» اولویت خودکار نیست.

No. Regexes are tested in config order and the first match stops the search. Order the rules to express the intended contract or redesign the prefix grouping; “more specific” is not an automatic priority rule.

۱۵. root درست است یا winner؟15. Is root wrong, or is the winner wrong?

marker نشان می‌دهد location مورد انتظار برنده شده، اما Nginx فایل را پیدا نمی‌کند. دو بررسی بعدی را به‌ترتیب بنویس.

The marker proves the intended location won, but Nginx cannot find the file. Name the next two checks in order.

پاسخ را ببینShow solution

اول مسیر نهایی را با قاعدهٔ همان root/alias محاسبه می‌کنم؛ بعد وجود فایل و permission پوشه/فایل را در همان مسیر می‌سنجم. عوض‌کردن regex در این مرحله مسئلهٔ انتخابی را که قبلاً ثابت شده دوباره باز می‌کند.

First calculate the final path using that rule’s root/alias behavior; then check file existence and directory/file permissions at that exact path. Changing the regex reopens a selection problem already proven correct.

۱۶. تغییر امن یک modifier16. Safely changing one modifier

در production، CSS از زیرمسیر API به regex می‌رود. قبل از افزودن ^~ چه دو چیز را روشن می‌کنی و چه چیزی را بعدش دوباره می‌سنجی؟

In production, CSS under an API path goes to a regex. What two things do you clarify before adding ^~, and what do you retest afterwards?

پاسخ را ببینShow solution

اول قرارداد مطلوب برای فایل‌های زیر API و دقیقاً کدام prefix بلندترین است؛ بعد مطمئن می‌شوم regex نباید عمداً برای آن مسیر اجرا شود. config را backup/review می‌کنم، -t می‌گیرم، reload کنترل‌شده و همان URL را با marker و status دوباره می‌آزمایم. تغییر modifier همهٔ رفتارهای برنامه را ثابت نمی‌کند.

First clarify the intended handling of files below the API and which prefix is actually longest; then confirm regex should not run for that path. Back up/review the config, run -t, reload in a controlled way, and retest the same URL with its marker and status. A modifier change does not prove every application behavior.

۱۷. نتیجهٔ خام و نرمال‌شده17. Raw and normalized request paths

یک URL دارای percent-encoding یا slashهای تکراری به prefix مورد انتظار نمی‌رسد. قبل از بازنویسی regex، چه شواهدی جمع می‌کنی؟

A URL with percent-encoding or repeated slashes does not reach the expected prefix. What evidence do you collect before rewriting the regex?

پاسخ را ببینShow solution

request خام و URIای که Nginx برای matching نرمال می‌کند را جدا بررسی می‌کنم، بعد با یک URL ساده و یک نمونهٔ encoded در config آزمایش درخواست می‌فرستم. تنظیم merge_slashes و نسخه را می‌سنجم؛ آن را صرفاً برای اینکه یک regex match شود خاموش نمی‌کنم.

Separate the raw request from the normalized URI Nginx matches, then test a simple URL and an encoded example against a lab config. Check version and merge_slashes; do not disable it merely to force one regex to match.

۱۸. بلیت عیب‌یابی نهایی18. Final debugging ticket

بلیت: «/docs/api/manual.pdf باید از API بیاید؛ الان از قاعدهٔ فایل‌های عمومی پاسخ می‌گیرد.» یک تشخیص مرحله‌ای بساز که exact، طولانی‌ترین prefix، ^~ و ترتیب regex را بررسی کند و به تغییر تصادفی ختم نشود.

Ticket: “/docs/api/manual.pdf should be handled by the API; it currently receives the general file response.” Build a stepwise diagnosis that checks exact match, longest prefix, ^~, and regex order without random edits.

پاسخ را ببینShow solution

با curl همان URL و body/header یکتا، winner فعلی را ثابت می‌کنم. در config مؤثر -T اول exactهای ممکن، سپس همهٔ prefixها و طولانی‌ترینشان را پیدا می‌کنم. اگر prefix API ^~ ندارد، regexها را به ترتیب می‌سنجم تا اولین match را بیابم. بعد با قرارداد تیم تصمیم می‌گیرم ^~ لازم است یا regex باید محدودتر شود؛ یک تغییر، -t، reload آزمایش‌شده و همان درخواست را تکرار می‌کنم.

Use curl with a unique body/header to prove the current winner. In the effective config from -T, check exact locations, then all prefixes and the longest one. If the API prefix lacks ^~, test regexes in order to find the first match. Decide from the team’s routing contract whether ^~ is needed or the regex should be narrower; make one change, run -t, reload safely, and repeat the same request.

ماموریت: جدول locationهای برنده را ثابت کنMission: prove your own winner table

یک پیکربندی کوچک در اختیار داری، نه Nginx یک محیط واقعی. باید ده نشانی را پیش‌بینی کنی، پاسخ واقعی بگیری، یک مسیر را عمداً به قاعدهٔ نادرست بفرستی و توضیح بدهی چه چیزی انتخاب را عوض کرد. معیار موفقیت تعداد دستورها نیست؛ جدول پیش‌بینی‌ای است که با متن پاسخ‌ها جور دربیاید.

You have a small config, not a production Nginx. Predict ten URLs, collect real responses, deliberately misroute one path, and explain what changed the winner. Success is not the number of commands; it is a prediction table that agrees with the response bodies.

  1. پیکربندی آزمایشگاه این فصل را در پوشهٔ LAB_DIR بساز و nginx -t بگیر. پیش از اجرا، آزادبودن پورت را بررسی کن.Create this chapter’s lab config under LAB_DIR and run nginx -t. Check that the port is free before starting.
  2. برای هر ده ردیف جدول تصمیم، location برنده و دلیل یک‌خطی را پیش از اجرای curl بنویس. اگر مطمئن نیستی، دقیقاً مشخص کن کدام قاعده‌ها ممکن است تطبیق کنند.Before curl, write a winner and one-line reason for each of the ten decision-table rows. If unsure, list exactly which rules may match.
  3. حلقهٔ درخواست‌ها را اجرا کن و متن پاسخ‌ها را ذخیره کن. هر اختلاف را با URI، prefixها و ترتیب regex توضیح بده؛ کد وضعیت ۲۰۰ به‌تنهایی کافی نیست.Run the loop and record the bodies. Explain every difference using the URI, prefixes, and regex order; status 200 alone is not enough.
  4. خرابی را بساز: در config آزمایش، ^~ را از /media/ بردار (یا آن را از /docs/api/ بردار تا عمداً regex جلو بزند). قبل از تغییر، پاسخ همان URL را ثبت کن.Create the failure: remove ^~ from /media/ (or from /docs/api/ so the regex deliberately wins). Record the same URL’s response before changing it.
  5. با یک تغییر اصلاحش کن، -t بگیر، فقط آزمایشگاه را reload کن و همان URL را دوباره بفرست. تغییر بدنه را به مرحلهٔ regex نسبت بده، نه چند تغییر هم‌زمان.Restore the modifier with one change, run -t, reload only the lab, and resend the same URL. Attribute the body change to the regex stage, not to several simultaneous edits.
  6. در پایان یک آزمایش جدا برای مسیر root و alias طراحی کن؛ مسیر فایل مورد انتظار را پیش از درخواست روی کاغذ محاسبه کن. اگر 404 شد، ابتدا همین محاسبه و وجود فایل را بررسی کن، نه اولویت location را که جداگانه ثابت کرده‌ای.Finally design a separate root/alias path test; calculate the expected file path before requesting it. If it returns 404, inspect that calculation and file existence first, not the location priority already proven separately.
  7. فرایند آزمایشگاه را با -s quit و همان -p/-c متوقف کن. PID را بررسی کن، مسیر LAB_DIR را دوباره چاپ و تأیید کن، و فقط بعد از پایان فرایند همان پوشهٔ موقت را پاک کن.Stop the lab with -s quit and the same -p/-c. Verify the PID, print and recheck LAB_DIR, then remove only that temporary directory after the process exits.
سرنخ‌ها را فقط اگر لازم شد باز کنOpen hints only if you need them

اگر location برنده را پیدا نمی‌کنی، اول exact را جدا کن؛ بعد prefixهای مطابق را از کوتاه به بلند بنویس؛ سپس ببین بلندترینشان ^~ دارد یا نه؛ در غیر این صورت regexها را به ترتیب فایل بررسی کن. این ترتیب را برعکس نکن.

If you cannot find the winner, isolate exact matches first; list matching prefixes from shortest to longest; check whether the longest has ^~; otherwise walk regexes in file order. Do not reverse this sequence.

گزارش پایان کارFinish with a short report

ده ردیف را با location برندهٔ پیش‌بینی‌شده و متن واقعی پاسخ تحویل بده. برای خرابی عمدی، یک جمله دربارهٔ علت، یک مدرک پیش از اصلاح و همان درخواست پس از اصلاح اضافه کن. بنویس آزمایش فقط روی loopback بوده و سلامت upstream، DNS عمومی یا فایل‌های واقعی سایت را ثابت نمی‌کند.

Submit ten rows with predicted winners and actual bodies. For the deliberate failure, include one sentence about its cause, evidence before repair, and the same request after repair. State that the lab used loopback only and does not prove upstream health, public DNS, or real site files.

حالا که location برنده را می‌دانیم، فایل واقعی چطور سرو می‌شود؟Now that we know the winner, how is a real file served?
