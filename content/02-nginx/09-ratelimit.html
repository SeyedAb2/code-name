rate limiting و محافظت

Rate limiting and protection

فرم ورود سالم است، اما یک کلاینت آن را پشت‌سرهم صدا می‌زند و پردازه‌های برنامه مشغول می‌مانند. آیا Nginx می‌تواند جلوی هر حمله‌ای را بگیرد؟ نه؛ اما می‌تواند بخشی از فشار را بر اساس کلیدی روشن و محدودیتی سنجیده کنترل کند. اول ببینیم کدام درخواست‌ها را واقعاً می‌خواهیم محدود کنیم.

The login form works, but one client calls it repeatedly and keeps app workers busy. Can Nginx stop every attack? No—but it can control some pressure using a deliberate key and a measured limit. First, let’s decide which requests we actually want to limit.

درخواست زیاد را با مهاجم یکی نگیریمDo not confuse high request volume with an attacker

بعد از فصل HTTPS، حالا ارتباط کاربر تا Nginx امن است؛ اما امنیت اتصال جلوی تکرار زیاد درخواست را نمی‌گیرد. ممکن است کاربر روی دکمه دوبار کلیک کند، مرورگر retry بزند یا ربات رمزها را حدس بزند. محدودکردن همه با یک عدد می‌تواند کاربران واقعی را هم بیرون بیندازد.

After HTTPS, the client-to-Nginx connection is secure—but secure transport does not stop repeated requests. A user may double-click, a browser may retry, or a bot may guess passwords. Applying one blunt number to everyone can lock out legitimate users too.

پس سؤال را کوچک می‌کنیم: کدام مسیر پرهزینه است؟ بر چه مبنایی درخواست‌ها را گروه می‌کنیم؟ چه مقدار فشار کوتاه‌مدت طبیعی است؟ اگر هر درخواست از IP یک proxy مشترک برسد، آیا محدودیت واقعاً هر کاربر را جدا می‌بیند؟

So narrow the problem: which route is costly? How should requests be grouped? What short burst is normal? If every request arrives from one proxy IP, will the limit really distinguish users?

rate limit سپر همه‌کاره نیستA rate limit is not a universal shield

Nginx می‌تواند پردازش بعضی درخواست‌ها را کم یا رد کند، اما DDoS حجیمِ شبکه را لزوماً متوقف نمی‌کند، IP توزیع‌شده را یکی نمی‌کند، حساب کاربری را نمی‌شناسد و جای احراز هویت، CAPTCHA، کنترل تقلب یا ظرفیت کافی را نمی‌گیرد.

Nginx can delay or reject some requests, but it does not necessarily stop a large network-layer DDoS, combine a distributed set of IPs into one identity, identify user accounts, or replace authentication, CAPTCHA, fraud controls, or sufficient capacity.

اول بگو «هر درخواست از چه کسی؟»First ask, “Who does each request belong to?”

Nginx برای محدودیت یک key می‌خواهد؛ مقدار آن می‌گوید وضعیت درخواست‌ها برای چه گروهی مشترک باشد. انتخاب رایج، IP کلاینت است: $binary_remote_addr. اما اگر Nginx پشت reverse proxy یا CDN باشد، $remote_addr معمولاً IP همان proxy است، نه کاربر.

Nginx needs a key for the limit: its value decides which requests share state. A common choice is the client IP, represented by $binary_remote_addr. But behind a reverse proxy or CDN, $remote_addr is usually the proxy’s address, not the user’s.

هدر X-Forwarded-For را هم نمی‌شود کورکورانه باور کرد؛ هر کلاینتی می‌تواند چنین headerی بفرستد. فقط وقتی آدرسِ اتصال از فهرست proxyهای مورداعتماد است، header تعیین‌شده از طرف همان proxy را بپذیر. شبکه‌های اعتمادشده را از مستند provider بگیر، نه از یک بازهٔ حدسی.

Do not blindly trust X-Forwarded-For; any client can send that header. Accept the configured forwarding header only when the connection comes from a trusted proxy. Get trusted ranges from the provider’s documentation, not from a guessed network.

فلش‌ها مسیر درخواست‌اند. اگر Nginx فقط اتصال proxy را ببیند، هر دو کاربر یک کلید خواهند داشت و بودجهٔ rate را شریک می‌شوند؛ header ارسالی فقط وقتی هویت می‌دهد که proxy فرستنده مورداعتماد باشد.

Arrows show the request path. If Nginx sees only the proxy connection, both clients share one rate key; a forwarded header is useful only when its sender is trusted.

در lab فعلی همهٔ درخواست‌های curl از 127.0.0.1 می‌آیند؛ پس طبیعی است یک کلید داشته باشند. این آزمایش رفتار IPهای متفاوت را شبیه‌سازی نمی‌کند. در محیط واقعی، log نشانی TCPای را که Nginx می‌بیند کنار header ورودی می‌گذارد؛ بعد از تنظیم ماژول real-IP، همان آزمایش را از مسیر proxy واقعی تکرار کن.

In this lab, all curl requests come from 127.0.0.1, so one key is expected. This does not simulate distinct client IPs. In production, log the TCP address Nginx sees alongside the incoming header; after configuring real-IP handling, repeat the test through the actual proxy.

rate یعنی میانگین؛ burst جا برای موج کوتاهRate is an average; burst allows a short wave

محدودیت نرخ را مثل شیر آب تصور کن: مقدار مشخصی درخواست در زمان پردازش می‌شود؛ موج کوتاه می‌تواند موقتاً از ظرفیت burst استفاده کند. این تصویر، مدل ذهنی leaky bucket است، نه نقشهٔ دقیق هر تصمیم داخلی Nginx.

Think of the rate limit as a drain: requests are processed at a configured average rate, while a short wave can use the burst allowance. This is a leaky-bucket mental model, not a diagram of every internal Nginx decision.

در حالت پیش‌فرض، درخواست‌های اضافه ممکن است با تأخیر پردازش شوند؛ با nodelay درخواست‌های داخل burst بی‌درنگ عبور می‌کنند ولی از ظرفیت burst خرج می‌شود. شکل فقط مدل leaky bucket را نشان می‌دهد، نه زمان‌بندی دقیق threadها.

By default, excess requests may be delayed; with nodelay, requests within the burst allowance pass immediately but consume that allowance. The sketch shows the leaky-bucket model, not exact thread scheduling.

برای نمونه، rate=2r/s یعنی میانگین حدود دو درخواست در ثانیه برای هر key؛ burst=4 چهار درخواست اضافه را تحمل می‌کند، نه اینکه نرخ دائمی را به شش برساند. درخواست‌های بیشتر از حد، با status انتخاب‌شده رد می‌شوند.

For example, rate=2r/s means an average of about two requests per second per key; burst=4 tolerates four excess requests, not a permanent rate of six. Requests beyond the allowance are rejected with the configured status.

zone مشترک وضعیت هر key را میان workerهای Nginx نگه می‌دارد. اندازهٔ 10m یعنی حافظهٔ مشترک برای این stateهاست، نه نرخ، نه تعداد درخواست مجاز و نه ذخیرهٔ log. اگر تعداد زیادی key یکتا داشته باشی، ظرفیت zone هم اهمیت پیدا می‌کند.

The shared zone stores each key’s state across Nginx workers. A size such as 10m is memory for that state—not a rate, request allowance, or log store. If many unique keys appear, zone capacity matters too.

پیش از محدودکردن، یک مسیر بی‌خطر بسازیمBefore limiting, create a harmless route

برای سنجیدن اثر تنظیم، endpoint مصنوعی می‌سازیم که فقط نام مسیر و مقدار کوچکی را برمی‌گرداند؛ هیچ حسابی نمی‌سازد و رمز ذخیره نمی‌کند. Nginx روی loopback است و برنامه روی loopback دیگری. این آزمایش را روی production یا نشانی عمومی اجرا نکن.

To measure the config, we will make a synthetic endpoint that only echoes its path and a small value; it creates no accounts and stores no passwords. Nginx and the app bind to loopback. Do not run this test against production or a public address.

اول آزادبودن پورت‌های 18090 و 19090 را بررسی کن و پوشهٔ موقت بساز. اگر پورت اشغال است، سرویسش را متوقف نکن؛ شمارهٔ آزاد دیگری بردار و در همهٔ فرمان‌ها جایگزینش کن.

سرور آزمایشی فقط دو مسیر دارد: /login و /slow. اولی مکث کوتاهی دارد تا موج درخواست قابل‌دیدن شود؛ دومی یک ثانیه می‌ماند تا محدودیت اتصال فعال را ببینیم.

The test app has only two paths: /login and /slow. The first pauses briefly so a request wave is visible; the second waits one second so we can observe an active-connection limit.

create a tiny loopback-only test app
cat > "$RATE_LAB/app.py" <<'PY'
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import urlsplit
import sys
import time

port = int(sys.argv[1])

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        path = urlsplit(self.path).path
        time.sleep(0.4 if path == "/login" else 1.0 if path == "/slow" else 0)
        body = f"test endpoint: {path}\n".encode()
        self.send_response(200)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

ThreadingHTTPServer(("127.0.0.1", port), Handler).serve_forever()

اول بدون burst: هر درخواست فوری؟First, no burst: does every request pass immediately?

حالا Nginx را جلو می‌گذاریم، اول بدون محدودیت تا خط پایه داشته باشیم. limit_req_zone فقط در http تعریف می‌شود؛ خود limit_req را بعداً برای مسیر ورود می‌گذاریم.

Now put Nginx in front, initially without a limit so we have a baseline. Define limit_req_zone in the http context; we will apply limit_req to the login route afterward.

start with an observable baseline configuration
cat > "$RATE_LAB/nginx.conf" <<'NGINX'
worker_processes 1;
pid run/nginx.pid;
error_log logs/error.log notice;
events { worker_connections 128; }
http {
    log_format rate '$remote_addr xff="$http_x_forwarded_for" "$request" status=$status '
                    'req=$limit_req_status conn=$limit_conn_status '
                    'time=$request_time';
    access_log logs/access.log rate;
    limit_req_zone $binary_remote_addr zone=login_ip:10m rate=2r/s;
    limit_conn_zone $binary_remote_addr zone=login_conn:10m;
    server {
        listen 127.0.0.1:18090;
        server_name localhost;
        limit_req_status 429;
        limit_conn_status 429;
        location / {
            proxy_pass http://127.0.0.1:19090;
            proxy_set_header Host $host;
        }
    }
}
NGINX
nginx -t -p "$RATE_LAB/" -c nginx.conf

log آزمایش IP اتصال و مقدار header ورودی XFF را جدا از هم ثبت می‌کند، کنار وضعیت rate و مدت پاسخ. header فقط مدرک چیزی است که فرستنده نوشته، نه هویتی که باید بی‌قید قبول کنیم. متغیرهای $limit_req_status و $limit_conn_status در نسخه‌های جدید OSS در دسترس‌اند؛ اگر نسخه‌ات آن‌ها را نشناسد، موقتاً از log_format حذفشان کن و به status و error log نگاه کن.

The lab log records the connection IP and incoming XFF header separately, alongside the rate/connection result and response time. The header proves only what the sender supplied, not an identity to trust blindly. $limit_req_status and $limit_conn_status are available in modern OSS versions; if your version lacks them, temporarily remove them from log_format and inspect status and the error log.

آیا منتظرماندن برای مسیر ورود قابل‌قبول است؟Is waiting acceptable on the login route?

حالت پیش‌فرض درخواست‌های اضافه را با تأخیر عبور می‌دهد تا متوسط نرخ حفظ شود. برای جست‌وجو یا ورود ممکن است همین تأخیر چندثانیه‌ای تجربهٔ بدی بسازد. nodelay درخواست‌های داخل burst را فوری عبور می‌دهد؛ ظرفیت burst همچنان محدود است و درخواست‌های فراتر از آن رد می‌شوند.

By default, excess requests are delayed so the configured average rate is maintained. That wait may be undesirable for search or login. nodelay passes requests within the burst allowance immediately; the allowance is still bounded, and requests beyond it are rejected.

برای مقایسه فقط همین یک گزینه را عوض کن؛ نرخ، مسیر و تعداد درخواست را ثابت نگه دار. پیش‌بینی کن: زمان پاسخ‌های قبول‌شده چه می‌شود و پاسخ‌های فراتر از burst چه؟

در نمونه، latency درخواست‌های قبول‌شده کمتر شده ولی فشار همان لحظه به برنامه می‌رسد. nodelay نرخ میانگین را حذف نمی‌کند؛ burst بودجهٔ محدود است. اگر retryهای مرورگر هم‌زمان شوند، ممکن است همان بودجه را سریع مصرف کنند.

In the sample, accepted requests have lower latency, but their load reaches the app at once. nodelay does not remove the average rate; burst is a finite allowance. Synchronized browser retries can consume it quickly.

برای endpoint واقعی ورود، نرخ را از رفتار عادی کاربر و هزینهٔ backend انتخاب کن. عدد lab نسخهٔ production نیست. اگر نسخهٔ Nginx پشتیبانی کند، limit_req_dry_run on کمک می‌کند ابتدا وضعیت اضافه‌بودن را ثبت کنی بی‌آنکه درخواست را متوقف کنی؛ نسخه و log را بررسی کن و بعد محدودیت واقعی را با rollout سنجیده فعال کن.

Choose a real login rate from normal user behavior and backend cost; the lab number is not a production preset. On Nginx versions that support it, limit_req_dry_run on can record excess requests without rejecting them. Verify the version and logs, then enable enforcement through a measured rollout.

نرخ درخواست با تعداد اتصال فرق داردRequest rate is not the same as active connections

یک درخواست کند می‌تواند مدت زیادی اتصال را باز نگه دارد حتی اگر نرخ ورود پایین باشد. limit_conn_zone وضعیت اتصال‌های درحال‌پردازش را بر اساس key در حافظهٔ مشترک نگه می‌دارد؛ limit_conn سقف آن را در مسیر موردنظر تعیین می‌کند.

A slow request can hold a connection for a long time even when arrivals are infrequent. limit_conn_zone stores per-key active-request state in shared memory; limit_conn sets its maximum at the chosen path.

برای دیدنش درخواست‌های یک‌ثانیه‌ای /slow را هم‌زمان می‌فرستیم و سقف را دو می‌گذاریم. Nginx فقط بعد از خواندن کامل header درخواست آن را می‌شمارد؛ این دستور سدِ همهٔ اتصال‌های خام یا حملهٔ لایهٔ شبکه نیست. در HTTP/2 هر درخواست هم‌زمان جداگانه شمرده می‌شود، نه فقط یک socket فیزیکی.

To observe it, send concurrent one-second requests to /slow and set the limit to two. Nginx counts a request only after its full header is read; this is not a barrier against every raw connection or network-layer attack. Under HTTP/2, each concurrent request is counted separately, not merely one physical socket.

cap active requests on the deliberately slow path
# Add this directive only to location = /slow:
location = /slow {
    limit_conn login_conn 2;
    proxy_pass http://127.0.0.1:19090;
}
nginx -t -p "$RATE_LAB/" -c nginx.conf &&
  nginx -s reload -p "$RATE_LAB/" -c nginx.conf
seq 1 8 | xargs -P8 -I{} curl -sS -o /dev/null \
  -w '%{http_code} %{time_total}\n' \
  "http://127.0.0.1:18090/slow?id={}" |
  sort | uniq -c
tail -n 12 "$RATE_LAB/logs/access.log"
... at most two requests are active together ...
... excess concurrent requests receive 429 ...

اینجا پاسخ 429 را limit_conn_status تنظیم کرده‌ایم؛ اگر آن را برنمی‌داشتی، مقدار پیش‌فرض Nginx، 503 بود. log، زمان و شمار status را با هم بخوان. endpoint فوری /login برای آزمایش limit_conn مناسب نبود چون اتصالش پیش از درخواست بعدی آزاد می‌شد.

Here limit_conn_status sets 429; without it, Nginx defaults to 503. Read the log, timings, and status counts together. The immediate /login endpoint was a poor limit_conn test because its connection could finish before the next request arrived.

دو محدودیت، دو سؤالTwo limits, two questions

limit_req می‌پرسد این key در طول زمان چند درخواست می‌فرستد؟ limit_conn می‌پرسد چند درخواستِ درحال‌پردازش هم‌زمان دارد؟ یکی را با دیگری جایگزین نکن؛ ممکن است هر دو روی مسیر متفاوت لازم باشند.

limit_req asks how many requests this key sends over time. limit_conn asks how many requests it has in progress concurrently. They are not substitutes; different routes may need either or both.

خرابی عمدی: همهٔ کاربران یک بودجه دارندDeliberate fault: every user shares one budget

تیم می‌گوید کاربران مختلف همدیگر را محدود می‌کنند. پیش از تغییر تنظیم، log را بخوان: مقدار $remote_addr برای درخواست‌های جدا چه بوده؟ آیا key همان چیزی است که فکر می‌کردیم؟

The team says different users are throttling each other. Before changing config, inspect the log: what is $remote_addr for separate requests? Is the key what we thought it was?

در Linux آزمایشگاه، دو نشانی source جدا از فضای loopback انتخاب می‌کنیم تا دو key قابل مشاهده داشته باشیم. اول هرکدام را با یکی دو درخواست سبک آزمایش کن؛ اگر curl گزینهٔ --interface را نمی‌پذیرد یا پورت loopback را نمی‌گیرد، این بخش را رد کن و روی سیستم پشتیبانی‌شده اجرا کن.

On Linux, we will use two distinct loopback source addresses to make separate keys observable. Test each with one or two light requests first; if curl does not support --interface or your loopback setup does not accept them, skip this subtest and use a supported system.

confirm the two source addresses reach the test listener

  -w 'source-a status=%{http_code}\n' http://127.0.0.1:18090/login
curl --interface 127.0.0.3 -sS -o /dev/null \

این فقط ثابت می‌کند دو source loopback به listener آزمایش رسیده‌اند. حالا key را عمداً از IP به $server_name تغییر بده؛ همهٔ درخواست‌های این سایت یک مقدار می‌بینند و با هم یک zone را پر می‌کنند.

This only proves two loopback sources can reach the test listener. Now deliberately change the key from the IP to $server_name; all requests to this site share one value and consume the same zone state.

introduce a deliberately shared key and compare clients
# In http {}, add a separate shared-key zone:
limit_req_zone $server_name zone=login_shared:10m rate=2r/s;

حالا هر دو نشانی در log جدا هستند ولی یک key مشترک دارند؛ پس کلاینت دوم ممکن است سهمش را از مصرف کلاینت اول بگیرد. zone را به $binary_remote_addr و نام login_ip برگردان، location را هم به آن وصل کن، reload کن و همان موج‌ها را تکرار کن. اگر Nginx پشت proxy است، این مقدار هنوز ممکن است IP خود proxy باشد؛ آن‌وقت فقط بعد از اعتماد محدود به proxy واقعی، real-IP را اصلاح کن.

The logs show two addresses but the key is shared, so the second client can consume the first client’s allowance. Restore $binary_remote_addr and the login_ip zone, point the location back to it, reload, and repeat the same waves. Behind a proxy, the value may still be the proxy IP; configure real-IP handling only after narrowly trusting the actual proxy.

تنظیم مفهومی پشت یک proxy شناخته‌شده چنین شکلی دارد؛ placeholderها را با IP/CIDR رسمی provider عوض کن و listener را طوری ببند که فقط همان proxy به origin برسد. هرگز همهٔ اینترنت را با set_real_ip_from 0.0.0.0/0 مورداعتماد اعلام نکن.

A conceptual setup behind a known proxy looks like this; replace placeholders with the provider’s official IP/CIDR ranges and restrict origin access to that proxy. Never trust the entire internet with set_real_ip_from 0.0.0.0/0.

برای دیدن مرز اعتماد در همین lab، دو XFF متفاوت از یک اتصال مستقیم بفرست. Nginx باید در log همان IP اتصال را ثبت کند؛ headerها فقط متن ورودی‌اند. این نمونه proxy واقعی نیست و عمداً نشان می‌دهد چرا تنظیم real-IP را نباید روی یک listener عمومی و بی‌قید فعال کرد.

To see the trust boundary in this lab, send two different XFF values over direct connections. Nginx should log the connection IP; the headers are only supplied text. This is not a real proxy—it deliberately shows why real-IP handling must never trust an unrestricted public listener.

compare socket address with untrusted forwarded text
curl -sS -H 'X-Forwarded-For: 198.51.100.10' \
  http://127.0.0.1:18090/login?xff=one -o /dev/null
curl -sS -H 'X-Forwarded-For: 203.0.113.22' \
  http://127.0.0.1:18090/login?xff=two -o /dev/null
tail -n 2 "$RATE_LAB/logs/access.log"
127.0.0.1 xff="198.51.100.10" ...
127.0.0.1 xff="203.0.113.22" ...

این دو مقدار از سمت همین client فرستاده شده‌اند؛ Nginx نباید فقط با دیدنشان key را عوض کند. در مسیر production باید header را proxy مورداعتماد تنظیم کند و client نتواند مستقیم به origin برسد.

These values were sent by the client itself; Nginx should not change the key merely because it sees them. In production, a trusted proxy must set the header, and clients must not be able to bypass that proxy to reach the origin.

trust only the proxy network documented by your provider
# Documentation-only example. Replace with your provider's actual range:
set_real_ip_from 192.0.2.5/32;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

# Then use the normalized client address as the limit key:
limit_req_zone $binary_remote_addr zone=login_ip:10m rate=2r/s;

If a direct client can spoof the forwarded header, blindly trusting it becomes a way around the limiter. Only authorized proxies should reach the origin; then select the header that proxy actually sets and verify it in logs. Header names differ among CDNs and proxy services.

این محدودیت دقیقاً چه چیزی را محافظت می‌کند؟What exactly does this limit protect?

محدودیت جلوی پردازش بخشی از درخواست‌های اضافی را در Nginx می‌گیرد؛ اما درخواست‌های ردشده هنوز به Nginx و شبکه رسیده‌اند. مهاجم می‌تواند IPهای زیاد استفاده کند، در پشت proxy با کاربران واقعی یکی شود یا endpoint دیگری را هدف بگیرد.

The limiter prevents some excess requests from reaching further processing in Nginx, but rejected requests still reached Nginx and the network. An attacker can use many IPs, collide with real users behind a proxy, or target another route.

تمرین‌ها: فشار را اندازه بگیر، بعد محدود کنExercises: measure pressure before limiting it

برای هر موقعیت بگو کدام وضعیت را اندازه می‌گیری، کدام key مناسب است و محدودیت چه چیزی را حل نمی‌کند. عددها را کورکورانه از lab به سایت واقعی نبر.

For each case, say what you would measure, which key fits, and what the limit cannot solve. Do not copy lab numbers blindly into a real site.

تمرین ۱ · معنی 2r/sExercise 1 · What does 2r/s mean?

zone با rate=2r/s تعریف شده. آیا این یعنی دقیقاً هر نیم‌ثانیه یک درخواست قبول می‌شود؟

A zone uses rate=2r/s. Does that mean exactly one request is accepted every half second?

پاسخ را ببینShow solution

نه؛ این متوسط نرخ پردازش برای هر key است. زمان‌بندی درخواست‌ها و burst هم مهم‌اند؛ برای رفتار واقعی status و زمان پاسخ را زیر موج کنترل‌شده بسنج.

No. It is the average processing rate per key. Request timing and burst also matter; measure statuses and response times under a controlled wave.

تمرین ۲ · burst کوچکExercise 2 · Small burst

نرخ 2r/s و burst=4 داری. burst نرخ دائمی را چند درخواست در ثانیه می‌کند؟

You have a rate of 2r/s and burst=4. What permanent requests-per-second rate does burst create?

پاسخ را ببینShow solution

هیچ نرخ دائمی تازه‌ای نمی‌سازد؛ چهار واحد ظرفیت اضافه برای موج کوتاه است. سپس اضافه‌ها با تأخیر پردازش می‌شوند یا پس از پرشدن burst رد می‌شوند.

It creates no new sustained rate; it allows four excess requests in a short wave. Excess is delayed or rejected after the burst allowance is full.

تمرین ۳ · درخواست‌های فوریExercise 3 · Immediate burst

با nodelay یک موج داخل burst بی‌درنگ می‌رسد. آیا هر موج بعدی هم بی‌نهایت عبور می‌کند؟

With nodelay, a burst within the allowance passes immediately. Does every later burst also pass without limit?

پاسخ را ببینShow solution

نه؛ ظرفیت burst محدود است و درخواست‌های فراتر از آن همچنان رد می‌شوند. فقط delay درخواست‌های قابل‌قبول حذف شده، نه rate یا سقف burst.

No; burst capacity is finite, and requests beyond it are still rejected. The delay for accepted excess requests is removed, not the rate or burst cap.

تمرین ۴ · zone حافظهٔ مشترکExercise 4 · Shared zone memory

در zone=login_ip:10m این 10m چه چیزی نیست؟

In zone=login_ip:10m, what is 10m not?

پاسخ را ببینShow solution

اندازهٔ حافظهٔ مشترک برای state keyهاست؛ نرخ، تعداد مجاز در ثانیه یا محل ذخیرهٔ access log نیست. اگر key یکتا زیاد شود، حافظهٔ zone هم باید معقول انتخاب شود.

It is shared memory for key state—not a rate, allowed request count per second, or access-log location. A high number of unique keys makes zone sizing relevant.

تمرین ۵ · limit_conn یا limit_req؟Exercise 5 · limit_conn or limit_req?

یک درخواست دانلود چند دقیقه باز می‌ماند ولی کاربر فقط یک بار آن را شروع می‌کند. کدام محدودیت به تعداد درخواست در ثانیه نگاه می‌کند و کدام اتصال‌های فعال را؟

A download stays open for minutes, but the user starts it once. Which limit considers requests per time, and which tracks active work?

پاسخ را ببینShow solution

limit_req نرخ درخواست را در زمان کنترل می‌کند؛ limit_conn درخواست‌های درحال‌پردازش را می‌شمارد. برای دانلود طولانی ممکن است دومی مرتبط‌تر باشد، اما سقف را با رفتار چند دانلود هم‌زمان طراحی کن.

limit_req controls request rate over time; limit_conn counts requests in progress. The latter may fit long downloads better, but size the cap around normal concurrent use.

تمرین ۶ · HTTP/2 و اتصالExercise 6 · HTTP/2 and connections

یک client روی یک socket، چهار درخواست HTTP/2 هم‌زمان می‌فرستد و limit_conn روی ۲ است. چطور باید اثر را تحلیل کنی؟

One client sends four concurrent HTTP/2 requests over one socket, and limit_conn is 2. How should you reason about the result?

پاسخ را ببینShow solution

Nginx هر درخواست هم‌زمان HTTP/2 را جداگانه برای این limit می‌شمارد؛ تعداد socketهای فیزیکی معیار کافی نیست. status و error log را روی همان نسخه بررسی کن.

Nginx counts each concurrent HTTP/2 request separately for this limit; physical socket count alone is not enough. Check status and error logs on the actual version.

تمرین ۷ · چرا 503؟Exercise 7 · Why 503?

درخواست‌های ردشده 503 می‌گیرند، اما API قرارداد 429 می‌خواهد. کدام directive را بررسی می‌کنی؟

Rejected requests get 503, but the API contract expects 429. Which directive do you inspect?

پاسخ را ببینShow solution

برای rate، limit_req_status 429; و برای اتصال، limit_conn_status 429; را بررسی کن؛ مقدار پیش‌فرض هر دو module، 503 است. هرکدام را در context مناسب بگذار و nginx -t و پاسخ واقعی را دوباره بسنج.

Check limit_req_status 429; for rate limiting and limit_conn_status 429; for connection limiting; both modules default to 503. Put each in a valid context, then repeat nginx -t and the request.

تمرین ۸ · هر کاربر یک بودجهExercise 8 · One allowance per user

همهٔ درخواست‌ها به یک $server_name می‌روند. چرا این key برای سهم جداگانهٔ هر IP مناسب نیست؟

All requests use the same $server_name. Why is this key wrong for per-IP allowances?

پاسخ را ببینShow solution

مقدار برای همهٔ درخواست‌های همان virtual server یکسان است و همه یک state مشترک مصرف می‌کنند. برای quota هر IP از نشانی نرمال‌شدهٔ client key بساز؛ برای سقف کلی سرور، key سرور ممکن است هدف دیگری داشته باشد.

The value is the same for requests to that virtual server, so everyone shares one state. Use a normalized client address for per-IP quota; a server-name key may serve a separate global-cap purpose.

تمرین ۹ · پشت CDNExercise 9 · Behind a CDN

در access log همهٔ clientها IP یکسان دارند و X-Forwarded-For متفاوت است. پیش از اعتماد به header چه مدرکی می‌خواهی؟

Every client has one IP in the access log, while X-Forwarded-For differs. What do you verify before trusting the header?

پاسخ را ببینShow solution

آیا اتصال مستقیم از IP/CIDR واقعی CDN می‌آید؟ مستند provider می‌گوید کدام header را خودش بازنویسی می‌کند؟ آیا firewall جلوی دورزدن CDN تا origin را گرفته؟ فقط پس از پاسخ روشن، set_real_ip_from محدود و real_ip_header را تنظیم کن.

Does the connection come from the CDN’s actual IP/CIDR? Which header does the provider overwrite? Does the firewall prevent bypassing the CDN to the origin? Only after verifying these, configure a narrow set_real_ip_from and the correct real_ip_header.

تمرین ۱۰ · هدر قابل جعلExercise 10 · A spoofable header

تیمی set_real_ip_from 0.0.0.0/0; گذاشته تا هر IP کاربر خوانده شود. خطر چیست؟

A team sets set_real_ip_from 0.0.0.0/0; to read every client IP. What is the risk?

پاسخ را ببینShow solution

هر client می‌تواند header جعلی بفرستد و IP دلخواه انتخاب کند؛ با key بر پایهٔ آن می‌شود محدودیت را دور زد. فقط آدرس‌های proxyای را مورداعتماد بدان که header را درست می‌سازند، و دسترسی مستقیم به origin را هم ببند.

Any client could send a forged header and choose an arbitrary address, potentially evading an IP-keyed limit. Trust only proxy addresses that set the header correctly, and restrict direct access to the origin.

تمرین ۱۱ · آستانه برای loginExercise 11 · Login threshold

می‌خواهی login را روی 1r/s و بدون burst بگذاری. چه رفتار عادی‌ای ممکن است ناخواسته 429 بگیرد؟

You plan to limit login to 1r/s with no burst. What legitimate behavior could be rejected?

پاسخ را ببینShow solution

دوبار کلیک، retry خودکار، چند tab یا چند کاربر پشت NAT ممکن است درخواست‌های نزدیک‌به‌هم بسازند. ترافیک واقعی و نرخ خطا را اندازه بگیر؛ عدد یک کاربر و همهٔ IP مشترک را با هم قاطی نکن.

Double-clicks, automatic retries, multiple tabs, or users behind NAT can create closely spaced requests. Measure real traffic and rejection rates; do not confuse one user with everyone sharing an IP.

تمرین ۱۲ · همه‌چیز 200 استExercise 12 · Everything is 200

با limit_req_dry_run on همهٔ درخواست‌ها 200 مانده‌اند. آیا limiter کار نمی‌کند؟

With limit_req_dry_run on, all requests still return 200. Is the limiter broken?

پاسخ را ببینShow solution

dry-run برای مشاهده است و درخواست را reject نمی‌کند. نتیجهٔ REJECTED_DRY_RUN یا log مربوطه را ببین، و فقط پس از تأیید threshold، enforcement را جداگانه فعال کن. این قابلیت به نسخهٔ Nginx وابسته است.

Dry run observes without rejecting. Look for REJECTED_DRY_RUN or its log entry, then enable enforcement separately after validating the threshold. This feature depends on Nginx version.

تمرین ۱۳ · هر socket؟Exercise 13 · Every socket?

آیا limit_conn همهٔ اتصال‌هایی را که هنوز header نفرستاده‌اند می‌شمارد؟

Does limit_conn count every connection that has not sent its request header yet?

پاسخ را ببینShow solution

نه؛ شمارش زمانی آغاز می‌شود که درخواست در حال پردازش باشد و کل header خوانده شده باشد. برای منابع اتصال خام و حملهٔ شبکه باید کنترل‌های دیگر را هم در نظر گرفت.

No; counting begins when a request is being processed and its full header has been read. Raw connection and network-attack controls require other measures too.

تمرین ۱۴ · zone پر می‌شودExercise 14 · The zone fills

در هر درخواست key تصادفی می‌سازی و shared zone کوچک است. چه خطری دارد؟

You generate a random key per request and use a small shared zone. What is the risk?

پاسخ را ببینShow solution

هر درخواست state تازه می‌خواهد، پس عملاً یک client محدود نمی‌شود و zone می‌تواند پر شود. key را از یک هویت پایدار و معنی‌دار بساز و اندازه را با تعداد واقعی keyها بسنج.

Each request needs new state, so a client is effectively never grouped and the zone can fill. Choose a stable meaningful identity and size the zone for the expected key count.

تمرین ۱۵ · 429 روی عکس‌هاExercise 15 · 429 on images

بعد از اعمال limit در سطح server، فایل‌های static هم 429 می‌شوند و صفحه نیمه‌کاره است. چه چیزی را بازبینی می‌کنی؟

After adding a server-level limit, static files also return 429 and the page is incomplete. What do you review?

پاسخ را ببینShow solution

سطح اعمال directive و ارث‌بری locationها را بررسی کن. limiter را در location مسیر پرهزینه بگذار یا استثناها را صریح طراحی کن؛ scope محدودیت باید با هدف محصول یکی باشد.

Review the directive’s context and location inheritance. Place the limiter on the costly route or design explicit exceptions; its scope should match the product goal.

تمرین ۱۶ · حمله از IPهای زیادExercise 16 · Many attacking IPs

هر IP زیر آستانه می‌ماند، اما هزاران IP login را می‌زنند. آیا per-IP limit کافی است؟

Each IP stays below the threshold, but thousands hit login. Is a per-IP limit enough?

پاسخ را ببینShow solution

نه؛ مجموع فشار توزیع‌شده می‌تواند بزرگ باشد. کنترل‌های account-level و برنامه، CDN/WAF، firewall و ظرفیت را با مشاهده و سیاست امنیتی ترکیب کن. Nginx limiter به‌تنهایی DDoS protection نیست.

No; distributed aggregate load can still be large. Combine account-level app controls, CDN/WAF, firewall, and capacity planning with monitoring and security policy. Nginx’s limiter alone is not DDoS protection.

تمرین ۱۷ · ترجیح صف یا رد فوریExercise 17 · Delay or immediate pass?

endpoint جست‌وجو موج کوتاه می‌گیرد و تأخیر چندثانیه‌ای قابل‌قبول است؛ endpoint اعلان باید فوری جواب دهد ولی ظرفیت burst محدود دارد. با کدام mode شروع می‌کنی؟

Search can tolerate a brief queue; a notification endpoint needs immediate responses but has a finite burst. Which mode would you test first?

پاسخ را ببینShow solution

برای جست‌وجو، حالت تأخیری را می‌سنجم؛ برای اعلان، nodelay با burst کوچک و سنجش backend را آزمایش می‌کنم. هیچ عددی را بدون latency و نرخ رد واقعی نهایی نمی‌کنم.

Test delayed handling for search; test nodelay with a small burst and backend measurements for notifications. Finalize no number without latency and rejection measurements.

تمرین ۱۸ · یک 429 برای همهExercise 18 · One 429 for everyone

پشت CDN، دفتر و خانه در log یک IP دارند؛ پس از rollout کاربران عادی 429 می‌گیرند. چه شواهدی پیش از تغییر نرخ جمع می‌کنی؟

Behind a CDN, the office and home share one logged IP; normal users get 429 after rollout. What evidence do you gather before changing the rate?

پاسخ را ببینShow solution

مقدار socket peer، headerی که CDN می‌فرستد، trusted proxy ranges، scope zone، و logهای REJECTED را بررسی کن. اگر همه زیر یک proxy key هستند، بالا بردن حد شاید فقط علامت را پنهان کند؛ real-IP را با فهرست اعتماد محدود درست کن و همان آزمایش را تکرار کن.

Inspect the socket peer, CDN-provided header, trusted proxy ranges, zone scope, and REJECTED logs. If everyone shares one proxy key, raising the limit may only hide the symptom; configure narrowly trusted real-IP handling and repeat the same test.

ماموریت: صبح روز انتشار، 429های غیرمنتظرهMission: unexpected 429s on release morning

تیم بعد از انتشار می‌گوید فرم ورود برای بعضی کاربران عادی 429 می‌دهد؛ هم‌زمان درخواست‌های login هم باید از موج ربات‌ها در امان باشد. بدون تغییر کورکورانهٔ عدد، باید بفهمی محدودیت روی کدام route است، چه کسی را یک key می‌بیند و آیا burst طبیعی حساب شده.

After a release, the team reports 429s for some normal login users; login requests also need protection from bot bursts. Without blindly changing a number, determine which route is limited, who shares a key, and whether normal bursts were considered.

  1. از access log زمان، status، $remote_addr و $limit_req_status را برای چند درخواست ردشده کنار هم بگذار.For rejected requests, compare time, status, $remote_addr, and $limit_req_status in the access log.
  2. scope directive و key zone را بخوان؛ بررسی کن آیا endpointها یا کاربران نامرتبط یک بودجه شریک‌اند.Inspect the directive scope and zone key; check whether unrelated routes or users share one allowance.
  3. با درخواست کم‌خطر و محدود، baseline بساز؛ بعد فقط key یا burst را—نه هر دو را—تغییر بده.Build a low-volume baseline, then change only the key or burst—not both at once.
  4. همان درخواست‌ها را تکرار کن و status، تأخیر و اثر روی endpoint را ثبت کن؛ برای proxy، trust range را مستند و محدود کن.Repeat the same requests and record status, delay, and endpoint effect; document and narrowly scope trusted proxy ranges.
سرنخ‌ها را یکی‌یکی باز کنReveal hints one at a time

اگر remote addressها یکی است ولی headerها فرق دارند، به مرز proxy فکر کن. اگر status ردشده 503 است، status directive و error log را بخوان. اگر فقط burst رد می‌شود، پیش از زیادکردن نرخ بررسی کن آیا burst یا nodelay با تجربهٔ موردانتظار سازگار است.

If remote addresses match but headers differ, inspect the proxy boundary. If rejections are 503, check status directives and error logs. If only bursts are rejected, review whether burst or nodelay fits expected behavior before increasing the sustained rate.

گزارش نمونه و معیار قبولیSample report and acceptance criteria

گزارش معتبر می‌گوید: route محدودشده کدام بود؛ key چه مقدار داشت؛ آیا هویت از proxy مورداعتماد می‌آمد؛ baseline چه status و latencyای داشت؛ کدام یک تغییر انجام شد؛ و همان موج بعد از تغییر چه تفاوتی نشان داد. نتیجهٔ درست فقط «429 قطع شد» نیست—باید کاربران مجاز همچنان پذیرفته شوند و burst اضافه هم مهار شود.

A sound report names the limited route and key value; says whether identity came from a trusted proxy; records baseline status and latency; identifies the one change made; and compares the same wave afterward. “429 stopped” is not enough—legitimate users must still pass while excess bursts remain controlled.

فقط همین آزمایشگاه را جمع کنClean up only this lab

پیش از توقف، logها را بخوان و اگر خروجی برای گزارش لازم است ذخیره کن. بعد Nginx همین prefix موقت و برنامه‌ای را که همین فایل را اجرا می‌کند متوقف می‌کنیم؛ هیچ processای را با نام عمومی مثل python3 نمی‌کشیم.

Read the logs and save any evidence needed for your report before stopping anything. Then stop only Nginx using this temporary prefix and the app running this exact file; do not kill processes by a generic name such as python3.
