Server blocks and virtual hosts

دو دامنه، یک IP و یک پورت: Nginx از کجا می‌فهمد کدام سایت باید جواب بدهد؟ این فصل با فرستادن درخواست‌های واقعی پیدایش می‌کند؛ نه با حدس‌زدن از روی اسم فایل‌ها یا ترتیب پوشه‌ها.

Two names, one IP, and one port: how does Nginx know which site should answer? We will find out by sending real requests—not by guessing from filenames or directory order.

یک ماشین، دو سایت؛ اولین پاسخ از کجا می‌آید؟One machine, two sites—which one answers first?

Nginx بالا است و صفحهٔ اولش هم باز می‌شود. همکارمان یک سایت دوم اضافه می‌کند؛ هر دو باید روی همان ماشین و پورت ۸۰ باشند. دامنهٔ دوم را هم هنوز در اینترنت تنظیم نکرده‌ایم. بااین‌حال، چطور همین‌جا روی لپ‌تاپ ثابت کنیم هر دو سایت قابل انتخاب‌اند؟

Nginx is running and its first page opens. A teammate adds a second site; both must use the same machine and port 80. We have not configured the second domain in public DNS yet. How can we prove locally that either site can be selected?

پیش از تغییر کانفیگ پیش‌بینی کن: اگر به IP وصل شویم، Nginx از کجا باید بفهمد منظورمان سایت «الف» است یا «ب»؟ اتصال TCP فقط ما را به یک آدرس و پورت می‌رساند؛ نام سایت هم باید راهی به درخواست پیدا کند.

Predict before changing the config: if we connect to an IP address, how can Nginx know whether we mean site A or site B? A TCP connection gets us to an address and port; the site name must also reach the request.

curl -i http://127.0.0.1/

Welcome to nginx!

این پاسخ می‌گوید یک سرویس HTTP روی loopback جواب داده؛ هنوز نمی‌گوید درخواست کدام سایت را انتخاب کرده یا از اینترنت عمومی هم در دسترس است. اگر چند server برای همان listener داشته باشیم و نامی تطبیق نکند، یک server پیش‌فرض باید جواب دهد. حالا باید این انتخاب را آشکار کنیم.

This response tells us an HTTP service answered on loopback; it does not yet tell us which site was selected or whether it is publicly reachable. If several servers share a listener and no name matches, one default server must answer. Let us make that selection visible.

انتخاب در دو گام انجام می‌شودSelection happens in two stages

برای درخواست HTTP ساده، Nginx اول سراغ مقصد شبکه می‌رود: کدام address و port آن را پذیرفته؟ بعد بین serverهایی که همان listener را دارند، مقدار نام میزبان را بررسی می‌کند. در HTTP/1.1 این نام معمولاً در سرآیند Host است.

For a plain HTTP request, Nginx first considers the network destination: which address and port accepted it? Then, among servers using that listener, it checks the requested host name. In HTTP/1.1, that name is normally carried in the Host header.

اول آدرس و پورت، بعد نام درخواست: فلش‌ها ترتیب تصمیم را نشان می‌دهند. اگر نام پیدا نشود، مقصد به default server همان address:port می‌رود.

First address and port, then the request name: arrows show the decision order. If no name matches, the request goes to the default server for that address:port.

پس listen می‌گوید این server block روی کدام address و port درخواست می‌پذیرد؛ server_name نام‌هایی را معرفی می‌کند که می‌توانند آن block را انتخاب کنند. این دو یکی نیستند: چند block می‌توانند یک listen مشترک داشته باشند، اما نام‌های متفاوتی را پاسخ دهند.

So listen says which address and port this server block accepts requests on; server_name lists names that can select that block. They are not the same thing: several blocks can share a listen endpoint and answer different names.

یک نکته برای امروزOne detail for today

در این فصل، منظور از نام درخواست همان نام HTTP/1.1 در Host است. HTTPS مرحلهٔ انتخاب دیگری هم دارد: نام SNI در handshake مربوط به TLS می‌تواند پیش از دریافت درخواست HTTP روی انتخاب پیکربندی اثر بگذارد. آن موضوع را در فصل TLS بررسی می‌کنیم.

In this chapter, “request name” means the HTTP/1.1 name in Host. HTTPS adds another selection stage: the SNI name in the TLS handshake can influence configuration selection before the HTTP request arrives. We will study that in the TLS chapter.

دو سایت را روی یک پورت می‌گذاریمPut two sites on one port

به‌جای دست‌زدن به Nginx نصب‌شده، یک آزمایشگاه موقت می‌سازیم که فقط روی 127.0.0.1:18080 گوش می‌دهد. دو پوشهٔ ریشه و دو فایل متفاوت می‌سازیم تا پاسخ خودش انتخاب‌شدن هر سایت را نشان دهد. این config مستقل است؛ با config سرویس واقعی قاطی‌اش نکن.

Instead of touching the installed Nginx, we will create a temporary lab that listens only on 127.0.0.1:18080. Two root directories and two distinct files will make each selected site visible. This configuration is isolated; do not mix it with the live service config.

این دو فایل HTML عمداً خیلی ساده‌اند. آنچه می‌آزماییم برنامهٔ سایت نیست؛ فقط می‌خواهیم بدانیم درخواست به کدام server block و root رسیده است.

These two HTML files are intentionally simple. We are not testing a website application; we only want to see which server block and root received each request.

create isolated lab directories
LAB_DIR=$(mktemp -d "${TMPDIR:-/tmp}/nginx-vhosts.XXXXXX")
mkdir -p "$LAB_DIR"/{logs,html/alpha,html/beta,html/default}
printf '%s\n' 'ALPHA SITE' > "$LAB_DIR/html/alpha/index.html"
printf '%s\n' 'BETA SITE' > "$LAB_DIR/html/beta/index.html"
printf '%s\n' 'DEFAULT SITE' > "$LAB_DIR/html/default/index.html"
printf 'Lab directory: %s\n' "$LAB_DIR"

چرا مسیر را چاپ می‌کنیم؟ چون همهٔ فایل‌ها، logها و PID آزمایش همین‌جا خواهند بود و cleanup باید دقیقاً همین پوشه را هدف بگیرد. اگر دستور ساخت پوشه خطا داد، ادامه نده؛ اول همان خطا را حل کن.

Why print the path? All lab files, logs, and the process ID will live there, so cleanup must target exactly this directory. If directory creation fails, stop and fix that error before continuing.

حالا سه server block می‌نویسیم. «default» را صریح انتخاب می‌کنیم؛ دو سایت دیگر همان listener را شریک می‌شوند. در گام اول عمداً نام BETA را اشتباه نمی‌نویسیم؛ خرابی را بعدتر، وقتی هر دو مسیر درست کار کردند، جداگانه می‌سازیم.

Now we define three server blocks. We choose the default explicitly; the two named sites share the same listener. We will not mistype BETA yet—we will introduce that failure separately, after both paths work.

write the lab configuration
cat > "$LAB_DIR/nginx.conf" <<'NGINX'
worker_processes 1;
pid logs/nginx.pid;
error_log logs/error.log notice;

events { worker_connections 64; }

http {
    default_type text/plain;

    server {
        listen 127.0.0.1:18080 default_server;
        server_name _;
        root html/default;
        index index.html;
        access_log logs/default.access.log;
    }

    server {
        listen 127.0.0.1:18080;
        server_name alpha.test;
        root html/alpha;
        index index.html;
        access_log logs/alpha.access.log;
    }

    server {
        listen 127.0.0.1:18080;
        server_name beta.test;
        root html/beta;
        index index.html;
        access_log logs/beta.access.log;
    }
}
NGINX
nginx -t -p "$LAB_DIR/" -c nginx.conf

مسیرهای root و log نسبی‌اند؛ گزینهٔ -p پیشوند آزمایشگاه را تعیین می‌کند. در نصب توزیعی معمولاً فایل‌ها جای دیگری‌اند، برای همین در این آزمایش -p و -c را صریح می‌زنیم. nginx -t فقط parse و بازشدن فایل‌های لازم را می‌سنجد؛ هنوز ثابت نکرده‌ایم port آزاد است یا درخواست درست پاسخ می‌گیرد.

The root and log paths are relative; -p sets the lab prefix. Packaged installations commonly use different paths, so this experiment passes -p and -c explicitly. nginx -t checks parsing and required files; it has not yet proved that the port is free or that requests receive the intended response.

اگر آزمون موفق شد، Nginx آزمایشی را با همین prefix و config بالا می‌آوریم. پیش از آن بررسی می‌کنیم listener آزمایشی اشغال نباشد؛ چون فقط loopback است، به شبکهٔ بیرون bind نمی‌شود.

If the test passes, start the lab Nginx with the same prefix and config. First check that the lab listener is not already occupied. Because it binds only to loopback, it is not exposed on an external interface.

check, then start the isolated server
if command -v ss >/dev/null && ss -ltn | grep -q ':18080 '; then
  echo 'Port 18080 is occupied; choose another lab port before continuing.'
else
  nginx -p "$LAB_DIR/" -c nginx.conf
fi

در هر دو درخواست، مقصد شبکه یکی است؛ فرق تعیین‌کننده Host است و بدنهٔ پاسخ مدرک انتخاب سایت. اگر هر دو خروجی یکسان‌اند، همین حالا سراغ حدس نرو: مطمئن شو config آزمایش را با -p/-c اجرا کرده‌ای، پورت را process دیگری نگرفته و نامی که فرستادی دقیقاً با server_name جور است.

Both requests use the same network destination; the differing Host value selects the site, and the response body is our evidence. If both bodies are identical, do not guess: confirm the lab config was started with -p/-c, another process does not own the port, and the sent name exactly matches server_name.

Host کجای درخواست است؟Where does Host appear?

در URL مرورگر، نام دامنه برای پیدا کردن IP استفاده می‌شود؛ اما بعد از اتصال، نام میزبان در درخواست HTTP هم فرستاده می‌شود. برای آزمایش، لازم نیست DNS واقعی یا حتی فایل hosts را تغییر بدهیم: می‌توانیم IP را مقصد اتصال نگه داریم و header را خودمان تعیین کنیم.

In a browser URL, the domain name is used to find an IP address; after connecting, the host name is also sent in the HTTP request. For a test, we need neither public DNS nor a hosts-file edit: we can keep the IP as the connection target and set the header ourselves.

URL یا `--resolve` مقصد اتصال را تعیین می‌کند؛ Host نامی را می‌دهد که Nginx برای انتخاب server می‌سنجد. این دو مسیر به هم مرتبط‌اند، اما یک داده نیستند.

The URL or `--resolve` sets the connection destination; Host supplies the name Nginx checks to select a server. The two are related, but they are not the same piece of data.

دو راه معادل برای تست داریم. راه اول header را صریح می‌فرستد؛ راه دوم به curl می‌گوید نام را برای اتصال به IP محلی resolve کند. در راه دوم URL هم نام درست را دارد و curl به‌طور طبیعی Host متناظر را می‌فرستد.

There are two equivalent test methods. The first sends the header explicitly; the second tells curl to resolve the name to a local IP. With the latter, the URL itself contains the intended name, so curl sends the matching Host header naturally.

two local ways to select a site
curl -i -H 'Host: alpha.test' http://127.0.0.1:18080/
curl -i --resolve beta.test:18080:127.0.0.1 http://beta.test:18080/

هر دو باید سایت متناظر را نشان دهند. اگر این دو روش با هم فرق دارند، request line و header واقعی را با curl -v ببین و مطمئن شو هر دو به همان IP و port می‌روند. این تست از DNS عمومی عبور نمی‌کند و دسترسی از اینترنت را هم نمی‌سنجد.

Each should return its matching site. If the methods disagree, inspect the actual request line and headers with curl -v, and confirm both target the same IP and port. This test bypasses public DNS and does not measure Internet reachability.

آزمایش با hosts محلیTesting with a local hosts file

وقتی می‌خواهی URL را مثل مرورگر واقعی بنویسی، نام‌ها را موقتاً به loopback نگاشت کن. در Linux/macOS فایل /etc/hosts است؛ در Windows فایل C:\Windows\System32\drivers\etc\hosts است. فایل را با دسترسی لازم باز کن و این خط را اضافه کن؛ اگر خطی مشابه از قبل هست، تکراری نساز.

If you want to type the URL as a browser would, map the names to loopback temporarily. On Linux/macOS the file is /etc/hosts; on Windows it is C:\Windows\System32\drivers\etc\hosts. Open it with the required permissions and add the line below; do not create a duplicate if an equivalent line already exists.

temporary hosts-file entry
127.0.0.1 alpha.test beta.test

بعد curl -i http://alpha.test:18080/ و curl -i http://beta.test:18080/ را بزن. پس از آزمایش فقط همان نگاشت موقتی را از hosts پاک کن؛ فایل را با نسخهٔ قدیمی جایگزین نکن، چون ممکن است تغییرهای دیگری در همین فاصله ثبت شده باشند. hosts فقط ترجمهٔ نام به IP را محلی انجام می‌دهد؛ درخواست هنوز باید Host درست را بفرستد.

Then run curl -i http://alpha.test:18080/ and curl -i http://beta.test:18080/. Afterwards, remove only the temporary mapping from the hosts file; do not replace the whole file with an old copy, because other edits may have happened meanwhile. hosts performs local name-to-IP mapping; the request must still send the right Host value.

default server یعنی «برای این listener»، نه «یک دامنهٔ خاص»The default belongs to the listener, not to a domain

در کانفیگ آزمایش، یک درخواست با نام ناشناس بفرست. انتظار داری چه شود؟ چون نامی از سه server_name پیدا نمی‌شود، Nginx باید default همین listener را انتخاب کند.

Send a request with an unknown name to the lab config. What do you expect? Since none of the three server_name values match, Nginx should choose this listener’s default.

unknown host name
curl -i -H 'Host: not-configured.test' http://127.0.0.1:18080/
HTTP/1.1 200 OK

DEFAULT SITE

بدنهٔ DEFAULT SITE نشان می‌دهد درخواست به block دارای default_server رسیده. default بودن صفت پورت/آدرسِ listener است، نه چیزی که با server_name _; ساخته شود. نام _ صرفاً یک نام قراردادیِ نامحتمل است؛ جادویی نیست و به‌تنهایی همهٔ دامنه‌های ناشناس را نمی‌گیرد.

The DEFAULT SITE body shows that the request reached the block marked default_server. Default status belongs to a listener address/port, not to a name created by server_name _;. The underscore is merely an unlikely conventional name; it is not magic and does not itself catch every unknown host.

اگر برای یک address:port هیچ‌کدام default_server نداشته باشند، اولین server block تعریف‌شده برای همان listener پیش‌فرض می‌شود. بهتر است در configهایی که چند سایت دارند default را صریح کنی تا خواننده مجبور نباشد ترتیب includeها را حدس بزند. این ترتیب مربوط به انتخاب default است؛ ترتیب فایل‌ها را با الگوریتم location قاطی نکن.

If no block declares default_server for an address:port, the first server block defined for that listener becomes the default. In multi-site configs, declaring it explicitly saves readers from guessing the include order. This ordering concerns default selection; do not confuse it with the location matching algorithm.

اگر درخواست بدون Host برسد، رفتار پیش‌فرض نام خالی هم وارد ماجرا می‌شود؛ لازم نیست هر نصب را از اول با یک قاعدهٔ دست‌ساز برای این حالت پیکربندی کنیم. برای ردکردن نام ناشناس می‌شود default ویژه‌ای ساخت، اما کد غیرمعمول 444 پاسخ HTTP استاندارد نیست و اتصال را می‌بندد؛ این انتخاب را فقط با شناخت رفتار کلاینت انجام بده.

If a request arrives without Host, the default empty server name is also relevant; there is no need to invent a custom rule for every installation. A special default can reject unknown names, but Nginx’s non-standard 444 is not an HTTP response—it closes the connection. Use it only when you understand the client-visible behavior.

نام BETA را خراب می‌کنیم؛ هنوز تعمیر نکنBreak BETA’s name—do not fix it yet

تا اینجا هر نام به سایت خودش رسید. حالا می‌خواهیم ببینیم اشتباه کوچکی در server_name چه شکلی دیده می‌شود. در config آزمایش فقط beta.test را به betta.test تغییر بده. پیش از reload، syntax را بررسی کن؛ typo از نظر دستور زبان درست است و احتمالاً nginx -t آن را رد نمی‌کند.

So far, each name reached its own site. Now we will see what a small server_name mistake looks like. In the lab config only, change beta.test to betta.test. Test syntax before reloading; the typo is valid syntax, so nginx -t will probably accept it.

در این مرحله دنبال «خطای config» نگرد؛ می‌خواهیم یک config معتبر اما از نظر قصد اشتباه را آزمایش کنیم. بعد از آزمون موفق، همان config آزمایش را reload کن و همان درخواست قبلی را بفرست.

Do not look for a syntax error here; we are testing a valid configuration that does not match our intent. After the test passes, reload the lab config and send the same request as before.

the symptom after the typo
nginx -t -p "$LAB_DIR/" -c nginx.conf
nginx -p "$LAB_DIR/" -c nginx.conf -s reload

DEFAULT SITE

درخواست موفق شده، پس ممکن است نتیجه را اشتباه «BETA سالم است» بخوانیم. اما body می‌گوید default جواب داده؛ این مدرک از status code مهم‌تر است. حالا دو فرض را جدا کن: آیا config بارشده همان فایلی است که ویرایش کردی؟ و آیا نام درخواست با نام تعریف‌شده در server block برابر است؟

The request succeeded, so it is easy to misread the result as “BETA works.” But the body says the default answered; that is more informative than the status code. Separate two hypotheses: did Nginx load the file you edited, and does the request name equal the name defined in the server block?

inspect the effective configuration
nginx -T -p "$LAB_DIR/" -c nginx.conf 2>&1 | grep -nE 'server_name|listen'
listen 127.0.0.1:18080 default_server;
server_name _;
listen 127.0.0.1:18080;
server_name alpha.test;
listen 127.0.0.1:18080;
server_name betta.test;

این خروجی ثابت می‌کند config مؤثر typo را دارد؛ هنوز فقط نام را می‌دانیم، نه اینکه request واقعاً به کدام block رفته. body پاسخ و نام موجود را کنار هم بگذار: beta.test برابر betta.test نیست، بنابراین default جواب داده. حالا typo را اصلاح کن، دوباره -t بزن، reload کن و همان curl را تکرار کن. تأیید نهایی باید BETA SITE باشد.

This output proves the effective config contains the typo; it does not by itself show which block handled the request. Compare the response body with the configured name: beta.test is not betta.test, so the default answered. Fix the typo, run -t again, reload, and repeat the same curl. The final evidence should be BETA SITE.

این آزمایش روی سرویس زنده نیستThis experiment is not on a live service

فقط فایل داخل $LAB_DIR را ویرایش کن. برای Nginx واقعی، پیش از reload از پیکربندی نسخهٔ پشتیبان داشته باش، با باینری و گزینه‌های همان سرویس -t بگیر، و نشانی را طوری آزمایش کن که بازگشت امن داشته باشی.

Edit only the file under $LAB_DIR. For a live Nginx, keep a configuration backup before reloading, test with that service’s binary and options, and use a verification path that gives you a safe way back.

دو جور تکرار داریم؛ یکی اخطار است، یکی خطای شروعTwo kinds of duplication: one warns, one prevents startup

یک همکار می‌گوید: «اگر دو block روی یک پورت‌اند، پس هر تکراری یعنی Nginx نمی‌تواند بالا بیاید.» این دو گزاره را یکی نکن. تکرار default_server برای یک listener و تکرار یک server_name وضعیت یکسانی ندارند.

A teammate says, “If two blocks use the same port, any duplication means Nginx cannot start.” Do not conflate these cases. Repeating default_server for one listener and repeating a server_name do not have the same outcome.

Read the severity and message from your own version; wording and process IDs can vary. Most importantly, do not equate a successful nginx -t with correct selection for every name. Do not ignore warnings, and verify each name with a real request.

IPv4 و IPv6؛ دو ورودی‌اند، نه دو اسمIPv4 and IPv6 are two endpoints, not two names

تا اینجا فقط روی 127.0.0.1 گوش دادیم؛ یعنی loopback در IPv4. اگر کلاینت با IPv6 به ::1 وصل شود، ممکن است اصلاً به همان listener نرسد. این مسئله قبل از انتخاب server_name رخ می‌دهد.

So far we have listened only on 127.0.0.1, the IPv4 loopback. A client connecting to ::1 over IPv6 may not reach that listener at all. This happens before server_name selection.

برای هر address:port، انتخاب default جداست. هر server block باید روی endpoint موردنظر listen داشته باشد؛ یک تعریف IPv4 به‌تنهایی حضور روی IPv6 را تضمین نمی‌کند.

Each address:port pair has its own default. A server block must listen on the intended endpoint; an IPv4 listener alone does not guarantee IPv6 reachability.

نمونهٔ صریح برای یک سایت می‌تواند دو خط داشته باشد: listen 80; برای IPv4 و listen [::]:80; برای IPv6. نشانی IPv6 در config داخل براکت نوشته می‌شود. پیکربندی دقیق به این بستگی دارد که Nginx روی کدام interfaceها bind می‌کند و سیستم‌عامل socket دوگانه را چطور تنظیم کرده است.

An explicit example for one site may contain two lines: listen 80; for IPv4 and listen [::]:80; for IPv6. IPv6 addresses are bracketed in the config. The exact setup depends on which interfaces Nginx binds and how the operating system configures dual-stack sockets.

در Nginx، پارامتر ipv6only=on|off روی رفتار IPv4-mapped اتصال‌های socket wildcard IPv6 اثر دارد و پیش‌فرض رسمی‌اش on است؛ این مقدار فقط هنگام start قابل تعیین است. بااین‌حال از روی یک خط config فرض نکن IPv6 در محیطت آماده است: وجود آدرس و listener را جدا بررسی کن. وقتی هر دو endpoint را تعریف می‌کنی، default را برای هر زوج address:port درست و بدون تکرار تعیین کن.

Nginx’s ipv6only=on|off parameter controls whether an IPv6 wildcard socket also accepts IPv4-mapped connections; its documented default is on, and it can only be set at startup. Still, do not infer IPv6 availability from one config line: verify that the address and listener exist. If you define both endpoints, assign a valid, non-duplicate default for each address:port pair.

inspect listeners before blaming server_name
ss -ltnp | grep -E ':(80|18080)\b'
curl -4 -i --resolve alpha.test:18080:127.0.0.1 http://alpha.test:18080/
curl -6 -i --resolve "alpha.test:18080:[::1]" http://alpha.test:18080/

اگر curl -6 شکست خورد، این به‌تنهایی typo در server_name را ثابت نمی‌کند؛ شاید listener یا IPv6 سیستم فعال نیست. اول خروجی ss و آدرس‌های میزبان را بخوان؛ بعد از رسیدن درخواست به listener سراغ نام برو. هر دستور را فقط وقتی اجرا کن که سرویس آزمایشی واقعاً روی آن port فعال است.

If curl -6 fails, that alone does not prove a server_name typo; the listener or host IPv6 may be unavailable. Read ss and the host addresses first, then inspect names only after the request reaches a listener. Run these requests only while the lab service is actually bound to that port.

هر سایت ریشه و گزارش خودش را داشته باشدGive each site its own root and access log

وقتی انتخاب block را دیدیم، یک سؤال عملی می‌ماند: از کجا بفهمیم پاسخ واقعاً از فایل‌های سایت درست آمده؟ برای هر server، root و access_log مستقل می‌گذاریم. این جداسازی هم پیدا کردن صفحهٔ اشتباه را آسان می‌کند، هم نشان می‌دهد هر درخواست کجا ثبت شده است.

Now that we have seen block selection, one practical question remains: how do we know the response came from the intended site’s files? Give each server its own root and access_log. This makes wrong-page diagnosis easier and shows where each request was recorded.

This command reads only the last few lines from the lab logs; it does not assess full logging or rotation settings. If your shell lacks tail, open the relevant file with that environment’s text viewer.

اگر همین ایده را روی نصب واقعی می‌بری…If you apply this to a real installation…

در آزمایشگاه، Nginx جداست. در یک VPS واقعی ممکن است configهای دیگری روی همان پورت باشند و تغییر تو default آن‌ها را عوض کند. پس پیش از افزودن سایت، اول بفهم کدام فایل‌ها واقعاً include شده‌اند و کدام process پورت را گرفته است.

The lab Nginx is isolated. On a real VPS, other configs may already share the port, and your change could alter their default. Before adding a site, find which files are actually included and which process owns the listener.

inspect before editing a packaged service
sudo nginx -T 2>&1 | grep -nE 'configuration file|listen|server_name'
sudo ss -ltnp | grep -E ':(80|443)\b'

از -T برای دیدن فایل‌های مؤثر و جای واقعی server blockها استفاده کن؛ خروجی ممکن است اطلاعات داخلی داشته باشد، پس آن را بی‌بررسی عمومی نکن. از ss می‌فهمی listener در اختیار چه processای است. هیچ‌کدام به‌تنهایی نمی‌گوید یک نام عمومی از اینترنت به این ماشین می‌رسد.

Use -T to inspect effective files and where server blocks actually live; its output may contain internal details, so do not publish it without review. ss identifies the process owning a listener. Neither alone proves that a public domain reaches this host from the Internet.

در نصب‌های توزیعی، نام‌هایی مثل sites-available و sites-enabled ممکن است وجود داشته باشند؛ در بستهٔ رسمی یا container شاید ساختار متفاوت باشد. معیار، فایل‌هایی است که باینری فعال واقعاً بار می‌کند، نه یک آموزش عمومی. قبل از reload، از همان config و با همان binary، nginx -t بگیر؛ اگر موفق بود، reload کن و همان درخواست کنترل‌شده را دوباره بفرست.

Packaged installations may use directories such as sites-available and sites-enabled; an official package or container may use a different layout. Trust the files the active binary actually loads, not a generic tutorial. Before reloading, run nginx -t against that config and binary; if it succeeds, reload and repeat the same controlled request.

ترتیب فایل، ابزار تشخیص نیستFile order is not a debugging method

اگر سایت اشتباه جواب می‌دهد، همهٔ فایل‌ها را جابه‌جا یا حذف نکن. body پاسخ، Host ارسال‌شده، listener، serverهای مؤثر در -T و نام‌های دقیق را کنار هم بگذار؛ بعد فقط اختلاف اثبات‌شده را اصلاح کن.

If the wrong site answers, do not reorder or delete every file. Compare the response body, sent Host, listener, effective servers in -T, and exact names; then fix only the demonstrated mismatch.

تمرین‌ها: انتخاب درست را از روی مدرک بفهمExercises: infer the selection from evidence

در تمرین‌های اول، نتیجه را پیش‌بینی می‌کنی. جلوتر، باید تشخیص بدهی کدام لایه هنوز آزمایش نشده و چه مدرکی قبل از تغییر بعدی لازم است. پاسخ‌ها را بعد از اینکه خودت فکر کردی باز کن.

The first exercises ask you to predict. Later, you will identify which layer has not been tested and what evidence is needed before the next change. Try each one before opening its solution.

۱. پیش‌بینی انتخاب1. Predict the selection

دو block روی 127.0.0.1:8080 گوش می‌دهند. اولی server_name a.test و دومی server_name b.test دارد. درخواست با Host: b.test می‌رسد. کدام block را انتظار داری؟

Two blocks listen on 127.0.0.1:8080. The first declares server_name a.test; the second, b.test. A request arrives with Host: b.test. Which block do you expect?

پاسخ را ببینShow solution

دومی، چون مقصد address:port با هر دو جور است و بعد نام Host با b.test تطبیق می‌کند. این پاسخ پیش‌بینی مدل است؛ با body متفاوت یا log جدا باید ثابتش کنی.

The second block: both match the address:port, then the Host value matches b.test. This is a model-based prediction; prove it with distinct response bodies or separate logs.

۲. URL با IP، Host با نام2. IP in the URL, name in Host

دستور curl http://127.0.0.1:8080/ -H 'Host: shop.test' به کدام IP وصل می‌شود و Nginx چه نامی را برای انتخاب می‌بیند؟

In curl http://127.0.0.1:8080/ -H 'Host: shop.test', which IP does curl connect to, and which name does Nginx inspect for selection?

پاسخ را ببینShow solution

curl به 127.0.0.1:8080 وصل می‌شود؛ Nginx برای انتخاب HTTP virtual host مقدار shop.test در Host را بررسی می‌کند. این تست DNS را دور می‌زند؛ به‌تنهایی ثابت نمی‌کند DNS عمومی درست است.

curl connects to 127.0.0.1:8080; Nginx checks shop.test in Host for HTTP virtual-host selection. This bypasses DNS and does not prove public DNS is correct.

۳. نام ناشناس3. An unknown name

هیچ blockای odd.test را ندارد، ولی پاسخ 200 و body سایت اول را می‌بینی. آیا Nginx نام ناشناس را تصادفی انتخاب کرده؟

No block declares odd.test, yet you receive status 200 and the first site's body. Did Nginx select an arbitrary name?

پاسخ را ببینShow solution

نه؛ درخواست به default همان address:port رسیده. اگر default صریح تعیین نشده باشد، اولین block برای همان listener پیش‌فرض می‌شود. body را با listenهای مؤثر تطبیق بده تا این فرض ثابت شود.

No. The request reached the default for that address:port. If none is explicitly declared, the first block for that listener becomes default. Compare the body with the effective listen configuration to verify it.

۴. underscore جادویی نیست4. The underscore is not magic

کسی می‌گوید server_name _; تمام نام‌های ناشناخته را می‌گیرد، حتی اگر block دیگری default_server باشد. کدام بخش حرفش اشتباه است؟

Someone claims server_name _; catches all unknown names even if another block has default_server. What is wrong with that claim?

پاسخ را ببینShow solution

_ نام خاصی نیست؛ یک نام قراردادی است. نقش default را پارامتر default_server در listen تعیین می‌کند. برای فهم نتیجه، فقط به نام نگاه نکن؛ listener را هم بررسی کن.

_ is not a special name; it is a convention. The default_server parameter on listen determines the default. Inspect the listener as well as the name.

۵. دو default روی یک listener5. Two defaults on one listener

دو server block هر دو روی 127.0.0.1:8080 default_server هستند. انتظار داری nginx -t چه کند؟

Two server blocks both use 127.0.0.1:8080 default_server. What do you expect nginx -t to do?

پاسخ را ببینShow solution

باید config را به‌خاطر default تکراری برای همان زوج address:port رد کند. block دوم را حذف یا نقش‌ها را روشن کن؛ پیش از reload، آزمون را دوباره بگیر. برای یک address یا port دیگر، default مستقل ممکن است مجاز باشد.

It should reject the config because the same address:port has duplicate defaults. Remove the duplicate or clarify the roles, then retest before reloading. A different address or port may have its own default.

۶. نام تکراری، پیام متفاوت6. A duplicate name, a different message

در دو block روی listener مشترک، server_name app.test تکرار شده. nginx -t می‌گوید syntax موفق و یک warning از conflicting server name می‌دهد. آیا reload را بی‌بررسی ادامه می‌دهی؟

Two blocks sharing a listener repeat server_name app.test. nginx -t reports valid syntax and a conflicting-server-name warning. Do you reload without further inspection?

پاسخ را ببینShow solution

نه. warning می‌گوید نام تکراری ممکن است نادیده گرفته شود؛ syntax موفق، نیت پیکربندی را تأیید نمی‌کند. با -T نام‌ها را در blockهای مؤثر پیدا کن و تصمیم بگیر کدام سایت باید آن نام را داشته باشد، بعد warning را برطرف و درخواست واقعی را آزمایش کن.

No. The warning says the duplicate name may be ignored; passing syntax does not validate your intent. Find the effective blocks with -T, decide which site should own the name, remove the conflict, and test a real request.

۷. HTTP یا HTTPS؟7. HTTP or HTTPS?

یک سرآیند Host درست به پورت ۸۰ فرستاده‌ای و سایت صحیح پاسخ می‌دهد. آیا همین مدرک انتخاب certificate درست در HTTPS است؟

You sent the correct Host to port 80 and got the right site. Does that prove HTTPS will select the right certificate?

پاسخ را ببینShow solution

نه. در HTTPS، TLS handshake پیش از درخواست HTTP رخ می‌دهد و SNI ممکن است پیکربندی/certificate را زودتر انتخاب کند. HTTP Host به‌تنهایی رفتار TLS را نمی‌آزماید؛ نام و گواهی را جدا در تست HTTPS بررسی کن.

No. The TLS handshake happens before the HTTP request, and SNI can select configuration/certificate earlier. HTTP Host alone does not test TLS behavior; verify the name and certificate in a separate HTTPS test.

۸. سرور فقط روی IPv48. The server listens only on IPv4

در config فقط listen 127.0.0.1:8080; داری. curl -6 http://[::1]:8080/ اتصال را رد می‌کند. آیا این به‌تنهایی ثابت می‌کند نام دامنه غلط است؟

The config has only listen 127.0.0.1:8080;. curl -6 http://[::1]:8080/ is refused. Does this alone prove the domain name is wrong?

پاسخ را ببینShow solution

نه؛ هنوز به HTTP name selection نرسیده‌ایم. باید ببینیم Nginx روی IPv6 گوش می‌دهد یا نه و خود سیستم IPv6 loopback دارد یا نه. خطای اتصال پیش از بررسی server_name رخ می‌دهد.

No; the request has not reached HTTP name selection. Check whether Nginx listens on IPv6 and whether the host has IPv6 loopback enabled. A connection failure occurs before server_name is checked.

۹. default برای هر زوج9. A default for each pair

یک سایت روی 127.0.0.1:80 و [::]:80 گوش می‌دهد. آیا می‌توانی بدون دیدن بقیهٔ config بگویی یک default_server کجا کافی است؟

A site listens on 127.0.0.1:80 and [::]:80. Can you tell where one default_server is sufficient without seeing the rest of the config?

پاسخ را ببینShow solution

نه. default برای هر address:port pair است؛ باید blockهای دیگر و socketهایی را که واقعاً bind شده‌اند ببینی. ممکن است برای endpointهای IPv4 و IPv6 default جدا لازم باشد؛ رفتار dual-stack میزبان را هم بررسی کن.

No. Default status is scoped to each address:port pair; inspect the other blocks and actual bound sockets. IPv4 and IPv6 endpoints may need separate defaults, and the host’s dual-stack behavior matters.

۱۰. دو ریشهٔ جدا10. Separate roots

alpha پاسخ درست می‌دهد ولی beta محتوای قدیمی alpha را نشان می‌دهد. هر دو server_name درست‌اند. سه موردی که اول بررسی می‌کنی چیست؟

alpha responds correctly, but beta shows alpha’s old content. Both server_name values are correct. What three things do you inspect first?

پاسخ را ببینShow solution

اول body و Host واقعی، بعد root هر block در -T، و در نهایت فایل موجود در مسیر root فعال beta. درخواست به block درست ممکن است برسد ولی root اشتباه باشد؛ این دو تشخیص جدا هستند.

First inspect the response body and actual Host, then each block’s effective root in -T, and finally the file under beta’s active root. The request may reach the correct block while using the wrong root; these are separate diagnoses.

۱۱. همهٔ نام‌ها default می‌شوند11. Every name lands on default

curl برای alpha.test و beta.test هر دو DEFAULT SITE می‌گیرد. یک علت محتمل در config و یک علت در درخواست نام ببر.

curl receives DEFAULT SITE for both alpha.test and beta.test. Name one plausible config cause and one request-side cause.

پاسخ را ببینShow solution

در config: typo یا server block بارنشده/بدون listener متناظر. در درخواست: Host اصلاً ارسال نشده یا نام/port به listener دیگری می‌رود. با -T config مؤثر را ببین و با curl -v header و مقصد را؛ سپس یک متغیر را تغییر بده و تکرار کن.

On the config side: a typo or an unloaded block/no matching listener. On the request side: Host was not sent, or the name/port reaches another listener. Inspect effective config with -T and destination/header with curl -v; then change one variable and retest.

۱۲. response code کافی نیست12. A status code is not enough

برای shop.test پاسخ 200 OK داری، اما کاربر می‌گوید صفحهٔ فروشگاه نیست. دقیقاً چه چیزی را در پاسخ بررسی می‌کنی؟

You get 200 OK for shop.test, but the user says it is not the shop page. What exactly do you inspect in the response?

پاسخ را ببینShow solution

بدنهٔ پاسخ را می‌خوانم و دنبال نشانگر یکتای سایت می‌گردم؛ بعد access log و root را با همان زمان/درخواست تطبیق می‌دهم. status موفق فقط پاسخ HTTP را ثابت می‌کند، نه انتخاب سایت یا محتوای درست.

Read the response body for a site-specific marker, then correlate the access log and root with that request. A successful status proves an HTTP response, not correct site selection or content.

۱۳. Host را صریح بفرست13. Send Host explicitly

DNS واقعی هنوز ساخته نشده. یک دستور curl پیشنهاد بده که بدون تغییر فایل hosts نام panel.test را به loopback بفرستد و انتخاب آن را بیازماید.

Public DNS is not configured yet. Give a curl command that tests panel.test on loopback without editing the hosts file.

پاسخ را ببینShow solution

مثلاً curl -i --resolve panel.test:18080:127.0.0.1 http://panel.test:18080/. این DNS را برای همان درخواست دور می‌زند ولی Host از نام URL می‌آید. موفقیتش public DNS یا firewall را ثابت نمی‌کند.

For example, curl -i --resolve panel.test:18080:127.0.0.1 http://panel.test:18080/. It bypasses DNS for this request while deriving Host from the URL name. It does not prove public DNS or firewall behavior.

۱۴. نام خطاست یا listener؟14. Wrong name or wrong listener?

در درخواست به پورت 18081 سایت default دیگری می‌بینی؛ در -T نام موردنظر وجود دارد اما فقط روی 18080 listen شده. قدم بعدی چیست؟

A request to port 18081 reaches a different default. The desired name appears in -T, but it listens only on 18080. What next?

پاسخ را ببینShow solution

این درخواست به listener نام موردنظر نرسیده؛ وجود server_name در config برای پورت دیگر کافی نیست. اول پورت واقعی مقصد و socketهای ss را تأیید کن، بعد تصمیم بگیر block باید روی 18081 هم listen کند یا درخواست اشتباه فرستاده شده.

The request did not reach the intended listener; having the server name on another port is not enough. Confirm the destination port and sockets with ss, then decide whether the block should also listen on 18081 or the request used the wrong port.

۱۵. نام تکراری، فایل تکراری15. A duplicate name in separate files

دو فایل در -T، هر دو server_name api.test و listener یکسان دارند. پاسخ فعلی تصادفاً درست است. آیا کافی است؟

Two files shown by -T both declare server_name api.test on the same listener. The current response happens to be correct. Is that enough?

پاسخ را ببینShow solution

نه. احتمالاً warning می‌بینی و یک نام conflictشده نادیده گرفته می‌شود؛ وابستگی به ترتیب یا config پنهان قابل اتکا نیست. ownership نام را در فایل‌های بارشده روشن کن، conflict را حذف کن و بعد درخواست api.test را تکرار کن.

No. A warning may indicate that one conflicting name is ignored; relying on include order or hidden config is fragile. Assign the name to one intended block, remove the conflict, and retest api.test.

۱۶. IPv6 به سرویس نمی‌رسد16. IPv6 cannot reach the service

IPv4 با curl -4 جواب می‌دهد؛ IPv6 connection refused است. Nginx log هیچ درخواستی نشان نمی‌دهد. کدام مرز را اول بررسی می‌کنی؟

IPv4 works with curl -4; IPv6 returns connection refused. Nginx logs show no request. Which boundary do you inspect first?

پاسخ را ببینShow solution

listener و مسیر IPv6 را؛ چون درخواست هنوز به Nginx نرسیده، بررسی log یا server_name بعدی است. آدرس، bind و خروجی ss -ltn را ببین. نبودن log به‌تنهایی علت را تعیین نمی‌کند، اما همراه connection refused سرنخ مرز شبکه است.

Inspect the IPv6 listener and path first. The request has not reached Nginx, so logs and server_name come later. Check addresses, bind settings, and ss -ltn. Missing logs alone are inconclusive, but combined with connection refused they point to the network boundary.

۱۷. پورت ۸۰ عمومی نیست17. Port 80 is not public

از خود VPS با curl -H 'Host: app.example' http://127.0.0.1/ سایت درست است؛ کاربر بیرونی timeout می‌گیرد. آیا virtual host شکست خورده؟ سه مدرک بعدی را انتخاب کن.

From the VPS, curl -H 'Host: app.example' http://127.0.0.1/ reaches the right site; an external user times out. Did virtual hosting fail? Choose the next three pieces of evidence.

پاسخ را ببینShow solution

نه لزوماً؛ تست محلی انتخاب داخل ماشین را نشان داده، نه DNS عمومی یا دسترسی شبکه را. بررسی می‌کنم DNS به IP درست اشاره کند، Nginx روی interface عمومی listen داشته باشد، و firewall/security group پورت ۸۰ را باز کند. هر مدرک مرز متفاوتی را می‌آزماید.

Not necessarily; the local test proves selection inside the host, not public DNS or network reachability. Check that DNS points to the right IP, Nginx listens on the public interface, and the firewall/security group allows port 80. Each tests a different boundary.

۱۸. بلیت تشخیص کامل18. A complete diagnostic ticket

1) Run curl -v --resolve shop.test:18080:127.0.0.1 http://shop.test:18080/ and verify destination/header. 2) Read nginx -T for the correct config and find the exact shop name and listener. 3) If there is a mismatch, make one small change, test with nginx -t, reload the lab, then repeat the same curl and verify the shop-specific body. ماموریت: دو سایت محلی و یک نام خرابMission: two local sites and one broken name

یک Nginx ایزوله بساز که دو سایت روی یک پورت loopback ارائه کند. باید با مدرک نشان بدهی نام‌ها به block درست می‌رسند، درخواست ناشناس به default می‌رود، و typo را بدون دست‌زدن به سرویس واقعی پیدا و اصلاح می‌کنی.

Build an isolated Nginx that serves two sites on one loopback port. Prove that names reach the right blocks, an unknown name reaches the default, and a typo can be diagnosed and fixed without touching the live service.

  1. پوشهٔ موقت و سه فایل نشانگر بساز؛ مسیر LAB_DIR را نگه دار. هدف هر فایل این است که پاسخ قابل تشخیص باشد.Create a temporary directory and three marker files; keep the LAB_DIR path. Each file makes its response identifiable.

  3. پیش از start، nginx -t -p "$LAB_DIR/" -c nginx.conf بزن. اگر port 18080 اشغال است، همهٔ عددهای 18080 در config و فرمان‌های آزمایش را با port آزاد دیگری عوض کن.Before starting, run nginx -t -p "$LAB_DIR/" -c nginx.conf.   5. در config آزمایش نام beta را عمداً غلط کن. اول -t بگیر، بعد فقط آزمایشگاه را reload و همان درخواست beta را تکرار کن. خروجی default را به‌عنوان علامت mismatch ثبت کن.Intentionally mistype beta’s name in the lab config. Confirm that PID is no longer active; then recheck the printed LAB_DIR path and remove only that directory.

برای توقف، اول PID ذخیره‌شده در فایل آزمایش را می‌خوانیم و از همان config فرمان graceful quit می‌فرستیم. اگر process هنوز زنده است، پوشه را پاک نکن؛ چند لحظه صبر کن و دوباره PID را بررسی کن. حذف فقط وقتی مجاز است که مسیر چاپ‌شده دقیقاً همان پوشهٔ موقت خودت باشد.

To stop the lab, read its saved PID and send a graceful quit using the same config. If the process is still alive, do not remove the directory; wait briefly and check again. Delete only after confirming that the printed path is exactly your temporary lab directory.

stop and verify before targeted cleanup
PID_FILE="$LAB_DIR/logs/nginx.pid"
if [ -s "$PID_FILE" ]; then
  LAB_PID=$(cat "$PID_FILE")
  nginx -p "$LAB_DIR/" -c nginx.conf -s quit
  sleep 1
  if kill -0 "$LAB_PID" 2>/dev/null; then
    echo "PID $LAB_PID is still alive; do not remove the lab directory."
  else
    printf 'Review this exact disposable path before cleanup: %s\n' "$LAB_DIR"
  fi
else
  echo 'Lab PID file is absent; inspect the process manually before cleanup.'
fi

فرمان بالا عمداً پوشه را خودکار پاک نمی‌کند؛ اول باید خروجی PID و مسیر را ببینی. فقط اگر مطمئنی این همان پوشه‌ای است که mktemp ساخته، آن را حذف کن. اگر PID هنوز زنده است یا فایل PID نیست، stop کن و وضعیت را دستی بررسی کن—process دیگری را با حدس متوقف نکن.

The command deliberately does not delete the directory automatically; inspect the PID result and path first. Remove it only if you are certain it is the directory created by mktemp. If the PID is still alive or the PID file is missing, stop and inspect manually—never stop another process by guesswork.

اگر جواب هر دو سایت یکسان شد، سرنخ‌ها را به‌ترتیب باز کنIf both sites return the same body, open hints in order

اول مطمئن شو درخواست به port درست می‌رود و header همان نامی است که فکر می‌کنی. بعد -T را برای پیدا کردن config و server block مؤثر بخوان. اگر نام هست ولی پاسخ default است، ببین آن block روی همان address:port هم listen دارد یا نه. در پایان body را با root و فایل شاخص تطبیق بده.

First confirm the request reaches the intended port and carries the name you expect. Then use -T to find the effective config and server blocks. If the name exists but the default answers, check whether that block also listens on the same address:port. Finally compare the response body with the root and marker file.

اگر موقع توقف یا پاک‌سازی شک داریIf you are unsure about stopping or cleanup

مقدار pid را از $LAB_DIR/logs/nginx.pid بخوان و همان process را بررسی کن؛ فرمان -s quit باید با همان prefix و config اجرا شود. اگر process تمام نشده، پوشه را پاک نکن و سرویس دیگری را kill نکن. مسیر دقیق را با printf چاپ کن؛ حذف بازگشت‌پذیر نیست.

Read the PID from $LAB_DIR/logs/nginx.pid and verify that exact process; -s quit must use the same prefix and config. If it has not exited, do not remove the directory or kill another service. Print the exact path before cleanup; deletion is not reversible.
