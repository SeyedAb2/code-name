WebSocket و آپلود حجیم

WebSockets and large uploads

چت وصل می‌شود و بلافاصله قطع می‌شود؛ فایل هم با 413 برمی‌گردد. این دو خطا یکی نیستند: یکی handshake و اتصال ماندگار است، دیگری محدودیت بدنهٔ درخواست. با شاهد پیدا می‌کنیم هر کدام کجا متوقف شده.

The chat connects and immediately drops; a file upload returns 413. These are different failures: one concerns a handshake and a long-lived connection, the other a request-body limit. We will use evidence to find where each one stopped.

یکی می‌گوید «صفحهٔ چت باز می‌شود، اما چند لحظه بعد قطع می‌شود». دیگری می‌گوید «فایل ۸ مگابایتی رد شد». اگر هر دو را با یک timeout یا افزایش بی‌حساب buffer حل کنیم، احتمالاً فقط شواهد را پاک کرده‌ایم.

One report says, “The chat opens, then disconnects a moment later.” Another says, “An 8 MB file was rejected.” If we try to fix both with one timeout or by blindly increasing buffers, we may only erase the evidence.

از فصل قبل می‌دانیم status و log را باید کنار هم خواند. برای چت می‌پرسیم: آیا handshake تا 101 رسیده و connection مانده؟ برای آپلود: کدام لایه درخواست را رد کرده—Nginx یا برنامه؟ اول مسیر را می‌کشیم، بعد هر کدام را جدا آزمایش می‌کنیم.

From the previous chapter we know to read statuses beside logs. For chat: did the handshake reach 101, and did the connection remain open? For uploads: which layer rejected the request—Nginx or the app? We will map the path and test each separately.

WebSocket از کجا شروع می‌شود؟ از یک HTTP معمولیWhere does WebSocket begin? With ordinary HTTP

در اتصال WebSocket روی HTTP/1.1، client با یک درخواست HTTP و headerهای Upgrade و Connection درخواست تغییر پروتکل می‌کند. اگر سرور بپذیرد، پاسخ 101 Switching Protocols می‌آید؛ بعد همان اتصال برای پیام‌های دوطرفه باز می‌ماند. 101 یعنی handshake پذیرفته شد، نه اینکه هر پیام بعدی حتماً درست کار می‌کند.

With WebSocket over HTTP/1.1, the client sends an HTTP request with Upgrade and Connection headers to request a protocol switch. If accepted, the server replies 101 Switching Protocols; the same connection then stays open for two-way messages. A 101 proves the handshake was accepted, not that every later message will work.

فلش‌های آبی درخواست handshake را به سمت برنامه می‌برند؛ فلش برگشتی پاسخ 101 است. پس از آن پیام‌ها همچنان از Nginx عبور می‌کنند؛ اتصال مستقیم client به برنامه ساخته نمی‌شود.

Blue arrows carry the handshake request toward the app; the returning arrow is the 101 response. Afterward, messages still pass through Nginx—the client does not become directly connected to the app.

Nginx headerهای hop-by-hop مثل Upgrade و Connection را خودکار به upstream نمی‌فرستد. برای همین ممکن است HTTP عادی proxy شود ولی WebSocket بالا نیاید. در فصل ۶ هدرهای proxy را شناختیم؛ اینجا باید تغییر پروتکل را صریح عبور بدهیم.

Nginx does not automatically pass hop-by-hop headers such as Upgrade and Connection to the upstream. Ordinary HTTP can therefore proxy correctly while WebSocket fails. We met proxy headers in Chapter 6; here we must explicitly forward the protocol switch.

Connection را برای هر درخواست یکسان نگذارDo not set Connection the same way for every request

برای یک endpoint WebSocket، مقدار ثابت Connection "upgrade" ممکن است جواب بدهد؛ اما همان server درخواست HTTP معمولی هم دارد. الگوی map در بخش http، وقتی client واقعاً Upgrade فرستاده مقدار upgrade می‌سازد و در بقیهٔ درخواست‌ها close می‌گذارد. map اینجا تصمیم هدر را روشن می‌کند.

For a WebSocket-only endpoint, a fixed Connection "upgrade" may work, but the same server also handles ordinary HTTP. A map in the http block sets upgrade when the client actually requested it and close otherwise. Here the map makes the header decision explicit.

the compatibility-conscious WebSocket proxy pattern
http {
    map $http_upgrade $connection_upgrade {
        default upgrade;
        ''      close;
    }
    server {
        location = /ws {
            proxy_pass http://127.0.0.1:19111;
            proxy_http_version 1.1;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection $connection_upgrade;
            proxy_read_timeout 75s;
        }
    }
}

در نسخه‌های Nginx قدیمی‌تر از 1.29.7، HTTP/1.0 مقدار پیش‌فرض proxy_http_version بود؛ در نسخه‌های جدیدتر پیش‌فرض 1.1 شده. ما آن را صریح می‌نویسیم تا رفتار فصل به نسخه وابسته نماند. map باید در context http باشد، نه داخل server یا location.

Before Nginx 1.29.7, the default proxy_http_version was HTTP/1.0; newer versions default to 1.1. We write it explicitly so the chapter’s behavior is not version-dependent. The map belongs in the http context, not inside server or location.

proxy_read_timeout 75s نمی‌گوید کل WebSocket فقط ۷۵ ثانیه عمر دارد. فاصلهٔ بی‌داده بین دو خواندن از upstream نباید از این مقدار عبور کند؛ ping منظم برنامه می‌تواند اتصال زنده را فعال نگه دارد. timeout را با heartbeat برنامه هماهنگ کن، نه با حدس.

proxy_read_timeout 75s does not cap the WebSocket’s total lifetime at 75 seconds. It limits the idle gap between successive reads from the upstream; regular application pings can keep an active connection alive. Coordinate the timeout with the app’s heartbeat rather than guessing.

پس از handshake موفق، WebSocket هنوز از Nginx رد می‌شود. «Tunnel» یعنی Nginx دو جریان پیام را روی اتصال proxyشده عبور می‌دهد؛ نه اینکه proxy ناپدید شود یا client به socket داخلی برنامه دسترسی پیدا کند.After a successful handshake, WebSocket still passes through Nginx. “Tunnel” means Nginx relays the two message streams over the proxied connection; the proxy does not disappear and the client does not gain access to the app’s internal socket.

وابستگی ws فقط در این پوشهٔ موقت نصب می‌شود. برنامه payload آپلود را ذخیره نمی‌کند؛ فقط تعداد بایت را می‌شمارد. سقف داخلی ۴ MiB هم می‌گذاریم تا اگر Nginx را دور زدیم، app بی‌محابا داده نپذیرد.

The ws dependency is installed only in this temporary directory. The app does not store upload payloads; it only counts bytes. We also set a 4 MiB application limit so bypassing Nginx does not make the app accept unlimited data.

create the tiny bounded echo and upload service
cd "$WS_LAB"
npm init -y
npm install ws
cat > server.js <<'JS'
const http = require('node:http');
const { WebSocketServer } = require('ws');
const server = http.createServer((req, res) => {
  if (req.method === 'POST' && req.url === '/upload') {
    const max = 4 * 1024 * 1024;
    let bytes = 0;
    let rejected = false;
    req.on('data', chunk => {
      bytes += chunk.length;
      if (bytes > max && !rejected) {
        rejected = true;
        console.log('UPLOAD rejected bytes=' + bytes);
        res.writeHead(413).end('app limit exceeded\n');
        req.resume();
      }
    });
    req.on('end', () => {
      if (rejected) return;
      console.log('UPLOAD accepted bytes=' + bytes);
      res.writeHead(200, { 'content-type': 'text/plain' });
      res.end('received=' + bytes + ' bytes; not stored\n');
    });
    return;
  }
  if (req.url === '/ws') {
    console.log('HTTP /ws without Upgrade');
    res.writeHead(426, { 'content-type': 'text/plain', 'sec-websocket-version': '13' });
    res.end('WebSocket upgrade required\n');
    return;
  }
  res.writeHead(200, { 'content-type': 'text/plain' });
  res.end('try /ws or POST /upload\n');
});
const wss = new WebSocketServer({ noServer: true });
server.on('upgrade', (req, socket, head) => {
  if (req.url !== '/ws') return socket.destroy();
  wss.handleUpgrade(req, socket, head, ws => wss.emit('connection', ws, req));
});
wss.on('connection', ws => {
  console.log('WS connected');
  ws.on('message', data => {
    console.log('WS message bytes=' + data.length);
    ws.send('echo: ' + data);
  });
});
server.listen(19111, '127.0.0.1', () => console.log('app listening on 127.0.0.1:19111'));

کد فقط دو نقش دارد: اگر Upgrade نرسد، /ws یک 426 روشن می‌دهد؛ اگر handshake برسد، echo service پیام را برمی‌گرداند. اگر npm install شکست خورد، قبل از ادامهٔ Nginx، شبکه/registry یا نسخهٔ Node را بررسی کن؛ این خطا هنوز دربارهٔ proxy چیزی نمی‌گوید.

The code has two jobs: if Upgrade is absent, /ws returns a clear 426; if the handshake arrives, the echo service sends the message back. If npm install fails, inspect network/registry or Node version before continuing; that failure says nothing about the proxy yet.

یک client کوچک هم لازم داریم که handshake واقعی بزند و یک پیام بفرستد. رخداد unexpected-response را چاپ می‌کند تا پاسخ ردشده را با «connection timeout» اشتباه نگیریم.

We also need a client that performs a real handshake and sends one message. It prints unexpected-response so we do not confuse a rejected handshake with a connection timeout.

write a one-message WebSocket client
cat > client.js <<'JS'
const WebSocket = require('ws');
const ws = new WebSocket('ws://127.0.0.1:18111/ws');
ws.on('open', () => ws.send('hello-nginx'));
ws.on('message', data => {
  console.log(data.toString());
  ws.close();
});
ws.on('unexpected-response', (_req, res) => {
  console.log('handshake rejected: HTTP ' + res.statusCode);
  process.exitCode = 1;
  ws.terminate();
});
ws.on('error', err => {
  console.error('connection error: ' + err.message);
  process.exitCode = 1;
});

خرابی اول: HTTP عادی می‌رسد، Upgrade نهFailure one: ordinary HTTP arrives, Upgrade does not

یک Nginx آزمایشی می‌سازیم که عمداً headerهای WebSocket را عبور نمی‌دهد. timeout را فعلاً دست نمی‌زنیم؛ می‌خواهیم یک چیز را عوض کنیم و ببینیم شکست handshake چه شکلی است.

We will configure test Nginx to deliberately omit the WebSocket headers. We will leave timeouts alone for now so one changed condition produces one observable handshake failure.

first config: HTTP proxy works, WebSocket headers are deliberately absent

اتصال ماندگار یعنی سکوت را درست تفسیر کنA persistent connection makes silence matter

برای request معمولی، بعد از پاسخ اتصال تمام می‌شود. WebSocket ممکن است باز بماند اما مدتی هیچ داده‌ای نفرستد. proxy_read_timeout زمان کل connection نیست؛ فاصلهٔ مجاز بین دو عملیات خواندن از upstream است. اگر app heartbeat ندارد، اتصال خاموش می‌تواند بعد از این فاصله بسته شود.

An ordinary request ends after its response. A WebSocket can stay open while sending no data for a while. proxy_read_timeout is not a total connection lifetime; it is the allowed gap between successive reads from the upstream. Without an app heartbeat, a quiet connection may close after that gap.

timeoutهای proxy معمولاً فاصلهٔ بی‌فعالیت بین عملیات‌های پیاپی را محدود می‌کنند، نه کل مدت اتصال را. عدد ۷۵ ثانیه اینجا نمونهٔ آزمایش است، نه نسخهٔ همگانی. heartbeat برنامه، timeout load balancer بالادست و رفتار client را کنار هم بررسی کن؛ timeout طولانی به‌تنهایی connection مرده را تشخیص نمی‌دهد.

Proxy timeouts generally limit the idle gap between successive operations, not the connection’s total lifetime. The 75-second value here is a lab example, not a universal recommendation. Check the app heartbeat, any upstream load-balancer timeout, and client behavior together; a longer timeout alone cannot detect a dead connection.

آپلود پیش از رسیدن به برنامه هم ممکن است رد شودAn upload can be rejected before reaching the app

در درخواست POST، کلاینت بدنه را به Nginx می‌دهد و Nginx آن را به برنامه proxy می‌کند. client_max_body_size سقف بدنهٔ درخواست client است و می‌تواند در http، server یا location تنظیم شود. اگر بدنه از سقف بگذرد، Nginx پاسخ 413 می‌دهد؛ برنامه لازم نیست اصلاً درخواست را ببیند.

For a POST, the client sends a body to Nginx, which proxies it to the app. client_max_body_size limits the client request body and can be set in http, server, or location. If the body exceeds the limit, Nginx returns 413; the app may never see the request.

شاخهٔ قرمز پیش از برنامه با 413 برمی‌گردد؛ شاخهٔ آبی اجازهٔ عبور از سقف Nginx را می‌گیرد اما هنوز باید از محدودیت خود برنامه رد شود. نوار پایین یادآوری می‌کند buffering می‌تواند دیسک موقت Nginx را درگیر کند.

The red branch returns 413 before the app; the blue branch passes Nginx’s gate but must still satisfy the app’s own limit. The lower note reminds us that buffering may use Nginx temporary disk space.

در آزمایش، سقف را 64 KiB می‌گذاریم و بدنه‌ای 128 KiB می‌فرستیم. چون خود برنامه درخواست‌های رسیده را در app.log ثبت می‌کند، سه چیز را می‌سنجیم: پاسخ client، status در access log و حضور یا نبود خط upload در app log.

In the lab we set a 64 KiB limit and send a 128 KiB body. Because the app logs requests that reach it, we check three things: the client response, Nginx access status, and whether an upload line appears in the app log.

تنظیم نمونه برای endpoint آپلود این است؛ سقف واقعی باید از نیاز محصول، فضای دیسک موقت و سقف برنامه به دست بیاید. عدد را صرفاً برای ساکت‌کردن 413 بی‌نهایت نکن.

This is a sample setting for an upload endpoint; choose a real limit from product needs, temporary disk capacity, and the application’s own limit. Do not make it infinite just to silence a 413.

scope the body-size policy only to the upload route
location = /upload {
    client_max_body_size 64k;
    proxy_request_buffering on;
    proxy_pass http://127.0.0.1:19111;
}

به‌طور پیش‌فرض Nginx درخواست را buffer می‌کند: کل body را از client می‌خواند و بعد برای upstream می‌فرستد. بدنهٔ بزرگ می‌تواند از bufferهای حافظه به فایل موقت برود؛ پس دیسک موقت هم بخشی از مسیر است. وقتی buffering خاموش باشد، Nginx بدنه را هم‌زمان با رسیدنش به upstream می‌فرستد.

By default Nginx buffers a request: it reads the full body from the client before sending it upstream. A large body may spill from memory buffers to a temporary file, so temporary disk is part of the path too. With buffering off, Nginx streams the body upstream as it arrives.

Turning buffering off is not a universal upload fix. If Nginx has sent part of the body and the upstream fails, it cannot safely retry that same request to another server. Chunked HTTP/1.1 behavior also depends on the proxied protocol version; measure the real flow before changing it.

سقف Nginx تنها سقف سامانه نیست. خود برنامه، framework، API gateway، فضای موقت و سیاست نگهداری فایل می‌توانند حدهای دیگری داشته باشند. درخواست از مسیر بیرونی و داخل lab جداگانه آزمایش می‌شود.Nginx’s limit is not the system’s only limit. The app, framework, API gateway, temporary storage, and file-retention policy may impose others. Test the external path and the lab path separately.

در محیط آزمایش یک فایل صفرپر و محدود می‌سازیم؛ دادهٔ واقعی یا فایل حساس نیست. با سقف 64 KiB، درخواست 128 KiB باید پیش از app رد شود. اگر status متفاوت بود، اول تنظیم مؤثر و اندازهٔ واقعی body را بررسی کن.

In the lab we create a small zero-filled file—not real or sensitive data. With a 64 KiB limit, a 128 KiB request should be rejected before the app. If the status differs, inspect effective configuration and actual body size first.

حالا همان درخواست را از سقف Nginx عبور می‌دهیم. یک تغییر محدود، آزمون syntax، reload و تکرار همان body؛ اگر نتیجه بهتر شد، علت نزدیک‌تری پیدا کرده‌ایم.

Now we let the same request pass the Nginx limit. One bounded change, a syntax test, reload, and the same body again; if the result changes, we have stronger evidence about the cause.

  nginx -s reload -p "$WS_LAB/" -c nginx.conf

حالا همان درخواست از Nginx پاسخ 200 می‌گیرد و app تعداد بایت را ثبت می‌کند؛ این بار هر دو لایه اجازه داده‌اند. تغییر config با nginx -t پیش از reload اعتبارسنجی شد. این آزمایش فقط مسیر و payload آزمایش‌شده را ثابت می‌کند؛ سقف‌های واقعی framework، gateway و filesystem باید جدا سنجیده شوند.

The same request now gets 200 through Nginx, and the app logs its byte count; both layers allowed it. We validated the config with nginx -t before reloading. This proves only the tested route and payload; real framework, gateway, and filesystem limits need separate checks.

۱. 101 یعنی چه؟What does 101 mean?

Nginx access log برای /ws مقدار 101 دارد، اما client هنوز پیام echo ندیده. چه چیزی ثابت شد؟

The Nginx access log shows 101 for /ws, but the client has not received an echo yet. What is proven?

تفسیرInterpretation

Handshake پذیرفته شده و تغییر پروتکل رخ داده؛ دریافت و پردازش پیام بعدی هنوز ثابت نیست. app log، رخداد message و اتصال پس از handshake را بررسی کن.

The handshake was accepted and the protocol switch occurred; later message delivery is not proven. Check app logs, the message event, and the connection after the handshake.

۲. 200 به جای 101200 instead of 101

client انتظار WebSocket دارد ولی پاسخ HTTP 200 می‌گیرد. یک فرضیهٔ اول چیست؟

The client expects WebSocket but gets HTTP 200. What is one first hypothesis?

پاسخ و قدم بعدAnswer and next step

ممکن است درخواست به route عادی رسیده یا Upgrade به upstream نرسیده باشد. response headers و app log را بخوان؛ بعد config location و proxy_set_header Upgrade را بررسی کن، نه اینکه فوراً timeout را زیاد کنی.

It may have reached an ordinary route or Upgrade may not have reached the upstream. Inspect response headers and app logs, then the location config and proxy_set_header Upgrade before increasing timeouts.

۳. header گم‌شدهA missing header

چرا Nginx header Upgrade را بی‌تنظیم به upstream نمی‌فرستد؟

Why does Nginx not forward Upgrade to the upstream automatically?

دلیلReason

Upgrade و Connection از headerهای hop-by-hop هستند و proxy آن‌ها را خودکار عبور نمی‌دهد. باید قصد تغییر پروتکل را صریح به upstream منتقل کرد.

Upgrade and Connection are hop-by-hop headers and the proxy does not automatically pass them through. The protocol-switch intent must be explicitly sent upstream.

۴. map کجا تعریف می‌شود؟Where does map belong?

Nginx می‌گوید map directive is not allowed here. احتمالاً چه چیزی جابه‌جا است؟

Nginx says map directive is not allowed here. What is probably misplaced?

اصلاح مفهومیConceptual fix

map باید در context سطح http باشد، نه در server یا location. جای directive را اصلاح کن و پیش از reload دوباره nginx -t بزن.

map belongs at http scope, not in server or location. Move it and rerun nginx -t before reloading.

۵. Connection همیشه upgrade؟Connection always upgrade?

چرا برای server دارای HTTP عادی و WebSocket، map از مقدار ثابت بهتر است؟

Why is a map better than a fixed value when one server handles HTTP and WebSocket?

پاسخAnswer

فقط درخواست دارای Upgrade مقدار upgrade می‌گیرد؛ باقی درخواست‌ها Connection معمولی/بسته دارند. این الگو نیت هر درخواست را متناسب با header ورودی تنظیم می‌کند.

Only a request carrying Upgrade gets the upgrade value; ordinary requests get a non-upgrade/close value. The map adapts the header to each incoming request.

۶. timeout گذشت و اتصال بسته شدThe connection closed after the timeout

Nginx اتصال 101 را پس از ۷۵ ثانیه سکوت بست. آیا این ثابت می‌کند کل عمر WebSocket سقف ۷۵ ثانیه دارد؟

Nginx closed a 101 connection after 75 seconds of silence. Does this prove the WebSocket’s total lifetime is capped at 75 seconds?

تفسیرInterpretation

خیر؛ proxy_read_timeout فاصلهٔ بی‌داده بین readهای upstream را محدود می‌کند. heartbeat، زمان آخرین پیام و timeout لایه‌های دیگر را هم بررسی کن.

No. proxy_read_timeout limits the idle gap between upstream reads. Check heartbeats, the last-message time, and timeouts at other layers too.

۷. فقط proxy_http_versionOnly proxy_http_version

نسخهٔ proxy را 1.1 گذاشتی ولی هنوز 426 می‌گیری. چرا این کافی نیست؟

You set the proxy version to 1.1 but still get 426. Why is that insufficient?

پاسخAnswer

HTTP/1.1 به‌تنهایی Upgrade را عبور نمی‌دهد. headerهای Upgrade و Connection باید صریح تنظیم و app log برای نوع درخواست بررسی شود.

HTTP/1.1 alone does not forward Upgrade. Explicitly set Upgrade and Connection, then inspect the app log to see what kind of request arrived.

۸. 413 با 128 KiB413 for 128 KiB

Nginx برای body برابر 128 KiB و سقف 64 KiB پاسخ 413 داده. app log خطی ندارد. نتیجهٔ محتمل چیست؟

Nginx returned 413 for a 128 KiB body with a 64 KiB limit; the app has no log line. What is the likely conclusion?

تفسیرInterpretation

درخواست احتمالاً در Nginx، پیش از رسیدن به app، رد شده. برای تقویت تشخیص، access/error log، اندازهٔ body و پیکربندی مؤثر همان location را کنار هم ببین.

The request was likely rejected at Nginx before reaching the app. Correlate access/error logs, body size, and effective config for that location to strengthen the diagnosis.

۹. app هم 413 می‌دهدThe app also returns 413

app log همان درخواست را ثبت کرده و response 413 است. آیا client_max_body_size قطعاً منشأ خطاست؟

The app logged the request and the response is 413. Is client_max_body_size definitely the source?

پاسخAnswer

نه؛ برنامه یا framework می‌تواند 413 برگرداند. متن پاسخ، headerها و log برنامه را بررسی کن. یک status کد لزوماً لایهٔ تولیدکننده را مشخص نمی‌کند.

No. The app or framework can return 413. Inspect the response body, headers, and app logs. A status code alone does not identify which layer generated it.

۱۰. بزرگ‌کردن تا بی‌نهایتIncrease it without limit

تیم برای رفع 413 می‌خواهد سقف را 0 بگذارد. چه نکته‌ای باید بداند؟

The team wants to set the limit to 0 to fix 413. What must they know?

هشدارCaution

در Nginx مقدار 0 بررسی اندازهٔ body را غیرفعال می‌کند؛ این ظرفیت نامحدود واقعی نمی‌سازد و می‌تواند مصرف منابع را باز بگذارد. نیاز محصول و سقف app/disk را مشخص کن و حد محدود بگذار.

In Nginx, zero disables request-body size checking; it does not create truly unlimited capacity and can expose resource consumption. Define the product, app, and disk needs, then set a bounded limit.

۱۱. multipart چقدر است؟How large is multipart?

فایل دقیقاً 64 KiB است و سقف هم 64 KiB؛ آیا باید حتماً پذیرفته شود؟

The file is exactly 64 KiB and the limit is 64 KiB. Must it be accepted?

پاسخAnswer

نه؛ client_max_body_size کل request body را می‌سنجد، نه فقط بایت فایل. multipart boundary و metadata هم به body اضافه می‌شوند. کمی سربار را در طراحی حد لحاظ کن.

No. client_max_body_size limits the whole request body, not just file bytes. Multipart boundaries and metadata add overhead; account for that when choosing a limit.

۱۲. buffering خاموش، failover هم خاموش؟Buffering off, failover off too?

با proxy_request_buffering off بخشی از body ارسال شده و upstream از دسترس خارج می‌شود. آیا Nginx می‌تواند بی‌خطر body را به backend دیگری بفرستد؟

With proxy_request_buffering off, part of the body has been sent and the upstream fails. Can Nginx safely send it to another backend?

توضیحExplanation

پس از شروع ارسال body، retry به upstream بعدی ممکن نیست؛ Nginx نمی‌تواند درخواست ناقص را از ابتدا تکرار کند. این هزینه را پیش از خاموش‌کردن buffering بپذیر.

Once body forwarding starts, retrying another upstream is not possible; Nginx cannot safely replay the incomplete request from the beginning. Understand this tradeoff before disabling buffering.

۱۳. فایل موقت پر شدTemporary storage filled

بعد از آپلودهای بزرگ، disk مربوط به temp پر شده ولی سقف body بالاتر نرفته. کجا را بررسی می‌کنی؟

After large uploads, temporary disk fills even though the body limit did not change. What do you inspect?

قدم بعدNext step

فضای filesystem و مسیرهای client-body temp Nginx، اندازه و تعداد uploadهای هم‌زمان و buffering را بررسی کن. بالا بردن limit ممکن است فشار دیسک را بیشتر کند.

Inspect filesystem capacity, Nginx client-body temp paths, upload size/concurrency, and buffering. Raising the limit may increase disk pressure.

۱۴. ورودی chunkedA chunked request

در proxy buffering خاموش است ولی بدنهٔ chunked همچنان buffer می‌شود. چه چیزی را بررسی می‌کنی؟

Proxy buffering is off, yet a chunked body is still buffered. What do you check?

پاسخAnswer

نسخهٔ protocol بین Nginx و upstream و رفتار مستند همان نسخه را بررسی کن. برای HTTP/1.1 chunked، مستند Nginx استثناهایی دارد؛ فقط یک directive را با نتیجهٔ فرضی تفسیر نکن.

Check the protocol version between Nginx and upstream and its documented behavior. Nginx documents exceptions for HTTP/1.1 chunked requests; do not infer behavior from one directive alone.

۱۵. محدودیت در سه لایهLimits at three layers

Nginx مجاز می‌داند، app رد می‌کند و gateway هم سقف جدا دارد. «حد واقعی آپلود» را چطور گزارش می‌کنی؟

Nginx allows the request, the app rejects it, and the gateway has another limit. How do you report the “real upload limit”?

پاسخAnswer

به‌صورت کوچک‌ترین سقف مسیر واقعی درخواست، با ذکر هر لایه و مسیر آزموده‌شده. client ممکن است از gateway دیگری عبور کند؛ policy را در کل مسیر مستند و end-to-end آزمایش کن.

As the smallest limit along the actual request path, naming each layer and tested route. Clients may traverse another gateway; document the end-to-end policy and test the full path.

۱۶. Upgrade در HTTP/2Upgrade with HTTP/2

مستند یا config سادهٔ این درس را برای HTTP/2 client عیناً به کار می‌بری؟

Would you apply this lesson’s simple config unchanged to an HTTP/2 client?

پاسخ دقیقPrecise answer

نه بدون بررسی. الگوی این درس WebSocket روی HTTP/1.1 با headerهای Upgrade/Connection است. WebSocket over HTTP/2 سازوکار متفاوتی دارد و به نسخه و زنجیرهٔ proxy وابسته است؛ scope فعلی را با آن یکی نکن.

Not without checking. This lesson’s pattern is WebSocket over HTTP/1.1 using Upgrade/Connection headers. WebSocket over HTTP/2 uses a different mechanism and depends on versions and the proxy chain; do not conflate the scopes.

۱۷. timeout را کجا زیاد کنیم؟Where should we increase a timeout?

اتصال هر ۵۹ ثانیه قطع می‌شود، هیچ 101 ثبت نشده. آیا افزایش proxy_read_timeout قدم اول است؟

Connections drop after 59 seconds, but no 101 appears. Is increasing proxy_read_timeout the first step?

استدلالReasoning

نه؛ بدون handshake 101 هنوز tunnel ساخته نشده. اول route، headerها، پاسخ app و access/error log را درست کن؛ timeout را فقط وقتی 101 و سکوت پس از آن را دیدی بررسی کن.

No. Without a 101, the tunnel was never established. First check route, headers, app response, and access/error logs; investigate timeout only after observing 101 followed by silence.

۱۸. گزارش کوتاه حادثهA short incident report

client یک 413 می‌بیند؛ access log Nginx آن را ثبت کرده ولی app هیچ خطی ندارد. چه چیزی را با اطمینان می‌نویسی و قدم بعدی چیست؟

A client sees 413; Nginx access logs it, but the app has no line. What can you state confidently, and what is your next check?

یک پاسخ قابل دفاعA defensible answer

درخواست از Nginx عبور کرده اما در app log نشانه‌ای از رسیدنش نیست؛ این با رد در proxy سازگار است، ولی نبود log به‌تنهایی اثبات مطلق نیست. اندازهٔ request، config مؤثر client_max_body_size، error log و مسیر مستقیم app را بررسی می‌کنم، سپس همان request را پس از تغییر محدود تکرار می‌کنم.

The request reached Nginx, but the app has no evidence of receiving it; that is consistent with proxy rejection, though a missing log alone is not absolute proof. I would check request size, effective client_max_body_size, error logs, and the direct app path, then repeat the same request after a bounded change.

ماموریت: دو قابلیت، دو شاهد جداMission: two features, two separate proofs

یک مسیر چت باید پیام را echo کند و endpoint آپلود باید تا ۱ MiB را بپذیرد. شرط تیم این است که Nginx WebSocket را proxy کند، درخواست بزرگ‌تر را در سقف مشخص رد کند، و گزارش نشان دهد رد از کدام لایه بوده. از همان lab موقت استفاده کن؛ فایلی را روی میزبان پر نکن.

A chat route must echo a message, and the upload endpoint must accept up to 1 MiB. The team requires Nginx to proxy WebSocket, reject larger requests at a defined limit, and report which layer rejected them. Use the disposable lab; do not fill host storage.

  1. نسخهٔ خراب را ثبت کن: WebSocket را اجرا کن و پاسخ 426 و خط app را نگه دار.
  2. headerهای درست را اضافه کن، nginx -t و reload بزن؛ پیام echo و 101 را نگه دار.
  3. یک body کوچک و بعد 128 KiB بفرست؛ پاسخ و دو log را مقایسه کن.
  4. سقف route را محدود به مقدار موردنیاز کن، نه 0؛ درخواست 128 KiB را از مسیر proxy بپذیر.
  5. عمداً سقف Nginx را موقتاً پایین بیاور، 413 و نبود خط app را ثابت کن، بعد تنظیم را برگردان و همان تست را تکرار کن.
  6. گزارش بنویس: نشانه، شاهد هر لایه، علت، تعمیر و همان آزمون پس از تعمیر.
  1. Record the broken baseline: run WebSocket and capture 426 plus the app log.
  2. Add the correct headers, run nginx -t, reload, and capture the echo and 101.
  3. Send a small body, then 128 KiB; compare the response and both logs.
  4. Set a bounded route limit appropriate to the need, not 0; allow the 128 KiB request through the proxy.
  5. Temporarily lower Nginx’s limit, prove the 413 and missing app line, then restore the config and repeat the same test.
  6. Write a report: symptom, evidence at each layer, cause, repair, and the same verification after repair.
راهنمایی؛ یک بار فقط header را تغییر بدهHint: change only the headers first

اگر app می‌گوید HTTP /ws without Upgrade، به timeout دست نزن. برای 413، نبود خط app را با access log و پاسخ همان درخواست کنار هم بخوان.

If the app says HTTP /ws without Upgrade, do not touch the timeout. For 413, correlate the missing app line with the access log and that request’s response.

راه‌حل نمونه؛ فقط چیزی را نتیجه بگیر که تکرار کردیSample resolution: claim only what you repeated

در نسخهٔ خراب، 426 و خط HTTP عادی در app، نبود Upgrade را نشان می‌دهند. پس از map و ارسال دو header، client پیام echo می‌گیرد و access log 101 ثبت می‌کند. برای آپلود، body کوچک 200 می‌گیرد؛ body بزرگ با سقف پایین 413 است و app خطی ندارد. پس از تنظیم محدود 1 MiB، همان body از proxy عبور می‌کند و app بایت‌ها را می‌شمارد. این نتیجه فقط برای مسیر و payloadهای آزمایش‌شده است؛ سقف framework، gateway و filesystem production باید جدا سنجیده شوند.

In the broken version, 426 plus the app’s ordinary-HTTP log shows Upgrade was missing. After the map and both forwarded headers, the client receives an echo and access logs 101. With a low upload limit, the small body gets 200 while the large one gets 413 and no app line. After setting a bounded 1 MiB limit, the same body passes the proxy and the app counts the bytes. This conclusion applies only to the tested path and payloads; production framework, gateway, and filesystem limits must be checked separately.

آزمایش را امن جمع کنClean up the lab safely

لاگ‌ها را تا پایان گزارش نگه دار. Nginx را با prefix همین آزمایش متوقف کن؛ برنامه را فقط وقتی بکش که command line آن به فایل server.js همین پوشه اشاره می‌کند. اگر بررسی هویت شکست خورد، PID را دست نزن و پوشه را هم حذف نکن.

Keep logs until the report is complete. Stop Nginx using this lab’s prefix; kill the app only if its command line points to server.js in this exact directory. If the identity check fails, do not touch the PID or remove the directory.

stop only matching processes; remove only the verified lab directory
nginx -s quit -p "$WS_LAB/" -c nginx.conf || true
MASTER_PID_FILE="$WS_LAB/run/nginx.pid"
for _ in $(seq 1 50); do
  [ -s "$MASTER_PID_FILE" ] || break
  kill -0 "$(cat "$MASTER_PID_FILE")" 2>/dev/null || break
  sleep 0.1
done
APP_PID=$(cat "$WS_LAB/pids/app.pid")
APP_ARGS=$(ps -p "$APP_PID" -o args= 2>/dev/null || true)
case "$APP_ARGS" in
  *"$WS_LAB/server.js"*) kill "$APP_PID" ;;
  *) echo 'App PID does not match this lab; leaving it untouched.' ;;
esac
if { [ -s "$MASTER_PID_FILE" && kill -0 "$(cat "$MASTER_PID_FILE")" 2>/dev/null; } || \
   { [ -n "$APP_ARGS" && kill -0 "$APP_PID" 2>/dev/null; }; then
  echo 'A lab process is still alive; keep the directory and inspect.'
else
  case "$WS_LAB" in
    /tmp/nginx-ws.*)
      printf 'Verified disposable directory: %s\n' "$WS_LAB"
      read -r -p 'Type REMOVE to delete it: ' CONFIRM
      [ "$CONFIRM" = REMOVE ] && rm -rf -- "$WS_LAB"
      ;;
    *) echo 'Unexpected path; nothing removed.' ;;
  esac
fi

حذف فقط در مسیر /tmp/nginx-ws.* مجاز است و تأیید متنی می‌خواهد. این آزمایش هیچ volume یا دادهٔ کاربر ندارد؛ همین مرز را حفظ کن و فرمان را برای پوشهٔ دیگری تغییر نده.

Removal is allowed only under /tmp/nginx-ws.* and requires typed confirmation. This lab has no user data or persistent volume; keep that boundary and do not adapt the command to another directory.
