فایل استاتیک، کش مرورگر، فشرده‌سازی

Static files, browser cache, compression

نسخهٔ تازه را منتشر کرده‌ای، اما یکی از همکارها هنوز ظاهر قبلی صفحه را می‌بیند. از کجا بفهمیم Nginx فایل اشتباه را فرستاده، مرورگر نسخهٔ قدیمی را نگه داشته، یا فایل روی سیم فشرده شده؟ به‌جای حدس، از هدرهای پاسخ سرنخ می‌گیریم.

You deployed a new version, but a teammate still sees the old page. Did Nginx send the wrong file, did the browser keep an older copy, or was the file compressed in transit? Rather than guess, we will use response headers as evidence.

در فصل قبل فهمیدیم کدام location پاسخ می‌دهد. این بار فرض می‌کنیم انتخاب درست است و فایل از مسیر درست خوانده می‌شود؛ بااین‌حال، چیزی که کاربر می‌بیند با نسخهٔ تازهٔ سایت جور نیست. پیش از دست‌کاری تنظیمات، یک سؤال: پاسخ سرور چه می‌گوید که بتوانیم فرق «فایل تازه»، «اعتبارسنجی نسخه» و «فشرده‌سازی» را بفهمیم؟

The previous chapter taught us which location handles a request. This time, assume the selected location and filesystem path are correct; still, the user does not see the new site. Before changing settings, ask: what can the server response tell us about a fresh file, a validated cached copy, and compression?

یک درخواست HEAD با curl -I بدنه را نمی‌گیرد، اما هدرهایی را نشان می‌دهد که برای تصمیم‌گیری دربارهٔ کش و encoding لازم‌اند. اول پاسخ HTML و بعد یک فایل CSS را نگاه می‌کنیم. فعلاً دنبال هدرهای خاصی نباش؛ فقط ثبت کن چه چیزی وجود دارد و چه چیزی نه.

Content-Type می‌گوید Nginx فایل را چه نوعی معرفی کرده، و Last-Modified و ETag دو شناسه برای سنجش نسخه‌اند. نکتهٔ مهم‌تر این است که هنوز Cache-Control ندیدیم: از این خروجی نمی‌شود نتیجه گرفت مرورگر حتماً فایل را برای مدتی نگه می‌دارد یا حتماً هر بار می‌گیرد.

More importantly, there is no Cache-Control shown yet: this output does not prove that the browser will keep the file for a fixed period or fetch it every time.

سه سؤال جداThree separate questions

«فایل درست را پیدا کرد؟»، «کلاینت اجازه دارد پاسخ را نگه دارد یا باید دوباره اعتبارش را بسنجد؟» و «بدنه با چه encodingای فرستاده شد؟» سه مسئله‌اند. هدر پاسخ کمک می‌کند هرکدام را جدا بررسی کنیم؛ یک 200 به‌تنهایی جواب همه نیست.

“Did Nginx find the intended file?”, “May the client reuse its copy, or must it revalidate?”, and “Which encoding was sent?” are separate questions. Response headers let us investigate each one; a 200 alone does not answer them all.

فلش بالایی درخواست از مرورگر به Nginx و فایل‌سیستم را نشان می‌دهد؛ پاسخ از فیلترهای Nginx می‌گذرد و برمی‌گردد. اگر پاسخ هنوز تازه باشد، مرورگر ممکن است اصلاً درخواست جدیدی نفرستد؛ اگر منقضی شده باشد، با validator درخواست می‌کند و شاید فقط 304 بگیرد. gzip در مسیر پاسخ است، نه تغییری در فایل روی دیسک.

The upper path is a browser request through Nginx to the filesystem; the response passes through Nginx filters on its way back. A still-fresh response may be reused without a new request. After it becomes stale, the browser may revalidate and receive only 304. gzip is applied to the response, not to the file stored on disk.

فایل روی دیسک است؛ Nginx چطور پیدایش می‌کند؟The file is on disk; how does Nginx find it?

تا اینجا فایل‌ها را ساخته‌ایم، اما هنوز سروری نداریم که پاسخ بدهد. root به Nginx می‌گوید URI را به چه پوشه‌ای وصل کند؛ index برای درخواست یک پوشه دنبال چه نامی بگردد؛ و try_files چه زمانی درخواست را با 404 تمام کند. یک تنظیم حداقلی می‌سازیم تا این سه رفتار را در محیط جدا ببینیم.

We have files, but no server is answering yet. root tells Nginx which directory to join with a URI; index says which filename to try for a directory request; and try_files determines when to end with 404. We will define a minimal isolated config to observe all three.

سه ردیف سه درخواست جدا هستند: فایل موجود با الحاق URI به root پیدا می‌شود؛ درخواست پوشه به index می‌رسد؛ و برای فایل ناموجود، try_files به 404 ختم می‌شود. فلش‌ها مسیر نگاشت و ادامهٔ پردازش را نشان می‌دهند.

The three rows are independent requests: an existing file is found by appending its URI to root; a directory request reaches index; and a missing file ends at 404 through try_files. Arrows show path mapping and request handling.

فایل config را داخل پوشهٔ آزمایش می‌گذاریم. چون مسیر root نسبی است، prefixای که با -p می‌دهیم پایهٔ مسیر آن خواهد بود. بلوک types این آزمایش، MIMEهای لازم را روشن تعریف می‌کند تا پاسخ JavaScript و JSON به‌اشتباه application/octet-stream نباشد.

We place the config inside the lab directory. Because root is relative, the prefix passed with -p is its base path. The small types block explicitly defines the MIME types needed here, so JavaScript and JSON are not accidentally served as application/octet-stream.

an isolated static server
cat > "$LAB_DIR/nginx.conf" <<'NGINX'
worker_processes 1;
pid logs/nginx.pid;
error_log logs/error.log notice;

events { worker_connections 64; }

http {
    types {
        text/html html;
        text/css css;
        application/javascript js;
        application/json json;
        text/plain txt;
    }
    default_type application/octet-stream;

    server {
        listen 127.0.0.1:18082;
        server_name _;
        root site;
        index index.html;

        location / {
            try_files $uri $uri/ =404;
        }
    }
}

مرورگر لازم نیست هر بار همان فایل را دوباره بگیردA browser need not download the same file every time

الان Nginx می‌فرستد Last-Modified و ETag، اما هنوز نگفته پاسخ تا چه زمانی تازه می‌ماند. این شناسه‌ها جای کش را نمی‌گیرند؛ وقتی نسخهٔ ذخیره‌شده نیاز به بررسی دارد، کمک می‌کنند کلاینت بپرسد «همان فایل قبلی است؟»

Nginx currently sends Last-Modified and ETag, but has not said how long the response stays fresh. These validators are not cache lifetimes. When a stored response needs checking, they let a client ask, “Is this still the same version?”

درخواست اول بدنه و validatorها را می‌گیرد. بعد از کهنه‌شدن پاسخ، درخواست شرطی می‌فرستد: اگر نسخه عوض نشده باشد 304 می‌آید و همان بدنهٔ ذخیره‌شده مصرف می‌شود؛ اگر عوض شده باشد 200 و بدنهٔ تازه می‌آید. validator خودش نمی‌گوید پاسخ تا چه زمانی تازه است.

The first request receives the body and validators. After the response becomes stale, a conditional request asks whether the version changed. If it did not, 304 lets the client reuse its stored body; if it did, 200 carries the new body. A validator does not determine how long a response stays fresh.

برای آزمایش، ETag همان پاسخ را از هدر curl -I کپی کن و در درخواست شرطی بفرست. مقدار نمونهٔ زیر ساختگی است؛ در اجرای خودت باید عین مقدار را جایگزین کنی. اگر فایل از زمان پاسخ اول عوض نشده باشد، انتظار داریم status برابر 304 باشد و بدنه‌ای برنگردد.

کد 304 می‌گوید شرط با نسخهٔ موجود در سرور جور بوده؛ مرورگرِ دارای بدنهٔ قبلی لازم نیست فایل را دوباره دانلود کند. این دستور curl به‌تنهایی نشان نمی‌دهد browser cache چگونه یا چه مدت فایل را نگه می‌دارد، و هر cache واسطی هم الزاماً رفتار یکسانی ندارد. اگر 200 گرفتی، ETag را دقیق کپی کن و ببین فایل بین دو درخواست تغییر کرده یا نه.

A 304 means the condition matched the current server version; a browser that already has the body need not download it again. This curl command alone does not show how long a browser keeps a response, and intermediaries need not behave identically. If you receive 200, check that the ETag was copied exactly and that the file did not change between requests.

کش فقط وقتی کمک می‌کند که قراردادش با نوع فایل جور باشدCaching helps only when its policy fits the kind of file

ETag جواب «همان نسخه است؟» بود؛ حالا باید جواب بدهیم کلاینت چه زمانی اجازه دارد دوباره سؤال نکند. این را معمولاً با Cache-Control مشخص می‌کنیم. Expires هم یک تاریخ می‌دهد؛ Nginx می‌تواند با directiveِ expires هر دو هدر را بسازد.

ETag answered “Is this the same version?” Now we must decide when a client may reuse a response without asking again. Cache-Control commonly expresses that policy. Expires provides a date; Nginx’s expires directive can generate both headers.

برای دیدن رابطهٔ این دو، فقط روی JSON آزمایش یک مهلت کوتاه می‌گذاریم. این تنظیم نه cache دیسکی Nginx می‌سازد و نه cache مرورگر را از راه دور پاک می‌کند؛ فقط هدر پاسخ را تغییر می‌دهد. curl -I باید یک تاریخ آینده و max-age=600 نشان بدهد.

To see how they relate, set a short freshness lifetime only for the lab JSON file. This neither creates an Nginx disk cache nor remotely clears a browser cache; it changes response headers. curl -I should show a future date and max-age=600.

If Content-Encoding is absent, check that the response exceeds gzip_min_length, its Content-Type is covered by gzip_types, and the request sent Accept-Encoding: gzip. If the result does not shrink, it may already be compressed or simply be a poor candidate. gzip does not change the source file, and JPEG, video, or ZIP data usually do not benefit like repetitive text.

فشرده‌سازی را کورکورانه روشن نکنDo not enable compression blindly

gzip از CPU استفاده می‌کند و فشرده‌کردن بدنهٔ هر پاسخی هم لازم یا به‌صرفه نیست. مهم‌تر اینکه فشرده‌سازی پاسخ‌های رمزنگاری‌شده‌ای که هم‌زمان راز و متن قابل‌کنترل مهاجم دارند، می‌تواند در شرایط خاص ریسک BREACH بسازد. این فصل فقط فایل‌های استاتیک آزمایش را فشرده می‌کند؛ دربارهٔ پاسخ‌های پویای حساس، با توجه به شرایط واقعی سرویس تصمیم بگیر.

gzip consumes CPU, and not every payload should be compressed. More importantly, compressing encrypted responses that mix secrets with attacker-controlled text can create BREACH risk in some conditions. This chapter compresses only lab static files; make a contextual decision for sensitive dynamic responses.

Brotli را در config جادویی فرض نکنDo not assume Brotli is magically available

شاید روی سرور دیگری directiveای به نام brotli دیده باشی. این به‌تنهایی بخشی از تضمین‌شدهٔ نصب استاندارد Nginx نیست: معمولاً باید ماژول جداگانه‌ای را نصب یا با نسخهٔ سازگار build و load کرد. فایل configای که روی یک سرور می‌پذیرد، ممکن است روی دیگری با «unknown directive» از کار بیفتد.

You may have seen a brotli directive on another server. That does not make it a guaranteed part of a standard Nginx installation: commonly, a separate module must be installed or built compatibly and loaded. A config accepted on one server may fail elsewhere with “unknown directive.”

ماژول شناخته‌شدهٔ ngx_brotli برای پاسخ پویا directiveهایی مثل brotli on و brotli_types دارد و برای فایل ازپیش‌فشرده‌شده هم قابلیت جدا دارد. اما module باید با build همان Nginx سازگار باشد؛ دستورهایش را فقط بعد از بررسی بسته، فایل load_module و nginx -t وارد کن. برای آزمایش اصلی این فصل، gzip کافی است و نبود Brotli هیچ قدمی را متوقف نمی‌کند.

The well-known ngx_brotli module provides directives such as brotli on and brotli_types for on-the-fly responses, plus a separate option for precompressed files. The module must be compatible with that Nginx build; only add its directives after checking the package, its load_module entry, and nginx -t. gzip is enough for our main lab, so missing Brotli blocks nothing.

یک تفاوت تعیین‌کنندهOne important distinction

قابلیت Brotli و gzip می‌تواند پاسخ را هنگام درخواست فشرده کند یا نسخهٔ ازپیش‌فشرده‌شده را بفرستد؛ این دو مسیر تنظیم و پیش‌نیاز یکسانی ندارند. روشن‌بودن مرورگرِ پشتیبان هم کافی نیست؛ Nginx باید encoding را واقعاً در پاسخ اعلام کند و cacheها variant را درست نگه دارند.

Brotli and gzip can compress a response on demand or serve a precompressed file; these paths have different requirements and configuration. A browser supporting an encoding is not enough: Nginx must actually declare it in the response, and caches must keep the variants straight.

A passing report proves three things separately: stable-URL HTML should not be declared fresh for a year without cause; a fingerprinted asset can have a long lifetime because a new deployment gets another URL; and the old file should remain available through the compatibility window. gzip is proven only when you observe Content-Encoding: gzip, Vary: Accept-Encoding, and a smaller raw response body. curl does not prove browser-cache behavior; report that observation from DevTools.

Before closing the terminal, save the headers and size comparison in your short report. Then stop the process for this config, confirm its PID file is gone, and verify that the directory is exactly the temporary lab. Remove the directory only after the process exits.

cleanup_lab() {
  if [[ ! "$LAB_DIR" =~ ^/tmp/nginx-static\.[A-Za-z0-9]{6}$ ]] ||
     [ -L "$LAB_DIR" ] || [ ! -f "$LAB_DIR/nginx.conf" ] ||
     [ ! -d "$LAB_DIR/site" ]; then
    echo "Unexpected lab path or contents; nothing removed: $LAB_DIR"
    return 1
  fi

  nginx -s quit -p "$LAB_DIR/" -c nginx.conf || {
    echo 'Nginx did not confirm shutdown; nothing removed.'
    return 1
  }
  for i in {1..20}; do
    [ ! -e "$LAB_DIR/logs/nginx.pid" ] && break
    sleep 0.25
  done
  if [ -e "$LAB_DIR/logs/nginx.pid" ]; then
    echo 'PID file remains; inspect the process and retry later.'
    return 1
  fi

  printf 'Verified cleanup target: %s\n' "$LAB_DIR"
  rm -r -- "$LAB_DIR"
}

# Run only after saving the lab evidence:
cleanup_lab
