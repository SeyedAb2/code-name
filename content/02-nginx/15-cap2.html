پروژهٔ ۲ — پروکسی جلوی یک اپ

Project 2 — proxying an app

در پروژهٔ قبل Nginx فایل می‌داد؛ این‌بار بین کاربر و یک برنامهٔ زنده می‌ایستد. باید بدون عمومی‌کردن پورت برنامه، HTTPS را تا لبه ببری، هویت درخواست را درست منتقل کنی، WebSocket را سالم نگه داری و آپلود را با حد مشخص عبور بدهی. تحویل نهایی فقط «صفحه باز شد» نیست؛ باید مسیر خطا هم قابل توضیح باشد.

In the previous project Nginx served files; this time it stands between users and a live application. Without exposing the app port, you will terminate HTTPS at the edge, forward request identity correctly, keep WebSocket working, and allow bounded uploads. Delivery is more than “the page opens”; failure paths must also be explainable.

مأموریت: اپ را پشت لبهٔ HTTPS بگذارMission: put the app behind an HTTPS edge

این‌بار اگر فقط صفحهٔ اصلی باز شود هنوز چیزی تمام نشده. برنامه چهار رفتار دارد—HTTP عادی، نمایش هدر، WebSocket و upload—و هرکدام باید از همان دامنهٔ HTTPS درست عبور کند. پورت برنامه برای کاربر بسته می‌ماند و Nginx تنها در ورودی عمومی می‌ایستد.

This time a working home page is not enough. The application has four behaviors—ordinary HTTP, header inspection, WebSocket, and upload—and each must work through the same HTTPS domain. The application port remains private, with Nginx as the only public entry point.

پروژهٔ قبل دامنه، گواهی و سایت استاتیک را آماده کرد. این‌بار certificate همان دامنه را reuse می‌کنی و فقط مسیر HTTPS را تا برنامه ادامه می‌دهی. پروژهٔ بعد چند سرویس را به یک gateway وصل می‌کند؛ فعلاً یک Nginx و یک برنامه داریم.

The previous project established the domain, certificate, and static site. Reuse that certificate and extend the HTTPS path to an application. The next project builds a multi-service gateway; for now there is one Nginx and one app.

فلش‌های افقی مسیر درخواست‌اند؛ فلش‌های پایین فقط محل جمع‌شدن لاگ را نشان می‌دهند، نه مسیر ترافیک. برنامه روی loopback است و پورتش public نمی‌شود.

Horizontal arrows are request flow; lower arrows mark log destinations, not traffic paths. The app binds to loopback and its port is not public.

معماری پروژه را عمداً کوچک نگه می‌داریم: Nginx و Node روی یک میزبان. این باعث می‌شود loopback یک مرز روشن باشد. اگر بعداً برنامه را به container یا ماشین دیگری ببری، همین فرض عوض می‌شود؛ آن را بی‌سر و صدا داخل این پروژه قاطی نکن.

The architecture is intentionally small: Nginx and Node on one host, making loopback a clear boundary. If the app later moves to a container or another machine, that assumption changes; do not silently mix that architecture into this project.

نقطهٔ ۱: رفتار اپ را مستقل از Nginx ثابت کنCheckpoint 1: prove the app works independently

starter را روی محیط کاری اجرا کن. endpoint اصلی و /whoami باید پاسخ بدهند، /upload تعداد byte را بشمارد، و /ws پیام را echo کند. از اول روی پورت public آزمایش نکن؛ اول مطمئن شو خود برنامه سالم است.

Run the starter in your work environment. The home and /whoami endpoints respond, /upload counts bytes, and /ws echoes messages. Do not start by testing the public port; first prove the app itself works.

در این نسخه، برنامه عمداً هدرهای ارسالی را فقط نمایش می‌دهد و از آن‌ها برای احراز هویت یا مجوز استفاده نمی‌کند. یک برنامهٔ frameworkدار باید پروکسی‌های مورداعتمادش را دقیق تنظیم کند؛ هر کلاینت می‌تواند هدر جعلی بفرستد.

This starter deliberately displays forwarded headers but does not use them for identity/authorization. A framework app must configure trusted proxies precisely; any client can send forged forwarding headers.

direct baseline before the edge
curl -i http://127.0.0.1:3000/
curl -s http://127.0.0.1:3000/whoami
ss -lntp | grep ':3000' || true
HTTP/1.1 200 OK
{"host":"127.0.0.1:3000","forwardedFor":null,"forwardedProto":null}
LISTEN ... 127.0.0.1:3000 ... node

مدرک مهم در ss، address برابر 127.0.0.1 است، نه 0.0.0.0. این فقط همین میزبان را نشان می‌دهد؛ پس از نصب سرویس روی VPS دوباره بررسی کن. WebSocket را با console مرورگر آزمایش کن: new WebSocket("ws://127.0.0.1:3000/ws") و پیام ping بفرست.

The key evidence in ss is address 127.0.0.1, not 0.0.0.0. This proves only this host; check again after installing the service on the VPS. Test WebSocket in the browser console with new WebSocket("ws://127.0.0.1:3000/ws") and send a ping message.

نقطهٔ ۲: سرویس را به Nginx وابسته و عمومی نکنCheckpoint 2: keep the app private and manageable

روی سرور یک کاربر systemd کم‌دسترسی برای اپ بساز و service را با restart-on-failure اجرا کن. آدرس node را از command -v node بگیر؛ مسیر binary در نصب‌های مختلف یکی نیست.

Create a low-privilege system user and run the app under a systemd unit with restart-on-failure. Get Node’s executable path from command -v node; installs may differ.

inspect the managed unit and its listening address
sudo systemctl daemon-reload
sudo systemctl enable --now codenames-app
sudo systemctl status codenames-app --no-pager
sudo journalctl -u codenames-app -n 30 --no-pager
ss -lntp | grep ':3000' || true

systemd وضعیت فرایند و خروجی stdout/stderr اپ را می‌دهد؛ Nginx هنوز در این مرحله نقشی ندارد. اگر port عمومی گوش می‌دهد، bind address را اصلاح کن یا فایروال را بررسی کن؛ فقط بستن فایروال کافی نیست اگر سرویس ناخواسته روی همهٔ interfaceها bind شده.

systemd reports process state and the app’s stdout/stderr; Nginx is not involved yet. If the port is publicly listening, fix the bind address or inspect the firewall. A firewall alone is not enough if the service is unintentionally bound to every interface.

نقطهٔ ۳: HTTPS و هدرهای مسیر واقعیCheckpoint 3: HTTPS and forwarding headers

وقتی proxy راه افتاد، فقط 200 را نبین. endpoint هدرها باید نشان بدهد برنامه Host، scheme و IP موردانتظار را چگونه می‌بیند. این checkpoint جایی است که قرارداد میان Nginx و برنامه را قابل مشاهده می‌کنی.

When the proxy starts working, do not stop at a 200. The header endpoint should reveal how the app sees Host, scheme, and client IP. This checkpoint makes the contract between Nginx and the application visible.

پیش از اتصال درست، یک بار upstream را عمداً به پورت ۳۰۰۱ ببر. درخواست همان URL را بزن و status را تنها تفسیر نکن؛ لاگ خطا باید مقصد را نام ببرد و direct curl/ss باید نشان دهند برنامه روی ۳۰۰۰ سالم است.

Before wiring it correctly, deliberately point the upstream at port 3001. Request the same URL, but do not interpret status alone: the error log should name the target, while direct curl/ss show the app is healthy on 3000.

fault drill: wrong port, then correlate error log and listener
curl -i https://example.org/whoami
sudo tail -n 20 /var/log/nginx/codenames.error.log
ss -lntp | grep -E ':(3000|3001)\\b' || true
curl -i http://127.0.0.1:3000/whoami
# Nginx error: connection refused to 127.0.0.1:3001
# app listener and direct request are healthy on 127.0.0.1:3000

وقتی شواهد هم‌خوان شد، مقصد را به ۳۰۰۰ برگردان، پیکربندی test و reload کن و همان درخواست proxied را تکرار کن. پاسخ direct به‌تنهایی proxy را ثابت نمی‌کرد؛ آزمون دوم می‌کند.

Once evidence agrees, restore port 3000, test/reload, and repeat the proxied request. The direct response alone did not prove the proxy; the second test does.

same endpoint, different network boundary
curl -s http://127.0.0.1:3000/whoami
curl -s https://example.org/whoami
curl -sSI http://example.org/
# direct: forwardedFor/Proto are absent
# via HTTPS: X-Forwarded-For contains the client path,
# X-Forwarded-Proto is https, Host is the public hostname
# HTTP request: 301 Location: https://example.org/

این نتیجه ثابت می‌کند همین vhost هدرها را فرستاده، نه اینکه اپ مجاز است به هر هدر ورودی اعتماد کند. برای یک proxy عمومی، $proxy_add_x_forwarded_for مقدار کلاینت-supplied قبلی را نگه می‌دارد و IP دیده‌شده را اضافه می‌کند؛ اپ باید فقط پروکسی‌های شناخته‌شده را trusted بداند و زنجیره را از سمت درست بخواند.

This proves this vhost forwarded the headers; it does not mean the app can trust arbitrary incoming values. On a public proxy, $proxy_add_x_forwarded_for preserves any client-supplied prefix and appends the observed address. The app must trust only known proxies and parse the chain from the correct side.

نقطهٔ ۴: WebSocket باید واقعاً ۱۰۱ شودCheckpoint 4: the WebSocket handshake must really reach 101

WebSocket باید با 101 شروع شود و بعد واقعاً پیام رفت‌وبرگشت کند. فقط دیدن صفحهٔ چت یا یک اتصال TCP کافی نیست. اگر 101 نداریم، اول handshake را درست می‌کنیم؛ اگر 101 داریم ولی بعد می‌افتد، تازه سراغ timeout و رفتار برنامه می‌رویم.

WebSocket must begin with 101 and then actually exchange messages. Seeing the chat page or an open TCP connection is not enough. Without 101, fix the handshake first; if 101 succeeds and the connection later drops, then investigate timeouts and application behavior.

diagnose the failed handshake before changing the location
curl -i https://example.org/ws
sudo tail -n 30 /var/log/nginx/codenames.access.log
sudo journalctl -u codenames-app --since '5 minutes ago' --no-pager
HTTP/1.1 426 Upgrade Required
...
# browser WebSocket panel has no successful 101 handshake

پاسخ ۴۲۶ یا درخواست معمولی به /ws یعنی handshake تبدیل نشده؛ آن را با ۵۰۲ اشتباه نگیر، چون اتصال عادی Nginx به برنامه می‌تواند سالم باشد. بعد map را در context سطح http تعریف و هدرهای لازم را در location /ws اضافه کن؛ proxy HTTP/1.1 را صریح بنویس تا نسخه‌های قدیمی‌تر هم درست کار کنند.

A 426 or ordinary HTTP request to /ws means the handshake did not upgrade; do not confuse it with 502 because ordinary Nginx-to-app connectivity may be healthy. Then define the map in http context and add upgrade headers in /ws; state HTTP/1.1 explicitly for older Nginx versions.

نسخه‌های فعلی Nginx از 1.29.7 به بعد HTTP/1.1 را به‌طور پیش‌فرض برای proxy دارند؛ نسخه‌های قدیمی‌تر پیش‌فرض متفاوتی دارند. در این مأموریت همچنان directive را صریح می‌گذاریم. پس از اصلاح، در DevTools باید ۱۰۱ و پیام echo ببینی؛ آزمون کنسول را با wss://example.org/ws انجام بده.

Nginx 1.29.7 and later default proxying to HTTP/1.1; older versions differ. This project sets the directive explicitly anyway. After repair, DevTools should show 101 and an echo; test from the browser console using wss://example.org/ws.

نقطهٔ ۵: آپلود محدود، نه نامحدودCheckpoint 5: bounded, not unlimited, uploads

آپلود را عمداً دو بار امتحان کن: یک فایل زیر سقف و یک فایل بالای سقف. برای هرکدام فقط status ثبت نکن؛ ببین برنامه درخواست را دیده یا Nginx پیش از آن متوقفش کرده. همین تفاوت نشان می‌دهد limit در کدام لایه عمل کرده.

Test uploads deliberately in two cases: one file below the limit and one above it. Do not record only the status; determine whether the application saw the request or Nginx stopped it first. That difference proves which layer enforced the limit.

generate one bounded test file and collect response/log evidence
head -c 1572864 /dev/zero > /tmp/codenames-upload.bin
wc -c /tmp/codenames-upload.bin
curl -i -F "file=@/tmp/codenames-upload.bin" https://example.org/upload
sudo tail -n 20 /var/log/nginx/codenames.error.log
sudo journalctl -u codenames-app --since '5 minutes ago' --no-pager

Nginx limit را فقط در location آپلود کمی بالاتر از محدودیت اپ بگذار، مثلاً ۳ MiB در لبه و ۲ MiB در برنامه. این دو لایه عمداً یکسان نیستند: proxy می‌تواند سرریزهای واضح را زود رد کند و برنامه هنوز حد خودش را نگه دارد. فایل ۱٫۵ MiB را دوباره بفرست؛ پاسخ باید تعداد byte را تأیید کند.

Raise Nginx’s limit only for the upload location and slightly above the app’s own cap—for example 3 MiB at the edge and 2 MiB in the app. The limits intentionally differ: the proxy can reject obvious excess early while the app retains its own bound. Retry the 1.5 MiB file; the response should confirm received bytes.

برای این endpoint، تعداد byte را ثبت می‌کنیم و فایل را ذخیره نمی‌کنیم. اگر محصول واقعی فایل را نگه می‌دارد، مسیر، quota، backup و پاک‌سازی جزو طراحی جدا هستند؛ این تمرین آن‌ها را پیاده‌سازی نمی‌کند.

This endpoint counts bytes without persisting the file. A real upload product needs separate design for storage paths, quotas, backups, and cleanup; this exercise does not implement those.

نقطهٔ ۶: timeout، لاگ و بازیابی سرویسCheckpoint 6: timeouts, logs, and service recovery

حالا یک خرابی upstream بساز. برنامه را متوقف کن و پاسخ، لاگ خطا و status سرویس را کنار هم ببین. بعد برنامه را برگردان و بدون تغییر اضافه همان درخواست را تکرار کن. هدف این checkpoint ساختن حافظهٔ عضلانی برای 502 است.

Now create an upstream failure. Stop the app and compare the response, Nginx error log, and service status. Bring the app back and repeat the same request without unrelated changes. This checkpoint builds muscle memory for a 502 incident.

correlate one request across two services
curl -i https://example.org/whoami
sudo tail -n 20 /var/log/nginx/codenames.access.log
sudo tail -n 20 /var/log/nginx/codenames.error.log
sudo journalctl -u codenames-app --since '5 minutes ago' --no-pager
sudo systemctl show codenames-app -p NRestarts

سرویس systemd را با unit خودش restart کن و health/درخواست را دوباره بسنج. برای آزمایش کنترل‌شده، فقط همین سرویس آزمایشی را با SIGKILL متوقف کن تا Restart=on-failure را ببینی؛ نام unit و PID را قبل از کار حتماً تأیید کن.

Restart only this systemd unit and retest. For a controlled drill, send SIGKILL only to this disposable service to observe Restart=on-failure; verify the unit and PID before doing so.

controlled restart drill for the named lab service only
sudo systemctl show codenames-app -p MainPID -p NRestarts
sudo systemctl kill --signal=SIGKILL codenames-app
sleep 2
sudo systemctl status codenames-app --no-pager
sudo systemctl show codenames-app -p MainPID -p NRestarts
curl -i http://127.0.0.1:3000/

افزایش NRestarts و پاسخ دوبارهٔ برنامه نشان می‌دهد systemd فرایند را بالا آورده، نه اینکه علت crash را فهمیده باشد. لاگ restart و خطای قبلی را نگه دار؛ restart policy جای diagnosis نیست. اگر property NRestarts روی systemd قدیمی نبود، journal و MainPID را شاهد بگیر.

An increased NRestarts and a responding app show systemd relaunched the process, not that it diagnosed the crash. Keep the restart and prior-error logs; restart policy is not diagnosis. If an older systemd lacks NRestarts, use the journal and MainPID as evidence.

نقطهٔ ۷: آزمون بیرونی و گزارش تحویلCheckpoint 7: external acceptance and handoff

اکنون از یک دستگاه بیرونی آزمون کن؛ درخواست localhost روی خود VPS مسیر واقعی TLS، DNS و فایروال را ثابت نمی‌کند. مرورگر، curl و DevTools باید هرکدام چیزی را ثابت کنند، نه اینکه سه screenshot یکسان بسازند.

Now test from an external device; localhost on the VPS does not prove the real TLS, DNS, and firewall path. Browser, curl, and DevTools should prove different properties rather than create three identical screenshots.

راهنمایی مرحله‌ایProgressive hints

۱. مستقیم کار می‌کند، دامنه ۵۰۲ می‌دهد1. Direct works, domain returns 502

پورت و address واقعی را از پیکربندی فعال بردار؛ ss، direct curl، Nginx لاگ خطا و journal را با همان زمان کنار هم بگذار. restart اولین آزمون نیست.

Read the actual address/port from active config; correlate ss, direct curl, Nginx error log, and journal at the same time. Restart is not the first test.

۲. صفحه باز می‌شود اما WebSocket نه2. Page works, WebSocket does not

در DevTools دنبال ۱۰۱ بگرد. اگر درخواست عادی ۴۲۶ یا ۴۰۴ می‌گیرد، Upgrade به backend نرسیده؛ map را در http context و هدرهای hop-by-hop را در همان location بررسی کن.

Look for 101 in DevTools. If a normal request gets 426/404, Upgrade did not reach the backend; check the map in http context and hop-by-hop headers in that location.

۳. upload بی‌صدا ۴۱۳ می‌شود3. Upload returns 413

در Nginx لاگ خطا اندازه و location را بررسی کن. اگر برنامه لاگ ورودی ندارد، درخواست احتمالاً در edge رد شده؛ اندازهٔ Nginx را برای همان مسیر بالا ببر و حد برنامه را حفظ کن.

Inspect size/location in the Nginx error log. If the app has no request log, the edge likely rejected it; raise the limit only for that route and keep the app cap.

۴. هدر IP به نظر جعلی است4. The forwarded IP looks forged

کلاینت می‌تواند X-Forwarded-For بفرستد. مسیر trusted proxy و روش انتخاب address را در framework بررسی کن؛ این هدر را تنها مبنای احراز هویت نگذار.

Clients can send X-Forwarded-For. Check trusted-proxy configuration and address selection in the framework; never use this header alone for authentication.

فایل اپلیکیشنApplication file

server.js — small HTTP/WebSocket service; upload is counted, not stored
const http = require("node:http");
const { WebSocketServer } = require("ws");
const PORT = Number(process.env.PORT || 3000);
const HOST = "127.0.0.1";

const server = http.createServer((req, res) => {
  const url = new URL(req.url, "http://localhost");
  const send = (code, body, type = "text/plain") => {
    res.writeHead(code, { "content-type": type });
    res.end(body);
    console.log(req.method, url.pathname, code);
  };

  if (req.method === "GET" && url.pathname === "/") {
    return send(200, "CodeNames app", "text/plain");
  }
  if (req.method === "GET" && url.pathname === "/whoami") {
    const data = {
      host: req.headers.host,
      realIp: req.headers["x-real-ip"] || null,
      forwardedFor: req.headers["x-forwarded-for"] || null,
      forwardedProto: req.headers["x-forwarded-proto"] || null
    };
    return send(200, JSON.stringify(data), "application/json");
  }
  if (req.method === "GET" && url.pathname === "/ws") {
    return send(426, "WebSocket upgrade required");
  }
  if (req.method === "POST" && url.pathname === "/upload") {
    let bytes = 0;
    let tooLarge = false;
    req.on("data", chunk => {
      bytes += chunk.length;
      if (!tooLarge && bytes > 2 * 1024 * 1024) {
        tooLarge = true;
        console.log(req.method, url.pathname, 413, bytes);
        res.writeHead(413, { "content-type": "text/plain" });
        res.end("application upload limit exceeded");
      }
    });
    req.on("end", () => {
      if (!tooLarge) send(200, "received " + bytes + " bytes");
    });
    return;
  }
  return send(404, "not found");
});

const wss = new WebSocketServer({ noServer: true });
server.on("upgrade", (req, socket, head) => {
  if (req.url !== "/ws") return socket.destroy();
  wss.handleUpgrade(req, socket, head, ws => {
    ws.on("message", data => ws.send("echo: " + data.toString()));
  });
});
server.listen(PORT, HOST, () => console.log("listening on " + HOST + ":" + PORT));

در برنامه واقعی، بدنه-size limit و rate/resource limits هم باید با نیاز محصول هماهنگ باشند؛ این starter برای upload فقط شمارنده است. نصب dependency را در working directory ثبت و lockfile را همراه نسخه‌بندی نگه دار.

A real app also needs product-appropriate body/resource limits. This starter only counts upload bytes. Install dependencies in the working directory and version the lockfile.

map و server blockMap and server block

فایل map را در جایی include کن که زیر block سراسری http خوانده شود، نه داخل server block. locationها تکرار هدرهای موردنیاز را دارند چون تعریف هدرهای proxy در location فرزند، وراثت دستورهای سطح بالاتر را قطع می‌کند.

Include the map file under the global http block, not inside a server block. Locations repeat required proxy headers because child-level proxy header directives stop inheritance from higher contexts.

for example, /etc/nginx/conf.d/00-websocket-map.conf
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

زمان ۷۵ ثانیه برای WebSocket یعنی فاصلهٔ بی‌داده بین readها، نه سقف عمر کل اتصال؛ اگر برنامه heartbeat می‌فرستد، آن را با timeout هماهنگ کن. این نمونه timeout را بی‌نهایت نمی‌کند.

The 75-second WebSocket timeout is an idle gap between reads, not a maximum connection lifetime. Coordinate it with application heartbeats; this example does not wait forever.

برای rollback، پیکربندی فعال را از نسخهٔ شناخته‌شده برگردان، nginx -t را اجرا کن و فقط پس از موفقیت reload کن؛ سپس همان curl، handshake و upload را دوباره آزمایش کن. سرویس را restart کردن جای rollback یا تشخیص نیست.

To roll back, restore the known-good active config, run nginx -t, and reload only on success; then repeat the same curl, handshake, and upload tests. Restarting the service is not diagnosis or rollback.

یادداشت مهندسی و تحویلEngineering note and handoff

در تحویل ثبت کن: port عمومی فقط Nginx است؛ برنامه روی loopback می‌شنود؛ هدرها از کجا می‌آیند؛ upload چه سقفی دارد؛ WebSocket چه هدر و timeoutی لازم دارد؛ service چطور restart می‌شود؛ لاگ‌ها کجا هستند؛ و چه چیزهایی عمداً پیاده نشده‌اند. این پروژه ثابت می‌کند یک edge می‌تواند HTTP، WS و بدنه محدود را به یک برنامه برساند؛ ثابت نمی‌کند برنامه برای بار تولید یا ذخیرهٔ فایل پایدار طراحی شده است.

Record that only Nginx is public; the app listens on loopback; where forwarded headers originate; upload cap; WebSocket headers/timeout; service restart behavior; log paths; and what is intentionally absent. This proves one edge can route HTTP, WS, and bounded bodies to one app—not that the app is production-load-ready or stores files persistently.

پروژهٔ بعد: از یک برنامه به gateway کاملNext: from one app to a complete gateway

یک برنامه را از لبه تا backend سالم تحویل دادی. پروژهٔ آخر همین الگو را چندبرابر می‌کند: چند سرویس، چند سیاست و یک gateway که باید هنگام خرابی هم قابل توضیح بماند.

You have delivered one application from edge to backend. The final project multiplies the pattern: several services, several policies, and one gateway that must remain explainable during failure.
