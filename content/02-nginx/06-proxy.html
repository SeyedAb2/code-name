Reverse proxy and headers

برنامه جواب می‌دهد، اما بعد از گذاشتن Nginx جلویش، همهٔ کاربران را با IP خود Nginx می‌بیند؛ بعضی مسیرها هم انگار تکه‌ای از نشانی‌شان گم شده. خود برنامه از پشت پروکسی چه چیزی را هنوز می‌فهمد، و چه چیزی را باید آگاهانه برایش بفرستیم؟

The application responds, but after Nginx is placed in front, it sees every user as Nginx; some paths also seem to lose part of their URL. What can the application still know behind a proxy, and what must we deliberately forward?

از چشم برنامه، کاربر یک‌دفعه عوض شدFrom the app’s view, the user suddenly changed

تا فصل قبل، Nginx فایل روی دیسک را پیدا می‌کرد و همان را جواب می‌داد. این بار پشت location یک برنامهٔ زنده داریم. کاربر به Nginx وصل می‌شود و Nginx یک اتصال تازه به برنامه باز می‌کند؛ دو اتصال داریم، نه یک اتصال که فقط از یک لوله رد شده باشد.

In the previous chapter, Nginx found a file and returned it. This time, a live application sits behind the location. The client connects to Nginx, and Nginx opens a separate connection to the app: two connections, not one connection passing through a transparent tube.

فلش‌های افقی دو اتصال TCP جدا را نشان می‌دهند. برنامه در اتصال دوم، همتای TCP خود را Nginx می‌بیند؛ headerهای پایین راهی‌اند که Nginx می‌تواند بخشی از زمینهٔ درخواست اول را منتقل کند. این headerها به‌خودی‌خود مدرک هویت نیستند؛ فرستنده‌شان باید قابل‌اعتماد باشد.

The horizontal arrows are two separate TCP connections. On the second connection, the app’s TCP peer is Nginx; the lower headers are a way for Nginx to forward selected context from the first request. These headers are not identity proof by themselves—the sender must be trusted.

پیش‌بینی کن: اگر برنامه IP اتصال را log کند، بعد از پروکسی چه می‌نویسد؟ برای اینکه حدس نزنیم، یک برنامهٔ بازتاب‌دهندهٔ کوچک می‌سازیم. این برنامه فقط path، چند header و آدرس TCP peer را پس می‌دهد؛ اطلاعاتی که می‌فرستیم عمداً ساختگی است و نباید هیچ راز واقعی‌ای در درخواست بگذاریم.

Predict what the app will log as the connection address after proxying. To replace guessing with evidence, we will run a tiny echo app. It returns only the path, selected headers, and TCP peer address; all values we send are intentionally fake, and no real secret belongs in these requests.

یک برنامهٔ کوچک که حرف‌های رسیده را پس می‌دهدA tiny app that repeats what arrived

آزمایش در یک پوشهٔ موقت و روی loopback می‌ماند. برنامه روی پورت 19090 و Nginx روی 18083 گوش می‌دهد؛ هیچ‌کدام را روی شبکهٔ عمومی باز نمی‌کنیم. اگر این پورت‌ها قبلاً استفاده می‌شوند، همهٔ نمونه‌های همان عدد را با پورت آزاد عوض کن.

The lab stays in a temporary directory and on loopback. The app listens on port 19090 and Nginx on 18083; neither is exposed publicly. If either port is already in use, replace every occurrence of that port with a free one.

پیش از فرستادن درخواست، مطمئن شو این سه پورت listener دیگری ندارند؛ این‌طوری آزمایش ناخواسته به سرویس دیگری وصل نمی‌شود. در Linux/WSL از ss و در macOS معمولاً از lsof کمک بگیر. اگر پورت اشغال است، آن را در تمام دستورها و config یکسان عوض کن.

Before sending requests, check that no other listener owns these three ports, so the lab cannot accidentally talk to another service. Use ss on Linux/WSL or usually lsof on macOS. If a port is occupied, change it consistently in every command and config.

check before using loopback ports
if command -v ss >/dev/null; then
  ss -ltn | grep -E ':(18083|19090|19091)([[:space:]]|$)' || true
elif command -v lsof >/dev/null; then
  lsof -nP -iTCP:18083 -iTCP:19090 -iTCP:19091 -sTCP:LISTEN
else
  echo 'Check ports 18083, 19090, and 19091 with your OS network tool.'
fi

اگر خروجی شامل هرکدام از این پورت‌ها بود، آن پورت را برای آزمایش انتخاب نکن. خالی‌بودن خروجی فقط می‌گوید در لحظهٔ بررسی listener دیده نشده؛ پیش از start دوباره خطا را جدی بگیر و اگر سرویس دیگری بالا آمد، به آن درخواست نفرست.

If output lists any of these ports, do not use that port for the lab. Empty output means only that no listener was visible at check time; if startup later reveals a conflict, do not send requests to the other service.

اول برنامه را می‌سازیم. چرا؟ چون قبل از دیدن پیکربندی پروکسی باید بدانیم خود مقصد چه چیزی دریافت و ثبت می‌کند. پاسخ JSON شامل مسیر، Host، سه header انتقالی و آدرس peer است؛ خود برنامه هم هر درخواست را در stdout می‌نویسد و سرور HTTP روش و مسیر را در stderr ثبت می‌کند.

First we create the app. Why? Before studying proxy configuration, we need to know what the destination receives and records. Its JSON response contains the path, Host, three forwarding headers, and the peer address; the app writes each request to stdout, while the HTTP server records the method and path to stderr.

create an isolated Bash lab and echo app
LAB_DIR=$(mktemp -d /tmp/nginx-proxy.XXXXXX)
printf 'Lab directory: %s\n' "$LAB_DIR"
mkdir -p "$LAB_DIR/logs"

cat > "$LAB_DIR/echo.py" <<'PY'
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
import json

class Echo(BaseHTTPRequestHandler):
    def do_GET(self):
        data = {
            "path": self.path,
            "host": self.headers.get("Host"),
            "x_real_ip": self.headers.get("X-Real-IP"),
            "x_forwarded_for": self.headers.get("X-Forwarded-For"),
            "x_forwarded_proto": self.headers.get("X-Forwarded-Proto"),
            "tcp_peer": self.client_address[0],
        }
        print(json.dumps(data), flush=True)
        body = (json.dumps(data, indent=2) + "\n").encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

ThreadingHTTPServer(("127.0.0.1", 19090), Echo).serve_forever()

This app has no framework or external dependency; it exists to expose the network boundary, not to serve production traffic. Each request is returned as JSON and written to stdout; the standard HTTP server also logs requests to stderr. Start it in the background and send one direct request. In the response, tcp_peer is the address on this connection—not a claim about a user’s public IP.

در اجرای loopback، peer برابر 127.0.0.1 است. اگر روی میزبان دیگری اجرا کنی، مقدار فرق می‌کند؛ خود مدل فرق نمی‌کند: برنامه فقط peer اتصال مستقیم خودش را می‌شناسد. هنوز دربارهٔ مسیر، headerها یا رفتار Nginx چیزی ثابت نکرده‌ایم.

On loopback, the peer is 127.0.0.1. On another host, the value differs; the model does not: the app knows only the peer of its own direct connection. We have not yet established anything about Nginx, forwarded headers, or proxied paths.

Nginx وصل می‌شود؛ چه چیزهایی را با خودش می‌برد؟Nginx connects—but what context does it carry?

حالا Nginx را با یک location ساده جلو برنامه می‌گذاریم. هنوز header سفارشی نمی‌فرستیم؛ خروجی همین حالت پایه نشان می‌دهد چه چیزی به‌طور پیش‌فرض می‌رسد و چه چیزی را باید خودمان تنظیم کنیم.

Now place Nginx in front of the app with one simple location. We will not add custom headers yet; the baseline response will show what arrives by default and what we must configure ourselves.

baseline reverse-proxy configuration
cat > "$LAB_DIR/nginx.conf" <<'NGINX'
worker_processes 1;
pid logs/nginx.pid;
error_log logs/error.log notice;
events { worker_connections 64; }

http {
    access_log logs/access.log;
    server {
        listen 127.0.0.1:18083;
        server_name _;

        location /api/ {
            proxy_connect_timeout 2s;
            proxy_send_timeout 10s;
            proxy_read_timeout 30s;
            proxy_pass http://127.0.0.1:19090;
        }
    }
}

دو خط را کنار هم بخوان: host حالا آدرس upstream است، نه shop.example.test که کاربر فرستاد؛ و headerهای IP و scheme خالی‌اند. tcp_peer هم peer اتصال تازهٔ Nginx به برنامه را نشان می‌دهد. در loopback هر دو peer ممکن است یک عدد دیده شوند، اما از نظر معماری همچنان دو اتصال جدا داریم. خود Nginx headerهای درخواست ورودی را عموماً عبور می‌دهد، ولی headerهای انتقالی استاندارد را خودش از هیچ نمی‌سازد.

Read the fields side by side: host is now the upstream address, not the client’s shop.example.test; the IP and scheme headers are absent. tcp_peer is the peer of Nginx’s new connection to the app. On loopback both peers may display the same number, but architecturally they remain separate connections. Nginx generally passes incoming request headers, but it does not invent the forwarding headers for you.

پروکسی آدرس شبکه را جعل نمی‌کندA proxy does not fake the network peer

بعد از proxying، برنامه آدرس اتصال TCP خودش را می‌بیند: آدرس Nginx یا واسطه‌ای که مستقیم به آن وصل شده. اگر می‌خواهیم context درخواست قبلی را به برنامه بدهیم، باید در HTTP header بفرستیم؛ header جای TCP را نمی‌گیرد و برعکس.

After proxying, the app sees the TCP peer of its own connection: Nginx or whichever intermediary connected directly to it. To pass context from the earlier request, we must send HTTP headers; a header does not replace the TCP connection address, nor vice versa.

Host، IP و scheme را با قصد روشن بفرستForward Host, address, and scheme deliberately

کاربر به https://shop.example.test وصل شده، اما برنامه شاید فقط upstream را ببیند و فکر کند درخواست HTTP بوده. این سه پرسش را جدا نگه داریم: کدام نام میزبان درخواست شده؟ اتصال قبلی از کدام peer آمده؟ و کاربر از HTTP آمده یا HTTPS؟

A user reached https://shop.example.test, but the app may see only the upstream and assume the request used HTTP. Keep three questions separate: which host was requested, which peer opened the previous connection, and did the client use HTTP or HTTPS?

هر ردیف یک نگاشت پیکربندی‌شده است، نه چیزی که پروتکل خودکار تضمین کند. به‌ویژه آدرس داخل X-Forwarded-For فقط وقتی قابل‌اتکاست که زنجیرهٔ proxyها و برنامه بدانند کدام hop مجاز به نوشتن آن است.

Each row is a configured mapping, not something the protocol automatically guarantees. In particular, an address in X-Forwarded-For is usable only when the proxy chain and app agree on which hops are allowed to write it.

در این آزمایش، Nginx مستقیم لبهٔ ورودی است؛ پس برای نشانی کلاینت مقدار $remote_addr را می‌فرستیم و header جعلی ورودی را جایگزین می‌کنیم. $host نام درخواست را می‌دهد؛ $scheme پروتکلی را که خود Nginx در این hop دیده گزارش می‌کند؛ و X-Real-IP یک مقدار تکی است.

In this lab, Nginx is the directly exposed edge, so we send $remote_addr as the client address and replace any client-supplied spoofed value. $host supplies the request host; $scheme reports the protocol Nginx saw on this hop; and X-Real-IP is a single value.

add explicit request context at the proxy edge
# add these lines inside location /api/ in nginx.conf
proxy_set_header Host              $host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;

nginx -t -p "$LAB_DIR/" -c nginx.conf && \
  nginx -s reload -p "$LAB_DIR/" -c nginx.conf
curl -sS -H 'Host: shop.example.test' \
  -H 'X-Forwarded-For: 198.51.100.77' \
  http://127.0.0.1:18083/api/orders?day=1

اگر کاربر خودش X-Forwarded-For: 198.51.100.77 بفرستد، config لبه آن مقدار را با $remote_addr عوض می‌کند. پاسخ مورد انتظار در loopback، Host: shop.example.test، headerهای تنظیم‌شده برای همین hop و tcp_peer: 127.0.0.1 است؛ X-Forwarded-Proto هم http خواهد بود.

If a client supplies X-Forwarded-For: 198.51.100.77, the edge config replaces it with $remote_addr. On loopback, expect Host: shop.example.test, the headers set for this hop, and tcp_peer: 127.0.0.1; X-Forwarded-Proto will be http.

برای درخواست همین‌جا از http://127.0.0.1:18083/... استفاده کن؛ در خروجی x_forwarded_proto باید http باشد. این مقدار ثابت نمی‌کند TLS در Nginx فعال است. اگر TLS در load balancer دیگری تمام شود، $scheme اینجا ممکن است همچنان http باشد و باید فقط از همان واسطهٔ مورداعتماد، scheme اصلی را بگیری.

For this lab request, use http://127.0.0.1:18083/...; x_forwarded_proto should be http. That does not prove TLS is enabled in Nginx. If another load balancer terminates TLS, $scheme here may still be http; obtain the original scheme only from that trusted intermediary.

یک slash در proxy_pass مسیر را عوض می‌کندOne slash in proxy_pass can change the path

برنامه مسیر /api/orders را انتظار دارد، ولی گاهی در log فقط /orders می‌بیند. پیش از دست‌کاری routing برنامه، خود proxy_pass را بخوان: آیا URL آن فقط upstream را دارد یا URI جایگزین هم مشخص کرده؟

The app expects /api/orders, but its log sometimes shows only /orders. Before changing application routing, inspect proxy_pass: does its URL contain only the upstream, or also a replacement URI?

در هر دو ردیف درخواست یکسان است. وقتی proxy_pass URI ندارد، مسیر اصلی به upstream می‌رود؛ وقتی / دارد، بخش منطبق با /api/ با همان URI جایگزین می‌شود. این قاعده را برای locationهای prefix معمولی می‌خوانیم؛ regex و rewrite حالت‌های ویژه دارند.

Both rows start with the same request. Without a URI in proxy_pass, the original path goes upstream; with /, the part matching /api/ is replaced by that URI. This describes ordinary prefix locations; regex locations and rewrites have special cases.

یک تفاوت ظاهراً کوچک را با خروجی خود برنامه می‌سنجیم: خطای نسخهٔ دوم عمداً در انتهای اسلش است. query string در مثال نگه داشته می‌شود؛ چیزی که جابه‌جا شده prefix مسیر است. پس قبل از تغییر config، مسیر لازم برنامه را از قرارداد API پیدا کن.

We will verify a deceptively small difference in the app’s own output: the second version deliberately changes the trailing slash. The query string remains in this example; the changed part is the path prefix. Before editing the config, establish the path required by the app’s API contract.

syntax سالم است و Nginx reload شده، پس خطا از parse نیست. مدرک تعیین‌کننده "path": "/orders?day=1" است: برنامه درخواست را گرفته، اما با URI دیگری. این خروجی خطای API واقعی یا منطق برنامه را نمی‌آزماید؛ فقط مسیری را که proxy فرستاده ثابت می‌کند.

The syntax is valid and Nginx reloaded, so this is not a parse failure. The discriminating evidence is "path": "/orders?day=1": the app received a request, but with a different URI. This does not test a real API response or application logic; it proves only the path sent by the proxy.

برای تعمیر، قرارداد را انتخاب کن، نه اسلش را با حدس جابه‌جا کن: اگر برنامه انتظار دارد /api/ حفظ شود، URI را از proxy_pass بردار. بعد همان URL را بفرست؛ باید /api/orders?day=1 برگردد. اگر طراحی API می‌خواهد prefix حذف شود، برنامه باید مسیر کوتاه‌تر را بشناسد؛ proxy قرار نیست قرارداد برنامه را حدس بزند.

Repair according to the contract, not by randomly moving slashes: if the app expects /api/ to remain, remove the URI from proxy_pass. Resend the same URL; it should return /api/orders?day=1. If the API is designed to omit the prefix, the app must recognize the shorter path—the proxy cannot guess the contract.

localhost از کدام محیط؟Which environment does localhost mean?

در این آزمایش Nginx و برنامه روی یک میزبان‌اند، پس 127.0.0.1 مقصد معناداری است. اگر Nginx داخل container باشد و برنامه بیرون آن، یا هرکدام در container جدا باشند، localhost به همان network namespace اشاره می‌کند و ممکن است مقصد اشتباه باشد. آن‌وقت نام سرویس/میزبان و شبکهٔ درست لازم است؛ این همان بحث شبکهٔ Docker است و اینجا وارد جزئیاتش نمی‌شویم.

In this lab, Nginx and the app share a host, so 127.0.0.1 is meaningful. If Nginx runs in a container and the app outside it—or each runs in a separate container—localhost refers to that process’s own network namespace and may be the wrong destination. Then use the correct service/host name and network; Docker networking is outside this chapter.

هر کسی می‌تواند header را بنویسد؛ به کدام فرستنده اعتماد داری؟Anyone can write a header—which sender do you trust?

در آزمایش قبلی عمداً فرستادیم X-Forwarded-For: 198.51.100.77. اگر Nginx آن را بدون بازبینی به برنامه بدهد، برنامه شاید فکر کند این IP واقعی کاربر است. اما کاربر خودش header را نوشته؛ مقدار داخلش فقط متن ورودی است، نه هویت تأییدشده.

In the previous test we deliberately sent X-Forwarded-For: 198.51.100.77. If Nginx passes it through unchecked, the app may mistake it for the user’s real IP. But the client wrote that header; its value is input text, not verified identity.

وقتی Nginx مستقیماً از اینترنت درخواست می‌گیرد، اتصال peer را خودش می‌بیند؛ برای این hop می‌توانیم مقدار ورودی را کنار بگذاریم و $remote_addr را بنویسیم. اما اگر یک load balancer مورداعتماد پیش از Nginx است، $remote_addr آدرس همان load balancer خواهد بود. آن‌وقت زنجیره را فقط بر پایهٔ مستندات همان سرویس و محدوده‌های IP مورداعتماد تفسیر کن.

When Nginx receives traffic directly from the internet, it sees the connection peer; for this hop we can discard the supplied value and write $remote_addr. But if a trusted load balancer sits in front, $remote_addr is that load balancer. Interpret the chain only using that service’s documented behavior and explicitly trusted IP ranges.

direct edge: replace, do not blindly preserve, client input
proxy_set_header X-Forwarded-For $remote_addr;

# Only when a known, trusted proxy already supplied a validated chain:
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

متغیر $proxy_add_x_forwarded_for مقدار header ورودی را نگه می‌دارد و $remote_addr را به انتهای زنجیره اضافه می‌کند. این کار برای زنجیرهٔ proxyهای شناخته‌شده می‌تواند لازم باشد؛ ولی اگر ورودی کلاینت را پاک‌سازی نکرده‌ای، ممکن است مقدار جعلی را هم با خودت عبور بدهی. «header را داریم» با «می‌توانیم برای کنترل دسترسی یا محدودیت درخواست به آن اعتماد کنیم» یکی نیست.

The $proxy_add_x_forwarded_for variable preserves the incoming header and appends $remote_addr. That can be needed across a known proxy chain, but if you have not sanitized client input, you may carry a spoofed value forward. “The header exists” is not the same as “we may trust it for access control or rate limiting.”

Practical consequence: if the app is also reachable from the internet, or anyone can connect directly to the backend, do not use a forwarded header as authentication or authorization. timeout یعنی فاصلهٔ سکوت؛ نه سقف کل زمان پاسخA timeout limits silence—not necessarily total response time

اگر upstream وصل نشود یا بعد از شروع پاسخ ساکت بماند، کاربر منتظر می‌ماند. چند timeout در proxy داریم، اما هرکدام یک فاصلهٔ مشخص را کنترل می‌کنند. بالا بردن همه به یک عدد بزرگ، علت کندی را درمان نمی‌کند.

If the upstream cannot be reached or goes silent after starting a response, the client waits. Proxying has several timeouts, each controlling a particular interval. Raising them all to a large number does not fix the cause of slowness.

پیکان‌های زمانی بازهٔ انتظار بین عملیات را نشان می‌دهند. مخصوصاً proxy_read_timeout برای سکوت بین دو خواندن پیاپی است؛ کل طول عمر پاسخ را سقف‌گذاری نمی‌کند.

The timed arrows represent waiting intervals between operations. In particular, proxy_read_timeout measures silence between successive reads; it does not cap the total lifetime of a response.

در config آزمایش، proxy_connect_timeout 2s برای برقرارشدن اتصال است؛ proxy_send_timeout فاصلهٔ بین دو عملیات نوشتن هنگام فرستادن درخواست به upstream را می‌سنجد؛ و proxy_read_timeout فاصلهٔ بین دو خواندن پاسخ را محدود می‌کند. مقدارها باید با رفتار واقعی برنامه جور باشند. خطای اتصال معمولاً 502 می‌دهد، ولی پایان مهلت انتظار در upstream می‌تواند 504 بدهد؛ برای علت دقیق، error log را کنار پاسخ بخوان.

In our config, proxy_connect_timeout 2s limits establishing the upstream connection; proxy_send_timeout measures the interval between successive write operations while sending the request upstream; and proxy_read_timeout limits the interval between successive response reads. Choose values to fit actual app behavior. A connection failure commonly yields 502, while an upstream wait expiring may yield 504; read the error log alongside the response to identify why.

نشانهٔ مهم این است که خطا «while connecting to upstream» رخ داده: Nginx نتوانسته اتصال دوم را برقرار کند. این مدرک می‌گوید کدام hop شکست خورده، نه اینکه چرا برنامهٔ اصلی پاسخ نداده؛ ممکن است مقصد/پورت اشتباه یا برنامه خاموش باشد. خط را به 19090 برگردان، nginx -t و reload کن و همان URL را دوباره بگیر.

The useful phrase is “while connecting to upstream”: Nginx could not establish the second connection. This identifies the failed hop, not why the intended app was unavailable; the destination/port may be wrong or the app may be stopped. Restore 19090, test and reload, then request the same URL again.

proxy_buffering هم دربارهٔ پاسخ upstream است: به‌طور پیش‌فرض Nginx پاسخ را در buffer می‌خواند و بعد به client می‌فرستد؛ اگر لازم شود ممکن است از فایل موقت هم استفاده کند. خاموش‌کردنش برای streamهایی مثل SSE می‌تواند رفتار ارسال را تغییر دهد، اما تنظیم عمومیِ بهتر نیست. با آن proxy_request_buffering را قاطی نکن؛ آن یکی دربارهٔ بدنهٔ درخواست ورودی است.

proxy_buffering controls the upstream response: by default Nginx reads it into buffers before sending it to the client, and may use a temporary file if needed. Turning it off can change delivery behavior for streams such as SSE, but it is not a universally better setting. Do not confuse it with proxy_request_buffering, which controls the incoming request body.

یک نکتهٔ کوچک برای قدم بعد: اتصال Nginx به upstream هم می‌تواند از اتصال‌های idle دوباره استفاده کند. دستور keepalive در گروه upstream اتصال‌های بیکارِ قابل‌استفاده را نگه می‌دارد؛ سقف تعداد کل اتصال‌ها نیست. چون این فصل یک مقصد مستقیم دارد، config کاملش را به فصل بعد و بحث گروه مقصدها می‌سپاریم.

One small preview for what comes next: Nginx can reuse idle connections to an upstream. The keepalive directive in an upstream group retains reusable idle connections; it is not a cap on the total connection count. This chapter has one direct destination, so we will leave the complete configuration for the next chapter on upstream groups.

تمرین ۱۱ · 504 یا پاسخ آهسته؟Exercise 11 · 504 or a slow response?

یک stream هر ۲۰ ثانیه داده می‌فرستد و proxy_read_timeout روی ۳۰ ثانیه است. آیا بعد از ۳۰ ثانیه حتماً قطع می‌شود؟ دلیل را بگو.

A stream sends data every 20 seconds and proxy_read_timeout is 30 seconds. Must it be cut off after 30 seconds? Explain.

پاسخ را ببینShow solution

نه لزوماً؛ این timeout فاصلهٔ بین دو read پیاپی را می‌سنجد، نه کل عمر stream. اگر upstream در هر فاصله داده بفرستد ممکن است stream طولانی‌تر بماند. بااین‌حال buffering و کلاینت هم بر تجربه اثر دارند؛ زمان کل را از این directive تنها نتیجه نگیر.

Not necessarily; it measures the interval between successive reads, not the stream’s total lifetime. If the upstream sends data within each interval, the stream may continue longer. Buffering and the client also affect the experience, so this directive alone does not establish total duration.

تمرین ۱۲ · X-Forwarded-Proto اشتباهExercise 12 · Wrong X-Forwarded-Proto

کاربر HTTPS می‌بیند، ولی برنامه redirect به http:// می‌سازد. TLS کجا تمام می‌شود و چه headerی را باید با چه منبعی بررسی کنی؟

The user uses HTTPS, but the app redirects to http://. Where might TLS terminate, and which header should you inspect—and trust from whom?

پاسخ را ببینShow solution

ممکن است TLS در load balancer تمام شود و Nginx/برنامه HTTP ببینند. مقدار X-Forwarded-Proto را در پاسخ echo و config مسیر بررسی می‌کنم؛ فقط اگر load balancer مورداعتماد آن را مستند و درست تنظیم کرده، برنامه باید آن را بپذیرد. کاربر می‌تواند header خودش را جعل کند.

TLS may terminate at a load balancer while Nginx and the app see HTTP. Inspect X-Forwarded-Proto in the echo response and the config along that path; the app should accept it only from a trusted, documented load balancer. A client can forge its own header.

تمرین ۱۳ · buffering و SSEExercise 13 · Buffering and SSE

SSE از برنامه می‌رسد اما کاربر پیام‌ها را یک‌جا و با تأخیر می‌بیند. آیا خاموش‌کردن proxy_buffering قدم معقولی است؟ چه چیزی را باید اندازه بگیری؟

SSE events arrive from the app, but the client sees them in a delayed batch. Is disabling proxy_buffering a reasonable test? What should you measure?

پاسخ را ببینShow solution

به‌عنوان آزمایش محدود، بله؛ ولی اول زمان ارسال app، headerها و رفتار خود client را ثبت می‌کنم و بعد فقط buffering همان location را تغییر می‌دهم. اگر پیام‌ها زودتر رسیدند، این تغییر علت را محدود می‌کند نه اینکه همهٔ پاسخ‌ها باید بدون buffer باشند. درخواست بزرگ و پاسخ بزرگ buffering جداگانه دارند.

As a scoped experiment, yes; first record app send times, headers, and client behavior, then change buffering only for that location. If events arrive sooner, the test narrows the cause; it does not mean every response should be unbuffered. Large request bodies involve separate request buffering.

تمرین ۱۴ · برنامه direct هم در دسترس استExercise 14 · The app is also directly reachable

Backend یک port عمومی دارد و برنامه بر اساس اولین IP در X-Forwarded-For دسترسی می‌دهد. چه تغییری در معماری و برنامه لازم است؟

The backend has a public port, and the app grants access based on the first XFF address. What should change in the architecture and app?

پاسخ را ببینShow solution

port backend را از اینترنت ببند و فقط از proxy مجاز دسترس‌پذیر کن. بعد برنامه باید اعتماد به proxy را محدود کند و بخش قابل‌اعتماد زنجیره را بر اساس توپولوژی واقعی بخواند. headerی که اتصال مستقیم عمومی دارد، مبنای کنترل دسترسی نیست؛ فقط تعویض کد بدون بستن مسیر مستقیم کافی نیست.

Remove public access to the backend and allow only the authorized proxy. Then limit the app’s trust to that proxy and select the trustworthy chain portion according to the real topology. A header on a publicly reachable direct connection is not an access-control basis; changing code without closing that path is insufficient.

تمرین ۱۵ · localhost اشتباهExercise 15 · The wrong localhost

کانفیگ Nginx داخل container است، ولی proxy_pass http://127.0.0.1:19090 به برنامه‌ای روی host اشاره می‌کند. چرا ممکن است اتصال رد شود؟

Nginx is inside a container, but proxy_pass http://127.0.0.1:19090 is intended to reach an app on the host. Why might the connection be refused?

پاسخ را ببینShow solution

127.0.0.1 داخل container به همان container اشاره می‌کند، نه host. مقصد و شبکهٔ واقعی را از محیط اجرا بررسی کن؛ اگر دو container جدا هستند، معمولاً نام سرویس روی شبکهٔ مشترک لازم است. این پاسخ به معنی این نیست که آدرس ویژه‌ای در همهٔ محیط‌های Docker یکسان است.

Inside the container, 127.0.0.1 refers to that container, not the host. Inspect the real runtime network and destination; for separate containers, a service name on a shared network is commonly used. This does not mean one special host address works identically in every Docker environment.

تمرین ۱۶ · دو نوع bufferingExercise 16 · Two kinds of buffering

همکار برای کم‌کردن تأخیر پاسخ، proxy_request_buffering off را عوض می‌کند. آیا این directive همان buffering پاسخ upstream است؟

A teammate changes proxy_request_buffering off to reduce response latency. Is this the same as upstream response buffering?

پاسخ را ببینShow solution

proxy_request_buffering دربارهٔ بدنهٔ درخواستی است که client به Nginx می‌فرستد؛ proxy_buffering دربارهٔ پاسخ upstream به client است. اول اندازه بگیر تأخیر کدام جهت دارد و بعد directive همان جهت را بررسی کن.

proxy_request_buffering concerns the body sent from client to Nginx; proxy_buffering concerns the upstream response sent to the client. Measure which direction is delayed, then investigate the matching directive.

تمرین ۱۷ · timeout را بالا ببریم؟Exercise 17 · Should we increase the timeout?

log می‌گوید اتصال به upstream با connection refused رد شده. تنظیم فعلی connect timeout دو ثانیه است. آیا افزایش آن به ۶۰ ثانیه احتمالاً درمان است؟

The log says the upstream connection was rejected with connection refused. The connect timeout is two seconds. Is raising it to 60 seconds likely to fix the issue?

پاسخ را ببینShow solution

نه؛ refusal یعنی مقصد پاسخ رد کرده یا listener در آن نشانی/پورت نیست، نه اینکه فقط دیر پاسخ داده. برنامهٔ فعال، bind address، پورت و شبکه را بررسی کن. timeout مدت انتظار برای اتصال را تنظیم می‌کند، نه اینکه برنامه را روی پورت درست اجرا کند.

No. Refusal means the destination rejected the connection or no listener exists at that address/port; it is not merely slow to respond. Check app state, bind address, port, and network. A timeout sets how long to wait—it does not start the app on the right port.

تمرین ۱۸ · گزارش عیب‌یابیExercise 18 · Debugging report

برنامه redirect اشتباه می‌سازد، logها همه یک IP دارند و /api/orders گاهی 404 است. سه مدرک اولت را طوری انتخاب کن که scheme، peer/header و URI از هم جدا شوند.

The app creates a wrong redirect, all logs show one IP, and /api/orders sometimes returns 404. Choose your first three checks so scheme, peer/header, and URI are investigated separately.

پاسخ را ببینShow solution

برای redirect، مقدار X-Forwarded-Proto در هر hop و محل پایان TLS را ثبت می‌کنم؛ برای IP، TCP peer برنامه را با XFF/X-Real-IP و فهرست proxyهای مورداعتماد مقایسه می‌کنم؛ برای 404، path رسیده به echo یا log upstream و خط proxy_pass را می‌سنجم. هر سه را در یک تغییر جمع نمی‌کنم؛ یکی را اصلاح و همان درخواست را دوباره آزمایش می‌کنم.

For the redirect, record X-Forwarded-Proto at each hop and where TLS terminates. For the address, compare the app’s TCP peer with XFF/X-Real-IP and the trusted-proxy list. For the 404, inspect the upstream path in echo/logs and the proxy_pass line. Do not bundle all three into one change; fix one and repeat that request.

ماموریت کوتاه: از درخواست تا log برنامه را دنبال کنShort mission: trace one request into the app log

همکارت می‌گوید login بعد از تغییر پروکسی کاربر را به HTTP می‌فرستد، log برنامه IP یکسان دارد و یک API هم 404 می‌دهد. قرار نیست همه‌چیز را یک‌جا تغییر بدهی؛ یک گزارش بساز که سه مرز را جدا ثابت کند.

اگر گیر کردی، سرنخ‌ها را به‌ترتیب باز کنIf stuck, reveal these hints in order
