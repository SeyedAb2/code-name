لاگ و journaldLogs and journald

دیشب سرویس کار می‌کرد، صبح systemctl می‌گه failed. اگه کل journal رو باز کنی با هزاران خط تنها می‌مونی. بهتره سؤال رو برعکس کنیم: خرابی تقریباً چه ساعتی اتفاق افتاده و کدوم unit اون موقع چی گفته؟

The service worked last night. This morning the page is down and systemctl says failed. Someone says the server rebooted; the next person opens the entire journal and faces thousands of lines. Instead of reading everything, let’s narrow the unit and time window, then reconstruct the failure from evidence.

همون سرویس فصل ۳؛ این‌بار تاریخچه‌اش رو بخوانThe Chapter 3 service, now with its history

لاگ وقتی به درد می‌خوره که بتونی بازه و منبعش رو محدود کنی. قرار نیست همه‌چیز رو بخونیم؛ می‌خوایم از بین کلی رویداد، چند خطی رو پیدا کنیم که داستان همین خرابی رو تعریف می‌کنن.

In Chapter 3, we created codenames-demo.service: Python served port 8787 on loopback and systemd sent the process output to the journal. Make a local request to create a fresh event, then inspect the unit. active tells you systemd sees a live process; it does not prove the application response is correct.

local VM — generate and locate one event
curl -i http://127.0.0.1:8787/
systemctl status codenames-demo.service --no-pager
sudo journalctl -u codenames-demo.service -n 12 --no-pager

در status، Active: و PID وضعیت رو می‌گن؛ در journalctl دنبال زمان همون درخواست و خط "GET / HTTP/1.1" 200 بگرد. این ثابت می‌کنه همون unit در اون زمان درخواست رو ثبت کرده، نه اینکه از laptop یا اینترنت هم دسترسی برقرار هست.

In status, Active: and the PID describe the current unit state. In journalctl, find the request time and a line like "GET / HTTP/1.1" 200. That proves this unit recorded the request at that time—not that a laptop or the internet can reach it.

رویدادها با اطلاعات مخزن جمع می‌شن؛ journalctl فقط view محدودشده می‌سازه. اگه قبل از ذخیره حذف شدن، فیلتر چیزی برنمی‌گردونه.

Events arrive with metadata; journalctl creates a scoped view. If records were never retained, filtering cannot bring them back.

systemd serviceهای معمول خروجی‌شان رو بی‌نیاز از فایل‌گردانی به journal می‌فرستن. در هر رکورد می‌تونه زمان، priority، PID، boot ID و unit ثبت بشه؛ برای همین می‌تونی به‌جای جست‌وجوی متن در تمام دیسک، با فیلدها جست‌وجو کنی. journal همهٔ logهای برنامه‌ها رو جادویی جمع نمی‌کنه: برنامه‌ای که فقط در فایل خودش می‌نویسه ممکنه در مسیر دیگری باشه.

Ordinary systemd services send their output to the journal without manual file routing. Records can include time, priority, PID, boot ID, and unit, so searches can use fields instead of scanning every file. The journal does not magically collect every application log: a program that writes only to its own file may live elsewhere.

کل journal رو نخوان؛ اول unit رو محدود کنDo not read the whole journal; scope by unit first

برای دیدن همهٔ رخدادها sudo journalctl رو اجرا کن. خروجی ممکنه از چندین unit و boot باشه؛ وسط اون پیدا کردن خط برنامه مثل جست‌وجوی سوزن در انبار هست. این فرمان فقط یک آزمایشِ پرسر‌وصداست: چند خط اول رو ببین و بعد بلافاصله به unit خودمان برگرد.

Run sudo journalctl to see all available entries. The output may span many units and boots; finding one application line is like searching a haystack. Treat this only as a noisy demonstration: inspect a few lines, then return to the unit we care about.

broad view, then a useful filter
sudo journalctl -n 8 --no-pager
sudo journalctl -u codenames-demo.service -n 8 --no-pager

در خروجی دوم نام unit و زمان‌های نزدیک به آزمایش رو می‌بینی. -u نتیجه رو برای unit محدود می‌کنه؛ -n 8 آخرین هشت ورودی رو می‌گیره و --no-pager برای اسکریپت/ترمینال خروجی رو مستقیم نشون می‌ده. این محدودسازی به معنی حذف logهای بقیه نیست—فقط view ما رو کوچک کرده.

The second output shows the unit and timestamps around the experiment. -u scopes entries to a unit; -n 8 takes the latest eight, and --no-pager prints directly for scripts or terminals. This does not delete other logs—it only narrows this view.

برای خطای آغاز systemd، journalctl -u ... و systemctl status رو کنار هم بخوان. اگه unit دیگری رو فیلتر کنی، نبودن نتیجه چیزی دربارهٔ سرویس اصلی نمی‌گه. نام unit رو با systemctl list-units --type=service تأیید کن؛ در توزیع‌ها ممکنه مثلاً ssh.service یا sshd.service باشه.

For a service-start failure, read journalctl -u ... alongside systemctl status. An empty result for the wrong unit says nothing about the service you intended. Confirm names with systemctl list-units --type=service; distributions may call the SSH unit ssh.service or sshd.service.

زمان و boot، محدودهٔ دوم جست‌وجو هستنTime and boot are the second search boundary

می‌دونیم مشکل حدود پنج دقیقهٔ پیش شروع شد. همون unit رو به همون بازه ببند؛ اگه ساعت VM اشتباه باشه، بازه هم اشتباه می‌شه، پس timestamps رو با زمان واقعی VM و منطقهٔ زمانیاش بسنج.

We know the problem began about five minutes ago. Restrict the same unit to that interval. If the VM clock is wrong, the interval will be wrong too, so compare timestamps with the VM’s actual clock and timezone.

one unit, bounded time window
sudo journalctl -u codenames-demo.service --since "10 minutes ago" --until now --no-pager

باید فقط ورودی‌های unit در اون بازه رو ببینی. --since و --until هر دو مرز رو می‌سازن؛ قالب‌های تاریخ دقیق و عبارت‌های نسبی مثل "yesterday" هم بسته به parser پذیرفته می‌شن. اگه خروجی خالی هست، زمان شروع رو گسترش بده یا منطقهٔ زمانی/ساعت رو بررسی کن—خالی بودن یک پرس‌وجو به‌تنهایی ثابت نمی‌کنه event رخ نداده.

You should see only entries for that unit in the interval. --since and --until set both boundaries; exact timestamps and relative expressions such as "yesterday" are also supported. If no lines appear, widen the window or check clock/timezone—an empty query alone does not prove the event never happened.

حالا boot رو جدا کن. journalctl --list-boots نشون می‌ده journal فعلی کدوم bootها رو داره؛ -b یعنی همین boot و -b -1 یعنی boot قبلی که ذخیره‌اش موجود باشه. شناسهٔ boot در هر رکورد کمک می‌کنه logهای دو راه‌اندازی رو اشتباه قاطی نکنی.

Now scope by boot. journalctl --list-boots lists boots represented in the available journal; -b means this boot and -b -1 means the previous boot, if its records were retained. The boot ID on each record prevents mixing events from separate starts.

current and previous boot, if retained
sudo journalctl --list-boots
sudo journalctl -b -u codenames-demo.service -n 12 --no-pager
sudo journalctl -b -1 -u codenames-demo.service -n 12 --no-pager

در --list-boots ستون‌های index و boot ID مرز نسل‌ها رو نشون می‌دن. اگه -1 خطا می‌ده یا چیزی برنمی‌گردونه، هنوز دو احتمال مهم داریم: اصلاً journal قبلی persist نشده، یا بعداً vacuum/پاک‌سازی شده. قبل از نتیجه‌گیری تنظیم storage و دایرکتوری journal رو بررسی کن.

In --list-boots, the index and boot ID identify each boot boundary. If -1 errors or returns nothing, two possibilities remain: the previous journal was not persisted, or it was later vacuumed/deleted. Check storage configuration and the journal directory before concluding.

برای لحظهٔ وقوع گوش کن؛ بعد شدت رو فیلتر کنFollow events live, then filter by severity

اگه خطا رو می‌تونی دوباره بسازی، لازم نیست هر بار پرس‌وجو رو تازه اجرا کنی. -f ورودی‌های جدید رو زنده دنبال می‌کنه. در ترمینال اول این رو باز بگذار و در ترمینال دوم یک curl بزن؛ باید خط GET تازه رو ببینی. -f منتظر رخداد بعدی می‌مونه و با Ctrl+C از دنبال‌کردن بیرون میای.

If you can reproduce the event, you do not need to rerun a query each time. -f follows new entries live. Leave it open in one terminal and make a curl request in another; you should see a new GET line. It waits for future events; use Ctrl+C to stop following.

terminal A follows; terminal B creates the request
sudo journalctl -fu codenames-demo.service

هر journal ورودی priority عددی ۰ تا ۷ داره: emerg, alert, crit, err, warning, notice, info, debug. اگه -p warning بدی، warning و شدت‌های مهم‌تر رو می‌گیری، نه فقط warning. این اشتباه رایج خروجی رو ناگهان شلوغ‌تر می‌کنه؛ برای فقط error و بالاتر -p err انتخاب کن.

Journal priorities run from 0 to 7: emerg, alert, crit, err, warning, notice, info, debug. -p warning includes warnings and more severe levels, not warnings alone. That common misunderstanding can make output noisier; use -p err for errors and more severe entries only.

برای آزمایش، به‌جای دست‌کاری severity سیستم، یک پرس‌وجو محدود بساز. اگه خطای شروع از systemd با priority err ثبت شده، -p err باید اون رو نشان بده؛ خط‌های HTTP عادی معمولاً در سطح پایین‌تری‌اند. priority برای غربال هست، نه حکم قطعی دربارهٔ اهمیت عملیاتی هر پیام.

Test with a scoped query instead of changing system severity. If the manager recorded a start failure at err, -p err should show it; routine HTTP lines are usually less severe. Priority is a filter, not a definitive judgement of an event’s operational importance.

unit + time + warning-or-more-severe
sudo journalctl -u codenames-demo.service --since "10 minutes ago" --priority warning --no-pager

وقتی خط متن کافی نیست، فیلدهای رکورد رو ببینWhen a text line is not enough, inspect record fields

خروجی پیش‌فرض کوتاه و خواناست، اما بعضی وقت‌ها می‌خوای منطقهٔ زمانی و دقت timestamp رو ببینی یا بفهمی پیام از کدوم boot/PID آمده. -o short-iso-precise زمان رو با دقت بیشتر چاپ می‌کنه؛ -o verbose اطلاعات مخزن کامل‌تر رو نشون می‌ده. مقدارهای واقعی بسته به نسخه و ماشین فرق می‌کنن.

The default output is compact and readable, but sometimes you need a timezone-aware, precise timestamp or want to see the boot/PID behind a message. -o short-iso-precise prints a more precise time; -o verbose exposes more metadata. Values vary across systemd versions and machines.

same unit, timestamp precision then metadata
sudo journalctl -u codenames-demo.service -n 3 -o short-iso-precise --no-pager
sudo journalctl -u codenames-demo.service -n 1 -o verbose --no-pager

در verbose به فیلدهایی مثل _SYSTEMD_UNIT, _PID, _BOOT_ID, PRIORITY و MESSAGE نگاه کن. این‌ها کمک می‌کنن منبع و context پیام رو بسنجی؛ PID ممکنه بعد از راه‌اندازی دوباره عوض شده باشه و زمان system clock هم باید درست باشه. دادهٔ structured هست، اما همهٔ برنامه‌ها همهٔ فیلدها رو نمی‌فرستن.

In verbose output, inspect fields such as _SYSTEMD_UNIT, _PID, _BOOT_ID, PRIORITY, and MESSAGE. They help identify source and context; the PID may change after restart and the system clock must be correct. Entries are structured, but not every application supplies every field.

برای ابزار یا pipeline می‌تونی JSON بگیری. json-pretty خواناست؛ json فشرده‌تر هست و فیلدهایی مثل MESSAGE و _SYSTEMD_UNIT رو جدا می‌ده. schema رو دستی با متن معمولی قاطی نکن، و اگه اسکریپت می‌نویسی به کلیدهای غیرضروری یا طول ثابت فرض نبند.

For a tool or pipeline, request JSON. json-pretty is easier to inspect; json is compact and exposes fields such as MESSAGE and _SYSTEMD_UNIT separately. Do not confuse the structure with plain text, and avoid depending on irrelevant fields or fixed output lengths in scripts.

structured output for one recent entry
sudo journalctl -u codenames-demo.service -n 1 -o json-pretty --no-pager
representative fields — values vary
{
  "_SYSTEMD_UNIT" : "codenames-demo.service",
  "_PID" : "1842",
  "_BOOT_ID" : "7e6a…",
  "PRIORITY" : "6",
  "MESSAGE" : "\"GET / HTTP/1.1\" 200 -"
}

اینجا PRIORITY=6 یعنی info و _SYSTEMD_UNIT همون سرویس رو معرفی می‌کنه؛ _BOOT_ID کمک می‌کنه این رویداد رو به boot مشخص وصل کنی. PID و boot ID نمونه‌ان. این رکورد فقط یک پیام رو توصیف می‌کنه، نه همهٔ درخواست‌ها یا health برنامه.

Here, PRIORITY=6 means info and _SYSTEMD_UNIT identifies the service; _BOOT_ID links the event to a boot. The PID and boot ID are illustrative. This record describes one message, not every request or the application’s health.

journal همون فایل‌های متنی قدیمی نیستThe journal is not the same as traditional text logs

ممکنه سال‌ها با /var/log/syslog و فایل‌های داخل /var/log کار کرده باشی. بعضی توزیع‌ها یا packageها با rsyslog پیام‌ها رو از journal به فایل متنی هم می‌فرستن؛ بعضی سیستم‌ها اون فایل رو ندارن یا همهٔ پیام‌ها رو آنجا نمی‌نویسن. نبودن /var/log/syslog ثابت نمی‌کنه logging خاموش هست.

You may be used to /var/log/syslog and files under /var/log. Some distributions or packages use rsyslog to forward journal messages into text files; other systems may not have that file or may not write every message there. Missing /var/log/syslog does not prove logging is disabled.

logrotate فایل‌های متنی رو طبق تنظیم خود می‌چرخونه؛ vacuum کردن journal کار دیگری هست و فایل‌های journal رو مدیریت می‌کنه. اگه برنامه خودش مستقیم در فایل می‌نویسه، journalctl لزوماً اون محتوای اختصاصی رو نمی‌بینه. برای تشخیص مسیر، systemctl status rsyslog, ls -l /var/log و تنظیم logging خود برنامه رو جدا بررسی کن.

logrotate rotates text files according to its configuration; journal vacuuming is different and manages journal files. If an application writes directly to its own file, journalctl will not necessarily contain that content. To identify the path, inspect systemctl status rsyslog, ls -l /var/log, and the application’s logging configuration separately.

از طرف دیگر، journalctl -u codenames-demo.service خروجی‌ای رو می‌بینه که systemd برای اون unit گرفته هست؛ اگه برنامه اون رو به فایل redirect کنه یا در خودش logهای دیگری نگه داره، اون‌ها رو هم جدا پیدا کن. «یک log نیست» مساوی «هیچ logی وجود نداره» نیست.

Conversely, journalctl -u codenames-demo.service shows output systemd collected for that unit. If the application redirects output to a file or maintains its own logs, locate those separately. “Not in one log” does not mean “no logs exist.”

چرا logهای boot قبلی ناپدید شدند؟Why did the previous boot’s logs disappear?

journalctl -b -1 خالی هست. قبل از گفتن «سیستم چیزی ثبت نکرده»، اول storage رو بخوان. با Storage=volatile داده‌ها زیر /run/log/journal در حافظه‌اند و reboot اون‌ها رو از بین می‌بره؛ Storage=persistent ترجیح می‌ده در /var/log/journal بنویسه؛ Storage=auto معمولاً به وجود همون مسیر نگاه می‌کنه. توزیع و تنظیم واقعی تعیین‌کننده‌اند.

journalctl -b -1 is empty. Before concluding the system recorded nothing, inspect storage. Storage=volatile keeps records under /run/log/journal in volatile storage, which disappears on reboot; Storage=persistent prefers /var/log/journal; Storage=auto generally looks for that directory. The actual distribution and configuration matter.

inspect effective configuration and storage
systemd-analyze cat-config systemd/journald.conf
test -d /var/log/journal && echo "persistent directory exists" || echo "no persistent directory"
sudo journalctl --list-boots
sudo journalctl --disk-usage

در تنظیم ادغام‌شده دنبال Storage= بگرد؛ اگه گزینه کامنت هست، مقدار پیش‌فرض/نسخه رو از man page همون ماشین تأیید کن. وجود directory نشانه هست، نه اثبات کامل: ممکنه سیاست دیگری، فضای دیسک، permission یا نگهداری نسخه‌ها روی نتیجه اثر گذاشته باشه. --list-boots نشون می‌ده چه bootهایی واقعاً باقی مانده‌اند.

Look for Storage= in the merged configuration; if it is commented out, confirm the default for that machine’s version in its local manual. The directory’s presence is evidence, not complete proof: other policy, disk space, permissions, or retention may affect the result. --list-boots shows which boots actually remain.

برای journal ماندگار در سیستم آزمایشی که سیاست اون اجازه می‌ده، directory رو بساز و دادهٔ runtime رو flush کن. با این تغییر log می‌تونه reboot رو پشت سر بگذارد؛ از اون به بعد هم باید فضا و نگهداری نسخه‌ها رو زیر نظر داشته باشی. در سرور محیط واقعی، اول سیاست نگهداری و ظرفیت رو با مسئول سیستم هماهنگ کن.

On a lab system whose policy permits persistence, create the directory and flush runtime data. This can let journal records survive a reboot; from then on, storage and retention need attention. On a production server, first align retention and capacity with the system owner.

enable the distro’s auto-persistent path on a lab VM
sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix=/var/log/journal
sudo journalctl --flush
sudo journalctl --disk-usage

--flush از journald می‌خواد logهای runtime رو به storage ماندگار منتقل کنه، اگه تنظیم مؤثر این کار رو اجازه بده. بعد از reboot آزمایشی باید boot قبلی در --list-boots بیاد؛ این فقط نگهداری ورودی‌های journal رو ثابت می‌کنه، نه نسخهٔ پشتیبان مستقل یا نگهداری نسخه‌ها نامحدود رو.

--flush asks journald to move runtime records to persistent storage, if the effective configuration permits it. After a lab reboot, the previous boot should appear in --list-boots; that proves journal retention, not an independent backup or unlimited retention.

دادهٔ لازم رو جمع کن، بعد دربارهٔ vacuum تصمیم بگیرCollect what you need before deciding to vacuum

فضا کم شده؟ اول --disk-usage رو بخوان تا مقدار فعلی journal رو ببینی؛ بعد journalctl --vacuum-size=500M رو فقط اگه سیاست نگهداری و مدرک خرابی اجازه می‌ده اجرا کن. vacuum فایل‌های archived رو حذف می‌کنه؛ فایل فعال ممکنه باقی بمونه، پس عدد نهایی لزوماً دقیقاً 500M نمی‌شه.

Running low on space? First inspect --disk-usage; only then consider journalctl --vacuum-size=500M if retention policy and incident evidence allow it. Vacuum removes archived files; active files may remain, so the final total need not be exactly 500 MB.

پاک‌سازی قبل از جمع‌آوری، مدرک رو می‌سوزاندVacuuming before collection destroys evidence

اگه خرابی در حال بررسی هست، اول بازهٔ مربوط رو ذخیره و دسترسی فایل رو محدود کن. vacuum کردن برگشت‌پذیر نیست و ممکنه boot یا unit موردنیاز رو حذف کنه. دستور زیر نمونهٔ سیاست هست، نه دستور پیش‌فرض هر سرور:

During an incident, first export the relevant window and protect the extract. Vacuuming is not reversible and may remove the boot or unit you still need. The command below illustrates a policy; it is not a default action for every server:

illustration only — deletes archived journal data
sudo journalctl --vacuum-time=7days

--vacuum-time=7days داده‌های archived قدیمی‌تر رو هدف می‌گیره، نه اینکه همهٔ ورودی‌های قدیمی رو به‌شکل تک‌خطی پاک کنه. --vacuum-size و --vacuum-time رو با هم هم می‌شه داد؛ قبلش مطمئن شو خرابی extract ذخیره شده و نگهداری نسخه‌ها مجاز هست. برای پاک‌کردن log برنامه از فایل متنی، این فرمان رو به‌جایش به‌کار نبر—مسیر و ابزار اون ممکنه logrotate باشه.

--vacuum-time=7days targets older archived data; it does not simply erase each old entry independently. --vacuum-size and --vacuum-time can be combined, but first ensure the incident extract is saved and the retention policy permits it. Do not use this command to rotate an application text file—that may be handled by logrotate instead.

لَب خرابی: یک خطای واقعی، یک گزارش کوچکIncident lab: one real failure, one concise report

این تمرین رو روی Ubuntu VM یک‌بارمصرفی انجام بده که فصل ۳ و codenames-demo.service رو داره. از ماشین شخصی/محیط واقعی استفاده نکن. ابتدا unit سالم و endpoint رو ثابت کن؛ بعد نسخهٔ سالم فایل unit رو با نام دقیق پشتیبان بگیر تا بتوانی برگردانی.

Use a disposable Ubuntu VM containing Chapter 3’s codenames-demo.service. Do not run this drill on a personal production server. First prove the unit and endpoint work; then make an exact backup of the known-good unit so it can be restored.

checkpoint 1 — healthy baseline and safe copy
systemctl is-active codenames-demo.service
curl -i http://127.0.0.1:8787/
sudo cp -a /etc/systemd/system/codenames-demo.service /tmp/codenames-demo.service.good

active و پاسخ HTTP 200 خط پایه رو می‌سازن؛ فایل پشتیبان باید دقیقاً همون unit سالم باشه. اگه endpoint جواب نمی‌ده یا unit وجود نداره، آزمایش شکست رو ادامه نده—اول همون فایل/سرویس فصل ۳ رو درست کن.

active and HTTP 200 establish the baseline; the backup must be the known-good unit. If the endpoint fails or the unit is missing, do not continue the fault injection—repair the Chapter 3 setup first.

حالا زمان رو ثبت کن و در فایل unit فقط فایل اجرایی در ExecStart رو عمداً به مسیر غیرواقعی تغییر بده، مثلاً /no-such-codenames-demo. WorkingDirectory, کاربر و Restart رو دست نزن تا یک علت رو جدا کنیم. بعد daemon-reload و start رو اجرا کن؛ خطای systemd باید در journal ثبت بشه و راه‌اندازی دوباره سیاست ممکنه چند بار تلاش کنه.

Record the time, then change only the executable in ExecStart to a deliberately nonexistent path such as /no-such-codenames-demo. Do not change WorkingDirectory, user, or restart policy; isolate one cause. Run daemon-reload and start. The manager should log the execution failure, and the restart policy may retry a few times.

checkpoint 2 — fault injection, disposable VM only
date --iso-8601=seconds
sudoedit /etc/systemd/system/codenames-demo.service
# Set only ExecStart=/no-such-codenames-demo
sudo systemctl daemon-reload
sudo systemctl reset-failed codenames-demo.service
sudo systemctl start codenames-demo.service

اگه systemd فوراً failed نشان داد، عالی؛ اگه راه‌اندازی دوباره attemptها پشت‌سرهم میان، چند ثانیه صبر کن اما بی‌جهت راه‌اندازی دوباره loop رو ادامه نده. حالا از unit، زمان و priority برای جداکردن پیام خطا استفاده کن. -p err خطای systemd رو می‌گیره؛ پیام عادی HTTP ممکنه با اون فیلتر دیده نشه.

If systemd immediately shows failed, good. If restart attempts repeat, wait only briefly—do not let the loop run unnecessarily. Now combine unit, time, and priority to isolate the error. -p err should catch the manager’s execution failure; ordinary HTTP messages may not meet that priority.

checkpoint 3 — extract evidence for the failed start
sudo systemctl status codenames-demo.service --no-pager
sudo journalctl -u codenames-demo.service --since "10 minutes ago" --priority err --no-pager
sudo journalctl -u codenames-demo.service --since "10 minutes ago" -o short-iso-precise --no-pager > ~/codenames-demo-incident.log
sed -n '1,20p' ~/codenames-demo-incident.log

دنبال Failed at step EXEC یا نام فایل اجرایی اشتباه و timestamp متناظر بگرد. خروجی status وضعیت آخر رو خلاصه می‌کنه؛ journal جزئیات تلاش‌ها رو نگه می‌داره. فایل خرابی در home توست؛ قبل از اشتراک‌گذاری اون رو از secret، hostname یا دادهٔ حساس پاک‌سازی کن.

Look for Failed at step EXEC, the wrong executable, and its timestamp. status summarises the latest state; the journal preserves attempt details. The extract is in your home directory; redact secrets, hostnames, or sensitive data before sharing it.

حالا فایل سالم رو برگردان، بعد تنظیمات رو reload کن و همون endpoint رو دوباره بررسی کن. این مرحله مهم‌تر از دیدن خطاست: باید همون سنجش baseline رو بعد از اصلاح تکرار کنی.

Restore the good file, reload the unit definition, and test the same endpoint again. This is more important than merely seeing the error: repeat the original baseline checks after repair.

checkpoint 4 — restore, verify, retain the extract
sudo cp -a /tmp/codenames-demo.service.good /etc/systemd/system/codenames-demo.service
sudo systemctl daemon-reload
sudo systemctl reset-failed codenames-demo.service
sudo systemctl restart codenames-demo.service
systemctl is-active codenames-demo.service
curl -i http://127.0.0.1:8787/

موفقیت یعنی active و دوباره HTTP 200، نه صرفاً «systemctl راه‌اندازی دوباره خطا نداد». فایل extract رو نگه دار تا بتوانی علت و اصلاح رو مستند کنی؛ بعد از پایان VM یک‌بارمصرف رو پاک‌سازی کن، نه مسیرهای عمومی سیستم رو.

Success means active plus HTTP 200 again—not merely that systemctl restart returned without an error. Keep the extract to document diagnosis and repair; clean up the disposable VM after the exercise, not broad system paths.

حالا persistence رو فقط اگه VM واقعاً یک‌بارمصرف هست آزمایش کن. اول journalctl --list-boots و تنظیم مؤثر رو ثبت کن. برای بازتولید حالت موقت، یک drop-in آزمایشی با Storage=volatile بساز، journald رو در همین VM راه‌اندازی دوباره کن، یک marker بی‌حساسیت ثبت و VM رو reboot کن؛ سپس journalctl -b -1 رو امتحان کن. این مرحله عمداً می‌ذاره logهای boot قبلی از دست بروند، پس روی سرور شخصی یا محیط واقعی انجامش نده.

Test persistence only if this really is a disposable VM. First record journalctl --list-boots and effective settings. To reproduce volatile storage, create a lab-only drop-in with Storage=volatile, restart journald on this VM, write a harmless marker, and reboot; then try journalctl -b -1. This step deliberately loses the previous boot’s volatile records, so never do it on a personal or production server.

isolated persistence drill — confirm VM snapshot/console first
sudo install -d -m 0755 /etc/systemd/journald.conf.d
printf '[Journal]\nStorage=volatile\n' | sudo tee /etc/systemd/journald.conf.d/99-codenames-lab.conf
sudo systemctl restart systemd-journald
logger -t codenames-lab 'marker before volatile reboot'
sudo reboot

بعد از بالا آمدن VM، --list-boots ممکنه فقط boot فعلی رو داشته باشه و -b -1 marker رو پیدا نکنه؛ این نشون می‌ده storage موقت برای نگهداری میان reboot کافی نیست. فقط نبود marker رو برای نتیجه‌گیری کافی ندان: تنظیمات رو هم ببین. برای پایان تمرین drop-in رو حذف، مسیر persistent رو بساز، --flush کن و تنظیم نهایی رو دوباره بررسی کن.

After the VM returns, --list-boots may show only the current boot and -b -1 may not find the marker; volatile storage did not retain it across reboot. Do not rely on the missing marker alone—inspect configuration too. To finish, remove the lab drop-in, create persistent storage, flush, and verify the resulting settings.

restore persistence on the lab VM
sudo rm /etc/systemd/journald.conf.d/99-codenames-lab.conf
sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix=/var/log/journal
sudo systemctl restart systemd-journald
sudo journalctl --flush
sudo logger -t codenames-lab 'marker after persistent setup'
sudo journalctl --list-boots

برای اثبات واقعی ماندگاری، فقط در همین VM یک reboot دیگر بزن و از کنسول بررسی کن که marker جدید زیر -b -1 پیدا بشه. اگه نشد، Storage=, permissionهای /var/log/journal, systemd-journal-flush.service و فضای فایل‌سیستم رو بررسی کن. این آزمایش نگهداری نسخه‌ها رو ثابت می‌کنه، نه نسخهٔ پشتیبان یا اینکه journal تا ابد نگه داشته می‌شه.

To prove persistence, reboot this VM once more and check from its console that the new marker appears under -b -1. If not, inspect Storage=, /var/log/journal permissions, systemd-journal-flush.service, and filesystem space. This demonstrates retention, not backup or indefinite storage.

تمرین‌ها: log رو پیدا کن، نه اینکه حدس بزنیExercises: find the log; do not guess

۱. سرویس فعال هست1. The service is active

systemctl is-active می‌گه active اما curl پاسخ نمی‌گیره. چه چیزی رو ثابت کرده‌ای و چه چیزی نه؟

systemctl is-active says active, but curl gets no response. What have you proved—and what have you not?

پاسخSolution

فقط systemd وضعیت پردازه رو فعال می‌بینه. endpoint، bind/port و logهای همون unit رو بررسی کن؛ پردازهٔ زنده لزوماً برنامهٔ سالم یا آماده نیست.

Only that systemd sees the process as active. Check the endpoint, bind/port, and this unit’s logs; a live process is not necessarily a healthy or ready application.

۲. خروجی خیلی بلند هست2. The output is too large

همکارت journalctl رو بدون گزینه فرستاده و هزاران خط داره. اولین فیلترهای کم‌خطر تو چیست؟

A teammate sent unscoped journalctl output with thousands of lines. What safe filters come first?

پاسخSolution

unit درست رو با -u, boot رو با -b و زمان رو با --since/--until محدود کن؛ بعد -n یا priority اضافه کن. فیلتر کردن فقط view رو عوض می‌کنه و مدرک حذف‌شده رو برنمی‌گردونه.

Scope by unit with -u, boot with -b, and time with --since/--until; then add a line limit or priority. Filtering changes the view and cannot restore deleted evidence.

۳. کدوم unit رو فیلتر می‌کنی؟3. Which unit should you filter?

سرویس Ubuntu به اسم ssh.service هست ولی پرس‌وجو روی sshd.service خروجی نداره. نتیجه؟

The Ubuntu service is named ssh.service, but a query for sshd.service returns nothing. What follows?

پاسخSolution

فعلاً فقط می‌دونی این نام unit رکوردی نداشته. نام واقعی رو با systemctl list-units --type=service پیدا کن و دوباره پرس‌وجو بزن؛ واحدهای توزیع‌ها نام یکسان ندارن.

You know only that this unit name had no matching records. Find the actual name with systemctl list-units --type=service and query again; distributions do not use identical unit names.

۴. بازهٔ زمانی خالی هست4. The time window is empty

journalctl --since "10 minutes ago" چیزی نشون نمی‌ده، اما خطا رو دیدی. دو بررسی بعدی چیست؟

journalctl --since "10 minutes ago" is empty, but you saw an error. What two checks come next?

پاسخSolution

ساعت/منطقهٔ زمانی ماشین رو با زمان مشاهده مقایسه کن و بازه رو گسترش بده؛ سپس مطمئن شو unit درست رو پرس‌وجو می‌کنی. خروجی خالی به‌تنهایی نبودن رویداد رو ثابت نمی‌کنه.

Compare the machine clock/timezone with your observation and widen the interval; then confirm the unit. An empty result alone does not prove that the event never occurred.

۵. فقط warning یا شدیدتر5. Warnings and more severe

-p warning دقیقاً چه priorityهایی رو نشون می‌ده؟

Which priorities does -p warning include?

پاسخSolution

warning و شدت‌های بالاتر مثل err/crit؛ نه فقط warning. اگه فقط خطاها رو می‌خوای -p err بزن. priority فیلتر هست، نه ارزیابی کامل اثر پیام.

Warnings and more severe levels such as err/crit—not warnings alone. Use -p err for errors only and above. Priority filters records; it does not fully measure operational impact.

۶. سرویس تازه راه افتاده6. The service just started

می‌خوای درخواست بعدی رو همون لحظه ببینی، نه هر بار پرس‌وجو رو تکرار کنی. چه گزینه‌ای لازمه؟

You want to see the next request live instead of rerunning the query. Which option do you need?

پاسخSolution

journalctl -fu codenames-demo.service: -f دنبال ورودی‌های تازه می‌مونه و -u scope رو حفظ می‌کنه. فقط بعد از اینکه برنامه پیامی نوشت چیزی می‌بینی؛ خود گزینه log تولید نمی‌کنه.

Use journalctl -fu codenames-demo.service: -f follows new entries and -u keeps the scope. You see something only after the application emits a message; the option does not generate logs.

۷. این پیام مربوط به کدوم reboot هست؟7. Which reboot produced this message?

چند بار VM reboot شده. چه فیلدی برای جداکردن bootها و چه گزینه‌ای برای فهرست‌کردنشان مفید هست؟

The VM has rebooted several times. Which field separates boots, and which option lists them?

پاسخSolution

_BOOT_ID شناسهٔ boot رو می‌ده؛ journalctl --list-boots bootهای باقی‌مانده و index رو فهرست می‌کنه. اگه storage قبلی persist نشده یا vacuum شده، boot قدیمی از فهرست برنمی‌گرده.

_BOOT_ID identifies a boot; journalctl --list-boots lists retained boots and their indexes. A boot that was not persisted or was vacuumed will not reappear.

۸. «boot قبلی log نداره»8. “The previous boot has no logs”

-b -1 خالی هست. آیا می‌تونی فوراً نتیجه بگیری سرویسی اون موقع اجرا نشده بود؟

-b -1 is empty. Can you conclude that the service was not running then?

پاسخSolution

نه. ممکنه journal موقت بوده و با reboot از دست رفته، log vacuum شده یا boot اصلاً در storage موجود نباشه. --list-boots, storage تنظیمات و مسیر /var/log/journal رو بررسی کن.

No. The journal may have been volatile and lost on reboot, vacuumed, or never retained. Check --list-boots, storage configuration, and /var/log/journal.

۹. timestamp مبهم هست9. The timestamp is ambiguous

لاگ‌ها باید با alert خارجی هم‌بسته بشن اما خروجی time کوتاه منطقهٔ زمانی رو نشون نمی‌ده. کدوم format رو امتحان می‌کنی؟

You need to correlate logs with an external alert, but the short time output lacks timezone context. Which format would you try?

پاسخSolution

-o short-iso-precise یا short-full رو انتخاب کن تا timestamp دقیق‌تر و منطقهٔ زمانی روشن‌تر باشه. ساعت سیستم رو هم مستقل بررسی کن؛ format زمان اشتباه رو درست نمی‌کنه.

Use -o short-iso-precise or short-full for clearer timezone and timestamp precision. Verify the system clock separately; a format cannot correct a wrong clock.

۱۰. متن پیام کافی نیست10. The message text is not enough

دو پردازه پیام مشابهی نوشته‌اند. کدوم اطلاعات مخزن به انتساب درست کمک می‌کنه؟

Two processes emitted similar messages. Which metadata helps attribute the right one?

پاسخSolution

_SYSTEMD_UNIT, _PID, _BOOT_ID, priority و timestamp رو در -o verbose یا JSON ببین. PID ممکنه با راه‌اندازی دوباره عوض بشه؛ یک فیلد رو به‌تنهایی حکم قطعی نگیر.

Inspect _SYSTEMD_UNIT, _PID, _BOOT_ID, priority, and timestamp with verbose or JSON output. A restart may change PID; do not rely on one field alone.

۱۱. اسکریپت باید message رو parse کنه11. A script must parse messages

چرا -o json-pretty از بریدن ستون‌های خروجی متنی بهتره؟

Why is -o json-pretty better than splitting aligned text columns?

پاسخSolution

JSON فیلدهایی مثل MESSAGE, PRIORITY, _SYSTEMD_UNIT رو جدا می‌ده و فاصله/ترتیب نمایشی رو مبنا نمی‌کنی. schema و version رو هم در اسکریپت بررسی کن و به وجود همهٔ فیلدها فرض نبند.

JSON separates fields such as MESSAGE, PRIORITY, and _SYSTEMD_UNIT, so parsing does not depend on display spacing. Still handle schema/version variation and optional fields.

۱۲. journal هست ولی syslog نیست12. The journal exists but syslog does not

/var/log/syslog پیدا نمی‌شه اما journalctl پر از ورودی هست. تناقضی هست؟

/var/log/syslog is missing, but journalctl has entries. Is something inconsistent?

پاسخSolution

نه. ممکنه rsyslog نصب/فعال نباشه یا پیام‌ها به text file forward نشن؛ journal مسیر جداگانه هست. unit rsyslog و تنظیم distribution رو بررسی کن، نه اینکه نبود فایل رو خاموشی logging تعبیر کنی.

No. rsyslog may not be installed/running or messages may not be forwarded to a text file; the journal is a separate path. Check the rsyslog unit and distribution configuration.

۱۳. logrotate چه چیزی رو می‌چرخونه؟13. What does logrotate rotate?

تیم می‌گه «برای کم‌کردن journal، logrotate رو اجرا کن.» دقیقاً کدوم سوءتفاهم رخ داده؟

A teammate says, “Run logrotate to shrink the journal.” What is the misunderstanding?

پاسخSolution

logrotate فایل‌های متنی رو مدیریت می‌کنه؛ journal فایل‌های ساختاریافتهٔ خودش رو داره و vacuum ابزار جداست. اول بفهم کدوم مسیر واقعاً فضا گرفته و قبل از حذف evidence رو جمع کن.

logrotate manages text files; the journal has its own structured files and separate vacuum controls. First identify which path consumes space and preserve evidence before deleting anything.

۱۴. Storage=auto یعنی چه؟14. What does Storage=auto imply?

در تنظیمات گزینه‌ای صریح نیست ولی /var/log/journal وجود داره. چه چیزی رو بررسی می‌کنی و چه چیزی رو هنوز نتیجه نمی‌گیری؟

There is no explicit setting, but /var/log/journal exists. What do you inspect, and what can you not conclude yet?

پاسخSolution

نسخه و تنظیمات ادغام‌شده رو بخوان؛ auto در رفتار پیش‌فرض معمولاً به وجود مسیر persistent تکیه می‌کنه. اما permission، disk space، سیاست و نگهداری نسخه‌ها هم اثر دارن؛ وجود directory به‌تنهایی تضمین ماندگاری نامحدود نیست.

Inspect the version and merged configuration; default auto behaviour generally uses the persistent directory’s presence. Permissions, disk space, policy, and retention still matter, so the directory alone does not guarantee indefinite storage.

۱۵. vacuum دقیقاً چه چیزی حذف می‌کنه؟15. What exactly does vacuum remove?

بعد از --vacuum-size=500M هنوز disk usage بالاتر از 500M هست. آیا حتماً اجرا شکست خورده؟

Disk usage remains above 500 MB after --vacuum-size=500M. Did the command necessarily fail?

پاسخSolution

نه؛ vacuum فایل‌های archived رو حذف می‌کنه و فایل فعال رو نمی‌تونه همون‌طور پاک کنه؛ --disk-usage هر دو رو حساب می‌کنه. خروجی vacuum و فایل‌های باقی‌مانده رو بخوان، اما برای کم‌کردن عدد، بارها کورکورانه حذف نکن.

No. Vacuum removes archived files, not the active file; --disk-usage counts both. Read the vacuum output and remaining files, but do not repeat deletion blindly just to force the displayed number lower.

۱۶. خرابی هنوز باز هست16. The incident is still active

فضای journal زیاد هست و علت outage هنوز معلوم نیست. قبل از vacuum چه کار می‌کنی؟

The journal is large and the outage is still under investigation. What happens before vacuuming?

پاسخSolution

بازهٔ مرتبط رو با unit/time/boot فیلتر و extract محدود رو با مجوز و دسترسی درست ذخیره کن؛ بعد نگهداری نسخه‌ها و disk usage رو بررسی کن. vacuum برگشت نداره و شاید مدرک لازم رو حذف کنه.

Filter the relevant unit/time/boot and save a scoped extract with appropriate permissions; then review retention and disk usage. Vacuum is not reversible and may destroy evidence.

۱۷. دو log از دو مسیر17. Logs come from two paths

journalctl -u پیام start رو نشون می‌ده اما stack trace برنامه در /opt/app/logs/app.log هست. چرا؟

journalctl -u shows the start message, but the application stack trace is in /opt/app/logs/app.log. Why?

پاسخSolution

برنامه بخشی از log رو مستقیم به فایل خودش نوشته؛ systemd خروجی وصل‌شده به journal رو نمی‌تونه حدس بزنه یا اون فایل رو خودکار ingest کنه. سیاست فایل، logrotate و journal رو جدا بررسی کن تا duplicate یا gap رو بفهمی.

The application wrote some messages directly to its own file; systemd cannot infer or automatically ingest that file. Inspect file permissions, logrotate, and the journal separately to identify duplication or gaps.

۱۸. گزارش خرابی رو تحویل بده18. Hand off the incident report

یک unit بعد از reboot fail شده، ساعت VM پنج دقیقه جلو هست و -b -1 خالی هست. ترتیب امن تشخیص و چه چیزی رو صریحاً نمی‌تونی ادعا کنی؟

A unit failed after reboot, the VM clock is five minutes fast, and -b -1 is empty. Give a safe diagnostic order and one claim you cannot make.

پاسخSolution

نام unit و bootهای موجود رو پیدا کن؛ ساعت/منطقهٔ زمانی رو ثبت کن؛ بازه رو با زمان VM تنظیم و log جاری/status رو بخوان؛ storage تنظیمات و journal path رو بررسی کن. بدون رکورد قبلی نمی‌تونی بگویی سرویس قبل از reboot سالم بوده یا اصلاً logش ثبت شده؛ boot قبلی رو هم از هیچ‌جا احیا نکن.

Identify the unit and retained boots; record clock/timezone; query current logs/status using VM time; inspect storage configuration and journal path. Without prior records, you cannot claim the service was healthy before reboot or that it was logged; do not pretend to recover a boot that was never retained.
