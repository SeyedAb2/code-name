کاربر، سرویس، فایروالUser, service, firewall

یک سرویس کوچک قرار است روی VM تیم اجرا شود. کدش آماده است، اما هنوز معلوم نیست با هویت چه کسی اجرا می‌شود، چه فایل‌هایی را می‌تواند بخواند و آیا پورتش واقعاً از شبکهٔ موردنظر باز است یا نه. مأموریتت فقط «بالا آوردن برنامه» نیست؛ باید طوری تحویلش بدهی که یک نفر دیگر بتواند با مدرک بگوید چه چیزی در حال اجراست و از کجا قابل دسترسی است.

A small service is going to run on the team’s VM. Its code is ready, but nobody has established which identity runs it, which files it can read, or whether its port is reachable from the intended network. Your mission is not merely to start the program; hand it over so another person can prove what is running and where it can be reached.

مأموریت: «روی سرور هست» کافی نیستMission: “it’s on the server” is not enough

همکارت می‌گوید سرویس را روی Ubuntu VM گذاشته و پورت ۸۰۸۰ را باز کرده. از لپ‌تاپ تو پاسخی نمی‌آید. یک نگاه به پنجرهٔ ترمینال نشان می‌دهد برنامه قبلاً با کاربر عادی اجرا شده، اما نمی‌دانی بعد از بستن پنجره زنده می‌ماند یا نه. هنوز چیزی را restart نکن؛ اول مرزهای مسئله را ثبت کن.

A teammate says the service is on an Ubuntu VM and port 8080 is open. Your laptop gets no response. A terminal window shows that the program was once started as a regular user, but you do not know whether it survives after that window closes. Do not restart things yet; record the boundaries first.

درخواست از چپ به راست پیش می‌رود؛ عبور از هر مرز را جداگانه ثابت کن. بازبودن پورت، مجوز فایل یا زنده‌بودن process را ثابت نمی‌کند.

The request moves left to right; prove each boundary separately. An open port does not prove file permissions or process health.

این پروژه را فقط روی Ubuntu VM یا ماشین آزمایشیِ خودت اجرا کن؛ نه روی VPS عمومی یا سرویس واقعی. لازم است sudo داشته باشی و یک client جدا از VM برای آزمون شبکه در دسترس باشد. اگر VM پشت NAT است، باید شبکهٔ میزبان یا port forwarding را بشناسی؛ نتیجهٔ curl از خود VM، دسترسی بیرونی را ثابت نمی‌کند.

Use only an Ubuntu VM or your own disposable test machine—not a public VPS or a real service. You need sudo and a client separate from the VM for network tests. If the VM is behind NAT, understand its host network or port forwarding; curl from inside the VM does not prove external reachability.

نقطهٔ ۱ از ۵: صحنه را ثبت کنCheckpoint 1 of 5: record the scene

پیش از ساختن سرویس، ببین پورت ۸۰۸۰ همین حالا دست چه کسی است و firewall چه وضعی دارد. خروجی را نگه دار؛ این «قبل» برای مقایسهٔ بعدی است. اگر پورت اشغال است، process را نکش—یک VM تمیز بساز یا پورت پروژه را با راهنمای پروژه هماهنگ کن.

Before creating the service, find out whether anything already owns port 8080 and inspect the firewall. Keep this output as your “before” snapshot. If the port is occupied, do not kill its process—use a clean VM or coordinate a different project port.

inspect before changing state
hostnamectl
id
sudo ss -lntp
sudo ufw status verbose

در ss دنبال :8080 بگرد. خالی‌بودنش یعنی در همین لحظه listener محلی ندیدی، نه اینکه port forwarding یا firewall بیرونی درست است. اگر UFW فعال است، قانون‌های موجود را نگه دار و تغییرهای پروژه را جدا یادداشت کن.

Look for :8080 in ss. An empty result means you saw no local listener at that moment; it says nothing about port forwarding or an upstream firewall. If UFW is already active, preserve its existing rules and record project changes separately.

مدرک این نقطه: snapshot دستورها، نام VM و تأیید اینکه پورت انتخابی آزاد است. هنوز چیزی را به اینترنت باز نکرده‌ای.

Evidence for this checkpoint: command snapshots, VM identity, and confirmation that the chosen port is free. Nothing has been exposed yet.

نقطهٔ ۲ از ۵: هویت و دسترسی فایلCheckpoint 2 of 5: identity and file access

برنامه فقط چند فایل ثابت را می‌خواند. پس به shell تعاملی، sudo یا نوشتن در فایل‌های سرویس نیاز ندارد. یک کاربر سیستمیِ بدون ورود تعاملی بساز و محتوا را با مالکیت روشن در /srv/codenames-demo/public قرار بده.

The program only reads a few static files. It does not need an interactive shell, sudo, or write access to service files. Create a system account without interactive login and place the content under /srv/codenames-demo/public with explicit ownership.

create the service identity and read-only content
sudo adduser --system --group --no-create-home --shell /usr/sbin/nologin codenames-web
sudo install -d -o root -g codenames-web -m 0750 /srv/codenames-demo
sudo install -d -o root -g codenames-web -m 0750 /srv/codenames-demo/public
printf '%s\n' '<h1>Service is reachable</h1>' | sudo tee /srv/codenames-demo/public/index.html >/dev/null
sudo chown root:codenames-web /srv/codenames-demo/public/index.html
sudo chmod 0640 /srv/codenames-demo/public/index.html
id codenames-web
namei -l /srv/codenames-demo/public/index.html

برای عبور از مسیر، process به مجوز اجرا روی پوشه‌های والد و خواندن فایل نیاز دارد. این‌جا root مالک فایل است و گروه سرویس فقط می‌خواند؛ process نمی‌تواند محتوای منتشرشده را تغییر بدهد. خروجی namei -l را از آخر مسیر به اول بخوان: هر پوشه باید برای user یا group سرویس قابل پیمایش باشد.

The process needs execute permission on parent directories to traverse the path and read permission on the file. Here root owns the file while the service group can only read it; the process cannot modify published content. Read namei -l from the final path component upward: every directory must be traversable by the service user or group.

حالا عمدی خرابش کن: sudo chmod 0600 /srv/codenames-demo/public/index.html. سرویس در نقطهٔ بعد اجرا می‌شود، اما کاربر codenames-web عضو گروه دسترسی نیست و فایل را نمی‌خواند. هنوز مجوز را اصلاح نکن؛ اول خطای درخواست و log را ثبت کن. اگر root هستی، آزمون با root این نقص را پنهان می‌کند.

Now introduce the deliberate fault: sudo chmod 0600 /srv/codenames-demo/public/index.html. The service will start in the next checkpoint, but codenames-web cannot read this file. Do not fix the mode yet; first capture the failed request and logs. Testing as root would hide the problem.

مدرک این نقطه: id، مالکیت/mode از namei -l، و نتیجهٔ آزمون دسترسی با همان هویت:

Evidence: account identity, ownership/modes from namei -l, and an access check under the same identity:

same identity as the service
sudo -u codenames-web test -r /srv/codenames-demo/public/index.html
echo $?

کد خروجی ۱ یعنی آزمون خواندن شکست خورده؛ به‌تنهایی نمی‌گوید کدام جزء مسیر مقصر است. namei -l مرز دقیق را نشان می‌دهد. پس از ثبت failure، mode را به 0640 برگردان و دوباره با همان user آزمایش کن؛ ۷۷۷ لازم نیست.

Exit status 1 means the read test failed; by itself it does not identify which path component is responsible. namei -l helps locate the boundary. After recording the fault, restore mode 0640 and repeat the test as the same user; 777 is unnecessary.

نقطهٔ ۳ از ۵: سرویس را به systemd بسپارCheckpoint 3 of 5: let systemd own the service

برای سرویس کوچک از HTTP server کتابخانهٔ استاندارد Python استفاده می‌کنیم؛ وابستگی تازه یا کد برنامه لازم نیست. پیش از ساخت unit مسیر Python را روی همین VM پیدا کن. دستور service باید در foreground بماند تا systemd همان process را مدیریت کند.

For this small service, use Python’s standard-library HTTP server; no new dependency or application code is needed. Find Python’s path on this VM before writing the unit. The service command must stay in the foreground so systemd can manage that process.

verify the interpreter, then create the unit
command -v python3
sudoedit /etc/systemd/system/codenames-demo.service

محتوای unit را با مسیر واقعی خروجی command -v کامل کن؛ در نمونه فرض شده مسیر /usr/bin/python3 است. اگر توزیعت جای دیگری نصب کرده، همان را بنویس.

Use the actual path returned by command -v; the example assumes /usr/bin/python3. If your distribution installs it elsewhere, use that path.

systemd unit — adapt only the interpreter path
[Unit]
Description=CodeNames disposable demo service
After=network.target

[Service]
Type=simple
User=codenames-web
Group=codenames-web
WorkingDirectory=/srv/codenames-demo
ExecStart=/usr/bin/python3 -m http.server 8080 --directory /srv/codenames-demo/public --bind 0.0.0.0
Restart=on-failure
RestartSec=2
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true

[Install]
WantedBy=multi-user.target

این برنامه فقط فایل می‌خواند، پس ProtectSystem=strict نوشتن در درخت فایل سیستم را برای این سرویس محدود می‌کند؛ PrivateTmp هم فضای موقت جدا می‌دهد. این گزینه‌ها جای permission مالک فایل را نمی‌گیرند و تضمین sandbox کامل نیستند. اگر unit به نوشتن نیاز پیدا کرد، مسیر لازم را آگاهانه با تنظیم مناسب باز کن، نه با برداشتن همهٔ محدودیت‌ها.

This program only reads files, so ProtectSystem=strict restricts writes to the filesystem hierarchy for this service; PrivateTmp provides a separate temporary directory. These settings do not replace file ownership checks or create a complete sandbox. If the unit later needs to write, grant only the required path deliberately rather than removing every restriction.

حالا unit را بارگذاری و اجرا کن. خروجی مهم فقط «active» نیست: در status به User= از unit، PID و exit state نگاه کن و با ps مالک واقعی process را مستقل بررسی کن.

Reload and start the unit. “Active” is not enough: inspect the unit’s User setting, PID, and exit state, then independently check the actual process owner with ps.

load, start, and gather process evidence
sudo systemd-analyze verify /etc/systemd/system/codenames-demo.service
sudo systemctl daemon-reload
sudo systemctl enable --now codenames-demo.service
systemctl status codenames-demo.service --no-pager
ps -o user,group,pid,args -C python3
sudo ss -lntp | grep ':8080'

اگر systemd-analyze verify خطا داد، پیش از start همان را اصلاح کن. در ps باید user اختصاصی را ببینی؛ listener باید روی ۸۰۸۰ باشد. bind به 0.0.0.0 یعنی روی interfaceهای IPv4 گوش می‌دهد، نه اینکه firewall یا مسیر شبکه حتماً اجازهٔ ورود می‌دهد.

If systemd-analyze verify reports an error, fix it before starting. ps should show the dedicated user, and the listener should be on port 8080. Binding to 0.0.0.0 means listening on IPv4 interfaces; it does not mean a firewall or network path permits inbound traffic.

در این لحظه درخواست محلی را بزن. به‌خاطر fault عمدی ممکن است خواندن صفحه fail شود؛ خود listener و سرویس می‌توانند همچنان بالا باشند. همین تفاوت به ما می‌گوید خطا در لایهٔ فایل است، نه الزاماً systemd یا شبکه.

Now make a local request. Because of the deliberate fault, serving the page may fail even while the listener and unit remain up. That distinction points to the file-access layer, not necessarily systemd or the network.

local request and service logs
curl -i --max-time 3 http://127.0.0.1:8080/
sudo journalctl -u codenames-demo.service -n 30 --no-pager
sudo -u codenames-web test -r /srv/codenames-demo/public/index.html

برای Python SimpleHTTPRequestHandler جزئیات پاسخ/لاگ ممکن است بین نسخه‌ها فرق کند؛ معیار ما این است که درخواست با mode 0600 موفق نیست و آزمون همان user هم خواندن را رد می‌کند. حالا مجوز را به 0640 برگردان، درخواست را تکرار کن و متن صفحه را ببین. این بار curl پاسخ محلی را ثابت می‌کند، نه دسترسی client بیرونی را.

Python’s SimpleHTTPRequestHandler response and log details may vary by version; our invariant is that mode 0600 prevents this user from serving the file, and the same-user read test fails. Restore mode 0640, repeat the request, and confirm the page body. This curl proves local service delivery, not reachability from an external client.

repair the narrow cause and verify again
sudo chmod 0640 /srv/codenames-demo/public/index.html
sudo -u codenames-web test -r /srv/codenames-demo/public/index.html
curl -fsS http://127.0.0.1:8080/

سرویس را یک بار از systemd دوباره راه‌اندازی کن و logهای start را ثبت کن. Restart=on-failure فقط برای exit ناموفق process تلاش می‌کند؛ permission خراب را درمان نمی‌کند و قرار نیست با هر تغییر محتوا restart کنی.

Restart the service once through systemd and capture its startup logs. Restart=on-failure retries after an unsuccessful process exit; it does not repair file permissions, and content changes do not require a restart.

restart behavior and recent journal
sudo systemctl restart codenames-demo.service
systemctl is-active codenames-demo.service
sudo journalctl -u codenames-demo.service --since '-5 minutes' --no-pager

مدرک این نقطه: unit سالم، process زیر user اختصاصی، listener محلی ۸۰۸۰، درخواست local موفق پس از اصلاح و journal. هنوز دربارهٔ client بیرونی چیزی ثابت نشده.

Evidence: a valid unit, process under the dedicated user, local listener on 8080, successful local request after repair, and journal entries. External reachability is not yet proven.

نقطهٔ ۴ از ۵: پورت از بیرون؛ fault دومCheckpoint 4 of 5: external port; the second fault

اول ببین درخواست از client جدا، قبل از تغییر firewall، موفق است یا نه. آدرس VM را با ip -br address پیدا کن و از دستگاهی که واقعاً به همان شبکه route دارد بزن:

First test from a separate client before changing the firewall. Find the VM address with ip -br address and request it from a device that is actually routed to that network:

replace with the VM address, from a separate client
curl -v --connect-timeout 3 http://VM_ADDRESS:8080/

اگر جواب می‌گیری، مسیر فعلی باز است؛ firewall را دست‌کاری نکن و مستقیم برو نقطهٔ ۵. اگر timeout/refused است، این نتیجه به‌تنهایی علت را مشخص نمی‌کند: ممکن است UFW، provider firewall، NAT، route یا bind address باشد. روی VM listener را دوباره ببین، بعد قانون‌ها را مقایسه کن.

If it succeeds, the path is already open; do not alter the firewall—continue to checkpoint 5. If it times out or is refused, that alone does not identify the cause: UFW, provider firewall, NAT, routing, or bind address may be involved. Recheck the listener on the VM, then compare firewall rules.

برای ساختن failure کنترل‌شده، تنها روی VM آزمایشی و فقط وقتی دسترسی کنسول داری این دو قانون را اجرا کن: اول قانون اشتباه ۸۰۸۱ را باز کن؛ بعد اگر UFW خاموش است، پورت واقعی SSH را مجاز کن و firewall را فعال کن. هیچ قانون دیگری را پاک نکن.

To create a controlled failure, do this only on the disposable VM and only when you have console access: add a rule for the wrong port, 8081. If UFW is inactive, allow the actual SSH port before enabling the firewall. Do not delete any other rules.

wrong-port drill — only on the disposable VM
sudo ufw allow 8081/tcp
sudo ufw allow OpenSSH
sudo ufw status numbered

اگر SSH روی پورت پیش‌فرض نیست، profile به‌جای آن پورت واقعی خودت را مجاز کن. بعد UFW را فقط اگر خاموش است فعال کن: sudo ufw enable. اکنون ss می‌گوید سرویس روی ۸۰۸۰ گوش می‌دهد، ولی قانون جدید فقط ۸۰۸۱ را مجاز کرده؛ از client بیرونی درخواست ۸۰۸۰ باید fail شود. در VM محلیِ NAT، UFW تنها یکی از چند مرز است.

If SSH is not on its default port, allow its actual port instead of the profile. Then enable UFW with sudo ufw enable only if it is inactive. ss will show the service listening on 8080 while the new rule allows only 8081; an external request to 8080 should fail. On a NATed local VM, UFW is only one of several boundaries.

با sudo ufw status numbered اختلاف شمارهٔ پورت را پیدا کن. قانون اشتباه را با شماره‌اش حذف کن؛ شماره‌ها بعد از حذف ممکن است جابه‌جا شوند، پس پیش از هر حذف دوباره فهرست را بخوان. بعد ۸۰۸۰/TCP را مجاز کن، status را ثبت کن و از client جدا دوباره curl بزن.

Use sudo ufw status numbered to find the port mismatch. Delete the wrong rule by its current number; numbering may shift after deletion, so list rules again before another removal. Then allow TCP 8080, capture status, and retry curl from the separate client.

remove only the drill rule, then allow the actual service port
sudo ufw status numbered
sudo ufw delete RULE_NUMBER
sudo ufw allow 8080/tcp
sudo ufw status verbose

اگر هنوز وصل نمی‌شود، قانون host firewall فقط یکی از شواهد است. مقصد IP، route، port forwarding و firewall ارائه‌دهنده را جدا بررسی کن. موفقیت curl از یک دستگاه همان LAN، دسترسی از اینترنت عمومی را ثابت نمی‌کند؛ محدودهٔ ادعا را دقیق بنویس.

If it still does not connect, the host firewall is only one piece of evidence. Check destination IP, routing, port forwarding, and provider firewall separately. A successful curl from a device on the same LAN does not prove public-internet access; state the scope of your claim precisely.

مدرک این نقطه: listener محلی، قانون UFW برای پورت واقعی و نتیجهٔ درخواست از client جدا. قانون‌ها را با قبل مقایسه کن تا مطمئن شوی چیزی جز مورد تمرین عوض نشده.

Evidence: local listener, UFW rule for the actual port, and a request result from a separate client. Compare rules with the initial snapshot to ensure no unrelated rule changed.

نقطهٔ ۵ از ۵: reboot، تحویل، پاک‌سازیCheckpoint 5 of 5: reboot, handoff, cleanup

تا این‌جا اجرای دستی را به systemd سپردی. اکنون VM آزمایشی را reboot کن—اما فقط پس از اینکه راه برگشت را می‌دانی. پس از اتصال دوباره، سه ادعای جدا را ثابت کن: unit فعال است، process با user درست اجرا می‌شود، client جدا پاسخ می‌گیرد.

You have handed execution to systemd rather than a manual terminal. Reboot the disposable VM—but only after confirming your recovery path. After reconnecting, prove three separate claims: the unit is active, the process runs as the intended user, and a separate client receives a response.

after reboot: repeat the same checks
systemctl is-enabled codenames-demo.service
systemctl is-active codenames-demo.service
ps -o user,group,pid,args -C python3
sudo ss -lntp | grep ':8080'
curl -fsS http://127.0.0.1:8080/
sudo journalctl -u codenames-demo.service -b --no-pager

curl محلی را روی خود VM اجرا کن و آزمون بیرونی را روی client جدا. systemctl is-active زنده‌بودن unit را نشان می‌دهد، نه سالم‌بودن همهٔ درخواست‌ها؛ journalctl -b هم فقط رخدادهای همین boot را نشان می‌دهد. این‌ها را کنار هم تفسیر کن، نه به‌جای هم.

Run local curl on the VM and the external test on the separate client. systemctl is-active reports the unit’s active state, not that every request is healthy; journalctl -b shows events from this boot only. Interpret them together, not as substitutes.

راهنماها؛ فقط اگر گیر کردیHints—only if you get stuck

راهنما ۱: process زنده است ولی صفحه نمی‌آیدHint 1: the process is alive but the page fails

از همان user سرویس بپرس فایل قابل خواندن هست یا نه؛ سپس permission تک‌تک پوشه‌های مسیر را با namei -l بررسی کن. root بودن ترمینال آزمون معتبری برای دسترسی سرویس نیست.

Ask whether the service identity can read the file, then inspect every directory in the path with namei -l. A root shell is not a valid test of service access.

راهنما ۲: local موفق است، client جدا نهHint 2: local works, the separate client does not

ترتیب بررسی: آدرس مقصد و route، bind و listener با ss، host firewall با ufw status numbered، بعد NAT و firewall ارائه‌دهنده. موفقیت local، هیچ‌کدام از مرزهای بیرونی را آزمایش نمی‌کند.

Check destination and route, bind/listener with ss, host firewall with ufw status numbered, then NAT and provider firewall. Local success tests none of those external boundaries.

راهنما ۳: سرویس بعد از logout می‌میردHint 3: the service dies after logout

اگر هنوز در shell اجرا می‌شود، systemd مالک lifecycle آن نیست. unit را verify کن، daemon-reload انجام بده، با systemctl راه‌اندازی کن و status/journal را بخوان؛ صرفاً nohup زدن هدف پروژه نیست.

If it still runs in your shell, systemd does not own its lifecycle. Verify the unit, reload systemd, start it with systemctl, and inspect status/journal; using nohup does not meet the mission.

راه‌حل مرجع: یک runbook کوتاه، نه جادوی حفظیReference solution: a short runbook, not a memorised trick

اگر می‌خواهی اول خودت حل کنی، همین‌جا مکث کن. در این runbook فرمان‌ها بر پایهٔ Ubuntu با UFW، پورت پیش‌فرض SSH و Python در /usr/bin/python3 هستند. پیش از اجرا، پورت SSH و مسیر interpreter را روی ماشین خودت بررسی کن. دستورهای firewall فقط برای VM آزمایشی‌اند.

Pause here if you want to solve it yourself first. This runbook assumes Ubuntu with UFW, the default SSH port, and Python at /usr/bin/python3. Verify the SSH port and interpreter path on your machine. Firewall commands are for the disposable VM only.

نمایش runbook پیشنهادیShow the suggested runbook

۱) قبل از تغییر، ss و UFW را ثبت می‌کنم و مطمئن می‌شوم پورت آزاد است. ۲) account بدون shell می‌سازم؛ parentها را ۰۷۵۰ و فایل را root-owned با group سرویس و mode ۰۶۴۰ می‌گذارم. ۳) fault ۰۶۰۰ را با آزمون همان user و namei تشخیص می‌دهم و فقط همان mode را اصلاح می‌کنم. ۴) unit را با user اختصاصی، فرمان foreground و restart محدود می‌سازم؛ verify، start، status، ps و journal را می‌خوانم. ۵) قانون اشتباه ۸۰۸۱ را با ۸۰۸۰ مقایسه می‌کنم، فقط قانون تمرین را حذف و پورت لازم را باز می‌کنم؛ SSH و بقیهٔ قانون‌ها دست‌نخورده می‌مانند. سرانجام از client جدا و پس از reboot همان آزمون‌ها را تکرار می‌کنم.

1) Before changing state, capture ss and UFW and confirm the port is free. 2) Create a no-login account; use 0750 parent directories and a root-owned file readable by the service group at mode 0640. 3) Diagnose the 0600 fault under the service identity with a read test and namei, then change only that mode. 4) Create a unit with a dedicated user, foreground command, and bounded restart policy; verify, start, and inspect status, ps, and journal. 5) Compare the wrong 8081 rule with 8080, remove only the drill rule, and allow the needed port while preserving SSH and unrelated rules. Finally repeat the tests from a separate client and after reboot.

اگر بیرون VM هنوز fail است، بدون شواهد firewall را خاموش نکن. مقصد، route، port forwarding و provider firewall را بررسی کن. اگر فقط LAN را آزموده‌ای، همان را در تحویل بنویس و ادعای اینترنت عمومی نکن.

If external access still fails, do not disable the firewall without evidence. Check destination, routing, port forwarding, and provider firewall. If you tested only the LAN, say so in the handoff instead of claiming public-internet reachability.

یادداشت تحویل: مسئله را به شاهد وصل کنHandoff note: connect the incident to evidence

در ۵–۸ خط ثبت کن: نشانهٔ اولیه چه بود؛ کدام آزمون ثابت کرد خطای فایل از خطای شبکه جداست؛ fault پورت را با چه اختلافی پیدا کردی؛ کدام تغییر کمینه مشکل را رفع کرد؛ و چه چیزی هنوز خارج از محدودهٔ آزمون است. نتیجهٔ خوب «همه‌چیز درست شد» نیست؛ نتیجه‌ای است که مهندس بعدی بتواند با همان مسیر دوباره بررسی‌اش کند.

In five to eight lines, record the initial symptom, which test separated file access from network reachability, how you found the port mismatch, the smallest change that fixed it, and what remains outside your test scope. A good conclusion is not “everything works”; it is a result the next engineer can verify using the same path.

در پروژهٔ بعد، همین سرویس‌ها را رها می‌کنیم و سراغ کاری می‌رویم که واقعاً باید در زمان مشخص تکرار شود: یک backup زمان‌بندی‌شده که شکستش هم بی‌صدا پنهان نماند. این‌بار واحد تحویل فقط process نیست؛ artifact قابل‌بررسی و سابقهٔ اجرای آن هم هست.
