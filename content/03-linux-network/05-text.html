ابزار متن: grep، awk، sedText tools: grep, awk, sed

سرویس کنه شده و جلوت چند هزار خط لاگه. قرار نیست بشینی از بالا تا پایین بخونیش. سؤال واقعی اینه: چند تا 5xx داشتیم؟ کدوم مسیر بیشتر خطا داده؟ کندترین جواب کدوم بوده؟ اگه سؤال رو خوب خرد کنیم، shell می‌تونه بقیهٔ کار رو برامون انجام بده.

The service is slow again and the log has thousands of lines. The immediate questions: how many 5xx responses occurred, which path failed most, and how long did the slowest response take? You do not need to read every line by hand; you need to turn the question into a few verifiable filters.

یک log کوچک که بتوانیم کامل ببینیمA small log we can inspect completely

برای اینکه وسط هزار خط گم نشیم، اول با یک لاگ کوچیک شروع می‌کنیم که همه‌ش جلوی چشممونه. بعد همون روش رو می‌بریم روی فایل بزرگ. هدف حفظ کردن grep و awk نیست؛ هدف اینه که بتونی از داده یک سؤال دقیق بپرسی.

We begin with a 12-line sample that is small enough to inspect completely. This lesson uses a simple fixed format: time, IP, method, path, status, response bytes, and latency. Real logs may be Nginx, JSON, or application-specific; understand the fields before writing a pipeline.

هر خط از کدوم stream میاد؟Which stream carries each line?

برنامه‌ها معمولاً خروجی معمولی رو روی stdout و خطا/هشدار رو روی stderr می‌نویسن. pipe ساده، stdout دستور چپ رو به stdin دستور راست می‌ده؛ stderr خودش به مسیر جدا می‌ره. این جدایی کمک می‌کنه گزارش رو فیلتر کنی بی‌آنکه خطای خود ابزار گم بشه.

Programs commonly write normal output to stdout and errors/warnings to stderr. A plain pipe sends the left command’s stdout to the right command’s stdin; stderr remains separate. This lets you filter results without losing the tool’s own errors.

پیکان بالایی جریان دادهٔ stdout به pipe و stdin هست؛ پیکان پایینی مسیر جداگانهٔ stderr رو نشون می‌ده. اگه فایلی وجود نداشته باشه، ممکنه awk صفر بشمارد و خطای grep جداگانه روی ترمینال بمونه.

The upper arrows show stdout flowing through a pipe into stdin; the lower route represents separate stderr. If a file is missing, awk may still count zero while grep’s error remains on the terminal.

برای دیدن تفاوت، grep 500 missing.log | wc -l ممکنه عدد صفر چاپ کنه و هم‌زمان پیام خطا روی stderr داشته باشی. صفر، اثبات «هیچ 500 نداریم» نیست؛ ممکنه ورودی خوانده نشده باشه. وجود فایل، exit وضعیت و پیام stderr رو هم بخوان.

To see the distinction, grep 500 missing.log | wc -l may print zero while an error appears on stderr. Zero does not prove “there are no 500s”; the input may not have been read. Check file existence, exit status, and stderr too.

اگه خروجی رو به فایل می‌فرستی، > از نو می‌سازه و قبلی رو overwrite می‌کنه؛ >> append می‌کنه. 2> stderr رو جدا می‌گیره. قبل از redirect مقصد رو ببین؛ یک اشتباه کوچک می‌تونه گزارش قبلی رو پاک کنه.

For output redirection, > creates/truncates a file while >> appends. 2> captures stderr separately. Check the destination before redirecting; a small mistake can erase a previous report.

grep: اول سطرهای نامزد رو پیدا کنgrep: find candidate lines first

برای سؤال «چند وضعیت از خانوادهٔ 5xx داریم؟» لازم نیست از اول awk بنویسی. grep -E سطرهای منطبق با regular expression رو جدا می‌کنه؛ در این قالب وضعیت قبل و بعدش فاصله داره، پس الگوی محدودتری می‌نویسیم.

For “how many 5xx statuses are there?” we do not need to start with awk. grep -E selects lines matching an extended regular expression; because status is space-delimited in this format, use a bounded pattern.

select 5xx, then count
grep -E ' 5[0-9]{2} ' access.log
2026-08-12T09:00:07Z 203.0.113.13 GET /api/items 500 64 1.842
2026-08-12T09:00:08Z 203.0.113.11 GET /api/items 502 64 2.141
...
grep -Ec ' 5[0-9]{2} ' access.log
4

در ERE، [0-9] یک رقم و {2} تکرار دوبارهٔ همون کلاس هست. -c تعداد سطرهای منطبق رو می‌شماره، نه تعداد matchها درون سطر. اگه هر درخواست در چند خط باشه، نتیجه دیگر تعداد درخواست‌ها نیست.

In ERE, [0-9] is one digit and {2} repeats that class twice. -c counts matching lines, not every match within a line. If one request spans multiple lines, this is no longer a request count.

برای عبارت literal مثل /api/items از grep -F استفاده کن؛ برای عبارت منظم از -E. quote دور الگو جلوی تفسیر زودهنگام توسط shell رو می‌گیره. معنا و جزئیات regex بین grepهای مختلف ممکنه فرق کنه؛ در این درس از قابلیت‌های رایج POSIX/GNU استفاده می‌کنیم، نه PCRE.

Use grep -F for a literal string such as /api/items, and -E for an extended regular expression. Quoting prevents the shell from interpreting the pattern first. Regex details vary across grep implementations; this lesson uses common POSIX/GNU features, not PCRE.

لوله رو مرحله‌به‌مرحله بسازBuild the pipeline one step at a time

قبل از ساخت pipeline بلند، یک نمونهٔ کوچک رو نگاه کن. head چند خط اول و tail چند خط آخر رو می‌ده؛ wc -l تعداد خط‌ها رو. این‌ها sanity check هستن: اگه log صفرخطی یا format متفاوت باشه، آمار بعدی رو زودتر زیر سؤال می‌بری.

Before composing a long pipeline, inspect a small sample. head shows the first lines, tail the last, and wc -l counts lines. These are sanity checks: if the log is empty or formatted differently, you can question later statistics early.

check the input before counting
head -n 3 access.log
tail -n 2 access.log
wc -l access.log
12 access.log

حالا تعداد وضعیتهای متفاوت و تعداد هرکدوم رو می‌خوایم. awk فعلاً ستون پنجم رو برمی‌دارد؛ sort سطرهای برابر رو کنار هم میاره؛ uniq -c فقط تکرارهای مجاور رو می‌شماره. اگه sort رو حذف کنی، تکرارهای جدا ممکنه جداگانه شمرده بشن.

Now count each distinct status. awk extracts field five; sort brings equal lines together; uniq -c counts only adjacent duplicates. Without sort, separated occurrences may be counted separately.

status distribution
awk '{print $5}' access.log | sort -n | uniq -c
      5 200
      1 201
      2 404
      3 500
      1 502

قبل از اعتماد به گزارش، جمع خروجی رو با تعداد سطرهای ورودی مقایسه کن: این‌جا ۵+۱+۲+۳+۱ دقیقاً ۱۲ هست. هر عدد رو می‌تونی به ردیف‌های نمونه برگردانی؛ اگه جمع جور درنمی‌آید، اول ورودی و pipeline رو بررسی کن، نه اینکه خروجی رو دستی اصلاح کنی.

Before trusting a report, compare its total with the input line count: here 5+1+2+3+1 is exactly 12. Each count maps back to sample rows; if totals disagree, inspect the input and pipeline rather than editing the displayed result by hand.

verified distribution
awk '{print $5}' access.log | sort -n | uniq -c
      5 200
      1 201
      2 404
      3 500
      1 502

الان تعدادها ۱۲ شد و هر وضعیت رو می‌شه به ردیف‌های نمونه برگرداند. ترتیب sort ممکنه به locale و پیاده‌سازی وابسته باشه؛ برای اعداد، -n رو صریح بگذار. uniq بدون sort فقط اجراهای پشت سر هم رو می‌شماره.

Now the counts total 12 and each status maps back to sample rows. Sort order can depend on locale and implementation; use -n explicitly for numbers. Without sort, uniq counts only consecutive runs.

cut برای delimiter ثابت؛ awk برای منطق فیلدcut for fixed delimiters; awk for field logic

cut وقتی delimiter ثابت هست و فقط یک ستون می‌خوای، ساده و خوب هست. این log با فاصله جدا شده ولی تعداد فاصله‌ها تضمین‌شده نیست؛ پس cut -d' ' -f5 ممکنه فیلد اشتباه بده. awk به‌طور پیش‌فرض چند فاصله/tab رو جداکنندهٔ فیلد می‌گیره و برای شرط و محاسبه هم مناسب هست.

cut is simple and useful when the delimiter is fixed and you need a column. This log is space-separated but spacing is not guaranteed, so cut -d' ' -f5 can select the wrong field. By default, awk treats runs of spaces/tabs as separators and also supports conditions and calculations.

برای فهم رفتار awk، به سؤال مشخص جواب بده: IP درخواست‌هایی که وضعیت اون‌ها 5xx هست چیست؟ شرط روی فیلد پنجم می‌ذاریم و فیلد دوم رو چاپ می‌کنیم.

Use awk to answer a concrete question: which IPs made requests with 5xx status? Filter on field five and print field two.

field selection plus condition
awk '$5 ~ /^5/ {print $2}' access.log
203.0.113.13
203.0.113.11
203.0.113.13
203.0.113.13

در awk، $0 کل رکورد، $1 فیلد اول و NF تعداد فیلدهاست. شرط $5 ~ /^5/ یعنی محتوای فیلد پنجم با 5 شروع بشه. این الگو فقط به قالب نمونه درست هست؛ در JSON یا قالب quoted log شمارهٔ فیلد معنای دیگری داره.

In awk, $0 is the whole record, $1 the first field, and NF the number of fields. $5 ~ /^5/ means field five begins with 5. This is valid only for the sample format; in JSON or quoted logs, whitespace field numbers mean something else.

برای top IP خطادارها، همین نتیجه رو sort و uniq می‌کنیم. اگه فقط uniq بزنی، IPهای تکراری که از میانشان سطر دیگری گذشته جدا می‌مونن. sort -nr عددها رو نزولی مرتب می‌کنه؛ ترتیب تساوی ممکنه به locale وابسته باشه.

To find the most frequent failing IP, sort and count those results. Plain uniq would leave repeated IPs separated by other lines as separate runs. sort -nr sorts numerically in descending order; tie ordering may depend on locale.

top failing IPs
awk '$5 ~ /^5/ {print $2}' access.log | sort | uniq -c | sort -nr
      3 203.0.113.13
      1 203.0.113.11

برای مسیرهای پرتکرار هم فیلد چهارم رو چاپ کن؛ اما برای «پرتکرارترین مسیرِ خطادار» شرط وضعیت رو نگه دار. اگه درخواست پرس‌وجو string داره، مسیر کامل می‌تونه چند variant بسازه؛ گاهی باید اون رو normalize کنی و تعریف دقیق سؤال رو اول روشن کنی.

For most-requested paths, print field four; for “most common failing path,” keep the status predicate too. Query strings can create multiple variants of one endpoint; you may need normalization, but first define exactly what you mean by “same path.”

awk فقط چاپ ستون نیست؛ می‌تونه حساب کنهawk does more than print columns

برای میانگین زمان پاسخ، هر خط یک record هست. awk مقدار هفتم رو به عدد تبدیل و جمع می‌کنه؛ در END میانگین رو چاپ می‌کنیم. این میانگین فقط همین پنجره و همین قالب log رو توصیف می‌کنه؛ tailهای آماری مثل p95 سؤال دیگری‌اند و این pipeline جوابشان نیست.

To calculate average latency, each line is a record. awk converts field seven to a number and sums it, then prints the mean in END. This describes only this sample window and format; tail metrics such as p95 are a different question that this pipeline does not answer.

mean response time
awk '{sum += $7; n++} END {if (n) printf "mean=%.3fs over %d rows\n", sum/n, n}' access.log
 mean=0.670s over 12 rows

عدد چاپی باید از اجرای همین فایل به دست بیاد. اگه قالب خالی، ستون هفتم نامعتبر یا رکورد ناقص باشه، محاسبه باید خط‌مشی مشخص داشته باشه؛ با دادهٔ کثیف میانگین رو بی‌صدا منتشر نکن. می‌تونی قبل از جمع، شرطی مثل NF == 7 اضافه و تعداد رکوردهای پذیرفته/ردشده رو جدا گزارش کنی.

The displayed value should come from running this exact file. If the format is empty, field seven is invalid, or a record is incomplete, the calculation needs an explicit policy; do not silently publish a mean from dirty data. You can require NF == 7 before summing and report accepted/rejected row counts separately.

sed: تبدیل جریان، اول بدون دست‌کاری فایل اصلیsed: transform a stream before editing the source

sed برای انتخاب بازهٔ سطر یا جایگزینی در جریان ورودی خوب هست. مثلاً می‌خوایم پرس‌وجو string رو از گزارش endpoint جدا کنیم؟ بهتره با awk فیلد بسازیم و بعد sed رو برای تبدیل مشخص به کار ببریم. یک جایگزینی ساده: فقط نمایش 5xxها و عوض‌کردن واژهٔ وضعیت با برچسب readable، بدون تغییر access.log.

sed is useful for selecting line ranges or substituting in an input stream. If we need to separate a query string from an endpoint, awk may be better for the fields; use sed for a clearly defined transformation. Here we label 5xx lines without modifying access.log.

transform to a new view
grep -E ' 5[0-9]{2} ' access.log | sed -E 's/ (5[0-9]{2}) / status=\1 /'
... GET /api/items status=500 64 1.842

در s/الگو/جایگزین/ معمولاً اولین match هر سطر عوض می‌شه؛ پسوند g همهٔ matchهای همون سطر رو تغییر می‌ده. sed -n '1,3p' فقط بازه رو چاپ می‌کنه. گزینهٔ in-place بین GNU و BSD تفاوت داره؛ برای گزارش مهم، خروجی رو در فایل جدا بساز و با diff بررسی کن، نه اینکه بی‌پشتیبان فایل اصلی رو بازنویسی کنی.

In s/pattern/replacement/, usually only the first match per line changes; suffix g changes all matches on that line. sed -n '1,3p' prints only a range. In-place options vary between GNU and BSD; for important data, write to a separate file and inspect a diff instead of overwriting the source without a backup.

خرابی عمدی: regex خیلی پهن، عددی که قانع‌کننده هستDeliberate failure: a broad regex and a convincing number

یک نفر برای شمردن خطاها این رو اجرا می‌کنه: grep -c '5.*' access.log. خروجی عدد می‌ده؛ آیا همون تعداد 5xx هست؟ هنوز نه. این pattern می‌تونه هر 5 رو در timestamp، IP، path، وضعیت یا latency پیدا کنه. نتیجه رو با نمونهٔ سطرها و یک pattern محدودتر مقایسه کن.

Someone counts errors with grep -c '5.*' access.log. It returns a number; is that the 5xx count? Not yet. The pattern can match a 5 in the timestamp, IP, path, status, or latency. Compare sample rows with a more constrained pattern.

compare the candidates
grep -n '5.*' access.log | head -n 4
grep -nE ' 5[0-9]{2} ' access.log
grep -Ec ' 5[0-9]{2} ' access.log
5

شمارهٔ سطر و محتوای چند match اول رو نگاه کن؛ «عدد plausible» شاهد کافی نیست. pattern محدودشده هنوز به قالب فاصله‌جدا و وضعیت سه‌رقمی ما وابسته هست. در JSON از parser JSON استفاده کن؛ در log استاندارد وب فیلد وضعیت رو مطابق همون قالب استخراج کن.

Inspect line numbers and the content of several matches; a plausible number is not enough evidence. The constrained pattern still assumes this space-delimited format and three-digit status. Use a JSON parser for JSON; extract status according to the actual web-log format.

یک خرابی دیگر از quote میاد. در Bash اگه برنامهٔ awk رو با double quote بنویسی، shell ممکنه $5 و $2 رو قبل از رسیدن به awk گسترش بده. خطا رو ببین و به‌جای تغییر شرط، اول ببین awk واقعاً چه کدی دریافت کرده هست.

Another failure comes from quoting. In Bash, double-quoting an awk program may expand $5 and $2 before awk receives them. When it fails, inspect what code awk actually got before changing the predicate.

quote for the shell, not for awk
awk "$5 ~ /^5/ {print $2}" access.log
awk: ... syntax error
awk '$5 ~ /^5/ {print $2}' access.log
203.0.113.13

single quote برنامه رو دست‌نخورده به awk می‌رسونه؛ داخل اون، awk خودش معنی $5 و $2 رو می‌فهمه. اگه نیاز داری shell variable رو داخل برنامه بفرستی، از روش صریح و کنترل‌شده مثل awk -v name=\"$name\" '...' استفاده کن؛ quoteها رو حدسی حذف نکن.

Single quotes pass the program intact to awk, which then interprets $5 and $2. If you need a shell variable inside the program, pass it explicitly, for example with awk -v name=\"$name\" '...'; do not remove quotes by guesswork.

locale گاهی ترتیب رو عوض می‌کنهLocale can change ordering

مرتب‌سازی رشته‌ها با sort می‌تونه با locale فرق کنه؛ مقایسهٔ حروف و ترتیب ممکنه روی سیستم‌های متفاوت عوض بشه. برای وضعیت و تعداد، گزینهٔ عددی مثل sort -n بگذار. اگه گزارش قابل تکرار بین سرورها می‌خوای، locale رو آگاهانه تنظیم کن، اما رفتار رو به‌عنوان جزئی از pipeline ثبت کن؛ اون رو جادویی فرض نکن.

String ordering with sort can depend on locale; character comparison and order may differ across systems. Use numeric sorting such as sort -n for statuses and counts. For reproducible reports across hosts, set locale deliberately and document it as part of the pipeline rather than treating it as invisible magic.

برای سؤال درست، ابزار درستChoose the tool for the question

grep سطرهای نامزد رو پیدا می‌کنه؛ awk فیلد و شرط و جمع‌بندی رو می‌فهمه؛ sed جریان رو جایگزین/محدود می‌کنه. pipeline خوب الزاماً بلند نیست؛ هر بخشش باید یک سؤال مشخص رو جواب بده.

grep selects candidate lines; awk handles fields, predicates, and aggregation; sed substitutes or limits a stream. A good pipeline is not necessarily long—each part should answer a specific question.

مأموریت: گزارش شیفت رو آماده کنMission: prepare the shift report

از access.log جواب بده: تعداد کل خط‌ها؛ تعداد 5xx؛ توزیع وضعیتها؛ IP پرتکرار میان خطاهای 5xx؛ مسیر پرتکرار میان همون خطاها؛ و درخواست‌های کندتر از یک ثانیه. گزارش رو در فایل جدا ذخیره کن، نمونهٔ ورودی و خروجی رو کنار هم ببین و تعدادها رو با جمع ردیف‌ها سازگار کن. فایل ورودی رو دست‌کاری نکن.

Answer from access.log: total lines, number of 5xx responses, status distribution, most frequent IP among 5xx requests, most frequent path among those errors, and requests slower than one second. Save the report to a separate file, inspect sample input and output, and reconcile counts. Do not alter the source log.

راهنمای مرحله‌ایProgressive hints

اول head/tail و wc؛ بعد grep محدود برای 5xx؛ سپس awk فیلدها رو چاپ کنه؛ در آخر sort/uniq -c. هر pipeline رو بدون head کردن هم اجرا کن تا مطمئن شوی نمونه‌گیری، نتیجهٔ نهایی رو پنهان نکرده.

Start with head/tail and wc, then a bounded 5xx grep, then awk field extraction, and finally sort/uniq -c. Run each pipeline without head as well so sampling does not hide the final result.

قبل از تحویل گزارش، تعداد 5xx رو با خروجی grep -Ec و تعداد سطرهای فیلترشده با شمارش awk مقایسه کن. اگه فرق داشت، format، quote، stderr و regex رو بررسی کن؛ خروجی رو با اصلاح دستی عددها «درست» نکن.

Before handing off the report, compare grep -Ec with the number of rows selected by awk. If they differ, inspect format, quoting, stderr, and regex; do not “fix” the report by manually changing the number.

تمرین‌ها: pipeline رو قابل توضیح نگه دارExercises: keep each pipeline explainable

۱. چند سطر در فایل؟1. How many lines?

با کدوم ابزار تعداد رکوردهای نمونه رو می‌گیری و چه چیزی رو نمی‌شماره؟

Which tool counts the sample records, and what does it not count?

پاسخSolution

wc -l access.log newlineهای سطر رو می‌شماره، نه لزوماً درخواست‌های منطقی در قالب‌های چندخطی یا فایل ناقص بدون newline آخر.

wc -l access.log counts newline characters/lines, not necessarily logical requests in multiline formats or a final unterminated record.

۲. سه خط آخر2. Last three lines

برای دیدن tail کوتاه log چه می‌زنی؟ چرا خروجی رو نمونه می‌دونی، نه نتیجهٔ آماری؟

How do you inspect a short log tail, and why is it a sample rather than a statistic?

پاسخSolution

tail -n 3 access.log. فقط سه خط پایانی رو نشون می‌ده؛ نمی‌گه خطاهای کل فایل چه توزیعی دارن.

tail -n 3 access.log. It shows only the last three lines, not the distribution of errors across the whole file.

۳. 5xx دقیق3. Exact 5xx selection

یک grep ERE بنویس که فقط وضعیت سه‌رقمی 5xx رو در این قالب پیدا کنه؛ چرا 5.* ضعیف هست؟

Write a grep ERE for three-digit 5xx statuses in this format. Why is 5.* weak?

پاسخSolution

grep -E ' 5[0-9]{2} ' access.log. مرز فاصله وضعیت رو محدود می‌کنه؛ pattern پهن ممکنه timestamp/path/latency رو match کنه.

grep -E ' 5[0-9]{2} ' access.log. Space boundaries constrain the status; a broad pattern may match timestamps, paths, or latency.

۴. شمارش وضعیت4. Count statuses

چرا قبل از uniq -c معمولاً sort میاد؟

Why does sort usually precede uniq -c?

پاسخSolution

uniq فقط مقادیر تکراریِ مجاور رو جمع می‌کنه؛ sort برابرها رو کنار هم میاره. برای فیلد عددی sort -n بگذار.

uniq combines only adjacent duplicates; sort groups equal values together. Use sort -n for numeric fields.

۵. cut یا awk؟5. cut or awk?

در log فاصلهٔ متغیر بین ستون‌ها هست. چرا awk از cut -d' ' -f5 مطمئن‌تر هست؟

The log has variable spacing. Why is awk safer than cut -d' ' -f5?

پاسخSolution

awk whitespace رو separator پیش‌فرض می‌گیره؛ cut با delimiter یک space می‌تونه فیلدهای خالی/جابجا بسازه. قالب quoted هنوز parser مناسب می‌خواد.

awk treats whitespace as the default separator; cut with one literal space can mis-handle repeated delimiters. Quoted formats still need an appropriate parser.

۶. IPهای خطادار6. Failing IP addresses

از نمونه فقط IP ردیف‌های 5xx رو بگیر؛ اولین ستون خروجی کدوم هست؟

Extract IPs for only 5xx rows. Which field is printed?

پاسخSolution

awk '$5 ~ /^5/ {print $2}' access.log؛ وضعیت در $5 و IP در $2 هست، طبق قالب ثبت‌شدهٔ نمونه.

awk '$5 ~ /^5/ {print $2}' access.log; status is $5 and IP is $2 according to the documented sample format.

۷. top خطادارها7. Top failing IP

چرا pipeline شامل sort، uniq -c و sort -nr هست؟

Why does the pipeline contain sort, uniq -c, and sort -nr?

پاسخSolution

sort اول IPهای برابر رو همسایه می‌کنه، uniq می‌شماره و sort -nr شمارش رو نزولی می‌چیند. خروجی به پنجرهٔ زمانی و format محدود هست.

The first sort groups equal IPs, uniq counts them, and sort -nr orders counts descending. Results are limited to this time window and format.

۸. میانگین latency8. Average latency

چطور با awk میانگین فیلد هفتم رو می‌گیری؟ چه metricی رو به‌دست نیاورده‌ای؟

How do you average field seven with awk, and what metric have you not obtained?

پاسخSolution

awk '{s+=$7;n++} END {if(n) print s/n}'. میانگین هست، نه median یا p95؛ رکوردهای ناقص هم باید سیاست صریح داشته باشن.

awk '{s+=$7;n++} END {if(n) print s/n}'. This is a mean, not median or p95; incomplete rows need an explicit policy too.

۹. شمارش فقط روی خطا9. Aggregate only errors

چطور latency میان درخواست‌های 5xx رو جداگانه میانگین می‌گیری؟

How do you average latency only for 5xx responses?

پاسخSolution

awk '$5 ~ /^5/ {s+=$7;n++} END {if(n) printf \"%.3f\\n\",s/n}' access.log. شرط قبل از aggregation رکوردهای پذیرفته رو محدود می‌کنه؛ قالب رو تأیید کن.

awk '$5 ~ /^5/ {s+=$7;n++} END {if(n) printf \"%.3f\\n\",s/n}' access.log. The predicate limits records before aggregation; verify the format.

۱۰. اشتباه quoting10. Quoting mistake

چرا awk program معمولاً با single quote میاد؟ چه چیزی double quote رو خطرناک می‌کنه؟

Why is an awk program commonly single-quoted? What makes double quotes risky?

پاسخSolution

shell ممکنه $5 رو داخل double quotes قبل از اجرای awk گسترش بده. single quote کد رو دست‌نخورده می‌رسونه؛ متغیر shell رو با -v صریح پاس بده.

The shell may expand $5 inside double quotes before awk runs. Single quotes preserve the program; pass shell values explicitly with -v.

۱۱. جایگزینی با sed11. sed substitution

در s/foo/bar/ چند وقوع در هر خط عوض می‌شه؟

How many occurrences per line change in s/foo/bar/?

پاسخSolution

به‌طور معمول اولین وقوع هر خط؛ افزودن g همهٔ occurrenceهای همون خط رو تغییر می‌ده.

Normally the first occurrence on each line; adding g changes every occurrence on that line.

۱۲. خروجی رو جدا نگه دار12. Keep output separate

چطور گزارش stdout رو در گزارش.txt و خطاها رو در errors.txt می‌نویسی؟

How do you write stdout to report.txt and errors to errors.txt?

پاسخSolution

command >report.txt 2>errors.txt. ترتیب مهم هست اگه streamها رو merge کنی؛ مقصد stdout رو هم می‌تونی ناخواسته overwrite کنی.

command >report.txt 2>errors.txt. Order matters when merging streams, and stdout redirection can overwrite its destination.

۱۳. خطای ورودی گم‌شده13. Missing input error

grep pattern missing.log | wc -l صفر می‌ده و پیام خطا هم هست. آیا «هیچ match نیست» ثابت شد؟

grep pattern missing.log | wc -l prints zero and an error. Is “no matches” proven?

پاسخSolution

نه؛ grep ورودی رو نخوانده. وجود فایل، stderr و exit وضعیت رو بررسی کن؛ pipeline ممکنه فقط وضعیت فرمان آخر رو نشان بده.

No; grep did not read the input. Check file existence, stderr, and exit status; a pipeline may expose only its final command’s status.

۱۴. count خط‌ها نه occurrence14. Lines versus occurrences

آیا grep -c foo file همهٔ occurrenceهای foo رو در کل فایل می‌شماره؟

Does grep -c foo file count every occurrence of foo in the file?

پاسخSolution

نه؛ تعداد سطرهای منطبق رو می‌شماره. چند occurrence در یک سطر باز هم یک خط هست.

No; it counts matching lines. Multiple occurrences on one line still count as one line.

۱۵. quoted CSV؟15. Quoted CSV?

چرا cut -d, -f3 parser مطمئنی برای CSV با comma داخل quote نیست؟

Why is cut -d, -f3 not a reliable parser for CSV with quoted commas?

پاسخSolution

cut delimiter ساده رو می‌شماره و grammar quote/escape در CSV رو نمی‌فهمه. از CSV parser آگاه به قالب استفاده کن.

cut splits a simple delimiter and does not understand CSV quoting/escaping rules. Use a format-aware CSV parser.

۱۶. locale متفاوت16. Different locale

دو سرور خروجی sort رشته‌ها رو متفاوت مرتب کرده‌اند، ولی داده‌ها یکی هست. چه متغیری رو بررسی می‌کنی؟

Two hosts sort strings differently despite identical data. Which setting do you inspect?

پاسخSolution

locale و تنظیم LC_COLLATE/LC_ALL رو بررسی کن؛ برای مقایسهٔ عددی از sort -n و برای گزارش تکرارپذیر locale مشخص استفاده کن.

Inspect locale and LC_COLLATE/LC_ALL; use sort -n for numeric values and a defined locale for reproducible reports.

۱۷. مبدأ log رو دست نزن17. Preserve the source log

چرا بهتره گزارش sed رو اول به فایل دیگری بنویسی و diff بگیری؟

Why write a sed report to another file and inspect a diff first?

پاسخSolution

گزینه‌های in-place بین GNU/BSD فرق دارن و خطای pattern می‌تونه منبع رو بازنویسی کنه. فایل جدا امکان بازبینی/بازگشت می‌ده.

In-place options vary between GNU/BSD, and a wrong pattern can overwrite the source. A separate output allows review and rollback.

۱۸. بلیت پایانی log18. Final log ticket

گزارش می‌گه ۵ مورد 5xx، اما نمونه فقط ۴ مورد داره. چه چیزهایی رو قبل از اصلاح گزارش بررسی می‌کنی؟

A report says there are five 5xx responses, but the sample has four. What do you inspect before correcting the report?

راهنماHint

تعریف «خطا»، قالب فیلد، pattern و منبع stdin/stderr.

Definition of “error,” field format, pattern, and stdin/stderr source.

پاسخSolution

تعریف وضعیتهای شمرده‌شده رو روشن کن؛ چند سطر نمونه رو با grep -n ببین؛ فرض fieldها و regex رو با قالب واقعی تطبیق بده؛ وجود/سلامت ورودی و stderr/exit وضعیت رو بررسی کن. بعد pipeline رو اصلاح و تعداد رو با یک روش مستقل کنترل کن—نه اینکه عدد نهایی رو دستی عوض کنی.

Define which statuses count; inspect matching rows with grep -n; compare field and regex assumptions with the real format; check input availability plus stderr/exit status. Repair the pipeline and cross-check with an independent method—never hand-edit the final count.

وقتی pipeline جا افتاد، چطور اون رو هر بار اجرا کنیم؟Once the pipeline works, how do we run it repeatedly?

حالا می‌تونی یک سؤال رو به فیلتر، استخراج فیلد و جمع‌بندی تبدیل کنی و نتیجه رو با چند سطر نمونه بسنجی. اگه همین تحلیل رو هر شیفت تکرار کنی، copy/paste پرخطاست؛ فصل بعد pipeline رو به یک bash اسکریپت تبدیل می‌کنیم، با ورودی و خطای قابل پیش‌بینی.

You can now turn a question into filtering, field extraction, and aggregation, then verify it against sample rows. Repeating the same analysis by copy/paste invites mistakes; next we will turn it into a Bash script with predictable inputs and errors.
