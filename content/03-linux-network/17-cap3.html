آماده‌سازی کامل یک VPS تازهPreparing a fresh VPS

آخرین مأموریت دیگه یک تمرین تک‌موضوعی نیست. تیکت می‌گه «سرور تا آخر امروز آمادهٔ تحویل باشه». آماده یعنی چی؟ یعنی اگه فردا تو نباشی، نفر بعدی بدونه چطور وارد بشه، سرویس کجاست، چه چیزی از اینترنت بازه و اگه خراب شد از کجا شروع کنه.

The ticket says only: “Make it ready to deploy by end of day.” But what does ready mean? Prove who can log in, which service runs, which port responds from where, and what can be recovered after a file is lost. Turn the raw server into a handoff another engineer can verify.

مأموریت: سرور قابل‌تحویل، نه فقط روشنMission: a handoff-ready server, not merely a running one

از اینجا به بعد هر کاری که می‌کنیم باید قابل تحویل و قابل برگشت باشه. فقط روشن موندن سرور کافی نیست؛ باید ورود، سرویس، شبکه، لاگ، منبع، نسخهٔ پشتیبان و reboot رو مثل یک زنجیره کنار هم ثابت کنیم.

Use an Ubuntu VPS or disposable VM. Deliver recoverable SSH access, documented updates and time, a small service with its own user and systemd unit, a narrow firewall, logs, resource checks, scheduled backup, and a restore rehearsal. Reboot at the end and repeat the same tests.

فلش‌ها ترتیب بررسی‌اند؛ قبولی هر مرحله مرحلهٔ بعد رو ثابت نمی‌کنه.

Arrows show the verification order; passing one stage does not prove the next.

در VPS واقعی تغییر SSH یا firewall فقط با نشست دوم و کنسول ارائه‌دهنده انجام می‌شه. کلید خصوصی رو در مخزن نگذار. خرابی عمدی فقط روی VM قابل‌بازگردانی.On a real VPS, change SSH or firewall only with a second session and provider console available. Keep private keys out of the repository. Deliberate failures belong on a recoverable VM.

نقطهٔ ۱ از ۹: تصویر لحظه‌ای قبل از تغییرCheckpoint 1 of 9: before-change snapshot

قبل از نصب چیزی، hostname، ورود، زمان، دیسک، listenerها و firewall رو ثبت کن. ماشین دارای سرویس یا قانون رو تازه فرض نکن.

Before installing anything, record hostname, login, time, disk, listeners, and firewall. Do not assume a machine with services or rules is fresh.

capture baseline
hostnamectl
whoami
id
uptime
timedatectl
df -h
df -i
sudo ss -lntup
sudo ufw status verbose

پردازه‌ای که روی پورت گوش می‌ده، پورت محلی رو نشون می‌ده، نه دسترسی بیرونی. UFW خاموش وضعیت firewall ارائه‌دهنده رو نمی‌گه. خروجی رو با زمان ذخیره کن.

A listener proves a local port is bound, not external access. Inactive UFW does not reveal provider firewall state. Save output with a timestamp.

نقطهٔ ۲ از ۹: SSH و راه برگشتCheckpoint 2 of 9: SSH and recovery path

حساب sudo و پورت واقعی SSH رو شناسایی کن. کلید عمومی روی سرور، کلید خصوصی فقط روی دستگاه خودت. تغییر sshd رو از نشست دوم آزمایش کن و نشست فعلی رو نبند.

Identify the sudo account and actual SSH port. Public key goes on the server; private key stays on your device. Test sshd changes from a second session and keep the current one open.

inspect and validate before reload
getent group sudo
sudo sshd -T | grep -E '^(port|permitrootlogin|passwordauthentication) '
sudo systemctl status ssh --no-pager
sudo sshd -t

sshd -t فقط syntax رو می‌سنجه؛ اتصال واقعی رو باید جداگانه تست کنی. VM محلی رو از کنسول بازیابی کن، VPS رو از کنسول provider.

sshd -t checks syntax only; test an actual login separately. Use the VM console for local recovery and the provider console for a VPS.

نقطهٔ ۳ از ۹: update، ساعت و فضاCheckpoint 3 of 9: updates, time, and space

Ubuntu از apt استفاده می‌کنه. پیش و بعد از upgrade فضا رو بسنج و failed serviceها رو ثبت کن. روی VPS واقعی تغییر پرریسک به maintenance window نیاز داره.

Ubuntu uses apt. Check free space before and after upgrades and record failed services. Risky changes on a real VPS need a maintenance window.

update and recheck
timedatectl status
sudo apt update
sudo apt upgrade
systemctl --failed --no-pager
df -h
df -i

apt update فهرست بسته‌ها رو می‌گیره؛ upgrade بسته‌های نصب‌شده رو تغییر می‌ده. ساعت برای timestampهای log و نسخهٔ پشتیبان مهم هست، اما سلامت کل شبکه رو ثابت نمی‌کنه.

apt update refreshes package indexes; apt upgrade changes installed packages. Time matters for log and backup timestamps, but does not prove overall network health.

نقطهٔ ۴ از ۹: سرویس non-root و خرابی مسیرCheckpoint 4 of 9: non-root service and path failure

صفحه‌ای ساختگی در /srv بساز؛ root مالک، گروه سرویس خواننده. پردازه زیر systemd و با کاربر اختصاصی اجرا می‌شه.

Create a synthetic page under /srv; root owns it and the service group reads it. systemd runs the process under a dedicated user.

service identity and content
sudo adduser --system --group --no-create-home --shell /usr/sbin/nologin codenames-web
sudo install -d -o root -g codenames-web -m 0750 /srv/codenames-vps-demo/public
printf '%s\n' 'VPS baseline page' | sudo tee /srv/codenames-vps-demo/public/index.html >/dev/null
sudo chown root:codenames-web /srv/codenames-vps-demo/public/index.html
sudo chmod 0640 /srv/codenames-vps-demo/public/index.html
command -v python3

در unit از User/Group اختصاصی، interpreter واقعی، پورت ۸۰۸۰، Restart=on-خطا و محدودیت‌هایی مثل NoNewPrivileges و ProtectSystem استفاده کن. این‌ها sandbox کامل نیستن. خرابی اول: ExecStart رو موقتاً به مسیر خیالی /usr/bin/python3-missing تغییر بده؛ وضعیت و journal رو بخوان، سپس مسیر رو درست کن و همون درخواست رو دوباره بزن.

Use the dedicated User/Group, actual interpreter path, port 8080, Restart=on-failure, and restrictions such as NoNewPrivileges and ProtectSystem. They are not a complete sandbox. Seed fault one by changing ExecStart to the nonexistent /usr/bin/python3-missing; inspect status and journal, repair the path, and repeat the same request.

save the unit at the path used below
sudoedit /etc/systemd/system/codenames-vps-demo.service
save the unit at this exact path
sudoedit /etc/systemd/system/codenames-vps-demo.service
unit outline and evidence checks
[Unit]
Description=CodeNames VPS demo
After=network.target
[Service]
Type=simple
User=codenames-web
Group=codenames-web
WorkingDirectory=/srv/codenames-vps-demo
ExecStart=/usr/bin/python3 -m http.server 8080 --directory /srv/codenames-vps-demo/public --bind 0.0.0.0
Restart=on-failure
RestartSec=2
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
[Install]
WantedBy=multi-user.target
diagnose, repair, verify locally
sudo systemd-analyze verify /etc/systemd/system/codenames-vps-demo.service
sudo systemctl daemon-reload
sudo systemctl enable --now codenames-vps-demo.service
systemctl status codenames-vps-demo.service --no-pager
sudo journalctl -u codenames-vps-demo.service -n 30 --no-pager
sudo ss -lntp | grep ':8080'
curl -i http://127.0.0.1:8080/
ps -o user,group,pid,args -C python3

فعال یا listener body پاسخ و کاربر درست رو ثابت نمی‌کنه؛ curl و ps رو هم ببین.

Active state or a listener proves neither the response body nor process identity; inspect curl and ps too.

نقطهٔ ۵ از ۹: firewall و درخواست بیرونیCheckpoint 5 of 9: firewall and external request

روی VM آزمایشی پورت واقعی SSH رو مجاز کن. خرابی دوم: به‌جای ۸۰۸۰، ۸۰۸۱ رو باز کن. اگه قانون از قبل داری، VM تازه به‌کار ببر؛ قانون موجود رو پاک نکن.

On the disposable VM, allow the actual SSH port. Seed fault two by allowing 8081 instead of 8080. If rules already exist, use a fresh VM; do not delete existing rules.

drill; preserve the SSH path
sudo ufw allow OpenSSH
sudo ufw allow 8081/tcp
sudo ufw status numbered
sudo ufw enable

اگه SSH پورت دیگری داره همون رو باز کن. از client جدا به ۸۰۸۰ وصل شو؛ listener رو با ss و قانونها رو با ufw وضعیت numbered تطبیق بده. فقط قانون همین تمرین رو با شمارهٔ فعلی حذف و ۸۰۸۰/TCP رو مجاز کن. NAT و firewall ارائه‌دهنده رو جدا بررسی کن.

If SSH uses another port, allow that port. Connect to 8080 from a separate client; compare the listener with ss and rules with ufw status numbered. Delete only the drill rule by its current number and allow TCP 8080. Check NAT and provider firewall separately.

inspect current number before removal
sudo ufw status numbered
sudo ufw delete RULE_NUMBER
sudo ufw allow 8080/tcp
sudo ufw status verbose

موفقیت LAN رو موفقیت اینترنت عمومی جا نزن؛ شبکهٔ آزموده‌شده رو ثبت کن.

Do not describe LAN success as public-internet success; record which network you tested.

نقطهٔ ۶ از ۹: log و منابعCheckpoint 6 of 9: logs and resources

یک پردازه فعال لزوماً سالم نیست. log، کاربر، listener، RAM، دیسک و inode رو ثبت کن. journal محل مشاهدهٔ log این unit هست؛ خودش rotation یا هشدار بیرونی نمی‌سازه.

An active process is not necessarily healthy. Record logs, user, listener, memory, disk, and inodes. The journal exposes this unit’s logs; it does not configure rotation or external alerting.

operational snapshot
sudo journalctl -u codenames-vps-demo.service --since '-15 minutes' --no-pager
free -h
df -h
df -i
uptime
sudo ss -lntup

این‌ها تصویر لحظه‌ای هستن، نه تشخیص کامل کندی. زمان خطا رو با journal و وضعیت همون بازه تطبیق بده.

These are snapshots, not a full performance diagnosis. Correlate failure time with journal and state from that interval.

نقطهٔ ۷ از ۹: نسخهٔ پشتیبان و خرابی سومCheckpoint 7 of 9: backup and third failure

الگوی پروژهٔ قبل رو به دادهٔ همین سرویس وصل کن: مبدأ مشخص، مقصد محدود، اجرای دستی، checksum، timer، journal و restore آزمایشی. مقصد همون VM خرابی میزبان رو پوشش نمی‌ده.

Apply the previous project’s pattern to this service: explicit source, restricted destination, manual run, checksum, timer, journal, and restore rehearsal. A destination on the same VM does not cover host loss.

خرابی سوم رو با بستن موقت مجوز نوشتن مقصد آزمایشی بساز. service رو اجرا و Result، ExecMainStatus و journal رو ثبت کن؛ mode رو فوری برگردان و اجرای تازه رو بررسی نهایی کن. prune گسترده لازم نیست.

Create fault three by temporarily removing write permission on the lab destination. Run the service and record Result, ExecMainStatus, and journal; immediately restore permissions and verify a fresh run. No broad prune is needed.

scheduled run evidence
systemctl list-timers --all --no-pager
systemctl show codenames-backup.service -p Result -p ExecMainStatus
sudo journalctl -u codenames-backup.service --since today --no-pager
sudo sha256sum -c /var/backups/codenames-demo/codenames-TIMESTAMP.tar.gz.sha256
tar -tzf /var/backups/codenames-demo/codenames-TIMESTAMP.tar.gz

موعد timer موفقیت رو ثابت نمی‌کنه؛ checksum و فهرست رو جدا بخوان و محل و محدودیت آرشیو رو بنویس.

A timer deadline does not prove success; inspect checksum and listing separately and document archive location and limits.

نقطهٔ ۸ از ۹: reboot و تکرارCheckpoint 8 of 9: reboot and repeat

فقط با راه برگشت reboot کن. بعد از بالا آمدن همون آزمون‌ها رو تکرار کن تا مقایسه معتبر بمونه.

Reboot only with a recovery path. After startup, repeat the same tests so the comparison remains valid.

after reboot
uptime
timedatectl status
systemctl is-enabled codenames-vps-demo.service
systemctl is-active codenames-vps-demo.service
ps -o user,group,pid,args -C python3
sudo ss -lntp | grep ':8080'
sudo ufw status verbose
curl -fsS http://127.0.0.1:8080/
sudo journalctl -u codenames-vps-demo.service -b --no-pager
systemctl list-timers --all --no-pager
df -h

از client جدا هم درخواست بزن. unit، listener و firewall سه مدرک فرق دارن؛ راه‌اندازی دوباره کورکورانه recovery نقشهٔ اجرا نیست.

Request from a separate client too. Unit, listener, and firewall are distinct evidence; a blind restart is not a recovery plan.

نقطهٔ ۹ از ۹: handoff و rollbackCheckpoint 9 of 9: handoff and rollback

runbook شامل hostname و OS، کاربرهای مجاز و راه بازیابی SSH، پورت‌ها و مالکشان، unit و کاربر سرویس، مسیر داده، فرمان log، disk/inode، timer، آخرین اجرای موفق و checksum هست. هیچ password یا کلید خصوصی در اون نیست.

The runbook records hostname and OS, authorised users and SSH recovery, ports and owners, unit and service identity, data path, log command, disk/inodes, timer, last success, and checksum. It contains no password or private key.

rollback یعنی فقط تغییرهای پروژه رو برگردانی: timer رو متوقف و disable کن، unitهای آزمایشی رو بردار و فقط قانونهایی رو حذف کن که خودت اضافه کرده‌ای. قانون SSH یا دادهٔ قبلی رو دست نزن؛ بعد SSH و firewall رو دوباره بررسی کن.

Rollback means undoing only this project’s changes: stop and disable the timer, remove lab units, and delete only rules you added. Preserve existing SSH rules and data, then recheck SSH and firewall.

بعد از تغییر SSH وصل نمی‌شویYou cannot reconnect after SSH changes

از نشست دوم یا کنسول ارائه‌دهنده استفاده کن؛ sshd -t و پورت واقعی رو بررسی کن. قانونها رو بی‌مدرک reset نکن.

Use the second session or provider console; check sshd -t and the actual port. Do not reset rules without evidence.

unit فعال هست ولی HTTP fail می‌شهUnit is active but HTTP fails

وضعیت، journal، پردازه کاربر، listener و مجوز فایل رو جدا بسنج. فعال فقط state systemd هست.

Check status, journal, process identity, listener, and file permissions separately. Active is only the systemd state.

timer موعد داره اما archive تازه نیستTimer has a deadline but no fresh archive

Correlate Result and ExecMainStatus with the journal at that time, then inspect the destination.

راه‌حل مرجع و گزارش خرابیReference approach and incident report

ترتیب امن: تصویر لحظه‌ای؛ SSH با نشست دوم؛ update و ساعت؛ کاربر و فایل؛ unit و خرابی مسیر؛ firewall و خرابی پورت؛ log و منابع؛ timer و نسخهٔ پشتیبان و خرابی permission؛ reboot؛ handoff. بعد از هر اصلاح همون آزمون شکست‌خورده رو تکرار کن. VPS واقعی رو با اسکریپت کور تغییر نده.

Safe order: baseline; SSH with a second session; updates and time; service identity and files; unit and path fault; firewall and wrong-port fault; logs and resources; timer/backup and permission fault; reboot; handoff. Repeat the failed test after each repair. Do not make blind changes to a real VPS.

گزارش خرابی رو با نشانه، شاهد، علت، اصلاح و راستی‌آزمایی تمام کن؛ بعد بنویس چه چیزی ثابت نشده، مثل ارائه‌دهنده firewall یا بازیابی بعد از گم‌شدن میزبان. «production-ready» برچسب نیست؛ مجموعه‌ای از ادعاهای آزموده‌شده هست.

Close the incident note with symptom, evidence, cause, repair, and repeated verification; then state what remains unproven, such as provider firewall behavior or recovery after losing the host. “Production-ready” is not a label; it is a set of tested claims.
