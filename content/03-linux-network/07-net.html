مدل شبکه در عمل: ip، route، DNSNetworking in practice: ip, route, DNS

برنامه روی لپ‌تاپ باز می‌شه، روی سرور هم پردازه زنده‌ست، ولی از بیرون هیچ جوابی نمیاد. از همین‌جا معمولاً آدم‌ها شروع می‌کنن به عوض کردن firewall، DNS و هر چیزی که دم دستشونه. ما برعکس کار می‌کنیم: مسیر یک packet رو دونه‌دونه دنبال می‌کنیم.

The application is running, but a user says, “I can connect by IP, not by name.” Before restarting anything or changing a firewall, ask three questions: what address does this host have, which route will it use, and which IP does the name resolve to?

سه سؤال؛ سه مدرک جداThree questions, three separate pieces of evidence

قبل از هر عیب‌یابی شبکه باید بدونیم درخواست از کجا راه می‌افته، به کدوم IP می‌رسه، چه مسیری رو رد می‌کنه و آخرش کدوم پردازه باید جواب بده. اگه این نقشه توی ذهنت روشن باشه، شبکه خیلی کمتر جادویی به نظر میاد.

Last chapter taught us not to let a script hide a failed step. The same discipline applies here: “the network is broken” is not a diagnosis. First determine whether the issue is the host’s address, route selection, or resolving a name to an IP.

DNS نام رو به نشانی تبدیل می‌کنه؛ route تعیین می‌کنه بسته از کدوم interface و احتمالاً به سمت کدوم gateway بره.

DNS maps a name to an address; routing selects an interface and possibly a gateway for the packet.

موفق شدن DNS ثابت نمی‌کنه مقصد reachable هست. داشتن IP هم ثابت نمی‌کنه route درست هست. و route انتخاب‌شده فقط تصمیم محلی kernel رو نشون می‌ده؛ نه پاسخ‌گویی برنامهٔ مقصد رو. در هر مرحله مدرک همون مرحله رو بگیر.

A successful DNS answer does not prove the destination is reachable. Having an IP does not prove the route is correct. And a selected route shows only the kernel’s local decision, not whether the remote application will answer. Gather evidence at each boundary.

اول ببین میزبان واقعاً چه آدرسی دارهFirst inspect the addresses the host actually has

نام interfaceهایی مثل lo، eth0 یا ens3 رو حدس نزن؛ روی هر VM و ارائه‌دهنده فرق می‌کنه. ip link وضعیت link رو نشون می‌ده و ip address آدرس‌های IPv4 و IPv6 رو. شروع با ip -br address خروجی رو کوتاه می‌کنه، اما جزئیات scope رو پنهان می‌کنه.

Do not guess interface names such as lo, eth0, or ens3; they vary across VMs and providers. ip link shows link state, while ip address lists IPv4 and IPv6 addresses. ip -br address is concise but omits some scope details.

inspect links and addresses
ip -br link
ip -br address
ip address show dev eth0

نام eth0 در فرمان آخر نمونه هست؛ اون رو با نامی که روی سیستم خودت دیدی عوض کن. دنبال UP در link و آدرس‌های زیر interface بگرد. آدرس 127.0.0.1/8 یا ::1/128 loopback هست و فقط برای خود میزبان معنا داره؛ آدرس fe80::/10 link-local هست و به‌تنهایی نشانی عمومی اینترنت نیست.

The final command’s eth0 is only an example; replace it with an interface you actually saw. Look for UP on the link and addresses underneath it. 127.0.0.1/8 and ::1/128 are loopback addresses for the local host; fe80::/10 is link-local, not a public Internet address by itself.

در خروجی‌ای مثل 192.0.2.34/24، بخش /24 prefix length هست: ۲۴ بیت اول شبکه رو مشخص می‌کنه و باقی بیت‌ها برای hostهای اون prefix هست. این یک راه نوشتن mask هست، نه شمارهٔ «تعداد دستگاه‌ها»؛ IPv6 هم همین نمایش prefix رو داره و معمولاً آدرس‌های بسیار بلندتر می‌بینی.

In an address such as 192.0.2.34/24, /24 is the prefix length: the first 24 bits identify the network prefix and the remaining bits identify hosts within it. It is not a count of devices. IPv6 uses the same prefix notation with much longer addresses.

یک interface می‌تونه چند آدرس داشته باشه؛ ممکنه هم IPv4 هم IPv6 ببینه، یا چند IPv6 با scope/lifetime متفاوت. وجود inet6 به‌تنهایی ثابت نمی‌کنه برنامه از IPv6 استفاده می‌کنه. تنظیمات برنامه، DNS و route هم دخیلن.

An interface may have several addresses, including IPv4 and IPv6 or multiple IPv6 addresses with different scopes and lifetimes. Seeing an inet6 line does not prove the application will use IPv6; application settings, DNS, and routes also matter.

آیا مقصد هم‌محلی هست؟Is the destination on-link?

با آدرس 192.0.2.34/24، prefix شبکه 192.0.2.0/24 هست؛ 192.0.2.90 در همین prefix قرار می‌گیره، اما 198.51.100.10 نه. این مثال‌ها از محدوده‌های مستندسازی‌اند. «هم‌محلی» یعنی میزبان برای رسیدن به مقصد، اون رو روی همون link می‌جوید؛ این اصطلاح تضمین فیزیکی‌بودن یک کابل یا موفقیت ارتباط نیست.

With 192.0.2.34/24, the network prefix is 192.0.2.0/24; 192.0.2.90 is inside it, while 198.51.100.10 is not. These are documentation-only ranges. “On-link” means the host treats the destination as directly reachable on that link; it does not guarantee a physical cable or successful communication.

مسیر /24 دقیق‌تر از /0 هست؛ برای مقصد بیرون شبکه، پیش‌فرض route تنها match این مثال هست.

The /24 is more specific than /0; for an off-subnet destination, the default route is the only match in this example.

اگه چند route با مقصد یکسان match بشن، در تصمیم forwarding معمولاً prefix خاص‌تر بر prefix کلی‌تر مقدم هست. بعد از انتخاب route ممکنه metric، سیاست routing، جدول‌های دیگر، مبدأ address و قانونها هم اثر بگذارند؛ برای همین ip route get از یک توضیح کلی دقیق‌تر هست.

When several routes match a destination, forwarding generally prefers the more specific prefix over a broader one. Metrics, policy routing, other tables, source address selection, and rules may also matter; that is why ip route get is more useful than a generic guess.

از جدول route بپرس، حدس نزنAsk the routing table instead of guessing

برای دیدن routeهای ثبت‌شده ip route و برای دیدن route IPv6 ip -6 route رو اجرا کن. دنبال route شبکهٔ محلی و خطی مثل default via ... dev ... بگرد. این خروجی دربارهٔ جدول route kernel هست؛ ممکنه سیاست rules یا VPN نتیجهٔ انتخاب نهایی رو تغییر بدن.

Use ip route to inspect IPv4 routes and ip -6 route for IPv6. Look for a connected subnet and a line such as default via ... dev .... This shows kernel route entries; policy rules or VPN routing can affect the final lookup.

inspect routes, then ask for one decision
ip route
ip -6 route
ip route get 1.1.1.1
ip route get 192.0.2.90

خروجی ip route get معمولاً عبارت‌هایی مثل via، dev و src داره: gateway بعدی، interface خروجی و مبدأ address انتخاب‌شده. این lookup تخمینی بر اساس وضعیت همین لحظه هست؛ بسته رو ارسال نمی‌کنه و اتصال انتهابه‌انتها رو ثابت نمی‌کنه.

An ip route get result commonly includes via, dev, and src: next-hop gateway, output interface, and selected source address. This is a lookup against current state; it sends no packet and proves no end-to-end connection.

برای مقصد هم‌محلی، معمولاً route بدون gateway نشان داده می‌شه و میزبان باید همسایه رو روی link پیدا کنه. برای مقصد بیرونی، gateway انتخاب می‌شه. ip neigh جدول neighborها رو نشون می‌ده—در Ethernet-like link معمولاً نگاشت IPv4 به MAC با ARP و IPv6 با Neighbor Discovery پر می‌شه. ورودی STALE الزاماً خرابی نیست؛ kernel ممکنه اون رو هنگام نیاز تازه کنه.

For an on-link destination, the route commonly has no gateway, and the host must find a neighbor on the link. An ip neigh entry shows neighbor state—on Ethernet-like links, IPv4 uses ARP and IPv6 uses Neighbor Discovery. STALE does not automatically mean failure; the kernel may refresh it when needed.

inspect neighbor cache
ip neigh
ip -6 neigh

DNS فقط یک فایل نیستDNS is more than one file

اگه curl https://service.example.test خطای resolve می‌ده، ابتدا مشخص کن برنامه از کدوم resolver استفاده می‌کنه. getent ahosts NAME مسیر name service سیستم رو می‌آزماید؛ اگه dig نصب باشه، پاسخ DNS رو مستقیم‌تر نشون می‌ده. این ابزارها الزاماً از یک cache یا مسیر کاملاً یکسان استفاده نمی‌کنن.

If curl https://service.example.test reports a resolution error, first find out which resolver path the program uses. getent ahosts NAME exercises the system name-service path; when installed, dig shows DNS answers more directly. These tools do not necessarily use exactly the same cache or path.

compare system lookup and DNS query
getent ahosts example.com
dig example.com A
dig example.com AAAA
resolvectl status
resolvectl query example.com

dig A برای رکوردهای IPv4 و AAAA برای IPv6 سؤال می‌کنه؛ ممکنه پاسخ چند IP داشته باشه یا پاسخ خالیِ موفق برای اون نوع رکورد باشه. resolvectl فقط وقتی در دسترس هست که systemd-resolved و ابزارش نصب/فعال باشن. اگه فرمان نیست، نبودنش به‌تنهایی مشکل DNS نیست؛ از getent, dig و تنظیمات همون توزیع کمک بگیر.

dig A asks for IPv4 records and AAAA for IPv6; a response may contain several addresses or a successful empty answer for that record type. resolvectl is available only where systemd-resolved and its client are installed/active. A missing command alone is not a DNS failure; use getent, dig, and that distribution’s resolver tooling.

/etc/resolv.conf رو ببین، اما اون رو فوراً ویرایش نکن. روی بعضی سیستم‌ها فایل واقعی و دستی هست؛ روی بعضی دیگر symlink به فایلی تولیدشده توسط systemd-resolved، NetworkManager، DHCP client یا ابزار دیگری هست. ls -l /etc/resolv.conf و readlink -f /etc/resolv.conf کمک می‌کنه مالکیت پیکربندی رو بفهمی. تغییر دستی ممکنه بازنویسی بشه یا پیکربندی مدیریت‌شده رو دور بزنه.

Inspect /etc/resolv.conf, but do not immediately edit it. On some systems it is a static file; on others it is a symlink to a file generated by systemd-resolved, NetworkManager, a DHCP client, or another manager. ls -l /etc/resolv.conf and readlink -f /etc/resolv.conf help identify ownership. A manual edit may be overwritten or bypass managed configuration.

DNS server آدرس مقصدی هست که پرس‌وجو رو دریافت می‌کنه؛ «پیش‌فرض gateway» و «DNS server» دو نقش فرق دارن، حتی اگه یک router هر دو رو داشته باشه. نام‌های کوتاه ممکنه search domain داشته باشن و پاسخ به interface یا VPN وابسته باشه. resolvectl status در سیستم‌های سازگار اطلاعات link-specific رو نشون می‌ده؛ روی میزبان بدون systemd-resolved چنین خروجی‌ای انتظار نداشته باش.

A DNS server receives name queries; it has a different role from the default gateway, even if one router provides both. Short names may use search domains and answers may depend on interface or VPN. On compatible systems, resolvectl status shows link-specific details; do not expect it on hosts without systemd-resolved.

دو خرابی شبیه؛ شواهد متفاوتTwo similar failures, different evidence

فرض کن اتصال به IP شناخته‌شده کار می‌کنه اما lookup نام شکست می‌خوره. این هنوز نمی‌گه «DNS server خراب هست»؛ ممکنه نام غلط، رکورد غایب، search domain یا resolver محلی مشکل داشته باشه. در مقابل، اگه getent نام رو به IP تبدیل کنه ولی ip route get بگه Network is unreachable، lookup موفق بوده و route محلی پیدا نشده هست.

Suppose access to a known IP works but a name lookup fails. That does not yet prove “the DNS server is broken”; the name, record, search domain, or local resolver may be wrong. Conversely, if getent returns an IP but ip route get says Network is unreachable, name resolution worked and the local route lookup did not.

read each signal separately
# An echo reply is evidence for this ICMP path only:
ping -c 1 1.1.1.1

# Name resolves, then inspect the chosen path:
getent ahosts example.com
ip route get 93.184.216.34

# A direct query to a documentation-only, unreachable resolver:
dig +time=1 +tries=1 @192.0.2.53 example.com A

# Check an IP path independently (ICMP may be filtered):
ip route get 1.1.1.1

نشانی 192.0.2.53 عمداً از محدودهٔ مستندسازی انتخاب شده و resolver عمومی واقعی نیست؛ در شبکهٔ معمول پرس‌وجو زمان‌دار باید بی‌پاسخ بمونه، اما محیط آزمایشگاهی می‌تونه استثنا باشه. اگه ping بالا جواب داد، فقط مسیر ICMP تا اون میزبان در اون لحظه شاهد داره؛ اگه جواب نداد، ممکنه ICMP فیلتر شده باشه. route برای 1.1.1.1 هم به‌تنهایی رسیدن به اینترنت رو ثابت نمی‌کنه. در خرابی واقعی، dig @... رو به DNS سرور مجاز سازمان بزن.

192.0.2.53 is deliberately from a documentation range, not a public resolver; in an ordinary network the bounded query should receive no answer, though a lab may be an exception. If the ping above replies, it is evidence only for an ICMP path to that host at that time; if it fails, ICMP may be filtered. A route to 1.1.1.1 alone does not prove Internet reachability either. In a real incident, use dig @... with an authorized organizational DNS server.

برای شبیه‌سازی route خراب، route زندهٔ سرور یا لپ‌تاپ رو پاک نکن—به‌خصوص وقتی از راه دور با SSH وصل هستی. اگه می‌خوای ip route del رو ببینی، در VM یک‌بارمصرف با console در دسترس انجام بده و قبلش مطمئن شو در همون محیط هستی. بعد از تغییر route، DNS در همون VM ممکنه دیگر به resolver نرسه؛ نتیجهٔ میزبان دیگری مدرک دسترسی این VM نیست.

To simulate a broken route, do not delete a live server or laptop route—especially over SSH. If you want to observe ip route del, use a disposable VM with console access and verify you are inside it. After changing a route, DNS in that VM may also lose access to its resolver; another host’s result is not evidence for this VM.

این آزمایش فقط در VM یک‌بارمصرف با console در دسترس انجام می‌شه؛ route سیاه‌چاله عمداً دسترسی به یک IP رو قطع می‌کنه. روی host کاری یا سرور SSH اجرا نکن.

Run this only in a disposable VM with console access; the blackhole route deliberately blocks one IP. Do not run it on a work host or an SSH-only server.

برای دیدن «DNS هنوز جواب می‌ده، اما route مقصد نه»، اول IPای رو که نام به اون resolve شده یادداشت کن. سپس فقط در همون VM برای همون IPv4 یک blackhole موقت بگذار؛ پرس‌وجو دوم باید همچنان IP بده، درحالی‌که بررسی مسیر می‌گه اون مقصد blackhole هست.

To see “DNS still answers, but the destination route does not,” first record an IPv4 address returned for a name. In that VM only, add a temporary blackhole route for that one address. The next lookup should still return an IP while the route lookup reports the destination as blackholed.

disposable VM only — remove the route afterwards
ip=$(getent ahostsv4 example.com | awk 'NR == 1 {print $1}')
test -n "$ip" || { echo 'no IPv4 answer; stop here' >&2; exit 1; }
sudo ip route add blackhole "$ip/32"
getent ahostsv4 example.com
ip route get "$ip"
sudo ip route del blackhole "$ip/32"

سطر blackhole نشون می‌ده route مقصد به‌عمد بسته شده، نه اینکه DNS نتونه نام رو پیدا کنه. آخر کار route رو حذف کن؛ اگه ترمینال قطع شد، از console همون VM فرمان حذف رو اجرا یا تصویر لحظه‌ای رو برگردان. چون ممکنه چند IP برگرده، تمرین رو با همون IPی که ثبت کردی دنبال کن.

The blackhole result shows the destination route was deliberately blocked, not that DNS failed to find the name. Remove the route afterward; if the terminal is interrupted, use that VM’s console to delete it or revert the snapshot. Since a lookup may return multiple IPs, keep using the exact address you recorded.

لَب: مسیر خودت رو بدون دست‌کاری آزمایش کنLab: inspect your path without changing it

این لَب read-only هست و روی Linux VM یا WSL قابل اجراست. هدف این نیست که خروجی تو عین نمونه بشه؛ آدرس‌ها، نام interfaceها، gatewayها و DNS serverها عمداً وابسته به محیط‌اند. هیچ route یا resolverای رو در میزبان اصلی تغییر نده.

This lab is read-only and works on a Linux VM or WSL. Your output need not match the sample; addresses, interface names, gateways, and DNS servers depend on the environment. Do not change routes or resolver configuration on your main host.

اول نام و وضعیت linkها رو بگیر. اگه ip نبود، ابزار iproute2 نصب نیست یا PATH مشکل داره؛ این به معنی نبود شبکه نیست. بعد آدرس‌ها رو به route table وصل کن.

First inspect link names and state. If ip is missing, iproute2 may be uninstalled or PATH may be wrong; that does not mean networking is absent. Then relate addresses to the route table.

checkpoint 1: local state
ip -br link
ip -br address
ip route
ip -6 route

برای دو مقصد خودت route رو پیش‌بینی و بعد با kernel مقایسه کن: یکی یک نشانی داخل subnet فعلی، دیگری یک IP بیرون اون. خروجی dev و via رو ثبت کن. اگه مقصد local هست ممکنه via نداشته باشه؛ اگه چند table/سیاست routing داری، این بررسی ساده ممکنه تمام قانونها رو پوشش نده.

Predict routes for two destinations: one inside your current subnet and one outside. Compare with the kernel and record dev and via. A local destination may have no via; with policy routing or multiple tables, a simple lookup may not capture every rule.

checkpoint 2: two route decisions
ip route get DESTINATION_INSIDE
ip route get DESTINATION_OUTSIDE
ip neigh

حالا یک hostname عادی رو با getent ahosts و اگه نصب داری با dig بپرس. پاسخ رو با ip route get برای همون IP مقایسه کن. اگه getent شکست خورد اما پرس‌وجو مستقیم dig @SERVER موفق شد، مشکل احتمالاً بین برنامه و resolver سیستم هست؛ اگه هر دو fail شدند، server، دسترسی شبکه، اسم و نوع رکورد رو بررسی کن.

Resolve a hostname with getent ahosts and, if installed, dig. Compare the answer with ip route get for that IP. If getent fails but dig @SERVER succeeds, the issue may lie between the application and system resolver; if both fail, investigate the server, network access, name, and record type.

checkpoint 3: name and resolver
getent ahosts example.com
dig example.com A
ls -l /etc/resolv.conf
readlink -f /etc/resolv.conf
resolvectl status

روی WSL ممکنه بخشی از DNS و network configuration رو Windows/WSL مدیریت کنه؛ کانتینر، VM، laptop و VPS هم مدل یکسانی ندارن. اگه resolvectl نیست، بخش‌های دیگر لَب رو ادامه بده و به‌جایش فایل resolver و getent رو بررسی کن. در گزارش نهایی بنویس کدوم سه سؤال رو جواب دادی، از کدوم سطرها، و چه چیزی هنوز ثابت نشده هست.

On WSL, Windows/WSL may manage parts of DNS and network configuration; containers, VMs, laptops, and VPSs also differ. If resolvectl is absent, continue with the other checks and inspect resolver configuration plus getent. In your notes, record the three questions, the lines that answered them, and what remains unproven.

تمرین‌ها: قبل از تغییر، مسیر رو بخوانExercises: read the path before changing it

بعضی خروجی‌ها وابسته به محیط‌اند؛ پاسخ رو با قاعدهٔ route و مرز هر ابزار بسنج، نه با حفظ یک IP ثابت.

Some outputs depend on the environment. Judge answers by routing rules and tool boundaries, not by memorizing one fixed IP.

۱. loopback پاسخ می‌ده1. Loopback answers

ip address آدرس 127.0.0.1/8 رو نشون می‌ده. آیا لپ‌تاپ دیگری روی LAN می‌تونه با این آدرس به میزبان وصل بشه؟

ip address shows 127.0.0.1/8. Can another laptop on the LAN use that address to reach this host?

پاسخSolution

خیر؛ loopback به خود میزبان برمی‌گرده. برای اتصال از دستگاه دیگر باید نشانی مناسب interface شبکه و سرویس در حال listen روی اون رو بررسی کنی؛ وجود loopback فقط پشتهٔ محلی رو نشون می‌ده.

No; loopback returns to the same host. For another device, inspect the network interface address and whether the service listens there; loopback proves only local-stack behavior.

۲. prefix /242. A /24 prefix

میزبان 192.0.2.34/24 داره. کدوم مقصد در همون prefix هست: 192.0.2.90 یا 192.0.3.90؟

A host has 192.0.2.34/24. Which destination is in the same prefix: 192.0.2.90 or 192.0.3.90?

پاسخSolution

192.0.2.90، چون سه octet اول با /24 برابر هست. مقصد دوم prefix دیگری داره و route معمولاً به gateway می‌ره؛ تصمیم واقعی رو با route table همون میزبان بررسی نهایی کن.

192.0.2.90, because the first 24 bits match. The second is in another prefix and usually uses a gateway; verify the actual decision using that host’s route table.

۳. UP یعنی اینترنت داری؟3. Does UP mean Internet access?

ip link interface رو UP نشون می‌ده، ولی درخواست بیرونی fail هست. این سطر چه چیزی رو ثابت می‌کنه؟

ip link shows an interface as UP, but an external request fails. What does that line prove?

پاسخSolution

وضعیت link منطقی گزارش‌شده رو نشون می‌ده، نه IP معتبر، gateway، DNS یا پاسخ سرویس بیرونی رو. آدرس و route رو جدا بررسی کن.

It shows the reported logical link state, not a valid address, gateway, DNS, or remote service response. Inspect addresses and routes separately.

۴. پیش‌فرض route4. Default route

خروجی default via 10.0.0.1 dev ens3 رو چطور می‌خونی؟

How do you read default via 10.0.0.1 dev ens3?

پاسخSolution

برای مقصدهایی که route خاص‌تری پیدا نمی‌شه، gateway 10.0.0.1 روی ens3 مسیر پیش‌فرض هست. وجود این ورودی ثابت نمی‌کنه gateway reachable یا اینترنت فعال هست.

For destinations without a more specific route, gateway 10.0.0.1 on ens3 is the default path. Its presence does not prove the gateway or Internet is reachable.

۵. انتخاب prefix خاص‌تر5. Choosing the more specific prefix

جدول هم 10.0.0.0/8 via A و هم 10.2.0.0/16 via B داره. مقصد 10.2.3.4 کدوم رو match می‌کنه؟

The table has both 10.0.0.0/8 via A and 10.2.0.0/16 via B. Which matches 10.2.3.4?

پاسخSolution

هر دو prefix رو می‌پوشانند، اما /16 طولانی‌تر و مشخص‌تر هست و در lookup متعارف بر /8 مقدم می‌شه. قانونهای سیاست routing و tableهای دیگر می‌تونن تحلیل ساده رو پیچیده کنن؛ ip route get رو بپرس.

Both prefixes cover it, but /16 is longer and more specific, so a conventional lookup prefers it over /8. Policy rules and other tables can complicate the simple model; ask ip route get.

۶. کدوم interface انتخاب شد؟6. Which interface was selected?

ip route get 203.0.113.9 شامل dev tun0 src 10.8.0.4 هست. چه چیزی رو می‌فهمی و چه چیزی رو هنوز نمی‌دونی؟

ip route get 203.0.113.9 shows dev tun0 src 10.8.0.4. What do you know, and what remains unknown?

پاسخSolution

kernel در این lookup tun0 و مبدأ 10.8.0.4 رو انتخاب کرده هست. این ثابت نمی‌کنه تونل طرف مقابل رو می‌رسونه یا برنامه پاسخ می‌ده؛ مسیر remote و firewall هنوز بررسی نشده‌اند.

The kernel selected tun0 and source 10.8.0.4 for this lookup. It does not prove the tunnel reaches its peer or that the application responds; remote routing and firewalls remain untested.

۷. via نداره7. No via field

مقصد 192.0.2.90 در subnet متصل هست و خروجی route dev eth0 src ... داره، بدون via. چه مرحله‌ای بعدی میاد؟

Destination 192.0.2.90 is on the connected subnet; route output says dev eth0 src ... with no via. What happens next?

پاسخSolution

میزبان مستقیم روی link همسایه رو resolve می‌کنه؛ IPv4 معمولاً ARP و IPv6 Neighbor Discovery داره. ip neigh مدرکی از cache هست، نه تضمین اینکه remote host یا سرویس زنده هست.

The host resolves a neighbor directly on the link—usually ARP for IPv4 or Neighbor Discovery for IPv6. ip neigh shows cache state, not proof that the remote host or service is alive.

۸. STALE یعنی خراب؟8. Does STALE mean broken?

ip neigh یک MAC با state=STALE نشون می‌ده. آیا باید ورودی رو پاک کنی؟

ip neigh shows a MAC with state STALE. Should you delete the entry?

پاسخSolution

نه لزوماً؛ یعنی ورودی تازه تأیید نشده و kernel ممکنه هنگام استفاده اون رو probe کنه. قبل از دست‌کاری cache، lookup و ارتباط مورد نیاز رو آزمایش و state بعدی رو ببین.

Not necessarily; the entry has not been recently confirmed and the kernel may probe it when used. Test the needed lookup/communication and observe its next state before changing the cache.

۹. نام resolve شد، route نشد9. The name resolves, the route does not

getent ahosts app.example.test یک IP می‌ده، اما ip route get IP خطای no route می‌ده. کدوم لایه اولاً کار کرده؟

getent ahosts app.example.test returns an IP, but ip route get IP reports no route. Which layer worked first?

پاسخSolution

name resolution موفق بوده و انتخاب مسیر برای اون IP شکست خورده. address/interface و route/سیاست table رو بررسی کن؛ تغییر DNS به‌تنهایی route غایب رو نمی‌سازه.

Name resolution succeeded; route selection for that IP failed. Inspect addresses, interfaces, and route/policy tables; changing DNS alone cannot create the missing route.

۱۰. IP کار می‌کنه، نام نه10. IP works, name does not

درخواست به یک IP موفق هست ولی hostname شکست می‌خوره. دو بررسی بی‌خطر اولت چیست؟

A request to an IP succeeds but the hostname fails. What are your first two safe checks?

پاسخSolution

نام رو با getent ahosts و اگه بود dig بررسی کن؛ بعد resolver فعال و /etc/resolv.conf/resolvectl status رو بخوان. موفقیت IP فقط اون مسیر/پورت و زمان رو ثابت می‌کنه، نه دسترسی DNS یا همهٔ پروتکل‌ها.

Check the name with getent ahosts and, if available, dig; then inspect the active resolver and /etc/resolv.conf/resolvectl status. IP success proves only that path/port at that time, not DNS access or every protocol.

۱۱. dig پاسخ خالی می‌ده11. dig returns no address records

dig example.test AAAA وضعیت پاسخ موفق داره اما بخش جواب رکوردی نشون نمی‌ده. آیا DNS قطع هست؟

dig example.test AAAA reports a successful response status but has no answer records. Is DNS down?

پاسخSolution

نه لزوماً؛ ممکنه نام وجود داشته باشه ولی AAAA ثبت نشده باشه. سؤال A، پاسخ/authority و وضعیت DNS رو بخوان؛ نبود IPv6 record رو با timeout resolver اشتباه نگیر.

Not necessarily; the name may exist without an AAAA record. Inspect the A query, answer/authority sections, and DNS status; do not confuse a missing IPv6 record with a resolver timeout.

۱۲. فایل resolv.conf symlink هست12. resolv.conf is a symlink

ls -l /etc/resolv.conf نشون می‌ده symlink به /run/... هست. چرا ویرایش مستقیم می‌تونه دوام نیاورد؟

ls -l /etc/resolv.conf shows a symlink into /run/.... Why might a direct edit not persist?

پاسخSolution

فایل مقصد احتمالاً توسط resolver یا ابزار مدیریت شبکه مثل DHCP/NetworkManager ساخته می‌شه و با راه‌اندازی دوباره/renew بازنویسی می‌شه. مالک تنظیم رو شناسایی و همون ابزار مدیریت‌شده رو اصلاح کن؛ فایل رو کورکورانه جایگزین نکن.

The target is likely generated by a resolver or network manager and may be rewritten on restart/renewal. Identify the configuration owner and change settings through it; do not blindly replace the file.

۱۳. resolvectl وجود نداره13. resolvectl is missing

دستور می‌گه not found. آیا نتیجه می‌گیری systemd-resolved خراب هست؟

The command reports not found. Can you conclude systemd-resolved is broken?

پاسخSolution

نه؛ ممکنه ابزار نصب نباشه یا سیستم resolver دیگری داشته باشه. getent, dig, symlink و تنظیمات توزیع رو بررسی کن؛ نبود کلاینت با شکست resolve یکی نیست.

No; the tool may be absent or another resolver may be used. Check getent, dig, the symlink, and distribution configuration; a missing client is not the same as failed resolution.

۱۴. IPv6 route متفاوت هست14. IPv6 takes a different route

IPv4 مقصد کار می‌کنه، اما AAAA هم وجود داره و IPv6 اتصال fail می‌شه. کدوم table رو جدا می‌بینی؟

The IPv4 destination works, but an AAAA record exists and IPv6 connection fails. Which table do you inspect separately?

پاسخSolution

ip -6 address, ip -6 route و ip -6 route get ADDRESS رو بررسی کن؛ IPv4 connectivity route IPv6 رو ثابت نمی‌کنه. برنامه ممکنه ابتدا یکی از آدرس‌ها رو انتخاب کنه و fallback زمان‌دار داشته باشه.

Inspect ip -6 address, ip -6 route, and ip -6 route get ADDRESS; IPv4 connectivity says nothing conclusive about IPv6 routing. The application may choose an address family first and use a timed fallback.

۱۵. DNS server همون gateway هست؟15. Is the DNS server the gateway?

هم default via 10.0.0.1 می‌بینی هم nameserver 10.0.0.1. آیا دو مفهوم یکی هستن؟

You see both default via 10.0.0.1 and nameserver 10.0.0.1. Are they the same concept?

پاسخSolution

نه؛ یک IP ممکنه هم gateway و هم DNS service رو ارائه کنه، اما اولی next hop شبکه و دومی resolver نام هست. خرابی هرکدوم رو جدا آزمایش کن.

No; one IP may provide both a gateway and DNS service, but the first is a network next hop and the second a name resolver. Test each role independently.

۱۶. می‌خوای پیش‌فرض route رو از راه دور حذف کنی16. You plan to delete the default route remotely

از SSH وصل هستی و می‌خوای ip route del default بزنی تا علت رو تست کنی. اقدام امن‌تر چیست؟

You are connected over SSH and want to run ip route del default to test a theory. What is safer?

پاسخSolution

دستور رو روی سرور زنده اجرا نکن؛ ممکنه همون SSH قطع بشه و راه بازگشت نداشته باشی. از ip route get read-only استفاده کن یا یک VM/namespace یک‌بارمصرف و console out-of-band آماده داشته باش.

Do not run it on the live server; it may cut off the SSH path with no recovery access. Use read-only ip route get or a disposable VM/namespace with out-of-band console access.

۱۷. نتیجهٔ ip route get رو بیش از حد تفسیر نکن17. Do not overread ip route get

فرمان ip route get 1.1.1.1 route و مبدأ IP برمی‌گردونه. آیا ثابت شد ICMP یا HTTPS حتماً جواب می‌ده؟

ip route get 1.1.1.1 returns a route and source IP. Does this prove ICMP or HTTPS will answer?

پاسخSolution

نه؛ فقط تصمیم محلی بررسی مسیر رو می‌خونه و packet ارسال نمی‌کنه. بعداً با ابزارهای فصل بعد به اتصال واقعی و تفاوت ICMP/TCP نگاه می‌کنیم.

No; it reads the local route decision and sends no packet. The next chapter will test actual connectivity and distinguish ICMP from TCP.

۱۸. بلیت پایان شیفت18. End-of-shift incident ticket

نام سرویس resolve می‌شه؛ ip route get gateway می‌ده؛ کاربر می‌گه HTTPS timeout هست. سه مدرک بعدی رو چطور جمع می‌کنی بدون اینکه DNS یا route میزبان رو تغییر بدی؟

The service name resolves and ip route get shows a gateway, but the user reports an HTTPS timeout. What three pieces of evidence do you collect next without changing host DNS or routes?

راهنماHint

lookup و route تا این‌جا جواب داده‌اند؛ حالا باید بفهمی packet از کدوم مرز عبور نمی‌کنه.

Name lookup and route selection have passed; now find which boundary the packet fails to cross.

پاسخSolution

IP و پورت دقیق مقصد و مبدأ address انتخاب‌شده رو ثبت کن؛ بعد فقط probe زمان‌دار به پورت موردنیاز اجرا کن و route/interface رو با زمان تست کنار هم نگه دار؛ در آخر از لاگ سمت سرور یا firewall/ارائه‌دهنده مسیر برگشت رو بررسی کن. route حاضر به‌تنهایی عبور packet یا listen بودن برنامه رو ثابت نمی‌کنه؛ فصل بعد ping/traceroute/ss/tcpdump رو برای جداکردن همین مرزها به‌کار می‌گیره.

Record the exact destination IP/port and selected source address; run a bounded probe to that port and keep its timestamp with the route/interface evidence; then inspect server or firewall/provider logs for the return path. A route entry alone proves neither packet delivery nor an application listener; the next chapter uses ping, traceroute, ss, and tcpdump to separate those boundaries.
