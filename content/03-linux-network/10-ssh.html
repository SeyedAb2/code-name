SSH، کلید، tunnel، ssh/configSSH, keys, tunnels, ssh/config

فصل قبل راه ورودی سرور را با فایروال محدود کردیم. حالا همان راه باز است، اما هر بار رمز می‌خواهد؛ بین bastion و سرور خصوصی هم باید مسیر امنی بسازیم. به‌جای حفظ چند دستور، ببینیم SSH به کدام هویت اعتماد می‌کند و هر tunnel کجا socket باز می‌کند.

Last chapter narrowed the server’s entry points with a firewall. The route is open, but it asks for a password every time; reaching a private server also means crossing a bastion. Rather than memorising commands, let’s see which identity SSH trusts and where each tunnel opens a socket.

اول یک سؤال: سرور را می‌شناسی، یا سرور تو را؟First question: do you know the server, or does it know you?

وقتی می‌زنی ssh user@server، دو طرف باید هویت هم را بررسی کنند. کلید میزبان (host key) می‌گوید «این endpoint همان serverی است که قبلاً دیده‌ام؟»؛ کلید کاربر می‌گوید «این client اجازهٔ ورود به حساب user را دارد؟» این دو کلید یک جفت نیستند و جای هم را نمی‌گیرند.

When you run ssh user@server, both sides establish identity. The server’s host key answers, “Is this the same server endpoint I have seen before?” The user key answers, “May this client log in as this account?” They are different keys with different jobs; neither substitutes for the other.

فلش بالا: client کلید میزبان را با known_hosts می‌سنجد. فلش پایین: server امضای client را با کلید عمومی مجاز می‌سنجد.

Top arrow: the client checks the host key against known_hosts. Bottom arrow: the server verifies the client’s signature using an authorised public key.

اولین بار ممکن است SSH بپرسد کلید میزبان را به known_hosts اضافه کند. این یعنی کلید برای client تازه است، نه اینکه هویت server تأیید شده باشد. fingerprint را از یک مسیر مستقل—مثلاً کنسول provider یا مدیر سرور—بگیر و مقایسه کن. ssh-keyscan کلید را می‌خواند اما مالکیتش را تأیید نمی‌کند.

On first contact, SSH may ask whether to add the host key to known_hosts. That means the key is new to this client, not that the server’s identity has been verified. Obtain its fingerprint through an independent channel—such as a provider console or administrator—and compare it. ssh-keyscan retrieves a key but does not verify its ownership.

احراز هویت و tunnel دو سؤال جدا هستند: tunnel می‌تواند با ورود رمزدار یا کلیددار برقرار شود. برای اینکه مسیر داده را اول روشن ببینیم، نمونه‌های ابتدایی از SSH loginای استفاده می‌کنند که از قبل در اختیار داری؛ چند بخش بعد آن را به کلید اختصاصی و config تمیز تبدیل می‌کنیم.

Authentication and tunnelling are separate concerns: a tunnel can use either password or key-based login. To make the data path clear first, early examples assume an SSH login you already have; later we replace it with a dedicated key and clean config.

verify from the server console, out of band
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

SHA256:... باید با fingerprintای که client نشان می‌دهد یکی باشد. این مقایسه هویت کلید میزبان را برای این اتصال می‌سنجد؛ امن‌بودن حساب کاربری یا برنامه‌های server را ثابت نمی‌کند. مسیر کلید host بسته به سیستم ممکن است فرق کند؛ در آن صورت از کنسول همان ماشین کلید عمومی درست را پیدا کن.

The SHA256:... fingerprint should match what the client displays. This checks the host key for this connection; it does not prove that the account or server applications are secure. Host-key paths vary by system, so obtain the correct public key from that machine’s console.

bastion: یک پرش، نه یک shell واسطهA bastion is a hop, not an intermediate shell

سرور خصوصی شاید اصلاً از اینترنت route نداشته باشد، ولی bastion دسترسی SSH مدیریت‌شده دارد. ProxyJump client را به bastion می‌رساند و از آنجا TCP را تا مقصد خصوصی relay می‌کند؛ لازم نیست وارد shell واسطه شوی و دستور SSH دومی اجرا کنی.

A private server may have no route from the internet while a managed bastion is reachable by SSH. ProxyJump connects the client to the bastion and relays TCP onward to the private destination; you do not need to open an intermediate shell and run a second SSH command.

اسم‌هایی مثل private-app و lab-bastion aliasهای config هستند که پایین‌تر تعریف می‌کنیم؛ اگر الان آزمایش می‌کنی، هرکدام را با user و نشانی واقعی جایگزین کن.

Names such as private-app and lab-bastion are config aliases defined later; while experimenting now, replace them with the real user and address.

پیکان‌ها مسیر اتصال SSH و relay شبکه‌اند؛ bastion گذرگاه است و مقصد را public نمی‌کند.

Arrows show the SSH connection and network relay; the bastion is a hop and does not make the destination public.

اگر ssh private-app به bastion وصل می‌شود اما به مقصد نه، مقدار HostName را با ssh -G private-app بخوان؛ بعد route، firewall و پورت SSH بین bastion و مقصد را بررسی کن. ورود به bastion ثابت نمی‌کند sshd روی private host پاسخ می‌دهد.

If ssh private-app reaches the bastion but not the destination, inspect HostName with ssh -G private-app, then check routes, firewall, and the SSH port between the two servers. Logging in to the bastion does not prove the private host’s sshd is reachable.

-L: پورت محلی به سرویس سمت server-L: a local port to a server-side service

وب‌سرویس داخلی روی server فقط به 127.0.0.1:8080 گوش می‌دهد؛ از laptop مستقیم باز نمی‌شود. به‌جای بازکردن firewall، روی client یک پورت محلی می‌سازیم و SSH را حامل بایت‌ها می‌کنیم. در -L، socket ورودی روی client است؛ مقصد را server از سمت خودش باز می‌کند.

An internal web service listens only on the server’s 127.0.0.1:8080, so the laptop cannot reach it directly. Instead of opening the firewall, create a local port on the client and carry bytes through SSH. With -L, the entry socket is on the client; the server opens the destination from its side.

برای اینکه روی شکل و فرمان‌ها تمرکز کنیم، این بخش فرض می‌کند از قبل یک SSH login معتبر داری و lab-server اسم کوتاه همان مقصد است؛ پایین‌تر آن را در ~/.ssh/config می‌سازیم. تا آن موقع می‌توانی alias را با learner@IP جایگزین کنی.

To focus on the socket mapping, this section assumes you already have a working SSH login and lab-server is a shorthand for that destination; we define it in ~/.ssh/config below. Until then, replace the alias with learner@IP.

عدد اول -L روی client گوش می‌دهد؛ مقصد بعد از آن را SSH از سمت server باز می‌کند.

The first port in -L listens on the client; SSH opens the destination after it from the server side.

در -L 127.0.0.1:18080:127.0.0.1:8080، پورت 18080 سمت client است و 127.0.0.1:8080 از دید server. -N یعنی shell اجرا نکن، فقط tunnel؛ ExitOnForwardFailure=yes خطای bind محلی را زود نشان می‌دهد. دستور را در terminal اول باز نگه دار.

In -L 127.0.0.1:18080:127.0.0.1:8080, port 18080 is on the client and 127.0.0.1:8080 is interpreted from the server. -N requests no shell, only forwarding; ExitOnForwardFailure=yes surfaces a failed local bind. Keep this command running in one terminal.

client — terminal A opens the tunnel; terminal B tests it
# Terminal A:
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:18080:127.0.0.1:8080 lab-server

# Terminal B:
curl --max-time 5 -I http://127.0.0.1:18080/
ss -lnt | grep ':18080'
representative result — versions/queue vary
HTTP/1.0 200 OK
Server: SimpleHTTP/0.6 Python/3.x
LISTEN 0 128 127.0.0.1:18080 0.0.0.0:*

HTTP response و ss با listener روی client ثابت می‌کنند مسیر client→SSH→سرویس برقرار است. این ثابت نمی‌کند port 8080 روی اینترنت باز است—لازم هم نیست. اگر tunnel بالا ماند ولی curl خطا داد، از خود server با curl 127.0.0.1:8080 و ss -lntp سرویس مقصد را بررسی کن.

The HTTP response and client-side listener prove that the client→SSH→service path works. They do not prove port 8080 is open to the internet—and it need not be. If the tunnel stays up but curl fails, inspect the destination from the server with curl 127.0.0.1:8080 and ss -lntp.

-R برعکس است؛ -D مقصد را پویا می‌کند-R reverses the listener; -D makes the destination dynamic

در -R socket ورودی روی server ساخته می‌شود و SSH اتصال را به سرویس client می‌رساند. در تنظیم معمول، listener remote روی loopback server است؛ تنظیم GatewayPorts یا bind address می‌تواند دامنهٔ دسترسی را عوض کند. آن را بی‌دلیل public نکن.

With -R, the entry socket is created on the server and SSH carries the connection to a client-side service. Normally the remote listener is on server loopback; GatewayPorts or the bind address can widen exposure. Do not publish it casually.

در -R پورت اول سمت server است؛ مقصد پایانی از دید client تفسیر می‌شود.

With -R, the first port listens on the server; the final destination is interpreted on the client.

برای دیدن آن، روی client یک server آزمایشی روی loopback و port 8090 بالا بیاور؛ با -R روی server پورت 18090 بساز؛ سپس از همان server به 127.0.0.1:18090 درخواست بده. این تمرین public listener نمی‌سازد.

To observe it, start a test server on client loopback port 8090, create server port 18090 with -R, then request 127.0.0.1:18090 from that server. This experiment does not create a public listener.

client terminal A, client terminal B, then server
# Client terminal A:
python3 -m http.server 8090 --bind 127.0.0.1

# Client terminal B:
ssh -N -o ExitOnForwardFailure=yes -R 127.0.0.1:18090:127.0.0.1:8090 lab-server

# Server, through another SSH command:
ssh lab-server 'ss -lnt | grep ":18090"; curl --max-time 5 -I http://127.0.0.1:18090/'

باید server روی 127.0.0.1:18090 گوش دهد و درخواست HTTP جواب بگیرد. اگر 0.0.0.0:18090 دیدی، توقف کن: bind از loopback بیرون رفته است. اگر port ساخته شد ولی پاسخ نیامد، listener client، مقصد 8090 و اجازهٔ AllowTcpForwarding در sshd را بررسی کن؛ policy را برای دورزدن محدودیت تغییر نده.

The server should listen on 127.0.0.1:18090 and the HTTP request should succeed. If you see 0.0.0.0:18090, stop: the bind escaped loopback. If the port exists but no response arrives, check the client listener, destination 8090, and sshd’s AllowTcpForwarding; do not change policy to bypass a restriction.

-D 127.0.0.1:1080 یک SOCKS proxy روی client می‌سازد تا برنامهٔ سازگار مقصدهای متفاوتی را از SSH درخواست کند. این پیش‌نمایش VPN نیست: همهٔ traffic سیستم را tunnel نمی‌کند و DNS/مجوز مقصدها هم بسته به client و policy فرق می‌کند. SOCKS را روی 0.0.0.0 نبند مگر اینکه exposure عمداً طراحی و محدود شده باشد.

-D 127.0.0.1:1080 creates a SOCKS proxy on the client so a compatible app can request different destinations through SSH. This is not a VPN: it does not tunnel all system traffic, and DNS/destination access depend on the client and policy. Do not bind SOCKS to 0.0.0.0 unless exposure is deliberately designed and restricted.

preview only — local SOCKS listener
ssh -N -D 127.0.0.1:1080 lab-server

رمز تکراری را با کلید کاربر عوض کنیمReplace repeated passwords with a user key

روی client یک جفت کلید می‌سازی: private key فقط پیش تو می‌ماند؛ public key را در حساب مجاز روی server ثبت می‌کنی. server هیچ‌وقت private key تو را لازم ندارد. اگر کسی آن را می‌خواهد، متوقف شو.

Generate a key pair on the client: keep the private key there; install the public key for the account on the server. The server never needs your private key. Stop if anyone asks you to copy it there.

برای لَب کلید جدا می‌سازیم تا فایل‌های شخصی‌ات را دست نزنیم. ed25519 برای OpenSSH امروزی انتخاب مناسبی است؛ -f مسیر را مشخص می‌کند و -C comment می‌گذارد. passphrase قوی انتخاب کن: از private key دزدیده‌شده به‌تنهایی جلوگیری نمی‌کند، ولی استفاده از آن را سخت‌تر می‌کند.

Create a separate lab key so we do not touch your personal credentials. ed25519 is suitable for current OpenSSH; -f selects the file and -C adds a comment. Use a passphrase: it does not make a stolen key harmless, but it makes immediate use harder.

client — create a lab-only identity
ssh-keygen -t ed25519 -a 64 -f ~/.ssh/codenames_lab_ed25519 -C "codenames-lab"
ssh-keygen -lf ~/.ssh/codenames_lab_ed25519.pub

در پرسش passphrase برای تمرین عبارت بگذار. fingerprint خط دوم شناسهٔ public key تازه است. این فقط می‌گوید جفت کلید ساخته شده—هنوز هیچ serverی آن را مجاز نکرده.

Set a passphrase for this exercise. The second command prints the new public-key fingerprint. This proves only that a pair was created—no server has authorised it yet.

ssh-copy-id معمولاً public key را به ~/.ssh/authorized_keys اضافه می‌کند؛ بار اول هنوز باید با روش ورود فعلی (مثلاً password) به همان حساب دسترسی داشته باشی. اگر اتصال دوم با کلید موفق شد، server امضای متناظر با public key ثبت‌شده را پذیرفته. این مجوز فقط به همان حساب/host مربوط است.

ssh-copy-id normally appends the public key to ~/.ssh/authorized_keys; initially you still need your existing access method, such as a password. If a second login with the key succeeds, the server accepted a signature matching the installed public key. That authorisation applies only to that account and host.

copy the public half only
ssh-copy-id -i ~/.ssh/codenames_lab_ed25519.pub learner@192.0.2.40
ssh -i ~/.ssh/codenames_lab_ed25519 learner@192.0.2.40

192.0.2.40 نشانی مستندی برای مثال است؛ در لَب IP واقعی VM را می‌گذاری. private key بدون پسوند را نه در Git بگذار، نه در پیام‌رسان بفرست و نه روی server کپی کن. فایل .pub راز نیست، اما fingerprint آن را همچنان از منبع مطمئن بگیر.

192.0.2.40 is a documentation-only example address; substitute the VM’s actual IP in the lab. Never commit, message, or copy the private key without .pub to the server. The .pub file is not secret, but still obtain its fingerprint from a trusted source.

اگر کلید هست، چرا OpenSSH نادیده‌اش می‌گیرد؟The key exists—why does OpenSSH ignore it?

اگر فایل private key برای دیگران هم قابل‌خواندن باشد، OpenSSH معمولاً پیش از امتحان‌کردنش آن را رد می‌کند. روی client مجوز .ssh و کلید را ببین؛ روی server هم مالکیت home، .ssh و authorized_keys مهم است. sshd با StrictModes مسیرهای ناامن را ممکن است نپذیرد.

If other users can read the private key, OpenSSH normally rejects it before trying it. Inspect .ssh and the key on the client; ownership of the server account’s home, .ssh, and authorized_keys matters too. With StrictModes, sshd may reject unsafe paths.

در ssh -vv دنبال UNPROTECTED PRIVATE KEY FILE، Offering public key و پاسخ server بگرد. Offering فقط یعنی client کلید را امتحان کرد؛ Authenticated to ... نشانهٔ موفقیت است. اگر server کلید را رد کرد، username، public key متناظر در authorized_keys و مالکیت مسیر را بررسی کن—کلیدهای دیگر را کورکورانه پاک نکن.

In ssh -vv, look for UNPROTECTED PRIVATE KEY FILE, Offering public key, and the server’s response. “Offering” only means the client tried the key; Authenticated to ... indicates success. If the server rejects it, check the username, matching authorized_keys entry, and path ownership—do not blindly delete other keys.

وقتی چند server داری، ممکن است client چند هویت را امتحان کند و از سقف تلاش server بگذرد. ssh-agent کلید را در client نگه می‌دارد و امضا را انجام می‌دهد؛ خود private key از شبکه رد نمی‌شود. agent جای passphrase یا کنترل دسترسی دستگاه نیست.

With several servers, the client may try many identities and exceed the server’s attempt limit. ssh-agent holds keys on the client and performs signatures; the private key itself is not sent over the network. An agent is not a substitute for a passphrase or device access controls.

use the existing session agent if present
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/codenames_lab_ed25519
ssh-add -l

اگر ssh-add -l fingerprint همین کلید را نشان داد، آن identity برای session حاضر در agent است؛ با ssh-keygen -lf ...pub مقایسه کن. این نشان نمی‌دهد کدام server کلید را مجاز کرده. agent-forwarding را پیش‌فرض روشن نکن: ماشین remote می‌تواند هنگام forwarding از agent درخواست امضا کند؛ private key را نمی‌گیرد، اما اختیار موقتی بی‌خطر هم نیست.

If ssh-add -l lists this fingerprint, the identity is available to the current session; compare it with ssh-keygen -lf ...pub. This does not say which server authorised it. Do not enable agent forwarding by default: a remote machine can request signatures while forwarding is active. It does not receive the private key, but the temporary authority still has risk.

فرمان eval "$(ssh-agent -s)" نمونهٔ shellهای POSIX مثل Bash در Linux/WSL است؛ در بعضی desktopها agent از قبل فعال است و نیازی به ساختن agent تازه نیست. Windows OpenSSH روش راه‌اندازی agent خودش را دارد؛ فرمان Bash را در PowerShell عیناً کپی نکن.

eval "$(ssh-agent -s)" is a POSIX-shell example for Linux/WSL; some desktops already run an agent. Windows OpenSSH has its own agent service setup, so do not paste the Bash command unchanged into PowerShell.

یک اسم کوتاه، به‌جای تکرار port و مسیر کلیدOne short name instead of repeating ports and key paths

دستور بلند را می‌شود هر بار کپی کرد، تا یک روز اشتباهی به production وصل شوی. ~/.ssh/config تنظیم‌های client را زیر alias نگه می‌دارد؛ server را تغییر نمی‌دهد و جای نگهداری راز نیست.

You can copy a long command each time—until one day it points at production by mistake. ~/.ssh/config stores client settings under aliases; it does not change the server and is not a place for secrets.

client config — keep only the hosts you use
Host lab-server
    HostName 192.0.2.40
    User learner
    Port 22
    IdentityFile ~/.ssh/codenames_lab_ed25519
    IdentitiesOnly yes
    AddKeysToAgent yes
    ForwardAgent no

Host private-app
    HostName 10.20.0.15
    User deploy
    IdentityFile ~/.ssh/codenames_lab_ed25519
    IdentitiesOnly yes
    ProxyJump lab-bastion

Host lab-bastion
    HostName 203.0.113.20
    User learner
    IdentityFile ~/.ssh/codenames_lab_ed25519
    IdentitiesOnly yes

نشانی‌های این نمونه مستندی‌اند؛ IP واقعی خودت را بگذار. Host نامی است که تایپ می‌کنی؛ HostName مقصد؛ User و Port حساب و درگاه؛ IdentityFile کلید؛ و IdentitiesOnly yes جلوی امتحان بی‌حساب کلیدهای agent را می‌گیرد. ProxyJump می‌گوید از bastion عبور کن تا به مقصد خصوصی برسی. برای لَب تک‌ماشینه، دو block آخر را حذف کن.

The addresses here are documentation-only; replace them with real lab values. Host is the alias you type; HostName is the destination; User and Port select account and port; IdentityFile selects the key; IdentitiesOnly yes avoids trying every agent identity. ProxyJump routes through the bastion to a private destination. Omit the last two blocks for the single-VM lab.

فایل باید متعلق به خودت باشد و دیگران نتوانند آن را بنویسند؛ chmod 600 ~/.ssh/config انتخاب متعارفی است. ssh -G تنظیم نهایی را resolve می‌کند؛ این دستور اتصال شبکه را امتحان نمی‌کند. بعد ssh -v را برای اتصال واقعی به‌کار ببر و مقصد، کلید و host key انتخاب‌شده را ببین.

The file should belong to you and not be writable by others; chmod 600 ~/.ssh/config is a common setting. ssh -G resolves effective settings but does not test the network. Then use ssh -v for a real connection and inspect the selected destination, key, and host key.

resolve, inspect, then connect
chmod 600 ~/.ssh/config
ssh -G lab-server | grep -E '^(hostname|user|port|identityfile|identitiesonly) '
ssh -v lab-server

Authenticated to 192.0.2.40 using "publickey".

در این نمونه، hostname/user/port/identityfile نشان می‌دهند config به مقصد موردنظر resolve شده؛ Offering یعنی کلید امتحان شده و Authenticated to یعنی احراز هویت موفق شده. IP و fingerprint نمونه‌اند. حتی این خروجی هم سلامت برنامه یا محدودبودن portهای دیگر را ثابت نمی‌کند.

Here, hostname/user/port/identityfile show that the config resolved to the intended target; Offering means a key was tried, while Authenticated to means authentication succeeded. The address and fingerprint are illustrative. Even this output does not prove that the application is healthy or other ports are restricted.

اگر ssh -G کاربر یا port اشتباه چاپ کرد، پیش از اتصال block متناظر را اصلاح کن. هشدار host key با alias از بین نمی‌رود. اگر کلید میزبان عوض شده، توقف کن و fingerprint را از کانال مستقل تأیید کن؛ فقط بعد از تأیید رکورد دقیق را حذف کن. معمولاً باید مقدار واقعی HostName را بدهی؛ برای پورت غیراستاندارد OpenSSH شناسه‌ای مثل [server.example]:2222 نگه می‌دارد. ssh-keygen -F HOST کمک می‌کند قبل از حذف، رکورد را پیدا کنی. known_hosts را برای ساکت‌کردن هشدار خالی نکن.

If ssh -G prints the wrong user or port, fix the matching block before connecting. An alias does not bypass host-key checks. If the host key changed, stop and verify the fingerprint independently; only then remove the exact record. Usually use the actual HostName; for a non-default port, OpenSSH stores a token such as [server.example]:2222. ssh-keygen -F HOST helps locate a record before removal. Never empty known_hosts just to silence a warning.

یک پیام خطا، یک تشخیص قطعی نیستOne error message is not a complete diagnosis

اگر ssh می‌گوید Permission denied (publickey)، اتصال به مرحلهٔ احراز هویت رسیده ولی کلید/حساب مجاز نشده؛ -vv نشان می‌دهد کدام identity offer شد. اگر Connection timed out می‌بینی، هنوز معلوم نیست route، firewall میزبان، provider یا ماشین خاموش مقصر است. فصل‌های route، عیب‌یابی شبکه و firewall را برای جداکردن این مرزها به‌کار ببر.

If SSH reports Permission denied (publickey), the connection reached authentication but the key/account was not accepted; -vv shows which identity was offered. Connection timed out does not yet tell you whether the route, host firewall, provider, or an offline machine is responsible. Use the route, network-debugging, and firewall chapters to separate those boundaries.

Now, only in the lab, make the private key too accessible. Read the verbose output first, then restore its permissions. We do not touch a real host key or known_hosts entry.

خطای permissions پیش از آن رخ می‌دهد که server کلید را بپذیرد؛ پس تغییر authorized_keys علت را درمان نمی‌کند. اگر پس از chmod 600 هنوز Permission denied می‌بینی، خروجی باید identity پیشنهادی را نشان دهد؛ بعد user، کلید عمومی متناظر، مالکیت مسیر و policy sshd را بررسی کن.

The permissions error happens before the server can accept the key, so editing authorized_keys would not address it. If Permission denied remains after chmod 600, inspect the offered identity, then check the account, matching public key, path ownership, and sshd policy.

هشدار host key را با پاک‌کردن حل نکنDo not “fix” a host-key warning by deleting it blindly

تغییر host key گاهی بعد از rebuild یا rotation کنترل‌شده طبیعی است؛ گاهی هم اتصال به ماشین اشتباه یا حملهٔ واسطه را نشان می‌دهد. تغییر را از کنسول/provider یا مدیر مستقل تأیید کن و hostname/port را بررسی کن؛ فقط بعد از تطبیق fingerprint جدید، رکورد همان مقصد را با ssh-keygen -R HOST بردار. StrictHostKeyChecking=no یا پاک‌کردن کل فایل روش عیب‌یابی نیست.

A host-key change can follow a controlled rebuild or rotation; it can also signal the wrong machine or an on-path attack. Verify the change through an independent console/provider or administrator and check hostname/port. Only after matching the new fingerprint should you remove that destination with ssh-keygen -R HOST. Disabling strict checking or deleting the whole file is not troubleshooting.

لَب: سرویس خصوصی را بدون بازکردن port ببینLab: reach a private service without opening its port

دو ماشین در شبکهٔ آزمایشی لازم داری: client و Ubuntu VM با SSH server. host + VM هم جواب می‌دهد، اگر client به VM دسترسی SSH داشته باشد. از production و کلید شخصی استفاده نکن. سرویس وب این تمرین فقط روی 127.0.0.1 گوش می‌دهد؛ لازم نیست پورت 8080 را در firewall باز کنی. فقط SSH آزمایشی از client مجاز باشد.

Use two machines on a lab network: a client and an Ubuntu VM running an SSH server. A host plus VM works if the client can SSH to the VM. Do not use production or a personal key. The web service listens only on 127.0.0.1; you do not need to open port 8080 in the firewall. Permit only lab SSH from the client.

روی client مقدارهای واقعی را در همان shell تنظیم کن. نشانی 192.0.2.40 مثال مستندی است و route واقعی ندارد. روی VM هم حساب عادی و روش ورود فعلی را داشته باش. پیش از قبول اولین host key، از console VM fingerprint بگیر:

Set real values in the client shell; 192.0.2.40 is documentation-only and is not a real lab route. On the VM, use a normal account with an existing login method. Before accepting a first host key, obtain its fingerprint from the VM console:

اگر روی VM آزمایشی SSH server نصب نیست، فقط همان‌جا بسته را نصب کن. systemctl status باید active (running) نشان دهد؛ این فقط زنده‌بودن سرویس را می‌گوید، نه اینکه firewall یا client به آن می‌رسد.

If the lab VM has no SSH server, install it there. systemctl status should show active (running); this proves only that the service is running, not that the firewall or client can reach it.

VM console — only if OpenSSH server is absent
sudo apt update
sudo apt install openssh-server
sudo systemctl status ssh --no-pager
verify the endpoint before authentication
# Client shell — substitute the actual values:
LAB_USER=learner
LAB_HOST=192.168.56.20

# VM console — send the displayed fingerprint to the client out of band:
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

# Client — first verify the displayed fingerprint, then connect:
ssh -p 22 "$LAB_USER@$LAB_HOST" 'id; hostname'

# VM console — confirm that sshd listens on the expected port:
sudo ss -lntp | grep ':22'

fingerprint کنسول و client باید یکی باشد؛ id و hostname هم رسیدن به حساب و ماشین موردنظر را نشان می‌دهند. ss باید پورت واقعی sshd را نشان دهد. اینها دسترسی public اینترنت را ثابت نمی‌کنند. اگر SSH روی پورت دیگری است، همان را در فرمان‌ها و config بعدی بنویس.

The console and client fingerprints should match; id and hostname show that you reached the intended account and machine. ss should show sshd’s actual port. None of these proves public internet reachability. If SSH uses another port, use it consistently below.

روی client جفت کلید آزمایشی بساز و public key را نصب کن. اگر ssh-copy-id نیست، از client public key را append کن؛ private key را هرگز در pipe نگذار. قبل از paste، user و IP را دوباره کنترل کن.

Generate a lab key pair on the client and install its public half. If ssh-copy-id is unavailable, append the public key from the client; never put the private key in the pipe. Recheck user and address before pasting.

client — key setup (manual fallback)
ssh-keygen -t ed25519 -a 64 -f ~/.ssh/codenames_lab_ed25519 -C "codenames-lab"
cat ~/.ssh/codenames_lab_ed25519.pub | ssh "$LAB_USER@$LAB_HOST" 'umask 077; mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys; chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys'
chmod 600 ~/.ssh/codenames_lab_ed25519
ssh -i ~/.ssh/codenames_lab_ed25519 "$LAB_USER@$LAB_HOST" 'id'

این fallback فقط فایل .pub را می‌فرستد و ممکن است اگر کلید قبلاً نصب بوده خط تکراری بسازد. اتصال آزمایشی را با ssh -i ثابت کن؛ اگر موفق نشد، ssh -vv را بخوان و مرز شکست را پیدا کن. تا وقتی public-key login کار نکرده، تنظیم ورودهای دیگر را تغییر نده.

This fallback sends only the .pub file and may create a duplicate line if it was already installed. Verify key login with ssh -i; if it fails, read ssh -vv and locate the boundary. Do not change other login settings until public-key login works.

حالا alias می‌سازیم. اگر پورت تو غیر از 22 است، مقدارش را در block عوض کن. ssh -G config را بدون اتصال بررسی می‌کند؛ بعد ssh -v را اجرا کن و host key، identity و پیام Authenticated to را ببین.

Now add an alias. If SSH uses another port, change it in the block. ssh -G checks the config without connecting; then run ssh -v and inspect the host key, identity, and Authenticated to message.

client — make a stable alias
cat >> ~/.ssh/config <<EOF
Host lab-server
    HostName ${LAB_HOST}
    User ${LAB_USER}
    Port 22
    IdentityFile ~/.ssh/codenames_lab_ed25519
    IdentitiesOnly yes
    ForwardAgent no
EOF
chmod 600 ~/.ssh/config
ssh -G lab-server | grep -E '^(hostname|user|port|identityfile|identitiesonly) '
ssh -v lab-server

در VM، سرویس آزمایشی را به foreground بیاور تا هم رفتار را ببینی و هم cleanup روشن باشد. terminalای که این فرمان را اجرا می‌کند باید باز بماند؛ هر درخواست هم یک خط در خروجی همان Python می‌نویسد. 127.0.0.1 مهم است: سرویس از شبکهٔ بیرون VM قابل دسترسی مستقیم نیست.

On the VM, run the test service in the foreground so its behaviour and cleanup are visible. Keep that terminal open; each request appears in Python’s output. 127.0.0.1 matters: the service is not directly reachable from outside the VM.

VM console — keep the test server in the foreground
python3 -m http.server 8080 --bind 127.0.0.1

در client terminal دوم tunnel محلی را باز نگه دار. در terminal سوم درخواست را بزن و listener سمت client را بررسی کن. اگر 18080 اشغال است، پیش از اجرا ss -lnt را بخوان و یک پورت آزاد دیگر انتخاب کن.

In a second client terminal, keep the local tunnel open. In a third, make the request and inspect the client listener. If 18080 is occupied, inspect ss -lnt first and choose another free port.

client terminal B opens; terminal C verifies
# Terminal B:
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:18080:127.0.0.1:8080 lab-server

# Terminal C:
curl --max-time 5 -I http://127.0.0.1:18080/
ss -lnt | grep ':18080'

# Control check, from the client: this direct path need not work.
curl --max-time 3 http://"$LAB_HOST":8080/

HTTP پاسخ‌گرفته از 18080 و listener روی 127.0.0.1:18080 سمت client مدرک عبور tunnel است؛ درخواست مستقیم به IP ماشین روی 8080 باید ناموفق باشد. tunnel را با Ctrl+C ببند و دوباره 18080 را امتحان کن؛ شکست بعد از بستن نشان می‌دهد listener محلی به عمر SSH وابسته بود. سرویس 8080 هنوز در کنسول VM زنده است؛ بعد از آزمایش آن را همان‌جا با Ctrl+C متوقف کن.

An HTTP response from port 18080 and a client listener on 127.0.0.1:18080 prove the tunnel path; a direct request to the VM’s IP on 8080 should fail. Stop the tunnel with Ctrl+C and retry 18080: failure shows the local listener depended on SSH. The 8080 service is still running in the VM console; stop it there with Ctrl+C after the test.

برای -R، روی client یک web server آزمایشی loopback در terminal اول اجرا کن، در terminal دوم tunnel را بساز و از VM به پورت 18090 درخواست بده. با ss مطمئن شو سمت VM فقط loopback listen می‌کند. هر سه process با Ctrl+C جمع می‌شوند؛ بعد از آن 18080 و 18090 نباید listener داشته باشند.

For -R, run a loopback-only test server on client terminal one, create the tunnel in terminal two, and request port 18090 from the VM. Use ss to confirm the VM listens only on loopback. Stop all three foreground processes with Ctrl+C; afterwards ports 18080 and 18090 should have no listener.

reverse the socket map, then clean up
# Client terminal A:
python3 -m http.server 8090 --bind 127.0.0.1

# Client terminal B:
ssh -N -o ExitOnForwardFailure=yes -R 127.0.0.1:18090:127.0.0.1:8090 lab-server

# From another client terminal, run a request on the VM:
ssh lab-server 'ss -lnt | grep ":18090"; curl --max-time 5 -I http://127.0.0.1:18090/'

# Stop the test server and both tunnels with Ctrl+C. Confirm cleanup:
ss -lnt | grep -E ':(18080|18090)\b' || true
ssh lab-server 'ss -lnt | grep -E ":(8080|18090)\b" || true'

اگر -R با پیام policy رد شد، این خودش مدرک محدودیت سمت server است؛ GatewayPorts یا AllowTcpForwarding را برای دورزدنش تغییر نده. اگر listener ظاهر شد ولی curl شکست خورد، آدرس مقصد را از دید client دوباره بخوان. هیچ مرحله‌ای به بازکردن port برنامه در firewall نیاز ندارد.

If -R is rejected by policy, that is evidence of a server-side restriction; do not change GatewayPorts or AllowTcpForwarding to bypass it. If a listener appears but curl fails, re-check the destination from the client’s perspective. No step requires opening the application port in the firewall.

تمرین‌ها: دو هویت و دو جهت tunnel را قاطی نکنExercises: keep identities and tunnel directions straight

۱. کلید ناشناخته برای کدام طرف است؟1. Which side has the unknown key?

client می‌گوید host key ناشناخته است. آیا باید public key کاربر را به authorized_keys بفرستی؟

The client says the host key is unknown. Should you copy the user’s public key into authorized_keys?

پاسخSolution

نه. client، host key را در known_hosts نگه می‌دارد؛ public key کاربر در حساب server و فایل authorized_keys مجاز می‌شود. fingerprint میزبان را مستقل بررسی کن، بعد ورود کاربر را تنظیم کن.

No. The client records the host key in known_hosts; the user’s public key is authorised in the server account’s authorized_keys. Verify the host fingerprint independently, then configure user login.

۲. همکار چه چیزی می‌سازد؟2. What should the teammate create?

همکارت برای ورود به همان حساب درخواست کلید کرده. فایل .pub را می‌فرستی یا فایل بدون پسوند را؟

A teammate needs a key to log into the same account. Do you send the .pub file or the file without an extension?

پاسخSolution

هیچ private keyای را نفرست. همکار باید جفت کلید خودش را بسازد و public key خودش را ثبت کند؛ بعداً می‌توان فقط دسترسی او را لغو کرد.

Send no private key. The teammate should generate a separate pair and register their own public key; their access can then be revoked independently.

۳. Offering public key یعنی چه؟3. What does “Offering public key” prove?

بلافاصله بعد از این خط Permission denied (publickey) می‌آید. کدام مرحله موفق شد؟

Permission denied (publickey) follows immediately. Which step succeeded?

پاسخSolution

client کلید را انتخاب و offer کرده؛ server آن را برای این حساب نپذیرفته. user، کلید متناظر در authorized_keys، مجوز مسیر و policy سمت server را بررسی کن. offer شدن برابر ورود موفق نیست.

The client selected and offered a key; the server did not accept it for this account. Check the user, matching authorized_keys, path permissions, and server policy. An offered key is not a successful login.

۴. خطا پیش از امتحان کلید4. Rejected before the key is tried

UNPROTECTED PRIVATE KEY FILE می‌بینی. آیا باید sshd را restart کنی؟

You see UNPROTECTED PRIVATE KEY FILE. Should you restart sshd?

پاسخSolution

نه؛ این خطای client-side است. مجوز private key را بررسی و معمولاً به 600 محدود کن، بعد همان اتصال را تکرار کن. پیام تازه مرز بعدی را نشان می‌دهد.

No; this is a client-side error. Inspect the private-key permissions, usually restrict them to 600, and retry the same connection. The new message reveals the next boundary.

۵. timeout پیش از احراز هویت5. A timeout before authentication

SSH timeout می‌شود و هرگز Permission denied نمی‌بینی. چه لایه‌هایی را اول بررسی می‌کنی؟

SSH times out and you never see Permission denied. Which layers do you check first?

پاسخSolution

route، IP/port واقعی، listener با ss -lntp، firewall محلی و provider را جدا کن. timeout یگانه‌علت نیست؛ کلید را پیش از رسیدن به مرحلهٔ auth متهم نکن.

Separate route, actual IP/port, listener via ss -lntp, host firewall, and provider policy. A timeout has no unique cause; do not blame the key before authentication is reached.

۶. درگاه اشتباه6. The wrong port

سرور روی port 2222 گوش می‌دهد ولی config می‌گوید 22 و نتیجه refusal است. چه مدرکی را با هم مقایسه می‌کنی؟

The server listens on port 2222, while the config says 22 and gets refused. Which evidence do you compare?

پاسخSolution

پورت را با ss -lntp روی server ببین و با ssh -G alias روی client مقایسه کن؛ config را اصلاح و همان اتصال را تکرار کن. refusal مسئلهٔ listener/port است، نه مدرک ردشدن public key.

Inspect the server socket with ss -lntp and compare it with client settings from ssh -G alias; fix the config and retry. Refusal points to the listener/port boundary, not public-key rejection.

۷. کدام فایل کجا می‌رود؟7. Which file belongs where?

No. The scan does not authenticate the key; an on-path attacker could supply their own. Compare the fingerprint through a provider console or administrator using another channel.

Edit the matching Host block to set User learner, then re-read ssh -G. It reports resolved settings only; it does not prove that the account exists or the network is reachable.

۱۰. agent چند کلید پیشنهاد می‌دهد10. The agent offers too many keys

۱۱. agent چه چیزی را جایگزین نمی‌کند؟11. What does an agent not replace?

«با agent دیگر فایل private key و passphrase لازم نیست.» کدام بخش این جمله غلط است؟

“With an agent I no longer need a private-key file or passphrase.” What is wrong here?

پاسخSolution

agent امضای درخواست را برای کلیدهای بارشده مدیریت می‌کند؛ private key رمزگذاری‌شده همچنان وجود دارد و passphrase از آن محافظت می‌کند. agent هم خودش اختیار مهمی است و باید از session محافظت شود.

The agent handles signatures for loaded keys; the encrypted private key still exists and its passphrase protects it. The agent itself is also authority and the session must be protected.

۱۲. پرش بدون agent forwarding12. Jump without agent forwarding

برای رسیدن به private host، آیا bastion باید private key تو را داشته باشد؟

To reach a private host, does the bastion need your private key?

پاسخSolution

نه. ProxyJump با client و relay TCP کار می‌کند؛ private key از client خارج نمی‌شود و معمولاً agent-forwarding لازم نیست. bastion هنوز باید route و اجازهٔ اتصال به مقصد داشته باشد.

No. ProxyJump uses the client and relays TCP; the private key stays on the client and agent forwarding is usually unnecessary. The bastion still needs a route and permission to reach the destination.

۱۳. مقصد خصوصی از نظر کدام طرف resolve می‌شود؟13. From whose side is the private destination reached?

ProxyJump کار می‌کند اما private host پاسخ نمی‌دهد. کدام ارتباط را جدا تست می‌کنی؟

ProxyJump starts, but the private host does not respond. Which connection do you test separately?

پاسخSolution

مسیر bastion تا مقصد، resolve شدن HostName، route/firewall آن‌ها و پورت SSH را بررسی کن. رسیدن client به bastion فقط hop اول را ثابت می‌کند.

Check destination name resolution, the bastion-to-host route/firewall, and the SSH port. Client reachability to the bastion proves only the first hop.

۱۴. در -L کدام port محلی است؟14. Which port in -L is local?

-L 127.0.0.1:18080:127.0.0.1:8080 اجرا شده. مرورگر به کجا وصل می‌شود و 8080 از دید کجاست؟

You ran -L 127.0.0.1:18080:127.0.0.1:8080. Where does the browser connect, and from whose perspective is 8080?

پاسخSolution

مرورگر به port 18080 روی client وصل می‌شود؛ مقصد 8080 از سمت server باز می‌شود. bind کردن listener به loopback باعث می‌شود دیگر میزبان‌های شبکهٔ client به آن وصل نشوند.

The browser connects to client port 18080; the server side opens destination 8080. Binding the listener to loopback prevents other client-network hosts from reaching it.

۱۵. -R را از server آزمایش کن15. Test -R from the server side

برای -R 127.0.0.1:18090:127.0.0.1:8090 caller به کدام socket وصل می‌شود؟

For -R 127.0.0.1:18090:127.0.0.1:8090, which socket does the caller use?

پاسخSolution

caller از سمت server به 127.0.0.1:18090 وصل می‌شود؛ SSH درخواست را می‌برد به client و آنجا 127.0.0.1:8090 را باز می‌کند. حفظ bind loopback exposure را محدود می‌کند.

The caller on the server connects to 127.0.0.1:18090; SSH carries the request to the client, which opens 127.0.0.1:8090. Keeping the bind on loopback limits exposure.

۱۶. SOCKS مساوی VPN نیست16. SOCKS is not a VPN

یک browser از ssh -D می‌رود، ولی بقیهٔ برنامه‌ها مسیر عادی دارند. تناقض کجاست؟

One browser uses ssh -D, while other apps use normal routes. Where is the contradiction?

پاسخSolution

تضادی نیست؛ -D یک SOCKS endpoint به برنامهٔ proxy-aware می‌دهد و traffic کل سیستم را tunnel نمی‌کند. DNS و مقصدهای مجاز هم به تنظیم client و policy بستگی دارند.

There is none: -D provides a SOCKS endpoint to proxy-aware apps; it does not tunnel all system traffic. DNS and permitted destinations depend on client settings and policy.

۱۷. host key تغییر کرده17. The host key changed

OpenSSH mismatch هشدار می‌دهد. آیا ssh-keygen -R server را فوراً اجرا می‌کنی؟

OpenSSH warns of a host-key mismatch. Do you immediately run ssh-keygen -R server?

پاسخSolution

نه. اتصال را متوقف کن؛ دلیل تغییر را از console/provider یا مدیر مستقل تأیید و fingerprint جدید را مقایسه کن. فقط اگر rebuild/rotation معتبر بود، رکورد همان hostname/port را بردار و کلید جدید را بررسی کن.

No. Stop; verify the change through an independent console/provider or administrator and compare the new fingerprint. Only after a confirmed rebuild/rotation should you remove that hostname/port entry and verify the replacement key.

۱۸. یک ticket مشکوک18. A suspicious ticket

درخواست می‌گوید tunnel را روی 0.0.0.0 bind کن، ورود رمز را خاموش و همهٔ known_hosts را پاک کن. چه کاری می‌کنی؟

A request says to bind the tunnel to 0.0.0.0, disable password login, and clear all known_hosts. What do you do?

پاسخSolution

هیچ‌کدام را یک‌جا اجرا نکن. هدف و caller را روشن کن، bind را loopback نگه دار مگر exposure عمداً مجاز باشد، mismatch را مستقل بررسی کن؛ و server auth را فقط بعد از آزمون کلید از اتصال تازه و آماده‌کردن راه برگشت تغییر بده. هر تغییر را جدا verify کن.

Do not apply the bundle. Clarify the goal and caller, keep the bind on loopback unless exposure is authorised, investigate the mismatch independently, and change server authentication only after a fresh key login succeeds and recovery is ready. Verify each change separately.
