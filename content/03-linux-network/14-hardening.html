سخت‌سازی سرورServer hardening

یک VPS تازه داری و برنامه‌ات از اینترنت باز می‌شود. هنوز چیزی خراب نشده—اما چه کسی می‌تواند وارد شود؟ چه پورت‌هایی بازند؟ اگر یک daemon آسیب‌پذیر شد، با چه دسترسی‌ای اجرا می‌شود و تا کجا می‌تواند برسد؟ پیش از جواب‌دادن با یک فهرست آماده، بیایید مسیر حمله را روی همین ماشین ببینیم و هر سطح را با دلیل کوچک‌تر کنیم.

You have a fresh VPS, and your application is reachable from the internet. Nothing has gone wrong yet—but who can log in? Which ports are open? If a daemon is vulnerable, what privileges does it have and how far can it reach? Before applying a generic checklist, let’s map the attack path on this machine and reduce each exposed layer deliberately.

به‌جای برچسب «امن»، سناریوی واقعی بسازReplace “secure” with a concrete scenario

برای VPS اینترنتی، چند اتفاق را در نظر بگیر: کسی رمز ضعیف یا کلید لو‌رفته‌ای را امتحان می‌کند؛ سرویسی که لازم نیست به اینترنت دسترسی دارد؛ برنامه‌ای با آسیب‌پذیری اجرا می‌شود؛ یا خودمان یک تغییر را اشتباه می‌زنیم و دسترسی را می‌بندیم. سخت‌سازی احتمال یا اثر بعضی از این اتفاق‌ها را کم می‌کند؛ هیچ گزینه‌ای تضمین نمی‌دهد که سرور «امن» شده.

For an internet-facing VPS, consider a few realistic events: someone tries a weak or leaked credential; an unnecessary service is reachable; a vulnerable application is exploited; or an operator misconfigures access. Hardening lowers the likelihood or impact of some events. No single setting guarantees a “secure” server.

در نسخهٔ پشتیبانِ وضعیت فعلی، قبل از تغییر، پورت‌های گوش‌به‌زنگ، firewall، userهای ورود و مسیرهای داده را ثبت کن. بعد از هر اصلاح همان اندازه‌گیری را تکرار کن. «قانون را اضافه کردم» با «پورت ناخواسته دیگر از بیرون قابل دسترسی نیست» یکی نیست.

Before changing anything, record listening ports, firewall rules, login users, and data paths. Repeat the same measurements after each change. “I added a rule” is not the same claim as “the unwanted port is no longer reachable from outside.”

درخواست اینترنت تا داده چه مسیری دارد؟How does an internet request reach data?

از سطح اینترنت تا داده، هر مرز یک کنترل متناسب می‌خواهد؛ کنترل‌ها جای هم را نمی‌گیرند.

Each boundary from the internet to data needs an appropriate control; controls do not replace one another.

اینجا روی پایه‌های یک Ubuntu VPS تمرکز داریم. اگر توزیعت فرق دارد، نام package، سرویس، فایل تنظیم و defaultها را روی همان ماشین تأیید کن. دستورات تغییر دسترسی را روی سرور production بی‌برنامه اجرا نکن.

We focus on an Ubuntu VPS baseline. If your distribution differs, verify package, service, configuration-file, and default names on that host. Do not improvise access-control changes on production.

اول فهرست مواجهه؛ هنوز چیزی را خاموش نکنInventory exposure before disabling anything

از همان نشست فعلی، listenerها را ببین. ss -lntup TCP/UDPهای گوش‌به‌زنگ را فهرست می‌کند؛ ستون Local Address می‌گوید روی loopback، همهٔ interfaceها یا آدرس مشخص bind شده‌اند. -p نام process را می‌خواهد و ممکن است برای دیدنش دسترسی لازم باشد.

From your current session, inspect listeners. ss -lntup lists listening TCP/UDP sockets; Local Address shows loopback, all interfaces, or a specific address. The -p process detail may require elevated access.

before snapshot — inspect, do not kill
sudo ss -lntup
systemctl --type=service --state=running --no-pager
sudo ufw status verbose

وجود listener ثابت نمی‌کند از اینترنت قابل دسترسی است؛ provider firewall، host firewall، routing و bind address هم دخیل‌اند. نبودن listener هم نمی‌گوید بسته به‌روز یا بی‌نقص است. برای هر پورت بپرس مالک کدام سرویس است و واقعاً لازم است یا نه.

A listener does not prove internet reachability; provider firewall, host firewall, routing, and bind address also matter. No listener does not prove software is patched or flawless. For each port, identify its owner and whether it is actually needed.

اگر لازم است، از یک شبکهٔ جداگانه probe بگیر و نتیجه را کنار provider panel و ss بگذار. تست از خود سرور به localhost دسترسی عمومی را ثابت نمی‌کند. این فهرست «قبل» را می‌سازد تا نتیجهٔ بعد را با همان روش بسنجی.

When appropriate, probe from a separate network and compare with the provider panel and ss. A request from the server to localhost does not prove public reachability. This is your “before” inventory for a comparable after-check.

patch را به عادت نگهداری تبدیل کنTurn patching into a maintenance habit

نرم‌افزار قدیمی می‌تواند آسیب‌پذیری شناخته‌شده داشته باشد. روی Ubuntu ابتدا package list را تازه کن و upgradeهای موجود را ببین؛ در ماشین عملیاتی از backup/console و برنامهٔ تغییر غافل نشو، چون بعضی updateها نیاز به restart سرویس یا reboot دارند.

Old software can carry known vulnerabilities. On Ubuntu, refresh package lists and review available upgrades. On an operational server, plan backup, console access, and change timing: some updates require a service restart or reboot.

review first, then apply within your maintenance plan
sudo apt update
apt list --upgradable
sudo apt upgrade

اگر با SSH وصل هستی، قبل از upgrade نشست بازیابی و امکان reboot از provider را بدان. بعد از آن systemctl --failed، سرویس مهم، و reboot-required indicator توزیع را بررسی کن. خروجی موفق apt به‌تنهایی سلامت برنامه را ثابت نمی‌کند.

If connected over SSH, know your recovery session and provider reboot/console path before upgrading. Afterwards inspect systemctl --failed, critical services, and the distribution’s reboot-required indicator. A successful apt transaction alone does not prove application health.

Ubuntu بسیاری از نصب‌های Server را با unattended-upgrades برای security update روزانه آماده می‌کند، ولی نسخه و configuration خودت را ببین؛ auto-update ممکن است package نصب کند یا reboot سیاست‌محور بخواهد. log را در /var/log/unattended-upgrades/ بررسی و cadence/اعلان/پنجرهٔ reboot را متناسب تنظیم کن. خودکارسازی بدون دیدن نتیجه، نگهداری کامل نیست.

Many Ubuntu Server installations use unattended-upgrades for daily security updates, but verify your release and configuration. Automatic updates can install packages and may require a policy-controlled reboot. Inspect /var/log/unattended-upgrades/ and set cadence, notification, and reboot windows appropriately. Automation without checking outcomes is not complete maintenance.

حساب روزمره با root یکی نباشدDo not use root as your everyday identity

یک حساب عادی برای کار بساز و فقط کارهای مدیریتی را با sudo بالا ببر. این کار هر خطری را حذف نمی‌کند—حساب sudoدار همچنان اختیار زیادی دارد—اما فرمان عادی و daemonهای کاربر را از root جدا می‌کند و برای audit یک هویت روشن می‌دهد.

Use a regular account for day-to-day work and elevate only administrative commands with sudo. This does not erase risk—a sudo-capable account is still powerful—but it separates routine commands and user processes from root and gives actions a clearer identity.

create an administrative account on Ubuntu
sudo adduser opsadmin
sudo usermod -aG sudo opsadmin
id opsadmin
sudo -l -U opsadmin

در id گروه sudo را می‌بینی؛ sudo -l مجوز واقعی را نشان می‌دهد، اما به معنی تأیید هویت آن شخص نیست. قبل از بستن root login مطمئن شو همین user می‌تواند با SSH key وارد و با sudo کار کند. حساب سرویس را وارد گروه sudo نکن.

The id output should show the sudo group; sudo -l shows actual authorization, not the person’s identity. Before disabling root login, confirm this user can authenticate with an SSH key and use sudo. Never add an application service account to sudo.

کلید داری؟ اول در نشست دوم ثابتش کنHave a key? Prove it in a second session first

کلید عمومی را به حساب مدیریتی اضافه کن و نشست جداگانه‌ای با همان key آزمایش کن. کلید private را به سرور یا repository کپی نکن؛ فقط public key در authorized_keys می‌رود. passphrase و نگهداری امن کلید client را هم در نظر بگیر.

Add the public key to the administrative account and test it in a separate session with that key. Never copy the private key to the server or repository; only the public key belongs in authorized_keys. Protect the client key and consider a passphrase.

from your client — key install and separate login
ssh-copy-id opsadmin@SERVER
ssh -o IdentitiesOnly=yes -i ~/.ssh/opsadmin_key opsadmin@SERVER

روی Ubuntu ممکن است config در /etc/ssh/sshd_config.d/ باشد و includeها قبل از مقدارهای بعدی خوانده شوند؛ مقدار مؤثر را با ابزار همان نسخه بررسی کن. root login و password authentication را بر اساس threat model و روش دسترسی سازمان تصمیم بگیر، نه چون «همه همین را می‌بندند».

On Ubuntu, configuration may live in /etc/ssh/sshd_config.d/, and include ordering can affect which value wins. Check effective settings with the installed version’s tools. Decide on root login and password authentication from your threat model and access policy, not because “everyone disables them.”

اگر تصمیم گرفتی password login را ببندی، اول key login را در نشست دوم ثابت کن، console provider را باز نگه دار و تنظیم را مرحله‌ای تغییر بده. PermitRootLogin no معمولاً مستقیم root login را می‌بندد؛ PasswordAuthentication no password auth را، اما ممکن است روش‌های دیگر auth جدا باشند. «دسترسی قطع است» را با یک دستور روی تنها نشست خودت آزمایش نکن.

If you decide to disable password login, first prove key login in a second session and keep the provider console available. PermitRootLogin no disallows direct root login; PasswordAuthentication no disables password authentication, but other methods may be configured separately. Never test access removal by risking your only session.

قانون را قبل از فعال‌کردن، از سمت خودت بخوانRead the rule before enabling the firewall

روی Ubuntu معمولاً ufw frontend سادهٔ firewall است؛ VPS ممکن است firewall جدا در پنل provider هم داشته باشد. هر دو لایه را در inventory ثبت کن. پیش از فعال‌کردن policy ورودی، rule مربوط به SSH و پورت واقعی‌اش را اضافه کن و اگر می‌توانی SSH را فقط از IP/VPN مدیریتی محدود کن.

On Ubuntu, ufw is a common simple firewall frontend; a VPS may also have a separate provider firewall. Record both layers. Before enabling an incoming policy, add the SSH rule for its actual port and, where feasible, restrict administration to a known IP/VPN.

inspect, allow required access, then enable
sudo ufw status verbose
sudo ufw allow OpenSSH
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw --dry-run enable
sudo ufw enable
sudo ufw status numbered

اگر SSH روی پورت دیگری است یا provider profile OpenSSH ندارد، rule مناسب همان پورت را اضافه کن؛ rule را با session دوم و پنل console verify کن. سپس فقط پورت‌هایی را باز کن که سرویس واقعاً لازم دارد. UFW IPv6 و provider filtering را هم بررسی کن؛ یک rule IPv4 تنها، همهٔ ورودی‌ها را لزوماً پوشش نمی‌دهد.

If SSH uses another port or the provider lacks the OpenSSH profile, add a rule for the actual port; verify using a second session and provider console. Then open only ports required by real services. Check IPv6 and provider filtering too; one IPv4 rule may not cover every ingress path.

تغییر firewall دسترسی را می‌تواند قطع کند؛ policy را بی‌دلیل disable نکن. خروجی ufw status numbered نشان می‌دهد چه rule ثبت است، نه اینکه از اینترنت واقعاً عبور می‌کند. probe خارجی و پنل provider را کنار آن بسنج.

Firewall changes can sever access; do not disable the policy casually. ufw status numbered shows configured rules, not actual internet reachability. Compare it with an external probe and provider settings.

هر listener باید صاحب و دلیل داشته باشدEvery listener needs an owner and a reason

فهرست اولیهٔ ss -lntup را با سرویس‌های فعال مقایسه کن. پورت database، cache یا admin panel معمولاً نباید بی‌دلیل روی همهٔ interfaceهای عمومی گوش دهد؛ اما سرویس را فقط از روی اسم خاموش نکن. اول dependency، owner و روش rollback را پیدا کن.

Compare your initial ss -lntup inventory with active services. A database, cache, or admin panel usually should not listen publicly without a clear need—but do not disable a service based on its name alone. Find dependencies, owner, and rollback path first.

inspect before disabling a confirmed unused unit
sudo ss -lntup
systemctl status SERVICE --no-pager
systemctl list-dependencies SERVICE
sudo systemctl disable --now SERVICE

فرمان آخر فقط وقتی است که service دقیقاً شناسایی شده، واقعاً لازم نیست و راه بازگشت داری؛ روی production به‌جای placeholder اسم واقعی نگذار بی‌آنکه بررسی کنی. بعد دوباره ss و سلامت برنامه را بسنج. سرویس خاموش‌شده ممکن است وابستگی دیگری را هم از کار بیندازد.

The last command is only for a confirmed unnecessary service with a recovery path; never replace the placeholder on production without investigation. Recheck ss and application health afterwards. Disabling a service may affect dependents.

service لازم است؛ root بودنش لازم نیستThe service is needed; root may not be

اگر برنامه فقط فایل‌های خودش را می‌خواند و روی یک مسیر مشخص می‌نویسد، برای همه‌چیز root نخواهد. account جدا با shell غیرتعاملی و دسترسی محدود بساز؛ مالکیت مسیر داده را دقیق تعیین کن. chmod 777 مرز دسترسی را پاک می‌کند، نه اینکه permission را درست طراحی کند.

If an application reads its own files and writes to a specific path, it may not need root. Create a separate account with a non-interactive shell and narrow access; assign ownership only where required. chmod 777 removes an access boundary instead of designing correct permissions.

inspect identity and targeted file access
id appuser
getent passwd appuser
namei -l /srv/myapp/data
stat -c '%A %U:%G %n' /srv/myapp /srv/myapp/data

ببین کدام component باید بخواند یا بنویسد، بعد فقط همان دایرکتوری را به group/user سرویس بده و mode محدود بگذار. namei -l permission هر ancestor را نشان می‌دهد؛ دسترسی فایل به مجوز همهٔ مسیر نیاز دارد. تست با user خود برنامه و یک فایل بی‌خطر انجام بده.

Identify which component must read or write, then grant that user/group only the required directory with a narrow mode. namei -l shows permissions for each ancestor; accessing a file depends on every path component. Test as the service user with a harmless file.

Fail2ban کمک می‌کند؛ جای کنترل SSH را نمی‌گیردFail2ban can help; it does not replace SSH controls

اگر logها تلاش‌های ناموفق تکراری دارند، fail2ban می‌تواند طبق filter/jail آدرس‌های تکرارشونده را موقتاً ban کند. این لایهٔ اختیاری است: حمله را متوقفِ بنیادی نمی‌کند، credential امن نمی‌سازد و اگر allowlist یا تشخیص IP پشت NAT اشتباه باشد ممکن است خودت را ban کنی.

If logs show repeated failed attempts, fail2ban can temporarily ban sources according to configured filters and jails. It is optional: it does not fundamentally stop attacks, create strong credentials, or guarantee correct source identification; a bad allowlist or NAT assumption can ban you.

قبل از نصب، ببین firewall backend و jailهای توزیع چه هستند، allowlist را با دقت بساز و recovery console داشته باش. نصب‌شدن package یا بالا بودن service ثابت نمی‌کند jail فعال است یا rule واقعاً اعمال شده؛ status و firewall state را بخوان. rate limiting هیچ‌وقت مجوز بازگذاشتن password ضعیف نیست.

Before installing, inspect the firewall backend and distribution jails, configure any allowlist carefully, and keep console recovery. An installed package or active service does not prove a jail is enabled or enforcement works; inspect jail and firewall state. Rate limiting is never a reason to keep weak passwords.

امنیت فقط ورود و پورت نیستSecurity is more than logins and ports

سخت‌سازی بدون بازیابی و پیگیری ناقص می‌ماند. نسخهٔ پشتیبان را بیرون از همان failure domain نگه دار و یک restore آزمایشی انجام بده؛ backupی که باز نشده، مسیر برگشت اثبات‌شده نیست. log احراز هویت و سرویس را نگه دار، اما retention و دسترسی‌اش را کنترل کن.

Hardening without recovery and follow-up is incomplete. Keep backups outside the same failure domain and perform a restore test; an untested backup is not a proven recovery path. Retain authentication and service logs with controlled access and retention.

ساعت هماهنگ برای مرتب‌کردن log و بررسی رخداد مهم است. روی Ubuntu وضعیت را با timedatectl ببین؛ releaseهای جدید ممکن است chrony و قدیمی‌ترها systemd-timesyncd داشته باشند. از تغییر NTP source روی سرور production بدون فهم policy شبکه خودداری کن.

A synchronized clock matters for correlating logs and incidents. On Ubuntu, inspect timedatectl; newer releases may use chrony while older ones may use systemd-timesyncd. Do not change production time sources without understanding network policy.

همین inventory کوچک را دوره‌ای تکرار کن: release/updateها، پورت و owner، firewall بیرونی/داخلی، loginها، permission داده، backup و وضعیت log/time. هدف بیشترکردن شمار تیک‌ها نیست؛ باید بدانی هر کنترل از کدام سناریو کم می‌کند و چه چیزی را پوشش نمی‌دهد.

Repeat a small inventory periodically: release/updates, ports and owners, provider/host firewalls, logins, data permissions, backups, and log/time health. The goal is not maximizing checked boxes; understand which scenario each control reduces and what it leaves uncovered.

خرابی عمدی SSH؛ راه برگشت را باز بگذارA deliberate SSH failure—keep recovery open

این تمرین را فقط روی VM disposable با snapshot و console provider اجرا کن؛ نه VPS تنها یا production. دو نشست SSH با حساب عادی و key باز نگه دار. در نشست اول فایل دقیق تنظیم را backup بگیر. بعد یک policy معتبر اما اشتباه می‌گذاریم که حساب مجاز را از allowlist جا می‌اندازد؛ sshd -t syntax را می‌سنجد اما نمی‌فهمد تو باید مجاز بمانی.

Run this only on a disposable VM with a snapshot and provider console—not your only VPS or production. Keep two SSH sessions open using a regular key-authenticated account. Back up the exact config first. We will add a syntactically valid but wrong allowlist that omits our user; sshd -t checks syntax, not whether you still belong in the policy.

preflight — this path must be unused
test ! -e /etc/ssh/sshd_config.d/99-codenames-lab.conf && echo "path is free"

اگر پیام «path is free» ندیدی، متوقف شو و مسیر را بررسی کن؛ فایل موجود را overwrite نکن. فقط پس از تأیید خالی‌بودن مسیر، allowlist حساب SSH فعلی را بساز و نسخهٔ سالم را backup بگیر.

If you do not see “path is free,” stop and investigate; do not overwrite an existing file. Only after confirming the path is unused, create an allowlist for the current SSH user and back up the known-good version.

create the known-good value and back it up
admin_user=$(id -un)
printf 'AllowUsers %s\n' "$admin_user" | sudo tee /etc/ssh/sshd_config.d/99-codenames-lab.conf
sudo chmod 600 /etc/ssh/sshd_config.d/99-codenames-lab.conf
sudo sshd -t
sudo cp -a /etc/ssh/sshd_config.d/99-codenames-lab.conf /tmp/99-codenames-lab.conf.good

اکنون مقدار AllowUsers را عمداً به نام خیالی nobody-lab تغییر بده. syntax را تست کن؛ چون directive معتبر است، ممکن است sshd -t بی‌خطا تمام شود. این یعنی parser قبول کرده، نه اینکه policy امن یا login تست شده باشد.

Now change AllowUsers to the fictional nobody-lab. Test syntax; because the directive is valid, sshd -t may succeed. That proves parser acceptance—not safe policy or working login.

syntax check is necessary but not sufficient
sudo sshd -t

در VM آزمایشی reload کن و از نشست دوم login تازه بگیر. اگر رد شد، نشست اول را نبند و از آن یا provider console مقدار را برگردان؛ یک session فعال ممکن است بعد از reload هم باز بماند و راه اصلاح بدهد. بعد با sshd -t و نشست تازه دوباره ثابت کن دسترسی برگشته. روی production این fault را تزریق نکن.

On the disposable VM, reload and attempt a fresh login in the second session. If denied, keep the first session open and revert from it or use the provider console; an existing session may remain available after reload. Then verify recovery with sshd -t and a new login. Never inject this fault into production.

فرمان‌های مرحلهٔ خطا و برگشتFault and recovery commands

در VM یک‌بارمصرف، بعد از backup، مقدار را به نام خیالی عوض کن؛ reload را فقط بعد از syntax test انجام بده و login تازه را از client آزمایش کن.

On the disposable VM, after taking the backup, change the value to the fictional account; reload only after the syntax test and try a fresh client login.

fault injection — disposable VM only
sudoedit /etc/ssh/sshd_config.d/99-codenames-lab.conf
# Set: AllowUsers nobody-lab
sudo sshd -t
sudo systemctl reload ssh.service

اگر login تازه رد شد، نشست قبلی را نبند. از همان نشست یا console نسخهٔ سالم را برگردان، reload کن، و فقط پس از ورود تازهٔ موفق فایل آزمایش را حذف کن.

If the fresh login is denied, keep the old session open. Restore the known-good copy from that session or the console, reload, and remove the lab file only after a fresh login succeeds.

restore, verify, then remove only the file created for this lab

۱۸ تصمیم؛ یک تهدید، یک مدرک18 decisions: one threat, one proof

۱. پورت ناشناس1. An unknown port

ss پورت ۹۰۰۰ را روی 0.0.0.0 نشان می‌دهد. پیش از بستن چه می‌کنی؟

ss shows port 9000 on 0.0.0.0. What precedes blocking it?

پاسخSolution

PID، unit، owner، dependency و کاربرد را پیدا کن؛ سپس دسترسی را از بیرون و هر دو firewall بسنج. bind عمومی نشانهٔ exposure است، نه اثبات reachability اینترنت.

Identify PID, unit, owner, dependencies, and purpose; then test reachability across both firewalls. A public bind signals exposure, not internet reachability by itself.

۲. دو لایهٔ firewall2. Two firewall layers

پنل provider اجازه می‌دهد، UFW رد می‌کند. آیا ruleها همدیگر را خنثی می‌کنند؟

The provider allows a port, but UFW denies it. Do the rules cancel out?

پاسخSolution

معمولاً هر دو لایه باید اجازه دهند؛ جداگانه بررسی و از شبکه‌ای بیرونی probe کن. IPv4 و IPv6 را هم ببین.

Usually both layers must allow traffic; inspect separately and probe externally. Check IPv4 and IPv6 too.

۳. listener روی loopback3. A loopback listener

127.0.0.1:5432 چه چیزی را نشان می‌دهد و چه چیزی را پنهان می‌کند؟

What does 127.0.0.1:5432 show, and what does it leave open?

پاسخSolution

روی loopback همان میزبان bind شده، نه interface عمومی؛ local users و tunnel/proxy احتمالی هنوز مهم‌اند. public reachability را با چند مدرک بسنج.

It is bound to the host loopback, not a public interface; local users and tunnels/proxies still matter. Verify public reachability with multiple clues.

۴. root برای سرعت4. Root for convenience

همکار می‌خواهد هر روز با root کار کند. چه جایگزینی و چه caveatی می‌دهی؟

A teammate wants to work as root every day. What alternative and caveat do you offer?

پاسخSolution

حساب نام‌دار عادی و sudo فقط برای کار مدیریتی؛ با id/sudo -l دسترسی را verify کن. sudoدار همچنان اختیار گسترده دارد.

Use a named regular account and sudo only for administrative work; verify with id/sudo -l. A sudo user still has broad authority.

۵. کلید در نشست جاری5. A key in the current session

کلید در نشست فعلی جواب داد. می‌توانی password login را ببندی و خارج شوی؟

The key worked in your current session. Can you disable password login and disconnect?

پاسخSolution

نه؛ نشست دوم تازه، sudo و recovery console را verify کن، نشست اول را نگه دار، config را test و مرحله‌ای reload کن.

No; verify a fresh second session, sudo, and recovery console; keep the first session, test the config, and reload carefully.

۶. دو directive SSH6. Two SSH directives

PermitRootLogin no و PasswordAuthentication no یک کار می‌کنند؟

Do PermitRootLogin no and PasswordAuthentication no do the same thing?

پاسخSolution

نه؛ یکی ورود مستقیم root و دیگری auth مبتنی بر password را محدود می‌کند. effective config و روش‌های دیگر auth را بررسی کن.

No; one restricts direct root login, the other password authentication. Inspect effective configuration and other auth methods.

۷. AllowUsers اشتباه7. A wrong AllowUsers

sshd -t موفق است اما allowlist حساب تو را جا انداخته. آیا ورود بعدی کار می‌کند؟

sshd -t passes, but the allowlist omits your account. Will the next login work?

پاسخSolution

تضمینی نیست؛ syntax درست است ولی policy ممکن است ردت کند. نشست/console را نگه دار و فقط در VM disposable login تازه را بیازما.

No guarantee; syntax is valid while policy may deny you. Keep a session/console and test a fresh login only on a disposable VM.

۸. sshd -t خطا می‌دهد8. sshd -t reports an error

بعد از ویرایش config parser خطا می‌دهد. restart کنی تا اعمال شود؟

After editing, the parser reports an error. Should you restart to apply it?

پاسخSolution

نه؛ تغییر را اصلاح یا backup را برگردان و دوباره syntax-test کن. فقط بعد از موفقیت و آماده‌بودن راه برگشت reload کن.

No; fix the change or restore the backup and run the syntax test again. Reload only after it passes and recovery is ready.

۹. deny incoming9. Deny incoming

هنوز rule SSH نداری ولی می‌خواهی UFW را فعال کنی. ترتیب امن؟

No SSH rule exists yet, but you want to enable UFW. What is the safe order?

پاسخSolution

اول پورت SSH واقعی را allow و dry-run/status را ببین، console و نشست دوم را آماده کن، بعد فعال و از بیرون verify کن.

Allow the actual SSH port, inspect dry-run/status, prepare console and a second session, then enable and verify externally.

۱۰. سرویس sudo دارد10. A service has sudo

daemon فقط یک پوشه می‌نویسد ولی user آن sudoدار و interactive است. دو کاهش اختیار؟

A daemon writes one directory, but its account has sudo and an interactive shell. Name two privilege reductions.

پاسخSolution

sudo را بردار و اگر سازگار است shell را nologin کن؛ فقط مسیر write لازم را به user/group سرویس بده و تست کن.

Remove sudo and use a nologin shell if compatible; grant the service user/group only the required writable path and test.

۱۱. ancestor غیرقابل‌دسترسی11. An inaccessible ancestor

mode خود config مناسب است اما service آن را نمی‌خواند. چه چیزی را بررسی می‌کنی؟

The config mode looks right, but the service cannot read it. What do you inspect?

پاسخSolution

namei -l را برای کل مسیر اجرا کن؛ هر directory به execute/traverse نیاز دارد. فقط ancestor مسئله‌دار را اصلاح کن.

Run namei -l for the full path; each directory needs traverse permission. Fix only the offending ancestor.

۱۲. chmod -R 77712. chmod -R 777

چرا این فرمان برای رفع خطا راه‌حل خوبی نیست؟

Why is this not a sound permission fix?

پاسخSolution

همهٔ userها می‌توانند بنویسند/اجرا کنند و recursion فایل‌های مختلف را بدتر می‌کند. owner، group و مسیر نوشتنی واقعی را پیدا کن.

Every user can write/execute, and recursion can damage mixed files. Identify the correct owner, group, and actual writable path.

۱۳. service ناشناخته13. An unfamiliar service

unitای را نمی‌شناسی و می‌خواهی disable --now کنی. پیش از تغییر چه می‌خوانی؟

You want to disable --now an unfamiliar unit. What do you inspect first?

پاسخSolution

description/package، process، dependency، listener و نقش برنامه را پیدا کن؛ backup/rollback را آماده و بعد در change window آزمایش کن.

Check description/package, process, dependencies, listener, and application role; prepare rollback, then test in a change window.

۱۴. apt موفق شد14. apt succeeded

upgrade بدون error تمام شد. چه شاهد دیگری می‌خواهی؟

The upgrade finished without error. What evidence do you still need?

پاسخSolution

unitهای failed، سلامت application و reboot-required را بررسی کن؛ package transaction موفق، سرویس سالم را تضمین نمی‌کند.

Check failed units, application health, and reboot requirements; a successful package transaction does not guarantee a healthy service.

۱۵. update خودکار15. Automatic updates

unattended-upgrades فعال است. چه چیزهایی را بازبینی می‌کنی؟

unattended-upgrades is enabled. What do you review?

پاسخSolution

version و policy، log، reboot policy، packageهای خارج از origin مجاز و health برنامه؛ auto-update جای نظارت را نمی‌گیرد.

Release/policy, logs, reboot policy, packages outside allowed origins, and application health; automatic updates do not replace monitoring.

۱۶. fail2ban فعال است16. fail2ban is active

unit فعال است ولی SSH jail در status نیست. نتیجه؟

The unit is active, but no SSH jail appears. What follows?

پاسخSolution

فعال‌بودن daemon اثربخشی jail را ثابت نمی‌کند؛ filter، log source و firewall action را بررسی کن. این ابزار جای key auth/patch نیست.

An active daemon does not prove an effective jail; inspect filter, log source, and firewall action. It does not replace keys or patching.

۱۷. backup بدون restore17. Backup without restore

فایل backup هر شب حاضر است. کدام ادعا هنوز ثابت نشده؟

A backup file appears nightly. What claim remains unproven?

پاسخSolution

بازیابی‌پذیری و سازگاری. در محیط جدا restore کن، دادهٔ شناخته‌شده را validate و زمان بازیابی را ثبت کن.

Recoverability and consistency. Restore separately, validate known data, and record recovery time.

۱۸. تحویل بازبینی18. Review handoff

همکارت می‌خواهد وضعیت VPS را review کند. چه inventory‌ای می‌دهی و از چه ادعایی پرهیز می‌کنی؟

A teammate is reviewing the VPS. What inventory do you provide, and what claim do you avoid?

پاسخSolution

release/patch، userها، SSH/recovery، port و owner، دو firewall، privilege/permission داده، backup/restore، log/time و شواهد قبل/بعد را همراه دلیل بده. به‌جای «امن است»، پوشش و محدودیت هر کنترل را بنویس.

Provide release/patches, users, SSH/recovery, ports/owners, both firewalls, privileges/data permissions, backup/restore, log/time, and before/after evidence with rationale. State control coverage and limits instead of claiming “secure.”
