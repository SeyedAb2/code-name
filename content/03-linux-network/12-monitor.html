مانیتورینگ منابع و دیسکResource and disk monitoring

سرور کند شده و هشدار می‌گوید دیسک دارد پر می‌شود. یک نفر می‌گوید CPU؛ یکی دیگر RAM؛ نفر سوم می‌خواهد پوشه‌ای را پاک کند. پیش از هر تغییری باید بفهمیم کدام منبع واقعاً زیر فشار است—و چه چیزی فقط هم‌زمان با مشکل دیده شده.

The server is slow and an alert says the disk is filling up. One person blames CPU, another RAM, and a third wants to delete a directory. Before changing anything, identify which resource is actually under pressure—and what merely happened at the same time.

هشدار «دیسک پر است»؛ کدام دیسک؟“Disk full”—which disk?

در فصل قبل با journalctl بازهٔ خطا را پیدا کردیم. حالا log می‌گوید نوشتن فایل شکست خورده. علت شاید CPU، حافظه، I/O، بلوک یا inode باشد. اول این snapshot خواندنی را ثبت کن.

In the previous chapter, we scoped the failure with journalctl. Now a log says a write failed. The cause may be CPU, memory, I/O, blocks, or inodes. Start with this read-only snapshot.

incident snapshot
date --iso-8601=seconds
uptime
df -hT
df -i
free -h

uptime loadهای ۱، ۵ و ۱۵ دقیقه؛ df -hT بلوک و نوع filesystem؛ df -i inode؛ و free -h حافظه و swap را نشان می‌دهد. خروجی علت را ثابت نمی‌کند، اما mount مشکوک را پیدا می‌کند—شاید /، /var، volume یا tmpfs باشد.

uptime reports 1-, 5-, and 15-minute load; df -hT shows blocks and filesystem type; df -i inodes; and free -h memory and swap. This does not prove a cause, but identifies a suspect mount—perhaps /, /var, a volume, or tmpfs.

فعلاً پاک نکنDo not clean up yet

خروجی را با زمان نگه دار. حذف ممکن است مدرک یا دادهٔ برنامه را ببرد و حتی فضا را آزاد نکند. اول مصرف‌کننده و filesystem را پیدا کن.

Keep the output with its timestamp. Deletion may remove evidence or application data and may not free space. Identify the filesystem and consumer first.

هر ابزار برای یک سؤالA different question for each tool

پردازه منتظر CPU است؟ RAM کمیاب شده؟ storage دیر جواب می‌دهد؟ بلوک یا inode تمام شده؟ ابزارها سرنخ‌اند، نه حکم نهایی.

Is a task waiting for CPU? Is RAM scarce? Is storage slow? Are blocks or inodes exhausted? Tools are clues, not verdicts.

هر شاخه را جدا بسنج؛ عددها را کنار زمان و بار واقعی برنامه تفسیر کن.

Measure each branch separately; interpret values alongside time and real workload.

روی VM اول وضعیت عادی را می‌گیریم، بعد یک تغییر کوچک و برگشت‌پذیر می‌دهیم. workload بی‌نهایت، fork bomb یا پرکردن filesystem واقعی نداریم.

On a VM, we first capture a baseline, then make one small reversible change. No unbounded workloads, fork bombs, or filling a real filesystem.

load بالا لزوماً CPU نیستHigh load is not necessarily CPU

load average شمار taskهای runnable و در انتظار غیرقابل‌وقفه، معمولاً I/O، را در طول زمان بازتاب می‌دهد؛ درصد CPU نیست. load برابر ۲ روی یک هسته و ۳۲ هسته یکسان نیست. nproc را کنار uptime بخوان؛ نسبت فقط سرنخ اولیه است.

Load average reflects runnable and uninterruptibly waiting tasks—often I/O—over time; it is not CPU percentage. A load of 2 differs on one core and 32 cores. Read nproc alongside uptime; the ratio is only an initial clue.

compare processors and activity
uptime
nproc
top

در top، us/sy کار user/kernel، id بیکاری و wa انتظار I/O گزارش‌شده است. task در R runnable و D معمولاً منتظر غیرقابل‌وقفه است. load بالا همراه idle نزدیک صفر CPU را مظنون می‌کند؛ wa یا D بررسی I/O را توجیه می‌کند. snapshot علت را ثابت نمی‌کند؛ روند و ps را ببین. htop ممکن است نصب نباشد؛ نصب ابزار روی production نیازمند مجوز است.

In top, us/sy are user/kernel work, id idle time, and wa reported I/O wait. R is runnable; D is usually uninterruptible wait. High load with near-zero idle makes CPU a suspect; wa or D warrants checking I/O. A snapshot does not prove cause; inspect trends and ps. htop may be absent; installing tools on production requires authorization.

RAM را از روی free قضاوت نکنDo not judge RAM by free alone

Linux از RAM بلااستفاده برای page cache و buffer استفاده می‌کند. در free -h، available معمولاً تخمین مفیدتری از حافظهٔ قابل‌استفاده است؛ نسخه‌های قدیمی ممکن است این ستون را نداشته باشند یا متفاوت حساب کنند.

Linux uses otherwise idle RAM for page cache and buffers. In free -h, available is usually a more useful estimate of memory that can be used; older versions may lack it or calculate it differently.

memory and process snapshot
free -h
vmstat 1 5
ps -eo pid,ppid,comm,%cpu,%mem,rss --sort=-%mem | head -n 12

در vmstat ردیف اول معمولاً میانگین از boot است؛ بعدی‌ها interval تازه‌اند. si/so swap-in/out هستند. swap پیوسته همراه available پایین مهم‌تر از swpd غیرصفرِ قدیمی است. RSS اندازهٔ resident تقریبی است، نه مالکیت انحصاری صفحه‌های مشترک؛ ps هم ممکن است رشد کوتاه را از دست بدهد.

In vmstat, the first row commonly averages since boot; later rows are fresh intervals. si/so report swap-in/out. Sustained swapping with low available matters more than historical nonzero swpd. RSS is approximate resident size, not exclusive ownership of shared pages; ps can miss brief growth.

در container/cgroup، آمار host را با limit قاطی نکن؛ free معمولاً کل میزبان را نشان می‌دهد. OOM را با log kernel و شواهد cgroup/container و زمان بسنج؛ مصرف بالا به‌تنهایی OOM نیست—فصل قبل این تفاوت را گفت.

For containers/cgroups, do not confuse host metrics with the limit; free commonly shows the whole host. Diagnose OOM with kernel logs, cgroup/container evidence, and event time; high usage alone is not OOM—the previous chapter covered that distinction.

CPU بیکار است ولی برنامه مکث می‌کندThe CPU is idle, yet the app stalls

اگر wa بالاست storage را بررسی کن؛ این عدد device خاصی را معرفی نمی‌کند. iostat از sysstat می‌آید و ممکن است نصب نباشد. نصب روی production را با مجوز و برنامه انجام بده.

If wa is high, investigate storage; it does not identify a specific device. iostat comes from sysstat and may be absent. Install on production only with authorization and a plan.

if available — map the device to the mount
iostat -xz 1 3
findmnt -T /var
lsblk -f

نمونه‌های بعد از اول را بخوان؛ گزارش نخست در بسیاری نسخه‌ها از زمان boot است. await میانگین صف و سرویس، aqu-sz اندازهٔ متوسط صف است. %util نزدیک ۱۰۰٪ در دستگاه serial می‌تواند اشباع باشد، اما برای SSD/RAID موازی به‌تنهایی سقف کارایی را ثابت نمی‌کند. device درست را به mount وصل کن.

Read samples after the first; on many versions the initial report is since boot. await is average queue-plus-service time, aqu-sz average queue size. %util near 100% may indicate saturation on serial devices, but alone does not establish a ceiling on parallel SSD/RAID. Map the correct device to its mount.

اگر iostat نیست، vmstat، top، findmnt و آمار VM/provider را کنار هم بخوان. I/O بالا شاید workload عادی باشد، نه علت کندی.

If iostat is absent, combine vmstat, top, findmnt, and VM/provider metrics. High I/O may be expected workload, not the cause.

df پر است؛ du چیزی پیدا نمی‌کندdf is full, but du finds little

mount را از df -hT بردار. df filesystem را می‌سنجد و du مسیرهای قابل پیمایش را جمع می‌کند؛ این دو نما یکی نیستند. du -xhd1 روی filesystem می‌ماند و عمق را محدود می‌کند، ولی permission ناکافی می‌تواند پوشه‌ای را پنهان کند.

Take the mount from df -hT. df measures the filesystem; du totals traversable paths. They are different views. du -xhd1 stays on one filesystem and limits depth, but missing permissions can hide directories.

compare one mount
df -hT /var
df -i /var
sudo du -xhd1 /var 2>/dev/null | sort -h | tail

اگر بلوک آزاد است ولی df -i صددرصد، ساخت فایل ممکن است با No space left on device شکست بخورد چون inode تمام شده؛ فایل ریز هم inode می‌گیرد. درصد هر دو را برای یک mount بخوان.

If blocks remain but df -i is at 100%, file creation may fail with No space left on device because inodes are exhausted; tiny files consume inodes too. Compare both metrics for one mount.

سرنخ «df پر، du خالی»The “df full, du empty” clue

اگر process فایل باز را unlink کند، نام ناپدید می‌شود اما blockها تا بسته‌شدن آخرین descriptor آزاد نمی‌شوند؛ مثلاً برنامه پس از حذف log همچنان روی descriptor قدیمی می‌نویسد. lsof +L1 فایل‌های باز با link count کمتر از ۱ را پیدا می‌کند؛ شاید root یا نصب lsof لازم باشد. process واقعی را بی‌برنامه نکش.

If a process unlinks an open file, its name disappears but blocks remain until the last descriptor closes—for example, an application keeps writing after its log pathname was removed. lsof +L1 selects open files with link count below one; root or the lsof package may be needed. Do not blindly kill a real process.

آزمایش محدود: ۶۴ مگابایت، نه دیسک میزبانBounded experiment: 64 MB, not the host disk

فقط روی VM آزمایشی با دسترسی root. tmpfs سقف ۶۴ مگابایت و inode محدود دارد و از RAM/swap استفاده می‌کند. اگر mount مجاز نداری یا VM کم‌حافظه است، فرمان‌های نوشتن را اجرا نکن.

Only on a lab VM with root access. This tmpfs is capped at 64 MB with limited inodes and uses RAM/swap. If you cannot mount it or the VM is memory-constrained, do not run write commands.

checkpoint 1 — verify the bounded mount
sudo mkdir -p /mnt/codenames-resource-lab
sudo mount -t tmpfs -o size=64m,nr_inodes=256,mode=1777 tmpfs /mnt/codenames-resource-lab
df -hT /mnt/codenames-resource-lab
df -i /mnt/codenames-resource-lab

نوع filesystem، سقف و inode را ببین؛ اگر فرق دارد توقف کن. حالا فقط ۲۴ مگابایت می‌نویسیم و مصرف را با df و du می‌سنجیم.

Verify filesystem type, ceiling, and inode limit; stop if they differ. Now write only 24 MB and compare df and du.

checkpoint 2 — bounded write and inode sample
dd if=/dev/zero of=/mnt/codenames-resource-lab/sample.bin bs=1M count=24 status=progress
df -h /mnt/codenames-resource-lab
sudo du -sh /mnt/codenames-resource-lab
for n in $(seq 1 80); do : > "/mnt/codenames-resource-lab/empty-$n" || break; done
df -i /mnt/codenames-resource-lab

برای اختلاف دو ابزار، پردازه‌ای می‌سازیم که فقط روی tmpfs بیست مگابایت بنویسد، نام را حذف و descriptor را ۹۰ ثانیه باز نگه دارد. این فایل آزمایش است، نه log واقعی.

To create a discrepancy, our process writes 20 MB only on tmpfs, unlinks the name, and holds the descriptor for 90 seconds. This is a lab file, not a real log.

checkpoint 3 — one deleted-but-open file
python3 -c 'import os,time; p="/mnt/codenames-resource-lab/held.bin"; f=open(p,"wb"); f.write(b"x"*(20*1024*1024)); f.flush(); os.fsync(f.fileno()); os.unlink(p); print("pid",os.getpid(),flush=True); time.sleep(90)' &
held_pid=$!
sleep 1
sudo lsof +L1 | grep codenames-resource-lab || true
df -h /mnt/codenames-resource-lab
sudo du -sh /mnt/codenames-resource-lab

در lsof دنبال held.bin (deleted) بگرد: df فضا را می‌شمارد و du مسیر حذف‌شده را نمی‌بیند. با پایان همین process فضا آزاد می‌شود. اگر lsof نصب نیست یا خروجی خالی است، PID و سنجش قبل/بعد را نگه دار؛ خروجی خالی نبود descriptor را ثابت نمی‌کند.

Look for held.bin (deleted): df counts the space and du cannot see the removed path. Exiting this process releases it. If lsof is absent or output is empty, keep the PID and before/after measurements; empty output does not prove no descriptor exists.

checkpoint 4 — stop only the lab process and clean up
kill "$held_pid"
wait "$held_pid" 2>/dev/null || true
df -h /mnt/codenames-resource-lab
findmnt /mnt/codenames-resource-lab
sudo rm -f /mnt/codenames-resource-lab/sample.bin /mnt/codenames-resource-lab/empty-*
sudo umount /mnt/codenames-resource-lab
sudo rmdir /mnt/codenames-resource-lab

حذف فقط برای همین lab است؛ پس از unmount دادهٔ tmpfs از بین می‌رود. mount واقعی را جایگزین نکن و مطمئن شو process آزمایش تمام شده.

Cleanup applies only to this lab; tmpfs data disappears at unmount. Never substitute a real mount, and confirm the lab process has exited.

بار کوتاه و قابل توقفA short, stoppable workload

روی VM و بدون بار دیگر، یک حلقهٔ CPU را پنج ثانیه اجرا کن. روی production اجرا نکن؛ اگر timeout نیست، ردش کن یا Ctrl-C بزن.

On a lab VM with no other load, run one CPU loop for five seconds. Never use production; if timeout is missing, skip it or use Ctrl-C.

one bounded CPU process
timeout 5s sh -c 'while :; do :; done'
top

مصرف process باید بالا برود و بعد تمام شود؛ این benchmark نیست. برای حافظه فقط اگر VM headroom دارد ۳۲ مگابایت را ۱۰ ثانیه نگه دار؛ ماشین کم‌حافظه را رد کن.

The process use should rise and then stop; this is not a benchmark. Allocate 32 MB for 10 seconds only if the VM has headroom; skip on a constrained machine.

bounded allocation — lab only
python3 -c 'import time; data=bytearray(32*1024*1024); print("allocated 32 MiB"); time.sleep(10)'
free -h

available شاید کم شود و برگردد یا تغییر واضح نکند. این allocation مدل OOM نیست؛ OOM را با log kernel و cgroup/container بررسی کن.

available may fall and recover or barely move. This is not an OOM model; use kernel and cgroup/container evidence.

اندازه‌گیری قبل از تصمیمMeasure before deciding

زمان کندی، load/CPU، available و swap، I/O، mount و درصد بلوک/inode را کنار هم بگذار. اگر مبهم است با ps، du یا lsof دامنه را محدود کن؛ host، container و tmpfs را با هم جمع نکن.

Compare slowdown time, load/CPU, available and swap, I/O, mount, and block/inode percentages. Narrow uncertainty with ps, du, or lsof; do not mix host, container, and tmpfs figures.

پاک‌سازی وقتی شروع می‌شود که مالک فایل، اهمیت داده و راه بازگردانی معلوم باشد. حذف فایل بزرگ inode پر را درست نمی‌کند؛ حذف مسیرهای دیگر فایل باز را آزاد نمی‌کند؛ cleanup هم علت workload غیرعادی نیست.

Cleanup starts only after ownership, data importance, and recovery are understood. A large-file deletion will not fix exhausted inodes; removing other paths will not release an open file; cleanup does not fix abnormal workload.

۱۸ موقعیت برای تشخیص بدون حدس18 situations to diagnose without guessing

۱. load را معنی کن1. Interpret the load

ماشین ۴ CPU دارد و loadهای ۷٫۲، ۶٫۱، ۳٫۰ است. چه می‌فهمی و چه نمی‌فهمی؟

A machine has 4 CPUs and load averages of 7.2, 6.1, and 3.0. What can and cannot you infer?

پاسخSolution

در بازهٔ کوتاه runnable/منتظرها زیاد بوده‌اند و میانگین رو به افزایش است؛ درصد CPU یا اثبات CPU bottleneck نیست. top، wa و taskهای D را ببین.

Recently there were many runnable/waiting tasks and the average is rising. This is neither CPU percentage nor proof of a CPU bottleneck. Check top, wa, and D tasks.

۲. load برابر ۲2. A load of 2

load روی میزبان ۳۲ CPU برابر ۲ است. آیا این به‌تنهایی incident است؟

Load is 2 on a 32-CPU host. Is that alone an incident?

پاسخSolution

نه. نسبت به شمار CPU سرنخ آرام‌تری است، اما latency کاربر، روند و انتظار سرویس مهم‌اند.

No. It is a quieter clue relative to CPU count, but user latency, trend, and service expectations matter.

۳. free کم، available مناسب3. Low free, reasonable available

free کم است ولی available زیاد و swap activity ندارید. چه می‌کنی؟

free is low, but available is high and there is no swap activity. What next?

پاسخSolution

احتمالاً cache بخشی از RAM را می‌گیرد و عدد به‌تنهایی کمبود را ثابت نمی‌کند. روند و علائم برنامه را ببین؛ cache را دستی خالی نکن.

Cache may use some RAM; the number alone does not prove shortage. Check trend and application symptoms; do not manually drop caches.

۴. swap قدیمی4. Historical swap use

swpd غیرصفر است اما si/so در چند نمونه صفرند. آیا اکنون thrashing داریم؟

swpd is nonzero, but si/so are zero across samples. Is the system thrashing now?

پاسخSolution

شواهد جابه‌جایی جاری دیده نمی‌شود؛ صفحات ممکن است قبلاً به swap رفته باشند. available و latency را هم بسنج.

There is no observed current swapping; pages may have moved earlier. Also check available and latency.

۵. wa بالا، پردازه در D5. High wa, a task in D

CPU wa بالاست و process در D دیده می‌شود. گام بعدی؟

CPU wa is high and a process is in D. What is next?

پاسخSolution

mount/device را با findmnt/lsblk مشخص کن و اگر هست iostat -xz 1 3 بگیر. این‌ها فرضیهٔ I/O را تقویت می‌کنند، علت نهایی نیستند.

Map mount/device with findmnt/lsblk and run iostat -xz 1 3 if available. These strengthen the I/O hypothesis, not a final diagnosis.

۶. util صددرصد روی SSD6. 100% util on an SSD

SSD مقدار %util=100 دارد. سقف کارایی اثبات شد؟

An SSD reports %util=100. Is its performance ceiling proven?

پاسخSolution

نه؛ برای دستگاه موازی این ستون به‌تنهایی سقف را ثابت نمی‌کند. await، queue، latency و آمار provider را مقایسه کن.

No; for parallel devices, this field alone does not establish a ceiling. Compare await, queue, latency, and provider metrics.

۷. iostat نصب نیست7. iostat is missing

iostat: command not found. آیا باید فوری روی سرور نصبش کنی؟

iostat: command not found. Must you install it on the server right away?

پاسخSolution

نه. از vmstat، top، findmnt و آمار VM/provider شروع کن؛ نصب sysstat را طبق مجوز و تغییرات مجاز انجام بده.

No. Start with vmstat, top, findmnt, and VM/provider metrics; install sysstat only under approved change policy.

۸. فقط /var پر است8. Only /var is full

/var در df -hT پر است ولی / جا دارد. کجا را بررسی می‌کنی؟

/var is full in df -hT, while / has space. What do you inspect?

پاسخSolution

mount جداگانه را با findmnt -T /var تأیید کن؛ بعد du -xhd1 /var و df -i /var. فضای root لزوماً filesystem جدا را نجات نمی‌دهد.

Confirm a separate mount with findmnt -T /var; then use du -xhd1 /var and df -i /var. Root space does not necessarily help a separate filesystem.

۹. block آزاد، inode صفر9. Free blocks, no inodes

df -h جا دارد اما df -i صددرصد است و فایل تازه ساخته نمی‌شود. فرق چیست؟

df -h has space, but df -i is at 100% and new files cannot be created. What is exhausted?

پاسخSolution

inode، نه الزاماً بلوک. تعداد و مالک فایل‌های ریز را پیدا کن؛ حذف یک فایل حجیم درمان خودکار نیست.

Inodes, not necessarily blocks. Find the count and owner of small files; deleting one large file is not an automatic fix.

۱۰. du اجازهٔ ورود ندارد10. du cannot enter a directory

du به‌خاطر permission یک subtree را نمی‌خواند. جمع کل معتبر است؟

du cannot read a subtree due to permissions. Is its total reliable?

پاسخSolution

نه؛ آن شاخه ممکن است از جمع جا افتاده باشد. با دسترسی مجاز تکرار کن یا دامنهٔ دیده‌نشده را ثبت کن؛ خاموش‌کردن خطاها اطلاعات اضافه نمی‌کند.

No; that subtree may be missing. Rerun with authorized access or record the unseen scope; suppressing errors does not add information.

۱۱. اختلاف هشت گیگابایتی11. An 8 GB gap

df هشت گیگابایت بیشتر از مصرف مسیرها نشان می‌دهد. یک فرض و ابزار بعدی؟

df reports 8 GB more than visible paths. Give one hypothesis and next tool.

پاسخSolution

فایل unlink‌شدهٔ باز یکی از فرض‌هاست؛ sudo lsof +L1 را روی mount درست بررسی کن. mount پنهان، reserve و permission هم می‌توانند اختلاف بسازند.

An unlinked open file is one hypothesis; check sudo lsof +L1 for the correct mount. Hidden mounts, reserved blocks, and permissions can also create a gap.

۱۲. حذف log، بدون آزادشدن فضا12. Deleted log, space not freed

log را حذف کرده‌ای، df تغییر نکرده و lsof descriptor را نشان می‌دهد. چرا؟

You deleted a log, df did not change, and lsof shows its descriptor. Why?

پاسخSolution

تا descriptor بسته نشود blockها آزاد نمی‌شوند. فایل را کورکورانه truncate نکن؛ owner و روش امن reopen/reload سرویس را پیدا کن.

Blocks remain allocated until the descriptor closes. Do not blindly truncate; identify the owner and the service’s safe reopen/reload procedure.

۱۳. mount فرعی13. A nested mount

du -sh /var/* با df /var جور نیست و /var/lib mount جدا دارد. چرا؟

du -sh /var/* disagrees with df /var, and /var/lib is a separate mount. Why?

پاسخSolution

جمع پوشه‌ها دادهٔ filesystem دیگر را قاطی می‌کند. با findmnt -T mount مسیر را پیدا کن و du -x را به filesystem هدف محدود کن.

The directory sum mixes another filesystem’s data. Use findmnt -T and keep du -x on the target filesystem.

۱۴. فایل log زنده14. An active log file

فایل بزرگی متعلق به برنامهٔ فعال است. پیش از حذف چه چیزهایی را می‌پرسی؟

A large file belongs to an active application. What do you ask before deleting it?

پاسخSolution

مالک، ارزش مدرک، rotation policy، descriptor باز و روش reopen را روشن کن. بعد از اقدام دوباره df را بسنج و سلامت سرویس را verify کن.

Confirm ownership, evidence value, rotation policy, open descriptors, and reopen procedure. Remeasure df and verify service health afterward.

۱۵. process ناپدید شده15. A process disappeared

process حافظهٔ زیادی داشت و بعد ناپدید شد. OOM ثابت شد؟

A process used substantial memory and then disappeared. Is OOM proven?

پاسخSolution

نه. kernel journal، رخدادهای cgroup/container و زمان exit را تطبیق بده؛ مصرف بالا علت خروج را تعیین نمی‌کند.

No. Correlate kernel journal, cgroup/container events, and exit time; high usage does not establish why it exited.

۱۶. /run پر است16. /run is full

/run پر است ولی دیسک اصلی جا دارد. تناقضی هست؟

/run is full, but the main disk has space. Is that contradictory?

پاسخSolution

نه؛ /run اغلب filesystem موقت جداست. نوع و mount را با df -hT/findmnt ببین؛ آن را با root disk یکی نگیر.

No; /run is often a separate temporary filesystem. Inspect it with df -hT/findmnt; do not conflate it with root storage.

۱۷. ردیف اول vmstat17. The first vmstat row

ردیف اول vmstat 1 5 با بقیه فرق دارد. کدام را برای رفتار همین حالا می‌خوانی؟

The first row of vmstat 1 5 differs. Which rows describe current behavior?

پاسخSolution

ردیف‌های بعدی intervalهای تازه‌اند؛ اولی معمولاً میانگین از boot است. نسخهٔ نصب‌شده و man page را هم چک کن.

Later rows are fresh intervals; the first commonly averages since boot. Check the installed version and its manual.

۱۸. یادداشت تحویل incident18. Hand off the incident

/var پر است، inode عادی، du -x کمتر از df و lsof یک فایل deleted نشان می‌دهد. تشخیص و اقدام امن؟

/var is full, inodes are normal, du -x is lower than df, and lsof shows a deleted file. Diagnose and act safely.

پاسخSolution

شواهد با فایل unlink‌شدهٔ باز سازگار است، نه inode exhaustion. PID، سرویس، اندازه، mount و زمان را ثبت کن؛ با owner برای reopen/restart کنترل‌شده هماهنگ شو؛ سپس df/lsof و سلامت سرویس را دوباره بسنج. process را بی‌برنامه نکش.

The evidence fits an open unlinked file, not inode exhaustion. Record PID, service, size, mount, and time; coordinate a controlled reopen/restart with the owner; then recheck df/lsof and service health. Do not kill it blindly.
