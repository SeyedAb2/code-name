cron و زمان‌بندیcron and scheduling

اسکریپت رو دستی می‌زنی و عالی کار می‌کنه؛ ساعت ۲ شب اما هیچ گزارشی ساخته نشده. این جملهٔ «دستی که کار می‌کنه!» دقیقاً همون جاییه که باید شک کنیم محیط اجرای cron با ترمینال ما یکی نیست.

You run a script by hand and it works. At 2 a.m., no report arrives. Perhaps the program is broken; perhaps it never ran, or ran as another user, time, directory, and environment. Before changing the scheduler, find evidence of its run.

«دستی کار می‌کنه»؛ کار زمان‌بندی‌شده کجاست؟“It works manually”—where is the job?

قبل از دست زدن به زمان‌بندی سه چیز رو پیدا می‌کنیم: کار با کدوم کاربر اجرا می‌شه، ساعت ماشین چنده و خروجی یا خطاش کجا می‌ره. بعد تازه می‌ریم سراغ خود cron و timer.

In the previous chapter, we correlated a symptom with time and measurements. This time we will run a harmless job every two minutes. First ask: what time does the host use, which user owns the job, and where should its result appear?

check clock and scheduler
date --iso-8601=seconds
timedatectl
systemctl status cron --no-pager

بسته به توزیع، unit ممکنه cron یا crond باشه. ساعت و منطقهٔ زمانی رو ثبت کن. فعال بودن daemon فقط زنده‌بودنش رو نشون می‌ده؛ نه اینکه ورودی درست هست یا اسکریپت موفق شده.

Depending on distribution, the unit may be cron or crond. Record the clock and timezone. An active daemon proves only that it is running—not that the entry is valid or the script succeeded.

زمان‌بند همون shell تو نیستThe scheduler is not your shell

ترمینال از profile، PATH، دایرکتوری فعلی و متغیرهای session کمک می‌گیره. cron محیط ساده‌تری داره. دستوری که با اسم کوتاه پیدا می‌شه ممکنه آنجا پیدا نشه؛ مسیر نسبی هم لزوماً از پوشهٔ مورد انتظار شروع نمی‌شه.

A terminal inherits profiles, PATH, its current directory, and session variables. Cron has a smaller environment. A command found by a short name may be missing there, and relative paths may start somewhere unexpected.

اسکریپت یکی هست، محیط فرق داره؛ اجرای دستی کار زمان‌بندی‌شده رو ثابت نمی‌کنه.

The script is the same, but the environment differs; manual success does not prove the scheduled job worked.

کاربر رو مشخص کن، فایل اجرایی و فایل رو با مسیر مطلق بنویس، directory لازم رو صریح کن و stdout/stderr رو نگه دار. هرکدوم سرنخی می‌ده، اما نتیجهٔ کاری رو تضمین نمی‌کنه.

Choose the user, use absolute executable and file paths, set any required directory explicitly, and capture stdout/stderr. Each creates a clue, but none guarantees the business result.

پنج خانهٔ زمان، بعد فرمانFive time fields, then a command

پنج فیلد کاربر crontab به‌ترتیب دقیقه، ساعت، روز ماه، ماه و روز هفته‌اند. در crontab کاربر، username نمیاد و کار زمان‌بندی‌شده با همون کاربر اجرا می‌شه؛ در /etc/crontab و /etc/cron.d فیلد username اضافه هست.

A user crontab has five fields: minute, hour, day of month, month, and day of week. It has no username field and runs as that user; /etc/crontab and /etc/cron.d add a username field.

every two minutes in a user crontab
*/2 * * * * /absolute/path/to/job.sh

*/2 یعنی هر دو دقیقه؛ 0 2 * * * درخواست اجرای روزانه ساعت ۲:۰۰ هست، نه دقیقاً هر ۲۴ ساعت. در پیاده‌سازی‌های رایج، اگه روز ماه و روز هفته هر دو محدود باشن، تطبیق یکی کافیه؛ manual همون daemon رو ملاک بگیر.

*/2 means every two minutes; 0 2 * * * requests 02:00 daily, not exactly every 24 hours. Common implementations match either restricted day-of-month or day-of-week field; use the installed daemon’s manual.

با crontab -l خط رو بازبینی کن؛ وجود ورودی موفقیت اجرا رو ثابت نمی‌کنه. قبل از ویرایش نسخهٔ قبلی رو نگه دار و بعد از تغییر timestamp و خروجی تازه رو بررسی کن.

Review entries with crontab -l; their presence does not prove execution success. Save the previous crontab before editing, then inspect a fresh timestamp and output.

دستی اجرا می‌شه، cron خطا می‌دهIt runs manually, cron reports an error

در پوشهٔ پروژه ./report.sh جواب می‌ده؛ cron همون directory یا PATH کامل رو نداره. اول خطا رو آشکار کن: برای کاربر آزمایش stdout و stderr رو به فایل خودش بفرست؛ secret در log نگذار و permission رو محدود کن.

From the project directory, ./report.sh works; cron does not share that directory or full PATH. Expose the error first: redirect stdout and stderr to the lab user’s own file; keep secrets out and permissions restricted.

deliberately faulty relative path — lab only
*/2 * * * * cd project && ./report.sh >> "$HOME/cron-lab.log" 2>&1

بعد از دو دقیقه log رو بخوان. خطای directory یا دستور فرضیه می‌سازه. خروجی خالی ثابت نمی‌کنه cron ندویده: برنامه شاید ساکت بوده، مسیر log غلط، permission ناکافی یا daemon خاموش هست.

Read the log after two minutes. A missing directory or command error gives a hypothesis. An empty file does not prove cron never ran: the program may be silent, the path wrong, permissions insufficient, or the daemon stopped.

اصلاح: اسکریپت و interpreter رو با مسیر معلوم اجرا کن و directory لازم رو در خود اسکریپت تعیین کن. PATH root رو کپی یا privilege رو زیاد نکن. اجرای دستی و کار زمان‌بندی‌شده تازه رو با timestamp، stderr و exit وضعیت مقایسه کن.

Fix it with known script/interpreter paths and set the working directory inside the script. Do not copy root’s PATH or add privilege. Compare manual and scheduled runs using timestamps, stderr, and exit status.

absolute script path and captured output
*/2 * * * * /bin/sh "$HOME/bin/report.sh" >> "$HOME/cron-lab.log" 2>&1

daemon log بسته به توزیع در journal یا syslog هست؛ نمونه‌ها journalctl -u cron، journalctl -u crond یا log سیستم‌اند. نام unit و مسیر محلی رو پیدا کن. این log ممکنه شروع فرمان رو ثبت کنه، نه موفقیت کار داخل اسکریپت.

Daemon logs vary by distribution and may be in the journal or syslog; examples include journalctl -u cron, journalctl -u crond, or the system log. Find the local unit/path. Such a log may show command start, not successful work inside the script.

stdout، stderr و اجرای هم‌زمانstdout, stderr, and overlapping runs

cron ممکنه خروجی رو با mail محلی بفرستد، اگه mail delivery تنظیم شده باشه؛ روی VM کسی اون رو نمی‌خونه. در lab redirect صریح بگذار؛ روی سرویس واقعی rotation/نگهداری نسخه‌ها لازمه تا log بی‌نهایت رشد نکنه.

Cron may mail output if local mail delivery is configured; nobody may read it on a VM. Redirect explicitly in the lab; real services need log rotation/retention so files do not grow without bound.

اگه اجرا از فاصلهٔ زمان‌بندی طولانی‌تر بشه، دو نمونه ممکنه هم‌پوشانی کنن. در Linux، flock -n می‌تونه اجرای دوم رو بدون انتظار رد کنه؛ مسیر ابزار رو چک کن. قفل کار زمان‌بندی‌شده گیرکرده رو تعمیر نمی‌کنه و skip رو باید در log ببینی.

If a run lasts longer than its interval, instances can overlap. On Linux, flock -n can skip a second run without waiting; verify the tool path. A lock does not repair a stuck job, and skipped runs should be visible in logs.

optional lock if flock is installed
*/2 * * * * /usr/bin/flock -n "$HOME/report.lock" /bin/sh "$HOME/bin/report.sh" >> "$HOME/cron-lab.log" 2>&1

۲ بامدادِ کدوم ساعت؟02:00 in which timezone?

date/timedatectl رو روی میزبان بخوان؛ ساعت laptop معیار نیست. cron عموماً از منطقهٔ زمانی میزبان یا override پشتیبانی‌شده توسط daemon استفاده می‌کنه. منطقهٔ زمانی رو فقط برای رفع یک کار زمان‌بندی‌شده تغییر نده؛ سرویس‌های دیگر هم جابه‌جا می‌شن.

Read date/timedatectl on the host; your laptop is not the reference. Cron generally uses the host timezone or a daemon-supported override. Do not change timezone just to fix one job; other services shift too.

تغییر ساعت تابستانی می‌تونه زمان دیواری رو حذف یا تکرار کنه؛ جزئیات به daemon و منطقهٔ زمانی بستگی داره. cron معمولاً run ازدست‌رفته هنگام خاموشی رو replay نمی‌کنه؛ anacron یا تنظیم توزیع می‌تونه فرق کنه. نیاز catch-up رو صریح طراحی و آزمایش کن.

Daylight-saving changes can skip or repeat a wall-clock time; details depend on daemon and timezone. Cron generally does not replay a run missed while powered off; anacron or distribution configuration may differ. Design and test catch-up explicitly if required.

timer و service دو واحد جدا هستنThe timer and service are separate units

در میزبان systemd، .timer یک .service رو فعال می‌کنه. service رو قبل از زمان‌بند دستی امتحان کن؛ timer فقط زمان اجرا رو اضافه می‌کنه.

On a systemd host, a .timer activates a .service. Test the service manually before scheduling it; the timer only adds the trigger.

oneshot service — replace lab user/path
[Unit]
Description=Harmless CodeNames report
[Service]
Type=oneshot
User=LAB_USER
WorkingDirectory=/home/LAB_USER
ExecStart=/home/LAB_USER/bin/report.sh

در VM، LAB_USER و مسیرها رو با مقدار واقعی جایگزین کن. بلوک رو در /etc/systemd/system/codenames-report.service ذخیره کن؛ بعد sudo systemctl daemon-reload و sudo systemctl start codenames-report.service رو اجرا کن. status و journalctl -u خروجی و exit رو نشون می‌دن.

On the VM, replace LAB_USER and paths with real values. Save the block as /etc/systemd/system/codenames-report.service, then run sudo systemctl daemon-reload and sudo systemctl start codenames-report.service. status and journalctl -u expose output and exit status.

calendar timer — every two minutes
[Unit]
Description=Schedule harmless report
[Timer]
OnCalendar=*-*-* *:0/2:00
Persistent=true
RandomizedDelaySec=10s
[Install]
WantedBy=timers.target

بلوک timer رو در /etc/systemd/system/codenames-report.timer ذخیره کن و syntax رو با systemd-analyze calendar '*-*-* *:0/2:00' روی نسخهٔ نصب‌شده بررسی کن. Persistent=true برای calendar timer اگه هنگام خاموشی دست‌کم یک بار رو از دست داده باشه یک catch-up می‌خواد، نه صف جدا برای همهٔ intervalها. RandomizedDelaySec trigger رو تا سقف تأخیر پخش می‌کنه؛ نسخه‌های قدیمی ممکنه نشناسندش.

Save the timer block as /etc/systemd/system/codenames-report.timer and validate syntax with systemd-analyze calendar '*-*-* *:0/2:00' on the installed version. For calendar timers, Persistent=true requests one catch-up if at least one run was missed during downtime; it does not queue every missed interval. RandomizedDelaySec spreads triggers by up to the configured delay; older versions may not support it.

activate, then inspect trigger and service result
sudo systemctl daemon-reload
sudo systemctl enable --now codenames-report.timer
systemctl list-timers --all
systemctl status codenames-report.timer --no-pager
journalctl -u codenames-report.service -n 20 --no-pager

NEXT و LAST در list-timers زمان trigger هستن، نه موفقیت اسکریپت. برای نتیجه وضعیت و journal خود service رو بخوان. تکرار trigger اجرای نامحدود موازی نمی‌سازه؛ اما کار زمان‌بندی‌شده طولانی هنوز به سیاست و قفل نیاز داره.

NEXT and LAST in list-timers are trigger times, not script success. Read the service status and journal for results. Repeated triggers do not create unlimited parallel instances, but long jobs still need an execution policy or lock.

لَب: یک کار ساده، دو زمان‌بند، یک خطای عمدیLab: one harmless task, two schedulers, one deliberate fault

روی VM آزمایش و با کاربر عادی خودت انجام بده، نه root. یک اسکریپت می‌سازیم که فقط زمان، کاربر و پوشه رو چاپ کنه؛ هر مرحله باید شاهد قابل‌مشاهده داشته باشه. اگه cron یا systemd روی محیط تو فعال نیست، دستورات سرویس رو اجرا نکن و محدودیت رو یادداشت کن.

Use a lab VM and your normal user, not root. We will create a script that prints only time, user, and directory; each step needs visible evidence. If cron or systemd is unavailable, do not run those service commands—record the limitation.

اول اسکریپت رو بساز و دستی اجرا کن. این خط پایه هست؛ log باید نام کاربر و زمان رو داشته باشه.

Create the script and run it manually first. This is the baseline; output should contain the user and time.

create a harmless, self-contained script
mkdir -p "$HOME/bin"
cat > "$HOME/bin/report.sh" <<'EOF'
#!/bin/sh
PATH=/usr/bin:/bin
export PATH
printf 'run_time=%s user=%s cwd=%s\n' "$(date --iso-8601=seconds)" "$(id -un)" "$PWD"
EOF
chmod 700 "$HOME/bin/report.sh"
"$HOME/bin/report.sh"

حالا در crontab خودت ورودی با فاصلهٔ دو دقیقه بگذار؛ نه در crontab سیستمی. چند دقیقه صبر کن و آخر log رو بخوان. زمان تازه نشون می‌ده cron به اسکریپت رسیده؛ محتوای مورد انتظار و exit موفق رو هم بررسی کن.

Now add a two-minute entry to your own crontab, not the system crontab. Wait a few minutes and inspect the end of the log. A fresh timestamp shows the script was reached; also verify expected content and successful exit.

install this line with crontab -e
*/2 * * * * "$HOME/bin/report.sh" >> "$HOME/cron-lab.log" 2>&1
after installing, verify entry and output
crontab -l
tail "$HOME/cron-lab.log"

برای خرابی عمدی، فقط در lab ورودی رو موقتاً به مسیر نسبی برگردان؛ بعد از دو دقیقه stderr رو بخوان و خطای cd/مسیر رو پیدا کن. اگه چیزی ثبت نشد، daemon log و مجوز نوشتن log رو چک کن. بعد ورودی رو به مسیر مطلق برگردان و یک خط تازه رو بررسی نهایی کن.

For the deliberate fault, temporarily change only the lab entry to a relative path. After two minutes, inspect stderr for a directory/path error. If nothing was captured, check daemon logs and log-file permissions. Restore the absolute path and verify a fresh line.

برای مقایسه، service و timer بخش قبل رو با همین اسکریپت نصب کن و نام کاربر/pathها رو عوض کن. بعد از daemon-reload timer رو فعال کن؛ list-timers باید NEXT و بعد از اجرا LAST نشان بده و journalctl -u codenames-report.service stdout/نتیجه رو. از صفحهٔ وضعیت به‌تنهایی موفقیت محتوایی رو نتیجه نگیر.

For comparison, install the service and timer from the previous section using this script, replacing user and paths. After daemon-reload, enable the timer. list-timers should show NEXT and, after a run, LAST; journalctl -u codenames-report.service shows output/result. Do not infer content success from unit status alone.

پایان تمرینClean up the lab

خط crontab آزمایش رو بردار، timer رو stop/disable کن و فقط همون دو unitی رو که خودت برای این lab ساختی حذف کن؛ سپس daemon-reload. log کاربر رو نگه دار تا مدرک مقایسه داشته باشی یا بعد از بررسی، خودت حذفش کن. فایل‌های سرویس دیگری رو پاک نکن.

Remove the lab crontab line, stop/disable the timer, and delete only the two unit files you created for this lab; then reload systemd. Keep the user log for comparison or remove it after review. Do not delete other service files.

For simple scheduling on a host with cron, cron is reasonable. When a systemd service needs journaling, dependencies, or catch-up, a timer is a natural fit. Neither replaces alerts or checking results.

۱۸ خرابی زمان‌بندی؛ از ساعت تا نتیجه18 scheduling incidents—from clock to outcome

۱. پنج فیلد1. Five fields

این خط رو بخوان: 15 3 * * 1-5. چه زمانی اجرا می‌شه؟

Read 15 3 * * 1-5. When does it run?

پاسخSolution

روزهای هفته در ساعت ۳:۱۵، بر اساس منطقهٔ زمانی/تنظیمات همون cron. معنی دقیق نام روز و منطقهٔ زمانی رو روی میزبان بررسی کن.

At 03:15 on weekdays, using that cron’s timezone/configuration. Verify weekday names and timezone on the host.

۲. هر ۲۴ ساعت یا هر روز؟2. Every 24 hours or every day?

0 2 * * * رو با اجرای هر ۲۴ ساعت مقایسه کن.

Compare 0 2 * * * with running every 24 hours.

پاسخSolution

این زمان دیواریِ هر روز ساعت ۲ هست؛ با تغییر ساعت یا خاموشی ممکنه فاصلهٔ واقعی متفاوت بشه و cron معمولاً missed اجرا رو catch-up نمی‌کنه.

It is a wall-clock time at 02:00 each day. Clock changes or downtime can alter elapsed time, and cron generally does not catch up missed runs.

۳. نام کاربر در خط3. A username in the entry

کاربر اسم خودش رو داخل crontab شخصی می‌نویسه و خط اجرا نمی‌شه. کدوم تفاوت قالب رو چک می‌کنی؟

A user puts a username in their own crontab and the line fails. Which format difference do you check?

پاسخSolution

کاربر crontab پنج فیلد زمان و بعد فرمان داره؛ username اضافه نمی‌شه. فیلد username برای /etc/crontab و /etc/cron.d هست.

A user crontab has five time fields followed by the command, with no username. The username field belongs to /etc/crontab and /etc/cron.d.

۴. دو خانهٔ روز4. Two day fields

روز ماه و روز هفته هر دو محدودن. برای چه دلیلی باید رفتار daemon رو تأیید کنی؟

Both day-of-month and day-of-week are restricted. Why verify the daemon’s behavior?

پاسخSolution

پیاده‌سازی‌های رایج وقتی هر دو محدودن تطبیق هرکدوم رو می‌پذیرن؛ این رو به همهٔ زمان‌بندها تعمیم نده و man page همون سیستم رو بخوان.

Common implementations accept either field when both are restricted; do not generalize to every scheduler—check the host manual.

۵. اسکریپت نسبی5. A relative script path

دستی از پوشهٔ پروژه ./report.sh کار می‌کنه؛ cron خطای فایل می‌ده. چه چیزی رو ثبت و اصلاح می‌کنی؟

From the project directory, ./report.sh works manually; cron reports a missing file. What do you capture and fix?

پاسخSolution

stderr رو ثبت کن؛ working directory رو صریح کن یا مسیر مطلق اسکریپت رو بده. اجرای دستی فقط محیط دستی رو ثابت می‌کنه.

Capture stderr; set the working directory explicitly or use the absolute script path. Manual success proves only the interactive environment.

۶. دستور not found6. Command not found

cron نمی‌تونه python3 رو پیدا کنه اما shell تعاملی می‌تونه. راه امن؟

Cron cannot find python3, but the interactive shell can. What is a safe fix?

پاسخSolution

مسیر interpreter رو با command -v python3 در همون میزبان پیدا و مطلق استفاده کن؛ PATH رو بی‌محابا به کل محیط root گسترش نده.

Find the interpreter with command -v python3 on that host and use its absolute path; do not indiscriminately copy root’s PATH.

۷. خطا کجا رفت؟7. Where did the error go?

اسکریپت cron شکست می‌خوره و هیچ‌کس mail محلی رو نمی‌خونه. اولین تغییر آزمایش؟

A cron script fails and nobody reads local mail. What is your first lab change?

پاسخSolution

stdout/stderr رو به log محدود و قابل‌خواندن redirect کن، permission و مسیر رو بسنج و log رو حاوی secret نکن.

Redirect stdout/stderr to a bounded readable log, check its path and permissions, and keep secrets out of it.

۸. log خالی8. An empty log

فایل خروجی خالی هست. آیا ثابت شد cron اجرا نشده؟ دو فرض جایگزین بگو.

The output file is empty. Is it proven that cron did not run? Give two alternatives.

پاسخSolution

نه؛ کار زمان‌بندی‌شده شاید سکوت کنه، redirect مسیر دیگری داشته باشه، مجوز نوشتن نباشه یا daemon فعال نباشه. timestamp و log daemon رو بررسی کن.

No; the job may be silent, redirect elsewhere, lack write permission, or the daemon may be inactive. Check timestamps and daemon logs.

۹. ساعت میزبان9. The host clock

کار زمان‌بندی‌شده ساعت ۲ به وقت ایران نوشته شده ولی VM UTC هست. قبل از تغییر منطقهٔ زمانی چه evidence می‌گیری؟

The job says 02:00 Iran time, but the VM is UTC. What evidence do you collect before changing timezone?

پاسخSolution

date/timedatectl، منطقهٔ زمانی، daemon/سیاست و زمان log رو ثبت کن؛ تغییر host منطقهٔ زمانی می‌تونه کارهای زمان‌بندی‌شده دیگر رو هم جابه‌جا کنه.

Record date/timedatectl, timezone, daemon policy, and log times; changing the host timezone can shift other jobs.

۱۰. خاموشی نیمه‌شب10. Downtime at midnight

cron هنگام خاموش‌بودن سرور چند اجرای روزانه رو از دست داده. آیا باید اجرای تک‌تک رو انتظار داشت؟

Cron missed several daily times while the server was off. Should you expect every missed run to replay?

پاسخSolution

نه، رفتار عمومی cron replay همهٔ دفعات نیست؛ نیاز catch-up رو با anacron یا timer مناسب طراحی و در همون توزیع آزمایش کن.

No; generic cron behavior does not replay every missed occurrence. Design catch-up with an appropriate anacron or timer setup and test on that distribution.

۱۱. دو اجرا روی هم11. Two runs overlap

کار زمان‌بندی‌شده هر دو دقیقه اجرا می‌شه اما گاهی سه دقیقه طول می‌کشه. خطر و یک کنترل؟

A job runs every two minutes but sometimes takes three. What is the risk and one control?

پاسخSolution

دو نمونه می‌تونن هم‌زمان داده رو تغییر بدن. اگه ابزار موجود و semantics مناسب هست flock -n بگذار یا cadence/طراحی رو تغییر بده؛ skip رو هم log کن.

Two instances may modify data concurrently. If available and appropriate, use flock -n or change cadence/design; log skipped runs too.

۱۲. flock پیدا نشد12. flock is missing

خط اجرای lockدار می‌گه /usr/bin/flock وجود نداره. چه نکنی و چه کنی؟

The lock command says /usr/bin/flock is absent. What should you avoid and do?

پاسخSolution

فرض نکن همه‌جا نصب هست یا کار زمان‌بندی‌شده رو با privilege بیشتر اجرا نکن. path/بسته ابزار رو بررسی کن؛ یا روش قفل متناسب با سیستم رو طراحی کن.

Do not assume it is universal or run with extra privilege. Check the tool/package path or choose a locking mechanism appropriate to the system.

۱۳. timer و catch-up13. Timer catch-up

calendar timer خاموش بوده و پنج بار trigger رو از دست داده. با Persistent=true چند catch-up رو انتظار داری؟

A calendar timer was inactive across five trigger times. With Persistent=true, how many catch-ups should you expect?

پاسخSolution

یک فعال‌سازی جبرانی، نه پنج اجرای صف‌شده؛ این گزینه برای OnCalendar هست و رفتار دقیق نسخه رو از manual تأیید کن.

One catch-up activation, not five queued runs; this option applies to OnCalendar timers, and the installed version’s manual is authoritative.

۱۴. NEXT هست ولی نتیجه نیست14. NEXT exists, but no result

list-timers برای فردا زمان NEXT داره. موفقیت آخرین اسکریپت ثابت شد؟

list-timers shows NEXT for tomorrow. Does this prove the last script succeeded?

پاسخSolution

نه؛ NEXT زمان برنامه‌ریزی آینده هست. LAST trigger و مهم‌تر از اون systemctl status و journalctl -u service رو بخوان.

No; NEXT is the future schedule. Inspect LAST and, more importantly, systemctl status and journalctl -u service.

۱۵. timer کار کرد یا service؟15. Did the timer work—or the service?

timer فعال هست ولی service با exit خطا تمام می‌شه. schedule رو عوض می‌کنی؟

The timer is active, but the service exits with failure. Do you change the schedule?

پاسخSolution

نه؛ اول service رو دستی اجرا و journal/ExecStart/کاربر/path رو بررسی کن. timer فقط فعال‌سازی رو انجام داده هست.

No; run the service manually and inspect its journal, ExecStart, user, and paths. The timer only triggered it.

۱۶. RandomizedDelaySec16. RandomizedDelaySec

نسخهٔ پشتیبان باید دقیقاً رأس نیمه‌شب تمام شده باشه. تأخیر تصادفی مناسب هست؟

A backup must be finished exactly at midnight. Is a randomized delay appropriate?

پاسخSolution

نه بدون بازطراحی deadline؛ گزینه trigger رو عقب می‌ندازه تا اجراها پخش بشن. زمان شروع و مدت کار زمان‌بندی‌شده رو هم از deadline جدا کن.

Not without reconsidering the deadline; the option delays triggers to spread work. Distinguish start time from job duration and completion deadline.

۱۷. CRON_TZ17. CRON_TZ

کار زمان‌بندی‌شده روی یک توزیع با CRON_TZ درست کار می‌کنه و روی دیگری نه. چرا؟

A job uses CRON_TZ on one distribution but not another. Why?

پاسخSolution

این افزونه در همهٔ cronها portable نیست. daemon و man page رو چک کن؛ منطقهٔ زمانی، ساعت log و ساعت schedule ممکنه متفاوت باشن.

This extension is not portable across cron implementations. Check the daemon manual; schedule timezone and log timestamps may differ.

۱۸. گزارش تحویل18. Incident handoff

کار زمان‌بندی‌شده دستی موفق، cron فعال، log می‌گه دستور not found و زمان VM UTC هست. ترتیب تشخیص رو خلاصه کن.

Manual run succeeds, cron is active, the log says command not found, and the VM is UTC. Summarize your diagnostic order.

پاسخSolution

timestamp/منطقهٔ زمانی رو ثبت کن؛ مالک و قالب crontab رو بررسی کن؛ stderr، PATH و working directory رو بخوان؛ دستور/اسکریپت رو با مسیر مطلق و کمترین دسترسی اجرا کن؛ ورودی تازه رو بررسی نهایی و خروجی/exit رو دوباره بسنج. فعال‌بودن daemon اجرای موفق رو ثابت نمی‌کنه.

Record timestamp/timezone; verify owner and crontab format; inspect stderr, PATH, and working directory; run the command with absolute paths and least privilege; verify the updated entry and recheck output/exit status. An active daemon does not prove a successful run.
