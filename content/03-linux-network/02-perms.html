کاربر، گروه، مجوزUsers, groups, permissions

فایل را می‌بینی. مسیرش هم درست است. اما وقتی برنامه آن را باز می‌کند، می‌گوید Permission denied. قبل از اینکه وسوسه شوی همه‌چیز را برای همه باز کنی، بیایید بفهمیم سیستم دقیقاً از چه کسی چه دسترسی‌ای خواسته است.

You can see the file, and its path is correct. But when the application opens it, you get Permission denied. Before making everything accessible to everyone, let us find out exactly which access the system denied to which identity.

۲نمودارdiagrams

برنامه فایل را می‌بیند، ولی اجازهٔ خواندن نداردThe application sees a file but cannot read it

فصل قبل یاد گرفتیم مسیر را با pwd و find بررسی کنیم. حالا یک خطای دیگر داریم: فایل تنظیمات پیدا شده، اما سرویس نمی‌تواند آن را باز کند. «من با حساب خودم می‌توانم» جواب کافی نیست؛ پردازه ممکن است با کاربر دیگری اجرا شود.

In the previous chapter we used pwd and find to check paths. Now we have a different error: the configuration file exists, but a service cannot open it. “I can read it as myself” is not enough; the process may run as another user.

inspect identity and file
id
uid=1000(sara) gid=1000(sara) groups=1000(sara),27(sudo)
ls -l /srv/app/settings.conf
-rw------- 1 root root 84 ... /srv/app/settings.conf

در id شناسهٔ کاربر (UID)، گروه اصلی (GID) و عضویت‌های گروهی را می‌بینی. در ls -l، فایل متعلق به root:root است و rw------- می‌گوید فقط مالک مجوز خواندن/نوشتن دارد. اگر برنامه با کاربر دیگری اجرا شود، این خطا قابل انتظار است.

In id, you see the user ID (UID), primary group ID (GID), and group memberships. In ls -l, the file belongs to root:root; rw------- means only its owner has read/write permission. If the application runs as another user, the error is expected.

نام‌ها خواناتر از عددها هستند، اما هسته با شناسه‌ها تصمیم می‌گیرد. دو حساب با نام متفاوت ممکن است UID یکسان داشته باشند، و گروه‌ها هم با GID شناخته می‌شوند. برای دیدن گروه‌های یک حساب دیگر، روی سیستم‌های معمول Linux می‌توانی از id USER کمک بگیری؛ ولی این فقط عضویت ثبت‌شده را نشان می‌دهد، نه اینکه فرایندِ از قبل اجراشده حتماً عضویت تازه‌ای را گرفته باشد.

Names are easier to read, but the kernel makes access decisions using IDs. Two differently named accounts can share a UID, and groups are identified by GIDs. On typical Linux systems, id USER shows a user’s configured groups—but it does not prove that an already-running process has picked up a newly changed membership.

سه دسته، سه بیت برای هر دستهThree classes, three bits in each

بعد از نوع فایل در خروجی ls -l، ۹ جایگاه مجوز می‌آید: سه‌تا برای مالک، سه‌تا برای گروه فایل و سه‌تا برای بقیه. هر دسته می‌تواند read، write و execute/search داشته باشد. خط تیره یعنی آن مجوز داده نشده.

After the file type in ls -l, nine permission positions follow: three for the owner, three for the file’s group, and three for everyone else. Each class can have read, write, and execute/search. A dash means the permission is absent.

برای 750، عددها از چپ به راست مالک، گروه و بقیه‌اند؛ داخل هر رقم مقدارهای r=4، w=2 و x=1 جمع می‌شوند. شکل فایل در ls -l یک جایگاه جداست و جزو این سه رقم نیست.

In 750, the digits from left to right mean owner, group, and other. Within each digit, add r=4, w=2, and x=1. The file-type character in ls -l is separate from these three digits.

این مجوزها فقط یکی از لایه‌های تصمیم‌اند. اگر مسیر شامل چند دایرکتوری باشد، دسترسی به فایل مقصد کافی نیست؛ باید اجازهٔ عبور از هر جزء مسیر را هم داشته باشی. در ضمن ACL، قابلیت‌های فرایند، mount options و سیاست‌های امنیتی دیگری می‌توانند نتیجه را تغییر دهند؛ فعلاً روی مجوزهای معمول تمرکز می‌کنیم.

These bits are only one layer in the decision. For a path containing several directories, permission on the final file is not enough: the process also needs to traverse each path component. ACLs, process capabilities, mount options, and other security policies can affect the result; for now we focus on ordinary permissions.

x روی فایل با x روی دایرکتوری یکی نیستExecute on a file is not the same as execute on a directory

روی فایل معمولی، r خواندن محتوا، w تغییر محتوا و x تلاش برای اجرا را اجازه می‌دهد. روی دایرکتوری، r خواندن فهرست نام‌ها، w ساخت/حذف/rename کردن ورودی‌های آن، و x جست‌وجو یا عبور از دایرکتوری است. برای بازکردن یک فایل، معمولاً باید در همهٔ دایرکتوری‌های مسیر x داشته باشی.

On a regular file, r allows reading content, w modifying it, and x attempting to execute it. On a directory, r allows listing names, w creating/removing/renaming entries, and x searching or traversing it. Accessing a file generally requires x on every directory in its path.

مسیر نمونه /srv/app/config/settings.conf است. حتی اگر فایل آخر برایت r داشته باشد، نبودن x روی /srv یا یکی از والدها مانع رسیدن به آن می‌شود.

The example path is /srv/app/config/settings.conf. Even if the final file grants you r, missing x on /srv or another parent prevents reaching it.

برای دیدن هر جزء مسیر از namei -l PATH استفاده کن. فرمان ممکن است در همهٔ نصب‌ها از ابتدا موجود نباشد؛ در آن صورت ls -ld را برای هر والد جدا اجرا کن. خروجی این ابزارها مجوزهای ثبت‌شده را نشان می‌دهد، نه تمام سیاست‌هایی را که ممکن است دخالت کنند.

Use namei -l PATH to inspect each path component. The command may not be installed everywhere; if absent, check each parent with ls -ld. These tools show recorded mode bits, not every policy that may be involved.

اول بپرس کدام هویت، روی کدام فایل؟First ask: which identity, on which file?

یک خطای مجوز را با بازکردن همهٔ دسترسی‌ها درمان نمی‌کنیم. هویت پردازه و mode فایل را کنار هم می‌گذاریم. در VM آزمایشی، دو حساب موقت می‌سازیم تا مشاهدهٔ واقعی داشته باشیم؛ روی VPS یا لپ‌تاپ کاری این حساب‌ها را نساز.

We do not fix a permission error by opening access to everyone. Compare the process identity with the file mode. In a disposable VM, create two temporary accounts for a real test; do not create these accounts on a production VPS or work laptop.

مرز آزمایشExperiment boundary

دستورهای ساخت کاربر و گروه به sudo نیاز دارند و وضعیت سیستم را تغییر می‌دهند. فقط در VM یک‌بارمصرف اجرا کن، پیش از شروع وجود نداشتن نام‌های آزمایش را بررسی کن و در پایان فقط همان منابع آزمایش را پاک کن.

Creating users and groups requires sudo and changes system state. Run this only in a disposable VM, verify the test names do not already exist, and remove only these test resources at the end.

preflight in disposable VM
getent group perm-lab || true
getent passwd perm-ana perm-beh || true

اگر هر نام از قبل وجود دارد، نام دیگری برای آزمایش انتخاب کن؛ هیچ حساب موجودی را تغییر نده. بعد گروه و دو حساب موقت را بساز. -M home ایجاد نمی‌کند و -s /usr/sbin/nologin ورود تعاملی را برای این حساب‌های آزمایش می‌بندد؛ مسیر nologin در بعضی توزیع‌ها ممکن است متفاوت باشد.

If any name already exists, choose different test names; do not modify an existing account. Then create a temporary group and two accounts. -M avoids creating home directories and -s /usr/sbin/nologin disables interactive login for these test accounts; the nologin path can vary by distribution.

temporary lab identities
sudo groupadd perm-lab
sudo useradd -M -s /usr/sbin/nologin -g perm-lab perm-ana
sudo useradd -M -s /usr/sbin/nologin -g perm-lab perm-beh
id perm-ana
uid=... (perm-ana) gid=... (perm-lab) groups=... (perm-lab)

عدد UID/GID را سیستم انتخاب می‌کند؛ دنبال برابری با نمونه نباش. حالا یک فایل خصوصی برای ana می‌سازیم و واقعاً می‌پرسیم Beh می‌تواند بخواند یا نه.

The system chooses the numeric UID/GID; do not expect the sample values. Now create a private file for ana and test whether beh can actually read it.

create and test
sudo mkdir -p /tmp/perm-lab-demo
sudo chown perm-ana:perm-lab /tmp/perm-lab-demo
sudo chmod 0750 /tmp/perm-lab-demo
sudo -u perm-ana sh -c 'printf secret > /tmp/perm-lab-demo/secret.txt'
sudo chmod 0640 /tmp/perm-lab-demo/secret.txt
ls -l /tmp/perm-lab-demo/secret.txt
-rw-r----- 1 perm-ana perm-lab ... secret.txt
sudo -u perm-beh cat /tmp/perm-lab-demo/secret.txt

اینجا Beh عضو گروه perm-lab است؛ پس با 0640 باید بتواند بخواند. اگر خواستیم خطای فایل را جدا بسازیم، گروه را از read محروم می‌کنیم؛ ولی برای اینکه خطا واقعاً از همین فایل باشد، باید عبور از دایرکتوری را هم داشته باشد. خطای نهایی را همراه با مالکیت و mode تفسیر کن، نه به‌تنهایی.

Beh belongs to perm-lab, so mode 0640 should allow group reading. To isolate a file-level denial, remove group read from the file while preserving directory traversal. Interpret the error alongside ownership and mode, not by itself.

file-level denial
sudo chmod g-r /tmp/perm-lab-demo/secret.txt
sudo -u perm-beh cat /tmp/perm-lab-demo/secret.txt
cat: .../secret.txt: Permission denied
ls -l /tmp/perm-lab-demo/secret.txt
-rw------- 1 perm-ana perm-lab ... secret.txt

در خروجی، پوشه هنوز برای گروه x دارد و خطای خواندن روی خود فایل رخ داده است. Repair را با بازگرداندن فقط گروهِ لازم انجام بده: اگر اعضای گروه باید بخوانند، chmod g+r FILE؛ اگر فقط یک نفر باید بخواند، مالکیت یا ACL مناسب‌تر است. سپس همان فرمان cat را دوباره اجرا کن.

The directory still grants group x, so this read denial is on the file itself. Repair only the needed group permission: use chmod g+r FILE if group members should read; if only one person needs access, ownership or an ACL may be more appropriate. Then rerun the same cat check.

این بار فایل مجاز است، اما راه رسیدن بستهThis time the file allows access, but the path is blocked

حالا namei -l را به بازی می‌آوریم. فایل را برای گروه readable نگه می‌داریم، اما x گروه را از یکی از دایرکتوری‌های مسیر برمی‌داریم. پیش‌بینی: ممکن است ls -l FILE mode خوب نشان دهد، ولی بازشدن فایل همچنان شکست بخورد.

Now bring in namei -l. Keep the file readable by the group, but remove group x from one directory in its path. Prediction: ls -l FILE may show a permissive mode while opening the file still fails.

break traversal, not file read
sudo chmod 0640 /tmp/perm-lab-demo/secret.txt
sudo chmod g-x /tmp/perm-lab-demo
namei -l /tmp/perm-lab-demo/secret.txt
sudo -u perm-beh cat /tmp/perm-lab-demo/secret.txt

در خروجی namei -l دنبال همان مؤلفه‌ای بگرد که برای گروه x ندارد. x روی دایرکتوری یعنی امکان search/traverse؛ اینجا نه فایل‌خوانی رد شده، نه لازم است mode فایل را بازتر کنیم. اصلاح حداقلی را روی دایرکتوری درست انجام بده و همان مسیر را دوباره باز کن.

In namei -l, look for the component that lacks group x. On a directory, x means search/traverse; this is not a file-read denial, and widening the file mode is unnecessary. Apply a minimal correction to the right directory and retry the same path.

repair traversal
sudo chmod g+x /tmp/perm-lab-demo
sudo -u perm-beh cat /tmp/perm-lab-demo/secret.txt

در محیط واقعی، ممکن است هرکدام از /، /tmp یا پوشه‌های میانی مشکل داشته باشند. namei -l عیب‌یابی را از حدس به بررسی جزءبه‌جزء تبدیل می‌کند؛ اگر نصب نیست، هر والد را با ls -ld ببین. پیام Permission denied به تنهایی نمی‌گوید کدام جزء یا کدام policy مقصر است.

On a real system, the problem could be /, /tmp, or any intermediate directory. namei -l turns guessing into a component-by-component check; if unavailable, inspect each parent with ls -ld. “Permission denied” alone does not identify the component or policy responsible.

chmod: تغییر دقیق، نه بازکردن همه‌چیزchmod: make a precise change, not open everything

chmod بیت‌های مجوز را عوض می‌کند. دو شکل رایج دارد: نمادین مثل u+x که یک تغییر مشخص را بیان می‌کند، و octal مثل 640 که سه دسته را یک‌جا تعیین می‌کند. شکل نمادین وقتی می‌خواهی فقط یک بیت را اضافه/کم کنی خواناتر است.

chmod changes permission bits. Two common forms are symbolic, such as u+x, which describes a targeted change, and octal, such as 640, which sets all three classes at once. Symbolic form is often clearer when adding or removing one bit.

نمادSymbolمعناMeaningنمونهExample
u / g / o / aمالک / گروه / بقیه / همهowner / group / other / allg+r
+ / - / =افزودن / برداشتن / دقیقاً تنظیم‌کردنadd / remove / set exactlyo-rwx
r / w / xخواندن / نوشتن / اجرا یا عبورread / write / execute or traverseu=rw,g=r,o=

مثلاً برای اینکه فایل برنامه فقط برای مالک خواندنی/نوشتنی و برای گروه خواندنی باشد، chmod 640 settings.conf می‌زنی. بعد stat یا ls -l را بخوان. موفقیت فرمان می‌گوید مجوز ثبت شده؛ ثابت نمی‌کند مالک، مسیر والد یا policyهای دیگر درست‌اند.

For a configuration file that should be readable/writable by its owner and readable by its group, use chmod 640 settings.conf. Then inspect it with stat or ls -l. Command success says the mode was set; it does not prove ownership, parent traversal, or other policies are correct.

فایل اجرایی و دایرکتوری را یکسان تنظیم نکن. chmod -R 755 tree معمولاً فایل‌های داخلش را هم executable می‌کند و ممکن است محرمانه‌ها را برای همه readable کند. روی شاخهٔ واقعی recursive chmod نزن مگر دقیقاً فهمیده باشی چه چیزی را تغییر می‌دهد؛ موردهای نیاز را جداگانه هدف بگیر.

Do not apply the same mode to executables and directories indiscriminately. chmod -R 755 tree may make every file executable and expose private content to everyone. Avoid recursive chmod on a real tree unless you understand every effect; target the necessary objects deliberately.

مالکیت: چه کسی owner است و کدام گروه؟Ownership: who is the owner, and which group?

در ls -l نام مالک و گروه فایل جداگانه می‌آیند. chgrp گروه را عوض می‌کند؛ chown مالک را و در صورت نیاز گروه را هم. تغییر owner معمولاً اختیار مدیریتی می‌خواهد. از sudo فقط برای همان تغییر محدود استفاده کن، نه برای اجرای کل برنامه به‌عنوان root.

In ls -l, owner and group are shown separately. chgrp changes the group; chown changes the owner and can also set the group. Changing owner usually requires administrative privilege. Use sudo for that narrow change, not to run the whole application as root.

change only the intended group
sudo chgrp perm-lab /tmp/perm-lab-demo/secret.txt
ls -l /tmp/perm-lab-demo/secret.txt
-rw-r----- 1 perm-ana perm-lab ... secret.txt

اگر خودت عضو گروه مقصد باشی، در بسیاری از سیستم‌ها می‌توانی گروه فایل خودت را به یکی از گروه‌هایت تغییر بدهی؛ تغییر به گروه دلخواه یا تغییر مالک محدودتر است. عضویت تازهٔ گروه معمولاً برای نشست‌های بعدی اعمال می‌شود؛ برای بررسی از id در همان نشست استفاده کن.

On many systems, you can change the group of your own file to a group you belong to; changing it to an arbitrary group or changing the owner is more restricted. New group membership commonly applies to later sessions; check with id in the session that will use it.

فایل تازه از چه مجوزی شروع می‌کند؟ umaskWhat permissions does a new file start with? umask

اگر هر فایل تازه‌ای را بعد از ساخت دستی chmod کنیم، زود خسته می‌شویم. umask بیت‌هایی را که هنگام ساخت باید کنار گذاشته شوند مشخص می‌کند. معمولاً فایل‌ساز mode پایهٔ 0666 و دایرکتوری‌ساز 0777 درخواست می‌کند؛ umask بخشی از آن‌ها را حذف می‌کند. برنامه می‌تواند mode محدودتری درخواست کند، پس این اعداد نقطهٔ شروع رایج‌اند، نه تضمین برای هر برنامه.

Manually chmodding every new file gets old quickly. umask specifies which permission bits should be withheld at creation. File-creating programs commonly request a base mode of 0666 and directory creation 0777; the umask removes bits. A program can request a more restrictive mode, so these are common starting points, not guarantees for every program.

predict, create, inspect
umask 0027
touch "$HOME/linux-lab/new.txt"
mkdir -p "$HOME/linux-lab/new-dir"
stat -c '%a %n' "$HOME/linux-lab/new.txt" "$HOME/linux-lab/new-dir"
640 .../new.txt
750 .../new-dir

در این نمونه، 0027 اجازهٔ write گروه و همهٔ دسترسی‌های بقیه را از mode پایه حذف می‌کند: فایل 640 و دایرکتوری 750 می‌شود. خروجی واقعی را با stat بسنج؛ اگر برنامه خودش mode بسته‌تری خواسته باشد، فایل می‌تواند محدودتر باشد. umask این shell را عوض کن، نه umask کل سیستم را.

Here, 0027 removes group write and all “other” permissions from the common base modes: the file becomes 640 and the directory 750. Measure the actual result with stat; a program that requests a stricter mode can create a more restricted file. This changes the current shell’s umask, not the whole system’s.

برای پوشهٔ همکاری مشترک، معمولاً فقط داشتن group write کافی نیست. اگر کاربران گروه فایل بسازند، ممکن است فایل‌هایشان گروه اصلی خودشان را بگیرند. setgid روی دایرکتوری کمک می‌کند فایل‌های تازه گروه دایرکتوری را به ارث ببرند؛ umask مناسب هم تعیین می‌کند اعضای گروه واقعاً بتوانند همکاری کنند.

For a shared directory, group write alone may not be enough. Users’ new files may otherwise receive their primary group. The setgid bit on a directory helps new entries inherit the directory’s group; a suitable umask determines whether group members can actually collaborate.

shared group directory
sudo chown perm-ana:perm-lab /tmp/perm-lab-demo
sudo chmod 2770 /tmp/perm-lab-demo
sudo -u perm-ana sh -c 'umask 0007; touch /tmp/perm-lab-demo/shared.txt'
ls -ld /tmp/perm-lab-demo
drwxrws--- ... perm-ana perm-lab ...
ls -l /tmp/perm-lab-demo/shared.txt

در mode دایرکتوری، حرف s در جای group-execute نشانهٔ setgid است؛ نام گروه فایل تازه را بررسی کن، بعد با حساب دیگر read/write را واقعاً آزمایش کن. setgid گروه را به ارث می‌دهد، اما به‌تنهایی مجوز مناسب یا دسترسی به همهٔ والدها را تضمین نمی‌کند. ACL را می‌توان بعداً با getfacl/setfacl بررسی کرد؛ فعلاً جزئیات ACL خارج از مسیر اصلی ماست.

In a directory mode, s in the group-execute position indicates setgid; inspect the new file’s group, then test read/write as the other account. Setgid inherits the group but does not by itself guarantee suitable permissions or access to all parents. ACLs can later be inspected with getfacl/setfacl; their details are outside our main path for now.

sudo ابزار تشخیص نیست؛ اختیار محدود استsudo is not a diagnostic tool; it grants scoped authority

اگر یک فرمان با sudo موفق شد، هنوز نمی‌دانیم علت دقیق چه بود؛ فقط می‌دانیم اجرای آن با اختیار بالاتر نتیجه را عوض کرد. قبل از sudo کردن، هویت و مسیر و mode را بررسی کن. فرمانی که privilege بیشتری دارد را تا جای ممکن به همان یک اقدام محدود کن.

If a command succeeds with sudo, we still do not know the exact cause; we only know that higher privilege changed the result. Check identity, path, and mode before using sudo. Keep the privileged command limited to that one action.

هرگز 777 را درمان پیش‌فرض نکنNever make 777 the default fix

chmod 777 به مالک، گروه و همهٔ کاربران read/write/execute می‌دهد. این هم مسئلهٔ محرمانگی را باز می‌کند و هم هر کاربری را قادر می‌کند فایل را تغییر دهد یا دایرکتوری را دست‌کاری کند. اول بپرس کدام هویت دقیقاً به کدام بیت نیاز دارد.

chmod 777 grants read/write/execute to owner, group, and everyone. It can expose private content and let any user modify files or directory entries. First ask which identity needs which specific bit.

آزمایشگاه: دو همکار، یک پوشهٔ مشترکLab: two teammates, one shared directory

با همین VM یک پوشهٔ همکاری بساز. Ana مالک باشد، هر دو حساب عضو گروه باشند، گروه بتواند فایل‌های لازم را بخواند و بنویسد و کاربران بیرون گروه به آن دسترسی نداشته باشند. دو خطا را عمداً بساز: یکی روی خود فایل، یکی روی عبور از دایرکتوری. هر بار با id، ls -l/ls -ld و namei -l علت را جدا کن؛ سپس فقط یک مجوز لازم را اصلاح و همان آزمون را تکرار کن.

Using the same VM, create a collaboration directory. Ana owns it, both test accounts belong to its group, the group can read/write the intended files, and outsiders have no access. Deliberately create two failures: one on a file and one on directory traversal. Diagnose each with id, ls -l/ls -ld, and namei -l; then change only the necessary permission and repeat the same test.

تمرین‌ها: از بیت‌ها تا بلیت واقعیExercises: from bits to a real ticket

۱. هویت پردازه1. Process identity

سرویس برایت Permission denied می‌دهد ولی فایل را با حساب خودت می‌خوانی. اولین تفاوتی که باید بررسی کنی چیست؟

A service gets Permission denied while you can read the file yourself. What is the first difference to inspect?

پاسخSolution

هویت UID/GID سرویس در برابر هویت خودت. مجوزها برای شناسه‌هایی ارزیابی می‌شوند که پردازه دارد، نه صرفاً نام انسانیِ صاحب سرور.

Compare the service’s UID/GID with your own. Permissions are evaluated for the process identity, not simply the human who owns the server.

۲. خواندن سه دسته2. Read the three classes

مجوز -rw-r----- به چه کسانی read می‌دهد؟

Who can read a file with mode -rw-r-----?

پاسخSolution

مالک و اعضای گروه فایل؛ other هیچ bitی ندارد. نوع فایل در ابتدای رشته مجوز جدا از سه دسته است.

The owner and members of the file’s group; other has no permission bits. The leading file-type character is separate from the three classes.

۳. معنای ۷۵۵3. What 755 means

755 را به شکل نمادین بنویس و بگو هر رقم برای کیست.

Write 755 symbolically and identify each digit’s class.

پاسخSolution

rwxr-xr-x: مالک همه، گروه read/execute، other read/execute. ۷=۴+۲+۱ و ۵=۴+۱.

rwxr-xr-x: owner gets all, group and other get read/execute. Seven is 4+2+1; five is 4+1.

۴. پوشهٔ فقط‌خواندنی کافی نیست4. Read on a directory is not enough

کاربر روی دایرکتوری r دارد ولی x ندارد. آیا می‌تواند از مسیر کامل، فایلی را باز کند؟

A user has r but not x on a directory. Can they open a file by its full path?

پاسخSolution

معمولاً نه؛ r فهرست نام‌ها را می‌خواند، x برای search/traverse لازم است. هر جزء مسیر باید قابل عبور باشد.

Usually not. r reads directory names; x is needed to search/traverse. Every path component must be traversable.

۵. حذف فایل از پوشه5. Removing an entry

برای حذف یک فایل، کدام مجوزهای دایرکتوری اهمیت دارند و چرا mode خود فایل همیشه تعیین‌کننده نیست؟

Which directory permissions matter for removing a file, and why is the file’s own mode not always decisive?

پاسخSolution

نوشتن و عبور از دایرکتوری والد مهم‌اند؛ حذف یعنی تغییر entry دایرکتوری. sticky bit یا policyهای دیگر هم می‌توانند محدودیت اضافه کنند.

Write and traversal on the parent directory matter because deletion changes its directory entry. Sticky bit or other policies can add restrictions.

۶. افزودن فقط یک bit6. Add just one bit

اسکریپت متعلق به مالک است و باید فقط برای مالک executable شود، بدون تغییر بقیهٔ مجوزها. فرمان؟

A script belongs to the owner and should become executable only by the owner, preserving other bits. Command?

پاسخSolution

chmod u+x script.sh. شکل نمادین فقط همان bit را اضافه می‌کند؛ بعد با ls -l نتیجه را ببین.

chmod u+x script.sh. Symbolic mode adds only that bit; verify with ls -l.

۷. فایل تنظیمات محرمانه7. A private configuration file

owner باید بخواند/بنویسد، گروه فقط بخواند، دیگران هیچ. Octal و symbolic پیشنهاد بده.

The owner needs read/write, group read-only, and other no access. Give octal and symbolic modes.

پاسخSolution

640 یا u=rw,g=r,o=. بعد مالکیت و parent traversal را هم بررسی کن؛ mode فایل تنها شرط دسترسی نیست.

640 or u=rw,g=r,o=. Also check ownership and parent traversal; the file mode is not the only access condition.

۸. چرا chgrp شکست خورد؟8. Why did chgrp fail?

کاربر می‌خواهد فایل خودش را به گروهی منتقل کند که عضو آن نیست. چه شواهدی می‌گیری و چه راه‌هایی ممکن است داشته باشی؟

A user wants to change their own file to a group they do not belong to. What evidence do you collect, and what options may exist?

پاسخSolution

id عضویت فعلی و ls -l owner/group را نشان می‌دهند. درخواست عضویت از مدیر، یا تغییر محدود با اختیار مدیریتی ممکن است مناسب باشد؛ chmod راه تغییر گروه نیست.

id shows current memberships and ls -l shows ownership. Request group membership or use a narrowly authorized administrative change; chmod does not change a file’s group.

۹. chown یا chgrp؟9. chown or chgrp?

فقط group فایل اشتباه است و مالک باید بماند. ابزار مناسب کدام است؟

Only the file’s group is wrong and the owner must remain unchanged. Which tool fits?

پاسخSolution

chgrp GROUP FILE تغییر را دقیق‌تر بیان می‌کند. بعد ls -l را بخوان تا مالک حفظ و گروه عوض شده باشد.

chgrp GROUP FILE expresses the narrow change. Check ls -l to verify the owner stayed and group changed.

۱۰. umask 002710. umask 0027

با mode پایهٔ رایج فایل 666 و دایرکتوری 777، نتیجهٔ معمول umask 027 چیست؟

With common base modes 666 for files and 777 for directories, what does umask 027 commonly produce?

پاسخSolution

فایل 640 و دایرکتوری 750. umask بیت‌ها را حذف می‌کند؛ برنامه می‌تواند mode محدودتری بخواهد، پس نتیجه را با stat اندازه بگیر.

File 640 and directory 750. Umask removes bits; a program can request a stricter mode, so measure the result with stat.

۱۱. یک فایل، دو آزمایش11. One file, two tests

چطور خطای read فایل را از خطای traverse مسیر جدا می‌کنی؟

How do you distinguish file-read denial from path-traversal denial?

پاسخ و شاهدSolution and evidence

اول هویت را با id و mode فایل را با ls -l ببین. بعد مسیر را با namei -l جزءبه‌جزء بخوان؛ برای آزمایش مستقل، یکی را تغییر بده و دیگری را ثابت نگه دار.

Check identity with id, file mode with ls -l, and each component with namei -l. For an isolated test, change one condition while holding the other constant.

۱۲. سرویس فایل را نمی‌بیند12. A service cannot see the file

فایل 0644 است، ولی سرویس همچنان denied می‌گیرد. چه چیزی را بعد بررسی می‌کنی؟

A file is mode 0644, yet a service still gets denied. What do you inspect next?

پاسخSolution

هویت واقعی سرویس و traversal تمام والدها؛ با id پردازه/حساب و namei -l مسیر. همچنین ACL یا محدودیت‌های دیگر ممکن است دخیل باشند.

Inspect the service’s actual identity and traversal on every parent using id and namei -l. ACLs or other restrictions may also be involved.

۱۳. راز 77713. The 777 trap

چرا chmod 777 ممکن است خطا را پنهان کند ولی repair مناسبی نباشد؟

Why might chmod 777 hide the error but still be a poor repair?

پاسخSolution

چون دسترسی نوشتن/خواندن/اجرا را به همه می‌دهد و مسئلهٔ owner/group را حل نمی‌کند. دسترسی لازم را به هویت یا گروه درست بده و سپس همان درخواست واقعی را آزمایش کن.

It grants read/write/execute to everyone and does not correct ownership design. Grant only the needed access to the right identity/group, then retry the real operation.

۱۴. دایرکتوری مشترک14. A shared directory

چرا 2770 برای دایرکتوری تیمی مفید است، و چه چیزی را تضمین نمی‌کند؟

Why can 2770 help a team directory, and what does it not guarantee?

پاسخSolution

setgid کمک می‌کند اعضای تازه group دایرکتوری را به ارث ببرند و 770 دسترسی را به owner/group محدود می‌کند. umask، مجوز والدها و تنظیمات دیگر هنوز مهم‌اند.

Setgid helps new entries inherit the directory group, while 770 limits access to owner/group. Umask, parent permissions, and other settings still matter.

۱۵. sudo موفق شد؛ پس علت چیست؟15. Sudo worked—so what was the cause?

فرمان با sudo موفق شده. آیا ثابت شد مالکیت علت مشکل بوده؟

The command worked with sudo. Does that prove ownership caused the problem?

پاسخSolution

نه؛ فقط می‌دانیم اجرای privileged نتیجه را عوض کرد. mode، مسیر، ACL و هویت را بررسی کن تا علت را محدود کنی؛ sudo تشخیص نیست.

No; only that privileged execution changed the result. Inspect mode, path, ACL, and identity to narrow the cause; sudo is not a diagnosis.

۱۶. عضویت گروه تازه16. Newly added group membership

کاربر را عضو گروه کردی اما shell بازشده هنوز فایل را نمی‌خواند. چه بررسی‌ای جلوی حدس را می‌گیرد؟

You added a user to a group, but their existing shell still cannot read a file. What check avoids guessing?

پاسخSolution

در همان نشست id بزن و عضویت مؤثر را ببین؛ نشست/فرایند قدیمی ممکن است گروه‌های قبلی را نگه داشته باشد. سپس مسیر و mode را هم دوباره بررسی کن.

Run id in that session and inspect effective memberships; an existing session/process may retain prior groups. Recheck path and mode too.

۱۷. acl به‌عنوان سرنخ17. ACL as a clue

mode به نظر درست می‌آید ولی رفتار متفاوت است. ACL را چطور به‌عنوان لایهٔ بعدی بررسی می‌کنی؟

The mode looks right but behavior differs. How do you inspect ACL as the next layer?

پاسخSolution

اگر ابزارها نصب‌اند، getfacl PATH را بخوان؛ ACL می‌تواند دسترسی‌های اضافه/محدودکننده داشته باشد. جزئیاتش موضوع دیگری است؛ فعلاً آن را با mode کلاسیک یکی نگیر.

If tools are installed, inspect getfacl PATH; ACLs can add or constrain access. Their details are a separate topic; do not conflate them with the classic mode display.

۱۸. بلیت عیب‌یابی پایانی18. Final debugging ticket

سرویس به فایل /srv/app/config/key نمی‌رسد. خروجی فایل -rw-r----- app ops است. چه evidence جمع می‌کنی، چه راه‌حل حداقلی را انتخاب می‌کنی و بعد چه چیزی را دوباره آزمایش می‌کنی؟

A service cannot reach /srv/app/config/key. The file shows -rw-r----- app ops. What evidence do you collect, what minimal repair might you choose, and what do you test again?

راهنماHint

فایل فقط برای app و ops خواندنی است؛ اما هنوز هویت سرویس و x والدها را نمی‌دانی.

The file is readable only by app and ops, but you do not yet know the service identity or parent x bits.

پاسخ و دلیلSolution and reasoning

هویت پردازه را با id یا ابزار سرویس، هر مؤلفه را با namei -l و ACL را در صورت نیاز بررسی کن. اگر سرویس باید گروه ops باشد و والدها قابل عبور باشند، عضویت/نشست مناسب یا تنظیم owner/group حداقلی را انتخاب کن؛ 777 نکن. سپس همان خواندن فایل را با همان هویت سرویس تکرار و log/نتیجه را ببین. mode فایل به‌تنهایی علت را ثابت نمی‌کند.

Check the process identity with id or service tooling, each path component with namei -l, and ACL if needed. If the service should use group ops and parents are traversable, choose appropriate membership/session or a minimal owner/group adjustment; do not use 777. Repeat the same file read as the service identity and inspect its result. File mode alone does not establish the cause.

وقتی مجوزها درست‌اند، نوبت کدام سؤال است؟Once permissions are right, what comes next?

حالا می‌توانی فرق خواندن فایل و عبور از مسیر را تشخیص بدهی، mode را بخوانی و دسترسی را محدود اصلاح کنی. اما اگر برنامه اصلاً اجرا نشود یا مدام متوقف شود، مجوز به‌تنهایی جواب نیست. فصل بعد یک پردازه را تا systemd دنبال می‌کنیم و می‌بینیم سرویس چرا بالا نمی‌آید.

You can now distinguish file reading from path traversal, read modes, and make a narrow permission repair. But if an application never starts or keeps stopping, permissions may not be the answer. Next we will follow a process into systemd and investigate why a service will not start.
