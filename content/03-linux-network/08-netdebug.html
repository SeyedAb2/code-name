عیب‌یابی: ping، traceroute، ss، tcpdumpDebugging: ping, traceroute, ss, tcpdump

تیکت فقط نوشته «سایت باز نمی‌شه». همین جمله می‌تونه از DNS باشه تا route، firewall، port یا خود برنامه. اگه از وسط شروع کنیم، ممکنه نیم ساعت چیز سالم رو دستکاری کنیم. بیا از نزدیک‌ترین نقطه به برنامه شروع کنیم و هر مرز رو با یک شاهد رد کنیم.

The ticket says only: “The network is broken.” Set that sentence aside. curl times out; we need to learn whether name resolution failed, the route was wrong, no listener owned the port, a firewall blocked it, TLS stalled, or the application returned HTTP 500.

از سؤال دقیق شروع کنیمStart with a precise question

قاعدهٔ این فصل ساده‌ست: هر بار فقط یک سؤال. آیا اسم resolve می‌شه؟ آیا IP در دسترسه؟ آیا TCP وصل می‌شه؟ آیا HTTP جواب می‌ده؟ جواب هر مرحله می‌گه قدم بعدی کجاست.

Last chapter separated the host’s address, DNS answer, and kernel route decision. Now we will find how far a real request gets. Resolve the name, inspect the route, probe the TCP port, read the TLS/HTTP response, and capture packets if the boundary is still unclear.

از چپ به راست جلو برو؛ هر ابزار فقط یک مرز رو روشن می‌کنه، نه کل مسیر رو.

Move left to right; each tool illuminates one boundary, not the entire path.

ping جواب می‌ده؛ پس چرا صفحه باز نمی‌شه؟Ping replies, so why does the page still fail?

ping پیام ICMP Echo می‌فرسته و برای پاسخ ICMP Echo Reply منتظر می‌مونه. یک reply شاهدی هست که در اون لحظه اون نوع ترافیک بین دو نقطه رفت‌وبرگشت داشته؛ ثابت نمی‌کنه TCP/443 باز هست، TLS درست هست یا برنامه سالم هست.

ping sends ICMP Echo Requests and waits for Echo Replies. A reply is evidence that this type of traffic made a round trip at that moment; it does not prove TCP/443 is open, TLS works, or the application is healthy.

bounded ICMP check
ping -c 3 -W 2 203.0.113.20

-c 3 تعداد درخواست‌ها رو محدود می‌کنه؛ در iputils لینوکس -W timeout پاسخ رو بر حسب ثانیه می‌گیره، اما جزئیات گزینه‌ها میان پیاده‌سازی‌ها فرق می‌کنه. اگه loss صفر نیست یا پاسخ نمیاد، این می‌تونه packet loss، فیلتر ICMP یا میزبان خاموش باشه؛ نمی‌گه کدوم‌یک. اگه ping بسته هست، آزمون TCP رو جدا اجرا کن.

-c 3 bounds the request count. On Linux iputils, -W sets a reply timeout in seconds, though option details vary across implementations. Packet loss or no reply could mean loss, filtered ICMP, or an unavailable host; it does not distinguish them. If ping is blocked, test TCP separately.

برعکسش هم ممکنه: ping پاسخ نگیره ولی HTTPS کار کنه؛ ICMP ممکنه فیلتر باشه درحالی‌که TCP مجاز هست. پس برای کاربر وب، پاسخ واقعی HTTP از ping کاربردی‌تر هست.

The reverse also happens: ping can fail while HTTPS works because ICMP is filtered and TCP is allowed. For a web user, an actual HTTP response is more relevant than ping.

بسته از کدوم‌جا ناپدید شد؟Where did the packet disappear?

وقتی میزبان دور جواب نمی‌ده، traceroute یا tracepath تلاش می‌کنه مسیر رو با TTL/hop limitهای پله‌ای آشکار کنه. بعضی روترها پاسخ نمی‌دن یا ICMP لازم رو فیلتر می‌کنن؛ ستاره (*) یعنی پاسخی در مهلت ابزار نگرفتیم، نه اینکه حتماً همون hop شبکه خراب هست.

When a remote host does not answer, traceroute or tracepath tries to reveal the path with increasing TTL/hop limits. Some routers do not reply or filter the needed ICMP; an asterisk means no response arrived before the tool’s timeout, not that this hop is definitely broken.

choose whichever tool exists
tracepath -n 203.0.113.20
traceroute -n -m 12 -w 1 203.0.113.20

این دو خط جایگزین یکدیگرند، لازم نیست هر دو نصب باشن. -n از lookup نام hopها صرف‌نظر می‌کنه؛ -m و -w در traceroute لینوکس تعداد hop و مهلت رو محدود می‌کنن. mode پیش‌فرض traceroute ممکنه UDP یا ICMP/TCP باشه و با گزینه‌ها/نسخه فرق می‌کنه؛ خروجی رو به‌عنوان مشاهدهٔ همون mode بخوان، نه نقشهٔ قطعی شبکه.

These are alternatives; you may not have both installed. -n skips hop-name lookups; Linux traceroute’s -m and -w bound hop count and wait. The default traceroute mode may use UDP or ICMP/TCP depending on options and version; treat results as observations from that mode, not a definitive network map.

برای مقصدی که route نداریم، فصل قبل ip route get رو دیدیم؛ حالا با یک probe واقعی مرز بعدی رو می‌سنجیم. nc -vz -w 2 HOST PORT می‌تونه اتصال TCP کوتاه بسازه، اما گزینه‌های nc میان OpenBSD، GNU و BusyBox یکسان نیستن و UDP scan با -u -z شاهد قابل اتکایی از باز بودن پورت نمی‌ده.

For a destination with a route, last chapter’s ip route get showed the local choice; now we probe the next boundary. nc -vz -w 2 HOST PORT can attempt a brief TCP connection, but options vary among OpenBSD, GNU, and BusyBox netcat. A UDP -u -z scan is not reliable evidence that a port is open.

bounded TCP probe
nc -vz -w 2 203.0.113.20 443

«succeeded» فقط handshake TCP از همین client تا اون IP/port رو نشون می‌ده؛ HTTP، TLS یا مجوز کاربر رو نه. «refused» معمولاً یعنی مقصد یا middlebox فعالانه RST/Reject داده؛ «timeout» معمولاً یعنی جوابی در مهلت نرسیده. یکسان بودن پیام ابزارها در همهٔ سیستم‌ها تضمین نیست.

“Succeeded” shows a TCP handshake from this client to that IP/port, not HTTP, TLS, or user authorization. “Refused” commonly means the destination or a middlebox actively reset/rejected it; “timeout” means no answer arrived in time. Exact wording is not universal.

روی سرور کسی واقعاً گوش می‌ده؟Is anything actually listening on the server?

روی خود سرور، ss -lntp socketهای TCP در حالت LISTEN رو فهرست می‌کنه. سطر 127.0.0.1:8080 فقط loopback رو می‌پذیره؛ 0.0.0.0:8080 به همهٔ آدرس‌های IPv4 محلی bind شده؛ [::]:8080 برای IPv6 هست و رفتار پذیرش IPv4 می‌تونه به تنظیم سیستم وابسته باشه.

On the server, ss -lntp lists TCP sockets in LISTEN state. 127.0.0.1:8080 accepts only loopback; 0.0.0.0:8080 is bound to all local IPv4 addresses; [::]:8080 is IPv6, and whether it also accepts IPv4 can depend on system settings.

inspect listeners and owning process
sudo ss -lntp
ss -tn state established
ss -s

اگه سطر listener نیست، connection از اون پورت به برنامه نمی‌رسه؛ اگه listener هست، هنوز ثابت نشده interface مناسب رو گرفته یا برنامه جواب درست می‌ده. بدون sudo ممکنه نام processها پنهان باشه. گزینه‌ها و خروجی‌های جزئی ss تابع نسخهٔ iproute2 هست.

Without a listener, a connection to that port cannot reach an application socket. With one, you still have not proved it is bound to the right interface or responds correctly. Without sudo, process names may be hidden. Some ss options and details depend on iproute2 version.

curl دقیقاً تا کدوم مرحله رسید؟How far did curl get?

برای HTTP، curl -v خط‌های شروع با * رو روی stderr می‌نویسه: resolve، اتصال TCP، TLS و بعد HTTP headers رو جدا دنبال کن. از timeout استفاده کن تا آزمایش خودش معلق نمونه.

For HTTP, curl -v writes * diagnostic lines to stderr. Follow resolution, TCP connect, TLS, and then HTTP headers as separate stages. Add a timeout so the experiment does not hang.

a bounded request with visible headers
curl -v --connect-timeout 2 --max-time 5 -D - http://SERVER_IP:8080/

Connected to یعنی TCP برقرار شده؛ > GET درخواست ارسالی و < HTTP/1.1 500 پاسخ HTTP برنامه/پروکسی رو نشون می‌ده. curl به‌طور معمول برای HTTP 500 هم ممکنه exit code صفر بده چون انتقال انجام شده؛ --fail-with-body در نسخه‌های جدیدتر برای HTTP خطای 400+ exit غیرصفر می‌ده، اما body رو نگه می‌داره. اول HTTP وضعیت رو بخوان، نه فقط exit code.

Connected to means TCP connected; > GET is the outgoing request, and < HTTP/1.1 500 is an HTTP response from the application or proxy. By default, curl may exit zero for HTTP 500 because the transfer succeeded. On versions supporting it, --fail-with-body returns non-zero for HTTP 400+ while retaining the body. Read the HTTP status, not only the exit code.

برای تفکیک DNS از خود وب‌سرور، curl --resolve host:port:IP URL نام رو برای همون درخواست به IP مشخص می‌بنده، ولی hostname در URL باقی می‌مونه؛ پس Host header و TLS SNI نام اصلی‌اند. این ابزار برای اثبات «پورت در IP درست کار می‌کنه اما lookup عادی نه» مفید هست—به شرط آنکه cache یا proxy دیگری دخالت نکنه.

To separate DNS from the web server, curl --resolve host:port:IP URL pins that name to an IP for one request while keeping the hostname in the URL, so Host and TLS SNI remain correct. This helps test “the service works at the right IP but ordinary lookup does not,” assuming no other cache or proxy changes the path.

bypass only the lookup for this test
curl -v --connect-timeout 2 --max-time 5 \
  --resolve app.example.test:443:203.0.113.20 \
  https://app.example.test/

وقتی پاسخ کافی نیست، چند packet ببینWhen the response is not enough, inspect a few packets

tcpdump روی interface مشخص packetها رو می‌بینه و filter انتخابی رو روی ثبت اجرا می‌کنه. لازم نیست همهٔ ترافیک رو بگیری؛ interface واقعی، host و port رو محدود کن و با -c تعداد رو ببند. ثبت ممکنه دادهٔ حساس داشته باشه، پس روی شبکه‌ای که مجاز به دیدنش نیستی اجرا یا منتشر نکن.

tcpdump observes packets on an interface and applies a capture filter. Do not capture everything: choose the relevant interface, host, and port, then bound the count with -c. Captures may contain sensitive data; never inspect or share traffic you are not authorized to access.

capture only one test flow
sudo tcpdump -ni eth0 -c 12 'host CLIENT_IP and tcp port 8080'

-n از reverse lookup نام‌ها جلوگیری می‌کنه و -i interface رو مشخص می‌کنه؛ اسم eth0 رو با خروجی ip -br link جایگزین کن. TCP [S] SYN، [S.] SYN+ACK و [R.] RST+ACK هست؛ handshake کامل معمولاً SYN، SYN+ACK و ACK داره. timestamp بین client و server باید با ساعت‌ها و منطقهٔ زمانیهای هم‌تراز تفسیر بشه.

-n avoids name lookups and -i selects an interface; replace eth0 with a name from ip -br link. TCP [S] is SYN, [S.] SYN+ACK, and [R.] RST+ACK; a complete handshake normally shows SYN, SYN+ACK, and ACK. Compare timestamps only after accounting for clock and timezone alignment.

اگه SYN روی server دیده شد ولی SYN+ACK یا RST برنگشت، درخواست به نقطهٔ ثبت رسیده، اما پاسخ از آنجا دیده نشده؛ firewall محلی، route برگشت، ثبت point یا offload رو بررسی کن. اگه هیچ packetی نیست، ممکنه interface اشتباه باشه یا traffic به سرور نرسه. نبود packet به‌تنهایی ثابت نمی‌کنه client چیزی نفرستاده هست.

If the server sees a SYN but no SYN+ACK or RST, the request reached the capture point but no reply was observed there; check the local firewall, return route, capture point, and offload. If no packet appears, the interface may be wrong or traffic may not have reached the server. Absence alone does not prove the client sent nothing.

فیلتر ثبت مثل 'tcp port 8080' ترافیک رو قبل از ذخیره/نمایش محدود می‌کنه. فیلتر اشتباه می‌تونه مدرک رو حذف کنه؛ قبل از تفسیر، filter رو روی flow کوچک یا فایل pcap قابل‌اشتراک‌گذاریِ بی‌حساسیت آزمایش کن. برای TLS، tcpdump معمولاً اطلاعات مخزن و handshake رو می‌بینه، نه محتوای رمز‌شده رو.

A capture filter such as 'tcp port 8080' limits packets before display/storage. A wrong filter can discard the evidence; test it against a small flow or a sanitized pcap first. With TLS, tcpdump generally sees metadata and handshake, not encrypted application content.

چهار خرابی؛ چهار نقطهٔ توقف متفاوتFour faults, four different stopping points

در یک شبکهٔ آزمایشگاهی میان دو VM یا دو container، یک web app سبک داشته باش که /ok رو 200 و /fail رو 500 بده. آدرس واقعی server رو ثبت کن. بعد هر بار فقط یک خرابی رو فعال کن و از client همون درخواست زمان‌دار رو بزن؛ قبل از اصلاح، مدرک client و server رو کنار هم بگذار.

In a lab network between two VMs or containers, run a small web app where /ok returns 200 and /fail returns 500. Record the actual server address. Enable one fault at a time and repeat the same bounded request from the client; collect client and server evidence before repair.

«refused» با «timeout» فرق داره، اما هیچ‌کدوم نام پردازه یا علت firewall رو به تو نمی‌گه. ثبت رو از سمت client و server با filter یکسان بگیر تا بفهمی SYN کجا دیده می‌شه و پاسخ کجا ناپدید می‌شه. ساعت‌ها رو قبل از کنار هم گذاشتن logها بسنج.

“Refused” differs from “timeout,” but neither identifies a process or proves a firewall cause. Capture on client and server with a matching filter to see where SYN appears and where the reply disappears. Check clocks before correlating logs.

لَب خرابی: یک مسیر، چند لایهIncident lab: one path, several layers

دو Linux VM/container روی یک شبکهٔ خصوصی آزمایشگاهی بساز؛ یکی server و یکی client. هیچ port یا firewallی رو روی host واقعی تغییر نده. در server یک برنامهٔ سادهٔ محلی اجرا کن که /ok وضعیت 200 و /fail وضعیت 500 بده؛ listen رو روی 0.0.0.0:8080 قرار بده. برای تست از access log برنامه یا لاگ stdout استفاده کن.

Create two Linux VMs/containers on a private lab network: one server and one client. Do not change ports or firewalls on a real host. Run a small server application that returns status 200 at /ok and 500 at /fail, bound to 0.0.0.0:8080. Use its access log or stdout as application evidence.

روی server یک ترمینال برای اجرای برنامه باز بگذار. این handler فقط سه مسیر داره و به بسته اضافه نیاز نداره؛ BaseHTTPRequestHandler درخواست رو می‌گیره و timestamp هر درخواست رو log می‌کنه.

Keep one server terminal open for the application. This handler has only three paths and needs no extra package; BaseHTTPRequestHandler handles requests and logs each request with a timestamp.

run on the disposable server VM
python3 - <<'PY'
from http.server import BaseHTTPRequestHandler, HTTPServer

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        status, body = {
            "/ok": (200, b"ok\\n"),
            "/fail": (500, b"deliberate test error\\n"),
        }.get(self.path, (404, b"not found\\n"))
        self.send_response(status)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

HTTPServer(("0.0.0.0", 8080), Handler).serve_forever()
PY

در server، ss -lntp باید listener روی *:8080 یا آدرس lab رو نشان بده. در client، getent ahosts SERVER_NAME رو ثبت و بعد curl -v --connect-timeout 2 --max-time 5 http://SERVER_IP:8080/ok اجرا کن. هم وضعیت HTTP رو ثبت کن، هم exit code؛ این دو پاسخ به دو سؤال فرق دارن.

On the server, ss -lntp should show a listener on *:8080 or the lab address. On the client, record getent ahosts SERVER_NAME, then run a bounded curl to /ok. Record both HTTP status and process exit status; they answer different questions.

خرابی اول رو با hostname اشتباه فعال کن: getent/curl باید قبل از اتصال شکست بخورند، ولی درخواست به IP ثبت‌شده ممکنه 200 بده. اصلاح یعنی اصلاح نام یا پیکربندی lab؛ تغییر resolver اصلی host لازم نیست. برای جداکردن نام از اتصال، یک بار از curl --resolve استفاده کن.

For the first fault, use a deliberately wrong hostname: getent/curl should fail before connecting, while a request to the recorded IP may return 200. Repair the lab name/configuration; do not change the host resolver. Use curl --resolve once to isolate name resolution.

خرابی دوم رو با port اشتباه فعال کن. nc -vz -w 2 SERVER_IP 8081 یا curl باید refusal ببینه؛ روی server ss -lntp رو دوباره بخوان و دنبال تفاوت 8080/8081 بگرد. بعد به پورت درست برگرد و همون درخواست رو تکرار کن.

For the second fault, target the wrong port. nc -vz -w 2 SERVER_IP 8081 or curl should see a refusal; recheck ss -lntp on the server and compare 8080 with 8081. Return to the correct port and repeat the same request.

برای firewall drill، فقط اگه VM یک‌بارمصرف با console در دسترس داری و سیاست اون برای آزمایش روشن هست، از ابزار مدیریت firewall همون توزیع یک قانون موقت و محدود به client IP/8080 اضافه کن که درخواست رو reject یا drop کنه. قبل از اون قانونهای فعلی رو ثبت کن؛ بعد از ثبت و probe همون قانون رو دقیقاً حذف و اتصال رو دوباره بررسی نهایی کن. دستورهای nftables/ufw فصل بعدند؛ اگه مجاز یا مطمئن نیستی، این مرحله رو با packet trace آمادهٔ مدرس تحلیل کن و firewall زنده رو تغییر نده.

For the firewall drill, only on a disposable VM with console access and a known test policy, add a temporary rule through that distribution’s firewall manager, narrowly scoped to the client IP and port 8080, to reject or drop the request. Record existing rules first; remove that exact rule after the capture/probe and verify connectivity again. nftables/ufw commands belong to the next chapter; if you are not authorized or sure, analyze a supplied trace instead and do not alter a live firewall.

optional — disposable Linux VM only, nftables example
sudo nft list ruleset
sudo nft add table inet codenames_lab
sudo nft add chain inet codenames_lab input '{ type filter hook input priority 0; policy accept; }'
sudo nft add rule inet codenames_lab input ip saddr CLIENT_IP tcp dport 8080 counter drop

# after capturing the timeout, remove only the lab table:
sudo nft delete table inet codenames_lab

این مثال فقط برای IPv4 و VM یک‌بارمصرف هست؛ CLIENT_IP رو جایگزین کن و قبلش مطمئن شو نام جدول تازه هست. حذف جدول آزمایش تمام تغییر این نمونه رو پاک می‌کنه. اگه دسترسی قطع شد، از console حذفش کن؛ این دستور رو روی host زنده یا بدون اجازه اجرا نکن.

This example is for IPv4 and a disposable VM only; replace CLIENT_IP and confirm the table name is unused. Deleting the lab table removes this example’s change. If access is interrupted, remove it from the console; do not run this on a live host or without authorization.

خرابی آخر /fail رو درخواست کن. انتظار داریم TCP وصل بشه و HTTP 500 دیده بشه. در همون timestamp، log برنامه رو پیدا کن؛ اگه logی نیست، پاسخ HTTP هنوز ثابت نمی‌کنه علت داخل کدوم تابع هست. اصلاح رو در برنامه انجام بده، سپس /ok و مسیر اصلاح‌شده رو دوباره امتحان کن.

For the final fault, request /fail. TCP should connect and HTTP 500 should be visible. Find the application log at the same timestamp; without one, the HTTP response still does not identify which function failed. Repair the application, then retest /ok and the repaired path.

در هر مرحله نتیجه رو با timestamp یادداشت کن. ثبت رو کوتاه و محدود بگیر: sudo tcpdump -ni SERVER_IF -c 20 'host CLIENT_IP and tcp port 8080'. اگه چند interface داری، any روی Linux برای دیدن همه‌شان مفید هست ولی ممکنه duplicate ظاهر بشه. فایل pcap رو فقط اگه واقعاً لازمه ذخیره کن و قبل از اشتراک‌گذاری payload/نشانی‌های حساس رو حذف یا ناشناس کن.

Record timestamps at every stage. Keep capture short and filtered. On Linux, any can include several interfaces but may show duplicates. Save a pcap only when needed, and remove or anonymize sensitive payloads/addresses before sharing.

پایان خرابی وقتی هست که همون درخواست اولیه دوباره پاسخ درست بده و شواهد client، server و برنامه با هم سازگار باشن. «ping جواب داد» یا «قانون رو تغییر دادم» به‌تنهایی آزمون تحویل نیست.

The incident is complete when the original request returns the expected response and client, server, and application evidence agree. “Ping replied” or “I changed a rule” is not an acceptance test by itself.

تمرین‌ها: جملهٔ «شبکه خرابه» رو بازنویسی کنExercises: replace “the network is broken”

۱. ping موفق1. Ping succeeds

ping جواب می‌ده اما HTTPS timeout هست. سه چیزی که ping ثابت نکرده چیست؟

Ping replies but HTTPS times out. Name three things ping did not prove.

پاسخSolution

TCP/443، handshake TLS و پاسخ برنامه رو ثابت نکرد. بعد با nc اتصال TCP و با curl -v مراحل TLS/HTTP رو جدا کن.

It proved neither TCP/443, TLS negotiation, nor application response. Separate these with nc and curl -v.

۲. ping بسته، TCP باز2. Ping blocked, TCP works

ping timeout می‌شه ولی nc -vz host 443 وصل می‌شه. تناقض هست؟

Ping times out but nc -vz host 443 connects. Is that contradictory?

پاسخSolution

نه؛ ICMP و TCP دو پروتکل/سیاست جدا هستن. TCP handshake شاهد خوبی برای همون port هست؛ ICMP ممکنه فیلتر باشه.

No; ICMP and TCP are separate protocols and policies. The handshake is evidence for that port; ICMP may be filtered.

۳. timeout در hop دوم3. A timeout at hop two

traceroute در hop دوم * * * داره ولی مقصد بعداً پاسخ می‌ده. کدوم نتیجه مجاز هست؟

Traceroute shows * * * at hop two, but the destination responds later. What conclusion is justified?

پاسخSolution

اون hop به probe یا مهلت ابزار جواب نداده؛ چون مقصد رسیدنی هست، ستاره به‌تنهایی خرابی forwarding اون hop رو ثابت نمی‌کنه. ممکنه control-plane اون پاسخ‌ها رو فیلتر کنه.

That hop did not answer the probe before timeout. Since the destination is later reached, the star alone does not prove forwarding failed there; its control plane may filter replies.

۴. refused یا timeout؟4. Refused or timed out?

یک port بلافاصله connection refused می‌ده و port دیگر timeout می‌شه. چه تفاوتی در شواهد داری؟

One port immediately returns connection refused; another times out. How does the evidence differ?

پاسخSolution

اولی معمولاً پاسخ فعال RST/Reject دیده؛ دومی در مهلت پاسخی نگرفته. این هنوز علت دقیق رو مشخص نمی‌کنه؛ ss روی server و ثبت دوطرفه کمک می‌کنه.

The first commonly received an active reset/reject; the second got no reply in time. Neither identifies the exact cause; server-side ss and captures from both ends help.

۵. listener فقط روی loopback5. Listener bound only to loopback

ss می‌گه 127.0.0.1:8080. client راه‌دور به IP شبکه وصل نمی‌شه. چه چیزی رو اصلاح می‌کنی؟

ss shows 127.0.0.1:8080; a remote client cannot connect to the network IP. What do you change?

پاسخSolution

اگه قرار هست remote client مجاز باشه، برنامه رو روی interface مناسب یا 0.0.0.0 bind کن و دوباره ss رو ببین. بعد firewall و دسترسی رو بسنج؛ bind سراسری exposure رو هم زیاد می‌کنه.

If remote clients should be allowed, bind to the intended interface or 0.0.0.0 and recheck ss. Then verify firewall and access controls; wildcard binding also increases exposure.

۶. پردازه نامعلوم6. Unknown process

ss -lntp پورت رو نشون می‌ده اما نام پردازه رو نه. اولین احتمال؟

ss -lntp shows the port but no process name. What is the first likely explanation?

پاسخSolution

ممکنه permission کافی نداشته باشی؛ با مجوز مجاز sudo ss -lntp رو امتحان کن. پردازه مخفی بودن به معنی نبود listener نیست.

You may lack permission; try sudo ss -lntp if authorized. A hidden process name does not mean no listener exists.

۷. curl وضعیت 500 و exit صفر7. curl reports HTTP 500 but exits zero

چرا ممکنه curl برای HTTP 500 exit code صفر بده؟

Why might curl exit zero for HTTP 500?

پاسخSolution

انتقال HTTP موفق انجام شد؛ وضعیت برنامه در سطح HTTP هست. وضعیت line رو بخوان یا رفتار --fail-with-body رو در نسخهٔ نصب‌شده بررسی کن.

The HTTP transfer completed; the application status is at the HTTP layer. Read the status line or check whether the installed curl supports --fail-with-body.

۸. TLS شکست خورد8. TLS fails

curl گزارش Connected to می‌ده و سپس certificate hostname mismatch داره. DNS/route/TCP چه وضعی دارن؟

curl reports Connected to, then a certificate hostname mismatch. What do you know about DNS, route, and TCP?

پاسخSolution

این تلاش به اتصال TCP رسیده و TLS هم شروع شده؛ مشکل فعلی با نام certificate در TLS هست. -k رو برای پنهان‌کردن خطا استفاده نکن؛ certificate/SNI/hostname مورد انتظار رو درست کن.

This attempt reached TCP and began TLS; the current failure is certificate-name validation. Do not hide it with -k; correct the certificate, SNI, or expected hostname.

۹. nc موفق شد9. nc succeeded

nc -vz به 443 وصل شد. آیا ثابت شد login یا صفحهٔ اصلی درست هست؟

nc -vz connected to 443. Does that prove login or the homepage works?

پاسخSolution

نه؛ فقط TCP handshake تا endpoint موفق بوده. برای TLS و HTTP curl -v و برای منطق برنامه پاسخ endpoint/log لازمه.

No; it proves only a TCP handshake to that endpoint. Use curl -v for TLS/HTTP and endpoint/log evidence for application behavior.

۱۰. SYN بدون SYN+ACK10. SYN without SYN+ACK

server-side tcpdump، SYN رو می‌بینه اما پاسخ نمی‌بینه. چهار احتمال رو فهرست کن.

A server-side capture sees SYN but no reply. List four possibilities.

پاسخSolution

firewall محلی drop می‌کنه، route برگشت خراب هست، ثبت روی نقطه/interface ناقص هست، یا پاسخ از مسیر دیگر/با offload خارج شده و اینجا دیده نمی‌شه. قواعد و ss رو هم‌زمان بررسی کن.

A local firewall drops it, the return route is wrong, the capture point/interface is incomplete, or the reply leaves elsewhere/is hidden by offload. Check firewall state and ss too.

۱۱. RST از کجا آمد؟11. Where did the RST come from?

tcpdump در سمت client RST می‌بینه. آیا قطعاً خود پردازه اون رو فرستاد؟

A client-side capture sees RST. Did the application process definitely send it?

پاسخSolution

نه؛ kernel وقتی listener نیست ممکنه RST بسازه، یا middlebox اون رو تولید کنه. ثبت سمت server و ss رو برای تشخیص مرز اضافه کن.

No; the kernel may reset when no listener exists, or a middlebox may generate it. Add a server-side capture and ss to locate the boundary.

۱۲. filter هیچ packetی نگرفت12. The capture filter matched nothing

tcpdump صفر packet نشون می‌ده. قبل از نتیجه‌گیری، چه چیزهایی رو چک می‌کنی؟

tcpdump shows zero packets. What do you check before concluding anything?

پاسخSolution

interface، IP واقعی، port، protocol، زمان اجرای ثبت و جهت traffic رو بررسی کن. filter رو ساده‌تر کن و -c رو موقتاً بردار یا روی flow خودت بازتولید کن؛ ممکنه filter اشتباه packet لازم رو حذف کرده باشه.

Check interface, actual IP, port, protocol, capture timing, and direction. Simplify the filter and reproduce your own flow; a wrong filter may have excluded the needed packets.

۱۳. timestampها فرق دارن13. Timestamps disagree

log سرور یک دقیقه بعد از ثبت client هست. آیا packet یک دقیقه در راه بوده؟

The server log is one minute later than the client capture. Was the packet in transit for a minute?

پاسخSolution

نه می‌شه چنین گفت نه رد کرد؛ ساعت/zone/clock sync دو میزبان رو بررسی کن و request ID رو اگه هست تطبیق بده. timestampها بدون ساعت هم‌تراز زمان latency رو ثابت نمی‌کنن.

You cannot infer that. Check clock synchronization/timezones and correlate request IDs if available. Unsynchronized timestamps do not establish latency.

۱۴. traceroute همه‌جا ستاره14. Traceroute shows only stars

همهٔ hopها * هستن ولی curl موفق هست. کدوم ابزار رو باور می‌کنی؟

Every traceroute hop is *, but curl succeeds. Which tool do you trust?

پاسخSolution

هیچ‌کدوم رو مطلق نمی‌کنم؛ curl مسیر کاربردی TCP/HTTP رو ثابت کرده و traceroute فقط جواب probeهایش رو نگرفته. سیاست فیلتر ICMP/UDP رو در نظر بگیر.

Neither is absolute. curl proves the application path worked; traceroute did not receive replies to its probes. Consider ICMP/UDP filtering policy.

۱۵. /fail پاسخ 500 داره15. /fail returns 500

TCP handshake کامل هست و curl وضعیت 500 داره. مشکل رو در کدوم لایه دنبال می‌کنی؟

The TCP handshake completes and curl reports 500. Which layer do you investigate?

پاسخSolution

برنامه یا proxy درخواست رو دریافت و پاسخ HTTP ساخته؛ body و log هم‌زمان رو بخوان. port scan یا route تغییر دادن علت application error رو پیدا نمی‌کنه.

The application or proxy received the request and produced an HTTP response. Inspect the body and correlated logs; route changes or port scans will not diagnose an application error.

۱۶. tcpdump فایل می‌نویسه16. tcpdump writes a capture file

چه ریسکی داره ثبت رو با -w traffic.pcap نگه داری و بفرستی؟

What is the risk of keeping and sharing a capture made with -w traffic.pcap?

پاسخSolution

ممکنه payload، نشانی‌ها، queryها یا اطلاعات حساس داشته باشه. فقط ترافیک مجاز و محدود ضبط کن، فایل رو محافظت/حذف کن و قبل از share کردن محتوا رو پالایش کن.

It may contain payloads, addresses, queries, or sensitive data. Capture only authorized, scoped traffic, protect/delete the file, and sanitize it before sharing.

۱۷. curl به IP جواب می‌ده17. curl works by IP

URL با IP گواهی TLS رو رد می‌کنه؛ با hostname DNS خراب هست. چطور آزمون رو جدا می‌کنی بی‌آنکه -k بزنی؟

TLS rejects the certificate when the URL uses an IP, while hostname DNS is broken. How can you isolate the test without using -k?

پاسخSolution

از curl --resolve hostname:443:IP https://hostname/ استفاده کن؛ Host/SNI همون نام باقی می‌مونه ولی lookup این درخواست به IP داده‌شده می‌ره. این DNS سراسری رو اصلاح نمی‌کنه.

Use curl --resolve hostname:443:IP https://hostname/; Host and SNI remain correct while this request uses the supplied IP. It does not repair system-wide DNS.

۱۸. تحویل خرابی18. Incident handoff

کاربر می‌گه «شبکه خرابه»، ولی تو فقط یک ساعت وقت داری. چه داده‌هایی رو در گزارش کوتاه ثبت می‌کنی تا تیم بعدی تکرارپذیر ادامه بده؟

A user says “the network is broken,” and you have one hour. What belongs in a short report so the next team can reproduce the diagnosis?

راهنماHint

نام، IP، port، ساعت، مرحلهٔ آخر موفق و مدرک همون مرز.

Name, IP, port, time, last successful layer, and evidence at that boundary.

پاسخSolution

hostname و IP resolveشده، route/مبدأ/interface، probe زمان‌دار و نتیجه‌اش، listener سمت سرور، HTTP/TLS وضعیت، چند خط ثبت محدود و timestamp هم‌تراز رو ثبت کن. secret یا pcap حساس رو پیوست نکن. بنویس هر مدرک چه چیزی رو ثابت می‌کنه و چه چیزی رو نه؛ بعد از اصلاح همون probe اولیه رو دوباره اجرا کن.

Record hostname and resolved IP, route/source/interface, a bounded probe and its outcome, server listener, HTTP/TLS status, a short scoped capture, and aligned timestamps. Do not attach secrets or sensitive pcaps. State what each item proves and does not prove, then repeat the original probe after repair.

وقتی firewall مرز مشکل شد، اون رو جدا بررسی می‌کنیمWhen the firewall is the boundary, inspect it separately

حالا می‌تونی به‌جای «شبکه قطع هست» بگویی «DNS جواب می‌ده، route از ens3 هست، SYN به سرور می‌رسه اما پاسخ نمیاد» یا «TCP وصل هست و برنامه 500 می‌ده». در فصل بعد سراغ firewall می‌ریم تا قانونهای مجاز/مسدودکننده رو بخونیم—اما فقط وقتی evidence همین لایه رو نشانه گرفته باشه.

You can now replace “the network is down” with “DNS answers, the route uses ens3, SYN reaches the server but no reply returns,” or “TCP connects and the application returns 500.” Next we will inspect firewall rules—but only when evidence points to that layer.
