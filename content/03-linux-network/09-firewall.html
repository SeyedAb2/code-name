فایروال: nftables / ufwFirewalls: nftables / ufw

یک rule جدید می‌نویسی تا برنامهٔ آزمایشی فقط از یک port در دسترس باشد. چند ثانیه بعد، SSH هم جواب نمی‌دهد. فایروال دقیقاً policyای را اجرا کرد که نوشته بودی—مشکل این بود که راه برگشت را قبل از تغییر آماده نکرده بودی.

You add a rule so a test application is reachable on only one port. Seconds later, SSH stops responding too. The firewall did exactly what the written policy said—the problem was that you had no recovery path ready before changing it.

فایروال قرار است چه تصمیمی بگیرد؟What decision is the firewall making?

در فصل قبل دیدیم SYN به server می‌رسد اما گاهی جواب برنمی‌گردد. فایروال یکی از جاهایی است که می‌تواند packet را قبول کند، رد کند یا بی‌صدا دور بیندازد. policy خوب از «همه‌چیز را ببند» شروع نمی‌شود؛ از این سؤال شروع می‌شود: کدام ارتباط ورودی واقعاً باید برقرار باشد؟

Last chapter showed that a SYN may reach the server without a reply. A firewall is one place where a packet can be accepted, rejected, or silently dropped. Good policy does not start with “block everything”; it starts with: which inbound connections must actually work?

روی Linux، netfilter در kernel مسیر packet را می‌بیند؛ nftables رابط مدرن تنظیم آن است. ufw یک ابزار ساده‌تر برای نوشتن policyهای رایج است و در Ubuntu Server معمولاً frontend پیشنهادی است. این دو را بی‌برنامه با هم قاطی نکن: هر دو می‌توانند روی همان زیرساخت kernel اثر بگذارند، ولی مالکیت ruleها و ترتیب chainها مهم است.

On Linux, kernel netfilter handles packet paths; nftables is the modern rules interface. ufw is a simpler frontend for common policies and is the usual recommended tool on Ubuntu Server. Do not mix them casually: both can affect the same kernel subsystem, and ownership/order of chains matters.

packet ورودی وارد input chain می‌شود؛ state و ruleهای مرتب‌شده نتیجه را می‌سازند. ادامهٔ اتصال SSH با مجوز اتصال تازه یکی نیست.

An inbound packet enters the input chain; state and ordered rules determine the verdict. Continuing SSH traffic is not the same as permitting a new connection.

فایروال host فقط یکی از لایه‌هاست؛ provider firewall، security group، router یا firewall داخل container هم ممکن است همان traffic را جداگانه فیلتر کند. rule محلی که اجازه می‌دهد، مانع provider را برنمی‌دارد.

The host firewall is only one layer; a provider firewall, security group, router, or container firewall may independently filter the same traffic. A local allow rule cannot remove a provider-side block.

بسته به کدام طرف میزبان می‌رود؟Which way is the packet crossing the host?

سه مسیر را از هم جدا کن. input بسته‌ای است که مقصدش همین host است—مثلاً SSH یا HTTP روی خود VPS. output از برنامهٔ همین host بیرون می‌رود—مثلاً اتصال DNS یا درخواست به API. forward از این host عبور می‌کند تا به ماشین دیگری برسد؛ router یا بعضی سناریوهای container با آن سروکار دارند.

Separate three paths. input is traffic destined for this host, such as SSH or HTTP on the VPS. output is traffic originated by a local process, such as DNS or an API request. forward passes through this host toward another machine; routers and some container scenarios use it.

اشتباه گرفتن input و forward دردسر رایجی است: اگر request به host می‌رسد و قرار است یک process همان‌جا جواب بدهد، معمولاً input را بررسی می‌کنی، نه forward. ip route و ss فصل قبل کمک می‌کنند تشخیص دهی packet کجا مقصد دارد و آیا listener محلی هست.

Confusing input and forward is common: if a request is destined to a local process, inspect input, not forward. Last chapter’s ip route and ss help determine where the packet is addressed and whether a local listener exists.

چرا برای هر reply یک allow جدا لازم نیست؟Why is there no separate allow for every reply?

یک client اتصال TCP را آغاز می‌کند و server پاسخ را برمی‌گرداند. فایروال stateful ارتباط را در conntrack دنبال می‌کند؛ قاعدهٔ ct state established,related accept به packetهای شناخته‌شدهٔ اتصال و بعضی ترافیک مرتبط اجازه می‌دهد. این برای برگشت پاسخ‌هاست، نه مجوز شروع هر اتصال جدید از هرجا.

A client starts a TCP connection and the server replies. A stateful firewall tracks the flow in conntrack; ct state established,related accept permits packets belonging to known connections and certain related traffic. This handles replies—it does not authorize every new connection from everywhere.

new معمولاً شروع اتصالی است که هنوز رفت‌وبرگشت کامل نشده؛ established flow شناخته‌شده‌ای است که ترافیک معتبر دوطرفه داشته؛ related اتصال جداگانه‌ای است که به flow موجود ارتباط دارد. این stateها برچسب‌های conntrack هستند، نه verdict. ruleهای بالاتر/پایین‌تر تعیین می‌کنند با هرکدام چه شود.

new commonly marks a connection beginning before a full exchange; established is a tracked flow with valid traffic in both directions; related is a separate flow associated with an existing one. These are conntrack labels, not verdicts. Rules decide what happens to each.

در nftables ruleها داخل chain به ترتیب بررسی می‌شوند. accept و drop verdict می‌دهند؛ priority میان base chainهایی است که به hook وصل‌اند، نه یک عدد برای همهٔ ruleها. اگر چند base chain روی یک hook باشند، accept در یکی لزوماً جلوی بررسی chain بعدی را نمی‌گیرد؛ rule بعدی هم ممکن است packet را drop کند. در این فصل chain جداگانهٔ یک مدیر دیگر را روی host عملیاتی اضافه نمی‌کنیم؛ اول ruleset موجود را می‌خوانیم و مالک آن را پیدا می‌کنیم.

Within an nftables chain, rules are checked in order. accept and drop give verdicts; priority orders base chains attached to a hook, not every rule globally. If several base chains share a hook, accept in one does not necessarily prevent a later chain from dropping the packet. This chapter does not add another manager’s chain to a production host; inspect the existing ruleset and identify its owner.

قبل از تغییر، آنچه همین حالا فعال است بخوانBefore changing anything, inspect what is active

روی هر سیستم اول بپرس کدام frontend صاحب policy است. روی Ubuntu، ufw status verbose خلاصهٔ policy و ruleهای UFW را می‌دهد؛ nft list ruleset نمای kernel از rulesetهای nftables را نشان می‌دهد. خروجی یکی جای دیگری را نمی‌گیرد و ممکن است ابزارهای دیگر ruleهای kernel را ساخته باشند.

First identify which frontend owns the policy. On Ubuntu, ufw status verbose summarizes UFW policy and rules; nft list ruleset shows nftables rulesets in the kernel. Neither output replaces the other, and other tools may have created kernel rules.

read-only inventory
sudo ufw status verbose
sudo ufw status numbered
sudo nft list ruleset
sudo systemctl status nftables

اگر UFW می‌گوید inactive، این ثابت نمی‌کند host هیچ فایروالی ندارد؛ ruleset nftables یا provider firewall را جدا ببین. اگر nftables.service inactive است، ممکن است NetworkManager، container runtime یا ابزار دیگری ruleها را مدیریت کند. قبل از دست‌کاری، از وضعیت و فایل پیکربندی snapshot بگیر.

If UFW says inactive, that does not prove the host has no firewall; inspect nftables and provider firewalls separately. If nftables.service is inactive, NetworkManager, a container runtime, or another tool may own the rules. Snapshot the current state and configuration before editing.

با UFW policy را واضح بنویسUse UFW to express a clear policy

برای یک VPS معمول Ubuntu، سؤال روشن است: پاسخ‌های ارتباط‌های شروع‌شده از داخل را نگه دار؛ از بیرون فقط SSH و port برنامه را باز بگذار. UFW را بعد از دیدن status و تأیید دسترسی console/rollback تنظیم می‌کنیم—نه با خاموش‌کردن firewall موجود.

For a typical Ubuntu VPS, the policy is clear: allow replies to outbound connections; expose only SSH and the application port inbound. Configure UFW only after checking status and confirming console/rollback access—not by disabling an existing firewall.

example policy — disposable Ubuntu VM first
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 8080/tcp
sudo ufw status verbose

سطرهای status باید policy ورودی deny، خروجی allow و اجازهٔ OpenSSH و 8080/tcp را نشان دهند. OpenSSH نام application profile است و روی هر نصب تضمین‌شده نیست؛ پیش از آن sudo ufw app list را ببین یا پورت واقعی SSH را صریح بنویس. هنوز فعال‌کردن policy و آزمون از client را انجام نداده‌ای؛ status فعلی ممکن است فقط draft را نشان دهد.

The status should show inbound deny, outbound allow, and permits for OpenSSH and TCP/8080. OpenSSH is an application profile and may not exist on every installation; check sudo ufw app list or allow the actual SSH port explicitly. You have not yet enabled and tested the policy from a client; current status may only show a draft.

پیش از ufw enable اگر SSH راه مدیریت توست، باید همان port واقعی و address family درست مجاز باشد. روی VM یک‌بارمصرف با کنسول باز، اجازهٔ SSH را اضافه کن، بعد اجازهٔ برنامه را؛ ruleهای شماره‌دار را ثبت و سپس از client جدید اتصال را آزمایش کن. فعال‌کردن policy فقط بعد از این checkpoint می‌آید.

Before ufw enable, if SSH is your management path, its actual port and address family must be allowed. On a disposable VM with console open, add SSH and application rules, record numbered rules, then test from a new client connection. Enabling the policy comes only after this checkpoint.

enable only after the recovery path is ready
sudo ufw --force enable
sudo ufw status numbered

اگر خروجی Status: active است و ruleهای 22/SSH و 8080 را می‌بینی، از ماشین client یک اتصال تازه به هر دو بزن؛ اتصال SSH فعلی را به‌عنوان تنها مدرک حساب نکن. ufw delete NUMBER یک rule را با شماره حذف می‌کند؛ شماره بعد از تغییر فهرست عوض می‌شود، پس درست پیش از حذف دوباره status numbered را بخوان.

If status is active and the SSH/22 and 8080 rules appear, open fresh connections from a client. Do not count the current SSH session as the only proof. ufw delete NUMBER removes a rule by number; numbering changes after edits, so re-read status numbered immediately before deleting.

UFW معمولاً IPv6 را هم مدیریت می‌کند وقتی IPV6=yes در /etc/default/ufw باشد؛ قبل از تکیه بر این رفتار، مقدار را بخوان و status verbose را با ruleهای IPv4/IPv6 مرور کن. اگر IPv6 را جا بیندازی، سرویس ممکن است از IPv6 در دسترس بماند حتی وقتی IPv4 درست محدود شده است.

UFW normally manages IPv6 when IPV6=yes is configured in /etc/default/ufw; verify the setting and review IPv4/IPv6 rules in verbose status. If IPv6 is overlooked, a service may remain reachable over IPv6 while IPv4 is restricted.

nftables: table، chain و rulenftables: tables, chains, and rules

در nftables، table ظرف گروه‌بندی ruleهاست؛ chain به hookای مثل input وصل می‌شود؛ rule شرط و verdict دارد. خانوادهٔ inet می‌تواند IPv4 و IPv6 را در یک table ببیند. prefixهای ip و ip6 در matchهای rule فقط نسخهٔ مربوط را هدف می‌گیرند.

In nftables, a table groups rules; a chain attaches to a hook such as input; a rule contains matches and a verdict. The inet family can handle IPv4 and IPv6 in one table. ip and ip6 matches target the corresponding address family.

نمونهٔ بعدی یک policy ورودی کامل برای VM یک‌بارمصرف است، نه چیزی برای paste روی server زنده. اول localhost و ترافیک stateful برگشتی را مجاز می‌کند؛ بعد ICMP و ICMPv6 لازم را نگه می‌دارد؛ SSH و port 8080 را برای اتصال تازه باز می‌کند؛ بقیهٔ inputها به‌خاطر policy پیش‌فرض drop می‌شوند. خروجی فیلتر نمی‌شود چون output chain تعریف نکرده‌ایم.

The next example is a complete inbound policy for a disposable VM, not something to paste on a live server. It permits loopback and tracked reply traffic, retains ICMP/ICMPv6, allows new SSH and TCP/8080, and drops other input by default. Outbound traffic is not filtered because no output chain is defined.

illustrative ruleset — isolated lab only
table inet codenames_lab {
  chain input {
    type filter hook input priority filter; policy drop;
    iifname "lo" accept
    ct state invalid drop
    ct state established,related accept
    ip protocol icmp accept
    meta l4proto ipv6-icmp accept
    tcp dport { 22, 8080 } ct state new accept
  }
}

برای اینکه فرمان‌های بعدی فایل واقعی داشته باشند، در VM یک‌بارمصرف بلوک بالا را در فایلی به نام lab.nft ذخیره کن؛ مثلاً nano lab.nft را باز کن، فقط متن داخل نمونه را paste کن و ذخیره کن. بعد sudo nft -c -f ./lab.nft را اجرا کن؛ -c اعتبار ruleها را بررسی می‌کند بی‌آنکه آن‌ها را اعمال کند. فقط اگر check موفق بود، در همین VM sudo nft -f ./lab.nft را بزن، sudo nft list table inet codenames_lab را بخوان و از client مسیرهای مجاز را آزمایش کن. خطای parse یعنی هنوز اعمال نکن.

To give the next commands a real file, save the contents of the example above as lab.nft in the disposable VM—for example, open nano lab.nft, paste only the ruleset, and save. Run sudo nft -c -f ./lab.nft; -c validates the rules without applying them. Only if the check succeeds, apply with sudo nft -f ./lab.nft in that VM, inspect sudo nft list table inet codenames_lab, and test allowed paths from the client. A parse error means do not apply it yet.

نکتهٔ مهم: ایجاد base chain با policy drop می‌تواند اتصال‌های تازه را ببندد. در سرور واقعی، همین table ممکن است با UFW، container runtime یا ruleset موجود تداخل کند؛ جایگزین‌کردن یا flush کردن کل ruleset خطرناک است. persistence هم جداست: اجرای nft rule را runtime می‌سازد؛ پیکربندی فایل و service راه‌اندازی به توزیع و مدیر سیستم وابسته است.

Important: a base chain with policy drop can block new connections. On a real server, this table may conflict with UFW, a container runtime, or existing rules; replacing or flushing the whole ruleset is dangerous. Persistence is separate: running nft creates runtime rules; loading files/services depends on the distribution and manager.

قبل از تغییر از راه دور، طناب برگشت را ببندBefore a remote change, secure a way back

از SSH تنها به SSH تکیه نکن. دو راه امن برای تمرین داری: VM یک‌بارمصرف با console باز، یا rollback زمان‌دار که قبل از تغییر آماده شده باشد. یک terminal دوم SSH هم مفید است، اما اگر rule تازه همهٔ connectionهای جدید را ببندد، session دوم نجاتت نمی‌دهد.

Do not rely on SSH as your only recovery path. Two safe lab options are a disposable VM with console open or a timed rollback armed before the change. A second SSH terminal helps, but cannot save you if the new rule blocks every new connection.

روی VMای که systemd و UFW دارد، rollback زمان‌دار می‌تواند UFW را در دو دقیقه خاموش کند. این فرمان را فقط در VM آزمایش اجرا کن، مسیر ufw و unit را قبلش تأیید کن و بعد از موفقیت، timer را لغو کن؛ در container/WSL بدون systemd چنین راهی وجود ندارد.

On a VM with systemd and UFW, a timer can disable UFW in two minutes. Use this only in a lab VM, confirm the ufw path and unit first, and cancel the timer after success; containers or WSL without systemd do not provide this recovery method.

arm rollback before touching the policy
command -v ufw
sudo systemd-run --unit=ufw-lab-rollback --on-active=2m "$(command -v ufw)" --force disable
sudo systemctl list-timers ufw-lab-rollback.timer

اگر timer در فهرست دیده نمی‌شود، تغییر را شروع نکن. حالا در console باز policy را آزمایش کن، ruleها را از client verify کن و تنها اگر دسترسی پابرجاست timer را با sudo systemctl stop ufw-lab-rollback.timer لغو کن. اگر قطع شد، منتظر rollback بمان یا از console بازیابی کن؛ firewall را برای همیشه خاموش‌گذاشتن راه‌حل نهایی نیست.

If the timer is not listed, do not start the change. Test in the open console, verify rules from a client, and cancel the timer only after access is confirmed. If locked out, wait for rollback or recover through the console; leaving the firewall disabled is not the final fix.

شبیه‌سازی failure را هم فقط همین‌جا انجام بده: پس از policy مجاز، یک rule موقت deny 22/tcp اضافه کن و از یک اتصال تازه ببین SSH راه نمی‌دهد. session موجود ممکن است به‌خاطر stateful rule زنده بماند؛ پس فکر نکن rule اعمال نشده. با console، rule را با شمارهٔ تازه پیدا و حذف کن، یا rollback زمان‌دار را فعال بگذار؛ بعد از client دوباره اتصال تازه بزن.

Simulate the failure only here: after the allowed policy is active, add a temporary deny 22/tcp and test a fresh SSH connection. An existing stateful session may remain alive, so do not assume the rule failed. Use the console to find and remove the current numbered rule, or let the rollback timer fire; then test a new connection again.

لَب: SSH و یک برنامه، نه درهای باز بی‌حسابLab: SSH and one app, without opening everything

یک Ubuntu VM یک‌بارمصرف با console، یک client دیگر روی همان شبکهٔ آزمایشی و UFW نصب‌شده لازم داری. اگر پورت SSH تو 22 نیست، عدد واقعی را یادداشت کن. پیش از هر تغییر، ufw status verbose، nft list ruleset و provider firewall را ثبت کن؛ اگر مالکیت ruleها معلوم نیست، آزمایش را متوقف کن.

You need a disposable Ubuntu VM with console access, another client on the lab network, and UFW installed. If SSH uses a nonstandard port, record it. Before changes, inspect UFW, nftables, and provider firewall; stop if rule ownership is unclear.

در VM کنسول‌محور ruleهای موجود را از نو reset نکن. روی نصب آزمایشی خالی، ابتدا اجازهٔ SSH واقعی و 8080/tcp را اضافه کن؛ policy پیش‌فرض را بخوان و فقط پس از تأیید console، incoming را deny و outgoing را allow کن.

Do not reset existing rules on a console-accessible VM. On a clean disposable installation, add the actual SSH port and TCP/8080 first; inspect default policy, and only after confirming console access set inbound deny and outbound allow.

checkpoint 1 — build the allow-list before enabling
sudo ufw allow 22/tcp
sudo ufw allow 8080/tcp
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw status verbose
sudo ufw status numbered

اگر sshd پورت دیگری دارد، به‌جای 22 همان را بگذار و rule اشتباه اضافه‌شده را حذف کن. IPv6 را هم چک کن: در Ubuntu IPV6=yes بودن UFW مهم است. مطمئن شو ruleها هم IPv4 و هم IPv6 را پوشش می‌دهند؛ status verbose و فایل تنظیمات را کنار هم بخوان.

If sshd uses another port, substitute it and remove any mistaken rule. Check IPv6 too: on Ubuntu, UFW’s IPV6=yes setting matters. Confirm that rules cover both address families by inspecting verbose status and the configuration together.

وقتی فهرست درست شد، enable کن و از client یک اتصال تازه به SSH و 8080 بزن. از همان server، ss -lntp باید listenerها را نشان دهد؛ از client، nc -vz -w 2 SERVER_IP 22 و curl --connect-timeout 2 --max-time 5 http://SERVER_IP:8080/ دو مسیر را می‌آزمایند. موفقیت هرکدام، ruleهای دیگر یا دسترسی public را ثابت نمی‌کند.

Once the list is correct, enable and test fresh connections to SSH and 8080 from the client. On the server, ss -lntp should show listeners; from the client, bounded nc and curl test both paths. Success does not prove other rules or public reachability.

checkpoint 2 — enable, then verify externally
sudo ufw --force enable
sudo ufw status verbose
sudo ufw status numbered

برای failure drill یک rule deny موقت به SSH اضافه کن؛ از client دوم connection تازه بساز و timeout/refusal را ثبت کن. اگر همان SSH قدیمی هنوز کار می‌کند، نتیجه را اشتباه نخوان—conntrack ممکن است آن flow را established بداند. از console شمارهٔ دقیق rule deny را پیدا و حذف کن؛ سپس دوباره status numbered و اتصال تازه را verify کن.

For the failure drill, add a temporary SSH deny rule and test a fresh connection from the second client. Record timeout/refusal. If the old SSH session still works, do not misread it—conntrack may classify that flow as established. From the console, find and remove the exact deny rule, then verify numbered status and a new connection.

در پایان، یک port بی‌نیاز مثل 8081 را از client تست کن؛ باید باز نباشد، ولی علت را فقط با timeout نام‌گذاری نکن. listener را با ss، مسیر را با ip route get و policy را با UFW/firewall بالادستی تطبیق بده. ruleها را مستند کن و فقط فایل‌های آزمایشی همین VM را جمع کن؛ provider firewall را جدا نگه دار.

Finally, test an unnecessary port such as 8081 from the client; it should not be open, but do not infer the cause from a timeout alone. Compare the listener, route, UFW policy, and upstream firewall. Document the rules and clean up only this VM’s lab artifacts.

تمرین‌ها: policy را با دلیل توضیح بدهExercises: explain the policy you would write

۱. مقصد packet خود host است1. The host is the packet’s destination

client به port 22 خود VPS وصل می‌شود. input را بررسی می‌کنی یا forward؟

A client connects to port 22 on the VPS. Do you inspect input or forward?

پاسخSolution

input، چون packet برای process محلی sshd تحویل می‌شود. forward برای packetی است که از host عبور کرده و مقصدش ماشین دیگری است.

Input, because the packet is delivered to local sshd. Forward is for traffic passing through the host toward another machine.

۲. سرور درخواست خروجی می‌فرستد2. The server initiates a request

برنامهٔ local به API بیرونی اتصال TCP آغاز می‌کند. packet آغازین از کدام hook می‌گذرد؟

A local application starts a TCP connection to an external API. Which hook sees the initiating packet?

پاسخSolution

output، چون process همین host آن را ساخته است. reply بعدی packet ورودی خواهد بود و ممکن است established state بگیرد.

Output, because a local process created it. The reply arrives inbound and may be classified as established.

۳. router بین دو subnet3. A router between subnets

VM بستهٔ LAN را route می‌کند تا به اینترنت برسد. کدام hook مهم است؟

A VM routes LAN traffic toward the Internet. Which hook matters?

پاسخSolution

forward، چون packet برای خود VM نیست. علاوه بر firewall، IP forwarding و routeها نیز باید درست باشند.

Forward, because the packet is not destined for the VM. IP forwarding and routing must also be configured.

۴. چرا established را allow می‌کنیم؟4. Why allow established traffic?

policy ورودی deny است. server یک درخواست DNS خروجی آغاز می‌کند. چرا پاسخ DNS می‌تواند برگردد؟

Inbound policy is deny. The server sends a DNS query. Why can its response return?

پاسخSolution

conntrack جریان را دنبال می‌کند و پاسخ را در state مربوط به ارتباط آغازشده تشخیص می‌دهد؛ rule established,related آن را قبول می‌کند. این مجوز DNS ورودی تازه از هر مبدأ نیست.

Conntrack tracks the flow and recognizes the reply as part of an initiated connection; an established/related rule allows it. This is not permission for arbitrary new inbound DNS.

۵. SSH فعلی باز است5. The current SSH session stays open

بعد از افزودن deny، session قدیمی زنده مانده ولی اتصال تازه شکست می‌خورد. آیا rule کار نکرد؟

After adding a deny, the old session survives but a new connection fails. Did the rule fail?

پاسخSolution

نه لزوماً؛ session قبلی می‌تواند established match شود و SYN تازه deny شود. برای سنجش، connection جدید از client دوم بساز.

Not necessarily; the existing session may match established while a new SYN is denied. Test with a fresh connection from another client.

۶. UFW می‌گوید inactive6. UFW reports inactive

آیا همین کافی است بگویی server فایروال ندارد؟

Is that enough to say the server has no firewall?

پاسخSolution

نه؛ nftables، ابزار دیگری در kernel یا provider firewall می‌تواند فعال باشد. همهٔ مرزها و rule ownerها را جدا بررسی کن.

No; nftables, another kernel rule manager, or a provider firewall may still be active. Inspect each boundary and rule owner separately.

۷. policy پیش‌فرض7. Default policy

در UFW incoming را deny و outgoing را allow گذاشتی. آیا این یعنی port 8080 مجاز است؟

UFW defaults to deny incoming and allow outgoing. Is port 8080 allowed?

پاسخSolution

نه؛ incoming deny به‌طور پیش‌فرض اتصال آغازشده از بیرون را رد می‌کند. باید rule allow مشخص و listener درست وجود داشته باشد.

No; inbound deny rejects new connections initiated from outside by default. You need an explicit allow and a working listener.

۸. loopback جا افتاد8. Loopback was omitted

ruleset ورودی default-drop شده و loopback اجازه ندارد. چه چیزهایی ممکن است مختل شود؟

The input chain defaults to drop and has no loopback allow. What might break?

پاسخSolution

ارتباطات local مثل سرویس‌هایی که روی 127.0.0.1 با هم حرف می‌زنند ممکن است بشکنند. policy معمولاً iifname lo accept را صریح نگه می‌دارد.

Local interactions, such as services communicating through 127.0.0.1, may break. A typical policy explicitly allows iifname lo.

۹. IPv4 امن، IPv6 فراموش9. IPv4 restricted, IPv6 forgotten

v4 inbound deny است ولی v6 service هنوز reachable است. کجا را بررسی می‌کنی؟

IPv4 inbound is denied, but the service remains reachable over IPv6. What do you inspect?

پاسخSolution

UFW setting IPV6, ruleهای v6 در status و provider firewall را بررسی کن. nft table خانوادهٔ inet یا ruleهای جداگانهٔ ip/ip6 را هم ببین.

Inspect UFW’s IPV6 setting, IPv6 rules in status, and provider firewall. For nftables, check inet-family or separate ip/ip6 rules.

۱۰. chain و table یکی نیستند10. A table is not a chain

در nftables، table را ساختی ولی rule هیچ packetی نمی‌بیند. چه چیزی را جا انداختی؟

You created an nftables table, but its rules see no packets. What may be missing?

پاسخSolution

chain باید به hook مناسب وصل شده باشد تا packet را ببیند؛ regular chain به‌تنهایی مسیر شبکه نیست. nft list ruleset را برای type/hook/priorities بررسی کن.

A chain must attach to the right hook to see packets; a regular chain alone is not a packet path. Inspect type, hook, and priorities in nft list ruleset.

۱۱. شمارهٔ UFW عوض شد11. UFW numbering changed

rule شمارهٔ 3 را حذف کردی؛ چرا نباید همان شماره را برای حذف بعدی حفظ کنی؟

You deleted UFW rule 3. Why should you not reuse that number for another deletion?

پاسخSolution

پس از حذف، شماره‌های بعدی جابه‌جا می‌شوند. هر بار status numbered تازه بخوان و rule را با محتوا تطبیق بده.

Deleting a rule shifts subsequent numbers. Re-read numbered status each time and match the rule by content.

۱۲. روی SSH rule می‌گذاری12. You are changing the SSH rule

از راه دوری و می‌خواهی default incoming را deny کنی. سه checkpoint پیش از اجرا چیست؟

You are remote and plan to deny inbound by default. Name three checks before applying it.

پاسخSolution

پورت SSH واقعی و allow rule را تأیید کن؛ کنسول یا rollback زمان‌دار را آماده و آزمایش کن؛ ruleset/provider firewall را ثبت کن. بعد rule را از client تازه verify کن.

Confirm the actual SSH port and allow rule; prepare and verify console or timed rollback; record current rules and provider policy. Then test with a fresh client connection.

۱۳. default drop و ICMPv613. Default drop and ICMPv6

چرا نباید تمام ICMPv6 را بی‌بررسی block کنی؟

Why should you not block all ICMPv6 without analysis?

پاسخSolution

IPv6 neighbor discovery و پیام‌های لازم مسیر/MTU به ICMPv6 وابسته‌اند. policy v6 را با نوع پیام‌ها و نیاز شبکه طراحی کن؛ کپی سادهٔ IPv4 کافی نیست.

IPv6 neighbor discovery and important path/MTU signaling rely on ICMPv6. Design IPv6 policy for required message types; a simple IPv4 copy is insufficient.

۱۴. forward خالی است14. The forward path is empty

UFW اجازهٔ SSH به VM می‌دهد ولی clientهای پشت آن route نمی‌شوند. چرا input allow کافی نیست؟

UFW allows SSH to a VM, but clients behind it cannot route. Why is input allow insufficient?

پاسخSolution

SSH به خود VM input است؛ ترافیک client که از آن عبور می‌کند forward می‌خواهد، به‌علاوه IP forwarding و route/NAT مناسب. port 22 rule آن‌ها را نمی‌سازد.

SSH to the VM is input; client traffic passing through it needs forward rules plus IP forwarding and appropriate routes/NAT. An SSH allow does not provide those.

۱۵. UFW و nftables را با هم اجرا کنیم؟15. Should we manage UFW and nftables together?

یک همکار با UFW کار می‌کند و تو مستقیم chain جدید می‌سازی. قبلش چه چیزی باید روشن شود؟

A teammate uses UFW while you add a chain directly. What must be clarified first?

پاسخSolution

مالک policy، order/priorities، persistence و اثر روی ruleهای generated باید معلوم باشد. ruleset کامل و مستندات توزیع را بخوان؛ مدیر دوم را روی host زنده وارد نکن.

Clarify policy ownership, order/priorities, persistence, and interaction with generated rules. Read the complete ruleset and distribution docs; do not introduce a second manager casually on a live host.

۱۶. rule runtime ماندگار نیست16. Runtime rule did not persist

بعد از reboot rule دستی nftables ناپدید شده. آیا kernel آن را «گم کرده»؟

A manually added nftables rule disappeared after reboot. Did the kernel “forget” it?

پاسخSolution

rule runtime بود و persistence را جدا پیکربندی نکرده بودی. فایل configuration و service مسئول بارگذاری را طبق همان توزیع تنظیم و reboot آزمایشی را در VM انجام بده.

It was runtime state without persistence configured. Set up the distribution’s configuration file and loading service, then test reboot behavior in a VM.

۱۷. listener نیست17. No listener exists

firewall اجازهٔ 8080 دارد ولی ss هیچ listenerی نشان نمی‌دهد. گام بعدی چیست؟

The firewall allows 8080 but ss shows no listener. What next?

پاسخSolution

مشکل را در application bind/process بررسی کن؛ allow rule برنامه را راه نمی‌اندازد. ss, service status و log را کنار هم بخوان.

Investigate the application process and bind address; an allow rule does not start the service. Compare ss, service status, and logs.

۱۸. بلیت lockout نزدیک است18. A lockout is imminent

policy فعلی تغییرهای مبهم دارد، SSH روی port سفارشی است و provider firewall هم فعال است. اجرای ufw enable را ادامه می‌دهی؟ چه مدرکی لازم است؟

The current policy is unclear, SSH uses a custom port, and a provider firewall is active. Do you proceed with ufw enable? What evidence do you need?

راهنماHint

تا وقتی راه بازگشت و زنجیرهٔ ruleها معلوم نیست، جواب پیش‌فرض «صبر کن» است.

Until recovery access and the rule path are clear, the default answer is “wait.”

پاسخSolution

نه، هنوز اجرا نکن. پورت SSH را با socket/service واقعی تأیید کن؛ provider policy و host ruleset را ثبت؛ allow rule را برای v4/v6 بساز؛ console یا timed rollback را از قبل آماده کن؛ بعد در VM یا maintenance window از client جدید SSH/برنامه/port بسته را آزمایش کن. فقط اگر همهٔ مسیرها روشن‌اند، enable کن؛ سپس همان آزمون‌ها را تکرار و rollback timer را لغو کن.

Do not proceed yet. Confirm the actual SSH socket/port; record provider and host rules; prepare IPv4/IPv6 allows; arm console or timed rollback; then test SSH, app, and a blocked port from a new client in a VM or maintenance window. Enable only when paths are clear, repeat the tests, and cancel the rollback timer.

فایروال راه را محدود کرد؛ حالا ورود را امن می‌کنیمThe firewall narrowed access; next we secure the login

حالا می‌دانی port باز باید به یک listener واقعی برسد، responseهای ارتباط موجود با connectionهای تازه فرق دارند و IPv6 هم از policy جا نمی‌ماند. در فصل بعد سراغ SSH key و config می‌رویم تا همین تنها راه مدیریتی را هم با روشی امن‌تر و قابل‌تکرار تنظیم کنیم.

You now know an allowed port must reach a real listener, replies to existing flows differ from new connections, and IPv6 belongs in the policy too. Next we will configure SSH keys and client settings so this management path is safer and repeatable.
