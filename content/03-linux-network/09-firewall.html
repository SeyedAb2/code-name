فایروال: nftables / ufwFirewalls: nftables / ufw

پورت روی سرور بازه و برنامه گوش می‌ده، ولی از بیرون هنوز وصل نمی‌شی. حالا نوبت firewallه؛ جایی که یک قانون کوچیک می‌تونه کل مسیر رو ببنده. قبل از اینکه قانون اضافه کنیم، اول می‌فهمیم packet از کدوم chain رد می‌شه و قانون فعلی دقیقاً چی می‌گه.

You add a rule so a test application is reachable on only one port. Seconds later, SSH stops responding too. The firewall did exactly what the written policy said—the problem was that you had no recovery path ready before changing it.

فایروال قرار هست چه تصمیمی بگیره؟What decision is the firewall making?

فایروال لیست جادویی «باز و بسته» نیست. یک packet میاد، از چند قانون رد می‌شه و در آخر اجازه می‌گیره یا رد می‌شه. وقتی این مسیر رو ببینی، UFW و nftables هم خیلی قابل‌فهم‌تر می‌شن.

Last chapter showed that a SYN may reach the server without a reply. A firewall is one place where a packet can be accepted, rejected, or silently dropped. Good policy does not start with “block everything”; it starts with: which inbound connections must actually work?

روی Linux، netfilter در kernel مسیر packet رو می‌بینه؛ nftables رابط مدرن تنظیم اون هست. ufw یک ابزار ساده‌تر برای نوشتن سیاستهای رایج هست و در Ubuntu Server معمولاً frontend پیشنهادی هست. این دو رو بی‌برنامه با هم قاطی نکن: هر دو می‌تونن روی همون زیرساخت kernel اثر بگذارند، ولی مالکیت قانونها و ترتیب chainها مهم هست.

On Linux, kernel netfilter handles packet paths; nftables is the modern rules interface. ufw is a simpler frontend for common policies and is the usual recommended tool on Ubuntu Server. Do not mix them casually: both can affect the same kernel subsystem, and ownership/order of chains matters.

packet ورودی وارد ورودی chain می‌شه؛ state و قانونهای مرتب‌شده نتیجه رو می‌سازن. ادامهٔ اتصال SSH با مجوز اتصال تازه یکی نیست.

An inbound packet enters the input chain; state and ordered rules determine the verdict. Continuing SSH traffic is not the same as permitting a new connection.

فایروال host فقط یکی از لایه‌هاست؛ ارائه‌دهنده firewall، security group، router یا firewall داخل container هم ممکنه همون traffic رو جداگانه فیلتر کنه. قانون محلی که اجازه می‌ده، مانع ارائه‌دهنده رو برنمی‌دارد.

The host firewall is only one layer; a provider firewall, security group, router, or container firewall may independently filter the same traffic. A local allow rule cannot remove a provider-side block.

بسته به کدوم طرف میزبان می‌ره؟Which way is the packet crossing the host?

سه مسیر رو از هم جدا کن. input بسته‌ای هست که مقصدش همین host هست—مثلاً SSH یا HTTP روی خود VPS. output از برنامهٔ همین host بیرون می‌ره—مثلاً اتصال DNS یا درخواست به API. forward از این host عبور می‌کنه تا به ماشین دیگری برسه؛ router یا بعضی سناریوهای container با اون سروکار دارن.

Separate three paths. input is traffic destined for this host, such as SSH or HTTP on the VPS. output is traffic originated by a local process, such as DNS or an API request. forward passes through this host toward another machine; routers and some container scenarios use it.

اشتباه گرفتن ورودی و forward دردسر رایجی هست: اگه request به host می‌رسه و قرار هست یک پردازه همون‌جا جواب بده، معمولاً ورودی رو بررسی می‌کنی، نه forward. ip route و ss فصل قبل کمک می‌کنن تشخیص دهی packet کجا مقصد داره و آیا listener محلی هست.

Confusing input and forward is common: if a request is destined to a local process, inspect input, not forward. Last chapter’s ip route and ss help determine where the packet is addressed and whether a local listener exists.

چرا برای هر reply یک allow جدا لازم نیست؟Why is there no separate allow for every reply?

یک client اتصال TCP رو آغاز می‌کنه و server پاسخ رو برمی‌گردونه. فایروال stateful ارتباط رو در conntrack دنبال می‌کنه؛ قاعدهٔ ct state established,related accept به packetهای شناخته‌شدهٔ اتصال و بعضی ترافیک مرتبط اجازه می‌ده. این برای برگشت پاسخ‌هاست، نه مجوز شروع هر اتصال جدید از هرجا.

A client starts a TCP connection and the server replies. A stateful firewall tracks the flow in conntrack; ct state established,related accept permits packets belonging to known connections and certain related traffic. This handles replies—it does not authorize every new connection from everywhere.

new معمولاً شروع اتصالی هست که هنوز رفت‌وبرگشت کامل نشده؛ established flow شناخته‌شده‌ای هست که ترافیک معتبر دوطرفه داشته؛ related اتصال جداگانه‌ای هست که به flow موجود ارتباط داره. این stateها برچسب‌های conntrack هستن، نه verdict. قانونهای بالاتر/پایین‌تر تعیین می‌کنن با هرکدوم چه بشه.

new commonly marks a connection beginning before a full exchange; established is a tracked flow with valid traffic in both directions; related is a separate flow associated with an existing one. These are conntrack labels, not verdicts. Rules decide what happens to each.

در nftables قانونها داخل chain به ترتیب بررسی می‌شن. accept و drop verdict می‌دن؛ priority میان base chainهایی هست که به hook وصل‌اند، نه یک عدد برای همهٔ قانونها. اگه چند base chain روی یک hook باشن، accept در یکی لزوماً جلوی بررسی chain بعدی رو نمی‌گیره؛ قانون بعدی هم ممکنه packet رو drop کنه. توی این فصل chain جداگانهٔ یک مدیر دیگر رو روی host عملیاتی اضافه نمی‌کنیم؛ اول ruleset موجود رو می‌خونیم و مالک اون رو پیدا می‌کنیم.

Within an nftables chain, rules are checked in order. accept and drop give verdicts; priority orders base chains attached to a hook, not every rule globally. If several base chains share a hook, accept in one does not necessarily prevent a later chain from dropping the packet. This chapter does not add another manager’s chain to a production host; inspect the existing ruleset and identify its owner.

قبل از تغییر، آنچه همین حالا فعال هست بخوانBefore changing anything, inspect what is active

روی هر سیستم اول بپرس کدوم frontend صاحب سیاست هست. روی Ubuntu، ufw status verbose خلاصهٔ سیاست و قانونهای UFW رو می‌ده؛ nft list ruleset نمای kernel از rulesetهای nftables رو نشون می‌ده. خروجی یکی جای دیگری رو نمی‌گیره و ممکنه ابزارهای دیگر قانونهای kernel رو ساخته باشن.

First identify which frontend owns the policy. On Ubuntu, ufw status verbose summarizes UFW policy and rules; nft list ruleset shows nftables rulesets in the kernel. Neither output replaces the other, and other tools may have created kernel rules.

read-only inventory
sudo ufw status verbose
sudo ufw status numbered
sudo nft list ruleset
sudo systemctl status nftables

اگه UFW می‌گه inactive، این ثابت نمی‌کنه host هیچ فایروالی نداره؛ ruleset nftables یا ارائه‌دهنده firewall رو جدا ببین. اگه nftables.service inactive هست، ممکنه NetworkManager، container runtime یا ابزار دیگری قانونها رو مدیریت کنه. قبل از دست‌کاری، از وضعیت و فایل پیکربندی تصویر لحظه‌ای بگیر.

If UFW says inactive, that does not prove the host has no firewall; inspect nftables and provider firewalls separately. If nftables.service is inactive, NetworkManager, a container runtime, or another tool may own the rules. Snapshot the current state and configuration before editing.

با UFW سیاست رو واضح بنویسUse UFW to express a clear policy

برای یک VPS معمول Ubuntu، سؤال روشن هست: پاسخ‌های ارتباط‌های شروع‌شده از داخل رو نگه دار؛ از بیرون فقط SSH و port برنامه رو باز بگذار. UFW رو بعد از دیدن وضعیت و تأیید دسترسی console/rollback تنظیم می‌کنیم—نه با خاموش‌کردن firewall موجود.

For a typical Ubuntu VPS, the policy is clear: allow replies to outbound connections; expose only SSH and the application port inbound. Configure UFW only after checking status and confirming console/rollback access—not by disabling an existing firewall.

example policy — disposable Ubuntu VM first
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 8080/tcp
sudo ufw status verbose

سطرهای وضعیت باید سیاست ورودی deny، خروجی allow و اجازهٔ OpenSSH و 8080/tcp رو نشان بدن. OpenSSH نام application profile هست و روی هر نصب تضمین‌شده نیست؛ قبل از اون sudo ufw app list رو ببین یا پورت واقعی SSH رو صریح بنویس. هنوز فعال‌کردن سیاست و آزمون از client رو انجام نداده‌ای؛ وضعیت فعلی ممکنه فقط draft رو نشان بده.

The status should show inbound deny, outbound allow, and permits for OpenSSH and TCP/8080. OpenSSH is an application profile and may not exist on every installation; check sudo ufw app list or allow the actual SSH port explicitly. You have not yet enabled and tested the policy from a client; current status may only show a draft.

قبل از ufw enable اگه SSH راه مدیریت توست، باید همون port واقعی و address family درست مجاز باشه. روی VM یک‌بارمصرف با کنسول باز، اجازهٔ SSH رو اضافه کن، بعد اجازهٔ برنامه رو؛ قانونهای شماره‌دار رو ثبت و سبعد از client جدید اتصال رو آزمایش کن. فعال‌کردن سیاست فقط بعد از این checkpoint میاد.

Before ufw enable, if SSH is your management path, its actual port and address family must be allowed. On a disposable VM with console open, add SSH and application rules, record numbered rules, then test from a new client connection. Enabling the policy comes only after this checkpoint.

enable only after the recovery path is ready
sudo ufw --force enable
sudo ufw status numbered

اگه خروجی Status: active هست و قانونهای 22/SSH و 8080 رو می‌بینی، از ماشین client یک اتصال تازه به هر دو بزن؛ اتصال SSH فعلی رو به‌عنوان تنها مدرک حساب نکن. ufw delete NUMBER یک قانون رو با شماره حذف می‌کنه؛ شماره بعد از تغییر فهرست عوض می‌شه، پس درست قبل از حذف دوباره status numbered رو بخوان.

If status is active and the SSH/22 and 8080 rules appear, open fresh connections from a client. Do not count the current SSH session as the only proof. ufw delete NUMBER removes a rule by number; numbering changes after edits, so re-read status numbered immediately before deleting.

UFW معمولاً IPv6 رو هم مدیریت می‌کنه وقتی IPV6=yes در /etc/default/ufw باشه؛ قبل از تکیه بر این رفتار، مقدار رو بخوان و status verbose رو با قانونهای IPv4/IPv6 مرور کن. اگه IPv6 رو جا بیندازی، سرویس ممکنه از IPv6 در دسترس بمونه حتی وقتی IPv4 درست محدود شده هست.

UFW normally manages IPv6 when IPV6=yes is configured in /etc/default/ufw; verify the setting and review IPv4/IPv6 rules in verbose status. If IPv6 is overlooked, a service may remain reachable over IPv6 while IPv4 is restricted.

nftables: table، chain و قانونnftables: tables, chains, and rules

در nftables، table ظرف گروه‌بندی قانونهاست؛ chain به hookای مثل ورودی وصل می‌شه؛ قانون شرط و verdict داره. خانوادهٔ inet می‌تونه IPv4 و IPv6 رو در یک table ببینه. prefixهای ip و ip6 در matchهای قانون فقط نسخهٔ مربوط رو هدف می‌گیرن.

In nftables, a table groups rules; a chain attaches to a hook such as input; a rule contains matches and a verdict. The inet family can handle IPv4 and IPv6 in one table. ip and ip6 matches target the corresponding address family.

نمونهٔ بعدی یک سیاست ورودی کامل برای VM یک‌بارمصرف هست، نه چیزی برای paste روی server زنده. اول localhost و ترافیک stateful برگشتی رو مجاز می‌کنه؛ بعد ICMP و ICMPv6 لازم رو نگه می‌داره؛ SSH و port 8080 رو برای اتصال تازه باز می‌کنه؛ بقیهٔ ورودیها به‌خاطر سیاست پیش‌فرض drop می‌شن. خروجی فیلتر نمی‌شه چون خروجی chain تعریف نکرده‌ایم.

The next example is a complete inbound policy for a disposable VM, not something to paste on a live server. It permits loopback and tracked reply traffic, retains ICMP/ICMPv6, allows new SSH and TCP/8080, and drops other input by default. Outbound traffic is not filtered because no output chain is defined.

illustrative ruleset — isolated lab only
table inet codenames_lab {
  chain input {
    type filter hook input priority filter; policy drop;
    iifname "lo" accept
    ct state invalid drop
    ct state established,related accept
    ip protocol icmp accept
    meta l4proto ipv6-icmp accept
    tcp dport { 22, 8080 } ct state new accept
  }
}

برای اینکه فرمان‌های بعدی فایل واقعی داشته باشن، در VM یک‌بارمصرف بلوک بالا رو در فایلی به نام lab.nft ذخیره کن؛ مثلاً nano lab.nft رو باز کن، فقط متن داخل نمونه رو paste کن و ذخیره کن. بعد sudo nft -c -f ./lab.nft رو اجرا کن؛ -c اعتبار قانونها رو بررسی می‌کنه بی‌آنکه اون‌ها رو اعمال کنه. فقط اگه check موفق بود، در همین VM sudo nft -f ./lab.nft رو بزن، sudo nft list table inet codenames_lab رو بخوان و از client مسیرهای مجاز رو آزمایش کن. خطای parse یعنی هنوز اعمال نکن.

To give the next commands a real file, save the contents of the example above as lab.nft in the disposable VM—for example, open nano lab.nft, paste only the ruleset, and save. Run sudo nft -c -f ./lab.nft; -c validates the rules without applying them. Only if the check succeeds, apply with sudo nft -f ./lab.nft in that VM, inspect sudo nft list table inet codenames_lab, and test allowed paths from the client. A parse error means do not apply it yet.

نکتهٔ مهم: ایجاد base chain با policy drop می‌تونه اتصال‌های تازه رو ببندد. در سرور واقعی، همین table ممکنه با UFW، container runtime یا ruleset موجود تداخل کنه؛ جایگزین‌کردن یا flush کردن کل ruleset خطرناک هست. persistence هم جداست: اجرای nft قانون رو runtime می‌سازه؛ پیکربندی فایل و service راه‌اندازی به توزیع و مدیر سیستم وابسته هست.

Important: a base chain with policy drop can block new connections. On a real server, this table may conflict with UFW, a container runtime, or existing rules; replacing or flushing the whole ruleset is dangerous. Persistence is separate: running nft creates runtime rules; loading files/services depends on the distribution and manager.

قبل از تغییر از راه دور، طناب برگشت رو ببندBefore a remote change, secure a way back

از SSH تنها به SSH تکیه نکن. دو راه امن برای تمرین داری: VM یک‌بارمصرف با console باز، یا rollback زمان‌دار که قبل از تغییر آماده شده باشه. یک ترمینال دوم SSH هم مفید هست، اما اگه قانون تازه همهٔ connectionهای جدید رو ببندد، session دوم نجاتت نمی‌ده.

Do not rely on SSH as your only recovery path. Two safe lab options are a disposable VM with console open or a timed rollback armed before the change. A second SSH terminal helps, but cannot save you if the new rule blocks every new connection.

روی VMای که systemd و UFW داره، rollback زمان‌دار می‌تونه UFW رو در دو دقیقه خاموش کنه. این فرمان رو فقط در VM آزمایش اجرا کن، مسیر ufw و unit رو قبلش تأیید کن و بعد از موفقیت، timer رو لغو کن؛ در container/WSL بدون systemd چنین راهی وجود نداره.

On a VM with systemd and UFW, a timer can disable UFW in two minutes. Use this only in a lab VM, confirm the ufw path and unit first, and cancel the timer after success; containers or WSL without systemd do not provide this recovery method.

arm rollback before touching the policy
command -v ufw
sudo systemd-run --unit=ufw-lab-rollback --on-active=2m "$(command -v ufw)" --force disable
sudo systemctl list-timers ufw-lab-rollback.timer

اگه timer در فهرست دیده نمی‌شه، تغییر رو شروع نکن. حالا در console باز سیاست رو آزمایش کن، قانونها رو از client بررسی نهایی کن و تنها اگه دسترسی پابرجاست timer رو با sudo systemctl stop ufw-lab-rollback.timer لغو کن. اگه قطع شد، منتظر rollback بمان یا از console بازیابی کن؛ firewall رو برای همیشه خاموش‌گذاشتن راه‌حل نهایی نیست.

If the timer is not listed, do not start the change. Test in the open console, verify rules from a client, and cancel the timer only after access is confirmed. If locked out, wait for rollback or recover through the console; leaving the firewall disabled is not the final fix.

شبیه‌سازی خطا رو هم فقط همین‌جا انجام بده: بعد از سیاست مجاز، یک قانون موقت deny 22/tcp اضافه کن و از یک اتصال تازه ببین SSH راه نمی‌ده. session موجود ممکنه به‌خاطر stateful قانون زنده بمونه؛ پس فکر نکن قانون اعمال نشده. با console، قانون رو با شمارهٔ تازه پیدا و حذف کن، یا rollback زمان‌دار رو فعال بگذار؛ بعد از client دوباره اتصال تازه بزن.

Simulate the failure only here: after the allowed policy is active, add a temporary deny 22/tcp and test a fresh SSH connection. An existing stateful session may remain alive, so do not assume the rule failed. Use the console to find and remove the current numbered rule, or let the rollback timer fire; then test a new connection again.

لَب: SSH و یک برنامه، نه درهای باز بی‌حسابLab: SSH and one app, without opening everything

یک Ubuntu VM یک‌بارمصرف با console، یک client دیگر روی همون شبکهٔ آزمایشی و UFW نصب‌شده لازم داری. اگه پورت SSH تو 22 نیست، عدد واقعی رو یادداشت کن. قبل از هر تغییر، ufw status verbose، nft list ruleset و ارائه‌دهنده firewall رو ثبت کن؛ اگه مالکیت قانونها معلوم نیست، آزمایش رو متوقف کن.

You need a disposable Ubuntu VM with console access, another client on the lab network, and UFW installed. If SSH uses a nonstandard port, record it. Before changes, inspect UFW, nftables, and provider firewall; stop if rule ownership is unclear.

در VM کنسول‌محور قانونهای موجود رو از نو reset نکن. روی نصب آزمایشی خالی، ابتدا اجازهٔ SSH واقعی و 8080/tcp رو اضافه کن؛ سیاست پیش‌فرض رو بخوان و فقط بعد از تأیید console، incoming رو deny و outgoing رو allow کن.

Do not reset existing rules on a console-accessible VM. On a clean disposable installation, add the actual SSH port and TCP/8080 first; inspect default policy, and only after confirming console access set inbound deny and outbound allow.

checkpoint 1 — build the allow-list before enabling
sudo ufw allow 22/tcp
sudo ufw allow 8080/tcp
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw status verbose
sudo ufw status numbered

اگه sshd پورت دیگری داره، به‌جای 22 همون رو بگذار و قانون اشتباه اضافه‌شده رو حذف کن. IPv6 رو هم چک کن: در Ubuntu IPV6=yes بودن UFW مهم هست. مطمئن شو قانونها هم IPv4 و هم IPv6 رو پوشش می‌دن؛ status verbose و فایل تنظیمات رو کنار هم بخوان.

If sshd uses another port, substitute it and remove any mistaken rule. Check IPv6 too: on Ubuntu, UFW’s IPV6=yes setting matters. Confirm that rules cover both address families by inspecting verbose status and the configuration together.

وقتی فهرست درست شد، enable کن و از client یک اتصال تازه به SSH و 8080 بزن. از همون server، ss -lntp باید listenerها رو نشان بده؛ از client، nc -vz -w 2 SERVER_IP 22 و curl --connect-timeout 2 --max-time 5 http://SERVER_IP:8080/ دو مسیر رو می‌آزمایند. موفقیت هرکدوم، قانونهای دیگر یا دسترسی public رو ثابت نمی‌کنه.

Once the list is correct, enable and test fresh connections to SSH and 8080 from the client. On the server, ss -lntp should show listeners; from the client, bounded nc and curl test both paths. Success does not prove other rules or public reachability.

checkpoint 2 — enable, then verify externally
sudo ufw --force enable
sudo ufw status verbose
sudo ufw status numbered

برای خطا drill یک قانون deny موقت به SSH اضافه کن؛ از client دوم connection تازه بساز و timeout/refusal رو ثبت کن. اگه همون SSH قدیمی هنوز کار می‌کنه، نتیجه رو اشتباه نخوان—conntrack ممکنه اون flow رو established بداند. از console شمارهٔ دقیق قانون deny رو پیدا و حذف کن؛ سپس دوباره status numbered و اتصال تازه رو بررسی نهایی کن.

For the failure drill, add a temporary SSH deny rule and test a fresh connection from the second client. Record timeout/refusal. If the old SSH session still works, do not misread it—conntrack may classify that flow as established. From the console, find and remove the exact deny rule, then verify numbered status and a new connection.

در پایان، یک port بی‌نیاز مثل 8081 رو از client تست کن؛ باید باز نباشه، ولی علت رو فقط با timeout نام‌گذاری نکن. listener رو با ss، مسیر رو با ip route get و سیاست رو با UFW/firewall بالادستی تطبیق بده. قانونها رو مستند کن و فقط فایل‌های آزمایشی همین VM رو جمع کن؛ ارائه‌دهنده firewall رو جدا نگه دار.

Finally, test an unnecessary port such as 8081 from the client; it should not be open, but do not infer the cause from a timeout alone. Compare the listener, route, UFW policy, and upstream firewall. Document the rules and clean up only this VM’s lab artifacts.

تمرین‌ها: سیاست رو با دلیل توضیح بدهExercises: explain the policy you would write

۱. مقصد packet خود host هست1. The host is the packet’s destination

client به port 22 خود VPS وصل می‌شه. ورودی رو بررسی می‌کنی یا forward؟

A client connects to port 22 on the VPS. Do you inspect input or forward?

پاسخSolution

ورودی، چون packet برای پردازه محلی sshd تحویل می‌شه. forward برای packetی هست که از host عبور کرده و مقصدش ماشین دیگری هست.

Input, because the packet is delivered to local sshd. Forward is for traffic passing through the host toward another machine.

۲. سرور درخواست خروجی می‌فرسته2. The server initiates a request

برنامهٔ local به API بیرونی اتصال TCP آغاز می‌کنه. packet آغازین از کدوم hook رد می‌شه؟

A local application starts a TCP connection to an external API. Which hook sees the initiating packet?

پاسخSolution

خروجی، چون پردازه همین host اون رو ساخته. reply بعدی packet ورودی می‌شه و ممکنه established state بگیره.

Output, because a local process created it. The reply arrives inbound and may be classified as established.

۳. router بین دو subnet3. A router between subnets

VM بستهٔ LAN رو route می‌کنه تا به اینترنت برسه. کدوم hook مهم هست؟

A VM routes LAN traffic toward the Internet. Which hook matters?

پاسخSolution

forward، چون packet برای خود VM نیست. علاوه بر firewall، IP forwarding و routeها نیز باید درست باشن.

Forward, because the packet is not destined for the VM. IP forwarding and routing must also be configured.

۴. چرا established رو allow می‌کنیم؟4. Why allow established traffic?

سیاست ورودی deny هست. server یک درخواست DNS خروجی آغاز می‌کنه. چرا پاسخ DNS می‌تونه برگرده؟

Inbound policy is deny. The server sends a DNS query. Why can its response return?

پاسخSolution

conntrack جریان رو دنبال می‌کنه و پاسخ رو در state مربوط به ارتباط آغازشده تشخیص می‌ده؛ قانون established,related اون رو قبول می‌کنه. این مجوز DNS ورودی تازه از هر مبدأ نیست.

Conntrack tracks the flow and recognizes the reply as part of an initiated connection; an established/related rule allows it. This is not permission for arbitrary new inbound DNS.

۵. SSH فعلی باز هست5. The current SSH session stays open

بعد از افزودن deny، session قدیمی زنده مانده ولی اتصال تازه شکست می‌خوره. آیا قانون کار نکرد؟

After adding a deny, the old session survives but a new connection fails. Did the rule fail?

پاسخSolution

نه لزوماً؛ session قبلی می‌تونه established match بشه و SYN تازه deny بشه. برای سنجش، connection جدید از client دوم بساز.

Not necessarily; the existing session may match established while a new SYN is denied. Test with a fresh connection from another client.

۶. UFW می‌گه inactive6. UFW reports inactive

آیا همین کافیه بگویی server فایروال نداره؟

Is that enough to say the server has no firewall?

پاسخSolution

نه؛ nftables، ابزار دیگری در kernel یا ارائه‌دهنده firewall می‌تونه فعال باشه. همهٔ مرزها و قانون مالکها رو جدا بررسی کن.

No; nftables, another kernel rule manager, or a provider firewall may still be active. Inspect each boundary and rule owner separately.

۷. سیاست پیش‌فرض7. Default policy

در UFW incoming رو deny و outgoing رو allow گذاشتی. آیا این یعنی port 8080 مجاز هست؟

UFW defaults to deny incoming and allow outgoing. Is port 8080 allowed?

پاسخSolution

نه؛ incoming deny به‌طور پیش‌فرض اتصال آغازشده از بیرون رو رد می‌کنه. باید قانون allow مشخص و listener درست وجود داشته باشه.

No; inbound deny rejects new connections initiated from outside by default. You need an explicit allow and a working listener.

۸. loopback جا افتاد8. Loopback was omitted

ruleset ورودی default-drop شده و loopback اجازه نداره. چه چیزهایی ممکنه مختل بشه؟

The input chain defaults to drop and has no loopback allow. What might break?

پاسخSolution

ارتباطات local مثل سرویس‌هایی که روی 127.0.0.1 با هم حرف می‌زنن ممکنه بشکنند. سیاست معمولاً iifname lo accept رو صریح نگه می‌داره.

Local interactions, such as services communicating through 127.0.0.1, may break. A typical policy explicitly allows iifname lo.

۹. IPv4 امن، IPv6 فراموش9. IPv4 restricted, IPv6 forgotten

v4 inbound deny هست ولی v6 service هنوز reachable هست. کجا رو بررسی می‌کنی؟

IPv4 inbound is denied, but the service remains reachable over IPv6. What do you inspect?

پاسخSolution

UFW setting IPV6, قانونهای v6 در وضعیت و ارائه‌دهنده firewall رو بررسی کن. nft table خانوادهٔ inet یا قانونهای جداگانهٔ ip/ip6 رو هم ببین.

Inspect UFW’s IPV6 setting, IPv6 rules in status, and provider firewall. For nftables, check inet-family or separate ip/ip6 rules.

۱۰. chain و table یکی نیستن10. A table is not a chain

در nftables، table رو ساختی ولی قانون هیچ packetی نمی‌بینه. چه چیزی رو جا انداختی؟

You created an nftables table, but its rules see no packets. What may be missing?

پاسخSolution

chain باید به hook مناسب وصل شده باشه تا packet رو ببینه؛ regular chain به‌تنهایی مسیر شبکه نیست. nft list ruleset رو برای type/hook/priorities بررسی کن.

A chain must attach to the right hook to see packets; a regular chain alone is not a packet path. Inspect type, hook, and priorities in nft list ruleset.

۱۱. شمارهٔ UFW عوض شد11. UFW numbering changed

قانون شمارهٔ 3 رو حذف کردی؛ چرا نباید همون شماره رو برای حذف بعدی حفظ کنی؟

You deleted UFW rule 3. Why should you not reuse that number for another deletion?

پاسخSolution

بعد از حذف، شماره‌های بعدی جابه‌جا می‌شن. هر بار status numbered تازه بخوان و قانون رو با محتوا تطبیق بده.

Deleting a rule shifts subsequent numbers. Re-read numbered status each time and match the rule by content.

۱۲. روی SSH قانون می‌گذاری12. You are changing the SSH rule

از راه دوری و می‌خوای پیش‌فرض incoming رو deny کنی. سه checkpoint قبل از اجرا چیست؟

You are remote and plan to deny inbound by default. Name three checks before applying it.

پاسخSolution

پورت SSH واقعی و allow قانون رو تأیید کن؛ کنسول یا rollback زمان‌دار رو آماده و آزمایش کن؛ ruleset/ارائه‌دهنده firewall رو ثبت کن. بعد قانون رو از client تازه بررسی نهایی کن.

Confirm the actual SSH port and allow rule; prepare and verify console or timed rollback; record current rules and provider policy. Then test with a fresh client connection.

۱۳. پیش‌فرض drop و ICMPv613. Default drop and ICMPv6

چرا نباید تمام ICMPv6 رو بی‌بررسی block کنی؟

Why should you not block all ICMPv6 without analysis?

پاسخSolution

IPv6 neighbor discovery و پیام‌های لازم مسیر/MTU به ICMPv6 وابسته‌اند. سیاست v6 رو با نوع پیام‌ها و نیاز شبکه طراحی کن؛ کپی سادهٔ IPv4 کافی نیست.

IPv6 neighbor discovery and important path/MTU signaling rely on ICMPv6. Design IPv6 policy for required message types; a simple IPv4 copy is insufficient.

۱۴. forward خالی هست14. The forward path is empty

UFW اجازهٔ SSH به VM می‌ده ولی clientهای پشت اون route نمی‌شن. چرا ورودی allow کافی نیست؟

UFW allows SSH to a VM, but clients behind it cannot route. Why is input allow insufficient?

پاسخSolution

SSH به خود VM ورودی هست؛ ترافیک client که از اون عبور می‌کنه forward می‌خواد، به‌علاوه IP forwarding و route/NAT مناسب. port 22 قانون اون‌ها رو نمی‌سازه.

SSH to the VM is input; client traffic passing through it needs forward rules plus IP forwarding and appropriate routes/NAT. An SSH allow does not provide those.

۱۵. UFW و nftables رو با هم اجرا کنیم؟15. Should we manage UFW and nftables together?

یک همکار با UFW کار می‌کنه و تو مستقیم chain جدید می‌سازی. قبلش چه چیزی باید روشن بشه؟

A teammate uses UFW while you add a chain directly. What must be clarified first?

پاسخSolution

مالک سیاست، order/priorities، persistence و اثر روی قانونهای generated باید معلوم باشه. ruleset کامل و مستندات توزیع رو بخوان؛ مدیر دوم رو روی host زنده وارد نکن.

Clarify policy ownership, order/priorities, persistence, and interaction with generated rules. Read the complete ruleset and distribution docs; do not introduce a second manager casually on a live host.

۱۶. قانون runtime ماندگار نیست16. Runtime rule did not persist

بعد از reboot قانون دستی nftables ناپدید شده. آیا kernel اون رو «گم کرده»؟

A manually added nftables rule disappeared after reboot. Did the kernel “forget” it?

پاسخSolution

قانون runtime بود و persistence رو جدا پیکربندی نکرده بودی. فایل configuration و service مسئول بارگذاری رو طبق همون توزیع تنظیم و reboot آزمایشی رو در VM انجام بده.

It was runtime state without persistence configured. Set up the distribution’s configuration file and loading service, then test reboot behavior in a VM.

۱۷. listener نیست17. No listener exists

firewall اجازهٔ 8080 داره ولی ss هیچ listenerی نشون نمی‌ده. گام بعدی چیست؟

The firewall allows 8080 but ss shows no listener. What next?

پاسخSolution

مشکل رو در application bind/پردازه بررسی کن؛ allow قانون برنامه رو راه نمی‌ندازه. ss, service وضعیت و log رو کنار هم بخوان.

Investigate the application process and bind address; an allow rule does not start the service. Compare ss, service status, and logs.

۱۸. بلیت lockout نزدیک هست18. A lockout is imminent

سیاست فعلی تغییرهای مبهم داره، SSH روی port سفارشی هست و ارائه‌دهنده firewall هم فعال هست. اجرای ufw enable رو ادامه می‌دی؟ چه مدرکی لازمه؟

The current policy is unclear, SSH uses a custom port, and a provider firewall is active. Do you proceed with ufw enable? What evidence do you need?

راهنماHint

تا وقتی راه بازگشت و زنجیرهٔ قانونها معلوم نیست، جواب پیش‌فرض «صبر کن» هست.

Until recovery access and the rule path are clear, the default answer is “wait.”

پاسخSolution

نه، هنوز اجرا نکن. پورت SSH رو با socket/service واقعی تأیید کن؛ ارائه‌دهنده سیاست و host ruleset رو ثبت؛ allow قانون رو برای v4/v6 بساز؛ console یا timed rollback رو از قبل آماده کن؛ بعد در VM یا maintenance window از client جدید SSH/برنامه/port بسته رو آزمایش کن. فقط اگه همهٔ مسیرها روشن‌اند، enable کن؛ سپس همون آزمون‌ها رو تکرار و rollback timer رو لغو کن.

Do not proceed yet. Confirm the actual SSH socket/port; record provider and host rules; prepare IPv4/IPv6 allows; arm console or timed rollback; then test SSH, app, and a blocked port from a new client in a VM or maintenance window. Enable only when paths are clear, repeat the tests, and cancel the rollback timer.

فایروال راه رو محدود کرد؛ حالا ورود رو امن می‌کنیمThe firewall narrowed access; next we secure the login

حالا می‌دونی port باز باید به یک listener واقعی برسه، responseهای ارتباط موجود با connectionهای تازه فرق دارن و IPv6 هم از سیاست جا نمی‌مونه. در فصل بعد سراغ SSH key و تنظیمات می‌ریم تا همین تنها راه مدیریتی رو هم با روشی امن‌تر و قابل‌تکرار تنظیم کنیم.

You now know an allowed port must reach a real listener, replies to existing flows differ from new connections, and IPv6 belongs in the policy too. Next we will configure SSH keys and client settings so this management path is safer and repeatable.
