بسته و ریپازیتوریPackages and repositories

در فصل قبل unit درست بود، اما executable روی سرور نبود. راه‌حل این نیست که اولین اسکریپت پیدا‌شده در اینترنت را با sudo اجرا کنیم. اول بفهمیم بستهٔ سیستم‌عامل از کجا می‌آید، چه چیزی نصب می‌کند و چطور صحت منبع بررسی می‌شود.

In the previous chapter, the unit was correct but the executable was missing from the server. The answer is not to run the first internet script we find with sudo. First, let us learn where an OS package comes from, what it installs, and how its source is checked.

۱نمودارdiagram

package manager فقط دکمهٔ نصب نیستA package manager is more than an install button

وقتی می‌گویی «نصب tree»، مدیر بسته باید بفهمد کدام نسخه برای همین توزیع مناسب است، وابستگی‌هایش چیست، فایل‌هایش کجا بروند و چه چیزی از قبل نصب شده. این اطلاعات از repository و metadata می‌آید؛ metadata قدیمی می‌تواند نام تازه‌ای را هنوز نشناسد، حتی اگر بسته در مخزن وجود داشته باشد.

When you ask to “install tree,” the package manager must determine which version fits this distribution, its dependencies, where its files belong, and what is already installed. That information comes from repositories and metadata; stale metadata may not know a newly published package even when the repository contains it.

repository منبع بسته و metadata است؛ manager وابستگی‌ها را حل و transaction را اجرا می‌کند؛ بعد فایل‌ها و پایگاه ثبت بسته‌های نصب‌شده تغییر می‌کنند. امضای معتبر به اعتماد به کلید و زنجیرهٔ توزیع وابسته است، نه فقط ظاهر اسم package.

A repository supplies packages and metadata; the manager resolves dependencies and executes a transaction; then files and the installed-package database change. A valid signature depends on trusting the key and distribution chain, not merely on a package’s name.

repository معمولاً با کلیدهای مشخص امضاها را تأیید می‌کند تا دستکاری ناخواسته یا بستهٔ غیرمنتظره بی‌صدا پذیرفته نشود. HTTPS مسیر انتقال را محافظت می‌کند، اما امضای بسته و اعتماد به maintainer مسئله‌های جدا هستند. اگر امضا یا کلید خطا داد، verification را خاموش نکن؛ منبع، تاریخ سیستم، keyring و تنظیمات repository را بررسی کن.

Repositories commonly use configured keys to verify signatures so altered or unexpected packages are not silently accepted. HTTPS protects the transport, while package signatures and trust in maintainers are separate concerns. If signature or key verification fails, do not disable verification; inspect the source, system time, keyring, and repository configuration.

apt update چیزی نصب نمی‌کندapt update does not install upgrades

روی Debian و Ubuntu، apt update فهرست metadata مخزن‌های فعال را تازه می‌کند. اسمش ممکن است آدم را گول بزند: بسته‌های نصب‌شده را ارتقا نمی‌دهد. برای دیدن ارتقاهای پیشنهادی از apt list --upgradable یا سیاست یک بسته استفاده کن.

On Debian and Ubuntu, apt update refreshes repository metadata for enabled sources. The name can mislead: it does not upgrade installed packages. Use apt list --upgradable or inspect a package’s policy to see candidate updates.

Debian-family inspection
apt-cache policy tree
tree:
  Installed: (none)
  Candidate: 2.1.1-2
  Version table:
     2.1.1-2 500
        500 http://deb.example/ stable/main amd64 Packages
apt show tree

مقادیر بالا نمونه‌اند. Candidate نسخه‌ای است که با metadata فعلی پیشنهاد می‌شود؛ منبع و اولویت هم در policy دیده می‌شود. این خروجی نمی‌گوید نصب حتماً موفق می‌شود یا candidate آخرین نسخهٔ دنیا است. اگر چیزی قدیمی/خالی بود، اول زمان آخرین update و repositoryهای فعال را بررسی کن.

These values are representative. Candidate is the version proposed by current metadata; policy also shows sources and priorities. This does not guarantee installation will succeed or that the candidate is the newest version anywhere. If it looks stale or empty, check when metadata was last refreshed and which repositories are enabled.

حالا فرق update و upgrade روشن‌تر است: update فهرست آدرس/نسخه‌های قابل‌شناسایی را تازه می‌کند؛ apt upgrade یک transaction برای نصب نسخه‌های جدیدتر برنامه‌ریزی و اجرا می‌کند. پیش از تأیید، فهرست تغییرها را بخوان. full-upgrade می‌تواند برای حل وابستگی‌ها بسته‌ای را حذف کند؛ روی سرور آن را بی‌بررسی تأیید نکن.

Now the distinction is clearer: update refreshes the index of known package versions and sources; apt upgrade plans and applies a transaction to install newer versions. Read the change list before confirming. full-upgrade may remove packages to resolve dependencies; do not approve it on a server without reviewing the plan.

در خانوادهٔ RHEL: dnf همین نقش‌ها را دارد، با واژگان خودشOn the RHEL family, dnf has similar roles with its own vocabulary

روی Fedora و بسیاری از توزیع‌های RHEL-family، dnf repository metadata را نگه می‌دارد و transaction نصب/ارتقا را حل می‌کند. دستورها را با apt قاطی نکن: metadata را با dnf makecache تازه کن، وضعیت repository را با dnf repolist ببین و candidate یک بسته را با dnf info بررسی کن. رفتار پیش‌فرض و ابزارهای فرعی ممکن است با توزیع فرق کنند.

On Fedora and many RHEL-family distributions, dnf manages repository metadata and resolves install/upgrade transactions. Do not mix its commands with apt: refresh metadata with dnf makecache, inspect repositories with dnf repolist, and inspect a package candidate with dnf info. Defaults and plugins vary across distributions.

RHEL-family inspection
dnf repolist
repo id                 repo name
fedora                  Fedora 43 - x86_64
updates                 Fedora 43 - Updates
dnf info tree
Available Packages
Name      : tree
Version   : 2.2.1
Repository: fedora

نسخه و repo نمونه‌اند. dnf makecache metadata مخزن‌های فعال را cache می‌کند؛ نصب و ارتقا کارهای جدا هستند. dnf upgrade نسخه‌های جدید را بررسی و transaction را پیشنهاد می‌دهد. transaction را بخوان و اگر repository unavailable یا خارج از release سیستم است، علت را پیدا کن؛ با نصب مخزن تصادفی درمانش نکن.

The version and repository are illustrative. dnf makecache caches metadata from enabled repositories; installation and upgrading are separate operations. dnf upgrade checks for newer versions and proposes a transaction. Review the transaction, and if a repository is unavailable or belongs to another system release, investigate rather than adding a random repository.

نصب یعنی یک transaction؛ قبل از yes، plan را بخوانInstallation is a transaction; read the plan before saying yes

برای آزمایش، ابزار کوچک tree را نصب می‌کنیم. اگر از قبل نصب است، مرحلهٔ نصب را رد کن یا در VM تازه انجام بده. روی Debian-family، از apt show tree و apt-cache policy tree شروع کن؛ بعد فرمان نصب را اجرا و فهرست packageهای پیشنهادی برای نصب را بخوان، پیش از تأیید.

We will install the small tree utility. If it is already present, skip installation or use a fresh VM. On a Debian-family system, start with apt show tree and apt-cache policy tree; then request installation and review the list of packages before confirming.

Debian / Ubuntu only
sudo apt update
sudo apt install tree
tree --version
dpkg-query -S "$(command -v tree)"

در خروجی نصب، نسخهٔ دانلودشده و وابستگی‌هایی که قرار است تغییر کنند مهم‌اند. tree --version وجود executable را نشان می‌دهد؛ dpkg-query -S می‌گوید کدام بسته مالک مسیر فایل است. این دو به‌تنهایی امضای منبع را دوباره audit نمی‌کنند؛ برای منبع، policy و repo فعال را بخوان.

In the install plan, notice the version to be downloaded and any dependencies that will change. tree --version proves the executable is available; dpkg-query -S identifies its owning package. These do not independently audit repository signatures; inspect policy and enabled sources for provenance.

روی RHEL-family همین lab را جداگانه انجام بده: به‌جای apt از dnf استفاده کن و پیش از تأیید transaction، بسته‌های نصب‌شونده را بخوان. این دو بلوک جایگزین هم‌اند، نه فرمان‌هایی برای اجرای پشت سر هم روی یک سیستم.

On a RHEL-family system, run the same lab separately with dnf and review the proposed transaction before confirming. These are alternatives, not commands to run sequentially on one machine.

Fedora / RHEL-family only
sudo dnf makecache
sudo dnf info tree
sudo dnf install tree
tree --version
rpm -qf "$(command -v tree)"

بررسی خروجی install به تو نشان می‌دهد dnf دقیقاً کدام نسخه و dependencyها را می‌خواهد. rpm -qf مالک فایل روی سیستم را پیدا می‌کند. اگر دستور یا package در توزیع تو نام دیگری دارد، اول dnf provides یا جست‌وجوی رسمی همان توزیع را ببین.

Reviewing install output shows which version and dependencies dnf intends to use. rpm -qf identifies the package owning a file on the system. If a command or package has another name in your distribution, consult dnf provides or that distribution’s official package search.

remove، purge و dependency را قاطی نکنDo not conflate remove, purge, and dependencies

اگر فقط می‌خواهی ابزار تمرینی را برگردانی، transaction حذف را ببین. در Debian، apt remove tree خود بسته را حذف می‌کند ولی معمولاً فایل‌های پیکربندی package را نگه می‌دارد؛ apt purge tree پیکربندی package را هم پاک می‌کند. این تضمین نمی‌کند داده‌های کاربر یا تغییرات دستی package حذف/بازگردانی شوند.

To undo the practice install, inspect a removal transaction. On Debian, apt remove tree removes the package but commonly keeps package configuration; apt purge tree also removes package configuration. Neither guarantees removal or restoration of user data or manual changes.

inspect before removing
sudo apt remove tree
The following packages will be REMOVED:
  tree
After this operation, ... disk space will be freed.
Do you want to continue? [Y/n]

این خروجی representative است؛ اگر فهرست حذف طولانی یا شامل بستهٔ مهم است، پاسخ n بده و علت را بررسی کن. apt autoremove هم transaction جداست: فهرست پیشنهادی را بخوان و فرض نکن هر dependencyِ بدون‌استفاده‌ای واقعاً قابل حذف است.

This output is representative. If the removal list is long or includes an important package, answer n and investigate. apt autoremove is another transaction: review its proposed list instead of assuming every dependency marked unused is safe to delete.

در DNF، dnf remove tree را اجرا کن و dependencyهایی را که می‌خواهد حذف کند ببین؛ بسته به تنظیمات ممکن است وابستگی‌های نصب‌شدهٔ بدون‌مصرف هم در transaction بیایند. حذف package را با حذف دادهٔ برنامه یا volume یکی نگیر.

With DNF, use dnf remove tree and inspect dependencies proposed for removal; configuration may include dependencies that are no longer needed. Do not confuse package removal with deleting application data or volumes.

خرابی عمدی: «بسته پیدا نشد»Deliberate failure: “package not found”

در VM آزمایشی فرض کن package تازه‌ای در repository اضافه شده، ولی index محلی از قبل مانده است. جست‌وجو نامی پیدا نمی‌کند. هنوز نتیجه نگیر بسته وجود ندارد یا باید verification را خاموش کنی. اول شواهد منبع و metadata را کنار هم بگذار.

In a disposable VM, suppose a package has recently appeared in a repository but the local index is old. Search finds nothing. Do not yet conclude the package does not exist or that verification should be disabled. Compare evidence about sources and metadata first.

Debian-family diagnosis
apt-cache policy example-tool
N: Unable to locate package example-tool
grep -R '^[^#].*deb ' /etc/apt/sources.list /etc/apt/sources.list.d/ 2>/dev/null
sudo apt update
apt-cache policy example-tool

بررسی اول نشان می‌دهد metadata فعلی candidate ندارد؛ source-list می‌گوید کدام مخزن‌ها تعریف شده‌اند؛ پس از update دوباره policy را بخوان. اگر هنوز candidate نیست، release/distribution، component، معماری و اسم package را بررسی کن. update کردن فقط metadata مخزن‌های فعال را تازه می‌کند؛ بستهٔ خارج از release را وارد نمی‌کند.

The first check says current metadata has no candidate; the source list shows configured repositories; after update, inspect policy again. If there is still no candidate, check release/distribution, component, architecture, and package name. Refreshing metadata does not import packages from another release.

روی DNF هم ابتدا dnf repolist و dnf info example-tool را بخوان؛ بعد در صورت نیاز dnf makecache و تکرار جست‌وجو. اگر repo متعلق به نسخهٔ دیگری است یا GPG error می‌دهد، آن را disable یا امضا را خاموش نکن؛ علت mismatch/key را جدا تشخیص بده.

With DNF, inspect dnf repolist and dnf info example-tool first; then run dnf makecache and repeat the search if appropriate. If a repository belongs to another release or reports a GPG error, do not disable it or signature checks; diagnose the release/key mismatch.

کلید امضا و pin کردن نسخهSigning keys and pinning a version

مدیر بسته معمولاً با کلیدهای مورد اعتماد، امضای package یا metadata را بررسی می‌کند. پیام «کلید ناشناخته» را با واردکردن هر کلیدی که یک سایت تصادفی پیشنهاد داده حل نکن؛ fingerprint و منبع کلید را از کانال رسمی توزیع بررسی کن. گزینه‌هایی مثل --nogpgcheck راه‌حل خطای عادی نیستند.

A package manager commonly verifies package or metadata signatures with trusted keys. Do not resolve an “unknown key” message by importing a key from a random site; verify its fingerprint and source through the distribution’s official channel. Options such as --nogpgcheck are not routine fixes.

pin/hold کردن می‌تواند ارتقای یک package خاص را موقتاً متوقف کند، اما بدهی نگهداری می‌سازد: آسیب‌پذیری یا ناسازگاری ممکن است باقی بماند. فقط وقتی نیاز عملی روشن، مالک و تاریخ بازبینی داری انجام بده. در Debian می‌توانی apt-mark hold NAME و بعد apt-mark unhold NAME را به‌کار ببری؛ DNF معمولاً برای versionlock به plugin و پیکربندی متناسب با نسخه/توزیع نیاز دارد.

Pinning/holding can temporarily prevent upgrades to a specific package, but it creates maintenance debt: vulnerabilities or incompatibilities may remain. Use it only with a clear operational need, an owner, and a review date. Debian provides apt-mark hold NAME and apt-mark unhold NAME; DNF version locking commonly requires a plugin and distribution/version-specific setup.

چرا curl | bash پرریسک است؟Why is curl | bash risky?

با curl URL | sudo bash متن دوردست را مستقیم به shell دارای اختیار می‌دهی. پیش از دیدن محتوا ممکن است اسکریپت repository، کلید، کاربر یا فایل سیستمی بسازد و چیزی را حذف کند. گاهی vendor راه نصب مستندی دارد؛ باز هم دامنهٔ اختیار، منبع کلید، نسخهٔ توزیع و کاری که script می‌کند را بررسی کن. package manager dependency و فایل‌ها را ثبت می‌کند و امکان دیدن transaction می‌دهد، اما خودش بی‌نیاز از اعتماد نیست.

With curl URL | sudo bash, remote text is sent straight to a privileged shell. Before inspecting it, the script could add a repository/key/user, alter system files, or delete data. A vendor may document an installer; still verify its privilege scope, signing-key source, target distribution, and actions. A package manager tracks dependencies and files and exposes a transaction plan, but it does not eliminate the need for trust.

ترتیب کم‌خطرترA safer order

اول package را از repository رسمی توزیع پیدا کن؛ source و candidate را ببین؛ transaction را مرور کن؛ بعد نصب و نسخه/مالک فایل را تأیید کن. اگر مخزن رسمی ندارد، روش رسمی vendor را بخوان و قبل از privilege دادن، محتوای script و امضای آن را بررسی کن.

First look for the package in the distribution’s official repositories; inspect source and candidate; review the transaction; then install and verify version/file ownership. If it is not available there, read the vendor’s official method and inspect the script and signature before granting privilege.

آزمایشگاه: بسته از کجا آمد و چطور برمی‌گردد؟Lab: where did the package come from, and how do we undo it?

در یک VM یک‌بارمصرف، پیش از نصب بررسی کن tree از قبل هست یا نه، candidate و repository را ببین، index را تازه کن، transaction را مرور و ابزار را نصب کن. بعد نسخه و package مالک executable را ثبت کن. در پایان حذف را درخواست بده و فهرستش را بخوان؛ اگر transaction فقط package آزمایشی را حذف می‌کند، تأیید کن و اگر نه لغو کن.

In a disposable VM, check whether tree is already installed, inspect its candidate and repository, refresh metadata, review the transaction, and install it. Record the version and owning package. At the end, request removal and review the plan; confirm only if it removes the intended test package, otherwise cancel.

Check the package name and release first; then inspect enabled repositories and metadata freshness. A signature error is a different branch—do not hide it by disabling checks.

تمرین‌ها: از index قدیمی تا انتخاب امنExercises: from stale indexes to safer choices

۱. بسته در برابر repository1. Package versus repository

یک package چیست و repository چه نقشی دارد؟

What is a package, and what role does a repository play?

پاسخSolution

package واحد نسخه‌بندی‌شدهٔ نرم‌افزار و metadata آن است؛ repository منبعی است که packageها و فهرست/metadata قابل جست‌وجو را منتشر می‌کند.

A package is a versioned software unit with metadata; a repository publishes packages and searchable indexes/metadata.

۲. apt update2. apt update

بعد از apt update آیا نسخهٔ نصب‌شدهٔ kernel یا web server ارتقا یافته؟

After apt update, has the installed kernel or web server been upgraded?

پاسخSolution

نه؛ update شاخص مخزن را تازه می‌کند. برای دیدن candidateهای ارتقا apt list/policy را ببین و upgrade را جداگانه، با مرور transaction انجام بده.

No; update refreshes repository indexes. Inspect upgrade candidates, then run upgrade separately and review its transaction.

۳. dnf makecache3. dnf makecache

آیا dnf makecache برنامه را نصب می‌کند؟

Does dnf makecache install an application?

پاسخSolution

نه؛ metadata مخزن‌های فعال را cache/sync می‌کند. نصب با dnf install transaction جداست.

No; it caches/synchronizes metadata for enabled repositories. Installation is a separate dnf install transaction.

۴. candidate خالی4. No candidate

apt-cache policy tool-x candidate نشان نمی‌دهد. سه بررسی منطقی چیست؟

apt-cache policy tool-x shows no candidate. What three checks make sense?

پاسخSolution

اسم دقیق بسته، metadata تازه شده یا نه، و repository/component مناسب برای release و architecture فعال است یا نه. غیرفعال‌کردن امضا علت نبودن candidate را حل نمی‌کند.

Check the exact package name, metadata freshness, and whether a suitable repository/component for the release and architecture is enabled. Disabling signatures does not fix a missing candidate.

۵. اطلاعات package5. Package information

در Debian-family برای دیدن candidate/source و شرح بسته از چه دستورهایی شروع می‌کنی؟

On a Debian-family system, which commands inspect a candidate/source and package description?

پاسخSolution

apt-cache policy NAME و apt show NAME. خروجی وابسته به metadata فعلی است؛ زمان refresh و منابع فعال را هم در نظر بگیر.

apt-cache policy NAME and apt show NAME. Results depend on current metadata, so consider refresh time and enabled sources.

۶. transaction غافلگیرکننده6. A surprising transaction

هنگام نصب یک ابزار، package manager می‌گوید ۲۴ بسته حذف می‌شود. چه می‌کنی؟

While installing a utility, the package manager proposes removing 24 packages. What do you do?

پاسخSolution

تأیید نکن؛ transaction را لغو کن و repository، release، pin و dependency conflict را بررسی کن. تغییر بزرگ‌تر از درخواست اولیه نیاز به تشخیص دارد.

Do not confirm. Cancel and inspect repositories, release, pins, and dependency conflicts. A transaction larger than the request needs diagnosis.

۷. remove یا purge7. Remove or purge

می‌خواهی خود برنامه برداشته شود اما config package بماند. در apt کدام را انتخاب می‌کنی؟

You want the application removed while keeping package configuration. Which apt action fits?

پاسخSolution

apt remove معمولاً configuration package را نگه می‌دارد؛ purge آن را هم حذف می‌کند. دادهٔ کاربر/تغییر دستی تضمین نمی‌شود.

apt remove commonly keeps package configuration; purge removes it too. User data/manual changes are not guaranteed.

۸. remove روی DNF8. DNF removal

چرا پیش از تأیید dnf remove فهرست را می‌خوانی؟

Why review the plan before confirming dnf remove?

پاسخSolution

ممکن است dependencyهای بیشتری هم در transaction حذف شوند. نام و تعداد بسته‌ها را بررسی کن؛ حذف دادهٔ برنامه جداگانه مدیریت می‌شود.

More dependencies may be included in the transaction. Review package names/count; application data is managed separately.

۹. package مالک executable9. Owning package

در Debian و RPM چطور می‌فهمی کدام package مسیر executable را آورده؟

How do you identify which package owns an executable path on Debian and RPM systems?

پاسخSolution

dpkg-query -S PATH یا rpm -qf PATH. این مالک ثبت‌شده را نشان می‌دهد، نه اینکه فایل دست‌کاری نشده یا از مخزن دلخواه آمده باشد.

dpkg-query -S PATH or rpm -qf PATH. This reports the recorded owner, not that the file is unmodified or came from an intended source.

۱۰. کلید GPG ناشناخته10. Unknown GPG key

repository می‌گوید کلید ناشناخته. آیا check را خاموش می‌کنی؟ قدم بعدی چیست؟

A repository reports an unknown key. Do you disable checking? What comes next?

پاسخSolution

نه. منبع مخزن و fingerprint کلید را از کانال رسمی توزیع/vendor بررسی کن؛ تاریخ سیستم و keyring را هم بسنج.

No. Verify the repository source and key fingerprint through the distribution/vendor’s official channel; also check system time and keyring.

۱۱. repository اشتباه release11. Wrong-release repository

روی یک release، مخزن release دیگری را اضافه کرده‌ای. چرا صرفاً نصب‌شدن یک بسته، این انتخاب را درست نمی‌کند؟

You added a repository for another release. Why does a successful install not make that choice sound?

پاسخSolution

dependency/versionهای آن مخزن ممکن است با کتابخانه‌های سیستم ناسازگار شوند. source و candidate را چک کن، repo اشتباه را حذف/اصلاح کن و transaction را دوباره مرور کن.

Its dependency/version set may conflict with system libraries. Inspect source and candidate, correct the mismatched repository, and review the transaction again.

۱۲. دکمهٔ ارتقای بزرگ12. A large upgrade

apt full-upgrade قرار است package مهمی را حذف کند. آیا این فقط نسخه‌های جدید را نصب می‌کند؟

apt full-upgrade proposes removing an important package. Does it only install newer versions?

پاسخSolution

نه؛ برای حل dependency ممکن است package حذف شود. transaction را لغو و تغییر release/repository و dependencyها را بررسی کن.

No; it may remove packages to resolve dependencies. Cancel and inspect release/repository changes and dependency conflicts.

۱۳. curl | bash13. curl | bash

یک راهنمای نصب curl URL | sudo bash پیشنهاد می‌دهد. چه ریسک‌هایی را باید قبل از اجرا بفهمی؟

An install guide proposes curl URL | sudo bash. What risks should you understand first?

پاسخSolution

اسکریپت دوردست با اختیار root اجرا می‌شود و شاید repo/key/user بسازد یا فایل تغییر دهد. منبع، محتوا، امضا، دامنهٔ تغییر و روش رسمی package را بررسی کن.

A remote script runs with root privilege and may add repositories/keys/users or alter files. Verify source, content, signature, scope, and the official package route.

۱۴. version pinning14. Version pinning

چه زمانی hold/versionlock موجه است و چه تعهدی ایجاد می‌کند؟

When is hold/versionlock justified, and what obligation does it create?

پاسخSolution

وقتی ناسازگاری مشخصی نیاز به توقف موقت دارد و مالک/تاریخ بازبینی معلوم است. ارتقای امنیتی ممکن است عقب بماند؛ برای رفع pin باید برنامه داشته باشی.

When a known incompatibility requires a temporary hold and an owner/review date is defined. Security updates may be delayed, so plan how to remove the pin.

۱۵. metadata cache15. Metadata cache

package manager آفلاین است ولی policy یک candidate قدیمی نشان می‌دهد. این تناقض است؟

The package manager is offline but policy shows an old candidate. Is that contradictory?

پاسخSolution

نه؛ اطلاعات cacheشده را می‌توان خواند، ولی تازه‌بودنش تضمین نیست. زمان آخرین sync و repository را ببین؛ برای نسخهٔ جاری به اتصال و metadata تازه نیاز است.

No; cached information can be read, but freshness is not guaranteed. Check last sync and repository; current candidates require connectivity and fresh metadata.

۱۶. upgrade در برابر install16. Upgrade versus install

فرق apt update با apt upgrade را برای همکارت در یک جمله توضیح بده.

Explain the difference between apt update and apt upgrade in one sentence.

پاسخSolution

اولی metadata مخزن را تازه می‌کند؛ دومی transaction ارتقای packageهای نصب‌شده را حل/اجرا می‌کند. یکی جای دیگری نیست.

The first refreshes repository metadata; the second resolves/applies a transaction to upgrade installed packages. They are not interchangeable.

۱۷. خروجی نصب را مرور کن17. Review an install plan

پیش از Y زدن به transaction، چه سه چیز را نگاه می‌کنی؟

What three things do you inspect before confirming an install transaction?

پاسخSolution

packageهای افزوده/حذف‌شده، نسخه و منبع candidate، و dependencyهای تغییرکرده. اگر دامنه غیرمنتظره است، لغو کن و plan را بفهم.

Packages added/removed, candidate version/source, and changed dependencies. If the scope is unexpected, cancel and understand the plan.

۱۸. بلیت incident: ابزار پیدا نمی‌شود18. Incident ticket: package not found

پس از ساخت unit، systemd می‌گوید executable نیست و apt هم package را پیدا نمی‌کند. ترتیب بررسی و مدرک repair چیست؟

After creating a unit, systemd says the executable is missing and apt cannot find its package. What is your investigation order and repair proof?

راهنماHint

اول خطای systemd را از «نصب نیست» جدا کن؛ بعد نام package و repository metadata را بسنج.

Separate the systemd error from the assumption “not installed”; then check package name and repository metadata.

پاسخSolution

journal/status مسیر ExecStart و خطای واقعی را مشخص می‌کند. بعد apt-cache policy و source-list را بررسی، apt update اجرا و policy را تکرار کن؛ transaction نصب را بخوان و تأیید کن. در پایان نسخه و مالک مسیر executable را بررسی، unit را restart و همان درخواست سرویس را تکرار کن. اگر امضا خطا داشت، check را خاموش نکن؛ منبع/کلید را تشخیص بده.

Journal/status identifies ExecStart and the actual failure. Inspect apt-cache policy and source lists, run apt update, and repeat the policy check; review and confirm the install transaction. Verify executable version and file owner, restart the unit, and repeat the same service request. If signature verification fails, do not disable it—diagnose source/key trust.

وقتی بسته نصب شد، چطور از log جواب بیرون بکشیم؟Once installed, how do we find an answer in a log?

حالا می‌توانی بفهمی نرم‌افزار از کدام repository آمده، package manager چه چیزی قرار است تغییر دهد و خطای package-not-found از کجا شروع می‌شود. سرور بعدی جواب را در logها می‌گذارد؛ فصل بعد سراغ grep و ابزارهای متن می‌رویم تا از میان خط‌های زیاد، نشانهٔ مهم را پیدا کنیم.

You can now inspect where software came from, what a package transaction will change, and where a package-not-found failure begins. The next server will leave its clue in logs; next we will use grep and text tools to find the important signal among many lines.
