اسکریپت پشتیبان‌گیری زمان‌بندی‌شدهA scheduled backup script

نیمه‌شب است و فایلی پاک شده. همکارت می‌گوید «backup داریم؛ هر شب یک tar ساخته می‌شود.» آخرین اجرای موفق کی بوده؟ فایل سالم است؟ می‌توانیم یک چیز مشخص را برگردانیم؟ این مأموریت فایل آرشیو را با backup قابل‌اعتماد اشتباه نمی‌گیرد.

It is midnight and a file has disappeared. A teammate says, “We have backups; a tar file is created every night.” When did the last run succeed? Is the archive intact? Can we restore one known item? This mission does not confuse an archive with a dependable backup.

مأموریت: آرشیو بساز، بعد بازیابی را ثابت کنMission: create an archive, then prove recovery

روی Ubuntu VM آزمایشی، داده‌ای ساختگی را هر سه دقیقه backup می‌گیریم تا لازم نباشد تا فردا صبر کنیم. نسخه‌های موفق timestamp و checksum دارند؛ پنج نسل آخر می‌ماند و خروجی job در journal ثبت می‌شود. یک فایل را حذف می‌کنی و به مسیر جدا restore می‌کنی؛ دادهٔ زنده را کورکورانه بازنویسی نمی‌کنیم.

On a disposable Ubuntu VM, back up synthetic data every three minutes. Successful generations have timestamps and checksums; keep the latest five and record job output in the journal. Delete one file and restore it to a separate path; we will not blindly overwrite live data.

نسخه پس از verify منتشر می‌شود و retention پس از ساخت نسخهٔ تازه اجرا می‌شود. restore در مسیر جدا جلوی overwrite ناخواسته را می‌گیرد.

A generation is published after verification, and retention runs only after a new copy succeeds. A separate restore path prevents accidental overwrite.

همه‌چیز در VM قابل‌بازگردانی انجام می‌شود؛ backup روی همان ماشین خرابی دیسک یا گم‌شدن VM را پوشش نمی‌دهد. این پروژه بازیابی سازمانی نمی‌سازد.

Run everything in a recoverable VM; a backup on the same machine does not protect against disk failure or VM loss. This is not an organisational recovery system.

نقطهٔ ۱ از ۷: source، account و مقصدCheckpoint 1 of 7: source, account, and destination

مسیرها را اول بررسی کن؛ اگر از قبل داده دارند، VM تازه یا مسیر تازه انتخاب کن. runner فقط source را می‌خواند و مقصد را می‌نویسد.

Inspect paths first; if they already contain data, use a fresh VM or new paths. The runner reads the source and writes to the destination.

نام کاربر، مجوز هر پوشه و خالی‌بودن مقصد را ثبت کن. آزمون موفق فقط همین مسیرها را می‌سنجد؛ شامل‌بودن فایل‌های دیگر را ثابت نمی‌کند.

Record the account, directory permissions, and empty destination. Success checks these paths only; it does not prove other files are included.

نقطهٔ ۲ از ۷: تعریف اجرای موفقCheckpoint 2 of 7: define a successful run

خروجی موفق یعنی archive timestampدار ساخته شده، tar آن را می‌خواند، checksum پاس می‌شود، journal پیام می‌گیرد و exit status صفر است. checksum بایت‌ها را می‌سنجد؛ تازگی یا کامل‌بودن معنایی داده را نه.

Success means a timestamped archive exists, tar can read it, its checksum passes, the journal has a message, and the exit status is zero. A checksum tests bytes, not data freshness or semantic completeness.

codenames-20260927T091500Z.tar.gz
codenames-20260927T091500Z.tar.gz.sha256

نقطهٔ ۳ از ۷: اسکریپت root-ownedCheckpoint 3 of 7: root-owned script

runner نباید بتواند script اجرایی خودش را عوض کند. archive ابتدا در پوشهٔ موقت همان filesystem ساخته و فهرست و checksum می‌شود؛ بعد rename و منتشر می‌شود. retention تا موفقیت کامل به نسل‌های قبلی دست نمی‌زند.

The runner must not be able to alter its own executable script. Stage the archive on the destination filesystem, list it, and compute its checksum before publishing with rename. Retention leaves old generations untouched until the new one succeeds.

create script path
sudo install -d -o root -g root -m 0755 /usr/local/libexec
sudoedit /usr/local/libexec/codenames-backup
complete reference script
#!/usr/bin/env bash
set -Eeuo pipefail
SRC=/srv/codenames-backup-demo/source
DEST=/var/backups/codenames-demo
KEEP=5
LOCK=/run/lock/codenames-backup.lock
stage=
newarchive=
newsum=
log() { printf '%s %s\n' "$(date -u +%Y-%m-%dT%H:%M:%SZ)" "$*"; }
finish() {
  rc=$?
  [[ -z "$stage" || ! -d "$stage" ]] || rm -rf -- "$stage"
  if (( rc != 0 )); then
    [[ -z "$newarchive" ]] || rm -f -- "$newarchive"
    [[ -z "$newsum" ]] || rm -f -- "$newsum"
    log "ERROR exit=$rc"
  fi
  exit "$rc"
}
trap finish EXIT
for t in tar sha256sum flock date find sort cut; do
  command -v "$t" >/dev/null || { log "ERROR missing tool=$t"; exit 127; }
done
[[ -d "$SRC" ]] || { log "ERROR source missing"; exit 1; }
[[ -d "$DEST" && -w "$DEST" ]] || { log "ERROR destination unavailable"; exit 1; }
exec 9>"$LOCK"
flock -n 9 || { log "ERROR another run holds lock"; exit 1; }
stamp=$(date -u +%Y%m%dT%H%M%SZ)
archive="$DEST/codenames-$stamp.tar.gz"
sumfile="$archive.sha256"
[[ ! -e "$archive" && ! -e "$sumfile" ]] || { log "ERROR generation exists"; exit 1; }
stage=$(mktemp -d "$DEST/.stage.XXXXXX")
tmp="$stage/archive.tar.gz"
sumtmp="$stage/archive.sha256"
tar -czf "$tmp" -C "$SRC" .
tar -tzf "$tmp" >/dev/null
digest=$(sha256sum "$tmp" | cut -d' ' -f1)
printf '%s  %s\n' "$digest" "$(basename "$archive")" > "$sumtmp"
mv -- "$tmp" "$archive"
newarchive=$archive
mv -- "$sumtmp" "$sumfile"
newsum=$sumfile
find "$DEST" -maxdepth 1 -type f -name 'codenames-*.tar.gz' -printf '%f\n' | sort -r | tail -n +6 | while IFS= read -r old; do
  [[ -z "$old" ]] || { rm -- "$DEST/$old"; rm -- "$DEST/$old.sha256"; }
done
newarchive=
newsum=
log "OK archive=$(basename "$archive") sha256=$digest"

در شکست، trap پوشهٔ stage و خروجی نیمه‌منتشرشدهٔ همین run را پاک می‌کند؛ آرشیوهای قبلی حفظ می‌شوند. GNU find گزینهٔ -printf دارد؛ این نمونه برای Ubuntu است. پاک‌سازی روی مقصد واقعی را پیش از اجرا بازبینی کن.

On failure, the exit trap removes staging and this run’s partially published files; earlier archives remain. GNU find provides -printf; this example targets Ubuntu. Review cleanup against the exact destination before running it elsewhere.

نقطهٔ ۴ از ۷: اجرا و آزمون restore اولیهCheckpoint 4 of 7: run and initial restore test

یک بار دستی با user خودش اجرا کن. archive و sidecar باید هم‌timestamp باشند. نام واقعی فایل را بردار؛ checksum صفر یعنی بایت‌ها برابرند، نه اینکه محتوای درست انتخاب شده باشد.

Run once manually as its own user. The archive and sidecar should share a timestamp. Use the actual filename; a successful checksum means bytes match, not that the right content was selected.

run, checksum, inspect, and extract one item to quarantine
sudo chmod 0755 /usr/local/libexec/codenames-backup
sudo chown root:root /usr/local/libexec/codenames-backup
sudo -u backup-runner /usr/local/libexec/codenames-backup
ls -l /var/backups/codenames-demo
cd /var/backups/codenames-demo
sha256sum -c codenames-TIMESTAMP.tar.gz.sha256
tar -tzf codenames-TIMESTAMP.tar.gz
sudo install -d -o backup-runner -g backup-runner -m 0700 /var/tmp/codenames-restore-check
sudo -u backup-runner tar -xzf /var/backups/codenames-demo/codenames-TIMESTAMP.tar.gz -C /var/tmp/codenames-restore-check ./data/restore-me.txt
cmp /srv/codenames-backup-demo/source/data/restore-me.txt /var/tmp/codenames-restore-check/data/restore-me.txt

آرشیو با مسیر نسبی ساخته شده؛ member ممکن است با ./ شروع شود. فهرست tar نام دقیق را می‌گوید. cmp بی‌خروجی و exit صفر یعنی برابری byte به byte؛ restore مستقیم روی source انجام نده.

The archive uses relative paths; a member may start with ./. The tar listing gives its exact name. Silent cmp with exit zero means byte equality; do not restore directly over the source.

نقطهٔ ۵ از ۷: خطای مجوز را پیدا کنCheckpoint 5 of 7: diagnose a permission failure

فقط مقصد ساختگی را موقتاً برای runner غیرقابل‌نوشتن کن و نتیجه را ثبت کن؛ فوراً mode را برگردان. در رخداد واقعی با stat و namei -l مسیر را بررسی می‌کنی، نه اینکه حدسی مالکیت را عوض کنی.

Temporarily make only the synthetic destination unwritable to the runner and record the result; restore its mode immediately. In a real incident, inspect the path with stat and namei rather than guessing at ownership.

bounded failure test
sudo stat -c '%A %U:%G %n' /var/backups/codenames-demo
sudo chmod 0500 /var/backups/codenames-demo
sudo -u backup-runner test -w /var/backups/codenames-demo
echo $?
sudo chmod 0700 /var/backups/codenames-demo
sudo -u backup-runner test -w /var/backups/codenames-demo

exit ۱ از test یعنی همین account نمی‌تواند بنویسد؛ علت دقیق parent را ثابت نمی‌کند. بعد از repair همان آزمون باید موفق باشد.

Exit 1 means this account cannot write; it does not identify the exact parent causing it. Repeat the same test after repair.

نقطهٔ ۶ از ۷: systemd timer و logCheckpoint 6 of 7: systemd timer and logs

service کار را انجام می‌دهد و timer زمانش را می‌چیند. این آزمایش هر سه دقیقه تکرار می‌شود؛ production cadence را جدا تعیین کن. این timer از OnBootSec/OnUnitActiveSec استفاده می‌کند، نه catch-up تقویمی. اول service را دستی از systemd اجرا و نتیجه‌اش را بخوان؛ موعد NEXT به‌تنهایی موفقیت نیست.

The service performs the work; the timer schedules it. This lab repeats every three minutes; choose production cadence separately. This timer uses OnBootSec/OnUnitActiveSec, not calendar catch-up. Start the service manually through systemd first; NEXT alone does not prove success.

create unit files
sudoedit /etc/systemd/system/codenames-backup.service
sudoedit /etc/systemd/system/codenames-backup.timer
codenames-backup.service
[Unit]
Description=Create a verified lab backup
[Service]
Type=oneshot
User=backup-runner
Group=backup-runner
ExecStart=/usr/local/libexec/codenames-backup
codenames-backup.timer
[Unit]
Description=Schedule the lab backup
[Timer]
OnBootSec=90s
OnUnitActiveSec=3min
AccuracySec=1s
Unit=codenames-backup.service
[Install]
WantedBy=timers.target
validate, run, inspect, schedule
sudo systemd-analyze verify /etc/systemd/system/codenames-backup.service /etc/systemd/system/codenames-backup.timer
sudo systemctl daemon-reload
sudo systemctl start codenames-backup.service
systemctl show codenames-backup.service -p Result -p ExecMainStatus
sudo journalctl -u codenames-backup.service -n 30 --no-pager
sudo systemctl enable --now codenames-backup.timer
systemctl list-timers codenames-backup.timer --all --no-pager

برای اجرای موفق Result=success و ExecMainStatus=0 و پیام OK در journal را ببین. سپس timer را متوقف، مقصد را ۰۵۰۰ کن و service را اجرا کن؛ failure باید در exit و log دیده شود. mode را فوراً ۰۷۰۰ کن، اجرای تازهٔ موفق بگیر و timer را دوباره روشن کن. journal log است، نه alert بیرونی.

For success, inspect Result=success, ExecMainStatus=0, and an OK journal entry. Then stop the timer, set destination mode to 0500, and run the service; exit and logs should show failure. Immediately restore mode 0700, obtain a fresh successful run, and restart the timer. The journal is logging, not external alerting.

failure, evidence, repair, retry
sudo systemctl stop codenames-backup.timer
sudo chmod 0500 /var/backups/codenames-demo
sudo systemctl start codenames-backup.service
systemctl show codenames-backup.service -p Result -p ExecMainStatus
sudo journalctl -u codenames-backup.service -n 20 --no-pager
sudo chmod 0700 /var/backups/codenames-demo
sudo systemctl start codenames-backup.service
sudo systemctl start codenames-backup.timer
find /var/backups/codenames-demo -maxdepth 1 -type f -printf '%f\n' | sort

پس از چند اجرا پنج archive و sidecar باید بمانند. GNU find گزینهٔ -printf دارد و توزیع‌های دیگر فرق می‌کنند. اگر retention fail شد، run کامل موفق نیست؛ دنبال پیام تازه بگرد.

After several runs, five archives and sidecars should remain. GNU find has -printf; other distributions may differ. If retention fails, the full run did not succeed; inspect fresh logs.

نقطهٔ ۷ از ۷: حذف و restore واقعیCheckpoint 7 of 7: delete and actually restore

پیش از حذف، مسیر دقیق را ببین و مطمئن شو فایل ساختگی است. generation را checksum کن و عضو را از فهرست پیدا کن؛ اگر هریک fail شد، restore نکن.

Inspect the exact path and confirm the file is synthetic before deleting it. Checksum the generation and find the member in its listing; if either fails, do not restore.

delete only the lab file, verify archive
sudo rm -- /srv/codenames-backup-demo/source/data/restore-me.txt
sudo ls -lt /var/backups/codenames-demo/codenames-*.tar.gz
cd /var/backups/codenames-demo
sha256sum -c codenames-TIMESTAMP.tar.gz.sha256
tar -tzf codenames-TIMESTAMP.tar.gz | grep 'restore-me.txt'

نام member واقعی را از listing بردار؛ ممکن است با ./ شروع شود. فقط همان فایل را به quarantine استخراج کن، با محتوای شناخته‌شده مقایسه و بعد به source برگردان. این ثابت می‌کند همین فایل از همین archive قابل بازیابی است، نه کل ماشین.

Use the actual member name from the listing; it may start with ./ . Extract only that file to quarantine, compare with known contents, then return it to the source. This proves this file can be recovered from this archive, not the whole machine.

restore one member and verify exact content
sudo install -d -o backup-runner -g backup-runner -m 0700 /var/tmp/codenames-restore-check
sudo -u backup-runner tar -xzf /var/backups/codenames-demo/codenames-TIMESTAMP.tar.gz -C /var/tmp/codenames-restore-check ./data/restore-me.txt
printf '%s\n' 'restore this exact file' | cmp - /var/tmp/codenames-restore-check/data/restore-me.txt
sudo install -o root -g backup-runner -m 0640 /var/tmp/codenames-restore-check/data/restore-me.txt /srv/codenames-backup-demo/source/data/restore-me.txt

پیش از پاک‌کردن quarantine محتوا و مسیر دقیق را بازبینی کن؛ کل archive را روی source باز نکن. اگر نام member متفاوت است، حدسی extract نکن.

Inspect the quarantine path and contents before cleanup; do not unpack the whole archive over source. If the member name differs, do not guess.

شرط قبولیAcceptance criteria

همکار باید بتواند از شواهد بفهمد کدام اجرا موفق بوده، کدام failure دیده شده، کدام نسخه سالم است و چه چیزی restore شده:

A teammate must be able to determine from evidence which run succeeded, what failed, which generation is intact, and what was restored:

  • script root-owned و مقصد فقط برای runner قابل نوشتن است.The script is root-owned and only the runner can write to the destination.
  • archive و sidecar با sha256sum verify می‌شوند.Archive and sidecar pass sha256sum verification.
  • timer موعد بعدی و journal نتیجهٔ واقعی را نشان می‌دهد.The timer shows its next activation; the journal shows actual results.
  • failure مجوز exit و log دارد؛ پس از repair اجرای تازه موفق است.Permission failure has a nonzero exit and log; a fresh run succeeds after repair.
  • حداکثر پنج نسل کامل و sidecar متناظر باقی مانده.At most five complete generations and matching sidecars remain.
  • فایل حذف‌شده در مسیری جدا restore و با دادهٔ شناخته‌شده مقایسه شده.The deleted file was restored separately and compared with known data.
  • handoff محدودیت local-only بودن backup را می‌گوید.The handoff states the backup is local-only.

راهنماهاHints

دستی موفق است ولی unit نهManual run works but unit fails

user، مسیرهای مطلق و journal را بررسی کن؛ shell تعاملی محیط متفاوتی دارد.

Check user, absolute paths, and journal; an interactive shell has a different environment.

موعد timer رسیده ولی نسل تازه نیستTimer fired but no new generation

schedule را از service result جدا کن؛ Result، ExecMainStatus و زمان log را ببین. موعد موفقیت نیست.

Separate schedule from service result; inspect Result, ExecMainStatus, and log time. A deadline is not success.

checksum fail شدهChecksum fails

این نسل را سالم فرض نکن. archive و sidecar شاید از دو run باشند یا فایل تغییر کرده؛ نسل دیگری را verify کن.

Do not trust this generation. The archive and sidecar may be from different runs or the file may have changed; verify another generation.

پاک‌سازی آزمایشLab cleanup

پس از ثبت مدرک timer را stop و disable کن، unitها را بردار و daemon-reload بزن. پیش از حذف هر مسیر source/archive/quarantine آن را بررسی کن. حذف archive شرط پروژه نیست.

After recording evidence, stop and disable the timer, remove its units, and reload systemd. Inspect any source/archive/quarantine path before deletion. Removing archives is not required.

در یادداشت ۵ تا ۸ خطی زمان آخرین اجرای موفق، نام generation، checksum، failure دیده‌شده، فایل restoreشده و محدودیت مقصد محلی را بنویس. backup وقتی ارزش دارد که ساختش دیده شود، شکستش پنهان نماند و restore واقعاً تمرین شده باشد.

In a five-to-eight-line handoff, record the last successful run, generation name, checksum, observed failure, restored file, and local-destination limitation. A backup is useful when its creation is visible, failures are not hidden, and restore has been rehearsed.
