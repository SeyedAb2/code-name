اسکریپت‌نویسی BashBash scripting

گزارش دیشب با اعتمادبه‌نفس نوشته «نسخهٔ پشتیبان موفق بود»، ولی فایل مقصد اصلاً وجود نداره. چند دستور درست رو کنار هم گذاشتن و خیال کردن اگه خط آخر اجرا شد یعنی همه‌چیز خوب بوده. این فصل قراره همین اعتماد الکی رو از اسکریپت بگیره.

Last night’s report says the backup succeeded, but the destination file is missing. Someone pasted a few commands into a script and assumed that reaching the end meant every step worked. This time we will build a script that does not report success when its input, archive, or final check failed.

چرا دستورهای درست، اسکریپت قابل اعتماد نمی‌سازن؟Why do correct commands not automatically make a reliable script?

دستورهایی که توی ترمینال خوب کار می‌کنن، خودبه‌خود اسکریپت قابل اعتماد نمی‌سازن. اسکریپت باید ورودی بد، خطای وسط کار و نتیجهٔ ناقص رو بفهمه و اگه واقعاً موفق نشده، موفقیت اعلام نکنه.

Last chapter, we answered a question from a log with grep and awk. Now the same check must run every night. The difference is important: at a terminal you usually see an error; in a scheduled script, only an exit code or an incomplete file may remain.

قرار نیست اسکریپت رو با چند گزینهٔ جادویی «ضدخطا» کنیم. هدف این هست که مرزهای مهم رو خودمان روشن کنیم: آرگومان‌ها معتبرند؟ فرمان واقعاً شکست رو گزارش می‌کنه؟ خروجی نهایی قابل خواندن هست؟ فایل موقت بعد از قطع برنامه چه می‌شه؟

We will not make the script “error-proof” with a few magic options. We will make its important boundaries explicit: are arguments valid, does a command failure reach the caller, is the final output readable, and what happens to temporary files if the program stops?

هر مرحله فقط بعد از موفقیت مرحلهٔ قبل جلو می‌ره؛ trap مسیر پاک‌سازی رو در پایان اجرا نگه می‌داره، نه اینکه خطای کار رو «درست» کنه.

Each step advances only after the previous one succeeds. The trap preserves cleanup at exit; it does not repair the underlying failure.

اول یک فایل واقعی، نه چند خط حفظیStart with a real file, not syntax trivia

یک پوشهٔ آزمایشگاهی بساز که نامش فاصله داره. این فاصله عمدی هست: اگه بعداً مسیر رو درست نقل‌قول نکنیم، ایراد رو زود می‌بینیم. دستورهای زیر فقط در home خودت فایل نمونه می‌سازن.

Create a lab directory whose name contains a space. The space is deliberate: if we later fail to quote a path, we will see the bug. These commands create sample files only in your home directory.

prepare a disposable source tree
mkdir -p "$HOME/bash lab/source dir"
printf 'alpha\n' > "$HOME/bash lab/source dir/one.txt"
printf 'beta\n' > "$HOME/bash lab/source dir/two file.txt"
find "$HOME/bash lab/source dir" -maxdepth 1 -type f -printf '%f\n'

دو نام فایل رو با فاصله می‌بینی. فعلاً اون‌ها رو parse یا به آرایه‌ای از کلمه‌ها تبدیل نمی‌کنیم؛ Bash رشته‌ها، آرایه‌ها و نام فایل‌ها رو با قواعد متفاوتی می‌بینه. برای پیمایش نام‌های دلخواه، الگوی for f in $(find ...) شکننده هست؛ دربارهٔ اون بعدتر حرف می‌زنیم.

You should see two filenames, one containing a space. We will not parse them into words: Bash handles strings, arrays, and filenames according to different rules. A loop such as for f in $(find ...) is fragile for arbitrary names; we will return to that.

فایل اسکریپت باید بگه با چه مفسری اجرا بشه. #!/usr/bin/env bash از env می‌خواد Bash رو از PATH پیدا کنه؛ این شکل در Linuxهای معمول رایج هست، اما وجود Bash و env در محیط مقصد رو تضمین نمی‌کنه. برای اسکریپت Bash اون رو با bash script.sh اجرا کن یا فایل رو فایل اجرایی کن.

A script should identify its interpreter. #!/usr/bin/env bash asks env to find Bash on PATH; this is common on Linux, but does not guarantee Bash or env exists on the target. Run a Bash script with bash script.sh or mark it executable.

hello.sh
#!/usr/bin/env bash
printf 'script interpreter: %s\n' "$BASH_VERSION"

اگه permission اجرا رو نداده‌ای، bash hello.sh هنوز می‌تونه فایل رو بخونه. برای اجرای مستقیم، chmod +x hello.sh و سپس ./hello.sh لازمه. خط اول به سیستم می‌گه مفسر چیست؛ به‌تنهایی permission نمی‌ده.

Without execute permission, bash hello.sh can still read the file. Direct execution needs chmod +x hello.sh followed by ./hello.sh. The first line selects an interpreter; it does not grant execute permission.

متغیر، نقل‌قول و خروجی یک فرمانVariables, quoting, and command output

در Bash هنگام مقداردهی دور = فاصله نمیاد: source_dir="...". متغیر با $source_dir خوانده می‌شه. دو نقل‌قول دور گسترش متغیر جلوی word splitting و glob expansion ناخواسته رو می‌گیره.

In Bash assignments, do not put spaces around =: source_dir="...". Read the variable as $source_dir. Double quotes around an expansion prevent unintended word splitting and glob expansion.

quote the path
source_dir="$HOME/bash lab/source dir"
printf 'source: %s\n' "$source_dir"
printf 'first argument: <%s>\n' $source_dir
printf 'quoted argument: <%s>\n' "$source_dir"

خط دوم چاپی مقدار رو نگه می‌داره. خط سوم عمداً خراب هست: shell مسیر رو به چند آرگومان می‌شکنه. خط چهارم یک آرگومان می‌فرسته. هنگام ساخت فرمان، به‌جای حدس از printf '%q\n' "$source_dir" هم می‌تونی نمایش escapeشده بگیری؛ اما این نمایش، مجوز اجرای رشته با eval نیست.

The second line prints the value intact. The third line is deliberately wrong: the shell splits the path into multiple arguments. The fourth passes one argument. To inspect an escaped representation, use printf '%q\n' "$source_dir"; that representation is not permission to execute a string with eval.

برای گرفتن خروجی فرمان از دستور substitution استفاده می‌کنیم: src=$(pwd). Bash خروجی stdout رو جایگزین می‌کنه و newlineهای انتهایی رو حذف می‌کنه؛ stderr رو نمی‌گیره. این روش برای یک مقدار ساده مناسب هست، نه برای نگهداری فهرست نام فایل‌هایی که می‌تونن newline داشته باشن.

Use command substitution to capture command output: src=$(pwd). Bash substitutes stdout and removes trailing newlines; stderr is not captured. This is suitable for a simple value, not a list of filenames that may contain newlines.

اسکریپت باید ورودی بد رو زود رد کنهA script should reject bad input early

این ابزار دو آرگومان می‌خواد: پوشهٔ منبع و پوشهٔ نگهداری. $# تعداد آرگومان‌ها و "$1" نخستین آرگومان هست. از اول هر آرگومان رو جداگانه نقل‌قول می‌کنیم؛ "$@" هم برای عبور دادن همهٔ آرگومان‌ها به‌شکل جداگانه به‌کار می‌ره، برخلاف "$*".

This tool needs two arguments: a source directory and a destination directory. $# is the argument count and "$1" the first argument. Quote each argument from the start. "$@" forwards all arguments separately, unlike "$*".

validate before changing anything
if [[ $# -ne 2 ]]; then
  printf 'usage: backup.sh SOURCE_DIR DEST_DIR\n' >&2
  exit 64
fi

if [[ ! -d $1 ]]; then
  printf 'source is not a directory: %s\n' "$1" >&2
  exit 66
fi

اینجا exit codeهای 64 و 66 قرارداد انتخابی همین برنامه‌اند، نه معنای جهانی برای همهٔ نرم‌افزارها. شرط‌های [[ ... ]] برای رشته، فایل و عدد کاربرد دارن و با [ ... ] قدیمی دقیقاً یکسان نیستن. قبل از ساخت فایل، تعداد آرگومان و نوع منبع بررسی شده هست.

Exit codes 64 and 66 here are conventions chosen by this program, not universal meanings for every application. Bash’s [[ ... ]] handles string, file, and numeric tests and is not identical to the older [ ... ]. Argument count and source type are checked before creating files.

برای چند ورودی، loop می‌خوایم. این نسخه آرایه‌ای رو با "${items[@]}" می‌پیماید و هر عضو رو یک آرگومان نگه می‌داره؛ نوشتن "${items[*]}" همه رو به یک رشته تبدیل می‌کنه.

For several inputs, use a loop. This version iterates an array with "${items[@]}" and preserves each item as one argument; "${items[*]}" joins them into a single string.

array and loop
items=("$HOME/bash lab/source dir/one.txt" "$HOME/bash lab/source dir/two file.txt")
for item in "${items[@]}"; do
  [[ -f $item ]] && printf 'found: %s\n' "$item"
done

وقتی pipeline شکست رو پنهان می‌کنهWhen a pipeline hides a failure

فرض کن می‌خوایم اندازهٔ آرشیو رو گزارش کنیم، اما خود archive ساخته نشده. چه exit codeی برمی‌گرده؟ در Bash معمولی وضعیت یک pipeline همون وضعیت آخرین فرمان هست؛ پس tar ... | wc -c ممکنه وضعیت موفق wc رو بده، هرچند tar شکست خورده باشه.

Suppose we want to report an archive’s size, but the archive was never created. Which exit status comes back? In ordinary Bash, a pipeline’s status is the last command’s status, so tar ... | wc -c may report successful wc even when tar failed.

failure hidden by wc
bash -c 'tar -czf /no-such-dir/out.tgz /no-such-dir/input | wc -c; printf "pipeline status=%s\n" "$?"'
0
tar: ... Cannot open: No such file or directory
pipeline status=0

ترتیب خطا روی stderr ممکنه با خروجی جابه‌جا بشه. مدرک تعیین‌کننده، pipeline status=0 هست: pipeline شکست tar رو به فراخواننده منتقل نکرد. گزینهٔ set -o pipefail وضعیت غیرصفرِ فرمان شکست‌خوردهٔ سمت چپ رو هم قابل مشاهده می‌کنه.

The stderr message may appear before or after stdout. The key evidence is pipeline status=0: the pipeline did not pass tar’s failure to its caller. set -o pipefail makes a failing command’s non-zero status visible through the pipeline.

enable pipeline failure propagation
bash -o pipefail -c 'tar -czf /no-such-dir/out.tgz /no-such-dir/input | wc -c; printf "pipeline status=%s\n" "$?"'
0
tar: ... Cannot open: No such file or directory
pipeline status=2

کد دقیق tar به نسخه و علت خطا وابسته هست؛ این‌جا مهم این هست که دیگر صفر نیست. برای همین اسکریپت گزینه‌ها رو صریح می‌نویسیم: set -u متغیر تعریف‌نشده رو خطا می‌کنه و pipefail خطای اعضای pipeline رو پنهان نمی‌کنه. set -e رو هم می‌شه اضافه کرد، اما رفتار اون استثناهای زیادی داره؛ جایگزین طراحی و بررسی وضعیت نیست.

Tar’s exact code depends on version and cause; what matters is that it is no longer zero. We will set options explicitly: set -u treats an unset variable as an error, and pipefail prevents a pipeline from hiding a failed component. set -e is also available, but has many exceptions; it is not a substitute for deliberate status handling.

set -e در شرط if، بخش‌هایی از &&/|| و چند زمینهٔ دیگر طبق قواعد Bash می‌تونه نادیده گرفته بشه؛ داخل function هم نتیجه به محل فراخوانی بستگی داره. برای فرمانی که ممکنه طبیعی شکست بخوره، مثل جست‌وجوی بدون نتیجه، وضعیت رو خودت در if بررسی کن. اگه خطا handling دقیق لازمه، به رفتار واقعی هر مرحله تکیه کن نه شعار «strict mode همه‌چیز رو حل می‌کنه».

Bash may ignore set -e in an if test, parts of &&/|| lists, and other contexts; functions are affected by their call context too. For a command that can legitimately return failure, such as a search with no match, inspect its status explicitly in an if. Reliable failure handling depends on each step’s real behavior, not the claim that “strict mode fixes everything.”

تابع‌ها و گزارش‌هایی که برای انسان‌اندFunctions and logs written for people

منطق تکراری رو در function می‌ذاریم. تابع در همون shell اجرا می‌شه و وضعیت آخرین فرمانش رو برمی‌گردونه، مگر اینکه return صریح بده. این تابع پیام زمان‌دار رو روی stderr می‌نویسه تا stdout برای داده یا خروجی قابل استفاده بمونه.

Put repeated logic in a function. A function runs in the same shell and returns the status of its last command unless it explicitly uses return. This function writes a timestamped message to stderr, leaving stdout available for data.

small reusable function
log() {
  printf '[%s] %s\n' "$(date -u +%FT%TZ)" "$*" >&2
}

log 'backup started'

برای پیام یک‌تکه، "$*" اینجا عمدی هست؛ اما برای عبور دادن آرگومان‌ها به فرمان دیگر، معمولاً "$@" رو می‌خوایم. اگه متن log دادهٔ کنترل‌نشده داشته باشه، newline می‌تونه خط‌ها رو جعل‌پذیر کنه؛ در سرویس واقعی ورودی رو sanitize یا ساختاریافته ثبت کن.

Here "$*" is intentional because the message is treated as one string. To forward arguments to another command, we usually want "$@". Untrusted newlines can forge log lines, so production services should sanitize or structure untrusted values.

فایل موقت: اگه وسط کار قطع شد چه؟Temporary files: what if the script stops halfway?

اگه tar وسط کار متوقف بشه، فایل نیمه‌کاره می‌تونه شبیه نسخهٔ پشتیبان واقعی به‌نظر برسه. mktemp نامی یکتا و فایل موقتی می‌سازه؛ trap ... EXIT پاک‌سازی رو هنگام خروج عادی یا خطا اجرا می‌کنه. trap خطا رو جبران نمی‌کنه، فقط اثر موقت همین اجرا رو جمع می‌کنه.

If tar stops halfway, an incomplete file can look like a real backup. mktemp creates a unique temporary file; trap ... EXIT runs cleanup on normal or error exit. A trap does not repair the failure; it only removes this run’s temporary artifact.

اسکریپت کامل پایین‌تر اول آرشیو رو در فایل موقت داخل پوشهٔ مقصد می‌سازه، بعد با tar -tzf می‌خواندش و تنها بعد از اون به نام نهایی منتقل می‌کنه. فایل موقت در همون filesystem هست تا rename معمولاً اتمی باشه؛ اما این روش، نسخهٔ پشتیبان گرفتن از فایل‌هایی که هم‌زمان تغییر می‌کنن یا صحت محتوای برنامه رو تضمین نمی‌کنه.

The complete script below writes the archive to a temporary file in the destination, checks it with tar -tzf, then moves it to its final name. Keeping the temporary file on the same filesystem makes the rename typically atomic; this does not guarantee a consistent snapshot of files changing during the backup or application-level correctness.

این لَب فقط از پوشهٔ نمونهٔ ساخته‌شده در home بکاپ می‌گیره. مسیر مقصد رو بیرون از منبع نگه دار و فرمان cleanup رو روی مسیرهای واقعی یا کل home اجرا نکن.

This lab backs up only the sample directory created in your home. Keep the destination outside the source and never aim cleanup commands at real data or your entire home directory.

حالا نسخهٔ اول رو بسازیمNow build the first complete version

تابع fail پیام رو به stderr می‌فرسته و با کد غیرصفر خارج می‌شه. اول آرگومان‌ها رو می‌سنجیم، مسیر منبع رو واقعی می‌کنیم، مقصد رو می‌سازیم و مطمئن می‌شویم مقصد داخل منبع نیست؛ وگرنه اجرای بعدی ممکنه نسخهٔ پشتیبان قبلی رو هم وارد نسخهٔ پشتیبان تازه کنه.

The fail function writes to stderr and exits non-zero. We validate arguments, resolve the source directory, create the destination, and ensure it is not inside the source; otherwise a later run could include an earlier backup in a new one.

backup.sh — validation and setup
#!/usr/bin/env bash
set -euo pipefail

log() { printf '[%s] %s\n' "$(date -u +%FT%TZ)" "$*" >&2; }
fail() { log "ERROR: $*"; exit 1; }

if [[ $# -ne 2 ]]; then
  printf 'usage: backup.sh SOURCE_DIR DEST_DIR\n' >&2
  exit 64
fi

[[ -d $1 ]] || fail "source directory not found: $1"
src=$(cd -- "$1" && pwd -P) || fail 'cannot resolve source path'
[[ $src != / ]] || fail 'refusing to archive the filesystem root'

mkdir -p -- "$2" || fail "cannot create destination: $2"
dest=$(cd -- "$2" && pwd -P) || fail 'cannot resolve destination path'
if [[ $dest == "$src" || $dest == "$src/"* ]]; then
  fail 'destination must be outside the source directory'
fi

این بخش روی Linux از pwd -P و قابلیت‌های رایج GNU استفاده می‌کنه. شرط [[ $dest == "$src/"* ]] مقصدهای داخل منبع رو رد می‌کنه. هنوز ثابت نکردیم منبع در حین آرشیو تغییر نمی‌کنه؛ اگه consistency مهم هست باید از تصویر لحظه‌ای یا سازوکار خود برنامه/فایل‌سیستم استفاده کنی.

This section targets Linux and uses common GNU facilities with pwd -P. The pattern rejects a destination nested inside the source. We have not proved the source remains unchanged during archiving; if consistency matters, use a snapshot or an application/filesystem-specific mechanism.

حالا یک فایل موقت یکتا می‌گیریم و trap رو قبل از شروع tar ثبت می‌کنیم. با mktemp "$dest/.backup.XXXXXX" فایل در همون مقصد ساخته می‌شه؛ اگه مقصد مجوز نوشتن نداشته باشه، برنامه همین‌جا با خطا می‌ایستد.

Now create a unique temporary file and install the trap before tar starts. mktemp "$dest/.backup.XXXXXX" creates it in the destination; if that directory is not writable, the script stops here.

archive, verify, then publish
tmp=''
cleanup() {
  if [[ -n ${tmp:-} && -e $tmp ]]; then
    rm -f -- "$tmp"
  fi
}
trap cleanup EXIT
trap 'exit 130' INT
trap 'exit 143' TERM

tmp=$(mktemp "$dest/.backup.XXXXXX") || fail 'cannot create temporary file'
name=$(basename -- "$src")
stamp=$(date -u +%Y%m%dT%H%M%SZ)
final="$dest/${name}-${stamp}-$$.tar.gz"
log "creating archive for $src"
tar -czf "$tmp" -C "$(dirname -- "$src")" "$name" || fail 'tar failed'
tar -tzf "$tmp" > /dev/null || fail 'archive verification failed'
[[ ! -e $final ]] || fail "refusing to overwrite: $final"
mv -- "$tmp" "$final" || fail 'cannot publish archive'
tmp=''
log "verified backup: $final"

نام نهایی زمان UTC و PID رو داره تا اجراهای نزدیک به هم معمولاً نام جدا بگیرن؛ قبل از جابه‌جایی هم overwrite رو رد می‌کنیم. این بررسی در برابر دو پردازه هم‌زمان یک قفل اتمی نیست، پس سامانهٔ حساس به هم‌زمانی به نام‌گذاری/قفل قوی‌تری نیاز داره. tar -tzf فقط می‌تونه آرشیو رو بخونه و فهرست کنه؛ ثابت نمی‌کنه دادهٔ زنده سازگار یا بازیابی موفق می‌شه.

The final name includes UTC time and PID so nearby runs usually differ; we also refuse an existing destination before moving. That check is not an atomic lock against two concurrent processes, so a concurrency-sensitive system needs stronger naming or locking. tar -tzf proves the archive can be read and listed; it does not prove live data was consistent or that a restore will succeed.

در handler مربوط به INT و TERM با کدهای قراردادی خارج می‌شویم؛ سپس trap خروج، فایل موقت رو پاک می‌کنه. پاک‌سازی فقط همون مسیر ساخته‌شده با mktemp رو هدف می‌گیره. برای همین متغیر مسیر رو نقل‌قول می‌کنیم و از rm -rf "$dest" خبری نیست.

The INT and TERM handlers exit with conventional statuses, then the EXIT trap removes the temporary file. Cleanup targets only the path created by mktemp. That is why the path is quoted and why there is no broad rm -rf "$dest".

دو خرابی رو خودمان ایجاد کنیمDeliberately create two failures

اول نسخهٔ خام رو بدون quote آزمایش کن: اگه نام مسیر فاصله داشته باشه، shell اون رو می‌شکنه. راهنما باید به ما نشان بده کدوم آرگومان واقعاً رسیده هست. سپس یک pipeline بدون pipefail رو خراب کردیم و دیدیم وضعیت فرمان آخر می‌تونه شکست اول رو پنهان کنه.

First test an unquoted version: when a path contains spaces, the shell splits it. The diagnostic should show which arguments actually arrived. Then we broke a pipeline without pipefail and saw how the last command’s status can hide the first command’s failure.

evidence, then repair
source_dir="$HOME/bash lab/source dir"
printf '<%s>\n' $source_dir
printf '<%s>\n' "$source_dir"

shellcheck backup.sh
bash -n backup.sh

دو جفت angle bracket در دو خط خروجی اول نشون می‌ده متغیر بی‌quote به دو آرگومان شکسته هست؛ یک جفت در خط بعد یعنی مسیر یک‌تکه مانده. ShellCheck ممکنه برای گسترش بی‌quote هشدار SC2086 بده؛ bash -n فقط نحو رو parse می‌کنه و درستی مسیر، tar یا منطق نسخهٔ پشتیبان رو ثابت نمی‌کنه.

The first output has two angle-bracketed arguments, showing that the unquoted expansion split; the next line has one. ShellCheck may report SC2086 for an unquoted expansion. bash -n only parses syntax; it does not prove paths, tar behavior, or backup logic are correct.

اگه ShellCheck روی سیستم نصب نیست، نصبش رو از مخزن معتبر توزیعت انجام بده یا از نسخهٔ آنلاین رسمی برای کد غیرمحرمانه استفاده کن. ابزار lint هست، نه اجراکنندهٔ اسکریپت و نه تضمین امنیت. هشدار رو بخوان؛ بی‌صدا خاموشش نکن. متغیر آرایه‌ای برای optionها معمولاً از رشته‌ای مثل opts="-x -y" امن‌تر هست.

If ShellCheck is unavailable, install it from a trusted distribution repository or use its official online service for non-secret code. It is a linter, not a script runner or security guarantee. Read warnings rather than silencing them blindly. An array for options is usually safer than a string such as opts="-x -y".

نام فایل‌ها رو با فاصله جدا نکنDo not split filenames on whitespace

نام فایل Unix می‌تونه فاصله و حتی newline داشته باشه؛ تنها NUL و slash داخل یک جزء نام مجاز نیست. برای همین for f in $(find ...) فهرست عمومی نام فایل‌ها رو درست منتقل نمی‌کنه: دستور substitution newlineهای انتهایی رو حذف می‌کنه و word splitting نام‌ها رو می‌شکنه.

A Unix filename may contain spaces and even newlines; NUL and slash are the exceptions within a path component. Therefore for f in $(find ...) cannot safely transport arbitrary filenames: command substitution removes trailing newlines and word splitting breaks names apart.

safe filename handling pattern
while IFS= read -r -d '' file; do
  printf 'file: %s\n' "$file"
done < <(find "$source_dir" -type f -print0)

این الگو NUL رو جداکننده می‌گیره، پس فاصله و newline داخل نام حفظ می‌شه. پردازه substitution یعنی <( ... ) در Bash در دسترس هست اما POSIX sh نیست؛ روی همهٔ shellها فرضش نکن. برای tar، معمولاً امن‌تر و ساده‌تر هست کل درخت پوشه رو به ابزار بسپاری، نه اینکه نام‌ها رو خودت parse کنی.

This pattern uses NUL as the delimiter, preserving spaces and newlines. Process substitution <( ... ) is a Bash feature, not POSIX sh; do not assume every shell supports it. With tar, it is often safer and simpler to pass the directory tree to the tool instead of parsing filenames yourself.

لَب: گزارش شبانه‌ای که شکست رو پنهان نمی‌کنهLab: a nightly report that does not hide failures

نسخه رو در یک فایل به نام backup.sh در پوشهٔ شخصی‌ات ذخیره کن. قبل از اجرا، مسیرها رو فقط به آزمایشگاه خودت بده. مرحلهٔ اول نحو رو بررسی می‌کنه؛ مرحلهٔ دوم اجازهٔ اجرای مستقیم رو می‌ده؛ مرحلهٔ سوم آرشیو می‌سازه و نتیجه رو فهرست می‌کنه.

Save the complete script as backup.sh in your home directory. Pass only your lab paths. First check syntax, then enable direct execution, then create and list the archive.

run against the disposable sample
bash -n "$HOME/backup.sh"
chmod u+x "$HOME/backup.sh"
"$HOME/backup.sh" "$HOME/bash lab/source dir" "$HOME/bash lab/backups"
find "$HOME/bash lab/backups" -maxdepth 1 -type f -name '*.tar.gz' -print
tar -tzf "$HOME"/bash\ lab/backups/*.tar.gz

اگه آرشیو ساخته شد، نام دو فایل رو در خروجی آخر می‌بینی. این فقط ثابت می‌کنه tar فهرست آرشیو رو می‌خونه. بعد ورودی نامعتبر رو امتحان کن: برنامه باید با کد غیرصفر برگرده و فایل تازه نسازه. برای دیدن کد، دستور رو اجرا کن و بلافاصله printf '%s\n' "$?" رو بزن.

If the archive was created, the last command lists both files. This proves only that tar can read the archive index. Next pass an invalid source: the script should return non-zero and create no new archive. To see the status, run it and immediately print $?.

negative check
"$HOME/backup.sh" "$HOME/no-such-source" "$HOME/bash lab/backups"
printf 'exit=%s\n' "$?"
find "$HOME/bash lab/backups" -maxdepth 1 -name '.backup.*' -print

مسیر نامعتبر باید پیغام خطا و وضعیت غیرصفر بده؛ جست‌وجوی فایل موقت نباید چیزی نشان بده. این‌بار pipeline رو هم عمداً خراب کن: در اسکریپت موقت set -o pipefail رو حذف کن و pipeline tar رو وارد کن؛ وضعیت رو قبل و بعد مقایسه کن، سپس نسخهٔ سالم رو برگردان. فایل اصلی اسکریپت رو با patch آزمایشگاهی خراب نکن؛ یک کپی در همون پوشه بساز.

An invalid path should produce an error and non-zero status; the temporary-file search should return nothing. Now deliberately break a pipeline: in a disposable copy, remove set -o pipefail and add the failing tar pipeline; compare statuses, then restore the working version. Do not damage your only script copy.

فهرست خوانا هنوز restore نیست. یک پوشهٔ تازه بساز، آرشیو رو همون‌جا استخراج کن و درخت رو با منبع مقایسه کن؛ این دستورها فقط مسیر مشخص آزمایشگاه رو لمس می‌کنن.

A readable listing is not yet a restore. Create a fresh directory, extract there, and compare the tree with the source; these commands touch only the named lab paths.

restore to a separate directory
mkdir -p "$HOME/bash lab/restore"
tar -xzf "$HOME"/bash\ lab/backups/*.tar.gz -C "$HOME/bash lab/restore"
diff -r "$HOME/bash lab/source dir" "$HOME/bash lab/restore/source dir"

اگه `diff` چیزی چاپ نکرد و وضعیت صفر بود، دو درخت در این مقایسه برابرن. این مدرک خوبی برای همین نمونه هست، نه تضمین recovery برای سرویس واقعی؛ فایل‌هایی که در حین نسخهٔ پشتیبان تغییر کرده‌اند ممکنه نیاز به تصویر لحظه‌ای سازگار داشته باشن.

If diff prints nothing and exits zero, these two trees match for this comparison. That is useful evidence for this sample, not a recovery guarantee for a real service; files changing during backup may require a consistent snapshot.

این بررسی لَب رو کامل می‌کنه؛ نسخهٔ پشتیبان تولیدی هنوز به نسخه‌بندی، نگهداری چند نسخه، فضای جدا و تست دوره‌ای restore نیاز داره.

This completes the lab; a production backup still needs versioning, retention, separate storage, and periodic restore tests.

وقتی شواهد رو نگه داشتی و مطمئن شدی مسیر دقیقاً آزمایشگاه خودت هست، پاک‌سازی این دادهٔ آزمایشی اختیاری هست: rm -r -- "$HOME/bash lab". این فرمان پوشهٔ هم‌نام زیر home رو حذف می‌کنه؛ اگه اون پوشه رو برای کار دیگری ساخته‌ای، اجرا نکن.

After preserving your evidence and confirming this is exactly your disposable lab path, cleanup is optional: rm -r -- "$HOME/bash lab". It removes that named directory under your home; do not run it if you use it for other work.

تمرین‌ها: از خواندن خروجی تا طراحی رفتارExercises: from reading output to designing behavior

برای چند سؤال کد رو اجرا کن؛ برای بقیه، قبل از دیدن پاسخ وضعیت و اثر روی فایل‌ها رو پیش‌بینی کن. هدف حفظ گزینه‌ها نیست—باید بتوانی بگویی کدوم مدرک موفقیت یا شکست رو ثابت می‌کنه.

Run the code for some questions; for others, predict status and filesystem effects before opening the solution. The goal is not memorizing options—you should be able to say which evidence proves success or failure.

۱. shebang چه کاری می‌کنه؟1. What does the shebang do?

فایل tool.sh با #!/usr/bin/env bash رو با bash tool.sh اجرا کرده‌ای. آیا shebang در این روش مفسر رو انتخاب کرد؟ اگه با ./tool.sh اجرا کنی چه چیز دیگری لازمه؟

You ran a file with #!/usr/bin/env bash using bash tool.sh. Did the shebang select the interpreter in that invocation? What else does direct ./tool.sh execution require?

پاسخSolution

در اجرای bash tool.sh خودت Bash رو صدا زده‌ای؛ سیستم shebang رو برای انتخاب interpreter به‌کار نبرده هست. اجرای مستقیم به مسیر interpreter معتبر و permission اجرا نیاز داره؛ chmod +x فقط permission رو تغییر می‌ده.

With bash tool.sh, you chose Bash yourself; the system did not use the shebang to select an interpreter. Direct execution needs a valid interpreter path and execute permission; chmod +x changes only the permission.

۲. دو آرگومان یا یک آرگومان؟2. One argument or two?

مقدار dir="$HOME/a b" هست. فرق printf '<%s>\n' $dir و printf '<%s>\n' "$dir" چیست؟

Given dir="$HOME/a b", what differs between printf '<%s>\n' $dir and printf '<%s>\n' "$dir"?

پاسخSolution

اولی معمولاً به‌خاطر word splitting دو آرگومان می‌ده؛ دومی یک آرگومان حفظ‌شده می‌ده. در مسیرها و بیشتر گسترش متغیرها quote بگذار، مگر اینکه splitting عمداً و با طراحی صریح خواسته شده باشه.

The first is normally split into two arguments; the second preserves one. Quote path and most variable expansions unless splitting is an explicit, deliberate part of the design.

۳. دستور substitution چه چیزی رو نمی‌گیره؟3. What does command substitution not capture?

اگه x=$(command) باشه، کدوم stream در x می‌ره و چه اتفاقی برای newlineهای انتهایی می‌افته؟

For x=$(command), which stream is captured, and what happens to trailing newlines?

پاسخSolution

stdout جایگزین می‌شه و newlineهای انتهایی حذف می‌شن؛ stderr جدا می‌مونه. برای یک مقدار متنی خوب هست، اما فهرست نام فایل دلخواه رو با اون منتقل نکن.

Stdout is substituted and trailing newlines are removed; stderr stays separate. It works for a simple textual value, not for transporting arbitrary filenames.

۴. ورودی نامعتبر4. Invalid input

چرا بررسی $# -ne 2 باید قبل از خواندن $1 و $2 انجام بشه، مخصوصاً با set -u؟

Why should you check $# -ne 2 before reading $1 and $2, especially with set -u?

پاسخSolution

با آرگومان کم، ارجاع به متغیر positional تعریف‌نشده با set -u می‌تونه اسکریپت رو متوقف کنه. اعتبارسنجی اول خطای قابل فهم و وضعیت قراردادی می‌ده و از اثر جانبی قبل از فهم ورودی جلوگیری می‌کنه.

With too few arguments, referencing an unset positional parameter under set -u can stop the script. Validating first produces a clear error and chosen status before side effects begin.

۵. فایل یا پوشه؟5. File or directory?

آرگومان منبع به فایل معمولی اشاره می‌کنه، ولی شرط [[ -d $1 ]] ردش می‌کنه. آیا این false positive هست؟

The source argument points to a regular file, but [[ -d $1 ]] rejects it. Is that a false positive?

پاسخSolution

نه؛ قرارداد این ابزار پوشه هست. اگه قرار هست فایل هم پذیرفته بشه، قرارداد و شاخه‌های رفتار رو صریح گسترش بده، نه اینکه شرط رو حذف کنی و فرض نامشخص بسازی.

No; this tool’s contract requires a directory. If files should also be accepted, extend the contract and branches explicitly rather than removing the test and creating ambiguous behavior.

۶. تلهٔ set -e6. The set -e trap

فرمان grep -q needle file داخل شرط if وضعیت غیرصفر داد. آیا الزاماً اسکریپت با set -e تمام شده هست؟

The command grep -q needle file returned non-zero inside an if condition. Must the script necessarily have exited under set -e?

پاسخSolution

نه؛ وضعیت فرمان در شرط if بخشی از زمینه‌هایی هست که errexit در اون‌ها عمل نمی‌کنه. بدون match بودن grep هم می‌تونه نتیجهٔ مورد انتظار باشه؛ اون رو با شاخهٔ else و معنی وضعیت مدیریت کن.

No; a command used as an if test is among the contexts where errexit does not act normally. No grep match can be expected; handle it through explicit branches and status meaning.

۷. pipeline چه وضعیتی می‌ده؟7. What status does the pipeline return?

false | wc -l با تنظیم پیش‌فرض Bash اجرا می‌شه. کدوم فرمان وضعیت نهایی رو تعیین می‌کنه؟

Run false | wc -l with Bash defaults. Which command determines the pipeline’s status?

پاسخSolution

بدون pipefail وضعیت فرمان آخر یعنی wc گزارش می‌شه، معمولاً صفر. set -o pipefail باعث می‌شه شکست یکی از اجزا وضعیت pipeline رو غیرصفر کنه؛ اگه چند فرمان شکست بخورند، Bash وضعیت آخرین فرمان شکست‌خورده رو می‌ده.

Without pipefail, the last command’s status—usually zero from wc—is returned. With set -o pipefail, a component failure makes the pipeline non-zero; if several fail, Bash returns the status of the rightmost failed command.

۸. exit code یعنی چه؟8. What does an exit code mean?

تابع check_source فرمان [[ -d $1 ]] رو آخرین خط داره و return نداره. اگه پوشه باشه یا نباشه، وضعیت تابع چه می‌شه؟

A function ends with [[ -d $1 ]] and has no explicit return. What is its status when the directory exists or not?

پاسخSolution

به‌طور معمول وضعیت آخرین فرمان تابع رو برمی‌گردونه: شرط موفق صفر، شرط ناموفق غیرصفر. فراخواننده باید این قرارداد رو بشناسد؛ عدد دقیق test builtin رو به‌عنوان API ثابت بین shellها فرض نکن.

Normally the function returns its last command’s status: a successful test is zero, a failed test non-zero. The caller must understand that contract; do not treat a test builtin’s exact non-zero number as a stable cross-shell API.

۹. چرا trap پاک‌سازی؟9. Why use a cleanup trap?

اسکریپت بعد از mktemp در میانهٔ tar با Ctrl+C قطع می‌شه. چه تضمینی می‌ده trap خروج؟

A script is interrupted with Ctrl+C after mktemp, during tar. What does an EXIT cleanup trap guarantee?

پاسخSolution

برای خروج‌های معمولی و signalهای مدیریت‌شده، فرصت اجرای cleanup می‌ده تا فایل موقت همون اجرا حذف بشه. در قطع برق، kill -9 یا خرابی سیستم‌عامل تضمین نمی‌ده؛ trap هم نسخهٔ پشتیبان ناقص رو معتبر نمی‌کنه.

For normal exits and handled signals, it gives cleanup a chance to remove this run’s temporary file. It cannot guarantee cleanup after power loss, SIGKILL, or OS failure, and it does not make an incomplete backup valid.

۱۰. مسیر مقصد کجاست؟10. Where should the destination go?

پوشهٔ مقصد رو زیر پوشهٔ منبع گذاشته‌ای و هر اجرا خروجی قبلی رو هم آرشیو می‌کنه. ریشهٔ مشکل کجاست؟

You put the destination under the source, so every run archives the previous output too. What is the root cause?

پاسخSolution

مرز مبدأ/destination اشتباه تعریف شده هست؛ مقصد باید بیرون منبع باشه یا از archive exclude بشه. در ابزار آموزشی ردکردن مقصد تودرتو ساده‌تر و امن‌تر هست؛ بعد دوباره محتوای آرشیو رو فهرست کن.

The source/destination boundary is wrong. Move the destination outside the source or explicitly exclude it. For this teaching tool, rejecting nested destinations is simpler and safer; then list the archive again.

۱۱. چرا فایل موقت در مقصد؟11. Why create the temporary file in the destination?

فایل موقت رو در /tmp ساخته‌ای و بعد به mount مقصد منتقل می‌کنی. چه چیزی دربارهٔ rename عوض می‌شه؟

You create the temporary file in /tmp, then move it to the destination mount. What changes about the rename?

پاسخSolution

اگه دو مسیر روی filesystemهای جدا باشن، rename اتمی ممکن نیست و mv ممکنه copy سپس delete کنه. فایل موقت در filesystem مقصد احتمال rename اتمی رو بالا می‌بره، اما تضمین دوام روی همهٔ storageها نمی‌ده.

Across filesystems, an atomic rename is unavailable and mv may copy then delete. Creating the temporary file on the destination filesystem enables an atomic rename in common cases, but does not guarantee durability for every storage system.

۱۲. ShellCheck می‌گه SC208612. ShellCheck reports SC2086

هشدار روی rm $tmp آمده و مسیر موقت احتمالاً فاصله نداره. چرا باز هم باید اصلاح بشه؟

The warning points to rm $tmp, and the temporary path probably has no spaces. Why fix it anyway?

پاسخSolution

فرض «احتمالاً فاصله نداره» با تغییر مسیر یا محیط می‌شکنه. rm -- "$tmp" جلوی word splitting و glob expansion رو می‌گیره و -- مسیرهایی رو که با خط تیره شروع می‌شن امن‌تر می‌کنه؛ باز هم scope متغیر رو درست تعیین کن.

The assumption “probably no spaces” breaks when paths or environments change. rm -- "$tmp" prevents splitting/globbing and uses -- for dash-leading paths; the variable’s scope must still be correct.

۱۳. archive خوانده شد؛ آیا نسخهٔ پشتیبان ثابت شد؟13. The archive lists; is the backup proven?

tar -tzf backup.tar.gz بدون خطا تمام شد. چه چیزهایی هنوز ثابت نشده؟

tar -tzf backup.tar.gz completed successfully. What is still unproven?

پاسخSolution

فهرست‌خوانی نشون می‌ده آرشیو قابل خواندن و ساختار index اون قابل پیمایش هست؛ سازگاری تصویر لحظه‌ای، صحت معنایی فایل‌ها، مجوزها در محیط مقصد و restore عملی ثابت نشده. به یک مسیر جدا restore و محتوا رو بررسی کن.

Listing shows the archive is readable and its index can be traversed. Snapshot consistency, semantic correctness, destination permissions, and a real restore remain unproven. Extract into a separate path and inspect it.

۱۴. چرا for f in $(find ...) خطرناک هست؟14. Why is for f in $(find ...) unsafe?

یک نام فایل notes from friday.txt هست. این حلقه چند عضو می‌بینه و چه الگویی بهتره؟

A filename is notes from friday.txt. How many items does the loop see, and what is safer?

پاسخSolution

احتمالاً سه کلمه می‌بینه؛ newline داخل نام هم می‌تونه خروجی substitution رو مبهم کنه. در Bash از find -print0 با read -r -d '' استفاده کن یا اصلاً درخت رو به ابزار مناسب بسپار و نام‌ها رو parse نکن.

It likely sees three words, and newlines in filenames make command-substitution output ambiguous too. In Bash, use find -print0 with read -r -d '', or pass the tree to an appropriate tool rather than parsing names.

۱۵. set -u چه چیزی رو می‌گیره؟15. What does set -u catch?

اسکریپت به‌جای $destination اشتباهاً $destnation رو نوشته هست. این گزینه چه کمکی می‌کنه و چه چیزی رو تشخیص نمی‌ده؟

A script accidentally uses $destnation instead of $destination. How does this option help, and what does it not detect?

پاسخSolution

اگه متغیر تعریف نشده باشه، set -u معمولاً گسترش اون رو خطا می‌کنه. typoیی که به متغیر تعریف‌شدهٔ دیگری برسه، اشتباه منطقی یا مقدار نامعتبر رو لزوماً تشخیص نمی‌ده؛ اعتبارسنجی همچنان لازمه.

If the variable is unset, set -u normally makes expansion an error. A typo that names another set variable, a logical mistake, or an invalid value may still pass; validation remains necessary.

۱۶. تکرارپذیری اجرای بعدی16. Make the next run repeatable

اسکریپت هر بار backups/latest.tar.gz رو overwrite می‌کنه. چه خطر و چه بهبود ساده‌ای پیشنهاد می‌دی؟

The script overwrites backups/latest.tar.gz on every run. What is the risk, and what simple improvement would you make?

پاسخSolution

خرابی اجرای تازه نسخهٔ سالم قبلی رو می‌پوشاند. نام یکتا بر پایهٔ زمان یا شناسه بساز، ابتدا در فایل موقت تولید و بررسی نهایی کن، سپس منتشر کن؛ نگهداری نسخه‌ها رو جدا و با سیاست معلوم انجام بده، نه پاک‌سازی تصادفی.

A failed new run can replace a known-good copy. Use a unique time/identifier, build and verify a temporary archive first, then publish it; manage retention as a separate explicit policy, not random cleanup.

۱۷. خروجی log کجا بره؟17. Where should logs go?

می‌خوای stdout برای نام فایل آرشیو قابل pipeکردن بمونه و پیام‌های شروع/خطا برای کاربر دیده بشه. تابع log رو به کدوم stream می‌فرستی؟

You want stdout to remain pipeable as an archive filename while start/error messages remain visible. Which stream should log use?

پاسخSolution

پیام‌های انسانی رو روی stderr بفرست؛ دادهٔ ماشینی رو روی stdout نگه دار. اگه هر دو رو قاطی کنی، فراخواننده نمی‌داند کدوم خط داده و کدوم تشخیص هست.

Send human diagnostics to stderr and keep machine-readable data on stdout. If mixed, a caller cannot tell data from diagnostics.

۱۸. بلیت خرابی18. Incident ticket

زمان‌بند می‌گه اسکریپت موفق بود، اما archive غایب یا صفر بایت هست. سه بررسی اولت چیست و بعد از اصلاح چه مدرکی جمع می‌کنی؟

A scheduler says the script succeeded, but the archive is missing or empty. What are your first three checks, and what evidence do you collect after repair?

راهنماHint

به وضعیت واقعی pipeline، stream خطا و مجوز/مسیر مقصد نگاه کن.

Check the real pipeline status, error stream, and destination path/permissions.

پاسخSolution

اول دستور line و آرگومان‌هایی که زمان‌بند اجرا کرده، دوم exit وضعیت و stderr، سوم مسیر/مالکیت/فضای مقصد رو بررسی کن. بعد pipeline رو با pipefail یا بررسی صریح وضعیت اصلاح، فایل رو در محل موقت بساز، tar -tzf اجرا و آرشیو رو در پوشه‌ای جدا restore کن. وضعیت صفر، log زمان‌دار و محتوای restoreشده رو با هم نگه دار؛ هیچ‌کدوم به‌تنهایی سلامت کامل نسخهٔ پشتیبان رو ثابت نمی‌کنه.

First inspect the exact command and arguments used by the scheduler, then exit status and stderr, then destination path/ownership/free space. Fix status propagation with pipefail or explicit checks; build to a temporary path, run tar -tzf, and restore to a separate directory. Keep the zero status, timestamped log, and restored contents together; no single item proves a complete backup by itself.

The script can now perform a repeated task with explicit inputs and failures. But if a service does not answer from outside, we still do not know how far the packet got. Next we will trace the path with ip, routes, and DNS—starting at the host instead of guessing about the application.
