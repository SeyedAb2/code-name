پردازه و سرویس (systemd)Processes and services (systemd)

برنامه را دستی اجرا می‌کنی، جواب می‌دهد؛ سیستم را reboot می‌کنی، دیگر خبری از آن نیست. یعنی برنامه خراب است؟ شاید نه. شاید فقط چیزی که در ترمینال زنده نگهش می‌داشت دیگر وجود ندارد. بیایید ردش را از پردازه تا systemd دنبال کنیم.

You run the application manually and it responds; after a reboot, it is gone. Is the application broken? Maybe not. Perhaps the terminal that kept it alive no longer exists. Let us follow it from process to systemd.

برنامه روی دیسک است؛ پردازه در حال اجراستA program is on disk; a process is running

فایل اجرایی خودش سرویس نیست. وقتی سیستم آن را اجرا می‌کند، پردازه‌ای با PID، کاربر، وضعیت و والد ساخته می‌شود. اگر برنامه را در foreground اجرا کنی، ترمینال منتظر می‌ماند و خروجی را می‌بینی؛ با Ctrl+C معمولاً SIGINT به پردازهٔ foreground می‌رسد.

An executable file is not itself a service. When the system runs it, a process appears with a PID, user, state, and parent. In the foreground, the terminal waits and shows output; Ctrl+C usually sends SIGINT to the foreground process.

a quick foreground process
python3 -m http.server 8787 --bind 127.0.0.1
Serving HTTP on 127.0.0.1 port 8787 ...
^C

تا وقتی فرمان در حال اجراست، shell prompt برنمی‌گردد. این آزمایش نشان می‌دهد پردازه در foreground زنده است؛ اما نه خودکار بعد از خروج shell می‌ماند، نه بعد از reboot بالا می‌آید. برای دیدن پردازه‌ها از ps استفاده کن؛ PID را در context خودش بخوان.

While the command runs, the shell prompt does not return. This proves that the process is alive in the foreground; it does not keep the process running after the shell exits or start it after reboot. Use ps to inspect processes, and interpret a PID in context.

inspect processes
ps -eo pid,ppid,user,stat,cmd
  PID  PPID USER  STAT CMD
  ...   ... sara  S+   python3 -m http.server 8787 ...
pgrep -af 'http.server 8787'

PID پردازه است؛ PPID والد آن. مقدارهای نمونه متغیرند. pgrep -af برای پیدا کردن سریع نام/فرمان مناسب است، اما اگر چند پردازه هم‌نام باشند باید خط کامل، کاربر و والد را هم بررسی کنی.

PID identifies the process; PPID its parent. Sample values vary. pgrep -af is useful for a quick name/command search, but with multiple matches, inspect the full command, user, and parent too.

kill اسمش ترسناک‌تر از کارش استThe name kill sounds harsher than its default action

برای متوقف‌کردن پردازه، kill PID به‌طور پیش‌فرض SIGTERM می‌فرستد: درخواست محترمانه برای پایان. برنامه می‌تواند آن را بگیرد و تمیزکاری کند؛ ممکن است هم نادیده بگیرد. فقط اگر پردازه پاسخ نداد و دلیل داری، SIGKILL را به‌عنوان آخرین راه در نظر بگیر. عدد PID را از خروجی تازه پیدا کن؛ PID قدیمی ممکن است دوباره به پردازه‌ای دیگر برسد.

By default, kill PID sends SIGTERM: a request to exit cleanly. The process may handle it and clean up, or ignore it. Consider SIGKILL only as a last resort when the process does not respond and you have a reason. Get the PID from fresh evidence; an old PID may later belong to another process.

به PID حدس‌زده‌شده signal نزنDo not signal a guessed PID

پیش از kill دوباره ps یا pgrep را ببین و فرمان/کاربر را تطبیق بده. kill -9 را راه‌حل عادی فرض نکن؛ پاک‌سازی برنامه اجرا نمی‌شود.

Before signalling, refresh ps or pgrep and verify the command and user. Do not treat kill -9 as routine; the program gets no chance to clean up.

می‌توانی فرمانی را با & در پس‌زمینهٔ shell بگذاری، اما این با سرویس فرق دارد: خروج از shell، قطع SSH، یا reboot می‌تواند رابطه را تغییر دهد. job control ابزار همان نشست تعاملی است؛ systemd مدیر عمر سرویس در سطح سیستم است.

You can put a command in the shell background with &, but that is not the same as a service: shell exit, SSH disconnect, or reboot can change its lifetime. Job control belongs to an interactive session; systemd manages service lifetimes at system level.

systemd چه چیزی را به عهده می‌گیرد؟What does systemd take responsibility for?

در توزیع‌هایی که systemd مدیر سرویس است، یک unit توصیف می‌کند چه چیزی باید شروع شود و با چه وابستگی/تنظیمی. نوع‌های مختلف unit وجود دارد؛ اینجا روی .service می‌مانیم. systemd پردازه را شروع می‌کند، وضعیتش را نگه می‌دارد، در صورت درخواست راه‌اندازی مجدد می‌کند و خروجی را به journal می‌فرستد.

On distributions where systemd is the service manager, a unit describes what should start and with which settings/dependencies. There are many unit types; here we focus on .service. systemd starts the process, tracks its state, restarts it when configured, and sends its output to the journal.

systemd پردازهٔ اصلی را شروع و پایش می‌کند. فلش‌ها شروع پردازه و استفادهٔ برنامه از فرزند/منبع را نشان می‌دهند؛ systemd جایگزین منطق داخلی برنامه نیست.

systemd starts and tracks the main process. Arrows represent process start and the application’s use of children/resources; systemd does not replace the application’s own logic.

سه بخش unit معمولاً چنین نقشی دارند: [Unit] توضیح و وابستگی‌ها؛ [Service] کار واقعی مثل ExecStart، کاربر و restart؛ [Install] اتصال برای enable شدن. همهٔ unitها مجبور نیستند هر سه بخش را داشته باشند. قالب دقیق و گزینه‌های موجود به نسخهٔ systemd وابسته است.

The three unit sections commonly serve these roles: [Unit] description and dependencies; [Service] the actual work such as ExecStart, user, and restart behavior; [Install] the relationship used for enabling. Not every unit needs all three sections. Exact syntax and available options depend on systemd version.

چرا فرمانی که دستی کار می‌کند اینجا می‌شکند؟Why can a command that works manually fail here?

ترمینال تو cwd، PATH، متغیرهای محیطی و shell خودت را دارد. system service با محیط محدودتر و کاربر/دایرکتوری‌ای که تو تعیین می‌کنی اجرا می‌شود. به همین خاطر در unit مسیر اجرایی و WorkingDirectory را صریح بنویس؛ به alias، فعال‌سازی مجازی shell یا PATH تعاملی تکیه نکن.

Your terminal has your cwd, PATH, environment variables, and shell. A system service runs with a more limited environment and the user/directory you specify. That is why a unit should name the executable and WorkingDirectory explicitly; do not depend on aliases, shell activation, or interactive PATH.

یک سرویس کوچک در VM یک‌بارمصرف می‌سازیم. Python با ماژول استانداردش روی loopback گوش می‌دهد؛ پورت عمومی باز نمی‌کنیم. پوشه و فایل را طوری می‌سازیم که کاربر www-data بتواند بخواند. اگر این حساب در توزیع تو نیست، حساب سرویس مناسب همان سیستم را انتخاب کن.

We will make a small service in a disposable VM. Python’s standard module listens on loopback; we do not open a public port. Set up the directory and file so www-data can read them. If that account does not exist on your distribution, choose an appropriate service account for that system.

disposable Ubuntu VM
sudo mkdir -p /opt/codenames-demo
printf 'systemd lab is alive\n' | sudo tee /opt/codenames-demo/index.html
sudo chown -R root:root /opt/codenames-demo
sudo chmod 0755 /opt/codenames-demo
sudo chmod 0644 /opt/codenames-demo/index.html
python3 -m http.server 8787 --directory /opt/codenames-demo --bind 127.0.0.1

این فرمان دستی باید با درخواست محلی جواب بدهد. در نشست دیگری، curl -i http://127.0.0.1:8787/ را اجرا کن و body را ببین. این پاسخ فقط می‌گوید server فعلی reachable است؛ هنوز systemd، reboot یا کاربر محدود را آزمایش نکرده‌ایم. بعد به ترمینال اول برگرد و با Ctrl+C همین پردازهٔ دستی را متوقف کن؛ اگر رهایش کنی، سرویس جدید برای همان پورت bind نمی‌شود.

The manual command should answer a local request. In another session, run curl -i http://127.0.0.1:8787/ and inspect the body. This response only proves the current server is reachable; we have not tested systemd, reboot, or the restricted service user yet. Return to the first terminal and press Ctrl+C to stop this manual process; otherwise the new service cannot bind the same port.

unit را به systemd معرفی کنIntroduce the unit to systemd

حالا همان برنامه را از نشست SSH جدا می‌کنیم. فایل unit سیستمی را با sudoedit در مسیر /etc/systemd/system/codenames-demo.service بساز. این فایل باید خودش root-owned باشد؛ برای اجرای برنامه، User=www-data اختیار پردازه را محدود می‌کند.

Now detach the application from the SSH session. Create a system unit with sudoedit at /etc/systemd/system/codenames-demo.service. The unit file itself should be root-owned; User=www-data limits the process identity.

codenames-demo.service
[Unit]
Description=CodeNames local demo web service
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/opt/codenames-demo
ExecStart=/usr/bin/python3 -m http.server 8787 --directory /opt/codenames-demo --bind 127.0.0.1
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target

systemd برنامه را مثل shell از روی رشتهٔ command اجرا نمی‌کند؛ ExecStart را به executable و آرگومان‌ها می‌شکند. پس shell expansion، redirect و pipe را بی‌واسطه ننویس. برای تنظیم محیط از Environment=KEY=value یا فایل محیطی با احتیاط استفاده کن؛ systemd unit محیط shell کامل تو را به ارث نمی‌برد.

systemd does not run ExecStart as a shell command string; it parses an executable and its arguments. Do not assume shell expansion, redirection, or pipes. Set environment with Environment=KEY=value or a carefully managed environment file; a unit does not inherit your full shell environment.

پس از ذخیرهٔ فایل، systemd باید تعریف تازه را دوباره بخواند. daemon-reload فایل unit را بازخوانی می‌کند؛ خودش سرویس را شروع نمی‌کند. بعد start اجرای همین لحظه را درخواست می‌کند. enable اتصال لازم برای شروع خودکار در boot را می‌سازد؛ enable و start دو کار جدا هستند.

After saving, systemd must reload the new unit definition. daemon-reload rereads unit files; it does not start the service. start requests a start now. enable creates the relationship for starting during boot; enabling and starting are separate actions.

load, start, enable, verify
sudo systemctl daemon-reload
sudo systemctl enable --now codenames-demo.service
systemctl is-enabled codenames-demo.service
enabled
systemctl is-active codenames-demo.service
active

خروجی enabled دربارهٔ راه‌اندازی هنگام boot است؛ active دربارهٔ وضعیت فعلی. هیچ‌کدام به‌تنهایی ثابت نمی‌کند HTTP endpoint پاسخ درست می‌دهد. همان curl را دوباره بزن و بعد status را با شاهد برنامه‌ای کنار هم بگذار.

“enabled” concerns boot activation; “active” concerns the current state. Neither alone proves that the HTTP endpoint returns the right response. Repeat the same curl and combine application-level evidence with unit status.

status خلاصه می‌دهد؛ journal جزئیاتstatus summarizes; the journal gives detail

وقتی systemctl می‌گوید failed، هنوز علت را نداری. status وضعیت unit، PID اصلی، زمان آخرین تلاش و چند خط log را کنار هم می‌گذارد. journalctl -u تاریخچهٔ همان unit را می‌دهد. دنبال خطا و exit status بگرد و ساعتش را با زمان تلاش خودت تطبیق بده.

When systemctl says failed, you do not yet have the cause. status summarizes unit state, main PID, last attempt, and some log lines. journalctl -u shows that unit’s history. Look for the error and exit status, and match their timestamps to your attempt.

systemd وضعیت اجرای unit را دنبال می‌کند. پیکان برگشت به retry فقط وقتی معنا دارد که سیاست restart اجازه دهد و محدودیت start rate جلوی تلاش‌های پی‌درپی را نگرفته باشد.

systemd tracks the unit’s execution state. The retry arrow applies only when restart policy allows it and start-rate limiting has not suppressed repeated attempts.

collect service evidence
systemctl status codenames-demo.service --no-pager
journalctl -u codenames-demo.service -n 30 --no-pager
curl -i http://127.0.0.1:8787/

اگر status active است ولی curl شکست می‌خورد، احتمالاً فقط فرایند را اثبات کرده‌ای، نه آماده‌بودن برنامه یا درستی bind/port را. اگر curl جواب می‌دهد اما status برای unit دیگری را می‌خوانی، شناسهٔ unit را دوباره کنترل کن. هر ابزار به یک سؤال جواب می‌دهد.

If status is active but curl fails, you have likely proved only the process state—not application readiness or the correct bind/port. If curl works but status refers to another unit, verify the unit name. Each tool answers a different question.

خرابی عمدی: دستی جواب می‌دهد، unit شکست می‌خوردDeliberate failure: manual run works, the unit fails

حالا در unit، WorkingDirectory را عمداً به مسیر ناموجود /opt/codenames-demo-missing تغییر بده، فایل را ذخیره کن، daemon-reload و restart بزن. هنوز fix نکن؛ اول ببین systemd چه چیزی ثبت کرده است.

Now deliberately change WorkingDirectory to the nonexistent /opt/codenames-demo-missing, save, run daemon-reload, and restart. Do not fix it yet; first inspect what systemd recorded.

read the failed attempt
sudo systemctl daemon-reload
sudo systemctl restart codenames-demo.service
systemctl status codenames-demo.service --no-pager
... Failed to change to the requested working directory ...
... status=200/CHDIR ...
journalctl -u codenames-demo.service -n 20 --no-pager

عبارت CHDIR سرنخ است: قبل از اجرای Python، تغییر cwd شکست خورده. پس نصب Python یا HTTP پاسخ‌گو هنوز مظنون اصلی نیست. مسیر را با ls -ld بررسی کن، مقدار را به /opt/codenames-demo برگردان، reload و restart کن، سپس status و curl را دوباره تکرار کن. متن دقیق status به نسخهٔ systemd فرق می‌کند؛ علت اصلی در journal مشخص‌تر می‌شود.

The CHDIR clue means changing cwd failed before Python ran. Python installation or HTTP behavior is not yet the leading suspect. Check the path with ls -ld, restore /opt/codenames-demo, reload and restart, then repeat status and curl. Exact status wording varies by systemd version; the journal usually gives the clearest cause.

اگر این مسیر درست بود ولی شروع باز هم شکست می‌خورد، نوبت بررسی executable مطلق /usr/bin/python3، کاربر و مجوز دسترسی به فایل/والدهاست. یک خطای اجرایی دیگر ممکن است 203/EXEC باشد، اما قبل از تفسیر عدد، journal و مسیر واقعی را بخوان.

If the directory is correct but startup still fails, check the absolute executable /usr/bin/python3, the service user, and access to the file and its parents. Another execution failure may appear as 203/EXEC, but read the journal and verify the real path before interpreting the code.

restart policy کمک می‌کند؛ علت را درمان نمی‌کندRestart policy helps, but does not cure the cause

در unit lab، Restart=on-failure یعنی پس از خروج ناموفق، systemd می‌تواند دوباره تلاش کند. RestartSec=3 فاصلهٔ تلاش بعدی را تعیین می‌کند. خطای پیکربندیِ پایدار ممکن است چرخهٔ شکست/تلاش بسازد؛ status و journal را ببین و اگر لازم شد unit را stop کن تا علت را اصلاح کنی.

Restart=on-failure lets systemd retry after an unsuccessful exit. RestartSec=3 sets a delay before another attempt. A persistent configuration error can create repeated failure/retry cycles; inspect status and journal, and stop the unit if needed so you can repair the cause.

systemd رفتار restart و محدودیت rate را طبق نسخه و تنظیمات مدیر اعمال می‌کند؛ پس از تلاش‌های زیاد ممکن است unit به حالت failed برسد و دیگر خودکار تلاش نکند تا reset/restart شود. restart policy جای health check برنامه یا عیب‌یابی را نمی‌گیرد و «active» هم معادل آماده‌بودن HTTP نیست.

systemd applies restart and rate-limit behavior according to its version and manager settings; after repeated attempts a unit may be marked failed and stop retrying until reset/restarted. Restart policy is not an application health check, and “active” does not mean HTTP is ready.

آزمایشگاه: سرویسی که بعد از reboot برمی‌گرددLab: a service that returns after reboot

در VM یک‌بارمصرف، سرویس loopback را با کاربر محدود اجرا کن، آن را enable کن، و با سه شاهد مستقل نتیجه بگیر: unit فعال است، PID متعلق به کاربر موردنظر است، و HTTP پاسخ درست می‌دهد. سپس WorkingDirectory را خراب کن، از status/journal علت را پیدا کن، repair کن و همان سه شاهد را دوباره بگیر.

In a disposable VM, run the loopback service as a restricted user, enable it, and verify with three independent signals: the unit is active, the PID belongs to the intended user, and HTTP returns the expected response. Then break WorkingDirectory, diagnose with status/journal, repair it, and collect the same three signals again.

اگر VM آزمایشی واقعاً از systemd boot می‌شود، reboot را امتحان و بعد همان سه شاهد را جمع کن. اگر محیطت container یا WSL است و systemd PID 1 فعال نیست، reboot را شبیه‌سازی نکن؛ lab را در VM Ubuntu واقعی انجام بده. موفقیت دستورات systemctl در یک نشست، به‌تنهایی تضمین boot بعدی نیست.

If your disposable VM truly boots with systemd, reboot and collect the same three signals. If your environment is a container or WSL without systemd as PID 1, do not pretend to simulate reboot; use a real Ubuntu VM. Successful systemctl commands in one session alone do not guarantee the next boot.

در پایان، ابتدا سرویس را disable و stop کن، فایل unit را حذف کن و daemon-reload بزن؛ بعد فقط پوشه‌ای را پاک کن که همین lab ساخته است. حساب www-data سیستمی است و نباید حذف شود.

At the end, disable and stop the service, remove its unit file, and run daemon-reload; then remove only the directory created by this lab. www-data is a system account and must not be deleted.

targeted lab cleanup
sudo systemctl disable --now codenames-demo.service
sudo rm /etc/systemd/system/codenames-demo.service
sudo systemctl daemon-reload
sudo rm -f /opt/codenames-demo/index.html
sudo rmdir /opt/codenames-demo

تمرین‌ها؛ پردازه را از سرویس جدا کنExercises: distinguish a process from a service

۱. برنامه یا پردازه؟1. Program or process?

فایل اجرایی روی دیسک هست ولی ps چیزی نشان نمی‌دهد. چه می‌فهمی؟

The executable exists on disk but ps shows no matching process. What can you conclude?

پاسخSolution

فایل برنامه وجود دارد، اما در لحظهٔ بررسی پردازهٔ منطبق پیدا نشده. ممکن است خروج کرده، با نام دیگری اجرا شده یا جست‌وجو محدود بوده باشد.

The program file exists, but no matching process was found at that moment. It may have exited, run under another name, or fallen outside the search.

۲. PPID چه می‌گوید؟2. What does PPID tell you?

در خروجی ps یک پردازه PID و PPID دارد. PPID دربارهٔ چه رابطه‌ای شاهد می‌دهد؟

A process listing shows PID and PPID. What relationship does PPID describe?

پاسخSolution

شناسهٔ پردازهٔ والد را نشان می‌دهد؛ به درک زنجیرهٔ اجرا کمک می‌کند، اما به‌تنهایی نمی‌گوید چرا برنامه متوقف شده یا چه کسی آن را مدیریت می‌کند.

It identifies the parent process and helps reconstruct the launch chain, but alone does not explain why the process stopped or who manages it.

۳. پس‌زمینهٔ shell3. Shell backgrounding

چرا افزودن & راه مطمئنی برای ماندن سرویس بعد از قطع SSH نیست؟

Why is appending & not a reliable way to keep a service alive after SSH disconnects?

پاسخSolution

این فقط job همان shell را پس‌زمینه می‌کند؛ مدیریت boot، restart و خروجی پایدار service manager را فراهم نمی‌کند.

It backgrounds a job in that shell; it provides no service-manager handling for boot, restarts, or persistent output.

۴. سیگنال پیش‌فرض4. Default signal

فرمان kill 4321 به‌طور معمول چه می‌فرستد؟ آیا یعنی فوراً و بدون cleanup کشته می‌شود؟

What does kill 4321 normally send? Does that mean immediate termination without cleanup?

پاسخSolution

SIGTERM؛ درخواست پایان است و برنامه می‌تواند آن را مدیریت کند. اول PID/فرمان را تازه تأیید کن و برای پاک‌سازی فرصت بده.

SIGTERM, a termination request the program can handle. Verify the PID/command from fresh evidence and allow time for cleanup.

۵. start یا enable؟5. Start or enable?

سرویس را همین حالا می‌خواهی اجرا کنی و در boot بعدی هم بالا بیاید. چه لازم است؟

You want a service running now and after the next boot. What do you need?

پاسخSolution

start برای همین لحظه و enable برای اتصال boot؛ enable --now هر دو را درخواست می‌کند. وضعیت هر دو را جدا بررسی کن.

start for now and enable for boot; enable --now requests both. Verify each state separately.

۶. تغییر unit6. Editing a unit

فایل unit را تغییر دادی ولی restart همان تعریف قدیمی را می‌بیند. کدام مرحله جا افتاده؟

You edited a unit file, but restart seems to use the old definition. What step is missing?

پاسخSolution

systemctl daemon-reload تا manager فایل‌های unit را دوباره بخواند؛ بعد restart. daemon-reload خودش برنامه را restart نمی‌کند.

Run systemctl daemon-reload so the manager rereads unit files, then restart. daemon-reload does not itself restart the application.

۷. active اما پاسخ‌گو نیست7. Active but not responding

unit active است اما curl به پورت مورد انتظار وصل نمی‌شود. چه چیز هنوز ثابت نشده؟

The unit is active, but curl cannot connect to the expected port. What remains unproven?

پاسخSolution

وضعیت active فقط وضعیت unit را می‌گوید، نه آماده‌بودن/درستی bind برنامه. فرمان اجرا، journal، پورت و مسیر درخواست را بررسی کن.

Active reports unit state, not application readiness or correct binding. Inspect the command, journal, port, and request path.

۸. ExecStart بدون shell8. ExecStart is not a shell

چرا ExecStart=echo hi > /tmp/x معمولاً فایل redirect نمی‌سازد؟

Why does ExecStart=echo hi > /tmp/x not usually create a redirected file?

پاسخSolution

systemd shell را خودکار اجرا نمی‌کند؛ redirect عملگر shell است و ممکن است به‌عنوان آرگومان برداشت شود. اگر واقعاً لازم است، shell را صریح اجرا کن یا log را به سازوکار مناسب بده.

systemd does not automatically invoke a shell; redirection is a shell operator and may be treated as an argument. If truly needed, invoke a shell explicitly or use the appropriate logging mechanism.

۹. WorkingDirectory9. WorkingDirectory

برنامه دستی relative file می‌خواند، ولی در unit آن را پیدا نمی‌کند. کدام دو نشانه را بررسی می‌کنی؟

A manually run app reads a relative file, but under the unit it cannot find it. Which two clues do you inspect?

پاسخSolution

WorkingDirectory و journal؛ system service لزوماً cwd ترمینال را ندارد. مسیر مطلق یا cwd صریح را انتخاب کن.

Check WorkingDirectory and the journal; a system service does not inherit the terminal’s cwd. Use an absolute path or an explicit working directory.

۱۰. هویت سرویس10. Service identity

چرا برای web service معمولاً User=www-data را می‌گذاری، نه اجرای برنامه با root؟

Why would a web service commonly use User=www-data instead of root?

پاسخSolution

حد اختیارات پردازه را کم می‌کند؛ اما فایل‌ها باید برای آن حساب خواندنی و مسیرها قابل عبور باشند. تنظیم User به‌تنهایی مالکیت را repair نمی‌کند.

It reduces the process’s authority, but files must be readable and paths traversable by that account. Setting User does not repair ownership by itself.

۱۱. Restart=on-failure11. Restart=on-failure

برنامه با exit موفق تمام می‌شود. آیا on-failure الزاماً آن را برمی‌گرداند؟

The process exits successfully. Does on-failure necessarily bring it back?

پاسخSolution

خیر؛ سیاست برای پایان ناموفق است و معنای پایان موفق/ناموفق با نوع سرویس و تنظیمات systemd سنجیده می‌شود. مستندات نسخهٔ میزبان را ببین.

No; the policy targets unsuccessful termination, interpreted with service type and systemd settings. Check the host version’s documentation.

۱۲. وضعیت failed12. Failed state

پس از چند شروع ناموفق، systemd دیگر تلاش نکرده. قبل از دست‌کاری rate limit چه جمع می‌کنی؟

After repeated failed starts, systemd stopped retrying. What evidence do you collect before changing rate limits?

پاسخSolution

status، journal، علت exit، زمان تلاش، executable و config را بررسی کن. اگر علت پایدار است، بازکردن rate limit فقط تلاش‌های بیشتری از همان شکست می‌سازد.

Inspect status, journal, exit cause, attempt times, executable, and configuration. If the cause persists, relaxing rate limits merely repeats the same failure.

۱۳. CHDIR یا EXEC؟13. CHDIR or EXEC?

journal می‌گوید تغییر WorkingDirectory شکست خورده. آیا اول PATH برنامه را عوض می‌کنی؟

The journal says changing WorkingDirectory failed. Would you change the executable path first?

پاسخSolution

نه؛ سرنخ نشان می‌دهد شکست پیش از اجرا و در chdir است. وجود مسیر و مجوز والد را بررسی کن؛ بعد سراغ executable برو اگر خطای تازه آن را نشان داد.

No; the clue indicates failure during chdir before execution. Check the directory and parent permissions; inspect the executable only if later evidence points there.

۱۴. PID قدیمی14. A stale PID

یادداشت قدیمی PID=4321 دارد. چرا نباید همان را کورکورانه kill کنی؟

An old note says PID=4321. Why should you not blindly kill it?

پاسخSolution

PIDها reuse می‌شوند. با ps/pgrep تازه، command line و user را تطبیق بده؛ نام مشابه هم ممکن است چند match داشته باشد.

PIDs are reused. Refresh with ps/pgrep and verify command line and user; similar names may have multiple matches.

۱۵. enable اما inactive15. Enabled but inactive

is-enabled می‌گوید enabled ولی is-active inactive. تناقض است؟

is-enabled says enabled while is-active says inactive. Is that contradictory?

پاسخSolution

نه؛ enable تنظیم boot است و start وضعیت جاری. سرویس می‌تواند برای boot فعال باشد ولی هنوز start نشده یا متوقف شده باشد.

No. Enablement configures boot behavior; start controls current state. A service can be enabled for boot but not yet started or currently stopped.

۱۶. environment متفاوت16. A different environment

برنامه در shell به‌خاطر PATH کار می‌کند اما unit می‌گوید executable پیدا نشد. Repair کم‌ابهام چیست؟

The shell finds the app through PATH, but the unit cannot. What is the least ambiguous repair?

پاسخSolution

مسیر مطلق executable را پیدا و در ExecStart ثبت کن، سپس daemon-reload و restart. محیط تعاملی خودت را به سرویس نسبت نده.

Find the absolute executable path and use it in ExecStart, then daemon-reload and restart. Do not assume the service shares your interactive environment.

۱۷. چه چیزی فعال‌بودن ثابت نمی‌کند؟17. What active does not prove

systemctl active است. سه بررسی مستقل برای یک HTTP service نام ببر.

systemctl says active. Name three independent checks for an HTTP service.

پاسخSolution

هویت/PID با ps یا status، خطاهای تازه با journalctl، و درخواست واقعی با curl. هیچ‌کدام به‌تنهایی همهٔ سلامت برنامه را تضمین نمی‌کنند.

Check PID/user with ps or status, recent errors with journalctl, and an actual request with curl. None alone guarantees overall application health.

۱۸. بلیت نهایی: فقط بعد از SSH کار می‌کند18. Final ticket: works only after SSH

یک web process دستی پاسخ می‌دهد اما پس از logout ناپدید می‌شود. مسیر تبدیلش به سرویس و شواهد موفقیت را مرحله‌به‌مرحله بنویس.

A manually started web process responds but disappears after logout. Outline how to turn it into a service and prove it works.

راهنماHint

مسیر مطلق، کاربر، cwd، unit file، reload، start/enable و یک درخواست واقعی را در نظر بگیر.

Think absolute path, user, cwd, unit file, reload, start/enable, and a real request.

پاسخSolution

در VM یک‌بارمصرف فایل unit با ExecStart مطلق، User محدود و WorkingDirectory معتبر بساز؛ daemon-reload، سپس enable --now. با status، ps، journal و curl بررسی کن. اگر شکست خورد، از خطای journal شروع کن؛ فعال‌بودن یا enable بودن را معادل پاسخ‌گویی ندان.

In a disposable VM, create a unit with an absolute ExecStart, restricted User, and valid WorkingDirectory; run daemon-reload, then enable --now. Verify with status, ps, journal, and curl. If it fails, start from the journal error; do not equate active/enabled with a responding app.

اگر executable اصلاً نصب نیست چه؟What if the executable is not installed?

تا اینجا فرض کردیم Python و ابزار لازم از قبل روی VM هستند. روی سرور واقعی، گاهی unit کاملاً درست است اما برنامه یا وابستگی‌اش نصب نیست یا از منبع نامناسب آمده. فصل بعد سراغ package و repository می‌رویم تا بفهمی نرم‌افزار از کجا می‌آید و چطور نسخه‌اش را بررسی کنی.

So far we assumed Python and the required tools already exist on the VM. On a real server, the unit may be correct while the application or dependency is missing or came from an unsuitable source. Next we will study packages and repositories to understand where software comes from and how to inspect its version.
